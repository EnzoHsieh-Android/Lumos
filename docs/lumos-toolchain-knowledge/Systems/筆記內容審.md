# 筆記內容審

白話:推送前,把這段範圍裡新寫、而且還留著的筆記行交給一位判定者(AI),一行一行問「這句只看程式碼就能確認嗎」。判成推得出來的要刪、改或申訴;判成脈絡的才算過。第一層([[Systems/筆記內容閘]])只擋形狀固定的兩種寫法,看意思的交給這一層。

- 程式在 `scripts/lumos` 的「筆記內容審」那一段(`_note_audit_*` 函式、`cmd_note_audit_*` 七個子指令(筆記內容審的 prepare、record、check、skip 四個,加回頭重讀的 reread-prepare、reread-record、reread-check 三個)、`cmd_decision_amend`、doctor 呼叫的 `_note_audit_doctor_lines`)。
- 設計、取捨、條款與三輪設計審:[[Projects/筆記內容審_計劃]]。
- 新筆記行怎麼從 git 抽出來(範圍、改名、合併提交、區塊、小標題、結構行、內容編號)是兩層共用的,家在 [[Systems/筆記內容閘]];這篇只管拿到那些行之後的事。
- 派工詞放在 `scripts/templates/note-audit-judge.md`,三個分類的定義逐字搬自 rtb 那次 68 句小實驗;改一個字就要照摘要那條 RULE 升版重跑。
- 操作順序(出清單 → 派判定者 → 記判定 → 刪改或申訴 → 提交判定檔 → 代碼審留痕 → 推)寫在 lumos-project-notes skill 的代碼審與推送那個子檔。

**★目前還沒接進推送前掛鉤與 CI★**:指令都能手動跑,但不會擋推送。接線條件是計劃的校準條款——兩家編排者各自四項都達標。

## 回頭重讀守檔筆記(reread 三個子指令,2026-10-01)

白話:改了程式、同一次也改了管那支程式的筆記,卻只在後面追加、前面的舊句沒回頭看——rtb 稽核 20 處真漂移裡最大的一類(9 處),而且名稱都還在,字面比對抓不到。推送前把「這次改到的程式檔的家、而且這次也被改過」的每篇筆記連同這次的程式 diff 交給判定者,問「哪幾行被這次改動弄得不成立了」。設計、條款、三輪設計審與實作紀錄:[[Projects/守檔筆記對照改動_計劃]]。程式在 `scripts/lumos` 的「回頭重讀守檔筆記」那一段(`cmd_note_audit_reread_*` 三個子指令與 `_note_reread_*`),派工詞範本是 `scripts/templates/note-audit-reread.md`。推送前掛鉤與 CI 呼叫 reread-check 的那一段歸 [[Systems/存量漂移守衛]] 管。

- **為什麼兩個指紋**(設計審 r1 到 r3):一個指紋同時當「判定者讀的是哪份材料」與「這篇對照過了沒」會互相打架。對照指紋只看程式那一半(筆記路徑、那篇頂端 about_code 每支檔的 blob、範本版本),給 reread-check 與紀錄檔名用——★不含範圍與 diff★:手動 prepare 與推送前 check 的起點算法不同(合過主線時一個走共用起點、一個走推送起點),含 diff 的話提醒永遠消不掉(r1 四席);★不含筆記自己的 blob★:作者照判定改了筆記,同一次推送再跑 check 不會馬上重列(r2 正確性席)。材料指紋再加上筆記 blob 與給判定者的 diff 全文,給項目檔名、報告的 `prepared:` 用:判定者還在跑時作者改筆記再 prepare,會得到新的一份、不蓋掉舊的(r3 兩席)。代價寫在計劃〈誠實界線〉:對照過一版程式之後,只要 about_code 列的檔都沒變,筆記後來新寫的句子不會被這道對照。
- **原本為什麼只提醒、後來為什麼轉擋**:第一版準度只在 rtb 驗過一次(15 個提交點出 26 行、真漂移 17、誤報 0),複判一致率約三分之二,所以只提醒、等兩週量準度。上線後的帳顯示提醒之後真的去判的很少(主線 18 次提醒、5 份紀錄),Enzo 2026-10-09 裁定不等量測、直接擋([[Projects/舊句兩道轉擋_計劃]]),準度改由那份計劃的 RETIRE-IF 上線後抽樣。判定不穩的影響靠「第二層只擋規則類條目」壓到最少:改掉比對字串就放行,不會因重判而循環。
REVISIT:2026-10-21 照計劃〈做法〉5 抽 30 行量準度(上線日晚於 2026-10-07 時跟著順延),結果寫進計劃、再決定轉擋或撤 [closed:2026-10-09 人裁轉擋,不等量測;準度改由 Projects/舊句兩道轉擋_計劃 的 RETIRE-IF 抽樣]
- **擋只在帶 `--gate` 時生效**(2026-10-09):只有推送前掛鉤帶;CI 與手動跑不帶,不論設定都照舊只印、回 0、記既有事件。這族開關第一次「設定寫 block 還要呼叫端帶旗標才擋」,是人裁「只在本機擋」的直接結果(CI 用整個 PR 的累計範圍重算,候選與指紋跟本機不同);較近的先例是 `bound-tests --advisory`、`doctor --ci` 由呼叫端旗標決定嚴格度。舊掛鉤搭新工具時(這台機器所有工作樹共用主工作目錄的掛鉤)reread-check 多印一句、`lumos enforcement` 把沒帶 `--gate` 的生效 pre-push 列為沒接上,不靜默失效。
- **兩層**:第一層是候選的對照指紋不在「已對照」集合;第二層是判定紀錄點出的規則類條目(`RULE:`、`★INVARIANT★`、帶測試綁定的摘要條目,標作廢的不算)比對字串還在、又沒有涵蓋那份紀錄指紋的 kind=reread 表態。第二層依筆記路徑讀頂端所有紀錄(不論來源核對,較保守;同一篇多份紀錄取聯集),不依指紋——筆記改名後舊路徑的紀錄不再適用,改名本身讓第一層要求重判。比對字串少於 6 字的列點不出任何行(判定者把行號點在空白行時,不會比中整篇)。條目讀法(`_reread_summary_entries`,含單行 summary)與規則類判斷(`_reread_rule_entry`)放這一段,存量漂移的 `drift ack --kind reread` 呼叫同兩支。
