# 派工鏡頭

派審查員時,鏡頭把相關筆記附在派工詞尾端。這篇管 `scripts/lumos` 裡派工鏡頭那一段(`dispatch-lens` 子命令與它的渲染、補選、快取函式):diff 模式從 impact 結果挑固定席、渲染合約行與外部事實行、改動碰到外部回應碼比對時從自由席補選碼表筆記、快取與 45 秒時間預算;設計審模式(`--spec`)共用同一支渲染,但不印外部事實行。

- 外部事實行的掃描全檔只有一支(`_external_fact_lines`),跟合約行掃描 `_contract_key_matches` 對稱。
- 外部碼比對的形狀字串與題目表八題共用,單一來源在題目表旁;題目那一半的現況見 [[Systems/棧別提問表態閘]]。
- 改動行由鏡頭自己跑 git diff 取得,過濾與正規化跟 pitfalls --diff 共用同一支函式;解析迴圈與 pitfalls 那段重複一份。
- 外部碼表補選、改動行的檔頭判斷、外部事實段的渲染、每篇內文的渲染各抽成獨立函式,不寫在鏡頭主函式與共用渲染函式裡:推送前的新增告警閘擋過兩次複雜度(渲染函式原本就是 12,內容一改就被當成新告警),抽出後渲染函式降到上限 10 以內、鏡頭主函式 34。

## 設計審的提交寫法與 spec-freeze(2026-10-14,[[Projects/派工鏡頭可指定目標repo_計劃]])

設計審的 `LUMOS-SPEC:` 多收 `<完整提交編號>:<計劃路徑>`:計劃常只在別的 git 工作樹裡,同一個 repo 的工作樹共用物件庫,lumos 在會談 repo 從物件庫讀那個提交裡的計劃,不去標記指到的任何目錄跑 git。這一行由 `lumos spec-freeze <計劃>` 在計劃所在的工作樹產生:用暫存 index 建一個不掛分支的提交;凍結快照在會談目錄用 `lumos spec-freeze <完整提交編號>:<路徑> --out governance/review-reports/<編號>/rN-snapshot.md` 從同一個提交寫出(計劃在會談目錄時一次帶 `--out` 即可),所以快照與提交一定一致。完全不同的 repo 照舊不支援。

- WHY:提交寫法只收 40 或 64 碼、解出的完整編號要等於輸入 [出處:[[Projects/派工鏡頭可指定目標repo_計劃]] 設計審 r3 兩席實測] [因:git 對不足完整長度的字串先當 ref 名解析,同名分支會搶走;縮寫也會隨提交增加變模稜兩可] [不選:收短編號或分支名]
- WHY:提交寫法下程式檔與連結節點存不存在照會談目錄判,只在提交裡的確認存在才另外列名(名字照出口以資料形式印,代碼審 r5 起取代原本的嚴格字元集),兩邊都沒有只印筆數 [出處:[[Projects/派工鏡頭可指定目標repo_計劃]] 設計審 r3、r4] [因:impact 讀的是會談目錄;連結抓法吃得下換行與任意長度,沒驗存在就列名,等於讓計劃作者把自由文字塞進派工詞] [不選:照提交判存在;列出所有連結名]
- WHY:spec-freeze 刻意落兩週後會被 gc 的懸空物件,每個 git 呼叫關掉掛鉤與 fsmonitor [出處:[[Projects/派工鏡頭可指定目標repo_計劃]] 設計審 r4 邊界席、架構對齊席] [因:設計迴圈只活一晚,要長期回放的東西不用它;指向暫存 index 時 read-tree 與 update-index 會跑 post-index-change 掛鉤] [不選:先正式提交草稿(撞提交前檢查與錨點簽名、多出要壓掉的半成品提交)]
- WHY:設計審失敗的事件只在失敗時記,note 是 `spec_<spec_source> <代碼>`,使用者輸入錯記 ok [出處:[[Projects/派工鏡頭可指定目標repo_計劃]] 設計審 r4 整合席] [因:成功也記等於記注入次數,違反 [[Projects/派工鏡頭注入_計劃]] 的「不擋不驗不記不量」;輸入錯記 error 會蓋過真的掛鉤錯誤] [不選:成功也記事件]
