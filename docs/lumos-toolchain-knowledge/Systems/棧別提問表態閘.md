# 棧別提問表態閘

> 白話：工具早就會在改檔前、推送前把「這個技術棧該問自己的效能問題」推到眼前，但推到眼前不等於有人回答——治理帳的審查留痕（pass／skip 事件）181 筆 <!--lumos:count=181 re="gate": "code-loop", "kind": "(?:passed|skipped)" in=docs/.governance-log.jsonl-->，留痕文字提到棧別檢核答案的 19 筆 <!--lumos:count=19 re="gate": "code-loop", "kind": "(?:passed|skipped)"[^\n]*(?:棧別.{0,4}檢核|棧檢核) in=docs/.governance-log.jsonl-->，其中答到題表內那幾棧（不是 Python）的只有 6 筆 <!--lumos:count=6 re=(?m)^(?!.*[Pp]ython)(?=.*"gate": "code-loop", "kind": "(?:passed|skipped)")(?=.*(?:棧別.{0,4}檢核|棧檢核)).*$ in=docs/.governance-log.jsonl-->、去掉同輪重記是 5 個迴圈（2026-09-09 機械重數；數字讓 doctor 自己重算，怎麼數在標記裡）。這道閘做兩件事：**（一）只問碰到的題**——每題掛一組觸發字（`when`），對這次改動的增刪行比對，沒碰到的題工具自動記「未觸發」，零 token；**（二）碰到的題推送前要有機器讀得懂的交代**——做到了（附證據）、不適用（附理由）、還沒做（連到待辦）——缺一題 `code-loop check` 就擋，跟風險分級（tier）無關。設計與三輪審查在 [[Projects/棧別提問表態閘_計劃]]。

## Dart／Flutter 這一棧（2026-09-13）

六題進表，鍵是 `dart`。**畫面特有的兩題靠觸發字自己決定要不要出現**——改一支純非同步的 Dart 檔不會被問 widget 重建，改 widget 檔才會（Enzo 2026-09-13 裁「兩邊都顧，用觸發字分流」，跟 Java 同一個裁決，不需要新機制）。

**符號形狀那格不能借 Kotlin**：型別命名看起來一樣，但 Flutter 的 State 類幾乎都是底線開頭的私有類別（`_HomePageState`）。借 Kotlin 那條 `^[A-Z]` 會讓筆記裡最常被點名的那種類別一律判成「查無」，所以另開一個只多允許前置底線的形狀。

**反面詞收了 `.then(` 鏈**：不用 async/await、改寫成 then 鏈做同一件事的舊碼要亮同一題——維護舊碼正是最需要被問的時候。

單源與誠實邊界（零真專案實證）在 [[Projects/Flutter補棧_計劃]]。

## 怎麼用（agent 在代碼審步驟 1 之後做）

```
lumos pitfalls --diff <merge-base>..HEAD --dispositions-template --carry > /tmp/disp.json
# 填 status 留空的題:satisfied(evidence: path:line 或 test:<名>)/ na(reason ≥10 中文字)/ todo(issue: Issues/<名> + reason)
#   / tension(chosen: existing|suggested + existing: [path:line…] + hazard + suggestion;選 suggested 再附 evidence)——帶 hint 的題是「可能撞」候選
lumos code-loop dispositions /tmp/disp.json            # 推 HEAD:別名 時加 --branch 別名
lumos code-loop check --diff <merge-base>..HEAD        # 自查;pre-push/CI 會再跑一次
```

- 改了程式碼表態就過期（跟 pass 留痕同一套規則：目標版本等於表態版本，或表態版本是祖先且中間只動簿記檔）；重跑樣板加 `--carry` 只答新題。
- 審查席若抓到「對得上某未觸發題」的問題：`lumos code-loop recall-miss <題目id> --note "<一句>"`，同題累積 3 次 `gov --stats` 列「觸發太窄候選」。
- 消費專案過渡：`.lumos/config.json` 的 `stack_questions.gate` 設 `high-only` 或 `off`；`ask_all_over_lines` 調「一個棧改幾行就全問」的門檻（預設 300）。

## 工具驗什麼、不驗什麼

| 表態 | 工具驗 | 不驗 |
|---|---|---|
| `satisfied` + `path:line` | 檔案在被推送的 commit 樹裡、行號在範圍內 | 那一行是不是真的解了那題 |
| `satisfied` + `test:<名>` | 工作樹 discovery（profile 語意、多平台）掃得到、且在被推送的樹裡整字 `git grep -w` 得到（未提交的測試不算）；標了 needs_backing 的七題另看破壞測試背書（寫表態時本機算、推送前只提醒，[[Projects/併發與效能表態要合約背書_計劃]]） | 其餘題的測試有沒有殺傷力；七題的背書是本機算的、CI 只能相信記錄 |
| `na` | 理由去空白標點後 ≥10 個中文字或 ≥25 字 | 理由成不成立 |
| `todo` | `Issues/<名>` 在被推送的樹裡存在且 status open/doing | 待辦會不會被做 |
| `tension`（張力，2026-09-09 起） | `existing` 每項 `path:line` 在被推送的樹裡、1–20 項；`hazard`／`suggestion` 過理由門檻且 ≤2000 字；`chosen` 小寫二值；選 suggested 的 `evidence` 同 satisfied 驗法 | 隱患真不真、建議對不對、選哪邊該不該——合法的 tension **不擋**，`check` 印成 ⚠ 讓人裁；設計見 [[Projects/兩席相反時端出張力_計劃]] |

答案對不對留給審查席：派工鏡頭把表態記錄附進派工單，席位反駁的就是這些答案。這是刻意的天花板——同設計審處置閘承認的「垃圾進垃圾出」，工具只抓最懶的謊。例外是併發與 N+1 類七題：satisfied 另外要有破壞測試背書，沒有只提醒不擋，背書的天花板（本機算、作者自宣涵蓋、偶發紅）見 [[Projects/併發與效能表態要合約背書_計劃]]〈天花板〉。

表態那一道在 `code-loop check` 裡跟合約測試、新增告警、代碼審留痕排在一起:不帶旗標是序列早退(先中的先報);推送前掛鉤帶 `--keep-going`(2026-10-14 起),四道都判完、表態不完整跟其他原因一次列出,見 [[Systems/pitfalls-code-loop]]〈code-loop check --keep-going〉。

## 邊界與刻意不做

- 適用範圍算在 `merge-base(主線, 被推送 sha)..被推送 sha`，所以把主線合進分支再推分支，不用替主線帶進來的碼表態；推主線本身才用推送範圍。合進主線後推主線是在主線名下重新判（marker 按分支），`--carry --branch <原分支>` 把答案帶過來。
- 平台 root 在 repo 外（跨 repo 多平台）：被推送的 sha 不屬於那個 repo，`test:` 只做工作樹那一道並在訊息註記。
- 本 repo 的 scripts/lumos 沒有副檔名、不在題表，改它不會觸發這道閘；但 scripts/test_lumos.py 這類 .py 會命中 py 題，2026-10-15 起 get.sh、governance/*.sh 這類 .sh 也會命中 infra 題（見下方 infra 段）。
- 不用 LLM 判答案、不用 LLM 前置分類決定適用性；等 auto-na 比例與 recall-miss 帳說 regex 不夠再開。
- 低風險推送的受波及合約測試維持「只提醒不擋」（2026-09-07 人裁）：pre-push 對低風險帶 `--bound-tests-advisory`，這是實作時為了保住既有裁定加的旗標，不在設計審的條款裡。
