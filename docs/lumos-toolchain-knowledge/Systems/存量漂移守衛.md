## 五種狀態一致檢查

scan、check、doctor Z 共用同一支檢查,也能跑在任一個提交的樹上(考試與推送檢查用)。種類與「只列出/會擋」的分法見計劃〈做法〉第 1 節第 4、5 點;轉正預告句的比對跟 [[Systems/guard-kill]] 的 settle 改寫共用同一支,兩邊不能各寫一份——各寫一份時,settle 改完的句子可能又被認成預告,轉正後的推送被自己擋。

## 條件式回頭條件(乙)

回頭條件可以寫成機器判得了的條件加期限,例如 `REVISIT:[when-file:<路徑>][by:<日期>] 待辦`,文法與判定規則在 [[Projects/存量漂移防線_計劃]]〈做法〉第 0、2 節。「這行是不是 REVISIT」全庫只有一支判定(doctor E5、筆記形狀擋、筆記內容審都用它),三處餵給它的也是同一版文字(剝掉行內程式碼,含雙反引號);各處自己判、或餵的東西不同,同一行會在一處算條件式、另一處算壞損或根本看不見(乙代碼審 r1:E5 原本只剝單反引號,雙反引號裡的範例在 E5 被唸到期、另兩層看不到)。推送時擋的是「這次推送讓條件從不成立變成立」;「同一條」只看條件標記,只改待辦文字或期限還是同一條,改了條件標記就是新寫的,新寫而已經成立的一樣擋。

## 跟設計稿不一樣的兩處(實作時決定)

- **考試的「誤報」不算同一篇同一種的兄弟句**:c1 一句一筆,一篇守衛紀錄有四句預告句,題目只考 TEST 那句,另外三句是同一個轉正事件的真發現,算成誤報會把「抓得對」算成「亂抓」。同一篇別種的發現、別篇的發現照算(代碼審 r1 外家席:第一版把同一篇全部排除,誤報被低估)。
- **doctor 的閘提醒放在開頭、發現放在 Z 段**:設計把兩者都寫在 Z 段。開關不是 block、CI 沒呼叫這兩行照筆記形狀擋與筆記內容審的位置放在 doctor 開頭(代碼審 r1 架構對齊席:同一種閘提醒不該有兩種呈現);c1–c5 的筆數是筆記內容的發現,跟 E5 一樣放 Z 段;某一種只剩已表態的不開段(全靜默,完整清單看 drift scan)——設計寫的是「照列、標已表態」,那是 scan 的做法,doctor 照列會讓表態完那一段永遠不安靜(代碼審 r2 正確性席)。開關提醒只在專案自己寫了開關、或已經接線時才印(代碼審 r1 外家席:關掉了要看得見;第一版只看接線,r2 改成一律印,r3 發現沒寫設定時預設就是 warn,每個專案每次 doctor 都多一行、也破壞既有軟段計數測試,收成現在這樣)。2026-09-30 預設改成 block 之後,不是 block 只剩專案自己寫了 warn/off,「沒寫設定、已接線時唸是預設的 warn」那一支拿掉;設定寫壞(拼錯、null、不是物件、JSON 壞)照預設 block,照樣講出寫錯的地方。

- **乙的 symbol/test 語料比設計寬一點**(乙代碼審 r1 正確性席):設計寫「副檔名清單裡的程式檔」,實作另收沒副檔名、開頭是 `#!` 的檔(主程式 scripts/lumos 就是這種);帶路徑的條件直接讀那支檔,不管它算程式檔還是測試檔——作者明寫了哪支檔,工具不該再用分類把它排掉。
- **scan 多列一種問題**:`[when-symbol:Config::load]` 這種「型別::方法」寫法照文法會切成路徑 Config、名稱 load,永遠不成立;路徑那段在樹上找不到、沒有 `/`、最後一段也不像副檔名(字母開頭、只有字母數字與 `_+-`、全小寫或全大寫)時,scan 列成「不像檔案路徑」——`v1.2`、`app.Config` 列,`.c++`、`.R` 不列(乙代碼審 r2、r3 邊界席、r3 外家席)。還沒建的檔(`src/new.py::main`)是正常的等待狀態,不列;`Makefile` 這種沒副檔名的根目錄檔分不出來,提示裡講明「還沒建的根目錄檔建了就會判,不用管」。
- **不帶路徑的條件怎麼算候選**(乙代碼審 r2、r3 正確性席;設計稿已同步改,計劃〈做法〉第 0 節):原設計寫「名稱出現在範圍的改動行」,改成「名稱出現在範圍裡改到的程式檔或測試檔的終點全文」,並加一條「兩端的測試資料夾版面不一樣」也算形狀改變——改動行抓不到「刪掉三引號」「加上 #!」,形狀改變原本抓不到「刪一支不算程式檔的檔,讓別的檔從測試檔變程式檔」。留在這一節是記「為什麼改」,現在設計與實作一致。
- **考試的改寫檔要先過文法**:改寫不合條件式文法(含沒帶期限)的,exam 直接擋下回 2,不照考——原本考過的 A7、B3、B4 三題都沒帶期限,是第一層會擋的寫法(乙代碼審 r1 外家席、正確性席)。

## 怎麼用

- 推送時自動跑(2026-09-30 接線):`scripts/hooks/pre-push` 對每個要推的 ref、`.github/workflows/ci.yml` 在 push 事件的 drift check 那一步,都叫 `lumos drift check --diff <遠端舊值>..<頂端> --push-remote <遠端名> --pushed-ref <遠端 ref>`(起點由工具算;不帶後兩個參數時照共用起點判法,手動跑用這種;這篇只管那一段呼叫,掛在哪、前後是哪些閘見 [[Systems/bound-tests-gate]]),沒寫設定就擋(2026-09-30 起預設 block;之前是 warn 只印);專案要先只提醒就在 .lumos/config.json 寫 `{"drift_check": {"gate": "warn"}}`、關掉寫 `off`,單次略過 `LUMOS_SKIP_DRIFT_CHECK=1`(留帳)。
- 同一個掛鉤與 CI 在漂移檢查那一段之後,還接了回頭重讀守檔筆記的 reread-check(2026-10-01,[[Projects/守檔筆記對照改動_計劃]]〈做法〉4):★那段只提醒、恆放行★——掛鉤只在它回 130(Ctrl-C)時停下整支推送,其他非零(含被系統砍掉)印一句照推;CI 那步帶 continue-on-error 並在指令尾巴吞掉回傳碼。參數照漂移檢查那段原樣交;判定怎麼做歸 [[Systems/筆記內容審]]。
- 健檢全圖譜:`lumos drift scan`(`--at <提交>` 看某個版本、`--json` 給修復清單用)。
- 照清單修:`lumos drift fix <節點> <行號> --kind c1..c5`(先加 `--dry-run` 看改法;c2 要 `--close --status … --reason` 或 `--keep --reason`,c3 要 `--status`、可加 `--reason`,c4 只列證據(卷證目錄標來源)、範本句與一條預填好的 `lumos set <節點> valid_under …` 指令,把 <整項新內容> 換成改寫後的整句、範本的 <卷證> 換成從清單挑的目錄再貼;set 改完先提交,再對同一篇跑別的 drift fix,不然乾淨檢查會擋);修完修復帳要跟筆記一起提交。
- 某一行確定照留:`lumos drift ack <節點> <行號> --kind <種類> --reason "…"`,提交進去才算;那一行一改就失效。舊句檢查(m1)要再帶名稱 `--name=<名稱>`(一個名稱一個、一律等號寫法),直接貼 check 印的那條、把 `<為什麼照留>` 換成真理由。

- 考試:`lumos drift exam <考卷> --repo <被考的 repo>`;`--history N` 對最近 N 個主線提交重放(門檻②)。
