# 規格閘

## 為什麼獨立成一支

設計審的散文收斂在本 repo 從沒收斂過(五輪 118 條、每輪都有 blocker;見 [[Projects/規格落成可驗收條件_計劃]])。這道閘把力氣搬到「條款能不能被機器認出來、有沒有接到真的測試、跑起來是紅是綠」。半套所有計劃照舊派審——它不減少審查,只讓「條款有沒有接到測試」變成可見的數字。

## 邊界

管計劃裡 `[SN]` 那幾行、它們綁的測試、以及「這份計劃風險高還是低」的判定。2026-09-17 起也判門、放行風險低、寫審查帳留痕、在推送前讀留痕跑測試(設計在 [[Projects/雙向門放行_計劃]]);逃逸帳的寫入語意在 [[Projects/逃逸自動記_計劃]]。門是機械判、預設單向:作者只能把門往嚴調(plan_risk: high),寫 two-way 沒有意義。

## 計劃風險怎麼判(完整版;2026-09-17 定案,舊稱單向門/雙向門)

**問題只有一個**:還原這次提交之後,外面的世界要不要人手動收拾?要=風險高,不用=風險低。程式碼本身永遠改得回來,所以判準看的是提交以外的副作用:

| 類 | 為什麼還原提交不夠 | 關鍵字表(PITFALL_CLASSES) |
|---|---|---|
| 金流 | 扣款退款已經發生,錢不會跟著回來 | 金流 payment stripe billing 退款 refund 扣款 |
| 對外送出 | 信、webhook、推播已經到對方手上,收不回 | 寄送 送出 send webhook notify LINE 推送 mail 簡訊 對外 |
| 不可逆資料 | DROP/DELETE/遷移把資料轉掉,還原程式碼不會把資料變回來 | prod production 遷移 migration 不可逆 DROP TABLE DELETE FROM 上架 |
| 守衛面 | 改的是閘與判定本身;它壞掉那段時間放行過的東西已經進去了,而且沒有別的閘能替它把關 | 錨點 anchor verify 收斂判準 canary 審計閘 pre-push hook |

**硬訊號(任一命中=風險高,不可申辯)**:①計劃全文可見行命中關鍵字表(只跳過實務隱患節內合格的已排除行;引用塊、圍欄、行內程式碼不算)②連到的節點(lands_in/related/正文連結)帶 ★IRREVERSIBLE★/★CHECKPOINT★ 合約行或 risk/ 標籤 ③計劃自帶 risk/ 標籤 ④作者標 `plan_risk: high`。**風險低的證明**:硬訊號零命中,且「## 實務隱患」節裡四類各一行 `已排除:<類>:<理由≥4 實字>`。作者只能往嚴標;寫 low 沒有意義。四行是 AI 自我認證(Enzo 裁不補人簽),糾錯靠逃逸帳與撤除條件。

**兩條路**:
- 風險高 → 句式/綁定/回退節擋、綁的測試跑一次只印紅綠、相依節點的合約測試收進驗收(紅擋)→ 設計審迴圈(lumos loop next)→ 實作 → 代碼審 → 推。
- 風險低 → 條款每條綁測試(或靠人驗 [manual:]),沒標 [keeps] 的測試現在要紅、標 keeps 的要在計劃進 git 之前就存在且綠,測試名互不相同,弱證據不算;過了 PASS、留痕(plan_risk、四行理由、測試名、條款指紋、規則版本)→ 直接實作 → 推送前:門重判、指紋比對、留痕裡的測試全跑(全靠人的改走小改動閘:擴散/相對量/歷史/目的)→ 代碼審(看改動風險分級,架構席每級必派)→ 推。逃逸帳按計劃風險與階段分開量,doctor S14 印三條撤除條件的分子。

**依據**:Amazon 單向門/雙向門判可逆與後果(不給大小數字);Meta RADAR/DRS 自動放行低風險 diff 走資格閘→靜態啟發式→ML 分數→LLM 審→確定性驗證,無公開行數上限;Google 每改必審、100 行合理;即時缺陷預測(Mockus & Weiss 2000、Kamei 2013)最強訊號是擴散度、相對變動量、歷史與是否修 bug——小改動閘四維度由此來。出處與數字在 [[Projects/雙向門放行_計劃]]。
