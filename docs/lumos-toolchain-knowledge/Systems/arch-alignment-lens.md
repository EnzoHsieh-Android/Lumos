# arch-alignment-lens

# arch-alignment-lens

> 白話:Enzo 2026-08-22 提的需求——自動開發的流程不能產出「跟原本不一樣」或「不入流」的寫法,破壞共同開發的體驗。以前審查席看的是正確性、併發、邊界、合約,沒有一席管「這樣寫跟專案既有的一不一樣」。

## 三個零件
1. **席位**:四個席位表各加一席「架構對齊」(required,不佔人數)。`lumos loop next` 會吐它。
2. **派工**:`skills/lumos-design-loop/templates.md` §7.6——三問(分層與依賴方向 / 命名與錯誤處理 / 有沒有引入第二種做法),每問附對照 file:line;嚴重度錨只給兩種情況 major。判不準(鄰居本身就不一致)標 ⚠ 交編排者,不硬判。
3. **對照組自動化**:`lumos pitfalls --diff` 對每支改動 code 檔列同層最像的 3 個既有檔 + 慣例 skill,人讀與 --json 都有(`arch_alignment`)。審查員拿這三個檔當「專案現在的寫法」。

## 跟棧別檢核題撞到時(2026-09-09 起)

這一席要「跟既有一樣」,棧別檢核題要「用比較好的做法」,兩者可能對同一段程式給相反意見([[Issues/架構對齊席與棧別檢核題可能相反]])。
Enzo 裁:不挑邊、把兩邊端上來。落成三塊(設計與審查在 [[Projects/兩席相反時端出張力_計劃]]):

1. **表態多一種值 `tension`**:作者答檢核題時可以說「我看見兩邊了,這次選沿用既有/改用建議」,附既有寫法在哪(path:line)、隱患、建議。合法的不擋,`code-loop check` 印成 ⚠ 交人裁。
2. **`pitfalls --diff` 端出「可能撞」候選**:改動檔的增行命中某題觸發字、對照的三個既有檔一個都沒有 → 印一行、表態樣板那題帶 `hint`。只端候選、不判——跟上面「不做機械判像不像」一致,看的是觸發字有沒有出現。
3. **派工詞口徑**(templates.md §7.6):遇到 tension 的題,本席查四欄真假(既有真的那樣寫嗎、隱患真的成立嗎、建議可行嗎、chosen 跟 diff 一致嗎),不重裁誰贏;自己發現「跟既有不一樣」而該題答了 satisfied,就把發現寫成張力形狀。

天花板:tension 跟 na 一樣可以敷衍(工具只驗存在與長度);候選只抓「新檔引入鄰居沒有的做法」,反方向「照舊寫法沒採建議」抓不到。

## 刻意不做的
- 不做機械判「像不像」(AST 相似度之類)——「不入流」是語意判斷,交給席位;機械層只負責把對照組端到審查員面前。
- 不把風格偏好算 finding。

## 目標架構基準(2026-10-09 起,[[Projects/架構對齊可宣告目標架構_計劃]])

白話:專案可以宣告「這些目錄照某篇目標架構審」,範圍內的改動檔不再拿同層舊鄰居當標準,改拿那篇筆記的 RULE 行;範圍外照舊比鄰居。為的是在舊系統裡長新模組(例:照 DDD 寫)時,不被判成「跟舊鄰居不一樣」。

為什麼這樣定(程式看不出來的部分):
- 宣告只讀改動起點那一版。被審的分支不能在同一次推送裡加宣告、放寬規則、再寫新寫法來決定自己怎麼被審;分支改的宣告下一次推送才生效。設計審沒有改動範圍,讀 HEAD,因為設計審不放行程式。
- 形狀照抄角色鏡頭的 review_roles:有序清單、第一條命中算數(所以沒有「範圍重疊」這種錯誤,要排除舊碼就在前面放一條 node 為 none)、壞宣告整份不用、警告不回填專案原值。
- 第一段是萬用字元的樣式(**、**/*.php、*.cs)整份不用:比對時開頭的 **/ 會被去掉再試,這些樣式等於整個 repo 或整個語言,是變相的全域開關。
- 規則不另立語法,用既有 RULE 摘要行:那種寫法已經有生命週期欄位與測試綁定檢查;另立一種會繞過這些把關。審查席引規則用原文,不用編號,規則改寫時舊引用不會錯位。
- 推送前風險分級只標「哪些檔用目標基準」、不讀節點:它刻意不載圖譜(載圖譜要好幾秒,它在推送前逐 ref 跑)。規則原文由本來就載圖譜的派工鏡頭附,做法同角色鏡頭的標記行。
- doctor 對壞宣告、節點不存在、沒有有效 RULE 行、命中 0 支檔只提醒不擋:節點改名或刪掉不該擋住整個 repo 的推送。
- 回退後範圍內的新寫法會重新被判「跟鄰居不同」,回退前要先告知有宣告的專案。

派工範本 §7.6 多一行 LUMOS-ARCH-TARGET: on 與一段「有[目標架構]段時」:段裡的檔照規則與範圍內其他新寫法判,段外照鄰居,兩組分開答;依賴方向兩頭都問;範圍內舊檔只判新增或改到的行;違反規則=major 並附「目標規則:」引句。三問本身沒換,沒有目標段時行為跟以前一樣。代碼審手冊([[Systems/每輪修補差異派工]] 管的那幾份)與推送說明表各補一句指路。

代碼審 r1 補上的三條(設計審沒看出來,記成逃逸):
- 宣告與規則一律讀「起點與主線的分叉點」那一版(代碼審 r2 改成這條統一規則):修補輪常用「上一輪終點..這一輪終點」當範圍、推分支時起點是遠端分支頂端,這些起點都是被審分支自己的提交,照讀就吃分支寫的宣告與規則。起點在主線上時分叉點就是起點本身。推送前分級、派工鏡頭、code-loop check、角色鏡頭的 review_roles 共用同一支(r1 第一版只在派工鏡頭擋、而且是「不附」,r2 兩席抓到分級那邊沒擋、角色鏡頭同形狀,改成這條)。例外與失敗(r3 補):本機找不到 main/master 時,派工鏡頭不附任何規則(照讀起點就會附上分支寫的規則),分級與角色鏡頭照舊讀起點(分級只標檔、不貼規則);跟主線沒有共同祖先、或 git 算不出分叉點時,分級、派工鏡頭、推送檢查、角色鏡頭都附一句固定說明,不靜默當成沒宣告。起點是空樹(新分支首推)時那一版本來就沒有宣告,當成沒宣告、不出聲(r4)。
- 特殊字元走專案共用的那組類別(C0/C1、雙向覆寫與零寬、行與段分隔):檔名是分支可控的,換行能在派工詞參考資料框外另起一行假指令,U+2028 會讓掛鉤逐行解析切壞 JSON、整段鏡頭附不上(r1 第一版只擋 C0,r2 兩席抓到)。宣告的 path/node 帶這種字元算壞宣告;命中檔照樣算進目標組、不偷偷踢出去,輸出一律跳脫成看得見的 \uXXXX。推送前分級的 JSON 輸出也改成無損跳脫(推送檢查用逐行方式找 JSON,原樣輸出會被切壞而放行)。
- 設定讀不懂時,只有原文提到 arch_targets 才警告:沒宣告的專案設定壞掉,架構對齊段不該多東西;git 本身失敗則一定附說明,不當成沒宣告。推送前分級與派工鏡頭的命中檔都走角色鏡頭那支改動檔清單(改名算新路徑、刪除不算);範圍終點是工作目錄時不分目標基準、明講要提交後再跑。推送前分級解析 diff 檔名時順手去掉 git 在含空白檔名尾端補的 tab。
