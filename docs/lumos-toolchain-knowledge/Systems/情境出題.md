# 情境出題

> 白話:[[Projects/後端工程提問與證據擴充_計劃]] 的 A 塊「情境出題」要先量再接。這篇管量測用的那支執行與計分程式;A 塊若過門檻接線,需求風險面表的內容源也落在這篇。

- 實驗的題目、標準答案、門檻與無效條件寫在同目錄的預先登記,算法改動要先改預先登記。
- 子命令:交錯執行(每個題目與場次甲乙各一場、先後由固定種子決定、可續跑)、輔助計分、產生盲評包(隱去受測者、組別、場次並打亂,對照表另存)、兩位評分員一致率、最後統計(逐題配對差與精確符號翻轉檢定)。
- 執行時呼叫 [[Systems/codex-harness]] 管的情境探針,一場一次,回答保存上限調到兩萬字。
- 程式本體:`governance/eval/qo-ablation-2026-10/qo_ablation.py`。
- 2026-10-12 依 Codex 外家第二次審查補強(預先登記第 3 版):續跑只認真正有效的場次(截斷、逾時、儀器例外都重跑),版本紀錄不一致拒絕混用;兩位評分員標註不完整就停,分歧走仲裁包與合併;最後統計自動套用全部無效條件、分母固定每題 6 項,另報只用單一評分員的敏感度(處理同模型評分的自我偏好);盲評包遮掉回答裡自報的身分與組別路徑。審查結論存在實驗目錄的 codex-review-v1.md、codex-review-v2.md。
- 同日開跑前驗收再補四處:仲裁結果只能是兩個候選之一、亂問數仲裁要落在兩位評分員的值之間;最後統計自己重算合併(不收外部給的合併結果);主判定與單一評分員判定不一致時改判「交給人裁」;shell 指令逐一檢查路徑。驗收結論存在 codex-review-v3.md。
- 2026-10-12 實跑中途:「先寫程式」判法改第 2 版(建置工具要在去掉引號字串後、出現在指令位置才算;第 1 版把只讀 grep 裡的 gradle 字樣誤判成寫檔),第 1 版結果並列報告。

## 待決問題與需求風險面(2026-10-12 接線,[[Projects/後端工程提問與證據擴充_計劃]] 決策 d9)

- 計劃筆記的〈待決問題〉一節由一支只吃文字的解析函式讀,規格閘、lint、`lumos pitfalls --stage` 三處共用;要查決策是否有效、測試名是否在條款裡的檢查只放 lint(規格閘只看狀態)。文法、六種狀態與各自必附寫在計劃 A 塊。
- 規格閘的擋法見 [[Systems/規格閘]];`--stage` 見 [[Systems/pitfalls-code-loop]];lint 規則掛在新規則那一路,擋不擋跟著專案的 note_lint.gate。
- 需求風險面表的內容源就是這一節:12 項,依任務書提問九類與六個階段挑出,每項是「什麼情況下要釐清什麼」,不是固定題目;觸發條件比對計劃筆記文字,「.」代表每份計劃都適用。

| id | 階段 | 要釐清什麼 | 何時觸發 |

| req-duplicate | 需求 | 重送、重按、重試怎麼處理 | 提到 API、送出、下單、兌換、預約、付款、扣、建立、寫入 |
| arch-necessity | 架構 | 新元件解決什麼、有沒有更簡單、誰維運 | 提到 Redis、Kafka、佇列、快取、微服務、拆成、新服務、訊息 |
