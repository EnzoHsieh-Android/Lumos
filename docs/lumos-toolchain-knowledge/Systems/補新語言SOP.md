# 補新語言 SOP

> 白話：lumos 八成的功能不看你的專案用什麼語言寫。真正綁語言的只有「工具對這個技術棧知道什麼」那一類，一共八格。這篇是把三次補棧（iOS/Node、Python、Java）走過的路凝鍊成一張可以照著走的清單，**重點不是每格填什麼，是哪些地方會漏、哪些坑三次都踩**。

## 0. 先確認真的要補

- 觸發條件：**有一個真的專案要接進來**。沒有專案就補，補出來的是零實證的文件，而零實證的文件會隨時間看起來越來越可信。
- 補之前先確認這個語言是不是已經被別的 profile 借走了（例如 `.java` 原本掛在 kotlin 的符號 profile 底下），借得對就別新開。

## 1. 派乾淨 agent 盤點八格

**不要把自己的結論丟給它**（丟了它會順著你講）。用原始問題問：「這套工具鏈對 X 專案的支援到什麼程度？哪些地方已經認得 X、哪些沒有？」

| 格子 | 在哪 | 空著的症狀 |
|---|---|---|
| 程式碼副檔名清單 | 主程式裡的幾份清單＋掛鉤（有測試釘一致，見 [[Systems/每支檔有家]]） | 改了那種檔，圖譜同步檢查不理你 |
| 符號形狀 profile | `SYMBOL_PROFILES` | 筆記提到的符號一律「查無」；或被別的 profile 借走而標「猜得很弱」 |
| **測試綁定 profile** | `TEST_PROFILES` | ★最嚴重★：掃不到測試 → 合約綁不上任何東西 → **閘靜默放行**，看起來一切正常 |
| 骨架測試指令 | `_SKELETON_RUN_CMD` | `init` 產出的設定該欄留白，使用者不知道要填什麼 |
| 效能追問題組 | `_STACK_QUESTION_SPECS` | 三個時機（動手前、推送前、終審）都不問這個棧的任何問題 |
| 副檔名→慣例 skill | `_ARCH_IDIOM_SKILL` | 架構對齊鏡頭不派慣例給審查員 |
| 慣例 skill 本體 | `skills/<語言>-idioms/` | 同上 |
| 兩份目錄 | [[Systems/效能檢核目錄]]、[[Systems/linter精選目錄]] | 審查鏡頭沒有這個棧的檢核表；使用者要自己從零挑 linter |

## 2. 先問人：題組要偏哪個方向

題目 id 被測試釘住，換 id 會讓在途分支重新表態，所以**方向要一開始就選對**。把選項攤開來問，別自己猜：

- Python 的答案是「偏長跑程序／資料處理，不收 Web 框架特有題」（首個消費端是交易機器人）。
- Java 的答案是「兩邊都顧，依照情況接特有檢查」——通用題常駐，平台特有題靠觸發字條件出現。

**這個問法之所以成立，是因為觸發機制本來就是條件式的**：題目只在改動行出現對應詞彙時才適用。所以「兩邊都顧」不需要新機制，不要為它發明東西。

決定要寫成計劃筆記的正式決策（四欄：context／至少兩個被否決的選項／why_chosen／trade_offs）。

## 3. 補測試綁定 profile（最容易漏、後果最嚴重的一格）

- 方法正則**不要照抄隔壁語言**。每種語言都要自己找一個收斂得住的錨：
  - Kotlin：註解 → 中間不跨 `{` → `fun` 方法名。
  - Java：照抄上面那條會壞，因為參數化註解自己帶大括號。改用非貪婪比對，靠「JUnit 規定測試方法必須回傳 void」收斂。
  - Swift：XCTest 靠 `test` 前綴、Swift Testing 靠巨集，兩代並收。
- 目錄慣例可以借（同樣是 Gradle/Maven 佈局的語言直接抄隔壁）。
- 補完檢查一件事：`init` 對這個副檔名猜到的兩個 profile 對不對，以及「猜得很弱」的旗標有沒有因此關掉。

## 4. 補骨架測試指令

- 重點是**形狀對**（要能只跑一支測試），不是它在你機器上跑得動。
- 每一條都要帶「能證明真的跑了東西」的那個旗標——這個表裡每一條的註解都在講某次假綠事故。查不到對應旗標就在註解裡寫明「這條沒有」。
- 沒裝那個建置工具就明講沒實跑，別讓形狀對冒充驗過。

## 5. 補效能題組

- 題數參考：kt=7、cs=5、vue=5、sql=4、swift=6、node=5、py=5、java=7。
- id 格式只准 `^[a-z]+-[a-z0-9]+$`（單一連字號）。
- 觸發字＝**範式詞＋反面詞**：範式詞是那塊地的詞彙，反面詞是同一個顧慮用舊法寫會出現的字。只收範式詞的話，「用爛方法寫同一件事」不會亮題，而那正是最需要被問的時候。
- 要看字串內容的條目分開放（整題看字串會讓日誌訊息變成假命中）。

## 6. 寫慣例 skill

- 版型直接借最近一份（Java 借 python-idioms）。
- 只寫**不隨框架選擇改變**的原則；框架選型歸專案圖譜。真的只有某平台成立的條款集中放最後，標題標明。
- 機檢欄的規則代號**要逐條查證**。Python 那次是本機 `ruff rule` 逐條跑過；Java 那次本機沒有建置工具，所以整份標「未實跑」——**做不到就標出來，不要讓查過文件冒充跑過**。

## 7. 測試與翻紅驗證

至少三支：
- `t_<語言>_profile_discovery`：測試方法掃得到／掃不該掃的不收／註解剝掉。
- `t_<語言>_stack_wiring`：題數、副檔名→慣例 skill、改檔附題、測試檔不附題、skill 真的存在。
- `t_stack_question_triggers`：把新 id 加進釘住的集合，加命中／不命中樣本。

**翻紅驗證是必做的**：每條接線拿掉一次，確認測試真的紅，再還原。三次補棧都做了，格式是一張「動了什麼 → 哪幾條翻紅」的表。

⚠ 寫樣本時會踩到的既有設計：**同一支檔改寫時，被刪掉的那行也算改動行**（「純刪除也要觸發」是刻意的）。要驗「兩題各自獨立」必須分成兩支檔，不然上一版的字串會讓另一題跟著亮。

## 8. 寫回圖譜

- 計劃筆記 `Projects/<語言>補棧_計劃`：八格盤點表、題目怎麼選、決策四欄、誠實邊界。
- 驗證紀錄 `Verification/<日期>_<語言>補棧合成樣本測試`：跑了什麼、翻紅驗證表、**這篇不能證明什麼**。
- **家在哪**：程式改動的說明要寫進被改檔案的家。這次的兩個家通常是 [[Systems/棧別提問表態閘]]（效能題組與慣例對映）與 [[Systems/test-profile-multiplatform]]（測試 profile）。

## 9. 同步四處散落清單（每次都會漏）

| 要改的地方 | 漏掉的後果 | 歷史 |
|---|---|---|
| 效能檢核目錄裡那串「全表各棧題數」 | 讀的人以為沒有這個棧 | 2026-09-11 漏、09-12 補回 |
| test-profile-multiplatform 裡那串「profile 共幾個」 | 同上 | 09-08、09-11 都漏，09-12 補回 |
| `ONBOARDING.md` 的 idioms 清單 | 新來的人不知道有這份慣例 | — |
| `skills/lumos-design-loop/templates.md` 的 idioms 清單（兩處：一般派工與資安席） | 審查員拿不到慣例 skill | — |
| 兩份 README 的支援語言表（中英各一） | 對外說明過時 | 2026-09-12 首次建立 |

## 10. 提交：一定要分兩個

「每支檔有家」的閘會擋「這次寫了說明的節點，不是任何一支改動檔的家」。兩份目錄筆記不是主程式的家，所以：

1. **第一個提交**：程式 ＋ 家節點 ＋ 計劃 ＋ 驗證紀錄 ＋ 慣例 skill ＋ README／範本。
2. **第二個提交**：只有兩份目錄筆記。

Python 與 Java 兩次都先撞到閘才分開，照這條走可以省一輪。

## 11. 收尾：標明零實證與回頭條件

- 計劃筆記、驗證紀錄、慣例 skill、兩份目錄段落，**四個地方都要標**「尚未在真專案跑過」。
- 帶日期的回頭條件寫成獨立一行 `REVISIT:YYYY-MM-DD`，健檢到期會唸。
- 第一個真專案接進來、跑完第一輪代碼審之後要回填：哪題從來沒亮過、哪題每次都答「不適用」（死題候選）、哪些坑 skill 沒收、哪些 linter 規則預設沒開或誤報多到要關。
