# 代碼審修正關卡

白話:代碼審一輪修完、派下一輪之前,先讓工具驗一次編排者的修正紀錄——每個折入的發現有沒有歸到一組根因、每條修了的路徑有沒有測試守著、那些測試在修好的版本裡真的存在而且是綠的、受波及的合約測試全綠。只提醒不擋。設計與取捨單源在 [[Projects/代碼審修正關卡第0步_計劃]];還沒做的「修之前會紅」在 [[Projects/代碼審修正關卡_計劃]]。

## 怎麼用

- 修完先提交,寫修正紀錄 `governance/review-reports/<迴圈編號>/<輪>-fix.json`;骨架:
  `lumos loop fix-check <迴圈編號> --round <輪> --record-template > governance/review-reports/<迴圈編號>/<輪>-fix.json`
  (`base` 從派工單的 `base_commit` 帶入;派工單在手冊第 2 步寫時記 `git rev-parse HEAD`)。
- 跑:`lumos loop fix-check <迴圈編號> --round <輪>`——一次約 5 分鐘(多半花在受波及合約測試),在背景跑。回 0 過、1 驗了沒過、2 輸入錯(不記帳)。
- 跳過:`LUMOS_SKIP_FIX_CHECK=1`(記一筆 `skipped-env`,`loop next` 改印「已跳過」)。
- 修正改到殺傷力配方指著的檔時,提醒段列出那幾條配方的重跑指令(只提醒)。
- `loop next` 對代碼審迴圈:最新一輪有要修正紀錄的折入、而治理帳沒有「同一輪、紀錄指紋相同、之後只動簿記檔」的通過紀錄時,印一行提醒與指令(`--json` 多 `fix_check` 欄);狀態與回傳碼不變。

## 驗哪幾項

1. 紀錄完整(折入的 `code` 類發現都歸組、類別在固定清單、`fixed` 有測試、`unaffected` 有理由、`at` 的檔與函式段對得上、`fixed` 的檔真的改過)。
2. 同類連兩輪(前一輪同類別、這輪 ≥major → 要寫 `prior`;`other` 不算同類)。
3. 測試存在(跟推送前合約測試閘同一支解析)。
4. 紀錄裡的測試在修正後是綠的(跟規格閘同一支判法:篩選選到好幾支不同的測試、被跳過、一支都沒跑到都不算綠)。
5. 受波及合約測試全綠(推送前那道閘在樹裡跑;有程式檔改名只提醒——`impact --diff` 的既有洞)。

## 共用出去的零件

- 隔離工作樹:跟 [[Systems/guard-kill]] 共用;修正關卡會在開頭清掉同前綴、超過一天的殘骸,guard kill 不清。
- 一批測試逐支判:跟 [[Systems/規格閘]] 的三處共用。
- 測試名解析成平台與方法、判在不在索引裡:跟 [[Systems/bound-tests-gate]] 共用。
