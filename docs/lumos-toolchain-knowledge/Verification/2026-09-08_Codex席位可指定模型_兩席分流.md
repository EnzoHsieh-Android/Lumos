# 2026-09-08_Codex席位可指定模型_兩席分流

> 白話:以前以為「Codex 的審查席不能各自指定模型,只能吃全域預設」。實測發現**可以**,
> 於是把外家審查席拆成兩個:日常用便宜一點的,高風險改動才派最強的那個。

## 推翻了什麼

`skills/lumos-code-loop/reference.md` 兩處寫著★不能逐席指定模型★,說模型只由 codex 的
`agents.default_subagent_model` 決定。**這是錯的**,已改。

## 怎麼驗的(三步,關鍵在第二步是反證)

**① 先試「自報模型」——這招沒用,別學。**
席位 TOML 指定 `gpt-5.4-mini`,叫它回報自己的模型代號,它答 `GPT-6`(父層是 astra)。
差點據此下結論「欄位被忽略」。★模型對自己的身分不可靠,自報不能當證據★。

**② 反證才作數:指定一個帳號一定用不了的模型。**
TOML 寫 `model = "gpt-6"`(這個 slug 帳號會被 400 退回)→ 席位啟動失敗,原始錯誤:
`The 'gpt-6' model is not supported when using Codex with a ChatGPT account.`
**欄位若被忽略就不會有這個錯**,所以欄位有效。

**③ 推理強度同樣有效,而且會驗值。**
`model_reasoning_effort = "banana_不存在的強度"` → 明確報錯並列出支援值:
`模型 gpt-5.4-mini 不支援設定的推理強度 …;支援 low、medium、high、xhigh`。

## 落地的編制

| 席位 | 模型 | 推理強度 | 什麼時候點名 |
|---|---|---|---|
| `lumos_reviewer` | gpt-5.6-terra | **medium** | 散文審(設計審、文件、spec);也是預設 |
| `lumos_reviewer_code` | gpt-5.6-terra | xhigh | 程式碼審,一般風險 |
| `lumos_reviewer_max` | gpt-6-astra | xhigh | 程式碼審,且 `pitfalls --diff` 判 tier=high |

> **同日下午再裁一次,從兩席變三席。** 原本三種情況只有兩席可用,結果散文審也吃到 xhigh——
> 實測拿它審一份 8k 字元的 README 語感,**慢到使用者當場喊停**。
>
> ★這件事的教訓比設定本身重要★:**推理強度要配題目,不是越高越好。** 它的成本是牆鐘時間,
> 而**審查慢到讓人不想派,就等於沒有這道防線**——那比強度低一階嚴重得多。
> xhigh 該留給「爆炸半徑判不出來」那種真的要想很久的題目。

**為什麼不全用最強的**:GPT-6 Astra 在 Plus 方案的額度很緊(查到每 5 小時 5–45 則,
★這個數字是網路查的,沒實測★)。全用它會一輪吃光,之後退回「沒有外家席」的狀態——
[[Issues/外家席長期缺席仍照跑loop]] 記過這個前科(九個審查席全同一家族)。額度花在刀口上。

## 順帶查到的

- **本機模型清單會過期**:`~/.codex/models_cache.json` 第一次讀到的是舊版 CLI(0.152.1)
  抓的,裡面沒有 astra;跑一次 codex 之後它自己更新成 0.153.2 的版本,astra 就排第一了。
  ★判斷「有沒有某個模型」之前先讓它刷新一次,不然會得到過期答案★(我就答錯過一次)。
- **乾淨環境下這個帳號的預設模型已經是 `gpt-6-astra`**;是本機 `~/.codex/config.toml`
  把它壓成 `gpt-5.6-sol` + `low`。
- Astra 需要 codex-cli **0.153.0 以上**,本機 0.153.2 符合。

## 守衛

`scripts/test_lumos.py` 的 `t_codex_d6_agent_toml` 加了 5 條:兩份 TOML 都要寫出來、
兩席的模型與推理強度要精確、名字不同但指示相同(框架單源)、teardown 兩席都收且清單照實列。
★餵壞值驗過會翻紅★:把高風險席降成 luna+low → 那條斷言紅,還原 → 綠。

## 改到既有測試的地方(留痕)

**動了一條既有斷言**:`t_codex_d6_agent_toml` 裡的「teardown 對外方檔回 False 不刪」。

- **為什麼不成立了**:那條假設只有一席。兩席之後,就算 `lumos_reviewer.toml` 是別人的檔
  (不刪),第二席 `lumos_reviewer_max.toml` 是我方的、照刪 → 回傳值不再是 False。
- **守衛的本意沒變**:它守的是「lumos 不刪別人的檔」,那件事仍然成立。
- **改成怎麼驗**:刪除清單裡不出現那個外方檔 ∧ 檔還在 ∧ 內容還是別人的。**比原本的
  「回 False」更精確**——原本那條就算函式改成什麼都不刪也會綠。

**順帶抓到自己剛引入的一個 bug**:改兩席時,teardown 的移除清單寫成無條件列兩席,
**只刪掉一席時會回報一個沒發生的動作**。修法是把 `_remove_codex_agent` 從回 bool
改成回「真正刪掉的檔名清單」,teardown 照那個清單列。★這是跑測試跑出來的,不是想出來的★。

## 邊界

- 只證明「欄位有效、席位起得來」,**沒有證明 astra 審得比 terra 好**——那要另外量。
- 額度數字沒實測,是查來的。真的撞到上限會怎樣(退回哪個模型、還是直接失敗)不知道。

## 這次我自己犯的一個措辭問題(值得記)

第一次全套跑出 7 條紅時,我跟 Enzo 說「那一跑可能不可信,因為我當時正在編輯 skill 檔,
測試讀到改到一半的檔」。**那是猜的,不是我查到的**——真正的原因是另一個 session 在提交時
`git add` 了同一個檔,把我未提交的兩席斷言夾帶上主線,造成「測試要求兩席、實作只有一席」。

同一天另一個 session 也栽在同一型上(它把「拿掉它重跑整套 0 條紅」寫成「所以構造不出來」,
被兩個審查席同時指出)。共同點是★把「我還沒查到」講成「事情就是這樣」★。

**收束成一句**:沒查出方法 ≠ 沒有方法;想不到原因 ≠ 原因不存在。**寫的時候要用前者的措辭。**

## 三席之外還有一刀(2026-09-08 下午,另一 session 的實測回饋)

我這輪只調了「模型」跟「推理強度」兩個旋鈕。另一個 session 同日跑了一輪真的代碼審,
回饋一個我沒想到的限制:

**外家席跑在唯讀沙盒裡,建不了暫存檔,所以它造不出現場、跑不了實驗。**
它的報告會全部標「讀碼推論,未實跑」。

那一輪的實際結果:六條裡兩條 blocker **實測全中**——推理是對的。但有一條 major
**它高估了**:它說無上限掃描會把看門狗耗死,編排者實際把檔案養到 68MB 跑起來只要
0.9 秒,而那個檔每天只長 1KB。

**★處置:席位跑不動實驗時,它的 severity 要當成「待查證」不是「已成立」★**,
而查證的成本會落在編排者身上——那是一筆沒被算進來的成本。

**候選(未做)**:給 code 席一個可寫的沙箱。效益可能比再調高一階推理強度更大——
因為推理強度買的是「想得更深」,可寫沙箱買的是「講得出來的能自己驗」,後者才是
把「待查證」變成「已成立」的那一步。
