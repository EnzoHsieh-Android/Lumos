# 2026-10-23_Android驗證收據第零階段試跑

白話:在實驗室 App 上注入已知的變慢(清單每列忙等 8ms),照 [[Projects/Android診斷證據接入_調研]] 第零階段走一次:錄 Trace、照官方 skill 分析、手寫收據、派沒脈絡的 Agent 只靠收據重跑;另加兩項 Enzo 當天要求的:沒脈絡的 Agent 只拿 Trace 能不能還原注入的錯,以及能不能指到哪一行。結論:流程跑得通、收據可重現、行號指得到;收據要補的欄位寫進 [[Projects/Android逐層診斷_計劃]]〈收據格式補強〉。

## 怎麼跑的

- 裝置 SM-X710(實體、未 root、Android 16),USB、`svc power stayon usb`;裝置上的 APK 雜湊與建置產物逐一比對相符。
- 滑動基準 `ScrollBenchmark#scrollList`,5 輪、CompilationMode.None;正常版與 `-e bindDelayMs 8` 各跑一次。收據在 macrobench-lab 的 `.lumos/receipts/android-20261023-scroll-bind8/`(manifest、report、49 條查詢);原始 Trace 只留本機 `.lumos/artifacts/`,記雜湊。
- `lumos macrobench` 比對報 3 項變慢:frameDurationCpuMs P90 4.3→10.4、frameOverrunMs P50 -3.5→-1.1、P90 -0.9→3.6(跨零)。

## 結果

1. 官方 triage(子代理照 triage.md):主嫌是主執行緒 `obtainView`,iter000 共 148 次 1151ms、最大 8.32ms,CPU 1150.6ms 對牆鐘 1151.1ms;基準 153 次 39ms。RenderThread、binder、LMK 無差異;溫度無資料 [GAP]。
2. 收據稽核(沒脈絡的 Agent,只給收據目錄與調研三節):檔案雜湊全符;核心數字全部重現一致;要自己補腳本才跑得完,「3 項變慢」那句沒有可重跑的來源。
3. 稽核抓到的 `cpuLocked` 差異(基準 true、候選 false):查 benchmark-common 1.4.1 `CpuInfo.isCpuLocked`,是依各核目前最低頻率猜的;順序反過來重跑兩邊都是 true。結論:未 root 裝置上會自己翻的雜訊,要記但不判成條件不等價。
4. 量測腳本缺陷:第二輪起清單停在底部、沒有真的捲(iter002–004 `obtainView` 0 次),只看總數字看不出來;修成每輪先殺行程(macrobench-lab a9848d3),重跑後 5 輪畫格數都約 1000。
5. 盲測還原(沒脈絡的 Agent,只拿修好後的兩組 Trace 與官方 skill,跑完 Step 1–4、三個候選並行深挖):判出「`obtainView` 裡、`calculateBounds` 之前約 8ms 的 Java 迴圈,在等時鐘走滿」;證據是頻率升 3 倍時長幾乎不變、結束點對齊整毫秒、被 GC 打斷 1.5ms 總長不變。行號標 [GAP]。限制:候選目錄名 `bind8` 洩露線索。
6. 指到行號:
   - Perfetto traced_perf(`cpu_profile`,1000Hz):主執行緒 1654 個樣本停在 `__kernel_clock_gettime`,全部 `unwind_error=invalid_map`,上不去;另有大量 kernel 緩衝溢出丟樣本(頻率太高)。
   - simpleperf 預設 DWARF 堆疊(`-g`):同樣斷在 vdso。
   - simpleperf `--call-graph fp`:接回 `getView`(鏈:clock_gettime ← systemTime ← uptimeMillis ← RowAdapter.getView),2215 個樣本。
   - 加 `setprop debug.generate-debug-info true` 與 `cmd package compile -f -m speed` 後,odex 帶 `.debug_line`;`annotate.py` 標出 `MainActivity.kt` 第 36 行 `busyWait(bindDelayMs)` 佔 86.6%,第 37 行 0.04%。
   - 跑完已還原:`setprop` 清空、`cmd package compile --reset`。
7. 調研草案的證據標籤 `[MEASURED]` 與官方不符;官方 skill 用 `[SQL]`/`[INFERRED]`/`[GAP]`。

## L3 試跑(同日,Enzo 裁「記憶體先試查一下」)

- s05 情境重現 30 秒,同時錄 `heap_profile --heaps com.android.art` 10 秒:取樣到的配置約 267MB,99.9% 經 `RowAdapter.getView` → `churn`。

## 不涵蓋

- 注入的忙等在 Trace 上非常明顯;真實退步通常更模糊,這次不證明真實案例也找得到。
- 只有一台 Samsung;vdso 斷堆疊與 `cpuLocked` 行為可能因廠牌而異。
- L3(記憶體)只在實驗室 App 試過一次(Enzo 同日裁),真實專案要先有保存規則。
