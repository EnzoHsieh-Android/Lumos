# 2026-08-22_指令索引與情境探針

> 白話:為了讓 Claude 不再跳過 lumos 直接 grep,建了一套按情境分類的指令索引、改寫注進 CLAUDE.md 的規則、再用「模擬情境看它會不會自己敲」驗收。結果 20 個情境 19 個自己敲對了。

## 做了什麼
- `skills/lumos-project-notes/commands/`:總目錄 `INDEX.md`(4.2k 字元,含「grep 衝動對照表」12 列)+ 八個子檔(19k,每次只開一個)。80 個子指令與八個父指令的二層子指令全部歸位。
- 測試 `t_command_index_complete`:從 argparse 取子指令全集,斷言每個都出現在索引;總目錄 ≤4.5k;每個子檔都被總目錄指到。新加指令忘了寫「什麼時候用」會紅。
- CLAUDE.md 注入範本重寫:「圖譜先行」段改成對照表(9 列)+ 指向 INDEX;全文白話;長度 6.6k→6.3k。本 repo 已 `lumos update --no-pull` 重新注入。
- `lumos-project-notes` SKILL.md:description 改成以「你正要 grep 去理解既有系統」為觸發;常用指令段改為索引指引+六條最常用。其他四份 skill 的 description 全改白話、加觸發情境。
- 情境探針 `scripts/scenario_probe.py` + `governance/scenarios/commands.jsonl`(20 題,涵蓋八類中的六類;安裝維運與自動跑的兩類不適合模擬):複製工作樹到臨時目錄,headless `claude -p` 跑情境,抓工具呼叫順序,判「期望的 lumos 指令出現在任何 grep/Read 之前」。

## 結果(2026-08-22,預設模型,max-turns 8)
- 第一輪 15/20;5 個沒過裡 3 個是儀器問題(副本用 git clone 只帶已 commit 的東西,剛寫的筆記不在,Claude 真的找不到才退到 grep)→ 儀器改成 rsync 工作樹。
- 真漏 2 個:「push 了看 CI」敲 `gh run list`(索引與範本都沒列 ci-wait/ci-status)→ 補列;「要不要過審」六輪內還在摸 git remote → 輪數放寬到 8。
- 第二輪重跑 5 題:4 過。唯一沒過的「建驗證紀錄」是副本裡已經有同名紀錄,Claude 讀到就沒再建(正確行為),情境失效。
- 合計 19/20。15 個「過」裡有 9 個第一動作是調用 skill(description 的觸發句有效),其餘直接敲 `lumos search/query/spec-trace/ci-wait`。
- 原始紀錄:`governance/scenarios/run-2026-08-22.json`、`run-2026-08-22-rerun.json`。

## 沒做 / 限制
- 只探 20 個代表情境,不是 80 個指令各一題;安裝維運(07)與 hook 自動跑(08)兩類本來就不該由 Claude 主動敲,沒設題。
- 探針每題 20 秒到 5 分鐘、吃真 token;適合改規則後抽查,不適合進 pre-push。
- 一次跑的結果有隨機性,19/20 是單次量測,不是保證。

## 第二組:換句話說的變體(Enzo 裁「要測相似情境會不會自動調用,不是綁特定詞句」)

- 第一輪 10/12。沒過的:①「直接改,不用解釋」→ 直接 Grep + Edit,圖譜一眼沒看(正是 Enzo 描述的破口);②「valid_under 欄位要填什麼」→ 調 skill 後讀 skill 參考文件——那是對的來源,題目出錯,換成問「某篇的前提條件還成立嗎」。
