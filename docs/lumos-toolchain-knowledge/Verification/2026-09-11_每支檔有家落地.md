# 2026-09-11_每支檔有家落地

> 白話：「每支檔有家」這道檢查照計劃做完、測過；在真實消費專案上跑還沒做（下一步整理三個 POS 圖譜時做）。

## 驗了什麼

- **測試**：新增測試函式 54 支（其中 t_nodehome_* 42 支、健檢那組 t_doctor_nodehome_* 5 支；另有一支既有的清單一致性測試改名成 t_code_exts_lists_agree）；計劃列的九個子集共 230 項檢查全過（計劃 39 條驗收條款綁了 36 條測試、3 條靠人）。
  - 數法（2026-09-11 代碼審第二輪折完後機械重數）：對主線（接上最新主線後是 eb947850）比測試函式名集合；跑計劃「驗收怎麼跑」列的子集、把每個子集的通過數加總。原本寫的 34 支／146 項是沒機械數的，代碼審整合席抓到。
- **代碼審第一輪的修正**：改行為的 10 條都先寫測試、修前翻紅再修；另外補測試（事故筆記帶 --code，實作本來就對）、測試改名、改說明（複製出來的檔那條，另釘一支測試，修前就綠——那條只改說明不改行為）、寫明兩套推送範圍的理由、重數本篇數字，各一條。
- **代碼審第二輪的修正**：六條都是小問題；改行為的 3 條（設定檔所在資料夾是捷徑、寫回失敗訊息印兩次、`--diff ""` 講錯原因）先寫測試、在沒修的那一版上確認翻紅再修——其中資料夾捷徑那條第一次寫的測試情境放錯檔名、修前修後都沒碰到問題，改對情境後修前讀到外面的「關掉」、修後退預設。
- **殺傷力**：51 種故意把程式改壞的寫法（先 19、再 6、4、6、13+2，最後推送前逐提交看那 1 種；照七份突變清單機械數）逐一跑對應測試，全部被抓到——第二輪有兩種第一次沒抓到，查出是測試情境寫錯（起點剛好是目前 checkout、改名偵測配到別支同內容的檔），修正情境後都抓到。
- **速度**（本工具鏈 65 篇節點，2026-09-11 量）：`lumos home check --staged` 0.65 秒；`--diff` 1 個提交 0.75 秒、10 個提交 0.81 秒。改之前推送前兩側各讀全部節點，第二輪審查員量到 2.3 秒。
- **在本工具鏈自己的圖譜上跑健檢**：沒有家的程式檔 43 支、用反引號寫了別人家檔名的節點 25 篇、管超過 3 支檔沒寫負責範圍的 2 篇——都是上線前的舊帳，只提醒。
- **既有測試的調整**：推送前不再呼叫以反引號為種子的點名（原本那支測試改成斷言不呼叫）；提交前「格式乾淨的節點要放行」那支在測試專案裡關掉新檢查（它只驗格式那道）；提交前同步點名那支改成用 about_code 宣告家來表達同一件事。
- **第一次在消費專案真的推送**（2026-09-11，三個 POS 專案依序更新、整理、落外帶）：客人網頁與後端推送前檢查都「新違規 0 條」；平板那次被擋，查出是逐提交看寫回時內容有沒有變卻拿整段頭尾比的漏洞（見計劃〈代碼審時對計劃的修訂〉），補測試修正後再推。
- **第一次真的提交與推送**（2026-09-11，推上遠端 3a59166c）：提交前那道在帳本提交時跑了，治理帳記「這次提交：新違規 0 條」；推送前那道把要推的範圍整段比過，記「這次推送：新違規 0 條」；CI 綠（GitHub Actions run 34608203780）。這次是從私有 clone 推的（原因見 [[Issues/code-loop-pass不能指定分支]]），那份 clone 的掛鉤指向它自己的新版掛鉤，所以跑的是這次改好的那兩道。
