# 2026-10-02_設計審後端未知狀態題小實驗

> 白話:想知道「逼作者在設計稿裡多回答四題(結果未知、失敗情境表、新舊版本並存、出事看得到嗎)」能不能讓設計稿擋住真實事故。拿兩件付款事故改寫成需求,一組照現況答題、一組多答四題,各寫三份,再請不知分組的評分代理打分。結果多答四題的那組只略好一點,沒過門檻;只有「所有能把單關掉的路徑都要經過付款確認」這一項明顯拉開。

## 怎麼做的

- 需求一:POS App 串金流做客掃 QR 付款,改寫自 POS 專案三件事故(輪詢回終態被當成已付、取碼失敗後再滑一次直接關單、改金額或換錢包後交易編號沒換)。
- 需求二:自助點餐機後端新增付款結果通知端點,改寫自點餐機專案一件事故(端點套了自家 API key 檢查,金流通知全被擋)。
- 需求只寫事故當時就知道的事實(金流文件的介面說明、現場操作、既有慣例),不寫答案。
- A 組作者拿到 pitfalls 現在對金流設計稿會印的五題;B 組多一節「失敗與未知狀態」四題。每組每份需求各 3 次,作者禁用工具。
- 評分標準在開跑前寫定;12 份設計稿按需求打散改成中性編號,兩位評分代理各評一份需求,不知道分組也不知道實驗目的。

## 結果

| 評分項 | A 組 | B 組 |
|---|---|---|
| 需求一 只有查單確認收到錢才關單 | 3 | 3 |
| 需求一 非成功結果維持未付、保留再查或作廢 | 2.5 | 3 |
| 需求一 失敗都復原狀態、所有關單路徑都經過付款確認 | 1.5 | 3 |
| 需求一 重來時換新交易編號或先作廢舊交易 | 3 | 3 |
| 需求一 取消時通知金流作廢 | 1.5 | 0.5 |
| 需求二 通知端點不套 API key、改驗簽章 | 3 | 3 |
| 需求二 有機制發現通知沒進來 | 3 | 3 |
| 需求二 重複或晚到的通知只關帳出單一次 | 3 | 3 |
| 需求二 核對金額與交易編號才標已付 | 2.5 | 3 |
| 合計 | 23 | 24.5 |

(每項滿分 3:三份各 1 分,部分算 0.5。)

## 結論與限制

- 照事先訂的判準不接線:B 組合計只多 1.5 分。
- 天花板效應很明顯:現行金流題加上目前的模型,已經會寫出事故的主要對策;這幾件事故真正的破口在實作(規則已知、只接到一半路徑),不在設計時沒想到。
- 「列出所有能推進到已完成的路徑、各自檢查什麼」這一句是唯一有訊號的題,但只有每組 3 份、而且是看到結果才挑出來的,不能當成已證明;要另做一次只測這一句的實驗。
- 評分不完全盲:B 組稿子多一個段落,評分代理看得出結構差異。
- 需求二「發現通知沒進來」那項的判準,在看過稿子之後多加了一句「只有每日對帳算部分」;六份都判「有」,這句沒有影響結果。
- 兩份需求都碰金流,現行金流題本來就會被觸發;「非金流的對外呼叫也該問」沒有測到。
- 材料(需求、評分標準、12 份設計稿、解盲對照)含另外兩個專案的事故細節,只留在當次會談的本機暫存區,刻意不進本 repo。
