# 2026-11-02_Android測試防竄改檢查實跑

> 白話:在一個真的 Android 專案上,故意做每一種「讓測試變得不會紅」的壞改動,看比對工具抓不抓得到;再拿它整段開發歷史跑一次,看平常的正常改動會被誤列多少。

公開摘要在 `governance/eval/results/android-test-guard-drill-20261102/`(去識別化);完整卷證在考場本機分支。

## 考場對照表([S21])

- 15 個壞改動各從考場同一個提交長出來(用暫存索引造提交,不碰考場工作目錄),**每一個都被對應規則抓到**(當時的規則;建置檔與 CI 的三個在代碼審 r4 縮範圍後不再列,見文末的縮範圍說明):加 `@Ignore`、刪測試、強斷言改弱、實際值換成常值、改預期值(單行、跨行字串、字串常值)、加沒斷言的測試、try/catch 沒 `fail()`、建置檔 `ignoreFailures`(Groovy 與 Kotlin 各一)、CI 加續行的 `-x test`、調大逾時、重錄基準圖、正式程式偵測 robolectric。
- 5 個正常改動**零候選**:新增有斷言的測試、本體不變只改測試名、測試原樣搬到另一支檔、整檔重新縮排、改正式程式碼。
- 同一次推送把閘設成 off 又加 `@Ignore`:照放寬前的 block 判、擋下;考場工作目錄的設定也改成 off 再判一次,寫出 `relax-deferred` 帳與提醒(判完已還原工作目錄)。

## 真實歷史與誤報([S22])

- develop 全部 776 個非合併提交逐一跟上一個提交比(第一個提交跟空樹比):44 條候選、落在 27 個提交、0 個錯誤,全部 46 秒、單次最慢 0.15 秒。
- 裁定:**作弊樣 0 條、合理改動 42 條、規則判錯 2 條(4.5%)**。合理改動都是提交說明載明的需求或契約變更(功能改版、輸出格式改、對外契約改版、砍掉沒人用的功能)。
- 方法照實講:抽看了 5 條的實際差異(兩條規則判錯都是看差異判的),其餘 39 條依提交說明判,沒有逐條看差異。
- 兩條規則判錯:
  - `tq/unparsable`:一支新增的測試輔助檔,原始碼裡寫了一個真的 NUL 字元當字元常值,被當成解析不了。**不收窄**:條款 [S11] 要含 NUL 的檔列成這條(NUL 通常是二進位檔或編碼壞掉),一年多的歷史只出現一次、新增檔放行一次就好。
  - `tq/assert-weakened`:六個 `assertTrue` 改寫成一個迴圈逐項檢查,靜態數字從 7 變 2,檢查內容其實沒變少。**不收窄**:靜態判讀分不出迴圈裡跑幾次,收窄等於放掉「真的刪斷言」;同一條規則另一條候選(把 `isEqualTo` 改成 `isNotEqualTo`、強斷言搬到兄弟測試)判讀正確。
- 兩條判讀正確但改動合理的例子,適合寫進放行理由的範例:強斷言搬到新增的兄弟測試;「不可拋例外」型測試本來就沒有斷言。

## Semgrep 自比規則([S17])

- 合成樣本逐檔跑(不帶前綴的五種與 Java 的 `is`,另加帶類別前綴的四種):Kotlin 與 Java 每一種都列到,`assertThat(f()).isEqualTo(3)`、`assertEquals(3, f())` 這類正常斷言不列;`--strict` 沒有錯誤。
- 第一版只加不帶前綴的樣式,帶前綴的 `Assert.assertEquals(x, x)`、`MatcherAssert.assertThat(x, equalTo(x))` 一條都抓不到;改成每種另加 `$Q.` 前綴版才抓到(記在 [[Systems/test-quality-multilang]] 的 PITFALL)。
- 在考場跑 `lumos test-quality scan --semgrep`(四份合成樣本加考場測試目錄):99 支檔(97 支 Kotlin、2 支 Java)都掃到、報告完整;22 條候選,21 條是合成樣本(等於逐檔掃描的 6+7+4+4)、1 條是上一輪演練故意放的自比壞測試——**考場真實測試沒有其他誤報**,上一輪「Kotlin 靜態掃描沒跑」那條回頭條件可以結案。第一次在考場跑時漏放 Java 帶前綴那份樣本(只有 17 條),代碼審 r1 合約席指出後補跑。
- 收證工具掃描的測試照樣全綠(`scripts/test_test_quality_scan.py` 28 支)。
