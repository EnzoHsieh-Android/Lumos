# 2026-08-14_跨session傳訊互動視窗實測

驗證一個先前被誤判的問題：跨 session 傳訊在**互動式視窗**能不能用。

先前 [[Projects/子代理續談調研]] 的結論是「互動 session 不可用」。那個結論成立，但**範圍只到「續問一個已經結束的子代理」**——那條路需要磁碟上的子代理逐字稿，而互動 session 不落地，所以必敗。本測要問的是另一件事：對一個**還在跑的 peer session** 傳訊，吃不吃同一個限制。

## 步驟與結果

1. **列 peer**：`ListAgents` 於互動式主對話中列出同機兩個互動 session（分別閒置 19 小時、1 天），非本 session 派出的子代理。→ 尋址面在互動環境**可用**。
2. **送訊**：`SendMessage` 送給閒置 1 天的那個 peer，內容為連通性測試（要求只回專案目錄＋約定字串、明令不得動任何檔案）。→ 當下即回 `success`，並標明投遞對象是 "another Claude session on this machine"。與續談失敗時「當下就報找不到 transcript」形成直接對照。
3. **收回覆**：約 1 分鐘內收到 `<cross-session-message>`，內容為對方專案目錄與約定字串，並主動聲明未動檔案。→ **對方在無人操作那個視窗的情況下自行醒來處理**，雙向通。

## 結論

- 互動式 session 之間傳訊**可用**，且能喚醒閒置 peer，不需要人在那頭。
- 這與子代理續談是兩套機制，先前的「互動不可用」不可外推到本場景。
- 對方**遵守了訊息裡的行為限制**（未動檔案）——單次觀察，不足以當保證。

## 未涵蓋

- 跨機器 / 雲端 session 未驗。
- 送給**已結束**的 session 會怎樣未驗。
- 反向注入面未驗：本 session 面對外來訊息的戒心強度沒有測。
- 回覆延遲只有一次觀察（約 1 分鐘），不構成延遲特性的結論。

## 風險發現（非本測目的，順帶觀察到）

peer 回覆的標頭帶 `from-mode="bypass"`，代表那個 session 跑在跳過權限確認的模式。合起來看：**同機存在一條「本 session 被閘擋下的動作，改請 peer 執行」的路徑**。工具說明本身明文禁止這樣用，但那是自律層，不是機制層的阻擋。治理側該不該把這條當威脅模型處理，見 [[Projects/跨session傳訊用途調研]]。
