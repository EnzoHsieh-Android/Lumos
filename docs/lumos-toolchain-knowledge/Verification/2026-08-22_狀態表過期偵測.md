# 2026-08-22_狀態表過期偵測

> 白話:一篇筆記用表格記進度,某一格寫著「待辦」,但那格連到的節點早就做完了。
> 現在 `lumos context` / `show` 在頭部就喊出來。**Enzo 定義的症狀:「查詢時斷言太早」。**

## 真實案例(這篇存在的理由)

2026-08-22:[[Projects/收斂機制優化調研2026-08-14]] 的候選狀態表寫「③ 建議升優先」,
而它指的 [[Projects/收斂閘殘餘估計降級_計劃]] **同一天就 status:done 交付完畢**
(S1-S4 全落地,含席位重疊報表)。

讀表的人照表回報「四個候選一個都沒動」——★四項裡兩項半是錯的★。
**看帳會得到與事實相反的結論**,而且沒有任何東西會喊。

## ★判準怎麼定的(先量再定,不是拍腦袋)★

全 vault(329 篇)實測兩版:

| 判準 | 命中 | 品質 |
|---|---|---|
| 同一行有待辦詞 + 連到已完成 | **28 處** | 抽驗三分之一是誤報——長 KEY 行裡夾著「未做」兩字;「B 可機械未做」是判準名稱的一部分 |
| **表格行 + 待辦詞獨佔一整格 + 連到已完成** | **1 處** | 正是上面那個真案例 |

**收窄後零誤報。** 誤報的代價不是「多看一眼」,是**變成背景噪音**——本 repo 有現成教訓:
某個提醒閘喊了 18,283 次、落在 42 個節點、平均每個被念 400+ 次,結論是
「會響但不收斂的閘等同沒有閘」。所以寧可窄到只剩真陽性。

## 落點為什麼是 context 不是 doctor

★病發生在「讀那篇的當下」,不是收工的時候。★ doctor 是巡檢,救不了「查詢時斷言太早」。
提示印在 `context` 頭部(meta 之後、valid_under 之前),`--brief` 也照印——
**摘要模式恰恰是最容易只讀表格就下結論的模式**。

## 測試(5 條,先紅後綠)

正例 2 條(有喊、喊對節點)+ ★反例 3 條★:
指向未完成的那格不喊 / 待辦詞夾在長句裡不算 / 散文行不算。
翻紅釘:把判準放寬回「同一行含待辦詞」→ 後兩條反例翻紅。

## 誠實缺口

- **只認表格**。同型的病寫成清單(`- [ ] ③ 待放行 見 [[X]]`)抓不到。
  ★沒擴大的理由★:清單行的誤報率沒量過,而 28 處那版已經示範了放寬的代價。
  **重啟條件:出現一次「清單寫待辦但目標已完成」害人下錯結論的實例。**
- **只認固定那幾個詞**(待辦/待裁/待放行/待處理/未做/還沒做/尚未/未動/沒做/TODO)。
  寫「暫緩」「擱置」「觀望」抓不到。同上,沒實例就不擴。
- **反方向不管**:表格說「已完成」但目標還在 doing——沒實例,不做。
- ★這道提示解決的是「表格與節點狀態打架」這一種,不是「斷言太早」的全部。★
  同日試過另外三個更廣的機械判準,**全部量到不成立**:
  ①「搜尋 0 筆才提醒」——當天四次錯誤沒有一次是 0 筆(實測 243 次工具呼叫中,
    命中不佳 4 次、事後都有繼續查,一次都不會響);
  ②「跨節點狀態一致性」——散文表格讀不出結構,退而求其次的 updated 比較在本案例
    兩篇同一天、比不出來;
  ③「否定斷言 + 這輪查證少」——實測 31 個回覆帶否定斷言,其中最可疑的六筆全是
    查證後正確的結論。**假陽性遠多於真陽性。**
  三個都留在這裡,免得下一個人重試一遍。
