# 2026-09-12 Java 補棧：合成樣本測試

> 白話：這篇只證明「照設計補的 Java 題組、測試掃描和慣例 skill 對應，在我自己造的小 repo 上會動」。它**不**證明真的 Java 專案接得上——那要等第一個真專案。而且這次比 Python 那次還弱一層：本機連 Maven／Gradle 都沒有，linter 那一半是純文件。

## 跑了什麼

| 測試 | 斷言 | 驗什麼 |
|---|---|---|
| t_java_profile_discovery（新） | 8 | JUnit5 `@Test void`、參數化 `@ValueSource(ints = {1,2,3})`、JUnit4 `@Test public void` 三種都掃得到；沒標註的 `void makeSut()` 不收；註解裡的假測試剝掉；profile 的副檔名只有 `.java`；`init` 對 `.java` 猜到 `java-junit`、符號 profile 借 kotlin 且「猜得很弱」旗標關掉；骨架指令帶得動單支測試 |
| t_java_stack_wiring（新） | 9 | java 七題存在；`.java` 派 java-idioms、效能題鍵是 `java`；改主程式附七題、測試檔不附；**後端改動（`repo.findAll()`）只讓 java-data 適用、不問 Android**；**Android 改動（`findViewById`）只讓 java-android 適用、不問交易邊界**；架構對齊附 java-idioms；java-idioms 真的有 SKILL.md |
| t_stack_question_triggers（擴充） | 51 | 全表 id 集合加七個 java id；java 命中（`CompletableFuture.allOf`）／不命中（純算術）樣本 |

## 寫測試時踩到的一個既有設計

驗「平台特有題各自獨立」時，第一版把 Android 的樣本寫進**同一支檔**去覆蓋前一版的 JPA 程式碼，結果兩題都亮。原因不是 bug：**被刪掉的那行也算改動行**（「純刪除的 diff 也要觸發」是刻意的既有設計，有自己的測試釘著）。所以樣本改成另開一支檔才驗得到。這件事寫進測試的註解裡了，避免下一個人又踩。

## 這篇不能證明什麼

- 真 Java 專案接得上：零消費端。
- 七題的觸發字抓得準：只在合成樣本上試過，沒有真 diff 的誤報／漏報數據。
- linter 那一半：Error Prone／SpotBugs／PMD 都要 Maven 或 Gradle，本機兩個都沒裝，**一條都沒實跑過**。

## 代碼審 r1 之後補的一段（2026-09-12）

這篇原本只證明「接線會動」。代碼審七席之後，多了一組**證明它守得住壞情況**的斷言——而那些壞情況在 r1 之前是真的會發生的：

| 新斷言 | 修之前實測 |
|---|---|
| 帶字串的註解不會讓真測試消失，字串裡的字也不會被當成方法名 | 真測試 `realTargetMethod` 完全掃不到，反而多出一個從字串裡抓來的 `run` |
| `@Test` 被當成另一個註解型別的組成部分時，不會把後面的方法當測試 | 會抓到隔壁類別的 `setUp` 並當成有效證據 |
| `@Test` 標在非 void 方法上，不會改抓到後面無關的方法 | 會抓到 `unrelatedHelperFarBelow` |
| 中文方法名收得到 | 整支消失 |
| 兩萬個配不到目標的註解要在 2 秒內掃完（Java 與 Kotlin 各一條） | Java 10.4 秒、Kotlin 11.3 秒；席位在 1MB 的檔上量到 43 秒 |
| Spring 的 `ApplicationContext` 不會被誤問 Android 題 | 會同時亮 java-data 與 java-android |

**這一段才是這批東西真正的防線**：原本那些「接線會動」的斷言，在有這些洞的版本上一樣全綠。
