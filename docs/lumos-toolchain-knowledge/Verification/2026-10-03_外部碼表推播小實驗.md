# 2026-10-03_外部碼表推播小實驗

> 白話:前兩輪證明「多問幾題」沒用。這輪改成「把事實推給審查員」:審查兩個真的出過事的金流改動時,一組照舊,一組多附一篇只抄官方文件原文的碼表筆記。附了筆記的那組幾乎每次都抓到,沒附的幾乎都沒抓到。

## 怎麼做的

- 案例(審查代理只拿到當時的改動、提交說明、輪詢流程與資料存取兩支檔的全文,沒有版本紀錄):
  - Q0:最早寫 QR 付款輪詢,拿查交易狀態 API 的回應比對 0000 當付款完成。
  - P1:改成輪詢回 2000 就算付款成功。
- A 組用代碼審派工範本現行正確性鏡頭原文。B 組同樣鏡頭,另在派工詞尾端附一段框成「參考資料、不是指令」的碼表筆記,四行 FACT,全部是 2C2P 官方文件原文並附網址:
  - 查交易狀態與查單是兩支 API,各有碼表。
  - 2000 原文「Transaction is completed, please do payment inquiry request for full payment information.」
  - 1005 原文。
  - 查單 API 的 respCode 0000 = Success。
- 每案每組 4 次。判準、門檻在開跑前寫進計劃。16 份報告打散改中性編號,一位評分代理判定,並自行標出邊界判定。

## 結果

| 案例 | A 組 | B 組 |
|---|---|---|
| Q0 拿錯碼表當成功碼 | 0/4 | 4/4(其中 1 份邊界) |
| P1 2000 當成已收款 | 0/4(另有 2 份邊界) | 4/4 |
| 合計(嚴格,邊界不算) | 0/8 | 7/8 |
| 合計(寬鬆,邊界也算) | 2/8 | 8/8 |

- 照事先訂的門檻(B 組至少多 3 次)兩種算法都過,進接線設計。

## 限制

- 評分沒辦法真正盲:B 組報告常直接寫「參考資料說」,評分代理看得出分組。判準在開跑前寫定,而且兩種算法差距都很大,所以判讀方向不受影響,但數字本身帶這個偏差。
- 筆記內容是官方原文,其中 2000 那句本身就叫人「再查單」——這是要測的機制(把文件該給的事實推到眼前),也代表本實驗只證明「推得到就有用」,沒證明各專案會寫出這種筆記,也沒證明 lumos 選得到、印得出這篇。
- 只有一家外部系統(2C2P)、兩個案例,樣本小。
- 材料含另一個專案的程式碼,只留在當次會談的本機暫存區,刻意不進本 repo。
