# 2026-09-07_loop-list開著的迴圈

> 白話:以前要知道「現在有哪些審查迴圈開著」,只能去 tail 一個日誌檔的最後一行,
> 或看 git 有哪些沒提交的審查報告資料夾——因為問下一步、問過不過、問審到哪,
> **三個指令全都強制要先給編號,卻沒有任何入口能先拿到編號**。現在有了:`lumos loop list`。

## 為什麼做這個

[[Projects/執行DAG_調研]] 查完世界與自家之後,**七條外家炮火打完唯一還站著、而且成本明確的一件事**就是這個缺口(外家獨立複核過:`loop` 四份 help 確實沒有這個入口;`canary-stats` 不帶編號雖會列全歷史,但不判開著沒開著)。

★刻意不做的事★:**沒有新增任何要人維護的狀態**。關門訊號取的是治理帳裡**本來就會寫**的放行事件——那份帳在閘過的當下自己會落,是可重算的。這正是該調研的成敗條件(「不能從證據重算的狀態就不要做」)。

## 關門是怎麼判的

- **關門事件**=治理帳 `.governance-log.jsonl` 裡這五種:`design-loop` 的 converged / cap-reached / rewrite、`code-loop` 的 passed / skipped;事件的 `nodes` 欄帶迴圈編號。
- **開著**=沒有關門事件,**或關門後又記了新的審查輪次**(後者是真實情境:放行後被打回重審)。
- **在飛 vs 空轉**:預設只列 14 天內有動的;超過門檻又沒關門的另外歸「空轉候選」,`--stale` 看。
- ★誠實界線(寫進輸出本身)★:關門事件這個慣例 **2026-08-22** 才開始(治理帳第一筆 `design-loop converged` 的日子),更早的迴圈天生沒有這一筆。所以工具只敢說「帳面沒看到關門事件」,**不說「沒做完」**。

`t_loop_list_open_loops`(18 條斷言),涵蓋:空帳仍 rc0 / 列出沒關門的 / 已關門的不列 / **code-loop 的放行事件同樣算關門** / **關門後又記新輪次要重新算開著** / 久沒動的落到空轉桶 / `--days` 調門檻後回到在飛 / 每筆帶最後活動日與距今天數與輪數 / `--exclude` 前綴排除 / **人讀輸出必須自己講明誠實界線並印出下一步指令** / 壞行跳過但不靜默且仍 rc0。

## 交付前自己找出來的兩個問題(送審之前先修掉的)

1. **★時間是拿字串在比大小的★**。兩本帳今天全部寫 `+08:00`(當場數過:審查帳 1101 筆、治理帳 26443 筆,無一例外),所以字串比對**剛好**會對——但那是巧合不是保證。只要有一筆從別的時區或 UTC 寫進來,就會**靜默**把開著判成關了或反過來。修法=加一層 `_loop_ts_key` / `_loop_ts_newer`,兩邊都解得動就比 UTC 秒數、否則退回字串比對(舊帳相容);★沒帶時區的一律不猜★(猜錯比退回字串比對更糟)。釘死它的測試:關門事件寫 `03:00Z`(真實時間**晚於**審查那筆 `10:00+08:00`),但字串上 `T03 < T10`——只比字串會誤判成還開著。
2. **`--now` 給壞值會直接吐 Python 堆疊**。修成擋下訊息 + rc2。

★這兩個都不是審查員抓到的,是交付前自己過一遍會被審到的地方時找出來的。★

## 不涵蓋什麼

- **不判「這個迴圈該不該繼續」**——那是 `loop next` / `loop status` 的事,本指令只給編號。
- **不涵蓋 2026-08-22 之前的迴圈**(那時還沒有關門事件),它們一律落在空轉候選裡;**這不代表它們沒做完**。
- **空轉候選那 88 個沒有人去判過**——本次只把它們列出來,一件都沒處理。
- **`--exclude` 是每次呼叫要自己帶的**,沒有設定檔預設;要不要給 `auto-` 一個預設值沒量過,沒量之前不做。

## 代碼審 r1 折入(2026-09-07,另一個 session 當編排者)

這支交付出去之後過了一輪三席代碼審(通才 + 架構對齊 + 外家 Codex),**十條全折、零放行,其中五條 blocking**。
卷證:`governance/review-reports/code-batch12/`。

### 最重的一條:一半的關門訊號是死碼

原本把五種關門事件放同一個集合,用治理帳的 `nodes` 欄比對迴圈編號。
**但兩本帳認迴圈的方式不一樣**:
- 設計審那組把編號寫進 `nodes`(109 筆全部有)。
- **code-loop 那組的 `nodes` 永遠是空陣列**(148 筆全空)——因為那本帳認的是「分支 + 版本」,
  跟審查帳的編號從來沒建過對應關係。

後果不是理論上的:**實測 23 個早就過閘的 code 迴圈被報成「空轉候選」**
(`code-234` / `code-kill` / `code-cochange` …),而且會永遠卡在那裡。

★這正是這支工具存在的理由反過來製造的噪音★——它要解的痛點是「先知道有哪些編號在飛」,
結果它自己把已經飛完的報成還在飛。

### 為什麼測試沒抓到

測試的 fixture **手刻 JSONL,而且刻的形狀現實中不存在**:對 code-loop 也塞了 `nodes: [編號]`。
同檔既有測試寫這兩本帳都是**真的呼叫指令**。繞過真寫入端,就驗不到格式對不對得上。

### 折入之後

- 兩組分開認:設計審比對 `nodes`;code-loop 從自由文字 `detail` 認編號。
  ★明寫這是啟發式,不是保證★(`detail` 是人寫的,沒有機制強制它帶編號),
  失效方向偏保守(認不到就報成沒關門,不會反過來誤報成關了)。
  正解是讓那支指令收一個 `--loop` 參數把編號寫進 `nodes`,那要動到推送閘的路徑,掛回頭條件。
- **★「關門後又記帳」不等於「重開」★**:這是修完第一條才浮出來的。實測**過閘之後才補記帳是常態**
  (`code-234` 唯一那筆記錄比過閘晚 8 分鐘、`code-kill` 晚 14 分鐘),原本的判定把它們算成「又開新輪」。
  改成超過 24 小時才算重開。★那個門檻是拍的不是量出來的★,已掛回頭條件。
- **合法 JSON 但不是物件的行**(`[]`、`null`、`42`)原本會讓整支炸掉,違反自己承諾的「壞行跳過」。
- **`--exclude ""` 改成擋下**:任何字串都以空字串開頭,原本會把清單排空,而印出來跟「全部結案」一模一樣。
- **輪次混用時不吐精確數字**(其他指令對混用是直接擋下,這支是唯讀查詢不該擋,但也不該假裝算得準)。
- **新增漂移守衛**:治理帳裡出現過的每一組事件都必須被歸類過(算關門 / 明確不算),
  而且表裡列的種類都要真的在帳上出現過。**四個沙盤全部驗過翻紅、還原全綠。**
