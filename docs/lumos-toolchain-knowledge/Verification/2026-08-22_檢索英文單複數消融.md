# 2026-08-22_檢索英文單複數消融

> 白話:想讓查 `token` 也找得到寫成 `tokens` 的地方。**寫了、量了、變差了、撤了。**
> 這篇是負結論即交付,同 [[Verification/2026-07-28_PPR邊權消融]] 的處理方式。

## 症狀(真實發生過一次)

2026-08-22 查「成本記帳有沒有做」,`grep -nE "elapsed|duration|token|cost"` 掃 `scripts/lumos`
——`token` 的命中全是 `_rank_tokenize`,**真正的欄名是複數 `--tokens`**,一個都沒撈到。
據此下了「我們缺這個功能」的結論,**事實是欄位早就在、只是零筆填過**。
(該次的完整脈絡見 [[Verification/2026-08-22_成本欄接上與撤除兩階段]])

## 做法

`_rank_tokenize` 的 ASCII 段補「去尾 s」的形式(**加不是取代**),文件端與查詢端跑同一支,
兩邊都補就對得上。保守四條:①原形保留 ②只砍尾 s 不碰 es(`notes` 去 es 會變 `not`)
③`ss` 結尾不砍(`class`→`clas` 是假詞)④長度 <4 不砍(`is`/`as` 砍了全是雜訊)。

單元測試 6 條先紅後綠(含三條反例:ss 不砍、太短不砍、中文不受影響)。

## ★消融結果:撤回★

同一釘定語料(snapshot=9fcb761)、同一 goldset、train split,只差這段 code:

| | 改動前 | 改動後 | 差 |
|---|---|---|---|
| search nDCG@5 | 0.8046 | 0.8039 | **-0.0007(噪音級,等於沒動)** |
| edit P@8 (fusion) | **0.6667** | **0.631** | **-0.036(-5.4%)** |

**search 面完全沒有受益,edit 面掉了。** 推測原因:去尾 s 產生的詞進了索引,
稀釋精準匹配;edit 面(impact hook 推薦)吃檔名/路徑匹配較重,對噪音更敏感。

### ★2026-08-22 當日訂正:上面那個 -5.4% 不可解讀★

另一個 session(乾淨脈絡,只讀 code 不讀我的結論)指出:計分的 `_labels_of` 把
`final=None` **當 0**,而候選池是 goldset 建檔當時從系統自己的 top-12 抓的——
**任何讓新節點浮上來的改動,新節點都沒標過、都被計 0,改動一定被罰。**

★口徑陷阱(第一版訂正用錯口徑,一併記下)★:第一次驗時直接呼叫 `collect_unjudged`,
用的是**現況 vault**(330 篇),算出 33→38;但 **eval 計分會先 `pin_snapshot` 把語料
釘回 goldset 建檔當時的 commit**(9fcb761)。兩個口徑的候選池完全不同,
**現況語料的數字不能拿來解釋釘定語料下的分數**。

正確口徑(釘定語料,即計分實際跑的狀態,用新加的 `--ablation` 閘量):

| | train 未標 | 閘 |
|---|---|---|
| 乾淨 code | **0** | 放行(rc 1,正常跑完) |
| 加回去尾 s | **4 個**(散在 E19、E20) | **擋下(rc 3)** |

**改動讓 4 個新節點浮上來,4 個全部沒標過、全部計 0。**
edit train 有效題 6 × k=8 = 分母 48 —— **4 個強制零分足以解釋整個 -0.036**。

★結論方向不變,但第一版寫的「5 個 / 33→38」作廢★——那是現況語料口徑。
**我差點用錯的口徑得出對的結論**,這種「碰巧對」比錯更危險,所以留痕。

★所以正確結論是「這次量測不可解讀」,不是「改動有害」。★
**撤回的決定維持**(search 面 0 提升,仍然沒有證據說它有益);**但理由改寫**。

原寫的「有微弱證據有害」★作廢★——那個證據來自尺的偏置,不是改動的效果。

### ★這不是本案的問題,是尺的結構性偏見★

候選池釘在建檔當時的 top-12,於是:**改善檢索 = 浮出新節點 = 踩未標地雷 = 被扣分**。
**這把尺對「改善」有系統性偏見**,不只單複數這一案。
處置排程見 [[Projects/檢索優化_計劃]](清廢題 → 未標偏置 → 換主指標 → 加題)。

## 未試的另一種修法(★重啟條件寫在這裡★)

污染來自**文件端索引**。理論上可以只做**查詢端擴展**(查 `token` 時另找 `tokens`),
文件索引不動,就不會稀釋。

**本次沒試**,理由:`_rank_tokenize` 是文件端與查詢端共用的單一實作,要拆得動呼叫方,
工程量明顯大於本案症狀的份量(症狀=1 次,且該次的真正損失是「下錯結論」而非「找不到」)。

★重啟條件★:再出現 **2 次**可追溯到「英文單複數對不上」的錯誤結論 → 值得做查詢端擴展。
屆時務必仍以本篇的 train split 對照為基線(0.8046 / 0.6667)。

## 這次量測本身的一個坑

歷史帳 `governance/eval/retrieval-eval-history.jsonl` 最後幾筆都是 **held** split,
**沒有可比的 train 基線**。基線是把改動暫時移除、重跑一次現場量的
(移除後先斷言 `_rank_tokenize('tokens')==['tokens']` 確認真的回到改動前才跑,
不靠「我以為我移乾淨了」)。

★下次做同型消融要記得★:先確認 history 裡有同 split 的基線,沒有就得自己跑一次對照,
不要拿不同 split 的數字比。
