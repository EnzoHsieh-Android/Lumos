# 2026-09-05_wrapper邊跑邊改實驗

一句話:**bash 是「邊讀邊跑」的——腳本在跑的時候被改檔,它會從舊的 byte 位置接著讀新檔。** 這篇用三個小實驗把「包進 main() 就沒事」這句話量清楚:對一半、漏一半。

## 為什麼要做
2026-09-05 09:30 的每日治理 wrapper(daily-governance.sh)死在自主迴圈那段回來之後:我在它跑的三小時內改了這支腳本,bash 回來讀到半行 `syntax error near ')'`,lint-watch / doctor / testmap 整天沒跑。第一版修法是「整段包進 main() 最後才呼叫」,註解寫「先整份讀完再執行」——代碼審 r1 三席(通才、架構對齊、外家 Codex)加我自己的實驗,發現這句話有兩處不準。

## 實驗一:main() 結尾沒有 exit,會怎樣
- 做法:一支 `main(){ echo step1; sleep 2; echo step2; }` 加結尾 `main "$@"`,啟動 0.5 秒後在 main() 前面插入約 300 字元的註解(檔案變長)。
- 結果:**step1/step2 各印了兩次**,中間夾一行 `command not found`。原因:main 跑完,bash 回到結尾那行之後的 byte 位置繼續讀;檔案變長了,那個位置現在落在 main() 定義中間,於是把 main() 又「讀到」並再呼叫一次。
- 換成同一行 `main "$@"; exit`:只印一次,rc 0。因為 bash 一次讀一整行,exit 已經在手上,main 回來就直接離開,不再碰檔案。
- 結論:**exit 不是裝飾,是必要的**;放在下一行也沒用(下一行還要再讀檔)。

## 實驗二:main() 之前的前奏窗口有多長
- 做法:前奏照真檔(set / DIR / ts() / mkdir),進 main() 第一行印從啟動到此刻的毫秒數,跑三次。
- 結果:35.8 / 35.9 / 35.9 毫秒。
- 結論:前奏那幾行仍是逐行讀,窗口存在,但是**幾十毫秒對三小時**——事故那種暴露基本消失。註解改成這樣寫,不再說「整份先讀完」。

## 實驗三:守衛測試對四種壞檔會不會翻紅(先紅後綠)
把真測試 `t_daily_governance_wrapper_is_function_wrapped` 複製到乾淨目錄,餵四種改壞的 wrapper:

| 壞法 | 誰提的 | 結果 |
|---|---|---|
| 在 `}` 和結尾呼叫之間塞一行子腳本呼叫 | 通才席 R1 | 翻紅(1 條斷言) |
| 刪掉 lint-watch 整步 | 通才席 R2 | 翻紅(五步名冊斷言) |
| 空殼 main():主體全搬回頂層、只留收尾 echo | Codex X1 | 翻紅(3 條斷言) |
| 結尾少了 `; exit` | 我(實驗一) | 翻紅(2 條斷言) |
| 原檔 | — | 8 條全綠 |

第一版測試只比三個字串,前三種都假綠——就是 [[Systems/測試假綠形態]] 說的第④型「測試存在但沒在驗它宣稱要驗的」,第 17 次。

## 這篇沒涵蓋
- 只測了「原地覆寫變長」;「寫暫存檔再 rename 覆蓋」那種編輯器行為,bash 拿的是舊 inode,理論上不受影響,沒實測。
- 沒測 zsh / dash;wrapper 明寫 `#!/bin/bash`。
