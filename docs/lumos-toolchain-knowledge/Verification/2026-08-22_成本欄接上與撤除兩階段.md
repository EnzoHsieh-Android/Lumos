# 2026-08-22_成本欄接上與撤除兩階段

> 白話:兩個 session 對審一整輪的交付。**三件都不是新機制,全是「既有的東西沒接上」**——
> 成本欄建好零筆填過、撤除 hook 一刀刪炸掉正在跑的 session、測試卡死看不出卡在哪。

## 一、成本欄接上(可觀測性)

**起點**:外界「graph engineering」編組那派的六條清單裡,我們唯一缺可觀測性(耗時/token 成本)。
**★但「缺」的說法是錯的★**:`canary record` 的 `--tokens` / `--wallclock-min` 兩個欄早就在,
實查 `docs/.canary-log.jsonl` **兩欄都是零筆**。不是缺欄位,是缺填欄位的人。

同型病今天撞到三次:kill 配方零條、check-s 喊 18,283 次落在 42 個節點沒人看、成本欄零筆。
**機制在、沒人用——比機制沒建難發現,因為表面上一切都有。**

**做法(填不建)**:

- `governance/autonomous_loop/orchestrator_result.py` 加 `extract_cost` / `cost_cli_args`。
  `claude -p --output-format json` 頂層本來就吐 `total_cost_usd` / `duration_ms` /
  `num_turns` / `usage`,**一直沒人接**。
- `governance/autonomous-loop.sh` 在解析 orchestrator 輸出那段接上:log 一行人話 +
  `canary record none --loop auto-<日期>` 帶兩個成本欄。fail-open 與 `run_probe`/`run_nags`
  同款,抽不到只 log 一句、不影響 loop。
- 兩份派席 skill 的記帳樣板加上那兩個參數。

**★fail-open 但不靜默★**(hook 提醒帶出 [[Issues/canary-record未落盤事件]] 才補的):
記帳失敗不擋 loop,但 rc 不能吞。那次事故是三筆 record **回報成功卻沒落盤**,靠外審清點
原始帳才發現;結案時已在 record 加寫後讀回自驗、驗不到回 rc2。**這裡若寫 `|| true` 把 rc
吞掉,等於重新製造同一個靜默窗口**——所以改成判 rc、失敗 log 一行「算出來了但沒落帳」。

**★tokens 只算 input+output,不含 cache_read★**——快取讀取計價差一個量級,加進去會把
「這輪多貴」灌水;cache_read 另存一欄供日後分析。

**消費者只有一個(寫不出消費者就是裝飾)**:Enzo 在週報看「本週自主 loop + 派席共花 $X、Y 小時」,
據以決定砍週抽題數或把某 tier 席數降一級。**沒有 dashboard、沒有 per-gate 成本表。**

**退場**:三個月內那行數字沒導致任何一次砍題/降 tier 的決定 → 停填,欄位留著。
重啟=有人要拿成本裁某個 loop 存廢而拿不出數字。

## 二、★撤除 hook 改兩階段★(發布相容期)

**症狀是真的發生過,不是理論**:`lumos install` 把已撤除 hook 的真檔刪掉,但**正在跑的
session** 在啟動當下讀進的 settings 快照還註冊著那支——檔案不在了,那些 session 每次觸發
都報錯。2026-08-22 有人為此手寫空殼補回去**兩次**(每跑一次 install 就被刪一次)。

**根因**:撤除是一刀切,沒有相容期。**這是「工具鏈自己沒有發布流程」的具體代價**——
版本號寫死 v1.0 從沒 bump,消費端無法釘版也無法回滾,所以連「上一版留著、下一版才刪」
這種最基本的相容期都表達不出來。

**修法**:`_RETIRED_CLAUDE_HOOKS` 拆成兩組。

| 階段 | 常數 | 行為 |
|---|---|---|
| 一(相容期) | `_RETIRED_STUB_CLAUDE_HOOKS` | 換成 `exit 0` 空殼,**不刪檔**;舊 session 照樣觸發、什麼都不做、不報錯 |
| 二(過期) | `_RETIRED_CLAUDE_HOOKS` | 真刪殘留檔 |

撤新的 hook:先進 STUB,下一版移到 DELETE。teardown 兩組都清(拆機後不該留我方任何檔)。

## 三、測試 runner 加 per-test 超時

**症狀**:全套跑到某支會卡死——CPU 只走 3 秒、牆鐘走 7 分鐘,得人工 kill 整輪,而且
看不出卡在哪一支。一輪 10 分鐘的套件卡住一次等於整輪報廢。

**修法**:`run_with_timeout` 用 SIGALRM(單進程、零依賴);預設 180 秒,`LUMOS_TEST_TIMEOUT`
可調,0=不設限。沒有 SIGALRM 的平台自動退回不設限,行為與加這條之前完全一致。

### ★上限要先校準,不然閘會變裝飾★(對審時另一個 session 打出來的)

原本直接定 180 秒。它的反假紅:**先量最慢那支現在跑多久,確認有 ≥3 倍餘裕**——CI 機器比
開發機慢,最慢那支若吃掉大半上限,CI 上就會假紅,而假紅的下一步永遠是有人把
`LUMOS_TEST_TIMEOUT` 設 0 繞過,閘就變裝飾。

量了(2026-08-22 本機,runner 順手加了「最慢 5 支 + 餘裕倍數」):

| 測試 | 耗時 | 180s 下的餘裕 |
|---|---|---|
| `t_ci_wait` | **132.3s** | **1.4x ⚠** |
| `t_every_subcommand_has_when` | 25.8s | 7x |
| `t_slim_gate` | 18.3s | 10x |
| `t_m2_cluster_gate` | 17.1s | 10x |
| `t_guard_kill_attribution` | 9.2s | 20x |

**它的擔心命中了**:最慢那支只有 1.4 倍餘裕。

**但修法不是把全域上限拉高**——那會讓真的卡死也要等到那個上限才被打斷,等於把偵測能力
送掉(它今天卡的那次是 7 分鐘,全域拉到 600s 就抓不到)。改成 per-test 覆寫:
`TIMEOUT_OVERRIDE = {"t_ci_wait": 450}`(餘裕 3.4x),**其餘維持 180s——次慢的 25.8s
還有 7 倍餘裕**。

配一條守衛測試:**覆寫表的名字必須真的存在於 `t_` 名單**。改名後覆寫會靜默失效,那支
回到 180s 被誤殺,而誤殺長得跟「真的卡死」一模一樣,是最難查的一種紅。

**★超時判紅,不判 skip★**:沒跑完就是沒驗過。判 skip 會讓消費 rc 的 pre-push/CI 把
「沒驗」當「驗過」——這個 repo 已為同型假綠付過代價(`-k` 選中 0 個也判紅)。

### 沒做的那半,以及為什麼

原本要把 `testmap affected` 接進 runner 做「只跑受影響測試」。**實查後不做**:
`testmap affected` 的粒度是**檔案級**(答案是「跑 scripts/test_lumos.py」),而那支正是
那個 10 分鐘的怪物——接上去等於沒接。要有價值得先讓 testmap 做到**函式級**,那是新工作
不是接線。

另外:runner **早就有 `-k <關鍵字>`** 只跑名稱含該字串的測試(對審時另一個 session 以為
沒有)。日常開發用 `-k` 就夠,不需要新入口。

## 誠實缺口

- **成本欄現在還是空的**。管線接好了,第一筆真數據要等下一輪自主迴圈跑完。在那之前它與
  「建了沒人填」只差一步。**重驗條件:2026-08-23 之後查 `docs/.canary-log.jsonl` 有沒有
  `tokens` 欄的筆數;還是零就是這次也白接。**
- **兩階段撤除沒有機械守衛逼人用**。下次撤 hook 的人可能直接加進 DELETE 組。
  重驗條件:下次有人撤 hook 時,看他有沒有先進 STUB。
- 版本號仍寫死 v1.0、消費端仍無法釘版/回滾——**這次只解了症狀(相容期),沒解根因(沒有發布流程)**。
