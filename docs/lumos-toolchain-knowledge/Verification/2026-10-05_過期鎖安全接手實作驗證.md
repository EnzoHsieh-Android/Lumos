# 2026-10-05_過期鎖安全接手實作驗證

## 目的與範圍

驗 [[Projects/過期鎖安全接手_計劃]] 的 S1–S5：既有鎖不能再按時間接手，正常建鎖、失敗清理、筆記庫與派工鏡頭的錯誤傳遞都要成立。S6 是切換實際安裝前的人工進場條件；本次只在隔離暫存目錄重現舊版與新版混用的不安全性，沒有操作使用者的真鎖、推送或部署。

## 方法與結果

- 舊實作先紅：用兩個不同 PID 與事件屏障固定「B 看過舊鎖、A 先換入新鎖、B 再按路徑搬鎖」；原版輸出兩者都取得。修後 `t_excl_lock_stale_takeover_is_single_owner` 拒絕接手，連同 S2、S3 的短寫、半成品清理、符號連結與錯誤分流，`python3.14 scripts/test_lumos.py -k excl_lock` 為 11 passed、0 failed。
- S4：`python3.14 scripts/test_lumos.py -k vault_stale_lock_fails_with_path` 驗殘留鎖等待上限與位置訊息、建鎖權限錯誤即時回報；既有 `-k vault_lock` 為 10 passed、0 failed，涵蓋正常釋放、可重入及不可信快取目錄退路。
- S5：`python3.14 scripts/test_lumos.py -k lens_stale_lock` 為 6 passed、0 failed，檢查舊鎖不再派第二支、狀態未知及建鎖失敗分流到 hook；`-k dispatch_lens_hook_timeout_notice` 為 5 passed、0 failed。`-k lens_timeout_keeps_warming_cache` 為 8 passed、0 failed，真的等背景程序寫完快取並清鎖。
- `python3 scripts/lumos spec-gate Projects/過期鎖安全接手_計劃`：6 條中 5 條測試綠、1 條人工條件，弱證據 0。這不等於 S6 已在實際安裝核可。
- S6 混版實驗：在隔離暫存目錄由新版建立鎖，再把 mtime 設成一小時前，讓基於 `619b4d1c` 的舊版在另一個 Python 程序呼叫同一原語；得到 `new_acquired=True` 與 `old_acquired=True`。故發布前必須停舊版程序並更新共用此鎖的安裝，不能把本案的同版單持有保證說成跨版本保證。

## 測試環境辨識

第一次跑背景暖快取整合測試時，隔離 clone 沒有本地 `main`，既有測試用 `git rev-parse main` 的非空標準輸出誤認它是提交，結果在測試進入鎖邏輯前就回 rc 2。已把測試改為 `rev-parse --verify <ref>^{commit}`，無本地主線時明確跳過。實驗過直接改用 `origin/main`，但鏡頭命令仍要求本地主線，實跑回 rc 4，所以沒有保留該備援。建立追蹤 `origin/main` 的本地 `main` 後，原整合測試 8 項全綠。這次假紅來自測試前提，不是本次鎖程式回歸。
