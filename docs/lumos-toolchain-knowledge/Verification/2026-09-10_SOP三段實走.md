# 2026-09-10 SOP 三段實走（PosTerminal）

> 白話：這篇證明「錄基準 → 改動 → 比對 → 重錄 → 還原」這一整套用腳本真的跑得起來，紅燈綠燈兩條路都走到了。跑在 PosTerminal 示範 app 上，不碰真店家資料。過程中撞到兩個值得寫進 SOP 的坑。

## 走了什麼（照 SOP 第 5 節）

| 步 | 做什麼 | 結果 |
|---|---|---|
| 錄基準 | `.maestro/visual-record.sh menu_main`（前置→拍→搬進 repo→99.9 連拍守衛） | 通過 |
| 改動 | 把購物車空提示加兩個字，重建（獨立 DerivedData）、裝上模擬器 | 畫面確實變了（見卷證 label_change_crop.png，下半有「點餐」） |
| 比對（本該紅） | `.maestro/visual-check.sh menu_main` | **綠**——相符 99.83%，見下方盲點 |
| 紅燈示範 | 丟棄式 flow 拿菜單基準去比「訂單」分頁 | **紅**——相符 94.40%，退出 1，證據三張圖齊全 |
| 跑版測試 | 三欄往右推 160pt 重建重裝，比對 | **紅**——相符 97.77%，diff 圖框出位移的整片商品格 |

| 還原 | `git checkout` 那一行、裝回原 app、基準圖蓋回原檔 | check 綠 |

## 兩個坑（都讓 SOP 更完整）

0. **版面破壞（跑版）抓得到，這正是它的強項。** 把三欄容器往右推 160pt，購物車被切掉一截，相符掉到 97.77%，紅。diff 圖把位移的商品格全框起來。跟小字改動對照著看最清楚：像素比對對「整塊位移／破圖」很敏感，對「差一個字」很遲鈍。

1. **小字改動躲得過門檻。** 加兩個字只動 0.17% 像素，門檻 99.5 放行。像素比對對「差一整塊」敏感，對「差一個字」遲鈍。**修法：文字關鍵的地方保留 `assertVisible "字串"`，跟截圖比對並用。** 這正好接上 Android 計劃那條「斷言重點是使用者看到什麼」。
2. **狀態列的「◀設定」回返鈕。** 從設定 app 叫起 app 時左上會多一顆返回膠囊，狀態列覆寫蓋不掉。基準圖要在乾淨啟動下錄。

## 門檻上緣

- iPad 同一畫面重跑：相符 99.913%。所以連拍守衛設 99.9 剛好在邊緣，設 99.99 會誤殺自己。
- Android 平板同一畫面：相符 ≥99.999，穩很多。
