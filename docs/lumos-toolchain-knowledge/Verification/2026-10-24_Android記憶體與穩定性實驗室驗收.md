# 2026-10-24_Android記憶體與穩定性實驗室驗收

白話:[[Projects/Android記憶體與穩定性驗收_計劃]] 的三條人驗條款(S17–S19)在測試專案 macrobench-lab 上走過一次:加了開關播放器畫面的情境(畫面裡建一個 Java SDK 與一個原生 SDK,關畫面時照參數決定要不要 release)、自己測自己的 UI Automator 驅動 `LeakCycleTest#cycle`、StrictMode VM 規則、`.lumos/macrobench.json` 的 stability 段與七條 check 門檻;每次用工具鏈的收集腳本跑(暖機 2 輪、量測 5 輪),再用 `lumos macrobench --stability` 判。

| 條款 | 情境 | 結果 |
|---|---|---|
| S17 | 正常版(兩個都 release) | 七項全過:原生沒人指著前後都 0、沒有類別增長、FakeJavaSdk 0 個、峰值 62 MB(上限 2.25 GB)、沒有結束紀錄、pid 沒變、沒有 StrictMode 違規、0 個凍結幀(最長阻塞 13ms、8 幀) |
| S18 | Java SDK 不 release | java_growth 沒過(FakeJavaSdk 多 5 個)、instances 沒過(7 個 > 上限 1);其餘照過 |
| S18 | 原生 SDK 不 release(.so 拿掉了符號,只剩兩個對外 JNI 函式名) | native_unreachable 沒過(多 10485760 位元組 5 塊 = 5 輪 × 2 MB);其餘照過 |
| S18 對照組 | App 快取一組 SDK 一直活著、其餘照常 release | 七項全過:instances 1 個 = 上限;原生沒人指著 0(活著握著原生記憶體不誤報) |
| S19 | 量測第 3 輪 am crash | exits 沒過(crash、pid 變了);需要完整 N 輪的五項列成跳過並寫「量測期間行程換過」 |

S18 的診斷(skill 的 L3):
- Java 那側:在 Java 漏法那次的第二份快照上照 heap_graph_reference 往回找,7 個 FakeJavaSdk 被一個 Object[] 指著,那個陣列屬於 ArrayList,ArrayList 是 SDK 自己的靜態欄位 `FakeJavaSdk.live`(SDK 內部追蹤活著的實例的清單)→ 物件被 SDK 的登記表留住,也就是沒呼叫 release。
- 原生那側:原生漏法下用 heapprofd(libc.malloc)錄 3 輪,沒釋放的 6 MB 全經過同一條呼叫鏈:`libfakesdk.so` 位移 0x744(函式名 `Java_com_example_mblab_sdk_FakeNativeSdk_nativeCreate`,對外公開所以拿掉符號也看得到)← `FakeNativeSdk.<init>` ← `PlayerActivity.onCreate`。
- 原本條款寫「App 哪一行呼叫的」,實際只到 App 的函式(`PlayerActivity.onCreate`),heapprofd 對 Java 那幾層只記函式不記行號(skill 的 L3 原本就寫明只到函式);代碼審 r1 整合席指出後,計劃 S18 與 skill 都改成「到 App 的函式」。

實機跑的過程抓到的缺陷(都已修並補測試):
- Perfetto 讀不到推到 `/data/local/tmp` 的錄製設定(errno 13)→ 改推到 `/data/misc/perfetto-configs/`。
- shell 對 perfetto 送 `kill -0` 回 Permission denied,錄製明明在跑卻判成提早結束 → 改用 ps 看在不在;`kill -TERM` 照樣有效。
- 宣告的類別在正常版兩份快照都沒有實例,被判成「拼錯或混淆」而跳過 → 改看快照裡的類別物件 `java.lang.Class<類別名>`,有它就算載入過、0 個。
- 收集腳本沒先停 App,上一次留下的物件算進這一次(原生漏法那次 instances 報 7 個)→ 開跑先 `am force-stop`,而且在讀前一次結束紀錄之前。
- 錄製開不起來時推上裝置的設定檔沒刪 → 開不起來也刪。
- run-id 有空白會壞掉裝置上的路徑(編排者在 zsh 下批次跑時把參數黏在一起)→ 收集腳本驗 run-id 字元。
- 中途崩潰後 App 被重啟,前後兩次量的是不同行程 → 行程換過時需要完整 N 輪的五項跳過。
