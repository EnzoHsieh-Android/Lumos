# 2026-11-15_改動選擇點真實Android端到端驗收

> 白話:[[Projects/改動選擇點都要有需求守住_計劃]] 合進主線後,第一次在真的 Gradle Android 專案把面試題那一行走完整圈——只綁送一次值的測試時判存活、推送前擋下;人裁補條款綁送兩次值的測試後判殺掉、推送不再因選擇點擋。另附在兩個真實 Kotlin 專案量的「選擇點涵蓋多少行」。

## S26 端到端(計劃〈驗收條款〉S26)

場地:測試品質實驗室 Android 副本(搜尋 ViewModel 逐一 import 版、`kotlin-junit` 平台、`./gradlew :app:testDebugUnitTest --offline --tests '*{method}'`),另複製一份跑,跑完刪。lumos 用主線 8994eab6f、ast-grep 0.51.2,`LUMOS_CHOICE_SINCE=2026-11-01`(計劃日期 2026-11-13 早於生效日 2026-11-16,推送那一道要覆寫生效日才會要求)。

改動:提交 A 把計劃〈驗收條款〉只留 S1(`oneQueryShowsItsResult`,只送一次值),`.flatMapLatest { flow { emit(search(it)) } }`;提交 B 改成 `.flatMapLatest { q -> flow { emit(search(q)) } }`。範圍 A..B 改到一行。

| 步驟 | 結果 | 耗時 |
|---|---|---|
| `lumos choice-points --diff A..B` | 那一行 C-28 API,壞法 `flatMapConcat`(補 import),狀態「沒跑」;改到 1、有選擇點 1、有壞法 1 | 2.7 秒 |
| `lumos choice-kill --diff A..B` | 1 個壞法 × 1 支測試:**存活**,rc 1;治理帳記 choice-kill 與 run | 17.5 秒(Gradle 熱) |
| 提交帳後 `spec-gate --push-check` | **擋下**:「選擇點 1 行沒有有效處置 — 存活 1 行」,附三種處置指令;治理帳記 blocked | — |
| `lumos situation-rule --point <檔>:20 --plan Projects/搜尋_計劃 --clause "當使用者連續輸入查詢,搜尋畫面 應 只顯示最後一次查詢的結果" --test onlyLatestQueryShown --consent …` | 隔離工作樹套壞法,`onlyLatestQueryShown` 紅 → **killed**;計劃寫回 S2,治理帳記人裁(帶 point)與 choice-kill killed(via situation-rule) | 7.6 秒(Gradle 熱) |
| 提交後 `choice-points` 與 `spec-gate --push-check` | 那一行「殺掉 by kotlin:onlyLatestQueryShown(Projects/搜尋_計劃#S2)」;推送前那一道不再因選擇點擋 | — |

- `--plan` 要寫 `Projects/搜尋_計劃`,只寫 `搜尋_計劃` 會 rc 2「找不到計劃」(訊息已指出寫法)。
- 這次沒單獨跑「先存活、補強測試後重跑 choice-kill 判殺掉」那條路;人裁路徑用的是同一套 `cmd_guard_kill` 零件。

## 選擇點涵蓋多少行(唯讀量測)

把兩個私有 Kotlin Android 專案的正式碼(略過 build、test、androidTest 目錄)整份當改動,用主線的 `configs/ast-grep/kotlin-choice/` 規則掃,扣掉乾節點範圍與含 ERROR 節點的行,算「有選擇點規則命中的行 ÷ 實質程式行(去掉空行、註解、import、package、單獨括號)」。這是近似:用節點起始行代替錨點行,不是 `choice-points` 指令的輸出。

| 專案 | kt 檔 | 實質程式行 | 有選擇點的行 | 節點數(依類別) |
|---|---|---|---|---|
| 私有專案甲 | 277 | 39834 | 5213(13.1%) | SBR 3467、UOI 1297、ROR 566、LCR 530、AOR 259、API 60 |
| 私有專案乙 | 63 | 5320 | 801(15.1%) | SBR 461、ROR 168、AOR 142、UOI 141、LCR 35、API 31 |

沒涵蓋的行(甲/乙):具名引數 `x = …` 36%/28%(多半是 Compose 參數與常數)、多行呼叫的參數行 20%/24%、`val`/`var` 指派 10%/13%、宣告 6%/7%、`when` 分支 6%/7%、註記 6%/5%、其他 14%/14%。

## 天花板

- 耗時是 Gradle daemon 與編譯快取都熱的情況;冷編譯沒量,計劃〈實務隱患〉要的「20 行改動實際耗時」仍缺。
- 只有一行一個壞法;多檔多壞法的批次行為只有單元測試(`t_choice_kill_batch`)。
- 涵蓋量測只用兩個專案、近似算法,不能代表 Android 專案的一般分布。
