# 2026-09-15_多詞題在主題庫量不到


## 一句話

**主題庫加不了中文多詞題——不是難，是結構上量不到。** 搜尋評測的兩臂都顯式要求「整串查詢當成一個片語、字要連在一起出現」，中文多詞查詢因此兩臂都回 0 個候選：沒有候選就沒有東西可標，題目進去只會被跳過。

## 量到什麼

用評測自己那兩臂實測（語料 521 篇，2026-09-15）：

| 查詢 | 舊排序臂 | 新排序臂 | 要標幾筆 |
|---|---|---|---|
| `合約 測試` | 0 | 0 | 0 |
| `快取 失效` | 0 | 0 | 0 |
| `回滾 不可逆` | 0 | 0 | 0 |
| `逾時 降級` | 0 | 0 | 0 |
| `合約 guard` | 0 | 0 | 0 |
| `guard kill` | 13 | 10 | 13 |
| `Check K` | 8 | 8 | 8 |
| `confused deputy` | 3 | 3 | 3 |

**現有那三題「多詞題」其實測的是片語比對，不是多詞檢索。** 它們是這個 repo 裡字面存在的詞組（一個子指令名、一個檢查名、一個資安術語），所以片語路徑撈得到。程式碼註解早就寫過這件事會發生，說「是還沒踩到，不是沒有，下次換題就會中」——這次換題就中了。

## 出題判準②（候選量不得超過全庫一成）卡錯了東西

那條判準是為了控制人要標幾筆。但標註成本的上限不是候選量，而是「計分觸及集」＝兩臂各取前十名去重，**最多 20 筆**，跟候選有幾百個無關。

實測最壞情況：查單字「的」，候選 505 篇（全庫 97%），**要標的只有 19 筆**。

所以判準②會把題目擋掉，而它要省的成本其實不存在。

## 中文多詞評測早就另有一套，而且還活著

姊妹計劃 2026-09-07 已明文裁過「評測另開一套、不進既有題庫」，理由跟這次量到的一模一樣（兩臂都固定關回退，塞進去兩臂都 0 候選、分母失義）。而那條裁定裡提到的那套，2026-08-03 就做好了：十題全中文多詞、雙評審標註完成、基線在案。

今天重跑它（要用扁平那份標註檔；另一份會讓它拋型別錯誤直接掛掉）：

```
python3 governance/eval/retrieval_eval_multiword.py \
  --labels governance/eval/multiword/mw-labels-flat.json \
  --pool governance/eval/multiword/mw-pool.json \
  --vault docs/lumos-toolchain-knowledge
```

**能跑，但這次跑出來的排序分數不能用。** 標註是語料只有 285 篇時做的，現在 521 篇，新增那 236 篇全都沒標、一律當成 0 分，分數被無標註的節點拖下去——排序品質從基線 0.767 掉到 0.388 **不是退步的證據**，是標註過期的證據。

**候選數那一欄跟標註無關，那個可以看**：同一題「合約 綁定 測試」的候選從 80 篇長到 450 篇（全庫 86%）。這正是「一個常見詞就把候選炸開」的症狀，也正是 [[Projects/檢索核心重建_計劃]] 要修的那件事。
