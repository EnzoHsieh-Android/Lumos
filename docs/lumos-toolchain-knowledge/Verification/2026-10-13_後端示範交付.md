## 流程實際跑出來的樣子

- **需求階段出題**:需求原文兩句話。`pitfalls --stage 需求` 只觸發 3 個需求風險面(成功的定義、本期範圍、重送),AI 把它們落成 8 題:4 題問需求方、3 題自答、1 題依量級自決;題目沒結之前規格閘確實擋著不讓進實作。
- **設計審**(高風險、5 席加架構對齊):一輪 34 條全折,包括「付款對逾時的驗收測試用同一個固定時鐘、測不到競態」——後來實作時拿掉付款的鎖,改寫過的測試真的抓到 200 張壞 3 張。
- **合約審計**:三輪都找到「綁定測試抓不到的壞法」,第三輪還找到一個真 bug(重送落在第一筆提交瞬間回 409)。第二輪後改加隨機操作測試(每步檢查不變式),審計員找到的壞法都抓得到;第 3 項「構造讓測試照過的壞法」沒有收斂終點,由需求方裁定收尾。
- **壓測**:原設計踩到計劃寫的撤除條件(賣完後的請求仍排隊搶鎖,P99 2.5 秒),需求方裁定加售完預查。
- **代碼審**:三輪。第一輪 26 條(4 條嚴重);第二輪精簡為 3 席,抓到的 5 條全是第一輪修補引入的;第三輪資安乾淨。

## 這次示範發現的 Lumos 改進候選

逐條都是實際操作時碰到的,要不要修見本節最後的回頭條件:

1. **需求風險面表偏薄**:搶購需求最關鍵的「量級多大」「同步還是排隊」「限購」都不是風險面表出的題,是 AI 自己補的;風險面表沒有「規模與量級」這一面。
2. **`lumos new project <名>` 不會補 `_計劃` 後綴**:照直覺打 `訂單下單` 建出的檔名不合慣例,要刪掉重建。
3. **設計審彙總記帳的條數限制容易誤會**:手冊說彙總那筆「彙整全輪 findings」,但 `--findings` 不能多於那一席自己報告的條數,全輪清單只能放在 `--findings-set`;照字面填會被擋。
4. **規格閘的金流關鍵字不看否定句**:計劃寫「不做退款」也被當成碰到金流、判風險高。
5. **`lumos guard kill-rm` 多帶一個位置參數時只印說明**:沒有錯誤訊息,看起來像成功。
6. **派工鏡頭的固定席跨 repo 算不出**:會談開在 lumos repo、審示範 repo 時,掛鉤附不上牽連筆記,只能手動跑 `lumos impact` 貼進派工詞(這是已知行為,但跨 repo 的示範幾乎一定會碰到)。
7. **合約審計第 3 項沒有收斂判準**:只要審計員肯重寫設計,永遠構造得出讓測試照過的壞法;現在只能靠人裁收尾。
