# 2026-11-06_Android情境題盲判實驗專案實跑

> 白話:在 Android 實驗專案的乾淨複本上,讓 AI 先寫一段兩支互不依賴呼叫的串行寫法,走一次推送前判定 → 照決策表改成並行 → 表態 → 派一個全新的盲判代理 → 再判定,看情境題整條路接不接得起來。結果:接得起來,情境題那一道最後放行;實跑發現兩處訊息問題,當場修掉。

## S8:實驗專案複本實跑

- 做法:實驗專案(`com.example.mblab`)用 git clone 取乾淨複本放在會談暫存區,把這個分支的 lumos 複製進複本的 `scripts/lumos`(消費專案的接法),`LUMOS_HOME` 指到這個工作樹讓它找到真型錄;每次判定都用推送前掛鉤那套 `code-loop check --diff <宣告後>..HEAD --keep-going --skip-bound-tests`(那個專案的合約測試要接實機,這次只看情境題那一道)。
- 第一步(AI 寫串行):`DashboardViewModel.open()` 在 `viewModelScope.launch` 裡先 `api.profile(userId)` 再 `api.notices()`。判定 9 秒,rc1,表態那一道擋下(還沒有表態紀錄);`pitfalls --diff` 切出 2 段(候選列 D-27;D-4、D-27),並印要跑盲判的四步指令。串行寫法本身沒有命中 D-1 的觸發字(`coroutineScope`),是靠 `viewModelScope.launch` 命中 D-4、D-27 才出段——D-1 這種「該寫卻沒寫」的情境要靠鄰列觸發,見計劃〈天花板〉第 3 條。
- 第二步(照決策表改):照 D-1 改成 `coroutineScope { async … await }`、照 D-8 把 try 包在 `coroutineScope` 外面、照 D-4 先 `loadJob?.cancel()`、照 D-27 改成單一 `DashboardUiState`。樣板 3 秒,切出 2 段 5 格(D-27;D-1、D-4、D-8、D-27),表態全答適用照標準寫法。判定 10 秒,rc1,擋下原因只剩「缺第一盲判 5 格」並印指令;D-27 在第二段的 evidence 指第 36 行,證據樣式對不上 → 只提醒、記帳。
- 第三步(盲判):`blind-judge --template` 3 秒,材料 12.8KB、2 段,不含任何表態內容(檢查過沒有 variant、evidence 與表態裡的行號);派一個全新的 sonnet 代理,派工詞只放材料(為了篇幅把每條對應檢查的網址清單拿掉,決策表 D-27 那列的來源網址留著),代理 0 次工具呼叫、約 6 秒交回 5 格全判適用且照做,理由都對得上程式(例:「先 loadJob?.cancel() 再把新的 launch 指派給 loadJob,符合命令式的標準寫法」)。寫入 rc0。
- 第四步:判定 11 秒,表態那一道放行(剩下的擋下是 tier=high 要代碼審留痕,跟這個實驗無關);`gov --stats` 印出 D-27 那則證據提醒「誤報 1」(盲判已判照做)。
- 整條路(不算代理)判定與指令合計約 40 秒;作者與盲判 5 格全一致,這次沒走到仲裁。

## 實跑發現、當場修掉的

- 盲判已判照做的那一格,證據提醒原本照寫「待盲判」,讀的人會以為還要再跑——改成標「盲判已判照做:多半是樣式誤報」(測試 `t_kt_situation_waive`)。
- 缺第一盲判的擋下訊息原本每一格各印一次段的位置,同一段四列就重複四次——改成一段一句列出缺的列(測試 `t_blind_judge_record_required`)。
