# 2026-09-03_派工攔截點實測

> 白話:[[Projects/impact鏡頭機械化_計劃]] 2026-08-29 停案,死因逐字是「派工發生在編排者的 agent 呼叫裡,**沒有任何 hook 攔得到**」,重開條件寫死=「先答出派工那一刻的機械強制點在哪——兩輪十席次沒有一席找得到」。★本篇實測答出來了:攔得到、看得到派工詞全文、也擋得住。★

## 實測怎麼做的

在 `~/.claude/settings.json` 的 `hooks.PreToolUse` **追加**一條 matcher 為 `Agent|Task|Subagent` 的 hook,指令只把 stdin 原封不動寫檔;然後派一個最小的子代理。重跑步驟與原始輸出在:

```
governance/eval/hook-intercept/
```

★測完設定已還原,並與備份逐欄比對確認完全相同(沒動到既有的三支 hook)。★

## 結果(Claude Code **2.1.259**,2026-09-03)

| 問題 | 答案 | 證據 |
|---|---|---|
| `PreToolUse` 匹配得到派子代理嗎 | ✅ 得到 | hook 收到的 JSON 中 `"tool_name":"Agent"` |
| 拿得到派工詞嗎 | ✅ 拿得到全文 | 派工詞裡埋哨兵 `SENTINEL-9f3a`,在 `tool_input.prompt` 逐字出現;另有 `description`/`subagent_type`/`model` |
| 擋得住嗎 | ✅ 擋得住 | 回 `permissionDecision:"deny"` → ★該次派工完全沒執行★,`permissionDecisionReason` 原文回饋給模型 |
| 會誤擋嗎 | ✅ 不會 | 對照組(不命中條件)照常派出、正常回覆 |
| `SubagentStart` 能用嗎 | ❌ 不能 | 它會 fire,但 input ★只有 `agent_id`/`agent_type`,沒有派工詞★——攔得到卻看不到內容,判不了該不該擋 |

## ★追測(同日):hook 不只能擋,還能改寫派工詞★

翻案後追加一組實測,問的是 `hookSpecificOutput.updatedInput` 這一格對派子代理有沒有效。

**做法**:hook 攔到帶哨兵的派工時,把一份「必查清單」(三個節點名)接在原派工詞後面回傳;
派出去的子代理被問「你收到的必查清單有哪幾項」。★派工詞本身一個節點名都沒提★,
所以它列得出來就只可能來自注入。

**結果**:子代理原封不動列出那三項(`Systems/lumos-cli-lifecycle` ★INVARIANT★、
`Systems/測試假綠形態` ★INVARIANT★、`Systems/reversibility-governance-ledger` ★RISK·守衛面★)。
✅ **`updatedInput` 對派子代理有效,可以機械改寫派工詞。**

### ★第一次測失敗,失敗本身是發現★

第一版把注入內容寫成「暗號是 PINEAPPLE-7742」,★子代理直接拒答★,回覆稱它認出這是提示注入測試。
換成長得像真實必查清單的內容才成功。兩條約束由此而來:

1. **注入內容必須看起來是正當的系統附加**——命令式、誘導式、或「暗號」這類形狀會被子代理當攻擊擋掉。
2. ★**這個機制與提示注入在技術上是同一件事**,差別只在善意★。同一個 hook 位置,惡意的人可以竄改
   任何子代理的派工詞。要落地的話,**該 hook 本身必須進錨點保護清單**(本 repo 已有該機制:
   驗證器檔案被動過就擋推送)。這一條是硬約束,不是提醒。

### 這一格為什麼比「擋」重要

原停案的設計是「派工詞沒附清單就擋下」。`updatedInput` 讓設計可以改成「沒附就直接塞進去」,
於是 ★該案唯一沒被推翻的那條裁定(2026-08-02:擋 high 抓不到 standard、擋 standard 逼人繞過)
整條不適用★——不擋就沒有繞過壓力。同日 [[Issues/推新分支時風險分級拿空樹當起點]] 量到的
「常態誤擋訓練人繞過」也一併消失。

## ★為什麼十席次會漏掉★

那兩輪審的是「`lumos` 這支 CLI 有沒有辦法攔」,結論是沒有——**那是對的**。
漏掉的是**往上一層看宿主**:攔截點不在我們的工具裡,在 Claude Code 的 hook 層。
★教訓:問「有沒有強制點」時,射程要含宿主平台,不能只掃自家工具。★
