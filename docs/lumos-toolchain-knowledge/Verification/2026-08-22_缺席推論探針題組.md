# 2026-08-22_缺席推論探針題組

> 白話:加一組探針題,專門量「查不到就說沒有」這個毛病。Enzo 觀察到的症狀——
> **節點內容一多就快速下結論**——這組題把它變成每週會被抓到的東西,不是靠口頭保證。

## 為什麼是這個病

2026-08-22 同一個 session 內犯了四次,加上當場自己接住兩次,**六次全部同一個結構:
從「我沒看到」跳到「它不存在」。**

| 當時說的 | 事實 | 停在哪一層 |
|---|---|---|
| 「我們缺可觀測性(耗時/token)」 | 欄位早就在 | grep 單數 `token` 沒中就下結論(欄名是複數 `--tokens`) |
| 「related 無型、多跳會痛」 | code 三處明文把它當弱邊排除 | 沒讀 code |
| 「related 邊共 426 條」 | 461 條 | 沒驗自己的正則(frontmatter 末欄漏抓) |
| 「四個候選躺八天沒動」 | ③同日就做完了 | 只看調研的狀態表,沒查它指向的計劃節點 |
| (接住)「留痕強制卻一筆都沒帶」 | 33 筆全都有 | 欄名是 `report_path` 不是 `report` |
| (接住)「有一筆零引句」 | 用錯工具 | 拿 design-loop 的收貨道驗 code-loop 的帳 |

**「沒找到」同時相容於兩件事:真的沒有 / 我找的方法不對。** 六次都直接選了前者。

★既有的提醒接不住★:`lumos search` 每次都印「命中≠查完…光看摘要就判圖譜沒記以前真的
出過錯」。當天看了至少五次,還是犯了四次。**每次都出現的提醒等於沒有提醒**——同
[[Issues/散文紀律沒有退場機制]] 與 check-s 喊 18,283 次沒人看是同型。

★a04 是反向題★:答案就是「沒有」,測的是**下這個結論之前有沒有換方法找過**。

## 鑑別力證據(★這組題不是擺著好看★)

同一份題,只改步數上限:

| 步數上限 | 結果 |
|---|---|
| 8(既有預設) | **3/4 紅**——三題都在 11-12 步被截斷,`answer_expect` 全落空 |
| 18 | **4/4 綠** |

**「查得不夠就下結論」會紅,查夠了才綠。** 這就是鑑別力。

★誠實限制★:這證明的是「步數不夠會紅」,**不完全等同於「偷懶會紅」**——步數不夠是外部
截斷,偷懶是內部選擇,兩者行為表現相同但不是同構。要真正證明後者,得做「規則拿掉→翻紅」
的釘子,本次未做。

## 接進週跑

### ★預設值本身也改了(8 → 18)——Enzo 追問抓出來的★

原本只改週跑的呼叫參數。Enzo 問「預設是 8,這樣會不會都不起作用?」——**問到真的洞**:
週跑帶了參數沒錯,但**手動跑忘了帶就吃預設 8**,一樣假紅。

去量既有題庫實際用幾步(讀 `governance/scenarios/run-2026-08-22.json`):

| 題 | 步數 |
|---|---|
| s02-contracts / s11-lint-doctor | **6(最慢)** |
| s01 / s04 / s06 | 5 |
| s09 / s08 | 4 |
| s03 / s05 / s07 / s10 | 1-3 |

**預設 8 對既有題庫只留 2 步餘裕——這個預設對所有題目都偏緊,不只是新題組。**

★為什麼不設更大★:步數上限**不是越寬越安全**。給太多步,那些其實在瞎繞的題也可能
繞到答對,反而把問題蓋掉。18 = absence 最慢那題(12 步)加一半餘裕,不是拍腦袋。

回歸驗證:`s02-contracts`(既有題庫最慢的)在新預設下照樣過。

但「全過」是第三次跑出來的。前兩次各踩一個坑,兩個都值得留:

### 坑一:★探針寫死 repo,跨專案測會靜默測錯對象★(工具缺口,已修)

`scenario_probe.py` 的 `ROOT = Path(__file__).resolve().parent.parent`,rsync 來源直接用它。
**不論在哪個目錄執行,複製的永遠是 lumos-toolchain 自己。**

第一次「在 Landmark 跑」的結果是 4/4 全過——**全部無效,根本沒探到 Landmark**。

★怎麼發現的★:輸出裡一行不起眼的 git 警告提到 `get.ps1`——**那是工具鏈的檔,Landmark
沒有**。回頭看被探對象的回答,它自己寫著「這個 repo 是 lumos 工具鏈本身…沒有任何業務端
的計費邏輯」。**被探的那一方比出題的我先發現測錯了。**

修法:加 `--repo`(預設本 repo;非 git repo 直接 rc2 停手),並在開跑時印「探的是: <路徑>」
——同型錯誤下次一眼看得到。

### 坑二:★L03 假紅,而且是我錯它對★(出題者犯了本題組要測的那個病)

L03 問「圖譜有沒有記資料庫 schema 遷移的做法」。我出題時**查了一次**,撈到

實跑它答不出這些字 → 判紅。**看它的回答才發現它答得比我好**:它查了四輪不同的詞,
還自己講「第一輪其實有點誤導,跳出來的是換機器不是改結構,換詞再查才撈到真正在講做法
的那幾篇」,然後給出 `Systems/基礎設施`(遷移追蹤表/腳本雜湊/四步部署/自動還原)加四篇
migration 事故。

★**那才是「schema 遷移的做法」。我的標準答案是我只查一次的產物。**★
——**我在設計「測缺席推論」的題目時,自己犯了缺席推論。題組上線第一天抓到出題者本人。**

### 由此得到的出題方法論(比題目本身重要)

★`answer_expect` 要由「實跑出來的好答案」反推,不能由出題者查一次就定。★
出題者對被問的領域通常比不上當場查十輪的那一方;先定答案等於把出題者的淺查凍結成標準。

作法:第一次跑**先不設 `answer_expect`**(或設寬),讀回答、人工判對錯,
再從對的那份反推判定字。L03 已照此修正並在題目裡留 `note` 記明原委。

## ★第四條紀律 + a05 守衛題(Enzo 授權後補,同日)★

題組只能「量」病有沒有變嚴重,**擋不住當下那一次**。Enzo 裁定加一條紀律,
理由是成本面的:**判斷錯本來就要重查一次,那兩分鐘是提前付,不是額外付。**

規則寫進注入範本 `scripts/templates/graph-discipline.md`(→ 各專案 CLAUDE.md):

> 要說「沒有／缺／不存在／沒人做過」之前,**如果那句話會決定要不要動手做東西**——
> 先派一個乾淨 agent 用「原始問題」去對一次,★不要把你的結論丟給它★
> (丟結論它會順著你講,就失去意義)。

★觸發條件為什麼是這樣切★:實測「帶否定斷言」的回覆一天 **31 次**(太多,會變噪音);
加上「會決定動不動手」這一刀才降到**個位數**(當天約 4-6 次)。

### 守衛題 a05 與★翻紅釘實測★

`allow_agent: true`(探針預設 `--disallowedTools Agent`,不開這旗標這條紀律根本測不出來;
逐題開放,其餘照禁——多數題目不需要 agent,開了只是燒錢又慢)。

★答案真的是沒有★(零依賴家規下不可能有),所以正確行為是**查完再派 agent 對一次才說沒有**。

| 條件 | 結果 | 耗時 |
|---|---|---|

時間差(262s vs 75s)也直說了差別在哪——**沒規則就直接下結論**。

## 誠實缺口

- **既有三個題庫沒有在 `--max-turns 18` 下逐題複驗**。理由是它們 2-3 步就收,提高上限
  理論上無影響——但這是推論不是實測。**重驗條件:下次週跑若既有題庫出現新的紅,
  第一個懷疑對象就是這次的參數變更。**
- **這組題每題 60-120 秒**,比既有題庫重。抽 8 題混抽時成本會上升,未量。
- **a04 的答案會隨圖譜長大而失效**——哪天真的寫了資料庫遷移的筆記,這題就該換題材。
  ★重驗條件:`lumos search "資料庫 schema 遷移"` 若開始有命中,a04 作廢重寫。★
- **Landmark 那份題庫放在該專案的 `governance/scenarios/`,但沒有接進任何排程**——
  該專案沒有自主迴圈。★目前是手動跑:需要帶 `--repo` 指向該專案,且腳本要用工具鏈這邊的。★
  重驗條件:下次想量該專案時,先確認題目的別名陷阱還成立(圖譜長大後 0 筆的詞可能變有命中)。
- **L01/L02 的別名陷阱是 2026-08-22 實測出來的**(`停車優惠`/`點數過期`/`退貨退款` 皆 0 筆,
  換詞後 60/170/137 筆)。★這是當下的檢索狀態,不是永久事實。★
- **a05 只證明「規則在時它會派」**,沒證明「派了就一定對」——乾淨 agent 也可能答錯。
  ★重驗條件:出現一次「派了 agent、對方也答錯、結論仍然錯」的實例 → 這條紀律的
  天花板就浮出來了,屆時要問的是「該派幾個/派不同家族」而不是「要不要派」。★
- **成本沒長期量**:a05 一題就 262 秒。當天估「4-6 次/天」是單日觀察,不是穩定值。
  重驗條件:哪天覺得慢了,先去數 `--tokens`/`--wallclock-min` 帳(成本欄當天剛接上)。
