# 2026-10-02_代碼審完成路徑一句小實驗

> 白話:第一輪看到「列出所有能推到已完成的路徑」這句好像有用,這輪改在代碼審單獨測它。拿四個真的引發過事故的改動給審查代理看,一組照現在的問句,一組多這一句。結果兩組抓到的次數一樣。沒人抓到的那兩案,缺的不是問法,是程式碼裡看不到的事實。

## 怎麼做的

- 案例(審查代理只拿到當時的改動、提交說明與相關檔案全文,沒有版本紀錄):
  - P1:POS 把 QR 付款成功判斷改成輪詢回 2000(4 行改動)。
  - P2:POS 加上「付款進行中就跳過付款分支」的防重入條件。
  - P3:POS 替換付款方式那條路徑抽出收款判斷規則,主付款流程沒跟著改。
  - L1:本 repo 收工檢查加上圖譜同步點名;它判斷「有沒有改程式」只看編輯工具紀錄。
- A 組用派工範本現行正確性鏡頭原文;B 組只多一行「完成路徑」。每案每組 2 次。
- 判準與門檻在開跑前寫進計劃。16 份報告打散改中性編號,一位評分代理依判準判定。

## 結果

| 案例 | A 組 | B 組 |
|---|---|---|
| P1 輪詢 2000 當已付 | 0/2 | 0/2 |
| P2 進行中旗標卡住後直接關帳 | 2/2 | 2/2 |
| P3 主流程沒套新規則 | 1/2(寫在補充段,邊界) | 1/2 |
| L1 看不到 Bash 改檔 | 0/2 | 0/2 |
| 合計 | 3/8 | 3/8 |

## 結論與限制

- 照事先訂的門檻不接線:B 組沒有多抓到。
- P1 的四份報告都接受「2000 等於付款完成」,只去質疑另一個碼;L1 的四份都沒想到改檔多半走 Bash。這兩件事都不在程式碼裡,是外部 API 的語意與本 repo 的實際使用情形——問句再多也問不出來,要靠圖譜把這類事實寫成規則或事故筆記推到審查員眼前。
- 評分時判準多補了兩句「什麼不算」(P1 只質疑 0000 不算、L1 只講 lumos 指令改筆記不算),是看過報告後才補的;它們沒有放寬原判準,但仍屬事後補充。
- 評分不完全盲:有一份 B 組報告用了「完成路徑盤點」當標題。
- 樣本小(每格 2 次),只能看方向。
- 材料含另一個專案的程式碼,只留在當次會談的本機暫存區,刻意不進本 repo。
