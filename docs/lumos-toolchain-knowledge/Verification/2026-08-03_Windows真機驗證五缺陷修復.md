# 2026-08-03 Windows 真機驗證五缺陷修復

> ★★本篇的 ① 修法（加 BOM）已於同日被真機**回歸測試**推翻★★
> BOM 只是把問題從「磁碟執行」搬到「`irm | iex`」，而後者正是 README 唯一教的入口。
> **現行做法是 ASCII-only + 不加 BOM**，見 [[Verification/2026-08-03_Windows回歸測試三缺陷]]。
> 本篇其餘四條（②③④⑤）仍然有效。**本篇原文保留不改**——它記錄的是當時做了什麼決定。

## 一句話

**三支 `.ps1` 開頭都寫著「沒有在真機 Windows 上跑過」——這次兌現了，而且 README 教的一行安裝指令在所有非西歐語系 Windows 上 100% 失敗。**

## 修了什麼

| | 缺陷 | 嚴重度 |
|---|---|---|
| ① | `.ps1` 無 BOM → 中文 Windows parser error，**什麼都沒裝** | **BLOCKER** |
| ② | 安裝失敗卻回報 `$LASTEXITCODE = 0` | **BLOCKER** |
| ③ | `return $LASTEXITCODE` 實際回傳 `Object[]` | MAJOR |
| ④ | 卸載撞唯讀 pack 檔，`.lumos-slim` **刪到一半**、把使用者鎖死 | MAJOR |
| ⑤ | skill 備份留在 skills 掃描目錄，**被當成新 skill 繼續載入** | MINOR |

## ★① 的根因值得單獨記★

Windows PowerShell 5.1 從**磁碟**執行 `.ps1` 時，**沒有 BOM 就用系統 ANSI codepage 讀檔**。
而 Windows 的 `MultiByteToWideChar` 對 DBCS **前導位元組（0x81–0xFE）會無條件吃掉下一個位元組**
——即使那個位元組不是合法尾碼。

UTF-8 中文字的位元組序列裡，只要某個前導位元組緊接著 `"`（0x22），**那個引號就消失了**。

於是 parser 配對錯亂，最後在一行**純 ASCII、完全無辜**的程式碼上報：

```
The string is missing the terminator: ".
```

**本測試在 macOS 上於位元組層模擬這條規則，重現出與真機回報完全相同的 5／1／1。**
那讓這條從「只能掃原始碼長相」升級成「驗真實失效機制」。

> `get.ps1` 差最多卻沒炸，純粹因為 `irm | iex` 是下載成字串由 .NET 用 UTF-8 解碼、**不經過磁碟**。
> 但它自己註解建議的「先 `curl -o get.ps1` 審閱再跑」——那條路會直接炸。

## ★④ 的傷害在訊息，不在失敗★

舊訊息只說「移除失敗」，**聽起來像安全地什麼都沒動**。實際上 `.git` 已經半殘。

而 `get.ps1` 用 `Test-Path "$Dest\.git"` 判斷「是不是我們的 clone」→ True → `git pull` → rc=128
→ 使用者看到 **「可能有本地改動，或不是 fast-forward」**。

**完全指錯方向。** 使用者必須自己想到要 `Remove-Item -Recurse -Force` 才能脫困。

修法因此有兩件：唯讀檔補權限再刪，**以及失敗時明講「已部分刪除、不再是可用的 clone」**。

## ★⑤ 帶出的設計取捨★

備份改落 `~/.local/share/lumos-slim/backups/` 之後，該目錄不再是空的，
「清空 `lumos-slim/`」那步**正確地不觸發**。

但★**刻意保留 ≠ 可以靜默**★——否則就是原本 manifest 殘留那條缺陷的同一形狀。
彙總現在會明講：

## 過程中自己犯的第 15 次假綠

④ 的測試第一版只 `chmod 444` 那個**檔案**——但 ★POSIX 與 Windows 的擋法根本不同★：
Windows 靠**檔案的唯讀屬性**擋刪除，POSIX **只看父目錄的寫入權**。
macOS 上兩種寫法都成功，翻紅釘**照樣全綠**。

改成讓**父目錄**不可寫才真的擋得住。**通則已記進 [[Systems/測試假綠形態]] 第④型：
在 A 平台重現 B 平台的缺陷時，先確認「擋住它的機制」在 A 上也存在。**

## ★誠實邊界（最重要的一段）★

| 缺陷 | 驗證層級 |
|---|---|
| ① | **位元組層模擬**真實失效機制（重現 5/1/1），但「PowerShell 真的不再 parse error」**未在真機複驗** |
| ② | 隨 ① 消失，**未獨立驗證** |
| ③ | **只驗原始碼長相**（第③型，刻意如此——macOS 沒有 PowerShell） |
| ④ | **真行為**，但用 **POSIX 類比**（父目錄不可寫）而非 Windows 的唯讀屬性 |
| ⑤ | **完整真行為驗證**（裝→塞使用者檔→卸→查兩邊目錄） |

★**只有 ⑤ 是完整的真機等價驗證。修完之後沒有任何一條在真機 Windows 上複驗過。**★

## 回報者確認沒問題的部分

`CLAUDE.md` 的處理是**位元組級完美**的：安裝時把完整版紀律區塊 base64 備份進 marker、
卸載時原樣還原，`git status` 驗證工作區完全 clean。使用者自有 skill 全程未被誤動。
`lumos.cmd` 指向 `~\.local\bin\lumos`（CLI 本體自帶一份），**比完整版硬編碼指到 vendored 副本更穩健**。

## ★獨立審計（maker≠checker）抓到的四條——全部已修★

那條 BOM 合約綁了測試，依合約鏈規矩必須經**無脈絡獨立 agent** 審合法性。判定 `legal`，但抓到四條，**全部正確**：

| | 它抓到什麼 | 處置 |
|---|---|---|
| 1 | 當時全部改動**未 commit**，「合約」還沒真正落進 repo 歷史 | 已提交 |
| 2 | `check(..., True, "")` 是**恆真斷言**（假綠第①型）——不管吞噬數算出多少都 ✓，連「吞掉 0 個」這種自相矛盾的訊息都會過 | 改成 `_n > 0`；**那才是「這個檔真的有危險」的斷言，沒有危險就不需要 BOM** |
| 3 | 「影響**所有非西歐語系**」**誇大**——cp1251 西里爾／1253 希臘／1254 土耳其／1255 希伯來／1256 阿拉伯／1257 波羅的海／1258 越南**全是單位元組**，不會觸發吞噬 | 改成「**CJK／雙位元組（DBCS）語系**」 |
| 4 | 「get.ps1 少 5 個引號」**不是** README 一行安裝失敗的原因——`irm \| iex` 不經磁碟；真正炸的是下游從磁碟執行的 `install.ps1` | 因果拆開講；get.ps1 那 5 個要等有人「先 `curl -o` 存檔再跑」才發作 |

★**第 2 條是我剛寫的測試裡的恆真斷言**★——寫的當下還在旁邊註明「純資訊，不斷言」，
以為誠實揭露就沒事。**但它佔著一個 ✓ 的位置，而 ✓ 是給人看「這件事被驗過了」的。**

★**第 4 條更值得記**★：我把回報者的三個數字（5／1／1）照抄成「所以一行安裝 100% 失敗」的理由，
**而回報者自己在文中就寫過 `irm | iex` 不經磁碟**。我讀到了那句、卻沒把它接進因果鏈——
