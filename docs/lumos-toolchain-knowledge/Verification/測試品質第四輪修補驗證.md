# 測試品質第四輪修補驗證

## 結論

一般錯誤路徑的程序群缺口已先紅後綠。fake launcher 啟動一個關閉 stdout/stderr 的長跑 worker 後以 rc1 離開；修前 `model_command` 返回後 worker 仍存活，修後會在返回前清理自己建立的程序群。原有 timeout 控制與 handbook 全套 17 項同時通過。本輪只建立 POSIX 資格，Windows 仍排除。

四個測試證據缺口也已收緊：orphan outcome 與 stale bytecode 案例改驗專屬拒收 reason；global `--vault` 案例先建立有效 source，再確認原因點名遺失的 scanner；Git rename fixture 的命令都有 10 秒 timeout，commit 明確停用 signing。五項定向 CLI 控制通過。

Semgrep finding 轉換改為每份來源只 decode/split 一次，並在取 snippet 前驗行號沒有超出來源；更新同源 bundle 指紋後，scanner 22 項控制通過。完整 CLI 曾在指紋尚未更新時整批回「配套版本不一致」，這是本輪中途真紅，不列產品回歸。

修補回歸審再找到 CLI capture 與 Semgrep backend 的同類程序群缺口：fake launcher 啟動 worker 後 rc1，修前會留下 worker；若 worker 繼承管線還會把已退出的 launcher 誤報 timeout。共用 runner 現在會偵測 launcher 已退出、清理自己建立的 POSIX 程序群，再排空管線。`--vault` 控制已改在它建立 source 的暫存目錄執行；刪掉 fixture 會使前置條件不成立。Semgrep 的 decode 次數保留單元控制，越界行號另走 fake backend 真入口驗結構化 unavailable。

固定 corpus 因 adapter 新增 core runner 相依而一度回 unavailable；凍結 scanner 時帶齊 `test_quality.py` 後恢復。更新兩支 sidecar 的 bundle 指紋後，完整 CLI 46 項、scanner 24 項與 handbook 17 項皆綠。

本篇是修補驗證，不代表第四輪代碼審處置閘通過。提交後仍須由乾淨席以最後快照審查。

## 第三輪修補回歸審之後

四位乾淨審查席看完上一輪修補後，再找到三件同族問題，都先在修補前版本紅、修後綠：

- handbook 模型命令仍是另一份程序群清理：模型印完輸出就退出，但留下握住管線的子程序時，修前 3 秒後被判逾時；改走共用 runner 後立即回傳 rc0，子程序被清掉。
- Semgrep backend 用訊息字串分類逾時，SIGTERM 也被收成單檔 unavailable：兩檔掃描中送 SIGTERM，修前要把第二檔整段 backend 逾時跑完才結束；改成型別分類、中斷往上傳後，5 秒內非零結束且 backend 程序群已清。修補前更早的版本會立刻結束，但會留下 backend 子程序。
- 原有控制殺不掉的變異：拿掉 launcher 退出後的清群、拿掉逾時分類、吞掉中斷、拿掉 backend 的 cwd 或 env，原本整套照綠；新控制對這五個變異都紅在目標斷言（worker 仍存活、狀態變 unavailable、5 秒內沒停、不在隔離 rules 目錄、metrics 環境變數為空）。

修後完整 CLI 46 項、scanner 26 項、handbook 19 項皆綠；scanner 新控制連跑三次後機器上沒有殘留測試程序。大輸出檢查：9 MiB 經共用 runner 與模型命令各約 0.04 秒，20 萬行事件流 0.1 秒，行程記憶體高點約 72 MiB，超過 10 MiB 仍回結構化錯誤。
