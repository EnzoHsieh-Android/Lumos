# 2026-09-29 前端卡小實驗

> 白話:在正式把前端卡接上之前,拿一個真實前端專案歷史上出過的 4 個 bug,各派兩位不知情的審查員審「引入那個 bug 的改動」,一位只拿一般派工詞、一位多拿前端卡,看誰抓得到。結果前端卡沒有多抓到。

## 怎麼做的

- 樣本來源:本機一個 React 自助點餐機專案(不是本 repo)。挑它修過的 4 個前端 bug,由代理用唯讀 git 指令找出引入那個 bug 的提交。其中 3 個出自同一個一萬四千多行的大提交,只截出出事的那支檔的差異(916、124、57 行);第 4 個的引入提交本身只有 44 行。
- 審查員讀的是「引入提交當時」匯出的原始碼副本,沒有版控紀錄,查不到後來的修正。
- 兩組派工詞一樣是正確性鏡頭那組問句;前端卡組多一段,內容就是程式實際產生的角色段文字。兩組都拿掉圖譜鏡頭那行,避免掛鉤附上別的東西。
- 判準在派工前寫定:席報告裡有一條講到根因的情境才算抓到,只點到相關區域不算。
- 樣本 B 第一輪兩組結果不同,兩組各重跑兩次(同上次資料狀態鏡頭實驗的做法)。

## 結果

| 樣本(bug) | 對照組 | 前端卡組 |
|---|---|---|
| A 結帳連點重複送出 | 0/1 | 0/1 |
| B 找不到店家時跳頁、蓋掉維護/休息彈窗 | 2/3 | 1/3 |
| C 重新整理內頁後店家代碼遺失 | 1/1 | 1/1 |
| D 同一畫面不重掛載就不重新解析、留著舊狀態 | 1/1 | 1/1 |
| 合計 | 4/6 | 3/6 |

- 前端卡組額外報了一條無障礙問題(付款按鈕讀屏讀不出選中狀態),對照組沒有;無障礙不在判準裡,只記觀察、不算分。
- 兩組在樣本 A 都另外報了刷卡逾時後才成功、金額用了過期計算結果等問題;這些是否為真沒有驗證。

## 結論與限制

- 這次沒看到前端卡有幫助;差一次在單次起伏範圍內,也不能說它有害。樣本只有 4 個、同一個專案、同一種模型。
- 證據(判準、12 份席報告、材料)含另一個專案的程式碼,只留在當次會談的本機暫存區,刻意不進本 repo。
- 對計劃的意義見 [[Projects/代碼審前後端角色鏡頭_計劃]] 的撤除條件:接線與否由人裁。
