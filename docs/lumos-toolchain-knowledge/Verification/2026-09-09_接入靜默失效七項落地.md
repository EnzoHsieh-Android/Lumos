# 2026-09-09 接入靜默失效七項：落地

> 白話：把「閘看起來過了、其實沒作用」的五道靜默補起來。六件是加提醒與產骨架，一件是真的改判定——因為那道閘現在會**主動報告假的好消息**。

## 七項各驗到什麼

| 項目 | 結果 | 怎麼確認的 |
|---|---|---|
| 設定骨架 | ✅ | 單語言猜對、多語言走多平台格式、認不出留空寫說明；產出的是**合法 JSON**（我第一版寫了註解，那會讓整份設定解析失敗） |
| 技術棧不符提醒 | ✅ | 判準是「跟 repo 實際副檔名不符」，設定檔寫死錯的值也照樣出聲；本 repo 實測抓到一條真的 |
| `about_code` 沒接上提醒 | ✅ | 收緊成「有合約且綁測試」後本 repo 2 篇，符合計劃門檻；抓到的其中一篇正是合約測試閘自己的節點 |
| 忽略設定跟設計一致 | ✅ | 治理帳不再被忽略（CI 唯一路徑）、本機留痕目錄改成忽略；既有設定不覆寫 |
| 零覆蓋出聲 | ✅ | 四種來源各一句人話，訊息帶推送前腳本認得的關鍵字 |
| **假綠改成擋** | ✅ | 端到端：沒有過濾能力的指令 → `unfilterable` 而不是 `green` |
| 表態訊息兩條路徑 | ✅ | 失敗與成功都不再說「治理帳是 CI 唯一讀得到的地方」那個錯誤主張 |

## 實作時才發現的三件

- **「找不到知識庫」那條原本走不到**：我照計劃把它從另一種狀態裡分出來，但沒有知識庫時，更早的波及計算會**先**失敗成一句沒人看得懂的話。把檢查移到最前面才真的講得出「是不是跑錯資料夾，或這個專案還沒初始化」。
- **既有測試的假執行器本身就是反面教材**：它不管傳什麼測試名都回成功——正是新閘要抓的形態。改成會拒絕不存在的測試名（更像真的測試工具），而不是放寬閘去遷就它。
- **兩支既有測試在斷言被刻意翻掉的舊行為**：治理帳必須被忽略。已改成斷言新行為，並在測試裡寫明為什麼翻。

## 我自己製造的三個錯（兩個被既有守衛接住）

- 在 JSON 設定檔裡寫註解——**那正好會製造出本案要解的那種靜默**（整份設定解析失敗、退回預設）。自己在驗證骨架能不能被讀回來時抓到。
- 新健檢在「知識庫不在 git 專案底下」時直接炸——既有的健檢測試翻紅抓到。
- 把測試檔寫壞而且**先寫檔才驗語法**，整個測試檔一度無法解析。改成先驗語法再寫檔。

## 沒驗到的

- **冒煙測試只在兩種執行器上驗過**（xcodebuild、shell 假執行器）。若有測試框架在「找不到指定測試」與「測試失敗」兩種情況都回非零，會被判成可信——那是保守方向，不會誤擋，但也就抓不到那種假綠。回頭條件在計劃節點。
- **CI 端完全沒跑過**：忽略設定的改動要等真的有專案接 CI 才驗得到。
- **既有專案不受影響**：只改初始化行為，已經產生的忽略設定不動——所以計算機專案目前仍是錯誤狀態（本機留痕被版控、治理帳被忽略），那是刻意留著當「既有專案遷移」的第一個樣本。
- 本 repo 健檢剩 1 個既有問題（合約測試閘的驗證節點被標失效），而它的重驗條件正是本次改到的那幾支函式——這篇就是那次重驗。
