# 凍結接受非綠判定

## 症狀

- 手動 `lumos loop replay <編號> --freeze`(含 `--note` 重凍)只在處置閘回 rc2 時擋下;rc1(判不過)照樣把 `{"rc": 1, "fails": [...]}` 寫進 `governance/replay/<編號>/verdict.json`。
- 週跑 `governance/autonomous_loop/replay_weekly.py` 對「有收斂紀錄但沒判定檔」的迴圈自動補凍,同樣不先確認現在是綠的。
- 2026-10-13 帳上 307 份判定檔有 5 份是 rc1(`code-batch14`、`code-batch13b`、`code-待決問題改存開頭欄位`、`code-審查跑滿回顧`、`code-兩席相反時端出張力-v2`),沒查過是刻意凍紅還是意外。

## 根因

凍結的語意是「把這一刻的判定固定成之後回放的標準答案」,設計時沒區分這一刻是不是綠。判準本身有錯、或舊工作樹跑舊程式時凍結,會把錯的紅燈固定下來;之後只能再重凍一次,而重凍本身又是同一個動作。

## 現在怎麼繞

回放報漂移時,先用最新程式跑一次處置閘;是綠的才 `--freeze --note` 重凍,是紅的先查判準(見 [[Projects/引句錨定整段比對_計劃]]〈回退〉)。

## 什麼條件算修好

- 先逐一查那 5 份 rc1 判定檔是刻意還是意外,結果寫回本篇。
- 已知的非綠來源要一併涵蓋:引句判準第一階段起,處置閘遇到判準丟例外會判失敗(rc1)而不是崩潰,凍結入口會把它凍成紅色標準答案(代碼審 code-引句錨定整段比對 r5 回滾席);第二階段新判準若有缺陷,會先凍成紅、修好才報漂移。
- 設計一條統一規則(例:凍結時判定非綠預設擋下 rc2,要凍紅必須另帶旗標並寫理由),手動凍結、重凍、週跑補凍三個入口都走同一支;照設計審走。
