# 治理帳多個寫入者都沒上鎖

白話:好幾支程式同時往同一本治理帳(記錄每道閘擋了誰、放了誰的流水帳)寫一行,都沒有排隊。兩行剛好同時寫,可能黏成一行壞掉的紀錄,而讀帳的程式遇到壞行會默默跳過——那筆「擋下」或「通過」就像沒發生過。

## 症狀

目前沒有抓到真的壞行(沒量過)。風險來自程式形狀:設計審四席各自讀程式碼指出同一件事,編排者也看過兩支寫入器確實直接 append。

## 根因

寫治理帳的入口至少四支,各寫各的,都直接以附加模式開檔寫一行:
- `_gate_event`(大多數閘的通用寫入器:每支檔有家、代碼審、新增告警閘、anchor、canary 等)
- `_codeloop_gov_log`(代碼審的通過與跳過)
- `_append_governance_log`(doctor、spec-gate、delguard、bound-tests、設計審等)
- 代碼審表態(dispositions)自己的一支

讀端(`lumos gov`、代碼審讀帳、doctor 等)解析失敗的行一律跳過,不報錯。

這幾支寫入器的家是 [[Systems/reversibility-governance-ledger]];修好後說明寫回那一篇,本篇結案。

## 現在怎麼繞

沒有繞法;靠同時寫的機率低。注意:[[Projects/筆記形狀擋_計劃]] 上線後,每次擋下與環境變數跳過會多寫一筆(放行不寫),寫帳頻率會略增。2026-09-28 [[Systems/存量漂移守衛]] 又多兩個寫入者:表態檔(一行一筆,追加後讀回自驗,但沒跟別的寫入者共用鎖)與 drift-check 閘事件(走通用寫入器);2026-10-11 回頭看時一起算。

## 什麼算修好

1. 所有寫入者共用同一把鎖,而且沿用專案唯一那套鎖檔做法(`_excl_lock_try`,筆記庫寫入鎖與派工鏡頭快取鎖都用它;專案記過「第二種鎖」被打掉的舊帳)。
2. 鎖等不到時照 `_gate_event` 既有契約:不改變閘的判定,只在 stderr 講一句;不能變成擋人,也不能丟裸例外。
3. 代碼審通過時「先寫本機標記、後寫治理帳」的順序要一起看:帳寫不進去時本機標記會讓本機放行、乾淨的 CI 卻紅。
4. 有一支測試同時從兩個行程寫,確認兩筆都完整落帳。

REVISIT:2026-10-11 跟 rtb 回饋那篇同一天決定要不要另開計劃修。第二層([[Projects/筆記內容審_計劃]],取代了原本寫在這裡的舊計劃)2026-09-28 收窄後不拿治理帳判涵蓋,壞行只影響它的觀測數字,但寫入頻率會變高,決定時把它算成第一個受影響的使用者。
