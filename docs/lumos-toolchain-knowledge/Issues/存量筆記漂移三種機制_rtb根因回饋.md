# 存量筆記漂移三種機制_rtb根因回饋


白話:9/27 回報的是「新寫的筆記別把程式現況寫進去」(工具組已上線來源標記與 note-audit)。這次查的是**存量**:已經寫進去的句子,程式後來改了卻沒人回頭改。抽查確認六成是真的,而且現有健檢一處都沒抓到。根因不是有人偷懶,而是現行閘只看「這次提交有沒有動到筆記」,不看「被改到的東西,圖譜裡還有哪些舊句子在講它」。

## 三種產生機制(20 處真漂移全部歸得進去,逐處證據見稽核全文)

1. **同篇只往後追加,不回頭改(9 處)**。讓句子失效的提交有改到這篇筆記,但只在後面加新段,同篇舊句沒掃。例:模型環境變數從三個變四個,提交只在筆記底部補一行;那條舊 RULE 之後又被改一次、確認日期更新了,數字卻沒重數。
2. **不歸這段程式管的筆記沒人通知(5 處)**。「目前沒有 X」「等 X 時回頭做」寫在計劃或 Issue,這些筆記不在 about_code 範圍內;做出 X 的提交只被要求改程式的家。同一條回頭條件抄在兩三篇,只有家那份被修。
3. **狀態指令只改欄位(6 處)**。事故預告合約轉正、計劃改完成時,散文不動(例如 F1/F2/F3 驗證紀錄仍寫「還沒有測試在守」),相關 Issue 與驗證紀錄也不連動。

放大因素:
- pre-commit「改 code 沒動圖譜」與「寫回要落在家」只看檔案層級,不看改的是哪一句;20 處裡 14 處的失效提交都合法改過筆記。
- 代碼審席位只判「程式有沒有違反筆記合約」,不判「筆記有沒有被這次改動弄錯」;撤掉 AI 決策那一輪,審材裡一篇筆記都沒有。
- delguard 只查前 40 個被刪名字、只提醒;大提交印出上百筆命中後等於沒人看。

## 候選防線(給工具組評估,依效果排序)

1. **推送前列出「被改到的東西,圖譜裡還有誰在講」,逐句表態**(對應①)。把 delguard 擴大到改名、常數改值、新增檔案,拿掉 40 個上限;推送前把全圖譜沒被這次改到、卻提到被改符號的舊句列出來;落在家與摘要行的要改掉或留理由才放行。列句子可全自動,改不改由人或模型判;誤報偏高,需要分層(家與摘要行擋、其餘只提醒)。
2. **回頭條件與「還沒有 X」改成可機械判定的探針**(對應②)。例如「某檔案出現」「某測試存在」「某計劃狀態變完成」;doctor 每次推送評估,成立就點名;新寫的沒帶探針就在提交時擋。誤報低;rtb 現有約 45 條要回補。
3. **狀態指令連帶處理散文與相關筆記**(對應③)。轉正時同步處理「還沒有測試」這類句子;計劃改完成時列出還開著的相關 Issue 與待定驗證紀錄要求處理;doctor 加狀態一致檢查。幾乎全自動,誤報低。

其他次要防線與「工具能做 vs 只能靠寫法規範」的分界見稽核全文。

## 跟既有工作的關係
- [[Issues/筆記把程式現況寫進脈絡而漂移_rtb實測回饋]] 管的是新寫入(寫的當下別寫程式推得出來的東西);本篇管存量已寫入的句子怎麼跟著程式失效被抓到。
- [[Projects/筆記內容審_計劃]] 的 note-audit 只審推送範圍內新寫的行、判「該不該寫」不判「對不對」,對存量無效;rtb 也還沒接上它(推送前與 CI 都沒呼叫)。
