# 回頭重讀指紋第六輪放行的小缺口

代碼審 code-回頭重讀指紋 第六輪七席只有 minor(11 條)或乾淨,依「上限後的輪次 minor 可附理由放行」全數放行、不再開下一輪;逐條原文在 governance/review-reports/code-回頭重讀指紋/r6-*-sonnet.md,處置在 r6-intake.md。這篇把它們收成一處,之後有人碰這一帶時照這裡補。

## 症狀

- 批次 diff 判「這支檔有沒有被這批問到」用串列做線性比對,原本是字典查找;一批上萬支時約一秒多(正確性 F1、邊界 F3)。
- 指紋耗時跟改動的筆記篇數成正比(每篇各開一次 git 子行程);一條分支同時改上千篇有關聯筆記時會撞到檢查的時間預算,多數篇退回舊版指紋後照擋(資源 F1;不是第五輪修補造成)。
- 「哪些檔在算指紋前就退回舊版」的條件在批次函式與單檔函式各寫一份,日後只改一邊會讓批次又收進不會被問到的大檔(架構 F1)。
- 判「兩半相同」的檔頭小工具放在回頭重讀區塊,卻被共用的 patch 解析呼叫,跟同一輪新增的切段小工具位置分裂(架構 F2)。
- 計劃 r3 那行摘要還寫「功能分支由 CI 補驗、推主線核對分岔點」,跟現況(CI 只印不擋、分岔點核對已拿掉)矛盾(合約 F1)。
- 「功能分支偽造追蹤 ref 屬範圍外」只寫在散文、沒記成決策紀錄,對應的回頭條件標了結案(合約 F2)。
- 單次跳過的訊息先印「已記進治理帳」才真的寫;專案沒有治理帳或寫失敗時說早了(合約 F4)。
- 測試缺口:跳過帳位置沒寫進條款、測試讀帳前沒檢查檔在不在(合約 F3);切段的行首錨點、兩半相同的比對與引號分支拿掉都不會紅(邊界 F1、F2)。

- 接上主線後全套抓到:回頭重讀新寫的三處 git diff 把關掉外部驅動器的旗標放在常數裡,主線既有的守衛(t_lumos_content_diffs_all_disable_external_drivers)逐行比字面、看不到常數內容;已在三處呼叫直接寫明 --no-ext-diff。審查子集沒涵蓋那支守衛。

- 函式太複雜(C901)以 lint-waive 放行、沒拆:`_patch_file_changes`(共用的 patch 解析,為還原含「 b/」的檔名多了檔頭分支)、`_note_reread_hunk_nodes`(縮排鏈一趟掃完的各種定案條件)。拆小要動解析順序或狀態傳遞,另案處理。

## 根因

都是第五輪修補(批次排除大檔、檔頭還原進共用解析、照實改天花板說法)的邊角與說法沒跟齊。沒有一條會讓沒對照過的筆記被當成已對照放行:效能那兩條最壞是多花時間或退回舊版指紋(偏嚴),其餘是放置、說法與測試覆蓋。第六輪資安席與通才席都是乾淨。

## 現在怎麼繞

- 一條分支改到上千篇有關聯筆記時,拆成幾次推送,或照訊息單次跳過(會留帳)。
- 讀到計劃 r3 摘要那行的「CI 補驗」時以計劃〈做法〉與 Systems/筆記內容審 的說法為準:功能分支信任本機追蹤 ref,CI 那一步只印不擋。

## 什麼條件算修好

- 批次成員改成集合;退回條件抽成一支兩邊共用;判兩半相同的小工具搬到切段小工具旁;計劃舊摘要照實改、範圍外裁定記成決策;跳過訊息在寫帳成功後才說「已記進」;上面每個測試缺口各有一支會紅的測試。
- 耗時跟筆記數成正比那條:量到一般分支(百篇以內)撞預算時才處理,做法是把每篇的 git 呼叫合成批次。
