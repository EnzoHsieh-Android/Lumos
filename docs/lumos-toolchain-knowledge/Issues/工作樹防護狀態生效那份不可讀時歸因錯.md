# 工作樹防護狀態生效那份不可讀時歸因錯

## 症狀

白話:防護狀態檢查在附加工作樹裡比對「本工作目錄的 hook」和「實際生效那份」時,兩邊任一邊讀不到都被說成本工作目錄讀不到。

- 生效那份可執行但不可讀(權限 0111)、本工作目錄那份大小相同:列 degraded,說「讀不到本工作目錄的 pre-commit」;實際上生效那份跑不起來,該列 inactive 並點名它。
- 同一支測試的跳過條件在權限還原後才判,在不支援權限位的檔案系統會誤失敗(只影響測試,不影響使用者)。

## 根因

`enforcement_status` 附加工作樹那一支用 `filecmp.cmp(本工作目錄那份, 生效那份)`,兩邊共用一個 `except OSError`;另外主工作目錄本身的判定也只看可執行、不看可讀(修前就如此)。

## 現在怎麼繞

不用繞:要碰到得先把 hook 權限設成可執行但不可讀,一般安裝不會這樣;狀態仍是 degraded、進場提醒照樣點名,只是歸因字句錯。

## 什麼條件算修好

- 比對前先判生效那份可讀,不可讀列 inactive 並點名生效那份;讀不到本工作目錄那份才說本工作目錄。
- 測試在 chmod 000 當下就判檔案是否真的不可讀,不可讀才斷言。
- 修法走自己的代碼審(這兩條是上限最後一輪放行的)。
