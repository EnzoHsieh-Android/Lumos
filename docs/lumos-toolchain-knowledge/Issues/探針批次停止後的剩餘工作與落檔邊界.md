# 探針批次停止後的剩餘工作與落檔邊界

第四輪 `code-probe-boundary-remediation` 的七條處置已過機械閘，這篇記其後以官方文件對照才找出的剩餘邊界，**不是**追改第四輪席位報告或聲稱已有真模型事故。下列第 1、2 項是當時的症狀與根因；2026-10-04 的本機修補及驗證見文末，第 3 項仍開放。

Python 例外最小重現：`python3 -c 'import subprocess; subprocess.run(["/definitely-missing-lumos-probe-executable"])'` 會由父程序收到 `FileNotFoundError`（`OSError` 子類）；它只核對官方機制，尚未驗證消融入口。

1. `run_job` 的 `subprocess.run` 位於結果解析及停止旗標處理之前。Python 文件指出執行檔不存在時會向父程序拋 `OSError`，逾時也會拋 `TimeoutExpired`。目前這類例外會從 future 的 `result()` 冒出，整個 `main` 未完成 summary 寫入；程序雖非零退出，事故仍缺可採信的批次摘要。故障注入應令 `subprocess.run` 拋上述兩類例外，驗收停止後續派工、summary 標失效、退出碼3。來源：https://docs.python.org/3/library/subprocess.html
2. `main` 一次提交所有工作並以 `ThreadPoolExecutor` 執行；stop 只在 `run_job` 起點檢查。Python 文件明確說明取消未開始的 future 不會取消已在執行的工作，`with` 離開還會等它們完成。因此最早發現事故的工作設 stop 時，另一個已啟動的模型仍可能繼續。用兩個受控 stub 工作卡住其中一個，讓另一個先報事故，量出事故後是否仍有模型動作；再決定採一批一個工作、外層進程隔離或可取消的子程序協定。來源：https://docs.python.org/3/library/concurrent.futures.html
3. 結果與 summary 目前直接 `write_text` 到目標檔；中途終止可留下半檔。現有讀取端會拒收半檔，避免誤算，但下次要減少恢復成本時可先寫同目錄暫存檔、完成 flush 後用 `os.replace` 替換，並以中斷注入確認不會出現半成品。Python 文件保證同檔案系統上成功的替換是原子操作。來源：https://docs.python.org/3/library/os.html#os.replace

2026-10-04 已以故障注入修補第 1、2 項：`FileNotFoundError`／注入的 `TimeoutExpired` 都使摘要標失效、退出 3、停止後題，並留下下次 `--merge-only` 也拒收的 fatal 嘗試；live 派工只准單路，同一輸出目錄另有進程持鎖時拒絕啟動且不覆寫舊摘要。先紅後綠及本機限制記於 [[Verification/2026-10-04_探針停派與失敗留痕]]。`TimeoutExpired` 是注入防回歸，本版外層呼叫沒有 timeout 參數；不得據此聲稱已有真模型逾時事故。這一段只驗本機 stub，恢復多路或跨機執行要按 [[Projects/探針隔離與清理收斂_計劃]] 的退場條件重新證明。

目前繞法與結案條件：後續代碼審的符號連結反例促使消融 `meta.json`、`summary.json` 與 `summary.md` 改用原子替換，該三檔不再跟隨既有目標符號連結；探針原始結果仍在其產生端直接寫入，終止時仍可能留下半檔。讀取端先拒收半檔，真模型批次前先確認輸出目錄沒有舊失效檔。出現實際半檔事故、需要多程序同步讀取結果、或下一次修改探針原始結果格式時，以中斷注入驗證產生端同目錄暫存與 `os.replace`，再決定是否結案。本 Issue 保持 open；第四輪 PASS 與本機續驗均不等於真模型驗收。
