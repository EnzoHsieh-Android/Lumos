# 會談編號環境變數接續後停在舊值

白話:Claude Code 的 Bash 裡其實讀得到 `CLAUDE_CODE_SESSION_ID`,舊筆記寫「拿不到會談編號、沒有環境變數」已經過時;但這個變數在會談接續後會停在接續前的舊編號,直接拿來用會對錯會談。

## 症狀

- [[Projects/進度從提交推導_計劃]] 記「普通 CLI 拿不到 session_id(無環境變數)」,跟 [[Projects/接手視圖_計劃]] 用 `CLAUDE_CODE_SESSION_ID` 排掉自己的記載互相矛盾。
- 2026-10-06 本會談實測:Bash 環境有 `CLAUDE_CODE_SESSION_ID`,值是會談一開始的編號;會談接續後工作資料夾已換成新編號,環境變數沒跟著換。

## 根因

2026-10-07 互動會談實測:`/clear`、`/compact`、互動模式接續三種情況官方編號都是對的;看到舊值的那一場是從 claude.ai 遠端橋接、又因內容太長而接續的會談(見 [[Verification/2026-10-06_會談編號外掛實測]] 的 10-07 段)。2026-10-06 的觀察:`CLAUDE_CODE_SESSION_ID` 是 `claude` 另外塞給 Bash 的,新開的會談與 `claude -p --resume` 都給對;本會談是對話壓縮後接續、換成新編號,給的仍是接續前的編號。外掛讀不到這一份(它只看得到 `claude` 啟動時繼承的環境),所以不能拿官方編號來配對;10-07 改用程式編號配對可行(見下一節)。

## 現在怎麼繞

`lumos handoff` 照用(拿來排掉自己,舊值在同一場會談裡仍成立);[[Projects/Claude-mod第二批_計劃]] 原本的外掛配對做法實測不成立、沒做。

可靠來源已經找到備案:外掛用小程式問到的程式編號跟 Bash 的 `CLAUDE_PID` 對得上,真有需要時可用來配對;目前常見情況官方編號就對,不做。
REVISIT:2026-12-06 兩個月內沒再遇到舊值就結案;再遇到就記下會談種類並改用程式編號配對

## 什麼條件算修好

兩個月內(到 2026-12-06)沒再遇到官方會談編號停在舊值,就結案;再遇到,就記下是哪種會談(遠端橋接、接續方式),改用程式編號配對,讓 lumos 在那種會談裡也讀到當下的編號。
