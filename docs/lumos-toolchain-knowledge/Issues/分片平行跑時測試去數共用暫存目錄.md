# 分片平行跑時測試去數共用暫存目錄

> 白話:有一條測試在「全套一起跑」的時候會隨機翻紅,單獨跑卻永遠是綠的。原因不是程式壞了,
> 是那條測試用錯了量尺——它去數一個大家共用的資料夾,而旁邊剛好有三個一樣的測試行程在動它。

## 怎麼發現的

2026-09-08 推送被閘擋下,4 片加總只有這一條紅:

```
✗ r1-③: 早退沒有留下現場(收尾在 finally 裡)  before=239 after=240
```

只差 1。單獨跑 `-k runner_isolation` → 12 passed / 0 failed,穩定綠。

## 根因

那條斷言的做法是:數一次系統暫存目錄底下有幾個 `gctl-run-*`(before)、跑一個會早退的
子進程、再數一次(after),要求 `after <= before`。

但 `scripts/hooks/pre-push` 會**切成四片同時跑**(`LUMOS_TEST_SHARDS` 預設 4),
**每一片都是獨立的測試行程、各自建一個 `gctl-run-` 根**。所以在 before 跟 after 中間,
別片隨時可能起來或留下殘骸——`after` 就多 1。

**被測的行為(早退要在 finally 裡收尾)本身沒有壞。壞的是量尺。**

## 修法

不要數共用的命名空間:給那個子進程一個**專屬的空暫存目錄**,跑完驗那個目錄裡一個
`gctl-run-` 都沒留,`finally` 收掉。跟別片完全無關。

順帶變嚴:原本只驗「沒有變多」,現在驗「一個都沒留」——原本那條就算收尾完全失效、
只要別片沒同時動,也可能是綠的。

## 通則(這才是要記的)

★只要測試會在平行分片下跑,就不能拿「全域目錄的計數」當斷言。★
要嘛給它專屬的命名空間,要嘛改成驗「屬於我的那一個」——不要驗「總數有沒有變」。
