# 風險掃描的linter那隻手沒送檔進去

## 這是什麼

算改動風險的那支掃描器,會去讀專案宣告的 linter 指令、跑一次、把結果當成風險訊號。指令裡寫著兩個佔位符:一個是「把結果寫到哪」,一個是「要檢查哪些檔」。★只有前者被換掉了★,後者原樣送出去,所以 ruff 收到的參數是一段沒有意義的文字,當場回報找不到檔案。

## 為什麼要在意

- **該擋的沒擋**:linter 是用來在推送前抓出新帶進來的問題的。這條路等於一直在回報「乾淨」,而它連看都沒看。
- **不該擋的擋了**:那句「找不到檔案」自己被當成一條發現,把風險分級撐成最高級。最高級要走完整審查迴圈——五席、最多三輪。今天這批改動實際上一條問題都沒有。
- 這跟先前記過的那次同一族:**一條都沒跑卻說乾淨**(見 [[Systems/測試假綠形態]])。差別是這次連「有沒有跑」都不必猜,工具自己回報了跑了一條命令。

## 怎麼證明的

1. 開一份拋棄式工作樹,加一支只有五行、含兩個明顯錯誤的 py 檔並提交。
2. ruff 直接跑那支檔:抓到 2 條。
3. 掃描器對同一個提交跑:`lint_ran` 說跑了 1 條命令,`claims` 是空的,分級一般。
4. 回主 repo 對這次要推的範圍跑:`claims` 只有一條,規則是 E902、檔名欄位就是那個沒被換掉的佔位符字串,分級被撐成最高級。
5. 手動把佔位符換成真的檔名再跑一次,對照這次改動的新增行:落在新增行上的是 0 條。

## 2026-09-16 已經修了(同日,Enzo 裁優先做這件)

原本這一節寫的是「先記帳不修」,當天稍晚 Enzo 裁了優先處理,五處全部修完,每一處都先寫會翻紅的測試再修。

- **把檔送進去** — 抽成一支共用函式,五個呼叫端全部改用它;原本冒煙、規則索引、新增告警閘三處各自手寫一份,現在只剩一份。另加一條測試★從原始碼層釘住「整支程式只准有一處在做這個替換」★,下次有人再寫第二份就會紅。
- **執行入口 fail-closed** — 佔位符沒被換掉就不跑,記成「這條沒跑」而不是產出一條假發現。就算未來有人新增第四個呼叫端又漏換,也只會少報、不會假報。
- **主程式進得了檢查範圍了** — 專案裡★早就有★一支「沒有副檔名就看第一行」的函式(2026-09-13 就是為了這支主程式寫的),但算風險這條路自己用副檔名又寫了一份。改成用同一支。實測:餵三支檔進去,以前只認得出那支有 .py 的,現在主程式也認得出來。

## 修完之後量到的副作用,一併處理了

linter 真的開始讀檔之後,★工作目錄不乾淨(或審的範圍比目前版本舊)時,會把改到的檔裡所有舊有問題全算進來★——這個 repo 實測 **1446 條**,分級必定最高級;對齊時只有 3 條而且都落在新增的行上。這條路以前無害只是因為 linter 根本沒讀到檔。

**處置**:對不齊時 linter 的發現照樣列出來(資訊不丟,帶標記讓讀的人知道沒對齊),但★不參與分級★。理由是分級問的是「這次改動有多危險」,而對不齊時分不出哪一條是這次帶進來的;拿它撐分級只會讓最高級變成常態、然後沒人當一回事。真正擋「新帶進來的告警」的是推送前那道閘(它比對兩份快照,跟對齊無關),不是這裡。★這是編排者判的,不是誰裁的★。
