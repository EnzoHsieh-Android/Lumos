# 探針以工作樹為來源會改到本體

> ✅ **已結案(2026-09-21)**:改成正面條件——問 git「來源的 git 目錄在哪」,不在來源底下就停手,並洗掉會蓋過 cwd 的 git 環境變數。實證:三種形狀各有測試、拆掉修法會翻紅、真跑一次探針後本體設定原封不動。
> **以下的症狀與根因是當時的排查紀錄,不是現況。**

## 症狀

用 `git worktree` 開的臨時樹當情境探針的 `--repo` 來源,跑完之後**本體 repo** 出現:

- `git remote -v` 空的,推不上去(`fatal: 'Lumos' does not appear to be a git repository`)。
- `core.hooksPath` 指向一個已被刪掉的探針臨時目錄,於是 pre-commit / pre-push / 收工提醒全部靜默不跑。
- 設定檔的時間戳是探針跑的那一刻。

**最危險的不是推不上去,是防護層失效不會有人發現**——推不上去會當場報錯,防護失效只會讓下一批改動一路綠燈進去。

## 根因

管沙盒的那支腳本(它的家在 [[Systems/codex-harness]])用 rsync 把來源整個複製過去,然後在副本裡跑三道隔離:拔掉所有遠端、把 hooks 路徑指到副本專用目錄、寫一支硬擋的 pre-push。

這三道都帶了工作目錄參數,寫法沒錯。**錯在前提**:它假設來源的 `.git` 是目錄。

- 主 repo 的 `.git` 是目錄 → rsync 複製一整份 → 副本的 git 指令落在副本上,隔離成立。
- `git worktree` 開出來的樹,`.git` 是**一行文字的檔**,內容是 `gitdir: <本體路徑>/.git/worktrees/<名>` → rsync 原樣複製 → 副本的 git 指令**全部落在本體上**。

所以三道隔離反向生效:拔的是真遠端,改的是真 hooks 路徑,硬擋的 pre-push 反而沒裝到本體。

## 現在怎麼繞

跑探針時**不要拿 worktree 當來源**,只給真 clone 的根目錄。要做「舊版設定」這種對照組,改用完整 clone(`git clone`)而不是 `git worktree add`。

踩到之後的復原:

```
git -C <本體> config core.hooksPath scripts/hooks
git -C <本體> remote add <名> <網址>
lumos enforcement        # 驗防護層有沒有全部回來
```

## 同一族還有兩種形狀(2026-09-21 審查席在隔離環境各重現一次)

第一版修法只擋「`.git` 是檔」,也就是只擋了作者自己踩到的那一種。同族還有:

- **`.git` 是 symlink 指到別處的目錄**:`is_file()` 會跟隨 symlink 判斷成目錄而回 False,檢查不觸發;rsync 預設保留 symlink 本體,副本的 git 指令一樣落在本體。
- **`GIT_DIR` / `GIT_WORK_TREE` 已設**:來源完全正常也沒用,git 判斷 repo 在哪時優先看環境變數,`cwd` 完全不算數。這條跟來源形狀無關,只要呼叫當下環境髒了就會發生。

所以判斷改成**正面條件**:問 git「來源的 git 目錄實際在哪」,要求它就在來源目錄底下;並把會蓋過 `cwd` 的 git 環境變數全部洗掉再跑。列舉壞形狀永遠會漏,正面條件一次涵蓋 worktree、symlink、`--separate-git-dir`、submodule。

審查席另外查過並排除的:submodule 與 `--separate-git-dir` 都會被擋、bare repo 在更早一層就被擋、停手發生在建臨時目錄之前所以沒有殘留、例外不會被吞掉、`git clone` 這個替代做法真的能達成對照組的目的。

## 什麼條件算修好

1. 來源的 git 目錄不在來源底下時,建沙盒直接停手並講清楚原因,不是照跑;會蓋過 `cwd` 的 git 環境變數一律洗掉。
2. 有測試分別餵 worktree、`.git` 是 symlink、`GIT_DIR` 已設三種來源,證明它會停手或至少不動到本體。
3. 復原步驟寫進說明,並且 `lumos enforcement` 能驗出防護有沒有回來(這條現在就成立)。

三條都達成,2026-09-21 當天收案;真的跑一次探針驗過本體的遠端與掛鉤設定原封不動。
