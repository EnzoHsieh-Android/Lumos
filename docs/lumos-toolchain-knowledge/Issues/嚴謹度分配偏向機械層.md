# 嚴謹度分配偏向機械層

> ★2026-09-01 Enzo 委任裁:試點併入 [[Issues/散文紀律沒有退場機制]] 修法 A 的 ablation(同一實驗回答兩題),不另開★

> 白話:同一個人,對程式碼要求「先寫會失敗的測試」,對自己寫的十五萬字規矩**一次都沒量過有沒有效**。

## 對照

| | 程式碼層 | 自己寫的紀律層 |
|---|---|---|
| 事前 | TDD 先紅後綠(強制) | 無 |
| 綁定 | ★INVARIANT★ → `[test:]` → `[audit:]` → `[kill:]` 四級鏈 | 無 |
| 事後驗證 | 沙盒真弄壞、綁定測試必翻紅 | 無 |
| 指涉正確性 | `refcheck` 機械驗 file:line | 無 |
| 規模 | — | 150,810 字元(skills 全樹) |
| 被前後量過效果的 | 全部 | **0 條** |

## 為什麼這不是資源問題

若是資源問題,應該看到「想量但排不進去」的痕跡——例如一張立著的待辦、一次失敗的嘗試。實際看到的是:

- [[Issues/散文紀律沒有退場機制]] 立於 2026-08-13,★到 2026-08-20 未動★。
- 同期新增的機制數量遠多於此:同一週落地了派工編制表、循序檔位、update 管線、鏡像自足、gov --stats。

★**造新機制的動作一直在發生,量測既有紀律的動作一次都沒有。**★ 這比較像偏好,不像排程。

## 反面提醒(不要過度修正)

**紀律不一定要能量測才有價值。** 有些規矩的價值在於「讓人在動手前多想三秒」,那種東西天生沒有機械 oracle——本專案自己就實證過 design-loop 對純散文空轉(見 memory `design-loop-completeness-ceiling-shown`)。

所以本單**不主張「所有紀律都要綁測試」**,主張的是:★至少要能分辨哪些紀律屬於「可量測卻沒量」,哪些屬於「本質不可量」★。目前這兩類混在一起,而混在一起的效果是全部都不用被檢查。
