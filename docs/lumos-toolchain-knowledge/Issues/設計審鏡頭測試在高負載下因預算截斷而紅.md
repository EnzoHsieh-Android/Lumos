# 設計審鏡頭測試在高負載下因預算截斷而紅

## 症狀

2026-11-05 凌晨在 shearwater 工作樹推送前跑全套時,`t_dispatch_lens_spec_mode_core` 的「太泛的單檔 CLI/總測試檔整檔略過並列在 too_generic」那條斷言紅,實際值只有 `['scripts/test_lumos.py(145 篇)']`,少了主程式那支。同一版程式在機器閒時重跑是綠的;紅的那次機器負載很高(同時有別的會談在跑全套與審查席)。

## 根因

設計審鏡頭(`lumos dispatch-lens --spec`)的四步共用一個 30 秒時間預算(常數 `_LENS_SPEC_BUDGET`),最貴的 impact 放在最後用剩的。這支測試拿真 repo 的計劃當材料,計劃提到的每支程式檔都要各開一次子行程跑 impact;主程式那支檔很大,負載高時輪到它之前預算已經用完,它就被放進「預算不夠、略過」那一格,而不是「太泛、略過」那一格。程式行為沒錯(預算截斷本來就該略過),是測試把「一定會算到這支檔」當成前提,而這個前提只在機器夠快時成立。

## 現在怎麼繞

- 機器閒時重跑推送前的閘;這一條紅、其他全綠時,先看同時間有沒有別的重負載。
- 不准為了過閘調大正式預算(那是 hook 45 秒總帳的一部分)。

## 什麼條件算修好

- 這支測試在跑之前把模組的預算暫時調大(同檔已有暫改 `_LENS_SPEC_BUDGET` 再還原的寫法),讓它驗的只剩「分類對不對」,不再依賴機器快慢;另有專門的測試驗預算截斷那條路。
- 改完後在高負載下(例如同時跑四片全套)連跑三次都綠。
