# 壞例標記與範本圍欄判讀的放行邊角

## 症狀

代碼審 code-情境決策點窮舉 第 4 輪(全部次要、附理由放行)留下的邊角。全部只會多報(自檢報假問題),不會讓壞寫法漏放;真壞例樣本 536 個 BAD 行修補前後輸出相同,〈叫不出的壞寫法〉目前沒有「範本」改由,所以現有資料都不受影響。

1. 範本圍欄守衛只看寬鬆讀法:嚴格讀法關得好的範本檔(圍欄中途有一行帶語言標記的三反引號)被報「沒關的圍欄」;測試只造兩種讀法都關不上的檔,把守衛改成嚴格讀法照樣全綠。
2. 單獨一行 // BAD 下一行的註記,後面只認空格與 tab:接換頁字元、NBSP、U+2028 時把註記行當目標(修補前的字面正規式用 `\s` 會跳過)。
3. 帶使用處標的的括號註記 `@field:[…]`、`@get:[…]` 不被當成註記(計劃寫支援 `@[…]`,實作只認 `@` 緊接 `[`)。
4. 泛型參數裡的 `->`(`@Foo<(Int) -> Unit>`)讓 `>` 提早配對;註記名稱與括號之間有空白(`@Foo (x)`)時括號不當參數。
5. 連續多行註記(`@A` 換行 `@B(1)` 換行 `fun z()`)的跳過沒有測試守。
6. 括號到檔尾都沒關的註記,每個標記都掃到檔尾,4000 組約 2.5 秒(修補前 0.1 秒)。
7. `_annotation_end` 用「回起始行號」表示「不是註記」,同組其他函式用 None 表示失敗;測試用類別假裝 scripts/lumos 模組,跟最近鄰居的寫法不同。

## 根因

註記與範本圍欄是自己解析 Kotlin 與 Markdown 原文,邊界多;第 3、4 輪改成照括號結構讀之後,剩下的是結構讀法本身沒涵蓋到的寫法與測試沒造到的組合。

## 現在怎麼繞

壞例樣本的單獨一行 `// BAD` 下一行避開上面 2–4 的註記寫法(改用行尾 `// BAD` 標在語句那一行);範本檔的圍欄內不要放帶語言標記的三反引號行。

## 什麼條件算修好

1–5 各有一個改壞會紅的案例並修正;範本圍欄守衛改成「嚴格讀法讀不完、寬鬆讀法也關不上」才報。
