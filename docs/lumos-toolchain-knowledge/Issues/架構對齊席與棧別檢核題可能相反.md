# 架構對齊席與棧別檢核題可能相反

> 白話:兩個審查角度的立場天生相反。一個說「照這個專案原本的寫法寫」,另一個說「這裡該用比較好的做法」。
> 大部分時候不會撞,但撞的時候目前沒有任何地方寫著該聽誰的。

## 怎麼發現的

2026-09-09 Enzo 讀 README 時問:「這個機制和後面的棧別提問和 linter 會不會衝突?因為他們的鏡頭
感覺是最佳寫法?」——**是讀文件讀出來的,不是跑出來的**。查證後成立。

## 三者的立場

| | 立場 | 標準來自哪 |
|---|---|---|
| 架構對齊席 | **跟這個專案既有的一樣** | `pitfalls --diff` 撈的同層最相似 3 個既有檔 |
| 棧別檢核題 | 該不該用比較好的做法 | 官方/社群共識(Android Compose perf、ASP.NET Core Best Practices…) |
| linter | 專案自己選的規則 | ★專案自己宣告要跑哪幾支,不是外部強加★ |

**linter 不在這個張力裡**——規則是專案自己選的。撞的是前兩者。

## 已經切乾淨的部分(不是問題)

- 檢核題 vs linter:**機械可查的歸 linter,機器查不了的才做成人判提問**(效能檢核目錄開頭明文)。
- 檢核題 vs idioms skills:idioms 是**寫的時候讀的教材**,檢核題是**審查時的提問**。

## 真的可能撞的地方(構想,尚無實例)

專案二十個檔都循序 `await` → 檢核題問「互不依賴的等待有沒有並行?」→ 照做改成並行
→ 架構對齊席看到「這個檔跟另外二十個不一樣」。

★這是構想出來的情境,帳上沒有實例★——因為兩者都很新(檢核題 2026-09-09 才落地),
而且逃逸帳是 0 筆、沒有任何機制在記「兩席意見相反」這件事。

## 現有的三道緩衝(能接住,但不是為這件事設計的)

1. **架構對齊的 major 門檻高**:只有「引入第二種做法」「跨層直呼」算嚴重。改並行不算引入第二套
   框架,**最多 minor**。
2. **檢核題可以答「不適用 + 理由」**:可以寫「這專案一律循序,改了會跟其他二十個檔不一致」。
   ★但工具只驗有沒有寫理由,不驗理由成不成立★。
3. **兩邊的發現都進處置閘**:每條都要有下落,衝突會被端到編排者面前。
   而且架構對齊席明文「判不準(鄰居本身就不一致)標 ⚠ 交編排者,不硬判」。

## 為什麼還是要記一筆

**三道接得住,但那是碰巧,不是設計。** 查證:
`arch-alignment-lens` / `效能檢核目錄` / `棧別提問表態閘` **三篇之間一條連結都沒有**,
圖譜也沒有任何一篇記過這個張力。所以撞到的時候,結果取決於編排者當下怎麼想——
★那正是這套機制最不喜歡的「靠人記得」★。

## 裁定(Enzo 2026-09-09)

**兩席意見相反時,不要挑一邊——要提出警告。**

- 棧別檢核題那條**照留**,不因為「跟既有不一致」就答 `na` 壓掉。
- 架構對齊那條也**照留**。
- 把兩者**併成一則警告**:既有寫法是 X、**隱患是 Y**、建議改成 Z,連同「改了會跟既有 N 個檔不一致」一起講。

★核心是「衝突要被看見,不是被裁掉」。★ 誰讓誰由人當下決定,工具只負責把兩邊都端上來。

**為什麼不採原本 AI 提的那條**(d1,已作廢):原提議是「架構對齊優先,除非那條檢核題指的是會出事的東西」
——★那會默默壓掉效能那條意見★,而且「算不算會出事」本身就要判斷,等於把一個判斷藏進另一個判斷裡。
**留下兩條、把矛盾攤開,資訊量嚴格大於挑一邊。**

## 後續(2026-09-09 同日)

Enzo 裁「開始解」:裁定落成機制,三塊都做——第四種表態 `tension`(張力)、`pitfalls --diff` 端出「可能撞」候選、派工詞口徑。
設計、審查與實作在 [[Projects/兩席相反時端出張力_計劃]];本篇 d2 的「目前只寫口徑不新增閘」一句由該案 d1 接手作廢,
「兩邊都留、不挑邊」的核心不變。
