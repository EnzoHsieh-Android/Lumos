# 風險掃描遇到非UTF-8內容整支中斷


## 現象

`lumos pitfalls --diff <範圍>`(推送前的檢查與 CI 都會跑)在 `scripts/lumos` 的 `_pitfall_diff_collect` 裡用文字模式讀整份 `git diff` 的輸出。
提交裡只要有一支檔的內容不是 UTF-8、而 git 沒把它當成二進位(例如開頭是 `\xff\xfe` 的文字檔),
解碼就丟 `UnicodeDecodeError`,整支中斷——推送前的檢查跟著停。

## 怎麼發現的

2026-09-10 代碼審第四輪(`code-工具自裝檔不算消費專案`)寫「工具檔內容不是 UTF-8 也要認得是原封不動」的測試時,
測試還沒走到要驗的地方,就先在風險掃描讀差異那段中斷。

## 怎麼修的(2026-09-11)

★工具裡每一個用文字模式讀 git 輸出、或看不出跑什麼的呼叫,都要明寫解不了的字元怎麼辦★(守衛管到的共 62 處:原本就有 3 處帶著;這次補了 59 處,其中 55 處換成替代字元、4 處嚴格解碼)。
內容與顯示用 `errors="replace"`——跟刪除守衛讀差異的既有寫法一樣。
解不了的位元組變成替代字元,只影響那幾個字元的比對,其他行照掃;推送檢查因此拿得到真的分級,不會再因為掃描壞掉而放行。
UTF-8 正常的輸出加了這個設定結果一模一樣。

★例外:找專案根目錄(`git rev-parse --show-toplevel`)的四處用 `errors="strict"`★(移除、一鍵拆機、初始化、安裝入口)。
這個路徑會拿去寫檔、刪檔;換成替代字元等於猜路徑——代碼審第三輪外家席實際示範:換出來的路徑剛好是旁邊另一個已安裝的專案,
移除指令就會刪掉它的圖譜。嚴格解碼時解不了就擋(移除與一鍵拆機會講明是路徑編碼的問題;初始化與安裝入口照原本的退路)。
守衛另有一條:凡是找專案根目錄的呼叫都必須是 strict。
其他把 git 吐出的檔名拿去動檔案的地方查過:從來源更新只在檔名「完全等於工具自己的帳本檔名」時才還原,換過字元的檔名不可能相等,只會擋下。

為什麼是全部、不是只修讀差異的那幾處:第一版只修了九處,代碼審第一輪指出——
- 九處裡只有三處有測試真的釘住(逐一拿掉修法跑測試,另外六處拿掉照樣綠);
- 刪除守衛自己的全域搜尋(`git grep` 會印出命中那行的內容)沒修到,碰到非 UTF-8 內容時守衛整個放棄、該出的警告不見;
- 非 UTF-8 不只在檔案內容裡:工具為了讓中文檔名能比對,好幾處刻意叫 git 不要轉義檔名,這時 Big5 之類的檔名位元組原樣吐出來,
  共改檢查挖歷史那一步會直接中斷;使用者自己把 `core.quotePath` 關掉(中文檔名的常見設定)時,連沒特別指定的呼叫也一樣。

所以改成機器保證:守衛測試讀工具的原始碼,找出每一個「文字模式、沒帶 errors=、跑的是 git 或看不出跑什麼」的呼叫,有一個就翻紅。
「看不出跑什麼」=命令從參數傳進來、或由函式算出來——代碼審第二輪兩席都抓到泛用包裝 `_sp_run_text(cmd)` 就是這樣漏的
(git 字樣只在呼叫端),所以寧可多抓;只放過命令清單開頭明確是別的程式的。
程式名稱放在變數裡(`exe = "git"`)也會往回找(第三輪外家席抓到原本會把它當成別的程式)。
守衛自己也餵壞的、好的、泛用包裝、別的程式、變數程式名五段,證明它真的會翻紅、也不會亂抓。行為面另有兩支測試:內容不是 UTF-8(風險掃描、推送檢查、波及計算、
派工鏡頭、不可逆提示掃描、刪除守衛)與檔名不是 UTF-8(測試分層、波及計算、共改檢查、測試地圖、代碼審留痕的有效性判斷)。

守衛只管 git。其他外部指令(抓網址、GitHub 查詢、查版本、呼叫自己)的輸出本來就是 ASCII 或 UTF-8,不在範圍內。

★放行本身沒改★:風險掃描真的壞掉時(例如 git 不在),推送檢查仍是放行、不擋人——那是刻意的設計,這次只拿掉「一個字元就能讓它壞掉」這條路。
