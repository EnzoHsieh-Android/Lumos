# 選擇點變異加速第四段代碼審接受風險的待補

## 症狀

代碼審第四輪(人裁加開的一輪)七席的發現,使用者裁「接受風險先推」:

- k1(major):第二段 S10 的「部分被取代」註記寫「合併基準逾時而輸出有 STARTED 事件行時,原因是 合併基準:逾時(跑到測試後掛住)」,但沒有測試真跑過 `merge_off` 與印出的那行;唯一的斷言只查 `_CHOICE_MERGE_BASE_WHY` 那張表。只影響一條罕見路徑的原因字樣,不影響判定。
- k2:`_choice_merge_shape` 新加的「含 {method} 的那一段緊接殼層元字元判形狀不支援」沒寫進計劃〈做法〉1、S1 條款與預期值表,函式說明的條件清單也沒列。
- k3:計劃〈做法〉3「照原字串帶出」與程式不符(印的字樣經 `_CHOICE_MERGE_BASE_WHY` 換字);〈落點〉沒列第二段 S10 的註記。
- k4:S2「截斷時 c 進未知層、順序 b、c、d、a」只在解析層斷言,沒有真跑逐支順序。
- e1:殼層元字元檢查沒看引號,引號裡的 `>`、`|` 也擋下合併(只少了加速)。
- g1、s1:`{method}` 後面緊接 `)`、反引號、`$(` 沒擋(合併基準白跑一次後退回逐支,不判錯);兩席都建議改成白名單。
- a1:`_CHOICE_MERGE_BASE_WHY` 新加的鍵手寫字面,沒用 `_CHOICE_MERGE_HANG_WHY`。
- a2:殼層元字元的字表沒取名成常數、沒寫跟 `_WIN_CMD_SPECIAL` 差在哪。
- r1:跑到測試後逾時的門檻 15,最壞多等 10 次快篩上限(設計審 r1 裁的取捨,受總時限夾住)。
- e2:`_choice_merge_events` 名字數 × 事件數,上千支測試時一次約 3 秒(修前就有)。

## 根因

修補時把精確的字樣與新規則寫進文件,卻沒有同一次把每一句對到一支真跑的斷言;同類缺口連兩輪各冒一處(跑滿回顧 `governance/review-reports/code-選擇點變異加速第四段/cap-retro.json`)。

## 現在怎麼繞

都不影響判殺掉或存活;合併判不了的情況退回逐支,只是慢。

## 什麼條件算修好

- k1:真跑一個合併基準逾時而輸出有 STARTED 的案例,斷言 `merge_off` 的值與標準錯誤那行。
- k2、k3:計劃〈做法〉1、S1 條款與預期值表寫進殼層元字元規則;〈做法〉3 改成實際字樣;〈落點〉補第二段 S10;函式說明列進條件。
- k4:真跑截斷案例斷言逐支順序。
- e1、g1、s1、a2:含 {method} 那一段改成白名單(只准一般字元、引號與 {method}),取名成常數、寫明跟 `_WIN_CMD_SPECIAL` 的分工;補 `)`、反引號、`$(`、引號內 `>` 各一案。
- a1:新鍵改用 `_CHOICE_MERGE_HANG_WHY`。
- r1、e2:不改,關單時寫一句理由。
