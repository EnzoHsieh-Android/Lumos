# 工作目錄治理資料讀端未走共用路徑守衛

白話:幾支讀「工作目錄裡的治理資料」(筆記內容審的判定檔、漂移表態帳)的函式,判斷資料夾安不安全時只看最後一層,沒用專案共用的逐層守衛;另有一處 JSON 解析沒接「巢狀太深」、一條讀不到資料夾的退路沒有測試。都是舊句兩道轉擋代碼審第四輪查到、修補前就有的同族問題,那條分支只修好了回頭重讀自己那一支。

REVISIT:2026-11-09 開一個改動,把下面三條一次掃完(先 grep 所有讀 governance/ 底下工作目錄資料的函式列清單,再逐支改走 _repo_path_unsafe)

## 症狀

1. **上層是符號連結時讀到 repo 外的檔**:`governance` 是指到 repo 外的連結時,筆記內容審的工作目錄讀端會把外面的判定檔當成已判定(`note-audit prepare` 因此回「沒有待審的筆記行」、跳過派判定者);漂移表態帳的讀端會讀外面的帳。寫端(`_note_audit_safe_dir`、`_drift_ledger_path_err`)同一情境拒寫,讀寫兩邊答案不同。
2. **判定檔巢狀太深時手動 check 崩潰**:`note-audit check` 讀到 13 萬層陣列的判定檔印出 RecursionError 堆疊。這道閘沒接進推送前掛鉤與 CI(那兩處只呼叫 `reread-check`),`doctor` 外層也有保護,所以只影響手動跑。
3. **退路沒有測試**:回頭重讀讀工作目錄紀錄時,守衛或列目錄丟 OSError 就當沒有紀錄;產品行為對,但把那個 except 改壞測試照綠。

## 根因

- 回頭重讀那一支在 2026-10-09 改走共用的 `_repo_path_unsafe(dirs=True)`(跟寫端同一份),同族的另外兩支讀端沒一起掃:它們不在那條分支的修補範圍,修前修後內容完全相同。
- `_note_audit_parse_verdict` 照舊只接 `(ValueError, UnicodeDecodeError)`;同一天兄弟閘讀設定的兩支已就地加接 RecursionError,讀判定檔這支是不同的檔案格式,沒在那次範圍裡。

## 現在怎麼繞

- 不要把 `governance` 或它底下的資料夾做成符號連結。最後的推送前檢查只認已提交的樹,所以第一條不會讓閘被繞過,只會讓 prepare 的提示誤導。
- 判定檔壞掉時刪掉那份重判。

## 什麼算修好

1. 所有讀工作目錄 `governance/` 底下治理資料的函式都經 `_repo_path_unsafe(dirs=True)` 判資料夾,各有一條「上層是連結」的測試。
2. `_note_audit_parse_verdict` 把巢狀太深當成讀不懂,有一條深層巢狀的測試。
3. `t_reread_wt_records_guarded` 有一組讀不到資料夾(例如 chmod 000)的案例,把外層 except OSError 改壞會紅。
