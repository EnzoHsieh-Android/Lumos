# 合約測試閘只在高風險推送跑

> 白話:有一道閘的職責是「改到帶硬合約的功能時,把那些合約綁的測試當場跑一遍」。
> 圖譜、計劃、三份說明書都寫「每次推送都跑」,但那行呼叫從第一天就寫在「高風險」那個分支裡面。
> 低風險的推送,合約綁的測試本機一次都沒跑;而持續整合又刻意跳過它,理由寫著「本機真跑」。
> **兩邊都在指望對方。**

## 可數的事實(逐條開檔查證過,不是轉述)

- 推送關卡腳本裡,`code-loop check` 的呼叫在「判定為高風險」的區塊內,
  而且還要再滿足「推的是分支不是 tag」這層條件。低風險推送根本不會呼叫到它。
- 持續整合設定檔把跳過合約測試的環境變數打開,註解逐字寫著
  「受波及合約測試在本機 pre-push 真跑;CI 已跑全套當後盾,不重跑」。
- 上一份計劃的需求第 1 條逐字寫著「`lumos code-loop check`(pre-push 每次推送都呼叫,不分 tier)」。
  **那句前提從一開始就不成立**,而那份計劃已經結案、還有一份通過的驗證紀錄。
- 三份說明書帶著同一個前提:代碼審與推送速查表、code-loop 說明書、自動跑的那張表。
- ★真正標 ★INVARIANT★ 的那一行本身沒有「每次推送」四個字★——帶這個前提的是它旁邊的白話流程段。
  這個區分很重要:要改的是流程說明,不是動合約行。
- `skills/lumos-project-notes/reference.md` **沒有**這個前提,它寫的是高風險才擋。

## 為什麼在本 repo 看不出來

本 repo 的推送關卡在那之後**無條件跑全套測試**,合約綁的那幾支本來就被跑到了。
看得出來的是**消費端專案**——它們沒有那道全套閘,而工具鏈也沒有分發任何 CI 樣板。

## 影響面

- 消費端的低風險推送,合約綁的測試**本機沒跑、CI 也沒跑**。
- 對不上的方向是最糟的那種:**宣稱有守、實際沒守**。讀文件的人(包括每個新 session 的 AI)
  會以為這道防線在,於是不會另外做。

## 順帶挖到的一條

上一份計劃寫「去重 38 支、28.7 秒」,它自己的驗證紀錄寫「42 支、28.9 秒」——
同一次量測兩份文件對不上。修的時候順手查清哪個才對。
