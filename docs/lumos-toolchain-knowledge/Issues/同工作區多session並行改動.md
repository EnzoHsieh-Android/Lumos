# 同工作區多session並行改動

> ★2026-09-01 Enzo 委任裁:誤報量測不辦——無自然數據源,硬量=再造假指標(引圖譜率案同週教訓);維持「三型再犯時回看」的事件入口★

> 白話:同一台機器、同一個工作目錄開兩個 Claude 對話一起做事,改動會互相波及。
> **git 不會攔,也沒有任何工具會喊。** 2026-08-22 一天撞到三次,兩次有實害。

## 三次實例(全部同一天,2026-08-22)

### ① 數字漂移:A 改的、B 修的、擋了測試

一邊把 `gov` 彙整的其中一本帳(rot-queue)的 loader 拆掉(寫帳的 hook 前一天已撤,留著是假名額),
但沒更新 [[Systems/reversibility-governance-ledger]] 裡「7 源」那個 Check N 可重算標記。

另一邊(不知情)跑全套測試,紅了一條——`t_claude_block_matches_template` 釘死
「本 repo doctor 整體 0 issues」,而 Check N 抓到 7 宣稱 vs 6 實測。

**★這條紅看起來像自己改壞的★**,查了半天才確定是另一個 session 的改動。

### ② 提交夾帶:訊息完全對不上內容

一邊做完自己的功能,`git add -A` 一掃,把另一邊當天全部的交付(三件功能 + 六篇圖譜改動)
一起 commit 進去,**訊息只寫自己的那件**。

被夾帶的內容本身是完整的(code 與測試沒被拆開),所以**沒有品質風險,但歷史讀不出真相**。
發現時還沒 push,已 amend 補一段「同批夾帶:…」載明來源。

★如果那時已經 push,就只能留一筆對不上的歷史★——這是本條最接近實害的一次。

### ③ 變數共用:結果是好的,但純靠人主動講

一邊新加的閘要用超時控制,直接沿用另一邊當天加的 `LUMOS_TEST_TIMEOUT`,沒有另立變數,
並主動傳訊說「你若改它的語意,這邊跟著動」。

**結果是好的**——沒長出第二個平行變數。但這完全來自那一邊主動開口,
**沒有任何機制會告訴你「你要改的這個東西,另一個 session 正在依賴」**。

## 為什麼現有的閘全部接不住

- **git**:同一個工作目錄就是同一棵樹,兩邊的改動天生混在一起。`git status` 分不出誰改的。
- **pre-commit / pre-push**:驗的是「這批改動合不合規」,不問「這批改動是不是同一個人的」。
- **`lumos doctor`**:驗圖譜一致性,對「改動來自幾個 session」沒有概念。
- **hook 推的必看合約**:推的是「你碰的檔關聯到哪些筆記」,不是「這個檔另一個 session 也在碰」。

**四層閘沒有一層的輸入裡有「session」這個維度。**

## 最小解形狀(★未立案,待裁★)

判準照家規:有症狀(三次,兩次有實害)、有消費者(同時開兩個對話的人=Enzo 本人),
但**最小解在哪一層還沒想清楚**,所以只記不做:

- **(a) 零機制,純紀律**:多開之前先講好誰動哪些檔。★問題:紀律沒有機械守衛,
  而本 repo 已有一整張 [[Issues/散文紀律沒有退場機制]] 在講這型的失效。★
- **(b) 提交時提醒**:pre-commit 看 `git diff --cached` 涉及的檔,若有檔案的
  mtime 明顯早於本 session 起始時間 → 印一句「這批可能夾帶了別人的改動」。
  ★零依賴、可機械判、不擋。但 mtime 是弱訊號,誤報率沒量過。★
- **(c) 用 git worktree 隔離**:各開各的工作樹,從根本上不共用。
  ★最乾淨,但代價是兩邊看不到對方的即時改動,而今天有幾次「看得到」反而是好事
  (數字漂移是另一邊順手修掉的)。★

**我的傾向是 (b)**,理由:(a) 沒守衛、(c) 代價大且會擋掉今天證明有用的互相補位。
但 (b) 的誤報率沒量過,量之前不該立案。

## 重驗條件

**下一次同工作區多開對話時,看這三型有沒有再犯。** 再犯一次、或出現一次
「已 push 才發現夾帶」的實害 → 升級為待處理,先量 (b) 的誤報率。

## 這條不涵蓋什麼

- **不涵蓋跨機器/跨 repo 的並行**——那是 [[Projects/跨session傳訊用途調研]] 的射程。
- **不涵蓋「兩個 session 該不該同時開」**——今天的實跑證明對審本身價值很高
  (另一邊打掉了三個站不住的提案、抓到一個會出事的超時設定)。
  ★本條只談「共用同一棵工作樹」的代價,不談協作本身。★

## 第四次(2026-09-07):新型——**對方存到一半的壞檔,讓我這邊每個指令都失敗**

事件入口成立(那條裁定寫的是「三型再犯時回看」),而且這次是**前三型都沒有的第四型**。

### 發生什麼

同一棵工作樹,一邊在跑設計審迴圈、一邊在做執行 DAG 調研並實作一支新子命令。
調研那邊改到 `scripts/lumos` 的過程中,檔案短暫處於**語法壞掉**的狀態
(字串裡出現真的換行)。這邊在那個瞬間跑 `lumos lint`,拿到的是 Python 的語法錯誤。

★關鍵是它長得不像別人造成的★:訊息是「`scripts/lumos` 第 5341 行字串沒收尾」,
第一反應會是「我自己剛剛寫壞了什麼」。我開始查損壞範圍、準備動手修——
**再看一次發現它自己好了,檔案修改時間是 7 秒前。** 那時才確定是另一邊正在即時寫。

### 為什麼這型比前三型更難

- 前三型(數字漂移、提交夾帶、變數共用)都是**事後**才發現,但發現時證據還在。
- 這一型是**瞬時的**:壞檔可能只存在幾秒。等你去查,現場已經沒了,
  而你手上只有一個看起來像自己造成的錯誤訊息。
- **它會誘發破壞性的補救**:我差一點就動手「修」對方寫到一半的檔。
  真的修下去,就是兩邊同時改同一段——比原本的問題嚴重得多。

### 這次沒有實害的原因,以及它有多脆

- **沒有夾帶**:我最後一個提交(08b0e61)時間點剛好在對方開始改之前,查證過沒有夾到。
  ★但這是運氣,不是機制★——我整場用的都是 `git add -A`,正是第二型點名的那個動作。
- **沒有誤修**:因為我多看了一次修改時間。★如果我第一次就動手,就出事了★。

### 這次真正管用的是什麼(值得記,因為它不在上面任何一個候選解裡)

**對方主動傳了一則訊息過來**,列出它動了哪些檔、明說它不會 commit、並提醒不要用 `-A`。
這跟第三型「純靠人主動講」是同一件事——**但這次是機器對機器講的,不是人轉述**。

所以最小解的候選清單要多一條:

- **(d) 同工作區的 session 之間直接互相通報**:開工時廣播「我要動哪些檔」,
  收工時廣播「我停手了」。成本近乎零。
  ★它擋的是「誤修」與「提交夾帶」,不是壞檔本身★——知道有人在動那支檔,你就不會去修它。
  問題:要兩邊都記得,忘了講就沒有。
- **(e) 寫側做原子存檔**(★寫的那一邊自己就能解決,不必兩邊配合★):
  寫暫存檔 → 自驗(對 Python 檔就是重新 parse 一次)→ 原子改名。
  **壞檔窗口是零,不是「幾秒」**。
  ★這條是這個 repo 本來就有的慣例,只是從來沒有人把它套用在「AI 改共用工具檔」上★:
  圖譜裡至少六篇計劃寫過「寫入一律 tmp→自驗→atomic」這條約束,
  而且 `scripts/lumos:9202` 有一支 `atomic_write_verify` 已經把這個形狀實作出來。
  **單邊就能生效的解,天生比雙邊解可靠**——(d) 要兩邊都記得,(e) 只要寫的那一邊做。

  ★精修(造成方 2026-09-07 開檔複驗後補):那支函式不能直接拿來用★——
  它的射程是**筆記的開頭欄位**:會去 parse frontmatter、確認要寫的欄位值真的寫進去了、
  並比對「有沒有引入新的 lint 指紋」,失敗就丟掉暫存檔、原檔不動。
  ★拿它去寫一支 `.py` 會直接爆掉★(那支檔沒有 frontmatter 可 parse)。
  所以可借的是**形狀**不是函式本身;而且它的自驗比「`ast.parse` 過得去」更嚴——
  它問的是「寫回去的值真的是我要的嗎、有沒有順手弄壞別的東西」。
  改 Python 原始碼的對應物是:寫 tmp → `ast.parse` → (可選)跑一次相關測試子集 → `os.replace`。
  **這個精修本身就是「宣稱程式碼是怎樣」那一型**:寫「現成函式就在那裡」讀起來像可以直接呼叫,
  實際上射程完全不同——要開檔看過才知道。

### ★我在這一段自己又犯了一次同型★

上面 (d) 那條,我第一版寫的是「**它是唯一能處理瞬時壞檔那一型的做法**」。
另一個 session 更正我,我去查證之後確認**它是對的、我那句「唯一」是錯的**——
(e) 不但存在,而且更好,而且是這個 repo 自己的既有慣例。

**時間點值得記**:我寫那句「唯一」的時候,距離我寫完

### 這次得到的可操作紀律(不是候選解,是現在就照做的)

1. **多開時一律逐檔 `git add`,不准 `-A`**。這條之前就寫在第二型裡,但沒有人在遵守——
   ★包括我自己整場都在犯★。
2. **指令突然壞掉、而錯誤指向一支共用檔時,先看那支檔的修改時間**。
   幾秒前被動過就是別人在寫,**不要動手修**。
3. **不要替另一個 session 修它寫到一半的東西**——等它說停手。

### ★寫的那一邊怎麼造成的(2026-09-07 由造成方補;只有寫的人知道)★

**成因是「分兩次存檔」,不是「寫得慢」。**

那次改 `scripts/lumos` 是用腳本做字串替換再整檔寫回。第一次寫進去的內容裡,
字串常數中的換行跳脫被產生器展開成**真的換行**,檔案當場語法壞掉;
發現後第二次寫回才修好。**兩次寫入之間大約一分鐘,樹上放著一支壞檔。**

★這裡的關鍵:本 repo 早就有一條慣例能擋住它★——實作計畫的共同約束寫著
**「寫入一律 tmp→自驗→atomic」**。那條一直被當成「工具寫帳本」時的規矩,
**沒有人把它套用在「AI 自己改共用工具檔」上**。這次證明兩者是同一件事。

**寫側的最小解(成本近乎零,只要寫的那一邊做)**:

1. 產生新內容 → 寫到暫存檔;
2. 就地自驗(Python 檔就 `ast.parse`,JSON 就 `json.loads`);
3. 驗過才原子換上去(`os.replace`)。

這樣壞檔的窗口是**零**,而不是「幾秒」。

### 因此要更正上面一句話

上面寫「(d) 同工作區 session 互相通報**是唯一**能處理瞬時壞檔那一型的做法」——**這句不成立**。

- **(e) 寫側原子存檔**才是根治:它消掉的是壞檔本身,而不是消掉「被誤判成自己造成的」這個後果。
- 而且 **(e) 只需要寫的那一邊做**,(d) 要兩邊都記得廣播——★單邊就能生效的解,天生比雙邊解可靠★。
- **(d) 仍然有價值,但價值不在防壞檔**:它的價值是「知道現在有人在動這支檔」,
  那能擋掉的是**誤修**(第四型裡差一點發生的破壞性補救),以及第二型的提交夾帶。

### 這一段不涵蓋什麼

  那是另一個層級的東西,本次不主張。
- **本次沒有量過**「分兩次存檔」在日常改動裡佔多少比例——只知道這次是這樣。

## 第五次(2026-09-08):新型——**我 `git add` 了不屬於我的改動,推上主線變成自相矛盾**

**這一型最危險的地方是:「逐個檔明寫、不用 `add -A`」擋不住它。**
前四型都是兩個 session 動不同的檔或同一個檔的不同時刻;這一型是
★同一個檔裡同時有我的改動和別人的改動★,而 `git add <那個檔>` 是全有全無的。

**經過**:我要提交自己對 `scripts/test_lumos.py` 的兩處修改,`git add` 了那個檔。
當時同一棵樹上另一個 session 正在改同一個檔(Codex 外家席從一席改成兩席,
在 `t_codex_d6_agent_toml` 加了五條斷言、改了一條既有斷言),**還沒提交**。
於是他們的測試改動跟我的一起被提交、一起推上遠端。

**後果**:主線變成自相矛盾——**測試要求兩份席位設定檔,而對應的 `scripts/lumos` 實作
還在對方的工作樹裡沒提交**。CI 當場紅:4286 passed / 2 failed。
本機推送閘沒擋住,因為本機工作樹裡「實作」也在,兩邊剛好對得上。
★也就是說:同工作區的未提交改動會讓本機的閘看到一個遠端不存在的世界。★

**還有一個連帶傷害**:我在回報裡跟對方說「那 7 條紅全部歸你」,那句話是錯的
——至少兩條是我造成的。我當時只看了自己最後一次全套的結果(全綠),
沒想到「我推上去的內容」跟「我本機跑的內容」不是同一個東西。

**怎麼收的**:
1. `git diff <commit>^ <commit> -- <檔>` 逐塊分辨哪些是我的、哪些是別人的——這次很乾淨,
   兩塊分屬兩個不同的函式。
2. 只回退別人那一塊(commit `3f32e34`),我自己那塊保留。
3. **把對方那段原樣寫回工作樹、維持未提交狀態**——不能只回退了事,那會讓對方的活消失。
4. 驗證用 `git worktree add --detach HEAD` 開一棵**乾淨的樹**跑全套
   ——★這是唯一能證明「主線本身」是綠的方法★,在髒樹上跑證明不了。
5. 推的時候錨點驗證擋下(工作樹的裁判檔含對方未完成內容),
   **不替別人未完成的檔簽名**,改走 `--no-verify` 並用 `lumos code-loop skip --note` 留痕,
   註明理由與「乾淨工作樹 4291/0」這個佐證。

**可以立刻用的兩條**(不需要等最小解立案):

- **提交前對每個要 add 的檔跑一次 `git diff -- <檔>`,問「這裡面每一塊都是我改的嗎?」**
  不是的話,用 `git add -p` 只挑自己的塊。
- **推之前,如果工作樹是髒的而且髒的不只你自己的檔,就在乾淨工作樹上驗一次**:
  `git worktree add --detach /tmp/verify HEAD && cd /tmp/verify && <跑全套>`。
  本機閘跑在髒樹上,證明的是「這棵樹綠」,不是「主線綠」。
