# 同工作區多session並行改動

> ★2026-09-01 Enzo 委任裁:誤報量測不辦——無自然數據源,硬量=再造假指標(引圖譜率案同週教訓);維持「三型再犯時回看」的事件入口★

> 白話:同一台機器、同一個工作目錄開兩個 Claude 對話一起做事,改動會互相波及。
> **git 不會攔,也沒有任何工具會喊。** 2026-08-22 一天撞到三次,兩次有實害。

## 三次實例(全部同一天,2026-08-22)

### ① 數字漂移:A 改的、B 修的、擋了測試

一邊把 `gov` 彙整的其中一本帳(rot-queue)的 loader 拆掉(寫帳的 hook 前一天已撤,留著是假名額),
但沒更新 [[Systems/reversibility-governance-ledger]] 裡「7 源」那個 Check N 可重算標記。

另一邊(不知情)跑全套測試,紅了一條——`t_claude_block_matches_template` 釘死
「本 repo doctor 整體 0 issues」,而 Check N 抓到 7 宣稱 vs 6 實測。

**★這條紅看起來像自己改壞的★**,查了半天才確定是另一個 session 的改動。

### ② 提交夾帶:訊息完全對不上內容

一邊做完自己的功能,`git add -A` 一掃,把另一邊當天全部的交付(三件功能 + 六篇圖譜改動)
一起 commit 進去,**訊息只寫自己的那件**。

被夾帶的內容本身是完整的(code 與測試沒被拆開),所以**沒有品質風險,但歷史讀不出真相**。
發現時還沒 push,已 amend 補一段「同批夾帶:…」載明來源。

★如果那時已經 push,就只能留一筆對不上的歷史★——這是本條最接近實害的一次。

### ③ 變數共用:結果是好的,但純靠人主動講

一邊新加的閘要用超時控制,直接沿用另一邊當天加的 `LUMOS_TEST_TIMEOUT`,沒有另立變數,
並主動傳訊說「你若改它的語意,這邊跟著動」。

**結果是好的**——沒長出第二個平行變數。但這完全來自那一邊主動開口,
**沒有任何機制會告訴你「你要改的這個東西,另一個 session 正在依賴」**。

## 為什麼現有的閘全部接不住

- **git**:同一個工作目錄就是同一棵樹,兩邊的改動天生混在一起。`git status` 分不出誰改的。
- **pre-commit / pre-push**:驗的是「這批改動合不合規」,不問「這批改動是不是同一個人的」。
- **`lumos doctor`**:驗圖譜一致性,對「改動來自幾個 session」沒有概念。
- **hook 推的必看合約**:推的是「你碰的檔關聯到哪些筆記」,不是「這個檔另一個 session 也在碰」。

**四層閘沒有一層的輸入裡有「session」這個維度。**

## 最小解形狀(★未立案,待裁★)

判準照家規:有症狀(三次,兩次有實害)、有消費者(同時開兩個對話的人=Enzo 本人),
但**最小解在哪一層還沒想清楚**,所以只記不做:

- **(a) 零機制,純紀律**:多開之前先講好誰動哪些檔。★問題:紀律沒有機械守衛,
  而本 repo 已有一整張 [[Issues/散文紀律沒有退場機制]] 在講這型的失效。★
- **(b) 提交時提醒**:pre-commit 看 `git diff --cached` 涉及的檔,若有檔案的
  mtime 明顯早於本 session 起始時間 → 印一句「這批可能夾帶了別人的改動」。
  ★零依賴、可機械判、不擋。但 mtime 是弱訊號,誤報率沒量過。★
- **(c) 用 git worktree 隔離**:各開各的工作樹,從根本上不共用。
  ★最乾淨,但代價是兩邊看不到對方的即時改動,而今天有幾次「看得到」反而是好事
  (數字漂移是另一邊順手修掉的)。★

**我的傾向是 (b)**,理由:(a) 沒守衛、(c) 代價大且會擋掉今天證明有用的互相補位。
但 (b) 的誤報率沒量過,量之前不該立案。

## 重驗條件

**下一次同工作區多開對話時,看這三型有沒有再犯。** 再犯一次、或出現一次
「已 push 才發現夾帶」的實害 → 升級為待處理,先量 (b) 的誤報率。

## 這條不涵蓋什麼

- **不涵蓋跨機器/跨 repo 的並行**——那是 [[Projects/跨session傳訊用途調研]] 的射程。
- **不涵蓋「兩個 session 該不該同時開」**——今天的實跑證明對審本身價值很高
  (另一邊打掉了三個站不住的提案、抓到一個會出事的超時設定)。
  ★本條只談「共用同一棵工作樹」的代價,不談協作本身。★
