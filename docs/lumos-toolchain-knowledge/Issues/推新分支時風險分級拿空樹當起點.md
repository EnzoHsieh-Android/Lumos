# 推新分支時風險分級拿空樹當起點

> 白話:推送前的守衛會先算「這批改動有多高風險」,高風險就擋下來要求先跑代碼審。但**推一個遠端還沒有的分支時,它沒有東西可以比對,就退回拿「空樹」當起點**——等於把整個 repo 當成全新檔案在算。2026-09-03 實測:它算了 **1841 個檔案**判 `tier: high`,而那次真正的改動只有 **25 個檔案**、用正確範圍算是 `standard`。

## 這不是 bug,是刻意的保守設計

`scripts/hooks/pre-push` 的範圍推導有三條分支,註解寫得很清楚:

- `remote_sha` 全零(新 ref,★含首推 main★)→ `_range="$_EMPTY_TREE..$_lsha"`,註解:「保守掃全部引入內容」
- `remote_sha` 本地找不到該物件(shallow / force-push 分岔未 fetch)→ 同樣退回空樹
- 一般情形 → `_range="$_rsha..$_lsha"`(增量)

★所以「拿空樹當起點」是明寫的 fallback,不是漏寫★。立這張單不是說它寫錯,是說**它的下游後果沒被想過**。

## 實際咬到的一次(2026-09-03)

- 動作:在 main 上做完一批圖譜改動,開新分支 `seat-coverage-offline-measure` commit 後推送。
- 結果:pre-push 跑完全套測試(★單獨計時超過 10 分鐘★)之後才擋下,理由是 `tier: high` 需要代碼審。
- 事後用正確範圍重算:`lumos pitfalls --diff Lumos/main..HEAD --no-lint` → **`tier: standard`**。那批 25 個檔案是 24 份 markdown 加一支唯讀 python 腳本。
- 處置:改推主線(遠端有 `main` 可比,範圍回到 25 個檔案),閘自然過,★沒有動用任何繞過機制★。

## 為什麼值得記(而不是「知道了就好」)

**三條出路裡有兩條是繞過守衛**:①跑一輪代碼審 ②留一句理由跳過(`code-loop skip`)③強制推(`--no-verify`)。
當一個閘在可預期的情境下常態誤報,①的成本又是「跑一輪多席代碼審」,人會很自然地走②或③。
★一個常態誤擋的閘,會訓練人習慣性繞過它——那比閘不存在更糟,因為帳面上看起來還有守衛。★

這與 [[Verification/2026-09-03_席間覆蓋率離線量測]] 量到的是同一類問題:**守衛的「叫」與「不叫」一旦跟真實風險脫鉤,它就從證據退化成儀式。**

## ★誠實界線:影響面比第一眼小★

- **這個 repo 的慣例是本地開分支、本地合併、只推 main**。實查:遠端 `git ls-remote --heads Lumos` ★只有 `main` 一個分支★,而本地有 8 個功能分支、歷史上有多筆 `merge: …` 提交。所以空樹那條路平常不會被走到,**是我偏離慣例(推分支上遠端)才踩到**。
- **不能把既有的跳過次數算在這個原因頭上**。治理帳裡 `code-loop` 閘共 120 筆:93 passed / 27 skipped(22.5%)。★這 27 次是不是因為誤判而跳過,我沒查、也不確定查不查得出來★——這裡只當背景數字,不當本單的證據。
- **首推 main 也會走空樹**(註解自己點名)。對這個 repo 已經沒差(main 早就在遠端),但對「用 lumos 的新專案」第一次推 main 時會遇到——那時候整個 repo 本來就都是新的,保守掃反而合理。所以這條 fallback 在「首推」情境是對的,問題只在「已有 main、另推分支」這個情境。

## 可能的修法(未裁,三個方向)

1. **新 ref 時退回跟預設分支比,而不是空樹**:`_range="$(git merge-base Lumos/main $_lsha)..$_lsha"`,取不到 merge-base 才退空樹。★風險:預設分支名不一定叫 main、遠端名不一定叫 origin,要先解出來;解錯會讓範圍變小=守衛變鬆,比現在的假陽性嚴重。★
2. **不改範圍,改訊息**:偵測到走的是空樹分支時,在擋下的訊息裡加一句「這次是新分支、範圍是整個 repo,可能是誤判;想確認請跑 `lumos pitfalls --diff <遠端預設分支>..HEAD`」。★成本最低、不動判準,但只是讓人更容易正確地繞過,沒有解決誤報本身。★
3. **不做**:記著這件事,遇到就用主線推。★這個 repo 的慣例本來就只推 main,誤報幾乎不會發生。★

★傾向:2 或 3,不傾向 1★——理由是 1 會讓守衛在解析失敗時變鬆,而本單抱怨的是「假陽性」,拿「可能變假陰性」去換不划算。但這是我的判斷不是裁定,留給下一個人。
