# 工具把自己安裝進去的檔，當成消費專案的程式碼在算

> 白話：一個小專案接進來，健檢當場掛掉；勉強跑起來之後，它又拿工具自己的檔當證據說你設定錯了。

## 怎麼撞到的

2026-09-10 接入第一個小型的前端專案（Vue，六個 JavaScript 檔）。
接入流程本身沒改，但這是**第一個同時滿足「很小」與「用多平台設定」的消費專案**——
自家 repo 和先前那幾個消費專案都不長那樣，所以接入靜默失效那七項落地當時是全綠的。

## 三個毛病，同一個病根

★病根一句話★：**工具會把自己複製到每個消費專案的 `scripts/` 底下，
而好幾處掃描把那些檔當成「這個專案的程式碼」。**
專案愈小，工具自己的體積佔比愈高——而剛接入的專案通常最小。

### ① 健檢整支中斷

多平台設定裡，每個平台那筆資料的「設定」欄位存的是**攤開後的設定物件**，
但技術棧那段檢查拿它當「設定的名字」去查表——用一個物件當查表的鍵，直接丟例外。

後果不是「那一段沒結果」，是**整支健檢死在那裡**，後面所有檢查都不跑。
而且任何用多平台格式的專案都會撞到，不分大小。

修法：那個欄位本來就是攤開的設定，直接用，不要再查一次表。
補了兩個案例：設定對的時候要安靜、設定錯的時候照樣要出聲。

### ② 拿自己的檔當證據唸人

工具會把自己的程式、自己的測試檔和五支 hook 複製到每個消費專案的 `scripts/` 底下，
那是**八個 Python 檔**。那個 Vue 專案自己只有六個 JavaScript 檔。

於是健檢數一數副檔名，說「你有 8 個 .py 但測試設定只認 .js，掃不到這些檔裡的測試」——
**舉的證據全是工具自己放進去的檔**。

★這個病的形狀值得記住★：**專案愈小，工具自己的體積佔比愈高，愈容易被自己唸**。
而剛接入的專案通常最小——也就是說，它專挑第一次用這套工具的人唸。

修法：算技術棧時跳過工具自己安裝的那些檔——★只認精確檔名★（見③的補記）。

### ③ 風險分級被撐成 high，推送被擋

這是同一個病最嚴重的一次。

那個 Vue 專案第一次提交，風險掃描報了 30 條，**沒有一條在專案自己寫的程式碼裡**——
全部在工具的 CLI 和五支 hook 裡。分級因此判成高風險，推送被擋下，
要求先對「一份不是自己寫的程式」做代碼審。

修法跟②同一套跳過判斷。★但這裡多一道★：**工具鏈自己的 repo 不能跳過**——
在那裡 `scripts/lumos` 就是產品本體，一起跳等於把這個閘整個關掉。
判別鍵沿用既有慣例：user-scope skill 的唯一源永遠不會被複製進消費專案。

★代碼審第一輪抓到的補記（2026-09-10）★：第一版是照「目錄」跳過（scripts/hooks、scripts/templates 整個不看），
**消費專案自己放在那兩個目錄底下的程式也一起被跳過**——四個審查員各自獨立抓到，其中一個直接做出
「帶後門的 hook 推得上去」的重現。改成只跳過一張「工具確實安裝的檔」精確清單：同名同路徑才算，
同目錄的其他檔照樣掃。清單要跟工具鏈 repo 裡那兩個目錄的受版控檔一模一樣，有測試逐檔比對。
另外兩個漏網的地方一併補上：lint 那一層原本沒套跳過、刪除行那條路少傳了一個參數。

★第三輪補上內容比對（2026-09-10）★：第一輪收尾時我把「消費專案改了工具自己的檔，改的內容會被跳過不審」
列成以後再看；第三輪被判重大——把風險程式碼放進那 15 個路徑之一，風險掃描就完全看不到。現在：
- 安裝與更新時，在 `.lumos/vendored.json` 記下每支工具檔的內容指紋（換行統一後的 sha256）；這個資料夾在消費專案本來就進版控，CI 看得到；
- 風險掃描看「改動範圍終點」那個版本的內容、健檢看工作目錄的內容：**檔名在清單上、而且內容跟指紋一模一樣**才跳過；
- 終點上整支刪掉、但起點時原封不動的工具檔（拆除工具鏈）也跳過，拆除時指紋清單一起拿掉；
- 沒有指紋清單（舊版安裝）→ 一支都不跳，寧可多掃；那些專案跑一次 `lumos update` 就會有清單；
- ★安裝只複製精確清單上的檔★（第三輪外家否決席：原本整個目錄照來源全抄，來源裡沒進版控的檔也被裝進去，
  可是跳過清單只列受版控的檔——裝進去的檔不在清單上，又被當成專案自己的程式掃）；
- 比對「清單＝來源受版控的檔」的那支測試只在工具鏈本體跑（在消費專案裡跑沒有意義，專案自己在 scripts/hooks 放檔就會假紅），
  並加進「模擬消費專案跑工具鏈測試」的回歸清單。

★邊界★：指紋清單本身放在專案裡，改工具檔的人如果連清單一起改，一樣跳得過——這道判斷防的是
「不小心改到工具檔、或把自己的程式放成工具的檔名」，不是刻意繞過的安全邊界。
REVISIT:2027-03-10 看治理帳有沒有「工具檔跟指紋清單在同一次提交裡一起被改、而且不是 lumos update 做的」推送;有就改成跟工具鏈來源比對,不再只信專案裡的清單

### ④ about_code 有一種寫法沒有指令改得動（同一天順手修的）

跟前三個不是同一個病根，但同一天、同一批專案撞到，一併記在這裡。

這個欄位是**清單**，列「這篇筆記主要在講哪幾支程式檔」（0 到 3 支）。它的作用是**排序**：
改那支檔的時候，這篇會排在前面給人看。★它不建立波及連結★——波及計算看的是正文裡用反引號寫出的路徑。

問題是有一種寫法沒有指令改得動：

- 讀的一側把「單一值寫法」（`about_code: src/x.ts`）當成一項的清單，沒問題；
- 寫的一側，`append` 卻說它不是清單、拒絕；`set` 又不收清單欄位——**從此沒有指令改得動**。

所以只能手改。手改一手滑，就成了「路徑後面多一個空清單記號」這種值：它不是路徑，
★後果是那篇的排序加分失效，健檢 [S4] 也會一直唸★（波及計算本身不受影響）。
從 git 歷史逐筆數：兩個消費專案加工具鏈自己，一共 13 篇（8 + 4 + 1），已全部修好。

修法：**`append`／`remove` 認得單一值寫法**（先改寫成一項的清單再加或刪），
`append` 寫 about_code 時★檢查路徑★：絕對路徑、跳出 repo、不存在、目錄都擋下，存成正規化的相對路徑。

★第一版修錯了，代碼審抓到★：第一版以為這個欄位「實務上都是單一路徑」，另開了一條 `set` 專用路。
結果會把**既有的多筆清單靜默壓成一筆**（四個審查員各自抓到）、絕對路徑與 `../` 可以繞出 repo、
含「: 」的路徑沒加引號寫出壞的欄位區、寫進去之後 `remove` 又清不掉，而且同一個欄位 `set` 當純量、
`append` 當清單，兩套規則。**前提就錯了**——這個欄位本來就是清單。第二版拿掉那條 `set`，改成上面的做法。

★第二版又差一點寫壞，第二輪派人之前自己抓到★：「把單一值改寫成一項的清單」這一步，碰到**同一行的清單寫法**
（`about_code: [src/a.ts, src/b.ts]`）會把整串 `[src/a.ts, src/b.ts]` 當成一項寫進去——原本工具遇到這種寫法是擋下的
（讀寫兩側都不解析同一行裡的逗號），第二版把「擋下」變成了「寫壞」。現在恢復成擋下，訊息講清楚要手動改成一行一項；
單一個連結寫成 `[[X]]` 不算同一行清單，照舊可以接著加。所有清單欄位（不只 about_code）都適用。
全庫與兩個消費專案的開頭欄位裡，這種寫法目前**零篇**，所以只擋不解析。

★第一版的擋法又被第二輪兩個審查員各自繞過★：它比對的是「原始字串長什麼樣」，
於是整串加引號（`"[a, b]"`）、逗號前後多打一個空白（`[[A]],  [[B]]`）都擋不到，照樣寫壞。
判準改成**看去掉引號後的值本身**，不列舉寫法：以 `[` 或 `{` 開頭（單一連結 `[[X]]` 除外）、
或一個值裡出現兩個以上連結開頭，就擋。加了引號的空清單 `"[]"` 跟讀的一側一樣當成空的。

同一輪順手收掉的四個小洞（都是「同一支檔被當成兩筆」或「訊息說謊」）：
- 值已經在了還是會把單一值寫法改寫成清單格式、還印「多了一項」→ 現在真的什麼都不做，訊息講「已經有了，檔案沒動」；
- about_code 的既有值寫成 `src/../src/a.ts`，再加 `src/a.ts` 會疊出第二筆 → 按正規化後的路徑去重；
- `remove` 沒走同一套正規化，用 `src/../src/c.ts` 加進去的值用同一個寫法刪不掉 → `remove` 也按正規化後的路徑找（只做字面正規化，
  不要求檔案還在：檔已刪掉的舊項也要清得掉）；
- 大小寫寫錯（`SRC/A.TS`）在大小寫不敏感的磁碟上也會通過 → 擋下並指出磁碟上的真實寫法。
  ★這不只是整潔問題★：排序加分拿 about_code 去比對 git 的改動路徑（大小寫敏感），寫錯就永遠對不上。
  只差 Unicode 寫法的（é 一個字 vs e 加重音符號）算同一個檔、照收：Mac 的磁碟兩種都認，目錄清單卻只列存進去的那一種，
  第一版逐層比對會把它誤當成大小寫寫錯（派第三輪之前自己抓到）。

★第三輪（2026-09-10，五席 Claude＋兩席外家）又抓到一批，都修了★：
- 「是不是同一支檔」只看字面時，symlink 別名、舊的大小寫錯字項都會被當成另一支檔，疊出重複又刪不掉 →
  比對鍵改成「檔案還在就看它在磁碟上的真實位置（解 symlink、大小寫與 Unicode 寫法照磁碟），不在了才看字面」，append 去重與 remove 找項共用；
- Windows 反斜線寫法（`src\a.ts`）永遠「找不到」→ 先轉成斜線；
- 目錄讀不到檔名清單時，大小寫檢查被當成「寫對了」放行 → 改成擋下並講明讀不到；
- 同一行清單「一個值裡兩個以上連結」讀的一側只認兩種寫法、寫的一側認全部，兩套規則 → 清單欄位讀寫共用同一個判斷
  （散文欄位講到兩個連結照舊不唸；現有筆記與三個消費專案零篇因此新翻紅）；
- 排序加分那一側讀 about_code 只剝開頭的 `./`、不解 `..` → 跟寫入側共用同一個路徑正規化；
- `lumos new verification --systems` 回掛時被同一行清單擋下，擋下訊息蓋掉了「新筆記其實已經建好」→ 照舊印「筆記建好了，但回掛沒成功」；
- ★同一篇筆記同時被好幾個程序寫★：暫存檔名是固定的，大家搶同一個暫存檔，實測六個同時跑六個都噴錯、一項都沒寫進去；
  就算不撞名，讀—改—寫之間沒有鎖，回報成功的也會被蓋掉 → 暫存檔名每次不同（照既有的 mkstemp 先例），
  set/append/remove 在同一個筆記庫上排隊做（鎖檔放系統暫存目錄，不弄髒筆記庫，程序結束自動放掉）。
  其他寫入指令（decision-add 等）還沒套這把鎖，照舊是後寫的蓋掉先寫的。
- 外家兩席另外抓到的：①單一值轉清單時，含雙引號的舊連結被重新加引號、加了反斜線，讀回來就不是原本那篇
  → 原本那一項有引號就照原樣搬；而且 append/remove 寫完的自我檢查原本只驗「新項在／要拿的不在」，
  現在也驗★原本其他每一項都還在★；②同一行清單的檢查還有兩種繞法（`[[Systems/A], Systems/B]` 開頭像連結的巢狀清單、
  引號裡面前面多一個空白）→ 單一連結要「整個值恰好是一個連結」才豁免（跟讀的一側索引連結用同一個判斷），判斷前先去空白；
  ③remove 同一支檔寫了兩種寫法時只拿掉一筆 → 每一種寫法都拿掉。
REVISIT:2026-12-10 盤點其他寫入指令(decision-add、new 等)有沒有同時寫同一篇被蓋掉的案例;有就套同一把鎖

★第四輪（2026-09-10，高風險三輪上限後由 Enzo 裁定加開；五席 Claude，外家兩席撞 Codex 用量上限沒產出）★：
