# 測試現場的假設會隨實作過期

> 白話:測試不只驗「輸出對不對」,它還**帶著一套關於現場長什麼樣的假設**。換掉實作的判斷依據時,輸出可能照樣對,但★現場的假設會靜靜地失效★——於是測試要嘛假綠(什麼都沒發生也通過),要嘛全紅(而每個紅都是新行為的正確表現)。兩種都會誤導人。

## 同一天踩到兩次(2026-09-18,收工點名改問版本控制那一批)

那批改動把「這一輪改了哪些程式碼檔」的判斷,從**讀對話紀錄認工具名**換成**問版本控制工作樹狀態**。

### 第一次:既有的擋停測試

那支測試造完現場就 commit,工作樹是乾淨的,只在對話紀錄裡「宣稱」改過某支檔。
- 舊實作讀紀錄 → 信了 → 測試綠。
- 新實作問工作樹 → 看到乾淨 → 閉嘴 → 測試紅。

**紅的是現場不真實,不是程式錯**:它要測「改了碼沒寫回」,那就該真的改檔。改的是現場,不是斷言。

### 第二次:給人手動跑的情境產生器

同一個形狀,但更難發現——**因為它不在測試套件裡,不會被 CI 抓到**。九個情境全部 FAIL,而每一個 FAIL 都是新行為的正確表現。

★更糟的一層★:它是**撤除條件依賴的儀器**(「每季重跑一次,情境全部回到修前結果就撤掉這條路徑」)。壞掉的它會永遠全 FAIL,那個判準等於永遠成立——**撤除條件被自己的儀器架空**,而且會在三個月後給出一個看起來有依據的錯誤結論。

★第一次踩到時已經處理過一次,卻沒想到第二處★:當下只修了正式測試,沒回頭問「還有什麼東西帶著同樣的舊假設」。

## 通則

**換掉「判斷依據」而不只是「判斷結果」時,要回頭掃一遍所有帶著舊依據假設的現場。**

不只是測試套件——還有:
- 給人手動跑的儀器、探針、評估腳本(它們不在 CI 裡,壞了沒人知道)
- 撤除條件、回頭條件所依賴的量測工具(壞了會讓判準永遠成立或永遠不成立)
- 文件裡寫的「怎麼驗證這件事」步驟

## 怎麼分辨「該修現場」還是「該修程式」

看紅的**方向**:

| 症狀 | 多半是 |
|---|---|
| 測試紅,而紅的內容正是新行為該有的樣子 | **現場的假設過期**——修現場 |
| 測試綠,但你拆掉新實作它照樣綠 | **現場沒有真的觸發**——現場假綠,修現場 |
| 測試紅,新行為確實做錯了 | 修程式 |

★最後一種跟第一種容易混★:判準是「照新的設計,這個現場本來就該得到這個結果嗎」。是的話就是現場過期。

## 怎麼避免

- 造測試現場時,**讓現場真的發生那件事**,不要只在紀錄/中繼資料裡宣稱。這條比「斷言寫得對」更基本——斷言驗的是結果,現場決定了結果有沒有機會發生。
- 儀器類腳本(不在 CI 裡的)**加一條自我檢查**:先跑一個「一定會觸發」的對照情境,它不過就代表儀器本身壞了,而不是被測物有問題。
- 改判斷依據時,**用關鍵字掃一遍**哪些地方在造現場(臨時倉庫、假逐字稿、mock 資料),逐個問「這個現場在新依據下還成立嗎」。
