# 推送只跑受影響測試代碼審放行的小問題

## 症狀

代碼審 code-推送只跑受影響測試 三輪裡附理由放行、留到下一批修的小問題(卷證 `governance/review-reports/code-推送只跑受影響測試/r1-intake.md`、`r2-intake.md`、`r3-intake.md`):

1. 主線不叫 main/master,而且遠端 HEAD 沒設(`git init` 加 `remote add` 的 repo)、或查主線候選失敗或逾時 10 秒時,直接推主線會被判成功能分支,本機只跑文件子集加關鍵字子集;這種分支本來也沒有推送觸發的 CI。r1–r3 邊界、資源、資安、通才席都報過。
2. t_prepush_feature_branch_mixed_with_main 一支跑四趟真掛鉤,本機約 83–86 秒、上限 180 秒,餘裕只剩 2 倍(r3 資源、合約圖譜席)。
3. 「新版 lumos、只改文件的功能分支推送」沒有測試案例:把降級條件放寬成連 docs 也降,測試全綠,只會多印一句誤導的「推功能分支」提示(r3 通才席)。
4. 計劃 [S6] 後半「原本就判 light 的功能分支推送不印降級那行」實際由 t_prepush_feature_branch_already_light 守,條款只綁 t_prepush_feature_branch_light_ok_false(r2 正確性、合約圖譜席)。
5. `.github/workflows/ci.yml` 檔頭還寫「push 後必跑的後盾」,功能分支沒開 PR 前其實不跑(r3 合約圖譜席)。
6. 掛鉤的 `_down` 只被判空,值 spec_light / feature_branch 只當註解用,跟 `_SUITE_BRANCH_DOWN` 記的是同一件事(r3 架構對齊席)。

## 根因

1. `_note_reread_mainline_names` 原本給回頭重讀用,失敗時只剩固定名的方向是「不擋」;這次拿來決定少跑全套,方向相反,沒有另外處理。
2. 判主線看推去的目的地要靠本機與遠端不同名的案例才釘得住,加在既有混推測試裡,一支測試的推送趟數變多。
3. 功能分支測試案例都是改程式檔,純文件只在舊版 lumos 案例裡出現(那裡沒有新欄位,走不到降級條件)。
4. 第一輪修補拆出新測試時,計劃已凍結設計判定,沒有回頭改條款綁定。
5. 這次只改掛鉤提示與說明文字,ci.yml 不在改動範圍。
6. 第二輪把兩段降級合成一段時,用一個原因變數記路徑,旗標仍沿用。

## 現在怎麼繞

1. 本 repo 主線是 main(固定名),不會踩到;其他主線名的 repo 用不到這道降級(只在有 test_lumos.py 的工具鏈本 repo 生效)。
2. 慢機器上這支超時時,單獨重跑確認;上限內的話不影響。
3–6. 行為正確,只是測試或文字沒跟上:全套與 PR 的 CI 照跑 t_prepush_feature_branch_already_light;降級判定只認 `suite` 為 full 的 ref。

## 什麼條件算修好

1. 失敗時改成「不知道就照全套」,或主線候選查不到時把被推的分支也當主線;補一條先紅後綠的測試(遠端 HEAD 沒設、主線 trunk)。
2. 把 feat:main、main:feat 兩案拆成獨立測試,每支餘裕回到 3 倍以上。
3. 補「新版 lumos、只改 README 的功能分支推送」案例:只跑文件子集、不印降級提示;用放寬條件的改壞驗證會紅。
4. 計劃收尾時 [S6] 補 `[test:t_prepush_feature_branch_already_light]`。
5. ci.yml 檔頭改成「推 main 與 PR 時跑」。
6. `_down` 改回只記旗標,或讓它的值真的被讀。
