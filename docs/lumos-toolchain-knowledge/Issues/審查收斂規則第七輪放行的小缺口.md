# 審查收斂規則第七輪放行的小缺口

代碼審 code-審查收斂規則 第七輪七席都只有 minor(18 條),依「上限後的輪次 minor 可附理由放行」全數放行、不再開下一輪;逐條原文在 governance/review-reports/code-審查收斂規則/r7-*-sonnet.md,處置在 r7-intake.md。這篇把它們收成一處,之後有人碰這一帶時照這裡補。

## 症狀

- 鏡頭排序:「改到存著殘留決策的筆記」與「判 untestable 的新問答指到真合約」同排級 1,後者夠多時可把前者擠到「另有 N 條未列」(正確性 F1)。
- 獨立 vault 佈局(repo 根直接放 MOC/、Systems/、Projects/)在舊格式或解不出的索引下,改圖譜筆記不升 high(正確性 F2、資安 F2、邊界 F4)。
- 鏡頭預算用完後判有沒有殘留的三次 git 呼叫各固定 3 秒,最壞超出內層 45 秒約 9 秒(資源 F1、通才 F2)。
- 鏡頭輸出改了但快取 schema 沒升,同範圍會命中修補前的舊快取(通才 F1)。
- 分級在有任何帶路徑的 notes 時就讀起點整棵樹,不管這次有沒有改圖譜檔(通才 F3)。
- `_vault_slug_of` 多了 `bare` 旗標(與別處 bare 同名異義)、第三份 ls-tree -r 解析、notes 欄混型(架構 F1–F3)。
- pitfalls 理由句裡 notes 相關路徑沒消毒(節點名帶換行時原樣保留;只到操作者終端,不進派工詞)(資安 F1)。
- `{"unresolved": ""}` 的理由句變成「:?」;`.MD` 判斷與起點樹 NFC 沒被測試釘住(邊界 F1–F3)。
- lumos 自己印的提示文字與 docstring 仍有四處說「審查席看這筆殘留」;06 那列與 pitfalls-code-loop 的照實說法沒守衛;計劃 WHY 一句口氣過強(合約 F1–F3)。
- 函式太複雜(C901)沒拆、以 lint-waive 放行:新函式 `_residual_check`、`_residual_test_files`、`_cmd_guard_residual_locked`、`_residual_tier_hits`、`_lens_residual_new_lines`(各種讀不出、位置未知、排序級的分支本來就多,拆小要動結構與行為,不在審查後做);既有大函式 `run_doctor`、`cmd_loop_escape`、`_guard_dispatch` 這次多了殘留相關的分支、複雜度變大(新增告警閘比的是函式開頭那行,沒算成新增、沒放行),拆函式另案處理。其餘新增告警(lambda 指派、串接、註解裡的長破折號、單字母變數名)已照寫法改掉,行為不變;`zip` 沒標 strict 的兩處(`_residual_index_mismatch`、`_doctor_residual_lines`)改回不帶參數的原寫法(新增告警閘沒把它們算成新增),因為專案有測試禁止主程式寫 `zip(..., strict=)`(t_lumos_no_zip_strict_for_py39)。

## 根因

都是第六輪修補(排序拆級、notes 原因、改用既有 helper、鏡頭不出段與不快取)的邊角與說法沒跟齊;沒有一條會讓新殘留不經高風險審就進主線(第六、七輪資安席都沒找到繞法)。方向多為偏嚴(多升 high)或只影響顯示與耗時。

## 現在怎麼繞

- 獨立 vault 佈局的專案:先跑 `lumos guard residual --reindex` 讓每筆殘留都記到決策所在筆記,就不會走到「位置未知」那條判定。
- 鏡頭快取疑似過期:`lumos dispatch-lens <範圍> --no-cache`。

## 什麼條件算修好

- 上面每一條各有一支會紅的測試或照實改好的說法;快取 schema 升版;預算後的 git 呼叫夾剩餘時間;起點樹只在有改圖譜檔時才讀;提示文字照實。
