# 過期鎖接手可能雙持

白話：鎖檔過期時，兩個程序原本應只有一個能接手。現在其中一個可以把另一個**剛建好的新鎖**也搬走，於是兩邊都以為自己持鎖。這是 [[Issues/治理帳多個寫入者都沒上鎖]] 準備沿用現有鎖時先撞到的地基缺口，不表示已在生產觀察到帳本壞列。

## 症狀

在乾淨 `main@2db51cc4` 的隔離 clone，以事件屏障固定兩個接手者的順序，`_excl_lock_try` 對 A、B 都回 `True`。主會談的 thread 注入輸出 `A_acquired=True, B_acquired=True`；獨立前掃席另以雙程序重現相同結果，`child_exit=0`。設計審凍結卷證在 `governance/review-reports/design-codeloop-ledger-integrity/r1-concurrency.md` 與 `r1-architecture.md`。

## 根因

舊持有者的鎖檔已過期時，函式先用 `stat` 判年齡，之後按**路徑** `rename`。兩步間若另一程序已把舊鎖換成新鎖，後到者搬走的是新鎖；函式沒有重新核對搬走者仍是剛才觀察的 inode 或持有 token。`rename` 本身原子，不等於「觀察舊鎖→搬走同一個舊鎖」原子。這反駁歷史 Issue 中「過期用換名原子接手，只有一人搶到」的適用範圍；後者在無交錯時成立，這個時序不成立。

## 現在怎麼繞

未修復前不要把 `_excl_lock_try` 的過期接手當成治理帳單一寫者保證。原有筆記庫寫鎖與派工鏡頭也用同一原語，需在各自的修復計劃裡驗這個交錯；不能靠加大過期秒數宣稱競態消失。治理帳新案停在設計審，不進實作。

## 什麼算修好

先在 `scripts/test_lumos.py` 加入能固定「B 看見舊鎖→A 接手新鎖→B 恢復」順序的跨程序紅燈；修後同一時序只能一人取得，另一人不能移除現持有者的鎖。回歸須同時驗無競態時取得／釋放、真正死鎖接手、等待上限、符號連結及清理只刪自己的鎖。鎖的修法不得引入專案第二套鎖策略；治理帳四個寫者的同鎖驗收另見 [[Projects/code-loop治理帳寫讀契約_計劃]]。

最短重現方式：在暫存目錄先建一把 mtime 超過 `stale_sec` 的鎖，攔住 B 對該鎖的 `os.rename`；讓 A 完整執行 `_excl_lock_try` 並回 `True` 後放行 B；現行 B 也回 `True`。實測輸出與時序見前述 r1 審查報告；重做時只需讀取程式並在暫存目錄放鎖，不得改真工作區鎖檔。
