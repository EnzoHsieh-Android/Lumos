# 推送前收集第五輪放行的小缺口

代碼審 code-推送前收集 第五輪七席都只有 minor 或 clean(10 條),依「上限後的輪次 minor 可附理由放行」全數放行、不再開下一輪;逐條原文在 governance/review-reports/code-推送前收集/r5-*-sonnet.md,處置在 r5-intake.md。

## 症狀

- 守衛掃描器(`t_prepush_touched_file_write_fails_quietly` 那支)讀不懂的 bash 寫法:here-doc 前提斷言對註解、字串、算術位移裡的 `<<` 誤判;`<<$x`、`<<.EOF` 這類合法 here-doc 漏判;`>|`、其他 fd、`2>>/dev/null`、帶引號的 `/dev/null` 判錯;雙引號 `$(…)` 裡的 `case … a)` 提早收尾;跨行與括號深度兩段新邏輯沒有手寫例子守(邊界 F1–F5)。
- 原生 Windows 的 runpy 退路與 setpgid 失敗時片不在自己的群組,兩發整組 TERM 都退回只殺片本人,孫行程收不到(資源 F1)。
- runpy 退路的 `sys.path[0]` 用 abspath,測試檔是符號連結時跟直接執行不同(正確性 F1)。
- `push-summary` 失敗時的簡版彙總把 ref 名原樣印出,沒有清 C1 控制字元與雙向覆寫、沒有截長度(資安 F1)。
- 通用原因句沒被正本守衛讀;工具鏈資安範圍只埋在一條 WHY 的括號裡、沒有獨立規則(合約 F1–F2)。
- [[Systems/棧別提問表態閘]] 摘要那條 FLOW 說 code-loop check「序列早退」:推送前掛鉤現在帶 --keep-going,四道判完才一次列出,這句已過時、以程式碼為準(推送前回頭重讀查到;那行是沒附來源的舊現況句,改寫會被筆記形狀擋,要整行改成程式碼答不了的寫法或刪掉)。

- 推送前全套測試在接上新主線後才抓到兩支:新增告警閘的順序測試還在比收集模式之前的原始碼位置(t_lint_new_gate,已改成看 `_codeloop_guard_verdict` 裡呼叫 `_codeloop_lint_new_step` 那一行),以及指令索引兩邊各加一段後超過 4500 字上限(t_command_index_complete,已縮句)。這兩支在第四、五輪的修補後一直沒跑到全套,審查子集沒涵蓋。

## 根因

都是第四輪修補(啟動器退路、第二發 TERM、掃描器補兩種寫法、原因句守衛)的邊角沒跟齊。掃描器是刻意不補成完整 bash 解析器,改成守住「掛鉤裡沒有 here-doc」的前提;前提斷言本身的誤判方向是多擋。沒有一條會讓本該擋下的推送通過。

## 現在怎麼繞

- 掃描器誤紅時,看訊息指的行是不是註解、字串或算術;是的話照原樣改寫成不含 `<<` 的寫法,或擴充掃描器。
- Windows 上推送被中斷後,手動確認沒有殘留的測試行程。

## 什麼條件算修好

- 掃描器邊角各有一條手寫例子或明寫不支援;Windows 退路改成照 POSIX 收法或寫明只收片本人;runpy 用 realpath;簡版彙總的 ref 名照 `_esc_clean` 同等消毒;通用句納入正本守衛;表態閘那條 FLOW 改寫或刪掉;資安範圍成為獨立規則(由「工具鏈審查鏡頭範圍」那份計劃處理)。
