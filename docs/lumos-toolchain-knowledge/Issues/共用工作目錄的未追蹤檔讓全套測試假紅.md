# 共用工作目錄的未追蹤檔讓全套測試假紅

> 白話：好幾個 session 共用同一個資料夾工作時，別人還沒提交的檔會讓你的測試紅。紅的原因不在你改的東西，但它跟真的紅長得一模一樣。

## 實際發生的那次（2026-09-13）

推一批 22 個提交之前跑全套，出來 4 條紅。逐條查的結果：

| 紅的那條 | 真正的原因 |
|---|---|
| 卷證目錄不得有任何腳本 | 另一個 session 在卷證目錄留了一支還沒提交的輔助腳本 |
| 快取測試（有時間上限） | 目錄裡多出來的大量未追蹤檔把掃描拖慢，超過測試寫的時間上限 |
| 圖譜健檢要 0 issues | 這條是真的——我自己的驗證紀錄沒掛回節點（修掉了） |

**四條裡兩條是假的。** 而假的那兩條，在乾淨的工作目錄跑同一個提交是全綠的。

## 怎麼判紅的真假

```
git worktree add --detach <暫存路徑> <要驗的提交>
```

在那個暫存目錄裡跑同一支測試。兩邊結果不同 → 不是碼的問題。跑完：

```
git worktree remove --force <暫存路徑>
```

## 為什麼不把測試改成忽略未追蹤檔

「卷證目錄不准放腳本」這道守衛存在的理由就是抓**還沒提交**的東西——卷證是證據，臨場寫一支腳本去正規化別人的報告，正是它要擋的行為。讓它略過未追蹤檔等於把它關掉。

## 留痕那一關

從暫存工作目錄推的時候，代碼審留痕（`code-loop pass`）記的是「目前分支」，而暫存目錄是不帶分支的狀態，會記成 `HEAD`、推送前檢查按 `main` 查就查不到。作法：先把主分支的指標移到要推的那個提交，在主工作目錄記留痕，再把留痕檔複製進暫存目錄，然後從暫存目錄推。

## 跟「假綠」的關係

[[Systems/測試假綠形態]] 記的是「綠的不一定驗到了」。這一篇是另一面：**紅的也不一定是真的**。合起來的意思是：全套跑完，兩種顏色都不能直接信——綠的要問「它到底驗到了什麼」，紅的要問「這是不是我改的」。

★最貴的代價不是白跑一輪★：只盯紅的會去改沒壞的碼；而習慣之後，人會開始用「大概又是髒檔」去解釋真的紅。
