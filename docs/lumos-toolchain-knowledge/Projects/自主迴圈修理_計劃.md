# 自主迴圈修理_計劃

> 白話:每天早上自動選一個治理缺口、寫成 spec、自審到收斂、停在放行閘等人的那條迴圈,最近三天燒了 156 美金、一件都沒落地。查下來是三個具體的洞。本 spec 經 r1 五席審查(24 條全折入——s1 七條/s2 六條/s3 四條/arch 兩條/ext 五條,含 6 條 blocker 級),記帳方案整個換向:結局帳走結構化欄+trap 保證必記,不搭成本帳便車。

PRIOR-ART: 全部借用,零依賴自寫幾行——「失敗的件不丟、進死信重排」是訊息佇列教科書做法(SQS/RabbitMQ 的 DLQ);「排隊太久的題目分數要動」是 OS 排程器 aging;「被重複點名=價值信號」是 LFU 快取;「每週一行花費對產出」是 SRE 成本儀表;「所有退出點統一落帳」是 shell trap EXIT 慣用法。

## 現況事實(2026-08-26 實查,r1 排乾與五席複驗過)

1. **丟件**:`gap_select.select()` 把選中的 gap 從 backlog pop 走(`backlog.py` `pop_top`);之後**任何**提前退出都不放回——不只解析失敗(autonomous-loop.sh:254 exit 1),連 anchor 驗證失敗(:177)也是 pop 後直接退。log 訊息「gap 留在 backlog 下輪自然重抽」是假話:08-24(API 529)、08-25(輸出截斷)兩天選中的 gap 已消失,不在 backlog 也不在 covered。
2. **選題退化 FIFO**:`backlog.py:28` 的 `decay_and_prune`(每天九五折、低於 0.2 淘汰)全 repo 無生產呼叫點(只有測試);live backlog 160 筆裡 153 筆凍在初始 0.5 分,`pop_top` 穩定排序同分最早插入者贏 → 08-23 選中 2026-06-29 的舊題。日報重複點名只更新 `last_seen`(死資料,無讀者)。
3. **成本已記、結局沒帳**:08-23 起每輪成本已落 canary 帳(`auto-<日期>`,--tokens/--wallclock-min 既有欄)。但結局(收斂/未收斂/管線死+死因)無帳,且現行成本落帳段結構上記不了結局:record 呼叫點(autonomous-loop.sh:245)在收斂判定(:257)**之前**執行,且被包在「成本抽得到才進」的分支裡(:226-229 信封 JSON 壞就 sys.exit(0)),PARSE_FAIL 時連帳都沒有。近三輪:08-23 $68.7 跑滿 6 輪未收斂(正常路徑)、08-24 $33.9 NO_JSON(529)、08-25 $53.3 NO_JSON(輸出截斷;信封=「claude -p --output-format json」回傳的頂層 JSON——這輪信封異常:1 turn/0.1 分鐘卻報 $53,原因未查明,先分類記帳不建理論)。

## 條款

- **[S1] 失敗不丟件(涵蓋所有早退點)**:
  ①選題 pop 之後,以 shell `trap EXIT` 保證:凡 gap 已選中且未被顯式處置(requeue_unconverged / mark_covered / 收斂寫 pending),退出前把**原始 JSON 列原封放回** backlog(直接 append 原列,**不走 add_gaps**——它會把分數重置 0.5),另在該列 `pipeline_failures` +1。
  ②`pipeline_failures` 滿 3 次 → `mark_covered` + LINE 喊人(鏡射既有 `requeue_unconverged` 的 max_unconv=3 熔斷語意:放棄自動、留人手動),不會無限反覆燒錢。
  ③log 訊息改真話。
  行為斷言:模擬 NO_JSON 一輪 → gap 在 backlog、分數不變、pipeline_failures=1;模擬 anchor 失敗早退 → 同樣放回;同一 gap 連三輪管線死 → 進 covered 且觸發喊人(打樁);已 requeue/covered/收斂的輪 → trap 不重複放回。
- **[S2] 選題修理**:
  ①衰減冪等按日差:不掛在 `select()`(skip-continue 會同日多打),腳本開場呼叫一次;sidecar 狀態檔 `governance/autonomous_loop/decay-state.json`(新檔)記上次衰減日,本次衰減=×0.95^(日差),同日重跑=0 次方不動。
  ②`decay_and_prune` 改簽名**回傳被淘汰的列**;呼叫端先把淘汰列 append 到 `governance/backlog-archive.jsonl`(新檔,與 live 的 `governance/backlog.jsonl` 同目錄)、**寫後讀回自驗**(照成本落帳段「回報成功≠已落盤」慣例,rc 判斷、失敗 log 不靜默),自驗過了才存縮後的 backlog——順序=先歸檔後刪,中斷最壞重複、不會遺失。
  ③回血:日報再次點名已在 backlog 的 gap → 分數**補回到初始 0.5(不超過、不疊加)**。連日被點名的題持續保持 0.5 是接受的行為(那是真實的重複投票信號;真做不動的會被 [S1]② 或既有 unconverged 熔斷接住)。
  ④排序去位置依賴:`pop_top` 改三鍵排序(value_score 降冪 → last_seen 新者先 → source_date 新者先),同分同日時新題贏,不再依賴 stable sort 的插入位置。
  ⑤壞行容錯+原子寫:`load_backlog`/`load_covered` 逐行 try/except,壞行跳過並 log 計數(不讓一行壞資料把整條迴圈打趴——set -euo pipefail 下未捕捉例外=從此天天當機);`_save` 改 tmp+os.replace 原子替換。
  行為斷言:同日兩次進場分數只衰減一次;隔 3 天進場衰減 0.95 三次方;淘汰列出現在 archive 且 live 消失,archive 寫入失敗時 live 不動並有 log;兩筆同分同 last_seen 的新舊題,source_date 新者先被選;含一行壞 JSON 的 backlog 照常運作並 log。
- **[S3] 結局帳:結構化欄+trap 必記**(r1 推翻原「note 自由文字」方案——五席獨立打死:①成本抽取與結局是兩個獨立失敗維度,綁死則 PARSE_FAIL 時連死因都蒸發;②record 呼叫點在結局判定之前,三種結局結構上寫不對;③note 是專案明文放棄的散文注入面,獨立驗證器一律丟棄):
  ①`lumos canary record` 加兩個結構化欄 `--outcome <token>` 與 `--usd <數字>`(要被機器回讀的資料開欄,是本專案既有先例——tokens/wallclock-min 當初正是如此;08-24「只用既有兩欄」的邊界因需求變更翻案,理由記於本節)。
  ②落帳時機改 shell `trap EXIT` 統一執行(與 [S1] 同一個 trap):退出前依當輪已知狀態組 outcome,天然涵蓋全部 8 個早退點——失敗日照樣有帳。
  ③outcome 兩層分類(主類:細類):`converged`、`unconverged:cap|disputed|degraded-high`、`tier-blocked:spec|gate|cross`、`skipped`、`pipeline_fail:api_error|truncated|parse_fail|anchor_fail|pending_write`(pending_write=收斂但 pending 目錄寫入失敗;code-r1 s4-f1 補宣告,CLI 端同步鎖為封閉列舉)。parse_fail 在 shell 層由 $PARSED 前綴判定,不依賴成本區塊的 json.load。
  ④成本抽得到就同筆附上(usd/tokens/分鐘),抽不到 outcome 照記——兩維度解耦。
  ⑤連續失敗喊人:以「有跑的日子」聚合(一日多筆逐筆看:當日全部為 pipeline_fail 才算失敗日);最近兩個有跑日皆失敗 → LINE 喊人。警示訊息**自組文字直接走 `line_notify.send()` 傳輸層,不套 `build_message` 模板**(模板寫死「備好 1 個待放行 spec」好消息標頭;既有錨點警示錯用模板屬既有債,本案不動、此處不重蹈)。
  行為斷言:PARSE_FAIL 輪(信封 JSON 壞)帳上有 `outcome=pipeline_fail:parse_fail` 且無 usd;converged 輪帳上 outcome 正確且含 usd;連兩個有跑日全失敗觸發喊人(打樁驗訊息文字無「待放行」標頭),中間隔沒跑的日子不算斷。
- **[S4] 七天產出一行**:每輪(含失敗輪——trap 保證)在 autonomous.log 印:「過去 7 天:跑 N 次、燒 $X、收斂 Y、備好待放行 Z、管線死 W(另 M 筆舊格式帳,只計成本不計結局)」。資料源=canary 帳 `auto-*` 列,**逐筆遍歷、絕不以 loop id 當鍵**(同日多筆已是現場事實:08-25 兩筆同 id 不同結局);無 `--outcome` 欄的舊格式列只計跑次與成本、結局歸「舊格式」桶明示。「備好待放行」=converged 且 pending 寫入成功;真放行(人 merge PR)不在此帳,見邊界。
  行為斷言:fixture 含新舊混合格式與同日多筆 → 彙總各數字與逐筆加總一致、舊格式筆數正確;模擬失敗輪結尾也印得出彙總行。

## 不做(邊界)

- 不加自動 retry(529 重試=最壞成本翻倍,無人看顧下不敢);止血靠 [S3]⑤ 喊人。
- 不動放行閘、N=1 閘、tier 收檔守衛、dry-run 紀律等既有裁定。
- 不查 08-25 信封異常根因(單一樣本;[S3] 分類累積證據,連續出現再立案)。
- 不給 orchestrator 加 turn/成本上限(08-23 $69 是正常跑滿 6 輪;等 [S4] 累積數據再判)。
- 「真放行」(人 merge)不入帳:放行動作在 GitHub,帳在 git 歷史可查,本案不建跨系統對帳。
- 既有錨點警示錯用 build_message 模板是既有債,本案不修(記於 [S3]⑤,修它要另判影響面)。
