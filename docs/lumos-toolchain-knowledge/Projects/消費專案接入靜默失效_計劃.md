# 消費專案接入時的五道靜默失效

> 白話：把 Lumos 接進一個新專案（這次是第一個真的 iOS 專案），有五道閘會「看起來好好的、其實沒在保護你」。共同長相一模一樣：**回 0、不印字、健檢說零問題**。其中一道更糟——它不是不出聲，是**主動報告了假的好消息**：測試一支都沒跑，閘說「四支全綠」。

## 五道各是什麼

| # | 現象 | 為什麼會這樣 | 使用者看到什麼 |
|---|---|---|---|
| ① | 測試掃描與符號檢查都用 C# 的規則 | 初始化不寫設定檔，兩支讀設定的在找不到設定時各自退回 C# 預設 | 什麼都沒看到；符號檢查照樣說「都找得到」（因為根本沒掃到那些檔） |
| ② | **零支測試跑過，閘說四支全綠** | 閘只看退出碼。測試指令的過濾條件對不到任何測試時，建置工具跑 0 支、仍印成功、退出碼 0 | **綠燈**——比靜默更糟，是假的好消息 |
| ③ | 波及計算對整個 diff 零覆蓋 | 節點標了 `about_code`，但連結是靠正文裡用反引號寫的路徑抽的 | 合約測試閘回「沒有可跑的」、退出碼 0、一個字都不印 |
| ④ | 新專案的忽略設定跟設計**恰好顛倒** | 初始化沒建排除本機狀態的那份忽略設定、卻建了忽略治理帳的那份 | 本機狀態被提交進版控；CI 要讀的那條路沒了 |
| ⑤ | 零覆蓋的三種原因被壓成同一種 | 「沒有節點引用」「有節點沒綁測試」「知識庫完全找不到」都回同一個狀態 | 跑錯目錄／還沒初始化時，被告知「沒有節點引用這些檔」 |

## ② 是這輪最重的一條（審查席升級的）

原本我把它寫成「接入文件沒講清楚三段式格式」。r1 兩席獨立指出這不夠，我照它們的判準實測：

- 把計算機專案的測試指令改回少一段的壞形狀 → 合約測試閘回報 `status=green, ran=4`，人讀訊息是「合約測試 4 支全綠」。
- 單獨把同一個識別字餵給建置工具 → **實際執行 0 支測試**，但它印 `TEST SUCCEEDED`、退出碼 0。

所以這不是接入問題，是**既有的閘信錯訊號**：它把「指令回成功」當成「測試跑過且通過」。任何過濾條件打錯字的專案都會拿到假綠，不限 iOS。

**折法借既有形狀**：工具鏈已經有「對 linter 跑一次冒煙測試證明它真的會動」的做法。對測試指令做同一件事——拿一個故意不存在的測試名跑一次，如果那樣也回成功，代表這個指令沒有過濾能力，閘不得信它。

## ④ 原本寫反了（三席獨立打掉）

我第一版寫「教人提交標記目錄、治理帳降級成本機備援」。三席從三個不同角度指出方向相反：

- 工具鏈自己的忽略設定明寫排除標記目錄，理由是「綁版本號的本機執行期狀態，不版控、不跨機當權威」。
- 治理帳那條讀取路徑是為了修 2026-08-22「標記檔不在 CI checkout 而假紅」的事故才建的。
- 機制節點在 2026-09-09（同一天）才寫下「治理帳是 CI 讀表態的唯一路徑」。

**正確的圖是**：標記檔＝本機狀態不版控，治理帳＝CI 唯一權威來源。而初始化產出的新專案恰好顛倒。**所以要改的是初始化的兩份忽略設定，不是文案。**

**我自己的錯要記在這裡**：我先前在計算機專案做的「clone 出來 CI 讀得到表態」實驗之所以成功，正是因為那個專案踩在錯誤狀態上（標記檔被誤提交）——**用錯誤配置驗出了錯誤結論**。

## 怎麼發現的

第一個真的 iOS 專案（一台 SwiftUI 計算機，在另一個 repo `~/harness/calc-ios`；它有自己的知識庫，所以這裡不用連結指過去）接入時逐項實跑八個機制。① ② 是設計審席位讀原始碼抓出來的（跑起來只會看到綠色），③ ④ ⑤ 是實跑卡住才查出來的。過程在計算機專案自己的驗證節點。

**特別值得記的一件事**：我為了確認符號檢查有沒有作用，在筆記裡塞一個不存在的方法名做翻紅測試，結果沒翻紅、一度以為機制壞了。查下去發現是**測試自己寫壞**——那句話裡有「不存在」三個字，剛好命中否定詞表，工具判定「筆記正確記錄某符號已消失」而刻意不報。**驗證用的假資料也會踩到機制本身的規則。**

## 要做什麼

- **[A] 初始化產出設定骨架**：依偵測到的技術棧寫 `.lumos/config.json`。**多語言 repo 用既有的多平台格式**，不挑一個猜；偵測不到就寫帶說明的骨架而非留空；**偵測到的也要標示「這是猜的、請確認」**；既有設定一律不覆寫。
- **[B] 設定與實際不符時出聲**：判準是「profile 跟 repo 裡實際有的程式碼副檔名不符」，**與值是預設還是使用者寫的無關**（原本寫「跟預設不符」會被 [A] 產出的骨架抵銷）。
- **[C] `about_code` 沒接上的提醒**：**只在該節點同時有合約且綁測試時才唸**（那才是零覆蓋真的讓閘失效的情況）。比對規則沿用既有的反引號路徑抽取那一套。
- **[D] 讓初始化的忽略設定跟設計一致**：建立排除標記目錄的忽略設定；治理帳不該被初始化忽略（它是 CI 唯一路徑）。**這條不改任何既有裁定，是讓新專案符合既有裁定。**
- **[E] 零覆蓋時講原因**：三種來源分別出聲（沒有節點引用／有節點沒綁測試／知識庫找不到）。**訊息要帶既有關鍵字，否則會被推送前的過濾器吞掉**；而且要在推送那條路上真的看得到，不只是底層函式回傳。
- **[F] 合約測試閘不得信「跑成功」當「跑過」**：★判準在代碼審 r1 被整條換掉★——原本只做「過濾能力冒煙測試」（拿一個不存在的測試名跑一次，看它回不回 0），實測發現**大多數測試工具都分不出「測試不存在」與「測試通過」**，只靠它等於把最常見的幾種棧全判成不可信。改成主力看**測試工具自己的輸出有沒有說「執行了 N 支」**（逐支判），沒有實測過輸出樣式的 profile 才退回冒煙測試。
- **[G] 表態訊息兩條路徑都改**：失敗訊息與**每次成功都會印的那句**講的是同一個主張，要一起改。

## 實務隱患

- **守衛面**：[F] 會改變一道閘的判定（從報綠改成報「無法確認」），這是刻意的——它現在給的是假綠。其餘六項只加提醒不改判定。
- **[F] 的誤擋風險（代碼審 r1 後重寫）**：主力判準改成比對測試工具的輸出樣式之後，誤擋來自「使用者換了自訂輸出格式或加了靜音旗標，摘要行的字樣變了」——那會被判成「證不出跑過」而擋下。已量到的實例：xcodebuild 帶 -quiet 就是這種（訊息直接點名它）。逃生門與紅測試共用，會留痕。
  REVISIT:2026-10-09 看治理帳裡「證不出跑過」有幾筆、各是真的假綠還是被自訂輸出誤傷；誤傷過半就把該 profile 的樣式放寬或拿掉（拿掉＝退回冒煙測試，不是不擋）。
- **[F] 的漏擋範圍（誠實列）**：輸出樣式只填了實測過的四種（Swift／C#／Node／Python），其餘四種沒有這台機器可跑的實例，一律退回冒煙測試——那條路只證得出「認得出完全不存在的名字」，證不出「精準只跑到那一支」。
