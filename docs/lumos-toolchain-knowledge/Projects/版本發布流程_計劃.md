# 版本發布流程（計劃）

`PRIOR-ART:` ① **最小解在既有層**——`LUMOS_VERSION` 常數與 `_ver_check` 版本 nudge 已存在（2026-07-05 落地），本案是「給它接上 git tag 與安裝入口」，不是造新機制。② **世界解過**（真搜非印象，2026-07-29）：curl|bash 的釘版本／checksum 是熟坑，主流解法為「安裝腳本支援指定版本、預設抓 GitHub Release、附 checksum」（Sigstore「A Safer curl|bash」、Kusari「Pinning Dependencies」）；發版流程的標準形態＝tag → CI 驗 → `gh release create` → CHANGELOG（GitHub Docs「Managing releases」、`gh release create`；release-it／conventional-changelog 屬同族自動化）。③ **裁定＝borrow-design**：照抄「tag＋Release＋CHANGELOG＋安裝腳本吃 tag」這個形態，**不採**任何外部工具（release-it／goreleaser／semantic-release 全排除——零依賴家規，且它們解的是多語言打包發布，本專案沒有 build artifact）。自建部分只有膠水：版本一致性守衛與 CI 的 tag 閘。

## 為什麼現在要做（動機誠實版）

外審把這條放在安全項，但「被供應鏈攻擊」對單人專案是低機率事件。**真正買到的是兩件更平凡的事**：

1. **推壞 commit 的視窗**：README 教陌生人 `curl | bash` 裝 main。任何一次壞 push 都會直接傳染給那五分鐘內照做的人。釘 tag ＝「只有我明確說可以的版本才會被裝到」。
2. **可回答「你在跑哪一版」**：目前唯一答案是 commit sha，而消費專案的 CLAUDE.md 只有一個手動 bump、允許漂的 `v1.0`。出事時無法對齊。

**明確不做**（範圍刀）：不做 semver 相容性承諾、不做多版本並存／降級、不做簽章與 SLSA provenance、不做自動 changelog 生成（commit message 非 conventional 格式，硬套會產出垃圾）。

## 條款

### [S1] 版本單一源與一致性守衛
- 單一源＝`scripts/lumos` 的 `LUMOS_VERSION`。格式收斂為 `vMAJOR.MINOR`（現行 `v1.0` 已合），不引入 patch 段與 semver 語意承諾。
- 新增測試 `t_version_single_source`：`LUMOS_VERSION` 必須與 `CHANGELOG.md` **最新一筆條目的版本**一致。
- **真值取得方式**：版本取自單一定義點（常數行），CHANGELOG 取最新版本標題；兩邊解析失敗都必須是**紅燈而非跳過**。沿今日教訓——「真值需要靠猜」就不算機械驗證。

### [S2] CHANGELOG
- 新增 `CHANGELOG.md`，骨架借 Keep a Changelog（版本標題＋日期＋分類條列），**手寫**。
- 每次發版必須有一筆；`[S1]` 的測試強制它與 `LUMOS_VERSION` 對齊。
- 首筆＝`v1.0`，內容為「首次正式標記；此前為未標記的持續開發」，不回溯編造歷史。

### [S3] 發版動作（人執行，有 checklist）
順序不可調換，每步失敗即中止：
1. 確認工作樹乾淨、在 `main`、與 remote 同步。
2. bump `LUMOS_VERSION` ＋ 寫 `CHANGELOG.md` 該筆 → commit → push。
3. **等該 commit 的 CI 綠**（`lumos ci-wait`；紅則不得發版）。
4. `git tag -a vX.Y -m "..."` → `git push origin vX.Y`。
5. `gh release create vX.Y`，release notes 取自該筆 changelog。
- 寫成 `RELEASING.md`（給人看的 checklist），**不寫成腳本**——發版是低頻、不可逆、需要人在場判斷的動作，自動化的收益低於「腳本出錯自動推出去」的風險。

### [S4] tag 閘（CI）
- 新增 tag 觸發的 workflow job：checkout 該 tag → 全套測試＋`doctor --ci`＋`anchor verify` → **並斷言 `LUMOS_VERSION == 該 tag 名`**。
- 目的是擋「tag 打在錯的 commit 上」與「忘了 bump」。**限制誠實記**：這是**事後**檢查（tag 已存在才跑），讓錯誤可見，不能阻止 tag 被推出去。事前保護是 [S3] 第 3 步的人工紀律。

### [S5] `get.sh` 消費 tag
- 預設行為改為 clone 最新 release tag；**取法擇一並明確處理「一個 tag 都沒有」的 fallback**。
- 新增 `--ref <tag|branch|sha>` 明確指定；`--main` 為 `--ref main` 的別名（前緣使用者的逃生口）。
- **`--pull` 語意需重新界定**：釘在 tag 上時 `git pull` 沒有意義（detached HEAD）——必須在設計中講清楚，否則會產生一個看似成功實則不動的更新路徑。既有 `bootstrap --pull` 是否連動，一併裁。
- **誠實天花板（必寫進 README）**：`get.sh` 腳本**本身**仍是從 `raw.githubusercontent.com/.../main/get.sh` 抓的，未釘。釘的是它 clone 的內容，不是它自己。要連腳本本身都釘，使用者得改用釘版本的 raw URL——只能建議、不能強制。

### [S6] notesmd 二進位 checksum
- `fetch-notesmd.sh` 已釘版本 `v0.3.6`，但無內容驗證（tag／release asset 上游可重傳）。
- 新增各平台 SHA256 常數表 → 下載後比對，不符即中止並保留暫存檔供人查（**不靜默重試、不 fallback 到照樣裝**）。
- 指紋來源＝**當下實際下載到的檔案**，節點記明「這是首次記錄時的值，非上游官方公布值」——誠實標示信任根在哪。
- 平台涵蓋 darwin_all / linux_amd64 / linux_arm64（腳本現有三分支）。

### [S7] Actions 釘 SHA
- `actions/checkout@v4` / `actions/setup-python@v5` 改完整 commit SHA ＋ 尾註原 tag 供人辨識。
- 代價明講：之後上游修補不會自動吃到，需人工升——列入 `RELEASING.md` 定期檢查項。

## 實務隱患

- **釘 tag 後「更新」路徑斷掉**：使用者裝在 detached HEAD 上，之後 `git pull` 無效、`lumos update` 只會 re-vendor 同一版。若沒設計「怎麼升到下一個 release」，會製造一批永遠停在 v1.0 的安裝。
- **版本一致性守衛自己漂**：若 `t_version_single_source` 用鬆散 regex 抓 CHANGELOG 標題，格式一變就靜默不驗（今日 `links`/`backlinks` 同型事故）。
- **tag 閘是事後的**：錯的 tag 推出去後才紅，此時已可能有人裝到。
- **checksum 的信任根是我自己第一次下載到的檔案**：若首次下載時上游已被替換，指紋會把錯的東西鎖成「正確」。TOFU 的固有限制，只能標示不能消除。
- **維護者自己的機器**：`~/harness/lumos-toolchain` 是活 clone，發版不該改變其行為；get.sh 改成釘 tag 後，重跑 get.sh 會不會把維護者 clone 也拉到 detached HEAD？（既有邏輯是「已有 clone 就跳過」，需確認仍成立。）
- **零 tag 的冷啟動**：第一次發版之前，「取最新 tag」會取不到東西，必須有明確 fallback 而非炸掉。
- **消費專案的 vendored 副本與 tag 無關聯**：vendored 檔案裡沒有版本戳，且目前**沒有 `lumos --version` 這種入口**，出事時仍難對齊。是否補，待審。
- **`gh` 不可用時的發版路徑**：[S3] 第 3、5 步都依賴 `gh`；若環境沒有，流程要能降級（純 git tag 也算發版？）還是硬中止？

## 測試策略

| 條款 | 測試 | 型態 |
|---|---|---|
| [S1] | `t_version_single_source`：LUMOS_VERSION ↔ CHANGELOG 最新筆一致；解析失敗即紅 | 機械守衛 |
| [S2] | 同上（CHANGELOG 存在且可解析） | 機械守衛 |
| [S3] | **無自動測試（人工 checklist，設計如此）**；唯一機械面＝`RELEASING.md` 必須存在且列出全部步驟，否則守衛紅 | 存在性守衛 |
| [S4] | tag workflow 的版本斷言（以 fixture 驗斷言邏輯，不真推 tag） | 單元 |
| [S5] | `get.sh` 的 ref 解析與零-tag fallback（假 remote／stub，不打真網路） | 單元 |
| [S6] | checksum 不符必須中止（餵內容被改過的假 tar，斷言 rc≠0 且不留下可執行檔） | 反事實 |
| [S7] | workflow 檔內不得出現可移動 tag 形式（regex 守衛） | 機械守衛 |

**反事實優先**：[S6] 與 [S1] 的價值全在「壞掉時會不會擋」，兩條都必須有「弄壞→必翻紅」的測試，而非只驗正常路徑。
