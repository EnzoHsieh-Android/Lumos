## 跟官方新建議直接衝突、但有自家實測的兩處(不直接改)

1. **審查派工詞的「抑噪」兩句**(「低嚴重度疑慮給不出具體失敗場景就不要標」「指不出 file:line 就不准臆測」,借自 PR-Agent)
   - 官方 Sonnet 5 專頁:審查指令叫它「只報高嚴重度」「保守」「別挑小毛病」,它會照做——調查一樣深,但報出來的變少,召回率下降;建議「全報、附信心與嚴重度,交給後段過濾」。我們本來就有後段過濾(編排者機械重現、引句錨定、處置閘)。
   - 自家實測:2026-08-04 做過只差這兩行的配對實驗(20 席、同一個便宜模型),沒有這兩行的一組抓到埋伏 2/10、有的一組 0/10,不顯著(p≈0.47);設計審重設計 d3 據此否決「只改措辭」這條路(見 [[Projects/canary注意力檢查失效]]、[[Projects/design-loop重設計]])。那次量的是抓不抓得到故意埋的錯,不是真問題數;模型也不是 Sonnet 5。
   - 判定:有新證據,值得在 Sonnet 5 上用真材料重做一次(建議一)。
2. **CLAUDE.md 第四條「說沒有之前先派乾淨 agent 對一次」**
   - 官方 Opus 5 專頁:「用子代理驗證」這類指令會造成過度驗證,刪掉品質不掉。
   - 自家實測:這條就是在 Opus 5 上立的(2026-08-22),當天情境探針做過正反對照——規則在,那題答對(262.8 秒);拿掉,那題答錯(74.7 秒)(見 [[Verification/2026-08-22_缺席推論探針題組]])。官方那句指的是「做完再驗一遍自己的工作」;這條是「找第二個獨立來源、不給它結論」,性質不同,而且只管會決定動不動手的否定句。
   - 判定:不動。它的成本只量過那一題,效益沒有長期統計——這個缺口原本就記在那篇驗證紀錄裡,不另開。

## 建議(候選,待 Enzo 裁;每條先量再改)

1. **(要實驗,最高槓桿)Sonnet 5 上重做「全報 vs 抑噪」**:拿一份已知真問題的凍結材料(例:今天 `code-資安席與多平台指令` 那條代碼審迴圈第一輪的凍結 patch——它的真問題已由第二、三輪與修正確認),派兩組 sonnet 席,一組現行派工詞、一組把抑噪兩句換成官方全報措辭;比席位報幾條、存活幾條、重現幾條、漏了哪幾條已知問題。量法沿用處置閘尾的「審查有沒有用」漏斗。成本約一次四席。
2. **(可直接整理,低風險)入口頁去時效、範本清死句**:
   - 代碼審、設計審兩支入口頁的日期與事故敘事搬進各自參考檔的「歷史」段或圖譜節點,入口頁只留規則和一句為什麼(照 07-29「搬家不刪義」)。
   - 派工範本刪掉 4 處已停用的 canary 句、開頭補目錄。
   - 參考檔開頭過時的行數一併修。
   - 動手前先跑一次情境探針當基線,改完再跑,掉了就回滾。
3. **(守衛)常駐規則長回來要有人看見**:健檢的紀律區塊那段,加一行「目前幾 KB、上次瘦身基線 5.1KB」的提醒(只提醒不擋);超過基線五成時,開一次瘦身。
4. **(小)參照改成一層**:指令索引的九支子檔很短(10–43 行),可以考慮併回索引或讓入口頁直接點名子檔;先看探針有沒有「讀了索引卻沒開子檔」的樣子再決定。
