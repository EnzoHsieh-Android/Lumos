# Android目標架構開關與舊檔畢業_計劃

> 白話:上一份範本是固定的十二條,專案只能整份照抄再自己刪。這份計劃把它改成「開關」:採用時由 AI 逐題問人六個架構選擇,再用一支產生器照答案組出規則節點、宣告與 Konsist 架構測試;另外讓舊檔可以照舊鄰居審、新檔才套目標規則,舊檔重構時從舊檔清單刪掉它那一行,就在同一個分支當場改照目標規則審。

## 用語

- **宣告**:`.lumos/config.json` 的 `arch_targets` 清單,每條 `{"path": 樣式, "node": 節點或 none}`,一支檔由上往下第一條命中的算數。
- **none**:命中這條的檔不套目標規則,照「鄰居」審——架構對齊審查席拿同資料夾、同副檔名、檔名最像的既有檔當對照,問新寫法跟它們一不一樣。
- **目標節點**:一篇 Systems 筆記,摘要裡的 `RULE:` 行就是這個範圍該照的規則;派工鏡頭(派審查席那一刻自動附在派工詞尾端的材料)會把規則原文附給架構對齊席。
- **舊檔清單**:`.lumos/arch-legacy.json`(新增),內容是 `{"files": ["<repo 相對路徑>", …]}`;列在上面、又被宣告判給某個目標節點的檔,照鄰居審。整條路徑比對(兩邊先轉 NFC),不當萬用字元。
- **起點版**:代碼審讀宣告與舊檔清單的那一版,也就是改動起點跟主線的分岔點(既有的可信版本讀法);沒有主線時各條路照現行做法:推送前風險分級把起點本身當起點版,派工鏡頭整段不附。
- **Konsist**:讀 Kotlin 原始碼的架構測試庫,跑在一般 JVM 單元測試裡。
- **畢業**:舊檔重構成新架構後,從舊檔清單刪掉它那一行,改照目標規則審。

## 問題與最小解

立案:Enzo 2026-10-30 在 Android 範本合併後提出三件事——多模組要寫進範本、檢查要有開關(不只多模組,還有其他架構選擇)、舊 class 維護照既有架構而新 class 才套用;並補充「一開始配置時詢問我再決定」與「舊檔重構」。開關清單由 Enzo 同日從建議裡全選:模組切法、舊程式處理、用例層可省略、DDD 深度、介面策略、畫面狀態形式。畢業生效時機 Enzo 選「同分支就生效」(不選「先合一個只刪宣告的小合併請求」)。

現況:
- 範本的十二條與 Konsist 骨架寫死在技能文件 `skills/lumos-project-notes/commands/target-arch-android-template.md` 裡,不適用的規則要人自己刪,刪了規則卻忘了刪對應測試、或反過來,沒有東西會抓。
- arch_targets 只認 `path` 與 `node` 兩欄,第一條命中算數,樣式第一段要是寫死的資料夾名;一條不合法整份不用。
- 代碼審的宣告只讀起點版(防被審分支自己放寬怎麼被審),所以舊檔重構時在同一分支改宣告,這次重構照樣比鄰居——最需要照目標審的那次反而沒審到。

做法:
1. **開關資料檔**:Android 規則與 Konsist 測試的唯一來源搬到 `scripts/templates/android-arch-target.md`(新增),每條規則與每支測試標「哪些開關值才收」;登記進工具自帶檔清單 `_VENDORED_TREE_FILES`(`lumos update` 靠這張表分發,另有逐檔比對的測試)。產生器照既有範本的讀法從專案根底下的 `scripts/templates/` 讀它,讀不到就提示跑一次 `lumos update`。新開 `Systems/android-arch-template` 當它與產生器說明的家。DDD 與前端兩份範本照舊是技能文件裡的抄貼式:它們沒有開關需求;06 那一列寫明「Android 用產生器、其他兩份照抄」。DDD 規則兩份各自是單源:DDD 範本管語言中立版,Android 資料檔管 Android 版(反例換成 Room、ViewModel),同義不同文是上一份範本就有的安排。
2. **產生器** `lumos arch-template android`,只讀不寫:
   - 必填:`--root <根套件>`、至少一個 `--scope <目錄>`(可重複,多模組每個模組各給一個)、六個開關各一個旗標(`--modules` `--legacy` `--usecase` `--ddd` `--interfaces` `--ui-state`,沒有預設值,要照訪談答案明給)。選填 `--node`(預設 `Systems/Android目標架構`)。規則日期一律用今天、回頭日一律一年後;測試綁定一律寫 `[test:<測試名>]`,測試不在預設平台目錄底下時照文件自己改前綴。
   - `--scope` 先去掉結尾斜線,再檢查:不能空、不能是 `.`、不能以 `./` 或 `/` 開頭、不能有反斜線或控制字元、不能有任何萬用字元(`*` `?` `[`)、不能有空段或 `..` 段、不能少於兩段、底下至少要有一支 git 已追蹤的檔;不合法就拒絕。產出的宣告交給讀宣告的同一支函式讀一次,讀出的條數不同就拒絕。
   - 輸出:`--print` 選 `node`、`targets`、`legacy`、`test` 之一就只印那一段的原文(讓採用的人用重導向或寫檔工具存成檔),不帶就印四段預覽加上每段該存到哪裡。lumos 不寫任何檔。
3. **採用步驟**(技能文件教,AI 照做):問人六題 → 跑產生器預覽給人看 → 依序存節點(存完 `lumos lint`)、把 `targets` 那段併進 `.lumos/config.json`、存舊檔清單(new-only 才有)、存架構測試 → 跑一次架構測試確認綠。採用之後不再重產舊檔清單(重產會把採用後新寫的檔也凍成舊檔)。
4. **舊程式處理** `--legacy`:
   - `all`:範圍內全部照目標審,不產舊檔清單。「只套用指定目錄」就是只給那幾個 `--scope`。
   - `new-only`:舊檔清單列出範圍內 git 已追蹤、架構對齊當程式檔看或架構測試會掃的每支檔(前者跟分目標節點用同一支判定,含 xml、gradle 腳本、androidTest 與 testFixtures;後者是不在 Konsist 認的測試原始碼集裡的 .kt;兩邊都不看的不收);轉 NFC、依字典序;檔名含 `"`、反斜線或控制字元就拒絕並列出。清單沒有條數上限(讀成集合查表)。
   - 每個 `--scope` 各一條目標宣告 `<目錄>/**`。
5. **讀舊檔清單**:推送前風險分級、派工鏡頭的代碼審路與設計審路、代碼審判定四處,在讀宣告的同一版用既有的按版本讀 JSON 函式(嚴格 UTF-8、容許開頭 BOM)讀清單;形狀不是 `{"files": [字串…]}` 就算讀不懂。被宣告判給目標節點、又在清單上的改動檔,照鄰居審。起點版清單不存在或讀不懂,就當空清單(全照目標審,審得更多)。改名沒有特別處理:新路徑不在清單上就照目標審。`lumos doctor` 讀目前提交那一版的清單,只印一行摘要:清單幾支、其中幾支已不存在、幾支沒被判給任何目標節點(只提醒不擋)。
6. **畢業**:起點版與頂端版的宣告完全相同、頂端版清單讀得懂(不存在算空清單)時,起點版清單有、頂端版清單沒有,而且這次範圍內有改動的檔,照它命中的目標節點審;規則原文照讀起點版。宣告有任何不同、頂端版清單讀不懂、這條路沒有可信起點版,就不畢業、全照起點版判。頂端版清單多出的行不影響審查(審查照讀起點版清單)。各處讀法共用一支判定函式;派工鏡頭的 500 條宣告與 5 秒上限照舊只套在宣告上。
7. **代碼審判定的說明行**:接在既有每個目標節點一行之後,依序最多三行:清單少了行時印「舊檔清單比起點少了 N 行,其中 M 支這次有改動、已照目標審」;清單多了行時印「舊檔清單比起點多了 N 行:審查本次照起點版、架構測試會跳過它們」;宣告或目標節點有改時照舊印「下次推送才生效」。
8. **Konsist 那一半**:產生的架構測試自己往上找含 `.lumos/config.json` 的資料夾當根(找不到就讓測試紅並說明,不靜默變綠;Gradle 子模組的工作目錄不是 repo 根也找得到);範圍目錄寫成測試裡的常數(採用後新增模組,要同時改宣告與這個常數,文件寫明);只檢查「相對根的路徑落在某個範圍目錄底下(以斜線為界)、又不在舊檔清單上」的類別,比對前兩邊都轉 NFC;聚合根名單這類「被參照的對象」照全部正式程式算。`legacy=new-only` 產出的測試讀舊檔清單(只取 `files` 陣列裡的字串;檔不存在或取不出就紅),`legacy=all` 產出的測試不讀清單。
9. **開關語意**:
   - `modules=multi`:多一條「模組依賴」規則(presentation 不依賴 data、domain 模組不套 Android 外掛),交給 Gradle 擋;分層與 Android 匯入兩支 Konsist 測試照留(依功能拆模組時 domain 可能還在 Android library 裡)。
   - `ddd=lite`:拿掉聚合根、識別碼參照、值物件三條規則與三支對應測試;其餘所有提到聚合的規則都換成不提聚合的版本(現在是 Repository、用例、ViewModel 業務規則、深模組、測試邊界五條)。
   - `usecase=optional`:ViewModel 可收 domain 的 Repository 介面,只禁 data 層實作與資料來源;ViewModel 建構子那支測試跟著改成只擋 `RepositoryImpl`、`DataSource`、`Dao`、`Api` 結尾的型別;用例規則改成「有用例時」。
   - `interfaces=always`:深模組那條換成「用例與 Repository 一律介面加 Impl」,用例測試的篩選同時認 `UseCase` 與 `UseCaseImpl` 結尾,另加一支「每個 Impl 都實作同名介面」的測試。
   - `ui_state=single`:唯讀狀態那條換成「每個 ViewModel 只公開一個 uiState」,測試跟著換。
10. **文件與既有測試**:技能文件改成講訪談題目、開關表、採用步驟、改主意怎麼做(換開關:重跑產生器、換掉節點與測試兩段,不重產清單;new-only 改 all:刪舊檔清單、用 `--legacy all` 重產測試;新增模組:宣告與測試常數各加一個;採用分支開著時主線進來的舊式檔,合併前補進清單)、已照舊範本採用的專案怎麼升級(先改名或刪掉舊節點與 arch_targets 再跑;不升級照常運作);寫明舊檔清單與 none 的分工——none 是目錄級的長期排除(樣式),舊檔清單是採用當下凍結的逐檔名單(字面),同一支檔被 none 命中就不看清單;不擴充 arch_targets 加欄位的理由:宣告形狀只收兩欄,舊版 lumos 讀到多一欄的宣告會整份不用,獨立檔被舊版忽略就好。06 那一列、技能首頁那句、`Systems/arch-alignment-lens`「下一次推送才生效」那句補上畢業例外與兩者分工;指令索引 INDEX.md 與 `--help` 的「什麼時候用」補上新指令(INDEX.md 有字數上限,要在上限內)。舊的三支範本測試:`t_arch_target_android_template_valid` 與 `t_arch_target_android_template_konsist_names_match` 改測產生器在「single、all、required、full、deep、any」這一組的產出(跟範本現在的十二條同組),`t_arch_target_android_template_linked_from_usage` 照留;舊計劃 `[[Projects/Android的MVVM與DDD目標架構範本_計劃]]` 的 S1、S3 綁定照名字不變,在那篇註明內容改由產生器提供。

舊否決對照:[[Projects/架構對齊可宣告目標架構_計劃]] 定了「代碼審只讀起點版宣告,分支改的宣告下一次推送才生效」,理由是被審分支不能自己改宣告決定自己怎麼被審。畢業部分推翻這條;Enzo 2026-10-30 在聽完這道保護與「另開一個只刪宣告的小合併請求」替代做法之後,仍選同分支生效。範圍因此只開一個口:宣告一字不改時,從清單刪掉的檔照目標審;規則原文照讀起點版。

PRIOR-ART:開關借 Android 官方架構指南本身的分歧點——領域層(用例)在指南裡標為可選、UI 狀態指南建議單一狀態物件但不強制;DDD 輕量版借「只取分層與 Repository、不取戰術模式」的常見做法;多模組借 Now in Android 的 core/feature 拆法。舊檔清單借靜態分析工具的 baseline 檔(採用當下凍結、新碼才擋,例:detekt baseline、Android Lint baseline 都是獨立檔、照字面比對、刪一行就恢復檢查),格式照 `.lumos/` 底下其他檔用 JSON。產生器只讀不寫,沿用專案讀範本的既有做法,不加依賴。
RETIRE-IF:2027-04-30 人裁時,若沒有任何 Android 專案用產生器建過目標架構節點,撤掉產生器與開關資料檔,範本退回固定版 [retire:人裁] [until:2027-04-30]。
RETIRE-IF:畢業判定若出現一次「分支靠刪清單行讓本該比鄰居的檔逃過審查」的實例,撤掉同分支生效、改回下次推送才生效 [retire:人裁] [until:2027-04-30]。

## 開關

| 開關 | 選項 | 影響 |
|---|---|---|
| 模組切法 `modules` | `single` 單模組 / `multi` 多模組 | multi 加一條模組依賴規則,Konsist 測試不減 |
| 舊程式處理 `legacy` | `all` 範圍內全部套用 / `new-only` 舊檔照舊 | new-only 寫舊檔清單;只套指定目錄=只給那幾個 `--scope` |
| 用例層 `usecase` | `required` 一定要有 / `optional` 可省略 | optional 時 ViewModel 可收 domain 的 Repository 介面,只禁 data 層實作與資料來源 |
| DDD 深度 `ddd` | `full` 完整 / `lite` 輕量 | lite 拿掉三條聚合類規則與測試,其餘規則換成不提聚合的版本 |
| 介面策略 `interfaces` | `deep` 深模組 / `always` 一律開介面 | always 換規則、用例測試篩選認 Impl、多一支介面測試 |
| 畫面狀態 `ui_state` | `single` 單一 UiState / `any` 不限 | single 換成「每個 ViewModel 只公開一個 uiState」規則與測試 |

## 驗收條款

分兩次交付:第一部分(舊檔清單與畢業)交 S5、S6、S9、S11;S1–S4、S7、S8、S10 屬第二部分(產生器與 Konsist 範本),第一部分合併時那幾條綁的測試名還找不到。

- [S1] 當產生器跑遍六個開關的全部 64 種組合時,每一份產出的節點經 lumos lint 應回報 0 問題,目標架構規則讀法讀到的有效 RULE 行數應等於那個組合該收的規則數;每條帶測試綁定的 RULE 行指到的測試名都應在同一份 Konsist 檔裡有同名測試函式,Konsist 檔裡的每個測試函式也都應被某條 RULE 行或命名慣例清單認領;產出的 arch_targets 經讀宣告的函式讀出的條數應等於 --scope 的個數。 [test: t_arch_template_android_all_combos]
- [S2] 當只切換一個開關時,產出應只在那個開關負責的地方不同:usecase=optional 時 ViewModel 規則與測試不再禁 Repository 介面;ddd=lite 時沒有三條聚合類規則與三支對應測試,而且整份節點的 RULE 行不含「聚合」二字;interfaces=always 時沒有深模組那條、有一律介面那條,用例測試的篩選認 UseCaseImpl,並多一支介面測試;ui_state=single 時有單一 uiState 那條;modules=multi 時多一條模組依賴規則,而分層與 Android 匯入兩支測試仍在。 [test: t_arch_template_android_switch_effects]
