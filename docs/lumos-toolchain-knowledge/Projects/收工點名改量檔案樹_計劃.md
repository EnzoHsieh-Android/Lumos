# 收工點名改量檔案樹

> 白話:收工時那句「這一輪改了 N 個程式碼檔」會少報。實測一輪改三支,它說一支——因為它是靠「看你用了哪個工具」去猜改了什麼,只認得 Edit/Write/MultiEdit 加上搬移複製刪除那幾個 shell 命令。用 `>` 重導向、`sed -i`、heredoc 改的檔,一支都不算數。不是不響,是少報;少報比不響難發現,因為它看起來像正常運作。

## 這是怎麼被發現的

起點是另一個問題:AI 派出去的子代理做事時,那些 hook 攔不攔得到。實測結論是攔得到(見下),但過程中順手量了一件事——最近 12 份對話紀錄裡,改程式碼檔的動作有 286 次走 shell、31 次走編輯工具。九成走在不被計入的那條路上。

## 實測證據(2026-09-18,Claude Code 2.1.274)

手法:造假的對話紀錄餵給那支 hook,看它印什麼。不看模型怎麼說,只看 hook 自己的輸出。

| 情境 | 這輪實際改了 | hook 說改了 |
|---|---|---|
| 只用 Write 改一支 | 1 支 | 1 支 ✅ |
| 只用 `cp` 改一支 | 1 支 | 1 支 ✅ |
| 只用 `echo > 檔` 改一支 | 1 支 | **完全沒輸出** ❌ |
| 只用 `sed -i` 改一支 | 1 支 | **完全沒輸出** ❌ |
| 混用:Write 一支 + `sed -i` 一支 + heredoc 一支 | **3 支** | **1 支** ❌ |

最後一列是最毒的:提醒響了、看起來正常,清單卻漏掉三分之二。

附帶實測(同一批,回答「hook 攔不攔得到子代理」):Write/Read 兩種工具、general-purpose/Explore 兩種子代理,四種組合全部攔得到,送進 hook 的資料多了 `agent_id` 與 `agent_type` 可供辨認。所以子代理不是破口,**工具種類才是**。

## 根因:能力早就有,被上游一道錯的守門擋住

那支 hook 的流程是四道閘:

0. 這個專案有沒有圖譜(沒有就閉嘴)
1. 這輪有沒有做過任何事(讀對話紀錄)
2. **算出「這輪改了哪些程式碼檔」——靠列舉工具名** ← 錯在這裡,算出空的就直接結束
3. 這輪有沒有動過圖譜——**這一道之後分岔成兩條互斥的路**

兩條路各印各的,同一輪只會走到其中一條:

| 閘門 3 的結果 | 走哪條 | 印什麼 | 「改了哪些檔」怎麼算的 |
|---|---|---|---|
| 這輪動過圖譜 | 呼叫 `_impact_missing` | 「動了筆記,但這幾篇直接相關的還沒動」 | 該函式自己用 `lumos impact --diff HEAD --sync-check`(工作樹 vs 上次提交),不看工具名 |
| 這輪沒動圖譜 | 直接印 | 「這一輪改了 N 個程式碼檔,筆記沒動」 | **用第 2 道閘算出來的清單,也就是工具名那一套** |

所以精確的說法是:

- **「改了哪些程式碼檔」這個清單,兩條路都卡在第 2 道閘的工具名判定上**——因為第 2 道閘算出空的就整個結束,兩條路都到不了。
- **只有「哪幾篇筆記該動沒動」那一步,已經是拿工作樹跟上次提交比。** 那是另一個問題的答案,不是「改了哪些檔」的答案。

★前掃訂正(2026-09-18):本節初稿把上面兩件事講成同一個「第 4 步」,並由此寫成「下游不動」。核心論點不變——錯的來源仍是第 2 道閘的工具名判定;但「下游已經是 git 比對」只適用於「算哪幾篇筆記沒動」那一支,不適用於「算改了哪些檔」。★

修這件事不是加能力,是把第 2 道閘的判斷來源換掉;下游那句「哪幾篇筆記沒動」本來就對,不用動。

## 方案

把「這一輪改了哪些程式碼檔」從**讀對話紀錄認工具名**,改成**量檔案樹**。

- 不再列舉工具名。列舉法永遠慢一步:這次補 `sed`、heredoc,下次還有 `tee`、`patch`、`git apply`、一行 python、編輯器暫存檔搬回去。每加一個名字都是再賭一次「這次列完了」。
- 量檔案樹對「用什麼工具改的」免疫,因為它看的是結果不是過程。

### 要解的一個真問題:怎麼切出「這一輪」

拿工作樹跟上次提交比,會把**所有**未提交的改動都算進來——包括不是這一輪改的、以及共用工作目錄裡別人留下的東西(2026-09-18 當下主 clone 樹上就有 4 支改動 + 27 筆未追蹤,多半不是當前會談造成的)。

做法:每次收工存一份快照(工作樹相對上次提交的檔案清單與雜湊),下一次跟上一次比,差集就是這一輪。

- 第一次跑、或快照讀不到時**沒有基準**:退回全量(工作樹 vs 上次提交)。這會多報,但多報是安全方向——少報才是這次要修的病。
- ★退回全量時必須明講「這次可能把不是這輪的改動也算進來」★,不要安靜地報一個看起來精確的數字。少報最毒的地方就是看起來像正常運作,退回全量時不能重蹈覆轍。

## PRIOR-ART

- 檔案雜湊前後快照取差集,用來回答「這段期間誰改了什麼」——是既有作法不是新發明;同一天另一個會談提到本機有一份量測儀器(算「AI 改到哪些檔」)就是這樣做的,它說那份儀器其他地方毛病不少、唯獨這一塊沒被挑出問題——★這條沒點名是哪一份、我也沒去查證,只當旁證不當依據★;真正站得住的旁證是下面那條(本 repo 自己的兩道閘)。
- 本專案自己的 `pre-commit` / `pre-push` 兩道閘也早就是量 git 索引,跟用什麼工具改的無關——**同一個 repo 裡已經有兩處在用正確作法,只有收工這一處在用列舉法**。
- 零依賴家規下不引入新套件:`git status --porcelain` 即可,本 repo 4074 個追蹤檔實測跑一次 30 毫秒。

## RETIRE-IF

- 連續四週,收工點名一次都沒有比舊作法多抓到檔(代表大家其實都走編輯工具,列舉法就夠) → 撤掉快照機制,退回原本的列舉法,省下狀態檔的維護。
- 或:快照差集的誤報(把別人 / 別輪的改動算成這輪)多過真報 → 同樣撤掉,改回全量並只印警告。

## 驗收條件

1. 上面那張表的五個情境重跑,**混用那列要報 3 支**,`echo >` 與 `sed -i` 兩列要從「沒輸出」變成有輸出。
2. 額外餵一個**方案裡沒列舉過的手法**(例如 `tee`、`patch`、或一行 python 寫檔),看它會不會漏——這比補完列舉表更能證明修對了。
3. 沒有基準時的退回路徑,要看得到那句「可能算進不是這輪的改動」。
4. 拆掉守衛要能翻紅:還原前先清 `__pycache__`,否則改動大小相同又落在同一秒,Python 會沿用舊的編譯快取,你會看到假的綠。

## 實作時已知的坑

前四條來自同一天另一個會談的回饋(它踩過或當天剛重現),第五條是本篇自己量到的。標明來源是因為第二條我沒有自己重現過,只是本專案早有同族前例。

1. **基準要每一輪重取,不是整個 session 取一次。** 收工 hook 是每輪結束跑一次;基準若只在開場取,第二輪起差集會含第一輪的改動,變成重複報同一批檔。
2. **判定一律比內容雜湊,不要只看修改時間加大小。** 同樣長度的字串換掉、整個動作落在同一秒內,時間和大小兩個都不會變。同族前例見 [[Systems/記憶過期清掃]] 裡那條「翻紅驗證踩到位元組碼快取」的教訓(拆除只改了一個字、檔案大小不變、還原又落在同一秒,直譯器沿用了拆除版的快取)——同一個原理會讓快照判成「沒改」。時間加大小可以當便宜的預篩,但**最後判定要回去比內容**。
3. **基準檔不能放在 repo 的工作樹裡。** 放進去它自己就變成未追蹤檔,汙染別的會談看到的 git 狀態——那正是本篇要解的問題的另一半。放會談自己的暫存目錄。
4. **退回全量只能當「標示過的降級模式」,不能當預設。** 續接舊會談、對話被壓縮、上一輪 hook 崩掉,都會讓基準不存在。此時樹上別人留下的未追蹤檔會全部被算成這一輪的(當天主 clone 就有 27 筆)。所以降級時一定要印出「這次的清單可能含不是這輪的改動」。
5. **共用工作目錄是常態不是例外。** 當天同一個主 clone 上同時有三個會談;任何「工作樹上有什麼就是我改的」的假設在這裡都不成立。

## 條款

- [S1] 當這一輪用任何方式改了程式碼檔(含重導向、原地取代、heredoc、管線寫入、以及沒有列舉過的手法),收工點名的清單應含每一支被改的檔,不得少報 [test:t_sync_nudge_counts_shell_writes]
- [S2] 當這一輪同時用編輯工具和 shell 改了不同的檔,清單應同時含兩邊,且印出的數字應等於清單長度 [test:t_sync_nudge_mixed_tools_counts_all]
- [S3] 當取不到上一輪的基準(首次執行、續接舊會談、上一輪崩掉),輸出應明講「這次的清單可能含不是這輪的改動」,不得安靜地印一個看起來精確的數字 [test:t_sync_nudge_no_baseline_says_degraded]
- [S4] 當基準存在,清單不應含上一輪已經算過的改動(每輪重取基準,不是整個會談取一次) [test:t_sync_nudge_baseline_is_per_turn]
- [S5] 當要存下這一輪的基準快照時,主體應把它寫在被檢查的 repo 工作樹之外(否則它自己會變成未追蹤檔,汙染其他會談看到的狀態) [test:t_sync_nudge_baseline_outside_worktree]
- [S6] 當檔案內容改了但長度與修改時間都沒變,仍應判定為「改過」(判定比內容雜湊,不只比時間與大小) [test:t_sync_nudge_detects_same_size_same_mtime_edit]

## 實務隱患

- 已排除:金流:這支 hook 只讀檔案狀態與印提醒,不碰任何金額、帳務或計價邏輯。
- 已排除:對外送出:全程本機執行,不發任何網路請求。會開子行程的有兩處(算波及的 lumos、反查筆記的 obsidian 命令列工具),兩處都在本機跑、都不連外。
- 已排除:不可逆:只讀不寫被檢查的檔;唯一寫入是自己的基準快照,放在會談暫存目錄,刪掉只會退回降級模式。
- **不能排除:守衛面**:本案改的就是一個守衛的判定來源,而且改的是它「算出哪些檔」這一步——算錯的後果正是本案要修的病(少報看起來像正常運作)。所以這一項不寫已排除,照走設計審。

## 回退

退回方式:把那支 hook 還原成改動前的版本(單檔還原,不牽動其他檔),並刪掉基準快照目錄。快照放在會談暫存目錄、不在 repo 內,所以刪掉不影響任何被檢查的專案。

退回的代價:回到現在這個少報的狀態——收工點名仍會響,但只算得到用編輯工具和搬移複製刪除改的檔,走 shell 改的仍然不列。也就是說,退回之後問題依舊存在但不會更糟;這支 hook 從頭到尾只讀檔案狀態與印訊息,不改任何被檢查的檔,所以沒有需要人事後收拾的殘留。

真正擋住壞改動的仍是提交前那道閘(它算的是版本控制索引,跟用什麼工具改的無關),本案的成敗不影響它。
