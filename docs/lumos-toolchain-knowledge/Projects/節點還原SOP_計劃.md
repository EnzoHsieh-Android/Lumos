## 使用場景(Enzo 指定,2026-08-24;d6。★本節於 r3 快照凍結後折入,未經迴圈審查★)

最典型的觸發:**要在龐大既有 codebase 上加新功能**——先把新功能會碰到的關聯面照本 SOP 還原成節點(只記 codebase 能證的事實),新功能的設計踩在這些節點上:沿用既有框架與元件、不破壞架構、不重造輪子。還原產出直接變成新功能 spec 的護欄素材:共用面清單=不准亂動的承重牆,合約候選=改了就壞的紅線(對應種子影片 forbidden 段的機械化來源);下游 code-loop 的架構對齊席負責抓「跟既有寫法不一樣」。一魚兩吃:這塊功能落成節點,新功能拿到正確脈絡。

**生長哲學=惰性**:節點不整倉攤平,進場先查(`lumos search`/`context`)——**有→照既有慣例用;有但殘缺→照步驟 4 前置 diff 補;沒有→走七步產一篇**。圖譜沿著實際被動過的面慢慢長回原始樣貌,永遠不欠「全倉還原」的債(世界解:Strangler fig 漸進接管在知識層的同構,Fowler 2004)。

## 設計:七步 SOP(任何技術棧,編號步驟 0–6)

適用場景:裝了 lumos、圖譜空或稀疏的既有專案;或本專案裡目擊紀錄佚失的舊模組。核心原則:**還原跟著任務走(d1)、產出落成節點而非留在對話、每條 why 亮身分(d2)、出口必過交叉查核**。

**步驟 0|進場與最小骨架**
圖譜空 → `lumos init` 裝殼。init **已經自動建好** `MOC/index.md` 空殼(r1 三席實錘)——**填它,不要另建**(`lumos new` 沒有 moc 型,另建也做不到;真另寫一篇會變成兩個互不知道的入口)。正文用 Edit 填:這個 repo 是做什麼的、幾個大件、各自入口在哪(檔案/目錄指針)。只寫指針不寫敘事。**先策展再自產**(世界解:Martraire):README/既有 ADR/測試名先撿,撿得到的算有證據,撿不到才寫推測。**整頁當「假設」經營**(世界解:reflexion models,1995):骨架標推測起步,之後每次任務跑出的實際依賴(步驟 2 追流、impact 結果)回頭對帳——猜對的升有證據、猜錯的改寫、猜了但不存在的刪;導覽頁從一次性靜態填寫變成會收斂的活假設。骨架停手線(可數,不用牆鐘):**一篇、指針 ≤30 行、不展開**;超大 monorepo 只列第一層大件,子件留給之後的任務驅動。

**步驟 1|錨點階梯定位**
從可觀察行為抓錨,反查到負責的 code 單元。冷啟動場景本步驟(含 2–3)**直接讀 code 不算違反「lumos 優先」鐵則**——那條管的是圖譜有料時;空圖譜 search 必 0 筆,不用跑滿換詞協定(r2 走查席抓到沒明講豁免)。錨點按便宜到貴排:
① **獨特字串**:網頁=畫面文字/元素 class;CLI=--help 或輸出文字;後端=log 訊息/錯誤碼;mobile=字串資源檔。
② 字串抓不到(minify/混淆、生成碼)→ **識別子**:i18n 是兩跳(畫面文字→語系檔抓 key→再搜誰用 key);函式名/類名/路由字串/協定欄位名/硬體暫存器位址。
③ 都沒有(embedded 韌體、宣告式資料管線——可觀察面是波形或排程行為,不是文字)→ **結構文件**:建置腳本、DAG 定義、接腳表、部署設定,從結構往回收斂。
④ 一到三級全滅(minify/DI/宣告式讓文字錨點失效)→ **動態差分**(世界解:software reconnaissance,1995):準備「會踩到該功能」與「不會踩到」兩個情境各跑一次,收執行軌跡或覆蓋率相減——只在前者出現的 code 就是該功能專屬;依賴注入與宣告式的間接性在執行期都已解掉,動態法天然免疫。**錨點信度**:單一技術命中=低信度,兩種獨立技術(如文字+依賴圖、文字+動態)交叉命中才算高信度(feature location 綜述的量化結論)。
承認:③④ 這兩級最貴也最容易漏,embedded/資料管線是本 SOP 的弱區(r1 s3 實錘),實跑驗證沒覆蓋到這兩類棧之前,對它們只有「階梯方向」沒有「驗過的流程」。

**步驟 2|追流+圈承重牆**
這個單元的輸入從哪來、輸出到哪去、**誰還共用它**。查共用面**至少兩個來源**:①拿單元名全域搜用法;②該棧的間接接線處——DI/IoC 設定、路由表、DAG 依賴清單、建置依賴圖、事件訂閱表;③加分來源:git co-change(長期一起被改的檔案=行為上的共用面,與靜態依賴互補)、或步驟 1 若跑了動態差分,兩情境軌跡的**交集**就是共用基礎設施的機械化定義(世界解:reconnaissance 同款)(r1 s3 blocker:純 grep 對依賴注入/反射/隱式介面會**默默漏抓**,找到一部分以為找全了,正是「改 A 壞 B」在還原階段重演)。**要下「沒有別人共用」這種否定結論、且它會決定少建節點時,照 CLAUDE.md ★第四條:派乾淨 agent 拿原始問題去對一次——這個場合原規則沒有降級選項(r2 抓到本文曾自己加「換詞重搜」備案稀釋強制性,已刪;換詞重搜是一般查詢紀律,不能替代派乾淨 agent)**。順手圈出**專案自己的錯誤語言**(包裝過的 logger、錯誤碼表——部落知識,git 考古不出來,種子影片點名的經典坑)。產出:FLOW 一行+共用清單。已有圖譜的專案先敲 `lumos impact --file <檔>`;冷啟動場景這條備援不存在,兩來源紀律就是唯一防線。

**步驟 3|考古還原 why(git 為主,非 git 補位)**
git 歷史是舊專案最容易拿到的目擊者:blame 找到改這段的 commit、log 讀訊息、revert/fix 紀錄、PR 描述。**招式具體化(世界解:git pickaxe/MSR)**:`git log -S'字串'` 找這行哪次進來/離開、`-G` 吃正則、`git log -L` 追單一函式全史;blame 撞到搬家雜訊用 `git blame <sha>^ -- 檔` 從上一版重跳;**blame 到 squash commit 別停**——撈 PR 編號去讀討論串,理由主要藏在 issue/PR 裡(MSR 綜述),squash 只抹平 git 內的顆粒,forge 上的第一現場還在。**git 沉默不等於 why 佚失**(r1 s3):squash 政策抹平細粒度、郵件補丁流沒有 PR、資料管線邏輯常改在外部平台、韌體 why 常在硬體資料手冊——git 挖不到時先問一圈**非 git 來源**(issue tracker、wiki、部署文件、資料手冊),都沒有才標佚失。標身分:答得出來源的標 `[git:sha]` 或 `[src:路徑:行號]`;推論標 `推測:`;查不到標 `佚失:`。**語序硬規定(r2 實測重現、r3 精化)**:標籤後可有空白,但 `推測:`/`佚失:` 必須是**第一個非空白內容**——`DECISION:推測:依據…`、`DECISION: 推測:依據…` 都合法;夾了文字(`DECISION: 原因不明,推測:…`)正則就比對不到照樣紅,錯誤訊息也不會解釋為什麼。**佚失是合格產出,不是步驟做壞了**——整個專案大量佚失(squash 起家)是預期結果;此刻正是最想編一個合理 why 的時刻,老實標比編漂亮重要。嚴禁從「現在長怎樣」反推發明「當初為什麼」;**`推測:` 行不准引用具體識別子當佐證**(檔名/函式名/欄位名——編造最常長在「像真的」的細節上;有把握引就該去驗證後改標 [src:])。**考古摘錄的紅線(r2 補的一整類)**:git log/PR/issue 常夾憑證、資安事件細節、內部人事內容——這些**不入圖譜**;挖到憑證照該專案安全流程處理,筆記只記「why 涉敏感背景,細節不錄」。圖譜會被索引、被 commit,把深處的敏感內容摘上檯面等於擴大外洩面。

**步驟 4|落節點**
**落筆前先查這篇是不是已存在**:`lumos search <模組名>`——舊節點還在(哪怕殘缺)就照重生守衛第一條 **diff 更新、別整篇換**(操作重述,字句以 reference〈重生守衛〉原文為準;保住殘存目擊內容;適用場景裡「目擊佚失的舊模組」正是這型,r2 通才席抓到七步漏了這條前置);真的從零才走下面全流程。起手 `lumos new system <模組>` 建骨架——骨架只有 FLOW/KEY/DEP/TEST 四行,**DECISION 行要手動加**(符號表把 DECISION 列在 Issues 下,但 system 筆記用它有先例、J-b 就是為它設的);摘要這幾行不在 set/append 指令值域,只能 Edit 手改,**注意 YAML 縮排與結尾 `---`**(記憶裡同日兩犯的坑)。摘要行分工(r1 通才席實錘,接上現成硬擋):
- FLOW=流程怎麼跑、DEP=依賴誰(指針級,快寫;注意 Check J **完全不掃**這兩種行)
- KEY=關鍵事實(指針級居多;沒標身分會吃 J-d 計數提醒,提醒不擋、屬預期噪音)。**步驟 2 的共用清單落在這裡**:`KEY:共用面:被 X/Y 使用(承重牆)[src:…]`——別塞 DEP,DEP 是反方向「這篇依賴誰」(r3 抓到查最重的產出沒地方放)
- **DECISION=考古出來的 why 放這裡**——J-b 對 DECISION 行是**硬擋**(缺 [src:]/[git:]/推測:/佚失: 直接紅),把 why 放 KEY 行等於自願放棄現成的機械保護
蓋章與時序:**正文與身分標記全部寫完 → `lumos set <節點> regen from-scratch/<日期>` 蓋章 → `lumos lint <節點>` → 同一次 commit**;不留「蓋了章還沒標完」的中間態過夜(機械層分不出半成品,見實務隱患)。落完跑 `lumos link-candidates <該模組主要 code 檔>` 看有沒有既有節點該連(接線,r1 通才席抓到掛名未接)。**多節點同批落時按依賴拓撲序**(先底層後上層——上層筆記寫時底層事實已就位;世界解:DocAgent 消融結論)。**知識分工**(世界解:Martraire):半衰期短、跟單檔綁死的細節就地寫 code 註解,長脈絡與跨檔 why 才進圖譜——別讓圖譜吸走本該住在 code 旁的東西。

**步驟 5|合約候選,不升格**
「改了就壞」的清單,開成章節 `## 合約候選(收斂時複核,候選≠已標)`,**放在這次還原批次的計劃筆記裡**(Projects/<主題>_計劃——還原批次照鐵則本來就要開計劃筆記),**不塞進 Systems 節點**:用過合約候選章節的先例**全在 Projects、零篇在 Systems**(逐字同款短版 3 篇,其餘同族變體;總數不寫死——r2 數 13、r3 兩席數 16,「計數型主張最會漂」的 L4 教訓②當場示範)。Systems 節點只在對應 KEY 行旁註「合約候選」字樣。**本步到此為止——標候選就是純文件動作。** 升格是**另一次任務**,走 code 側正常紀律,順序明列(r1 外家抓到缺步驟):取得意圖證據→把該行改標 ★INVARIANT★(regen 節點須附 [src:]/[git:],J-a 擋發明)→`lumos guard scaffold`→寫測試→`guard bind`→`guard audit`,全鏈走完才算合約——三個 guard 指令都有必帶參數(scaffold 要 --node/--invariant/--method/--type/--claim 等),**實形照 reference.md〈lumos guard〉段敲,本文不重抄防漂移**(r2 外家抓到裸寫序列照敲直接報錯)。專案沒測試→升格前先補特徵化測試(characterization test,世界解:Feathers 2004:把現況行為釘住,不判對錯;綁的測試證「改了就壞」是真的,不證行為是對的)——**這也屬升格任務,不在本 SOP 交付範圍**。施工法三招(同屬升格任務):綁不上測試≠降格,標「待 seam」(Feathers:seam=不改這裡的 code 就能換這裡行為的切點,先開 seam 才綁得上);golden master(大量輸入+輸出快照)最適合 AI 代產;綁上後跑 mutation 驗收——變異不翻紅的測試不算數(接本專案既有反假綠紀律)。且承認:embedded/資料管線補測試是基礎設施問題(要先搭 harness/模擬器),成本另計,不是「叫 AI 補幾條」就有。

**步驟 6|出口:交叉查核+接回既有紀律**
還原批次收尾先跑一道**引用實體機械掃描**(世界解:DocAgent Verifier 的便宜版):機器逐篇掃「筆記引用的檔名/函式/欄位是否真的存在於 code」(refcheck/`lumos search --code` 既有零件)——防編造第一道濾網,比派 agent 便宜一個數量級、可重算;掃完才跑**變體 B 交叉審計**,照 reference.md 原文的機制原樣用(r2 三席抓到上一版借名走樣,此處全對齊):**逐節點**各派兩個乾淨 agent——階段一只讀單篇筆記,萃取 **12~15 條可被程式碼驗證的具體主張、且逐條必須可證偽**(原文兩句分開抄,別合併——「可驗證」比「可證偽」寬);階段二只讀 code(禁讀 docs)逐條判 ✅/❌/❓。處置照原文:❌=修筆記(**以 code 為準**;code 本身是 bug 就開 Issue,不改筆記遷就)→**建 Verification 紀錄→相關 Systems 的 `verified_by` 雙向同步**——這就是出口的正式留痕。留痕**雙軌**:除上述 Verification+verified_by 外,逐節點**照樣蓋 `lumos self-audit`**——r2 曾判「錯綁」刪掉,r3 翻案:L4 清帳(同構的雙 agent 交叉審計)30 節點全蓋章+Verification 雙軌是真實先例,且體檢 Check S 只讀 self_audit 欄,不蓋=已審過的節點被誤報「從未審過」。r2 那次只看指令說明沒對先例,正是★第四條要防的「只信一個來源」——這次是審查員自己犯,r3 抓回。**PASS 批次也建一篇批次 Verification**(L4 先例同款),不是只有 ❌ 才留(r3 外家抓到 PASS 零留痕缺口)。**兩條本 SOP 自加的延伸裁定(變體 B 原文是選配巡檢手法,沒有這兩條;明標出處是本案,r2 架構席抓到上一版沒標)**:①還原批次**必跑**——理由:30 個被點名過期節點的清帳(有偏樣本:被軟閘點名的高危群)實測 16.3% 主張與 code 不一致,還原型節點同屬高危;②❓(找不到驗證點)不可原樣放行——回頭把該句改標 `推測:`/`佚失:` 或修掉。審計抓到要修的,**開新 commit、重跑 lint**——步驟 4 的「同一次 commit」管首次落節點的原子性,「中間態」專指「蓋了章但身分標記沒寫完」;審計後修正是正常的後續 commit,不算中間態(r2 抓到兩步銜接沒講)。之後要動手改 code,從這裡起全走現行流程:`lumos impact`、design-loop、code-loop。**警語(種子影片吸收)**:還原完直接動 production 級 code 前,至少讓改動走完 code-loop;還原節點內容日後被行為事實打臉→照 CLAUDE.md 既有規則立事故筆記,錯的節點標作廢或 supersede,這就是還原內容的收回路徑。
