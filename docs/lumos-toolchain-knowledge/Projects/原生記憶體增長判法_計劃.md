# 原生記憶體增長判法_計劃

白話:[[Projects/原生記憶體增長提示_計劃]] 先交付「量測結束時還留著最多的原生配置排行」,快取與池也會上榜。這份要回答的是排行上的哪幾個「到最後還在漲」(漏)、哪幾個「漲到一定量就停」(快取、池、一次性初始化),讓排行能把後者標出來。上一份計劃的設計審跑滿三輪,兩種判法(取三個時間點、錄製時段四等份取窗口最小值)都被時間對齊打穿:heapprofd 接上行程要等下一次配置之後幾百毫秒、傾印每秒一次、切點照錄製總時長算,池子情境在 64 組時間參數下全判成在漲,也分不出一次性跳升(卷證在 governance/review-reports/原生記憶體增長提示/ 的 r1–r3)。所以這份先做實驗,量準了再寫判法條款(上一份的 d5)。

PRIOR-ART: 增長判法借「重複回到同一個畫面、每輪都在漲才算漏」的形狀:BLeak(Vilk & Berger,PLDI 2018)與 Square LeakCanary 3.0 的堆積增長偵測(square.github.io/leakcanary/changelog:重複跑情境直到不再增長)。兩者都用「每一輪結束時」量一次,不是照時間切;這正是上一份兩種判法缺的:切窗要對到輪的邊界。裁定:借「每輪量一次、看增量有沒有停」的形狀,切窗改用驅動每輪的記號,不用時間比例。
RETIRE-IF: 實驗室造出的六種形狀(見〈要做的實驗〉)裡,有任何一種用每輪記號切窗仍分錯、而且改判法也修不好,就停掉這份,排行維持不分漲停。
REVISIT:2027-01-31 還沒開始實驗就重看一次這份要不要做:排行上線後真實專案前 20 名裡快取與池佔幾成,佔少數就擱置

## 要做的實驗

1. 每輪記號:驅動每輪開始與結束時留一個記號,要能在 heapprofd 錄檔的時間軸上找得到(候選:App 端寫 atrace 標記並在錄製設定加 track_event 或 atrace 資料源;或主機端在每輪前後讀裝置的 BOOTTIME 跟錄檔時鐘對齊)。先在 macrobench-lab 量哪一種在錄檔裡對得準、會不會拖慢量測。
2. 判法候選:每輪結束那一刻的累計 C1…CN(取該刻之前最後一次傾印的值),看後半輪的增量;每輪內配了又還的,因為只取輪結束時的值而不受影響。
3. 實驗室造六種形狀各跑三次:每輪漏固定量;SDK 內部留登記;上限 4 塊的池;第 3 輪一次性初始化;每輪配了又還;前段大量配、之後每輪少量漏。記每種的分類結果與重跑的抖動。
4. 量完才寫判法條款與門檻,走自己的設計審。

## 上一份留下的已知失效形狀(判法要能分對)

- 池子在量測前段填滿:上一份兩種判法都可能判成在漲。
- 中途才第一次走到的功能做一次性初始化:窗口最小值判法會判成在漲或判成不增長,看終點怎麼取。
- 輪長不均(後段變慢):照時間切的窗可能整段落在某一輪中段。
- 同一函式帶一份穩定大緩衝、再每輪少量漏:用「後半增量 ÷ 總量」的比例判會被大基底遮住。

## 不做

- 不在這份改排行本身(排行在上一份)。
- 不擋推送:判法做出來也只提醒,跟上一份 d2 一致。
