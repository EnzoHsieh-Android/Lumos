# 留痕驗過審查_計劃

白話:推送前的「審查通過」紀錄現在像一張自己填的簽到單,寫了就算,工具不看審查到底做完沒。這份計劃讓它在寫下之前先看一眼現成的判定檔:這個審查迴圈有沒有凍結判定、判定是不是過、判定之後帳有沒有再變。沒過就不給寫,真的不審走既有的 `skip`,照樣留痕、照樣被統計。總路線見 [[Projects/代碼審收尾強化_計劃]]。

WHY:`pass` 寫入前讀既有凍結判定檔,不重算處置閘、不新增第二道閘 [出處:2026-11-01 調研報告第 1 條與程式核對] [因:手冊本來就規定留痕前要凍結,判定檔已帶結果與逐列指紋;防的是忘記與順序錯,不是刻意偽造] [不選:pass 內重跑處置閘(要自帶 spec 路徑,還多一條判定入口);code-loop check 讀判定(推送檢查的合併與新分支路徑已很複雜,且 CI 跟著變);golden 回放(帳本長大只列出不紅,抓不到判定後又加輪)]
WHY:沒帶 `--loop` 且專案有審查帳就擋 [出處:2026-11-01 使用者裁,本篇 d1] [因:2026-10-15 起 113 筆留痕有 52 筆備註含已凍結迴圈名,靠自由文字認迴圈不可靠;`skip` 是既有出口] [不選:先只印不擋四週(只提醒的東西沒人回頭);讓 tier=high 才要求(pass 不算 tier,要多一次分級計算)]
WHY:人裁接受風險的迴圈放行,不逼走 `skip` [出處:r1 回滾與正確性兩席;2026-11-01 三個真實迴圈實測] [因:這類判定 rc 非 0 是帳上永久結果,重凍不會變;`skip` 會把審過且人裁的迴圈記成沒審] [不選:明寫只能 skip(統計失真,且正好觸發撤除條件)]
PRIOR-ART: 世界解是合併條件綁審查狀態:Anthropic 內部逐條必答才能合併,GitHub 的必要檢查也是同型。本 repo 既有先例是 `check` 綁提交編號的留痕與 `loop replay --freeze` 的判定閉包,這裡借用閉包,不新增帳本。調研依據在 `governance/research/code-review-world-2026-11/report.md`。
RETIRE-IF: 上線滿三個月,`pass` 擋下的事件經人判讀,誤擋多於抓到真漏審,或擋下幾乎全部改走 `skip`,就撤掉判定檔檢查、只留 `--loop` 綁定。
REVISIT:2026-12-15 用放行事件的 `nodes` 加審查帳離線算最後一輪 major 修補沒人看過的比例與之後逃逸,判斷要不要擋;要擋先解決第三輪上限衝突。
REVISIT:2026-12-15 比對高風險推送的算出分級與迴圈帳上分級,判斷 `pass` 要不要驗「帳上分級不低於算出分級」。
REVISIT:2026-12-15 數跑滿上限又沒有合格回顧卻過了 `pass` 的迴圈,判斷 `pass` 要不要連跑滿回顧一起驗。
REVISIT:2026-12-15 比對放行事件綁的迴圈凍結 patch 跟當時分支改動檔,數零重疊的筆數,判斷「迴圈跟分支沒綁定」這個天花板要不要收;順便判斷 `check` 要不要也讀 `nodes`。

## 問題與現況

- `cmd_code_loop` 的 pass 分支只寫 marker 與治理帳,`pass` 與 `skip` 共用同一分支;手冊也寫明這是既有天花板。[[Projects/code-loop分支留痕一致_計劃]] 2026-10-04 前掃時把「程式不驗審查完成」列成人工前提,不是否決,那案本身未合入。
- `LOOP_CLOSE_EVENTS_BY_DETAIL` 上方的 REVISIT(2026-11-07)指定的正解就是 `--loop` 參數寫進 `nodes`,本案順帶關掉它。現有 642 筆 code-loop 放行事件的 `nodes` 全是空的,讀側 `_loop_close_stamps` 靠編號在 `detail` 全文做邊界比對。
- 判定檔在 `<repo 根>/governance/replay/<編號>/verdict.json`。事實(2026-11-01 讀 `cmd_loop_replay`):結果在 `verdict.rc`,判定不過也會寫檔(255 個代碼審判定檔有 6 個 rc=1,其中 3 個是人裁接受風險);`fails` 只有標籤,沒有原因;無輪次與舊 panel 帳的迴圈拒凍;凍結跳過第八步跑滿回顧。重凍要帶 `--note`,卷證要先提交。
- 帳上事實(2026-10-01 起的 code 迴圈,160 個):有判定檔 132 個;高風險 5 個、標準級 9 個沒有,部分是棄案或換編號,沒逐一確認;輕量 11 個沒有。標準級無輪次 2 個。全帳分級空白且無輪次 5 個,這段期間 0 個。輕量但有輪次 8 個。

## 做法

1. `lumos code-loop pass` 新增 `--loop <編號>`;`skip` 完全不動,不收 `--loop`。判定寫成獨立函式 `_codeloop_pass_verify`,不塞進 `cmd_code_loop`。所有印出來的指令,編號一律過 `_rf_qloop`。
2. 審查帳路徑固定 `<repo 根>/docs/.canary-log.jsonl`,跟 `cmd_severity_check` 與 `_codeloop_gov_log` 同根。vault 不在 `docs/` 底下的專案視同沒有帳。不為讀帳建 `Env`。
3. 寫入前判定,依序,任何一條擋下都回 rc2、不寫 marker 與放行事件:
   - 帳檔不存在 → 不驗,行為照舊(vault-free 專案的相容邊界)。帶了 `--loop` 只印一句「這個專案沒有審查帳,沒有驗」,`nodes` 不寫,所以 passed 事件的 `nodes` 非空就代表驗過或輕量放行;舊事件 `nodes` 為空不代表沒驗。
   - 沒帶 `--loop` → 擋,訊息給帶編號的指令,並點出不審走 `skip`。
   - 編號含路徑字元(同 `cmd_loop_replay` 的三種)、不是 `code-` 開頭(同 `_roster_kind`)→ 擋。歷史編號 `codestage`、`code側刪除傳播守衛` 不受理。
   - 帳檔讀不到或帳裡有壞行 → 擋,印壞行行號,訊息給修帳的下一步與 `skip` 出口。壞行指不是合法 JSON、巢狀過深、不是物件的行,範圍是整本帳(壞行歸不到迴圈),同處置閘;非 UTF-8 用替代字元讀,不算壞行,因為指紋要跟凍結時同一種解碼。舊形狀迴圈處置閘是容忍的,這裡比它嚴,出口是 `skip`。
   - 篩完(不算規格閘留痕與結局帳列)帳上沒有這個編號的列 → 擋,訊息指向 `loop next` 開迴圈或 `skip`。編號比對跟 replay 一樣用字面相等。
   - 分級取 `_loop_anchor_tier`,輪次格式取 `_loop_round_format`。輪次混用 → 擋,不分分級。其他分級無輪次 → 擋。這兩條擋下的訊息指向 `skip` 或換編號重記(沿用 `_RF_RENUMBER` 的措辭),不給凍結指令,因為照做也凍不成。
   - 分級 light 且無輪次:判法同 `loop next` 的 escalate,帳上有 `kind` 是 caught 或 none 而 severity 是 major 或 blocker 的列 → 擋,訊息指向開 `<編號>-std` 完整迴圈或 `skip`;沒有 → 放行,不要求判定檔。
   - 判定檔不存在 → 擋,給凍結指令加 `skip` 出口;`--spec` 只取最後一輪自己的 `spec_path`(同 `loop next` 補指令那段,不借更早輪次),路徑以 repo 根為錨、檔案要存在,取不到就留 `<凍結 patch>` 佔位;指令帶 `--repo`。
   - 判定檔不是合法 JSON(含巢狀過深)、不是物件、缺 `verdict`、`all_row_shas`、`round`,或型別不對 → 擋。判定輪指判定檔的 `round`。不比 `engine_rev`:這裡只讀結果,不重算。
   - 現帳指紋跟判定檔 `all_row_shas` 以集合比較不同 → 擋,給帶 `--note` 的重凍指令。這條排在看結果之前:判定已經不代表現帳時,裡面的結果沒有意義,舊判定失敗而補輪收斂的迴圈才走得出來。雙向都算:replay 把「帳本長大」當常態是因為它只看判定有沒有漂移,這裡要回答的是判定還代表不代表現帳。只比最後一輪編號抓不到同輪多一席。逐字重複的列不算變,現帳有 5 個迴圈是這樣,來自一次合併。
   - `verdict.rc` 不是 0:用 `_retro_gov_events` 讀人裁紀錄,最新一筆 `_retro_is_decision` 成立的紀錄是 `accept-risk` 而且它的 `rounds` 含判定輪時放行,印一句「人裁接受風險」;否則擋,印 `fails` 標籤,給帶 `--spec` 與 `--repo` 的 `loop status <編號> --disposal` 指令看原因,並講出口:把問題修完加一輪再凍結,到上限走人裁,都不適用就 `skip`。治理帳讀不到時擋。人裁接受的是整個迴圈收尾,不分 `fails` 種類,這道防忘記,不代替人裁判斷。
   - 每次擋下用 `_gate_event_or_warn(repo_root, "code-loop", "blocked", note, hard=True, head_sha=…)` 落一筆,note 以 `pass-refused:` 開頭、帶編號與原因。訊息照三段式:擋下什麼、為何在意、下一步指令獨立一行。
4. 讀帳走現成核心 `_canary_ledger_rows`(`errors="replace"`,壞行進 `bad`),加一個可選參數把解析成物件的列的原文一起交回,算指紋要用,原文要跟 replay 凍結時用 `_ledger_lines` 切出來的逐字相同,實作時拿現有判定檔全部比一次。篩法(編號相等、不算規格閘留痕與結局帳列)抽成一支,`cmd_loop_replay` 的 `_load_rows` 跟 pass 共用;replay 的讀法與跳過壞行不動。`_is_outcome_row` 說明裡的入口清單與計算整本帳被讀幾次的守衛要同步。
5. 過了才寫:marker 不變;`_codeloop_gov_log` 加有預設值的 loop 參數,`nodes` 寫 `[編號]`;`_loop_close_stamps` 對 code-loop 放行事件 `nodes` 有字串就直接蓋戳,不依賴 known_loops,空的才走現有全文比對。`_STATS_NODE_SEMANTICS` 補 code-loop 的說明。`LOOP_CLOSE_EVENTS_BY_DETAIL` 上方的 REVISIT 與 `_loop_close_stamps` 說明同步改掉,`cmd_code_loop` 說明的 rc 表補上 pass 被擋。
6. 改提示與手冊,以下列全:
   - `scripts/lumos`:`code-loop check` 表態那段印的 `pass --note` 指令;原因句「tier=high 且無留痕」不動,裡面沒有指令,而且 pre-push 的逃逸判定靠它開頭。
   - `scripts/hooks/pre-push`:逃生路那行 `審過 lumos code-loop pass --note`。`pp_cl_reason` 不動。
   - `.github/workflows/ci.yml` 的 `pass|skip --note` 拆開寫。
   - `skills/lumos-code-loop/SKILL.md`(description、六道判定那段、步驟 8)、`reference.md`(範例三處)、`skills/lumos-project-notes/commands/06-代碼審與推送.md`、`skills/lumos-project-notes/reference.md` 的範例都帶 `--loop`,而且凍結寫在 `pass` 前面。
   - SKILL 與 reference 裡「pass 本身不回頭驗問閘」同一句改寫。
7. 舊筆記同步:[[Projects/審查跑滿回顧_計劃]] 與 [[Systems/loop-retro]] 講「沒有程式拿凍結判定當放行依據」的句子;[[Projects/代碼審資安席_計劃]] 講 pass 不驗的句子與 2026-12-11 回頭條件改指本篇;[[Projects/逃逸帳對得起來_計劃]] 講留痕不帶編號的句子;[[Systems/lumos-cli-read]] 那句 nodes 帶編號在本案之後才成真;[[Systems/bound-tests-gate]] 那句「掛在 check 不掛 pass」補上適用範圍。
8. 測試:`t_codeloop_pass_survives_bookkeeping_commits` 的第二次 `pass` 在有審查帳的 repo,改版後會回 rc2 而測試忽略 rc,變成假綠;要改帶 `--loop` 或調整帳檔時機,並補一句斷言 rc0。`t_loop_list_open_loops` 的 fixture 註解「nodes 永遠是空的」同步改寫。

## 驗收條款

- [S1] 當 repo 有審查帳而 `pass` 沒帶 `--loop` 時,應 回 rc2、不寫 marker 與放行事件,應 落一筆 note 開頭 `pass-refused:` 的 blocked 帳,訊息 應 含帶編號的指令與 `skip` 出口 [test:t_codeloop_pass_requires_loop]
- [S2] 當 repo 沒有審查帳時,`pass` 不帶 `--loop` 應 照舊成功寫入;帶 `--loop` 應 成功、`nodes` 為空並印「沒有驗」 [test:t_codeloop_pass_no_ledger_unchanged]
- [S3] 當帶的編號含路徑字元、不是 `code-` 開頭、或篩完帳上沒有列時,應 回 rc2 且不寫放行事件;當帳檔讀不到、帳裡有壞行、巢狀過深或不是物件的行時 應 回 rc2、不丟 traceback,訊息 應 含 `skip`;印出的編號含空白時 應 加引號 [test:t_codeloop_pass_rejects_bad_loop]
- [S4] 當標準或高風險迴圈的判定檔不存在、不是合法 JSON、不是物件、缺欄位時,應 回 rc2 且不寫放行事件;判定檔不存在時訊息 應 含帶 `--repo` 的凍結指令與 `skip`,最後一輪 `spec_path` 取不到或檔案不存在時 應 留佔位不崩;`verdict.rc` 為 0 且帳沒變時 應 寫入,`nodes` 為 `[編號]` [test:t_codeloop_pass_checks_verdict]
- [S5] 當 `verdict.rc` 非 0、帳沒變、而且最新人裁是涵蓋判定輪的 accept-risk 時,應 放行並印人裁字樣;最新人裁是 extra-round、沒有人裁、或 accept-risk 不含判定輪時 應 回 rc2,訊息 應 含帶 `--spec` 的 `loop status --disposal` 指令與 `skip`;治理帳讀不到時 應 回 rc2 [test:t_codeloop_pass_accept_risk]
- [S6] 當凍結後帳上多一列或少一列審查紀錄時,應 回 rc2 並給帶 `--note` 的重凍指令,即使判定 rc 非 0 也 應 先給這條;只多規格閘留痕、結局帳列,或逐字重複列時 應 放行;現有判定檔用這個讀法算出的指紋 應 跟檔內相等 [test:t_codeloop_pass_stale_verdict]
- [S7] 當迴圈分級 light 且無輪次、帳上沒有 major 以上的列時,應 放行且不要求判定檔;帳上有 major 以上的列時 應 回 rc2 並指向 `-std`;分級 light 但全有輪次時 應 跟標準級一樣驗判定檔 [test:t_codeloop_pass_light_loop]
- [S8] 當迴圈輪次混用(不分分級)或非 light 的迴圈無輪次時,應 回 rc2,訊息 應 含 `skip` 與換編號,不含凍結指令 [test:t_codeloop_pass_roundless_dead_end]
- [S9] 當治理帳的放行事件 `nodes` 有編號時,關門判定 應 認得該迴圈,即使審查帳沒有這個編號;舊事件 `nodes` 為空時 應 照舊用 `detail` 全文比對 [test:t_loop_close_reads_nodes_first]
- [S10] 當跑 `skip` 時,行為與寫入的事件 應 跟改動前完全相同,不收 `--loop`,`nodes` 維持空 [test:t_codeloop_skip_unchanged]
- [S11] 當 pre-push 的原因句與 lumos 的種類比對時,既有守衛 應 維持綠,`pp_cl_reason` 與「tier=high 且」開頭 應 不變 [test:t_prepush_cl_reason_table_matches_lumos]

## 不做

- 不改 `code-loop check` 與 CI 的判定,只改提示文字。所以「留痕合格」暫時有兩個定義:`pass` 寫入時驗判定,`check` 只驗提交綁定;舊留痕、合併側帶進來的留痕照認。閘放在 `pass` 而不是 `check` 的理由是 `check` 今天不知道分支對應哪個迴圈,綁定只在 `pass` 當下才產生;既有「掛在擋的路徑不掛記錄的路徑」那句管的是合約測試,測試結果隨提交變,判定是凍結當下的一次性事實。
- 不驗迴圈跟這條分支有沒有關係:判定檔沒有提交或範圍資訊,任何綠的舊編號都過得了,審完又加提交再 `pass` 同一個編號也過得了。這是刻意的天花板:帳上編號本來就是記帳的人自己填的,這道防忘記與順序錯,不防拿別的編號頂替。要連起來得拿凍結 patch 跟分支改動比檔案,而修補輪、合併後重留痕都會讓比對誤擋。
- 不重算處置閘,不驗跑滿回顧:凍結本來就跳過第八步,所以 `pass` 這條路上沒有人驗跑滿回顧。
- 不擋也不在 `pass` 記錄最後一輪修補沒人看:第三輪修完再派席就是第四輪,要 `cap-decision`,直接擋會把人裁變成每次必走。觸發率實測約三到五成,是全折即收斂的常態,印提醒只是雜訊;數字用 `nodes` 加審查帳離線就算得出來,不加欄位。
- 不解 `pass --branch`:那是 [[Projects/code-loop分支留痕一致_計劃]] 的範圍,候選碼在實驗分支,本案不併。
- 不擋刻意偽造:判定檔與帳都在同一個 repo,工具鏈威脅模型把這排除在外;消費專案也只防忘記。
- 標準級與輕量級推送本來就不查留痕,這點不變;這道只在有人跑 `pass` 時生效,實際涵蓋高風險級。

## 實務隱患

已排除:金流:不碰金額與付款。
已排除:對外送出:只寫本機 marker 與治理帳,不對外傳送。
不可逆:治理帳只追加,新寫的 `nodes` 與 blocked 事件無法撤。閘類讀者不看 `nodes`;`cmd_gov` 統計與 `gov --node` 會把 code-loop 事件算進去,同一提交不同編號不再折成一筆。`pass-refused` 事件會併進「硬擋 code-loop」計數,而且 `gov` 去重會把同提交連續擋下折成一筆,所以撤除條件不看 `gov --stats`,直接讀原檔:`grep '"note": "pass-refused:' docs/.governance-log.jsonl`。
守衛面:`pass` 是推送閘的前置,改壞會擋住全部高風險推送。對策是擋下訊息一律給可照做的下一步,`skip` 路徑不動當出口。推送前還有三道:`scripts/test_lumos.py` 與 `scripts/hooks/pre-push` 在簽章基準裡,要使用者核可才能簽;`cmd_code_loop` 定義行多一個參數會讓新增告警閘把既有複雜度告警算成新的,照既有先例登記豁免;`_codeloop_pass_verify` 一串條件會超過複雜度門檻,實作時拆段,拆不下去才登記豁免。
相容:消費專案共用同一份工具,合入後一起生效。迴圈還沒凍結的照訊息凍結。舊 panel 帳與無輪次迴圈凍不了,只能 `skip`。專案有審查帳就要帶編號:只用過規格閘、或審查在迴圈外做的專案,每次 `pass` 都會被擋,出口只有 `skip`,人工審過的也會記成跳過,這是 d1 的代價,不是一次性的;決策欄寫的「被擋一次」以這裡為準。消費專案的審查帳預設不進版控,換機器或開新工作樹就是沒有帳,落到不驗,是放行方向。
測試:`code-loop pass` 實際 19 處呼叫,只有 `t_codeloop_pass_survives_bookkeeping_commits` 的第二次在有審查帳的 repo,見做法第 8 步。`_codeloop_gov_log` 有測試直接帶六個位置參數,新參數要有預設值。
順序:手冊順序是提交、凍結、`pass`;凍結要求卷證已提交,判定檔是凍結後才產生,`pass` 讀工作目錄的判定檔,未提交也讀得到。
邊界:同分支兩個功能各一個迴圈時只綁一個編號,綁風險最高的那個;留痕綁的是 HEAD,範圍涵蓋整條分支,不收多值。把迴圈標成 light 就不用判定檔是已知缺口,由開頭第二條回頭條件追。
效能:實測讀整本審查帳(5.8 MB、5518 列)加算指紋約 0.08 秒,實作後重量一次寫進驗證紀錄。

## 回退

不要 `git revert` 功能提交,也不要把檔案整支換回舊版:功能提交含只追加的審查帳,後面又有帳本提交,revert 會在帳檔衝突;`scripts/lumos`、`scripts/test_lumos.py`、`skills/` 改動頻繁,整支換回會抹掉後來別人的提交。

1. 另開一個提交,對 `scripts/lumos`、`scripts/hooks/pre-push`、`scripts/test_lumos.py`、`.github/workflows/ci.yml`、`skills/` 底下改到的手冊,反向套用功能提交的差異:`git diff <功能提交>^ <功能提交> -- <這些路徑> | git apply -R`;功能提交若是經 PR 合併,範圍取合併提交對第一親代的差異。遇到後來的改動造成衝突就手解。兩本帳與判定檔不動。
2. 同一個提交更新圖譜,不然 pre-commit 會擋:做法第 7 步改過的筆記改回或補註,本計劃狀態改 `abandoned`、條款綁定的測試已不存在要改標、d1 記翻案、四條回頭條件加 `[closed:…]`。
3. 動到簽章基準的檔,要使用者核可重簽。回退提交本身走 `skip` 留痕並寫明理由。

還原後 `pass` 回到只寫留痕,閘類讀者忽略多的欄位。回退期間的放行事件 `nodes` 為空,`loop list` 靠備註認編號,備註沒寫迴圈名的會被報成開著,這是可接受的顯示差異。手冊學到的 `pass --loop` 在回退後會被 argparse 回 rc2。

只放寬不是改一處:拿掉「沒帶 `--loop`」要連帶加提前返回、改 S1 與測試、重簽、記 d1 翻案。RETIRE-IF 那條「只留 `--loop` 綁定」同樣照這個走。提交編號落地後補在這裡。
