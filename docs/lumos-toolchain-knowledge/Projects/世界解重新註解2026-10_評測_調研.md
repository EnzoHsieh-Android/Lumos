# 世界解重新註解2026-10_評測_調研

> 白話:這一類在問「Lumos 那些治理機制到底有沒有幫上忙,要怎麼量才不騙自己」。世界在 2025–2026 已收斂出一套慣例:同模型換工具鏈、每題多跑幾次、報區間與成本、先查題目本身有沒有壞、讀逐字稿;而且工具鏈(harness,包在模型外面那層)的改動對成功率通常只差幾個百分點,對成本卻能差好幾倍。對 Lumos 最要緊的兩件事:一是每週探針「有一題沒過就通知」的設計,在規矩完全沒變時也約七成的週會響,分不出真退步;二是探針的受測副本裡放著題庫判準與歷次結果,至少 4 場實際打開過歷次結果檔,量出來的通過率可能偏樂觀。兩件都能用純標準庫、零額外額度先修。

本篇是九類重新註解的第 5 類,總覽見 [[Projects/世界解重新註解2026-10_總覽_調研]]。材料:研究筆記(Opus 5.5,2026-10-11)、乾淨 agent 的現況核對答案(以下稱「核對答案」)、舊判斷對照 B 組,以及本篇撰寫時的少量查證。

## 這一類在問什麼、Lumos 現在怎麼做

本類問三件事:①機制有沒有讓 AI 照規矩做(過程);②照規矩後結果有沒有變好(療效);③花了多少(成本)。Lumos 現在的量法如下,只寫定位:

- [[Systems/autonomous-iteration-loop]]:每週排程跑四件觀測(情境探針、查詢考卷、審查回放、推播漏網),決定哪些要發 LINE 通知人。
- 情境探針:在凍結副本開 headless 的 Claude 或 Codex 會談,看工具呼叫序列有沒有照規矩敲 lumos;程式的家是 [[Systems/codex-harness]](本類沒有專屬節點)。
- [[Systems/ablation-lumos-first]]:兩臂對照(有/無某段紀律),每題多跑,預先寫死判準。
- [[Systems/retrieval-ranking]]:查詢考卷(搜尋與改檔推播兩種題),算 nDCG、P@k 等,固定門檻加棘輪。
- [[Systems/多詞評測]]:整串片語與拆詞的比較題庫,雙評審加人裁,並有題目字面掃描防污染。
- [[Projects/標註刷新_計劃]]:語料前進時只補判新進候選(TREC 式增量判定,TREC 是資訊檢索界的評測慣例),兩席同值即採用、不同才人裁。
- [[Systems/改檔前推播]] 與 [[Projects/推播miss量測_計劃]]:解析真實會談逐字稿,量「推了的筆記有沒有被讀、沒推卻被讀了(漏網)」,只出分布不設門檻。
- 審查回放(改制回測):用現在的判定程式重算凍結卷證,不重叫模型,抓判定邏輯漂移。
- [[Systems/canary-audit]]:植入瑕疵考審查員,2026-08-14 停用。
- [[Systems/judge-perturbation-stability]]:用擾動測評審穩定度,2026-06-20 否決。
- [[Systems/convergence-evidence-gate]]:收斂證據閘;其中的剩餘缺陷估計(Chao1,一種由重複捕獲數推估未見數量的公式)已降為參考。
- [[Systems/review-convergence-eval]]:比較兩組審查流程的修復、保留、新缺陷、輪數、成本;唯讀,2026-10-11 核對時查無實輪資料。
- [[Projects/審查評測集_計劃]]:以逃逸帳與駁回帳做成 21 題核心審查評測集。
- [[Projects/審查有沒有用記帳_計劃]] 與 `lumos loop escape-stats`:審查產量帳與逃逸率,逃逸率附 Wilson 區間(一種小樣本也可靠的比例信賴區間)。
- [[Systems/lumos事件帳]]:Claude Code 外掛把回合、工具呼叫、子代理寫成帳;Codex 端沒有。
- [[Systems/reversibility-governance-ledger]]:治理帳,記每道閘的擋、跳、放行。
- 回測類:[[Systems/drift-history]](沿 git 史量幽靈符號)、[[Systems/historical-test-quality]] 與 [[Systems/test-quality-evidence]](以歷史真實弱測試重播、故障紅還原綠)、[[Systems/verification-rot-eval]](已被取代)。
- 受控實驗:[[Projects/Lumos定位_程式碼為主脈絡為輔_計劃]] 的刻意埋錯筆記實驗(Haiku 有圖譜 12/25、只看程式碼 20/25)。
- 污染事故:[[Issues/評測題目寫進圖譜就毀掉那一題]] 與「圖譜筆記本身會洩漏標註答案」兩篇 Issue。

**W1 Anthropic〈Demystifying evals for AI agents〉**(2026-01-09,來源 1)
- 機制:task/trial/grader/transcript 分層;pass@k(k 次至少一次過)與 pass^k(k 次全過,0.75³≈42%)分開用;能力評測(起點低)與回歸評測(應近 100%)分軌;每次試驗乾淨環境(曾有模型讀前一次的 git 史占便宜);從 20–50 題真實失敗起步;多次都 0% 先懷疑題目壞了。
- 證據 C:官方實務經驗,不談區間。深度:讀官方文件。
- 關係:驗證(凍結副本、儀器例外不計分、缺席題)+可借鏡(紀律題用 pass^k、分軌)。

**W2 Miller〈Adding Error Bars to Evals〉**(arXiv 2411.00640,2024-11-01,來源 2)
- 機制:標準誤、群集標準誤、每題重抽 K 次讓題內變異降為 1/K、兩系統比較用逐題配對差;樣本數公式顯示偵測 3 點差約需 969 題。
- 證據 A:統計方法學。深度:讀全文。
- 關係:可借鏡(考卷「比舊法提升 ≥15%」與勝負判定只比點估計)。

**W3 Bowyer 等〈Don't Use the CLT in LLM Evals With Fewer Than a Few Hundred Datapoints〉+ bayes_evals**(ICML 2025,來源 3)
- 機制:小樣本用 Wilson 或 Beta 後驗;N=100 時常態近似的 95% 區間實際只蓋到 92.5%;同題比較用配對貝氏。附單檔實作。
- 證據 A:模擬加理論。深度:讀全文、讀碼。
- 關係:可借鏡。Lumos 已有 Wilson 區間函式,只用在逃逸率,週評沒沿用。

**W4 Terminal-Bench 2.0**(arXiv 2601.11868,2026-01-17,來源 4)

- 證據 A:方法與資料公開。深度:讀全文(前段)。
- 關係:驗證(凍結、移除未來)+可借鏡(空過試探)。

## 世界證據對 Lumos 做法的挑戰

1. **週評通知分不出退步**:依 W2、W3,8 場單次、每週換題的設計分不出 6/8 與 8/8。被挑戰的前提:「有題沒過就值得叫人」。驗證法:候選 1 的回放;若新規則下通知次數大降,而被省掉的通知事後都判為非退化,挑戰成立。
2. **泛用 context 效益小、成本高**:CTXbench、SkillsBench(W11、W12)顯示 LLM 生成或自寫的 context 平均無效、成本約 +20%。被挑戰的前提:由 AI 依紀律寫回的圖譜有淨效益。Lumos 自己的資料只有「錯筆記會害弱模型」與受控實驗戊組「H2 只一題有鑑別力」;週評量的是「有沒有查」,不是「查了有沒有幫助」。驗證法:以結果為錨的能力題組(延伸 1),同時報成本。
3. **探針量到的通過率可能偏樂觀,影響範圍大**:
   - 受測副本是整個工作樹的複本,裡面有題庫判準(含 paraphrase 1 題、absence 3 題、answers 5 題的答案判準)、19 份歷次結果檔,以及討論題目與失敗原因的圖譜筆記(例如評測設計與爬坡調研逐題寫了哪題為何失敗)。
   - 本篇查證:掃 19 份結果檔的 132 場工具呼叫,8 場碰過題庫目錄;其中至少 4 場直接打開歷次結果檔或週抽歷史(2026-08-22 兩場重跑、同日一場紀律題、2026-08-24 週抽的紀律題 d04)。有幾場是因為題目本身在問探針系統,屬題目設計問題。沒有逐場判斷這些讀取是否改變了過不過。
   - 影響範圍:每週探針通過率、09-02 消融的絕對通過率都可能偏高。消融的差值也可能被放大:有紀律的那臂被要求先敲 lumos search,而搜尋會把討論題目的筆記排上來,洩題暴露在兩臂間不對稱(本篇推論,未驗證)。
   - 另外兩個失真來源:探針沿用跑探針那台機器的使用者層 hooks、skills、外掛與 MCP,從分支工作樹跑時 skills 卻指向主 checkout,結果跟著機器狀態變(Q05-11);模型可能認出自己在考試(W9),而 Lumos 停用金絲雀時用過這個理由,同一問題沒套到探針。
   - 驗證法:候選 2 改完後,同一批題在「有洩題副本」與「乾淨副本」各跑一次比通過率;察覺被測用候選 3 的掃描器計數,並與候選 4 的真實會談符合率並排。
4. **規則與觸發會衰減、對措辭敏感**:Vercel 56% skill 沒觸發、IFScale 規則越多越掉(W13、W16)。被挑戰的前提:CLAUDE.md 散文紀律在長會談裡一直有效。除了消融量過的那一節,其他紀律沒有量測。驗證法:候選 4 分會談前後段算符合率。
5. **判者擾動的放棄理由可能過寬**:RAND JRH(W17)在離線、有標籤、獨立生成擾動的設定下做到了 Lumos 認為逃不出自證悖論的事。放棄的另一個前提「換家族做不到」2026-06-26 已被跨家族複核推翻。驗證法:候選 7 跑兩個月。
6. **自動審查可能拉長週期時間、自評不可靠**:Beko +42%(W20)、METR 感受與量測相反。被挑戰的前提:審查流程值得它的時間成本。讀側不印比率保護了帳本不被灌水,但也讓 ROI 缺定量。驗證法:候選 9 的週期時間分 tier,與逃逸率並排。
7. **原生工具正在吞掉量測層**:plugin eval、`/skill-doctor`、OTel 歸因(W14、W21)讓手抄成本基線與自建觸發評測變成重複投資。驗證法:候選 6、10 雙軌比對。

## 延伸方向

- 延伸 1 以結果為錨的常設能力題組:把受控實驗裡「答案不在程式碼裡」且有鑑別力的題,做成每月跑的能力評測,和回歸評測分軌。現況:正在進行(方向已定),程式碼為主定位計劃 2026-09-27 改向「成效指標改成結果」,常設題組沒排。
- 延伸 2 跨 runner 與模型的可攜性分數:同題庫在 Claude、Codex 等 harness 上量守規率。現況:部分有,探針已能用 Codex 跑(2026-09-04);跨 harness 分數沒在算。
- 延伸 3 匯出物件中心事件記錄(OCEL)給外部流程探勘,找實際工作流變體與返工迴圈。現況:2026-10-11 核對查無對應機制。
- 延伸 4 推播漏網當排序標籤,並找線上代理指標。現況:延後,推播漏網計劃寫明「結果不回灌排序」,有 10 筆以上判不出類別才立案。
- 延伸 5 序貫監控:跨週累積時用 e-process 控制誤報。現況:相鄰否決(審查迴圈收斂停機排除過 SPRT,理由是分布每輪變);週評在兩次改規則之間分布大致不變,理由只部分適用。
- 延伸 6 消費專案層的 git-only 長期趨勢(複製貼上、搬移、兩週 churn、變更失敗)。現況:調研提過、沒有裁定,2026-09-02 掃描提醒「先問誰會看這個數字」。
- 延伸 7 匯出 OTel 評測結果事件或 ATIF 軌跡,讓外部後端顯示。現況:2026-10-11 核對查無(Q05-04,未經第二次核對);OTel 只在計劃裡當命名參考。

## 筆記與程式或來源對不上的地方

1. **金絲雀審計那篇引 arXiv 2606.19749 沒寫適用範圍**。
   - 原句大意:摘要的 `KEY:` 行與正文說「植錯誤考審查系統實測最強單席僅 71.6%、六模型並集才 83.3%」,據此推「廣度只能靠多席×多鏡頭×跨家族買」。
   - 實際:核對答案打開原文,論文評的是審查「科學論文」的系統,不是程式碼或設計規格審查;71.6% 是在 24 篇前沿子集上算的;「configuration」是整套系統配一個模型,不是審查小組的一個席位;論文自己的結論是「基礎模型強度比 harness 設計重要」,模型聯集只是「有前景的方向」;六個模型剛好來自六家,沒單獨量「跨家族」,「多鏡頭」沒量。
   - 同一說法也抄進了設計迴圈判準重定位計劃、canary 注意力檢查失效計劃,以及 lumos-design-loop skill 的參考文件。
   - 建議:改句,補「論文審查領域、類比外推」與子集說明,把「只能」改成「論文支持多模型聯集能提高召回」;不需要立 Issue。
