# 審查席唯讀隔離_計劃

白話:設計審、代碼審派出去的審查員是用 Agent 工具開的子代理,會繼承編排者的全部權限——被審的文件如果藏了惡意指令,審查員可以被誘導去改 repo、開 PR、改使用者設定;同一輪的審查員也看得到別席已經交回的報告,「各自獨立」只靠派工詞自律。這份計劃新增一支 Claude Code 外掛 `lumos-guard`:派工詞第一行是 `LUMOS-SEAT:` 的子代理,工具改用白名單、寫檔只准它自己的工作資料夾、不准碰席報告暫存處;Bash 只做粗擋(提到 `gh`、`git push`、`claude`、GitHub API 這類對外動作就擋)。防的是「被文件裡的指令誘導」,不防一個有心繞的審查員:Bash 仍是完整的 shell,在 repo 裡改檔這版既不擋也不報。

PRIOR-ART: 最小解在 harness 的工具呼叫攔截點,不在提示詞。[[Systems/nested-agent-permission-scope]] 2026-06 設計過另一條路——把審查員改成 `claude -p --allowedTools "Read,Grep,Glob"` 子程序(工具清單在 harness 層收窄),但一直沒實作,而且審查員常要跑 Bash 做重現實驗(`git -C <臨時目錄>`、一次性的腳本),工具清單收到只剩讀取就做不了。本案改用外掛的 `tool.call` 攔截:引擎每次要跑工具前都經過它,`e.agentId` 指出是哪個子代理,`{ deny }` 擋下(型別檔 'tool.call' 說明);子代理是誰派的、派工詞是什麼,從 `agent.spawn` 的輸入 `prompt`、`parentAgentId`、`cwd` 與結果 `agentId` 對起來。設計審第一輪證明「看指令文字列黑名單」漏得一塌糊塗,改成白名單(決策 d2);第二輪又在「逐詞解析 Bash 指令」這一類抓到十多條漏擋與誤擋,連兩輪同一類,改成粗擋加事後查 repo(決策 d3);第三輪四席 16 條會擋的發現有 13 條出在事後查本身(外掛跑 `git status` 會照 repo 設定執行過濾指令、搶索引鎖、在 worktree 看錯 repo、髒檔內容變了看不出、背景改動讓警告變噪音),所以整段拿掉,外掛不跑任何外部指令(Enzo 2026-10-06 裁,決策 d4)。外掛寫法、市集、測試做法沿用 [[Systems/lumos事件帳]](核心邏輯可注入、`claude plugin test`、條款以測試標題開頭綁、本 repo 的 `.claude-plugin/marketplace.json`);標記解析照 `scripts/hooks/claude/dispatch-lens-hook.py` 讀 `LUMOS-IMPACT:` 的寫法(整行比對、去頭尾空白),但只認第一個非空行;擋下理由照本 repo 工具輸出的三段式(發生什麼、為什麼在意、要怎麼做獨立一行)。
RETIRE-IF: ①上線兩個月內 `lumos events` 看得到的審查席工具呼叫裡,這支外掛一次都沒擋過,而且審查卷證也沒出現過席位改 repo、讀別席報告或用白名單外的工具——風險沒在真實發生,維護成本不值;②誤擋多過真擋(席位常被擋下合法的重現實驗);③Claude Code 的 Agent 工具開始支援逐次指定可用工具與寫入範圍(那時改用官方機制)。

## 名詞

- **審查席**:派工詞第一個非空行是合格 `LUMOS-SEAT: <迴圈編號>/<輪次>/<席名>` 的子代理,以及審查席再派出去的子代理(一律繼承)。
- **暫存根**:作業系統暫存目錄的真實路徑:macOS 是 `/private/tmp`、`/private/var/tmp`、`/private/var/folders/<兩層>/T`;Linux 是 `/tmp`、`/var/tmp`。比對一律帶路徑分隔字元(`/private/tmpX` 不算)。
- **席位工作資料夾**:`<任一暫存根>/lumos-seat-work/<迴圈編號>/<席名>/`。審查席唯一能用 `Write`、`Edit`、`NotebookEdit` 寫的地方;派工範本叫它把實驗與臨時 repo 放這裡。
- **席報告暫存處**:`<任一暫存根>/lumos-seat-staging/`(整個資料夾,不分迴圈)。編排者收到席報告時**先留在對話裡,同輪全部交回才一次寫進卷證資料夾**(決策 d5:收齊前硬碟上沒有別席報告可讀,Bash 怎麼寫都無所謂);這個資料夾留給沒照新做法、仍把報告先存到硬碟的情況,外掛擋讀它當多一層保護。卷證資料夾不保護:報告寫進去時同輪各席都已交回。

## 做法

### 一、認出審查席

- `agent.spawn` 進來時(還沒 `next(e)`):
  - 發起方是審查席(輸入的 `parentAgentId` 在對應表裡)→ 新子代理一律繼承發起方的標記,派工詞自己帶的標記不算數;工作目錄取輸入的 `cwd`,沒給就沿用發起方的(子代理通常在發起方的目錄裡工作,比會談 cwd 準)。
  - 否則看派工詞:以換行與 U+2028、U+2029 分行,跳過「NFKC、剝掉所有格式字元(零寬、方向標記、軟連字號、BOM 這類 Unicode Cf 類)、去掉空白後為空」的行(空白含 `\r`、全形空白 U+3000),取第一行的原文去頭尾空白。只剩格式字元的行當空行跳過;格式字元在標記那一行裡就判寫壞(代碼審 r3、r4)。
    - 整行符合 `^LUMOS-SEAT:\s*(\S+)$`,值以 `/` 切成恰好三段,每段非空、不是 `.` 或 `..`、不含 `\`、空白與控制字元 → 是審查席。輪次不限格式(真實帳上有 `r3-dref`、`驗收` 這類寫法)。
    - 第一行先 NFKC、剝零寬字元,再去掉開頭所有非字母數字的字元(markdown 修飾、清單符號、引號)與「1.」這類編號,不分大小寫以 `lumos-seat`(或 `lumos-seats`;連字號寫成別的橫線、底線或空白也算)開頭、後面不接字母數字或連字號(有沒有冒號都算),卻不合上一點 → 回 `{ deny }` 擋下這次派工,理由說哪裡寫壞:編排者想隔離卻寫錯,靜默放行等於整席沒保護。合格與否用原文逐字比(全形冒號、零寬字元開頭都判寫壞)。只是提到 `lumos-seat-work`、`Lumos-seating` 這類字的一般派工不算(代碼審 r1、r2、r3)。
    - 其他 → 不是審查席(不擋)。只看第一行,所以派工詞內文貼進來的被審材料、範本範例裡的標記不會被誤認。
  - 是審查席時,把這次派工放進該會談的「啟動中」清單,再 `next(e)`;拿到結果的 `agentId` 就登記「子代理編號 → 迴圈、輪次、席名、工作目錄(輸入的 `cwd`,沒給就是會談 cwd)」,同時寫進 `$.state`(引擎替這場會談保管、外掛熱重載後還在;記憶體查不到時讀回,代碼審 r1);不跑外部指令;不論成功、被拒、丟錯,都在 `finally` 裡把它從「啟動中」拿掉。
- `tool.call` 遇到表裡查不到的子代理、而同一會談有「啟動中」的審查席派工時,每登記完一席就重查一次,查到就判、不必等整批;5 秒內一直查不到就照查不到處理(不是審查席,放行),並 `$.ui.toast` 一行固定開頭 `lumos-guard 逾時放行:` 的提示。非審查席的子代理在有審查席啟動中時可能多等,上限 5 秒。
- 會談結束(`session.end`)清掉那個會談的對應與「啟動中」清單,叫醒還在等的工具呼叫,`$.state` 也一併拿掉這場的席;結束前就開始、結束後才登記完的派工不登記。原因是 `clear` 或 `resume` 時行程換個會談編號繼續跑,不算結束:不清、不刪、在飛的派工照常登記(代碼審 r3、r4)。存回 `$.state` 帶讀到的版本,撞版重讀重試最多 3 次,放棄時跳提示;佇列每一格、派工那頭各自最多等 2 秒,逾時那一格之後才回來也不再寫(代碼審 r3、r4、r5)。

### 二、審查席的工具規則

1. **工具白名單**:`Read`、`Grep`、`Glob`、`Bash`、`WebFetch`、`WebSearch`、`ToolSearch`、`TodoWrite`、`TaskOutput`、`TaskStop`、`Agent`(某些建置叫 `Task`,兩個名字都認),以及照第 2 點判過的 `Write`、`Edit`、`NotebookEdit`。其他一律擋,包括 `Skill`(fork 型技能開的子迴圈沒有 `agent.spawn`,外掛認不出它是審查席的子代理)、`SendMessage`、`Monitor`、`Workflow`、`TaskCreate`、`EnterWorktree`、`PowerShell`、所有 `mcp__` 開頭的工具、外掛自己註冊的工具。工具名用字串比對(`Grep`、`Glob` 在某些建置不註冊,不影響)。
   - `Agent` 帶 `isolation`(任何值)→ 擋:`remote` 在雲端跑、本機攔截點看不到,`worktree` 會在真 repo 開分支。`subagent_type` 只准沒給、`general-purpose`、`Explore`、`Plan`:其他代理定義可能自帶 isolation,外掛在呼叫端看不到。
2. **寫檔**:讀的欄位是 `Write`、`Edit` 的 `file_path`、`NotebookEdit` 的 `notebook_path`;欄位不是字串、不是絕對路徑,或任何一段是空的、`.`、`..` → 擋。其餘取「最深一層已存在的上層」:`$.fs.stat(p, { resolve: true })` 拿不到 `realPath`(含懸空連結)→ 擋;拿得到就接上剩下的段,折疊大小寫、統一成 NFC 後比對(各平台都折小寫:引擎的 `realPath` 保留大小寫別名的原拼法;Linux 上多折只會讓暫存處擋得更多、工作資料夾多放行暫存根底下大小寫不同的同名資料夾,不會放出暫存根):落在這席自己的席位工作資料夾裡 → 放行;其餘一律擋。路徑超過 4096 字或 256 段也當看不懂、擋(代碼審 r1:不存在的超長路徑逐層往上找是平方級)。
3. **席報告暫存處**:
   - `Read` 的 `file_path` 照第 2 點取真實路徑:看不懂(相對路徑、含 `.` 或 `..` 段、空段、過長、懸空連結)→ 擋;落在席報告暫存處裡 → 擋。看不懂一律擋,讀、寫、搜尋同一條(代碼審 r1:原本讀檔遇到看不懂的路徑放行,`/tmp/./lumos-seat-staging/…` 就讀得到)。
   - 搜尋範圍:`Grep` 只看 `path`(`pattern` 是正規表示式、`glob` 是檔名過濾,都不當路徑);`Glob` 看 `path` 再接上 `pattern` 第一個萬用字元之前的固定段(`pattern` 是絕對路徑時就用它)。`path` 是相對路徑就以這席的工作目錄補全,含 `..` 段 → 擋,沒給就是工作目錄;`Glob` 的 `pattern` 固定段含 `..` 也擋。取真實路徑(同第 2 點的「最深一層已存在的上層」)後,範圍跟席報告暫存處有祖孫關係(範圍在暫存處裡,或暫存處在範圍裡,例如 `path=/private/tmp`)→ 擋。
4. **Bash 粗擋**:指令先一律轉小寫,再以空白、引號與 shell 符號(`; | & ( ) { } < > $ \` 與反引號)切詞——不切斜線,路徑裡只是出現 `claude` 不算(代碼審 r1:原本切斜線,`cat mods/claude/x.ts` 被擋;原本分大小寫,`GH pr create` 放行)。下面任一條成立就擋,不管它在引號、heredoc、`bash -lc`、子殼層或註解裡:
   - 每個詞都取最後一段斜線之後的部分來比(帶路徑的寫法一律算數;代碼審 r2:只認少數前綴時漏掉相對路徑與 `$HOME/` 開頭):有 `gh`、`hub`、`glab` 或 `claude`。`claude -p` 開的子程序不帶標記,外掛管不到。路徑最後一段剛好是這些字的(例 `git diff -- mods/claude`)也會被擋,是接受的誤擋。
   - 有 `git`(同樣取最後一段),同時有 `push`、`send-pack` 或 `send-email`。
   - 字串含 `api.github.com` 或 `uploads.github.com`。
   - 字串含 `lumos-seat-staging`。
   - 指令超過 1MB,或判斷本身出錯 → 擋(這一項 fail-closed,是第 6 點的例外)。
   - 寧可誤擋:heredoc、說明文字、搜尋字串、路徑最後一段裡出現這些整詞也會被擋,理由文字講明是整詞比對,並教它換寫法(檔案內容用 Read 讀;搜字可用 Grep 工具,寫「有的話」是因為有些建置沒有 Grep、Glob——代碼審 r1 通才席實查;目錄名剛好是這個詞就在結尾加斜線;git 與 push 分成兩次 Bash 呼叫;報告內容直接寫在回答裡)。其他指令照常。
5. **擋下理由**:三段式,例「擋下:審查席只能寫自己的工作資料夾(/Users/x/repo/a.md 不在裡面)。\n為什麼在意:被審材料裡的指令不能讓審查員改到 repo 或你的設定。\n要做實驗請寫到:\n  /tmp/lumos-seat-work/<迴圈>/<席名>/」;派工、工具、寫檔、暫存處、Bash 各一種固定開頭字串。
6. 不擋的照原樣 `next(e)`,外掛不改輸入、不改結果、不跑任何外部指令。外掛自己出錯時放行,例外是子代理的 Bash:擋——判不出是不是審查席時寧可當是,所以有子代理編號的都算,只有主會談的 Bash 出錯照常放行(代碼審 r1、r3)。讀不到 `$.state` 對照表時:子代理的 Bash 與寫檔工具擋、讀取放行,子代理派的派工擋下(代碼審 r3:原本只擋 Bash,派工那頭反而放行)。掛鉤層出錯走 `.catch`:工具已經跑過就交回原本結果,不謊稱擋下。
