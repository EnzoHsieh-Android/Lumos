# 簡報審查抓到的機制缺口_計劃

> 白話:面試簡報請 Codex 以面試官角度逐頁審,回頭查 Lumos 實際怎麼處理時查出四件事。這份計劃做其中兩件:Service 裡合理的背景收集被 Flow 收集規則誤擋、README 的實驗句講錯比較組。另外兩件(人工指定高風險路徑、行內忽略註解要留紀錄)在設計審連兩輪被打穿,改開 [[Projects/人工指定高風險路徑_計劃]] 與 [[Projects/行內忽略註解要留紀錄_計劃]] 重新設計。

PRIOR-ART: 規則例外照官方對 repeatOnLifecycle 的適用範圍收窄:官方說它是為了「只在 UI 顯示在畫面上時處理」,Service 不是畫面;排除寫法照同包 kt-register-without-unregister 排除 Application 的既有形狀(`not: inside: class_declaration` 加 `has: delegation_specifier` 與 regex)。README 改寫照兩份原始實驗紀錄,不照摘要。
RETIRE-IF: Android Lint 或 compose-rules 出了同一種只管畫面收集的檢查 → 自寫規則撤掉、型錄改指現成檢查。

## 範圍

1. **規則例外**:`kt-lifecycle-collect-without-repeat`(型錄 STATE-5)兩個分支(`lifecycleScope.launch { … collect … }`、`.launchIn(lifecycleScope)`)都不再報包在 Service 類別裡的收集。認法:任何一層外圍類別,它自己的直接繼承清單裡有一項是建構子呼叫形式的 `LifecycleService(`、`MediaSessionService(`、`MediaLibraryService(`(可帶 `androidx.lifecycle.` 或 `androidx.media3.session.` 前綴);只看那個類別自己的繼承清單,不往它的類別本體裡找(所以 Activity 裡有內部 Service 類別時,Activity 自己的收集照報);寫成 `MediaSessionService.Listener` 這種巢狀介面不算。外圍是 Service 時一律不報,連在 Service 裡用 ProcessLifecycleOwner 收也不報:看寫法只認得外圍類別,Service 裡這樣寫的意圖看不出來,交給審查。型錄 STATE-5 那列在名稱欄補一句「只管畫面;Service 本來就在背景收,不在範圍內」,不動實測與接電欄。
2. **README 實驗句**:中英兩版照原始紀錄寫:Haiku 4.5 只看程式碼答對 20 場、讀到故意寫錯的筆記只剩 12 場;Opus 每組都 25 場全對,實驗對它在天花板;筆記正確時另做過一批 80 場,只有一題看得出幫助(只看程式碼 0/5、有筆記的三組合計 8/15),其餘三題大多接近滿分(只測 Haiku)。

## 不做

- ProcessLifecycleOwner 在非 Service 類別裡不豁免:官方說它可以看作所有 Activity 的合成生命週期,用來在 App 回前景或進背景時反應;它的 STARTED 就是 App 有畫面在前景,正是這條規則管的情況。(2026-11-09 改寫理由:原本寫「沒說它不是畫面,依據不足」,面試簡報看圖審查指出那只是沒找到放行依據,不是阻擋依據。)
- 自寫基底類別間接繼承 Service 的情況認不出,照舊報,走放行。
- 人工指定高風險路徑、行內忽略註解要留紀錄:移到另外兩份計劃。

## 實務隱患

- Service 裡的內部類別(連內部 Fragment)也會被豁免;這是沿用同包既有排除寫法的語意,實務上罕見。
- 已排除:金流:不碰付款或點數
- 已排除:對外送出:不送任何資料到外部
- 已排除:不可逆:只改一條規則、樣本與文件,整段還原就回到原狀
- 已排除:守衛面:這次只把一條規則的範圍收窄,不改推送閘或任何判定程式
