# 選擇點存活回指條款_計劃

## 白話

選擇點變異(`lumos choice-kill`)把改動的每一行換成一個壞法,跑這次碰到的進行中計劃條款綁的測試。殺掉就記哪條條款守住它;存活就擋推送、交人處置。現在存活那筆帳上**沒有任何條款資訊**,人只看到「這行存活」,不知道該往哪條條款底下補;而且每個壞法都跑全部守的測試,沒有測試經過的行也照跑,慢;壞法編不過時記成「跑不出結果」,讓人去查一個不存在的問題。

這份是 [[Projects/選擇點對應需求路線_計劃]] 的第 1 步。這個功能要抓的是「AI 寫程式時自己做了決定、人也沒想到」的細邊界:需求通常只講目的與粗略的系統邊界,條款是一大塊行為,語法裡更細的規則(算不算在內、空的時候回什麼)可能改變條款的結論。存活的修法分四層,每層不同:

1. **規格沒寫**:計劃的條款與正文都排除不了改壞後的行為,兩種都說得通,是 AI 自己選的。要問人;輸出直接寫成業務問題:「當…時,要 A 還是 B,現在程式是哪個」。
2. **正文寫了、條款沒收**:計劃正文有一句排除了改壞後的行為,但沒有任何驗收條款或預期值表列收它。照正文補子條款與一支邊界測試,不用問人。
3. **條款寫了、測試沒驗到**:某條驗收條款的字面就排除了改壞後的行為,只是綁的測試沒驗到。在那條條款底下補測試。
4. **等價**:改壞前後行為在規格範圍內相同。判讀只標建議,人確認後放行。(編譯不過的不是壞法,不進這四層。)

做法:choice-kill 把一個「準備物件」交給 `cmd_guard_kill`(形狀照合併快篩交 `_KillMerge` 的做法),guard-kill 建好隔離工作樹、跑配方之前呼叫它,在同一棵樹裡做三件事;之後才進語意判讀:

- **合批編譯檢查**:先編一次沒套壞法的原樹當對照(原樹就紅表示環境壞了,整段跳過、一個壞法都不判無效);再把這次所有壞法同時套上、編譯一次,依錯誤的檔與行找出嫌疑壞法,每個嫌疑單獨再編一次確認才算無效;無效的換同一行的下一個候選再合批編,最多 3 批,時間不超過總時限四分之一。編不過的不是壞法,不會變成「跑不出結果」;候選用完的行比照乾節點不擋。這是 mutant schemata「全部壞法一次編譯」的輕量做法。
- **逐測試覆蓋(PIT 的做法)**:在原版程式上把每支守的測試各單獨跑一次、同時掛 JaCoCo(這一輪也就是合併快篩本來就要「先量齊」的單支基準);再一次 Gradle 呼叫、在 Gradle 程序裡用 JaCoCo 的分析 API 逐份分析,只輸出壞法那幾行被哪些測試經過。有了它:①每條條款經過哪幾行 = 那條條款綁的測試的經過聯集;②每個壞法只跑經過那一行的測試;③沒有任何守的測試經過的行,壞法不用跑就知道殺不掉(壞法已經編譯檢查過,不會把無效壞法誤記成存活)。
- **覆蓋可信檢查**:每支 Robolectric 測試跑完,當場讀它的覆蓋資料數「有執行紀錄的專案類別」;設定沒生效時這個數是 0(實測),那支測試的覆蓋就不算數、前 5 支都是 0 就當場停掉覆蓋,不會把壞掉的覆蓋當成「沒有條款經過」。
- **語意判讀**:拿條款原文與計劃正文對照「改壞前後兩種行為」,判條款字面能不能排除改壞後的行為、不能的話正文能不能。照盲判的做法:工具產生判讀材料,編排者派一個全新的代理只看材料判,拿不準一律歸第 1 層。每筆判讀記下它依據的東西;依據變了,判讀標「計劃改過、待複核」但照樣顯示,一批處置完再一次重判,不會處置一條就讓其餘全部消失。

覆蓋只答得了「有沒有條款經過這行」:第 1 層和第 3 層都是「有經過」,分不開;第 2 層要讀計劃正文才看得到。所以覆蓋是篩子、線索與加速,不是分類本身。

例(實驗專案批 3,2026-11-24 存活重判):選擇點存活 62 條。舊做法只按「有沒有條款經過這行」分三類,得「AI 自己做的決定」4 條;改成「條款字面能不能排除改壞後的行為」由全新代理逐條重判(不看舊結論),得第 1 層 7 條(多出的 3 條使用者已裁)、規格已決定 38 條(其中 22 條只寫在計劃正文、沒有任何驗收條款收,是第 2 層)、等價 17 條(其中 4 條其實是編譯不過)。較早的最小實驗(2026-11-23,長跑當時 20 個存活行)另看到:有一行只有沒綁條款的測試跑到,用全部測試的覆蓋會誤判成「跑到」,所以條款經過與否一定要用條款綁的那幾支測試算。

速度(2026-11-26 實驗專案實測,見〈依據來源〉):同一支 Robolectric 測試不掛覆蓋約 4.7 秒、掛覆蓋約 6.2 秒;12 支測試的覆蓋資料一次程序內分析 0.66 秒(166 個類別),整次 Gradle 呼叫 5.4 秒。上次那批 169 支測試的單支基準約 773 秒,掛覆蓋估多約 4 分鐘、分析約 15 秒;合批編譯檢查每批一次編譯。換來的是:沒有測試經過的壞法不跑、其餘只跑經過的測試、編不過的壞法不進測試階段。

使用者原話(2026-11-24):「回指驗收測試,是顆粒比較粗的規格,通常語法樹計較的是更細的邊界,有可能改變原本規格的結論,這就是想用來抓出AI擅自決定,或是原本規格不清的」;2026-11-26:「我不想對整個功能願景做偏離的妥協」「不要懼怕改動,改動大沒有關係,我要的是完美符合願景,能實際幫上code review的功能」「但是速度這件事,也是要保證好,不要又變回十幾個小時」;目的那段原話見路線總圖〈白話〉。

這一步做:準備物件(合批編譯檢查、逐測試覆蓋、可信檢查)、依覆蓋選測試、存活的條款經過分類、判讀材料與判讀記錄、輸出與推送閘提示依層換句。**不改擋的判定規則與回報上限**(「沒有可用壞法」比照乾節點不擋;依覆蓋判存活的行照舊擋),**不機械判等價**(判讀說等價只標建議,照舊要人放行),**不實跑分得出兩版的輸入**(第 3 步)。

- 母計劃〈不做〉「不讓 AI 自動判等價」:照舊。判讀代理判第 4 層只記「建議等價」,不自動放行、不改擋不擋。
- 情境題盲判那份〈不做〉「不在推送前閘或 CI 呼叫模型」:照舊,判讀由編排者派代理跑,lumos 只產材料、驗格式、記帳。
- [[Systems/guard-kill]] 否決「另抽一支共用的殺傷力函式」:不抽;`cmd_guard_kill` 只多收一個選用的準備物件(形狀同 `_KillMerge`),沒交時行為不變,殺傷力判定照舊。

## 用詞

- **守的測試**:choice-kill 已收集的守衛測試清單(只收進行中計劃、profile 是 kotlin-junit 的平台、已扣掉 `[manual:]` 與 `[keeps]` 的條款),每支帶 `keys`:它屬於哪幾條條款,值是 `(計劃路徑, 條款號)`。
- **準備物件**:choice-kill 交給 `cmd_guard_kill` 的選用物件 `_KillPrep`(每個平台組一份,交法同 `_KillMerge`)。guard-kill 建好隔離工作樹、跑任何配方之前,對每個平台組呼叫它一次——這個呼叫點跟合併快篩開不開、能不能合併無關(`--no-merge`、`LUMOS_SKIP_CHOICE_MERGE=1`、合併道不足 2 支都照樣呼叫);它用 guard-kill 那棵樹、guard-kill 的 `_kill_run`、基準快取與 `mstate`。
- **量齊基準**:把合併快篩現有的 `_kill_merge_singles`(每支量完用實測平均重估剩下支數 × 平均 × 1.5、不夠就收手、第一支冷編譯不拿來估、被時限截斷的那支不寫進基準)抽成共用的 `_kill_measure_singles(c, wrap=None)`;合併快篩照舊用它,準備物件也用它,`wrap` 給逐支指令加覆蓋用的 init script。不另寫量基準的迴圈。
- **合批編譯檢查**:準備物件先編一次沒套壞法的原樹(對照組);原樹紅、逾時或被中斷,這次整段跳過、記 run 事件 `compile: "env"`、不記任何無效。原樹綠才把這一批壞法同時套上(泛化 `_kill_merge_apply`/`_kill_merge_restore` 成多檔版,沿用 `_kill_wait_new_second` 與 `mstate` 錯開,包在 try/finally 裡、還原後比對檔內容等於原版,對不上就整個準備物件中止、照現在跑)跑一次編譯任務,依錯誤的檔與行列出「嫌疑壞法」(壞法改的行範圍含那一行);每個嫌疑壞法再單獨套上編一次確認,單獨也紅才算無效;錯誤對不回任何壞法、輸出被截斷(`_kill_cap` 砍過中段)、或單獨編也綠,都不記無效。換了候選的行再一批,最多 3 批。
- **編譯預算**:合批編譯檢查(含對照組、確認、換候選)用掉的時間不超過 `--max-seconds` 的四分之一;超過就停在批與批之間,還沒確認的壞法照現在交給測試階段(編不過時照現在記 `no_result`),run 事件 `compile: "budget"`。
- **無效壞法**:合批編譯檢查確認編不過的壞法,身分 `(檔, 行指紋, new_sha)`;記一筆 `invalid` 事件(帶這次 run 的 `at_sha` 與那支檔的 blob)。
- **跳過集合(skip)**:某一行在帳上所有 `invalid` 事件裡、`blob` 等於那支檔現在 blob 的 `new_sha`;累積,不只看最近一次 run。choice-points、推送前掃描、`situation-rule --point`、判讀材料與準備物件都用同一個定義,所以挑到同一個候選。檔內容變了(blob 不同)就重新從第一個候選驗;檔沒變但別支檔改了(`at_sha` 跟 invalid 記的不同)時,準備物件把那些舊的無效候選放進這次合批編譯當探針(不跑測試),能編了就記一筆 `invalid` 的補償(`kind: "invalid"`、`cleared: true`),從跳過集合拿掉,下一次挑回它。
- **沒有可用壞法**:同一行全部候選都在跳過集合裡;挑壞法時那一行的狀態是 `exhausted`(跟乾節點 `arid` 同一層級的行狀態,不是處置判定),不擋、不跑;檔內容變了就重驗。
- **覆蓋基準**:準備物件用 `_kill_measure_singles` 加覆蓋 init script(開 `enableUnitTestCoverage`、jacoco 外掛套上後設 `includeNoLocationClasses = true` 與排除 `jdk.internal.*`;init script 寫進 `wt.scratch`,同 `_choice_merge_init_write`)把每支守的測試各跑一次;每支開跑前刪掉 AGP 固定位置的覆蓋資料檔,跑完沒有新檔就記「覆蓋資料沒產出」,有就複製到續跑快取。模組與變體從那支測試的指令(`run_cmd` 代換後的 `:<模組>:test<變體>UnitTest`)推出。
- **專案類別有紀錄數**:lumos 自己用 Python 讀 JaCoCo 覆蓋資料檔(JaCoCo 公開的 exec 二進位格式:區塊型別、類別編號、類別名、探針陣列),數「類別名所在套件是平台主程式的 package 宣告(平台根底下 .kt、.java 檔,跳過共用的跳過清單加 .gradle,以及 src 底下 test、androidTest 開頭或 Test 結尾的測試資料夾(含變體 testDebug、多平台 jvmTest;Android 官方〈Advanced test setup〉);符號連結與非一般檔不開;沒有宣告就是預設套件)、而且有任一探針為真」的類別數(代碼審 r1 改:原本照資料夾猜套件,預設套件與資料夾跟 package 不符時對不上;第一段放行後 2026-11-26 實測再改:原本只看改到的檔的套件,Robolectric 測試只碰別的套件時數到 0、前 5 支就誤斷路,覆蓋在實務上等於沒作用);每支跑完當場算。
- **覆蓋可信**:某支測試的專案類別有紀錄數大於 0;或這支測試不是 Robolectric 測試(看那支測試的覆蓋資料:Robolectric 建 Android 環境的類別(`AndroidTestEnvironment`,4.5 起還有 `AndroidSandbox`、4.4 以前 `SdkEnvironment`)有執行紀錄才算 Robolectric 測試——第一段放行後 2026-11-26 實測:專案用 Robolectric 時每支測試的覆蓋資料都有 `org/robolectric/` 的 runner 類別(334 份全有),只有 284 份真的建了 Android 環境,原本「有任一 `org/robolectric/` 類別就算」會把只讀原始碼的架構測試的 0 當成設定沒生效;不看原始碼,`@RunWith(AndroidJUnit4::class)` 與繼承帶 runner 的基底類別都沒有 runner 字樣——代碼審 r1 改)——`includeNoLocationClasses` 只影響 Robolectric 載入的類別,一般 JUnit 測試的 0 就是真的沒碰專案類別。不可信的那支測試對所有行都算「不明」。
- **經過**:用 JaCoCo 分析 API 讀某支測試的覆蓋資料,壞法改的行範圍裡至少一行的指令覆蓋計數大於 0。某條條款經過 = 那條條款綁的守的測試裡至少一支經過。
- **覆蓋分類**:每個壞法行一個:`clause`(列出經過的條款)、`none`(每支守的測試都可信而且都沒經過)、`unknown`(有任一支不明,或這一行在覆蓋例外裡,附原因)。
- **覆蓋例外**:壞法行在 `inline fun` 本體裡、在 `const val`、在頂層或 companion 的屬性初始值裡,或分析時那幾行沒有任何指令紀錄,一律記 `unknown`、跑全部守的測試。
- **依覆蓋選測試**:`clause` 的行只跑經過的守的測試;`none` 的行不跑、直接記存活;`unknown` 的行跑全部守的測試。
- **覆蓋指紋 `cov_sha`**:`(這次的 tests_sha, 壞法所在檔 blob, new_sha, 覆蓋 init script 版本)` 的雜湊;全部是讀端不用跑覆蓋就算得出的值。
- **層**:存活的最終分類,1 規格沒寫、2 正文寫了條款沒收、3 條款寫了測試沒驗到、4 建議等價(定義見〈白話〉)。都是判讀代理給的。
- **計劃正文**:碰到的進行中計劃裡,frontmatter、〈驗收條款〉、〈預期值表〉、〈審計修正紀錄〉以外的段落;段名是從二級標題到最近標題的路徑(`〈範圍〉/〈1. 覆蓋〉`),同名再加 `#2`;第一個標題前的文字段名 `〈前言〉`。
- **判讀材料**:每個存活一段,含選擇點位置、包住那一行的宣告(取法同 `_kt_sit_material`,取不到時改附前後各 20 行)、壞法的改動(原文 → 改壞後)、覆蓋分類與經過的條款原文;每份材料對它涉及的每份計劃附一次全部條款、預期值表與分段正文;作答格式;不含任何已記的層、處置提示或放行理由。
- **判讀依據**:一筆判讀寫下的 `basis`,每項 `{plan, where, quote}`:`where` 是條款號(`S3`)或段名,`quote` 是從那條條款或那一段逐字引的句子。
- **判讀狀態**:`有效`(依據都沒變)、`待複核`(壞法身分沒變、依據有變)、`作廢`(壞法身分變了或被撤回)。

## 範圍

1. **設定與旗標**:
   - 平台設定多兩個選填鍵,穿過 `load_platforms` 帶進平台資料(舊單平台的 `test` 那節同樣讀;型別不對照既有欄位丟 `ValueError`):`coverage`(布林,`true` 才做逐測試覆蓋)、`compile_check`(布林,預設:Android 平台 `true`、其他 `false`;`false` 關掉合批編譯檢查)。合批編譯的指令從那支測試的 `:<模組>:test<變體>UnitTest` 推成 `:<模組>:compile<變體>UnitTestKotlin`(壞法跨模組就每個模組各一次),推不出就不做。
   - `choice-kill` 多三個旗標:`--no-cov`(這次不做覆蓋,run 事件 `cov: "off"`)、`--no-compile-check`(這次不做合批編譯檢查,`compile: "off"`)、`--cov-audit N`(抽查行數,預設 2,0 關掉)。說明表與 `commands/INDEX.md` 一併登記。
2. **準備物件流程**(每個平台組,guard-kill 建樹後、跑配方前):
   - ① 合批編譯檢查(見〈用詞〉,受編譯預算管)。
   - ② 開了 `coverage` 時跑覆蓋基準(用 `_kill_measure_singles`,時間政策與收手規則照它;收手時沒量到的測試覆蓋算不明、基準照現在逐支流程補量)。掛覆蓋紅的那支不掛再跑一次,綠就用不掛那次當基準、覆蓋算不明;紅掉的測試不算進斷路器的支數。
   - ③ 斷路器(任一條就停止掛覆蓋、其餘測試照現在量基準,run `cov: "tripped"`、全部不明):前 5 支 Robolectric 測試(不足 5 支就全部)的專案類別有紀錄數都是 0;連續 3 支掛覆蓋紅、不掛綠;一支掛覆蓋跑滿單支上限而不掛綠(不掛也逾時是測試本身慢,不斷路);量完全部、不分 Robolectric 沒有一支記到專案類別(JaCoCo 插不了樁,例:agent 版本不支援這個 JDK 的類別檔——第一段放行後網路調研補)。Robolectric 專案類別 0 的覆蓋資料不進續跑快取;分析輸出 hits、nolines、noclasses 三個鍵都要在、型別對才算數。
   - ④ 量齊後一次 Gradle 呼叫在 Gradle 程序裡用 JaCoCo 分析 API 讀全部覆蓋資料檔,只分析這次壞法所在檔的類別(init script 從每個模組收類別資料夾,先挑壞法所在檔的套件資料夾,再只留 JaCoCo 記的原始檔名等於那支檔的),輸出 `{測試序號: [經過的壞法編號]}` 的 JSON;這次呼叫的逾時是 `max(60, 測試支數 × 0.5)` 秒,剩下的時間不夠就不做,全部算不明。
   - ⑤ 抽查:從 `none` 的行用 `run_id` 當種子抽 N 行(不足 N 就全部)改當 `unknown` 跑全部測試;另從 `clause` 的行抽 1 行跑全部測試。抽查在記任何 `via: "cov"` 事件之前決定。
   - ⑥ 回傳給 guard-kill:換掉的配方(新壞法;choice-kill 這邊的配方編號含 `new`,不跟舊的撞)與每個配方的測試子集;同時呼叫 choice-kill 交進來的回呼,讓 `_ChoiceKillRun` 用同一份資料更新 `plan_of`(壞法身分、`order` 改成子集)與 `rid_map`——判定照子集判,不會因為沒跑的測試沒有列而判成缺結果;候選用完的行從待跑清單拿掉、run 事件計進 `exhausted_n`,不佔 `ran`。
   - 中斷:準備物件跑在 choice-kill 既有的訊號範圍裡,合批編譯與分析這兩種 Gradle 呼叫帶合併快篩那種當場收的標記(收的方式同 `_KillMerge.on_signal`);量齊基準照 `_kill_measure_singles` 的現行規則(等手上那支跑完);任何時候中斷,try/finally 先還原壞法,這次不寫 reach 事件。
   - 續跑快取:每支測試的覆蓋資料檔(不是分析結果)依 `(at_sha, 平台, 測試名, 測試所在檔 blob, 覆蓋 init script 版本)` 存在工作目錄 `choice-cov/<at_sha>/`;同一個 `at_sha` 再跑直接取用、不重跑那支測試(連那支的綠基準一起存成同名 `.base.json`,取用時一起放回基準快取;第一段放行後實測:只存覆蓋資料時合併快篩把取快取的 169 支逐支重量了 689 秒),分析每次都對當下這批壞法重做。換提交(`at_sha` 變)就重量,這一輪就是合併快篩本來每次都要量的基準,只多覆蓋的那三成。
   - 工作目錄:擴充 `_note_audit_work_dir` 那套規則(符號連結拒用、自帶 `.gitignore`)到子資料夾,清檔改成:`choice-cov/` 只留最近 2 個 `at_sha`、`choice-layer/` 留 14 天;清檔在每次 choice-kill 與 choice-layer 開頭做。
3. **依覆蓋選測試與合併快篩**:`clause` 的行用經過的測試組合併指令(照 `_choice_merge_cmd`);合併判讀(`_choice_merge_classify`)的 `names` 傳那個子集、`mg.survived` 依子集算;合併基準仍是整組那一條,子集合併呼叫有失敗就照現在轉逐支確認。`none` 的行 choice-kill 直接記壞法事件 `verdict: "survived"`、`via: "cov"`、`judged: "cov"`、`cov_sha`,而 `tests_sha` 寫成 `"cov:" + tests_sha`——舊版程式(回退後)比對 `tests_sha` 一定對不上、一定重跑,不會把沒跑過的存活帶過去。
4. **記帳**(全部閘名 choice-kill、自帶 `token`;治理帳 (gate, kind) 白名單、`LOOP_NOT_CLOSE_EVENTS` 分類、gov 讀取欄位白名單與 `_GOV_FIELD_TYPES` 補上新 kind 與欄位,型別寫在括號裡):
   - `reach`(每個壞法行一筆):`file`、`fp`、`new_sha`(str)、`reach`(str)、`reach_clauses`(list[str],依計劃路徑、條款號數字序排序;單筆超過 4096 位元組時照 `_gate_event_fit` 截,截斷旗標 `reach_clauses_truncated` 一併登記型別)、`reach_n`(int,截前的條數)、`reach_why`(str,只用下表)、`cov_sha`(str)、`run_id`。
   - `reach_why` 字串表(標 * 的是暫時性,`--reach-only` 會重補):「沒開覆蓋」*「覆蓋接不起來」*「覆蓋資料沒產出」*「分析失敗」*「時間不夠」*「基準不綠」*「掛覆蓋才紅」*「覆蓋例外」「這一行沒有指令紀錄」「名稱檢查沒過」(測試方法名不合法或撞名,那支覆蓋不算數;名稱不改就不會變,所以不是暫時性)。
   - `invalid`:`file`、`fp`、`new_sha`、`row`(str)、`at_sha`(str)、`blob`(str)、`run_id`、`cleared`(bool,選填;`true` 是補償,表示重驗能編了)。
   - `cov-audit`:`file`、`fp`、`new_sha`、`killed`(bool)、`killing_test`(str)、`run_id`。
   - run 那筆多 `cov`(str:`on`|`off`|`tripped`)、`cov_secs`(int)、`cov_skipped`(int)、`cov_selected`、`cov_full`(int)、`cov_judged`(int,這次用覆蓋直接判存活、沒跑壞法的行數;`merged + single + cov_judged` 等於 `ran`)、`compile`(str:`on`|`off`|`env`|`budget`)、`compile_batches`(int)、`invalid_n`(int)、`exhausted_n`(int)。
5. **抽查判錯**:抽到的 `none` 行照跑被殺掉時,記 `cov-audit` `killed: true`、印「覆蓋判錯」,這次 run 其餘 `none` 的行全部改當 `unknown`(在記任何 `via: "cov"` 事件之前,所以不會一行兩筆終態);改跑的時間吃剩下的 `--max-seconds`,不夠的那些行照現在「時間到停在配方之間」留到下次。帳上有 `cov-audit killed: true` 的 `at_sha`,之後同一個 `at_sha` 再跑都不判 `none`(全部當 `unknown`)。
6. **讀者**:
   - `_choice_ledger_index` 照舊只收 kind choice-kill;新增 `_choice_ledger_aux(evs)` 回 `{(file,fp): {"reach":…,"layer":…,"invalid":[…]}}`。用到它的地方:`_choice_points_lines` 一帶、`_choice_kill_pick`、跳過集合(choice-points、推送前掃描、`situation-rule --point`、判讀材料、準備物件)、`_choice_push_read`(多回傳 aux,呼叫端 `_choice_push_round` 推送與 `site="pass"` 兩處一起改)、`_choice_push_judge`(多收 aux)。
   - 挑壞法:`_choice_pick` 多一個 `skip`(〈用詞〉跳過集合);全部候選都在 skip 裡時 `_choice_file_points` 記行狀態 `exhausted`;`_CHOICE_STATUS_TEXT` 加 `"exhausted": "沒有可用壞法"`。不唯一的候選照現在回傳、標 `not_unique`。
   - 帶過去規則(`_choice_kill_pick`):`via: "cov"` 的存活,只有這次也開覆蓋、`cov_sha` 相同、而且那個 `at_sha` 沒有 `cov-audit killed: true` 才帶過去,否則重跑;其餘照現在比 `tests_sha`。
   - reach 有效(印分類用):最新一筆 reach 的 `cov_sha` 等於現在算出的值。`unknown` 也算有效(印「覆蓋不明(原因)」);`--reach-only` 只重補 `reach_why` 是暫時性的那些。
   - gov「第一次判定」照現在數 `attempt == 1 and via == "run"`;`via: "cov"` 另列「依覆蓋判存活」,之後重跑才有的第一次 `via: "run"` 判定另列「依覆蓋判存活後改跑」;`invalid` 不是壞法事件、不影響 `attempt`。
7. **補跑**:`lumos choice-kill --reach-only --diff <範圍>`:對帳上目前是存活、沒有有效 reach(或 reach 是暫時性 `unknown`)的行,照常挑壞法、交配方與準備物件給 guard-kill,但 `cmd_guard_kill` 多一個 `prep_only=True`:準備物件做完合批編譯與覆蓋就結束、不跑任何配方(零配方在 `prep_only` 時不回 rc2);只補 reach,不寫壞法事件;跟 `--no-cov`、`--only`、`--max-mutants`、`--no-merge` 同給時 rc2;乾淨工作目錄檢查同一般 choice-kill;寫一筆 `kind: "reach-run"`(不是 run)帶 `cov_secs`。
8. **判讀材料**:`lumos choice-layer --template [--diff <範圍>] [--part <n>] [--redo <檔>:<行>]`:
   - 對範圍裡帳上目前是存活、判讀狀態不是 `有效` 的行(`--redo` 指定的行一律出;`待複核` 的照出)出材料;一個都沒有時印「沒有要判讀的存活」、rc0。
   - 第一次呼叫(沒帶 `--part`)把份清單寫到 `_note_audit_work_dir` 同一套規則下的 `choice-layer/<清單編號>.json`(每份的存活鍵、材料雜湊),stdout 印第 1 份,stderr 印份數與取法;之後的 `--part n --list <編號>` 從清單取,不重算。
   - 分份:依「主計劃」分組——有經過條款的行取第一條經過條款所屬的計劃,沒有的放「未歸計劃」組(材料附碰到的全部計劃);每份最多 20 個存活;位元組數(UTF-8)超過 200 × 1024 就把存活數減半再切,減到 1 個仍超過時,那份的計劃正文改成只附段名清單、全文另存工作夾 `choice-layer/<清單編號>-<序號>.md` 由材料指路,stderr 註明。
9. **判讀記錄**:`lumos choice-layer <結果.json> --list <清單編號>`:
   - 結果每筆 `{file, fp, layer, before, after, basis, question, reason}`,先整份驗證,不合就整份拒收(rc2)並逐筆印出哪一筆、哪一項不合,什麼都不寫:
     - `file`+`fp` 要在那份清單裡;同一份同一鍵只出現一次;沒有不認得的欄位;`layer` 是 1–4。
     - 長度:`before`、`after`、`question`、`reason` 各 ≤ 300 字;`basis` ≤ 5 項;每項 `quote` 10–200 個實字(上下限都用 `_real_chars` 算)。引句比對沿用情境題的 `_kt_sit_quote_norm`(不另寫正規化)。
     - 第 3 層:`basis` 至少一項 `where` 是那份計劃裡有綁測試的條款號(不是 `[manual:]` 或 `[keeps]`),`quote` 在那條條款原文裡找得到。
     - 第 2 層:`basis` 至少一項 `where` 是那份計劃的段名,`quote` 在那一段裡找得到,而且在任何條款原文與預期值表列裡都找不到。
     - 第 1 層:`question` 必填,含「當」「要」「還是」「現在」四個字樣。
     - 第 4 層:`reason` 至少 10 個實字。
     - `basis` 的 `plan` 要是那份材料涉及的計劃。
   - 結果檔或清單檔讀不到時 rc2、印「清單不在了,重跑 `--template`」。
   - 全過才寫:每筆判讀全文存成 `governance/choice-layers/<內容雜湊>.json`(寫法沿用 `_note_audit_write_verdict`:原子換名、單份上限;加進 `_BOOKKEEPING_DIRS`,同 `governance/reread-verdicts/` 的先例,提交它不會讓代碼審留痕失效);治理帳每筆一個 `kind: "layer"` 事件(`file`、`fp`、`layer`(int)、`new_sha`(str)、`judgment`(str,那份檔的相對路徑)、`judgment_sha`(str)、`deps_sha`(str,依據指紋,見下表合成一個雜湊)、`token`)。
   - 判讀狀態(讀側,同一鍵取帳上最後一筆 layer 事件,含撤回;「最後」照治理帳的檔內順序,跟既有讀者取 `evs[-1]` 一樣):

     | 層 | `deps_sha` 由這些算 |
     |---|---|
     | 全部 | 壞法 `new_sha` 不同就是 `作廢` |
     | 3 | 引的每條條款原文;那條條款綁的測試清單與所在檔 blob |
     | 2 | 引句所在那一段的原文;全部條款原文與預期值表(判「仍不在條款裡」) |
     | 1、4 | 碰到的每份計劃的條款全文加正文(不含 frontmatter 與審計修正紀錄) |

     `deps_sha` 跟現在算的一樣是 `有效`,不一樣是 `待複核`;同一次呼叫裡每份計劃的條款與段落雜湊、每支測試檔的 blob 各只算一次、存活之間共用;判讀檔讀不到或雜湊對不上當成沒有判讀。推送閘從 B 版的樹讀判讀檔。
   - 撤回:`lumos choice-layer --withdraw <檔>:<行> --reason "<≥10 實字>"` 寫一筆 `kind: "layer"`、`layer: 0`、`new_sha` 填現在的、`judgment` 空字串、`reason`(str)的補償事件;那一行變成沒有判讀。
10. **輸出**:

## 不做

- 不機械判等價;判讀的第 4 層只當建議,不放行。
- 不實跑分得出兩版的輸入(第 3 步);第 1 層的業務問題由判讀代理讀程式寫。
- 不用覆蓋分類當最終分類;條款經過不用全部測試的覆蓋算(只用條款綁的守的測試)。
- 不在推送前閘、CI 或 choice-kill 裡呼叫模型;判讀由編排者派代理,lumos 只產材料、驗格式、記帳。
- 不讓層改變擋不擋:第 2、3 層照樣要補到殺掉才算處置完,第 1 層照樣要人答,第 4 層照樣要人放行。
- 不改回報上限、放行鍵、殺傷力判定;不在推送前或 code-loop pass 裡跑覆蓋。
- 不在同一個 JVM 裡逐支歸零取覆蓋;不做完整 mutant schemata(壞法改成執行期開關)。
- 不自動改使用者專案的 Gradle 設定檔(只靠每次呼叫的 init script);只支援 JaCoCo 與 Gradle。

## 實務隱患

- 覆蓋設定沒生效、覆蓋全 0:2026-11-26 實測,init script 太早設定時 Robolectric 測試的覆蓋資料裡專案類別有紀錄數是 0,正確設定時同一支是 345;〈用詞〉覆蓋可信就用這個數(每支跑完當場用 Python 讀覆蓋資料檔算),前 5 支 Robolectric 測試都是 0 就當場斷路,不會把它當成「沒有條款經過」。
- 依覆蓋選測試的正確性:壞法只改那幾行,原版程式上沒經過那幾行的測試,跑壞法版也不會執行到那幾行,所以殺不掉——PIT 與 Google 都用這個前提。例外寫在〈用詞〉覆蓋例外(行內函式、常數、屬性初始值、沒有指令紀錄的行),一律照跑全部;剩下的漏網靠每次 run 抽查(範圍 5)發現。
- 速度:掛覆蓋每支測試多約 1.4 秒(3 次平均);分析一次呼叫、程序內每支約 55 毫秒;覆蓋基準用的就是合併快篩本來的量齊迴圈(同一套預估收手、同一棵暖樹),壞法第一次不會冷編譯;中斷後同一個 `at_sha` 接著跑。最壞情況的上限:覆蓋全不可信 → 斷路在前 5 支、之後照現在;合批編譯對不回 → 不記無效、受總時限四分之一管;抽查判錯 → 其餘 `none` 改照跑、吃剩下時限、跑不完留到下次。三種最壞都不會比現在的合併快篩加逐支更慢超過「前 5 支多 1.4 秒 + 總時限四分之一」。REVISIT 看 `cov_secs`、`cov_full - cov_selected`。
- 合批編譯檢查的失效開放:原樹自己編不過、Gradle 環境壞掉、輸出被截斷、錯誤對不回、單獨編也綠——全部不記無效(寧可照現在交給測試階段);嫌疑壞法要單獨再編一次確認才記;還原用 try/finally 並比對內容,還原不乾淨就整個準備物件中止。
- 中斷:準備物件在 choice-kill 既有的訊號範圍內跑;合批編譯與分析的 Gradle 呼叫當場收,量齊基準照現行等手上那支跑完;try/finally 先還原壞法、不寫 reach 事件、已完成的覆蓋資料檔留在續跑快取。
- 判讀把該問人的歸成第 2、3 層:人就不會被問到,這是四層裡最貴的錯。四道擋:拿不準歸第 1 層寫進派工詞;引句 10 字以上、要落在它標的那條條款或那一段(機械驗);REVISIT 抽樣對照;判錯用 `--withdraw` 撤回、`--redo` 重判。引句對得到但意思讀錯機械驗不出來,靠抽樣。
- 判讀被帶風向:材料由工具產生、不含舊分類與處置;編排者仍可能在派工詞裡夾帶結論——照本工具「單人、AI 依序操作、不防 AI 刻意偽造」的威脅模型不另防,手冊寫明派工詞只放材料與作答格式。
- 判讀成本:每個存活一次代理判讀,一份最多 20 個;依據變了只標待複核,一批處置完再重判一次。
- 新舊帳互讀:舊程式讀到新 kind:`_choice_ledger_index` 只收 kind choice-kill、gov 對不認得的 kind 略過(r1 回滾席與整合席已驗);新程式讀舊帳:沒有 reach 印 `未分類`、沒有 invalid 就照現在挑壞法。
- 併發與交易:已排除:單人單機依序操作。
- 已排除:金流:只讀測試覆蓋、不碰金額計算。
- 已排除:對外送出:覆蓋在本機跑,不對外送資料。
- 已排除:不可逆:治理帳只追加;判讀錯了用補償事件撤回;覆蓋判錯由抽查發現、那個 `at_sha` 之後不判 `none`、下一次 run 重算;`via: "cov"` 的存活 `tests_sha` 帶 `cov:` 前綴,新舊程式都不會把它帶過去而不重跑;無效壞法只綁那支檔的 blob,檔一改就重驗。
- 守衛面:不排除——推送閘的提示結構會變、行狀態多一種 `exhausted`、挑壞法多一個 `skip`;S9、S10、S16、S22 守住擋不擋、讀者與環境壞掉時不放行。

## 驗收條款

## 天花板

1. 「經過」只代表條款的測試跑過這一行,不代表它檢查了這一行的結果;存活本來就表示沒檢查到。
2. 依覆蓋選測試靠「沒經過那幾行的測試殺不掉那幾行的壞法」;覆蓋例外以外的漏網靠抽查,抽查只是樣本。
3. 只支援 JaCoCo 與 Gradle;並行跑測試時逐測試覆蓋分不出(覆蓋基準一支一支跑)。
4. 分類準不準靠 S12、S18 一個專案量過;多專案的數字等 REVISIT。
5. 層是模型判的,不是證明:引句機械驗得到「真的出自那條條款或那一段」,驗不到「真的排除了改壞後的行為」;拿不準歸第 1 層是把錯往「多問人」那邊偏。
6. 第 1 層的「現在程式是哪個」是代理讀程式答的,沒有實跑一個分得出兩版的輸入(第 3 步補)。
7. 合批編譯檢查只把「單獨也編不過」的壞法記無效;合批時被別的壞法連累、單獨卻編得過的,照常進測試;單獨編得過但合批時讓別人編不過的壞法,本身不受影響。編譯錯誤報在跟壞法無關的位置時一律不記無效,照現在交給測試階段。
8. `待複核` 的判讀可能已經過時;它只影響提示文字,擋不擋不看層。
