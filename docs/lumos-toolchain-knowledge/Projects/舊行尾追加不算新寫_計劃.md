# 舊行尾追加不算新寫_計劃

白話:清舊筆記時最常做的事,是在舊句後面補一個「(更正:…)」。現在兩道檢查都把那整行當成新寫的來查——第一層(筆記形狀擋)把舊句本來就有的問題算到補更正的人頭上,第二層(筆記內容審)讓判定者重判整句舊話。這份計劃讓兩層都只看**這次補在尾巴的那段括號**。只認「起點版本裡的舊句一個字都沒動、只在尾巴補括號」,其他改法照今天整行查。

依據:
- 消費專案清漂移回傳(2026-10-02,第 3 項,去識別):在舊句後補更正括號,整行被當新寫——舊行原有的「還沒」觸發否定現況句提醒 24 條;一條上線前合法的舊 DEP 被當成新寫的 DEP 擋下,只好改寫成歷史 WHY。
- 本 repo 重現(2026-10-02,用測試小工具 `_ns_repo`/`_ns_note`/`_ns_stage` 建暫存專案):先提交 `DEP:付款走舊閘道 scripts/pay.py 還沒換掉`,再在句尾接「(更正:2026-10-02 已換成新閘道,見 `Systems/Pay`)」並暫存,`note-shape --staged` 回 1(沒寫來源的 DEP),並對原本就有的「還沒」再提醒一次。會寫成 [S1][S2] 的測試。
- 消費專案那兩批清理提交的實測(2026-10-03,`git diff -U0` 逐區塊數):346 個改動區塊裡 345 個是「刪幾行就加幾行」;按位置一對一、新行以舊行開頭的有 193 處,其中 192 處追加段是括號、長度中位 103 字、九成在 190 字內、最長 279 字;唯一不是括號的是在行尾補狀態標籤。上限與括號形狀照這組數字定(〈做法〉1)。
- 前案 [[Projects/舊行插字不算新寫_計劃]]:設計審三輪(97 條、major 27 條),末輪 4 條 major 都在「自己找舊行」的配對規則。本案換掉配對方式,其餘已審過的結論沿用(否定提醒只看新加的字、前綴提醒不套用、放寬帳用獨立種類、喚醒那一路不動)。
- 程式現況:第一層 `_note_shape_eval` 取 `_notelines_new` 的新行,對每行跑 `_ns_check_line`、`_ns_revisit_violations`,再跑「新程式檔喚醒舊引用」(用已報過的行避免重報),提交前另收否定與前綴提醒;第二層 `_note_audit_items` 用同一支取新行,`_note_audit_render_list` 把整行(`>>>` 那行)與前後文交給判定者,判定檔每列記內容編號與判定。兩層取改動都走 `_ns_diff`,解析走 `_notelines_parse_added`。提交前模式用新增行號;推送與 doctor 模式用逐提交新增的文字認新行。已存在的分支推送時,推送前掛鉤與 CI 的筆記形狀擋起點相同(都經 `_lens_push_base` 再截到上線點;掛鉤給遠端舊頂端、CI 給 `$BEFORE`,是同一個提交);新分支首推時兩邊不同(掛鉤從「第一個不在任何遠端上的提交」的上一版算,CI 拿到 40 個 0、改從跟主線的分岔點算,這是既有的差異、所有筆記形狀檢查都受影響),淺層 clone 時兩道都整支跳過並記 `skipped-env`。

PRIOR-ART: 「只評這次改到的部分」是 lint 接 PR 的標準做法(reviewdog `-filter-mode=added`、Danger 只看 diff 行);本案在「行」之下再細到「行尾補的括號」,配對直接用 git diff 的改動區塊按位置對,不另寫找舊行的演算法;diff 的區塊讀法改成照 `@@` 計數走(同 `git apply`/unidiff 類解析器的做法);範本雜湊與版本號一起用測試釘住,照抄 `t_note_audit_reread_template_pinned`。
RETIRE-IF: 上線八週後任一成立就撤掉或重想:①從放寬帳(〈做法〉5)抽 20 行對回提交,有一半以上其實是借括號把新的程式現況塞進舊句——改回整行查;②八週內推送時一次放寬都沒有,而且抽查那段期間第二層的送審清單也沒有任何「只判這次補在句尾的」項目(第一層提交前的提醒放寬不記帳,只看這兩處會低估)——機制是死的;③筆記形狀擋改成以「欄位」或「句子」為單位判新舊,這條被取代。
REVISIT:2026-12-01 從 docs/.governance-log.jsonl 數閘 note-shape、種類 relaxed 近八週的筆數(state 是 done 與失敗的 git-failed、error 分開數),並抽查同期第二層清單,對 RETIRE-IF ①②;失敗不是 0 先查壞在哪

## 做法

1. **配對(兩層共用一支)**:新寫 `_notelines_append_pairs(repo_root, staged, base_where, tip_where, vault_rel)` → `(配對表, 失敗原因)`。配對表是 `{NFC 路徑: {終點版本行號: 舊行原文}}`;失敗原因平常是 None,只有「git 呼叫失敗」或「例外」才帶字串(例外的類別名),這時配對表是空的、這次全不配對、照今天整行查。例外在這支函式裡吞掉(同 `_ns_negation_prepare` 回元組的先例)。**不算失敗**:沒有起點版本(新分支從空樹、起點是空樹)、沒有候選篇——這些是沒東西可比,回空表、原因 None;單篇讀不到、超過上限、解不開、路徑被 git 加引號——只有那一篇不配對,其他篇照配。
   - **起點就用呼叫端自己的範圍起點,不另算**:提交前是釘住的 HEAD(取改動用 `_ns_diff("--cached", <HEAD 的完整 sha>, "--", 圖譜目錄)`,不在兩次呼叫之間各自解析 HEAD);推送前與 CI 是 `cmd_note_shape` 已經算好的起點(`_lens_push_base` 再截到上線點;已存在的分支兩邊同一個,新分支首推不一定,見天花板 10);doctor 是上線點;第二層是 `_note_audit_resolve` 算好的起點。起點版本裡的行在它被推上去時已經過了第一層(或留了跳過帳),跟其他已推上去的行同等,所以拿它當「舊句」;第二層有沒有判過它不保證(天花板 3)。設計審 r1 曾改成「舊句要在主線分岔點裡」,r2 查證:那輪的前提「CI 從主線起點整行再查」不成立(見依據最後一條),而且分岔點算法會是專案裡第三套(既有 `_lens_push_base` 與 `_push_range_start`,收斂路在 [[Issues/推送前其他閘的範圍在合過主線時會多算]]),還會讓沒有本地 main 的 CI 全不配對——撤回。
   - **取改動區塊**:推送、CI、doctor、第二層用 `_ns_diff(<起點>, tip_where, "--", 圖譜目錄)`。不跟 `_NotelinesNet` 共用——它只在 `keep_other` 時建、而且刻意用到才算(代碼審 r2 併發席),本案不動它。什麼時候才跑見〈做法〉2、4。
   - **統一的區塊讀法**:新寫 `_notelines_parse_hunks(raw)`,照 `@@ -a[,b] +c[,d] @@` 的計數走(沒寫計數就是 1,計數 0 的那邊沒有行;標頭後面可以帶函式上下文);`diff --git` 重置狀態;在區塊裡照計數吃 `-`、`+`、空白開頭的上下文行,`\ No newline` 不吃計數;計數吃完才回到檔頭狀態,所以內容行 `++ x`(在 diff 裡是 `+++ x`)不會被當成檔頭。上下文行把一個區塊切成幾個「改動段」。`--- `/`+++ ` 路徑照現行(去掉 `a/`、`b/` 與尾端 TAB;被 git 加引號的路徑、`/dev/null`、改名、二進位或純改名沒有內容)——這幾種不配對。
     - **舊解析器一起改**:`_notelines_parse_added` 改成包這支(只交出被加的行與正確的新行號),所以提交前、推送逐提交、合併提交判不了的退路、`_NotelinesNet` 四處一起修掉「`++ x` 之後同檔新行全漏查」與「上下文行讓行號錯位」兩個既有洞(設計審 r1 正確性、整合、架構三席各自實測,編排者重現)。回傳形狀不變。
     - **同族另兩處**:`_ns_deleted_summary_lines` 讀被刪行也改走 `_notelines_parse_hunks`(代碼審 r1 架構席;它只收縮排的摘要前綴行,`---` 判斷原本就碰不到它要的行,所以這是收斂成一支讀法、行為不變,不是修洞),旗標照舊自己組(不偵測改名)。`_diff_added_lines` 只有一支測試在呼叫、正式流程沒用到。
     - **釘住 git 的切法**:`_ns_diff` 加 `--inter-hunk-context=0` 與 `--diff-algorithm=myers`,走 `_ns_diff` 的呼叫端不再受本機設定(`diff.interHunkContext`、`diff.algorithm`)影響,本機與 CI 切法一樣。讀法照計數走,就算有上下文行也不會錯位。
   - **配對規則**:每個改動段裡,被刪的行數等於被加的行數才配,第 i 條被刪的對第 i 條被加的;行數不等的整段不配。插在舊行前面的新行會讓行數不等,搶不走舊行(設計審 r1 正確性席實驗,編排者重現)。
   - **每一對的條件**(常數:`_NS_APPEND_MIN_OLD`=8、`_NS_APPEND_MAX_TAIL`=300、`_NS_APPEND_MAX_LINE`=2000、`_NS_APPEND_BASE_MAX_BYTES`=524288):
     - 兩邊只去掉尾端空白(含 CR):O'=舊行.rstrip()、N'=新行.rstrip();N' 以 O' 開頭而且比 O' 長。開頭的縮排要一樣(縮排變了不算追加)。
     - O' 去頭尾空白後至少 8 個碼點(含 8)。
     - 追加段 T=N'[len(O'):]:去掉頭尾空白後,必須整段由一個或幾個「括號群」組成,群與群之間只能是空白(零個也行)。括號群=從半形 `(`(U+0028)或全形 `（`(U+FF08)開始、照深度數到對應的半形 `)`(U+0029)或全形 `）`(U+FF09)為止(半形全形視為同一種、可以混用、可以巢狀);群外有任何別的字就不算。行內程式碼(反引號)裡的括號照樣計數,所以裡面有單邊括號就配不起來(偏嚴)。例:「 (更正:…)」「(更正:…) （見 X）」「(a)(b)」算;「(更正) 逾時改 30 秒(見 X)」不算(中間有群外的字)。
     - T 去掉頭尾空白後不超過 300 個碼點(含 300);N' 不超過 2000 個碼點(含)。上限固定,不隨舊行變長。
     - 起點版本那一行的文字與這個被刪的行,兩邊都去掉尾端空白(含 CR)後要相等(也就是都等於 O');不等就不配。
     - **同一個脈絡**:舊行在起點版本、新行在終點版本的區塊(`_notelines_regions`)相同、兩邊都在圍欄外(`_visible_lines`)、那篇的重建標記兩個版本相同。起點版本只讀有候選的那幾篇,用 `_nodehome_cat_blobs_capped`,單篇超過 524288 位元組(大於才算超過)就那篇不配;回來的位元組自己用 `utf-8-sig` 解,行照位元組切(不換掉 CR)。拿去 git 讀用 diff 檔頭上的原樣路徑,回傳表的鍵用 NFC,兩層查表時用 `nfc(路徑)`。
   - **撞名與總量上限**(代碼審 r1):diff 裡 NFC 正規化後同名、原樣路徑不同的篇(NFC 與 NFD 兩種寫法並存)整組不配——配對表與查表都用 NFC 當鍵,撞在一起時一篇的舊行會被拿去扣另一篇的新違規(資安席實測可繞過);有候選的篇超過 `_NS_APPEND_MAX_FILES`=200、候選對超過 `_NS_APPEND_MAX_PAIRS`=20000、或起點加終點要讀的位元組總和超過 `_NS_APPEND_MAX_TOTAL_BYTES`=32 MiB(代碼審 r2 併發席:單篇上限管不到總量)時這次全不配,失敗原因回 `"cap"`——不算失敗、不記 git-failed/error,但第一次查表時印一句提醒(「候選太多、全部照整行查,分幾次提交或推送就能只查補上的那段」;代碼審 r2 通才席:原本靜默,清舊筆記的人照擋下提示做仍被擋、看不出原因),推送時記一筆 state `capped` 的放寬帳。**新行抽取那一層也有同一個撞名洞**(代碼審 r2 資安席、邊界席):新行以 NFC 當鍵,兩種寫法的同名筆記新行會併成一篇、另一篇整篇漏查——這是本案之前就有的;被檢查版本裡同名並存、而且這次有新寫的行時,第一層與第二層都直接擋下說清楚(`_ns_nfc_clash_errs`),數並存要用 `_nodehome_list` 不去重的那份路徑清單(以 NFC 為鍵的那份已經併成一筆,r2 折入時在 macOS 暫存區實測)。起點與終點版本用同一次 `_nodehome_cat_blobs_capped` 批次讀(提交前的終點是暫存區 `:路徑`),不逐篇起 git。
   - 成本:配對對每個改動段是線性的(按位置對,不做兩兩比較)。新函式照 `lint-new` 的複雜度上限拆小(`_note_shape_eval`、`cmd_note_shape` 已有放行的複雜度告警,改動讓數字變時照既有放行流程處理,不新增放行)。
2. **第一層:只報多出來的違規**。配到的新行 N(舊行 O):
   - **用到才算、但要在喚醒之前扣**:配對結果包成一個跟 `_NotelinesNet` 同形的小類別 `_NotelinesPairs`(建構時只存參數;第一次呼叫 `table()` 才跑 `_notelines_append_pairs`,整個範圍一次、之後重用;失敗時 `failed` 為真、`error` 記原因,`table()` 回空表)——不另寫閉包加元組那種第二套「用到才算」(設計審 r3 架構席)。`_note_shape_eval` 逐篇處理時,某篇的 `_ns_check_line`/`_ns_revisit_violations` 有違規才呼叫 `table()`;扣減在那一篇的違規收進總表**之前**做,所以被放寬的行不會留在「新程式檔喚醒」那一段用來避免重報的已報集合裡,喚醒那一路會照報它([S20])。
   - `_ns_check_line` 對 N 與 O 各算一次(同一份檔案清單、同一個 regen 與區塊),照計數只報 N 比 O 多的。**只扣照片段比的規則**(`_NS_FRAG_KEY_RULES`:程式行號引用、釘版本不合法,鍵是(規則, 片段))——括號裡出現一個新的 `路徑:行號` 會產生新片段、照報。**整行層級的規則一律不扣**:鍵只有規則名(或固定改法)的規則,扣了的話括號裡新寫的東西會借舊行的債溜過——「現況描述沒寫來源」(Enzo 2026-10-03 代碼審 r1 後裁「括號要帶來源才放寬」:第二層判的是推不推得出、也不判缺來源;括號自己帶了 [來源:…] 整行就不犯這條,沒帶就照報)、「SEE 只放連結」「條件寫在不評估的地方」(代碼審 r2 通才席、正確性席:舊 SEE 行本來就夾句子、舊表格列本來就有不評估的條件標記時,括號裡再夾新內容原本不重報)是同一族,收成一條規則,不逐條比規則名。同一行同一個片段 `_ns_check_line` 只出一條,括號裡重複舊行已有的同一個引用不會多報(天花板 4)。**新規則預設是整行層級、不扣**;要扣,在那條規則自己的計劃寫明理由並加進片段鍵表。

## 實務隱患

- **繞過**:
  - 另寫一行「舊句+新內容」而舊行還在——舊行沒被刪,不配。刪掉舊行、在遠處寫「舊句+新內容」——不在同一個改動段,不配。在改過的舊行正上方插一行「舊句+新內容」——改動段裡加的比刪的多,整段不配。
  - 括號外夾字(「(更正) 新斷言 (見 X)」)——不是純括號群,不配。
  - 舊句是這次範圍才寫的——不在起點版本裡,不配。
  - 在舊行尾巴補括號、括號裡寫新的程式現況——行號引用照片段比會擋;「沒寫來源」這條舊行本來就犯、第一層不重報,要靠第二層判定者單獨判括號(2026-10-03 寫這份計劃時第二層沒接進推送前掛鉤與 CI、只能手動跑,天花板 1);括號上限固定 300 字。
  - 起點版本裡的舊句本身沒被第二層判過(它在第二層上線前、或用跳過、或 `--no-verify` 推上去的)——本案不補判它,跟所有已推上去的行同等;第二層的標籤寫「起點版本已有」,不宣稱它被審過。
  - 每次推送後再補一段:每次各自受 300 字上限、各自被第一層照片段比、被第二層判(接線後);沒有跨推送的累計上限(天花板 1 一起回頭)。
- **效能**:第一層只有在某篇有違規、或那一行有否定命中時才跑配對(整個範圍一次);第二層有送審項目時多一次;起點版本只讀有候選的篇、有大小上限;配對按位置對、線性。消費專案全圖譜一千個提交的範圍 diff 約 4 MB、0.1 秒(設計審 r1 邊界席量)。
- **併發**:只讀 git 物件;提交前的起點釘成 sha,不在兩次呼叫之間各自解析 HEAD;放寬時多寫一筆治理帳,走既有寫入器,登記進既有的鎖 Issue。
- **回滾**:還原配對與放寬那一個提交即回到整行查(解析器修補是另一個提交、留著);已寫的 `relaxed` 帳留著無害(沒有讀者靠它);第二層派工詞版本退回上一版;判定檔裡帶 `tail` 的列在退回後的程式讀起來是多一個沒人看的欄位——`_note_audit_parse_verdict` 現在只驗 `id` 與 `class`,多欄照收,所以這些列會被當成整行判定(偏鬆,只影響退回期間那幾行;要追查就照〈回退〉重跑)。
- **相容**:第一層擋得只會變少(解析器修洞的部分會多抓到原本漏查的行——那本來就該查);判定檔新增可省略欄位,舊判定照舊有效;`_ns_diff` 新旗標讓走它的呼叫端的區塊切法跟本機設定無關;`scripts/lumos` 要維持 3.9 能解析(既有 PITFALL,CI 有 py39 語法檢查與 `t_lumos_no_zip_strict_for_py39` 守),新程式不用 3.10 之後的語法;筆記格子開擋後補更正的舊行仍會被格子要求補齊(見 REVISIT,S1 到 S4 的測試寫明「格子未開擋」前提)。
- **跨環境**:已存在的分支,本機推送前與 CI 用同一個起點,配對結果一樣;新分支首推時兩邊起點不同(既有差異,見依據最後一條),CI 可能比本機嚴(舊句只在另一條已推上去、沒進主線的分支上時,CI 那邊不配、整行查),不會比本機鬆(天花板 10);淺層 clone 時筆記形狀擋與筆記內容審本來就整支跳過(記 `skipped-env`),本案不改。
- 已排除:金流:這道檢查只讀筆記與 git 物件,不碰任何付款流程
- 已排除:對外送出:不呼叫網路、不寄送、不寫到 repo 之外
- 已排除:不可逆:只決定擋不擋、送審印什麼,還原一個提交就回到原本的判法
- **守衛面**:兩道都是擋提交與推送的閘,改的是「哪些內容算新的」——放得太寬就是一條繞過的路,所以不排除、照走設計審。

實作分成兩個提交:第一個是解析器修補(`_notelines_parse_hunks`、`_notelines_parse_added` 改包它、`_ns_diff` 的兩個新旗標),第二個是配對與兩層的放寬(第一輪問閘時提示累計折入太多、建議拆小)。要退回放寬,只還原第二個:兩層都回到「新增的行整行查/整行送審」;設定格式沒變,`relaxed` 帳留著無害;判定檔裡帶 `tail` 的列在退回後被當成整行判定(〈實務隱患〉回滾);解析器修補留著,`++ x` 與上下文行錯位兩個舊洞不會回來。已經靠這條放行、推上去的舊行不會被追溯擋下,要追查就用還原後的版本跑 `lumos note-shape --diff <起點>..<終點>` 重看那段範圍。

## 天花板

1. 放過的是「舊句本來就犯的、照片段比的違規」(程式行號引用、釘版本)與否定提醒;「現況描述沒寫來源」不放寬(括號要自己帶 [來源:…],代碼審 r1 後 Enzo 裁——設計審時寫「要靠第二層判括號」不成立,第二層判推不推得出、不判缺來源)。整行層級的規則(SEE 只放連結、三條回頭條件規則…)也不扣(代碼審 r2、r3):舊行本來就犯的,補了括號照報——想只補更正就得順手把整行修好。括號裡寫新的程式現況(推得出的)要靠第二層判;第二層接進推送前掛鉤與 CI 之前(2026-10-03 寫這份計劃時沒接),這段只有手動跑才會被判。每次推送後可以再補一段,沒有跨推送的累計上限。回頭時機:第二層接線那一步(入口在 [[Projects/筆記內容審_計劃]] 的接線條件)要一併決定要不要加累計上限。
2. 只認句尾補括號:補更正時順手改了一個字、插在句中、或尾巴有括號外的字,整行照新寫查。
3. 舊句以各道檢查自己的範圍起點為準:起點版本裡的舊句本身有沒有被第二層判過,本案不管(跟所有已推上去的行同等);沒有起點版本(從空樹算)時全不配對。
4. 同一行同一個程式行號引用只算一條:括號裡重複舊行已有的一字不差的引用不會多報。
5. 否定字眼跨在舊句與追加段交界抓不到(只是提醒、不擋)。
6. 配對只靠 git 的改動段:刪的行數跟加的不等(例如同一段裡另外插了新行)、或 git 把舊行與新行分到不同段時配不到,照整行查(偏嚴)。
7. doctor 用上線點當起點:上線點之後分幾次推送各補一段括號,doctor 第一層看到的是累積的那段,超過 300 字就會唸(訊息會列出這個可能);第二層 doctor 不比範圍。
8. 被 git 加引號的檔名(含 TAB、引號、換行)照現行讀不到路徑,本案不改。
9. 提交前與推送前量的範圍不同:同一批工作分幾個提交各補一段,每個提交前各自量、推送前量累積;累積超過 300 字時提交前放行、推送前整行查——壓成一個提交或縮短括號。括號被判推得出時,只有推送前 `reset --soft` 回範圍起點再重提才改得動(`commit --amend` 改不動);已推上去的括號改寫或刪掉都會整行照查,只能在後面再補一段括號。
10. 新分支首推時本機掛鉤與 CI 的起點不同(既有差異):舊句只在另一條已推上去、沒進主線的分支上時,本機照配、CI 整行查——CI 只會比本機嚴。回頭時機:[[Issues/推送前其他閘的範圍在合過主線時會多算]] 收斂起點算法那一步一併重驗 [S41]。
11. 候選超過總量上限(200 篇、20000 對或 32 MiB)時這次全部整行查:會印提醒、推送時記 capped 帳,分幾次推就能只查補上的那段。同一篇筆記的檔名有 NFC 與 NFD 兩種寫法並存、而且這次有新行時直接擋下,不猜哪一份是新寫的。
12. 放寬帳不去重:一次推好幾條分支、範圍重疊時同一行會各記一筆,統計要照(推送編號, 路徑, 行號)去重(代碼審 r3)。
13. 只判句尾的申訴蓋不掉同編號的整行判定:整行判 CODE 之後清單換成帶句尾的範圍,照現在的清單送句尾申訴,check 仍算 CODE,申訴照收、不報錯——要申訴整行判定就送整行申訴,或直接改掉那行(代碼審 r3 併發席;r2 為了不讓句尾申訴把整行 CODE 蓋成 CONTEXT 刻意這樣分)。回頭時機:第二層接進推送前掛鉤與 CI 那一步(入口在 [[Projects/筆記內容審_計劃]] 的接線條件)一併決定申訴要不要對這種情況報錯。
14. 候選太多的提醒印在共用的配對物件裡,doctor 事後掃描(起點是上線點)碰到時也會印「分幾次提交或推送」這句對它不適用的建議;要上線點之後累積超過總量上限才會出現(代碼審 r3 架構對齊席)。
