# 選擇點表第四批常用語法_計劃

## 白話

選擇點表([[Projects/改動選擇點都要有需求守住_計劃]])每列是「一個語法節點換成兄弟寫法」的機械壞法:換了測試還綠,就表示沒有測試守住那個選擇,推送前要作者補測試、寫回規格或寫理由放行。前三批收了運算子、集合與 Flow 兄弟寫法、空值處理、Compose 副作用、協程與業務情境寫法。這是路線總圖 [[Projects/選擇點對應需求路線_計劃]] 的第 4 步:補「常用語法」——2026-11-23 調研裡別的變異工具有、我們表裡沒有、價值列為高的六類。

這一批收(候選 20 列,範圍 7 的實測門檻過了才給號,從 C-56 起):
- **回傳值換成預設值**(新類別 RET,6 列):函式宣告了回傳型別 `Boolean`、`Int`/`Long`、`List<…>`、`Set<…>`、`Map<…>`、可空型別時,回傳的那個運算式換成 `true`/`false`、`0`、`emptyList()`、`emptySet()`、`emptyMap()`、`null`。問:「這個函式算出來的結果,有哪條需求在檢查?」
- **刪掉跳出**(SBR,2 列):`break`、`continue`、不帶值的 `return`/`return@標籤`,以及「沒有 else 的 if」裡的提早 `return 值`。問:「遇到這個條件時,要不要就此停下或跳過?」
- **範圍邊界**(ROR,3 列):`..` → `..<`、`..<` → `..`、`until` → `..`。問:「上限那個值本身算不算在內?」
- **屬於/不屬於**(ROR,3 列):`a in b` ↔ `a !in b`,`when` 分支的 `in …` → `!in …`。問:「條件是『在裡面』還是『不在裡面』?」
- **刪掉賦值**(SBR,1 列):陳述層級的 `x = …`、`a.b = …`、`x += …`(例 `_state.value = …`)。問:「這一步要不要更新這個狀態?」
- **反向保留與漏一個鏈式呼叫**(API,5 列):`takeIf` ↔ `takeUnless`;拿掉 `.trim()`、`.distinct()`、`.sorted()`。問:「條件成立時留下還是丟掉?」「前後空白算不算有效輸入?」「重複的要不要合併?」「順序有沒有要求?」

不收:`is` ↔ `!is`(換了會打斷智慧轉型而編不過)、拿掉 `.take(n)`(Flow 上會掛住)等,理由見〈不做〉。

## 為什麼

使用者 2026-11-23:選擇點變異的主要價值是把「規格沒寫、AI 寫程式時自己默默做的細規則決定」機械地翻出來交人拍板(原話見路線總圖〈白話〉:「這個功能的價值,是在抓出這種AI自己做決定,人也沒想到的隱患」);這六類是日常程式裡最常藏著這種決定的寫法(上限算不算、空的時候回什麼、要不要提早離開、要不要去重排序)。

PRIOR-ART: 同前三批的論文〈Practical Mutation Testing at Scale〉https://arxiv.org/pdf/2102.11378 (2.2 在語法樹上產生、表 1 的 ROR 與 SBR、3.1 乾節點、3.2.1 編不過的壞法事前擋;SBR 原本就是刪陳述,這批把刪的對象從呼叫擴到跳出與賦值)。各類的來源(2026-11-23 調研,全文在使用者的私人實驗 repo `research-choice-point-feasibility.md`):回傳值替換是 PIT 預設壞法 https://pitest.org/quickstart/mutators/ ;刪 return/break/continue 與漏一個鏈式呼叫是 Just 2014 列為「要更強的壞法才對得上的真 bug」(刪 return/break 12 個、漏一個鏈式呼叫 4 個)https://cs.ubc.ca/~rtholmes/papers/fse_2014_just.pdf ;刪欄位賦值、刪鏈式呼叫、刪 distinct/sorted/limit 是 Arcmutate 的擴充壞法 https://docs.arcmutate.com/docs/extended-operators ;範圍邊界對應 Defects4J 好修的 bug 裡差 1 占 13.7%、比較運算子錯 11.7%(未逐字)https://arxiv.org/pdf/2402.14471 ;反向判斷是 UOI 延伸。語意出處:Kotlin 官方 Ranges and progressions(`..`、`..<`、`until`)https://kotlinlang.org/docs/ranges.html ;`..<` 是 Kotlin 1.9 起穩定的 `rangeUntil` 運算子 https://kotlinlang.org/docs/whatsnew19.html ;`takeIf`/`takeUnless` https://kotlinlang.org/docs/scope-functions.html ;智慧轉型 https://kotlinlang.org/docs/typecasts.html 。ast-grep 實跑(本機 0.51.2,2026-11-23,試做規則與樣本另存在使用者私人實驗資料夾 plan-trace-samples/,結果寫進〈預期值表〉):`$A in $B` 用預設比對會同時命中 `!in`,要用 `strictness: cst` 才分得開;`..` 與 `..<` 都是 range_expression、記號不同,樣式分得開;`until` 是 infix_expression 中間夾識別字。不採:`is` ↔ `!is`(智慧轉型,見〈不做〉);拿掉 `.take(n)`(型錄「不收」清單已列 `take`/`takeLast`,Flow 上拿掉會掛住);同型別引數對調(沒有型別資訊難做,調研列中);刪 `when` 分支(母計劃〈不做〉列不收,要翻案另開)。

## 舊否決比對

- 母計劃〈範圍〉SBR「只刪呼叫陳述」:這份把 SBR 擴到跳出陳述與賦值陳述(論文表 1 的 SBR 是刪陳述,沒限呼叫;母計劃當時只收呼叫是第一版的範圍),不翻母計劃的 A.1.12 不刪清單,另加跳出自己的排除(範圍 2)。
- 型錄〈選擇點表〉說明段「不收」清單有 `take`/`takeLast`:那是兄弟互換;這份的「拿掉 `.take(n)`」也照不收(Flow 上會掛住),一致。
- 母計劃〈不做〉「不收數字常數、字串常數、`when` 分支刪除」:RET 換的是回傳的整個運算式、換成型別預設值,不是改數字常數;`when` 分支刪除照舊不收。
- 第二批〈不做〉「回傳型別不同的互換」:這份每一列換完型別不變(RET 換成同型別的預設值;範圍邊界在整數、字元上型別不變,其他型別見〈實務隱患〉)。
- 母計劃〈不做〉「不讓 AI 自動判等價」:照舊;RET 的等價(函式本來就回 0)靠規則排除字面值與人放行。
- [[Systems/kotlin規則包]] 否決過「把 Detekt 規則點名的寫法全收」:這份每列有調研來源與要問的業務問題,不是照規則清單收。

## 用詞

- **論文**、**選擇點表**、**乾節點規則**、**錨點**、**型別前提**:同 [[Projects/改動選擇點都要有需求守住_計劃]]〈用詞〉。
- **宣告的回傳型別**:`function_declaration` 底下、在 `function_value_parameters` 之後(不是接收者型別 `fun String.f()` 那個)的 `user_type` 或 `nullable_type`;沒寫回傳型別、寫成型別別名的,不命中。
- **回傳的運算式**:`return 運算式`(不帶標籤)那個運算式,或運算式本體 `fun f(): T = 運算式` 那個運算式;往外找最近一層 `function_declaration` 或匿名函式 `fun() { }`,停在匿名函式時不算(那是匿名函式的回傳)。
- **早退 if**:沒有 `else`、當陳述用(父節點是陳述清單)、條件裡沒有 `null` 字面值、沒有 `!` 開頭的記號(含 `!is`、`!=`、`!in`、前綴 `!`)、沒有 `isNullOrEmpty`/`isNullOrBlank` 的 `if`。條件有這些時,本體裡的跳出拿掉會讓後面的智慧轉型斷掉、編不過,所以排除(寧可漏)。
- **跳出陳述**:`jump_expression` 的 `break`、`continue`、`return`、`return@標籤`、`return 值`。

## 不做

- `is` ↔ `!is`:`if (x is Foo) x.bar()`、`x is Foo && x.bar`、`if (x !is Foo) return` 之後用 `x`,換了都會打斷智慧轉型而編不過;K2 起連 `val ok = x is Foo; if (ok) x.bar()` 這種存進區域變數的也會智慧轉型,語法樹判不出哪些安全。同母計劃把「跟 null 比較」列為乾節點(論文附錄 A.1.10)的理由。
- `when` 分支 `!in …` → `in …`:要新增「拿掉分支開頭的 `!`」這種編法,通用路徑沒有;這批不改程式,REVISIT 看 `in` 那一列的數字再說。
- 拿掉 `.take(n)`:Flow 的 `take(1)` 拿掉後收集一個熱流會永遠等下去,測試掛住、落成跑不出結果;語法樹分不出接收者是集合還是 Flow。型錄「不收」清單已列 `take`/`takeLast`。
- 回傳 `String` 換成 `""`、`Double` 換成 `0.0`、`Flow` 換成 `emptyFlow()`:調研的高價值類只列空集合、null、true、false、0;`emptyFlow()` 還要補 import。看 RET 六列的數字再決定。
- 回傳字面值 `true`/`false` 互換:字面值回傳的函式多半是覆寫的旗標,先不收。
- 刪「帶值的 return」在早退 if 以外的位置(函式最後一個 return、if/else 兩邊都 return):拿掉會讓函式少一條回傳路徑,一定編不過。
- 同型別引數對調、刪 `when` 分支、Elvis 右值換值、相似字串方法:調研價值列中,不在這批。
- 不改一行一個壞法、回報上限、乾節點表、殺傷力判定、處置鍵與推送前那一道。

## 實務隱患

- 編不過(語法樹沒有型別):①範圍 `..` → `..<` 要 Kotlin 1.9 以上;接收者是 `Comparable`(例 `LocalDate`)時 `..` 回 `ClosedRange`、`..<` 回 `OpenEndRange`,存進宣告了型別的變數會編不過;浮點字面值由規則排除,浮點變數排除不了。②`until` 只有整數與字元有,換成 `..` 一定有。③賦值刪掉後,延後初始化的區域變數(`val x: Int` 下一行 `x = 1`)讀它時編不過。④`.sorted()` 接在 `Set` 上回 `List`,拿掉後變回 `Set`,後面用索引或存進 `List` 型別時編不過;`.distinct()` 接在陣列上同理。⑤RET 換掉回傳值後,原本只在回傳運算式裡用到的區域變數變成沒人用,只有警告;專案開 `allWarningsAsErrors` 時編不過。⑥不帶大括號的跳出換成 `Unit`,會不會出「沒用到的運算式」警告沒有實編過(本機沒有 kotlinc),範圍 7 實編確認。⑦早退 if 的排除是近似:條件裡呼叫了帶 contract 的自訂函式(`if (!isValid(x)) return` 之後智慧轉型)排除不到。編不過的都落成跑不出結果、人可判不適用,RETIRE-IF 的「跑不出結果超過一半」會撤列。
- 等價存活:RET 在函式從來沒被規格測試跑到時必定存活(這正是要問的「這個結果有沒有需求在檢查」,但量會多;路線總圖第 1 步上線後改先看覆蓋,見 REVISIT);`_state.value = 同一個值`(StateFlow 相同值不重送)刪掉等價;`.distinct()`、`.sorted()` 在測試資料本來就不重複或已排序時存活——這些存活正是要逼作者補「重複資料」「亂序」的測試,不算白擋。
- 掛住:刪掉 `while (true)` 裡唯一的 `break` 會讓迴圈不停,測試逾時落成跑不出結果;這批沒有排除(`while (true)` 在 Android 程式裡少見),REVISIT 看「測試掛住」的筆數。
- 推送負擔:`return`、賦值、`..` 很常見,有選擇點的行會變多;範圍 7 用實測門檻決定每一列上不上線。
- 同一行重疊:`if (n > 100) return 100` 同一行有 ROR(`>`)、UOI 與這批的跳出,一行只挑一個(論文 4.1);`return s?.trim()` 同一行有第二批 C-33(`?.`)、RET-6 與 `.trim()`。處置以行為單位,不重複要求。
- 輸出量與時間:往上找超過兩層的 RET、跳出、賦值規則都外包雙重否定(範圍 2 的實測數字);樣本掃描時間 0.08 秒(1000 行的合成輸入)、巢狀 300 層 0.79 秒。
- 併發與交易:已排除:沿用前三批,單人單機依序操作。
- 已排除:金流:只改型錄、規則與樣本,不碰付款或金額計算
- 已排除:對外送出:掃描與殺傷力都在本機跑,不對外送任何資料
- 已排除:不可逆:治理帳照舊逐筆追加,撤列後新推送不再產那一列的壞法,已記的處置照第一版以行為單位續用
- 守衛面:不排除——新列會改推送前選擇點那一道挑出的壞法,所以走設計審;S7 守住第一版六支樣本檔裡不含第二到四批語法的行,挑選結果不變;型錄、規則、樣本任一項半套會讓整張表判壞、所有 Kotlin 推送被擋,〈回退〉要一次做齊並先跑 check.py。
