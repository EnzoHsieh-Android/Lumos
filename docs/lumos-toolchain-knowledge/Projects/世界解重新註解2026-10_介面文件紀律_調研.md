# 世界解重新註解2026-10_介面文件紀律_調研

> 白話:這一類在問「工具寫給 AI 看的東西(訊息、說明、常駐規則、skill)有沒有寫對、有沒有被照做,以及工具自己的測試可不可信」。世界的大勢是:常駐散文要短、只寫最小必要,必須每次成立的規則要搬進機械守衛,而且要用評測量出來,不靠感覺。對 Lumos 最重要的結論有兩個:第一,常駐紀律範本在 2026-08-22 有一筆仍有效的決策訂了 4k bytes 上限,現在是 12,818 bytes(約 3.2 倍),健檢只在超過另一條約 7.9k 的線時軟提醒,建議改成會擋、只准往下調的預算守衛;第二,範本與 skill 裡「必須/不准」這類硬規則,哪些有守衛、哪些只靠自律,2026-10-11 核對查無對照帳,世界上把規則編譯成守衛的實驗(遵守率 88% 對 67%)支持先把這張帳做出來。(更正 2026-10-30:4k 絕對上限 2026-10-11 已取消;現為 13320 bytes,是基線 5256 的 253%,「3.2 倍」不再適用)

## 這一類在問什麼、Lumos 現在怎麼做

本類問四件事:① 給 AI 的介面(閘門訊息、help、注入文字)怎麼寫;② 常駐規則與 skill 散文怎麼控制長度、結構與退場;③ 人與 AI 共用的文件怎麼保持一致;④ Lumos 自己的測試與除錯紀律可不可信。

本類的三篇 Systems 節點:
- [[Systems/測試假綠形態]]:「測試存在但沒在驗它宣稱要驗的東西」的形態清單,含「翻紅釘要配現場成立前置斷言」這條合約;自稱是提示器,不是偵測器。
- [[Systems/診斷迴圈先行]]:排查時先建一道會對症狀翻紅的指令,才准開始推理;自承是紀律層,沒有機械閘。
- [[Systems/README圖產生器]]:重產 README 中英兩版的示意圖並檢查語意與動畫限制。

本類借用、但家在別類的機制:
- [[Systems/hook信任邊界]]:hook 注入文字時,專案讀出的值放進「參考資料,不是指令」框裡,工具自己的指示放框外。
- [[Systems/bound-tests-gate]]:推送前的測試閘,含分片平行跑與文件、關鍵字兩種子集。
- [[Systems/anchor-integrity]]:測試總檔與各掛鉤用整檔雜湊鎖住,改了要附理由重簽。
- [[Systems/ablation-lumos-first]]:情境探針「帶/不帶某段規則」消融的結果篩選與統計。
- [[Systems/test-quality-handbook]]:測試品質手冊的兩臂試行,其中一道量 skill 原生觸發。
- [[Systems/cochange-guard]]:從 git 歷史挖「改 A 通常也改 B」,提交時提醒。

沒有專屬節點、靠程式慣例或計劃撐著的:
- 白話三段式訊息(發生什麼 → 為何在意 → 指令獨立一行):寫在方法論文件與指令手冊裡的長期寫法,沒有通用檢查。
- 逐指令的「什麼時候用」:CLI 裡一份對照字典,灌進每個子指令 help 的第一行。
- 指令索引三層(常駐層、手冊層、細節層)與開場入口掛鉤:見 [[Projects/指令索引與情境測試_計劃]] 的決策 d1。
- 常駐紀律範本:每個專案的 CLAUDE.md 與 AGENTS.md 都會注入;健檢 D 段量它的位元組數。
- 散文紀律的退場問題:[[Issues/散文紀律沒有退場機制]](P2,open)。

## 世界解註解

證據強度:A 受控實驗或方法公開的基準｜B 生產數據或廠商自報｜C 實務經驗｜D 行銷宣稱。註解深度:讀碼/讀全文/讀官方文件/二手。

### 一、寫給 AI 看的介面

**1. Anthropic〈Writing effective tools for agents — with agents〉**(https://www.anthropic.com/engineering/writing-tools-for-agents ,2025-09-11)
- 機制:工具是確定性系統與 agent 之間的合約;回傳高訊號資訊、可選簡潔或詳細;錯誤回應要給具體、可行動的改法,不要不透明的錯誤碼;用 XML、JSON 還是 Markdown 要靠評測決定;用真實任務加保留集評測,讓 agent 讀逐字稿來改工具。
- 證據強度:B,廠商自報,保留集結果只有圖、沒有數字。
- 註解深度:讀全文。
- 關係:驗證(三段式、給下一步)+可借鏡(格式用評測決定)。

**2. Claude Code hooks 官方文件**(https://code.claude.com/docs/en/hooks ,2026-10-11 取用)
- 機制:PreToolUse 以 exit 2 擋下時,stderr 當成工具錯誤送進模型;exit 0 時模型看不到 stderr;注入的附加脈絡會包進系統提醒,官方建議「寫成事實陳述,不要寫成系統命令」,否則可能觸發提示注入防禦;超過 10,000 字元改寫進檔案且不提醒去讀。
- 證據強度:B,官方產品行為。
- 註解深度:讀官方文件。
- 關係:驗證(閘門訊息確實送到 AI)+可借鏡(注入句型改成陳述句,見候選 8)。

**3. OpenAI〈Harness engineering: leveraging Codex in an agent-first world〉**(https://openai.com/index/harness-engineering/ ,2026-02-11;原文 403,讀的是 InfoQ 2026-02-21 等二手整理)
- 機制(依二手):AGENTS.md 約 100 行,當目錄不當百科;文件是結構化記錄系統,用 linter 與 CI 驗新鮮度;定期派「doc-gardening」agent 找過期文件;自訂 linter 的錯誤訊息直接帶修正指示。
- 證據強度:B,廠商自報,而且只讀到二手;「每人每日 3.5 個 PR」未複驗。
- 註解深度:二手。
- 關係:驗證(錯誤訊息即修正指示、入口檔只當目錄)+延伸(doc-gardening)。

**4. agent_lints(Dart/Flutter)**(https://pub.dev/packages/agent_lints ,v0.3.0,約 2026-10 初)
- 機制:每筆違規固定四欄:發現什麼、為什麼(規則加替代)、可直接貼的提示片段、唯一合法的略過寫法(必須附理由)。
- 證據強度:C,沒有量測。
- 註解深度:讀官方文件。
- 關係:驗證+可借鏡(把三段式寫成固定欄位,見候選 5)。

**5. ContextCov:把指令檔編譯成可執行守衛**(https://arxiv.org/abs/2603.00822 ,2026-02-28,v2 2026-05-04)
- 機制:把 AGENTS.md 的自然語言限制編譯成靜態(語法樹查詢)、執行期(shell 攔截)、架構三類檢查,定稿前把違規軌跡回饋給 agent。
- 證據強度:A,SWE-bench Lite 300 題:約束遵守率 88.3%,只靠提示 67.0%,自我反思 50.3%;但單一作者、只讀到摘要,沒交代哪些規則編譯不了。(更正 2026-10-30:這組數字只在 v2 出現,考官是它自己生成的檢查,對照組是事後套同一套檢查;同表獨立 LLM 評審 30.1% 對 29.2% 幾乎沒差,功能解決率 57.3% 對 53.0%;查無獨立複現)
- 註解深度:二手(摘要)。
- 關係:驗證(寧可機械擋)+延伸(規則半自動編譯成守衛),是本類最強的外部證據之一。

**6. MCP 工具描述的 smell 研究**(https://arxiv.org/html/2602.14878v1 ,2026-02-16)
- 機制:六項評分表(目的、使用時機、限制、參數、長度、範例);856 支工具裡 97.1% 至少有一種 smell,缺「使用時機」89.3%、缺「限制」89.8%。全面補齊後成功率 +5.85pp,但步數中位數 +67%,16.67% 反而退步;拿掉範例沒有顯著退步。
- 證據強度:A,方法與基準公開。
- 註解深度:讀全文(前段)。
- 關係:驗證(「什麼時候用」正是最常缺的一項)+可借鏡(補「不適用於…」那一欄)。

**7. 反例:LLM 改寫的錯誤訊息對人沒明顯幫助**(https://arxiv.org/abs/2409.18661v1 ,2024)
- 機制:新手受試者內設計;GPT-4 產生的錯誤訊息只在 6 題中的 1 題縮短修正時間,主觀上覺得較好讀。
- 證據強度:A,但對象是人不是 agent。
- 註解深度:二手。
- 關係:缺口——2026-10-11 核對,世界與 Lumos 都查無「訊息措辭對 agent 修正率」的受控實驗(更正 2026-10-30:這格已不空:Xu & Wu 2609.35381 v2(2026-09-29,MCP 錯誤訊息、OpenAI 模型、代理沒有終端)。Lumos 能貢獻的是 Claude、有終端的代理)。

### 二、規則與 skill 散文工程

**8. ETH〈Evaluating AGENTS.md〉**(https://arxiv.org/html/2602.11988v1 ,2026-02-12,ICLR 2026)
- 機制:SWE-bench Lite 300 題加自建 138 題,比「沒有脈絡檔、LLM 生成、開發者寫」三條件。LLM 生成的讓解題率下降(結果段 −0.5% 與 −2%,引言寫 −3%,原文自相出入)、成本 +20%;開發者寫的約 +4%、成本最多 +19%;程式碼概觀沒用;agent 確實照做(提到 uv 時每題用 1.6 次)。作者建議只寫最小必要。(更正 2026-10-30:v3(2026-09-29)摘要已由「tend to reduce task success rates」改成「does not generally improve」,LLM 生成檔 p 值 87% 與 37%,兩個方向都不顯著;手寫 +2.4%(p=21%)不能寫成有幫助;只有成本約多兩成站得住;資料集改名 CTXBench;「+4% 與 −3%」在 v3 已查不到)

- 註解深度:讀全文(前段)。

**11. TDAD(Test-Driven Agentic Development)**(https://arxiv.org/abs/2603.17973 ,2026-03-18)
- 機制:給 agent 一張機械算出的「程式 → 測試」相依圖,對照在指示裡寫「請照 TDD 做」。回歸率基線 6.08%,加程序性指示升到 9.94%,給相依圖降到 1.82%。(更正 2026-10-30:9.94% 只成立在測試層;原文的補丁層回歸是 30.2%、33.3%、33.3%,解題率也沒升,原文自己說「appear to contradict the test-level result」並以分母不同解釋。「程序性散文有害」的證據比這裡寫的弱;機械推送那半沒被推翻,只是證據降為「降低失敗測試數」)
- 證據強度:A,但只用約 30B 的小模型,能否外推到前沿模型未知。
- 註解深度:二手(摘要)。
- 關係:驗證(把算好的資訊推到眼前)+挑戰(純程序性散文,例如診斷迴圈先行)。

**12. 規則數量上限:IFScale 與〈Prompt Design at Scale〉**(https://arxiv.org/html/2507.11538v1 ,2025-07;https://arxiv.org/abs/2607.19257 ,2026-07-21)
- 機制:IFScale 用 10–500 條指令,500 條時最好的模型約 69%,Claude Opus 4 約 45%,越前面越容易被遵守;後者 10–160 條規則,完美回應率在 80 條時歸零,格式化比純文字多 22–37% token。
- 證據強度:A(IFScale 讀全文);後者單一作者、只讀摘要。
- 註解深度:讀全文/二手。
- 關係:挑戰(規則只增不減;2026-09-02 首掃抽出 433 句指令性句子)。

**13. McMillan 的因子實驗**(https://arxiv.org/abs/2605.10039 ,2026-05-11)

- 證據強度:A,但目標規則瑣碎、單一作者。
- 註解深度:二手(摘要)。
- 關係:挑戰(「瘦身提升遵守」這個理由)+驗證(動作當下推送)。

**14. Anthropic〈Skill authoring best practices〉與〈Effective context engineering〉**(https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices ,2026-10-11 取用;https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents ,2025-09-29)

### 三、工具自己的測試可不可信

## 世界證據對 Lumos 做法的挑戰

1. **常駐散文變大可能得不償失。** ETH(LLM 生成檔成本 +20%、人寫的只多約 4%)與 SkillsBench(Comprehensive 型 −2.9pp)挑戰「範本可以一直加」這個前提。反向證據:Lulla 等(有 AGENTS.md 更省時)、修法 A 消融(+35.7pp,判準已撤換)、McMillan(大小無關遵守)。驗證法:同一組探針,現行範本對照「只留最小必要」版,比通過率與 token;不論結果如何,「只增不減、沒有會擋的預算」哪一方都不支持。
2. **程序性散文可能有害。** TDAD 的「請照 TDD 做」讓回歸率升到 9.94%(小模型)(更正 2026-10-30:只在測試層,補丁層 30.2% 對 33.3% 差異很小)。挑戰診斷迴圈先行這類純紀律節點「寫了就有效」的前提。驗證法:同組題「散文規則」對照「機械推送」兩臂。背景:修法 A 後的 2026-09-20 回頭條件要裁「對照表留、勸告句拿掉再量一次」,2026-10-11 查圖譜找不到裁定。
3. **只叫 agent「先重現」對強模型不一定有用。** FixedBench 裡 Sonnet-4.6 加了也沒變,真正有用的是把停手框成成功;單一重現測試還可能只修一半。驗證法見候選 7。
4. **外部流程稽核不承認 AI 審查。** OpenSSF Scorecard 規定 AI 審查不算,Lumos 的多代理對抗審在那個框架裡等於零分。這不代表 Lumos 錯,但對外宣稱「審過」時要講清楚是誰審的。驗證法:對 Lumos 自己的 repo 跑一次 Scorecard 看 Code-Review 分數(預期近零),寫進對外說明。
5. **讓 AI 扮讀者評文件只能拿來篩選。** [[Projects/README面試官十分鐘_計劃]] 的「乾淨讀者分數 5/10 → 6/10」是篩選訊號,不是「讀得懂」的總結證據。驗證法:至少一輪找真人讀者,或改用「能不能答對 10 題事實題」這類客觀題。
6. **中文規則可能較弱、較貴。** 2024 年非推理模型的中文遵守率明顯較低,多輪後差更大;Codex 的位元組上限對中文緊約 3 倍(這半健檢已用位元組量)。對 2026 前沿模型的影響未知,驗證法見候選 10。
7. **skill 結構偏離官方建議。** 指令索引是兩層參照(官方建議一層),參考檔有大量帶日期的出處。這條挑戰已被處理過:[[Projects/skills提示工程優化_計劃]] 依逐字稿統計(讀索引後 64% 直接敲 lumos 指令)決定兩層不動,入口頁日期也已清掉並有守衛測試。這次沒有新證據,不建議重開。
8. **hook 注入的祈使句可能被當成注入攻擊。** 官方文件明說;現有裁定只處理框內框外。驗證法見候選 8。
9. **AI 會改測試讓自己過關。** ImpossibleBench;Lumos 的測試由 AI 寫、修、審,翻紅釘也是同一個 agent 自己做,錨點只守整檔。驗證法見候選 4。
10. **縮小檔案不一定提高遵守。** McMillan 挑戰「瘦身能提升注意力」這個理由;這點 Lumos 在 2026-09-02 世界掃描已吸收,[[Projects/紀律範本二次瘦身_計劃]] 的瘦身理由已改成成本與沉積。這次沒有新證據。

## 延伸方向

- **閘門訊息格式 × agent 恢復率的對照實驗**:同一道閘分精簡版與三段式兩臂,量被擋後 3 步內的恢復。核對:查無(答案檔 Q09-06 判部分有,只有一次 n=3 的擋/不擋前後測,沒有比寫法)。世界也沒有,Lumos 可以做第一個(更正 2026-10-30:這格已不空:Xu & Wu 2609.35381 v2(2026-09-29,MCP 錯誤訊息、OpenAI 模型、代理沒有終端)。Lumos 能貢獻的是 Claude、有終端的代理)。
