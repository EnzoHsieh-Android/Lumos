# 代碼審通過前自動跑選擇點_計劃

## 白話

改動選擇點(Kotlin 改動行上挑壞寫法、跑計劃條款綁的測試,壞法活下來就要處置)現在只在推送前那一道機械判定;`lumos choice-kill` 要編排者自己記得在代碼審記通過之前跑。忘了跑,推送時才被擋——這時才補放行檔或改計劃,已經記好的代碼審留痕會失效,整個要重跑。這份計劃讓 `lumos code-loop pass`(代碼審最後一關)在記通過之前,用推送前那一圈的同一支判定快速看一次(不跑測試):有行缺紀錄、存活沒處置,就不記通過,當場印出要跑的 `choice-kill` 與處置指令。

WHY:`code-loop pass` 記通過之前,在新增告警與表態兩道之後多一道「選擇點預判」:不跑測試,只用推送前那一圈判一次,有擋下原因就不記通過並指路 [出處:2026-11-21 使用者要 choice-kill 在代碼審最後一關自動觸發;設計審 r1 指出既有方針「會跑測試的閘掛在擋的路徑、不掛記錄的路徑」與 pass 內跑 choice-kill 最壞 20 分鐘以上後,使用者裁「pass 只預判不跑測試」] [因:選擇點的處置(放行檔、situation-rule 改計劃、補測試)都會改非簿記檔,必須在記通過之前做;只靠推送前那道擋,發現時已經太晚;預判只要幾秒,不違反「跑測試不掛 pass」] [不選:pass 內自動跑 choice-kill(違反既有方針、最壞 20 分鐘以上、對話裡會被逾時砍、使用者 2026-11-21 裁不走);推送前自動跑(存活處置時已記過通過,陷阱只解一半);pass 時另寫一套判定(第二種做法);在 pass 自動處置存活(處置是人裁)]
PRIOR-ART: Google〈Practical Mutation Testing at Scale〉把變異結果放在 code review 當下呈現,讓審查者在合併前處理,而不是事後(https://arxiv.org/pdf/2102.11378 2.3、5);本 repo `code-loop pass` 已經在記通過前自動跑新增告警與表態兩道([[Projects/Android寫法寫完當下自動檢查_計劃]] 範圍 2,`_codeloop_pass_mech`;那兩道不跑測試,跑測試的受波及合約測試閘照方針掛在 check),新的一道照同形狀接在後面;判定直接重用推送前那一圈 `_choice_push_round`,多一個「場合」參數(推送或 pass),跟 `_codeloop_guard_verdict` 的 `mech_only` 同一種「同一支判定、模式參數分流」寫法。
RETIRE-IF: 上線兩個月後,`site` 為 pass 的選擇點擋下是 0 筆(pass 這道一次都沒有提早抓到東西),或使用者回報 pass 擋得多、改走 `skip`——就把這一道拿掉,回到只靠推送前那道。

## 舊否決比對

- [[Projects/留痕驗過審查_計劃]] 否決過「pass 內重跑處置閘」(要自帶 spec 路徑、多一條判定入口)。這次不重跑處置閘;跑的是選擇點判定,而且直接呼叫推送前那一圈 `_choice_push_round`,不新增判定入口。
- [[Systems/pitfalls-code-loop]] 記新增告警與表態兩道進 pass 時,否決過「另寫一支共用判定(兩套判法會漂開)」——這次照那次的做法,重用推送前同一支。
- 受波及合約測試閘([[Systems/bound-tests-gate]])定下「會跑測試的閘掛在擋的路徑(check)、不掛記錄的路徑(pass)」,理由是測試結果隨提交變。設計審 r1 撞到這條,使用者 2026-11-21 裁照方針走:pass 這道只預判、不跑測試。

## 範圍

- 做:①`code-loop pass` 在新增告警與表態兩道之後、留痕驗證之前多一道「選擇點預判」(`_codeloop_pass_gate` 裡,跟那兩道一樣不被「沒有審查帳」「light」提早返回跳過);②判法重用 `_choice_push_round`,多一個場合參數 `site`(預設 `push`,行為不變;pass 傳 `pass`),它決定三件事:帳從哪讀、事件記在哪個場合、去重分不分場合;訊息照推送前原樣,pass 只補自己的出口;③有擋下原因 → 不記通過,印同一段原因與處置指示,治理帳記一筆 `code-loop-pass` 擋下(`blocks` 帶 `choice`);④`gov --stats` 的選擇點段把「被擋筆數」分出 pass 與推送;⑤手冊與筆記同步。
- 不做:pass 不跑 `choice-kill`、不跑任何測試;不改判定規則本身(原因、回報上限、生效日、乾節點、只看 Kotlin);推送前那一道行為不變(`site` 預設值);不自動處置存活;不自動提交帳;不改 standard、light 分級要不要跑 `pass`(它們不一定走到這一關,推送前那道照舊兜底);不新增略過旗標。

## 做法

- **接點**:`_codeloop_pass_gate` 裡,`_codeloop_pass_mech` 回 True 之後、`_codeloop_pass_verify` 之前,呼叫新的 `_codeloop_pass_choice(repo_root, head_sha, branch)`;回 False 時 gate 回「不放行」。預判只讀帳與掃語法樹,不跑測試,所以排在留痕驗證之前不會讓人白等。
- **範圍**:pass 照推送前掛鉤會給的輸入模擬一次推送,交給推送前那一圈同一支 `_choice_push_range`/`_push_range_start` 算起點,不另算:頂端=目前分支頂端;被推 ref=`refs/heads/<目前分支>`;遠端=`_lens_default_remote`(同 `_choice_range` 的取法);遠端舊值=本機追蹤的 `refs/remotes/<遠端>/<分支>`,沒有就當新分支首推(全零)。於是直推主線(遠端舊值..頂端)、已推過的分支(增量)、新分支首推(分岔點起)三種情況都跟推送前那道同一段。限制:本機追蹤的遠端分支沒 fetch 時可能比遠端舊,範圍會多看幾個已推過的提交(多擋,不會少擋)。分支名用共用的 `_redbase_branch_name`(不用 `symbolic-ref --short`:有同名 tag 時會回 `heads/<名>`)。detached HEAD(沒有分支名)→ 印一行「沒有分支,選擇點留給推送前判」、放行;沒有設定遠端(`_lens_default_remote` 回空)同樣印一行、放行。
- **先看是不是 Kotlin 專案**:`_choice_push_has_kotlin(rr)` 不成立(專案沒有 kotlin-junit 平台)→ 這一道直接放行、不印字,不做任何 git 範圍運算。
- **不用圖譜物件**:`_choice_push_round` 一族只用 repo 根(`env` 參數沒有被讀),pass 傳 `None`。沒有圖譜資料夾的專案,`_choice_requirement` 判不了要不要求(樹裡沒有圖譜目錄),照那一圈的規則只提醒、放行;治理帳不存在時事件也不寫。
- **場合參數 `site`**:從 `_choice_push_round` 穿到 `_choice_push_scan`、`_choice_push_unverified`、`_choice_push_part_unverified`、`_choice_push_read`、`_choice_push_ledger`、`_choice_push_verdict`、`_choice_push_event`。`site="pass"` 只改三件事:
  - 帳:`_choice_push_ledger` 讀工作目錄那一份(`_gov_rows_at` 的 rev=None 模式),因為編排者剛跑的 `choice-kill` 紀錄是簿記檔、pass 時還沒提交。放行檔、守的測試、計劃照舊從頂端提交讀。
  - 事件:擋下與算不出來照舊記 gate `choice-kill` 的 blocked/unverified,多一個欄位 `site: "pass"`(推送那邊不帶);去重鍵改成 kind、頂端、原因清單加 `site`,pass 與推送在同一頂端各擋一次就各記一筆。欄位名用 `site` 不用 `origin`、`via`:`origin` 在放行檔表示誰放行(人或 AI),`via` 在 choice-kill 事件表示判定怎麼來(跑出來或人裁),這裡要的是「在哪一關擋下」。
  - 訊息:不改字樣,照推送前那一段原樣印(同 `_codeloop_pass_mech`「每道印推送前同一段擋下訊息,再印 pass 自己的出口」的做法),最後補一句 pass 的出口 `_CHOICE_PASS_TAIL`:這是 pass 預判、缺紀錄或帳不在先跑 `lumos choice-kill`(紀錄不用先提交)再 pass、其他原因照上面處置、放行檔與計劃與補的測試要先提交才算、表態擋下就 `--carry` 重答、choice-kill 紀錄跟代碼審帳本一起提交。
- **擋下**:`_choice_push_round` 回的清單不空 → 印出來、再印 `_CHOICE_PASS_TAIL`,記 `code-loop-pass` 擋下(`blocks` 帶 `choice`,跟那兩道同形狀)。`choice` 只出現在 pass 的擋下事件,不是 `code-loop check` 的 reason_kind;實作時確認推送前掛鉤的原因對照表測試(`t_prepush_cl_reason_table_matches_lumos`)掃的範圍,要列入就照它補。其餘提早返回全照那一圈:生效日(當天就要判)、要不要求、型錄缺檔只提醒、型錄表壞擋、ast-grep 不在或算不出來只提醒、無規格擋、只能人驗只提醒。
- **統計**:`gov --stats` 讀帳時,choice-kill 那一列的欄位白名單(`_gov_row` 的 `ck`)加上 `site`;選擇點段原本的「推送被擋 N 筆」改成「被擋 N 筆(推送 X、pass 預判 Y)」(數 `site == "pass"` 的 blocked;舊帳沒有這欄的都算推送)。

## 驗收條款

- [S1] 當生效日已過、範圍內有 Kotlin 改動行有選擇點且碰到進行中計劃、帳上沒有紀錄時,`code-loop pass` 應 以 rc 2 不記通過,印出推送前同一段訊息與 pass 的出口(先跑 `lumos choice-kill`、紀錄不用先提交、放行檔與計劃要先提交才算),治理帳多一筆 `code-loop-pass` 擋下(`blocks` 含 `choice`)與一筆 gate `choice-kill` blocked(`site` 是 pass),而且不跑任何測試 [test:t_codeloop_pass_choice_blocks]
- [S2] 當編排者照指示跑完 `choice-kill`、壞法都被殺掉、紀錄還沒提交時,`code-loop pass` 應 讀工作目錄的帳判過、照常記通過;對同一頂端跑推送前那一道(紀錄沒提交) 應 照舊擋缺紀錄 [test:t_codeloop_pass_choice_blocks]

- [S5] 當 ast-grep 不在 PATH 時,`code-loop pass` 應 只提醒、照常記通過 [test:t_codeloop_pass_choice_skips]

- [S10] 當直接在主線上提交、還沒推(本機追蹤的遠端主線比頂端舊)、新提交有缺紀錄的選擇點時,`code-loop pass` 應 照推送前同一段範圍擋下;已推到頂端、沒有新提交時,`code-loop pass` 應 照常記通過(跟推送前增量同一段,範圍是空的) [test:t_codeloop_pass_choice_range]

## 回退

- 把 `_codeloop_pass_gate` 呼叫 `_codeloop_pass_choice` 那一行拿掉,`site` 參數留著(預設值等於推送前的行為),統計那一句照留(沒有 pass 的事件就印 0);手冊還原。推送前那一道的行為沒變,回退不影響任何凍結判定。

## 實務隱患

已排除:金流:只改代碼審記通過前的檢查,不碰付款
已排除:對外送出:不連網、不寄送;pass 這道不跑測試
已排除:不可逆:擋下時不寫留痕、不改程式;只寫治理帳(簿記檔)
- 守衛面:`code-loop pass` 是代碼審留痕的寫入口,多一道會擋的檢查。擋錯的代價是 pass 記不進去、要處置或跑 choice-kill;防線:判定跟推送前那道同一支函式,範圍照推送前掛鉤的輸入模擬(同一支起點函式;本機追蹤分支過舊時多擋不少擋),工具沒裝或算不出來只提醒,生效日前不判。
- 耗時:預判只掃語法樹與讀帳,不跑測試;掃描沿用推送前那道的時限(`_CHOICE_PICK_BUDGET` 等),這次沒另外量 pass 時的耗時。真正耗時的 choice-kill 由編排者照指示另跑,可放背景。
- 讀工作目錄的帳:pass 時工作目錄的治理帳可能有別的未提交簿記事件,判定只取 gate `choice-kill` 的列(`_gov_rows_at` 的篩選),其他不看;讀不出來的壞行由 `_gov_rows_at` 先丟掉,型別不對的列再由 `_gov_event_types_ok` 略過。
- 審過之後的修補:存活的處置(補測試、改計劃)發生在代碼審之後、pass 之前,這段改動沒有被審查席看過;這跟現在推送前被擋再處置一樣,pass 只是把時間點提前。處置提交後表態那道綁的提交變了,第二次 pass 可能先被表態擋,要用 `--carry` 重答(擋下訊息有寫)。
- 測試環境沒裝(Gradle、JDK):choice-kill 會判「跑不出結果」,pass 預判照擋;出路照推送前那道:修環境重跑,或 `lint-waive choice:… 不適用`。
- 併發與交易:單人依序操作,不考慮兩個程序同時寫帳。
