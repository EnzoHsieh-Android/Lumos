# 探針設定指紋_計劃

> 白話:情境探針(在凍結副本開 headless 會談,看 AI 有沒有照規矩用 lumos)跑的時候,會載入跑探針那台機器的全部使用者層設定——外掛、skill、MCP 伺服器、輸出風格、SessionStart 掛鉤。換一台機器或多裝一個外掛,通過率就可能變,但結果裡沒有任何紀錄看得出這場是在什麼設定下跑的。這篇讓每場探針記下「實際載入了什麼」的指紋,週抽歷史也記下這批用了哪幾個指紋,之後比較不同週的通過率時才分得出是規矩變了還是環境變了。來源是世界解總覽〈跨類優先順序〉第 1 名的後半(前半「副本遮題庫」2026-10-11 已做)。

PRIOR-ART: Claude Code 的 `--output-format stream-json` 第一批事件裡有 `system/init`(列出實際載入的工具、外掛與版本、skill、MCP 伺服器、輸出風格、Claude Code 版本)與每個 SessionStart 掛鉤的 `system/hook_started`;探針本來就收這份輸出,直接從裡面取,不另讀設定檔(設定檔寫了不代表真的載入),也不多花一次模型呼叫。評測界的做法是把評測環境版本跟分數一起記(例:HELM、lm-eval-harness 在結果裡記模型與任務版本),這裡照搬「環境指紋跟分數同列」。
RETIRE-IF: 探針改成在乾淨的使用者層(例如隔離 HOME 或 `--setting-sources` 只留專案層)跑、使用者層不再載入任何外掛與 skill 之後,指紋只剩一種值,這欄就沒有分辨力,可以拿掉;或連續 12 週週抽歷史的指紋都只有一種、也沒有人拿它判讀過任何一次通過率變化。

## 實測(2026-10-13)

- 本機跑一次 `claude -p … --output-format stream-json --verbose`:`system/init` 事件列出 Claude Code 2.1.296、12 個外掛(含版本)、67 個 skill、8 個 MCP 伺服器、輸出風格「Colleague plain」;另有一筆 SessionStart 的 `hook_started`,而且是整段輸出的第一行、在 `system/init` 之前(所以「只算 init 之前的掛鉤」不會漏掉啟動掛鉤)。也就是說探針受測會談帶著使用者自己的輸出風格與全部外掛在跑。
- 同一事件裡也有每場都會變的欄位(session_id、uuid、cwd、memory_paths、messaging_socket_path),不能進指紋。

## 範圍

- 只記錄,不隔離:不改探針載入什麼設定,也不改判分。隔離使用者層是另一件事(會改到探針量的東西本身),要先有這把尺才看得出隔離前後差多少。
- 只做 Claude 執行器;Codex 的 `codex exec --json` 沒有對應的初始化事件,結果記「取不到」(2026-10-11 使用者裁定 Codex 先不管)。
- git 歷史仍翻得到題庫那一半不在本篇,留在 `Systems/codex-harness` 既有的回頭條件由人裁。

## 做法

- 新函式從 stream-json 各行取出 `system/init` 與 `system/hook_started`,留穩定欄位:Claude Code 版本、模型、權限模式、輸出風格、外掛(名稱@版本)、skill 名、MCP 伺服器名、代理類型名、斜線指令名、SessionStart 掛鉤名(只算 init 之前、去重:會談中途壓縮再觸發的不是啟動時載入的);工具清單不進指紋(題目標 allow_agent 會多開 Agent,同一週會有兩種工具清單,MCP 帶來的工具由 MCP 伺服器名涵蓋);欄位寫了卻不是清單就當空的並記在摘要的 `bad_fields`,取指紋任何意外都退成 null 並寫原因,不讓整場被記成儀器例外;排序後做成 JSON,算 SHA-256 取前 12 碼當指紋。每場結果多兩欄:`env_fp`(指紋)與 `env`(上面那些欄位的摘要:版本、輸出風格、外掛清單、各類數量)。找不到初始化事件就記 `env_fp: null` 與原因。
- 週抽歷史(每週一列)多一欄 `env_fps`:這批有效場次出現過的指紋與各幾場。同一批出現兩種以上「真的」指紋時多帶 `env_mixed: true`(取不到的場次照樣記在 `null` 那一格,但不算一種環境)。
- 探針的主函式已經超過複雜度上限(見 [[Issues/探針與消融腳本函式複雜度超標]]),新邏輯一律放在獨立小函式,`run_one` 與 `history_record` 只各加一兩行呼叫。

## 驗收條款

- [S1] 當 stream-json 輸出含 `system/init` 時,指紋 應 只由穩定欄位決定:同樣的外掛、skill、版本但 session_id、uuid、cwd、memory_paths 或工具清單不同、或 init 之後再出現 SessionStart 掛鉤的兩份輸出,指紋 應 相同;多一個外掛或外掛版本不同、輸出風格、skill、MCP 伺服器、模型、Claude Code 版本或啟動時的 SessionStart 掛鉤不同時,指紋 應 不同 [test:t_probe_env_fingerprint_stable_fields]
- [S2] 當 stream-json 輸出沒有 `system/init`(例如逾時前什麼都沒印、或是 Codex 執行器)時,結果的 `env_fp` 應 是 null 並帶原因,探針 應 照常判分、不丟例外;init 的清單欄位型別不對時 應 當空的照算指紋並記在 `bad_fields`,算雜湊出錯時 應 退成 null 並寫明例外種類,夾一行解析不了的 JSON 時 應 照算指紋 [test:t_probe_env_fingerprint_missing_init]
- [S3] 當一批結果的有效場次出現兩種指紋時,週抽歷史那一列 應 帶 `env_fps`(各指紋與場數)與 `env_mixed: true`;只有一種真指紋(可加取不到的場次)時 應 不帶 `env_mixed`;被排除的場次(截斷、用量上限)應 不算進 `env_fps` [test:t_probe_history_records_env_fps]
- [S4] `run_one` 用假的 `claude` 指令跑一場時,回傳結果 應 帶從它輸出取出的 `env_fp` 與 `env` 摘要 [test:t_probe_run_one_records_env_fp]

## 回退

- 單一提交還原即可。新欄位只是多寫進結果檔與週抽歷史;舊版程式讀到多出的欄位不會用到,新舊歷史混在一起也不影響既有判讀(既有統計不讀這兩欄)。
- 只想停用不還原:沒有開關——它不改任何判定,停用沒有好處;真要停就還原提交。

## 實務隱患

- 指紋把 skill 與斜線指令名都算進去,使用者多裝或刪一個 skill 指紋就會變。這是刻意的:探針量的就是「AI 有沒有照規矩用 lumos」,skill 清單會直接影響它。代價是指紋變得很勤,判讀時要看 `env` 摘要裡差在哪,不能只看指紋變沒變。
- Claude Code 改版可能改掉 `system/init` 的欄位名;取不到的欄位記空、整個事件取不到記 null 與原因,不讓探針壞掉。
- 已排除:金流:不碰任何金流或扣款相關程式
- 已排除:對外送出:只在本機寫結果檔與歷史檔,不送任何東西到外部服務
- 已排除:不可逆:只多寫兩個欄位,還原提交就回到原狀;既有紀錄不改寫
- 已排除:守衛面:不改探針判分、不改週評通知條件,也不碰任何推送閘
