## 做法

### 1. 新增摘要行的指令(F8、B6、W8)

現況:`summary-line` 只能換或刪一行裡的一段,新片段不准含換行;新開節點的骨架只有四個空前綴行,要多寫幾條 RULE 只能手改開頭欄位,跟紀律「開頭欄位用指令改」打架。2026-10-06 那份計劃因「rtb 那輪插行 0 次」不做插行;這次示範兩個代理都踩到,使用者裁定加(d1)。

做法:新子命令 `lumos summary-add <節點> "<一行>" [--after "<片段>"] [--nth N] [--dry-run]`,函式 `cmd_summary_add`,跟 `cmd_summary_line` 同一支檔、同一把寫入鎖。

1. 輸入:新行去頭尾空白後不得是空的、不得含 `str.splitlines` 認得的換行類字元(同 summary-line 那條檢查,抽成一支共用);新行要以摘要前綴開頭(`SYMBOL_RE` 認得的 `WHY:`、`RULE:`、`PITFALL:`、`FACT:` 等),沒有前綴就擋(rc2)——沒前綴的行會變成不屬於任何條目的孤行,形狀與格子檢查對它都不生效(設計審 r1 正確性席 F2);摘要寫成單行值 `summary: 一句`、或這篇沒有摘要欄 → 擋(rc2),講要先改成區塊寫法(同 summary-line 不支援單行值)。
2. 去重:摘要區裡已有一行去頭尾空白後跟新行一字不差 → 印「已經有」、rc0、檔案不動(同 append 的去重語意)。
3. 位置:預設接在摘要區最後一個實體行之後;帶 `--after` 時用 summary-line 同一支定位(找不到、對到多處就擋並列候選,`--nth` 指定),插在那一條之後——那一條有續行(`_ns_summary_logical` 認得的)就插在整條之後。縮排照摘要區第一個實體行的前導空白。
4. 寫前形狀檢查(跟提交時同一套):呼叫 `_drift_fix_shape_err(root, [(新行, "summary")])`——內部就是筆記形狀擋逐行用的 `_ns_check_line` 加 `_ns_revisit_violations`;會被提交擋下的寫法(程式行號引用、沒寫來源的 FACT/FLOW/DEP、SEE 夾句子、回頭條件格式壞)在這裡就 rc2 不寫,印同一句改法。格子缺鍵用 `_ns_slot_line_problems(新行, 舊行鍵, 現在)`,「舊行鍵」照提交時的來源組:這篇在 HEAD 版本摘要裡的每一行(`_ns_slot_key`),summary-line 另加被換掉的那一行(提交時「這次刪掉的行」也算舊行)——同前綴、同文字鍵的就算舊行,改了欄位的舊行不套必有鍵,跟提交時一樣放行;不准傳 None(那會把改舊行當成新寫)。擋不擋照 `_ns_slots_mode` 讀到的專案開關:block 就 rc2 不寫、warn 寫入並印提醒、off 不看。這一道與格子都照 note_shape 總開關:off 不檢查、warn 寫入並印提醒(跟提交時一樣;drift fix 共用同一支,代碼審 r1 正3、r2 架5)。確定不是 git 專案時:summary-add 擋下(rc2,講要在 git 專案裡用);summary-line 跳過檢查、照改動前的行為寫入(不讓既有指令在非 git 退步,代碼審 r1 邊2);git 跑不起來(逾時、壞掉)不算「不是 git」,兩支都擋(代碼審 r2 安1)。
5. 寫入照 `atomic_write_verify`(驗新行在、其他行一字不動),同一次把 `updated:` 改成今天(沿用 `_summary_line_rebuild` 的改法);印新增那一行與它在第幾行,提示 `lumos lint <節點>`。`--dry-run` 只印不寫。
6. 統一規則「工具往摘要寫新句子之前先跑提交時那套形狀檢查,舊行照提交時的舊行規則」:`summary-line` 換出來的新行也跑第 4 點同一支,舊行鍵照第 4 點組(新片段給空字串、只是刪掉一段的不跑)。這是 summary-line 行為的收緊:以前寫得進去、提交才擋的,現在寫入時就擋。
7. 文件同步:指令說明字典(「什麼時候用」那張)與 argparse、`skills/lumos-project-notes/commands/03-寫回圖譜.md` 加一列、`commands/INDEX.md` 的指令清單、`skills/lumos-project-notes/SKILL.md` §3 寫回表加「摘要加一行/改一行」、頂層指令數(現在寫 91 的地方:`ARCHITECTURE.md` 第 3 節標題、同節圖裡的根節點、同節結尾那句共三處,`skills/lumos-project-notes/reference.md` 裡子命令全覽那句與介紹 `commands/INDEX.md` 是幾個指令總目錄那句共兩處;`t_docs_command_count` 會掃全部活文件,但它只認「N 個頂層命令」這類寫法,認不到 reference.md 的「N 個指令的總目錄」——這次順手把那種寫法補進守衛的比對,五處漏改哪一處它都紅)。寫入指令的列舉也要補 summary-add:`skills/lumos-project-notes/reference.md` 子命令全覽的「寫入」那串、`README.md` 講維護摘要那句、[[Systems/lumos-cli-write]] 列寫入原語的那行 KEY 與它的指令表(那行原本連 summary-line 都沒列,一起補);這幾處沒有守衛,實作時逐一改。紀律範本 `scripts/templates/graph-discipline.md` 鐵則 2 括號改成列出 `lumos set` / `append` / `summary-add` / `summary-line` / `decision-add`;改完在本 repo 跑 `lumos update` 重注入 `CLAUDE.md` 與 `AGENTS.md`(doctor Check D 守兩邊一致),照上次改範本的慣例 bump `LUMOS_VERSION`,消費專案下次 `lumos update` 帶過去(還原時版本號只能再往前 bump、不能倒回,見〈回退〉)。
8. [[Projects/改摘要單行的指令_計劃]] 正文〈範圍〉已補一句指到本篇 d1(2026-10-15 寫計劃時一起補;不改它的摘要與狀態)。

### 2. set 說明列出可改欄位(B7)

現況:`lumos set --help` 只有「什麼時候用」一句與三個位置參數;可改的欄位清單只在打錯時的擋下訊息裡(`_cmd_set_locked` 組 `SCALAR_KEYS` 與 `COND_KEYS`)。

做法:抽一支 `_set_keys_text()` 回「純量欄位:…;整欄換掉:valid_under、revalidate_when」,`set` 的 argparse 把它放進 `key` 參數的 help 與說明尾巴,擋下訊息也改呼叫它——兩處同一份,不另抄。`append` 的 `key` 參數同樣列 `LIST_KEYS`(同一個缺口,一起補)。

### 3. append 的落點寫成連結時自動改純字串(F14)

現況:`_cmd_append_locked` 對 `lands_in` 照收任何值;lint 只提醒(`_nl_rule_lands_in`),處置閘才擋(`_disposal_landing_step`)。

做法:`key == "lands_in"` 時先用既有的 `link_target` 正規化(去外層 `[[ ]]`、別名、結尾 `.md`、頭尾空白;`_cmd_append_locked` 去重本來就用它,不另寫一段);正規化後用 `_lands_in_bad` 判(lint 與處置閘同一支)——合格就照正規化後的值寫入,有改就印「已改成純字串 Systems/x(lands_in 只收這種寫法)」;仍不合格就 rc2 不寫,印跟處置閘同一句格式說明。統一規則:寫入端跑讀取端同一支判斷。

### 4. 否定現況句提醒不唸條件與時序子句(F17、W9)

**B2 改 done 後推送閘不再重跑**。現況:`_spec_gate_push_scan` 只對 `status == "doing"` 的計劃跑留痕裡的測試;照「做完再改狀態」的習慣,把狀態改成 done 跟實作同一次推送,這次推送就跳過唯一的閘。當初只看 doing 是怕放著沒人管的計劃變成擋所有人的地雷(雙向門放行 r2 簡化席)。做法:改到計劃檔本身的 done 計劃本來就在候選裡(`_spec_gate_push_candidates` 已收 `touched_plans`),擋住它的是 `_spec_gate_push_scan` 裡 `full` 的狀態條件(只認 doing)——要改的是這個條件:狀態是 done、而且這次推送範圍改到了計劃檔本身,也照跑留痕裡的測試;沒被改到的 done 計劃照舊不查,地雷顧慮不變。寬待只給推送範圍起點就已經是 done 的(起點用既有 `_range_base`,三點範圍取 merge-base;這次推送才從 doing 改成 done 的照 doing 一樣嚴,不能拿改狀態繞過),而且只寬待兩種「沒出路」:留痕的條款指紋跟現在對不上(完成後才改條款,重跑規格閘拿不到紅),或某支留痕測試名找不到(後來改名或刪了)——印一行講明原因,不做清單那道照查、其餘找得到的測試照跑、紅了照擋;讀不成文字、測試索引建不起來、門現在判成風險高(例:正文新加金流詞)三種不在寬待範圍,照 doing 擋(代碼審 r1 正1、正2、安1;r2 架1;r3 G1)。起點狀態只對這次改到的 done 候選算,merge-base 一次推送只算一次(r3 G8)。這推翻 [[Projects/雙向門放行_計劃]] 推送前只看 doing 的裁定的一部分,記為決策 d3,並在那篇正文補一句指過來。

**B3 留痕在被 gitignore 的本機帳**。2026-10-15 實測(暫存目錄造 fixture repo,docs/.gitignore 照 `init` 寫的忽略 .canary-log.jsonl):原 repo 條款測試紅 → 推送閘 rc1 擋;`git clone` 出來的乾淨 clone 同一個範圍 → rc0,一個字都不印(帳不在、`rec` 是 None、整份計劃當沒留痕跳過)。本 repo 的審查帳有進版控,所以工具鏈自己沒中;消費專案(`init` 產的)全中。做法(統一規則:推送閘要讀的留痕一律進版控的治理帳,同代碼審留痕):

- 讀:推送閘有要跑全套的候選(狀態與門都符合)時,第一次才讀治理帳、存進查表給後面的計劃共用——照 `_nogo_ctx_gov` 的接法;讀法用既有的 `_gov_vc_gate_events(root, "spec-gate")`(路徑守衛、切行、位元組先篩、帳壞回原因),再篩 `kind == "spec-gate-record"`,不另寫讀帳。治理帳讀不動 → 照審查帳讀不到的既有規矩擋下講原因(fail-closed)。兩本帳的留痕合在一起:以 token 去重,同一份計劃取 `ts` 最晚的那筆(`ts` 是帶時區的 ISO 字串,用既有 `_loop_ts_key` 比)。不是「審查帳找不到才讀」——那樣先後在兩台機器跑規格閘時,舊機器的本機帳留著舊留痕、看不到新的,會誤判過期(設計審 r1 正確性、邊界兩席)。只有沒有要跑全套的候選時才不讀,成本跟現在一樣。

**W10 同一句警告印三次**。現況:`load_platforms` 每被呼叫一次就對不存在的 root 印一次「⚠ 平台 'x' 的 root 不存在」,規格閘一次跑會呼叫三次。做法:模組層一個集合記「這次程式執行已經警告過的 (平台, root)」,同一組只印一次;所有呼叫端共用,不逐處去重。
