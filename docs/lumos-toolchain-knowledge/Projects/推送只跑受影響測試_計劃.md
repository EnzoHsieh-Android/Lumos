# 推送只跑受影響測試_計劃

> 白話:現在推一個改到程式的功能分支,本機推送前要跑完 3700 多支測試(四片同時跑,平常 5–10 分,2026-11-05 實測一次一小時以上)。這篇是兩步走的第一步,**名字沿用、內容是「推功能分支本機不跑全套」**:推功能分支時本機只跑便宜的檢查與現行的關鍵字小子集(冒煙測試,不當保證);全套照舊由 PR 的 CI 跑(PR 事件本來就一律全套),合併一律走 PR、等 PR 最新頭提交的全套綠。CI 不改。第二步(靠「每支測試上次碰過哪些函式」挑測試,讓 CI 也能少跑)另開 [[Projects/依實測覆蓋挑測試_計劃]]。使用者原話(2026-11-05):「是不是可以不要每次開發新功能就把既有的斷言全部跑過一遍?如果後續造成什麼功能壞掉,在返休就好了」;設計審 r1 指出靜態選測先天漏抓、查過世界解之後,使用者同意「兩步走」;r3 收不乾淨,使用者裁「收不乾淨的你就上網釐清方向」,查過後定成現在的形狀。這也是 [[Projects/推送與CI提速_計劃]] 留下的第二階段。

PRIOR-ART: 兩段式 CI:快的檢查每次推送跑、完整測試在要合併前跑(Mergify 兩段式 https://docs.mergify.com/merge-queue/two-step.md );pre-push 只跑快的、全套交 CI,而且掛鉤可以被繞過、CI 才是真正擋的那道(https://dev.to/jameson/pre-push-hooks-42g5 、https://pypi.org/project/prepush-ci/ )。CI 觸發的世界常規:push 只限預設分支、pull_request 不限,避免同一個提交推上去又開 PR 時跑兩次;代價是沒開 PR 的功能分支沒有 CI,RubyGems 明寫接受(https://adamj.eu/tech/2025/05/14/github-actions-avoid-simple-on/ 、https://docs.publishing.service.gov.uk/manual/test-and-build-a-project-with-github-actions.html 、https://github.com/rubygems/rubygems/commit/924d916a73 )——本 repo 的 ci.yml 正是這個形狀,所以不改。GitHub 的必過檢查要在 PR 最新的頭提交上過,舊提交的結果不算(https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks );本 repo 用「合併前對 PR 頭提交 `lumos ci-wait` 判定 green」做同一件事,機械擋要分支保護(Q2)。不採:r2–r3 試過的「CI 推任何分支都跑」(把 gates 的後盾閘、沒有本機 main 的環境、逐次推送的增量範圍一起帶進功能分支,三輪都收不乾淨;世界常規也不這樣做)。

RETIRE-IF: 上線後八週內,PR 的 CI 全套(shards 工作)在 PR 頭提交上紅、要回頭修的 PR 超過這段期間 PR 數的三成 → 改回推功能分支時本機跑全套。這一步的價值是「推送不再被全套擋住、人可以先做別的」,不是總等待時間變短(PR 的 CI 全套本來就要 15–20 分);三成紅代表大部分 PR 都要來回修,推送時省下的那段被來回修吃掉。數法:GitHub 的 PR 清單與各 PR 的 shards 工作結論,唯讀統計、不進閘;上線當天另量上線前八週的同一比例,上線後比例比它高出一倍以上也算觸發(代表少跑本機全套真的讓更多紅漏到 PR)。

## 舊否決對照

- [[Projects/CI加速_計劃]](2026-10-06)否決「只跑受影響的測試子集」(覆蓋變少)與「本機全綠就不等 CI 先合併」(要改全域規則)。這一步不同:全套沒有變少,只是從本機換到 CI 跑,合併前照等;兩條舊否決的理由都不成立。

## 做法

1. **pitfalls 輸出兩個新欄位**:
   - `pitfalls` 加旗標 `--pushed-ref <遠端 ref>`(只用來判主線,不改 `--diff` 的範圍;不需要遠端名,所以跟 `room-guard` 等「`--push-remote` 與 `--pushed-ref` 要一起給」的命令不同:那些命令拿兩個旗標重算範圍,這裡只判主線,刻意單獨收)。給了就在 `--json` 輸出 `pushed_mainline`:被推的不是 `refs/heads/` 底下(含空字串)→ true(這裡的「主線」意思是「照全套」,跟 `_note_reread_push_old` 對標籤直接回「不算推主線」方向相反,刻意保守);分支短名在 `_note_reread_mainline_names(root, tip)` 回的集合裡 → true(這個集合永遠含 `main`、`master`,再加主線候選實際指到的分支名,不看遠端名——推網址、別名遠端、新遠端首推 main 都認得);其他 → false。`tip` 取 `--diff` 範圍的終點(既有 `_diff_range_ends`),`deadline` 給 10 秒(逾時只剩固定名,照既有行為)。沒給旗標 → 不輸出這個欄位。
   - `--json` 一律多輸出 `suite_computed`:在 `_test_suite_for_range` 的回傳 dict 加布林鍵 `computed`(兩個失敗的 return 點為 false,其餘含守衛檔提早回 full 的都是 true),`cmd_pitfalls` 兩處組 JSON 的地方(有 lint 與 `--no-lint` 兩條路)都照抄這個鍵;不靠比對 `reason` 字串。
2. **掛鉤**:先照掛鉤既有的探旗標慣例(讀 lumos 原始碼找字樣、不執行,同 `_CL_KG`)找 `pitfalls` 專屬的 `dest="pf_pushed_ref"` 字樣;找得到才在每個 ref 叫 `pitfalls` 時多帶 `--pushed-ref "$_rref"`(直接呼叫用陣列式引號,不用 `pp_q`)。找不到(舊版 lumos)就不帶、`pushed_mainline` 自然沒有、照全套,其他提醒照舊讀得到。這個 ref 判 `full` 時,只有三個條件都成立才改判 `light`:`pf_json` 裡有 `"pushed_mainline": false`、有 `"suite_computed": true`、而且能讀到這兩個欄位(用掛鉤現有讀 `pf_json` 的 `grep` 寫法)。降成 light 時在這個分支裡讀 `affected_keys` 與 `autoloop_full`(跟現行 light 那段同樣讀法)。其他情況(`pf_json` 空或讀不懂、舊版沒欄位或不認得旗標、推主線、算不出範圍)照現行全套。原本判 docs 或 light 的照舊;多個 ref 照現行「任一要全套就全套」。降級刻意不受 `light_ok` 約束(改到測試檔、守衛檔也降):全套由 PR 的 CI 跑。
3. **訊息**:掛鉤裡四處講「CI 會跑全套當後盾」「CI 會兜底」的舊句(抽不出關鍵字那句、關鍵字沒對到測試那句、開跑前提示裡的「嫌久可 --no-verify,CI 會兜底」、spec-gate light 那段的註解)改成不承諾 CI 一定跑:「全套由 PR 的 CI 跑(沒開 PR 前沒有 CI)」;迴圈結束、`_suite_mode` 定案之後只印一次:最終是 light 而且至少一個 ref 是因「功能分支」降下來的 → 「推功能分支:本機只跑文件子集與關鍵字子集(關鍵字空的就只有文件子集);全套由 PR 的 CI 跑——合併一律走 PR,等 PR 最新頭提交的 `lumos ci-wait --sha <PR 頭提交>` 判定是 green(rc 0 不等於綠)才合併,用一般合併(不要 squash、rebase,會讓審查留痕失效);合併後再對 main 的合併提交 `ci-wait` 一次」。
4. **說明文字同步**(逐處,只改本 repo 的):專案 `CLAUDE.md` 紀律區塊外〈本 repo 的測試子集怎麼跑〉一段;`skills/lumos-project-notes/commands/08-自動跑的.md` 的 pre-push 那句(這是本 repo 的 skill 來源,消費專案靠 symlink 讀,講的是工具鏈本 repo 的掛鉤行為,寫明「工具鏈本 repo」);[[Systems/bound-tests-gate]] 2026-09-18 那行的結論;[[Systems/pitfalls-code-loop]] 寫 `--pushed-ref`、`pushed_mainline`、`suite_computed`;掛鉤 `_suite_word` 與做法 3 的四處舊句;父計劃 [[Projects/推送與CI提速_計劃]] 那行「REVISIT:2026-11-14 推送前掛鉤的大改合併後,開第二階段」(該篇有兩行 2026-11-14 的 REVISIT,只動這一行)照 [[Projects/漂移防治路線圖_計劃]] 的寫法加 `[closed:]`。紀律範本不動(見〈不做〉)。使用者全域 CLAUDE.md 是 Q1,不由 AI 改。

## 實務隱患

- 守衛面:本機不跑全套,壞東西要等 PR 的 CI 才看到。PR 事件一律全套、帳本提交會在 PR 頭上再觸發一次全套,所以 PR 頭提交一定有全套結果;直接推 main 照樣本機全套(`pushed_mainline` 為 true);剩下的洞是在 GitHub 上合併 PR 時沒等頭提交綠——main 沒有分支保護,靠訊息與既有規矩,機械擋是 Q2。另一個洞跟以前一樣存在:PR 的 CI 測的是「PR 頭加上當時的 main」,main 之後前進不會重跑,兩個會談各自綠、先後合併的組合要到合併後推 main 的 CI 才第一次全套(以前推送前本機全套也只測分支本身,不是新洞);所以訊息要求合併後再對 main 的合併提交 `ci-wait`,紅了當場修。機械擋要合併佇列或分支保護的「要求分支最新」(Q2)。PR 事件不跑後盾閘(code-loop、筆記形狀、漂移、回頭重讀只在推 main 時跑),這些照舊靠推送前掛鉤與合併後的 main CI。沒開 PR 的功能分支沒有任何全套(世界常規接受的代價),只要不合併就不影響主線。
- 算不出來的方向:`pf_json` 空、舊版沒欄位或不認得旗標(argparse 拒絕、`|| true` 吞掉 → `pf_json` 空)、`suite_computed` false 一律照全套。舊版 lumos 不認得新旗標時連純文件推送也會變全套(比現在慢,方向安全)。
- 主線判定查候選失敗:只剩 `main`、`master` 兩個固定名;預設分支叫別的名字(例如 develop)時那次會被當功能分支——本 repo 的主線就是 main,接受。
- 時間:PR 的 CI 全套約 15–20 分(16 份給 8 台);GitHub 免費帳號同時執行的工作有上限,多個會談同時開 PR 會排隊,`ci-wait` 逾時(rc 0、判定 timeout)不等於綠,要再等。
- 併發:多個會談各自推分支,本機各自只跑小子集,負載比現在低。
- 已排除:金流:不碰付款或計費。
- 已排除:對外送出:不改 CI、不開 Issue、不新增對外呼叫。
- 已排除:不可逆:掛鉤、`pitfalls` 欄位、範本都能還原。
