# 存量漂移防線_計劃

白話:筆記形狀擋與筆記內容審只管「新寫進來的句子該不該寫」。這一篇管另一半的一部分——**已經寫進去的句子,因為別處的狀態或程式變了而過期,要有東西把它指出來**。rtb 抽查 33 處,20 處是這種漂移,現有健檢一處都沒抓到([[Issues/存量筆記漂移三種機制_rtb根因回饋]],證據全文 `governance/audits/2026-09-28-rtb-drift-rootcause/rootcause.md`)。三種產生方式裡,這一篇做兩道誤報低的:**甲**(改狀態時連帶處理,機制③)與**乙**(回頭條件改成機器能判的條件,機制②);第三種(程式改了、舊句還在講,機制①)誤報與漏抓要實測才知道,拆到 [[Projects/舊句偵測實驗_計劃]] 先做實驗。每道做完先拿考卷考一次。

依據:Enzo 2026-09-28 裁「把沒防護到的修一修,然後用新工具健檢一次筆記,看能修復多少」;設計審 r1 後裁「拆開:甲乙先做、丙先實驗」。

PRIOR-ART: 最小解在工具鏈自己這一層(筆記與程式都在同一個 git 裡)。世界解:[[Projects/先問世界_存量掃描裁定]] 點名過 Doorstop 的邊級 suspect 與 Swimm 的行級錨點——要先埋錨點,rtb 現有筆記沒有,留作候選;回頭條件寫成可判定條件的做法,世界上最接近的是 ADR 工具的 superseded 鏈與 feature flag 的「到期條件」,都是作者明寫、工具判定,本計劃照這個形狀。借用:①推送範圍起點借三道檢查共用的推送起點判法(`_lens_push_base`),再用 `_nodehome_clamp_base` 截到自己的上線點,參數照筆記內容審那一處(推送前掛鉤裡的標記,不是提交前掛鉤);②閘的形狀(block/warn/off 三態、略過開關只認 1、只看這次帶進來的、治理帳事件、doctor 印模式行與 CI 沒呼叫的提醒)照筆記形狀擋與筆記內容審;③讀某個提交的樹借 `_nodehome_reader`、列某個提交的全部路徑借 `_nodehome_list`;④測試檔判定借 `_nodehome_is_test`,並照它的要求先用那棵樹的全部路徑算版面(`_nodehome_layout`)再傳進去;⑤狀態欄位與標籤同步借 `edit_fm_sync_status_tag`,寫入借 `atomic_write_verify` 並包在 `_vault_write_lock` 裡(照 `cmd_set`);⑥可見行判定借 `_strip_code_text`(圍欄與行內反引號一次剝,全檔唯一的剝碼函式,不另寫反引號正則);表格行照 doctor E5 既有判法(去掉行首空白後以 `|` 開頭);⑦新寫的 REVISIT 行擋在筆記形狀擋(第一層)裡,照它「只看新行、截到上線點」的規矩;⑧筆記改名的對應借筆記形狀擋與筆記內容審共用那支(`_notelines_range_added`)裡的 `-M` 改名追蹤,它現在是內部函式,要抽成可共用的一支,不另寫第二套;⑨表態檔寫入借 `_jsonl_append_verified`(追加後讀回自驗)。自建:條件語法(`[when-…:…]`)與它的評估、甲的狀態一致檢查、一支三處共用的「這行是不是 REVISIT」判定、考試指令。跟既有的 `drift-history`(沿歷史重放 Check Y 的離線量測)不重疊:那支量「符號還在不在」,本計劃不碰符號存在性(那是 [[Projects/舊句偵測實驗_計劃]] 的題目)。跟 `valid_under`/`revalidate_when` 的分工:那兩欄照舊是人讀的前提與重驗時機,工具不評估;條件式只在正文與摘要行生效(見〈做法〉第 0 節)。

## 做法

### 0. 共用:條件的文法、指令家族 `lumos drift`、一支推送閘

**條件標記的文法**(第一層、scan、check、doctor 共用一支解析):
- 形狀 `[when-<鍵>:<值>]`,鍵只有 `file`、`symbol`、`test`、`status` 四種;值是冒號後到第一個 `]` 為止,不能含 `]` 與換行,頭尾空白去掉後不能是空的。值裡可以有空白(路徑含空白照收)。
- 各鍵的值:`file` 是 repo 內一支檔的相對路徑(不准 `/` 開頭、不准 `..` 段;指到目錄時 scan 列成寫錯的條件);`symbol` 與 `test` 是 `<名稱>` 或 `<路徑>::<名稱>`(從**最後一個** `::` 切,名稱不能空;有 `::` 時路徑也不能空、同 file 的規定);`status` 是 `<節點>=<值>`(從第一個 `=` 切,兩邊都不能空;`<節點>` 跟 `[[連結]]` 同一種寫法——圖譜相對路徑不帶 `.md`,只寫檔名主幹也行,三處(第一層、check/scan、`lumos set` 第③項)都用同一支連結解析;值可寫 `a|b` 表示任一,用 `|` 切開後每段去頭尾空白,任一段是空的就算寫錯)。形狀不合的叫**寫錯的條件**。
- **期限 `[by:YYYY-MM-DD]`**:條件式回頭條件在條件標記後面**必須**帶一個期限——條件成立或到期,任一先到就該處理。它不是條件(不參與「全部成立」),由 doctor E5 當日期檢查。為什麼必須:名字拼錯、Python 常數寫成工具認不得的樣子、路徑寫錯,條件就永遠不會成立;有期限,最晚那天 E5 會唸。原本「事件或到某天」的散文(考卷 B1、B2)照原日期寫進期限;原本「到某天時看事件決定怎麼做」的(考卷 B5:日期才是觸發,事件只決定動作)不該改寫成條件式,照留日期式。
- **只在正文與摘要(summary)的可見行生效**:圍欄內的行、表格行(去掉行首空白後以 `|` 開頭)、行內程式碼(一對反引號)裡的標記都不算——那是範例。開頭欄位裡 summary 以外的**任何**欄(`valid_under`、`revalidate_when`、decisions…)裡的標記不評估。寫在表格行或這些欄位的條件標記:第一層擋新寫的,doctor Z 段列成「寫在不評估的地方」。
- 一行多個條件全部成立才算成立;要「任一成立」就寫成兩行。
- 呼叫 git 一律用 `-e <值>` 與 `--` 隔開路徑,值不會被當成 git 選項。

**「這行是不是 REVISIT」**(E5、第一層、第二層共用一支):去掉行首空白,再去掉一層列表或引用記號(`- ` `* ` `+ ` `1. ` `1) ` `> `),以 `REVISIT:` 開頭;表格行與圍欄內不算。`REVISIT:` 後面(去掉空白)若以 `[when-` 開頭,就連續吃掉條件標記與一個 `[by:…]`(中間可有空白),這行是**條件式回頭條件**;否則取到第一個空白為止的字串,用跟 E5 現在一樣的 `date.fromisoformat` 解析,成功是**日期式**,失敗是格式壞損(E5 照舊算壞行、第一層擋新寫的)。這支判定比 E5 現在多認 `+ ` `1. ` `1) ` `> ` 四種記號,E5 改用它之後範圍跟著變大;2026-09-28 工具鏈圖譜裡這四種開頭的 REVISIT 行是 0 條,不會一上線就多出一批壞行。

**「同一條」怎麼認**(判「這個條件是不是這次才成立」要用):先用 git 的改名偵測把終點的筆記路徑對回起點的路徑(借用清單⑧),再看起點那篇裡有沒有一行**條件標記一模一樣**(同樣的標記、同樣的順序,`[by:]` 與後面的待辦文字不算)的條件式回頭條件。有就是「同一條」,只改待辦文字、改期限都還是同一條;條件標記改了就是另一條。

**指令**:
- `lumos drift check --diff <起點>..<終點>`:推送前與 CI 的閘(閘名 `drift-check`)。有「要處理」的發現才回 1,只有「只列出」的回 0;參數錯回 2。範圍起點照 `_lens_push_base`,再截到上線點(推送前掛鉤裡出現標記 `drift check` 的第一個提交)。讀被推送頂端提交的樹(`_nodehome_reader`),不讀工作目錄。**只評估這次推送可能改變結果的行**(篩選單位是「行」,不是單一條件):一行裡任一條件落在下列情形,這一行就是候選——①`file`:路徑在範圍裡被新增、刪除或改名(改名的兩端都算);②`symbol`、`test` 帶路徑:那支檔在範圍裡有任何變動(改動、新增、刪除、改名);不帶路徑:名稱出現在範圍的改動行,或範圍裡有程式檔或測試檔被新增、刪除、改名(改名可能讓檔換了類別、名稱不在改動行裡)——這時所有不帶路徑的 `symbol`/`test` 行都當候選;③`status`:指到的筆記在範圍裡有任何變動(含新增、刪除、改名);④這次新寫或改了條件標記的行。候選行在起點與終點**各評估它的全部條件**(一行是「全部成立」)。不是候選的行,起點與終點結果一定一樣,不評估。範圍的改動只算一次(一次 `git diff --name-status -M` 加一次 `git diff -U0`),兩端的全部路徑各列一次,讀檔有快取——不逐條件各起一次 git。
- `lumos drift scan [--at <提交>] [--json] [--budget <秒>]`:對整份圖譜(**含 superseded 的筆記**)現況或某個提交的樹,跑甲的五種一致檢查與乙的全部條件評估,列出全部發現,已表態的標「已表態」另計。不擋、不寫帳。這是回退時清點條件式行、修復階段產清單用的。
- `lumos drift ack <節點> <行號> --kind probe|c1|c2|c3|c4|c5 --reason "<為什麼照留>"`:表態「這行照留」。用 `_jsonl_append_verified` 寫進 `governance/drift-acks.jsonl`(加進簿記豁免),每筆存:路徑、行的原文、種類、理由、日期、表態時的小標題與行號(只供人讀)。**對得上**的條件是「同一路徑、一字不差的原文、同一種類」——改小標題不失效;改了那一行或筆記改名就失效,失效時工具用「原文與種類相同」在表態檔裡找,找到就印出舊理由供照抄。理由少於 4 個字拒絕;每筆記一筆治理帳 `acked`。check 只認**被推送頂端提交裡**的表態檔(照第二層「判定檔要提交才算」),所以表態後印提交指令。scan 與 doctor 對已表態的行照列、標「已表態」。
- `lumos drift exam <考卷.json> --repo <被考的 repo> [--probes <改寫檔>]`:在被考 repo 的歷史上重放,算甲乙各自擋到、點到、漏、誤報(〈做法〉第 3 節)。考試模式不寫治理帳、不寫任何檔。
- doctor Z 段:**不評估條件**(不跑 `git grep`、`ls-tree`),只讀筆記:條件式回頭條件幾條、沒帶期限的幾條、寫錯的條件幾條、寫在不評估的地方的幾條,甲的五種一致檢查各幾筆與前幾筆;要看哪些條件已成立,跑 `lumos drift scan`。唯一的 git 呼叫是判斷「有沒有接線」時讀一次推送前掛鉤(`git show HEAD:<掛鉤>`,照筆記內容審那處的判法)。照 doctor 的全靜默慣例:全部是 0 就整段不印。每次推送多出的成本是讀一遍筆記加一次 `git show`。
- 開關:`.lumos/config.json` 的 `drift_check.gate` = block / warn / off,讀被推送頂端提交裡的設定;**設定檔沒寫時的預設值**寫在程式裡,照〈做法〉第 4 節第 4 點的門檻定——過門檻是 block,沒過是 warn(兩處講的是同一個值);單次略過 `LUMOS_SKIP_DRIFT_CHECK=1`(只認 1,記 `skipped-env`);淺層 clone 跳過並記帳(同兩層筆記閘)。gate 不是 block、而且專案自己寫了開關或已經接線時 doctor 印一行(沒寫設定也沒接線時預設就是 warn,不唸;實作期代碼審 r3、r4 改);接線後,專案 CI 沒呼叫 `drift check` 時 doctor 也印一行並給要貼的步驟(照筆記形狀擋與筆記內容審的 CI 提醒)。
- 閘名 `drift-check` 登記進既有閘名單;事件種類:`blocked`、`warned`、`skipped-env`、`skipped`、`degraded`、`acked`。沒發現的放行不寫帳(同筆記形狀擋)。
- **判不了的時候**:git 單次沿用 `_lens_git` 的 20 秒逾時;check 總預算 60 秒。check 要評估的條件都跟這次推送有關、數量小,**判不了的(git 失敗、逾時、預算用完)算「要處理」**並印原因——判不了就放行,等於給了一條繞過的路;要推就單次略過(留帳)。scan 判不了的列成「判不了」、不擋、不寫帳(scan 不是閘;讀指令不寫帳是既有決定,實作期代碼審 r3 改)。

### 1. 甲:狀態指令連帶處理(對應機制③,考卷 A4–A6、E1–E3)

1. **`guard settle` 轉正時,把守衛紀錄裡 `guard plan` 寫的四種預告句改成歷史說法**(只動工具自己寫出的固定句型)。四種句型用**行首前綴**認(去掉摘要的縮排後,從行首比對;前綴照 `guard plan` 樣板的實際字元,含反引號),settle 與 c1 共用同一支比對函式:
   - 摘要前綴 `TEST:還沒有測試在守這條` → 整行換成 `TEST:[<轉正日期>] 預告已轉正,合約改由 [[<家筆記>]] 的正式合約行守`(講「哪天發生了什麼」,不重複寫測試名——那是程式碼答得了的,筆記內容審會判成推得出);作者只改了日期或負責人,前綴照樣認得;
   - 摘要前綴 `WHY:[`、而且同一行有 `]預告這條合約但還沒做:` → 行尾加 `(<轉正日期> 已轉正)`,行尾已經有「已轉正」就不再加;
   - 正文前綴 `為什麼還不做:` → 換成 `預告當時為什麼還不做:`(新的前綴不以 `為什麼還不做:` 開頭,c1 不會再認);
   - 正文前綴 ``做完之後跑 `lumos guard settle` 轉正``(樣板整句是 ``做完之後跑 `lumos guard settle` 轉正,不要手改狀態。``)→ 整行換成 `(<轉正日期> 已轉正)`。
   - 找不到固定句型(作者手改過)就跳過那一句並印一行提醒,settle 照樣成功。
2. **settle 的寫入順序與補救**:整個 settle 包在 `_vault_write_lock` 裡;先改家筆記的預告行(既有邏輯),再**一次寫入**守衛紀錄(status pending→pass、標籤同步、上面四種句型,同一次 `atomic_write_verify`)。**補救路徑**:再跑一次 settle 時,若家筆記已經有這條合約的正式行(合約文字相同、而且行內有 `[test:<方法>]`;後來 `guard audit` 加上的 `[audit:…]` 等標記不影響比對)而守衛紀錄還是 pending,就只做第二步——中途失敗也能用同一個指令補完;若守衛紀錄也已經是 pass(例如另一個程序剛做完),印「已轉正,不用再做」、回 0。**同一篇家筆記的讀改寫者都拿同一把鎖**:`guard plan`、`guard settle`、`guard abandon` 各自整段(從讀家筆記到寫完)包在 `_vault_write_lock` 裡——現在三者改家筆記都在鎖外,兩個指令同時改同一篇家筆記,後寫的會用舊內容蓋掉先寫的(例:settle 蓋掉同時 plan 寫進去的預告行,留下一篇 pending 守衛紀錄卻沒有預告行)。
3. **`lumos set <計劃> status done|superseded` 列出連帶待辦**(只多印,不擋、不寫;只讀筆記,不跑 git):①跟這份計劃有連結(任一方向的 `[[連結]]`,方向寫出來)而且 status 是 open/doing 的 Issue;②`plan_refs` 指到它、status 是 pending、沒有 `guards` 欄、而且 `plan_refs` 其他項也都已收尾的驗證紀錄(跟 c3 同一個集合,用同一支函式)。每項給一行**檢視**指令(`lumos context <節點>`),不給會改狀態的指令——連結有時只是參考,是不是該結案要人看。不是計劃、或不是改成 done/superseded 就不印(計劃的合法狀態只有 todo/doing/done/superseded)。乙做完後再加第③項(見第 2 節第 7 點)。
4. **五種狀態一致檢查**(scan、check、doctor Z 共用一支函式;每筆發現回報「哪篇、哪一行」,欄位層級的就回報那個欄位所在行):
   - **c1 轉正了還寫預告**:驗證紀錄 status 是 pass、有 `guards` 欄,而且還有第 1 點那四種固定句(同一支前綴比對;WHY 那句沒有「已轉正」後綴才算)。**一句一筆**:一篇最多 4 筆,各自回報行號、各自表態;算噪音時同一篇的 c1 合算一筆。

   - **c3 計劃收尾了、驗證紀錄還待定**:驗證紀錄 status 是 pending、沒有 `guards` 欄(守衛紀錄到期前本來就是 pending),`plan_refs` 至少一項、每項都找得到而且是計劃、全都已收尾。只列出。
   - **c4 前提寫「還沒提交」**:`valid_under` 含「未提交」「還沒提交」「uncommitted」任一詞就成立,同一句裡有沒有別的詞都不影響(考卷 E3 就是「本工作樹(未提交、未過代碼審)」)。關鍵詞清單裡刻意不放「工作樹」:「釘在某提交的乾淨工作樹」是合法的可重現寫法,本來就不含這三個詞。只列出。

## 回退

- **推送閘**:掛鉤與 CI 各拿掉一行即不擋;`drift scan`、doctor Z 段與 E5 對條件式的處理**留著**——已經照新寫法寫的條件式回頭條件才有地方被看見。要連評估一起拿掉,得先用 `lumos drift scan --json`(含 superseded 筆記)列出全部條件式行、改寫成日期式,否則 E5 退回舊版後會把它們算成格式壞損。
- **第一層的 REVISIT 規則**:第一層只有一個整體開關,沒有只關這一條的開關。單次誤擋用 `LUMOS_SKIP_NOTE_SHAPE=1`(留帳);設 `note_shape.gate=warn` 會連既有的行號引用、現況沒寫來源、釘版本等規則一起變成只提醒,不是只撤這一條。這條規則本身判錯,就還原它那一處程式碼(不給單條開關:開關會讓同一篇筆記在不同專案有兩種結果)。
- **guard settle 的改寫**:只動工具自己寫的四種固定句型。要撤掉某一篇的改寫,手改那幾行即可(不動 status)——改回預告句型後,那篇會被 c1 當成「轉正了還寫預告」一直列在 scan 與 doctor,所以同時對那幾行 `drift ack --kind c1` 寫明為什麼要留;要整個功能退回,還原程式碼——已轉正的紀錄兩篇都一致(家筆記是正式行、守衛紀錄是 pass),舊程式讀得懂。**不要單獨用 git 還原守衛紀錄**:那會把它退回 pending 而家筆記已是正式行,舊程式沒有補救路徑、轉正與棄置都會擋下(guard-kill 記過這種卡死);真的還原了,用新程式重跑 settle 補完,或手改 status。不給開關:改寫只碰工具自己的樣板句,開關只會讓同一個指令有兩種結果。
- **lumos set 的連帶待辦**:只多印,不寫。
- **第二層排除條件式回頭條件**:單獨還原這一處,已寫的條件式回頭條件在所屬計劃收尾(完成審)時會被重新送審,可能被判成推得出——要還原就先把條件式行改寫成日期式,再還原。
- **消費專案**:更新 lumos 後推送開始被擋,設 `drift_check.gate=warn|off` 即可;doctor 會照慣例印一行模式提醒。
- 表態檔與考卷都是新增檔,刪掉不影響其他功能。

## 實務隱患

- **誤報與表態疲勞**(RETIRE-IF ①):推送時只擋 c1、「這次推送讓條件成立」與「判不了」三種,都是作者或工具明寫的東西,不猜語意;c2–c5 只列出。
- **效能**:doctor Z 段不評估條件,只讀筆記加一次讀掛鉤檔;check 只評估這次推送可能改變結果的行(第 0 節);範圍改動只算一次、兩端路徑各列一次、讀檔有快取,git 呼叫次數不隨條件數成長;scan 是手動指令,對全圖譜的條件各跑一次,預算 60 秒、可用 `--budget` 放寬。都不跑 `git log -G` 這種全歷史搜尋。
- **多分支一次推**:check 在推送前掛鉤的逐分支迴圈裡跑,每個分支各自一個 60 秒預算;doctor 只在迴圈前跑一次、只讀一次掛鉤檔。最壞約「分支數 × 60 秒」,實際條件少時遠低於此。
- **併發**:plan、settle、abandon 各自整段包在 `_vault_write_lock` 裡(照 `cmd_set`,那把鎖可重入);現在三者改家筆記都在鎖外,這是順手補的既有縫。兩個 settle 同時跑,後拿到鎖的看到已轉正就回 0。表態檔與 drift-check 事件的寫入跟治理帳同一類「多個程序同時追加同一個 jsonl、沒有共用鎖」的問題([[Issues/治理帳多個寫入者都沒上鎖]]):表態是人手動敲、頻率低,事件走既有 `_gate_event` 的寫法;都是一次追加一行,那篇 Issue 的 2026-10-11 回頭看時把這兩個寫入者也算進去,整體怎麼修由那篇決定。
- 已排除:金流:不碰任何付款、帳務或金額計算的程式
- 已排除:對外送出:只讀筆記與程式、寫本機檔,沒有寄送或外部寫入
- 已排除:不可逆:新增的檔與改寫都在 git 裡,整批還原提交即回復;只單獨還原守衛紀錄這一種會卡住,〈回退〉那一條寫了怎麼補
- **守衛面**:碰——新增一道推送閘、改 `guard settle` 的寫入、改第一層與第二層各一處。處置:三態開關、略過留帳、判不了算要處理(不留繞過的路)、settle 可補救;設計審與代碼審照 high 看待。
- **輸入安全**:條件值來自筆記,呼叫 git 時用 `-e` 與 `--` 隔開,不會被當成選項;路徑值不准絕對路徑與 `..`。

## 誠實界線

- **乙靠作者寫條件**:條件式只判得了寫了的;舊的散文回頭條件要人補寫;新的散文回頭條件由第一層擋,但作者可以改寫成日期(日期到了照舊由 doctor 唸)。
- **`when-symbol` 對非 Python 是整字比對**:名字先出現在註解或字串裡,條件會在那個提交提早成立(那次就擋一次);之後真正的定義加進來時起點已經成立,**這次就不會再擋**——提早成立會吞掉真正的事件。帶路徑的寫法 `<路徑>::<名稱>` 能收窄,同檔內的註解重名仍擋不住。REVISIT 那天看消費專案的 `blocked` 事件裡 `when-symbol` 佔幾成。
- **「任一成立」要寫兩行**:原本一句話講兩個觸發(考卷 B2),後半沒有明確的檔或名稱可寫就寫不成條件,只能留散文或靠日期,考試也只考得到前半;兩行各自觸發,處理完一行時要記得一起處理兄弟行,否則另一個觸發成立時會再擋一次同一件事。
- **筆記改名會讓表態失效**:比對含路徑,改名後要重表(工具印出舊理由可照抄);不做「跟著改名走」是因為改名同時常伴隨內容改寫,自動沿用可能蓋掉該重看的句子。
- **同一路徑裡一字不差的兩行**會共用一筆表態。
- **「同一條」只看條件標記**:只改待辦文字或期限還是同一條;把條件標記改成另一個也已成立的條件,算新寫而且已成立,照樣擋。起點就已成立的舊行 check 不列,只在 scan 列——上線前就該處理而沒處理的,靠〈做法〉第 4 節的修復清掉。
- **期限是保底不是精準**:名字拼錯、路徑寫錯的條件永遠不成立,要等 `[by:]` 那天 E5 唸才會被看到;期限寫得太遠,這段時間就是盲區。
- **考卷是設計用的那一份**:〈做法〉第 4 節第 4 點①要求全對,只證明照設計做出來了,不證明在沒看過的句子上一樣準;不會亂擋的證據主要來自工具鏈自己的歷史重放。
- **settle 只處理守衛紀錄第一篇家筆記的預告行**:這是既有限制(`guard plan` 只寫一篇家筆記,多篇要手改 `guards` 欄才會出現),本計劃沒改。
- **c2–c5 只列出**:要靠人看列出來的清單處理;沒人看就還是會留著。
- **程式改了、舊句還在講(機制①)這一篇不管**,在 [[Projects/舊句偵測實驗_計劃]]。
- **只看這次推送帶進來的**:上線前已經過期的句子推送閘不擋,只在 scan 與 doctor 列;靠〈做法〉第 4 節的一次性修復清掉。
