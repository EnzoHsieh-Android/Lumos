# 陌生棧不變量簡報五案評測_計劃

## 目的與邊界

PRIOR-ART: 借用 OpenAI Harness Engineering 的「專案內可檢索知識＋機械化不變量」分工（https://openai.com/index/harness-engineering/）；Lumos 內側直接重用現有棧別觸發題、前後端角色卡、八份 idiom skill 與 [[Projects/審查評測集_計劃]] 的外部答案原則，不另建第二套語言規則庫或審查帳本。

白話目標：開發者不熟某個語言時，不需先背完整本手冊，但要先握住「這次改動絕對不能破壞什麼」。本階段只用五個可對答案的小案例，測一張短簡報是否真能改善 code review；不先接進 `pitfalls`、不改 code-loop 收旂語意、不新增推送閣。

這批「陌生棧五案」與 [[Projects/代碼審修復穩定性試行_計劃]] 的「修復會不會帶來新回歸」是不同問題，分開計數、分開結論；相同歷史案例未來可共用原始素材，但不得把一次執行同時充當兩個試行的獨立樣本。

## 要測的東西：Invariant Brief v0

每案簡報最多 12 條，一頁可讀完。它不給修法答案，只給 reviewer 四種握把：

1. **範圍**：改動檔案、語言／執行環境、任務明說的成功條件。
2. **不變量**：用現有穩定 ID 指到 idiom 條款、角色卡、棧別觸發題或專案合約；不複製第二份規則全文。
3. **適用理由**：點出這份 diff 的哪個結構讓條款成立，不因副檔名就把整本手冊塞入。
4. **反例與證據要求**：要 reviewer 走一個具體時序、生命週期、錯誤或資源情境，並引用實際代碼位置；「最佳實務上應該」不計命中。

簡報固定表格欄位為 `id / invariant / applies_because / challenge / source`。輸入不足時要列 `unknowns`，不出自動推測的專案框架結論。

## 五案案例集

第一版用本機已有原生 runner 的五種語言，每案只放一個主缺陷與一個外型相似但正確的鄰近寫法，防止 reviewer 用關鍵字全抓：

| 案 | 語言 | 主軸 | 可對答案的故障 |
|---|---|---|---|
| U1 | C#/.NET | 作業與 DI 生命週期 | 背景作業捕獲 request-scoped 物件，request 結束後使用已釋放資源 |
| U2 | Dart | stream 與畫面生命週期 | 重複進畫面後訂閱累積，dispose 後仍收事件 |
| U3 | Swift | actor 重入 | 跨 `await` 後沿用舊狀態，並行請求讓後到的舊結果覆蓋新結果 |
| U4 | Node.js | 有界並行 | 對無界輸入直接 `Promise.all`，超過可觀測的同時處理上限 |
| U5 | Java | 交易邊界 | Spring 同類自調 `@Transactional` 方法，導致原應原子回滾的兩步寫入留下半套狀態 |

每案必備：凍結的 buggy source、正常路徑、可重跑 oracle、答案檔、案例實際使用的 Brief，以及 SHA-256 manifest。案例是合成 micro-case，只能驗所選不變量與審查行為，不得寫成真實專案成效。

## 成對評測法

每案兩臂，共 10 場有效會談：

- control：任務、diff、必要專案內容，沒有 Brief。
- brief：同一份材料，只多 Invariant Brief。
- 同案兩臂不由同一會談連續審，避免記住答案；模型、effort、工具、時間與 token 上限固定，出場順序交錯。
- 審查員看不到答案與 oracle；評分只看預先凍結的主缺陷、正常反例與可執行證據。
- 開場先記 reviewer 對該語言的自報熟悉度；有日常實務經驗者不算「陌生棧」效果樣本，但原始結果仍保留為參考。

逐案記五個數：主缺陷是否命中、是否引到正確代碼與故障時序、假陽性條數、是否誤傷正常反例、時間／token。召回與假陽性分開報，不合成一個漂亮總分。

決策線只用來決定要不要繼續擴大，不宣稱普遍有效：五個有效成對案例全數完成後，Brief 臂需至少在 2 案多命中一個 control 漏掉的主缺陷，且總假陽性不得比 control 多超過 1 條、正常反例誤傷不得變多。未達決策線就不接生產流程；達線也只能進入真實歷史 PR 的第二階段。

## 驗收條款

[S1] 五案 manifest 應在任何模型會談前凍結案例 ID、語言版本、檔案 SHA、主缺陷、正常反例、oracle 指令與預期結果；後改必須升版，不覆寫已跑版。 [test:t_unfamiliar_stack_brief_manifest_hashes]

[S2] 每案 oracle 應先在 buggy 版顯示目標故障、在 fixed 版通過，正常反例兩版都通過；編譯失敗、零測試、程序整體逾時不算抓到。 [manual:在新的隔離暫存目錄逐案執行 manifest 指令，核對四格結果與原始 stdout/stderr]

[S3] Brief 應每案不超過 12 條，每條五欄齊全且 source 只指現有穩定 ID；不得出現直接說破壞行、預期修法或答案關鍵字的洩題。 [manual:不看答案的人交叉檢查五份 Brief，再與 answer key 比對是否有直接洩題]

[S4] runner 應只寫入指定的新輸出目錄，開跑前拒絕已存在目錄、類別數不是 5、臂別數不是 10、模型／effort 不一致或答案檔被放進派工材料。 [test:t_unfamiliar_stack_brief_preflight_rejects_invalid_inputs]

[S5] 報告應逐案並列兩臂原始分數、invalid 理由、熟悉度與時間／token；召回、假陽性、正常反例誤傷分開，並以上述事前決策線輸出 `stop / proceed-to-historical`，不自創綜合分數。 [test:t_unfamiliar_stack_brief_summary_decisions]

[S6] 驗證紀錄應只把完成五案寫成「這套案例上有／無擴大訊號」，並明文寫出合成案例、模型、工具鏈、樣本數與陌生度自報的邊界，不把文件通過當成實際 code review 改善。 [manual:結果入圖前由一名未參與評分的人核對結論句與原始 receipt]

## 實作順序

1. 建 `governance/eval/unfamiliar-stack-brief/` 的 schema、五案 fixture、answer key、Brief 與 manifest；先只驗 oracle，模型呼叫 0。
2. 寫零依賴的資格預檢與匯總入口；入口不生成 Brief，Brief v0 人工從既有規則裁切，先驗假說再造自動器。
3. 通過 S1–S4 後才凍結 10 場會談的模型參數、順序與有效性規則；有效場不足時只補原定那一格，不挑成績補樣本。
4. 用新 Verification 紀錄原始數據、限制與 `stop / proceed-to-historical` 結論；達線後另寫第二階段計劃，不在本案自動改生產流程。

## 階段交接與續辦邊界

合併審查修正：舊 v1 的 U4 oracle 未驗回傳值，不能作完整 S2 通過依據。qualification-v2 只替換 U4 兩支來源並補驗結果保留，其餘四案 SHA 不變、沿用原資格證據；候選 Brief v2 與資格版本 v2 是不同用途，不表示候選 Brief 已通過 S3。舊 v1 與探索性模型 receipt 均保留原樣，正式十場不得使用舊 U4。

使用者要求先保存目前進度併回 main；本計劃維持 doing。資格預檢的證據見 [[Verification/2026-10-16_陌生棧五案資格預檢]]，跨模型單案探索見 [[Verification/2026-10-16_陌生棧簡報跨模型試跑]]。合併只保存評測材料、輔助函式與紀錄，不代表正式評測或生產接線放行。

選材可由模型協助：使用者確認產品目的與取捨；技術語意由版本相符的來源、可執行反例與獨立審查核對，不能要求使用者熟悉每個技術棧才能給技術標記。兩家一致不能替代外部判準。候選 v2 是 assistant 的編輯產物，非 Astra 實跑；每案只選確實適用的條款，12 條是上限而非配額。v1 凍結材料保持原樣，候選 v2 採用時須另版 manifest。

接手順序：先補候選 Brief 的獨立洩題審與來源核對，再凍結兩臂共同任務及工具可見材料、模型設定與有效性判準；之後才跑正式十場。僅以模型自報陌生度不能證明對真人陌生棧開發有效，模型效果與真人學習效果應分列。U4 探索不計入正式樣本，也不登記到另一個修復穩定性試行。

REVISIT:2026-11-16 核對候選v2洩題審與正式十場評測的續辦狀態；證據不足時維持doing，不從資格預檢或跨模型同意推導成效。

## 實務隱患

已排除:金流:案例只用本機合成狀態，不連金流、生產資料庫或真實第三方。

已排除:對外送出:資格預檢與 oracle 都是本機子程序；模型會談只審凍結材料，不操作業務帳號或對外 API。

已排除:不可逆:所有編譯與故障注入在新建暫存目錄，不改安裝的 SDK、HOME、git 歷史或網路設定。

已排除:守衛面:這是 eval，不用結果放行提交、推送或 code-loop；不會因案例全過就自動上線新閣。

主要實驗風險是 Brief 無意間洩題、不同語言案例難度不同，以及合成小題太容易。對應控制是先凍結兩臂共用材料、每案都放正常反例、逐案成對報數不橫向當難度相同，並要求 Brief 交叉洩題審查。

## 回退與退場

本階段沒有生產接線。回退時可撤回本計劃、eval 入口與未執行的 fixture；已產生的原始 receipt 不改寫，判定器有錯就將該批標 invalid，升版後另開新輸出目錄。

RETIRE-IF: 五個有效成對案例完成後，Brief 沒多命中任何一個 control 漏掉的確認缺陷，或新增假陽性／正常反例誤傷超過上述決策線，就停止把 Invariant Brief 接進 Lumos，保留負結果，不再用同一批小題改字測到贏。
