# Android寫法語意情境表態與盲判_計劃

> 白話:型錄裡有一類寫法是機器看長相判不出來的——「這兩支呼叫互不依賴嗎」「這是事件還是狀態」——要先判情境才知道該用哪種寫法。這份計劃讓這類情境走三步:①改動碰到某個情境的觸發字時,AI 推送前要對每段程式表態「決策表的候選列哪幾列適用、各照哪個寫法寫在哪一行」;②機器到那一行核對,真的出現那列寫法的特徵才算(防「寫了規範卻完全沒參考」);③另派一個沒看過 AI 答案的盲判代理,只看程式與候選列自己判一次,兩邊對不上就擋,再派第二個盲判仲裁。使用者原話(2026-11-05):「判斷當下是什麼情況、該用什麼的是 AI,但有沒有真的照做是機械執行」「我怕出現寫了但完全沒參考的狀況」「有沒有必要起一個 subagent 來覆檢這個情境的狀態,沒有 context 比較沒有偏誤?」→「好,加進去」。是 [[Projects/Android協程與API寫法機械檢查標準_計劃]] 分批表的第三批。

PRIOR-ART: ①同 repo:棧別提問表態閘([[Systems/棧別提問表態閘]])已有「觸發字決定哪題適用 → 推送前逐題表態 → 機器驗證據存在」整條路,四種狀態、改碼後表態過期、治理帳加標記檔的讀寫都現成;本案在它上面多一組題目,並把 satisfied 從「驗行號存在」加嚴成「驗那一行長得像那列的寫法」,不另起新閘。張力表態([[Projects/兩席相反時端出張力_計劃]])是「兩方意見相反時攤開給人裁」的既有形狀。②世界解:架構決策要靠可執行的檢查守住、不靠文件(架構適應度函式,ADR 每條對應至少一支自動檢查,https://concepts.dsebastien.net/concept/architectural-fitness-functions/ ;ArchUnit 把決策寫成測試,https://medium.com/publicis-sapient-france/enforcing-architecture-decisions-with-archunit-4d8b9f61cf4a )——採用「每列決策要有機器核得到的特徵」。③多標籤標註:Cohen's kappa 要求每個樣本恰好落在一個互斥類別(https://en.wikipedia.org/wiki/Cohen%27s_kappa );決策表的列不互斥,一段程式可以同時屬於多列,所以比對單位是「(段,列)」,每列各判一個二元答案,一致度逐列算二元 kappa——多標籤資料的標準做法是逐標籤各算一致度(https://en.wikipedia.org/wiki/Multi-label_classification )。r1 試過「每列各問、作者答不適用、盲判答單選」對不上,r2 試過「每段單選一列」在列重疊時卡死,兩次都被打穿才換到逐(段,列)二元判。④盲判:LLM 當評審時,讓它先看到別人的標籤會被帶著走(錨定),看不到的盲判跟嚴格標註者較一致(https://www.researchsquare.com/article/rs-10688342 ,預印本未同儕審);評審一致度要用扣掉偶然一致的指標看,單看相符率會高估(https://arxiv.org/html/2606.19544 )——採用「盲判材料由工具產生、不含作者答案」,一致度統計用 Cohen's kappa 而不只是相符率。不選:推送前閘裡直接呼叫模型(推送閘不呼叫模型是既有原則,[[Projects/Android寫法寫完當下自動檢查_計劃]]〈不做〉同一條)。
RETIRE-IF: 上線八週後在消費專案用 `lumos gov --stats` 看:①某一列作者判適用的(段,列)≥ 20、正一致率 ≥ 0.95 而且盲判全判照做 → 那一列拿掉盲判、只留證據樣式核對(盲判沒抓到東西);②某一列的段放行超過該列段數的一成 → 那列的證據樣式重寫或改成 `(無)`;③整組情境段八週內少於 5 段 → 撤掉整組,只留告警帶寫法;④平均每次推送超過 10 段、而且盲判判「不適用」超過一半 → 觸發字太寬,收窄或加進停用字表。

## 用詞

- **情境段**:這次改動在被推版本的增行裡,命中〈情境決策表〉任一列觸發字的區段。切法:只看同一個 diff 區塊(hunk)裡的增行;相鄰命中增行的行號差不超過 4(中間至多隔 3 行)、而且在同一個段材料(見下面〈段材料〉:往上最近的頂層或類別層宣告)裡,才併成一段;跨段材料一律切開;一段最多 40 行,超過就從第 41 行起另開一段。段範圍=段裡的增行加前後各 3 行。不出段的:只改空白或縮排的增行(去掉空白後跟刪行相同)、`import` 與 `package` 行、只有刪行命中的(被刪掉的寫法在推上去的版本裡不存在)。比對前先用 `_kotlin_strip` 把整支檔(不是只剝片段)剝掉註解與字串字面值。
- **Kotlin 剝註解與字串**(實作是 `_strip_c_comments(..., kotlin=True)`,掃描本體 `_kt_strip_spans`;設計時叫 `_kotlin_strip`。新增,跟 [[Projects/Android寫法寫完當下自動檢查_計劃]] 的改檔前推列共用,兩案誰先實作誰建):輸入整支檔,換行先統一成 `\n`,只用 `\n` 切行;處理 `//`、可巢狀的 `/* */`、`"…"`、`"""…"""`、字串樣板 `${…}`(大括號內是程式碼、要保留,內部的字串照剝);被剝掉的字元換成空白,行數與欄位不變。不認 Kotlin 沒有的 `'''`、`@"…"`。
- **段材料**:包住這段的那個函式或宣告(從段的第一行往上找最近一個在頂層或類別層的 `fun`/`val`/`var`/`class`/`object` 開頭,用剝過的文字配大括號找到結尾),最多 120 行;找不到或超過 120 行時用段前後各 20 行。盲判看的、證據比對的、段身分雜湊的都是同一份段材料。
- **段身分**:`sha256(檔路徑 + "\0" + 段材料原文(換行統一成 \n)+ "\0" + 候選列編號清單 + "\0" + 第幾次出現)` 取前 16 碼;「第幾次出現」是同一支檔裡段材料原文相同的段依行序編號(1 起),讓複製貼上的兩段各有身分。段材料裡任何一行改了身分就變、舊記錄自動不算;rebase 或壓提交後段材料沒變就照樣有效。
- **候選列**:這一段命中觸發字的所有決策表列。觸發字比對用 `_kt_trigger_re`(跟第二批共用):觸發字 `re.escape`;只在觸發字開頭是英數或底線時,要求前一個字元不是英數或底線;只在結尾是英數或底線時,要求後一個字元不是英數或底線;分大小寫。
- **情境題**:棧別題表 `kt` 題組新增一題 `kt-situation`,標 `android_only` 與 `shape_only`(不因改動行數超過門檻就整組適用),跟既有題同一張表、同一條適用性判定、同一個平台排除與樣板路徑。觸發字在 lumos 載入題表時從型錄〈情境決策表〉讀出,照 `_kt_trigger_re` 編成 `(?-i:…)` 包住的分大小寫樣式(局部分大小寫照既有 `kt-springdata` 的寫法);讀表函式 `_kt_decision_table`(新增,依表頭名稱取欄)跟第二批共用。改動行命中觸發字、但一段都切不出來時,這題視同不適用、不出現在樣板。型錄讀不到或格式壞 → 不加這一題(型錄隨工具鏈安裝,讀不到代表安裝壞掉,本 repo CI 由型錄格式檢查擋;沒有型錄就沒有題目可問);`pitfalls --diff` 與表態樣板碰到 kt 改動時印一行提醒;推送前表態那一道對 Android 的 kt 改動:型錄或讀表程式的檔找不到算環境不可用(照新增告警閘「工具沒裝 → 自動放行並記帳」的先例,提醒、記 fail-open 帳、不擋),檔在但讀表失敗判無法驗證、擋下(代碼審 r1 D3;2026-11-06 編排者裁定)。型錄與讀表程式從工具鏈來源找(來源 repo 裡的 lumos 用旁邊那份,複製進消費專案的走 `_lumos_src()`);`LUMOS_KT_CATALOG` 只在測試執行器裡生效。
- **逐列判定**:每一段的每一個候選列各是一題「這一列適不適用這段程式;適用的話有沒有照做」。照做=照那一列的標準寫法、或照那一列「不適用時」寫的例外寫法寫對。決策表的列不互斥(例:並行與失敗連坐可以同時成立),所以一段可以有多列適用。
- **情境表態**:`kt-situation` 適用時只收 satisfied,欄位是 `segments`(不用頂層 `evidence`;表態驗證遇到這一題改驗 `segments`):每段一筆 `{seg, rows: {D-<n>: {applies, variant, evidence}}}`,每個候選列都要答;`applies` 為真時 `variant`(`main` 對證據樣式的 `主:`、`alt` 對 `例外:`)與 `evidence`(單一 `path:line`,要落在這一段的段範圍內,不是整個函式)必填。換列的列(「不適用時」標 `(換列)`)不准選 `alt`。這一題不收 na、todo、tension;機器判不了、要人裁的出口是範圍 5 的段放行。
- **證據樣式**:決策表新增一欄,`主:` 與 `例外:` 兩段,各寫一到三條反引號包住的 Python 正規式;第一條要在 `evidence` 那一行(剝過註解與字串)上找得到,其餘每一條要在段材料裡找得到(且)。寫不出字面特徵的(標準寫法是「不要寫某樣東西」或「照某個順序」,例 D-2 循序呼叫)寫 `(無)`,那一列只靠盲判;「不適用時」是換到別列的,格子開頭標 `(換列)`、`例外:` 寫 `(無)`(工具只認這個標記)。每條正規式要編譯得過,由第一批的型錄格式檢查驗;每列樣式附正例與反例,由規則包自檢經真的切段與核對程式跑過(正例要對得上、反例要對不上;推送前對不上只提醒),壞寫法跟標準寫法只差在語意時那一段寫 `(無)`。證據樣式只是「有照做」的必要條件,用對沒用對交給盲判。
- **盲判**:一個沒看過作者表態的代理,拿工具產生的材料逐段逐列判 `{applies, followed}`(`followed` 只在適用時填)。材料由 `lumos code-loop blind-judge --template` 產生,只含每段的身分、檔名、段範圍的行號(同一個函式裡有兩段時,盲判靠它知道判哪一處)、段材料、候選列的「情境/標準寫法/不適用時」三欄,不含任何表態內容。
- **仲裁盲判**:作者與第一個盲判在某段某列對不上時,再派一個全新的代理只判那幾個(段,列)(`--template --disagreements` 產生)。
- **票**:每個(段,列)上,作者的票是 `(applies, 照做)`(作者答適用就是宣稱照做);盲判的票是 `(applies, followed)`;不適用時票就是 `(不適用)`。兩票相同才算一致。

## 範圍

1. **決策表加欄並由程式讀**:型錄〈情境決策表〉加「證據樣式」欄(列編號 `D-<n>` 已在第一批型錄合併時加上);`_kt_decision_table` 依表頭名稱讀出列編號、情境、標準寫法、不適用時、觸發字、證據樣式。列編號只准往後加、不准重排或重用(刪列時那一列標「(停用)」留著);第一批型錄格式檢查驗連號、停用列與證據樣式能編譯。
2. **情境題接進表態閘**:`_STACK_QUESTION_SPECS["kt"]` 多 `kt-situation` 一題,觸發字表 `_STACK_TRIGGERS` 照既有的載入時編譯一起編;平台排除、樣板、`--carry`、改碼後過期全走既有路徑。段要讀被推版本的檔,所以切段不在 `_stack_applicability`(它只收各棧的增刪行文字)裡做,而是在表態樣板與表態核對兩處、拿到範圍與版本之後呼叫新函式 `_kt_situation_segments(repo, 範圍, 版本)`;`_stack_applicability` 只判「觸發字有沒有中」。表態樣板對 `kt-situation` 多印每段的身分、檔:行範圍與候選列。`stack_questions.gate` 設 `high-only` 或 `off` 時這題與盲判核對跟著既有規則不跑。
3. **表態對程式**(推送前,在表態那一道裡):重算被推版本的情境段;每段每個候選列查作者的答案:缺段或缺列 → 擋;`applies` 為真而 `evidence` 不在段範圍內 → 擋;那列那個 variant 的證據樣式不是 `(無)`,而第一條不在 evidence 那一行、或其餘任何一條不在段材料裡 → 印提醒(附那列的標準寫法、證據樣式與段放行指令)、記一筆治理帳(待盲判),不擋(代碼審 r2 換形狀,見〈依據來源〉)。
4. **盲判記錄與核對**:
   - `lumos code-loop blind-judge --template [--disagreements|--missing] [--diff <範圍>] [--at-sha <提交>]`:材料一律從被推的版本讀(預設 HEAD,範圍預設同 `code-loop check`);每份最多 30 段,超過就分成多份印;`--missing` 列出還有任何一個候選列沒有第一盲判的段(只列缺的那幾列)。
   - `lumos code-loop blind-judge <結果.json> [--arbiter] [--branch <名>] [--at-sha <提交>]`(旗標意思同 `code-loop dispositions`):結果每段一筆 `{seg, rows: {D-<n>: {applies, followed, reason}}}`。**先整份驗證**(段身分對得上被推版本的某一段、列在那段的候選列裡、`applies` 與 `followed` 是布林、同一份檔裡同一段只出現一次、沒有不認得的欄位),有一筆不合就整份拒收(rc2)、什麼都不寫;全過才寫:先寫治理帳一筆 `blind-judge` 事件(帶 `written_at`,去重鑑別子照 `dispositions`、`recall-miss` 補進治理帳讀入的欄位表與去重鍵;事件種類登記進 `LOOP_NOT_CLOSE_EVENTS`),再併進標記檔 `governance/code-loop/<分支>.blind-judge.json`(以段身分為鍵、每列 `first` 與 `arbiter` 兩格;同一格已有值就不覆蓋,印「已有記錄,以第一筆為準」)。讀側:標記檔優先,沒有就把治理帳裡這個分支所有 `blind-judge` 與 `situation-waive` 事件依檔案行序重建(每格取第一筆)。寫入沿用表態那一組治理帳與標記檔的寫入函式,不另抄。
   - 推送前核對(表態那一道裡):每段每列要有 `first`;沒有 → 擋,訊息印「跑盲判」的指令。作者票與 `first` 票一致 → 過;不一致 → 要有 `arbiter`,沒有 → 擋並印 `--template --disagreements` 指令;`arbiter` 票等於作者票 → 過(記「仲裁採作者」);否則 → 擋,印三方的票與理由,出口是改碼(段材料變、身分變、重判)或改表態後重核,或範圍 5 的段放行。
   - 同一段只認第一筆盲判;改了段材料就是新的一段,要重新判——改一個無關空白就能換身分重抽,這是內容綁定的代價,由統計的「同一份程式被重判幾次」看(範圍 7)。
5. **段放行(人裁出口)**:(代碼審 r1 D2 提前上線,形狀改成直接沿用 `lint-waive`:`lumos lint-waive kt-situation:<段身分> --rule kt-situation --file <檔> --note "<理由>"`,記在新增告警閘的放行檔,理由門檻、origin、ack、doctor 計數同一套;證據樣式提醒後面印好這行;段放行只關掉那段的證據提醒,缺段缺列照擋。下面原寫的 `situation-waive` 指令、治理帳事件與標記檔的 `waived` 格等範圍 4 有那套帳時再對齊)原設計:`lumos code-loop situation-waive <段身分> --reason "<理由>"`,形狀照新增告警既有的 `lint-waive`:理由門檻同表態 na;沿用 `_waive_origin_tty` 判是不是人在終端下的、記 `origin: ai|human`;AI 下的放行在 doctor 與推送前小結持續列出,直到 `--ack`。寫治理帳一筆 `situation-waive` 事件(登記進 `LOOP_NOT_CLOSE_EVENTS`)並併進同一個標記檔的 `waived` 格;核對時那段整段放行——範圍 3 的表態對程式(缺列、evidence、證據樣式)與範圍 4 的盲判核對都略過,印 ⚠、計數(已改:現在只略過證據樣式提醒,缺段缺列與答案形狀照擋,見上面括號);統計時那段的每個候選列各算一次放行。

## 天花板

1. 證據樣式只證「長得像照做了」,不證「用對了」;盲判本身是模型判斷,會錯。
2. 盲判看不到作者答案,但看得到同一份程式;程式寫得誤導時(例:變數名騙人)三方可能一起錯。
3. 觸發字沒出現的情境(用自家包裝函式藏起來的寫法)不會出段,只能靠代碼審席位的 recall-miss 回報補觸發字。
4. 只看增行:把正確寫法刪掉改壞的改動,若新寫法沒有命中任何觸發字就不出段,靠規則包告警與代碼審。
5. 段材料是從命中行往上最近的頂層或類別層宣告(函式、屬性或類別,最多 120 行);跨宣告的情境(例:並行的兩支呼叫分在兩個函式、dispatcher 在建構子而 withContext 在方法裡)盲判看不到全貌,證據樣式的第二條以後也不寫跨宣告的特徵。
6. 消費專案的推送前閘或 CI 找不到工具鏈來源的型錄時這題不核,只提醒並記 fail-open 帳(環境不可用,照新增告警閘先例);主擋在裝好工具鏈的本機推送前閘,統計看 fail-open 次數。
