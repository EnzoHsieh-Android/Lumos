# Android寫法語意情境表態與盲判_計劃

> 白話:型錄裡有一類寫法是機器看長相判不出來的——「這兩支呼叫互不依賴嗎」「這是事件還是狀態」——要先判情境才知道該用哪種寫法。這份計劃讓這類情境走三步:①改動碰到某個情境的觸發字時,AI 推送前要表態「這段屬於決策表哪一列、照那列的寫法寫在哪一行」;②機器到那一行核對,真的出現那列寫法的特徵才算(防「寫了規範卻完全沒參考」);③另派一個沒看過 AI 答案的盲判代理,只看程式與候選列自己判一次,兩邊對不上就擋,再派第二個盲判仲裁。使用者原話(2026-11-05):「判斷當下是什麼情況、該用什麼的是 AI,但有沒有真的照做是機械執行」「我怕出現寫了但完全沒參考的狀況」「有沒有必要起一個 subagent 來覆檢這個情境的狀態,沒有 context 比較沒有偏誤?」→「好,加進去」。是 [[Projects/Android協程與API寫法機械檢查標準_計劃]] 分批表的第三批。

PRIOR-ART: ①同 repo:棧別提問表態閘([[Systems/棧別提問表態閘]])已有「觸發字決定哪題適用 → 推送前逐題表態 → 機器驗證據存在」整條路,四種狀態、改碼後表態過期、治理帳加標記檔的讀寫都現成;本案在它上面多一組題目,並把 satisfied 從「驗行號存在」加嚴成「驗那一行長得像那列的寫法」,不另起新閘。張力表態([[Projects/兩席相反時端出張力_計劃]])是「兩方意見相反時攤開給人裁」的既有形狀。②世界解:架構決策要靠可執行的檢查守住、不靠文件(架構適應度函式,ADR 每條對應至少一支自動檢查,https://concepts.dsebastien.net/concept/architectural-fitness-functions/ ;ArchUnit 把決策寫成測試,https://medium.com/publicis-sapient-france/enforcing-architecture-decisions-with-archunit-4d8b9f61cf4a )——採用「每列決策要有機器核得到的特徵」。③單選標註:Cohen's kappa 要求每個樣本恰好落在一個互斥類別(https://en.wikipedia.org/wiki/Cohen%27s_kappa ),所以比對單位要是「一段程式選一列」,不能是「每列各問一次」(r1 三席實測後者在多列重疊時無解)。④盲判:LLM 當評審時,讓它先看到別人的標籤會被帶著走(錨定),看不到的盲判跟嚴格標註者較一致(https://www.researchsquare.com/article/rs-10688342 ,預印本未同儕審);評審一致度要用扣掉偶然一致的指標看,單看相符率會高估(https://arxiv.org/html/2606.19544 )——採用「盲判材料由工具產生、不含作者答案」,一致度統計用 Cohen's kappa 而不只是相符率。不選:推送前閘裡直接呼叫模型(推送閘不呼叫模型是既有原則,[[Projects/Android寫法寫完當下自動檢查_計劃]]〈不做〉同一條)。
RETIRE-IF: 上線八週後在消費專案用 `lumos gov --stats` 看:①某一列被作者選中的段數 ≥ 20、正一致率 ≥ 0.95 而且盲判全判照做 → 那一列拿掉盲判、只留證據樣式核對(盲判沒抓到東西);②某一列的段放行超過該列段數的一成 → 那列的證據樣式重寫或改成 `(無)`;③整組情境段八週內少於 5 段 → 撤掉整組,只留告警帶寫法。

## 用詞

- **情境段**:這次改動在被推版本的增行裡,命中〈情境決策表〉任一列觸發字的區段。同一支檔裡相鄰(間隔不超過 3 行)的命中增行併成一段;段的範圍是那幾行前後各 3 行。只看增行:被刪掉的寫法在推上去的版本裡不存在,沒有東西可核,不出段。比對前先用 Kotlin 版的剝註解與字串函式 `_kotlin_strip`(新增,跟 [[Projects/Android寫法寫完當下自動檢查_計劃]] 的改檔前推列共用,兩案誰先實作誰建)。
- **段身分**:`sha256(檔路徑 + "\0" + 段範圍的原文 + "\0" + 候選列編號清單)` 取前 16 碼(段範圍是命中增行前後各 3 行;`_kotlin_strip` 保留行數,剝掉的字元換空白)。內容不變身分就不變(rebase、壓提交後盲判記錄照樣有效);程式一改身分就變(舊記錄自動不算)。
- **候選列**:這一段命中觸發字的所有決策表列。觸發字比對用 `_kt_trigger_re`(跟第二批共用,同一份規則):每個觸發字 `re.escape` 後前面不准緊接英數或底線、後面不准緊接英數或底線(前面是 `.` 可以,方法呼叫 `.flatMapLatest` 照樣中),分大小寫。
- **證據範圍**:比證據樣式用的範圍,比段範圍寬:從段的第一個命中增行往前 20 行到最後一個命中增行往後 20 行(多行 `async { … }` 區塊的 `.await()` 常在 10 行以外)。evidence 行要落在證據範圍內。
- **情境題**:棧別題表 `kt` 題組新增一題 `kt-situation`(標 `android_only`),跟既有題同一張表、同一條適用性判定、同一個平台排除與樣板路徑。它的觸發字在 lumos 載入題表時從型錄〈情境決策表〉讀出來,每個觸發字照 `_kt_trigger_re` 的規則編成 `(?-i:…)` 包住的分大小寫樣式(既有題組整組不分大小寫,局部分大小寫照既有 `kt-springdata` 的寫法);改動行命中觸發字、但剝掉註解與字串後一段都切不出來(例如只有刪行命中)時,這題視同不適用、不出現在樣板;讀表函式 `_kt_decision_table`(新增)跟第二批共用。型錄讀不到或格式壞 → 不加這一題;提醒只在 `pitfalls --diff`、表態樣板與 `code-loop check` 碰到 kt 改動時印一行(其他指令不印);本 repo CI 由第一批的型錄格式檢查擋型錄壞掉。
- **情境表態**:`kt-situation` 適用時只收 satisfied,而且多一個欄位 `segments`:每段一筆 `{seg, row, variant, evidence}`,`row` 是候選列之一或 `none`;`row` 不是 `none` 時 `variant`(`main` 對證據樣式的 `主:`、`alt` 對 `例外:`)與 `evidence`(單一 `path:line`,要落在那一段的證據範圍內;不收 `test:`)必填。決策表「不適用時」寫「見下一列」這類換列的,作者應選那一列而不是 `alt`;那種列的 `例外:` 寫 `(無)`。`segments` 要涵蓋被推版本重算出來的每一段,多的段(身分對不上)忽略並提醒。這一題不收 na、todo、tension(那三種會讓作者繞過整套核對);機器判不了、要人裁的出口是範圍 5 的段放行。
- **證據樣式**:決策表新增一欄,`主:` 與 `例外:` 兩段,各寫一到三條反引號包住的 Python 正規式;一段裡的每一條都要在證據範圍(剝過註解與字串)裡找得到才算(且)。寫不出字面特徵的(標準寫法是「不要寫某樣東西」或「照某個順序」,例如 D-2 循序呼叫)寫 `主: (無)`,那一段只靠盲判核。證據樣式只是「有照做」的必要條件,不是充分條件;用對沒用對交給盲判。每條正規式要編譯得過,由第一批的型錄格式檢查驗。
- **盲判**:一個沒看過作者表態的代理,拿工具產生的材料逐段判:這段屬於哪一個候選列(或 `none`)、`row` 不是 `none` 時有沒有照那列寫(`followed`)。材料由 `lumos code-loop blind-judge --template` 產生,只含每段的身分、檔名、段範圍加前後各 10 行、候選列的「情境/標準寫法/不適用時」三欄,不含任何表態內容。
- **仲裁盲判**:作者與第一個盲判對不上的段,再派一個全新的代理判(材料同上,只列那幾段,`--template --disagreements` 產生)。
- **票**:作者的票是 `(row, 照做)`;盲判的票是 `(row, followed)`;`row` 是 `none` 時票就是 `(none)`。兩票相同才算一致。

## 範圍

1. **決策表加欄並由程式讀**:型錄〈情境決策表〉加「證據樣式」欄(列編號 `D-<n>` 已在 2026-11-05 第一批型錄合併時加上);`_kt_decision_table` 讀出每列的列編號、情境、標準寫法、不適用時、觸發字、證據樣式。決策表列編號只准往後加、不准重排或重用(刪列時那一列標「(停用)」留著),免得舊記錄與統計對錯列;第一批型錄格式檢查驗連號與停用列。
2. **情境題接進表態閘**:`_STACK_QUESTION_SPECS["kt"]` 多 `kt-situation` 一題(見〈用詞〉),觸發字表 `_STACK_TRIGGERS` 照既有的載入時編譯一起編;平台排除、樣板、`--carry`、改碼後過期全走既有路徑。表態樣板對 `kt-situation` 多印每段的身分、檔:行範圍與候選列,讓作者填 `segments`。`stack_questions.gate` 設 `high-only` 或 `off` 時這題與盲判核對跟著既有規則不跑。
3. **表態對程式**(推送前,在表態那一道裡):重算被推版本的情境段;每段查作者的 `segments`:缺段 → 擋;`row` 不在候選列也不是 `none` → 擋;`row` 不是 `none` 而 `evidence` 不在證據範圍內 → 擋;那列那個 variant 的證據樣式不是 `(無)`,而證據範圍裡少了任何一條 → 擋並印那列的標準寫法與證據樣式。
4. **盲判記錄與核對**:
   - `lumos code-loop blind-judge --template [--disagreements|--missing] [--diff <範圍>] [--at-sha <提交>]`:材料一律從被推的版本讀(預設 HEAD,範圍預設同 `code-loop check`);每份最多 30 段,超過就分成多份印,每段都有自己的身分,分幾份不影響核對;`--missing` 只列還沒有第一盲判的段。
   - `lumos code-loop blind-judge <結果.json> [--arbiter] [--branch <名>] [--at-sha <提交>]`(旗標意思同 `code-loop dispositions`;寫入沿用表態那一組治理帳與標記檔的寫入函式,不另抄):結果每段一筆 `{seg, row, followed, reason}`。寫入時先寫治理帳一筆 `blind-judge` 事件(帶 `written_at`,去重鑑別子照 `dispositions`、`recall-miss` 的寫法補進治理帳讀入的欄位表與去重鍵;事件種類登記進 `LOOP_NOT_CLOSE_EVENTS`),再把結果併進標記檔 `governance/code-loop/<分支>.blind-judge.json`(以段身分為鍵、`first` 與 `arbiter` 兩格;同一段同一格已有值就不覆蓋,印「已有記錄,以第一筆為準」)。讀側:標記檔優先,沒有就把治理帳裡這個分支所有 `blind-judge` 事件依檔案行序重建(每格取第一筆),不是只取最後一筆。
   - 盲判結果裡的段身分若對不上被推版本的任何段 → 忽略並提醒(多半是程式又改了)。`row` 不在那段的候選列也不是 `none` → 寫入時拒收(rc2)。
   - 推送前核對(表態那一道裡):每段要有 `first`;沒有 → 擋,訊息印「跑盲判」的指令。作者票與 `first` 票一致 → 過;不一致 → 要有 `arbiter`,沒有 → 擋並印 `--template --disagreements` 指令;`arbiter` 票等於作者票 → 過(記「仲裁採作者」);否則 → 擋,印三方的票與理由,出口是改碼(段身分變、重判)或改表態後重核,或範圍 5 的人工放行。
5. **段放行(人裁出口)**:`lumos code-loop situation-waive <段身分> --reason "<理由>"`(理由門檻照表態 na 的既有門檻),寫治理帳並併進同一個標記檔的 `waived` 格;核對時那段印 ⚠ 放行、計數。這是機器判不了時給人的出口,跟既有新增告警的放行同一個形狀。
6. **代碼審手冊**:lumos-code-loop 手冊在「表態」那一步之後加「盲判」:①`lumos code-loop blind-judge --template > /tmp/<分支>-bj.json`(段多時會印成多份,每份派一個代理)②每份派一個全新的 sonnet 代理,派工詞只放那份材料與作答格式,寫明不得讀表態檔與 `governance/code-loop/` ③`lumos code-loop blind-judge <結果>` ④`lumos code-loop check` 說有不一致時,`--template --disagreements` 再派一個全新代理、`--arbiter` 寫入。`pitfalls --diff` 在有情境段時多印「要跑盲判」與這幾行指令。推送前沒有盲判記錄就擋,所以不靠人記。
7. **統計**:`lumos gov --stats` 的表態段加情境題:每列被選為作者 row 的段數、該列的正一致率(作者選這列的段裡,第一盲判也選這列且照做的比例)、整體作者與第一盲判的相符率與 Cohen's kappa(類別=票:每列分「照做」與「沒照做」兩類,加 `none`,跟閘比的是同一個東西;跨段合算;段數少於 20 或偶然一致率等於 1 時印「樣本不足」不印數字)、仲裁採作者與採盲判的次數、段放行次數。同一段身分只算一次(取最早的記錄)。

**不做**:不在推送前閘或 CI 呼叫模型(盲判在代碼審迴圈裡跑,推送前只核記錄);不改既有九題與其他棧的題;證據樣式不做跨檔或型別判斷;不替 Codex 編排寫盲判派工(Codex 照 `--template` 輸出自己派)。

## 實務隱患

- **證據樣式太鬆被敷衍**:作者在段裡剛好有那幾個字就過;這是必要條件,盲判那一道補。`(無)` 的列完全靠盲判。
- **證據樣式太嚴誤擋**:同一寫法有多種長相(具名參數、換行、別名匯入)。正規式比對的是整段(含前後 3 行)而不是單一行;誤擋的出口是段放行並計數,RETIRE-IF ② 看比例。
- **盲判成本**:一份材料最多 30 段;仲裁只對不一致的段;段身分綁內容,rebase 與壓提交不用重派。觸發字收了常用字會讓段數暴增——第一批型錄格式檢查用停用字表擋(2026-11-05 實作時補進第一批範圍 1 與 S3)。
- **盲判被帶風向**:材料由工具產生、不含表態;編排者仍可能在派工詞裡夾帶自己的答案——依本工具「單人、AI 依序操作、不防 AI 刻意偽造」的威脅模型不另防,手冊寫明禁止;同一段只認第一筆盲判,重派到同意為止的路被堵掉。
- **段放行被濫用**:`situation-waive` 只靠理由門檻,AI 也能自己放行;每次推送印放行段數,統計列每列放行比例,RETIRE-IF ② 看比例;依單人威脅模型不另防。
- **型錄版本落差**:作者機器與 CI 的工具鏈版本不同時,觸發字與候選列可能不同,段身分對不上;本機推送前閘用本機型錄判,CI 讀不到型錄時這題不出(印提醒)。消費專案的 CI 是後盾,主擋在推送前。
- **舊否決對照(2026-11-05 跑 `lumos rejections`,438 行,按概念比對)**:[[Systems/棧別提問表態閘]]〈邊界與刻意不做〉寫「不用 LLM 判答案;等 auto-na 比例與 recall-miss 帳說 regex 不夠再開」。本案的盲判就是用模型判答案,跟那條相反;依據是使用者 2026-11-05 明確要求加覆檢代理(見白話段原話),而且只對型錄情境段、在代碼審迴圈裡跑、推送前只核記錄,不動既有題組。[[Systems/doctor-irreversible-hint]] 否決「LLM 判可逆性」是另一件事(推送前提醒的判斷),不衝突。表態閘那篇的那一句在本案落地時改寫成「情境題例外,見本計劃」。
- **跟第二批改同一區**:第二批在推送檢查的收集模式加「只跑新增告警與表態」選項;本案在表態判定內部加情境題核對,改的函式不重疊。兩案共用讀表與 Kotlin 剝字串兩支新函式,誰先實作誰建。
- **跟既有「證明 satisfied 屬實」的另一條路分工**:併發與 N+1 七題的破壞測試背書證「有測試咬住」,本案的證據樣式證「寫法特徵在場」,對象不同題,不互相取代。
- 已排除:金流:不碰付款或點數
- 已排除:對外送出:盲判在本機代理跑,不送資料到第三方以外的地方(代理本來就是編排者在用的模型服務)
- 已排除:不可逆:新增題目與記錄,退提交即回原狀;治理帳是追加
- 守衛面:改推送前表態閘的判定、會擋人,屬守衛面,走完整設計審(不寫成已排除)
- 資安:不新增自動執行命令的地方;盲判材料只含這次改動的程式段

## 驗收條款
