# 設計審後端失敗與未知狀態_計劃

> 白話:設計稿要動到「呼叫別人的系統」時,多逼作者回答四件事——對方逾時了你怎麼知道成不成功、每一步壞掉時資料會變什麼狀態、新舊版本同時在跑會怎樣、出事時誰會知道。先做小實驗看有沒有用,有用才接進 lumos。

## 問題與範圍

- 問題:使用者讀的後端教材裡,哪些審查角度最該補進 lumos 的設計階段;要不要寫成 skill。
- 範圍:設計審(散文設計稿)的作者必答題與規格閘;代碼審只在對照時提。
- 不在範圍:改代碼審的審查員鏡頭(那條已由 [[Projects/代碼審資料狀態鏡頭_計劃]] 與 [[Projects/代碼審前後端角色鏡頭_計劃]] 處理)。

## 現況(2026-10-02,最新主線,以程式碼為準)

- 設計稿碰到金流字眼時,pitfalls 會要求作者在「實務隱患」節回答通用四題加一題金流專題(冪等鍵、重複扣款、部分失敗補償與對帳);其他對外呼叫(第三方 API、跨服務、佇列)只有對外送出那類的重試與去重題。
- 規格閘要求風險高的設計稿有回退節,問退回哪一版、怎麼退;沒問退回後舊版讀不讀得懂新資料。
- 代碼審的後端角色卡只有 API 相容與授權兩題。
- 用結果未知、寄件匣、狀態機、失敗矩陣、混合版本、新舊版本搜主程式與兩個審查 skill,都是 0 筆。

## 從事故看到的一件事

- POS 專案的「客掃 QR 輪詢回終態被當成已付」事故:正確規則(只有查單確認錢收到才算付款完成)在設計審三輪就被指出,也寫進了程式註解,但只接到換付款方式那條路徑,主付款流程沒接上,於是沒收到錢就關單。
- 意思是:光問「怎麼判成功」不夠,還要列出**所有能把資料推進到「已完成」的路徑**,逐條寫它們檢查了什麼。這是候選第②題要加那一句的原因。

## 最小實驗(先寫設計、再開跑,結果不回頭改標準)

- 素材:兩件真實付款事故改寫成需求(不洩漏答案)。
  - 需求一:POS App 串金流做客掃 QR 付款(對應三件事故:輪詢終態當已付、取碼失敗後再滑一次直接關單、改金額或換錢包後交易編號沒換)。
  - 需求二:自助點餐機後端新增付款結果通知端點(對應事故:端點套了自家 API key 檢查,金流的通知全被擋,沒人發現)。
- 分組:每份需求 A、B 兩組各 3 次,作者代理用 sonnet。
  - A 組:照現況,在「實務隱患」節回答 pitfalls 現在會印的五題。
  - B 組:A 組全部,再加「失敗與未知狀態」節回答新四題。
- 評分:一個不知道分組的評分代理,把同一份需求的 6 份設計稿打散編號,依事先寫好的標準逐條判「有/部分/沒有」並引原句。
- 判準:B 組在事故根因項目的命中明顯多於 A 組(兩份需求合計至少多 3 項,且沒有任何一項 A 組比 B 組多 2 項以上),才進接線設計;否則照撤除條件收案。
- 限制:樣本小,只看方向;兩份需求都碰金流,「非金流的對外呼叫也要問」這點沒測到。

## 實驗結果(2026-10-02)

- 詳見 [[Verification/2026-10-02_設計審後端未知狀態題小實驗]]。合計 A 組 23 分、B 組 24.5 分,沒過門檻,四題整組不接線(決策 d1)。
- 天花板效應:現行金流題加上目前模型,已經寫得出這幾件事故的主要對策。對照「從事故看到的一件事」那節,這幾件事故的破口在實作只接到一半路徑,不在設計時沒想到。
- 唯一拉開的是「途中任一步失敗都復原狀態、所有能關單的路徑都經過付款確認」(A 1.5、B 3)。這一句是看到結果才挑出來的,只能當下一個假設,不能當結論。

## 下一步(2026-10-02 使用者同意做第二輪,結果見下一節)

- 原候選:只測「列出所有能把資料推進到已完成的路徑、各自檢查什麼」這一句。

## 第二輪實驗:只測「完成路徑」一句,放在代碼審(2026-10-02,開跑前寫定)

- 使用者同意做第二輪。改放代碼審,因為第一輪顯示破口在實作:規則已知,只接到一半路徑。
- 素材:四個「引入事故」的提交,審查代理只拿到當時的改動與相關檔案全文,沒有版本紀錄。
  - P1:POS 把 QR 付款成功判斷改成輪詢回 2000(4 行改動)。
  - P2:POS 加上「付款進行中就跳過 QR 與刷卡分支」的防重入條件。
  - P3:POS 替換付款方式那條路徑抽出收款判斷規則(必須看查單碼),主付款流程沒跟著改。
  - L1:本 repo 收工檢查加上圖譜同步點名;它判斷「有沒有改程式」只看編輯工具紀錄(非金流對照)。
- 分組:A 組用代碼審派工範本現行的正確性鏡頭問句;B 組多一句「完成路徑:列出所有能把資料推進到已完成類終態的路徑(含重試、重按、例外分支、提早 return、別的入口),逐條寫它檢查了什麼;同一條規則只套在其中幾條,其他條就是洞」。每案每組 2 次,審查代理用 sonnet。
- 判準(席報告裡要有一條講到這個情境才算抓到,只點到相關區域不算):
  - P1:指出 2000 或「交易完成」不代表錢收到(被拒、取消也可能完成),成功前要用查單結果確認。
  - P2:指出付款進行中的旗標若在某個失敗或提早結束的路徑沒被復原,下次結帳會跳過付款分支直接關帳,沒收到錢就關單;或指出關帳路徑本身沒檢查是否已收款。
  - P3:指出主付款流程仍用輪詢碼判成功,沒套用新規則。
  - L1:指出透過 Bash 寫檔改的程式(sed -i、重導向、python 寫檔)抓不到、閘門靜默放行;或指出用 git 判斷的那條只在圖譜已動過時才用到。
- 門檻:B 組合計抓到的次數比 A 組多至少 3 次(各 8 次),且沒有任何一案 A 組比 B 組多 2 次以上,才進接線設計。
- 評分:一個不知道分組的評分代理,把 16 份席報告打散編號後依上面判準判定。

## 第二輪結果與收案(2026-10-02)

- 詳見 [[Verification/2026-10-02_代碼審完成路徑一句小實驗]]。A 組 3/8、B 組 3/8,沒過門檻,不接線(決策 d2)。
- 兩輪合起來的結論:
  - 設計稿與代碼審的作者、審查者,用現行題目已經想得到大部分對策;多加題目沒有可見的差距。
  - 真正沒人抓到的,是程式碼外的事實:金流輪詢碼「完成」不等於收到錢、本 repo 多半用 Bash 改檔。這類事實該寫成圖譜的規則或事故筆記,靠推播送到審查員眼前,不是寫成審查問句。
- 本計劃照撤除條件收案;不另寫後端 skill。
