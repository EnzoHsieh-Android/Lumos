# 高風險測試證據加嚴_計劃

> 白話:現在越危險的功能,工具對它的測試反而管得越鬆——風險低的計劃要求每條新行為的測試在實作前先紅,風險高的只印不擋,交給設計審與代碼審。但審查本身也是 AI 在判斷,拿它補最重要的那一塊說不通。這份計劃讓推送前對「這次真的在實作的風險高計劃」做一次基準重播:把它新行為條款綁的測試,放到分岔點那一版的舊程式上跑,必須紅;放到推送版上跑,必須綠——證明測試真的在驗這次的改動,跟測試先寫後寫無關。預期值寫成一張表、每列寫需求來源,推送前整張表要有人簽(預設人簽,AI 簽也放行但記下來)。「紅要紅在斷言上」、建置檔讓測試不跑、改到的行跑變異測試這三件要讀 Gradle 的輸出,排第二批。

## 名詞

- 風險高/風險低:規格閘的門判定(`_door_judge`)判的:任一硬訊號命中(連到標了金流、對外送出、不可逆、守衛面的節點等),或〈實務隱患〉缺任一類「已排除」行,就是風險高;作者只能往嚴調。那四行「已排除」是作者自填的。
- 新行為條款:驗收條款裡沒標 `[keeps]`、綁了 `[test:]` 的那幾條;標 `[keeps]` 的是「維持既有行為」,測試本來就該綠。
- 推送版:推送範圍的終點那個提交(不是 HEAD、不是工作目錄)。
- 分岔點:推送版跟主線的 merge-base(主線用推送範圍指令找主線的 `_push_mainlines`);不是「上次推到哪」,所以同一條分支推第二次、壓過提交再推,分岔點都還是實作開始前那一版。
- 基準重播:開兩個隔離工作樹(`_isolated_worktree`,殺傷力驗證與修正關卡已在用),一個是分岔點、一個是推送版;把這次範圍裡新增或改過的測試檔(`_nodehome_is_test` 判的)從推送版複製進分岔點那一棵,正式程式碼留舊版;兩棵各跑一次計劃綁的測試(`_spec_gate_judge_items`,修正關卡已拿它在隔離工作樹裡跑;樹的準備也跟修正關卡共用)。新行為測試在舊版紅、推送版綠,叫「證實」。世界上同樣的做法叫 fail-to-pass(見調研)。
- 對照組:基準重播時,標 `[keeps]` 的條款測試在舊版也要綠;推送版那一棵的新行為測試要綠,也是對照——兩棵是同一種方式建的,環境壞了兩棵都會壞,不會只讓舊版紅。
- 弱證據:規格閘紅、綠之外的第三種判定,意思是「這次跑的結果證明不了什麼」——一支都沒跑到、篩選選中好幾支、被跳過(`_spec_gate_verdict`)。
- 生效日:程式常數 `_HIGH_RISK_EVIDENCE_SINCE`,純日期,寫法同 `_NOTE_LINT_PLAN_SINCE`,值在實作提交裡事先訂好、不早於合併日;計劃的日期取開頭欄位 `created` 與計劃第一次進 git 歷史的日期(`_plan_first_commit`)兩者較晚的,都讀不到才當成生效日之後。
- 預期值表:計劃裡一節 `## 預期值表`,底下一張表,逐列寫「哪條條款、輸入什麼、預期什麼、這個預期從哪條需求來」。
- 表指紋:整張預期值表的內容指紋,任一格改了任何一個字就變;換行符號、格子頭尾的空白不算。
- 簽核:有人看過預期值表、確認每列對得上需求,工具記下表指紋與簽的是人還是 AI。
- 治理帳與審查帳:治理帳是 `docs/.governance-log.jsonl`,各道閘的事件都寫這裡,進版控;審查帳是 `docs/.canary-log.jsonl`,消費專案預設被 git 忽略。本計劃新寫的事件與讀的簽核都只在治理帳。
- 考場:mOrangePos 的演練工作樹與只留本機的分支,拿來實機驗 lumos,不推、不併。
- 逃逸帳:審查放行之後,在實作、CI、正式環境才被發現的洞,用 `lumos loop escape` 記下來的帳。

## 問題與最小解

立案(2026-11-04,Enzo 原話):「風險高的靠review 補位？ 但是重點在於，風險高的測試，到底是不是實在的測試」「直接開新計劃，網路印證方向、做法，排除已有人實驗無效的坑」。設計審 r2 之後 Enzo 要求「搜世界解」,並裁「換成基準重播(推薦)」。

1. **風險高的計劃幾乎都沒有先紅的證據**:審查帳裡規格閘留痕 458 筆(2026-09-17 到 11-03)共 133 份計劃;每份取最新一筆看風險,風險高 102 份(77%);這 102 份裡,任何一筆留痕跑出過紅的只有 13 份(只看最新一筆是 7 份)。風險高的沒有紅燈版,推送前比對抓不到「預期值被改成實作的輸出」,只剩審查。
2. **預期值對不對需求,工具完全沒管**:先紅、紅燈版、防竄改比對都只證明「測試會抓錯」,證明不了預期值本身對;前面每一關都過、預期值寫成打八折而需求是打九折,照樣上線。現有 `lumos signoff` 記一筆「誰點了頭」(棄置合約時 `guard abandon` 會讀它帶的參照),不綁內容,也沒有推送前的閘讀它。
3. **「紅」不分原因**(第二批):Kotlin/Java 的測試輸出讀不出跑了幾支(`_RAN_EVIDENCE` 沒有這兩種),只能照退出碼判;編譯失敗、`--tests` 篩不到、被測程式還是 `TODO()`,全都判紅。

最小解:前兩輪設計審證明,要從帳上證明「實作前紅過」得接好幾個既有機制的接縫(r1 另寫一套翻帳、r2 沿用風險低的推送前檢查,兩輪各抓到大量誤擋與繞過)。改成推送當下直接從 git 算:分岔點的舊程式就是「還沒實作」的版本,在它上面跑新測試必須紅——不用帳、不用判設計審過了沒、不管先寫後寫,連「實作寫完再搬走造假紅」也不怕(重播用的是真的舊版)。預期值表與簽核另外新增。

PRIOR-ART:fail-to-pass 基準重播是世界上已有的做法:devops-cli 的 `ci fail-to-pass`(在暫存目錄建分岔點的樹、把推送版的測試覆蓋上去、只認呼叫階段失敗、收集錯誤不算數、要有附理由的不適用出口、另設自檢重播已知提交)、PRProof(分岔點 git 工作樹加複製改過的測試檔,舊版紅且推送版綠才判 PROVEN,跑不可靠回 ERROR);只要求「修前紅、修後綠」不夠的實證(UTBoost,ACL 2025:Verified 裡 26/500 題測試不足、345 個錯誤修補被判通過)與 PRProof 自承「錯的修補配錯的測試照樣 PROVEN」,所以預期值另外要人簽。簽核綁內容指紋、內容改了舊簽作廢,同 GitHub「推新提交作廢舊核可」與 Gerrit copyCondition;表格解析照 GFM 表格規則(格內 `\|` 是字面管線),欄數不符時不照 GFM 補或丟,一律擋。借用:`_isolated_worktree` 與修正關卡的樹準備(抽成共用)、`_push_mainlines`、`_spec_gate_judge_items`、`_spec_gate_run_clauses` 的合條款規則、`_spec_gate_twoway_static`、`_spec_gate_twoway_run_verdict`、`_clause_check_twoway`、`_redbase_row_reason` 的逾時規則、`_is_code_file`、`_nodehome_is_test`、`_plan_first_commit`、`_NOTE_LINT_PLAN_SINCE` 的生效寫法、`_h2_section_lines`、`_real_chars`、`_waive_origin_tty`、lint-waive 的 `origin` 欄與端到端驗收的簽核人取法、既有 `signoff` 閘名;自建:基準重播的串接、預期值表解析、表指紋與兩道推送前檢查。
RETIRE-IF:生效後連續 90 天,治理帳的 `base-replay-failed` 與 `expected-unsigned` 兩種擋下事件都是 0,而且同期逃逸帳裡沒有一筆描述是「測試預期值抄實作」或「測試沒在驗」——代表這兩道沒在擋任何東西,改回只印;或 `expected-signed` 事件裡 origin 是 ai 的連續 90 天佔 100% 且逃逸帳沒有預期值類的洞,簽核這道改成只記不擋;或 `base-replay-skipped` 事件(含寫了 `base_replay_skip`、找不到主線、平台釘不住版本、測試指令只能整套跑)佔要重播的一半以上,代表重播在實務上跑不起來,回頭檢討做法。

## 調研結論(2026-11-04,四路網路調研)

- **只靠先紅不夠,要配紅燈版與變異測試**:UTBoost(上)與 PatchDiff(Wang、Pradel、Liu,ICSE 2026:通過測試的修補 29.6% 行為跟標準解不同)。先紅是入場券;「事後把實作搬走造假紅」查不到專門對策,對最終程式跑變異測試跟先寫後寫的順序無關,是第二批要補的那一塊。
- **Gradle 報告分不出紅的原因**:Gradle 的 JUnit XML(`JUnitXmlResultWriter`)把 `errors` 寫死成 0,所有例外都歸 `<failure>`;要看失敗的型別。Truth、AssertJ、kotlin.test、MockK 的 verify 都丟 `AssertionError` 子類;Kotlin `TODO()` 丟 `NotImplementedError`(繼承 `Error`,不是 `AssertionError`)。
- **證明「紅發生在實作之前」靠不住**:用提交順序認定 TDD 的研究(Borle 等,EMSE 2017)得放寬到晚一週提交也算才收得到樣本;Fucci 等(TSE 2017)發現順序本身沒有重要影響。不走這條。
- **AI 看得到實作,預期值就會照實作寫**:Konstantinou 等(2024/2026 v2)斷言「mainly capture the actual program behavior」;Charoosaei 等(2026)AI 測試 8–17% 把錯誤行為寫成預期值,其中 83–91% 之後一直通過。支持「預期值逐列寫需求來源」。
- **人工核可會鬆**:審查留言只有 14% 講缺陷(Bacchelli、Bird 2013);先看到 AI 的答案再問人對不對,人多半只看 AI 指的地方(Tufano 2024)。所以只對風險高的要簽,表要小,每列帶出處。
- 已被證明無效、這份計劃避開的:拿 XML 的 failure/error 分紅因;把 LLM 判官當唯一的閘(SWE 類任務上監看器只抓 42–50% 作弊,ImpossibleBench);只靠 TDD 提示詞(TDAD 預印本:回歸錯誤升到 9.94%);用提交順序證明先寫測試;簽核不綁內容(簽完再改預期值等於沒簽)。
- 設計審 r1(2026-11-04)後補查:GFM 表格規則裡格內 `\|` 是字面管線;欄數少於表頭補空格、多於表頭丟掉多的(本計劃不照這個寬鬆做法,見 PRIOR-ART)。

## 做法

### 第一批(本次實作):推送前基準重播,加預期值表與簽核

0. **最小實驗(設計審 r3 後,2026-11-04)**:在本 repo 用 `_isolated_worktree` 開推送版(加一個新函式與呼叫它的新測試)與跟主線的分岔點兩棵樹,把測試檔覆蓋進分岔點那一棵,用 `_spec_gate_judge_items` 跑。結果:呼叫新函式的測試推送版綠、分岔點紅(例外:舊版沒有這個函式);不依賴改動的新測試兩邊都綠(會被擋成「舊程式上就綠」);既有測試兩邊都綠。每支測試每棵樹約 2.7 秒。另外量到:這個 repo 的測試程式只要有紅就保留暫存現場(`gctl-run-*`),沒有開關可關;重播在舊版上本來就要紅,所以要自己收(第 4 點)。指令與輸出記在 `governance/review-reports/高風險測試證據加嚴/r3-intake.md`。
1. **哪些計劃要重播**(`lumos spec-gate --push-check` 裡新增一道,排在既有的風險低檢查之後;pre-push 呼叫,CI 不跑,見〈不做〉):
   - 計劃要符合:檔名以 `_計劃.md` 結尾、`type: project`(同 `_nl_rule_lands_in` 對計劃的認法)、至少一條 `[SN]` 條款;在推送版裡(第 3 點)門重判是風險高;status 是 doing,或推送版是 done 而分岔點不是 done(這次才完成);生效日判定見第 6 點。
   - 觸發:推送範圍(用推送版對分岔點算 `git diff --name-status -M`)改到這份計劃檔,而且改到至少一支 `_is_code_file` 判成程式檔、`_nodehome_is_test`(帶 `_nodehome_layout` 的專案目錄設定)判成不是測試的檔。只改計劃、卷證、帳本、文件的推送不觸發;只推測試(TDD 先推紅的測試)也不觸發——推送版本來就還沒綠。
   - 只因連到同一個系統節點被拉進推送前檢查的計劃,不重播、不查表、不查簽。
   - 計劃開頭欄位 `base_replay_skip` 有理由時不重播:理由用 `_real_chars` 數至少 10 個字;印出理由、寫一筆治理帳事件(閘 `spec-gate`、kind `base-replay-skipped`、`nodes` 帶計劃)。這是 devops-cli「附理由的不適用」出口,寫在計劃裡、進版控、審查看得到。要能用 `lumos set` 寫,`base_replay_skip` 加進 `SCALAR_KEYS`、`_KNOWN_FRONTMATTER_KEYS`、`remove` 允許的鍵,`set` 的鍵說明一起補。
2. **分岔點與推送版**:
   - 推送版是推送範圍的終點那個提交(不是 HEAD、不是工作目錄)。
   - 分岔點是推送版跟主線的 merge-base,主線用推送範圍指令找主線的同一支(`_push_mainlines`);跟 test-guard 一樣不用「上次推到哪」,所以同一條分支第二次推送、壓過提交再推,分岔點都是實作開始前的版本。
   - 推標籤、找不到主線、merge-base 算不出、分岔點就是推送版:不重播,印一句原因、寫一筆 `base-replay-skipped`(原因欄寫是哪一種)。這跟推送前檢查「算不出範圍就放行」的既有約定一致(工具壞了不擋所有人);RETIRE-IF 的第三條會看到這類跳過太多。
3. **讀被推送的那一版**:計劃文字(條款、綁定、門重判、`base_replay_skip`、預期值表)一律從推送版讀(`git show <推送版>:<計劃路徑>`,同 `_pq_push_remind` 讀推送版的做法);工作目錄沒提交的改動不算。
4. **準備兩棵工作樹**:
   - 用 `_isolated_worktree` 各開一棵:分岔點、推送版(前綴 `lumos-replay-`,建樹前清同前綴的殘骸)。同一次推送有好幾份計劃要重播時,兩棵樹共用,不逐份重建。
   - 樹的準備抽成一支共用函式,修正關卡與基準重播都用它(現在是寫在 `cmd_fix_check` 裡的一段):主工作目錄的 `.lumos/config.json` 沒進版控就複製進樹;用 `_lint_link_deps` 把 `node_modules`、`.venv`、`venv` 連回主目錄;平台根在樹外、沒進版控、是子模組或符號連結的,標成釘不住版本。基準重播遇到釘不住版本的平台:不重播那個平台的測試,寫 `base-replay-skipped`(兩棵樹跑的其實是同一份程式,重播沒有意義)。
   - 覆蓋測試檔:推送範圍裡新增或改過、判成測試的檔,從推送版複製進分岔點那一棵;改名的(`-M` 給的舊路徑、新路徑)先刪掉分岔點那一棵的舊路徑再複製新的(不然同名測試變兩支,被判成「篩到好幾支」);刪掉的測試檔在分岔點那一棵也刪。複製只搬內容、不帶檔案模式,測試檔是符號連結就不複製、當跑不了(同修正關卡複製設定檔的做法)。
   - 重播跑測試時,子程序的暫存目錄(環境變數 `TMPDIR`)指到隔離工作樹自己的暫存資料夾底下,跟樹一起收掉(實驗量到測試跑紅會留下現場資料夾)。
5. **重播與判定**:
   - 平台的測試指令沒有 `{method}`(只能整套跑)時不重播那個平台(同 `_spec_gate_runnable` 的判法),寫 `base-replay-skipped`。
   - 重播前在推送版那份計劃上直接呼叫 `_spec_gate_twoway_static`(至少一條不標 keeps、keeps 的測試在計劃建立前就存在)與 `_clause_check_twoway`(綁的測試存在、不同條款不能綁同一支);擋下訊息開頭講「風險高計劃的推送前重播」,`_clause_check_twoway` 的「或把門升成單向」那句不印。新行為條款全是 `[manual:]` 時不重播、印一句、不擋。
   - 兩棵各用 `_platform_test_index` 建索引、用 `_spec_gate_judge_items` 跑,得到逐支的列。分岔點那一棵的列先換一次判定:列的第 6 欄(原始細節)以「超時」開頭的,紅改成弱證據——借 `_redbase_row_reason` 的同一條規則,抽成一支共用小函式兩邊用。然後照 `_spec_gate_run_clauses` 的規則把逐支列合成逐條判定,交給 `_spec_gate_twoway_run_verdict`:新行為條款要紅、keeps 要綠、弱證據不算。推送版那一棵:新行為條款的每一支都要綠(逾時不算綠)。
   - 不過時的訊息依原因分:新行為在分岔點綠(「這支測試在還沒改的程式上就過了,沒在驗這次的改動」)、keeps 在分岔點不綠(「既有行為的測試在舊程式上沒綠,重播環境不可信」)、分岔點弱證據、推送版不綠。每一種擋寫一筆治理帳事件(閘 `spec-gate`、kind `base-replay-failed`、`nodes` 帶計劃、原因分類)。不自動記逃逸。
   - 分岔點的紅是例外造成的(這個 repo 的測試程式輸出 `EXCEPTION:`、Kotlin 編譯失敗、jest 的 Test suite failed to run)還是斷言失敗,第一批不分;印一句「分岔點的紅沒分是例外還是斷言(第二批補)」。pytest 收集錯誤的輸出會被現有判法數成兩支而判弱證據,這時擋下訊息要講「可能是匯入錯誤:新測試匯入了舊版沒有的模組」。
   - 每支測試的逾時用 `LUMOS_REPLAY_TEST_TIMEOUT`(預設 900 秒;冷樹第一次編譯常超過現在的 180 秒);整個重播另有總預算 `LUMOS_REPLAY_BUDGET`(預設 1800 秒),超過就停、沒跑到的當弱證據並講是預算用完。
   - 中途按 Ctrl-C:跑測試的子程序照並行路徑的收法(`_BtProcs.reap`)收掉再收樹,不留在被刪掉的目錄裡跑。
6. **生效日與開關**:
   - 常數改名 `_HIGH_RISK_EVIDENCE_SINCE`(純日期,值事先訂好,不早於合併日)。計劃的生效日取「開頭欄位 `created`」與「計劃第一次進 git 歷史的日期(`_plan_first_commit`)」兩者較晚的那個;都讀不到才當成生效日之後。`created` 可以用 `lumos set` 改,只看它一個不可信(`_plan_first_commit` 的說明就這樣寫)。
   - `.lumos/config.json` 加 `high_risk_evidence: block|warn|off`(預設 block),同其他會擋的閘有專案層開關;warn 只印不擋、off 整道不跑,兩者都寫一筆事件。
7. **預期值表**(對第 1 點選出的計劃,不論有沒有寫 `base_replay_skip`;另外規格閘對門判風險高、生效日之後的計劃也做同一個檢查,不過就擋 rc1,插在 `_spec_gate_clause_part` 之後):
   - 找節:用 `_h2_section_lines` 找 `## 預期值表`(標題字要完全相同);替它加一個選填參數回報這個標題出現幾次(其他呼叫端不帶,行為不變),出現兩次以上算格式錯。節不存在、節裡沒有表、表寫在圍欄裡(它本來就跳過圍欄)都算「沒有表」。
   - 表的範圍:去掉行首 0 到 3 個空白後以 `|` 開頭的行是表格列(同 GFM;4 個以上空白是程式碼區塊);節裡第一個表格列是表頭,往下連續的表格列都是表,遇到第一個不是表格列的行(含空行)表就結束。表結束後同一節裡又出現去掉行首空白後以 `|` 開頭的行(不論縮排幾格),算格式錯(「表後面還有表格列」)。
   - 拆格:先逐字元掃過一行,`\\` 還原成 `\`、`\|` 還原成字面 `|`(不當分隔),其他反斜線照留;再用沒被跳脫的 `|` 切格;第一格與最後一格若是空的(行頭行尾的外側管線)丟掉,只丟這兩格。這支拆格寫成共用函式;專案裡另外兩處寬鬆的拆法(工具輸出的表、報告解析)用途不同、不改,寫回筆記時註明三者的關係。
   - 每一格去掉頭尾空白、做 NFC(既有 `nfc`,不做 NFKC)。表頭四格必須依序是「條款」「輸入」「預期」「來源」;第二列是分隔列,四格都要符合 `:?-{3,}:?`;資料列至少一列、每列剛好四格、四格都不能是空的。
   - 條款欄必須完全符合 `S` 加不以 0 開頭的數字(`S3`;`s3`、`S03`、全形 `Ｓ３` 都算格式錯),一列一條;不加方括號,免得被條款解析當成第二次定義 `[S3]`。寫不存在的條款、或寫標了 `[keeps]` 的條款,算格式錯。
   - 每條新行為條款(含只有 `[manual:]` 的)至少一列;來源欄用 `_real_chars` 數至少 4 個字。
   - 範例寫進 lumos-project-notes 的寫法說明:`| S2 | 單筆消費 1000 元 | 折扣 100 元 | 需求文件〈滿額折扣〉第 2 點:滿 1000 打九折 |`。
8. **表指紋與簽核**:
   - 表指紋:資料列依序、每列四格(拆格後的值)組成清單,`json.dumps(…, ensure_ascii=False)` 之後算 sha256;JSON 編碼讓格裡有什麼字都不會讓兩張不同的表撞成同一個指紋。
   - `lumos signoff <計劃> --expected --note "<一句>"`:計劃文字只讀一次(工作目錄那份,簽的人看的就是它),同一份文字做表格檢查、算指紋、印給人看。不是第 1 點那種計劃或表格檢查不過,rc2、不寫;同時帶 `--by` 或 `--ref` 是用法錯,rc2。
   - 誰簽的:用 `_waive_origin_tty`,把整張表(先過 `_out_clean`)與「確認這張預期值表對得上需求?」一起放進提示字串;`_waive_origin_tty` 加一個選填的「沒同意時印什麼」參數(預設照舊印「沒放行」,簽核傳「沒簽」)與選填逾時(簽核預設 300 秒,表要讀;其他呼叫端不傳、照舊)。答 y 記 human;答 n 或 Ctrl-C 印「沒簽」、rc1、不寫;沒有互動終端或逾時,記 ai、印一句「記成 AI 簽」。不設金鑰、不防代簽(d3)。
   - 寫一筆治理帳事件:閘用既有的 `signoff`,kind `expected-signed`,`nodes` 帶計劃,欄位 `plan`(圖譜相對路徑)、`table_sha`、`row_count`(列數;不用 `rows`,那個欄名在別的事件裡是清單)、`origin`(human 或 ai,同 lint-waive)、`who`(人簽照 `_e2e_who`;AI 簽寫 `ai`)、`token`(隨機)、`note`(截到 200 字,同端到端驗收放行);不擋(hard 為否)。`origin` 加進 `_GOV_FIELD_TYPES`。寫不進去(含沒有 `docs/` 目錄)rc2、印原因。
   - 帶 `--expected` 時不寫筆記開頭欄位的 `signed_off`、不寫 `.signoff-log.jsonl`。
   - 簽核事件寫在治理帳(帳本),跟功能一起提交;代碼審留痕之後才簽的,併進留痕後那個固定訊息的帳本提交(`chore(lumos): 記錄代碼審通過`),不另開提交。
   - 跟 lint-waive、端到端驗收放行的 `--ack` 不同是刻意的:AI 簽的不會在 doctor 與開場一直列到人看過(d3)。
9. **推送前查表與簽**(第 1 點選出的計劃,用推送版那份文字):
   - 重做第 7 點的表格檢查(整節刪掉、改成沒有來源、表後偷加列、縮排加列,推送前都會被擋)。
   - 用 `_gov_vc_gate_events` 讀治理帳 `signoff` 閘的 `expected-signed` 事件(另讀一趟,實測 21MB 約 0.2 秒);推送版的表指紋要等於某一筆 `plan` 相同(NFC 後比)的事件的 `table_sha`。只要內容跟某次簽過的一模一樣就算簽過——改了又改回去,簽的還是同一張表。
   - 沒有就擋,印簽核指令,寫一筆治理帳事件(閘 `spec-gate`、kind `expected-unsigned`、`nodes` 帶計劃)。
   - 放行時,對上的事件(同一張表簽過好幾次時取最晚一筆)`origin` 是 ai,印一行「預期值表由 AI 簽」不擋。
   - `lumos gov --stats`:`_gov_row` 對 `signoff` 閘的 `expected-signed` 帶出 `token` 與 `origin`(token 進去重鍵);統計輸出新增一行「預期值表簽核:人 N 次、AI M 次」。
10. **跟著改的說法**(同一個提交改掉;改掛鉤與注入範本照前例升小版號、寫 CHANGELOG,讓舊專案被提示 `lumos update`):
   - 程式與掛鉤:pre-push 掛鉤那兩行「風險低計劃的條款測試沒全綠」改成中性的「規格閘推送前檢查沒過(原因見上面)」;`_spec_gate_push_check` 的表頭與結尾改成照計劃風險講;`_auto_escape` 的推送閘描述;`HELP_WHEN["spec-gate"]`、spec-gate 與 signoff 的參數說明補新行為。

7. **紅要紅在斷言上(Kotlin/Java)**:第一批的基準重播會把分岔點上的編譯失敗當成紅;第二批讓重播與規格閘都分得出紅因。設計審 r1 已抓到的坑,第二批照這些設計(卷證在 `governance/review-reports/高風險測試證據加嚴/`):

   - 不能只借 `_secev_junit_facts`:它只回「狀態、是不是斷言」,分不出「有型別但不是斷言」與「沒有型別」,`junit()` 的失敗內文截在 4000 字,`Caused by:` 常在截掉的那段;`scripts/test_quality.py` 有部署指紋,只借不改。
   - 斷言型別的判法不用逐一列字表(Mockito 的 `WantedButNotInvoked`、JUnit5 的 `MultipleFailuresError`、AssertJ、Kotest 的多重失敗都不在現有白名單),照 [[Systems/test-guard]] 已有的做法「照型別名字的字尾認」,另外補 Mockito 的 verify 例外(`WantedButNotInvoked`、`ArgumentsAreDifferent` 這類字尾不是 Error 或 Failure,字尾規則認不出,要看套件名);例外鏈只看 `Caused by:` 行與 type 屬性,不看斷言訊息(訊息裡可能本來就有那幾個例外名)。
   - 報告裡那支是 passed 或 skipped 時不算紅;測試逾時、走目錄逾時都不算紅(同紅燈版「逾時的紅不算」與 guard-kill 的 `timed_out_weak`)。

   - 還有:單一報告檔要設大小上限(同安全證據閘的 `_SECEV_FILE_MAX`);找報告走目錄要排除 `node_modules`、`.git`、`Pods`;跑在手機上的測試報告沒有失敗型別,要另外判;「找不到報告判弱證據」與「走目錄逾時」的失效方向要一致(都不算紅)。
8. **建置檔與 CI 讓測試不跑**:不走「比對建置檔字串」當主力(變數、`gradle.properties`、`buildSrc`/`build-logic`、init script 都繞得過,test-guard 已否決「再補一輪字表」);改兩層:
   - 只在這次改到建置相關檔(`*.gradle*`、`gradle.properties`、`buildSrc/`、`build-logic/`、`junit-platform.properties`、`META-INF/services/`、`robolectric.properties`)時,工具帶一支 repo 外的 init script 讀每個 Test 任務實際生效的設定(`ignoreFailures`、`enabled`、`onlyIf`、篩選、`dryRun`、`failOnNoDiscoveredTests`、`unitTests.isReturnDefaultValues`、測試原始碼目錄),跟進版控的設定快照比,有變就列候選、要放行理由。
   - 有跑全套的地方(CI 或推送前)比 JUnit 報告的測試總數、跳過數與快照:總數下降或跳過數上升要理由(CI-Odor,Vassallo 等 ICSE 2019 的判法;受訪開發者 53.3% 贊成直接判失敗)。`isReturnDefaultValues` 這種測試照跑照綠的,只有第一層抓得到。
   - 已知不要做的:把 `failOnNoDiscoveredTests` 當安全網(有篩選、沒原始碼、dryRun 都不擋);看到 `continue-on-error` 就擋(CD-Linter 回報的這類 47% 被維護者拒絕,要限定在跑測試的那一步);把 `paths-ignore`、`junit.jupiter.conditions.deactivate`、`failFast` 當削弱。
9. **CI 對改到的行跑變異測試**(風險高計劃):
   - 照 Google 的三條:只變異改到而且有測試覆蓋的行、每行最多一個變異、跳過不值得測的地方(log、analytics、逾時常數)。Google 的數字:每個改動的變異數中位數全量 820、每行一個 77、再去掉不值得測的剩 7(Petrović 等,TSE 2021)。
   - 擋的是「每個活下來的變異都有處置(補測試殺掉,或附理由放行)」,不擋分數百分比(Google 不擋;flaky 讓分數平均飄 4 個百分點,Shi 等 ISSTA 2019;分數跟抓真 bug 的相關性控制測試數後是 weak,Papadakis 等 ICSE 2018)。
   - 放行紀錄綁檔案、行、變異寫法與程式指紋,程式改了就失效;「改到行卻 0 個變異」要報出來,不當通過。另放一個一定要被抓到的植入變異當自檢,防變異根本沒套上。
   - 只能跑本機單元測試(src/test);跑在手機上的測試沒有工具支援。工具選擇見待決問題。
   - 跟舊否決的關係:[[Projects/guard殺傷力驗證_計劃]] d1 決定合約的殺傷力驗證「不自動產生變異」,理由是等價變異不可判定、誤報 4–39%、零依賴;另外守衛閘門的世界解調研記了自動變異工具 2026-08-26 退場。這裡不一樣的地方:活下來的變異不直接判失敗,而是要處置(等價的附理由放行),誤報的代價從「擋下」變成「多寫一句理由」;引入外部變異工具跟零依賴家規衝突,第二批開計劃時要先過這一關(只在 CI 跑、不進 lumos 本體,或另找零依賴做法);第二批開計劃時要拿真實專案量「活下來但被判沒用」的比例(Google 早期 85%、調過不值得測的過濾後降到 11–20%),考場試跑超過一半就縮成只提醒。
   - 已知不要做的:追 100%、全量跑、擋百分比、把高分當預期值正確(Konstantinou、Zhao 等 ISSTA 2026)、讓 LLM 自己判等價就放行(Meta ACH 的 LLM 判等價 recall 0.47)、用開源 PIT 已移除的 `scmMutationCoverage`、沒人維護的 pitest-kotlin、原版 gradle-pitest-plugin(跟 Android 不相容)。
