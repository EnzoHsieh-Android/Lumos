# 高風險測試證據加嚴_計劃

> 白話:現在越危險的功能,工具對它的測試反而管得越鬆——風險低的計劃要求每條新行為的測試在實作前先紅,風險高的只印不擋,交給設計審與代碼審。但審查本身也是 AI 在判斷,拿它補最重要的那一塊說不通。這份計劃讓推送前對「這次真的在實作的風險高計劃」做一次基準重播:把它新行為條款綁的測試,放到分岔點那一版的舊程式上跑,必須紅;放到推送版上跑,必須綠——證明測試真的在驗這次的改動,跟測試先寫後寫無關。預期值寫成一張表、每列寫需求來源,推送前整張表要有人簽(預設人簽,AI 簽也放行但記下來)。「紅要紅在斷言上」、建置檔讓測試不跑、改到的行跑變異測試這三件要讀 Gradle 的輸出,排第二批。

## 名詞

- 風險高/風險低:規格閘的門判定(`_door_judge`)判的:任一硬訊號命中(連到標了金流、對外送出、不可逆、守衛面的節點等),或〈實務隱患〉缺任一類「已排除」行,就是風險高;作者只能往嚴調。那四行「已排除」是作者自填的。
- 新行為條款:驗收條款裡沒標 `[keeps]`、綁了 `[test:]` 的那幾條;標 `[keeps]` 的是「維持既有行為」,測試本來就該綠。
- 分岔點:推送範圍的起點那一版(三點範圍取 merge-base,同推送前檢查現有的 `_range_base`)。
- 推送版:推送範圍的終點那一版。
- 基準重播:開兩個隔離工作樹(`_isolated_worktree`,殺傷力驗證與修正關卡已在用),一個是分岔點、一個是推送版;把這次範圍裡新增或改過的測試檔(`_nodehome_is_test` 判的)從推送版複製進分岔點那一棵,正式程式碼留舊版;兩棵各跑一次計劃綁的測試(`_spec_gate_judge_items`,修正關卡已拿它在隔離工作樹裡跑)。新行為測試在舊版紅、推送版綠,叫「證實」。世界上同樣的做法叫 fail-to-pass(見調研)。
- 對照組:基準重播時,標 `[keeps]` 的條款測試在舊版也要綠;推送版那一棵的新行為測試要綠,也是對照——兩棵是同一種方式建的,環境壞了兩棵都會壞,不會只讓舊版紅。
- 弱證據:規格閘紅、綠之外的第三種判定,意思是「這次跑的結果證明不了什麼」——一支都沒跑到、篩選選中好幾支、被跳過(`_spec_gate_verdict`)。
- 生效日:程式常數 `_HIGH_RED_SINCE`,純日期,寫法同 `_NOTE_LINT_PLAN_SINCE`(拿計劃開頭欄位 `created` 比,讀不懂的日期當成生效日之後);值在實作提交裡事先訂好,不早於合併日。
- 預期值表:計劃裡一節 `## 預期值表`,底下一張表,逐列寫「哪條條款、輸入什麼、預期什麼、這個預期從哪條需求來」。
- 表指紋:整張預期值表的內容指紋,任一格改了任何一個字就變;換行符號、格子頭尾的空白不算。
- 簽核:有人看過預期值表、確認每列對得上需求,工具記下表指紋與簽的是人還是 AI。
- 治理帳與審查帳:治理帳是 `docs/.governance-log.jsonl`,各道閘的事件都寫這裡,進版控;審查帳是 `docs/.canary-log.jsonl`,消費專案預設被 git 忽略。本計劃新寫的事件與讀的簽核都只在治理帳。
- 考場:mOrangePos 的演練工作樹與只留本機的分支,拿來實機驗 lumos,不推、不併。
- 逃逸帳:審查放行之後,在實作、CI、正式環境才被發現的洞,用 `lumos loop escape` 記下來的帳。

## 問題與最小解

立案(2026-11-04,Enzo 原話):「風險高的靠review 補位？ 但是重點在於，風險高的測試，到底是不是實在的測試」「直接開新計劃，網路印證方向、做法，排除已有人實驗無效的坑」。設計審 r2 之後 Enzo 要求「搜世界解」,並裁「換成基準重播(推薦)」。

1. **風險高的計劃幾乎都沒有先紅的證據**:審查帳裡規格閘留痕 458 筆(2026-09-17 到 11-03)共 133 份計劃;每份取最新一筆看風險,風險高 102 份(77%);這 102 份裡,任何一筆留痕跑出過紅的只有 13 份(只看最新一筆是 7 份)。風險高的沒有紅燈版,推送前比對抓不到「預期值被改成實作的輸出」,只剩審查。
2. **預期值對不對需求,工具完全沒管**:先紅、紅燈版、防竄改比對都只證明「測試會抓錯」,證明不了預期值本身對;前面每一關都過、預期值寫成打八折而需求是打九折,照樣上線。現有 `lumos signoff` 記一筆「誰點了頭」(棄置合約時 `guard abandon` 會讀它帶的參照),不綁內容,也沒有推送前的閘讀它。
3. **「紅」不分原因**(第二批):Kotlin/Java 的測試輸出讀不出跑了幾支(`_RAN_EVIDENCE` 沒有這兩種),只能照退出碼判;編譯失敗、`--tests` 篩不到、被測程式還是 `TODO()`,全都判紅。

最小解:前兩輪設計審證明,要從帳上證明「實作前紅過」得接好幾個既有機制的接縫(r1 另寫一套翻帳、r2 沿用風險低的推送前檢查,兩輪各抓到大量誤擋與繞過)。改成推送當下直接從 git 算:分岔點的舊程式就是「還沒實作」的版本,在它上面跑新測試必須紅——不用帳、不用判設計審過了沒、不管先寫後寫,連「實作寫完再搬走造假紅」也不怕(重播用的是真的舊版)。預期值表與簽核另外新增。

PRIOR-ART:fail-to-pass 基準重播是世界上已有的做法:devops-cli 的 `ci fail-to-pass`(在暫存目錄建分岔點的樹、把推送版的測試覆蓋上去、只認呼叫階段失敗、收集錯誤不算數、要有附理由的不適用出口、另設自檢重播已知提交)、PRProof(分岔點 git 工作樹加複製改過的測試檔,舊版紅且推送版綠才判 PROVEN,跑不可靠回 ERROR);只要求「修前紅、修後綠」不夠的實證(UTBoost,ACL 2025:Verified 裡 26/500 題測試不足、345 個錯誤修補被判通過)與 PRProof 自承「錯的修補配錯的測試照樣 PROVEN」,所以預期值另外要人簽。簽核綁內容指紋、內容改了舊簽作廢,同 GitHub「推新提交作廢舊核可」與 Gerrit copyCondition;表格解析照 GFM 表格規則(格內 `\|` 是字面管線),欄數不符時不照 GFM 補或丟,一律擋。借用:`_isolated_worktree`、`_spec_gate_judge_items`、`_range_base`、`_nodehome_is_test`、`_spec_gate_twoway_static`、`_clause_check_twoway`、`_NOTE_LINT_PLAN_SINCE` 的生效寫法、`_h2_section_lines`、`_waive_origin_tty`、lint-waive 的 `origin` 欄與端到端驗收的簽核人取法、既有 `signoff` 閘名;自建:基準重播的串接、預期值表解析、表指紋與兩道推送前檢查。
RETIRE-IF:生效後連續 90 天,治理帳的 `base-replay-failed` 與 `expected-unsigned` 兩種擋下事件都是 0,而且同期逃逸帳裡沒有一筆描述是「測試預期值抄實作」或「測試沒在驗」——代表這兩道沒在擋任何東西,改回只印;或 `expected-signed` 事件裡 origin 是 ai 的連續 90 天佔 100% 且逃逸帳沒有預期值類的洞,簽核這道改成只記不擋;或基準重播被 `base_replay_skip` 跳過的計劃佔要重播的一半以上,代表重播在實務上跑不起來,回頭檢討做法。

## 調研結論(2026-11-04,四路網路調研)

- **只靠先紅不夠,要配紅燈版與變異測試**:UTBoost(上)與 PatchDiff(Wang、Pradel、Liu,ICSE 2026:通過測試的修補 29.6% 行為跟標準解不同)。先紅是入場券;「事後把實作搬走造假紅」查不到專門對策,對最終程式跑變異測試跟先寫後寫的順序無關,是第二批要補的那一塊。
- **Gradle 報告分不出紅的原因**:Gradle 的 JUnit XML(`JUnitXmlResultWriter`)把 `errors` 寫死成 0,所有例外都歸 `<failure>`;要看失敗的型別。Truth、AssertJ、kotlin.test、MockK 的 verify 都丟 `AssertionError` 子類;Kotlin `TODO()` 丟 `NotImplementedError`(繼承 `Error`,不是 `AssertionError`)。
- **證明「紅發生在實作之前」靠不住**:用提交順序認定 TDD 的研究(Borle 等,EMSE 2017)得放寬到晚一週提交也算才收得到樣本;Fucci 等(TSE 2017)發現順序本身沒有重要影響。不走這條。
- **AI 看得到實作,預期值就會照實作寫**:Konstantinou 等(2024/2026 v2)斷言「mainly capture the actual program behavior」;Charoosaei 等(2026)AI 測試 8–17% 把錯誤行為寫成預期值,其中 83–91% 之後一直通過。支持「預期值逐列寫需求來源」。
- **人工核可會鬆**:審查留言只有 14% 講缺陷(Bacchelli、Bird 2013);先看到 AI 的答案再問人對不對,人多半只看 AI 指的地方(Tufano 2024)。所以只對風險高的要簽,表要小,每列帶出處。
- 已被證明無效、這份計劃避開的:拿 XML 的 failure/error 分紅因;把 LLM 判官當唯一的閘(SWE 類任務上監看器只抓 42–50% 作弊,ImpossibleBench);只靠 TDD 提示詞(TDAD 預印本:回歸錯誤升到 9.94%);用提交順序證明先寫測試;簽核不綁內容(簽完再改預期值等於沒簽)。
- 設計審 r1(2026-11-04)後補查:GFM 表格規則裡格內 `\|` 是字面管線;欄數少於表頭補空格、多於表頭丟掉多的(本計劃不照這個寬鬆做法,見 PRIOR-ART)。
- 設計審 r2(2026-11-04)後 Enzo 要求搜世界解:fail-to-pass 基準重播。devops-cli 的 `ci fail-to-pass`(在暫存目錄建分岔點的樹、覆蓋推送版的測試、只認呼叫階段失敗、收集錯誤不算、附理由的不適用出口、自檢重播已知提交;它踩過重播環境把每支都弄紅、檢查形同虛設的坑,issue #3124);PRProof(分岔點 git 工作樹加複製改過的測試,舊版紅且推送版綠才 PROVEN,跑不可靠回 ERROR;自承「錯的修補配錯的測試照樣 PROVEN」)。另有 verify-fix 這類「沒修紅、修了綠」的指令。用提交順序或時間認定先寫測試,沒有找到可靠的工具。

## 做法

### 第一批(本次實作):推送前基準重播,加預期值表與簽核

1. **哪些計劃要重播**(`lumos spec-gate --push-check` 裡新增一道,pre-push 呼叫;CI 不跑這道,見〈不做〉):
   - 只看推送範圍改到的計劃檔(`_spec_gate_touched_plans` 給的那份);只因連到同一個系統節點被拉進來的計劃不重播、不查表、不查簽。
   - 現場重判門是風險高(`_door_judge`);開頭欄位 `created` 不早於 `_HIGH_RED_SINCE`(讀不懂的日期當成生效日之後);status 是 doing 或 done;這次範圍另外改到至少一支程式檔——不算圖譜目錄底下的檔、不算 `_BOOKKEEPING_FILES` 列的帳本、也不算 `_nodehome_is_test` 判成測試的檔。只改計劃與帳本(設計審期間的推送)不重播。
   - 計劃開頭欄位寫了 `base_replay_skip: "<理由>"`(理由去掉空白標點至少 10 個字,用 `lumos set` 寫)時不重播,印出理由、寫一筆治理帳事件(閘 `spec-gate`、kind `base-replay-skipped`)。理由不夠長當沒寫。這是世界解(devops-cli)「附理由的不適用」出口,給重播在環境上跑不起來的專案用;寫在計劃裡、進版控、設計審與代碼審看得到。
2. **重播前的靜態檢查**(照風險低既有兩支,直接呼叫,不經 `_clause_check` 的門分支):
   - `_spec_gate_twoway_static`:至少一條不標 keeps;標 keeps 的測試在計劃建立前就存在。
   - `_clause_check_twoway`:條款綁的測試要存在、不同條款不能綁同一支(擋「一支紅測試替十條作證」)。
   - 新行為條款一條 `[test:]` 都沒有(全靠 `[manual:]`)時:不重播,印一句「這份風險高計劃沒有可以重播的新行為測試,只靠人驗」,不擋——條款能不能靠人驗,是設計審的判斷。
   - 任一不過就擋,跟風險低擋下的字一樣,但開頭講是風險高計劃的推送前重播。
3. **怎麼重播**:
   - 起點取推送範圍的起點(`_range_base`,三點範圍取 merge-base);取不到起點(`_range_base` 回空,例如遠端還沒有這條分支時的首次推送)就判「重播跑不了」,見第 4 點。
   - 用 `_isolated_worktree` 各開一棵:分岔點、推送版(前綴 `lumos-replay-`,建樹前清同前綴的殘骸)。
   - 推送範圍裡新增或改過、`_nodehome_is_test` 判成測試的檔,從推送版複製進分岔點那一棵(刪掉的不動);分岔點那一棵其餘檔維持舊版,平台設定用它自己的。
   - 兩棵各用 `_platform_test_index` 建測試索引、用 `_spec_gate_judge_items` 跑:新行為條款綁的每一支測試(兩棵都跑)與標 keeps 的條款測試(只在分岔點跑,當對照組)。
4. **判定**(逐支;全部證實才放):
   - 證實:分岔點紅、推送版綠。分岔點的紅若是逾時(結果原因是逾時),不算紅,當弱證據(同紅燈版「逾時的紅不算」)。
   - 擋——在舊程式上就綠:「這支測試在還沒改的程式上就過了,沒在驗這次的改動」;印出是哪條條款、哪支測試。
   - 擋——推送版不綠:「推送版上這支測試沒綠」。
   - 擋——對照組在分岔點不綠:「既有行為的測試在舊程式上沒綠,重播環境不可信,這次證明不了」(devops-cli 踩過「重播把每支都弄紅、檢查形同虛設」)。
   - 擋——分岔點弱證據(沒跑到、篩到好幾支、逾時)、或重播跑不了(起點取不到、建樹失敗、平台設定讀不動):講原因;出口是修好環境,或寫 `base_replay_skip`。
   - 每一種擋都寫一筆治理帳事件(閘 `spec-gate`、kind `base-replay-failed`,帶計劃路徑與原因分類),RETIRE-IF 數這個。不自動記逃逸(風險高計劃有審查,推送前被擋不等於審查漏網)。
   - Kotlin/Java 新寫的類別在分岔點不存在,測試編譯失敗,現有判法照退出碼判成紅——會被當成證實。第一批照實印一句「分岔點的紅分不出是編譯失敗還是斷言失敗(第二批補)」,不擋;第二批第 7 點補紅因判讀。
5. **預期值表**(對第 1 點選出的計劃,不論有沒有寫 `base_replay_skip`;另外規格閘對門判風險高、`created` 不早於生效日的計劃也做同一個檢查,不過就擋 rc1,讓設計審看得到表):
   - 找節:用 `_h2_section_lines` 找 `## 預期值表`(標題字要完全相同);替它加一個選填參數回報這個標題出現幾次(其他呼叫端不帶,行為不變),出現兩次以上算格式錯。圍欄裡的行它本來就跳過,所以表寫在圍欄裡等於沒有表。
   - 表的範圍:節裡第一個以 `|` 開頭的行是表頭,往下連續以 `|` 開頭的行都是表;遇到第一個不以 `|` 開頭的行(含空行)表就結束。表結束後同一節裡又出現以 `|` 開頭的行,算格式錯(「表後面還有表格列」)。
   - 拆格:去掉行頭行尾空白後,外側的 `|` 各去掉一個(只去一個);格與格之間用沒被反斜線跳脫的 `|` 分開;`\|` 還原成 `|`、`\\` 還原成 `\`,其他反斜線照字面留著。每一格去掉頭尾空白、做 NFC(既有 `nfc`,不做 NFKC)。
   - 表頭四格必須依序是「條款」「輸入」「預期」「來源」;第二列是分隔列,四格都要符合 `:?-{3,}:?`;資料列每列都要剛好四格、四格都不能是空的。不符的逐項列出(第幾列、哪一格)。
   - 條款欄必須完全符合 `S` 加不以 0 開頭的數字(`S3`;`s3`、`S03`、全形 `Ｓ３` 都算格式錯),一列一條;不加方括號,免得被條款解析當成第二次定義 `[S3]`。寫不存在的條款、或寫標了 `[keeps]` 的條款,算格式錯。
   - 每條新行為條款(含只有 `[manual:]` 的新行為條款)至少一列;來源欄去掉空白與標點後至少 4 個字(中文字、英文字母、數字都算)。
   - 範例寫進 lumos-project-notes 的寫法說明:`| S2 | 單筆消費 1000 元 | 折扣 100 元 | 需求文件〈滿額折扣〉第 2 點:滿 1000 打九折 |`。
6. **表指紋與簽核**:
   - 表指紋:資料列依序、每列四格(拆格後的值)組成清單,`json.dumps(…, ensure_ascii=False)` 之後算 sha256。用 JSON 編碼而不是分隔字元接起來,格裡有什麼字都不會讓兩張不同的表撞成同一個指紋;換行符號與格子頭尾空白在拆格時已去掉,不影響指紋。
   - `lumos signoff <計劃> --expected --note "<一句>"`:計劃文字只讀一次,同一份文字做表格檢查、算指紋、印給人看。不是第 1 點那種計劃(門判風險低、`created` 早於生效日)或表格檢查不過,rc2、不寫。同時帶 `--by` 或 `--ref` 是用法錯,rc2。
   - 誰簽的:用 `_waive_origin_tty`,把整張表與「確認這張預期值表對得上需求?」一起放進提示字串(同既有呼叫端把資訊放進提示)。答 y 記 human;答 n 或 Ctrl-C 印「沒簽」、rc1、不寫(同 lint-waive 與端到端驗收放行答 n 的回傳碼);沒有互動終端或逾時,記 ai、印一句「記成 AI 簽」。逾時沿用 `LUMOS_TTY_TIMEOUT`;表大時人要先把環境變數調大,說明寫進擋下訊息與寫法說明。不設金鑰、不防代簽(Enzo 2026-11-04 裁,見 d3)。
   - 寫一筆治理帳事件:閘用既有的 `signoff`,kind `expected-signed`,欄位 `plan`(圖譜相對路徑)、`table_sha`、`rows`(列數)、`origin`(human 或 ai,同 lint-waive 的欄名)、`who`(人簽時照端到端驗收放行的 `_e2e_who`:先 git `user.name`、再系統使用者名;AI 簽寫 `ai`)、`token`(隨機)、`note`(截到 200 字,同端到端驗收放行)。不走 `_gate_event_fit`(欄位都是固定小欄位,note 已自己截)。寫不進去(含沒有 `docs/` 目錄)rc2、印原因。
   - 帶 `--expected` 時不寫筆記開頭欄位的 `signed_off`、不寫 `.signoff-log.jsonl`。
   - 跟 lint-waive、端到端驗收放行的 `--ack` 不同是刻意的:AI 簽的不會在 doctor 與開場一直列到人看過(d3)。
7. **推送前查表與簽**(第 1 點選出的計劃):
   - 重做第 5 點的表格檢查(整節刪掉、改成沒有來源、表後偷加列,推送前都會被擋)。
   - 用 `_gov_vc_gate_events` 讀治理帳 `signoff` 閘的 `expected-signed` 事件(跟留痕索引不同趟,多讀一次治理帳,實測 21MB 約 0.2 秒);現在的表指紋要等於某一筆 `plan` 相同(NFC 後比)的事件的 `table_sha`。只要內容跟某次簽過的一模一樣就算簽過——改了又改回去,簽的還是同一張表。
   - 沒有就擋,印簽核指令,寫一筆治理帳事件(閘 `spec-gate`、kind `expected-unsigned`)。
   - 放行時,對上的事件(同一張表簽過好幾次時取最晚一筆)`origin` 是 ai,印一行「預期值表由 AI 簽」不擋。
   - `lumos gov --stats`:`_gov_row` 對 `signoff` 閘的 `expected-signed` 帶出 `token` 與 `origin`(token 進去重鍵,同一個提交簽兩次不會被折成一筆);統計輸出新增一行「預期值表簽核:人 N 次、AI M 次」。
8. **跟著改的說法**(同一個提交改掉;改掛鉤與注入範本照 v1.3、v1.4 的前例升小版號、寫 CHANGELOG,讓舊專案被提示 `lumos update`):
   - 程式與掛鉤:pre-push 掛鉤那兩行「風險低計劃的條款測試沒全綠」改成中性的「規格閘推送前檢查沒過(原因見上面)」(掛鉤只拿得到回傳碼);`_spec_gate_push_check` 的表頭與結尾兩句改成照計劃風險講;`HELP_WHEN["spec-gate"]`、spec-gate 與 signoff 的參數說明補新行為。
   - 注入範本(`CLAUDE.md` 與 `AGENTS.md` 的來源)「風險高再進實作前的審查迴圈」後面補一句:風險高計劃要寫預期值表、推送前做基準重播與查簽核。
   - 手冊:lumos-design-loop 的 SKILL.md(description、步驟 10〈過了之後〉補「實作時測試先寫、推送前會重播;預期值表要簽」)與 reference.md 講「綁的測試真跑印紅綠不擋」那句;lumos-code-loop 的 SKILL.md 補一句簽核放在推送前、留痕之後也可以(治理帳是帳本);lumos-project-notes 的 `commands/INDEX.md`、`commands/05-設計審查迴圈.md`、`commands/03-寫回圖譜.md` 的 signoff 那列、它自己的 `reference.md` 的 signoff 段。
   - 使用者文件:`docs/指令參考.md` 與 `docs/command-reference.md` 講「風險高只印不擋」那句。
   - 圖譜:`Systems/規格閘`(風險高照半套那幾行補「推送前另有基準重播」)、`Systems/reversibility-governance-ledger`(新 kind 的 WHY 行,順手補負責範圍)、`Systems/bound-tests-gate`(pre-push 掛鉤那段的家)、`Projects/雙向門放行_計劃`(風險高照半套的單一來源)、`Projects/規格閘紅燈測試快照_計劃`〈四、不做〉、`Projects/業務簽核留痕_計劃`,各加一句指過來。
9. **會紅的既有測試**:pre-push 掛鉤訊息的字串測試、`signoff` 的參數測試照新說法改;規格閘本身對風險高的行為沒變(仍只印不擋),`t_spec_gate_oneway_keeps_halfset` 不受影響;推送前檢查的既有案例沒有改到風險高計劃檔加程式檔的,逐支看一遍。

### 第二批(另開計劃實作):Gradle 執行端

第二批要實際跑 Gradle,得先在 Android 考場試跑才定得了細節;本計劃只定方向與已知的坑,不寫驗收條款。

7. **紅要紅在斷言上(Kotlin/Java)**:第一批的基準重播會把分岔點上的編譯失敗當成紅;第二批讓重播與規格閘都分得出紅因。設計審 r1 已抓到的坑,第二批照這些設計(卷證在 `governance/review-reports/高風險測試證據加嚴/`):
   - 報告要在每支測試那一次執行結束當下讀(`_run_bound_tests` 現在整批跑完才回結果,同類別的 `TEST-<類別>.xml` 會被後一支覆蓋;平行跑時同一個 build 目錄互蓋)。
   - 不能只借 `_secev_junit_facts`:它只回「狀態、是不是斷言」,分不出「有型別但不是斷言」與「沒有型別」,`junit()` 的失敗內文截在 4000 字,`Caused by:` 常在截掉的那段;`scripts/test_quality.py` 有部署指紋,只借不改。
   - 斷言型別的判法不用逐一列字表(Mockito 的 `WantedButNotInvoked`、JUnit5 的 `MultipleFailuresError`、AssertJ、Kotest 的多重失敗都不在現有白名單),照 [[Systems/test-guard]] 已有的做法「照型別名字的字尾認」,另外補 Mockito 的 verify 例外(`WantedButNotInvoked`、`ArgumentsAreDifferent` 這類字尾不是 Error 或 Failure,字尾規則認不出,要看套件名);例外鏈只看 `Caused by:` 行與 type 屬性,不看斷言訊息(訊息裡可能本來就有那幾個例外名)。
   - 報告裡那支是 passed 或 skipped 時不算紅;測試逾時、走目錄逾時都不算紅(同紅燈版「逾時的紅不算」與 guard-kill 的 `timed_out_weak`)。
   - JUnit5 在報告裡的名字可能帶 `()` 或參數化的 `[n]`,比對規則要在考場實測後定;Maven 的報告在 `target/surefire-reports`。
   - 還有:單一報告檔要設大小上限(同安全證據閘的 `_SECEV_FILE_MAX`);找報告走目錄要排除 `node_modules`、`.git`、`Pods`;跑在手機上的測試報告沒有失敗型別,要另外判;「找不到報告判弱證據」與「走目錄逾時」的失效方向要一致(都不算紅)。
8. **建置檔與 CI 讓測試不跑**:不走「比對建置檔字串」當主力(變數、`gradle.properties`、`buildSrc`/`build-logic`、init script 都繞得過,test-guard 已否決「再補一輪字表」);改兩層:
   - 只在這次改到建置相關檔(`*.gradle*`、`gradle.properties`、`buildSrc/`、`build-logic/`、`junit-platform.properties`、`META-INF/services/`、`robolectric.properties`)時,工具帶一支 repo 外的 init script 讀每個 Test 任務實際生效的設定(`ignoreFailures`、`enabled`、`onlyIf`、篩選、`dryRun`、`failOnNoDiscoveredTests`、`unitTests.isReturnDefaultValues`、測試原始碼目錄),跟進版控的設定快照比,有變就列候選、要放行理由。
   - 有跑全套的地方(CI 或推送前)比 JUnit 報告的測試總數、跳過數與快照:總數下降或跳過數上升要理由(CI-Odor,Vassallo 等 ICSE 2019 的判法;受訪開發者 53.3% 贊成直接判失敗)。`isReturnDefaultValues` 這種測試照跑照綠的,只有第一層抓得到。
   - 已知不要做的:把 `failOnNoDiscoveredTests` 當安全網(有篩選、沒原始碼、dryRun 都不擋);看到 `continue-on-error` 就擋(CD-Linter 回報的這類 47% 被維護者拒絕,要限定在跑測試的那一步);把 `paths-ignore`、`junit.jupiter.conditions.deactivate`、`failFast` 當削弱。
9. **CI 對改到的行跑變異測試**(風險高計劃):
   - 照 Google 的三條:只變異改到而且有測試覆蓋的行、每行最多一個變異、跳過不值得測的地方(log、analytics、逾時常數)。Google 的數字:每個改動的變異數中位數全量 820、每行一個 77、再去掉不值得測的剩 7(Petrović 等,TSE 2021)。
   - 擋的是「每個活下來的變異都有處置(補測試殺掉,或附理由放行)」,不擋分數百分比(Google 不擋;flaky 讓分數平均飄 4 個百分點,Shi 等 ISSTA 2019;分數跟抓真 bug 的相關性控制測試數後是 weak,Papadakis 等 ICSE 2018)。
   - 放行紀錄綁檔案、行、變異寫法與程式指紋,程式改了就失效;「改到行卻 0 個變異」要報出來,不當通過。另放一個一定要被抓到的植入變異當自檢,防變異根本沒套上。
   - 只能跑本機單元測試(src/test);跑在手機上的測試沒有工具支援。工具選擇見待決問題。
   - 跟舊否決的關係:[[Systems/guard-kill]] 決定合約的殺傷力驗證「不自動產生變異」,理由是等價變異誤報 4–39%、會讓綁定測試被判失敗。這裡不一樣的地方是活下來的變異不直接判失敗,而是要處置(等價的附理由放行),誤報的代價從「擋下」變成「多寫一句理由」;第二批開計劃時要拿真實專案量「活下來但被判沒用」的比例(Google 早期 85%、調過不值得測的過濾後降到 11–20%),考場試跑超過一半就縮成只提醒。
   - 已知不要做的:追 100%、全量跑、擋百分比、把高分當預期值正確(Konstantinou、Zhao 等 ISSTA 2026)、讓 LLM 自己判等價就放行(Meta ACH 的 LLM 判等價 recall 0.47)、用開源 PIT 已移除的 `scmMutationCoverage`、沒人維護的 pitest-kotlin、原版 gradle-pitest-plugin(跟 Android 不相容)。
