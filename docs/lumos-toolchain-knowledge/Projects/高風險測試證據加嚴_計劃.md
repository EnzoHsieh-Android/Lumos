# 高風險測試證據加嚴_計劃

> 白話:現在越危險的功能,工具對它的測試反而管得越鬆——風險低的計劃要求每條新行為的測試在實作前先紅,風險高的只印不擋,交給設計審與代碼審。但審查本身也是 AI 在判斷,拿它補最重要的那一塊說不通。這份計劃讓風險高的計劃也要拿出機械證據:實作前先紅、而且紅在斷言上;預期值逐列寫需求來源、推送前要有人簽(預設人簽,AI 簽也放行但記下來)。建置檔讓測試不跑、改到的行跑變異測試這兩件要實際跑 Gradle,排第二批。

## 名詞

- 風險高/風險低:規格閘的門判定(`_door_judge`)判的:任一硬訊號命中(連到標了金流、對外送出、不可逆、守衛面的節點等),或〈實務隱患〉缺任一類「已排除」行,就是風險高;作者只能往嚴調。那四行「已排除」是作者自填的。
- 新行為條款:驗收條款裡沒標 `[keeps]`、綁了 `[test:]` 的那幾條;標 `[keeps]` 的是「維持既有行為」,測試本來就該綠。現在只有風險低的計劃會算 keeps(`_spec_gate_keeps_rows`),風險高的要另外叫它。
- 先紅:實作前跑一次條款綁的測試,它要失敗;證明測試真的在驗還沒做的新行為。
- 紅在斷言上:測試失敗是因為斷言不成立(預期值跟實際值不同),不是編譯錯、不是被測程式丟「還沒實作」或空指標這類例外。後兩種紅只證明「程式還不存在」,證明不了測試會比對結果。
- 紅因:規格閘判紅時記下的原因,三種值:斷言(報告證實是斷言失敗)、未判(這種測試讀不出失敗型別,例如 Python、跑在手機上的測試)、非斷言(讀得出型別、但不是斷言;這種不算紅)。
- 弱證據:規格閘的第三種判定(紅、綠之外),意思是「這次跑的結果證明不了什麼」——一支都沒跑到、篩選選中好幾支、被跳過;不算紅也不算綠(`_spec_gate_verdict`)。
- 紅燈版:規格閘判出紅的那一刻,把那支 Kotlin/Java 測試檔整份存下;推送前拿它當新測試的改動前版本比對,抓「預期值被改成實作的輸出」(Projects/規格閘紅燈測試快照_計劃)。
- 例外鏈:Java/Kotlin 的例外可以包另一個例外(cause),報告裡的失敗內文會一層層印出來;`assertThrows` 抓到非預期的例外時,會丟一個斷言失敗、把原本的例外包在裡面。
- 空殼:實作前先開好類別與方法,裡面回傳預設值(0、空字串、空清單),讓測試編譯得過、跑得到斷言、在斷言上紅。
- 預期值表:計劃裡一張表,逐列寫「哪條條款、輸入什麼、預期什麼、這個預期從哪條需求來」。
- 列指紋:預期值表一列的四格各自去掉頭尾空白、連續空白壓成一個、全形半形統一(NFKC)之後,用 Tab 接起來算 sha256。只改了空白或全半形,指紋不變、不用重簽;改了任何一個字,指紋就變。
- 簽核:有人看過預期值表、確認每列對得上需求,工具記下每列的列指紋與簽的是人還是 AI。
- 生效日:這份計劃合併上主線的那天,寫成程式常數。
- 首筆規格閘留痕:審查帳裡這份計劃的迴圈編號最早的一筆規格閘留痕(kind=spec-gate)。規格閘跑完才寫留痕,被擋下(rc1)的那次不寫;從沒有留痕的計劃一律當成生效日之後的新計劃(不然跳過規格閘就繞過這兩道檢查)。
- 治理帳與審查帳:治理帳是 `docs/.governance-log.jsonl`,各道閘的事件都寫這裡,設計上進版控;審查帳是 `docs/.canary-log.jsonl`,設計審、代碼審的記帳與規格閘留痕寫這裡。規格閘留痕兩本都寫一份。
- 考場:mOrangePos 的演練工作樹與只留本機的分支,拿來實機驗 lumos,不推、不併。
- 逃逸帳:審查放行之後,在實作、CI、正式環境才被發現的洞,用 `lumos loop escape` 記下來的帳。

## 問題與最小解

立案(2026-11-04,Enzo 原話):「風險高的靠review 補位？ 但是重點在於，風險高的測試，到底是不是實在的測試」「直接開新計劃，網路印證方向、做法，排除已有人實驗無效的坑」。

1. **風險高的計劃幾乎都沒有先紅的證據**:審查帳裡規格閘留痕 458 筆(2026-09-17 到 11-03)共 133 份計劃;每份取最新一筆看風險,風險高 102 份(77%);這 102 份裡,任何一筆留痕跑出過紅的只有 13 份(只看最新一筆是 7 份)。風險高的沒有紅燈版,推送前比對抓不到「預期值被改成實作的輸出」,只剩審查。
2. **「紅」不分原因**:Kotlin/Java 的測試輸出讀不出跑了幾支(`_RAN_EVIDENCE` 沒有這兩種),規格閘只能照退出碼判:編譯失敗、`--tests` 篩不到任何測試、被測程式還是 `TODO()` 丟 `NotImplementedError`,全都判紅。這些紅只證明程式不存在或測試沒跑到,測試裡就算一個斷言都沒有也會紅。風險低的擋下訊息有教人「讓測試在斷言上紅」,但放行只看退出碼。
3. **預期值對不對需求,工具完全沒管**:先紅、紅燈版、防竄改比對都只證明「測試會抓錯」,證明不了預期值本身對;前面每一關都過、預期值寫成打八折而需求是打九折,照樣上線。現有 `lumos signoff` 記一筆「誰點了頭」(棄置合約時 `guard abandon` 會讀它帶的參照),不綁內容,也沒有推送前的閘讀它。

最小解:沿用風險低已有的「新行為各自紅」規則,擴到生效日之後的風險高計劃,只是擋的時點從規格閘挪到推送前、而且只在這次推送真的在實作那份計劃時擋(風險高的計劃在規格閘時還在設計審,測試可能還沒寫);紅的原因借安全證據閘已在用的 JUnit 報告讀法;預期值表與簽核走治理帳既有的事件格式。

PRIOR-ART:「紅在斷言上」的判準與空殼回傳預設值,同 tdd-guard 的規則檔(nizos/tdd-guard `rules.ts`:「must fail for the RIGHT reason (not syntax/import errors)」、空殼「empty, constant return」),差別是它交給 LLM 判、這裡用失敗型別機械判;只要求「修前紅、修後綠」不夠,有 SWE-bench 的實證(UTBoost,ACL 2025:Verified 裡 26/500 題測試不足、345 個錯誤修補被判通過);簽核綁內容指紋、改哪列重簽哪列,同 GitHub「推新提交作廢舊核可」與 Gerrit copyCondition。借用:風險低的 keeps 規則(`_spec_gate_keeps_rows`)、安全證據閘讀 JUnit 報告的 `_secev_junit_facts`(底下是 `scripts/test_quality.py` 的 `junit()` 與斷言型別白名單;那支檔有部署指紋釘住,只借不改)、治理帳 `_gate_event`、端到端驗收放行「沒有互動終端記成 AI」的 `_waive_origin_tty`;自建:預期值表格式與它的推送前檢查。
RETIRE-IF:生效日後連續 90 天,風險高計劃在推送前因「沒有先紅」或「預期值沒簽」被擋的次數為 0,而且同期代碼審與正式環境逃逸帳裡沒有一筆是「測試預期值抄實作」或「測試沒在驗」——代表這兩道沒在擋任何東西,改回只印;或 AI 簽的列數連續 90 天佔 100% 且逃逸帳沒有預期值類的洞,簽核這道改成只記不擋。

## 調研結論(2026-11-04,四路網路調研)

- **只靠先紅不夠,要配紅燈版與變異測試**:UTBoost(上)與 PatchDiff(Wang、Pradel、Liu,ICSE 2026:通過測試的修補 29.6% 行為跟標準解不同)。先紅是入場券;「事後把實作搬走造假紅」查不到專門對策,對最終程式跑變異測試跟先寫後寫的順序無關,是第二批要補的那一塊。
- **Gradle 報告分不出紅的原因**:Gradle 的 JUnit XML(`JUnitXmlResultWriter`)把 `errors` 寫死成 0,所有例外都歸 `<failure>`;要看失敗的型別。Truth、AssertJ、kotlin.test、MockK 的 verify 都丟 `AssertionError` 子類;Kotlin `TODO()` 丟 `NotImplementedError`(繼承 `Error`,不是 `AssertionError`)。
- **證明「紅發生在實作之前」靠不住**:用提交順序認定 TDD 的研究(Borle 等,EMSE 2017)得放寬到晚一週提交也算才收得到樣本;Fucci 等(TSE 2017)發現順序本身沒有重要影響。不走這條。
- **AI 看得到實作,預期值就會照實作寫**:Konstantinou 等(2024/2026 v2)斷言「mainly capture the actual program behavior」;Charoosaei 等(2026)AI 測試 8–17% 把錯誤行為寫成預期值,其中 83–91% 之後一直通過。支持「預期值逐列寫需求來源」。
- **人工核可會鬆**:審查留言只有 14% 講缺陷(Bacchelli、Bird 2013);先看到 AI 的答案再問人對不對,人多半只看 AI 指的地方(Tufano 2024)。所以只對風險高的要簽,表要小,每列帶出處。
- 已被證明無效、這份計劃避開的:拿 XML 的 failure/error 分紅因;把 LLM 判官當唯一的閘(SWE 類任務上監看器只抓 42–50% 作弊,ImpossibleBench);只靠 TDD 提示詞(TDAD 預印本:回歸錯誤升到 9.94%);用提交順序證明先寫測試;簽核不綁內容(簽完再改預期值等於沒簽)。

## 做法

### 第一批(本次實作):規格閘這一端

1. **紅的原因(Kotlin/Java)**,只對首筆規格閘留痕晚於生效日的計劃(風險高低都算;在途的計劃照舊用退出碼,不追溯):
   - 規格閘跑完一支 Kotlin/Java 測試、退出碼判紅時,在 repo 裡名叫 `build` 的目錄底下找這次跑出來的報告:本機單元測試在 `build/test-results/`,跑在手機上的在 `build/outputs/androidTest-results/`;只讀修改時間晚於這次開跑、檔名是 XML 的檔,用 `_secev_junit_facts` 讀成 `{身份: (狀態, 是否斷言失敗)}`,找名字對得上這支測試的那一筆(身份是「類別::方法」,比方法那一段)。
   - 判法(依序):
     a. 找得到、有失敗型別而且是斷言類:再讀那一筆 testcase 的失敗內文,例外鏈出現 `NotImplementedError` 或 `UnsupportedOperationException` 就判非斷言;沒有就判紅,紅因記「斷言」。
     b. 找得到、有失敗型別但不是斷言類(例如 `kotlin.NotImplementedError`、`NullPointerException`):判弱證據,紅因記「非斷言」,印補法:空殼改回傳預設值,不要用 `TODO()` 或丟例外。
     c. 找得到、但報告沒有失敗型別(跑在手機上的測試報告就是這樣):照退出碼判紅,紅因記「未判」。
     d. 哪裡都找不到這支測試的報告(通常是編譯失敗、或 `--tests` 篩不到,Gradle 一支都沒跑):判弱證據,印「這次沒跑到這支測試,先確認編譯得過、測試名對得上」。報告整檔被讀法拒收(`_secev_junit_facts` 回原因代碼)也算這種,原因代碼一起印。
   - 其他棧(Python、Swift、JS 等)照舊用退出碼判,紅因記「未判」。
   - 只有判紅的(紅因是斷言或未判)才存紅燈版,跟現在「判紅才存」一致;非斷言紅變弱證據之後不存。
2. **規格閘留痕逐條記判定**:留痕(spec-gate 那筆,審查帳與治理帳各一份)多一欄 `clause_verdicts`,每條條款記 `{判定, 紅因, 測試名}`;風險高也照記。舊留痕沒有這欄,讀側當「沒記」。
3. **風險高推送前要有先紅的證據**:
   - 哪些計劃要查:`lumos spec-gate --push-check`(pre-push 呼叫;CI 不跑這道)現有的候選計劃裡,風險高、首筆規格閘留痕晚於生效日(或沒有任何留痕),而且符合下面任一條的:這次推送範圍改到那份計劃檔、同時也改到程式檔;或那份計劃的 status 已經是 done。只是連到同一個系統節點、計劃檔沒動也還沒做完的,不查——那份計劃可能還在設計審,不能擋別人的推送。
   - 查什麼:計劃現在每條新行為條款(風險高也叫 `_spec_gate_keeps_rows` 算 keeps),在審查帳這份計劃的所有規格閘留痕裡,找「同一個條款編號、同一個測試名、判定是紅」的紀錄(紅因是斷言或未判)。任一條找不到就擋,印出是哪幾條,與風險低那套補紅燈的做法(先提交、把實作換回空殼、跑規格閘、換回來)。沒有任何留痕的,擋下並請它先跑規格閘。
   - 規格閘本身對風險高的紅綠仍只印不擋(計劃在設計審時,測試可能還沒寫);句式、綁定、回退節、相依回歸這些照舊會擋。印紅綠那行改講「推送前會要每條新行為都紅過一次」。
   - 推送前擋下訊息現在寫死「風險低」(pre-push 掛鉤與 `_spec_gate_push_check` 各一處),改成照計劃風險講。
4. **預期值表**:
   - 格式:計劃裡一節 `## 預期值表`,底下一張表,表頭固定四欄「條款 | 輸入 | 預期 | 來源」;條款欄寫條款編號(例 `[S3]`),一條可有多列。
   - 規格閘(風險高、首筆留痕晚於生效日或沒有留痕):每條新行為條款至少一列,來源欄至少 4 個實字(不算空白標點);缺就擋(rc1),列出缺哪幾條。插在條款句式與綁定檢查(`_spec_gate_clause_part`)之後、跑測試之前;句式那段提早結束(條款解析不出、零條款)時,這道也不跑——那些情況本來就會擋或沒有新行為條款。
   - 範例(寫進 lumos-project-notes 的寫法說明):`| [S2] | 單筆消費 1000 元 | 折扣 100 元 | 需求文件〈滿額折扣〉第 2 點:滿 1000 打九折 |`。
5. **簽核**:
   - `lumos signoff <計劃> --expected --note "<一句>"`(`--note` 照現有參數必填):算預期值表每一列的列指紋,寫一筆治理帳事件:閘名 `expected-signoff`(加進 `_KNOWN_GATES`)、kind `expected-sign`,帶計劃、每列指紋、簽核人類別(human 或 ai)、備註。比照規格閘留痕,不走 `_gate_event_fit` 裁長度(裁掉指紋清單就等於少簽幾列)。
   - 帶 `--expected` 時不寫筆記開頭欄位的 `signed_off`、不寫 `.signoff-log.jsonl`(那兩樣記的是整篇點頭,不綁內容;這裡要的是逐列綁內容,而且要進版控)。
   - 誰簽的:用 `_waive_origin_tty` 那套判法:有互動終端時印出整張表、問一句,答 y 記成人簽,答 n 或 Ctrl-C 不寫;沒有互動終端或 30 秒沒回,記成 AI 簽並印一句「記成 AI 簽」。不設金鑰、不防代簽(Enzo 2026-11-04 裁,見 d3)。
   - 推送前檢查(同第 3 點的範圍與條件):預期值表每一列的列指紋都要出現在這份計劃的某筆 `expected-sign` 事件裡;沒有的列(新增或改過的)列出來並給簽核指令,擋下。只改其他列時,已簽的列不必重簽。
   - 放行時表裡有 AI 簽的列,印一行「預期值表 N 列由 AI 簽」不擋;`lumos gov --stats` 分開算人簽與 AI 簽的列數(`_gov_row` 只取白名單欄位,要把這兩個數加進去),讓「人抽離了多少」看得見。

### 第二批(另開計劃實作):Gradle 執行端

第二批要實際跑 Gradle,得先在 Android 考場試跑才定得了細節;本計劃只定方向與已知的坑,不寫驗收條款。

6. **建置檔與 CI 讓測試不跑**:不走「比對建置檔字串」當主力(變數、`gradle.properties`、`buildSrc`/`build-logic`、init script 都繞得過,test-guard 已否決「再補一輪字表」);改兩層:
   - 只在這次改到建置相關檔(`*.gradle*`、`gradle.properties`、`buildSrc/`、`build-logic/`、`junit-platform.properties`、`META-INF/services/`、`robolectric.properties`)時,工具帶一支 repo 外的 init script 讀每個 Test 任務實際生效的設定(`ignoreFailures`、`enabled`、`onlyIf`、篩選、`dryRun`、`failOnNoDiscoveredTests`、`unitTests.isReturnDefaultValues`、測試原始碼目錄),跟進版控的設定快照比,有變就列候選、要放行理由。
   - 有跑全套的地方(CI 或推送前)比 JUnit 報告的測試總數、跳過數與快照:總數下降或跳過數上升要理由(CI-Odor,Vassallo 等 ICSE 2019 的判法;受訪開發者 53.3% 贊成直接判失敗)。`isReturnDefaultValues` 這種測試照跑照綠的,只有第一層抓得到。
   - 已知不要做的:把 `failOnNoDiscoveredTests` 當安全網(有篩選、沒原始碼、dryRun 都不擋);看到 `continue-on-error` 就擋(CD-Linter 回報的這類 47% 被維護者拒絕,要限定在跑測試的那一步);把 `paths-ignore`、`junit.jupiter.conditions.deactivate`、`failFast` 當削弱。
7. **CI 對改到的行跑變異測試**(風險高計劃):
   - 照 Google 的三條:只變異改到而且有測試覆蓋的行、每行最多一個變異、跳過不值得測的地方(log、analytics、逾時常數)。Google 的數字:每個改動的變異數中位數全量 820、每行一個 77、再去掉不值得測的剩 7(Petrović 等,TSE 2021)。
   - 擋的是「每個活下來的變異都有處置(補測試殺掉,或附理由放行)」,不擋分數百分比(Google 不擋;flaky 讓分數平均飄 4 個百分點,Shi 等 ISSTA 2019;分數跟抓真 bug 的相關性控制測試數後是 weak,Papadakis 等 ICSE 2018)。
   - 放行紀錄綁檔案、行、變異寫法與程式指紋,程式改了就失效;「改到行卻 0 個變異」要報出來,不當通過。另放一個一定要被抓到的植入變異當自檢,防變異根本沒套上。
   - 只能跑本機單元測試(src/test);跑在手機上的測試沒有工具支援。工具選擇見待決問題。
   - 跟舊否決的關係:[[Systems/guard-kill]] 決定合約的殺傷力驗證「不自動產生變異」,理由是等價變異誤報 4–39%、會讓綁定測試被判失敗。這裡不一樣的地方是活下來的變異不直接判失敗,而是要處置(等價的附理由放行),誤報的代價從「擋下」變成「多寫一句理由」;第二批開計劃時要拿真實專案量「活下來但被判沒用」的比例(Google 早期 85%、調過不值得測的過濾後降到 11–20%),考場試跑超過一半就縮成只提醒。
   - 已知不要做的:追 100%、全量跑、擋百分比、把高分當預期值正確(Konstantinou、Zhao 等 ISSTA 2026)、讓 LLM 自己判等價就放行(Meta ACH 的 LLM 判等價 recall 0.47)、用開源 PIT 已移除的 `scmMutationCoverage`、沒人維護的 pitest-kotlin、原版 gradle-pitest-plugin(跟 Android 不相容)。

## 實務隱患
- 已排除:金流:只改規格閘、推送前檢查與簽核指令,不碰收費或扣款流程
- 已排除:對外送出:不寄信不推播,只讀本機測試報告、寫本機治理帳
- 已排除:不可逆:治理帳是追加的、新欄位舊讀側當沒記;生效日常數讓既有計劃不受影響,改壞了回退就回來

- 天花板四:推送範圍只碰到計劃檔、沒碰程式檔(先推計劃再推實作),或實作分成好幾次推、中間那幾次沒改計劃檔,那幾次不查;最後把 status 改成 done 的那次推送會查
