# 高風險測試證據加嚴_計劃

> 白話:越危險的功能,工具對它的測試反而管得越鬆——風險低的計劃要求每條新行為的測試在實作前先紅,風險高的只印不擋,交給設計審與代碼審;但審查本身也是 AI 在判斷。測試會不會抓錯有紅燈版、防竄改比對、基準重播在管,可是「預期值本身對不對需求」沒有任何一關在管:前面每一關都過、預期值寫成打八折而需求是打九折,照樣上線。這份計劃要求風險高的計劃把預期值寫成一張表、每列寫需求來源,規格閘查表的格式,推送前查這張表有沒有人簽(預設人簽,AI 簽也放行但記下來)。「測試在舊程式上要紅」的基準重播搬到另一份計劃([[Projects/PR基準重播_計劃]]);「紅要紅在斷言上」、建置檔讓測試不跑、改到的行跑變異測試這三件要讀 Gradle 的輸出,排第二批。

## 名詞

- 風險高/風險低:規格閘的門判定(`_door_judge`)判的:任一硬訊號命中(連到標了金流、對外送出、不可逆、守衛面的節點等),或〈實務隱患〉缺任一類「已排除」行,就是風險高;作者只能往嚴調。那四行「已排除」是作者自填的。
- 新行為條款:驗收條款裡沒標 `[keeps]` 的那幾條(綁 `[test:]` 或 `[manual:]` 都算);標 `[keeps]` 的是「維持既有行為」。
- 要簽的計劃:門判風險高、生效日之後(第 2 點)、至少一條新行為條款的計劃。
- 生效日:程式常數 `_HIGH_RISK_EVIDENCE_SINCE`,純日期,寫法同 `_NOTE_LINT_PLAN_SINCE`,值取實作合併日的隔天。
- 預期值表:計劃裡一節 `## 預期值表`,底下一張表,逐列寫「哪條條款、輸入什麼、預期什麼、這個預期從哪條需求來」。
- 表指紋:整張預期值表的內容指紋,任一格改了任何一個字就變;換行符號、格子頭尾的空白不算。
- 簽核:有人看過預期值表、確認每列對得上需求,工具記下表指紋與簽的是人還是 AI。
- 推送前規格閘:`lumos spec-gate --push-check <範圍>`,推送前掛鉤已經在呼叫;它挑「這次推送碰到的計劃檔,加上連到被碰到的 Systems 節點或被改程式檔的家的 doing 計劃」,讀工作目錄的計劃與版控治理帳。
- 治理帳與審查帳:治理帳是 `docs/.governance-log.jsonl`,各道閘的事件都寫這裡,進版控;審查帳是 `docs/.canary-log.jsonl`,消費專案預設被 git 忽略。本計劃新寫的事件與讀的簽核都只在治理帳。
- 考場:mOrangePos 的演練工作樹與只留本機的分支,拿來實機驗 lumos,不推、不併。
- 逃逸帳:審查放行之後,在實作、CI、正式環境才被發現的洞,用 `lumos loop escape` 記下來的帳。

## 問題與最小解

立案(2026-11-04,Enzo 原話):「風險高的靠review 補位？ 但是重點在於，風險高的測試，到底是不是實在的測試」「直接開新計劃，網路印證方向、做法，排除已有人實驗無效的坑」。設計審 r5 後 Enzo 裁「拆開：這份只做表與簽(推薦)」(d8)。

1. **預期值對不對需求,工具完全沒管**:先紅、紅燈版、防竄改比對、基準重播都只證明「測試會抓錯」,證明不了預期值本身對。現有 `lumos signoff` 記一筆「誰點了頭」(棄置合約時 `guard abandon` 會讀它帶的參照),不綁內容,也沒有推送前的閘讀它。
2. **風險高的計劃幾乎都沒有先紅的證據**(搬到 [[Projects/PR基準重播_計劃]]):審查帳裡規格閘留痕 458 筆(2026-09-17 到 11-03)共 133 份計劃;每份取最新一筆看風險,風險高 102 份(77%);這 102 份裡,任何一筆留痕跑出過紅的只有 13 份。
3. **「紅」不分原因**(第二批):Kotlin/Java 的測試輸出讀不出跑了幾支(`_RAN_EVIDENCE` 沒有這兩種),只能照退出碼判;編譯失敗、`--tests` 篩不到、被測程式還是 `TODO()`,全都判紅。

最小解:預期值寫成表、每列帶需求來源,讓簽的人(或 AI)對著需求一列一列看;簽核綁整張表的指紋,改了一格就要重簽。表的格式在規格閘查(設計審就看得到表),有沒有簽在推送前規格閘查——它已經會挑這次碰到的計劃、讀工作目錄的計劃與版控治理帳,不用另開指令、不用開工作樹、不跑測試(d9)。

PRIOR-ART:簽核綁內容指紋、內容改了舊簽作廢,同 GitHub「推新提交作廢舊核可」與 Gerrit copyCondition;表格解析照 GFM 表格規則(格內 `\|` 是字面管線),欄數不符時不照 GFM 補或丟,一律擋;只要求「修前紅、修後綠」不夠、預期值要另外有人看的實證見〈調研結論〉(UTBoost、PRProof 自承、Konstantinou、Charoosaei)。借用:`_h2_section_lines`、`_real_chars`、`_waive_origin_tty` 與 `_confirm_tty`、lint-waive 的 `origin` 欄與端到端驗收的簽核人取法(`_e2e_who`)、既有 `signoff` 閘名與指令、`_door_judge`、`_NOTE_LINT_PLAN_SINCE` 的生效寫法、推送前規格閘的挑計劃(`_spec_gate_push_candidates`)與逐份查(`_spec_gate_push_scan`)、版控治理帳讀法 `_gov_vc_gate_events`;自建:預期值表解析、表指紋。
RETIRE-IF:生效後連續 90 天,治理帳的 `expected-unsigned` 擋下事件是 0,而且同期逃逸帳裡沒有一筆描述是「測試預期值抄實作」或「預期值不符需求」——代表這道沒在擋任何東西,改回只印;或 `expected-signed` 事件裡 origin 是 ai 的連續 90 天佔 100% 且逃逸帳沒有預期值類的洞,簽核這道改成只記不擋。

## 調研結論(2026-11-04,四路網路調研)

- **只靠先紅不夠**:UTBoost(ACL 2025:Verified 裡 26/500 題測試不足、345 個錯誤修補被判通過)與 PatchDiff(Wang、Pradel、Liu,ICSE 2026:通過測試的修補 29.6% 行為跟標準解不同);PRProof 自承「錯的修補配錯的測試照樣 PROVEN」。所以預期值另外要人看。
- **AI 看得到實作,預期值就會照實作寫**:Konstantinou 等(2024/2026 v2)斷言「mainly capture the actual program behavior」;Charoosaei 等(2026)AI 測試 8–17% 把錯誤行為寫成預期值,其中 83–91% 之後一直通過。支持「預期值逐列寫需求來源」。
- **人工核可會鬆**:審查留言只有 14% 講缺陷(Bacchelli、Bird 2013);先看到 AI 的答案再問人對不對,人多半只看 AI 指的地方(Tufano 2024)。所以只對風險高的要簽,表要小,每列帶出處。
- **Gradle 報告分不出紅的原因**(第二批):Gradle 的 JUnit XML(`JUnitXmlResultWriter`)把 `errors` 寫死成 0,所有例外都歸 `<failure>`;要看失敗的型別。Truth、AssertJ、kotlin.test、MockK 的 verify 都丟 `AssertionError` 子類;Kotlin `TODO()` 丟 `NotImplementedError`(繼承 `Error`,不是 `AssertionError`)。
- **證明「紅發生在實作之前」靠不住**:用提交順序認定 TDD 的研究(Borle 等,EMSE 2017)得放寬到晚一週提交也算才收得到樣本;Fucci 等(TSE 2017)發現順序本身沒有重要影響。不走這條。
- 已被證明無效、這份計劃避開的:簽核不綁內容(簽完再改預期值等於沒簽);把 LLM 判官當唯一的閘(SWE 類任務上監看器只抓 42–50% 作弊,ImpossibleBench);只靠 TDD 提示詞(TDAD 預印本:回歸錯誤升到 9.94%)。
- 設計審 r1 後補查:GFM 表格規則裡格內 `\|` 是字面管線;欄數少於表頭補空格、多於表頭丟掉多的(本計劃不照這個寬鬆做法,見 PRIOR-ART)。
- 基準重播(fail-to-pass)的調研與 r5 後的選測試粒度查證,搬到 [[Projects/PR基準重播_計劃]]。

## 做法

### 第一批(本次實作):預期值表與簽核

0. **拆分**(d8):設計審 r1 到 r5 的基準重播設計(推送前、PR 檢查兩種位置,以測試檔為單位選測試)整段拿掉,搬到 [[Projects/PR基準重播_計劃]] 照世界做法從頭寫、從第一輪審;卷證留在 `governance/review-reports/高風險測試證據加嚴/`。
1. **要簽的計劃**:門判風險高(`_door_judge`)、生效日之後(第 2 點)、至少一條新行為條款。全部條款都標 `[keeps]` 的、風險低的、生效日之前的,不要求表與簽。
2. **生效日**:常數 `_HIGH_RISK_EVIDENCE_SINCE`(純日期,值取實作合併日的隔天,同專案「設隔日不設當日」的慣例)。計劃的日期取開頭欄位 `created` 與計劃第一次進 git 歷史的日期兩者較晚的;後者只追改名(d12):找這條路徑第一次新增的提交(同 `_plan_first_commit` 的 `--diff-filter=A`,它沒帶 `--follow`,改名後會回改名那次提交,設計審 r5 邊界席實測),再用 `git diff-tree -M`(只開改名偵測)看那個提交是不是把別的檔改名過來,是就換成舊路徑再找;不用 `git log --follow`——它連複製一起追,拿舊計劃複製一份寫新計劃時會被追到舊計劃的日期而漏查(實作時實測)。每次 git 逾時 20 秒,逾時當讀不到。淺複製(`git rev-parse --is-shallow-repository` 是 true)時只看 `created`;兩個都讀不到才當成生效日之後。比較用「不早於」(等於當天算生效)。生效常數可用環境變數 `LUMOS_HIGH_RISK_EVIDENCE_SINCE` 覆寫(同 `LUMOS_PANEL_RETIRE_CUTOFF`;不是 YYYY-MM-DD 就用常數),測試總開關預設成 9999,新測試自己改。
3. **預期值表**(只對要簽的計劃):
   - 找節:`_h2_section_lines` 找 `## 預期值表`(它本來就回 `(行號, 原始行)`),替它加一個選填參數回報標題出現幾次,兩次以上算格式錯。節不存在、節裡沒有表、表寫在圍欄裡都算「沒有表」。表格列連續看的是行號相連,中間隔了小標題或圍欄的兩段不併成一張表。
   - 表的範圍:去掉行首 0 到 3 個空白後以 `|` 開頭的行是表格列;第一個表格列是表頭,往下行號連續的表格列都是表;之後同一節裡又出現去掉行首空白後以 `|` 開頭的行(不論縮排),算格式錯「表後面還有表格列」。
   - 拆格:一次逐字元掃過,`\\` 是字面 `\`、`\|` 是字面 `|`(不當分隔),其他反斜線照留,遇到沒被跳脫的 `|` 就切;切完後第一格與最後一格去掉空白後是空的(外側管線、含行尾空白)就丟掉,只丟這兩格。這支拆格寫成共用函式;專案裡另外兩處寬鬆的拆法用途不同、不改,寫回筆記時註明三者的關係。
   - 每一格去掉頭尾空白、做 NFC。表頭四格依序是「條款」「輸入」「預期」「來源」;第二列是分隔列,四格都要符合 `:?-{3,}:?`;資料列(不含表頭與分隔列)至少一列、最多 500 列,每列剛好四格;每格 NFC 之後最多 2000 個字元;「輸入」「預期」兩格用 `_real_chars` 數至少 1 個字(只有標點或零寬字元的格算空),來源欄至少 4 個字。
   - 條款欄完全符合 `S` 加不以 0 開頭的數字(`s3`、`S03`、全形都算格式錯),一列一條,不加方括號;寫不存在的條款、或寫標了 `[keeps]` 的條款,算格式錯。每條新行為條款(含只有 `[manual:]` 的)至少一列。
   - 規格閘對要簽的計劃做這個檢查(插在 `_spec_gate_clause_part` 之後),不過就擋 rc1、逐項列出,讓設計審看得到表。
   - 範例寫進 lumos-project-notes 的寫法說明:`| S2 | 單筆消費 1000 元 | 折扣 100 元 | 需求文件〈滿額折扣〉第 2 點:滿 1000 打九折 |`。
4. **表指紋與簽核**:
   - 表指紋:資料列依序、每列四格組成清單,`json.dumps(…, ensure_ascii=False)` 之後算 sha256(JSON 編碼不會撞)。
   - `lumos signoff <計劃> --expected --note "<一句>"`:計劃文字只讀一次(工作目錄那份,推送前規格閘讀的也是工作目錄),同一份文字做表格檢查、算指紋、印給人看。資格:要簽的計劃(跟 status 無關,實作完、status 改成 done 之後也能簽);不合資格或表格檢查不過 rc2、不寫;同時帶 `--by` 或 `--ref` 是用法錯,rc2。
   - 誰簽的:整張表先用一般輸出印出來(一列一行、每格各自過 `_out_clean`),再用 `_waive_origin_tty` 問「確認上面這張預期值表(N 列,指紋前 12 碼)對得上需求?」——提示本身只有這一句,不把整張表塞進終端寫入。`_waive_origin_tty` 與 `_confirm_tty` 各加選填的「沒同意時印什麼」(預設照舊印「沒放行」,這裡傳「沒簽」)與選填逾時(這裡傳 300 秒;有設環境變數 `LUMOS_TTY_TIMEOUT` 時以環境變數為準,測試靠它縮短)。答 y 記 human;答 n 或 Ctrl-C 印「沒簽」、rc1、不寫;沒有互動終端或逾時,記 ai、印一句「記成 AI 簽」。不設金鑰、不防代簽(d10)。
   - 治理帳事件:閘 `signoff`(已登記在 `_KNOWN_GATES`)、kind `expected-signed`、`nodes` 帶計劃,欄位 `plan`(圖譜相對路徑,跟 `cmd_signoff` 記的 `rel`、推送前規格閘的計劃鍵同一種寫法)、`table_sha`、`row_count`、`origin`(human 或 ai)、`who`(人簽照 `_e2e_who`,AI 簽寫 `ai`)、`token`、`note`(截到 200 字);hard 為否;`plan`、`table_sha`、`origin` 以字串、`row_count` 以整數加進 `_GOV_FIELD_TYPES`。不走 `_gate_event_fit`;寫不進去 rc2。帶 `--expected` 時不寫 `signed_off` 與 `.signoff-log.jsonl`。
   - 簽核事件寫在治理帳(帳本白名單裡),跟功能一起提交;代碼審留痕之後才簽的,用留痕後那個固定訊息的帳本提交帶上(`chore(lumos): 記錄代碼審通過`)。
   - 跟 lint-waive、端到端驗收放行的 `--ack` 不同是刻意的:AI 簽的不會在 doctor 與開場一直列到人看過(d10)。
5. **推送前查表與簽**(推送前規格閘,`_spec_gate_push_scan` 逐份查的迴圈裡另走一支):
   - 對象:推送前規格閘本來就挑出來的計劃裡,狀態是 doing、或這次推送改到計劃檔本身的 done(同既有 `_live` 的判法),而且是要簽的計劃(用工作目錄的計劃文字重判門與生效日)。實作提交只改程式檔、不碰計劃檔時,靠既有「被改程式檔的家」那條連結挑到。
   - 重做第 3 點的表格檢查(整節刪掉、改成沒有來源、表後加列,都會被擋)。
   - 用 `_gov_vc_gate_events(<repo>, "signoff")` 讀版控治理帳,只留物件、`kind` 是 `expected-signed`、`plan` 與 `table_sha` 都是字串的事件(其他行跳過、不丟例外);表指紋要等於某一筆 `plan` 跟這份計劃相同(NFC 後比)的事件的 `table_sha`。帳讀不到時擋下並講原因(同這支函式對審查帳、治理帳讀不到的既有做法)。
   - 沒有對上的就擋(rc1),印簽核指令,寫一筆 `expected-unsigned` 事件(閘 `spec-gate`,hard)。
   - 放行時,對上的事件(同一張表簽過好幾次取檔內最後一筆)`origin` 是 ai,印一行「預期值表由 AI 簽」不擋。
   - `lumos gov --stats`:`_gov_row` 對 `signoff` 閘的 `expected-signed` 帶出 `token` 與 `origin`(token 進去重鍵);統計輸出新增一行「預期值表簽核:人 N 次、AI M 次」。
6. **跟著改的說法**(同一個提交改掉;注入範本有改就照前例升小版號、寫 CHANGELOG,發版照 `RELEASING.md` 由人裁):
   - 程式:`HELP_WHEN["spec-gate"]` 與 spec-gate、signoff 的參數說明補新行為;沒有新的頂層命令。
   - 注入範本(`scripts/templates/graph-discipline.md`)「風險高再進實作前的審查迴圈」後面補一句:風險高計劃要寫預期值表並簽核,推送前會查;本 repo 的 `CLAUDE.md` 與 `AGENTS.md` 重新注入。
   - 手冊:lumos-design-loop 的 SKILL.md(description、步驟 10〈過了之後〉補「預期值表要簽」)、reference.md、templates.md 講規格閘判風險高之後的那幾句(風險低的推送前輕量審那幾句不動);lumos-code-loop 的 SKILL.md 補簽核放的位置;lumos-project-notes 的 SKILL.md 與 reference.md 講 signoff 的地方補 `--expected` 跟「業務確認」的差別、`commands/INDEX.md`、`commands/05-設計審查迴圈.md`、`commands/03-寫回圖譜.md`、`commands/06-代碼審與推送.md` 的推送閘清單。
   - 使用者文件:`docs/指令參考.md` 與 `docs/command-reference.md`、`ARCHITECTURE.md` 的規格閘流程、`docs/心智模型.md` 與 `docs/mental-model.md`、`docs/methodology/圖譜即合約.md`;`assets/spec-gate-zh.svg` 與 `assets/spec-gate-en.svg` 的圖說補一格。
   - 圖譜:`Systems/規格閘`(負責範圍補預期值表檢查與推送前查簽)、`Systems/reversibility-governance-ledger`(新 kind 的 WHY、補負責範圍)、`Projects/雙向門放行_計劃`、`Projects/業務簽核留痕_計劃`。
7. **會紅的既有測試**:
   - 規格閘的預期值表檢查只對要簽的計劃;測試的計劃產生器(`_sg_plan`、`_sg_plan2`、`_sg_plan_linked`、`_qo_plan` 與直接寫 `type: project` 的那批)不帶 `created`,提交日又是跑測試那天——會被當成生效日之後。不逐支補 `created`:測試總開關把生效日預設成 9999,讀不到日期的計劃仍當生效日之後,要逐支看哪幾支因此要求表與簽、補 `created`。
   - `t_spec_gate_help_says_low_risk_blocks`、`t_spec_gate_oneway_keeps_halfset` 照新說法看;`signoff` 參數的字串測試照新說法改;`t_gov_stats_gate_drift` 與 `HELP_WHEN` 的漂移守衛照跑綠。
   - `scripts/test_lumos.py` 在 `governance/anchor-baseline.json` 的錨點裡,改測試檔前先 `lumos anchor approve`。

### 第二批(另開計劃實作):Gradle 執行端

第二批要實際跑 Gradle,得先在 Android 考場試跑才定得了細節;本計劃只定方向與已知的坑,不寫驗收條款。

1. **紅要紅在斷言上(Kotlin/Java)**:基準重播([[Projects/PR基準重播_計劃]])與規格閘都把編譯失敗當成紅;第二批讓兩者分得出紅因。設計審 r1 已抓到的坑,第二批照這些設計(卷證在 `governance/review-reports/高風險測試證據加嚴/`):
   - 報告要在每支測試那一次執行結束當下讀(`_run_bound_tests` 現在整批跑完才回結果,同類別的 `TEST-<類別>.xml` 會被後一支覆蓋;平行跑時同一個 build 目錄互蓋)。
   - 不能只借 `_secev_junit_facts`:它只回「狀態、是不是斷言」,分不出「有型別但不是斷言」與「沒有型別」,`junit()` 的失敗內文截在 4000 字,`Caused by:` 常在截掉的那段;`scripts/test_quality.py` 有部署指紋,只借不改。
   - 斷言型別的判法不用逐一列字表(Mockito 的 `WantedButNotInvoked`、JUnit5 的 `MultipleFailuresError`、AssertJ、Kotest 的多重失敗都不在現有白名單),照 [[Systems/test-guard]] 已有的做法「照型別名字的字尾認」,另外補 Mockito 的 verify 例外(`WantedButNotInvoked`、`ArgumentsAreDifferent` 這類字尾不是 Error 或 Failure,字尾規則認不出,要看套件名);例外鏈只看 `Caused by:` 行與 type 屬性,不看斷言訊息(訊息裡可能本來就有那幾個例外名)。
   - 報告裡那支是 passed 或 skipped 時不算紅;測試逾時、走目錄逾時都不算紅(同紅燈版「逾時的紅不算」與 guard-kill 的 `timed_out_weak`)。
   - JUnit5 在報告裡的名字可能帶 `()` 或參數化的 `[n]`,比對規則要在考場實測後定;Maven 的報告在 `target/surefire-reports`。
   - 還有:單一報告檔要設大小上限(同安全證據閘的 `_SECEV_FILE_MAX`);找報告走目錄要排除 `node_modules`、`.git`、`Pods`;跑在手機上的測試報告沒有失敗型別,要另外判;「找不到報告判弱證據」與「走目錄逾時」的失效方向要一致(都不算紅)。
2. **建置檔與 CI 讓測試不跑**:不走「比對建置檔字串」當主力(變數、`gradle.properties`、`buildSrc`/`build-logic`、init script 都繞得過,test-guard 已否決「再補一輪字表」);改兩層:
   - 只在這次改到建置相關檔(`*.gradle*`、`gradle.properties`、`buildSrc/`、`build-logic/`、`junit-platform.properties`、`META-INF/services/`、`robolectric.properties`)時,工具帶一支 repo 外的 init script 讀每個 Test 任務實際生效的設定(`ignoreFailures`、`enabled`、`onlyIf`、篩選、`dryRun`、`failOnNoDiscoveredTests`、`unitTests.isReturnDefaultValues`、測試原始碼目錄),跟進版控的設定快照比,有變就列候選、要放行理由。
