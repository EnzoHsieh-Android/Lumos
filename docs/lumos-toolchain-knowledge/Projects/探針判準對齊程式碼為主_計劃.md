# 探針判準對齊程式碼為主_計劃

> 白話:情境探針是一套考題,每週抽 8 題開一個新的 Claude 會談去做,看它有沒有照規矩查圖譜。這次改兩件事:①AI 做到一半被步數上限砍掉的場次,不再算它不及格,改成「這場不算分」另外記;②考題的評分標準還停在舊規矩(必須第一步就查圖譜),改成新規矩(先讀程式碼可以,但該查圖譜的最後要查到;沒查就動手改仍然不行)。

PRIOR-ART: 官方 claude-api skill 的 eval-audit 健檢清單(截斷不能算錯、要單獨計數、排除在平均外)與 hillclimb 指南的失敗分類表(撞上限歸「儀器問題,先從分母拿掉」);本 repo 內部先例=Codex 執行器早就把逾時標成「儀器例外、不算分」,用量上限也已排除。借用,不自建新機制:截斷沿用既有的「儀器例外」前綴,對照實驗的有效場次判定因此自動跟上。
RETIRE-IF: 截斷的處理——claude -p 不再有回合上限或探針改成不設上限時撤;讀碼禁令的拿掉——紀律改回「第一個工具呼叫是 lumos」時要翻回來(那時 [S5] 的測試應改成反向斷言)。

## 範圍

- 情境探針的 claude 執行器、總結與歷史紀錄;Codex 執行器只補一個欄位。
- 題庫四份裡含讀碼禁令的 30 題(答案題 5、指令題 16、口語題 9);紀律題與缺席題不含讀碼禁令,不動。
- 自主迴圈每週抽查那一段不改(它屬守衛面);靠總結行本身的數字觸發它既有的通知條件,見做法 2。
- 不做:反向題(該直接讀碼的情境)、題目鑑別力篩選、雜訊門檻——這三件是調研條款 3–7,另開。

## 做法

1. **截斷不算分。** claude 執行器從結果事件讀到 subtype 是 error_max_turns,或子程序逾時,就把這場標成截斷:不算通過,理由以「儀器例外」開頭(沿用既有前綴,對照實驗的有效場次判定因此自動排除它),另帶一個截斷欄位。用量上限的判定照舊優先。Codex 執行器逾時本來就是儀器例外,只補同一個截斷欄位,讓兩個執行器的紀錄形狀一致。
   - 半途已經敲對指令、後來才被砍的場次也不算分,跟 Codex 執行器既有理由一致:截斷的紀錄不完整,判過或判不過都是在猜。
2. **總結只算有效場次。** 分母扣掉截斷、用量上限與其他儀器例外;總結行保持「p/n 個情境 Claude 自己敲對了」開頭(自主迴圈靠這個格式判要不要發通知),後面列出各類排除幾場。
   - 同一題重跑多次、截斷過半時點名這題:代表題目或步數上限有問題,不是 AI 的問題。
   - 有效場次不到整批一半時,分母退回整批(被排除的場次當成沒過),總結行加一句「有效場次不到一半,這批不能下結論」,回傳碼非 0。自主迴圈只在「p 不等於 n」時發通知;不退回的話,整批被截斷會變成 0/0 安靜地顯示全過。寧可多發一次通知,不要安靜。
3. **歷史紀錄。** 歷史列的沒過清單只放有效場次裡沒過的題;另記被排除的題與判準版本字串,讓人分得出新舊判準的紀錄。
4. **讀碼禁令整批拿掉。** 30 題的「禁止先做」清單拿掉讀碼類(Grep、Glob、Read、grep、rg、cat、ls、find、git log/status/diff);寫入類與替代類保留(Edit、Write、sed、mv、gh run、git push)。期望的 lumos 指令不變,只是不必排第一。
5. **唯一的純程式碼題改判準。** 「_BOOKKEEPING_FILES 是幹嘛的、哪些地方靠它」兩個子問都是程式碼答得了的,改成期望「有讀程式碼」(Grep/Read 或在 shell 裡 grep、sed 程式檔,不含圖譜資料夾),lumos 可敲可不敲;另加答案內容要提到「帳」相關字樣。其餘 29 題問的是為什麼、規則、事故、決策,或對應紀律表裡的指定指令,仍要求最後有敲到。
6. **圖譜收尾。** 對照實驗那篇驗證紀錄的前提(判準=lumos 在 Grep/Read 之前)已不成立,標明失效原因與日期;[[Projects/Prompt稽核_計劃]] 10-25 那個回頭點補一句「用新判準跑」。

## 條款

- [S1] 當 claude 執行器的一場以回合上限或逾時結束,探針應把它標成截斷、不算通過,理由以「儀器例外」開頭並帶截斷欄位;同一場若是用量上限,應照舊標用量上限;Codex 執行器逾時也應帶截斷欄位 [test:t_probe_truncated_run_not_scored]
- [S2] 當一批跑完印總結與寫歷史,通過率的分母應只算有效場次,總結行應仍以「p/n 個情境 Claude 自己敲對了」開頭並列出各類排除數,歷史列的沒過清單應只含有效場次裡沒過的題並另記被排除的題與判準版本 [test:t_probe_summary_excludes_instrument_runs]
- [S3] 當同一題重跑多次而截斷過半,總結應點名這題;當有效場次不到整批一半,分母應退回整批、總結行應加「這批不能下結論」且回傳碼非 0(自主迴圈既有的「p 不等於 n 就通知」因此會觸發) [test:t_probe_flags_truncation_heavy_batches]
- [S4] 當題庫裡的題目不是純程式碼題,它的禁止先做清單不應含讀碼類動作,寫入與替代類禁令應保留,期望的 lumos 指令應不變 [test:t_probe_scenarios_allow_code_first]
- [S5] 當 2026-09-28 週抽那場「先 grep、讀程式碼、答對、沒敲 lumos」的紀錄套新判準,應判過;只 grep 圖譜資料夾、沒讀程式碼的紀錄應判不過 [test:t_probe_code_question_regrade]

## 回退

- **全部回退**:還原本計劃的提交即可。程式與題庫都在同一個 repo、沒有消費專案副本(探針與題庫不隨 lumos update 發佈),沒有外部狀態要收。還原後週抽歷史裡會留著帶判準版本欄位的幾列,舊程式不讀這個欄位,不影響。
- **只回退判準(第 4、5 點)**:只還原三份題庫檔與 v04 那一行;截斷處理可以留著,兩件互不依賴。
- 回退本身是一次提交,照紀律跟圖譜的對應改動放同一個提交。

## 實務隱患

- 已排除:金流:探針只跑本機 claude -p 與讀寫 repo 裡的紀錄檔,不碰任何付款或計費設定
- 已排除:對外送出:不改通知腳本;通知是否發出沿用自主迴圈既有條件,本計劃只改總結行的數字
- 已排除:不可逆:改的是程式與題庫文字,還原提交即復原;週抽歷史只追加欄位、不改舊列
- 已排除:守衛面:不動自主迴圈腳本、hook、pre-commit/pre-push 或任何閘;探針是量測工具,結果不擋提交或推送

## 誠實界線

- 沒有真的開新會談重跑任何一題,新判準對通過率的影響要等下次每週抽查才看得到;[S5] 只用一場歷史紀錄驗。
- 拿掉讀碼禁令之後,探針量的是「最後有沒有查到」,不再量「是不是先查」——9/2 對照實驗量到的 35.7 個百分點差距主要就在順序上,新判準下那條規矩的效果會看起來小很多,這是判準換了,不是規矩變弱。
- 29 題「仍要查圖譜」的判斷是我逐題讀題目做的,沒有第二個人看過;歸錯的題會把「該直接讀碼」的行為判成不及格。
