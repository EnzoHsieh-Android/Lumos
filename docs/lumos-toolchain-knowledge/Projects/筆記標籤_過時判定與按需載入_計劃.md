# 筆記標籤_過時判定與按需載入_計劃

> 白話:兩個宗旨——程式碼推得出來的事實,筆記不寫;其他脈絡(為什麼、規則、踩過的坑、程式答不了的現況)照前綴分類寫。分類要有規律,AI 改程式時才知道要回頭檢查哪幾類、每類查什麼。這份計劃做四件事:①寫的時候怎麼分(定義留在紀律範本,判斷例子交給判定者)②誰來檢查分得對不對(沿用既有的「筆記內容審」AI 判定者,讓它多判一層前綴)③改程式時怎麼逐類回頭查(先看合約與事故,再把那支檔的家筆記摘要行完整拉出來,照每類一行的清單查)④機械只做準、又不打架的提醒。依賴欄位那種「數字變了就擋」的機械判定,拆到另一份計劃。

依據:
- 使用者需求(2026-10-01,經 lumos-toolchain-ff 會談轉達):①制定筆記寫法規則,搭配特定標籤 ②制定檢查:判定某句或某個標籤已經過時 ③同一套也能拿來篩、只載入需要的片段 ④不溯及既往 ⑤網搜前例、規劃推薦做法。之後 Enzo 在本對話陸續裁定與補充,見上方摘要的 WHY 行。

## 現況(盤點與實驗結論)

- **舊的 KEY 行像雜物抽屜**:工具鏈抽 50 條,47% 一行混兩到三類,12% 是程式推得出的事實;會員系統專案抽 250 句,程式推得出 19%、「某天做了什麼」的過程紀錄 16%、混合 19%。工具鏈管主程式的 40 篇家筆記,摘要行 KEY 535、WHY 80、PITFALL 70、RULE 10、FACT 2——多數脈絡還在 KEY 裡。
- **關鍵字規則分不準**:先歸納再凍結、去猜沒看過的句子,工具鏈加 rtb 54%(扣掉合約行 47%)、會員系統 36%。準的只有結構性線索:合約記號、審查記號、一行很長又同時有兩類線索(12/15、3/5)、DEP 只放連結(19/19,但那是既有規範教的正規寫法,見〈不做〉)。

- **前綴缺一類**:過程紀錄(施工步驟、審查處置、版本沿革)兩個專案各佔約 14% 到 16%,沒有前綴可放;作者自創的前綴都對得回標準前綴,沒有新類別要開。

- **單一來源**:前綴定義的唯一來源是紀律範本,skill 兩處都寫「唯一來源是紀律範本」,`t_note_convention_single_source` 釘著不准有第二份定義表。

- **回頭重讀已經在做「改程式後回頭查」的一半**:推送時把這次 diff 加上一起改過的家筆記全文交給判定者,問哪幾行不成立了。

## 設計原則

0. **兩個宗旨**:程式碼推得出來的事實,筆記不寫;其他脈絡照前綴分類寫。
1. **分類交給 AI 判定者,機械只做準又不打架的提醒**。
2. **一行一類**:混合句拆開寫;判定者回報「這行該拆成哪幾類」。
3. **過程紀錄不進筆記**:屬於 git 歷史、驗證紀錄與審查卷證;判定者會指出,不另做機械提醒。
4. **合約行一律豁免**:`KEY:★INVARIANT★` / `★DEBT★` 等合約行有自己的格式與測試綁定,不判前綴、不提醒拆。
5. **不另起爐灶、不放寬政策**:定義單一來源不動;判定者沿用筆記內容審;提醒走否定現況句那種「不進違規清單」的路;RULE 效力規則不動;時間到期只提醒。
6. **只看新寫的行**:提醒與前綴判定都只看上線點之後新增的行;舊筆記不回頭補。不分新舊專案。

## 分類規格(寫的時候)

- **定義**:維持紀律範本〈寫筆記時〉那張前綴表為唯一來源,不搬到 skill;第 0 步只修它自己兩處 RULE 效力說法的不一致,並補一行「一行一類、過程紀錄不寫進筆記」。KEY 那列寫明「新寫只用於合約行」。
- **判斷例子**:每類的常見線索與易混淆形狀(下表)寫進判定者派工詞,給判定者用;skill 只放「判斷例子」的散文段並指回範本,不放前綴定義表列(單源測試照舊要綠)。

| 前綴 | 常見線索(只是提示) | 易混淆 |
|---|---|---|
| WHY | 否決、裁定、避免、所以選、刻意、取代;寫得出「考慮過什麼、選了哪個、為什麼、代價」最好(MADR) | 審查沿革與處置紀錄(「r2 折入」「某席指出」)是過程紀錄;「修法是…」是 PITFALL 的一部分或程式推得出 |
| RULE | 必須同版、要人裁、不可、人工控管、法規、合約 | 規格條款(「X 時應 Y」)與合約行是程式行為;業務數字在程式或設定檔裡就是程式推得出 |
| PITFALL | 根因、靜默、誤擋、死結、事故、教訓 | 只描述程式現在怎麼做(沒有「踩到」)是程式推得出 |
| FACT/FLOW/DEP | 生產實測、資料庫的值、外部廠商行為 | 在 repo 裡 grep 得到的(含 CI 設定、appsettings)是程式推得出;只放連結的 FLOW/DEP 是既有規範的「指路行」,照舊合法 |

其他前綴(PRIOR-ART、DECISION、TEST、VERIFY、AUTH、FLAG、CORE、REVISIT、RETIRE-IF、KEY 合約行)判定者不判前綴對錯,只判既有的三類。

## 分類檢查(AI 判定者)

沿用筆記內容審的判定者流程,不另開:
- **多判一欄**:對新寫的行,判定者在既有四欄(編號、類別、證據、理由)之後多附第五欄「前綴建議」:寫這行應該屬於的前綴,一行該拆就用 `+` 連(例 `WHY+PITFALL`),是過程紀錄寫 `過程紀錄`,程式推得出寫 `-`;合約行與上面列的其他前綴寫 `略`。放在最後一欄,舊報告與舊解析照讀(位置取欄不受影響)。
- **只判新寫的行**:筆記內容審在計劃收尾時會整篇重審(既有行為),那時舊行只判既有三類、不填前綴建議。
- **折疊**:同一編號多席或申訴時,前綴建議跟著既有規則選中的那一列走(取最重類別那一列),不另訂折法。
- **出口只提醒**:`note-audit record` 多印一段「前綴建議」:列出前綴與建議不同、該拆、是過程紀錄的行;不擋,也不進「還沒被涵蓋」的判定。
- **照筆記內容審的紀律升版**:派工詞改字就升 `_NOTE_AUDIT_PROMPT_VERSION`;原本的 68 句只重跑既有三類(它沒有前綴答案),前綴判對率改用 `bank/` 150 句量,判定者用正式模型;第一次量的結果就是本案的基準,記進本計劃;總判對率低於 70% 不接。版本號退回時,用新版準備的清單要重新 prepare(既有的來源比對會丟掉輕的判定),寫進回退。
- **前置條件**:筆記內容審接進推送前掛鉤之前,這一步只在人手動跑 prepare/record 時生效;接線本身屬於 [[Projects/筆記內容審_計劃]]。

## 改程式時的分類檢查清單

改某支檔之前:
1. `lumos impact --file <檔>`:先看合約(★INVARIANT★)、事故、決策——這些有挑戰程式碼的效力,清單不重複它們。
2. `lumos search --about <檔>`:把那支檔的家筆記摘要行完整拉出來(包含舊的 KEY 行;不給 `--prefix` 就是全部前綴),逐類對照:

| 前綴 | 改到它相關的程式時查什麼 |
|---|---|
| WHY | 這次改動有沒有推翻它的理由或前提;推翻了就改寫並記新決定,舊的標 `[status:superseded]` 加連結 |
| RULE | 這次改動有沒有違反它;撤除條件成立了沒;`[confirmed:]` 是不是超過半年(要挑戰程式碼就得重新確認) |
| PITFALL | 防回歸的測試還在不在、這次改動有沒有讓它重新可能發生 |
| FACT/FLOW/DEP | 程式驗不了;改動若影響部署、資料或外部行為,回頭確認 |
| KEY(舊寫法) | 讀內容判它屬於哪一類,照那一類查 |

3. 推送時,既有的回頭重讀會再對「這次一起改過的家筆記」問一次哪幾行不成立了——清單管改之前、回頭重讀管推之前,兩道互補。

## 搜尋行模式

擴 `lumos search`,不開新指令:
- `--prefix`:只要這幾種摘要行前綴(help 寫明跟限資料夾的 `--path` 不同)。
- `--about <檔>`:那支檔的家筆記的摘要行;家用既有「每支檔有家」的對照表(about_code 列了它的 Systems 筆記,不讀 git),路徑接受 repo 相對、`./` 開頭與 repo 內的絕對路徑。
- 給了 `--prefix` 或 `--about` 而沒給 `term`,進入「行模式」(位置參數改成可省略);給了 `term` 就照既有搜尋,再用這兩個旗標篩命中行。行模式不套每篇 8 行截斷、不套每行 90 字截斷:每行輸出 `篇名:行號: 整行`;`--top` 預設照舊是 0(全給),給了才限總行數;排序是 RULE、PITFALL、WHY、FACT/FLOW/DEP、其他,同類內照篇名。
- **大檔**:家的篇數達到既有的大檔門檻(`LUMOS_IMPACT_ABOUT_MAX`,預設 8)時,不倒全文:stdout 只印每篇家筆記的篇名與各前綴行數,stderr 說「這支檔有 N 個家,請加 `term` 或 `--prefix` 縮小」。
- **空結果講清楚**:stderr 分三種說明——檔案不在 repo 裡、這支檔沒有家、有家但沒有符合的行。
- 行模式預設隱藏「已作廢的行」(判法照 `parse_rule_fields` 的欄位解析,先去掉行內程式碼,文字裡只是提到這個標記的不算),`--include-retired` 才給;隱藏行數印在 stderr,`--json` 另帶 `hidden_lines`。既有的 `--include-superseded`(節點層)意思不變。只看靜態標記,不求值任何條件。

## 結構性提醒(只看提交前新增的行,所有專案,只提醒)

- **自成一套**:子開關 `note_shape.tag_hints`(`warn` 預設 / `off`)用自己的解析函式(不改既有兩值回傳的設定讀取);提醒用自己的容器、自己的例外隔離(出錯只印一句,不影響否定現況句提醒、不改回傳碼)、自己的治理帳事件(`hinted`,`check: tag-hints`,記觸發的規則名、行數、篇數);照否定現況句提醒的路,只在提交前(`--staged`)算、**不進違規清單**,所以 `note_shape.gate` 是 block 也不會因此擋。`note_shape.gate` 是 off 時整道檢查不跑,這些提醒也不出(既有從屬關係)。開關是 off 或壞值時,doctor 講一句(照否定現況句的先例)。
- **H2 一行混兩類**:新寫的摘要行超過 140 字,而且同時有兩類的線索詞(詞表放在一處、由測試逐字釘住)→ 提醒拆行。合約行與其他前綴(見〈分類規格〉末段)不提醒。
- **W4 RULE 生命週期**:新寫的 RULE 行,判定沿用既有 `rule_lifecycle_warnings`(不另寫),印它既有的訊息(缺 since、retire,until 過期,confirmed 過期或沒寫,欄位被截斷)。
- **已作廢缺連結**:WHY、RULE、PITFALL 行帶 `[status:superseded]` 卻沒有 `[[連結]]` → 提醒;既有 lint 對 RULE 的 superseded 訊息(「整行刪掉」)改成同一句「留著並加指向取代者的連結」,有連結就不唸。
