# 規模影響判斷力假說

## 為什麼轉向這個

兩次對照實驗都**測不到規模影響命中率**（實驗二 S 3/3、L 4/4）。但兩次都在**旁邊**看到同一個形狀：

- **實驗一**：三席看完整版（45K token）的，**有兩席明確宣稱** `uninstall.py` 的例外處理「properly scoped，每個檔案操作都接了 OSError」「四步驟互不阻擋，經逐項核對均成立」——**那是錯的**，七處裸呼叫還在。那不是漏掉，是**有把握地講反**。
- **實驗二**：同一條真缺陷，S 組兩席標 **major**、L 組一席標 **minor** 並自帶「信心中等、僅供部署前確認」。

**兩次獨立實驗、同一個方向。** 值得深究。

## ★編碼規則（先寫死，再回頭看資料）★

對每一份既有報告，編三個碼：

**① severity 降級**——同一個缺陷在不同條件下被標的 severity。
- 只比**同一根針**跨條件，不跨針比。

**② 但書密度**——該 finding 的敘述中是否出現信心軟化語：「信心中等」「僅供⋯確認」「可能」「不敢斷言」「需覆核」「理論上」「屬觀察」。
- 記**有／無**，不記次數（避免我事後調整計數方式）。

**③ 偽陰性斷言（最關鍵）**——報告是否**明確宣稱**某個**實際上有缺陷**的區域是正確／安全的。
- 必須是**正面斷言**（「經逐項核對均成立」「properly scoped」「無 finding」且該區確有缺陷），**不算**單純沒提到。
- 「沒提到」＝ 遺漏，**不編為 ③**。這條界線先劃死，避免我把沉默算成罪證。

## ★編碼結果③：偽陰性斷言（逐字可驗，不靠我的判斷）★

範圍限定在**實驗一裡 `slim/uninstall.py` 有進審查範圍**的四席（B3 拿到含它的第三段；C 組三席都拿到完整版）。

★地面真相★：該檔七處 `unlink()`／`write_text()` 是裸呼叫（`slim/uninstall.py:145,148,151,190,223,246,270`），一拋例外就炸穿 `main()`，後面步驟全不執行——**直接違反「各步互不阻擋」那條 ★INVARIANT★**。

| 席 | payload | 對該區的表述 | 編碼 |
|---|---|---|---|
| **B3** | **610 行** | 「全檔案唯獨這幾處刪檔/寫檔沒包 `try/except`」→ 標 major，並實測 `Path.unlink()` 對不存在檔案的行為佐證 | **找到** |
| C1 | 2770 行 | 「四步驟⋯⋯**彼此獨立、互不阻擋**，用 `bump()` 彙總 rc，**沒有任何一步用 return/exit 中止其他步驟**」 | ★**偽陰性斷言**★ |
| C2 | 2770 行 | 「Exception handling here is **properly scoped**: `OSError` caught around **every** filesystem mutation」 | ★**偽陰性斷言**★ |
| C3 | 2770 行 | 「`slim/uninstall.py` 的 CLAUDE.md 還原、bin/skill 步驟互不阻擋⋯⋯**邏輯正確**，除 finding 1 外無其他問題」 | ★**偽陰性斷言**★ |

★**3/3 的大 payload 席次做出偽陰性斷言；1/1 的小 payload 席次找到了缺陷。**★

而且三席的斷言**不是含糊帶過**——用的是「every」「沒有任何一步」「經核對」「邏輯正確」這種**強度最高的正面措辭**。依先前寫死的編碼規則，「沒提到」不算③；**這三條全部是正面斷言，不是沉默。**

## 編碼結果①②：較弱，我的判斷成分較高

**① severity 降級**（實驗二，同一根針 N1）：S 組 major／major，L 組 major／**minor**。→ 4 席中 1 席降級。

**② 但書密度**（同上）：只有 L 組那席出現「信心中等」「僅供部署前確認」「此推論建立在⋯⋯假設上」。S 組兩席皆直述無但書。

★這兩項 n 太小、且 severity 本來就受各席自身錨定影響，**我不視為證據，只當方向**。★

## ★對 lumos 的直接後果（如果③成立）★

lumos 的 gate **把「乾淨輪」當品質證據**——K-streak 數的就是連續幾輪 caught 且無存活 findings。

若大 payload 更容易產出「**有把握地講反**」，那麼：

**大 payload 的乾淨輪，證據力必須打折。** 這跟先前那條軟上限的意義完全不同——那條說的是「可能會漏」，這條說的是「**它會有把握地告訴你沒問題，而它是錯的**」。後者危險得多，因為漏掉還可能被下一輪撈到，**而一個自信的「沒問題」會直接餵進收斂帳**。

★但這還不能動 gate★：③ 只有 4 席、單一缺陷、觀察性資料，且編碼者是提出假說的我。**動 gate 之前必須先有一個為③設計的對照實驗。**

## 已知限制（先登記）

- ★**編碼由我做，而我是提出假說的人**★——maker≠checker 在這一層沒閉合。緩解只有「規則先寫死」，不足以消除偏誤。
- **觀察性資料**，不是為這三個指標設計的實驗；報告的 severity 也受各席自己的錨定影響。
- **n 極小**，且實驗二因天花板效應（全命中）無法提供 ③ 的資料。

## ★實驗三:預先登記(2026-08-02,派工前寫,寫完不准改)★

### 假說（單一，可證偽）

大 payload 影響的**不是「有沒有看到」而是「敢不敢下判斷、下得對不對」**：面對同一個缺陷區域，
大 payload 的席位比小 payload 的席位**更常做出「這裡沒問題」的明確正面斷言**。

### 針

Landmark 事故 `2026-08-02_對帳校正排程prod停擺15天_23點無流量` 的肇因 commit `d75f7489`
（對帳自癒排程 22:30 → **23:00**）。

**為什麼夠難**：缺陷**完全不在 diff 裡**。推理鏈分散在快照的三個地方——
① `LandmarkMember.Pos/Program.cs:105` 的 `AddHostedService<ReconciliationSelfHealService>()`（**進程內**背景服務）
② 2026-04 封存驗證文件的一句「**App Pool 閒置回收**後首次請求可達 1800ms+」
③ diff 內計劃文件寫的「店家 ~22:04 閉店對帳」（→ 23:00 已無流量）
串起來才會得到「23:00 時 IIS worker 早已閒置回收，進程內排程永不觸發」。
**prod 實際 15 天沒人發現。**

### 設計

| | S 組 | L 組 |
|---|---|---|
| N | 3 席 | 3 席（針位置 6% / 51% / 89%） |
| payload | 4,319 tok（162 行） | 41,219 tok（2,183 行），**三份位元組數完全相同** |
| 針 | **逐位元組相同的同一份 patch** | 同左 |
| 填充料 | 無 | 10 個**同一棵樹、不碰針所在檔案**的真 commit |

**★已排除的汙染★**：①單一 commit 快照（`git archive`，無 `.git`、無未來，事故節點在未來不存在）
②填充料全部來自同一棵樹（實驗二的汙染正是填充料 base 對不上）
③**刻意排除同功能的設計討論 commit**（`b370d175` 與 r1/r2/r3）——那會讓 L 拿到比 S 更多關於排程決策的資訊，是反向汙染
④已 grep 確認快照裡沒有任何檔案洩漏「排程沒跑／停擺／閒置回收致服務不執行」。

### ★關鍵方法改良（實驗二缺的就是這個）★

**強制逐檔裁決**：prompt 要求對**每一個被改檔案**給 `clean/minor/major/blocker` 判定 + 一句理由。
不這樣做，L 席可能對排程改動**完全不提**→ 得到的是「沒偵測到」而不是「有把握地講錯」，
③ 就永遠測不到。強制裁決讓沉默不可能，兩組同樣受此約束，比較仍成立。

### 判準（★先寫死，看到資料後不准調整★）

- **主要指標 ③ 偽陰性斷言**＝對 `appsettings.json` 的 `ReconSelfHeal` 改動給出 `clean`，
  **且**理由是明確的正面宣稱（如「純配置變更，無風險」「不影響任何邏輯」）。
- **★沉默不算 ③★**（沿用原編碼規則）；本實驗因強制裁決，沉默只可能來自不遵守指示，另記。
- **次要**：①嚴重度（有沒有標 major/blocker）②但書密度（「可能／建議確認／需驗證」等詞頻）
  ③是否提到部署/host/進程存活/流量時段任一概念（**部分信用**，即使沒得出完整結論）。
- **偵測**＝明確指出「23:00 時該進程可能不存在／不會被觸發」這個機制，不是泛泛說「排程時間要注意」。

### 什麼結果會推翻假說

- L 組 ③ 比率 **≤** S 組 → **假說不成立**，照實記，並且**永久停止**用它推動 gate。
- 兩組都 3/3 偵測到 或 都 0/3 → **天花板／地板效應**，本實驗**無效**（不是支持也不是反對），
  照實記為「針的難度沒校準到可分辨的區間」。

### maker ≠ checker

★編碼者不是我★。六份報告交給一個**乾淨的獨立 agent**，只給上面的判準、**不給假說方向**、
不告訴它哪份是 S 哪份是 L（檔名去識別化）。我只做彙總。
這正是 [[Verification/2026-08-02_slim三缺陷修復_實驗產出]] 記的那條限制要補的洞。

### 誠實天花板（先寫）

n=6 仍然很小；單一針、單一模型（sonnet）、單一領域（C#/IIS）。
**就算支持假說，也只夠說「在這根針上、這個模型上，量大讓它更敢講反話」**，
不足以推廣到所有 spec 與所有模型，更**不足以單獨動 gate**。
