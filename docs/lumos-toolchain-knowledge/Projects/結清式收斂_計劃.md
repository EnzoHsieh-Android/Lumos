# 結清式收斂（AREX 借鏡）計劃

> 緣起：2026-07-27 調研日報三篇（AREX／LoopTrap／Sage）齊指「驗證層自己可不可信」。便宜可直接落的當日已 ship（rubric、終止輸入紀律）；這裡收「要設計才能動」的部分。

PRIOR-ART: ① 最小解層級——非新機制，是既有收斂閘（loop status G1/G2）的判準升級，opt-in 疊加。② 世界解——AREX（arXiv 2607.21461）內圈生/外圈逐條約束查＋結構化壓縮；其「驗證比生成便宜、因可拆逐條檢查」前提與本方法論同賭注。③ 裁定=borrow-design（借判準設計，原生實作進 lumos loop status，零依賴不變）。

## 規格（[S] 條款，落地 Verification 認領）

- [S1] **結清模式收斂閘（opt-in）**：`loop status --gate --settle <清單>`——spec 的 ★INVARIANT★／載重宣稱逐條列成「約束清單」（機械格式，一條一狀態：unverified／refcheck-ok／audited）；收斂條件從 K-streak 換成「清單全結清」。能機械查的（引用存在性／行號）走既有 refcheck 通道；語意條才派 LLM 查證。高風險 spec（金流／不可逆）建議用；一般 spec 維持 K-streak。
- [S2] **結構化壓縮（治長跑 governance decay）**：自跑迴圈長上下文不交通用摘要，壓成「已驗證證據＋未結約束」兩欄結構化狀態；★INVARIANT★、「停在放行點」、anchor 驗證列入**壓不掉白名單**。對接 07-26 期「長跑會把安全規矩摘要掉」痛點。
- [S3] **獨立進度驗證器（LoopTrap 貴的那半）**：收斂／進度判斷由一個**看不到被審材料**的小驗證器覆核——只讀客觀指標（findings 機械計數、refcheck 結清數、canary 帳），不讀 spec/報告散文。與 [S1] 天然相容（結清清單本身就是客觀指標）。

## 邊界（明確不做）

- 不替換現行 K-streak 閘（兩模式並存，settle 為 opt-in）。
- 不自動生成約束清單 v1（人／編排者從 spec 手拆；自動拆是後續）。
- 壓縮工具不外掛模型（AREX 用自學工具，我們 v1 用規則式白名單結構）。

## 待辦

- [ ] 動工前過 design-loop（本文即 spec 底稿；預估 tier 標準、金流無涉）
- [ ] [S1] 清單格式與 `--settle` 介面設計（含與 G2 枯竭錨的關係——結清模式下 G2 是否仍需）
- [ ] [S2] 白名單條目定案（哪些紀律必須壓不掉）
- [ ] [S3] 驗證器輸入契約（哪些帳算「客觀」、如何防被審材料滲入）

## 誠實邊界

- 結清＝「列出來的都驗了」，**清單本身漏列的照樣漏**（清單完整性是新的單點，v1 靠人拆＝人的注意力上限）。
- AREX 的前提「驗證可拆成便宜逐條檢查」對語意合約只部分成立——語意條的單條查證仍是 LLM 判斷，rubric 化能錨定但不消除判官不穩（Sage 天花板同在）。
