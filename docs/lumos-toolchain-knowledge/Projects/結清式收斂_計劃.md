# 結清式收斂（AREX 借鏡）計劃

> 緣起：2026-07-27 調研日報三篇（AREX／LoopTrap／Sage）齊指「驗證層自己可不可信」。便宜可直接落的當日已 ship（rubric、終止輸入紀律）；這裡收「要設計才能動」的部分。

PRIOR-ART: ① 最小解層級——非新機制，是既有收斂閘（loop status 四條合取 K-streak∧G1∧G2∧G3）的判準升級，opt-in 疊加。② 世界解——AREX（arXiv 2607.21461）內圈生/外圈逐條約束查＋結構化壓縮；其「驗證比生成便宜、因可拆逐條檢查」前提與本方法論同賭注。③ 裁定=borrow-design（借判準設計，原生實作進 lumos loop status，零依賴不變）。

## 規格（[S] 條款，落地 Verification 認領）

- [S1] **結清模式收斂閘（opt-in，v1 只接 legacy 路徑）**：`loop status --gate --settle <清單檔>`（`--settle` 為**本計劃新增旗標**，現行 CLI 尚無）。
  - **模式邊界（r1 折入）**：現行三種收斂判準並存（legacy K-streak／`--panel` 結構信號／`--light` 單席謂詞，互斥）。v1 的 `--settle` **只替換 legacy 的 K-streak 條件**；與 `--panel`/`--light` 併用＝**rc2 互斥**（panel/light 的 settle 化留後續評估，不在 v1）。G1／G2／G3 三錨**照舊合取**（settle 換的只是 K-streak 那一條；G2 在 settle 下語意變弱、是否降 advisory 見待辦）。
  - **約束清單**：spec 的硬合約／載重宣稱逐條列成機械格式，一條一狀態：`unverified`（未查）／`mech-ok`（機械查訖：refcheck 通道，僅買「引用存在／行號有效」）／`llm-ok`（語意查訖：LLM 實質查證過宣稱成立）。狀態名刻意不用 audited（避免與合約鏈 `[audit:]` 撞語意——那是「合法性」審計，這裡是「宣稱成立」查證，兩軸不同）。
  - **結清終態規則（r1 折入，堵語意條機械放行）**：機械條（純引用存在性宣稱）`mech-ok` 即結清；**語意條必須 `llm-ok` 才結清**——`mech-ok` 對語意條只是中繼態。條目建檔時標 `kind: mech|semantic`（人拆時判）。
  - **canary 醒著條件保留（r1 折入，堵拔守衛）**：settle 輪照 skill 紀律植 canary；**該輪 missed（審計員沒抓到）＝該輪所有 `llm-ok` 推進不採信、狀態回滾**——「查證的人醒著」仍是語意條結清的前置，settle 換掉的是「數趨勢」不是「驗審計員」。
  - **清單↔spec 版本綁定（r1 折入，借 G3 慣例）**：清單檔記 `spec_sha`；gate 時比對現行 spec sha，不符＝清單過期 rc1（指出須重拆或確認未受影響條目）。條目失效軸＝**spec 內容變更（hash）**，不是輪次計時。
  - 收斂＝清單全結清 ∧ G1 ∧ G3（∧ G2 視待辦裁定）。高風險 spec（金流／不可逆）建議用；一般 spec 維持 K-streak。與 skill 既有「高風險建議 `--need 3`」的關係：settle 取代 need（結清是逐條存在證明，不再數輪）——skill 文案落地時同步。
- [S2] **結構化壓縮（治長跑 governance decay 殘餘面）**：自跑迴圈長上下文不交通用摘要，壓成「已驗證證據＋未結約束」兩欄結構化狀態；硬合約、「停在放行點」、anchor 驗證列入**壓不掉白名單**。
  - **價值域校準（r1 折入）**：圖譜既有裁定（[[Systems/autonomous-iteration-loop]] 2026-07-26 對帳）＝架構已有結構性 counter（每輪重注入／fresh spawn），殘餘面只剩「對話中途口頭約定」——本條治的是**殘餘面**，非全開的洞。
  - **掛載面（r1 折入）**：自主 loop 的編排入口與 scratch 狀態（`governance/autonomous_loop/orchestrator-prompt.md`、`governance/autonomous-loop.sh`）；輸出 schema／檔名／消費步驟＝待辦展開。
- [S3] **獨立進度驗證器（LoopTrap 貴的那半）**：收斂／進度判斷由一個**看不到被審材料**的小驗證器覆核——只讀帳面結構欄位（findings 計數、settle 清單狀態、canary caught/missed），不讀 spec/報告散文。
  - **誠實界定（r1 折入，辯方裁後措辭校準）**：這些帳是「結構欄位」不是「客觀真值」——findings 數與 severity 源頭仍是 LLM 裁決、canary 帳由植入者自判（既有系統天花板，非本計劃新增）；驗證器隔離的是**散文注入面**，隔離不了「帳本由被驗方書寫」。**已知合法散文通道＝record 的 `--note` 欄**：驗證器輸入契約必須做欄位級過濾（只讀結構欄位、丟棄 note）——[S3] 測試的對抗散文即從 note 欄注入（通道明確，測試不空轉）。

## 邊界（明確不做）

- 不替換現行 K-streak 閘（settle 為 opt-in；不帶 `--settle` 行為 bit 不變）。
- v1 不接 `--panel`/`--light`（互斥 rc2；panel 的結清化留後續）。
- 不自動生成約束清單 v1（人拆；**編排者代拆時清單完整性回到 maker bias**——見誠實邊界）。
- 壓縮工具不外掛模型（規則式白名單結構）。

## 實務隱患

- **self-governance（真命中）**：本 spec 改的是「守自己的閘」——結清模式若設計錯，收斂閘形同虛設且不易察覺（壞掉的守衛比沒有守衛更危險）。防範：① opt-in 並存、不替換現行閘（壞了退回既有路徑零成本）② 本計劃動工前自身過 design-loop（吃自己的狗糧，r1 已跑：抓到含 blocker 級的真缺陷並折入）③ canary 醒著條件在 settle 下明文保留 ④ [S3] 驗證器輸入契約欄位級過濾。
- **payment（不適用）**：spec 內「金流」字樣僅作為「哪類 spec 建議用結清模式」的舉例情境，本計劃不觸任何金流代碼或資料。
- **prod-irreversible（不適用）**：改動全部落在 repo 內的 gate 邏輯與 skill 文本，git 級可逆；無部署面、無外部消費者。

## 誠實邊界

- 結清＝「列出來的都驗了」，**清單本身漏列的照樣漏**（清單完整性是新的單點）；v1 靠人拆＝人的注意力上限，**編排者（LLM）代拆時清單完整性直接回到 maker bias**——被閘的一方拆自己的驗收清單，此半無外部守衛（r1 折入）。
- AREX 的前提「驗證可拆成便宜逐條檢查」對語意合約只部分成立——語意條的單條查證仍是 LLM 判斷，rubric 化能錨定但不消除判官不穩（Sage 天花板同在）；canary 醒著條件買的是注意力下限，不是查證正確性。
