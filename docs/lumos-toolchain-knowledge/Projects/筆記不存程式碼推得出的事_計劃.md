# 筆記不存程式碼推得出的事_計劃

白話:筆記只准寫程式碼推不出來的東西(為什麼、否決過什麼、事故、程式看不到的限制)。程式碼推得出來的內容一寫進去就會過期、而且讀的人分不出來——rtb 在新規則下寫的筆記,抽樣現況句 41% 已經跟程式碼對不上。這次不再靠寫法規範,改成兩層機械擋:提交時擋形狀固定的東西,推送前派一個沒有脈絡、會去讀程式碼的審查員,逐行判新增的筆記內容是不是程式碼推得出來,判是的就不准推。

依據:[[Issues/筆記把程式現況寫進脈絡而漂移_rtb實測回饋]] 的 d1–d6(Enzo 2026-09-27 裁);為什麼前一版沒擋住見 [[Projects/Lumos定位_程式碼為主脈絡為輔_計劃]]〈檢討〉。

**★2026-09-27 拆分(Issue d7,Enzo 裁;分工以 d8 為準)★**:本計劃設計審兩輪(r1 38 條、r2 32 條,都全折)後拆成兩份。第一層形狀擋、「範圍與行」共用函式、紀律範本改寫,移到 [[Projects/筆記形狀擋_計劃]] 先審先做;治理帳寫入加鎖兩份都不做,移到 [[Issues/治理帳多個寫入者都沒上鎖]] 另外決定(第二層要寫通過紀錄,上線前要先看那篇有沒有結論);本篇只留第二層推送前 AI 審查員(含計劃轉 done 的整篇審、decision-amend、校準),之後在原迴圈開 r3 審剩下的部分。下面標「已移出」的段落保留原文供對照,以那一份為準。

PRIOR-ART: 機制層借本 repo 兩個既有形狀:①代碼審留痕閘([[Systems/pitfalls-code-loop]])的「推送前查這批改動有沒有通過紀錄、`--no-verify` 硬推時 CI 標紅、帶理由的 skip 出口」;②新增告警閘放行檔的「綁內容指紋不綁版本」(`lumos lint-waive`,理由是綁版本會讓每次提交都要重來)。★綁定方式照②不照①★:代碼審留痕綁提交祖先鏈,壓提交或 rebase 後內容沒變也會失效(pitfalls-code-loop 2026-09-22 那條事故),本案若照抄就會讓每個後續程式提交都逼人重審。判定者照無脈絡審查席的派法(乾淨 agent、只給原始問題不給結論)。世界的做法:文件與程式碼同步多半走「從程式碼生成文件」(openwiki 一類,見 [[Systems/外部對照-code衍生wiki]]),它讓文件免疫漂移,但裝不下程式碼沒有的脈絡——本案反過來,讓筆記只裝那一種。不採用新依賴。
RETIRE-IF: 上線兩個月後任一成立就撤掉或重想第二層:①作者申訴被第二席認同的比例超過三成(判定者不可靠);②對上線後新增的筆記行隨機抽樣,仍有一成以上是程式碼推得出來的(擋不住);③新增的脈絡行(判成 CONTEXT 的)月量掉到上線前的三分之一以下(大家乾脆不寫筆記了,擋掉的比救下的多)。
REVISIT:2026-11-27 跑上面三個量;順便在 rtb 重做一次跟 2026-09-27 同方法的漂移抽樣,拿 41% 當基準比。

## 判定者能不能用:小實驗(2026-09-27)

把 rtb 的 68 句打亂、拿掉標題旁的提示,給兩個沒有脈絡的審查員,各自讀 rtb 程式碼判「程式碼推得出 / 脈絡 / 一半一半」。其中 55 句是稽核逐句對過程式碼的現況句(答案應該是推得出或一半一半),13 句是決策欄位裡的「為什麼選這個」(答案應該多半是脈絡)。卷證在 `governance/audits/2026-09-27-rtb-notes/judge-experiment/`。

| 審查員 | 55 句現況句抓到 | 13 句理由誤判成純程式碼 | 花的時間 |
|---|---|---|---|
| opus | 55(53 推得出、2 一半一半) | 0(9 脈絡、4 一半一半) | 約 4.4 分鐘 |
| sonnet | 54(漏 1 句:在講已刪掉的程式,它判成歷史) | 3 | 約 9.7 分鐘 |

- 兩席在「要不要擋」上 68 句同意 64 句。判成一半一半的理由句我逐句看過,裡面確實夾著程式現況(例如「某函式在第幾階段加的、路由和評估都靠它」)。
- **誠實界線**:正例是稽核挑出來的現況句,比真實新增行好判;反例只有 13 句;對照答案由我一人訂。真正難的是「一句話裡理由跟現況混在一起」,這類樣本太少。所以 claude 編排時判定者用 opus(Codex 編排時用同一家的審查席模型,見〈做法〉第二層第 2 點,那一家的準度要另外校準)、派工詞要明寫「描述已刪掉的程式、用現在式寫的,也算推得出」,而上線後的申訴率是第一個要看的數。
- 句型比對做不到這件事:同日對近一個月 25,282 行新增筆記跑「目前沒有/只有 N 種」句型,抽樣約三分之一是真的,見 Issue〈擋什麼的初步實測〉。

## 做法

### 共用:哪些行算「這次新增的筆記行」(已移出:範圍與行的定義以 [[Projects/筆記形狀擋_計劃]] 為準;本篇只加「計劃轉 done 整篇進集合」那一條)

- **範圍**:提交前=暫存區差異。推送前:遠端已有那個版本就用「遠端版本..本機版本」;★新分支或本機沒有遠端那個版本時,照「每支檔有家」推送檢查的既有算法★——起點是「不在任何遠端分支上的提交」裡最早那個的上一個提交;全部已在遠端就不查;最早那個沒有上一個提交(真的全新)才從空樹比。不用「跟預設分支的分岔點」:本 repo 2026-07-21 因為直接在主線工作時分岔點等於自己、整組守衛靜默跳過,把那種算法拆掉過([[Projects/prepush主幹範圍修法_計劃]]),而且消費專案的預設分支不一定叫 main。CI:推送前後兩個版本;新分支首推(前一版全零)時照同一個「不在其他遠端分支上」的算法,排除這條分支自己的遠端參照,CI 那一步要抓完整歷史;★不照 CI 既有代碼審那一步的空樹兜底★(那會把整庫舊筆記當新增)。
- **行**:圖譜筆記在範圍內新增或改動的行(改名用 git 的改名偵測認成同一篇,只算真正變動的行;偵測不到改名時新檔整篇算新增,方向是多審不是漏審)。**算進來的**:正文(含程式碼圍欄裡的內容與「引句:」行)、開頭欄位的 `summary` 摘要區塊、`decisions` 每條底下所有文字值的子欄(不列欄名,因為實際寫法有 `alternatives_considered`、`alternatives`、`trade_offs` 等好幾種;只排除 id、日期、valid、superseded_by 這類結構子欄)。**不算的**:其他開頭欄位(tags、連結清單、日期、status、lands_in、aliases、about_code 這類結構欄)。刪掉的檔不算。
- **計劃在範圍內被改成 done**(比對改名前的舊路徑狀態;改名偵測不到時新檔本來就整篇算):那篇計劃整篇正文都進集合,不只新增行。這是 d2「改到才清」的「改到」,也是 d4 的執行方式——判成推得出或一半一半的現況細節刪掉,剩下的是開工的問題與理由這類脈絡;不另設「只准剩一句」的行數規則(脈絡本來就可以不只一句,要擋的是現況)。
- 圍欄判定一律用既有的 `_visible_lines`,不另寫一套。筆記檔讀不成 UTF-8:整支擋下並講是哪支檔。

### 第一層:提交時擋形狀固定的東西(已移出,見 [[Projects/筆記形狀擋_計劃]])

只看上面定義的新增行,舊行不管(d2)。兩條:
1. **程式行號引用**:`路徑:數字`、`路徑#L數字`,而路徑是 repo 裡的程式檔或測試檔——用每支檔有家那套程式檔判定(它認得沒有副檔名、開頭是 `#!` 的主程式),再把它排除掉的測試檔加回來。圍欄裡的不算(那是當時的輸出)。`.md` 這類文件路徑不擋。**放行寫法**:釘住版本的 `路徑@<提交>:數字`;要指到測試就寫測試名。用中文寫「某檔第 42 行」這種不在形狀裡,歸第二層判。
2. **現況類前綴沒寫出程式碼答不了的來源**:新增的(圍欄外的)`FACT:` `FLOW:` `DEP:` 行要帶 `[src:部署]` `[src:資料庫]` `[src:生產]` `[src:外部]` `[src:人工]` 其中之一(d3);只寫「以程式碼為準」加查詢不再算數。

回傳碼照鄰居:0 過、1 擋、2 參數錯;不是 git 或找不到 lumos 就照既有 hook 慣例放行並說一句。閘名 `note-shape` 登記進既有閘名單。擋下訊息要明講「內容還在工作目錄,改完再提交」(提交前被擋時沒有產生提交,hook 不得動工作目錄)。

### 第二層:推送前的筆記內容審(`lumos note-audit`)

1. **`prepare --diff <範圍> --orchestrator claude|codex`**(編排者那一家必填,不預設——照 `loop next` 的既有規矩,猜錯家族是事故來源):算出新增行集合;集合是空的就說「沒有新增筆記行」、rc0、不產生檔。每行給「內容編號」=路徑加那行文字的短雜湊;同一段文字在同一篇出現好幾次,清單列出每一處的行號與次數。清單連同判定者派工詞用既有的原子寫入(暫存檔再換名,`_write_lf`)寫成 `.lumos/note-audit/<集合指紋>.md`;集合指紋=所有(路徑, 行文字)排序後的雜湊。`.lumos/note-audit/` 加進 `.gitignore` 與初始化時的忽略設定;prepare 順手清掉 14 天前的舊清單。
2. **派審查員**:判定者跟編排者同一家——claude 派 opus、codex 派 Codex 那邊審查席的既有模型;不派外家席(內容只送到會談本來就在用的那一家)。派工詞由 prepare 產生:`judge_prompt.md` 的三類分類定義逐字沿用,專案路徑與技術棧換成被審 repo 自己的(那支檔開頭寫死 rtb 的路徑與「Python」,不能照抄),再加四句:①用現在式描述已刪掉的程式,也算推得出;②一行有多個子句時逐子句判,一半一半要列出哪幾個子句推得出;③推得出的部分附證據——`file:line`,或 `search: <字串> in <路徑> => <命中數>`(「沒有 X」這類寫 `=> 0`);④用文字描述程式某一行位置也算推得出。報告開頭三行固定:`seat:`(席名)、`provider:`、`model:`。行數多就切批平行派,每批用內容編號;每批不超過 150 行(計劃轉 done 時整篇上千行也照這個切),讓每批的規模跟校準時量的一樣。
3. **作者處理**:推得出的整行刪;一半一半刪掉推得出的子句;「引句:」行被判就整句刪、不改字(改字就是竄改原話)。`decisions` 裡被判的,用新的 `lumos decision-amend` 改——★只准改「任何一個遠端追蹤分支上的那篇筆記裡都還沒有」的決策編號★(逐一讀遠端追蹤參照上的同一篇來判,跟分支拓撲無關;沒有任何遠端就都能改);已推上去的照舊只能翻案。**申訴**:另派一席(席名必須跟第一席不同)單判那一行、不給它前一席的結論;第二席判得比第一席輕就以第二席為準。★申訴成立只改變要做的事★:降成一半一半,原行仍要消失(刪掉推得出的子句);降成脈絡才准原樣留。
4. **`record --diff <範圍> --report <報告> [--report …] [--dispute <報告> …]`**:不信報告自己列的清單,重算集合,要求:①每一行的內容編號都在某份報告裡有判定(報告產生後才加的、改寫後變成新內容的,都要另有判定);②同一編號在兩份非申訴報告裡判得不一樣就拒絕(要走申訴,不准用重跑蓋掉);③判推得出的行、以及申訴後仍是一半一半的行,原行都已不在集合裡;④證據:`file:line` 的檔存在、行號不超過檔長;`search:` 由工具自己跑一次(字串至少 4 個字、路徑是檔或資料夾都可、資料夾就遞迴掃、跳過 .git),命中數要跟報告寫的一致;⑤報告開頭三行齊全、申訴報告的席名跟被申訴那份不同、provider 跟 prepare 時給的編排者同一家。都過才寫一筆通過,綁集合指紋,並記下 provider、model、申訴筆數與結果。沒過 rc1、不寫帳、列出哪幾行缺判或還在。
5. **治理帳寫入**:一律走治理帳既有的通用寫入器 `_gate_event`(閘名 `note-audit`,事件種類沿用鄰居的 passed / skipped / blocked,登記進既有閘名單),不另開寫入路徑。★順手讓 `_gate_event` 與代碼審那支 `_codeloop_gov_log` 在寫入時拿同一把治理帳檔案鎖★(兩支現在都是直接 append、沒有鎖;只替新指令加鎖擋不住跟舊寫入者的交錯)。等鎖超過上限照既有 rc 協議印「擋下:…」回 2,不丟裸例外。
   (已移出,2026-09-27 d8:上面這段「順手替 `_gate_event` 與代碼審寫入加共用鎖」不在本計劃做,見 [[Issues/治理帳多個寫入者都沒上鎖]];本計劃只照既有寫入器寫帳。)
6. **`check --diff <範圍>`**:推送前與 CI 另開一支平行呼叫(跟 `home check` 同形狀)。算集合指紋,治理帳有對得上的通過或 skip 就放行,否則 rc1 並印 prepare 那行指令。指紋只看內容:rebase、壓提交、只改程式碼都不影響。★通過紀錄要進提交才算數★:照代碼審既有的「簿記檔還沒提交」處理,record 之後列出要提交的治理帳,check 在推送前發現對得上的紀錄只在未提交的工作樹裡就擋並印提交指令——不然本機綠、乾淨 checkout 的 CI 紅。
7. **出口**:`lumos note-audit skip --diff <範圍> --note "<理由至少 4 個字>"`,skip 除了綁集合指紋還綁這次推送的頂端提交(只對這一次推送有效,程式碼再變就要重來)。專案開關 `.lumos/config.json` 的 `note_audit.gate`:block(預設)/ warn / off(值照鄰居 `lint_new.gate` 與 `node_home.gate` 的叫法);★不是 block 時,`lumos doctor` 每次都印一行「這個專案把筆記內容閘設成 warn/off」(照 `node_home.gate` 既有先例),check 每次放行也寫一筆 skipped 事件★,所以關掉的專案不會從 RETIRE-IF 的量裡消失。環境變數 `LUMOS_SKIP_NOTE_AUDIT=1` 單次跳過並寫帳。模型限流、服務中斷時走 skip。
8. **消費專案的 CI**:`lumos update` 不會動各專案的 CI 設定檔。所以 `lumos doctor` 檢查專案 CI 有沒有呼叫 note-shape 與 note-audit check,沒有就每次印一行並給要貼的那一步;另外 doctor 事後掃「已推上遠端、卻找不到通過或 skip 紀錄的新增筆記行」,有就列出(抓 `--no-verify` 繞過)。

### 上線前校準(接線之前做,每一家編排者各做一次)

小實驗餵的是稽核員切好的單句,正式跑的是原始整行。所以把 check 接進推送前之前,每一家(claude、codex)各做一次:用 prepare 對 rtb 近一週真實的新增行、再加一份 300 行以上的已完成計劃整篇,兩席各自獨立判,編排者抽 30 行人工對照。兩席「要不要擋」一致率低於 85%,或人工對照有超過 2 行純理由被判推得出,那一家就先不接線、改派工詞重來。換模型也要重做。

### 規範文字跟著改

紀律範本〈寫筆記時〉那張表的 `FACT:` `FLOW:` `DEP:` 整列改成 d3 的收窄說法(只准寫程式碼答不了的現況、要帶 `[src:]`),並寫明兩層擋的存在、放行寫法(釘版本的行號)、申訴、skip 與專案開關。各專案各自跑 `lumos update` 拉新版(那支指令是從工具鏈原始 repo 拉進本專案,不是由這裡推出去)。skill 裡只指路、不放第二份定義。

## 回退

照這個順序,反過來會卡住別人推送:
1. **先改 CI**:把工具鏈自己 `.github/workflows/ci.yml` 裡新增的兩步拿掉——這支檔不在 `lumos update` 的同步清單裡,要手改;不先拿掉,指令一移除,CI 對每次推送都會因為找不到子指令而變紅。消費專案自己貼過那兩步的,也要各自拿掉。
2. 消費專案不用等中心:各自把 `.lumos/config.json` 的 `note_audit.gate` 設成 off 就停第二層。
3. 拿掉提交前與推送前 hook 裡的呼叫,再移除 note-shape / note-audit / decision-amend 指令與 doctor 那兩段;各專案 `lumos update` 拉回。
4. (已移出:治理帳加鎖改由 [[Issues/治理帳多個寫入者都沒上鎖]] 決定,本計劃沒有鎖要回退。)
5. 治理帳裡已寫的紀錄留著:不會被拿去擋任何東西,但 `lumos gov --stats` 會照樣列出這個閘名的舊筆數(它不挑閘名)。
6. 紀律範本那列改回舊句時要先想好:舊句正是讓現況描述留存的出口(見〈檢討〉第 4 點)。
7. 被第一層擋下的內容從沒進過 git,只在作者的工作目錄。

## 實務隱患

- 守衛面:新的擋人機制,誤擋會讓人習慣繞過——所以第一層只看新行、不擋文件路徑、有釘版本的放行寫法;第二層有申訴、skip 與專案開關,而且關掉或跳過都寫帳、doctor 持續印,全部進 RETIRE-IF 的量。
- 對外送出:筆記行與被讀的程式碼會送到判定者那一家模型;限定跟編排會談同一家、不派外家席,所以不會多出一家供應商看到專案內容。
- 資源併發:兩個會談同時 prepare → 清單檔以集合指紋命名、原子寫入;同時寫治理帳 → 所有寫入者共用一把鎖;審查中途斷掉 → 沒有通過紀錄就是沒過,重跑 prepare 得到同一檔;審查期間又改筆記 → record 重算集合,新內容沒判定就拒絕。
- 可用性:模型限流或服務中斷時走 skip(留理由、進帳、只對那次推送有效),不用 `--no-verify`。
- 已排除:不可逆:第一層擋下時不產生提交、hook 不動工作目錄,內容留在作者手上;第二層擋在推送前,提交都還在本機;拿掉閘就恢復原狀
- 已排除:金流:不碰任何付款或計費流程

## 誠實界線

- 判定者的準度只驗過一次、68 句、反例 13 句,而且是切好的單句;所以接線前每一家都要照〈上線前校準〉再驗一次,上線頭兩週逐筆看申訴。
- 兩席在三類判定上 68 句有 9 句不一致,一半以上是「推得出」對「一半一半」——申訴規則就是為這種雜訊設的,但它也讓作者多一次重擲的機會;申訴成立率是 RETIRE-IF ① 的量。
- 通過紀錄只綁筆記內容。一句當初判成脈絡的話,之後程式碼改了、變成程式碼推得出來,不會觸發重審(d2 不回頭清);這靠 RETIRE-IF ② 的每月抽樣抓。REVISIT 那天看抽樣裡有幾句是這種。
- 沒有接 CI 的消費專案,`--no-verify` 推上去當下擋不住;doctor 事後會列出來,但那時已經在遠端了。
- 第二層只審這次推送新增的行,舊筆記裡的現況句還會被讀到,直到有人改到那篇或把計劃轉成 done。
- 花費:本 repo 近一個月約 473 個提交新增 25,282 行筆記,一次推送要判幾十到幾百行,計劃轉 done 時可能上千行;Enzo 已表明不在意額度(d6),但推送前要多等審查員跑完。
