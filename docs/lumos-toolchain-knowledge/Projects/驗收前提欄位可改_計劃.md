# 驗收前提欄位可改_計劃

PRIOR-ART: 沿用自家寫入原語的形狀:`set` 的原子寫入加寫後自驗(`atomic_write_verify`)、單一值的引號規則(`fmt_scalar`)與清單項的引號規則(`fmt_list_item`)、同一把圖譜寫入鎖;不另開新指令(跟 2026-08-23 `remove <note> <key>` 不帶值那次一樣:一個指令學一次)。
RETIRE-IF: 驗收紀錄改成不再用這兩欄(例如前提改寫進正文某個結構化段落),或 set 改成通用的「任何開頭欄位都能整欄換掉」。

## 一句話

讓 `lumos set` 能整欄換掉驗收紀錄的前提與回頭條件:給一個值寫成單行,給多個值寫成一行一項的清單,不管原本是什麼形狀。

## 做法

- `set` 的值參數改成可以給多個;除了這兩欄,其他欄位給超過一個值照樣擋(說只收一個值)。
- 這兩欄另列一組,不併進單一值白名單(那份白名單的數量有圖譜漂移守衛在數,併進去要一起改;而且這兩欄本質上可以是清單,不是單一值)。
- 原本的形狀(單行、清單、空的、多行區塊)整段拿掉,換成新寫法;欄位不存在就新加。
- 每個值不能空、不能有換行(一行一個條件;要多條就給多個值)。
- 寫完照舊在記憶體裡重新讀一次,確認讀回來的條件跟給的一模一樣才落檔;不對原檔不動。

### 不做的

- 不讓 append/remove 收這兩欄:這兩欄是散文,常提到連結;append/remove 判斷「同一項」用的是連結目標,兩條提到同一篇的不同條件會被當成重複。要改就整欄重給。
- 不順便讓 set 能整欄換任何欄位:其他欄位各有自己的寫入規矩(決策、清單連結),放寬會繞過它們。

## 條款

- [S1] 當 `lumos set` 對 valid_under 或 revalidate_when 給一個值,寫入後該欄位應只剩這一個條件,不管原本是單行、清單、空的或多行區塊 [test:t_set_condition_fields_replace_any_shape]
- [S2] 當 `lumos set` 對這兩欄給兩個以上的值,寫入後應是一行一項的清單,讀回來的條件順序與內容跟給的相同 [test:t_set_condition_fields_multi_values]
- [S3] 若給這兩欄的任一個值是空的或含換行,則寫入應被擋下、檔案不變 [test:t_set_condition_fields_reject_bad_values]
- [S4] 若對其他欄位給兩個以上的值,則寫入應被擋下、檔案不變,原本只給一個值的用法行為不變 [test:t_set_other_keys_single_value_only]
- [S5] 當這兩欄被換掉,開頭其他欄位與正文應一字不差 [test:t_set_condition_fields_keep_other_lines]
- [S6] 當 set 或 append 寫出一個值,本工具與標準 YAML 讀回來應相同:不在安全白名單內的值要加引號,有反斜線或雙引號改用單引號;若同時有單引號與雙引號或反斜線則應擋下、檔案不變 [test:t_set_condition_fields_standard_yaml_safe]
- [S7] 當 decision-add 或 decision-supersede 寫出決策的文字欄位,應跟 set/append 走同一套白名單與加引號規則 [test:t_decision_add_standard_yaml_safe]

## 回退

把 `set` 的值參數改回只收一個、拿掉那一組欄位;已經寫進去的前提都是合法的單行或清單寫法,讀的一側本來就認得,不用搬資料。

## 實務隱患

- 已排除:金流:只改本機筆記開頭的兩個欄位,不碰任何付款或計費
- 已排除:對外送出:只寫本機檔案,不送任何東西出去
- 已排除:不可逆:原子寫入且寫錯不落檔,改錯了用同一個指令再改一次就回來
- 已排除:守衛面:不放寬任何既有檢查,其他欄位的 set 行為不變(條款 S4 綁測試)

## 誠實界線

- 只管寫入;前提過不過時照舊由健檢的「超過 90 天沒更新」與進場提醒來喊,這次不改。
