# 推送與CI提速_計劃

> 白話:一個功能從推送到能合併常要 25–40 分鐘。等最久的是本機推送前的全套(5–10 分)和 PR 的 CI(約 12 分);CI 的 16 份測試照名字輪流分、不看耗時,最慢的機器要等到 12.4–14.3 分。這篇分兩階段:第一階段讓 CI 各份照耗時分平均、同一個 PR 有新推送就取消舊的 CI;第二階段(等另一個會談改完推送前掛鉤)讓推功能分支時本機不跑全套。

PRIOR-ART: 世界上的共識是「便宜的子集擋大多數錯、完整測試每個提交只跑一次」:Google TAP 提交前跑受影響的、提交後跑完整(https://abseil.io/resources/swe-book/html/ch23.html);Meta 預測式選測只跑約三分之一仍抓到 99.9% 有問題的改動(https://engineering.fb.com/2018/11/21/developer-tools/predictive-test-selection/)。依耗時分片同 pytest-split 的做法(一份各測試耗時表、讓每片總耗時接近,https://pypi.org/project/pytest-split/);同 PR 新推送取消舊 CI 用 GitHub 原生的 `concurrency` + `cancel-in-progress`(https://docs.github.com/en/actions/concepts/workflows-and-actions/concurrency)。來源整理見 2026-10-14 兩路調研(Claude 與 Codex 各一份,結論一致)。本 repo 既有的 [[Projects/CI加速_計劃]] 已把全套分到多台機器;這篇在它之上動分法與觸發,不改測試內容。

RETIRE-IF: 依耗時分片上線後連續 20 次全套 CI,各台 shards 機器耗時的最大值與最小值之差,沒有比上線前(抽樣 6.1–14.3 分,差約 8 分)縮小一半以上,就刪掉耗時表、退回照名字輪流分。

## 現況(2026-10-14 量)

- CI(`.github/workflows/ci.yml`)有三個工作:prep(編譯檢查、判這次跑全套還是文件子集)、shards(全套分 16 份給 8 台機器,每台同時跑 2 份)、gates(後盾閘)。最近 300 次:推到 main 206 次、PR 94 次;成功 287 次,整次中位數 12.2 分。抽 4 次成功的 CI,每台 shards 機器跑完兩份要 6.1–14.3 分,最慢的一台每次都在 12.4–14.3 分;差這麼多是因為照名字輪流分、不看耗時。CI 目前只印每台的總時間,每份的時間量不到。
- 每個功能,改到程式而且不是輕量改動時:本機全套(推送前掛鉤切 4 片,掛鉤提示寫約 4–5 分,實測常到 5–10 分)+ PR 的 CI 約 12 分 + 合併後主線的 CI 約 12 分(主線那次在背景跑,不會讓人等)。只改文件或判成輕量的推送,本機只跑子集。

## 範圍

- 第一階段(這篇交付):①依耗時分片(本機推送前與 CI 共用測試執行器的同一支分片函式);②同一個 PR 有新推送時取消舊的 CI(主線每個提交都跑完,不取消、不取代);③CI 印出每一份的耗時,讓撤除條件量得到。
- 第二階段(不在這篇交付,另開條款):推功能分支時本機不跑全套。推送前掛鉤正被另一個會談大改,等它合併後再做。
- 不做:主線略過全套與快轉合併(設計審 r1 三席指出 PR 與主線的 git 環境對不齊、主線排隊中的 CI 會被取代、查詢條件與權限難以寫死;它只省 GitHub 機器時間、不縮短人的等待,使用者 2026-10-14 裁定拿掉);縮小 CI 的測試範圍(要先讓選測器陪跑、證明不漏抓,另案);合併佇列(單人加兩三個會談,搶合併的情況少);快取(零依賴,沒有可快取的建置產物)。

## 做法

- **耗時表**:新檔 `governance/test-durations.json`,格式 `{"version": 1, "tests": {"測試名": 秒數, …}}`,進版控,本機與 CI 讀同一份。放 `governance/`:那裡已有進版控的資料檔(防竄改基準線),而且只改它的推送會被判成文件改動、只跑文件子集;另加進代碼審的簿記檔清單,刷新它不會讓已過的代碼審留痕失效。耗時表錯了只會分得不平均,不會漏跑(見下面的聯集保證),所以可以當資料看。
- **記錄實測秒數**:測試執行器(`scripts/test_lumos.py`)每支測試跑完都記秒數,不論過、紅、逾時或丟例外(逾時記到逾時那一刻;跳過的不記)。跑完寫進 `.lumos/test-durations-run*.json`(分片時檔名帶 `shard1of4` 這種片號,同快取的命名;不分片時同名舊檔的內容先合進來,跑一小段子集不會把先前全套量到的蓋掉;也記下這次紅的是哪幾支;暫存檔名每次不同;本機、加進 `.gitignore`,只在來源 repo 寫,同既有 `test-cache` 快取的條件與先寫暫存再換名的寫法)。
- **刷新耗時表**:新增子指令 `lumos test-durations refresh`(改寫進版控的檔,所以放在 lumos 主程式、不放在執行器的「這次怎麼跑」旗標裡):讀 `.lumos/test-durations-run*.json`,同一支測試取檔案時間最新的那一筆,沒跑到的保留舊值,寫回 `governance/test-durations.json`(秒數存到小數三位),讀完刪掉那些 run 檔。run 檔讀不懂就略過、裡面不合法的秒數那一筆不收;run 檔標成紅的那幾支只在比舊值大時才收(紅或逾時只能讓一支看起來更慢,環境壞掉時一堆瞬間紅不能把表拉小);同一時間只准一個刷新(`.lumos/` 裡的獨佔鎖檔);舊表讀不懂或有一筆不合法就擋下(rc 2)、不覆蓋,要重建先刪掉它——刷新與執行器讀表用主程式同一支函式(執行器載入主程式來呼叫,不另寫一份),刷新寫得出來的表執行器一定讀得進。寫檔用主程式既有的原子寫入(暫存檔名每次不同)。什麼時候刷新:人或代理覺得 CI 各台又不平均時手動跑,或每月一次(下面的回頭條件)。
- **分片(`--shard i/n`)**:
  - 執行順序照現行:`--suite` 先篩,再分片,再 `--ff` 重排、`--seed` 打亂,最後 `-k`。
  - 讀耗時表:檔案不存在 → 照名字輪流分,印一行「沒有耗時表,照名字輪流分」(消費專案就是這條)。檔案存在但讀不進或不是上面的格式(不是一般檔、不是物件、`tests` 不是物件、秒數不是非負有限數字、`tests` 是空的)→ 每一份都以 rc 2 擋下並說明哪裡不對;因為同一個提交的每一份讀到的是同一個檔,所以每一份會得出同一個結論,不會一份退回、一份照表分。
  - 分法:每支測試的權重 = 表裡的秒數,表裡沒有的用全表中位數;權重下限 0.05 秒(避免一堆 0 秒的測試全擠進同一份)。權重由大到小、同權重照名字排序,逐支丟給「總權重最小」的那一份,同總權重取「已分到支數最少」的,再相同取編號最小的。同一份表、同一份測試清單,每一份算出來的分法完全一樣,各份聯集等於全部、沒有重複。
  - 每一份印一行「分法:耗時表 <表的 SHA-256 前 8 碼>,共 <總支數> 支,這份分到 <支數> 支」,事後核對各份是不是讀到同一份表。
  - 每一份跑完再讀一次耗時表,雜湊跟開頭不同(被刪、被改、從無到有)就以 rc 2 擋下:各份同時啟動、各跑幾分鐘,有人在各份啟動之間換表時,先啟動的那份結尾一定讀到新表。
  - 片數比測試多時照樣會有空片,空片照舊擋下;分法只算到測試數那麼多份,不照片數配置;帶 `--suite`(只跑文件子集或關鍵字子集)時,子集比片數少造成的空片照舊算過。
- **取消過期 CI**:`ci.yml` 加 `concurrency`:群組鍵 PR 事件用 PR 編號(`github.event.pull_request.number`,不用分支名,避免不同來源的同名分支互相取消)、推到 main 用提交編號(`github.sha`,每個提交各自一組,所以排隊中的主線 CI 不會被後來的推送取代);`cancel-in-progress` 只對 PR 事件為真。被取消的舊 run 結論是 cancelled;`lumos ci-wait` 等的是目前頂端提交的 run,舊提交被取消不影響它的判定。
- **CI 印每份耗時**:shards 工作在每一份的日誌開頭印開始時間、結尾印「第 i 份耗時 N 秒」;測試紅了也要印,所以那個子殼層先 `set +e`(Actions 預設 bash -e 會在測試紅時直接結束子殼層)。

## 驗收條款

- [S1] 當耗時表存在且格式正確時(以下測試與子指令都是這篇新增),`--shard i/n` 應 依權重由大到小分給總權重最小的那一份(同總權重取支數少的、再取編號小的),權重下限 0.05 秒、表裡沒有的用全表中位數;各份聯集 應 等於全部且不重複,而且每份的總權重 應 比照名字輪流分時更接近;每一份 應 印出表的 SHA-256 前 8 碼與總支數 [test:t_runner_shard_by_duration]
- [S2] 當耗時表不存在時 應 照名字輪流分並印一行說明;當耗時表存在但格式不對(不是物件、`tests` 不是物件或是空的、秒數不是非負有限數字)時 每一份 應 以 rc 2 擋下並說明;片數比測試多時 應 照舊有空片並擋下,帶 `--suite` 的子集空片 應 照舊算過 [test:t_runner_shard_by_duration]
- [S3] 當測試跑完時(過、紅、逾時、例外都算,跳過的不算),執行器 應 在來源 repo 的 `.lumos/test-durations-run*.json` 記下各支秒數;`lumos test-durations refresh` 應 取每支最新的一筆寫回 `governance/test-durations.json`、沒跑到的保留舊值、讀完刪掉 run 檔 [test:t_test_durations_refresh]
- [S4] 當 `ci.yml` 被讀時,應 有 `concurrency`:PR 事件以 PR 編號分組且取消進行中的工作,推到 main 以提交編號分組且不取消;shards 工作 應 印出每一份的耗時 [test:t_ci_yml_speed_shape]
- [S5] 當只改 `governance/test-durations.json` 時,代碼審留痕 應 不失效(它在簿記檔清單裡) [test:t_test_durations_refresh] [test:t_codeloop_pass_survives_bookkeeping_commits]
- [S6] 當一份跑的期間耗時表被換掉(被刪、被改、從無到有)時,那一份 應 以 rc 2 擋下;表沒換 應 照常 [test:t_test_durations_refresh]

## 實務隱患

- 已排除:金流:只動測試分片與 CI 觸發,不碰任何付款或計費。
- 已排除:對外送出:不寄信、不發通知,也不新增任何對外呼叫。
- 已排除:不可逆:耗時表與 CI 設定都能直接還原,不改資料也不刪東西。
- 已排除:守衛面:不少跑任何測試(各份聯集等於全部由分法本身保證,表錯只會不平均),主線每個提交照舊跑全套與後盾;取消只作用在同一個 PR 被新推送取代的舊工作。
- 耗時表過期或量自 macOS:新測試以中位數計、刪掉的測試忽略,最壞是分得不平均,不會漏跑。
- 本機推送前四份同時跑時,若耗時表在跑的當下被改(切分支、rebase),各份可能讀到不同的表、聯集不再等於全部;所以每一份跑完再讀一次表,跟開頭不同就擋下([S6])。只在依序手動跑各份、中間換表時擋不到(那時沒有哪一份跨過換表那一刻),推送前掛鉤與 CI 都是同時啟動,不會這樣跑。
- 併發:取消只作用在同一個 PR 的舊工作;主線每個提交各自一組,不會被取代。
