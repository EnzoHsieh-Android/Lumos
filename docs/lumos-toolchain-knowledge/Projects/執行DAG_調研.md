# 執行DAG_調研

> 白話:有人建議 Lumos 再長第二張圖——知識圖譜管「為什麼」,執行圖管「做到哪」。
> 查完的結論是:**方向對,但起點錯**。這裡不缺執行記憶,已經有三套;缺的是
> 「狀態不用人維護也會對」。手維護的執行狀態在這個 repo 已經爛過四次,有數可數。

PRIOR-ART:①最小解在既有機制層——「唯一下一動作」的神諭已經有了(`lumos loop next`,只讀帳本結構不讀散文),只差一個「列出現在開著的迴圈」的入口;結構化逐條進度清單也已有自家前例(見下「兩個可抄的前例」);原子認領+租約原語同樣現成(`dispatch-lens --arm/--claim`,10 分 TTL)。②世界解過——五條路線見下,但★沒有任何一條給出對照組數據★,「任務 DAG 對 coding agent 有用」目前是共識不是證據。③不採用新依賴(零依賴家規):beads 需要一個可版控的 SQL 資料庫,Task Master/Backlog.md 是 npm 生態,三者皆出局為「可借形狀、不借實作」。

## 這篇在調研什麼

外部評論(GPT,2026-09-07 Enzo 帶進來)主張:Lumos 已有知識/證據/決策/風險/審查五種記憶,**唯獨缺執行記憶**,建議建立獨立的 Execution DAG,用 reference 與知識圖譜串接,第一版做一份任務狀態檔加八個 CLI 指令(add/list/show/ready/claim/complete/fail/graph)。

本篇是對這份主張的查證與裁定。

## 外部評論哪裡對、哪裡錯

**對的兩點(不改)**

- **兩張圖不該揉成一張**:知識節點是長期的,任務是會大量產生又消失的。生命週期不同,分開是對的。
- **任務只存指標、不存內容**:這點**這裡已經是這樣做了**(`plan_refs`/`related`/DEP 行指回權威節點,不重抄)。它不是建議,是現況描述。

**錯的一點(事實錯誤)**

- **「Lumos 缺執行記憶」不成立**。現況有三套:
  1. **實作計畫筆記的任務拆解**——T1..Tn、「包①→②→③嚴格順序」、每任務寫明改哪/測什麼/斷言什麼,底下「進度」段記日期與教訓。
  2. **節點狀態欄 + `lumos query --active`**——列得出所有自稱在飛的東西。
  3. **自主迴圈的待辦帳**(`governance/backlog.jsonl`,185 筆)——有價值分、每日衰減、已涵蓋永久排除、熔斷、「同時只准一件在飛」。

**最危險的一點(這是本篇的核心)**

- **它建議第一版就開一份新的、要人手維護的任務狀態檔**。這正是本 repo 已經爛過四次的那一型東西。詳見下節數字。

**★自家前例:一個真的可抄,一個是反證(外家 f3 翻轉)★**

1. **只讀結構不讀散文的進度指令**:`lumos loop verify-progress` 的 help 自述「不看散文,只從帳本結構欄位看審到哪了(防被報告措辭帶風向)」;`lumos loop next` 更直接——**吐出唯一的下一動作**(現在什麼狀態/第幾輪/派幾席/上限幾輪)。這就是 DAG 想要的東西,已經在跑。
2. **★結構化逐條進度清單——原稿當成正面前例,外家查證後翻成反證★**:`.lumos/settle/公開精簡版-settle.json`,35 條,每條 `{id, kind, claim, status, spec_sha, note}`,狀態分佈 `unverified 15 / mech-ok 11 / llm-ok 9`,全 repo 只此一份。
   - **它現在是死的**:外家實跑該閘,**35/35 全判 `spec_sha 過期`**,另有 G1、G3 失敗;[[Projects/結清式收斂_計劃]] 還留著首輪 dogfood 三項未完成;現行 design-loop 已改走 `--disposal`,settle 只剩 opt-in legacy。
   - **腐化機制我自己驗了**:★35 條的 `note` 全部寫著「重蓋 sha」★——spec 一改版,就由人逐條確認「本條沒受影響」再手動蓋一次雜湊。**手維護了 35 次,最後還是沒結清。**
   - ★所以它證明的是相反的事★:**結構化不等於不腐化**。schema 可以抄,維護模型**絕對不能抄**——照抄就是把方案 B 剛否決掉的「人維護狀態」原樣搬回來。

**認領原語:可借的比原稿說的少很多(外家 f4)**。原稿寫「原語已現成,到時接上即可」——**這句要撤**。`dispatch-lens --arm/--claim` 深度綁死代碼審場景:
- `--arm` 得先算 git diff 範圍的派工鏡頭;metadata 固定存 range/base/head;`N` 是**審查席數**不是任務 id 集合。
- TTL 寫死 600 秒(`_LENS_ARM_TTL_SEC`),無 CLI/設定可調;狀態放使用者快取目錄。
- token 領完即刪整個目錄、過期也整夾刪;**沒有續租、完成、失敗、釋放、持久歷史、重派**。
- token 不分收件人——程式註解自己承認同 repo 的無關子代理會搶走席位。
★能借的只有「用 `os.rename` 原子搶 token」那十幾行的**概念**,不是一個現成的任務租約★。把認領層當低成本接線,會把 B/C 的估價算得太低。

## 缺口重新定義

不是「沒有執行記憶」,是三件事:

- **(a) 執行狀態靠人維護 → 必然腐化**。四個數字見上。
- **(b) 依賴只活在散文裡 → 機器算不出「現在可以開工的是哪些」**。零依賴欄位,機械驗過。
- **(c) 沒有跨 session 互斥**。[[Issues/同工作區多session並行改動]] 已立案:一天撞三次、兩次有實害,原話「四層閘沒有一層的輸入裡有 session 這個維度」。★該案已裁不做誤報量測,故 (c) 的嚴重程度給不出數字,只有三次實例。★

## 三個方案與裁定

**方案 A:不建第二張圖,把「現在可以做什麼」從既有狀態算出來**(Dagster 模型)
- 聚合既有隊列:doctor 六張機械待辦(4 篇沒被 L4 審計/10 篇 about_code 過期/5 份驗證引用已翻案決策/1 張連鎖單零判定/1 件 REVISIT 到期/1 個數字宣稱對不上)、rel-cascade 未判、decision-refs backlog、stale 到期、backlog.jsonl 高分項。
- ★實得比直覺少★:`spec-trace`(條款級追溯)在本 repo **實測幾乎沒餵資料**(三篇實跑:6/6 無人認領、8/8 無人認領、1 篇「opt-in 未啟用」)——**那不是「沒有待辦」,是「沒人填格式」**,聚合它只會得到雜訊。
- 只解 (a),不解 (b)。

**方案 B:最小 DAG,只做在「有客觀判準」的範圍**(★原稿的地基被外家打穿兩個洞,以下是修正後版本★)
- 只結構化實作計畫的任務拆解 + [[Projects/全repo審視_計劃]] 的 50 群主清單——那是 repo 裡唯一真有依賴、有分包、有嚴格順序的地方。
- 原始關鍵設計:**任務完成狀態不准由人勾,要由證據算**;任務已寫明對應的測試函式名 → 「做完了沒」＝「那個測試存在且綠」。

**★洞一:覆蓋率只有四分之三,而且缺口是天生的(外家 f1;兩造獨立數,結果一致)★**
- 本家數 56/74 個任務段(75%)、外家數 62/83(74.7%)——★切法不同、數字幾乎一樣,這條可信★。
- 缺的不是漏填:Android 真機驗收、skill 散文改寫、圖譜回填這幾類**本來就沒有一個 Python 測試函式能代表完成**。
- 更糟:`關係層主網_實作計畫` 用別種標題寫法,機械切分得到 **0 個任務**——★連「任務」怎麼寫都沒有統一格式★。

**★洞二:「測試存在且綠」根本推不出「任務完成」(外家 f2,這是最致命的一條)★**
- 多個任務共用同一個測試函式:`code側刪除傳播守衛_實作計畫` 的 Task 1–5 全部往同一個 `t_delguard()` 裡「續加」斷言(★本家開檔驗過★)。那個測試綠,分不出 Task 2 還是 Task 5 做完了。
- 有些任務段只寫「跑全套」,不指名函式。
- **既有測試在任務開工前就可能已經綠**——只檢查「存在且綠」會直接判成完成。
- ★後果★:機器會產出**假完成狀態**,正好蓋掉這份調研想解的那個缺口。這比沒有 DAG 更糟。

**所以 B 要能成立,得先定義四件事(外家開的清單,本家接受)**:①哪幾類任務有資格進 DAG;②沒有測試函式的任務,客觀完成證據是什麼(commit trailer?diff 觸及檔?回指的 Verification 節點?);③任務切分的統一 schema;④一個測試對多個任務時怎麼防假完成。
- **形狀不要照 settle JSON 抄**(見上,那份是反證);要抄的是 `loop verify-progress` 那種「狀態從帳本結構重算」的模型。

**方案 C:外部評論原案(完整第二張圖 + claim/complete + 多 agent 認領)**
- 平行度現況:design-loop 的多席子代理(同 session 內、編排者派工,且 Claude Code 的 Workflow 工具本身已提供平行/管線語意)+ 偶爾兩個 session。
- ★外家 f5 修正:C 不該整包裁,要拆★——[[Issues/同工作區多session並行改動]] 記載的一天三次碰撞、兩次有實害,**已經是「兩個執行者爭用同一工作面」的真實需求,不必等更多 agent**。可延後的是任務 DAG 與 complete/fail;該獨立評估的是 session 級的範圍宣告/檔案歸屬/工作樹隔離。
- 認領層**不是低成本接線**(見上 dispatch-lens 那段),估價要重算。

**★第四類:三條「不建任何新圖」的路,原稿漏列(外家 f5/f7)★**
- **git worktree 隔離**:直接消滅「共用同一棵工作樹」這個根因,不需要第二張圖。代價已記在來源 Issue(兩邊看不到對方的即時改動,而那個 repo 自陳「看得到」有時反而有用)。
- **commit trailer / session manifest**:解「提交夾帶、歸屬讀不出來」,成本極低。
- **在既有 typed-edge 模型加一個 task-prerequisite 型別**:不另建儲存層,直接長在現有的邊模型上。
- ★這三條都比完整 C 小、又比「先不做」更對症;A/B/C 的選單原本把它們漏掉了。★

## ★成敗條件(若只記一句,記這句)★

**任何新的任務狀態,只要「不能從證據重算」,就不要做。**

不是偏好,是本 repo 自己量出來的規律(四個腐化數字),且有外部佐證——[[Issues/散文紀律沒有退場機制]] 記的 TDAD(arXiv 2603.17973):AI 改壞既有測試的比率,什麼都不加 6.08%、**只加一段「請照測試先行做」的程序散文惡化到 9.94%**、給機械算好的該跑清單降到 1.82%。

翻成本案:**一張機器算出來的執行圖會有用;一張要人手維護的執行圖,很可能比沒有更糟。**
