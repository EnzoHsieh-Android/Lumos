# 選擇點變異加速第二段_計劃

## 白話

[[Projects/選擇點變異加速_計劃]] 上線後(合併快篩:每個壞法先把守的測試合成一次 Gradle 呼叫),實驗專案 11-24、11-25 兩次實測還是每個壞法約 4.6–5.4 分鐘,照這個速度 225 行約 17–20 小時。2026-11-25 帶紀錄重跑一次,看到時間花在三個地方,都跟合併呼叫本身無關:

1. **被殺的壞法白跑幾十次單支。** 合併呼叫已經知道哪幾支紅了(結果檔裡寫著),但規矩是「合併不判殺掉、照逐支流程從頭跑」,逐支流程照守的測試排序一支一支跑到第一支紅才停。實測四個被殺的壞法,合併之後又逐支跑了 19、19、72、96 次(64–391 秒);照合併結果先跑紅的那支,每個只要 1 次(約 5 秒)。
2. **只跑一個壞法時根本不合併。** 「這次壞法少於 2 個不合併」那條,讓 `--only` 單點重跑的存活壞法逐支跑完 169 支、約 30 分鐘;合併呼叫 16–18 秒就判得完。
3. **時限不夠量齊就靜默不合併。** 合併前的時限門要「剩下的總時限 ≥ 支數 × 10 秒 × 1.5」:169 支要 2535 秒,預設 `--max-seconds` 1800 秒,所以照預設旗標跑時 169 支的專案整次都不合併,而且一個字都不印。

這份改四件事:逐支流程先跑合併結果裡紅的測試(判法規則不變,只改順序;判定可能在殺掉與跑不出結果之間換,見〈實務隱患〉);一個壞法也合併;合併沒開時每次都印一行講原因(時限不夠時講要帶多大的 `--max-seconds`)並記帳;快篩沒跑乾淨的原因印出來並記帳(11-25 凌晨斷路器跳開過一次,原因沒記下來、事後查不出)。好比找漏水的水管:總閥測出整條有漏(合併呼叫),現在是從第一節開始一節一節拆,改成先拆壓力表顯示會漏的那幾節。

WHY:合併快篩結果是「有失敗」時,逐支流程照原本守的測試排序,先跑合併結果裡失敗或錯誤的那幾支,再跑其餘;誰殺掉仍由單支結果判;判定可能在殺掉與跑不出結果之間換,不會變成存活 [出處:2026-11-25 使用者裁「照調研方向先處理好工具的這一段」「優先處理速度」;實驗專案帶紀錄實跑] [因:被殺的壞法成本大頭在逐支依序找第一支紅的(實測 19–96 次);合併結果已經指出哪幾支紅,先跑它們通常一次就殺掉;判定照舊由逐支單支結果決定,不違反「合併不判殺掉」] [不選:合併直接判殺掉(第一版設計審兩輪 24 條卡在歸因與作廢,使用者 2026-11-23 否決,見〈舊否決比對〉);用結果檔歸因到哪一支記成殺掉(同上)] [代價:合併時測試互相影響、單支卻不紅的那幾支會多跑一次才回到原順序;殺掉它的測試可能跟 `--no-merge` 記的不是同一支,那行紀錄何時因條款改綁而過期也跟著不同;原順序前面那支會逾時而名單裡那支會殺掉時,判定從跑不出結果變成殺掉,反過來也可能(見〈實務隱患〉)] [test:t_choice_kill_merge_failed_first]
WHY:一個壞法也合併(拿掉「這次壞法少於 2 個不合併」) [出處:2026-11-25 實驗專案:`--only` 單點三次各 1652–1964 秒,逐支 169 支;同一個壞法合併呼叫 16–18 秒] [因:原理由「單一壞法量齊基準只會更慢」只在被殺的壞法成立(第一支就紅);存活的單一壞法逐支要付 169 次呼叫,量齊基準(約 169 × 4.5 秒)加一次合併仍少一半以上;被殺的單一壞法照新順序只多一次合併呼叫] [代價:被殺得快的單一壞法多付量齊基準約 12 分鐘(原本用到才量)] [test:t_choice_kill_merge_single_mutant]
WHY:快篩沒跑乾淨時,把斷路器計數的原因(`_choice_merge_classify` 的「逾時」「被系統收掉」「找不到 JUnit 結果檔」「結果檔讀不出來」「結果檔超過大小上限」五個字串)分平台計數記進 run 事件、斷路器跳開那行印出最後一次的原因 [出處:2026-11-25 查 11-25 02:54 那次斷路器跳開,治理帳只有 merge_tripped 真,原因沒記;重跑 5 次合併都乾淨,重現不出] [因:這幾種原因修法完全不同,不記就只能猜] [test:t_choice_kill_merge_unclean_reasons]
WHY:一個平台組這次不合併時,把固定種類的原因記進 run 事件並印一行(例外:合併基準不乾淨沿用既有那行字樣、不另印;中斷與時限到只記不印,接著就停);時限不夠時講要帶多大的 `--max-seconds` [出處:2026-11-25 設計審前掃:預設 1800 秒對 169 支(要 2535 秒)整次靜默不合併;設計審 r1 邊界席:指令過長、名稱檢查、flaky 等四條路同樣靜默] [因:靜默退回逐支讓人以為合併沒效;不改預設是因為預設時限也管對話裡的單次呼叫不被逾時砍] [不選:把預設 --max-seconds 調大(對話裡跑會被工具逾時砍掉)] [test:t_choice_kill_merge_budget_hint]

PRIOR-ART: ①PIT:被殺的壞法跑到第一支殺掉它的測試就停,而且先跑最可能殺掉它的測試(依覆蓋與執行時間排序)(https://pitest.org/faq/ ;作者的設計說明 https://github.com/nickmoone/Pitest-Reactor/blob/master/so_you_want_to_build_mutation_testing_system.md)。②Zhang、Marinov、Khurshid〈Faster Mutation Testing Inspired by Test Prioritization and Reduction〉ISSTA 2013:成本以「壞法 × 測試」配對數計,把殺得掉的測試排前面(https://personal.utdallas.edu/~lxz144130/publications/issta2013a.pdf)。③Just 等 ISSRE 2012:依執行時間與覆蓋排序加非冗餘算子,總成本最多少約 65%(https://homes.cs.washington.edu/~rjust/publ/mutation_test_prio_issre_2012.pdf)。採用:①②的「先跑最可能殺掉的」,用合併結果當排序依據(比覆蓋更直接:它就是這個壞法實際讓誰紅)。排除:mutant schemata(一次編譯包全部壞法),Android 實測只快約 6%(METFORD https://arxiv.org/html/2501.02875v2),成本不在編譯。

## 用詞

- **強殺掉、停**:照逐支流程現在的停止集合 `_CHOICE_STOP_ON`(killed、compile_error、timed_out_weak):單支結果是其中之一,同組其餘配方略過;帶弱證據的殺掉(killed_weak、killed_unattributed)不停、照跑下一支。條款裡「單支沒紅」指結果不在停止集合內。
- **合併失敗名單**:一次合併快篩結果是〈用詞〉「有失敗」時,合併道裡的測試名 m,只要結果檔裡有任何一筆狀態是 `failure` 或 `error` 的案例,它的完整名([[Projects/選擇點變異加速_計劃]]〈用詞〉)等於 m 或以「`.` 加 m」結尾,m 就列進名單;不要求恰好一筆(參數化測試多個參數失敗、合併道裡 `foo` 與 `A.foo` 並存都照列)。名單只拿來排順序、不判任何事,所以從寬。
- **先紅順序**:這個壞法的配方照原本守的測試排序,名單裡的排前面(彼此維持原排序),其餘接在後面(維持原排序)。

## 做法

### 1. 有失敗時先跑紅的

- 名單在 `_choice_merge_classify` 的「有失敗」分支從它已經讀到的 facts 算(不另讀檔);classify 多收一個選用參數(要不要算名單),回傳形狀不變:名單交給呼叫端放的地方,照既有 `c.sh` 的做法掛在平台現場物件上(`c.merge_failed`,每個壞法開快篩前清空),不另開回傳通道。
- `_kill_merge_screen` 回 "single" 時名單已在 `c.merge_failed`;重排在 `_kill_merge_iter` 交出配方那一步做(現在是 `yield from chunk` 原順序交出),照先紅順序重排這個壞法的配方再交;逐支流程本體不改(停止規則照〈用詞〉)。逐支迴圈只依交出的順序跑,下游(`on_row` 以配方身分對回、`finish` 計數、`tests_sha`)不依賴順序。
- 名單為空、或結果不是「有失敗」(編不過、沒跑乾淨)時照原順序。
- 殺掉它的測試照逐支流程記(先紅順序的第一支強殺掉的那支)。
- **每個壞法記兩個欄位**(choice-kill 事件,`_choice_event_extra` 那一組):`merge_kind` 是字典 {平台: pass|fail|compile|unclean|none}(none=這個平台組這個壞法沒跑快篩),`single_runs` 是整數(這個壞法在壞法階段逐支呼叫了幾次,開頭量基準不算)。型別登記進 `_GOV_FIELD_TYPES`(`(dict,)`、`(int,)`)並加進 `ck` 子字典鍵清單;讀帳時缺的當 none 與 0。用途:RETIRE-IF ①④ 與 S6 量得到。

### 2. 一個壞法也合併

- `_kill_merge_ready` 拿掉 `mg.n_mutants < 2`;其餘條件(時限夠量齊、名稱檢查、flaky、筆記未提交、指令長度、結果資料夾圍欄)不變。
- `_KillMerge` 拿掉 `n_mutants` 參數(不再當合併條件、別處不讀;既有測試的建構呼叫一起改;代碼審 r1 g3)。
- 合併道少於 2 支(`_kill_merge_base` 的 `len(lane) < 2`)照舊不合併:守的測試只有 1 支時合併沒有可省的。守的不同名字不到 2 支在 `_kill_merge_ready` 時限門之前就判(記 `合併道不足 2 支`;不然會提示調大時限、照做仍不合併;代碼審 r1 b1)。

### 3. 合併沒開時講出來、記下來

- `_kill_merge_ready` 的檢查順序改成時限門排最後(名稱檢查、flaky、筆記未提交、`_secev_tq()`、結果資料夾圍欄、指令長度都先判,這幾道都只算字串與路徑),所以時限門擋下時,其他條件都已經成立,照提示帶大時限就會合併。
- 一個平台組這次不合併時,原因只記在既有的 `_KillMerge.plats`:`plats[平台] = (False, 原因)`(啟用的是 `(True, "")`;不另開一份字典,代碼審 r1 a1),原因只用這幾種固定字串:`指令形狀不支援`(`_choice_merge_shape` 回 None)、`時限不夠`、`名稱檢查沒過`、`平台不穩或筆記未提交`、`指令過長`、`結果資料夾不在工作樹`、`讀結果檔的模組不在`、`基準量不齊`(`_kill_merge_singles` 重估收手)、`合併道不足 2 支`、`合併基準:<原因>`(原因是 `_choice_merge_classify` 對合併基準回的字串:逾時、被系統收掉、找不到 JUnit 結果檔、結果檔讀不出來、結果檔超過大小上限、有失敗、編不過、rc 不是 0,以及「N 支對不到結果檔裡的名字」一律記成「對不到名字」;不經 `_CHOICE_MERGE_BASE_WHY` 換字,那張表只管印字)、`中斷`(量基準途中收到訊號,模組常數 `_CHOICE_MERGE_HALT_SIGNAL`)、`時限到`(量基準途中總時限用完、沒收到訊號;代碼審 r2 e1;模組常數 `_CHOICE_MERGE_HALT_DEADLINE`);斷路器跳開記 `斷路器`(模組常數 `_CHOICE_MERGE_TRIPPED`,另有 `merge_tripped`)。量完單支基準後要記 `基準量不齊` 或 `合併道不足 2 支` 之前先看停止旗標,已停就改記 `中斷` 或 `時限到`(代碼審 r3 b1)。分中斷與時限到靠 `_KillMerge.interrupted`,由訊號處理器的第一個訊號回呼設;choice-kill 建訊號處理時就把回呼交進去,處理器裝上之前就在,沒有漏設的空窗(代碼審 r3 c1)。run 事件的 `merge_off` 由 `plats` 算出:沒啟用、而且原因不是 `斷路器` 的平台組。
- 印字:每個不合併的平台組印一行到標準錯誤,照既有格式 `⚠ {_kill_esc(平台)}:這次不合併({原因}),照逐支跑`(合併基準不乾淨那行既有字樣照留、不重複印;`中斷` 與 `時限到` 只記不印,接著就停,「照逐支跑」不成立。印不印由呼叫端傳參數決定,不看原因字串;代碼審 r1 a2)。原因是 `時限不夠` 時同一行接「;合併要先量齊 N 支基準,約需 M 秒,剩 R 秒;要合併請帶 --max-seconds X」:M = 支數 × 10 × 1.5;R = max(剩下的總時限, 0) 取整數;X = (這次呼叫從 `t0` 到現在已花的秒數 + M + 60) 無條件進位到百。`基準量不齊` 時 N 是全部支數、M 用已量的實測平均乘全部支數乘 1.5(帶大時限重跑是新的一次呼叫,基準要從頭全部量;代碼審 r1 g3)、同樣給 X。
- 不改預設 `--max-seconds`。前一份計劃〈做法〉1「條件不合不印字」與〈做法〉5〈印字〉那兩句、`_kill_merge_ready` 的 docstring「不印字」同一提交改掉(見〈落點〉)。

### 4. 快篩沒跑乾淨的原因記下來

- `_KillMerge` 多 `unclean`(字典 {平台: {原因: 次數}})與 `last_unclean`(字典 {平台: 原因})。`_kill_merge_breaker` 多收一個原因參數(`_kill_merge_screen` 不再丟掉 classify 的原因),只在計斷路器的那幾種時加一並記最後一次;鍵直接用 `_choice_merge_classify` 現有的字串(「逾時」「被系統收掉」「找不到 JUnit 結果檔」「結果檔讀不出來」「結果檔超過大小上限」),不另折一份對照。這幾種都不帶數字,鍵數有上限。
- 斷路器跳開那行改成「⚠ {平台}:合併連續 5 次沒跑乾淨(最後一次:{last_unclean[平台]}),這次剩下的改逐支」。`unclean` 是累計、斷路器看連續,兩者不同步是預期的。
- run 事件多 `merge_unclean`(上面那個兩層字典;沒有就空字典)與 `merge_off`(〈做法〉3 由 `plats` 算出的字典;沒有就空字典):型別登記進 `_GOV_FIELD_TYPES`(都是 `(dict,)`),並加進 `_gov_row` 的 choice-kill `ck` 子字典鍵清單;讀舊帳缺欄時當空字典。

## 回退

- 先關不還原:`LUMOS_SKIP_CHOICE_MERGE=1` 或 `--no-merge`,合併整個不開、逐支照原順序(先紅順序與一個壞法也合併跟著失效);使用者自己關掉的不算〈做法〉3 的「不合併」,不印、不記 `merge_off`。
- 只想關「先跑紅的」:沒有單獨開關;還原功能提交。帳上已記的紀錄照舊有效(都是單支跑出來的判定);跟 `--no-merge` 比,少數壞法的判定可能是殺掉對跑不出結果、殺掉它的測試也可能不同,要對齊就照 [[Projects/選擇點變異加速_計劃]]〈回退〉用 `--no-merge --only` 逐行重判。

## 實務隱患

- 判定可能跟 `--no-merge` 不同,只在殺掉與跑不出結果之間:停止集合裡逾時(timed_out_weak)與殺掉是先遇到誰就停在誰,順序一改,原順序前面那支會逾時、名單裡那支會殺掉的壞法,從跑不出結果變成殺掉;名單裡那支單支逾時、原順序前面那支會殺掉的,從殺掉變成跑不出結果。兩個方向都不會記成存活,推送閘不會因此放行壞程式:跑不出結果推送閘照擋、下次重跑。PIT 與 Stryker 都把逾時算成已偵測(https://pitest.org/faq 、https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/),本工具照舊算跑不出結果,不改。逾時變多由 RETIRE-IF ④ 盯。
- 殺掉它的測試跟 `--no-merge` 不同,紀錄過期的時機也不同:`_choice_disposition` 判有效處置要 `killing_test` 還綁在進行中的計劃上,不在就判過期要重跑。先紅順序記的是名單裡那支,`--no-merge` 記的是原順序第一支;之後只有其中一支被改綁或拿掉時,兩種跑法的那行紀錄一個有效、一個過期。過期只會多要求重跑,不會放行。
- 名單從寬(〈用詞〉):多列的只會多跑一次就回到原順序,不影響判定。
- 跑太久:一個壞法也合併,被殺得快的單點重跑多付量齊基準(約 169 × 4.5 秒,補測試後重跑最常見的就是這種);時限不夠量齊照舊不合併並印原因;由 RETIRE-IF ③ 盯。
- 已排除:金流:只在本機跑測試,不碰付款
- 已排除:對外送出:不連網、不寄送
- 已排除:不可逆:只在暫時工作樹裡改檔,治理帳只追加
- 併發與交易:同 [[Projects/選擇點變異加速_計劃]],一次呼叫一棵工作樹一條執行緒
