# 測試品質部署配套校驗_計劃

## 問題與最小解

推送前第二輪已重現：新 CLI 配上舊 sidecar（隨 lumos 一起安裝的三支測試品質輔助檔 test_quality.py、test_quality_scan.py、test_quality_semgrep.py）可把矛盾 JUnit 收成成功；即使來源更新，時間戳與大小相同的舊 bytecode 仍能回到舊判讀。只查檔案存在不足以確認實際執行配套。

PRIOR-ART: 沿既有工具檔指紋函式 `_vendored_digest`（換行統一成 LF 再算 SHA-256），載入改用 `spec_from_file_location` 建模組後直接 exec 已驗 bytes——既有 `_handoff_load_hook` 走 `exec_module`、會從磁碟重讀並可能用舊 bytecode，做不到「驗過的就是執行的」，所以這裡另寫；安裝檔內容校驗的成熟先例為 https://packaging.python.org/en/latest/specifications/recording-installed-packages/ 。不新增依賴、不重建安裝器、不宣稱簽章或安全沙盒。

為什麼另立 `_TEST_QUALITY_BUNDLE_DIGESTS`，不沿用安裝時寫的 `.lumos/vendored.json`：那份記的是「安裝當下檔案長怎樣」，混裝時會連混裝內容一起記進去，回答不了「這三支 sidecar 跟這支 CLI 是不是同一版」；來源 repo 與全域 symlink 也沒有那份清單。兩者分工：vendored.json 判「安裝後有沒有被改過」，指紋表判「CLI 與 sidecar 是否配套」。
RETIRE-IF: 安裝入口不再逐檔複製（`_vendor_toolchain` 的 copy2 被一次換整組、帶版本的配套取代），且混裝與 stale-bytecode 反例改由該入口擋下時，撤除入口專用配套指紋 [retire:人裁] [until:2027-04-09]。

## 做法與驗收

CLI 綁定三支 sidecar 的內容指紋；每支只收一般檔案（FIFO、裝置檔直接判不完整，免得讀檔卡住每個指令），先讀最多 10 MiB 的 bytes，全部對上才從同一批 bytes 載入。載入順序固定為依賴順序 `_TEST_QUALITY_LOAD_ORDER`（共用 runner 最先），因為 Semgrep 轉接器頂層 import 共用 runner；被依賴者若還沒從已驗 bytes 登記，標準 import 會從磁碟另載一份、吃舊 bytecode。載入後再逐一核對每支 sidecar 引用的配套物件都是已驗那份，對不上即判不完整，往後新增依賴或改順序也擋得住。模組名稱與標準 import 相同；載入時任何例外都回復該次修改的模組登記，只讓 test-quality 回部署不完整，不拖垮其他指令。這只證版本配套一致，業務 oracle 與報告真實性仍由呼叫者負責。

配套在 `main()` 開頭載入（parser 建立前就要知道配套完不完整，所以三支都在這時載入；只部分延後載入會重新打開混裝的口子）。部署錯誤留在 parser 建立期，不另解析 argv。完整配套註冊既有子命令；不完整配套註冊不 import sidecar 的佔位入口。正式 argparse 解析後只對 test-quality 回結構化錯誤（含 `test-quality -h`）；其他指令照既有流程。子指令前就放其他選項（例 `test-quality --json scan`）屬 argparse 用法錯誤，不在結構化保證內。報告裡的 `source_sha256`、`adapter_source_sha256` 是執行期重讀磁碟算的原始 SHA-256，不等於配套校驗結果。

改或新增 sidecar 時要同步五處：`_VENDORED_TOOLKIT`、`_TEST_QUALITY_BUNDLE_DIGESTS`（重算指紋）、`_TEST_QUALITY_LOAD_ORDER`、兩支 git 掛鉤的工具檔豁免清單，以及指令說明與文件指令數；新檔名必須以 `test_quality` 開頭才會被要求與校驗。

- [S1] 當 test-quality 配套缺檔、混裝或來源不可讀時，CLI 應在執行收證命令前回退出2及 complete:false、not_assessed 的 JSON，提供更新指引。 [manual:跑 `python3.14 scripts/test_test_quality_cli.py`，看 test_partial_sidecar_returns_structured_invalid、test_missing_all_sidecars_explains_update、test_mixed_sidecars_refused_before_false_green、test_fifo_sidecar_does_not_hang_other_commands、test_sidecar_runtime_error_only_blocks_test_quality、test_incomplete_bundle_short_help_is_structured 全綠]
- [S2] 當來源 bytes 合格而存在同時間戳同大小的舊 bytecode 時，CLI 應執行已驗 bytes 的判讀；完整正常配套的 scan、capture、check、capabilities 行為仍成立。 [manual:跑同一檔的 test_source_bytes_not_stale_bytecode_authorize_capture（capture 路徑）與 test_semgrep_adapter_uses_verified_runner_not_stale_bytecode（scan --semgrep 路徑）全綠]
- [S3] 當使用合法頂層 --vault 選項時，test-quality 部署錯誤應和直接形式同樣結構化；部署不完整亦不妨礙既有 --help、--version 入口。 [manual:跑同一檔的 test_global_vault_option_retains_structured_deployment_error（`lumos --vault X test-quality …` 排列）與 test_missing_quality_sidecar_does_not_break_legacy_help 全綠]

## 回退

回退本次入口校驗與必要控制即可回到上一版；不改動既有 push/CI 判閘及原生歷史卷證。不能把回退後混裝可能假綠的版本冒稱本計劃通過版。

## 實務隱患

已排除:金流:無正式資料或支付服務。
已排除:對外送出:模組只載入本機已配套的工具來源，反例用 fake 命令。
已排除:不可逆:不刪檔、不更新安裝來源、不修改歷史卷證。
已排除:守衛面:不調整 code-loop、CI、風險分級或審查輪數；不把一致性判定升格成測試品質放行。

併發：`lumos update` 逐檔複製期間，同時啟動的 lumos 可能看到新舊混裝而回「配套版本不一致」，屬預期的暫時拒絕（fail-closed，更新完成即恢復），不會假綠。
效能：每次啟動多讀三支檔、算 SHA-256 並 exec，約 8 ms，`lumos --version` 量不出差異。
資源：每檔上限 10 MiB，三支合計最多約 30 MiB，讀完即釋放。
