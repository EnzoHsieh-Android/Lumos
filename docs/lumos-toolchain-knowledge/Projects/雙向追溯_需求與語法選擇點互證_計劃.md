# 雙向追溯_需求與語法選擇點互證_計劃

> 狀態:構思草稿(2026-11-13 沉澱,還沒走規格閘與設計審)。動工前先讀〈待驗〉那節的 PIT 實驗結果。

## 起因

- 使用者 2026-11-13:「我舉 flatmaplatest 只是拋磚引玉,我是覺得改動中的語法,必定是代表一種需求,而這個需求,必須引得出規格,以這樣的方式能找出系統邊界不全,所產生的語法謬誤,而語法是可以被窮舉的,也就代表 code review 是可以被機械層檢查」。
- 使用者 2026-11-13:「ACH 是從需求出發→生成壞法→生成測試,但這條也對應到我們 Spec 拆分任務以需求推出的測試為主,是一樣的概念,是不是也可以借鑑? 只是後續 code review 我們多一層方向相反的審查,全面覆蓋風險」。
- 前因:[[Projects/情境題答案要引規格出處與回寫循環_計劃]] 把「Android 情境題答案要引規格、規格沒寫交人裁並寫回條款與會紅的測試」做成推送閘,但觸發來源只有 Kotlin 型錄〈情境決策表〉幾十列;2026-11-13 第一次在真 Gradle 專案實跑,缺口記在 [[Issues/人裁殺傷力在真實Android專案跑不動的四個缺口]]。

## 核心論點

1. 改動裡每個「有替代寫法」的語法選擇(`flatMapLatest` 對 `flatMapConcat`、`<` 對 `<=`、`List` 對 `Set`、逾時 5 秒對 30 秒、四捨五入對捨去)都在表達一個需求。
2. 這個需求必須引得出規格;引不出來 = 系統邊界沒定義完整(規格沒寫)或語法謬誤(寫錯)。
3. 語言裡「有替代寫法的選擇點」是可窮舉的有限集合,所以這一層 code review 可以機械化:逐點要出處,沒出處就擋、交人裁、寫回規格、綁一支換成替代寫法就會紅的測試。
4. 正向(需求 → 壞法 → 測試)與反向(語法選擇 → 需求)兩條一起做,才全面覆蓋風險;這就是 DO-178C 的雙向追溯形狀。

## 兩個方向

| | 正向:從需求出發 | 反向:從程式出發 |
|---|---|---|
| 問的問題 | 每條需求有沒有測試真的守住(分得出對錯) | 程式裡每個選擇有沒有需求撐腰 |
| 抓的漏洞 | 需求有寫、測試分不出對錯(面試題:只送一次值) | 程式做了決定、規格沒寫(系統邊界不全) |
| 時間點 | 規格拆任務、實作前後 | 代碼審、推送前 |
| 現有 | 規格閘:條款綁測試、實作前要紅、預期值表 | 情境題引出處(只涵蓋型錄幾十列) |
| 現有的漏洞 | 「實作前要紅」只證明測試在「沒做」時紅,不證明在「做錯」時紅:只送一次值的測試對空殼是紅的、對 `flatMapConcat` 是綠的,規格閘會放行 | 選擇點只窮舉到型錄那幾列 |

## 借鑑與打算怎麼接

- 正向借 Meta ACH:每條條款除了綁測試,再列出「近似錯誤寫法」(來源:型錄兄弟寫法、PIT 運算子清單、AI 依需求生的情境壞法);實作後推送前跑殺傷力,條款的測試要殺得掉它列的每一個。規格閘的「實作前要紅」保留當第一道。
- 反向:改動行的每個變異點(PIT 能產的運算子變異 + 型錄的 API 兄弟寫法)都要落在三種處置之一:被綁在條款上的測試殺掉、判等價(AI 先篩、盲判覆核)、交人裁寫回規格(沿用 `lumos situation-rule` 的循環)。閘規則照「每個變異體要嘛被有名字的測試殺掉、要嘛有寫明的理由」。
- 兩條共用零件:變異引擎(PIT 在位元碼層改,順便避開「換寫法 import 跟不上」;型錄補 API 層兄弟寫法)、等價變異篩選、人裁寫回循環、條款綁測試與規格閘(追溯不另引進 OpenFastTrace/Doorstop,已有的就是同一件事)。
- 順序:先實驗 PIT → 正向先做(補規格閘現有漏洞、影響每份計劃)→ 反向再做(選擇點窮舉範圍大,邊做邊收斂)。

## 天花板

1. 兩條都只證「程式、測試、規格三者一致」,不證規格本身對;規格寫錯永遠要人。
2. 條款跟程式是不是在講同一件事,機器目前只驗引句逐字(同前因計劃天花板 1)。
3. 單一選擇點可窮舉,多個選擇點的組合(逾時 × 重試次數)會爆炸。
4. 每個選擇點都要條款,條款數會暴增;要先濾掉等價變異(換了寫法行為不變的不算需求)。

## 待驗

- **PIT 實驗結果(2026-11-13,測試品質實驗室 Android 副本,`pl.droidsonroids.pitest` 0.2.25、STRONGER 運算子、完整殺傷矩陣,範圍只鎖搜尋 ViewModel 與它的測試)**:
  - 跑得起來:Android + `kotlinx-coroutines-test` 的 `runTest` 沒問題,分析 1 秒、整個建置 4 秒。
  - 殺傷矩陣讀得出:每個 KILLED 的變異體在 `mutations.xml` 的 `killingTests` 列出哪幾支測試殺了它(例:拿掉 `onQuery` 的 `MutableStateFlow` 設值,由 `onlyLatestQueryShown` 殺掉)。
  - **雜訊太多,不能直接拿來擋**:37 個變異體(KILLED 16、SURVIVED 18、沒覆蓋 3)絕大多數落在 Kotlin 編譯器內聯進來的協程函式庫程式碼(`Emitters.kt`、`Merge.kt`、`SafeCollector.common.kt`)與協程狀態機(`throwOnFailure`、`switch`),落在手寫邏輯上的只有一兩個;SURVIVED 幾乎都不代表測試弱。PIT 自己提示要 Arcmutate 的 Kotlin 擴充(商用)過濾這類程式碼。
  - **沒有 API 層兄弟寫法**:沒產生 `flatMapLatest` → `flatMapConcat`,面試題情境抓不到。
  - **新發現的方向**:`flatMapLatest` 與 `flatMapConcat` 函式簽名相同,位元碼層「把呼叫換成同簽名的兄弟函式」可行——寫一個 PIT 自訂變異外掛,依型錄的兄弟寫法表換呼叫,同時解掉「API 層兄弟寫法」與 [[Issues/人裁殺傷力在真實Android專案跑不動的四個缺口]] 第 1 點的 import 缺口(位元碼層不用改原始碼、不用改 import)。
  - 待查:自訂 PIT 變異外掛的寫法與成本(PIT 有外掛介面);只取「落在改動行、而且不在內聯函式庫或狀態機」的變異體當雜訊過濾,能不能不靠 Arcmutate 做到(例:以 `sourceFile` 是否為專案自己的檔過濾)。
- Arcmutate 支不支援 Android 模組沒查到。

PRIOR-ART: Meta ACH 在 10,795 個 Android Kotlin 類別依關注需求生少量針對性變異體再生測試(9,095 變異體、571 測試、工程師接受 73%,等價變異 AI 篩前處理後 precision 0.95/recall 0.96);PIT 是 JVM 主流變異測試、Android 用 droidsonroids 分支外掛;有追溯工具把驗收標準定成「每個變異體被有名字的測試殺掉或有寫明理由」;DO-178C 要求雙向追溯與結構覆蓋證明沒有非預期功能。採用:引擎借 PIT、閘規則借那條驗收標準、正向借 ACH;不採:另引進需求追溯工具(條款綁測試已是同一件事)、逐點追溯做成單一工具功能(MUT4SLX 經驗:貴又搬不走)。
RETIRE-IF: 試行兩個月,反向那條擋下的「沒出處選擇點」超過八成被人裁判成「不是需求、只是實作細節」(誤報多過真報),或正向的近似錯誤殺傷力驗證讓每次推送多花超過十分鐘而抓到的弱測試少於每月一支——就把該方向降成只提醒或撤掉。
