# 推送前一次列出全部擋下原因_計劃

> 白話:推送前的閘現在是「遇到第一道擋下就結束」,一次只看得到一個原因;修好、重推(每次掛鉤要跑幾分鐘)才看到下一道。改成:全套測試之前那些便宜的閘全部跑完、把擋下原因收集起來,跑到全套之前只要有任何一道擋下,就一次列出全部原因並結束(不跑全套)。另外加一個預演指令,包住 `git push --dry-run`:不推送、不跑全套測試,只跑那些閘給你看結果(代碼審那一道本來就會跑的受波及合約測試照跑)。

## 緣起

- 2026-10-13 推 qo-frontmatter 那批時被依序擋了四次(新增告警、漂移檢查、回頭重讀、測試紅),每次修完重推才看到下一道;10-14 推示範回饋小修又被擋兩次(裁判簽名、新增告警)。出處是使用者 2026-10-14 的口述(問「這次有什麼 lumos 可以改進」時列為第一條);[[Verification/2026-10-13_後端示範交付]] 的改進候選當時沒收這一條,收工時補進去。
- 推送前掛鉤 `scripts/hooks/pre-push` 有十幾處擋下就 `exit 1`;`lumos code-loop check` 內部四道判定(合約測試、表態、新增告警、代碼審留痕)也是第一道沒過就停。2026-09-06 全 repo 審視 #12 只調了順序(便宜的先跑),沒做「一次列出全部」。

- 舊裁定:[[Projects/全repo審視_計劃]] #12 的 PRIOR-ART 全句是「裁定=borrow-design(fail_fast 不借——本 repo 已裁每道閘本來就 exit 1)」。那句的語境是不用另外借工具的遇錯就停開關,沒有評估過「一次列出全部」;F52 講的是測試第一支紅就停,是另一層。使用者 2026-10-14 聽完「推送前的閘一次只報一個原因」後明確要求修這一條——推翻該句;實作時在 #12 那段旁註記被本計劃取代。

PRIOR-ART: 外部:Git 生態最常用的 pre-commit 框架預設 `fail_fast: false`——每個 hook 都跑、最後一次列出全部失敗;`make -k`(keep going)同理。本 repo 內:pre-commit 掛鉤的 Gate L 已經是「旗標記下、迴圈繼續、各自印擋下說明、迴圈後統一 `exit 1`」——本計劃是同一種做法的跨閘版本,承襲它,不另造。預演借 git 自己的 `git push --dry-run`(它會照常呼叫推送前掛鉤、由 git 組出掛鉤要讀的推送行、保證不送出物件),不在 lumos 裡重算推送範圍。
RETIRE-IF: 上線 8 週內,版控治理帳裡真推送(不含預演)的 `prepush-summary` 事件中「兩道以上不同的閘」那幾筆為 0——撤掉收集邏輯、回到遇錯就停。
REVISIT:2026-12-15 數一次 `prepush-summary` 事件裡兩道以上不同閘的筆數,照 RETIRE-IF 判要不要撤。

## 做法

1. **掛鉤收集擋下原因**:掛鉤裡全套測試之前的每一道會擋的閘——裁判簽名(`anchor verify`)、簽名檔沒提交(`governance/anchor-baseline.json` 有未提交改動)、圖譜健檢(`doctor --ci`)、每支檔有家(`home check`)、筆記形狀(`note-shape`)、雙向門放行(`spec-gate --push-check`)、代碼審判定(`code-loop check`)、存量漂移(`drift check`)、回頭重讀(`note-audit reread-check --gate`),共 9 道——擋下時不再 `exit 1`,改呼叫共用函式 `pp_record_block <閘名> <ref 或空> <一句原因>`,照原樣把該道的完整說明印出來,然後繼續下一道。同一道被多個 ref 擋下時各記一筆。
   - **擋不擋只看記憶體裡的旗標**:`pp_record_block` 第一件事是設兩個純量變數 `_PP_BLOCKED=1`、`_PP_NBLK=$((_PP_NBLK+1))`(純量,bash 3.2 搭 `set -u` 不會有空陣列展開的問題),第二件事才把一行追加到 `$_PP_TMP/blocks`。判斷點只看 `_PP_BLOCKED`;暫存檔只拿來印彙總。追加失敗(磁碟滿、暫存目錄被刪)不影響擋下,彙總那一步看到檔案讀不到或筆數少於 `_PP_NBLK` 時,印「共 N 筆擋下,其中有幾筆的原因沒寫進暫存檔,細節看上面各段」。
   - **暫存檔一行的格式**:`printf '%s\t%s\t%s\n'`,三欄是閘名、ref、原因。ref 空的時候寫 `-`(bash 用 tab 當分隔讀回時,連續兩個 tab 會被合成一個,空欄會被吃掉——`/bin/bash` 3.2.57 實測)。原因一律是掛鉤裡寫死的一句(不放工具輸出),ref 名照 git 規則不含 ASCII 控制字元(0x00–0x1f、0x7f;U+0085、U+2028、U+2029 這類 Unicode 斷行字元 git 仍放行,見 [[Systems/bound-tests-gate]]);函式仍先把三個欄位裡的 tab、換行換成空白再寫。
   - **裁判簽名也收集,不再立刻停**:裁判簽名管的是測試檔與掛鉤(錨點清單),不管 `scripts/lumos`。被改的若是掛鉤本身,它在這一刻已經在跑,停不停都由它決定,提早結束換不到可信度。後面的閘大多是 `scripts/lumos` 在判,不經過測試檔;例外是代碼審那一道的受波及合約測試與雙向門放行,它們會在全套之前跑 `scripts/test_lumos.py` 裡的測試——這兩道的綠燈這次用的是沒簽名的測試檔。不論結果,這次推送都已經因為裁判簽名被擋,所以不會變成放行;彙總裡有裁判簽名那筆時,最前面加一行「裁判檔沒簽名:代碼審與雙向門放行這次跑的測試用的是沒簽名的測試檔,它們的綠燈不算數;簽名後重推會重跑」。
   - **裁判簽名與圖譜健檢維持「非零就擋」**:這兩道現在用 `if ! …` 寫,非零一律擋。改成取回傳碼之後,128 以上照第 2 點停下,其他非零照舊記成擋下(不能變成「只有 1 才擋」,否則回 2 的工具錯誤會變放行)。
   - **刪除與 tag 照舊**:逐 ref 迴圈遇到刪除照舊跳過、tag 照舊不跑代碼審判定,只把原本的擋下換成記下。
   - **跟 pre-commit 的關係**:pre-commit 的 Gate PY、Gate H、Gate NS 之間仍是遇錯就停,本計劃不改。理由:那幾道合計幾秒,修完重提交的代價是幾秒;推送這邊每重推一次要幾分鐘,這才是要解的痛。
2. **中斷一律結束**:
   - **列舉,不逐行**:判斷點之前要接 `pp_stop_if_signaled` 的,是 9 道裡的 8 支 lumos 呼叫(簽名檔沒提交那道是 git)加上新分支首推起點(`push-range`)與這次推送改到哪些檔那一支;清單寫在掛鉤一個註解區塊裡,守衛測試照清單逐支驗。刻意不接的照列在同一個註解區塊、各附一句理由:`|| true` 寫法的盡力而為呼叫(逃逸自動記帳、該補哪層測試、低風險合約測試提醒、`pitfalls`)與管線裡的呼叫——被中斷時它們本來就走放行,不會把擋下變成放行;中斷照樣會由下一支在清單上的呼叫或第 2 點的陷阱接住。現有的 `t_prepush_gates_stop_on_signal` 數 8 行的寫法改成照這份清單驗。
   - **陷阱拆開**:`EXIT` 負責 `impact_done`、刪 `$_PP_TMP`,以及在預演模式下刪掉驗過的那張票(第 7 點);`INT` 改成「先 `kill` 掛鉤自己的背景工作(`jobs -p`),再 `exit 130`」,`TERM` 同樣但 `exit 143`,`HUP` 同樣但 `exit 129`(結束時再走 `EXIT` 那支收拾;HUP 是代碼審第二輪併發席補的:ssh 或編輯器只對掛鉤送掛斷時,沒接的話掛鉤直接死、各片全變孤兒)。現在 `trap … EXIT INT TERM` 共用一支、裡面不結束,掛鉤自己收到中斷時會刪掉暫存目錄後繼續往下跑(`/bin/bash` 3.2.57 實測:陷阱跑完印出下一行);這是現有的缺陷,收集模式會讓它更常踩到,一起修。
   - **全套測試的各片也要收掉**(代碼審第一輪併發席):`jobs -p` 只列得到掛鉤的直接子行程,也就是跑測試的那個子殼;各片是子殼用 `&` 起的孫行程。而且非互動 bash 用 `&` 起的背景命令忽略 SIGINT,按 Ctrl-C 時整個行程群組收到的 INT 也殺不到各片。所以子殼(`run_group`)自己接 TERM 與 HUP:收到就把它起的各片收掉再結束。掛鉤的 INT/TERM/HUP 陷阱送給子殼的 TERM 由它往下傳。子殼收片用主殼同一支 `_pp_kill_jobs`(子殼裡 `jobs -p` 列的就是它自己起的各片),不自己記 pid 收:「`&` 起片」與「記下 pid」是兩個敘述,訊號落在中間時剛起的那片不在清單上(代碼審第二輪併發席、架構對齊席);記下的 pid 只拿來 `wait` 收各片的離開碼。`/bin/bash` 3.2.57 實測:改之前被砍或按 Ctrl-C 後,四片都變成 ppid=1 的孤兒;改之後一片都不剩。
     - **各片各自一個行程群組,整組收**(代碼審第三輪併發席):只收片本人的話,片自己起的子行程(測試裡的 git、子行程)全變孤兒,訊號落在起片後幾毫秒內時連片本人都會漏。所以起片時先經一層 Python 換到自己的行程群組(`setpgid` 後 `exec` 成測試執行器;bash 3.2 沒有 `setsid`),`_pp_kill_jobs` 對每個工作先整組送 TERM,那個工作不是群組組長(跑測試的子殼、剛起還沒換群組的片)才退回只送給它本人;主殼與子殼共用這一支。不選子殼裡 `set -m`:同一個模擬下它留下孤兒的次數多得多(數字在代碼審第三輪修正紀錄)。終端機按 Ctrl-C 只送到前景群組(掛鉤那一組),各片不在裡面,靠掛鉤的 INT 陷阱經子殼收;子殼直接收到 HUP 時由它自己的 HUP 陷阱收。測試自己用 `start_new_session` 起的子行程不在片的群組裡,整組收也收不到,由那支測試自己負責。
     - **只有子殼收到 HUP 時掛鉤回 1**:子殼收掉各片後以 129 結束,主殼把非零的子殼結束碼一律當成測試沒過,印「test_lumos.py 有紅」、回 1 擋下。這時「紅的是這幾支」底下是空的:沒有任何一支測試真的紅,是跑測試的子殼被掛斷了。不另外分辨:這種情形只在有人只掛斷子殼時發生,擋下是安全的方向,重推就會重跑。
     - **整組送 TERM 之後短等再送第二發**(代碼審第四輪併發席):訊號是逐一投遞給群組當下的成員,送的那一刻正在 fork 的成員被殺時,剛生出來的孩子已經在群組裡,卻沒收到那一發。所以 `_pp_kill_jobs` 送完第一發後等 0.2 秒,再對每個群組送一次 TERM,群組已空的錯誤吞掉。只送一發時,掛鉤啟動後 20–45 毫秒送 TERM 會留下孤兒,補第二發後實測沒有(`/bin/bash` 3.2.57 模擬,數字在代碼審第四輪修正紀錄)。
     - **沒有 `os.setpgid` 的 Python 不換群組**(代碼審第四輪正確性席、併發席、通才席):原生 Windows 的 Python 沒有 `setpgid`,它的 `os.execv` 又是起新行程後讓舊的立刻回 0。所以換群組那段只在有 `setpgid` 時才換、再 `exec`;沒有就在同一個行程裡用 `runpy` 跑測試檔。`setpgid` 本身失敗時不換群組、照樣 `exec`。離開碼一律是測試檔自己的。[test: t_prepush_interrupt_launcher_without_setpgid]
   - **時機**:bash 要等前景子程序結束才跑陷阱。按 Ctrl-C 時整個前景程序組都會收到 INT,子程序自己會先停;只對掛鉤送 TERM 時,掛鉤會等手上那支子程序跑完才結束——S10 寫的「立刻」是指「目前那支子程序結束之後,不再開始下一道」。
3. **全套測試之前統一判**:判斷點放在建 `_AUTOLOOP_LOG`、`_TESTS_LOG` 那兩個 log 檔之前。兩個 log 都放在 `$_PP_TMP` 裡,正常結束、擋下、中斷時都由 `EXIT` 陷阱一起清。原本它們用 `mktemp` 建在 `$_PP_TMP` 外,中斷與全綠時都會留下(代碼審第一輪併發席)。測試紅時要指給人看的那一份,先複製到暫存資料夾外,再印複製出去那份的路徑(S18)。
   - `_PP_BLOCKED` 是 1 時,呼叫 `lumos push-summary --blocks-file "$_PP_TMP/blocks" --count "$_PP_NBLK" --refs <這次非刪除的推送行數>`:由它印「這次推送共有 N 筆擋下(M 道閘)」的彙總(N 是筆數,同一道被多個 ref 擋或代碼審內部擋兩個原因都各算一筆;M 是不同閘名的個數),逐筆一行:閘名、ref、原因,詳細處理方式看上面那一段。ref 欄在 `--refs` 大於 1 時印。它同時落一筆治理帳(閘名 `prepush-summary`、kind `blocked`、hard、帶 `LUMOS_PUSH_ATTEMPT`、`extra` 裡放 N、M、不同閘名的清單與推送行數)。`prepush-summary` 要登記進已知閘名清單 `_KNOWN_GATES`,不然事件會被拒寫。
   - 不論 `push-summary` 成不成功,掛鉤接著一律 `exit 1`,不跑自主迴圈測試與全套測試。`push-summary` 回非零或不存在(舊版 lumos)時,掛鉤自己用 `while IFS=$'\t' read -r` 逐行印一份簡版彙總——觀測失效不得改變擋下。
   - `_PP_BLOCKED` 不是 1 才照舊往下跑測試。
   - 為什麼由掛鉤呼叫一支會記帳的子命令:先例是掛鉤呼叫 `loop escape --auto`,把掛鉤算好的內容交給它記帳。彙總必須在所有閘之後才算得出來,只有掛鉤知道全部結果;印彙總與記這一筆是 `push-summary` 自己的工作,不是開一個任意寫帳的入口(它只收這一種格式的檔)。
   - 連帶擋下照實列:圖譜健檢擋下時,依賴圖譜索引的閘(每支檔有家、雙向門放行、回頭重讀)可能跟著擋。彙總照實列出,不去猜哪道是連帶;這會讓 RETIRE-IF 的筆數偏多,方向是「更不容易撤」,可以接受。
4. **前提壞掉的照舊立刻停**:找不到 Python 3.14、暫存目錄建不起來(掛鉤開頭的總暫存目錄,與測試前建 log 檔那一步)、使用者中斷(第 2 點)——這幾種後面什麼都跑不了或不該再跑,維持立刻結束。找不到 `scripts/lumos` 照舊是「提醒後放行」(`exit 0`),不在收集範圍。
5. **代碼審判定內部也全部判完**:`lumos code-loop check` 新增 `--keep-going`(名字照 PRIOR-ART 的 `make -k`):
   - 各道判定(合約測試、表態、新增告警、代碼審留痕;2026-10-20 起有資安登記時另有安全證據,排最前;2026-10-27 起有 e2e 段時另有 Android 端到端驗收,排在安全證據之後;共六道)都跑完,每道擋下各印各的訊息(原本的擋下句一字不改),最後只要有一道擋下就 rc1。
   - **一處判**:判定函式在這個模式下把擋下累積進一個清單,函式裡所有回傳都經過同一個收尾函式:清單非空就回擋下,清單是空的才照原樣回放行。放行站點的意思變成「這一道過了」,不能蓋掉前面記下的擋下。現有的放行站點有 8 個:pitfalls 失敗、pitfalls 沒有 JSON、pitfalls 例外、tier 不是 high、留痕有效(sha 直接相符)、留痕過時但屬簿記豁免、留痕要求被環境變數跳過、合併側放行。守衛測試掃這支函式的原始碼,每個 `return` 只准兩種形狀:直接 `return _fin(...)`;或回傳由收集分流 `kg.hit(...)` 指派的變數,而且緊接在判它非空的 `if <那個變數>:` 底下(不帶旗標時 `hit` 回的就是收尾後的結果;帶旗標時回 None,不判非空就回傳會讓整個函式回 None,代碼審第二輪合約席)。另外逐站點各一支行為測試(S13)。
   - **合約測試有兩個擋下點**:一般的那個,與「帶低風險提醒旗標但算出 tier=high 時重跑」的那個;兩個在這個模式下都記成 `reason_kind: bound_tests` 並繼續。
   - **pitfalls 失敗時**:表態需要 pitfalls 的資料,照現在 fail-open 不判;代碼審留痕需要 tier,同樣不判;新增告警閘只看改動範圍、不需要 pitfalls,照跑。前面記下的擋下照算。(不帶這個旗標時照舊整個 fail-open。)
     - **所以推送前比直接跑 CLI 嚴**:掛鉤認得這個旗標就一律帶上。所以「pitfalls 暫時失敗(逾時、環境壞),而且這次改動帶進新告警」時,不帶旗標會放行,推送前會因新增告警擋下(`LUMOS-BLOCKS: lint_new`)。這是有意的,方向是更嚴、不是放行(代碼審第一輪正確性席要求寫明)。[test: t_code_loop_keep_going_pf_fail_stricter]
   - 合約測試先紅時照樣算風險分級,後面幾道照判。
   - 帶 `--json` 時多一個 `blocks` 清單(每筆 `reason_kind` 與 `reason`);`blocked`、`reason`(放第一筆)照舊;`tier` 在這個模式下一律是算出來的分級,pitfalls 失敗時是 `unknown`。不帶 `--keep-going` 時行為與輸出一字不變(其他呼叫者如 CI 不受影響)。
   - 印合約測試狀態的那幾句照「合約測試有沒有記成擋下」選,不照第一個擋下原因選:記成擋下就不印「低風險只提醒不擋」那類句子。
   - 治理帳照舊一次判定一筆 `code-loop` `blocked` 事件(現有統計的筆數意義不變),`extra` 多放 `blocks` 的 `reason_kind` 清單。
   - **給掛鉤讀的那一行**:這個模式最後多印一行 `LUMOS-BLOCKS: <reason_kind 以逗號分隔>`。掛鉤的規則:`code-loop check` 回 1 時,不論這一行在不在、解析出幾筆,至少記一筆 `code-loop`;解析得到就每個 `reason_kind` 各記一筆(閘名一律是 `code-loop`,所以 M 只算一道),原因用對照表寫死的一句,對照表查不到的用通用句「代碼審判定擋下(細節在上面)」;有多行時取最後一行。掛鉤把這一行從要印給人看的輸出裡濾掉。
     - **對照表六句的正本在這裡**(掛鉤的對照表與測試的預期值都照這六句逐字寫;要改句子先改這裡,再改那兩處):`bound_tests` 是「受波及合約的測試沒過(或證不出跑過)」;`dispositions` 是「棧別檢核題表態不完整」;`lint_new` 是「這次改動帶進了新的告警」;`review` 是「高風險改動沒有有效的代碼審留痕」;`security_evidence` 是「資安護欄的證據不合格(或判不清)」;`android_e2e` 是「Android 端到端驗收沒過、沒紀錄(或判不清)」。2026-10-20 [[Projects/安全主張驗收閘_計劃]] 加了第五道,2026-10-27 [[Projects/Android端到端驗收_計劃]] 加了第六道。(代碼審第三輪合約席:原本只有表態那句在這裡有出處)
   - 為什麼不直接讀 `--json`:掛鉤要把給人看的文字原樣印出來,逃逸自動記帳也靠文字裡的兩句擋下句;改讀 JSON 就得呼叫兩次或另外組文字。所以文字輸出之外只加這一行,它是掛鉤唯一的機讀通道。
   - 逃逸自動記帳照現在的判斷,認「受波及合約的測試沒過」與「tier=high 且」兩句。**一個 ref 只記一筆,合約測試紅優先**(代碼審第一輪通才席):原本遇錯就停,只會印第一句;帶這個旗標後兩句會同時印出。各記一筆的話,修好測試重推時缺留痕那筆會再記一次,`push-gate-unreviewed` 的筆數就比實際抓到的漏多。[test: t_prepush_escape_records_once]
6. **新舊版本混用不能變成放行**:掛鉤與 `scripts/lumos` 分開複製到消費專案,而且 `core.hooksPath` 會讓好幾個工作樹共用同一份掛鉤(本 repo 的工作樹現在就指到本機安裝的那份),所以兩邊版本會錯開。
   - 新掛鉤配舊 lumos:掛鉤在逐 ref 迴圈之前讀一次 `scripts/lumos` 的原始碼,看有沒有 `"--keep-going"` 這個字樣。寫法是 `grep -q -- '"--keep-going"'`,跟掛鉤探 `--shard`、`--suite`、`--graph` 同一種,不執行對方;第一輪代碼審前是執行 `--help`,架構對齊席指出是第二種做法。沒有就不帶這個旗標、不讀 `LUMOS-BLOCKS:` 行,代碼審那一道 rc1 時照舊記一筆——不會因為舊版不認得旗標回 2 而被 fail-open 放行。`push-summary` 不存在時走第 3 點的簡版彙總。
   - 舊掛鉤配新 lumos:舊掛鉤不帶新旗標,行為照舊;`push-preview` 會先檢查掛鉤(見第 7 點)。
   - 兩種版本探測方向不同,手法都是讀檔、不執行對方:掛鉤探測 lumos 是找 `"--keep-going"` 字樣;`push-preview` 探測掛鉤是找 `# lumos-hook-cap: push-preview`。後者是能力標記,不是工具用 `git log -S` 找上線點的那兩串上線標記註解,兩者的分工寫進 [[Systems/bound-tests-gate]]。
7. **預演指令** `lumos push-preview [<遠端> <refspec>]`:包住 `git push --dry-run`。
   - **參數只收這兩個位置參數,不透傳任意 git 旗標**:這樣 `--no-dry-run`(git 2.39.2 實測會取消預演、真的推出去)、`--no-verify`(掛鉤不跑)、跟 lumos 慣用的 `--repo` 撞名都不會發生。沒給參數時:目前分支有追蹤的遠端分支,用 git 的預設;沒有追蹤、或 detached HEAD,回 2 並印要人帶參數的例子:
     `lumos push-preview Lumos HEAD:refs/heads/<分支>`
     (沒追蹤時不猜遠端:多遠端時「主線在哪個遠端」沒有可靠判法,`git push --dry-run <遠端>` 不帶 refspec 也會因為沒有上游而失敗——邊界席實測。)
   - **先確認掛鉤支援預演**:用 `git rev-parse --path-format=absolute --git-path hooks/pre-push` 找到會被呼叫的掛鉤檔(照 `core.hooksPath` 走;現有找掛鉤資料夾的共用函式能重用就重用),檔裡要有一行 `# lumos-hook-cap: push-preview`;沒有就回 2,說「掛鉤是舊版,先 `lumos update`」,不跑(免得舊掛鉤跑完 8 分鐘全套)。
   - **一次性票**:`push-preview` 產生 32 個十六進位字的隨機值,在 `git rev-parse --path-format=absolute --git-common-dir` 底下的 `lumos/` 建一個檔 `push-preview.<隨機值>`,內容是「隨機值 空白 自己的 pid」,並帶環境變數 `LUMOS_PUSH_PREVIEW=<隨機值>` 跑 `git push --dry-run <遠端> <refspec>`(`--dry-run` 由 `push-preview` 自己放,使用者參數不可能蓋掉)。放在 git 共用資料夾而不是 `~/.cache/lumos/`:票要讓「同一個 repo 的任何工作樹」的掛鉤都找得到,又不能讓別的 repo 的掛鉤找到;git 共用資料夾正好是這個範圍。
   - **掛鉤怎麼認票(只在開頭判一次)**:環境變數有值、而且是 32 個十六進位字、對應的檔存在、檔裡的隨機值相符——四項都成立才進預演模式,判定結果存在變數裡,之後不再重判。任何一項不符,印一句「忽略 LUMOS_PUSH_PREVIEW(不是預演指令叫的),這次照真推送跑」,把變數清掉,照常跑完整掛鉤,也不碰那張票。所以把這個變數寫進 shell 設定、或從別的程序漏進來,都不會讓真推送跳過測試。
   - **預演模式還要確認 lumos 也支援**:掛鉤呼叫的是 repo 自己的 `scripts/lumos`,可能比 `push-preview` 舊。進預演模式後,掛鉤先探測 `push-summary --help` 存不存在(預演分流與它同一版上線);不存在就在結果檔寫「unsupported」並結束,`push-preview` 回 2 說「這個 repo 的 lumos 太舊」——免得舊版寫入器把預演事件寫進版控帳。
   - **預演模式下掛鉤做什麼**:跑完 9 道與統一判斷,在判斷點停,把結果寫進票旁邊的結果檔 `push-preview.<隨機值>.result`(一行:非刪除推送行數、擋下筆數),然後**一律 `exit 1`**——掛鉤回 1 時 git 不會推送任何東西,所以就算 git 因為任何原因沒有照預演跑,這一次也推不出去。git 會因此回非零並印「failed to push」,`push-preview` 把那段收起來不印。
   - **回傳碼只看結果檔**:結果檔不在或解析不出兩個數字 → 2(掛鉤沒跑到判斷點:git 連不上遠端、掛鉤舊版、被中斷,附上 git 的訊息);推送行數是 0 → 2(沒有任何 ref 被檢查:已是最新,或 git 先把被拒的 ref 剔掉了——非快轉時掛鉤照樣被叫但收到的推送行是空的,邊界席實測),附上 git 的訊息;擋下筆數大於 0 → 1;否則 0,並印「便宜的閘都過了;全套測試沒跑(預演不跑),真推送時還會跑」。回 0 不代表全套測試綠。
   - **檔案誰刪**:掛鉤的 `EXIT` 陷阱刪掉它驗過的那張票(結果檔留給 `push-preview` 讀);`push-preview` 讀完結果後刪票與結果檔;`push-preview` 每次開始時,只刪那個資料夾裡「票上記的 pid 已經不在」的票與結果檔(收拾上一次被中斷的殘檔)——不看建立了多久,所以另一個工作樹還在跑的預演(最壞可以超過 10 分鐘)不會被誤刪。
   - **為什麼是新子命令、不是 `--dry-run` 旗標**:專案慣例的 `--dry-run` 都是加在「會做事的那個 lumos 指令」上;推送不是 lumos 指令,對應的旗標就是 git 自己的 `git push --dry-run`。`push-preview` 只是替它加上票與結果檔的薄包裝,名稱對齊既有的 `push-range`。
   - **工作目錄有未提交改動時**先印一句:圖譜健檢與簽名檔那兩道看工作目錄、其他道看提交,預演結果可能跟提交之後不一樣。
8. **預演不寫版控帳,也不進統計**:
   - 掛鉤在預演模式下不呼叫 `loop escape --auto`(逃逸帳的筆數被其他機制拿來當退回門檻,預演沒推送,不算逃逸)。
   - 寫治理帳的兩支函式(逐閘事件那支與健檢那支)在分流之前,用跟掛鉤同一條驗法(環境變數是 32 個十六進位字、票檔存在且隨機值相符)判斷「這是預演」,是就替事件標上 `preview: true`;分流判定(現在決定哪些事件進本機帳的那一支)第一條規則改成「帶 `preview` 的一律進本機帳 `docs/.governance-local.jsonl`」,排在現有「非 hard、在白名單裡」那條之前。白名單旁那句「代碼審事件永遠不准進本機帳」是講真推送的事件,補一句預演例外。票在掛鉤整段執行期間都在(掛鉤結束才刪),所以中途寫的事件都驗得到。
   - 統計類讀者(按時間讀兩本帳的那支,與 `lumos gov` 的載入)略過帶 `preview` 的事件——預演留觀測,但不混進真推送的數字。
   - 直接寫版控帳、不經分流的另外兩支(代碼審留痕與表態的寫入器)只被 `pass`、`skip`、`dispositions` 呼叫,掛鉤路徑不會碰到,不改;實作第一步仍照 S9 的判準盤點一次,盤點表寫進本節。

## 實務隱患

- 守衛面:這是推送閘本身。最大的風險是「收集」寫錯讓某道擋下被吞掉、變成放行。對策:掛鉤只用一個共用函式記、一處判;`code-loop check` 只用一個收尾函式判;版本混用先探測;預演要票。S6 逐道、S13 逐放行站點各驗一次,S7 驗混用,S8 驗漏出來的變數。
- 已排除:金流:不碰任何付款或點數。
- 對外連線:預演跑 `git push --dry-run`,會連遠端讀它有哪些分支(唯讀),不送出任何物件;連不上時回 2(第 7 點)。真推送照舊。
- 已排除:不可逆:只改掛鉤的判斷流程與兩個子命令,還原提交即可;擋下的情況不會變少。
- 輸出變長:一次列出全部之後,被擋時的訊息會比現在多;彙總段放在最後、逐道一行,讓人一眼看到總數。
- 時間:預演與真推送一樣會跑代碼審那一道的受波及合約測試(整套逾時 600 秒)與雙向門放行留痕裡的測試,這不算在「全套測試」裡。收集模式的最壞時間,等於「今天一次便宜閘全過的推送」跑到全套之前的最壞時間——同樣那幾道,今天全過時本來就全部要跑。逐 ref 的大項:漂移判定本體每個 ref 最壞 60 秒、它之前算範圍的 git 呼叫每次最多 20 秒、回頭重讀約 30 秒、新增告警閘最多 300 秒(代碼審判定在表態先擋下時,今天不會跑到它,收集模式會跑),一次推多個 ref 會相加。跟今天比,多出來的只是「第一道擋下之後那幾道」的時間;而這些時間在修完第一個原因重推時本來就要花,再加上那次重推的等待。所以不另設總時限。
