# 世界解重新註解2026-10_九類之外_調研

> 白話:Lumos 的九類研究方向,把「代理怎麼拿到脈絡、怎麼被審、怎麼被擋、怎麼被量、怎麼裝上去」這條機器側的鏈蓋得很完整;這篇從整個世界的議題地圖往外看,找九類都沒管到的地方。沒管到的集中在三塊:人(注意力、理解、同時看多個專案)、錢與法(成本、法規、出處、資料能送去哪)、真實世界的回饋(生產事故、長期品質趨勢、交付成果)。另一半在評估過時風險:2025 年 Lumos 手工做的不少底層功能,到 2026-10 廠商都有原生版本了,哪些該借用、委派、照留或縮小。所有「Lumos 有沒有 X」都以 2026-10-11 乾淨代理的核對為準,研究筆記說法不同的地方逐條註明。

## 世界議題地圖

- 怎麼來的:研究員以 Hassan 等人的代理式軟體工程路線圖、Thoughtworks 技術雷達 34 期、ICSE 與 ASE 2026 的代理工作坊徵稿題與錄取清單、各廠商官方文件拼出 25 個議題群組(來源 1–5)。九類的定義見 [[Projects/工具分類_計劃]];同組其他九篇與總覽見 [[Projects/世界解重新註解2026-10_總覽_調研]]。

## 九類之外的議題逐一註解

- 證據強度:A 受控實驗或方法公開的基準;B 生產數據或廠商自報;C 實務經驗或質性研究;D 行銷宣稱或只確認功能存在。註解深度:讀全文、讀官方文件、二手摘要。
- 「現況核對」一律採 2026-10-11 乾淨代理的答案(每題經第二席複查);「以前怎麼判過」來自前例對照,只當背景,不拿來刪候選。
- 排序依對使命(人不必逐行看 diff、同時推進多個專案)的衝擊:人 → 錢與安全 → 法與出處 → 真實世界回饋 → 低優先。

### G1 人的注意力與非同步監督(C10,九類沒有歸屬)

- 世界代表做法:
  - Claude Code agent view(官方文件,2026-10-11 讀取,研究預覽,版本列到 2.1.290;來源 6):一個終端畫面管所有背景工作階段,分「需要輸入、待審、工作中、完成」;小模型替每列寫摘要;同時觸發通知用的 hook(工具在特定時點自動跑的腳本)。強度 D:功能存在已確認,成效無數據。深度:讀官方文件。
  - Claude Code auto mode(Anthropic 工程文章,2026-03-25;來源 7):用分類器取代逐次權限提示,理由是使用者本來就照准 93% 的提示。強度 B:內部流量 n=10,000 誤擋 0.4%,但「過度積極」動作只有 n=52、漏放 17%,樣本太小。深度:讀官方文件。
  - Claude Code Projects(官方文件,2026-10-11 讀取,公開測試;來源 8)、Cursor Projects(2026-09-10;來源 9)、GitHub Agent HQ(2025-10-28;來源 10):都把工作分成「等你/進行中/完成」,一個入口管多代理、多 repo。強度 D。深度:前兩者讀官方文件,Agent HQ 只讀上線報導。
  - Dhanorkar 等〈Human oversight of agentic systems in practice〉(arXiv,2026-06-03;來源 11):17 位資深開發者訪談,監督分事前控制、共同規劃、即時監看、事後審查四種;常見捷思是「把測試結果當正確性保證」。強度 C:質性、樣本小。深度:二手摘要。
  - OpenAI〈The Shift to Agentic AI: Evidence from Codex〉(arXiv,2026-06-25;來源 12):某週超過一成使用者同時管三個以上 Codex 代理。強度 B:廠商資料,方法在論文中。深度:二手摘要。
  - Hassan 等的代理式軟體工程路線圖(arXiv,2025-09-23;來源 1):代理要人時產出「諮詢請求包」,裁決存成進版控的紀錄,並把「讓沒參與的決策者快速看懂、依專長路由」列為一級研究題。強度 D:願景。深度:讀全文。
- 為什麼對使命重要:人不看 diff 之後,稀缺資源從「讀 diff 的時間」變成「做裁定的注意力」。廠商主控台正在變成人唯一的入口;Lumos 的人裁事項不出現在那裡,人就看不到。auto mode 的 93% 也直接說明「人點同意」不等於監督。
- Lumos 現況核對(答案判「部分有」):
  - 單一專案內的待人訊號都有,但散在各處:健檢的回訪到期、審查跑滿上限的提示、`lumos loop list` 開著的迴圈、`lumos gov --nags 14` 軟閘連喊的組合;待決 Issue 只能用通用查詢。
  - 跨專案或主動通知只在維護者自己機器的排程腳本:每週把工具鏈本體和一個寫死路徑的消費專案的空轉清單、考卷、探針異常推到 LINE。只帶清單前 5 組,而 2026-10-11 唯讀跑出 127 組;這些腳本不隨安裝分發。
  - 「業務簽核待確認」沒有任何清單:簽核欄位在程式裡只被寫入,沒有地方判「哪些該簽還沒簽」。跑滿待人裁的事件也不進連喊清單。
  - 照准率、等待天數:2026-10-11 核對,圖譜沒有任何一處量過;也查無接 Claude Code 通知 hook 或 agent view 的紀錄。
- 以前怎麼判過:前例對照判「已採用並實作(部分)」。回訪掃描計劃(2026-08-31)當時就診斷出「待裁事項散在十餘張 open Issue,無任何機制定期端到人面前」,做法是一次性清單,不是常設佇列。[[Projects/每日治理wrapper活著沒_計劃]] 記過「沒有任何東西在讀它印的東西」,「印了沒人看」在 Lumos 內部發生過。這次有新證據:agent view、Projects、auto mode 的 93% 都沒進過圖譜。
- 最小切入點:唯讀的「人裁佇列」查詢,把既有帳本裡等人的事項(跑滿未裁、到期回訪、待決 Issue、本週評測通知)列成一份機器可讀清單加白話清單,格式讓通知 hook 或 agent view 吃得下。先回溯 4 週量:每週件數、平均等待天數。翻紅條件:回溯找到一件「等人超過 7 天而人不知道」的事項。撤除條件:連續 8 週平均少於 1 件,或廠商主控台能直接讀 Lumos 帳本。

### G2 人的理解債與技能保持(C11,九類沒有歸屬)

- 世界代表做法:
  - Shen、Tamkin(Anthropic)〈How AI assistance impacts the formation of coding skills〉(2026-01-29;來源 13):52 名工程師學新函式庫,有 AI 組測驗平均 50%、手寫組 67%(Cohen's d=0.738,p=0.01),差距最大在除錯題;低分型態是全委派、靠 AI 除錯,高分型態是生成後追問理解。強度 A:隨機對照,但每組 26 人、只量立即理解、非代理式工具。深度:讀官方文件。
  - Storey〈From Technical Debt to Cognitive and Intent Debt〉(arXiv,2026-03-23,v4 2026-04-06;來源 14):三重債——技術債在程式碼、認知債在人(團隊共享理解的侵蝕)、意圖債在外化知識(理由、目標、限制的缺席)。強度 C/D:概念論文。深度:二手摘要。
  - Thoughtworks 雷達 34 期「Codebase cognitive debt」列 Caution(2026-04-15;來源 2):建議回饋感測器、追蹤團隊認知負荷、架構適應度函數。強度 C。深度:二手摘要。
  - Cognition Codemaps(2025-11-04;來源 15):AI 註解的程式碼地圖,把「人看懂」當產品目標。強度 D:文章自承沒做基準。深度:讀官方文件。
  - METR 開發者生產力研究:2025 年資深開源開發者用 AI 平均慢 19% 卻自覺變快;2026-02 改做問卷(來源 16)。強度 A(2025)/C(2026),未複驗。深度:二手摘要。
- 為什麼對使命重要:Storey 的模型給 Lumos 一個精準定位——圖譜是意圖債的償還機制,認知債是空白。「人不看 diff」和「人負責裁定」之間有張力:人越不看,越可能在簽核、跑滿裁定、接受風險時蓋章;而 Lumos 所有人裁點都靠這份理解。
- Lumos 現況核對(答案判「查無」):`lumos signoff` 只要求理由非空,說明文字原文是「工具只記留痕,不證明確認真的發生」;`lumos loop cap-decision` 只驗理由至少 10 字;量測對象(情境探針、自我稽核、README 理解分)都是 AI 不是人。理由欄可由代理代填,工具分不出來。圖譜另記本 repo 98.6% 提交出自同一人,「人接手」在一篇調研裡列為未處理缺口。
- 以前怎麼判過:查無先例。最接近的是 [[Projects/業務簽核留痕_計劃]](2026-07-10):只要求一句確認了什麼,「何時該簽由人/流程判,工具不擋」。這次有新證據:Anthropic 隨機對照、Storey、雷達條目都沒進過圖譜。
- 最小切入點:「人裁前三問」只記不擋——在簽核、跑滿裁定、接受風險之前,由代理從相關節點的合約、決策、事故出 2–3 題白話題(例:「這條規則拿掉後,哪個使用者情境會出錯?」),人用自己的話答;只記「答了沒、自評對不對、答完有沒有改判」,跑 4 週。翻紅條件:出現一次「答錯但仍照准」。撤除條件:連續 8 週答對率 90% 以上且沒有改判,降為每月抽考。

### G3 一人多專案的艦隊級治理(C12,部分涵蓋)

- 世界代表做法:
  - Claude Code 受管指令與受管設定(官方記憶文件,2026-10-11 讀取;來源 17):組織級 CLAUDE.md 不能被個人排除;「專案指令」設定有四種值,其中「只載入受管指令」會讓專案與使用者層的 CLAUDE.md、規則目錄、所有 AGENTS.md 都不載入;「兩者都讀」會同時載入 CLAUDE.md 與 AGENTS.md。強度 D:功能存在。深度:讀官方文件。
  - Codex 受管 hooks(官方文件,2026-10-11 讀取;來源 18):企業定義的 hooks 由政策信任、使用者關不掉;非受管 hooks 的信任綁雜湊,改了就要重新核可。強度 D。深度:讀官方文件。
  - Claude Code Projects 跨 repo(來源 8):每個 repo 一條雲端執行緒各開 PR;文件明寫「no repository's permission rules reach a cloud thread」,專案指令「are instructions Claude keeps to, not enforced settings」。強度 D。深度:讀官方文件。
  - DORA AI 能力模型(Google Cloud,2025-09-24;來源 19):七項能力含「高品質內部平台」「清楚溝通的 AI 立場」。強度 B/C:近 5,000 份問卷,沒有效果量。深度:讀官方文件。
- 為什麼對使命重要:使命寫「同時推進多個專案」,Lumos 給人的卻是 N 份各自的健康報告;而廠商跨 repo 雲端執行緒不套用各 repo 規則,Lumos 的保護在艦隊層可能整片失效。
- Lumos 現況核對(答案判「部分有」,見 G1):跨專案只有規則層的核心知識共用;`lumos enforcement`(逐層報防護有沒有生效)一次只看一個 repo。另外,Lumos 把同一段紀律同時注入 CLAUDE.md 與 AGENTS.md,也處理了 Codex 指示檔的 32 KiB 上限;但 2026-10-11 核對,受管指令載入、「兩者都讀」造成的重複載入、路徑限定規則都查無偵測。
- 以前怎麼判過:查無先例。跨專案的不變量基準線那篇是擱置狀態,條件是「核心知識的消費端多於一個再實作」。這次有新證據:四種專案指令設定、Projects 的跨 repo 限制、Cursor Projects 都沒進過圖譜。平台分發那一路對「兩者都讀會載兩次」另有條目,見 [[Projects/世界解重新註解2026-10_平台分發_調研]]。
- 最小切入點:唯讀「艦隊快照」腳本,對一份 repo 清單逐一跑 `lumos enforcement --json`、`lumos ci-status`、健檢摘要,加上 G1 的人裁佇列,彙成一張表,每週跑、跑 4 週,記「人原本不知道的異常」件數。翻紅條件:第一次跑就有專案的防護層低於宣告值而人不知道。另一條:讓 `lumos enforcement` 讀出「只載入受管指令」與「兩者都讀」兩種設定並報出來。

### G4 成本、預算與模型路由(C13,部分涵蓋)

- 世界代表做法:
  - Claude Code 成本文件(2026-10-11 讀取;來源 20):平均每位開發者每個活躍日約 13 美元、每月 150–250 美元;組織、群組、個人三層花費上限;單次執行可設美元上限;用量指令依 skill、子代理、外掛歸因;OpenTelemetry(OTel,業界通用的遙測格式)是唯一能即時串出每人 token 與成本的管道。強度 B:廠商自報。深度:讀官方文件。
  - Claude Code 原生代碼審定價(來源 21):每次平均 15–25 美元,可設每月上限,到上限就跳過並在 PR 留言。強度 B。深度:讀官方文件。
  - Bai 等〈How Do AI Agents Spend Your Money?〉(arXiv,v1 2026-04-24,v3 2026-10-02;來源 22):代理式寫程式約為聊天的 1000 倍 token;同任務可差 30 倍;準確率常在中等成本達峰後持平;模型自估 token 系統性低估。強度 A:方法公開的基準,但只讀摘要。深度:二手摘要。
  - Salim 等〈Tokenomics〉(二手報導 2026-06-11;來源 23):ChatDev 流程裡「審查」階段平均吃掉 59.4% token。強度 A-,原文未取得,未複驗。深度:二手摘要。
- 為什麼對使命重要:「同時推進多個專案」乘上「每個高風險改動多席、最多三輪」,Lumos 自己的開銷可能成為主要成本。沒有單位成本,就答不了「多席審比原生審查值不值」。

### G10 長期可維護性的趨勢量測(C19,部分涵蓋)

- 世界代表做法:
  - He、Kästner、Vasilescu 等〈Does AI-Assisted Coding Deliver?〉(MSR 2026;來源 46):807 個採用 Cursor 的開源 repo 對配對對照的雙重差分研究,速度短暫上升,靜態警告與複雜度持續上升,而且品質惡化是長期拖慢的主因。強度 A:準實驗,但只有開源、對照組不一定沒用 AI。深度:二手摘要。
  - GitClear〈The Maintainability Gap〉2026(來源 47):6.23 億次變更,重構搬移 −70%、區塊重複 +81%、兩週內改寫 +15%。強度 B,未複驗。深度:二手摘要。
  - METR 維護者審查研究(2026-03;來源 48):296 個 AI 產的 PR,維護者合併率比自動測試通過率低約 24 個百分點。強度 A-,只讀二手,未複驗。

- Lumos 現況核對(答案判「查無」,而且圖譜明文決定不做):新增告警閘只擋這次新增的告警;已超標的函式再變更複雜,告警還是同一條、算舊債不擋(覆核代理舉的例子是某函式複雜度從 26 漲到 63 沒被擋,這個數字沒重跑)。Compose 指標只對一份基準比。

- 最小切入點:不擋、不當目標,只觀察斜率,而且先回答「誰會看」——把專案已宣告 linter 的告警總數、複雜度規則命中數、兩週內被改寫的行數每週寫進評測帳,比較導入 Lumos 前後各 8 週。這跟「不追整體比率」不直接衝突(不擋、不逼改),但要先指名讀者。翻紅條件:導入後斜率高於導入前。撤除條件:8 週沒人據此行動。

## 最小切入建議(排序)

- 排序原則:對使命的衝擊 × 實驗成本 × 拖延的代價。前三項都是「先唯讀量測或探針,不先建機制」。核對後,第 1 項的範圍比研究筆記窄(推播已加框),但派工鏡頭原文與秘密掃描兩個洞是程式碼確認過的,仍排第一。

1. 毒筆記紅隊探針+合約行清洗+筆記正文掃描(G5)
   - 做什麼:驗證「能寫筆記的人能不能指揮代理或審查席」。
   - 最小版本:沿用情境探針框架,3 個毒樣本(節點名含零寬字元、合約行夾指令、看似合法的外洩規則);修法只做兩件——合約行進派工詞前過既有控制字元清洗、節點名清洗擴到 Unicode 格式字元。
   - 怎麼驗證:探針先紅(代理照做或原樣送出),修後綠;再用繞過測試確認清洗擋得住。
   - 成本與風險:低;清洗太寬可能改壞合法的中文標點,要附負樣本。
   - 以前怎麼判過:推播那條路 2026-09-06 已堵;派工鏡頭的說明自稱「零自由文字」所以沒被當成缺口。
2. 人裁佇列與艦隊快照,唯讀(G1+G3)
   - 做什麼:把各專案等人的事項與防護層狀態彙成一張表。
   - 最小版本:一支唯讀腳本讀既有帳本與 `lumos enforcement --json`,輸出機器可讀清單加白話清單;補上「該簽未簽」需要的判準。
   - 怎麼驗證:回溯 4 週,數「等人超過 7 天而人不知道」與「防護層掉了而人不知道」的件數。
   - 成本與風險:中;帳本格式多,讀錯會給假安心。
   - 以前怎麼判過:各種提醒各自都有;回訪掃描當年做過一次性清單;跨專案彙總查無先例。
3. 人裁前三問,只記不擋(G2)
   - 做什麼:量人裁點是不是在蓋章。
   - 最小版本:在簽核與跑滿裁定前由代理出 2–3 題,人答完照常放行,只記結果。
   - 怎麼驗證:4 週內有沒有「答錯但照准」。
   - 成本與風險:低;每次多花人幾分鐘,可能被當成形式而亂答,所以自評欄要跟結果比對。
   - 以前怎麼判過:查無先例。
4. 對齊原生原語,降低過時風險(跨類,由本篇觸發)
   - 做什麼:路徑規則衍生檔、情境探針改寫成外掛評測案例、`lumos enforcement` 讀出受管與「兩者都讀」設定、修 worktree 下 git 掛鉤誤報 inactive(見下一節)。
   - 怎麼驗證:在「只載入受管指令」設定下開一場工作階段問代理「改檔前要做什麼」,答不出 Lumos 紀律即紅。
   - 成本與風險:中;衍生檔是第二份真相,一定要有漂移檢查。
   - 以前怎麼判過:路徑規則這個載體 2026-09-02 提過,待裁;外掛評測當時還跑不了。
5. 每個 major 的成本,與原生審查 A/B(G4)
   - 最小版本:先讓成本欄機器取值,再做 5 個 diff 的 A/B。
   - 怎麼驗證:每個 major 的成本與抓到率對比。
   - 成本與風險:原生審查每次約 15–25 美元,5–10 個 diff 約 75–250 美元。
   - 以前怎麼判過:已排在全 repo 審視第 21 項,只在計劃。
6. 紀律版本自動尾註(G7):由提交訊息掛鉤自動補,缺漏時健檢點名。成本極低;以前因「靜默漏寫」否決過人工尾註,這版要正面回應那個理由。
7. 生產事故回放(G8):拿 3 件生產事故回放推播與合約綁定;沿用 rule-gap 欄位。
8. 模型供應商盤點(G9):列每一道送外步驟,先盤點再決定要不要做宣告。
9. 法規對照表與 CRA 24 小時演練(G6):視消費專案市場決定;結論需要專業確認。
10. 可維護性趨勢與交付成果量測(G10+G11):先指名讀者,再開帳本欄位,掛在 2026-11-30 的北極星回頭看一起看。

## 筆記與程式或來源對不上的地方

1. 研究筆記 G5 說「Lumos 會在改檔前把 repo 裡的筆記推進代理脈絡」。實際:2026-09-06 起推播只送節點名、固定字彙、合約類別,加框。建議:本篇已改寫;資安一路引用時以 hook 信任邊界那篇為準。
2. hook 信任邊界那篇正文與 `lumos dispatch-lens` 的說明文字都說派工鏡頭「零自由文字、只印固定字彙」。實際(2026-10-11 讀程式碼確認):派工鏡頭的節點內文段把合約行原文截 200 字放進派工詞,只保證取自基準版、不是被審分支。建議:立一篇 Issue,修說明或加清洗,二選一。
3. 那篇 checkout 即執行的 Issue 說錨點「分支上新增的 checkout 時點 hook 不在清單」。實際:2026-09-06 起錨點驗證會比對掛鉤目錄的實際檔案集合,多一支就紅,只是要到推送或 CI 才發現。建議:更新 Issue 正文。
4. 指令說明字典裡 `"list"` 鍵出現兩次(2026-10-11 確認),後者(合約綁測試狀態)蓋掉前者,所以 `lumos loop list --help` 印的是合約清單的說明。建議:拆成兩個不同的鍵,加一支測試防重複鍵。
5. LINE 通知的標頭寫死「今天備好 1 個待放行 spec」(2026-10-11 確認),空轉週報、考卷、探針、回放通知都共用,內容跟標頭對不上。建議:依通知種類換標頭。
6. 在共用主 checkout 掛鉤路徑的工作樹裡,`lumos enforcement` 把 git pre-commit 與 pre-push 報成 inactive,實際 git 仍會執行主 checkout 那份掛鉤。建議:偵測改成「指向任一份本 repo 的 checkout」都算接上,並註明跑的是哪一份的版本。
7. 研究筆記 G4 說「Lumos 實際每輪花費本次唯讀未量」。實際:2026-09-05 量過一次 token 基線(截圖來源,換不成美元)。建議:本篇已改寫。
8. 研究筆記 G7 的翻紅指令假設「查不出是哪個模型寫的」。實際:Claude Code 的署名尾註已記模型與會談;缺的是紀律版本與行級歸屬。建議:本篇已把切入點改成紀律版本自動尾註。
9. 研究筆記 G10 只寫「查無長期趨勢指標」,沒提圖譜有明文「不追整體比率」的立場。建議:本篇已補;下一個實作者要先回應那個立場。
10. 2026-06-19 的治理帳設計稿寫過「治理帳輪替上限 2000 筆」,程式沒做;本 repo 治理帳 2026-10-11 已約 12 萬行、19.8 MB。建議:設計稿標註未實作,或另立保存政策(接 G6)。(2026-10-13 已立設計:[[Projects/治理帳封存_計劃]])
11. 研究筆記的機制對照表把記憶過期清掃寫成「重驗剩下的價值」,沒提它的規則行已有撤除條件。建議:本篇已補,以那條撤除條件為裁定依據。
