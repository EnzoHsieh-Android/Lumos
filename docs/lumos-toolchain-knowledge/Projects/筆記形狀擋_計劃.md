# 筆記形狀擋_計劃

白話:筆記不留程式碼推得出來的東西(d1),這份先做機械上「一看就知道」的那一半:提交時擋下新寫的程式行號引用,以及沒寫出「程式碼答不了的來源」的現況描述。看意思才判得出來的那一半(推送前的 AI 審查員)在 [[Projects/筆記不存程式碼推得出的事_計劃]],兩份是 Enzo 2026-09-27 裁的拆分(Issue d7,分工以更正後的 d8 為準)——原本合在一起審了兩輪、折了 70 條還在冒,分開讓這一半先生效。

依據:[[Issues/筆記把程式現況寫進脈絡而漂移_rtb實測回饋]] 的 d1–d6 與 d8(d8 取代 d7,更正拆分分工:治理帳加鎖不在本計劃);第 2 條規則管到 FLOW/DEP 的依據是 d3(現況描述只准寫程式碼答不了的)——d6 列的「FACT 沒寫來源」是舉例,紀律範本本來就把 FACT/FLOW/DEP 同列為現況描述;前一版規則為什麼沒擋住見 [[Projects/Lumos定位_程式碼為主脈絡為輔_計劃]]〈檢討〉;下面每一條做法都已經過那份大計劃兩輪設計審(卷證 `governance/review-reports/筆記不存程式碼推得出的事/`),這裡只收跟第一層有關的結論。

## 做法

### 範圍與行(寫成一支共用函式,第二層之後直接用)

- **範圍**:
  - 提交前=暫存區差異;★正在合併(有 MERGE_HEAD)時整支跳過★並說一句(推送前會查合併結果),照每支檔有家。
  - 推送前:遠端已有那個版本就用「遠端版本..本機版本」;新分支或本機沒有遠端版本時,起點是「不在任何遠端分支上的提交」裡最早那個的上一個,全部已在遠端就不查,最早那個沒有上一個才從空樹比。合併提交只算它自己多改的行:拆出來的那支函式回傳「合併結果裡、在每一個上一版都找不到的行」,只查那些(天花板照原函式註解:解衝突時只刪不加不算寫;新寫的行剛好跟上一版別處某行一字不差會漏算)。
  - CI:推送前後兩個版本;前一版全零(新分支首推)時,那一步先 `git fetch --no-tags origin '+refs/heads/*:refs/remotes/origin/*'` 把所有遠端分支抓下來(CI 預設只抓觸發的那一條;這一步是新寫的,本 repo CI 沒有先例)、再用同一算法並排除這條分支自己的遠端參照;還是找不到其他分支時,由上線點截斷兜底。★已經在主線上的提交不重查,主線只認本地 main/master 的 upstream★(借既有 `_mainline_ref`;代碼審 r1 查出「排除所有遠端分支」可以先推到別的分支繞過,r2 查出另寫一套找主線跟既有的不一致);頂端已經包含在主線裡時(CI 推 main 時 origin/main 就是這次的頂端)不拿主線排除,否則整批不查(r2 編排者自查);CI 那步建一個追蹤 origin/main 的本地 main,給 PR 與其他分支觸發的專案用。★CI 必須抓完整歷史(`fetch-depth: 0`)★:淺層 clone 找不到上線點、也找不到「上一個提交」,會退回空樹把整庫當新增;所以 note-shape 發現自己在淺層 clone 裡(`git rev-parse --is-shallow-repository`)就不算範圍、印一句「淺層 clone 算不出範圍,這次不查;CI 請設 fetch-depth: 0」、寫一筆 skipped-env、回 0,doctor 也檢查專案 CI 有沒有設完整歷史。
  - ★三者最後都經上線點截斷★:起點早於 note-shape 上線的那個提交(提交前掛鉤第一次出現 `note-shape --staged` 字樣的提交)時,改從上線點算——上線前進來的是舊帳(d2)。這也涵蓋「整個 repo 第一次推送」與「CI 抓不到其他分支」:最壞退到上線點,不會退到空樹。
- **行**:圖譜筆記在範圍內新增或改動的行(改名用 git 的改名偵測認成同一篇,只算真正變動的行;偵測不到改名時新檔整篇算新增——方向是多查)。算不算在範圍內用「那一行落在被檢查版本的哪一塊」判,不靠解析欄位:落在正文、開頭欄位的 `summary` 區塊、`decisions` 區塊(含底下任意縮排的巢狀清單)算;落在其他開頭欄位不算;`decisions` 區塊裡鍵名是 id、decided、valid、superseded_by 這類結構鍵的行不算。刪掉的檔不算。
- ★程式碼圍欄裡的行照樣查★(原稿不查,r1 三席指出包進圍欄就一鍵繞過、圍欄沒關好連後面都看不到)。貼在圍欄裡的舊輸出若帶行號,一樣要釘版本或拿掉——它同樣會跟現在的程式對不上。圍欄只用來判「這一行是不是 `FACT:` 開頭的摘要行」這類結構。
- 筆記檔讀不成 UTF-8:整支擋下並講是哪支檔。

### 兩條規則(`lumos note-shape`,提交前 `--staged`、推送前與 CI `--diff <範圍>`)

1. **程式行號引用**:`路徑:數字`、`路徑#L數字`,反引號包著或裸寫都算。裸寫的候選規則:前面是行首、空白、中文字或標點,後面是 `:數字` 或 `#L數字`;路徑含 `/` 時要在被檢查的版本裡真的存在;沒有 `/` 的單一檔名(例如 `daily-governance.sh:26`)只有在 repo 追蹤的程式檔裡恰好一支叫這個名字時才算。★路徑必須在被檢查的版本裡真的存在★、是程式檔或測試檔(副檔名清單或開頭 `#!`,內容從被檢查的版本讀;只排除 `.md` 等文件)。不存在的路徑(舉例、別的專案)這一刻不擋——但見下面「新程式檔喚醒舊引用」。**放行寫法** `路徑@<提交>:數字`:`<提交>` 必須是至少 12 位的十六進位提交編號、解析出來的完整編號真的以這串開頭(擋掉剛好取名成十六進位的分支或標籤)、★這個提交在某個本機分支或遠端追蹤分支的歷史上★(擋掉在本機用 `git commit-tree` 捏造、從沒進過任何分支的提交)、那個提交裡有這個路徑、行號在那個版本的檔長之內(用 `_validate_repo_ref` 帶 `at_sha` 驗);`HEAD`、分支名、標籤、`main~1` 這類會移動的名字寫成 `@` 形狀時照樣擋。同一套拆解也讓 `lumos refcheck` 與設計審放行前的引用檢查對釘版本的引用改成對那個提交驗,不再把它當成一支不存在的檔。要指到測試就寫測試名。
   **新程式檔喚醒舊引用**:範圍內有路徑「起點版本不是程式檔、終點版本是」(新增、改名過來、加了 `#!`、檔案類型改變都算,照每支檔有家對 A/M/T/R 的判法)時,用 `git grep` 在終點版本的筆記裡找指向這些路徑、沒釘版本的行號引用;★那一行在 note-shape 上線點的版本裡就已經有的不算★(舊帳,d2),其餘就擋——先寫引用、後加檔案的兩步走照樣抓得到。成本跟這次變成程式檔的路徑數成正比,不是每次全庫掃。
2. **現況類前綴沒寫出程式碼答不了的來源**:★只看開頭欄位 `summary` 區塊裡★新增的 `FACT:` `FLOW:` `DEP:` 行(寫在正文裡、長得像摘要行的舊寫法不在這條範圍,交給第二層;FLOW、DEP 納進來的依據是 d3——紀律範本本來就把 FACT/FLOW/DEP 同列為現況描述),要帶 `[來源:部署]` `[來源:資料庫]` `[來源:生產]` `[來源:外部]` `[來源:人工]` 其中之一(d3;五類對應紀律範本「程式碼答不了」那一句列的部署設定、資料庫實際值、生產觀測、外部、人工核可)。★不用 `[src:]`★——那個標記已經是「從程式碼重建的筆記」指向程式位置的出處標記,帶 `regen` 的筆記會把 `[src:部署]` 當成一支叫「部署」的檔去找而判成幻覺證據(r1 三席)。只寫「以程式碼為準」加查詢不再算數。實作是改既有 `_CONTEXT_MARKER_RULES` 的 FACT 規則並加上 FLOW、DEP 兩條(只給 note-shape 用,見 PRIOR-ART ⑦),所以 FACT 行 `lumos lint` 對整篇、note-shape 對新增行判的是同一套;FLOW、DEP 只有 note-shape 看新增行。

回傳碼照鄰居:0 過、1 擋、2 參數錯;不是 git 或找不到 lumos 就放行並說一句。hook 只認 1 為擋。閘名 `note-shape` 登記進既有閘名單;★只有擋下(blocked)與環境變數或淺層 clone 跳過(skipped-env)寫事件,放行不寫★(2026-10-03 起例外:推送時舊行尾補括號減掉違規記 relaxed,見 [[Projects/舊行尾追加不算新寫_計劃]])(刻意跟每支檔有家每次都寫 passed 不同)——每次提交都寫一筆會讓治理帳多一堆沒資訊的行(rtb 回饋第 4 項抱怨的正是這種重複),也會讓工作樹每次多一行未提交的帳。寫帳走 `_gate_event`,寫帳失敗照它的契約不改變擋不擋。擋下訊息列出每一處(檔、行、哪條規則、怎麼改),並明講「內容還在工作目錄,改完再提交」;hook 不改筆記、不動暫存區(治理帳那一行照既有各閘的慣例是簿記檔)。

**開關與跳過**:`note_shape.gate`:block(預設)/ warn / off,★從被檢查的版本讀★(提交前讀暫存區、推送前與 CI 讀頂端提交),工作樹裡沒暫存的 off 關不掉它;不是 block 時 `lumos doctor` 每次印一行(照 `node_home.gate`)。環境變數 `LUMOS_SKIP_NOTE_SHAPE=1` 單次跳過,寫一筆 `skipped-env` 事件。RETIRE-IF ① 的「繞過次數」= skipped-env 事件數 + doctor 看到的非 block 專案數 + doctor 事後掃到的繞過行數。

### 治理帳寫入加鎖(移出)

原稿把「替治理帳寫入加鎖」放在這裡;r1 七席有四席指出它動的是所有閘共用的寫入器、會把寫帳問題變成擋人、還漏了其他寫入者。它跟本計劃要擋的東西無關,已移到 [[Issues/治理帳多個寫入者都沒上鎖]] 另外處理;本計劃照既有寫入器現況寫帳。

### 紀律範本改寫

紀律範本〈寫筆記時〉那張表的 `FACT:` `FLOW:` `DEP:` 整列改成 d3 的收窄說法:只准寫程式碼答不了的現況,要帶 `[來源:…]`;程式碼查得到的一律不寫。同一節寫明第一層會擋哪兩種形狀、放行寫法、開關與跳過。各專案各自跑 `lumos update` 拉新版。skill 裡只指路、不放第二份定義;★`lumos-project-notes` skill 裡還在教舊寫法的地方一起改★:reference.md 的 FACT 範例格與 Systems 寫法那句、commands/INDEX.md 的三條核心規矩裡「標以程式碼為準並加查詢」那條——不然新人照官方入口寫的第一句就被擋。

### 消費專案的 CI

`lumos update` 不會動各專案的 CI 設定檔。所以 `lumos doctor` 檢查專案 CI 有沒有呼叫 `note-shape --diff`,沒有就每次印一行並給要貼的那一步(含「先抓所有遠端分支」);另外 doctor 對上線點之後、已推上遠端的提交跑一次 note-shape,有違規就列出來(抓 `--no-verify` 繞過)。工具鏈自己的 CI 手動加那一步。

## 條款

- [S1] 若新增行(含圍欄內)有指向被檢查版本裡真的存在的程式檔或測試檔的行號引用(反引號或裸寫;含沒有副檔名、開頭是 `#!` 的主程式;單一檔名要恰好對到一支),則 note-shape 應擋下並列出每一處;指向不存在路徑或 `.md` 的、沒改動的舊行不應擋 [test:t_note_shape_line_refs_existing_code_new_only]

## 回退

照這個順序,反過來會卡住別人推送:
1. 先拿掉工具鏈自己 `.github/workflows/ci.yml` 裡的 note-shape 那一步(這支檔不在 `lumos update` 同步清單裡,要手改)。
2. 消費專案不用等中心:各自把 `note_shape.gate` 設成 off(要提交才生效)就停。
3. 拿掉提交前與推送前 hook 裡的呼叫;★note-shape 指令改成只印「已撤除」並回 0,而且永久保留★——消費專案自己貼在 CI 裡的那一步不受 `lumos update` 管,工具鏈這邊看不到它們有沒有拿掉,指令一刪它們的 CI 就每次紅;空殼幾行程式,留著沒有成本。
4. `_CONTEXT_MARKER_RULES` 的 FACT 規則改回舊判準、拿掉 FLOW/DEP 那兩條;抽取器的三個選項、上線點函式的標記參數、合併函式拆出的那支都可以留著(預設值就是原行為);★釘版本解析要留★——拿掉的話,已經寫進筆記的 `路徑@<提交>:數字` 會被 refcheck 當成不存在的檔。
5. 紀律範本那列改回舊句時要先想好:舊句正是讓現況描述留存的出口(見〈檢討〉第 4 點)。
6. 被擋下的內容從沒進過 git,只在作者的工作目錄。

## 實務隱患

- 守衛面:新的擋人機制,誤擋會讓人習慣繞過——所以只看新行、上線前的舊帳截掉、合併不重查、不存在的路徑與文件路徑不擋、有嚴格驗過的釘版本寫法、有開關與跳過且都看得見,全部進 RETIRE-IF ①。
- 資源併發:note-shape 只讀不寫筆記;寫治理帳照既有寫入器現況(那個寫入器本身沒鎖的問題另記在 [[Issues/治理帳多個寫入者都沒上鎖]],本計劃只在擋下、warn 模式的違規提醒與跳過(環境變數、淺層 clone)時各寫一筆,沒違規的放行不寫(2026-10-03 起另有 relaxed 例外,見 [[Projects/舊行尾追加不算新寫_計劃]]),頻率略增,那篇已註明)。擋下時治理帳會多一行未提交的內容:這跟每支檔有家等既有閘擋下時的行為一樣,治理帳本來就是會隨提交一起進版控的簿記檔,之後被一般提交帶進去不會誤導任何讀者(那一行記的就是一次真實的擋下)。
- 已排除:對外送出:只在本機讀 git 與檔案,不送任何內容到外部服務
- 已排除:不可逆:擋下時不產生提交、hook 不動工作目錄,內容留在作者手上;拿掉閘並照回退順序做就恢復原狀,沒有留下拿不掉的機制
- 已排除:金流:不碰任何付款或計費流程

## 誠實界線

- 這一層只擋兩種形狀;rtb 稽核裡漂移最多的「目前沒有 / 只有 N 種」句型、貼錯標籤的 WHY 行、done 計劃的現況段,形狀都不固定(句型比對抽樣準度約三分之一),要等第二層。在第二層上線前,這些照樣寫得進去。
- 行號引用的抽樣 12/12 是單人目測、樣本小;把圍欄也納入後,貼在圍欄裡的舊輸出會被擋,這部分沒有抽樣過,是 RETIRE-IF ① 要盯的誤擋來源。
- 沒有接 CI 的消費專案,`--no-verify` 推上去當下擋不住;doctor 事後會列出來,但那時已經在遠端了。
