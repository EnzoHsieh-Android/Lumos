# 後端工程提問與證據擴充_計劃

> 白話:讓 Lumos 能帶著 AI 做完一個後端功能的整個過程,但不另蓋一套系統。三件事要補:①開工前 AI 自己找出需求缺口,先自己查,真的要人決定的才問,而且依階段問,不是一開始全丟出來;②知道「這個問題要什麼證據、哪個工具拿得到」,碰真實資料庫或壓測時有權限邊界;③「做完了」要有真的跑過的證據——沿用既有的測試綁定與破壞測試,AI 自己寫的數字不算。示範載體是另開 repo 的高併發訂單系統,但三件事都不綁訂單業務。

## 緣起與現況(2026-10-12 盤點)

- 起點:2026-10-12 使用者在對話中貼了一份任務書(下稱「任務書」,原文沒有進 repo),要 Lumos 延伸成能驅動後端開發全流程的工具,要求先盤點、不重造。本篇用到它的三樣東西:①提問九類——需求、架構、一致性、併發、失敗、擴展、安全、維運、驗證;②七道驗收關卡——需求就緒、架構就緒、實作就緒、功能驗證、可靠性驗證、效能驗證、交付就緒;③示範情境——高併發訂單系統(庫存 100、同時 1000 筆下單不得超賣、冪等鍵、非同步故障、壓測、故障注入)。
- 盤點方式:四個唯讀代理各拿原始問題分頭查(規格與提問、驗證與證據、掛鉤與權限、後端棧與評測),結論都附函式名。以下是摘要;現況以程式碼為準。

## 做法

### A. 情境出題(Question Orchestration)

- **題目住哪**:計劃筆記一節 `## 待決問題`,一題一行,文法:
  `- [Q<n>] <問題> [類:<值>][階段:<值>][狀態:<值>]` 之後可接 `[阻塞]` `[不可逆]` 兩個旗標、`→ <連結>`、`出處:<…>`、`理由:<…>`、`測試:<測試名>`。
  - 方括號標記順序不拘;只認上面列的鍵,其他方括號文字算題目內文。一題一行,同一節 `Q` 編號不得重複(重複=lint 錯)。
  - `類` 起始值域是任務書的提問九類(見緣起);`階段` 取 需求/架構/實作/驗證/效能/交付。
  - `狀態` 六種與各自必附:待查、待人(無);自答=`出處:`(檔與函式、節點連結或指令,至少 4 字);延後=`理由:`(至少 4 字);已決=`→` 指到一條存在且 `valid: true` 的決策(`#dN` 指本篇,`[[節點]]#dN` 指別篇);已驗=已決的連結再加 `測試:`,那個測試名必須出現在本篇某條驗收條款的 `[test:]` 裡(lint 只驗出現;測試真的綠不綠由規格閘跑(綁成 ★INVARIANT★ 合約的另由推送前綁定測試閘重跑,見 C),不在 lint 重判)。
  - 標 `[不可逆]` 的題不得是自答——不可逆的決定一律要人裁;標 `[阻塞]` 的題不得是延後——延後就代表它不阻塞,兩者矛盾。
  - 不另設「誰答」欄:狀態本身就說明誰在答(待人=人、自答=AI),兩欄並存會互相矛盾。
- **題目從哪來**:新開一張結構化的「需求風險面」表 `_REQUIREMENT_FACETS`,條目形狀沿用棧別題庫 `_STACK_QUESTION_SPECS` 的鍵(`id`、`q`、`when`),多一個 `stage` 鍵標它屬哪個階段;`when` 比對計劃筆記文字。它不混進計劃稿題庫 `_PITFALL_QUESTIONS`,也不是規格閘的風險類(不進 `_DOOR_CLASS_ZH`)。每個風險面是「什麼情況下要釐清什麼」,AI 依當下需求、既有決策、程式碼、工具查得到的事實寫成具體問題。表的內容源與挑選理由寫進新開的 Systems/情境出題。
- **先查後問**:題目出生時先試著自己答;答得了的(圖譜、程式碼、工具查得到、規格推得出、有安全預設)標自答並附出處。只有業務規則、成本、風險接受度、不可逆決定、產品行為,且證據定不了的,才標待人。
- **排序規則(透明、不打分)**:待人的題目依序 ①標阻塞的 ②標不可逆的 ③其餘,同級照編號;一次最多列三題給人,其餘標「下一輪」。
- **時機(新做)**:`lumos pitfalls <計劃筆記路徑>` 新增 `--stage <階段>`,只列那一階段的風險面與那一階段還沒結的題;不帶 `--stage` 時輸出與現行逐位元相同;`--stage` 給了不認得的值、或與 `--diff` 一起用,回 2。規格閘直接讀〈待決問題〉(不呼叫 pitfalls);實作與之後的階段,由人或 AI 在進那個階段前跑 `lumos pitfalls <計劃筆記路徑> --stage <階段>`(`pitfalls --diff` 只收改動範圍、不接計劃,不改它)。
- **機械把關**:
  - 規格閘:做成規格閘前段的一步,跟條款綁定檢查同一層(風險高低都擋,印出原因回 1);放在「沒有條款就提早結束」與 `--no-run` 提早結束之前,所以只有〈待決問題〉、沒有條款的計劃也會被擋。擋的是:有標阻塞、階段是需求或架構、狀態是待查或待人的題;其他階段的阻塞題不擋規格閘。
  - 解析只寫一份:規格閘、lint、`pitfalls --stage` 三處共用一支只吃文字的解析函式(照條款解析被規格閘、處置閘、筆記形狀共用的既有做法);「決策存在且有效」「測試名在本篇條款裡」這類要讀圖譜的檢查只放規格閘與 lint,`pitfalls` 本來就不讀圖譜,不做這兩項。
  - lint:照新增 lint 規則的既有做法掛在新規則那一路,擋不擋跟著專案的 `note_lint.gate`(沒設就只提醒;本 repo 設 on,所以在本 repo 是報錯)。每行照上面的文法與「必附」驗;已決指到不存在或已作廢的決策、自答沒出處、延後沒理由、不可逆卻自答、阻塞卻延後、已驗的測試名不在本篇條款裡,都報錯。
- **決策紀錄不加欄位**:題目到決策是單向指針(題目行 `→ #dN`),不在決策上加反向的「回答哪題」欄——照計劃側不設 `fulfilled_by` 鏡像欄位的既有規矩,雙寫必漂移;不選的方案照既有慣例寫進 `why_chosen` 的「不選:」。
- **先量再接**:A 塊的程式動工前,先用情境探針做最小對照:同一組刻意不完整的後端需求(至少 6 題,含任務書的訂單需求與兩題非訂單業務),甲組照現行流程、乙組多帶風險面與〈待決問題〉寫法,各跑 3 次;判準事先寫好=「該被問到的人決定」清單命中數,與「不該問人卻問了」的題數。乙組命中沒有多於甲組、或亂問多於甲組,A 塊不接進規格閘,只留寫法說明,回報人裁。

### C. 驗收證據(沿用既有機制,決策 d6)

- **功能、併發、冪等、故障恢復**:寫成示範 repo 的測試(JUnit + Testcontainers),綁在示範 repo 自己計劃筆記的驗收條款 `[test:]` 上,規格閘真跑一次並留痕(留痕只存測試名與紅燈數)。推送前綁定測試閘只重跑 ★INVARIANT★ 合約綁的測試,不重跑計劃條款綁的測試;計劃條款的測試只有風險低的計劃才在推送時重跑。所以示範的三條核心行為——不超賣、同一冪等鍵不重複建單也不重複扣庫存、事件重送不重複產生業務效果——要在示範 repo 寫成 ★INVARIANT★ 合約並綁測試,推送時才保證每次都重跑;其他條款測試靠規格閘或人手動重跑。併發測試只斷言次數與最終狀態(成功訂單數、庫存),不斷言毫秒——照 [[Projects/併發與效能表態要合約背書_計劃]] 的裁定,次數型才進推送關卡。
- **故障注入**:不變式(例如「成功訂單數不得超過初始庫存」)在示範 repo 標 ★INVARIANT★ 並綁併發測試,用既有的 `lumos guard kill-add` 宣告「拿掉庫存競爭保護」這條壞法,`lumos guard kill` 在隔離工作目錄跑出 killed,證明那支測試咬得住;還原後同一測試與回歸再跑綠。破壞測試在最新提交的乾淨工作目錄裡跑,被忽略的本機設定檔不在裡面——示範的測試只靠環境變數或 Testcontainers 動態產生的帳密,配方與測試要先提交。
- **壓測**:k6 跑在本機 Docker 環境,門檻寫進腳本(門檻沒過 k6 會回非零);毫秒數字不進推送關卡,條款標 `[manual:]`,k6 的摘要檔與 JUnit 報告存在示範 repo 的報告目錄,交付報告列出數字、指令與檔案雜湊。
- **MCP 拿到的資料**:要當驗收依據的,一律寫成測試或指令重跑(例如測試裡直接查資料庫最終狀態);MCP 回傳值本身不當證據(事件帳外掛不存回傳值,見 Q3)。
- **交付報告**:示範 repo 的 Markdown 報告,由 `lumos spec-trace` 的輸出、測試報告與破壞測試的判定組成;不另做產生器。

## 實務隱患

- 併發:〈待決問題〉的檢查只讀計劃筆記、不寫共用檔,沒有並行寫入面;示範 repo 的併發安全由 S5 的測試與 S6 的破壞測試證明。

- 秘密:示範 repo 的資料庫帳密一律走環境變數(測試用 Testcontainers 動態產生的帳密),不進版控;測試不得依賴被忽略的本機設定檔(破壞測試的乾淨工作目錄裡沒有它);k6 與測試報告不印連線字串。
- 不可逆:MCP 能對真實系統下指令。處理:寫入類 MCP 設成每次詢問(B);示範 repo 只連本機 Docker;正式環境只給唯讀帳號。
- 已排除:金流:本案與示範都不含付款流程(訂單只到建立與扣庫存)。
- 已排除:對外送出:壓測只打本機環境,示範的埠只綁 127.0.0.1,k6 腳本非 localhost 就中止;不寄信、不推通知、不呼叫第三方。
- 守衛面:本案會改規格閘(新加一條擋法)與 lint 規則,誤擋會訓練人繞過——沒有〈待決問題〉一節的計劃行為不變(S1)、不帶 `--stage` 輸出不變(S3),兩塊各自一個提交以便單獨回退。

- 不把毫秒門檻放進推送關卡。
- 不在決策紀錄加反向欄位。

## 回退

- 第 3 階段兩塊各自一個提交,可單獨回退:
  - Spring 觸發詞:回退那組觸發詞與它的測試;已寫進治理帳的表態紀錄留著(題目 id 不變)。
  - 情境出題:回退規格閘那一條擋法、lint 規則、`--stage` 與風險面表;計劃裡已寫的〈待決問題〉留著當散文,舊判定不認得這一節,不會因它擋。
- 2.5 階段實驗沒過門檻時,S1–S3 在同一個提交改成 `[manual: 未接線,見出題實驗的驗證筆記]`;回退情境出題或 Spring 觸發詞時,對應條款同樣改寫,不留指向已刪測試的綁定。
- 舊否決復活:作廢指令不讓已被翻案的舊決策再翻回來,所以做法是在 [[Systems/開發工作流總覽]] 用 `lumos decision-add` 新記一條「計劃節點不做模板化盤問」(context 寫明是復活、指回原 d1 與本篇),再用 `lumos decision-supersede` 把本篇 d1 作廢、指向那條新決策。
