# 後端工程提問與證據擴充_計劃

> 白話:讓 Lumos 能帶著 AI 做完一個後端功能的整個過程,但不另蓋一套系統。三件事要補:①開工前 AI 自己找出需求缺口,先自己查,真的要人決定的才問,而且依階段問,不是一開始全丟出來;②知道「這個問題要什麼證據、哪個工具拿得到」,碰真實資料庫或壓測時有權限邊界;③「做完了」要有機器擷取的原始輸出當證據,AI 自己寫的數字不算。示範載體是另開 repo 的高併發訂單系統,但三件事都不綁訂單業務。

## 緣起與現況(2026-10-12 盤點)

- 起點:2026-10-12 使用者在對話中貼了一份任務書(下稱「任務書」,原文沒有進 repo),要 Lumos 延伸成能驅動後端開發全流程的工具,要求先盤點、不重造。本篇用到它的三樣東西:①提問九類——需求、架構、一致性、併發、失敗、擴展、安全、維運、驗證;②七道驗收關卡——需求就緒、架構就緒、實作就緒、功能驗證、可靠性驗證、效能驗證、交付就緒;③示範情境——高併發訂單系統(庫存 100、同時 1000 筆下單不得超賣、冪等鍵、非同步故障、壓測、故障注入)。
- 盤點方式:四個唯讀代理各拿原始問題分頭查(規格與提問、驗證與證據、掛鉤與權限、後端棧與評測),結論都附函式名。以下是摘要;現況以程式碼為準。
- **已經有、直接用**:
  - 計劃筆記+規格閘([[Systems/規格閘]]):依關鍵字判風險,低風險直接做、高風險進多席審查(輪數上限寫在 `_TIER_PARAMS`,滿了交人)。
  - 兩套固定題庫:計劃稿階段的 `_PITFALL_GENERAL` / `_PITFALL_QUESTIONS`(四種風險類,關鍵字觸發),改檔與推送階段的 `_STACK_QUESTION_SPECS`(九種棧,Java 七題,內容源 [[Systems/效能檢核目錄]]);推送前每題表態([[Systems/棧別提問表態閘]])。
  - 合約綁測試、推送前真跑([[Systems/bound-tests-gate]]);破壞測試([[Systems/guard-kill]])在隔離工作目錄把保護拿掉、要求測試變紅——這就是任務書「故障注入」情境要的工具。
  - 決策紀錄(`cmd_decision_add`):內容、背景、理由、日期、有效與否。
  - AI 行為評測(情境探針,[[Systems/ablation-lumos-first]]):無人看守地出題、用規則判工具呼叫順序。
- **部分有、要擴**:
  - 驗證筆記的狀態只有 pass/stale/superseded/pending/abandoned(`_STATUS_ENUM`),寫不出「失敗」;新建範本預設 pass;原始輸出、環境、預期對實際只在正文散文裡。
  - 決策紀錄沒有「回答哪一題、誰決定、否決了哪些選項」三個欄位。
  - 工具呼叫紀錄([[Systems/lumos事件帳]] 那個外掛)只記指令前 500 字,不遮蔽敏感資訊。
- **完全沒有**:
  - 拿需求找缺口、排優先、分階段出題(計劃稿題庫只看關鍵字,`--check` 只驗有沒有〈實務隱患〉小節)。
  - MCP 整合、工具能力清單、工具權限政策(唯一的工具限制在審查子代理身上,見 [[Systems/lumos-guard]])。
  - 破壞性操作要人核准、敏感資訊遮蔽。
  - 「計劃標完成前必須有對應證據」的檢查。
  - Spring Boot、Docker、壓測、應用可觀測性的支援;任何示範後端專案。

## 做法

### A. 情境出題(Question Orchestration)

- **題目住哪**:計劃筆記一節 `## 待決問題`,一題一行,文法:
  `- [Q<n>] <問題> [類:<值>][階段:<值>][狀態:<值>]` 之後可接 `[阻塞]` `[不可逆]` `[要驗]` 三個旗標、`→ <連結>`、`出處:<…>`、`理由:<…>`、`證據:<證據編號>`。
  - 方括號標記順序不拘;只認上面列的鍵,其他方括號文字算題目內文。一題一行,同一節 `Q` 編號不得重複(重複=lint 錯)。
  - `類` 起始值域是任務書的提問九類(見緣起);`階段` 取 需求/架構/實作/驗證/效能/交付。
  - `狀態` 六種與各自必附:待查、待人(無);自答=`出處:`(檔與函式、節點連結或指令,至少 4 字);延後=`理由:`(至少 4 字);已決=`→` 指到一條存在且 `valid: true` 的決策(`#dN` 指本篇,`[[節點]]#dN` 指別篇);已驗=已決的連結再加 `證據:` 一個有效證據編號(有效的定義見 C)。
  - 標 `[不可逆]` 的題不得是自答——不可逆的決定一律要人裁。
  - 不另設「誰答」欄:狀態本身就說明誰在答(待人=人、自答=AI),兩欄並存會互相矛盾。
- **題目從哪來**:新開一張結構化的「需求風險面」表 `_REQUIREMENT_FACETS`,形狀照棧別題庫 `_STACK_QUESTION_SPECS` 的條目寫法(`{id, stage, ask, when[]}`,`when` 比對計劃筆記文字),不混進計劃稿題庫 `_PITFALL_QUESTIONS`,也不是規格閘的風險類(不進 `_DOOR_CLASS_ZH`)。每個風險面是「什麼情況下要釐清什麼」,AI 依當下需求、既有決策、程式碼、工具查得到的事實寫成具體問題。表的內容源與挑選理由寫進新開的 Systems/情境出題。
- **先查後問**:題目出生時先試著自己答;答得了的(圖譜、程式碼、工具查得到、規格推得出、有安全預設)標自答並附出處。只有業務規則、成本、風險接受度、不可逆決定、產品行為,且證據定不了的,才標待人。
- **排序規則(透明、不打分)**:待人的題目依序 ①標阻塞的 ②標不可逆的 ③其餘,同級照編號;一次最多列三題給人,其餘標「下一輪」。
- **時機(新做)**:`lumos pitfalls <計劃>` 新增 `--stage <階段>`,只列那一階段的風險面與那一階段還沒結的題;不帶 `--stage` 時輸出與現行逐位元相同。規格閘呼叫時帶需求與架構;交付檢查帶驗證、效能、交付;實作階段由人或 AI 在動手前跑 `lumos pitfalls <計劃> --stage 實作`(`pitfalls --diff` 只收改動範圍、不接計劃,不改它)。
- **機械把關**:
  - 規格閘(風險高低兩種門都適用,這是現行風險高「只印不擋」之外新加的一條擋法,回 1):有標阻塞、階段是需求或架構、狀態是待查或待人的題,不放行;其他階段的阻塞題留到交付檢查。
  - lint:每行照上面的文法與「必附」驗;已決指到不存在或已作廢的決策、自答沒出處、延後沒理由、不可逆卻自答,都報錯。
  - 交付檢查:見 D。
- **決策紀錄不加欄位**:題目到決策是單向指針(題目行 `→ #dN`),不在決策上加反向的「回答哪題」欄——照計劃側不設 `fulfilled_by` 鏡像欄位的既有規矩,雙寫必漂移;不選的方案照既有慣例寫進 `why_chosen` 的「不選:」。
- **先量再接**:A 塊的程式動工前,先用情境探針做最小對照:同一組刻意不完整的後端需求(至少 6 題,含任務書的訂單需求與兩題非訂單業務),甲組照現行流程、乙組多帶風險面與〈待決問題〉寫法,各跑 3 次;判準事先寫好=「該被問到的人決定」清單命中數,與「不該問人卻問了」的題數。乙組命中沒有多於甲組、或亂問多於甲組,A 塊不接進規格閘,只留寫法說明,回報人裁。

### B. 工具與權限(MCP Orchestration)

- **不做指令、不加設定區塊**(決策 d5)。第 2 階段的工具調查寫成調研筆記(Projects/後端MCP能力矩陣_調研):每個候選 MCP 的維護者、是否持續維護、實際工具清單(照實際安裝後列出,不照文件抄)、權限需求、適不適合本機示範、更簡單的替代(CLI/SDK),分「已確認/要設定/不支援/未驗」四格。
- **權限說明**寫進 Systems/證據擷取:哪類 MCP 工具(寫入、執行、管理)要在 Claude Code 的設定裡設成每次詢問;Codex 對應的核准設定在第 2 階段查證後補上。正式環境的連線只給唯讀帳號,寫進示範 repo 的環境設定範本。
- **證據擷取不能當權限的後門**:`lumos evidence run` 開頭不得加進 Claude Code 的允許清單(加了,包在它後面的任何指令都會跳過詢問);這條寫進說明,也寫進 `lumos evidence run --help`。
- **防失控**:單次 MCP 呼叫的重試由 Claude Code 自己管,Lumos 管不到;Lumos 管的是證據層的停止條件(E)。

### C. 證據擷取(Evidence-Based Verification)

- **指令**:`lumos evidence run --criterion <計劃>#S<n> [--env <名>] [--expect-exit <碼>] [--expect-match <正規式>] [--timeout <秒>] -- <程式> <參數…>`;另有 `lumos evidence void <證據編號> --reason "<至少 4 字>"`(更正記錯的列,追加一列作廢,不刪舊列)。頂層只多一個 `evidence` 指令。
- **怎麼跑**(照破壞測試 `_kill_run` 的子程序寫法,但改掉它不合用的兩處):
  - 直接執行參數清單、不經 shell;stdin 接空裝置;開新的程序群組,逾時(預設 600 秒)整群殺掉。
  - 找不到程式、沒有執行權限、逾時、被訊號殺掉(退出碼為負)、Lumos 自己被 Ctrl-C 中斷——一律記一列 BLOCKED(中斷時先寫帳再以 130 結束),不算 FAIL。
  - 結果:退出碼等於 `--expect-exit`(預設 0)且(沒給 `--expect-match` 或比對成立)=PASS,否則 FAIL;AI 不能手填結果。沒給 `--expect-match` 的 PASS 標 `weak: true`,交付檢查不認弱證據。
  - 回傳碼照既有慣例:PASS 回 0;FAIL 或 BLOCKED 回 1;證據帳寫不進去回 2(帳寫不進就不算取證,不能像治理帳事件那樣「寫失敗只警告、不改判定」)。
- **原始輸出**(決策 d4):stdout 與 stderr 各自以位元組原樣串流寫進本機的 `.lumos/evidence/<證據編號>/`(不解碼,二進位與非 UTF-8 都不壞);比對在串流時逐行做,判定先於截斷。單一串流超過 50MB 時,檔案只留頭尾各 1MB 並標截斷,帳上照記完整串流的雜湊與位元組數。`lumos init` 與 `lumos update` 把 `.lumos/evidence/` 加進忽略清單。
- **證據帳**:docs 目錄下的 .evidence-log.jsonl(照既有帳檔的命名),進版控、CI 讀得到。
  - 欄位:編號、時間、條款、環境名、指令(顯示用,遮蔽後截到 1000 字;完整參數存原始檔目錄)、工作目錄、退出碼、訊號、是否逾時、預期退出碼、比對規則、結果、弱證據旗標、髒樹旗標、HEAD、程式內容指紋、兩個串流的雜湊與位元組數、截斷旗標、原始檔目錄、工具名、Lumos 版本。
  - 單列保證小於 4KB(既有追加寫法 `_ledger_append` 的上限),超過的欄位只留在原始檔目錄;追加用單次寫入,帳檔不存在時建立。
  - 證據編號=`e-<UTC 時間>-<8 位隨機十六進位>`,原始檔目錄用「不存在才建立」的方式開,撞名就換號重試;不採「讀帳取最大號加一」。
  - 帳檔加進 `_BOOKKEEPING_FILES`(不然每次提交帳檔,代碼審留痕就失效),同時對照它的三個使用者(小改動閘、風險掃描、推送前測試範圍)與 cochange 的預設排除清單;消費專案 docs 目錄的忽略清單範本不得忽略它。
  - 每個專案的 CLI 是提交進 repo 的同一份副本,同一 repo 內不會有新舊版本混用;升級前的舊版不認得這本帳,只會忽略它。
- **新舊怎麼判**:證據列記「程式內容指紋」——HEAD 的 `git ls-files -s`(檔案模式、內容雜湊、路徑)排除知識圖譜目錄、`governance/`、`.lumos/` 與簿記名單後算 sha256。內容一樣指紋就一樣,所以提交筆記、改帳本、壓提交、rebase 都不會讓證據過期;改到程式才會。跑的當下工作樹有未提交的程式改動,列上標髒樹,這列不算數。
- **遮蔽**(帳上的指令與摘要,以及原始檔都套):名字含 TOKEN、PASSWORD、PASSWD、SECRET、KEY、CREDENTIAL 的環境變數,值至少 8 字的換成遮罩(短值不換,避免把數字證據毀掉);網址裡 `帳號:密碼@` 的密碼;`Authorization:` 標頭的值;`--password=`、`-p<值>` 這類參數的值。遮蔽抓不全,但原始檔不離開本機,外流面只剩帳上截短過的指令與摘要。
- **MCP 拿到的資料**:用等價的 CLI 走 `evidence run` 重跑一次留證;MCP 的回傳值本身不當證據(事件帳外掛不存回傳值,見 Q3)。
- **驗證筆記不動**(決策 d3):狀態值、範本、`lumos set` 對驗證筆記的行為全部照舊;驗證筆記要引證據,就在正文寫證據編號。

### D. 七道關卡對到哪裡

| 任務書的關卡 | 落在 | 新增什麼 |
|---|---|---|
| 1 需求就緒 | 規格閘 | 需求與架構階段的阻塞題未決不放行(A) |
| 2 架構就緒 | 規格閘+多席審查 | 架構類題目要有比較;決策照既有「不選」慣例 |
| 3 實作就緒 | 表態閘 | 棧別題庫的 java 題組補 Spring 觸發詞(看改動行) |
| 4 功能 / 5 可靠 | 綁定測試+破壞測試 | 無,沿用 |
| 6 效能 | 證據擷取 | k6 輸出走 `evidence run`,只當交付證據,不進推送關卡 |
| 7 交付 | 交付檢查(新) | 見下 |

- **交付檢查**=`lumos spec-trace <計劃> --delivery`,不另開指令;不帶 `--delivery` 時 `spec-trace` 的行為與輸出不變。
  - 條款可以綁 `[evidence]`(不帶參數;證據列用 `--criterion` 指回條款)。設計期它算「已綁定」(新狀態「待證據」),跟 `[test:]`、`[manual:]` 並列;風險低的門照現行規矩只收 `[test:]`,`[evidence]` 跟 `[manual:]` 一樣不讓風險低放行。要同步改的有:合法標籤集合 `INV_TAG_RE`、條款綁定判定 `clause_bindings` 與它的狀態中文表、規格閘的條款文法檢查,以及兩份技能說明裡「條款只寫 `[test:]` 或 `[manual:]`」的句子。
  - `--delivery` 時要過四件事:①每條 `[evidence]` 條款,最新一列非作廢、非弱、非髒樹的證據是 PASS,且指紋等於現在的程式內容指紋;②〈待決問題〉標 `[要驗]` 的題都是已驗、而且引的證據編號符合①;③沒有任何階段的阻塞題還沒結;④沒有條款處在 E 的停止狀態。全過回 0,有沒過的回 1 並逐條列出,證據帳讀不了回 2。
  - `lumos set <計劃> status done`:計劃有 `[evidence]` 條款或有〈待決問題〉一節時,先跑同一套交付檢查,沒過就拒絕;兩者都沒有的計劃行為不變。
  - 交付檢查每次擋下或放行都寫一筆治理帳事件(沿用 `_gate_event`),`lumos gov` 的統計同時接上證據帳與這些事件——RETIRE-IF ②③ 才量得到。
- 依需求啟用:沒有對應條款的關卡就不檢查,不另做開關。

### E. 失敗後的修復迴圈與停止條件

- 同一條款,從最近一列 PASS 之後算(沒有 PASS 就從頭算),連續 3 列非作廢的 FAIL 或連續 3 列 BLOCKED,就進「停止狀態」:交付檢查不放行,`evidence run` 對這條款拒絕再跑並印交人提示。
- 解除只有一條路:人看過後跑 `lumos evidence run … --human-ok "<至少 4 字的理由>"`,這會先記一列 `human-ok` 把計數歸零,再照常執行。修好之後有 PASS 也會自然歸零。
- 不另做「失敗原文雜湊相同」的判法:正規化規則一定漏(暫存路徑、埠號、亂數),計數就夠。
- 修復前後對照:同一條款的 FAIL 列與之後的 PASS 列都留在帳上;破壞測試本身的紀錄仍在 kill-log,證據帳只記「還原後同一測試與回歸」那幾次執行,不重記破壞測試。

## 實務隱患

- 併發:證據帳是逐列追加的共用檔,兩個程序同時寫靠單次寫入不交錯、編號靠隨機尾碼與「不存在才建立」的目錄避免撞名(S7)。
- 資源:原始檔可能很大,串流寫入、超過上限只留頭尾(C);逾時整群殺掉子程序(S5)。
- 秘密:遮蔽規則抓不全;原始檔不離開本機(d4),帳上只留截短後的遮蔽版(S6)。
- 不可逆:MCP 與 `evidence run` 都能對真實系統下指令。處理:寫入類 MCP 設成每次詢問、`evidence run` 不得進允許清單(B);示範 repo 只連本機 Docker;正式環境只給唯讀帳號。
- 已排除:金流:本案與示範都不含付款流程(訂單只到建立與扣庫存)。
- 已排除:對外送出:證據擷取與壓測只打本機環境,示範的埠只綁 127.0.0.1,k6 腳本非 localhost 就中止;不寄信、不推通知、不呼叫第三方。
- 守衛面:本案會改規格閘、`spec-trace`、`lumos set` 的判定與簿記名單,誤擋會訓練人繞過——每個新判定都有「舊行為不變」的對照測試(S3、S10、S11 的不帶旗標或不適用情況),每塊各自一個提交以便單獨回退。
