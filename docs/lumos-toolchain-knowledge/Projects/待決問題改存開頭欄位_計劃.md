# 待決問題改存開頭欄位_計劃

> 白話:計劃的「待決問題」原本寫在正文一節、用正規式解析,規格閘拿它來擋還沒決定的阻塞題。代碼審三輪都在這裡換形狀,已撤出([[Projects/後端工程提問與證據擴充_計劃]] 決策 d10)。這篇重做:題目存在開頭欄位、用指令寫入,讀不清楚就整份擋。**狀態是草案,動手前要先過 `lumos spec-gate`。**

## 緣起

- 原做法:正文 `## 待決問題` 一節,一題一行 `- [Q1] 問題 [類:..][階段:..][狀態:..][阻塞] → #d1 出處:… 測試:…`,規格閘、lint、`pitfalls --stage` 共用一支逐行正規式解析,外加一道「題目形狀的行沒被讀到就擋」的外層看門。
- 代碼審 code-後端情境出題 三輪 21 席反覆撞到同一類:圍欄沒關(含四個反引號開三個收、`~~~` 開 ``` 收)把題目藏起來;標題寫成「三、待決問題」、粗體;旗標寫成 `［阻塞］`、`[阻 塞]`;一般敘述文字(`- Q4 上線 [階段一:灰度]`、題目文字裡的 `[阻塞性能]`)被誤擋;幾條正規式對長行平方級回溯。卷證在 governance/review-reports/code-後端情境出題/。

## 外部做法(2026-10-12 與 Codex 外家討論、加上網路查核)

PRIOR-ART:結構化資料與正文分開、只准用指令改,是主流做法;本專案的決策紀錄(開頭欄位 decisions + `lumos decision-add`)已經是這個模式,借用,不自建新格式。
- 開頭欄位(Jekyll、Hugo、Obsidian 的 properties):型別、合法值、編號重複都驗得了;Obsidian 社群普遍把它當比寫在正文裡的欄位更穩、更通用的預設。
- 寫在正文裡的欄位(Dataview 的 `key:: value`):易寫,但仍混在自由文字裡,圍欄、重複、跳脫字問題一樣在;Dataview 的後繼者 Datacore 據論壇轉述改成預設不讀(沒查到官方文件)。
- GFM 勾選清單:只表達做完沒,裝不下階段、阻塞、決策連結。
- 正規的 Markdown 解析器(CommonMark、markdown-it):要外部依賴,違反零依賴;而且解析對了也判斷不了 `[阻塞性能]` 是不是旗標。CommonMark 規定收尾圍欄要同字元、至少一樣長,沒關的圍欄延到檔尾——正文解析要自己重做這套才不漏。
- Issue 追蹤器(GitHub Issues、Jira)與 Backlog.md:標題、狀態、阻塞關係存成有型別的欄位,只透過表單、API 或指令改;Markdown 只負責描述。

## 做法(草案)

- 題目存在計劃開頭欄位的 `pending_questions` 清單,每題:id、text、class、stage、status、blocking、irreversible、decision、source、reason、tests。照決策紀錄那一套:只支援受限的格式、改哪行動哪行、寫完重讀驗證,不引入 YAML 套件。
- 指令寫入:新增題、改狀態(改成已決時要給決策連結)。手改照樣讀,但讀不清楚就擋。
- 統一規則:**只有開頭欄位裡的才算題目;這份清單只要有任何一處讀不清楚(鍵重複、不認得的鍵、型別錯、值不合法、編號重複、半條紀錄),整份當無法判定,規格閘擋。** 不再猜正文哪一行像題目、不取最後一個值、不跳過壞的那筆。lint 報細節,規格閘只說「資料無法判定」,`pitfalls --stage` 不列不完整的清單。
- 舊寫法:repo 裡只有一篇計劃用過正文一節(7 題),手動用新指令重建,不寫遷移工具。正文還留著舊寫法的 `- [Q<n>] … [狀態:…]` 行時當無法判定、擋下,訊息教人改用指令(這一條只看「節標題是待決問題、行首是 Q 編號」的精確形狀,不做寬鬆猜測)。
- 取捨:手改寫錯會被擋(誤擋局部、看得出原因、用指令修得好);換來的是漏擋有邊界——不在清單裡的就不是題目。

## 順手處理(重做時一併改)

- `scripts/lumos` 的 `PQ_STAGES`:名字還帶待決問題的縮寫,但現在只給 `pitfalls --stage` 驗階段;重做時改名(例如併到需求風險面表旁),或讓新的題目欄位共用它(代碼審 r4 架構席)。
- 主測試檔的 `_QO_DEC` 常數與 `_qo_plan` 的 decisions 參數:撤出後沒人用;新測試要寫跨篇決策連結時會用到,重做時用上或刪掉(代碼審 r4 邊界席、合約圖譜席)。

## 不做

- 不引入 Markdown 解析器或 YAML 套件。
- 不寫舊格式遷移指令(只有一篇、7 題)。
- 不讓正文與開頭欄位雙寫;正文只放給人看的說明。

## 待決問題(這一篇自己的;給人看的清單)

- 開頭欄位變長,計劃筆記要不要另給一個「只看待決問題」的顯示指令?
- 指令要幾支:一支新增、一支改狀態夠不夠?
- 改成已驗時要不要像現在一樣檢查測試名在本篇條款裡?
