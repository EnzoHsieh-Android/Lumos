# 待決問題改存開頭欄位_計劃

> 白話:計劃的「待決問題」原本寫在正文一節、用正規式解析,規格閘拿它來擋還沒決定的阻塞題。代碼審三輪都在這裡換形狀,已撤出([[Projects/後端工程提問與證據擴充_計劃]] 決策 d10)。這篇重做:題目存在開頭欄位、用指令寫入,讀不清楚就整份擋。**2026-10-12 設計審過(一輪四席,40 條全折)、已實作;S1–S6 綁測試,S7 搬遷已逐題核對。**

## 緣起

- 原做法:正文 `## 待決問題` 一節,一題一行 `- [Q1] 問題 [類:..][階段:..][狀態:..][阻塞] → #d1 出處:… 測試:…`,規格閘、lint、`pitfalls --stage` 共用一支逐行正規式解析,外加一道「題目形狀的行沒被讀到就擋」的外層看門。
- 代碼審 code-後端情境出題 三輪 21 席反覆撞到同一類:圍欄沒關(含四個反引號開三個收、`~~~` 開 ``` 收)把題目藏起來;標題寫成「三、待決問題」、粗體;旗標寫成 `［阻塞］`、`[阻 塞]`;一般敘述文字(`- Q4 上線 [階段一:灰度]`、題目文字裡的 `[阻塞性能]`)被誤擋;幾條正規式對長行平方級回溯。卷證在 governance/review-reports/code-後端情境出題/。

## 外部做法(2026-10-12 與 Codex 外家討論、加上網路查核)

PRIOR-ART:結構化資料與正文分開、只准用指令改,是主流做法;本專案的決策紀錄(開頭欄位 decisions + `lumos decision-add`)已經是這個模式,借用,不自建新格式。
- 開頭欄位(Jekyll、Hugo、Obsidian 的 properties):型別、合法值、編號重複都驗得了;Obsidian 社群普遍把它當比寫在正文裡的欄位更穩、更通用的預設。
- 寫在正文裡的欄位(Dataview 的 `key:: value`):易寫,但仍混在自由文字裡,圍欄、重複、跳脫字問題一樣在;Dataview 的後繼者 Datacore 據論壇轉述改成預設不讀(沒查到官方文件)。
- GFM 勾選清單:只表達做完沒,裝不下階段、阻塞、決策連結。
- 正規的 Markdown 解析器(CommonMark、markdown-it):要外部依賴,違反零依賴;而且解析對了也判斷不了 `[阻塞性能]` 是不是旗標。CommonMark 規定收尾圍欄要同字元、至少一樣長,沒關的圍欄延到檔尾——正文解析要自己重做這套才不漏。
- Issue 追蹤器(GitHub Issues、Jira)與 Backlog.md:標題、狀態、阻塞關係存成有型別的欄位,只透過表單、API 或指令改;Markdown 只負責描述。

## 做法

### 資料放哪、長怎樣

- 計劃筆記開頭欄位一個清單 `pending_questions`,每題一個項目,只收這幾個鍵(都是單行值;`tests` 用半形逗號分隔):

```yaml
pending_questions:
  - id: Q1
    text: 訂單成功的定義是什麼
    class: 需求
    stage: 需求
    status: 待人
    blocking: true
    irreversible: false
    decision: "#d1"
    source: README 第一段
    reason: 等示範跑完再定
    tests: t_a, t_b
```

- 必有:`id`(`Q` 加不帶前導零、最多 6 位的 ASCII 正整數,`Q01`、全形或阿拉伯數字、7 位數都算格式不對;題號到 `Q999999` 就不能再加)、`text`、`class`(自由分類,非空單行,不驗值)、`stage`(需求/架構/實作/驗證/效能/交付,跟 `pitfalls --stage` 共用 `PQ_STAGES` 同一組)、`status`(待查/自答/待人/延後/已決/已驗)。其餘選填;`blocking`、`irreversible` 只收不加引號的 `true`/`false`,沒寫當 `false`。
- 「必附」= 某些狀態必須附的欄位:已決、已驗要 `decision`;已驗另要 `tests`;自答要 `source`;延後要 `reason`。
- 「結了」= 狀態是已決或已驗,而且 `decision` 指到存在、沒作廢的決策。規格閘、lint、兩支指令都用這一條判,不各寫一套。
- 決策連結沿用決策紀錄既有的全域編號格式 `<節點>#dN`(就是 `decision-add` 印出來的那串,解析用 `_dref_parse`);指本篇的決策可簡寫成 `#dN`。帶路徑的寫法要整條對得上(不退回只比短名);只寫短名而同名不只一篇,當格式不合(代碼審 r1 邊界席:`env.resolve` 會退回比短名、撞名取第一篇,指錯篇也能過)。比對不分大小寫、先做 NFC,完全相符的路徑優先,短名查共用的 `by_stem` 索引(代碼審 r2、r3)。WHY:這裡比 `_dref_norm` 嚴(帶路徑不退回短名、撞名不取第一篇),因為它決定規格閘放不放行,指錯篇就等於假決策過關;`_dref_norm` 服務的決策引用養成是建議清單,寬一點只多列候選。`[[節點]]#dN`、`[[節點#dN]]` 這類寫法不收,lint 報「決策連結格式不合」並給正確寫法。
- `tests`:用半形逗號切,每段去頭尾空白;空段、重複的名字算讀不懂;測試名本身不能含逗號(參數化這類含逗號的名字寫不進 `tests`,要驗它就改綁不含逗號的名字)。比對時兩邊都走條款綁定那一套平台前綴規則(`resolve_test_refs`+專案的平台設定):多平台專案裡沒寫前綴=預設平台;單一平台專案不切前綴,`py:t_x` 就是另一個名字(代碼審 r1 架構席:原本另寫一套「沒前綴就只比名字」,lint 放行的名字到規格閘會判懸空)。測試名也不能含中括號(會被當成另一個 `[test:]` 拆開,代碼審 r2 正確性席)。平台設定一篇只讀一次,讀不動講一句。
- `pending_questions` 加進開頭欄位的已知鍵清單(`_KNOWN_FRONTMATTER_KEYS`),新版 lint 不對它報「沒見過的鍵」。
- 值怎麼寫:文字類的值經 `_yaml_plain_ok`/`_yaml_quote` 決定加不加引號；`blocking`/`irreversible` 照字面寫 `true`/`false`。不可見字元以 Unicode 16 `Default_Ignorable_Code_Point` 為底：三面英國地區旗只收完整固定序列；ZWJ/ZWNJ 只在阿拉伯、敘利亞、N'Ko、印度系、藏、緬、高棉、蒙古等需要連字控制的文字系統字母或記號後放行(下一字可為任何非可忽略字元)，emoji ZWJ 仍須兩側都是 emoji；軟連字號須夾在兩個字母間；蒙古變體選擇符只准一個接在蒙古字母後；FE0E/FE0F 只接 emoji 或鍵帽基底；「emoji」用近似 Unicode 16 Extended_Pictographic 的碼位表(BMP 逐段、補充平面 1F000–1FAFF 整段)加膚色修飾(不用 Unicode 類別 So:So 含框線、度數這類一般符號，字縫會變成藏字通道)；emoji 之間的 ZWJ 一串最多 3 個(標準序列最長的四人家庭就是 3 個)。軟連字號只在非東亞文字的字母之間；私用區與未指派碼位一律拒讀。合法位置仍受額度 `min(32,max(2,可見字元數//4))`，emoji 用的連接符與異體選擇符不計入這份額度，但整份值的可忽略字元合計不得超過 `min(64,max(16,可見字元數))`；超量、相鄰可忽略字元、非 NFC、雙向控制、零寬空格、BOM、補充異體選擇符都拒絕。錯誤訊息指向第一個真正不合的碼位並在印出前清洗；只有看不見的字元(含點字空白、韓文填充字)仍算空值。[test:t_qfm_r6_unicode_table_and_positions,t_qfm_r8_unicode_scripts_and_budget]

### 讀法:寧可擋,但只看這一個欄位

- 寫入端定位項目沿用決策紀錄的 `decisions_items`(加「欄位名」參數);嚴格讀法是這個欄位專用的一支 `_pq_scan`,入口 `pq_parse`。原設計說「`parse_decisions` 加 strict 參數」,代碼審 r1 架構席指出那只是名義上共用:決策清單收多行值與子清單、縮排從第一個 dash 推,這份只收單行值、縮排寫死,文法本來就不同,所以拆成獨立一支、`parse_decisions` 回原樣。規格閘、lint、`--stage` 三個消費端和兩支指令的寫前驗證都呼叫同一支 `pq_parse`,所以「寫的時候驗過」和「閘讀到的」是同一份判定。讀法只吃開頭欄位那幾行文字,不需要筆記庫(`--stage` 只拿到檔案路徑也能用);判鍵名用索引往前走的掃描,沒有會回溯的正規式,也不在迴圈裡切片(代碼審 r1、r8:原本兩種寫法對長空白行、連串 `- ` 是平方級)。
- 文法(寫死,實作照這張表):
  - 範圍:從頂格、恰好是 `pending_questions:`(冒號後只可有空白)的那行開始,到下一個頂格的「鍵: 值」為止；範圍內維持既有 2/4 格題目文法。只要開頭欄位含這個欄位，範圍外每一行不分擁有者與縮排，只套同一條規則：行首結構縮排是否為 ASCII 空白；`鍵: 值`(可帶重複 `- `、可在 flow collection 裡)的鍵名經 NFKC/大小寫正規化後，是否為題目專用的 `text/class/stage/blocking/irreversible`、非頂格的 `status`，或值不是 `d` 加數字的 `id`；結構位置是否為 anchor/alias/tag。鍵的寫法照 YAML 文法認:引號鍵(含引號與冒號間的空白、JSON 風格冒號緊接值、雙引號跳脫)、flow 片段裡帶 anchor/tag 的鍵、`-<tab>` 起頭都算；`? ` 複雜鍵(含單獨一行的 `?`)可以跨行藏鍵名,清單外一律判讀不懂；flow 要在同一行閉合,跨行判讀不懂；status 只有鍵在第 0 欄才豁免；頂格註解不結束清單；清單頭只認頂格 `pending_questions:`,縮排、清單項、`?` 複雜鍵、流式或 `<<:` 合併鍵寫出的清單頭判讀不懂(block scalar 內文提到不算)；中文鍵、非題目鍵的引號鍵、數字開頭鍵、續行純量、巢狀 mapping、頂格清單、`KEY:` 說明行與不同縮排的合法決策交還各欄位原讀法，不另替擁有者寫文法。[test:t_qfm_r8_outside_key_rule]
  - 一題的開頭:恰好 2 格空白加 `- id: Q<n>`;第一個鍵必須是 `id`,`id` 不在第一個的寫法 YAML 合法,但這裡算讀不懂。
  - 這一題的鍵:恰好 4 格空白加 `鍵: 值`,鍵名英文字母開頭(底線開頭的寫不進來)。其他縮排深度、tab 開頭、頂格的清單項,都算讀不懂。
  - 空行、註解行(空白之後以 `#` 開頭)放過;行尾空白去掉再判;檔案的 CRLF 與開頭 BOM 照開頭欄位既有讀法處理。
  - 值只收三種:不加引號且通過 `_yaml_plain_ok` 的、整個包在一對雙引號裡且內部沒有雙引號和反斜線的、整個包在一對單引號裡且內部沒有單引號的(就是 `_yaml_quote` 會寫出的兩種)。值以 `|`、`>`、`[`、`{` 開頭(多行或 flow 寫法)、不加引號卻含「空白加 `#`」(標準 YAML 會當註解切掉)、`blocking`/`irreversible` 加了引號,都算讀不懂。
  - `pending_questions: []` 單獨一行 = 零題;`[]` 後面又接題目行 = 讀不懂。`pending_questions:` 後面沒有任何題 = 零題。零題的判定與輸出跟沒有這個欄位一樣。`pending_questions:` 後面直接接其他值、開頭欄位裡出現兩次,都算讀不懂。
  - 拼錯的欄位名:頂格鍵去掉引號與冒號前空白、轉小寫、連字號與空格當底線之後以 `pending_question` 開頭、卻不是恰好 `pending_questions:` 那一行(例如 `pending_questions :`、`"pending_questions":`、`pending_question:`、`pending-questions:`、`Pending Questions:`)算讀不懂,不當成「沒有這個欄位」。
  - 合併衝突標記落在範圍內,照「看不懂的行」擋。
- 讀不懂的情形:上面文法外的行、不認得的鍵、同一題同一個鍵寫兩次、編號重複或格式不對、缺必有鍵、`stage`/`status` 值不在清單、布林不是 `true`/`false`、`tests` 有空段或重複。**只要有一處讀不懂,整份清單當無法判定**:不取最後一個值、不跳過壞的那題。錯誤訊息一律給**檔案的行號**、哪裡不對、該改成什麼樣子。
- 不再看正文。正文寫了什麼〈待決問題〉都不影響判定(這是 [[Projects/後端工程提問與證據擴充_計劃]] d10 撤出的原因)。

### 2026-10-13 第八輪定案：三條單一規則

**本節取代第七輪的逐擁有者文法；與上面任何歷史段落衝突時，以本節為準。**

- PRIOR-ART:Unicode 可忽略字元不自訂分類，採 Python 3.14 對應的 Unicode 16.0.0 `DerivedCoreProperties.txt` 之 `Default_Ignorable_Code_Point`；結構掃描沿用本檔既有逐行 parser 與 `parse_decisions`/`fm_structure` 的零依賴做法。
- RETIRE-IF:標準庫日後提供可直接查詢、版本與 `unicodedata` 綁定的 `Default_Ignorable_Code_Point` 屬性時，撤掉內嵌範圍表與二分搜尋，改用標準庫單一來源。
- 清單外只有一條鍵名規則：逐行檢查非 ASCII 結構縮排、題目專用鍵/非決策 `id`，以及 flow collection 內同樣的鍵；頂格 `status` 是筆記欄位而豁免。四種既有 block scalar 開頭 `|`、`|-`、`>`、`>-` 共用 `BLOCK_SCALAR_HEADERS`，內容是縮排嚴格深於鍵欄位的連續行；`|2`、`|+` 不算 block scalar，內容仍逐行套鍵名規則(四種頭後面帶 ` #註解` 照 YAML 仍算)。anchor/alias/tag 在結構位置照舊拒讀，其他寫法一律不猜。[test:t_qfm_r8_outside_key_rule]
- 看不見字元只有一條「文字系統位置＋總量」規則：位置白名單照本節上方〈值怎麼寫〉，非 emoji 的 ZWJ/ZWNJ/軟連字號/蒙古變體與特殊 Zs 合計不得超過 `min(32,max(2,可見字元數//4))`(天花板 32 是真實樣本最多 12 個的兩倍以上,只靠比例的話文字越長能藏越多)；相鄰 DICP 拒絕，只有 emoji 序列內的 `FE0F+ZWJ+emoji` 例外。DICP 表由測試端獨立抄 Unicode 16 官方逐段清單並核對 4174 個碼位，不從產品常數產生期待值。[test:t_qfm_r6_unicode_table_and_positions,t_qfm_r8_unicode_scripts_and_budget]
- 寫入只有一條拒絕原語與一個簽核時機：`load_raw_for_edit` 只把讀取失敗轉成 `WriteBlocked`，不因符號/硬連結拒絕；真正寫入前由 `_write_refusal_reason` 統一拒絕符號連結與 `nlink>1`，`atomic_write_verify`、drift fix、簽核帳都用它。`WriteBlocked` 的訊息在建立時就以 `_esc_clean` 清洗，各分派照既有寫法接(印「擋下」回 2)，沒被接到的由命令列入口 `_cli()` 接(分派函式維持叫 `main`,精簡版產生器靠這個形狀)；分派內既有 try 只接自己的其他錯誤。`signoff` 拿鎖後才讀原稿，先寫筆記，再用 `os.open`(O_APPEND、O_NOFOLLOW、不帶緩衝)開帳並記原長度；寫入、fsync 或連結檢查任一步失敗，就以 `os.ftruncate` 截回原長度(這次新建的帳整個刪掉)，再在鎖內還原筆記，訊息逐邊照實回報；成功 stdout 保留 set 與 signoff 兩行。`guard kill` 的 BOM/非 UTF-8 唯讀行為不變，decision 自由文字含任一換行類字元一律拒寫。[test:t_qfm_r8_signoff_and_write_refusal]

### 三個消費端

- 規格閘是**進實作之前**的關卡,只在手動 `lumos spec-gate <計劃>` 時擋(放在判門之後、「沒有條款就提早結束」與 `--no-run` 之前,風險高低都一樣):清單無法判定 → 回 1,印「待決問題清單無法判定」與 lint 指令;有題標阻塞、階段是需求或架構、而且沒「結了」(狀態不是已決/已驗,或決策連結指不到存在且有效的決策;延後、自答也算沒結)→ 回 1,列出那幾題。
- 推送前(`spec-gate --push-check`,只對這次推送範圍改到的計劃):有阻塞、需求或架構、沒結的題就印一行提醒(不擋);某個題號在舊版有、這一版不見了,或同一個題號的題目文字變了,也印一行提醒(這是「用編輯器刪題」唯一留下的訊號)。舊版=兩點範圍 `a..b` 的 a、三點範圍 `a...b` 的合併基準;整份計劃被刪的不比(不是刪題);兩版用一次 `git cat-file --batch` 讀,有逾時,讀不到印一句跳過。
- lint(掛在新規則那一路,擋不擋照 note_lint.gate;規則函式拿得到 `env` 和筆記本身,開頭欄位與正文都讀得到):清單無法判定時逐處報原因與檔案行號;讀得懂時查必附——已決、已驗的 `decision` 要「結了」、已驗要有 `tests` 且每個都在本篇驗收條款的 `[test:]` 裡、自答要有 `source`、延後要有 `reason`、標不可逆不得自答、標阻塞不得延後。條款那邊用條款定義行的讀法取 `[test:]` 的名字(圍欄與反引號裡的不算),不建平台測試索引;測試真的存不存在交給既有的條款綁定檢查(`lumos spec-trace`)。
- `pitfalls <計劃> --stage <階段>`:需求風險面照舊,再列那一階段沒結的題(待查、待人),依阻塞、不可逆、其餘排序,同級照編號的數字大小(`Q10` 排在 `Q2` 後面),不截斷。清單無法判定時照常印需求風險面,再印原因、回 2。`--json`:沒有這個欄位(或零題)時輸出跟現在一模一樣、只有 `stage` 和 `facets`;有題時多一個 `questions` 鍵(每題 `id`、`text`、`stage`、`status`、`blocking`、`irreversible`);清單無法判定時多一個 `questions_error` 鍵放原因、回 2。

### 指令

- 兩支指令整段「讀檔→算編號或改值→驗→寫檔」都包在 `_vault_write_lock` 裡(跟 `set`、`append` 同一把鎖)。決策紀錄的 `decision-add` 原本沒上鎖(同時起跑 8 個實測只留下 6 條),而決策與待決問題寫在同一份開頭欄位,沒鎖會互相蓋掉,所以改成一條規則:所有讀改寫開頭欄位的入口都先拿同一把鎖(決策四支含 reindex --all 與 amend、決策引用、守衛綁定與審計;寫法照鄰居「`cmd_*` 拿鎖再叫 `_*_locked`」),`atomic_write_verify` 沒拿這個筆記庫的鎖就不寫(代碼審 r1、r2 併發與正確性席:逐支補一直漏);拿鎖逾時一律「擋下」rc2;decision-amend 的 git fetch 放鎖外(r3)。寫入時別篇的決策從磁碟重讀,不信鎖外載入的內容。
- 寫入走 `atomic_write_verify`:寫檔前在記憶體組好新內容,用嚴格讀法驗過整份清單讀得懂、符合下面的寫入規則才寫檔;「這一題內容跟要寫的一致」放進 `atomic_write_verify` 的讀回檢查(跟 decision-add 同一個掛法)。沒過就不寫、回 2、說缺什麼。這是寫前驗證,沒有「寫完重讀再還原」這一步。兩支指令都不改 `updated`(跟 `decision-add` 一樣,題目怎麼變看 git)。
- 寫入規則(跟 lint 同一條「結了」判定,判的是寫完之後那一題的樣子,不管是新增、改狀態還是改旗標):必附要齊;同時標阻塞又是延後的題不准寫出;同時標不可逆又是自答的題不准寫出;給了 `decision` 就要指到存在、沒作廢的決策;現有清單本身讀不懂時一律拒寫(先修好再寫)。
- `lumos question-add <計劃> "<問題>" --class <類> --stage <階段> [--status 待查] [--blocking] [--irreversible] [--decision "<節點>#dN"] [--tests …] [--source …] [--reason …]`:
  - 給下一個編號 = 現有題號數字的最大值加 1;回印全域編號 `<計劃的相對路徑>#Q<n>`(跟 `decision-add` 印的 `<相對路徑>#dN` 同一種形狀)。
  - 沒有這個欄位時把欄位加在開頭欄位末尾(跟 `decision-add` 加 `decisions` 的位置一樣);欄位是 `pending_questions: []` 時,先把那一行改成 `pending_questions:` 再加題(`decision-add` 在 `decisions: []` 上會寫壞而被擋,實測過,不照抄)。
  - 說明裡的例子一律把決策連結加引號:在 shell 裡單獨一個以 `#` 開頭的參數會被當成註解吃掉。
- `lumos question-set <計劃> Q<n> <鍵>=<值> [<鍵>=<值> …]`:一次可改好幾個鍵(例如 `status=已決 decision=#d3`)。
  - WHY:用「鍵=值」而不是 `--field/--text` 或一次一鍵,因為「改成已決必附 decision」這類跨鍵規則要一次改完才驗得過;`decision=#d3` 這種寫法 `#` 在字中間,shell 也不會當註解。
  - 每個參數只切第一個 `=`;沒有 `=` 的參數、不認得的鍵、要改 `id` 都回 2。`鍵=`(空值)代表拿掉這個選填鍵,必有鍵不准空;拿掉後照樣驗必附。原本沒有的選填鍵加在這一題最後一行之後。
- 不提供刪題:題目改成延後(附理由;阻塞題不行)或已決;真的寫錯就用編輯器刪——推送前會印「題號不見了」的提醒(見〈三個消費端〉),編號不會被重用的保證只到「現有最大號加 1」為止。

## 實務隱患

- 守衛面:規格閘多一條擋法,誤擋會訓練人繞過——擋的條件只看開頭欄位這一處、文法寫死、讀不懂時訊息給檔案行號與該怎麼改(S2);沒有這個欄位的計劃完全不變(S6)。漏擋那一面:延後、自答、指到假決策都繞不過(S1、S3)。
- 已排除:金流:不碰付款或扣款,也不處理任何金額
- 已排除:對外送出:只寫本機筆記,不呼叫外部服務、不寄信
- 已排除:不可逆:寫入走改哪行動哪行、寫前驗證、沒過不寫,壞了用 git 還原;不刪檔、不改別的筆記
- 並行會談:兩支指令讀改寫整段上鎖(S3 有兩個程序同時寫的測試)。
- 資料相容:舊版 lumos 讀到這個欄位會當成不認得的開頭欄位,lint 只多一條「沒見過的鍵」提醒、不擋(本 repo 的 note_lint.gate 是 on,實測仍只提醒;「沒見過的鍵」不在 gate 管的那一路);`lint`、`spec-gate`、`decision-add` 不崩,`set`/`append` 對這個欄位回「擋下」,對同一篇的其他欄位照常寫(r1 整合回退席在臨時庫實測)。
- Obsidian 屬性面板這類編輯器重存開頭欄位時,可能改寫縮排或引號;改出文法表外的形狀就會被擋,訊息指出檔案行號,照訊息改回或用 `question-set` 重寫那題。舊版不擋阻塞題、也驗不了這個欄位,有人用舊版或編輯器改壞,要等新版的規格閘或 lint 才看得到。
