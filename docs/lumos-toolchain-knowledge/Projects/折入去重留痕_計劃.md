# 折入去重留痕_計劃

> 白話:審查迴圈每輪收到好幾席的報告,編排者會把「三席講的其實是同一個洞」合併成一份發現清單再折進設計——★這個合併判斷今天已經在做,只是沒有被記下來★。所以事後永遠答不出「哪一席抓到哪個洞」「這個洞被幾席抓到」。本案只做一件事:**把那個已經在做的判斷寫進一個檔**,讓「被幾席抓到」從人手數變成機器數,順便讓「每個發現對應到報告裡哪句話」變成可回溯。不加新判斷、不動帳 schema、不碰圖譜。

PRIOR-ART: ① 最小解層級——`capture-counts` 已有 `--from-pitfalls <range>` 把 linter 命中自動收割成 finder(`scripts/lumos:4831`);本案照同一形狀加 `--from-fold <rN-fold.json>`,每席=一個 finder、key=去重後的發現 id。key 是任意字串+casefold(`[[Systems/heterogeneous-finder-ensemble]]` 明寫),不需要節點、不碰圖譜,★vault-free 合約保得住★。② 世界解過沒——「把人工去重判斷記成 (raw finding → canonical id) 映射」是任何多評審流程的基本表(inter-rater 分析的 coding sheet);本 repo 自己的 `rN-dispatch.json`/`rN-intake.md` 就是同型的每輪結構化留痕。③ 裁定=borrow-design,零依賴。

## 一句話

★折入時已經在做的去重判斷,寫成檔;capture-counts 讀那個檔。★

## 為什麼是這個,不是昨天那個

[[Projects/審查帳節點映射_計劃]](2026-09-03 停案)想用「節點集合」當缺陷指紋,被真實三重命中推翻(三席同一缺陷引姊妹節點)。本案★不定義指紋★——指紋就是編排者折入時已經給的那個 id(如 `R7`、`refcheck重造`),機器只負責記「哪一席的哪句話被歸到它」。

實證:`驗證層自證三件` r1 五席 32 條原始發現被編排者合併成 15 個 id,★席報告與卷證目錄裡找不到任何一處記錄這個對應★(機械 grep 0 命中)。[[Verification/2026-09-03_席間覆蓋率離線量測]] 的 64.6% 靠的是手填的 `capture_counts`,該欄 08-23 後零筆——本案讓它變成從檔算出來。

## 設計(最小)

1. **新留痕檔** `governance/review-reports/<編號>/rN-fold.json`:
   `{"round":"rN","carrier_findings_set":[...],"seats":{"<席名>":[{"quote":"<該席報告的一句逐字引句>","id":"<去重後 id>"},...]}}`
   ★用引句當 raw finding 的定位,不用標題編號★——引句是席報告唯一強制且機器驗過的欄(quote-check);標題格式各席自由(`## ①`/`## F1`/`### 1.`)不可靠。
2. **`capture-counts --from-fold <rN-fold.json>`**:每席一個 finder,key=id 列表;與既有 `--finder`/`--from-pitfalls` 合併算,輸出不變。★只讀 JSON 檔,不開帳、不開圖譜。★
3. **寫入驗證(fail-closed,rc2)**:每條 `quote` 必須錨得回該輪凍結快照(重用 `_quote_rows`);每個 `id` 必須 ∈ `carrier_findings_set`;同一席同一 quote 不得重複。
4. **編排者流程只多一步**:折入時把「這席這句→哪個 id」寫進 fold.json(★這正是他當下在做的判斷★),記帳的 `--capture-counts` 改由 `--from-fold` 算出、貼進去。

## 這解掉什麼

- **昨天基建案的三個 blocker**:不需要指紋(id 由人給)、不動帳 schema(檔在卷證目錄)、不破 vault-free(讀 JSON)。
- **早上 v1 的死因**:id → (席, 引句) → 引句在快照的位置(`hay.find`)——「發現對應到哪段文字」有鏈了。
- **下午試點的 D1/D2**:清單命中=id 對應的引句是否落在注入節點相關段落——★仍需一步判斷,本案不做,只讓它變成可做。★

## ★未解(要審查席正面打)★

1. **還是靠人填**:fold.json 由編排者寫。差別=它記的是已經在做的判斷、且有 fail-closed 驗證(引句錨定+id 存在)。帳上同款帶驗證欄位 `finding_kinds` 填寫率 78.5%、`refute_verdicts` 0%——★哪一種比較像本案,我不知道★。回頭條件見下。
2. **一席一條發現被歸到多個 id、或一個 id 跨席引句不同段**:允許嗎?capture 語意是「id 被幾席抓到」,多對多不影響計數,但 D1 那層會歧義。
3. **歷史迴圈不補**;新舊段不可比。
4. **要不要讓 disposal 閘也讀 fold.json 核 `findings_set` 一致**:本案不動閘;若日後接,是另案。

## 驗收

- 機械:`--from-fold` 對一份真實輪(自己這案的 r1)算出的 capture_counts,與人手數一致;三條寫入驗證各有翻紅釘。
- 行為:落地後首 10 個多席輪,fold.json 存在率。★REVISIT:2026-10-03 存在率<50% 即承認「記已在做的判斷」也靠不住,改成折入指令化(把 fold.json 變成 `lumos fold` 子指令的輸出)。★

## 誠實界線

- 「被幾席抓到」的正確性=編排者去重判斷的正確性,本案只買算術正確(同 `heterogeneous-finder-ensemble` 的誠實邊界)。
- 不碰 D1/D2 的判斷層;不動任何閘;不回補歷史。
- 兩個母案都停,本案的即時消費者=`capture_counts` 欄本身(讓 [[Verification/2026-09-03_席間覆蓋率離線量測]] 的儀器有新資料)。★若 10 輪後仍無人重開母案,本案的價值只剩「覆蓋率量測不斷炊」——夠不夠,人裁。★
