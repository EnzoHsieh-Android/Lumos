# 測試品質掃描試行_計劃

## 問題與最小解

使用者於 2026-10-07 要求開始：用小型試行驗證測試品質規範，並建立事後唯讀掃描。目標是未來實作時的測試，不只修訂輪。使用者同日進一步要求涵蓋 Android、iOS、C#、Python、Node.js；規範跨語言共用，檢測分語言／框架接入。

PRIOR-ART: 借用 Python 標準庫 AST 的語法結構比較 https://docs.python.org/3/library/ast.html 、Matt Pocock 的獨立判準原則 https://github.com/mattpocock/skills/blob/main/skills/engineering/tdd/tests.md ；故障注入沿用既有隔離方法。mutmut https://mutmut.readthedocs.io/en/latest/ 可作較全面的變異工具，但此次先做零依賴、有限案例，不自建通用變異執行器。
RETIRE-IF: 若已接入的通用工具能在同一固定壞例與合理反例上提供相同定位、錯誤狀態及較低維護成本，撤除自訂掃描並改指該工具。

## 條款

[S1] 當輸入已啟用語言的測試檔時，掃描器應按明示的語言／規則能力辨識候選（Python 初版含自比、同函式產預期值與只斷言來源文字，其他語言先含特定介面自比），輸出位置、理由與人工確認方向；命中不是裁決。 [manual:固定案例驗收候選與合理結構反例]
[S2] 當選填明確實作來源時，語言適配器應在已驗證的語法範圍內比對重抄算法候選；不猜任意跨檔語義，超出能力時標示未分析。 [manual:獨立字面值與故意重抄算式案例]
[S3] 掃描器應只 parse 原始碼，不 import、執行測試或改寫輸入；解析／讀取／輸入錯誤必須使結果 incomplete 並回傳 2，候選本身回傳 0。 [manual:子程序測惡意頂層與不合法輸入]
[S4] 固定主線案例應驗證兩個已知盲點；測試故障變體需原版綠、目標斷言紅、還原綠。 [manual:隔離案例故障驗證與既有盤點互證]
[S5] 手冊試行應使用固定開發題、兩臂規範與同一評分器；保存模型及題目、輸出與故障證據，不以一次結果宣稱普遍有效。 [manual:實際執行兩臂並保留無效或未知結果]

## 邊界與回退

規範涵蓋各語言；第一個實作適配器先交付 Python 與明確路徑，各語言／規則逐項公布分析範圍，unsupported 必須顯示在報告；候選全供人看，不加 CI 阻擋、不改既有代碼審判閘。算法比對只接受單一算式函式；字面值測試不保證覆蓋足夠。回退可刪除新工具及指路文字，既有功能不受影響。

設計審取捨：唯讀、無外部寫入與新依賴的小型工具，先以可翻紅的固定案例探索；先判門，若低風險採直接實作。

## 跨語言分層

1. 共用規範：獨立判準、可觀察行為、情境成立與相關故障翻紅，不按語言複製政策。語言慣例 skill 只補例子及入口。
2. 靜態適配器：辨識測試與斷言、expected 的局部來源，回報可疑理由。優先評估既有語法工具作選配 backend；不為各語言各造 parser，也不以 regex 猜完整語義。Python stdlib AST 是零依賴第一個樣本。
3. 抓錯適配器：優先接專案既有 runner、多平台綁定與 guard kill。擴充變異工具僅作選配，由消費專案鎖版與隔離，不引入 Lumos 核心依賴。
4. 共用證據：輸入版本、語言、框架、工具版本、掃描範圍／略過範圍、測試身份、位置、規則、理由、原文、判準來源、故障位置、基準結果、故障結果、還原結果、耗時及人工裁決。

結果分開報：靜態 candidate／人工確認 confirmed 或 dismissed；執行 detected／survived／invalid-mutant／timeout／unavailable。基準失敗、零測試、編譯錯、未歸因失敗與未知一律不算 detected。工具未裝與語法不支援必須列出；零候選不等於測試有用。

## 平台適配矩陣（候選，需實測後才宣告支援）

| 場景 | 測試介面 | 靜態接入方向 | 抓錯候選與限制 |
|---|---|---|---|
| Android Kotlin／Java | JUnit、Kotest、常見 assertion library | 共用語法 backend 加框架斷言規則 | 純 JVM 模組評估 PIT；Android Gradle plugin／裝置測試另驗相容性，不宣稱 JVM 支援等於 Android 支援 |
| iOS Swift | XCTest、Swift Testing | 同時驗 XCT assertions 與 #expect | Muter 等候選；需驗 Xcode／Swift／測試選取及結果歸因，UI 測試另層 |
| C# | xUnit、NUnit、MSTest、FluentAssertions | C# AST backend 或原有 analyzer | Stryker.NET 候選，依 test runner 與 .NET 版本確認 |
| Python | unittest、pytest、既有 t_ runner | stdlib AST 第一個樣本 | 既有隔離故障驗證；mutmut 候選 |
| Node.js JS／TS | Jest、Vitest、node:test | JS／TS AST backend 加框架斷言規則 | StrykerJS 候選；runner 未列內建支援時另驗 command runner，不宣稱支援 |

Semgrep 文件列出這些語言，但商業版與 CE 的跨檔／資料流能力不可混用： https://docs.semgrep.dev/supported-languages 。採用前需要在指定版本與授權能力上跑固定案例；這裡沒有承諾它現成規則已能抓本議題。

來源：
- JVM／Kotlin: https://github.com/pitest/pitest-kotlin
- Android 相容限制: https://github.com/szpak/gradle-pitest-plugin （FAQ 明寫一般 plugin 不直接支援 Android）
- Swift 候選: https://github.com/muter-mutation-testing/muter

## 固定考卷與支援門檻

各語言用同一業務題與故障定義，覆蓋：自比、expected 重用被測程式、重抄算法、只有來源字串、拒絕理由代打，以及合理的穩定性／結構／可信參考實作反例。不得把上述所有形式一律當錯；以判準來源與守護目的裁決。

每個適配器須有正例／反例／解析失敗／零測試／工具缺失案例，報告漏報、誤報、未分析數與耗時。手冊效果與掃描器效果分開：前者固定模型與開發題，兩臂只有是否帶新規範不同，盲評輸出並用預先凍結的相關故障檢查；後者看固定標註集，不拿掃描器自己的判斷當標註真值。記錄重複次數及樣本限制。

落地順序：先共用報告與跨語言考卷；Python 驗證一條端到端路徑；Node／C# 接入，再 JVM 與 Swift。每一語言獨立標記 planned／synthetic-verified／project-verified，多語言能力依框架、規則與證據範圍宣告。AI 審查先讀候選與未分析區；只針對本次變更、bug 修復與關鍵守衛抽查故障，避免把所有 PR 拖進全套變異測試。
