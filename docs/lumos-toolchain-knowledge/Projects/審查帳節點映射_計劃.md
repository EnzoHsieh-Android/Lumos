# 審查帳節點映射_計劃

> **★停案:r1 攤牌後 Enzo 裁不做(2026-09-03,見 d2)。本篇是「為什麼現在不做」的紀錄,不是待辦。★**
> **撞死在哪**:①「節點集合當缺陷指紋」不成立——母案三席寫同一缺陷卻引程式碼行/設計節點/實作節點(姊妹),相等與交集兩判準同時失效;同一節點也可同時有多個缺陷,節點只能當座標 ②帳規則一輪只准一筆處置集合,逐席映射無處落帳,「被幾席抓到」重建不出 ③capture-counts 派發時 env=None 明文 vault-free,自動路徑破約——本 repo 第三次撞這道牆(impact 鏡頭/已知坑前置) ④D1 公式:缺欄退化空集合恆算「清單外」,自灌。
> **存活的**:expected-nodes 可照抄 _ids;既有讀取端全部安全;節點名須存正規化路徑;finding_kinds 帶驗證填寫率 78.5%(vs refute_verdicts 0%、capture_counts 12%)。
> **更小的方向(未開案)**:席報告每條發現帶規範化 key,capture-counts 直接讀報告檔——不加帳欄、不碰圖譜。重開條件見 d2。
> **今天第四份死在「圖譜沒查乾淨」的計劃**;第五份先查再開。


> 白話:審查帳記了「這輪抓到哪些發現」,但★沒記「這輪本來應該查哪些節點」,也沒記「每個發現對應到哪個節點」★。這兩個洞今天讓兩份計劃死掉:早上想量「閘漏了多少」的,死在發現編號反推不出文字;下午想「派工時自動補清單」的,死在偽陽性檢查算不出來、主指標欄位八月底後沒人填。本案只做一件事:**在帳上補這兩個欄位,並讓「每個缺陷被幾席抓到」改成機器算,不靠人填。**

PRIOR-ART: ① 最小解層級——不動判定引擎、不動任何閘;只在 `lumos canary record` 加兩個選配欄位、在 `capture-counts` 指令加一條從欄位自動算的路徑、在 `recount.py` 加對應讀法。② 世界解過沒——「finding 帶座標/歸屬」是任何缺陷追蹤系統的基本欄(SARIF 的 `locations`、Sentry 的 fingerprint);本 repo 的 pitfalls manifest 已經帶 `file:line`,是同型的既有慣例。③ 裁定=borrow-design,零依賴原生實作。

## 一句話

★帳上補「應查節點」與「發現→節點」兩欄,讓覆蓋率不再靠人填。★

## 為什麼(兩份計劃的共同死因,機械證據)

- [[Projects/收斂閘漏項敏感度_計劃]] v1 r1 blocker:`folded_set`(帳上「這輪哪些發現被折進設計」的 id 集合)只存編排者自取的助憶 id(`R1`、`refcheck重造`),抽查 40 筆僅 17 筆能在自家席報告找到任一 id,★id→文字的鏈從未被記錄★。
- [[Projects/派工時自動補清單_計劃]] r2 四席獨立指出:`capture_counts` 是無 id 整數陣列,`recount.py:59` 自己寫死「無法直接對到 findings_set(帳上該輪全部發現的 id 集合)的 id」;整個帳 schema 沒有「這輪注入/應查了哪些節點」或「finding 對應哪個節點」欄位——★D1/D2 是空的預註冊★。
- `capture_counts` 是編排者手填:最後一筆 2026-08-23,之後 365 列零筆。★口徑寫死(前掃抓到我抄了別席的數字沒重算)★:2026-08-04~2026-09-03 多席輪(同 loop+round 有≥2 個不同 auditor)=112,其中帶 capture_counts=13,填寫率=12%。★靠人填的欄位已經實證會斷★。
- 現行帳欄位(34 個)機械數過,沒有任何一個記節點歸屬。

## 設計(最小)

1. **`canary record` 加兩個選配欄**(不給=行為與今日相同——本 repo 的「相容鐵則」:新增選配欄位時,舊呼叫方式的輸出必須逐位元不變):
   - `--expected-nodes <逗號串>`:本輪應查的固定席節點(來源=`lumos impact --diff` 的 pinned(輸出裡標「固定席」的節點=帶硬合約或出過事故、審查必答的那批);派工時算一次、記帳時貼進來)。
   - `--finding-nodes <id=節點[,節點],…>`:每個 finding 對應到哪些節點(可多、可空)。
2. **`capture-counts` 加自動路徑**:多席報告的 finding 若帶相同 `finding-nodes`,視為同一相異缺陷 → 直接算「被幾席抓到」,★不再靠編排者手數★。無 `finding-nodes` 的 finding 退回今日行為。
3. **`recount.py` 加兩個讀法**(D1/D2 是母案〈派工時自動補清單〉預註冊的兩個指標名,本案只提供取數):D1 清單外發現數(finding-nodes ∩ expected-nodes = ∅ 者)、D2 清單命中率(expected-nodes 中被任一 finding 命中的比例)。
4. **寫入端驗證**:`finding-nodes` 的 id 必須 ⊆ `findings_set`;節點必須存在於圖譜(不存在 rc2 擋)。

## ★未解(要審查席正面打)★

1. **「發現對應到哪個節點」由誰判**:仍是編排者在記帳時填——這是判斷不是機械。★但它跟今天的差別是:填在記帳當下、有寫入驗證、且每條 finding 逐一對應,不是事後從助憶 id 反推。★是否仍構成「靠人記得」的步驟,審查時要打。
2. **歷史 80 個迴圈不會有這兩欄**:本案只管未來;早上那把尺的歷史基線(64.6%)照舊用舊欄位算,新舊兩段不可直接比。
3. **同一缺陷不同席寫不同節點**:自動歸併的判準是「finding-nodes 交集非空」還是「相等」?寬了會把不同缺陷併成一個,嚴了會把同一缺陷拆開。★沒定,要打。★
