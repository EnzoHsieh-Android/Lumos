# 世界解重新註解2026-10_檢索_調研

> 白話:這篇回答「給一個任務,哪些筆記該浮上來、排得對不對」這件事,世界怎麼做、Lumos 怎麼做。世界的主流跟 Lumos 一樣靠字面搜尋加少量結構訊號,不靠向量索引;圖演算法、社群摘要這類重武器在單跳查詢上普遍輸給調好的 BM25(一種按詞頻與稀有度打分的經典排序公式)。Lumos 真正的弱點不在排序,而在「推了之後有沒有用」:改檔前推播只送節點名,推了沒人去讀的比例高,而且從來沒有量過推播開或關對任務結果的差別。所以最該先做的是結果層的開關對照,再決定要不要把必看合約的條款摘錄直接推進去。本篇屬於 [[Projects/世界解重新註解2026-10_總覽_調研]] 的第 2 類。

## 這一類在問什麼、Lumos 現在怎麼做

這一類問三件事:使用者或 agent 主動查的時候怎麼排(拉)、改檔前該主動送哪些筆記(推)、改動會波及哪些地方(影響)。以下只寫定位,細節以各節點與程式為準。

- [[Systems/retrieval-ranking]]:搜尋與影響清單的排序核心,字面撈候選後用 BM25F(多欄位版 BM25,先把各欄詞頻加權再做飽和)打分,不建持久化索引,不用嵌入。
- [[Systems/lumos-cli-read]]:`lumos search`、`lumos context`、`lumos show` 這組讀指令;含多詞回退(整串 0 命中時改成任一詞命中)、逐詞覆蓋提示、預設藏起已作廢節點。
- [[Systems/改檔前推播]]:Claude Code 改檔前(Codex 是 apply_patch 前)的 hook,決定要不要推、冷卻窗(同檔 20 分鐘內只比事故)、把查到的節點名框成「參考資料」交給模型。
- [[Systems/派工鏡頭]]:派審查子代理時附在派工詞尾端的參考資料;這是全 Lumos 唯一會把合約行原文送進模型的路線。
- [[Systems/hook信任邊界]]:規定 hook 不准把圖譜自由文字以系統口吻逐字送進主對話;改檔前推播只推名、只印合約類別,就是這篇定的。
- [[Systems/每支檔有家]]:每支程式檔要有管它的節點;推播的「家」入口靠它。
- [[Systems/cochange-guard]]:從 git 歷史挖「常一起改的檔」,提交時警告漏改,不擋。
- [[Systems/lumos-context]]:Claude 外掛,壓縮前在摘要指示後附一段交棒要求;不負責壓縮後重新推播。
- [[Systems/多詞評測]]:中文多詞查詢的獨立考卷。
- [[Systems/ablation-lumos-first]]:情境探針消融結果檔的有效性篩選與統計合併;本類的行為層驗證靠它。
- 沒有自己 Systems 節點、但屬於本類的機制:`lumos impact --diff`(審查用影響清單)、`lumos testmap`(依 diff 建議該跑哪些測試)、`lumos link-candidates`(補連結候選)、`lumos context --recommend`(圖分融合,目前沒接進任何預設流程)、`lumos handoff`(見 [[Projects/接手視圖_計劃]])、推播漏網量測([[Projects/推播miss量測_計劃]])與推播利用率量測([[Projects/主session鏡頭利用率_計劃]])。

## 世界解註解

欄位:出處與日期、怎麼運作、證據強度(A 受控實驗或方法公開的基準｜B 生產數據或廠商自報｜C 實務經驗｜D 行銷宣稱)、註解深度、跟 Lumos 的關係。來源編號見文末。研究筆記標「未複驗」的照標。

### 推還是拉

**1. Delivery, Not Storage(線索錨定的工作記憶)**
- 出處:arXiv 2607.20972,2026-07-23,單一作者〔來源 1〕。
- 怎麼運作:主張操作性事實由 harness 依線索(路徑 glob、符號、語意、事件、時間)確定性注入,不讓 agent 自己決定讀不讀。平常給精簡索引,線索命中給全文;每個 session 一本觸發帳壓掉重複注入,並在壓縮邊界重置。
- 結果:自願組 114 輪裡 0 次記憶操作;只存在對話裡的 10 個事實,108 次壓縮有 106 次全數遺失,放在 harness 自有儲存的 138 次全數送達。
- 證據強度:C。單一任務、作者即實作者,自稱只是方向性證據;符號與時間兩類觸發在評分中從未觸發｜註解深度:讀全文。
- 跟 Lumos:驗證「確定性推播」;可借鏡「壓縮後重置冷卻窗」與「命中時給全文」。它宣稱逐字稿不記改檔前 hook 的注入,這點與 Claude Code 官方文件、Lumos 自己在逐字稿量到的注入附件都衝突。

**2. Claude Code 路徑規則與子目錄 CLAUDE.md**
- 出處:官方文件 memory、context-window,2026-10-11 讀〔來源 2、4〕。
- 怎麼運作:規則檔用 paths glob 限定範圍,Claude 讀、寫、改(含 cat、head 這類讀檔指令)碰到相符的檔就把整份規則載入;這些載入算訊息歷史,壓縮時會被摘要掉。官方說記憶是「上下文,不是強制設定」,建議 CLAUDE.md 少於 200 行。
- 證據強度:官方行為說明;「越長遵循度越低」是經驗談,沒附數據(C)｜註解深度:讀官方文件。
- 跟 Lumos:原生功能重疊,也是可借鏡——原生在「讀」時就推、推全文;Lumos 只在改檔前推、只推名。

**3. 跨廠商的依路徑推:Cursor rules、Copilot applyTo、Kiro steering、Windsurf rules**
- 出處:Cursor、Copilot、Kiro 官方文件 2026-10-11 讀;Windsurf 只有二手來源〔來源 5、6、7、53〕。
- 怎麼運作:四家都有「永遠載入/依 glob 載入/依描述由 agent 判斷/手動」幾種模式;Cursor 套用時把規則全文放在上下文開頭,Kiro 的 fileMatch 只在處理相符檔時載入。Windsurf 字元上限 6,000/12,000 未複驗。
- 證據強度:官方行為說明,沒有效果數據(C)｜註解深度:Cursor、Copilot、Kiro 讀官方文件;Windsurf 二手。
- 跟 Lumos:驗證「依檔推」已是業界標準形態;延伸——可把事故路徑規則投影成這些格式,讓 Lumos 不支援的 harness 也收得到。

**4. Claude Code hooks 的 additionalContext**
- 出處:官方 hooks 文件,2026-10-11 讀〔來源 3〕。
- 怎麼運作:多數事件都能回傳附加上下文,以系統提醒形式插在觸發位置;單一字串上限 10,000 字元,超過只給路徑加 2,000 字預覽,而且不會要求模型去讀。官方建議寫成事實陳述,命令式寫法可能觸發提示注入防禦、改成浮給使用者看。注入會存進逐字稿,SessionStart 在壓縮後會重跑。
- 證據強度:官方行為說明(C)｜註解深度:讀官方文件。
- 跟 Lumos:驗證推播走官方管道、逐字稿量得到;可借鏡——Lumos 框外那句「動手前看一眼上面這些筆記」是命令式。

**5. Vercel:AGENTS.md 裡的索引勝過 skills**
- 出處:Vercel 部落格,2026-01-27〔來源 9〕。
- 怎麼運作:Next.js 16 新 API 任務。無文件 53%、skill 預設 53%、skill 加明確指示 79%、AGENTS.md 放一份 8KB 壓縮文件索引 100%;skill 在 56% 案例裡從未被呼叫;「You MUST invoke」這種措辭反而讓 agent 錨在文件上。
- 證據強度:B。自家評測,任務數與模型沒揭露,作者自稱解釋只是工作假設｜註解深度:讀全文。
- 跟 Lumos:驗證「推」勝過「等 agent 自己拉」,也提示關鍵是「被動、始終看得到」——Lumos 的推播是一次性的,還會被壓縮掉。

**6. ETH〈Evaluating AGENTS.md〉**
- 出處:arXiv 2602.11988,2026-02-12〔來源 10〕。
- 怎麼運作:SWE-bench Lite 300 題加 AGENTbench 138 題,跨 Claude Code、Codex、Qwen Code。LLM 生成的脈絡檔成功率平均 −0.5%/−2%;開發者寫的約 +4%,但在 Claude Code 上沒改善;成本 +20%/+23%。agent 確實照檔裡的指示做,但脈絡檔沒有縮短「第一次碰到該改的檔」之前的步數。
- 證據強度:A(方法公開,偏 Python)｜註解深度:讀全文。
- 跟 Lumos:支持推播要依情境、少量;對開場長紀律是挑戰(屬別類)。

**7. 〈Do Context Files Help Coding Agents?〉兩代理消融**
- 出處:arXiv 2607.27250,2026-07-28〔來源 11〕。
- 怎麼運作:Claude Code 與 Codex,3 個 repo、17 個真實任務、288 次評分;脈絡注入策略對正確率沒有可量測影響,等價檢定把影響界在 10–15 個百分點內;失敗多半是實作能力,不是缺 repo 知識。
- 證據強度:A−(只讀摘要,小樣本)｜註解深度:二手/摘要。
- 跟 Lumos:挑戰——推播對任務成敗的效益要用結果層證據證明,Lumos 沒有這種證據。

**8. GitHub Copilot Memory(帶引用的記憶,使用前即時驗證)**
- 出處:GitHub 部落格 2026-01-15(作者 Tiferet Gazit;另一網址路徑寫 01-09,以頁面為準)〔來源 12〕。
- 怎麼運作:每條記憶含主題、事實、指向程式位置的引用、理由;開場依「最近」挑進提示;用之前先讀引用處驗證,錯了存更正版,對了刷新時間。
- 結果:PR 合併率 90% 對 83%,code review 正面回饋 77% 對 75%,p<0.00001;植入與程式矛盾的記憶,agent 會自我修正。
- 證據強度:B(廠商 A/B,方法揭露有限)｜註解深度:讀全文。
- 跟 Lumos:驗證「程式碼為主、筆記要對得回程式」;可借鏡「推出去的當下驗引用」;它也是「推內容」那一派的生產證據。

### 檢索器本身

**9. Cognition SWE-grep(強化學習訓練的快速檢索子代理)**
- 出處:cognition.com 部落格,2025-10-16〔來源 13〕。
- 怎麼運作:只給 grep、read、glob,每輪最多 8 個並行呼叫、最多 4 輪,輸出「檔+行範圍」;獎勵是檔級與行級加權 F1,評估刻意用 F0.5(偏重精度),作者明說「汙染比遺漏更傷」。
- 證據強度:B(廠商自報,F1 只畫在圖上)｜註解深度:讀全文。
- 跟 Lumos:可借鏡指標設計;與 Lumos「固定席寧多勿漏」有張力。

**10. Cursor 語意搜尋(拿 agent 軌跡訓練嵌入)**
- 出處:cursor.com 部落格,2025-11-06〔來源 14〕。
- 怎麼運作:語意搜尋與 grep 並用;嵌入的訓練目標是吻合「LLM 事後排出的每一步最有幫助內容」。離線準確率平均 +12.5%;線上程式保留率 +0.3%,1,000 檔以上 repo +2.6%。
- 證據強度:B(廠商自報,小 repo 效果很小)｜註解深度:讀全文。
- 跟 Lumos:可借鏡——「軌跡當監督訊號」可零依賴用在標註,不必用在嵌入;嵌入本身違反零依賴家規。

**11. Aider repo map(tree-sitter 加個人化 PageRank)**
- 出處:aider 原始碼 commit 5dc9490,2026-05-22〔來源 16〕。
- 怎麼運作:抽出每支檔定義與引用的符號,建「引用檔→定義檔」加權圖跑個人化 PageRank(以任務相關的檔為起點的 PageRank);被提到的識別字權重 ×10、在 5 支以上檔被定義的識別字 ×0.1;輸出受 token 預算控制(預設 1,024),用二分搜尋讓長度落在目標 ±15%。
- 證據強度:C(沒找到消融);Agent Retrieval Bench 摘要稱它在 8K 預算下產出最好｜註解深度:讀碼。
- 跟 Lumos:驗證「到處都有的詞要降權」(同構於扇出降權);可借鏡「用字元預算而非篇數控制推播長度」。

**12. LocAgent**
- 出處:arXiv 2503.09089,2025-03〔來源 17〕。
- 怎麼運作:把 repo 建成目錄、檔、類、函式的異質圖,給 agent 搜尋實體、走圖、取實體三個工具。消融(微調 7B,完整 88.32/71.53):拿掉走圖 86.13/66.06,拿掉搜尋實體 68.98/53.28,拿掉 BM25 索引 75.18/60.22(檔級 Acc@5/函式級 Acc@10)。嵌入檢索 84.67 對 BM25 61.68(檔級)。
- 證據強度:A｜註解深度:讀全文。
- 跟 Lumos:驗證「圖訊號打不過調好的關鍵字搜尋」;嵌入對 BM25 的差距是對零依賴家規的挑戰。

**13. RepoNavigator〈One Tool Is Enough〉**
- 出處:arXiv 2512.20957,2025-12〔來源 18〕。
- 怎麼運作:只給一個語言伺服器(LSP,編輯器用來跳定義、找引用的服務)的跳轉工具,用強化學習訓練 issue 定位;7B 消融中多加三個結構工具反而讓 IoU 從 24.28 掉到 13.71。
- 證據強度:A(只做 Python,gold 來自 patch)｜註解深度:讀全文。
- 跟 Lumos:驗證「少而準的訊號勝過多路圖工具」;支持結構查詢委派給原生 LSP,不自建程式圖。

**14. HippoRAG 與 HippoRAG 2**
- 出處:arXiv 2405.14831(NeurIPS 2024)、2502.14802〔來源 19〕。
- 怎麼運作:個人化 PageRank 的種子乘上「特異度」(這個詞出現在幾段的倒數,也就是 IDF 的概念);拿掉後平均 R@2 從 57.4 掉到 54.7。第 2 版把所有原文段落也當種子、但只給 0.05 權重,掃描 0.01–0.5 以 0.05 最好。建摘要圖的方法(GraphRAG、LightRAG)QA 分數落後,索引成本高一到兩個數量級。
- 證據強度:A｜註解深度:讀全文。
- 跟 Lumos:驗證撤掉「入連結數當權威度」與 PPR;若要重試圖擴散,種子要用特異度加權。

**15. RAG 對 GraphRAG 系統比較**
- 出處:arXiv 2502.11371,v3 2026-03-04〔來源 20〕。
- 怎麼運作:單跳 NQ 上普通 RAG 64.78 勝過社群式全域搜尋 54.48;全域搜尋在資訊不足題只有 19.27;建出的知識圖只涵蓋約 66% 答案實體;LLM 評審有位置偏差,兩份摘要對調順序結論可能翻轉。
- 證據強度:A｜註解深度:讀全文。
- 跟 Lumos:驗證不做社群摘要——改檔前推播本質是單跳查詢;可借鏡「用 LLM 評審時要對調位置」。

**16. Lucene CJKBigramFilter 與中文 IR 研究**
- 出處:Lucene 9.11 文件 2026-10-11 讀;Nie 等人只讀摘要〔來源 24〕。
- 怎麼運作:對漢字、平假名、片假名、諺文四種文字預設切兩字一組,孤立字輸出單字,可選同時輸出單字與兩字組。Nie 等人:用詞或用 n-gram 建索引效果相近,最佳是最長匹配分詞加單字。
- 證據強度:A(標準實作加 foundational 研究)｜註解深度:讀官方文件+二手。
- 跟 Lumos:缺口——Lumos 對長段漢字只切兩字組、不出單字,假名與諺文完全不切。

**17. 隱式回饋、交錯比較、frecency、doc2query**
- 出處:Joachims SIGIR 2005、Radlinski CIKM 2008、zoxide 演算法文件、doc2query arXiv 1904.08375〔來源 26〕。
- 怎麼運作:點擊有偏好高名次的偏差,但「點了這個、跳過上面那個」的成對偏好與人工判斷大致一致;交錯比較(把兩個排序交錯合成一張清單,看使用者點哪邊多)比八種絕對指標都更能分出優劣;frecency(頻率加新近度)每存取 +1、依時間衰減;doc2query 離線預測文件會被怎麼問、附加進文件。
- 證據強度:A(foundational)｜註解深度:二手/摘要。
- 跟 Lumos:可借鏡,全部都能零依賴做;推播漏網量測自承的位置偏差,標準解就是交錯或成對偏好。

### 變更影響

**18. Meta Predictive Test Selection**
- 出處:arXiv 1810.05286,2018-10(PDF 第 3–7 頁直接讀)〔來源 21〕。
- 怎麼運作:用歷史測試結果學「這次變更會讓哪些測試失敗」;特徵含近期變更次數、歷史失敗率、建置依賴圖距離,以及改動檔與測試路徑的共同詞元數(詞彙距離)。交付策略是「過門檻的 ∪ 分數前 k 名」;每週重訓,過預設條件才換上;另抽約四分之一變更跑全部測試,取得無偏的召回估計。
- 結果:基礎設施成本減半,仍抓到 95% 以上的個別測試失敗(結果段數字取自摘要)。
- 證據強度:A/B(生產規模,方法公開)｜註解深度:讀全文(第 3–7 頁)。
- 跟 Lumos:驗證推播「門檻+名額+保底」的形狀;可借鏡「抽樣跑全量」來無偏估計截斷線漏掉多少。

**19. ROSE 共改挖掘與共改學習排序**
- 出處:ICSE 2004/TSE 2005;arXiv 2411.19099、2512.19481〔來源 22、23〕。
- 怎麼運作:ROSE 從版本史挖關聯規則,改 A 時建議常一起改的 B;前三個建議含正確位置約 64%–70%(取自搜尋摘要,未逐字複驗)。共改學習排序 NDCG@5 勝其他方法 2.5–12.8%,歷史超過 60 天會衰退。另一篇讓 GPT-5 直接判變更影響,precision、recall、F1 中位數全是 0。
- 證據強度:A(ROSE)/A−(後兩篇)｜註解深度:二手/摘要;LLM 影響分析那篇讀了結果段。
- 跟 Lumos:驗證「共改當警告不當排序權重」與「lumos 只算不判、模型只判不算」的分工。

### 評測

**20. ContextBench**
- 出處:arXiv 2602.05892,2026-02〔來源 27〕。
- 怎麼運作:1,136 個 issue、66 個 repo、8 種語言,人工標出解題需要的上下文,沿 agent 軌跡量召回、精度、冗餘與「證據丟失」(看過但沒留在最終上下文的比例)。精巧鷹架只帶來邊際改善;召回與成功率正相關;證據丟失 Claude 0.196、GPT-5 0.179。
- 證據強度:A｜註解深度:讀全文。
- 跟 Lumos:驗證——Lumos 的推播利用率與證據丟失是同一件事的兩面;延伸成「推了→讀了→改動有沒有遵守」整條鏈。

**21. Agent Retrieval Bench**
- 出處:arXiv 2607.24882,2026-07-27(部分讀)〔來源 28〕。
- 怎麼運作:427 個樣本、25 個 repo,相關性定義為「agent 下一步需要什麼」;含 edit2ripple(給一支檔的 diff 找其他受影響檔)與 50 題自然「沒有答案」題。用對照題校準的棄權門檻在自然無答案題上反而變差(作者稱校準落差)。種子介入:無種子 F1 0.3222、字面法種子 0.3981、oracle 0.6337。
- 證據強度:A−(很新、單次、沒有信賴區間)｜註解深度:讀全文(部分)。
- 跟 Lumos:驗證「給好的初始上下文能提高 agent 檢索」這個推播前提;缺口——Lumos 考卷沒有刻意的無答案題。

## 借鏡與補強候選(排序)

排序依據:能不能打到 Lumos 自己量到的最弱環節、獨立來源有幾個、成本、能不能用 Lumos 自有評測(查詢考卷、推播漏網、情境探針、消融)驗證。跟研究筆記的排序不同處:研究筆記把「推條款原文」排第一;本篇把「推播開關的結果層對照」提到第一,因為兩份核對都確認 Lumos 從沒量過推播對任務結果的效果,沒有這把尺,其他推播改動(包括推條款)都只能看碰觸率,而碰觸率分不出「沒送到」和「送到沒用」。

### 1. 推播開關的結果層對照,加送達金絲雀
- 要做什麼:同一組改檔任務,開與關改檔前推播各跑一臂,量違反合約次數、重犯已記錄事故次數、完成率、token 與步數;另加一臂注入一段事實陳述型的獨特標記,事後問模型引不引得出來,用來分開「沒送到」與「送到沒用」。
- 改哪個機制:改檔前推播加一個關閉開關;結果檔交給情境探針與消融那套(ablation-lumos-first 所管)。
- 最小版本:6–10 題「照常改會踩到某條合約或已記事故」的題,Claude 與 Codex 分臂(呼應〈Is Grep All You Need?〉的 harness 差異)。
- 怎麼驗證:這條本身就是驗證;差距要超出兩代理消融給的等價界(10–15 個百分點)才算有效果,落在界內就如實記「量不出」。
- 證據強度與成本:A(ETH、兩代理消融的方法)加 B(Copilot 生產 A/B);要探針額度;小樣本只給方向。量出「推播沒效果」也是有用結果——那會直接影響候選 2、3 值不值得做。
- 以前怎麼判過:結果層查無先例;排序層消融有(推筆記認家的旋鈕開關,量 P@8 與必看命中);2026-09-02 修法 A 消融拔的是開場紀律,兩組都保留推播 hook。
- 現況核對:Q02-10 答案與複查都判查無;改檔前推播沒有關閉開關,14 個排序旋鈕只供網格消融。Q02-08 兩份都判查無常設送達驗證,只有 2026-09-03 對子代理那一次實測。

### 2. 必看合約推條款摘錄(線索命中給內容,平時給指標)
- 要做什麼:改檔前推播的必看段裡,帶 `★INVARIANT★` 或 `★IRREVERSIBLE★` 的節點,在框內附該合約行的清理後摘錄,總長設上限。
- 改哪個機制:改檔前推播的輸出組裝;抽取與截斷直接重用派工鏡頭已有的做法(只從主線可達的版本讀、每行截 200 字)。
- 最小版本:旋鈕預設關;分支上新寫的合約行不推;每行截短、總長不超過 2,000 字;放在框內並寫成事實陳述;按 session 分兩臂。
- 怎麼驗證:候選 1 的探針加「會違反某條合約」的題,量違約率;推播利用率按臂比碰觸率;考卷必看召回不能退。
- 證據強度與成本:C+(Delivery, Not Storage)、B(Copilot)、自家 [[Verification/2026-10-03_外部碼表推播小實驗]](審查席派工詞附內容,嚴格算 0/8 到 7/8)、自家碰觸率(固定席只有 1 篇時 0/16,改程式檔時 0/11);實作小。風險是注入:任何能寫進筆記的人,能把文字以接近系統的口吻送進主對話。
- 以前怎麼判過:明確否決。2026-09-06 起 hook信任邊界 為防注入,把觸發原因改成固定字彙、合約只印類別前綴,並把兩條要求印原文的斷言翻成守衛;派工鏡頭那一側推合約行與外部事實行則已實作。新證據夠不夠推翻:新證據全是「效用」面(碼表實驗、碰觸率、Copilot),當時的理由是「安全」面,所以**不足以單獨推翻,足以重開**——要裁的是「只讀主線版、截短、框內、事實陳述」能不能同時滿足安全;派工鏡頭已經在走這條路,是現成的先例。
- 現況核對:Q02-01 答案與複查一致判查無,改檔前推播只送節點名、種類標籤、合約類別。

### 3. 壓縮後重置冷卻窗
- 要做什麼:對話壓縮後,同一個 session 的冷卻標記作廢,下一次改同一支檔重推完整清單。
- 改哪個機制:改檔前推播的冷卻窗;觸發點用 SessionStart 的壓縮來源。
- 最小版本:先實測一次,因為壓縮後 hook 拿到的 session 編號會不會換,repo 答不了——同一支檔 20 分鐘內「改一次→手動壓縮→再改一次」,看暫存目錄有沒有多出新的 session 資料夾、第二次注入是完整清單還是只有事故段。編號會換就等於已經重置,不用做;不換才實作。
- 怎麼驗證:推播漏網量測多一欄「壓縮後 20 分鐘內的改檔有沒有完整推播」,前後比漏網數。
- 證據強度與成本:C+(Delivery, Not Storage 壓縮遺失 106/108)加官方文件(hook 注入與路徑規則都在訊息歷史裡,壓縮會被摘要掉);很小;風險是重複注入讓上下文變長。
- 以前怎麼判過:查無先例。相鄰的「壓縮後重新注入紀律」被 lumos-context 列為不選,理由是開場 hook 本來就會再跑——那是開場紀律,不是改檔推播。主動影響幅度偵測計劃選 20 分鐘時間窗時考慮過「早先注入被壓縮捲走」,選了時間窗而不是偵測壓縮。
- 現況核對:Q02-02 兩份一致判查無;全 repo 唯一碰壓縮的是 lumos-context 外掛,而它的結構測試禁止它碰檔案系統,碰不到冷卻標記。

### 4. 單字漢字與假名、諺文的詞元修正
- 要做什麼:查詢是一個漢字時,讓長段文字裡的出現也能得分;順手讓假名與諺文切成兩字一組。
- 改哪個機制:retrieval-ranking 的切詞。
- 最小版本:查詢詞元是單一漢字時,直接數候選各欄文字裡的出現次數當詞頻,文件長度不變;查詢沒有單字詞元時程式路徑完全不變。
- 怎麼驗證:搜尋卷單字 4 題(閘、坑、審、帳)的 nDCG@5 前後對照;其餘題可機械證明不變;另造日文、韓文 5 題。
- 證據強度與成本:A(Lucene 標準實作、Nie 等人);小。風險是高頻字爆量——當初只在查詢端切單字就是怕「系、統、計」淹沒排序;這條只動單字查詢。
- 以前怎麼判過:查無先例,單字只被當評測題討論過(查「的」會爆到 500/516 篇)。切詞函式的說明掛著 2026-11-14 再看要不要擴大字元範圍的回頭條件。
- 現況核對:Q02-03 兩份一致判查無。研究筆記量「閘」489 個候選 425 個 0 分;答案檔量「審」684 篇只有 36 篇大於 0、「檢」537 篇只有 6 篇;複查量到某篇計劃 62 次「審」只有 9 次被計分;假名、諺文切詞結果是空的,分數全 0。

### 5. 考卷加「無答案題」,量誤推
- 要做什麼:改檔卷加約 10 題確實沒有相關節點的改動(新目錄、純格式改動),新增「誤推篇數」指標,計分不再跳過這類題。

- 最小版本:先只加題與指標,不動門檻;有了數字再在訓練卷網格選動態門檻係數(現為 0.65)、在保留卷驗證。
- 怎麼驗證:P@8 與誤推數兩把尺都不能退。

## 世界證據對 Lumos 做法的挑戰

- **推指標還是推內容**:推內容的一派有 Delivery, Not Storage、Copilot Memory、各家原生規則;推指標的一派有 Anthropic 的 just-in-time 主張與 Vercel 的索引(但那份索引始終在上下文裡)。Lumos 對必知合約也只推名,自家碰觸率 0/16、0/11 指向「推了名字沒人去讀」。這是安全與效用的取捨,不是疏漏;以前為安全否決過,新證據只在效用面(見候選 2)。
- **精度優先還是寧多勿漏**:Cognition 用 F0.5、IFScale 與 Chroma 說越多越不可靠;反方是 ContextBench 的召回與成功率正相關,以及 Lumos 自己「固定席越多碰得越多」的數字。固定席上限要用結果實驗定(候選 1、11)。
- **推更多知識不保證任務成功**:ETH 與兩代理消融都這樣說。Lumos 的評測停在排序指標與「碰觸」,沒有結果層——這是本類最大的挑戰。ETH 這一面以前在散文紀律那篇 Issue 引過,不算新;兩代理消融的等價界是新的。
- **語意檢索在大 repo 有增益**:Cursor、LocAgent(84.67 對 61.68)。零依賴家規明確否決嵌入;新證據沒有改變家規。替代路是別名、doc2query 式擴充、讓 agent 自己改寫查詢;但 Lumos 同義詞題只有 4 題、別名覆蓋 12%,這個缺口多大目前量不出。
- **量測儀器的效度**:推播漏網與利用率都建在逐字稿上;官方說逐字稿是內部格式會變,#19432 顯示「有紀錄」不等於「送到了」。Lumos 有 fail-open 與版本表,但沒有常設送達驗證(候選 1 的金絲雀)。
- **不造狀態源 vs 造進度檔**:Anthropic 造進度檔與功能清單;Lumos 明確否決,理由是本 repo 每個新造的狀態源都被實測打穿。世界沒有對照數據可裁,維持現狀。
- **「圖傳播打不過 BM25F」的適用範圍**:成功的 PPR(HippoRAG)用特異度加權種子並低權重納入原文;Lumos 試的版本有沒有這樣做,對照檔查無。這條結論在 GraphRAG 調研已寫成前提(候選池中位數 3 篇、推薦位 8 個)並掛了回頭條件,應讀成「在這份考卷、這個天花板下成立」。

## 筆記與程式或來源對不上的地方

- **[[Projects/按需檢索_計劃]]**:摘要的現況行與正文都說改檔前推播「窗外推固定席加前 8 篇並貼內容」。實際:程式只印節點名與固定字彙標籤(Q02-01 答案與複查一致)。那句是現況描述,以程式碼為準;建議改掉那兩句,並立一篇 Issue 記錄這句筆記錯在哪。
- **研究筆記的候選 9(D3 委派 LSP)**:研究筆記在候選表把「D3 計劃明文『結構查詢委派 LSP』」寫在最小版本欄,讀起來像現況。實際:D3 計劃與全圖譜都沒有 LSP 字樣,全圖譜只有 impact 鏡頭機械化計劃描述別家工具時提過一次(本篇 2026-10-11 用 grep 複查同結果)。處理:本篇已改寫成候選 13 的「要補的決定」。
- **使用紀錄帳的版控狀態**:lumos-cli-read 與 [[Projects/治理帳例行紀錄分流_計劃]],以及寫入它的程式註解,都說這支本機帳「被忽略、不進版控」。實際:它從 2026-10-08 的提交 532f5a15 起被 git 追蹤,10-09 合併後同時被追蹤又被忽略規則列名,遠端主線也有;doctor 有軟提醒「已被版控追蹤,忽略規則對它無效」,但不擋。本篇 2026-10-11 用 git ls-files 複查仍在追蹤。建議由使用者決定是否從版控移除(會改 git 狀態,本次沒做),並修正那幾句描述。
