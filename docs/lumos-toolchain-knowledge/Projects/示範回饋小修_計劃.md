# 示範回饋小修_計劃

> 白話:後端示範(搶購下單)走完整套流程時碰到的小毛病,挑改動小、確定該修的一起修:①建計劃筆記時名稱完全沒有後綴,建好後提醒慣例與重建指令;②需求階段出題補「量級」,架構階段補「同步回結果還是先收下再通知」;③設計審記帳手冊把「彙總那筆」的條數規則講清楚。來源是 [[Verification/2026-10-13_後端示範交付]] 的改進候選。

PRIOR-ART: ①沿用既有慣例與既有提醒形狀(圖譜紀律「計劃一律寫成 Projects/<主題>_計劃」;2026-10-13 實數 340 篇:280 篇「_計劃」、33 篇「_調研」、其他後綴 17 篇、完全沒底線 10 篇;提醒照 `new system` 沒寫 about_code 時建好再提醒的形狀);②沿用需求風險面表的既有形狀(id/stage/q/when),只加兩列;③只改手冊措辭。三項都不新建機制。
RETIRE-IF: ①上線 8 週內提醒出現時,建的人都照原名繼續用(沒有人照提醒重建)——提醒沒用,拿掉;②兩個新風險面上線 8 週內,在消費專案的待決問題裡沒有一題來自它們——拿掉。

## 做法

1. **計劃筆記沒有後綴就提醒**:`lumos new project <名>` 的名稱完全沒有底線後綴時,照原名建檔,建好之後印「提醒:計劃筆記的慣例是 Projects/<主題>_計劃…」與刪掉重建的指令(指令加引號,名稱帶空白或特殊字元也能照貼)。只看「完全沒有底線」:含底線但後綴不是 _計劃 的名稱(例:order_flow)不提醒——刻意放寬,免得干擾 _草案 這類既有寫法(代碼審 r2)。不擋、不改名:既有的 _調研、_草案 等寫法照用,改名會讓接著用原名下指令的人找不到這篇(代碼審 r1 架構對齊席:建檔指令對不合慣例的輸入從沒改過使用者給的名字)。其他類型不動。
2. **需求風險面補兩列**(`_REQUIREMENT_FACETS`,內容源在 [[Systems/情境出題]]):
   - `req-scale`(需求):量級多大——峰值每秒幾筆、資料量多少、熱點集中在少數幾筆還是分散?這會決定架構,要在定架構之前問。觸發:提到大量、高併發、搶購、搶票、秒殺、尖峰、流量、開賣、檔期、萬人/千人/百人、同時搶、很多人同時或一起(不用單獨的「同時」「活動」「搶」:一般句子太常見,代碼審 r1 量到改密碼的需求被誤判;r2 補回「上萬人同時搶」「開賣很多人一起下單」這類寫法)。
   - `arch-sync`(架構):結果要當場回,還是先收下、之後再通知(會牽涉要不要上佇列)?觸發:同上,再加排隊、非同步。
   - 既有的 `perf-target`(效能階段:目標數字與量測口徑)保留,問的是「怎麼量」,不重複。
3. **設計審記帳手冊**:`skills/lumos-design-loop/SKILL.md` 步驟 7 講彙總那筆的地方,補一句「彙總那筆的 `--findings` 填它自己報告的存活條數(不能多於它的報告),全輪的發現 id 放在 `--findings-set`」。

## 驗收條款

- [S1] 當 `lumos new project` 的名稱完全沒有底線後綴時,應照原名建檔,建好之後印出慣例提醒與重建指令;名稱有後綴(_計劃、_調研、_草案)時應原樣建立、不提醒;system 類型不出這個提醒;名稱帶空白、`$`、單引號時,提醒裡的指令照貼給 shell,切出來的參數應剛好是那一篇與正確的新名稱。[test: t_new_project_warns_missing_plan_suffix]
- [S2] 當計劃寫「活動開始時大量使用者同時下單」時,`pitfalls --stage 需求` 應列出 `req-scale`,`--stage 架構` 應列出 `arch-sync`(「秒殺活動當天開賣」「演唱會搶票」「上萬人同時搶限量球鞋」「雙十一檔期預期千人同時結帳」「熱門商品開賣很多人一起下單」同樣要列出);當計劃只寫「做一個會員資料修改頁」,或只出現「同時」「活動」這類一般詞時,兩者都不應出現。[test: t_stage_facets_scale_and_sync]
- [S3] 當讀設計審手冊步驟 7 時,應看得到彙總那筆 `--findings` 與 `--findings-set` 各填什麼。[manual: 讀 skills/lumos-design-loop/SKILL.md 步驟 7 有這句]
