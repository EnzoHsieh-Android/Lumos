# 人工指定高風險路徑_計劃

> 白話:讓人能在專案設定裡列出敏感路徑(例如登入、付款的目錄),改到就一律當高風險、推送前要過高風險代碼審。從 [[Projects/簡報審查抓到的機制缺口_計劃]] 移出:那份計劃的設計審連兩輪在這一件上被打穿,這裡重新設計。

PRIOR-ART: GitHub CODEOWNERS 用路徑指定敏感區要誰審(https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners),寫錯的行會被靜默略過;本 repo 讀宣告的既有做法:`_trusted_decl_ref`(起點與主線分叉點那一版)、`_lumos_config_at_ref`(ok/missing/unreadable/git-failed 四態)、殘留索引的改到檔清單(`git diff --name-only -z --no-renames`)。
RETIRE-IF: 有宣告這個設定的專案,一年內清單裡的路徑一次都沒被改到(用 git log --name-only 離線算)→ 檢討清單是否過時或拿掉這個設定。

## 依據來源

| 機制 | 依據 | 出處 |
|---|---|---|
| 用路徑清單指定敏感區、改到就加嚴審查 | GitHub CODEOWNERS 用路徑樣式指定誰必須審;語法錯的那一行會被略過,所以寫錯路徑要另外看得見 | https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners |
| 設定讀主線分叉點那一版、讀不出分四態 | 本 repo 既有讀宣告的做法 `_trusted_decl_ref` 與 `_lumos_config_at_ref` | `scripts/lumos` |
| 不能用提交訊息標記、改到的檔要自己算、理由串接 | 這份計劃移出前兩輪設計審的席報告與收貨判讀 | `governance/review-reports/簡報審查抓到的機制缺口/r2-intake.md` |

## 審查帶過來的問題

設計輸入,原文在 `governance/review-reports/簡報審查抓到的機制缺口/` 的 r1、r2 席報告;括號裡的 c、b、i、a 編號是 `r1-intake.md`、`r2-intake.md` 收貨時編的流水號(c 正確性、b 邊界、i 整合、a 架構對齊),對照與原文出處在那兩份收貨紀錄的判讀表:

- 不能用提交訊息標記:合併主線、空樹起點、壞編碼訊息、壓提交都會讓標記失效或誤升(r1 c1、c2、b1、b2、b3、i13)。
- 讀哪一版設定:起點要用主線分叉點那一版,否則分兩次推送就能先拿掉清單再改程式(r2 c2、b2、i1、a1)。
- 改到的檔要自己算:分級函式收到的清單已濾掉刪除、改名、權限、二進位與 .md/.json 的刪除,還會重複(r2 c1、b1、i2)。
- 讀不出時:沒宣告這個鍵的專案設定檔壞掉不該變 high;要分 git 讀不出與內容壞掉(r2 b3、c8、a3)。
- 寫錯路徑要看得見:推送路上只讀 JSON、人讀輸出只在 high 時印,提醒要走 doctor 或 JSON 欄位;路徑要先過 `_e2e_relpath_err` 與 NFC(r2 b4、i3、c10、a4)。
- 理由串接:殘留命中時提早回傳,會吞掉新理由(r2 b5、c7、i7)。
- 下游影響:合約測試變硬擋、high-only 表態閘、掛鉤提醒文字、掛鉤與測試檔要 anchor approve(r1 b6、i2;r2 i11)。
- 要一起改的文件:指令參考〈專案開關〉表(中英)、lumos-code-loop 的 SKILL 與 reference、06 指令頁、README「先判風險」(r1 i7;r2 i4)。
- 既有缺口:高風險改動用輕量審查通過也能推送,另見 [[Issues/高風險改動用輕量審查通過也能推送]];不修它,人工指定高風險只會多要一筆留痕。
