# 合約測試閘什麼時候跑_計劃

> 白話:一道閘該在「可能弄壞硬合約」的時候跑,而不是在「這段程式碼看起來危險」的時候跑。
> 現在它綁在後者身上。

診斷與可數事實在 [[Issues/合約測試閘只在高風險推送跑]];這一篇只講怎麼修。
盤點出處是 [[Projects/全repo審視_計劃]] 的主題 #17,那條明寫「這是一次判準變更,要人裁,不能順手改」。

## ★人裁(2026-09-07 Enzo)★

**低風險推送照樣把合約測試跑一遍,紅了印出來、記帳,但不擋推送;高風險照舊擋。**

裁的時候看到的三個數字(實測,不是估計):
- 多出來的成本**只有「真的跑那些測試」**,因為算「這次改動碰到哪些筆記」那一步
  **推送關卡本來就每次都在跑**(下面 [S1] 講)。這個 repo 現在是 46 支、約 42 秒。
- 消費端實測五個裝了 Lumos 的專案,**五個都沒宣告測試怎麼跑**,所以它們在第一步就返回,行為零變化。
- 但 42 秒兩週漲了六成(28.9 → 46),而且政策上還在推高綁定率,會繼續漲。

**為什麼不選「低風險也擋」**:擋下去最可能的結果不是人去修測試,是人改走 `--no-verify`——
而推送關卡自己在別的地方就把那條當第三選項在教,那條零留痕。
**為什麼不選「維持現狀只改文件」**:那會讓一條合約的守備範圍取決於另一支工具的風險判斷,
而改一行低風險的碼一樣可以打破合約。

## 先講幾個詞(不然下面看不懂)

- **波及計算**:`lumos impact --diff`,吃一段改動範圍、算出受影響的筆記並排序。
- **固定席**:波及計算的輸出裡,帶硬合約或出過事故的那幾篇,無條件排前面。
- **可過濾的測試指令**:專案宣告的測試指令裡有「跑哪一支」的佔位符(例如 `pytest -k {method}`)。
  沒有佔位符就只能整套跑。

## 前兩輪把兩個前提打掉了,這裡誠實記

**r1**:五席用三組實測與一條既有裁定否掉了「把呼叫搬出風險分級」的字面做法。
**r2**:五席又否掉了 r1 逼出來的替代方案,而且推翻了 r1 的前提本身:

- ★r1 拿來否決我的那條裁定,本身已經作廢★:2026-08-02 裁「不准把波及計算掛進推送熱路徑」
  (理由:慢 26 倍),但**同一篇計劃在 2026-08-22 補了一行說那條已作廢,
  因為推送關卡現在本來就無條件對每次推送跑一次完整的波及計算**(名字叫 sync nudge)。
  查證屬實:那支在判風險分級**之前**、對每個要推的 ref 各跑一次,而且不是便宜分支。
  **所以「要避開這個成本」這個前提整個不成立——它已經在那裡了。**
- r2 為了避開那個不存在的成本,發明了「反過來算」(拿綁測試的節點問它們點名哪些檔再取交集)。
  r2 通才席實測:**現有 10 篇綁測試的節點裡有 2 篇會永遠算不出交集**,
  而且剛好是這道閘自己的治理節點,觸發條件是全庫改動最頻繁的那個檔。**那是漏洞不是取捨,已刪除。**
- r2 邊界席實測:那個「便宜」的第 3 步如果照 r2 寫的「重用既有實作」,
  跑起來要 16 到 59 秒——因為既有實作第一行就是呼叫那支貴的波及計算。**自相矛盾,已刪除。**

## 設計

### [S1] 判斷順序:重用已經算過的,不要再算一次

一道獨立的判定,依序問,**任一步答「沒有」就記一筆帳、當場返回**:

1. **這個專案有沒有宣告測試怎麼跑?**(讀一個設定檔,近乎免費)
   沒有 → 記 `no-config`,返回。**消費端實測 5/5 停在這裡。**
2. **這個圖譜裡有沒有任何硬合約行綁了測試?**(對已載入的圖譜掃一次,實測 0.001 秒)
   沒有 → 記 `no-bound`,返回。
3. **拿推送關卡已經算好的那份波及結果**,取其中「帶合約且綁了測試」的節點。
   ★不另外算一次、也不自己發明一套便宜的近似★——sync nudge 每次推送都在算同一件事。

   ★具體的傳遞方式(r3 兩席都判 blocking:上一版只寫「要接起來」沒寫怎麼接,
   照字面實作會變成一次推送算兩次,那正是原本要避免的事)★:

   - 推送關卡對每個 ref **算一次** `lumos impact --diff <範圍> --json`,結果寫進一個暫存檔。
   - `impact` 新增 `--sync-only --from-json <檔>`:不再自己算,直接讀那份結果來印同步點名。
   - 新的合約測試判定同樣吃 `--from-json <檔>`。
   - **失敗隔離**:算不出來時暫存檔不存在或是空的——同步點名維持現在的行為(靜默),
     合約測試判定記 `range-unavailable` 放行。★一個失敗不准拖垮另一個★。
   - 暫存檔在 ref 迴圈結束時刪掉,不進版控。

   沒有這種節點 → 記 `no-pins`,返回。
4. **跑那些測試**(★但先看下面那條例外★)。
   - **例外(見 [S4]):測試指令不可過濾、而且這次是低風險 → 不跑,記 `whole-suite-deferred`。**
     這條在第 4 步之前判,是 [S1] 唯一的例外,[S4] 只是講它的理由。
   - 低風險:紅了印出來、記 `red-advisory`,**放行**。
   - 高風險:紅了擋,訊息要講「這要修測試,不是補審查留痕」。

### [S2] 拆成獨立的判定入口

新增 `lumos bound-tests --diff <範圍> [--json] [--advisory]`(**扁平頂層指令,不包子動詞**——
這個 repo 對單一動詞的工具一律扁平,群組式是留給天生有兩個以上動詞的)。
回傳三種狀態:`green` / `red` / `nothing-to-run`,擋不擋由呼叫端依 `--advisory` 決定。

**為什麼一定要拆**(r1 外家席判 blocking):現在合約測試紅了會讓 `code-loop check` 回 rc1,
而推送關卡把所有 rc1 一律解讀成「高風險改動還沒審查」,叫人去跑 `code-loop pass`——
**留下審查紀錄修不好一支紅掉的測試,下次照樣被擋**。訊息與處置必須分流。

### [S3] 新分支首推:改用主線當起點,不要用空樹

現在遠端沒有那條 ref 時,推送關卡拿「空樹到 HEAD」當範圍,於是整個 repo 都是 diff,
那支判定直接記 `diff-unavailable` 放行——所以「每次推送都跑」在首推時是假的。

**改法不是拿掉特例、讓它跑滿全部**(r2 圖譜席算過:首推時交集近乎全中,
等於每個新分支的第一次推送都跑滿全部合約測試)。
**改法是給它一個有意義的起點**:遠端沒有那條 ref 時,改用主線 tip 當起點。

★改在哪一側要講死(r3 通才席判 blocking:上一版兩種讀法都通)★:
**改在 Python 那一側,不動推送關卡的 bash。** 具體是:合約測試判定看到起點是空樹雜湊時,
不再直接記帳返回,而是自己去問主線 tip(判準沿用既有的那支 `_mainline_ref`:
依序試已推上去的 main / master、再試本地的)。
★那支現在只有派工鏡頭在用,而且埋在武裝流程裡★——本案要把它抽成一支乾淨的內部原語再共用,
不要把武裝流程的副作用一起拖進來。
主線也問不到(全新的 repo)才記 `range-unavailable` 放行,並印一行說明。

### [S4] 不可過濾的測試指令:低風險不跑,誠實記

沒有佔位符時只能整套跑,逾時上限 600 秒。**低風險推送不值得付這個**:
記 `whole-suite-deferred`、印一行「你的測試指令不能只跑一支,所以這次跳過;
把指令改成可過濾的,這道閘才會每次推送都保護你」。高風險照舊跑。
★不要假裝這種情況也守住了★。

### [S5] 逃生門

低風險不擋,所以不需要逃生門。高風險維持既有兩條:
CLI 旗標(要求非空理由,記 `skipped-flag`)、環境變數(CI 用,不要求理由,**改記成 `skipped-env`**)。
**整支繞過不留任何紀錄,本機無解**——誠實寫著,不要假裝回頭條件量得到它。

### [S6] 帳要數得出來,回頭條件才接得上電

- 按類別分帳:`green` / `red-advisory` / `red-blocked` / `skipped-flag` / `skipped-env` /
  `no-config` / `no-bound` / `no-pins` / `whole-suite-deferred` / `range-unavailable`。
- ★耗時要存成獨立欄位★:現在塞在自由文字的備註裡(「46 綠 41.8s」),
  回頭條件量不到。而且現在那個秒數**只算跑測試那段**,不含前面的計算——要分開存。

### ★那條「不能靠回頭條件」的,改成機械守衛了★

計劃裡寫得很清楚:同步點名**從不寫治理帳**,所以「它印了東西但那道閘說沒有」這件事,
帳上根本查不到——原本那條回頭條件看起來能查、其實不能。

守衛的做法是餵一份**合成的**波及結果(只點名一篇、範圍是假造的 `SYNTHETIC..RANGE`),
兩個消費者都必須只認那一篇;**而且加一條前置斷言**:同一個假範圍自己重算是算不出東西的
——所以上面兩條只可能來自那份檔。任一邊改成自己重算就翻紅(實測都紅)。

### 七個翻紅釘

| 弄壞什麼 | 測試 |
|---|---|
| 合約測試閘偷偷自己重算 | 紅 |
| 同步點名偷偷自己重算 | 紅 |
| 首推不換主線起點(退回舊行為) | 紅 |
| 紅了不分 advisory / blocked | 紅 |
| advisory 也擋 | 紅 |
| 不可過濾時照樣跑(低風險) | 紅 |
| 不可過濾時高風險也不跑 | 紅 |

★「advisory 也擋」那個探針第一次沒翻紅★——代表我當時**沒有任何測試在守「低風險不擋」**,
而那正是這次人裁的核心。補了才有。這是同一天第六次「斷言沒咬到目標層」。

### 既有測試翻紅三條,三條都是它們在釘舊行為

帳的類別從 `red` 拆成 `red-blocked`、`skipped` 拆成 `skipped-flag`、
首推從 `diff-unavailable` 變成真的換起點。**三條都是這一案刻意要改的行為**,
更新它們時把意圖釘得比原本更緊(例如首推那條現在同時斷言「不跑滿全部」與
「不再是舊的 diff-unavailable」,並補一條「連主線都問不到 → range-unavailable」的新現場)。

## 代碼審 r1:折入的九條(外家否決席六條、架構對齊席三條)

★外家席全部標「讀碼推論、未實跑」(它的沙箱不可寫),所以每一條我都自己敲過。★

| # | 是什麼 | 我怎麼查證 |
|---|---|---|
| 1 | **首推的起點用了主線 tip 而不是共同祖先**(blocker) | 造一個主線與 feature 各有獨有 commit 的 repo:`主線..feature` 動到兩邊的檔,`merge-base..feature` 只動到 feature 那個。**主線獨有的改動會被反向算進這次推送**,誤點到的合約若有紅測試,高風險那條路會擋掉一次本來該過的推送 |
| 2 | **範圍換過了卻還吃舊範圍算出來的結果**(major) | pre-push 給的 payload 是「空樹..HEAD」算的,而範圍已經換成「共同祖先..HEAD」;照樣吃就是**首推跑滿全部**,正是設計明令要避免的那條稅 |
| 3 | **多平台混合時整批判**(major) | 只要有一個平台可過濾就整批照跑,於是不可過濾的那幾個平台照樣被跑整套(單套逾時 600 秒) |
| 4 | **結果檔的形狀驗得太鬆**(major) | `{"results":[1],"sync":[]}` 這種合法 JSON 會通過,然後在下游拋例外、被 `\|\| true` 吞掉——**不是按設計記 range-unavailable,是靜默失效** |
| 5 | **`hard` 欄位沒跟著 kind 改名**(major) | kind 從 `red` 拆成 `red-blocked` 之後,那行還在比對舊的 `"red"`,於是**高風險真的擋下去的那一筆被記成 `hard:false`** |
| 6 | **暫存檔在硬擋或訊號時洩漏**(minor) | 清理只在 ref 迴圈正常尾端跑,而高風險 rc1 會直接 exit。加了 `trap ... EXIT INT TERM` |
