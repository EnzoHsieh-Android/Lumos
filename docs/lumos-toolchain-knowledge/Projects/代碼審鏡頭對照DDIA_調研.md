# 代碼審鏡頭對照DDIA_調研

> 白話:代碼審現在派出去的審查員,各自戴著不同「眼鏡」看 diff(正確性、邊界、架構對齊、資安……)。這次問的是:能不能照 DDIA 那本書的角度重新配眼鏡?答案是**可以借,但借法是「改到資料狀態才發那副眼鏡」,不是照書多派十個人**。

## 問題與範圍

- 問題:目前代碼審(code loop)的鏡頭,可否遵循 DDIA 模式。
- 「DDIA 模式」本篇解讀為:用《Designing Data-Intensive Applications》的角度審改動——資料會不會壞、壞了救不救得回、新舊版本能不能共存、衍生資料跟來源對不對得上、失敗和時間怎麼處理。
- 不在範圍:設計審(散文 spec)的鏡頭;只在需要對照時提。

## 現況:鏡頭從哪來(2026-09-29 讀程式與 skill 的觀察,以程式碼為準)

- 編制表(`scripts/lumos` 的 `_TIER_ROSTER`)只定「幾席、哪一家、必不必派」,鏡頭 1–4 是空位,**鏡頭內容由編排者臨場寫**。
- 鏡頭的文字來源:
  - 派工範本 [[Systems/design-loop]] 的 templates §3:正確性鏡頭四問(邊界、資源釋放、例外與 None、冪等與併發)、pitfalls manifest、圖譜鏡頭、一格本案特定鏡頭。
  - templates §7.7 立場表:正確性、邊界、整合知識同步、資源併發、回滾、架構對齊、資安、簡化。
  - templates §7.6 架構對齊席、§7.8 資安席。
  - 棧別效能檢核題([[Systems/效能檢核目錄]]):命中觸發詞才出題、作者先表態、審查席拿表態去反駁。
- 實際用了什麼:102 個代碼審迴圈、182 份派工紀錄裡,lens 欄是自由文字,「通才」字樣出現一百多次;具名鏡頭以架構對齊、正確性、邊界、合約與圖譜一致、資安為主。
- 一個結構性落差:pitfalls 的通用追問(含「部分失敗怎麼補償」「遷移順序與鎖表窗口」)只在審 `.md` 設計稿時印;`pitfalls --diff` 走 `_pitfall_diff_mode` 提早返回,不印那批。所以沒跑設計審的改動,這幾個 DDIA 味最重的問題沒人問。

## 逐項對照(獨立 agent 用原始問題核對,編排者抽驗兩條關鍵說法屬實)

| DDIA 面向 | 代碼審有沒有明確要求 | 說明 |
|---|---|---|
| 冪等與重試 | 有 | §3 正確性鏡頭明寫「重跑、同時進來會壞嗎」;Java/Python/Dart 棧別題問不可逆操作重送 |
| 交易與隔離 | 部分 | 有「兩個請求同時進來」、diff 追問「寫入有沒有交易包裹」、SQL 棧問隔離等級;讀-改-寫、lost update、write skew 沒點名 |
| 可靠性(部分失敗、寫一半) | 部分 | 只問資源有沒有釋放,不問當掉後留下什麼狀態;「中途失敗」只在高風險且剛好派了資源併發鏡頭時才有 |
| 擴展性與負載 | 部分 | 散在各棧效能題(大檔一次讀進、分頁、連線池),都是效能框架,沒有「量級長大十倍行為變不變」 |
| 可維運性 | 部分 | 可演進由架構對齊席蓋到;可觀測(出事看不看得到)沒有 |
| 資料編碼與演進(新舊互讀) | 沒有 | 只在 §3 本案特定鏡頭的填空範例提到 migration |
| 衍生資料 vs 真相來源 | 沒有 | 快取只從效能與記憶體上限問;沒人問失效、對帳、可重建 |
| 時鐘與時間 | 沒有 | 只在邊界填空範例提到時區;182 份派工 0 份提到時鐘 |
| 一致性保證(讀己之寫、順序) | 沒有 | 只有 Vue 非同步 watch 競態、Python 斷線重連兩個擦邊 |

## 為什麼跟本專案切身

- 本 repo 自己的資料形狀:append-only 帳本(治理帳、用量帳、canary 帳)、凍結快照與 sha256 指紋、派工鏡頭快取(20 分鐘有效)、testmap 與搜尋索引、frontmatter 欄位長期演進、多個會談同時寫同一個工作區。
- 知識圖譜裡 47 條 `PITFALL:` 行,用關鍵字粗分有 12 條落在 DDIA 類別(格式相容 4、冪等重跑 3、原子競態 2、順序 2、部分失敗 1、衍生資料 1;時鐘 0)。
  - 口徑:只數 `PITFALL:` 開頭的行、關鍵字正則比對,一行可同時算多類;沒逐條人讀,會有誤判與漏判。舊的 `KEY:` 事故行沒數。
- 消費專案更重:即時競價(RTB)、會員系統(.NET+SQL Server)、POS 與廚房出單(離線同步=副本衝突)、自動交易。

## 建議(候選,待 Enzo 裁)

1. **不照書新增固定席**。
   - 原因一:鏡頭數的增益在文獻上不穩(PBR),本專案 reference 已記「重點在異質驗證器 mix 而非 LLM 鏡頭數」。
   - 原因二:實際派工多數是通才,新增具名席不等於有人真的戴那副眼鏡。
   - 原因三:外家額度已經緊(2026-09-11 資安席上線當天就撞上限)。
2. **改成「命中才出題」的資料狀態題組**,沿用棧別效能檢核題那套機制:
   - 觸發:diff 的增刪行碰到寫檔/附加寫入/DB 寫入/快取/序列化格式/欄位增刪/migration。
   - 題目(每題都要能指出輸入和行):
     - 新程式讀舊資料、舊程式讀新資料,哪一邊會壞?
     - 寫到一半當掉(或被 kill),留下的檔/列是什麼狀態?下次啟動認得嗎?
     - 這份資料是真相來源還是衍生出來的?衍生的話,跟來源不一致時誰贏、能不能整份重建?
     - 同時兩個行程/會談讀-改-寫同一份,會不會有一方的修改被蓋掉?
     - 用時間戳排序或判過期的地方,時鐘倒退、時區不同、兩台機器時間不一樣會怎樣?
     - 量級變十倍時(帳本行數、節點數),這段的行為或時間會不會變性質?
   - 好處:沿用既有的表態閘與審查席反駁流程,不多一席;壞處:觸發字寫太寬會誤傷(棧別題已踩過「裸單字誤傷」)。
3. **補 §3 的一句通用提醒**:把「中途當掉後的狀態」「新舊版本互讀」加進正確性鏡頭的問句池,讓通才也吃得到——成本最低,但會稀釋既有四問的注意力,要跟 2 一起量。
4. **把設計審的通用追問接到 diff 路徑**:目前「部分失敗怎麼補償」「遷移順序」只在審設計稿時出現;沒跑設計審的改動就漏掉。這是結構性洞,跟 DDIA 無關也該看。

## 下一步:最小實驗(接線前先做)

- 講得出會翻紅的指令之前不建理論(見 [[Systems/診斷迴圈先行]])。
- 做法:從已過審、而事後在 PITFALL 裡記了 DDIA 類坑的迴圈挑 3–5 個,拿同一份凍結 patch 各派兩席——一席照舊通才、一席加上第 2 點題組——看誰指出那個已知坑。
- 判準:題組席命中已知坑的次數明顯多於通才席,才進 `_計劃` 接線;否則照 RETIRE-IF 撤。
- 限制:樣本小,只能看方向,不能下定論;逃逸帳目前放行數多半不到 20,也無法用它量效果。

## 最小實驗結果(2026-09-29)

- 做法:從本 repo 歷史挑 5 個已知的資料狀態類 bug,拿 bug 還在那版的改動,派 sonnet 審查員各審一次;A 組=現行正確性鏡頭,B 組=多給七題資料狀態題。審查員不知道要找什麼、不准讀現行檔(避免看到修法)。案 2、案 4 各組再重跑兩次。
- 材料:同時讀改寫(逃逸帳讀兩次)、時區(UTC 時間戳對本地日期)、不可逆刪除(整夾 rmtree)、衍生狀態(CI 重跑轉綠仍報紅)、寫一半(checkout 後寫回失敗丟行)。

| 案 | A 組 | B 組 |
|---|---|---|
| 1 同時讀改寫 | 0/1 | 0/1 |
| 2 時區 | 0/3 | 1/3 |
| 3 不可逆刪除 | 1/1 | 1/1 |
| 4 衍生狀態 | 1/3 | 1/3 |
| 5 寫一半(三個 bug) | 各抓到一個 | 各抓到一個,B 講得完整、多報救援指令救不回 |

- 結論:B 在 9 次裡多抓到 1 次,落在單次起伏範圍內——沒變差、可能稍好,不能說有效。
- 質性:B 的時間題 3 次裡 2 次答了卻判「沒問題」;題目只提醒看哪裡,不保證看對。案 4 第一次 B 被題目帶離、漏掉 A 抓到的洞(重跑後兩組同為 1/3)。
- ★量的是「題目放進審查員鏡頭」;「作者推送前表態」那個形式沒量過★。
- 後續:推送前表態版計劃經設計審 r1 後撤案重寫([[Projects/代碼審資料狀態題組_計劃]]),改走 [[Projects/代碼審資料狀態鏡頭_計劃]]。
