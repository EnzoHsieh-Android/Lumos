# 型錄接電要附證據_計劃

> 白話:型錄每列的「通電批次」欄會寫「批四(CI 範本:Android Lint)」,意思是消費專案照範本接上 Android Lint 或 compose-rules 後,CI 會擋這列的壞寫法。這個標記原本靠型錄自檢讀「現成規則」欄的字面判(段裡有規則碼、而且不含「待查」「相關」這類註記就算接上)。2026-11-08 代碼審三輪加一次事後審查,四次都抓到「標了會擋、那條檢查其實擋不到」的列:r1 是註記寫「相關」一類卻照算、r2 是 STATE-5 那條檢查只管呼叫位置、r3 是 ARCH-17 註記寫「只管」卻一個壞例都擋不到、事後審查是 PERF-1 的「需 `@WorkerThread` 標註」被反引號隔開躲過排除字;接著全表核對又找到三種漏法(檢查預設關、等級是 Hint 不會讓建置失敗、Slack 的檢查在範本裝的版本裡根本沒有)。字面判斷已經同類被打穿四次,這份計劃換形狀:每個「宣稱會擋」都要在型錄〈接電證據〉節有一筆判定,判定以真跑為準:照範本設定建最小專案,把壞寫法欄的例子原文放進去跑一次 Android Lint 與 detekt,報出而且讓任務失敗才算擋得到(這一步同時驗了會報、預設開、等級夠);編不過的少數才退回讀官方頁;自檢只認判定表,字面判錯的代價從「悄悄多宣稱」變成「被擋下來要補判定」。

PRIOR-ART: ①世界怎麼確定一條 lint 檢查管什麼:Android Lint 用測試樣本定義每條檢查會報什麼(`lint().files(kotlin("..."))`,https://googlesamples.github.io/android-custom-lint-rules/api-guide.html 〈Testing〉),最可靠的是拿壞例真跑。2026-11-08 先導實驗證明本機能真跑(AGP 8.13.2、Gradle 8.13 在快取,23 列全部編得過、報告齊全;卷證 `governance/review-reports/型錄接電要附證據/sweep/pilot.md`),而且真跑結果跟兩輪讀頁判定在爭議列上一致。②照範本設定跑就同時驗了預設開關與等級:沒開 `checkAllWarnings` 時只跑預設開的檢查,`warningsAsErrors` 讓 warning 升 error、Hint 不升(https://developer.android.com/reference/tools/gradle-api/8.7/com/android/build/api/dsl/Lint)。③粒度:lint baseline 以「issue id + 位置」為單位記錄(https://googlesamples.github.io/android-custom-lint-rules/usage/baselines.md.html),判定表照樣以(編號,標籤,檢查)為單位。④放哪:照型錄既有〈待查證〉節的做法,在同一份檔裡加一節、雙向比對(check.py 的 `_pending_table` 與 `pending_problems`)。排除:繼續補排除字表(四次被打穿)、另開 TSV(設計審 r1 架構對齊席:第二種做法)、用 lint-api 讀檢查清單當判定(只能讀已載入的套件,沒載入的會被誤判成不存在;設計審 r2 證據可信席)、抽樣真跑(抽樣框只含一邊;設計審 r2)。
RETIRE-IF: 範本裝的 lint 版本能在 CI 裡跑一次壞例樣本之後,判定表的「擋得到」改成以 CI 真跑為準、這張手寫判定撤掉;或判定表連續兩次全表重驗都 0 列翻案,降成只在新增列時要求判定。

## 用詞

- **型錄**:`skills/kotlin-idioms/checks-catalog.md`,一列一種 Kotlin/Android 寫法;**現成規則欄**是第 6 欄(登記哪些現成檢查管這列),**壞寫法欄**是第 3 欄,**通電批次欄**是第 10 欄。
- **批一**:型錄自己的 ast-grep 規則包已上線會擋;**批四**:消費專案照 linter 目錄範本接上 Android Lint(CI)或 detekt 外掛 compose-rules(推送前)之後才擋;**未接**:沒有任何檢查接上(型錄既有值)。兩個**標籤**:「CI 範本:Android Lint」「推送前:detekt 外掛 compose-rules」。
- **候選**:型錄自檢 `batch4_expected_tags` 從現成規則欄抽出的(標籤,規則碼)——只看結構(前綴加規則碼、不在 `B4_DEFAULT_OFF`、段裡不含排除字表 `_B4_SKIP` 的字);排除字只會讓候選變少(少宣稱),不會讓沒判定的宣稱成立。
- **判定**:〈接電證據〉節的一列,單位是(編號,標籤,檢查)——每個候選恰好一列。
- **真跑**:Android Lint 那個標籤:建一個最小 Android 專案,lint 區塊照 [[Systems/linter精選目錄]] 的範本(`warningsAsErrors`、`checkDependencies`),不用 baseline、不開 `checkAllWarnings`,讀報告逐筆看,不看任務結束碼。compose-rules 那個標籤:照推送前的命令跑 detekt CLI(`--build-upon-default-config --disable-default-rulesets --config configs/detekt/compose.yml` 加 compose-rules 外掛)。
- **擋得到**:Android Lint:真跑時那條檢查在樣本上報出,而且檢查**原本的等級**(升級前)是 Fatal、Error 或 Warning(範本的 `warningsAsErrors` 把 Warning 升成 Error,所以三者都會擋;Hint、Informational 不升,不擋;預設關的照範本設定根本不跑)。compose-rules:真跑時報出(`compose.yml` 裡是 active 的規則才會報;新增告警閘擋任何新告警),等級欄寫 detekt。一個標籤有多個候選時,任一個擋得到,那個標籤就算擋得到。
- **漏網帳**:`docs/.escape-log.jsonl`,放行之後才被抓到的缺陷紀錄(`lumos loop escape --list` 看)。

## 範圍

1. **〈接電證據〉節**:型錄在〈待查證〉節之後新增一節。第一行固定是 `真跑環境:<日期>,AGP <版本>,Gradle <版本>,<套件>@<版本>…`(記這次真跑用到的 lint、androidx 各套件、Slack compose-lints、資安包、detekt、compose-rules 的版本)。接著一張表,欄位「編號 | 標籤 | 檢查 | 判定 | 等級 | 理由 | 出處」:
   - 判定只收「擋得到」「擋不到」;等級只收 Fatal、Error、Warning、Hint、Informational、detekt、沒報(記檢查原本的等級,不記升級後的);判定「擋得到」只准配 Fatal、Error、Warning(Android Lint 標籤)或 detekt(compose-rules 標籤);理由一句(擋不到時寫為什麼,例如「沒報」「只報 Hint」「範本版本沒有這條」;寫「沒報」時附樣本用到的依賴)。
   - 檢查欄照現成規則欄的寫法(Android Lint 用 issue id;compose-rules 用 `cr:compose:` 後面那段 kebab 名)。
   - 出處只收兩種:〔真跑 日期:<編號>.kt.txt〕(樣本檔在 `configs/ast-grep/kotlin-android/samples/lint-wiring/`(新增),檔名就是那一列的編號加 `.kt.txt`),或〔查證 日期:網址〕(只限真跑樣本編不過的候選,那一筆理由以「樣本編不過:」開頭)。
2. **資料**:168 列宣稱接電的列,每個候選都真跑一次。一列一支樣本檔,同一列的多個候選共用那支。樣本照壞寫法欄寫:有程式碼例子的照抄(可以補參數、回傳值、import 與外層宣告讓它編得過),只有文字描述的照描述寫最小寫法;不准另加壞寫法欄沒說的觸發條件(例:UI-11 不准另寫一個把 vm 往下傳的呼叫端);import 照壞寫法欄寫的類別選,沒寫套件的一律選 androidx。樣本照實可以是 Kotlin、manifest、資源 XML 或 Gradle 設定片段。編不過的才讀官方頁,另列清單寫進〈天花板〉。
3. **型錄自檢**(`configs/ast-grep/kotlin-android/check.py`,接進 `catalog_problems`;讀新節照 `_pending_table` 的骨架:`_MAIN_ROW_RE` 認列、`_cells` 切欄,節的切法抽成一個共用函式,`_abbr_table`、`_pending_table` 與新節三處共用;錯誤訊息開頭寫〈接電證據〉;候選抽取新增一個回傳(標籤,規則碼)清單的函式,`batch4_expected_tags` 改成呼叫它):
   - `_batch4_problems` 換成新比對,只管有候選的列(沒有候選的列,例如 55 列「批四(現成規則)」,照舊值不動):每列該寫的批四標籤 = 該列判定擋得到的標籤,順序固定 Android Lint 在前;用 `批四\([^)]*\)` 從「告警帶寫法=」那一段值抽出比對,其餘子段不管。測試 `t_kt_catalog_batch4_wiring` 裡驗舊行為的斷言(直接呼叫 `_batch4_problems`、口徑句列齊 `_B4_SKIP`)與 `_kt_batch2_b4_problems` 那 7 列寫死批四的斷言,改成驗新行為。
   - 每個候選(編號,標籤,檢查)要恰好一筆判定;判定對不到候選、編號不在主表、同一三元組兩筆、固定值以外的值,各報指名那一列。
   - 擋得到配了 Hint、Informational 或沒報,報等級跟判定矛盾;Android Lint 標籤配 detekt、compose-rules 標籤配 lint 等級,也報。
   - 出處〔真跑〕的樣本檔名要恰好是 `<編號>.kt.txt` 而且存在;〔查證〕重用 `_VERIFIED_RE`,那筆理由要以「樣本編不過:」開頭。樣本內容照不照壞寫法欄寫,不用字面規則判(見〈天花板〉),由代碼審派一席逐支對照壞寫法欄判讀。
   - 「真跑環境:」那一行要在,驗開頭、日期、AGP 版本、Gradle 版本四段;後面的套件清單照抄不驗。
   - 〈統計〉加一行「接電證據 N 筆」,由 `stats_problems` 重數核對。
4. **型錄資料改動**:只動有候選的列——判定後某標籤沒有擋得到的,從「批四(…)」括號拿掉那個標籤;兩個標籤都沒有了,「批四(…)」整段連同相鄰的頓號拿掉;告警帶寫法的值因此變空時寫「未接」;其他子段(表態對程式、盲判席、行為測試或正向約束)保留。不新增批一。UI-100 壞例補 `@Preview`;判成擋不到、而實測欄寫了「實跑命中」的列(UI-11、STATE-5 等),那句改成這次真跑結果。
5. **型錄〈輸入與口徑〉**:通電批次那一句改寫成「批四以〈接電證據〉節的判定為準」,寫明擋得到與真跑的定義。
6. 不做:不在 CI 真跑(CI 沒有 Android 建置環境,自檢在 CI 只驗判定表);不改排除字表。

## 實務隱患

- 真跑樣本可能寫得跟壞寫法欄不一樣(改寫成會報的變體):自檢要求樣本含壞寫法欄某段原文;只能防「整段換掉」,防不了「原文照留、旁邊再加會報的變體」,寫進〈天花板〉。
- 判定表與主表會漂:自檢雙向比對(候選沒判定、判定對不到候選都報)。
- 真跑用的版本跟消費專案不同:環境行記版本;天花板寫雙向(新版多檢查會多擋、舊版少檢查會少擋)。
- 新增型錄列的人不知道要補判定:錯誤訊息寫要在〈接電證據〉節補哪一列哪個標籤哪個檢查。
- 併發寫入不考慮:工具鏈單人、AI 依序操作。
- 已排除:金流:只改型錄與型錄自檢,不碰付款。
- 已排除:對外送出:真跑只從 Maven 下載依賴,不寄信、不上傳;自檢只讀本機檔。
- 已排除:不可逆:全部是 repo 內的文字檔,退回提交即還原。

## 天花板

- 真跑環境的版本是一組固定版本;消費專案用更新的版本可能多擋(新檢查)、用更舊的 androidx 或 Compose 可能少擋(檢查還沒加入),判定表不反映。
