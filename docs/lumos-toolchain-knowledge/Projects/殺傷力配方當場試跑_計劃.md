# 殺傷力配方當場試跑_計劃

白話:殺傷力配方是「故意把程式改壞,看綁定的測試會不會紅」。現在重加一條配方之後,要跑整篇的 `lumos guard kill` 才知道新寫的那條殺不殺得掉;健康檢查(doctor 的 P2 段)只看配方原文還對不對得上程式,看不出「原文對得上、真跑卻殺不掉」。這份計劃做四件小事:①`guard kill` 能只跑指定短身分的那幾條;②`kill-add --try` 寫完當場只跑新加的那一條;③P2 段另外列出「最近一次真跑判 survived」的配方;④修正關卡在修正改到配方指著的檔時,提醒重跑那幾條。全部只提醒,不擋。

依據:
- rtb(另一個使用 lumos 的消費專案)2026-10-01 修 10 條失配配方的回報(rtb 提交 c531ac7,記在 rtb 的 `Issues/存量筆記漂移等工具修復`;下面的「第 1 點」等是 rtb 回報的編號,不是本計劃〈做法〉的 ①–④):第 1 點,第一次驗證有 2 條重寫時選錯位置而 survived,要跑整篇才發現——想要重加後當場試跑那一條;第 4 點,另外撞到一條不在 10 條裡的既有配方 survived(核可有兩道防護,拿掉一道測試照綠),「P2 只看原文對不對得上,看不出這種對得上卻殺不掉」。第 2、3 點已在 [[Projects/殺傷力配方修補體驗_計劃]] 做完。
- Enzo 2026-10-01 裁路線圖順序「1a-4 → 修正關卡 → 1a-3 → 1b」,本計劃是 1a-3([[Projects/漂移防治路線圖_計劃]]);第 ④ 件「修正改到配方指著的檔時提醒重跑」是 [[Projects/代碼審修正關卡_計劃]] 設計審時轉來的。

PRIOR-ART: 全部沿用 lumos 既有零件——配方短身分 `_kill_recipe_id`(kill-rm 與 guard kill 結果行已在用)、kill-rm 的前段比對規則與不帶 --id 時的列表 `_guard_kill_rm_list`、殺傷力帳本讀法 `_backing_kill_rows`(合約背書已在用:欄位型別擋、對回筆記現有配方)、單一檔 `diff --quiet` 的既有寫法(`_lens_git` 帶 `--literal-pathspecs --no-ext-diff --no-textconv`)、P2 段的軟提醒、doctor 同類提醒另開閘名的先例(check-s/check-s2/check-s3)、cmd 函式用選用 `result_out` 字典交回結果的先例(`_loop_status_disposal`)。「這筆紀錄之後有沒有動代碼」那支 `_codeloop_record_valid_ex` 不用:它判整版、這裡要判單一支檔。突變測試工具(mutmut、cargo-mutants)都有「只跑指定突變」的選項,做法同 ①。
RETIRE-IF: rtb 10-15 回報與本 repo 下一次修配方時都沒用到 `--try` → 拿掉 `--try`,保留 `--id`(guard kill 本來就該能挑;kill-log 沒有「這次是不是只跑一條」的欄位,用量只能靠問);P2 列出的 survived 配方連續一個月都被判成「本來就殺不掉、配方該拿掉」而不是真漏洞,就把那段降到 `--verbose` 才印。
REVISIT:2026-10-15 跟 rtb 的殺傷力回報同一天:問 rtb 有沒有用 `--try`、P2 的 survived 清單有沒有幫到(第 4 點那條「核可兩道防護、拿掉一道照綠」的配方,rtb 內部編號 F7,是怎麼處理的)。

## 名詞

- **短身分**:kill-rm 與 guard kill 結果行印的那 12 碼十六進位,是配方完整身分(`_kill_recipe_id(節點, 筆記裡那條配方)`,由節點、合約、檔、原文算出;格式壞的配方也有身分)的前段。**本計劃印出的短身分一律從筆記那條配方算**,不取 kill-log 那一行的 `recipe_id`(配方欄位被手改成不是字串時兩者不同,帳上那份拿去 kill-rm 會對不到)。比對照 kill-rm:收 8 碼以上十六進位(前後空白去掉、轉小寫)、對整篇配方用前段比對、對到零條或兩條以上不同完整身分都擋。
- **判定**:guard kill 每條配方的 verdict(killed、killed_unattributed、timed_out_weak、survived、drifted、abort、error)。**證據弱**:kill-log 每行的 `weak` 欄(整套一起跑、flaky 平台、筆記有未提交改動、修改時間沒錯開會設 true),跟判定是兩回事;合約背書只採信「判定 killed 而且 weak 不是 true」的那筆。本計劃不用「強證據」這個詞,回傳碼只看判定。
- **配方指的檔**:配方的 `file`,路徑相對配方平台根所在 repo 的最上層。guard kill 對平台根建隔離工作樹、以工作樹根為基準;P2 與 kill-add 提醒用 `_kill_plat_top` 模擬同一層。

## 範圍

- 做:`guard kill <節點> --id <短身分>`;`cmd_guard_kill` 多兩個選用參數(要跑的短身分清單、把逐條結果交回呼叫端的字典)——判法、回傳碼、kill-log、`--json` 都不變;`kill-add --try`;kill-add 寫完印試跑那一條的指令;doctor P2 另列最近一次真跑判 survived 的配方;`loop fix-check` 印「這幾條配方指著改過的檔」;P2 的跳過規則、kill-rm 的前段比對與列表逐行格式抽成共用小函式;`_kill_p2_scan` 多回「已逐條列出」的配方身分;`_backing_note_recipes` 多帶筆記那條配方(`_recipe` 欄);P2 專用的取最近一筆小函式 `_kill_log_latest`;`_lens_git` 多一個選用的逾時參數。
- 不做:P2 不自動跑 guard kill(doctor 要快);survived 不擋任何閘;不改 kill-log 欄位,也就不處理「身分不含壞法本身」那件事(見〈實務隱患〉);不修既有的「格式壞的配方讓 guard kill 當掉」(已有 Issue,這次只保證 `--id` 不會把人帶進那個崩潰;代碼審 r3 與另開一輪後順手修掉其中一批,還會崩的列在那篇 Issue,見〈實作紀錄〉)。

## 做法

### 共用的小整理

- P2 掃配方時的跳過規則(verification 型、status 是 superseded/stale、沒有 `kill_recipes` 欄)抽成 `_kill_note_skipped(note)`,P2 掃描、survived 清單、修正關卡提醒三處共用,行為不變。doctor P 段與其他段那幾份內嵌的「verification 型、superseded/stale」不動(它們不看 `kill_recipes` 欄,規則不同);`_kill_p2_scan` 那句「跳過的節點逐字照 P 段」註解改成「照 P 段、再多跳沒有配方的」。
- kill-rm 不帶 --id 時列表的逐行格式抽成 `_guard_kill_rm_rows(rel, recipes, dup_note)`(回文字行、不含結尾句;`dup_note` 是重複配方那行的註記)。`_guard_kill_rm_list` 照舊印到標準輸出、重複註記照舊「(同一條 ×n,移除會一起移掉)」、結尾照舊印「移除」;guard kill 找不到短身分時用同一個逐行格式、印到標準錯誤、重複註記改「(同一條 ×n,會一起跑)」、結尾改印「只跑某一條:lumos guard kill <節點> --id <短身分>」。
- kill-rm 的前段比對(8 碼以上十六進位、對到零條或多條擋)抽成 `_kill_match_prefixes(rel, recipes, prefixes)`(回對到的配方位置,或哪一個值、為什麼對不到),kill-rm 與 ① 共用;S1 的「整篇裡對到兩條」直接呼叫它測。
- `_lens_git` 多一個選用參數 `timeout`(預設照舊 20 秒),給 ③ 把單次 git 夾進剩餘時間。

### ① `guard kill <節點> --id <短身分>`

- 新旗標 `--id`(可重複;argparse 的 dest 用 `gk_id`、`action="append"`,照這組子命令 `gk_`/`gkr_` 前綴的慣例)。
- `cmd_guard_kill` 新參數 `id_prefixes`(短身分清單,原樣傳入)。解析在函式裡、讀完整篇配方之後、合約片段過濾之前,**對整篇配方**比對(跟 kill-rm 同一份清單、同一個規則,所以同一個短身分在兩個指令裡的對到與否一致):
  1. 每個值不是 8 碼以上十六進位、對到零條、或對到兩條以上不同完整身分 → 回 2,標準錯誤印是哪一個、為什麼,接著用共用逐行格式列出這篇每條配方。
  2. 對到的配方裡有格式壞的(跟 doctor P2、kill-add 提醒同一套判法 `_kill_recipe_judge` 判 malformed:guard kill 會拒跑或程式出錯的那幾種,例如不是物件、file 或 old 不是字串)→ 回 2,印「第 N 條格式壞,先 lumos guard kill-rm <節點> --id <短身分> 再重加」,不往下跑(既有程式碰到格式壞的配方會當掉)。
  3. 都對到 → 只留對到的那幾條(完整身分相同的重複配方一起留),再照舊套合約片段過濾。短身分對得到、但被合約片段濾光 → 走既有的「沒有任何突變配方可跑」擋下(回 2)。
- 新參數 `result_out`(呼叫端給一個空字典;照 `_loop_status_disposal` 的先例):跑完在蓋章迴圈補齊 `weak` 與 `recipe_id` 之後、第一個 `return` 之前,放 `result_out["rows"] = [{"recipe_id", "short", "verdict", "weak"}…]`;在那之前就回 2 的路徑(找不到 run_cmd 等)不放。兩個參數都不給時跟現在一模一樣。

### ② `kill-add` 寫完後的試跑

- 新配方的短身分:鎖外拿 `warn_box` 裡那條配方(既有內容不改,放的就是這次寫進去、或只更新 covers 時指到的那條),直接算 `_kill_recipe_id(節點, 那條)[:12]`。
- 不帶 `--try`:寫入成功時,原本那行「下一步: lumos guard kill 跑殺傷力驗證」改成「下一步:只跑這一條 lumos guard kill <節點> --id <短身分>」(節點用 `_kill_node_arg` 的寫法)。只更新 covers 的那條路照舊。
- 帶 `--try`(dest 用 `gk_try`;`try` 是 Python 關鍵字):寫入成功(含只更新 covers)後,在鎖外、提醒印完之後呼叫 `cmd_guard_kill(env, node, id_prefixes=[完整身分], result_out={})`,結果照 guard kill 的人讀格式印。
- 回傳碼:寫入失敗照舊 2、不試跑。寫入成功時照 guard kill 的回傳碼——判定 killed 回 0;任一 survived、或全部只拿到 killed_unattributed / timed_out_weak 回 1;drifted、abort、error 回 2。**回傳碼不看 weak**:`--try` 時筆記一定還沒提交、weak 一定是 true,看 weak 的話回傳碼永遠分不出殺不殺得掉。
- 另印的提示(都印到標準錯誤):
  - 試跑結果的 `weak` 是 true(`--try` 一定是:筆記剛寫還沒提交)→「這次試跑是弱證據(筆記還沒提交等),合約背書不採信;提交程式與筆記後跑 lumos guard kill <節點> --id <短身分> 留一筆算數的」。
  - survived →「配方已寫進筆記;換位置重寫就 lumos guard kill-rm <節點> --id <短身分> 再重加」。
  - 全部只拿到 killed_unattributed / timed_out_weak →「紅燈沒歸因到綁定測試或逾時,不是殺不掉;看結果行的說明」。
  - 回 2 的三種印一行「配方已寫進筆記,試跑沒跑成(判定 X)」——跟寫入失敗的「擋下」句分開,看標準錯誤有沒有這一行就知道是哪一種;接著:drifted →「試跑是對 HEAD 跑的,程式改了還沒提交時原文對不上:提交後跑 lumos guard kill <節點> --id <短身分>(別重跑 kill-add,會被判重擋下)」;abort →「baseline 沒綠:綁定測試在 HEAD 上沒過,或剛綁的測試還沒提交:提交後跑同一行」;error → 照 guard kill 結果行。
- 預先講清楚的現象:kill-add 剛把筆記改成未提交,`--try` 一定會先印 guard kill 那行「repo 有未提交變更」的警告。

### ③ doctor P2 列出最近一次真跑判 survived 的配方

- `_kill_p2_scan` 多回一個 `listed`:**已在「原文對不上」那段逐條列出的配方**完整身分集合(`_kill_recipe_id(rel, 那條)`)——只收 `_kill_p2_one` 回 `malformed`、`noplat`、`error`,以及其他不是 `ok`/`cfg`/`noroot` 的狀態碼(`hits`、`missing`、`undecodable`、`path` 這類,就是真的加了一行進 items 的那幾種)。`cfg`(設定檔讀不了)與 `noroot`(平台根找不到、只併成一句「N 條沒驗」)不算已列出,survived 清單照列。
- 讀殺傷力帳本一次(`_backing_kill_rows`:型別不對、`head_sha` 不是完整 sha、對不回筆記現有配方的行都略過)。`_backing_note_recipes` 對上筆記那條配方時,多把那條配方放進行的 `_recipe` 欄(合約背書不讀這欄;實作時確認背書那幾支測試不比對整列)。照 `_kill_note_skipped` 跳過不該看的筆記。帳本照 `_backing_kill_rows(repo_root)` 讀,它用 `_vault_in(repo_root)` 對回筆記;多知識庫專案裡那個知識庫可能不是 doctor 這次掃的——只列「對回的筆記也在 doctor 這次掃的筆記裡」的那幾條,其餘不列。
- 每條配方取**最近一筆**:比 `ts`(guard kill 自己寫的當地時間字串,同一台機器上字串大小就是先後);`ts` 不是字串的當最舊;同 `ts` 取先出現的(跟合約背書取最新那筆同一個規則)。不只看檔內順序,是因為本 repo 的 kill-log 進版控、多個會談各自追加再合併,合併後檔內順序可能跟跑的先後相反。這跟合約背書的取法刻意不同:背書判 survived 看「這版任何一筆」、跟順序無關,檔內最後一筆只拿來取 covers——兩邊要的東西不一樣,不共用一支。取最近一筆的小函式 `_kill_log_latest(rows)` 只給 P2 用。
- 最近一筆判定是 survived、而且身分不在 `listed` 的列出來。一行寫:筆記、短身分(照〈名詞〉從 `_recipe` 算)、合約前段(取 `_recipe` 的 `invariant`、經 `_kill_show`)、那次跑的日期(`ts` 要是字串,取前 10 字、只留數字與連字號)、版本前 8 碼、兩個指令(重跑 `lumos guard kill <節點> --id <短身分>`;確定這條本來就殺不掉就 `lumos guard kill-rm <節點> --id <短身分>`)。
- 行尾附註(都只是提示,不改判斷):
  - 那次的 `weak` 是 true → 「(那次證據弱,先重跑)」。
  - 配方指的檔在那次的版本到現在的 `HEAD` 之間改過,或判不了 → 「(配方指的檔之後改過,先重跑)」。判法:在配方平台根所在 repo 的最上層(`_kill_plat_top`)跑 `_lens_git(top, "--literal-pathspecs", "diff", "--no-ext-diff", "--no-textconv", "--quiet", head_sha, "HEAD", "--", file, timeout=…)`——旗標照既有單一檔 diff 的寫法(檔名含 `[ ]`、`*` 不當萬用字元,Next.js 的 `app/[id]/page.tsx` 這種路徑才不會被別的檔的改動誤觸);標準錯誤一律收掉不印(壞版本、淺 clone 的 `fatal:` 不洗版);回傳碼非 0、逾時或出錯都算改過。每個(版本、檔)只判一次;整段時間上限沿用 `_BACKING_BUDGET`(20 秒),每次呼叫的逾時夾在剩餘時間內(照背書那段的做法),用完的直接加這句;設定檔讀不了、平台找不到時也直接加這句。
- 這段只看配方指的那支檔:綁定測試改過(survived 最常見的修法)不會觸發行尾那句——配方只記測試方法名、不記測試檔,判不了。所以段標題本身就寫「之後補強過測試的先重跑」。
- 印法:P2 段原本的 if/elif 鏈(設定檔讀不了 / 原文對不上 / 都對得上 / 沒有配方)不動,survived 清單接在它後面、同一段裡、**自己一個例外保護**:有列出的另開一個軟提醒,標題「有 N 條殺傷力配方最近一次真跑判 survived(那次原文對得上卻殺不掉;之後補強過測試的先重跑;不擋)」;同一段先出現「✓ 原文都對得上」再出現這個提醒是對的,兩句講的是不同的事。算不出來只印一行「survived 清單算不出來(例外類別: 訊息),先跳過」,跟原本那句「這一段算不出來」分得開。設定檔讀不了時這段照樣算(它不靠設定檔判對不對得上)。
- 落帳:每篇涉及的筆記各記一筆事件,閘名另開 `check-p2s`(照 check-s/check-s2 同類提醒另開閘名的先例)、kind `warned`、hard false——這樣治理帳的「同一道軟閘對同一篇喊多天沒人理」與同日折疊照常算得到它。`check-p2s` 加進已知閘名清單;治理帳列舉閘名的文件與守衛測試照要求同步。
- 只看最近一筆而不是「同一版本上任何一次 survived」:合約背書是閘,寧嚴;P2 是提醒,只要指出現在還殺不掉的,重跑後殺得掉就不該再吵。

### ④ 修正關卡提醒重跑

- `lumos loop fix-check` 在隔離工作樹裡讀完設定、算出「平台清單」與「釘不住版本的平台」之後(只在這輪有要修正紀錄、沒早退時跑到),逐篇看筆記(`_kill_note_skipped` 跳過的不看)的每條配方(格式壞的跳過):
  - **平台用修正關卡自己讀的那份設定**(樹裡、提交裡那份),不另讀主工作目錄的設定——同一個指令裡平台根只有一個來源;配方也讀樹裡那份筆記,工作目錄沒提交的改動不算。

## 實務隱患

- **配方身分不含壞法本身**:kill-log 的 `recipe_id` 由節點、合約、檔、原文算出,不含 `new`;同一處重寫壞法(原文沒變)之後身分不變,P2 會一直列著舊的 survived,直到重跑一次。提示本來就叫人重跑,重跑之後最新一筆就換掉了。不在這次改帳本欄位。
- **時間戳不帶時區**:guard kill 寫的 `ts` 是那台機器的當地時間、不帶時區。不同時區的機器把同一份 kill-log 合併時,先後可能錯幾小時,錯的代價是多列或少列一次 survived(提示本來就叫人重跑)。回頭條件:guard kill 寫 `ts` 那行改成帶時區時(`cmd_guard_kill` 裡算 `ts` 的那句),`_kill_log_latest` 一起改成比帶時區的時間。
- **時間**:`--try` 等於跑一次只有一條的 guard kill(baseline 一次加配方一次,加上 1a-4 的「等到新的一秒」;rtb 實測每條約多 0.75 秒);P2 多讀一次 kill-log、每個(版本、檔)判一次 git,整段上限 20 秒,單次 git 夾在剩餘時間內。
- **本機才有帳**:消費專案的 kill-log 不進版控,survived 清單只在跑過 guard kill 的那台機器有東西可列;CI 上這段多半是空的。本 repo 的 kill-log 進版控,所以才要比 `ts`(見 ③)。
