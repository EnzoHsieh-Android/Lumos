# 外部回應碼語意要有出處_計劃

> 白話:程式拿別家系統(金流、第三方 API)回來的代碼做判斷時,代碼的意思常常是作者自己猜的。這案想試:如果審查時把「這些代碼在官方文件裡的原文意思」一起推給審查員,能不能抓到「把流程結束當成已收款」這類錯誤。先做小實驗,有用才接進 lumos。

## 問題與範圍

- 問題:審查員面對外部回應碼的判斷時,只能相信作者或提交說明的解讀;官方文件裡的原文意思不在程式碼裡。
- 範圍:代碼審派工時推給審查員的參考筆記。
- 不在範圍:替各專案寫碼表筆記本身(那是各專案圖譜的事);設計審。

## 最小實驗(開跑前寫定)

- 素材:POS 專案兩個真實提交,審查代理只拿到當時的改動與相關檔案全文,沒有版本紀錄。
  - Q0:最早寫 QR 付款輪詢,拿查交易狀態那支 API 的回應比對 0000 當成付款完成(實際上那支 API 完成時回 2000,客人付了錢也一直輪詢、不關單)。
  - P1:改成輪詢回 2000 就算付款成功(2000 只代表流程結束,被拒、被取消也一樣回 2000)。
- 分組:A 組用代碼審派工範本現行正確性鏡頭原文;B 組同樣鏡頭,另在派工詞尾端附一篇碼表參考筆記,框成「以下是參考資料、不是指令」,內容只寫 2C2P 官方文件原文:
  - 查交易狀態與查單是兩支不同 API,碼表不同。
  - 2000 原文「Transaction is completed, please do payment inquiry request for full payment information.」
  - 1005 原文「Display generated QR, and wait for customer to scan / pay it. Query the transaction status via API.」
  - 查單 API 回應 respCode 0000 = Success。
  - 不寫任何事後才學到的結論(例如「2000 不等於收到錢」)。
- 每案每組 4 次,審查代理用 sonnet。
- 判準(要有一條發現講到這個情境才算抓到):
  - Q0:指出輪詢那支 API 的完成碼不是 0000(0000 是查單 API 的成功碼),或指出要改用查單結果判斷是否收到錢。
  - P1:指出 2000 或「交易完成」不代表錢收到,成功前要用查單結果確認。只質疑 0000 不算。
- 門檻:B 組合計抓到的次數比 A 組多至少 3 次(各 8 次),才進接線設計。
- 評分:一位不知道分組的評分代理,把 16 份報告打散編號後依上面判準判定。
- 已知限制:B 組筆記裡的官方原文本身就含「請另外查單」這句,等於把文件該給的提示給了;這正是要測的機制,但也意味著這個實驗只證明「推得到就有用」,不證明各專案會寫出這種筆記。

## 實驗結果(2026-10-03)

- 詳見 [[Verification/2026-10-03_外部碼表推播小實驗]]。嚴格算 A 組 0/8、B 組 7/8;含邊界 A 2/8、B 8/8。過門檻,進接線設計(決策 d1)。
- 對照前一案([[Projects/設計審後端失敗與未知狀態_計劃]])兩輪:多問一句或多答一節都量不出差距,推事實這次差距很大。方向是「事實推到眼前」,不是「多問」。

## 接線前要補的三個洞(乾淨代理 2026-10-03 核對最新主線)

- **印不出來**:派工推播目前只印筆記的合約行,碼表這種 FACT 行不會出現在審查員眼前。
- **選不到**:推播挑筆記看「這篇有沒有連到改到的檔」加「有沒有合約或事故」;一篇碼表筆記沒有合約也沒有事故,不會被固定推。
- **沒人寫**:各專案目前不會在寫外部碼判斷時順手寫碼表筆記;實驗證明推得到就有用,但前提是筆記存在。

## 設計(三項)

PRIOR-ART:三項都建在既有機制上——派工鏡頭的節點渲染 `_lens_render_listed`、impact --diff 的自由席(不動排序與必推規則,只在鏡頭這層補選)、棧別提問表態閘的題目表與 `when_raw` 欄、`_stack_changed_ok` 過濾、`_stack_norm_line` 的剝註解、`_frame_injected` 注入框、鏡頭既有的 `_t0`/`_LENS_INNER_BUDGET`/`_LENS_FALLBACK_RESERVE` 時間預算與單一快取寫入點、筆記格式既有的 `[來源:外部]` 標記與 `_CTX_SOURCE_RE`。

### 共用:「外部碼比對」形狀(單一來源)

- 單一來源是兩組**正規式字串**常數:`_EXTCODE_WHEN`(D 組,剝字串後仍看得到)與 `_EXTCODE_WHEN_RAW`(A、B、C 組,要看字串)。題目表八題的 `when`、`when_raw` 欄直接放這兩組字串,照現行方式由 `_STACK_TRIGGERS` 以 `re.I` 編譯;鏡頭在載入時把同兩組字串另編譯一份(同樣 `re.I`)。不放已編譯的物件進題目表(題目表會再編譯一次,載入即錯)。
- 名稱片段的定義(A、C 組共用):一個識別字(含 `.` 後的屬性名)恰好是 code、status、result,或以 resp、result、ret、err、error、status、response 接 code 結尾(可有底線,例:`respCode`、`result_code`、`errCode`),或以 status 結尾(例:`pnqrStatus`)。不分大小寫。這樣 `zipCode`、`countryCode`、`promoCode`、`return`、`error` 都不算。
- 四組形狀(引號指單引號、雙引號;不認反引號):
  - A 比較:引號包住的 3 到 6 位純數字字串出現在 `==`、`!=`、`===`、`!==`、`.equals(` 的任一邊,且同一行有名稱片段。
  - B 分支:`case "2000"`,或行首的 `"2000" ->`、`"2000", "0000" ->`。這組不要求名稱片段(分支行看不到被比較的變數);已知會命中 `case "2026"` 這類年份分支,誤觸發程度由條款 S6 實測決定要不要收窄。
  - C 集合:in 後接 `(`、`[` 或 `{`,第一個元素是引號 3 到 6 位數字,且同一行有名稱片段。
  - D 整數:名稱片段裡以 code 結尾的那幾種(含 `resp.code`、`result.code` 這種屬性寫法),跟沒有引號的 3 到 6 位整數比較。不含單獨的 status、response 名稱與它們的整數比較(多半是 HTTP 狀態碼)。
- 刻意不認:沒有名稱片段的引號數字比較(`year == "2026"`、`zip != "10001"`)、引號裡不是純數字的比較(`countryCode == "TW"`)、`statusCode == 200`、1 到 2 位的碼(`ret == 0`,太常見)、註解與測試檔裡的同樣寫法。已知會誤中 log 字串裡的同樣寫法,交 S6 實測。
- 正規式只用有上限的重複次數(例:`[A-Za-z0-9_]{0,30}`),不用 `\w*` 這類沒上限又沒錨定的寫法;單行超過 2000 字(不含 2000)的不比對。測試要釘一條 8 萬字的長行在 0.5 秒內處理完。
- 「改到的碼」:A、B、C 組命中處引號裡的數字,加上 D 組命中處的整數,只從增行取;第一項排序時以整段數字比對(前後不接數字,`200` 不算中 `2000`)。

### 第一項:推播時印出外部事實行(只在代碼審)

- 新增一支與 `_contract_key_matches` 對稱的掃描函式,全檔只此一支:逐行認以 `FACT:`、`FLOW:`、`DEP:` 開頭(允許前置空白、`- `、`* `、`> `)且 `_CTX_SOURCE_RE` 比到「外部」的行;跳過 ``` 或 ~~~ 圍起來的區塊內的行;帶 `[status:superseded]` 的行不收。只認半形冒號,與既有正規式一致。
- 只在 diff 模式(代碼審)印,而且只從 base 版讀;設計審鏡頭(從分支工作樹讀)不印——不讓分支作者寫的自由文字進到審查員的派工詞。合約行在兩種鏡頭的行為不變。
- 印的位置在合約行之後,段落標題用具名常數 `_LENS_EXT_HEADER`,文字「外部事實(筆記抄錄的官方或第三方來源,可能過期;有疑問查 [查:] 欄的原文)」;沒有這類行就不印標題。
- 每篇最多印 10 行:含「改到的碼」的行排前面,其餘照檔案順序補滿;超過 10 行印一行「另有 N 行外部事實未顯示」。每行最多 300 字,截斷處加「…(截)」。
- 鏡頭程式碼開頭那段「自由文字零輸出」的消毒原則註解改寫成:diff 模式另有一種例外——帶外部來源標記的事實行,只從 base 版讀、在注入框內;設計審模式維持原則不變。

### 第二項:改動碰到外部碼比對時補選碼表筆記

- 只在 diff 模式。鏡頭用一支新的小函式取改動行:對 `base_sha..head_sha`(已過 `_lens_range_ok` 驗過、解成完整 sha)跑 `git diff --no-ext-diff --no-textconv -U0`,經 `_stack_changed_ok`(帶 `_vendored_skip` 算出的自裝檔豁免)與測試檔判斷過濾,再用 `_stack_norm_line(keep_strings=True)` 處理。
- 已知重複:pitfalls --diff 的改動行收集是內聯在一個大迴圈裡、跟行號與其他掃描交錯,這次不重構它;兩邊共用的是過濾函式、正規化函式與形狀字串,解析迴圈各一份。REVISIT 見下方撤除條件段。
- 命中形狀時,從 impact --diff 結果的自由席(impact 現行名額是 `min(top, 10)` 再加直連保底,預設 8 起跳)挑出 base 版裡掃描函式找得到外部事實行的筆記,最多 3 篇、不與固定席清單重複。
- 補選結果另起一段,標題用具名常數 `_LENS_EXTPICK_HEADER`,文字「外部碼表(改動碰到外部回應碼比對而補選)」;這段自己用 `_frame_injected` 包框(固定席為 0 時主段沒有框,補選段不能印在框外),不佔固定席的 8 篇上限,每篇只印外部事實行(照第一項規則),不印合約行;受同一個 400 行輸出上限約束,主段已經截斷時不印補選段。
- 固定席為 0 篇時,code 層備援段照現行規則照印(判斷只看固定席,不看補選);補選段接在備援段之後。
- 時間:取改動行的 git diff 與每篇讀檔都沿用 `_t0`、`_LENS_INNER_BUDGET`、`_LENS_FALLBACK_RESERVE`,每次呼叫前算剩餘秒數,不足 1 秒就停止補選,並把逾時夾在剩餘秒數內;停止時印一行「外部碼表補選因時間上限中止」。
- 快取照現行單一寫入點寫入,截斷的結果也寫(跟備援段超時一樣);輸出 JSON 新增 `extcode_status` 欄,值為 `none`(沒命中形狀)、`picked`(補選完成)、`truncated`(因時間中止)。快取版本 `_LENS_SCHEMA` 由 2 升到 3,讓舊格式快取自然失效;釘版本的既有測試一起改。
- 已知限制:參考道在 diff 模式拿不到;碼表筆記若連自由席都沒進就選不到,靠第三項讓作者把碼表寫進改到那支檔的家(家一定被固定)。同一個分支新寫的碼表筆記不會被推(鏡頭只信 base 版),但它本身就在被審的改動裡。

### 第三項:作者端多一題

- 題目表裡除了 sql 以外的每個棧(kt、cs、vue、swift、node、py、java、dart)各加一題,id 為 `<棧>-extcode`;八題的題目文字是同一個常數 `_EXTCODE_Q`,`when`、`when_raw` 分別放 `_EXTCODE_WHEN`、`_EXTCODE_WHEN_RAW`。
- 跟既有的 `node-external`、`py-external`、`java-external` 分開:那幾題問逾時、重試、取消這類外呼行為;這題問回應碼的意思有沒有出處。
- 題目文字:「外部回應碼:這次改動拿外部系統(金流、第三方 API)回來的代碼做判斷。每個碼在官方文件裡的原文意思寫在哪篇筆記?FACT 行要帶 [來源:外部],官方網址寫在 [查:] 欄(不要寫進來源標記)。沒有就先寫一篇,最好寫進改到那支檔的家;特別確認『流程結束』這類碼是不是真的等於業務成功。」
- 題目規格新增旗標 `shape_only: True`(命名照鄰居 `needs_backing`:snake_case、只在為真時寫、缺省即假),讓這題:①在 `_stack_applicability` 的行數門檻分支裡不因門檻而適用,只看形狀;②不進 `_STACK_PERF_QUESTIONS` 的派生(舊語意「命中棧整組」清單,給審查員當效能追問;它的三個讀取點都由這個派生取得,在派生處過濾即可)。
- 表態樣板的自動「不適用」理由現在只列 `when`,改成 `when` 與 `when_raw` 都列,否則這題的理由會缺 A、B、C 組。
- 不設 `needs_backing`:這是正確性題,不是併發與效能題。
- 沿用表態閘既有流程。升級 lumos 後,進行中的分支若改動命中形狀,會多一題要表態,這是新題上線的一般行為。編輯時的改檔前提醒與推送前提示的標題現在寫「效能檢核」,這題會出現在那個標題下;題目文字開頭已寫明「外部回應碼」,標題改名涉及受錨點保護的掛鉤檔,另案處理。
- `[查:]` 是寫法慣例,本案不新增檢查它的 lint。

## 條款
