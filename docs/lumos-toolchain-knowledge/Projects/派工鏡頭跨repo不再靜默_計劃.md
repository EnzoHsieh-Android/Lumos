# 派工鏡頭跨repo不再靜默_計劃

白話:派代碼審的審查員時,有一支掛鉤會在派工詞尾端自動接上「這次改動牽連到的圖譜筆記」(派工鏡頭)。它用「這個對話開在哪個專案」去算;對話開在 A 專案、審的卻是 B 專案的分支時,範圍在 A 找不到,鏡頭算不出來,掛鉤就什麼都不附、也不講——rtb 一個迴圈四輪派工全部沒附,自己翻報告才發現。這次讓它在算不出來時講一句,說清楚範圍、在哪個專案算的、怎麼繞過。

依據:rtb 2026-10-07 回報(四輪派工 0 份附加,證據在主線 `governance/review-reports/code-審查跑滿回顧/`);本機實驗:`ce2a961f` 在 lumos 工具鏈存在、在 rtb 專案不存在,`lumos dispatch-lens ce2a961f..HEAD --repo <rtb 專案>` 回「範圍有一端不是本地存在的 commit」;同一天開在 lumos 工具鏈的會談派的席位都確認看到附加段。

PRIOR-ART: 沿用 [[Projects/第二輪審視六修_計劃]] 對「超時」那次的翻案形狀——[[Projects/派工鏡頭注入_計劃]] 原設計〈失敗一律放行、預設靜默〉,v1.3 因「39 次派工 21 次放空、編排者完全不知道」改成超時附一行固定句;本案把同一形狀套到「範圍算不出來」這一族。說明句沿用既有 `TIMEOUT_NOTE` 那組的寫法(`LUMOS-LENS:` 開頭、零自由文字、只填固定欄位);派工鏡頭失敗時印 JSON 沿用角色卡選項已有的失敗 JSON(帶 `role_text`)。
RETIRE-IF: 掛鉤改成從子代理實際工作的目錄算鏡頭(例如 Claude Code 在派工事件帶出子代理的工作目錄),會談專案與審查目標不再可能錯開,這句說明就該拿掉。

## 範圍

- 做:派工鏡頭(`--json`)在「範圍算不出來」時,標準輸出印一行 JSON,帶固定字彙的原因代碼欄 `lens_fail`:`commit_missing`(範圍有一端在這個專案不存在)、`not_git`(指定的目錄不在 git 專案裡)、`sha_unresolved`(兩端解析不到完整提交編號)、`no_mainline`(找不到 main/master)、`base_not_mainline`(base 不在主線上)、`empty_range`(起點等於終點——標記終點寫 HEAD、卻在會談專案解讀成 base 本身時最常見);前五種回傳碼不變(2/2/2/4/4),`empty_range` 原本照算出全零備援段、改成回 2。有角色卡時同一行 JSON 照帶 `role_text`。
- 做:掛鉤在派工鏡頭回非零碼、JSON 帶認得的 `lens_fail` 時,改派工詞附一行固定說明(`LUMOS-LENS:` 開頭):這次沒附固定席節點、範圍、在哪個專案算的(會談專案路徑,去反引號、換行換成空白、截 300 字)、原因(由代碼查固定句)、繞法(標記終點寫完整提交編號、從開在目標專案的會談派席,或派工前手動 `lumos impact --diff <範圍>` 把固定席內容貼進派工詞);範圍不合保守的 ref 字元集(英數與 `._/~^-`)就以 `<範圍>` 代替,不轉述原文;有角色卡照附在說明之後;記一筆掛鉤事件(同超時那條)。
- 做:說明同步(派工範本鏡頭 3 的三件事、代碼審手冊步驟 2、派工鏡頭計劃誠實界線)。
- 不做:讓標記行指定 repo;範圍格式寫錯(`main...HEAD` 之類)仍照舊放行(標記文法另案);沒有圖譜(rc3)、主線找不到(rc4 另一種)照舊;Codex 認領那條路不動。

## 實務隱患

- **舊 lumos 配新掛鉤**:掛鉤是複製進使用者目錄的,兩邊版本錯開是常態;舊版失敗不印 `lens_fail` → 掛鉤照舊放行(只附角色卡),不會報錯。
- **路徑消毒**:會談專案路徑來自環境變數,不是圖譜或改動內容,但目錄名可由 clone 網址決定,仍要清。跟鎖路徑同一支 `_clean_field`:先過同層掛鉤共用的正典 `_plain_label`(單行化、去框線與控制字元、截長),再多清反引號與 Unicode 換行類(U+2028/U+2029/U+0085)。正典不動、多清的寫在外面,同 memory-sweep 的 `_clean`(代碼審第三輪:原本另寫一套較弱的清理,控制字元與 U+2028 都會原樣進派工詞)。
- **空範圍不能再拿來武裝**:Codex 領席那支測試(t_codex_s1_lens_arm_claim)為了省時間,後面幾次武裝用 `<upstream>..<upstream>` 空範圍;本案讓起點等於終點回 empty_range 之後它直接失敗,推送前全套才抓到(審查時只跑了名字含 dispatch_lens 的子集,這支不含)。改成跟第一次同一個主線上最小的提交,單支 12 秒變 35 秒。測試裡原本寫「其餘三次用空 diff、1.4 秒」的舊註解一併改寫,另加「別改回空範圍」一段(收尾 r3 兩席同報;Enzo 裁接受風險不再開第四輪)。
- **複製式共用要守「該有的都有」**:掛鉤彼此 import 不到,★注入框★ 區塊靠逐字複製加守衛;守衛原本只比「有的複本一致」,派工鏡頭掛鉤從沒抄過這段、卻在 Codex 領席超時那條路呼叫 `_frame_injected`,一走就 NameError。第三輪把區塊抄進來;收尾審查再抓到守衛只看寫死的清單(memory-sweep 有同一段卻不在清單上)、只比框常數不比清理函式本體,改成自動找:用到框函式或清理函式的 hook 都要有完整區塊,連同 lumos 本體整段逐字相同。
- 已排除:金流:只改派工詞的附加段,不碰任何金流
- 已排除:對外送出:不連網、不送任何東西出去
- 已排除:不可逆:不寫任何資料檔,退回提交即恢復
- 已排除:守衛面:掛鉤只改派工詞、不擋派工,任何失敗照舊放行;不改任何閘的判定

## 驗收條款

- [S1] 當派工鏡頭以 `--json` 執行、範圍有一端在指定專案不存在、指定目錄不在 git 專案裡、找不到主線、base 不在主線上、或範圍是空的時,應 在標準輸出印一行帶 `lens_fail`(分別是 commit_missing、not_git、no_mainline、base_not_mainline、empty_range)的 JSON,前四種回傳碼照舊、空範圍回 2;範圍格式不合法時 應 照舊什麼都不印 [test:t_dispatch_lens_fail_reason_json]
- [S2] 當掛鉤收到派工鏡頭非零回傳、JSON 帶認得的 `lens_fail` 時,應 改派工詞附一行 `LUMOS-LENS:` 說明(含範圍、會談專案路徑、原因句、繞法、終點要寫完整提交編號),範圍不合保守字元集時以 `<範圍>` 代替、路徑去反引號與換行並截長,有角色卡照附在說明之後;JSON 沒有 `lens_fail` 或值不認得時 應 照舊(只附角色卡或原樣放行) [test:t_dispatch_lens_hook_fail_reason_notice]
