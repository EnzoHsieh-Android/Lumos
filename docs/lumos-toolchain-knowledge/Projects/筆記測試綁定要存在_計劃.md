## 名詞

- **note-shape / 筆記內容閘**:`lumos note-shape` 指令,提交前掛鉤跑 `--staged`、推送前與 CI 跑 `--diff 起點..終點`;節點 [[Systems/筆記內容閘]] 管它。**被檢查的版本**:提交時是提交索引、推送時是範圍終點。**單次跳過**:環境變數 `LUMOS_SKIP_NOTE_SHAPE=1`,整道跳過一次並記帳。**治理帳**:`docs/.governance-log.jsonl`,各道閘的事件。
- **碰到的筆記**:這次有新寫的行落在正文或摘要的筆記。新寫的行照筆記內容閘既有定義(提交時是這次暫存新增的行;推送時是範圍裡逐提交新增、終點還在的行,已在主線上的提交不重查、合併提交只算它自己多寫的行、上線點之前的不算;入口 `_notelines_new`,跟其他 note-shape 規則同一趟)。具體判法:`slots["notes"]` 裡每篇的新寫行,至少一行的區塊是 `body` 或 `summary`,或是開頭欄位 `summary:` 那一行本身(單行寫法)。所以這幾種**不算碰到**:只被主線合進來、自己沒寫任何一行;只刪行;只改名或搬資料夾;新增的行後來在同一範圍又刪掉;只改開頭欄位其他欄(`status`、`updated`、`tags`、`related`…,例如 `lumos set` 改狀態);只改 `decisions` 欄(這組不掃它)。
- **整篇要乾淨**:碰到的筆記,在被檢查的版本裡整篇(不分新舊行)都要符合〈做法〉3 的規則。舊的壞名字碰到了就要順手修。
- **測試名**:筆記一條裡 `slot_parse` 解出的 `test` 鍵(同一條可寫多次)的值,用半形或全形逗號切開、去前後空白、去掉空項、去掉包住整個名稱的反引號(索引那邊 Kotlin 的反引號測試名也是去掉後收的);平台前綴認半形或全形冒號(全形換成半形),前綴與名稱之間的空白去掉;切分寫成一支 `_test_names_of`,note-shape 與 doctor S20 共用。程式碼圍欄裡的不算(`_visible_lines`);**HTML 註解裡的照算**——全檔的可見性零件都不偵測註解(偵測本身被證明是洞:先關再開會把後面整份藏掉),要寫範例就放圍欄或反引號;縮排四格寫成的程式碼區塊不認(`_visible_lines` 本來就不認,已知限制)。**一條**:摘要裡用 `_note_summary_entries` 取的每一條(區塊寫法接回續行、單行寫法整個值算一條,行號是 summary 那一行;`>` 折疊而續行縮排跟前綴行一樣深時續行會漏——跟 doctor S16–S19 同一個已知限制);正文裡一個實體行。開頭欄位只看 summary,`decisions` 與其他欄不看。
- **合約行**:摘要裡符合 `INVARIANT_RE` 的條目,已由 doctor Check T(全庫、`--ci` 擋)驗存在、波及到的另由推送前合約測試閘真跑。**條款定義行**:計劃(開頭欄位 `type: project`)裡 `clause_bindings` 回的 `defined` 為真的條目的行號(那個編號第一次寫在行首的那一行;重複定義的第二行不在內,照一般正文行判——重複本身 spec-trace 會唸)。這兩種行上的測試名本案不驗存在;其他規則照查——合約行查佔位字、空方括號、`[test-gone:]` 說假話,條款定義行查 `[test-gone:]` 說假話但不查佔位字(設計先行,條款先寫、測試後寫);標了作廢還掛活測試時兩種都算(〈做法〉3 第 4 項;rtb 那 12 條就是計劃條款行)。(代碼審 r1 通才席:原本整條豁免,條款行上的 `[test-gone:活測試]` 沒有任何檢查會看。)名稱一律用 `slot_parse` 取,不另用合約那支 `TEST_REF_RE`。
- **指得到 / 指不到 / 判不了**(每個名稱):第①道 `_classify_test_refs`(工作目錄的測試索引),判 `real` 才過,`fake`/`dangling`/`bad-name` 算指不到。第②道 `_test_in_tree`(把表態閘 `_dispositions_check_test` 裡 `git grep -w -F` 那段抽出;名稱帶 `.` 時找最後一段,跟第①道比方法集合的取法一樣)回四種原因:`found`、`notfound`、`outside`(平台根在 repo 外)、`error`(git 回 0、1 以外);逾時照舊丟例外;逾時秒數由呼叫端傳入。表態閘照原樣對回:`found` → 過;`outside` → 過(只做第①道,同原本);`notfound` → 不過、原本的「整字 grep 不到」訊息;`error` → 不過、原本的「無法對推送版本的樹驗證」訊息帶回傳碼;逾時的例外照舊由每題外層接成「無法驗證」;子模組判斷不在表態閘這側(原本就當找不到)。組合:第①道沒過 → 指不到;第①道過、第②道 `found` → 指得到;第①道過、第②道 `notfound` → 指不到(測試寫了沒提交,推上去也沒有守衛,一樣算),但終點的樹裡平台根落在子模組底下(含等於它)、或平台根底下有子模組時 → 判不了(子模組由 `git ls-tree -r <終點>` 列出的 160000 項判,一次推送查一次);第②道 `outside`、`error`、逾時 → 判不了。判不了不擋、印一行。提交時與 doctor 沒有被推的版本,只做第①道。
- **明標刪除**:`[test-gone:名稱]` 或 `[test-gone:名稱@提交]`——這支測試已經刪了,提交編號選填(只當追溯線索,不驗;格子只驗寫法——有 `@` 時後面至少 7 碼十六進位)。驗的是內容:名稱不能是空的或佔位字,而且不能指得到真測試(還指得到就是假話)。它不算 PITFALL 防回歸那一格。
- **作廢的條目**:那一條 `slot_parse` 解出 `status` 是 `superseded`(`_ns_superseded` 同一判法,任何前綴、正文行與條款行也適用);只有 `[被取代:]` 沒有 status 的不算。**活測試**:指得到真測試的測試名。
- **佔位字**:去掉平台前綴後名稱整個是 `待補`、`待定`、`TODO`、`TBD`(不分大小寫)其中之一。

## 範圍

- 做:note-shape 多一組規則「碰到的筆記整篇要乾淨」(推送時與 CI 擋、提交時只提醒);`[test-gone:]` 登記成格子鍵;doctor 多一段全庫提醒(同一套判法、不分碰沒碰);設定 `note_shape.test_refs`;把表態閘「在被推的版本找測試」那段抽成共用。
- 不做:合約行與條款定義行的存在檢查——合約行由 doctor Check T 與推送前合約測試閘管;條款定義行交 spec-trace 與 doctor S5,它們對懸空只提醒、推送時只擋風險低的 doing 計劃,本案也不擋:計劃寫條款時測試常常還沒寫(設計先行),擋了會卡設計階段的推送。已收尾計劃的條款懸空因此沒人擋——已知缺口;rtb 2026-10-02 量到的 58 個指不到全部不在條款行或合約行上(doctor 的條款段與合約段都沒看到它們;出處記在 `governance/review-reports/筆記測試綁定要存在-r4/r2-intake.md` 那張表的 b6 列),所以本案先不收,回頭條件在 REVISIT。其他不做:不真跑測試;不自動把指不到的改成 `[test-gone:]`;不清 rtb 或本 repo 既有的(各自清,見路線圖的循環;本 repo 這次會碰到的除外,見〈做法〉12);散文寫的撤除不擋,只在 doctor 列候選;不改 PITFALL 的三選一;不認「檔裡有 `def 名稱(` 但 profile 認不得」的寫法(會把一般函式名也放行,設計審 r4 實測);Python 寫在類別裡、profile 不認得的測試會被判指不到——已知限制,用 `warn` 退。

## 做法

1. **碰到的筆記從哪來**:`cmd_note_shape` 呼叫 `_note_shape_eval` 時一律帶 `slots` 容器(格子要跑時照舊帶 `mark2`;不跑時傳空容器——它只取回 `notes` 與 `old_by`,格子規則由之後的 `_ns_slots_violations` 另外判,不會被打開)。這組從 `slots["notes"]` 的 `(路徑, 全文, 新寫行)` 照〈名詞〉的判法挑出碰到的篇。不另呼叫第二次 `_notelines_new`。
2. **讀內容**:直接用 `slots["notes"]` 裡的全文(那就是被檢查版本的全文,提交時讀索引、推送時讀終點),不再讀一次。用 `_note_from_text` 建筆記物件取摘要條目與 `type`。
3. **規則**(這組自己的違規清單),對碰到的每一篇整篇:
   1. 測試名(合約行與條款定義行除外)指不到 → 違規,印筆記、行號、名稱、原因與改法:改成真的測試名;測試已刪就寫 `[test-gone:名稱]`(PITFALL 另要 `[防回歸:無 理由]` 或 `[repro:指令]`);沒有測試就拿掉,PITFALL 同樣改寫防回歸無或 repro;名稱含 `:` 而平台前綴沒定義、看起來是人工驗證(例如 rtb 的 `[test:browser:…]`)時另提示改用 `[manual:一句怎麼驗]`。
   2. 摘要條目裡有佔位字、或 `[test:]` 方括號裡沒有名稱 → 違規,不判存在;改法照那一條的前綴;摘要裡要提到這個標記本身,就包反引號寫成 `` `[test:]` ``(`slot_parse` 不看成對反引號裡的東西)。正文裡散文提到 `[test:]` 這個標記本身不算;`slot_parse` 對沒收尾的方括號給的錯誤欄位不當名稱。
   3. `[test-gone:]` 名稱是空的、是佔位字、或指得到真測試 → 違規(最後一種:測試還在,改回 `[test:]`)。
   4. 作廢的條目(含條款定義行、合約行)掛著活測試 → 違規。改法照那種行給:一般摘要條目把綁定移到接手的那一條(`[被取代:]` 指的那裡)或拿掉,作廢的 PITFALL 拿掉後補 `[防回歸:無 已作廢]`(新寫的作廢 PITFALL 格子照樣要三選一);合約行整行刪掉、或拿掉 `★INVARIANT★` 記號降成一般條目再移走或拿掉綁定(留著記號只拿掉 `[test:]` 會變成裸合約,doctor `--ci` 照擋);條款定義行改寫成 `[manual:已撤除,見 被取代 指的那裡]`(拿掉會變成「沒標」讓 spec-trace 唸);不建議改成 `[test-gone:]`(測試還在,那是假話)。
   5. PITFALL 條目有 `[test-gone:]`、沒有 `test`、`repro`、`防回歸` 任一 → 違規(格子規則會把只改欄位的舊行放過,這裡補上)。
4. **判存在**:有要查的名稱時才 `_platform_test_index` 一次,名稱以「(平台, 名稱)」去重、照「筆記路徑、行號」排序後依序查(同一次推送每次查的順序一樣)。整組共用一個 20 秒上限,從建索引起算、每查一個名稱前看一次(第①道沒命中時要在整個 repo 文字裡比對一次,本 repo 1000 個不存在的名稱約 2.8 秒,這段也算在上限內;單一名稱的比對中途不打斷);第②道每次的逾時秒數是 8 秒與剩餘時間取小,不讀表態閘的 `LUMOS_DISP_GIT_TIMEOUT`;逾時或用完時剩下的名稱這次不查、印一行。索引建不起來、或某平台的根不存在、掃不到任何測試方法 → 那個平台這次不查、印一行;這組任何一步丟例外 → 整組這次不查、印一行(note-shape 本來就 fail-open)。
5. **保險**(推送時,這組只提醒不擋並說原因):①目前簽出的提交(`git rev-parse HEAD`)不是推送終點——CI 的分離簽出就等於終點,不觸發;②`git diff HEAD --name-only --diff-filter=MD` 在各平台根底下(根在 repo 外的平台略過)列出的檔裡,有檔名符合該平台 profile `file_name_match` 的(沒有這欄的 profile 改用測試副檔名;排除 `docs/`、`governance/`)——含已暫存與沒暫存的修改或刪除,新加的檔不算;③`.lumos/config.json` 有沒提交的改動(第①道讀的是工作目錄的設定)。這三種時工作目錄的索引跟被推的版本對不上。新開一支還沒追蹤的測試檔不在保險內,照擋。本 repo 的測試都寫在已追蹤的 `scripts/test_lumos.py`,它有沒提交的改動時本機只提醒、交給 CI。
