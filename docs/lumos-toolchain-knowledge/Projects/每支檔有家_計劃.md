# 每支檔有家_計劃

> 白話：每支程式檔都要有一篇「管它的」節點；節點只准寫自己管的檔，別人的一律用連結；程式改了，說明要寫進改到那支檔的那一篇，而且要往圖譜寫說明，改到的每支檔都得先有家；計劃寫明現況要落在哪一篇。新加的違規當場擋，舊帳只提醒；整道閘有專案層級的開關。

## 為什麼（這批的來源）

2026-09-11 對三個 POS 消費專案做節點健檢，客人網頁那個專案**又長成一篇包全部**——距離後端第一次長歪、拆開、加上合約條數提醒，不到兩天。

- 客人網頁 9/10 15:15 出生就只有一篇（客人端決策層），摘要的依賴行用反引號列了四支別的程式檔；之後吃完再結、外帶兩個功能都寫回同一篇：說明行 9→11、全文 47→96 行、掛 3 份計劃。13 支程式檔只有 1 支是它正式管的（about_code），3 支靠依賴行順帶連上，其餘 9 支（8 支畫面加入口檔）改的時候不會推出任何筆記——依賴行寫的是資料夾路徑，波及計算對不到任何檔。
- 篇內還留著翻案前的殘渣：流程行與一段正文寫「開場會去讀這桌已經點了什麼」，那條路 9/10 就拿掉了，同一篇的合約自己寫「沒有讀單的路」（程式與一個乾淨查證員兩邊對過）。
- POS 平板：7 支程式檔沒有任何節點提到（6 支是畫面），另 5 支只被別篇順帶提到；後端：9 篇裡 6 篇的依賴行寫了別人的檔，伺服器裡「客人的路只准這幾條」的合約，改伺服器那支檔時不會被推出來。

**沒有哪道檢查失效，是沒有檢查量這個形狀**（兩個來源對過：自己讀碼＋乾淨查證員讀碼）：

1. 合約條數提醒只數合約（門檻 10，提醒不擋）；它原本的「提到 ≥3 支檔」在設計審被拿掉並寫成合約「不看提到幾個檔」（[[Systems/節點範圍與索引守衛]]）。
2. 依賴行的內容沒有任何檢查；「一支檔一個家、別人的用連結」只寫在私人記憶與那道提醒的文字裡（合約破 10 條才看得到），教寫節點的說明裡沒有，在消費專案開的會談讀不到。
3. 提交前「改程式要動圖譜」只看有沒有動任何一篇；旁邊「該動哪篇」的點名以反引號命中的節點為種子，再加連結擴散與文字相似度排序——在客人網頁，種子永遠是那篇大雜燴。**工具在把人往那篇推。**
4. 改檔前推「必看筆記」只認正文反引號路徑，about_code 只加分（[[Projects/固定席扇出降權_計劃]] 的裁定）；不會提醒「這篇管很多檔」。★2026-09-12 這一條已經翻案★：確認過的家（那篇的正文或摘要真的寫出這支檔）現在直接進必推名單，見 [[Projects/推筆記認家_計劃]]。

**跟即興開發的關係（Enzo 問）**：加速器，不是根。POS 每個功能都有規格與設計審；lumos 自己一份份規格做出來，核心節點照樣累積——[[Systems/design-loop]] 摘要有 32 行 KEY、全文 176 行，KEY 行標的日期橫跨 7–9 月二十幾天、正文連到 14 份計劃（2026-09-11 量），只是合約 1–2 條、提醒從沒響。缺的是「規格寫明現況落在哪一篇」這一步，以及寫回時落對篇的機械檢查。

## 世界上怎麼做的

PRIOR-ART: ① 最小解層級——about_code 欄位、改檔前推筆記的抽取、工具自裝檔判定、測試地圖的測試檔判定、處置閘「照首筆帳日期生效」、提交前掛鉤呼叫 lumos 子指令的形狀、效能檢核閘的專案開關都已存在，這案是把它們接成一道「寫的當下」的閘，不新增依賴。② 世界解過沒——「每支檔對應負責人」是 GitHub CODEOWNERS，它的驗證工具 codeowners-validator 有專抓「沒人負責的檔」的 notowned 檢查（實驗功能）；「只對新增的部分嚴格、舊的慢慢還」是 diff-cover 只檢查這次改到的行的做法；「只能透過宣告過的介面引用別的模組」是 Nx 的 enforce-module-boundaries 規則。③ 裁定：借這三個形狀自建（零依賴家規）；負責人表不另開一份檔，直接用每篇節點既有的 about_code，避免兩份來源漂移。

## 名詞

- **需要家的檔**：專案自己的程式檔。四個條件都要成立：
  1. 受版控，而且在提交索引或提交裡的檔案模式是一般檔（100644 或 100755）——連結檔（120000）與子模組（160000）不算；模式從 `git ls-files -s`（提交前）與 `git ls-tree -r`（推送前）讀，跟既有程式碼在算「受版控一般檔」時同一種判法。
  2. 是程式檔：副檔名在「改程式要動圖譜」那道閘的清單裡，或沒有副檔名而首行是 `#!`。那份清單現在是四份副本（提交前、提交後兩支掛鉤，Claude 端兩支掛鉤）由一支一致性測試釘住；lumos 主程式新增**第五份同內容的具名常數**，並把它接進那支一致性測試（擴成五份一致），不另起一套判法，也不借用主程式裡另一份內容不同、給符號查核用的副檔名表。
  3. 不在排除清單：docs/ 與建置輸出夾（跟提交前那道閘的排除表同一份）、測試檔（見下）、lumos 自己裝進去而且內容沒改過的檔（內容指紋判定；在 lumos 來源 repo 不排除，跟提交前那道閘同一條規則）、專案設定 `node_home.ignore` 列的樣式。
  4. 檔名是合法 UTF-8：圖譜筆記是 UTF-8 文字，寫不進那種路徑，所以這種檔永遠不算需要家的檔，只在健檢提醒「建議改名或加進 ignore」。
- **測試檔**：用測試地圖那一支判定；副檔名不在它清單裡的程式檔（例如 shell、Go、Rust、C/C++），套它同一組目錄與檔名規則——路徑裡有 tests／test／__tests__／spec／specs 這一層目錄、檔名含 `.test.` 或 `.spec.`、主檔名以 `test_` 開頭、或以 `_test`／`_tests`／`_spec`／`_specs` 結尾（例：Go 的 `foo_test.go`）；另認各棧的測試資料夾，從測試棧對照表推——Gradle 的 `src/` 底下 androidTest（和 test）、Xcode 與 .NET 頂層名稱以 Tests 結尾的資料夾（要去掉結尾的同名頂層資料夾裡有同一種副檔名的檔；Gradle 那條要緊接在 `src` 下一層、副檔名屬於那一棧、同模組 `src/main` 有同一種副檔名的檔），資料夾裡同一棧副檔名的輔助檔一起算（別種語言的輔助檔，例如 Xcode 測試資料夾裡的橋接標頭 .h，照舊要家）（2026-09-12 補，見下方「代碼審時對計劃的修訂」最後一條）。
- **`node_home.ignore`**：字串清單；每一項是比對 repo 相對路徑的 glob，語法跟既有共改排除樣式那一支相同（`fnmatch`，`**/` 開頭的另外去掉前綴再試一次，才吃得到根目錄的檔）；非清單、或清單裡不是字串的項，那一項略過並出聲，其餘照用。
- **家**：狀態是 doing、done 或 stale 的 Systems 節點，about_code 列了這支檔。
  - planned、deferred 還沒成為現況，rejected、superseded 已經不是現況——這四種都不算家。stale（回頭條件到期待重驗）照樣是家：它仍然是那支檔的說明，只是該重看了。
  - 比對用字面比對鍵（路徑正規化＋NFC），★不讀磁碟★——about_code 寫入時已經照磁碟校正過（解連結、大小寫、Unicode 寫法）；推送一個不是目前 checkout 的分支時，磁碟上的拼法跟那個提交對不上，照磁碟比會把同一個提交裡順手改好的大小寫改名誤判成沒家（第二輪實跑重現）。
  - **只看欄位值，不看 about_code 的預標指紋有沒有過期**：那個指紋在正文一改就過期，而規則三要求寫回、寫回就會改正文——看指紋的話，每次合規的寫回都會讓家消失；另外 `lumos new` 建的節點本來就沒有指紋。那個指紋管的是「預標的品質」，不是「宣告」。
  - Issues 的 about_code 不算家——事故筆記本來就該被推，但它不是現況的歸屬。
  - 一支很大的檔可以有好幾個家（後端訂單檔本來就分狀態、訂單列、保存三篇）。
- **別人的檔**：節點正文或摘要裡用反引號寫、改檔前推筆記那套抽取會認成某支需要家的檔，而那支不在這篇的 about_code 裡。
- **內容有變**：兩個版本之間，摘要、決策、正文三者任一不同（逐欄比對兩個版本解析後的值）；其他開頭欄位（verified_by、plan_refs、related、tags、aliases、updated、status 等）的變動算簿記。★不沿用既有只算正文的那支雜湊★——摘要與決策都在開頭欄位裡，那支雜湊看不到，而節點長大主要就長在摘要。
- **讀哪個版本**：提交前一律讀提交索引裡的版本（節點與程式檔都是），不讀工作目錄——同一個工作目錄另一個會談寫到一半、還沒加進索引的東西不會被讀到；推送前讀範圍兩端的提交。讀法：跟磁碟一樣的直接讀磁碟，不一樣的那幾支才用既有的 `git show` 包裝一支一支讀；推送前的起點那一側只讀這段範圍裡有變動的節點，其餘跟終點那一側共用。設定（`.lumos/config.json`）、工具自裝檔的內容指紋、圖譜位置也從同一個版本讀——工作目錄裡沒暫存的「關掉」關不掉提交索引的檢查。★不另寫批次讀取★——這個 repo 的架構審查曾把另寫一套批次讀取判成「第二種做法」退回（工具自裝檔判定那一段的註解有記）。
- **新違規**：這次提交（或這次推送的整段範圍）造成的違規，跟之前比多出來的；之前就存在的叫**舊帳**。

## 核心裁定

### 規則一：每支檔都要有家

- [S1] 「需要家的檔」照上面的定義；程式檔判定用主程式新增的第五份清單，並接進既有的一致性測試（五份一致）。 [test:t_nodehome_required_files_definition]
- [S2] 「家」照上面的定義：狀態只認 doing、done、stale；只看 about_code 欄位值、不看預標指紋；比對用字面比對鍵、不讀磁碟。 [test:t_nodehome_home_definition] [test:t_nodehome_other_branch_rename_uses_commit_spelling]
- [S3] **擋**：這次新增（含改名成新路徑，以及這次才變成需要家的檔：捷徑檔換成真的程式檔、沒副檔名的檔補上 #!——git 標的是 T 或 M 不是 A）的需要家的檔，之後沒有家。同一個提交裡順手建家就過。 [test:t_nodehome_check_blocks_new_homeless_file] [test:t_nodehome_newly_required_file_counts_as_new]
- [S4] **擋**：這次讓一支原本有家的檔變成沒家——從 about_code 拿掉、家那篇被刪、或家那篇的狀態改成 planned、deferred、rejected、superseded。改成 stale 不算。 [test:t_nodehome_check_blocks_home_removal]
- [S5] 改到之前就沒家的舊檔：這次沒有任何 Systems 節點內容有變 → **只提醒**；有 → 照規則三的 [S13b] 擋（決策 d4）。 [test:t_nodehome_touched_legacy_homeless_warns_without_write_back]
- [S6] 擋下的訊息把沒家的檔依資料夾分組，每組附候選家（同資料夾其他檔的家、正文提到它的節點）與可以直接改的指令樣板（新開一篇帶 `--code` 與 `--responsibility`；或加進確實在講它的那篇）；最多列 10 支，超過印「還有 N 支」，跟既有「改程式沒動圖譜」那道擋下訊息同一個上限。 [test:t_nodehome_check_message_groups_and_truncates]
- [S34] **新專案出生**：剛接上 lumos 的專案第一個加程式的提交，每支檔都是新增，全部要有家——這是刻意的：節點怎麼切在出生那一刻就要決定，這次事故就是出生時只建一篇。訊息照 [S6] 分組、給樣板。 [test:t_nodehome_birth_commit_requires_homes]

### 規則二：節點只准用反引號寫自己家的檔

- [S7] 只看 Systems 節點。「這篇寫到哪支檔」的抽取**重用改檔前推筆記那一支**（完整路徑＋在受版控檔裡唯一的裸檔名），不另寫一套——兩套算法一定分岔，而分岔時沒有東西會翻紅。 [test:t_nodehome_foreign_ref_uses_impact_extraction]
- [S8] 只有需要家的檔算「別人的檔」；測試檔、非程式檔、工具自裝檔寫了照舊可以。裸檔名在受版控檔裡不唯一時，推筆記那支不認它、也就不會因此把這篇推給那支檔，所以不算認領——這條規則要防的正是「節點變成別人檔的入口」。 [test:t_nodehome_foreign_ref_definition]
- [S9] **擋**：這篇之後比之前多出來的別人的檔（這次新開的節點＝全部都算新）；另外，這次新增的檔如果讓一篇沒改的節點原本就寫著的檔名變成別人的檔，也算這次的新違規（那篇從這次起就是那支檔的入口）；那篇這次沒改、同一個提交裡改它又會被規則三擋，所以擋下訊息要講明「另開一個只改筆記的提交先改它」，並分「原本就在講這支檔→改寫成連結」與「只是剛好同名→把檔名改寫掉」兩種改法。已經寫在裡面的舊檔名只提醒。 [test:t_nodehome_check_blocks_new_foreign_ref] [test:t_nodehome_new_file_awakens_foreign_ref]
- [S10] 訊息指出是哪支檔、它的家是哪篇，建議改寫成節點連結；那支檔沒家就指回規則一。 [test:t_nodehome_foreign_message_points_to_home]

### 規則三：寫回要落在改動檔的家

- [S11] 只在這次改了（含刪掉、改名）需要家的檔時生效；純圖譜提交（整理節點、補家）不受這條管。推送前整段比時規則三逐個提交看：只看同一個提交裡也改了程式的節點、配那個提交改的檔——不然一次推送裡「改程式的提交」加「純整理節點的提交」會被混在一起誤擋（[S13b] 同理）。★「那篇內容有沒有變」也逐個提交算★：內容是前一個純整理提交改的、改程式的提交只替它補簿記欄位，不算後者寫回（2026-09-11 平板 POS 第一次真推送踩到，原本拿整段頭尾比）。 [test:t_nodehome_route_skips_docs_only_commit] [test:t_nodehome_route_counts_deleted_files] [test:t_nodehome_diff_route_per_commit] [test:t_nodehome_diff_route_counts_content_per_commit]
- [S12] 「內容有變」照上面的定義（摘要、決策、正文逐欄比對；決策比解析後的值，只改引號這種等價寫法不算）；簿記欄位的變動不算。 [test:t_nodehome_route_content_change_definition] [test:t_nodehome_decisions_compared_by_value]
- [S13] **擋**：內容有變、而且狀態能當家（doing、done、stale）的每一篇 Systems 節點（含這次新開的），之後必須是某支改動檔的家；刪掉的檔看它刪之前的家。作廢、否決、還沒成為現況的節點寫說明不受這條管（它們不是現況，寫進去不會長成大雜燴）；被刪的節點由 [S4] 管。 [test:t_nodehome_check_blocks_write_back_to_non_home]
- [S13b] **擋**：只要有任何 Systems 節點內容有變，每支改動的需要家的檔之後都要有家——這是提交層級：只要有一篇內容有變，這次改到的每支檔都要有家，跟那篇講什麼無關。這堵的是「順帶改到一支有家的檔，就把別的沒家檔的說明用散文塞進同一篇」——規則二只看得到反引號，看不到散文，而這正是客人網頁長歪的方式。 [test:t_nodehome_write_back_requires_every_changed_file_homed]
- [S14] 訊息列出這次改的每支檔各自的家，給兩條路：寫進那些家；或這篇真的在講那支檔，就把檔加進它的 about_code（明文、審得到，受規則四的上限管）。**不另開逃生口**（整道閘的開關見 [S37]）。 [test:t_nodehome_route_message_offers_two_ways]
- [S15] 提交前與推送前「該動哪篇」的點名改成照家算，取代原本以反引號為種子的那一套（兩支掛鉤都不再呼叫它；推送前那份波及計算只留給合約測試閘用）：每支改動檔的家、這次沒被動到的列出來（提醒不擋）；一支改動檔的家超過 8 篇時（跟推筆記那邊「一支檔被太多篇標成關於它就不加分」同一個門檻），不逐篇列，改印一句「這支檔有 N 個家、這次一篇都沒動，說明寫進真的在講這次改動的那一篇」（不叫人去查計劃的落點欄位：那是計劃的欄位，這支檔在這裡沒有對應的計劃）。 [test:t_nodehome_sync_nudge_by_home]
- [S35] 這條管「寫到哪裡」，不管「有沒有寫」：改了程式卻完全沒動任何節點內容，照舊由既有「改程式要動圖譜」那道閘管（它接受任何一篇圖譜筆記有動）。不強制每次改程式都改家那篇的內容——很多改動（修錯字、重構）不改變記下來的行為，逼寫只會產生填充句。 [test:t_nodehome_route_does_not_require_content_change]
- [S36] 天花板：一支檔的家很多時（lumos 主程式現在有 30 篇），這條只驗得出「寫進其中一個家」，分不出寫對哪一個；寫到一個有家的檔、但散文講的是另一支也有家的檔，也驗不出來。這兩種落點靠規則五（計劃寫明落點、設計審看）與推筆記把正確的家推到眼前。 [manual:在本工具鏈改 lumos 主程式並寫回一篇節點，確認提交前的點名照 [S15] 印出「這支檔有 N 個家，落點請照計劃寫的」]

### 規則四：每篇要寫負責範圍（新開的一律要，舊篇管超過上限才要）

- [S16] Systems 節點多一個欄位 `responsibility`：一句話講這篇負責什麼、不負責什麼；至少 10 個字、要有實字（全標點、空白視同沒寫）。收進純量欄位白名單，用 `lumos set` 寫。 [test:t_nodehome_responsibility_field_validation]
- [S17] **擋**：這次新開的、或這次才成為現況（planned／deferred 之類改成 doing／done／stale）的 Systems 節點沒寫 responsibility。出生時就要講清楚負責什麼——這案的起點就是出生時只建一篇、什麼都往裡放；「規劃中的節點升格」也是出生，不然管 3 支以內的檔就能不寫。 [test:t_nodehome_check_blocks_new_node_without_responsibility] [test:t_nodehome_planned_to_doing_requires_responsibility]

## 範圍外（刻意不做）

- **不改「改檔前推必看筆記」的算法**：照舊認正文反引號路徑。規則二讓「節點只寫自己家的檔」之後，反引號路徑就等於家，不必推翻 [[Projects/固定席扇出降權_計劃]] 的裁定。
- **不改健檢的合約條數提醒**：它照舊只數合約；管幾支檔改由規則四管。會在 [[Systems/節點範圍與索引守衛]] 補一條決策說明分工，不改它的合約。
- **不自動拆節點、不判內容好壞**：拆成什麼、一句負責範圍寫得好不好，歸設計審與人。
- **不強制「每次改程式都要改家那篇的內容」**：見 [S35]。
- **不偵測篇內新舊打架**（例如翻案後殘留的流程行）：機械偵測做不到可靠。REVISIT:2026-10-11 用三個 POS 圖譜整理後的實例，評估「某篇之後又落了 N 份計劃、流程行卻沒動過」這個訊號值不值得做成提醒
- **不回頭整理別的專案**：三個 POS 圖譜是第一批實測，其他消費專案（兩個舊 Android 專案的節點完全沒填 about_code）在它們下次 `lumos update` 之後照「舊帳提醒」處理；它們第一次往圖譜寫說明時，會被 [S13b] 要求先替改到的檔安家——每次只要改到的那幾支，不是全部。

## 落點

圖譜節點（實作完成後寫進 `lands_in` 欄位）：

- 新開 `Systems/每支檔有家`：管 lumos 主程式、提交前掛鉤、推送前掛鉤三支（about_code 三支，沒超過上限），responsibility 寫「程式檔歸屬與寫回落點的提交前、推送前檢查與健檢舊帳；不管節點內容好壞，也不管設計審出口」。規則一到四與開關、讀版本、健檢三段的現況寫在這篇。
- 更新 `Systems/design-loop`：處置閘多的那一步與派工附落點現況（規則五）寫在這裡——它是條款綁定那一步的家，同一種機制放同一篇，新開的那篇不跨去管設計審出口。
- 更新 `Systems/節點範圍與索引守衛`：補一條決策——管幾支檔改由本案規則四管，合約條數提醒照舊只數合約。

非節點（寫在這裡、不進 `lands_in`）：開新節點提示、教寫節點的 skill、節點還原 SOP 兩處、紀律區塊範本、設計審派工範本的架構對齊那一節（見 [S30]）。

## 實務隱患

- **誤擋**：規則三在「一句說明同時講兩支檔」時會擋；[S13b] 是提交層級——只要有一篇節點內容有變，這次改到的每支檔都要有家，跟那篇講什麼無關；舊專案第一次寫回時要先替改到的檔安家。處置：唯一的解法是把檔加進對的那篇（明文、審得到），不開單條逃生口；整道閘有 warn／off 開關（[S37]）；回頭條件見下。
- **漏擋**：散文講另一支也有家的檔、家很多的檔分不出寫對哪個家（[S36]）。處置：承認天花板，靠規則五與推筆記；回頭條件人工抽查。
