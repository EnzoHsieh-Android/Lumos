# 代碼審資料狀態鏡頭_計劃

> 白話:代碼審派審查員時,派工詞裡的「正確性」那副眼鏡多問五個 DDIA 式的問題(新舊版本讀得懂嗎、寫一半當掉會怎樣、衍生資料取哪一筆、時區對不對、會不會刪到不該刪的),並把既有的「冪等與併發」那一問寫寬一點。不擋推送、作者不用多做事。

## 現況(2026-09-29 讀檔的觀察,以檔案為準)

- 範本 §3 上一次同型修改(2026-08-28 名詞清單改成帶例子的問句)記在 [[Systems/design-loop]] 的決策 d6,所以本案 lands_in 也列那篇(std r1 整合 F1)。範本、代碼審 skill 與 reference 這幾支 .md 目前沒有登記在任何 Systems 節點的 about_code 裡(既有欠帳,每支檔有家不管 .md;std r1 架構對齊 F2),本案不處理。
- 兩處用「冪等併發」「邊界」當名字的歷史段(代碼審 reference 與設計審 reference 的舊 canary 注入型別)跟本案要改的派工詞無關,grep 會混進來,不改(std r1 整合 F3)。

- 代碼審派工詞的單一來源是 design-loop skill 的派工範本第 3 節:代碼審 reference 的 refute framing 兩處寫「完整鏡頭以範本第 3 節為準」;代碼審 skill 步驟 2 只指到第 3 節的 Codex 做法與圖譜鏡頭格式,沒提正確性鏡頭內容。
- 第 3 節的審查鏡頭有四點:正確性四問(邊界、資源、例外與 None、冪等與併發)、pitfalls manifest、圖譜鏡頭、本案特定鏡頭。沒有新舊互讀、寫一半、衍生資料、時間這幾類。
- 設計審的業務類追問(對外送出、做了回不去)只在審設計稿時出現;直接審程式改動的路徑沒有。本計劃把這兩類併進同一段問句,算是交付 Enzo 那句「設計審追問接到 diff 路徑」——只在審查員鏡頭層,不在 pitfalls 的輸出層。

## 設計(第三版:light r1 十一條+std r1 十七條折入,各條出處見〈審計修正紀錄〉)

1. **併進第 3 節派工詞第 1 點「正確性」,不另開一點**:既有四個子題後面接五個新子題,寫法同既有子題——無條件列出、同樣要求挑具體輸入走一遍。
2. **重疊的兩題不另立,擴寫既有「冪等與併發」子題**:同時讀改寫、對外送出重試併進那一條。
3. **邊界子題的填空範例拿掉「時區」**:時間比較改由新的「時間」子題固定問。
4. **「不可逆」子題只問「會不會連帶動到不該動的」**:standard 單席沒有回滾席,需要這一問;panel 的回滾席照 §7.7 立場往深處挖(退不退得掉、資料救不救得回)。
5. **用詞對齊既有風險分類**:「不可逆」「對外送出」。
6. **panel 多席怎麼分(std r1 外家 F1、整合 F2)**:第 3 節是每一席的共同底稿,第 1 點本來就會發給每一席——「只跟著正確性席走」不是現況,要明寫。做法:在範本 §7 平行 panel 節加一句分流規則——**多席時,五個新子題只留給正確性/邏輯席;其他席派工時從第 1 點刪掉這五個新子題**(既有四個子題維持原樣,不在本案範圍)。standard 單席照單全收。這條靠編排者照做,沒有機械擋(派工詞是編排者當場組的,工具看不到每席實際拿到什麼)。
REVISIT:2026-12-29 抽 5 份 high 代碼審的 rN-dispatch 與派工詞,看非正確性席是否真的沒帶五個新子題;帶了就把分流做進 dispatch-lens 或改寫範本成每席一段
7. **reference 只改現行那一份(std r1 外家 F2、正確性 F1)**:代碼審 reference 有兩份濃縮複本,一份在現行的 refute framing,另一份在「歷史與停用」區(只供回放舊帳,不是現行規則)。只改現行那份;歷史區保持原文,守衛還要驗它**沒有**被補上新子題,免得舊帳回放時看起來像當時就問過。
8. **代碼審 skill 步驟 2 加半句指路**,指到第 3 節正確性鏡頭含資料狀態幾問。
9. **第 1 點改完的全文**(全形標點,同既有子題;資源、例外與 None 兩行照抄現行原文,std r1 邊界 F2):

```
   · 邊界：空集合／只有一個元素／最大值或溢位／{本案高風險形態，如日期窗口、off-by-one}，這段扛得住嗎？
   · 資源：連線／鎖／交易，在錯誤路徑和提早 return 上確定釋放了嗎？
   · 例外與 None：哪個呼叫會丟例外或回 None，這段接了嗎？
   · 冪等與併發：同一操作重跑、或兩個請求同時進來，會壞嗎？同一次計算讀了兩次、中間被別人改了，結果會不會拼自兩個時間點？對外送出或扣款的重試會不會重複生效、收端怎麼去重？
   · 新舊互讀：新程式讀舊資料、舊程式讀新資料（新增的紀錄種類、欄位、格式），各會怎樣？
   · 寫一半：寫到一半被中斷（例外、被 kill、磁碟滿），留下什麼狀態？下次讀認得出、救得回嗎？錯誤訊息教的救法真的救得回嗎？
   · 衍生資料：它是真相來源還是算出來的（快取、索引、彙總、狀態提示）？同一件事有多筆紀錄（重跑、重試、撤回）時取哪一筆？
   · 時間：時間戳與日期比大小、判過期時，拿一個具體時刻走一遍（例如台北凌晨 1 點＝UTC 的前一天）；時鐘倒退、兩台機器時間不一致呢？
   · 不可逆：刪除、覆寫、截斷、搬移資料，會不會連帶動到不該動的？
```

10. **範本內容守衛**(不叫「漂移守衛」——那個名字在本專案指「同一個關鍵字有沒有散落到每一份該提的檔」;這支主要驗範本內容齊不齊):
    - **怎麼找到那段派工詞**(std r1 邊界 F3):從標題行「## 3. Code-loop reviewer」開始、到下一個「## 」開頭的標題為止,在這段裡取第一個內容含「審查鏡頭」的 ``` 圍欄。找不到就當紅,不當綠。
    - **不只驗標頭,也驗內容**(std r1 邊界 F1、正確性 F2):測試檔裡放一張「子題標頭 → 必要字樣」對照表,九個子題各至少一個必要字樣(例:資源→「錯誤路徑和提早 return」、例外與 None→「丟例外或回 None」、冪等與併發→「讀了兩次」與「重複生效」、新舊互讀→「舊程式讀新資料」、寫一半→「救得回」、衍生資料→「取哪一筆」、時間→「具體時刻」、不可逆→「不該動」);邊界那行另驗不含「時區」。檢查函式回傳缺了哪幾題(標頭不在,或標頭在但必要字樣不在)。
    - 誠實天花板:保留必要字樣、刪掉其他字仍會綠——它擋的是整題被刪或被改成別的意思,不擋逐字精修。
    - 消費專案沒有 skills 目錄時照既有慣例標「沒驗到」。
11. **這些測試會擋推送**(std r1 外家 F3):測試進全套,推送前的全套檢查與 CI 紅了就擋。這是刻意的——防止範本被悄悄改掉;誤擋時的處理=改範本的人同步改對照表(測試訊息會指出缺哪一題)。所以〈實務隱患〉的守衛面判成命中,不是已排除。
12. 措辭有兩處是實驗後才調的(時間題附具體時刻、衍生資料題加「多筆紀錄取哪一筆」)——實驗量的是調整前的版本,調整後的效果沒量過。
