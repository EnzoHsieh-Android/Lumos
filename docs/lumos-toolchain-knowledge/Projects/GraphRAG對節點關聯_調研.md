# GraphRAG對節點關聯_調研

> 白話:Graph RAG 的招牌手法(沿著連結擴散算分數、用模型抽知識圖、社群摘要)對我們幫助有限——擴散我們 7 月試過、被消融實驗砍掉;抽知識圖會丟資訊,而我們的圖本來就是人寫的;社群摘要答的是「整體有哪些」這種題,我們有範圍標籤和目錄頂著。真正卡住我們的是「評測題太少、而且出題判分同一個來源」,Graph RAG 解決不了這個。外界這一年最有用的訊號反而是「讓 agent 自己去搜,比預先塞好內容更好」——對我們的意義是:編輯時推播到底有沒有被用上,要開始量。

## 問的問題

Enzo 2026-09-11:「調研 Graph RAG 的實現方式,對我們節點演算法跑關聯性提供給 agent 的應用,有沒有什麼助益可以優化?」

我們的「節點關聯」有三個面(單源 [[Systems/retrieval-ranking]]):
- **search**:agent 下關鍵字找筆記。中文兩字切詞+BM25F(一種按欄位加權的關鍵字排序),評測 nDCG@5 0.8556(n=30)。
- **recommend**:從一篇筆記找相關筆記。距離衰減+共同被引用+鄰居相似度,再跟關鍵字分數融合。目前沒在用(dormant)。
- **編輯時推播**(impact hook 與派工鏡頭):agent 要改某支檔之前,把相關的合約、事故、筆記推給它。固定席(事故+合約)+自由席;保留題上前 8 名命中率約 0.73–0.75。

PRIOR-ART: ①最小解層級=先看圖譜既有檢索調研([[Projects/檢索優化_調研]]、[[Projects/檢索PPR邊權_計劃]])已經做過什麼,本篇只補 2026-07 之後或當時沒涵蓋的 ②世界解過:GraphRAG 系統性評比(arXiv 2502.11371)、GraphRAG-Bench(ICLR 2026)、LazyGraphRAG、Claude Code 放棄 RAG 改 agentic search、GRASP(2026-05)、LocAgent(ACL 2025),逐條讀到的內容見卷證 ③裁定=大部分不借(理由逐條寫在下面);可借的只有兩個小點,而且都要先有量測才准做

## 先查圖譜:這個方向我們已經走過哪些

- **2026-07-10 已經做過一輪完整調研**([[Projects/檢索優化_調研]]):HippoRAG 的 Personalized PageRank(從查詢相關的節點出發、沿連結擴散算分數)、LEGO-GraphRAG「圖分數一定要跟關鍵字分數融合」、Borodin 2005 小圖實證(千級節點上,簡單的「按距離衰減」78% 勝過 PageRank 48%)。落地採了距離衰減+融合。
- **PageRank 擴散 2026-07-28 已經被消融實驗砍掉**([[Projects/檢索PPR邊權_計劃]]):基準版 nDCG@8 0.9831,加 PageRank 的幾種版本約 0.981,沒變好。前提是候選池中位數只有 3 篇、推薦位 8 個——池子比推薦位小的時候,重新排序怎麼排都不會改變結果。
- **現行系統自己記的天花板**([[Projects/固定席扇出降權_計劃]]):評測題少(train 8 題)、判準文字與考卷裁決都經同一手,是同一個來源在自己驗自己。
- **程式結構圖補鏈**([[Projects/結構訊號補鏈D3_計劃]])已佔位,啟動條件是「出現現有兩種補鏈都接不住、只有程式結構耦合接得住的實證 miss」,目前零實證。
- **「推了之後有沒有被用」已經有一支唯讀量測**([[Projects/主session鏡頭利用率_計劃]],儀器 `governance/eval/lens-utilization/recount.py`):讀 Claude Code 逐字稿,用 toolUseID 對到那次編輯,看之後有沒有讀被釘住的筆記;只印分佈、不出單一命中率、不寫任何帳。2026-09-04 第一份報表:推送 33 次進分母;只釘 1 篇的之後有讀 2/16,釘 11 篇以上的 7/13(集中在同一支測試檔,可能本來就在碰);推送前就讀過的 24/33。10 筆人工抽樣排在 2026-09-17。
- **否決過的機制**:「把每支命令一筆寫進 `docs/.usage-log.jsonl`」([[Projects/全repo審視_計劃]] F08)——使用帳沒有 session、沒有時區、被 git 追蹤,每回合寫會讓合併衝突變常態;派工鏡頭定案「不擋不驗不記不量」([[Projects/派工鏡頭注入_計劃]])。另外 impact hook 只認 Edit/Write/MultiEdit/apply_patch,用 Bash 改檔永遠不會推送。
- **規模**:本 repo 圖譜 475 篇、約 3,000 條連結;消費專案約 300 篇級。外界 Graph RAG 的效益大多量在萬級以上的大語料,小圖上要打折看(這一點 7 月那篇已經用 Borodin 實證過一次)。

## 外界這一年說了什麼(只列本次實際讀到的)

1. **Graph RAG 不是萬靈丹,只在多跳題小贏**(arXiv 2502.11371 系統性評比)
   - 單一事實、細節型的題:普通檢索贏(NQ F1 64.78 對 60.04)。
   - 要跨好幾步推理的題:圖檢索小贏(MultiHop-RAG 70.27% 對 67.02%)。
   - 用模型自動抽知識圖:答案裡的實體只有約 66% 進得了圖——資訊在建圖那一步就掉了。
   - 兩者合併比依題型二選一好(+6.4% 對 +1.1%)。
   - GraphRAG-Bench(ICLR 2026)摘要原話:「GraphRAG frequently underperforms vanilla RAG on many real-world tasks」。各題型數字在全文,本次沒讀到,不引。
2. **微軟的 LazyGraphRAG:不預先做摘要,查詢時才花錢**
   - 建索引時只用名詞片語抽概念、算共現、切社群,不叫模型寫摘要,成本跟一般向量檢索一樣,是完整 GraphRAG 的 0.1%。
   - 查詢時用模型把問題拆成 3–5 個子查詢,再拿概念圖裡相符的詞改寫子查詢;逐步加深,由一個「相關性測試預算」控制花多少錢。
3. **讓 agent 自己去搜,勝過預先塞好內容**
   - Claude Code 早期用 RAG+本機向量庫,很快發現 agentic search(讓模型自己 grep、讀檔、再搜)比較好,而且沒有索引過期、權限、可靠度那些麻煩(Boris Cherny 原話,見卷證)。
   - GRASP(2026-05):把多跳問題拆成有先後順序的小計劃、子 agent 在圖上一步一步走,贏過「PageRank 預先檢索+逐步推理」的組合,token 還少四到五成。
   - LocAgent(ACL 2025):把程式碼庫變成異質圖,給 agent 一組圖探索工具做多跳定位;開源模型微調後可比專有模型,成本降 86%。

## 逐條對照:哪些借、哪些不借

- **PageRank / 圖擴散排序 → 不借(已殺)**
  - 我們 7 月自己量過沒有用,原因是候選池比推薦位小。外界評比也說圖檢索只在多跳題小贏,而編輯時推播本質是「這支檔跟哪些筆記有關」的單跳查詢。
REVISIT:2026-12-11 量編輯時推播的自由席候選池中位數;超過 8(推薦位數)才重開圖擴散排序的消融
- **用模型抽知識圖 → 不借**
  - 外界實測會丟約三成的實體;我們的圖是人寫、帶型別的連結(DEP、合約、驗證、決策),本來就比模型抽的準。我們版本的「建圖品質」問題是筆記沒連到程式碼,已經由 [[Projects/連結缺失補全_計劃]] 和 about_code 欄位在處理。
- **社群摘要(GraphRAG 的 global search)→ 不借**
  - 它答「整體有哪些主題」這種題,評比上會犧牲細節(查詢導向摘要 6.99 對 10.08)。agent 多常問這種題我們判不出來(沒有查詢紀錄);真的要問,有人工分好的九類範圍標籤(`lumos query --tag scope/…`)和目錄頂著,等於人寫好的社群。
  - 回頭條件:要先有查詢紀錄才判得出「agent 到底會不會問整體題」,見下方建議二。
- **兩種檢索合併 → 已經在做**
  - 我們現在就是關鍵字分數 0.6+圖分數 0.4 的線性融合。7 月那篇留下的開放題「線性加權還是名次融合(RRF)」,在候選池比推薦位小的前提下量不出差別,不值得先做。
- **程式結構圖 → 維持佔位**
  - LocAgent 支持「給 agent 圖探索工具找程式碼位置」,但我們的問題方向相反(從程式碼找筆記),[[Projects/結構訊號補鏈D3_計劃]] 的啟動條件(先有實證 miss)照舊合理。建議一的量測正好能產出這種 miss。

## 建議(依價值排序,都是「先量再做」)

- **建議一:量「推了什麼、agent 有沒有用上」,重點是 miss**——這是唯一能打破「同一個來源自己驗自己」的東西
  - ★2026-09-11 修正(乾淨 agent 覆核後)★:原本寫「在 lumos 新增推播帳、讀取紀錄帶工作階段代號」,那條路撞到兩個既有裁定(F08 否決寫進使用帳、派工鏡頭不記不量),而且推播全文其實已經在 Claude Code 逐字稿裡(帶 sessionId、toolUseID、注入全文)。**改成擴充既有唯讀儀器 recount.py,lumos 不新增任何寫帳。**
  - 加 miss 偵測:某次編輯檔 F 之後,agent 自己去讀、推播卻沒推的筆記,列成候選;「跟 F 有沒有關」由既有規則判(正文反引號寫到 F、或 about_code 含 F),判不出的交人/雙評審,補進評測題。
  - 逐字稿約 30 天會被清(Claude Code 預設 cleanupPeriodDays),要定期跑、把推導出來的列留存下來——這會改動儀器「不寫任何帳」的現行約定,要在計劃裡裁。
  - 限制:agent 會讀被推的東西,「推了而且被讀」有位置偏差,不能直接當成相關;「沒推卻被讀」比較可信。用 Bash 改檔不會觸發推送,這一段量不到。
  - 對應外界:LazyGraphRAG 用模型逐句判相關;我們有 agent 自己的行為可以當相關性測試,而且不花錢。
- **建議二:搜尋零命中時,用圖裡的詞幫忙改寫**——借 LazyGraphRAG「用概念圖改寫子查詢」,但不用模型
  - 痛點有實證:一個消費專案實測 8 句有 3 句零命中(原本寫在圖譜紀律區塊,2026-09-11 範本二次瘦身搬到 [[Projects/中文無空白查詢回退_計劃]]),現在靠 agent 自己換同義詞(紀律區塊「查得到才算先行」①)。
  - 做法:從筆記文字統計詞與詞的共現(同一行 KEY、同一個標題),某個詞零命中時,列出最常跟它一起出現的詞與 aliases 當建議。純標準函式庫做得到。
  - 前提:要先知道零命中有多常見。搜尋指令與輸出也在逐字稿裡(agent 用 Bash 敲 `lumos search`),同一支儀器一起數,不另開查詢帳。
  - 2026-09-11 量到了,但儀器量錯:[[Projects/推播miss量測_計劃]] 的零命中計數把「一次指令串多個搜尋」只記第一個查詢,W33–W37 只數到約 4 次真的用詞對不上;乾淨 agent 從逐字稿人工數出一個月 81 次零命中、34 次是「換個說法就查得到」(本 repo 30、Landmark 4),卷證 `governance/review-reports/搜尋零命中改寫/零命中獨立查核-sonnet.md`。儀器缺陷記了逃逸(code-推播漏網量測)。
  - 34 次的形狀:約三分之一是黏成一串的多概念中文(跟 [[Projects/中文無空白查詢回退_計劃]] 的 `--cjk-loose` 同一個坑;試 6 個,2 個第一名就對、2 個撈出兩三百篇前幾名不相干)、約一半是英文/程式識別字/中英互換(shuffle→隨機、requires_core→核心 掛載,查詢詞在筆記裡從沒出現,共現無從下手)、幾個是當時還沒寫的東西(死人開關、基準圖現在查得到)。本建議原本的「共現改寫」只對一小部分有用;方向待 Enzo 裁。
- **不建議做**:PageRank 重排、模型抽圖、社群摘要、融合公式換 RRF——理由與回頭條件如上。

## 誠實缺口

- GraphRAG-Bench 各題型的數字、PathRAG(把關聯路徑寫成文字給模型看)、RAPTOR、Graphiti(邊帶有效時間)這次都沒讀原文,只當線索、不當證據。
- 消費專案圖譜的連結密度、候選池大小沒量;上面「小圖」的判斷用的是本 repo 與記憶裡 Landmark 的篇數。
- 建議一不動 hook、不新增 lumos 寫帳,只擴充唯讀儀器;建議二會改 search 的輸出(零命中時多印建議詞),屬於 agent 天天用的介面,先寫計劃、過設計審。
