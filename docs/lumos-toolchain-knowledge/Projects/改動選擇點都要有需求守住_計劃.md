# 改動選擇點都要有需求守住_計劃

## 白話

改動裡「換一種寫法照樣編得過、行為卻不同」的地方(選擇點),是寫的人做了一個決定,背後應該有一條需求。這份計劃照 Google 的差異式變異測試(論文〈Practical Mutation Testing at Scale〉,以下稱「論文」)做:用 ast-grep(tree-sitter 的 Kotlin 語法樹)找出改動行上的語法節點,每一行挑一個壞法(把節點換成另一種寫法),批次跑計劃條款綁的測試:
- 測試紅了(殺掉) → 記下是哪條條款守住這一行的選擇;
- 測試沒紅(存活) → 這個選擇沒有需求守著:規格沒寫、測試太弱、或換了其實一樣 → 推送前擋下交人裁;人裁寫回規格並綁一支會紅的測試,或判「換了一樣/不是需求/壞法不適用」留帳。

不是每一行:log、斷言、時間、樣板方法這類「乾節點」(論文的 arid node)不產生壞法;一行只產生一個壞法(論文 4.1);要人處置的存活有上限「改到的檔數 × 7」(論文 2.3)。哪些節點產生什麼壞法、哪些節點是乾的,由 Kotlin 型錄的〈選擇點表〉與〈乾節點規則〉列出,每列對應一條 ast-grep 規則;乾節點規則由人照回饋手動增補(論文 3.1)。

這份把 [[Projects/雙向追溯_需求與語法選擇點互證_計劃]] 的正向(條款的測試分不分得出對錯)與反向(程式的選擇有沒有需求撐腰)併成同一個機制:殺掉的那一行是正向的證據,存活的那一行就是反向要找的「沒有出處的選擇」。

大方向(使用者 2026-11-13):「改動中的語法,必定是代表一種需求,而這個需求,必須引得出規格……語法是可以被窮舉的,也就代表 code review 是可以被機械層檢查」;「我想涵蓋的就是所有開發需求中的程式碼,不是特定哪一種類別的語法」;範圍是選擇點、不是每一行;「那就照那份論文來實作」「有什麼問題,優先參考」;設計審兩輪都被「沒有語法樹」打穿後,使用者 2026-11-14 裁「改用 ast-grep 語法樹」。

  - 相等(論文附錄 A.1.23):`==` 只換 `!=`、`===` 只換 `!==`;`!=` 只換 `==`、`!==` 只換 `===`(本計劃比照)。型別前提:一邊是 `null` 字面值的不產生(附錄 A.1.10;Kotlin 換了會破壞智慧轉型而編不過)。
  - LCR:`$A && $B` → `$A || $B`、`$A`、`$B`、`true`、`false`;`||` 同形。錨點是運算子所在行。
  - AOR:`$A + $B` → `$A - $B`、`$A * $B`、`$A / $B`、`$A % $B`、`$A`、`$B`;其餘同形。型別前提:任一運算元是字串字面值或字串樣板 → 不產生。錨點是運算子所在行。
  - UOI:`prefix_expression` 的 `!$B` → `$B`;`if`/`while` 條件或 `&&`/`||` 運算元裡的簡單識別字、屬性存取(`state.isLoading`)或呼叫 `$B` → `!$B`(論文表 1 的 `b → !b`;`a++`/`a--` 不做,Kotlin 多半是 val)。錨點是運算元起始行。

## 不做

- 不是每一行:乾節點不產生壞法;一行只一個壞法(論文 4.1)。
- 不引進外部變異工具(PIT 等);ast-grep 只當剖析器,是 Kotlin 規則包既有的外部工具。
- 不做論文 4.2–4.5 的依歷史排序與語法樹相似度;不接覆蓋率;不收數字常數、字串常數、`when` 分支刪除;REVISIT 看數字再加。
- 不讓 AI 自動判等價;判「不是需求」不自動推廣,乾節點規則人工增補(論文 3.1)。
- 推送前不重跑殺傷力;只讀帳、重算哪些行有壞法、驗新鮮度。
- 不管非 Kotlin 專案;測試檔、測試輔助 source set、`.kts` 不算。
- 不做多個選擇點的組合(天花板 4)。

## 實務隱患

- 跑太久:一行一個壞法;同一平台一次呼叫一棵工作樹;基準每條測試指令只跑一次、基準不綠的測試拿掉;同一壞法殺掉就停(`stop_group_on`;存活先用合併呼叫確認,見 [[Projects/選擇點變異加速_計劃]]);相關的測試排前面;`--max-mutants` 分批;只跑沒有有效處置的行;每次呼叫記 `run` 給 RETIRE-IF ②。Android 新工作樹冷編譯仍貴,實作時量一次 20 行改動的實際耗時寫進報告。
- 中斷白跑:`on_row` 逐列交結果,判定完整的壞法當場記帳;強制結束印工作樹路徑。
- 噪音:乾節點規則(論文附錄 A 譯成 Kotlin 的語法樹規則)、單元測試分不出或會掛住的寫法不收、型別前提事前擋編不過(論文 3.2.1)、回報上限檔數 × 7、只改縮排的行不算、測試輔助 source set 不算。
- 壞法仍編不過或掛住:no_result 記原因,人可判 `not-applicable`;`--stats` 依列號累計給人改表。
- 判定被敷衍:判定必帶理由與同意、`--stats` 列處置分布與殺很多檔的單一測試。
- 殺掉它的測試後來被換弱:要求 `killing_test` 還在守的測試裡;測試本體改過只提醒。
- 型錄改了:有效處置以行為單位,舊帳照算;帳上記型錄雜湊備查。
- ast-grep 版本差異:不同版本剖出的節點可能不同,`run` 記版本;規則樣本由 `check.py` 驗。
- 帳量:版控治理帳已約 22MB;每筆只存雜湊,守的測試對照每次呼叫只記一次;不寫殺傷力帳本。
- 帳沒提交就推:choice-kill、lint-waive choice: 結尾都印「提交治理帳」;推送閘從 B 讀,沒提交就是缺紀錄,訊息附「記得提交帳」。
- 跟代碼審的先後:lint-waive 與 choice-kill 都在 `code-loop pass` 之前做(situation-rule 會改計劃,也在之前);通過後只提交治理帳(放行檔不在帳本檔清單,通過後提交它會讓留痕失效)。回報上限的種子不受帳本提交影響。
- 跟情境題那道重疊(同一行既是情境決策表觸發字又是選擇點):兩道各管各的;人裁事件以 `point` 欄分開統計與分開預期值表豁免;可能各跑一次 Gradle(天花板 6)。
- 併發與交易:已排除:單人單機依序操作,沿用 guard kill 的隔離工作樹與人裁的訊號收尾;治理帳逐筆追加。

- [S2] 當運算子節點的運算元跨行或含括號與呼叫,choice-points 應 依語法樹的後設變數組出候選壞法並在巢狀時加括號;字串串接的 `+` 與跟 `null` 比較 應 不產生 [test:t_choice_points_operands]
- [S3] 當同一行內容與上下文不變而重跑(含 rebase 改了行號),choice-points 應 挑出同一個壞法;一個類別都被型別前提排除時 應 換下一個節點或類別;那一行不唯一時 應 往外帶行求唯一,仍不唯一標不唯一 [test:t_choice_points_stable]
- [S4] 當節點落在乾節點規則命中的範圍(含跨行引數、樣板方法本體、整個 delay 呼叫),choice-points 應 不在裡面產生壞法 [test:t_choice_points_arid]
- [S5] 當 SBR 的候選陳述是 lambda 最後一個陳述、當值用的區塊最後一個陳述、或函式本體唯一陳述,choice-points 應 不產生刪除壞法 [test:t_choice_points_sbr]
- [S6] 當 ast-grep 不在 PATH,choice-points 應 回 3、choice-kill 應 回 2;推送前那一道 應 只提醒、記 unverified、印安裝指令 [test:t_choice_no_ast_grep]
- [S7] 當同一平台有多個壞法,choice-kill 應 只呼叫一次殺傷力、每條測試指令基準只跑一次、同一壞法強 killed 或編不過或逾時就略過其餘測試,並依 recipe_id 把結果對回 [test:t_choice_kill_batch]
- [S8] 當某壞法有一支守的測試強 killed,choice-kill 應 記 killed、帶排序第一支殺掉它的測試與條款(合併有失敗時先跑名單裡的,見 [[Projects/選擇點變異加速第二段_計劃]]);每支都有列而且都 survived 應 記 survived 並回 1 [test:t_choice_kill_verdicts]
- [S9] 當沒有強 killed 而有弱證據、drifted、error、壞法編不過、測試掛住或缺結果,choice-kill 應 記 no_result 帶原因並回 2;某支測試基準 abort 時 應 拿掉那支、其餘照判 [test:t_choice_kill_no_result]
- [S10] 當工作目錄不乾淨、範圍沒碰到進行中計劃、計劃沒有可守的測試、或 run_cmd 沒有 {method},choice-kill 應 回 2 不跑 [test:t_choice_kill_rejects]
- [S11] 當同一行已有有效處置,choice-kill 應 跳過;已 survived 而守的測試沒變的行 應 不重跑;壞法超過 --max-mutants 或時間超過 --max-seconds 應 停在配方之間並說還剩幾個;每次呼叫 應 記一筆 run [test:t_choice_kill_incremental]

## 天花板

1. 只證「選擇點表列到的寫法有測試守著」;表沒列到的選擇(數字常數、`when` 分支、整段邏輯)這一版不管(第二批補了空值處理、範圍函式、Flow 合併與 Compose 副作用六列,見 [[Projects/選擇點表第二批常見誤用寫法_計劃]];第三批補了協程作用域、筆數、找不到與解析失敗、晚到的訂閱者、延後啟動、緩衝滿了、取消後還要做完、重試、新值取消舊的這幾組業務情境寫法,見 [[Projects/選擇點表第三批業務情境寫法_計劃]]);表與乾節點規則列得好不好決定上限(論文也承認規則依環境調)。
2. ast-grep 給的是語法樹、沒有型別;型別前提只能用語法情境近似(字串字面值、null 比較),推不出型別的壞法仍可能編不過,落成 no_result 要人放行。ast-grep 或文法版本變了,節點可能不同;規則樣本由 check.py 驗。乾節點不做複合遞迴:兩個運算元都乾的 `&&` 照樣會產生 LCR 壞法。SBR 把 Unit lambda 的唯一陳述(`launch { repo.load() }`)也排除,是保守側的漏。
3. 沒有覆蓋率:沒被守的測試跑到的行一定存活,要人處置;每個壞法跑全部守的測試(排序加殺掉就停),比論文的最小測試集慢;論文是每個壞法一份暫存版本平行跑,我們是一棵工作樹依序跑,靠 `--max-seconds` 分批。
4. 一行一個壞法、不做組合;同一行其他類別這次沒被挑到就不驗——面試題那種 `flatMapLatest` 若跟條件式同一行,有一半以上的機會挑到別的類別(論文的取捨;情境題那道另外會問 D-4)。
5. 殺掉只證「換成那個壞法時有測試紅」,不證測試紅的理由就是那條需求;條款跟選擇點是不是講同一件事靠人裁與代碼審。
6. 推送前不重跑,信帳;帳是作者自己跑出來的,同代碼審留痕的天花板。跟情境題那道對同一行可能各跑一次 Gradle。這一道只在 pre-push 掛鉤、CI 不接;沒裝 ast-grep 或 `--no-verify` 就不檢查(留 unverified 或沒有紀錄)。
7. 回報上限之外的存活不擋;新的存活行出現時重抽。
8. 判「不是需求」全靠人;判錯會放過規格缺口,乾節點規則寫錯會整類放過。
9. 掃描算不出來(含沒裝 ast-grep)時那一圈放行(規格閘既有方針),只留 unverified 紀錄。
10. 連前後各 2 行都相同的兩行共用一個行指紋,放行一處等於放行兩處(它們本來就分不開)。
11. tree-sitter 的 Kotlin 文法認不得中文識別字等語法,那些行整行略過、不產生壞法。
12. 沒給 `--diff` 而 repo 沒有遠端時,choice-points 照推送閘的既有規則從空樹算,整個 repo 都算改到的行。
