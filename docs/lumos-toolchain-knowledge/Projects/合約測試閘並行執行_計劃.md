# 合約測試閘並行執行_計劃

> 白話:推送前那道「改到硬合約就真跑它綁的測試」的閘,現在一支一支循序跑。本 repo 一次推送要跑約 51 支、三分鐘上下。這篇讓專案可以在設定檔打開「同時跑 N 支」,預設不變;本 repo 打開成 4。來源是立案清單第 2 項「合約測試閘變慢:先查原因」。

PRIOR-ART: pytest-xdist、本 repo 全套測試的 `--shard` 切片同時跑——都是「每支測試各自隔離、外層開多個工作者」;這裡照搬外層多工作者,每支仍走既有的單支執行函式(各自的程序群組與暫存輸出),不新增依賴。
RETIRE-IF: 打開後連續 8 週,同量級範圍(綠的支數 50 以上)的合約測試閘牆上時間中位數沒有比循序手量基準 176.5 秒低三成以上(即沒低於約 124 秒),或出現一次因同時跑造成的假紅(單獨重跑就綠),就把本 repo 的設定改回 1 並重新評估。帳上沒有打開前可比的牆上時間(舊帳 secs 是逐項相加),所以基準用這份計劃的手量值。
REVISIT:2026-12-15 看上線後 8 週治理帳 bound-tests 那一欄 secs 的中位數(只取帶 secs_kind=wall 的列;`lumos gov` 不帶 bound-tests 的 secs,直接讀帳:`python3 -c "import json,re,statistics;r=[json.loads(l) for l in open('docs/.governance-log.jsonl')];s=[x['secs'] for x in r if x.get('gate')=='bound-tests' and x.get('secs_kind')=='wall' and int((re.match(r'\d+',x.get('note') or '') or ['0'])[0])>=50];print(len(s),statistics.median(s) if s else None)"`),只取綠的支數 50 以上(同量級範圍,note 開頭是支數),跟上面的循序實測 176.5 秒對照,對照 RETIRE-IF

## 量測(2026-10-13)

- 一次推送範圍(本 repo 一條改到 `scripts/lumos` 與測試總檔的分支)波及 12 篇帶硬合約的筆記,綁定項目 59 個;執行函式已經用「解析後完整指令」去重,實際跑 51 支。
- 逐支量(機器負載約 9,絕對秒數偏高,只看相對):51 支合計約 171 秒。最慢三支合計 82 秒(處置閘條款測試約 41 秒、合約測試閘自己的測試約 23 秒、guard kill 優先序約 18.5 秒);其餘多在 1 秒上下,其中約 0.85 秒是每支重開程序載入測試總檔的固定成本。
- 排除過的猜想:①測試名被 `-k` 當子字串比對、連帶多跑別的測試——逐一算過,每個綁定名都只比對到自己;②同一支測試被多篇筆記綁而重跑——執行函式早就去重。
- 結論:時間花在循序執行本身,同時跑能把牆上時間壓到接近最慢那一支加排隊。實測同一批 59 項(51 支)接連跑三次:同時 4 支 55.8 秒、循序 176.5 秒、同時 4 支 56.0 秒,三次都 59/59 綠。
- ★閘回報與記帳的 secs 原本是每個綁定項目秒數相加,不是牆上時間★:同一支被幾篇綁就加幾次,同時跑時各支時間重疊又會被加總放大(實測同時跑時 CLI 報 215 秒、實際約 60 秒)。所以立案清單引的「中位數 65→223 秒」量的是這個加總,含重複計算,不等於實際等待時間,跟改後的牆上時間不能直接比。

## 範圍

- 只改「怎麼排程這些已去重的執行」:每支要不要跑、怎麼判紅綠、逾時、跑過證據、輸出尾巴,全部照舊。
- 不做:縮小綁定範圍(只跑直接相依那層)、本 repo 推送時因為之後會跑全套就跳過這道閘——前者改的是「該守什麼」,後者改的是閘的判定語意,都另案。
- 不改去重鍵、不改結果的順序與形狀。
- 順手修 secs:改記跑測試那段的牆上時間(逐項的秒數照舊留在每一項裡)。

## 做法

- 新設定 `.lumos/config.json` 的 `bound_tests.parallel`:整數 2–16 才算數;沒寫、1、布林、小數、字串、超出範圍一律當 1(循序,跟現在一樣);有寫但不合法、或 `bound_tests` 整個區塊不是物件時,印一句提醒(跟其他設定看不懂時出聲同一個慣例)。放在自己的區塊,不塞進 `test`(多平台模式下 `test` 不生效)。
- `_run_bound_tests` 先照原順序走過所有項目,把需要真跑的「去重鍵」依第一次出現的順序收集起來;N≥2 時用自建的 daemon 工作執行緒同時跑這些鍵(不用標準執行緒池,原因見實務隱患;每支仍呼叫既有的 `_kill_run`,它各自開程序群組與暫存輸出檔,本來就沒有共用狀態),主流程逐條等、每次最多 0.1 秒,N=1 時照現在一支接一支;全部跑完後再照原項目順序組出結果與 `tails`。
- 本 repo 的設定打開成 4(全套測試推送時也是切 4 片同時跑,這邊的測試已證可並行)。消費專案不動;各專案的測試工具能不能同時跑(例如會互搶建置目錄的工具)由專案自己判斷要不要打開。

## 驗收條款

- [S1] 當同一組綁定項目分別以 N=1 與 N=3 跑時,兩次的結果清單(去掉秒數)與 tails 對應 應 逐項相同、順序相同,紅、綠、跑過證據不足、逾時各至少一例 [test:t_bound_tests_parallel_matches_sequential]
- [S2] 當 N=3 時,執行期間 應 觀察到至少兩支同時在跑;當設定沒寫、為 1、0、負數、布林、小數、字串或大於 16 時,任一時刻 應 只有一支在跑 [test:t_bound_tests_parallel_config_values]
- [S3] 本 repo 的 `.lumos/config.json` 的 `bound_tests.parallel` 有寫時 應 是程式認得的值(1 或 2–16 的整數),程式讀到的 應 是它;不釘「一定要打開」,照〈回退〉改成 1 不會讓測試轉紅 [test:t_bound_tests_parallel_repo_config_valid]
- [S4] 當兩篇筆記綁同一支約 2 秒的測試時,閘回報的 secs 應 是跑測試那段的牆上時間(約 2 秒),不是兩個綁定項目相加(約 4 秒);記帳那筆 應 帶 `secs_kind: wall` 跟舊帳分得開 [test:t_bound_tests_secs_is_wall_time]
- [S5] 當同時跑時有一支開程序就丟例外(例如平台 root 不存在),不論它排第一或跟慢測試同時開跑,例外 應 馬上往外丟、不再派新的,整個程式 應 能馬上結束,不等其他已開跑的測試跑完,同批已開跑的其他測試子程序 應 被收掉(整個程序群組)不留孤兒 [test:t_bound_tests_parallel_error_stops_fast]
- [S6] 當同時跑、第一條工作執行緒先收工而別支還在跑時,主流程等待期間的 CPU 時間 應 遠小於牆上時間,不空轉 [test:t_bound_tests_parallel_wait_is_quiet]
- [S7] 當同時跑時主流程被中斷(Ctrl-C),工作執行緒 應 不再派新的測試 [test:t_bound_tests_parallel_interrupt_stops_dispatch]
- [S8] 當跑測試那段期間系統時鐘被往回調時,secs 應 不是負數 [test:t_bound_tests_secs_monotonic]

## 回退

- 合併前這個功能會壓成一個提交,之後單一提交還原即可;還沒壓之前要整段還原,用 `git revert -n <分支起點>..HEAD`(新到舊),會一併拿掉這段期間追加的審查帳與治理帳行,先把那幾行另存、還原後接回帳尾。只想關掉不還原程式時,把本 repo 設定的 `bound_tests.parallel` 拿掉或改成 1,行為就回到循序;S3 的測試只驗「有寫就要合法」,改成 1 不會轉紅。設定檔不在簿記清單,改它要照常走推送閘(只改設定檔時風險分級是 light)。
- 回退後帳上 secs 會混著兩種值:還原程式後新寫的帳沒有 `secs_kind`(逐項相加),只改設定的話照舊帶 `secs_kind: wall`。統計一律只取帶 `secs_kind: wall` 的列。
- 舊版程式讀到這個新鍵會直接忽略,新舊混用不影響判定。

## 實務隱患

- 同時跑時機器負載變高,單支測試耗時會拉長,逼近逾時上限的測試可能轉紅;逾時判定照舊每支各自計時,真碰到時先看那支是不是本來就慢(最慢那支約 41 秒,離 180 秒上限仍有餘裕)。
- 同時跑時一支出錯或按 Ctrl-C:不再派新的、馬上往外丟,程式也馬上結束(工作執行緒是 daemon,不用標準執行緒池——它結束時會等工作者收尾,map 依提交順序取結果也讓排在後面的例外晚浮上來);主流程逐條等每次 0.1 秒,不盯單一條(那條先收工後會空轉);同批已開跑的子程序整個程序群組一併收掉(收尾前等每個已領走的工作都登記了程序或確定失敗,最多 2 秒,免得剛開出來的那支漏收);循序模式按 Ctrl-C 的行為不變(仍可能留下正在跑的那一支)。
- 陌生 repo 自己的 `.lumos/config.json` 可以把同時跑拉到上限 16 支;能改這份設定的人本來就能寫 run_cmd 讓推送閘執行任意指令,所以這不是新的攻擊面,但打開陌生專案前要知道推送閘會照它的設定開多個程序。
- 規格閘與修正關卡判綁定測試也走同一支執行函式,設定打開後它們也同時跑;同一個專案的同一個不合法值,一個程序裡只提醒一次。
- 終端輸出若有逐支印進度,同時跑時順序會亂;目前這段只在全部跑完後組結果,沒有逐支印,所以不受影響。
