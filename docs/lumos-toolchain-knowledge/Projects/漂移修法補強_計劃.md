## 做法

### 1. c4 卷證目錄

- 取驗證紀錄第一次被提交的提交(`_plan_first_commit`;shallow 由既有 `_git_is_shallow` 先擋)。列那個提交加進來或改名進來的檔:`_nodehome_git(root, "show", "-z", "--name-only", "--diff-filter=AR", "--format=", <提交>)`,`_nodehome_split_z` 拆;只收路徑至少四段、形如 `governance/review-reports/<目錄>/<檔>` 的第三段目錄名,目錄名先 `nfc`、去重,只留目前還存在於 `governance/review-reports/` 底下的(改名或刪掉的舊目錄不列)。這是「同提交」清單;git 失敗或逾時當空,證據頁寫「同提交:查不到(git 失敗或沒有)」。
- 「計劃名」清單照舊用 `_drift_c4_key` 比對。
- 證據頁全部列出、每個標來源(兩者、同提交、計劃名),排序:兩者 → `code-` 開頭 → 其他,同級照字母;同提交清單超過 3 個時另起一行先印「可能含別的計劃的卷證(整批匯入或壓成一個的提交)」。每個目錄各印一行、各自過 `_esc_clean`(不把整張清單接成一行再截斷;無法編碼成 UTF-8 的字元先換掉,免得印的時候當掉)。
- 範本句改成「提交 <前 12 碼>;代碼審見 <卷證>」,查不到提交時提交那段寫成字面 `<sha>`;卷證一律放字面 `<卷證>`——兩個字面都取自第 2 節同一份常數,由人從清單挑(整句貼進 `lumos set` 會被第 2 節擋下,逼人換成真的目錄與提交)。
- 預填的 `lumos set` 指令照舊(要改的那項放 `<整項新內容>`),這次不改它的展開與長度處理。證據頁最後加一行:「用 lumos set 改完先提交,再對同一篇跑別的 drift fix(不然乾淨檢查會擋;別照它的提示 git checkout,那會洗掉 set 的修改)」。

### 2. `lumos set` 多擋兩個佔位字

- 在 `_SET_COND_SLOT` 旁邊加模組常數 `_SET_COND_SLOTS = ("<整項新內容>", "<卷證>", "<sha>")`(`_SET_COND_SLOT` 保留、等於第一個);證據頁的範本與預填指令都從這裡取字面。`_set_conditions_locked` 的第一道檢查改成「值裡有任一個」,訊息點名是哪一個。其他檢查與順序不動。既有 `_DRIFT_PLACEHOLDER_RE`(擋 drift fix 的 `--reason`)照舊、用途不同,不合併。

### 3. c1 與 settle 的訊息

- guard settle 既有的單一出口 `_guard_settle_missing_say` 就是組字函式;`_drift_fix_c1` 改成也呼叫它(不另寫一支)。字樣改成「找不到{名稱}——可能已經是轉正後的說法(不用改),或被手改過(看一下)」,{名稱}直接用既有 `_GUARD_PROSE_NAMES` 的值(它本身已經含「預告句」等字,不再疊)。不改判定、不改回傳值、不改名稱表(settle 測試 ⑥ 斷言它)。

### 4. c3 的理由

- 接線:`_DRIFT_FIX_ALLOWED["c3"]` 加 `"reason"`;argparse `--reason` 的說明改成「c2、c3」;`_drift_fix_c3_args` 裡呼叫既有 `_drift_placeholder_err`(長度與單行由 `_drift_fix_args_err` 既有的 `_drift_fix_reason_ok` 管)。理由先去頭尾空白。
- 補的那一行三種寫法(有 `--by` 且是 pass:「由 `[[X]]` 解決」;有 `--by` 其他狀態:「參考 `[[X]]`」;沒 `--by`)都一樣:有給理由就在最後接「;理由:<理由>」,沒給照舊。理由裡的 `[[連結]]` 不驗存在(同 c2)。

### 5. 刪除守衛跳過工具自裝檔

- `_delguard_parse_diff` 加 `vendored_skip` 參數(預設空集合;函式裡已經有區域變數叫 `skip`,不能同名),抽 `-` 行名稱與收 `+` 行回收表兩遍都跳過 `skip` 裡的路徑;跟既有 `_DELGUARD_*` 排除清單分開,不併進去(那份有 `t_precommit_whitelist_drift_guard` 釘著)。
- `cmd_delguard_check`:不是工具鏈本身(`_is_toolchain_repo` 為假)時,`vendored_skip = _VENDORED_ALL`;是工具鏈本身時為空(那些檔是它自己的程式)。純路徑判斷,不讀安裝清單、不跑 git,沒有額外時間。
- `_delguard_parse_diff` 回傳多一個鍵 `vendored_skipped`(這次 diff 碰到並跳過的工具檔路徑),`cmd_delguard_check` 把它傳給既有的 `_delguard_log_result`/`_delguard_log_degraded`,在 `note` 裡加 `vendored-skip=<支數> files=<最多 20 支,逗號分隔>`(治理事件本身已帶提交編號);沒碰到就不加。

### 6. 文件與測試同步

- 既有測試 `t_drift_fix_c4_evidence_then_replace` 斷言自動填卷證的舊範本,改成斷言 `<卷證>` 與兩份清單;它同時釘著「set 擋 `<整項新內容>`」(lumos-cli-write 那條 WHY 綁它),那一段保留。
- 文件:[[Systems/存量漂移守衛]](c4 說明與 WHY 行「由人給要換的片段」改成現況、前一份計劃 RETIRE-IF ③ 被取代)、[[Systems/lumos-cli-write]](set 多擋兩個佔位字)、[[Systems/guard-kill]](settle 訊息)、[[Systems/delguard]](工具檔跳過與 note 欄位)、lumos-project-notes 的 commands/03(`lumos set` 那列)、04(c3 參數列加 `--reason`、c4 那列)、08(刪除守衛那列)。`_drift_fix_hint` 的 c3 提示加 `[--reason "…"]`。
- skills 文件跟 repo 即時同步、消費專案的工具要 `lumos update` 才換:文件寫的新參數(`--reason`)在舊版工具上會被拒;commands/04 那列註明「要新版工具」。

## 實務隱患

- 已排除:不可逆:只改本機的工具輸出與檢查,不改筆記內容的寫法;還原提交後外面不用收拾
- 已排除:金流:這是本機命令列工具,不碰任何付款或帳務
- 已排除:對外送出:不寄信、不打外部服務
- 守衛面(碰到):刪除守衛(只提醒不擋)在消費專案少抽工具自裝檔,跳過數記進治理事件;c1 與 settle 只改訊息字樣,不改判定。消費專案自己改工具檔又刪了名稱的情形會被放過,寫進誠實界線
- 資安(碰到):卷證目錄名印到終端前過 `_esc_clean`;範本句不再自動帶目錄名,少一條把外來字串帶進照貼內容的路
- 效能(碰到):卷證目錄多兩次有逾時的 git 查詢(找第一次提交、列那個提交的檔),只在 c4 證據頁跑;刪除守衛的跳過是純路徑比對,沒有額外成本
- 併發(不碰):不新增寫入路徑;set 的寫入與鎖照舊

## 誠實界線

- c4 修正走 `lumos set`,不進漂移修復帳;稽核靠 git 歷史(set 的修改在提交裡看得到)。rtb 回報的第二條(帳上少 c4)因此只以「改成靠 git 稽核」處理,不補帳。
- 卷證目錄的同提交找法,前提是「程式、筆記、卷證放同一個提交」;驗證紀錄另外提交時同提交清單是空的,只剩計劃名比對。範本不自動填,所以找錯不會直接被照貼寫進筆記,但人仍可能從清單挑錯。
- c1 與 settle 的訊息不再區分「已轉正」與「被手改」,由人自己看;rtb 回報的第三條以「措辭不再像出錯」處理。
- 刪除守衛在消費專案一律不看工具自裝檔(只比精確檔名,跟既有四處「指紋跟安裝清單一致才跳過」的口徑不同——設計審 r3 架構對齊席 F1,編排者放行,理由:刪除守衛只提醒不擋,指紋判定在 r2 被抓到沒有時間上限、位置點錯,縮小成純路徑是刻意的):消費專案自己改工具檔、刪掉名稱、而圖譜提到那些名稱時,不會提醒。

- c4 走 `lumos set` 後同一篇驗證紀錄若還有 c3,set 的修改沒提交前 drift fix 的乾淨檢查會擋;證據頁最後一行提醒先提交。
