## 做法

### 1. c4 卷證目錄

- 取驗證紀錄第一次被提交的提交(`_plan_first_commit`;shallow 由既有 `_git_is_shallow` 先擋)。列那個提交加進來或改名進來的檔:`_nodehome_git(root, "show", "-z", "--name-only", "--diff-filter=AR", "--format=", <提交>)`,`_nodehome_split_z` 拆;只收路徑至少四段、形如 `governance/review-reports/<目錄>/<檔>` 的第三段目錄名,目錄名去重,只留目前還存在於 `governance/review-reports/` 底下的(改名或刪掉的舊目錄不列)。這是「同提交」清單。查不到第一次提交(這篇還沒提交、shallow)或 git 失敗、逾時時,證據頁寫「同提交:查不到(git 失敗或沒有)」(「沒有」指查不到提交);git 成功但那個提交沒加卷證目錄時不印這句,清單裡就只剩計劃名比對到的。★印的一律是現在真的存在的那個目錄名(磁碟上的實際名字)★(代碼審第二輪改裁;r1 版印 git 裡的名字,macOS 上 git 存 NFC、磁碟是 NFD 時印出不存在的路徑、同一個目錄列兩行):git 裡的名字只拿比對鍵(NFC 再 casefold,`_drift_c4_dir_key`;代碼審第三輪外家否決、邊界席補上不分大小寫的檔案系統:磁碟名只差大小寫時原本對不上)去對應現存目錄;一個現存目錄一行,兩種來源都有就標「兩者」;比對鍵對到好幾個現存目錄(分正規化或分大小寫的檔案系統)才每個都列。目錄名裡的 Unicode 格式字元(方向控制、零寬)印成看得見的 `\uXXXX`(代碼審第二輪資安席,只在這一處,不改共用的 `_esc_clean`)。
- 「計劃名」清單照舊用 `_drift_c4_key` 比對。
- 證據頁全部列出、每個標來源(兩者、同提交、計劃名),不設上限。第一輪邊界席要的「超過 20 個只列前 20 個 + 列完整清單的指令」在代碼審第三輪撤回:三輪長出四個新缺陷(指令少列 git 會加引號的目錄名、沒照現存名稱與格式字元處理、「另有 N 個」跟指令數量說法打架、散檔那條測試測不到),長清單罕見,證據頁是人主動叫出來看的,多幾行不礙事。排序:兩者 → `code-` 開頭 → 其他,同級照字母;同提交清單超過 3 個時另起一行先印「可能含別的計劃的卷證(整批匯入或壓成一個的提交)」。每個目錄各印一行、各自過 `_esc_clean`(不把整張清單接成一行再截斷;無法編碼成 UTF-8 的字元先換掉,免得印的時候當掉)。
- 範本句改成「提交 <前 12 碼>;代碼審見 <卷證>」,查不到提交時提交那段寫成字面 `<sha>`;卷證一律放字面 `<卷證>`——兩個字面都取自第 2 節同一份常數,由人從清單挑(整句貼進 `lumos set` 會被第 2 節擋下,逼人換成真的目錄與提交)。
- 預填的 `lumos set` 指令照舊(要改的那項放 `<整項新內容>`),這次不改它的展開與長度處理。證據頁最後加一行:「用 lumos set 改完先提交,再對同一篇跑別的 drift fix(不然乾淨檢查會擋;別照它的提示 git checkout,那會洗掉 set 的修改)」。

### 2. `lumos set` 多擋兩個佔位字

- 在 `_SET_COND_SLOT` 旁邊加模組常數 `_SET_COND_SLOTS = ("<整項新內容>", "<卷證>", "<sha>")`(`_SET_COND_SLOT` 保留、等於第一個);證據頁的範本與預填指令都從這裡取字面。`_set_conditions_locked` 的第一道檢查改成「值裡有任一個」,訊息點名是哪一個。緊接著再擋打錯的變體(代碼審 r1 邊界席):只擋兩邊都有角括號、括號裡只有佔位字本身的——全形角括號、括號內多空白、sha 大小寫。少一邊角括號的第一版也擋,代碼審第二輪四席重現「若卷證>20個就重驗」「輸出 git-sha> 時重驗」被誤擋,拿掉;`<卷證 目錄>`、`<sha 1>`、`<git-sha>`、`<SHA-1>`、`<sha256>` 照收。其他檢查與順序不動。既有 `_DRIFT_PLACEHOLDER_RE`(擋 drift fix 的 `--reason`)照舊、用途不同,不合併。

### 3. c1 與 settle 的訊息

- guard settle 既有的單一出口 `_guard_settle_missing_say` 就是組字函式;`_drift_fix_c1` 改成也呼叫它(不另寫一支)。字樣改成「找不到{名稱}——可能已經是轉正後的說法(不用改),或被手改過(看一下)」,{名稱}直接用既有 `_GUARD_PROSE_NAMES` 的值(它本身已經含「預告句」等字,不再疊)。不改判定、不改回傳值、不改名稱表(settle 測試 ⑥ 斷言它)。

### 4. c3 的理由

- 接線:`_DRIFT_FIX_ALLOWED["c3"]` 加 `"reason"`;argparse `--reason` 的說明改成「c2、c3」;`_drift_fix_c3_args` 裡呼叫既有 `_drift_placeholder_err`(長度與單行由 `_drift_fix_args_err` 既有的 `_drift_fix_reason_ok` 管)。理由先去頭尾空白。
- 補的那一行三種寫法(有 `--by` 且是 pass:「由 `[[X]]` 解決」;有 `--by` 其他狀態:「參考 `[[X]]`」;沒 `--by`)都一樣:有給理由就在最後接「;理由:<理由>」,沒給照舊。理由裡的 `[[連結]]` 不驗存在(同 c2)。

### 5. 刪除守衛跳過工具自裝檔(不做,代碼審第三輪撤掉)

- 原本要讓刪除守衛在消費專案不從工具自裝檔抽被刪名稱。三輪代碼審每輪都在「這支檔算不算工具原樣」上錯一種位置:只比檔名,漏看專案改過的同名檔(r1);比指紋但讀工作目錄,跟守衛看的暫存區對不上(r2);只看改之後,漏掉 `lumos update` 之前就被專案改過的檔(r2);改成改前改後兩態後,新增行與刪除行的跳過不對稱,舊版安裝第一次寫安裝清單、或專案改過再 update 時,把只改了一半、名稱還在的函式也當成刪掉(實測一次抽出 379 個名稱、逾時降級),而且兩態讀 git 不受守衛 deadline 約束(r3)。同一類第三次,照第二輪定下的預先裁定整類拿掉。
- 程式回到 9cc20926 的樣子:不跳過任何檔、治理事件 note 沒有 `vendored-skip=`;為了新增告警閘拆的三支小函式一起回到原樣(改動最小:那一段跟基準一字不差)。
- 消費專案更新工具時的誤報照舊,改開 [[Issues/刪除守衛在消費專案把工具更新刪掉的名稱當成專案的]] 追蹤;那篇寫了四種錯位與一個可能的正確判法方向(只對「改之前與改之後都原封不動、而且名稱在改之後的工具檔裡確實不見」才跳)。

## 誠實界線
