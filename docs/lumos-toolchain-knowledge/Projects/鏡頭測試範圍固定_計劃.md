# 鏡頭測試範圍固定_計劃

白話:有兩支測試在驗「派工鏡頭的席位認領」,武裝時會拿真實 repo 的「主線到目前版本」當範圍去算一次鏡頭。主線推送時範圍是空的,很快;可是在合併請求裡,範圍就是那個合併請求的改動,改到的東西讓鏡頭算很久時,測試就卡過 180 秒的上限而紅。2026-10-06 合併請求 #14 只改了一篇計劃筆記,鏡頭就要算 3 分 14 秒,兩支都紅了兩次。這次改成跟 `t_lens_timeout_keeps_warming_cache` 一樣,挑主線上改動最小的那一個提交當範圍。

依據:Enzo 2026-10-06「先修」。

PRIOR-ART: 同專案 `t_lens_timeout_keeps_warming_cache` 2026-10-04 修過同一類(拿主線 tip 與 tip~1 當範圍,合併大 PR 後假紅),改成 `_lens_smallest_commit` 在主線最近 30 個非合併提交挑改動最小的 X、範圍 X~1..X;[[Systems/測試假綠形態]] 有那條 PITFALL。本案沿用同一支輔助函式。
RETIRE-IF: 派工鏡頭對任意範圍的成本都壓到幾秒以內(例如另案修好鏡頭本身的慢),「挑最小範圍」就不必要,可以改回簡單寫法。

## 範圍

- 做:兩支測試裡用到 `{ml}..HEAD` 的四處(兩次武裝、一句斷言、一次互斥檢查)改成 `{base}..{head}`(`head = _lens_smallest_commit(repo, ml)`、`base = head~1`;兩端都在主線上);斷言裡比對 `LUMOS-LENS range=` 那句跟著換。
- 做:新增一支守衛測試,掃測試檔裡呼叫 `dispatch-lens` 的地方,不准再出現對真實 repo 用 `..HEAD` 的範圍(同族以後不要再長出來)。
- 不做:派工鏡頭本身為什麼對那篇筆記算 3 分鐘(另開 Issue 追)。
- 不做:改其他測試的逾時上限。

## 做法

1. 兩支測試在取得 `ml` 後,用 `_lens_smallest_commit(repo, ml)` 取 head、`git rev-parse head~1` 取 base;取不到就照既有寫法丟 `_SrcOnly`(不在來源 repo 或歷史太短)。
2. 武裝與互斥檢查改用 `rng = f"{base}..{head}"`;`s1-arm` 那句斷言比對 `LUMOS-LENS range={rng} 第 1/2 席`。
3. 新增 `t_lens_tests_avoid_branch_dependent_range`:讀本檔原始碼,找出含 `"dispatch-lens"` 字樣的測試函式,這些函式裡不得出現 `..HEAD` 後面緊接引號(雙引號或單引號)這種接在真實 repo 主線之後的範圍字面(臨時造的 repo 不在此限:以函式裡有沒有 `Path(GRAPHCTL).resolve().parent.parent` 判斷是不是用真實 repo)。
4. 另開 [[Issues/派工鏡頭對單篇計劃筆記算三分鐘]] 記下鏡頭慢的現象與重現指令。
5. 寫回 [[Systems/測試假綠形態]]:那條 PITFALL 的同族補上這兩支。

## 實務隱患

- **最小提交剛好算很久**:挑的是改動行數最少的非合併提交,行數少不保證鏡頭快;既有那支用了兩天沒出事,這兩支沿用同一個判準。
- 已排除:金流:只改測試檔
- 已排除:對外送出:不連網,也不寄送任何東西給外部
- 已排除:不可逆:只改測試與筆記,還原提交即可
- 已排除:守衛面:不改任何閘或工具行為,只改兩支測試挑範圍的方式並加一支防同族的測試

## 驗收條款

- [S1] 當目前分支比主線多一個會讓鏡頭算很久的提交時,`t_codex_s1_lens_arm_claim` 與 `t_codex_s1_r1_fixes` 應 在 180 秒內跑完而且綠 [manual:在 ci-speedup-notes 分支(PR #14,改 CI加速_計劃 那個提交)上用修好的測試檔跑這兩支,記耗時]
- [S2] 當有測試函式對真實 repo 呼叫 `dispatch-lens` 又用 `..HEAD` 範圍時,守衛測試 應 列出那支函式並紅;修好的本檔 應 綠 [test:t_lens_tests_avoid_branch_dependent_range]

## 回退

還原本案的提交即可:只改測試檔與筆記,工具行為不變;退回後那兩支測試回到依賴當下分支內容的舊寫法,遇到讓鏡頭算很久的改動會再逾時。

## 天花板

1. 守衛測試只認 `..HEAD` 後面緊接引號的字面;換成變數拼出來的範圍、`..HEAD` 後面接別的字(例 `..HEAD~0`)、或把鏡頭呼叫放進非 `t_` 開頭的輔助函式再由測試傳範圍,都抓不到。
2. 守衛另有一條前置斷言:一定要掃到那兩支認領測試,篩選字串改名時才不會一支都篩不到而恆綠。
