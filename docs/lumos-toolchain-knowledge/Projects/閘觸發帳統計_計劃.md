# 閘觸發帳統計_計劃

> 白話:治理帳寫了兩萬多筆,從來沒人回頭算過「哪道閘在做事、哪道從沒響過、哪道每次都響」。本案給既有的 `lumos gov` 加一段唯讀統計,把**每道閘的筆數/節點數/commit 數/起訖日**列出來,外加一份「本帳裡完全沒出現過的閘」清單。★只陳述數字,不貼標籤、不下判斷★(2026-08-20 裁定)。**恆觀測、不進閘、不改任何判定。** 它的用途是給「紀律要不要退場」這個至今無尺可量的問題,第一次提供資料。

## 新機制準入三問(Growth test)

1. **真事故?** ★半過,弱點明講★。可數事實有(上表);但**查無一筆「因為警告淹沒而漏掉某事」的已記錄事故**。★**r2 後此理由已被打薄,如實記錄**★:s2 席指出「先造尺」的承諾在最高風險處兌現不了——硬閘(anchor verify/測試閘)這把尺**根本看不到**,而看得到的最大宗來源(`check-s`)量的是**可被一次批次補戳製造出來的自報欄位**。故本案能買到的東西比原本宣稱的小:它能看見的是「軟提醒有沒有人理」與「有記帳的閘有沒有響過」,買不到「硬閘該不該退場」。支持仍立案的(已縮小的)理由:本案不是新機制,是對既有機制的**讀側量測**——而「紀律要不要退場」這題的既有處境是 [[Issues/散文紀律沒有退場機制]] 記載的「被前後量過效果的紀律=0 條」,★沒有尺,就永遠湊不出事故帳★。先造尺是解開死結的唯一入口。若裁定者認為此理由不足以豁免第一問,本案應同 [[Projects/宣稱級時間戳_計劃]] 落為 gap 佔位。
2. **風格偏好?** 否。「宣稱有守衛、實際從沒響過」是正確性問題,不是美感。(★注意:砍成純數字後本案只陳述「沒出現」,不主張「沒作用」——後者要人另外查證★)
3. **既有小修蓋得住?** 蓋得住,本案即是小修:`lumos gov` 本來就在讀這本帳,加一段統計輸出;零新子命令、零新帳檔、零新紀律。

## 設計草案(待 design-loop)

### S1 `lumos gov --stats`

**母體 = `lumos gov` 既有讀入的帳**(bypass/rot-queue/governance/canary/kill/signoff/ci)。★「七本」不是固定常數★:第 7 源 ci 帳是條件載入(`scripts/lumos:2941-2947`,專案未宣告 ci 區塊就完全不 load),故輸出首行印**本次實際載入哪幾源**,不寫死數字。

#### ★三層數字,不可互相冒充★(r1 三席一致抓到)

`cmd_gov` 的管線有三層,每層數字都不同:

| 層 | 是什麼 | 實測(全史) |
|---|---|---|
| 原始行 | 帳檔實際寫入的行數 | 20,139 |
| **去重列** | 以 (commit, 節點集, gate, kind, token) 去重後(`scripts/lumos:2950-2957`) | 8,156(governance 一本)/ **8,700**(多源合流) |
| 呈現行 | 預設模式再過一層**呈現去噪**(同日同 gate/kind/node 折 ×N、>6 節點群收單行,`scripts/lumos:2961-3000`) | **901** |

**本統計一律以「去重列」計數,並併印原始行數。**
★硬規格:輸出必須明寫「本統計不等於 `gov` 預設畫面的行數——預設畫面另有一層呈現折疊」★。原草案寫「去重後的列即『人會看到幾筆』」是**錯的**(去重 8,700 vs 預設畫面 901,差 9.7 倍),已刪。★**8,825/1,026 那組舊數字本身也是錯的**(r3 s1 席抓到,編排者實跑證實):那是 `wc -l` 量的**輸出行數**,含表頭與裝飾約 125 行;事件筆數要濾出以日期起頭的列才算得對。量錯的方法值得記——「印幾行」與「有幾筆」在這支指令上差兩位數。★

#### ★這把尺量得到什麼、量不到什麼(r2 s2 席,立案前必讀)★

**量不到(範圍硬限制,不是實作缺陷)**:

- **硬擋事件完全不寫帳**。`anchor verify` 是 pre-push 硬閘、擋下 push 時**不寫任何帳**(`cmd_anchor_verify` 全函式無帳本寫入,`scripts/lumos:9993-10029`);帳上 `anchor-approve` 那 139 筆是「人核准了錨點變更」,不是「閘擋過誰」。pre-push 的測試閘同理。★所以本帳的性質是「軟提醒 + 人為留痕」,不是「閘的攔截史」;最該被評估的硬閘,這把尺看不到,連一列零都不會出現★。
- 只有走上述 15 個 gate 名之一的事件會被看到;不記帳的守衛(不論多重要)在本統計中不存在。

**零觸發有三種,本統計分不出來**:①跑了沒事 ②接了帳但從沒被觸發 ③**守的功能從來沒被用過**。`check-j` 屬第三種——其整段邏輯掛在 `if _regen_rels:` 之下(`scripts/lumos:1293`),而全庫帶 `regen:` 欄位的節點數實測為 **0**,迴圈一次都沒進去過。★輸出必須把這三種一律標成「未觸發(原因不明)」,不得暗示等價★。

**為什麼收斂指標被裁掉(2026-08-20)**:`check-s` 的判準就是「節點 frontmatter 有沒有一個 `self_audit` 日期且不早於 `updated`」(`scripts/lumos:814-825`)——★量的是自己填的欄位,不是外部事實★。實測全庫有 **19 個節點掛著同一個 `self_audit: sonnet/2026-07-24` 戳**,與「一次批次補戳」相容,與「19 次獨立自審」同樣相容,本統計分不出來。且 `check-s` 本身通過 `hard=false, kind=warned` 這道原本用來擋 `anchor-approve` 偽陽性的濾網——★該濾網對本統計最大宗的來源不生效★。**結論:這個指標會產出一個看起來客觀、實際上可被一次批次補戳製造的數字,故整個拿掉。**

#### 讀到的欄位(本文用到的帳本欄位,先定義)

`cmd_gov` 把各帳檔映射成統一列,本案只用其中五個欄位:
- `gate`:哪道閘(如 `check-s`)。`kind`:該次結果,值域**由各來源自定、非封閉枚舉**;`governance-log` 一本實見 `warned`/`approved`/`passed`/`skipped`(★`blocked` 在程式碼中有定義但本帳零筆——r2 s1 席指出原文把它列成「實見」與基線表矛盾★),其餘六源另有各自值域。
- `hard`:布林,`true`=硬擋、`false`=軟提醒(advisory)。`nodes`:涉及節點名清單,**可為空陣列**。
- `token`:去重鑑別子。★填的來源不只 canary★——`signoff`(`scripts/lumos:2922`)、`kill`(`2927`)、`ci`(`2946`)也填(r3 s1 席:原文照抄了一句過時的程式碼註解);本案除參與去重外不使用它。

#### 逐 gate 輸出(★2026-08-20 Enzo 裁:砍成純數字報表★)

**六欄,全部是可重算的硬事實**:去重後筆數、原始行數、不同 nodes 值數、不同 commit 數、首見日、末見日。

- **首見日/末見日**:只取 `ts` 解析得出日期的列;`ts` 缺失或空白的列**仍計入筆數,但不參與日期計算**;該 gate 全部列皆無可用 `ts` → 兩欄印 `n/a`(r3 s3 席:原文未定義,真實資料目前未觸發,屬潛伏)。

- **不同 commit 數**:來源 mapper 硬寫 `commit: ""` 者(canary,`scripts/lumos:2931`)→ 此欄印 `n/a(該來源不記 commit)`,★不得印成 1★。
- **不同 nodes 值數**:★判準=**逐資料實算**,不看程式碼哪裡硬寫★——該 gate 在窗口內所有列的 `nodes` 聯集為空 → 印 `n/a(該來源不記節點)`,否則印聯集大小。
  - 原草案用「mapper 硬寫 `nodes: []`」當判準是錯的(r3 s3 席):`code-loop` 的空 nodes 是**寫入端**寫的(`scripts/lumos:13956`),讀取端走 governance-log 的動態 mapper——照原判準它不算「mapper 硬寫」,會印出字面 `0` 而非 `n/a`。改成逐資料判即一併涵蓋。
  - ★**此欄語意不同質,必須標**★(r3 s1 席,編排者實查證實):`anchor-approve` 的 nodes 存的是**錨點檔案路徑**(`scripts/hooks/pre-commit`、`scripts/test_lumos.py` 等),不是圖譜節點名。故欄名為「不同 nodes 值數」,並對非圖譜語意的 gate 於同列標註「(此來源記的是檔案路徑)」。★不得讓讀者以為各 gate 這欄可互相比較★。
  - `anchor-approve` 另有 5 列 nodes 為空——空是**每列**的性質不是每 gate 的性質,逐資料判天然涵蓋。

#### ★刪掉的東西(2026-08-20 裁定,不是漏寫)★

原草案有的**三桶分類(零觸發/不收斂/正常)與收斂指標,全部拿掉**。理由不是做不出來,是它們買到的東西撐不住 r2 查到的事實:

- **收斂指標**量的是 `check-s` 的 `self_audit` 欄位——自己填的,且實測 19 個節點掛同一個 `sonnet/2026-07-24` 戳,「一次批次補戳」與「19 次獨立自審」在資料上無法分辨。指標存在只會製造一個看起來客觀的假訊號。
- **不收斂桶**需要一個沒有根據的門檻(原草案 20),且已知對人為留痕(`anchor-approve`)偽陽性。
- **零觸發桶**降級成「未出現清單」——同一份資料,但不再貼「這道閘可能沒用」的標籤。

★換來的是:本功能不再有任何「無機械 oracle 的判準」;每一個印出來的數字都可以拿原始帳重算驗證。★

#### 與既有旗標的互動(全部明講,不留未定義)
