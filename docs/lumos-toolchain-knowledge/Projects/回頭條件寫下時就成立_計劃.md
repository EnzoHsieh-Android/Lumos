# 回頭條件寫下時就成立_計劃

白話:一條條件式回頭條件如果寫下的當下條件就已經成立,它從來沒提醒過任何人。推送時新寫的已經會被擋(既有),但那道檢查上線以前寫的舊行,`lumos drift scan` 只說「條件已經成立」,有人表態照留之後就看不出它是「生來就成立」。這份要讓 scan 對現在成立的條件標出「寫下時就已成立」,表態過的也照標。

狀態:待重新設計。原本是 [[Projects/回頭條件消失式與生來成立_計劃]] 的第二半,設計審三輪(卷證 `governance/review-reports/回頭條件消失式與生來成立/`)每輪都在「往回查歷史」挖出結構問題,2026-10-03 Enzo 裁縮案拆出,這裡從頭設計、重新跑設計審。

依據:
- 消費專案清漂移回傳(2026-10-02,第 11 項,去識別):drift probe 只說「現在成立」,而且表態後就靜音,看不出它生來就成立、從沒提醒過任何人(四條);建議提交當下就檢查新寫的條件——推送時已經擋新寫的已成立條件(`t_drift_when_probes_evaluate_and_trigger` ⑨),所以剩下的是存量。

PRIOR-ART: 待重新設計時先看既有的單篇逐版往回讀 `_note_status_seq`(帶 `--follow` 跟著改名、批次讀版本、檢查 UTF-8、`deadline` 預算;設計審 r3 架構對齊席點名),不要另寫走訪器;讀某提交的圖譜沿用 `drift scan --at` 的 `_drift_tree_env` 與 `_drift_vault_rel`。
RETIRE-IF: 設計完成前不適用;重新設計時照「標記在工具鏈與消費專案各跑一次都是 0 筆、兩個月沒有新的舊行被標就拿掉」寫進來。
REVISIT:2026-11-03 決定重新設計的排程(或撤案);撤案就把這篇設成 superseded 並在路線圖寫原因

## 三輪設計審留下的坑(重新設計時逐條回答)

- 「寫下時」怎麼認:用 `git log -S` 找第一次出現的文字會找錯提交(改字、搬位置、刪了又寫、舊的較長行包含它);要照系統認「同一條」的規矩比條件標記,找「這一世」的開頭。
- 歷史順序:預設 `git log -- 路徑` 遇到合併提交會讓兩條分支的版本交錯,不是祖先鏈;改名、拆篇也會讓「寫下時」說得比查到的強。
- 讀版本:`_nodehome_cat_blobs_capped` 把「那一版沒有這篇」「超過上限」「讀不出」都回 None;`_nodehome_list` 回的路徑都已 NFC,沒有「原樣路徑」那份,NFD 檔名的筆記會查歪。
- 同一篇裡條件標記一樣的兩行、歷史裡複製出來的第二行,會追到錯的來源。
- 淺層 clone 看不到歷史;partial clone 讀舊版本會去網路抓。
- 資源:每個不同提交建樹加讀程式語料實測約 2 秒(不帶路徑的 symbol/test 要讀全語料),共用的列樹快取上限 8。
- 呈現:已表態的發現在現行文字輸出結構裡不印補充行(`_drift_prev_ack_line` 只印在未表態的列底下);發現的字典沒有帶條件解析結果;`--json` 的新欄位名不要跟頂層 `unknown` 撞。
