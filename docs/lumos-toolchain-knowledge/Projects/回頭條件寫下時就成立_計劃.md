# 回頭條件寫下時就成立_計劃

白話:一條條件式回頭條件(或 RULE 的機器式撤除條件)如果寫下的當下條件就已經成立,它從寫下那天起就沒在等任何事。推送時新寫的已經會被擋(既有),但那道檢查上線以前寫的舊行、或繞過推送檢查寫進來的,`lumos drift scan` 只說「條件已經成立」,有人表態照留之後連這句都只剩「(已表態)」,看不出它是「生來就成立」。這份讓 scan 對現在成立的條件往回找寫下那一版、在那一版判同一組條件,成立就標「寫下時就已成立」,表態過的也照標。

狀態:已上線(2026-10-03,代碼審三輪收斂)。以下是設計當時的紀錄。原本是 [[Projects/回頭條件消失式與生來成立_計劃]] 的第二半,設計審三輪(卷證 `governance/review-reports/回頭條件消失式與生來成立/`)每輪都在「往回查歷史」挖出結構問題,2026-10-03 Enzo 裁縮案拆出。這一版的做法:**每一步只要有一點不確定就判不了、不標**——標錯(把沒問題的條件說成生來就成立)比漏標糟,漏標的頂多是維持現狀。

依據:
- 消費專案清漂移回傳(2026-10-02,第 11 項,去識別):drift probe 只說「現在成立」,而且表態後就靜音,看不出它生來就成立(四條);建議提交當下就檢查新寫的條件——推送時已經擋新寫的已成立條件(`t_drift_when_probes_evaluate_and_trigger` ⑨),所以剩下的是存量。

PRIOR-ART: 最小解在工具這一層:「這一行是哪一版寫的」世界上的標準答案是 `git blame`,但 blame 以文字行為單位——改了待辦文字、搬了位置就算新寫,跟本系統「同一條」的規矩(條件組一模一樣,`_drift_probe_old`)對不上,所以不用 blame,改沿用既有的單篇逐版往回讀 `_note_status_seq`(`git log --follow` 取每一版的路徑、批次讀版本、預算)——把它取版本清單那段抽成共用的一支,兩邊共用,不另寫走訪器;在某一版判條件沿用 `drift scan --at` 的 `_drift_tree_env`、`_drift_vault_rel`、`_drift_probe_tree`、`_drift_probe_line`。
RETIRE-IF: 在工具鏈與消費專案各跑一次 `drift scan --json`,`born.state` 是 true 的都是 0 筆,而且兩個月沒有新的舊行被標,就把這個標記拿掉(推送檢查已經擋新寫的,存量清完就沒有用處)。
REVISIT:2026-12-03 對工具鏈與消費專案各跑一次 `lumos drift scan --json` 數 `born.state` 為 true 的筆數,照 RETIRE-IF 判

## 範圍

- **做**:`drift scan`(文字與 `--json`、工作目錄與 `--at`)對**現在成立**的回頭條件與 RULE 撤除條件,標出寫下時成不成立。
- **不做**:推送判定(新寫的已經擋)、doctor、表態規矩(標記不讓表態失效、不擋)、寫治理帳(讀指令不寫帳,既有決定 Systems/lumos-cli-read d1)。
- **不做**:現在不成立的條件不往回查(還在等的條件,寫下時成不成立都還有用)。

## 做法

1. **「同一條」照推送判定的規矩**:那篇筆記裡解析出的條件組一模一樣(`_drift_probe_old` 比的那個)。只改待辦文字、搬位置、行號變了仍是同一條;改了條件就是新的一條,從改的那一版算。
2. **「寫下那一版」怎麼找**:沿那篇筆記在**主線(第一父鏈)**上的歷史由新到舊一版一版看。那一版這篇裡**恰好一行**是這組條件就往前;碰到沒有(含那一版沒有這篇)就停,停之前最後看到的那一版就是這一世的開頭。
   - 版本清單:`git log --first-parent --follow --format=%H --name-only -z <起點> -- <路徑>`(2026-10-03 實測 git 2.39:兩個選項可以並用,側分支的提交不出現、合併提交代表那一版,改名跟得到)。起點是 `--at` 給的提交;工作目錄模式用 `HEAD`。
   - 側分支上寫、合併進主線的行,以合併那一版算——訊息寫「進主線那一版」,不寫「寫下那一刻」。
   - 從別篇搬過來的(拆篇、合篇),以搬進這篇那一版算——訊息寫「第一次出現在這篇」。
   - **停在複製**(實作時實測):`--follow` 也會跟「複製」,而且關不掉(`-M`、`--no-find-copies`、`diff.renames=true` 都一樣)——新開一篇跟舊篇很像的筆記,會被認成從舊篇複製來、一路追進舊篇的歷史。版本清單改帶變動種類(`--name-status`),碰到複製(C)就留下那一版、再往前的丟掉;改名(R)照跟。
   - **同一版裡這組條件不只一行 → 判不了**(分不出走的是哪一行的歷史);走過的每一版都檢查,**含終點那份文字**(工作目錄或 `--at` 那一版;代碼審 r1:工作目錄多寫一行同條件、還沒提交,原本兩行都追到舊提交)。
   - 讀版本用既有批次讀 `_nodehome_cat_blobs`,**一次 32 版、碰到邊界就停**,不一次讀全部歷史。路徑用 git log 吐出的原樣路徑(不是 NFC 過的)。讀回 None(那一版沒有這支檔)算「沒有」;那一版不是 UTF-8 → 判不了;批次讀失敗 → 判不了。
   - 共用:把 `_note_status_seq` 裡「`git log --follow` 取 (提交, 那時的路徑)」那段抽成 `_note_versions(repo_root, rng, path, first_parent=False)`,`_note_status_seq` 照原參數呼叫。停在複製寫在共用那支裡,所以狀態序列也一起修好:原本新開一篇跟舊計劃很像的計劃,狀態序列會混進舊計劃的 doing→done(同一類問題一次修,不只修被點名的這條路)。
3. **在寫下那一版判同一組條件**:那一版的圖譜位置 `_drift_vault_rel(root, X) or vault_rel`,建那一版的 `_drift_tree_env` 與 `_drift_probe_tree`,預讀後用 `_drift_probe_line`——跟 `drift scan --at X` 同一套。True → 寫下時就已成立;False → 不標;None → 判不了(原因沿用 `_drift_row_unread` 點名)。
4. **工作目錄模式**:現在這一行的條件組不在 `HEAD` 版的這篇裡(還沒提交;或這篇改了名還沒提交、`HEAD` 找不到這個路徑)→ 判不了「還沒提交,推送時會判」。
5. **整體前提,一次判、全部同一個原因**:不是 git 專案、淺層 clone(`git rev-parse --is-shallow-repository`,同筆記形狀擋的判法)、partial clone(`git config extensions.partialClone` 有值——讀舊版本會去網路抓)、起點沒有提交。
6. **預算**:用 scan 剩下的總預算(同一個期限);另外每次 scan 最多在 **6 個**不同的提交建樹判條件(列樹快取 `_DRIFT_LS_CACHE` 上限 8,留兩格給終點;設計審 r3 實測每個提交約 2 秒),超過的判不了「超過上限」。同一篇的多條共用一次版本清單與版本讀取。
7. **呈現**:
   - 文字:每條寫下時就已成立的發現(不管有沒有表態)底下多一行:「寫下時就已成立:這組條件從 <短編號>(<日期>)起連續出現在這篇,那一版條件就已經成立——這段期間沒在等任何事;改成真的會發生的條件,或刪掉」。只講查到的(從那一版起連續出現),不講「第一次出現」(代碼審 r1:中間改壞再修好的會說得太強)。已表態的列原本只印一行,這行照印。
   - 判不了的不逐條印:發現清單後面印一行彙總「另有 N 條查不出寫下時成不成立(原因:…)」,原因去重後列前三個。
   - `--json`:回頭條件(probe)與撤除條件(retire)的發現多一欄 `born`:`{"state": "true"|"false"|"unknown", "commit": 完整編號或 null, "date": "YYYY-MM-DD" 或 null, "why": 判不了的原因或 null}`;其他種類不加。欄名不叫 `unknown`(頂層已經有)。
   - 發現的字典不帶條件解析結果:這一步用(路徑, 行號)對回那篇筆記,用同一支抽取(`_probe_lines` / `_retire_lines`)重抽一次拿條件組,不改發現字典的形狀。
   - 日期用寫下那一版的提交日期(`git show -s --format=%cs`),只對判成成立的那幾個提交問。

## 實務隱患

- **效能**:每條現在成立的條件多一次 `git log` 與分段的版本讀取;每個不同的寫下版本多建一次樹與圖譜(約 2 秒),上限 6 個、共用 scan 的總預算。只對現在成立的條件做,還在等的不做。
- **記憶體**:版本一次讀 32 版;一篇筆記 300 版、每版 100KB 時最多同時留 3.2MB。
- **併發**:只讀 git 物件與工作目錄;不寫帳、不寫檔。
- **網路**:partial clone 讀舊版本會去網路抓——整體判不了、不讀(做法 5)。
- **回滾**:還原本案的提交,scan 輸出少一行與 `born` 欄;沒有資料要收。
- **相容**:`--json` 只多一欄;既有欄位不變。`_note_status_seq` 改呼叫共用的版本清單:只有「這篇是從別篇複製來的」這種情況行為改變(不再混進來源那篇的狀態),其他照舊(既有筆記內容審測試守)。
- **跨環境**:CI 常見淺層 clone → 整體判不了,文字輸出彙總一行講原因;本機完整 clone 才判得出。
- 已排除:金流:只讀筆記與 git 物件
- 已排除:對外送出:不呼叫網路(partial clone 刻意不讀)
- 已排除:不可逆:只多印資訊,不擋、不寫
- 已排除:守衛面:不碰推送判定與任何閘,scan 本來就不擋

## 天花板

1. 只看主線(第一父鏈):側分支上寫下時不成立、合併前才成立的,會被說成「進主線那一版就已成立」——訊息只講進主線那一版,不講寫下那一刻。
2. 「同一條」只認條件組:兩篇各寫一條一樣的條件互不影響;同一篇兩行一樣的整條判不了。
3. 拆篇、合篇只追到搬進這篇那一版,不追到別篇的源頭。
4. 寫下那一版條件判不了(那一版的程式檔讀不出、讀不準)就判不了,不往更新的版本找替代。
5. 「寫下時就已成立」不等於「從沒提醒過任何人」:條件中間不成立過又成立的,那次推送其實提醒過;訊息只講寫下那一版的事實。
6. NFD 檔名的筆記:`git log` 用 NFC 路徑查不到歷史時判不了(不另做路徑對回)。
7. 中間某一版那一行改壞(解析不到、條件被拿掉)再修好:這一世從修好那一版算——修好時條件已成立就會被標,即使最早寫下時不成立;訊息只講「從那一版起連續出現」(代碼審 r1 附理由接受:改壞的那幾版確實不是一條條件)。
8. partial clone 只看 `extensions.partialClone`,不看各 remote 的 `promisor` 設定(專案沒有既有判法可對;git 開 partial clone 時兩個都會寫)。

## 三輪設計審留下的坑(原拆案清單,逐條對應)

- 「寫下時」怎麼認:用 `git log -S` 找第一次出現的文字會找錯提交 → 不用文字,用條件組認同一條、找「這一世」的開頭(做法 1、2)。
- 歷史順序:合併提交讓兩條分支交錯 → 只看第一父鏈(做法 2);改名、拆篇讓「寫下時」說得太強 → 訊息改講「進主線那一版、第一次出現在這篇」(做法 2、天花板 1、3)。
- 讀版本:「那一版沒有這篇」「超過上限」「讀不出」都回 None → 用不帶上限的批次讀,None 只剩「那一版沒有這支檔」一種意思;不是 UTF-8 另判(做法 2)。路徑用 git log 的原樣路徑,不用 NFC 過的列樹結果(做法 2、天花板 6)。
- 同一篇條件一樣的兩行、歷史裡複製出來的第二行 → 走過的每一版都要恰好一行,否則判不了(做法 2)。
- 淺層 clone、partial clone → 整體判不了(做法 5)。
- 資源:每個不同提交約 2 秒、列樹快取上限 8 → 上限 6 個、共用總預算(做法 6)。
- 呈現:已表態的不印補充行 → 已表態照印(做法 7);發現字典沒有條件解析結果 → 對回重抽(做法 7);`--json` 欄名不撞 `unknown` → 叫 `born`(做法 7)。
