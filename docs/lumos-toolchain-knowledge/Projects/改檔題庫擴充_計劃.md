# 改檔題庫擴充_計劃

> 白話:檢索評測裡量「改檔前推筆記準不準」的那半份考卷(改檔題)太小,保留組只有 9 題算得出分數,消融實驗(拿掉一個機制看分數掉多少)量不出小差距。這份計劃把改檔題加到保留組至少 25 題有效題,並讓出題規則跟實際的改檔前掛鉤一致。搜尋題那半份不在這裡擴,理由見〈不做〉。

PRIOR-ART:題庫要多大用「題數設計」反推,不拍數字——Sakai 用過去評測的逐題分數變異,照配對 t 檢定的樣本數公式算要幾題(https://link.springer.com/article/10.1007/s10791-015-9273-z);Voorhees 與 Buckley 實證題數少時「換一組同樣多的題、結論就翻」的機率比預期高(https://dl.acm.org/doi/10.1145/564376.564432)。候選池補標沿用本 repo 既有的標註刷新流水線(`governance/eval/refresh_labels.py` 的 delta → material → merge → apply),出題沿用 `governance/eval/build_goldset.py` 的追加模式;借用,不自建。
RETIRE-IF:擴充後連續三次消融實驗,保留組的逐題差異標準差算出來的「量得出 5 個百分點」所需題數都已低於現有有效題數的一半 → 停止再加題;或掛鉤的觸發規則換掉、出題母體跟它不再一致 → 重新檢討第 1 條。

## 現況數字(2026-11-12 實測)

- 改檔題 23 題,其中保留組 12 題、調參組 11 題;用現在語料算,有分數的只有 17 題(保留 9、調參 8)。沒分數的是 `.gitignore`、壓縮過的第三方 js、評測紀錄檔這類候選池為空的廢題(8 月下旬加垃圾過濾以前出的),以及題級門檻擋掉的題。
- 逐題配對差異的標準差:推薦準確率(前 8 名有幾成相關)融合排序對只看關鍵字是 0.090、對只看連結結構是 0.075。照配對 t 檢定的樣本數公式(顯著水準 5% 雙尾、檢定力 80%,係數 2.8)換算:要量得出 5 個百分點差距約需 25 題有效題、3 個百分點約需 70 題。
- 現有「融合排序贏過只看關鍵字」那道週閘,兩邊實際只差 1.3 個百分點,遠低於現有題數量得出的範圍。
- 真正的程式檔約 130 支,近 1500 個提交改過其中約 103 支;近 400 個提交「改過的檔」有上千支,但幾乎全是審查報告與規則樣本檔。
- 同一支常改檔的不同改動,推出來的前 8 名(扣掉固定席)兩兩重疊率:主程式 0–0.1、測試總檔 0–0.12、推送前掛鉤 0–0.2。

## 條款

- [S1] 當追加改檔題時,出題腳本 應 只收改檔前掛鉤判成會觸發的檔(用掛鉤自己那支單檔判斷函式,審查報告、規則樣本、文件不出題)。[test:t_goldset_edit_cases_hook_eligible]
- [S2] 當追加時帶了每支檔題數上限,出題腳本 應 讓同一支檔最多出到上限題(題庫裡已有的算進名額,同檔的題要出自不同提交且改動片段不同)。[test:t_goldset_file_quota_cap]
- [S3] 當追加時沒帶上限,出題腳本 應 維持每支檔最多一題、既有題目與標註一字不動、空池題不進卷、不就地改輸入。[test:t_goldset_append] [keeps]
- [S4] 當新題標註放行後,編排者 應 重跑考卷並把保留組改檔題補到至少 25 題有效題(走既有標註刷新流水線:兩位評分員各自標、不一致的另派一位讀過再裁、使用者批次放行)。[manual:保留組改檔題的有效題數寫回本節點,不到 25 題就再追加一批]
- [S5] 當兩位評分員意見一致時,編排者 應 抽一成交給第三位重判,不一致超過一成就把這批一致的全部改成要人看。[manual:抽驗筆數、不一致筆數與處置寫回本節點]
- [S6] 當新題庫寫回後,編排者 應 用同一份程式在新舊題庫各跑一次考卷並都記進評測歷史,之後才拿新題庫當基準。[manual:新舊兩筆考卷的評測歷史時間與主要數字寫回本節點]

## 做法

1. 出題腳本:新增「要不要出題」判斷,載入掛鉤腳本、呼叫它的單檔判斷函式(帶 repo 根,讓無副檔名檔走直譯器宣告判定);追加模式抽題時先過這道,再過既有的垃圾過濾。
2. 追加模式加 `--per-file N`(預設 1)與 `--window N`(往回看幾個提交,預設 400):同一支檔依提交新到舊取,已在題庫的題數算進名額,同檔同提交或同改動片段的跳過。加題函式同樣收這個上限,預設 1 時行為不變。
3. 跑追加:`--per-file 3`,一批一批加,每批照標註刷新流水線補標。評分員的派工詞寫明:判讀只寫進卷證目錄、不寫進節點;讀到節點裡有別人對這些題的判讀要主動講。
4. 放行後跑考卷,依〈S6〉留新舊重疊點,有效題數不到 25 題就再加一批。
5. 結果寫回本節點與 [[Systems/retrieval-ranking]]。

## 不做

- 不擴主搜尋題庫:那套評測不接受多詞查詢(兩臂都把整串當片語),而本機對話紀錄裡實際下過的 20 種搜尋詞有 16 種是多詞,加單詞題量不到實際用法;多詞那套另開計劃(見 [[Projects/評測尺修復_計劃]] 的 d1)。
- 不刪既有的廢題:它們在評測時本來就被跳過,刪了會改既有題目,違反〈S3〉。
- 不改出題的改動片段取法(提交裡第一行新增、最長 100 字):新舊題取法不同等於同一份考卷兩種題型。
- 不改評測器的計分與週閘門檻。

## 回退

出題腳本的改動是兩個新選項加兩道過濾(掛鉤判斷、範例與測試資料資料夾)。`--per-file` 不帶只回到「每支檔一題」,出題母體仍是新的(掛鉤不觸發的檔不出題);要回到舊母體,得把掛鉤判斷與範例資料夾那道過濾一起拿掉。題庫檔是 git 追蹤的 JSON,新加的題與標註用 git 還原到加題前那一版就回來;評測歷史是追加寫入,多出的考卷紀錄留著無害。

## 實務隱患

- 已排除:金流:只動評測用的出題腳本與題庫檔,不碰任何收費流程
- 已排除:對外送出:只讀本機 git 與圖譜、寫本機題庫檔,不對外送任何東西
- 已排除:不可逆:題庫檔在 git 裡,加錯了還原那一版就回來
- 已排除:守衛面:出題腳本不擋推送也不改任何閘的判準;週閘讀題庫的方式不變
- 效能:每出一題要跑兩次影響查詢(每次約 7 秒),一批 20 題約 5 分鐘;追加時往回看的提交數可調
- 標註成本:每題候選池最多 12 篇,保留組要到 25 題有效題約需加 50 題、初標約 600 筆,兩位評分員各一份
- 天花板一:同一支檔的多題共用檔案背景與評分員,題目不完全獨立,實際有效樣本比題數少;上限 3 只是壓低,不是消除
- 天花板二:評分員是語言模型,讀得到節點正文裡別人寫的判讀;靠派工詞要求主動揭露加〈S5〉抽驗,擋不住刻意照抄
