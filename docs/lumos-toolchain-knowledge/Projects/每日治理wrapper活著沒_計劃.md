# 每日治理wrapper活著沒_計劃

> 白話:每天早上 9:30 有一支腳本自動跑五件事。**9/5 那次它跑到第二步就死了,第 3 到 5 步全沒跑,
> 而且整天沒人發現。** 原因不是它沒印錯誤——是**沒有任何東西在讀它印的東西**,而且它不管發生什麼都回 0。

診斷的可數事實在下面〈現況查證〉。相關的既有節點:
[[Systems/autonomous-iteration-loop]](同一支腳本、同一週的「監看者與被監看者同命」教訓)、
[[Issues/自足性審計提醒空轉四十六天]](「軟提醒沒人看」的前科)、
[[Systems/reversibility-governance-ledger]](這本帳的既有裁定)、
[[Verification/2026-09-05_wrapper邊跑邊改實驗]](9/5 那次事故本身)。

## ★第一輪打掉了兩個前提,先誠實記★

- **★「通知那條腿是斷的」是錯的★**:那支週報在暫停開關**之前**就執行,而且真的會推播。
  真正的問題不是斷了,是**太慢**——它要同一道閘對同一篇連喊 **14 天**才通知,
  拿來偵測「36 小時前死掉」根本來不及。第一版說「斷了」等於用錯的理由選了錯的接法。
- **★把死人開關押在健檢輸出,正是前科事故失敗過的同一招★**:那則事故的節點寫著
  「算得出觸發帳,但『誰會去看』仍無路徑;造了尺,沒造回看的觸發點,病灶未解」,
  一條軟提醒響了 46 天、18,283 次沒人發現。而且那道閘至今仍在天天觸發,不是舊病灶。

還有三條是我把機制看走眼:
- **鎖的主要接管判準是「持鎖行程還活著嗎」**,不是我寫的「鎖齡 60 分鐘」;
  60 分鐘只用在「pid 是空的」那個更窄的競態。
- **鎖的清除是靠 `trap ... EXIT`**,不是寫在函式結尾。我只寫了目標沒寫機制。
- **五步加總照現有寫法會失效**:那種 `echo "[$(ts)] rc=$?"` 裡的 `$?` 抓到的是指令替換自己的
  結束碼。而且函式現在**恆回 0**(最後一條是無條件的收尾 echo),不是我寫的「回最後一步的結果」。

## 現況查證(自己開檔看的)

- 那支腳本主體包在函式裡、結尾同一行接 `exit`(9/5 事故之後補的,防邊跑邊改)。
- **沒有整跑鎖**。**沒有完成戳記**。**沒有任何程式在讀它的紀錄檔**(全 repo 搜零命中)。
- **治理帳 30 天長了 94%**:2026-08-08 是 2,047,015 位元組,今天是 3,966,503。
- 排程設定只有日曆觸發,**沒有任何依賴退出碼的鍵**——非零不會停止排程也不會狂重試,
  但同樣不會通知任何人。(第一版寫「要查」,現在查完了,這條銷案。)

## 設計

### [S1] 健康狀態寫成一份機器局部的 JSON,不是一個「跑完了」的戳記

★第一版的戳記只記「我跑完了」,於是「五步都跑、其中一步失敗」會被標成存活★(外家席指出)。
改成一份原子寫入(先寫暫存檔再改名)的 JSON,內容:
開始時間、結束時間、**各步的結果**、加總結果、這次的執行編號。

**五個結果要存進五個獨立變數**,而且一定用「指令與賦值同一行、中間不插別的指令替換」的寫法
——現在第 1、2 段那種寫法抓到的不是前一支腳本的結果。函式最後一行換成真正的加總值,
不能再讓收尾 echo 當隱式回傳。

★「加總」是指「任一非零就非零」的邏輯聚合,不是算術相加★(r2 通才席實測):
退出碼只能吃 0 到 255。兩步各回 128(那是「被訊號中止」的慣例編碼)算術相加是 256,
取模之後**變成 0**——兩個真實失敗會被壓成「全部成功」,跟現在「恆回 0」是同一種靜默失敗,
只是從必然變成特定數值下才發生。

檔案放在版控外,位置與命名比照既有那批「每台機器各自的執行期狀態」
(扁平放在同一層、附一句為什麼不能進版控的理由),不另開新目錄。
★暫存檔要跟目的檔放同一層★(r2 指出,而且這是這個 repo 的既有寫法:
既有的原子寫入把暫存檔命名成「目的檔名 + 一個固定後綴」,刻意同目錄,就是為了避開跨檔案系統改名失敗)。
不要用系統暫存目錄再搬過來——那在這台機器上目前剛好同一顆磁碟不會炸,換一台就不一定。

**★檔案不存在的語意要定死★**(外家席指出,第一版完全沒定義):
- 不存在 = **從來沒跑完過**,訊息要跟「死掉了」分開講(新機、重新 clone、清過紀錄都會這樣)。
- 不存在**不算逾期**,但要印一句「這台機器上那支從來沒跑完過」。

### [S2] 死人開關:一支獨立的看門狗,健檢只當第二通道

★主通道不能是健檢輸出★(第一輪 blocker):那正是前科事故失敗過的做法。

**主通道 = 一支獨立的、極短的排程看門狗**:每小時跑一次,只做三件事——
讀那份健康 JSON、判斷逾期或加總結果非零、有事就寫一筆治理帳並印出來。
★它跟被監看的那支是兩個不同的失敗域★——這正是「監看者與被監看者同命」那條教訓要的。

★用哪一種排程、以及它到底叫不叫得醒機器,這台機器上有兩個互相矛盾的證據★(r2 通才席判 blocking):
- 被監看的那支自己的檔頭寫著「閉蓋的 Mac 幾乎一直在睡,日曆排程不會把機器叫醒」,
  所以它才另外設了一個每天 09:28 的強制喚醒。查證屬實:這台機器只設了那一個喚醒。
- **但這台機器上另一支每小時的排程,過去 7 天 168 個小時零缺口全部準時跑。**
  原因是睡眠目前被幾支常駐程式掐住(通話服務、藍牙、caffeinate),機器實際上幾乎沒真的睡著。

**裁定**:看門狗照那支已經證明可行的每小時排程做(同一種機制、同一個時點慣例)。
★但要誠實記:它現在跑得準,靠的是「睡眠剛好被別的程式掐住」這個跟本案無關的巧合★——
那幾支程式關掉,看門狗就會跟著開始漏跑。
REVISIT:2026-10-07 查看門狗的紀錄有沒有缺小時;有缺就代表要另外掛強制喚醒,或改設計。

★寫帳要邊緣觸發,不要每小時寫一筆★(外家席):照字面實作的話,故障持續期間每天會寫 24 筆同樣的東西,
而**這份計劃自己正在處理帳本膨脹**。改成:第一次發現寫一筆、狀態改變寫一筆、之後每天仍故障寫一筆、
恢復時再寫一筆。

**第二通道 = 健檢的軟提醒**:同一個判斷,但只在有人跑健檢時出現。
★必須接不會讓 issue 計數增加的那一支函式★——同一支程式裡已經有一段標題寫著「提醒,不擋」、
實際卻用了會擋的那支,依慣例就近仿寫會在腳本死掉的當下連帶擋住全 repo 的推送。
新段落要有自己的段落編號與閘名稱,才數得出來、也才進得了 14 天升級鏈。

**推播那條**:既有的週報路徑可以用,但它要連喊 14 天才通知。
★本案明文接受這個延遲當作第三層兜底,不假裝它是即時通道★;即時性靠看門狗那條。

**★36 小時門檻要能分辨「機器沒開機」★**(第一輪指出):真實紀錄裡有過一次 **129 小時**
的合法空窗(長假)。看門狗的判斷加一個條件:**這台機器從睡眠醒來超過兩小時**才算數。

★量法要寫死,不然這條防護會變成裝飾品★(r2 通才席判 blocking,我自己實測驗過):
最直覺的做法是問「開機多久」,**但那是錯的量**——這台是閉蓋的 Mac,幾乎一直在睡但從不關機,
實測開機時間是 59 天前(7/10),所以「開機超過兩小時」永遠成立,等於這個條件從第一天就是空的,
而且**不會有任何錯誤訊息**——正是本案在防的那種靜默失效。
**正確的原語是問「上次真正從睡眠醒來是什麼時候」**(`sysctl kern.waketime`,單一系統呼叫)。
我實測:開機時間 7/10、上次醒來 9/5 19:50——兩個差 57 天,證明它們量的不是同一件事。

### [S3] 抄鎖:把非顯而易見的細節寫下來,並加防漂移

抄的是那把「建目錄當原子鎖」的實作。★這五個細節第一版漏了或寫錯,現在寫清楚★:
1. 建目錄是唯一的原子取鎖點。
2. **主要接管判準是「持鎖行程還活著嗎」**——死了就立刻接管,跟鎖存在多久無關。
3. 60 分鐘只用在「pid 是空的」那個競態(對方剛建好目錄還沒寫 pid);量不出鎖齡時也要讓行。
4. 接管是「刪掉再建」,兩個接管者之間仍有競態。**來源腳本有 `set -e` 兜著,這支沒有**
   ——原樣抄過去,第二個接管者建目錄失敗後會繼續跑。**重新取鎖必須顯式檢查成功**。
5. **清除靠 `trap ... EXIT`,不是寫在函式結尾**;而且 trap 要在取到鎖之後**立刻**安裝
   (來源是初始化一大段之後才裝,那段窗口也可能殘鎖,不要照搬)。

★2026-09-07 code-batch19 之後,上面第 2 與第 4 條要接著讀這三句(碼已經改了,這裡不改就會說反話)★:

- **第 2 條的「持鎖行程還活著嗎」怎麼判,換過機制。** 中間一版是「問 `ps` 的指令列裡有沒有
  我們的腳本名字」,**那一版被實跑打穿**:持鎖者換個名字啟動(符號連結、包一層 wrapper)
  就認不出來,鎖被搶走、兩個行程同時跑。現在是 pid 加上「那個行程的啟動時刻」,名字不參與。
- **第 4 條講的「`set -e` 兜著」對來源那支也不成立。** 取鎖函式被寫成 `take_lock || {…}` 的
  左手邊時,bash 會把整個函式體的 errexit 關掉。所以兩支都一樣:**要顯式檢查,不能靠 `set -e`**。
- **第 5 條的「立刻安裝」在來源那支收斂成更乾淨的形式**:收尾器定義整段搬到取鎖之前,
  全檔只留一個 `trap`,跟這支一致(中間一版用旗標,被架構對齊席擋下)。

**★防漂移★**(架構席指出):這個 repo 對複製同一段邏輯的既有立場是二選一——
機械守衛比對,或至少留同源回指註解。本案採**兩者都做**:
抄過去的那段開頭附一句「同源:自主迴圈那支的取鎖段」,並加一條測試比對兩份的關鍵行為
(取鎖方式、接管判準、清除機制)一致,不一致就翻紅。

### [S4] 帳本門檻:數字要填,而且要對得上真實曲線

★第一版的「N MB」那個 N 我根本沒填★。現在填:**5 MB**(現在 3.97 MB,依近期曲線約兩到三週會到)。

★「近 7 日平均每日 500 筆」對不上實際曲線★:近 8 天是 62 / 61 / 91 / 159 / 391 / 669 / 931 /
1155(最後一天只到上午),7 日均值 337.7 還沒過,但**連續三天單日已破 500 且逐日翻倍**——
這條門檻上線沒幾天就會天天叫,變成第三種「叫了但沒人在意」的訊號。
**改成看成長率**:近 7 日均值**比前 7 日均值成長超過一倍**才出聲。這樣抓的是「異常加速」,
不是「量大」。順手記下來:目前成長主要來自兩道閘(近四天從 188/38 漲到 486/260),
真正該處理的可能是那兩道閘在重複寫同一批未修的提醒,那是另一案。

★「先不分檔」的理由要訂正★:第一版寫「四個整檔讀者 + 判定回放要逐行算雜湊閉包」。
**雜湊閉包讀的是另一本帳,不是這一本**;四個整檔讀者這半查證為真,單獨就足以撐住結論。
錯的那半刪掉。

## 非目標

- 不做帳本分檔(見 [S4])。

## 實務隱患

- **看門狗本身也會死**:它是獨立的排程項目,但排程器整個掛掉就兩支都不會跑。
  ★這一層本機沒有解★——要解得靠機器外的東西。
  **正式的替代方案(外家席提,列成可翻案的選項而不只是參考)**:
  跑完之後向一個機器外的心跳服務報到,由那個服務在寬限期過後通知。
  它同時涵蓋「排程器整個失效」與「機器長期離線」——**這是本機兩支排程都覆蓋不到的失敗域**。
  代價:網路依賴、外部服務、通知設定、可能要管憑證。
  REVISIT:2026-11-07 若出現「兩支都沒跑但沒人發現」的實例,就翻到這條。
- **看門狗的誤報**:開機後兩小時內跨過門檻仍會誤報一次。
  REVISIT:2026-10-07 查看門狗寫的那個閘:若誤報(當時腳本其實是好的)超過真報,門檻要調。
- **軟提醒被接成硬擋**:見 [S2],計劃已明講要接哪一支。
  落地時加一條測試:餵一個逾期的健康檔進去,斷言健檢的 issue 計數**不變**。
- **鎖會不會把人鎖在外面**:60 分鐘接管那條是抄來的既有做法。本案的鎖目錄要真的進忽略清單。
  ★訂正一條我自己寫錯的診斷★:第一版我寫「來源那支的鎖目錄沒有被現有忽略清單涵蓋」——
  **那是錯的**。實測建立那個目錄再查,它命中忽略清單第 15 行的規則;而且追 git 歷史,
  那條規則跟鎖機制是**同一次進 repo** 的,從頭就有涵蓋,不是「平常不落地才沒炸」的僥倖。
  ★這句話的來源是第一輪某席報告的一句附帶提醒,我沒查證就抄進計劃★——
  同型再犯,已記進 [[Issues/把自己的推論寫成repo明文寫過]]。
- **這支腳本是本 repo 專用的**:安裝器的清單裡沒有它,不隨工具鏈分發。
  本案的所有東西都只服務本 repo,不要寫成好像消費端也會拿到。

PRIOR-ART: 最小解在收尾一份健康 JSON 加一支獨立看門狗;
世界解=healthchecks.io / Cronitor 的心跳加寬限期、systemd 的 OnFailure、

### 一、看門狗只有一個來源,而那個來源的沉默被它當成了「沒發生過」

**它每天喊一次「這台機器上的 wrapper 從來沒跑完過」,而 wrapper 自己的紀錄檔裡,

成因:「跑完要寫一份健康狀態檔」是這一批才加進 wrapper 的,而排程每天 09:30 叫的
還是舊版本(改動當天稍晚才落地)。舊版不寫那個檔 → 檔不存在 → 看門狗照字面判「從來沒跑完過」。
機械證據:wrapper 的紀錄檔裡「開始(run …)」與「五步 rc=…」這兩行**新版才有**的字,
出現次數都是 0。

★這正是本 repo 那條「只信一個來源、沒去對第二個」的老坑,而且犯在一支
「專門用來告訴人真相」的元件上。★ 它手邊就有第二個來源(wrapper 自己的紀錄檔),沒去看。

**修法**:健康檔不在時,先讀 wrapper 的紀錄檔找最後一次「完成」。
- 在門檻(36 小時)內 → 換句話講:「wrapper 有在跑(最後一次 …),但沒有留下健康狀態檔
  ——這支看門狗因此看不到它的結果。」★仍然要喊★:那個狀態代表看門狗是瞎的,值得知道一次。
- 找不到、或已經超過門檻 → 才說「從來沒跑完過」。
- **紀錄檔本身不在 → 退回原本的判斷**(fail-safe:第二個來源缺席不能讓警報消失)。

守衛:`t_wrapper_watchdog_no_health_but_wrapper_ran`,五條斷言。翻紅釘三個全紅
(拿掉第二個來源 / 不管那次多久以前一律當成跑過 / 把「開始」也當成「完成」)。

**這批提示會自己停**:下一次 09:30 跑的是新版,健康檔一寫出來就進正常判斷。
