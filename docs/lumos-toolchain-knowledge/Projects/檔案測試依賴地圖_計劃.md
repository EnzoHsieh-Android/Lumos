# 檔案↔測試依賴地圖_計劃（①）

## 目標與問題

TDD／code-loop 迴圈裡「改了 X，該跑哪些測試」目前靠人腦或全跑。`test-layers` 只到**棧層**粒度（碰 .cs → 跑 C# 層）；本案補**檔案**粒度：src 檔 ↔ 測試檔的邊，advisory 推薦，並反向暴露「沒有任何已知測試指向它」的裸檔。

`PRIOR-ART:` TIA（test-impact analysis）生態——pytest-testmon（動態 coverage 圖，單語言）、Jest `--findRelatedTests`（靜態 import 圖）、Bazel `rdeps`（建構圖）。本 repo 群多語言（kt/cs/vue/sql/py）且零依賴家規，動態 coverage 與 AST import 圖皆不可得 → 裁定 **borrow-design**：借「diff→受影響測試」的產品形態，原生實作為雙源靜態近似（naming 慣例＋git 共變），精度天花板如實聲明、advisory 不硬擋。

## 範圍刀（明確不做）

- **不做**動態 coverage、不 parse AST、不解析 import 語句（多語言 parser＝依賴地獄）。
- **不做**硬閘：`affected` 恆 rc0（同 `test-layers` advisory 家族）；不掛 pre-push、不進 doctor。
- **不做**測試「方法」粒度；粒度到**檔案**為止。
- **不自動 rebuild**：map 是顯式 `build` 產物；陳舊性只提示不擋（見 [S2]）。
- v1 **不掛 hook**；skill 文件僅一行提及（見 [S5]），深整合待實戰回饋。
- v1 常數（conf 值、stem 門檻、掃描上限、cochange conf 下限）**刻意寫死不開設定檔**——先讓 [S4] 驗證裁值，有實戰回饋再考慮 `.lumos/` 覆寫（明文取捨，非疏漏）。

## 條款

### [S1] `lumos testmap build [--repo R] [--json]`——三路訊號挖掘

vault-free。定根：`--repo R` 或 `_anchor_repo_root` 自動解析；build 前置驗證 **R 必須是 repo 根**（`git -C R rev-parse --show-toplevel` 結果 == R 的 resolve；子目錄／非 repo → stderr 診斷＋rc2——`_anchor_repo_root` 不驗 `.git`，子目錄會讓 ls-files（子樹相對）與 git log（root 相對）兩套路徑空間不相交、靜默零邊，故此驗證必做）。**所有 git 呼叫一律 `-C <repo_root>`（或 cwd=repo_root）＋ `timeout=30`（同 `cmd_test_layers` 慣例）**。輸出 `.lumos/testmap.json`：

```json
{"version": 1, "built_at_commit": "<HEAD sha>", "built_at": "<UTC ISO-8601 秒級>",
 "edges": [{"src": "a/B.cs", "test": "t/BTests.cs", "sources": ["naming","cochange"], "conf": 0.9}]}
```

- `edges` 依 (src, test) 字典序排序、每邊 `sources` 字典序——**確定性承諾限 `edges` 內容**（同內容重 build 的 `edges` 零 diff；`built_at`/`built_at_commit` 明文排除）。`sources` 值域＝`{"naming","content","cochange"}`（三路訊號各一標籤）。
- 寫檔：`.lumos/` 不存在先 `mkdir(parents=True, exist_ok=True)`；tmp 檔同目錄、`os.replace` 原子覆寫。**產物不進版控**：實作時把 `.lumos/testmap.json` 加進 repo `.gitignore`（`built_at` 每次變動，追蹤只產垃圾 diff）。
- **unborn branch（零 commit）**：`rev-parse HEAD` 失敗 → stderr「空歷史，無可挖」＋rc2（v1 明文限制）。含換行字元的檔名不支援（未用 `-z` NUL 分隔，明文限制）。

**檔案全集**＝`git -C <root> -c core.quotePath=false ls-files`（追蹤檔；不掃 filesystem）。路徑一律 repo-root-relative。

**副檔名白名單（字面值集合）**＝`{kt,java,cs,py,ts,tsx,js,jsx,vue,swift,sql}`（比對大小寫不敏感）。測試檔與候選 src 檔都**先過白名單**——md/png/yaml 等永不入場。

**測試檔判定**（白名單內，下列兩者取聯集）：
- 路徑段命中 `(^|/)(tests?|__tests__|specs?)(/|$)`（大小寫不敏感）；或
- **完整檔名**（不經 `Path.stem`）命中：stem 前綴 `test_`／stem 尾綴綴詞（見下表，**須帶邊界**）／檔名含 `.spec.` 或 `.test.` 段（如 `Foo.spec.ts`）。

**綴詞表（判定與剝除共用一張，長度降序）**：`_tests`(6)＝`_specs`(6)＞`Tests`(5)＝`Specs`(5)＝`_test`(5)＝`_spec`(5)＞`Test`(4)＝`Spec`(4)；同長度依表列順序（底線變體優先）。**邊界條件（防 `Latest.ts`/`Contest.cs` 誤判）**：底線變體天然帶邊界；無底線變體（`Tests`/`Test`/`Specs`/`Spec`）須**原字面首字母大寫**（駝峰段語意——`FooTests` 命中、`latest`/`Latest` 不命中：`Latest` 的 `test` 前無駝峰邊界）。

**候選 src 檔**＝白名單內、且非測試檔。（無副檔名檔案如 `scripts/lumos` 本體不入候選——已知天花板，見 [S4]。）

**訊號一 naming**：src-stem＝src 檔 `Path.stem`。測試檔比對 stem：完整檔名**只剝最後一段語言副檔名**，緊鄰其前是 `.spec`/`.test` 標記段則連同剝除（`Foo.spec.ts`→`Foo`；不泛剝點段，`Foo.generated.Tests.cs`→`Foo.generated.Tests`）；再依綴詞表**單次**剝尾綴（無尾綴才剝前綴 `test_`），**剝後尾端殘留 `.` 或 `_` 一併去除**（`Foo.generated.Tests`→剝 `Tests`→去尾點→`Foo.generated` ✓；`foo_spec`→剝 `Spec`→去尾底線→`foo` ✓）。剝後與 src-stem 大小寫不敏感全等 → 邊，conf=0.9。多個同 stem src 檔＝各建邊。僅目錄規則命中、無綴詞可剝者，stem 原樣參與比對。

**訊號二 content（內容引用）**：測試檔內文（UTF-8 `errors="ignore"`）以詞邊界 regex 匹配 `re.escape(src-stem)` 或 `I`+src-stem（C# 介面 DI 慣例，Landmark 實查）；大小寫敏感（識別字語意）；**門檻作用於 src-stem 本身**：len(src-stem)<4 一律不建 content 邊（`I`+stem 變體亦不搜）。**效能**：全部 src-stem 合併單一 alternation regex、每測試檔掃一次（O(檔) 非 O(檔×stem)）。單檔上限 200KB；超限或讀檔失敗（OSError）→ 逐檔跳過 content、stderr 記一筆，不中斷、不影響 naming。→ 邊，conf=0.5。

**訊號三 cochange**：
- `cfg, notes = _cochange_load_config(repo_root)`（**(cfg, notes) 二元組**，單變數接＝tuple 餵進挖掘層直接 TypeError）；notes 文字模式印 stdout、`--json` 模式走 stderr。
- `rules, n_txn, n_files, err = _cochange_mine(repo_root, cfg)`（**四元組**；`rules` 的值是 `(conf, support)` **二元組**——`conf, support = rules[(src, test)]` 再用，直接拿去比大小＝TypeError）。
- `err`（git 挖掘失敗）→ **cochange 源整條跳過**＋stderr 診斷，naming/content 邊照出（advisory 產物，單源可用勝於全敗；不升 rc）。
- 只收 (src→test) 方向、src ∈ 候選 src、test ∈ 測試檔的 pair；**挖掘 conf < 0.3 不建邊**（噪音地板，v1 先驗值，[S4] 實測裁）；**寫入 map 的 conf＝min(挖掘 conf, 0.8) 封頂**——防 freq=2/support=2 的巧合邊挖掘 conf=1.0 壓過 naming(0.9)與自證(1.0)佔頂排序。
- **cfg 沿用範圍明文**：`exclude`／`max_changeset` 生效（預設排除 Migrations/`*.g.cs` 等、>20 檔 commit 整筆丟棄——大重構挖不到邊，cochange 源已知天花板，見實務隱患）；`min_confidence`（0.8）與 `min_support`（3）**刻意不套**（testmap 要 recall；挖掘層硬底線 support≥2 天然生效）——專案調 `.lumos/cochange.json` 的這兩值對 testmap 無效，如實記。

**邊合併**：同 (src,test) 多訊號命中 → `sources` 併列、`conf = max(各源 conf)`。

**失敗路徑**：repo root 驗證失敗／非 git repo／repo 級 git 指令失敗 → stderr 診斷＋**rc2**（對齊 `cmd_cochange_rules` 對 git 失敗 rc2 慣例；rc1 不用）。檔案級失敗不升級（逐檔跳過）；cochange 源失敗不升級（整源跳過）。

**stdout（文字模式）**：`testmap: edges=<N> src=<N> tests=<N> → .lumos/testmap.json`。
**`build --json`**：`{"edges":.., "src_files":.., "test_files":.., "path":".lumos/testmap.json"}`——stdout 恆單行純 JSON；cochange notes 走 stderr（刻意偏離 `cmd_cochange_rules --json` notes-stdout 前例：該前例為 pre-commit hook 吞 stderr 場景設，build 非 hook 場景，純度優先）。

### [S2] `lumos testmap affected --diff <range> [--repo R] [--json]`——advisory 查詢

定根同 [S1]（`_anchor_repo_root`；root 解析失敗＝fail-open 路徑之一，非 rc2）。map 從 `<root>/.lumos/testmap.json` 讀。

**map 有效性（三級守衛）**：
1. **整檔失效**（視同無 map）：JSON 解析失敗／根非 object／`edges` 非 list／`version` ≠ 1／`built_at_commit` 或 `built_at` 缺、非字串、或 `built_at_commit` 不符 `^[0-9a-f]{7,40}$`（消毒後才准進 git 指令）。
2. **逐邊跳過**：edge 缺 `src`/`test`、值非字串、或 `conf` 非有限數值。
3. 有效 map 才走陳舊判定與建議。

**查詢**（diff 檔集＝`git -C <root> -c core.quotePath=false diff --name-only <range>`）：
- 改動檔在 map 有邊（src 端）→ 列其測試檔；src 檔現存與否不影響查邊（刪 src 正是會弄壞測試的改動）。
- 改動檔本身是測試檔（依 [S1] 規則現算）**且當前 ls-files 存在** → 列入建議，conf=1.0、srcs=[]（自證）；**已刪除的測試檔不自證**（推薦跑不存在的檔＝錯誤行為），與 uncovered 刪檔語意一致。
- 同一測試檔多路徑指到（多 src 邊／自證）→ 輸出端去重一筆：conf 取 max、srcs 取聯集（cochange 封頂 0.8 後自證 1.0 恆置頂；同 conf 按路徑 tie-break）。
- 改動的**現存候選 src 檔**無任何邊 → 「無已知測試」段（按路徑排序）；非白名單副檔名與已刪除檔靜默略過。
- 建議排序：conf 降序、同 conf 按測試檔路徑。

**文字模式輸出格式**：有 map 時首行 `map built at <built_at> (<built_at_commit 前8碼>)`；建議行 `  <conf> <test檔路徑>`（conf 兩位小數）；裸檔段標題行 `無已知測試:` 後逐行路徑。

**rc 合約**：恆 rc0；唯一 rc2＝缺 `--diff`。**fail-open 路徑全枚舉**（皆 stderr 診斷＋rc0）：① `--diff` 值 `-` 開頭；② repo root 解析失敗；③ 無 map 檔（提示「先跑 lumos testmap build」）；④ map 整檔失效；⑤ git diff 失敗（range 不存在/逾時/例外）。

**陳舊提示（雙訊號，advisory，僅有效 map）**：①② 獨立判定，任一真 → stderr「map 可能過期，建議 rebuild」。① `built_at_commit` 非 HEAD 祖先（`git merge-base --is-ancestor` 失敗）；② `git diff --name-only <built_at_commit>..HEAD` 與「（當前候選 src ∪ 測試檔）∪ map 內 edges 的 src/test 路徑」交集非空（含 build 後被刪的檔）。②自身 git 失敗 → 略過②不影響①。

**`--json`**（stdout 恆恰一行合法 JSON，所有提示/banner 走 stderr）：
- 正常：`{"map_built_at":.., "built_at_commit":.., "stale": bool, "suggests":[{"test":..,"conf":..,"srcs":[..],"sources":[..]}], "uncovered":[..]}`（`uncovered` 元素＝路徑字串；`suggests` 帶 `sources` 供消費端辨訊號出身，自證項 `sources=["self"]`）。
- **fail-open ①-④**（拿不到有效 map／diff 檔集）：`{"map_built_at":null,"built_at_commit":null,"stale":false,"suggests":[],"uncovered":[]}`。
- **fail-open ⑤**（map 有效、僅 git diff 失敗）：`map_built_at`/`built_at_commit` 照實、`stale` 依①判（②不可用）、`suggests`/`uncovered` 空——與文字模式同狀態說同一件事。
- 無 map 時自證/uncovered 理論上可運作（不依賴 map），v1 **刻意全空換一致性**（明文取捨）。

### [S3] 測試（TDD，`scripts/test_lumos.py` 新 `t_testmap_build`＋`t_testmap_affected` 兩函式——純組織選擇，不援引家族拆法前例）

沙盒 git repo 鋪 src＋測試檔＋共變歷史，至少覆蓋：
1. naming 邊（`Foo.cs`↔`FooTests.cs`，conf 0.9）＋多段副檔名（`Foo.spec.ts`↔`Foo.ts`）＋**點分 basename**（`Foo.generated.Tests.cs`↔`Foo.generated.cs`——剝綴詞後去尾點）＋**底線 spec**（`foo_spec.py`↔`foo.py`——去尾底線）；
2. content 邊（conf 0.5）＋短 stem（<4）不建邊（含 `I`+stem 不搜）＋`I`+stem 介面慣例命中；
3. cochange 邊（共變歷史 → conf 進邊；挖掘 conf<0.3 不建邊；**寫入 conf 封頂 0.8**）；
4. 多源合併（sources 併列、conf 取 max）＋`edges` 排序確定性（兩次 build 的 `edges` 逐字相等）；
5. affected：推薦降序／自證 conf=1.0＋sources=["self"]／自證與邊建議去重一筆／裸檔進 uncovered／md 檔靜默／**已刪除測試檔不自證**；
6. rc 矩陣：無 map rc0＋提示；爛 JSON rc0；git diff 失敗 rc0；缺 `--diff` rc2；build 非 git 目錄 rc2；**build --repo 指 repo 子目錄 rc2**；
7. 陳舊雙訊號：①非祖先 sha；②祖先 sha＋build 後候選檔 commit；**②′ build 後刪檔也觸發**（並集含 map 內路徑）；
8. 200KB 上限：超限跳過 content（stderr 記一筆）、naming 不受影響；
9. 同 stem 多 src 各建邊；**目錄規則命中**（`tests/helpers.py` 無綴詞檔名判為測試檔）；
10. `--json` 純度：affected 正常與 fail-open（無 map）皆恰一行合法 JSON；build --json 時 notes 在 stderr；
11. map 守衛：edge 缺欄跳該邊；`edges` 非 list 整檔失效；**`built_at_commit` 缺欄整檔失效（不 crash）**；
12. 誤判邊界：`foo_tests.py`↔`foo.py` 建邊；**`Latest.ts` 不判為測試檔**；白名單外副檔名（如 `foo_test.md`）不入場；
13. `.lumos/` 不存在時 build 自建目錄（mkdir）。

### [S4] Landmark 驗證（成效裁決，轉正閘）

- 在 LandmarkMember 真庫 `testmap build`，人工抽 **10 對金標**算 recall：
  - **分層抽樣（防自欺，r1 折入）**：金標須跨 `LandmarkMember.Tests`（逐類命名，naming 友善，~6 檔）與 `LandmarkMember.IntegrationTests`（情境命名如 `RedeemIdempotencyTests`，naming 盲區，30+ 檔）兩層，**各層至少 4 對**、附抽樣依據與分佈——不得偏抽 naming 友善層灌 recall。
  - **recall**（金標對被 map 命中比例）——主指標；
  - **噪音度**：suggests 中位條數／改動檔（供人感受，不設硬閘）。
- 裁決帶：recall ≥0.7 → 轉正；0.5–0.7 → 攤給人裁（帶噪音度）；<0.5 → 殺（或裁掉表現差的源降級重測一次）。
- toolchain 自庫如實記天花板：`test_lumos.py` 單檔巨測 → map 退化為「全部指向一檔」；`scripts/lumos` 無副檔名不入候選 src——本 repo 最重要的檔在 map 外。兩者**不得當成效證據**，自庫僅驗機械正確性。

## 實務隱患

- naming 慣例漂移（專案不用 `*Tests` 慣例）→ 源 A 空集，cochange 兜底；Landmark 驗證會暴露。
- 內容引用源在大測試檔上的掃描成本 → 200KB 上限＋stderr 記帳（[S1]）。
- cochange 的「共改≠覆蓋」語意誤讀 → conf 承接挖掘值(封頂 0.8)、輸出標 sources 讓人看得到邊的出身。
- cochange 沿用 exclude/max_changeset:>20 檔的大重構 commit 整筆丟棄——最需要 testmap 的場景恰是 cochange 源盲區,靠 naming/content 兜底(明文天花板)。
- map 陳舊誤導 → [S2] 雙訊號軟提示（祖先鏈＋build 後候選檔異動）。
- 情境命名整合測試（`RedeemIdempotencyTests` 類）naming/內容雙源都可能落空 → cochange 是唯一兜底，[S4] 分層抽樣如實量測。
