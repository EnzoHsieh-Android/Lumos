# 檔案↔測試依賴地圖_計劃（①）

## 目標與問題

TDD／code-loop 迴圈裡「改了 X，該跑哪些測試」目前靠人腦或全跑。`test-layers` 只到**棧層**粒度（碰 .cs → 跑 C# 層）；本案補**檔案**粒度：src 檔 ↔ 測試檔的邊，advisory 推薦，並反向暴露「沒有任何已知測試指向它」的裸檔。

`PRIOR-ART:` TIA（test-impact analysis）生態——pytest-testmon（動態 coverage 圖，單語言）、Jest `--findRelatedTests`（靜態 import 圖）、Bazel `rdeps`（建構圖）。本 repo 群多語言（kt/cs/vue/sql/py）且零依賴家規，動態 coverage 與 AST import 圖皆不可得 → 裁定 **borrow-design**：借「diff→受影響測試」的產品形態，原生實作為雙源靜態近似（naming 慣例＋git 共變），精度天花板如實聲明、advisory 不硬擋。

## 範圍刀（明確不做）

- **不做**動態 coverage、不 parse AST、不解析 import 語句（多語言 parser＝依賴地獄）。
- **不做**硬閘：`affected` 恆 rc0（同 `test-layers` advisory 家族）；不掛 pre-push、不進 doctor。
- **不做**測試「方法」粒度；粒度到**檔案**為止。
- **不自動 rebuild**：map 是顯式 `build` 產物；陳舊性只提示不擋（見 [S2]）。
- v1 **不掛 hook**；skill 文件僅一行提及（見 [S5]），深整合待實戰回饋。
- v1 常數（conf 值、stem 門檻、掃描上限、cochange conf 下限）**刻意寫死不開設定檔**——先讓 [S4] 驗證裁值，有實戰回饋再考慮 `.lumos/` 覆寫（明文取捨，非疏漏）。

## 條款

### [S1] `lumos testmap build [--repo R] [--json]`——雙源挖掘

vault-free（同 `cochange`/`test-layers` 家族；定根用 `_anchor_repo_root`——注意 `cochange` 家族實際用的是 `_cochange_repo_root`（多驗 `.git`），本案取前者並在 build 失敗路徑自行驗 git）。輸出 `.lumos/testmap.json`：

```json
{"version": 1, "built_at_commit": "<HEAD sha>", "built_at": "<UTC ISO-8601 秒級>",
 "edges": [{"src": "a/B.cs", "test": "t/BTests.cs", "sources": ["naming","cochange"], "conf": 0.9}]}
```

- `edges` 依 (src, test) 字典序排序、每邊 `sources` 字典序——**確定性輸出**（同內容重 build 零 diff）。
- 寫檔：`.lumos/` 不存在先 `mkdir(parents=True, exist_ok=True)`（同 `cmd_anchor_approve` 慣例）；tmp 檔與目標同目錄、tmp→rename。

**檔案全集**＝`git -c core.quotePath=false ls-files`（追蹤檔；測試檔與 src 檔同源，不掃 filesystem——排除 ignored/vendor/未追蹤）。路徑一律 repo-relative。

**測試檔判定**（兩者取聯集，**全部大小寫不敏感**）：
- 路徑段命中 `(^|/)(tests?|__tests__|specs?)(/|$)`；或
- **完整檔名**（不剝副檔名）命中：stem 前綴 `test_`／stem 尾綴 `_test(s)`、`Test(s)`、`Spec`（尾綴指最後一個副檔名點之前的 stem 尾端）／檔名含 `.spec.` 或 `.test.` 段（如 `Foo.spec.ts`——比對整檔名子字串，不經 `Path.stem`，避免多段副檔名剝壞）。

**候選 src 檔**＝檔案全集內、副檔名 ∈ {kt,java,cs,py,ts,js,vue,swift,sql}、且非測試檔。（無副檔名檔案如 `scripts/lumos` 本體不入候選——已知天花板，見 [S4]。）

**src-stem（比對鍵）**：src 檔的 `Path.stem`。**測試檔比對 stem**：完整檔名先去掉副檔名鏈（`.spec.ts`/`.test.js` 整段視為副檔名鏈剝除），再**單次**剝測試綴詞——優先剝尾綴（`Tests`>`Test`>`Spec`>`_tests`>`_test`，最長優先），無尾綴才剝前綴 `test_`；剝一次即止。剝後與 src-stem **大小寫不敏感全等** → 邊，conf=0.9。多個同 stem src 檔＝各建邊（誠實多指，不猜唯一）。僅目錄規則命中、檔名無綴詞可剝者，stem 原樣參與比對。

**源 A 內容引用**：測試檔內文（UTF-8 `errors="ignore"` 解碼，best-effort）以詞邊界 regex 匹配 `re.escape(src-stem)` **或 `I`+src-stem**（C# 介面 DI 慣例——整合測試常只引 `IMemberRepository` 不引 `MemberRepository`，Landmark 實查證實）；**大小寫敏感**（識別字語意）；stem 長度 ≥4 才算（防 `Api`/`Db` 短詞噪音）→ 邊，conf=0.5。單檔掃描上限 200KB；超限或讀檔失敗（OSError）→ **逐檔跳過內容源**、stderr 記一筆，不中斷 build、不影響該檔 naming 源。

**源 B（cochange）**：`cfg = _cochange_load_config(repo_root)`（吃專案 `.lumos/cochange.json` 的 exclude/max_changeset；其 `notes` 依 cochange 家族慣例**印 stdout**）→ `_cochange_mine(repo_root, cfg)`；取方向 (src→test) 的 conf；只收 src 為候選 src 檔、另端為測試檔的 pair；**conf < 0.3 不建邊**（噪音地板；不沿用查詢家族的 min_confidence 0.8——testmap 要 recall，0.8 會殺光弱共變訊號；0.3 為 v1 先驗值，[S4] 實測裁）。support≥2 硬底線由 `_cochange_mine` 挖掘層天然沿用。

**邊合併**：同 (src,test) 多源命中 → `sources` 併列、`conf = max(各源 conf)`。

**失敗路徑**：找不到 repo root／非 git repo／git 指令失敗 → stderr 診斷、**rc 2**（對齊家族慣例：`cmd_cochange_rules`/`cmd_anchor_verify` 對「repo/git 前置失敗」皆 rc2；rc1 保留給「跑成功但驗出問題」語意，本指令不用）。檔案級讀取失敗不升級——逐檔跳過（見內容引用段）。

**stdout（文字模式）**：`testmap: edges=<N> src=<N> tests=<N> → .lumos/testmap.json`（一行摘要，對齊 `cochange rules` 風格）。
**`build --json`**：`{"edges": <邊數>, "src_files": <候選src數>, "test_files": <測試檔數>, "path": ".lumos/testmap.json"}`（單行純 JSON；**唯一例外**：cochange cfg notes 明文走 stdout、印在 JSON 行之前——刻意與 `cmd_cochange_rules --json` 現行為一致，消費端 parse 最後一行）。

### [S2] `lumos testmap affected --diff <range> [--repo R] [--json]`——advisory 查詢

- diff 檔集（`git -c core.quotePath=false diff --name-only`，`-` 開頭值防護同 `test-layers`：stderr 提示＋**rc0** 跳過，非 rc2）→ 查 map：
  - 改動檔在 map 有邊（src 端）→ 列其測試檔；**檔案現存與否不影響查邊**（刪除的 src 仍列其舊邊測試——刪檔正是會弄壞測試的改動）。
  - 改動檔本身是測試檔（依 [S1] 判定規則現算）→ 列入建議，**conf=1.0、srcs=[]**（自證）。
  - 同一測試檔被多路徑指到（多 src 邊／自證併發）→ **輸出端去重一筆**：conf 取 max（自證 1.0 天然置頂）、srcs 取聯集。
  - 改動的**現存候選 src 檔**（[S1] 定義，以當前 ls-files 判）無任何邊 → 列入「無已知測試」段（裸檔暴露；排序按路徑）；非候選副檔名（md/json/yml…）與已刪除檔靜默略過。
  - 建議排序：conf 降序、同 conf 按測試檔路徑。
- **恆 rc0**；唯一 rc2＝缺 `--diff`（同 `cmd_test_layers` 慣例）。fail-open 全覆蓋：無 map 檔→stderr 提示「先跑 lumos testmap build」；**map 壞損**（JSON 解析失敗／根非 object／`edges` 非 list／edge 缺 src/test 欄──缺欄跳該邊、其餘整檔視為無 map）；git diff 失敗（range 不存在/逾時/例外）→ 一律 stderr 診斷＋rc0＋空結果（同 `cmd_test_layers` 的 fail-open 合約）。
- **陳舊提示（雙訊號，advisory）**：文字模式**有 map 時**首行印 `map built at <built_at> (<built_at_commit 前8碼>)`（無 map／壞 map 走 fail-open 提示，無此行）。滿足任一 → stderr 加「map 可能過期，建議 rebuild」：① `built_at_commit` 非 HEAD 祖先鏈可達（`git merge-base --is-ancestor` 失敗——rebase 掉了）；② `git diff --name-only <built_at_commit>..HEAD` 與「候選 src ∪ 測試檔」交集非空（**build 之後真的有 code 動了**——典型過期情境；舊 SHA 仍是祖先所以 ① 抓不到，此訊號補上）。②失敗（如 ① 已 fail）則只出 ①。
- **`--json`**：單行純 JSON `{"map_built_at":..., "stale": true|false, "suggests":[{"test":..,"conf":..,"srcs":[..]}], "uncovered":[..]}`；**文字首行 banner 與所有提示在 json 模式一律走 stderr**（stdout 保持單行可 parse——`cmd_cochange_rules` 的 notes 混 stdout 是既知前例坑，本案明文規避）。

### [S3] 測試（TDD，`scripts/test_lumos.py` 新 `t_testmap_build`＋`t_testmap_affected`，對齊 `t_testlayers_*` 拆法）

沙盒 git repo（既有測試慣例）鋪 src＋測試檔＋共變歷史，至少覆蓋：
1. naming 邊（`Foo.cs`↔`FooTests.cs`，conf 0.9）＋多段副檔名（`Foo.spec.ts`↔`Foo.ts` 建邊——完整檔名判定不經 stem 剝壞）；
2. 內容引用邊（測試檔內文提及 stem，conf 0.5）＋短 stem（<4字元）不建邊＋`I`+stem 介面慣例命中；
3. cochange 邊（兩次共改 commit → conf 進邊；conf<0.3 不建邊）；
4. 多源合併（sources 併列、conf 取 max）＋edges 確定性排序（重 build 零 diff）；
5. affected：src 命中推薦降序／測試檔自證 conf=1.0／自證與邊建議同測試檔去重一筆／裸檔進 uncovered／md 檔靜默；
6. 無 map fail-open rc0＋提示；**壞 map**（爛 JSON）fail-open rc0；**git diff 失敗**（不存在 range）fail-open rc0；缺 `--diff` rc2；build 於非 git 目錄 **rc2**；
7. 陳舊提示雙訊號：①map 記非祖先 sha → rebuild 建議；②祖先 sha 但 build 後有候選檔 commit → rebuild 建議；
8. 內容掃描 200KB 上限：超限測試檔跳過內容源（stderr 記一筆）、naming 源不受影響；
9. 同 stem 多 src（`a/Foo.cs`＋`b/Foo.cs`↔`FooTests.cs`）→ 各建邊；
10. `--json` 純度：affected --json stdout 恰一行合法 JSON（banner 在 stderr）、含 `stale` 欄位。

### [S4] Landmark 驗證（成效裁決，轉正閘）

- 在 LandmarkMember 真庫 `testmap build`，人工抽 **10 對金標**算 recall：
  - **分層抽樣（防自欺，r1 折入）**：金標須跨 `LandmarkMember.Tests`（逐類命名，naming 友善，~6 檔）與 `LandmarkMember.IntegrationTests`（情境命名如 `RedeemIdempotencyTests`，naming 盲區，30+ 檔）兩層，**各層至少 4 對**、附抽樣依據與分佈——不得偏抽 naming 友善層灌 recall。
  - **recall**（金標對被 map 命中比例）——主指標；
  - **噪音度**：suggests 中位條數／改動檔（供人感受，不設硬閘）。
- 裁決帶：recall ≥0.7 → 轉正；0.5–0.7 → 攤給人裁（帶噪音度）；<0.5 → 殺（或裁掉表現差的源降級重測一次）。
- toolchain 自庫如實記天花板：`test_lumos.py` 單檔巨測 → map 退化為「全部指向一檔」；`scripts/lumos` 無副檔名不入候選 src——本 repo 最重要的檔在 map 外。兩者**不得當成效證據**，自庫僅驗機械正確性。

## 實務隱患

- naming 慣例漂移（專案不用 `*Tests` 慣例）→ 源 A 空集，cochange 兜底；Landmark 驗證會暴露。
- 內容引用源在大測試檔上的掃描成本 → 200KB 上限＋stderr 記帳（[S1]）。
- cochange 的「共改≠覆蓋」語意誤讀 → conf 承接挖掘值、輸出標 sources 讓人看得到邊的出身。
- map 陳舊誤導 → [S2] 雙訊號軟提示（祖先鏈＋build 後候選檔異動）。
- 情境命名整合測試（`RedeemIdempotencyTests` 類）naming/內容雙源都可能落空 → cochange 是唯一兜底，[S4] 分層抽樣如實量測。
