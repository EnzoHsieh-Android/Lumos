# 新分支首推會擋的閘改用真起點_計劃

白話:推送前的掛鉤在推「遠端還沒有的分支」時,沒有舊版本可以比,就拿空樹(什麼都沒有)當起點,等於把整個 repo 當成這次的新改動。只提醒的檢查多掃無妨,但會擋的那幾步因此誤擋:風險分級被整個 repo 的舊寫法拉成高風險、新增告警閘把全 repo 的舊告警算成新的(rtb 2026-10-06 推 cap-retro 被 715 條擋下)、doctor 把別人逾期的預告合約當成你碰到的。lumos 裡已經有一支「起點只在這裡算一處」的函式,會跟主線比、找出這次真正的新改動,存量漂移檢查一直在用。這次給它開一個指令,讓掛鉤在新分支首推時用它算起點。

依據:Enzo 2026-10-06 裁「修工具」;rtb 會談同日回報的重現(本機 `lumos code-loop check` 自己算 merge-base 時沒有新增告警、可以推;同一個頂端經推送前掛鉤就被擋)。

PRIOR-ART: lumos 的 `_push_range_start`(推送閘接漂移檢查時定下「起點只在這裡算一處」,存量漂移檢查與 `note-audit reread-check` 經 `--push-remote/--pushed-ref` 在用;CI 的 code-loop check 對全零起點走的 `_lens_push_base` 也是跟主線分岔點同一個想法)。本案只給它開一個印範圍的指令,掛鉤照漂移檢查的帶法傳遠端名與遠端 ref。
RETIRE-IF: pitfalls、impact、spec-gate、code-loop check 都自己吃 --push-remote/--pushed-ref(或全零起點)時,`lumos push-range` 這個中間指令與掛鉤的 `pp_block_range_for` 一起撤掉,改成直接把推送參數傳給各指令。

## 範圍

- 做:新指令 `lumos push-range --diff <遠端舊值>..<頂端> --push-remote <遠端名> --pushed-ref <遠端 ref> [--repo <根>]`:呼叫 `_push_range_start`,stdout 印一行範圍——有起點印 `起點..頂端`;頂端已在主線上(沒有新東西)印 `頂端..頂端`;git 查詢失敗(判不了)或起點是空樹時,一律印「這個 repo 自己的空樹編號..頂端」(`_drift_empty_tree`,SHA-256 的 repo 也對);說明印到 stderr。參數錯、少帶 --push-remote 或 --pushed-ref、不在 git 專案 → rc2。
- 做:掛鉤新函式 `pp_block_range_for <遠端舊值> <本地頂端> <遠端 ref>`:先照舊算 `pp_range_for`;只有遠端舊值是全零、而且遠端 ref 是 `refs/heads/*` 時,才呼叫 `lumos push-range`(stderr 丟掉);rc 128 以上 → 照 `pp_stop_if_signaled` 停下;rc0 而且印出的一行符合「40 或 64 位十六進位..同長十六進位」→ 用它;其他(舊版 lumos 沒有這個指令、失敗、怪輸出)→ 用 `pp_range_for` 的結果(空樹,同今天),並印一句「新分支首推的起點沒算出來,照舊從空樹比」。
- 做:吃 `pp_block_range_for` 的:`pp_touched_file`(餵 doctor 的 `--touched-from`,會擋)、`impact_once`(結果經 `--from-json` 餵 code-loop check 的受波及合約測試,高風險時會擋)、那次 `pitfalls --diff --json`(決定分級、測試子集與 advisory 旗標)與高風險列命中那次、`spec-gate --push-check`、`code-loop check --diff`、兩處 `loop escape --range`(跟 code-loop check 同一個範圍,記帳才對得上)。
- 做:`pp_touched_file` 在所有 ref 的 `git diff --name-only` 都成功、結果卻是空的(這次推送的分支已整段在主線上)時,照樣交一份空清單給 doctor(意思是「這次什麼都沒碰到」);任何一個 ref 的 diff 失敗才照舊不交清單(全擋)。
- 不做:遠端舊值本機找不到(force-push 後沒 fetch)、推標籤——照舊從空樹算(寧可多擋)。
- 不做:標籤路徑的風險提醒、`bound_tests_advisory`、`test-layers` 照舊用 `pp_range_for`(只提醒)。
- 不做:每支檔有家與筆記形狀擋(各有自己的起點推導;改它們是 [[Issues/推送前其他閘的範圍在合過主線時會多算]] 的範圍)。
- 不做:存量漂移檢查、回頭重讀(已經自己帶 `--push-remote/--pushed-ref`)。
- 不做:CI、一般增量推送的範圍。

## 做法

1. lumos 新增 `cmd_push_range(repo, diff_range, push_remote, pushed_ref)`(放在 `_push_range_start` 旁,家是 [[Systems/存量漂移守衛]]):`--diff` 照 `_lens_range_ok` 解析,頂端轉完整 sha;呼叫 `_push_range_start`;回 None → 印 `頂端..頂端`;回 `_PUSH_START_UNKNOWN` 或 `_EMPTY_TREE_SHA` → 印 `_drift_empty_tree(root)..頂端`;其他印 `起點..頂端`。唯讀、不寫治理帳。`--push-remote`/`--pushed-ref` 必帶(值可以是空字串:手動跑掛鉤時遠端名是空的,`_push_range_start` 照存量漂移檢查的規矩處理):掛鉤一定帶,沒有不帶的呼叫端,不照 drift check「都不給也行」的寬鬆規矩。
2. 掛鉤新增 `pp_block_range_for`(見範圍);在 `$(...)` 裡跑時把 rc 帶出來(例如輸出最後一行附 rc,或先寫暫存檔),讓外層能照 `pp_stop_if_signaled` 停下。
3. 迴圈裡每個 ref 算一次 `_brange`(推刪除 ref 的那一行本地頂端是全零,迴圈開頭就跳過);上面「範圍」列的呼叫改吃 `_brange`。`pp_touched_file` 改呼叫 `pp_block_range_for`,並照範圍第 4 條處理空清單。
4. 註解與舊句同步:`_range` 那段、`pp_range_for` 與掛鉤 309–312 行一帶講「新 ref 保守掃全部」的註解、每支檔有家那段「兩套刻意不同」的註解;[[Systems/每支檔有家]] 講兩套範圍的那條 KEY、[[Systems/bound-tests-gate]] 講 impact_once 範圍的那句、[[Systems/pitfalls-code-loop]] 講推送範圍的那句、`_lens_push_base` 與 `_push_range_start` 的說明;舊單的 DECISION 行。
5. 新增頂層指令的連帶:`skills/lumos-project-notes/commands/` 補 `lumos push-range` 一條、ARCHITECTURE.md 與 `skills/lumos-project-notes/reference.md` 的指令數加一(指令索引與指令數兩支守衛測試會盯)。
6. 舊單 [[Issues/推新分支時風險分級拿空樹當起點]] 結案:寫明採用的方向、當初擔心的「解析預設分支會變鬆」怎麼被 `_push_range_start` 的主線候選與失敗退回空樹處理掉、只修了新分支首推。
7. 掛鉤是錨點檔,改完要 `lumos anchor approve`。

## 實務隱患

- **舊版 lumos**:`lumos update` 會同批更新掛鉤與 lumos,新掛鉤配舊 lumos 只在少數情況出現;那時 `push-range` 不存在 → 退回空樹(同今天),只多印一句說明。
- **找不到主線**(預設分支不叫 main/master 又沒有遠端 HEAD、遠端名是網址或空的):`_push_range_start` 對全零起點回空樹 → 同今天。
- **時間**:每個新分支首推多兩次 lumos 啟動(`pp_touched_file` 與迴圈各一次,實測單次約 0.8 秒)。
- **CI 後盾**:CI 只在推 main 與合併請求時跑,code-loop check 那步只在推 main 時跑;新分支首推本機放行之後,要到合進 main 才有 CI 的 code-loop check 再看一次(那時用的是跟主線的分岔點,同一個想法)。
- 已排除:金流:只改推送前掛鉤的範圍推導與一個唯讀指令,不碰任何金流
- 已排除:對外送出:不連網、不送任何東西出去
- 已排除:不可逆:只改掛鉤與一個唯讀指令,退回提交即恢復
- 守衛面:新分支首推時會擋的那幾步看的範圍變小(從整個 repo 變成跟主線的分岔點之後);起點由存量漂移檢查已在用的那支算,判不了、找不到主線、指令不存在一律退回空樹(多擋);其他推送形狀不變。

## 驗收條款

- [S1] 當推一個遠端還沒有、只比主線多一個乾淨提交的新分支,而主線本身有大量會被當成新增告警的舊寫法時,推送前掛鉤 應 放行,而且風險分級只算那一個提交 [test:t_prepush_new_branch_block_range]
- [S2] 當新分支裡那一個新提交真的帶進新告警時,推送前掛鉤 應 照擋 [test:t_prepush_new_branch_block_range]
- [S3] 當新分支先合過主線(主線在分岔後又多了會被當成告警的提交)再首推時,推送前掛鉤 應 只算分支自己的提交、放行 [test:t_prepush_new_branch_block_range]
- [S4] 當新分支的頂端已整段在主線上時,會擋的那幾步 應 跑空範圍並放行,doctor 應 收到空的觸及清單 [test:t_prepush_new_branch_block_range]
- [S5] 當遠端已有那個分支、遠端舊值本機找不到、或推的是標籤時,會擋的那幾步的範圍 應 跟改之前一樣 [test:t_prepush_new_branch_block_range]
- [S6] 當 `lumos push-range` 不存在或失敗時,掛鉤 應 退回空樹起點並印一句說明;被訊號中斷(rc 128 以上)時 應 停下不放行 [test:t_prepush_new_branch_block_range]
- [S7] 當 `lumos push-range` 收到頂端已在主線、找得到分岔點、git 失敗、SHA-256 repo 找不到主線四種情形時,應 各印「頂端..頂端」「分岔點..頂端」「這個 repo 的空樹..頂端」「SHA-256 空樹..頂端」;少帶 --push-remote 或 --pushed-ref 應 rc2 [test:t_push_range_cli]
- [S8] 當掛鉤裡 `pp_touched_file`、`impact_once`、分支路徑的兩次 `pitfalls`、`spec-gate --push-check`、`code-loop check`、兩處 `loop escape` 任一處沒有吃 `_brange` 時,守衛測試 應 點名那一處並紅 [test:t_prepush_block_range_callers]

## 回退

退回本案的提交即可:只改推送前掛鉤與新增一個唯讀指令,退回後新分支首推恢復從空樹算(會再被誤擋)。消費專案要重跑 `lumos update` 才拿到新掛鉤;退回也一樣要更新一次。

## 天花板

1. 只修新分支首推;一般增量推送合過主線、重定基底後 force-push(舊值還在本機)時的多算照舊(另一張 Issue)。
2. 每支檔有家與筆記形狀擋仍用各自的起點推導;掛鉤裡同時有兩種起點,直到收斂。
3. 找不到主線的 repo(主線叫 develop/trunk 又沒有遠端 HEAD)新分支首推照舊從空樹算。
