# 新增告警閘_計劃

> 白話：讓檢查工具在每一次推送前真的跑一遍，而且**只擋你這次弄出來的新問題**，舊問題不管。誤報一定會有，所以放行的門第一天就要開好、而且走正式管道會留下紀錄。

## 現況：缺的比想像中少

| 已經有的 | 缺的 |
|---|---|
| 標準格式的橋（工具吐 SARIF、核心解析合併） | **現況**：自動路徑一律帶「不跑 linter」，只有手動敲才跑 |
| 按改動檔的副檔名挑該跑哪些命令 | **現況**：告警只拿來墊高風險分級，自己不會擋——本計劃 [S4] 就是要補上「自己會擋」這一層 |
| 跑命令、逾時保護、解析結果 | 沒有放行管道，誤報只能繞過整個檢查 |
| 把告警對到這次改動 | 對法是「行級過濾」，會靜默漏掉（見那篇事故） |

## 實測數字（2026-09-13，本機）

這些數字決定了下面幾條的門檻，不是拍腦袋定的：

| 量什麼 | 結果 | 影響哪一條 |
|---|---|---|
| 843 行的檔，151 條社群規則 | 1.8 秒（幾乎都是啟動成本） | 正常大小的檔沒有速度問題 |
| 26718 行的主程式，同一批規則 | **105 秒**，跑兩次就三分半 | [S6] 單檔大小上限變成必要配套 |
| 線上規則庫、未登入 | 可用，151 條規則，含下載約 2 秒 | 不需要帳號 |
| 沒有副檔名的檔（掃目錄時） | **靜默跳過**；明確指名就會掃 | [S1] 一定要傳明確的改動檔清單 |
| 基準比對對未提交改動的影響 | 不動改動、不動未追蹤檔、不建暫存 | 安全，但文件說「髒了會拒跑」與實際不符 |
| 首次真跑的命中 | 1 條，是誤報（對刻意設 0700 的目錄建議改成 0644） | [S5] 放行管道不能延後 |

## 條款

> r2 折入後的版本。r1 把原稿打穿一次、r2 抓到「修正本身引入的反向錯」，兩輪的重寫理由都寫在「審計修正紀錄」。

- **[S1] 宣告檔只擴充一個佔位符，命令必須吃得下檔案清單。** 現有的輸出檔佔位之外，新增 `{LINT_FILES}`（這次要掃的檔案清單，**多檔各自跳脫後以空白相接**，不是整串一起跳脫）。**這一批不做「讓工具自己比基準」那種模式**——那種模式的工具實際上是直接讀當下的工作樹、只用版本控制做過濾，跟 [S2]「兩邊都掃快照」是互斥的兩套做法，混在一起會讓保證破功；等這一批站穩再評估。**命令裡沒有檔案清單佔位的，核心無法為它做基準比對**：那**一條命令**的告警只報不擋（不是整道閘降級——舊宣告不擋人，不等於它可以拖累同一個專案裡合格的新宣告），並明說「要進閘就在宣告裡加上檔案清單佔位」。[test:t_lint_new_declaration]
- **[S2] 兩邊都從版本庫解出快照來掃，而且解在專案底下。** [test:t_lint_new_baseline] 取基準版與被推送版兩個版本，**逐檔**把內容取出來寫進兩個暫存目錄（逐檔取，不整批打包——整批打包時只要清單裡有一個檔在基準版不存在，整批會失敗；基準版沒有的檔就是新檔，它的告警全部算新增）。
  - **暫存目錄開在專案根底下、每次隨機名、加進忽略清單。** 不放系統暫存區：檢查工具找設定檔的做法是「從被掃的檔案往上找」，解到專案外面會讓它**完全找不到專案的規則設定、退化成只用預設規則跑**，比對出來的結果不可信。開在專案底下，往上找就會找到專案根的設定。隨機名是為了兩個工作階段同時跑不會讀到對方的檔案。
  - **兩端都必須解析得出版本代號**，任一端解析不出（例如只給單一參考點、終點其實是工作樹）就是環境不可用，不硬猜。
  - 不碰版本控制的工作樹註冊機制（那是全域狀態，這台機器上同一個 repo 有別的工作階段在用）。
- **[S3] 執行層要把「在哪裡跑」與「路徑相對誰」拆成兩個參數。** 現有的執行函式用同一個參數同時決定兩件事，直接沿用會讓兩次掃描算出帶著各自暫存目錄前綴的檔名、**指紋永遠比不到、每一條舊告警都被當成新的**。所以：工作目錄維持專案根，路徑基準各自傳自己那份暫存目錄，還原成專案相對路徑再進指紋。**新增的那個參數必須有預設值（不給就等於沿用工作目錄）**——這支函式有兩個既有呼叫點與七處既有測試都用單一值呼叫，改成兩個必填參數會讓它們全部爆掉。[test:t_lint_new_pathmap]
- **[S4] 指紋用多重集合比對，算次數不算有無；正規化保留相對縮排。** 指紋＝規則代號＋專案相對檔名＋正規化後的片段。**比的是同一個指紋出現幾次**：基準版一次、現在版三次就是新增兩條——用「有沒有出現過」會讓複製貼上多出來的問題被吃掉。正規化：去掉行尾空白、內部連續空白壓成一個、丟掉空行，**前導空白原樣保留、不做任何縮排正規化**。這是刻意選誤報而不選漏擋：保留縮排的代價是「整批重新縮排」的提交會產生一批假新增（有放行管道可處理，或那次把閘關掉）；抹掉縮排的代價是「同一段程式碼被搬進另一個會執行的區塊」比不出來——那是行為改變卻無聲放行，沒有補救。[test:t_lint_new_fingerprint]
- **[S5] 片段取不到時的退路要明講。** 工具沒附片段的（實測：主流 Python 檢查器完全不附），核心自己照起訖行去讀那幾行補上。**行號缺失、小於一、或超出檔案長度時，就是取不到片段**——那條退到「規則代號＋檔名＋訊息」的次數比對，並在輸出裡標明它是弱比對。[test:t_lint_new_weakkey]
- **[S6] 第四道判定，不看風險分級。** 在代碼審那一關的判定序列裡，排在表態之後、留痕之前。**跟表態一樣對每一次推送都跑**——願景要的是覆蓋每一次提交，只在高風險跑就不成立。既有的風險分級計算維持原樣（照舊快算、不跑檢查工具），這道閘是獨立的一條路。[test:t_lint_new_gate]
- **[S7] 放行管道，要上鎖。** 一條指令把某個指紋標成已放行、要寫理由，紀錄寫進 `.lumos/lint-waivers.json`（**這個檔要進版本控制**——只活在本機的話，換一台機器或在遠端跑就整批復活擋人；被忽略的是 [S2] 那個 `.lumos/lintbase-*` 暫存目錄，不是這個檔），同時記一筆治理帳。檔案結構：一個物件、底下一個清單，每筆帶指紋、規則代號、檔名、理由、誰放的、時間。**讀-改-寫要上鎖**（沿用既有的寫入鎖，它的鎖鍵是路徑雜湊、傳哪個檔就鎖哪個檔，不會跟既有用途互撞）——只做原子換名不夠，兩個工作階段同時放行不同指紋，後寫的會整份蓋掉先寫的。放行綁指紋不綁版本。[test:t_lint_waive]
- **[S8] 單檔上限同時看行數與位元組數；超過不是免費放行。** 只看行數會被「整支檔只有一行」的壓縮檔騙過去。超過門檻的檔**明白說出來**（幾行、幾位元組、超過哪個門檻），而且**要走放行管道登記才算過**——把「檔太大」歸進自動放行等於公告「把檔案撐大就能繞過這道閘」，那是可重現的繞道，不是偶發的環境問題。登記一次之後那支檔就不再每次擋人。[test:t_lint_oversize]
- **[S9] 兩類失敗分開處理，對齊既有的兩套慣例。** [test:t_lint_undone_classes]
  - **環境不可用**（工具沒裝、命令逾時、拉不到規則、版本代號解析不出、放行檔讀不了）→ **自動放行並自動記一筆帳**，不要求人手寫說明。這跟既有合約測試遇到環境問題的做法一致。**閘名固定用 `lint-new`，而且要登記進既有的閘名清單**——沒登記的閘名，記帳那支會拒寫、只印一行警告就算了，「有記帳」這句話會變成空頭支票。
  - **真的有未放行的新增告警**、**檔太大沒被檢查** → 擋，逃生門是人手動放行並寫理由。
  - **「命令沒有檔案清單佔位」不在這張表裡**——那是 [S1] 的逐命令降級，只影響那一條命令，不讓整道閘降級。
  - **放行檔讀不了時不可以當成「沒有放行紀錄」**——那會讓所有既有放行瞬間復活、整批擋人。
- **[S10] 時間預算要能真的中斷，而且每條命令有保底時間。** 剩餘預算要傳進命令執行層，單條命令的逾時取「既有上限」與「剩餘預算」兩者較小值。**但要有保底，而且數值與最終判定都寫死**：整條閘的總預算預設 300 秒、單條命令保底 30 秒，兩者都可在設定檔調。剩餘預算不足 30 秒時，**不要用一個必然逾時的值去跑剩下的命令**——停下來，把沒跑到的命令列出來，**判定跟「檔太大」同一類：擋，逃生門是留痕說明**。不歸進自動放行——那會變成「第一條命令慢，後面全部無聲放行」的沉默繞道。[test:t_lint_budget]
- **[S11] 改名另開一支自己的差異查詢。** 開啟改名偵測，改名的檔用它在基準版的舊路徑取內容。**另開一支只給這道閘用的查詢，不動既有那支共用的**——那支同時餵給風險掃描、棧別提問、架構對照好幾個消費者。新設計比的是兩份快照的差集、不依賴「哪幾行算新增」，所以既有那支不需要動。[test:t_lint_rename]
- **[S12] 整道閘要有關掉的開關，環境變數叫 `LUMOS_SKIP_LINT_NEW`。** 跟既有每道閘的命名慣例一致（既有的是 `LUMOS_SKIP_` 開頭接閘名）。[test:t_lint_killswitch]
- **[S13] 設定放 `.lumos/config.json` 的 `lint_new` 區塊，不放 `.lumos/lint.json`。** 三態（擋／只報告／關閉）、總預算、單條保底、單檔行數與位元組門檻全部放這裡。**不可以放進 `.lumos/lint.json`**——那個檔的每個頂層鍵都被當成「副檔名→命令清單」嚴格驗證，多一個設定鍵會讓健檢對每個採用的專案判紅。既有的棧別提問設定就是走 `.lumos/config.json` 的區塊，照抄那個做法。[test:t_lint_gate_modes]
- **[S14] 自動放行要被數，健檢要唸。** 健檢多一項：這個專案最近自動放行了幾次。自動放行是已知的繞道向量，沒有人去數就等於沒有守衛——這句話本身也要有測試釘住，不然又是一張空頭支票。[test:t_lint_autopass_counted]
- **[S15] 工具鏈自己要接上，否則交付即零實證。** 這個 repo 目前一個檢查工具都沒宣告（健檢已經在唸），閘做完也不會對任何東西生效。交付要包含替這個 repo 宣告檢查工具——**但這需要在這台機器上裝東西，屬於人的決定，不自作主張**。[manual:問過人再裝,裝完跑冒煙驗證]
- **[S16] 翻案與文件同步。** 推翻「擋推鏈恆不跑檢查工具」那條裁定並寫明翻案理由；同步代碼審的 skill、指令速查、上手文件、兩份 README 的說明。[manual:文件同步逐項核]

## 刻意不做

- **不接管 linter 的安裝。** 消費專案自己裝、自己宣告，核心只認格式——這是既有定位，不動。
- **不做離線快取。** 人裁「不管離線」，沒網路就判跑不動、留痕。
- **不按嚴重度分級擋。** 嚴重度是各工具自己標的、跨工具不一致；判準只有「是不是這次新增的」。
- **不動那四十四題棧別提問。** 規則跟提問分工不同，兩邊都留。

## 實務隱患

逐類答，判「不碰」也要寫理由：

- **資源（暫存目錄）**：兩份快照要解到磁碟。**開在專案根底下、每次隨機名、加進忽略清單**——不是系統暫存區：檢查工具找設定檔靠「從被掃的檔案往上找」，解到專案外面會讓它找不到專案規則、退化成預設規則跑。隨機名是為了兩個同時跑的工作階段不會讀到對方的檔案。正常結束與一般中斷靠收尾清理；**被強制砍掉（機器休眠判死、外力強殺）時清理不會執行**，殘骸會留在專案底下那個被忽略的目錄裡，這點老實承認：每次名字不同、不會污染下一次比對，另外每次開跑前順手清掉同前綴、超過一天的舊目錄。
- **資源（子行程）**：跑檢查命令是開子行程。沿用既有那條路的保護（獨立行程組、逾時到整組砍掉），不自己再造一套；**差別是逾時值要改成可以由呼叫端指定**，否則整條閘的時間預算管不到正在跑的那條命令。
- **併發（多工作階段共用同一個工作目錄）**：這台機器上同一個 repo 同時有別的工作階段在用。所以不碰版本控制的工作樹註冊機制（那是全域狀態），**暫存目錄開在專案根底下(見 [S2])而不是系統暫存區**——解到專案外面會讓檢查工具找不到專案的規則設定。**兩次掃描都用版本庫裡的快照而不是當下的工作樹**，所以掃描期間別人改檔不會讓比對錯位。
- **併發（放行檔的寫入）**：放行紀錄是讀了再改再寫的檔。**原子換名只保證檔案不會半寫，不保證兩筆更新都留下來**——兩個工作階段同時放行不同指紋，後寫的會整份蓋掉先寫的，一條放行就這樣消失。所以要沿用既有的寫入鎖，兩件事都做。
- **效能**：整條閘有時間預算（[S10]），單檔有大小上限（[S8]），超過都明說不靜默。推送前那關已經十一分鐘，加上去的秒數要實測。
- **回滾**：整道閘有關掉的開關（[S12]），跟這個判定序列裡其他每一道閘同級。逐條放行不是止血手段。
- **不碰的類**：金流、對外寄送、正式環境不可逆操作——這個計劃一項都不碰，純粹是本機與 CI 的檢查流程。

## 誠實邊界

- **零真專案實證。** 上面所有數字都是在工具鏈自己這個 repo 上量的。誤報率、實際擋下什麼、放行比例，要等第一個消費專案接進來才知道。
- **本 repo 的主程式不會被社群規則覆蓋到**——它兩萬六千行，超過單檔上限。這是刻意的取捨（不這樣做推送前那關會多三分半），但意思是工具鏈自己的核心檔只有快的那些檢查看得到，這一條要寫進交付說明，不要讓人以為全 repo 都被蓋住了。
- **環境不可用一律自動放行，這是可以被利用的。** 工具沒裝、逾時、拉不到規則都走自動放行（只記一筆帳）。也就是說，**把檢查弄慢或把工具移掉，就能繞過這道閘**。選這條是為了跟既有的閘一致（環境問題不該把人鎖在門外），代價是它不是防惡意的機制，只是防疏忽的機制。**配套是健檢要唸「這個專案最近自動放行了幾次」**——沒有人去數，這句話就是空頭支票。
REVISIT:2026-12-13 回頭看自動放行的次數:如果某個專案的自動放行占比高到讓這道閘形同虛設,就要把「工具沒裝」從自動放行改成要留痕
- **（已移除）檔太大不再是免費放行**：那會變成「把檔案撐大就能繞過」的可重現繞道，改成要走放行管道登記一次。
- **同一支檔裡字面相同的多處，會被同一條放行一起蓋掉。** 內容相同、判斷也該相同，這是刻意的；但如果兩處相同的程式碼其實該有不同判斷，放行會蓋過頭。
- **新檔與搬檔會整批算新增。** 一個在基準版不存在的檔，它所有的告警都算新增。從別處搬進來的舊程式碼會一次擋一大批，只能靠放行管道處理。這是「只擋新增」這個判準的固有代價，不是 bug。
- **整批重新縮排的提交會產生一批假新增。** 指紋保留前導空白，所以重新縮排會讓既有告警的指紋全變。這是刻意選的方向——**寧可誤報，不要漏擋**：誤報有放行管道、也可以那次把閘關掉；而抹掉縮排造成的漏擋（同一段程式碼被搬進另一個會執行的區塊、文字沒變）是無聲的，沒有補救。
- **檢查工具太慢會直接擋人。** 預算用完、剩下的命令沒跑到，判定是擋不是放行。這會有摩擦，但「沒檢查到就自動過」等於公告一條沉默的繞道。常撞到的話該修的是宣告（把慢的命令拆小、或只掃改動檔），不是放寬這道閘。
- **放行永久有效**是已知的設計缺口：數量會累積，只有健檢會唸。真的變成問題再加期限。
