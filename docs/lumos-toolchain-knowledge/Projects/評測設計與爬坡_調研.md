# 評測設計與爬坡_調研

> 白話:官方出了一篇「怎麼設計評測、怎麼一步步把分數推高又不騙自己」的文章。我們的評測做法大半已經自己長出來了,這篇的用處是當體檢表。拿它的健檢清單對情境探針(量「AI 有沒有照規矩先查圖譜」那套題)做了一次體檢,找到三個會讓數字誤導人的問題,全部只用舊資料、沒花額度。

PRIOR-ART: 官方 claude-api skill 的 build-eval / hillclimb / eval-audit 三份指南(Claude Code 2.1.284 內建;沒有新依賴,報表產生器是 skill 自帶的單檔 node 腳本,不進 repo)。我們既有的同形狀件:情境探針、9/2 對照實驗的題目鑑別力分類、檢索評測的公開/保留切分。
RETIRE-IF: 下面的條款落地後,連續三次改規矩的前後量測都沒有用到「雜訊寬度」或「保留題」這兩個數字做出任何取捨(=條款沒有改變決策),就把條款降回參考、不再當閘。

## 文章講什麼(只留跟我們有關的)

- 好評測四條:題目像真實使用、越強的模型越高分、最強設定離滿分有距離且差距不是壞題造成、重跑不亂跳。
- 別因為「現在的模型答不出來」收題——量到的是那個模型的弱點形狀;收題要說得出為什麼難。
- 爬坡:開跑前先確認雜訊比「值得採用的最小進步」小;每輪只改一處、改根源;公開題升保留題平→退回;卡住兩三輪先把失敗分類(常抓到壞題、評分器寫錯);最後附信賴區間,落在雜訊裡就說不建議合併。
- 官方指南比文章多兩條具體紀律:撞到上限或逾時的場次**不准算成失敗**,要單獨記、排除在平均外;提出改動的那一方**只准看公開題的紀錄**,保留題的內容一眼都不能看(否則等於洩題)。

## 用官方健檢清單審情境探針(2026-09-29,只讀舊資料)

照嚴重程度排。前三條會讓數字直接誤導決策。

1. **撞到回合上限被算成「沒照規矩」。**
   - 探針的 claude 執行器(`scripts/scenario_probe.py` 的 run_one)有記結果事件的 subtype,但判分沒用它;Codex 執行器反而會把逾時標成「儀器例外、不算分」,兩邊不一致。
   - 近兩次週抽(9/21、9/28)四個失敗裡三個是 error_max_turns,其中「設計寫進圖譜」那題 9/28 跑了 282 秒、19 個動作、最後回覆是空的——它還沒做到要寫的那步就被砍了。
   - 9/2 對照實驗 168 場裡有 10 場撞上限;s22 那題兩組各三場全撞上限,當時被分類成「弱/不穩」,實際上是這題在 18 步內根本做不完。
   - 官方指南把這類歸為「儀器問題,先從分母拿掉」。
2. **判準跟現行紀律打架。**
   - 30/53 題的「禁止先做」清單含 Grep/Read,是「第一個工具呼叫是 lumos」時代的判準;2026-09-21 紀律改成程式碼為主,第一步是先讀程式碼。
   - 9/28 週抽那題問「這個常數是幹嘛的、哪些地方靠它」,後半句是程式碼答得了的事。AI 先 grep、再把兩次事故的來龍去脈講完整,是新紀律要的行為,卻判不及格。
   - [[Projects/Lumos定位_程式碼為主脈絡為輔_計劃]] 的〈探針那條線索的結論〉只處理了題目腐爛,沒提判準本身要不要跟著改(是否有別處處理過,見〈獨立查核〉)。
3. **週抽樣本太小,通過率起伏是雜訊。** 8 題×1 次,粗估正負 35 個百分點;歷史紀錄 7/8、6/8 之間的變化沒有意義。週抽能用來抓「整批全垮」這種大事,不能用來判「規矩變好變壞」。
4. **題庫單向。** 53 題裡 52 題期望「敲 lumos」,唯一例外是「說沒有之前先派 agent 查」那題。官方稱這叫 both-directions coverage:只量「該查時有沒有查」,不量「不該查時有沒有亂查」,「每次都先查」就能拿滿分。
5. **近半題目沒有鑑別力。** 9/2 實驗 28 題裡 13 題兩組都全過、1 題兩組都全不過,對「這條規矩有沒有用」不提供訊號。官方建議爬坡時只跑有鑑別力的題,最後才在全套上確認一次。

沒找到問題的:沙盒隔離(拔遠端、pre-push 硬擋、每題之間清工作樹)比官方要求的「每次乾淨環境」更嚴;用量上限已經標成儀器例外、不算分;題目腐爛已有跑前檢查。

## 官方報表試跑

- 把 9/2 對照實驗的舊結果轉成官方報表吃的格式:拔掉規矩那組當基線、現況那組當第一版,撞上限的場次標成截斷。依題目鑑別力分類分層,用固定種子隨機切成公開 18 題、保留 10 題。轉檔腳本與報表放在該次對話的暫存目錄,沒進 repo。
- 重算結果(逐題平均後取成對差,95% 區間):全部 +35.8 個百分點、正負 17.8;公開題 +31.5、正負 20.8;保留題 +44.4、正負 34.4。
- 讀法:結論方向不變,但保留題只有 9 題有分數,區間寬到正負 34——**題目太少時,切出保留題就量不準**。官方的解法是加重跑次數或加題,不是放棄切分。
- 官方的精簡版報表只有逐題表格和紀錄連結,沒有圖表和逐字稿檢視(完整版要另外安裝才有)。對我們來說不比既有的摘要檔多多少,**真正有用的是它逼你把「截斷」和「分組」寫成欄位**。

## 條款(提案,可驗收;都還沒做)

1. **截斷不算失敗。**(2026-09-29 已落地:[[Projects/探針判準對齊程式碼為主_計劃]]) 撞回合上限或逾時的場次標成截斷,排除在通過率外、另外計數;某題截斷率過半就視為題目或步數上限有問題。驗收:造一場假的撞上限結果,判分結果是「截斷」而不是「不過」。
2. **判準跟紀律對齊。**(2026-09-29 已落地,同上;實際做法是讀碼類禁令整批拿掉、寫入與替代類保留,只有 v04 一題是純程式碼題)30 題的「禁止先做」逐題重審:問「為什麼、決策、事故」的題保留先查圖譜;問「現在怎麼運作、哪裡用到」的題拿掉 Grep/Read 禁令,改成看答案有沒有帶到程式碼給不了的脈絡。驗收:9/28 那場的原始紀錄套新判準會過。
3. **先算雜訊再下結論。** 任何用探針或檢索評測做「改前改後」的決定,計劃筆記裡要並列兩個數:這次 題數×次數 的雜訊寬度,和最小想採用的進步;前者比後者大就不准下結論。驗收:下一篇用到探針的計劃有這兩個數。
4. **每輪都看保留題。** 爬坡式改動(一次改一處、連改好幾輪)時,題目隨機切公開與保留(依分類分層,不准照分數挑);每輪兩邊都跑,公開升保留平就退回;提出改動的一方只看公開題的紀錄。驗收:每輪紀錄有兩個分數。
5. **強弱對照當評測健檢。** 新題庫或改判準後,用強弱兩種設定各跑一次(例:強模型對便宜模型,或有規矩對沒規矩);弱的反而高的題先查題,不先查模型。
6. **補反向題。** 至少加幾題「該直接讀碼、查圖譜是浪費」的情境,判準是沒有不必要的 lumos 呼叫,並且答對。驗收:「永遠先敲 lumos」這種策略在新題庫上不能拿滿分。
7. **收題寫理由。** 新題要寫一句「這題為什麼難、為什麼重要」;不收只因為「現在會失敗」的題。
