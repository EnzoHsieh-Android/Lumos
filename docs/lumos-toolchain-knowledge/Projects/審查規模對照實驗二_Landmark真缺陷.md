# 審查規模對照實驗二（Landmark 真缺陷）

## 為什麼要有第二版

[[Projects/審查規模對照實驗]]（第一版）的主要指標不支持假說，但它有**三個致命瑕疵**，使得「不支持」這個結論本身也不夠可信：

| 瑕疵 | 第二版怎麼修 |
|---|---|
| **沒有真答案**——不知道材料裡有幾個真缺陷，只能比相對數量，且由我自己裁決 | 用 **Landmark 上線後才發現的真缺陷**當針，結果變成**二元命中／未命中**，不用我裁決 |
| **不同段是不同的碼**，缺陷密度天生不等 | **同一根針、不同大小的草堆**（用無關的前端變更填充），針的位置固定在 ~40% 深度 |
| **半數 findings 靠讀未來 git 歷史找到** | 實驗 repo 用 `git archive` 重建成**只有一個 commit**，修法的關鍵字（`IpMaxSendsPerHour`／`UPDLOCK`）實測查無 |

## 材料

| 針 | 來源 | 缺陷 | 真實後果 |
|---|---|---|---|
| **N1** | `72f4687c`（267 行） | SMS 註冊發碼的 rate limiter 是 **per-IP FixedWindow 5 次/小時** | 賣場 WiFi／電信 CGNAT 共用對外 IP → **同 IP 第 6 人起一小時發不了驗證碼**。2026-07-14 上線後才發現 |
| **N2** | `d7859c33`（76 行） | 作廢冪等檢查是**普通 SELECT**、走預設 READ COMMITTED | 同一 `posOrderNo` 兩筆**同時**在飛可都通過 voided 檢查 → 各自退款 → **重複退款**（TOCTOU） |

| 條件 | N1 | N2 |
|---|---|---|
| **S** | 267 行 ≈3.9K token | 76 行 ≈1.1K |
| **M** | 1279 行 ≈13.2K | 1088 行 ≈10.4K |

## ★預先登記：命中判準（派工前寫死）★

**N1 命中** ＝ 報告指出「**以 IP 為維度限流，會誤殺共用出口 IP（NAT／CGNAT／賣場或公司 WiFi）的不同使用者**」。
- ★不算命中★：只說「加了 rate limiter」、只談 `X-Forwarded-For` 可偽造、只談限額數字大小。

**N2 命中** ＝ 報告指出「**先查後做之間不是原子的，併發下兩筆可同時通過檢查 → 重複退款／重複 CustTransfer**」（TOCTOU／race／缺鎖或交易隔離）。
- ★不算命中★：只說「加了冪等檢查」、只談回傳碼語意、只談錯誤訊息。

判定由我做，但**判準是二元且事先寫死的**，比第一版「我裁決 finding 真假」窄得多。

## ★預先登記：判讀規則★

1. **主要指標** ＝ 各 size 格的命中率（每格 n=6：2 針 × 3 重複）。
2. **支持假說** ＝ 命中率隨規模**單調下降**（S ≥ M ≥ L，且 S 明顯高於 L）。
3. **不支持** ＝ 打平、或非單調。
4. **無論結果如何都寫回本節點與 [[Systems/canary-audit]]**，不得只在支持時才記。
5. 若某根針**在所有 size 都 0 命中**（針太難）或**都 100% 命中**（針太顯眼），該針**不納入主要指標**，另記為「針校準失敗」。

## ★結果：假說再次不成立，而且這次的設計嚴謹得多★

| 條件 | ≈token | 命中 / 派工 | 命中率 |
|---|---|---|---|
| **S**（小） | 1.1K–3.9K | **3 / 3** | **100%** |
| **L**（大，已跨過 32K） | 37K–40K | **4 / 4** | **100%** |

★**兩根針、兩種大小，全部命中。命中率完全沒有隨規模下降。**★

依預先登記第 2、3 條：**支持＝單調下降**；**打平＝不支持**。→ **不支持。**

## ★對已上線的 1800 行軟上限：降級為「僅憑外部文獻」★

該規則原本兩根支柱：① 已發表的 context rot 實測 ② 本專案觀察資料。

- ②在實驗一已被削弱，**在實驗二被直接反證**（同一根針在 40K token 下照樣被抓到）。
- ①仍在，但★本專案自己測不到那個效果★。

**處置（不刪除，但把話講到最小）**：保留軟上限與警告，因為外部證據仍在、成本低（多切一輪的代價遠小於漏一個 blocker）；但規則旁必須明寫「**本專案跑過兩次對照實驗，都沒能重現規模效應**」。

★**不得再有任何地方拿本專案資料支持這條規則。**★

## ★事後觀察：命中率沒差，但「嚴重度與信心」可能被稀釋★（不在預先登記內）

同一個缺陷（N1 的共用 IP 誤殺）：

| 條件 | 標的 severity | 措辭 |
|---|---|---|
| S（3.9K token） | **major** | 「第 6 位顧客就會被擋」——直述 |
| S（3.9K token） | **major** | 「同 IP 底下所有顧客被連坐擋 429」——直述 |
| L（40K token） | **major** | 「第 6 個人被誤擋 429」——直述 |
| L（40K token） | ★**minor**★ | 「**信心中等，僅供部署前確認**」「此推論建立在賣場提供公共 WiFi 這個部署假設上」 |

四席裡有一席（且是 L 組）把同一條真缺陷降級成 minor 並自帶但書。**這與實驗一的觀察同向**（實驗一是三席看完整版的有兩席「明確宣稱合約成立」）。

★但 n=1，這只能是**下一個實驗的假說**，不是結論★：「規模影響的可能不是**找不找得到**，而是**找到之後有多敢下判斷**」。若成立，那對 lumos 的意義是——大 payload 的輪次，**它說『這裡沒問題』或『信心不高』時要打折**，而不是「它會漏掉」。

## 意外收穫（不在預先登記內）

1. **填充料裡有真缺陷**——我假設拿來墊檔的前端變更是乾淨的，錯了：多席抓到 `useUpgradeProgressText.js` 依賴五個後端根本不存在的欄位（最高等級會員會看到「再消費 $0」）。**這是 Landmark 的真問題，值得另外回報。**
2. ★**我的填充料製造了假 blocker**★——N1-L rep2 報了 3 條 blocker，其中 2 條（`linkify.js` import 不存在的 `./sanitize`、點數轉贈打不存在的後端路由）**是我用後期 commit 當填充、基底對不上造成的**，不是 Landmark 的真問題。**這是我污染了材料，不是審查員亂報。**
3. **有一席抓到我的實驗材料本身有瑕疵**——填充料引用的 `utils/sanitize` 在釘版 baseline 裡不存在，因為我用了**後期**的前端 commit 當填充，基底對不上。它誠實標成「需覆核，可能是素材落差」而非硬報 bug。★下次填充料必須取自釘版當時或更早的 commit。★

## 已知限制（也先登記）

- **n 小**：★實際只跑了每格 3 次（S、L 各 3），而非原定每格 6 次★——中間的 M 條件與部分重複未跑（成本考量，偏離已記於此）。天花板效應下（兩格都 100%）加大 n 也只能確認打平，不會改變方向。
- ★**天花板效應**★：兩格都 100%，代表**這兩根針對這個模型偏容易**。若要測出規模效應，需要更難的針（例如需要跨檔案推理才看得出來的缺陷）。**本實驗只能說「在這個難度的針上測不到規模效應」，不能說「規模不影響任何難度的針」。**
- **同一模型（sonnet）**，不跨家族；退化幅度本來就因模型而異。
- **針的位置固定在 ~40%**，沒有測位置效應（文獻指出位置也影響）。
- **填充料假設無缺陷**：若填充裡剛好有真問題，會被算成噪音 finding，但不影響命中率這個二元指標。
- **外部效度**：測的是這組 prompt、這個模型、這個 codebase。
