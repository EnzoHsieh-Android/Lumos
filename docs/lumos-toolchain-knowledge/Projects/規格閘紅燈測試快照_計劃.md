# 規格閘紅燈測試快照_計劃

> 白話:新功能的測試在規格閘跑出紅的那一刻,是「實作還沒做到的 expected」。這份計劃把每次跑紅時的測試內容存下來(紅燈版),推送時把同一支測試的歷次紅燈版依序跟推送版接起來比;實作期間把 expected 改成實作輸出、放寬斷言、新加 `expected =`、調大逾時,就跟改既有測試一樣會被列出來。

## 問題與最小解

立案(2026-11-03,Enzo 原話依序):「我們當初規劃spec拆任務的時候，是以"需要驗收哪些測試"為spec完成的基準，是不是在這個階段，可以扣回測試這個主旨？」→「只是說法要改嗎？ 我們工具需要把這兩環串接起來？」→「直接開新計劃」。

斷點:`lumos test-guard` 拿主線分岔點當改動前版本。新功能的測試在分岔點不存在,`_tg_fn_cands` 遇到沒有前一版的函式只判 `tq/no-assertion` 與 `tq/catch-no-fail`(跳過與 assume 走另一條次數差,新測試帶 `@Ignore` 今天就會列)。於是「規格閘時 `assertEquals(900, checkout(1000))` 是紅的,實作算成 800 之後把測試改成 `assertEquals(800, …)`」推得出去。這正是預期答案研究裡最強的那條結論要防的事(預期值不能從實作現在的輸出來,`governance/eval/results/ai-test-verification-research-20261102/oracle.md` 結論 1、3)。規格閘手上有實作前的那一版,但 `_spec_gate_record` 只記測試名,沒記內容;推送前會壓提交,只記當時的版本編號也不夠(防竄改計劃的 4 筆規格閘留痕,用各自的版本編號查:第一筆 13 支綁定測試 0 支存在,其後三筆各 1 支存在,`n_red` 全是 0;2026-11-03 查證)。

舊否決比對(開審前,2026-11-03):`lumos rejections` 撞到 [[Projects/規格閘不把不做節的詞算進風險_計劃]] 否決的「內容比對 ratchet」(輕量審抓到 major 後洗不掉的比對,靠帳上自填的編號、輪次、快照,r4–r7 連四輪被繞過;[[Systems/規格閘]] 的 PITFALL 同一件事)。本案也是「留一份內容事後比」,差在紅燈版由工具在跑紅時自己寫、照檔案路徑與函式鍵找,改名與刪除另列候選,剩下「同時改紅燈版與帳本」照實寫成天花板。問人後 Enzo 裁「照設計開審」。

最小解:規格閘寫留痕時,把判成紅的 Kotlin/Java 綁定測試所在的檔案內容存一份;比對工具遇到「相對分岔點是新測試、但有紅燈版」的函式,把歷次紅燈版與推送版依序兩兩比,跑既有的函式級判斷,列成三條專屬規則。不做語意判斷,不建暫時工作樹。

PRIOR-ART: ImpossibleBench 建議實作期間測試唯讀、評分前還原原版(對「改測試」這招最有效,擋不住實作端特判;https://arxiv.org/pdf/2510.20270);社群 TDD 技能有「紅燈先提交、綠燈後請另一個代理判斷綠燈提交有沒有改變紅燈測試的語意」(https://skills.sh/mrsimpson/skills-coding/tdd ,靠模型判斷,這裡不採)與「綠燈後對紅燈階段的不可改紀錄比對」(adev write-test 技能,頁面拒絕存取、細節沒驗到)。判斷有沒有照 TDD 做,學界靠一串紅綠事件的順序而不是單一快照(Zorro,Kou 與 Johnson,先導驗證 89% 片段判對;https://unpaywall.org/10.1007%2FS10515-009-0058-8),本案因此改成歷次紅燈版依序比、並記「判綠過」的觀測。實務工具 tamperguard 把「expected 被改」在 diff 層判不準的情況標成要人看而不是擋(https://pypi.org/project/tamperguard/0.1.0/),本案 expected 與被測呼叫同時改的那一類留到第二批照這個口徑做。輸入檔壞掉屬「分析失敗」不能當乾淨結果(ESLint 退出碼 2、Kiuwan 把缺報告當內部錯誤),本案讀不到紅燈版時列成擋下但可逐筆放行的候選,不當成沒有紅燈版。比對借 `lumos test-guard` 既有的確定性判斷,合理改動走既有 `lint-waive` 附理由放行;兩版治理帳的讀法借 `_residual_blob_at` 與 `_residual_ask_rows_delta` 的行差。
RETIRE-IF: 各專案人工抽查自己的放行檔(`lumos lint-waive --list`,規則欄看得到 `tq/redbase-*`)時,`tq/redbase-weakened` 三個月內的放行理由多數是「需求在實作期間變了」而不是作弊或誤寫,那個專案就把這條改成只提醒;所有有抽查的專案都這樣,就撤掉紅燈版的寫入與比對(各專案自己抽、不期待跨專案統計) [retire:人裁] [until:2027-05-03]

## 名詞

- **紅燈版**:某次規格閘判紅時,那支綁定測試所在檔案的完整內容,加上測試名、它綁的條款編號、檔案路徑、函式鍵。它只證明「那一刻這支測試沒過」,不保證寫在實作之前(見做法一的不存條件與實務隱患的天花板)。不是設計審的凍結快照(`spec-freeze`),也不是截圖基準圖(`tq/snapshot-changed` 管的那種)。
- **紅**:`_spec_gate_verdict` 回 red。Python 有支數證據;Kotlin/Java 沒有(`_RAN_EVIDENCE` 沒收這兩個棧),紅等於「跑那支測試的指令退出碼非 0」,含編譯失敗;逾時也記紅,但不存紅燈版(做法一);規格閘這條路的測試項都找得到,不會出現懸空。
- **函式鍵**:`lumos test-guard` 認測試函式的身分,類別路徑加函式名(同名多載加序號)。
- **分岔點**:被推分支跟遠端主線的共同祖先,`lumos test-guard` 的改動前版本。

## 做法

### 一、規格閘寫紅燈版

- 逐支結果:`_spec_gate_judge_items` 的回傳本來就逐支(條款、平台、方法、判定、原因、細節),它另有三個呼叫端(相依回歸、推送前重跑、修正關卡),不改它;只改 `_spec_gate_run_clauses`,在原本的回傳之外多回一份逐支結果(條款、平台、方法、判定、原因都已在 `_spec_gate_judge_items` 的列裡)。`_spec_gate_prepare` 不改(`cmd_spec_gate` 對它的回傳做 6 元解構,加欄會壞)。
- 判完紅當下就取內容:每支判成紅的 Kotlin/Java 綁定測試,測試跑完立刻用 `_platform_name_files`(整個規格閘只建一次索引)找它所在的檔,以位元組讀檔、記 sha256;寫紅燈版時再讀一次,sha256 不同就不存(原因「判紅後檔案又被改」)。
- 不存的情況(每一種都在規格閘輸出印一句,並記進留痕的 `redbase_skipped`,見下):
  - 不是 `.kt`、`.java`;紅的原因是逾時(`_run_bound_tests` 的原因文字以「超時」開頭;規格閘這條路的測試項一律是找得到的,不會出現懸空);
  - 測試所在檔不在 repo 根底下、或被 git 忽略(紅燈版只存會進版本紀錄的檔);
  - 檔裡有超過 2 萬字的行、或剝完字串與註解後括號配不平(跟比對工具 `_tg_test_file` 的病態輸入處理同一套判法);
  - 檔案不是合法 UTF-8;找到的檔不只一支;同一支檔裡同名函式不只一個;用 `_tg_functions` 找不到那支函式;
  - 這支測試在這條分支上曾被規格閘判綠過(見「判綠觀測」);
  - 函式本體跟這條分支上一份紅燈版完全相同(不重複存);
  - 加進去會讓這份紅燈版 JSON 超過 5 MB(跟 `lumos test-guard` 的單檔上限同一個數)。
- 規格閘找得到的測試只認 `@Test`、`@ParameterizedTest`、`@RepeatedTest`(Kotlin 的 `KOTLIN_TEST_RE`、Java 的 `JAVA_TEST_RE`);`@TestFactory`、`@TestTemplate`、`@Theory` 的測試規格閘本來就綁不到,也就沒有紅燈版。
- 分岔點:寫入端要跟分岔點比的兩處(判綠觀測、不重複存),用 `_lens_fork_point`(遠端主線優先,跟比對工具的 `_tg_start` 共用)算分岔點,工作目錄的治理帳減掉分岔點那一版;分岔點等於頂端(分支剛開、還沒有自己的提交)照樣減,只有直接在 main/master 或分離頂端上工作、或算不出分岔點時才看整本工作目錄治理帳(代碼審 r1、r2 改定)。
- 判綠觀測:規格閘判出 Kotlin/Java 綁定測試是綠的時候(含風險低「新行為沒紅」擋下那條路,`_spec_gate_low_not_red`),寫一筆治理帳事件 `spec-gate-green`(走 `_gate_event`,帶迴圈編號與那幾支測試名)。之後同一條分支再跑出紅,那支測試不存紅燈版,原因「曾判綠(實作後補跑)」。`_spec_gate_low_not_red` 印的補跑步驟加一句「這樣補跑的測試不會有紅燈版」。判綠觀測只讀工作目錄的治理帳、只看這條分支自己寫的那幾筆(跟分岔點那一版做行差)。
- 寫檔:時機跟留痕相同(風險低在 PASS 時、風險高在相依回歸全綠時;其餘出口本來就不寫留痕)。寫成 `governance/redbase/<迴圈編號>/<留痕 token>.json`(新增),內容 `{"version": 1, "tests": [...], "files": {...}}`:`tests` 每支測試一列(測試名、它綁的條款編號清單、檔案相對路徑、函式鍵),同一支測試被好幾條條款綁只算一列;`files` 每支檔一份文字內容。以 LF、UTF-8 位元組用既有原子寫入(暫存檔、自驗、換名)寫出,寫完讀回核對 sha256。寫檔失敗時照舊寫留痕、不帶 `redbase` 欄位並印一句,規格閘本身不因此擋。
- 留痕(審查帳與治理帳兩筆)多三個欄位:`redbase: {"path": <相對路徑>, "sha256": <整份 JSON 檔位元組的 sha256>}`(有寫檔才帶);`redbase_skipped`:沒存的綁定測試名與原因,最多 20 筆(「判綠」排最後,不擠掉其他原因);`redbase_skipped_n`:沒存的總數。測試的身分是(平台、測試名):兩個平台各有一支同名測試時各存各的,判綠事件 `spec-gate-green` 的 `items` 也帶平台。
- `governance/redbase/`(新增)加進簿記資料夾清單(`_BOOKKEEPING_DIRS`):它是紀錄不是碼,代碼審通過後補跑規格閘不該讓代碼審留痕失效。只有代碼審留痕失效的判斷會另外看資料夾裡有沒有程式檔;小改動閘、風險掃描、推送前測試範圍、回頭重讀這些消費者只看前綴,放進這個資料夾的檔對它們一律是簿記。紅燈版的格式以 [[Systems/規格閘]] 為單一來源,[[Systems/test-guard]] 用 `SEE:` 指過去。

### 二、比對工具讀紅燈版

- 什麼時候讀:`<起點>..<終點>` 的改動清單裡有 `docs/.governance-log.jsonl` 或 `governance/redbase/`(新增)底下的檔才讀治理帳;另外兩種情況不讀治理帳也要看:推的就是工作目錄的頂端時,紅燈版資料夾裡還沒提交的檔(沒追蹤、加進暫存區,或用 `git add -N` 只登記要加的;治理帳與紅燈版都忘了提交);這條分支的提交刪過、起點那一版沒有的紅燈版檔(`git log --no-renames --diff-filter=D`;不帶 `--no-renames` 時,同一個提交刪舊的、加內容相近的新的會被配成改名而看不到那次刪除;起點就有的是主線上的舊紅燈版,回退節建議整個資料夾刪掉,不算);git 讀不出這段歷史時整段記成比對沒跑完,不當成沒刪過。三樣都沒有就什麼都不讀,行為跟現在逐字相同。起點是空樹(找不到主線)時不用紅燈版(新增告警閘本來就對空樹起點印一句、只印不擋)。
- 讀哪些紀錄:用 `_residual_blob_at` 讀起點與終點兩版的 `docs/.governance-log.jsonl`,照 `_residual_ask_rows_delta` 的多重集合行差取終點多出來的行(把閘名與種類篩選參數化,不另寫第三份讀法);起點那一版沒有帳檔當成空。只取 `spec-gate-record` 裡的 `redbase` 欄位,也就是這條分支自己寫的紅燈版;已經合進主線的舊計劃不會被誤套。紅燈版 JSON 檔用 `_nodehome_cat_blobs_capped` 從終點那一版批次讀(有單檔上限,`_residual_blob_at` 沒有),不讀工作目錄;治理帳本身大於 5 MB,照舊用 `_residual_blob_at`。紅燈版內嵌的檔文字餵 `_tg_functions` 之前,先過 `_tg_test_file` 對終點檔用的同一套病態輸入處理(超長行抹掉、括號配不平),不過的列 `tq/redbase-unreadable`。
- 驗,任一不過就列 `tq/redbase-unreadable`(擋下、可放行,原因分開寫):欄位形狀不對(`path` 不是字串、`sha256` 不是 64 位十六進位)、路徑不在 `governance/redbase/` 底下、終點那一版沒有這支檔(工作目錄有它時原因寫「還沒提交,請 git add 那支檔」,沒有時寫「被刪了,請從版本紀錄還原」)、讀不出、超過 5 MB、不是合法 JSON、`version` 不認得、位元組的 sha256 對不上欄位、加進去會讓這次推送超過比對工具 200 MB 的總量。另外,改動清單裡新增(含被配成改名的新路徑)的紅燈版檔沒有任何一筆留痕指到它(孤兒檔,多半是合併主線時解治理帳衝突弄丟了那一行),列這條、講用 `git log -p` 找回那一行、不要刪檔,而且照它的內容比;這條分支刪過的紅燈版檔也列、講從刪掉前那一版還原,同樣照它刪掉前的內容比(代碼審 r2 資安席);留痕還在、檔被刪的只列這一條,照留痕的 sha256 核對刪掉前那一版再比;這條的放行指紋不帶刪掉它的提交編號,rebase 或 amend 之後沿用(代碼審 r3)。不當成「沒有紅燈版」放過去。
- 串起來比:同一個「檔案路徑+函式鍵」的歷次紅燈版,照它們在終點那一版治理帳的行序排(不比 `ts`),依序兩兩比,最後一份再跟終點比。沒有留痕的那幾份(孤兒檔、沒留痕又被刪的)排不出先後,不接進這條鏈,各自直接跟終點比一次:接在鏈尾會倒著比,骨架孤兒接在 900 後面時 900→骨架列成斷言變少、真正的 900→800 消失;token 是亂數,照字典序排一樣會反(代碼審 r3 單審席)。每一步以前一份當前一版跑 `_tg_fn_cands` 的函式級判斷(放寬斷言、改 expected、新加 `expected =`、調大逾時),丟掉它裡面的 `tq/no-assertion` 與 `tq/catch-no-fail`(那兩條由分岔點比對列,不重複);終點那支測試完全沒有斷言時不做紅燈版比對(`tq/no-assertion` 已經列了,再比只會多一條 `assert-weakened` 說同一件事);命中一律列成 `tq/redbase-weakened`,原因寫出是哪一步、哪一種(例「相對規格閘紅燈版 <token>:expected 被改」)。跳過與 assume 的次數差不在這裡算(紅燈版的測試跑出紅就不是被跳過的,次數一定是 0,跟分岔點比對重複)。
- expected 與被測呼叫一起改:這一批不比(移到〈第二批〉);`_tg_pairs` 配不起來的斷言照舊不列,寫進抓不到。
- 排除與找不到:
  - 終點那一版的測試函式在分岔點有同一個函式鍵(或改名配對得上)→ 照舊用分岔點那一版,不看紅燈版。
  - 紅燈版記的測試,先看它的檔在分岔點那一版是否已有同一個函式鍵(有就跳過);再看終點那一版同一路徑有沒有,沒有就在這次改動清單裡的測試檔找同函式鍵(唯一就當搬家照比);終點那一版有同名多載(比紅燈版多出同名函式)時不猜,當找不到。找不到、不只一處、或整支檔已經不在,列 `tq/redbase-unmatched`(擋下、可放行),原因寫 token、測試名、它綁的條款編號。不讀計劃、不分條款是否還在。查找只讀紅燈版記到的路徑與這次改動清單裡的測試檔,用 `_nodehome_cat_blobs_capped` 批次讀,內容算進比對工具一次推送 200 MB 的總量。
- 指紋照 `_tg_cand` 的算法,身分字串固定為「紅燈版 token + 子規則名 + 子候選原本的身分字串 + 子候選的指紋」(子候選的指紋已帶同一身分第幾次出現);放行一條不會順帶放掉同一函式的另一條,也不會放掉分岔點比對的同名候選。
- 新規則代號與抓不到的變動,同步寫進規則一覽:`_TG_WHY` 補三條原因、`_TG_LIMITS` 與標準文件 `test-quality-standard.md` 的「抓不到」同一份(`t_tq_guard_cli_contract` 釘著)。抓不到新增:實作後第一次跑規格閘就手動把實作搬走造紅、之前沒判綠過的測試,紅燈版是實作後的內容;只存在某次跑紅時已經寫好的斷言(骨架之後才補、而補完後再也沒跑紅的不保護);判綠過的、逾時紅的不存;expected 寫在註記資料列(`@CsvSource`)或同檔常數時改值判不到;expected 與被測呼叫同時改(這一批不比,見第二批);同名多載插入時當找不到。

### 五、加機制的理由(不加它的最小解為什麼不夠)

- 判綠觀測事件:最小解是只把「實作後補跑」寫成天花板;不夠,因為那是工具自己印給人照做的步驟、一步就走到(規格閘 WHY 的出處就是這個事故),照做的人不知道防護因此失效。
- 歷次紅燈版依序比(取代「只取最早」):最小解是只取最早一份;不夠,TDD 先骨架紅、再補斷言重跑是常態,實測最早一份是骨架時後補的斷言被改成實作輸出零候選。
- `tq/redbase-unreadable` 可放行(取代「記成比對沒跑完」):沿用比對工具「單一怪檔是可放行候選」的既有慣例,不是新機制;原本那條會讓漏 `git add` 這種日常失誤只能整道閘關掉。

## 實務隱患

- 守衛面:新增告警閘對「規格閘時紅過的新測試」變嚴,原本只判有沒有斷言、吞斷言與跳過次數,現在也判放寬、改 expected、新加 `expected =`、調大逾時。需求在實作期間真的變了,要逐條附理由放行;一個計劃改很多條時會多一批放行。出口與既有閘相同(放行附理由、整道關掉是設定 off 或 `LUMOS_SKIP_LINT_NEW=1`)。
- 守衛面:紅燈版讀不到、沒提交、被改過時列成擋下但可放行的候選;漏 `git add` 是最常見的原因,訊息直接講。
- 守衛面:規格閘多寫一個檔與一種事件,寫入失敗時規格閘照舊寫留痕、不帶欄位並印一句,不讓規格閘本身因此擋;代價是那一次沒有紅燈版可比。
