# 前端知識與風險詞_計劃

> 白話:lumos 的提問、審查範本和風險詞表都是照後端長出來的。一次 React 前端示範裡,該問的前端問題(載入/錯誤狀態、時鐘、輪詢、回應亂序、e2e 腳本收尾)全靠編排者自己想到,反過來前端的日常字眼(「送出請求」「ORDER_PAYMENT_TIMEOUT」)又被當成對外送出、金流。這份計劃把前端該問的放進設計階段看得到的地方,並把那兩種誤判拿掉,不碰其他判法。

## 緣起

- 2026-10-15 order-web 示範(React + TypeScript + Vite;order-web 是示範用的消費專案,本機另一個 repo,不在本 repo 裡;卷證在那個 repo 的 `governance/review-reports/code-搶購下單畫面/`):兩輪設計審 96 條發現,lumos 自己的出題、檢核題、規格閘預先指出的是 0 條,全部來自派工詞裡編排者手寫的前端版鏡頭(F19)。代碼審三輪裡,e2e 腳本那一族(共用埠與容器、/tmp 鎖與狀態檔、pid 驗證、路徑別名、curl 沒逾時)換了三次形狀才收斂(rN=那次代碼審的第 N 輪:r1 全機共用資源 → r1 修補把鎖放到 /tmp → r2 資安席實測別的本機使用者可預放狀態檔讓收尾 kill 任意程序 → r2 改成每份工作樹自己的資源 → r3 路徑別名讓 `--cleanup` 假成功、健康檢查沒逾時)。
- 本計劃負責 [[Projects/Web示範前端缺口_調研]](示範缺口比對表)的 C 組(F4、F10、F19、F13、F18、F27、F30、W11)與 D 組(F5、W3、W4);本文的 F/W/B 編號都是那篇比對表的列號(F=示範編排者記的、B=後端代理回報、W=前端實作代理回報)。
- 使用者 2026-10-15 裁「加前端與識別字例外」(d1):風險詞表的「送出」接在請求、表單、第二個這類前端語境時不算對外送出,全大寫識別字裡的 PAYMENT 不算金流。前端那一半同日由編排者撤回(代碼審三輪證明單一正則做不到不漏又不誤中,見做法 9 與 d1),只留 PAYMENT 參數名例外;[[Projects/雙向門放行_計劃]] 取捨段「送出被判對外送出、不改表」對送出照舊成立。

PRIOR-ART: 全部借既有形狀,不長新機制——前端面照需求風險面表 `_REQUIREMENT_FACETS` 的列(id/stage/q/when);本機腳本題組照棧別題庫 `_STACK_QUESTION_SPECS` 的形狀(id/q/when),自動進 pitfalls 清單、改檔前推播與表態閘;範本補充照 templates.md §7.7 A 表與 §7.8〈消費專案六類〉之後加 ### 小節的先例;詞表例外寫成詞表本身的正規式,沿用規格閘不做節代碼審第 11 輪已用過的 lookaround 寫法,門判定與 `pitfalls --check` 兩條路自動一起變。前端題目內容參考 OWASP 前端資安清單(XSS、CSRF、開放式轉址、CSP、postMessage)與 Testing Library user-event 官方文件的 `advanceTimers` 選項。

## 做法

### 1. 前端字樣只多列提醒,不決定審查方向(F4、F13、F10 共用)

- 新增一個正規式字串常數 `_REQ_FE_WHEN`(放在 `_REQUIREMENT_FACETS` 旁邊、名字跟需求風險面同一族),整條不分大小寫(`(?i)` 開頭),當成前端各列的 when(字串清單裡的一個字串,跟既有列同型,`--stage --json` 照樣序列化得了)。收:副檔名 `.tsx` `.jsx` `.vue` `.svelte`;框架與工具名 react、vue、svelte、angular、next.js、nuxt、vite、solid-js、preact(前後不是英文字母或數字,大小寫與連字號寫法都算,例 `react-query`、`vite.config`);中文「前端」「瀏覽器」。不收「畫面」「元件」「頁面」(後端計劃也常寫)。框架名跟 `_NODE_FRONTEND_MARKERS` 對齊(多一個 vite;那份比的是 package.json 的套件名、這份比計劃散文,所以不共用同一個集合,在註解寫明)。
- 比對對象三個入口一律是**計劃全文**(讀進來的原文,不是 `_pitfall_strip_spec` 剝過的 corpus),同一份計劃三個入口結論相同。
- **這條判準只決定「多列幾題」,不決定審查員看哪個方向**。後端計劃寫「回傳欄位給前端」也會多列前端面,代價是作者多答幾題(可以答「不適用」);設計審鏡頭要不要加前端補充,交編排者照「這份計劃要改的檔」判(做法 4),不看這條詞判。

### 2. F4 需求風險面加前端面

在 `_REQUIREMENT_FACETS` 加下列各列,每列多一個鍵 `role: "frontend"`(既有列不帶這個鍵,`--stage --json` 的輸出只是多一個鍵):

| id | 階段 | 要釐清什麼 |
|---|---|---|
| req-fe-states | 需求 | 載入中、空資料、失敗、結果不確定(逾時、斷線、送了沒回)四種狀態各長什麼樣?使用者在每種狀態能做什麼、不能做什麼? |
| req-fe-device | 需求 | 支援哪些裝置、瀏覽器與螢幕寬度?無障礙做到哪(只用鍵盤、螢幕報讀、對比)?哪些瀏覽器的鍵盤行為不同(例:macOS Safari 預設 Tab 不停在按鈕)? |
| arch-fe-clock | 架構 | 倒數、期限、「現在能不能按」用誰的時間?瀏覽器時鐘偏快或偏慢幾分鐘時畫面會怎樣?要不要用伺服器回應的時間校正? |
| arch-fe-stale | 架構 | 畫面上的資料多舊算過期?過期時怎麼讓使用者看得出來、什麼時候重抓? |
| arch-fe-origin | 架構 | 前端跟 API 是不是同一個來源?跨來源時 CORS、cookie、CSRF 誰設定?開發時的代理跟正式環境差在哪? |
| perf-fe-budget | 效能 | 首屏時間、bundle 大小、互動延遲的目標各是多少?在什麼裝置與網路下量? |

### 3. F13 前端問題族進設計階段

同一張表再加(同樣帶 `role: "frontend"`):

| id | 階段 | 要釐清什麼 |
|---|---|---|
| arch-fe-poll | 架構 | 輪詢多久一次、失敗時怎麼退避(間隔拉長、上限、背景分頁暫停)?同時開著的使用者數乘上頻率,後端與連線池扛不扛得住? |
| impl-fe-race | 實作 | 同一畫面連發兩次請求、舊的比新的晚回來,會不會蓋掉新資料?離開畫面或換使用者時,在途請求的結果怎麼丟掉? |
| impl-fe-lifecycle | 實作 | 計時器、輪詢、訂閱在元件卸載時有沒有收掉?重複掛載時會不會跑兩份(React StrictMode 開發模式會故意掛兩次)? |
| impl-fe-idem | 實作 | 連點、重新整理、重送時的冪等鍵由誰產生、存在哪?換使用者、換商品或上一筆已成功時要不要換新的? |

- 設計階段看得到的三個入口,都用做法 1 的判準、比計劃全文:
  1. `pitfalls --stage <階段>` 照階段列(現有通道)。
  2. 計劃模式 `pitfalls <計劃>`(不帶 `--check`)在既有輸出後面多一段「前端面(計劃提到前端字樣:命中「…」)」,不分階段逐條列出所有 role 為 frontend 的列;`--json` 多一個鍵 `frontend_facets`(同形狀的列清單,沒命中就沒有這個鍵)。
  3. `pitfalls <計劃> --check` 在 ✓ 與 ✗ 兩條路都多印一行,開頭「提醒:」,寫「計劃提到前端字樣(命中「…」):`lumos pitfalls <計劃>` 有前端面要逐條答(不適用就寫不適用);這份計劃真的要改前端檔時,設計審派工照 templates.md §7.7〈前端補充〉加問」,回傳碼不變。設計審手冊第 2 步本來就跑 `--check`,編排者一定看得到這行。提醒不寫「這份計劃是前端」。
- 跟角色卡的分工:角色卡問「程式有沒有做到」(代碼審),前端面問「設計怎麼定」(設計審),所以亂序、卸載兩族兩邊都有、措辭不同;`_ROLE_CARDS` 不動(題號計數是它的撤除條件,改了等於量測歸零)。
- 內容源照既有規矩記在 [[Systems/情境出題]]:那篇「需求風險面表的內容源」那一節寫死的「14 項」與「依任務書提問九類與六個階段挑出」改成 25 項,並寫明新 11 列來自這次示範的哪一族發現、不是任務書九類。

### 4. F10、F19 設計審派工範本的前端補充

- templates.md §7.7 在 A 表的「三條硬性配套」之後、`### C` 之前加一個 ### 小節〈前端補充〉(不改 A 表、不切開配套)。
- **用不用由編排者看「這份計劃要改的檔」決定**:`lands_in` 指到的系統或計劃寫明要改的檔裡有網頁前端檔(`.tsx` `.jsx` `.vue` `.svelte` `.html`、前端 package.json 底下的 `.ts` `.js`)才用;只是正文提到前端(像本計劃、[[Projects/前端框架從vue分出_計劃]] 這種改 lumos 自己的計劃)不用。前後端都改的計劃,席位照 A 表的原立場、再**加問**下表那一句,不取代原本要看的(遷移、連線、鎖照看)。
- 下表跟 A 表一樣是**語意規格**,派工當下自己換句話說、不逐字貼(A 表配套第 2 條);簡化、架構對齊、資安、通才四席沒有對應列(資安走 §7.8〈網頁前端類〉,其他三席本來就不分前後端)。

## 實務隱患

- 守衛面(碰,照實寫):
  - 門的詞表放寬一個詞:PAYMENT 緊接時間或重試尾碼的識別字不算金流,規格閘可能把原本判高的計劃判低;`pitfalls --check` 同步少命中。量到的影響是 0 份改判、不做清單略過詞 0 份改變(做法 9)。「送出」的前端例外撤回後,前端計劃提到送出照舊判高。
