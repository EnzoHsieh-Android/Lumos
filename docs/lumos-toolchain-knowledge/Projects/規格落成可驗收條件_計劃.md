# 規格落成可驗收條件_計劃

白話:設計審現在是「派幾個審查員輪流讀散文、折進去、再讀一輪」,你自己的帳說它折進去的九成四是「文件寫得不夠好」、第二輪還有九成七抓到重大——散文收斂在這裡從來沒收斂過。**這份計劃(第 5 版,拆後的半套)只做一件事:驗收條款一律寫成能直接變成測試的句式並綁上測試,規格閘把綁的測試真的跑一次、把紅綠印出來;處置閘第五步跟規格閘共用同一支檢查器。** 所有計劃仍照舊派審(全部當單向門)。「雙向門不派審」整套搬到 [[Projects/雙向門放行_計劃]] 待命;逃逸自動記已落地、獨立成 [[Projects/逃逸自動記_計劃]](Enzo 2026-09-17 裁「拆兩份、先上半套」——四輪設計審 95 條折入裡,守原題的條款只占 27%、守「守機制的機制」占 42%,r4 簡化席機械數)。

PRIOR-ART: ①最小解層級=改條款格式與處置閘第五步的判定,不動筆記結構、不做自動生測試、不動門與留痕 ②世界解過:EARS(Rolls-Royce 出身、Kiro 拿來當規格層)、BDD 的 Given/When/Then;亞馬遜單向門/雙向門與 Meta RADAR 是第二階段的事 ③借用不自建:條款存在性沿用 `_clause_bindings_for`(處置閘第五步那支)、測試執行沿用 `.lumos/config.json` 的 `run_cmd`;**支數解析是新寫的**(r3 訂正:既有 `_ran_evidence_check` 只證「有東西跑過」),落地時收進 `_RAN_EVIDENCE` 逐棧表(r4 架構對齊席)
RETIRE-IF: ①句式規則上線 60 天內,有條款的計劃比例反而下降(口徑:分母=首筆帳晚於 `_SPEC_GATE_SINCE` 的設計迴圈,分子=其中計劃檔有 `[SN]` 的;跟 [[Systems/design-loop]] 既有那條 `REVISIT:2026-11-08` 量「過審計劃有 [SN] 的比例」是同一件事,到期時用本口徑一次量、兩處合併,r5 回滾席)→ 規則改成軟提醒或收掉 ②半套上線 90 天內,治理帳 `spec-gate-run` 列裡曾經紅的條款從沒在後來的列裡變綠 → 「跑」那一步收掉,只留句式與綁定 ③治理帳 `spec-gate-run` 列裡不同計劃 ≥30 份、且 [[Projects/逃逸自動記_計劃]] 對回率過關 → 才開 [[Projects/雙向門放行_計劃]] 的審

## 為什麼(數字都從審查帳算;口徑=**全帳**的設計審記錄,不是本迴圈——r5 回滾席用本迴圈四輪算出 81/13/5 對不上,是口徑沒寫;全帳 2026-09-16 是 94/4/1、2026-09-17 含本迴圈四輪後是 92/6/2)

| 觀察 | 數字 | 意思 |
|---|---|---|
| 折進去的是什麼型 | spec 94% / code 4% / process 1% | 設計審抓到的絕大多數是「文件本身寫得不夠好」,不是「這個做法會做出錯的程式」 |
| 每一輪最高嚴重度是重大的比例 | r1 98% / r2 97% / r3 93% | 條數遞減(11→9→7)但嚴重度沒降;跑到第二輪的 64 條裡 62 條仍抓到重大 |
| 逃逸帳 | 6 筆 / 128 條迴圈(口徑:`loop` 不以 `code-` 開頭且帳列有輪次欄位;不要求輪次則 159 條) | 這套流程從來沒量過自己的漏網率;帳空不代表沒漏,只代表沒人記 |
| 分級用量 | 記錄層級 standard 622 / high 96 / light 12;迴圈層級 93 / 10 / 11(口徑:設計迴圈=`loop` 不以 `code-` 開頭,不要求輪次欄位) | 便宜路徑有人走但少(約一成迴圈)。**r2 簡化席抓到初版「629/83/3」是多加了「帳列要有輪次欄位」的篩選,把 9 筆沒輪次的輕量檔列篩掉的假象**;d3 因此改寫理由,不再拿「沒人走」當硬擋的依據。分級看的是改動規模與風險面,不看 spec 本身的品質,這點不變。d11 的新理由(格式不是提醒)與這個數字獨立,r3 簡化席核可「不是換說法保結論」 |
| 自家硬證據 | 一份自相矛盾的測試 spec 撐過六輪設計審,實作真跑才抓到 | 散文審看不出來的,跑一次就現形(見記憶 design-loop 完整性天花板) |

世界那邊一致的說法:模型自我批評的收穫集中在前一兩輪、二到三輪飽和,**更強的模型做第二輪反而會變差**;根本原因是自我批評修得了表面問題、修不了深層錯誤,**除非有外部工具回饋**(例如測試結果)。這正好解釋上面那筆六輪沒抓到。

**兩個對不上的地方要誠實寫**:世界說二到三輪飽和,本 repo 的帳是第三輪還有九成三抓到重大。可能原因是每一輪折進去的修改本身又帶來新問題(記憶:全折之後別直接放行,再派一席又抓到三十條)——散文修改本身不可驗證,反而支持改成「跑」。另一個:「重大」是審查員自己標的,而受控實驗(在 graph-vs-code 分支的 lumos-gvc 工作樹,`Projects/圖譜效用受控實驗_計劃`)已證明模型判定員不可靠,這 98% 裡有多少是真問題帳上分不出來。

## 兩層要分開(Enzo 2026-09-17 問「不同公司規格格式不同怎麼辦」)

- **規格書**(PRD、需求單、客戶的 Word 檔、Figma)——格式不限,工具不碰。
- **驗收條款**(計劃裡 `[S1]`、`[S2]` 那幾行)——從規格書萃取出來的「可以驗的宣稱」,每份計劃通常五到十條。**句式只約束這一層。** Kiro 也是把自然語言翻成觸發式句子,不是要求一開始就那樣寫;BDD 的 Given/When/Then 同理。
- 翻譯範例:規格書寫「月租到期後給住戶三天緩衝,期間可進出但照臨停收費」→ `[S1] 當租約到期且未滿 72 小時,通行閘應放行 [test:…]`、`[S2] 在寬限期間,計費應套用臨停費率 [test:…]`、`[S3] 當到期滿 72 小時,通行閘應拒絕 [test:…]`。規格書一個字不用改。
- **翻不成句式的就不是驗收條款,是指引**(「程式碼要好讀」「效能要好」),留在散文、不掛 `[S]`、不進閘。這是功能不是缺陷:它逼作者分清「能不能驗」;翻不出來的要嘛拆到能驗(「效能要好」→「當查詢 1000 筆時,系統應在 200 毫秒內回應」),要嘛承認是指引。
- 句式關鍵字**半套只認中文**(當/在/若啟用/若/應;英文 When/While/Where/If…then/shall 等第二階段,r5 簡化席)。**不做設定檔讓團隊自訂句式**——一開放就沒人用標準型;等真有第二個團隊撞到再說。

## 設計(半套)

### 一、條款句式(一條文法,五個名字)

**r1 三席抓到:初版把「狀態」型鎖死在「期間」二字,結果本篇自己的 S4、S12 就過不了自己的句式;S4 還是「在…裡,若…,則…」的複合觸發。**改成一條文法,五個型只是給人讀的名字,機械只驗這條:

```
定義行 = "- [S<n>] " 觸發子句? 主體 "應" 回應 " [test:…]"(或 [manual:≥4 字含實字])
觸發子句 = ("當" | "在" | "若啟用" | "若") 內容 分隔 ("則")?      分隔 = "," | "，"
無條件型 = 沒有觸發子句,而且句首不是 當/在/若(★這條排除規則是硬的,否則任何句子都能落入無條件型兜底★)
停用詞   = 當然|當下|當前|在此|在於|若干|若是   (句首命中停用詞 → 視為無條件型,不當觸發詞)
缺分隔   = 句首是觸發詞、不在停用詞表、整行沒有分隔 → 格式看不懂,印「觸發子句缺逗號」(r5 正確性席:這種行原本兩邊都掉不進去)
```

- **半套只認中文觸發詞**(r5 簡化席:散文寫「英文同等」但文法裡沒有,S1 的測試會證偽那句話)——英文關鍵字等第二階段;英文開頭的定義行在半套照文法就是無條件型。

- **停用詞表(r2 正確性/邊界席)**:中文沒有詞界,「當然」「在此」「若干」的第一個字元就是觸發關鍵字,又配不出逗號分隔的觸發子句,兩邊都掉不進去、條款會被靜默判成「格式看不懂」。停用詞表寫死在程式、只准增不准刪;閘擋下時訊息照既有兩段式印法(r5 架構對齊席):先一行「句首『在…』被當觸發詞」,再一行「不是觸發請改寫或用主體開頭;若是常用詞,把它加進 `_TRIGGER_STOPWORDS`」,不能只印「格式看不懂」。**表列不齊是已知的(r3 正確性席:「若不」「在場」「當機」「當初」都不在)**——失敗模式是明確報錯不是靜默放行,誤判率靠使用者回報加詞收斂。

- **一條條款只准一個觸發子句**;複合觸發(「在 X 裡,若 Y,則…」)一律拆成兩條。
- 「在」型不再要求「期間」二字(狀態可以是「在雙向門的計劃裡」「在閘上線前」)。
- 不合文法的定義行 → 不算條款,閘印「格式看不懂」(沿用處置閘第五步那條的處置)。
- **五個名字(無條件/事件/狀態/選項/非預期)只出現在文件與範例,不出現在程式判定裡**——r1 簡化席問「五型換到什麼」,答案是:換到可讀性與寫測試時的提示,機械上就是一條文法。
- 句式只驗形狀不驗意思;擋空話的不是句式,是第三節「跑」印出來的紅綠。模糊詞由既有 prose-lint 提醒。**誠實寫:這條文法很鬆**(r2 接手席)——機械上只驗「有沒有觸發詞前綴、有沒有『應』字」,「不應」也含「應」照過;它換到的是「一行一條款、一條款一觸發」的機械可辨識性,不是語意正確性。

### 二、綁定與回退節

- 每條條款綁 `[test:<測試名>]` 或 `[manual:≥4 字含實字]`;存在性走 `_clause_bindings_for`(處置閘第五步實際呼叫的那支);**懸空(測試名對不到)只提醒不擋**——這是處置閘現行語意,有翻紅釘鎖著(r3 接手席),半套不改。
- **有 `[S]` 條款的計劃**要有「## 回退」節,內容 ≥20 字含實字(r1 邊界席:「非空」會被一個標點放行)。**範圍寫死(r5 邊界席 blocker)**:處置閘第五步對沒有任何 `[SN]` 的計劃整步跳過,是 design-loop 那條 ★INVARIANT★ 的既有語意,半套不擴大——所以「全部計劃」是錯的,是「掛了條款的計劃」。**判準寫死(r5 正確性/邊界席)**:標題精確是二級 `## 回退`(允許尾端括號後綴,不認「回退與復原」「Rollback」);節範圍到下一個 `##`;走 `_visible_lines`(fence 內不算);引用塊(`>` 開頭)的行不算實字;同名節多個就加總。
- `[manual:]` 只認半形冒號(既有 `MANUAL_REF_RE`);全形冒號會被當「沒標」,閘印提示「看到 `[manual：` 全形冒號,改半形」而不是只印通用訊息(r5 邊界席)。
- `[keeps]` 標記、測試名互異、雙向門禁 manual 都是第二階段的事,半套不認。

### 三、新閘 `lumos spec-gate <計劃.md>`(印法照處置閘;半套只擋格式、跑的結果只印)

1. **句式**:幾條合格、幾條看不懂(含停用詞誤判的提示)、有沒有複合觸發 → 看不懂的擋。
2. **綁定**:缺幾條(擋)、manual 不足 4 字(擋)、懸空幾條(提醒)、回退節有沒有且夠長(擋)。
3. **跑**:每條 `[test:]` 用 `run_cmd`(要帶 `{method}`,沒有就略過這一步並印怎麼改)真跑一次。**跑的機器借既有 `_run_bound_tests`**(r5 簡化席:同一支檔裡已有「真跑、紅/綠/弱證據、no-cmd、逾時」整套,掛在推送閘上;本篇只多一種 items 來源=`[SN]` 綁定,不另寫跑的機器)。**支數 N 的定義=測試工具說「篩到幾支測試」,不是斷言數**(r5 接手/邊界席 blocker:本 repo 自己的 `scripts/test_lumos.py` 印的 `N passed, N failed` 數的是 `check()` 斷言次數,一支函式 5 條斷言就會被誤判 N≥2;它印「lumos 測試(N 案例)」那一行才是支數)——`_RAN_EVIDENCE` 每棧加一條「支數」正則:本 repo runner 讀 `(\d+) 案例`、unittest 讀 `Ran (\d+) tests?`、pytest 讀 failed/passed/skipped/error/xfailed 相加;其他三棧(swift/xunit/jest)落地時各補一條、補不出的棧印「這棧還讀不出支數,只印有沒有跑過」。N==1 且那支是 skipped/xfail → 弱證據(r5 正確性席);N==1 且失敗 → 紅;N==1 且通過 → 綠;N==0 → 印「弱證據:一支都沒跑到」;N≥2 → 印「篩選匹配到 N 支,測試名要唯一(本 repo `-k` 是子字串比對,測試名互為子字串的組數依算法 158 或 409,r5 回滾席重算口徑不同,只說明現象存在)」。**半套不擋紅綠**:紅=新行為還沒做、綠=既有行為或已做完,兩種都合法;這一步的價值是把「條款有沒有真的接到測試」變成可見的數字,餵 RETIRE-IF ②。
4. 印匯總:條款數/合格數/綁了/懸空/紅/綠/弱證據,接著印「接著走 `lumos loop next`」。

**不寫審查帳(半套沒有放行這件事);但每次跑往治理帳寫一行 `kind: spec-gate-run`**(計劃、條款數、每條的紅/綠/弱、時間;走既有 `_append_governance_log`)——r5 正確性/簡化/回滾三席:沒有這一行,RETIRE-IF ②「紅有沒有變綠」、REVISIT 的比例、第二階段「跑過 30 份」全部量不到。**後果寫明(r5 簡化席 blocker)**:半套不寫 `kind: spec-gate` 留痕,所以 [[Projects/逃逸自動記_計劃]] 裡 `push-gate-unreviewed` 那一路(靠雙向門留痕判)在第二階段上線前恆為零筆——那份計劃已寫、本篇也要寫。

### 四之一、相依回歸(Enzo 2026-09-17 裁:驗收標準必須含「相依功能沒有回歸」,單雙向都一樣)
