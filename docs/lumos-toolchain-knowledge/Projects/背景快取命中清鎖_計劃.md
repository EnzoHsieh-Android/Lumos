# 背景快取命中清鎖_計劃

## 問題與邊界

[[Issues/背景快取命中留下暖機鎖]] 是前案第三輪找到的獨立缺陷：派工端建立 `.warming` 鎖，背景程序繼承暖機標記與派工端 PID 副本，負責在工作結束時清理那把鎖；但 `_dispatch_lens_graph` 早期讀到快取時直接返回，跳過函式尾端的清鎖。快取過期後殘留鎖阻止新暖機。前掃另查到快取未命中後仍有 impact、JSON、base 樹等錯誤提前出口，也會繞過尾端清理；本小修讓已啟動的背景程序在所有出口都清理派工端交給自己的那把鎖。`Popen` 根本沒啟動時的錯誤回報由 [[Issues/背景啟動失敗誤報逾時]] 另案處理。等待端仍只讀快取，不得按「曾取得」推論現在持有而刪鎖。

設計審發現同一派工程序可啟動不同範圍的兩把鎖，兩把的鎖內 PID 一樣；而背景程序若重新解析會移動的 `main`，可能算出另一把鎖的快取路徑。故派工端在取得鎖時已知的完整 `base_sha..head_sha` 要傳給背景端，取代會變的符號參照；同時只傳既有快取目錄裡的鎖檔**名稱**作為背景清理目標。清理 helper 從可信的私有快取目錄重建路徑，檢查名稱形狀、非 symlink、`_LENS_WARM_ENV` 及鎖內 PID 與繼承的 `LUMOS_LENS_LOCK_OWNER` 相符後才刪。名稱把同 PID 的不同範圍分開；沒有可信目錄或身份不符就保留鎖供人查，不能按任意環境變數路徑刪檔。保留既有鎖格式與 PID 比對，暖機標記及鎖名稱是新增的清理守衛。

在 `cmd_dispatch_lens` 的背景工作入口外層用 `try…finally` 統一清理，涵蓋快取命中、正常算完、解析與 impact 等早期錯誤及未預期例外；**移除舊函式尾端的清鎖，只留下這一個釋放點**，一般呼叫沒有暖機標記時 helper 不碰鎖。這只延伸現行同版身份界線，不把 PID 當跨版本或人工換檔的強身份保證。同一版沒有自動偷鎖：某背景工作已啟動後，另一工作不能合法取得**同一鎖名稱**，直到它被清掉；若人或舊版程序外部換鎖，仍受原案混版／人工復原限制。唯讀辯方逐個查過同版取鎖與釋放路徑，未發現合法同名換入者；但 `read_text` 到 `unlink` 不是原子操作，不能宣稱抵抗外部惡意換檔。切換實際安裝時依原案 S6 重新核對舊版程序，人工復原若曾在工作仍活時移鎖，也要回本案重驗。

## 驗收條款

- [S1] 當受託清鎖的背景程序一進場命中快取時，`cmd_dispatch_lens` 應回快取並清掉派工端交給自己的鎖；測試先在舊碼驗 rc 0 且鎖仍在，再驗修後鎖消失。 [test:t_lens_warmer_cache_hit_releases_owned_lock]
- [S2] 當鎖內 PID 不符、一般呼叫沒有暖機標記或同 PID 的另一範圍持鎖時，`cmd_dispatch_lens` 應保留非本次的鎖；測試分別斷言這三種情境。 [test:t_lens_warmer_ref_move_keeps_lock_identity]
- [S3] 當背景程序算完新快取時，`cmd_dispatch_lens` 應清自己的鎖，且等待端命中快取應保留其他持有者的鎖。 [test:t_lens_timeout_keeps_warming_cache] [test:t_lens_stale_lock_reports_uncertainty]
- [S4] 當背景程序在 impact、JSON、base 樹失敗或未預期例外時提前離開，`cmd_dispatch_lens` 應在保留原返回碼或例外的同時清自己的鎖。 [test:t_lens_warmer_error_exit_releases_owned_lock]
- [S5] 當派工後符號參照移動而同 PID 又派另一範圍時，`_lens_spawn_warmer` 應傳不可變的完整提交範圍與本次鎖名稱，背景應清 A 鎖、保留 B 鎖。 [test:t_lens_warmer_ref_move_keeps_lock_identity]
- [S6] 當平台沒有 `os.getuid` 時，`_lens_cache_read` 應沿用 `_trusted_private_dir` 的平台分支讀合法快取；POSIX 仍須拒絕非自己擁有或他人可寫的快取。 [test:t_lens_cache_read_without_getuid]
- [S7] 當早期命中快取的背景清鎖後該快取 TTL 過期，`_lens_wait_or_warm` 應可重新取得鎖並派新背景工作。 [test:t_lens_warmer_cache_ttl_retries]
- [S8] 當背景第一次清鎖後另一同版程序立即取得同名鎖時，`cmd_dispatch_lens` 應只執行一次清理並保留新持有者的鎖。 [test:t_lens_warmer_cleanup_runs_once]

PRIOR-ART: [Python `try…finally` 語法文件](https://docs.python.org/3/reference/compound_stmts.html#the-finally-clause)確認 `return` 也會走清理段；本案把背景清鎖掛在 `cmd_dispatch_lens` 的整個工作出口，不再逐個錯誤分支補呼叫。[Python `subprocess.Popen` 文件](https://docs.python.org/3/library/subprocess.html#subprocess.Popen)說明 `env` 可明確指定子程序環境；此處只傳已決定的範圍與鎖名稱，不傳可任意刪檔的絕對路徑。[Python `os.getuid`](https://docs.python.org/3/library/os.html#os.getuid) 只在 Unix 可用，Windows 快取讀取沿用本 repo `_trusted_private_dir` 的平台分支。[Python `os.unlink`](https://docs.python.org/3/library/os.html#os.unlink) 仍按名稱刪除；單加 inode 複查不會關閉外部換檔競爭，故不把同版排他取得的結論擴到舊版／人工換檔。

RETIRE-IF: 若同版程序能在前一背景工作未結束時合法換入**同名**且同 PID 的新鎖，或再有一例「清不到自己的鎖／清到別人的鎖」，撤掉鎖名稱加 PID 的身份判斷，改用每次取鎖唯一 token；若跨版本並行變成必要，另設跨版本協議，不假定舊版會讀新名稱。

## 實務隱患

已排除:金流:此路徑只計算派工鏡頭快取，不處理付款。
已排除:對外送出:本修復不推送、不部署、不寄送資料。
已排除:不可逆:只動隔離 clone 的程式與測試，真實鎖不在本次操作範圍。
守衛面:誤刪他人的鎖會讓兩支背景工作同時運作；S2 必須釘住身份不符及一般呼叫。

## 回退

若新 helper 誤刪他人鎖，先在受影響的 hook 執行環境設 `LUMOS_DISPATCH_LENS_NO_CACHE=1`：`_dispatch_lens_graph` 已用它跳過快取等待與背景暖機，代價是改為同步計算。停掉已派出的舊背景程序並查核鎖後，才回退本次分支到父提交 `930915bb`；父提交仍有 F1/F2，不開回暖機、不當成可部署的安全版本。

## 驗證順序

在隔離來源 repo 用 Python 3.14、可解析本地 `main` 或 `master`、足夠兩筆提交的前提下先跑 S1/S2/S4/S5/S6/S7 的紅燈，再做修補；S8 要在修補版用第一次清鎖後立刻換入的同版交錯驗。檢查各指定測試實際執行且零 skip，不能把 skip 當綠。S3 的既有整合測試也須同一前提下真跑；無原生 Windows 執行環境時，`os.getuid` 缺失注入只證明分支邏輯，真 Windows 檔案權限語意列為切換前人工重驗。完成後記獨立驗證紀錄、審查快照與處置；前案仍因 F2 未修保持 pending，不把此小修聲稱為整體放行。
