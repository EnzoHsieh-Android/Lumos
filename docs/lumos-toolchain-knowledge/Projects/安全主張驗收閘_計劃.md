## 一、區隔：資安護欄怎麼標、怎麼跟 Invariant 共存、怎麼一眼看出驗證不健全

**怎麼標**：沿用盤點已實作的 `lumos-security-v1` 圍欄，`concerns` 含 `security` 的條目才是資安護欄；`flag/security-relevant` 標籤照舊只用來抓「有標籤卻沒登記」，在本篇不算登記痕跡（見〈四〉擋下條件）。不用標題字樣或「Invariant」字樣猜分類。
- 理由：盤點的解析、讀檔邊界與錯誤分類已過設計審與實作驗收，再發明一套標法就是兩個家。
- 不選：另開 `★SECURITY★` 合約標記——會把部署掃描、期限性政策硬塞成永久合約，正是母計劃 d5 否決的方向。

**跟 Invariant 共存**：同一條規則要嘛是既有 ★INVARIANT★（source.kind=invariant，指到那條合約全文），要嘛是獨立要求（source.kind=requirement）；同一來源只列一筆，`concerns` 同時寫 business 與 security。驗收結論分開：業務合約照舊由 bound-tests-gate 擋紅燈，資安證據判定只看 concerns 含 security 的條目；同一份證據兩邊都能用，但不互相繼承通過。
- 理由：母計劃 d5「來源與關注面分離」。
- 不選：業務與資安互斥分類（同一條「他人不能取消訂單」得寫兩份）、所有資安一律升 Invariant（部署設定、依賴掃描不是永久不變式）。

**用哪個指令看**：新增唯讀子命令 `lumos security evidence`（`--json` 同內容；`--commit <sha>` 改讀那個提交，見〈四〉）。它拿 `security list` 同一份報告當輸入，逐條、逐證據種類核對工具結果，印出：
- 每條護欄一列：id、revision、來源（invariant 或 requirement 與節點）、lifecycle、威脅類別、整體判定（sound／unsound／excepted，規則見下）、護欄層原因代碼，以及最先要修的一項。
- 每條展開每個必要證據種類一列：種類、判定（qualified／failed／invalid／stale／missing／uncalibrated）、原因代碼（清單見〈原因代碼〉）、證據檔路徑、工具名與版本、綁定的版本、觀察時間、例外到期日、`limitations`（這份證據證明不了的事，例如跨環境套用、內容一致的偽造報告、AI 審查人的紀錄放行不了人工權責項；字串陣列，沒有就是空陣列）。
- 頂端照抄盤點的讀取完整度與登記完整度，固定 `security_verdict: not_assessed`；文字與 JSON 都寫明「證據合格不等於產品安全」。另列凍結比對的結果：merge-base 版與主線 tip 版的提交編號（主線是怎麼認出來的也印）、有哪些條目、判定輸入、證據項或工具清單跟那兩版比變弱、各自有沒有核可鏈上的有效核可。

**整體判定的彙總規則**（逐條護欄，依序判，先中先停）：
1. 護欄層有問題就是 unsound，例外蓋不掉：必要種類少於威脅類別最低要求（`insufficient_required_evidence`，算法見〈二〉）、`required_evidence` 沒寫或是空陣列（`required_evidence_empty`）、威脅類別沒寫或是空陣列（`threat_categories_missing`）、威脅類別含表裡沒有的 id（`threat_category_unknown`）、護欄記的表版號工具不認得（`threat_table_version_unknown`）、來源決策作廢（`source_decision_invalid`）、引用的待決問題還沒結（`question_open`，見 S15）。空集合不能算出零下限：彙總規則 2 的「每個必要種類都 qualified」對空集合不成立，空的就是上面這條擋。
2. 每個必要種類（含 review）都是 qualified → sound。
3. 不是 qualified 的每個種類都被一條有效例外蓋住（例外的 `covers_kinds` 含該種類），其餘都是 qualified → excepted。
4. 其他一律 unsound。只要有一個不是 qualified 的種類沒被有效例外蓋住，就算其他種類都有例外也是 unsound。
- 閘門只看必驗集合裡條目的整體判定：unsound 擋，sound 與 excepted 放行；excepted 每次都記帳（見〈四〉）。candidate 條目照樣算出整體判定給人看，但不進必驗集合、不擋。
- 閘門呼叫的是同一支判定函式：同一個提交、同一個主線 tip、同一個 UTC 日期，「`security evidence --commit <sha>` 看到 unsound」與「推送那個提交被擋」是同一個答案，本機與 CI 也是。
- **判定跟日期有關**：例外與核可到期、`vulndb_stale`、`review_expired` 都照當天 UTC 日期算，同一個提交今天放行、過幾天可能擋；本機在 UTC 午夜前放行、CI 在午夜後跑，也可能 CI 紅（依 d9，CI 本來就是事後）。回退到舊樹（`git revert` 回上一個通過的狀態、對舊 release 補 tag）沒有特例，照當天重判，過期的證據要重收或由使用者簽例外。
- 理由：「驗證不健全」需要讀工具結果，盤點契約明文「evidence_check 永不到 verified、不讀報告內容」；擴 `security list` 等於改它的輸出契約與唯讀保證的語意，另開子命令可以讓盤點的判定契約一字不動。
- 不選：在 `security list` 加判定欄位（要改盤點計劃 S4 的 never_verified 合約候選）；只在推送時才算（使用者要能在推送前自己排查）。
- **`security list` 維持盤點計劃 S7「唯讀、無網路、無程序執行」**：要讀某個提交、要驗簽章的都放在 `security evidence`（它本來就跑 git 與 `ssh-keygen`），`security list` 不加 `--commit`、不驗章；它對 considerations 只顯示「簽章未驗」，格子算不算數由閘門與 `security evidence` 判。

**兩個指令的狀態詞不通用**（同一個子系統裡兩套詞，`stale`、`missing` 兩邊都有但意思不同）：

| 詞 | `security list`（盤點，不讀報告內容） | `security evidence`（證據判定，讀報告） |
|---|---|---|
| `missing` | 該必要種類沒有 `evidence_refs` 列，或列指到的節點找不到（`_secinv_evidence` 的預設值） | 該種類沒有任何證據項（或審查紀錄、背書） |
| `stale` | Verification 節點的 status 是 stale 或 superseded | 證據綁的 blob、護欄 revision 或日期對不上要推的提交 |
| `incomplete`、`declared_only` | 盤點自己的狀態，證據判定沒有對應詞 | — |
| `qualified`、`failed`、`invalid`、`uncalibrated` | — | 證據判定自己的詞，見〈二〉 |

兩邊的文字與 JSON 輸出各在開頭印一行「本表狀態詞跟 security list／security evidence 不通用」。

## 二、合格驗證的判準：每種證據怎麼由真實執行結果機械判定

### 證據種類（schema v2，契約變更）

盤點 v1 的五種（behavior、fault_sensitivity、review、deployment、dependency_scan）表達不了並發壓測、靜態分析、秘密、動態掃描、模糊測試與設定掃描。v2 改成下表；新增種類照盤點規矩升 schema_version，不用未知字串冒充。

| 種類 | 證明什麼 | 合法對照要求 | 允許的 format |
|---|---|---|---|
| behavior | 非法操作被正確拒絕、資料與副作用不變（單元、整合、HTTP 實測） | 同一份證據必須另有合法操作成功的案例，與前置斷言（目標存在、身分正確） | `junit` |
| fault_sensitivity | 只拿掉這條防護時，同一支測試的目標斷言翻紅、還原再綠 | 基準綠、還原綠，且還原版與基準版指紋相同 | `tq_capture`、`guard_kill` |
| concurrency | 重送、並發、壓力下,宣告不該生效的操作（他人操作、重複生效、超過配額）仍不生效 | 同次執行另有合法流量成功計數，避免服務掛掉也「全被拒」 | `k6_summary`、`junit`（並發測試） |
| static_analysis | 指定規則在指定範圍掃過、沒有未處置的命中 | 同工具同版本對已知陽性樣本命中（校準） | `sarif` |
| dependency_scan | 指定鎖檔掃過、沒有未處置的已知漏洞 | 校準：已知有漏洞的鎖檔樣本命中 | `sarif` |
| secret_scan | 指定範圍掃過、沒有未處置的秘密 | 校準：植入假秘密的樣本命中 | `sarif` |
| dynamic_scan | 對本機或已授權目標掃過、登入狀態成立、路由有觸及 | 校準：已知漏洞路由命中；加登入成功證據 | `sarif` |
| fuzz | 指定目標跑了足夠次數、沒有未處置的當機 | 校準：已知會當的種子確實被抓到 | `junit`（一個 fuzz 目標＝一個案例） |
| config_scan | 容器、IaC 或部署設定掃過、沒有未處置的違規 | 校準：已知錯誤設定樣本命中 | `sarif` |
| deployment | 實際部署設定符合（人工核對平台上的實際設定;也是 config_scan 沒有工具時的替代） | 人工核對；跟 review 同一套審查紀錄規則 | `review_record` |
| review | 判準獨立、適用性、合法對照是否真的合法等人工判斷 | 不是機械判定；依 d2、d8 要有審查紀錄，閘門核紀錄齊全、審查人不是作者、審查人種類、版本綁定與時效 | `review_record` |

- **種類 × 格式只准用上表那一欄**：圍欄項的 `kind` 跟 `format` 不在同一列，判 `invalid:kind_format_mismatch`；工具在清單登記的工具類別（〈三〉的表）產生不了這個種類，判 `invalid:tool_kind_mismatch`。這樣 secret_scan 拿一份兩個案例都通過的 JUnit 就過不了關。
- 一筆 `review_record` 只算它自己宣告的那一個 `kind`：護欄同時要 review 與 deployment，就要兩項，不能一筆紀錄算兩次。

護欄條目在 v2 另外新增一個選填欄位 `question_refs`：這條護欄的權限或適用性答案所在的待決問題，寫成 `<節點>#Qn`（指消費專案計劃開頭欄位的 `pending_questions`）。S15 只看這個欄位：列了的題目只要有一題沒「結」、或找不到，該護欄整體判 unsound（`question_open`）；沒列就不判這一項（盤點計劃 v1 沒有護欄連到待決問題的欄位，工具不從文字猜是哪一題）。
- 「結了」照既有 `_pq_settled`：狀態是已決或已驗，**而且**決策連結指到存在、沒作廢的決策（比「已決或已驗」嚴：已決但決策被翻案的題也算沒結）。規格閘、lint 用的也是這一條，三處同一個判準。
- 解析：題目在哪一篇、是哪一題，用 `pq_parse` 讀那篇開頭欄位的 `pending_questions` 找 `id`。`_pq_decision_target` 只收 `#dN`（`_dref_parse` 的正則是 `(.+?)#(d\d+)`，2026-10-20 實跑 `Projects/X_計劃#Q3` 回 `bad`，見 `governance/review-reports/安全主張驗收閘/r2-intake.md` 的〈r2 機械重現〉），所以把它「節點部分怎麼解」那一段抽成共用的 `_pq_node_target`，`_pq_decision_target` 改呼叫它、行為不變，`question_refs` 也呼叫它；不另寫第二套路徑解析。
- 讀的是閘門用提交樹快照建的那個 env，不讀工作目錄。

**最低種類怎麼算（`insufficient_required_evidence` 的唯一擁有者在本篇閘門）**：
- 每條資安護欄的 `required_evidence` 不能比它全部威脅類別最低種類的**聯集**少；最低種類與「沒有工具時改成什麼」的替代欄以 [[Systems/資安威脅類別表]] 為準。
- **用哪一版表**：用護欄自己記的 `threat_table_version` 那一版（鏡像常數保留每一個核可過的版本，不改舊版）；護欄沒記（v1 圍欄、null）用第一個核可版；記了工具不認得的版號判護欄層 `threat_table_version_unknown`。這樣表升版、最低種類變嚴時，已登記的護欄照它登記時那版判，不會在 `lumos update` 之後一起被擋；要改用新版，作者自己改 `threat_table_version`（改成最低種類較少的版本算變弱，見〈四〉）。這跟姊妹計劃「表改版後，舊版號的資料列照舊算數」一致。
- **表還沒核可時**(歷史規則,保留給之後新的表版號用):v1 已經雙家協定核可、鏡像常數上線(見 [[Systems/資安威脅類別表]] 與 d11),閘門照表擋最低種類。之後新加的版號在核可前,閘門照護欄宣告的 `required_evidence` 判,最低種類檢查與未知類別檢查改印一行「威脅類別表未核可，最低種類未比對」，不擋；`required_evidence_empty` 與 `threat_categories_missing` 不需要表，照擋。
- **空與未知**：`required_evidence` 為空、`threat_categories` 為空、或含表裡沒有的 id，一律是護欄層錯誤（見〈一〉彙總規則 1），例外蓋不掉；不把查不到的類別當成「沒有最低種類」，也不讓查不到變成整道 `evaluation_error`。
- 「有沒有工具」只看要推的提交裡的 `.lumos/security-tools.json`：某個最低種類要的工具類別在清單上一個核可工具都沒有，才照類別表的替代欄換成替代種類（例如沒有設定與容器掃描工具時 config_scan 換成 deployment;沒有秘密掃描工具時 secret_scan 換成 review 多蓋判斷 `manual_check_scope`）；替代可以是「已在集合裡的種類多蓋一項判斷」,這時被替代的種類照樣列出、標明走了替代,不當成原掃描已完成；不由作者在護欄裡自述沒工具。清單讀不出來時不做任何替代，照原最低種類判。
- 只有閘門讀得到工具清單，所以 `insufficient_required_evidence` 只由閘門（與同一支函式的 `security evidence`）判；`security list` 不判這一項，姊妹計劃 S5 指到本篇 S14。
- 這是防「為了合格而合格」的第一道：作者不能只宣告最好過的那一種。每類的最低集合都含 `review`，因為判準獨立（V1）機械做不到。

### 證據從哪來：沿用既有收證，外部工具只讀它自己的輸出

依有效決策（[[Projects/後端工程提問與證據擴充_計劃]] d6：證據走既有測試綁定與破壞測試，塞不進的再另開小計劃），不另建證據帳：
- **behavior，來源是 Invariant**：bound-tests-gate 的推送當場真跑不能當資安證據來源（2026-10-19 讀 `scripts/lumos` 的 `_bound_tests_for_diff` 與 `_bound_tests_check`、`.github/workflows/ci.yml` 的 code-loop gate 步驟）：它只跑這次改動波及到的合約，沒被波及的合約不跑；CI 那一步設了 `LUMOS_SKIP_BOUND_TESTS=1` 整道跳過；低風險推送帶 `--bound-tests-advisory`，紅了只提醒不擋。所以資安的 behavior 證據不分來源，一律要有自己的執行收據（工具輸出檔加證據圍欄，跟非 Invariant 的 behavior 同一條路），閘門讀收據判；bound-tests-gate 照舊管業務合約，它當次的綠燈不升格成資安證據。
- **fault_sensitivity**：兩條既有路擇一。
  - ① guard kill：照表態閘的做法（`code-loop dispositions` 寫表態時在本機算背書），新增寫入型子命令 `lumos code-loop security-backing <護欄 id>`（放 code-loop 族，跟寫表態的 `code-loop dispositions` 同一族；`security` 族維持唯讀）：在本機讀 `.kill-log.jsonl`，有效列照既有 `_backing_valid_rows`（head_sha 是目標版本的祖先、中間只動簿記檔），把每個配方組的結果連同護欄 id、revision、配方 id、配方改到的檔與 head_sha 寫進**專用的受版控小檔 `docs/.security-backing.jsonl`**；閘門（本機與 CI）只從**要推的提交樹**讀這個檔，不讀工作目錄、不讀 kill-log。原因：kill-log 在 scaffold 寫的 `.gitignore` 裡、不進消費專案版控，推送前的 CI 讀不到；不寫進治理帳 `docs/.governance-log.jsonl`，因為那本現在就有 20,480,865 位元組（2026-10-20 量，本 repo），比證據的單檔上限還大，閘門每次推送都要整本讀才找得到那幾行。
  - 背書檔進 `_BOOKKEEPING_FILES`（簿記檔名單），所以「寫完背書再提交」那一個提交不會讓背書自己變 stale；寫入用既有的追加寫法，單行上限 4096 位元組，配方改到的檔太多、一行裝不下時拒寫並請使用者拆配方，不截斷；閘門讀到截斷過的行（帶 `_truncated`）或超長的行一律判 `invalid:backing_truncated`。檔本身照證據檔的 16 MiB 單檔上限讀，超過時引用它的 guard_kill 項判 `invalid:evidence_too_large`。
  - 背書的冪等鍵是（護欄 id、種類、head_sha）：同鍵已有一筆就不再寫；第一筆寫錯（例如工具缺陷造成的錯判）時，`code-loop security-backing <護欄 id> --supersede` 寫一筆新的，帶 `supersedes: <被更正那一行的 sha256>`，閘門跳過被更正的行。閘門讀到多筆時只取 head_sha 等於要推的提交或是它祖先、沒被更正的那幾筆裡最新的一筆。沒有任何一筆判 `missing:backing_missing`；背書的 head_sha 不是祖先、或中間動到非簿記檔，判 `stale:binding_changed`。背書沒提交就推：閘門讀提交樹看不到，判 `missing:backing_missing`，本機與 CI 同一個答案。
  - **每組怎麼判（不沿用 `_backing_judge_groups`）**：那支函式靠 `covers` 選配方組，而且只回 strong 或 none 加一句理由，會把 `kill_unattributed`、`kill_timed_out_weak`、`kill_drifted`、`kill_abort`、`kill_error`、`kill_weak_only`、`survived` 全壓成 none（2026-10-20 讀 `scripts/lumos` 的 `_backing_judge_groups`）。本篇只沿用 `_backing_valid_rows` 的有效列判法，逐組判另寫一支：同一配方組有 survived 判 `failed:survived`；沒有非弱的 killed 時，照最後一筆的 verdict 對映上面的 invalid 代碼；判法優先序照 [[Systems/guard-kill]] 的 rc 優先序（survived→rc1、drifted/abort/error→rc2、弱證據不放行），方向一致。
  - ② test-quality check：閘門自己從要推的提交讀三份 capture，重跑同一套 load_receipt 與三階段核對，不採信作者存的 check 結果檔。`check()` 現在吃 argparse 參數並寫輸出檔，`load_receipt(folder)` 經 `read()` 從磁碟讀 `receipt.json`、`report.xml` 與快照檔，所以兩支都要抽：`load_receipt` 抽成吃「檔名 → 位元組」字典的純函式，核對本體抽成吃三份（或四份）載入結果的純函式，都放在 `scripts/test_quality.py` 自己裡面（它的家是 [[Systems/test-quality-cli]]），`check()` 與原 `load_receipt` 改成呼叫它們；抽出前後 `test-quality check` 的輸出與既有測試照綠；`scripts/lumos` 裡 `_TEST_QUALITY_BUNDLE_DIGESTS` 的雜湊跟著更新。`tq_capture` 項的 `path` 是一個目錄，底下固定三個子目錄 `baseline/`、`fault/`、`restored/`，另有重構相位時加 `refactor/`，名稱照 `check()` 的四個參數；少一個判 `invalid:receipt_not_executed`。配套缺檔（`_test_quality_load_bundle` 回部署不完整）而專案有資安登記痕跡時，整道擋 `toolchain_incomplete`，不放行。
  - 改 `scripts/test_quality.py` 與 bundle digest 會命中 [[Verification/測試品質第四輪修補驗證]] 的 `revalidate_when`（「改動…test-quality 拒收原因、bundle digest」），實作時要照那篇重驗一次並更新它的狀態。
  - **配方對到哪條護欄是新增的對應方式**：現有配方的 `covers` 是棧別檢核題的題號（`_backing_judge_groups` 拿題號 qid 比），沒有任何「這個配方守哪條 Invariant 或資安護欄」的比對。本篇新增：證據圍欄的 fault_sensitivity 項寫明 `recipe_ids` 與它對的護欄 id，背書只認圍欄列名的配方；配方改到的每支檔都要在那一項的 `bindings` 裡，不在判 `invalid:kill_recipe_unbound`（擋「拿一個不相干、早就 killed 的配方 id 冒充」）。不沿用 `covers`，也不從配方內容猜。
- **其他種類與全部 behavior**：工具自己的標準輸出檔，進消費專案版控；由那條護欄引用的 Verification 節點正文裡一塊 `lumos-evidence-v1` JSON 圍欄指路。
  - **跟盤點圍欄的關係**：盤點規定它自己的 `lumos-security-v1` 圍欄只准在 Systems，放在別處列 `misplaced_block`；`lumos-evidence-v1` 規定反過來：只准放在 Verification。兩種圍欄共用同一支讀法：把 `_secinv_blocks` 改成吃「圍欄標記」與「准放的節點類型」兩個參數，底下照舊用 `_fence_regions` 的嚴格結果（[[Systems/lumos-cli-read]] 已定另寫一份 toggle 或正則就是第二套邊界判定），盤點的 `misplaced_block` 判法只認 `lumos-security-v1`，不受影響。JSON 一律用 `_secinv_json_loads`（拒重複鍵、NaN）；它本身沒有深度上限，盤點是在呼叫端 `_secinv_parse_block` 接 `RecursionError` 轉成錯誤，所以證據圍欄這個新呼叫端也自己接 `RecursionError`，轉成 `invalid:evidence_fence_invalid`。圍欄未閉合、一篇多塊、壞 JSON 都判那篇的圍欄讀不出來（引用它的證據判 `invalid:evidence_fence_invalid`，見下），不退回「這篇沒有證據」，也不整道擋。
  - **配對規則**：一項只算 `control_id` 等於引用這篇的那條護欄的證據；項的 `kind` 必須等於該護欄 `evidence_refs` 指到這篇那一列的 `kind`，不等判 `invalid:evidence_kind_mismatch`；沒有任何護欄引用的項只列提醒 `orphan_evidence_item`、不擋。Verification 節點本身的 `status` 是 superseded 或 stale 時，它裡面的每一項都判 `stale:verification_node_stale`，不比盤點的 evidence_check 鬆。
  - **鍵名與必填**（頂層物件 `{"schema_version": 1, "items": [...]}`，兩個鍵都必填、不准有未列的鍵；`items` 每項不准有未列的鍵）：

### 綁版本與環境指紋

- 推送時以要推的那個提交為準：閘門用 git 讀那個提交裡每個綁定檔的 blob、證據檔與工具清單，跟證據記的比；任一不同、或綁定檔不在了，就是 stale。不讀工作目錄（見〈四〉的〈從提交樹產快照〉）。
- **報告本身也綁**：JUnit、SARIF、k6 的 `report_sha256` 讓「改了報告一行」變成 invalid；`tq_capture` 沿用 receipt 自己記的雜湊。作者把綁定的 blob 改成新版、卻不重跑測試時，報告雜湊沒變但綁定檔的內容是新的——這擋不住，因為雜湊只證明「這份報告與這些檔一起被提交」，不證明報告是用這些檔跑出來的；這一句寫進每份證據的 `limitations`，由〈機械做不到的判斷〉的「報告是不是真的跑出來的」承擔。
- 綁定集合至少要涵蓋：護欄所在 Systems 節點（護欄的家）about_code 列的全部程式檔、`test_sources` 列的測試原始檔、`fixture_globs` 在要推的提交樹上展開出的全部檔（夾具、共用 helper、runner 設定）、`environment_ref` 那支環境描述檔、`calibration_path` 那支校準輸出檔(d18);review 與 deployment 的審查紀錄也照這一條,家的程式檔改了審查就 stale;少一支就是 `binding_incomplete`（invalid）。借「每支檔有家」：家列了哪些檔，那條護欄的證據就得綁哪些檔，作者不能挑；測試原始檔與夾具則由作者明列——測試 id 推不回檔案（Gradle、pytest、Jest 的 id 形狀各不相同），所以照 test-quality 的做法要呼叫端明示。
- **工具天花板（綁定）**：作者沒寫進 `test_sources` 或 `fixture_globs` 的夾具與 helper，工具自動找不到（要讀懂各語言的 import 與讀檔路徑）；改了那支檔、沿用舊報告，舊證據不會 stale。這一句寫進每份 behavior、concurrency、fault_sensitivity 證據的 `limitations`，由 review 的 `independent_oracle` 與 `report_provenance` 那兩項人工判斷承擔。

### 每種格式的「合格」判定

所有格式共用三條：真的跑過（案例數或請求數或掃描檔數大於 0、有觀察時間、版本與綁定對得上）；目標有被評估到（指定的測試 id、規則 id、門檻真的出現在結果裡，宣告清單不能是空的）；失敗與 invalid 分開：failed＝證據有效地跑完、結論是負面，代表有缺陷（行為證據的目標斷言紅、掃描對宣告規則有未處置的命中、壓測安全計數超標，或故障證據裡拿掉防護後測試照綠的 survived——那是「測試咬不住」的缺陷）；invalid＝沒驗到（跑不起來、零案例、逾時、非目標失敗、格式或綁定不合格）。兩者都擋，但訊息不同。

**同一護欄同一種類有多筆證據**：每筆各自判；只要有任何一筆不是 qualified，這個種類就取那幾筆裡最差的判定（優先序 failed、invalid、stale、uncalibrated），不准用好的蓋壞的。逐筆判定照樣在 `security evidence` 列出，所以「一壞一好」時人看得到好的那份是 qualified、種類卻不是。作者把壞的那份從圍欄刪掉也不會轉綠：主線 tip 版有、推送版刪掉的項照算，除非有更新的同 control、同 kind、同 targets 項取代（見〈證據從哪來〉的〈證據項被刪也凍結〉）。

**SARIF 另寫嚴格解析，不共用新增告警閘的讀法**（2026-10-19 讀 `scripts/lumos` 的 `_lint_run_and_parse`）：那支函式會自己 `Popen` 執行指令，不是純解析；`results` 是 null 時用 `or []` 當成空陣列，缺 driver 名的 run 直接跳過，不看 invocations、notifications，同時接受 SARIF 1.0 與 2.1。這些對新增告警閘是刻意的寬鬆（要吃各家 linter，包括只吐 v1 的 dotnet），對安全證據正好是 invalid 條件。取捨：新寫一支只吃資料的嚴格解析給安全證據用；新增告警閘的既有行為一字不改。
- **uri 正規化現在就決定：不抽、各寫**。理由：那一小段現在內嵌在 `_lint_run_and_parse` 裡、沒有獨立函式；抽出來就得改一支會執行外部指令、有既有測試釘住的函式，只為了共用十來行；而兩邊的語意也不同（新增告警閘遇到解析不了的 uri 是跳過那一筆，安全證據要判 invalid）。安全證據自己寫一支，在本篇子系統裡測。
- 不選：直接共用 `_lint_run_and_parse`（要嘛新增告警閘開始拒收它現在吃得下的 v1 與缺欄位報告，要嘛安全證據把 null 當空陣列）。

**SARIF 的命中與處置**（決定 failed 與 qualified 的分界）：
- **命中**：`ruleId`（或 `rule.id`）是 `targets.rules` 裡宣告的規則的 result，`level` 是 `error` 或 `warning`、或 `kind` 是 `fail`，就是命中；`level` 沒寫時照 SARIF 規格的預設 `warning` 算。`note`、`none`、`kind` 是 `pass`、`notApplicable`、`informational` 不算命中。
- **處置**：result 帶 `suppressions`（含 `kind: inSource`，也就是 `nosemgrep`、`# nosec` 這類程式內註解）或 `baselineState: unchanged` 都**不算**處置，因為 AI 自己加一行抑制註解重掃就有；只有核可鏈上有一筆有效的 `suppression` 核可（`target` 是規則 id 加位置雜湊，位置雜湊＝規範化後的 `artifactLocation.uri`、`region.startLine`、`partialFingerprints` 的 sha256）蓋住的命中才算已處置。
- 有任何一個命中沒被核可蓋住，判 `failed:finding_unresolved`，`security evidence` 列出那幾筆的規則與位置，讓使用者決定修或簽。

**SARIF 證明不了「真的掃到東西」，要另一份覆蓋證明**（2026-10-19 查各工具官方文件與原始碼）：規格只把 `invocations` 的 executionSuccessful 列為選填，`rules` 可以只列打中的規則、`artifacts` 不必列全部掃過的檔；gitleaks 與 ZAP 的 SARIF 沒有 invocations，Trivy 預設有發現也回 0，OSV-Scanner 回 128 是「沒找到可掃的套件」、CodeQL 回 32 是「沒找到可分析的程式碼」。所以每個掃描工具在工具清單登記一種覆蓋證明，從固定的小集合裡選，閘門照它讀 `coverage_path` 那份工具自己的 JSON 或 SARIF 欄位：SARIF invocation 成功且無 error 通知、Semgrep 的 `paths.scanned` 非空、OSV-Scanner 以 `--all-packages` 輸出的套件清單非空、Trivy 或 Checkov 的設定檢查計數（Successes、resource_count）大於 0、ZAP 的內部統計（登入成功數、送出請求數、主動掃描 URL 數）大於 0。集合外的工具判 `coverage_unproven`（invalid），要用就先補讀法與正反樣本。退出碼一律只拿來交叉比對，不當主判據，因為各工具語意互相衝突（gitleaks 的 1 同時代表有發現與出錯）。

**依賴掃描結果跟著漏洞庫變**：OSV-Scanner、Trivy 查的是會更新的漏洞庫，釘工具版本不夠。證據要記 `vulndb_fetched_at`；距今（UTC 日期）超過 14 天算 `stale:vulndb_stale`（d14：第 14 天仍有效、第 15 天起 stale）。`vulndb_fetched_at` 晚於 `observed_at` 判 `invalid:vulndb_after_observed`（掃描不可能用到觀察之後才抓的漏洞庫；擋「填一個未來日期就永遠不 stale」）。

**合法對照強制存在**：behavior 要宣告合法對照案例 id；concurrency 要宣告合法流量成功計數指標；掃描類要有校準檔。前兩者缺了或是空陣列判 invalid，掃描類缺校準判 uncalibrated；三者都擋，不是提醒。

**「找到 0 個問題」不等於證成**：掃描類只有「跑過、沒找到」加上「同工具、同版本、同規則對已知陽性樣本找得到」兩份一起，才算 qualified；只有前者判 `uncalibrated`，照擋。校準檔必須對 `targets.rules` 的每一條都命中，少一條判 `uncalibrated:calibration_rule_missing`。校準樣本依 d15 不提交進消費專案版控：在臨時隔離副本裡由一支受版控的產生腳本現場產生、掃完就刪，綁定的是那支腳本與校準輸出檔；跟正式掃描同一版本的工具與規則；工具或規則升版就要重做。

### 讀不可信資料的上限與失敗處理

證據檔是不可信資料，而且比筆記大得多（大專案的 SARIF、JUnit 動輒數 MB）。盤點的上限（單檔 2 MiB、總量 64 MiB、一萬檔）是為 Markdown 筆記定的，不沿用：
- 單一證據檔上限 16 MiB：比 test-quality `read()` 的 10 MiB 寬，因為閘門從 git 讀位元組直接餵只吃資料的解析，不經 `read()`；16 MiB 夠裝中型 repo 的 Semgrep、CodeQL SARIF，再大多半是掃描範圍設錯。
- 一次判定讀的證據總量上限 256 MiB，**按不同的 blob 算一次**：同一份專案級 JUnit 被一千條護欄引用，只算一次額度。累計順序固定：所有要讀的證據 blob 照（路徑、blob）排序後依序累加，超過的那一份與之後的每一份判 `invalid:evidence_too_large`；所以新增一條護欄不會因為排序把別條原本合格的證據推過額度線，除非它帶進一份新的、排在前面的大檔，而那會在輸出裡指名。
- 證據項總數上限 10000（跟盤點檔數上限同一個量級）：超過時照（護欄 id、種類、路徑）排序，第 10001 項起判 `invalid:evidence_too_large`。
- 超過任一上限，只把超限的那幾項判 `invalid:evidence_too_large` 並指出是哪個檔，不判整道讀取不完整，所以一份過大的 SARIF 只擋引用它的那幾條護欄。
- **深度**：JUnit 的 `junit()` 改成用 `xml.etree.ElementTree.XMLParser(target=…)` 自訂 target 邊解析邊數深度（start 回呼加一、end 回呼減一，超過 64 層立刻停;C 版解析器的 iterparse 不收自訂 builder,所以不用 iterparse,見 [[Systems/test-quality-cli]]），超過判 `invalid:report_too_deep`；同時把每個案例處理完就清掉元素，不先建整棵樹（r2 資源席實跑：6.7 MiB 的深巢狀 `<a>` 現在照吃、最後才報零案例，常駐 387 MiB）。改的是 [[Systems/test-quality-cli]] 的 `junit()`，拒收訊息字串一字不改，`test-quality check` 的輸出照舊。JSON 各個新呼叫端（證據圍欄、SARIF、k6、工具清單、核可鏈、背書檔）自己接 `RecursionError`，轉成那一項 invalid（`report_too_deep` 或那個檔的「讀不出來」），不落到整道 `evaluation_error`。
- **拒收帶型別**：`junit()` 現在對所有拒收都丟無型別的 `ValueError`、訊息是英文字串；[[Systems/test-quality-cli]] 的 WHY 否決過「各呼叫端比對例外訊息字串」。改成丟 `ValueError` 的子類別 `JUnitRejected`，帶一個原因代碼欄（既有呼叫端照舊接得到 `ValueError`），對映：`zero testcases`→`zero_cases`、`duplicate test identities`→`report_duplicate_identity`、`runner/suite errors`→`suite_error`、suite 計數矛盾→`count_mismatch`、`testcase missing name` 與 `outcome outside testcase` 與根元素不是 testsuite(s)→`report_malformed`、XML 語法錯或含 DTD→`report_unparseable`、深度超限→`report_too_deep`。SARIF、k6、證據圍欄的 JSON 讀不出來一律 `report_unparseable`。
- **快取只存濃縮事實**：同一次判定內，以（路徑、blob）當鍵快取的是判定要用的事實——JUnit 存案例的（身份、狀態、是否斷言失敗）、SARIF 存 driver 名與版本、每條宣告規則的命中位置與覆蓋證明的計數、k6 存版本、腳本雜湊與指標計數——不存解析樹。每份證據濃縮後最多 10 萬筆案例或命中，超過判 `invalid:evidence_too_large`。一份專案級 JUnit 被一千條護欄引用，只解析一次。
- **解析後記憶體預算**：同一時間只解析一份證據，解析完濃縮、丟掉解析樹再讀下一份。峰值約為單檔上限的 20 倍（r2 資源席實測 11.6 MiB 的 SARIF 經 `_secinv_json_loads` 常駐約 219 MiB），所以單檔 16 MiB 的峰值約 320 MiB，加上濃縮事實；不會因為 256 MiB 總量上限而同時留著十幾棵樹。
- git 讀取批次化，走既有的 `_nodehome_cat_blobs_capped`（先 `--batch-check` 問大小、超過單檔上限的不讀進記憶體、有總量上限與逾時，見〈四〉的〈從提交樹產快照〉），每批讀進來的位元組合計不超過 64 MiB，處理完這一批再讀下一批，不一次把三版的快照與全部證據都放在記憶體裡。
- **Verification 節點太大**：證據圍欄所在的 Verification 節點走盤點快照，單檔上限照盤點的 2 MiB；超過時不整道擋（不算讀取不完整），只讓引用那篇的護欄的證據判 `invalid:evidence_node_too_large`，訊息給拆法：一條護欄一篇、或一個種類一篇，綁定很多的家把 `bindings` 拆到多項。Systems 節點超過 2 MiB 照盤點原規則，整道讀取不完整。
- **時間預算**：整道判定每個 ref 60 秒（跟 pre-push 對其他閘每個 ref 判定本體 60 秒的預算同一個數），超過就停，整道擋 `evaluation_timeout`，訊息指出判到哪條護欄、跑了多久；不 fail-open。`code-loop check` 在 `evaluation_error` 與 `evaluation_timeout` 都回退出碼 1（pre-push 只把 1 當擋下，其他非 0 非 128 以上的退出碼會 fail-open 放行，2026-10-20 讀 `scripts/hooks/pre-push` 的 code-loop 那一段）；pre-push 新增的 `--security-only` 那條路徑把任何非 0 退出碼都當擋下。
- 判定函式裡任何沒預期到的例外（型別錯、遞迴過深、記憶體錯誤）一律轉成擋下，整道代碼 `evaluation_error`，訊息指出當時在判哪條護欄、哪個檔；不放行、不印 traceback 給推送流程。
- **判定層不兜例外、型別閘只在讀進來那一層**（代碼審 r3,同類第二次出現後改整類形狀）：讀法（解析外來位元組、讀外來欄位的那幾支）把外來資料缺欄或型別不對判成那一項的代碼並講哪一列哪一欄，回代碼、不丟例外；判定碼與它呼叫的程式（含 fault_check、核可鏈驗章）不寫接一般例外的 except，丟什麼都往上判整道 `evaluation_error`——單項不合格可以被例外蓋掉放行，程式自己的錯不准落到那一格。原本設計的專用例外類別從沒有丟出點，拿掉。讀進來的日期與時間離上下限不到 366 天就判看不懂（S67），不在各個加天數的地方各自接。
- **fail-closed 是刻意偏離同族**：同族的閘（新增告警閘等十來處）遇到缺環境或內部錯誤走 `_gate_failopen`——放行、落一筆帳，不讓推送整個卡死。這一道不走 `_gate_failopen`：母計劃 d9 要「判不清就擋」，`evaluation_error`、`evaluation_timeout` 都擋；誤擋的出路是使用者簽 gate 降級（見〈四〉的〈哪些整道擋下可以降級〉）。

以下由 review 證據種類承擔。依 d2，要有一筆非作者的審查紀錄才放行；依 d8，紀錄分 AI 審與人審，兩者能放行的範圍不同。紀錄寫在 Verification 的證據圍欄（`format: review_record`），閘門核：
- 紀錄存在；`reviewer` 跟 `author` 比對時先去頭尾空白、統一全形半形、不分大小寫，任一作者等於審查人判 `invalid:review_not_independent`。

- **壓測與動態掃描的目標限制**：證據要記目標位址；不是回環位址、也不在核可清單上，判 `target_not_authorized`（invalid）。這只檢查作者記的值；真正防誤打靠消費專案腳本自己檢查（order-demo 的 k6 腳本已經在非本機時中止）。
- **之後接新工具**：能出 SARIF、JUnit 的工具不需要改 lumos，只要登記清單與校準樣本；只有吐自家格式又無法轉 SARIF 的工具，才在 lumos 加一個讀法，而且要先有那個工具的正反樣本。
- 理由：一個格式一個讀法，比一個工具一個讀法少；SARIF 已是本 repo 新增告警閘在用的格式。
- 不選：每個工具寫專屬解析（工具多一個就多一套）；lumos 代為安裝或執行（違反零依賴、成本與授權都不在 lumos）。

**k6 第一個接**：k6 跑在消費專案（order-demo 既有的搶購壓測腳本可參考，腳本的家在 order-demo 自己的建置與啟動節點）；釘版本照清單（容器映像 digest 或 release 二進位的 sha256）；腳本一律開新的機器可讀摘要並寫到固定路徑。安全門檻對應主張的方式以 OD-04「重送與並發不能讓他人操作生效」為例：腳本用 B 身分對 A 的有效訂單重送與並發，自訂計數 `foreign_effects`（伺服器回成功的次數，開頭先 `add(0)`）門檻是等於 0、`foreign_rejected` 大於 0（攻擊流量真的送出去了），另一段 A 自己的合法流量 `legit_ok` 大於 0；整體請求數 `http_reqs` 不少於清單登記的 `min_requests`；k6 看不到資料庫，所以「訂單與庫存保持不變」另由同一次執行後的整合測試讀資料庫（behavior 證據），兩份一起才算這條的 concurrency 主張驗完。

**要使用者核可的**（不由 AI 決定）：每個專案裝哪些工具與版本、執行預算、壓測與動態掃描的目標，依 d4 逐專案、逐工具在要用時問使用者，AI 不自行安裝；OD-04 的 k6 實跑已依 d3 核可（order-demo、k6 v2.3.0、條件照母計劃 d8）；校準樣本依 d15 不進消費專案版控，現場產生、用完刪掉。

## 四、閘門：code-loop check 的「安全證據」判定

**位置**：`code-loop check` 的判定函式（`_codeloop_guard_verdict`）裡，跟表態閘、新增告警閘並列、不看 tier（母計劃 d9 要求所有專案都擋），但**排在所有放行早退之前**：取到要推的提交（marker_sha）之後、推導 diff 範圍之前就判。
- 為什麼不照原案排在新增告警閘之後（2026-10-19 讀 `_codeloop_guard_verdict`）：那個位置前面有五條直接放行的早退——取不到 HEAD、merge-base 等於 HEAD、算不出 merge-base、全零起點找不到真起點、pitfalls 失敗（`return _fin(pf_fail)`）。排在後面，這五條路上安全判定根本跑不到，跟母計劃 d9 的「判不清就擋」衝突。
- 選「往前排」而不是「把這五條早退對有資安登記的專案改成擋」：安全判定看的是要推的那個提交的內容與 merge-base，不需要 diff 範圍與 tier，排到最前面就不必去改五條早退的既有放行行為（它們對其他幾道仍然照舊）。
- **先判有沒有登記痕跡，再判起點**：取到要推的提交之後，第一步是廉價預檢（見下〈從提交樹產快照〉），對要推的提交與主線 tip 各跑一次；兩邊都沒有登記痕跡就回 None（`no_registration`），後面的淺層 clone、起點、主線認定一概不判。所以沒登記的專案在淺層 clone 的 CI 上也照舊放行，〈不受影響〉那句「輸出與退出碼跟現在逐字相同」才成立。主線認不出來時只對要推的提交預檢。
- 取不到要推的提交時：工作目錄有資安登記痕跡（見下〈擋下條件〉）就擋，原因代碼 `commit_unavailable`；沒有痕跡照舊放行。
- 形狀照新增告警閘那一步：沒擋回 None，擋了回帶 `reason_kind: security_evidence` 的結果；帶 `--keep-going` 時各道各自記、各自印。
- **tag 與其他非分支的 ref 也判**：現在 pre-push 對不是 `refs/heads/*` 的 ref 根本不叫 `code-loop check`、只提醒，CI 也只聽 main 的 push（設計審 r1 實跑,見 `governance/review-reports/安全主張驗收閘/r1-intake.md` 的〈r1 機械重現〉）。新增 `code-loop check --security-only --at-sha <sha>`，只跑這一道；pre-push 在非分支那條路徑也呼叫它、照擋（任何非 0 退出碼都當擋下）；CI 加 `push: tags` 觸發，跑同一個指令。母計劃 d9 要的是「推得出去的東西都判過」，不只分支。刪除 ref（本機那一側全零）照 pre-push 現在的寫法直接跳過，不判。
- **PR 事件不跑這一道**：依 d9 不設伺服器端保護，CI 的 code-loop gate 那一步只在 push 事件跑（`if: github.event_name == 'push'`），PR 上照舊不跑，所以本篇不定 PR 的起點。
- 本機與 CI 判定相同：核可都在核可鏈、驗的是內容，兩邊讀同一份推送版的鏈、對同一個主線 tip 驗；日期一律取 UTC。前提是同一個主線 tip 與同一個 UTC 日期（見〈一〉的〈判定跟日期有關〉）；本機的主線 tip 是本機最後一次 fetch 的位置，CI 的是推送當下的遠端，兩者不同時以 CI 為準。CI 那一步目前沒帶 `--keep-going`，訊息會只印第一道擋下，實作時一起評估。

**從提交樹產快照**：盤點的 `_secinv_snapshot` 只會從工作目錄逐層開檔，`_secinv_build` 吃的是快照字典，接縫就在這裡。新增一支 `_secinv_snapshot_tree(repo_root, sha, vault_rel)`，**建在既有的 `_nodehome_list`（提交樹列檔加內容編號、連結檔與子模組不算一般檔）與 `_nodehome_cat_blobs_capped`（先 `--batch-check` 問大小、超過單檔上限的不讀進記憶體、有總量上限與逾時）之上**，不另寫第三份 `ls-tree`／`cat-file --batch` 解析（`scripts/lumos` 既有註解記過：另寫一份批次讀取被架構席點成第二套）。產出跟 `_secinv_snapshot` 同形狀的快照，沿用同一組容量常數與錯誤代碼：
- 轉接：`_nodehome_list` 回報為連結檔的 → `symlink_rejected`；子模組與其他特殊模式 → `special_file`；`_nodehome_cat_blobs_capped` 回報超過單檔上限 → `file_too_large`，總量超限 → `total_size_exceeded`，檔數超過 → `too_many_files`；路徑含換行（`_nodehome_cat_blobs` 遇到這種路徑整批回 None）→ 那一篇記 `unsupported_safe_read`、其他照讀，整批回 None 時整份快照判 `enumeration_failed`；不是 UTF-8 → `not_utf8`。
- 快照進 `_secinv_env` 照舊先查 NFC 碰撞（兩篇路徑 NFC 後相同就兩篇都不採用，`normalized_path_collision`），這是 [[Systems/lumos-cli-read]] 記過「提交樹、考試樹等其他 Env.from_texts 入口」的同族坑，S56 釘住提交樹這條路徑。
- **vault 路徑各版各自解析**：`vault_rel` 不從工作目錄找，對每一版從那一版的提交樹解析（照 `find_vault` 與 `_secinv_select_vault` 的規則：同一層找到不只一個圖譜就報錯、不猜）。圖譜在 merge-base 版或主線 tip 版存在、推送版消失或搬家時：推送版那一邊照搬過去的新路徑讀；三版的條目以護欄 id 對齊，不以路徑對齊，所以搬目錄不會讓凍結比對落空；推送版整個圖譜不見而另兩版有 active 資安條目，那些條目照必驗集合判（判 `missing:control_removed_unapproved`）。
- 要推的版、merge-base 版、主線 tip 版都用它，不讀工作目錄，所以 checkout 停在 main 而推的是別的分支時也判對版本。`security list` 不走這一支（它維持只讀工作目錄、不執行程序）；S4 比的是「`security evidence --commit <sha> --json` 的盤點區塊」與「在那個提交的乾淨 checkout 上跑 `security list --json`」。不沿用 `_drift_tree_env`（它沒有盤點那套容量上限）。
- 廉價預檢：先用一次 `git grep -l -F lumos-security-v1 <sha> -- <vault>` 找出提到這個字樣的檔；一篇都沒有就直接判「沒有登記痕跡」，不建完整快照。有命中才建快照、照盤點的嚴格讀法判有沒有真的圍欄（散文裡提到這個字樣不算痕跡）。

**主線怎麼認**（不另寫第四套，用既有那一組）：
- 主線候選照 `_push_mainlines`（遠端 HEAD、main/master 的 upstream、遠端 main/master，跳過「就是這次被推的那條」），再加本機 main/master（手動 `code-loop check` 的預設起點 `_codeloop_default_base` 也是這樣加）；分岔點照 `_push_range_start` 的算法，`git merge-base --all <頂端> <全部候選>`。理由：那一組已經處理過「remote 未必叫 origin」、「CI 的 checkout 不建 origin/HEAD」、git-flow 與 fork 兩頭顧不到（固定順序取第一個會錯）、git 查詢逾時被當成「找不到」而縮成少查——這些坑本篇重寫一份會再踩一次。
- **不沿用 `_push_range_start` 的退路**：它找不到主線時退到「遠端舊值、全零從空樹、或只查最後一個提交」（2026-10-20 實跑：沒有 remote、沒有 main 的 repo，`_push_range_start` 回空樹起點，見 r2-intake〈r2 機械重現〉），那對漂移檢查是少查，對凍結比對是整個失效。所以本篇只借候選與分岔點的算法，找不到主線時另判：
  - 有登記痕跡而認不出主線（有設 remote 但本機沒有任何追蹤 ref、git 查詢失敗或逾時、候選全部被跳過）→ 擋 `mainline_unknown`，訊息給兩條路：先 `git fetch`，或在**主線上**的 `.lumos/config.json` 設 `security_evidence.mainline`。
  - **只有確定是新 repo 才當空樹**：沒有設任何 remote、也沒有本機 main/master（`_mainline_ref` 在這種 repo 回 None，2026-10-20 實跑），起點＝空樹、主線 tip＝無，所有護欄當成新增照判。有本機 main 而沒有 remote（例如 order-demo 現況：`git remote -v` 空、本機有 main，2026-10-20 查），主線就是本機 main。
  - `security_evidence.mainline`（只收 `refs/remotes/` 開頭的遠端追蹤 ref，例如 `refs/remotes/upstream/trunk`）**只從主線 tip 版的設定讀**:先用全部候選挑出主線 tip,那一版的設定有寫就改用它;它指到的 ref 不存在照擋 `mainline_unknown`。被推的提交自己寫的不採用、只印一行(代碼審第一輪資安席:被推的提交指定「拿誰比」,改一個檔就讓凍結比對與核可鏈前綴都變成自己對自己)。
  - 主線 tip 怎麼挑:全部候選一起算 `git merge-base --all <頂端> <全部候選>`,取歷史最長的分岔點;主線 tip 是含那個分岔點的候選裡歷史最長的一個(不靠候選順序,規格對照席)。
- **推的就是主線本身**（推 main、CI 的 main push 事件）：主線 tip＝推送前的位置——pre-push 用遠端舊值，CI 用事件的 `before`。舊值全零（首推主線）時照「新 repo」那條判；舊值在本機找不到（force push 把主線退回舊提交）時擋 `mainline_unknown`，訊息寫明這是 force push 退版，不退成空樹或只查最後一個提交；依 d9 CI 本來就是事後，主線已經退回去了，紅燈只提醒有人沒照規矩。
- **工具天花板（主線）**：主線 tip 從本機 ref 讀；AI 能改本機 ref（`git update-ref`）就能造一個假主線。CI 用 checkout 時從遠端抓來的 ref，所以 CI 那一側是最後的核對（依 d9 是事後）；這一句寫進 `security evidence` 的 `limitations`。

**起點一律是 merge-base**：
- 起點＝要推的提交跟主線 tip 的 merge-base（照上面〈主線怎麼認〉）。不用「這個 ref 的遠端舊值」當起點——那是這個分支上次推送的位置，中途若有一次繞過把縮小推上去，之後每次比的都是已經縮小的版本。
- 多個提交的推送一律只對 merge-base 與主線 tip 判，不逐提交、不看要推的提交的母提交。
- 主線存在但跟要推的提交沒有共同祖先：擋 `freeze_base_unavailable`。
- 淺層 clone（`git rev-parse --is-shallow-repository` 是 true）：擋 `shallow_clone`，訊息給一行 `git fetch --unshallow`；CI 的 checkout 已是完整歷史（`fetch-depth: 0`）。這兩條都只在有登記痕跡時才判（見上〈先判有沒有登記痕跡〉）。

**必驗集合與判定輸入以三版為底**（承接母計劃 G1 的凍結要求）：
- 必驗集合 = 推送版、merge-base 版、主線 tip 版三版裡 active 且關注面含 security 的全部條目的聯集（以護欄 id 對齊）。加進主線 tip 版，是因為在途分支從 M0 分出、主線之後在 M1 新增 active 護欄 C，F 與 M0 都沒有 C；只看推送版與 merge-base 版，C 就漏了，對 F 打的 release tag 也會放行。
- 推送版裡沒有、或被降成 candidate 或 retired、或 `concerns` 拿掉 security 的條目，除非核可鏈上有一筆有效的 `revision` 核可，否則照樣當必驗、用另外兩版裡較新的那一版（主線 tip 版優先）的內容判；被刪的那條沒有證據可讀，判 `missing:control_removed_unapproved`。主線 tip 版才新增的條目，推送版沒有它（分支還沒接上主線）也判 `missing:control_removed_unapproved`，訊息寫「主線新增了這條，先接上主線」。
- **判定輸入也凍結，「變弱」只比這幾樣**：同一條護欄，推送版跟 merge-base 版、主線 tip 版各比一次，下列任一項變少就算變弱——`required_evidence`、`threat_categories`、`assets`、`surfaces` 少了任何一個值；`evidence_refs` 的種類集合少了一種；某個種類的 `evidence_refs` 列數變少；`threat_table_version` 換成另一版而那一版對這條護欄算出的最低種類比原版少。**同一種類把指到的 Verification 節點換成另一篇不算變弱**（重收證據的正常做法就是新開一篇、改指過去），新節點照常判。
- 變弱而沒有核可鏈上的 `revision` 核可時，照嚴的判：集合欄位取聯集；某種類的列數比舊版少時，缺的那幾列判 `missing:evidence_ref_removed`；表版號取最低種類較多的那一版——但依 d11,改用的那一版表若已有雙家協定核可紀錄(在鏡像常數的核可版號集合裡),換版號不算變弱、照新版判。`security evidence` 列出哪一欄變弱、照什麼判。只新增不刪除不算變弱。
- **判定輸入雜湊**（例外與修訂核可蓋住的內容）＝規範化 JSON 的 sha256，內容是 `required_evidence`、`threat_categories`、`assets`、`surfaces`（各自排序）、`threat_table_version`，加上 `evidence_refs` 的「種類 → 列數」，**不含** `evidence_refs` 指到的節點名，所以重收證據換節點不會讓例外與人審核可作廢。
- **核可修訂紀錄**記在核可鏈（`type: revision`，見〈核可鏈〉），不放在 Systems 節點裡，所以整篇 Systems 節點刪掉、改名或搬家都還讀得到。內容是 `control_id`、`before`（revision 與判定輸入雜湊）、`after`（同上）或 `removed: true`、`decision_ref`；一筆只核可「從這個雜湊變到那個雜湊」，同一條護欄改成別的樣子要另一筆。`decision_ref` 指不到有效決策（走 `_pq_decision_state`）或缺任何一欄，那一筆不算數。舊的修訂核可在到期日後自動失效，不會被拿來重放（見〈核可鏈〉的到期上限）。
- 起點或主線算不出來而專案有資安登記痕跡：擋，代碼見上；判不清不放行。

**擋下條件**（任一）：
- 必驗集合裡有任何條目的整體判定是 unsound（規則見〈一〉的彙總規則）。
- 盤點讀取不完整或登記錯誤（`errors`，不含姊妹計劃的格子層錯誤 `cell_errors`；閘門不讀 `cell_errors`），而三版任一有資安登記痕跡：判不清就擋，不當零條目放行。Verification 節點超過單檔上限不算這一條（見〈二〉的〈Verification 節點太大〉）。
- **登記痕跡只認 `lumos-security-v1` 圍欄**（盤點讀到一塊合格的或是 `malformed_block`）；只有 `flag/security-relevant` 標籤、零條目的專案不算痕跡，只在 `security evidence` 與 `--json` 列提醒。2026-10-19 在工具鏈自己的工作樹實跑 `security list`：`read_complete: true`、`registration_complete: false`、零條目、`errors` 空，有兩篇只帶標籤、沒有圍欄——照舊判法會被當成「有痕跡又登記不完整」擋下工具鏈自己的每次推送，照現在的判法不擋（設計審 r1 實跑,見 `governance/review-reports/安全主張驗收閘/r1-intake.md` 的〈r1 機械重現〉）。
- 「全部條目被刪」不另設代碼：三版的聯集已經把被刪的條目留在必驗集合，每條各自判 `missing:control_removed_unapproved`。只有 candidate、從來沒有 active 條目的專案，三版的必驗集合都是空的，照下面〈不受影響〉放行並列提醒。
- 主線認不出（`mainline_unknown`）、凍結比對的起點算不出來、淺層 clone、取不到要推的提交、test-quality 配套缺檔（見上）。
- 核可鏈的主線 tip 版不是推送版的開頭一段（`approvals_diverged`，見〈核可鏈〉）。
- 判定函式本身出錯（`evaluation_error`）或超過時間預算（`evaluation_timeout`）。
- 例外過期、超過 30 天、缺欄位、核可鏈上沒有對應的有效核可或核准的內容跟現在不同——這些情況例外不算數，底下的種類照原判定。

**擋或只提醒的設定**：`.lumos/config.json` 的 `security_evidence.gate`，值域只有 `block`（預設）與 `warn`。形狀照 `lint_new.gate`（那一族的值域是 `block|warn|off`，`node_home.gate` 那一族是 `on|warn|off`，兩族不同；本篇不收 `off`）；讀法沿用 `_lint_new_config(..., from_snapshot=True)` 那一型，從要推的提交讀設定位元組，不讀工作目錄；看不懂的值、型別錯、`off` 一律當 `block`，並印一句「security_evidence.gate 的值看不懂，照 block 判」（同族慣例是看不懂照預設並講一句）。
- 改成 `warn` 時判定照算、照印、照記帳，只是不擋；但要核可鏈上有一筆有效的 `gate_setting` 核可（`target` 是 `security_evidence.gate`，內容是 `{"value":"warn"}`，最長 30 天），沒有、過期或驗不過一律當成 `block`，並印一行說明為什麼。所以 AI 改一行設定關不掉這道閘，把歷史上簽過的 warn 貼回來也會因為到期或對不上鏈而無效；依 d13 不給升級過渡期;誤擋時要退，簽一筆就能降成只提醒，最長 30 天，到期自動恢復擋。

**哪些整道擋下可以降級**（核可鏈讀的是推送版與主線 tip 版，不依賴 merge-base 版，所以多數整道擋下時 gate 設定照樣驗得出來）：

| 整道代碼 | warn 有沒有效 | 原因與出路 |
|---|---|---|
| `read_incomplete`、`registration_error`、`toolchain_incomplete`、`freeze_base_unavailable` | 有效 | 鏈從推送版讀、對主線 tip 驗前綴，不需要 merge-base |
| `shallow_clone` | 主線 tip 的物件讀得到時有效 | 根本解是 `git fetch --unshallow` |
| `evaluation_error`、`evaluation_timeout` | gate 設定先在自己受保護的那一步解出來；錯誤發生在那一步之後時有效，發生在讀設定或驗鏈本身時無效 | 無效時照擋，訊息指出錯在哪一步 |
| `mainline_unknown`、`approvals_diverged` | 無效 | 沒有可信的主線鏈可對，鏈本身不可信；出路是 `git fetch`、在主線上設 `security_evidence.mainline`、或把分支接上主線 |
| `commit_unavailable` | 無效 | 什麼都讀不到；出路是修好 git 狀態 |
| 新 repo（空樹起點） | 有效，鏈第一筆照〈第一次釘金鑰〉的規則收 | — |

**不受影響**：
- 沒有任何資安登記痕跡的專案，這一步回 None、不寫治理帳，輸出與退出碼跟現在逐字相同；只在 `--json` 輸出多一個鍵 `security_evidence: {"status": "no_registration"}`，文字輸出不加行。這樣沒登記的專案每次推送不會弄髒工作樹、也不讓治理帳增長；淺層 clone 的 CI 也照舊放行（見上〈先判有沒有登記痕跡〉）。
- 純業務合約（concerns 只有 business）不進必驗集合。
- candidate 不擋、只列提醒（d12）；candidate 放超過 30 天（以那條護欄的 revision 日期或寫入那一版的提交日期算）在 `security evidence` 標出。
- review 種類照 d2、d8 判，沒有合格的審查紀錄或過期就擋（見〈機械做不到的判斷〉），不再有「只宣告不擋」的狀態。

**訊息形狀**（由 `_cl_say_sec_block` 印，三段式）：每個擋下的「護欄 × 種類」：
- 發生什麼：`安全證據 擋下：OD-01 [fault_sensitivity] invalid:zero_cases 證據 governance/…/receipt.json`；護欄層的問題寫成 `安全證據 擋下：OD-01 [護欄] insufficient_required_evidence`。
- 為什麼在意：一句白話，例如「這條安全主張現在沒有一份真的跑過的故障證據，等於沒驗」。
- 怎麼修：指令獨立一行；最後一行指路 `lumos security evidence` 看全表。JSON 鍵 `security_evidence` 帶完整逐條判定。
- 放行時也印提醒：7 天內到期的核可（例外、gate 設定、人審、修訂、金鑰）、7 天內會變 `vulndb_stale` 或 `review_expired` 的證據，各一行，含到期日；不擋。

### 核可物件：例外與 considerations 共用一套

母計劃 d9 的「例外只有使用者能核可、最長 30 天」在兩篇計劃有兩個入口：本篇護欄的 `exception`，與姊妹計劃格子的 `considerations`（`risk_accepted` 與 `not_applicable`）。兩者用同一個核可物件形狀、同一支檢查函式（從既有 `_secinv_check_exception` 長出來），不各寫一套；核可本身（誰核可、哪天、到哪天）一律記在核可鏈，物件裡不放簽章：

| 鍵 | 例外 | considerations 的 risk_accepted | considerations 的 not_applicable |
|---|---|---|---|
| `decision_ref`、`reason`（v1 既有） | 必填 | 必填 | 必填 |
| `compensating`（補償措施） | 必填 | 必填 | 不填 |
| `expires_on`（v1 既有；要等於核可鏈那一筆的 `expires_on`） | 必填 | 必填 | 不填（物件不寫；核可鏈那一筆照樣有到期日，見下） |
| `covers_kinds`（蓋住哪些證據種類） | 必填 | 不填 | 不填 |

- 核可鏈上對應的那一筆：例外是 `type: exception`、`target` 是（護欄 id、`covers_kinds` 排序後的清單），`content_sha256` 蓋住 `control_id`、`control_revision`、判定輸入雜湊（〈判定輸入也凍結〉）與物件的全部鍵；considerations 是 `type: consideration`、`target` 是格子 id，內容蓋住入口、資產、類別、角色、outcome、表版號與物件的全部鍵（姊妹計劃〈四〉列的那幾樣）。
- **30 天怎麼算**：用核可鏈那一筆的 `approved_on` 與 `expires_on`。`expires_on` 減 `approved_on` 小於等於 30 天有效，31 天起無效（`exception_too_long`）；`approved_on` 晚於今天（UTC）那一筆判 `approval:approval_in_future`；`expires_on` 當天有效、隔天起無效（`exception_expired`）。`approved_on` 由 `lumos security approvals payload` 自動填當天 UTC 日期，使用者不手填，所以台灣清晨簽的不會因為本地日期比 UTC 大一天而被當成未來。
- 物件找不到核可鏈上對應的有效一筆判 `exception:exception_unapproved`；有對應 `target` 的有效一筆但 `content_sha256` 對不上（例如護欄 revision 或判定輸入變了）判 `exception:exception_content_changed`，要使用者重簽。
- 每次判定都用當天 UTC 日期重算，過期隔天自動恢復擋，不需要任何人去改狀態。例外只蓋「擋不擋」，不改證據判定本身，`security evidence` 照樣顯示底下是 invalid 還是 missing。
- 用到例外時在治理帳記一行（閘名 `security-evidence`，護欄、種類、到期日、核可決策、核可鏈 seq）；冪等鍵是（護欄、種類、核可鏈 seq），**只在這筆核可第一次被用到時寫**。不用 head_sha 當鍵：帳本提交本身就是新的 head_sha，用它當鍵會讓例外有效的整段期間每次推送都多一行、工作樹每次都髒。

### 核可鏈（d10，取代 d7 的分散簽章）

**為什麼不是 PR 核准**（2026-10-19 核對現況，d1 原寫「CI 端核對該例外列是由使用者核准的 PR 帶進來的」，做不到）：
- 本 repo 的 CI（`.github/workflows/ci.yml`）在 push 到 main 與 pull_request 兩種事件觸發，但 code-loop gate 那一步只在 push 事件跑；PR 上不跑，等例外合進 main 才判，已經晚了。
- CI 的權限是 `contents: read`，讀不到 PR 的核准紀錄；`scripts/lumos` 唯一呼叫 GitHub API 的地方是 lint-watch 查工具最新版本，沒有任何讀 PR 核准的程式。
- AI 推送與開 PR 用的就是使用者本人的 GitHub 帳號，GitHub 上分不出這個核准是使用者按的還是 AI 按的；而且 GitHub 不准 PR 作者核准自己的 PR。

**為什麼不是提交簽章（d6）**：d6 用 `git blame` 找最後改到例外那幾行的提交、再 `git verify-commit`。提交會被重寫：壓成一個、rebase、合併提交、GitHub 的 squash 合併都會產生新提交，簽章不是消失就是換人；排版或 `lumos regen` 動到那幾行，blame 就指到 AI 的提交；例外跨多行時「那幾行」怎麼取沒定；簽章只綁那幾行文字，AI 只改外層護欄的要求，舊核准照樣蓋住新內容。

**為什麼不是各物件自己帶簽章（d7）**：d7 改成簽內容、簽章放在被核可物件的 `signature` 欄、准用金鑰取 merge-base 版的 `.lumos/security-approvers`。設計審 r2 指出它可以重放：gate 降級與修訂紀錄沒有到期日、也沒綁專案，簽過一次的 warn 能從 git 歷史貼回來、或貼到另一個釘了同一把金鑰的專案；換金鑰清單的 `.sig` 只簽新清單全文，撤銷外洩金鑰之後，把舊清單連同當年的 `.sig` 貼回來，被撤的金鑰就復活；人審簽章沒蓋 `bindings` 與 `kind`；第一次釘金鑰沒有任何驗證，打錯一個字就鎖死；整道擋下時 merge-base 算不出來，降級設定也驗不了；舊分支的 merge-base 版清單裡還有主線已經撤掉的金鑰。這些都出在「每個核可各自帶簽章、撤銷靠另一份檔」，d10 把順序與撤銷綁進同一份可驗的資料。

**做法**：
- **一個檔、只追加**：`.lumos/security-approvals.jsonl`，受版控，一行一筆 JSON。每筆的鍵（不准有未列的鍵）：
  - `seq`：從 1 起連續的整數。
  - `prev_sha256`：前一筆（含它的 `signature`）規範化 JSON 的 sha256；第一筆是空字串。
  - `project_id`：這個 repo 的根提交 sha（主線 tip 能走到的根提交，不只一個時取排序後第一個；新 repo 還沒有主線時取要推的提交的根提交）。
  - `type`：`approvers_init`、`approvers_add`、`approvers_revoke`、`exception`、`revision`、`gate_setting`、`human_review`、`tool_list_change`、`threat_table_change`、`consideration`、`suppression` 之一。
  - `target`：依 type，見下表。
  - `content_sha256`：被核可物件規範化 JSON 的 sha256，蓋什麼見下表。
  - `keys`：只有 `approvers_init` 與 `approvers_add` 有，allowed_signers 格式的列陣列（簽章人、金鑰類型、公鑰）；`content_sha256` 就是它的雜湊。
  - `approved_on`：核可日，UTC 日期，由 `lumos security approvals payload` 自動填。
  - `expires_on`：到期日，每筆都有，上限見下表。
  - `signer`：簽章人（allowed_signers 裡的 principal），驗章時當 `ssh-keygen -Y verify -I` 的參數，不用枚舉清單或 `find-principals`。
  - `signature`：`ssh-keygen -Y sign -n lumos-security` 對「去掉 `signature` 欄之後的規範化 JSON」的簽章（ssh 簽章文字整段放進 JSON 字串）。
  - `outcome`:只有 `consideration` 有,`risk_accepted` 或 `not_applicable`(到期上限靠它分 30 天或 180 天;這一欄也在簽章範圍內)。
- **規範化 JSON**：`json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False)` 的 UTF-8 位元組；空白、換行、鍵的順序都不進雜湊。

| type | target | content_sha256 蓋什麼 | 到期上限 |
|---|---|---|---|
| `approvers_init` | `approvers` | `keys` | 730 天 |
| `approvers_add` | `approvers` | `keys` | 730 天 |
| `approvers_revoke` | 被撤的 principal | `{"principal":…}` | 730 天（到期不會讓被撤的金鑰復活，撤銷永久有效；到期只代表這一筆不再算數的核可，撤銷不需要續） |
| `exception` | （護欄 id、`covers_kinds`） | 例外物件全部鍵加 `control_id`、`control_revision`、判定輸入雜湊 | 30 天 |
| `revision` | `<護欄 id>\|<decision_ref>`(target 帶 decision_ref:同一條護欄可能有好幾次修訂,鏈上要看得出是哪一筆決策授權的) | `before`、`after` 或 `removed`、`decision_ref` | 30 天 |
| `gate_setting` | `security_evidence.gate` | `{"value":"warn"}` | 30 天 |
| `human_review` | （護欄 id、種類） | 整份 review_record（含 `kind`、`bindings`、`test_sources`、`fixture_globs`、`author`、`judgments`、`reviewer`、`observed_at`、`expires_on`） | 90 天 |
| `tool_list_change` | 工具名 | 推送版那一列（刪掉時是空內容） | 30 天 |
| `threat_table_change` | （護欄 id、新表版號） | `{"from":舊版號,"to":新版號}` | 30 天（d11 起不用：表的變弱以 [[Systems/資安威脅類別表]] 的雙家協定核可紀錄放行；工具仍認得這一型以免舊鏈讀不進，但不再要求） |
| `consideration` | 格子 id | 物件全部鍵加入口、資產、類別、角色、outcome、表版號 | risk_accepted 30 天、not_applicable 180 天 |
| `suppression` | （規則 id、位置雜湊） | `{"rule":…,"location_sha256":…,"reason":…}` | 90 天 |

- 30 天的幾種（例外、修訂、gate 設定、工具清單、威脅類別表）：修訂、工具清單、表版號的核可只在「這個變弱還沒進主線」的期間有用——進了主線，主線 tip 版就是新版，不再算變弱；30 天夠一個分支合進去。到期 7 天內在放行訊息印提醒（見〈訊息形狀〉）。
- **驗證**（`security approvals verify` 與閘門同一支函式）：
  1. 從要推的提交樹讀鏈（不讀工作目錄），照 `_secinv_json_loads` 嚴格讀，自己接 `RecursionError`；單檔照證據的 16 MiB 上限、筆數上限 2000(每一筆都可能要另起一次 `ssh-keygen` 驗章,最壞情況要落在每個 ref 60 秒的預算裡);超過上限不截斷,整道判 `read_incomplete`(`security approvals verify` 擋下並說驗不了)。
  2. **主線前綴**：主線 tip 版的鏈必須逐位元組是推送版鏈的開頭一段，否則整道擋 `approvals_diverged`，訊息：「核可鏈跟主線分岔，先把分支接上主線（rebase 或合併主線）」。所以主線新撤的金鑰，舊分支一定看得到；分支上刪掉、改寫或調換主線已有的任何一筆，都會分岔。例外：主線版的鏈從第一筆起就沒有任何一筆有效過(結構或簽章從頭就壞,例如第一次釘金鑰時壞掉、而那時還沒有這條規則保護),推送版可以整條換掉,並印一行警告;這跟〈第一次釘金鑰〉的信任前提相同。★主線鏈有過有效筆(含現在已全部到期的)就永遠只能追加★:到期只取消效力,不清掉信任歷史(代碼審第一輪外家、整合、資安席:原本「現在沒有 ok 筆」就准整條換掉,金鑰兩年沒續就等於任何人都能重釘)。
  2b. **核可日不准回填**:每筆的 `approved_on` 不准早於前面任何一筆有效筆的核可日,早於就判 `approval:approval_backdated`、它核可的不算(擋拿已到期的金鑰回填舊日期讓它復活;前面沒有更晚的筆時回填偵測不到,是天花板)。
  3. 從第一筆往下逐筆驗：`seq` 連續、`prev_sha256` 對得上、`project_id` 等於這個 repo；`signer` 在「這一筆之前」算出的有效金鑰裡（撤銷之後的筆用被撤金鑰簽的判 `approval_signer_revoked`）；用只含那把金鑰的暫時 allowed_signers 跑 `ssh-keygen -Y verify -f <暫時檔> -I <signer> -n lumos-security -s <簽章>`；`approved_on` 不晚於今天、`expires_on` 減 `approved_on` 不超過那一型的上限。斷在某一筆（`seq` 跳號、`prev_sha256` 對不上、壞 JSON 行）時，那一筆與之後每一筆都判 `approval:approval_chain_broken`，前面的照算；刪掉中間一筆、調換順序、重放舊筆都會在這一步斷。
  4. 有效金鑰從第一筆往下重算：`approvers_init` 只能是第一筆，而且要用它自己 `keys` 裡的一把簽（證明持有）；`approvers_add` 與 `approvers_revoke` 要用當時有效的金鑰簽；金鑰本身的 `approvers_*` 那一筆過期，那把金鑰從過期隔天起失效（到期 7 天內提醒，續期就是同一把金鑰再寫一筆 `approvers_add`）。
  5. 某個物件要用核可時，找鏈上 `type` 與 `target` 相符、而且有效的筆裡最新的一筆，比 `content_sha256`；`project_id` 對不上的筆（從別的專案貼來）判 `approval_project_mismatch`、不算數。
  6. 驗證不讀 merge-base 版的任何東西，所以「起點算不出」這類整道擋下時，gate 設定照樣驗得出來（見〈哪些整道擋下可以降級〉）。暫時的 allowed_signers 放系統暫存目錄、判完就刪；找不到 `ssh-keygen` 時每一筆都判 `approval_signature_invalid`。
- **怎麼加一筆**：`lumos security approvals payload <type> <target> --signer <principal> --expires-on YYYY-MM-DD --out <檔>`（唯讀;`--out` 存的檔沒有結尾換行,把輸出轉存成檔會多一個換行、簽章對不上;`exception`、`human_review`、`revision`、`consideration`、`tool_list_change` 的內容從 HEAD 那個提交算,要先提交再跑;target 寫法見下表,例外是 `<護欄 id>#<排序後的 covers_kinds>`、人審是 `<護欄 id>#<種類>`、修訂是 `<護欄 id>|<decision_ref>`）印出要簽的那一筆（`seq`、`prev_sha256`、`project_id`、`content_sha256`、`approved_on` 都由工具從要推的提交算好填上;`consideration` 另帶 `--outcome risk_accepted|not_applicable`,寫進那一筆的 `outcome`、到期上限照它分 30 天或 180 天,不帶時上限照 180 天、閘門仍照格子列的 outcome 再卡 30 天;`suppression` 要帶 `--reason`;內容不從提交算的型別可用 `--content-file <JSON 檔>` 直接給要簽的物件;`--commit <sha>` 改用別的提交算內容），使用者自己用 `ssh-keygen -Y sign -n lumos-security -f <私鑰>` 簽，再在自己的終端機用 `lumos code-loop security-approval-add <簽好的檔>` 追加：工具把這一筆接在工作目錄那條鏈後面，用同一支驗證函式驗過「整條鏈加這一筆」才寫入，驗不過不寫並說原因;驗得過之後還要 stdin 與 stdout 都是互動終端、使用者照抄一段當場隨機產生的確認碼才寫入(d17),非互動一律擋下、給可複製的指令;簽章金鑰不是硬體金鑰(`sk-` 開頭)時印一行提醒、不擋。
- **第一次釘金鑰**：`approvers_init` 由使用者手動做：先 `security approvals payload approvers_init approvers --signer <principal> --expires-on YYYY-MM-DD --key <principal>=<公鑰檔>… --out <檔>` 印出內容，自己簽，再 `code-loop security-approval-add`；工具在寫入前用 `security approvals verify` 當場對這一筆驗一次（格式、金鑰類型、自簽驗得過），驗不過就不收——打錯一個字、貼成私鑰、金鑰類型不收，當場就知道，不會先合進主線再鎖死。驗得過之後，這一筆跟著提交進主線；之後它就是主線鏈的第一筆，分支改不掉。工具每次判到核可都印出現在有效的金鑰指紋，讓使用者看得到是哪幾把。
- **金鑰數量與遺失**：建議至少釘兩把，一把日常用、一把離線備份。一把遺失時用另一把簽一筆 `approvers_revoke` 撤掉遺失的、再簽一筆 `approvers_add` 加新的。

**為什麼這些重放不再成立**：
- 把歷史上簽過的 warn、修訂或例外貼回來：舊筆在鏈上有固定的 `seq` 與 `prev_sha256`，貼成新的一行接不上鏈；就算原本那一筆還在鏈上，它也有到期日（最長 30 天），過期就不算數。
- 貼到別的專案：`project_id` 對不上。
- 撤銷的金鑰復活：撤銷寫在鏈上，主線鏈必須是推送版的前綴，分支拿掉那一筆就分岔；撤銷之後的筆用那把金鑰簽的一律無效。
- 人審簽完改程式：`human_review` 的內容雜湊蓋住 `bindings` 與 `kind`，改了就對不上。
- 壓提交、rebase、合併提交、排版：驗的是鏈的內容，不看提交是誰簽的；規範化 JSON 不受空白與鍵順序影響。

**工具的天花板**：
- 「每次簽章都要實體觸碰或輸入密碼」是使用者那端的金鑰設定（例如 `ed25519-sk` 硬體金鑰要求觸碰、私鑰加密碼），工具只驗得到「由這把公鑰對應的私鑰簽的」，驗不到簽的時候有沒有觸碰或輸入密碼；私鑰若沒設這兩樣、又放在 AI 碰得到的地方，AI 就簽得出來。
- 第一次釘金鑰沒有東西可驗；新專案主線還沒有鏈時，搶先合進主線的那把金鑰就是信任根——AI 用自己的金鑰寫 `approvers_init` 並合進主線，工具分辨不出來，只能靠使用者看 `security evidence` 與 `security approvals verify` 印的有效金鑰指紋。
- 確認碼(d17)只擋 `code-loop security-approval-add` 這一支指令被 AI 照常操作時順手一步跑完(AI 在非互動的殼裡跑,payload→簽→追加會被攔在這一步)。它不擋繞過這支指令:直接寫 `.lumos/security-approvals.jsonl`(自產金鑰、用 payload 算好內容自己簽、手寫那一行再提交;第二輪代碼審資安席實證 `approvals verify` 判有效),也不擋用 `script` 之類工具偽造終端、自動照抄確認碼——閘門驗的是簽章與鏈,不知道那一行是怎麼寫進去的。依信賴原則(d19,使用者 2026-10-21 裁)這些刻意多步偽造屬範圍外:閘要防的是照常操作時不小心走過去,不防 AI 刻意偽造。
- 工具驗不出私鑰有沒有設密碼或實體觸碰:私鑰沒設、又放在 AI 碰得到的地方,AI 就簽得出來(上一條的直接寫檔不需要偽造終端)。
- 專案識別取根提交:fork 或從範本複製出的專案共用根提交,兄弟 repo 的核可鏈筆在識別上分不開;要被收還得護欄 id、revision、輸入雜湊與日期全部吻合,實際危害低(代碼審第一輪資安席)。
- 第一次登記護欄時改標較鬆的威脅類別(最低種類跟著變少)沒有主線版可比,凍結比對抓不到;只靠 review 的 threat_categories 判斷與人看(order-demo 實地實驗)。
- 工具清單每一列的核可決策(`decision_ref`)只驗「指到有效決策」,不驗那條決策是誰寫的:AI 自己 `decision-add` 一條寫進工具清單的決策,工具分不出來(〈三〉〈工具清單變弱要核可〉已承認、所以清單另跟主線 tip 版比;第一次寫清單時沒有主線那一列可比,實地實驗;靠信賴原則與審查)。
- behavior 的前置斷言與反例可以在同一批、同一支測試裡跑;工具只驗兩者都在而且都綠,不驗前置斷言真的先於反例成立、或兩者真的獨立(實地實驗;由 review 的 independent_oracle 承擔)。
- 核可日回填只在「前面有更晚的有效筆」時偵測得到;鏈上最後一筆之後持過期私鑰回填更早的日期,工具分不出來(撤銷照樣永久有效)。
- 主線 tip 從本機 ref 讀，AI 改得動本機 ref 就造得出假主線鏈；CI 用從遠端抓的 ref，是最後的核對（依 d9 是事後）。
- 全部金鑰都遺失或過期時，工具沒辦法自救：加金鑰要現有金鑰簽，例外與修訂也簽不出來。剩下的路只有使用者自己決定跳過本機閘（依 d9 的規矩，跳過檢查一律由使用者本人裁）或整道回退工具版本；伺服器端的強制或救援依 d9 不做。
- 不選：使用者另開第二個 GitHub 帳號只拿來核准例外 PR——要多維護一個帳號，CI 要加讀 PR 的權限與一步 API 查詢，帳號憑證若放在 AI 碰得到的地方就失效，而且 PR 上不跑 code-loop 的問題照舊。

## 五、合格測試守住閘門本身

下列條款實作前逐條改綁真測試（先紅）；可機械化的不准長期停在 manual。測試全在隔離的合成 vault 與合成工具輸出上跑，不在任何真專案執行工具；簽章樣本用測試當場產生的 ssh 金鑰。

**區隔與範圍**

- [S1] 當專案沒有任何 `lumos-security-v1` 圍欄時,code-loop check 的安全證據判定應回不擋、文字輸出與退出碼跟既有判定逐字相同、不寫治理帳,只在 `--json` 輸出多一個 no_registration 鍵;只有 `flag/security-relevant` 標籤而零條目的專案應同樣不擋,只在 `--json` 多一行提醒。 [test:t_secev_s01_no_registration_unchanged]
- [S2] 當同一條 Invariant 同時登記 business 與 security 關注面時,`security evidence` 應只列一筆並只對 security 判定證據,純 business 條目應不進必驗集合。 [test:t_secev_s02_concerns_partition]
- [S3] 當盤點報告讀取不完整或登記有錯而三版任一有資安登記痕跡時,閘應擋下並說明判不清,不得當零條目放行;推送版把全部資安條目刪掉時,每條應各自判 missing:control_removed_unapproved;三版都只有 candidate 的專案應放行並列提醒。 [test:t_secev_s03_registration_errors_block]
- [S4] 當 `security evidence --commit <sha>` 與 code-loop check 對同一提交、同一主線 tip、同一 UTC 日期判定時,兩者的逐條判定應完全相同,而且 `security evidence --commit <sha> --json` 的盤點區塊應等於在那個提交的乾淨 checkout 上跑 `security list --json` 的報告,即使工作目錄停在別的提交。 [test:t_secev_s04_evidence_equals_check_and_list]

**合格判準與為了合格而合格的反例**

## 世界解與採用判斷

PRIOR-ART: 最小解落在既有 code-loop check 加一道並列判定，證據沿用 bound-tests-gate、guard kill、test-quality capture/check；外部工具只讀標準輸出：JUnit（沿用 `scripts/test_quality.py` 的讀法）、SARIF（另寫嚴格解析，uri 正規化也各寫）、k6 新格式摘要（新寫一個小讀法）。核可用 OpenSSH 的 `ssh-keygen -Y sign/verify`（git 自己的 ssh 簽章也是用它）簽內容，不自建簽章格式；核可鏈借用「只追加、每筆帶前一筆雜湊」的雜湊鏈做法（透明日誌與 git 自己的提交鏈都是這個形狀），只用標準庫的 sha256 與 JSON，不引入新依賴。主線與分岔點沿用既有 `_push_mainlines`、`_push_range_start` 的算法，快照讀取沿用 `_nodehome_list`、`_nodehome_cat_blobs_capped`。借用 OSCAL「要求／實作／評估分層」的原則（盤點計劃已引，只借資料與結論分離）。不另造掃描器、runner、證據帳或安全總分。
