# enforcement可觀測性_計劃

> 全 repo 審視 #19(編號 F21、F95、F25、F30;工量 M)。
> ★這是 [[Projects/enforcement儀表板_計劃]] 的續案,不是重開★:那一批做的是
> 「有沒有裝上/接上」的唯讀匯總,這一批要把判準從**生效=有註冊**升格成
> **生效=最近真的跑過**,並且把「擋了誰、放行了誰、被跳了幾次」變成帳上查得到的東西。

## 為什麼(每一條都是我自己量過的,不是抄清單)

### 一、治理帳 29,348 筆,★hard=true 一筆都沒有★

實測(2026-09-08):

| 量的東西 | 數字 |
|---|---|
| 治理帳總筆數 | 29,348 |
| `hard=true` | **0** |
| `kind=blocked` | **0** |
| `kind=warned` | 27,795(94.7%) |

不是沒人寫這個欄位,是**會寫 `hard=true` 的那幾處從來沒觸發過**
(前掃機械數過:碼裡直接寫 `"hard": True` 的只有 **3 處寫入點,分屬 2 個閘**
——可逆性檢查 check-r 兩處、check-j 一處。原本寫「三道」是不精確的)。
真正的缺口在別的地方:**hook 層那些 `exit 1` 擋下人的時候,一筆帳都不寫。**
機械數過:`scripts/hooks/pre-push` 有 7 處 `exit 1`、`scripts/hooks/pre-commit` 有 3 處。
它們擋掉一次推送,治理帳上完全看不出來。

而 README 對外宣稱「每道關卡攔了誰、硬擋還是提醒」都在帳上——**那句話目前不成立。**

### 二、★儀表板現在對它最重要的兩列講錯話,而且已經錯了不知道多久★

`lumos enforcement` 在這台機器上把 `git-pre-commit` 與 `git-pre-push` 都印成 **inactive**
——而那兩道閘今天擋過我兩次、每次推送都在跑全套測試。

根因是一行字串比對:

- `core.hooksPath` 這台機器上的值:`/Users/enzo/harness/lumos-toolchain/scripts/hooks`(絕對路徑)
- 碼裡比的是字面字串:`scripts/hooks`(相對路徑)
- 相等嗎:**否** → 判 inactive

★方向是「該說有卻說沒有」★:表面上是安全方向(不會假綠),但實際後果更糟——
**那兩列長期是紅的,所以真的哪天 hook 掉了,那個紅沒有任何訊號價值。**
這就是「狼來了」,而且是儀表板自己喊的。

★這一條本身就證明了這批要做的事★:一個只驗「有沒有註冊」的判準,
連「註冊成什麼樣子」都會判錯;而**只要沒有人真的去看「它最近有沒有跑過」,錯了也不會有人知道**。

### 三、五支 Claude hook 的成功/超時/失敗,只有開 debug 才看得到

`scripts/hooks/claude/` 底下五支(進場、波及提醒、收工圖譜同步、CI 狀態、派工鏡頭注入)。
要知道它們最近有沒有跑、跑了幾次、超時幾次,現在唯一的辦法是去 grep 逐字稿。
而 `lumos enforcement` 對它們只驗「有沒有註冊在設定檔裡」。

### 四、逃生口是全有全無的

`--no-verify` 一按,連 1 秒的錨點檢查與健檢都一起跳掉——通常是為了省 8 分鐘的全套測試。
`docs/.bypass-log.jsonl` 目前有 67 筆,但它記的是**提交層**的繞過,
而且記完之後沒有任何地方在問「哪一道閘最常被跳」。

## 做什麼(r1 三席審完後大幅改形狀)

★r1 收到 17 條、4 個 blocker,而且三個核心機制全部要換形狀。★
下面每一節開頭先寫「原本想怎麼做、為什麼不行」,再寫現在的做法。

### [S1] 擋下時要落帳——但**不新開「請幫我記一筆」的端點**

**原本想的**:hook 在每個 `exit 1` 前呼叫一個新的 lumos 子命令去寫一筆帳。

**為什麼不行**(架構對齊席,而且它挖出我自己的失敗前例):
這個 repo 既有的寫入模式是**「做事的那支子命令,順便把自己的判定落帳」**
(`_append_governance_log` 的寫者是 `doctor --ci` 與 `anchor approve`;
`_codeloop_gov_log` 的寫者是 `code-loop` 自己)。
★沒有任何先例是「hook 呼叫一個專門用來記帳的端點」★。
而且——**我一天前才撞過這面牆**:[[Projects/每日治理wrapper活著沒_計劃]] 裡白紙黑字寫著
「我寫了一個不存在的指令 `lumos gov-event`,查了才發現沒這支」,結論是
「工具沒有給外部腳本寫治理帳的入口」。**今天我又提了同一個形狀,而且沒引用自己那次。**

**現在的做法**:擋人的那幾道本來就是 lumos 子命令(`anchor verify`、`doctor --ci`、
`code-loop check`、`pitfalls`)——**由它們各自在回非零時寫自己的 blocked 事件**,
hook 完全不碰記帳。不新開子命令,也就不必付那份同步稅。

★誠實邊界★:pre-push 裡有幾道**沒有 lumos 擁有者**的判斷(最典型是「找不到 lumos 或 python3
就降級放行」)。那幾道 lumos 根本不在場,**結構上記不了帳**。
這件事要明寫進文件,不能假裝涵蓋。

### [S2] pre-push 的耗時與 fail-open——同一個原則

由做判斷的那一方記,不是由 hook 記。整支耗時需要一個把多筆事件串起來的識別,見 [S6]。

### [S3] 跳閘:★用既有的形狀,而且可跳的集合比我原本寫的小很多★

**原本想的**:新的 `LUMOS_SKIP=<gate-id>` 通用環境變數,可跳四道。

**三個為什麼不行**:

1. **這個 repo 已經有這個機制了,而且是另一種形狀**(架構對齊席):
   `LUMOS_SKIP_BOUND_TESTS=1`、`LUMOS_STOP_BLOCK_OFF`、`LUMOS_ENTRY_HOOK_OFF`
   ——**每一道閘一個布林變數**,而且既有的那支已經在記 `skipped-env` / `skipped-flag`。
   我提的通用單一變數是新形狀,而且沒有承認既有的存在。
2. **★可跳的判準是錯的★**(外家否決席 + 通才席,我逐道實查過 CI 設定):
   | 我原本列的 | 實際 |
   |---|---|
   | 健檢 | ✅ CI 無條件跑,判準成立 |
   | 風險分級 | ❌ CI **沒有獨立步驟**,只在代碼審那步內部被重算 |
   | 代碼審留痕 | ❌ 那一步掛 `if: github.event_name == 'push'`,**PR 不跑** |
   | 測試層次 | ❌ CI 完全沒跑,**而且它本來就是「恆 rc 0、不擋」的軟提醒——根本不是閘** |
   加上 CI 只在推主線與開 PR 時觸發,**feature 分支推上去不跑 CI**。
3. **★跳「代碼審留痕」會連帶跳掉我自己寫明不可跳的那道★**(通才席,我驗過):
   合約測試閘是 `code-loop check` 內部的第 2.5 步(「不分 tier;紅就擋」),
   而推送閘自己那次獨立呼叫是 `--advisory` 加 `|| true`、**不擋**。
   所以「不呼叫 code-loop check」＝連合約測試閘一起跳掉。
   **而 CI 那邊也關著它**(`LUMOS_SKIP_BOUND_TESTS: "1"`),理由是「全套測試當後盾」
   ——但全套測試驗的是「現有測試會過」,**驗不出「這個合約根本沒綁測試」**。
   兩層疊起來,那個覆蓋率缺口本機和 CI 都沒人抓。

**現在的做法**:

- **形狀照既有的**:每道閘一個布林環境變數,命名與 `LUMOS_SKIP_BOUND_TESTS` 同款,
  落帳沿用既有的 `skipped-env`。
- **可跳的只剩健檢一道**——那是唯一 CI 無條件兜得住的。
- **風險分級與代碼審留痕**:★只在「這個 repo 目前是直推主線」這個前提下才有後盾★。
  實查(2026-09-08):主線**沒有分支保護**(回 404)、**一張 PR 都沒有**。
  所以現況安全,但**這是假設不是通則**——要明寫,並附回頭條件。
  REVISIT:2026-12-08 或「這個 repo 開始用 PR / 加上分支保護」時,重新判這兩道能不能跳。
- **測試層次從清單移除**——它不是閘。
- **代碼審留痕如果要可跳**,實作上必須拆開:只跳「留痕要求」那一步,
  ★合約測試閘的呼叫要留在環境變數之外、永遠執行★。
- **「記理由」這條要求撤掉**:布林變數帶不動理由(外家否決席指出),
  而既有那支也只記 `env LUMOS_SKIP_BOUND_TESTS=1` 這種機器事實。
  ★要答的問題是「哪一道最常被跳」,機器事實就夠了,人寫的理由是我多加的。★
- **外家否決席提了一個更硬的替代**:不要臨時環境變數,改成「具名、帶理由、綁 commit 與分支、
  會過期的例外收據」(`lumos gate waive …`),hook 只認 CLI 產生的短效收據、CI 再驗一次。
  ★這個設計比環境變數硬得多,但它是一個新機制、範圍遠大於這一批。★
  **本批不做,記成候選**;如果之後量出「跳閘次數多到需要治理」,再開案評估。

### [S4] hook 有沒有真的在跑:★三個要換的地方★

**原本想的**:五支 hook 各寫一行 jsonl 到 `~/.cache/lumos`,`enforcement` 多一欄「近 7 天跑 N 次 / 注入 N / 超時 N」。

**換掉的三件**:

1. **★位置改回 repo 樹內★**(三席都提,架構席判 blocker)。
   這個 repo 的慣例是產生物放 repo 樹內、`.gitignore` 蓋掉
   (`scripts/bin/`、`governance/.notifier/` 都是),碰家目錄只限 OS 逼你放那裡的東西。
   ★我給的理由(「不是治理帳」)回答的是「這筆帳算哪一類」,不是「檔案該放哪裡」——兩件事。★
   改放 `governance/runtime/hook-events.jsonl`,gitignore 蓋掉,權限收緊,**有容量上限**。
   順帶解決跨 repo 污染:放 repo 樹內,別的專案的事件就進不來。
   (通才席另外查到:派工鏡頭那支的家目錄快取**鍵裡有 repo 根**,證明作者早就意識到這個問題。)
2. **「跑」的定義要釘死**(通才席):記在**成功完成點**,不是進入點。
   逾時、例外、輸出契約失敗各記成不同的 kind,**不得算成「跑過」**。
   ★同型前例就在隔壁★:[[Systems/hook逾時預算]] 記的正是「寫在 except 分支裡的清理動作
   結構上永遠跑不到,而且沒人發現」,時間是 2026-09-07——前一天。
3. **★「近 7 天跑過」本身就是假綠來源,判準要更硬★**(外家否決席 blocker):
   hook 今天上午跑過、下午被移除,接下來七天照樣顯示「有效」。
   正確的判準至少是三個條件同時成立:
   **①現在有註冊 ②現在的檔案指紋對得上 ③最近有一筆同 repo、同 hook、同版本的成功完成事件**。
   沒有近期成功時要標 `stale` / `unknown`,**不能標 inactive**——那可能只是七天內沒有自然觸發。

**另外兩件**:

- **寫入邏輯集中成 lumos 裡一支共用函式**給五支 hook 呼叫,不要五份各自實作
  (通才席;理由跟 S1 同源——原子寫入、上限、例外處理漏一處就是一個獨立的坑)。
- **「近 7 天跑 N 次」這種統計不要塞進 `enforcement`**(架構對齊席):
  那張表是「當下狀態」,統計是另一種性質的資料,這個 repo 已經有 `gov --stats` 在做聚合。
  ★`enforcement` 只升級它的**狀態值**(active / stale / unknown,用上面那個三條件判準),
  次數與時間序列去 `gov --stats`。★

**★[S4] 要正面回答的一個張力(通才席 F5,不能繞過)★**:
派工鏡頭那案的 d1 原文是「不擋不驗**不記不量**」,而且它自己規劃的查法是**一次性的回頭條件**,
不是常駐計數器。我原本只處理了「不進治理帳」那半句,**「不量成效」那半句沒有面對**
——「注入 N 次」本質上就是在幫那支 hook 量成效,只是換了個地方存。

**裁定:這一批只做「活著沒」,不做「有沒有用」。**
- 記:跑過 / 逾時 / 失敗(這是**防護的存活訊號**,是本批的主題)。
- **不記:注入 N 次**(那是成效,d1 明令不量)。
- 這條分界要寫進實作的註解,免得下一個人順手把它加回去。

### [S5] 修 `core.hooksPath` 的字串比對——★用既有的那支,不要寫第二份★

架構對齊席查到:`_deinit_unbar_gate` 裡**已經有一模一樣的做法**
(`vp.resolve() == ours.resolve()`,而且連字串比對的退路都有)。抽成共用函式沿用,不要重寫。

驗收輸入要涵蓋三種寫法:相對、絕對、**以 `~` 開頭**(通才席補的;`core.hooksPath` 允許 `~` 展開)。
★而且要有反向對照★:把 hook 真的拿掉,那兩列要翻紅——只驗「它說 active」不算驗過。

### [S6] 事件要有辦法串成同一次執行(外家否決席)

pre-push 是**逐 ref 迴圈**(每行 `<local_ref> <local_sha> <remote_ref> <remote_sha>`),
而錨點與健檢跑在迴圈**外面**——所以「當下的 commit」對整支層級的閘**沒有唯一答案**。
照原本寫法,lumos 自己去取 HEAD 會在「同次推多個 ref」「推的不是目前 checkout 的 ref」
「detached HEAD / 推 tag」三種情況下歸錯 commit。

Schema 要明定:**整支層級的事件用一個 `attempt_id`;逐 ref 的事件用那一行真正的 sha**。
S2 的「整支耗時」也要靠這個 id 才串得起來。

### [S7] 記帳失敗時,閘的判定不准被改寫(外家否決席)

既有的治理帳寫入器是 `except OSError: pass`——**I/O 錯誤靜靜吞掉**(我讀過那段碼)。
新的寫入如果照抄,「每個 exit 1 前寫一筆」就不是可保證的行為:磁碟滿、權限錯、帳檔壞掉時,
hook 照樣擋,但沒有那筆帳,**承諾在最需要的時候是空的**。

規則兩條:
- **原本的判定不可被記帳失敗改寫**——該擋還是擋(反過來要求「寫成功才擋」會讓觀測系統故障變成放行)。
- **記帳失敗要在 stderr 明講**,而且 `enforcement` 要能把觀測層本身標成 degraded。

## 實務隱患

- **帳本膨脹**:治理帳已經 29,348 筆,其中 94.7% 是 `warned`。
  再加 blocked/skipped/fail-open 三種事件,要先想清楚**誰在讀**。
  ★這裡我原本的語氣不對,通才席實跑更正了★:那 27,795 筆 `warned` **不是沒人讀**——
  `gov --stats` 對每個閘做去重與首末見日聚合、`gov --nags` 專門篩它找「同一道閘對同一篇
  連續喊 N 天沒人理」的空轉清單,結果餵進自主迴圈週報。
  所以「每種新事件都要指名一個讀它的地方」這條自我要求對舊帳**是成立的**,不是空話。
  新事件照這條走:**blocked/skipped 進 `gov --stats` 的哪一段,要在實作時指名**。
- **`LUMOS_SKIP` 會不會變成更好用的 `--no-verify`**:設計目的是「量得出哪道閘最常被跳」,
  但如果它比 `--no-verify` 好打,人會更常跳閘。要在擋下訊息裡明講「這會留一筆帳」,
  而且 `gov` 要有一段把跳閘次數印出來——★沒有人看的留痕等於沒有留痕★。
- **`~/.cache/lumos` 的清理與競態**:五支 hook 可能同時寫;要 append-only、
  單行原子寫入,而且要有上限(不能無限長)。這個 repo 對共用檔的既有教訓是原子寫入。
- **hook 變慢**:每支 hook 多一次寫檔。hook 有逾時預算(見 [[Systems/hook逾時預算]]),
  要量新增的耗時,不能只用「應該很快」帶過。
- **★驗證方法本身的陷阱★**:這一整批的主題是「怎麼知道它真的生效」,
  而最容易掉的洞就是**問它、它說有,就當成有**。
  同工作區另一個 session 2026-09-08 實測過一個同型的坑:叫審查席自報模型代號,它會答錯。
  **所以這批的每一條驗收都要用反證**:把那道閘弄壞(或把 hook 拿掉),看儀表板會不會翻紅
  ——只驗「它說 active」不算驗過。
- **不涵蓋什麼**:不做消費端 hook-local 覆寫、不做 rebase 偵測、
  不改 `--no-verify` 本身(它是 git 的東西,擋不掉),只是把建議的出口換掉。

PRIOR-ART: 最小解在既有 jsonl 帳本多幾筆事件加一個環境變數。世界解四個(★都當場一句話解釋★,
前掃指出這幾個外部名詞原本沒展開):

- **OPA 的 decision logs**:OPA 是一套「把准入判斷抽出來獨立跑」的開源政策引擎,
  它每做一次准入判斷就落一筆結構化紀錄——**判斷本身就是要被記錄的事件**,這正是這批缺的那一半。
- **K8s 的 `failurePolicy=Ignore` 必配 audit**:Kubernetes 的准入檢查允許「檢查掛掉就放行」,
  但那個放行一定會進稽核日誌。**跟我們的 fail-open 同型,差別在他們規定放行也要留痕。**
- **pre-commit framework 的 `SKIP=<hook>`**:那是一套第三方的 git hook 管理工具
  (★跟本 repo 自己的 `scripts/hooks/pre-commit` 撞名,不是同一個東西★),
  它用環境變數逐道跳閘,而不是全有全無地關掉整層——就是 [S3] 要抄的形狀。
- **OpenTelemetry 的 logs 資料模型**:一套跨語言的可觀測性標準,
  它對「一筆事件該有哪些欄位」有共同約定,可以拿來對照我們治理帳的欄位夠不夠。
