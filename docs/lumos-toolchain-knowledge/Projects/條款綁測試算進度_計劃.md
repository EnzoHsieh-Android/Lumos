# 條款綁測試算進度_計劃

> 題目一句:設計審產出的驗收條款清單,實作時「認領→做完勾掉」怎麼不漂?
> 派工者:Enzo 2026-09-08 裁「寫計劃、送設計審、不直接做」。
> 兩份乾淨 agent 調研(不帶結論、只給原始問題)在 `governance/review-reports/條款綁測試算進度/`。
> ★這是 [[Projects/進度從提交推導_計劃]] 四版被打穿之後、[[Projects/接手視圖_計劃]] 落地之後的續案★——
> 那條線仍有效的三條裁定(d3 完成判準掛實作端看測試 / d9 帳不爛只因寫入有驗證+入口綁定 / d12 先造唯讀)是本案的地基,不重審。

## 為什麼(先講現況,每個數字都是 2026-09-08 我自己量的)

- **「認領→勾」的模型這個 repo 已經有了,而且幾乎沒人用。** `[SN]` 條款標記 + `lumos spec-trace`:
  認領 = 某篇 Verification 筆記的 `plan_refs` 欄位回指本計劃、而且那篇筆記全文出現過 `[SN]` 字樣。實算:**有 `[SN]` 條款的計劃 33 篇,
  條款全未認領的 15 篇**(圖譜裡舊的「158 篇 126 篇從沒用」是另一種算法,今天用 `spec-trace --json`
  逐篇跑是這個數)。它沒人用的結構原因,自家調研講得準:**沒東西逼(不掛閘、opt-in)、沒地方消費(只有人跑指令才看得到)**。
- **「勾掉」這個動作本身,世界上能不漂的例子清一色是「狀態不另存,從有代價偽造的產物直接讀」**
  ——BDD 讀測試結果、GitHub 子 issue 關掉父清單自動勾、PR 合併自動關 issue。
  「有人去勾」的全承認沒機械對帳(Beads=給 AI agent 用的 issue 追蹤器、TASKS.md=用 markdown 勾選框、Spec Kit=GitHub 的規格驅動開發套件)。世界調研沒找到「設計審條款原生綁 CI 結果」的現成工具。
- **自家四版「造新狀態源」全被打穿**(提交 trailer / 當場跑測試 / hook 事件帳 / 自報帳),
  四版共同結論:「同步任務狀態在這裡不能靠造,只能靠讀」。

### ★轉述的設計裡三個前提,我開檔驗過,對不上★

| 轉述的前提 | 實際 | 對設計的影響 |
|---|---|---|
| 「完成=不跑測試,讀測試每次跑都留的快取」 | 推送閘寫的 `.lumos/test-cache-shard*.json` **只有 `{"failed": []}`**,是 fail-fast 重跑用的失敗清單,**沒有哪支測試在哪個 commit 幾點綠** | 「讀快取算綠」在現有產物上**不成立**。要另找有代價的證據源(見 [S2]) |
| 「認領=條款旁綁 `[test:]`,可機械驗存在(Check T 那套)」 | Check T 的 `extract_contracts` **只讀任一節點 frontmatter `summary` 欄位裡的 ★INVARIANT★ KEY 行**(不限節點型別,只是今天只有 System 節點這樣寫);**計劃正文它完全不讀**,條款旁的 `[test:]` 不會被看到 | 要新開一條**只驗存在**的小解析路徑,但**沿用** `resolve_test_refs` 與 Check T 的方法集合比對,不自寫第二份 |
| 「`lumos task record` 是否落地」(自家調研沒查到) | **不存在**(`lumos task` 回「沒有這個指令」);v4 那條裁定沒有實作,d12 轉向後不會實作 | 本案不依賴它,也不復活它 |

另外兩個數字更正:**測試撞名今天實算 841 支、同名 0 對**(v2 那個「664 支裡 95 對」是別的算法或舊資料;
多平台消費專案的撞名由 `resolve_test_refs` 的平台前綴處理,本 repo 現在沒有);
`bound-tests` 治理帳一筆記的是 **節點清單 + 「46 綠」這種計數**,★不記測試名★。
本 repo 的 `test.method_regex` 只收「行首 `def` 且前綴 `t_`」——`test_` 前綴就算搬到行首也不收(r1 通才席指出我原本只講了一半)。

## 做什麼(r1 折入後的版本;r1 之前的寫法見卷證 r1-snapshot.md)

### [S1] 「認領」= 在條款那一行綁測試名,寫法跟合約行一樣

- `[S3] 接手視圖印一行指路 [test:t_handoff_view]`——`[test:名]` 照 ★INVARIANT★ 的寫法,多平台用同一套 `平台:名` 前綴。
- **配對範圍=同一行**:一個 `[SN]` 只認自己那一行、在它之後出現的 `[test:]`/`[manual:]`;同一行有兩個 `[SN]` 就各認到下一個 `[SN]` 之前。
  跨行、寫在下一段的一律不算(印「條款行上沒有綁定」)。這是為了不讓不同實作者各自猜範圍(r1 通才席)。
- **沒有測試可掛的條款寫 `[manual:一句怎麼驗]`**(skill 散文、圖譜回填、真機驗收)——跟 `[test:]`/`[audit:]` 同一個標記家族,
  不發明別的形狀;它的意思是「這條靠人,而且講了怎麼驗」,不是「跳過」。
- **存在性機械驗**:新一支唯讀函式把條款行交給既有的 `_classify_one`(它吃的就是含 `[test:]` 的一段文字,
  不要求來自 frontmatter),解析與方法集合比對全沿用,**沒有第二套分類引擎**(r1 簡化席開碼確認)。不動 Check T、不動 doctor 判定。
- **狀態四種,不是三種**(r1 通才席、接手席):
  1. 未標——這一行既沒 `[test:]` 也沒 `[manual:]`。
  2. 靠人——有 `[manual:]`。
  3. 綁了——`[test:]` 指到的測試真的存在。
  4. 懸空——`[test:]` 指到的不存在。★但要再分兩種★:**寫錯**(方法集合裡沒有這個名字)與**設定認不到**
     (名字在檔裡找得到、只是 `test.method_regex` 不收——本 repo 設定只收「行首 `def` 且前綴 `t_`」,
     `test_` 前綴與 class 內的 144 支全在這一類)。「設定認不到」不能算成寫錯,也**不進 REVISIT 那個比例的分母**(通才席 F2:否則盲區會污染量測)。
     怎麼分:方法集合比對失敗後,再用 `git grep -E "def <名>\s*\("` 掃該平台的測試檔,找得到=設定認不到。這一步唯讀、幾十毫秒。
- 「改名會被 Check Y 抓」那句訂正:Check Y 是**提醒不擋**(簡化席 F2);本案不靠它,靠自己的存在性驗。

### [S2] 「證據欄」:算出來、不勾,證據只讀 CI 帳——★第二階段★

**開工條件**:REVISIT 那次量到「設計審過關的計劃裡條款綁測試比例 ≥ 五成」才做;沒到就不做(簡化席 F12:S2 的價值完全押在 S1 的習慣有沒有養成,
而 r1 全部 blocker 都落在 S2,先出 S1 把風險最集中的那塊留到證明值得)。設計現在就審完,不留白。

- **證據源只剩一本:CI 帳 `docs/.ci-log.jsonl`**。bound-tests 治理帳整個不用(外家席 blocker 2、簡化席 F4):
  它一筆只有節點名+計數、不記測試名,而節點的綁定會隨時間變,拿今天的綁定去套當年的紀錄=假證據。
- **同一 sha 多筆的讀法=沿用 `cmd_ci_status` 那段(抽成共用函式,不另寫)**:同 sha 全部筆、先紅、再非綠、最後才最後一筆
  (架構席 major、通才 F3、簡化 F3/F9)。後果要講白:目前 7 個多筆 sha 裡 6 個是「等待逾時→兩分鐘後 success」,
  既有規則對它們報 `timeout-waiting`(非綠)——本案照報,不自己判它其實綠了。這是既有讀法的已知邊界(v1 F-bnd-4 同型),
  修它是 ci-status 那邊的事,列在本案末尾候選,不在這裡偷改。
- **★證據 sha 上必須真的有這支測試,而且本文跟現在一樣★**(外家席 blocker 1):從最新的 CI 列往回走,對每個候選 sha 用
  `git grep -E "^def <名>\s*\(" <sha> -- <測試檔>` 確認定義存在(實測 27 毫秒),再用 `git show <sha>:<檔>` 抽出函式本文跟工作樹比;
  本文相同才印那個 sha;不同印「有更早版本的證據 @sha,目前本文尚無」。實例:合併前的 commit 樹裡沒有 `t_handoff_view`,
  舊寫法會拿那個 commit 的綠來印,新寫法印「尚未推上主線」。
- **每一列的字要自帶天花板,不靠表頭**(接手席 F-S2-1、簡化席 F5/F10):
  - `整套綠 @<sha7>(<時間>)·單支未證`——意思是「這支存在於那個 sha,而那個 sha 整套沒紅」,**不是這支單獨跑綠,更不是做對**。
  - `整套紅 @<sha7>·不一定是這條`——CI 是整套結論,別處壞了這條也紅(簡化席 F5)。
  - `無綠證據 @<sha7>(帳:timeout-waiting)`——帳上最新這筆不是綠也不是紅。
  - `尚未推上主線`——沒有任何含這支測試的 sha 有 CI 列(CI 只在推送主線後跑;feature branch 期間全部是這個)。
  - 表頭再講一次:「整套綠」含 skip 不可知;顯示值會隨後來無關的 CI 變動(簡化席 F10 要求講的代價)。
- **成本**:CI 帳 44KB、每條款一次 `git grep`(27ms)+ 最多一次 `git show`;通才席擔心的 4.5MB 治理帳已經不讀了(bound-tests 砍掉)。

### [S3] 入口:條款表住在 `spec-trace`、handoff 只指路、處置閘加一道檢查

- **`lumos spec-trace <計劃>` 印條款表**(它本來就是「條款認領追溯」指令,只是今天只認驗證筆記回指):每條印 S1 的四態,
  S2 上線後多一欄證據。★單一裁決來源=綁測試★;舊制「驗證筆記回指」欄保留印出、標「舊制,對照用」,不再是並列的第二種認領
  (架構席 minor 2、接手席 F-VS-SPECTRACE)。
- **`lumos handoff` 不印這張表**(接手席 F-S3-1:接手視圖的範圍刀白紙黑字「不判完成、不印進度」,那是它免設計審的理由,本案不撤它):
  只印一行「這份計劃有 N 條驗收條款,綁了測試 M 條、靠人 K 條、未標 J 條 → lumos spec-trace <計劃>」。這是文字上的計數,不是進度。
- **處置閘加一道(這才是有東西逼的那一半)**:`lumos loop status --disposal --spec <計劃>` 已經會讀那份計劃(算 hash);
  加一步「計劃裡有 `[SN]` 條款的,每條要嘛 `[test:]` 要嘛 `[manual:]`,否則 ⛔ 印出哪幾條沒標」。
  只對計劃有 `[SN]` 的生效(opt-in 不變),不回溯舊迴圈。★這是改處置閘的語意★——`Systems/design-loop` 是 ★RISK★ 節點,
  這一條要列合約候選、實作時走 code 迴圈;接手席原判「design-loop 不影響」在折入後不再成立,intake 記。
  漏洞要講:計劃可以整份不寫 `[SN]` 來繞過——所以 REVISIT 那次連「設計審過關的計劃有 `[SN]` 的比例」一起量。
- 設計審 skill 的「合約候選」那段加一句「每條驗收條款寫 `[test:]` 或 `[manual:]`」(簡化席 F11 確認是純文件改動)。

### [S4] 範圍刀

唯讀、不造帳、不改 hook、不跑測試、不動 Check T 判定、不動 handoff 的「不判完成」、不用 bound-tests 帳、不用 test-cache、
不改 ci-status 的讀法(沿用+抽共用)、不改 `test.method_regex`(認不到的印「設定認不到」);
處置閘那一步是本案唯一會「擋」的改動,獨立成一個實作項走 code 迴圈。

## 實務隱患(r1 折入後)

- **v2 的死因逐條答**:
  - *skip 靜默變綠*:本案不跑測試;CI 那本沒有 skip 計數,所以列上寫「整套綠·單支未證」而不寫「綠」。要 skip 數得改 CI 回流欄位,是另一案。
  - *撞名*:今天 841 支 0 對;多平台走前綴,前綴未定義 raise;呼叫端比照 `_bound_tests_for_diff` 接成一列「壞名」,不讓 spec-trace 噴例外(架構席提醒)。
  - *快取過期*:不用快取;證據永遠帶 sha 與時間。
  - *test-cache 是推送閘的*:不碰。
  - *「綁了」≠「做對」*:每列自帶「單支未證」。
- **「綁測試名」仍是人要做的動作,為什麼不會像 spec-trace 一樣沒人用**:
  ①存在性有機械驗;②★處置閘擋★——沒標的條款過不了設計審(這一條在 r1 之前只是流程規則,接手席查證它零約束,已改成閘);
  ③spec-trace 每次接手都被 handoff 指路。②是真的有東西逼,①③是可見度。成功判準要可量,回頭條件獨立一行:
- REVISIT:2026-11-08 量兩個比例——「設計審過關的計劃有 [SN] 的比例」與「有 [SN] 的計劃裡條款綁 [test:]/[manual:] 的比例」(分母扣掉「設定認不到」);任一低於五成就承認入口沒接上,回頭看是閘沒生效還是大家繞過 [SN]
- **證據粒度的誠實**:整套綠 ≠ 單支綠;「存在但被 skip」擋不住;紅不一定是這條。三句都印在列上。
- **多 session 的漂移(r1 外家席訂正)**:跨 checkout 的合併衝突走 git;**同一個 checkout 兩個 session 同時改同一份計劃,是圖譜寫入原語既有的
  last-write-wins 窗**(它的說明自己寫著「單機 CLI,不上鎖,accepted」)——後寫的 `lumos set` 會把前一秒別人加的 `[test:]` 蓋掉,git 不會報衝突。
  本案不修這個(是全圖譜的既有邊界,記在 [[Issues/同工作區多session並行改動]]),但要講:綁完 `[test:]` 馬上提交,窗口才小。
- **CI 帳當證據源是 v1 回鍋**:v1 六個 blocker 群逐條對過(簡化席 F7–F10):trailer 夾帶、凍結假完成、查歷史 sha 三群因換了定址與語意而不成立;
  「同 sha 重跑轉綠仍報紅」(F-bnd-4)在既有 ci-status 今天仍在,本案沿用它、明列不修;「尚無證據混三種不知道」(F-bnd-8)拆成「無綠證據(帳上是什麼)」與「尚未推上主線」兩列。
- **不涵蓋**:沒有程式碼可掛的工作寫 `[manual:]` 印「靠人」,不假裝算得出來——上一案 v1 就這樣裁(只蓋四分之三),後面四版翻的是載體不是這條。

## 合約候選(gate 過後再蓋章;不確定不標)

- 處置閘:計劃有 `[SN]` 而某條沒 `[test:]`/`[manual:]` → 不得 PASS(改 `Systems/design-loop` 的行為,走 code 迴圈)。
- spec-trace 的證據列永遠不印裸的「綠」「紅」「完成」三個詞。
- 證據 sha 必須含該測試定義且本文與工作樹相同,否則不印該 sha。
- 候選(另案):ci-status 對「等待逾時→補 success」的同 sha 多筆仍報非綠;CI 回流加 skip 計數。

PRIOR-ART: 最小解在既有 `[SN]`+`[test:]` 兩種標記合起來用、讀既有兩本機器帳;世界解=BDD 活文件(讀測試結果)、
GitHub 子 issue/PR 合併自動關(讀既有事件)、需求追溯矩陣(自動回填結果、連結仍人工);裁定=borrow-design
(狀態不另存、從有代價偽造的產物直接讀;連結那一步——綁測試名——是人做的,靠存在性驗+入口綁定撐,而且要量)
