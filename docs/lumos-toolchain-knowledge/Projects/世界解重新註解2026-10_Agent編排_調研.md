# 世界解重新註解2026-10_Agent編排_調研

> 白話:這一類問的是「多個 AI 代理一起做事時,誰跑、照什麼順序、各自帶什麼脈絡、有什麼權限、能不能同時跑」。世界在 2025–2026 收斂成一句話:寫程式的只留一條線,多代理只負責出判斷;審查員吃乾淨脈絡、只看證據不看作者說法;隔離交給 harness(包在模型外面、負責跑工具與管權限的那層程式,例如 Claude Code、Codex)。Lumos 的大方向全部對齊,但有兩件最要緊的事:**審查席彼此看不到對方的前提,被 Claude Code 2026-08 以後的新功能(分叉子代理、即時落地的逐字稿、自動成隊)鑿出側門**;以及**換模型家族的價值放錯了位置**——世界證據說換家族對「找 bug」幫助小,對「判決」(辯方降級、判乾淨)幫助大,而 Lumos 2026-09-30 起辯方預設同門。

## 這一類在問什麼、Lumos 現在怎麼做

本類問五件事:誰跑(席位編制)、什麼順序(骨架由誰控制)、帶什麼脈絡(派工詞裡放什麼、壓縮後留什麼)、什麼權限(審查席能碰什麼)、能不能平行(多會談、多分支)。Lumos 對應的機制(狀態以 2026-10-11 查詢為準):

- [[Systems/pitfalls-code-loop]] 與 [[Systems/design-loop]]:代碼審與設計審兩條審查迴圈;主對話照手冊派席、收貨、去重、派辯方,lumos 只出編制表、算重疊、記帳與判閘,不自己派代理。
- [[Systems/risk-tiered-review]]:依風險分級決定派幾席;high 是五個不同鏡頭,另加架構對齊席與必派的資安席。
- [[Projects/派工編制資料化_計劃]]:把編制寫成資料,`lumos loop next` 印「應派」、`loop status --roster` 對帳「實派」,只觀察不進閘。
- [[Systems/派工鏡頭]]:派工詞帶 `LUMOS-IMPACT:` 標記時,在派出那一刻把被改檔的合約行、綁定測試、外部事實行接到派工詞尾端;只讀分叉點版、砍掉自由文字。
- [[Systems/棧別提問表態閘]]:作者對棧別檢核題的表態(satisfied 附證據、tension 四欄)會被派工鏡頭一起附給審查席,讓席去反駁。
- [[Systems/finding-refute]]:辯方席,對低共識的 ≥major 發現另開乾淨對話試著反駁;派工本身是純提示紀律。
- [[Systems/arch-alignment-lens]]:常設架構對齊席,拿同層最像的既有檔當對照組,目標架構宣告只讀分叉點版。
- [[Systems/heterogeneous-finder-ensemble]]:LLM 席之外,把 linter、測試、mutation 當獨立的「找問題來源」;殘餘缺陷估計 2026-08-14 因鑑別力近零降為只供參考。
- [[Systems/cross-family-audit]]:自主迴圈放行前打一次不同廠商模型(qwen3-max)複核,三態、出錯就放行不否決。
- [[Systems/lumos-guard]]:Claude Code 外掛,認出派工詞第一行 `LUMOS-SEAT:` 的子代理,限制它的工具、寫檔範圍、擋讀席報告暫存處、粗擋推送與 GitHub 指令;自承不是沙盒。
- [[Projects/審查席唯讀隔離_計劃]]:lumos-guard 的設計與決策(含 d4「外掛不跑 git」、d5「席報告收齊前不落地」)。
- [[Systems/nested-agent-permission-scope]]:自主迴圈審計員改成唯讀子程序、每巢狀一層只能更窄;狀態 planned,自主迴圈開 PR 的模式因此停用。
- [[Systems/lumos-context]]:壓縮對話那一刻,在摘要指示後附「請逐字保留五類交棒資訊」;靠摘要器照做。
- [[Systems/lumos事件帳]]:按會談記回合、工具呼叫、子代理派出(含席名、實際模型、寫檔路徑)。
- [[Systems/autonomous-iteration-loop]]:每天自動選題的自主迴圈,編排者是 `claude -p`;目前暫停派工。
- [[Issues/同工作區多session並行改動]]:同一工作目錄多個會談互相夾帶改動的事故帳,四型事故、三條紀律,回頭條件 2026-10-07 已到期。
- 外家席:Codex 三種唯讀審查角色,Gemini 腳本只當備援;2026-09-30 起外家席改為條件席。

## 世界解註解

證據強度:A 受控實驗或方法公開的基準｜B 生產數據或廠商自報｜C 實務經驗｜D 行銷宣稱。註解深度照研究筆記自報;標「分支讀」的由同模型分支讀後交回、主線未逐條重驗。

1. **Anthropic〈How we built our multi-agent research system〉**(2025-06-13)
   - 怎麼運作:主代理規劃、平行派 3–5 個子代理;每個子代理要拿到「目標、輸出格式、工具指引、任務邊界」,含糊就重複做;子代理把產物存外部、只回輕量指標。原文承認寫程式「fewer truly parallelizable tasks」。
   - 證據 B(內部評測多代理高 90.2%,廠商自報)｜讀全文｜關係:驗證(多代理只用在可平行的判斷;跨會談只傳指標)。
2. **Cognition〈Don't Build Multi-Agents〉與〈Multi-Agents: What's Actually Working〉**(2025-06-12;2026-04-22)
   - 怎麼運作:十個月內改口為「寫入維持單線、其他代理只貢獻判斷」;審查代理「不事先共享任何脈絡」時最好,只看 diff;寫碼方用自己的完整脈絡過濾審查意見。認為同模型審查沒問題。
   - 證據 C(Devin Review 每 PR 約 2 個 bug、58% 嚴重為自報,未複驗)｜讀全文｜關係:驗證(乾淨脈絡、單線寫入);在「要不要換家族」上與 Lumos 衝突,見第 18–19 條。
3. **MAST〈Why Do Multi-Agent LLM Systems Fail?〉**(NeurIPS 2025,v3 2025-10-26)
   - 怎麼運作:7 個框架 1,642 條軌跡,人工標註 κ=0.88,分出 14 種失敗;驗證類(沒驗、驗不全、驗錯)合計約 23.5%(研究筆記自己加總);原文「many existing verifiers perform only superficial checks」。
   - 證據 A(框架與模型偏 2024 年代)｜讀全文約 62%｜關係:驗證(Lumos 重心放在收貨驗證與明確終止條件)。
4. **〈Towards a Science of Scaling Agent Systems〉**(Google Research 等,v3 2026-04-08)
   - 怎麼運作:260 種組態受控比較;SWE-bench Verified 上四種多代理架構全輸單代理(−2.1% 到 −14.9%);單代理準確率超過 45% 的任務,加代理是負報酬;集中式架構錯誤放大最小。
   - 證據 A(R² 只有約 0.4)｜讀全文約 52%｜關係:驗證(實作單線、編排者集中聚合);延伸:前沿模型下 high 五席是否划算屬量測問題,見 [[Projects/世界解重新註解2026-10_評測_調研]]。
5. **Claude Code 託管 Code Review、ultrareview、官方 code-review 外掛**(研究預覽 2026-03/04;外掛讀到 2026-10-09 提交)
   - 怎麼運作:多席平行找不同類問題 → 每條候選「對實際程式行為驗證」→ 去重 → 分級(含「既有缺陷」一類);ultrareview 原文「every reported finding is independently reproduced and verified」;開源外掛 2 席查 CLAUDE.md 規則、2 席找 bug,每條發現再派一個驗證子代理,沒驗證成立就丟。
   - 證據 B(每次約 15–25 美元為官方;「實質意見 16%→54%」為二手,未複驗)｜讀官方文件+讀碼｜關係:驗證拓撲;可借鏡「每條都驗」;原生功能重疊(找 bug+驗證那段可當額外證據來源)。
6. **Alibaba OpenCodeReview**(論文 2026-08-10;讀到 2026-10-10 提交)
   - 怎麼運作:過濾器只看 diff、不看審查代理的探索過程,只准刪「diff 證明是錯」的意見,證據不足就放行;併發、記憶體安全、行為改變列為受保護主題,過濾器不准刪;結構化輸出裡分析欄必須排在判決欄前面(順序反了模型會先選好要刪的編號)。
   - 證據 A/B(自建基準 SEM-F1 25.10% vs 11.57%)｜讀碼(分支讀)｜關係:強力驗證辯方設計;可借鏡「不得降級清單」與「先分析後判決」。
7. **Cursor Bugbot**(2026-01-15)
   - 怎麼運作:第一版 8 趟平行,每趟餵打亂檔案順序的 diff,讓模型走不同推理路線,再分桶、多數決、驗證模型濾假陽性;後改代理式。
   - 證據 B(解決率 52%→70% 以上,自報)｜讀官方文件(分支讀)｜關係:可借鏡(亂序是同門席最便宜的去相關手段)。
8. **Refute-or-Promote**(arXiv 2604.19049,2026-04-21)
   - 怎麼運作:多獵手 → 兩關反駁(脈絡不對稱)→ 一關必須實證 → 最後跨家族評論者。OpenSSL 案 10 個代理一致確認一個不存在的漏洞,一個新實例跑三個測試就推翻,原文「One test killed what 80+ agents' reasoning could not.」
   - 證據 C(單一操作者、無消融)｜讀全文(分支讀)｜關係:衝突——「多席一致就直接折」的前提是一致等於可信。
9. **多代理辯論證據群**(Debate or Vote 2508.17536;Talk Isn't Always Cheap 2509.05396;Multi-Agent Debate for LLM Judges 2510.12697 等,2025–2026)
   - 怎麼運作:辯論收益多半來自多數決本身;代理常因同伴反駁把對的改錯;第二輪就塌成「全對或全錯」的兩極。
   - 證據 A｜多數讀摘要,2510.12697 讀全文約 60%(Lumos 引它佐證「第二輪塌縮」經核對成立)｜關係:驗證「審查席禁互辯、編排者只聚合」。
10. **Claude Code 子代理:全新脈絡、分叉模式、逐定義收窄**(官方文件讀取 2026-10-11,版本註記到 v2.1.292)
    - 怎麼運作:一般子代理全新脈絡,只帶派工詞、CLAUDE.md、git 快照與同級名冊;**分叉**(fork)子代理繼承完整對話,互動會談自 v2.1.232(2026-08 中)預設開分叉模式,由模型自行選用;子代理逐字稿存在家目錄的專案/會談/subagents 資料夾。
    - 證據 B｜讀官方文件;「逐字稿執行中就寫到硬碟」研究筆記與舊判斷對照各實測一次(只看檔名、大小、修改時間)｜關係:缺口——直接動到 d5「收齊前硬碟上沒有別席報告」的前提。
11. **Mitropoulos 等〈Measuring and Exploiting Confirmation Bias in LLM-Assisted Security Code Review〉**(arXiv 2603.18740,2026-03-19)
    - 怎麼運作:在審查提示裡斷言「沒有某類漏洞」,偵測率崩跌(GPT-4o-mini 97.2%→3.6%、Claude 3.5 Haiku 68.4%→8.5%);對抗 PR 騙過 Claude Code(GitHub Actions)88.2%;**只刪 PR 說明**就救回 68.75%,原文「instructions are less reliable when the information remains in context」。反向:Thornton(2602.16741)測程式碼內註解,效果小。(更正 2026-10-30:這裡是 v1 的數字;v5(2026-10-27,ICSE 2027)標題改〈When AI Agrees Too Much〉,主結果換成迭代潤飾的宣稱打穿 32/33(97%),遮蔽 PR 說明救回 16/32(50%),第二道防禦由「叫模型忽略」改成「遮蔽全部 commit 中繼資料」;模板式宣稱在真實流程無效且可能反效果。Claude Opus 4.5 強框架 95.7%→88.8%(−6.9)未達顯著,Claude Sonnet 4.5 97.4%→75.5%(−21.9)。上面那句「instructions are less reliable」在 v1 與 v5 都找不到逐字原句,v1 實際是「indicating limits of instruction-based debiasing when information remains in context」)
    - 證據 A(研究一用小模型;研究二 n=34/17)｜讀全文約 76%｜關係:驗證「砍自由文字」;與「把作者表態附給審查席」衝突(待量測)。
12. **〈Governance Decay〉**(arXiv 2606.22528,v2 2026-06-27)
    - 怎麼運作:規則只活在對話裡時,一次壓縮後違規率由 0% 升到彙總 30%(Claude-Sonnet-4.6 為 19%);**成敗由摘要器決定**(同一代理換摘要器,違規 7%–93%);組織特定的「軟規則」衰減最多;放在系統訊息的規則不衰減;解法「Constraint Pinning」把規則抽到不參與壓縮的緩衝區、壓縮後逐字重注入,約 47 token,違規回到 0%。
    - 證據 A｜讀全文(主文 9 頁)｜關係:衝突——[[Systems/lumos-context]] 把保留使用者裁定交給摘要器自律。
13. **OpenAI Codex 的壓縮實作**(main 分支,讀取 2026-10-11)
    - 怎麼運作:摘要提示要求產「給另一個模型接手的交棒摘要」;另外**從最新往回逐字保留使用者訊息**,上限 2 萬 token;壓縮後把初始脈絡與已核准權限重新插回。
    - 證據 B(機制確認,無效果量測)｜讀碼｜關係:可借鏡(結構保留,不靠摘要器)。
14. **Factory〈Evaluating Context Compression〉**(2025-12-16)

    - 證據 B(廠商自評、單一評審)｜讀全文｜關係:驗證 `lumos handoff` 從 git 算檔案狀態;可借鏡探針評估法。
15. **Claude Code worktree 強制檢查**(官方文件讀取 2026-10-11,版本註記到 v2.1.290)
    - 怎麼運作:會談或子代理在 worktree(同一 repo 的獨立工作目錄)裡時,harness 強制擋寫主 checkout、擋工作目錄落在主 checkout 的 shell、擋 `git -C` 等重導,且不能關;子代理可逐次帶 `isolation: worktree`;v2.1.247 起建 worktree 跳過 repo 自帶的 filter driver,理由是「repo 設定能讓 git 執行指令」——與 Lumos d4 同一結論。官方自承擋不住 `cp` 與 shell 重導。
    - 證據 B｜讀官方文件｜關係:驗證 d4;可借鏡(補 lumos-guard 最大的洞「Bash 改 repo 與改狀態的 git」)。
16. **Claude Code 子代理定義與 CLI 權限旗標**(官方文件讀取 2026-10-11)
    - 怎麼運作:子代理定義檔可設工具白名單、禁用清單、只對該子代理生效的 hook;但逐次派工只能指定模型、強度、名稱、isolation,不能逐次指定工具。CLI 原文:`--allowedTools` 是「免詢問」,要限制可用工具得用 `--tools`;`--restricted`(v2.1.248+)拿掉會跑程式的工具、只載指定設定、拒絕跳權限。
    - 證據 B｜讀官方文件｜關係:衝突(nested 那篇「子代理完整繼承父工具集」只對沒有定義檔的子代理成立);可借鏡(使用者層審查席定義檔)。
17. **Lethal trifecta(Willison)、Agents Rule of Two(Meta)與 2026「Comment and Control」事故**(2025-06-16;2025-10-31;CSA 2026-04-17)
    - 怎麼運作:同一會談最多只能同時具備「讀不可信內容、碰敏感資料、改狀態或對外通訊」三者中的兩項;2026-04 的事故是 CI 上的審查代理被 PR 標題與留言劫持,經 GitHub 自己的留言與 API 把金鑰送出。

19. **Correlated Errors(ICML 2025)、Great Models Think Alike(ICML 2025)、自我偏好與 Preference Leakage(2025–2026)**
    - 怎麼運作:越強的模型跨廠商錯誤越相關;評審偏袒自己或同血緣模型的產出,在自己也做錯的題目上仍偏袒,強模型更明顯;先寫長推理再判決可緩解。
    - 證據 A｜Goel 讀全文約 44%,其餘多為摘要(分支讀)｜關係:缺口——換家族的實證價值在判決角色,而 Lumos 辯方 2026-09-30 起預設同門;查無一手研究直接量「LLM 審自家寫的程式碼會不會放水」。
20. **Claude Code 跨會談傳訊**(官方文件讀取 2026-10-11;v2.1.224+,2026-08 第一週)
    - 怎麼運作:訊息只有文字、不帶對話歷史;收方「不能核准任何事、不能改設定」,寄方被指示不得把自己被擋的動作轉請別的會談;`crossSessionInbound` 可設接受、暫留、拒絕,收方是跳權限模式時預設暫留;`notify_when_idle` 在對方閒置時回通知。

## 世界證據對 Lumos 做法的挑戰

1. **「多數決只壓隨機變異,系統性盲點靠異家族 panel」(design-loop 手冊 §B3)**
   - 世界證據:第 18、19 條——跨家族只小幅去相關,最相關的三對都跨家族,越強越像。
   - 挑戰的前提:換品牌就能補系統性盲點。
   - 怎麼驗證:從歷史卷證的「席 × 發現」矩陣算有效獨立票數,分家族比較(屬 [[Projects/世界解重新註解2026-10_評測_調研]] 的量測)。
2. **2026-09-30「辯方預設同門」**
   - 世界證據:自我偏好與同血緣偏袒(A)集中在判決角色。
   - 挑戰的前提:同門辯方與外家辯方在降級判斷上等價。d11 當時自己寫下了這個代價,所以是用成本換掉的,不是沒想到。
   - 怎麼驗證:候選 2 的翻轉率回放。
3. **「多席獨立一致就直接折」(設計審)**
   - 世界證據:Refute-or-Promote 的 OpenSSL 案;Lumos 自己 2026-09-03 的量測也寫過一致可以兩個都錯。
   - 挑戰的前提:一致代表獨立確認;但一致可能來自共同錯誤前提,而且「席位真的獨立」本身正被下一條動搖。
   - 怎麼驗證:候選 3 的撤回率回放。
4. **作者表態附進派工詞**
   - 世界證據:Mitropoulos——「無 bug」框架讓偵測率崩跌,資訊留在脈絡裡時,叫模型忽略的效力打折。(更正 2026-10-30:崩跌幅度依模型差很多,v5 裡 GPT-4o-mini 掉 93.5 點、Claude 3.5 Haiku 59.9、DeepSeek V3 42.9、Claude Sonnet 4.5 21.9、Gemini 2.0 Flash 16.2 都達顯著,只有 Claude Opus 4.5 掉 6.9 點未達顯著;Lumos 派的 Sonnet 席是 5.5、這裡沒量過,只能推論,不能當成安全;唯一通用防線是不把表態放進去)
   - 挑戰的前提:附上去是「讓席反駁」,不會帶風向。效應在前沿模型上多大未知。
   - 怎麼驗證:候選 6 的消融。
5. **審查席獨立性的新漏洞(決策 d5、手冊「每輪派全新 agent」)**:d5 的前提是「收齊前硬碟上沒有別席報告、席只看得到派工詞」。四個側門,確認程度不同:
   - 分叉子代理繼承對話——**Lumos 側已讀碼確認**:lumos-guard 的派工攔截只看第一行標記與上層代理編號,不看子代理型別;只有「席自己再派」那層限制型別(答案檔 Q04-01 讀碼)。**Claude Code 側只讀官方文件**:分叉模式 2026-08 起預設開、分叉繼承完整對話;編排者實際會不會用分叉派席、分叉席是否真的看到別席報告,**是推論、沒實測**。
   - 子代理逐字稿邊跑邊寫——**已實測**:研究筆記與舊判斷對照各看到執行中的逐字稿檔持續變大(只看大小與時間、沒讀內容);**已讀碼確認**:lumos-guard 沒有任何規則涉及這個資料夾,Bash 本來就是完整 shell。**未實測**:審查席實際去讀它。附帶:Projects/子代理續談調研(2026-08-14)寫「互動會談子代理正文一律不落地」,與這兩次觀察相反。
   - agent teams 互傳訊息與自動成隊——**只讀官方文件**:開旗標後帶名稱的派工會變 teammate、teammate 有信箱;**Lumos 側查無偵測**(單次核對);teammate 會不會經過 lumos-guard 的派工與工具事件,repo 答不了、**沒實測**。lumos-guard 白名單不含 SendMessage,若攔得到就擋得住訊息,但攔不攔得到正是未知。
   - 工具白名單側門——**已讀碼確認**:審查席白名單含 `TaskOutput`(本篇查證屬實)、WebFetch、WebSearch;**未實測** `TaskOutput` 讀不讀得到同輪別席的輸出。
   - 怎麼驗證:候選 1 的情境探針,四個側門各一案,記在事件帳。
6. **lumos-context 把保留使用者裁定交給摘要器**
   - 世界證據:Governance Decay——軟規則衰減最大、摘要器決定成敗、結構釘選回到 0%;Codex 用結構逐字保留使用者訊息。
   - 挑戰的前提:摘要器會照指示逐字保留。注意 Lumos 在自主迴圈那條線已用 `[PIN]` 做結構釘選,挑戰只針對互動會談。
   - 怎麼驗證:候選 7 的小基準。
7. **「禁互辯」對上 Claude Code 官方範例鼓勵 teammate 互辯**
   - 世界證據:辯論文獻(A)支持禁互辯;官方範例(C)針對多假設除錯這類探索任務。
   - 結論:審查判斷上 Lumos 站得住,不必推廣到所有任務;不需改動。
8. **「跨 session 傳訊此條純自律無機械守衛」**
   - 世界證據:Claude Code 2.1.224+ 收方不代批、不改設定、跳權限收方預設暫留。
   - 挑戰的前提:這條敘述在 Claude Code 側已部分過時(依文件,未實測);Codex 側仍成立。
9. **「多代理只用在審查」是對的,但五席值不值得**
   - 世界證據:單代理基線超過 45% 時加代理是負報酬;前 5 席已拿 90% 可得獨立性。
   - 這指向量測,不是本類的改動;交給評測那一類。
10. **反向驗證(世界證據支持、可作為守住的理由)**:寫入單線(Cognition、Google scaling、CooperBench、agent teams 文件);審查員乾淨脈絡與零自由文字(Cognition、Mitropoulos、OpenCodeReview);外掛不跑 git(Claude Code v2.1.247 同一理由);合併順序不交 LLM(BulkPR-Bench);跨會談只傳指標;`lumos handoff` 從 git 算檔案狀態(正對 Factory 量到最弱的「檔案軌跡」)。

## 筆記與程式或來源對不上的地方

1. **heterogeneous-finder-ensemble 的文獻引述**:摘要行、決策 d1 的選擇理由、正文都說 arXiv 2511.16708「用 submodularity 數學證明異質分析器各加獨立資訊」,code-loop 手冊照寫。實際:論文的四個「代理」是 Python 靜態分析模組、沒有 LLM;定理前提「條件獨立」作者自承沒驗;自己的消融表上全組合(72.4%)輸給最佳兩個(79.3%),也不比最強單一模組(75.9%)好。另外 code-loop 手冊把 AutoSafeCoder 標成 2511.16708,節點把它連到 2409.10737。建議:立一篇 Issue,四處一起改寫成「改引執行證據去相關的文獻」,並修正 AutoSafeCoder 出處。
2. **design-loop 手冊 §B3**:原句大意「多數決只壓隨機變異,系統性盲點靠異家族 panel,兩者不互替」。實際:Nine Judges 等 A 級證據顯示換家族只小幅去相關。建議改寫為「系統性盲點靠不同的證據來源(執行、測試、人抽驗),換家族只能小幅補」,立 Issue。
3. **nested-agent-permission-scope 的摘要行**:原句大意「Claude Code 的 Agent 工具不支援 allowedTools,子代理完整繼承父會談工具集」。實際:只對沒有定義檔的一般子代理成立;依定義檔收窄是原生功能;而且 `--allowedTools` 是「免詢問」不是「限制」,原生限制用 `--tools`。建議改句,並在設計段改用 `--tools` 加 `--restricted`。
