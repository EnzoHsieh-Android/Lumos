# 過期鎖安全接手_計劃

## 問題與裁定

[[Issues/過期鎖接手可能雙持]] 的跨程序交錯已在主線重現：B 看見過期鎖後暫停，A 搬走舊鎖並取得新鎖，B 恢復後又搬走 A 的新鎖，兩者均回取得。`os.rename` 的單次原子性不能保證它搬走的仍是先前觀察的檔案。筆記庫寫入和派工鏡頭共用 `_excl_lock_try`；後者的鎖記錄的是短命的派工者 PID，背景計算會在派工者結束後繼續。因此即使加輔助鎖，也不能用「鎖內 PID 已死」判定背景工作已停。

本案最小修法是**取消 `_excl_lock_try` 的自動過期接手**，保留 `O_CREAT|O_EXCL` 的正常取鎖。已存在的鎖一律回未取得，不因 mtime 或 PID 推論可刪；不增加第二套 `flock` 或救援輔助鎖。正常建鎖若在寫入 PID、時間時短寫，應補寫到完整；寫入失敗則應關閉 fd 並清掉**這次新建且身份未變**的半成品；不能回成功也不能留下自己造成的永久鎖。`FileExistsError` 表示已存在而回 `False`；其他建檔與寫入錯誤向呼叫端傳遞，不再偽裝為另一持有者。代價是程序異常結束後可能留下鎖，需要先確認真持有者與背景工作均已停止，再由人移除。這個取捨優先避免兩名寫者同時自認持鎖，讓後續治理帳設計有可靠地基。

筆記庫等待上限維持 60 秒，到期訊息須給鎖檔位置與人工查核方向，不能宣稱一定是另一程序仍在寫；建檔本身失敗則立刻回帶位置的錯誤，不等滿 60 秒。派工鏡頭對正常短暫等待保留原 JSON 值與返回碼；若期限到時鎖齡已超過舊過期門檻且仍無快取，JSON 回 `lock_uncertain=true`、`still_warming=false`、鎖位置與範圍，原返回碼 5 維持，hook 須把「狀態未知、需檢查鎖」傳給真正的派工流程。建檔本身失敗應立刻回 rc 2 與含鎖位置的 `lock_error=true` JSON，hook 亦須傳達「鎖無法建立、請檢查鎖」，不當作背景工作。鎖齡不足門檻也不能證明背景仍活著，所以任何超時文案只能說「可能在算」。不自動刪鎖，也不在此案修改快取與背景工作釋放機制。

安全界線只對**已切換到本版原語的程序**成立。舊版 `_excl_lock_try` 不讀新標記，舊程序仍可按 mtime 偷新版的鎖；啟用前須停掉正在使用同一筆記庫或鏡頭快取的舊程序，並更新會共同使用這些路徑的工具鏈安裝。無法確認沒有舊版仍在跑時，不宣稱跨版本單持有，也不把治理帳新寫者接上此鎖。這是發布前進場條件，非本案程式可單方強制的保證；若實際工作常需新舊版本並行，回到 Issue 設計跨版本鎖協議。

## 驗收條款

- [S1] 當兩個已切換本版的不同 PID 遇既有過期鎖時，`_excl_lock_try` 應都拒絕接手且不移除該鎖；測試在舊碼的 `stat` 間隙穩定翻紅，修後可不再進入舊分支。 [test:t_excl_lock_stale_takeover_is_single_owner]
- [S2] 當過期鎖已存在時，`_excl_lock_try` 應保留活 PID、死 PID 或符號連結的舊鎖且回未取得；無鎖時仍正常獨佔建立。無 symlink 權限的平台可只跳過該子斷言。 [test:t_excl_lock_existing_is_not_stolen]
- [S3] 當新鎖寫入短寫或失敗時，`_excl_lock_try` 應補齊短寫；失敗時關閉 fd、拒絕取得並只清掉身份未變的本次半成品；當無權限建鎖時，應傳遞與已存在不同的錯誤。 [test:t_excl_lock_creation_failure_cleans_own_file]
- [S4] 當筆記庫遇殘留鎖時，`_vault_write_lock` 應在有限等待後拒絕寫入並給鎖位置與人工查核方向；建鎖錯誤應立即報錯。正常取鎖、巢狀與釋放仍須維持。 [test:t_vault_stale_lock_fails_with_path]
- [S5] 當派工鏡頭遇超過舊門檻的鎖且沒有快取時，`_lens_wait_or_warm` 應不新派第二支，超時僅回狀態未知；若建鎖失敗則應立刻回 rc 2 與 `lock_error`，hook 應把兩類狀態分別傳到派工詞；正常暖快取與原返回碼仍維持。 [test:t_lens_stale_lock_reports_uncertainty]
- [S6] 當此版工具準備接到筆記庫或派工快取時，發布者應先確定共用鎖的舊版程序已停止並更新安裝；無法確定時不得宣稱跨版本單持有。 [manual:在隔離的舊版程序與新版程序共存實驗中驗舊版仍可偷過期鎖，再查實際安裝與進程並記進場裁定]

最小紅燈先用 S1 的跨程序屏障重現雙持，再用 S2–S5 的獨立測試釘住可用性、半寫入與實際 hook 訊息；每個子程序有逾時；歷史紅燈須證明舊碼走進競態間隙，永久回歸容許修後直接拒絕，不要求進已刪除的 `stat` 分支；caller 級測試須證明進對應入口。修法若要求改派工鏡頭背景工作的所有權或引入新租約協議，本案停止擴張，另開案評估。完工時同步 `_excl_lock_try`、筆記庫鎖與派工鏡頭的舊註解，以及仍引用「過期會自動接手」的進行中計劃，不讓舊說明冒充新行為。

PRIOR-ART: [Python `os.open`](https://docs.python.org/3/library/os.html#os.open) 的 `O_CREAT|O_EXCL` 可在鎖不存在時獨佔建立；[Python `os.rename`](https://docs.python.org/3/library/os.html#os.rename) 只保證單次更名原子，不替先前 `stat` 做檔案身份比對。沿用既有獨佔建檔，停掉無法證明安全的自動接手；用本專案跨程序測試驗證 ABA，而非把文件當成競態證明。

[Linux `open(2)` 手冊](https://www.man7.org/linux/man-pages/man2/open.2.html) 也指出 `O_CREAT|O_EXCL` 對既有檔及符號連結會拒絕，但舊 NFS 配置可能不支援這個互斥語意。本案測的是隔離機器本地檔案系統；若鎖路徑移到 NFS，需先驗排他建立，不能直接套本案結論。

RETIRE-IF: 若 S1 在原版主線就無法重現 `True/True`，撤回此方案重查實際競態；若連續四週有兩次以上因殘留鎖阻斷正常寫入、實際使用必須混用新舊工具，或人工復原成本大於避免雙持的收益，重開具背景工作身份的租約方案，不直接恢復按 mtime 搬鎖。[Lease 設計先例](https://martinfowler.com/articles/patterns-of-distributed-systems/lease.html) 要求真持有者續約；本案沒有可驗的背景身份，因此不假裝鎖齡就是租約。

## 回退

若新鎖原語引入其他回歸，優先 roll-forward 修正或暫停筆記寫入／派工鏡頭入口；不得直接還原含過期 rename 的舊版並宣稱仍有單持有保證。S1 在舊碼會重新翻紅；治理帳新寫者在修復完成前仍不能接上。舊版與新版共用鎖的切換窗口要先停舊程序、換安裝、再開新版；做不到就維持停用該共用入口。

遇到殘留鎖，先從錯誤訊息的鎖位置與派工範圍找到對應工作。鎖內 PID **僅是啟動者，不是背景持有者證明**；在 Unix 可查當前 `dispatch-lens` 命令列與相同 repo／range，在 Windows 查程序命令列或工作管理員；任何平台只要無法確認相關背景程序已停，就保留鎖、不人工刪除，改從尚未佔用的環境做診斷。確認全部停止後才人工移除。這是人工恢復操作，不是讓工具在 timeout 時替人刪鎖。
