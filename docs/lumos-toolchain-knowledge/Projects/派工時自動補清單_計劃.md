# 派工時自動補清單_計劃

> 白話:每次派審查員之前,規矩要求先跑一道指令算出「這批改動碰到哪些帶硬合約或出過事故的筆記」,再把清單貼進派工詞。**實帳 28 份代碼審派工單,0 份做過這一步。** 過去兩年想把它機械化都卡在「派工那一刻沒有東西攔得到」。★2026-09-03 實測證明攔得到,而且不只能攔——能直接把清單塞進派工詞。★ 本案就是做那件事:**不擋任何人,只在派工當下把機器算好的清單補上去。**

PRIOR-ART: ① 最小解層級——不新增指令、不新增閘、不要求任何人多記得做一件事;只在既有的 Claude Code `PreToolUse` hook 位置,把既有的 `lumos impact --diff` 輸出接進既有的派工路徑。本 repo 已有一支同位置的 hook(改檔前注入合約提示),本案是它的第二個消費者。② 世界解過沒——「在工具呼叫前注入上下文」是 Claude Code 官方明列的能力(`hookSpecificOutput.updatedInput`),不是自創機制;但★沒有查到有人拿它做「審查派工的必查清單注入」★,故借機制、自己搭。③ 裁定=borrow-design,零依賴原生實作。

## 一句話

★把「派工前記得跑一道指令並手工貼清單」這條沒人做得到的紀律,換成「派工當下機器自己塞」。不擋、不判、不記帳,只補。★

## 這不是重跑被停的那個案子

[[Projects/impact鏡頭機械化_計劃]] 2026-08-29 停案,死因是「派工那一刻沒有機械強制點」,重開條件=先答出強制點在哪。**2026-09-03 實測答出來了**(見 [[Verification/2026-09-03_派工攔截點實測]]),該死因已翻案。

但★本案與那個案子是不同的題目★,不是同一個方案換皮:

| | 停掉的那案 | 本案 |
|---|---|---|
| 動作 | 派工詞**沒附清單就擋下** | 派工詞**沒附清單就補上** |
| 落點 | `lumos` 自己的指令層 | Claude Code 的 `PreToolUse` hook(宿主層) |
| 失敗模式 | 誤擋 → 逼人繞過 | ★沒有擋,所以沒有繞過壓力★ |
| 2026-08-02 裁定是否適用 | 適用(該裁定正是講「擋」的兩難) | ★整條不適用★ |
| 靠人記得嗎 | 靠(另一支你可能不跑的指令) | 不靠 |

★這張表是本案能不能成立的關鍵,審查時請優先打它。★ 若某席認為「補」在實質上等同「擋」,或認為 2026-08-02 裁定仍適用,那是 blocker,本案應退回。

## 憑什麼說做得到(實測,不是推論)

全部出自 [[Verification/2026-09-03_派工攔截點實測]],Claude Code **2.1.259**,重跑步驟在 `governance/eval/hook-intercept/`:

- `PreToolUse` 的 matcher 匹配得到派子代理,`tool_name` = **`Agent`**。
- hook 收到的 `tool_input` 帶 **`prompt`(派工詞全文)**、`description`、`subagent_type`、`model`。
- 回 `hookSpecificOutput.updatedInput` **可以改寫派工詞**——實測子代理原封不動列出只存在於注入文字裡的三個節點名。
- 回 `permissionDecision:"deny"` 擋得住(本案**不用**這條,但它證明這個位置有實權)。
- `SubagentStart` 拿不到派工詞,**不能用**。

## 憑什麼說值得做(數字,不是感覺)

- **「建了沒人跑」有帳**:2026-08-30 盤點,28 份代碼審派工單 **0 份**做過「貼固定席內容」這一步。
- **漏的東西有量過**:[[Verification/2026-09-03_席間覆蓋率離線量測]]——★一個審查席會漏掉同儕找到的 64.6% 真缺陷★(85 個確定多席輪、822 個相異缺陷),而且加席位邊際遞減(2 席 74.2% → 3 席 60.8% → 4 席 58.3%)。**多給每一席一份機器算的必查清單,是少數不用多派人就可能提高覆蓋率的做法。**
- **清單本身已經算得出來**:`lumos impact --diff` 會吐固定席節點,每篇標明為什麼被釘住(不變量/守衛面/不可逆)與被哪個檔牽連。實測一段真實 code 範圍:23 檔 → 21 篇固定席。

## ★硬約束(實測撞出來的,不是預想)★

1. **注入內容必須看起來是正當的系統附加。** 第一次實測把內容寫成「暗號是 PINEAPPLE-7742」,★子代理拒答並指認為提示注入測試★;換成長得像真實清單的內容才成功。所以注入文字要用中性的「以下為機械算出的必查清單」框架,不得使用命令式或誘導式措辭。
2. **這個 hook 本身必須進錨點保護清單。** 此機制與提示注入技術上是同一件事,差別只在善意——同一個位置,惡意的人可以竄改任何子代理的派工詞。本 repo 已有錨點機制(驗證器檔案被動過就擋推送),★這支 hook 必須納入,否則本案是在自己身上開一個後門★。這是硬約束,不是提醒。
3. **不得擋任何派工。** 本案唯一允許的回傳是 `permissionDecision:"allow"` 加 `updatedInput`;★任何情況都不得回 `deny`★。理由=誤擋會訓練人繞過(見 [[Issues/推新分支時風險分級拿空樹當起點]] 同日實證),而本案的整個賣點就是沒有繞過壓力。
4. **hook 失敗必須靜默放行。** 算不出清單、超時、`lumos` 不在、不是 git repo——一律原樣放行,不得阻斷派工。★守衛壞掉不能變成工作停擺。★

## ★未解(本案最需要被審的地方,我沒有答案)★

以下四項我沒查、沒量,寫在這裡是要審查席正面打它們,不是佔位:

1. **範圍怎麼收**:這個 hook 會對**每一次**派子代理 fire,包括跟審查完全無關的(查資料、跑測試、寫文件)。判「這次是審查派工」的依據是什麼?`subagent_type`?派工詞關鍵字?★都還沒想清楚,而且判太寬的代價是每次派工都跑一次影響計算★。
2. **算清單要多久**:hook 有超時上限。`lumos impact --diff` 在大 diff 上要跑多久,★我沒量過★。超時就靜默放行(約束 4),但那等於在最需要清單的大改動上最容易失效——這個反向失效模式要正面處理。
3. **清單會不會太長反而有害**:固定席實測常有 20-26 篇。全塞進去會不會稀釋注意力?★外部研究說材料太多審查員看不完,但本 repo 自己三次實驗都量不到那個效應(見 `Systems/canary-audit` 審查規模那條線,已裁停止投資)——兩邊都沒定論★。要截斷嗎?截斷的依據是什麼?
4. **拿什麼 diff 範圍算**:hook 拿得到 `cwd`,但拿不到「這次審查在審哪個範圍」。用 `Lumos/main..HEAD`?未提交的工作區?★派工詞裡通常寫著審查對象,但從散文抽範圍是啟發式,會錯★。

## 怎麼驗它真的有效(不只是「裝上去了」)

★不接受「hook 裝好了」當交付★。驗收條件:

- **機械條件**:重跑 `governance/eval/hook-intercept/README.md` 的注入實測,確認在**真實審查派工**上生效(不是哨兵測試)。
- **行為條件**:接上後的下一批代碼審,派工單裡固定席內容的出現率從 **0/28** 變成多少——★這個數字要真的去數,不是宣稱★。
- **反向條件**:確認無關的派工(查資料、跑測試)**沒有**被塞清單,也沒有被拖慢。
- **不驗**:本案★不宣稱★能提高審查品質或降低漏抓率。那要用 [[Verification/2026-09-03_席間覆蓋率離線量測]] 的同一把尺量,是另一件事。誠實界線見下。

## 誠實界線

- **本案只解決「清單有沒有到審查員眼前」,不解決「審查員看了有沒有用」。** 席間覆蓋率 64.6% 那個數字是**現況**;塞了清單之後會不會變好,★本案不量、也不宣稱★。
- **綁版本 2.1.259**。`tool_name`、`tool_input` 欄位名、`updatedInput` 行為都可能隨版本變;動工前先重跑實測。
- **只涵蓋本機的 Claude Code 派工路徑**。用自然語言喚起子代理的那條路徑(若存在)不在射程內,我沒驗過。
- **這是紀律的機械化,不是正確性的保證**。清單是機器算的,但「該不該把某節點列為固定席」仍由既有的排序與釘選邏輯決定,那一層的品質不在本案射程。
- REVISIT:2026-10-03 若本案未開工,回頭判是資源問題還是那四個未解項其實答不出來。

## 實務隱患

命中風險類 `self-governance` 與 `prod-irreversible`(後者由 `pitfalls --check` 機械點名,逐條答如下):

**`prod-irreversible`(改的是每台機器都會跑的全域設定)**:

- **改的是 `~/.claude/settings.json`,不是專案檔。** 一旦寫壞,★該機器上所有 session 的全部 hook 都會靜默失效★(該檔 JSON 壞掉會整份設定失效,不只壞掉的那條)。這比一般的專案改動不可逆——它不在版控裡、壞了不會有測試紅、CI 也看不到。
- **緩解(三條,缺一不可)**:①安裝時**先備份再合併**,合併後立刻 `jq -e` 驗證 JSON 合法且抓得到新增那條;②★絕不取代 `hooks.PreToolUse` 陣列,只追加★(該陣列已有改檔前注入那支 hook,取代等於拆掉別人的守衛);③提供一行卸載,且卸載後要能與備份逐欄比對相同。★這三條在 2026-09-03 的實測裡已經實際走過一遍並驗證過,不是紙上規劃。★
- **★未解★**:多機分發怎麼辦。本 repo 的 skill 是每台機器裝一次,但這支 hook 改的是全域設定——新機器安裝、既有機器升級、以及「某台機器的設定已被別人改過」三種情況怎麼處理,★我沒想清楚,審查時要打★。

**`self-governance`(用我們自己的機制治理我們自己)**:

- **自己開後門**:見硬約束 2。緩解=hook 進錨點保護,且該保護的存在要有測試釘。
- **裁判兼球員**:設計者與被治理的流程是同一套。緩解=驗收條件裡的行為條件(固定席出現率)是外部可數的,不靠自評。
- **靜默失效**:約束 4 要求失敗放行,代價是「沒塞成功」和「不需要塞」在外觀上一樣。★緩解未定——這正是未解項 2 的一部分,審查時要打★。
- **對無關派工的稅**:每次派子代理都多跑一段。緩解依賴未解項 1 的範圍收斂,尚無方案。
- **★沒有機械守衛的部分★**:硬約束 1(注入措辭要中性)純靠寫的人自覺,沒有程式擋得住有人把它寫成命令式。回頭條件=接上後首批派工,人工抽看三份注入內容的措辭;REVISIT:2026-10-03 與本篇其他回頭條件同批。
