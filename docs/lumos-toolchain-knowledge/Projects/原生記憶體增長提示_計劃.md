# 原生記憶體增長提示_計劃

白話:記憶體與穩定性驗收現在用「沒人指著的原生記憶體」掃描抓 .so 忘了 release,但 SDK 自己留一份清單、還指著那塊記憶體時掃描是 0,抓不到;這種只剩 Native Heap 前後兩個數字(只寫在收集腳本的結果檔,lumos 判定不讀也不印)。這份計劃讓人替要查的情境(例如結帳)自己打開、預設關(d4),打開的情境在既有量測之後另跑一段 N 輪,只錄 Perfetto 的原生配置記帳(heapprofd,掛在 malloc/free 上記每個呼叫位置配了多少、還了多少;d1),按呼叫位置(從 malloc 往上跳過 libc、libc++ 這些配置器,第一個不是配置器的函式)彙總量測結束時還沒釋放的量,列成**原生配置排行**(哪支 .so 的哪個函式、App 哪個函式呼叫的、結束時還留著多少),照留著的量排序,**只提醒、不擋推送**。排行不分「在漲」還是「停住」:快取與物件池也會上榜,要人看;分漲停的判法三輪設計審都被時間對齊打穿,拆到 [[Projects/原生記憶體增長判法_計劃]] 先做實驗(d5)。2026-10-28 Enzo 要求「把能優化的效能問題抓出來優化,不是找碴」,並要求先查精準的世界解、再到實驗室實測。

PRIOR-ART: 最小解在既有的收集腳本裡:它已經有「暖機 W 輪 → 量測 N 輪」兩次驅動呼叫,量測期間本來就錄一份 Perfetto 追蹤檔;skill lumos-android-evidence 的 L3(逐層診斷的第四層「誰配置、誰留住」,要宣告測試資料才做)已經在用 heapprofd(`--heaps libc.malloc`)事後診斷原生漏法。世界解:①Perfetto heapprofd(Android 10 以上;user 建置只限 profileable 或 debuggable 的 App)的 HeapprofdConfig 欄位照 v57.2 的 protos/perfetto/config/profiling/heapprofd_config.proto(github.com/google/perfetto/blob/v57.2/…):`process_cmdline`、`sampling_interval_bytes`(預設 4096,不能是 0)、`shmem_size_bytes`(預設 8 MiB、2 的次方)、`no_startup`(只接已經在跑的行程,Android 11 以上)、`continuous_dump_config { dump_phase_ms dump_interval_ms }`(第一次傾印在 dump_phase_ms 毫秒後,之後每隔 dump_interval_ms 毫秒傾印一次);②trace_processor 的 `heap_profile_allocation` 每列是「這次傾印跟上一次比的差額」(配置正、釋放負;v57.2 src/trace_processor/importers/proto/profile_packet_sequence_state.cc 的 alloc_delta、free_delta),所以某個傾印時間點還沒釋放的量 = 同一呼叫位置、ts 不晚於那一刻的 size 加總,官方 stdlib 的 android.memory.heap_profile.summary_tree 也是 `sum(size)` 當沒釋放的量;③判斷「在漲還是停住」的世界解(BLeak、LeakCanary 3.0 的堆積增長偵測)隨判法搬到 [[Projects/原生記憶體增長判法_計劃]]。裁定:錄製與查詢原樣借 Perfetto,自己只寫按呼叫位置歸併與排行;不採 dump_at_max(只有峰值那一刻,不是結束時還留著的量)。

## 實驗室實測(2026-10-28)

在 macrobench-lab 另開工作目錄與分支 native-growth-lab(不推送、不合併)做:假原生 SDK 多兩種情境,SM-X710 / Android 16,benchmark 建置(profileable、非除錯版)。每種:停 App → 啟動 → 驅動暖機 2 輪 → 讀「沒人指著的原生記憶體」與 Native Heap → 開 heapprofd(只接已在跑的行程、每秒傾印一次)→ 驅動量測 8 輪 → 等 3 秒停錄 → 再讀兩個對照數字。每輪開畫面配 2 MB。

| 情境 | 沒人指著(前→後) | Native Heap KB(前→後) | heapprofd 判法 | 點到的呼叫位置 |
|---|---|---|---|---|
| ①沒呼叫 release、記憶體沒人指著 | 0 → 16 MB(8 塊) | 9176 → 26468 | 線性增長:結尾 16 MB,前半增 8、後半增 6 | `nativeCreate` @ libfakesdk.so |
| ②SDK 全域清單留著每個 handle、App 沒 release | 0 → 0(抓不到) | 11576 → 30860 | 線性增長:結尾 16 MB,前半增 8、後半增 6 | `nativeCreateTracked` @ libfakesdk.so ← `PlayerActivity.onCreate` |
| ③上限 4 塊的池(暖機已配 2 塊) | 0 → 0 | 11244 → 16268 | 停住:結尾 4 MB,前半增 2、後半增 0 | `nativePoolAcquire` @ libfakesdk.so |
| 正常版(都有 release) | 0 → 0 | 7220 → 6264 | 不增長 | `nativeCreate`(開關之間在 0 與 2 MB 來回) |

- 當時的草稿判法(分漲停的判法已拆到 [[Projects/原生記憶體增長判法_計劃]];這份只用表裡的結尾累計):把量測期間的傾印依時間切成前後兩半,每個呼叫位置算「中間那次傾印比第一次多多少」(前半增)與「最後一次比中間多多少」(後半增);結尾還留著、前半有增、後半增量至少是前半的一半 → 線性增長;結尾還留著、但後半沒有跟著漲 → 停住;其他 → 不增長。只列結尾或增量超過 1 MB 的。四種情境都分對。
- heapprofd 只記開始記帳之後的配置,所以暖機期間配的(包括池已經配好的那 2 塊)本來就不算進來,不用另外扣基線。
- 呼叫鏈看得到 .so 匯出的 JNI 函式名(這支 .so 沒拿掉匯出符號)與 App 的函式,跟既有 L3 的結論一樣只到函式、沒有行號。
- 錄檔與暫存都已刪掉(錄檔當含個資處理,只留上面的數字)。

實驗當時的查詢(trace_processor;malloc 上一層的函式當呼叫位置;正式版改法見〈排行怎麼算〉第 1、2 條與〈打算怎麼做〉第 4 步):

```
create perfetto table site as
select a.ts, a.size, coalesce(pf.name, '?') || ' @ ' || coalesce(pm.name, '?') as site
from heap_profile_allocation a
join stack_profile_callsite c on c.id = a.callsite_id
left join stack_profile_callsite p on p.id = c.parent_id
left join stack_profile_frame pf on pf.id = p.frame_id
left join stack_profile_mapping pm on pm.id = pf.mapping
where a.heap_name = 'libc.malloc';
create perfetto table dumps as select distinct ts from site;
select d.ts, s.site, sum(s.size) as unreleased
from dumps d join site s on s.ts <= d.ts group by d.ts, s.site order by s.site, d.ts;
```

實驗當時的錄製設定(正式版時長與檔名見〈打算怎麼做〉第 3 步;推到裝置 `/data/misc/perfetto-configs/`,`perfetto --txt -c … -o /data/misc/perfetto-traces/… --background`,停錄用 `kill -TERM`):


## 排行怎麼算

收集腳本取數、lumos 排與印(收集腳本照既有慣例只縮減資料、不判過不過):

1. 呼叫位置(收集腳本):從 malloc 那一框往上走,跳過「配置器那幾層」,第一個不是的框架就是呼叫位置。
   - .so 名稱先取「所在 .so」:mapping 名有「!」時取最後一個「!」之後的部分(.so 未解壓、直接從 APK 載入時,名稱是 `…/base.apk!libfoo.so`,見 r4-intake 的查證),沒有就取路徑最後一段;mapping 沒有名字時記「?」。
   - 配置器那幾層:所在 .so 是 libc.so、libc++.so、libc++_shared.so、libstdc++.so(這幾支裡的全部框架都跳過,歸責給呼叫它們的 SDK);或函式名(heapprofd 存的是未還原的 mangle 名)精確等於 malloc、calloc、realloc、posix_memalign、memalign、aligned_alloc、__libc_malloc、je_malloc、tc_malloc、__wrap_malloc;或以 _Znw、_Zna(operator new 系列)、_ZNSt、_ZNKSt(靜態連結進 SDK 的標準庫容器內部)開頭——比對前綴用 GLOB,不用 LIKE(底線在 LIKE 裡是萬用字元)。
   - 函式名以「ERROR 」開頭的是回溯失敗時補上的偽框架,跟「整條都是配置器」一樣記成「?」。
   - 呼叫者:呼叫位置往上的第一個不在 libart.so 的框架(跳過 ART 的 JNI 跳板);沒有、或那一框是 ERROR 偽框架,就記「?」。
   - name 是 NULL 或空字串當沒有符號,函式名寫成「.so 名稱+0x相對位址」(rel_pc 也是 NULL 時寫 +0x?)並標沒有符號;沒有符號時是按呼叫點歸併,同一個沒有名字的函式裡的不同呼叫點會分成不同列。函式名與呼叫者存檔前截到 500 字元。
   - 系統函式庫:mapping 完整路徑在 /system/、/apex/、/vendor/、/product/、/system_ext/、/odm/ 底下。
2. 數字(收集腳本):每個 callsite 結束時還沒釋放的量 = 它所有列的 size 加總(heapprofd 只記開錄之後的配置;停錄時會傾印一次,錄製設定的 data_source_stop_timeout_ms 內沒寫完就不補、stats 記 heapprofd_non_finalized_profile,照〈打算怎麼做〉第 4 步寫 failed)。先對不重複的 callsite 往上找呼叫位置,再歸併到呼叫位置(函式、.so 名稱、系統旗標三者當鍵;系統與非系統的同名 .so 不會混在一起,兩支都在 App 底下的同名 .so 會併成一列),再篩結束累計至少 1 MiB(1048576 位元組)的,照結束累計降冪、函式名升冪、.so 升冪、系統旗標升冪取前 200 個;呼叫者取「從它進來的那些 callsite 結束累計加總」最大的那個,並列時有名字的排在「?」前面、再照呼叫者名字升冪。1 MiB 只在這裡篩一次。
3. 排與印(lumos):保持收集腳本的順序,最多印 20 個;每行印函式、所在 .so、呼叫者、結束時還留著多少、有沒有符號、是不是系統函式庫;最上面一行寫明「量測結束時還留著、而且是開錄之後才配的原生配置,含快取與池,不代表漏」;ok 但一個都沒有時印一行「原生配置排行:沒有結束時還留著 1 MiB 以上的呼叫位置」。函式名照存的 mangle 名印,不在 lumos 還原。

## 打算怎麼做

1. 預設關,按情境打開(d4):`stability` 段加一個選填鍵 `native_retained`,值是情境名的清單,`"@default"` 代表沒指定情境的那一段(沒設 LUMOS_STABILITY_SCENARIO;情境名只收英數字、底線、連字號,這個名字不會跟情境撞;既有程式內部用 None 代表這一段,設定檔裡要有個字面名才寫得出來,reference.md 的設定表寫明);沒寫等於空清單。型別(清單、元素是非空字串、不重複)照其他 stability 選填鍵在 `_macrobench_stab_optional_err` 驗;名字要對到 `stability_scenarios` 或是 "@default" 這條跨段檢查放 `_macrobench_stab_top_err`(那裡拿得到 `stability_scenarios`);不合格回 2 擋下。**不寫進 `stability_scenarios`、不動 E2E_SCENARIO_KEYS、不改既有情境名規則**:舊版 lumos 不驗 stability 段的未知鍵,退回舊版時設定不會被擋下。收集腳本的 `load_config` 把這次的情境名一起回傳(e2e 測試用正規式抓的 `scen[k] for k in (…)` 那一行不動),`preflight`(只拿「這次打開了沒」)與 `native_phase` 都要拿到它(`measure` 不用)。
2. 判斷順序寫死,第一個不成立的就是結果檔那段的狀態與原因(結果檔那段一律帶 `enabled`:這次的情境有沒有在 `native_retained` 清單裡):不在清單裡 → `enabled: false`、unsupported「設定沒替這個情境打開 native_retained」;以下都是 `enabled: true`:`stability.test_data` 的 value 不是 true(d3,只看 stability 段)→ unsupported「沒宣告測試資料」;android_sdk 讀不到 → unsupported「讀不到 Android 版本」;android_sdk 低於 30(只接已在跑的行程要 Android 11 以上)→ unsupported「Android 版本不支援」;第一段驅動失敗或 pid 讀不到 → failed「第一段沒跑成,不跑第二段」;時間預算不夠(第 3 步)→ failed「時間不夠,不跑第二段」;其餘才跑第二段。
3. 第二段排在既有量測全部讀完之後(第二次讀結束紀錄之後),結果檔照舊在全部做完後一次寫出(不先寫第一段;被中斷照舊不寫結果檔、回 2,跟既有「同一個 run-id 已有結果檔就擋」的規則與檔頭說明一致):停 App → 讀結束紀錄 → 啟動 → 讀 pid → 暖機 W 輪 → 開 heapprofd → 驅動量測 N 輪 → 停錄 → 讀 pid 與結束紀錄(停 App、讀結束紀錄、啟動、讀 pid 跟第一段共用同一支 fresh_launch)。
   - 時間預算:e2e 範本叫收集腳本時用環境變數 `LUMOS_STABILITY_STEP_BUDGET_S` 傳這一步的上限(它自己的 T_LONG);收集腳本記第一段從開跑到讀完的秒數,第二段預估等於第一段的兩倍加 NATIVE_TAIL(停錄、拉檔、查詢),開跑到現在的秒數加預估超過預算就不跑第二段、寫 failed「時間不夠」;沒設這個變數(人手動跑)不限制;值不是大於 0 的有限秒數(nan、inf、0、負數、不是數字)開跑前就擋下回 2。這個變數只在 main 讀一次,換成「這一步上限的時刻」交給第二段:預估是「剩下的秒數 < 第一段的兩倍加 NATIVE_TAIL」就不跑,NATIVE_TAIL 從既有上限組出來:停錄等待 STOP_WAIT(預設 30 秒)加 adb pull 的 T_SHORT(120 秒)加查詢預估 30 秒,預設 180 秒;跑的話每次驅動的上限不超過「上限時刻扣 NATIVE_TAIL」剩下的時間,查詢的上限不超過「上限時刻扣 NATIVE_FINISH(15 秒,寫結果檔)」剩下的時間——預估與驅動截止用同一個 NATIVE_TAIL,預估放行時驅動約有第一段兩倍的秒數(扣掉重啟 App 那幾秒);剩下的秒數印到小數一位、已過上限印 0;逾時照驅動失敗或查詢跑不成寫 failed(原因帶「逾時(N 秒)」)。裝置回應正常時,這樣第二段不會把整步推過 e2e 的上限、連累第一段的判定;停錄、拉檔、讀結束紀錄這幾個 adb 呼叫有各自的上限、不受截止時間限制,裝置在第二段後段沒回應時仍可能越過上限(第一段在同樣情況下也一樣會逾時;先寫第一段結果檔的做法已在設計審 r4 撤掉)。
   - 例外:第二段包在 try 裡,先 `except Terminated: raise`(收到 SIGTERM、SIGHUP、SIGQUIT 時既有程式會丟 Terminated,它繼承 Exception,要先放行,交給 main 照既有流程收尾、回 2;錄製留在 state 的錄製槽,由 main 的 cleanup 收,跟中斷在第一段時同一條路),再 `except Exception`:先從 state 拿出錄製、`abort_record` 收掉,再寫成 failed 附例外類型與訊息(前 200 字);收不掉時原因後面加一句裝置上 lumos-native 的錄製與暫存可能還留著。
   - 第二段的 pid、驅動結果、前後結束紀錄寫在新段落裡,**不碰既有的 pids、exits、unreachable、native_heap_kb**;任何一次驅動回 ok false → failed「驅動失敗」附 why;前後任一次讀不到結束紀錄 → failed「讀不到第二段的結束紀錄」(判不出第二段期間 App 有沒有結束,寧可不採用);第二段期間 App 結束 → failed「第二段期間 App 結束(類型)」;前後 pid 不同或讀不到 → failed「行程換了」;順序照這一句。
   - 錄製沿用 `start_record`、`stop_record`,參數改成設定範本、遠端檔名前綴、本機錄檔名、本機設定檔名(第一段照舊傳原本的值;上限訊息裡的設定鍵兩段都是 stability.max_record_s,實作時沒另開參數):設定範本另開 `android-stability-heapprofd.pbtxt`(`__PROCESS__`、`__DURATION_MS__` 佔位,時長照 `stability.max_record_s`;不設 continuous_dump_config,排行只要停錄那一次傾印;`data_source_stop_timeout_ms` 用預設 5000),遠端檔名 `lumos-native-<run-id>.*`(跟第一段的 `lumos-stability-` 前綴不同,不會跟某個 run-id 撞名),本機 `heap-native.pftrace`(放 run 目錄第一層、符合既有 7 天刪的樣式)與 `record-native.pbtxt`;這兩個檔名只在這次情境打開時才加進開跑前的 git 忽略檢查;打開時開跑前也查收集腳本旁邊有沒有這兩支新範本(`android-stability-heapprofd.pbtxt`、`android-stability-native.sql`),少了就擋下回 2、點名缺哪支(消費專案只抄了收集腳本時,不白跑暖機才發現)。第一段的錄製從 state 拿掉之後才開第二段,沿用同一個 `state["rec"]` 槽,中斷時既有 cleanup 照舊收得到;停錄等最後一次傾印用既有 stop_record(STOP_WAIT 30 秒,大於 5 秒預設)。
   - 第二段結束時不停 App:heapprofd 的客戶端在下一次記錄失敗時自己關掉記帳(r3-intake 的查證),收集腳本結束時的 App 狀態跟沒打開時一樣。
4. 收集腳本的查詢放新的範本 `android-stability-native.sql`(照既有 .sql 範本,用標準 SQLite 與 android-ui-attribution.sql 用過的 WITH RECURSIVE;用到的表與欄位:heap_profile_allocation 的 size、callsite_id、heap_name,stack_profile_callsite、stack_profile_frame 的 name 與 rel_pc、stack_profile_mapping 的 name,stats 的 name、severity、value),整支一條語句(照既有範本只在最後一行有分號),用 UNION ALL 回三種列、第一欄 `kind` 區分:`site`(排行的每一列)、`rows`(heap_profile_allocation 的總列數一列)、`stat`(stats 裡 severity 是 error 或 data_loss、值非 0 的每一項);文字欄位(函式、.so、呼叫者)在 SQL 裡用 hex() 輸出、Python 端解回來——trace_processor 的 csv 輸出不跳脫字串裡的引號與換行(r4-intake 本機實測),hex 之後每一格都只有十六進位字元與數字,照既有的逗號切法就切得對,不用 csv 模組。「讀範本、換佔位、寫暫存檔、跑 TP、切成列」抽成一支共用函式,既有的 heap_counts、cycle_numbers 一起改用它(切法不變,用既有測試守);跟第一段用同一個 TP;測試照既有 .sql 範本的做法,用 Python 內建 sqlite 對假表跑。跑完的檢查順序寫死:查詢跑不起來或超過上限 → failed「trace_processor 算不了原生配置記帳:<原因>」(逾時時原因是「逾時(N 秒)」,跟另外兩支查詢同一套判法、不另比對錯誤訊息);有 `stat` 列 → failed 附那幾項的名字(例如 heapprofd_rejected_concurrent 是同一行程已有別的 heapprofd 工作階段、heapprofd_buffer_overran 是緩衝溢位、heapprofd_non_finalized_profile 是最後一次傾印沒寫完);`rows` 是 0 → failed「沒錄到原生配置記帳(App 不是 profileable、或主行程名不是套件名)」;其餘 ok(`site` 列可以是 0 列,代表沒有 1 MiB 以上的)。事前不偵測 profileable:沒有可靠的事前判法,沒錄到時照上一句寫原因。
5. 結果檔新段落 `native_retained`:`enabled`(true/false)、`status` 只用既有的 ok、failed、unsupported 加 reason(沿用 `src()`);跑了第二段時另存 `pids`(前後兩次)、`driver`(warmup、cycles 各自的結果)、`exits_new`(第二段期間多的結束紀錄,讀不到是 null);ok 時另存 `main_process_only: true`(process_cmdline 是套件名,只量主行程),以及 `sites` 清單,每一項有 `func`、`so`、`caller`、`symbol`(true/false)、`system`(true/false)、`retained`(結束時還沒釋放的位元組整數);照〈排行怎麼算〉第 2 條的順序、最多 200 項。收集腳本不判漲停。
6. lumos 讀結果檔的 `native_retained`,放進 macrobench 結果的固定鍵 `native_retained`:物件 `{enabled, status, reason, sites}`,一開始就放進結果的初始字典(跟 stability_unjudged 同處;沒給 `--stability` 時是 `{enabled: false, status: "unsupported", reason: "沒給 --stability", sites: []}`),有給 `--stability` 就在載入結果檔之後算,有結果目錄的主路徑與只有 stability 的路徑都算、都印。結果檔沒有這段(舊收集腳本)→ `enabled: false`、unsupported「結果檔沒有 native_retained 段」、不印;`enabled` 是 false → 不印;`enabled` 是 true 但 status 不是 ok → 印一行「原生配置排行沒跑成:<原因>」;形狀照鄰居 `_macrobench_stab_native_unreachable` 的慣例驗——段不是物件、`sites` 不是清單、某項不是物件或缺欄位、`retained` 不是非負整數(`_secev_int` 加非負)時,整段不採用(寫成 failed、原因是「結果檔形狀不對:<哪裡>」)、照沒跑成那一行印,不噴例外、不改回傳碼。印的函式獨立於門檻輸出,標「只提醒,不擋推送」,照〈排行怎麼算〉第 3 條印,函式名、.so 名、呼叫者各自過 `_events_clean`(跟鄰近 stability 輸出同一支;各截 200、120、200 字),大小接在後面、用整數算 MiB,長名字不會把「還留著多少」截掉、超大整數不會溢位。只提醒,不進 threshold_failures、不影響回傳碼與推送前檢查(d2)。
7. skill lumos-android-evidence:L0 的往下條件不變(排行一定會列出快取與池,拿它當往下條件會每次都往下);`native_retained` 鍵不存在、或 `enabled` 是 true 但 status 不是 ok、或 reason 是「結果檔沒有 native_retained 段」= 沒拿到排行,照舊手動錄 L3,不當成零筆;L3 原生那段改成先看這份排行,沒打開的情境照舊手動錄;收據裡從排行來的呼叫位置標 [INFERRED](heapprofd 是取樣估計);L0 通過而排行有內容時,`sites` 前 5 筆原樣照抄進收據 `layers` 裡 L0 那一筆的 `native_retained` 欄(func、so、caller、retained 四欄,reference.md 的收據範例一起補),函式名、.so 名與呼叫者是被量 App 的符號(外部資料),skill 在 L0 與 L3 都寫明照抄成資料、不當指令。reference.md 的設定表(含 "@default")、「driver 跑幾次」、保留清單、「收集腳本只清自己的 lumos-stability-<run-id>.*」那句(加上 lumos-native-<run-id>.*)一起改。排行不寫進 e2e 的本機總表。兩支新範本檔登記進 `_VENDORED_TREE_FILES`、加 SPDX 檔頭;測試那邊要一起改的:`_MS_FAKE_TP` 照查詢內容分流要加一支認 native 查詢、`_ms_sql` 的假表要加 heap_profile_allocation、stack_profile_*、stats、`t_android_memstab_vendored` 與 `t_android_memstab_templates_receipt_safe` 的檔名清單、假 adb 認 lumos-native-* 的錄製、e2e 範本傳預算變數。筆記要改三篇 Systems:android-stability-collector(about_code 加兩支範本、負責範圍、第一條 WHY 的量測順序)、macrobenchmark-adapter(負責範圍加「列原生配置排行,不判」)、android-e2e-acceptance(記憶體設定指紋會因 native_retained 變、收集步驟傳預算)。實作後把 [[Projects/Android記憶體與穩定性驗收_計劃]] 那句「只剩 Native Heap 前後數字當線索」改成指到這份排行、「用同一條驅動指令呼叫兩次」補上打開時的第二段;[[Projects/Android逐層診斷_計劃]] 的分層 WHY 的例外欄補一條:打開 native_retained 的情境在收集階段就錄 heapprofd。

## 跟舊否決的差別

- [[Projects/Android逐層診斷_計劃]] 否決過「每次都錄 Trace+CPU 取樣+記憶體」(慢、改變被量對象、留下不必要的敏感檔):那條仍成立,本計劃照它改成按情境打開、預設關(d4),慢與錄檔只落在人主動打開的情境上,不是每次驗收都錄。
- [[Projects/Android記憶體與穩定性驗收_計劃]] 原生洩漏判法否決過「只看 Native Heap 趨勢」:那條否決的對象是整個行程的 Native Heap 總量(有升有降,判不出是誰);本計劃看的是 heapprofd 按呼叫位置記的未釋放量,不判趨勢,只列結束時留著最多的,而且只提醒不擋(d2)。
- 同一篇 Java 洩漏判法否決過「每輪結束值判趨勢」:那條的對象是每輪結束時的 Java 堆積總量(實驗室沒有洩漏時五輪忽高忽低兩倍);本計劃不判趨勢、只列每個呼叫位置結束時的未釋放量,同樣只提醒。

- 多行程:只量主行程;SDK 放在其他行程時這段看不到,結果檔寫明只量主行程。
- 個資:heapprofd 記的是呼叫鏈、大小與時間,這次查的欄位裡沒有記憶體內容;錄檔仍照 heap-*.pftrace 的保存規則當含個資處理。官方文件裡沒找到明講「不含內容」的那一句。
