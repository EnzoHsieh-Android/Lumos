# 提交推送規範_計劃

## 為什麼

2026-09-10 Enzo:「推太多雜七雜八的訊息,希望針對功能 push 就好,不用拆這麼多個,然後白話」;
「第一次 push 的時候,希望它遵循 push 慣例的訊息,不要自己亂寫」。第一個提交的寫法由 Enzo 選定 `chore: 建立專案骨架`。

查到的兩個原因:

- **提交說明的格式沒有任何規則在管**——AI 照 repo 過去的風格寫,塞滿內部代號(像「r1 設計審(四席 17 條全折)」)。
- **零碎提交是流程逼的**:代碼審的留痕綁在提交版本上,通過之後只准再提交帳本檔;凍結判定寫的
  `governance/replay/<編號>/verdict.json` 不在帳本豁免清單裡,只能推完再補一個提交。
  一個高風險功能因此至少三個提交(功能、帳本、凍結);設計審每折一輪又各自提交一次。

PRIOR-ART: 業界通行的 Conventional Commits(`<type>(<scope>): <subject>`);第一個提交沿用它的 `chore:` 類型,用中文白話寫。

設計審:跳過——內容是 Enzo 直接裁定的寫作規範;唯一的流程改動只調換步驟順序(凍結判定挪到留痕之前),
不動任何閘。可行性已查:凍結指令的前置檢查只要求卷證已提交進版控,記的是檔案內容指紋(sha256 與 git blob),不是提交編號。

## 做什麼

- [S1] 規範寫進紀律區塊範本〈提交與推送〉,消費專案的 CLAUDE.md / AGENTS.md 經 reinject 帶到 [manual:讀範本與 reinject 後的 CLAUDE.md 對照]
- [S2] 代碼審步驟 8 改成:同步檢查 → 凍結判定併進功能提交 → 留痕 → 只提交帳本(訊息固定) → 推 → 等 CI [manual:讀 lumos-code-loop 技能步驟 8]
- [S3] 設計審每輪折入後的提交是本機提交,推之前跟實作壓成同一個功能提交 [manual:讀 lumos-design-loop 技能步驟 6]

## 實務隱患

- 同一個工作目錄有別的會談時,「推之前壓成一個」若用 `git add -A` 或整包重來,會把別人的改動帶走——範本明寫只加自己的檔
  (見 [[Issues/同工作區多session並行改動]])。
- 凍結判定併進功能提交要在推之前做;已經推出去的功能不能改寫,那種情況照舊補一個提交。
- 這批只是寫作規範,沒有機械守衛:格式寫錯、夾了代號都不會被擋。
REVISIT:2026-11-10 抽查近一個月的提交標題有沒有照格式、還有沒有內部代號;還有就加推送前的格式提醒(先只提醒不擋)

## 沒做的

壓到真的只剩一個提交,要把「留痕綁提交版本」改成綁內容指紋——等於改守衛設計,要走設計審;這次不做。
