# 審查規模對照實驗

## 要檢驗什麼

宣稱：**`code-slim-python` r1/r2 的 0 findings，是因為審查員「看不完」45K token，而不是那批碼真的乾淨。**

原本的觀察資料有**兩個混淆**：

1. r1/r2 審的是 bash→Python 移植（1769 行新增），r3–r6 審的是**後來才加的 manifest 步驟**——**不同的碼**，缺陷密度本就可能不同。
2. 兩邊都是單席，所以「席數」這個變因沒有被觀察到。

## 設計

同一份材料（`py-r1.patch`，2770 行，**無 canary**——本次量的是真 finding 產出，不是注意力檢查），同一份 prompt，只變一件事：

| 組 | 席數 | 每席看到 | ≈token |
|---|---|---|---|
| **A**（既有） | 1 | 完整 2770 行 | 45K |
| **B**（新） | 3 | 各三分之一（1273／887／610 行） | 23K／13.8K／8.6K |
| **C**（新，對照） | 3 | **各完整 2770 行** | 45K ×3 |

★C 組是關鍵★：只跑 B 會變成「3 席 vs 1 席」的比較，那是在比**席數**不是比**規模**。C 把席數固定在 3，唯一差別就剩 payload 大小。

## ★預先登記的判讀規則（結果出來之前寫死）★

1. **主要結果** ＝ 去重後、經編排者裁決存活的真 finding 總數。
2. **B > C** → 支持「規模是原因」。
3. **B ≈ C** → 先前的觀察其實是**席數效應**，與規模無關；`canary-audit` 裡那條重讀要再降級。
4. **B < C** → 假說反向，查為什麼。
5. **無論結果如何都寫回 [[Systems/canary-audit]]**，不得只在支持假說時才記。

## ★結果：預先登記的主要指標「不支持」假說★

六席全數回報。逐條去重、並按「**獨立讀碼找到**」vs「**翻未來 git 歷史找到**」分類（★此分類是事後才加的，不在預先登記內，如實標明★）。

依預先登記第 3、4 條，[[Systems/canary-audit]] 裡「r1/r2 那兩個 0 是看不完」的重讀**必須降級**——已照做。

## 事後觀察（★不在預先登記內，n 極小，只能當線索★）

1. **唯一一條獨立找到的 major，出自最小的那一段（610 行）**——而且它是**還活在已交付碼裡的合約違反**（`slim/uninstall.py` 七處裸 `unlink()`／`write_text()`，一旦拋例外就炸穿 `main()`，後面步驟全不執行）。
2. **三席看完整版的，有兩席明確宣稱那條合約成立**（「exception handling properly scoped: OSError caught around **every** filesystem mutation」「四步驟互不阻擋⋯⋯經逐項核對均成立」）。那不是「漏掉」，是**有把握地講反**。
3. 所以真正的差別**可能不在「找到幾條」，而在「否定性宣稱的可信度」**——大 payload 的席次照樣產出 findings，但它們說「這裡沒問題」時比較不可信。★這是新假說，本實驗沒有設計來測它，不得當結論★。

## ★實驗設計的重大瑕疵（事後發現）★

**約半數 findings 是靠讀 repo 的未來 git 歷史找到的**（`de1f32b`／`7eae1de` 的 commit message 直接寫著答案）。有一席甚至明講「這給了我機會用『後來真的被抓到的 bug』來核實我自己的判斷」。

- **對 B vs C 的比較影響有限**：兩組都有同樣的管道。
- **對「跟原本 r1 的 0 相比」則完全無效**：r1 當時 HEAD 就是被審狀態，沒有未來答案可翻。
- **正確做法**：`git worktree add <tmp> 80ee628`，把 repo 釘在被審當下的狀態再派工。**下次要重跑必須這樣做。**

## 對已上線的軟上限（1800 行）怎麼處置

該規則的兩根支柱：① 已發表的 context rot 實測（有效脈絡 60-70%、32K 起退化）② 本專案的觀察資料。

**②已被本實驗削弱**（主要指標不支持）。①不受影響——那是外部獨立證據。

**處置：保留上限，但把理由完全改掛在①，並在規則旁明記「本專案自己的對照實驗未能在 finding 數量上重現該效果」。** 不刪除的理由是外部證據仍在、成本低；但★不得再引用本專案資料當支持★。

## 已知限制（也先登記）

- **n=1 的材料**，單一 diff、單一主題，不能外推到「所有審查」。
- **無 canary**，所以無法排除「某席根本沒認真讀」——這是為了不讓找餌消耗注意力而做的取捨。
- **findings 的真假由我裁決**，maker≠checker 在這一層沒有閉合（與 loop 本身同樣的天花板）。
- 切段依檔案界線，三段大小不均（1273／887／610），非等量對照。
