# 截圖基準驗收流程（SOP，2026-09-10）

> 白話：QA 驗收最花時間的是「這畫面跟上次核可的一樣嗎」。這套流程把「上次核可的樣子」存成一張基準圖，之後每次改動讓 Maestro 自己拍一張跟基準圖比，一樣就過、不一樣就把差異畫紅框給人看。人只在兩個時刻出手：核可基準圖、裁定差異是回歸還是預期改版。能力查證在 [[Projects/Maestro截圖基準比對_調研]]，這篇只講「怎麼做、誰做、做到哪算完」。

## 0. 一句話版本

功能做完 → 人看畫面點頭 → 跑一次「錄基準」→ 之後每次改動 agent 跑「驗收比對」→ 紅了人看 diff 圖 → 回歸就修、改版就重錄。

## 1. 範圍與前提

- **畫面級比對**，用 Maestro 原生 `assertScreenshot`。元件級快照測試（swift-snapshot-testing、Roborazzi）另案。
- **兩個專案都套**：Android 的 mOrangePos、iOS 的 PosTerminal。兩個 repo 都是單平台。
- **前置沿既有慣例**：只對「標可自動、跑測試門店／測試帳」的 flow 自動跑（見 [[Projects/Android側UI測試綁圖譜工作流_計劃]] 的實務隱患）。達不到條件的畫面只手動、終審走 `lumos code-loop skip --note` 留痕。
- **只認模擬器**。真機尺寸不同，基準圖對不上；真機驗收仍走既有「agent 開頁看一眼」慣例。
- **文字關鍵處要配 `assertVisible`**。像素比對抓得到版面位移／破圖，但抓不到小字改動（T5：加兩字→99.83%，過門檻放行）。所以有文字的畫面，flow 除了 `assertScreenshot` 還要對關鍵字串加 `assertVisible`，截圖負責「長得對不對」、assertVisible 負責「字對不對」。
- **驗收前一定要先把「待驗的那份 code」建置＋裝上模擬器**。`visual-check.sh` 是啟動裝置上「已裝的 app」，改了 code 卻沒重建重裝，會拿舊版畫面得到綠燈（假通過）。§5b 第 0 步就是這件事。
- **「人核可」「agent 不得動基準圖」目前是紀律不是機械擋**（見 frontmatter 同名 KEY 與 §8 天花板）；照做，但別把它當成已經擋住的事實。

## 3. 三支腳本（沒過前置不准跑比對）

實作已落地在兩個 repo 的 `.maestro/`（PosTerminal 是 iOS 版、mOrangePos 是 Android 版），新專案照抄再改裝置那幾行。三支的分工：

- **preflight**：確認指定裝置開著、釘狀態列、（iOS）外觀 light，印尺寸。
- **record**：前置 → 帶 `UPDATE_BASELINE=true` 跑 flow 並指定暫存產物目錄 → 把 `takeScreenshot` 的圖從產物目錄搬進 `.maestro/baseline/` → 立刻帶 `THRESHOLD=99.9` 再跑一次（連拍守衛）→ 印「開 PR 讓人看圖」。
- **check**：前置 → 跑 flow → 過退出 0；不過印一行「畫面 X 相符率 Y%，門檻 Z%，diff 在 …」退出 1；給了證據目錄就把 diff、實際、基準三張圖複製進去（是複製不是搬移，diff 仍留在基準圖旁、已被 gitignore）。**永遠不動基準圖。**

★變數一律寫 `${NAME}` 加大括號★：sh 會把緊跟在 `$NAME` 後面的中文字元吃進變數名，印出來變亂碼（今天實踩）。呼叫 maestro 的那一層要自己 export `DEVELOPER_DIR`，preflight 是子行程，它的 export 傳不回來（今天實踩，症狀是「device not connected」）。

**iOS 前置的核心指令**：

    #!/bin/sh
    set -e
    UDID="${MAESTRO_UDID:-EA712A4B-...}"   # ★實裝是「有預設值」不是「強制設定」★:換機忘了設 MAESTRO_UDID 不會叫你設,而是報「裝置 …沒開」,第一次接手先看 README(r1 f19)
    export DEVELOPER_DIR="${DEVELOPER_DIR:-/Applications/Xcode.app/Contents/Developer}"
    xcrun simctl list devices booted | grep -q "$UDID" || { echo "裝置 $UDID 沒開"; exit 1; }
    xcrun simctl status_bar "$UDID" override --time 12:30 --batteryState charged --batteryLevel 100 --wifiBars 3 --cellularBars 4
    xcrun simctl ui "$UDID" appearance light
    echo "appearance=$(xcrun simctl ui "$UDID" appearance)"
    xcrun simctl status_bar "$UDID" list

**Android 前置的核心指令**：

    #!/bin/sh
    set -e
    DEV="${MAESTRO_DEVICE:-emulator-5554}"
    ADB="${ANDROID_HOME:-$HOME/Library/Android/sdk}/platform-tools/adb"
    [ "$($ADB -s "$DEV" shell getprop sys.boot_completed | tr -d '\r')" = "1" ] || { echo "裝置 $DEV 沒開完"; exit 1; }
    $ADB -s "$DEV" shell settings put global sysui_demo_allowed 1
    $ADB -s "$DEV" shell am broadcast -a com.android.systemui.demo -e command enter
    $ADB -s "$DEV" shell am broadcast -a com.android.systemui.demo -e command clock -e hhmm 1200
    $ADB -s "$DEV" shell am broadcast -a com.android.systemui.demo -e command battery -e level 100 -e plugged false
    $ADB -s "$DEV" shell am broadcast -a com.android.systemui.demo -e command network -e wifi show -e level 4
    $ADB -s "$DEV" shell wm size

跑完比對後 Android 記得離開 demo mode：

    adb -s "$DEV" shell am broadcast -a com.android.systemui.demo -e command exit

**方向是機械釘的，不要跟下面混。** 方向在 flow 裡用 `setOrientation` 釘（見 §4），不是環境設定——建新畫面別漏了它，平板一漏就整批 94.7% 翻紅（mOrangePos 首錄實踩）。

**真正釘不住、只能寫進 `.maestro/README.md` 的只有兩樣：語系、字級**（iOS 的 `simctl ui content_size`、Android 的 `font_scale` 今天沒實測能不能釘），先由人設定一次、README 記下來。基準圖檔名不帶裝置代號，因為 README 已釘死機型。

**環境漂移要防**（r1 f16）：preflight 現在會印出實際 runtime 版本（iOS 的 iOS 26.x／Android 的 release），換 Xcode 或系統映像後對照 README 記的版本；OS／字型渲染引擎升級會讓整批基準圖無聲對不上。REVISIT:2026-11-10 累積一次 Xcode 或 Android 系統映像升級後，回頭量一次同畫面重拍相符率有沒有掉出 99.5。

**並發要擋**（r1 f17）：check／record 開跑會用 `.maestro/.lock-<裝置>` 搶鎖，同一台裝置一次只准一個在跑，拿不到鎖就報原因退出。★執行期間裝置不能被別的流程碰★——包括人手動點、另一個 agent、以及 mOrangePos 那支「偵測到 build 就自動重裝重啟 app」的 hook，被打斷會產生跟版面無關的假紅。

**三支腳本是逐 repo 複製的**（r1 f12）：兩個 repo 各一份 `visual-*.sh`，沒有共用套件自動同步——因為它們是兩個獨立 repo、裝置層本來就不同，硬做共用套件成本高於收益。單一真相源是本篇 SOP；範本改了要手動回填各 repo。REVISIT:出現第三個消費 repo 時重新評估要不要抽共用。

## 4. flow 範本與門檻規則

    appId: com.example.app          # Android 是 package，iOS 是 bundle id
    name: menu_main_visual          # 圖譜綁定用，識別字、不含空白
    ---
    - launchApp
    - setOrientation: LANDSCAPE_LEFT   # iPad 橫向；★Android 平板寫 PORTRAIT★（自然方向就是橫向）
    - waitForAnimationToEnd
    - evalScript: "${output.th = (typeof THRESHOLD === 'undefined' || THRESHOLD === '') ? 99.5 : Number(THRESHOLD)}"
    - runFlow:
        when:
          true: ${UPDATE_BASELINE == 'true'}
        commands:
          - takeScreenshot: ./baseline/menu_main
    - runFlow:
        when:
          true: ${UPDATE_BASELINE != 'true'}
        commands:
          - assertScreenshot:
              path: ./baseline/menu_main.png
              thresholdPercentage: ${output.th}

- **檔頭不放 `env:` 預設值。** 2.6.1 實測檔頭預設會蓋掉命令列的 `-e`；變數沒定義時判斷就是 false，正好是「預設驗收、加旗標才更新」。
- **要切到元件就兩邊都加同一個 `cropOn`**（拍與比都要），否則尺寸不合直接失敗。
- **門檻固定 99.5。** 三個實測的「已知改版」相符率 96.2、98.3、97.6 都遠低於它，「同畫面重拍」100、99.986、100 都高於它。Maestro 預設的 95 三個案例全部放行，不能用。★但 iPad 菜單同畫面重拍只有 99.913（T5）★，所以 99.5 到「同畫面」之間的安全邊際在 iPad 上只有約 0.4 個百分點，不是三四個——連拍守衛設 99.9 是貼著邊的（設 99.99 會誤殺自己）。門檻底線已寫進 check 腳本：`THRESHOLD` 低於 99.5 直接拒收（r1 f5）。
- **這套只驗淺色。** preflight 把 iOS 釘在 light 外觀，深色模式限定的視覺回歸會 100% 放行且不會有人被提醒（r1 f13）。要驗深色得另錄一張深色基準、另開一支 flow，本版沒做。
- **畫面有會動的東西（時鐘、單號、頭像、隨機排序）→ 釘資料、釘狀態列或 cropOn。不准降門檻。** 降門檻等於把「沒在驗」寫成綠燈。
- 錄完基準，record 腳本立刻帶 `THRESHOLD=99.9` 再比一次（連拍守衛）；★沒過腳本會自動還原舊基準、不留壞檔★（r1 f11）。沒過通常是畫面上有會動的東西→去釘資料或 cropOn；但因為 iPad 同畫面本來就貼著 99.9（見上），偶爾可能只是渲染雜訊，先重跑一次再下結論。人另外打開基準圖看一眼。
- 2.10.0 重驗（2026-09-10）：diff 圖已在基準圖旁、門檻吃變數、缺基準圖仍不自動建、檔頭 env 仍蓋掉 -e；★新差異是 takeScreenshot 改寫進產物目錄★，record 腳本已對應。

## 5. 三段執行

### 5a. 錄基準（人）

0. **新畫面第一次**：從 §4 範本複製一份 `.maestro/<畫面>.yaml`（檔名＝`name:`，改 `appId`、`name:`、兩處 `./baseline/<畫面>`、加 `tags: [visual]`）。`visual-record.sh` 沒有 flow 檔會直接失敗，所以這步在錄基準之前，由功能開發者做（不是驗收 agent）。
1. 功能做完、單元測試綠。
2. 人在指定模擬器上看畫面，點頭。
3. 跑錄基準腳本（會自己做前置、拍圖、搬進 repo、連拍守衛）：

        .maestro/visual-record.sh menu_main

4. 腳本最後一行印「基準圖已更新…連拍守衛 99.9 通過」才算錄好。
5. 基準圖＋flow 一起開 PR。審的人**看圖**再 merge。基準圖就是驗收紀錄。

### 5b. 驗收比對（agent 或 CI）

0. **先確認模擬器上裝的是「待驗的那份 code」**：改了 code 就要先 build＋install 再驗，否則 check 拿舊版畫面會假通過（r1 f6）。這一步腳本擋不了，是操作紀律。
1. 跑驗收腳本，證據目錄給既有的卷證位置：

        .maestro/visual-check.sh menu_main_visual governance/review-reports/<loop-id>/ui-evidence

2. 前置沒過腳本會退出 1 並說原因；回報「環境未就緒＋原因」，不得靜默跳過。
3. 退出 0：這支 flow 的畫面跟基準相符。★這只是「這一個畫面沒變」的證據，不是整份終審★——終審 `lumos code-loop pass --note` 要蓋的是所有相關畫面＋既有測試，別拿一支綠 check 當全部過關。
4. 退出 1：腳本印一行「畫面 <名> 相符率 <X>%，門檻 99.5%，diff 在 <路徑>」，照抄回報。**agent 不得自行更新基準圖。**

### 5c. 裁定（人）

- **先分兩種退出 1**：①有相符率、有 diff 圖＝真的比出不一樣，往下走裁定；②沒有相符率（腳本印「比對沒跑到」）＝flow 在跑到 assertScreenshot 之前就掛了（元素找不到、app 沒起來、被並發打斷），這種沒有 diff 圖，不要當視覺回歸裁，先查環境／flow 本身。
- 看 diff 圖的紅框。**回歸** → 修 code，回 5b。**預期改版** → 回 5a 重錄，PR 裡新舊圖並列給審的人。
- 裁定寫進該功能節點的驗證筆記（相符率、門檻、基準圖路徑、裁定）。

## 6. 綁圖譜與慣例接線

- flow 的 `name:` 綁到功能節點的條款。★分兩種★：
  - 條款是合約行(不變量級) → `lumos guard bind <節點> "<條款子字串>" menu_main_visual --platform maestro`。
  - 條款是一般 KEY（版面這種非合約）→ 在該 KEY 行手標 `[test:maestro:menu_main_visual]`。`guard bind` 只綁星標合約行，綁非合約行會被擋（天花板 ⑥）。兩個 repo 的首支 flow 都是這一種，都用手標。
- **flow 檔名要＝`name:` 欄位**（r1 f21）：既有九支 smoke flow 全是「檔名去副檔名＝name」，visual flow 也照這規矩（`menu_main_visual.yaml` 的 `name:` 就是 `menu_main_visual`），別讓同目錄有第二套命名法。

- 驗證筆記寫：基準圖路徑、相符率、門檻、裁定。
- [[Systems/pitfalls-code-loop]] 的 UI 層驗收慣例加一句：有基準圖的畫面，終審跑 flow；沒有的照舊開頁看。
- skill `lumos-project-notes` 的〈產 maestro UI flow 的派工要求〉加一小節「有基準圖的畫面」指回本篇。

## 7. 失敗時怎麼讀 diff 圖

- 紅框是「不同像素聚成的區塊」，線寬 10、最小框 40 像素；一個紅框不等於一個改動，一段文字可能拆成好幾框。
- iOS 模擬器截圖是直立畫格，橫向 app 的 diff 圖是躺的，轉 90 度再看。
- 相符率是像素比例：「差一個字」跟「差一整塊留白」權重一樣，所以要看紅框在哪，不要只看數字。

## 8. 天花板與回頭條件

- 版面一改就要重錄，重錄一定走 PR。
- 沒有遮罩。動態區只有 cropOn 或釘資料兩條路。**cropOn 只保裁切框內**——只裁一個穩定元件，框外整片版面的回歸就漏掉了，SOP 仍記成畫面級 pass。要裁就把「只驗這一塊」寫進裁定，框外重要區域另外安排驗收（r1 f20）。
- **小字改動會躲過門檻**（T5：2 字→99.83%）。文字關鍵處靠 `assertVisible` 補（§1），不是靠截圖比對。
- **強項結論的樣本有限**：「抓得到版面位移」只用一次 160pt 大位移驗過；顏色微調、單一圖示替換、幾 px 的小位移都沒測過，可能跟小字改動同屬盲點，別過度宣稱（r1 f14）。
- **只驗淺色**：深色模式限定的回歸 100% 放行（r1 f13，見 §4）。
- **「人核可、agent 不動基準、PR 看圖」目前是紀律不是機械擋**（見 frontmatter「機械擋到哪」KEY）；已加的機械擋只有 check 底線、record 還原、裝置鎖三道。
- **驗收前要先建置＋裝上待驗 code**（§5b 第 0 步），這步腳本擋不了，靠紀律（r1 f6）。
- 真機不在範圍。
- CI 接法另案；v1 由 agent 本機跑。
