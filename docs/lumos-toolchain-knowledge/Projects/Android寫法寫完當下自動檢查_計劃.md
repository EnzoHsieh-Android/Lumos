# Android寫法寫完當下自動檢查_計劃

> 白話:[[Projects/Android協程與API寫法機械檢查標準_計劃]] 做出型錄與規則包(第一批)之後,這份計劃把機械檢查接進代碼審查迴圈:代碼審要記「通過」之前,先跑新增告警與表態兩道機械檢查,不乾淨不准記;另給一支指令 `lumos lint-new --diff` 讓審查前自己先查。使用者原話(2026-11-05):「我會希望是 code review 的 loop 中就檢查乾淨,不用等到推送」「最好是自動化檢查,不需要我記得敲什麼指令才去盤點」。原本這份還有「回合結束自動檢查」與「改檔前推相關列」兩個機制,兩輪設計審累計折入 80 多條、問題集中在那兩塊,2026-11-06 第二輪後照熔斷提示拆到 [[Projects/Android寫法回合結束檢查與改檔前推列_計劃]],本份只留代碼審這段。

PRIOR-ART: ①「審查前先讓機器查乾淨」:Google 的程式碼審查把靜態分析結果在送審前就貼到變更上(Tricorder,Sadowski 等 2018,CACM「Lessons from building static analysis tools at Google」),人只看機器抓不到的;GitHub 的必過檢查(required status checks)也是合併前先跑。採用:在 lumos 自己的「記通過」那一步前跑既有的兩道判定。②不另寫判定:推送檢查已有「每道都判完」的收集模式(`_codeloop_guard_verdict` 的 `keep_going`),本案加一個只跑其中兩道的選項,判法跟推送前閘逐字相同。③被擋留帳:沿用推送閘既有的 `_gate_event_or_warn`(放行記 fail-open 的同一支),讓撤除條件數得到。
RETIRE-IF: `code-loop pass` 被這兩道擋下的治理帳事件連續三個月零筆,而推送前閘同期照樣擋過新增告警或表態 → 查是不是漏接;仍零筆就拿掉這一步,回到只靠推送前閘。

## 用詞

- **告警身分(指紋)**:新增告警閘替每條告警算的身分字串(規則、檔、去掉行號後的內容),放行紀錄也用它。新增告警閘本體的說明在 [[Systems/pitfalls-code-loop]]。
- **兩道機械檢查**:推送前 `code-loop check` 六道判定裡的「新增告警」與「表態」兩道([[Systems/棧別提問表態閘]]);不含安全證據、合約測試、端到端驗收與代碼審留痕。
- 型錄、規則包、接電方式、表態的定義見母計劃〈用詞〉。

## 範圍

1. **新增告警指令** `lumos lint-new --diff <範圍> [--repo <根>]`(新增):
   - 跟推送前閘的新增告警那道完全同判(呼叫同一支判定函式、同一份設定讀法、預算不夠沒跑到的命令照既有規則算擋)。`--diff` 沒給 → rc2 印用法;給單一版本時照判定函式既有規則走環境不可用(rc3),訊息提醒要給兩端。`--repo` 沒給時用目前目錄往上找 git 根(跟 `code-loop check` 同一個找法)。
   - 退出碼照判定函式既有的八種狀態分三類:**擋**(blocked)rc1,每條印「檔:行、規則訊息、放行用的指紋」,最多印 20 條、其餘印條數;**乾淨或刻意不查**(clean、warn、off、no-config、no-files)rc0,每種各印一句講明是哪一種(warn 照印新增告警但註明「設定成只報告」);**沒檢查到**(not-checked、env-unavailable)rc3,印哪條命令沒跑、為什麼(第一個詞找不到執行檔就明說「沒裝 <工具>」),結尾一句「這次沒有被檢查,不算乾淨」。rc3 在 lumos 其他指令另有「找不到知識圖譜」的意思,這支指令的說明與輸出結尾寫明它在這裡的意思。
   - 這支指令不寫治理帳(放行帳只有推送前閘記)。
2. **代碼審通過前先跑機械檢查**:不另寫共用函式,沿用推送檢查既有的「每道都判完」收集模式(`_codeloop_guard_verdict` 的 `keep_going` 路徑),多一個選項「只跑新增告警與表態兩道」(不含合約測試、安全證據、端到端驗收與代碼審留痕——帶進留痕那道會讓 pass 自己擋自己)。`lumos code-loop pass` 在進留痕驗證(它有「沒有審查帳就回沒東西可驗」與 light 兩條提早返回)之前就呼叫它,範圍跟 `code-loop check` 不帶 `--diff` 時相同。分岔點算不出來時照 check 既有規則放行並記一筆放行帳;分岔點等於 HEAD(沒有改動)時照 check 既有規則直接放行、不記帳。兩道的判法跟推送前閘完全相同(環境不可用照既有規則自動放行並記帳)。任一道擋下就不寫留痕、照 pass 既有被擋的退出碼(rc2)、印擋下原因與修法,並用 `_gate_event_or_warn(根, "code-loop-pass", "block", 原因)` 寫一筆治理帳(撤除條件數這個)。`code-loop skip` 不受影響。
3. **代碼審手冊**:lumos-code-loop 手冊在「派審查席」之前加一步「跑 `lumos lint-new --diff <分岔點>..HEAD`,rc0 才派;rc3 代表沒檢查到,不是乾淨,要先裝好工具或在派工詞寫明哪些類別沒被機械檢查」。審查席派工材料附機械檢查結果,寫明「機械已查(rc0 且是 clean)的類別席位不報」。手冊這條只是建議人怎麼做;機器擋的是範圍 2 的 pass 與推送前閘。

**不做**:推送前閘的判定結果不變(範圍 2 加選項是行為不變的擴充,既有測試釘住);不在推送前閘呼叫模型;回合結束自動檢查、工作樹檢查、改檔前推列、自動執行白名單拆到 [[Projects/Android寫法回合結束檢查與改檔前推列_計劃]];表態對程式與盲判在第三批([[Projects/Android寫法語意情境表態與盲判_計劃]])。

## 實務隱患

- **代碼審通過變嚴**:範圍是整條分支,分支裡較早帶進、沒放行的新增告警會在 pass 被擋;出口是放行並寫理由(同推送前閘)。
- **pass 變慢**:pass 從幾乎瞬間變成要跑 pitfalls、表態判定與新增告警(新增告警照既有預算);這是把推送前會付的時間提早到記通過前,推送時同一份判定還會再跑一次。
- **跟 detekt 那案、第三批改同一區**:[[Projects/Android的detekt推送前真的擋_計劃]] 已合併(新增告警閘的佔位符替換);[[Projects/Android寫法語意情境表態與盲判_計劃]] 在表態判定裡加情境題,本案只呼叫表態判定、不改它,後合的那個要重跑相關測試。
- **舊否決對照(2026-11-05 跑 `lumos rejections` 按概念比對)**:新增告警閘出錯就放行(本案沿用);[[Systems/pitfalls-code-loop]] 記的「閘放在 pass 不放 check,因為 check 不知道分支對應哪個迴圈」與不選「pass 內重跑處置閘」——本案在 pass 加的是不依賴迴圈編號的兩道,沒有碰到那條否決。
- 資安:不新增自動執行命令的地方;pass 跑的命令跟推送前閘完全相同。
- 已排除:金流:不碰付款或點數
- 已排除:對外送出:檢查只在本機跑,不送資料出去
- 已排除:不可逆:新增指令與選項,退提交即回原狀;治理帳只追加
- 守衛面:改代碼審通過條件,屬守衛面,走完整設計審(不寫成已排除)

## 驗收條款

- [S1] 當 `lumos lint-new --diff <範圍>` 跑在推送前閘判過的同一範圍時,狀態 應 跟推送前閘相同;八種狀態 應 各對到擋 rc1、乾淨或刻意不查 rc0、沒檢查到 rc3;沒給 `--diff` 應 rc2;只給一個版本 應 rc3 並提醒給兩端;沒裝工具時 應 rc3 並印「沒裝 <工具>」;給 `--repo` 指到另一個 repo 時 應 判那個 repo [test:t_lint_new_cli_status_codes]
- [S2] 當 `lumos code-loop pass` 從主線分岔點到 HEAD 有未放行的新增告警或表態不完整時,應 不寫留痕、照既有被擋退出碼、印擋下原因,並在治理帳留一筆 `code-loop-pass` 的擋下事件;pitfalls 出錯時新增告警那道 應 照跑;帳上沒有審查紀錄或走 light 時 應 照樣先跑這兩道;工具沒裝時 應 照推送前閘自動放行並記帳;分岔點等於 HEAD 時 應 直接放行不記帳;兩道都乾淨時 應 照舊寫留痕;`code-loop skip` 應 不受影響;推送檢查與 pass 應 走同一個收集模式 [test:t_codeloop_pass_requires_clean_mechanical]

## 回退

退回本案的提交:`lint-new` 指令消失;`code-loop pass` 回到不先跑機械檢查;治理帳裡已寫的 `code-loop-pass` 擋下事件留著(追加帳,讀側不認得的會略過)。

## 天花板

2. AI 寫完到記通過之間的自動檢查拆到另一份計劃。
