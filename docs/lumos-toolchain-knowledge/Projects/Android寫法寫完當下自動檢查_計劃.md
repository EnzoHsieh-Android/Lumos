# Android寫法寫完當下自動檢查_計劃

> 白話:[[Projects/Android協程與API寫法機械檢查標準_計劃]] 做出型錄與規則包(第一批)之後,這份計劃把檢查接到「AI 寫完當下」與「代碼審查迴圈」:回合結束自動跑工作樹檢查、改檔前推型錄的相關列、代碼審通過前先跑機械檢查,讓使用者不用記指令、推送只是最後確認。2026-11-05 從那份計劃拆出:那份第二輪設計審四席報了 43 條,其中 36 條整條、另 2 條的一部分落在這幾個新機制(暫時索引、鉤子預算、逐字稿列舉寫過的檔、改檔前推列的比對與標記),照審查的熔斷提示(累計折入超過 20 條建議拆小)拆開,讓第一批先過審實作。使用者原話見母計劃的白話段。

## 狀態

初稿(2026-11-05 拆出時的版本)。下面〈範圍(初稿)〉是母計劃第二輪設計審時的原文(只改了編號),**照字面實作會踩到〈開審前必須先解〉列的問題**;開這份的設計審之前,先把每一組解掉並寫進範圍,再跑 `lumos spec-gate`。前置:母計劃第一批與 [[Projects/Android的detekt推送前真的擋_計劃]] 已合進主線。

## 用詞

- **告警身分(指紋)**:新增告警閘替每條告警算的身分字串(規則、檔、去掉行號後的內容),用來判斷「同一條告警」;放行紀錄也是用它。「同一批告警」= 這次工作樹檢查新增告警的指紋多重集合(同一指紋出現幾次也算),排序後取雜湊。
- **工作樹檢查**:對「還沒提交的改動」跑新增告警比對——基準是 HEAD 那一版、現在版直接讀工作樹的檔。既有新增告警閘只比兩個提交(終點解不出來時判成環境不可用),本案多一個明示的「工作樹」終點。新增告警閘本體的說明在 [[Systems/pitfalls-code-loop]](設定、關閉方式寫在那篇)。
- 型錄、規則包、接電方式、表態、盲判席的定義見母計劃〈用詞〉。

## 範圍(初稿)

1. **新增告警指令**:`lumos lint-new`(新增)兩種用法:`--diff <範圍>` 對提交範圍跑既有的新增告警判定;`--worktree [--only <檔>…]` 跑工作樹檢查。兩種都加 `--budget 秒`。有新增告警 rc1,每條印「檔:行、規則訊息、放行用的指紋」;沒有 rc0;環境不可用(工具沒裝、跑不出結果)rc0 並印哪條命令沒跑、為什麼(第一個詞找不到執行檔就明說「沒裝 <工具>」);全部命令都沒跑到時印「沒有檢查到任何東西,不算乾淨」,不印「沒有新增的告警」。這支指令不寫治理帳(放行帳只有推送前閘記,避免每回合灌一筆)。
2. **工作樹檢查**:判定函式多收一個明示參數「終點是工作樹」(不沿用「終點解不出來」那條路,那條照舊判環境不可用);基準取 HEAD,現在版讀工作樹。改動清單用暫時索引算:複製目前索引到暫時檔、在暫時索引上 `git add -A`、`git diff --cached --find-renames HEAD`,真正的索引不動(git 自己的 stash 也用暫時索引;2026-11-05 實驗:未追蹤的改名 `mv Foo.kt Bar.kt` 配得到 R100,真索引仍是 D 加 ??)。合併衝突中的檔(狀態 U)不掃,列成「衝突中、沒檢查」。路徑在 `.lumos/` 底下的一律不掃(新增告警閘自己的快照暫存放在那裡,消費專案不一定忽略它)。`--only` 給了就只看那幾支。時間預算不夠而沒跑到的命令,工作樹檢查只列出、不算擋,但工作樹模式的單條保底降成 1 秒(既有保底 30 秒是給推送前跑 detekt 這種慢工具的,照用會讓 20 秒內的檢查一條都不跑)。
3. **回合結束自動檢查**:收工點名那支回合結束鉤子(Claude 與 Codex 共用同一支)多一道「寫法檢查」,跟既有「改 code 沒動圖譜」那道並列、各自判,插在既有那道的所有提早離開(找不到圖譜、動過筆記、同批檔已講過)之前,所以沒有圖譜的專案、這輪也動了筆記的情況照樣跑。條件:專案根有 `.lumos/lint.json`;這一輪逐字稿裡有寫檔動作;payload 沒有 `stop_hook_active`;`LUMOS_STOP_LINT_OFF`(新增)沒設。檢查範圍只限這一輪逐字稿裡寫過的程式碼檔(`--only`),不碰同一工作目錄別的會談的改動。時間:不另加設定鍵,從鉤子既有的內層預算(外層天花板乘 0.7 扣掉已用)切一半給這道、上限 15 秒,另一半留給既有那道;鉤子天花板只有註冊表一個來源。有新增告警就回 decision:block,原因寫「這幾條新增告警要先修」加每條「檔:行、規則訊息、放行指紋」,結尾一行教放行指令。防無限擋:同一會談同一批告警(這一批告警指紋的多重集合——同一指紋出現幾次也算進去——排序後的雜湊)只擋一次,之後只提醒;一個會談這道最多擋三次,之後只提醒;名額標記放既有擋停名額的同一個目錄、過同一個信任檢查。兩道都要擋時把兩段原因合成一則 decision:block,各自的名額各自記。
4. **改檔前推相關列**:比對在 lumos 本體做,鉤子只印(跟既有棧別題同一個分工)。鉤子把寫入內容交給 `lumos impact --file <檔> --delta-stdin`(新增旗標),lumos 回傳命中的決策表列,鉤子把它們接在既有輸出後面;既有輸出是空的時候單獨輸出。比對規則:只看寫入的新內容(Edit 的新字串、Write 的全文),去掉註解與字串字面值;觸發字整詞比對、分大小寫;決策表的觸發字分「強」(專有 API 名,如 `flatMapLatest`、`supervisorScope`)與「弱」(`map`、`try` 這類常用字),一列要有一個強字或兩個不同的弱字才算命中;命中多列時照命中字數多寡、再照表序取前三列;只有真的印出的那幾列才記「同會談講過」(用既有的同會談只講一次標記,鍵是列編號)。型錄由 lumos 從自己的安裝位置找。只做 `.kt`、`.kts`。Codex 的改檔工具拿不到寫入內容,這一版不推。
5. **代碼審通過前先跑機械檢查**:把推送檢查裡「新增告警」與「表態」兩段抽成一支共用函式,推送檢查與 `lumos code-loop pass` 都呼叫它(不另寫判定)。`pass` 的範圍跟 `code-loop check` 不帶 `--diff` 時的預設範圍相同(跟主線的分岔點到 HEAD);這比推送前只看「遠端已有到這次」的範圍寬,分支裡更早的提交若帶未放行的新增告警,`pass` 會擋,出口是 `lumos lint-waive`。任一道擋下就不寫留痕、rc1,印擋下原因與修法。`code-loop skip` 不受影響;現在 pass 與 skip 走同一段程式,檢查只加在 pass 那一支。
6. **代碼審手冊**:lumos-code-loop 手冊在「派審查席」之前加一步「跑 `lumos lint-new --diff <分岔點>..HEAD`,乾淨才派」(手冊要求凍結前先提交,所以用提交範圍,不用工作樹);不用 `lumos code-loop check`,因為 tier high 在派席之前必然因為還沒有審查留痕而擋,看不出機械那幾道乾不乾淨。審查席的派工材料附機械檢查結果,寫明「機械已查的類別席位不報」。表態時機照手冊既有寫法(派審查員之前做)。

**不做**:不改推送前閘本身的判定;不在推送前閘或回合結束鉤子裡呼叫模型;表態對程式與盲判席在第三批。

## 開審前必須先解

來源:母計劃第二輪設計審卷證 governance/review-reports/android協程與api寫法機械檢查標準/ 的四份 r2 席報告(編號:正=正確性席、邊=邊界席、資=資源席、架=架構對齊席),依根因分組。每組寫「照字面會出什麼錯」與重寫方向;方向只是候選,開審前要先查世界。

1. **暫時索引加整樹 `git add -A` 這個做法本身**(正1、邊1、正6、資F2、邊2、正12、邊16、邊14):衝突檔被 add 成第 0 階、狀態 U 消失,衝突標記被拿去掃;整樹 add 不受 `--only` 與預算約束,大的未追蹤檔會花數秒並把物件寫進真的物件庫;一個不可讀檔讓 add 整個失敗;linked worktree 的索引位置不是 `.git/index`;零提交的 repo 沒有 HEAD;超過 1000 支改名或相似度不到一半的改名退成刪加新增。方向:不 add,改讀真索引的 `git status --porcelain=v2 -z`(不算雜湊)加 `git ls-files -u` 判衝突,改名配對只對 `--only` 那幾支做;零提交的 repo 明定行為。
2. **「這一輪寫過的檔」怎麼算**(正2、邊3、正3、邊4、正4、正15、邊5):只寫了筆記那一輪 `--only` 是空的,會變成掃整個工作樹;逐字稿列舉漏掉 shell 寫的檔(圖譜 [[Systems/graph-sync-coverage]] 記過 286 次走 shell 對 31 次走編輯工具,收工點名因此改問版本控制);切進 linked worktree 的會談路徑全被濾掉;同一輪先寫後提交,工作樹檢查看不到。方向:空清單整道不跑;範圍改成「這輪逐字稿提到的檔 ∪ 版本控制看得到的、這個會談開始後才改的檔」或明講代價;worktree 照改檔前推播的 `_sibling_worktree_root` 解;先提交的情況交給代碼審通過與推送前閘並寫進天花板。
3. **時間預算與子程序**(資F1、資F3、資F5、正5、資F4、邊19):鉤子逾時只殺得到 lumos、殺不到它開的掃描子程序與暫存;`--budget` 起算點在抽檔之後;切一半的公式讓既有那道只剩 13 秒;慢命令(detekt)排前面時快命令(ast-grep)一條都跑不到;沒有圖譜的專案也要整份讀逐字稿(實測 406MB 逐字稿常駐記憶體約 4GB);檔太多時命令列過長。方向:鉤子用程序群組殺整棵;預算從指令開頭起算;工作樹模式只跑宣告裡標了「快」的命令或照預估耗時排序;逐字稿改成從尾端只讀這一輪。
4. **擋停的語意**(邊12、邊13、正7、邊11、邊15、正14):專案設 `lint_new.gate` 為 warn 或 off 時鉤子仍擋;`lint-new` 的輸出沒涵蓋 off、沒宣告、沒檔、warn、沒檢查;「乾淨」跟「沒檢查」(工具沒裝)rc 都是 0,代碼審手冊會把沒檢查當乾淨、還叫席位別報;「只提醒」在 exit 0 時模型看不到;擋停原因沒有條數與字數上限(既有限 1500 字)。方向:`lint-new` 照判定函式既有的 8 種狀態各定 rc 與輸出,沒檢查跟乾淨分開;鉤子只在判定說「擋」時擋。
5. **改檔前推列**(架a、邊9、資F6、正8、正9、正10、正11、邊10、邊8 後半):`--delta-stdin` 跟既有 `--stdin-payload` 重複,應在既有 payload 加鍵、同一次呼叫;已講過的列要由 lumos 在取前三之前排除,否則沒印出的列永遠推不出來;現成的剝字串函式是 Python 形的、會吞掉 Kotlin 真程式碼;既有 `extract_delta_text` 含 Edit 的舊字串;「Codex 拿不到寫入內容」不成立(apply_patch 帶 patch 全文),改寫成「這版不做」;同會談標記是先標後講、並行兩個改檔會重推;型錄〈情境決策表〉要加強弱觸發字欄。
6. **代碼審通過前先查**(正13):共用函式若沿用推送檢查的非 keep-going 路徑,pitfalls 一出錯新增告警那段就不跑。
7. **資安**(邊20):回合結束鉤子會在每次收工自動執行打開資料夾裡 `.lumos/lint.json` 宣告的命令,跟同一支鉤子「被打開的資料夾不准指使我們執行指令」的先例相反;要在威脅模型下明確裁一次。

## 實務隱患(初稿)

- **回合結束檢查拖慢每一輪**:只掃這一輪寫過的檔;時間從鉤子既有內層預算切一半、上限 15 秒;ast-grep 對幾支檔是毫秒級;detekt 這類慢工具也在同一份宣告裡時被預算截斷,截斷的命令只列出不擋(推送前閘會再跑完整的)。鉤子被平台強制結束時,新增告警閘的快照暫存照既有規則一天後清;因為工作樹檢查不掃 `.lumos/` 底下,殘留不會被當成新檔。
- **擋停迴圈**:同一批只擋一次、續做那輪不擋、一個會談最多擋三次,推送前閘照擋,逃生門是放行並寫理由。續做那輪新加的告警要到下一次收工才查,推送前閘兜底。
- **共用工作目錄**:回合結束檢查只看這一輪逐字稿寫過的檔,別的會談的未提交改動不算進來;`lint-new --worktree` 不帶 `--only` 時看整個工作樹,輸出每條都帶檔名,人看得出是誰的。
- **改檔前推列太吵**:強字/弱字門檻、最多三列、同列同會談只推一次。
- **代碼審通過變嚴**:通過時先擋的就是推送前會擋的那兩道,但範圍是整條分支(推送前只看這次推的增量),分支裡較早帶進、沒放行的新增告警會在 pass 被擋;出口是放行。沒有 `.lumos/lint.json` 的專案新增告警那道本來就放行;表態那道不看宣告、看改動有沒有碰到棧別題,照它在推送前的規則判。
- **跟 detekt 那案改同一道閘**:[[Projects/Android的detekt推送前真的擋_計劃]] 也改新增告警閘(逗號佔位符與探針)。那案先做;本案的工作樹終點在那案合進主線後再接,工作樹檢查對逗號佔位符命令照那案的規則加探針。
- **資安**:回合結束鉤子會自動執行 `.lumos/lint.json` 裡宣告的命令(原本只有推送前與手動冒煙會跑);依本工具單人、AI 依序操作的威脅模型,宣告檔是專案自己進版控的,不另防。

## 驗收條款(初稿,開審前會依上面重寫)

- [S1] 當工作樹有未提交的 kt 改動時,`lumos lint-new --worktree` 應 對新增一條規則包告警 rc1 並印檔:行、訊息、指紋;只動到 HEAD 已有告警所在檔但沒新增 應 rc0;未追蹤的新 kt 檔裡的告警 應 算新增;`mv` 改名(未 add)的檔裡原有的告警 應 不算新增;合併衝突中的檔 應 列成沒檢查;`.lumos/` 底下的檔 應 不掃;所有命令都因預算沒跑到時 應 印「不算乾淨」且 rc0;`--diff <範圍>` 應 跟推送前閘對同一範圍的判定一致 [test:t_lint_new_worktree]
- [S2] 當回合結束鉤子遇到專案有宣告、這一輪寫過的 kt 檔有新增告警時,應 回 decision:block 且原因含檔:行與規則訊息;專案沒有圖譜或這一輪也動了筆記時 應 照樣檢查;別的檔(這一輪沒寫過)的告警 應 不算;同一批第二次 應 只提醒,同一指紋多出一處 應 算新的一批再擋;一個會談第四次 應 只提醒;payload 帶 `stop_hook_active` 時 應 不擋;`LUMOS_STOP_LINT_OFF=1` 時 應 不跑這一道;兩道都要擋時 應 合成一則訊息且各自記名額;這道用掉的時間 應 不超過內層預算的一半也不超過 15 秒 [test:t_stop_hook_lint_new_worktree]
- [S3] 當改檔前鉤子的目標是 kt 檔時,寫入的新內容有某列的一個強字或兩個不同弱字 應 推那一列;只有一個弱字、只出現在註解或字串裡、只出現在被刪掉的舊內容裡 應 不推;命中超過三列 應 只推命中字數最多的三列,沒印出的列 應 下次還能推;同一會談同一列第二次 應 不推;既有推播輸出為空時 應 照樣單獨推;目標不是 kt/kts 時 應 不推 [test:t_impact_hook_kotlin_decision_rows]
