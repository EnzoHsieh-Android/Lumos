# Android寫法寫完當下自動檢查_計劃

> 白話:[[Projects/Android協程與API寫法機械檢查標準_計劃]] 做出型錄與規則包(第一批)之後,這份計劃把檢查接到「AI 寫完當下」與「代碼審查迴圈」:①AI 每回合要收工時,自動對這一回合改過的檔跑規則包,有新增告警就擋下叫它先修;②AI 要改 kt 檔時,把型錄〈情境決策表〉裡相關的一到三列推到它眼前;③代碼審要記「通過」之前,先跑新增告警與表態兩道機械檢查,不乾淨不准記。使用者原話(2026-11-05):「我會希望是 code review 的 loop 中就檢查乾淨,不用等到推送」「最好是自動化檢查,不需要我記得敲什麼指令才去盤點」。2026-11-05 從母計劃拆出(母計劃第二輪設計審 43 條裡 36 條落在這幾個新機制;設計審流程的熔斷提示是「累計折入超過 20 條就建議拆小」);拆出時列的七組未解問題,本版逐組改寫範圍,對照見〈開審前的改寫〉。

PRIOR-ART: ①回合結束擋停借既有收工點名鉤子(擋一次讓模型續做、`stop_hook_active` 與會談標記兩道護欄防無限擋);改檔前推列借既有改檔前影響鉤子的 `--stdin-payload`。②工作樹改動清單:不用暫時索引加 `git add -A`(母計劃 r2 八條問題的根源),改讀 `git --no-optional-locks status --porcelain=v1 -z`(沿用 repo 既有 `_handoff_files` 那一族的解法;porcelain 格式是 git 官方給程式解析的穩定格式,https://git-scm.com/docs/git-status#_short_format ;`--no-optional-locks` 讓 git 不順手改寫索引檔,https://git-scm.com/docs/git#Documentation/git.txt---no-optional-locks )。④子程序收尾:只用程序群組殺,殺不到自己另開會談的孫程序,做法是中間那層接到 SIGTERM 時自己收掉它的子程序(https://bugs.python.org/msg354818 、https://alexandra-zaharia.github.io/posts/kill-subprocess-and-its-children-on-timeout-python )——採用。③「改動當下就給回饋」:ESLint、Clippy 這類工具在編輯器裡即時標錯的慣例;Claude Code 的 Stop 鉤子可以回 `decision: block` 加理由讓模型續做(https://docs.claude.com/en/docs/claude-code/hooks )。採用;不選:每次改檔(PostToolUse)就跑——一回合改十幾次檔會跑十幾次,收工時跑一次就夠。
RETIRE-IF: 回合結束檢查連續三個月零擋停,降成只在審查迴圈跑;改檔前推列連續三個月沒有一列被推出,拿掉;代碼審通過前的機械檢查三個月內沒擋過任何一次,而推送前閘照樣有擋 → 查是不是漏接。

## 用詞

- **告警身分(指紋)**:新增告警閘替每條告警算的身分字串(規則、檔、去掉行號後的內容),用來判斷「同一條告警」;放行紀錄也是用它。「同一批告警」= 這次工作樹檢查新增告警的指紋多重集合(同一指紋出現幾次也算),排序後取雜湊。
- **工作樹檢查**:對「還沒提交的改動」跑新增告警比對——基準是 HEAD 那一版、現在版直接讀工作樹的檔。既有新增告警閘只比兩個提交(終點解不出來時判成環境不可用),本案多一個明示的「工作樹」終點。新增告警閘本體的說明在 [[Systems/pitfalls-code-loop]]。
- **回合時間戳**:回合結束鉤子每次跑到最後,在新目錄 `stop-turn/`(跟既有 `stop-block/`、`stop-printed/` 同一個建法與信任檢查、同一個七天清理)寫 `<會談>` 檔,內容是這一次的時刻。不放 `stop-block/`(那裡的既有性質是「只有擋過的會談才留東西」,有測試釘住)。
- **這一回合碰過的檔**:工作樹上有未提交改動的程式碼檔(`git status` 列得到),而且檔案修改時間晚於這個會談的回合時間戳。沒有回合時間戳(會談第一次收工、檔被七天清理掉、會談編號是空的)→ 這一次不檢查、只寫時間戳,下一次才開始;不拿逐字稿猜回合開頭(擋停回饋與壓縮接續在逐字稿裡跟使用者輸入同形,逐字稿第一筆也約 15% 沒有時間欄,r1 邊界席實測)。用修改時間而不是逐字稿列舉工具名,shell 寫的檔也算得到([[Systems/graph-sync-coverage]] 記過走 shell 的寫檔遠多於編輯工具)。
- **決策表列編號**:型錄〈情境決策表〉每列第一欄 `D-<n>`(2026-11-05 第一批型錄合併時已加);讀表函式 `_kt_decision_table`(新增)跟 [[Projects/Android寫法語意情境表態與盲判_計劃]] 共用,兩案誰先實作誰建。
- **鉤子時間上限**:鉤子註冊表(`scripts/merge-claude-settings.py` 的 `HOOK_BUDGET`)給每支鉤子的秒數;跟本文〈天花板〉(能力限制)是兩件事。
- **自動執行白名單**:工作樹檢查只跑通過這道檢查的宣告命令(寫死在 lumos,不讀專案設定,因為被打開的專案自己的設定不可信):用 `shlex` 切詞後,第一個詞恰好是 `ast-grep`(不帶路徑);第二個詞是 `scan`;一定要有 `--config`/`-c`,而且它的值(展開 `$HOME` 後)要落在 lumos 工具鏈自己的安裝目錄裡(規則設定檔可以宣告自訂語言、載入原生程式庫,不准用被打開的專案自己的設定檔;不給 `--config` 時 ast-grep 會往上找專案自己的 `sgconfig.yml`,所以也不准);其餘每個詞只能是 `{LINT_FILES}`、`{LINT_FILES_CSV}`,或旗標 `--format`、`--json`(含 `=stream` 等值)、`--filter`、`--globs` 及它們的值,外加恰好一個 `>` 後面接 `{LINT_SARIF_OUT}`;整條命令除了開頭的 `$HOME` 之外不得含 `;`、`|`、`&`、`` ` ``、`$`、`<`、`>>`、`*`、`?`、`~`、換行。`-U`/`--update-all`(會改檔)、`-i`/`--interactive`、`--custom-languages`(會載入原生程式庫)一律不准。不合的命令列成「工作樹模式不跑」。
- 型錄、規則包、接電方式、表態、盲判的定義見母計劃與 [[Projects/Android寫法語意情境表態與盲判_計劃]]〈用詞〉。

## 範圍

1. **新增告警指令** `lumos lint-new`(新增):
   - `--diff <範圍>` 或 `--worktree [--only-stdin]` 恰好給一個,都沒給或都給 → rc2 印用法。`--diff` 給單一版本時照判定函式既有規則走環境不可用(rc3),訊息提醒要給兩端。
   - `--budget 秒`:從指令一開始起算(含抽檔)。
   - `--only-stdin`:從標準輸入讀要看的檔(以 NUL 分隔、路徑相對 git 根);不走命令列參數,檔名以 `-` 開頭或檔很多都不會出事。
   - 退出碼照判定函式既有的八種狀態分三類(`--diff` 跟推送前閘完全同判:預算不夠沒跑到的命令照既有規則算擋):**擋**(blocked)rc1,每條印「檔:行、規則訊息、放行用的指紋」,最多印 20 條、其餘印條數;**乾淨或刻意不查**(clean、warn、off、no-config、no-files)rc0,每種各印一句講明是哪一種(warn 照印新增告警但註明「設定成只報告」);**沒檢查到**(not-checked、env-unavailable)rc3,印哪條命令沒跑、為什麼(第一個詞找不到執行檔就明說「沒裝 <工具>」),結尾一句「這次沒有被檢查,不算乾淨」。
   - 這支指令不寫治理帳(放行帳只有推送前閘記)。
2. **工作樹檢查**:判定函式多收一個明示參數「終點是工作樹」(不沿用「終點解不出來」那條路,那條照舊判環境不可用)。
   - 改動清單:沿用既有 `_handoff_files` 那一族的 `git --no-optional-locks status --porcelain=v1 -z --untracked-files=all` 解法(不另寫 v2 解析器;`--no-optional-locks` 讓 git 不順手改寫索引檔,2026-11-05 實測一般 `git status` 會改寫):狀態碼兩格任一是 `U`(或 `AA`、`DD`)的是合併衝突,不掃、列成「衝突中、沒檢查」;`R` 照它給的舊路徑當基準;未追蹤檔(`??`)基準為空,但若同一份清單裡有已刪除的檔、而且檔名(不含目錄)相同而且唯一,就拿那支的 HEAD 內容當基準(Kotlin 搬套件會改 `package` 行,逐位元組相同配不到;檔名對照用字典,一次 `git cat-file --batch` 讀,不逐檔開子程序)。
   - repo 正在合併、rebase、cherry-pick 或 revert(`.git` 裡有 `MERGE_HEAD`、`REBASE_HEAD`、`rebase-merge/`、`rebase-apply/`、`CHERRY_PICK_HEAD`、`REVERT_HEAD`,用 `git rev-parse --git-path` 找)→ 整次不檢查、rc3、印「合併或重定基底進行中」:那時工作樹上有大量不是 AI 寫的改動,會被誤當新增。
   - 給了 `--only-stdin` 就只看那幾支(跟清單取交集);交集是空的 → no-files,不擴大成整個工作樹。
   - 路徑一律相對 `git rev-parse --show-toplevel`;`.lumos/` 底下的一律不掃。
   - 沒有任何提交的 repo(沒有 HEAD):整次不檢查、rc3(沒有基準,也沒有可比的宣告檔版本)。
   - 宣告檔 `.lumos/lint.json` 在 HEAD 裡不存在(`git cat-file -e HEAD:.lumos/lint.json` 失敗),或它與 `.lumos/config.json` 有沒提交的修改(用 `git diff --quiet HEAD -- <檔>` 判,換行轉換設定不影響)→ 整次不檢查、rc3、印「宣告檔沒提交或有沒提交的修改,工作樹模式不執行」。
   - 只跑通過自動執行白名單的命令;其他宣告命令(含依賴層 `lint-deps.json` 全部)列成「工作樹模式不跑」。一條都沒跑時狀態是 not-checked(rc3),不是 clean。
   - 作弊比對(要兩個提交)工作樹模式不跑,輸出註明「作弊比對留給推送前閘」。
   - 單條命令保底 1 秒(推送前閘的 30 秒保底不變);工作樹模式下預算不夠沒跑到的命令歸「沒檢查到」(rc3)、不擋。
   - 收到 SIGTERM 時:結束自己開的每個檢查工具的程序群組(那些工具各自開在新會談裡,外層殺不到),刪掉這次的快照目錄,印一行「被中止」後以 rc3 結束。
3. **回合結束自動檢查**:收工點名那支回合結束鉤子(Claude 與 Codex 共用)多一道「寫法檢查」,跟既有「改 code 沒動圖譜」那道並列、各自判。
   - 位置:鉤子 `main()` 一開始就記下開跑時刻(`_BUDGET_START`,讓既有那道的「已耗時」含這道);寫法檢查插在既有那道所有提早離開(找不到圖譜、動過筆記、同批檔已講過)之前,所以沒有圖譜的專案、這輪也動了筆記的情況照樣跑。
   - 條件:專案根有 `.lumos/lint.json`;payload 沒有 `stop_hook_active`;`LUMOS_STOP_LINT_OFF` 與既有的 `LUMOS_STOP_BLOCK_OFF` 都不是 1(關收工擋停的人預期不再被擋);會談編號非空;這一回合碰過的檔非空而且不超過 50 支(超過就印一行「這回合改了太多檔,留給推送前閘」不跑——一次搬大量檔多半是重構,工作樹檢查會把基準配不到的舊告警全當新增);外層時間上限至少 55 秒(已安裝機器的註冊還是舊的 40 秒時,印一行「重跑安裝才會啟用」不跑,免得擠掉既有那道)。宣告檔有沒提交的修改這件事不在鉤子判,交給 `lint-new` 回 rc3(判斷只在 lumos 一處)。
   - 呼叫 `lumos lint-new --worktree --budget 8 --only-stdin`、從標準輸入送這一回合碰過的檔,子程序開在新程序群組;12 秒到了先送 SIGTERM 給整個群組,再等 1 秒送 SIGKILL。新增告警閘的快照暫存若因 SIGKILL 殘留,照既有規則一天後清。
   - 時間:鉤子時間上限從 40 秒調成 55 秒。既有那道照同一公式(上限 × 0.7 減已耗時,已耗時含這道):55 × 0.7 − 12 = 26.5 秒,不少於它實測需要的 25 秒。
   - 只在 `lint-new` 回 rc1 時擋;rc0 不出聲;rc3 印一行到 stderr。擋下原因寫「這幾條新增告警要先修」加每條「檔:行、規則訊息、放行指紋」,最多 10 條、整段最多 1500 字,結尾一行教放行指令。
   - 防無限擋:沿用既有「一個名額一個獨佔建立的檔」做法,在 `stop-block/` 建 `<會談>.lint-<批次雜湊>`(只在真的擋下時建,既有性質不變):同名檔已存在 = 同一批已擋過、這次不擋;同會談這種檔已有 3 個 = 不再擋。先佔名額再輸出,輸出寫不出去就刪掉剛佔的檔(既有那道的順序)。
   - 兩道都要擋時:各自先判、各自佔名額,最後只輸出一則 `decision: block`,原因是兩段接起來;只有一道要擋時只輸出那一段。
   - 回合時間戳:這道一開始(任何提早離開之前,含 `stop_hook_active` 那一次)先讀出上一個時間戳,接著立刻寫入這一次的時刻;會談編號是空的才不寫。所以續做那一輪改的檔,下一次收工會被查。
4. **改檔前推相關列**:比對在 lumos 本體做,鉤子只印。
   - 鉤子照舊一次呼叫 `lumos impact --stdin-payload`(冷卻窗內那條 `--incidents-only` 路徑也一樣帶);payload 多三個鍵:`delta_new`(只放寫入的新內容:Edit 的 `new_string`、MultiEdit 每段的 `new_string`、Write 的 `content`,上限 2 MB,超過就不放、這次不推列)、`session_id`、`pushed_rows`(鉤子從自己的標記目錄讀到的「這會談已推過的列」清單)。
   - 專案沒有知識圖譜時,`cmd_impact` 既有在找不到圖譜就提早返回;本案讓帶了 `delta_new` 而且目標是 `.kt`/`.kts` 的呼叫,在那個提早返回之前先算 `decision_rows` 並回傳(其他輸出照舊為空)。鉤子對沒有圖譜的專案也要送這種呼叫(現在只對有圖譜的專案出聲)。
   - lumos 讀決策表,對 `delta_new` 先剝掉 Kotlin 的註解與字串字面值(`_kotlin_strip`,新增,兩案共用:處理 `//`、巢狀 `/* */`、`"…"`、`"""…"""`,字串樣板 `${…}` 裡的程式碼保留;被剝掉的字元換成空白、換行原樣保留,行數與欄位不變),再用 `_kt_trigger_re`(新增,兩案共用的觸發字比對)比:每個觸發字 `re.escape` 後前面不准緊接英數或底線、後面不准緊接英數或底線(前面是 `.` 可以,所以 `.flatMapLatest` 會中),分大小寫。`_kt_decision_table` 依表頭名稱取欄,不依欄位位置(第三批會多加欄)。
   - 一列命中至少一個觸發字就算命中;排除 `pushed_rows` 之後,照命中字數多寡、再照表序取前三列,放在回傳 JSON 的新鍵 `decision_rows`。
   - 鉤子改三處:①既有「影響脈絡是空的就不印、直接返回」那條路,有 `decision_rows` 時改成單獨印這幾列;②同一條路上「脈絡是空就撤掉冷卻標記」那一步,有印列時不撤;③冷卻窗內的事故比對路徑也印 `decision_rows`。
   - 印完才在既有的 `lumos-impact-<會談>/` 標記目錄建 `row-<D-n>` 空檔(沿用既有只講一次標記的寫法,鍵換成列編號)。那個目錄照既有規則 24 小時清,之後同列可以再推一次。並行兩次改檔可能重推同一列,不另防。
   - 只做 `.kt`、`.kts`。Codex 這一版不做(它的 apply_patch 帶得到全文,另案接)。
   - 型錄的觸發字由第一批的型錄格式檢查把關:不准收一般常用字(停用字表與檢查在 [[Projects/Android協程與API寫法機械檢查標準_計劃]] 範圍 1 與 S3,2026-11-05 實作時補進)。
5. **代碼審通過前先跑機械檢查**:不另寫共用函式,沿用推送檢查既有的「每道都判完」收集模式(`_codeloop_guard_verdict` 的 `keep_going` 路徑),多一個選項「只跑新增告警與表態兩道」(不含合約測試、安全證據、端到端驗收與代碼審留痕——帶進留痕那道會讓 pass 自己擋自己)。`lumos code-loop pass` 在進留痕驗證(它有「沒有審查帳就回沒東西可驗」與 light 兩條提早返回)之前就呼叫它,範圍跟 `code-loop check` 不帶 `--diff` 時相同;分岔點算不出來或等於 HEAD 時照 check 既有規則放行並記帳。兩道的判法跟推送前閘完全相同(環境不可用照既有規則自動放行並記帳)。任一道擋下就不寫留痕、照 pass 既有被擋的退出碼(rc2)、印擋下原因與修法。`code-loop skip` 不受影響。
6. **代碼審手冊**:lumos-code-loop 手冊在「派審查席」之前加一步「跑 `lumos lint-new --diff <分岔點>..HEAD`,rc0 才派;rc3 代表沒檢查到,不是乾淨,要先裝好工具或在派工詞寫明哪些類別沒被機械檢查」。審查席派工材料附機械檢查結果,寫明「機械已查(rc0 且是 clean)的類別席位不報」。手冊這條只是建議人怎麼做;機器擋的是範圍 5 的 pass 與推送前閘。

**不做**:推送前閘的判定結果不變(範圍 2 加參數、範圍 5 加選項都是行為不變的擴充,既有測試釘住);不在推送前閘或回合結束鉤子裡呼叫模型;回合結束不跑白名單以外的命令;表態對程式與盲判在第三批([[Projects/Android寫法語意情境表態與盲判_計劃]])。

## 實務隱患

- **回合結束檢查拖慢每一輪**:只對這一回合碰過、至多 50 支的檔,只跑白名單命令,上限 12 秒;ast-grep 對幾支檔是毫秒級(母計劃 2026-11-05 實測);lumos 啟動約 0.8 秒(r1 資源席實測)。
- **擋停迴圈**:同一批只擋一次、續做那輪不擋、一個會談最多擋三次;推送前閘照擋,逃生門是放行並寫理由。
- **共用工作目錄**:修改時間晚於回合時間戳的檔,可能包含同一工作目錄別的會談同時改的檔;擋下訊息每條都帶檔名,模型自己判斷;建議每個會談用自己的工作樹(全域規則本來就這樣要求)。
- **時鐘與修改時間**:檔案修改時間被工具保留成舊值(例如 `cp -p`、`git checkout` 舊檔)時,那支檔不算這一回合碰過,推送前閘兜底。
- **合併、搬檔**:合併或 rebase 進行中整次不查;搬套件靠檔名配對基準;同名檔有多支被刪時配不到,照新檔算(天花板)。
- **改檔前推列太吵**:最多三列、同列同會談 24 小時內只推一次、常用字不准當觸發字。
- **代碼審通過變嚴**:範圍是整條分支,分支裡較早帶進、沒放行的新增告警會在 pass 被擋;出口是放行。
- **已安裝機器的註冊是舊值**:鉤子腳本是符號連結會立刻換新,但註冊裡的時間上限要重跑安裝才更新;上限不到 55 秒時寫法檢查不跑、印一行提醒。
- **跟 detekt 那案、第三批改同一區**:[[Projects/Android的detekt推送前真的擋_計劃]] 改新增告警閘的佔位符替換;[[Projects/Android寫法語意情境表態與盲判_計劃]] 在表態判定裡加情境題。本案加終點參數、收集模式的選項與新指令;讀表函式本案與第三批共用,誰先實作誰建;後合的那個要重跑相關測試。
- **舊否決對照(2026-11-05 跑 `lumos rejections` 按概念比對)**:母計劃記的三條照舊(新增告警閘出錯就放行沿用;改檔前推播零命中不講沿用;回合結束鉤子只印一行——本案的「乾淨不出聲、沒檢查到印一行」同向)。
- 資安:回合結束會自動執行宣告命令;只限白名單(寫死在 lumos、逐詞驗、禁改檔與載入原生程式庫的旗標),宣告檔有沒提交的修改時不跑;跟同一支鉤子「被打開的資料夾不准指使我們執行指令」的先例對齊:專案自己的設定不能放寬白名單。
- 已排除:金流:不碰付款或點數
- 已排除:對外送出:檢查只在本機跑,不送資料出去
- 已排除:不可逆:新增指令、鉤子分支與選項,退提交即回原狀;治理帳只追加
- 守衛面:改回合結束擋停、代碼審通過條件,屬守衛面,走完整設計審(不寫成已排除)

## 天花板

1. 回合結束檢查只看這一回合碰過、還沒提交的檔;同一回合先寫後提交的、續做那輪新加的告警,等代碼審通過前或推送前閘。

3. 修改時間判「這回合碰過」:時間戳被保留成舊值的檔漏掉,同一工作目錄別的會談同時改的檔會被算進來;會談第一次收工不檢查。
4. 搬檔配基準只認唯一的同名檔;一次搬超過 50 支檔的回合不檢查。
