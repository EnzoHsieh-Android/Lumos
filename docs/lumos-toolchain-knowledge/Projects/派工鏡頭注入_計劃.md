# 派工鏡頭注入_計劃

> 白話:派審查員的時候,規矩要求把「這批改動碰到哪些帶合約或出過事故的筆記」貼進派工詞——實帳沒人做到。本案在派子代理那一刻,由 hook 把機器算好的那份清單**附**進派工詞。★它是鏡頭,不是閘★:不擋、不驗、不記帳、不量成效。成不成功只看一件事——派工詞裡真的多了那段。

PRIOR-ART: ① 最小解層級——攔截點、清單算法、截斷規則、安裝器、注入位置全是既有的:`PreToolUse` hook(本 repo 已有一支同位置的 `impact-hook.py`)、`lumos impact --diff` 的固定席、[[Systems/design-loop]] d9 的 cap=8、`scripts/merge-claude-settings.py`。本案自己寫的只有一支 hook 腳本與一段注入措辭。② 世界解過沒——「先把該查的列出來、再讓判官逐條看」是 [arXiv 2608.31016](https://arxiv.org/abs/2608.31016) 量到唯一有效的補救(找漏 25%→37%),其餘(換措辭/多席/提示詞優化)全部無效;而★它只是輔助,清單在眼前判官仍漏六成★——所以本案定位為鏡頭。③ 裁定=borrow-design,零依賴。

## 一句話

★派工詞帶標記時,hook 把固定席節點附上去;不帶就完全不碰。★

## 為什麼是鏡頭,不是閘(今天五份計劃的結論)

2026-09-03 五份計劃全死在設計審,四份死在「想證明它有用」——量覆蓋率、記映射、做對照組、定指紋。存活的事實只有三件:
- ★攔得到★:[[Verification/2026-09-03_派工攔截點實測]]——`PreToolUse` 匹配派子代理(`tool_name`=`Agent`)、拿得到派工詞全文、`updatedInput` 改得了、子代理照單全收。
- ★清單早就算得出來★:`lumos impact --diff` 的固定席(帶硬合約或出過事故的節點),每篇標為什麼被釘、被哪個檔牽連。
- ★沒人貼★:規則 2026-08-29 上線後唯一一個迴圈、編排者=規則作者本人、次日,零執行([[Projects/code席爆炸半徑供糧_計劃]])。

Enzo 裁(2026-09-03):散文審查的清單本質是鏡頭;可執行那層(合約綁測試、推送前真跑)已經存在且只有它該是閘;★不要求鏡頭證明自己有用★。

## 對現行裁定的處置(三條,全部不繞過)

1. **`impact --diff` 聚合版「不接 hook」**(`Systems/retrieval-ranking:51`、[[Projects/impact-diff橋接_計劃]]):理由=非固定席那層無機械保證、靠審查員兜。★本案只附固定席★,落在它明說有保證的那層;且本案不是閘,不承擔「兜」的角色——審查員仍在場。
2. **[[Systems/design-loop]] d9**(2026-09-01):「上限內貼內容必答、超出列名不必答」,cap 沿 `_print_sync_nudge(cap=8)`。★直接採用★。
3. **[[Projects/主動影響幅度偵測_計劃]]:同位置 hook「不進 anchor、永不 block」**。★比照★:本案不進 anchor、永不回 deny。本案與它的差別=改寫輸入(`updatedInput`)而非只注入上下文(`additionalContext`)——理由是後者注給派工者、子代理是新對話拿不到;★2026-09-03 晚已實測:additionalContext 只到派工者、子代理回「沒有清單」——updatedInput 是唯一路徑★(見 [[Verification/2026-09-03_派工攔截點實測]] 追測二)。

## 設計

1. **觸發**:`PreToolUse`,matcher `Agent`。派工詞含一行 `LUMOS-IMPACT: <diff 範圍>` 才動作;沒有就原樣放行。★範圍由標記明寫,不從散文猜。★
2. **內容**:跑 `lumos impact --diff <範圍>`,取固定席;照 d9:前 8 篇貼內容(節點名+為什麼被釘+被哪個檔牽連+合約行),其餘只列名。
3. **措辭**:中性系統附加框架,固定標頭 `## [lumos 自動附加] 本次改動的固定席節點`。★不用命令式、不用「暗號」型措辭★(實測會被子代理指認為提示注入而拒答)。
4. **失敗一律放行**:算不出、超時、不是 git repo、lumos 不在——原樣放行,stderr 印一行(白話三段式)。內層 subprocess timeout 必須明顯小於外層宣告(本 repo 栽過同款:內層 20s > 外層 10s)。
5. **安裝**:比照四支既有 hook——住 `scripts/hooks/claude/`,加進 `_GLOBAL_CLAUDE_HOOKS` 與 `HOOK_ENTRIES`,由既有合併器安裝。不自造流程、不引入外部二進位。
6. **不做**:不 deny、不驗證審查員有沒有讀、不記治理帳、不量成效、不進 anchor。

## 驗收(只有兩條)

- **機械**:在一次真實審查派工上,派工詞含標記 → 子代理收到的 prompt 含固定標頭與 ≥1 篇固定席(用 hook 實測同款方法:埋哨兵、看回覆)。
- **反向**:不含標記的派工,prompt 逐位元不變。
- ★不驗收「有沒有用」★——那是另一條線,今天已裁不走。

## 讓標記被寫的方式(唯一的採用機制)

★不靠人記得★:把 `LUMOS-IMPACT: {range}` 寫進 `skills/lumos-code-loop`/`lumos-design-loop` 的派工詞模板(`templates.md` §1/§3)當固定一行——這正是 [[Projects/impact鏡頭機械化_計劃]] 停案時留下的「唯一正途=改派工模板層」。編排者照模板派工,標記自然在;hook 把清單補上。
