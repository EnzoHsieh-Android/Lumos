# 治理帳封存_計劃

> 白話:治理帳(每道閘擋下、放行、核可都記一行的那本帳)只增不減,2026-10-13 已經 12 萬行、約 20 MB。這篇是「主帳只留近 90 天、舊的按月搬進封存檔、不刪除」的設計,本篇只管設計。盤點發現有好幾個讀者要讀全歷史,直接搬會讓它們悄悄算錯,所以要先改讀取端、再搬。

## 為什麼現在只寫設計

- **現在照 90 天切只能搬 3,162 行,約 2.6%**(2026-10-13 實量)。帳從 7 月才開始記,大宗是 9 月的例行提醒(約 8.5 萬行、12.7 MB)。
- 那類例行提醒 10-04 起已經改寫進不進版控的本機帳(見 [[Projects/治理帳例行紀錄分流_計劃]]),主帳之後長得慢很多。
- 所以真正有感要等 12 月中 9 月那批滿 90 天。在那之前可以先做讀取端與名單補丁(本身就降低風險),封存指令晚點做。

## 誰在讀這本帳(盤點結果)

完整盤點(14 個讀者、4 支寫入函式、95 支寫死帳路徑的測試)在研究資料夾的 18 號盤點檔,不進版控;以下是做決定需要的部分。動手前以程式碼為準重量一次。

**必須改,不改會算錯或把該擋的放掉:**

- **跑滿回顧判「有沒有欠回顧」**:人裁紀錄被搬走,會判成「沒有人裁」,回顧義務就消失。這支原本刻意設計成讀不到就擋,搬走等於反過來放寬。
- **迴圈清單**:審查帳沒封存、還列著那些迴圈,結案紀錄卻搬走了,早就結案的迴圈會被報成還開著。
- **逃逸統計**:放行過的迴圈數變少,逃逸率失真。
- **`lumos gov`**:預設看 90 天剛好不受影響,但使用者給更長的區間時會悄悄少資料。

**建議改,影響是偏嚴或只差在顯示:** 修正關卡最後一輪結果、重寫血緣警告、超過 12 週的度量式撤除條件、doctor 的規格閘清單、週回放補凍結。

**不用改:** CI 找代碼審通過留痕與表態(只要最新一筆,90 天沒動程式的分支推送本來就不算高風險)、合併提交讀另一側的帳(讀的是 git 樹裡最近 20 個提交)、doctor 帳增速觀測、新增告警閘近 30 天放行計數。

**兩份名單要跟封存同一個提交補,不然封存那個提交本身就會出事:**

- 「簿記檔」名單不認得封存資料夾:在已過代碼審的分支上提交封存,會被當成改了程式,通過留痕失效、推送被擋。
- 共改守衛的排除名單同理。

## 設計

### 1. 讀取統一走一支函式

- 新增一支讀取函式:回傳「封存檔照檔名順序 + 主帳」接起來的內容;給了起始日就只讀需要的封存檔(檔名就是月份,不用打開就能跳過)。
- **判定類讀者要的是帳裡原本的先後順序**(跑滿回顧取「最新一筆人裁之後」、留痕取最後一筆),所以接起來的順序就是原順序,**不准改成依時間重排**。統計類讀者在它之上再合本機帳、依時間排,沿用現有分工。
- 封存檔跟主帳用同一套開檔守衛與切行規則:不是一般檔、是捷徑、有別的硬連結 → 判「帳壞」並擋,不是「沒有紀錄」。

### 2. 只切檔頭連續的一段

- 從檔頭往下找第一筆時間晚於截止日的行,只搬它之前的;之後就算有更舊的時間(分支晚合進來的)也留在主帳。
- 這樣「封存檔依序 + 新主帳」逐位元組接起來就等於原檔,先後順序零變動。
- 搬出來的那段按月份切成一月一檔;萬一同一段裡月份倒退,就併進前一檔,不重排。

### 3. 只在主線、用單一指令做,一個提交只動兩樣

- 只動主帳和封存資料夾。
- 先寫封存檔(暫存檔 → 自驗 → 換名),驗「封存檔 + 新主帳 = 原主帳」,再換掉主帳。
- **全專案的寫入函式都沒上鎖**(見 [[Issues/治理帳多個寫入者都沒上鎖]]):換主帳前重看大小,變大了就把多出的尾巴補進新主帳再換,重試幾次還在變就放棄這次。根治是讓四支寫入函式走同一支追加函式再加鎖,另案處理。
- 主帳永遠留著(空檔也行):有讀者把「檔不在」判成「這個專案還沒有治理帳」。不用硬連結、不用捷徑做備份。
- 另寫一份清單檔,記每個封存檔的行數、雜湊、時間範圍,讀取端可以拿來驗封存檔沒被改。

### 4. 封存檔進版控

- 迴圈清單、逃逸統計、`lumos gov` 長區間要全歷史;封存檔不進版控的話,每台機器、每次 clone、CI 看到的歷史都不一樣。
- git 歷史本來就留著這些行,不進版控也省不了 repo 體積;省的是工作目錄檔案大小與每次讀帳的成本。
- 專案骨架寫的忽略清單不要忽略封存資料夾,跟主帳同理。

## 分兩步推

1. **第一步:讀取端與名單補丁。** 統一讀取函式、四個必須改的讀者改走它、兩份名單補封存資料夾。封存檔不存在時行為跟現在一樣(只讀主帳)。
2. **第二步:封存指令。** 第一步上線、穩定一段時間後才做,第一次真的搬等 12 月中重量之後決定。

## 先紅的測試

1. 接起來等於原檔:造一本跨三個月、中間夾一筆晚合進來的舊時間行;封存後接起來逐位元組相等,那筆舊行留在主帳。
2. 跑滿回顧不放寬:人裁紀錄在封存檔、帳裡沒有回顧紀錄 → 仍判「欠回顧」(現況程式會判沒有人裁,這支先紅)。
3. 迴圈清單不誤報:結案紀錄在封存檔 → 判已結案。
4. 逃逸統計分母不變:封存前後輸出相同。
5. `lumos gov` 長區間:給 400 天時封存前後筆數、起訖日相同;給 7 天時不打開任何封存檔。
6. 留痕不失效:分支已過代碼審,之後只提交封存 → 推送照放行。
7. CI 後備:乾淨副本、主帳只剩近期 → 近期的通過留痕找得到,已封存的舊留痕不會被當成最新。
8. 併發:換主帳前有別的程序追加一行 → 那行在新主帳裡。
9. 帳壞照樣擋:封存檔是捷徑、有硬連結或不是一般檔 → 判帳壞,不是沒有人裁。
10. 切行一致:新讀取函式不用會把怪字元當換行的切法(既有的掃原始碼測試要掃得到它)。
11. 主帳被搬到空:doctor 不印「還沒有治理帳」、閘照常追加。
12. 效能:20 MB 帳量下 `lumos gov` 預設區間與代碼審檢查,封存後不能比封存前慢。

## 回退

- 封存是單一提交、只動主帳與封存資料夾,`git revert` 那個提交就能還原:檔頭那段加回去、封存檔刪掉;之後新加的行在檔尾,跟檔頭不相鄰,不會衝突。
- 不靠 git 也能還原:照清單檔順序把封存檔接回主帳前面,驗行數與雜湊對得上,再刪封存資料夾。
- 第一步的讀取端在封存檔不存在時照常運作,所以回退封存不必連讀取端一起退。

## 盤點時順便發現的

- doctor 帳增速觀測那段的程式註解寫「這本帳有四個整檔讀者」,實際至少 10 個。實作第一步時一併改註解,以這篇的清單為準。
