# 選擇點變異平行_計劃

## 目的

讓 `lumos choice-kill` 同時開幾份隔離工作樹,各跑不同的壞法,把牆上時間再除以份數。原本寫在 [[Projects/選擇點變異加速_計劃]] 的〈做法〉2,使用者 2026-11-23 裁定拆出來另開。

## 狀態

等合併呼叫([[Projects/選擇點變異加速_計劃]])上線、並在 Android 實驗專案實測每個壞法的秒數與記憶體用量之後再設計;這份目前只是待辦草稿,不是可以實作的設計。

## 第一輪設計審針對平行的發現(待重新設計時逐條處理)

卷證在 `governance/review-reports/選擇點變異加速/`,審的是拆開前的合併版快照。

- rs1:主程序的判定迴圈出例外時,沒有收掉各份的測試程序群組與工作樹。
- rs2:「工作樹建不起來」在程式裡是交出 error 列、不是例外,照原寫法那一份的壞法會被記成跑不出結果。
- rs3:第一份失敗、或在量基準時收到中斷,其餘份怎麼啟動沒有定義。
- rs6:清殘骸跳過登記中路徑的比對,在 macOS 上會因 `/var` 與 `/private/var` 不同而永遠對不上。
- rs7:主程序迴圈的結束判斷順序沒寫,執行緒結束前最後交出的列可能漏收。
- rs8:記憶體上限只看實體記憶體,沒有看可用記憶體與磁碟空間(每份一棵工作樹加建置資料夾)。
- i6:逐支模式下第二份以後的第一個壞法要冷編譯,共用的單支基準只有幾秒,逾時上限蓋不過。
- i8:否決 `_BtProcs` 的理由寫錯(`_kill_run` 本來就收 started 參數),剛開還沒登記的程序在強制結束時會成孤兒。
- i9:平行條款要真開三份,預設記憶體估計在 16GB 的機器只開一份,條款會紅;估計值給非數字或負數沒定義。
- i12:共用基準表在第一份提早結束時,後面幾份會同時各量一次;共用的基準輸出遮的是第一份的工作樹路徑。
- a3:平行份數的旋鈕(`--jobs`、1–8、不合法 rc 2)跟既有的 `bound_tests.parallel`(2–16、不合法當 1)命名與處理不同。
- a4:程序登記用 `_KILL_RUN_LIVE`、輪流預先分配、某份出錯不停其他份,三點跟合約測試閘的平行形狀不同。
- b1:記憶體上限可能算出 0 份(8GB 機器),連預設一份都不跑;沒有壞法時也沒有第一份可等;Windows 沒有 `os.sysconf`。
- b2:共用基準表的鍵不含平台,「表已填」只有整張一個粒度,合併基準分出的幾組測試集合沒地方放。
- b8:〈實務隱患〉說逾時照各份自己的基準算,〈做法〉卻是各份共用第一份的基準,兩處矛盾。
- b10:某一份分到的壞法全都沒有配方時,`cmd_guard_kill` 會印擋下並回 2,算不算那份當掉沒寫。
- c8:某份當掉時「已交出部分列的壞法不記帳」跟 `on_row` 遇到決定性的列就當場記帳衝突。
- rb6:同 c8,要寫明已判定的照記、只有補記「缺結果」才跳過。
- rb7:第一份在立起「基準量好了」之前就結束,其餘份的基準與逾時沒定義。

## 重新設計前要先有的數字

- 合併上線後,實驗專案每個壞法的牆上秒數、CPU 使用率、單份的記憶體峰值(Gradle 背景程序、Kotlin 編譯背景程序、測試行程)。
- 單份時 CPU 有沒有吃滿;沒吃滿才有平行的空間。
