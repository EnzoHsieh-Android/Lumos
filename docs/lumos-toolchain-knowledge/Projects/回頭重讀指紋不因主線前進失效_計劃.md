# 回頭重讀指紋不因主線前進失效_計劃

> 白話:推送前的「回頭重讀」會記住「這篇筆記對照過這一版程式」。現在它認的是程式檔在分支頂端的整份內容,所以只要主線有人改了同一支檔、你 rebase 上去,你自己的改動一個字沒變,所有對照過的筆記也全部要重讀一遍。改成認「你這條分支對那支檔做的改動本身」:主線前進、rebase 之後,只要你的改動沒變,對照紀錄照樣算數。

## 緣起

- 2026-10-13 一條分支因主線連續前進兩次而 rebase 兩次,回頭重讀也跟著重派兩次;自己的改動沒變,判定者讀的是同一段改動。`scripts/lumos` 被大約 49 篇筆記的 about_code 管著,主線上任何人改到它,所有管它的筆記在每條進行中的分支上都會失效。出處:使用者 2026-10-14 問「這次示範有什麼 lumos 可以改進」時列的第 3 條。
- 詞彙:**候選**=這次推送要對照的家筆記(改到的檔的家 ∩ 這次被改過的筆記);**主線候選**=算分岔點用的主線分支(遠端 HEAD、main/master 的上游等);**頂端**=被推送(或被 prepare)的那個提交;**對照紀錄**=`governance/reread-verdicts/` 裡以對照指紋開頭的判定紀錄。
- 原設計 [[Projects/守檔筆記對照改動_計劃]] 的對照指紋是雜湊(筆記路徑、那篇頂端 about_code 每支檔的頂端 blob、範本版本),刻意不含範圍與 diff。理由寫在它的〈做法〉第 1、2 節:「手動 prepare 與推送前 check 的起點算法可能不同,含 diff 的指紋對不上、提醒永遠消不掉」(設計審 r1 四席)。本計劃要推翻「不含 diff」這一半,所以必須正面回應那條理由(見〈做法〉3)。

PRIOR-ART: git 自己的 `git patch-id --stable` 就是為了「rebase 之後認出同一個改動」而設計(`git cherry`、`git rebase` 判斷哪些提交已經在上游都靠它):把 diff 去掉行號後雜湊。借它「去掉行號、`index` 行」的想法,但不借它「忽略所有空白」那一半——本 repo 以 Python 為主,縮排就是語意,忽略空白會把縮排不同的改動當成同一個(前掃實測:把 `return y` 搬進迴圈與只縮成兩格,patch-id 相同);正規化重用本 repo 既有的逐檔改動指紋函式 `_patch_file_changes`(資安席用來認「rebase 之後同一版改動」),不另跑 `git patch-id`、不另寫第二套。主線分岔點借本 repo 既有的手動代碼審預設起點算法(主線候選與推送閘共用);同一次 check 裡候選範圍與指紋用不同的起點函式,理由見〈做法〉3。
RETIRE-IF: 上線 8 週內,`note-reread` 事件裡「靠 `v2` 命中」的篇數是 0(新指紋沒有省下任何一次重讀),或從「靠 `v2` 命中、`v1` 不會命中」那一群抽查到一次該重讀卻被當成已對照——撤回成只認 `v1`。
REVISIT:2026-12-15 照 RETIRE-IF 數一次 `note-reread` 事件的 `covered_by` 與 `fp_counts` 欄位,並從「靠 `v2` 命中」那一群抽 5 篇,人工比對判定者當時讀的 diff 與頂端的程式,看舊句有沒有該點出卻沒點出的。

## 做法

1. **新指紋(`v2`)認「這條分支對每支檔的改動」**:雜湊(筆記路徑、範本版本、一行 `指紋算法 v2`、那篇 about_code 每一項配上「它在分岔點..頂端的改動指紋」)。舊指紋(`v1`)= 現在的頂端 blob 指紋,雜湊輸入一字不改、不加版本字樣。
   - **先拿清單、不靠路徑比對**:跑一次 `git diff --raw -z --no-renames <分岔點> <頂端>`(不帶 pathspec),得到這條分支改過的每支檔(git 原樣路徑的位元組、兩邊的物件編號與 mode、狀態)。原樣路徑經 `_nodehome_key` 換成 NFC 鍵,跟 about_code 的鍵比;「未改」的意思是「不在這份清單裡」(那一項寫成固定字樣 `<鍵>\t未改`,主線怎麼改它都不影響指紋),不是「diff 沒有輸出」——樹裡存的是 NFD 檔名、或 about_code 的鍵當成 pathspec 比不到,都不會被誤記成未改(r1 正確性席、邊界席實測過這個洞)。about_code 的某一項在分岔點與頂端兩邊的樹裡都找不到(拼錯、是資料夾),整篇退回 `v1`。
   - **文字檔**:對清單裡的每一支,單獨跑一次 diff(全域開 `--literal-pathspecs`,路徑用 git 原樣路徑、前面加 `--` 分隔,**不加** `:(literal)` 前綴——兩者併用時 git 會把前綴當成檔名的一部分、輸出變空,r2 三席實測);清單裡有這支檔、diff 卻是空的,那篇退回 `v1`。輸出交給既有的逐檔改動指紋函式 `_patch_file_changes`——它本來就是「rebase 之後還認得同一版改動」的指紋(資安席在用),會去掉行號與文字檔的 `index` 行、處理引號路徑、mode 與新增刪除。它預設連 `@@` 後面 git 印的段落標頭一起算;本計劃給它加三個參數 `headers`、`lf_only`、`hunk_tag`,預設都不變(資安席照舊),回頭重讀這邊都打開:`headers=False` 不算 git 印的段落標頭——那是 hunk 之前最近一行頂格的整行,主線在上方新增頂格的一行,作者的改動一字未變它也會變(r1 三席實測),而且 git 依屬性檔挑標頭規則;`hunk_tag` 給每個 hunk 一個我們自己算的標籤(縮排鏈,見下一點)代替它;`lf_only=True` 只用 `\n` 切行——它預設用 `splitlines()`,會在換頁符號(`\x0c`)、U+2028 等字元處多切一刀,切出來的後半段不以 `+`、`-`、空白開頭而被丟掉,同一行換頁符號之後的改動就不進指紋(r2 兩席實測)。(2026-10-14 代碼審 r2 合約席更正:原本寫「加兩個參數」「不算函式名標頭」,跟後來加的 `hunk_tag` 讀起來互相打架。)
     - **但每段改動上面那幾層要算——縮排鏈的原文**(2026-10-14 代碼審 r1 資安席 major、正確性席 1;r2 六席):整個標頭拿掉之後,同一段改動搬到同檔另一個前後三行相同的函式(`-check(user)/+allow(user)` 從公開端點搬到管理員端點),指紋不變,`v1` 會擋的這裡不擋。每個 hunk 帶一個標籤(`_note_reread_hunk_tags`,核心是 `_note_reread_hunk_nodes`),我們自己從頂端版本的內容算、不靠 git 依屬性檔選的規則:**跳過的行**是空行、只有空白、只有 ASCII 標點與括號的行(`{`、`}`、`):`、`];`;非 ASCII 的字元算有字;2026-10-14 代碼審 r3 正確性 1、邊界 1:black 風格多行簽名的收尾 `):`、Allman 另起一行的 `{` 原本是「縮排較淺的最近一行」,整個檔的函式拿到同一條鏈、搬到另一個函式指紋不變);**起點**是這段在頂端版本的範圍裡第一個不跳過的行;**鏈**是從起點往上,縮排比起點淺的最近一行(跳過的行不算;縮排把 tab 照 8 欄展開後比欄寬),記那行去掉頭尾空白的原文,再從那行往上找比它更淺的,一路到縮排 0——起點本身縮排 0 就沒有鏈;範圍裡全是跳過的行時,有只有標點的行(例如只改 `)`)就從第一個這種行自己的縮排往外推(只收縮排比它淺的行;2026-10-14 代碼審 r4 邊界 2:原本當成無限深、鏈取上面最近一行有字的行,常比 `)` 自己那層多一層,鄰近的參數行被主線改就要多重讀一次),只有空行與空白就當成無限深(鏈從它上面最近的不跳過的行起算)。鏈的計算邊切行邊看指紋這一步的截止時間,到了那支檔退回 `v1`、原因「逾時」(第 5 點;r4 併發 3:原本一次切成整個串列,記憶體約檔案的 30 倍、切完才看截止時間)。鏈由外到內串起來雜湊成標籤。**不分語言、不猜名字**:Kotlin 的 `fun pub` 與 `fun adm`、Java/Kotlin 類別裡的兩個方法、C 的 `int pub(...)` 與 `int adm(...)`、TS 的 `export const a = () =>` 與 `b`、Go 不同接收者的同名方法、Rust 兩個 `impl` 區塊的同名方法、Python 的 `m1/helper` 與 `m2/helper`、`A.X.f` 與 `A.Y.f`,那幾行的原文本來就不同(S20)。頂格的賦值行不在任何改動的鏈上(除非改動縮排在它底下),主線在上方插頂格行、改了上方另一個函式,都不影響(S8)。新側行數是 0 的 hunk 沒有鏈:指紋的 diff 帶 3 行上下文,新側只要還有一行,hunk 就帶到上下文,所以新側 0 行只在頂端那一版是空的(刪檔、清空)時出現,那時舊側從第 1 行起、上面沒有任何一行,鏈本來就是空的,不必另讀分岔點那一版(派工詞原本說「純刪除用舊側起點在分岔點版本找」,實作時查到結果必然是空、省掉那次讀)。**代價**:主線改了外層那一行(例如這段改動所在函式的簽名、所在類別那一行),指紋會變、要多重讀一次,方向是多擋(black 風格的多行簽名只有 `def f(` 那一行在鏈上,參數行的縮排跟本體一樣、不在鏈上;S22;2026-10-14 前這裡說「參數與簽名不算」——那是 r1 猜函式名的做法,好幾種語言兩個不同函式拿到同一個名字,r2 六席實測,由縮排鏈取代)。
   - **不讀工作樹的屬性檔**(2026-10-14 代碼審 r1 邊界席 1):`-diff` 這類屬性原本取自當下簽出的 `.gitattributes`,簽出 main 與簽出分支算出的指紋不同。本機 git 2.39 沒有 `--attr-source`,實測裸庫模式(`--git-dir` 加 `--bare`)仍從「目前目錄」讀 `.gitattributes`,所以 git 呼叫的目前目錄設成 git 目錄本身(裡面不會有這個檔);git 2.42 起裸庫改讀 `attr.tree`(預設 HEAD),另把它指到空樹,使用者全域的屬性檔指到 `/dev/null`。結果是指紋只看樹裡的內容:被設成 `-diff` 的文字檔照文字比,真的二進位檔(內容有 NUL)照 git 自己的偵測記物件編號。給判定者的 diff 走同一支,判定者也讀得到這種檔的內容。`$GIT_DIR/info/attributes` 照舊讀(本機設定,兩台機器不同只會多列)。
   - **二進位檔、子模組**(被設成 `-diff` 的文字檔 2026-10-14 起照文字比,見下面「不讀工作樹的屬性檔」):diff 帶 `--full-index`;`_patch_file_changes` 本來就對「Binary files … differ」改記 `index` 行裡改後那一邊的物件編號(帶 `--full-index` 才是完整編號),子模組的「Subproject commit」行是一般增刪行,照算。所以不另外判二進位。這些檔主線改了也會讓指紋變,方向是多列。型別變更(`--raw` 狀態 `T`,例如一般檔變符號連結)那篇退回 `v1`。
   - **選項的來源**:「釘住 hunk 切法」的兩個旗標(`--inter-hunk-context=0 --diff-algorithm=myers`)抽成一個常數,筆記形狀閘那兩份既有的 diff 選項與這裡共用;指紋用的這組在現有給判定者組 diff 的 `_NOTE_REREAD_DIFF_ARGS` 旁定義、由它延伸;git 呼叫用 `_lens_git`(它有逾時參數,`_ns_git` 沒有)。全域選項放在 `diff` 之前(`--literal-pathspecs`、`-c core.quotePath=false`、`-c core.precomposeunicode=false`、`-c diff.suppressBlankEmpty=false`、`-c diff.indentHeuristic=true`——放在 `diff` 之後 git 會回 129,r1 兩席實測),diff 選項是 `--no-ext-diff --no-textconv --no-color --no-renames --full-index --submodule=short --ignore-submodules=none --diff-algorithm=myers --inter-hunk-context=0 -U3` 加已釘的前綴(`--raw` 那次也帶 `--submodule=short --ignore-submodules=none`)。`core.precomposeunicode=false` 讓 git 照原樣位元組比對路徑:macOS 預設會把路徑轉成 NFC,樹裡存 NFD 時傳原樣路徑也會得到空 diff,Linux 沒有這個轉換,不釘的話兩個平台算出不同指紋(r3 邊界席實測)。`.git/info/attributes` 讓某支檔在一台機器上變成 `-diff` 的情形照樣會讓兩台機器算出不同指紋,只會多列,不另處理(使用者全域的 `core.attributesFile` 2026-10-14 起指到 `/dev/null`,見下面「不讀工作樹的屬性檔」)。
   - **位元組原樣**:git 輸出以位元組讀、用 `surrogateescape` 解碼再編碼回去雜湊,不用 `errors="replace"`(那會把不同的非 UTF-8 位元組變成同一個字)。
   - **大小上限**:跑 diff 之前,用 `git cat-file --batch-check` 一次看清單裡每支檔兩邊的物件大小(新增檔的舊側、刪除檔的新側是全零編號,跳過;子模組的編號在本 repo 查不到,也跳過),任一邊超過 32 MB 那篇退回 `v1`、不跑 diff。上限看的是檔案大小:本 repo 最大的兩支是 `scripts/test_lumos.py` 約 5.5 MB、`scripts/lumos` 約 3.2 MB,對它們跑 diff 約 0.05 秒,所以上限要留足空間,只擋真的異常的大檔(r3 邊界席:原本的 4 MB 會讓 `test_lumos.py` 的 9 篇筆記永遠退回 `v1`)。`--raw` 加 `--no-abbrev`,物件編號是完整的。
   - **快取**:逐檔結果放進那一次掃描的 `scan` 裡,鍵是(分岔點、頂端、原樣路徑);一次推送多個 ref、測試在同一個程序裡跑很多暫存 repo,都不會互相污染。
2. **全部「未改」就退回 `v1`**:候選是用範圍起點算的,指紋是用分岔點算的,兩者可能不同,會有「是候選、但 about_code 每一項在分岔點..頂端都未改」的筆記(這次把某檔移出 about_code、分支先改又改回、手動給的範圍很寬)。這種筆記的 `v2` 會是一個跟程式版本無關的常數,一旦記過一次,之後任何同形狀的分支都會被當成已對照——所以整篇改用 `v1`(r1 邊界席)。
3. **分岔點只有一種算法,跟推送參數無關**(回應舊否決理由;推主線例外,見本點最後一條):手動代碼審的預設起點那支函式 `_codeloop_default_base`(主線候選照推送閘的 `_push_mainlines`,外加本機 main/master;多個共同祖先照 `_push_pick_base` 取歷史最長的)的本體,搬到推送起點那一區成為共用函式 `_lens_default_base(repo_root, tip=None, include_local=True)`,`_codeloop_default_base(repo_root)` 留成呼叫它的薄包裝(行為不變,代碼審判定唯一的呼叫點與 7 支既有測試照舊):
   - `tip=None`:跟現在一樣看 HEAD 與目前簽出的分支;
   - **回頭重讀傳 `include_local=False`**:主線候選只收遠端那幾個,不加本機 main/master。本機 main 上還沒推出去的提交沒有任何一次推送替它重讀過,把它算進主線,那段改動就沒人對照(r2 正確性席);只有本機主線、沒有遠端主線時,算不出分岔點,退回 `v1`。因此「推本機 main、上面有還沒推出去的提交」時,分岔點是遠端主線,那幾個提交照樣算成要對照的改動、走 `v2`——它們就是作者自己的改動;只有頂端已經在遠端主線上時,分岔點才等於頂端、退回 `v1`;
   - `tip` 是一個提交編號時,「這條分支的上游遠端」改成看「指向這個提交的本機分支」:恰好一條就用它登記的上游遠端;零條或多條就跟現在沒有分支時一樣(有 origin 用 origin、只有一個遠端用它)——不看目前簽出的是哪條,這樣結果只取決於 refs 與頂端,跟在哪個工作樹、簽出什麼無關。`merge-base --all` 也改對 `tip` 算。
   - 回頭重讀一律傳解析好的提交編號。所以手動 prepare 與推送前 check 在同一份 refs 狀態、同一個頂端下算出的分岔點必然相同。舊理由說的「起點算法可能不同」是指範圍起點:兩個子指令都經 `_note_audit_start` 取起點,不帶推送參數走 `_lens_push_base`(給定的起點在本機找得到就原樣用),帶推送參數走 `_push_range_start`;那個起點照舊只決定「誰是候選」,不進指紋。
   - 為什麼不用 `_push_range_start`:它吃 `--push-remote`、`--pushed-ref`,手動 prepare 沒有這兩個值,正是舊理由說的分歧來源。這個新消費者登記進 [[Issues/推送前其他閘的範圍在合過主線時會多算]] 的收斂清單;那篇 Issue 與 [[Issues/預設起點與名冊人數收尾小問題]] 講的是同一支函式,`--short` 與分支、標籤同名的問題照那篇 Issue 的條件另修,本計劃不併入,在兩篇 Issue 互相連結。
   - 已知會變的情形(都是多列方向,不擋正確性):fetch 之後沒 rebase,分岔點不變;遠端追蹤 ref 比分支裡含的主線舊時,分岔點落在舊的追蹤 ref,別人的改動被算進來、指紋跟著變,只是多列;交叉合併有多個共同祖先時照歷史最長取。
