# 世界解重新註解2026-10_節點內容_調研

> 白話:這篇問的是「一篇筆記該長什麼樣、怎麼標,下一個沒脈絡的 AI 才用得上」。世界各家(Claude Code、Cursor、Copilot、Codex、Kiro……)的脈絡檔都收斂成「純 Markdown 加載入範圍」,幾乎沒有出處、時效欄位;受控實驗顯示寫進程式推得出的東西沒用、還多花約兩成成本,這跟 Lumos「程式碼推不出的才寫」同方向。世界比 Lumos 多走一步的地方有三個:句子綁程式位置並在使用前驗證(GitHub Copilot Memory)、決策附「怎麼確認仍被遵守」(MADR 4)、「當初寫錯」與「後來被取代」分開標(Wikidata)。最該先做的是:讓單句綁程式錨點、只把錨點變了的那一行送回頭重讀;把建檔骨架換成現行前綴;替決策補確認方式(或改掉紀律範本裡說決策有測試把關的那半句)。所有關於 Lumos 現況的判斷都經 2026-10-11 對 repo 逐題核對,研究筆記說錯的地方已標明改正。

本篇是這一輪九類重新註解的第 1 類,總表與跨類排序在 [[Projects/世界解重新註解2026-10_總覽_調研]]。檢索排序、推播屬第 2 類,機械閘本身屬第 6 類,這裡只在對位時點到。

## 這一類在問什麼、Lumos 現在怎麼做

本類問三件事:筆記裡該放什麼(判準)、每一句怎麼標出處與時效(標記)、標了之後誰來發現它過期或寫錯(檢查)。Lumos 現在的機制:

- [[Systems/lumos-cli-write]]:筆記開頭欄位、摘要單行、決策增改翻一律用指令寫,寫後自驗、原子替換、上鎖;也管 `lumos new` 的建檔骨架。
- [[Systems/筆記內容閘]]:提交時看新寫的行有沒有照「一行一類」的前綴與方括號格子寫法;擋新寫的程式行號引用、擋沒帶來源的現況行。
- [[Systems/筆記內容審]]:讓 AI 判定者判一句是「程式答得了」還是「程式答不了」;以及推送前的「回頭重讀守檔筆記」(把這次程式改動和家筆記一起交判定者,問哪幾行不成立)。
- [[Systems/存量漂移守衛]]:推送時與手動掃描,抓狀態改了舊句沒跟、程式名稱已刪筆記還在講、回頭條件或撤除條件已經成立。
- [[Systems/check-j-regen-guard]]:從程式重建的筆記,每條摘要必須標來源(程式位置、提交、推測、佚失四級),擋瞎編。
- [[Systems/check-n-recomputable]]:數量標記,讓筆記裡的數字能被工具重數。
- [[Systems/check-u-overgeneralization]]:抓「把單一模組做法寫成全系統通則」的過度概化。
- [[Systems/check-y-symbol-existence]]:筆記點名的方法、類別在程式裡找不到就提醒。
- [[Systems/check-t-sentinel]]:合約行(`★INVARIANT★`)必須綁測試與審計的健檢一族。
- [[Systems/節點還原]]:舊專案冷啟動時「需要才產、推測必標、出口交叉審計」的七步還原法。
- [[Systems/外部對照-code衍生wiki]]:記錄 Lumos 跟「從程式自動生成 wiki」這類工具的分工定位。
- [[Systems/core-invariant-baseline]]:跨專案核心知識被改時要人核可的基線守衛(擱置中,只有設計)。
- [[Systems/ablation-lumos-first]]:情境探針的有/無消融儀器(結果檔有效性、缺場補跑、統計合併)。

另有幾項是寫法規定、不是獨立節點:`RULE:` 行要寫齊 `[since:]` `[retire:]` `[confirmed:]` 才能挑戰程式碼;現況行要帶 `[來源:]` `[confirmed:]`,可選 `[recheck:]`;回頭條件分日期式與條件式(`[when-file:]` 等五種);決策四欄與翻案連鎖帳;Issue 四段(症狀、根因、怎麼繞、什麼條件算修好);自足性審計(乾淨 agent 只讀筆記還原脈絡)。單句時間戳在 [[Projects/宣稱級時間戳_計劃]] 被裁定不另立機制。

本類兩個未結的大事故是判斷缺口的背景:[[Issues/筆記把程式現況寫進脈絡而漂移_rtb實測回饋]](rtb 抽 55 句現況斷言,可判的 54 句有 22 句已跟程式對不上,41%;健檢只抓到 1 句)與 [[Issues/存量筆記漂移三種機制_rtb根因回饋]](20 處真漂移裡 9 處是「同篇只往後加、前面舊句沒人回頭改」)。

## 世界解註解

證據強度:A 受控實驗或方法公開的基準、B 生產數據或廠商自報、C 實務經驗、D 行銷宣稱。註解深度:讀碼、讀全文、讀官方文件、二手(只讀摘要頁或搜尋摘要)。研究筆記標「未複驗」的數字照標。

**W1. ETH Zurich〈Evaluating AGENTS.md〉(AGENTbench)**
- 出處與日期:arXiv 2602.11988,2026-02-12。深度:讀全文。
- 運作:在 SWE-bench Lite 與自建的 AGENTbench(138 題、12 個本來就有開發者脈絡檔的 Python repo)比「沒有脈絡檔/LLM 生成/開發者手寫」三條件。依正文第 4.2 節:LLM 生成檔成功率平均降約 0.5% 與 2%,成本升約 20% 與 23%;手寫檔除了 Claude Code 之外都讓成功率上升,成本至多 +19%。把 repo 其他文件拿掉後,LLM 生成檔反而 +2.7%——傷害來自「跟既有文件重複」。結論:手寫檔「只寫最低限度的要求」。
- 證據強度:A(每題只抽一次、只有 Python;論文引言與第 4.2 節數字不一致)。
- 關係:**驗證**(推得出、重複的內容沒用甚至有害)+**挑戰**(脈絡檔普遍多花約兩成成本,Lumos 注入的紀律與推播也在付)。

**W2. Agent READMEs:2,303 份脈絡檔實證**
- 出處與日期:arXiv 2511.12884,2025-11-17(NAIST 等多國作者)。深度:讀全文(前 10 萬字,結論章未讀)。
- 運作:分析 922 份 CLAUDE.md、694 份 AGENTS.md、687 份 Copilot 指示檔。CLAUDE.md 有 67.4% 被多次修改、相鄰修改中位間隔 24.1 小時、幾乎只增不刪;手標內容以測試(75.0%)、實作細節(69.9%)、架構(67.7%)最多。作者提出「context debt(脈絡債)」,建議用 linter 對照建置指令與實際腳本。
- 證據強度:A(描述性,未量效果)。
- 關係:**驗證**(世界脈絡檔大多是程式推得出的建置、架構、實作細節,正是 Lumos 要防的形狀);世界的分類表沒有「理由/被否決方案」這一類。

**W3. Khatri〈Do Context Files Help Coding Agents?〉兩代理消融**
- 出處與日期:arXiv 2607.27250,2026-07-28,單一作者。深度:二手。
- 運作:Claude Code 與 Codex、3 個 repo 17 題、288 次評估,用等價檢定把脈絡策略對正確率的效果界在 10–15 個百分點以內;失敗分診顯示代理卡在實作功力,不是缺 repo 知識。
- 證據強度:A(樣本小、等價界寬)。
- 關係:**挑戰**(脈絡檔整體對正確率的效果可能很小);但它沒分內容類型,留下「只有程式推不出的規則才有效」的空間。

**W4. McMillan〈Instruction Adherence in Coding Agent Configuration Files〉因子實驗**
- 出處與日期:arXiv 2605.10039,2026-05-11,單一作者。深度:二手。
- 運作:1,650 個 Claude Code 對話、16,050 個函式級觀察,測檔案大小、指示位置、階層或扁平、相鄰檔矛盾四個變數對遵從度的影響:全都沒有可偵測效果,大小與矛盾兩個虛無有 Bayes 因子支持;最大的效果是同一對話每多寫一個函式,遵從勝算降約 5.6%(事後發現)。
- 證據強度:A(只量遵從、兩個 TypeScript codebase)。
- 關係:**挑戰**——Lumos 格子寫法的正當理由只能是「機器查得出過期」,不能延伸成「這樣寫 AI 比較會照做」。

**W6. GitHub Copilot Memory:帶引用、用前驗證、不用就過期**
- 出處與日期:工程部落格 github.blog〈Building an agentic memory system for GitHub Copilot〉2026-01-15;官方文件 docs.github.com 的 copilot-memory 頁,讀取 2026-10-11。深度:讀官方文件(兩篇全文)。
- 運作:代理存 repo 範圍的事實,每條四欄:主題、事實、程式位置引用(檔:行)、為什麼值得記。套用前先去看引用位置還支不支持;矛盾或位置不在就存更正版,成立且有用就重存續命;28 天沒被驗證使用就自動刪。植入「引用指錯」的假記憶做對抗測試,部落格稱代理能一致驗出(無量化)。
- 證據:生產 A/B,coding agent PR 合併率 90% 對 83%、code review 正面回饋 77% 對 75%(p<0.00001)。

**W7. Zep/Graphiti:雙時間軸、衝突才失效、舊的不刪**
- 出處與日期:github.com/getzep/graphiti(commit 964bb11,2026-10-10);論文 arXiv 2501.13956,2025-01。深度:讀碼+讀全文。
- 運作:每條事實邊帶「何時成立/何時不再成立」與「何時寫入/何時被系統判失效」;新舊事實是否矛盾由 LLM 判,但提示詞寫死規則:「除非新事實明確使舊事實為假,絕不標矛盾」「不要只因較新、日期較晚、標題寫『更新』就推論矛盾」「做了某專案的工作不等於推翻他是負責人」;判定後的失效由確定性程式執行。未來式句與軟期限另有正則處理,不算失效。
- 證據:論文 LongMemEval 時序推理題 36.5→54.1%(gpt-4o-mini),但單場助手題下降;論文自承基準條件不對等。
- 證據強度:B(作者即廠商)。
- 關係:**驗證**(Lumos 決策層已是「衝突觸發失效、不覆寫留史」)+**可借鏡**(判定者提示詞的三條防誤判規則)。宣稱級時間戳計劃引的「58.1 對 21.7」在 Zep 論文找不到對應數字,據稱出自 neo4j 部落格,未複驗。

**W10. ACE〈Agentic Context Engineering〉**
- 出處與日期:arXiv 2510.04618,v3 2026-03-29(ICLR 2026)。深度:讀全文(前 10 萬字)。
- 運作:脈絡是一條一條帶 id 的小條目,各有「被標有幫助/有害」計數;更新是局部差分,合併用非 LLM 的確定性邏輯。實驗:反覆整篇重寫會「脈絡塌陷」——第 60 步 18,282 token、準確率 66.7,下一步縮成 122 token、掉到 57.1,低於不調適基線 63.7。沒有可靠回饋時會退化。
- 證據強度:A。
- 關係:**驗證**(逐條、確定性合併、不整篇重寫,是 Lumos 用指令改單行的科學理由)+**延伸**(行級有用/有害計數)。

## 世界證據對 Lumos 做法的挑戰

1. **脈絡檔整體效果小、成本高**(W1、W3):Lumos 注入紀律、改檔前推播、合約置頂都在付成本;主線唯一一次消融(2026-09-02)已被標「只算歷史」,也沒收 token。要量淨效益與成本,不只量「有沒有先查圖譜」。對應候選 7。
2. **「推得出就不寫」不是世界唯一解**(W6):Copilot 正是記推得出的慣例,靠「帶引用、用前驗證、不用就刪」拿到生產正效果。Lumos 自家證據(rtb 41% 漂移、健檢 22 句只抓 1 句)支持的是「**在沒有用前驗證的前提下**」不寫。2026-09-27 明確選了「不留存」、放棄「標好或定期重驗」;如果候選 1、5 做出來,這條禁令值得重裁,而不是永久教條。這是本類最值得重新裁的一條。
3. **格式不提升遵從度**(W4):格子寫法的理由只能是「機器查得出過期」。格子計劃本來就這樣主張(「換到的是機器認得出、擋得住」),寫進任何格式規則的理由欄時都不要引遵從度。
4. **只新增不覆寫是新主流**(W7、W8、W9):Lumos 對 `RULE:` 與決策已這樣做,但 WHY、PITFALL 摘要行原地改,舊說法只在 git。影響多大目前沒有量測(世界也沒找到量這件事的研究)。
5. **單一根因**(W20):PITFALL 的 `[根因:]` 是單值鍵,規格沒寫理由;Lumos 自己的大事故筆記(漂移三種機制)其實已寫成多因素。
6. **檔:行指標**:HumanLayer 推薦、Copilot 實際採用;Lumos 擋新寫的未釘版本行號。Lumos 證據(行號會漂)較強;世界的解法是「用前驗證」而非「禁止」,差在有沒有驗證機制。
7. **整倉、每次提交重生的 wiki**(W21 與其他世界解):在可推得層更省力;Lumos 的價值若不集中在推不出的那層,會被原生功能取代。
8. **「多久沒改就算舊」**:GitHub Next 用「距上次修改超過 90 天」;Lumos 刻意用事件不用時間,並有 2026-09-30 的量測支持(改動時間召回 3/20)。事件式較準也較貴,兩者沒有正面比較過。
9. **宣稱級時間戳的「不立」前提被自家後續數據削弱**:2026-08-18 以「無事故支撐」裁定不立;之後 2026-08-22 狀態表過期事故、2026-09-27/28 rtb 41% 漂移都發生了,2026-10-01 格子寫法又讓 `RULE:` 與現況行帶了 `[since:]` `[confirmed:]`——事實上已是單句時間戳。裁定節點 updated 仍是 2026-08-18,沒有人判過那些事故算不算它的啟動條件。

- **缺口:不分「當初寫錯」與「被取代」**(核對查無):候選 6。
- **缺口:建檔骨架不合紀律、Issue 四段沒人查**(核對查無):候選 2。
- **篇內矛盾**(核對部分有):有「已收尾卻寫待定」等幾條窄的字面規則與手動 fold-check;摘要對正文、有效決策對 WHY 行查無。rtb 第 13、14 項的字面同篇比對 2026-10-07 量到誤報遠多於真報,已裁先不做。延伸做法:健檢新段只列不擋,把「摘要行 vs 正文同主題段」交判定者找互斥敘述;ContraDoc 提醒細微矛盾 AI 也不可靠。
- **自足性審計自動化**(核對只在計劃):[[Projects/自足性審計閉環_計劃]] 設計審三輪未收斂、交付物從未存在;現在只有手動留戳(92 篇 Systems 有 68 篇,最近 2026-10-08)與只提醒的健檢 Check S,空轉週報列出同一提醒最久喊了 95 天沒人接。延伸:世界查無「乾淨 agent 只讀筆記還原意圖」的直接對應,這格 Lumos 是新穎的,但它不自動跑就不會發揮。
- **核心知識同步**(核對只在計劃):目前只驗指針指的檔在不在;基線守衛擱置,條件是消費端超過一個;本 repo 筆記沒有任何 core_refs 欄位。延伸:只把核心索引走原生組織層發佈。
- **行級有用/誤導訊號**(單行層級查無使用紀錄,對照檔查無先例):借 ACE,從代碼審席報告、情境探針、回頭重讀紀錄抽「哪一行被引用、哪一行被判誤導」累積成計數,只用來挑候選刪除行。
- **長節點重整**(核對檔未涵蓋,對照檔查無先例):存量漂移守衛摘要約六十行;只允許逐條合併與作廢,禁止整篇重寫,避開 ACE 量到的脈絡塌陷。
- **`[出處:]` 不分一手、轉述、推論**(核對檔未涵蓋):借 PROV-O 的三分,只做寫法約定;對應 [[Issues/把自己的推論寫成repo明文寫過]](同型第四次)。
- **貢獻給世界的一格**:所有脈絡檔研究都沒把「程式推得出」與「程式推不出」分開量。Lumos 2026-09-18~21 的受控實驗就是照這兩類分的,但留在 lumos-gvc 工作樹;做成公開題組並報等價檢定的效果界,是世界缺的那一刀。

## 筆記與程式或來源對不上的地方

兩邊都沒改,只在此指出;每條附建議處理。

1. **紀律範本對決策紀錄的說法**
   - 哪篇:注入 CLAUDE.md 的紀律範本〈怎麼用〉第 3 條。
   - 原句大意:決策紀錄與合約行「有獨立審計與綁定測試把關」,所以 `RULE:` 才需要用近期確認來補。
   - 實際:程式只對合約行要求 `[test:]` 與 `[audit:]`;決策條目沒有測試綁定、沒有審計欄,連決策區裡手寫的 `[test:]` 都不在掃描範圍。圖譜裡沒有任何決策條目帶確認類欄位。
   - 建議:做候選 3,或把那半句改成只說合約行;並開一篇 Issue 記這句錯在哪。
2. **建檔骨架仍是舊前綴,而且有測試固定**
   - 哪篇:lumos-cli-write 管的建檔範本;紀律範本〈寫筆記時〉前綴表;手冊「Issue 要四段齊」。

## 誠實界線

- **Lumos 現況以 2026-10-11 核對為準**:每題由一位核對者讀程式、在暫存複本跑唯讀指令與小實驗,再由沒拿到結論的第二席用原題重查。研究筆記與核對衝突時本篇採核對,改掉的地方:①「只有重建節點有程式位置標記」改為「部分有」(撤除條件、條件式回頭條件、數量標記都綁程式東西,只是不看內容);②回頭重讀只涵蓋「同次推送也改了的家筆記」,研究筆記沒寫;③自足性審計閉環確定「只在計劃」、從未實作;④有/無消融確定量了成敗、沒量成本,而且結論已標歷史;⑤格子必有鍵是提醒不是擋;⑥讀取帳確定沒有讀者,且排了 2026-11-19 退場;⑦依賴條件不是全無,有字面湊法。
