# CI加速_計劃

白話:CI 慢在「全套測試」那一步——四份測試擠在同一台 GitHub 機器上,現在要 32 到 38.5 分鐘,工作上限是 45 分,快被砍了。這次把全套拆給多台機器同時跑,目標 10 分鐘內。測試一條都不少,Linux 上跑的保護也還在。原本一起考慮的「主線不重跑全套」經設計審發現會漏掉看提交歷史的測試,Enzo 裁定不做。

依據:Enzo 2026-10-06 對話裁定(先「1 跟 2 一起做」,設計審 r1 後改「只做方案 1」)。repo 公開(GitHub 標準機器不另收費);主線沒有分支保護(改工作名稱不會卡合併)。

PRIOR-ART: GitHub Actions 的 `strategy.matrix` 把同一個工作分給多台機器(業界拆測試的標準做法,pytest-split、Jest `--shard` 同一招)。同專案:測試執行器早有 `--shard i/n`(排序後輪流分配,`t_runner_shard_partitions_completely` 守聯集完整);推送前掛鉤與 CI 共用;純文件推送只跑文件子集([[Systems/bound-tests-gate]] 的 suite 機制)。
RETIRE-IF: 全套在 CI 的最慢一個工作連續一個月低於 5 分鐘,而且改回單一工作也在 10 分鐘內,撤掉多台拆分(多台的代價是失敗訊息分散在好幾個工作、每台各裝一次環境)。

## 範圍

- 做:CI 拆成三個工作——
  - `prep`(準備):編譯檢查、3.9 語法守衛、SyntaxWarning 閘、決定測試範圍,用 job 層級 `outputs:` 輸出 `suite`(full 或 docs)與 `graph`(純文件推送裡有沒有圖譜筆記,有的話文件子集加 `--graph`);純文件推送時文件子集就在這個工作裡照現在的寫法跑(子集很小,不值得分機器);
  - `shards`(全套測試):`suite` 是 full 時才跑,多台機器同時跑,每台跑一份或幾份;
  - `gates`(後盾):自主迴圈測試、健檢、代碼審留痕閘、筆記形狀閘、存量漂移檢查、回頭重讀提醒、錨點驗證。
- 做:每個工作各自 `actions/checkout`(`fetch-depth: 0`)、合併請求事件補本機 main(`git branch --track main origin/main`)、裝 Python 3.14——工作之間不共用機器,以前靠同一台機器前一步留下的東西都要各自重做。
- 做:每個工作設 `timeout-minutes`(prep 15、shards 依實驗結果、gates 20),不吃 GitHub 預設的 360 分。
- 做:機器數與每台跑幾份,先用真的 CI 量出來再定(〈做法〉0)。目標:全套那一步在 10 分鐘內。
- 不做:主線推送跳過全套(見摘要第二行)。
- 不做:改測試執行器的切份演算法(輪流分配不保證每份耗時一樣,實驗量最慢那份)。
- 不做:Windows 機器上的 CI(另案)。
- 不做:改給消費專案的 CI 步驟片段(lumos 只給 note-shape、note-audit、drift check 三段貼進既有工作的片段,沒有整份範本;rtb 維持單一工作)。

## 做法

0. **先量**:開實驗分支(只放實驗用的兩組 matrix,量完關掉不合併),試 8 台各跑 1 份(`--shard i/8`)、4 台各跑 2 份(同一台背景跑兩份)兩組,每組至少跑兩次(GitHub 共用機器耗時會抖),記下每次最慢那個工作的分鐘數與整次牆鐘時間;選最快、又不超過 10 分鐘的那組,`shards` 的逾時上限設成量到的最慢值的兩倍。量到的數字寫進本篇〈實作紀錄〉。
1. **拆工作**:
   - `prep`:現有的編譯類三步與「這次推送要跑哪個測試範圍」那步搬進來;純文件推送時接著跑文件子集(照現在全套那步的 `--suite docs` 寫法,同一台切 4 份)。
   - `shards`:`needs: prep`、`if: needs.prep.outputs.suite == 'full'`;`strategy.matrix` 用一個清單列出每台要跑的份數編號(例:`shards: ["1 2", "3 4", …]`),分份總數 N 寫在 matrix 旁同一個 `env` 或步驟內一處;`fail-fast: false`;每台對自己那幾份背景同時跑,失敗片段照現在的寫法印。
   - `gates`:`needs: prep`(不等 `shards`,兩者同時跑——以前全套紅了後面就不跑,現在後盾照跑,資訊變多);後盾那幾步照搬:每步的 `run:` 內容、`if:`、`continue-on-error:` 逐字不改,`env:` 裡讀前一步輸出的 `${{ steps.suite.outputs.* }}` 改成 `${{ needs.prep.outputs.* }}`,YAML 註解可以改(拆分後變假話的要改);步驟順序照原樣(筆記形狀閘在錨點驗證之前、存量漂移檢查的下一步緊接回頭重讀提醒);縮排跟現在一樣(步驟在 6 格、`run: |` 在 8 格),既有測試用這個縮排切步驟;不新增含「note-audit check」字樣的註解或步驟。自主迴圈測試照原樣留在 `gates`,靠 `SUITE` 自己決定跑 `-k real_claude_md` 子集或全部(實作時改的:這樣它的 run 與 if 完全不用動)。
2. **寫回圖譜與註解**:拆分後變假話的句子一併改——
   - [[Systems/bound-tests-gate]]:「CI 的全套測試改成切 4 片同時跑」那行(改成多台機器、附量測數字);「CI 設 LUMOS_SKIP_BOUND_TESTS=1(CI 已跑全套)」那句的「已跑全套」改成「全套在另一個工作同時跑」;
   - ci.yml:開頭 `timeout-minutes: 45` 那行註解、存量漂移檢查步驟註解「全套測試在這步前面(既有安排,沒搬)」、代碼審留痕閘 `LUMOS_SKIP_BOUND_TESTS` 那行註解;
   - [[Systems/存量漂移守衛]] 裡講「全套測試在 drift check 前面」的句子(若有);
   - 實作時 grep「CI」「全套」「切 4」「同一台」掃一次圖譜,有講 CI 單一工作跑法的句子都列進〈實作紀錄〉並處理。
   - 推送前掛鉤 `scripts/hooks/pre-push` 印給人看的訊息裡講 CI 怎麼跑的句子(例:「CI 會兜底」)也掃一次;掛鉤自己的跑法不改。

## 實務隱患

- **拆成多台後失敗訊息分散**:每台各自印失敗片段,GitHub 介面上每個 matrix 工作分開看;`ci-wait` 記帳時的失敗步驟取自 jobs API(`_ci_failed_step` 用分號串起多個),多個工作同時紅時都會列。
- **既有測試與健檢對 ci.yml 的字串檢查**:大約 9 支測試讀本 repo 真的 ci.yml(逐字比對步驟內容、步驟順序、縮排、`python-version`),健檢 `_ci_jobs_calling_without_full_history` 檢查呼叫閘的工作有沒有 `fetch-depth: 0`;後盾步驟的指令、順序、縮排照舊,所在工作帶完整歷史。
- **測試在多台機器上的狀態互相干擾**:每台是獨立機器,沒有共用磁碟;快取檔名本來就按份數分開(`test-cache-shard{i}of{n}.json`)。
- **自我治理(改的是治理機制本身)**:這次改的是 CI 這道最後後盾怎麼跑,不是被它守的東西;改壞了不會有更外層的東西抓到。所以 ci.yml 的形狀有測試釘住([S1]);上線後第一次主線推送人工看一次各工作耗時與日誌(〈實作紀錄〉記結果,見下面回頭條件)。

- 已排除:金流:只改 CI 設定
- 已排除:對外送出:不送資料到 GitHub 以外的地方,CI 本來就跑在 GitHub
- 已排除:不可逆:CI 設定可以還原,沒有寫任何資料
- **守衛面(沒排除)**:CI 是 `--no-verify` 的最後一道後盾;拆工作時漏搬一道後盾、或某份測試沒被跑到,就等於放寬了守衛——[S1] 釘住後盾步驟全在、份數編號完整。

## 驗收條款

- [S1] 當讀 ci.yml 時,全套測試應 在 matrix 工作裡、matrix 清單裡的份數編號合起來剛好是 1 到 N 各一次、`fail-fast` 是 false、只在 suite 是 full 時跑;後盾那幾步(健檢、代碼審留痕閘、筆記形狀閘、存量漂移檢查、回頭重讀提醒、錨點驗證、自主迴圈測試)應 都在 `gates` 工作裡、`run:` 內容與 `if:` 跟拆分前那一版逐字相同(比對基準是測試裡寫死的拆分前那一版步驟指紋)、順序相同;三個工作 應 都有 `fetch-depth: 0` 與 `timeout-minutes` [test:t_ci_yml_matrix_and_gates_shape]
- [S2] 當 CI 的全套測試跑在多台機器上時,最慢那個工作 應 在 10 分鐘內完成 [manual:看實驗分支與上線後第一次 CI 的各 matrix 工作耗時,記進實作紀錄]

## 回退

還原本案的提交即可:ci.yml 回到單一工作;沒有新指令、沒有寫任何狀態或資料。

## 天花板

1. 測試切份是按名字輪流分,不按耗時;某一份剛好分到很多慢測試時,那份就是瓶頸。
2. 主線推送照跑全套,每個功能的 CI 總時數仍是合併請求一次加主線一次;方案 1 讓每次都變短,但次數沒變。
3. `ci-wait` 紅燈時記帳抓的是失敗日誌的尾端;好幾個工作同時紅時,帳上未必有每一份的失敗斷言,要到 GitHub 介面看各工作日誌。
