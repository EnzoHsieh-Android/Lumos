# 每輪修補差異派工_計劃


白話：日後代碼審的修訂輪，讓新審查員看清楚這一輪補了哪些地方，並核對原本正常的路徑是否仍正常。

WHY:第一步落在派工手冊與範本，借用既有版本記錄與 Git 差異 [出處:2026-10-06 使用者開始授權與每輪修復副作用調研] [因:需要的是聚焦修補副作用的材料與問法，現有工具足以產生資料]
PRIOR-ART: 借用 Gerrit 兩版比對與 Git diff，來源 https://gerrit-review.googlesource.com/Documentation/user-review-ui.html 與 https://git-scm.com/docs/git-diff；手冊採用既有 fix-check base/head，不新增 CLI 或套件。
RETIRE-IF: 試行十個有修補的迴圈後，修補鏡頭零個可重現命中且準備材料中位數超過五分鐘，簡化為短版提問；數值為候選觀察值，以既定第0步觀察事件核對。
REVISIT:2026-10-20 在第0步觀察入口核對修補鏡頭實際使用、命中與成本；未量測不得宣稱縮短審查輪數。

## 範圍

改三份技能來源文件：代碼審手冊增加派工前材料步驟；共用範本 §3 增加只在修訂輪使用的鏡頭；速查只指向唯一詳細做法。設計審與其他段落保持原樣。

修補差異起點使用上一輪派工單 base_commit；終點是已提交修補的固定版本。核對 fix-check 回報的 base/head，起點不同就先釐清再產材料。多份派工單、欄位缺漏或讀取失敗均須明寫材料不可得，不猜上一個提交，不把空材料當沒有問題。

兩版比較不用 merge-base 縮小差異，因為那會漏掉非祖先版本的內容。非祖先、換基底、合併其他變更要附明確的歸因界線。一般祖先關係也不能單靠版本關係證明所有改動都是修復。

每輪材料保留完整改動可讀入口、修補差異、兩端提交與樹指紋、patch 指紋；只在固定版本查完整函式和呼叫者。完整原始差異歸檔，必讀範圍覆蓋產品碼、技能、測試、設定與決策；純歷史紀錄逐檔列為archive_only且保留查核入口，不能按目錄前綴排除可執行檔。材料總量超過原1800行上限就拆席／拆範圍，不只算新增的差異。席位不讀上輪報告或作者的因果結論。

下一輪必問：原問題是否解決？原本正常路徑是否維持？新發現是否有修前修後證據？不能比較、測試未跑與環境差異明寫未判定。這是人工判讀步驟，不是證明不會出新問題。

## 條款

- [S1] 當代碼審進入修訂輪時，手冊應給出兩端固定版本、修補差異、完整改動入口與材料總量界線的準備步驟，並由範本引用同一份定義 [manual:逐條核對三份技能來源文件]
- [S2] 當起點缺漏、歧義或與修正關卡不同時，手冊應明寫不可猜版本或將材料不可得當空差異；換基底與一般祖先關係應各有歸因界線 [manual:用臨時Git版本核對同基底與非祖先兩種差異]
- [S3] 當審查員收到修訂輪材料時，範本應要求核對修復效果、正常路徑保留及新發現的兩版證據；未判定不得說成無回歸 [manual:用修復回歸、原有漏查與證據不足三種案例核對提問]
