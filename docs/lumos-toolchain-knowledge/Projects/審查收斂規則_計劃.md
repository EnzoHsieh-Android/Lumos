# 審查收斂規則_計劃

> 白話:合約審計的第 3 問「構造一個違反保證、但綁的測試照過的壞法」沒有終點——審計員只要肯重寫設計,永遠構造得出來,只能靠人喊停。改成:照 2026-10-13 那次人裁的判準,把反例分成「局部退化」(一定要被測試殺掉)與「繞過設計」(記成殘留、交給代碼審),而且分類不由想收斂的那一方說了算;殘留用一個獨立標記寫在合約行上,派工鏡頭看得到、碰到它的改動一律走高風險代碼審。原本也想讓資安席修補輪只看變過的檔,審查後決定不做(見〈不做〉)。

## 緣起

- 2026-10-13 後端示範:合約審計連三輪都推翻三條合約,第 3 問每輪補完測試又構造得出新的壞法,最後由需求方人裁收尾(示範計劃決策 d12:修 bug、補實際會發生的三類,刻意繞過設計的三種寫法列為已知殘留)。同一次示範,代碼審第三輪資安席把整份 35 支檔重讀一遍,只因為第二輪修補動了 6 支。出處:使用者 2026-10-14 問「這次示範有什麼 lumos 可以改進」時列的第 5 條;[[Verification/2026-10-13_後端示範交付]] 改進候選第 7 條。
- d12 的人裁:「實際可能發生的退化都補測試;刻意繞過設計的改法屬於代碼審要擋的範圍」。本計劃把它寫成照做的規則,同時守住本 repo「提出的人不准自己認證」的規矩(`skills/lumos-project-notes/reference.md` 審計段:讓提出者自己評必手下留情)。

PRIOR-ART: 變異測試(mutation testing)的業界做法是只用局部改動當壞法,並承認「等價變異」(改了但行為不變)殺不掉、要人工排除;本 repo 的 `guard kill` 破壞配方是同一類工具,借它記錄並真跑局部退化。殘留標記照本 repo 行內標記「一個方括號一個欄位、一個正規式」的慣例(`[test:]`、`[audit:]`、`[kill:]`、`[rollback:]`)另立 `[residual:]`;解析「節點#決策」重用既有的決策指標解析與「節點在、決策在、沒被標無效」的判斷。
RETIRE-IF: 上線後 8 週內,有一次逃逸帳記錄的 `residual_ref` 指到某筆殘留決策、而那個缺陷其實是一個保留設計機制、只是用錯的局部退化——撤回 B 規則,第 3 問回到「構造得出就不合格」。
REVISIT:2026-12-15 數一次:圖譜裡帶 `[residual:]` 的合約行幾條、各指到哪幾筆殘留決策;逃逸帳裡帶 `residual_ref` 的幾筆;照 RETIRE-IF 判。
WHY:「同一反例只准問一次」降為方便,真正的把關改成新增殘留的推送升 high、走高風險代碼審(派工鏡頭把殘留決策與問答附給審查席;只保證跑一輪高風險代碼審,審查席有沒有答沒有機械核對) [出處:代碼審 r3] [因:反例編號是編排者自己取的標籤,r1 換大小寫標點、r2 改字換指紋與刪帳列、r3 換編號與改節點名,字面身分怎麼比都擋不住換一個新名字;把挑答案的那次推送送進一輪高風險代碼審才擋得住] [不選:繼續加字面身分檢查]

## 不做

- 不做「資安席修補輪只看變過的檔」。理由:處置閘判資安席涵蓋,看的是帳上掛的凍結 patch,不是席位實際讀了哪幾支;若派工叫資安席只讀清單、清單又以「帳上看過」推下一輪,就會出現一支檔從頭到尾沒有資安席真的讀過、閘卻判涵蓋的情形——這正是 [[Projects/代碼審資安席_計劃]] 第一輪用「同檔名內容改掉」實測出來、改成比內容才堵上的洞(r1 整合席)。現行「每輪整份重讀」是那道防線的代價,保留。上限輪資安席抓到問題、折掉之後,判定的仍是那一輪的凍結 patch,不會卡住,所以也沒有要解的收斂問題。

## 做法

1. **反例分三種去向**(寫進 `lumos-project-notes` 的〈[audit:] 獨立合法性審計〉五問段;派工時照那一段的防應試化規則改述措辭,不逐字貼):
   - **局部退化,殺得掉**:保留設計點名的機制(鎖、約束、冪等鍵查詢、交易邊界……),只是用錯或漏用——漏呼叫、條件寫反、範圍或順序錯、錯誤處理吞掉、少了一條約束、新增的一條路徑沒經過那個機制。審計員附一條 `lumos guard kill-add` 的配方(先提交,`kill-add --try` 的試跑是弱證據),補測試直到 `lumos guard kill` 對它是 `killed`;`survived` 繼續補,`drifted` 先改寫配方。這是預設去向:分不清的都先當這一類。
   - **局部退化,殺不掉**:努力補過測試,配方仍是 `survived`、`killed_unattributed` 或 `timed_out_weak`,而原因是行為其實等價、只在特定交錯時序才出事而現有測試設施跑不穩、或要多檔多處才寫得出(`kill-add` 一條配方只收一處替換)。記成殘留。
   - **繞過設計**:要改架構或部署形態才做得到(例:把單一資料庫換成多節點並改用程式內互斥、改成另一種儲存的分桶查詢)。記成殘留。
   - 後兩種要記殘留時,一律照第 2 點過第二個獨立代理。殘留決策用 `lumos decision-add` 記(四欄齊),內容逐型列出殘留、每型標明是「殺不掉」還是「繞過設計」與反例編號、寫「第幾輪審計收斂」,尾端寫 `checker:<第二個代理的模型>/<日期>`(決策欄位是單行文字)。
   - **d12 那三型照新判準重分**:「庫存多時另開不加鎖的快路徑」與「拿掉資料庫約束」是局部退化(併發壓測打所有下單入口、檢查資料庫結構都測得到),先補測試;「改用程式內互斥並跑多個節點」屬繞過設計。示範 repo 的 d12 依此修訂是那個 repo 的事,本計劃只在手冊裡用這三型當例子。
2. **分類不由想收斂的一方決定**:分類由審計員(無對話脈絡的獨立代理)做;編排者可以把審計員判成要記殘留的改成「局部退化,殺得掉」(更嚴),不准反過來。要記殘留的每一條,另派一個沒看過審計報告結論的獨立代理,只給那條反例、合約行與它綁的測試,問「這能不能在現有測試設施下穩定測到」。
   - **問過就留痕,而且只准問一次**:新指令 `lumos guard residual-ask <合約節點> "<KEY 子字串>" --case <反例編號> --checker <模型>/<日期> --verdict testable|untestable` 把這次的問答記一筆治理帳事件(閘名 `residual-ask`,帶合約節點、合約行的指紋、反例編號、checker、結論)。同一條合約、同一個反例編號已經有一筆,第二次 `residual-ask` 回 2;判過 `testable` 的反例記在同一把鍵(節點、合約指紋、反例編號)上。**只准問一次是方便,不是保證**:反例編號是編排者自己取的,換編號、改節點名、改合約一個字都問得到第二次。**真正的把關是新增殘留的推送要過高風險代碼審**(第 5 點):派工鏡頭把殘留決策與那幾筆問答附給審查席,換代理重問到想要的答案的那次推送要過一輪高風險代碼審(代碼審 r3;只保證跑一輪審,審查席有沒有答沒有機械核對)。結論是 `testable` 就照它說的方法補測試(回到第一種去向)。
   - 跟既有的穩定性探針不衝突:探針管的是「這條合約合不合法」的判決,這裡管的是反例的分類;兩邊不一致時這裡一律取嚴的那一邊,不另交人裁。這一步寫進審計派工流程(`lumos-project-notes` 審計段),理由引 maker≠checker。
3. **殘留用獨立標記**:合約行尾加 `[residual:<節點>#<決策 id>]`(放在既有標記之後;可以多個,一筆殘留決策一個;節點寫圖譜相對路徑、不帶 `.md`;決策指標的解析重用既有的 `_dref_parse`/`_dref_norm`,格式是它們認得的 `<節點>#d<數字>`)。
   - **新增 `RESIDUAL_REF_RE`,並把 `residual` 加進共用的剝標記正規式 `INV_TAG_RE`**:乾淨宣稱文字、合約定位(`_kill_find_contract`)、家筆記正式行比對(`_guard_formal_line`)、`guard list`、contracts、lint 訊息都經過它;不加的話,帶殘留的合約行跟計劃裡預告的原句比對不相等,轉正與漂移檢查會誤報(r2 正確性席實測)。實作時照 `INV_TAG_RE` 上方註解列的呼叫點逐一確認。
   - **新指令** `lumos guard residual <合約節點> "<KEY 子字串>" --add <節點>#<決策 id> --case <反例編號>…`(加),或 `--remove <節點>#<決策 id>`(拿掉一個);兩者擇一。決策指標只收帶資料夾的全名(例 `Projects/a_計劃#d12`),不收短名(短名日後可能撞名)。寫入流程照 `guard audit` 的形狀:外層拿筆記庫寫入鎖、用 `_kill_find_contract` 定位(子字串對到兩條以上就拒絕)、寫後用 `atomic_write_verify` 自驗。同一個標記已在就回 0 說「已經有了」;`--remove` 找不到那個標記回 2。
   - **寫入當下就驗**:決策指標的狀態用既有的 `_pq_decision_state`,不是 `ok` 就不寫、回 2(找不到、已被翻案、名稱解析不明都算);決策內容要非空;`--case` 列的每個反例編號都要在治理帳裡有一筆這條合約的 `residual-ask`、結論是 `untestable`,而且決策內容裡要出現那一筆的 `checker:<模型>/<日期>`(決策四欄是單行文字,`checker:` 寫在 content 的尾端,用 `decision-add` 寫得進去);合約行要已經有 `[audit:]`(殘留是審計的產物)。
   - **第 3 問的放行與記殘留的順序**:這一問過 = 每個反例都殺掉,或經第二個代理確認測不到(不是「已記成殘留」——記殘留要先有 `[audit:]`,兩句會互卡,代碼審 r1 合約席)。順序:`guard residual-ask` 記問答(判 untestable)→ 五問其餘也過了,`guard audit` 蓋 `[audit:]` → `decision-add` 記殘留決策 → `guard residual <節點> "<KEY 子字串>" --add …`;最後一步寫入當下驗:問答判 untestable、這條合約最近一次 `guard audit` 晚於那個反例最晚一筆問答(比治理帳上兩筆事件的完整時間戳記,`guard audit` 每次都記一筆 `guard-audit`;早於或帳上找不到審計紀錄就擋、叫人照順序重審,代碼審 r2、r3)、決策在且內容含那筆 `checker:`。
   - `[audit:]` 照舊,`guard audit` 重審只換 `[audit:]` 那一段、不碰 `[residual:]`,所以重審不會抹掉殘留。
   - **doctor**:放在既有的「綁了測試卻沒審計」那一段,多驗每個 `[residual:]` 指到的決策狀態仍是 `ok`;找不到時報錯並印「去 <節點> 補回那筆決策,或用 `guard residual --remove` 拿掉標記並重審」。決策跨節點(殘留可以記在計劃節點),doctor 本來就載入整個圖譜,不增加依賴。
4. **派工鏡頭看得到**:鏡頭印合約行時只印前 200 字,戳記常在後半(r1 整合席數過:36 條帶 `[audit:]` 的合約行有 22 條的戳記在第 200 字之後),所以「帶殘留」放進接在後面的徽章(「⚠帶殘留 N 筆」,N 是不同決策的個數),而且不依賴綁定測試徽章的計算(平台設定讀不到時那個徽章不顯示,殘留徽章照樣顯示)。鏡頭讀的是主線版的合約行,同一個分支裡才加的殘留看不到——那種情形殘留決策本身就在這次的 diff 裡,審查席照樣看得到。代碼審派工範本加一句:看到帶殘留徽章,去讀那幾筆殘留決策,那幾型壞法測試抓不到、要靠你看。範圍內新增了殘留或判測不到的問答時,鏡頭另附「這次新增的殘留」一小節與一題逐條必答(代碼審 r4,見〈實作時定下的細節〉)。
5. **碰到帶殘留的合約一律走高風險代碼審**:用一份進版控的小索引 `governance/residual-index.json`(由 `guard residual` 每次加或拿掉標記時重寫:每條帶殘留的合約一筆,記合約節點、合約行指紋、殘留決策指標,與那篇節點當下的 about_code 檔清單,加上合約綁定測試所在的檔)。`pitfalls --diff <起點>..<頂端>` 算風險分級時,讀**起點與頂端兩個版本**的索引(`git show <提交>:governance/residual-index.json`,不載入圖譜,`pitfalls` 分級不讀圖譜的既有決策不動),取聯集;這次改到的檔(含改名的舊路徑與新路徑——檔案清單用 `--no-renames` 取)只要有一支在聯集裡,分級升 high,說明寫「改到帶殘留合約守的程式」(代碼審 r1–r3 補強:綁定測試所在的檔也整檔算;新增殘留、拿掉殘留、縮小殘留守的範圍、索引或檔名清單讀不出、刪改治理帳的 `residual-ask` 列也升 high——見〈實作時定下的細節〉)。
   - 讀起點版本,所以同一個提交把標記拿掉、改程式也躲不掉;直推主線時,起點是遠端上原本的主線,同樣在。讀頂端版本,所以這次推送才加的殘留也算。索引不存在(新專案、沒有任何殘留)就什麼都不做;起點版本的索引 git 讀不出(不是不存在)當成有殘留、升 high(代碼審 r2)。
   - 升成 high 之後,用的是既有的整套機制:`code-loop check` 要求代碼審留痕、推送前掛鉤與 CI 都跑它(`--no-verify` 跳過本機掛鉤,CI 照樣擋);不另寫一道閘,也不碰推送前規格閘。
   - doctor 驗索引跟圖譜一致(每筆對得到一條帶 `[residual:]` 的合約行、about_code 清單與綁定測試所在的檔相同;圖譜裡每個 `[residual:]` 都在索引裡);不一致時報錯並給 `lumos guard residual --reindex` 重建。
   - 過度的那一面(節點管很多檔、跟那條合約無關的小改動也要代碼審)接受:帶殘留的合約本來就是測試守不住的地方。
6. **逃逸能歸因到殘留**:`lumos loop escape` 加選填 `--residual-ref <節點>#<決策 id>`,用同一支 `_pq_decision_state` 驗格式與存在,記進逃逸帳的 `residual_ref` 欄;它加進撤回路徑與 `--list` 的「不准混用」檢查,`--auto` 不支援(自動記帳沒有歸因來源)。`loop escape-stats` 印帶 `residual_ref` 的筆數。RETIRE-IF 靠它量。
7. **要一起改的說法**:`skills/lumos-project-notes/SKILL.md` 的合約行範本、`reference.md` 的五問段與 `[audit:]` 說明與標記清單、`commands/06-代碼審與推送.md` 的 `guard` 指令表(加 `guard residual`)、`docs/methodology/圖譜即合約.md` 講第 3 問、maker≠checker、未審合約檢查的幾處、[[Systems/design-loop]] 講五問與防應試化的 KEY 行、[[Systems/pitfalls-code-loop]] 講風險分級的段落、`skills/lumos-design-loop/templates.md` 代碼審派工段(徽章那句)。防應試化的「定期無表抽考」照舊;抽考時不帶這套分類,比較兩邊結論時把「帶殘留通過」當成「不合格」看,落差才不會被系統性拉大(r1 整合席)。
