# 兩席相反時端出張力（2026-09-09 立案；同日 r1 折入稿——折入 5 席 27 條）

> 白話：兩個審查角度天生會吵——一個說「照這個專案原本的寫法寫」，另一個說「這裡該用比較好的做法」。
> 人已經裁了：撞到時不挑邊，把兩邊都端到人面前（既有怎麼寫、隱患是什麼、建議怎麼改、改了會跟幾個檔不一致）。
> 這篇做的是讓「端上來」不靠人記得：答題時多一個誠實的選項、改動前就有人提醒可能撞、審查席知道撞到時查什麼。

### 衝突今天從哪兩個洞漏掉

1. **答題那一側沒有誠實的選項。** 表態只認 `satisfied`／`na`／`todo`（`_DISP_STATUSES`）。「我看到這題，但刻意沿用專案既有寫法、沒採建議」哪一種都不是，最後被塞進 `na`——工具只驗理由長度，正是裁定禁止的「默默壓掉」。
2. **沒有任何東西會說「這個檔用了鄰居都沒用的做法」。** `_arch_alignment_hints` 只把同層最像的三個既有檔路徑端給架構對齊席；有沒有看出差異全靠那一席，編排者要不要把兩邊併起來講全靠當下記得。

## 設計

### 一、第四種表態 `tension`（張力）

- **形狀**：`{"status":"tension","question":原文,"chosen":"existing"|"suggested","existing":["path:line",…],"hazard":"…","suggestion":"…","evidence":"path:line 或 test:<名>"}`。`chosen` 講這次改動選了哪邊：`existing`＝沿用既有寫法（隱患留著）、`suggested`＝改用建議做法（跟既有不一致）；只認小寫，跟 `status` 同一條規矩（r1 邊界席 B2）。`existing` 是既有寫法的位置，一項一個 `path:line`，**1 到 20 項、每項 ≤300 字**；去重後的路徑數就是「跟既有 N 個檔不一致」的 N。`hazard`／`suggestion` 各自 **≤2000 字**（上限是 r1 外家 F2／通才 G3／邊界席 B4 三席一致：單題核對沒有中途檢查點，無上限的清單會拖垮推送前 20 秒預算）。`evidence` 只在 `chosen=suggested` 時必附，指到這份改動裡採新做法的那一行；**規則同 `satisfied`：`path:line` 或 `test:<名>`／`test:<平台>:<名>`，走同一條驗法**（r1 架構對齊席 A1：同鍵名不得語意窄化）。
- **寫側**（`_dispositions_validate`）：`status` 四值只認小寫，錯誤訊息改成「只認小寫 satisfied/na/todo/tension」；**`_cmd_codeloop_dispositions` 整份形狀壞時印的那行「規則:status 只認小寫…」同步改四值並列出 tension 的必填欄**（r1 通才 G2：那是第二處硬編字串）。`tension` 缺 `chosen` 或值不在小寫兩者 → 錯；`existing` 要是清單、1–20 項、每項 ≤300 字且用既有 `_dispositions_split_path_line` 切得開（絕對路徑、`..`、缺行號照舊拒收）；`hazard`／`suggestion` 各自過既有 `_dispositions_reason_ok`（去空白標點後 CJK ≥10 或總長 ≥25）且 ≤2000 字；`chosen=suggested` 時 `evidence` 必附且過 `satisfied` 同一套切分（`test:` 走 `_dispositions_split_test`）。壞 → rc2 不寫並講原因，跟其他三值同一條路。未知鍵（含樣板帶的 `hint`）照既有不擋、原樣存。
- **讀側**（`_dispositions_verdict` 的 `_one`）：`tension` → **先重驗 `existing` 是非空清單且 ≤20 項**（r1 邊界席 B3：治理帳重建或手改壞的紀錄可能給空清單，零次迴圈不得判過），每項走既有 `_dispositions_check_path_line`（對被推送 sha 的樹驗存在與行號範圍，不驗內容）；`chosen=suggested` 的 `evidence` 走 `satisfied` 同一個分支（`test:` 用 `_dispositions_check_test`）；文字門檻、上限與 `chosen` 值再驗一次（治理帳重建來的紀錄不信形狀：缺欄一律 `str(… or "")` 接住，同 `_lens_dispositions_lines` 的防禦寫法、表態閘 r1 正確性席 f3；`_one` 自己既有的另一道是「任一例外接成該題無法驗證、不整份 fail-open」，r1 正確性席 f1／邊界席 f1，本案沿用）。全過 → `checked+1`，並 append 到新欄 `out["tensions"]`：`{id, chosen, existing, files, hazard, suggestion}`（`files`＝去重路徑數；對外鍵不帶 `n_` 前綴，同 `_cochange_mine` 把 `n_files` 印成 `"files"` 的既有慣例，r1 架構對齊席 A2）。任一不過 → 進 `problems`（擋），訊息帶題目 id 與哪一欄。
- **印法**（`cmd_code_loop check` 人可讀模式）：判定印完（OK 或 BLOCKED 都一樣）之後，`tensions` 非空就在 stderr 多印一段三段式——「⚠ 張力 N 則（兩個審查角度相反，工具只端上來、不裁）」；每則三行：「`<id>` 選了{沿用既有｜改用建議}：既有寫法在 {existing 裡**前 3 個不同路徑**}（共 N 檔）」（r1 邊界席 B5：切原清單會印出 1 個檔名卻寫共 2 檔）、「隱患：{hazard}」、「建議：{suggestion}」；末行「在意的原因：兩邊都留下來才看得見矛盾；誰讓誰由人定，這裡不擋」。`--json` 時放 `verdict.dispositions.tensions`。**rc 不因 tension 改變**：合法 tension＝該題已交代。
- **`--carry`**：`tension` 跟其他人答的值一樣帶過（`_DISP_STATUSES` 判定，不另寫）；帶過來時**明寫 `ent.pop("hint", None)`**（r1 通才 G6：既有是 `dict(prev)` 整包淺拷貝，不剝就會把上一輪的候選提示帶到新一輪）。
- **派工鏡頭**（`_lens_dispositions_lines`）：`tension` 的尾巴印「選 {chosen}｜既有 {existing 逗號串}｜隱患 {hazard}｜建議 {suggestion}」，同既有 200 字截斷。審查席反駁的就是這四欄。（r1 架構對齊席 ⚠：同函式其他三值是簡單串接；編排者裁保留 `｜`——四欄需要分隔，`｜` 在本檔錯誤訊息與筆記 DEP 行皆有既有用法。）
- **治理帳**：事件形狀不變（`dispositions` 物件整包存，新欄自然在裡面；樣板帶的 `hint` 若人沒刪也一起存——這正是候選唯一的持久落點，見〈二〉），事件另加一欄 `candidates`＝這次表態裡帶 `hint` 的題數（r1 接手席 H3）。mapper 白名單放行 `candidates`。`gov --stats` 表態段的桶加 `tension`，印「張力 N」，另印「候選題 N、其中答 tension M」；**死題候選的分母 `_human` 併入 tension**（r1 接手席 H4：8 次 na＋5 次 tension 不能被標成「全是不適用」），判準文字不變（人答 ≥10 且全是 na）。

### 二、`pitfalls --diff` 端出候選（可能撞）

- **母體**：`_pitfall_diff_collect` 走 diff 時另收 `added_lines = {檔: [增行內容…]}`——只收 `+` 行、**且只收 `_stack_changed_ok(檔)` 為真的檔**（r1 通才 G5：`arch["files"]` 的過濾比 `changed_lines` 鬆，少排 `governance/review-reports/` 與簿記檔；不加這道，簿記檔上的候選題會掉出 `stack_questions_applicable`，打破下面的不變量）。既有 `changed_lines`（增刪行，給適用性用）不動：候選看的是「新引入」，刪行不算。
- **算法**：對 `arch["files"]` 裡、且有 `added_lines` 的每個改動檔 F：`sk = _stack_key_for_file(F, repo_root)`（既有簽名兩個必填參數，`.ts`／`.js` 要看 package.json），`sk` 不在 `_STACK_TRIGGERS` → 跳過。F 的增行逐行 `_stack_norm_line`（剝字串、剝行尾註解、跳過以 `#`／`//`／`--`／`/*`／`*` 開頭的行）得 `norm`。對該棧每題 `(qid, pats, _)`、每個 `pat`：`pat` 在 `norm` 命中 → 讀 F 的對照檔（`arch["files"][F]`，≤3 個），逐行同一支 `_stack_norm_line` 後搜 `pat`；**至少一個可讀對照檔、且全部沒命中** → 記候選 `(F, qid, pat.pattern)`。`when_raw`（看字串內容的那幾條）不看：鄰居的字串字面比對沒有意義。
- **正規化的天花板（承認不修）**：`_stack_norm_line` 逐行、沒有跨行狀態，區塊註解內**不以 `*` 開頭的裸行**會被當程式碼（r1 外家 F1／通才 G4 實測 `'   async { // still comment'` 回 `'   async {'`）。這是既有適用性判定同一條天花板；增行來自 hunk 片段本來就無從得知是否在註解內，對照檔雖是整檔也用同一支、兩邊對稱——偏差方向是「對照檔註解裡的字被算成存在 → 少一個候選」，安全側。
- **對照檔怎麼讀**（r1 邊界席 B6）：讀 bytes，`decode("utf-8")` **嚴格**（不用 `errors="replace"`），`UnicodeDecodeError`／`OSError`／檔案 >2 MB 一律記 `unreadable` 並跳過。這是刻意偏離本檔既有「解碼永不失敗」的讀檔慣例：候選要分得出「讀到了沒命中」跟「根本沒讀到」，替換成亂碼再比對會把後者偽裝成前者。
- **輸出**：`arch_alignment["tension_candidates"] = [{"file":F,"question":qid,"patterns":[…],"siblings":[可讀對照檔],"unreadable":[…]}]`，按 (F, qid) 聚合、patterns 去重保序；沒有候選 → 鍵不出現。人可讀：在 `[架構對齊]` 對照檔清單之後印「可能撞：{F} 新增的 {patterns 用／連} 在對照的 {n} 個檔裡都沒出現（這是 {qid} 那題的做法）——沿用既有或改用新做法都用 tension 表態，審查席會查兩邊」，**最多印 6 行**，其餘一句「另有 N 條，`--json` 看全量」（r1 通才 G7：比照既有對照檔清單 `[:6]`）。
- **沒有對照組的檔**（r1 邊界席 B7）：新目錄裡第一個同副檔名的檔，`_arch_alignment_hints` 本來就不收（`sibs` 空），所以沒有候選、也沒有 `unreadable`——這是對照組機制的既有邊界，本案不加訊號；S3 明寫。
- **不變量**：候選的 `qid` 必在 `stack_questions_applicable`——候選來自同一組觸發字命中 F 的增行，F 過了 `_stack_changed_ok`，增行是增刪行的子集，所以該棧那題必適用（超過門檻全問時更是）。測試釘，並用簿記路徑當反例（放在 `governance/` 簿記檔裡的增行不得產生候選）。
- **樣板**（`_dispositions_template`）：有候選的 qid，其適用題 entry 加 `"hint": "候選張力:{F} 新增 {patterns},對照檔 {siblings} 都沒有——刻意沿用既有寫法或刻意改用新做法,status 填 tension"`。`hint` 是資訊欄，validate／check 不讀；寫側原樣存進治理帳（候選的持久分母），`--carry` 剝掉。
- **預算**（r1 邊界席 B8：上限不得切在同一個改動檔的對照組中間，否則「第三個沒讀的對照檔其實有那個字」會變成假候選）：**以改動檔為單位**——最多處理 20 個改動檔（每檔 ≤3 個對照檔＝最多 60 次讀檔），一個檔的對照組要嘛整組讀完、要嘛整組不算；超過 20 個的改動檔不判候選，JSON 帶 `arch_alignment.candidates_truncated: true`，人可讀印一句「改動檔太多，候選只算了前 20 個檔」。單檔 >2 MB 記 `unreadable`。pre-push 熱路徑跑的 `pitfalls --diff --no-lint --json` 也算候選；測試釘檔數與大小上限，不宣稱秒數（r1 邊界席 B9：秒數宣稱沒有測試會翻紅，刪掉）。

## 實務隱患

- **守衛面**：本案動 `code-loop check`，但只**加寬**合法答案（第四種值），不新增任何擋的條件——唯一新的 BLOCKED 是「tension 欄位對不上」（含空清單、超上限），跟 `satisfied` 證據對不上同級，而且寫側已經先擋過一次。合法 tension 永遠不擋（合約候選①）。閘內部錯誤仍走既有 `_gate_failopen`。已排除：pre-push 與 CI 讀治理帳重建的路徑不變（新欄在同一個物件裡）；沒有 tension 的表態檔行為逐位元相同。
- **效能**：兩條路都有上限——表態核對：`existing` ≤20 項、每項 ≤300 字、文字 ≤2000 字，單題最多 20 次 `git cat-file`＋`git show`（r1 三席一致抓到「單題內無中途檢查點」）；候選：≤20 個改動檔、每檔 ≤3 對照檔、單檔 ≤2 MB。跑在 pre-push 熱路徑（`pitfalls --diff --no-lint --json`）上；測試釘上限，不宣稱秒數。
- **併發**：無新寫入路徑；tension 走既有「先寫治理帳再原子寫 marker」，同 sha 重表態後者覆蓋（既有限制原樣）。
- **不可逆**：無。治理帳（`docs/.governance-log.jsonl`）有版控可 git 還原；marker（`governance/code-loop/*.dispositions.json`）**不版控**（`governance/.gitignore` 排除），遺失走既有「marker 優先、沒有退治理帳」fallback（r1 邊界席 B10）。沒有刪任何既有值。
- **對外送出／金流**：無——只寫本機治理帳與 marker、跑唯讀 git 查詢與本機 regex，沒有網路呼叫（五席皆驗過）。
- **假候選**：觸發字有寬的（`\bContext\b`、`\bView\b`），對照檔碰巧沒有那個字就會亮；候選只印一行、不進閘、不進 tier，代價是多讀一行。REVISIT 數「候選題幾題、其中真用了 tension 幾題」。
- **敷衍**：tension 可以填四段廢話——工具只驗對照檔存在與文字長度，同 na 的天花板；派工鏡頭把四欄端給審查席反駁是唯一的第二道。
- **反方向抓不到**：「沿用既有寫法沒採建議」在 diff 裡沒有新字，機械無候選；靠人選 tension。這是承認的天花板，不是待辦。
- **本 repo 自己**：Python 不在題表，這三塊在本 repo 只靠合成樣本測試驗證；第一個消費專案（Landmark／KDS 類）碰到候選時要回填實例到 Verification。
- **消費專案的工具落後**（r1 接手席 H5 訂正：skills 是 symlink 回來源 repo，合進主線即時生效，不用重裝）：真正落後的是每個消費專案 vendored 的 `scripts/lumos`——舊副本的 `_DISP_STATUSES` 沒有 tension，會把 tension 表態當形狀壞拒收（rc2），要跑 `lumos update` 才認得；`bootstrap`／重裝不會補這個落後。

## 刻意不做

- 不裁誰讓誰、不擋推送——裁定說工具只把兩邊端上來。
- 不用 AST 或相似度判「像不像」（[[Systems/arch-alignment-lens]] 明文不做），只看觸發字有沒有出現在對照檔。
- 不在改檔前的 hook 算候選——hook 手上只有編輯內容、沒有 diff 的檔案集合與對照組；推送前的候選足以逼出表態。等表態帳出現 tension 實例再看要不要提前。
- 不修 `_stack_norm_line` 的跨行註解狀態——hunk 片段無從判斷，改了對照檔那側也會失去對稱。
- 不用 LLM 判 hazard 真不真。
- 不加新的治理帳 kind——tension 住在既有 `dispositions` 事件裡，候選次數也靠同一事件的 `candidates` 欄。
