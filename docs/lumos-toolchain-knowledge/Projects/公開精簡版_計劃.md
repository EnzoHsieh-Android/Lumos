# 公開精簡版（離職交接用）

`PRIOR-ART:` ① **最小解在既有層**——不造新機制；CLI 從既有單檔生成子集，skill／hooks 直接複製既有檔案。② **世界解過**：「單一源產出 minimal 發行版」有成熟先例（busybox applet 白名單、vim tiny/huge build）。③ **裁定＝borrow-design**：借「白名單驅動的建置變體」形態，**不採**打包工具（零依賴家規，且本案是一次性產出，引入 build pipeline 不划算）。自建只有一支 ast 剖析腳本。

## 目標（一句話）

> **新人 clone 專案 → 裝上精簡版 → 能讀懂專案既有的知識圖譜。**

不是發布一個產品，是**交接一份可讀的資產**。

★**優先序（2026-07-31 使用者更正）**★：**「可讀」是目標，「可維護」是加分**。
**不設任何強制**——不擋 commit、不擋 push、不催更新圖譜。交接後他們維不維護得下去，是他們的選擇，本案不用機制去逼。

## 情境與相容性（已實查，2026-07-31）

| 事實 | 影響 |
|---|---|
| Landmark 已 vendored 完整版 `scripts/lumos`（checked in） | 新人 clone 就有；但他**機器上**沒有全域指令、沒有 skill、沒有 Claude hooks |
| **Landmark 的** `CLAUDE.md` 引用 `lumos-project-notes` **9 次**（本 repo 自己的 CLAUDE.md 是 4 次，勿混），而該 skill 是 user-scope symlink 到維護者個人 clone | ★**這是真正的缺口**★——維護者離開，skill 消失，紀律區塊會叫 agent 去用一個不存在的東西 |
| git hooks 呼叫 `$REPO_ROOT/scripts/lumos`（vendored），非全域指令 | **精簡版與既有工作流並存不衝突**，不需要動 Landmark |
| 新人只在「改 code 且 tier=high」時會撞到 code-loop 閘 | 那是寫程式活動、不在本案目標內；退路 `python3 scripts/lumos ...` 仍在 |

### [S2] 生成方式（ast，非 regex）
- 用 python 內建 `ast` 移除白名單外的**指令實作函式**、其 subparser 註冊（**含迴圈註冊形式**——`links`/`backlinks` 正是迴圈註冊）、其 dispatch 分支。
- ★**移除對象不是「`cmd_*` 前綴」，是「從保留 dispatch 不可達的指令實作」**★（r1 修正）：以 `cmd_` 命名只是慣例，`lint-watch` 的實作叫 `_lint_watch_mode`（`scripts/lumos:8630`）、`compose-metrics` 叫 `_compose_metrics_mode`（`scripts/lumos:8447`）、保留的 `doctor` 叫 `run_doctor`（`scripts/lumos:440`）。用前綴當謂詞會把兩支該砍的實作原封留下（含 `_lint_watch_mode` 內活的 `urllib.request` 外部呼叫），只是變成不可達死碼。
  - **正解**：刪除集 = 從「保留指令的 dispatch 分支」出發做 AST 可達性閉包後的**補集**。這個定義同時解掉「刪到還被引用的 handler」的風險（結構上不可能）。
- **共用 helper 一律保留**（保守：寧可多留，也不要生成出跑不動的檔）。
- 產物須 `compileall` 通過、SyntaxWarning 為零。
  - 註（r1 剝除一條誤報）：現況完整檔 `ast.parse`／`compileall` 實跑 **0 個 SyntaxWarning、rc=0**，這道閘不是天生不可達。
- **為何用 ast 不用 regex**：2026-07-30 實證 regex 剖 Python 兩次出錯（漏抓迴圈註冊指令→53 誤算 51；漏抓三元式賦值→verdict 值域少一個）。
- **已量測的有利事實（r1 辯方實作原型驗證）**：`main()` 分派段（`scripts/lumos:11675-11995`）51 條語句中，**沒有一條是「保留與移除混合」的 tuple**；三處 `args.cmd in (...)` 全部 100% 落在白名單內；全檔無動態派發（`globals()[`／`getattr(sys.modules`／`eval(` 皆零命中）。故不需要 statement-level 手術，也不會生出空 `if`。**唯二實作坑**（原型踩過、皆三行修正）：巢狀 subparser 變數（如 `canary` 的 `csub`）、與 `Expr` 形式的註冊（`sub.add_parser("uninstall", ...)` 未賦值給變數，`scripts/lumos:11522`）。

### [S3] ★安裝器只做機器層★（本案最容易毀掉東西的一條）
新寫一支安裝器，**只做兩件事**（r1 更正：原稿第 3 項是取消通知，不是動作）：
1. 全域 `lumos` 指令 → **指向新人自己拿到的那份精簡版包**（不是維護者的 clone）
2. `~/.claude/skills/lumos-project-notes/`（**實體複製**，不是 symlink）
   - ★**「來源會消失」指的是誰**★：現況 `~/.claude/skills/lumos-project-notes` 是 symlink 指向**維護者的個人 clone**（`_install_skills`，`scripts/lumos:7266-7273`），維護者離職那份就沒了。第 1 項的精簡版包是新人手上的東西、不會消失，兩者不是同一個目錄——故「CLI 也該實體複製」不成立。

**碰撞語意（沿用既有政策，不自創）**：目標已存在時的處置照 `cmd_install` 的階梯（`scripts/lumos:6607-6616`）——symlink 已正確 → 冪等放行；一般檔／別版 symlink／broken symlink → **非 `--force` 一律 rc=2 拒絕**並印出現況。skill 目錄的放置與冪等照 `scripts/lumos:7235-7263`（含 junction 不被 `is_symlink()` 認出的 W4 事故防護）。

**明確不做**：不 scaffold 圖譜、**不注入／不更新任何 CLAUDE.md**、不 vendor 工具進專案、**不設 `core.hooksPath`**、不裝任何 Claude hook（見 [S4]）。

> **已查證的有利事實（2026-07-31）**：`core.hooksPath` 存在於 `.git/config`，而該檔**不隨 clone 傳遞**。故新人 clone 後 git hooks **天然就不生效**——只要安裝器不去設它，「不擋新人」這件事不需要額外工程。

**不得沿用哪些、以及正確的理由（r1 更正——原稿理由是錯的）**：
| 對象 | 原稿理由 | 查證後的真實情況 |
|---|---|---|
| `scripts/install-graph-toolchain.sh` | 碰專案層 | ✅ 正確——它轉呼叫 `lumos init --force`（`install-graph-toolchain.sh:17`） |
| `install.sh` | 碰專案層 | ❌ **錯誤**——它只有一行 `exec ... lumos install --force`，`cmd_install` 全部動作都在 `$HOME`，**不碰專案任何檔案**。<br>★真正的地雷是別的★：它尾端呼叫 `_sync_global_claude`（`scripts/lumos:6620-6623`），會把 `check-graph-sync.py`／`verification-rot-check.py`／`impact-hook.py`／**`ci-status-hook.py`**（`scripts/lumos:7293`）複製進 `~/.claude/hooks/` 並改寫 `~/.claude/settings.json`——正是 [S4] 說「不給」的那組（且 `ci-status-hook.py` 連 [S4] 的清單都沒提到）。<br>**若實作者照原稿理由推論「install.sh 只碰 $HOME，那可以借用」，就會把被禁的 hooks 裝回去。** |
| `lumos bootstrap`／`init`／`update`／`teardown` | 碰專案層 | ✅ 正確 |

### [S5] README（自足性——本案的第二個重點）
交接後無人可問，README 必須讓沒看過這套東西的人自己上手：
- 怎麼裝、怎麼確認裝好了
- 進場三步（search → context → contracts）
- **frontmatter 四條鐵則**（違反會長 ghost 節點、整篇 property 失效）——這是最容易踩壞的
