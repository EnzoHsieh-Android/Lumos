# 公開精簡版（計劃）

`PRIOR-ART:` ① **最小解在既有層**——不造新機制，只加一個**發版步驟**（生成子集），消費既有的 `LUMOS_VERSION`／release 流程。② **世界解過**：「單一源產出多種發行版」是成熟形態（feature-flag build、tree-shaking、多 target 打包），但那些解的是**編譯期最佳化**；本案要的是「**移除功能入口**」，最貼近的先例是 CLI 的 minimal/full 雙發行（busybox 的 applet 白名單、vim tiny/huge build）。③ **裁定＝borrow-design**：借「白名單驅動的建置變體」形態，**不採**任何打包工具（零依賴家規；本專案沒有 build pipeline，引入等於新增一整層）。自建只有一支 ast 剖析腳本。

## 決策脈絡（2026-07-31 使用者裁定，逐條記）

| 提問 | 裁定 | 連帶後果 |
|---|---|---|
| `doctor` 給不給、要不要關合約檢查 | 初裁「給但關掉合約檢查」→ **因下一條翻案，改為完整給（含 Check T/R/J）** | 合約鏈沒有 Check T 就沒有牙（裸合約不會被擋），既有 21 條合約會退化成裝飾 |
| 合約鏈（`guard`/`contracts`）算不算在砍的範圍 | 初裁「算在內（砍）」→ **改裁「保留合約鏈」** | `lumos-project-notes` skill 因此**幾乎不用改**（原本 48 處合約鏈內容要刪） |
| git hooks 給不給 | **給**（讓消費端持續維護圖譜） | `pre-push` 必須改寫（它呼叫已砍的 `code-loop skip`） |
| 其他 skills | **`lumos-core-knowledge` 與 `lumos-pitfalls-gapfill` 都不給** | 只發 `lumos-project-notes` |
| `guard kill` | **給** | 合約鏈最後一哩；`[test:]` 只證保鑣存在，`kill` 才證它會動手。無 config 宣告即跑不動，天然不礙事 |
| `anchor` | **給** | 它保護的正是合約鏈依賴的那些測試檔（防「偷偷把測試改成永遠會過」） |

## 分界原則（可判，非逐條拍腦袋）

> **維護圖譜本身 → 給；產出審計／評測結果 → 砍**

## 條款

### [S1] 白名單（單一常數，機械可驗）
**保留**：
- 讀取／導航：`search` `context` `show` `contracts` `links` `backlinks` `map` `export` `decisions` `stale` `recent` `stats`
- 寫入：`set` `append` `new` `archive` `decision-add` `decision-supersede` `decision-reindex`
- 健檢：`lint` `doctor`（含 Check T/R/J）
- 合約鏈：`guard`（list/scaffold/bind/audit/trace/kill/kill-add）
- 圖譜維護紀律：`impact` `cochange` `self-audit` `sync-verified-by` `rel-cascade` `spec-trace` `signoff` `anchor`
- 生命週期：`install` `uninstall` `init` `deinit` `update` `bootstrap` `teardown`

**移除**：`pitfalls` `code-loop` `canary` `loop` `fold-check` `refcheck`（對抗審計 loop）、`testmap` `test-layers` `lint-check` `lint-watch` `sqlfluff-sarif` `stylelint-sarif` `compose-metrics`（測試／linter 工具鏈）、`gov`（治理帳，主要彙整 loop 產物）。

白名單以**單一常數**存在於源 repo；生成腳本與驗證測試都讀它，**不得有第二份清單**。

### [S2] 生成方式（ast，非 regex）
- 用 python 內建 `ast` 剖析 `scripts/lumos`，移除：①白名單外的 `cmd_*` 函式定義 ②其 subparser 註冊（**含迴圈註冊形式**——`links`/`backlinks` 正是迴圈註冊，regex 會漏）③其 dispatch 分支。
- **共用 helper 一律保留**（保守：寧可多留，也不要生成出跑不動的檔）。
- 產物必須 `python3 -m compileall` 通過、SyntaxWarning 為零（沿 CI 既有閘）。

### [S3] 三道機械驗證（發布前硬前提）
1. **負向**：`--help` 的 choices **不得出現**任何被移除的指令名。
2. **正向**：白名單內每一支指令都能被呼叫；`doctor` 要**實跑**（不只 `--help`）。
3. **等價**：拿 `governance/eval/retrieval-goldset.json`（30 條查詢）對完整版與精簡版各跑一次，**搜尋結果必須一致**。
   → 這是跨版本的**行為合約**，讓「兩份不漂移」變成機械可驗，而非靠人記得同步。

### [S4] hooks 與 skills 的對應變體
- **git hooks**：`pre-commit`／`post-commit` 原樣給；**`pre-push` 必須改寫**——移除呼叫 `lumos code-loop skip` 的整段，保留 `doctor --ci` ＋ `anchor verify`；錯誤訊息內指向已砍指令的字串一併清除（否則使用者會照著打一個不存在的指令）。
- **Claude hooks**：`check-graph-sync.py`／`verification-rot-check.py`／`impact-hook.py` 給；`ci-status-hook.py` 砍。
- **skills**：只發 `lumos-project-notes`（含 `reference.md`）。

### [S5] 併入發版流程
本案是 [[Projects/版本發布流程_計劃]] `[S3]` 發版 checklist 的一個步驟：CI 綠 → 生成精簡版 → 跑 [S3] 三道驗證 → 同步到公司 repo。**驗證未過不得同步。**

## 實務隱患

- **白名單漂移**：新增指令時若忘了決定它屬公開或內部，生成腳本行為未定義。→ 需要「新指令必須落在白名單或黑名單其一」的守衛，**缺一即紅、不得有預設值**。
- **共用 helper 保留造成的誤解**：公開版仍看得到治理相關小函式，可能被誤讀為「功能其實還在」。→ 公開版 README 必須明講範圍與界線。
- **`doctor` 的檢查項與白名單耦合**：若日後某個 Check 依賴被砍的指令，精簡版的 doctor 會壞。→ [S3] 正向驗證要涵蓋 `doctor` 實跑。
- **`guard kill` 需要 config 宣告 run_cmd**：消費端沒宣告就跑不動——這是預期行為，但錯誤訊息要說得清楚，不能只丟 traceback。
- **同步方向單一**：公司 repo 的精簡版**不得反向合併回源**（那會把子集當成全集）。需明文政策與（若可行）機械阻擋。
- **`impact`/`cochange` 依賴 git 歷史**：在剛 clone 或淺複製的 repo 上行為未驗證。
- **已發布版本收不回**：生成錯誤若已同步出去，只能前滾發新版修正。

## 測試策略

| 條款 | 測試 | 型態 |
|---|---|---|
| [S1] | 白名單常數與 `--help` 對照；**新指令未分類即紅**（反事實：加一個假指令不列入任一清單 → 必翻紅） | 機械守衛＋反事實 |
| [S2] | 生成後 `compileall` 通過＋SyntaxWarning 為零；**迴圈註冊的指令在該砍時真的被砍掉** | 單元＋反事實 |
| [S3] | 三道驗證各自有測試；**等價驗證要能抓到差異**（反事實：故意改精簡版排序參數 → 必翻紅） | 反事實 |
| [S4] | `pre-push` 變體不得含已砍指令字串；hooks 白名單與實際檔案雙向對稱（沿 `t_docs_enumeration_drift` 的寫法） | 機械守衛 |

**反事實優先**：[S1][S3] 的價值全在「壞掉時會不會擋」，兩條都必須有「弄壞→必翻紅」的測試。

## 誠實天花板

- **這不是藏程式碼**：Python 是原始碼語言，給了檔案就給了內容。本案移除的是**功能入口**，共用 helper 仍在。對外不得宣稱「已移除全部相關程式碼」。
- **等價驗證只涵蓋搜尋**：goldset 是檢索用的，不保證其他指令在兩版行為一致。
- **生成腳本本身沒有第二來源可對照**：它若剖錯，三道驗證能抓到「指令還在／不能跑」，但抓不到「語意被改壞」。
