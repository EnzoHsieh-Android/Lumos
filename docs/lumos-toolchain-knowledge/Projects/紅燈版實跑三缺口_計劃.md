# 紅燈版實跑三缺口_計劃

> 白話:規格閘紅燈版那批推上去之前,在 mOrangePos 考場拿一個假想功能(結帳服務費,五條驗收條款,四條 JVM、一條平板儀器測試)從設計一路走到推送前驗收,實跑抓到三個自動測試沒抓到的缺口:字串預期值被改漏報、平板測試在推送前被丟到 JVM 指令跑而誤判紅、專案把治理帳設成忽略時紅燈版的提醒指錯方向。這份計劃三個一起修,另補修好之後才會浮現的一件事:綁裝置測試的計劃,沒接裝置時不能被當成測試失敗、記成逃逸。

## 名詞

- 比對工具:推送前新增告警閘裡的測試防竄改比對(`lumos test-guard`),拿「改動前」的測試跟推送版逐支比,列出改弱、改預期值、刪測試這類候選。
- 分岔點比對:拿這條分支跟主線分岔那一版的測試當改動前版本。新測試在分岔點不存在,所以另有紅燈版比對。
- 紅燈版:規格閘判出紅的那一刻,把那支 Kotlin/Java 測試檔整份存到消費專案的 governance/redbase/ 資料夾;紅燈版比對拿它當新測試的改動前版本。
- 留痕:規格閘判完寫的一筆紀錄,寫進審查帳(本機)與治理帳(`docs/.governance-log.jsonl`,進版控),記測試名、條款指紋、紅燈版的路徑與指紋。推送前驗收照它重跑測試。
- 孤兒紅燈版:紅燈版檔在提交裡,治理帳裡卻沒有任何留痕指到它。
- 放行指紋:比對工具每條候選的 16 碼身分,`lumos lint-waive` 認它放行;身分字(`_tg_rb_bad` 的 ident 參數)是組成指紋的那段穩定文字,不給就用整句提醒。
- 逃逸:推送閘擋下風險低計劃時自動記進逃逸帳的一筆,意思是「沒人審的計劃在下游被抓到洞」。
- 平台:專案設定 `.lumos/config.json` 的 platforms 底下每一項(各有根目錄、測試格式、跑單支測試的指令);`default_platform` 是條款裡 `[test:名字]` 沒寫前綴時用的那一個。考場設了 android(JVM 單元測試)與 device(平板儀器測試)兩個。
- 考場:mOrangePos 的演練工作樹與只留本機的分支,不推、不併。
- 弱證據:規格閘與推送前驗收的三種判定之一(紅、綠、弱證據),意思是「驗不了」(一支都沒跑到、篩選對到好幾支、被跳過);不算綠,推送照擋。
- 環境沒跑起來:本案新增的一種弱證據原因,測試輸出命中測試格式宣告的環境樣式(Kotlin/Java 是 AGP 找不到裝置的 DeviceException)時用它,不當成測試失敗。

## 問題與最小解

立案(2026-11-03,Enzo 原話依序):「我機器接起來了，你直接測」→「測試應該是以一個假想功能設計為始，測試拆分驗收項目、直到串到真正驗收那環」→(看完實跑結果)「修」。

實跑卷證在 mOrangePos 考場本機分支 drill/service-charge-e2e 的 drill-evidence/redbase-real/(只留本機;公開摘要在落地的驗證紀錄)。三個缺口:

1. **字串預期值被改漏報**:比對工具切斷言參數時只數括號深度、沒跳過字串,`assertEquals("服務費 $1,235", label(fee))` 被切成三個參數(`"服務費 $1`、`235"`、`label(fee)`),預期值被改的那一半落進「其餘部分」,新舊兩行配不起來。分岔點比對(`tq/expected-changed`)與紅燈版比對(`tq/redbase-weakened`)用同一支切法,兩邊都漏。金額、清單、JSON 這類字串預期值很常見。同一支切參數函式另有 Room 守衛一處呼叫,那裡拿到的是已剝字串的原始碼,不受影響。
2. **推送前把非預設平台的測試丟到預設平台的指令跑**:規格閘留痕的 tests 欄只記方法名,丟了 `[test:device:名]` 的平台前綴;推送前照預設平台(JVM)的指令跑平板測試,Gradle 回「找不到測試」、退出碼非零被判紅。結果是正確的程式也推不上去,而且推送閘還自動記一筆假的逃逸(風險低計劃被推送閘擋下會自動記逃逸)。舊留痕在實作完成後重跑規格閘也不會被重寫(條款全綠、最新留痕風險低、條款指紋與門規則版本都相同時不寫新留痕,`_spec_gate_low_not_red`),不補相容會永遠卡住。
3. **治理帳被忽略時孤兒紅燈版的提醒指錯方向**:mOrangePos 的 .gitignore 從 2026-06 起忽略 docs/.governance-log.jsonl(那時一次會談手動加的,早於 2026-09-09「治理帳不能被忽略」那條規則),規格閘寫的留痕進不了提交,每份紅燈版推送時都成了孤兒,提醒卻說「多半是合併時解治理帳衝突弄丟了那一行」、叫人去版本紀錄找一支從沒提交過的檔。紅燈版照樣拿內容比、不會漏擋,問題是提醒指錯方向。同一族的另一句「工作目錄有還沒提交的紅燈版檔:請 git add 那支檔與治理帳一起提交」在治理帳被忽略時也一樣錯:git add 被忽略的檔會失敗。

舊否決比對(開審前,2026-11-03):`lumos rejections` 427 行按概念比過。最接近的是 [[Systems/test-guard]] 否決的「孤兒檔當沒有紅燈版」;本案孤兒照樣拿內容比,只改提醒措辭,不撞。其餘(只記版本編號、內容寫進治理帳本體、帳本 merge=union)與本案無關。

最小解:①切參數照剝過字串的文字判逗號與括號,剝字串掃描會讀錯的兩種情形退回現況;②多平台專案的留痕一律寫 `平台:名字`,推送前讀到沒前綴的舊名字時照現在計劃條款補平台;③沒接裝置判成環境沒跑起來,照擋但不記逃逸;④孤兒紅燈版與還沒提交的紅燈版兩句提醒先問 git 治理帳是不是被忽略,是就講明蓋到的規則與改法,規格閘寫紅燈版當下與 doctor 也提醒;⑤撤回考場那兩筆假逃逸。

PRIOR-ART: 切函式參數的通用做法是一趟掃描同時記括號深度與「在不在字串裡」(Foundry 的 split_call_args 照頂層逗號切、略過括號與引號裡的逗號:https://foundry-rs.github.io/foundry/cast/call_spec/fn.split_call_args.html);本案借本檔既有的「字串內容換成等長空白」掃描(`_strip_c_comments` 的 keep_length,括號配對已經在用它),不另寫一支詞法掃描。測試身分帶執行環境:JUnit Platform 的 UniqueId 第一段就是 engine(https://docs.junit.org/5.0.0-M6/api/org/junit/platform/engine/UniqueId.html),同名測試在不同執行環境是不同的測試,留痕記平台是同一個道理。必要檔被忽略的檢查沒有現成工具,通用做法是 `git check-ignore -v` 列出蓋到的那一行規則(https://man.he.net/man1/git-check-ignore);本案照抄,不新增設定;git 呼叫借本檔既有的 `_lens_git_dl`(比對工具這一帶都帶截止時間),判法照 `_local_ledger_doctor_msgs`(先判已追蹤、再判忽略)。Kotlin 官方文法認字串模板靠模式堆疊(`${` 推進一層,https://kotlinlang.org/spec/syntax-and-grammar.html),本檔的剝字串掃描是單層正規式、認不得模板裡的巢狀引號;本案不另寫一支有堆疊的掃描,只在掃描會讀錯的兩種情形退回現況的切法。測試結果把「環境沒跑起來」跟「測試失敗」分開記是建置工具的通例(Bazel 的測試狀態把 REMOTE_FAILURE、FAILED_TO_BUILD、BLAZE_HALTED_BEFORE_TESTING 跟 FAILED 分開:https://bazel.googlesource.com/bazel/+/HEAD/src/main/protobuf/test_status.proto),本案照這個分法處理「沒接裝置」。git 的忽略規則以較深層目錄的設定檔優先、同一支檔裡後面的規則蓋前面的(https://git-scm.com/docs/gitignore 的 PATTERN FORMAT 與優先序說明),所以改法要指到蓋到的那支檔,不能一律叫人在根目錄加否定行。
RETIRE-IF: 紅燈版整套撤掉時(見 [[Projects/規格閘紅燈測試快照_計劃]] 的撤除條件),做法 4 的兩句提醒與規格閘多印的那一行跟著撤;做法 1(比對工具本身)、做法 2 與 3(推送前驗收本身)、doctor 那一行(治理帳被忽略不限紅燈版)不隨之撤 [retire:人裁] [until:2027-05-03]

## 做法

1. **切參數不切字串裡的逗號與括號**:`_tg_call_parts` 已經用剝字串後的文字(`_tg_strip`,字串內容換成等長空白、長度跟原文一一對應)配括號,切參數卻用原文。`_rg_split_args` 加一個選填參數 `stripped`(剝過字串的同段文字,長度同原文):給了就不自己數深度,改照 `_rg_bracket_map(stripped)` 配好的括號對跳過括號內部,頂層的逗號(剝過的文字那一格是逗號)才切,再回原文取字。配括號只有 `_rg_bracket_map` 一套,不另寫深度規則(它跟 `_rg_balanced` 的等價已由 t_rg_methods_expression_body_and_backtick 綁住)。`_tg_call_parts` 的兩處切參數(呼叫本身與串接的 `.isEqualTo(…)` 這類)都帶它;Room 守衛的呼叫不帶(它拿到的本來就是剝過字串的原始碼),行為不變。
   **剝字串掃描會讀錯的兩種情形退回現況**:一段斷言裡有字串沒收尾(例 Kotlin 原始字串 `"""a""""`,掃描把最後一個引號當成新字串的開頭、吃到行尾),或字串裡有 `${` 卻在同一段字串裡沒有對應的 `}`(模板裡有巢狀引號,例 `"${foo("a,b")}"`,掃描把它切成兩段字串、`a,b` 露在外面)時,這一段斷言照現況用原文切。判法用同一支掃描(`_C_STRIP_PAT`)逐個字串看有沒有收尾、`${…}` 有沒有在段內配平。這樣字串裡的不成對括號(`")"`、`'('`、`"1) 項目"`)、逗號(`"$1,235"`)都修到;退回的兩種寫法跟現況切法相同:現況列得出的照樣列(例 `"${foo("a,b")}"`,逗號在括號裡),現況本來就漏的照樣漏(例 `"${a}, ${f("x")}"`,模板裡同時有頂層逗號與巢狀引號,代碼審 r1 單審席 F4 實測),由下面的 REVISIT 回頭處理。只給 `angle=False`(不把 `< >` 當括號)的呼叫走剝過文字那條路——配括號表本來就沒有 `< >`。
   **本體簽名同族修**(實作時發現):比對先看一支測試的本體有沒有變,本體簽名原本把整段的空白全拿掉,字串裡的空白也一起拿掉,`"a, b"` 改 `"a,b"` 被當成沒改、整支略過。改成兩份簽名:判本體有沒有變用 `_tg_ident`(字串原樣保留、字串外空白整理成一格),只差空白版面(拿掉全部空白後相同)的只比預期值、其他規則不重判(整檔重新縮排時多行字串跟著變,不讓沒斷言的既有測試被列,代碼審 r2);找搬家與改名照舊用拿掉全部空白的那份(搬進巢狀類別時,多行字串跟著多縮排一層,用保留字串的那份會配不起來、誤列刪測試,代碼審 r1 單審席 F1)。同 clone 偵測的分法:只差空白版面的算同一支(Type-1),內容改了另判。
   **斷言文字只壓字串外的空白**(代碼審 r3):抽出來的斷言原本整段壓空白,字串裡的空白也被壓掉,`"a b"` 改 `"a  b"` 漏報;改成字串外的連續空白壓成一格、字串原樣保留(語言的詞法本來就這樣分,`git diff -w` 正因為不分而會藏住字串裡的改動)。
   **字串樣式認得三引號**(代碼審 r4):斷言文字保留字串原樣後會帶換行,比對工具判字串常值的樣式(數強斷言、判訊息參數、判容差、判恆真條件共 5 處)原本只認單行字串,多行原始字串裡寫的 `assertEquals` 字樣會被算成強斷言、蓋掉斷言變弱;樣式補上三引號那段(同剝字串掃描的寫法),5 處一起生效。
   **已知多報**:帶 `.trimIndent()` 的多行原始字串整段重新縮排時,執行時的值不變(Kotlin 官方:trimIndent 去掉共同最小縮排,https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.text/trim-indent.html),但比對把字串原樣保留,會多列一條可放行的 tq/expected-changed;不模擬 trimIndent(要精確還得處理模板值帶縮排),只多報、不漏擋。
   REVISIT:2027-05-03 看 test-guard 放行紀錄裡有沒有「trimIndent 字串重新縮排」被放行的 tq/expected-changed;一季超過三筆就照官方語意對「三引號緊接 .trimIndent()」的字串先去掉共同縮排再比
   **已知漏判**(代碼審 r5 放行):判常值斷言的 `_TG_CONST_PAT` 也只認單行字串,`assertEquals("""a""", """a""")` 不會被當成常值斷言(修補前就這樣;常值斷言判定本來就是近似判讀,三引號常值斷言少見)。
   REVISIT:2027-05-03 改到 `_tg_ident` 或 `_TG_LIT_PAT` 時一併做:`_TG_CONST_PAT` 補三引號、`_tg_ident` docstring 改成傳 `_tg_ws_collapse`、`_TG_LIT_PAT` 註解寫明跟 `_C_STRIP_PAT` 的差別(不收沒收尾的三引號與三個單引號);沒改到就在這天看一次要不要單獨開一批
   **相容**:原本切錯的斷言改切對以後,改到這類斷言的測試可能多列出原本漏掉的候選(改預期值、改成常值斷言),這正是要抓的。
   REVISIT:2027-05-03 看 test-guard 的放行紀錄與漏報回報裡有沒有「字串模板裡有巢狀引號」或原始字串結尾連續引號的案例;有就把剝字串掃描換成認得 `${}` 的寫法,不再退回原文切法
2. **留痕記平台**:現行 `_spec_gate_record` 的 tests 來自 `_spec_gate_prepare` 算的 `names`(每條條款引用的方法名,含懸空的;平台在那一行就丟了;同一份 `names` 也餵雙向判定,不改它的形狀)。改成 `_spec_gate_prepare` 另外產一份同樣集合、帶平台的清單(同一個 `resolve_test_refs` 結果,不只取方法名;懸空的引用照樣在,`manual_only` 判法不變),由呼叫端傳給 `_spec_gate_record`。**多平台專案(設定有 platforms)一律寫成 `平台:名字`,含預設平台**;單平台專案照舊寫名字。理由:推送前讀這欄是把每一項包成 `[test:…]` 交給全庫唯一的切法 `_split_test_ref`,跟計劃條款同一種寫法;預設平台也寫裸名的話,名字本身含冒號(Kotlin 反引號名字 `` `fee: rounds up` ``)會被當成平台前綴而崩潰或跑錯平台,`default_platform` 改了也會被重新解到別的平台。判綠事件用成對的 items 記,那是內部的集合;留痕的 tests 欄是給推送前照條款寫法重新解析的,兩種形狀用途不同,不合併。
   **推送前讀舊留痕**:多平台專案的留痕裡出現沒有前綴的名字,一定是這次之前寫的舊留痕。`_spec_gate_push_stale` 本來就讀了計劃文字、算了條款綁定(`_clause_bindings_for`);改成把計劃文字與綁定列一起回傳,`_spec_gate_push_one` 用手上的 split 與 default 呼叫既有的 `_spec_gate_items` 得到現在條款的 (平台, 名字),不另掃正文、不重算綁定。留痕沒過期(條款指紋相符)時,舊名字整串先跟現在條款的名字逐字比:比到了、而且只綁在一個平台,就用那個平台;同名綁在兩個以上平台、或比不到,照舊包成 `[test:…]` 解析(沒前綴就是預設平台)。條款指紋不符而計劃已完成的那條路不補(條款可能改綁到別的平台),照舊解析,找不到就走既有的「留痕裡的測試找不到」提醒。整串先逐字比,是為了讓舊留痕裡本身含冒號的名字(`fee: rounds up`)不被當成前綴:那種留痕在實作完成後重跑規格閘也不會被重寫,只能在讀的時候認出來。
   **平台不在設定裡**:解析留痕名字遇到沒定義的平台前綴(平台改名或刪掉)時,不丟例外:計劃還在做的照擋,訊息講「留痕記的平台 X 不在 .lumos/config.json 裡(改名或刪了?);照現在的設定改條款的平台前綴後重跑規格閘」(改了條款,指紋變了,重跑才會寫新留痕);已完成的計劃降成提醒,跟找不到測試同一條路。
