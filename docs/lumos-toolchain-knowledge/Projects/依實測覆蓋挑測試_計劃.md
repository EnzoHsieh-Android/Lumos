# 依實測覆蓋挑測試_計劃

> 白話:兩步走的第二步(第一步是 [[Projects/推送只跑受影響測試_計劃]]:推功能分支本機不跑全套)。這篇要讓 PR 的 CI 也能只跑受影響的測試:跑全套時順便記下「每支測試實際碰到哪些函式」,之後改了函式,只跑上次碰過它的測試;全套改到合併後與每晚跑。使用者 2026-11-05 同意兩步走。

PRIOR-ART: Datadog Intelligent Test Runner:一支測試只有在「它上次通過時碰到的檔案,這次一個都沒變」才跳過,其餘照跑;自承盲點是資料檔、外部服務、編譯選項,主線分支預設不啟用(https://docs.datadoghq.com/intelligent_test_runner/how_it_works);pytest-testmon 同一種做法(https://pypi.org/project/pytest-testmon/0.9.18);coverage.py 量子程序要在子程序啟動時掛鉤(https://coverage.readthedocs.io/en/6.5.0/subprocess.html)。本 repo 零依賴,打算用 Python 3.14 內建的程式監控(`sys.monitoring`)自己記,不裝 coverage.py——要先做最小實驗證明子程序也記得到。
RETIRE-IF: 上線後八週內,主線合併後全套紅、而紅的那支在當時被判成可跳過,累計 3 次以上 → 撤掉、PR 的 CI 回到全套。

## 狀態

初稿,還沒開設計審。最小實驗已做(見下),子程序記得到;下一步是設計「每支測試 → 碰過的函式」的對應怎麼存、怎麼刷新。

## 最小實驗(2026-11-05)

- 問題:測試多半另開子程序跑主程式,`sys.monitoring` 在子程序裡記得到主程式跑過哪些函式嗎?
- 做法:臨時目錄放一支 `sitecustomize.py`,環境變數 `LUMOS_COVMAP_DIR`、`LUMOS_COVMAP_FILE=scripts/lumos` 有設時,用 `sys.monitoring` 的 PY_START 事件記下 `co_filename` 結尾是 `scripts/lumos` 的 `co_qualname`(第一次碰到就 DISABLE,開銷只在第一次),程序結束時寫一檔;用 `PYTHONPATH` 指到那個目錄,跑 `python3.14 scripts/test_lumos.py -k t_room_guard_unrelated_diff_silent`(這支會另開子程序跑 `lumos room-guard`)。
- 結果:測試照綠(3 passed);記到兩個程序,一個 0 個函式(測試執行器本身沒載入主程式為腳本)、一個 87 個主程式函式,其中 15 個是 Room 守衛的 `_rg_` 系列——正是這支測試在驗的東西。執行器的環境隔離沒有擋掉 `PYTHONPATH`。
- 結論:零依賴的動態覆蓋在子程序可行;要補的是「哪支測試觸發了哪個子程序」的對應(實驗只跑一支,所以不用分);可行做法是執行器每跑一支測試設一次環境變數帶測試名。

## 開審前必須先解(從 [[Projects/推送只跑受影響測試_計劃]] 設計審 r1 帶過來)

卷證:governance/review-reports/推送只跑受影響測試/r1-*.md。

1. 靜態關鍵字選測漏得很兇(正確性席):`scripts/lumos` 2817 個頂層函式 62.6% 沒有任何測試整字提到;60 個提交裡 93% 至少改到一個這種函式;有提交照規則只選中 0–4 支。這篇改用實測覆蓋就是為了這條。
2. 執行器本體、選測函式本身、模組層常數的改動(通才、邊界、正確性席):實測覆蓋也記不到「改了就影響全部」的東西,要有一律全套的清單,而且判「有沒有動到選測」要拿基準版比(邊界席:被改的那一版自己判自己)。
3. 執行器現行「單一關鍵字選中超過三成就丟掉」的規則(通才、正確性席)會跟任何門檻打架。
4. 合併後全套紅怎麼讓人知道(平台、架構對齊席):本專案的 CI 回流管道是 `lumos ci-wait`/`ci-status` 進治理帳,不是 GitHub Issue;要先對照這條管道再決定。
5. CI 第一次跑子集,要明講是修訂 [[Projects/CI加速_計劃]] 的結構(架構對齊席);改 `ci.yml` 的自主迴圈步驟會踩到逐字指紋守衛(合約圖譜席)。
6. PR 事件的範圍要用 `pull_request.base.sha...head.sha`,不是合併預覽提交(平台席);漏抓統計的範圍用推送事件的 before..sha(平台、邊界席)。
