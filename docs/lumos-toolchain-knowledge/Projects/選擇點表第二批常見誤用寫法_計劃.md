# 選擇點表第二批常見誤用寫法_計劃

## 白話

[[Projects/改動選擇點都要有需求守住_計劃]] 第一版的選擇點表只收論文表 1 的五類運算子加 13 個集合與 Flow 兄弟寫法;在兩個真實 Kotlin 專案量到只有 13–15% 的程式行有選擇點([[Verification/2026-11-15_改動選擇點真實Android端到端驗收]])。使用者 2026-11-15 要「上網搜一下,最容易誤用的情境語法列進來」。這份把網上有公開來源點名「常被誤用、換成兄弟寫法照樣編得過、行為卻不同、單元測試分得出」的 Kotlin/Android 寫法收成第二批列,每列仍是一個語法節點對一組一對一機械壞法,沿用同一套掃描、挑壞法、殺傷力與推送前那一道,不改判定規則。

第二批(候選,設計審定案;每一列上線前還要過範圍 7 的實測門檻):
- 空值處理:`$A ?: $B` → `$A!!`(遇到 null 從用預設值變成當掉);`$A?.方法` → `$A!!.方法`(從略過變成當掉)。
- 範圍函式:`.let` → `.also`(回傳值從區塊結果變成接收者本身;只收回傳值有被用到的 `.let`)。
- Flow 合併:接收者寫法 `a.combine(b) { … }` → `a.zip(b) { … }`(任一邊有新值就輸出 → 兩邊成對才輸出)。頂層寫法 `combine(a, b) { … }` 不收:kotlinx.coroutines 的 `zip` 只有擴充函式、沒有頂層兩參數版本,換識別字必定編不過,要改成接收者寫法又得搬引數(多節點)。
- Compose 副作用與記憶:`LaunchedEffect(<key…>) { … }` 的 key 換成 `Unit`(key 變了不重跑);`remember(<key…>) { … }` 拿掉 key(參數變了還顯示舊值)。

PRIOR-ART: 第一版同一套(論文〈Practical Mutation Testing at Scale〉https://arxiv.org/pdf/2102.11378 2.2 在語法樹上產生、表 1、3.2.1 型別前提事前擋;MutApi 的 API 兄弟改寫表(Wen 等,ICSE 2019,https://doi.org/10.1109/ICSE.2019.00093,全文 https://sqlab-sustech.github.io/files/paper/ICSE2019-mutapi.pdf))。誤用證據:Kotlin null safety 官方頁 https://kotlinlang.org/docs/null-safety.html 與 Detekt `UnsafeCallOnNullableType`(https://detekt.dev/docs/rules/potential-bugs);範圍函式官方頁 https://kotlinlang.org/docs/scope-functions.html;Flow 官方頁 combine 與 zip 段 https://kotlinlang.org/docs/flow.html;Compose 副作用官方頁 https://developer.android.com/develop/ui/compose/side-effects(LaunchedEffect key)與狀態官方頁 https://developer.android.com/develop/ui/compose/state(remember key)。必然等價的壞法用規則事前排除,依據論文附錄 A 的乾節點做法與等價壞法研究(Trivial Compiler Equivalence,https://discovery-pp.ucl.ac.uk/id/eprint/1499169/1/Jia_Trivial_Compiler_mutation-testing-papadakis-icse15.pdf;常見寫法造成的等價可用便宜的靜態分析抓,https://homes.cs.washington.edu/~rjust/publ/equi_mutants_ems_issta_2024.pdf)。不採:`runCatching` 吞取消(Detekt `SuspendFunSwallowedCancellation` https://detekt.dev/docs/rules/coroutines)——壞的方向是把 try/catch 改寫成 runCatching,跨多個節點、不是一對一壞法,改由情境決策表或 Detekt 規則管;Flow `catch` 換位置——要動兩個節點的順序;頂層 `combine(a, b)` → `zip`——見上;`launch`↔`async`、`groupBy`↔`associateBy`、`MutableStateFlow`↔`MutableSharedFlow`——回傳型別不同多半編不過;`remember`↔`rememberSaveable`、拿掉 `derivedStateOf` 外的 remember——單元測試分不出(論文附錄 A.1.4 同理);`==`→`===`——論文附錄 A.1.23 只換對應的否定。

## 用詞

- **論文**、**選擇點表**、**乾節點規則**、**錨點**、**型別前提**、**跑不出結果**:同 [[Projects/改動選擇點都要有需求守住_計劃]]〈用詞〉。
- **接收者寫法**:`a.combine(b) { … }`,`combine` 出現在 `.` 之後的 navigation_suffix 裡,走第一版的「方法名」錨點。
- **`?:` 的錨點**:照第一版「運算子」錨點的位置規則——兩個運算元之間跳過空白與註解後的運算子位置。字面 `?:` 只在 NUL 類 `?:` 那一列的錨點比對時認,其他列照舊只用運算子正規式 `_CHOICE_OP_RE`;`_CHOICE_OP_RE` 與優先層級表 `_CHOICE_PREC` 都不動——那支正規式也給 `_choice_top_prec` 算運算元的優先層級,它把表外運算子(含 `?:`)當 0、一律加括號,把 `?:` 加進正規式會查 `_CHOICE_PREC` 查不到而當掉(設計審第二輪五席實測 KeyError)。`?:` 換行寫在續行時,錨點行就是 `?:` 那一行。
- **新錨點「安全呼叫符」**:`?.` 那兩個字元的位置(navigation_suffix 開頭),錨點行是 `?.` 那一行。
- **新錨點「引數」**:ast-grep 規則命中的節點本身就是呼叫的 `value_arguments`(左括號到右括號)。`_choice_anchor` 多收「改動行集合」,對這個錨點回傳節點範圍內第一個改動行的開頭位移(範圍內沒有改動行就回節點開頭,選行時自然落選);引數跨多行、只改中間某個 key 也算。錨點仍只有 `_choice_anchor` 一個出處,選行處照舊只看錨點行在不在改動行裡。
- **單一記號**:照第一版 `_choice_atomic` 的判定(識別字、點、`?`、`!` 與成對括號的呼叫,例 `a.b()`、`x?.y`);其餘(含空白的 `a + b`、`x as? Foo`)都不是。
- **新類別 NUL**:null-safety 運算子(`?:`、`?.`)的壞法。不是論文縮寫,也不是 NUL 字元(`\0`)。
- **第二批各列的類別**:`?:`、`?.` 兩列 NUL;`.let`、接收者 `combine`、`LaunchedEffect`、`remember` 四列 API。API 類照第一版本來就不只換方法名(第一版已有 `(拿掉呼叫)` 拿掉 `.distinctUntilChanged()`),所以改引數的兩列歸 API、不另開類別。

   - 每列印:壞法數、終態殺掉、存活、跑不出結果各幾個;跑不出結果的原因冒號前那段等於「基準不綠沒跑」的(程式裡的字面字串),那個壞法整個不算進那一列(不是壞法的錯)。
   - 放行:用放行事件自己帶的列號(`ck_waive` 的 `row`,現行形狀計數也用它);同一個 (檔, 行指紋) 多筆放行只算一筆(不同提交重複放行同一行不灌水),取 `ts`(提交時間)最大的那筆的列號與理由——同一個提交的重複放行去重時已併掉,所以不會打平;列號不是字串的另計「沒有列號」,不進任何一列的分子與分母。理由照現行標籤「等價」「不是需求」「不適用」分開計。
   - 帳上有、型錄已沒有的列號照印(讀帳不讀型錄);撤列時把那一列的數字抄進 Verification(統計有時間窗,過窗就讀不到),見〈回退〉第 1 項。
   - 不加它的最小解為什麼不夠:現行選擇點段的跑不出結果依原因文字計、放行依 (列號, 外層宣告) 形狀滿三次才列,RETIRE-IF 要的「某一列的比例」讀不出來。

## 實務隱患

- 編不過:`.let`→`.also` 在區塊結果型別跟接收者不同、而外面有用到結果時編不過;`$A ?: $B`→`$A!!` 與 `?.`→`!!.` 在接收者不是可空型別時編譯器只警告不報錯(行為不變,等價存活),專案開 `allWarningsAsErrors` 時這個警告變成編不過。語法樹沒有型別,這幾列除了「運算元有 null 字面值」與範圍 2 的規則排除之外不設型別前提(近似條件判不準,寧可讓它跑);編不過的落成跑不出結果、人可判不適用,範圍 5 依列號累計,超過一半照 RETIRE-IF 拿掉那一列。第一版的跑不出結果每次 choice-kill 都重跑(這份不改),編不過的壞法每次都重編一次、佔 30 個名額裡的位置;範圍 7 先量編不過比例。
- 同名:專案自訂的 `LaunchedEffect`、`remember`、別的型別自己的 `.combine`、`.let` 語法樹分不出,換了多半編不過或等價,落成跑不出結果或放行;import 別名(`combine as flowCombine`)不命中,是漏判。
- 等價存活:`$A!!` 在 `$A` 實際不會是 null 的地方是等價;回傳值沒人用的 `.let`、全是常數 key 的 `LaunchedEffect` 由範圍 2 規則排除,其餘靠回報上限與放行理由「等價」承接,RETIRE-IF 看比例。
- 換壞法:含第二批語法的既有改動行(例 `x?.filter { … }`),類別變多後洗牌結果可能挑到別的壞法。處置鍵是 (檔, 行指紋)、不含壞法,所以那一行既有的殺掉、存活或放行照算給新挑到的壞法(第一版既定取捨,見〈天花板〉第 5 條);只含第一版語法的行挑法不變(S7)。
- 推送負擔:`?.`、`?:`、`.let` 是 Kotlin 最常見的語法,有選擇點的行與每次推送要跑的壞法會變多;回報上限只限存活,沒帳的行照擋,choice-kill 每次最多 30 個壞法、總時限 1800 秒,大改動要分幾輪跑。範圍 7 用實測門檻決定每一列上不上線,不靠兩個月後的 RETIRE-IF 才發現。
- 挑壞法時限:`_CHOICE_PICK_BUDGET` 15 秒整次推送所有檔共用,超時之後的檔整支記成驗不了、只提醒放行——新規則讓挑壞法變慢,等於把守衛降成提醒;範圍 7 用真實提交量每次的總耗時與驗不了檔數。掃描:第二批多六條 ast-grep 規則,設計審席位用人造密集檔實測掃描時間多約一成、輸出量約 2.4 倍,輸出超過 64MB 上限會退回逐檔、再超過就記驗不了;掃描時限 `_KT_SIT_BUDGET` 照第一版,範圍 7 量真實最大檔的輸出位元組。深層巢狀 `a ?: b ?: c ?: …` 的輸出量隨長度平方成長(每一層都是一個命中、各帶整段文字),跟第一版長串 `+`、`&&` 同一類,靠輸出上限落成驗不了、只提醒,不另設檢查。
- Compose 測試成本:`LaunchedEffect`、`remember` 列要 Compose UI 測試(`createComposeRule`)才分得出,單元測試平台 `kotlin-junit` 跑不到時那幾行只能人驗或放行;推送前那一道碰到沒有可守測試時照第一版只提醒不擋。
- 併發與交易:已排除:沿用第一版,單人單機依序操作。
- 已排除:金流:只改型錄、規則與產壞法的程式,不碰付款或金額計算
- 已排除:對外送出:掃描與殺傷力都在本機跑,不對外送任何資料
- 已排除:不可逆:治理帳照舊逐筆追加,拿掉第二批列後新推送不再產第二批壞法,已記的處置照第一版以行為單位續用
- 守衛面:不排除——新錨點與新類別會改推送前選擇點那一道挑出的壞法,所以走設計審;S7 守住只含第一版語法的行挑選結果不變;型錄、規則、樣本任一項半套會讓整張表判壞、所有 Kotlin 推送被擋(表從安裝版型錄讀),所以〈回退〉要一次做齊並先跑 check.py。

## 回退

1. 單列撤掉:同一個提交裡一起做——拿掉型錄那一列、規則檔裡那條規則、樣本檔裡那一列的 HIT/MISS 標記;〈統計〉的列數改掉;列號加進說明段 `已撤列號:` 那一行;說明段的不收理由補撤列原因與日期;撤之前把 `gov --stats` 那一列的「依列號」數字抄進 Verification。推之前跑一次 `python3 configs/ast-grep/kotlin-android/check.py --catalog-only --sg <ast-grep 路徑>`:規則對不上列、列數對不上、已撤列號又出現、樣本標記指向表裡沒有的列號,任一項漏了它會紅(範圍 4)。
2. 整批撤掉:同第 1 項對第二批的每一列做一次,外加刪掉 `nul.yml` 與 `samples/choice-batch2.kt`,改掉 Systems/kotlin規則包 的 `about_code` 與第二批那條 WHY 行;新錨點、NUL 類別、「依列號」統計的程式碼留著,沒有列會走到它們(S7 守第一版各行挑法不變)。
3. 撤掉之後,已記的處置照第一版以 (檔, 行指紋) 為單位續用,同一行之後挑到的第一版壞法會沿用那筆處置——撤列的觸發條件正是「等價」放行偏多,所以撤掉那一列時,那批「這個 `!!` 等價」的放行會外溢成同一行第一版壞法的放行(處置不含列號,第一版既定取捨,〈天花板〉第 5 條);要不要在撤列提交時把這些行列出來重看,由人決定。回報上限的抽樣種子跟著重洗;人裁寫回計劃的條款與綁定測試留在計劃裡照算(條款本身是需求,跟哪一列無關)。

## 天花板

1. 只收網上有公開來源點名的少數寫法;沒列到的誤用照樣不管(同第一版天花板 1)。
2. 語法樹沒有型別:`let`→`also`、`$A!!` 的型別前提只能近似,同名自訂函式分不出;編不過的落成跑不出結果要人放行。
3. Compose 兩列在只有單元測試平台的專案多半沒有可守的測試,只提醒、靠人驗。
4. 誤用證據來自官方文件與規則頁的說明,沒有頻率統計;「最容易誤用」是依來源強度排的,不是量出來的。
5. 處置以「行」為單位(第一版舊否決的取捨):型錄加列或撤列讓混合行換挑壞法時,那一行既有的處置照算給新壞法,不重跑;要逐壞法精準就得改處置鍵,那是另一份計劃。
