# 選擇點表第二批常見誤用寫法_計劃

## 白話

[[Projects/改動選擇點都要有需求守住_計劃]] 第一版的選擇點表只收論文表 1 的五類運算子加 13 個集合與 Flow 兄弟寫法;在兩個真實 Kotlin 專案量到只有 13–15% 的程式行有選擇點([[Verification/2026-11-15_改動選擇點真實Android端到端驗收]])。使用者 2026-11-15 要「上網搜一下,最容易誤用的情境語法列進來」。這份把網上有公開來源點名「常被誤用、換成兄弟寫法照樣編得過、行為卻不同、單元測試分得出」的 Kotlin/Android 寫法收成第二批列,每列仍是一個語法節點對一組一對一機械壞法,沿用同一套掃描、挑壞法、殺傷力與推送前那一道,不改判定規則。

第二批(候選,設計審定案):
- 空值處理:`$A ?: $B` → `$A!!`(遇到 null 從用預設值變成當掉);`$A?.方法` → `$A!!.方法`(從略過變成當掉)。
- 範圍函式:`.let` → `.also`(回傳值從區塊結果變成接收者本身)。
- Flow 合併:`combine` → `zip`(任一邊有新值就輸出 → 兩邊成對才輸出;接收者寫法與頂層函式寫法都收)。
- Compose 副作用與記憶:`LaunchedEffect(<key…>)` 的 key 換成 `Unit`(key 變了不重跑);`remember(<key…>) { … }` 拿掉 key(參數變了還顯示舊值)。

PRIOR-ART: 第一版同一套(論文〈Practical Mutation Testing at Scale〉https://arxiv.org/pdf/2102.11378 2.2 在語法樹上產生、表 1、3.2.1 型別前提事前擋;MutApi 的 API 兄弟改寫表(Wen 等,ICSE 2019,https://doi.org/10.1109/ICSE.2019.00093,全文 https://sqlab-sustech.github.io/files/paper/ICSE2019-mutapi.pdf))。誤用證據:Kotlin null safety 官方頁 https://kotlinlang.org/docs/null-safety.html 與 Detekt `UnsafeCallOnNullableType`(https://detekt.dev/docs/rules/potential-bugs);範圍函式官方頁 https://kotlinlang.org/docs/scope-functions.html;Flow 官方頁 combine 與 zip 段 https://kotlinlang.org/docs/flow.html;Compose 副作用官方頁 https://developer.android.com/develop/ui/compose/side-effects(LaunchedEffect key)與狀態官方頁 https://developer.android.com/develop/ui/compose/state(remember key)。不採:`runCatching` 吞取消(Detekt `SuspendFunSwallowedCancellation` https://detekt.dev/docs/rules/coroutines)——壞的方向是把 try/catch 改寫成 runCatching,跨多個節點、不是一對一壞法,改由情境決策表或 Detekt 規則管;Flow `catch` 換位置——要動兩個節點的順序;`launch`↔`async`、`groupBy`↔`associateBy`、`MutableStateFlow`↔`MutableSharedFlow`——回傳型別不同多半編不過;`remember`↔`rememberSaveable`、拿掉 `derivedStateOf` 外的 remember——單元測試分不出(論文附錄 A.1.4 同理);`==`→`===`——論文附錄 A.1.23 只換對應的否定。
RETIRE-IF: 上線兩個月後讀 `gov --stats` 的選擇點分列:第二批任一列被回報的存活裡判「等價或不是需求」超過八成,或「跑不出結果(壞法編不過)」超過一半,就把那一列從表裡拿掉(計劃〈回退〉第 2 條)。
REVISIT:2027-01-15 跟第一版的 REVISIT 一起看第二批各列的殺掉率、編不過率與放行理由,決定留哪幾列、要不要再收 Compose 參數常數

## 舊否決比對

- [[Projects/改動選擇點都要有需求守住_計劃]]〈不做〉「不收數字常數、字串常數、when 分支刪除」:這份不碰,只加 API 與空值兩種節點。
- 同一份〈選擇點表〉的「不收」清單(first/last、collectLatest、Dispatchers.* 等):這份不翻,理由同(單元測試分不出或常掛住)。
- 論文附錄 A.1.10「跟 null 比較不產生」:這份的空值兩列換的是 `?:` 與 `?.`,不是 `== null`;乾節點規則 A-8 不動。

## 用詞

- **論文**、**選擇點表**、**乾節點規則**、**錨點**、**型別前提**:同 [[Projects/改動選擇點都要有需求守住_計劃]]〈用詞〉。
- **新錨點「函式名」**:頂層呼叫 `combine(a, b) { … }` 的函式名識別字所在行;壞法只替換那個識別字(同「方法名」錨點的換法,只是前面沒有 `.`)。
- **新錨點「引數」**:呼叫的 `value_arguments` 節點起始行;壞法替換或刪掉整個引數清單。
- **新類別 NUL**:空值處理運算子(`?:`、`?.`)的壞法;型錄類別欄多一個合法值,`check.py` 與 lumos 讀表時認得它。

## 不做

- 不收多節點壞法(`runCatching` 改寫、`catch` 換位置)、回傳型別不同的互換、單元測試分不出的互換(理由見 PRIOR-ART)。
- 不改一行一個壞法、回報上限、乾節點、殺傷力判定與推送前那一道的規則。
- 不收 Compose 參數常數(`16.dp` 等),等 REVISIT 看數字。

## 實務隱患

- 編不過:`.let`→`.also` 在區塊結果型別跟接收者不同時編不過;`$A ?: $B`→`$A!!` 在 `$A` 不是可空型別時編譯器只警告不報錯(行為不變,等價存活)。語法樹沒有型別,這兩列不設型別前提(近似條件判不準,寧可讓它跑);編不過的落成 no_result、人可判不適用,`--stats` 依列號累計,編不過超過一半照 RETIRE-IF 拿掉那一列。
- 等價存活:`$A!!` 在 `$A` 實際不會是 null 的地方是等價;回報上限與放行理由「等價」承接,RETIRE-IF 看比例。
- Compose 測試成本:`LaunchedEffect`、`remember` 列要 Compose UI 測試(`createComposeRule`)才分得出,單元測試平台 `kotlin-junit` 跑不到時那幾行只能人驗或放行;計劃碰到沒有可守測試時照第一版只提醒不擋。
- 掃描量:新規則讓有選擇點的行變多,推送前時限照第一版(`_KT_SIT_BUDGET`、`_CHOICE_PICK_BUDGET`);實作時在兩個真實專案重量一次掃描耗時。
- 併發與交易:已排除:沿用第一版,單人單機依序操作。
- 已排除:金流:只改型錄、規則與產壞法的程式,不碰付款或金額計算
- 已排除:對外送出:掃描與殺傷力都在本機跑,不對外送任何資料
- 已排除:不可逆:治理帳照舊逐筆追加,拿掉第二批列即回到第一版行為
- 守衛面:不排除——新錨點與新類別會改推送前選擇點那一道挑出的壞法,所以走設計審;S7 守住第一版各列的挑選結果不變。

## 驗收條款

- [S1] 當改動行有 `$A ?: $B`,choice-points 應 挑出 NUL 類壞法 `$A!!`,外層是運算式時加括號;`$A` 是 null 字面值的不產生 [test:t_choice_points_nul_elvis]
- [S2] 當改動行有 `a?.b?.c` 鏈,choice-points 應 只把挑中的那一個 `?.` 換成 `!!.`、其餘不動 [test:t_choice_points_nul_safecall]
- [S3] 當改動行有 `.let {` 與接收者寫法 `.combine(`,choice-points 應 照方法名錨點換成 `also`、`zip`;頂層 `combine(a, b) {` 應 照函式名錨點換成 `zip` [test:t_choice_points_batch2_api]
- [S4] 當改動行有 `LaunchedEffect(k1, k2) {`,choice-points 應 把引數清單換成 `(Unit)`;`remember(k) {` 應 刪掉引數清單;沒有尾隨 lambda 的 `remember(k)` 應 不產生 [test:t_choice_points_compose]
- [S5] 當型錄有 NUL 類別、函式名或引數錨點的列,check.py 與 lumos 讀表 應 認得;類別或錨點寫錯 應 擋並指出哪一列 [test:t_choice_table_batch2]
- [S6] 當新樣本檔跑過 check.py,每條第二批規則 應 命中該命中的、不命中不該命中的 [test:t_kotlin_rulepack_samples]
- [S7] 當第二批列加入後,第一版各列在既有樣本上挑出的壞法 應 不變(行指紋相同、壞法相同) [test:t_choice_points_stable]

## 回退

- 單列誤報或編不過多:從〈選擇點表〉拿掉那一列(下一次推送就不再算;舊帳以行為單位照算)。
- 整批撤掉:拿掉 C-32 起的列與新規則檔;新錨點與 NUL 類別的程式碼留著不影響第一版。

## 天花板

1. 只收網上有公開來源點名的少數寫法;沒列到的誤用照樣不管(同第一版天花板 1)。
2. 語法樹沒有型別:`let`→`also`、`$A!!` 的型別前提只能近似,編不過的落成 no_result 要人放行。
3. Compose 兩列在只有單元測試平台的專案多半沒有可守的測試,只提醒、靠人驗。
4. 誤用證據來自官方文件與規則頁的說明,沒有頻率統計;「最容易誤用」是依來源強度排的,不是量出來的。
