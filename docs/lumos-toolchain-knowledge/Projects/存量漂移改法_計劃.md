## 做法

### 1. `lumos drift fix` 入口與寫入順序

- 語法:`lumos drift fix <節點> <行號> --kind <種類> [--dry-run] [種類專屬參數]`。`--kind` 只收 c1–c5;`probe`(乙的條件式回頭條件成立)不在這裡,回 2 並指到「把待辦做掉後刪行或改寫,照留就 drift ack」。`drift` 子命令現在「不是 scan 就當 ack」,改成明確分派 scan、ack、fix 三支(不然 fix 會被當成 ack 執行);`HELP_WHEN` 與 argparse 的 help 一起補。
- 順序(每一步失敗都回 2、印原因):
  1. **鎖外只讀準備**:先確認那一篇在 git 裡沒有未提交的改動(工作目錄與暫存區都乾淨;有就回 2,說明「先提交或還原,不然改壞了用 git 退不回來」,`--dry-run` 不受限);用 `load_raw_for_edit` 讀一次(它對 BOM、CRLF 直接拒絕——在這一步就回 2,`--dry-run` 也一樣,預覽跟實寫才會一致);依種類做需要 git 的查詢——c1 推轉正日期(第 2 節;只有沒給 `--date`、正文也沒有已寫的轉正日期、又有要寫日期的預告句時才去查 git)、c4 查證據(第 5 節)。git 查詢逾時、不在 git repo 都回 2 並講原因。git 放在鎖外,因為寫入鎖 30 秒沒放就被當成死鎖接手(`_VAULT_LOCK_STALE_SEC`)。參數與種類不合(例:`--kind c3` 卻給 `--old`、c1 給 `--by`、pending 的 settle 給 `--date`、c4 只給 `--old` 或只給 `--new`、`--old` 是空字串)、`--date` 格式錯或晚於今天,在這一步回 2。
  2. **`--dry-run`**:不拿鎖,用第 1 步讀到的內容照第 4 步算出改後內容,印改前改後,回 0;不寫筆記、不寫帳。c4 帶 `--old/--new` 時印改前改後,不帶時印證據與範本(第 5 節)。
  3. **拿筆記庫寫入鎖**(`_vault_write_lock`,可重入),★鎖內重建整個圖譜物件★(`Env(vault)`;c3 要看別篇計劃的狀態、c2 要看連結,只換目標那一篇,其他篇還是等鎖前的舊資料;只呼叫 `load_vault` 換不掉 `Env` 建的名稱與連結索引),用 `_drift_state_findings(env, only={那一篇的路徑})` 重判(only 是集合,傳字串會變成子字串比對),指定的行要還是這一種發現;不是就回 2,訊息講「這一行現在不是 <種類>:可能已經被修掉(c1 一次改整篇),重跑 drift scan 看最新清單」。c1 若鎖內內容需要日期、第 1 步卻沒推(兩步之間被別人改過),回 2 要人重跑。
  4. **算出改後內容**(各種類見下)。
  5. **寫筆記**:`atomic_write_verify`(它在取代原檔之前先驗開頭欄位;失敗丟例外、原檔不動,例外照鄰居 settle 的接法轉成回 2)。取代之後再從磁碟重讀、重建圖譜物件、跑同一支判定,確認這一筆已處理——判準依種類:c1 那一篇沒有 c1;c2、c3、c5 那一篇沒有這一種發現;c4 被換的那一段不再含那三個詞(同一欄別項還含是別筆)。沒處理到就還原:★只在磁碟上的內容還是我們剛寫的那一版(指紋相同)時,才把改前原文寫回★;指紋不同表示有不拿鎖的寫入者在中間改過,不還原、回 2 並印兩個版本的指紋讓人處理(`lumos set`/`append`/`remove` 有拿鎖,但 `decision-add`、`guard bind`、`new` 這類直接寫檔的沒有)。還原本身失敗(權限、磁碟滿)也回 2,印改前改後的指紋與「用 git checkout 那一篇還原」——第 1 步已確認這篇沒有未提交的改動,所以 git 一定退得回去。
  6. **寫修復帳**(第 7 節)。帳寫不進去:同第 5 步的條件把筆記還原、回 2。
- 故障注入接縫(給測試用):環境變數 `LUMOS_DRIFT_FIX_FAULT=verify|ledger` 讓第 5 步的驗證或第 6 步的寫帳假裝失敗,測試才觀察得到「還原」那條路;只認這兩個值。

### 2. c1:已 pass 的守衛紀錄補改預告句

- 前提(鎖內):守衛紀錄讀得出 `預告的合約:` 那一行;家節點(守衛紀錄指名的功能節點)現在的摘要裡有這條合約的正式行、而且綁了至少一支測試(`_guard_formal_line` 不給測試名時的判準)。不符就回 2,說明兩條出路:「這條合約其實還沒轉正——把 status 改回 pending 後走 guard settle」或「正式行寫在別處——手動改句後對剩下的 c1 用 drift ack」。
- 改法:`_guard_settle_rewrite` 改整篇(四種預告句是一組;改完那篇的 c1 全部消失)。
- 轉正日期(只有要寫日期時才需要——TEST、WHY 兩句與換成「(日期 已轉正)」的 settle 句;只改「為什麼還不做:」或 settle 句因手補段而刪掉時不需要),依序:
  1. `--date YYYY-MM-DD`。
  2. 那篇裡已經寫過的轉正日期:正文人手補的「<日期> 已轉正」段、或摘要 WHY 行尾已有的「(<日期> 已轉正)」;用那個日期(同一篇不出現兩個日子)。兩處都有而日期不同就回 2,要人給 `--date`。
  3. 守衛紀錄自己的歷史:`git -c core.quotePath=false log --reverse --format=%H%x09%as -G "^status: pass" -- <守衛紀錄>`(走 `_nodehome_git`;路徑用那個提交裡 git 實際存的寫法——先用 `_nodehome_list` 列出 HEAD 的路徑,找 NFC 相同的那一條,不拿磁碟上的寫法直接查),逐筆讀那個提交的那一篇,第一筆 status 是 pass 的取它的日期。settle 轉正時同一次寫入就把 status 改成 pass,所以這一筆就是轉正那天。不用 `git log -S <合約文字>`:settle 是原地換行,合約文字出現次數不變,`-S` 找不到轉正那次(設計審 r1 四席報到,編排者重現)。
  4. 推不出來(沒有這樣的提交、repo 是 shallow(`_git_is_shallow`)、守衛紀錄改過名)就回 2,要人給 `--date`;不拿今天充數。
- 跟手補的段不疊(新行為,現在一律替換):改寫「做完之後跑 lumos guard settle 轉正」那句時,往下跳過空行,下一個非空行如果符合 `^\(?\d{4}-\d{2}-\d{2}\)? ?已轉正`,就刪掉 settle 句本身那一行(不是手補那行),連同它後面緊接的一個空行,避免留兩個空行;因此刪掉的 settle 句算處理過,不進 `missing`。`_guard_settle_rewrite` 改成可以刪行;settle 與 fix 共用這一支。

### 3. `guard settle` 對 pass 節點

- 現在:pass 一律印「已轉正,不用再做」回 0。改成:還有預告句就走第 2 節同一支(前提、日期、不疊、修復帳 `via: guard settle`);沒有預告句照舊。這是新行為,不是既有的「做到一半補完」(那個指家節點已是正式行、守衛紀錄還 pending)。
- 鎖的順序跟 fix 一樣:`cmd_guard_settle` 現在整段包在寫入鎖裡。改成先在鎖外讀一次狀態——pass 而且要推日期就先推(同第 2 節,鎖外),再拿鎖、鎖內重讀重判;鎖內發現需要日期、鎖外卻沒推(兩步之間被改過),回 2 要人重跑。pending 照舊整段在鎖內。settle 沒有 `--dry-run`,要先看改法就用 `drift fix --kind c1 --dry-run`。`HELP_WHEN` 的 settle 說明一起改(pass 補改、`--test` 選填、`--date`)。
- 參數:`--test` 從必填改成選填——pending 沒給回 2(訊息同現在必填時的說明);pass 補改句用不到,給了也不檢查。現在一開頭就驗測試名合法(`IDENT_RE`),挪到讀完狀態、確定是 pending 之後。新增 `--date`:只給 pass 補改句用;pending 給了回 2(轉正那一刻就是今天)。pass 補改句的成功訊息不印 `[test:…]`。

### 4. c2 與 c5

- **c2(還開著的 Issue 連著已收尾計劃)**:要人判 Issue 解決了沒,工具只提供兩條路,擇一、必填:
  - `--close --status <值> --why "<一句為什麼算解決,附提交或測試>"`:值限 Issue 的結案狀態(`QUERY_CLOSED_STATUSES` 裡 Issue 會用到的 done、resolved、wontfix);status 用 `edit_fm_scalar` + `edit_fm_sync_status_tag` 改;正文最後加一行「YYYY-MM-DD 結案(存量漂移 c2):<why>」(加行的位置照第 5 節 c3 的規則);改完照第 6 節列出這篇還留著的回頭條件。
  - `--keep --reason "<為什麼還沒解決>"`:等同 `drift ack --kind c2`(同第 8 節記 related 與時間戳記),不改筆記、只寫表態檔。
- **c5(轉正做了一半:家筆記已是正式行、守衛紀錄還 pending)**:只改守衛紀錄一篇(status 改 pass、同步標籤、四種預告句改寫——跟 settle 第二步 `_guard_settle_record` 做的一樣)。那支現在自己寫檔、自己印訊息,不能直接叫;拆出「給舊的行、回新的行」那一段(`_guard_settle_record_lines`),settle 與 fix 共用,寫入、驗證、還原、記帳照第 1 節走。測試名不用人給:從家節點那條正式行讀出它綁的測試(`resolve_test_refs`,多平台專案帶平台前綴時取識別字),好幾支就取第一支並在訊息寫出來;修復帳記下用了哪一支。家節點還留著重複的預告行(settle 的「只把重複的預告行拿掉」那種情況)就回 2,指到 `guard settle`——fix 不代改家節點。日期用今天(補完的那一刻就是轉正完成)。

### 5. c3 與 c4

- **c3**:參數 `--status`(必填)、`--by <節點>`(選填)。合法值:驗證紀錄的合法狀態扣掉 pending(pass、stale、superseded、abandoned;abandoned 指這份驗證不做了)。這張表現在是 `_lint_collect` 裡的區域字典 `_STATUS_ENUM`(類型→狀態集合),抽成模組層常數,lint 與 fix 共用;筆記形狀擋 `_nl_rule_status` 那份手寫字串表不在本計劃範圍,不動。寫入:status 用 `edit_fm_scalar` + `edit_fm_sync_status_tag`;正文最後加一行,文字依狀態:pass 寫「YYYY-MM-DD 狀態改為 pass(存量漂移 c3)」,有 `--by` 接「,由 `[[<節點>]]` 解決」;stale、superseded、abandoned 寫「YYYY-MM-DD 狀態改為 <值>(存量漂移 c3)」,有 `--by` 接「,參考 `[[<節點>]]`」。`--by` 先查 `env.by_stem` 看同名有幾篇(`env.find` 遇同名只印警告、回第一篇,判不出猜不準),找不到或同名好幾篇回 2,只有一篇才用 `env.find` 解;寫進去的連結用解出來的完整相對路徑(去 `.md`),不寫人給的短名。加的那一行放在正文最後一個非空行之後、隔一個空行,檔尾保留一個換行;正文為空就放在開頭欄位結束那行之後;正文結尾停在沒閉合的程式碼圍欄裡就回 2(加進去會變成程式碼的一部分)。原本的正文不改。
- **c4 不帶改寫參數**(`--dry-run` 同):列證據與範本,回 0 不寫——①那篇驗證紀錄第一次被提交的提交編號(既有的 `_plan_first_commit`;改過名的只看得到改名後那次);②`governance/review-reports/` 底下目錄名含那篇 plan_refs 計劃名(去 `_計劃`、NFC、不分大小寫、`.` 與空白轉連字號)的卷證目錄;③範本句「提交 <sha>;代碼審見 <卷證>」。查不到的寫「查不到」;shallow 時①寫「shallow,查不到最早提交」。
- **c4 帶 `--old "<原片段>" --new "<新片段>"`**:在那篇開頭欄位 `valid_under` 的原始文字行(欄位那一行到下一個欄位之前)裡找 `--old`,★剛好出現一次才換★(零次或好幾次回 2,並列出那幾行讓人挑更長的片段);直接在原始文字上換掉那一段,欄位的寫法(單行、清單、多行區塊)、其他項目與排版一字不動。`--new` 不得含換行、不得含那三個詞(會立刻再被列出,回 2,提示改用 drift ack)。同一欄有兩項以上含那三個詞時,一次修一項,每修一項那一項就不再含,不會因為別項還含而被當成沒修好(第 1 節第 5 步的 c4 判準)。`--new` 跟範本句一樣時修復帳記 `template_used: true`。

### 6. 結案 Issue 的回頭條件

- 抽出一支共用函式 `_revisit_lines(text)`:用 `_search_visible_lines` 剝程式碼區,餵 `_strip_inline_markup` 之後的 `_revisit_split`,回這篇每一條回頭條件(行號、種類、日期、原文)。E5 改用它(行為不變),下面的結案列出也用它——這兩處共用;其他地方(乙的 `_probe_lines`、第一層、第二層)各自的逐行迴圈不在本計劃範圍,不動。

## 誠實界線

- c4 的卷證目錄是用名字比對猜的,可能漏或多;所以只提議、不寫入。
- c1 的日期看守衛紀錄第一次變成 pass 的提交:守衛紀錄改過名(`git log` 不跟改名)、或當時人手改 status 再另外 settle,推出來的日子會不對或推不出,這種要人給 `--date`。日期取作者日期(`%as`),推送前把好幾個提交壓成一個時,是壓成的那一筆的作者日期,可能比實際轉正早一兩天。
- c4 的「第一次提交」:驗證紀錄改過名的,只看得到改名後那一次。
