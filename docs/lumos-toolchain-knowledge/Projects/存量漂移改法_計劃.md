## 範圍

- **做**:①`lumos drift fix <節點> <行號> --kind <種類>`:五種發現都有工具路——c1 補改預告句、c2 結案(開頭加結案橫幅)或照留、c3 改狀態加一行、c4 精確替換前提片段、c5 補完轉正;②`guard settle` 對「pass 但預告句還在」補做改句,`--test` 改選填、多一個 `--date`;③doctor E5 對已結案 Issue 的到期回頭條件標出「這篇 Issue 已結案」,`lumos set` 把 Issue 改成結案狀態時列出它還留著的回頭條件(E5 與這裡共用一支判定);④c2、c3 的表態記下當時連著的已收尾計劃與遞增序號,之後多了新的收尾計劃就重新列出;沒記清單的舊 c2、c3 表態不再算數;⑤修復帳:每改一筆記一行稽核紀錄;⑥提示文字指到新指令(單一產生處)。
- **不做**:改 drift check 的判定規則;把 drift check 接進推送前掛鉤與 CI(那是 [[Projects/存量漂移防線_計劃]]〈做法〉第 4 節第 4 點,本計劃落地後照它的三個門檻做);機制①(程式改了、舊句還在,歸 [[Projects/舊句偵測實驗_計劃]]);自動還原(改壞了用 git 還原,工具只負責不在不乾淨的筆記上動手);rtb 那 24 筆由 rtb 會談用新指令修(本計劃只負責工具)。

## 做法

### 1. `lumos drift fix` 入口與寫入順序

- 語法:`lumos drift fix <節點> <行號> --kind <種類> [--dry-run] [種類專屬參數]`。`--kind` 只收 c1–c5;`probe`(乙的條件式回頭條件成立)回 2 並指到「把待辦做掉後刪行或改寫,照留就 drift ack」。`<節點>` 同名好幾篇(`env.by_stem` 多於一篇)回 2,要人給完整路徑——fix 會改檔,不能靠 `env.find` 猜第一篇。`drift` 子命令現在「不是 scan 就當 ack」,改成明確分派 scan、ack、fix 三支;`HELP_WHEN` 的 drift 與 settle 說明、argparse 的 help 一起補。
- 參數與種類的組合(不合就回 2):c1 收 `--date`;c2 收 `--close --status <值> --reason "<…>"` 或 `--keep --reason "<…>"`(二擇一、必填);c3 收 `--status`(必填)、`--by`;c4 不帶參數或同時帶 `--old`、`--new`(只給一邊、空字串回 2);c5 不收參數。`--date` 格式錯或晚於今天回 2。`--reason` 一行、4 到 200 字(同 drift ack 的下限)。
- 順序:
  1. **乾淨檢查**:那一篇要在 git 裡有追蹤(未追蹤、被忽略的回 2:不在版控裡,改壞了退不回來),而且跟 HEAD 相比沒有改動,★或者★現在的內容指紋等於修復帳裡這一篇最後一筆的 `after_sha256`(改動全是工具自己留下的——所以同一篇可以一項一項修,修完一起提交)。不乾淨回 2,說明「先提交或還原」。`--dry-run` 不做這一步。
  2. **讀與判定(鎖外)**:用 `load_raw_for_edit` 讀那一篇(BOM、CRLF 直接拒絕,回 2;`--dry-run` 也一樣,預覽跟實寫才會一致),記下它的內容指紋;新建一份圖譜物件(`Env(vault)`),用 `_drift_state_findings(env, only={那一篇的路徑})` 判定指定的行現在確實是這一種發現,不是就回 2(「這一行現在不是 <種類>:可能已經被修掉,重跑 drift scan 看最新清單」);跑各種類的前提檢查;需要 git 的查詢(c1 推日期、c4 查證據)也在這一步,git 查詢逾時、不在 git repo 都回 2 並講原因。重判與前提都放在鎖外:鎖 30 秒沒放就被當成死鎖接手(`_VAULT_LOCK_STALE_SEC`),大圖譜重建可能超過。
  3. **算出改後內容**(各種類見下),並檢查:工具要寫的自由文字(`--reason`、`--new`、`--by` 解出的連結)先跑筆記形狀擋的同一支判定(新寫的程式行號引用、沒帶來源的 FACT/FLOW/DEP),會被擋就回 2——不寫出一份提交前一定被擋的筆記。
  4. **`--dry-run`**:印改前改後(c4 不帶 `--old/--new` 時印證據與範本),回 0;不寫筆記、不寫帳。因為第 2、3 步都做了,預覽過的真跑只會因為「兩步之間那篇被改了」而不同。
  5. **寫(鎖內)**:拿筆記庫寫入鎖(`_vault_write_lock`),從磁碟重讀那一篇,指紋要等於第 2 步記下的;不同就回 2(「判定之後這一篇被改過,重跑」),不寫。相同就用 `atomic_write_verify` 寫入(它在取代原檔之前先驗開頭欄位;失敗丟例外、原檔不動),寫入例外(含 OSError)一律轉成回 2 並印原因。放鎖。
  6. **驗證(鎖外)**:從磁碟重讀,內容指紋要等於第 3 步算出的改後內容——這樣「只改了一半」也抓得到;再重建圖譜物件跑一次判定,確認這一筆已處理(判準見各種類)。不符就回 2,印「寫入後內容跟預期不同,用 `git checkout -- <路徑>` 還原後重跑」——★不自動還原★:自動還原要處理不拿鎖的寫入者、還原本身失敗、中斷等情況,設計審三輪都在這裡長出新洞;第 1 步保證了這一篇在版控裡而且改前是乾淨的(或只有工具自己的改動),git 一定退得回來。
  7. **寫修復帳**(第 7 節)。帳寫不進去回 2,印「筆記已改好,但修復帳沒記到;這一篇的改動用 git diff 看得到」——不動筆記。
- 故障注入接縫(給測試用):環境變數 `LUMOS_DRIFT_FIX_FAULT=verify|ledger` 讓第 6 步的驗證或第 7 步的寫帳假裝失敗,只認這兩個值。

### 2. c1:已 pass 的守衛紀錄補改預告句

- ★放哪裡★:改句(`_guard_settle_rewrite`)、前提檢查、轉正日期推導都放在 guard 區段(家是 Systems/guard-kill),drift fix 與 guard settle 都往下呼叫;guard 區段不呼叫 drift 區段(現況的方向是 drift 呼叫 guard 的判準)。修復帳、drift 的事件只由 drift fix 寫。
- 前提:守衛紀錄讀得出 `預告的合約:` 那一行;家節點(守衛紀錄指名的功能節點)現在的摘要裡有這條合約的正式行、而且綁了至少一支測試(`_guard_formal_line` 不給測試名時的判準)。不符就回 2,說明兩條出路:「這條合約其實還沒轉正——把 status 改回 pending 後走 guard settle」或「正式行寫在別處——手動改句後對剩下的 c1 用 drift ack」。
- 改法:`_guard_settle_rewrite` 改整篇(四種預告句是一組;改完那篇的 c1 全部消失)。處理到的判準:那一篇沒有 c1,而且磁碟內容等於算出的改後內容。
- 轉正日期(只有要寫日期時才需要——TEST、WHY 兩句與換成「(日期 已轉正)」的 settle 句;只改「為什麼還不做:」或 settle 句因手補段而刪掉時不需要),依序,取第一個有的:
  1. `--date YYYY-MM-DD`。
  2. 那篇裡已經寫過的轉正日期:正文人手補的「<日期> 已轉正」段、或摘要 WHY 行尾已有的「(<日期> 已轉正)」。兩處都有而日期不同就回 2,要人給 `--date`。
  3. 守衛紀錄自己的歷史:`git log --reverse --format=%H%x09%as -G "^status: pass" -- <守衛紀錄>`(走 `_nodehome_git`;路徑用 `git ls-files -z` 列出的原樣位元組比對 NFC,找到那一條就用它——`_nodehome_list` 回的是 NFC 正規化後的路徑,不能直接拿來查),逐筆讀那個提交的那一篇,第一筆 status 是 pass 的取它的日期。★那一筆如果也是這個檔第一次出現的提交★(`--diff-filter=A`,整批匯入、搬目錄、改名後重新加入都會這樣),日期是匯入那天不是轉正那天,回 2 要人給 `--date`。不用 `git log -S <合約文字>`:settle 是原地換行,合約文字出現次數不變,`-S` 找不到轉正那次(設計審 r1 四席報到,編排者重現)。
  4. 推不出來(沒有這樣的提交、repo 是 shallow(`_git_is_shallow`)、上一條的匯入情況)回 2,要人給 `--date`;不拿今天充數。
- 跟手補的段不疊(新行為,現在一律替換):改寫「做完之後跑 lumos guard settle 轉正」那句時,往下跳過空行,下一個非空行如果符合 `^\(?\d{4}-\d{2}-\d{2}\)? ?已轉正`,就刪掉 settle 句本身那一行(不是手補那行),連同它後面緊接的一個空行;因此刪掉的 settle 句算處理過,不進 `missing`。`_guard_settle_rewrite` 改成可以刪行;pending 轉正也走這一支,遇到手補段一樣刪——同一種句子不因入口不同而結果不同。
- 寫錯日期怎麼辦:改寫後的句子是一般筆記文字,手改日期即可;修復帳記著改了哪幾行。

### 3. `guard settle` 對 pass 節點

- 現在:pass 一律印「已轉正,不用再做」回 0。改成:還有預告句就補改(第 2 節同一支:前提、日期、不疊);沒有預告句照舊回 0。這是新行為,不是既有的「做到一半補完」。★前提不符會回 2★,以前這種情況回 0:把 settle 當「重跑無害」在腳本裡呼叫的地方會看到新的失敗——訊息講清楚兩條出路。
- 鎖的順序:讀狀態、推日期、前提檢查在鎖外,拿鎖後比對那一篇指紋沒變才寫(同第 1 節第 5 步);pending 照舊整段在鎖內。settle 不寫修復帳、不做乾淨檢查(它是守衛自己的轉正指令,既有的 pending 轉正也沒有);要先看改法、或要乾淨檢查與修復帳,用 `drift fix --kind c1`。
- 參數:`--test` 從必填改成選填——pending 沒給回 2(訊息同現在必填時的說明);pass 補改句用不到,給了也不檢查。現在一開頭就驗測試名合法(`IDENT_RE`),挪到讀完狀態、確定是 pending 之後。新增 `--date`:只給 pass 補改句用;pending 給了回 2。pass 補改句的成功訊息不印 `[test:…]`。

### 4. c2 與 c5

- **c2(還開著的 Issue 連著已收尾計劃)**:要人判 Issue 解決了沒,工具只提供兩條路:
  - `--close --status <值> --reason "<一句為什麼算解決,附提交或測試>"`:值限 Issue 的合法狀態裡的結案值——done、resolved、wontfix(從狀態表的 issue 那一格與結案集合取交集,不用跨類型的 `QUERY_CLOSED_STATUSES` 直接判)。status 用 `edit_fm_scalar` + `edit_fm_sync_status_tag` 改;★正文第一個 `# ` 標題之後、第一段之前加結案橫幅★(專案規定:已結案 Issue 正文第一段就寫已結案、修法、實證,並標明以下是當時的排查紀錄——見 lumos-project-notes reference 的 Issue 寫法):「> 已結案(YYYY-MM-DD,<值>):<reason>。以下是當時的排查紀錄,不是現況。」;那一篇第一段已經是「已結案」開頭的橫幅就不加、在訊息寫出來。改完照第 6 節列出這篇還留著的回頭條件。處理到的判準:那一篇沒有 c2、磁碟內容等於算出的改後內容。
  - `--keep --reason "<為什麼還沒解決>"`:等同 `drift ack --kind c2`(第 8 節),不改筆記、只寫表態檔,不做乾淨檢查、不寫修復帳。
- **c5(轉正做了一半:家筆記已是正式行、守衛紀錄還 pending)**:只改守衛紀錄一篇(status 改 pass、同步標籤、四種預告句改寫——跟 settle 第二步 `_guard_settle_record` 做的一樣)。那支現在自己寫檔、自己印訊息,拆出「給舊的行、回新的行」那一段(`_guard_settle_record_lines`,放 guard 區段),settle 與 fix 共用。測試名不用人給:從家節點那條正式行讀出它綁的測試(`resolve_test_refs`,多平台專案帶平台前綴時取識別字),好幾支就取第一支並在訊息寫出來;修復帳記下用了哪一支。家節點還留著重複的預告行就回 2,說明「家節點同時有預告行與正式行,先手動刪掉預告行再跑」(settle 對重複好幾條也是擋下,指回 settle 會繞圈)。日期用今天(補完的那一刻就是轉正完成)。處理到的判準:那一篇沒有 c5 也沒有 c1、status 是 pass、磁碟內容等於算出的改後內容。

### 5. c3 與 c4

- **c3**:`--status` 合法值:驗證紀錄的合法狀態扣掉 pending(pass、stale、superseded、abandoned;abandoned 指這份驗證不做了)。這張表現在是 `_lint_collect` 裡的區域字典 `_STATUS_ENUM`,抽成模組層常數,lint、fix、c2 共用;筆記形狀擋 `_nl_rule_status` 那份手寫字串表不在本計劃範圍,不動。寫入:status 用 `edit_fm_scalar` + `edit_fm_sync_status_tag`(同 `cmd_set`;fix 的 c2、c3、c5 與 settle 的狀態改寫都走這一對,不另寫);正文最後加一行,文字依狀態:pass 寫「YYYY-MM-DD 狀態改為 pass(存量漂移 c3)」,有 `--by` 接「,由 `[[<節點>]]` 解決」;stale、superseded、abandoned 寫「YYYY-MM-DD 狀態改為 <值>(存量漂移 c3)」,有 `--by` 接「,參考 `[[<節點>]]`」(連結不加反引號,它要算連結)。`--by` 先解:給的是完整路徑就直接查那一篇;給短名就看 `env.by_stem`,找不到或同名好幾篇回 2;寫進去的連結用解出來的完整相對路徑(去 `.md`)。加的那一行放在正文最後一個非空行之後、隔一個空行,檔尾保留一個換行;正文為空就放在開頭欄位結束那行之後;正文最後一行落在沒閉合的程式碼圍欄裡(用 `_visible_lines` 判,正常以圍欄結尾且已閉合的不算)就回 2。處理到的判準:那一篇沒有 c3、磁碟內容等於算出的改後內容。
- **c4 不帶改寫參數**(`--dry-run` 同):列證據與範本,回 0 不寫——①那篇驗證紀錄第一次被提交的提交編號(`_plan_first_commit`,加上逾時參數,逾時當查不到;改過名的只看得到改名後那次);②`governance/review-reports/` 底下目錄名含那篇 plan_refs 計劃名(去 `_計劃`、NFC、不分大小寫、`.` 與空白轉連字號)的卷證目錄;③範本句「提交 <sha>;代碼審見 <卷證>」。查不到的寫「查不到」;shallow 時①寫「shallow,查不到最早提交」。
- **c4 帶 `--old "<原片段>" --new "<新片段>"`**:

## 誠實界線

- c4 的卷證目錄是用名字比對猜的,可能漏或多;所以只提議、不寫入。
- c1 的日期看守衛紀錄第一次變成 pass 的提交:守衛紀錄改過名(`git log` 不跟改名)、當時人手改 status 再另外 settle、推送前把好幾個提交壓成一個(作者日期是壓成的那一筆的),推出來的日子會不對或推不出,這種要人給 `--date`。
- c4 的「第一次提交」:驗證紀錄改過名的,只看得到改名後那一次。
- c2 表態的 `related` 存的是路徑:連著的計劃改名後,會被當成「多了新計劃」重新列出(誤報,方向是多列);重新表態一次就好。
- c2 的 `related` 只記「哪幾篇」,不記它們當時的狀態:同一份計劃重新打開、又再收尾一次,清單不變,舊表態照樣算數。這種情況靠 Issue 本身的回頭條件兜底。

- E5 只標已結案的 Issue:已結案計劃留著的過時回頭條件照樣唸、沒有標記,靠計劃收尾時的連帶待辦處理。
