# 存量漂移改法_計劃

白話:存量漂移健檢(`lumos drift scan`)現在只會「指出」過期的句子,改要人自己動手。rtb 2026-09-29 照清單修的時候,28 筆裡有 24 筆工具沒有路可走,只能留著。這份計劃補「改法」:一個指令 `lumos drift fix`,依發現的種類給現成的改法;另外補兩個結案時的漏洞(結案 Issue 的回頭條件、c2 表態會蓋掉之後的新情況)。

依據:Enzo 2026-09-29 裁「現在開始」(原排 10/13 決定);缺口清單出自 rtb 會談實測回報,記在 [[Projects/存量漂移防線_計劃]]〈修復結果〉。

PRIOR-ART: 最小解在工具鏈自己這一層。①c1 的改句邏輯現成(`_guard_settle_rewrite`,guard settle 第二步),rtb 會談直接呼叫它,7 篇全改對——只差入口;照 guard settle「做到一半可以補完」的既有做法,把「已 pass 但預告句還在」當成第二步沒做完。②外面的做法:lint 工具的 `--fix`(ruff、eslint)是「偵測與改法同一條規則、改法只做機械確定的、其他只提示」,本計劃照這個分:c1 自動改、c3 改狀態加範本一行、c4 只給證據與範本由人填。③表態帶「當時的關係清單」借 ADR 的 superseded 鏈:決定綁著當時的前提,前提變了決定不再自動適用。
RETIRE-IF: 上線兩個月後任一成立就撤掉或重想:①`drift fix` 在工具鏈與 rtb 合計被用不到 5 次(大家寧可手改,入口沒價值);②c1 自動改寫後被人手改回或再改的比例超過兩成(改法不對);③c4 的證據提議被人照抄的不到一半(提議不準)。
REVISIT:2026-11-28 跟 [[Projects/存量漂移防線_計劃]] 的 RETIRE-IF 一起量上面三個數

## 範圍

- **做**:①`lumos drift fix <節點> <行號> --kind <種類>`:c1、c3、c4 三種有改法,其他種類說明沒有改法、指到 `drift ack`;②c1 自動改寫(日期推算、跟手補的「已轉正」段不疊);③c3 改狀態並在正文加一行「由誰解決」;④c4 列出證據(涵蓋那篇的提交、代碼審卷證)與範本,由人給新句子再寫入;⑤doctor E5 對已結案筆記的到期回頭條件標出「這篇已結案」,`lumos set` 把 Issue 改成結案狀態時列出它還留著的回頭條件;⑥c2 的表態記下當時連著的已收尾計劃,之後多了新的收尾計劃就重新列出。
- **不做**:c2、c5 的自動改法(c2 要人判 Issue 解決沒;c5 已有 `guard settle` 重跑);改 drift check 的判定規則;rtb 那 24 筆由 rtb 會談用新指令修(本計劃只負責工具)。

## 做法

### 1. `lumos drift fix` 入口

- 語法:`lumos drift fix <節點> <行號> --kind c1|c3|c4 [--dry-run] [種類專屬參數]`。先用跟 `drift scan` 同一支判定(`_drift_findings` 或對應的種類函式)確認「這一行現在確實是這一種發現」,不是就擋下回 2(防止改錯行)。
- 寫入一律拿筆記庫寫入鎖(`_vault_write_lock`)、用 `atomic_write_verify` 寫、改完重讀自驗;`--dry-run` 只印改前改後,不寫。
- c2、c5 與其他:回 2,說明「這一種沒有自動改法」並印 `drift ack` 或 `guard settle` 的指令。

### 2. c1:已 pass 的守衛紀錄補改預告句

- 用 `_guard_settle_rewrite` 改整篇(不是只改指定那一行:同一篇的四種預告句是一組,只改一句會留下自相矛盾的半套)。
- 轉正日期:`--date YYYY-MM-DD` 有給就用;沒給就從 git 推——家節點裡這條合約的正式行(`KEY:★INVARIANT★ <預告的合約> [test:…]`)第一次出現的提交日期(`git log -S` 找最早那筆);推不出來就擋下、要人給 `--date`,不拿今天充數(rtb 的 F1–F3 實際轉正在 2026-09-23,用今天會寫錯歷史)。
- 跟手補的段不疊:改寫「做完之後跑 lumos guard settle 轉正」那句時,如果它後面(跳過空行)下一段已經以「<日期> 已轉正」開頭,就刪掉這句而不是換成「(日期 已轉正)」(rtb F4–F7 當時人手補過)。
- 找不到的句型照 settle 現在的做法印提醒(`missing`),不當錯誤。
- `guard settle` 本身對 pass 節點的行為:改成「還有預告句就補做第二步」,日期規則同上;沒有預告句照舊印「已轉正,不用再做」。這樣兩個入口共用一支,不分岔。

### 3. c3:驗證紀錄改狀態加一行

- 參數:`--status pass|fail`(必填)、`--by <節點>`(選填,後續解決這件事的紀錄)。
- 寫入:status 用 `edit_fm_scalar` + `edit_fm_sync_status_tag`(同 `cmd_set`);正文最後加一行「YYYY-MM-DD 狀態改為 <值>(存量漂移 c3)」,有 `--by` 就接「,由 [[<節點>]] 解決」。`--by` 指的節點要找得到,找不到擋下。
- 不改正文原本那段(例如「記 pending,因為…紅」):歷史說法保留,新加的一行說明後來怎樣了。

### 4. c4:前提句的證據與範本

- 不帶 `--replace`:列出證據——①那篇驗證紀錄第一次被提交的提交編號與日期(`git log --diff-filter=A`);②`governance/review-reports/` 底下名字含那篇計劃(plan_refs)或 feature 關鍵字的卷證目錄;③範本句「提交 <sha>;代碼審見 <卷證>」。回 0,不寫。
- 帶 `--replace "<新前提句>"`:把 valid_under 裡含「未提交/還沒提交/uncommitted」的那一項換成新句子(清單欄位只換那一項,純量欄位整欄換)。新句子還含那三個詞就擋下(會立刻再被列出),提示用 `drift ack`。
- 不自動寫入:前提是人寫的判斷,工具只找證據。

### 5. 結案 Issue 的回頭條件

- doctor E5:到期清單裡,來源筆記的 status 在 `QUERY_CLOSED_STATUSES` 的,那一行後面加「(這篇已結案)」;照樣列、照樣計數。★不跳過★:已收尾的計劃常刻意留著撤除用的回頭條件(例:[[Projects/最低Python版本改3.14_計劃]] 的 lumos.cmd 那條),跳過會漏。
- `lumos set <Issue> status <結案狀態>`:改完之後,這篇正文與摘要裡還有日期式或條件式回頭條件就逐行列出(行號加原文),提示「結案了,這幾行要改成結案說明或刪掉」;只印、不擋、不改(同計劃收尾時列連帶待辦的做法)。

### 6. c2 表態綁當時的關係

- `drift ack --kind c2` 寫入時多記 `related`:當時那筆發現列出的已收尾計劃清單(排序後的路徑)。
- 比對(`_drift_split_acked`):表態帶 `related` 的,要現在的清單是它的子集才算對得上;現在多出新的收尾計劃就重新列出,並印舊理由供參考(`_drift_old_reason`)。沒帶 `related` 的舊表態照舊只比路徑、原文、種類(2026-09-29 已寫的 17 筆不失效)。
- c3 同理(清單是 plan_refs 裡已收尾的計劃)。其他種類不變。
- 行號移位:表態本來就不綁行號(比的是路徑+原文+種類),寫一條測試釘住「同一篇上面插幾行,表態照樣對得上」。

## 回退

- `drift fix` 是新指令:回退就是拿掉子命令與三支改法函式,既有指令不受影響;已經用它改過的筆記是一般筆記改動,照 fixed.txt 可以找出來(rtb 與工具鏈的修復都要求留 fixed.txt)。
- `guard settle` 對 pass 的新行為:回退成原本的「已轉正,不用再做」一行;已經補改的筆記不用還原(改寫結果本來就是 settle 會產生的樣子)。
- E5 標記與 set 的列出:純多印,回退就是拿掉那幾行印出。
- c2/c3 表態的 `related`:回退時比對忽略這個欄位即可(舊行為);已寫的欄位留在表態檔裡無害。

## 實務隱患

- **資料正確性(碰到)**:c1 自動改筆記內容。防法:只改 `_guard_planned_prose` 認得的四種句型,其他行一字不動;先用 scan 的判定確認種類;`--dry-run`;寫入自驗。
- **歷史日期(碰到)**:c1 的轉正日期寫錯會改寫歷史。防法:推不出就擋,不拿今天;`git log -S` 取最早一筆,shallow clone 推不準時也擋(提交數不足判不出「最早」)。
- **併發(碰到)**:多個會談同時修同一篇。防法:寫入鎖、鎖內重讀狀態(同 settle)。
- **自我治理(碰到)**:改的是漂移健檢的表態比對,比對放寬會讓該列的不列。防法:[S8] 的「舊表態照舊」只放行沒記清單的舊資料;新寫的一律帶清單。
- **向後相容(碰到)**:表態檔多一個欄位,舊版 lumos 讀到會忽略(`_drift_acks_load` 只取需要的鍵),不會壞。
已排除:金流:只改圖譜筆記與表態檔,不碰任何金額或付款流程
已排除:對外送出:不寄信、不打外部服務,只讀本機 git
- 不可逆(碰到,可還原):改的是版控裡的筆記,git 還原得回來;照 fixed.txt 可整批找出
- 效能(不碰):一次只修一篇,git log -S 限定家節點一支檔

## 誠實界線

- c4 的證據是「猜」:卷證目錄用名字比對,可能漏或多;所以只提議不寫入。
- c1 的日期推算靠 git 歷史裡正式合約行的文字;家節點改過名或那行被改寫過,推出來的是改寫那天,不是轉正那天。這種情況要人給 `--date`,工具分不出來。
- E5 不跳過已結案的回頭條件:結案 Issue 的過時提醒照樣會唸,只是多了標記;要安靜得靠 [S7] 在結案當下處理。
