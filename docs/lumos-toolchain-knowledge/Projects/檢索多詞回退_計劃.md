# 檢索多詞回退（計劃）

## 問題（有實例）

```
$ lumos search "BM25 檢索 搜尋 排序 欄位加權"
(候選 0)
```

不是圖譜裡沒有，是**那五個字沒有連在一起出現過**。候選階段是整串子字串比對：

```python
needle = nfc(term).lower()
matches = lambda s: needle in nfc(s).lower()
```

**BM25F 本來就會處理多詞**（`impact --diff` 用整段 hunk 當 query，運作正常）。壞掉的是**前面那道撈候選的關卡**，而它 0 命中時**不回退**（`Systems/retrieval-ranking` 已登記的技術債）。

## ★根因：量測工具的盲區傳染進了量測集★

`build_goldset.py`：

```python
pool = search_pool(q)      # legacy + ranked,兩邊同一道子字串比對
if not pool:
    sheet.append("- (無候選——查詢在 vault 無命中,標註跳過)")
```

多詞查詢池為空 → 那題靜默變空 → **goldset 30 題有 29 題是單詞**。

**要修的那個缺陷，從頭到尾不在尺上。** 這與 2026-08-02 同日的另外兩例（合約條文只枚舉一種失效形態、實驗指標跟著 payload 變）是同一個形狀。

## 修法：fallback-only

**只在片語 0 命中時**才退成各詞 OR 召回，再交給 BM25F 排序。

### 為什麼零回歸是「可證」不是「可量」

實測：**現有 goldset 30 題全部回 >0 候選** → 回退條件永不觸發 → **那 30 題行為一行不變**。

這是機械論證，不需要跑評測。若改成「永遠 OR」就不成立——`N/df/avgdl 以候選集為語料`，擴召回會擾動既有排序。

### 代價落在哪

第二趟掃描**只在第一趟 0 命中時發生**——也就是今天本來就什麼都拿不到的查詢。**順利路徑零成本。**

## 順序（★上一版想錯了★）

原本打算「先補評測集，再動 code」。**做不到**——候選池撈不出東西就沒得標。

正確順序：

1. **實作 `--any`，預設關**（不是行為變更，只是多一條可量測的路）
2. **組池**：三來源聯集
3. **標註**：沿用既有雙評（claude/codex）＋不一致深讀裁決寫 `why`
4. **量測**
5. **才決定**要不要變預設

## 待辦與未定

- [ ] M1：`--any` 實作 + 測試（本階段，trivial 級可跳 design-loop）
- [ ] M2：goldset 復驗（先確認尺現在跑出什麼）
- [ ] M3：多詞題組池 + 標註（285d429 worktree）
- [ ] M4：量測 → 裁定預設

**未定**：`--any` 要不要同時支援「AND 優先、OR 墊底」的階梯（先試全詞都中的節點，再放寬）？v1 不做，先看資料。

## ★Landmark 真庫驗證（2026-08-02，284 篇，全程唯讀）★

10 題現實查詢**先寫死再跑**（避免看了資料才挑好看的題目）。

### 結果一：缺陷不是邊角案例

**10/10 在預設下全部 0 命中。** 每一個現實會打的多詞查詢，今天都拿不到東西。

### 結果二：`--any` 的第一名，7/10 明顯正確

`POS 作廢 未同步` → `Issues/2026-07-18_POS作廢未同步_對帳真差異_北村102`（幾乎逐字命中）；
`點數 交易 死鎖` → `Issues/2026-07-27_PointComplete死鎖_CustTransfer全表掃`；
`背景排程 心跳 監控` → `Systems/背景排程總覽`；以及簡訊、LINE、稽核、升降等四題。

3 題不理想：`對帳 假差異 自癒`（相關但不是最該回的）、`發票 補登 排除`、`續會 門檻 計算`。

### ★結果三：最差那題不是排序爛，是查詢用詞錯——而工具沒告訴我★

逐詞覆蓋：`★續會:0★  門檻:50  計算:35`。

**「續會」在整個 Landmark 圖譜裡一篇都沒有**（是我猜錯他們的用語）。剩下兩個超常見詞把結果洗走。

### ★由此發現 OR 回退最大的風險（原本沒想到，是實測逼出來的）★

> **回退之後，搜尋幾乎不可能再回 0——「查無」這個訊號會消失。**

今天「0 筆」至少有時候代表「這個概念不在圖譜裡」。加了 OR 之後，
**你永遠會拿到看起來合理的東西**，而那可能只是常見詞的噪音。
★這比「排序不夠準」嚴重得多★：排序不準你看得出來，訊號消失你看不出來。

**M1.5 的內容**：回退觸發時，把逐詞覆蓋印到 stderr：

```
（多詞回退:整串片語全庫無命中,改用各詞 OR 召回）
  逐詞覆蓋: ★續會:0★  門檻:50  計算:35
```

看到 `續會:0` 就當場知道是用詞錯了，而不是圖譜沒有——**把消失的那個訊號用另一種形式還回來**。

**本輪刻意不順手做**：M1 範圍就是 `--any`，而同日已因趕工出過一次假綠（見下）。M1.5 自己帶測試。

## ★M1 過程中自己犯的假綠（第 12 次，記為教訓）★

`t_search_multiword_fallback_is_opt_in_and_only_on_zero` 的第三條斷言
（「片語真的存在時，回退絕不能觸發」）**第一版是假綠**。

現場用「丙丁」當片語——**單一 token、中間沒有空白**——於是 `len(_fb_terms) > 1`
這道閘直接判假，**OR 路徑一次都沒被執行**。把 fallback-only 守衛拿掉（改成永遠 OR）的
翻紅釘**照樣全綠**。

這正是 [[Systems/測試假綠形態]] 第④型「現場走不到被測分支」，**而且是這條測試自己犯的**。

修法：現場改成**真的是多詞**的片語「丙 丁」，並另建一個只含「丙」的節點——
沒有那個可被誤撈的節點，這條斷言就沒有鑑別力（第⑤型）。修完翻紅釘才真的紅。

## ★M1.5 落地（2026-08-02）★

回退觸發時，把逐詞覆蓋印到 **stderr**：

```
（多詞回退:整串片語全庫無命中,改用各詞 OR 召回;逐詞覆蓋 ★續會:0★  門檻:50  計算:35）
  ★有詞在全庫 0 命中(標 ★)——多半是查詢用詞與圖譜用語不一致,先換那個詞再查,
    別把結果當「圖譜沒有」★
```

- **算在預檢那圈**：它本來就讀了每個檔、也做過同樣的 code 排除，多幾次子字串測試幾乎免費，不另開一圈
- **走 stderr**：與既有「已隱藏 N 筆作廢結果」同慣例，不污染 `--json`／`--files-only` 的機器可讀輸出

### ★實作時抓到的漂移（值得記）★

預檢與主迴圈是**兩份實作**，第一版預檢**沒套用「隱藏作廢節點」的過濾** → 覆蓋數比實際搜得到的多
（Landmark 實測 `門檻 55` vs 搜尋顯示的 `50`，差在 7 筆 superseded）。

★**覆蓋數若 > 實際，使用者會以為「這個詞有東西」而其實搜不到——誤導方向與本功能要解的問題正好相反。**★

因此測試裡放了一條**強斷言**：`覆蓋數必須與逐詞搜尋完全一致`（拿掉過濾就只有這條翻紅，精準）。

**驗證**：9 條斷言含 3 條「現場成立」前置；兩個翻紅釘（拿掉輸出／拿掉過濾）各驗一個方向。
