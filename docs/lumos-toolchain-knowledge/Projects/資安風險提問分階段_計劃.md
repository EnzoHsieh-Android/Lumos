# 資安風險提問分階段_計劃

## 接手先讀：這份計劃管什麼

白話：資安問題漏掉，多半不是不會答，而是當時沒想到要問。這份計劃讓問題從「要保護什麼、誰會碰、從哪裡進來」的清單長出來，像查帳時逐格對表，而不是靠當下想起什麼問什麼；每個問到的問題最後都要有去向，沒去向的會變成看得到的缺口。

- 只管「想到哪些問題、什麼時候問、答案去哪」，不管證據合不合格；證據判定與推送閘在姊妹計劃 [[Projects/安全主張驗收閘_計劃]]。兩篇共用同一套資產、入口、證據種類與工具類別詞彙：證據種類的值域與定義、工具類別的叫法以姊妹計劃〈二〉的證據種類表與〈三〉的工具類別表為準，本篇照抄名稱不另取。
- **兩篇 schema v2 新欄位的唯一完整清單在姊妹計劃〈一〉的〈schema v2 新欄位〉**，含 v1 圍欄讀到時的預設與 v1/v2 怎麼並存；本篇只講這些欄位怎麼用，不另列一份。
- 威脅類別表的正本是 [[Systems/資安威脅類別表]]（2026-10-20 已從本篇〈二〉搬過去、v1 定稿 14 類;待決 Q2 題目寫的「12 類」是發問當時的版本）；「威脅類別 → 最低證據種類 → 工具類別」的對照以那篇為準，姊妹計劃只引用。
- 要求來源：母計劃 [[Projects/消費專案產品安全Brief與證據驗收_計劃]] 的〈提問依決策時機安排，不等交付才確認權限〉（需求、架構、驗證、交付各階段都要有）、〈消費專案資安護欄盤點指令〉的安全覆蓋盤點（G8）、P2 五案三臂方法試行。
- 沿用：需求風險面表 `_REQUIREMENT_FACETS` 與 `pitfalls --stage`（[[Projects/後端工程提問與證據擴充_計劃]] d12、d13）、開頭欄位 `pending_questions` 與它的阻塞規則（[[Projects/待決問題改存開頭欄位_計劃]]）、唯讀盤點的 inventory 與 coverage（[[Projects/資安護欄唯讀盤點_計劃]]）。
- 威脅類別表是「類別對照」，不是題庫：它只決定一格該套哪類問題的模板；產生出來的題一律進消費專案計劃既有的 `pending_questions`，不另開提問帳、不另存一份題目清單。這跟母計劃 d7「不新增平行題庫」不衝突：d7 擋的是另建一套跟情境出題並行的題目與流程，本篇的類別表接在既有需求風險面與 `pending_questions` 後面，題目的家仍是那兩處。

## 一、從「要保護什麼」出發

問題由盤點長出來，不靠臨場回想：
- 沿用盤點 `lumos-security-v1` 的 inventory（已核可的資產與入口清單）當起點；母計劃 G8 本來就要求有版本、有核可的入口盤點。
- inventory 要多三樣才長得出問題（schema v2，欄位清單與 v1 預設見姊妹計劃〈一〉）：
  - `actors`：角色清單（例：擁有者、同站他人、未登入者、管理員、外部系統），每項有 id 與描述。
  - surfaces 每項加 `kind`（固定值域：http_api、web_page、export、file_upload、file_download、webhook_in、outbound_call、batch、message_consumer、admin、cli）、`actor_ids`（誰會從這裡進來）、`boundary_crossed`（這個入口跨了哪道信任邊界，文字）。
    - **盤點規則（威脅類別表 v1 定稿）**：一個入口只有一個 `kind`，不會自動繼承別的 kind 的題目。一個功能同時有瀏覽器畫面、上傳、下載、匯出、外呼、批次處理或訊息消費多種性質時，每種性質各登一個對應 kind 的入口（例如管理後台有瀏覽器畫面時，登 `admin` 之外另登 `web_page`）；依使用者給的網址或主機名發出請求的功能必須另登 `outbound_call`；CLI 處理外來檔案、遠端資料或做高權限操作時照性質另登，不因為是操作者啟動就當成沒跨信任邊界。入口漏登由 review 的 `inventory_complete` 判斷抓。
    - 為什麼不叫 `trust_boundary`：護欄 v1 已經有一個 `trust_boundary` 欄位，意思是「這條護欄在哪道邊界強制」；入口上的是「這個入口跨了哪道邊界」。兩者不必相同（一個入口跨外網到服務端，守它的護欄可能在資料庫層強制），工具不互相比對，所以分兩個名字，讀者不會以為要一致。
  - 用來寫「想過、不適用」與「想過、接受風險」的 `considerations` 清單（見〈四〉）。它是圍欄頂層的鍵，可以放在任何 Systems 節點的 `lumos-security-v1` 圍欄裡，跟那個模組的護欄放在一起，不必全部塞進 inventory 那一塊（現況全庫最多一份 inventory、單檔上限 2 MiB，大專案的 considerations 會撐爆那一篇）。
  - 保留入口 id `@repo`：代表「整個部署單位」，給以 repo 為單位問一次的四類（secrets-mgmt、crypto-use、supply-chain、config-deploy）當格子的入口；它不寫在 surfaces 裡、作者不能自己宣告同名入口（inventory 的 id 照舊不准 `@` 開頭），它的資產固定是 `@repo`（整個 repo 的秘密、依賴、部署設定）。本篇的**部署單位就是一個 repo 根**：一個 repo 根一組 `@repo` 格子，同一 repo 裡有幾個服務也不拆，跟「全庫最多一份 inventory」一致。
    - **要改的檢查**：現在 `_secinv_check_links` 會把護欄 `assets`、`surfaces` 裡的 `@repo` 判成 `reference_error`（指到 inventory 沒有的 ID），四類就永遠登記不上。改法：`_secinv_check_links` 對 `assets` 與 `surfaces` 兩欄放行字面值 `@repo`，id 規則只對這一個字放寬；considerations 的入口與資產欄同一支檢查、同一條放寬。其他任何 `@` 開頭的值照舊是錯誤。
  - controls 的 `required_evidence` 值域擴成姊妹計劃〈二〉證據種類表的全部種類（現行盤點只認 behavior、fault_sensitivity、review、deployment、dependency_scan；新增 concurrency、static_analysis、secret_scan、dynamic_scan、fuzz、config_scan），定義以那張表為準；照盤點規矩升 `schema_version`，不用未知字串冒充。
- 理由：問題要逐格產生，格子的軸（入口、資產、類別，三類再加角色）必須是結構資料；寫在散文裡工具算不出缺口。
- 不選：另開一份威脅模型檔或引入 pytm 的 Python 模型（零依賴家規下不採；pytm 的威脅庫還會 eval 字串）；從程式碼自動推入口（推得出路由，推不出哪個資產敏感、誰不該碰）。
- 入口盤點本身漏項，工具發現不了；這點承接盤點計劃 Q1（誰審入口盤點、多久重驗），不在本篇另問。

## 二、每格套固定威脅類別

格子＝入口 × 該入口對應的資產 × 適用的威脅類別；**authz-object、authn-identity、flow-abuse 三類再乘上角色**（入口 × 資產 × 類別 × 角色，角色取該入口的 `actor_ids`），其他類不加角色。理由：這三類問的就是「誰能做」，一條只驗「他人不能改擁有者的訂單」的護欄，不能順便把「管理員能不能改」那一格也關掉；其他類（注入、檔案、秘密…）跟誰進來關係不大，加角色只會讓格子數乘上角色數。
- 「該入口對應的資產」就是那個入口自己的 `asset_ids`，不是全部資產；`asset_ids` 是空陣列時一格都長不出來，所以列格子層錯誤 `surface_without_assets`，不當成「沒有缺口」。三類加角色時，入口的 `actor_ids` 是空陣列，同樣列 `surface_without_actors`。
- 以 repo 為單位的四類，格子是 `@repo × @repo × 類別`，每個 repo 根各一格。
- 適用與否由入口 kind 決定（表的「適用入口」欄），不由作者臨場挑。
- 每格的 id 是 `<入口>/<資產>/<類別>`，有角色維度的是 `<入口>/<資產>/<類別>/<角色>`；這個 id 是候選題的去重鍵（見〈三〉）。

分類只借，不宣稱合規：類別骨架用 STRIDE 逐元素的想法（入口對資料流與處理、資產對資料儲存、角色對外部互動者），每類掛 ASVS 5.0.0 章節當驗收錨點、WSTG v4.2 類別當測法提示、OWASP API Security Top 10 2023 當 API 入口的細分提示。ASVS 章節對 STRIDE 沒有 OWASP 官方對照，下表的對應是本篇自建。

### 威脅類別表

正本在 [[Systems/資安威脅類別表]]（14 類、11 欄；v1 已依 d5 由 Claude 與 Codex 雙家一致核可，卷證在 `governance/security-consensus/threat-table-v1/`），本篇不留第二份。下限與替代怎麼算、誰問什麼不重複問、另登規則、各類共同的附問、標準對應只是查閱索引、版號跟著資料列走、改名或刪除怎麼報錯、單一來源與漂移測試的比法，都以那篇為準。要改表先改圖譜正本、依 d5 經 Claude 與 Codex 雙家一致核可升版，再改 `scripts/lumos` 的鏡像常數。

## 三、依決策時機排進既有分階段提問

格子回答的是「這份產品要想哪些」，需求風險面回答的是「這份計劃現在這個階段該釐清哪些」。兩條路分工：
- **需求風險面表**（`pitfalls --stage`，比對計劃文字）：補下列七項，只決定「這個階段多列幾題」，仍是提醒，不擋。既有 25 項（含 `deliver-security`）的問題句、觸發詞與階段一字不改——這照母計劃 d7 標題下〈提問依決策時機安排〉一節「不改既有風險面表的觸發字、階段」。七項新列寫進 [[Systems/情境出題]]（需求風險面表的內容源）與它的「25 項」敘述。

| 新 id | 階段 | 要釐清什麼 | 觸發（草案；強詞表見下） |
|---|---|---|---|
| req-sec-assets | 需求 | 這功能碰到哪些要保護的資料與操作?誰可以做、誰不可以做(角色 × 資源 × 動作)?最不能發生的事是什麼(寫成看得到的結果)? | 通用強詞至少兩個不同的 |
| req-sec-actors | 需求 | 誰可能濫用這功能(他人、未登入者、內部人、外部系統)?他能做到什麼程度? | 同上 |
| arch-sec-boundary | 架構 | 身分從哪來、何時可信?授權在哪個服務端邊界強制?外部輸入在哪一層驗? | 同上；或通用強詞至少一個，再加邊界詞（API、入口、webhook、回呼、匯入、第三方、管理後台）至少一個 |
| arch-sec-secrets | 架構 | 會用到哪些秘密、金鑰、憑證?放哪、誰讀得到、外洩了怎麼換? | 秘密詞至少兩個不同的 |
| arch-sec-supply | 架構 | 要新加的依賴、映像或掃描工具從哪來、版本怎麼釘、誰核可? | 供應鏈詞至少兩個不同的 |
| verify-sec-evidence | 驗證 | 每條資安護欄要哪幾種證據?用哪個工具(查威脅類別表)?沒有工具時換成什麼?合法對照是什麼? | 通用強詞至少兩個不同的 |
| deliver-sec-exceptions | 交付 | 還有哪些資安護欄沒驗或走例外?例外誰核可、哪天到期? | 同上 |

- **`deliver-security` 不改**：原句「誰能做這件事?有哪些敏感資料?邊界在哪?」、觸發詞與交付階段照舊；「未驗與例外」另加 `deliver-sec-exceptions` 一項問。原本打算把它改寫、把「誰能做」移到需求階段，那會改既有風險面的問題句，跟母計劃 d7 小節衝突；Q4 依 d8 定為保留原句、另加一項。日後若要改寫：把 deliver-security 的問題句換成 deliver-sec-exceptions 那句、刪掉 deliver-sec-exceptions、S9 改回「只問未驗與例外」，其餘不動；這樣翻只動兩列與一條條款。
- **誤觸發怎麼壓**：
  - 三張詞表都只收少歧義的詞。「使用者」「會員」不算強詞。
  - 詞界照實寫，不說照抄哪一條：每個英文詞寫成 `(?i)(?<![a-z0-9])詞s?(?![a-z0-9])`——每個 `words` 元素各自帶 `(?i)`（因為每個元素各自 `re.search`，沒有「整條」可以共用旗標）、允許複數尾 `s`（secrets、tokens、cookies、sessions 都會中）、前後不接英數字（所以 `pip` 不會撞到 pipeline）。這跟 `_REQ_FE_WHEN` 不一樣：那條的框架名尾端是 `(?![a-z])`，刻意讓 Vue3、React18 能中；安全詞不需要緊貼版本號。中文詞照字面比，不加詞界。
  - 通用強詞：登入、權限、個資、租戶、他人的、別人的、擁有者、所有權、越權、上傳、下載、匯出、密碼、金鑰、憑證，以及英文 secret、api key、oauth、jwt、session、cookie、csrf、cors、token。
  - 秘密詞：金鑰、私鑰、憑證、密碼、加密、secret、api key、token、keystore、kms。
  - 供應鏈詞：新依賴、新增依賴、映像、鎖檔、供應鏈，以及英文 docker、npm、gradle、maven、pypi、lockfile、sbom、`pip install`（兩個字之間可有空白）。原草案的「安裝」「套件」「pip」拿掉：前兩個是太常見的單詞，pip 沒詞界會撞 pipeline。
  - 所有新項都要求至少兩個**不同的**詞才觸發（「不同」是指詞表裡不同的兩列，同一個詞出現多次只算一個）；arch-sec-boundary 另有「一個強詞加一個邊界詞」這條替代規則。
  - **在工具鏈 repo 量到的偏差**（2026-10-20 在提交 e56c7234 上，用上面的通用強詞表與詞界寫法對 `Projects/*_計劃.md` 全文 `re.search`）：298 篇有 71 篇命中至少兩個不同強詞；其中 21 篇同時有 session 與 token，7 篇只靠這兩個詞湊到兩個。這個 repo 的 session 多半是 AI 會談、token 是用量，不是資安意思，所以〈五〉的誤報量測不能只用本 repo 的計劃，order-demo 那半要另算；若人工標註顯示這兩個詞的誤報主要來自本 repo，就把它們移出通用強詞、只留在秘密詞。這是命中數，不是誤報數；誤報與漏報照〈五〉的人工標註量。
  - 被觸發但不適用的，作者照既有規矩一句話寫不適用就結束，不必建問題。
- **觸發規則的新資料形狀（引擎改動，新增）**：現在每一項只有 `when`（正規式字串清單），`_pitfalls_stage` 用「任一條命中就觸發」判。新增一個選填鍵 `triggers`，七個新項只用它、不寫 `when`；既有 25 項照舊只用 `when`，行為不變。
  - 形狀：`"triggers": [{"words": [正規式字串, …], "min_distinct": 2}, {"words": […], "min_distinct": 1, "plus_any": [正規式字串, …]}]`。一條規則成立＝`words` 裡至少 `min_distinct` 個不同的元素對全文 `re.search` 命中，且有 `plus_any` 時其中至少一個也命中；`triggers` 裡任一條規則成立，這一項就觸發。
  - 一項只能有 `when` 或 `triggers` 其中一個（兩個都有或都沒有，表的自我檢查測試紅）。判斷收成一支函式，`--stage` 與其他讀風險面表的地方都呼叫它，不在各處各寫。
  - `--stage --json` 現在會把整列原樣序列化；`triggers` 裡只有字串與整數，照樣原樣輸出，所以新項的 JSON 多一個 `triggers` 鍵、沒有 `when` 鍵，既有 25 項的 JSON 逐字不變。
  - 正式的 JSON 形狀寫進 [[Systems/pitfalls-code-loop]] 的 `--stage` 那段，實作當次一起寫。
- **指路行改成表的選填鍵**：需要多印一句指路的項，在表裡加選填鍵 `hint`（字串）；`_pitfalls_stage` 的通用迴圈印完某項的問題句後，有 `hint` 就多印一行，不在迴圈裡寫死任何 id（同族做法：前端面靠資料欄位 `role` 區分）。`--stage --json` 照舊原樣序列化整列，`hint` 就在那一項的物件裡；既有 25 項沒有這個鍵，JSON 逐字不變。verify-sec-evidence 與 deliver-sec-exceptions 的 `hint` 是：「這份計劃連到的資安護欄與 open 格子，跑 `lumos security list` 或 `lumos spec-gate <計劃>` 看」。
- **問題怎麼進待決問題**：該人裁的照既有 `question-add` 寫進消費專案計劃的 `pending_questions`，標階段；會影響實作的權限題標需求階段與阻塞，規格閘照既有規則擋。題目文字帶格子 id，寫成 `[cell:<格子 id>]`（例：`[cell:orders-pay/order/authz-object/stranger]`），讓人讀得出是哪一格、也讓候選題輸出能去重；格子狀態不靠這段字算（見〈四〉）。
  - 不選：在 `pending_questions` 加「格子」欄（改既有開頭欄位契約，而且題目結了不代表格子有去向，兩者會漂移）。
- **候選題怎麼產生**：新增 `lumos security list --questions`（不另開子命令，因為它就是盤點同一份格子的另一種輸出）：
  - 依 open 格輸出候選題句：表的模板代入入口、資產名稱；有角色維度的類別一格就是一個角色、一題；其他類別的 `{角色}` 代入該入口全部 `actor_ids` 的名稱（用頓號串起來）。每題前面帶 `[cell:<id>]`，尾端固定附一句「這道防護依賴的服務逾時、丟例外或不可用時，是拒絕還是放行?」（威脅類別表 v1 定稿的共同附問；寫在產生規則裡、不寫進表的模板欄）。
  - 帶 `--plan <計劃>` 時，讀那份計劃全文(不只 `pending_questions`),已經出現同一個 `[cell:<id>]` 的格子不再輸出，所以重跑是冪等的；不帶就全列。看全文的理由:題目結了之後可能整理進正文或決策,只看 `pending_questions` 會把已處理過的格子再問一次(代碼審第一輪規格對照席點出跟原寫法不同,照程式改寫)。
  - 一次最多輸出 30 題（`--limit` 可改），超過只印前 30 題加一行「還有 N 題」，避免一次灌幾百題進計劃。
  - 只輸出、不寫檔；要進 `pending_questions` 仍由人或 AI 逐題跑 `question-add`。
- **格子怎麼看**：盤點 coverage 加一區 `cells`（每格帶 id、狀態、資料列的表版號），由 `security list` 列出。`security list` 不驗章（維持盤點 S7 不執行程序，見姊妹計劃〈一〉）：有 considerations 的格子在 list 輸出標 `considered_unverified:<outcome>`（例如 `considered_unverified:not_applicable`），只代表「有一列考量、簽章未驗」，不代表算數；這一列最終算不算數、格子是 not_applicable／risk_accepted 還是 open，由姊妹計劃的閘門與 `security evidence` 判。預設只印各狀態的格子數與 open 格的清單，`--all` 才逐格全列；`--json` 照舊一份完整物件。
- **跟筆記庫有關的檢查放在讀得到筆記庫的指令**：`pitfalls --stage` 只讀那份計劃的文字、不讀筆記庫（`_pitfalls_stage` 只收計劃檔路徑、自己讀那一個檔，連待決問題也是從那份檔的開頭欄位解析），解析不了計劃連到哪篇 Systems、那篇登記了哪些護欄、哪些格子是 open。所以「這份計劃連到登記了資安護欄的 Systems」與「這些 Systems 的 open 格子」由 `security list`（盤點，本來就讀筆記庫）與 `spec-gate`（規格閘，本來就讀筆記庫）列出。spec-gate 這一行是新增的提醒，家在 [[Systems/規格閘]]：
  - **先便宜地看要不要讀**：只看計劃 `lands_in` 與 `related` 連到的那幾篇節點原文有沒有 `lumos-security-v1` 字樣；一篇都沒有就不印這一行、也不建快照。
  - **讀法只有一支**：有字樣才呼叫一支公開的共用函式（例如 `_secinv_report(vault)`，`security list` 也改成呼叫它），走盤點既有的硬化快照與 `_secinv_build`，不另寫 inventory 解析，也不從 spec-gate 手上的一般 Env 讀。
  - **印什麼**：連到的節點裡登記了哪些護欄；open 格子數的口徑是「連到的節點裡的護欄引用到的入口，再加上連到的節點若放了 inventory 就是全部入口」上的 open 格子；另印一個全庫 open 總數，讓人看得出全庫還有多少。
  - **出錯時**：盤點讀取不完整、`errors` 非空、讀到不認得的 schema_version，或這一步自己拋錯，一律只印一行警告（例如「資安盤點讀取不完整,這一行略過」），不印格子數；不影響規格閘的判門、退出碼與留痕。

## 四、每個答案只有三條去向，機械追得到

一格的狀態只由盤點資料算出，不靠作者勾選：

| 去向 | 寫在哪 | 格子狀態 |
|---|---|---|
| 登記成護欄，交給驗收閘 | controls 條目同時滿足：lifecycle 是 active、`concerns` 含 security、不是 retired；`surfaces` 含該入口、`assets` 含該資產、而且該資產在**那個入口自己的** `asset_ids` 裡；`threat_categories` 含該類別；有角色維度的類別另要 `actor_ids` 含該角色 | `control:<id>`；之後證據合不合格由驗收閘判 |
| 只有候選護欄 | 同上，但 lifecycle 是 candidate | `candidate:<id>`；不算有去向，跟 open 一起列進缺口數 |
| 不適用 | `considerations` 一列：入口、資產、類別（有角色維度再加角色）、`outcome: not_applicable`、核可欄位 | `not_applicable`；盤點另列一區「待審適用性的格子」 |
| 接受風險 | `considerations` 一列：同上、`outcome: risk_accepted`、核可欄位（含補償措施與到期日） | `risk_accepted`；過期或不合格就變回 `open` |
| 想過但沒下文 | 什麼都沒寫 | `open`：盤點輸出的缺口，不能當安全 |

- **覆蓋口徑跟現行入口覆蓋一致**：現行 `_secinv_surface` 只算 `concerns` 含 security、非 retired 的條目，並分 active 與 candidate；格子沿用同一個口徑，純 business 的 Invariant 就算填了 `threat_categories` 也不覆蓋格子。
- **護欄覆蓋格子不吃交叉積**：一條護欄寫了兩個入口、兩個資產，只覆蓋「入口 × 它自己 `asset_ids` 裡有的資產」那幾格，不是 2×2 全蓋。要更細就拆成兩條護欄。以 repo 為單位的四類：護欄的 `surfaces` 與 `assets` 寫 `@repo`。
- **部署面的宣稱另登一條 repo 層級護欄**：備份、快照、日誌保存、儲存加密、日誌防竄改這類部署面宣稱，另登一條 `surfaces`、`assets` 為 `@repo`、`threat_categories` 含 config-deploy 的護欄，不在入口護欄上加標 config-deploy（威脅類別表 v1 定稿的另登規則）。
- **護欄層 not_applicable 跟格子層 not_applicable 是兩件事**：護欄自己的 `reported_status: not_applicable`（v1 既有）是「這條護欄宣稱自己不適用」，照現在的行為進 `applicability_pending_control_ids`；它覆蓋到的格子狀態仍是 `control:<id>`，不會變成格子的 not_applicable。格子層的 not_applicable 只來自 considerations。
- **待審適用性的格子是新行為**：現在的 `applicability_pending_control_ids` 只來自護欄自己的 `reported_status`（`scripts/lumos` 的 `_secinv_surface`），沒有 considerations。v2 新增一區 `applicability_pending_cells`，列出所有格子層 not_applicable 的格子；盤點只列、不裁核可足不足。
- **核可走姊妹計劃的核可鏈**：considerations 的核可一律走姊妹計劃 d10 的核可鏈（`.lumos/security-approvals.jsonl`，`type: consideration`、`target` 是格子 id，內容雜湊蓋住入口、資產、類別、角色、outcome、表版號與那一列的全部鍵），形狀與檢查函式以姊妹計劃〈四〉的〈核可物件：例外與 considerations 共用一套〉為準，這裡不另寫。那一列只放 `decision_ref`、`reason`、`compensating`（risk_accepted 必填）與 `expires_on`，`expires_on` 必須等於鏈上對應那一筆的 `expires_on`；核可日、簽章人與簽章都在鏈上那一筆，不放在列裡。到期上限照鏈上那一筆算：risk_accepted 最長 30 天（31 天起無效），not_applicable 最長 180 天（見 d9;d4 已作廢）；到期日當天有效、隔天起變回 open，日期一律 UTC。鏈上沒有對得上的有效一筆，這一列不算數、格子是 open。所以 AI 寫一列 considerations 關不掉缺口。
- **核可不合格的列不參與互斥**：過期、超過那一型的到期上限、到期日早於鏈上的核可日、`expires_on` 跟鏈上那一筆不同、核可決策找不到或作廢、缺 `decided` 的決策、缺欄位、核可鏈上沒有對得上的有效一筆的列都「不算數」：它不讓格子變成 not_applicable 或 risk_accepted，也不跟覆蓋這一格的護欄衝突；有有效護欄就是 `control:<id>`，沒有就是 open。輸出另列這些不算數的列與原因，留著不刪也不出錯，審計軌跡保留。
- **去向之間互斥**（S3 怎麼判）：同一格同時有「覆蓋它的護欄（不論那條護欄的 reported_status）」與「一列算數的 considerations」，或同一格有兩列算數的 considerations，就列格子層錯誤 `cell_conflict`，該格狀態是 `conflict`，不任選一個。
- 「想過沒下文」不靠追問題：只要格子在、三種去向都沒有，就一直是 `open`。題目結成已決但沒有寫成護欄或 considerations，格子照樣 open。
- open 格子現在**不擋推送**：母計劃 d9 擋的是「已登記護欄的證據不合格」；open 只在 `security list` 列出、spec-gate 提醒（見〈三〉）。要不要擋，等〈五〉的量測。

**格子層錯誤另放一區，不擋推送**：
- 下列錯誤放進 `security list` 新的 `cell_errors` 區，**不進既有的 `errors`**，所以不改退出碼，也不會被姊妹計劃閘門的「盤點登記錯誤就整道擋」接到（姊妹計劃寫明閘門不讀 `cell_errors`）。`cell_errors` 只收 considerations 列與入口層的問題；護欄（controls）自己的問題歸姊妹計劃的護欄層錯誤：`cell_conflict`；`surface_kind_missing`（v1 入口沒有 kind）；`surface_without_assets`；`surface_without_actors`；`unknown_category`（considerations 引用表裡沒有的類別）；considerations 指到不存在的入口、資產或角色（`consideration_unknown_ref`）；類別對該入口 kind 不適用（`consideration_category_not_applicable`）；資產不在該入口的 `asset_ids`（`consideration_asset_not_on_surface`）；`outcome` 不是兩值之一（`consideration_outcome_invalid`）；surfaces 出現 `@` 開頭的 id；格子數超過上限（`cells_limit_exceeded`，見下）。
- 為什麼不進 `errors`：這些是「格子算不清楚」，不是「護欄登記壞掉」；一個格子的筆誤不應該讓整個專案推不出去，而 open 格子本來就不擋。
- **讀不完整時格子不算**：盤點 `read_complete` 是 false、inventory 壞掉或沒有 inventory 時，`cells` 整區標 `status: unknown`、不輸出 open 數，避免把「沒讀到」顯示成「沒有缺口」；spec-gate 那一行照〈三〉只印警告。

**規模與上限**：
- 先把護欄與 considerations 各掃一遍，建（入口、資產、類別、角色）為鍵的索引，再逐格查表，時間跟「格子數 + 護欄數 + considerations 數」成正比，不逐格掃全部護欄。
- 格子數上限 100000：威脅類別表 v1 定稿是 14 類，http_api 適用 7 類（其中 3 類乘角色）；200 個入口、每個入口 50 個資產、5 個角色時，每個 http_api 入口最壞是 50 ×（3×5＋4）＝950 格，全部 200 個約 19 萬格，會先超過上限、只剩計數。依另登規則，管理後台有瀏覽器畫面時一個功能要登 `admin` 與 `web_page` 兩個入口，題目數也跟著加倍算進這個估計。實務上一個入口的 `asset_ids` 遠少於 50，上限暫不調；超過就不展開、`cells` 只給各狀態計數並列 `cells_limit_exceeded`，人要拆 inventory 或縮小 asset_ids。
- considerations 拆在各 Systems 節點，每篇仍受盤點既有的單檔 2 MiB 上限，總量受 64 MiB 上限；超過照盤點既有的讀取不完整處理。
