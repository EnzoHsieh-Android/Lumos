# 筆記欄位關卡補齊_計劃

PRIOR-ART: 沿用自家已驗過的形狀,不自建:推送前健檢的段落、專案設定開關 `node_home.gate` 的 on/warn/off 三態(沒設、看不懂的處理方式照它);lint 既有的錯誤等級規則原樣拿來重跑。設計審 r1 否決了兩個原本想借的形狀——「比上一版只擋新違規」(每支檔有家那套)與「推送前只看碰到的筆記」(預告合約那套),理由見摘要與審計修正紀錄。
RETIRE-IF: ①推送前這段在打開的專案連續 8 週零次擋下 → 降成只在 CI 跑(提交前的關已經足夠);②它擋下的案例有一半以上事後判定是誤擋 → 預設改回只提醒、重看規則。

## 一句話

推送前健檢加一段「筆記格式」,對整個圖譜重跑 lint 裡會擋的規則,擋不擋看專案開關(沒設只提醒);lint 補上盤點發現沒人查的幾個欄位,一律有違規就擋;現存的 10 篇違規在同一次改動裡修掉。

## 做法

### 一、推送前健檢加「筆記格式」段

- 對圖譜裡每一篇筆記跑 lint 的**錯誤等級**規則(提醒等級不跑,避免重複嘮叨);有錯的列出篇名與第一條錯誤。
- **擋不擋看專案開關** `.lumos/config.json` 的 `note_lint.gate`:
  - `on`:有任何一篇錯 → 這段算問題、推送前與 CI 都擋。
  - `warn`(**沒設就是這個**):只提醒,印出篇數,並印一行「整理完可以打開:把 note_lint.gate 設成 on」。
  - `off`:整段不跑,開頭印一行說它被關了(跟 node_home.gate 關掉時的講法一樣)。
  - 值看不懂:當 `warn`,並印一行設定看不懂。這裡刻意跟 node_home.gate(看不懂當 on)不同:這段是新上的、影響所有消費專案,看不懂時寧可不擋。
- 本 repo 在自己的 `.lumos/config.json` 設 `on`。
- **不接碰到清單**:整段看整個圖譜,不讀 `--touched-from`,也不改 CI 的呼叫方式——CI 本來就跑 `doctor --ci`,自動吃到這段;預告合約逾期那段在 CI 的全擋行為不受影響。
- 被擋時會跟其他擋下的段一樣寫進治理帳;開關是 warn 時不算問題、不寫。

### 二、lint 補欄位規則(一律有違規就算錯誤)

- `status`:system、project、verification、issue 四種類型必填(現在沒填完全不擋)。
- 日期格式:`created`、`updated`、`date`、決策的 `decided` 與 `ended` 必須是年-月-日(現在只擋加引號)。
- 決策的 `valid`:只能是 true 或 false(現在寫成 no、0 會被當成有效)。
- `about_code`:每一項要在版本控制的索引裡(`git ls-files` 列得到,已加進提交的也算)。寫入指令(`lumos append`、`new --code`)刻意維持只驗磁碟:常見做法是先建節點再把程式檔加進提交,寫入當下就要求進版控會卡住;到提交時兩者都在索引裡了。
- 計劃(專案筆記名稱以「_計劃」結尾)必須有 `lands_in`,而且每一項都要是 `Systems/<名稱>` 的純字串、指到存在的節點(跟設計審落點那一步同一套判法;現在 lint 完全不查格式——r1 之後編排者自己的四份計劃都寫成 `[[連結]]` 一路沒被發現,直到處置閘擋下)。用檔名不用 `type: project`:研究筆記(「_調研」)也是 project 但不要求落點;設計審落點那一步用 type 判,是因為它只跑在已經送審的計劃上。兩套刻意不同。
- 每條錯誤訊息要講怎麼修(例:缺 status → 可以用 `lumos set <節點> status <值>`,並列出這個類型允許的值)。
- **對舊筆記的影響**:提交前 lint 只查這次加進提交的筆記,所以舊筆記只有被改到時才會被要求補齊;推送前那段在消費專案預設只提醒。

### 三、寫入當下

- `lumos set <節點> responsibility <值>`:去掉空白後不到 10 個字就擋、檔案不動(現在只有新開節點時要求)。

### 四、同一次改動修掉現存的 10 篇違規

- 9 篇計劃補 `lands_in`(紀律範本二次瘦身、代碼審資安席、空轉週報誤報復發、社群規則覆蓋每次提交、Flutter補棧、Java補棧、推播miss量測、Python補棧、skills提示工程優化)。
- 1 篇 Issue(把自己的推論寫成repo明文寫過)的 `about_code` 寫成了一篇筆記路徑,改成連結。

### 不做的(設計審 r1 拿掉)

- **不比上一版**:讀不到上一版的情境太多(首次推送、強制推送、新遠端分支、淺層複製),決策又沒有穩定身分可以配對;現存違規只有 10 篇,直接修掉比較簡單。
- **不在 CI 接碰到清單**:同一個旗標會把預告合約逾期那段從全擋放寬成只擋碰到的。
- **不把提交前 lint 改成讀提交內容**:lint 用的筆記物件只能從磁碟組出來,改讀索引要另寫一套;部分加入提交造成的落差,由 CI(讀的是實際提交進去的內容)兜底。

### 不在本案範圍

- 沒有程式讀的三個欄位(`signed_off`、`phases`、`commit`)要不要拿掉,另案看。
- 決策 `superseded_by` 指向的目標存不存在、`decisions.id` 唯一性:健檢已有提醒段,本案不升級。

## 條款

- [S1] 當專案開關 note_lint.gate 是 on,健檢發現任一篇筆記有 lint 錯誤等級的問題時應擋下並列出篇名 [test:t_doctor_note_lint_gate_on_blocks]
- [S2] 若專案沒設 note_lint.gate 或設成 warn,則同樣的問題應只提醒、不影響退出碼,並印出篇數與怎麼打開 [test:t_doctor_note_lint_gate_default_warns]
- [S3] 若 note_lint.gate 是 off,則這段應整段不跑,並印一行說它被關了 [test:t_doctor_note_lint_gate_off]
- [S4] 若 note_lint.gate 的值看不懂,則應當成 warn 並印一行設定看不懂 [test:t_doctor_note_lint_gate_unknown_value]
- [S5] 當健檢帶著碰到清單跑,筆記格式段的結果應與不帶時相同,且預告合約逾期那段的擋法不變 [test:t_doctor_note_lint_ignores_touched_list]
- [S6] 若 system、project、verification、issue 筆記沒有填 status,則 lint 應報錯誤並講允許的值 [test:t_lint_status_required]
- [S7] 若筆記的建立日、更新日、日期、決策日期或結束日不是年-月-日格式,則 lint 應報錯誤 [test:t_lint_date_fields_format]
- [S8] 若一條決策的 valid 不是 true 或 false,則 lint 應報錯誤 [test:t_lint_decision_valid_boolean]
- [S9] 若筆記的 about_code 有一項不在版本控制的索引裡,則 lint 應報錯誤;已加進提交但還沒提交的檔應算在索引裡 [test:t_lint_about_code_must_be_tracked]
- [S10] 若名稱以「_計劃」結尾的專案筆記沒有 lands_in,或其中一項不是 `Systems/<名稱>` 的純字串、或指到不存在的節點,則 lint 應報錯誤;名稱以「_調研」結尾的不受影響 [test:t_lint_plan_requires_lands_in]
- [S11] 當 `lumos set` 寫 responsibility 且去掉空白後不到 10 個字,寫入應被擋下、檔案不變 [test:t_set_responsibility_min_length]
- [S12] 當這次改動完成,本 repo 圖譜的每一篇筆記都應通過 lint,且本 repo 的 note_lint.gate 是 on [test:t_repo_graph_passes_note_lint]

## 回退

- 消費專案(工具是複製過去的,這邊退回它們不會跟著退):在自己的 `.lumos/config.json` 把 `note_lint.gate` 設成 `warn` 或 `off`,不必改程式、不必等更新。
- 本 repo:同上把開關設成 warn;要整個拿掉就還原這批提交(健檢新段、lint 新規則、set 的長度檢查各自獨立)。
- 已修的 10 篇筆記不用退(補的是本來就該有的欄位)。

## 實務隱患

- 已排除:金流:只檢查知識庫筆記的欄位格式,不碰任何交易或計費路徑。
- 已排除:對外送出:lint 與健檢都只讀本機檔案與 git,不發任何對外請求。
- 已排除:不可逆:擋的是提交與推送的退出碼,開關一改就恢復;修掉的 10 篇只是補欄位。
- 守衛面:是——這是新的擋點。消費專案預設只提醒、開關在各自設定檔、看不懂的值當 warn,三道保險都是為了不在更新當下卡住它們。
- 舊筆記:提交前被改到的舊筆記會被要求補齊新欄位(例如補 status);錯誤訊息要講怎麼補,避免人只好 --no-verify。

## 誠實界線

- 推送前健檢讀的是工作目錄:推送的不是目前分支時(例:停在 A 分支推 B),看的是 A 的筆記。這是健檢所有段落共同的限制,不是這段新增的;本 repo 由 CI(讀實際推上去的內容)兜底,消費專案要看它們的 CI 有沒有跑健檢。
- 提交前 lint 讀磁碟:部分加入提交時,驗的跟提交的可能不是同一份;同樣靠 CI 兜底。
- `about_code` 查的是索引裡有沒有這支檔,不查它是不是程式檔、是不是真的歸這篇管。
