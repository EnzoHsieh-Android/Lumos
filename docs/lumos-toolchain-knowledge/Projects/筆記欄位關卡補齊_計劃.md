# 筆記欄位關卡補齊_計劃

PRIOR-ART: 沿用自家已驗過的形狀,不自建:健檢既有的 L 段(已經對整個圖譜跑、有問題就擋)擴充內容;專案設定開關照 `node_home.gate` 的讀法(`_nodehome_config`:設定檔不存在、讀不了、JSON 壞掉、是捷徑檔、欄位不是物件 → 用預設並印警告;值看不懂 → 當 on);落點格式直接用處置閘那支判斷(`_lands_in_bad`);負責範圍長度直接用新開節點那支判斷(`_nodehome_resp_ok`);about_code 的存在判法跟寫入指令一樣看磁碟,並把「不在圖譜資料夾裡」同時補進寫入指令。設計審 r1 否決了兩個原本想借的形狀——「比上一版只擋新違規」(每支檔有家那套)與「推送前只看碰到的筆記」(預告合約那套),理由見摘要與審計修正紀錄。
RETIRE-IF: ①推送前這段在打開的專案連續 8 週零次擋下 → 降成只在 CI 跑(提交前的關已經足夠);②它擋下的案例有一半以上事後判定是誤擋 → 預設改回只提醒、重看規則。

## 一句話

健檢既有的 L 段擴充成「對每篇筆記跑 lint 的錯誤等級規則」;lint 補上盤點發現沒人查的幾個欄位;這些新東西擋不擋看專案開關 `note_lint.gate`(沒設只提醒),提交前與推送前同一個開關;現存違規在同一次改動裡修掉。

## 做法

### 一、健檢 L 段擴充

- L 段原本只查「會讓工具讀錯的開頭欄位寫法」(解析指紋),這部分照舊、照舊擋。
- 新增:對圖譜裡每篇筆記跑 lint 的**錯誤等級**規則(原有的與這次新增的都跑;提醒等級不跑),有錯的列出篇名與第一條錯誤。**這整個擴充部分擋不擋都看開關**(見三)——原有規則過去只在提交前對改到的那篇跑,第一次改成整個圖譜跑,消費專案舊筆記若本來就違反,不能因為更新工具就被硬擋(r3 外家席)。
- 呼叫方向:把 lint 的判定抽成一支只回傳「錯誤清單、提醒清單」的函式,`lumos lint` 指令與 L 段都呼叫它;L 段不去呼叫 `lumos lint` 這個指令,也不另寫一份規則。
- **不接碰到清單**:整個圖譜跑、不讀 `--touched-from`、不改 CI 的呼叫方式——CI 本來就跑 `doctor --ci`,自動吃到;預告合約逾期那段在 CI 的全擋行為不受影響。
- 被擋時跟其他擋下的段一樣寫進治理帳;開關是 warn 時不算問題、不寫。

### 二、lint 補欄位規則

- `status`:system、project、verification、issue 四種類型必填;寫成空字串或只有空白也算沒填(跟既有值域檢查一致:它對空值不檢查,正是這條要補的)。
- 日期格式:`created`、`updated`、`date`、決策的 `decided` 與 `ended` 必須是年-月-日。
- 決策的 `valid`:有寫的話只能是 true 或 false,不分大小寫;**沒寫不算錯**(現在讀的地方都把沒寫當成 true,這條不改那個語意)。
- `about_code`:每一項要是磁碟上存在的檔,而且不在圖譜資料夾裡(筆記不是程式檔)。寫成單一字串而不是清單的,當成只有一項。「看磁碟」這點跟寫入指令(`append`、`new --code`)一樣;「不在圖譜資料夾裡」是**新規則**,寫入指令現在沒有這條(那篇 Issue 就是用 append 寫進筆記路徑的),這次一併補進寫入指令,兩邊才一致。lint 不去掃版本控制索引。
- 計劃必須有 `lands_in`:只管 `type: project`、檔名以「_計劃」結尾、而且**筆記建立日(`created`)在 2026-09-12 以後**的。日期取處置閘落點那一步同一天,但**判準不同**:處置閘看的是審查迴圈第一筆帳的時間,這裡看的是筆記建立日(lint 沒有迴圈可看)。之前的舊計劃 141 篇多半沒寫,不回溯。每一項的格式照處置閘那支判斷(`Systems/<名稱>` 的純字串);**不要求節點已經存在**——處置閘允許落到這次才新開的節點,這裡也一樣。
- 每條訊息要講怎麼修(例:缺 status → `lumos set <節點> status <值>` 並列出允許的值)。

### 三、專案開關 `note_lint.gate`

`.lumos/config.json` 的 `note_lint.gate`,一個開關同時管二與一的新增部分,以及四:

- `on`:新規則算錯誤、提交前擋;健檢 L 段的擴充部分(原有規則與新規則)擋。
- `warn`(**沒設就是這個**):新規則在提交前只提醒;健檢 L 段的擴充部分只提醒,印出篇數與一行「整理完可以打開:把 note_lint.gate 設成 on」。
- `off`:新規則不跑;健檢 L 段的擴充部分不跑,印一行說它被關了。L 段原本的解析指紋檢查不受開關影響。
- 值看不懂:當 `on`,並印一行設定看不懂(跟 node_home.gate 一樣)。
- 設定檔不存在:當沒設(warn),不印警告。設定檔讀不了、JSON 壞掉、是捷徑檔、`note_lint` 不是物件:當沒設(warn),並印一行警告——結構照 `_nodehome_config`,只是預設值不同(它預設 on)。
- 開關從磁碟上的設定檔讀(lint 讀筆記也是讀磁碟);CI 讀的是實際提交進去的設定。
- 提交前:開關只管這次新增的規則;lint 原本就有的錯誤等級規則照舊擋提交、不受開關影響。
- 本 repo 在自己的 `.lumos/config.json` 設 `on`。

### 四、寫入當下

- `lumos set <節點> responsibility <值>`:用新開節點時那支判斷(至少 10 個字、要有實字),不過就擋、檔案不動——跟 `new --responsibility` 一樣**不看開關**(r3 架構席:同一個欄位的兩個寫入口擋法要一樣);這條只擋寫入過短的負責範圍,誤擋的代價是多寫幾個字。
- `lumos append <節點> about_code <檔>` 與 `new --code`:補上「不在圖譜資料夾裡」,跟 lint 一致。

### 五、同一次改動修掉現存違規

- 9 篇 09-11 以後建立、沒寫 `lands_in` 的計劃補上(紀律範本二次瘦身、代碼審資安席、空轉週報誤報復發、社群規則覆蓋每次提交、Flutter補棧、Java補棧、推播miss量測、Python補棧、skills提示工程優化)。其中 5 篇建立於 09-11,不在新規則範圍(規則從 09-12 起),照 CLAUDE.md〈每支檔有家〉本來就該寫,一併補;實作時實際以新規則重掃的結果為準。
- 這些筆記修正放**獨立一個提交**(不跟程式同提交),退回程式時不會連筆記一起退。
- 1 篇 Issue(把自己的推論寫成repo明文寫過)的 `about_code` 寫成了一篇筆記路徑,改成連結。
- 實作時全圖譜重掃一次,有新規則抓到而這裡沒列的一併修掉,並在驗證紀錄寫下實際修了幾篇。

### 不做的(設計審拿掉)

- **不比上一版**(r1):讀不到上一版的情境太多、決策沒有穩定身分可以配對。
- **不在 CI 接碰到清單**(r1):同一個旗標會把預告合約逾期那段從全擋放寬成只擋碰到的。
- **不把提交前 lint 改成讀提交內容**(r1):lint 用的筆記物件只能從磁碟組出來;部分加入提交的落差由 CI 兜底。
- **不另開健檢新段**(r2):L 段已經整個圖譜跑、會擋,擴充它。
- **about_code 不查版本控制索引**(r2):lint 只看單篇筆記,不掃 repo;跟寫入指令用同一種判法。

### 不在本案範圍

- 沒有程式讀的三個欄位(`signed_off`、`phases`、`commit`)要不要拿掉,另案看。
- 決策 `superseded_by` 指向的目標存不存在、`decisions.id` 唯一性:健檢已有提醒段,本案不升級。

## 條款

- [S1] 當專案開關 note_lint.gate 是 on,健檢 L 段發現任一篇筆記有 lint 錯誤等級的問題(原有或新增規則)時應擋下並列出篇名;L 段原本的解析指紋檢查照舊 [test:t_doctor_note_lint_gate_on_blocks]
- [S2] 若專案沒設 note_lint.gate 或設成 warn,則新規則在提交前應只提醒,健檢 L 段的擴充部分(含原有規則對整個圖譜的結果)應只提醒、不影響退出碼,並印出篇數與怎麼打開 [test:t_note_lint_gate_default_warns]
- [S3] 若 note_lint.gate 是 off,則新規則應不跑,健檢 L 段應印一行說它被關了 [test:t_note_lint_gate_off]
- [S4] 若 note_lint.gate 的值看不懂,則應當成 on 並印一行設定看不懂;若設定檔讀不了、JSON 壞掉、是捷徑檔或 note_lint 不是物件,則應當成沒設並印一行警告 [test:t_note_lint_gate_bad_config]
- [S5] 當健檢帶著碰到清單跑,L 段的結果應與不帶時相同,且預告合約逾期那段的擋法不變 [test:t_doctor_note_lint_ignores_touched_list]
- [S6] 若 system、project、verification、issue 筆記沒有填 status 或寫成空字串,則新規則應報出來並講允許的值 [test:t_lint_status_required]
- [S7] 若筆記的建立日、更新日、日期、決策日期或結束日不是年-月-日格式,則新規則應報出來 [test:t_lint_date_fields_format]
- [S8] 若一條決策寫了 valid 且不分大小寫後不是 true 或 false,則新規則應報出來;寫成 True、FALSE 或沒寫都不算錯 [test:t_lint_decision_valid_boolean]
- [S9] 若筆記的 about_code 有一項在磁碟上不是檔、或在圖譜資料夾裡,則新規則應報出來;寫成單一字串的當成一項 [test:t_lint_about_code_must_exist]
- [S10] 若 type 為 project、檔名以「_計劃」結尾、筆記建立日(created)在 2026-09-12 以後的筆記沒有 lands_in,或其中一項不是 `Systems/<名稱>` 的純字串,則新規則應報出來;指到還不存在的節點不算錯,「_調研」與更早的計劃不受影響 [test:t_lint_plan_requires_lands_in]
- [S11] 當 `lumos set` 寫 responsibility 而新開節點那支判斷不過,寫入應被擋下、檔案不變,不看開關 [test:t_set_responsibility_min_length]
- [S12] 當這次改動完成,本 repo 圖譜每一篇筆記都應通過 lint 的原有與新增規則(測試不經開關、直接跑規則,所以本 repo 把開關改成 warn 退回時這條不必跟著改) [test:t_repo_graph_passes_note_lint]
- [S13] 若新規則的開關是 warn 或 off,則 lint 原本就有的錯誤等級規則應照舊擋提交 [test:t_note_lint_gate_does_not_relax_existing_rules]
- [S14] 當 `lumos append` 或 `new --code` 要把圖譜資料夾裡的路徑寫進 about_code,寫入應被擋下、檔案不變 [test:t_about_code_writer_rejects_vault_path]

## 回退

- 消費專案(工具是複製過去的,這邊退回它們不會跟著退):在自己的 `.lumos/config.json` 把 `note_lint.gate` 設成 `warn` 或 `off`——提交前、健檢、`set` 的新檢查同時降級或停跑,不必改程式、不必等更新。
- 本 repo:同上把開關設成 warn(S12 的測試不經開關,不必改);要整個拿掉就還原程式那個提交。
- 已修的筆記放在獨立的提交,還原程式時不會跟著退;它們補的是本來就該有的欄位,不用退。

## 實務隱患

- 已排除:金流:只檢查知識庫筆記的欄位格式,不碰任何交易或計費路徑。
- 已排除:對外送出:lint 與健檢都只讀本機檔案,不發任何對外請求。
- 已排除:不可逆:擋的是提交與推送的退出碼,開關一改就恢復;修掉的筆記只是補欄位。
- 守衛面:是——新的擋點。消費專案沒設開關時提交前、推送前都只提醒,開關在各自設定檔,三個入口同一個開關。
- 舊筆記:開關 on 的專案,提交前被改到的舊筆記會被要求補齊新欄位;錯誤訊息要講怎麼補,避免人只好 --no-verify。

## 誠實界線

- 推送前健檢讀的是工作目錄:推送的不是目前分支時,看的是目前分支的筆記。這是健檢所有段落共同的限制;本 repo 由 CI(讀實際推上去的內容)兜底。
- 提交前 lint 讀磁碟:部分加入提交時,驗的跟提交的可能不是同一份;同樣靠 CI 兜底。
- `about_code` 只查磁碟上有沒有這支檔、不在圖譜資料夾裡,不查它有沒有進版控、是不是真的歸這篇管。
- 落點規則只管 09-12 以後建立的計劃;更早的 141 篇沒寫落點的計劃不回溯。
