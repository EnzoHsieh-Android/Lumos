# 工具鏈代碼審資安與資源鏡頭範圍_計劃

> 白話:lumos 是一個人在自己電腦上、讓 AI 依序操作的工具,不是雲端系統。所以審 lumos 自己的程式時,資安審查員只看三種真的會出事的洞(外部文字混進給 AI 的指令、讀寫或執行跑到不該碰的地方——含打開陌生 repo 時掛鉤執行對方的程式、安裝腳本的下載來源、新寫進程式或公開文件的密鑰、平常操作一步就意外繞過守衛),「有人刻意花好幾步偽造帳本或 git 內部」這類就不再追著加機制;原本的「併發與資源」審查員改成只看「資源」(殘留程序、逾時誤擋、記憶體與大輸入)。用 lumos 的其他專案照舊。

## 裁定來源

使用者 2026-10-14 原話:
- 「幫我思考一下，工具開發的併發鏡頭和資安鏡頭到底該不該存在，這工具是讓人在本機使用，並不是雲端系統，也需要這兩個鏡頭，耗費過度設計在這些防範上嗎」
- 之後裁定:「先照新範圍收尾手上五項,再開一份計劃把規則正式改掉。 但消費專案用舊規則」
- 更早(2026-10-13,待決問題改存開頭欄位代碼審第九輪):「先不用過度設計，只要思考中英文、一個人使用，全權讓AI操作的時候也沒什麼併發問題」

這份計劃只把上面的裁定落成正式規則與派工範本,不重新討論要不要。

## 怎麼分辨「工具鏈本 repo」

沿用 scripts/lumos 既有的 `_is_toolchain_repo(root)`:repo 根有 `skills/lumos-project-notes/SKILL.md` 就是工具鏈本 repo。這支檔是 user-scope skill 的唯一來源,`lumos update` 不會把它複製進消費專案(該函式說明與 `_self_repo_origin` 同一個判別鍵)。現有 6 處呼叫(推送前分級、提交前檢查跳過工具自裝檔等)都靠它,不另寫一套。

root 取法照 `loop next` 既有那支:`Path(repo).resolve() if repo else _vault_repo_root(env)`。

## 新規則

只套工具鏈本 repo 的代碼審;消費專案(用 lumos 的其他 repo)照舊。範圍以**被審的那個 repo** 為準。`loop next` 那一行看的是帳本所在 repo(或 `--repo`);跨 repo 派工(會談開在 A、審 B 的分支)時,編排者自己看 B 的根有沒有 `skills/lumos-project-notes/SKILL.md` 決定貼哪一份,**不要為了這一行帶 `--repo`**(`--repo` 也是在審材料、修正關卡、跑滿回顧的解析根,指到 B 會把 A 帳上的路徑解析錯)。

1. **資安席照樣必派,處置閘那一步不動**。派工範圍只看三類:
   - ①提示注入:作者或外部可控的自由文字(筆記內容、檔名、分支名、帳本欄位、席報告)進到給 AI 的派工詞、hook 附加段或指令。
   - ②讀寫與執行越界:讀寫跑到 repo 外、使用者全域設定、圖譜外,或照著外來路徑寫檔(含捷徑跟過去);hook、安裝腳本、CI 會不會執行不可信位置的檔或做 shell 插值(打開陌生 repo 時 hook 執行對方的程式,正是當初設資安席的起因,d6),安裝腳本從哪下載、下載網址能不能被環境變數覆蓋;新寫進程式、範本或公開文件的密鑰與信箱。卷證與派工單裡的本機絕對路徑(`file:` 佐證、`repo 在…`)是既有慣例、已大量進版控,不報。
   - ③非刻意、一步就能繞過的守衛:照平常操作一個指令或一次編輯就意外走過去(例:按一次 Ctrl-C、檔名帶空白或中文、舊版工具、合併提交、新分支首推、shell 裡殘留的 `LUMOS_SKIP_*` 或別的程序帶進來的 `PYTHONPATH` 這類非刻意的環境)。資安席的「攻擊路徑四件」在這類照下面對應填:誰=使用者本人或照常操作的 AI;從哪=哪個指令或哪次編輯;送什麼=那一步的輸入;拿到什麼=哪道守衛被意外走過。四件填得出就不封頂在推論。
   - **接受不看**(使用者裁定的範圍之外,不是「沒有這些面」):登入與權限、加密與傳輸(安裝腳本下載來源那部分已併進 ②)、行動端;依賴與供應鏈照零依賴家規,新增依賴本來就要人裁,不另審。
   - **範圍外(系統天花板)**:刻意多步偽造——偽造 git 內部物件或 ref、自己手填帳本欄位、換編號或改檔名重來、為了繞過而刻意設定環境變數讓閘提早回 0(非刻意殘留的環境屬 ③)。資安席看到可以順手提一句,一律標 minor、blocking: 否。**不加機制**。
   - **範圍外發現的處置**(固定寫法,不現場決定):代碼審同一輪只要有任一席 major 以上,accepted 就必須為空(處置閘既有規則,不改),所以範圍外的發現一律**折入**,折入動作固定兩步:
     - 在 [[Issues/工具鏈範圍外手法紀錄]](本案新開,只追加)記一行:日期、迴圈與輪次、手法一句、被繞過的守衛、「依 Systems/pitfalls-code-loop 工具鏈資安範圍 RULE 不防」。
     - 文件原本宣稱擋得住它,而且那句是散文(筆記正文、範本、說明檔),就照實拿掉那句不存在的保護說法;那句是 ★INVARIANT★ 合約行、決策欄位或程式註解,不在這一輪動它,只在上一步那行註明位置(合約與決策照各自的撤除或翻案流程另議)。
     - 記帳時這類發現帶 `--finding-kind <id>=process`(流程自己要求的文件,不寫修正紀錄、不補測試)。
     - 同一輪全部 minor 時,也可以改成附理由放行(理由寫「範圍外:刻意多步偽造,見 Systems/pitfalls-code-loop RULE」)。席位仍標成 major 或 blocker,照樣走上面的折入,不另派辯方。
     - 代價照實講:同一輪有真 major 時,這類折入跟著那一輪一起進下一輪(SKILL 步驟 5 收斂前派新席掃修補差異),不會自己多開一輪,但也不會讓那一輪少一輪。
2. **原「併發與資源」席在工具鏈本 repo 改成「資源」鏡頭**:孤兒行程(子程序沒收掉)、逾時誤擋(預算不夠把正常操作擋下或放行)、記憶體與大輸入耗時(大 diff、大帳本、深層巢狀)。不再審多人或多會談同時寫入的競態(兩個程序同時寫同一個檔、檢查與寫入之間被換檔)。
3. **§3 代碼審派工詞第 1 點「冪等與併發」那一項**(d3,取代 d2):工具鏈本 repo 只問重跑與對外重試,「兩個請求同時進來」「同一次計算讀了兩次、中間被別人改了」兩問不問;「寫一半」那一項照舊。`pitfalls --diff` 附給審查席的併發類檢核題(鎖、交易包裹)在工具鏈本 repo 照新規則 2 判「範圍外、不審」即可標誤報,manifest 本身不改。
4. 消費專案的代碼審照舊:§7.8 原六類、併發與資源鏡頭、§3 第 1 點都不變。

## 不改的部分與理由

- **編制表席名**:`("code","high")` 的鏡頭席本來就叫 鏡頭1~5,鏡頭名是派工時編排者給的,沒有程式認「併發」這個席名(查過 scripts/lumos,沒有比對併發席名的地方)。改名或拆表沒有好處,反而讓工具鏈與消費專案的編制表分岔。席報告的席名在工具鏈本 repo 寫 `資源-<模型>`。
- **處置閘資安席一步**:使用者指定不動;判法(席名、報告 sha、看過的檔涵蓋最後一版)兩種 repo 一樣。
- **資安席席名** `資安-<模型>`:處置閘靠它認席,不能因為範圍收窄就改名。
- **風險分級(`pitfalls --diff`)與推送前的棧別檢核題**:類軸與題目裡的「併發」照舊。規則講的是審查席看什麼,不是推送前要不要表態;表態題是另一道閘,要改另開。
- **d6 不作廢**:d6 是「必派而且會擋」,本案沒推翻它,只收窄工具鏈本 repo 的派工範圍。

- 不改消費專案的任何派工、編制、閘;唯一例外是刪檔紀律(做法 9),那是使用者對所有專案的裁定。
- 不改設計審的鏡頭(§1 審計員第 5 點的併發題、§7 設計審 panel 的資源併發席);使用者這次講的是代碼審。已決不一起收窄(d1)。§7、§7.7 是兩種審查共用的段落,〈做法〉3 補進去的句子都寫明只限代碼審。
