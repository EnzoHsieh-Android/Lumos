# 改檔前推播失敗出聲_計劃

白話:改檔前會有一支 hook 把「這次改動牽連到的筆記」推到 AI 眼前。它在查詢沒跑成時(找不到 lumos、逾時、lumos 出錯、輸出讀不懂)一個字都不講,AI 分不出「這支檔沒有相關筆記」和「推播壞了」;hook 事件帳也把這些情況記成成功跑完。這次讓它在圖譜專案裡沒跑成時講一句固定的話,並把事件記成逾時或錯誤。

依據:2026-10-29 調研 codegraph(github.com/colbymchenry/codegraph)時對照 lumos 現況——推播 hook 有六條失敗路徑不出聲;主工作目錄的 hook 事件帳裡這支 hook 近期 285 筆全是 ok,因為吞掉失敗後照樣正常結束,共用記帳模組預留的「我吞掉了失敗」回報函式(`_hookevent.mark`)這支沒有接。

PRIOR-ART: ①codegraph 在索引還沒同步完時,於查詢回覆開頭加一句警告、點名哪些檔還沒同步、請 AI 對那幾支自己讀原檔,不假裝資料是新的;它的設計教訓是「可恢復的狀況回正常格式的提示,不回錯誤」。②本 repo 的派工鏡頭 hook 已走過同一形狀兩次([[Projects/第二輪審視六修_計劃]] 的超時出聲、[[Projects/派工鏡頭跨repo不再靜默_計劃]] 的範圍算不出來):固定字彙原因、零自由文字、帶值的句子進注入框、工具寫死的指示放框外、吞掉失敗處呼叫 `_hookevent.mark`。本案照抄那個形狀,不另立慣例。
RETIRE-IF: 上線後兩個月內,hook 事件帳裡這支 hook 的逾時與錯誤合計佔比低於 0.5%、而且沒有一次說明行讓人或 AI 發現推播壞掉,就把說明行拿掉、只留事件記帳;或 Claude Code 與 Codex 都提供「hook 失敗時把原因交給模型」的內建管道,改用內建的。

## 範圍

- 做:hook 在**圖譜專案**裡(被查的 repo 底下找得到圖譜,判法同 lumos 找圖譜的規則:`docs/*-knowledge`、`docs/knowledge`,或 repo 本身是獨立圖譜根)遇到下列情況時,經既有的附加脈絡管道送一段固定說明,仍然放行改檔:找不到可信的 lumos、查詢逾時、lumos 啟動失敗、lumos 回非零結束碼、輸出讀不懂、lumos 回「找不到圖譜」但 repo 底下明明有圖譜目錄。
- 做:說明分兩半照派工鏡頭慣例——帶原因的那句放注入框裡(`LUMOS-IMPACT:` 開頭,原因由代碼查固定句,非零結束碼只帶整數),工具寫死的指示(自己查的指令、同原因不再重複)放框外;不帶檔名、不轉 lumos 的錯誤原文。
- 做:同一個會談、同一個原因只講一次(記號放在既有冷卻窗的同一個暫存目錄,跟著 24 小時惰性清理走)。
- 做:上述每次失敗都呼叫 `_hookevent.mark`:逾時記 timeout,其他記 error;同一次多檔時有任何非逾時的失敗就記 error。輸入讀不懂(hook 收到的 JSON 壞掉)也記 error,但不出聲(判不出是不是圖譜專案)。
- 不做:零命中(查成功、沒有相關筆記)照舊安靜;不是圖譜專案照舊安靜、不記事件;hook 自己丟例外那條路照舊交給共用的 guard 記 error(要讓它也出聲得改五支 hook 共用的模組,另案);不改冷卻窗、排序、查詢本身。

## 實務隱患

- **全域安裝的噪音**:這支 hook 在任何 repo 改檔都跑;沒有圖譜的 repo 裡 lumos 回「找不到圖譜」是常態。判斷「是不是圖譜專案」由 hook 自己看目錄,不靠 lumos 的結束碼,所以 lumos 壞掉或不在時也判得出來。hook 是獨立檔、import 不到 lumos,找圖譜的規則只能複製一份;用一支測試對照 lumos 的 `_vault_in` 守住不漂。
- **長期壞掉時只講一次**:同原因一個會談只講一次,之後同原因的失敗不再出聲;說明句本身寫明「之後同一個原因不再重複提醒,沒看到推播不代表沒有相關筆記」,事件帳照樣每次記。
- **舊 lumos 配新 hook**:hook 只看結束碼、逾時與輸出能不能解析,不讀 lumos 新欄位,版本錯開不影響。
- **Codex 側**:同一支 hook 兩家共用,說明走的是兩家都收得到的附加脈絡管道([[Systems/codex-harness]] 記 Codex 只看附加脈絡與決定兩個通道),跟既有推播同一條輸出。
- 已排除:金流:只改 hook 附加給 AI 的文字,不碰任何金流
- 已排除:對外送出:不連網、不送任何東西出去
- 已排除:不可逆:只多寫暫存目錄裡的記號檔與既有事件帳的一行,退回提交即恢復
- 已排除:守衛面:hook 不擋改檔,任何失敗照舊放行;不改任何閘的判定

## 驗收條款

- [S1] 當被查的 repo 是圖譜專案、而且找不到可信的 lumos、查詢逾時、lumos 啟動失敗、lumos 回非零結束碼、輸出讀不懂、或 lumos 回找不到圖譜時,hook 應 回 0 並在附加脈絡送一段 `LUMOS-IMPACT:` 說明,框內那句帶對應的固定原因句(非零結束碼帶整數),框外帶自己查的指令,不留冷卻標記;被查的 repo 不是圖譜專案(上述任何一種失敗)、或查詢成功但零命中時 應 照舊不輸出任何東西,也不記失敗事件(出聲與安靜是同一條判準的兩面,同一支測試對照) [test:t_impact_hook_six_failures_voiced]
- [S3] 當同一個會談第二次遇到同一個原因時,hook 應 不再送說明;換一個原因或換一個會談時 應 照樣送 [test:t_impact_hook_failure_voice_once]
- [S4] 當一次改多支檔、其中一支查到筆記另一支查詢失敗時,附加脈絡 應 同時有那支的推播與失敗說明 [test:t_impact_hook_failure_voice_multifile]
- [S5] 當查詢逾時時 hook 應 以 timeout 呼叫事件回報函式,其他失敗與 hook 收到的輸入讀不懂時 應 以 error 呼叫;同一次多檔混有逾時與其他失敗時 應 記 error;成功、零命中、非圖譜專案時 應 不呼叫 [test:t_impact_hook_failure_marks_event]
- [S6] 當 repo 佈局分別是 `docs/x-knowledge`、`docs/knowledge`、獨立圖譜根、`docs` 底下只有一般目錄、沒有 `docs` 時,hook 判斷是不是圖譜專案的結果 應 跟 lumos 找圖譜的規則一致 [test:t_impact_hook_graph_check_agrees]
