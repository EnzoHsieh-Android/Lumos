# 按需檢索_計劃

> 白話:現在是「你要改檔,我先塞八篇筆記給你」。要改成「你要改檔,我先給你一張目錄,你覺得需要才自己去讀」。省的是每次都付的 token,換來的風險是有人懶得點進去讀。

## 現況(以程式碼為準,不是印象)

改檔前的推播已經有一層降噪,不是把整個圖譜倒給 agent:

- 冷卻窗外:算波及,推「固定席 + 前 8 篇」,**這 8 篇是貼內容的**,不是只給篇名。
- 冷卻窗內:只跑事故比對,重型計算降頻。
- 規矩層另外要求「改 code 前至少 `lumos impact --file <檔>` 一行」,寫在紀律範本、skill 索引、進場提醒三處。

所以目前的形狀是 **Code First → 無條件推內容**,建議原文要的是 **Code First → 看目錄 → 挑 → 才深讀**。差的是中間兩步。

## 落差(三項)

1. **沒有「需不需要」這一步**:推播無條件跑,任務完全能從程式碼回答時也照推。
2. **推的是內容不是目錄**:前 8 篇直接貼正文,agent 沒有「先看一眼再決定」的機會。
3. **規矩層仍強制至少一次檢索**:即使是純重新命名、排版、加測試這種 code-contained 任務。

## 三個選項

| | 做法 | 好處 | 壞處 |
|---|---|---|---|
| **甲(建議)** | **兩段式**:第一段只推目錄(篇名+標籤+一行摘要+有沒有合約),agent 要看才敲 `lumos context <節點>` | token 大降;深讀與否有痕跡可量;不需要任何分類器 | 多一次來回;agent 可能偷懶不深讀 |
| 乙 | **任務分類路由**:先判這次編輯是不是 code-contained,是就靜默不推 | 真的零成本 | 分類會錯,錯過事故節點的代價最高 |
| 丙 | 維持現況,只放寬「至少一次 impact」的硬規矩 | 最便宜 | 沒解決成本問題,等於不做 |

**建議走甲,並且事故與合約那一層維持無條件推內容**。理由:甲不引入會判錯的新元件,只是把「內容」換成「目錄+拉取」;而乙的失敗模式是漏看事故,那是這套機制最貴的錯。

## 怎麼驗收(判準先寫死,跑完不准改)

三支既有儀器,不開新的:

- **鏡頭利用率重算**(`governance/eval/lens-utilization/recount.py`):量「推了幾篇、真的被讀進去幾篇」。目錄式的深讀率要能看出 agent 有在挑,不是全部略過。
- **用量掃描**(`scripts/usage_scan.py`):量 token 有沒有真的降。
- **情境探針**(`scripts/scenario_probe.py`):量行為沒退步。

**放行判準**:目錄式那組的「真問題發現率」不得低於現況組,且 token 要降。**任一條沒達到就退回現況**,不准用「理論上比較好」放行。

## 誠實界線

- 建議原文裡四個假設,這條(檢索成本)是**唯一完全沒有實驗數據的**,前面的受控實驗一場都沒測到它。
- 「agent 會不會偷懶不深讀」沒有先驗答案,這正是甲案唯一的風險,也是驗收要量的東西。
- 本 repo 的推播早就有冷卻窗降噪,所以「現在很貴」這句話本身還沒量過——**開工第一步是先量現況成本,量不出問題就不要做**。
RETIRE-IF:量完現況發現推播成本佔比很小(例如低於整體 token 的 2%),這整個計劃撤掉,不值得換複雜度。
