# 筆記內容審_計劃

白話:筆記只准寫程式碼推不出來的東西。第一層([[Projects/筆記形狀擋_計劃]],已上線)在提交時擋兩種形狀固定的寫法;這一篇是第二層:推送前,派一個沒有脈絡、會去讀程式碼的審查員(下稱「判定者」),逐行判這次新寫的筆記內容是不是程式碼推得出來,判是的要刪掉才推得上去。

依據:[[Issues/筆記把程式現況寫進脈絡而漂移_rtb實測回饋]] 的 d1–d6、d8(Enzo 2026-09-27 裁)。

**★這篇是重寫稿★**:前身是 [[Projects/筆記不存程式碼推得出的事_計劃]] 的第二層部分,設計審三輪(r1 38 條、r2 32 條、r3 35 條)後,r3 查出核心設計有洞——通過紀錄重跑一次判定者就能洗掉、計劃轉 done 的整篇重審會空轉、「直接借第一層」借不動、記錄那一步不知道是哪一家判的——Enzo 2026-09-27 裁「重寫、開新一輪審查」。r3 的 34 條折進本篇(對照見文末〈前身 r3 發現怎麼處理〉),1 條駁回。

PRIOR-ART: 借本 repo 四個既有形狀,借法寫死:①「哪些筆記行是這次新寫的」借第一層已上線的算法,但先把它從第一層內部抽成兩層共用的函式(見〈做法〉第 1 節);②判定結果存成「一份報告一個檔」、進版本控制——★這是新存法★,只從關係層連鎖帳本 `governance/rel-cascade/<id>.jsonl` 借到「進版本控制的逐件檔」這個形狀,寫法用既有的 `_write_lf`,折疊規則(取最重、申訴只換它指名的那筆)是新定的;為什麼不照既有兩種存法,見〈做法〉第 2 節(r1 架構對齊席:原稿把新做法掛在連鎖帳本名下,講錯了);最接近的防竄改先例 `loop replay --freeze`/`--golden` 刻意不用,因為防竄改不在範圍(〈做法〉第 0 節,r2 架構對齊席);③推送前查有沒有紀錄、`--no-verify` 硬推時 CI 標紅、帶理由的 skip 出口,照代碼審留痕閘([[Systems/pitfalls-code-loop]]);④設定從被檢查的版本讀、不是 block 時 doctor 每次印一行,照第一層 `note_shape.gate`。判定者照無脈絡審查席的派法(乾淨 agent、只給原始問題不給結論)。世界的做法:文件與程式碼同步多半走「從程式碼生成文件」(見 [[Systems/外部對照-code衍生wiki]]),它讓文件免疫漂移但裝不下程式碼沒有的脈絡——本案反過來,讓筆記只裝那一種。不採用新依賴。
RETIRE-IF: 上線兩個月後任一成立就撤掉或重想:①作者申訴被第二席認同的比例超過三成(判定者不可靠);②對上線後新增的筆記行隨機抽樣,仍有一成以上是程式碼推得出來的(擋不住);③新增的脈絡行月量掉到上線前的三分之一以下(大家乾脆不寫筆記了,擋掉的比救下的多)。
REVISIT:2026-11-27 跑上面三個量;順便在 rtb 重做一次跟 2026-09-27 同方法的漂移抽樣,拿 41% 當基準比;同一天看判定檔目錄的檔數與大小。

- 派工詞第 2 版(2026-10-03,[[Projects/舊行尾追加不算新寫_計劃]] 加「只判句尾」那段)另跑一組補括號樣本 9 句(消費專案真實更正去識別,答案事先寫好,樣本不進 repo):舊句推得出+括號是脈絡、舊句是脈絡+括號推得出、括號是混合各 3 句。第一次跑 7/9(B 組兩句判一半一半——括號夾了歷史經過,我挑樣本沒挑乾淨;不改答案、記為沒過),範本用字也要改(代碼審 r1 通才席:confirm 改 confirm or refute),Enzo 裁改範本後重跑並換掉 B 組樣本;重跑 8 句判對、1 句判定者把編號抄錯而收不下(照位置看它判的跟答案一樣)、0 句因舊句推得出就把括號判成推得出。回歸 68 句兩次都是 55 與 0。Codex 那家沒跑,照下方〈上線前校準〉接線前再跑。第 2 版範本在這次重跑前改過用字、版本號沒再升:改字發生在第 2 版第一次推送之前,沒有用它發出的舊清單,所以不算改版;推送之後改一個字就要升版(範本雜湊與版本常數由測試一起釘住)。
- 兩席在「要不要擋」上 68 句同意 64 句。判成一半一半的理由句我逐句看過,裡面確實夾著程式現況(例如「某函式在第幾階段加的、路由和評估都靠它」)。
- **誠實界線**:正例是稽核挑出來的現況句,比真實新增行好判;反例只有 13 句;對照答案由我一人訂。真正難的是「一句話裡理由跟現況混在一起」,這類樣本太少。所以 claude 編排時判定者用 opus(Codex 編排時用同一家的審查席模型,見〈做法〉第 3 節第 2 點,那一家的準度要另外校準)、派工詞要明寫「描述已刪掉的程式、用現在式寫的,也算推得出」,而上線後的申訴率是第一個要看的數。
- 句型比對做不到這件事:同日對近一個月 25,282 行新增筆記跑「目前沒有/只有 N 種」句型,抽樣約三分之一是真的,見 Issue〈擋什麼的初步實測〉。

## 做法

### 0. 防什麼、不防什麼(r2 後收窄,Enzo 2026-09-28 裁「收窄成防疏忽」)

- **要防的是疏忽**:AI 會談寫筆記時沒注意到自己寫進了程式碼推得出的東西。所以機械要保證的只有三件:①每一行新寫的筆記都有判定;②判成推得出、一半一半的,那一行不消失就推不上去;③已提交的較重判定,不會被之後較輕的一般判定蓋掉;申訴能調輕它指名的那一筆,但多份申訴取最重的(第 2 節第 1 步)。
- **不防存心繞過**:刪掉或改掉判定檔、還沒提交就把判定檔或治理帳丟掉再重判、手寫判定檔、手改治理帳——這些跟 `git push --no-verify` 同一級,是故意的動作。本機檔案沒有祕密可以簽名,r1、r2 兩輪為了防它加的「判定檔只准新增」「判定檔跟治理帳指紋互驗」「申訴一生一次」等機制,每一層都長出新的洞(r2 三條最嚴重的都在這裡),所以整批拿掉。發現靠每月抽樣(RETIRE-IF ②)與 doctor 印出判定檔被刪的次數。
- **信任只需要單向**(r2 正確性席):重的判定(推得出、一半一半)只會讓擋得更嚴,沒人需要偽造它、也不用驗它的來歷;要小心的只有「脈絡」「略過」這兩種會放行的結果。下面的規則都照這個方向設計:可疑時,重的照收、輕的不收。

### 1. 哪些行要審:先把第一層的「新寫的行」抽成共用函式

第一層設計當時的樣子(以程式碼為準,查法:讀 `scripts/lumos` 的 `_note_shape_eval`;2026-09-28 實作時範圍函式改名 `_notelines_range_added`,兩層共用):範圍函式(當時叫 `_ns_range_added`) 只回「範圍裡每個提交加過的行文字」的集合,不帶行號、後來刪掉的也還在;「終點版本裡還在、落在哪一塊、第幾行」是 `_note_shape_eval` 在自己的迴圈裡邊查規則邊算的。所以第二層不能只呼叫那支範圍函式(前身 r3 三席實測)。

- **抽出一支共用函式**「範圍裡新寫、而且終點版本還在的筆記行」,回傳每一行的(git 原樣路徑、行號、行文字、所在區塊、所屬小標題);第一層改成呼叫它,第二層也呼叫它。區塊判定沿用第一層那支。第一層的所有既有測試不改一字要照綠。
- **命名與家**:抽出來的共用函式與區塊判定改成兩層共用的名字,說明寫進 [[Systems/筆記內容閘]],那篇的負責範圍改寫成「不管第二層的判定與紀錄,但『哪些筆記行算新寫的』共用函式歸這裡」。上線點與範圍起點那兩支函式的家照舊是 [[Systems/每支檔有家]]。第二層自己的程式開新家 `Systems/筆記內容審`。
- **所屬小標題**:正文是往上找最近一行 `#` 開頭的標題,★找的時候跳過圍欄內的行★(用全檔唯一的圍欄判定 `_visible_lines`,它認得三個以上反引號或波浪號的圍欄、關閉時要同字元且不短於開頭,r2 兩席:圍欄裡的 `#` 註解會被當成標題);一個標題都沒有就是空字串。summary 裡的行一律是 `summary`。decisions 裡的行是「decisions/<決策編號>/<欄名>」(r2 三席:原稿只寫「欄名」,分不出是哪一條決策)。★要新寫一支小函式★:既有 `decisions_items` 只給每一條決策的起訖行(r3 三席查證),在它給的範圍裡,用 `decision-supersede` 同一支的 `id:` 比對取決策編號,再逐行歸屬欄名(`鍵:` 開頭的行是那個欄,後面縮排更深、沒有 `鍵:` 的續行跟著前一個欄),同時讀出那條決策的 `valid`。
- **第二層的「上線」只看範圍,不逐提交判**:第一層逐提交看「那個提交自己的提交前掛鉤」,因為提交前掛鉤在寫的那一刻跑;第二層在推送時才跑,跑的是 `core.hooksPath` 指向的工作目錄那份推送前掛鉤,跟被推的每個提交樹裡那份無關(r2 正確性席:原稿寫成「被推分支自己那一版」不對)。所以第二層的判準是「這一行在第二層上線後才第一次被推」:範圍起點截到第二層上線點(上線點函式與截斷函式加「看哪支掛鉤」參數,第二層傳推送前掛鉤與標記 `note-audit check`;上線點照第一層從被推頂端的歷史找),已在主線上的提交照第一層排除;逐提交判上線那一段,第二層傳一個明確的「不過濾」值——★不是不傳★,不傳會落到第一層的預設(r2 正確性席)。上線前開、上線後才推的分支上的行照樣要判。
- **找不到上線點時**:照既有語意,不截斷也不過濾(全部新增行都收)。只會多審、不會漏。
- **不審的行**:空白行;圍欄記號行(照 `_visible_lines` 的判定:縮排不超過三格、以三個以上反引號或三個以上波浪號開頭的行);表格分隔行(整行只有 `|`、`-`、`:` 與空白);分隔線(整行只有三個以上的 `-`、`*` 或 `_`);只有清單記號的行(整行只有 `-`、`*`、`+`、`數字.`、`數字)`,後面可接一個 `[ ]` 或 `[x]`,再來只剩空白)。
- **計劃在範圍內被收尾**:「計劃」= `type: project` 的筆記;「收尾」= 範圍終點版本的 status 是 done 或 superseded,而且★範圍裡有某個提交把那篇的 status 從非收尾改成收尾★——逐提交讀那篇的 status(用批次讀檔,改名照改名偵測找舊路徑;範圍起點版本不存在時,第一個提交就算)(r2 正確性席:以 superseded 收尾的也要審;r3 兩席:原稿只比範圍兩端,同一次推送裡「收尾→改回 doing→再收尾」起點終點都是 done,一行都不審)。那篇的正文、summary、decisions 文字子欄都進「完成審」;★decisions 裡 `valid: false`(已翻案)的整條決策不進★,用上面那支新函式讀每條決策的 valid(★這個排除只用在完成審★:新寫的行照一般規則判,就算它所在的決策已翻案,r3 正確性席)。同一行同時是新寫的、又在完成審的那篇裡,只要完成審編號。同一次推送裡收尾好幾次,只審一次(完成審編號不綁提交,見第 2 節)。
- 只在推送前與 CI 跑,提交前不跑。筆記讀不成 UTF-8:照第一層列成錯誤、擋下並講是哪支檔。

### 2. 內容編號、判定檔、判定怎麼算

- **內容編號**=(NFC 路徑、所在區塊、所屬小標題、去頭尾空白的行文字)的短雜湊(16 個十六進位字)。同一小標題下一字不差出現兩次的,共用一個編號,清單列出每一處;判定者對一個編號只給一個判定,兩處語境不同時給較重的那個(派工詞第⑦句)。
- **完成審編號**:同上四樣再加「完成審」標記,★不綁任何提交的版本號★(r3 正確性席:原稿綁「收尾那個提交」,照本 repo「推之前壓成一個提交」的規矩,判定檔一放進那個提交,版本號就變,永遠對不上;rebase、壓縮合併也一樣)。進行中的判定不涵蓋完成審。一行以完成審判過之後,之後再收尾不用重判那一行(它已經在「做完了」的眼光下審過);重開後新寫或改過的行,下次收尾時是新內容、會判。
- **判定檔**:一份判定者報告(或一次申訴、一次略過)寫一個檔,放在新資料夾 governance/note-verdicts/,檔名 `<UTC 時間 YYYYMMDDTHHMMSSZ>-<32 個十六進位字的亂數>.json`,用既有的 `_write_lf`(暫存檔再原子換名)寫;★只有檔名合這個格式的才算判定檔★,`_write_lf` 被中斷留下的暫存檔(檔名尾巴是 `.tmp-wlf`)不算(r2 正確性席)。判定檔裝:來源(席名、編排者、模型、派工詞版本、清單檔指紋、清單當時的頂端提交、時間、種類=判定|申訴|略過、申訴的是哪個判定檔)與每一行的(內容編號、分類、證據、理由、證據驗過沒;舊行尾只補括號、清單上只判句尾的那幾列多一個 `tail`=舊句雜湊 16 碼十六進位,2026-10-03 起,見 [[Projects/舊行尾追加不算新寫_計劃]])。判定檔壞掉(不是合法 JSON、缺欄位):★當作不存在並印出檔名★,它裡面的判定都不算(r3 正確性席:原稿讓一個壞檔擋住之後所有推送,連沒有待審行的也擋);壞檔裡若有重的判定,那幾行會變回待審,方向是多擋。
- ★這是專案裡新的存法★:專案既有兩種——治理帳那種「大家寫同一個 jsonl、讀的時候取最後一筆」與放行檔那種「一個 json、讀改寫上鎖」——都不適合:前者讓重擲的最後一筆蓋掉前面,後者幾乎每次推送都改同一個檔、兩條分支合併必衝突。連鎖帳本只借到「進版本控制的逐件檔」這個形狀。專案裡最接近的防竄改先例是審查判定的凍結與回放比對(`loop replay --freeze`/`--golden`,檢查「只追加的帳有沒有少東西」),本案刻意不用——見第 0 節,防竄改不在範圍內。
- **判定怎麼算**(對每一個內容編號):
  1. 列出所有種類=判定的檔裡對它的判定;每一筆如果被申訴過,就換成★所有指名它的申訴裡最重的那個結果★;
  2. 取這些(換過之後的)判定裡最重的(推得出 > 一半一半 > 脈絡);
  3. 沒有任何判定時,有略過就算略過。
  結果唯一、跟讀檔順序無關:兩條分支各自申訴同一筆判定、合併後,取兩個申訴裡較重的(r2 三席)。多申訴幾次只會更嚴、不會更鬆,所以不用限制申訴次數(拿掉 r1 的「一生一次」)。
- **涵蓋**=算出來是「脈絡」或「略過」。推得出、一半一半都不涵蓋——那一行只能消失。
- **讀的成本**:check 讀被推頂端的判定檔資料夾,用一次列目錄加一次批次讀檔(`_nodehome_cat_blobs` 那種讀法),不逐檔開程序。REVISIT 那天量實際檔數與 check 花的時間,超過 5 秒再做索引(r2 邊界席)。
- **治理帳**:只記觀測用的短事件——`prepare`(派出,帶清單指紋與行數)、`recorded`(帶判定檔名與各類筆數)、`skipped`、`skipped-env`、`warned`、`blocked`;★不拿治理帳來判涵蓋★。閘名 `note-audit` 登記進既有閘名單 `_KNOWN_GATES`。

### 3. 指令(`lumos note-audit`)

1. **`prepare --diff <範圍> --orchestrator claude|codex [--only <內容編號>…]`**:算出第 1 節那批行,扣掉已被涵蓋的——★prepare 讀工作目錄裡的判定檔★(剛 record、還沒提交的也算,免得重派;check 只認已提交的)。剩下的是待審;空的就說「沒有待審的筆記行」、rc0、不產生檔。★待審超過 150 行就切成多份清單★,每份不超過 150 行;切法:先照筆記分組,同一篇放同一份;單篇超過 150 行時在小標題邊界切,單一小標題下就超過 150 行時照行數硬切(r3 邊界席)。每份清單分兩段:★本文★先寫當下頂端提交,再逐行列內容編號、區塊、小標題、行號、前後各兩行的上下文與上下文指紋;★開頭★寫編排者、判定者模型、派工詞版本與清單指紋。★清單指紋=本文那一段的雜湊★(開頭不算進去,所以開頭能寫出指紋給判定者照抄,不會自己指到自己,r3 兩席);本文含頂端提交,所以同一家在不同頂端對同一批行 prepare,指紋也不同(r3 併發席)。檔名 `.lumos/note-audit/<清單指紋>-<編排者>.md`。`--only` 只列指定的內容編號,給申訴用(r2 正確性席:原稿的申訴沒有「只判一行」的做法)。清單用 `_write_lf` 寫;目錄第一次建立時放一支只寫 `*` 的 `.gitignore`;順手清掉 14 天前的舊清單。治理帳記一筆 `prepare`(清單指紋與行數),「派了卻沒記」查得到(只觀測)。

3. **作者處理**(順序:先 record 原判定,再處理):推得出的整行刪;一半一半刪掉推得出的子句(刪完是新內容、新編號,下一次 prepare 會再列出來);「引句:」行被判就整句刪、不改字。`decisions` 裡被判的:還沒推上去的用 `decision-amend` 改,已推上去的用既有 `decision-supersede` 翻案、新決策文字只寫脈絡。**申訴**:原判定 record 之後,`prepare --only <那幾個內容編號>` 產一份小清單,另派一席(席名跟原判定的席名不同)判,用 `record --dispute --disputes <原判定檔>` 記(r2 正確性席:原稿的順序走不通)。
4. **`decision-amend <節點> <決策編號> --field <欄名> --text "<新文字>"`**:只改那一條決策的那一個文字子欄;`id`、`decided`、`valid`、`superseded_by`、`ended` 這些結構欄不准用它改(r2 外家席、r3 接手席)。只准改還沒推上去的決策:★它自己先跑一次 `git fetch --all`★,fetch 失敗(沒網路、遠端要驗證)就拒絕並講原因(r3 四席實測:原稿看追蹤參照的 reflog,但全新 clone 沒有紀錄、遠端沒變時 fetch 也不寫紀錄,照提示跑 fetch 之後還是拒絕,卡死)。判法:對每一個遠端追蹤參照,用改名偵測找出這篇在那個參照上的舊路徑,讀那個版本:沒有這個決策編號 → 可改;有 → 拒絕,訊息同時講兩種可能:「已經推上去了,請用翻案指令」或「兩條分支撞號,請先把你的決策改號」(r2 正確性席:本機手改過已推的決策會被誤判成撞號,工具分不出來,就兩種都講)。沒有任何遠端就都能改。
5. **`record --diff <範圍> --prepared <清單檔> --report <報告> [--report …]`,申訴用 `record --diff <範圍> --prepared <小清單> --dispute --disputes <判定檔> --report <報告>`**:
   - **來源錨點**:每份報告開頭四行要齊;`provider:` 要等於清單的編排者、`model:` 要等於清單記的模型(字串完全相同)、`prepared:` 要等於那份清單的指紋;清單的派工詞版本要等於工具目前的版本。★不合時照信任方向★:那份報告裡判推得出或一半一半的行照收(重的不用驗來歷),判脈絡的行不收(r3 正確性席:原稿連重的都丟,等於讓疏忽變成換一席再判)。
   - **逐行收,照信任方向**:報告裡每一行,分類要在三類之內、不在的那一行不收;同一份報告對同一個編號寫了好幾列,取其中最重的(r3 正確性席);編號要在清單裡;★上下文指紋變了的那一行:判推得出或一半一半照收,判脈絡不收(那行照樣待審)★(r2 正確性席:照規定先刪一行再 record,原稿會連帶讓鄰居的推得出都不收)。證據只做紀錄:`file:line` 用 `_validate_repo_ref` 帶清單當時的頂端提交讀 git 版本(讀的是 git 裡的內容,捷徑讀到的是連結文字,不會讀到 repo 外的檔);`search:` 在那個提交的樹裡掃 repo 內相對路徑、最多 20,000 支檔;驗不過的標「證據不合格」記進判定檔,判定照樣生效。
   - 比既有判定輕的一般判定也照收(依第 2 節不會生效,但留下紀錄)。
   - 申訴:報告席名要跟被申訴那份判定檔的席名不同;`--disputes` 指名的判定檔要真的判過報告裡的那幾行。
   - 每份報告寫一個判定檔;治理帳記 `recorded`。印出「還沒被涵蓋的行」與要提交的檔。
6. **`check --diff <範圍>`**:推送前與 CI 另開一支平行呼叫(跟 `home check`、`note-shape --diff` 並排,★推送前掛鉤與工具鏈自己的 CI 裡都排在 `code-loop check` 之前★,r3 接手席)。★範圍起點照三道檢查共用的推送起點判法★(實作時改,2026-09-28:原稿寫「40 個 0 一律當空樹」;第一層修漏網時發現新分支開在主線頂端會把主線上的舊帳誤擋,所以每支檔有家、筆記形狀擋、代碼審改共用一支判法——頂端落後或等於主線就沒有新東西、其他從跟主線的分岔點算、找不到主線才用空樹,見 [[Projects/筆記形狀擋_計劃]];r3 兩席要的「40 個 0 不能放行」照樣成立)。判定檔一律從被推送的那個頂端提交裡讀。每一行都被涵蓋就放行;否則 rc1,列出沒被涵蓋的行(最多 20 行,其餘給筆數)並印 prepare 指令;涵蓋它們的判定檔只在工作目錄、還沒提交時,另外印提交指令。
7. **出口與開關**:

   - 模型限流、服務中斷時走 skip。
8. **跟代碼審的先後**:★判定檔資料夾加進簿記豁免 `_BOOKKEEPING_DIRS`,四個消費者逐一確認★(r3 接手席:不加的話,判定檔的大段 JSON 會被小改動閘當成程式改動量,撐爆相對量門檻;r2 當時不加是因為沒分析影響,現在分析):小改動閘的改動清單(判定檔不算程式改動量——對,它是紀錄)、風險型樣掃描(不掃判定檔——對)、改動風險分級(判定檔不抬分級——對)、代碼審留痕有效性(只新增判定檔的提交不讓留痕失效——對,判定檔不是碼;★筆記行的刪改照舊會讓留痕失效★,筆記不在這組裡)。四個消費者各補一條測試(S17)。順序仍建議:先過筆記內容審(record、提交判定檔),再做代碼審留痕。推送前掛鉤裡 note-audit check 排在 code-loop check 之前,所以沒審的會先在這裡被擋。已經先留痕才被擋的:只提交判定檔不影響留痕;若照判定刪了筆記行,那個提交會讓留痕失效,程式碼沒變,重跑一次 `code-loop pass --note` 就好,不用重審。skill 流程照這個順序寫(拿掉 r1 那條「`code-loop pass` 印提醒」,它拿不到範圍,r2 兩席)。
9. **消費專案的 CI 與 doctor**:`lumos update` 不會動各專案的 CI 設定檔,所以 doctor 檢查專案 CI 有沒有呼叫 `note-audit check`(跳過 YAML 註解行;第一層那段同一支一起改),沒有就印一行並給要貼的那一步,步驟照第一層 doctor 給的那步,在它後面加 note-audit check 那一步;★範圍起點直接把 GitHub 給的前一版(可能是 40 個 0)交給工具★,由工具的共用推送起點判法處理(第 3 節第 6 點;實作時改:原稿要 CI 步驟自己換空樹,跟共用判法重複又會把主線舊帳算進來)。條件式步驟是否真的會跑不判。另外 doctor 事後掃兩件事,都從遠端頂端提交讀、照第一層只看遠端最新 200 個提交、不在 `--ci` 路徑跑:「已推上遠端卻沒被涵蓋的新增筆記行」,以及「主線歷史裡判定檔被刪過幾次」(只印數字,給 RETIRE-IF 看)。

### 4. 上線前校準與接線

小實驗餵的是稽核員切好的單句,正式跑的是原始整行加上下文。所以接線之前,兩家都要各做一次、都達標才接線(推送前掛鉤全 repo 只有一份,分不出這次推送是哪一家在編排):用 prepare 對 rtb 近一週真實的新增行、再加一份 300 行以上的已完成計劃整篇、再混入 68 句小實驗裡的 55 句已知現況句,兩席各自獨立判,編排者抽 30 行人工對照。達標要同時滿足:①55 句已知現況句抓到至少 50 句;②兩席「要不要擋」一致率至少 85%;③人工對照純理由被判推得出不超過 2 行;④報告裡能被 record 逐行收下的行至少九成。任一不過就不接線、改派工詞重來。換模型、改派工詞都要重做。

- 紀律範本〈寫筆記時〉那張表的 FACT/FLOW/DEP 列第一層已改好;第二層在同一段補一句:推送前會派判定者逐行判新寫的筆記,判成程式碼推得出來的要刪,不服可以申訴、真的來不及用 skip(會留帳)。

## 實務隱患

- 守衛面:新的擋人機制,誤擋會讓人習慣繞過——所以有申訴、skip 與專案開關,關掉或跳過都寫帳、doctor 持續印,全部進 RETIRE-IF 的量。存心繞過不在防的範圍(第 0 節)。
- 對外送出:筆記行、上下文與被讀的程式碼會送到判定者那一家模型;限定跟編排會談同一家、不派外家席,不會多出一家供應商。
- 資源併發:兩個會談同時 prepare → 清單檔名是清單指紋加編排者(本文含頂端提交,不同頂端不同名),原子寫入;同時 record → 各寫各的亂數檔名判定檔、原子換名,不共用檔、不用鎖;兩條分支各自寫判定檔 → 檔名不同,合併不衝突,合併後依「取最重」可能讓某一條分支原本涵蓋的行重新不涵蓋(方向是多擋);審查中途斷掉 → 沒有判定檔就是沒涵蓋。治理帳:寫入頻率會變高(幾乎每次推送都有 prepare、recorded 事件),兩條分支各自追加、合併時可能衝突(這是所有閘共用這本帳的既有狀況,r2 兩席);★第二層不拿治理帳判涵蓋★,所以帳的壞行或合併時丟行只影響觀測數字。[[Issues/治理帳多個寫入者都沒上鎖]] 的 REVISIT(2026-10-11)照看。
- 可用性:模型限流或服務中斷時走 skip(留理由、進帳)。
- 容量與速度:每份報告一個檔;本 repo 近一個月 473 個提交,估一個月數百個小檔、合計幾 MB 以內。check 用批次讀檔;REVISIT 那天量檔數、大小與 check 花的時間。要壓縮時,壓縮結果必須保留每一筆的申訴關係與略過(不能只留最重)。
- 已排除:不可逆:擋在推送前,提交都還在本機;decision-amend 只改還沒推上去的決策;拿掉閘就恢復原狀
- 已排除:金流:不碰任何付款或計費流程

## 誠實界線

- 判定者的準度只驗過一次、68 句、反例 13 句,而且是切好的單句;所以接線前兩家都要照〈上線前校準〉再驗,上線頭兩週逐筆看申訴。
- 存心繞過擋不住(第 0 節):刪改判定檔、判完不提交就丟掉再重判、手寫判定檔,check 都看不出來。這跟 `--no-verify` 同一級;doctor 只印判定檔被刪的次數,抽樣靠 RETIRE-IF ②。
- 小改筆記換編號:行尾加一個字,那一行就是新寫的行、編號也換,要重判;重判是新內容的正常判定,但也給了繞路的空間。只改小標題或把筆記改名時,底下沒動的行不算新寫的行、不會被收進來重判(r2 正確性席);被搬到另一個小標題下的行,如果這次也算新寫,才會用新編號重判。
- 逐行判有縫:刻意把一句推得出的話拆成很多行,上下文擋得住大部分,擋不住存心的。
- 報告的 `model:` 是判定者照抄的,工具驗不了實際跑的是哪個模型;派錯模型只能靠 skill 的派工步驟與校準發現。
- 編號含路徑與小標題:寬範圍時(CI 從空樹起算、doctor 事後掃描),改過名或改過小標題的舊行會被報成沒被涵蓋——多擋,對那些行再 record 就好(r3 正確性席)。
- 判定只綁那一行的文字。當初判成脈絡的話,之後程式碼改了變成推得出,不會重審(d2 不回頭清);計劃收尾時整篇重審一次。
- 本機與 CI 的範圍可能不同(本機新分支排除所有遠端分支上的提交,CI 從空樹截到上線點、只排除主線);CI 可能多看到一些行、而涵蓋它們的判定檔在另一條還沒合進來的分支上——CI 紅、看得見,合進那條分支或對那些行再 record 就好。warn 或 off 期間推上主線、沒判過的行,之後只在這種寬範圍時才會冒出來。
- decision-amend 自己先 fetch 所有遠端,但 fetch 之後到改之間,別人仍可能推上同一個決策。
- doctor 只看 CI 設定裡(註解以外)有沒有那一步,不判它的條件會不會成立。
- 沒有接 CI 的消費專案,`--no-verify` 推上去當下擋不住;doctor 事後會列出來,但那時已經在遠端了。
- 花費與等待:本 repo 幾乎每次推送都有新增筆記行,所以幾乎每次推送都要派判定者;一次要判幾十到幾百行,計劃收尾時可能上千行(切成多份平行派)。Enzo 已表明不在意額度(d6),但推送前要多等判定者跑完。
