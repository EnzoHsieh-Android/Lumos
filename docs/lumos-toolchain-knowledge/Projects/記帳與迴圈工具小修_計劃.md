# 記帳與迴圈工具小修_計劃

> 白話:前端示範(order-web)記審查帳時踩到的一串小坑,最痛的是「照 `loop next` 給的範本記了一筆沒輪次的帳,整個迴圈就判不了、只能換編號重記」。這份把它收成一條規則——**分級 standard/high 的迴圈每筆都帶輪次,寫進去會讓迴圈「有的帶、有的不帶」就當場擋**——再順手修八個「工具沒講清楚」的小地方:`none` 當成 id、設計審收了用不到的欄位、表態證據型別錯看不懂、留痕入帳後沒提醒不能改、pitfalls 判 standard 沒講還要審、拆包審填錯整份、資安包與載體最後記的順序、首輪先排乾再凍結。來源:示範流水帳 F11、F16、F20–F25、F28、F31——這些編號是那次示範編排者自己記的流水帳序號,逐條比對表收在調研筆記 `Projects/Web示範前端缺口_調研`(2026-10-15 寫這份時它在 EnzoHsieh-Android/web-gaps 分支,所以這裡寫路徑、不寫連結)。

## 用詞

- **載體(載體席)**:同一輪審查裡,唯一帶處置清單(`--findings-set`/`--folded-set`/`--accepted-set`)記帳的那一席;其餘席只記嚴重度、條數與報告。處置閘看到同輪兩筆載體就擋。
- **寫側／讀側**:寫側=`canary record` 把一筆寫進審查帳(`docs/.canary-log.jsonl`)之前的檢查;讀側=之後讀帳判定的指令(`loop next`、`loop status --disposal` 處置閘、回放)。帳本只能追加,寫側擋得住的錯,讀側只能事後判不過。
- **佔人數(W)**:分級規定每輪要幾位審查員(`loop next` 印的「這輪要 N 人審」)。名冊上「不算進人數／不佔 W」的席(架構對齊、資安、外家)是額外加派,不抵這個數。
- **載體最後記**:代碼審 minor 解綁(PR #95,2026-10-15 合進主線,單源 [[Projects/代碼審minor解綁_計劃]])加的寫側規則——同一輪已經有帶 `--finding-source` 的載體之後,再記同輪任何一席都擋,因為新報告會讓逐條放行的核對失效;要補只能記下一輪。

### 1. 輪次一條規則(F23、F24)

現況(以程式為準,2026-10-15 在 web-ledger 工作樹重現):
- `cmd_loop_next` 對 code- 迴圈、分級 standard、帳上沒有帶輪次的記錄時把 `seq` 設成真(循序單審,[[Projects/循序codeloop-tier錨定_計劃]] 的設計);`_tpl_flags` 對 `seq` 省略 `--round`,所以**全新的** standard 代碼審第一輪印的 `record_cmd` 與 `disposal_cmd` 都不帶 `--round`。實測 `loop next code-zzz-probe --tier standard --orchestrator claude` 的兩條範本都沒有 `--round`。
- 但 `cmd_canary` 對處置帳(`--findings-set`)硬要 `--round`(「處置帳必須綁 --round 和 --auditor」),所以 `disposal_cmd` 那條範本照抄必被擋;而 `record_cmd` 那條照抄會寫進一筆沒輪次的帳。之後載體加上 `--round` 寫進去,迴圈就變成「有的帶、有的不帶」,`loop next` 與處置閘(`cmd_loop_status` 的 disposal 路徑)都 rc2,帳撤不掉,只能換編號重記。
- 文字輸出只印 `canary_type/record_cmd/scope_cap/cluster_hint/note` 五個鍵,`disposal_cmd` 只在 `--json` 裡看得到——人照文字走,只看得到不帶處置清單的那條。
- 真帳(2026-10-15 數 `docs/.canary-log.jsonl`):定錨 standard 的 code- 迴圈 147 個,144 個每筆都帶輪次,2 個全不帶,1 個混用(`code-兩席相反時端出張力`)。循序不帶輪次的形狀實際上只剩極少數,而且**它記不了處置帳**(處置帳必綁輪次),有發現就過不了處置閘。

做法(一條規則;判法一支,`loop next` 與寫側共用):
- **新增一支判法** `_loop_round_format(rows)` 回 `empty / all / none / mixed`,數法是 `"round" in r`(讀 `_loop_records`,規格閘留痕已在讀帳時濾掉),**結局帳列不算**(讀帳入口用 `_is_outcome_row` 濾掉,見下一條與 Systems/loop-convergence-recording;代碼審 r1 通才 1 之後的編排者裁定:結局帳結構上不能帶輪次,照算會讓帶輪次的迴圈寫完結局帳就卡死)。寫側、`loop next`、`loop status --panel`、處置閘與跑滿上限提示的範圍都呼叫它、讀側一律先濾結局帳(代碼審 r1 架構 1、通才 4:原本讀側各自數)。
- **規則**:分級 standard 或 high 的迴圈(不分代碼審、設計審)每筆都帶 `--round`。所有分級都適用:迴圈已經有的格式定死,寫進去會變成 `mixed` 就擋。**light 不規定第一筆的格式**(帶不帶都收):light 代碼審有發現時載體一定要帶輪次(處置帳必綁輪次),真帳 14 個 light 代碼審有 8 個每筆帶輪次、都記了處置帳;light 設計審 12 個裡 9 個不帶。light 到底該不該統一,牽到 `loop next` 與 `loop status --light` 對 light 帶輪次 rc2 的既有守衛,另開待決問題 Q1,本案不裁。
- **`loop next`**:`seq` 只留給「帳上已經有記錄、而且全部不帶輪次」的舊循序迴圈(相容,行為不變);**全新編號**(帳上零筆)的 code standard 不再走 `seq`,`record_cmd`、`disposal_cmd` 都帶 `--round r1`。人數照舊取應派名冊(一位審查員,架構對齊不佔人數),上限照舊 3 輪。連帶的輸出變化照實接受:第一輪 `canary_type` 從單一值變成 `{slot1: …}`(非 seq 的既有形狀),第一輪會多印既有的 `cluster_hint`。名冊表 `("code","standard")` 的 `mode` 標籤改成 `single`(一位審查員、帶輪次);程式沒有讀者,但既有測試 `t_tier_roster_table` 斷言它是 `sequential`,那條斷言隨 d1 改(測試期望跟新決策走,不是放寬規則)。
- **`loop next` 文字輸出**:在既有的 `for k in (...)` 白名單加 `disposal_cmd`(只在 JSON 已有它時印),讓人照文字走也看得到處置帳範本帶 `--round`;不另開輸出路徑。
- **`canary record` 寫側**——**獨立成段**,條件 `loop and outcome is None`(不放進既有「載體最後記」那段:那段包在 `if loop and round_id and outcome is None:` 裡,這筆沒帶 `--round` 時根本不會進去,而沒帶 `--round` 正是要擋的主情境)。為了只讀一次帳,把 `_loop_records_checked(env, loop)` 這一行提到兩段之前、條件放寬成 `loop and outcome is None`,兩段共用結果;「載體最後記」那段自己的進入條件與判斷照舊。
  - 這筆是結局帳(`--outcome`)就跳過整段(結局帳結構上不能帶 `--round`)。
  - **帳壞**(`_loop_records_checked` 回了原因:讀不到、不是 UTF-8、這個編號有一列輪次不是字串):擋(rc2),訊息照三段式講帳壞在哪、為什麼不能照零筆處理(會把第二、三席誤當第一筆)、修好那一行再記。跟「載體最後記」對 `--finding-source` 帳壞時擋同一方向。
  - 既有列加上這一筆,`_loop_round_format` 會變成 `mixed` → rc2,訊息三段式:
    - 發生什麼:「這個審查編號既有 N 筆裡 A 筆帶輪次、B 筆不帶,這筆[帶/不帶] --round」(N、A、B 都不算結局帳——讀帳入口已濾掉,代碼審 r1 通才 1 之後)。
    - 為什麼在意:寫進去之後 `loop next` 和處置閘整個判不了、帳撤不掉。
    - 下一步(獨立一行):既有都帶輪次 → 「補上 --round 再記」;既有都不帶、這筆是處置帳(帶 `--findings-set`)→ 「這個編號記不了這筆(處置帳一定要輪次),換新編號重記:lumos loop next <新編號> …」;既有已經混用 → 同一句換新編號;既有都不帶、這筆是一般席 → 「拿掉 --round 再記」。
  - 帳上零筆(這是第一筆)、或既有列沒有任何定錨時,**有效分級=帳上定錨,沒有就取這筆的 `--tier`**:有效分級是 standard/high 而這筆沒帶 `--round` → rc2(三段式;下一步那一行是補了 `--round r1` 的示意指令,工具拿不到原始指令列,只示意關鍵旗標)。第一筆沒帶 `--tier`、編號是代碼審(`str(loop).startswith("code-")`,跟 `--finding-source` 同一個判法)而沒帶 `--round` → 同樣 rc2,訊息說「代碼審第一筆要帶 --tier 與 --round;照 loop next 印的範本記」。設計審沒帶 `--tier` 的第一筆照舊放行(舊制 legacy 形狀,不溯及)。
  - 擋下照既有做法用 `_gate_event_or_warn(..., "canary", "blocked", "round-format ...", hard=True)` 留擋下事件,RETIRE-IF 數的就是它。
- **手冊**:見第 10 節的同步清單。
- **回應既有決策**:[[Projects/循序codeloop-tier錨定_計劃]] 當初放寬的是「code∧standard∧無輪次」不被 `loop next` 誤擋,範圍刀寫明收斂閘一字不動;那時處置閘還沒取代 panel 閘。現在處置帳必綁輪次,無輪次的 standard 代碼審一有發現就判不過,循序形狀對新迴圈只剩坑。本案不收回舊迴圈的放寬(帳上全無輪次的舊迴圈 `loop next` 照舊走循序樣式),只讓新迴圈不再進這個形狀。
- **跟 [[Issues/代碼審next把新處置帳誤判舊panel]] 的關係**:那張是「帶輪次的新處置帳被 `loop next` 送進退役 panel 閘」;現行 `old_panel` 已用 `_panel_retired_for` 分流。本案讓新 standard 代碼審一律帶輪次,所以要多一條條款確認這條路走得通([S3]);過了就可以順手把那張 Issue 關掉(在實作提交寫回)。

### 2. 集合旗標認 `none`(F16)

現況:`cmd_canary` 的內部函式 `_ids` 只把空字串當空集合;`--accepted-set none` 被當成一個叫 `none` 的 id,接著被「放行清單裡有 id 不在發現清單」擋。真帳已有 5 筆 `folded_set` 裡真的寫進了 `none` 這個 id(舊帳,不動)。

做法(決策 d3;代碼審 r2 編排者裁定 G2 之後的版本):**`none` 是保留字**。整串只寫 `none`(不分大小寫)是「一條都沒有」——`--folded-set`、`--accepted-set`、`--regression-set` 都當空集合;任何清單出現叫 `none` 的發現 id(`--findings-set` 裡有 none、其他清單把 none 跟別的 id 並列、`--refuted-set` 的 id 叫 none)一律 rc2,講 none 是保留字、換個 id。原本(第二版)為了守 [[Projects/載體零引句在記帳前拒收_計劃]]「none 可以是真實 ID」,讓發現清單有 none 時其他清單的 none 照字面,結果 `--regression-set none` 第一輪死路、之後把 id none 記成回歸(代碼審 r2 邊界 1、正確性 3)。`--refuted-set` 的格式是 `id=理由`,整串 none 照舊是空集合。判法一支:`_none_reserved_lines`。

### 3. `--regression-set` 只收代碼審(F20)

現況:`--regression-set` 對任何迴圈都收;實際讀這個欄位的只有 `loop fix-check`(代碼審修正關卡,看第 2 輪起的載體有沒有記這欄、沒有就提醒),`loop next` 只是在代碼審範本裡寫出這個旗標、不讀帳上的值;設計審手冊沒要求,`templates.md` §3.1 標明「僅供 code-loop」。真帳設計審也記過 16 筆(9 筆有 id),沒有任何地方讀。

做法:跟 `--finding-source` 用同一個判法——編號不是 `code-` 開頭(`str(loop or "").startswith("code-")` 為假)時帶 `--regression-set` → rc2:「--regression-set 只給代碼審(code- 開頭的迴圈)用——設計審沒有讀它的地方,記了也不會被用到;拿掉再記」。`codeX` 這類看不出種類的編號跟 `--finding-source` 一樣不收(同一族「只給代碼審」的旗標只用一種判法)。舊帳不溯及。

### 4. 表態證據型別錯講清楚(F21)

現況:`_dispositions_validate` 與 `_dispositions_tension_shape` 用 `str(ent.get("evidence") or "")`,清單被轉成 `"['a.py:3', …]"` 再拿去切 `path:line`,訊息是「evidence '[…]' 切不開」,看不出是型別錯;`existing` 每一項同樣先 `str()`。

做法:一個共用小判斷——欄位**有這個鍵、值不是 None、又不是字串**(含 `[]`、`{}`、`0` 這類現在被 `or ""` 當成「沒附」的值)就是型別錯,印「evidence 要是一個字串(path:line 或 test:<名>),你給的是清單;多個證據挑最直接的一個,其餘寫進 reason」(依實際型別講「清單 / 物件 / 數字」),不再往下切;`existing` 每一項同理。用在三處:寫側 `_dispositions_validate`(satisfied 的 evidence)、`_dispositions_tension_shape`(tension 的 evidence 與 existing,寫側讀側共用)、讀側 `code-loop check` 對 satisfied 那條 `_ev(str(...))` 之前(治理帳重建的紀錄不信形狀;tension 讀側本來就先過 `_dispositions_tension_shape`)。

### 5. 留痕入帳後提醒不能改(F22)

現況:`canary record` 對 `--report`/`--snapshot`/`--intake` 都算 sha256 入帳,但記完什麼都不說;記帳後再改 intake,要到問閘才看到指紋不符。

做法:記帳成功、真的寫進帳之後,只要這筆帶了上述任一份留痕,往 stderr 印一行:「提醒:<列出這筆入帳的留痕檔名(過既有的 `_esc_clean`)> 的指紋已經寫進帳,之後改一個字處置閘就判不過;要更正請另開一份檔(例如 rN-intake-更正.md)寫在卷證裡,不要改這幾份」。不擋、不改帳的內容、不改回傳碼。訊息只印一次(一筆一行),不分迴圈種類。

### 6. pitfalls 每個分級印要派誰(F25)

現況:`_pitfall_tier` 判 standard 時人可讀輸出只印「tier: standard(有程式檔改動、沒命中風險型樣)」(審查帳有全靠人驗的風險低留痕時,括號裡再接一段「跑 lumos spec-gate --push-check 看是不是 light」),沒有任何一句講 standard 仍要審;示範時後端代理讀成「standard 不用審」。

做法:人可讀輸出在 `tier:` 那行下面多印一行「這級仍要代碼審:<該派的席>」,席位清單**從應派名冊 `_TIER_ROSTER[("code", tier)]` 讀**(必派席列名;條件席與 `required-gated` 席照 `loop next` 既有的 `_REQUIREMENT_LABEL` 標示,名冊沒有的字樣這裡不新造),不在 pitfalls 另寫一份;後面接 `lumos loop next code-<編號> --tier <tier> --orchestrator claude` 一行。light 也印(只派一席架構對齊)。`--json` 不動(pre-push 讀 JSON,不加欄位免得動到熱路徑的解析)。

### 7. 拆包審的範圍與材料(F28)

現況:`--scope-lines` 只看自填數字,超過 `_CANARY_SCOPE_SOFT_CAP_LINES`(1800)就在帳上標 `scope_oversize`(弱證據),標了撤不掉;`record_cmd` 只寫 `--scope-lines <這輪審了幾行>`、`--snapshot <凍結快照.md>`,沒講拆包時填該席那一包。派工單每席的材料記帳不讀。

做法(**只改文字、不讀派工單、不擋**):
- `record_cmd` 的佔位字改成 `--snapshot <這一席審的那份凍結材料(拆包審時填該席那一包)>`、`--scope-lines <這一席那份的行數>`;`disposal_cmd` 同步。
- 既有的超標提醒(在 `cmd_canary` 較早處印、寫帳照常)多一句「拆包審時 --scope-lines 與 --snapshot 要填這一席那一包,不是整份」。
- 手冊 `skills/lumos-code-loop/SKILL.md` 步驟 6 的記帳說明補同一句。
- 資安席的包本來就要含全部改到的檔(見下一節),整份大於 1800 行時它照舊會被標,這是真話,不另開例外。
- **為什麼不從派工單推、也不擋**(設計審 r1 六席裡四席指出):派工單在真帳上至少三種形狀(頂層 `materials` 單席、`seats` 清單每席自帶 `materials`、`seats` 只有席名而材料在頂層;另有每席一檔的 `rN-dispatch-<席>.json` 與 `seats` 是物件的少數例外);`seats[].auditor` 常是模型名(約三分之一的派工單有重複值),席名在 `seat`;材料路徑有 repo 相對、絕對暫存路徑(多半已被暫存清理刪掉)與裸檔名三種。要可靠比對,得先擴充既有的 `_roster_dispatch_entries` 讓它回每席材料,再定席位比對鍵與路徑正規化——這是一個獨立的設計題,不是小修。擋錯又沒有出口,代價比標一筆弱證據大,所以這次只把話講清楚。
- REVISIT:2026-12-15 數這段期間新增的 `scope_oversize` 帳列裡,同輪派工單是拆包(各席材料不同)的有幾筆;還有就另開計劃擴 `_roster_dispatch_entries` 回每席材料,在記帳當下核對

### 8. 高風險代碼審的資安包與順序(F31)

現況:`loop next` 對 high 代碼審只在應派席印一行「資安…必派(問閘會擋)」;`_disposal_security_step` 要求資安席看過的檔涵蓋判定輪凍結 patch 的全部檔,而且每支檔的改動指紋(`_patch_file_changes` 算的 hunk 內容)要跟資安席那份凍結 patch 裡的相同——之後又改過的檔算沒看過,訊息分「內容跟資安席看的不一樣」與「資安席沒看過」兩種;到問閘才擋。PR #95 加了「載體最後記」:同輪已有帶 `--finding-source` 的載體後,再記同輪任何一席都被擋,要補只能記下一輪——示範時就是因此在上限之後多記一輪。

做法:
- `loop next` 新增一個提示清單 `hints`(JSON 鍵 `hints`,文字輸出每項一行 `  提醒: …`),由一支小函式依「迴圈種類、分級、第幾輪」組出來,第 8、9 節的提示都放這裡,不各自散印;只在階段 plant-canary 印(要派工的時候),converged、cap-reached、escalate、gate-pending 不印;文字輸出走既有 `for k in (...)` 白名單那段之後逐項印,不另開輸出路徑。分級用有效分級(帳上定錨,沒有就取這次 `--tier`)。高風險代碼審印兩條:「資安包要含這輪凍結 patch 改到的全部檔(含筆記與文件),不要拆掉;最後一次修補之後要對最新的凍結 patch 再派一次資安」、「記帳順序:資安與其他席先記,載體最後記;載體帶了 `--finding-source`(major 輪逐條放行 minor)的話,記完以後同輪任何一席都不能再補,補資安只能記到下一輪,已到上限要先 `lumos loop cap-decision`」。
- PR #95 的「載體最後記」擋下訊息(`cmd_canary` 裡那段)不動判斷,只在被擋的這筆席名對得上資安席(用既有 `_auditor_matches_slot`)時多印一句「要補的是資安席:記到下一輪(輪次自己取一個新的,例如 r<N+1>;輪次是自由字串,取不出數字就只印「下一輪」),那一輪只派資安、對最新凍結 patch;已到上限先記 cap-decision」。判斷式與核對流程一字不改,不跟 `_minor_release_check`、`_disposal_minor_release_step` 衝突。

### 9. 設計審首輪先排乾再凍結(F11)

現況:手冊步驟 1–3 寫「先機械排乾(首輪加前掃)→ spec-freeze → 派工」,`loop next` 首輪不提順序;`spec-freeze --out` 遇到已存在而內容不同的快照會拒絕覆寫,凍早了要刪舊快照才能重凍。

做法:
- 第 8 節的 `hints` 對設計審(`_roster_kind` 是 design)、階段 plant-canary 印一條:「順序:先排乾(refcheck、prose-lint、pitfalls --check)再 spec-freeze 凍這輪快照、才派工;凍了以後才修真檔,席位會審到舊版」;第一輪多一句「首輪還要先跑前掃(手冊步驟 2 的四項),前掃排乾之後才凍」。

## 實務隱患

- 守衛面:**會碰**。`canary record` 新增三種擋(輪次格式含帳壞、`none` 混寫、非 code- 編號帶 `--regression-set`),`loop next` 改範本與輸出;拆包只改文字不擋。帳本只進不出,寫側擋錯的代價是「這筆記不上、照訊息改了再記」,比現在「記上了、整個迴圈作廢換編號」輕;誤擋面最可能在結局帳、舊循序迴圈與 light,三者都有條款釘住([S2]、[S11]、[S14])。light 代碼審第一筆照 `loop next` 範本不帶輪次、之後載體要帶輪次,會撞到混用擋——這是既有的坑被提早到寫帳前講出來(帳不會中毒),怎麼統一另開待決問題 Q1。這也回應否決清單裡「`loop next` 屬守衛面,一行提示就要整套設計審」([[Projects/否決提案收齊查重_計劃]]):本案接受走設計審,不主張小改動跳過。
- 相容:舊帳一律不溯及;全無輪次的舊循序迴圈照舊可以繼續記(不帶輪次);帳上已經混用的迴圈本來就判不了,這次不修(換編號是唯一路)。
- 範圍外影響:新 standard 代碼審一律帶輪次後,會落進「多席格式」的那幾個功能——跑滿上限提示與跑滿回顧([[Projects/審查跑滿上限提示_計劃]]、[[Projects/審查跑滿回顧_計劃]] 都排除「循序單審」)。真帳 144/147 個 standard 代碼審早就帶輪次,等於已經在範圍內,實際行為不變;實作時用 `-k cap_hint`、`-k retro` 確認。
- 效能:讀帳那一行提到兩段之前共用,寫側不多讀;不讀派工單;不碰 pre-push 熱路徑(`pitfalls --json` 不變)。設計審 r1 資源席實測整本帳(4787 列、4.9 MB)掃一次 0.056 秒、峰值約 52 MB。

- 併發:單人、AI 依序操作(專案威脅模型),不處理兩個會談同時記同一個編號。
