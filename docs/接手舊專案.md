# 接手一個沒有筆記的舊專案

[← 回 README](../README.md)

你接手一個**已經在跑、但一篇筆記都沒有**的專案——公司的舊系統，或是自己 vibe 了一個月的東西。怎麼開始？

**Lumos 的答案不是「把整個 repo 攤平自動生文件」。** 那種產出沒人查核過，錯得很自信，而且錯得很像真的。

正確的做法是照著一套七步的還原流程走。下面是那七步濃縮成的五個要點；逐步操作見本文末的指路。

---

## 1. 惰性生長：不要一次補完

**進場先查——有就照著用；殘缺就補；沒有才產一篇。**

筆記沿著「實際被動過的地方」慢慢長。你不會需要一個涵蓋整個系統的完整文件，你需要的是「這次要動的那幾塊，脈絡是清楚的」。

---

## 2. 先看懂再動手

順序是固定的：

1. **從看得到的行為往回追**——畫面上的文字、log、錯誤碼，反查到程式碼。
2. **追資料流，圈出「誰還共用它」**——那些就是承重牆。
3. **從 git 歷史還原「為什麼」**——`git blame` 追到被壓平的 commit，就去讀那個 PR 的討論串。

---

## 3. 每句話都要標出處

- 有程式碼或 git 證據的 → 標證據。
- 是你推論的 → 老實標「推測」。
- 查不到的 → 標「佚失」。

**有機械檢查在把關，嚴禁看著現狀編故事。** 一篇「聽起來很合理但沒人驗過」的筆記，比沒有筆記還危險——下一個人會信它。

---

## 4. 出口必過交叉查核

還原完不算完成，要過這一關：

- 一個 AI **只讀筆記**，列出裡面所有「可以驗證的主張」。
- 另一個 AI **只讀程式碼**，逐條判真假。
- 兩個互不知情，對完才算還原完成。

---

## 5. 典型用法是「加新功能之前」

不要為了還原而還原。最划算的時機是**要加新功能、但會碰到舊東西的時候**：

先還原會碰到的那幾個關聯面，新功能踩在這些筆記上開發。還原產出的「共用面清單」和「合約候選」，直接變成新功能的護欄——不破壞架構、不重造輪子。
