# 心智模型與機制

[← 回 README](../README.md)

這份寫給「已經決定要用、想知道它到底怎麼運作」的人。README 只講了為什麼；這裡講內部長什麼樣、哪一道檢查擋什麼、哪些事工具證得了、哪些只有人能答。

---

## 1. 四句話講完整套想法

1. **筆記是「意圖」的真相來源。** 「當初為什麼、規則是什麼」以筆記為準。
   但「現在實際跑成什麼樣」的權威是測試和正式環境——兩邊打架時**不自動信筆記**，而是查清哪邊錯了、記一筆事故。
2. **先讀再動。** 要動既有系統，第一個動作是查筆記，不是 grep。筆記先給你邊界和地雷，程式碼拿來印證細節。
3. **退場寫回。** 做完當場把決策和驗證結果寫回去——趁你還是目擊者的時候寫，別留給日後的人當考古學家。
4. **提交時強制。** 上面三條靠自覺一定會爛。所以提交前的檢查硬擋「改程式碼沒動筆記」，健檢定期驗整疊筆記的一致性。

## 2. 筆記分五種

| 型別 | 記什麼 |
|---|---|
| `system` | 一個模組：流程怎麼跑、依賴誰、有什麼不能破的規則 |
| `verification` | 一次測試或審計的紀錄（在什麼前提下驗的、何時該重驗） |
| `issue` | 一個發現或事故 |
| `project` | 一個計劃或設計 |
| `moc` | 導覽頁（Map of Content，整疊筆記的目錄） |

每篇開頭有幾行帶前綴的摘要：`FLOW:`（流程）`KEY:`（關鍵事實）`DEP:`（依賴誰）`TEST:`（測試狀態）`DECISION:`（決策）。

**設計目的是只讀開頭就能掌握全貌，不用讀完整篇。** 大節點先 `lumos context <節點> --brief`（合約行照樣放在頭部），要全文再 `lumos show`。

## 3. 三條「掛證據」的鏈

一般 wiki 的問題：寫的人說了算，錯了沒人知道。

Lumos 給三種「載重的宣稱」掛上鏈——**不掛證據就過不了關**。

### 合約鏈：這是不是真規則？

```
KEY:★INVARIANT★ <改了會壞的業務規則> [test:測試方法名] [audit:模型/日期]
```

- `★INVARIANT★`**必須**綁一支真的存在的測試（`[test:]`）。空口宣稱，健檢會擋。
- 還要過一次**獨立審計**（`[audit:]`）：派一個不知道前因後果的乾淨 AI 判「這真的是合約嗎？測試是不是在自己騙自己？」——寫的人不能自己當裁判。
- **拿不準是不是合約？就不要標。** 嚴禁看著程式碼反推「這應該是規則吧」。
- 另有 `★DEBT★` 標「已知只是剛好長這樣，可以改」。

### 可逆性鏈：搞砸了收得回來嗎？

```
KEY:★IRREVERSIBLE★ <收不回:例如正式環境的資料庫遷移> [rollback:decisions]
KEY:★CHECKPOINT★   <改了難救:例如部署到測試機>
```

標了「不可逆」就**必須**寫下回退步驟——真的指令、真的補償流程，健檢會查。沒標＝可逆，放手改。

### 誠實天花板（最重要的一段）

工具能證明的是**形式**：測試存在、回退有寫、獨立審過、每條意見有交代。

「這條規則今天還符不符合業務」「那個回退步驟真的跑得動嗎」——**只有人能答**。

別把「有掛證據」當成「絕對安全」。

## 4. 強制力從軟到硬

| 層 | 做什麼 | 擋不擋 |
|---|---|---|
| 改檔前的推播 | 改程式碼前告訴你會波及哪些筆記、踩過什麼雷 | 只提醒 |
| 收工檢查 | 這一輪改了程式碼、筆記沒動就擋一次，要補或說明 | 擋一次（同對話只一次；`LUMOS_STOP_BLOCK_OFF=1` 關） |
| `lumos lint` | 單篇筆記快檢 | 提前預警 |
| `lumos doctor` | 全部筆記健檢（孤兒、斷連、裸合約、缺回退） | `--ci` 模式會擋 |
| 代碼審留痕 | 高風險改動沒過審 | push 時硬擋 |
| push 前的閘 | 健檢＋完整性驗證＋代碼審留痕，三合一 | 硬擋 |

這套大量用 **fail-open**（環境不全就先放行，CI 當後盾）。好處是治理工具一壞不會全公司卡住；副作用是**你看不出現在到底有幾層真的在守**。

`lumos enforcement` 把各層現況查一遍、印一行「幾層生效」。本機測不到的遠端設定（例如 GitHub 的必過檢查）誠實列 unknown，不假裝有。

## 5. 寫入請走指令，別手改開頭欄位

筆記開頭的結構化欄位（狀態、連結、決策）一律用指令寫：

```bash
lumos set <節點> <欄位> <值>
lumos append <節點> related "[[X]]"
lumos decision-add <節點> "<內容>" --decided 日期
```

指令會自動排版＋寫完自驗。**手改最常見的坑：多個連結擠在同一行，會長出「幽靈節點」。**

## 7. 設計原則

- **零依賴**：純 python 標準庫，CI 直接跑，不帶任何套件。
- **別治理過頭**：只給載重的宣稱掛鏈；軟提醒維持軟；不疊沒有對等價值的儀式。
- **誠實的天花板**：工具證形式，不證業務正確；講不出的就明說講不出。
- **寫的人不能自己當裁判**：沒有標準答案的判斷，交給不知情的獨立 AI。
