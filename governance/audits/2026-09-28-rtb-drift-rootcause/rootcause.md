2. **漂移主要有三種產生方式（20 處全部歸得進去）：** ① 同一篇只往後追加、不回頭改（9 處）；② 不歸這段程式管的筆記（計劃、Issue）沒人通知（5 處）；③ 用工具改狀態時只改欄位、不改散文，也不連動相關筆記（6 處）。另外有四個放大因素：審查只看「程式有沒有違反筆記」、大量擠壓成一個提交、確認日期順手更新、清理只修抽到的句子。
3. **現有工具抓到的，幾乎都是最不重要的那幾類。** doctor 直接列出的約 24 處（推翻決策 18、索引 5、計劃條款 1），其中 18 處早在 9/25 裁定過「仍成立」。20 處真漂移裡，doctor 和 lint 都抓到 0 處。提交時的刪除傳播提醒（delguard）理論上能點名其中約 6 處，實際在 Phase 14 那個提交印了 175 筆命中，但它只提醒不擋，沒人處理。note-audit 只審新寫的行，對存量沒用，而且在 rtb 還沒接線。
4. **效果最大的三條防線：**
   - 推送前把「這次改到的符號，全圖譜還有哪些舊句子在講它」一句一句列出來，逐句要求改掉或表態，對應機制①。
   - 「沒有／還沒／等 X 時」這類句子與回頭條件改寫成機械可判定的探針，由 doctor 每次推送時評估，對應機制②。
   - 轉正、結案、改完成這類狀態指令，連帶處理散文和連入的 Issue／驗證紀錄，並在 doctor 加狀態一致檢查，對應機制③。
5. **機制①②的根本漏洞在提交前那道檢查。** 「改 code 沒動圖譜」只要看到任何一篇筆記加進提交就放行；「寫回要落在家」只要求至少一支改動檔的家有被改到。兩道都不管改的是哪一句。20 處真漂移裡，有 14 處失效的那個提交都「合法地」改過筆記。

**機制①　同篇追加式寫回（9 處：A1、A2、A3、C1–C3、D1–D3）**
- 失效的提交有改到那篇家筆記，而且那篇正是被改程式的家；提交前兩道檢查都合法放行。
- 但改法是「在尾端加一節新的」或「只改自己想到的那一段」，同一篇裡講同一件事的舊句沒被找出來。
- 代表例：
  - c177791：程式把三個變數改成四個，同篇只在底部加一行，說明「權杖跟三個模型變數放同一組」。這一行本身就把舊數字又抄了一次。
  - d98b4ca：過期句就在代碼審 diff 的上下文裡，還是沒人看到。
- b2fc512 一個提交就佔了其中 6 處：大擠壓提交裡，作者用「逐節掛撤除橫幅」處理舊內容，憑節標題判斷，漏掉四節。

**機制②　不歸這段程式管的筆記沒人通知（5 處：A7、B1、B2、B4、B3 的回頭條件部分）**
- 句子寫在計劃或 Issue（about_code 空的），內容是「目前沒有 X」或「等 X 時回頭做 Y」。
- 做出 X 的那個提交只被要求改 X 的家。牽連分析會把這些計劃列出來，但混在 90 篇裡，沒有句子定位。
- 事件用散文寫，機械上判不出「X 出現了」。同一條回頭條件抄了兩三份（Phase 4 計劃、分析行程、Phase 11B 計劃各一份），只有家那一份被改。

**機制③　工具改狀態只改欄位（6 處：A4–A6、E1、E2、E3）**
- `guard settle` 只換合約行和 status；`lumos set … status done` 只改一個欄位。
- 驗證紀錄的前提（「未提交」）在提交那一刻失效，但提交流程不看 valid_under。
- 這一類完全不經過「改 code 沒動圖譜」那道，因為本來就是純文件提交。

### 2.4 放大因素（讓上面三種漂移活下來的原因）

1. **審查只看一個方向。**
   - 480 個代碼審席位裡，只有 6 席的鏡頭提到筆記。
   - Phase 14 增量 3（撤掉 AI 的那個增量）三輪 snapshot 都沒有筆記 diff。
   - 鏡頭 4 逐篇看了 Systems，但問題設計成「這次改動有沒有違反這篇的合約」，而不是「這篇有沒有句子被這次改動推翻」。9/27 Issue 也記錄了派工只貼合約行。
2. **大擠壓提交加上刪除傳播提醒的上限。**
   - delguard 只取前 40 個被刪 token，時限 15 秒，只提醒。
   - 治理帳記錄：859 次執行裡 94 次超時降級、103 次有命中，全部只是印出來。
   - b2fc512 那次印了 10 篇、175 筆命中，沒人處理。
3. **[confirmed:] 戳隨手更新。** A2 那一行在 b2fc512 被局部改寫時，確認日期跟著改成 9/26，數字沒重驗。照 CLAUDE.md，帶齊欄位、半年內確認過的 RULE 可以挑戰程式，所以這種戳是有效力的。
4. **清理只修被抽到的句子。** 9/27 的 Issue 自己列了「還沒處理的同款句」：Phase 3、4、5、12 計劃與 Phase 4、5 驗收紀錄。那份清單的「沒有啟動程式」類，大多是這批已知剩下的。

## 4. 防止方法

### 4.1 前三名（依能蓋住的真漂移數排）

**第 1 名：改到的符號，列出全圖譜的舊句子，逐句表態（蓋機制①，9/20；部分蓋②）**
- 做法：
  - 把 delguard 從「只抓被刪的 token」擴成「被改的東西」：被刪／改名的函式、類別、測試名、命令列旗標；常數值或 tuple 長度變了；新增檔案。
  - 拿掉 40 個 token 的上限，改成依重要性排序（def/class/test/旗標/常數名優先）。
  - 在全圖譜找「這次提交沒改到、卻提到它們」的句子，連同所在節名一起印出。
  - 摘要行（RULE/WHY/PITFALL）與沒掛撤除橫幅的節裡的命中，要嘛這次改掉，要嘛用 `lumos note-ack <節點> <句指紋> --reason` 表態，表態會留帳。
- 擋在哪一步：提交時提醒；推送前對「改動檔的家」與摘要行的命中要表態才放行；CI 重算。
- 機械判定到什麼程度：列句子 100% 機械；該不該改要人或 LLM 判。
- 預估誤報：高。b2fc512 那次會列上百句，所以要分層：家與摘要行必須表態，其他只列。以 c177791 為例會列出一鍵展示裡提到 `MODEL_VARIABLES` 的兩三句；A2 那行 RULE 本身沒寫符號名，要靠「常數長度變了就一併找數量詞＋概念詞」的啟發式才抓得到。
- 需不需要人裁：需要，逐句表態。

**第 2 名：否定句與事件型回頭條件改成機械探針（蓋機制②，5/20；也蓋 A3、E3）**
- 做法：
  - 回頭條件的事件改寫成可判定的探針，例如 `REVISIT[when:file src/rtb/analyzer/runner.py]`、`[when:symbol rtb.executor.guardrails]`、`[when:test test_x]`、`[when:status Projects/RTB_Phase12…=done]`、`[when:commit-landed]`。
  - 「目前沒有／還沒／尚未 X」句同樣要帶 `[until:…]` 探針，或標上寫下日期。
  - doctor 每次推送都評估：探針成立的句子，改由推送前點名，並在治理帳記觸發。
  - note-shape 擋新寫、有事件字眼卻沒探針的 REVISIT 與否定句。
- 擋在哪一步：寫的時候（提交時擋格式）；推送前與 CI 評估觸發；開場 handoff 也可以唸。
- 機械判定到什麼程度：探針本身 100% 機械；探針寫得對不對要人。
- 預估誤報：低。探針是明寫的，不猜語意。存量約 45 條要回補。
- 需不需要人裁：寫探針時要一次；觸發後處置要人。

**第 3 名：狀態指令連帶散文與連入節點，加狀態一致檢查（蓋機制③，6/20）**
- 做法：
  - `guard settle` 轉正時，同步把被觀察筆記的「TEST:還沒有…」「為什麼還不做」改成歷史或刪掉；做不到就要求 `--note`。
  - `lumos set <計劃> status done` 列出連入的 open Issue、pending 驗證紀錄、還沒觸發的回頭條件，要求處理或表態。
  - doctor 新增一致檢查：
    - open Issue 被一份 done 計劃當「需求原文」連入；
    - Issue 的 REVISIT 寫「某計劃開工／收尾時結案」，而那份計劃已 done；
    - 驗證紀錄 pending，它的計劃卻已 done；
    - valid_under 含「未提交／工作樹」，而該檔已在主線上。
- 擋在哪一步：指令當下；doctor 推送前提醒，其中「計劃 done 但 pending 驗證」可以擋。
- 機械判定到什麼程度：幾乎全機械。
- 預估誤報：低，只有少數 Issue 刻意在計劃完成後還開著，給一個 `keep_open_reason` 欄位就好。
- 需不需要人裁：只有例外需要。

### 4.3 工具能做的，和只能靠寫法規範的

**工具能做（可機械判定或可強制點名）：**
- 被改或被刪的符號、測試、旗標、常數在全圖譜的舊句列表（第 1 名）。
- 回頭條件與否定句的探針評估（第 2 名）。
- 狀態指令的連動與狀態一致檢查（第 3 名）。
- 懸空的 `[test:]`、確認日期的更新路徑、完成計劃的快照橫幅、重複句偵測、索引補列、E3 降噪。
- 代碼審的「筆記對程式」席：派工能機械化，判定還是 LLM。

**只能靠寫法規範（工具最多提醒）：**
- 句子寫在哪裡：撤除或改動時，改原句或在原句旁標，不要只在文末開新節。工具能把舊句推到眼前，但改成什麼要人寫。
- 不在 WHY/RULE/PITFALL 或正文寫程式推得出的現況。note-shape 只管 FACT/FLOW/DEP 前綴，所以實際的現況句都藏在其他前綴與正文裡。note-audit 能對新行提醒，但判「推得出」本身靠 LLM。
- 同一件事只寫一處、其他用連結。工具能偵測字面重複，偵測不到換句話說的重複。
- 計劃的「現況」段用過去式、標題帶日期。
- 「已知缺口」段每個條目附探針。沒有探針的缺口，工具不知道什麼時候它已經不是缺口。
