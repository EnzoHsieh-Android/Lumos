## Finding 1：CI 無法用既有讀側同時重建兩種獨立留痕

severity: blocker

blocking: 是——若未定義 pass/skip 與 dispositions 兩條事件如何合併，乾淨 checkout 必然可能把已表態判成缺失。

spec 段落：三、表態何時寫、閘放哪裡；[S6] CI 路徑。

引句:「本機讀 marker、CI 從治理帳事件重建」

問題：`dispositions` 與稍後寫入的 pass/skip 是不同事件；既有讀側只挑最後一筆 pass/skip，不能靠「加欄位」取得更早的 dispositions。spec 必須明定按 branch 分別選有效 pass/skip 與 dispositions，再各自以 head_sha／簿記祖先規則驗證後合併，或明定 pass/skip 寫事件時複製當前 dispositions。

file: `scripts/lumos:20408` `_codeloop_read_from_ledger` 只回傳一個 marker 同形 dict。

file: `scripts/lumos:20423` 讀側明確排除非 passed/skipped 事件；新 `kind=dispositions` 會被跳過。

file: `scripts/lumos:21031` pass/skip 在 dispositions 之後另寫一筆事件，且 spec 明定它們不帶表態旗標。

## Finding 3：`git diff --quiet` 不能證明測試索引來自 at_sha

severity: blocker

blocking: 是——未提交的測試可被當成被推送 commit 的有效證據。

spec 段落：四、錨點怎麼驗；[S5]。

引句:「要求該平台 root 在 `git diff --quiet <at_sha> -- <root>` 下乾淨」

問題：CI 乾淨 checkout 時此檢查通常成立；本機髒工作樹時它能抓 tracked 的 staged/unstaged 差異，卻完全忽略 untracked 檔，而 `_platform_test_index` 直接掃工作樹。攻擊／誤用路徑是新增一個未追蹤測試方法、用它作 `test:` 證據，quiet 仍綠；應從 `at_sha` 暫存樹建立索引，或另以 `git ls-files --others --exclude-standard <root>` 封鎖未追蹤檔。

## Finding 5：added-line regex 無法覆蓋「缺少／移除」型問題

severity: blocker

blocking: 是——大量題目問的是某保護是否缺席，僅看新增行無法可靠決定不適用，會讓硬閘自動放過真正風險。

spec 段落：一、哪些問要答；刻意不做。

引句:「每題都必須有觸發；寫不出觸發的題本身就是設計問題」

問題：例如移除 cancellation、穩定 key、timeout、using 或資源清理可以是純刪除；另有「互不依賴」「生命週期是否匹配」「索引是否支撐」等跨行／跨檔關係，任何 added-line regex 都無法證明不適用。應將負向／關係型題改成較寬的檔案或語法構造觸發，並為 deletion-only、跨檔與缺席條件建立 recall corpus，否則 `auto:true` 是未查證的免答。

file: `scripts/lumos:15047` C# 題包含 CancellationToken 斷鏈與互不依賴等待。

file: `scripts/lumos:15051` 資源題包含例外路徑能否收回連線。

## Finding 6：`stack_questions` 的「向後相容」只保住型別，沒有保住語意

## Finding 7：tag 推送仍留有不表態的出口

severity: major

blocking: 是——總則宣稱「缺一問就不准推」，但現有 pre-push 對非 branch ref 明確只提醒。

spec 段落：三、表態何時寫、閘放哪裡；[S7]。

引句:「閘條件：diff 有適用題就擋，不看 tier」

問題：spec 只說把 standard advisory 改成同一道閘，沒有處置現有 `refs/heads/*` 之外一律 advisory 的分支；直接推 tag 仍能避開本機表態閘。若 tag 刻意不擋，需縮小總則並補 CI 後盾測試；若也要擋，需定義 tag 的留痕座標，不能冒充 branch。

file: `scripts/hooks/pre-push:195` 硬擋限定目的 ref 為 `refs/heads/*`。

file: `scripts/hooks/pre-push:219` 非分支 ref 走另一分支。

## Finding 8：併發段只處理 marker 覆寫，未處理 tracked ledger 的競爭與順序

severity: major

blocking: 否——單機常態可運作，但「最後一筆」必須先定義並補競爭測試。

spec 段落：實務隱患／併發。

引句:「check 取該 sha 最後一筆事件」

問題：`os.replace` 只能保證 marker 不出現半檔，不能讓 marker 與 ledger 成為同一交易；兩個程序可能各自覆寫 marker、追加不同事件，而 CI 最後看到的順序又取決於提交／合併後的檔案順序。需明定 ledger 的最後一筆是檔案順序而非 `ts`、處理同 sha 重複事件及衝突合併，並測試兩程序交錯寫入。

file: `scripts/lumos:20443` 現有 marker 與 ledger 是兩個獨立寫入函式。

file: `scripts/lumos:20419` ledger 依檔案行序掃描，後行覆蓋前行。

file: `scripts/lumos:20474` ledger append 沒有跨程序鎖或與 marker 共用交易。

blocking: 否——可用上限、快取和測試把成本界線補實。

spec 段落：實務隱患；驗收條款。

引句:「適用性讓每次表態成本壓到幾行」

問題：check 可能為多個 `test:` 證據建立多平台測試索引，hook 又要掃整檔 regex；spec 沒有檔案大小、regex 數量、平台數、索引耗時或超時預算，因此「成本壓到幾行」只描述 token，不代表執行成本。應加大型 diff／大檔／多平台 benchmark，以及 regex 編譯失敗與超時的明確 fail-open/blocked 歸屬。
