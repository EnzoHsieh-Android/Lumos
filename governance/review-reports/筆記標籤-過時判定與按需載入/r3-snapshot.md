# 筆記標籤_過時判定與按需載入_計劃

> 白話:兩個宗旨——程式碼推得出來的事實,筆記不寫;其他脈絡(為什麼、規則、踩過的坑、程式答不了的現況)照前綴分類寫。分類要有規律,AI 改程式時才知道要回頭檢查哪幾類、每類查什麼。這份計劃做四件事:①寫的時候怎麼分(一張定義加線索的規格)②誰來檢查分得對不對(沿用既有的「筆記內容審」AI 判定者,讓它多判一層前綴)③改程式時怎麼逐類回頭查(一張每類一行的檢查清單,加上搜尋能只拉出跟這支檔有關的那幾類行)④機械能做的只做結構性的提醒。依賴欄位那種「數字變了就擋」的機械判定,拆到另一份計劃。

依據:

## 現況(盤點與實驗結論)

- **舊的 KEY 行像雜物抽屜**:工具鏈抽 50 條,47% 一行混兩到三類,12% 是程式推得出的事實;會員系統專案抽 250 句,程式推得出 19%、「某天做了什麼」的過程紀錄 16%、混合 19%,Systems 筆記裡 84% 的句子含程式推得出的成分或過程紀錄。
- **關鍵字規則分不準**:先歸納再凍結、去猜沒看過的句子,工具鏈加 rtb 54%(扣掉合約行 47%)、會員系統 36%。準的只有結構性線索:DEP 行只放連結(19/19)、合約記號、審查記號、一行很長又同時有兩類線索。
- **AI 判定者分得比較準**:會員系統 80 句盲判,只給定義 66%、定義加速查表 75%;速查表主要效果是減少誤判(WHY 精準度 8/14 → 8/8)。最難的是混合句(只抓到 3 到 4 句/11 句,常被硬塞成一類)與「程式答不答得了」(要讀程式才判得出)。
- **前綴缺一類、有一類被挪用**:過程紀錄(施工步驟、審查處置、版本沿革)兩個專案各佔約 14% 到 16%,沒有前綴可放;會員系統的 DEP 有 96% 只是「相關連結」清單,不是外部依賴。作者自創的前綴(症狀、根因、修法、變更、資料…)都對得回標準前綴,沒有新類別要開。
- **筆記內容審已經有判定者流程**:它判每行是「程式推得出/脈絡/混合」並要附程式證據;派工詞改一個字就要升版號並重跑 68 句小實驗;它還沒接進推送前掛鉤(那份計劃的 REVISIT 2026-10-12 校準)。
- **文件自己有四處對不上**:reference.md 的 RULE 範例不是欄位寫法;舊精簡表的 FLOW/FACT 定義跟新規範相反;紀律範本自己兩處說 RULE 效力的寫法不一致(一處三欄齊加半年內確認、表格那行可讀成兩欄),程式註解寫兩欄;RETIRE-IF 不在摘要前綴表裡。

## 設計原則

0. **兩個宗旨**:程式碼推得出來的事實,筆記不寫;其他脈絡照前綴分類寫。
1. **分類交給 AI 判定者,機械只做結構性提醒**:實驗證明關鍵字規則分不準;判定者要能讀程式(判「程式推得出」要證據)。
2. **一行一類**:混合句先拆成單類句子再分類(判定者被要求先拆、後判,不靠它自己標「混合」)。
3. **過程紀錄不進筆記**:施工步驟、審查處置、版本沿革屬於 git 歷史、驗證紀錄與審查卷證;要留的理由改寫成 WHY 或 PITFALL。
4. **不另起爐灶、不放寬政策**:判定者沿用筆記內容審;提醒沿用筆記形狀檢查;RULE 效力規則不動;時間到期只提醒。
5. **只看新寫的行**:提醒與判定都只看上線點之後新增的行;舊筆記不回頭補。不分新舊專案。

## 分類規格(寫的時候)

| 前綴 | 寫什麼 | 必帶 | 常見線索(只是提示,不是判準) | 易混淆 |
|---|---|---|---|---|
| WHY | 為什麼這樣決定、否決過什麼;照 MADR 的分法寫得出「考慮過什麼、選了哪個、為什麼、代價」最好 | 出處(日期、決策、提交或對話) | 否決、改成、裁定、避免、所以選、刻意、取代 | 審查沿革與處置紀錄(「r2 折入」「某席指出」)是過程紀錄,不是 WHY;「修法是…」是 PITFALL 的一部分或程式推得出 |
| RULE | 程式看不到的限制:相容性、法規、合約、要人工核可、「人說了算」的紀律 | `[since:]` `[retire:]`;要挑戰程式碼還得 `[confirmed:]` 半年內(既有政策) | 必須同版、要人裁、不可、人工控管 | 規格條款(「X 時應 Y」)與合約行是程式行為,不是 RULE;業務數字在程式或設定檔裡就是程式推得出 |
| PITFALL | 踩過的坑、事故根因 | 出處 + 防回歸(`[test:]` 或重現指令) | 根因、靜默、誤擋、死結、事故、教訓 | 只描述程式現在怎麼做(沒有「踩到」)是程式推得出 |
| FACT/FLOW/DEP | 只寫程式答不了的現況:部署、資料庫實際值、生產觀測、外部系統、人工狀態 | `[來源:]`(既有,note-shape 擋) | 生產實測、資料庫的值、外部廠商行為 | 在 repo 裡 grep 得到的(包括 CI 設定、appsettings)是程式推得出;DEP 只放連結是「相關筆記」,寫進 frontmatter 的 related,不寫 DEP |
| REVISIT、RETIRE-IF | 回頭條件、撤除條件 | 日期或 `[when-*]` 條件(REVISIT 既有) | — | RETIRE-IF 只是前綴,沒有機械判定 |
| KEY | 舊的未分類寫法 | 新寫不用 | — | — |

另外三條:①一行一類,混合的拆開寫 ②過程紀錄不寫進筆記 ③範例裡包欄位的反引號只是排版,實際寫的時候不加。

規格的單一來源寫在 lumos-project-notes skill 的「寫回圖譜」子檔;紀律範本只加一行指路(範本已超過瘦身基線)。

## 分類檢查(AI 判定者)

沿用筆記內容審的判定者流程,不另開:
- **判定者多判一層**:對「脈絡」與「混合」拆出的脈絡部分,多給一個前綴判定(WHY / RULE / PITFALL / FACT / 過程紀錄 / 其他),並判「這行寫的前綴對不對」。派工詞照上面的分類規格(定義加線索加易混淆),判定者先把混合句拆成單類句子再判。
- **照筆記內容審的紀律升版**:派工詞改字就升 `_NOTE_AUDIT_PROMPT_VERSION`,並重跑小實驗——這次用兩次分類實驗的去識別化題庫(工具鏈加 rtb 150 句)加原本的 68 句,前綴判對率低於 70% 就不接。
- **紀錄格式**:每行判定多一欄前綴;舊格式的紀錄照讀(那一欄空著)。
- **出口只提醒**:前綴判錯、該拆、是過程紀錄、是程式推得出——都只列出來讓人改,不擋;筆記內容審自己的「程式推得出」擋不擋,照它自己的計劃與校準結果,本案不動。

## 改程式時的分類檢查清單

改某支檔之前,先把跟它有關、還有效的脈絡行拉出來,逐類對照:

| 前綴 | 改到它相關的程式時查什麼 |
|---|---|
| WHY | 這次改動有沒有推翻它的理由或前提;推翻了就改寫並記新決定,舊的標 `[status:superseded]` 加連結 |
| RULE | 這次改動有沒有違反它;撤除條件成立了沒;`[confirmed:]` 是不是超過半年(要挑戰程式碼就得重新確認) |
| PITFALL | 防回歸的測試還在不在、這次改動有沒有讓它重新可能發生 |
| FACT | 程式驗不了;改動若影響部署、資料或外部行為,回頭確認並更新確認日期 |

取行的入口(skill 的查詢表加一行):
```
lumos search --about <檔> --prefix RULE,PITFALL,WHY
```

## 搜尋行模式

擴 `lumos search`,不開新指令:
- `--prefix`:只要這幾種摘要行前綴(help 寫明跟限資料夾的 `--path` 不同)。
- `--about <檔>`:那支檔的家筆記(用既有「每支檔有家」的對照算,不是所有 about_code 列了它的筆記)的摘要行。
- 給了 `--prefix` 或 `--about` 時 `term` 可以不給(位置參數改成可省略),進入「行模式」:不套每篇 8 行截斷;`--top` 預設照舊是 0(全給,不靜默截斷),給了才限總行數;排序是 RULE、PITFALL、WHY、FACT 類、其他,同類內照篇名。
- 行模式預設隱藏帶 `[status:superseded]` 的行,`--include-retired` 才給;隱藏行數印在 stderr,`--json` 另帶 `hidden_lines`(跟既有的 `hidden_superseded` 並列)。既有的 `--include-superseded`(節點層)意思不變。只看靜態標記,不在搜尋時求值任何條件。
- 輸出沿用既有逐行片段格式,每行帶篇名;`--json` 在行模式多一個片段文字欄位。

## 結構性提醒(筆記形狀檢查,只看上線點之後新增的行,所有專案,只提醒)

子開關 `note_shape.tag_hints`:`warn`(預設)/ `off`,第 0 步就加(W4 跟它一起上線),照 `note_shape.negation` 的先例,壞值照 warn 並講一句;`note_shape.gate` 是 off 時整道檢查不跑,這些提醒也不出(既有從屬關係,明講)。
- **H1 DEP 只放連結**:新寫的 DEP 行除了 `[[連結]]` 沒有別的字 → 提醒「這是相關筆記,寫進 related,不是外部依賴」(實驗 19/19)。
- **H2 一行混兩類**:新寫的摘要行超過 140 字,而且同時有兩類的線索詞(線索表單源在 skill,測試釘住)→ 提醒拆行(實驗 12/15、3/5,只提醒)。
- **H3 過程紀錄**:新寫的摘要行以日期或審查輪次開頭、後面是動作(「折入」「改成」「完成」)而且沒有 WHY、PITFALL 的線索 → 提醒「這是某天做了什麼,改寫成理由或坑,或移到驗證紀錄」。
- **W4 RULE 生命週期**:新寫的 RULE 行,沿用既有 `rule_lifecycle_warnings` 判(不另寫),印缺 since、retire 與 until 過期;既有對 `[status:superseded]` 的訊息改成「留著並加指向取代者的連結」(跟本案一致)。
- **已作廢擴大**:WHY、PITFALL 行也可以帶 `[status:superseded]`;同一行沒有 `[[連結]]` → 提醒。
- 線索詞表、長度門檻放在一處、由測試逐字釘住;提醒全部印出、不設上限(同否定現況句提醒),但同一次提交同一條規則超過 10 行時只印前 10 行加總數。

## 健康檢查補一段

doctor 列出所有 RULE 行裡 `[until:]` 已過期、或 `[confirmed:]` 超過半年的(舊行也列、只提醒):到期是時間函數,只看新行的提醒永遠送不到沒人碰的舊 RULE(設計審 r2 正確性席)。

## 不溯及既往怎麼做

- 判定與提醒只看上線點之後新增的行,沿用筆記形狀檢查與筆記內容審既有的上線點。
- 健康檢查的過期 RULE 清單是例外:它只提醒、不擋,列舊行是為了讓到期的規則有人看到。
- 不新增「新接入專案」的判別,不改 `lumos init`。
