# 派工時自動補清單_計劃

> **★r1 五席審後重寫定位(2026-09-03)。原版是「交付一個機制」,現在是「帶預註冊指標的試點」。★**
> r1 收 37 條、5 個 blocker;要修的多半不是文字,是「該查沒查的四條現行裁定」與「自己造的兩個假事實」。
> 逐條折入見〈r1 折入紀錄〉。

> 白話:每次派審查員之前,規矩要求先算出「這批改動碰到哪些帶硬合約或出過事故的筆記」再貼進派工詞——**實帳沒人做得到**。本案在派子代理的那一刻,由機器把清單直接塞進派工詞。★但這一版不主張它是成品,而是一個試點★:先在明示要求時才注入,跑到帶標記與不帶標記兩組各累積夠多的多席輪(輪數門檻在開跑前算出並寫進〈預註冊〉),用今天早上做好的那把尺量「席位之間的覆蓋率有沒有改善」。**做得出來已經實測過;有沒有用,要量了才知道。**

PRIOR-ART: ① 最小解層級——不新增指令、不新增閘;用既有的 `PreToolUse` hook 位置、既有的 `lumos impact --diff` 輸出、既有的設定合併器 `scripts/merge-claude-settings.py`、既有的截斷規則(`Systems/design-loop` d9)、既有的量測儀器(`governance/eval/seat-coverage/recount.py`)。★本案自己寫的只有一支 hook 腳本與一段注入文字。★ ② 世界解過沒——「在工具呼叫前注入上下文」是官方明列能力;而**為什麼該注入**有外部理論支撐(見下),但★沒查到有人拿它做「審查派工的必查清單注入」並量成效★。③ 裁定=borrow-design,零依賴原生實作(★不引入 `jq` 或任何外部二進位★)。

## 一句話

★AI 判得動、攤不出來——所以把「攤清單」交給機器,「逐條判」留給 AI;然後用既有的尺量這一刀有沒有用。★

## ★這一版是試點,不是交付★

| | r1 版(被審的那版) | 本版 |
|---|---|---|
| 定位 | 交付一個常設機制 | ★帶預註冊指標的試點★ |
| 觸發 | 對每一次派子代理都 fire,靠猜「這次是不是審查派工」 | ★明示 opt-in:派工詞沒有標記就完全不碰★ |
| 成效 | 明寫「不量、不宣稱」 | ★預註冊指標 + 讀法,跑完就有答案★ |
| 安全宣稱 | 宣稱錨點保護(兌現不了) | ★誠實寫明沒有機械防篡改,這是本機實驗★ |

**為什麼 opt-in 不是退讓**:r1 我擔心 opt-in 會退回「靠人記得」,而那正是本案要消滅的東西。★但那是穩態採用的風險,不是試點階段的風險★——跑實驗的人本來就會記得加標記,而且 opt-in 剛好給出實驗需要的**兩組對照**(有清單 / 沒清單)。兩個階段的問題我 r1 時混在一起了。

## 為什麼該做:外部理論 + 自家數字,兩邊指同一件事

**外部**([arXiv 2608.01000](https://arxiv.org/abs/2608.01000),程式領域):同一個模型,**叫它寫出判準 F1 約 0.99;叫它把判準涵蓋的東西一條條攤出來就垮**(產出的測試只接受 19-42% 的正確解)。作者原話是問題不在它不懂、也不在說不出規格,而在★無法把一份規格涵蓋的範圍具體攤出來★。另一篇([arXiv 2608.31016](https://arxiv.org/abs/2608.31016))量到判官抓「漏掉的東西」判別力 0.50-0.63,而且★換措辭、多席投票、提示詞優化全部無效★——便宜的路已被封死。

**自家**([[Verification/2026-09-03_席間覆蓋率離線量測]]):★一個審查席漏掉同儕找到的 64.6% 真缺陷★(85 個確定多席輪、822 個相異缺陷),加席位邊際遞減(2 席 74.2% → 3 席 60.8% → 4 席 58.3%),且獨家發現幾乎不是誤報(全帳 1941 條發現只有 21 條附理由放行=1.1%)。

★兩邊指的是同一個能力斷層★:AI 判得動、攤不出來。所以「機器攤清單、AI 逐條判」不是拍腦袋的分工,是照著已知斷層切的。

## ★對四條現行裁定的處置(r1 查出我全漏了)★

### ① `impact --diff` 聚合版「不接 hook」——★正面翻案,不繞過★

裁定原文(`Systems/retrieval-ranking:51`、`Projects/impact-diff橋接_計劃`):「advisory 審計鏡頭,不是自動閘——★機械保證只涵蓋合約/事故類固定席,其餘經排序無保底★;code-loop 有 reviewer 在場,保底與噪音都由人兜」。

★翻案論證★:該裁定的理由是「非固定席那一層沒有機械保證,不該自動化」。**本案只注入固定席**——正好落在它明說有機械保證的那一層。所以不是繞過它,是**在它劃的線內**。
★但這是我方的論證,不是裁定作者的意思★;r2 若有席位認為「只注入固定席仍算把聚合版接上 hook」,那是 blocker,本案應退回。

### ② `Systems/design-loop` d9(2026-09-01)——★直接採用★

原文:「code 迴圈固定席以落成核對 capped 節錄為準——上限內貼內容必答、超出列名不必答」,cap 落地實作 `_print_sync_nudge(cap=8)`(`scripts/lumos:16455`)。

r1 我寫「截斷的依據是什麼,我沒有答案」——★而這條兩天前就裁了,且 `Systems/design-loop` 就在本篇 related 裡:我開了節點,沒讀出裡面最新那條決定★。本版直接採用:**上限 8,上限內貼內容、超出列名**。

★連帶化解 r1 的一個 blocker★:兩席打「截斷後審查員還是得手動展開,套你自己的證據標準他不會做」。**但 d9 裁的正是「超出上限的不必答」**——該批評的前提是「審查員需要完整清單才能做好工作」,而裁定裁的是不需要。**兩席拿 d9 打我沒查,卻沒看出 d9 同時解掉了他們自己的 blocker。**

### ③ 錨點清單不含 claude 端 hook——★不打破,改成誠實揭露★

r1 我把「這支 hook 必須進錨點保護」寫成硬約束。**兌現不了**:錨點校驗的是 repo 內受 git 追蹤的原始碼,而真正在跑的是 `~/.claude/hooks/` 的複製檔(不受版控),`~/.claude/settings.json` 更不在版控;`anchor verify` 只在 pre-push(可 `--no-verify` 繞過)與 CI 事後跑。

★本版處置:刪掉那條假保護,改成明文揭露★——「這是本機實驗,**沒有機械防篡改**;能改到你家目錄的人本來就能做任何事,本案不增加也不減少那個風險面」。★假裝有保護比誠實說沒有更危險。★

### ④ 鄰居 hook 選 `additionalContext` 而非 `updatedInput`——★補上 r1 漏寫的技術理由★

鄰居那條是寫進圖譜、經多輪收斂的決策。**但它注給的是派工者;子代理是全新對話,拿不到那段內容。** 要把清單送進**子代理**眼前,`updatedInput` 是唯一做得到的路。

★r1 架構席已經預見這個理由並明說「若確實如此那會是站得住的技術理由,但材料裡完全沒寫」★——所以這條的錯是我沒寫論證,不是做法錯。**本版補上,並標明:這個論證未經實測(沒有驗過 additionalContext 到不到得了子代理),r2 應要求補驗或降級為推論。**

## ★預註冊的指標與讀法(跑之前寫死)★

**兩組**:注入組(派工詞帶標記)vs 對照組(不帶)。同一段期間、同一批人跑,不另設條件。

**★最可能的偽陽性:同質化★**(r1 後自己想到的,無人提出):給所有席位同一份清單,可能讓它們的發現**更重疊**。
★「覆蓋變好」和「大家被同一份清單框住、變得更像」在獨家率上長得一模一樣。★
**分辨方法(預註冊)**:
- **D1 清單外發現數**:每輪統計「不在注入清單上的相異缺陷」有幾個。覆蓋變好 → 清單外發現**不應該減少**;同質化 → 清單外發現會一起掉。
- **D2 清單命中率**:注入的 8 篇裡,有幾篇真的被某席寫成 finding。若命中率高但清單外發現掉 → 判同質化。
- ★D1 不降是判「有效」的必要條件★;只有獨家率下降而 D1 也下降,一律判同質化、不算有效。

**讀法(門檻在樣本量定後、開跑前取整並寫進本篇)**:
1. 獨家率下降 且 D1 未降 → 有效,寫成驗證紀錄並考慮從試點轉常設。
2. 獨家率下降 但 D1 也降 → 同質化,★判無效並記為「注入把席位變同質」的實證★(這本身是有價值的負面結果)。
3. 獨家率沒動 → 無效;此時看 D2,若命中率也低 → 清單根本沒被讀,問題在措辭或位置而非概念。
