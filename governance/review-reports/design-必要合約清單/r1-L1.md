severity: blocker

## F1 單一 phase 欄位 + 不准延期,對「一條合約跨多個階段」會造出無解死結

severity: blocker
blocking: yes

觀察到什麼:待完成節點的必填欄位裡「階段」只有一個值,而 S5 的擋下條件只看「這個節點標的那個階段」是否已在驗收紀錄宣告完成,不看這條合約實際依賴的是不是還有更晚的階段。

引句:「計劃節點參照、階段、最遲日期、理由」
引句:「當該階段已在驗收紀錄宣告完成而節點仍待完成,主體應擋下」
引句:「逾期之後唯一出路是做完轉正,或走棄置流程(要簽核)」

會怎麼出事:假設一條合約本來就要橫跨 P2、P3 兩個階段才能真正兌現(例如「P2 先做好資料層、P3 接上 API 後才能整條測完」),預告時只能填一個 `phase`。填 P2:P2 驗收紀錄一宣告完成,S5 立刻判「該階段已完成、節點仍待完成」而擋下推送與 CI——但這條合約客觀上還沒做完(P3 都還沒開始),而設計裁定「不准延期」,逾期/被 S5 擋下之後「唯一出路是做完轉正,或走棄置流程」。做完轉正做不到(P3 真的還沒做),棄置又不對(這條合約沒有要放棄,只是天生要跨兩個階段),於是唯一能繼續推送的辦法變成:要嘛謊報轉正(在合約還沒兌現時硬轉 pass,S6/S10 之後可能抓到綁定是假的,但當下先騙過 S5),要嘛真的走棄置流程騙一次簽核。兩條路都是逼人說謊才能推得動。填 P3 也不能繞開:那只是把同一個矛盾往後挪一階,P2 階段結束後這條合約仍然「屬於 P3」,但 P2 完成時它若曾經被預告成 P2 相關就一樣會撞到 S5(而且「該階段」判準若靠 phases 欄位或字串比對,兩階段都可能命中)。

為什麼是設計問題:這不是實作可以修的字串比對誤差,而是資料模型本身「一個守衛節點只綁一個 phase」的假設,跟「不准延期、逾期只能做完或棄置」這條鐵律疊在一起,對任何天生跨階段的合約永遠無解——不是誤擋,是結構性死結,沒有任何合法輸出。文件的〈四個取捨〉一節逐條裁定了階段判法、簽核綁定、延期、已實作未轉正四件事,唯獨沒有處理「合約範圍 vs 階段範圍」不對齊這個更根本的問題;鏡頭問題也明確點名「一條合約跨多個階段」這個情境,設計稿對它沒有任何著墨。

## F2 既有「非 pass 即死」的五處硬編碼枚舉,設計清單沒排進要更新的東西,會讓 abandoned 墓碑行為自相矛盾

severity: major
blocking: yes

觀察到什麼:設計稿承認要在 `_STATUS_ENUM` 加兩個新值,但只提到「加值」本身,沒有提到程式裡另外還有至少五處把 verification 的「非活躍/死」狀態寫死成 `("stale","fail","superseded")` 或單獨 `"superseded"` 的字面枚舉,這些枚舉在 `abandoned` 被加進去之後不會自動把 abandoned 也當成「死」。

引句:「要加 `pending` 與 `abandoned`」
引句:「刪要留墓碑(棄置狀態)且要簽核」

會怎麼出事:設計要求刪除/放棄一條合約要留墓碑(轉 abandoned),讓後面的人還看得到「這裡曾經預告過、後來棄置了」。但目前:
- Check E1「失效背書」只把 `("stale","fail","superseded")` 當死背書 `scripts/lumos:1751`,不含 abandoned——某 Systems 節點的 `verified_by` 還指著一個已 abandoned 的守衛節點時,doctor 不會警告這是死背書,讀者會以為這個守衛節點還健在。
- Check 3「verified_by 漏寫」的略過集合同樣是 `("stale","fail","superseded")` `scripts/lumos:1120`,不含 abandoned——代表 Systems 節點被要求持續反向登記一個已經棄置的守衛節點,不然 doctor 天天唸「漏寫」,逼人一直背著死鏈結不能拿掉。
- 孤兒檢查只豁免 `superseded` `scripts/lumos:1048`,abandoned 節點若哪天連結被清掉(例如 Systems 節點更新時順手拔掉死鏈結),會被當成「沒人引用的驗證紀錄」持續唸下去,跟其他真正該處理的孤兒混在一起。
- `_is_forgotten`(真遺忘,決定 search/檢索要不要藏)只認字面 `"superseded"` `scripts/lumos:3062`,不含 abandoned——已棄置的守衛節點會繼續出現在一般搜尋與檢索排序裡,跟活著的節點搶版面,違背「墓碑」本來該是「留著但不擋路」的直覺。
- `ARCHIVABLE = {"pass","done","superseded"}` `scripts/lumos:14393` 不含 abandoned——已棄置的守衛節點年紀再大也永遠不會被 `lumos archive` 收進 Archive,只能永久留在正式 vault 目錄裡。

疊起來的結果是:doctor 一邊逼你保留通往死節點的鏈結(Check 3 不豁免),一邊永遠不提醒你那條鏈結其實是死的(E1 不含 abandoned),同時那顆節點既不會被搜尋過濾掉也不會被歸檔——這四件事合起來比「乾脆全部照舊當 superseded 處理」還糟,是設計新增兩個狀態值時漏掉的既有假設,不是實作順手能補齊的細節,因為設計文件的〈要新增的東西〉清單裡完全沒提到要動這幾支既有函式。

## F3 新的 pending 狀態跟既有 stale 生命週期怎麼互動,設計完全沒講

severity: major
blocking: yes

觀察到什麼:設計稿只定義了「pending → pass(轉正,S8 反向要簽核)」與「pending → abandoned(棄置,S7 要簽核)」兩條轉換,但圖譜裡本來就有一個獨立於這次設計的既有狀態 `stale`(查:`scripts/lumos:11632` 的 `cmd_stale`,經 `lumos set <篇> status stale` 人工轉入),語意是「曾經 pass、現在前提可能過期、待重驗」。設計稿沒有回答:一顆已經 `stale` 的既有驗證節點,能不能/該不該被收編成新機制下的 `pending` 守衛節點?

引句:「實作並綁好測試後轉 pass,同一個節點就是該階段的驗收紀錄」
引句:「bound 降級回待完成同樣要簽核」

會怎麼出事:情境一——某條驗收紀錄本來 `pass`,後來因前提過期被人手動轉成 `stale`(既有機制),現在同一個階段又被新機制的 S6 規則盯上(「圖譜已有綁了真測試、綠、有審計的對應合約而節點仍待完成,主體應擋下並要求轉正」)——但此刻它是 `stale` 不是 `real/pass`,S6 的判定依據是 `classify_invariants`(real/dangling/fake/naked),不看 verification 節點本身的 status,於是完全有可能出現「★INVARIANT★ 綁定仍是 real,但它掛著的 Verification 節點其實已經 stale」這種狀態不一致,S6 該不該擋、要擋成什麼(要求重驗?還是直接當作未轉正逼你新開一個 pending?)設計沒有回答。情境二——「bound 降級回待完成同樣要簽核」明講的是 `pass → pending` 需要簽核,但完全沒提 `stale → pending` 算不算同一件事:如果不算,代表有一條路徑(先把節點改 stale,再改 pending)可以繞過 S8 的簽核要求淨降級;如果算,設計又從沒寫出來,實作者只能自己猜。

為什麼是設計問題:鏡頭問題明確問了「stale 的節點能不能降回待完成」,這不是實作瑣事——`stale` 是這個專案既有、獨立運作多時的生命週期狀態(有自己的排序、`--candidate` 查詢、人工轉入流程),新機制的兩個新狀態插進同一個狀態欄位卻完全沒交代跟 `stale` 的交集,會讓兩套機制在同一個節點上各自為政,而且沒有任何一條驗收條款(S1–S12)覆蓋到這個轉換,連測試都不會紅。

## F4 abandoned 能不能復活、跟 superseded 的界線沒說清楚

severity: minor
blocking: no

觀察到什麼:設計稿定義了「進入 abandoned 要簽核」(防悄悄刪除),但完全沒定義「離開 abandoned」——是不是終局狀態(像墓碑一樣不可逆),還是允許復活回 pending?也沒有講清楚新的 `abandoned` 跟既有 `superseded`(驗證紀錄既有狀態值之一)語意上怎麼分工:一條原本要做的合約如果因為計劃整個改方向而不再需要,該標 `abandoned` 還是 `superseded`?

引句:「刪要留墓碑(棄置狀態)且要簽核」
引句:「當守衛節點被棄置而沒有對得上的簽核紀錄,主體應擋下」

會怎麼出事:如果 abandoned 其實允許復活(例如專案優先序又變回來,原本棄置的合約要重新追),但設計沒訂「復活要不要簽核」,實作者可能直接放行任何人把 abandoned 改回 pending,悄悄迴避了「棄置要簽核」原本想擋的悄悄刪除/悄悄反悔問題;如果 abandoned 其實是終局狀態,設計也沒明講,之後有人想復活一條合約時會發現機制根本不支援,只能新開一個 pending 節點,原本的 abandoned 節點跟新節點之間的關聯(它們其實是同一件事)也沒有欄位可記。跟 superseded 的分工不清會導致同一種「這條合約不用了」的情境,不同人各自選一個狀態值,篩選統計(`_STATUS_ENUM` 值域執法的初衷)又會再度變回文件開頭引的野化問題。

為什麼是設計問題:這兩個狀態值是這次設計唯一新增的狀態,狀態轉換圖沒有畫出「棄置」這個節點的所有出邊(只有入邊的簽核條件),鏡頭問題明確要求檢查這件事;不是實作時隨手選一種行為就好,因為兩種選擇(終局 vs 可逆)對應到完全不同的資料模型(要不要留「復活」的簽核條款、要不要留 abandoned↔原節點的關聯欄位)。
