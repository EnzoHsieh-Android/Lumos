# 必要合約清單_計劃

> 白話:現在的閘只會說「你標成合約的這條沒綁測試」。它不知道「這個專案本來就該有哪幾條合約」,所以少標一條沒人發現;也不知道「這條打算之後做」,寫在筆記裡就沒人追。做法是:**一宣告「之後要有這條合約」,當場就長出一個待完成的驗證節點守著它**,做完了那個節點就地轉成正式驗收紀錄,不用搬家。
>
> **而且預告那一行就寫在節點裡**:下一個人為了別的事去查那篇節點,開頭那段「動手前一定要看」會一併告訴他「這裡還有一條合約預告了但還沒做,最遲某月某日」——不必等到逾期被擋,也不必有人記得去翻守衛節點。這是 2026-09-22 Enzo 追問出來的,原本的設計沒有守住這個場景。

## 威脅模型:防忘記,不防繞過(2026-09-22 Enzo 裁定)

**這套機制防的是「誠實的人忘了做」,不是「有人想讓閘過去」。** 設計審六席指出四條繞法全都成立:直接改最遲日期就等於延期、把節點的 `type` 改掉整套機制就當它不存在、成員帳自己沒人守、簽核只驗「有沒有那一列」不驗「誰簽的」。使用者裁定這些不在防守範圍內。

**這個裁定的後果要講明白**:
- 簽核、墓碑、成員帳這些留痕**留著,但它們的作用是「讓下一個人看得到發生過什麼」,不是「擋住有心人」**。文件與訊息不准寫成後者,寫成後者會讓人高估它。
- 上面四條繞法寫進〈誠實界線〉,不補洞。要補是之後真的發生過再說,那時才知道要防哪一種。

## 使用者已裁定(不要再問,照做)

1. **原子**:一個指令同時做「寫預告標記」與「建待完成的驗證節點並雙向連好」。分兩步人一定會漏。
2. **不要另外的清單檔**:圖譜是唯一事實來源,清單檔會跟圖譜 drift。
3. **生命週期**:預告時「待完成」→ 實作並綁好測試後轉 pass,同一個節點就是該階段的驗收紀錄。
4. **待完成節點必須有**:計劃節點參照、階段、最遲日期、理由。
5. **四條機械規則**:缺欄位擋;階段已宣告完成卻還待完成 → 擋;逾期 → **擋**(不是提醒,而且不准延期);已有符合條件的已綁合約 → 必須轉正,不能兩邊並存。
6. **刪除與降級要留痕**:改棄置狀態、或從已轉正降回待完成,都要有對得上的簽核紀錄。作用是留下痕跡,不是防偽造(見威脅模型)。
7. 生效位置:推送前與 CI。沒用這個機制的專案完全不受影響,零依賴。

## 啟動判準:只認這套機制自己建的節點(設計審折入)

**所有新規則只對「登記在必要集合帳裡的節點」生效,不看 `status` 欄位的字面值。**

理由:`pending` 是非常自然的英文字,任何人手寫一篇驗證節點隨手填這個字,今天 lint 會當錯字擋下並告訴他合法值有哪些——一句話就解決。若把它變成合法值又讓所有新規則照字面值生效,那個人會突然被要求填計劃參照、階段、最遲日期、理由四個他從沒聽過的欄位,而他只是想表達「這篇還沒驗完」。那等於「沒用這個機制的專案完全不受影響」這句承諾不成立。

所以:節點由指令建立時同時登記進必要集合帳,規則只掃帳上的成員。手寫同名狀態值的節點,行為跟今天一樣。

## 四個取捨:2026-09-22 Enzo 裁定

| 取捨 | 裁定 | 代價 |
|---|---|---|
| 「階段已完成」怎麼判 | 驗收紀錄新增 `phases:` 欄位;**找不到該欄位時退回整字比對階段名,並在輸出標明這條是靠字串比對、可能不準** | 要寫進寫法規範;過渡期兩種判法並存 |
| 簽核怎麼綁到合約 | `signoff` 加一個可選的 `--ref <字串>`,閘機械比對這個欄位 | 動到既有指令,但只加可選欄位,向下相容 |
| 延期 | **完全不准延期**。逾期之後唯一出路是做完轉正,或走棄置流程(要簽核) | 趕著交付時會真的被擋死,只能選「做完」或「當著人的面棄置」 |
| 已實作卻還待完成 | **擋**,要求轉正 | 趕著推的時候會被卡一次,但修法只是改一個欄位 |

**「不准延期」比我原本建議的「上限兩次」嚴,而且讓設計變簡單**:不需要延期指令、不需要延期次數上限、不需要延期的 append-only 帳。轉達過來的原始要求有「延期要留痕」這條,使用者當面裁掉了,以使用者為準。

| 驗證節點的狀態值域 | `_STATUS_ENUM["verification"] = {pass, stale, superseded}` | **要加 `pending` 與 `abandoned`**,並確認既有假設「驗證節點就是 pass」的地方不會誤判 |

| doctor 分段與軟硬提醒 | `section()` / `ok()` / `warn()`(算 issues 影響 rc)/ `warn_soft()`(不算) | 要擋的用 `warn()` |

**九成的工作是「讀節點 + 比對既有判定結果 + 幾條日期規則」,不需要新的判定引擎。**

## 預告要在節點裡看得到,但不能撞既有的閘(設計審 blocker,折入;2026-09-22 Enzo 追問後再改一次)

**問題**:全庫只有一種合約語法,而既有自檢對每條合約判「沒綁測試」「綁了但方法不存在」「綁到非測試」三種壞法,三種都是推送前的硬擋。預告時不帶測試名會被判沒綁,先帶上未來的測試名會被判懸空——**人一預告就被擋,走不到逾期才擋**。

**第一版改法(已作廢)**:預告不寫進節點,只存在守衛節點裡。Enzo 追問「那我打開那篇 Systems 節點會看不到嗎」,問到了要害——實測 `lumos context` 的輸出,那段「動手前一定要看」只抓正式合約行,預告中的合約會掉出最顯眼的位置,只在連出清單留一筆指標。**而預告中的合約恰恰最該被看見,因為它還沒有測試在守**。這個取捨的輕重我一開始判錯了。

**現在的改法:預告寫在節點摘要裡,但用不同的記號。**

```
KEY:★INVARIANT-PLANNED★ <一句話合約> [guard:Verification/<守衛節點>] [due:YYYY-MM-DD]
```

機械驗過(2026-09-22,兩種候選各測一次):

| 候選寫法 | 被既有合約抓取撈到 | 被既有格式檢查誤報 |
|---|---|---|
| `PLANNED:★INVARIANT★ …` | 否 | **會**(那道檢查看的是「出現合約記號但不是標準前綴開頭」) |
| `KEY:★INVARIANT-PLANNED★ …` | 否 | 否 |

所以用後者。重跑驗證:`python3 -c` 對兩種寫法各跑一次 `INVARIANT_RE.match` 與「含記號但非 KEY 前綴」判定。

**還要做的一件事**:`lumos context` 開頭那段「動手前一定要看」要一併印出預告中的合約與它的最遲日期,不然寫在摘要裡也還是不顯眼。這是這個改法的重點,不是附加。

**轉正時**把這行換成正式合約行並補上測試名,由轉正指令做,不要人手改。

## 擋的範圍:只擋碰到的人,不擋全隊(設計審 blocker,折入)

原本寫「逾期就擋推送與 CI」,沒界定擋誰。字面讀法是圖譜裡有任何一個逾期節點就擋掉所有人的所有推送,包含跟那條合約毫無關係的改動。防忘記不需要這麼粗,而且人放假就全隊停擺。

**改法三層,由窄到寬:**
1. **本機推送前**:只擋「這次改動碰到的檔,其家節點連到的守衛節點」逾期的情形。沒碰到就不擋,只在自檢裡提醒。
2. **CI**:擋全部逾期,因為 CI 是整個 repo 的守門員,而且不會有人在那邊趕時間。
3. **自檢**:一律列出來,不分碰到沒碰到。

守衛節點要記「負責人」,擋下來的訊息要指名是哪個節點、誰負責、下一步敲什麼——防忘記的機制如果不告訴人怎麼解,就變成防做事。

## 時區與到期日(設計審折入)

**一律用本機日期,到期當天不算過期,隔天才算。** 理由:最遲日期是人手寫的本地日期,不是時間戳;用本機日期比對才跟人腦裡的那天一致。CI 跟本機可能差一天,寧可晚一天擋,不要早一天擋——防忘記的機制誤擋一次的代價,比漏擋一天高。

## 到期前預警(設計審折入)

只有過期當下才第一次讓人知道,加上不准延期,週五訂的日期會在連假後第一次推送直接炸。**自檢要在到期前七天開始唸**,而且唸在不擋的那一層。

## 一條合約跨多個階段(設計審折入)

原本只給一個階段欄位,加上不准延期會死結。**改法:階段欄位收多值**,全部完成才算完成;任一階段未完成都還是待完成。

## 要新增的東西

- **指令**:`lumos guard plan`(預告合約並建守衛節點,原子)、`lumos guard settle`(轉正)、`lumos guard abandon`(棄置墓碑,要簽核)、`lumos guard required`(列出必要集合現況)。**沒有延期指令**——使用者裁定不准延期。名稱最終以實作為準。
- **狀態**:驗證節點加 `pending`(待完成)、`abandoned`(棄置)。
- **成員帳**:只增不改,記每次預告、轉正、棄置;成員變少要對得出簽核。**必須走既有的「附加後讀回自驗」原語與共用治理帳寫入口,並把新閘名登記進既有的閘名清單**——不要新開第五本帳(設計審折入;那支原語的出身就是一次「回報成功但其實沒落盤」的事故)。
- **doctor 一段**:列 bound / 待完成 / 逾期數量,違規用會影響 rc 的那種提醒。

## 怎麼驗收(判準先寫死,跑完不准改)

沒用這個機制的專案行為一模一樣(拿現有全套綠當證據)。每一條規則都要有先紅後綠的測試:
缺欄位、逾期、階段已完成仍待完成、已實作仍待完成、棄置沒簽核、降級沒簽核、成員變少對不出簽核、已轉正節點守的合約消失、守的測試懸空或紅。
另外要真的在臨時專案上跑一次 `doctor --ci`,確認擋得住也放得行。

## 回退

這套的所有新行為都只在「專案的圖譜裡存在待完成或已轉正的守衛節點」時才會啟動,沒有這種節點的專案完全走舊路。所以回退分兩層:

- **工具層**:還原這批提交就回到舊行為,不需要在專案端做任何收拾——新增的狀態值只是被 lint 放行的字串,還原後那些節點會被判成不合法狀態並在自檢時唸出來,但不會刪資料、不會改別人的檔。
- **專案層**:已經建出來的守衛節點是普通的圖譜筆記,還原工具之後它們仍在,只是沒有閘去讀它們。要完全退乾淨就把那些節點刪掉或改回既有狀態值。

**退不回去的部分**:成員帳是只增不改的治理帳,還原提交不會把已經寫進去的成員列刪掉;那份帳被別的機制讀到的話會看到一批它不認得的列。代價是治理帳多了一段沒人用的紀錄,不影響判定。

**出事故時的最小動作**:把專案 `.lumos/config.json` 的這道閘關掉(等同沒宣告),或還原工具層這批提交;兩者都不需要動已經寫好的筆記。

## 誠實界線

- 測試綠由既有機制負責,它只保證「跑過而且綠」,不保證測試真的測到那條合約——那是殺傷力驗證的事,不在這次範圍。
- 「階段已完成」無論哪種判法都是靠宣告,沒有人真的去驗那個階段做完了沒。
- **逾期就擋、而且不准延期,會在最忙的時候擋死推送**。這是使用者當面裁的,沒有繞道:只能做完或當著人的面棄置。代價要寫進文件第一段,不要讓人上線之後才發現。
- 直接 `rm` 掉節點檔而且沒人 commit 過成員帳的話,第一次就抓不到;成員帳只能抓「曾經有、現在少了」。

**四條已知繞法,刻意不補(威脅模型是防忘記,不是防繞過)**:

1. **直接改最遲日期就等於延期**,而且比走流程還乾淨——連留痕都沒有。「不准延期」是不提供延期指令,不是鎖住那個欄位。
2. **把守衛節點的 `type` 改掉**,整套機制就當它不存在。不是刪除,連結還在,自檢不會叫。
3. **成員帳自己沒人守**。它是 repo 裡的一份檔,改它跟改別的檔一樣容易;它只擋得住「忘了把節點一起交上來」。
4. **簽核擋的是「有沒有那一列」,不是「誰簽的」**。偽造一列很輕鬆。

**這四條寫在這裡,是為了讓文件與擋下來的訊息不要把這套講成防得住有心人。** 講成那樣的話,人會高估它,而高估一道守衛比沒有守衛更危險。要補是之後真的發生過再說,那時才知道要防哪一種。

## 既有五處狀態分支逐處查證(2026-09-22,以程式碼為準)

設計審指出「有五處硬編碼假設驗證節點不是 pass 就是死的」。逐處打開看,結論比預期好——**四處不用動,一處要動**:

| 在哪 | 現在怎麼判 | 加新狀態之後 | 要不要動 |
|---|---|---|---|
| 空條件提醒(`valid_under`/`revalidate_when` 沒寫就唸) | 只對 `status == "pass"` 的節點唸 | 待完成節點不會被唸——**這正是我們要的**,預告時還沒有前提可寫 | 不用動 |
| 狀態值域檢查 | 值域寫死三個值 | 要加兩個值 | **要動,而且只有這一處是非動不可的** |
| 新節點骨架 | 產出時寫死 `status: pass` | 預告指令自己產骨架,不走這條路 | 不用動 |
| 歸檔允許清單 | 只收 pass/done/superseded | 待完成與棄置都不在清單裡 → 不會被歸檔掉 | 不用動,而且是對的 |
| 過期候選 | 不看狀態,掃的是「重驗條件」欄位命中關鍵字 | 待完成節點沒寫重驗條件就不會出現 | 不用動 |

**所以新狀態的波及面比設計審擔心的小**:非動不可的只有值域那一處,其餘四處的現有行為剛好都是我們想要的。這個結論要在實作時用測試釘住,不是寫在這裡就算數。

## 新舊狀態怎麼互動(2026-09-22 定義)

| 從 | 到 | 誰做 | 要不要簽核 |
|---|---|---|---|
| 待完成 | 已通過 | 轉正指令(要求合約已綁真測試、綠、有審計) | 不用,這是變嚴 |
| 待完成 | 棄置 | 棄置指令 | 要 |
| 已通過 | 待完成 | 降級指令 | 要 |
| 已通過 | 過期 | 既有機制,不變 | 不用 |
| 棄置 | 任何 | **不准**,要重新預告一條新的 | — |
| 過期 | 待完成 | **不准**,過期的意思是「驗過但前提變了」,跟「還沒做」是兩件事 | — |

**棄置跟「被取代」的差別**:被取代是「有新的一篇接手同一件事」,棄置是「這件事決定不做了」。前者要指向接手的那篇,後者不用但要簽核。
