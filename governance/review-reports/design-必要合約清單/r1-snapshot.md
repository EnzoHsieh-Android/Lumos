# 必要合約清單_計劃

> 白話:現在的閘只會說「你標成合約的這條沒綁測試」。它不知道「這個專案本來就該有哪幾條合約」,所以少標一條沒人發現;也不知道「這條打算之後做」,寫在筆記裡就沒人追。做法是:**一宣告「之後要有這條合約」,當場就長出一個待完成的驗證節點守著它**,做完了那個節點就地轉成正式驗收紀錄,不用搬家。

## 使用者已裁定(不要再問,照做)

1. **原子**:一個指令同時做「寫預告標記」與「建待完成的驗證節點並雙向連好」。分兩步人一定會漏。
2. **不要另外的清單檔**:圖譜是唯一事實來源,清單檔會跟圖譜 drift。
3. **生命週期**:預告時「待完成」→ 實作並綁好測試後轉 pass,同一個節點就是該階段的驗收紀錄。
4. **待完成節點必須有**:計劃節點參照、階段、最遲日期、理由。
5. **四條機械規則**:缺欄位擋;階段已宣告完成卻還待完成 → 擋;逾期 → **擋**(不是提醒,而且不准延期);已有符合條件的已綁合約 → 必須轉正,不能兩邊並存。
6. **防悄悄刪除**:刪要留墓碑(棄置狀態)且要簽核;必要集合的成員記進只增不改的治理帳,成員變少要對得出簽核;pass 的守衛節點要宣稱守哪一條合約,那條消失或測試不存在或紅 → 擋。
7. **bound 降級回待完成同樣要簽核。**
8. 生效位置:推送前與 CI。沒用這個機制的專案完全不受影響,零依賴。

## 四個取捨:2026-09-22 Enzo 裁定

| 取捨 | 裁定 | 代價 |
|---|---|---|
| 「階段已完成」怎麼判 | 驗收紀錄新增 `phases:` 欄位;**找不到該欄位時退回整字比對階段名,並在輸出標明這條是靠字串比對、可能不準** | 要寫進寫法規範;過渡期兩種判法並存 |
| 簽核怎麼綁到合約 | `signoff` 加一個可選的 `--ref <字串>`,閘機械比對這個欄位 | 動到既有指令,但只加可選欄位,向下相容 |
| 延期 | **完全不准延期**。逾期之後唯一出路是做完轉正,或走棄置流程(要簽核) | 趕著交付時會真的被擋死,只能選「做完」或「當著人的面棄置」 |
| 已實作卻還待完成 | **擋**,要求轉正 | 趕著推的時候會被卡一次,但修法只是改一個欄位 |

**「不准延期」比我原本建議的「上限兩次」嚴,而且讓設計變簡單**:不需要延期指令、不需要延期次數上限、不需要延期的 append-only 帳。轉達過來的原始要求有「延期要留痕」這條,使用者當面裁掉了,以使用者為準。

## 要新增的東西

- **指令**:`lumos guard plan`(預告合約並建守衛節點,原子)、`lumos guard settle`(轉正)、`lumos guard abandon`(棄置墓碑,要簽核)、`lumos guard required`(列出必要集合現況)。**沒有延期指令**——使用者裁定不准延期。名稱最終以實作為準。
- **狀態**:驗證節點加 `pending`(待完成)、`abandoned`(棄置)。
- **成員帳**:只增不改,記每次預告、轉正、棄置;成員變少要對得出簽核。
- **doctor 一段**:列 bound / 待完成 / 逾期數量,違規用會影響 rc 的那種提醒。

## 條款(每條要綁一支現在會紅的測試)

- [S1] 當專案沒有任何待完成守衛節點,主體應讓所有既有行為與輸出完全不變 [test:t_guard_plan_absent_is_noop]
- [S2] 當呼叫預告指令,主體應在同一次呼叫內寫好合約標記與守衛節點並雙向連上;任一步失敗應全部回滾,不得留下半套 [test:t_guard_plan_atomic]
- [S3] 當待完成節點缺計劃參照、階段、最遲日期或理由任一項,主體應擋下並指出缺哪一項 [test:t_guard_pending_requires_fields]
- [S4] 當今天已過最遲日期,主體應擋下推送與 CI,並且不提供延期出路 [test:t_guard_pending_overdue_blocks]
- [S5] 當該階段已在驗收紀錄宣告完成而節點仍待完成,主體應擋下 [test:t_guard_phase_done_still_pending]
- [S6] 當圖譜已有綁了真測試、綠、有審計的對應合約而節點仍待完成,主體應擋下並要求轉正 [test:t_guard_already_bound_must_settle]
- [S7] 當守衛節點被棄置而沒有對得上的簽核紀錄,主體應擋下 [test:t_guard_abandon_requires_signoff]
- [S8] 當已轉正的節點被降回待完成而沒有對得上的簽核紀錄,主體應擋下 [test:t_guard_downgrade_requires_signoff]
- [S9] 當必要集合的成員比治理帳少、且少掉的那些對不出簽核,主體應擋下 [test:t_guard_member_shrink_needs_signoff]
- [S10] 當已轉正節點宣稱守衛的合約消失、或它綁的測試不存在或是紅的,主體應擋下 [test:t_guard_settled_contract_vanished]
- [S11] 當驗收紀錄有 phases 欄位,主體應以欄位判斷階段完成;沒有該欄位時應退回整字比對並在輸出標明這條是靠字串比對 [test:t_guard_phase_field_then_fallback]
- [S12] 當簽核帶 --ref,主體應把它記進簽核帳且不影響沒帶 --ref 的既有用法 [test:t_signoff_ref_backward_compatible]

## 怎麼驗收(判準先寫死,跑完不准改)

沒用這個機制的專案行為一模一樣(拿現有全套綠當證據)。每一條規則都要有先紅後綠的測試:
缺欄位、逾期、階段已完成仍待完成、已實作仍待完成、棄置沒簽核、降級沒簽核、成員變少對不出簽核、已轉正節點守的合約消失、守的測試懸空或紅。
另外要真的在臨時專案上跑一次 `doctor --ci`,確認擋得住也放得行。

## 回退

這套的所有新行為都只在「專案的圖譜裡存在待完成或已轉正的守衛節點」時才會啟動,沒有這種節點的專案完全走舊路。所以回退分兩層:

- **工具層**:還原這批提交就回到舊行為,不需要在專案端做任何收拾——新增的狀態值只是被 lint 放行的字串,還原後那些節點會被判成不合法狀態並在自檢時唸出來,但不會刪資料、不會改別人的檔。
- **專案層**:已經建出來的守衛節點是普通的圖譜筆記,還原工具之後它們仍在,只是沒有閘去讀它們。要完全退乾淨就把那些節點刪掉或改回既有狀態值。

**退不回去的部分**:成員帳是只增不改的治理帳,還原提交不會把已經寫進去的成員列刪掉;那份帳被別的機制讀到的話會看到一批它不認得的列。代價是治理帳多了一段沒人用的紀錄,不影響判定。

**出事故時的最小動作**:把專案 `.lumos/config.json` 的這道閘關掉(等同沒宣告),或還原工具層這批提交;兩者都不需要動已經寫好的筆記。

## 誠實界線

- 測試綠由既有機制負責,它只保證「跑過而且綠」,不保證測試真的測到那條合約——那是殺傷力驗證的事,不在這次範圍。
- 「階段已完成」無論哪種判法都是靠宣告,沒有人真的去驗那個階段做完了沒。
- **逾期就擋、而且不准延期,會在最忙的時候擋死推送**。這是使用者當面裁的,沒有繞道:只能做完或當著人的面棄置。代價要寫進文件第一段,不要讓人上線之後才發現。
- 直接 `rm` 掉節點檔而且沒人 commit 過成員帳的話,第一次就抓不到;成員帳只能抓「曾經有、現在少了」。
