# 設計審查:必要合約清單_計劃(繞過與弱化鏡頭)

站在「想讓閘過去的人」那一邊看這份設計稿(governance/review-reports/design-必要合約清單/r1-snapshot.md,sha256 b1e222e9…54b8a)。逐條列可繞的路,並回答「繞完之後閘還看得見嗎」。

## F1 「不准延期」的裁定沒有任何欄位防護,直接改日期就形同延期而且沒人擋

severity: blocker
blocking: yes

引句:「**完全不准延期**。逾期之後唯一出路是做完轉正,或走棄置流程(要簽核)」
引句:「當今天已過最遲日期,主體應擋下推送與 CI,並且不提供延期出路」

設計稿把「不准延期」當成整份設計最嚴、也讓設計變簡單的裁定(第 45 行:「不需要延期指令、不需要延期次數上限、不需要延期的 append-only 帳」)。但它防的只是「有沒有一個叫延期的指令」,不是「最遲日期這個欄位能不能被改」。待完成節點的四個必填欄位(計劃節點參照、階段、最遲日期、理由)在設計裡就是普通的 frontmatter 純量欄位,跟現有的 `status`/`type`/`created` 同一等級。查 `scripts/lumos:12368` 的 `SCALAR_KEYS` 與 `scripts/lumos:12800` 的 `_cmd_set_locked`:只要欄位名在 `SCALAR_KEYS` 集合裡,`lumos set <節點> <欄位> <值>` 就直接改,唯一的檢查是「改完之後這個值真的寫進去了沒」,沒有任何欄位標成「這個要簽核才能改」或「這個只能往前走一次」。設計裡描述的簽核要求(第 32 行)只綁在「棄置」「降級」「成員變少」三件事上,完全沒提到「改最遲日期本身」要簽核或要留痕。

具體情境:某個功能要趕在今天推送前上線,但守衛節點今天到期。趕工的人不需要懂圖譜機制,只要 `lumos set <守衛節點> 最遲日期 2026-12-31`(或直接用編輯器改那個檔的 frontmatter,連 lumos 都不用),S4 讀到的日期就不再是今天,擋推送的檢查直接不觸發。事後任何人看治理帳或成員帳,都只看得到「這個節點的最遲日期一直是 2026-12-31」——因為節點本身不是 append-only,沒有留下「原本寫的是哪一天」的痕跡。閘看不見這件事發生過。

為什麼是設計問題:這不是實作細節可以之後補一個檢查就解決的小事——設計稿把「不准延期比上限兩次更嚴」當作賣點(第 45 行),但它給的「更嚴」完全建立在「沒有延期指令」這種靠使用者自律的防護上,跟同一份設計對棄置、降級、成員變少所要求的機械級防護(簽核 + 治理帳)不是同一個等級。四條機械規則裡最重的一條(逾期擋且不准延期),防護力反而是四條裡最弱的。

## F2 把守衛節點的 `type` 改掉,整條機制就當它不存在——不是刪除,連結還在,doctor 不會叫

severity: blocker
blocking: yes

引句:「要加 `pending` 與 `abandoned`」
引句:「驗證節點加 `pending`(待完成)、`abandoned`(棄置)」

設計盤點現況時明講,狀態值域是 `_STATUS_ENUM["verification"]`(第 54 行「現況盤點」表格),新加的 `pending`/`abandoned` 也是掛在「驗證節點」這個 `type` 底下。也就是說,整套機制(S3–S10)幾乎可以肯定是靠掃描 `type: verification` 的節點來認出「這是一個守衛節點」。但 `type` 跟最遲日期一樣是普通 `SCALAR_KEYS` 欄位(`scripts/lumos:12368`),`lumos set <守衛節點> type system` 一行指令就能把它從驗證節點變成別的類型。查過 `scripts/lumos`,沒有找到任何限制「type 只能是某幾個合法值」的檢查(對照:`status` 有 `_STATUS_ENUM` 逐型檢查,`type` 沒有對應的值域檢查),也沒有找到「連結指向的節點型別要跟連結語意相符」的檢查(`verified_by`/`plan_refs` 只驗連結目標存不存在,`scripts/lumos:1099`-`1104`,不驗目標的 `type` 是不是 verification)。

具體情境:守衛節點已經逾期,眼看要被 S4 擋。與其改日期(可能被 F1 那種修法補上留痕),換一招:把節點的 `type` 從 `verification` 改成 `system`。節點檔案本身沒有被刪,`plan_refs`/`verified_by` 兩邊的連結都還解析得到那個檔案,doctor 的「連到不存在筆記的連結」與「orphan Verification」兩段檢查都不會叫(因為這兩段檢查認的是「連結解不解得到檔案」,不是「檔案現在還是不是 verification」)。這個節點從此不再被任何 verification 專屬的狀態值域檢查、S3–S10 的機械規則、`lumos guard required` 的必要集合掃描認出來——它憑空從必要集合裡消失,而且不會觸發「成員變少要簽核」(S9),因為 S9 比對的多半是「現在圖譜裡型別為 verification 的守衛節點」對「治理帳」,型別一換,兩邊的現況掃描就先看不到它,連比對的機會都沒有。

為什麼是設計問題:設計把整套防悄悄刪除的機制(墓碑、簽核、治理帳)都設計成守著「這個節點被刪除或降級」這個動作,但根本沒有討論「這個節點還在,只是不再被算進必要集合」這個更安靜的退場方式。這是設計覆蓋面的缺口,不是某個檢查函式沒寫好。

## F3 「必要集合成員記進只增不改的治理帳」——這份治理帳自己是誰在守?

severity: blocker
blocking: yes

引句:「必要集合的成員記進只增不改的治理帳,成員變少要對得出簽核」
引句:「當必要集合的成員比治理帳少、且少掉的那些對不出簽核,主體應擋下」

設計稿把整套「防悄悄刪除」的最後一道防線押在「治理帳只增不改」這句話上,但通篇沒有講這份帳本身怎麼被保護成「只增不改」。查全庫,唯一對 append-only 帳做過完整性驗證的機制是 design-loop 的 golden verdict 回放(`scripts/lumos:730`-`762`):它拿凍結當下「全部列的 sha256 集合」跟現在帳裡的 sha 集合互相比對,而且連 golden 檔本身都要拿 `git cat-file` 對 HEAD blob 驗證有沒有被動過(第 736-745 行的註解直接寫「凍結檔的竄改偵測以版控為錨」)。必要合約清單設計裡的「成員治理帳」沒有提到任何類似的 sha 集合比對或 git blob 錨定——它就是 repo 裡一個普通的 jsonl 檔。

具體情境:某人要讓「必要集合」看起來一直都只有 5 條,即使實際上曾經預告過第 6 條又想悄悄拿掉。直接用文字編輯器打開治理帳那個 jsonl,刪掉或改掉對應那一列(不是新增一列抵銷,是真的把歷史那行改掉/拿掉),再把節點檔也一併刪掉或按 F2 的方法換型別。這時候「現況」與「治理帳」兩邊重新算出來的集合是一致的——因為治理帳的「歷史」本身已經被改寫,S9 拿現況跟帳比對,兩邊都不記得那條合約存在過。也適用設計稿明講要提防的「在別的分支建成員帳」情境:另開一條沒人審過的分支,一次寫進一長串看起來按時間排列、其實是憑空捏造的預告/轉正紀錄,再合併回主線——沒有任何機制檢查這些帳目列的時間順序或內容是否對應到真的發生過的提交。

為什麼是設計問題:這正是設計稿自己在「誠實界線」點名過的風險('直接 `rm` 掉節點檔而且沒人 commit 過成員帳的話,第一次就抓不到',第 104 行),但設計把這句話寫成「已知局限」帶過,沒有像 golden verdict 回放那樣配一個對應的完整性機制——而全庫已經有現成的作法可以照抄,設計卻沒有採用或討論為什麼不採用。

## F4 「要簽核」防的是有沒有那一列紀錄,不是誰簽的——偽造一列輕而易舉

severity: major
blocking: yes

引句:「刪要留墓碑(棄置狀態)且要簽核」
引句:「當守衛節點被棄置而沒有對得上的簽核紀錄,主體應擋下」

設計把「棄置」「降級」「成員變少」三件最高風險的操作,全部靠同一個既有機制擋:`--ref` 之後仍然是 `cmd_signoff`(`scripts/lumos:6151`)。這支函式除了要求 `--note` 非空之外,`by` 參數(第 6151 行的簽核人)是呼叫端自由傳入的字串,存進 `.signoff-log.jsonl` 時原樣寫入(第 6171-6176 行),沒有跟 git commit 作者、repo 的核可角色名單或任何外部身份核對過。

具體情境:要棄置一個逾期的守衛節點又不想真的找人核可,自己在終端機打 `lumos signoff <節點> --note "已確認可棄置" --by "Enzo" --ref <合約字串>`(或設計要新增的 `guard abandon` 之下走同一條簽核路徑)。這一列紀錄跟真的由 Enzo 本人核可寫出來的紀錄,在治理帳裡長得一模一樣——S7/S8/S9 檢查的是「對不對得出一列簽核紀錄」,不是「這列紀錄是不是真的由有核可權的人留的」。

為什麼是設計問題:設計稿的語言(「要人簽核」「要對得出簽核」)暗示簽核是一道人工核可關卡,但底層機制只留痕、不驗身份(`cmd_signoff` 的 docstring 自己也寫「工具只記留痕,不證明確認真的發生」)。設計選擇把最高風險的三個操作(悄悄刪除、悄悄降級、悄悄縮編必要集合)全部押在這同一個弱原語上,卻沒有討論這個原語的信任模型跟這次要防的威脅(想繞過閘的人)是不是匹配——同一個人既是「想繞過閘的人」也可以是「簽核的人」時,這道關卡形同虛設。

想過但沒有寫成獨立發現的情境(結論是「閘看得見」,不構成新發現):直接 `rm` 掉守衛節點檔——doctor 的「連到不存在筆記的連結」段(`scripts/lumos:1099`-`1104`)與 orphan 段都是 `warn()`(會計入 `issues`、影響 rc,`scripts/lumos:993`-`1006`),推送前與 `doctor --ci` 都會擋,所以單純刪檔會被抓到(除非同時按 F3 的方法把成員帳跟連結來源一起處理掉)。`git push --no-verify`——CI 端 `.github/workflows/ci.yml:96-97` 獨立重跑 `doctor --ci`,不依賴本機有沒有掛 hook,所以跳過 pre-push 不等於跳過這套機制。
