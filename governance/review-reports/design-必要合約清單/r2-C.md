severity: blocker

## F1 S6(已綁真測試還待完成要擋)沒有範圍界定,兩種讀法會做出效能與正確性都不同的系統

severity: blocker
blocking: yes

引句:「當圖譜已有綁了真測試、綠、有審計的對應合約而節點仍待完成,主體應擋下並要求轉正」

觀察到什麼:S4(逾期擋)明確寫了「三層,由窄到寬」的範圍界定——本機只擋這次改動碰到的、CI 擋全部、自檢一律列出,理由是「防忘記不需要這麼粗,而且人放假就全隊停擺」。但 S6 完全沒有等價的範圍字句。而「綠」這個判準目前唯一的機械來源是 `lumos bound-tests`,它是 **diff 範圍**的:`_bound_tests_check` 先算 diff range(`scripts/lumos:27530` 呼叫 `_bound_tests_range`),再用 `_bound_tests_for_diff(repo_root, _rng, payload=payload)`(`scripts/lumos:27542`)算出「這次改動波及到的」合約才去跑測試——沒有一條既有路徑可以問「圖譜裡任何一個 pending 節點守的那條合約,現在是不是綠的」而不依賴當次 diff。`classify_invariants`(`scripts/lumos:10305`)只回答「綁定存在」(real/dangling/fake/naked),不執行測試,doctor 自己的註解也寫明「doctor 不執行測試」(`scripts/lumos:1258`)。

會怎麼出事:兩個實作者會做出不同的系統,而且都有真的問題。
- 讀法 A(沿用 diff 範圍):S6 只在「本次改動剛好也碰到那條合約綁的程式檔」時才會去驗證並擋下。多數情況下一個 pending 節點守的合約會在跟這次推送完全無關的分支上被實作完成,S6 因為沒東西可跑而永遠不會觸發——這正是這條規則存在的理由(防止「已實作卻還標成待完成」被忘記轉正),卻在最常見的情境下悄悄失效。t_guard_already_bound_must_settle 這支測試如果照這個讀法寫,紅燈情境會侷限在「這次 diff 剛好也碰到那條合約」,測試看起來過了,但規則在真實使用中大半時候不會生效——這是測試綠但規則沒守住的落差,不是能靠事後修測試補的事。
- 讀法 B(逐一檢查全部 pending 節點,不論 diff 有沒有碰到):要在每次本機推送時,對圖譜裡**所有**待完成守衛節點的合約各跑一次它綁的測試,才能判斷「有沒有哪個其實已經綠了」。這正是同一支程式檔案裡另一段註解明確要避免的代價:「★正是設計明令要避免的『首推跑滿全部』那條稅★」(`scripts/lumos:27538`)——S6 的字面要求跟這個既有設計原則直接衝突,而設計稿完全沒有討論這個衝突。

為什麼是設計問題:這不是「實作時看著辦」的細節——兩種讀法一個是「規則常態性不生效」、一個是「違反同一份程式碼庫剛立下的效能鐵則」,兩者都要在動手寫 t_guard_already_bound_must_settle 之前先choice,而設計稿的「現況盤點」table 把 `classify_invariants` 和 `bound-tests` 都寫成「直接用,不要自己再判一次/不要再寫第二套」,暗示這是讀節點+比對既有結果就能做完的事,但實際上要讓 S6 在真實情境下生效,需要新的判定範圍設計(要嘛新開一支不依賴 diff 的「查這一條合約現在綠不綠」入口,要嘛明講 S6 也吃三層範圍、並接受「本機推送不主動查未觸碰的合約」這個代價)——這正是「九成是讀節點+比對」這句話撐不住的地方。

## F2 「既有五處狀態分支逐處查證」漏了至少一處,而且漏的那處會讓 abandoned 節點永久污染既有指令輸出

severity: major
blocking: yes

引句:「非動不可的只有值域那一處,其餘四處的現有行為剛好都是我們想要的」

觀察到什麼:設計稿逐一核對了五處硬編碼假設 verification 只有 pass 或死掉的地方,結論是只有 `_STATUS_ENUM` 值域要改。但程式碼裡至少還有一處同類的硬編碼分支沒被列進這張表:`scripts/lumos:11718` 的 `QUERY_CLOSED_STATUSES = {"done", "pass", "superseded", "resolved", "wontfix"}`,這是 `lumos query --active`(排除已收案節點)用的收案狀態集合(`scripts/lumos:11721` 起的 `cmd_query`)。這集合是寫死的字面值列表,跟 `_STATUS_ENUM` 完全是兩份獨立的資料,改 `_STATUS_ENUM` 不會連帶改到它。

會怎麼出事:設計稿新增的 `abandoned`(棄置)狀態語意上等同「這件事決定不做了」,跟 `wontfix` 是同一類「已收案、不再是待辦」。但 `QUERY_CLOSED_STATUSES` 沒有 `abandoned`,只動值域那一處的話,任何一個被棄置的守衛節點會在 `lumos query --active` 的結果裡**永久**顯示成「還活著」——而且因為棄置的意思正是「不會再有人碰它」,這筆髒資料不會像一般待辦一樣被人手動清掉,會一直留在每一次 `--active` 查詢裡,而且沒有任何條款(S1–S16)綁測試去釘住這個行為,設計稿自己也沒把它算進「非動不可」的清單。

為什麼是設計問題:設計稿把「五處查證」當成完整盤點寫進正式結論,並且明講「這個結論要在實作時用測試釘住,不是寫在這裡就算數」——但連盤點本身都不完整,實作者會直接信任這張表跳過搜尋,而不會知道還有第六處要找。這不是實作細節,是設計稿對「波及面有多大」這個核心判斷本身出了漏洞。

## F3 「驗收紀錄宣告階段完成」沒有定義比對的資料來源與比對鍵,S5/S11 兩個實作者會做出不相容的系統

severity: major
blocking: yes

引句:「當驗收紀錄有 phases 欄位,主體應以欄位判斷階段完成」

觀察到什麼:S5 的判準是「該階段已在驗收紀錄宣告完成」,S11 說明機制是比對 `phases:` 欄位、缺欄位時「退回整字比對階段名」。但設計稿從沒說清楚:①「驗收紀錄」指的是哪一篇——是同一個守衛節點自己(生命週期那段說「同一個節點就是該階段的驗收紀錄」),還是圖譜裡**另一篇**已經 pass 的 Verification 節點?如果是後者,②怎麼認定「那篇跟這個守衛節點是同一個計劃的同一個階段」——靠 `plan_refs` 相等,還是純比對 `phases:` 欄位字串本身?③ fallback 的「整字比對階段名」是去比對哪一份文字——所有 Verification 節點的 summary、還是只比對同一個 `plan_refs` 底下的節點?全庫搜尋 `phases:` 這個欄位目前完全不存在(`scripts/lumos` 沒有任何一處讀寫這個鍵),也沒有既有慣例可以類推;而「驗收紀錄」這個詞在既有圖譜筆記裡只是口語用法(例如 `docs/lumos-toolchain-knowledge/Projects/截圖基準驗收流程_計劃.md:53` 拿它形容一張截圖,跟這裡要的「帶 phases 欄位的正式紀錄」完全是兩回事),不是一個有固定 schema 的節點型別。

會怎麼出事:實作者 A 把「驗收紀錄」理解成守衛節點自己(等它轉正時附帶宣告哪個階段做完),於是 S5 永遠不會觸發,因為守衛節點還 pending 就代表它自己還沒宣告任何階段完成,「該階段已在驗收紀錄宣告完成而節點仍待完成」這個狀態在這種理解下根本造不出來,`t_guard_phase_done_still_pending` 這支測試連紅燈情境都設計不出來。實作者 B 認為「驗收紀錄」是圖譜裡任何一篇 pass 的 Verification 節點,只要它 `phases:` 欄位裡有相同字串就算數,於是兩個完全不相干計劃裡剛好都寫了「Phase 2」的守衛節點會互相誤判成同一階段完成。這兩種系統的行為完全不同,而且都能自圓其說地符合字面條款。

為什麼是設計問題:這是判準本身的資料模型缺了一塊,不是命名或程式風格的問題——沒有先講清楚「跟誰比、比什麼鍵」,寫測試的人只能自己發明一套比對邏輯,而發明出來的東西不會是同一套。

## F4 S3 列的守衛節點必填欄位沒有「連到檔案的家節點」這一項,但 S4 的本機範圍縮限正好靠這條連結才能運作

severity: major
blocking: yes

引句:「這次改動碰到的檔,其家節點連到的守衛節點」

觀察到什麼:S4 的本機推送範圍界定寫的是「只擋『這次改動碰到的檔,其家節點連到的守衛節點』逾期的情形」——要做到這件事,系統得能從「這次改動的檔案」一路走到「守著它的守衛節點」,中間要經過「檔案的家節點」(Systems 節點,靠 CLAUDE.md 鐵則五與 `about_code` 建立)再到「連到那個家節點的守衛節點」。但 S3 列出的守衛節點必填欄位只有「計劃參照、階段、最遲日期、理由」,後面加負責人也只到五項,完全沒有「連到哪個 Systems 節點」這一項;「要新增的東西」那節列出的四支新指令(`guard plan`/`settle`/`abandon`/`required`)也沒有提到要接一個 `--systems` 或等價的檔案連結參數。對照既有的 `lumos new verification`(`scripts/lumos:14358-14360`)在建 Verification 節點時會同時把 `--systems` 指定的節點寫 `verified_by` 連回來——這條線既有慣例是存在的,但設計稿的必填欄位清單裡沒有把它列進去,S3 的擋下條件字面上也不會因為「沒接 Systems 節點」而擋。

會怎麼出事:照 S3 字面實作出來的 `guard plan`,一個只填了計劃參照、階段、最遲日期、理由、負責人、完全沒有任何 `verified_by`/檔案連結的守衛節點,會被判定「必填欄位齊全」而放行建立。這種節點一旦逾期,S4 的本機範圍縮限邏輯找不到任何「這次改動碰到的檔」能連到它——因為它跟任何 Systems 節點都沒有連結——於是它**永遠不會在本機推送時被擋下**,只能靠 CI 的全量擋才會抓到。而防忘記機制的第一道防線(本機)對這種節點形同虛設,卻沒有任何條款或欄位檢查會提醒建立節點的人少做了這一步。

為什麼是設計問題:S4 的整段範圍設計(三層、由窄到寬)是這次設計稿花最多篇幅去談的取捨之一,理由是「不能因為別人的合約逾期就擋死全隊」;但支撐這個設計的圖邊(檔案→家節點→守衛節點)沒有被寫進必填欄位或建立流程裡,等於精心設計的範圍縮限機制少了一根柱子,而且這個缺口在條款清單裡完全看不出來——要對照既有 `lumos new verification` 的實作慣例才找得到。
