## F1 「任一步失敗全部回滾」跟本 repo 對「多產物寫入」的既定做法相反

severity: major
blocking: yes

引句:「任一步失敗應全部回滾,不得留下半套」

觀察到什麼:[S2] 要求 `lumos guard plan` 在同一次呼叫內「寫合約標記」與「建守衛節點並雙向連上」,任一步失敗要**全部回滾**,還配了一支要跑紅再跑綠的測試 `t_guard_plan_atomic` 釘死這個行為。但這個 repo 對「一個動作要同時動好幾個產物」這類問題,已經有寫死在程式碼裡的既定立場,而且立場是**刻意不做真回滾**:
- `scripts/lumos:12974` `_cmd_remove_locked` 的註解直接說「回滾要『刪 stamp』,但 set 只能覆寫、沒有刪除原語——回滾最後一步是空的」——這個 repo 的寫入原語天生沒有「刪除」這一步,回滾機制在架構上是搭不起來的。
- `scripts/lumos:14010` `rel_cascade` 的決策連動寫入(決策帳本 + decision_refs 回寫兩個不同檔)明講「回寫失敗=軟警告不回滾(帳本才是地面真相,decision_refs 是衍生、可從帳本重建)」。
- `scripts/lumos:30602` 同一條路徑再標一次「fail-open:決策寫入已 atomic 完成,不回滾」。

會怎麼出事:這三處都是**同一類問題**——一個動作要落地到兩個不同檔案(一份是權威記錄、一份是衍生/連結資料),而這個 repo 對這類問題的解法統一是「先讓其中一個檔案的寫入是單檔原子(`_write_lf`/`atomic_write_verify`,tmp→os.replace),另一邊寫失敗就印警告、不動第一邊,靠之後重建或人補」。`guard plan` 面對的正是同一形狀的問題:「寫合約預告標記」在來源筆記(或計劃節點)的檔案裡,「建守衛節點」是另一個新檔案,兩者再雙向連結。如果照 [S2] 字面做「全部回滾」,實作者要嘛(a)發明一個這個 repo 從沒建過的跨檔案交易/復原機制,要嘛(b)在沒有刪除原語的前提下假裝能回滾第一步已經成功落盤的寫入(例如已經 `os.replace` 完成的合約標記檔),兩者都會撞上 `scripts/lumos:12974` 講的那道牆。更具體的情境:`guard plan` 先把預告標記原子寫進來源筆記(成功),接著建守衛節點檔案時磁碟滿了 / 併發鎖逾時失敗——這時候「回滾」意味著要把已經成功寫進磁碟、且可能已被別的 `lumos doctor` 或別的 session 讀到的第一個檔案改回去,這正是本 repo 明確放棄過的做法。

為什麼是設計問題:這不是「這行字可以寫更好」,是條款 [S2] 把一個已經被本 repo 兩處架構決策明確否決過的解法(真回滾)寫成機械規則並綁測試,implementer 要嘛違反既有架構共識另開一套,要嘛做不到測試要求的紅轉綠——這會在實作階段才爆,而不是現在。建議在動工前先對齊:要嘛比照既有慣例改成「先建守衛節點(衍生/可重建的那邊)成功後才寫合約標記(權威那邊),失敗只印警告不宣稱回滾」,要嘛明確說明這次為什麼需要、要怎麼繞過「沒有刪除原語」這個既有限制。

## F2 「成員帳」沒有提到复用既有的共用治理帳寫入口,像是要再開一本帳

severity: major
blocking: yes

引句:「只增不改,記每次預告、轉正、棄置」

觀察到什麼:設計稿「要新增的東西」把「成員帳」跟「指令」「狀態」「doctor 一段」並列成獨立項目,但整份設計稿沒有任何一句提到要復用哪一支既有的寫入口。這份設計稿的「現況盤點」表格明明就是為了「別人有的別自己刻」而寫的(逐條列出 classify_invariants / bound-tests / signoff / 狀態值域 / verified_by 雙向連結 / doctor 分段六樣要直接用的東西),偏偏漏掉了跟「成員帳」最直接相關的既有機制:
- `scripts/lumos:7575` `_jsonl_append_verified`——這支函式的docstring 明講出身是「2026-07-28 record 回報成功未落盤事故」,是這個 repo 因為真的出過事故才補上的「append+讀回自驗」統一原語,`.canary-log.jsonl`/`.escape-log.jsonl` 都走它。
- `scripts/lumos:826`、`scripts/lumos:950`、`scripts/lumos:965` 的 `_gate_event`/`_append_governance_log`——這是給「任何新機制的放行/擋下事件」用的共用治理帳寫入口,寫入 `docs/.governance-log.jsonl`,配一張集中維護的閘名清單 `_KNOWN_GATES`(`scripts/lumos:6192`)登記新閘名,而不是每個新機制各開一支 `.xxx-log.jsonl`。

會怎麼出事:如果實作者照字面把「成員帳」當成一份全新獨立檔案、自己手寫 `open(path, "a")`,會出現兩種可預期的壞結果。第一種是重蹈 2026-07-28 那次事故——寫入成功但沒讀回驗證,claim 記帳成功但實際沒落盤,這正是 `_jsonl_append_verified` 存在的原因,而設計稿完全沒提醒要用它。第二種是「成員帳」變成第五本帳(現有已經有 canary/governance/signoff/escape 四本),`lumos gov --stats` 這類統計面(`_KNOWN_GATES` 全集)讀不到它,治理帳統計會漏算這條機制的放行/擋下次數,跟現有「新閘要登記進 `_KNOWN_GATES` 才進統計」的慣例脫節。

為什麼是設計問題:設計稿自己立的規矩是「九成工作是讀節點 + 比對既有判定結果,不需要新的判定引擎」,但唯獨對「成員帳怎麼寫」這件事完全沒有交代要接哪個既有寫入口——這正是「自己再刻一份已有的機制」的典型徵兆,而且是在「現況盤點」明明已經展示過盤點方法論、卻獨漏這一項的情況下發生。這不是實作細節(用哪個函式名),而是架構層級要先講清楚「這本新帳走哪個既有寫入口、要不要登記進 `_KNOWN_GATES`」,否則實作時很可能各自為政多開一套。
