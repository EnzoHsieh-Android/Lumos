# 殺傷力驗證編譯快取誤判_計劃

白話:`lumos guard kill` 在同一個隔離工作樹裡一條接一條「把程式改壞 → 跑綁定測試 → 還原」。測試工具如果靠「檔案修改時間(到秒)+ 大小」判斷要不要重新編譯(Python 的編譯快取、macOS 內建的 make 就是),兩次寫檔落在同一秒、大小又一樣,後一次就拿到前一次留下的編譯結果——實際跑的不是這一條的壞法。誤判是雙向的:一條根本沒傷害的壞法被判成殺得掉(假的「合約有守住」),一條真的會傷到合約的壞法也可能吃到原檔的快取被判成沒殺掉。修法:每次寫檔(套壞法、還原)之前,如果現在跟上一次寫檔或上一次跑測試結束落在同一秒,就等到下一秒再寫——寫出來的修改時間是真實的、而且每次都不同秒,任何靠修改時間的快取都會重編;不把時間設到未來。

依據:
- [[Issues/guard kill在Python專案會沿用編譯快取誤判殺得掉]](殺傷力配方修補體驗代碼審第 1 輪的審查員回報;rtb=另一個用 lumos 的消費專案)。
- 編排者 2026-10-01 重現(改動前版本、本機):`_mk_kill_env` 的 repo,同一篇兩條配方指 `prod.py`——第一條 `LIMIT = 5` → `LIMIT = 99`(讓測試紅)、第二條 `def check(n):` → `def check(n): `(無害,多一個空白,改完跟第一條一樣多一個字)。第二條單獨跑 5/5 判 survived;排在第一條後面 5/5 判 killed。兩條改完檔案大小相同是必要條件(兩條都改成同長度、跟原檔一樣大時沒重現)。本機的 `python3` 是 macOS 內建 3.9,編譯快取寫在 `~/Library/Caches/com.apple.python/<絕對路徑>`,不在工作樹的 `__pycache__`;手動在兩條之間睡 1.5 秒誤判就消失。
- 兩種修法在複本上各跑 5 次都修好(5/5 判 survived):甲=跑測試時設 `PYTHONDONTWRITEBYTECODE=1`;乙=寫入壞法後把檔的修改時間設成嚴格遞增的未來時間。過程中編排者的重現腳本一度寫錯(參數被清空、兩次「測修法」跑的都是原版),修正後才得到這個結果。
- 設計審第 1 輪正確性席實測:乙(未來時間)會造出新的假 killed——綁定測試或被測程式拿檔案修改時間跟「現在」比(例:檔沒改過就回 304)時,一條傷不到合約的壞法改後 3/3 判 killed;改成「設完等時鐘追上才跑」全部判對。本計劃因此改成「等到下一秒再寫」(丙),不設未來時間。
- Enzo 2026-10-01 裁定路線圖順序「1a-4 → 代碼審修正關卡 → 1a-3 → 1b」,本計劃是 1a-4。

PRIOR-ART: ①Python 的編譯快取預設以「原始檔修改時間(秒)+大小」判斷是否過期(PEP 552 另有以內容雜湊判斷的模式,但要改產生快取的方式,工具鏈管不到使用者專案);make 以修改時間比較目標與來源(GNU make 在支援奈秒時間戳的檔案系統上看得出同一秒內的先後;在只到秒的檔案系統上同一秒內不會重編)。②突變測試工具多半每個突變獨立一份工作目錄或在記憶體裡換掉程式,本專案的 guard kill 是共用一份隔離工作樹逐條改,所以要自己處理快取。③裁定=丙(每次寫檔前等到跟上一次寫檔、上一次測試結束都不同秒,修改時間用真實的):不限 Python,make 這類靠修改時間的也一起蓋到,而且不設未來時間(乙會造出新的假 killed,見依據);甲只對 Python 有用,而且 `_kill_run` 還有其他 3 處呼叫(guard kill 自己的 baseline、合約測試閘的跑測試、一處探針),改它的環境會波及。Issue 原本建議甲(或清快取),這裡改選丙,Issue 跟著補一句。代價:每條配方最多多等約 2 秒(套壞法與還原各最多 1 秒)。
RETIRE-IF: guard kill 改成每條配方各自一份全新工作樹(或在記憶體裡換掉程式)時,這段就可以拿掉。

## 範圍

- 做:guard kill 每次寫檔(套壞法、還原)之前,如果現在跟同一組上一次寫檔或上一次跑測試結束落在同一秒,就等到下一秒;寫完把修改時間讀回來,跟上一次寫檔落在同一秒(檔案系統只到 2 秒,例:FAT)就再等、再碰一次(`os.utime(path)` 不帶時間=設成現在),最多重試 3 次。
- 不做:不改合約測試閘與其他呼叫 `_kill_run` 的地方;不把任何檔的修改時間設到未來;不改 guard kill 的判法、回傳碼、`--json` 輸出;不清使用者專案的快取資料夾。

## 做法

- 在 `cmd_guard_kill` 每個平台組開工作樹之後,記「這一組上一次寫檔的秒」與「上一次跑測試結束的秒」(都從 0 開始;baseline 那次跑完也記)。
- 新增一支小函式 `_kill_wait_new_second(state)`:`while int(time.time()) <= max(上一次寫檔的秒, 上一次測試結束的秒): sleep(0.05)`。
- 套壞法:等(上一支函式)→ 寫檔 → 讀回修改時間;`int(修改時間) <= 上一次寫檔的秒` 就等 1 秒、`os.utime(path)`(設成現在)再讀回,最多 3 次 → 記下這次寫檔的秒。
- 跑完測試記下結束的秒。
- 還原:等 → `git checkout -- <file>` → 讀回修改時間,同上補碰 → 記下。
- 重試 3 次還是同一秒(極少見)就印一行提醒到標準錯誤(照 kill-log 寫入失敗那條的寫法,固定走標準錯誤、不汙染 `--json`)、照常跑,並把這條結果的 `weak` 設成 true(弱證據,不當背書)。
