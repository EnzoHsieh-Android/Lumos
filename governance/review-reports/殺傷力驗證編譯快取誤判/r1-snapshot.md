# 殺傷力驗證編譯快取誤判_計劃

白話:`lumos guard kill` 在同一個隔離工作樹裡一條接一條「把程式改壞 → 跑綁定測試 → 還原」。測試工具如果靠「檔案修改時間 + 大小」判斷要不要重新編譯(Python 的編譯快取就是),兩條壞法改完的檔大小一樣、又落在同一秒內,第二條就會拿到第一條留下的編譯結果——實際跑的是第一條的壞法。一條根本沒傷害的壞法因此被判成殺得掉,等於假的「合約有守住」。修法:每次寫入壞法後,把那支檔的修改時間設成「比現在晚、也比上一條壞法晚」的時間,讓任何靠修改時間的快取都一定重編。

依據:
- [[Issues/guard kill在Python專案會沿用編譯快取誤判殺得掉]](殺傷力配方修補體驗代碼審第 1 輪的審查員回報;rtb=另一個用 lumos 的消費專案)。
- 編排者 2026-10-01 重現(改動前版本、本機):`_mk_kill_env` 的 repo,同一篇兩條配方指 `prod.py`——第一條 `LIMIT = 5` → `LIMIT = 99`(讓測試紅)、第二條 `def check(n):` → `def check(n): `(無害,多一個空白,改完跟第一條一樣多一個字)。第二條單獨跑 5/5 判 survived;排在第一條後面 5/5 判 killed。兩條改完檔案大小相同是必要條件(兩條都改成同長度、跟原檔一樣大時沒重現)。本機的 `python3` 是 macOS 內建 3.9,編譯快取寫在 `~/Library/Caches/com.apple.python/<絕對路徑>`,不在工作樹的 `__pycache__`;手動在兩條之間睡 1.5 秒誤判就消失。
- 兩種修法在複本上各跑 5 次都修好(5/5 判 survived):甲=跑測試時設 `PYTHONDONTWRITEBYTECODE=1`;乙=寫入壞法後把檔的修改時間設成嚴格遞增的未來時間。過程中編排者的重現腳本一度寫錯(參數被清空、兩次「測修法」跑的都是原版),修正後才得到這個結果。
- Enzo 2026-10-01 裁定路線圖順序「1a-4 → 代碼審修正關卡 → 1a-3 → 1b」,本計劃是 1a-4。

PRIOR-ART: ①Python 的編譯快取預設以「原始檔修改時間(秒)+大小」判斷是否過期(PEP 552 另有以內容雜湊判斷的模式,但要改產生快取的方式,工具鏈管不到使用者專案);make 以修改時間比較目標與來源(GNU make 在支援奈秒時間戳的檔案系統上看得出同一秒內的先後;在只到秒的檔案系統上同一秒內不會重編)。②突變測試工具多半每個突變獨立一份工作目錄或在記憶體裡換掉程式,本專案的 guard kill 是共用一份隔離工作樹逐條改,所以要自己處理快取。③裁定=乙(修改時間嚴格遞增):不限 Python,make 這類靠修改時間的也一起蓋到;甲只對 Python 有用,而且 `_kill_run` 還有其他 3 處呼叫(合約測試閘的跑測試與兩處探針),改它的環境會波及。Issue 原本建議甲(或清快取),這裡改選乙,Issue 跟著補一句。
RETIRE-IF: guard kill 改成每條配方各自一份全新工作樹(或在記憶體裡換掉程式)時,這段就可以拿掉。
REVISIT:2026-10-15 跟 rtb 回報同一天,看 rtb 那邊 guard kill 有沒有因為修改時間在未來而冒出新的警告或錯誤(例:make 印的時鐘偏差警告、測試因時間比對而失敗)。

## 範圍

- 做:guard kill 每次把壞法寫進檔之後、以及還原之後,都把那支檔的修改時間設成嚴格遞增的未來時間(至少比現在晚 1 秒、也比同一組上一次設的晚 1 秒)。
- 不做:不改合約測試閘與其他呼叫 `_kill_run` 的地方;不改 guard kill 的判法、回傳碼、`--json` 輸出;不清使用者專案的快取資料夾。

## 做法

- 在 `cmd_guard_kill` 每個平台組開工作樹之後,記一個「這一組上一次設的修改時間」(初始 0)。
- 套壞法那一步寫完檔之後:`新時間 = max(現在 + 1 秒, 上一次 + 1 秒)`,用 `os.utime` 把那支檔的存取與修改時間都設成新時間,記下來。
- ★還原(`git checkout -- <file>`)成功之後也照同一條規則設一次★(前置掃描實測:測試跑超過 1 秒時,還原寫回的修改時間會等於剛才設給壞法的未來時間,原檔又跟壞法一樣大時,還原後的檔吃到壞法的快取——下一條配方改的是另一支檔、測試卻 import 這支時就誤判)。
- 設時間失敗(`os.utime` 丟出 OSError)不擋:印一行提醒到標準錯誤,照常跑測試(結果可能吃到舊快取,提醒裡寫明)。測試以行程內呼叫 `cmd_guard_kill`、把 `os.utime` 換成丟 OSError 的替身來製造。

## 條款

- [S1] 當同一篇兩條配方指同一支 Python 檔、第一條壞法讓綁定測試變紅、第二條壞法無害而且改完的檔跟第一條一樣大時,guard kill 對第二條應判 survived(不應沿用第一條的編譯結果判成 killed) [test:t_guard_kill_no_stale_build_cache]
- [S2] 當 guard kill 套上壞法、或還原之後,那支檔的修改時間應比當下晚、也比同一組上一次設的時間晚;第一條改 a、第二條改 b、測試同時 import a 與 b 時,第二條的判定不應受第一條影響 [test:t_guard_kill_no_stale_build_cache]
- [S3] 當設修改時間失敗時,guard kill 應在標準錯誤印一行提醒並照常跑完,判定與回傳碼的規則不變 [test:t_guard_kill_no_stale_build_cache]

## 回退

- revert 實作提交:guard kill 回到不設修改時間,舊的誤判會回來;筆記與配方都不受影響。
- revert 之後本計劃條款綁的 `[test:]` 會懸空,status 改 superseded 或在〈實作紀錄〉記一句「已撤回」。

## 實務隱患

- **未來時間**:工作樹裡被改的那支檔修改時間會比現在晚幾秒;make 會印「時鐘偏差」警告(Python、Gradle、jest、go 不會),不影響判定;工作樹是暫存的,跑完就刪,不會留到使用者的工作目錄。
- **測試靠時序**:S1 的測試要在一秒內連跑兩條才會重現,本機實測 5/5;CI 機器較慢時可能剛好跨秒而照綠(假綠,不會假紅)——S2 直接檢查修改時間,不靠時序,兩條一起才釘得住。
- **既有測試**:`t_guard_kill*` 只比對判定與輸出字面,設修改時間不影響;文件守衛測試從 `cmd_guard_kill` 原始碼抽 verdict 值域,別新增 `"verdict": "…"` 字面。
- 已排除:金流:不碰任何付款或計費
- 已排除:對外送出:只改本機暫存工作樹裡的檔案時間,不連網
- 已排除:不可逆:只在 guard kill 自己的暫存工作樹裡設時間,跑完就刪;revert 就回得去
- 已排除:守衛面:判法與回傳碼不改,只讓測試真的跑到壞法;不擋推送或提交
