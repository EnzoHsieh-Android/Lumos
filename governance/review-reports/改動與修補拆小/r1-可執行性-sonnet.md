severity: major

派工詞尾端沒有附到固定席節點,所以沒有逐條判的對象,這點請編排者確認。以下依「照字面實作」鏡頭,對 `/tmp/改動與修補拆小-r1.md` 和 `Word-wild-search-rst` 的真實帳本、卷證做的實測。實測範圍是 `docs/.canary-log.jsonl` 裡 `code-` 開頭的 2354 列(277 個迴圈),加上 `governance/review-reports/` 下的檔案。

**F1 凍結 patch 的「不含 `+++` 檔頭」濾法會丟掉真實內容行,檔案歸屬也沒指定取法**

引句:「以 `+` 開頭、不含 `+++` 檔頭的內容行,扣掉第 N-1 輪已有的同內容行(逐行序列比對);所屬檔案是簿記的不算。」

severity: major
blocking: 是

- 照字面,寫法最自然的是「`startswith('+') and not startswith('+++')`」。
- 實測:全部 `r*-snapshot.patch` 裡,有 58 行非簿記檔的真實新增內容以 `+++` 開頭。其中 43 行在 `scripts/test_lumos.py`,內容是測試裡嵌的 patch 文字。其餘在 `governance/eval/results/*` 的 fixture。
- 簿記目錄(`governance/review-reports/` 的卷證檔)裡更多。凍結 patch 常夾帶別的卷證檔,像 `++++ b/app/Real.kt` 這種行很常見。
- 反過來,若實作者改用「看到 `+++ ` 就當檔頭」來判歸屬,這些內容行會被誤認成新檔頭,把後面的行算到錯的檔上。簿記判定因此失準。
- 檔頭的取法也沒寫:
  - 該認 `diff --git` 行還是 `+++` 行?
  - 非 ASCII 路徑在 patch 裡是 `diff --git "a/..."` 的加引號形式(實測 19 個 patch 有),要怎麼解?
  - 刪檔是 `+++ /dev/null`,新檔是 `--- /dev/null`,rename 沒有 hunk。
  - 另有 43 處 `Binary files` 或 `GIT binary patch`。
  - 另有 2614 處 `\ No newline at end of file`。
- 應該寫成:以 hunk 的 `@@ -a,b +c,d @@` 計數逐行消耗,只有檔頭區段才認 `---`/`+++`。檔案歸屬取 `diff --git` 行(含引號形式),以及 binary、`\ No newline` 的處理。測試要放一條「內容以 `++` 開頭」的新增行。

**F2 「扣掉上一輪已有的同內容行(逐行序列比對)」有至少三種合理實作,結果不同**

引句:「扣掉第 N-1 輪已有的同內容行(逐行序列比對)」

severity: major
blocking: 是

- 這句有三種讀法,數字會不同:
  - 全域多重集合相減。
  - 逐檔相減。
  - 對整個新增行序列做 LCS(最長共同子序列)。
- 空白行、`+    return`、`+}` 這類行在不同檔裡內容相同。全域相減會把「修補在 B 檔新加的 `}`」扣掉,因為上一輪 A 檔有同樣的行。
- 這個數字是整份計劃的主自變數,四分組、勝算比、邏輯迴歸全吃它。
- 實測:r2 的 patch 是相對 merge-base 的累積 patch,不是增量(`code-ablation-probe` r1 有 750 個 `+` 行、r2 有 959 個)。所以必須相減沒錯,但要明講用哪一種。
- 有些迴圈目錄還有 `r3-delta.patch`(增量 patch)或 `r3-s3-snapshot.patch`(分席 patch)。「第 N 輪凍結材料 `rN-snapshot.patch`」只認前者,沒說後兩者怎麼處理。
- 應該寫成:逐檔、以(檔路徑, 行內容)的多重集合相減。並說明檔被 rename 時怎麼辦。

**F3 配對缺一輪、缺 patch 的處理沒寫,真實資料裡很常見**

引句:「單一凍結 patch 或席報告讀不了、超過大小上限 → 那一輪進 `skipped` 附原因,不補值、其他照算。」

severity: major
blocking: 是

- 實測:632 個(迴圈, 輪)裡有 99 個沒有 `rN-snapshot.patch`,34 個迴圈根本沒有卷證目錄。
- 修補新增行數需要 N 和 N-1 兩份 patch。缺 N-1 時:
  - 是跳過第 N 輪,還是把 N-1 當空集合?(後者會把整份累積 patch 算成修補,數字爆大。)
  - N+1 輪的「上一輪折入數」要不要連帶丟?
  - 計劃只說「那一輪」進 skipped,沒定義配對鍵。
- 輪次不連續也存在:`code-audit-batch8` 和 `code-外家審計定位` 只有 r2。另外 36 列的 `round` 是 `null`。
- 「帳上輪數 3 以上叫跑滿三輪」沒說輪數是看「有幾個不同 round」還是「最大 N」。不連續時兩者不同。
- 應該寫成:配對鍵是(迴圈, N),要求 N 與 N-1 兩份 patch 都在;缺任一份就整對進 skipped,附原因。跑滿三輪取 max N,或明寫以 distinct 計。

**F4 席報告的 `severity:` 解析對真實報告大量不成立,「怎麼辦」沒寫**

引句:「檔首第一個 `severity:` 行之後,每個頂格的 `severity: <值>` 行開始一條發現,到下一條為止」

severity: major
blocking: 是

- 實測:在有 `report_path` 的 2225 列裡,2 列檔案不存在。其餘 2223 列中:
  - 約 2025 列檔案第一個非空行就是 `severity:`,格式相符。
  - 約 135 列有 `severity:` 行但不在檔首。
  - 54 列完全沒有頂格 `severity:` 行。
- 沒有該行的例子:
  - `code-delguard/r1-s2.md`:發現寫成 `## F2(major)… 引句:「…」`。
  - 載體席的 `…-判讀.md`(例 `code-resid-adv/r1-判讀.md`)沒有 severity 行,屬於彙整檔。
- 照字面實作,這些報告會解出 0 條發現。那就等於「沒有 major」,把這輪的下一輪 major 偏低、悄悄混進分母。
- 計劃只說讀不了進 skipped,沒說「讀得了但解不出發現」算什麼。
- 應該寫成:解出 0 條發現但報告含 `引句:` 或 `(major)` 字樣時,進 skipped 附原因 no-parse,不當作 0 major。
- 同一份報告的嚴重度還有另一個問題。`F3(major→編排者降 minor)` 這類被編排者降級的條目,取原始等級還是降後等級,沒定。
- 報告裡還有 `【canary,不計】` 的植入故障條目(例 `code-delguard/r1-s2.md` 的 F1 blocker)。字面規則會把它算成真 blocker,拉高「下一輪 major 比例」。要明講排除。

**F6 `--since` 的日期時區沒定,實測會讓約兩成迴圈換組**

引句:「迴圈依首筆帳的 `ts` 日期分成之前、之後兩組」

severity: major
blocking: 是

- 實測:`ts` 全是帶 `+08:00` 的 ISO 字串。把首筆 `ts` 轉 UTC 後日期會變的有 60 個,佔 277 個迴圈的約 22%。

- 「首筆」也要定義:實測檔案順序等於 `ts` 順序,但字面沒保證。
- 還有一點:`--since 2026-10-15` 的邊界日算「之前」還是「之後」,沒寫。
- 應該寫成:取 `ts` 字串前 10 碼(帳上的本地日期),`>= since` 為之後組。並寫進 `--help`。

**F7 簿記判準「直接載入 `scripts/lumos`」的失敗模式與可測性沒給**

引句:「簿記判準直接載入 `<repo>/scripts/lumos` 讀 `_BOOKKEEPING_FILES` 與 `_BOOKKEEPING_DIRS`(同 `scripts/test_lumos.py` 載入主程式的做法),不在工具裡另抄一份;載入失敗 rc 2。」

severity: major
blocking: 是

- 實測:`SourceFileLoader` 載入 `scripts/lumos` 約 2.3 秒,目前能載入。這是 exec 整支 4 萬多行的主程式,有模組級副作用的風險。
- 測試用的「小型假 repo」要有 `scripts/lumos`。測試只能複製真檔(會綁住測試與主程式)或寫個假檔(假檔就是計劃禁止的第二套判準)。計劃沒選。

**F8 統計段在小樣本與退化輸入下行為沒定義,而 90 秒逾時和固定種子都要靠它**

引句:「邏輯迴歸(log2 修補行數、log2 上一輪折入、第 3 輪以後、分級 high),以迴圈為單位重抽 `--bootstrap` 次(預設 500,固定種子)取 95% 區間」

severity: major
blocking: 是

- 零依賴(純 stdlib)下要自己寫 IRLS(迭代重加權最小平方法)。計劃沒提這些情形的處理,兩個人會寫出不同結果:
  - 完全分離或不收斂(重抽小樣本很常見)。
  - 單一類別(全 0 或全 1)。
  - `log2(0)`:修補行數可能是 0,折入數也可能是 0。
  - 設計矩陣奇異,例如假 repo 裡沒有 `high` 分級。
- 失敗的重抽要略過、計入失敗數,還是回傳 null,沒寫。
- 「依排序等量切四組」遇到大量同值(0 行修補、折入數 1)時,切點怎麼處理沒寫。
- 「層內以中位數分大小兩半」遇到等於中位數的值時,算哪一邊沒寫。
- MH(Mantel-Haenszel)勝算比遇到零格要不要加 0.5 修正沒寫。
- 固定種子:未指定是 `random.Random(固定整數)` 還是對輸入雜湊。雜湊的話,同帳本不同次序會不同。
- S3 的「整組在 90 秒內跑完」以 `--bootstrap 50` 的假 repo 驗,但真實帳本是 277 個迴圈乘 500 次重抽、純 Python IRLS。沒有任何條款量過真資料的耗時。
- 另外,載入 `scripts/lumos` 光自己就占 2.3 秒。

**F9 引句落點判定的比對域沒講清,實測「兩邊都有」「錨不到」佔比不小**

引句:「那段裡 `引句:「…」` 的內容去掉空白後,只出現在第 N 輪新改的行 → 差異內,只出現在沒變的行 → 差異外,兩邊都有、沒引句、錨不到各自另計。」

severity: minor
blocking: 否

- 「第 N 輪新改的行」只出現一次,沒說比對對象是「patch N 減 patch N-1 的新增行串接」還是「逐行」。
- 實測用「全部新增行去空白後串接」的比對:r2、r3 的 2089 條引句中:
  - 1802 條錨得到新增行。
  - 100 條只在上下文行或刪除行。
  - 187 條兩邊都不在。
- 跨行的引句只有串接比對才找得到,逐行比對會把它們全判成錨不到。
- 引句本身常帶 patch 前綴 `+`(例 `引句:「+    scratch = tempfile.mkdtemp(…)」`)。去空白後前綴 `+` 還在,所以要先剝前綴再比。
- 「兩邊都有」只要引句很短就會成立,沒有最短長度。
