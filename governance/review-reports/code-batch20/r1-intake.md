★這支只有一個來源,而那個來源的沉默被它當成了「沒發生過」。★

## 編排者自己重現的(≥major 一律自己查過才折)

外家席全部標「讀碼推論,未實跑」(唯讀沙盒建不了暫存檔),所以每一條我都自己造現場敲過:

1. **健康檔的完成時間在未來 → 監看器完全失明**(f1,blocker)。
   餵一份 `finished_at` 在五小時後、五步全 0 的健康檔:★整支沒有任何輸出★。
   年齡算出來是負數,既不算逾期也不算讀不動,直接落進「沒事」。**HIT。**
2. **鎖齡量不出來 → 被當成「正在跑、沒事」**(f2,blocker)。
   現場:鎖在、pid 活著、指令名對得上、鎖齡 72 小時,但 python3 壞掉
   (launchd 那種精簡環境真的會遇到)→ ★卡了 72 小時一聲不吭★。**HIT。**
3. **「完成」沒有綁定整行**(f4 / 通才 F1,major)。
   我餵一行「⚠ daily-governance wrapper **完成不了**,要人來看」——它判成跑完了。
   ★方向是把真警報降級成沒事★,正是這支不能有的方向。**HIT。**
   (通才席獨立用一模一樣的手法命中,而且它另外查到:那份紀錄檔是 stdout 與 stderr 共用同一個檔,
   所以任何被印出來、恰好含那四個字相鄰的訊息都會被誤收——這條佐證比我的更完整。)
4. **無上限掃描**(f3,major)——**這條我推翻了它一半的推論**。
   它說「單次監看可能長時間不結束並一直持有看門狗鎖」。我把紀錄檔養到 68 MB 實測:
   **0.9 秒**(通才席獨立量到 0.38 秒,同一個量級)。而這個檔每天大約長 1 KB,
   ★要一百多年才會到那個大小★。**所以「會卡死」量不出來**;但「沒有上限」本身是真的,
   而加上限只要兩行,照折。**帳上記的是實測數字,不是它的推測。**

## ★架構席兩條 major 都是機械可查的,我複驗過★

- **A1 第二個來源的路徑只有讀的那一側寫死**,而真正的權威是 `~/Library/LaunchAgents/`
  底下那份排程設定的 StandardOutPath ——**那份檔不進版控**。
  我查:`daily-wrapper.log` 這個字串在產出側出現 **0** 次、在讀取側出現 1 次。**HIT。**
  處置:兩邊都宣告同一條路徑 + 守衛比對(`t_wrapper_log_path_agrees`)。
  ★誠實記:這只把「單邊猜測」變成「雙邊約定」,擋不住有人去改那份排程設定★——
  它不在版控裡,這個 repo 看不到它。已寫進碼與圖譜,掛 REVISIT:2026-12-08。
- **A2 我引進了全 repo 唯一一處沒有時區的時間比較**。
  我查:`strptime` 在 `governance/*.sh` 與 `scripts/lumos` 裡只出現在我這一處;
  `fromisoformat` 在 `scripts/lumos` 出現 18 次、在這支出現 1 次。**HIT。**
  處置:`strptime(...).astimezone()` 接回既有那一套,同一個檔不再養兩套。
