## 方法說明

## Findings

### F1 — 正則吃過頭:把「完成不了」的錯誤訊息誤判成「完成事件」(major, blocking: 是)

file: `governance/wrapper-watchdog.sh:156`(對照 patch 第 67 行)
引句:「m = re.match(r"^\[(\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2})\].*wrapper 完成", ln)」
`.*wrapper 完成` 只要求子字串出現,不要求那四個字是那一行的結尾。實跑證明:餵這一行

```
[2026-09-08 00:34:21] ⚠ daily-governance wrapper 完成不了,第 3 步逾時,人工介入中
```

看門狗真跑後印出:

```
每日治理 wrapper 有在跑(它自己的紀錄檔:最後一次完成 2026-09-08 00:34:21),但沒有留下健康狀態檔——這支看門狗因此看不到它的結果。
```

「完成不了」——一句正在講「壞了」的話——被讀成「完成」。方向正是這支腳本自己聲明不能有的:把一個真警報訊號降級成「大概沒事,只是缺個檔案」。這個字串目前不會被 `daily-governance.sh` 現有的唯一一行 `echo "[$(ts)] daily-governance wrapper 完成"`(daily-governance.sh:278)誤觸,但 `daily-wrapper.log` 是 launchd plist 的 `StandardOutPath`**與** `StandardErrorPath` 共用同一個檔(我讀了 `~/Library/LaunchAgents/com.enzo.lumos.daily-governance.plist`,兩個 key 指向同一路徑),任何未來被印到 stdout/stderr、恰好含有「wrapper 完成」四字相鄰的訊息(包括這種「完成不了」的錯誤句)都會被誤收。

### F2 — 未來時間戳(負秒數)沒有被擋掉(major, blocking: 是)

file: `governance/wrapper-watchdog.sh:168-169`(對照 patch 第 79-80 行)
引句:「print(int((datetime.datetime.now()-d).total_seconds()))" "$1" 2>/dev/null || echo ''」
沙箱餵一行「10 小時後」的完成時間戳,`secs_since_local` 算出負數(例如 `-36000`),而 `[ "$ls_" -le "$STALE_SEC" ]` 對負數一樣成立(POSIX `[` 認負整數),於是被判成「最近才跑完」。實跑輸出:

```
每日治理 wrapper 有在跑(它自己的紀錄檔:最後一次完成 2026-09-08 11:34:43),但沒有留下健康狀態檔——…
```

當時的實際時間是 `2026-09-08 01:34:43`——訊息裡的「完成」時間比現在晚了 10 個小時,原封不動印給人看。時鐘被調過、有人手貼一行未來時間、或系統時間被 NTP 大幅校正,都會踩進這條。这不是「不喊」(仍然有訊息),但它會用一個不可能成立的時間戳把「有在跑」講得煞有介事,而如果當時 wrapper 真的從來沒跑完過,這個假象會蓋掉更準確的「從來沒跑完過」警報。同一份 diff 裡緊接著讀健康檔那段(`wrapper-watchdog.sh:236-240`)算 `age` 時也沒有擋負數,是同一個洞的第二個入口,只是那段本來就不是這批新加的程式碼(既有 `read_health` 邏輯),所以我只把它列在這裡當佐證,不重複開一條 finding。

### F3 — 測試沒有驗證「取最後一筆完成,不是第一筆」(minor, blocking: 否)

file: `scripts/test_lumos.py:29954`,場景②在 29990-30004 行
引句:「r = _run()」
        check("★紀錄檔說最近才跑完 → 不准講「從來沒跑完過」★",」

我對 `wrapper_log_last_finish()` 做了個 mutant:找到符合的行就 `break`(改成「取第一筆」而不是「取最後一筆」)。跑 `t_wrapper_watchdog_no_health_but_wrapper_ran` 五個場景全綠,mutant 沒被任何斷言抓到:

```
7 passed, 0 failed
```

追查發現:實際跑碼(未被 mutant 動過)是正確的——因為迴圈裡沒有 `break`,每次比對成功就覆蓋 `last`,append-only 的紀錄檔本來就保證後面的行時間更新,所以「不 break」天然等於「取最後一筆」,我另外真跑「第一筆 80 小時前、第二筆 2 小時前」的紀錄檔驗證過,程式確實回報 2 小時前那筆。**這不是活著的 bug,是測試覆蓋的洞**:目前五個場景都只放一筆「完成」,沒有一個場景放兩筆以上驗證順序,所以任何把「取最後」改成「取第一」的未來改動都不會被這支測試擋下來。

### F4 — bundle 識別碼「換版本號」規則沒有機械保證(minor,讀碼推論,未實跑,blocking: 否)

file: `governance/install-watchdog.sh:54`,測試在 `scripts/test_lumos.py:30269`
引句:「NOTIFIER_ID="com.enzo.lumos.watchdog-notifier.v3"」
引句:「換識別碼是唯一逼它重讀的辦法)。圖示邏輯以後再動,這個號要往上加。」
這句規則寫的範圍是「以後動圖示邏輯,這個號要往上加」——不是「每次重建都要換號」(這批只是照這條既有規則,把 `.v2` 換成 `.v3`,這個換動作本身沒有問題)。但我查了唯一相關的測試(`scripts/test_lumos.py:30269`):

```python

```

這只驗證「識別碼長得像帶版本號」,不驗證「這次改動有沒有真的把號往上加」。也就是說,如果下次有人真的動了 `sips`/`iconutil` 那幾行卻忘了把 `.v3` 改成 `.v4`,這支測試照樣綠燈,同一顆「快取吃到舊圖示」的雷會用完全相同的方式再炸一次,而且不會有任何機械訊號。我沒有實跑 `install-watchdog.sh`(會對這台機器上真實安裝、正在跑的 `com.enzo.lumos.wrapper-watchdog` 通知 app 動手,重新註冊 LaunchServices、跳出真通知、可能要求重新授權——風險/收益不成比例,故意不跑,標記讀碼推論)。

### 檢查過但沒問題的項目

- **fail-safe 方向的結構性檢查**(item 4):我把 `elif [ ! -f "$HEALTH" ]` 這個分支的兩個子分支都讀過一遍——`now_state="nohealth|..."` 和 `now_state="never|..."` 兩條路徑都無條件把 `msg` 設成非空字串。這個分支結構上**沒有第三條路徑**能落到「不設 msg / 不喊」,所以無論 `wrapper_log_last_finish` 或 `secs_since_local` 內部哪個 `|| echo ''` 被觸發(紀錄檔不存在、python3 壞掉、時間解析失敗、`[ ]` 對非數字報錯),最終都只會在「有在跑但沒健康檔」和「從來沒跑完過」這兩個都會發通知的狀態之間切換,不會消音。這點我認為是這批修法裡設計最紮實的部分。
- **非 UTF-8 位元組**:沙箱塞入含 `\xff\xfe` 的行,搭配一行正常的完成紀錄,`errors="replace"` 正確吞掉壞位元組、正常抓到完成時間,沒有拋例外、沒有讓 `except OSError` 意外吃掉整個結果。
- **半行寫入(模擬併發寫)**:紀錄檔尾端故意留一行寫到「…wrapper 完」就斷掉(缺「成」字),程式正確判定「沒有完整的完成行」,回報「從來沒跑完過」——方向正確(多喊不少喊)。
- **無上限檔案掃描**:把紀錄檔灌到 68MB/50 萬行,真跑量到 0.38 秒,不是效能問題;沒有上限這件事本身是真的,但目前量不出會卡死的門檻。
- **有人手動塞一行假的完成紀錄**:會把「從來沒跑完過」降級成「有在跑但沒健康檔」,但兩者都還是會發通知,不會被吞成靜默——只是這條路徑對紀錄檔內容零信任檢查,值得知道但不到 major。
- **時區/DST**:這台機器 `date +%Z` 是 `CST`(`Asia/Taipei`),不用夏令時間,`secs_since_local` 用 naive local time 相減在這個部署環境下不會因 DST 跳動出錯;沒有把這個列成正式 finding。
- **regex 抓「開始」誤判成「完成」**:mutant 把 regex 放寬到只要 `.*wrapper`(不要求「完成」)就被場景④的斷言抓到,證明這條防線是真的有殺傷力,不是空殼。
- **`t_wrapper_watchdog_no_health_but_wrapper_ran` 其餘四個斷言**:對 mutant A(整個 log-fallback 邏輯關掉,模擬功能沒做)、mutant B(拿掉 36 小時門檻判斷)都能正確翻紅,證明測試不是全面假綠,只有 F3 提到的「取最後一筆」語意沒被覆蓋。

## 給文字版總結

這支看門狗要解決的問題本身(健康檔不在時不要亂喊「從來沒跑完過」)修法方向是對的,而且我驗證過它的 fail-safe 骨架很紮實——任何內部小函式失手都會被結構性地兜回「還是要喊」而不是「悄悄放行」。真正的洞在細節:認「完成」的正則太鬆,會把一句「完成不了」的錯誤訊息認成完成事件;判斷時間新舊時沒擋未來時間戳,一個被調亂的時鐘或一行手誤貼上去的假紀錄,都能讓它印出一個不可能成立的完成時間。這兩點都不會讓警報完全消失,但都會讓警報講錯話——而這支腳本存在的唯一理由就是「講對話」。
