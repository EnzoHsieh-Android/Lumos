| 你在想… | 敲 |
|---|---|
| 這件事為什麼這樣 / 圖譜記了嗎 | `lumos search <詞>` → `lumos context <節點>`;0 命中先換同義詞;**中文概念之間加空白**(`作廢 收回 點數`,別黏成一句) |
| 動這段有什麼不能碰 | `lumos contracts <節點>` |
| 要讀全文再下結論 | `lumos show <節點>`(search 只給索引行;拿摘要判「沒記」以前真的錯過——值在筆記第 64 行,靠摘要判成沒有) |
| 篩條件(金流 / 未收案 / 連到 X) | `lumos query --tag 家族/值 [--active] [--linked <節點>]` |
| 開工掌握現況 | `lumos query --tag status/doing`;`lumos recent --days 7` |
| 圖譜空或稀疏(接手 brownfield) | 走節點還原 SOP:`commands/09-節點還原.md`(七步;需要才產節點、有就照慣例用) |

看到筆記有 `core_refs:` 或 `CORE:` → 權威在跨專案核心圖譜,改那邊(`lumos-core-knowledge` skill)。
**查得到才算先行**(Landmark 實測):0 筆看「逐詞覆蓋」標 ★ 的詞換同義詞,換三次再問人,別轉 grep;大節點先 `--brief`;單篇內部新舊打架時摘要有日期的 KEY 行 > 正文,衝突影響決策去 code 裁再回頭修。
**分清你在哪種 session**:本機 Claude Code(含手機/網頁遙控本機)有本機 git 憑證、能 push;網頁版 claude.ai/code 是雲端沙盒,對主分支沒 push 權、只能推 feature branch——「遙控」不等於「遠端版」,曾騙到 AI 一次。
被催「直接改、不用解釋」也一樣:不解釋可以,不查不行——改 code 前至少 `lumos impact --file <檔>` 一行。

## 2. 動手前

- `lumos impact --file <檔>` / `--diff <範圍>`:哪些筆記、驗證、決策會受影響(Edit 前 hook 也會塞一份,但只推你碰到的檔)。
- `lumos pitfalls --diff <範圍>`:風險分級;`tier: high` 要過代碼審(`lumos-code-loop`)。
- 要刪 / 改名東西:`lumos search <舊名> --code` 逐句判哪些筆記還在講它。
- 改了環境 / 流程 / 設定(版本、金鑰、hook、排程):`lumos stale --candidate --match <關鍵字>` 列出寫了「改到這個就該重驗」的驗證紀錄。
- 設計、spec、計劃一律寫成 `Projects/<主題>_計劃` 筆記(`type: project`),不寫到別的路徑;動筆前一行 `PRIOR-ART:`(最小解在哪層 / 世界解過沒 / 借用‧自建‧採用)。

## 3. 寫回(同一次工作內;pre-commit 擋「改 code 沒動圖譜」)

| 要做 | 敲 |
|---|---|
| 新筆記 | `lumos new <system\|issue\|verification\|project> <名>`;驗證紀錄加 `--plan <計劃> --systems <節點>` 自動雙向連 |
| 改狀態 / 日期 | `lumos set <節點> <欄位> <值>`(日期不加引號) |
| 加 / 刪清單項 | `lumos append <節點> <欄位> "[[x]]"` / `lumos remove …` |
| 記決策 / 翻案 | `lumos decision-add <節點> "<內容>" --decided <日期>` / `lumos decision-supersede` |
| 正文段落 | Edit;寫完 `lumos lint <節點>` |

**四條血換的開頭欄位鐵則**:① 多個連結一行一項,擠成一串會長假筆記 ② `summary: |` 區塊裡的 `[[連結]]` 不算連結,要關聯另放 list 欄位 ③ 值含「冒號+空格」要引號或區塊 ④ 同層不能重複鍵。用指令寫天生避開;手改才會踩。

**合約標記(動筆前掃一眼;不確定就不標,嚴禁看 code 反推)**:
```
KEY:★INVARIANT★ <業務合約,改=破壞性> [test:測試名] [audit:模型/日期] [kill:recipes]
KEY:★DEBT★ <偶然行為,可改>
KEY:★IRREVERSIBLE★ <做了回不去> [rollback:decisions]     KEY:★CHECKPOINT★ <改了難救>(建議補 [rollback:])
```
- 綁測試 / 留審計走指令:`lumos guard bind <節點> "<KEY 片段>" <測試名>`、`lumos guard audit …`;裸合約 doctor 擋,未審計 pre-push 擋。綁之前對照 [[Systems/測試假綠形態]](最隱蔽的一型:現場根本走不到被測分支;修 bug 的翻紅測試要配一條「現場成立」的前置斷言)。
- 外部不可逆(信已寄、下游已吃)用 `[guard:decisions]` 寫怎麼防重複。`[test:]` 只證程式對,「規則還符不符合業務」要人確認:`lumos signoff`。
- 從 code 重建的筆記先 `lumos set <節點> regen from-scratch/<日期>`,每條主張標 `[src:]`/`[git:]`/`推測:`/`佚失:`;佚失就寫佚失,嚴禁編。

**摘要區塊**(Systems/Issues 必有):`FLOW:`流程 `KEY:`關鍵概念 `DEP:`依賴 `TEST:`測試;Issues 用 `FLAG:`(只收 TECHNICAL/DECISION/ORIGIN) `DECISION:` `KEY:`。已結案的 Issue 正文第一段要有結案橫幅(status 在開頭欄位,`show --body-only` 看不到,讀者會把修好的當現況)。
**標籤**:`type/` `status/`(值域 lint 硬擋)、`priority/` P0–P3、`scope/`(feature/ area/ 已停用)、`risk/` 金流‧對外送出‧不可逆‧守衛面、`flag/`。

**決策與驗證**:重大決策填四欄(context / alternatives≥2 / why_chosen / trade_offs),缺資訊問人不編。驗證紀錄填 `valid_under`(前提)與 `revalidate_when`(何時重驗),用 `plan_refs` 指回計劃;漏掛 `lumos sync-verified-by --apply`。計劃結案前 `lumos spec-trace <計劃>` 看哪些條款沒人認領。

**承認風險的鐵則**(Enzo 2026-08-22 裁):筆記或訊息裡寫「沒機械守衛 / 只提醒不擋 / 單次量測 / 這數字是拍的」這類承認句,**旁邊必須有「什麼時候回頭看」**(週報、重驗條件、revalidate_when、到期日);寫不出重驗條件的,就是該處理不該承認。**回頭條件要接電**(2026-08-31 回訪案):帶日期的寫成獨立一行 `REVISIT:YYYY-MM-DD 一句要做什麼`(緊鄰原句,doctor 到期會唸、逾 14 天沒人動升級週報);綁事件的明寫事件入口——純散文=52 件盤點實證的死文。

## 4. 收工

1. `lumos lint <每篇動過的>` → `lumos doctor`(紅的段先修;`--verbose` 看全部提醒)。
2. code 有「拿掉 / 反轉」的改動:把那些名字逐個 `lumos search <名> --code`,逐句判筆記還成不成立,不成立當場改或標作廢。動到畫面 → 補可重放的 UI flow 並 `[test:<平台>:<flow>]` 綁回(沒裝置要明寫「未驗+原因」)。
3. 圖譜實質更新後:派乾淨 agent 只讀圖譜還原脈絡,對不上就補到一致,留痕 `lumos self-audit <節點>`。
4. push 後(專案有宣告 ci 區塊才有):`lumos ci-wait`,紅就當輪修,修不完要在收尾明講。
5. 跨 session 傳訊只傳「指標+觸發」(我動了哪篇、你去讀哪篇),不傳內容本身;規則權威在圖譜不在誰的記憶。

# 每日治理wrapper活著沒_計劃

> 白話:每天早上 9:30 有一支腳本自動跑五件事。**9/5 那次它跑到第二步就死了,第 3 到 5 步全沒跑,
> 而且整天沒人發現。** 原因不是它沒印錯誤——是**沒有任何東西在讀它印的東西**,而且它不管發生什麼都回 0。

診斷的可數事實在下面〈現況查證〉。相關的既有節點:
[[Systems/autonomous-iteration-loop]](同一支腳本、同一週的「監看者與被監看者同命」教訓)、
[[Issues/自足性審計提醒空轉四十六天]](「軟提醒沒人看」的前科)、
[[Systems/reversibility-governance-ledger]](這本帳的既有裁定)、
[[Verification/2026-09-05_wrapper邊跑邊改實驗]](9/5 那次事故本身)。

## ★第一輪打掉了兩個前提,先誠實記★

- **★「通知那條腿是斷的」是錯的★**:那支週報在暫停開關**之前**就執行,而且真的會推播。
  真正的問題不是斷了,是**太慢**——它要同一道閘對同一篇連喊 **14 天**才通知,
  拿來偵測「36 小時前死掉」根本來不及。第一版說「斷了」等於用錯的理由選了錯的接法。
- **★把死人開關押在健檢輸出,正是前科事故失敗過的同一招★**:那則事故的節點寫著
  「算得出觸發帳,但『誰會去看』仍無路徑;造了尺,沒造回看的觸發點,病灶未解」,
  一條軟提醒響了 46 天、18,283 次沒人發現。而且那道閘至今仍在天天觸發,不是舊病灶。

還有三條是我把機制看走眼:
- **鎖的主要接管判準是「持鎖行程還活著嗎」**,不是我寫的「鎖齡 60 分鐘」;
  60 分鐘只用在「pid 是空的」那個更窄的競態。
- **鎖的清除是靠 `trap ... EXIT`**,不是寫在函式結尾。我只寫了目標沒寫機制。
- **五步加總照現有寫法會失效**:那種 `echo "[$(ts)] rc=$?"` 裡的 `$?` 抓到的是指令替換自己的
  結束碼。而且函式現在**恆回 0**(最後一條是無條件的收尾 echo),不是我寫的「回最後一步的結果」。

## 現況查證(自己開檔看的)

- 那支腳本主體包在函式裡、結尾同一行接 `exit`(9/5 事故之後補的,防邊跑邊改)。
- **沒有整跑鎖**。**沒有完成戳記**。**沒有任何程式在讀它的紀錄檔**(全 repo 搜零命中)。
- **治理帳 30 天長了 94%**:2026-08-08 是 2,047,015 位元組,今天是 3,966,503。
- 排程設定只有日曆觸發,**沒有任何依賴退出碼的鍵**——非零不會停止排程也不會狂重試,
  但同樣不會通知任何人。(第一版寫「要查」,現在查完了,這條銷案。)

## 設計

### [S1] 健康狀態寫成一份機器局部的 JSON,不是一個「跑完了」的戳記

★第一版的戳記只記「我跑完了」,於是「五步都跑、其中一步失敗」會被標成存活★(外家席指出)。
改成一份原子寫入(先寫暫存檔再改名)的 JSON,內容:
開始時間、結束時間、**各步的結果**、加總結果、這次的執行編號。

**五個結果要存進五個獨立變數**,而且一定用「指令與賦值同一行、中間不插別的指令替換」的寫法
——現在第 1、2 段那種寫法抓到的不是前一支腳本的結果。函式最後一行換成真正的加總值,
不能再讓收尾 echo 當隱式回傳。

★「加總」是指「任一非零就非零」的邏輯聚合,不是算術相加★(r2 通才席實測):
退出碼只能吃 0 到 255。兩步各回 128(那是「被訊號中止」的慣例編碼)算術相加是 256,
取模之後**變成 0**——兩個真實失敗會被壓成「全部成功」,跟現在「恆回 0」是同一種靜默失敗,
只是從必然變成特定數值下才發生。

檔案放在版控外,位置與命名比照既有那批「每台機器各自的執行期狀態」
(扁平放在同一層、附一句為什麼不能進版控的理由),不另開新目錄。
★暫存檔要跟目的檔放同一層★(r2 指出,而且這是這個 repo 的既有寫法:
既有的原子寫入把暫存檔命名成「目的檔名 + 一個固定後綴」,刻意同目錄,就是為了避開跨檔案系統改名失敗)。
不要用系統暫存目錄再搬過來——那在這台機器上目前剛好同一顆磁碟不會炸,換一台就不一定。

**★檔案不存在的語意要定死★**(外家席指出,第一版完全沒定義):
- 不存在 = **從來沒跑完過**,訊息要跟「死掉了」分開講(新機、重新 clone、清過紀錄都會這樣)。
- 不存在**不算逾期**,但要印一句「這台機器上那支從來沒跑完過」。

### [S2] 死人開關:一支獨立的看門狗,健檢只當第二通道

★主通道不能是健檢輸出★(第一輪 blocker):那正是前科事故失敗過的做法。

**主通道 = 一支獨立的、極短的排程看門狗**:每小時跑一次,只做三件事——
讀那份健康 JSON、判斷逾期或加總結果非零、有事就寫一筆治理帳並印出來。
★它跟被監看的那支是兩個不同的失敗域★——這正是「監看者與被監看者同命」那條教訓要的。

### 來源那支的同型洞(2026-09-07 當天補做,Enzo 指示)

`governance/autonomous-loop.sh` 的取鎖段(這支就是抄它的)有同樣三個問題。
原本排 9/14,Enzo 當天就指示先修掉。**三個洞都實測重現過,不是靠「同型」推論**:

| 洞 | 舊行為實測 |
|---|---|
| 接管競態 → 雙開 | 30 輪 × 8 行程,**1 輪多人同時拿到鎖** |
| pid 被無關的活行程重用 | 10 天前的殘鎖 + 一個活著的無關行程 → 印「另一份正在跑」直接退出,**自主迴圈永久停擺而且沒有訊息** |
| pid 檔內容不是數字 | pid 寫 garbage、鎖 0 秒齡 → **當場接管** |

★`set -e` 幫不上忙★:#18 那批的註解寫「來源腳本有 set -e 兜著」——那句話**只對了一半**。
它攔掉「輸的那個 mkdir 失敗」那半(所以雙開率 1/30 比這支的 19/30 低),

### 折入過程自己量出來的兩條(沒有席位報)

- **`open -a APP --args "訊息"` 的參數不會進到 applet**。而且 handler 寫成 `on run argv` 時
  applet **整支不執行**(連第一行都沒跑到),`open` 照樣回 0。所以要寫 `on run`、訊息從檔案讀。
- **applet 一定要寫 `quit`**。不寫會留在 GUI 事件迴圈裡不結束——每小時一則就是每小時一個殭屍行程。

### ★訂正我在這篇裡寫過的一句★

第一版這裡寫「安裝時就要發一則,不然第一次真的出事那天通知會被靜默丟掉」,語氣像是**問題解決了**。
實際上**沒有**:安裝時發一則只是讓權限問題**在安裝當下被人看到**,它不會讓機器有能力偵測
「我喊了但沒人看到」。實測三條路都不行:

- `open` 的回傳碼 → 只反映有沒有啟動(故意 error 的 applet 實測 rc=0)
- 讓 applet 自己回報 → 只證明它跑到了,不證明使用者看得到(`display notification` 被權限擋時不報錯)
- 查通知權限 → 沒有官方 CLI;去翻 NotificationCenter 的 sqlite 是 SIP 保護、格式沒保證,

**所以「權限被關掉 = 靜默不喊」這個洞,這一層補不起來。** 它靠的是:安裝時人確認一次,
加上兩條不受通知權限影響的通道——這支自己的紀錄檔、健檢的 `[A1]` 段。
外家席說「這只是把沒人聽得到從一個樓層搬到另一個樓層」,那句話在「只靠通知」的前提下是對的,
但前提不成立:通知從來不是唯一通道,是三條裡最不可靠、也最不需要人主動查的那一條。

**留了退路**:app 不在、執行檔被砍、或 applet 沒跑到就退回 `osascript` 直接發。
圖示會是系統預設的,但話還是講得出去。★寧可醜也要發得出去★——價值在有人看得到,不在好看。

## 交付之後真人回報的兩件事(2026-09-08)

使用者的原話是「為什麼看門狗老是出現這些不明所以的提示?而且 icon 圖也不見了」。

### 一、看門狗只有一個來源,而那個來源的沉默被它當成了「沒發生過」

**它每天喊一次「這台機器上的 wrapper 從來沒跑完過」,而 wrapper 自己的紀錄檔裡,
前一天和當天都白紙黑字寫著「完成」(五步全 rc=0)。**

成因:「跑完要寫一份健康狀態檔」是這一批才加進 wrapper 的,而排程每天 09:30 叫的
還是舊版本(改動當天稍晚才落地)。舊版不寫那個檔 → 檔不存在 → 看門狗照字面判「從來沒跑完過」。
機械證據:wrapper 的紀錄檔裡「開始(run …)」與「五步 rc=…」這兩行**新版才有**的字,
出現次數都是 0。

★這正是本 repo 那條「只信一個來源、沒去對第二個」的老坑,而且犯在一支
「專門用來告訴人真相」的元件上。★ 它手邊就有第二個來源(wrapper 自己的紀錄檔),沒去看。

**修法**:健康檔不在時,先讀 wrapper 的紀錄檔找最後一次「完成」。
- 在門檻(36 小時)內 → 換句話講:「wrapper 有在跑(最後一次 …),但沒有留下健康狀態檔
  ——這支看門狗因此看不到它的結果。」★仍然要喊★:那個狀態代表看門狗是瞎的,值得知道一次。
- 找不到、或已經超過門檻 → 才說「從來沒跑完過」。
- **紀錄檔本身不在 → 退回原本的判斷**(fail-safe:第二個來源缺席不能讓警報消失)。

守衛:`t_wrapper_watchdog_no_health_but_wrapper_ran`,五條斷言。翻紅釘三個全紅
(拿掉第二個來源 / 不管那次多久以前一律當成跑過 / 把「開始」也當成「完成」)。

**這批提示會自己停**:下一次 09:30 跑的是新版,健康檔一寫出來就進正常判斷。

   141	# ★這支只有一個來源,而那個來源的沉默被它當成了「沒發生過」。★
   142	# 現在的規矩:健康檔不在 → 去看 wrapper 自己的紀錄檔;它最近有跑完的話,
   143	# 講的話要換成「有在跑但沒留下健康檔」,而不是「從來沒跑完過」。
   144	# ★仍然要喊★:那個狀態代表這支看門狗是瞎的,值得知道一次;只是不能講假話。
   145	# 紀錄檔的路徑跟 launchd 那份 plist 的 StandardOutPath 對齊;檔不在就當問不出來,
   146	# 退回原本的判斷(fail-safe:第二個來源缺席不會讓警報消失)。
   147	WRAPPER_LOG="$DIR/logs/daily-wrapper.log"
   148	wrapper_log_last_finish() {   # 印出最後一次「完成」的時間(本地時間字串);問不出來印空字串
   149	  [ -f "$WRAPPER_LOG" ] || { echo ''; return 0; }
   150	  python3 - "$WRAPPER_LOG" <<'PY' 2>/dev/null || echo ''
   151	import re, sys
   152	last = ""
   153	try:
   154	    with open(sys.argv[1], encoding="utf-8", errors="replace") as fh:
   155	        for ln in fh:
   156	            m = re.match(r"^\[(\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2})\].*wrapper 完成", ln)
   157	            if m:
   158	                last = m.group(1)
   159	except OSError:
   160	    pass
   161	print(last)
   162	PY
   163	}
   164	secs_since_local() {   # $1="YYYY-MM-DD HH:MM:SS"(本地);印出距今幾秒,算不出來印空字串
   165	  [ -n "$1" ] || { echo ''; return 0; }
   166	  python3 -c "
   167	import datetime,sys
   168	d=datetime.datetime.strptime(sys.argv[1], '%Y-%m-%d %H:%M:%S')
   169	print(int((datetime.datetime.now()-d).total_seconds()))" "$1" 2>/dev/null || echo ''
   170	}

   172	# 健康檔一次讀出四件事,四行:finished_at / 哪些步驟非零 / total 跟 steps 對不對得上 / steps 讀不讀得到。
   173	# ★不能只讀 total★(代碼審 r1 邊界席):健檢的 [A1] 段讀的是 steps,這支第一版讀 total,
   174	# 餵一份「五步全 0、只有 total 壞掉」的檔,兩邊會講出完全相反的結論——而我在健檢那段
   175	# 的註解裡還寫了「兩條讀同一份健康檔,所以不會各說各話」,那句話當場被打臉。
   176	# 現在兩邊都以 steps 為準,total 只當交叉檢查:對不上就是這份檔壞了,單獨喊一種狀態。
   177	read_health() {
   178	  python3 - "$HEALTH" <<'PY' 2>/dev/null || return 1
   179	import json, sys
   180	d = json.load(open(sys.argv[1]))
   181	fin = d.get("finished_at")
   182	fin = fin if isinstance(fin, str) else ""
   183	steps = d.get("steps")
   184	if isinstance(steps, dict):
   185	    bad = ",".join(str(k) for k, v in steps.items() if v != 0)
   186	    agg = 1 if bad else 0
   187	    mismatch = "1" if d.get("total") != agg else "0"
   188	    readable = "1"
   189	else:
   190	    bad, mismatch, readable = "", "0", "0"
   191	print(fin); print(bad); print(mismatch); print(readable)
   192	PY
   193	}

   252	          now_state="stale|$today"

   254	        fi
   255	      elif [ "$mismatch" = "1" ]; then
   256	        now_state="inconsistent|$today"
   257	        msg="每日治理 wrapper 的健康狀態檔自相矛盾($HEALTH 的 total 跟 steps 對不上)——這份檔不能拿來判斷。"
   258	      elif [ -n "$bad" ]; then
   259	        now_state="failed|$today"
   260	        msg="每日治理 wrapper 最後一次跑完但這些步驟失敗:$bad(見 $HEALTH 的 steps 欄)。"

   262	        now_state="ok|$today"
   263	      fi
   264	    fi
   265	  fi

   272	       esac ;;
   273	  esac

    76	build_notifier() {
    77	  for c in osacompile sips iconutil plutil; do
    78	    command -v "$c" >/dev/null 2>&1 || { echo "缺 $c,跳過通知圖示這一步(通知照發,只是用系統預設圖示)"; return 1; }

    87	    sips -z "$s" "$s" "$ICON_SRC" --out "$iset/icon_${s}x${s}.png" >/dev/null 2>&1 || return 1
    88	    sips -z $((s*2)) $((s*2)) "$ICON_SRC" --out "$iset/icon_${s}x${s}@2x.png" >/dev/null 2>&1 || return 1
    89	  done
