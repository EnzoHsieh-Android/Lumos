## 2. 第二種做法 — major(僅時間運算部分),blocking:是

先分開判:python heredoc 解析日誌這一段跟既有寫法一致——`read_health()` 本來就是 `python3 - "$HEALTH" <<'PY' ... PY` 這種寫法,新加的 `wrapper_log_last_finish()` 完全照抄同一個殼(見 `wrapper-watchdog.sh:150` `python3 - "$WRAPPER_LOG" <<'PY'`),這部分乾淨,沒有引入新做法。

但時間差計算這一段是真的第二套。這個 repo 從 `scripts/lumos` 到 `wrapper-watchdog.sh` 自己既有的 `age` 計算,全部只用一種手法:UTC-aware `fromisoformat`,拿 `datetime.now(datetime.timezone.utc)` 相減——包括這支檔案自己既有的那一行:

file: `governance/wrapper-watchdog.sh:264`
引句:「d=datetime.datetime.fromisoformat(sys.argv[1].replace('Z','+00:00'))」
新加的 `secs_since_local()` 用的是完全不同的另一套:naive 本地 `strptime`,拿 naive 的 `datetime.now()`(無時區)相減:

file: `governance/wrapper-watchdog.sh:168-169`
引句:「d=datetime.datetime.strptime(sys.argv[1], '%Y-%m-%d %H:%M:%S')」
機械查證:對整個 `governance/*.sh` 與 `scripts/lumos` 跑 `grep -n "strptime"`,全 repo 唯一一處 `strptime` 用法就是這批新加的這行——`fromisoformat` 才是這個檔案(以及整個工具鏈)一路以來唯一的時間解析慣例。這不是「這個資料來源逼你這麼做」——log 行的時間戳是本地 naive 字串沒錯,但 python 的 `strptime(...).astimezone()` 就能把它轉成跟既有 `age` 計算同一種 tz-aware 值,不需要另開一條「本地 naive、用 `datetime.now()` 而不是 `datetime.now(utc)`」的第二套比較邏輯。現在的結果是同一個檔案裡「UTC ISO 一套、本地字串一套」並存,跟題目問的完全對上——這算引入了這個檔案原本沒有的第二種時間處理法,不是風格偏好,是機械可查的「唯一一處」。

## 6. bundle 識別碼那一改 — minor,blocking:否

這批本身只是照既有做法把 `.v2` 換成 `.v3`,附了理由(圖示快取),沒有偏離舊做法本身。但題目問的「靠註解自律 vs 機械守衛」這一刀,查證結果是:

file: `governance/install-watchdog.sh:53`
引句:「圖示邏輯以後再動,這個號要往上加。」(舊註解,這批沿用未改)」
file: `scripts/test_lumos.py:30269`
引句:「_re.search(r'NOTIFIER_ID="[^"]*\.v\d+"', src) is not None,」
這支既有守衛只驗「字串長得像有版本尾巴」,驗不到「這次改動真的把號往上加了」——一個把 `.v3` 手誤寫回 `.v2`、或下次改了圖示忘記加號的 diff,一樣能通過這條 check。CLAUDE.md 鐵則四明講「回頭條件要接電……純散文的回頭條件＝沒人會回頭」,而「這個號要往上加」正是這種靠人記得的散文承諾,沒有 `REVISIT:` 或事件掛鉤,也沒有機械閘會在漏加時翻紅。

但這不是這批新引入的——這個註解與這支守衛的缺口在這批之前就存在,這批只是又用了一次同樣的舊模式,沒有讓情況變得更差,也沒有引入「這個 repo 原本沒有的第二種做法」(它跟上一版做法完全同款)。依題目給的判準(「只有引入第二種做法或跨層直呼才算 major」),這不夠格 major;列為 minor、不擋這次推送,但值得提一句:下次真的要動圖示邏輯時,補一條「比對兩個版本間 NOTIFIER_ID 是否真的變了」的守衛,會比再加一句註解可靠。
