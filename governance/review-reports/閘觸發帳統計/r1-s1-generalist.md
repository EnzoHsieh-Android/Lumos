# 審查報告:閘觸發帳統計-r1(generalist,全篇通讀)

審查對象:`/tmp/閘觸發帳統計-r1.md`(112 行)
審查方式:逐節通讀 + 對照 `scripts/lumos` 實碼與 `docs/.governance-log.jsonl` 實資料驗證。

## 發現 1(blocker):S1 設計無法產生「零觸發」桶——本案頭號證據本身不可實作

> 引句:「逐 gate 吐:去重後筆數、原始行數、不同節點數、不同 commit 數、首見/末見日期,以及**收斂指標**。」
> 引句:「**零觸發**:該 gate 在窗口內零筆。」

**問題**:S1 的統計方法是「逐 gate 吐」——隱含實作方式是掃 `.governance-log.jsonl` 等七本帳讀出的列(`ded`),依 `gate` 分組後逐組輸出。但一個「零觸發」的 gate 定義上**在帳裡一筆都沒有**,不會出現在任何一組分組結果裡——分組式掃描天生看不到「完全沒出現過的鍵值」。要讓 `--stats` 印出「check-r: 0 筆(零觸發)」這種行,程式必須先掌握一份**獨立於帳本資料之外的「所有可能 gate 清單」**(gate 全集/registry),再拿全集去對帳、找出缺席者。設計文件全篇沒有提到這份清單從哪裡來、如何維護。

**證據**:
- 實查 `docs/.governance-log.jsonl` 全檔僅出現 4 種 `gate` 值:`anchor-approve`、`check-e1`、`check-s`、`code-loop`(`grep -o '"gate": *"[^"]*"' docs/.governance-log.jsonl | sort -u`)。文件自己列為「零觸發」典範的 `check-r`/`check-j`/`check-k`/`check-e2`/`check-e3` 在整個帳本歷史裡**一行都沒出現過**——這正是「掃描分組法看不到」的鐵證。
- `scripts/lumos` 全檔搜尋 `GATE_NAMES`/`ALL_GATES`/`KNOWN_GATES` 等常數皆無結果——沒有任何現成的 gate 全集清單可供 `--stats` 借用。這五道 check 的 gate 名稱只以字串字面量散落寫在各自的 `gov_events.append(...)` 呼叫點(`scripts/lumos:785,789,792,819,825,866,948,989,1030,1303`),彼此互不知道對方存在。
- 文件本身在「實測基線」第 3 點正是靠這五道「從沒響過」的 gate 當作整個提案最核心的三大發現之一(「五道 doctor 檢查在 516 次 `--ci` 中零觸發」),但這個發現的算法(手動查 `gov_events.append` 呼叫點)並未寫進 S1 的實作設計裡。

**正確版本該說什麼**:S1 需要明確定義並維護一份「gate 全集」的來源——例如:靜態掃描原始碼裡所有 `gov_events.append({"gate": "..."` 與 `cmd_gov` 內各 `load(...)` mapper 寫死的 `"gate": "..."` 字面量,產出一份 gate registry(可以是 `grep` 腳本、可以是手寫常數表,但必須存在且可維護),再用它與帳本資料做 outer join,才可能讓「零觸發」桶真正被觸發。否則 `--stats` 只會回報「帳裡出現過的 gate 各自的統計」,永遠不會印出任何一行「零觸發」。

## 發現 2(major):「不收斂」桶公式對零節點欄位的 gate 會除以零/未定義

> 引句:「改用**每節點平均重複次數** = 去重後筆數 / 涉及節點數,超過門檻(草案 20)即入桶。」

**問題**:此公式的分母「涉及節點數」對某些 gate 結構性地恆為 0——不是資料湊巧稀疏,是 mapper 寫死不填 `nodes`。文件僅在「收斂指標定義」段落末尾提到「無節點欄的 gate(如 `code-loop`)→ 指標印 `n/a`,不入分類」,但這句話語境明確附屬於**收斂指標**(另一個獨立公式),而「不收斂」桶用的是**另一個新公式**(每節點平均重複次數),文件從未明講這條「n/a 排除」規則是否也套用到這個新公式,也未給出除以零時的行為。

**證據**:
- `code-loop` 的寫入函式 `_codeloop_gov_log`(`scripts/lumos:13940-13962`)無條件寫死 `"nodes": []`(第 13956 行);而 `code-loop` 在帳本裡已有 77 筆真實資料(文件自己第 32 行列出「77/77/—/77」)。若依字面公式算,`77 / 0` 會撞 `ZeroDivisionError` 或需要臨時補丁,但文件完全沒提。
- 同樣結構性 `nodes: []` 的還有 `canary`(`scripts/lumos:2931-2932` 硬寫 `"nodes": []`)與 `ci`(`scripts/lumos:2944-2945` 硬寫 `"nodes": []`)、`L2`/bypass-log(`scripts/lumos:2911-2912` 硬寫 `"nodes": []`)——這四個 gate 全部落在文件自己宣稱的「母體 = 既有讀入的七本帳」(第 56 行)範圍內,理應會被 `--stats` 統計到,但文件驗證用的「實測基線」表(第 27-33 行)完全沒有覆蓋這四個 gate 的實際輸出行為,等於這個除以零的坑目前零驗證。
- 測試策略第 4 條 `t_gov_stats_buckets`(第 83 行)只造了「零筆 gate」「平均 25 次」「平均 3 次」「收斂指標非 0 但平均超門檻」四種情境,沒有一種是「有真實筆數但節點數=0」——除以零的路徑完全沒被測試策略覆蓋,但這條路徑在**目前的真實資料**上就會被 `code-loop` 觸發。

**正確版本該說什麼**:S1 必須明講「無節點欄」的排除規則同時適用於收斂指標**與**不收斂桶的分母,並定義這類 gate 在三桶分類裡的歸屬(不入三桶任何一桶?還是印一個第四種標記如「n/a」?),並在測試策略里加一條「有筆數、節點數=0」的案例(用 `code-loop` 這種真實存在的 gate 當 fixture)。

## 發現 3(major):「516 次 `--ci`」把「全帳去重後不同 commit 數」誤標成「`--ci` 執行次數」,證據不支持此因果標籤

> 引句:「**五道 doctor 檢查在 516 次 `--ci` 中零觸發**」

**問題**:文件第 25 行明確定義「516 個不同 commit」是整份 `.governance-log.jsonl`(涵蓋 `check-s`/`check-e1`/`anchor-approve`/`code-loop` 四種 gate 混合)的去重後不同 commit 總數,不是「`--ci` 被執行了幾次」的量測。但第 38 行把它直接重貼標籤成「516 次 `--ci`」,暗示分母是「doctor --ci 執行機會數」。這兩者是不同母體:`anchor-approve`(來自 `lumos anchor approve` 指令,`scripts/lumos:10071`)與 `code-loop`(來自 code-loop 收斂留痕,`scripts/lumos:13940-13962` `_codeloop_gov_log`)完全不經過 `doctor --ci`,是各自獨立的指令觸發寫入同一本帳檔——不是「--ci 執行時捎帶寫入」。

**證據**:
- `run_doctor` 函式內註解明講(`scripts/lumos:453`)「本輪 gate findings → governance-log(--ci 才寫)」,且落帳呼叫點在 `scripts/lumos:1323`(`_append_governance_log(env.vault, gov_events)`),只在 `ci=True` 分支執行——這確認 `check-s`/`check-e1`/`check-r`/`check-e2`/`check-e3`/`check-k`/`check-j` 這一組 gate 才是「--ci 才寫」的產物。
- 但 `anchor-approve` 的落帳呼叫在完全不同的函式路徑(`scripts/lumos:10071`,`lumos anchor approve` 指令內),`code-loop` 的落帳在 `_codeloop_gov_log`(`scripts/lumos:13940`),兩者皆與 `doctor --ci` 無關。
- 文件自己第 27-32 行列出的分項 commit 數加總(420+181+138+77=816)遠大於「516 個不同 commit」,說明 516 是跨四種 gate 的**聯集**去重結果(commit 常同時觸發多道 gate),而非「執行 --ci 這件事發生了 516 次」的獨立計數。把聯集式的「全帳不同 commit 數」直接拿來當「--ci 執行次數」分母,缺乏任何佐證這兩者相等(尤其 `anchor-approve`/`code-loop` 觸發的 commit 若剛好沒跑過 `--ci`,會把 516 灌水,使「0/516」這個比率失真)。

**正確版本該說什麼**:若要主張「零觸發相對於多少次 `--ci` 執行的機會」,分母必須只從 `check-*` 系列(doctor --ci 專屬)的 gate 事件推導,而非整份帳檔的聯集 commit 數;或者乾脆不下「516 次 --ci」這種因果性標籤,只如實陳述「516 是全帳去重後不同 commit 數」。

## 發現 4(major):`canary` 的 gate mapper 把 `commit` 寫死為空字串,「涉及 commit」欄位對它必然回報誤導性的「1」

> 引句:「惟 `lumos gov` **本來就把七本帳合流成同一組 gate 值**,故本案統計天然涵蓋它們(見 S1 範圍)。」

**問題**:文件明確主張 `canary`(連同 `signoff`/`kill`)雖然寫在各自的帳檔,但因為 `lumos gov` 讀入時合流成同一組 gate 值,所以「本案統計天然涵蓋它們」。但 `canary` 的 mapper 對每一筆事件都把 `commit` 欄硬寫成空字串:

```
load(".canary-log.jsonl", lambda d: {"ts": d.get("ts", ""), "commit": "",
     "gate": "canary", ...
```
(`scripts/lumos:2931-2932`)

**問題影響**:S1 設計的「涉及 commit」欄位定義是「不同 commit 數」(第 60 行)。對 `canary` 而言,所有列的 `commit` 都是同一個空字串,去重後「不同 commit 數」恆為 **1**——不管實際有多少場稽核。文件自己在第 40 行陳述 canary 帳有 448 筆真實資料,若這 448 筆全部落入 `--stats` 的 `canary` 分組,輸出的「涉及 commit=1」會是明顯錯誤/誤導的數字(canary 稽核本來就不綁 commit,語意上該印 `n/a`,而不是一個看似有意義實則恆定的「1」)。

**正確版本該說什麼**:S1 應該像處理「無節點欄」一樣,明講哪些 gate 是「無 commit 欄」(canary 是明確一例,`commit` 恆空字串),對這類 gate 的「涉及 commit」欄印 `n/a` 而非帶出一個恆定但無意義的數字。

## 發現 5(major):「計數用去重後的列」被錯誤等同於「人會看到幾筆」,與 `gov` 實際預設輸出行為不符

> 引句:「**計數用去重後的列**(與 `gov` 既有呈現一致,即「人會看到幾筆」)」

**問題**:`cmd_gov` 的資料流程實際上有**兩層**過濾,不是文件講的一層:
1. 硬去重(commit, 節點集, gate, kind, token)→ 產出 `ded` 列表(對應文件第 25 行「去重後 8,156 筆」)。
2. 在**預設(非 `--full`)模式**下,額外做一層「去噪」摺疊:同日同 gate 同 kind 的 advisory 列,依節點折成「`×N`」單行,若同群節點數 >6 則整群再收成一行摘要(`scripts/lumos:2961-3000`)。

這代表使用者在**不加 `--full`**跑 `lumos gov` 時,終端機上真正印出的行數,會比 `ded` 的 8,156 筆**更少**(尤其 `check-s` 這種平均每節點被念 173 次的 gate,折疊後同一天同節點的上百筆會摺成一行「`×173`」)。文件把「去重後」直接註解成「即『人會看到幾筆』」,這個等式在程式碼裡不成立——真正的「人會看到幾筆」是去噪折疊後的行數,是一個 `ded` 之外、目前完全沒被文件計算或提及的**第三個數字**。

**證據**:`scripts/lumos:2961-3000` 的 `agg`/`_is_advisory`/`_agg`/`_drop`/`_printed` 邏輯確認:非 `--full` 模式下,同一 `(date, gate, kind)` 群組裡同節點的多筆會摺成一行帶 `×N`,>6 節點的群組還會再摺成一行摘要,兩者都讓「印出的行數」嚴格小於 `ded` 的筆數。

**影響**:本案第 23 行本身立了「★兩套數字,不可混用★」的鐵則,正是為了避免「帳裡幾行」與「人看到幾筆」被混為一談——但 S1 對「去重後」這個數字的定義說明,恰好把它跟一個**第三個、實際上更小的數字**(真正渲染出的行數)混為一談,違反了文件自己立的鐵則精神。若之後有人拿「去重後 8,156 筆」去回答「使用者這 90 天到底被洗了幾行版面」這種問題,答案會偏高。

**正確版本該說什麼**:要嘛把「去重後」的定義改回精確敘述(「commit×節點集×gate×kind×token 去重後的事件數」),拿掉「即人會看到幾筆」這個不成立的類比;要嘛真的把「去噪折疊後行數」算成 `--stats` 的第三欄,兩者只能選一個,不能兩個都不做卻宣稱已對齊「人看到幾筆」。
