## Finding 1 — BLOCKER:「去重後筆數」被誤標成「人會看到幾筆」,但兩者相差可達 128 倍

引句：「計數用去重後的列**(與 `gov` 既有呈現一致,即」

**逐字引句**:
> 「與 `gov` 既有呈現一致,即「人會看到幾筆」」(line 56)

另一處同一混淆:
> 「「帳裡幾行」與「人會看到幾筆」不是同一個數」(line 23)

**問題**:文件把「去重後的列」等同於「使用者跑 `lumos gov`(不帶 `--full`)時實際看到幾行」。但讀 `scripts/lumos:2961-3000` 會發現:非 `--full` 模式在**去重之後還有第二層摺疊**——同(日,gate,kind,node)的 advisory 列摺成 `×N` 一行(2973-2984),同(日,gate,kind)群組 >6 節點再摺成一行群組摘要(2988-2998)。這層摺疊在去重之後才發生,文件完全沒提到、也沒引到這段行號(只引了 2950-2957 的去重段)。

**證據**(對 `docs/.governance-log.jsonl` 完整重放 `cmd_gov` 的去重＋非 `--full` 摺疊邏輯,只看 `check-s`):

```
dedup rows for check-s: 7287
actual printed lines for check-s under non-full gov output: 57
```

7,287 → 57,相差 **127.8 倍**。也就是說,文件基線表與桶判準所用的「去重後筆數」(7,287)跟一個人實際跑 `lumos gov` 時眼睛看到的行數(57)是**第三種、且差距巨大的數字**,既不是「帳裡幾行」也不是「人會看到幾筆」。

**這為什麼要緊**:本案的整個立論框架借的是 SRE 告警治理(「每次都響而沒人動作的告警等於沒有告警」)——這個論證的前提是「量的是人實際感知到的噪音」。但「每節點平均重複次數」桶判準(S1)、以及「重複警告佔壓倒多數 98.9%/97.4%」的敘事,用的都是「去重後」這個既不是原始也不是人眼所見的第三種數字,卻被貼上「人會看到幾筆」的標籤。若字面照做,`--stats` 輸出的欄位標籤與敘事會誤導使用者(以及日後拿這份統計去裁「紀律要不要退場」的人)。

**正確的講法應該是**:三層數字都要分開標,不能只分兩欄:①原始行數(帳裡幾行)②去重後筆數(dedup 邏輯輸出,無視覺摺疊)③(若要主張「人的實際感知噪音」)非 `--full` 模式摺疊後的行數。若 S1 的桶判準是想量「人的感知疲勞」,分母該用③而非②;若只是想量「去重後的事件量」,則欄位標籤不能寫「人會看到幾筆」。

## Finding 2 — BLOCKER:收斂指標分母為 0(除以零)的情況,規格沒有涵蓋,而且現在的帳本上就有 5 道閘會踩到

引句：「無節點欄的 gate(如 `code-loop`)→ 指標印 `n/a`,不入分類。」

**逐字引句**:
> 「無節點欄的 gate(如 `code-loop`)→ 指標印 `n/a`,不入分類。」(line 62)

**問題**:S1 只針對「結構上沒有 nodes 欄位的 gate」(如 `code-loop`,其 mapper 固定 `"nodes": []`)給了 `n/a` 例外。但 `check-r`/`check-j`/`check-k`/`check-e2`/`check-e3` 這五道閘,其 mapper(`scripts/lumos:2916-2918`,標準 `.governance-log.jsonl` 通用 mapper)結構上**有** nodes 欄位,只是現在窗口內筆數為 0(見基線表本身:「0 / 0 / — / —」)。這五道閘不落入文件給的 `n/a` 例外條件,但按收斂指標定義「分母=該 gate 曾警告過的節點總數」,分母會是 **0**——除以零。

**證據**:重放 `docs/.governance-log.jsonl` 確認,現實帳本上這五個 gate 的 dedup 筆數與節點數皆為 0(與文件基線表一致,已列於 line 33)。這不是假設性的邊界案例,是**現有真實資料上必然會踩到的路徑**——只要 `--stats` 一上線立刻對這 5 道閘跑出未定義行為(crash 或印出無意義值,規格沒說)。

**測試策略沒接住**:`t_gov_stats_buckets`(item 4)只驗證「零筆 gate→零觸發桶且措辭含自曝限制句」,驗的是**分類桶**這個欄位,完全沒驗證同一批零筆 gate 的**收斂指標欄位**印出什麼——規格漏、測試也跟著漏。

**正確的講法應該是**:收斂指標的 `n/a` 例外條件要改成「分母為 0(不論是結構性無 node 欄還是窗口內零筆)→ 印 `n/a`」,並補一條測試案例明確釘零筆但有 node 欄的 gate(用真實例子:`check-r`)。

## Finding 3 — MAJOR:收斂指標定義用「曾警告過」,但套進非 warned 類事件(如 `anchor-approve`)會算出失真的高收斂率,而文件自己的未決段落又預期它會被算進去

引句：「分母=該 gate 曾警告過的節點總數」

**逐字引句**:
> 「分母=該 gate 曾警告過的節點總數」(line 62)

文件自己在未決段承認 `anchor-approve` 會進同一套分類機制:
> 「`anchor-approve` 是人為動作留痕,平均 28 會被門檻 20 誤判進不收斂桶,這是已知偽陽性」(line 107)

**問題**:「曾警告過」字面上該對應 `kind=="warned"`。但實際帳本裡,`anchor-approve` 的 `kind` 全部是 `"approved"`(人為核准動作,不是警告),`code-loop` 是 `"pass"` 之類(且無 node,已被排除)。文件既沒有在 S1 明講「收斂指標只吃 kind=warned」,也沒有明講「不分 kind、只要是這個 gate 底下的事件都算」——兩種讀法差很多,而未決段落的討論(擔心 `anchor-approve` 被桶判準誤傷)暗示作者其實預期 `anchor-approve` 會流進同一套收斂/分桶管線,而不是被「曾警告過」這個措辭排除在外。

**證據**(對真實帳本重算 `anchor-approve` 的收斂指標,若不做 kind 過濾、直接套用 S1 定義):

```
anchor-approve per-node last-seen: {'post-commit': '2026-07-24', 'pre-commit': '2026-08-11',
  'pre-push': '2026-07-29', 'test_autonomous_loop': '2026-07-09', 'test_lumos': '2026-08-19'}
anchor-approve convergence 4 / 5 = 0.8
```

對照同帳本裡真正的 advisory 閘 `check-e1`:

```
check-e1 convergence 0 / 5 = 0.0
```

`anchor-approve` 收斂指標算出來是 **0.8**(比 `check-s` 的 0.286 高得多),但這 0.8 完全不是「警告被修好了」——`post-commit`/`pre-push`/`test_autonomous_loop` 這幾個 hook 只是最近沒有新的人為核准動作(這是人觸發的低頻事件,不是自動重複告警),跟「問題被修掉」毫無關係。而 `check-e1` 因為每次 commit 都自動觸發、天天有新事件,收斂率反而是 0——收斂指標把「事件本來就稀疏(人為動作 log)」跟「警告真的停了」混為一談,產生**與本案想量的東西方向相反的誤導性高分**。這正好命中文件自己在 96 行講的風險(「零觸發 ≠ 無價值」),但**收斂指標本身**(而非零觸發桶)完全沒有對稱的自曝限制句,規格對此毫無防呆。

**正確的講法應該是**:S1 要明確定義收斂指標的 kind 篩選範圍——要嘛只對 `kind=="warned"` 的 gate 計算(此時 `anchor-approve`/`code-loop`/`canary`/`kill`/`signoff` 全部落 `n/a`,分母恆 0),要嘛明講「不分 kind」但加上跟零觸發桶對等的自曝限制句(人為動作類 gate 的高收斂率不代表問題被修好,只代表事件本來就稀疏)。

## Finding 4 — MAJOR:「每節點平均重複次數」用去重後**列數**除節點數,遇到一列多節點時不等於「每節點平均被記幾次」

引句：「每節點平均重複次數** = 去重後筆數 / 涉及節點數,超過門檻(草案 20)即入桶」

**逐字引句**:
> 「= 去重後筆數 / 涉及節點數,超過門檻(草案 20)即入桶」(line 66)

**問題**:此公式假設「一列一節點」。`check-s`/`check-e1` 現實資料確實一列一節點,公式在那兩道閘上沒問題。但 `anchor-approve` 的列不是這樣——實測 `anchor-approve` 142 筆原始事件裡,有 15 列是**多節點**列(2 節點 13 列、3 節點 1 列、5 節點 1 列):

```
anchor-approve node-count-per-row distribution: [(0, 5), (1, 122), (2, 13), (3, 1), (5, 1)]
```

去重後 139 列裡,節點出現次數總和(node-occurrences)是 **153**,不是 139。用文件的公式算「平均重複次數」是 `139/5 ≈ 27.8`(文件寫「≈28」),但如果公式真的要量「每個節點平均被記幾次」,正確算法應該是 occurrence 而非 row:`153/5 = 30.6`。

**證據**:

```
anchor-approve dedup rows= 139 distinct nodes= 5 node-occurrences= 153
row/node avg= 27.8   occ/node avg= 30.6
```

這次剛好兩個數字都超過門檻 20、桶判準結論不變,但這是巧合——公式本身對「一列多節點」的 gate 算出的數字,字面上就跟它自稱要量的東西(「每節點平均重複」)對不上。只要未來出現一個一列多節點且 occurrence/row 比值落在門檻附近的 gate,兩種算法就會給出不同桶。

**正確的講法應該是**:公式改成「Σ(每列節點數)/ 涉及節點數」(node-occurrences / distinct nodes),而不是「去重後列數 / 涉及節點數」;或者明講此桶判準只對「一列恆一節點」的 gate 有效,對 `anchor-approve` 這種多節點列的 gate 另案處理。

## Finding 5 — MAJOR:基線敘事裡「六個節點同日一起停」的節點數算錯,實際是九個

引句：「其中六個節點在 2026-07-24 同日一起停,像是一次批次補審」

**逐字引句**:
> 「其中六個節點在 2026-07-24 同日一起停,像是一次批次補審」(line 37)

**問題**:這句話是文件用來支撐「不是全然零收斂」論證的具體證據,也是它推翻「收斂指標=0」判準、改用「平均重複次數」桶判準的實測依據之一。但實際對帳本重算 `check-s` 每節點末次被警告日,2026-07-24 這天停止的節點是 **9 個**,不是 6 個:

**證據**:

```
2026-07-24  9 nodes: ['lumos-refcheck', 'risk-tiered-review', 'compose-metrics-adapter',
  'lint-version-watch', 'pitfalls-lint-adapter', 'cochange-guard', 'guard-kill',
  'cross-family-audit', 'lint-declaration-health']
```

(完整分佈:2026-07-16×1、2026-07-24×9、2026-07-26×1、2026-08-15×1、2026-08-19×30,合計 42;已停 12、活躍 30——12/42=0.286 這個總數本身是對的,只有「六個」這個子分類細節錯。)
