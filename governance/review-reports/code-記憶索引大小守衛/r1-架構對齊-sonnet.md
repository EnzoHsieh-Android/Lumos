## F1 新常數的 KB 換算單位跟同檔既有常數不一致(1000 vs 1024)

severity: minor
blocking: no

引句:「_INDEX_MAX_BYTES = 25000」

`scripts/hooks/claude/memory-sweep.py` 檔頭原本就有一個位元組上限常數 `MAX_BYTES = 64 * 1024`(單篇最多讀多大),這份檔案裡「KB」一律照 1024 進位算。這次新加的 `_INDEX_MAX_BYTES = 25000` 改用十進位(25 KB = 25000,不是 25 * 1024 = 25600),而且顯示那句「記憶索引 MEMORY.md 現在 %.1f KB」也是用 `size / 1000` 換算,同一支檔案裡兩套「KB」換算標準並存、沒有註解說明為什麼要換。既有慣例在:`MAX_BYTES = 64 * 1024`(檔案頂端常數區塊,`memory-sweep.py` 第 45 行附近)。不影響正確性(這裡本來就是照官方文件寫死的門檻,官方講的可能就是十進位 KB),但同檔案內同一個單位詞兩種算法,下一個人接手改數字容易照抄錯的那一套。

## F2 新的索引大小守衛塞進不相關的既有段落標題底下,沒有自己的區塊分隔

severity: minor
blocking: no

引句:「# ── 找記憶目錄與圖譜 ────────────────────────────────────────────────────────」

這份檔案對跨切面的獨立機制(注入框、內層逾時預算)都有自己一組明顯的 `# ──★標題★── … # ──★標題結束★──` 分隔注解(例:`# ── ★注入框:把「機器附加的內容」跟系統話明確分開★ ──` … `# ── ★注入框結束★ ──`),讓人一眼看出這段是獨立的一塊機制、跟上下文無關。這次新增的「索引大小守衛」(`_INDEX_MAX_BYTES`/`_INDEX_MAX_LINES`/`index_size_note`)直接插在既有的「# ── 找記憶目錄與圖譜 ──」標題正下方,但它跟「找記憶目錄」或「找圖譜」完全是兩件事,也沒有補一個自己的區塊標題(或至少在既有標題後面另起一段)。同檔案裡已經有這個「獨立機制自己開一個框」的慣例,這次沒有照著做,下一個人在「找記憶目錄與圖譜」這個標題底下讀,會先被一段不相干的大小檢查擋住。

已看、沒問題的地方:
- `_emit` 對新的 `size_note` 走「框外插一句工具自己寫死的指示」這條路(`tail = nxt + ...`),跟既有 `nxt`(下一步建議)、`ci-status-hook.py` 的 `_frame_injected(msg) + "\n本輪開工前..."` 是同一套慣例,沒有另開一套。
- 新測試 `t_memory_sweep_index_size` 沿用 `t_memory_sweep_core` 同樣的「找 hook 檔案、沒有就 `_SrcOnly`」寫法與 `翻紅釘:`/`出身:` docstring 格式,跟鄰近測試一致。
- 訊息文字有「現在幾 KB/幾行」+ 門檻、有分級(80%/95%),符合本專案「工具輸出白話三段式」的「數字旁一句是什麼+門檻」慣例。
