# 筆記形狀擋_計劃

白話:筆記不留程式碼推得出來的東西(d1),這份先做機械上「一看就知道」的那一半:提交時擋下新寫的程式行號引用,以及沒寫出「程式碼答不了的來源」的現況描述。看意思才判得出來的那一半(推送前的 AI 審查員)在 [[Projects/筆記不存程式碼推得出的事_計劃]],兩份是 Enzo 2026-09-27 裁的拆分(Issue d7)——原本合在一起審了兩輪、折了 70 條還在冒,分開讓這一半先生效。

依據:[[Issues/筆記把程式現況寫進脈絡而漂移_rtb實測回饋]] 的 d1–d7;前一版規則為什麼沒擋住見 [[Projects/Lumos定位_程式碼為主脈絡為輔_計劃]]〈檢討〉;下面每一條做法都已經過那份大計劃兩輪設計審(卷證 `governance/review-reports/筆記不存程式碼推得出的事/`),這裡只收跟第一層有關的結論。

PRIOR-ART: 全部借本 repo 既有形狀,不發明新做法——①「每支檔有家」的閘([[Systems/每支檔有家]]):提交前 `--staged`、推送前 `--diff <範圍>`、判定全在 lumos 裡、hook 只呼叫,新分支起點用「不在任何遠端分支上的最早提交」;②程式檔判定沿用它的 `_is_code_file`;③圍欄判定沿用 `_visible_lines`;④專案開關與跳過照新增告警閘的 `lint_new.gate`(block / warn / off)與 `LUMOS_SKIP_LINT_NEW`;不是 block 時 doctor 持續印,照 `node_home.gate` 的先例;⑤治理帳寫入走既有通用寫入器 `_gate_event`。不採用新依賴。
RETIRE-IF: 上線兩個月後任一成立就撤掉或改規則:①被擋之後改用 skip、專案開關或 `--no-verify` 的次數超過被擋次數的三成(誤擋多到大家在繞);②對上線後新增的筆記行抽樣,行號引用或沒來源的現況前綴仍佔一成以上(擋不住);③兩條規則連續兩個月零觸發,而且抽樣也看不到這兩種形狀(問題已經不存在,閘只剩成本)。
REVISIT:2026-11-27 量上面三個數,跟大計劃的回頭日同一天。

## 做法

### 範圍與行(寫成一支共用函式,第二層之後直接用)

- **範圍**:提交前=暫存區差異。推送前:遠端已有那個版本就用「遠端版本..本機版本」;新分支或本機沒有遠端那個版本時,照「每支檔有家」推送檢查的既有算法——起點是「不在任何遠端分支上的提交」裡最早那個的上一個提交;全部已在遠端就不查;最早那個沒有上一個提交(真的全新)才從空樹比。★不用「跟預設分支的分岔點」★(本 repo 2026-07-21 因主線直推時分岔點等於自己、守衛靜默跳過而拆掉過那種算法,見 [[Projects/prepush主幹範圍修法_計劃]];消費專案的預設分支也不一定叫 main)。★也不用 CI 既有代碼審那一步的空樹兜底★(會把整庫舊筆記當新增,大計劃 r1 外家席實跑整庫 57,474 行)。CI:推送前後兩個版本;前一版全零(新分支首推)時照同一算法、排除這條分支自己的遠端參照,那一步要抓完整歷史。
- **行**:圖譜筆記在範圍內新增或改動的行(改名用 git 的改名偵測認成同一篇,只算真正變動的行;偵測不到改名時新檔整篇算新增——方向是多查不是漏查)。**算進來的**:正文、開頭欄位的 `summary` 摘要區塊、`decisions` 每條底下所有文字值的子欄(實際寫法有 `alternatives_considered`、`alternatives`、`trade_offs` 等好幾種,不列欄名)。**不算的**:其他開頭欄位(tags、連結清單、日期、status、lands_in、aliases、about_code 這類結構欄)。刪掉的檔不算。
- 程式碼圍欄一律用 `_visible_lines` 判;第一層兩條規則都不看圍欄裡的內容(那是當時的輸出)。
- 筆記檔讀不成 UTF-8:整支擋下並講是哪支檔。

### 兩條規則(`lumos note-shape`,提交前 `--staged`、推送前與 CI `--diff <範圍>`)

1. **程式行號引用**:`路徑:數字`、`路徑#L數字`,而路徑是 repo 裡的程式檔或測試檔——用 `_is_code_file`(它認得沒有副檔名、開頭是 `#!` 的主程式),再把它排除掉的測試檔加回來(測試的行號一樣會漂)。`.md` 這類文件路徑不擋(審查卷證與規範引用不是程式現況)。**放行寫法**:釘住版本的 `路徑@<提交>:數字`,指的是某一次提交的那一行,不會漂;要指到測試就寫測試名。
2. **現況類前綴沒寫出程式碼答不了的來源**:新增的 `FACT:` `FLOW:` `DEP:` 行要帶 `[src:部署]` `[src:資料庫]` `[src:生產]` `[src:外部]` `[src:人工]` 其中之一(d3);只寫「以程式碼為準」加查詢不再算數。

回傳碼照鄰居:0 過、1 擋、2 參數錯;不是 git 或找不到 lumos 就照既有 hook 慣例放行並說一句。閘名 `note-shape` 登記進既有閘名單,事件走 `_gate_event`(blocked / passed)。擋下訊息列出每一處(檔、行、哪條規則、怎麼改),並明講「內容還在工作目錄,改完再提交」——提交前被擋時沒有產生提交,hook 不得動工作目錄。

**開關與跳過**:`.lumos/config.json` 的 `note_shape.gate`:block(預設)/ warn / off;不是 block 時 `lumos doctor` 每次印一行、每次放行寫一筆 skipped 事件。環境變數 `LUMOS_SKIP_NOTE_SHAPE=1` 單次跳過並寫帳。

### 治理帳寫入加鎖

`_gate_event` 與代碼審那支 `_codeloop_gov_log` 現在都直接 append 同一本治理帳、沒有鎖;兩個行程同時寫可能產生壞行,而讀端遇到壞行會靜默跳過(大計劃 r1 併發席、r2 外家席)。改成兩者寫入時拿同一把治理帳檔案鎖;等鎖逾時照既有 rc 協議印「擋下:…」回 2,不丟裸例外。這是第一層自己要寫事件、也是第二層將來要寫通過紀錄的前提,所以放在這份先做。

### 紀律範本改寫

紀律範本〈寫筆記時〉那張表的 `FACT:` `FLOW:` `DEP:` 整列改成 d3 的收窄說法:只准寫程式碼答不了的現況,要帶 `[src:]`;程式碼查得到的一律不寫。同一節寫明第一層會擋哪兩種形狀、放行寫法、開關與跳過。各專案各自跑 `lumos update` 拉新版(那支指令是從工具鏈原始 repo 拉進本專案)。skill 裡只指路、不放第二份定義。

### 消費專案的 CI

`lumos update` 不會動各專案的 CI 設定檔。所以 `lumos doctor` 檢查專案 CI 有沒有呼叫 `note-shape --diff`,沒有就每次印一行並給要貼的那一步;另外 doctor 對「已推上遠端、在閘上線之後」的提交跑一次 note-shape,有違規就列出來(抓 `--no-verify` 繞過)。工具鏈自己的 CI 手動加那一步。

## 條款

- [S1] 若新增行含指向程式檔或測試檔的行號引用(含沒有副檔名、開頭是 `#!` 的主程式),且不在程式碼圍欄內,則 note-shape 應擋下並列出每一處;指向 `.md` 的、釘住版本的 `路徑@<提交>:數字`、沒改動的舊行都不應擋 [test:t_note_shape_line_refs_code_only_new_only]
- [S2] 若新增的 `FACT:` `FLOW:` `DEP:` 行沒帶五種 `[src:]` 類別之一,則應擋下;只有「以程式碼為準」加查詢的也應擋下;圍欄內的不應擋 [test:t_note_shape_current_state_prefix_requires_source]
- [S3] 推送前遇到新分支或本機沒有遠端版本時,起點應為「不在任何遠端分支上的最早提交」的上一個,全部已在遠端應不查;CI 新分支首推應用同一算法並排除自己的遠端參照;兩者都不應把舊筆記行算成新增;預設分支不叫 main 的專案行為應相同 [test:t_note_lines_range_new_branch_not_on_remotes]
- [S4] 新增行集合應含正文、summary 區塊、decisions 每條所有文字值子欄(含 `alternatives_considered`),且應排除其他開頭欄位;改名應認成同一篇;筆記檔讀不成 UTF-8 時應 rc1 並指名那支檔 [test:t_note_lines_scope_rename_and_non_utf8]
- [S5] 擋下時應印每一處的檔、行、規則與改法,且不得改動工作目錄;不是 git 或找不到 lumos 時應放行並說一句 [test:t_note_shape_block_message_and_fail_open]
- [S6] `note_shape.gate` 設 off 時應放行並寫 skipped 事件,warn 時應只印不擋並寫事件,兩者 doctor 都應印一行;`LUMOS_SKIP_NOTE_SHAPE=1` 應放行並寫一筆跳過 [test:t_note_shape_config_modes_visible]
- [S7] `_gate_event` 與代碼審治理帳寫入應拿同一把檔案鎖,兩個行程同時寫(一個 note-shape、一個 code-loop)兩筆都應完整落帳;等鎖逾時應印擋下並回 2 [test:t_governance_ledger_writers_share_lock]
- [S8] 紀律範本的 FACT/FLOW/DEP 那列應寫 d3 的收窄說法,各專案注入的紀律區塊應與範本一致 [test:t_discipline_current_state_row_narrowed]
- [S9] doctor 應在專案 CI 沒呼叫 `note-shape --diff` 時印一行並給要貼的步驟,並列出閘上線後已推上遠端卻違反兩條規則的新增行 [test:t_doctor_note_shape_ci_and_bypass_scan]

## 回退

照這個順序,反過來會卡住別人推送:
1. 先拿掉工具鏈自己 `.github/workflows/ci.yml` 裡的 note-shape 那一步(這支檔不在 `lumos update` 同步清單裡,要手改);消費專案自己貼過的也各自拿掉。
2. 消費專案不用等中心:各自把 `note_shape.gate` 設成 off 就停。
3. 拿掉提交前與推送前 hook 裡的呼叫,再移除 note-shape 指令與 doctor 那段;各專案 `lumos update` 拉回。
4. 治理帳的共用鎖**留著**:它讓舊的寫入者也不會交錯,拿掉反而退回壞行風險。
5. 紀律範本那列改回舊句時要先想好:舊句正是讓現況描述留存的出口(見〈檢討〉第 4 點)。
6. 被擋下的內容從沒進過 git,只在作者的工作目錄。

## 實務隱患

- 守衛面:新的擋人機制,誤擋會讓人習慣繞過——所以只看新行、不擋文件路徑、有釘版本的放行寫法、有開關與跳過且都寫帳、doctor 持續印,全部進 RETIRE-IF ①。
- 資源併發:note-shape 只讀不寫筆記;寫治理帳走共用鎖;兩個會談同時提交各自只看自己的暫存區。
- 已排除:對外送出:只在本機讀 git 與檔案,不送任何內容到外部服務
- 已排除:不可逆:擋下時不產生提交、hook 不動工作目錄,內容留在作者手上;拿掉閘就恢復原狀
- 已排除:金流:不碰任何付款或計費流程

## 誠實界線

- 這一層只擋兩種形狀;rtb 稽核裡漂移最多的「目前沒有 / 只有 N 種」句型、貼錯標籤的 WHY 行、done 計劃的現況段,形狀都不固定(句型比對抽樣準度約三分之一),要等第二層。在第二層上線前,這些照樣寫得進去。
- 行號引用的抽樣 12/12 是單人目測、樣本小。
- 沒有接 CI 的消費專案,`--no-verify` 推上去當下擋不住;doctor 事後會列出來,但那時已經在遠端了。
