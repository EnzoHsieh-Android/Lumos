## 2. 步驟 1|特徵字串定位

### Finding 2.1 — severity: major
引句:「字串是最便宜的錨,比讀架構文件快且不會騙人。」

問題:「任何棧都有可觀察面」的舉證清單只列網頁/CLI/後端/mobile 四種。至少兩類棧結構性不成立:資料管線/批次(無畫面、宣告式管線的「code 單元」可能是 YAML 配置);embedded/韌體(PID 迴路、GPIO 輸出沒有人類可讀字串,可觀察面是波形/實體行為,release build 常 strip 除錯字串)。這兩類不是「騙人」問題,是**錨根本不存在**,spec 沒承認也沒給替代錨點(硬體暫存器位址、協定欄位名)。

### Finding 2.2 — severity: major
引句:「網頁=畫面文字/元素 class(影片的「右鍵檢查」是此步的網頁特例)」

問題:前端 SPA 的 minify/i18n 間接化沒處理:CSS Modules/styled-components 把 class 雜湊成無語意字串,右鍵抓到的在原始碼查無此字;i18n 畫面文字是 key 解出來的,原始碼只有語系檔有,要兩跳(先抓 key 再問誰用了 key)。種子影片示範是未 minify 的開發環境,spec 把開發環境特例寫成通用棧規則。

## 3. 步驟 2|追流+圈承重牆

### Finding 3.1 — severity: blocker
引句:「這個單元的輸入從哪來、輸出到哪去、**誰還共用它**(拿單元名再全域搜一次用法)。」

問題:「拿單元名再全域搜一次」是純文字 grep,對 DI/反射/隱式介面(Java Spring 註解掃描、C# 容器按型別解析、Go 隱式實作)與宣告式管線(依賴寫在 DAG dependencies/排程設定)會**靜默漏抓**——不是 fail loud,是找到一部分以為找全了,跟 SOP 開頭引以為戒的「改 A 壞 B」同一失效機制,在還原階段重演。備援 `lumos impact --file` 在冷啟動(圖譜空)的目標場景不存在——盲點恰好落在 SOP 自己要解決的情境上。spec 沒有任何「grep 之外還要查什麼」的補充手段(DI 設定檔、路由表)。

## 4. 步驟 3|git 考古

### Finding 4.1 — severity: major
引句:「舊專案唯一剩下的目擊者是 git 歷史:blame 找到改這段的 commit、log 讀訊息、revert/fix 紀錄、PR 描述。」

問題:「唯一目擊者」假設一切都在 git 裡:①squash-merge 政策抹平細粒度 blame ②「PR 描述」假設 GitHub 式工作流,對郵件補丁/無 review 流程不成立 ③資料管線邏輯常定義在外部系統(Databricks notebook、Airflow UI)、韌體 why 常在硬體資料手冊——git 沉默但 why 留在別處,spec 把「git 沒有→推測/佚失」當唯一分岔,缺第三條「查非 git 來源」的路。from-scratch重生守衛_計劃 天花板段講的是「git 也沒有時老實佚失」,不是「還有非 git 來源沒查」,spec 混在一起。

## 5. 步驟 5|合約候選

### Finding 5.1 — severity: major
引句:「專案沒測試 → 先補特徵化測試(characterization test:把現況行為釘住,不判對錯)再談升格」

問題:embedded/韌體補測試是基礎設施問題非紀律問題(bare-metal 需實體硬體或 QEMU/HIL);沒測試的資料管線同樣要先重建落地環境。種子影片情境是 npm test 現成跑得動的前端專案,spec 沿用時沒補這個落差。

### Finding 5.2 — severity: minor

## 6. 步驟 6|出口 + openwiki 引用一致性

### Finding 6.1 — severity: blocker
引句:「收尾:派乾淨 agent 只讀新節點還原脈絡(自足性審計),對不上補到一致。」

問題:借用「自足性審計」既有術語但輕掉最關鍵的一半。既定定義(Verification/2026-08-21_L4交叉審計30節點清帳.md L13):「每個節點兩個乾淨 agent 交叉審計(一個只讀筆記萃取主張、一個只讀程式碼逐條判真假)」;該機制緣起=軟閘響 18,283 次 46 天沒人理,清帳實測 16.3% 主張與程式碼不一致。spec 版本是單 agent、只讀新節點本身——只能抓內部自洽,抓不到「講得通順但跟 code 對不上」,而後者正是還原型 SOP 最該防的錯誤類型。借了名字漏掉驗證力最重的那半,且沒提及落差。
對照:Verification/2026-08-21_L4交叉審計30節點清帳.md 第 13 行;Issues/自足性審計提醒空轉四十六天.md。

### Finding 6.2 — severity: major(與 6.1 同根,獨立佐證)
引句(d2 context):「openwiki 對照節點「導覽層一分為二」裁定的直接應用;影片 SOP 無此區分,AI 逆向 why 會編得非常自信。」

問題:引「一分為二」沒變形,但選擇性引用——略過同一節點同一小節對自己最不利的半句:「lumos 唯一塌陷回 openwiki 失效模式的例外=from-scratch 重生」及緩解②「真重生是對『圖譜史+code』非 code-only,底料更富」(外部對照-code衍生wiki.md L92-95)。本 SOP 的定義場景=圖譜是空的,「圖譜史」底料結構性不存在——不是邊角案例,是 SOP 存在理由本身。而 from-scratch 計劃把緩解落成 M2「from-scratch 節點強制過對抗審」,**M2 未落地**(該計劃 L74-77);spec 既沒觸發 M2 也沒交代。
