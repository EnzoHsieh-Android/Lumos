## Finding

### 文字模式每個字多跑一道隱形字判定,最壞輸出的耗時約變兩倍
severity: minor
blocking: 否
引句:「return _kill_esc(raw, wide=True, hidden=True)」
`_secinv_show` 現在對所有輸出字串都加 `hidden=True`。`_kill_esc` 是逐字呼叫 Python 函式判斷,所以文字模式的輸出越大,多花的時間越多。

失敗場景:
- 輸入:9000 篇筆記,每篇一個登記塊裡放 60 個 `{}`,全部非法,共 35MB。圖譜根目錄放在臨時目錄。
- 預期:文字模式耗時跟修前差不多。
- 實際:修前約 18.6 秒,修後約 39.0 秒(輸出約 115MB)。`--json` 不經這支函式,兩版都約 6.4 秒。
- 上限:每篇最多記 50 筆錯誤,所以輸出大小有固定上界,不會失控,只是變慢。

歸因:有證據的修復回歸。
- 兩版命令:`python3.14 scripts/lumos --vault <flood> security list`,在修前與修後各跑一次。
- 結果:修前 `rc=2 out=136015091 18.56s`,修後 `rc=2 out=114956121 38.95s`。
- 內文的 `_kill_esc` 沒變,多出來的就是 `hidden=True` 這個參數。

建議:只對登記內容與路徑字串做隱形字判定,錯誤清單的固定欄位可以走快路徑;或對不含特殊字元的字串先用正規式整串快篩。

## 三問的回答

① 原問題的修復效果,各附同一案例的修前、修後結果:
- 錯誤清單爆量(r2 資源席提的 8MB 輸入產生 279 萬筆、5GB):
  - 案例:30 篇、每篇 2MB(約 1.5MB 的 `{}` 陣列),共 57MB。
  - 修前:`--json` 輸出 4,375,001,561 位元組、RSS 11.6GB、173 秒。
  - 修後:輸出 446,251 位元組、RSS 411MB、70 秒。
  - 判定:每篇 50 筆上限有效,RSS 也有界。
- 決策表重解析(r2 提的每條控制項重解析整篇決策):
  - 案例:`dupid` 兩版輸出都是 89,942,931 位元組,分別 4.0 秒與 4.4 秒;`bigevid`(25000 條證據引用)兩版都約 1 秒。
  - 判定:耗時是線性,沒有二次方,資源面沒有退步。
- `inventory` 的 ID 查重改成集合:修後 `surf`(2000 個入口乘 1500 條控制項,每條都指到全部入口)5.7 秒、RSS 1.17GB,修前 6.8 秒。這是輸入本來就決定的輸出量,是線性。
- 檔案描述元洩漏:
  - 做法:在 `load_vault_safe` 的 6 個內部函式上各注入一次 `KeyboardInterrupt`,比對 `/dev/fd` 前後數量。
  - 結果:6 個點的差都是 0,沒有洩漏。
- 上限都在讀之前或讀的同時擋:先看 `fstat` 的大小,`_read_fd_capped` 最多讀上限加 1 位元組。這個共用函式取代了 `_vault_safe_read_rel` 與 `_retro_read_bytes` 各自的讀取迴圈。
- 本 repo 圖譜(907 篇、11MB)耗時 0.87 秒,沒有退步。

② 修補處的正常、錯誤與相鄰路徑:
- `--json` 在爆量案例下,`read_complete` 與 `references_valid` 的判定沒被截斷影響,因為用的是 `attempted()` 計數而不是清單長度。
- 巢狀 150 萬層的登記塊(`deep`)被 `RecursionError` 接住,0.78 秒、rc=2。
- 3 萬個重複登記塊(`manyblocks`)兩版輸出一致(328003 位元組)。
- 相鄰路徑 `_retro_read_bytes` 改用共用函式後,因為每次請求不超過距離上限加 1 的量,「超過 256KB」錯誤訊息裡的「至少 N 位元組」會從最多多出 64KB 變成剛好上限加 1。我沒有查有沒有測試釘死那個數字,未判定。

③ 新發現的同一案例修前、修後:只有上面那一條(18.56 秒對 38.95 秒)。
