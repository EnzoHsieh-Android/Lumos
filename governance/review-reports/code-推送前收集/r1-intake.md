## 根因分組與處置

同輪有 major(併1、通1、架1),accepted 必空,15 條全部折入。

- G1 中斷收不乾淨(併1、併2):收背景工作只殺直接子行程,全套測試各片是孫行程,Ctrl-C 或被砍後繼續跑;兩個 log 暫存檔建在暫存資料夾外,中斷時留下。→ 跑測試的子殼自己接中斷、收掉它起的各片;log 檔改放暫存資料夾內(測試紅時要給人看的那份照留,另外搬出)。
- G2 版本探測寫法(架1):掛鉤既有三處探測都讀檔找旗標字樣,這處改成執行 `--help`。→ 改成讀檔找字樣,拿掉多出來的中斷條目。
- G3 新增告警閘擋下自己(通1):兩個函式簽名一改,舊的複雜度告警被當成新的;其中 `cmd_code_loop` 複雜度實際從 53 降到 26,`_codeloop_guard_verdict` 從 35 升到 40。→ 前者附理由 lint-waive;後者把收集模式的分流抽成小函式,壓回 35 以下,不放行。
- G4 解析與輸出的小邊界(邊1、邊2):Python 端用 splitlines 切暫存檔,ref 名含 U+2028 時整筆被丟;寫暫存檔失敗的錯誤訊息擋不住。→ 照換行字元切;重導向包成一組。
- G5 兩邊各寫一份、沒測試綁(邊3、合1、合2、架3):掛鉤端的原因對照表與簡版彙總跟 Python 端各寫一份;多種類、取最後一行、提示句都沒有測試。→ 補測試(多種類、兩行機讀行取最後一行、提示句、對照表每種原因);加一支漂移測試把兩邊的原因字串綁在一起。
- G6 文件與註解(正1、合3、合4):收集模式下 pitfalls 失敗仍跑新增告警閘的差異沒寫進計劃也沒測試;手冊索引少列 push-summary;幾處註解與翻紅標籤是舊說法。→ 計劃寫明並補測試;索引補一列;註解與標籤改對。
- G7 逃逸一次推送記兩筆(通2):收集模式下合約測試紅與缺高風險審查兩句都會印,兩筆都記。→ 照原本的意圖,一次推送只記一筆(合約測試紅優先)。
- G8 找 repo 根的寫法(架2):push-summary 自己用 Path(repo),同類的 push-range 用 `_note_audit_root`。→ 改用同一支。
