# 代碼審修正關卡_計劃

白話:代碼審一輪抓到問題、編排者修好之後,現在是直接派下一輪審查員;修補本身弄出來的新 bug 要等下一輪審查員才看得到,所以很多代碼審跑三到五輪。這個計劃在「這輪問閘過了」和「派下一輪」之間加一道修正關卡:編排者寫一份修正紀錄(每組根因修了哪些檔的哪些地方、哪幾支測試守著),新指令 `lumos loop fix-check` 機械驗它——紀錄完整、測試真的存在、把紀錄裡列的修正拿掉時測試會紅、修正後會綠、受波及的合約測試全綠;第 2 步再加壓力指令、決策備忘錄底稿與統計。前兩週只提醒不擋,量到基準再決定要不要擋。

REVISIT:2026-10-30 第 2 步上線滿兩週左右,用 `lumos gov --stats` 的修正關卡段看:擋下過幾次真問題、跳過比例、每輪耗時、收斂輪數、上一輪修補造成的比例、宣告「這組沒有先紅」的組數。至少擋到過一次真問題才開「轉成擋」的小改動(做法見〈上線〉);一次都沒擋到就先檢討檢查項;帶了 `--regression-set` 的輪不到 5 輪就判「輔助指標量不到」,只看收斂輪數。

## 名詞

- **審查帳**:`docs/.canary-log.jsonl`,`lumos canary record` 寫的那本;每輪每席一筆。**載體席**:同一輪裡帶了 `--findings-set` 的那一筆(一輪只准一筆,處置閘會驗);它的 `findings_set` 是這輪的**發現清單**、`folded_set` 是**折入清單**(這輪改進程式或文件的發現)、`finding_kinds` 是每條在修什麼(`code`/`spec`/`process`,選填但給就要給全)、`finding_severities` 是個別嚴重度(選填)。代碼審載體席都帶 `round`(2026-10-02 數過審查帳 314 筆,全帶)。
- **治理帳**:`docs/.governance-log.jsonl`,各道閘的過、擋、跳過事件;`fix-check` 的事件寫這本,不寫審查帳。
- **凍結材料**:每輪派工前凍結的 `rN-snapshot.patch`;**派工單**:同一刻寫的 `rN-dispatch.json`;**編排者**:派席、判讀、修正的主會談;**辯方**:被派去反駁發現的席。都是 lumos-code-loop 手冊的詞。
- **平台、`run_cmd`、平台根**:`.lumos/config.json` 的單平台 `test.run_cmd` 或多平台 `platforms.<名>.run_cmd` / `.root`(多平台時平台根可能是子資料夾,例如 `ios/`)。
- **一支測試的判法**:規格閘那套——`_run_bound_tests` 逐支真跑,`_ran_count` 讀篩到幾個案例,`_spec_gate_declared` 數程式裡宣告了幾支名字含這個字串的測試,`_spec_gate_verdict` 判紅、綠或弱證據(篩選選到好幾支不同的測試、那一支被跳過、一支都沒跑到都是弱證據;同一支測試的多組輸入不算撞名)。
- **受波及合約測試**:`base..修正後` 改到的檔所牽連的、帶 ★INVARIANT★ 合約的節點,其合約行綁的測試;算法與判法都是推送前合約測試閘那套(`_bound_tests_check`,[[Systems/bound-tests-gate]])。
- **簿記檔**:代碼審留痕認定「改了不算改程式」的檔——`_BOOKKEEPING_FILES`、`_BOOKKEEPING_DIRS` 列的帳本與卷證,加圖譜筆記資料夾。本計劃凡說「程式有沒有改」都照它判,不另訂。
- **壓力指令**:專案自己宣告的「餵大輸入、深層巢狀、看記憶體上限」指令,例如 `python3 scripts/stress_nested.py --depth 5000`;修補常在這種輸入下才炸,所以修完跑一次。
- **決策備忘錄**:迴圈到上限時,給人裁定「再審一輪、換做法還是停」用的整理稿。

## 範圍

- 做(第 1 步):修正紀錄格式與樣板;`lumos loop fix-check` 驗六件事(紀錄完整、同類連兩輪要寫為什麼、測試存在、先紅後綠、受波及合約測試全綠、總時間);每次跑記治理帳;`lumos loop next` 在最新一輪有折入卻沒過修正關卡時印提醒、第 2 輪起的記帳範本帶 `--regression-set`;`lumos canary record` 載體席多一個選填的 `--regression-set`;把 guard kill 建、收隔離工作樹那段抽成共用函式(guard kill 改用它,行為不變);`_kill_run` 被中斷時一併收掉子行程。
- 做(第 2 步):壓力指令;`lumos loop memo` 決策備忘錄底稿;doctor 提醒沒宣告壓力指令;`lumos gov --stats` 修正關卡段。
- 不做:不改輪數上限、處置閘的判定、外家辯方、審查帳既有欄位、推送前與 CI 的全套測試;這兩步都不擋派工、不改處置閘結果(轉成擋另開小改動);設計審迴圈不適用(只對 `code-` 開頭的迴圈);不做殺傷力重跑(見〈跟提案不同〉);不修 `impact --diff` 會把純改名的檔只算新路徑那個既有洞(另開 Issue,見〈實務隱患〉);不修規格閘判「被跳過」時會把失敗訊息裡的 `1 skipped` 字樣也算進去那個既有誤判(同上,另開 Issue)。

## 做法

### 修正紀錄(每輪一份)

- 位置固定:`governance/review-reports/<迴圈編號>/<輪>-fix.json`(`<輪>` 是審查帳上那一輪的 `round` 字串,通常是 `r1`、`r2`;不解析數字)。不提供指到別處的旗標——前一輪紀錄與 `loop next` 的比對都靠固定位置找。
- `base` 的家:派工單多一個欄位 `base_commit`(派工當下 `git rev-parse HEAD` 的 40 碼;手冊第 2 步寫派工單時一起寫)。凍結材料、派工單都在卷證資料夾裡進版控,換會談、上下文壓縮之後照樣找得回來。
- 樣板:`lumos loop fix-check <迴圈編號> --round <輪> --record-template`(命名照 `--dispositions-template`)把骨架 JSON 印到標準輸出、提示印到標準錯誤(`> 檔` 重導只拿到 JSON),不寫檔:`base` 從派工單的 `base_commit` 帶入(沒有就留空)、這輪要修正紀錄的折入發現各列一組待填。只需要迴圈與輪次存在,不跑其他先決條件。
- 形狀:
  ```json
  {
    "base": "修正前的提交(40 碼)",
    "groups": [
      {
        "id": "G1",
        "category": "output-path",
        "note": "選 other 時必填一句",
        "findings": ["F1", "F3"],
        "paths": [
          {"at": "scripts/lumos:_kill_run", "status": "fixed", "tests": ["t_x"]},
          {"at": "scripts/lumos:_kill_cap", "status": "unaffected", "reason": "只截輸出,不碰檔名"}
        ],
        "no_red_reason": "只有這組的修正全在測試裡(例:發現是測試沒釘住)時才寫",
        "prior": {"why_failed": "上次修法為什麼沒守住", "new_approach": "這次換什麼做法"}
      }
    ]
  }
  ```
- `base`:修正前的提交;可以填任何認得出的寫法(短 sha、分支名),工具一律先轉成 40 碼再用、事件記 40 碼;不要求它是修正後提交的祖先(壓提交、改寫提交之後就不是了)。
- 要修正紀錄的發現:載體席有 `finding_kinds` 時,只有 `code` 的折入發現要落在某一組;`spec`、`process` 的(改文件、改流程,寫不出先紅後綠的測試)不用,輸出列出「這幾條判成不用修正紀錄」。沒有 `finding_kinds` 時全部折入的都要(寧嚴),輸出提醒「記帳時帶 `--finding-kind` 可讓文件、流程類發現免填」。
- 根因類別固定清單(`category` 只能填左邊的值):`escaping` 跳脫或清洗不完整、`path` 路徑處理、`nesting` 巢狀深度或遞迴、`output-path` 輸出路徑不一致(文字對 JSON 等)、`name-collision` 名稱碰撞、`concurrency` 並行或交易邊界、`perf-memory` 效能或記憶體、`boundary` 邊界值、`other` 其他(要寫 `note`)。
- 路徑狀態兩種:`fixed`=這條路徑這次修了,要列守著它的測試;`unaffected`=查過、同一根因不會出現在這裡,要寫理由。
- `at` 寫「檔案:函式」,在第一個冒號切開(檔案路徑不含冒號;函式那段可以含 `::`、不能是空的);檔案要在修正後的提交裡,函式那段要在那支檔裡出現、前後不接英數字或底線(不驗它真的是函式定義——各棧寫法不同,驗到字面就停)。`fixed` 的檔必須在 `base..修正後` 之間有改動(標了已修卻沒改過那支檔=紀錄寫錯)。路徑一律用 `-z` 取得、不經 git 的引號跳脫(中文、空白檔名照原樣比)。
- **★`fixed` 列的檔就是「這次的修正」★**:先紅那邊只把這些檔換回 `base`(見下),其他檔(測試、夾具、資料、沒列的程式)一律留修正後的版本。所以修正動到幾支檔,就要把幾支檔都列成 `fixed`——漏列的那支不會被換回去,先紅那邊多半會判「修之前就通過」(失敗方向是擋)。
- `no_red_reason`:這組的修正全在測試裡(發現本身是「測試沒釘住」)、拿掉修正就等於拿掉測試時寫(至少四個字、要有實字);寫了這組的測試只跑綠那邊、不跑紅那邊,輸出列「這組沒驗先紅」並記進事件。
- `prior` 只有同類連兩輪(見下)才必填。

### `lumos loop fix-check <迴圈編號> --round <輪> [--repo <根>] [--json]`

名字:頂層的 `fold-check` 已經是設計審「折完看前後矛盾」的指令,所以放在 `loop` 底下叫 `fix-check`。`--repo` 照 `loop status` 的寫法(預設現在的 repo)。

一開始:記下 `HEAD` 的 40 碼當**修正後**——之後所有步驟都在對這個提交建的隔離工作樹裡跑,事件也記它;主工作目錄只讀審查帳、治理帳與修正紀錄,跑的期間別的會談改檔、提交都不影響這次結果。掃一次上次被砍留下的殘骸(見〈中斷與殘骸〉)。整次執行期間把行程環境的 `TMPDIR` 指到修正關卡自己的暫存資料夾(子行程繼承;結束時刪掉、還原環境),本 repo 的測試工具紅的時候會在 `TMPDIR` 留暫存現場。

先決條件(任一不成立回 2、印原因、不寫治理帳事件——這是輸入錯,不是驗了沒過):
- 迴圈編號是 `code-` 開頭;審查帳找得到這一輪的載體席。要修正紀錄的折入發現是 0 條 → 印「這輪沒有要修正紀錄的折入,不用跑」回 0、不寫事件。
- 修正紀錄讀得到、是合法 JSON(解析深度過深、形狀不對都回 2;解析沿用治理帳那支容錯讀法的防護)、`base` 轉得成存在的提交。
- 平台根都在 repo 裡(算相對路徑失敗就回 2,說明哪個平台)。

不是先決條件、只印提醒:主工作目錄有簿記檔以外的已受版控改動沒提交(含已暫存,`git status --porcelain -z`;改名條目兩個路徑都看)→ 印「這次驗的是提交裡的版本,工作目錄這幾支沒提交的改動不算」列前幾支。同一個 repo 常有別的會談的改動,所以不擋;修正忘了提交時,先紅那邊多半會判「修之前就通過」或 `fixed` 的檔沒改動。

逐項驗(任一不過整次回 1;能驗的都驗完再一起印,輸出寫明哪一項、哪一組哪一條、怎麼修):
1. **紀錄完整**:要修正紀錄的折入發現每條都落在某一組;組裡的發現都在這輪的發現清單裡;類別在固定清單裡,`other` 有 `note`;每組至少一條 `fixed` 路徑;每條 `fixed` 至少一支測試,測試名去掉前後空白後不能是空的;每條 `unaffected` 有理由(至少四個字、要有實字,判法同 `[manual:]`);`at` 的檔與函式找得到,`fixed` 的檔有改動。
2. **同類連兩輪**:審查帳上這一輪的前一輪(照帳上輪次出現的順序)有修正紀錄、其中有一組跟這組同類別,而且這組收的發現裡有任一條嚴重度 ≥ major,這組就必須有 `prior.why_failed` 與 `prior.new_approach`(各至少十個字)。個別嚴重度看載體席的 `finding_severities`;沒記的那條改看這一輪各席宣告的最高嚴重度(這輪最高只到 minor,就整輪都當 minor)。
3. **測試存在**:每支測試名包成 `[test:名]` 交給合約綁定那套解析(`resolve_test_refs`),要恰好解析出一支、而且在綠樹的測試索引裡找得到(`_platform_test_index` 的根換成綠樹);只在原始碼文字裡出現、或找不到的都算不過。
4. **先紅後綠**:開兩個隔離工作樹,都檢出修正後的提交(用從 guard kill 抽出的共用函式建、收;見〈共用的隔離工作樹〉):
   - **綠樹**:原樣。
   - **紅樹**:把這輪修正紀錄所有 `fixed` 路徑的檔,在紅樹裡用 `git checkout <base> -- <檔>` 換回 `base` 的內容(`base` 沒有那支檔就刪掉)。用 git 換,符號連結、執行權限、二進位檔照 git 的規則處理,不會穿過連結寫到工作樹外;`base` 那邊是子模組指標或資料夾時換不了 → 這項判不過並說明。紅樹 = 修正後減掉紀錄列的修正,其他一律不動,不靠路徑猜哪些是測試、哪些是程式。
   - 依賴資料夾預設不連:`.lumos/config.json` 的 `fix_check.link_dirs`(相對 repo 頂的路徑清單,例如 `["node_modules", "ios/Pods"]`)列了的,才在兩棵樹的同一位置用連結指回主工作目錄(寫法照新增告警閘的 `_lint_link_deps`)。不預設連的理由:Python 可編輯安裝、Node 的 workspaces 會讓紅樹經由連結載到主工作目錄裡修正後的程式,紅那邊失真(第 2 輪審查實測);要連的專案自己宣告,並在〈實務隱患〉看清楚這個風險。
   - 跑法與判法全部沿用規格閘(見〈名詞〉):要跑的測試(沒寫 `no_red_reason` 的組的測試)在綠樹用 `_run_bound_tests(綠樹, …)` 跑、在紅樹用 `_run_bound_tests(紅樹, …)` 跑(它在「工作樹 + 平台根」用平台的 `run_cmd` 帶 `{method}` 跑,逾時 `LUMOS_TEST_TIMEOUT` 預設 180 秒),每支結果用 `_ran_count`、`_spec_gate_declared`(宣告集照規格閘拿放寬那份)、`_spec_gate_verdict` 判:
     - 綠樹判綠 → 綠那邊過;判紅或弱證據 → 不過(弱證據附規格閘給的原因;另附一句「如果是隔離工作樹缺東西——子模組、依賴資料夾——在主工作目錄跑得過也算這項不過,請看輸出判斷;依賴資料夾可用 `fix_check.link_dirs`」)。
     - 紅樹判紅 → 紅那邊過;其中因逾時判紅的(修卡死類的修正,修之前跑不完)照樣算過,輸出標「逾時算紅」。紅樹判綠 → 不過:「修之前就通過,沒守住這次的問題」。紅樹判弱證據 → 不過,附原因(例:「篩選匹配到 2 支,測試名要唯一」——紀錄寫 `t_fcdemo`、還有一支 `t_fcdemo_strip` 時;同一支測試的多組輸入不算)。這棧讀不出支數(`_ran_count` 回不出數字)時,規格閘照退出碼判,輸出標「這棧讀不出支數」;但讀得出支數的棧(像 python)在沒逾時卻讀不到支數時,當成「修之前選不到這支測試」判不過。
     - 平台的 `run_cmd` 沒有 `{method}`(只能整套跑)→ 這支判不過並說明(同規格閘)。
5. **受波及合約測試全綠**:在綠樹裡呼叫 `_bound_tests_check(綠樹, "base..修正後")`(推送前那道閘的同一支,含過濾探針那層;它寫的治理帳事件、測試快取都落在綠樹裡、跟著刪掉,不進主 repo;過濾探針的快取鍵含樹的路徑,所以每次都會重探一次,讀不出支數的棧每次多一次探針,接受)。`green`、`no-pins`、`no-bound`、`no-vault`(沒有牽連合約)過,後三種印說明;`red`、`unfilterable`(回成功但證不出跑過)、`no-config`、`diff-unavailable`、`range-unavailable`、`whole-suite-deferred` 不過;`skipped`(有人設了 `LUMOS_SKIP_BOUND_TESTS`)也不過,印「合約測試被跳過,這項沒驗;要跳過整道修正關卡請用 `LUMOS_SKIP_FIX_CHECK`」。`base..修正後` 有簿記檔以外的檔被改名時這項也判不過,印「改名的檔,舊路徑牽連的合約沒算到」(`impact --diff` 只算改名後的路徑,見〈實務隱患〉)。照檔案對應(測試地圖建過才有;那份地圖不進版控,讀主工作目錄的)推出來的測試檔只印成「參考:可能也該跑」,不跑。
6. **總時間**:`.lumos/config.json` 的 `fix_check.budget_sec`(秒,照鄰居時間設定的單位;預設 1200;0、負數、不是數字都用預設並印一行警告)。每支測試的逾時取「自己的逾時」與「剩下的時間」較小的;用完時還沒跑的測試與項目不跑、這項判不過,印「超過總時間,沒驗完的是哪些」。第 5 項開始前剩不到 300 秒就不跑它、判不過;開始之後跑到完(它沒有中途停的入口),所以整次最多超出預算一段第 5 項的時間。

另外(只印,不影響過不過):這一輪不是第一輪、載體席沒有 `regression_set` 欄(看欄位在不在,空清單=判過沒有,不算沒填)→ 印一行提醒(帳已經記了補不了,提醒的是下一輪記帳時要帶)。

記帳與跳過:
- 跑完逐項驗(過或不過)用 `_gate_event_or_warn` 寫一筆治理帳,閘名 `fix-check`(加進 `_KNOWN_GATES`)、`hard=False`;kind:過 `passed`、不過 `warned`(這兩步都只提醒不擋,照不擋的閘的用字;轉成擋那個改動再改成 `blocked`)、跳過 `skipped-env`;`head_sha`=修正後的 40 碼;`extra` 放 `loop`、`round`(兩欄名稱與型別同審查帳)、`record_sha256`、`secs`(浮點,同合約測試閘事件的欄名)、`failed_items`(不過的項目代號清單)、`no_red`(宣告不驗先紅的組數)、`token`(每次跑的隨機碼)。
- 治理帳讀端(`cmd_gov` 的轉換)對 `fix-check` 事件吐出 `token`(去重鍵本來就含 `token`,轉換沒吐它,同一個提交上連跑兩次同結果就會被折成一筆)與上面這些欄位;`_GOV_FIELD_TYPES` 補 `record_sha256`、`secs`(收整數與浮點)、`failed_items`、`no_red`、`head_sha` 的型別——第 2 輪審查掃過三本帳(治理帳約 10 萬筆、審查帳約 2600 筆、簽核帳 8 筆),這幾個欄名沒有型別衝突;實作時加之前再掃一次,不得讓任何既有行從「型別對」變成「型別不對」(第 1 輪審查實測:照第 1 版補 `tests` 整數型別,會讓 81 筆既有審查帳行被靜默丟掉)。
- 寫不進治理帳(沒有 `docs/`)時照 `_gate_event_or_warn` 印警告,輸出多一句「這次通過沒記到帳,`loop next` 會一直提醒」。
- `LUMOS_SKIP_FIX_CHECK=1`:不驗、回 0、記一筆 kind `skipped-env`。

### 中斷與殘骸

- `_kill_run` 在等子行程時收到任何中斷(Ctrl-C 等),先砍掉整個子行程群組再往上丟(現在只有逾時才砍,第 1 輪審查實測 Ctrl-C 後測試子行程變孤兒、而它的資料夾已被刪)。合約測試閘、規格閘、guard kill 也用它,行為只多「被中斷時收乾淨」(第 2 輪審查查過三處呼叫者,不衝突)。
- `fix-check` 執行期間把 SIGTERM 轉成跟 Ctrl-C 一樣的例外,讓收工作樹的 finally 跑得到;結束時還原原本的處理方式。專案裡目前沒有訊號處理的先例(第 2 輪審查查過),這是第一個。
- 被 SIGKILL 這種收不到的砍法時一定會留殘骸。共用工作樹函式在建暫存資料夾之後、`git worktree add` 之前,先在暫存資料夾寫一個標記檔(行程編號與建立時間);呼叫端可以要求開頭先掃殘骸(修正關卡要求,guard kill 不要求、行為不變):掃 `git worktree list --porcelain`,兩邊路徑都先取實際路徑再比(macOS 的暫存資料夾 `/var/...` 跟 git 印的 `/private/var/...` 是同一個),只認「位在系統暫存資料夾底下、資料夾名以修正關卡前綴開頭」的;標記檔的行程還在的不動(行程編號被重用就保守地當成還在);沒有標記檔的,資料夾修改時間超過 24 小時才清(標記檔寫之前那一瞬間被看到、或是別的工具建的,都不會被誤刪)。清法:`worktree remove --force`、刪資料夾、`worktree prune`。
- 被砍的那一次不會有治理帳事件(耗時統計只算跑完的,這點寫進統計段的說明)。

### 共用的隔離工作樹

- 把 `cmd_guard_kill` 裡「暫存資料夾 + `git -C <在哪建> worktree add --detach <路徑> [<提交>]` + finally 收掉(`worktree remove --force`、刪資料夾、`worktree prune`)」抽成一個共用函式(with 區塊),參數:在哪個 repo 建(guard kill 傳平台所在 repo 的頂層,照它現在的 `-C`)、檢出哪個提交(空的就不帶,照 guard kill 現在 `ghead` 為空時的寫法)、資料夾前綴、要不要保留(`--keep-worktree`;保留時照 guard kill 現在印出路徑的方式)、開頭要不要掃殘骸、標記檔。`worktree add` 失敗時不丟例外、回傳失敗原因,呼叫端自己決定(guard kill 照現在記成 error 繼續下一個平台;修正關卡判這項不過)。函式只管 repo 頂層;平台根的子路徑由呼叫端自己接。
- 第 2 輪審查查到現在沒有測試釘住 guard kill「`worktree add` 失敗」與「多平台路徑」兩條,抽函式前先補這兩條測試,再抽(先綠、抽完照綠)。

### `lumos loop next` 的提醒與記帳範本(第 1 步)

- 代碼審迴圈、審查帳最新一輪的載體席有要修正紀錄的折入發現,而且治理帳找不到符合下列全部條件的 `fix-check` 事件 → 在輸出加一行提醒與要敲的指令(指令裡的編號與輪次照 shell 規則加引號;`--json` 多一個 `fix_check` 欄位):kind `passed`、`loop` 與 `round` 相同、`record_sha256` 等於現在那份修正紀錄檔的 sha256、事件的 `head_sha` 跟現在的 `HEAD` 之間沒有簿記檔以外的檔案改動(`git diff --no-renames --name-only -z`;那個提交已經不存在也算有改動)。不管這次判到哪個狀態(`plant-canary`、`gate-pending`、`converged`、`cap-reached`、`escalate`)都印——★到上限那條路尤其要印★:最後一輪的修補沒有下一輪審查會看到,推之前跑一次修正關卡是唯一的機械檢查。修正紀錄檔不存在也印(提醒裡說要先寫、附 `--record-template` 指令)。
- 第 2 輪起,`loop next` 給的載體席記帳範本多帶 `--regression-set <id串|none>`。
- 狀態、回傳碼都不變;設計審迴圈不印。
- 讀治理帳:新寫一支讀函式,逐行先用字串預篩含 `"fix-check"` 的行再交給 `_drift_jsonl_parse`,壞行跳過(本 repo 治理帳約 16MB,第 1 輪審查實測預篩掃一遍約 0.1 秒)。

### `canary record --regression-set`(第 1 步)

- 載體席選填 `--regression-set <id 串|none>`:這輪的發現裡,編排者判斷是上一輪修補造成的;`none`=判過、這輪沒有。解析照 `--folded-set`;id 都要在 `--findings-set` 裡,否則回 2;沒帶 `--findings-set` 的那筆帶了回 2(加進 `cmd_canary` 那串「要跟 `--findings-set` 一起給」的旗標);這個迴圈在審查帳上還沒有更早的輪、卻帶了非空的清單,回 2(第一輪沒有「上一輪」)。存成排過序的 `regression_set` 清單(`none` 存空清單)。
- 由編排者標,辯方不推翻(辯方只殺程式層的假陽性,「是不是上一輪造成的」要看兩輪的改動,屬編排者的判讀)。所以它只當 RETIRE-IF 的輔助指標,主指標是機械數得出來的收斂輪數。
- 不加進 `--finding-kind` 的值:那欄是「這條在修程式、文件還是流程」,是量流程自產工作量的唯一欄位;上一輪修補造成的發現也是程式缺陷,混進去會把那個量弄壞。
- 欄位說明寫進管處置欄位的 [[Systems/finding-refute]](`folded_set`、`finding_kinds` 也在那篇)。

### 第 2 步

- **設定讀取**:新增一支讀 `.lumos/config.json` 的 `fix_check` 區塊的函式(照 `_drift_config` 那類寫法:沒設定用預設、單一欄位讀不懂用預設並警告,不整個關掉),第 1 步的 `budget_sec`、`link_dirs` 也走它——所以這支函式第 1 步就建,第 2 步只加 `stress` 欄位。
- **壓力指令**:`fix_check.stress` 是陣列,每項 `{"cmd": "…", "timeout": 秒}`(逾時預設 300);`fix-check` 在綠樹的 repo 頂逐條跑,非 0 或逾時算不過,也吃總時間。沒宣告 → 印提醒、這項算過,事件記 `stress: "undeclared"`;宣告成空陣列並寫 `fix_check.stress_none_reason`(至少四個字)算已宣告。
- **決策備忘錄底稿**:`lumos loop memo <迴圈編號>`(唯讀,印到標準輸出)整理審查帳上每一輪:嚴重度、發現數、折入、放行與理由、重現不到的、上一輪修補造成的;再加每輪修正紀錄的組與類別、`fix-check` 最後一次的結果;最後留「選項與各自代價」「建議」兩節給編排者填,填完拿去問人。代碼審迴圈 `loop next` 判到上限時,多印這個指令。
- **doctor 提醒**:新開一段(照 doctor 既有段落編號往下排、記 `check-` 事件):治理帳裡有過至少一筆 `fix-check` 事件、而 `fix_check.stress` 沒宣告 → 印一行提醒;從沒跑過修正關卡的專案不吵。
- **統計**:`lumos gov --stats` 多一段修正關卡:`passed`/`warned`/`skipped-env` 次數、耗時中位數(只算跑完的)、最常不過的項目、宣告不驗先紅的組數、代碼審迴圈收斂所需輪數、每輪發現裡上一輪修補造成的比例(審查帳讀端要補轉 `regression_set`;帶了的輪才算進分母,沒帶的印 ?)。

### 上線

- 第 1 步、第 2 步各一個功能提交、各走代碼審。
- 兩步都只提醒不擋。轉成擋是另一個小改動:`loop next` 在缺通過紀錄時改回新狀態 `fix-check-pending`;處置閘加一步「上一輪有要修正紀錄的折入就要有修正關卡通過紀錄」,只對首筆帳晚於切換日的迴圈生效(另寫一支切點判斷,寫法照 `_panel_retired_for`:常數日期 + 環境變數覆寫 + 不像日期的時間戳當舊帳),舊迴圈回放不翻;不過時的 kind 改成 `blocked`。條件與時間見上面的 REVISIT。

## 跟提案不同

- 指令名 `lumos loop fix-check`(提案寫 `loop fold-check`,頂層 `fold-check` 已被佔用,同名會讓人以為是同一件事)。
- 修正紀錄用 JSON、位置固定、提供樣板,`base` 記在派工單(提案留給工具鏈決定)。
- 「上一輪修補造成的」用新的選填欄 `--regression-set`,不加進 `--finding-kind`(理由見上);RETIRE-IF 主指標改成機械數得出來的收斂輪數,這個比例只當輔助(編排者自報,沒有機械對照)。
- 受波及的測試只跑合約測試+紀錄裡的測試(Enzo 2026-10-02 裁定)。
- 同類連三輪不另設規則、決策備忘錄不設機械擋:高風險與一般代碼審上限都是三輪,連三輪必然同時到頂;到頂本來就停下來問人,備忘錄改成到頂時印底稿指令(Enzo 2026-10-02 裁定)。
- 修正提交不另記欄位:`fix-check` 一開始釘住當下的提交,治理帳記它。
- 先紅那邊不是「把程式退回修正前、只套上新測試」,而是「從修正後出發、只把紀錄列為已修的檔換回修正前」:哪些檔算「修正」由寫紀錄的人列,不靠路徑猜(兩輪設計審都證明猜會錯);效果一樣是「只有修正被拿掉」。
- 文件、流程類的折入(`finding_kinds` 記 `spec`/`process`)不要求修正紀錄:寫不出先紅後綠的測試(審查帳上代碼審約兩成的輪折過這類);修正全在測試裡的組可以宣告不驗先紅(要寫理由、會被統計)。
- 不做殺傷力重跑:提案的動機實例(配方原文對得上卻打在錯的路徑)是改配方時的問題,不是修程式時的;路線圖下一項 1a-3「重加後可當場試跑那一條、健康檢查列出真跑沒抓到的配方」正是處理它的地方;做在這裡還要改 guard kill 能只跑指定配方,單次修正關卡也會超過十分鐘(第 1 輪審查估)。轉交 1a-3 考慮「修正改到配方指著的檔時提醒重跑」。

## 實務隱患

- **時間**:先紅後綠每支測試跑兩次;本 repo 一支 `-k` 測試實測約 2.7 秒、建一棵工作樹約 2 秒(第 1 輪審查量),一輪修正通常 3–10 支,先紅後綠約 1–2 分鐘;受波及合約測試在綠樹裡實測 59 支 258 秒(第 2 輪審查量);第 2 步壓力指令每條逾時預設 300 秒。總時間預設上限 1200 秒,第 5 項開始後不中斷。實測補進〈實作紀錄〉;每輪中位數超過 15 分鐘就是 RETIRE-IF 的一條。
- **修正紀錄漏列檔**:先紅那邊只換回 `fixed` 列的檔;修正其實動了三支檔、紀錄只列一支時,紅樹還帶著另外兩支的修正,多半判「修之前就通過」→ 回 1,失敗方向是擋;極少數情況(漏列的那支剛好不影響這支測試)會照樣過,這時紀錄本來就該補那支的 `fixed` 或 `unaffected`,屬紀錄品質,不是判法放水。
- **讀不出支數的棧**:只有 python 的輸出讀得出支數;其他棧的紅綠照退出碼判、標「這棧讀不出支數」,也沒辦法擋「名字選中多支」——那幾個棧的子字串誤判要等它們的支數樣式補上才擋得到。第一個非 python 消費專案跑修正關卡時(看治理帳第一筆非本 repo 的 `fix-check` 事件),回頭看這段的誤判情況。
- **依賴資料夾**:預設不連,需要的專案在 `fix_check.link_dirs` 自己列;列了之後,Python 可編輯安裝、Node 的 workspaces 這類「依賴資料夾裡指回專案原始碼」的設置會讓紅樹載到主工作目錄裡修正後的程式,紅那邊判「修之前就通過」(失敗方向是擋,但會誤擋)。第一個宣告 `link_dirs` 的專案接入時,在那次接入的紀錄裡實測一次紅樹載到的是哪一份。
- **程式跟測試寫在同一支檔的棧**(像 Rust 的檔內測試):把 `fixed` 的檔換回修正前,同時也把測試拿掉了,紅那邊會判「選不到這支測試」→ 不過;這種組可以寫 `no_red_reason`。本工具鏈目前支援的棧都是分開的測試檔,沒實測;第一個用檔內測試的棧接入時(新增那個測試 profile 的提交),在那次的計劃裡重看這段。
- **改名**:`impact --diff` 用 git 預設的改名偵測,純改名的檔只算新路徑,舊路徑牽連的合約會漏(第 1 輪審查實測:改一行時牽連 26 篇,純改名後 0 篇)。這是推送前合約測試閘也有的既有洞,另開 Issue 修;修正關卡這裡先保守:有簿記檔以外的檔改名就把第 5 項判不過。
- **規格閘判「被跳過」的既有誤判**:`_ran_count` 只要輸出裡出現 `1 skipped` 這類字樣就當成有跳過,失敗訊息裡剛好有這串字時,紅那邊會被判弱證據 → 不過(失敗方向是擋;第 2 輪審查指出)。沿用規格閘就一起沿用這個洞,另開 Issue 在 `_ran_count` 修,兩邊一起好。
- **紀錄寫錯的代價**:`base` 填錯(例如填成已含修正的提交)會讓紅那邊判「修之前就通過」→ 回 1,失敗方向是擋,不是放水。
- **治理帳比對**:`loop next` 的提醒靠修正紀錄 sha256 與提交都對得上;紀錄改過、或之後又改了程式就要重跑——這是故意的(驗的東西變了)。
- **共用工作樹函式動到 guard kill**:1a-4 剛改過 guard kill;抽函式只搬建、收那兩段,不碰套壞法、等新的一秒、還原那些;先補兩條沒被釘住的行為測試(S13)再抽,`-k guard_kill` 子集當回歸。
