# 紅燈版實跑三缺口_計劃

> 白話:規格閘紅燈版那批推上去之前,在 mOrangePos 考場拿一個假想功能(結帳服務費,五條驗收條款,四條 JVM、一條平板儀器測試)從設計一路走到推送前驗收,實跑抓到三個自動測試沒抓到的缺口:字串預期值被改漏報、平板測試在推送前被丟到 JVM 指令跑而誤判紅、專案把治理帳設成忽略時紅燈版的提醒指錯方向。這份計劃三個一起修。

## 名詞

- 比對工具:推送前新增告警閘裡的測試防竄改比對(`lumos test-guard`),拿「改動前」的測試跟推送版逐支比,列出改弱、改預期值、刪測試這類候選。
- 分岔點比對:拿這條分支跟主線分岔那一版的測試當改動前版本。新測試在分岔點不存在,所以另有紅燈版比對。
- 紅燈版:規格閘判出紅的那一刻,把那支 Kotlin/Java 測試檔整份存到消費專案的 governance/redbase/ 資料夾;紅燈版比對拿它當新測試的改動前版本。
- 留痕:規格閘判完寫的一筆紀錄,寫進審查帳(本機)與治理帳(`docs/.governance-log.jsonl`,進版控),記測試名、條款指紋、紅燈版的路徑與指紋。推送前驗收照它重跑測試。
- 孤兒紅燈版:紅燈版檔在提交裡,治理帳裡卻沒有任何留痕指到它。
- 放行指紋:比對工具每條候選的 16 碼身分,`lumos lint-waive` 認它放行;身分字(`_tg_rb_bad` 的 ident 參數)是組成指紋的那段穩定文字,不給就用整句提醒。
- 逃逸:推送閘擋下風險低計劃時自動記進逃逸帳的一筆,意思是「沒人審的計劃在下游被抓到洞」。
- 平台:專案設定 `.lumos/config.json` 的 platforms 底下每一項(各有根目錄、測試格式、跑單支測試的指令);`default_platform` 是條款裡 `[test:名字]` 沒寫前綴時用的那一個。考場設了 android(JVM 單元測試)與 device(平板儀器測試)兩個。
- 考場:mOrangePos 的演練工作樹與只留本機的分支,不推、不併。

## 問題與最小解

立案(2026-11-03,Enzo 原話依序):「我機器接起來了，你直接測」→「測試應該是以一個假想功能設計為始，測試拆分驗收項目、直到串到真正驗收那環」→(看完實跑結果)「修」。

實跑卷證在 mOrangePos 考場本機分支 drill/service-charge-e2e 的 drill-evidence/redbase-real/(只留本機;公開摘要在落地的驗證紀錄)。三個缺口:

1. **字串預期值被改漏報**:比對工具切斷言參數時只數括號深度、沒跳過字串,`assertEquals("服務費 $1,235", label(fee))` 被切成三個參數(`"服務費 $1`、`235"`、`label(fee)`),預期值被改的那一半落進「其餘部分」,新舊兩行配不起來。分岔點比對(`tq/expected-changed`)與紅燈版比對(`tq/redbase-weakened`)用同一支切法,兩邊都漏。金額、清單、JSON 這類字串預期值很常見。同一支切參數函式另有 Room 守衛一處呼叫,那裡拿到的是已剝字串的原始碼,不受影響。
2. **推送前把非預設平台的測試丟到預設平台的指令跑**:規格閘留痕的 tests 欄只記方法名,丟了 `[test:device:名]` 的平台前綴;推送前照預設平台(JVM)的指令跑平板測試,Gradle 回「找不到測試」、退出碼非零被判紅。結果是正確的程式也推不上去,而且推送閘還自動記一筆假的逃逸(風險低計劃被推送閘擋下會自動記逃逸)。舊留痕在實作完成後重跑規格閘也不會被重寫(條款全綠、最新留痕風險低、條款指紋與門規則版本都相同時不寫新留痕,`_spec_gate_low_not_red`),不補相容會永遠卡住。
3. **治理帳被忽略時孤兒紅燈版的提醒指錯方向**:mOrangePos 的 .gitignore 從 2026-06 起忽略 docs/.governance-log.jsonl(那時一次會談手動加的,早於 2026-09-09「治理帳不能被忽略」那條規則),規格閘寫的留痕進不了提交,每份紅燈版推送時都成了孤兒,提醒卻說「多半是合併時解治理帳衝突弄丟了那一行」、叫人去版本紀錄找一支從沒提交過的檔。紅燈版照樣拿內容比、不會漏擋,問題是提醒指錯方向。同一族的另一句「工作目錄有還沒提交的紅燈版檔:請 git add 那支檔與治理帳一起提交」在治理帳被忽略時也一樣錯:git add 被忽略的檔會失敗。

舊否決比對(開審前,2026-11-03):`lumos rejections` 427 行按概念比過。最接近的是 [[Systems/test-guard]] 否決的「孤兒檔當沒有紅燈版」;本案孤兒照樣拿內容比,只改提醒措辭,不撞。其餘(只記版本編號、內容寫進治理帳本體、帳本 merge=union)與本案無關。

最小解:①切參數時照「字串內容換成等長空白」那份文字找逗號與括號,再回原文取字;②留痕寫測試時非預設平台帶前綴,推送前讀到沒前綴的舊名字時照現在計劃條款寫的平台補;③孤兒紅燈版的提醒先問 git 治理帳是不是被忽略,是就講明是哪一行忽略規則、怎麼改,規格閘寫紅燈版當下也提醒一次。

PRIOR-ART: 切函式參數的通用做法是一趟掃描同時記括號深度與「在不在字串裡」(Foundry 的 split_call_args 照頂層逗號切、略過括號與引號裡的逗號:https://foundry-rs.github.io/foundry/cast/call_spec/fn.split_call_args.html);本案借本檔既有的「字串內容換成等長空白」掃描(`_strip_c_comments` 的 keep_length,括號配對已經在用它),不另寫一支詞法掃描。測試身分帶執行環境:JUnit Platform 的 UniqueId 第一段就是 engine(https://docs.junit.org/5.0.0-M6/api/org/junit/platform/engine/UniqueId.html),同名測試在不同執行環境是不同的測試,留痕記平台是同一個道理。必要檔被忽略的檢查沒有現成工具,通用做法是 `git check-ignore -v` 列出蓋到的那一行規則(https://man.he.net/man1/git-check-ignore);本案照抄,不新增設定;git 呼叫借本檔既有的 `_lens_git`,判法照 `_local_ledger_doctor_msgs`(先判已追蹤、再判忽略)。
RETIRE-IF: 三個修補都是修正既有機制的錯,不新增機制;紅燈版整套撤掉時(見 [[Projects/規格閘紅燈測試快照_計劃]] 的撤除條件)第 3 項的兩句提醒跟著撤,第 1、2 項屬比對工具與推送閘本身,不隨之撤 [retire:人裁] [until:2027-05-03]

## 做法

1. **切參數不切字串裡的逗號**:`_tg_call_parts` 已經用剝字串後的文字(`_tg_strip`,字串內容換成等長空白、長度跟原文一一對應)配括號,切參數卻用原文。`_rg_split_args` 加一個選填的遮罩參數(長度同原文):給了遮罩時,一個逗號要「遮罩那一格是逗號、遮罩算的括號深度是 0、原文算的括號深度也是 0」才當分隔,其餘照原文取字。兩邊都要是 0 的理由:遮罩掃描不認 Kotlin 字串模板裡的巢狀引號(`"${foo("a,b")}"` 會被當成兩段字串,中間的 `a,b` 露在外面),只看遮罩會把這種寫法切錯、比現況退步;只看原文就是現況的錯。兩邊都要求時,切點只會比現在少,少掉的都是字串裡的逗號。Room 守衛的呼叫不帶遮罩(它拿到的本來就是剝過字串的原始碼),行為不變。已知不處理:字串裡有不成對的括號時(`"a(b"`),原文深度在字串後面仍是 1,後面真的分隔逗號照舊切不到,跟現況相同。
2. **留痕記平台**:`_spec_gate_record` 拿不到平台(收的 `names` 在 `_spec_gate_prepare` 就丟了平台,而且同一份 `names` 還餵給雙向判定,不改它的形狀);改成呼叫端另把 `_spec_gate_items` 算出的 (條款, 平台, 方法) 傳進來,寫 tests 時非預設平台寫成 `平台:名字`,預設平台照舊寫名字(舊讀者不受影響)。推送前 `_spec_gate_push_one` 讀到沒有前綴的名字時:留痕沒過期(條款指紋相符,現在的條款就是當時記的那份)才看現在計劃條款裡同名的引用,只綁在一個非預設平台就用那個平台;其餘照舊用預設平台。條款指紋不符而計劃已完成的那條路不補平台(條款可能改綁到別的平台,補了會補錯),照舊用預設平台、找不到就走既有的「留痕裡的測試找不到」提醒。條款指紋不含平台設定本身(`.lumos/config.json` 改了平台指令不算過期),這是既有行為。
3. **治理帳被忽略的提醒**:比對工具遇到孤兒紅燈版,或「工作目錄有還沒提交的紅燈版檔」時,問一次 git 治理帳是不是被忽略(只在真有這兩種情形時問,一次推送最多問一次):先 `git ls-files --error-unmatch` 判已追蹤(已追蹤就不算被忽略,改動照樣能提交),再 `git check-ignore -q` 判被忽略(會照 `!` 否定規則算),被忽略才用 `git check-ignore -v` 取出蓋到的規則來源與行號(不一定是 `.gitignore`,也可能是 `.git/info/exclude` 或全域忽略設定)。被忽略時兩句提醒都換成「治理帳被 git 忽略(來源:行號:規則),規格閘留痕進不了提交:加一行 `!docs/.governance-log.jsonl` 或把那條規則收窄;上層目錄整個被忽略時要改那條規則」,沒被忽略照舊。兩句提醒的身分字改用固定字(孤兒、還沒提交),措辭換了放行指紋不變;2026-11-03 立案時紅燈版那批停在 PR #153、未合併,沒有專案存過這兩句的放行,所以換身分字不會讓既有放行失效。規格閘寫出紅燈版時也照同一個判法問一次,被忽略就多印一行同樣的提醒。
4. **考場的假逃逸**:實跑時推送閘誤判紅、自動記了兩筆逃逸(只在考場本機的逃逸帳,沒進任何版控)。修完重跑考場時用 `lumos loop escape --withdraw` 撤回並附理由,撤回是追加一筆、統計不算。

## 驗收條款

- [S1] 當測試只把字串預期值 `"服務費 $1,235"` 改成 `"服務費 $1,234"` 時,比對工具應列出那支測試(分岔點比對列 tq/expected-changed、紅燈版比對列 tq/redbase-weakened;字元常值與三引號字串裡的逗號同樣不當分隔,兩行一字不差不列;Kotlin 字串模板 `"${foo("a,b")}"` 切法跟現況相同) [test:t_tq_guard_string_comma_args]
- [S2] 當規格閘寫留痕時,留痕的 tests 欄應把非預設平台的測試寫成「平台:名字」(預設平台照舊只寫名字),推送前照前綴的平台指令跑那一支 [test:t_spec_gate_record_keeps_platform]
- [S3] 當推送前讀到只寫名字的舊留痕、留痕沒過期、而那個名字在現在的計劃條款裡只綁在一個非預設平台時,推送閘應照那個平台的指令跑(條款裡找不到、綁在預設平台、或計劃已完成而條款指紋不符,照舊用預設平台) [test:t_spec_gate_push_bare_name_platform]
- [S4] 當治理帳被 git 忽略時,孤兒紅燈版與還沒提交的紅燈版兩句提醒應講明治理帳被忽略並附蓋到的規則與改法(否定規則讓它實際沒被忽略、或治理帳已被追蹤時照舊;兩種措辭的放行指紋相同) [test:t_tq_guard_redbase_ledger_ignored]
- [S5] 當規格閘寫出紅燈版而治理帳被 git 忽略時,規格閘應當場多印一行提醒,講明留痕進不了提交、推送時會列成沒有留痕(沒被忽略不印) [test:t_spec_gate_redbase_ledger_ignored]
- [S6] 當這批修完時,回 mOrangePos 考場重跑結帳服務費完整流程的結果應符合 S1、S2、S4 [manual:考場本機分支照實跑卷證重跑四步(實作前跑規格閘判紅、有錯的實作加改預期值後跑比對與推送前驗收、修好後再跑一次規格閘與推送前驗收、平板那條在平板上跑),撤回兩筆假逃逸,結果寫進驗證紀錄]

## 回退

四項各自獨立:切參數那項把 `_tg_call_parts` 改回不帶遮罩;留痕那項把 tests 欄改回只寫名字、拿掉推送前補平台那段;提醒那項拿掉比對工具與規格閘兩處的忽略查詢、規格閘多印的那一行,兩句提醒的措辭與身分字改回原樣;假逃逸的撤回紀錄留著(撤回本身也是追加的紀錄)。

## 實務隱患
- 已排除:金流:只改比對工具與規格閘的判讀,不碰收費或扣款流程
- 已排除:對外送出:不寄信不推播,只多叫本機 git 一次
- 已排除:不可逆:改判讀、提醒文字、留痕 tests 欄在非預設平台多一個前綴、兩句提醒的身分字;舊留痕照讀;兩句提醒的身分字換掉不影響既有放行(立案時紅燈版那批停在 PR #153,見做法 3);改壞了回退就回來
- 守衛面:動到比對工具(推送前的新增告警閘)與規格閘推送前驗收的判讀,走設計審與代碼審
- 效能:忽略查詢(兩到三次 git 呼叫)只在有孤兒、有還沒提交的紅燈版、或規格閘寫出紅燈版時才叫;切參數多算一份遮罩深度,仍是一趟線性掃描
- 相容:留痕 tests 欄多前綴,讀這欄的只有推送前驗收(`_spec_gate_push_one` 解析 `[test:…]`,本來就認前綴)與判空;判綠紀錄讀的是它自己那筆事件的 items 與 tests,不讀留痕的 tests

## 審計修正紀錄
