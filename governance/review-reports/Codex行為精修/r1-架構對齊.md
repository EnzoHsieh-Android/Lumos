## Q2:命名與錯誤處理

**(a) 標記檔位置家族——對到 `~/.cache/lumos/...`(dispatch-lens),不是 `tempfile.gettempdir()`(impact-hook)**

對照:本專案現有兩種標記檔家族——`impact-hook.py` 的 TTL 冷卻標記用系統暫存目錄 `Path(tempfile.gettempdir()) / f"lumos-impact-{session_id}"`(`scripts/hooks/claude/impact-hook.py:171-174`),沒有 owner/權限檢查,靠內容裡的 pid+隨機 token 防止跨寫入互相覆蓋(`scripts/hooks/claude/impact-hook.py:194-220`);`dispatch-lens` 的 armed 目錄則用家目錄快取 `~/.cache/lumos/dispatch-lens/armed/`(`scripts/lumos:17265`)。spec 選的路徑 `~/.cache/lumos/stop-block/<session_id>` 對到後者的家族(家目錄快取,不是系統暫存目錄),這個選擇是對的——同一命名空間下新增一個 `stop-block/` 子目錄,跟現有慣例一致。

severity: clean
引句:「若 session 標記檔 `~/.cache/lumos/stop-block/<session_id>` 已存在 → 不再 block(第二道:同一 session 最多擋一次,跨輪也算)。」

**(b) 只抄了 0700,沒抄 owner-uid 檢查**

對照:`~/.cache/lumos/...` 這個家族目前的完整安全模型不只是「目錄 0700」,`_lens_arm_dir_ok`(`scripts/lumos:17283-17296`)與 `_lens_cache_read`(`scripts/lumos:16991`)都額外檢查 `st.st_uid != os.getuid()` 與 group/other 可寫位元(`_stat.S_IWGRP | _stat.S_IWOTH`),因為 `~/.cache/lumos` 路徑可預測、注解裡明講這是防「路徑可預測可偽造」的威脅模型。spec 的「實務隱患」段只提到「標記檔以 session_id 命名放 0700 目錄」,沒有提 owner-uid 檢查——只抄了同一家族既有安全模型的一半。

severity: minor
引句:「標記檔以 session_id 命名放 0700 目錄,lazy 清超過一天的。」

**(c) 環境變數命名 `LUMOS_STOP_BLOCK_OFF` 對上既有 `LUMOS_*_OFF` 家族**

對照:`lumos-entry-hook.py` 已有同款 ablation 開關 `LUMOS_ENTRY_HOOK_OFF`(`scripts/hooks/claude/lumos-entry-hook.py:89`),同樣是「探針/ablation 用,平時沒人設、行為不變」的定位。spec 的 `LUMOS_STOP_BLOCK_OFF` 命名結構(`LUMOS_<FEATURE>_OFF`)與用途都對得上這個家族。

severity: clean
引句:「加環境變數 `LUMOS_STOP_BLOCK_OFF=1` 才能跑」

**(d) reason 首行 `LUMOS-STOP:` 命名家族**

對照:本專案已有 `LUMOS-<NOUN>` 這個標記字首家族——`LUMOS-IMPACT:`(`dispatch-lens-hook.py:20` 的 `MARKER_RE`,派工詞裡標一個 diff range)、`LUMOS-LENS`(`scripts/lumos:17393`,armed context 首行,標一段鏡頭文字)。`LUMOS-STOP:` 結構上跟這個家族一致(同樣是「這段文字是 lumos 自動附加、可用固定字首辨識」的用途)。

## Q3:第二種做法

**「Stop 續做」是不是本專案第二種「擋人」機制?2026-07-06 撤的 Stop nag 跟本案差在哪,spec 有沒有寫清楚?**

對照:`docs/lumos-toolchain-knowledge/Projects/code-loop必用守衛_計劃.md` 有一個明確的 ADR(decision `d1`,`:29-32`),裁定「撤除 Stop hook 每回合 code-loop nag,強制改由 pre-push git hook 單點把關」,理由寫在 `why_chosen`:「push 才是真正需要把關的時點」(`:31`)。這個 ADR 背後的架構原則不只是「頻率太吵」,§1 明白寫著(`:44`,同一句話也在 frontmatter KEY `:18` 重複一次):**Stop hook 只注入不擋——「Stop 分不出『做完』vs『中途』,擋會開發中每回合卡死」**,所以三守衛點裡只有 pre-push(git 原生、明確的「做完那一點」)允許硬擋,Stop 永遠只能注入 additionalContext。這是本專案目前唯一的「擋人」層——commit/push 邊界的 git hook。

這份 spec 的改動 (A) 在 Stop 事件上使用官方 `decision:block` 讓 Codex 續做——這是在 conversational turn 邊界新開一種硬擋,跟 pre-commit/pre-push 是兩種不同層級的「擋」(一個擋的是 git 操作,一個擋的是「這輪能不能結束」)。spec 自己的 PRIOR-ART 段有意識到要跟 2026-07-06 那次撤除做區隔,寫的理由是「Codex 版只在『真的改了碼且沒寫回』且每 session 一次」——但這只回應了舊 nag「每回合擾民」的**頻率**問題,完全沒有回應 ADR 真正給的架構理由:Stop 事件本質上分不出「這一輪真的做完了」還是「中途要停」。`stop_hook_active` 只解決「不要無限迴圈續擋」,不等於解決「這次 Stop 是不是真的『做完』」——spec 沒有論證為什麼這個結構性顧慮在 Codex 這邊不成立,只用「擋一次+可以一句話帶過」去弱化影響,但沒有正面回答「這是不是又把 Stop 當成硬擋點在用」這個 ADR 明確否決過的做法。

附帶一提:這份 spec 的 frontmatter `related` 列了四篇筆記(`Projects/Codex完全支援_計劃`、`Projects/主session鏡頭利用率_計劃`、`Projects/指令索引與情境測試_計劃`、`Systems/lumos-cli-lifecycle`),沒有連到 `Projects/code-loop必用守衛_計劃`——這篇恰好是本案在架構上最直接的對照決策節點,卻沒有被引用或交叉參照,下一個 session 讀這份 spec 看不出它在跟哪個既有 ADR 對話。

severity: major
引句:「本專案 2026-07-06 裁撤 Stop nag(每回合擾民)——★這裡不是重開那個★:Codex 版只在」
