# 選擇點存活回指條款_計劃

## 白話

選擇點變異(`lumos choice-kill`)把改動的每一行換成一個壞法,跑這次碰到的進行中計劃條款綁的測試。殺掉就記哪條條款守住它;存活就擋推送、交人處置。現在存活那筆帳上**沒有任何條款資訊**,人只看到「這行存活」,不知道該往哪條條款底下補;而且每個壞法都跑全部守的測試,沒有測試經過的行也照跑,慢;壞法編不過時記成「跑不出結果」,讓人去查一個不存在的問題。

這份是 [[Projects/選擇點對應需求路線_計劃]] 的第 1 步。這個功能要抓的是「AI 寫程式時自己做了決定、人也沒想到」的細邊界:需求通常只講目的與粗略的系統邊界,條款是一大塊行為,語法裡更細的規則(算不算在內、空的時候回什麼)可能改變條款的結論。存活的修法分四層,每層不同:

1. **規格沒寫**:計劃的條款與正文都排除不了改壞後的行為,兩種都說得通,是 AI 自己選的。要問人;輸出直接寫成業務問題:「當…時,要 A 還是 B,現在程式是哪個」。
2. **正文寫了、條款沒收**:計劃正文有一句排除了改壞後的行為,但沒有任何驗收條款或預期值表列收它。照正文補子條款與一支邊界測試,不用問人。
3. **條款寫了、測試沒驗到**:某條驗收條款的字面就排除了改壞後的行為,只是綁的測試沒驗到。在那條條款底下補測試。
4. **等價**:改壞前後行為在規格範圍內相同。判讀只標建議,人確認後放行。(編譯不過的不是壞法,不進這四層。)

做法:choice-kill 把一個「準備物件」交給 `cmd_guard_kill`(形狀照合併快篩交 `_KillMerge` 的做法),guard-kill 建好隔離工作樹、跑配方之前呼叫它,在同一棵樹裡做三件事;之後才進語意判讀:

- **合批編譯檢查**:把這次所有壞法同時套上、編譯一次,編譯器一次列出全部錯誤,依錯誤的檔與行對回是哪一個壞法;編不過的當場換同一行的下一個候選,再合批編一次,直到全部能編或該行候選用完。編不過的不是壞法,不會變成「跑不出結果」;候選用完的行比照乾節點不擋。這是 mutant schemata「全部壞法一次編譯」的輕量做法。
- **逐測試覆蓋(PIT 的做法)**:在原版程式上把每支守的測試各單獨跑一次、同時掛 JaCoCo(這一輪也就是合併快篩本來就要「先量齊」的單支基準);再一次 Gradle 呼叫、在 Gradle 程序裡用 JaCoCo 的分析 API 逐份分析,只輸出壞法那幾行被哪些測試經過。有了它:①每條條款經過哪幾行 = 那條條款綁的測試的經過聯集;②每個壞法只跑經過那一行的測試;③沒有任何守的測試經過的行,壞法不用跑就知道殺不掉(壞法已經編譯檢查過,不會把無效壞法誤記成存活)。
- **覆蓋可信檢查**:每支測試的覆蓋資料裡至少要有一個專案自己的類別被執行過;設定沒生效時這個數是 0(實測),那支測試的覆蓋就不算數,不會把壞掉的覆蓋當成「沒有條款經過」。
- **語意判讀**:拿條款原文與計劃正文對照「改壞前後兩種行為」,判條款字面能不能排除改壞後的行為、不能的話正文能不能。照盲判的做法:工具產生判讀材料,編排者派一個全新的代理只看材料判,拿不準一律歸第 1 層。每筆判讀記下它依據的東西;依據變了,判讀標「計劃改過、待複核」但照樣顯示,一批處置完再一次重判,不會處置一條就讓其餘全部消失。

覆蓋只答得了「有沒有條款經過這行」:第 1 層和第 3 層都是「有經過」,分不開;第 2 層要讀計劃正文才看得到。所以覆蓋是篩子、線索與加速,不是分類本身。

例(實驗專案批 3,2026-11-24 存活重判):選擇點存活 62 條。舊做法只按「有沒有條款經過這行」分三類,得「AI 自己做的決定」4 條;改成「條款字面能不能排除改壞後的行為」由全新代理逐條重判(不看舊結論),得第 1 層 7 條(多出的 3 條使用者已裁)、規格已決定 38 條(其中 22 條只寫在計劃正文、沒有任何驗收條款收,是第 2 層)、等價 17 條(其中 4 條其實是編譯不過)。較早的最小實驗(2026-11-23,長跑當時 20 個存活行)另看到:有一行只有沒綁條款的測試跑到,用全部測試的覆蓋會誤判成「跑到」,所以條款經過與否一定要用條款綁的那幾支測試算。

速度(2026-11-26 實驗專案實測,見〈依據來源〉):同一支 Robolectric 測試不掛覆蓋約 4.7 秒、掛覆蓋約 6.2 秒;12 支測試的覆蓋資料一次程序內分析 0.66 秒(166 個類別),整次 Gradle 呼叫 5.4 秒。上次那批 169 支測試的單支基準約 773 秒,掛覆蓋估多約 4 分鐘、分析約 15 秒;合批編譯檢查每批一次編譯。換來的是:沒有測試經過的壞法不跑、其餘只跑經過的測試、編不過的壞法不進測試階段。

使用者原話(2026-11-24):「回指驗收測試,是顆粒比較粗的規格,通常語法樹計較的是更細的邊界,有可能改變原本規格的結論,這就是想用來抓出AI擅自決定,或是原本規格不清的」;2026-11-26:「我不想對整個功能願景做偏離的妥協」「不要懼怕改動,改動大沒有關係,我要的是完美符合願景,能實際幫上code review的功能」「但是速度這件事,也是要保證好,不要又變回十幾個小時」;目的那段原話見路線總圖〈白話〉。

這一步做:準備物件(合批編譯檢查、逐測試覆蓋、可信檢查)、依覆蓋選測試、存活的條款經過分類、判讀材料與判讀記錄、輸出與推送閘提示依層換句。**不改擋的判定規則與回報上限**(「沒有可用壞法」比照乾節點不擋;依覆蓋判存活的行照舊擋),**不機械判等價**(判讀說等價只標建議,照舊要人放行),**不實跑分得出兩版的輸入**(第 3 步)。

## 舊否決比對

- [[Projects/代碼審通過前自動跑選擇點_計劃]] 否決「code-loop pass 內自動跑 choice-kill」(最壞 20 分鐘以上):覆蓋只在人手動跑 `choice-kill` 時跑,不加進 pass 或推送前那一道。
- 母計劃 [[Projects/改動選擇點都要有需求守住_計劃]]〈不做〉「不接覆蓋率」:那句沒有否決理由,是延後到它的 REVISIT(2027-01-15「要不要接 Kotlin 覆蓋率(JaCoCo)挑最小測試集」),天花板 3 寫明沒有覆蓋率所以比論文慢、沒被跑到的行一定存活。這份就是那條回頭條件的落地,論文本來就只對有覆蓋的行產生壞法。
- 母計劃「一行一個壞法」(論文 4.1):照舊。編不過的不是壞法;換候選是換到那一行第一個有效的壞法,不是一行跑多個;路線總圖 REVISIT「同一行換下一個候選壞法」講的是「一行只驗一點」(同一行有兩個選擇點),跟這裡不同,照留。
- 母計劃〈不做〉「不讓 AI 自動判等價」:照舊。判讀代理判第 4 層只記「建議等價」,不自動放行、不改擋不擋。
- 情境題盲判那份〈不做〉「不在推送前閘或 CI 呼叫模型」:照舊,判讀由編排者派代理跑,lumos 只產材料、驗格式、記帳。
- [[Systems/guard-kill]] 否決「另抽一支共用的殺傷力函式」:不抽;`cmd_guard_kill` 只多收一個選用的準備物件(形狀同 `_KillMerge`),沒交時行為不變,殺傷力判定照舊。

## 用詞

- **守的測試**:choice-kill 已收集的守衛測試清單(只收進行中計劃、profile 是 kotlin-junit 的平台、已扣掉 `[manual:]` 與 `[keeps]` 的條款),每支帶 `keys`:它屬於哪幾條條款,值是 `(計劃路徑, 條款號)`。
- **準備物件**:choice-kill 交給 `cmd_guard_kill` 的選用物件 `_KillPrep`(每個平台組一份,跟 `_KillMerge` 同樣交法);guard-kill 建好隔離工作樹後、跑任何配方之前,對每個平台組呼叫它一次,它用 guard-kill 那棵樹與 guard-kill 的 `_kill_run`、基準快取、修改時間追蹤(`mstate`)做事,做完回傳要換掉的配方與每個配方要跑的測試子集。
- **合批編譯檢查**:準備物件把這一批所有壞法同時套到樹上、跑一次編譯任務(平台設定的 `compile_cmd`,Android 預設 `./gradlew :<模組>:compileDebugUnitTestKotlin`),讀編譯錯誤的檔與行,對回壞法(壞法改的行範圍含那一行);對得回的記無效並換同一行下一個候選;對不回的錯誤(在沒有壞法的檔或行)整批改成逐個編譯找出元凶;最後還原。
- **無效壞法**:合批編譯檢查判出編不過的壞法,身分 `(檔, 行指紋, new_sha)`;記一筆 `invalid` 事件(帶這次 run 的 `at_sha`)。
- **沒有可用壞法**:同一行全部候選都無效;那一行在挑壞法時狀態是 `exhausted`(跟乾節點 `arid` 同一層級的行狀態,不是處置判定),不擋、不跑。
- **覆蓋基準**:準備物件在 guard-kill 那棵樹、原版程式上把每支守的測試各單獨跑一次、同時掛 JaCoCo,跑完把那支的覆蓋資料檔複製到工作夾;結果(rc、尾段、秒數、逾時、不確定)直接寫進 guard-kill 的基準快取,鍵用 guard-kill 自己組的那條測試指令(init script 由準備物件在執行時加上,跟合併快篩加 init script 的方式相同,快取鍵不含它)。
- **覆蓋可信**:某支測試的覆蓋資料裡,至少一個專案自己的類別(平台根底下原始碼的套件)有執行紀錄。不可信的那支測試對所有行都算「不明」。
- **經過**:用 JaCoCo 分析 API 讀某支測試的覆蓋資料,壞法改的行範圍裡至少一行的指令覆蓋計數大於 0。某條條款經過 = 那條條款綁的守的測試裡至少一支經過。
- **覆蓋分類**:每個壞法行一個:`clause`(列出經過的條款)、`none`(每支守的測試都可信而且都沒經過)、`unknown`(有任一支不明,或這一行在下面例外裡,附原因)。
- **覆蓋例外**:壞法行在 `inline fun` 本體裡、在 `const val`、在頂層或 companion 的屬性初始值裡,或分析時那幾行沒有任何指令紀錄,一律記 `unknown`、跑全部守的測試(這幾種行的執行會被算在別的行或別的類別)。
- **依覆蓋選測試**:`clause` 的行只跑經過的守的測試;`none` 的行不跑、直接記存活;`unknown` 的行跑全部守的測試。
- **層**:存活的最終分類,1 規格沒寫、2 正文寫了條款沒收、3 條款寫了測試沒驗到、4 建議等價(定義見〈白話〉)。都是判讀代理給的。
- **計劃正文**:碰到的進行中計劃裡,frontmatter、〈驗收條款〉、〈預期值表〉、〈審計修正紀錄〉以外的段落;段名是從二級標題到最近標題的路徑(`〈範圍〉/〈1. 覆蓋〉`),同名再加 `#2`;第一個標題前的文字段名 `〈前言〉`。
- **判讀材料**:每個存活一段,含選擇點位置、包住那一行的宣告(取法同 `_kt_sit_material`,取不到時改附前後各 20 行)、壞法的改動(原文 → 改壞後)、覆蓋分類與經過的條款原文;每份材料對它涉及的每份計劃附一次全部條款、預期值表與分段正文;作答格式;不含任何已記的層、處置提示或放行理由。
- **判讀依據**:一筆判讀寫下的 `basis`,每項 `{plan, where, quote}`:`where` 是條款號(`S3`)或段名,`quote` 是從那條條款或那一段逐字引的句子。
- **判讀狀態**:`有效`(依據都沒變)、`待複核`(壞法身分沒變、依據有變)、`作廢`(壞法身分變了或被撤回)。

## 範圍

1. **設定**:平台設定多兩個選填鍵,穿過 `load_platforms` 帶進平台資料(舊單平台的 `test` 那節同樣讀;型別不對照既有欄位丟 `ValueError`):
   - `coverage`:布林;`true` 才做逐測試覆蓋。
   - `compile_cmd`:合批編譯檢查用的指令字串;沒寫時 Android 平台用預設、其他平台不做合批編譯檢查(照現在,編不過在測試時才發現,記 `no_result`)。
2. **準備物件**(`_KillPrep`,choice-kill 建、交給 `cmd_guard_kill` 新的選用參數 `prep`;guard-kill 在 `_kill_merge_iter` 先量齊基準的同一個位置呼叫它):
   - 合批編譯檢查先做(壞法換定之後才量覆蓋基準);每批一次編譯,換了候選的行再一批,最多到該行候選用完;每次編譯的逾時照 guard-kill 量基準的上限 `max(600, floor)`。
   - 開了 `coverage` 時跑覆蓋基準:測試順序照現在的排序;每支開跑前看 `--max-seconds` 剩下多少,不夠就停,沒跑到的測試算不明;Gradle 呼叫帶合併快篩那種「訊號到就當場收」的標記。
   - 掛覆蓋的基準紅了:同一支不掛覆蓋再跑一次;綠的話基準用不掛覆蓋那次、那支測試覆蓋算不明;也紅就照現在的「基準不綠」處理。
   - 覆蓋基準跑完,一次 Gradle 呼叫(init script 登記的分析任務)在 Gradle 程序裡用 JaCoCo 分析 API 逐份讀覆蓋資料,只分析壞法所在檔對應的類別(init script 從每個模組收類別資料夾,先挑出壞法所在檔的套件資料夾裡的類別,分析後只留 JaCoCo 記的原始檔名等於那支檔的,所以一支 Kotlin 檔編出的 `FooKt`、`Foo$Companion`、lambda 類別都算得到),輸出 `{測試: {專案類別有紀錄數, 經過的壞法行}}` 的 JSON 到工作夾;剩下的時間不到 30 秒就不分析,全部算不明。
   - 斷路器:前 5 支(守的測試少於 5 支時就是全部)覆蓋都不可信,這次 run 關掉覆蓋、印一行原因,其餘照現在。
   - 工作夾:沿用 guard-kill 那棵樹的暫存位置(`wt.scratch`);覆蓋資料檔名用測試序號(`t0001.exec`),不用測試名。
   - 續跑快取:每支測試的覆蓋結果(專案類別有紀錄數、經過的壞法行)寫進 `_note_audit_work_dir` 同一套工作目錄規則下的 `choice-cov/<at_sha>/`(符號連結拒用、自帶 `.gitignore`、14 天清檔),鍵是平台、測試名、測試所在檔 blob;同一個 `at_sha` 再跑時直接取用,被中斷的 run 下次接著跑。
   - 回傳:換掉的配方(新壞法,配方編號由 choice-kill 這邊的配方含 `new` 一起算,不跟舊的撞)與每個配方的測試子集;guard-kill 照子集跑。
3. **依覆蓋選測試與合併快篩**:`clause` 的行合併快篩用經過的測試組一條合併指令(照 `_choice_merge_cmd`);合併基準仍是整組那一條,子集沒有自己的合併基準——子集合併呼叫有失敗就照現在轉逐支確認,所以合併基準不涵蓋子集只會多逐支跑、不會誤判殺掉。`none` 的行 choice-kill 直接記壞法事件 `verdict: "survived"`、`via: "cov"`、`attempt` 照現在的計數、`judged: "cov"`、`tests_sha`、`cov_sha`。
4. **記帳**(全部閘名 choice-kill、自帶 `token`;治理帳 (gate, kind) 白名單、`LOOP_NOT_CLOSE_EVENTS` 分類、gov 讀取欄位白名單與 `_GOV_FIELD_TYPES` 補上新 kind 與欄位,型別寫在括號裡):
   - `reach`(每個壞法行一筆):`file`、`fp`、`new_sha`(str)、`reach`(str)、`reach_clauses`(list[str],最多 20 條,依計劃路徑與條款號排序)、`reach_more`(int,超過 20 的條數)、`reach_why`(str,只用下表)、`cov_sha`(str:經過或可能經過這一行的守的測試名與所在檔 blob、壞法所在檔 blob,依名排序後算)、`run_id`。
   - `reach_why` 字串表:「沒開覆蓋」「覆蓋接不起來」「覆蓋資料沒產出」「分析失敗」「時間不夠」「基準不綠」「掛覆蓋才紅」「覆蓋例外」「這一行沒有指令紀錄」。
   - `invalid`:`file`、`fp`、`new_sha`、`row`(str)、`at_sha`(str)、`run_id`。
   - `cov-audit`(抽查,見範圍 5):`file`、`fp`、`new_sha`、`killed`(bool)、`killing_test`(str)、`run_id`。
   - run 那筆多 `cov`(str:`on`|`off`|`tripped`)、`cov_secs`(int)、`cov_skipped`(int:依覆蓋不跑的壞法數)、`cov_selected`、`cov_full`(int:實際跑與假設全跑的測試支數總和)、`compile_batches`(int)、`invalid_n`(int)。
   - 單筆事件超過 4096 位元組時照 `_gate_event_fit` 截 `reach_clauses`(`reach_more` 補數)。
5. **抽查**:每次 run 從 `none` 的行隨機抽 2 行(`--cov-audit N` 可改、0 關掉)照跑全部守的測試;殺掉了就記 `cov-audit` 事件 `killed: true`、那一行改用殺掉的結果記壞法事件、印一行「覆蓋判錯」、這次 run 的 `none` 一律改成照跑(等於斷路);沒殺掉記 `killed: false`。
6. **讀者**:
   - `_choice_ledger_index` 照舊只收 kind choice-kill;新增 `_choice_ledger_aux(evs)` 回 `{(file,fp): {"reach":…,"layer":…,"invalid":[…]}}`。用到它的地方:`_choice_points_lines` 一帶(印分類與層)、`_choice_kill_pick`(帶過去規則)、挑壞法的 `skip`(choice-points、推送前掃描、`situation-rule --point`、判讀材料)、`_choice_push_read`(多回傳 aux)、`_choice_push_judge`(依層拆子原因)。
   - 挑壞法:`_choice_pick` 多一個 `skip`(這一行最近一次 run 的 invalid `new_sha` 集合);全部候選都在 `skip` 裡時 `_choice_file_points` 記行狀態 `exhausted`(跟 `arid` 一樣不產壞法);`_CHOICE_STATUS_TEXT` 加 `"exhausted": "沒有可用壞法"`。不唯一的候選照現在回傳、標 `not_unique`。
   - 帶過去規則(`_choice_kill_pick`):`via: "cov"` 的存活,只有這次也開覆蓋而且 `cov_sha` 相同才帶過去,否則重跑;其餘照現在。
   - reach 有效:最新一筆 reach 的 `cov_sha` 等於現在算出的值,而且 `reach` 不是 `unknown`。
   - gov「第一次判定」照現在數 `attempt == 1 and via == "run"`;`via: "cov"` 另列「依覆蓋判存活」一行;`invalid` 不是壞法事件,不影響 `attempt`。
7. **補跑**:`lumos choice-kill --reach-only --diff <範圍>`:照常交準備物件、不產配方之外的事:只做覆蓋基準與分析,對帳上目前是存活、而且沒有有效 reach 的行補 reach;跟 `--no-cov`、`--only`、`--max-mutants`、`--no-merge` 同給時 rc2;乾淨工作目錄檢查同一般 choice-kill;寫一筆 `kind: "reach-run"`(不是 run)帶 `cov_secs`。
8. **判讀材料**:`lumos choice-layer --template [--diff <範圍>] [--part <n>] [--redo <檔>:<行>]`:
   - 對範圍裡帳上目前是存活、判讀狀態不是 `有效` 的行(`--redo` 指定的行一律出;`待複核` 的照出)出材料;一個都沒有時印「沒有要判讀的存活」、rc0。
   - 第一次呼叫(沒帶 `--part`)把份清單寫到 `_note_audit_work_dir` 同一套規則下的 `choice-layer/<清單編號>.json`(每份的存活鍵、材料雜湊),stdout 印第 1 份,stderr 印份數與取法;之後的 `--part n --list <編號>` 從清單取,不重算。
   - 分份:依「主計劃」分組——有經過條款的行取第一條經過條款所屬的計劃,沒有的放「未歸計劃」組(材料附碰到的全部計劃);每份最多 20 個存活;位元組數(UTF-8)超過 200 KB 就把存活數減半再切,減到 1 個仍超過時,那份的計劃正文改成只附段名清單、全文另存工作夾 `choice-layer/<清單編號>-<序號>.md` 由材料指路,stderr 註明。
9. **判讀記錄**:`lumos choice-layer <結果.json> --list <清單編號>`:
   - 結果每筆 `{file, fp, layer, before, after, basis, question, reason}`,先整份驗證,不合就整份拒收(rc2)並逐筆印出哪一筆、哪一項不合,什麼都不寫:
     - `file`+`fp` 要在那份清單裡;同一份同一鍵只出現一次;沒有不認得的欄位;`layer` 是 1–4。
     - 長度:`before`、`after`、`question`、`reason` 各 ≤ 300 字;`basis` ≤ 5 項;每項 `quote` 10–200 個實字。引句比對沿用情境題的 `_kt_sit_quote_norm`(不另寫正規化)。
     - 第 3 層:`basis` 至少一項 `where` 是那份計劃裡有綁測試的條款號(不是 `[manual:]` 或 `[keeps]`),`quote` 在那條條款原文裡找得到。
     - 第 2 層:`basis` 至少一項 `where` 是那份計劃的段名,`quote` 在那一段裡找得到,而且在任何條款原文與預期值表列裡都找不到。
     - 第 1 層:`question` 必填,含「當」「要」「還是」「現在」四個字樣。
     - 第 4 層:`reason` 至少 10 個實字。
     - `basis` 的 `plan` 要是那份材料涉及的計劃。
   - 全過才寫:每筆判讀全文存成 `governance/choice-layers/<內容雜湊>.json`(加進 `_BOOKKEEPING_DIRS`,同 `governance/reread-verdicts/` 的先例,提交它不會讓代碼審留痕失效);治理帳每筆一個 `kind: "layer"` 事件(`file`、`fp`、`layer`(int)、`new_sha`(str)、`judgment`(str,那份檔的相對路徑)、`judgment_sha`(str)、`deps_sha`(str,依據指紋,見下表合成一個雜湊)、`token`)。
   - 判讀狀態(讀側,同一鍵取帳上最後一筆 layer 事件,含撤回;「最後」照治理帳的檔內順序,跟既有讀者取 `evs[-1]` 一樣):

     | 層 | `deps_sha` 由這些算 |
     |---|---|
     | 全部 | 壞法 `new_sha` 不同就是 `作廢` |
     | 3 | 引的每條條款原文;那條條款綁的測試清單與所在檔 blob |
     | 2 | 引句所在那一段的原文;全部條款原文與預期值表(判「仍不在條款裡」) |
     | 1、4 | 碰到的每份計劃的條款全文加正文(不含 frontmatter 與審計修正紀錄) |

     `deps_sha` 跟現在算的一樣是 `有效`,不一樣是 `待複核`;同一次呼叫裡每份計劃的條款與段落雜湊、每支測試檔的 blob 各只算一次、存活之間共用;判讀檔讀不到或雜湊對不上當成沒有判讀。推送閘從 B 版的樹讀判讀檔。
   - 撤回:`lumos choice-layer --withdraw <檔>:<行> --reason "<≥10 實字>"` 寫一筆 `kind: "layer"`、`layer: 0` 的補償事件;那一行變成沒有判讀。
10. **輸出**:
    - `choice-points` 的存活列後面加一段(在 `_choice_points_lines` 裡);choice-kill 判完全部壞法後另印一份「存活與分類」清單,每個存活一行加同一段:
      - 有判讀:`第 1 層 規格沒寫:<業務問題>`/`第 2 層 正文寫了、條款沒收:<計劃>〈<段>〉「<引句>」`/`第 3 層 條款寫了、測試沒驗到:<計劃#SN>`/`第 4 層 建議等價(要人放行):<理由>`;`待複核` 的前面加 `⚠ 計劃改過、待複核:`。
      - 沒有判讀:覆蓋分類 `經過 計劃#S3、計劃#S5`/`沒有條款經過`/`覆蓋不明(<原因>)`,後面加 `未判讀`;沒有有效 reach 印 `未分類`。
    - 行狀態 `exhausted` 印 `沒有可用壞法`。
    - 引句、問題、理由印出前過 `_kill_esc`、截到 200 字。
    - `gov --stats` 選擇點段多五行:覆蓋分類各幾筆;四層各幾筆與未判讀幾筆;依覆蓋省掉的壞法執行數與測試支數(`cov_full - cov_selected`);無效壞法幾個、沒有可用壞法幾行(依型錄列號);抽查幾次、判錯幾次。只數帳上最新一筆,不判有效。
11. **推送閘提示**:`_choice_push_judge` 把「存活」原因拆成子原因 `存活·第1層`、`存活·第2層`、`存活·第3層`、`存活·第4層`、`存活·未判讀`(`_CHOICE_PUSH_REASONS`、`_CHOICE_PUSH_FIX` 跟著加),每個子原因各自計行數、列示例(上限照 `_CHOICE_PUSH_SHOW`)、一句處置:
    - 第 1 層:「問人;答案用 `lumos situation-rule --point <檔>:<行> --plan <計劃> --clause "<新條款文字>" --test <測試名>` 寫回」,示例行附業務問題。
    - 第 2 層:「照計劃正文〈段〉那句補一條條款與邊界測試,不用問人」,範例指令同上。
    - 第 3 層:「在條款 <計劃#SN> 補一支驗到這個邊界的測試,綁到那一條的 `[test:]`」(不用 situation-rule)。
    - 第 4 層:「判讀建議等價:人確認後 `lint-waive choice:<檔>:<行> --note "等價:<理由>"`」。
    - 未判讀:「跑 `lumos choice-layer --template`,派全新代理判讀後 `choice-layer <結果> --list <編號>` 記下、提交治理帳與 `governance/choice-layers/`(新增)」;經過條款的示例行附條款號。
    - `待複核` 的判讀照它的層歸子原因,處置句後面加「計劃改過,處置完這一批後重跑 `choice-layer --template` 複核」。

12. **文件**:現況寫進 [[Systems/規格閘]](choice-kill 的家)的選擇點那段,並把它的 responsibility 補上 choice-kill 的準備物件、依覆蓋選測試、判讀記錄;[[Systems/guard-kill]] 只補一句「`prep` 參數:呼叫端交進準備物件,在建樹後、跑配方前呼叫,沒交時行為不變」;`choice-layer` 登記子命令說明表與 lumos-project-notes 的 `commands/INDEX.md`;lumos-code-loop 手冊在選擇點那一步補判讀四步;[[Projects/選擇點變異覆蓋選測試_計劃]] 標成由這份做掉;本計劃收尾時路線總圖第 1 步改成指向 Verification。

## 不做

- 不機械判等價;判讀的第 4 層只當建議,不放行。
- 不實跑分得出兩版的輸入(第 3 步);第 1 層的業務問題由判讀代理讀程式寫。
- 不用覆蓋分類當最終分類;條款經過不用全部測試的覆蓋算(只用條款綁的守的測試)。
- 不在推送前閘、CI 或 choice-kill 裡呼叫模型;判讀由編排者派代理,lumos 只產材料、驗格式、記帳。
- 不讓層改變擋不擋:第 2、3 層照樣要補到殺掉才算處置完,第 1 層照樣要人答,第 4 層照樣要人放行。
- 不改回報上限、放行鍵、殺傷力判定;不在推送前或 code-loop pass 裡跑覆蓋。
- 不在同一個 JVM 裡逐支歸零取覆蓋;不做完整 mutant schemata(壞法改成執行期開關)。
- 不自動改使用者專案的 Gradle 設定檔(只靠每次呼叫的 init script);只支援 JaCoCo 與 Gradle。

## 實務隱患

- 覆蓋設定沒生效、覆蓋全 0:2026-11-26 實測,init script 太早設定時 Robolectric 測試的覆蓋資料裡專案類別有紀錄數是 0,正確設定時同一支是 345;〈用詞〉覆蓋可信就用這個數,前 5 支都不可信就斷路,不會把它當成「沒有條款經過」。

## 天花板

1. 「經過」只代表條款的測試跑過這一行,不代表它檢查了這一行的結果;存活本來就表示沒檢查到。
2. 依覆蓋選測試靠「沒經過那幾行的測試殺不掉那幾行的壞法」;覆蓋例外以外的漏網靠抽查,抽查只是樣本。
3. 只支援 JaCoCo 與 Gradle;並行跑測試時逐測試覆蓋分不出(覆蓋基準一支一支跑)。
4. 分類準不準靠 S12、S18 一個專案量過;多專案的數字等 REVISIT。
5. 層是模型判的,不是證明:引句機械驗得到「真的出自那條條款或那一段」,驗不到「真的排除了改壞後的行為」;拿不準歸第 1 層是把錯往「多問人」那邊偏。
6. 第 1 層的「現在程式是哪個」是代理讀程式答的,沒有實跑一個分得出兩版的輸入(第 3 步補)。
7. 合批編譯檢查靠編譯錯誤的檔與行對回壞法;兩個壞法互相影響(一個讓另一個編得過或編不過)時,合批結果可能跟單獨編不同——套壞法時每行一個、行與行之間互相影響的機會小,真遇到就以單獨編為準(對不回時本來就會逐個編)。
8. `待複核` 的判讀可能已經過時;它只影響提示文字,擋不擋不看層。
