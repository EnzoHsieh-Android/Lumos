### f2 — major — `restamp --by` 沒有守住 `batch-` 命名空間,人工核過的標籤可被無關的 `revert --batch` 誤殺

file: `scripts/lumos:15295`(新增的 `--by` 參數,無驗證)、交互對象 `scripts/lumos:7827`(`revert` 既有的第一段精確比對邏輯,本 diff 未動但因新參數而產生新風險面)、`scripts/lumos:7763`(把 `by` 原樣接進 stamp 第一段)

引句:「acs.add_argument("--by", default="claude", help="第一段「誰核的」(預設 claude)")」

這支 diff 自己宣稱的合約是(docstring,`scripts/lumos:7741-7742`)「第一段離開 batch- 後,`revert --batch` 不再撤它(合約候選 #4「人工修正過的不被誤撤」)」,並在 `Projects/固定席扇出降權_計劃.md:342` 白紙黑字寫「第一段離開 `batch-` 後,`revert --batch` 就不會再撤它」。但 `--by` 是完全不受限的自由字串,只要使用者(或未來接自動化的呼叫端)給的值本身長得像 `batch-<日期>`,restamp 寫出來的 stamp 第一段就還在 `batch-` 命名空間裡——`revert` 的比對是精確字串相等(`stamp.split("/", 1)[0].strip() == want`),完全不知道這個 `batch-2026-08-23` 是「剛好長這樣的人工核可標記」還是「當初批次預標」,會把它當成同一批一起撤掉。這正是這整個功能被設計出來要防的「誤傷」那一類,卻沒有任何輸入驗證擋住。

失敗場景:有人(人或未來的自動化流程)對某篇筆記核可時,`--by` 用了一個剛好符合 `batch-YYYY-MM-DD` 形狀的值(例如把批次日當標籤,或誤用既有 stamp 的第一段當範本複製) → 之後任何人對那個日期跑一次無關的 `revert --batch`,會把這篇「已經人核過、理應免疫」的節點連同 `about_code`、`about_code_stamp` 一起清空,且指令回報「撤成功」,不會有任何警告。

重現(已跑過,確認每一步輸出):
```bash
# 1. 建一篇有 about_code 的筆記,任意舊 stamp
cat > docs/be-knowledge/Systems/X.md <<'EOF'
---
type: system
status: done
about_code:
  - scripts/lumos
about_code_stamp: claude/2026-08-01/aaaaaaaaaaaa
---
# X
body
EOF

# 2. 「人核過」,但 --by 剛好長得像批次標籤
python3 scripts/lumos --vault docs/be-knowledge about-code restamp Systems/X --by "batch-2026-08-23"
# → ✓ restamp Systems/X.md:about_code_stamp = batch-2026-08-23/2026-08-24/a01e3eb34066(表示你核過標籤對現在的正文仍正確)

# 3. 之後有人(不知道上面那次核可)跑一次無關的批次撤銷
python3 scripts/lumos --vault docs/be-knowledge about-code revert --batch "2026-08-23"
# → 批次 batch-2026-08-23:1 篇 / ✓ remove about_code / ✓ remove about_code_stamp / ✓ about-code revert:撤了 1 篇
# 結果:Systems/X.md 的 about_code、about_code_stamp 全部被拿掉,「人核過不被誤撤」的合約被打破,且沒有任何錯誤或警告。
```

觸發條件較窄(需要 `--by` 剛好落在 `batch-YYYY-MM-DD` 形狀),但一旦觸發是 100% 確定性的破壞、且無任何機械守衛擋著,故列 major 而非 minor。建議修法:`cmd_about_code_restamp` 對 `by` 值加一道擋——若 `by.startswith("batch-")` 就拒絕(或至少 print warning)。
