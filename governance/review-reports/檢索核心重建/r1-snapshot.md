# 檢索核心重建（2026-09-14 立案）

> 白話：現在每查一次，程式把五百多篇檔案全部從硬碟讀一遍再比字串，要 0.7 秒，而且**查三個詞只有那三個字剛好連在一起寫過才算命中**。這一關壞了，後面排序再聰明也救不回沒進候選的東西。這次把這一關換成真正的索引。

## 為什麼是現在做這個

上游是 [[Projects/標籤系統精簡_計劃]]。那個案子兩輪設計審被挑出 50 條問題、34 條標 blocking，**過半指向同一個地方：撈候選那一關**。與其在會晃的地基上補洞，先把地基換掉——換完之後，那個案子的核心條款大半會變成索引的一行設計決定。

## 量到的基線（2026-09-14，512 篇）

> **數字口徑**：下表與下節的實驗數字量於 2026-09-14、513 篇當下，**量級可信、精確值不可重現**（前掃重跑搜尋得 0.45–0.48 秒，比下表低約三成；機器負載與檔案快取都會影響）。[S1] 要求收工前用固定提交重跑一次釘住。篇數在同一天從 509 長到 513，所以本篇出現的分母不一致是真實增長不是筆誤。

| 量的東西 | 現況 |
|---|---|
| 單次搜尋耗時 | 約 0.5–0.7 秒，且隨篇數線性成長（消費專案三千篇 ≈ 數秒） |
| 索引 | 沒有。每查一次讀全部檔案 |
| 候選判準 | 整串子字串比對；程式自己註解寫著「只要那幾個字沒連在一起出現過就是 0 候選」 |
| 排序語料 | 文件數／詞頻／平均長度取自**候選集**，不是全庫 → 候選集一變，留下節點的分數跟著變 |
| 別名欄填寫率 | 511 篇裡真正有值的 59 篇（11.5%），而它是排序權重第二高的欄位 |
| 動手前注入怎麼用標籤 | 會讀風險類標籤，但**只路由進「參考道」**（上限 3 筆、不進必看、不進排序權重）。缺口是「只打折用」不是「沒接線」 |

## 最小實驗（已跑，2026-09-14）

用標準函式庫的 sqlite3 FTS5 建索引、token 流交給 repo 自己那支斷詞器產生：

| | 現況 | 實驗 |
|---|---|---|
| 建索引 | — | 512 篇 0.75 秒（一次性） |
| 查「殺傷力」 | 0.65 秒 | 0.1 毫秒 |
| 查「標籤 排序 權重」 | 0 候選 | 5 筆，第一名正確 |
| 查「BM25 檢索 排序」 | 0 候選 | 5 筆，第一名正確 |
| 新依賴 | — | 零 |

**這只證明「可行且快」，不證明排序品質不退步**——那要靠金標對照（[S12]）。★而且「第一名正確」是我主觀判斷，那兩題不在金標題庫裡、沒有機械對照組★；真正算數的只有金標三指標。

## 條款

- **[S1] 先量基線再動手。** 速度、精準、召回三面各留一組可重跑的數字，之後每一條改動都要對得上這組基線。沒有基線就沒辦法證明變好，只能宣稱。 [test:t_retrieval_baseline_recorded] [manual:把速度與金標三指標的基線數字寫回本節點]

- **[S2] 索引用標準函式庫的 FTS5，token 流由既有斷詞器產生。** 不引入新依賴、不引入第二套切詞語意。索引欄位對齊既有排序欄位（標題／別名／摘要／標籤／正文）。 [test:t_index_uses_existing_tokenizer] [test:t_index_no_new_dependency]

- **[S3] 索引的標籤欄吃「合成後」的標籤，而且要明訂哪些家族進得去。** 從純量欄位合成型別與狀態，不索引檔案裡的字面鏡像標籤。**這一條讓 [[Projects/標籤系統精簡_計劃]] 的核心承諾變成索引的一行設計決定**——殘留的舊標籤自動不被看見。★前掃指出的銜接漏洞★：現況把整串標籤接起來丟進排序欄位，**研究方向標籤（`scope/` 家族）因此已經在影響排序**，而那跟 [[Projects/工具分類_計劃]] 白紙黑字寫的邊界相反。索引要**逐家族明訂進不進**，不能沿用「全部接起來」的預設——否則 [S11] 說的「由人看數字裁」其實已經被這裡的預設提前決定了。 [test:t_index_tags_are_synthesized] [test:t_index_tag_families_are_explicit]

- **[S4] 候選階段改吃索引，召回破口一併修。** 多詞查詢不再要求那幾個字連在一起出現。既有的「多詞回退」補丁（只在整串全庫零命中時才退成逐詞）隨之退場——它是為了繞過這個破口而存在的。 [test:t_candidate_from_index_multiword] [test:t_multiword_fallback_retired]

- **[S5] 排序仍走既有 BM25F，只換候選來源與語料口徑。** 不動已校準的欄位權重與型別先驗。**語料口徑要明訂**：現況的文件數／詞頻／平均長度取自候選集，改成取自全庫統計（索引本來就有），這樣候選集變動不再擾動留下節點的分數。 [test:t_rank_corpus_is_whole_vault] [test:t_rank_weights_unchanged]

- **[S6] 三條字面路徑共用同一份索引。** 搜尋的候選階段、動手前的入口召回、關聯推薦，三者現在各自掃檔或共用剝碼原語；改成都問同一份索引。 [test:t_entry_hook_uses_index] [test:t_reco_uses_index]

- **[S7] 索引的失效、重建與壞掉時的行為。** 判失效看檔案修改時間與篇數；索引不存在或壞掉要**出聲並退回現況的掃檔路徑**，不得靜默降級（靜默降級＝使用者以為在用索引、其實在跑慢路徑）。首次建立成本要印出來。併發重建要有互斥。 [test:t_index_invalidates_on_mtime] [test:t_index_corrupt_falls_back_loudly] [test:t_index_rebuild_is_mutually_exclusive]

- **[S8] 決定風險類標籤在注入裡要不要升級（不是從零接線）。** [test:t_risk_lane_promotion_is_switchable] [manual:跑注入面金標前後對照，數字寫回本節點] ★前掃更正了本條原本的前提★：注入現在**已經**會讀風險類標籤，只是被 2026-08-24 的降噪設計路由進「參考道」（上限 3 筆、不進必看、不進排序權重）。當初降級的理由是「樞紐筆記搭便車、是噪音主力」。**本條要問的是：索引落地、候選集品質改善之後，當初那個理由還成不成立？** 做法是加一個可切換的旋鈕、跑注入面金標前後對照；**數字不支持升級就維持現況**，不得因為「標籤該被用到」這種直覺硬接。

- **[S9] 優先級標籤接待辦排序。** [[Projects/標籤系統精簡_計劃]] 原本要退場這個家族，2026-09-14 Enzo 改裁「給它一份工作」。15 篇問題節點掛了 priority 值（P1／P2／P3，不是統計學的 p-value），目前除了值域檢查與進場印出來之外沒有任何機制吃它。接進待辦排序後它才有存在理由。 [test:t_backlog_order_reads_priority_tag]

- **[S10] 別名回填。** 排序權重 3.5（只輸標題），但只有 11.5% 的節點填了；金標題庫裡 41% 的題型（縮寫、同義詞、單字）正是它在解的。回填要有品質判準——**湊數的別名比空的更糟，這句話目前只在提示訊息裡、沒有機械判準**，本案要給它一個。 [test:t_alias_quality_check] [manual:回填後重量覆蓋率與金標三指標，數字寫回本節點]

- **[S11] 研究方向標籤（`scope/` 家族，本圖譜用它分九個研究方向，見 [[Projects/工具分類_計劃]]）進排序的消融。** 從 [[Projects/標籤系統精簡_計劃]] 移交。★要先承認現況不是中性的★：它**已經**在影響排序（上游調研實測：搜 evals 前十筆有七筆的唯一命中行就是那一行標籤），而計劃文件寫的是「不進排序」。索引重建了排序的語料基礎，在舊基礎上量的數字沒有意義，要在新基礎上量。結論（改文件承認它有進、還是把它排除）由 Enzo 看數字裁。 [manual:加可切換旋鈕，跑有它與沒它的金標對照，數字寫回本節點]

- **[S12] 收工前的前後對照。** 速度、金標三指標、召回率三面各跑一次前後對照。**任一面退步就不得收案**，退步的原因要查出來寫進節點，不是調參數調到好看。 [manual:三面前後對照全部跑完並把數字寫回本節點]

## 邊界與不做

- **不換掉既有的 BM25F。** 那組欄位權重與型別先驗是金標校準過的資產，換掉等於丟掉已驗證的東西。FTS5 只當候選產生器。
- **不改斷詞語意。** 餵索引的 token 流用 repo 自己那支斷詞器產生，不用 FTS5 內建分詞器（實測它的三字元分詞器對兩個字的中文查詢回 0 筆，而兩字查詢正是金標題庫的大宗）。
- **不動結構化查詢的欄位型篩選語意。** 那條路走解析後的欄位，跟索引無關。
- **不在本案做鏡像標籤的存量清理。** 那是 [[Projects/標籤系統精簡_計劃]] 的事，本案只負責讓索引不看字面鏡像。

## 實務隱患

- **★可攜性（前掃指出，未解）★** — lumos 是要被複製到各消費專案的零依賴單檔，而 FTS5 有沒有編進 sqlite3 取決於各機器的 python 建置。本機實測有，**不代表每台都有**。設計要：啟動時偵測、沒有就退回現況的掃檔路徑並**出聲告知**（同 [S7] 的不得靜默降級原則），而且退回時所有測試仍要能跑。
- **效能** — 索引本身就是為了效能，但要防「建索引比查詢還久」：首次建立 0.75 秒可接受，增量更新要只重建變動的篇。索引檔放哪要避開共用暫存目錄（既有前例把快取放使用者家目錄下）。
- **正確性回歸** — 最大的風險是候選變多之後排序品質下降（更多雜訊進來）。這是 [S12] 存在的唯一理由，也是本案唯一不能省的閘。
- **併發** — 多個會談同時觸發重建要互斥；索引寫到一半被讀到要能偵測。
- **資源** — 索引檔會長大，要有大小上限與清理策略。
- **不可逆與回滾** — 索引是衍生資料、刪掉就重建，**沒有不可逆的東西**。程式面的回滾是 git。
- **狀態同步** — 索引是圖譜的衍生層，圖譜才是真相。索引過期時的行為在 [S7] 定義。
- **快取** — 索引本身就是快取，失效判準寫在 [S7]；測試不得靠快取判綠。
- **認證、限流、個資、金流、對外寄送** — 無。不出本機、不碰網路、不碰個資。

## 風險與回頭條件

- **「候選變多」可能讓精準度下降**，這是把召回破口修好的必然代價。處置：[S12] 三面對照，任一面退步不得收案。
- **索引靜默降級是最危險的失效模式**——使用者以為快、其實在跑慢路徑，而且不會有人發現。處置：[S7] 明訂要出聲。
