## 發現一：沒有任何機制保證「有索引」與「沒索引」兩條路徑對同一查詢給一樣答案——只有一句文件承諾

問一問的是「有沒有機制」，不是「有沒有意圖」。通讀 S4、S6、S7 全文，找不到任何一條測試名、任何一句條文提到「索引路徑與掃檔路徑的候選集要對得上」這件事本身要被驗證；[S12] 的前後對照是拿「有索引的新系統」跟「沒索引的舊系統」比，比的是**新舊版本**的品質差異，不是**同一版本、有沒有索引兩種執行狀態**的一致性。這兩者是不同的軸：[S12] 就算全過，也完全證明不了「同一支 lumos 二進位，在裝了 FTS5 的機器上跟沒裝的機器上，對同一句查詢回同一組候選」。

而這條軸剛好是本案最脆弱的地方：S2 明講 token 流沿用既有斷詞器（`_rank_tokenize`，`scripts/lumos:2675`），這支函式對長度大於一的連續漢字段只吐相鄰兩字的 bigram，對長度剛好一的段才吐 unigram——也就是說，同一個字「愛」，出現在查詢字串裡（整串只有一個字）會被切成 unigram「愛」，出現在文件「愛心捐款的筆記」裡（四字連續段）只會被切成「愛心」「心捐」「捐款」三個 bigram，永遠不含「愛」。索引路徑靠 token 相等比對，兩邊 token 不相交，回 0；掃檔路徑（`scripts/lumos:3034` 的 `needle in nfc(s).lower()`）是整串子字串比對，找得到。這是同一支程式在兩台機器上，對同一句查詢給不同答案，而且是**系統性**的（凡是單字查詢、詞被嵌在更長詞語裡就會發生），不是邊角案例。

引句:「索引用標準函式庫的 FTS5，token 流由既有斷詞器產生。」

S2 這句話字面上聽起來像「沿用」是安全動作，但沒有一條測試名鎖住「查詢字串本身也要過同一支斷詞器再組 MATCH」——這正是通才席 F2 點名的缺口，而 r2 材料原封不動留著。

severity: blocker
blocking: 是——照字面實作，兩台機器對同一查詢給不同答案是可重現、系統性的錯誤行為，命中的正是這份設計自己在別處承認「必解」的問題，卻沒有一條條文真正解掉它。

## 發現二：查詢字串直接餵進索引會拋例外，而這個 repo 滿篇都是會踩到的寫法——獨立重現，S4/S6 完全沒提字串怎麼組 MATCH

自己跑了一段最小重現（不依賴 r1 的實驗，獨立驗證）：

```
import sqlite3
con = sqlite3.connect(":memory:")
con.execute("CREATE VIRTUAL TABLE t USING fts5(body)")
con.execute("INSERT INTO t(body) VALUES ('KEY: 這是一個測試 test: hello')")
con.execute("SELECT * FROM t WHERE t MATCH ?", ("KEY:",))
```

結果拋 `sqlite3.OperationalError: no such column: KEY`；`test:` 拋同款錯誤；未閉合括號、結尾 `OR`、單獨 `*`、未配對單引號各自拋不同的 `OperationalError`。而「KEY:」「test:」正是本 repo frontmatter 與 spec 條文自己滿篇在用的半形冒號慣例（這份被審的材料自己就寫了 `[test:t_candidate_from_index_multiword]` 這種字串），使用者把一段筆記內容複製去搜，或程式把 `KEY:` 開頭的一行拿去當查詢，會直接讓 CLI 拋未捕捉例外，不是排序變差。

引句:「候選階段改吃索引，召回破口一併修。」

S4 全文只講「候選不再要求連在一起」，沒有一個字提到查詢字串要怎麼組 FTS5 的 MATCH 語法、要不要跳脫、遇到 FTS5 保留字元（`:` `(` `)` `*` `'` `OR` `AND` `NOT`）要怎麼處理。S6 把三條路徑（search／入口召回／關聯推薦）全部接到同一份索引，代表這個例外不是只有 `search` 指令會踩到，入口召回（動手前的 hook 自動觸發）與關聯推薦也會踩到——而入口召回是**自動**呼叫、使用者不會主動選字串，若被動手前的檔案路徑或既有筆記正文（含 `KEY:`／`test:`／`DEP:`）當成查詢餵進去，會在使用者無感的情況下讓 hook 整段失敗。

severity: blocker
blocking: 是——這是會讓指令當場拋未處理例外的輸入類別，而該輸入形狀是本專案自己的日常書寫慣例，不是邊角案例；照字面實作必定會在近期內被真實觸發。

## 發現三：降級要「出聲」，但出聲要出給誰、出在哪，条文完全沒界定——子行程的 stdout 最後一行被單獨解析，其餘一律消失

引句:「索引不存在或壞掉要**出聲並退回現況的掃檔路徑**，不得靜默降級（靜默降級＝使用者以為在用索引、其實在跑慢路徑）。」

## 發現七：把工具複製到別的專案時，索引檔是空的還是別人的舊資料，条文沒討論——可攜性只解決了「FTS5 有沒有編進去」這一半，沒解決「衍生檔本身會不會跟錯語料」這一半

問五分兩層，材料只答了一層。第一層（FTS5 編譯能力因機器而異）在「實務隱患」段有明講且要求偵測＋退回＋出聲——這是前掃已經打進去、確實存在的內容，我核對過不是虛報。但第二層完全沒有任何文字碰到：**索引檔本身是不是也會被複製**。lumos 的散布方式是把整支腳本（乃至整個工具目錄）複製或以 symlink 拉進消費專案；如果索引檔物理上放在工具目錄底下、或者複製流程用 `cp -r` 整包搬，新專案拿到的索引檔內容是**上一個專案的語料**，不是空的。而 S7 的失效判準只看「檔案修改時間與篇數」，不看語料身分（vault 路徑、內容雜湊）——如果新舊兩個專案的檔案數量湊巧接近、且複製動作本身重寫了索引檔的修改時間（比對比修改時間更新），S7 的判準會判定「沒過期」，於是新專案直接吃到上一個專案的搜尋結果，這不是「變慢」，是**答非所問**：查的是這個專案的詞，回的是別的專案裡湊巧同名的節點。

severity: major
blocking: 是——這句話把「可攜性風險」窄化成一個二元的環境能力問題（有沒有編進去），完全沒觸及衍生索引檔本身作為一個會被複製、且沒有語料身分校驗的檔案，會不會把錯誤的搜尋結果跨專案帶過去；而 S7 的失效判準（修改時間＋篇數）不足以擋下這個情境，前面已論證。

## 發現八：改名與刪除永遠偵測不到，這個問題也只停在 frontmatter 那一行 KEY，S7 條文原封不動

跟發現一同款的模式，但這裡是刪除／改名而非查詢語意。S7 全文：

引句:「判失效看檔案修改時間與篇數；索引不存在或壞掉要**出聲並退回現況的掃檔路徑**」

只看「檔案修改時間」與「篇數」兩個聚合訊號。改名操作既不改動新檔內容的修改時間、篇數也不變（一篇消失、一篇出現，總數持平）；刪除一篇再新增一篇無關的篇也一樣，篇數持平。兩種情況索引都會判定「沒變」，於是：舊檔名底下的死條目永遠留在索引裡繼續被搜到、新檔名的內容永遠進不去索引。這件事直接影響我的鏡頭要看的「退回是否安全」——因為死條目不會讓程式報錯，是安安靜靜地回錯答案（回一個已經不存在的路徑，或漏掉剛改名的那篇），比拋例外更難被使用者發現，而且沒有任何一條測試名（`t_index_invalidates_on_mtime`）看得出涵蓋改名或刪除這兩種操作。

severity: blocker
blocking: 是——這是圖譜日常操作（改名、刪除筆記在這個專案每天都在發生），照字面實作會產生系統性、不會自我修復的假陰性／死條目，且沒有任何條文或測試釘住這個維度，跟 r1 邊界席 F1／F8 判定的等級一致，而 r2 材料在這一條上沒有任何字面變動。
