S13 的存在理由是防止 2026-08-22 那次「改善檢索→新節點沒標過→全部計 0→假退步被讀成有害」的事故重演，條款本文寫「前後對照之前，要先把新系統撈到、而舊池沒有的候選補標」——時間順序是 S13 在 S12 之前跑。但兩者的編號是 S12 在前、S13 在後，而且 S12 自己的文字（「速度、金標三指標、召回率三面各跑一次前後對照」）完全沒有提到要先跑 S13、要用擴大後的池，也沒有引用 S13 這個編號。一個只照編號順序或只讀 S12 本身當驗收清單的人，完全可能先跑 S12、拿舊池的三指標當收工依據——那正是 S13 整條存在要防的那件事又原地重生。這是折入本身製造的新問題：折了 A（新增 S13 解決回滾席#3）卻沒有同步改依賴 A 的 B（S12 這個真正的閘）。

引句:「前後對照之前，要先把新系統撈到」

### F7 「數字口徑」提示框說 S1 要求釘住固定提交重跑，但 S1 本文沒有這句話

severity: minor
blocking: 否

量到的基線那一段的提示框寫「[S1] 要求收工前用固定提交重跑一次釘住」，把這件事講成是 S1 條款自帶的要求。但翻回 S1 本文（「先量基線再動手。速度、精準、召回三面各留一組可重跑的數字，之後每一條改動都要對得上這組基線」），完全沒有提到要釘固定提交重跑。這是「同一件事在材料裡有兩種說法」的典型：提示框和它引用的條款本身內容對不上，只把 S1 自己的文字當驗收清單的人會漏掉這個步驟。

引句:「[S1] 要求收工前用固定提交重跑一次釘住」

### F8 候選來源／語料口徑（spec 自認最高風險項）沒有配旋鈕，跟同一份文件裡另外兩個等風險項的處置不一致

severity: major
blocking: 是

S8、S11 都配了「可切換的旋鈕」，用來在數字出來之前不擅自替 Enzo 決定答案。S4（候選從掃檔換成索引）、S5（語料從候選集換成全庫統計）是這份設計裡影響面最大、r1 三席共同認定風險最高的兩個改動，卻完全沒有等價的開關——風險與回頭條件段落仍只寫「索引是衍生資料、刪掉就重建，沒有不可逆的東西。程式面的回滾是 git」。這代表一旦候選來源本身有問題，唯一的收斂方式是整支分支回退，會連帶退掉建立在新索引之上的所有後續條款（S6、S9、S10 等），跟同一份文件對同等風險項目的處置慣例不一致。

引句:「**沒有不可逆的東西**。程式面的回滾是 git」

### F9 「不得靜默降級」沒有處理降級訊號怎麼穿過 hook 的 stdout-only JSON 解析

severity: major
blocking: 是

S7 要求索引壞掉或缺席時「不得靜默降級」，並把靜默降級定義成「使用者以為在用索引、其實在跑慢路徑」。但這份設計會被三條字面路徑共用（S6），其中一條是動手前注入用的入口召回，是被 hook 呼叫、hook 只解析子程序 stdout 最後一行 JSON 印進注入內容的。子程序把降級警告印到 stdout 或 stderr，不代表這個警告會被 hook 轉送進真正注入給使用者／下一個 session 的文字裡。S7 全篇沒有一個字提到降級狀態要放進 hook 消費的那個 JSON 合約裡，「不得靜默降級」這句話本身在 hook 這條路徑上仍然可能是空話。

引句:「不得靜默降級（靜默降級＝使用者以為在用索引、其實在跑慢路徑）」

### F10 查詢編譯契約完全沒定義（AND/OR 預設、特殊字元跳脫、跟既有旗標的相容性）

severity: major
blocking: 是

S4 只寫「多詞查詢不再要求那幾個字連在一起出現」，沒有指定多詞之間預設是 AND 還是 OR（外家席實測兩者候選數差了 8 篇對 204 篇）、沒有指定 FTS5 特殊字元（引號、括號、連字號）在查詢字串裡要不要跳脫或消毒、也沒有處理跟既有 `--regex`／`--no-any`／`--cjk-loose` 幾個旗標要怎麼相容。全篇搜不到 `MATCH`、AND/OR 語意、或任何跳脫規則。這不是措辭問題——同一句條款字面上可以被實作成候選數量相差數十倍的兩種版本，且兩種版本都「符合」條款文字。

引句:「多詞查詢不再要求那幾個字連在一起出現」

### F11 併發互斥沒點名要借用哪個既有原語，而本 repo 明文警告過「另開第二套鎖」

引句:「首次建立成本要印出來。併發重建要有互斥」
