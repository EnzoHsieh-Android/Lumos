severity: major

## F1 效能與提早熔斷(S8/S9)的計算時機自相矛盾
severity: major
blocking: 是——照字面實作,實作者要嘛讓 S8/S9 的提早熔斷永遠不觸發,要嘛讓「平常不算」的效能承諾破功,兩者只能選一個,選錯就是做出違反條款的系統。
引句:「只在輪數達上限或觸發熔斷條件時才算,平常不算」
引句:「即使還沒跑滿上限」
敘述:「實務隱患」的效能段落說報告只在「輪數達上限」或「已觸發熔斷條件」時才計算三個訊號,平常(未達上限)不算。但 S8(連續兩輪過半修正引起)與 S9(累計折入超過 20 條)兩個提早熔斷條款的定義就是要在「還沒跑滿上限」的每一輪都判斷「這一輪是不是已經觸發」——要知道「有沒有觸發」,唯一辦法就是先算出訊號(修正引起比例、累計折入數),這件事沒辦法在「已觸發」之後才做,因為「已觸發」正是算完訊號才知道的結論。也就是說 S8/S9 要求的「不等到最後一輪」跟效能段落寫的「只在達上限或已觸發時才算」在邏輯上互斥:若真的只在達上限或已觸發時才算,`loop status --disposal` 在未達上限、尚未觸發的每一輪都不會去檢查是否觸發,S8/S9 兩條就永遠不會被觸發(因為觸發本身需要先算)。反之若要讓 S8/S9 真的每輪都能生效,就必須每輪都算三個訊號,效能段落的「平常不算」就不成立。程式碼現況:`scripts/lumos` 的 `_loop_status_disposal`(scripts/lumos:18265)每輪呼叫一次,目前沒有任何「先便宜判斷要不要算」的機制可以在不算訊號的情況下就知道是否該提早熔斷。

## F2 併發容錯寫在 pitfall,但既有 disposal 的壞行守衛已經在報告函式跑到之前就整段擋掉
severity: major
blocking: 是——S6 要求「輪數已達上限時 `loop status --disposal` 應印出與 S1 相同的一段」,但在計劃自己點名的併發情境(同工作目錄多會談同時記帳)下,這段輸出實際上印不出來,S6 在真實併發場景下等於沒被滿足。
引句:「讀到寫一半的最後一行要當沒這行,不得整段報錯」
file: `scripts/lumos:9598-9605` `_loop_status_disposal` 的呼叫端(`cmd_loop_status`,scripts/lumos:9542 起)在讀 `.canary-log.jsonl` 時,任何一行 JSON 解析失敗就把 `n_badlines` 加一(這是掃整個檔案的所有行,不分是不是這個 `loop_id` 的資料),不是只看「最後一行」。
file: `scripts/lumos:18276-18283` `_loop_status_disposal` 一進函式最先做的事,就是「若 `n_badlines` 非零,印『擋下』並直接 `return 2`」——這一步在任何七個處置閘步驟、以及計劃要新增的「上限報告」呼叫點之前就發生,直接短路整個函式。
敘述:計劃的「併發」隱患段落假設新報告函式自己會對「讀到寫一半的最後一行」做容錯(當沒這行、不整段報錯)。但 `loop status --disposal` 這條路徑(S6 指定的印出點)在報告函式有機會執行之前,就已經被既有的 `n_badlines` 檢查攔下並直接回傳 rc2、不印任何東西(包括原本七步驟的其他輸出、以及計劃要加的上限報告)。也就是說,在計劃自己描述的最壞情境——「同一個工作目錄好幾個會談同時記帳,帳本最後一行寫到一半」——`loop status --disposal` 本身已經會整段報錯退出,新報告函式的容錯邏輯根本沒有機會被執行到,S6 承諾的「輪數已達上限時印出同一段」在這個情境下不成立。這不是新程式碼要不要做對的問題,是既有守衛的攔截點比計劃設想的容錯點更早,新邏輯寫得再好也碰不到輸入。

## F3 PRIOR-ART 聲稱沿用 quote-check 的引句定位,但既有 quote-check 不回傳行號、也不做「新增行」比對
severity: major
blocking: 是——S2 與 S7 的判準都建立在「引句落在凍結審材的哪一行、那一行是不是上一輪沒有的新增行」,但可沿用的既有函式只做「正規化後全文字串是否存在」的布林判斷,不記錄、也無法回推對應行號,S2/S7 字面實作不出來,要嘛另起一套行級比對邏輯(不算沿用既有機制,計劃的「不加新依賴」前提就不成立),要嘛就做不出計劃要求的行為。
引句:「定位到的那行是新增行,而且這行不在上一輪凍結審材的任何地方」
file: `scripts/lumos:17869-17886` `_quote_rows`(quote-check 核心,T4 抽出供 CLI 與 disposal gate 共用)裡,比對邏輯是 `anchored = nq in hay or nq.replace(" ", "") in hay_ns`——`hay`/`hay_ns` 是整份凍結審材正規化後摺成一整串空白分隔文字的字串,函式回傳的每一列只有 `{'quote','ok', ...}`,完全沒有行號或位置資訊。
file: `scripts/lumos:18588-18617` `cmd_quote_check` 直接消費 `_quote_rows` 的回傳,一樣只印「✓/✗ 第幾句引言」,不涉及、也算不出「這句引言落在凍結審材第幾行」。
敘述:計劃第 2 個訊號(修正引起的比例)與 S7(引句定位不到單獨列計)都預設「引句可以定位到凍結審材的某一行,再跟上一輪的凍結審材逐行比對是否為新增行」,但現有 quote-check 機制(`_quote_rows`/`cmd_quote_check`)做的是「正規化後拿掉換行與多餘空白,整份文字當一個字串做子字串存在性判斷」,設計上就沒有行的概念(甚至刻意把跨行內容摺成一行,見 `_quote_norm` 對換行與 blockquote 記號的處理,scripts/lumos:17849-17857)。要做 S2/S7 要求的「行級定位 + 逐行新增比對」,勢必要另外寫一套從正規化字串位置回推原始行號、再對兩份凍結審材做逐行 diff 的邏輯——這是全新的機制,不是計劃 PRIOR-ART 段落所說「沿用既有的…quote-check 的引句定位、不加新依賴」能涵蓋的範圍,計劃低估了 S2/S7 的實作複雜度與新引入的程式碼量。

已看,無:計劃的機制入口(`loop next` 的 cap-reached 分支 scripts/lumos:10675-10680、`loop status --disposal` scripts/lumos:9625-9631/18265 起)確實存在且如計劃所述,可以在這兩處掛新的報告呼叫,不需要新增指令或改動既有判定路徑;S6「不改變原本的過關判定與退出碼」與 S9「不改變過關判定與退出碼」在目前 `_loop_status_disposal` 的結構下是可行的(只要新報告呼叫點只印文字、不影響 `fails` 累積與最終 return 值)。`--finding-class` 目前不存在(`lumos canary record --help` 確認),計劃把它列為「選填新旗標」而非既有旗標,沒有名實不符的問題。計劃提到 `record_cmd` 已改印 `canary record none`(不再建議已停用的 `caught|missed`),對照 scripts/lumos:10641-10650 屬實,「順帶看到」段落的修正紀錄與程式碼現況一致。對照 `[[Systems/design-loop]]` 的 ★INVARIANT★(處置閘第五步的判定優先序與條款綁定合取邏輯):本計劃只在既有輸出後面加印一段文字、不改動 `_disposal_clause_step`、`_hash_chain_check`、`fails` 累積等既有判定路徑,也不改變 `emit()` 的 phase 優先序(escalate→gate-pending→converged→cap-reached→plant-canary),不影響該節點宣稱的行為或合約。`_TIER_PARAMS`(scripts/lumos:9801)裡代碼審 standard/high 的 cap 皆為 3,計劃摘要提到多個代碼審迴圈跑到 4 輪以上甚至 28 輪、遠超上限,與帳本現況一致,沒有失真。

## 實務隱患逐類
- 併發:有具體疑慮,見 F2——既有 `n_badlines` 全檔掃描 + fail-closed 的攔截點比計劃設想的「報告函式自己容錯」更早,計劃的併發容錯在 S6 路徑上實際不可達。
- 效能:有具體疑慮,見 F1——「平常不算」與 S8/S9「不等跑滿就要能觸發」在邏輯上互斥。
- 金流/對外送出/不可逆/守衛面:計劃自陳「已排除」且理由具體(純讀帳、純印文字、不呼叫外部服務、回退只是拔掉兩處呼叫、不改任何閘的判定),對照程式碼現況(`_loop_status_disposal` 的 `fails` 清單與 return 值決定過不過關,新輸出若只是額外 print 不寫入 `fails`,確實不影響判定),這四類「已排除」成立,不再另開。

最嚴重 severity: major;blocking 共 3 條(F1、F2、F3)。
