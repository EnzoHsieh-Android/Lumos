**Finding 1: if only the batch process is killed, its probe child keeps running, the lock is gone, and a second batch can start the same job in parallel**
severity: minor
blocking: 否
引句:「同一輸出目錄的另一個 CLI 可能已在跑模型；其 stop 旗標不會跨進程共享。」
file: `governance/eval/ablation_lumos_first.py:437` (the `lock_fd` / flock section), `governance/eval/ablation_lumos_first.py:205` (`subprocess.run`)

Cause: the directory lock and the old-style lock are held only by the batch process. The probe child doesn't inherit them (`close_fds`), and it isn't put in the runner's process group or terminated when the runner dies.

Sequence:
1. Batch A calls `run_job(with, q1, 3)`, and the probe child starts calling the model.
2. Someone runs `kill -9 <A's pid>`, or a supervisor sends SIGTERM to that pid only.
3. The kernel releases both of A's locks, but the probe child carries on.
4. Batch B starts and gets both locks. q1 has no result file yet, so `needed` = 3 and B starts a second q1 probe.
5. Two models now run in parallel, which defeats the point of "single-path dispatch". When both finish, q1 has 6 valid runs, so it is over-weighted in `_arm_stats`.

Why it's only minor:
- Ctrl-C or closing the terminal sends the signal to the whole foreground process group, so the child dies too. Only a kill aimed at the runner's pid alone triggers this.
- The pre-patch version had no lock at all, so this is a gap in the new protection, not a regression.
- I couldn't produce a red reproduction with the real model.

Minimal reproduction sketch: replace `PROBE` with a script that sleeps 30 s and then writes a valid result → start A → `kill -9` A → immediately start B → B gets rc≠3 and starts a probe while A's child is still alive.
