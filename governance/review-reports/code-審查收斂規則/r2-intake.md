# code-審查收斂規則 r2 收貨紀錄

七席全回(正確性、併發、邊界、合約、通才、架構對齊、資安),report-normalize 都不用改、quote-check 全數錨定。共 21 條:正1–3、併1–2、邊1–4、合1–3、通1–2、架1–3、資1–4。

## 根因分組與處置

同輪有 major(正1、邊1–3、通1、資1–3),accepted 必空,21 條全部折入。

- G1 測試檔收窄造成漏判(正1、邊1、通1、資2、邊4):上一輪為了降噪,讓測試檔只在 diff 碰到綁定測試名時才算命中;git 段落標頭只抓頂格行,縮排在 class 裡的測試方法(Kotlin、Java、Swift、class 式 pytest)改本體判不到,改輔助函式或夾具也判不到。四席獨立實測重現。→ 測試檔改回整檔算命中(拿掉收窄,邊4 的字邊界測試缺口隨之消失);代價是本 repo 改到測試總檔常升 high,在計劃寫明。
- G2 正規化過頭(正2、邊2、邊3):反例編號只留字母數字讓 `c1.1` 與 `c11` 撞在一起;宣稱指紋去掉所有標點讓「上限 1.5 倍」與「上限 15 倍」、「回傳 -1」與「回傳 1」撞在一起。→ 編號:NFKC、casefold,連續的非字母數字合成一個分隔符、頭尾去掉;指紋:NFKC、空白壓成一個、去掉句尾標點,句中符號保留。
- G3 改字或刪帳重問(資3):判過測得到的反例,改一個字換掉指紋或刪掉帳列就能重問。→ 判過 testable 的反例以(節點、反例編號)記,不綁指紋,之後不准再判 untestable;推送範圍刪掉治理帳裡 residual-ask 的列時升 high。
- G4 分兩次推送縮小守備範圍(資1、資4):拿掉殘留只比(節點、殘留指標),about_code、測試檔清單、測試名縮小不算。→ 同一筆殘留在起點有、頂端沒有的守備項目也算拿掉殘留、升 high。
- G5 git 出錯時方向不一(併1):起點索引讀不到當成空的、檔名清單失敗當成沒改。→ 起點讀不到(不是檔案不存在)記成讀不出並升 high;檔名清單失敗而索引有殘留時升 high。
- G6 沒事可做的路也重寫索引(併2、通2):「已經有了」「沒有這個標記」都重寫索引,打錯字的指令在工作樹留下沒要求的改動,補好了也不講。→ 只在索引跟重算結果不同時才寫,寫了就講。
- G7 不認得的判定值會當掉(正3):帳裡的問答判定值不是 testable 或 untestable 時取空清單第一項丟例外。→ 不認得的判定值當成沒有這筆問答,不當掉。
- G8 條款、回頭條件與手冊說法(合1、合2、合3):[S6] 沒跟上新規則、新測試沒綁條款;四個殘餘風險只有兩個有回頭條件、承認句沒搬成獨立一行;手冊說寫入時驗了前三步的順序,實際只驗存在。→ 條款改寫並綁測試;每個殘餘風險各一行回頭條件,原行刪掉承認句;寫入時驗 [audit:] 的日期不早於問答日期。
- G9 寫法對齊(架1、架2、架3):兩套決策指標比對沒註明分工;寫失敗回原因的寫法沒註明先例;去註解函式離主要呼叫者太遠。→ 補註解、搬位置。
