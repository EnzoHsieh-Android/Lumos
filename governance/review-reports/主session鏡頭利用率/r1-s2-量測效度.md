# r1-s2 量測效度審(主session鏡頭利用率)

席位:量測效度。前提假設=這份 spec 定義的「命中率」有系統性偏差,逐條找偏差來源。

### f1 推播抵達的時間點在「Edit 之前」這個窗之外,窗內只能收到巧合

hook 是那次 Edit 的 PreToolUse,注入文字隨該次 tool result 抵達;spec 卻只認那次 Edit 之前的碰觸,所以凡是「被這次推播引發」的閱讀一律落在窗外、算成沒碰。窗內唯一算得到命中的是「推播還沒發生就自發查過」的巧合,而那恰恰不是鏡頭的功勞。照字面量出來的數字會逼近零,直接踩 <20% 那條線。

引句:「同一回合裡、那次 Edit 之前,session 對 P 裡任一節點做過 `lumos context/show`(使用帳)」

file: `scripts/hooks/claude/impact-hook.py:400`(「PreToolUse 的 additionalContext 注在 tool result 旁」)

severity: blocker
blocking: 是

### f2 第三種證據建在一個認不得 cat/sed/grep 的函式上

spec 把「Bash 指令裡出現筆記路徑」直接掛到既有 `extract_bash_file_paths`,但那支只認 rm/mv/cp/git rm/git mv 五種破壞性操作,`cat` / `sed -n` / `grep` 的第一個 token 一律在 `head not in BASH_FILE_OPS_PATH_BEARING` 被丟掉。本 repo 幾乎不用 Read(實測三份最近逐字稿 Read 各 0/0/1 筆、Bash 366/60/337 筆),所以第三種證據會恆為空,spec 想修掉的假陰性原封不動留著。

引句:「既有 `extract_bash_file_paths` 已能從 Bash 指令抽檔案路徑(第三種證據直接沿用)」

file: `scripts/hooks/claude/check-graph-sync.py:69`

### f3 分母 |P| 由「改到哪支檔」決定,同一種行為可以量出 50% 或 10%

實測同一份 vault:改 `check-graph-sync.py` 推 4 篇固定席、改 `test_lumos.py` 推 20 篇。同樣是「動手前查了 2 篇」,前者=50%(裁「第二段不做」)、後者=10%(裁「必答」)。而 `test_lumos.py` 近 14 天被改 94 次、占 code 檔改動的 34%,總命中率會被這種大分母檔主導,量到的是檔案的圖譜密度不是 session 的行為。

引句:「命中率=|P∩碰過|/|P|」

### f4 最常改的 `scripts/lumos` 沒有副檔名,永遠不會被推、也永遠不進樣本

引句:「它推的固定席=`pinned: true` 的節點(帶硬合約或出過事故)」

### f6 使用帳沒有 session_id,對不了帳;時間戳又沒時區

現有 375 筆使用帳的欄位全部只有 ts/node/cmd,pushed 事件帶 session_id、touched(context/show)不帶,兩邊只能用時間窗湊。多 session 併行(本 repo 常態)時,別的 session 的 `lumos show` 會落進窗內被算成本回合碰過(假陽性)。ts 是 `2026-09-03T20:30:58` 這種無時區本地時間,而 spec 自己說多機 append 會合併,跨機時間窗根本不可比。
