## 二、本輪 findings

### f1 pinned 解析的字串格式六週內至少改版一次,r2-s2 的「28 次/2 個 session」很可能是解析失敗的偽陽性,不是真母體

`build_ranked_context` 的必看段標頭字串在 2026-08-22(commit 9cf8812)從 `必看(合約/事故固定席 N):` 改成 `必看——這 N 篇帶著不能破壞的合約或出過事故:`。實測本專案 44 次真實推送裡,舊格式 16 次(37434956、2050a426 兩個 session,2026-08-14~18)、新格式 28 次(1d8277bf、dd1cfb7c 兩個 session,2026-08-22~09-02)——r2-s2 的「28 次、2 個 session」精確等於新格式子集,舊格式的 16 次(另外 2 個 session)完全沒出現在 r2-s2 任何一條 finding 裡。

引句:「pinned 清單★從注入全文解析★」

指令+輸出:`git log` 對 `impact-hook.py` → `9cf8812 2026-08-22 style(hooks): 訊息白話第一批`(改「必看(合約/事故固定席 {len(pins)}):」→「必看——這 {len(pins)} 篇帶著不能破壞的合約或出過事故:」);本專案 44 次注入按格式與 session 分組 → `舊格式 16(37434956:8, 2050a426:5,含空 pinned 前為 raw count)/新格式 28(1d8277bf:19, dd1cfb7c:9)`

severity: blocker

blocking: 是

### f2 就算不管 f1,拿 r2-s2/r3 自己認定的母體算,分層抽樣的「每 session 至多 3 筆」也湊不出 10 筆

r2-s2 f11 與 r3 現況都認定「歷史推送只在 2 個 session」(1d8277bf、dd1cfb7c);這兩個 session 裡有 pinned 的推送分別是 14 與 9 筆。「每 session 至多 3 筆」的上限下,兩個 session 最多只能貢獻 3+3=6 筆,比規則要求的 10 筆少 4 筆——這不是機率小,是這個上限與這個母體在算術上互斥,規則寫不出來能執行的抽樣程序。

引句:「分層抽(每 session 至多 3 筆、每檔型至少 2 筆),10 筆」

指令+輸出:對 1d8277bf、dd1cfb7c 兩份逐字稿的 Edit/Write 注入分類 → `1d8277bf: total 19 nonempty 14 / dd1cfb7c: total 9 nonempty 9`;`2 個 session × 3 筆上限 = 6 < 10`

severity: blocker

blocking: 是

### f3 「60% 推送在子代理」這個數字本身仍未重驗,獨立重數是「全機子代理 0 次」不是「本專案子代理 0 次」

r2-intake 已經把 s2 的「子代理 42」列為「本專案重現不了、腳本第一件要釐清的事」,但 r3 的誠實界線段落原封不動保留「60% 推送在子代理」這句話當既定事實。我把範圍從「本專案」擴大到整台機器(1404 份子代理逐字稿、含本專案 799 份),`attachment.type == hook_additional_context` 不分 hookName 一律算,結果是 0——不只 Edit/Write 是 0,連任何 hookName 都是 0;逐字稿裡出現「必看」字樣的地方全部是筆記內文被 Read 出來,不是真注入附件。這代表 42/70/60% 這組數字目前看起來不是「口徑不同重現不了」,而是量測本身有錯,而 r3 把它寫進了本該最誠實的那一段。

引句:「子代理推送與主 session 分開報(60% 推送在子代理)」

指令+輸出:`find ~/.claude/projects/*/*/subagents/*.jsonl | wc -l` → 1404;逐檔過濾 `attachment.type=="hook_additional_context"` 不分 hookName → 命中 0(本專案 799 份子項也是 0);另外對含「必看」子字串的 1827 處逐一核對型別 → 全部是 `type: tool_result` 裡的筆記正文,不是 `type: attachment`

severity: blocker

blocking: 是

### f4 「寫回不算讀」的動詞規則把「先讀再寫」的腳本整批誤判成純寫回,漏掉將近一半確實讀過內容的樣本

規則把任何含筆記路徑的 `python3 - <<EOF` 一律算 wrote_back、不算碰觸,不看腳本內部做了什麼。實測本專案歷史裡碰筆記路徑的 `python3 - <<EOF` 呼叫共 1293 次,其中 572 次(44%)腳本內同時有 `read_text()` 與 `write_text()`——先讀進內容做字串核對(不少還帶 `assert s.count(old)==1`)才寫回,跟人手動打開檔案讀過再編輯是同一個動作,卻被規則整批打成「沒讀,只是寫回」,直接漏記將近一半的真實讀取證據。

引句:「`python3 - <<` 內含筆記路徑的改寫」

指令+輸出:掃 `python3 - <<` 且指令含 `docs/`或`-knowledge` 的呼叫 → `總數 1293,同時含 .read_text(/open(...,'r' 與 .write_text(/open(...,'w' 的 572 次`;例:`p = Path("docs/lumos-toolchain-knowledge/Systems/slim-scan-掃描器.md"); s = p.read_text(); ...assert s.count(old)==1; p.write_text(...)`

severity: major

blocking: 是

### f5 ⚠ 背景執行的 Bash 讓「行序」錨點跟「模型真的看到內容」這件事脫鉤,規則沒處理

`run_in_background=true` 的 Bash 呼叫,tool_use 行落地的時間點與內容真正回到模型手上(透過另一次 BashOutput/monitor)的時間點可以差很多、甚至跨到後面幾十行之後——但規則②只看指令字串本身(動詞+路徑 token)在哪一行,不看內容何時真的可見。本專案歷史有 287 次背景 Bash,其中至少 1 次是對圖譜路徑的讀動詞指令;母體小,不足以估計影響有多大,但規則完全沒提到這個情境,判不準只能標記。

引句:「碰觸事件…錨點=toolUseID 對到的那次 Edit tool_use 的行序」

指令+輸出:`run_in_background:true` 的 Bash 呼叫共 287 次;其中指令字串本身是讀動詞+圖譜路徑的 → 1 次(`scripts/lumos anchor verify … | head -3 …`)

severity: minor

blocking: 否

### f6 ⚠ rule 4 保留的「檔型:scratch」跟 rule 3「scratch 不進分母」自相矛盾,rule 6 的分層抽樣要嘛抽不到、要嘛抽到不該抽的

rule 3 明文把 scratchpad/repo 外的目標檔排除出分母;rule 4 的每筆推送 schema 卻仍然列「檔型(test/scratch/code)」三型;rule 6 的分層抽樣要求「每檔型至少 2 筆」。兩種讀法都有問題:如果 scratch 真的被排除在外,分層抽樣去哪裡抽 2 筆 scratch 型?如果 scratch 沒被排除、只是文字上說「不進分母」但仍在抽樣池裡,那就是 r2-s2 f12 講的老問題原封不動——scratch 檔本來就該跳過,把僅有的 10 個抽樣名額硬性分兩個給「正確答案是不用查」的案例。

引句:「檔型(test/scratch/code)」

指令+輸出:對照 r3 全文——rule 3「★scratchpad 與 repo 外的目標檔另計不進分母★(歷史 28 次有 3 次)」與 rule 6「分層抽(每 session 至多 3 筆、每檔型至少 2 筆)」同時存在,兩條規則對「scratch 算不算在抽樣母體裡」給出不一致的答案

severity: major

blocking: 是
