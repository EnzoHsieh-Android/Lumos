# r2-s2 量測效度審(主session鏡頭利用率)

席位:量測效度。假設=這份 spec 量出來的數字,量不到它宣稱的東西。
本輪新增的量測基礎:逐字稿裡 hook 注入是有紀錄的(`attachment.type == hook_additional_context`,帶 `toolUseID`、注入全文、時戳),全機共 **70 次真實推送**(主逐字稿 28 + 子代理逐字稿 42),我用它把 spec 的演算法在歷史資料上乾跑了一遍,底下的數字都出自這一跑。

## 一、r1 十三條驗收

- **r1-f1(時間窗與注入時機互斥)**:已解——窗改成「推送 ts 之後到回合結束」,方向對了(但錨點選錯,見本輪 f1)。
- **r1-f2(extract_bash_file_paths 不認 cat/sed)**:已解——不沿用那支,改自寫 `collect_turn_touches`,規則②明寫 cat/sed/grep/head 都算。
- **r1-f3(分母隨圖譜密度浮動)**:未解——比率砍掉了,但二值 `any` 的分母仍是 |P|,實測 |P| 從 0 到 27(本輪 f4)。
- **r1-f4(scripts/lumos 無副檔名永不入樣)**:已解——`hook_decide` 加 shebang 判定是真的改行為;但該檔實務上走 Bash 改,補到的樣本近乎零。
- **r1-f5(跳過是合規、精確度未知)**:已解——門檻全砍、改人工抽樣判跳過(抽樣設計本身有洞,本輪 f11)。
- **r1-f6(使用帳無 session_id / 無時區)**:已解——證據全改從逐字稿取,使用帳明寫不動。
- **r1-f7(collect_turn_actions 丟順序)**:已解——獨立收集器回有序 [(ts, kind, path|cmd)],不改原回傳形態。
- **r1-f8(對帳被早退閘吃掉)**:已解——獨立 hook、明寫放在任何判斷之前、不與 check-graph-sync 合體。
- **r1-f9(contracts/search 不寫使用帳)**:已解——它們是 Bash 指令,逐字稿看得到,不再依賴使用帳。
- **r1-f10(TTL 偏樣本)**:未解——只在誠實界線加一句承認,沒有處置也沒有回頭條件,且 TTL 鍵與子代理共用(本輪 f14)。
- **r1-f11(n≥30 信賴區間跨兩門檻)**:已解——n≥30 與 50%/20% 兩條線都刪了。
- **r1-f12(受測者讀得到自己的分數表)**:未解——帳改 gitignored、對帳不印,但同時登進 `lumos gov` 第八源,而 `lumos gov` 是模型自己在跑的指令(本輪 f10)。
- **r1-f13(子代理歸屬未定義)**:未解——spec 給的分辨法(逐字稿無 isSidechain、靠 SubagentStop)實測是錯的,歸屬仍沒定義(本輪 f8)。

已解 9 / 未解 4。

## 二、本輪 findings

### f1 推送 ts 用 hook 執行時間,比 Edit 晚 1.3–3.4 秒,窗內的動作會被誤判成推送前

28 次真實注入實測:注入落地時戳減去該次 Edit 的 tool_use 時戳,中位 2.42 秒、最大 3.44 秒;這段窗裡模型已經送出的下一個工具呼叫(28 次中有 2 次)時戳小於推送 ts,照規則會被歸進 pre_touched。逐字稿本身已經有正確錨點——注入那行帶 `toolUseID`,可以直接對上是哪一次 Edit,不必拿另一個時鐘去比。

引句:「同一逐字稿、碰觸 ts > 推送 ts、路徑/節點 ∈ pinned」

指令+輸出:掃 3 份含注入的逐字稿 → `impact-lens injections found: 28 matched to an Edit: 28`;`hook_additional_context ts minus Edit tool_use ts (sec): min 1.31 median 2.42 p90 3.40 max 3.44`;`non-Edit assistant tool_use lines emitted between the Edit and the injection: {1: 2, 0: 26}`

severity: major

blocking: 是

### f2 儀器整段在重建逐字稿已經有的東西,而且記的是 hook 的清單不是模型看到的清單

推送本來就寫進逐字稿:`attachment.type = hook_additional_context`,欄位有 `hookName: PreToolUse:Edit`、`toolUseID`、注入全文(含必看清單)、UTC 時戳——lens push 子命令、獨立帳、gov 第八源三樣都是重複建置。差別只在一處而且是反的:帳記的是 hook 算出來的 pinned 名單,逐字稿記的是模型真的看到的那份文字,量「碰沒碰」該對的是後者。

引句:「`impact-hook.py` 在 `inject_ranked_context` 真的輸出時,subprocess 呼叫」

指令+輸出:`attachment keys: ['content', 'hookEvent', 'hookName', 'toolUseID', 'type']`;`hookName: PreToolUse:Edit`;content 內含完整「必看——這 1 篇帶著不能破壞的合約或出過事故」清單

severity: major

blocking: 是

### f3 五分之一的推送必看清單是空的,這些的 any 恆為 false

實測 28 次注入裡有 5 次(18%)完全沒有 pinned 節點,只有自由席或守衛面參考;`inject_ranked_context` 只要 results 或 lane 任一非空就輸出,所以這些照 spec 也會記一筆推送。它們的 `any` 定義上永遠是 false,直接把「推了沒碰」的分佈墊高 18%,而人讀分佈時看不出這一段是儀器造成的。

引句:「每次推送記 {touched:[…], any: bool, pre_touched:[推送前已碰的]}」

指令+輸出:對 28 次注入解析必看段 → `pinned-count distribution over real injections: {0: 5, 1: 16, 6: 1, 11: 6}`

severity: major

blocking: 是

### f4 二值 any 沒有拿掉密度依賴,只是把它藏起來

實測 |P| 分佈是 0/1/6/11(`scripts/lumos` 手動跑是 27),同一批逐字稿裡「該回合碰到那 4 篇固定席任一」是 1.2%、「碰到那 20 篇任一」是 5.8%——同一種行為,基準率差 5 倍,這正是 r1-f3 判死比率的那個理由,換成二值照樣成立。要靠「分檔型分佈」拆開,每一型都得有幾十筆,而全機歷史加起來只有 28 筆主 session 推送。附帶說明:我這席原本假設「推 20 篇時 any 幾乎必然為真」,乾跑不支持——|P|=11 的 6 次全部 any=false,|P|=1 的 16 次有 3 次 true,問題是變異不是飽和。

引句:「改每次推送記二值+明細,人讀分佈」

指令+輸出:全 856 回合掃描 → `turns hitting >=1 of the 20 pinned (test_lumos.py): 50 5.8 %`、`turns hitting >=1 of the 4 pinned (check-graph-sync.py): 10 1.2 %`;乾跑 → `pushes by |P|: {1: 16, 11: 6, 6: 1}`、`any=true by |P|: {1: 3, 6: 1}`

severity: major

blocking: 是

### f5 pre_touched 只有 4% 會 fire,而且跟 touched 的歸屬互相打架

乾跑 23 筆有 pinned 的推送,pre_touched 非空的只有 1 筆(4%)——這個欄位撐不起「推送前已碰過的不算命中也不算沒碰」這件事,絕大多數推送它就是空的。更麻煩的是同一篇推送前後都碰時規則自相矛盾:命中規則只看「碰觸 ts > 推送 ts」,那篇會同時進 touched(any=true)與 pre_touched,散文卻說推送前碰過的不算命中,實作者兩種都寫得出來。

引句:「推送前已碰過的另記,不算命中也不算沒碰」

指令+輸出:乾跑 → `injections with >=1 pinned: 23 any=true: 4 any=false: 19`、`injections with non-empty pre_touched: 1`、`cases where a node is in BOTH touched and pre_touched: 0`

severity: major

blocking: 是

### f6 規則②不看動詞,寫筆記、git add、變數賦值都會記成「看了鏡頭」

實測含筆記路徑的 Bash 指令 1037 條,主流形態是 `cd …; grep …` 複合句、`python3 - <<EOF` 讀進來改寫再寫回的腳本、`P=docs/…/x.md;` 這種賦值,以及 `git add <筆記>`——照規則全部算碰觸。這些恰好是收工寫回的動作,而 Stop hook 的 `_impact_missing` 專門點名「跟你改的碼直接相關、帶合約、這輪卻沒動」的 pinned 筆記逼你去動,所以「碰」跟 impact-hook 這個鏡頭之間沒有因果——乾跑抓到的 any=true 案例裡就有一條是 `git add … <筆記>`。

引句:「Bash 指令任一 token 是圖譜根下的路徑(cat/sed/grep/head 都算)」

file: `/Users/enzo/harness/lumos-toolchain/scripts/hooks/claude/check-graph-sync.py:349`(`_impact_missing` 取 `pinned` 未動的前 8 篇)、`:404`-411(印出來逼動)

severity: major

blocking: 是

### f7 規則③的 search 分支是空條款,真正在跑的只有 contracts

全機逐字稿 289 次 `lumos search`,詞等於節點名或檔名主幹的 **0 次**——家規要求中文查詢概念之間加空白,所以 search 的詞永遠不是節點名。同一批資料 `lumos contracts` 只有 28 次,規則③實際上只靠 context/show/contracts 三個動詞在撐;反過來若哪天真的 fire 了,`lumos search <節點名>` 命中的是一張列表不是那篇內文,照樣記成碰。

引句:「Bash 指令是 `lumos context|show|contracts|search <詞>` 且 <詞> 對上 pinned 節點名或其檔名主幹」

指令+輸出:`lumos search invocations: 289 whose term equals a node name: 0`;`lumos contracts invocations: 28`

severity: minor

### f8 子代理那句現況是錯的:逐字稿有 isSidechain,session_id 主子同值,而六成推送在子代理身上

實測 786 份子代理逐字稿(路徑 `<session>/subagents/agent-*.jsonl`)**每一行都有 isSidechain=True 並帶 agentId**,而它們的 `sessionId` 就是主 session 的 id——spec 寫的分辨法既是錯的也不必要,而 push 端 `is_subagent` 從哪個欄位來完全沒寫。這件事直接決定裁定規則能不能算:全機 70 次推送有 42 次(60%)落在子代理逐字稿裡,主子分不開的話,「主 session 推送 <20 次」是拿一個六成是子代理的混合池在判。

引句:「子代理推送與主 session 分開報;子代理逐字稿無 isSidechain 標記,靠 SubagentStop 事件分辨」

指令+輸出:`subagent transcripts total: 786`、`injections inside subagent transcripts: 42`;單檔 `isSidechain Counter({True: 62})`、`sessionId set {'26a6b57a-9efc-4073-b845-c27e42a2fbb1'}`(=主 session id)、`keys` 含 `agentId`

severity: blocker

blocking: 是

### f9 ⚠ SubagentStop 拿到哪一份逐字稿沒寫死,給錯就是整類推送恆 any=false

主逐字稿與子代理逐字稿內容不相交:子代理的工具呼叫只存在 `subagents/agent-*.jsonl`,主逐字稿一行都沒有(r1 掃 4476 行 isSidechain 全 False 就是這個原因)。tally 若拿到主逐字稿去對子代理的推送,那 42 次全部記成推了沒碰;拿到子代理逐字稿去對主 session 的推送同理。判不準的是 Claude Code 實際傳哪一份——spec 只寫「payload 拿 transcript_path」,沒寫它可能是哪一種,而兩種錯法產生的帳長得跟「鏡頭沒被用」一模一樣。

引句:「payload 拿 `session_id`+`transcript_path`,subprocess `lumos lens tally --session <id> --transcript <path>`」

指令+輸出:主逐字稿 `isSidechain Counter({False: 3195, None: 1440})`(無 True);子代理檔獨立存在且 62/62 行 isSidechain=True

severity: major

blocking: 是

### f10 登進 gov 第八源,等於把「不印給模型」那條自己拆掉

`lumos gov` 是把各源事件逐行印到 stdout 的指令,而模型自己在跑它——全機逐字稿有 130 次 Bash 呼叫帶 `lumos gov`(含 `--stats`、`--nags`)。lens-push / lens-tally 一旦登成第八源,受測者隨時可以看到自己這兩週的推送數與 any 分佈,Hawthorne 那條緩解只擋住了 Stop hook 那個出口。

引句:「登進 `lumos gov` 第八源(`kind` 慣例)」

指令+輸出:`python3 scripts/lumos gov | head -30` → 逐行印各源事件(`[L2/bypassed/軟]`、`[canary/caught/軟]`、`[anchor-approve/approved/軟]` …);逐字稿統計 `bash calls invoking lumos gov: 130`

severity: major

blocking: 是

### f13 逐字稿不是嚴格時序,收集器要先講清楚只認哪幾種行

### f14 ⚠ TTL 那句只是承認,而冷卻鍵跟子代理共用會把推送壓掉

誠實界線寫了「第 2 回合起同檔多半 N=0」,但沒有處置、也沒有回頭條件,依家規這種承認要附重驗時機。更實際的是 TTL 鍵是 session+檔,而子代理的 sessionId 就是主 session 的 id(f8 實測),單一 session 開 71 個子代理是常態——並行子代理與主 session 會互相把對方的推送壓成 incidents-only 或壓掉。判不準的是 PreToolUse payload 給子代理的 `session_id` 是否等於逐字稿裡那個,這一步我沒有辦法在不改設定的情況下實測。

引句:「TTL 窗內只推事故子集(mode 記著,分開報);冷卻窗跨回合,第 2 回合起同檔多半 N=0」

指令+輸出:`ls <session>/subagents/*.jsonl | wc -l` → 單一 session 71 份子代理逐字稿;子代理逐字稿 `sessionId` = 主 session id

severity: major
