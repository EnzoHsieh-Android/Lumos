### f1 SubagentStop 的 `transcript_path` 是主 session 的逐字稿,不是子代理那份

照 spec 字面,tally hook 在 SubagentStop 拿 `transcript_path` 去掃,掃到的是主 session 檔案,子代理自己的動作全在另一份檔裡,於是每一筆子代理推送算出來的 `any` 恆為 False。2.1.259 的 payload schema 明白分成兩個欄位:基底的 `transcript_path` 與 SubagentStop 專屬的 `agent_transcript_path`。修法:SubagentStop 分支必須改讀 `agent_transcript_path`。

severity: blocker

blocking: 是

引句:「payload 拿 `session_id`+`transcript_path`,subprocess `lumos lens tally --session <id> --transcript <path>`」

指令+輸出:`LC_ALL=C grep -a -o 'hook_event_name:x("SubagentStop").\{0,300\}' /Users/enzo/.local/share/claude/versions/2.1.259` →
`hook_event_name:x("SubagentStop"),stop_hook_active:M(),agent_id:i(),agent_transcript_path:i(),agent_type:i(),last_assistant_message:i().optional()…`;基底 `Ae()` = `session_id:i(),transcript_path:i(),cwd:i(),prompt_id:i().optional()…`

severity: blocker

### f3 壓縮(compaction)會把「最後一則 user 訊息」推到回合中間,該回合的推送被整筆丟掉

自動壓縮會在回合中途插一行 `type:"user"`、`message.content` 是字串、`isCompactSummary:true` 的紀錄,它符合既有 `_is_real_user_input` 的判定,所以「最後一則 user 訊息之後」的窗口從壓縮點起算。壓縮之前發生的那次推送 ts 落在窗外 → tally 選不到它 → 這筆推送永遠不會有對應的 lens-tally 事件,重算腳本的分佈裡它憑空消失(不是 any=False,是不見)。payload 已有現成的正確切點 `prompt_id`(schema 描述:同一則 user prompt 到下一則之間的所有事件共用),spec 沒用。

severity: major

blocking: 是

引句:「讀該 session 的 lens-push 事件(本回合=最後一則 user 訊息之後)」

file: `~/.claude/projects/-Users-enzo-harness-lumos-toolchain/26a6b57a-9efc-4073-b845-c27e42a2fbb1.jsonl:2994`(該行 `"type":"user","isCompactSummary":true`,content 為字串 `This session is being continued from a previous conversation…`;前一行 2993 為 `"subtype":"compact_boundary"`,`trigger:"auto"`)。判定函式:`scripts/hooks/claude/check-graph-sync.py:86-104`

### f5 TTL 標記在「還不知道會不會注入」之前就寫下去,而且主/子代理共用同一個窗

`_ttl_should_inject` 是在呼叫 lumos 之前判定並寫標記的,所以一次完全沒注入的 Edit(實測 `governance/autonomous_loop/run_ledger.py` pins=0/free=0/lane=0,不注入)照樣開啟該檔 20 分鐘冷卻窗,窗內同檔改走 incidents-only,而 incidents-only 路徑把 direct/BFS/lane/stack_questions 全跳過,沒事故的檔就是零注入、零推送。標記鍵是 session+檔,而子代理與主 session 共用同一個 session_id,所以子代理的一次 Edit 會吃掉主 session 對同檔的推送。結論:推送次數系統性低於 Edit 次數,而 spec 的分岔規則直接拿這個數字當「樣本不存在 → 改題成 Bash 改檔路徑」的證據,會把 TTL 抑制誤讀成家規用 Bash。

severity: major

blocking: 是

引句:「主 session(非子代理)推送 <20 次或 session 數 <5 → ★樣本不存在,改題★」

file: `scripts/hooks/claude/impact-hook.py:127-172`(窗外分支先 `marker.write_text(str(now))` 再 return True)、`scripts/hooks/claude/impact-hook.py:460`(`in_cooldown` 在 subprocess 之前算)、`scripts/lumos:16133` 與 `16193`(`if not incidents_only:` 把自由席/lane/about 整段跳過)

### f8 家規指定的多詞查詢形式,照證據③一律算「沒碰」

### f11 帳檔被刪之後靜默從零重算,和「推送本來就很少」長得一模一樣

帳是 gitignored 單機檔,一次 `git clean -xfd` 或手動清理就會消失;既有 append helper 用 `open(path, "a")`,下次寫入自動建新檔、不報錯,計數從 0 重來。兩週後 REVISIT 讀到的低計數無從分辨是「真的很少推」還是「帳被刪過」,而這正是 spec 唯一的分岔點,建議在帳裡放一行開帳事件(首次寫入時記 `ts`)讓重算腳本能算出實際觀測天數。

severity: minor

引句:「帳是單機 gitignored;多機不合併(量測用,不是治理紀錄)」

### f12 「行級原子(同 ci-log 慣例)」引到的那個 helper 不是 O_APPEND 單次 write

ci-log 走的是 `_jsonl_append_verified` 的 buffered `open(path,"a")`+`f.write`,不是同檔另一支明文保證原子的 `_ledger_append`(O_APPEND fd + 單次 `os.write`,並拒 >4KB)。本案的併發是真的(主 session 與多個子代理共用 session_id、同時寫同一份帳),實測事件約 300–600 位元組、遠小於緩衝區,實務上不會撕裂,但 spec 的理由句引錯了先例。修法:寫帳直接走 `_ledger_append` 那條路,或把理由改成「事件小於一次 write 的大小」。

severity: minor

blocking: 否

引句:「單行 append 行級原子(同 ci-log 慣例)」

file: `scripts/lumos:9263-9279`(`_ledger_append`,O_APPEND+os.write+短寫檢查)vs `scripts/lumos:4344-4355`(ci-log 實際走的路)
