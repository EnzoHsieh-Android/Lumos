# enforcement可觀測性_計劃 r1 — 架構對齊席(不佔人數)

severity: blocker

裁的是一件事:這份 spec 的做法,跟這個 repo 既有的做法一不一樣。六題逐項判,每項都指名對照組。

---

## 1. 新事件的寫入路徑(S1)

判:**major**,blocking:是
對照組:`scripts/lumos` 的 `_append_governance_log`、`_codeloop_gov_log`;`docs/lumos-toolchain-knowledge/Projects/每日治理wrapper活著沒_計劃.md`

既有寫入點的形狀是一致的:一個**做實質檢查工作**的子命令(`doctor --ci`、`anchor approve`、`code-loop pass/skip/check`),把「要不要記一筆」當成自己邏輯裡的副作用來決定,寫者的身分是「正在做那件事的子命令本身」,不是「hook 另外呼叫一個專門用來記帳的端點」。

對照(引自其他檔,非被審材料):「寫者=doctor --ci + anchor approve:把 gate findings append 到 docs/.governance-log.jsonl。」
對照(引自其他檔,非被審材料):「把 code-loop 事件 append 到 docs/.governance-log.jsonl(同 bypass-log 哲學)。」
S1 講的是「每個 exit 1 前寫一筆」——pre-push/pre-commit 裡至少四處 exit 1(簽名檔未提交、mktemp 建不出暫存檔、`test_autonomous_loop.py` 紅、`test_lumos.py` 紅)**現在完全沒有對應的 lumos 子命令**,純粹是 bash 判斷後直接印訊息、`exit 1`。對這幾處,S1 等於要**新開一個「hook 主動要求 lumos 記一筆」的端點**——這個形狀在這個 repo 從未存在過,而且**已經被試過一次、失敗了**:

對照(引自其他檔,非被審材料):「我寫了一個不存在的指令:`lumos gov-event`。查了才發現沒這支,而且新開子命令要付」
對照(引自其他檔,非被審材料):「設計裡「看門狗寫一筆治理帳」那句落不了地——」
對照(引自其他檔,非被審材料):「工具沒有給外部腳本寫治理帳的入口。」
那個案子最後**沒有**開新子命令,而是拆成兩條路:看門狗自己留即時紀錄(不進治理帳)、既有健檢的軟提醒段落落治理帳(用既有的 `gov_events.append` 通道,不是新開端點)。S1 對這個剛發生過的失敗前例隻字未提,也沒說要開一個新端點還是把邏輯掛進既有子命令。

why: 這不是「風格偏好」,是「這個 repo 已經試過一次『開一個薄的記帳端點給 hook 呼叫』,而且明確失敗、換了設計」——S1 現在要重走同一條路,卻沒有回應那次失敗學到的東西。同一批四處無子命令可掛的 exit 1,若真要記帳,該先問「能不能掛進既有子命令(比照 code-loop pass/skip 那樣,由做事的那支子命令決定要不要記),還是要接受某幾處就是不記」,而不是預設「開一個新端點」。

## 2. 新開子命令的稅

判:**minor**,blocking:否(與第 1 項同案,待第 1 項的寫入路徑定案後一併算)
對照組:`docs/lumos-toolchain-knowledge/Projects/enforcement儀表板_計劃.md`、`docs/lumos-toolchain-knowledge/Projects/Codex行為精修_計劃.md`、`scripts/test_lumos.py::t_docs_command_count`

spec 自己只寫一句:

引句:「新開子命令要付的稅要算進來:五份文件 + 指令索引的同步(既有守衛會擋)。」

這句話低估了實際的稅。機械守衛 `t_docs_command_count` 不是比對「五份固定檔案」,是**動態掃全部活文件**(排除外審歸檔/圖譜/review-reports 等歷史快照)找「N 個頂層命令」字樣,逐一核對——上一次真的開一個頂層指令時,實測是:

對照(引自其他檔,非被審材料):「新指令觸發 8 條同步守衛翻紅——指令索引(commands/04)補 enforcement 行、五份文件命令數 64→65」
而且這個 repo 剛好有一個「開新指令 vs. 掛進既有東西」的正面對照,同一批工作量級(遠小於這批):

對照(引自其他檔,非被審材料):「開一個指令要同步五份文件與索引,成本大於 40 行」
那次的裁定是**不**開新子命令,把邏輯留在既有 hook 裡。spec 沒有討論「既有的 `gov`、`code-loop`、`canary record` 能不能收」這個問題,也沒有引用這兩個近在眼前的先例——這件事本身該在 spec 裡出現,不該由審查席翻出來。

why: 獨立列出來是因為它跟第 1 項的裁決方向相關但不完全重疊——就算第 1 項最後決定「掛進既有子命令、不開新的」,這條「稅算太輕」的觀察仍然成立,該在 spec 裡補一句量出真實範圍(掃全部活文件,不是五份)。不擋,因為它不是「引入第二種做法」,是「成本估計不夠準」。

## 3. `~/.cache/lumos` 這個位置

判:**blocker**,blocking:是
對照組:`docs/lumos-toolchain-knowledge/Projects/每日治理wrapper活著沒_計劃.md`(2026-09-07,同一個「架構對齊席」角色親自裁過的案子)、`scripts/fetch-notesmd.sh`、`.gitignore`、`governance/.notifier/`

這題最重,而且答案已經在這個 repo 裡寫死了——**就在昨天**。同一個審查席角色,審的是同類問題(「產生物該放哪裡」),裁定是:

對照(引自其他檔,非被審材料):「這個 repo 的慣例是**放 repo 樹內、用 `.gitignore` 蓋掉**」
對照(引自其他檔,非被審材料):「會碰家目錄的只有 OS 逼你放那裡的 plist,和安裝器做 symlink / 改設定檔。」
具體例子:`scripts/fetch-notesmd.sh` 下載的二進位放 `scripts/bin/`(`.gitignore` 蓋)、`dist/` 同款、每日治理 wrapper 自己的執行期狀態最後也搬進了 `governance/.notifier/`(`.gitignore` 蓋),不是放使用者家目錄。

spec 選 `~/.cache/lumos` 的理由是:

引句:「寫到 `~/.cache/lumos`:★私有目錄、不進 git、**不是治理帳**★」

這個理由答的是「這筆資料算不算治理帳」(一個分類問題),不是「這個檔案該放在磁碟的哪裡」(一個位置問題)。「不是治理帳」不需要放家目錄才能成立——`governance/.notifier/` 底下的狀態檔一樣不進 git、一樣不是治理帳,照樣放在 repo 樹內被 `.gitignore` 蓋掉。用「避免撞到某條裁定」去正當化一個跟那條裁定完全無關的位置選擇,是套錯了理由。

正確的位置應該是 repo 樹內某處(例如 `governance/.hook-telemetry/` 之類,五支 hook 各寫一行 jsonl 到那裡),`.gitignore` 蓋掉,跟 `.notifier/`、`code-loop/`、`.daily-governance-health.json` 同一個家族。

why: 這是唯一一題真正符合「引入專案原本沒有的第二種做法」的硬判準——repo 對這一類「per-machine 產生物放哪裡」已經有明確、剛審過、剛執行過的立場,spec 選了另一個位置,而且给的理由沒有觸及位置本身。升到 blocker 是因為這不是「沒查過」的失誤,是**同一個問題在同一個 repo 裡,一天之內被同一個審查角色裁過一次**——這批如果照原樣做,等於把已經改正的錯誤原地重犯一次。

## 4. 第二種做法(`LUMOS_SKIP`)

判:**major**,blocking:是
對照組:`scripts/lumos` 的 `LUMOS_SKIP_BOUND_TESTS`(`_bound_tests_check`)、`LUMOS_STOP_BLOCK_OFF`(`scripts/hooks/claude/check-graph-sync.py`)、`LUMOS_ENTRY_HOOK_OFF`(`scripts/hooks/claude/lumos-entry-hook.py`)

這個 repo**已經有**「用環境變數改變閘行為,而且要分開記錄」的機制,不是要引入的第一個:

對照(引自其他檔,非被審材料):「★旗標跳過與環境變數跳過要分開記★(設計 [S6])」
`_bound_tests_check` 裡對這件事的實作是:`skip`(旗標,人手動決定)跟 `LUMOS_SKIP_BOUND_TESTS=1`(環境變數,多半是 CI 常態設定)分別記成 `skipped-flag` / `skipped-env` 兩種 kind,而且真的呼叫 `_bound_tests_log(...)` 落帳。命名形狀是**一個閘一個布林環境變數**:`LUMOS_SKIP_<GATE_NAME>=1`,同一家族還有 `LUMOS_STOP_BLOCK_OFF=1`、`LUMOS_ENTRY_HOOK_OFF=1`。

spec 的 S3:

引句:「`LUMOS_SKIP=<gate-id>` 細粒度跳閘」

這是**另一個形狀**:單一個環境變數、用值選擇要跳哪一道閘。概念上兩者做同一件事(跳過一道閘、留一筆帳),但命名與語意都不一樣——一個是「布林 × N 個變數名」,一個是「一個變數 × 值域」。spec 完全沒提到 `LUMOS_SKIP_BOUND_TESTS` 已經存在,也沒有說要不要把它併進新方案(例如新方案上線後 `LUMOS_SKIP_BOUND_TESTS=1` 該不該继续吃、還是改成 `LUMOS_SKIP=test-layers` 之類)。

why: 這正是本題單獨點名要查的東西——「如果已經有一套,新的這個跟它一不一致」。答案是不一致,而且 spec 沒有意識到已經有一套。要嘛沿用既有形狀(每道可跳的閘各自一個 `LUMOS_SKIP_<GATE>=1`,四道閘就四個變數名,跟 `LUMOS_SKIP_BOUND_TESTS` 同款),要嘛在 spec 裡明講「這次要把散落的單閘變數統一收成一個泛型變數,`LUMOS_SKIP_BOUND_TESTS` 之後怎麼處理」——現在兩種都沒說,是漏了一個既有機制。

## 5. `enforcement` 的欄位擴充(S4 近 7 天欄)

判:**minor**,blocking:否
對照組:`cmd_gov` / `_render_gov_stats`(`lumos gov --stats`)、`enforcement_status` docstring

`enforcement_status` 裡每一列的資料來源都是**當下讀一次**:讀 `~/.claude/settings.json`、跑 `git config core.hooksPath`、比對檔案是否存在/可執行、比對版本戳——沒有一列是「過去 N 天累積了幾次」這種時間序資料。docstring 自己講得很清楚:

對照(引自其他檔,非被審材料):「純唯讀、每層各自 try 包住(一層測不出來不拖垮整份;fail-open 本身要能被觀測)。」
而這個 repo**已經有**專門呈現「治理事件時間軸/彙整統計」的地方,跟「當下狀態」的視圖是分開的:

對照(引自其他檔,非被審材料):「唯讀彙整六帳(bypass/governance/canary/kill/signoff/ci;rot-queue 2026-08-22 拆出)→ 治理事件時間軸。」
`_render_gov_stats` 就是幹這件事的函式(`lumos gov --stats`)。S4 要加的「近 7 天跑 N 次/注入 N/超時 N」是同一種性質的資料(時間序統計),spec 卻打算塞進 `lumos enforcement` 那張「現在有沒有裝上」的表裡,跟既有「當下狀態視圖 vs. 彙整統計視圖分開呈現」的先例不一致。

why: 不到 major,因為這不是「引入一個原本沒有的機制」——聚合統計的機制(`gov --stats`)已經存在,只是 spec 選錯了呈現的容器。建議:近 7 天統計走 `gov --stats`(或新開一個同語意的 `--recent` 旗標),`enforcement` 的表繼續只答「現在有沒有生效」;真要留在同一個指令底下,至少要在輸出裡明顯分兩段,不要混進同一批列。不擋是因為這是呈現層的選擇,不影響資料本身怎麼收集,晚一點調整不傷筋動骨。

## 6. S5 那個修法(`core.hooksPath` 比對)

判:**minor**,blocking:否
對照組:`_deinit_unbar_gate`(`scripts/lumos`)

現在 `enforcement_status` 裡犯錯的那行是:

對照(引自其他檔,非被審材料):「ok = hp == "scripts/hooks" and f.is_file() and os.access(str(f), os.X_OK)」
字面字串比對,這就是 spec 描述的那個 bug。但**同一支檔案裡已經有一份寫對的版本**,`_deinit_unbar_gate` 為了同一件事（判斷 `core.hooksPath` 是不是指向 lumos 自己的 `scripts/hooks`）寫過:

對照(引自其他檔,非被審材料):「same = vp.resolve() == ours.resolve()」
而且它連「resolve 失敗時退回字串比對」的備援都寫了(`except Exception: same = str(vp) == str(ours)`),絕對/相對路徑都吃。spec 講「要用路徑解析後比對」是對的方向,但沒有提到這支既有函式——如果各自重寫一份 resolve 邏輯,等於同一件事在這支檔案裡出現兩份獨立實作,兩份日後各自演化、彼此不知道對方存在,是重複而非共用。

why: 不到 major,因為 spec 提的解法(resolve 後比對)跟既有解法方向一致,不是引入新形狀,只是沒有指名可以直接抽出來共用的既有實作。建議實作時把 `_deinit_unbar_gate` 裡那段判斷邏輯抽成一個小共用函式(例如 `_hooks_path_matches(root)`),兩處一起呼叫,而不是各寫一份。

## 小結

六項裡,**#3(`~/.cache/lumos` 放家目錄)是本輪最重的一條**——這個 repo 昨天才由同一個審查角色裁過同類問題,裁定寫得很清楚(放 repo 樹內、`.gitignore` 蓋掉),這批 spec 對同一類產生物選了另一個位置。**#1(S1 寫入路徑)跟 #4(`LUMOS_SKIP` 命名)也都是「已經有一套,新方案沒對齊」**的真第二種做法。#2 是稅算太輕(跟 #1 同案)、#5/#6 是呈現層/重複實作的小事,不擋。
