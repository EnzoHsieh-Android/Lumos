## F1(對應第4點)★S3 的 `LUMOS_SKIP=code-loop` 字面實作,會連帶讓「不可跳的三道」之一失效★

spec 把「代碼審留痕(code-loop)」列進可跳四道,但把「合約測試閘」列進不可跳三道,理由是:

引句:「不可跳的三道**:錨點(它是「裁判有沒有被換掉」那一層)、合約測試閘(它是人裁 2026-09-07 才剛硬化的)」
我讀了 `scripts/lumos` 裡 `_codeloop_guard_verdict`(即 `lumos code-loop check` 的實作,pre-push 第 196 行高風險路徑唯一呼叫點)——它內部第「2.5」步就是先真跑合約測試閘(`_bound_tests_check`),**不分 tier、紅就直接回 `blocked: True`**,然後才往下算 tier、查 pass/skip 留痕。也就是說,pre-push 對高風險推送**從來沒有獨立呼叫過合約測試閘**——它整個被包在 `code-loop check` 這一次呼叫裡面。

照 S1 定的「hook 維持薄殼」原則,`LUMOS_SKIP=code-loop` 最自然、最省事的實作就是「不呼叫 `lumos code-loop check`」——這樣做,會把内嵌在同一次呼叫裡的合約測試閘**一起**跳掉,而它是 spec 自己剛剛才寫明「不可跳」的那一道。

更糟的是 CI 那邊沒有第二道防線:`.github/workflows/ci.yml` 的 code-loop gate 步驟本身就設了 `LUMOS_SKIP_BOUND_TESTS: "1"`(理由是「CI 已跑全套當後盾,不重跑」)。合約測試閘裡「這個合約沒有任何測試綁定(no-pins)」這類**覆蓋率缺口**,不是全套測試能查出來的東西(全套測試只驗證「現有測試通過」,驗不出「該有測試卻沒有」)。所以一旦本機用 `LUMOS_SKIP=code-loop` 跳過,「合約沒測試」這件事在本機和 CI 都不會被任何機制抓到——兩層跳閘疊在一起,產生一個 spec 明講不該存在的洞。

- severity: blocker
- blocking: 是
- 建議:`LUMOS_SKIP=code-loop` 不能實作成「跳過整支 `code-loop check` 呼叫」,必須拆成只跳「pass/skip 留痕要求」那一步,合約測試閘的呼叫要獨立於這個環境變數之外、永遠執行。

## F2(對應第4點)可跳四道裡,pitfalls 與 code-loop 的 CI backstop 只在 push 事件成立,pull_request 事件完全沒查

引句:「★這個切法本身是設計決定,要給審查席看★:判準是「跳掉之後 CI 還兜得住嗎」。」
實跑對照 `.github/workflows/ci.yml`:doctor(`Graph doctor (strict)`)、anchor verify、全套測試三支都沒有 `if:` 限制,push 和 pull_request 都會跑——這三道判準成立。但「code-loop gate」步驟(唯一重算 pitfalls tier、也是唯一查 code-loop 留痕的地方)寫著 `if: github.event_name == 'push'`——pull_request 事件完全不執行這步。也就是說,可跳四道裡的「風險分級(pitfalls)」與「代碼審留痕(code-loop)」,CI 只在**直接推到 main**時才兜得住,若走 PR 流程(開 PR、CI 跑 pull_request 事件、審查者看綠燈核准),這兩道在 merge 前完全沒有 CI 訊號。

實測本 repo 目前:`gh api repos/:owner/:repo/branches/main/protection` 回 404「Branch not protected」,`gh pr list --state all` 空——目前是純直推 main、沒有分支保護、沒有 PR,所以這個缺口暫時不會被踩到(merge 到 main 那一刻的 push 事件終究會補查)。但 spec 的判準是寫成一般性原則,沒有把「僅在直推工作流下成立」這個前提寫進去——如果哪天這個 repo(或抄這個設計模式去 vendor 的消費專案)改用 PR + branch protection,這個判準就會安靜地失效。

- severity: major
- blocking: 否(目前實際工作流下風險低,但判準本身站不住,建議 spec 把這個前提明寫成假設並附回頭條件)

## F4(對應第2點)「hook 跑了但失敗」——spec 沒定義「跑」是記在進入點還是完成點
