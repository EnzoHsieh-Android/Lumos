# enforcement可觀測性_計劃

> 全 repo 審視 #19(編號 F21、F95、F25、F30;工量 M)。
> ★這是 [[Projects/enforcement儀表板_計劃]] 的續案,不是重開★:那一批做的是
> 「有沒有裝上/接上」的唯讀匯總,這一批要把判準從**生效=有註冊**升格成
> **生效=最近真的跑過**,並且把「擋了誰、放行了誰、被跳了幾次」變成帳上查得到的東西。

## 為什麼(每一條都是我自己量過的,不是抄清單)

### 一、治理帳 29,348 筆,★hard=true 一筆都沒有★

實測(2026-09-08):

| 量的東西 | 數字 |
|---|---|
| 治理帳總筆數 | 29,348 |
| `hard=true` | **0** |
| `kind=blocked` | **0** |
| `kind=warned` | 27,795(94.7%) |

不是沒人寫這個欄位,是**會寫 `hard=true` 的那幾處從來沒觸發過**
(前掃機械數過:碼裡直接寫 `"hard": True` 的只有 **3 處寫入點,分屬 2 個閘**
——可逆性檢查 check-r 兩處、check-j 一處。原本寫「三道」是不精確的)。
真正的缺口在別的地方:**hook 層那些 `exit 1` 擋下人的時候,一筆帳都不寫。**
機械數過:`scripts/hooks/pre-push` 有 7 處 `exit 1`、`scripts/hooks/pre-commit` 有 3 處。
它們擋掉一次推送,治理帳上完全看不出來。

而 README 對外宣稱「每道關卡攔了誰、硬擋還是提醒」都在帳上——**那句話目前不成立。**

### 二、★儀表板現在對它最重要的兩列講錯話,而且已經錯了不知道多久★

`lumos enforcement` 在這台機器上把 `git-pre-commit` 與 `git-pre-push` 都印成 **inactive**
——而那兩道閘今天擋過我兩次、每次推送都在跑全套測試。

根因是一行字串比對:

- `core.hooksPath` 這台機器上的值:`/Users/enzo/harness/lumos-toolchain/scripts/hooks`(絕對路徑)
- 碼裡比的是字面字串:`scripts/hooks`(相對路徑)
- 相等嗎:**否** → 判 inactive

★方向是「該說有卻說沒有」★:表面上是安全方向(不會假綠),但實際後果更糟——
**那兩列長期是紅的,所以真的哪天 hook 掉了,那個紅沒有任何訊號價值。**
這就是「狼來了」,而且是儀表板自己喊的。

★這一條本身就證明了這批要做的事★:一個只驗「有沒有註冊」的判準,
連「註冊成什麼樣子」都會判錯;而**只要沒有人真的去看「它最近有沒有跑過」,錯了也不會有人知道**。

### 三、五支 Claude hook 的成功/超時/失敗,只有開 debug 才看得到

`scripts/hooks/claude/` 底下五支(進場、波及提醒、收工圖譜同步、CI 狀態、派工鏡頭注入)。
要知道它們最近有沒有跑、跑了幾次、超時幾次,現在唯一的辦法是去 grep 逐字稿。
而 `lumos enforcement` 對它們只驗「有沒有註冊在設定檔裡」。

### 四、逃生口是全有全無的

`--no-verify` 一按,連 1 秒的錨點檢查與健檢都一起跳掉——通常是為了省 8 分鐘的全套測試。
`docs/.bypass-log.jsonl` 目前有 67 筆,但它記的是**提交層**的繞過,
而且記完之後沒有任何地方在問「哪一道閘最常被跳」。

## 做什麼(四件一批)

### [S1] 每個 exit 1 前寫一筆 `kind=blocked / hard=true` 的帳

- **邏輯進 lumos 子命令,hook 維持薄殼**——這是 2026-09-03 r3 的既有裁定,
  ★不得在 hook 裡塞 `python - <<'PY'` 小段★。
- 新開子命令要付的稅要算進來:五份文件 + 指令索引的同步(既有守衛會擋)。
- 每一筆要帶:哪一道閘(`gate`)、擋的是什麼(`note`)、`hard=true`、當下的 commit。

### [S2] pre-push 記整支耗時與五條 fail-open

現在 fail-open 的地方有明文註解(缺 lumos/python3 降級放行、空樹算不出來放行、
pitfalls 自己出錯放行…),但**放行的事實沒有落帳**。
要記的是「這一次放行了,原因是 X」——fail-open 可以,但每次 fail-open 都要留一筆可查的紀錄。

### [S3] `LUMOS_SKIP=<gate-id>` 細粒度跳閘

- 被跳的閘記 `kind=skipped` 與理由,**這樣才量得出哪一道最常被跳**。
- ★錨點檢查刻意不可跳★(它是「裁判有沒有被換掉」那一層)。
- 擋下時的訊息把「第三條路」從 `--no-verify` 改成 `LUMOS_SKIP`。
- ★範圍刀:只收窄在源 repo 的 pre-push★,而且**要明寫是哪幾道**——前掃指出原本只寫「四道閘」
  卻沒說是哪四道,而 pre-push 的註解列的是七道。**這批可跳的是這四道**:
  健檢(doctor)、風險分級(pitfalls)、代碼審留痕(code-loop)、測試層次(test-layers)。
  **不可跳的三道**:錨點(它是「裁判有沒有被換掉」那一層)、
  合約測試閘(它是人裁 2026-09-07 才剛硬化的)、全套測試(跳它就等於沒跑)。
  ★這個切法本身是設計決定,要給審查席看★:判準是「跳掉之後 CI 還兜得住嗎」。
- **不重提**消費端 hook-local 覆寫與 rebase 偵測。
  ★這句話要講精確★(前掃抓到的不精確處):那條裁定的原文是
  「`.lumos/config.json` 的宣告式開關已經是使用者親裁的正規出口」,
  而**實際被實作出來的宣告式開關只有 `ci` 區塊那一種**;
  `hook-local` 覆寫與 rebase 偵測**從來沒有建過**(查:碼裡與檔案系統都找不到)。
  所以正確的意思是「這種設計模式已經被裁定夠用,不必再建」,
  不是「現在已經有一個管 hook-local/rebase 的開關」。

### [S4] 五支 Claude hook 各寫一行 jsonl,enforcement 多一欄「近 7 天」

- 寫到 `~/.cache/lumos`:★私有目錄、不進 git、**不是治理帳**★
  ——這點一定要寫清楚,才不會撞到派工鏡頭那案 d1「不記治理帳、不量成效」的裁定。
- `enforcement` 多一欄:近 7 天跑 N 次 / 注入 N / 超時 N。
- 判準從「生效=有註冊」升格成「**生效=最近真的跑過**」。

### [S5] 順手修上面第二條那個字串比對(不是新功能,是現行錯誤)

`core.hooksPath` 要用**路徑解析後比對**,不是字串相等。
守衛要同時蓋住兩種寫法(相對與絕對),而且要有一個「hook 真的不在時會翻紅」的反向對照。

## 實務隱患

- **帳本膨脹**:治理帳已經 29,348 筆,其中 94.7% 是 `warned`。
  再加 blocked/skipped/fail-open 三種事件,要先想清楚**誰在讀**——
  沒有消費者的帳只是更大的垃圾場。**每一種新事件都要指名一個讀它的地方**(例如 `gov --stats` 的哪一段)。
- **`LUMOS_SKIP` 會不會變成更好用的 `--no-verify`**:設計目的是「量得出哪道閘最常被跳」,
  但如果它比 `--no-verify` 好打,人會更常跳閘。要在擋下訊息裡明講「這會留一筆帳」,
  而且 `gov` 要有一段把跳閘次數印出來——★沒有人看的留痕等於沒有留痕★。
- **`~/.cache/lumos` 的清理與競態**:五支 hook 可能同時寫;要 append-only、
  單行原子寫入,而且要有上限(不能無限長)。這個 repo 對共用檔的既有教訓是原子寫入。
- **hook 變慢**:每支 hook 多一次寫檔。hook 有逾時預算(見 [[Systems/hook逾時預算]]),
  要量新增的耗時,不能只用「應該很快」帶過。
- **★驗證方法本身的陷阱★**:這一整批的主題是「怎麼知道它真的生效」,
  而最容易掉的洞就是**問它、它說有,就當成有**。
  同工作區另一個 session 2026-09-08 實測過一個同型的坑:叫審查席自報模型代號,它會答錯。
  **所以這批的每一條驗收都要用反證**:把那道閘弄壞(或把 hook 拿掉),看儀表板會不會翻紅
  ——只驗「它說 active」不算驗過。
- **不涵蓋什麼**:不做消費端 hook-local 覆寫、不做 rebase 偵測、
  不改 `--no-verify` 本身(它是 git 的東西,擋不掉),只是把建議的出口換掉。

PRIOR-ART: 最小解在既有 jsonl 帳本多幾筆事件加一個環境變數。世界解四個(★都當場一句話解釋★,
前掃指出這幾個外部名詞原本沒展開):

- **OPA 的 decision logs**:OPA 是一套「把准入判斷抽出來獨立跑」的開源政策引擎,
  它每做一次准入判斷就落一筆結構化紀錄——**判斷本身就是要被記錄的事件**,這正是這批缺的那一半。
- **K8s 的 `failurePolicy=Ignore` 必配 audit**:Kubernetes 的准入檢查允許「檢查掛掉就放行」,
  但那個放行一定會進稽核日誌。**跟我們的 fail-open 同型,差別在他們規定放行也要留痕。**
- **pre-commit framework 的 `SKIP=<hook>`**:那是一套第三方的 git hook 管理工具
  (★跟本 repo 自己的 `scripts/hooks/pre-commit` 撞名,不是同一個東西★),
  它用環境變數逐道跳閘,而不是全有全無地關掉整層——就是 [S3] 要抄的形狀。
- **OpenTelemetry 的 logs 資料模型**:一套跨語言的可觀測性標準,
  它對「一筆事件該有哪些欄位」有共同約定,可以拿來對照我們治理帳的欄位夠不夠。
