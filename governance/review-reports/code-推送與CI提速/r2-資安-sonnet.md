## 四類逐項

1. **不可信輸入流到危險操作:已看,無。**
   - 耗時表只影響 `_shard_by_duration` 的權重。函式對傳入的每個 `names` 都排序並指派給恰好一份,所以聯集永遠等於全部。
   - 表裡多出來的鍵會被忽略。缺的鍵用中位數補。
   - NaN、Infinity、負數、布林、超大整數在載入時被 `_duration_ok` 擋掉,擋下時每份都 rc2。
   - 極大但合法的值(例如 1e308)會讓權重加總溢位成 inf。排序和 `min(..., (loads, counts, j))` 仍是決定性的,所以各份照樣一致,測試不會被漏掉。
   - 結尾重讀比對:各份是同一個提交的獨立 checkout,讀到同一個檔。要讓開頭和結尾雜湊一樣、分法卻不同,必須在跑的當下改寫檔案,這需要在 runner 內執行任意程式,而 PR 本來就能改 runner 和測試。所以沒有新增的權限。
   - 雜湊只取 8 碼(32 位元)。碰撞對這個流程沒有意義,因為雜湊只用來偵測同一份檔案在跑的期間有沒有被換掉,攻擊者要換內容必須先能執行程式。
   - `--shard` 的字串經過 `int()` 解析,不會帶 `/` 或 `..`。`.replace('/', 'of')` 組出的 run 檔名因此不能跳出 `.lumos/`。
   - PR 能改耗時表,最多讓分片不平均、逾時或 rc2。這屬於 DoS,依指示不報。
2. **CI:已看,無。**
   - 群組鍵 `ci-${{ github.event_name }}-${{ pull_request.number || github.sha }}` 只含事件名、整數和 sha,沒有分支名或標題等攻擊者可控字串,所以沒有注入面。
   - `cancel-in-progress` 只對 pull_request 為真。外部人無法取消 main 的 run,也無法取消別人 PR 的 run。
   - 子殼層 `( set +e; ...; rc=$?; ...; exit $rc )` 保留了 python 的離開碼。外層 `wait "$job" || rc=1` 照舊,所以沒有吞離開碼的路徑。
   - `$i` 和 `$SHARD_TOTAL` 來自 workflow 的 matrix 和環境變數,不是 PR 可控。
3. **執行邊界:已看,無。**
   - 刷新用的 glob 刪檔是 `Path.unlink()`。遇到符號連結只刪連結本身,不會刪到目標。
   - 對 `.lumos/` 底下的符號連結,`read_bytes` 會跟隨連結。但 run 檔是 gitignored 的本機檔,而且只有 tests 字典裡數值合法的項目會被合進表,洩漏面可以忽略。
   - 耗時表走 `_write_lf`:先用 `O_EXCL` 建唯一暫存名,再 `os.replace`。符號連結會被換成一般檔,不會跟著寫到目標。硬連結只換掉自己這個名字。測試也用固定名的符號連結 `.lumos-tmp` 驗過。
   - 執行器寫 run 檔用固定暫存名 `.lumos-tmp` 加 `write_text`,這個寫法沿用既有的 `test-cache` 失敗快取。要利用它,得先在 `.lumos/` 放一個符號連結,例如 PR 用 `git add -f` 強制加入。這要求受害者在本機跑 PR 的 runner,而跑 PR 的 runner 本來就等於執行 PR 的程式,所以我判斷沒有新增權限,也不報。
   - 耗時表列進 `_BOOKKEEPING_FILES` 後,留痕有效性判斷用 `git diff --raw --no-renames -z`。我確認過,所以「把被審的程式檔改名成耗時表來藏刪除」這條路是關上的。
   - 簿記清單裡的個別檔不做模式檢查(符號連結、可執行位元)。這是既有行為,對 `.jsonl` 帳也一樣。耗時表內容只被當 JSON 解析,不會被執行,所以夾帶不到執行能力。
   - 只改耗時表會被判成文件改動、CI 只跑文件子集。耗時表不改測試選取,文件子集也同樣載入表並在壞表時 rc2,所以測試不會因此少跑。
4. **繞過面:已看,無。**
   - 沒有辦法借耗時表或分片讓推送前或 CI 的測試少跑而不被發現。
   - 分片先在穩定清單上切,表只決定切法。空片照舊 rc1(`--suite` 子集例外,維持原有行為)。
   - 結尾比對放在 `return 1 if FAIL else 0` 之前。前面的提早離開(如 `-k` 選中 0 個)本來就是非 0 或不分片。
