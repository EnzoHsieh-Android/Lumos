# 推送前一次列出全部擋下原因_計劃

> 白話:推送前的閘現在是「遇到第一道擋下就結束」,一次只看得到一個原因;修好、重推(每次掛鉤要跑幾分鐘)才看到下一道。改成:全套測試之前那些便宜的閘全部跑完、把擋下原因收集起來,跑到全套之前只要有任何一道擋下,就一次列出全部原因並結束(不跑全套)。另外加一個預演指令,不推送、不跑全套,只跑那些閘給你看結果。

## 緣起

- 2026-10-13 推 qo-frontmatter 那批時被依序擋了四次(新增告警、漂移檢查、回頭重讀、測試紅),每次修完重推才看到下一道;10-14 推示範回饋小修又被擋兩次(裁判簽名、新增告警)。出處是使用者 2026-10-14 的口述(問「這次有什麼 lumos 可以改進」時列為第一條);[[Verification/2026-10-13_後端示範交付]] 的改進候選當時沒收這一條,收工時補進去。
- 推送前掛鉤 `scripts/hooks/pre-push` 有十幾處擋下就 `exit 1`;`lumos code-loop check` 內部四道判定(合約測試、表態、新增告警、代碼審留痕)也是第一道沒過就停。2026-09-06 全 repo 審視 #12 只調了順序(便宜的先跑),沒做「一次列出全部」。

- 舊裁定:[[Projects/全repo審視_計劃]] #12 的 PRIOR-ART 全句是「裁定=borrow-design(fail_fast 不借——本 repo 已裁每道閘本來就 exit 1)」。那句的語境是不用另外借工具的遇錯就停開關,沒有評估過「一次列出全部」;F52 講的是測試第一支紅就停,是另一層。使用者 2026-10-14 聽完「推送前的閘一次只報一個原因」後明確要求修這一條——推翻該句;實作時在 #12 那段旁註記被本計劃取代。

PRIOR-ART: Git 生態最常用的 pre-commit 框架預設 `fail_fast: false`——每個 hook 都跑、最後一次列出全部失敗,要遇錯就停反而得另外打開;`make -k`(keep going)同理。借用這個預設,不自建新機制:掛鉤裡把「擋下就結束」改成「記下原因、繼續跑」,在全套測試之前統一判。
RETIRE-IF: 上線 8 週內,被擋的推送裡「一次列出兩個以上原因」的次數為 0(代表閘之間其實很少同時擋)——撤掉收集邏輯、回到遇錯就停。

## 做法

1. **掛鉤收集擋下原因**:掛鉤裡全套測試之前的每一道會擋的閘——裁判簽名(`anchor verify`)、簽名檔沒提交(`governance/anchor-baseline.json` 有未提交改動)、圖譜健檢(`doctor --ci`)、每支檔有家(`home check`)、筆記形狀(`note-shape`)、雙向門放行(`spec-gate --push-check`)、代碼審判定(`code-loop check`)、存量漂移(`drift check`)、回頭重讀(`note-audit reread-check --gate`),共 9 道——擋下時不再 `exit 1`,改呼叫共用函式 `pp_record_block <閘名> <ref 或空> <一句原因>`(累積在 `_PP_BLOCKS` 陣列),照原樣把該道的完整說明印出來,然後繼續下一道。同一道被多個 ref 擋下時各記一筆。
2. **全套測試之前統一判**:判斷點放在「建測試用暫存檔」之前(掛鉤現在第 586 行那一步之前)。只要 `_PP_BLOCKS` 有任何一筆,就印一段「這次推送共有 N 道擋下」的彙總(逐筆一行:閘名、ref(多 ref 時)、原因,詳細處理方式看上面那一段),然後 `exit 1`,不跑自主迴圈測試與全套測試。彙總裡有裁判簽名那一道時,最前面加一行「裁判檔被改過、沒重新簽名:下面其他道的結果是用被改過的工具算的,只供參考」。沒有任何一筆才照舊往下跑測試。
3. **前提壞掉的照舊立刻停**:找不到 Python 3.14、暫存目錄建不起來(掛鉤開頭的總暫存目錄,與測試前建 log 檔那一步)、使用者中斷(`pp_stop_if_signaled`,回傳碼 128 以上)——這幾種後面什麼都跑不了或不該再跑,維持立刻結束。找不到 `scripts/lumos` 照舊是「提醒後放行」(`exit 0`),不在收集範圍。
4. **代碼審判定內部也全部判完**:`lumos code-loop check` 新增 `--collect`:四道判定(合約測試、表態、新增告警、代碼審留痕)都跑完,每道擋下各印各的訊息(原本的擋下句一字不改),最後 rc1;合約測試先紅時照樣算風險分級,第四道才判得了。帶 `--json` 時多一個 `blocks` 清單(每筆 `reason_kind` 與 `reason`),原本的 `blocked`、`reason`、`tier` 欄位照舊(`reason` 放第一筆)。掛鉤呼叫時帶上 `--collect`。不帶時行為與輸出不變(其他呼叫者如 CI 不受影響)。逃逸自動記帳照現在的判斷(掛鉤認「受波及合約的測試沒過」與「tier=high 且」兩句;收集模式同時印出時各記一筆)。
5. **預演指令** `lumos push-preview`:不推送、不跑測試;用目前分支推到它追蹤的遠端分支(沒有追蹤就用主線所在的遠端、同名分支)組出掛鉤要讀的那一行(本地 ref、本地提交、遠端 ref、遠端提交;遠端查不到那個分支就當新分支,遠端提交填全零),帶環境變數 `LUMOS_PUSH_PREVIEW=1` 跑掛鉤;掛鉤看到它,到統一判斷那一步就停:有擋下回 1,沒有回 0 並印「便宜的閘都過了;測試沒跑(預演不跑),真推送時還會跑」。回 0 不代表測試綠。

## 驗收條款

- [S1] 當兩道彼此獨立的便宜閘同時擋下(例:圖譜健檢有壞連結,且 `governance/anchor-baseline.json` 改過沒提交)時,推送前掛鉤應回 1,彙總裡兩道都列出,而且全套測試沒有被跑到。[test: t_prepush_collects_all_blocks]
- [S2] 當只有一道擋下時,應回 1、印出那一道原本的完整說明加彙總,全套測試沒有被跑到;當沒有任何一道擋下時,應照舊跑到全套測試。[test: t_prepush_collects_all_blocks]
- [S3] 當找不到 Python 3.14 時,掛鉤應立刻結束(不收集、不往下跑)。[test: t_prepush_collects_all_blocks]
- [S4] 當 `lumos code-loop check --collect` 遇到表態不完整且有新增告警時,兩個原因都應印出、回 1;合約測試紅且 tier=high 又沒有代碼審留痕時,兩個原因也都應印出;不帶 `--collect` 時應照舊只印第一個,輸出與現在一字不差。[test: t_code_loop_check_collect]
- [S5] 當執行 `lumos push-preview` 時,不應推送、不應跑任何測試,應印出各道結果;有擋下時回 1、全過時回 0 並說明測試沒跑;遠端沒有這個分支時應當成新分支首推處理。[test: t_push_preview_runs_gates_without_suite]
- [S6] 收集模式下,任何一道記下的擋下最後都應讓掛鉤回 1——沒有一條路徑能把擋下變成放行。[test: t_prepush_collects_all_blocks]

- 既有守衛要一起更新:`Systems/bound-tests-gate` 綁的 `t_prepush_gates_stop_on_signal`(中斷要停)與 `t_prepush_cheap_gates_run_before_expensive_suite`(便宜的閘擋下時不跑全套)行為不變,斷言照舊要綠。

## 實務隱患

- 守衛面:這是推送閘本身。最大的風險是「收集」寫錯讓某道擋下被吞掉、變成放行;所以只用一個共用函式記、一處判(S6),每一處原本的 `exit 1` 都換成同一個呼叫,測試拿兩道真的閘驗。
- 已排除:金流:不碰任何付款或點數。
- 已排除:對外送出:預演不推送;只有真推送才連遠端,行為照舊。
- 已排除:不可逆:只改掛鉤的判斷流程與一個子命令,還原提交即可;擋下的情況不會變少。
- 輸出變長:一次列出全部之後,被擋時的訊息會比現在多;彙總段放在最後、逐道一行,讓人一眼看到總數。
- 時間:多跑的只有本來就要跑的便宜閘(全部約十幾秒、漂移最壞每個分支 60 秒);全套測試在有擋下時照舊不跑。

## 回退

- 還原提交即可回到遇錯就停;`code-loop check` 不帶 `--collect` 的行為沒變,其他呼叫者不受影響。
