# lumos 專案知識圖譜——一頁手冊

圖譜記「為什麼、邊界、不能改的、驗過沒」;code 只記「現在長怎樣」。圖譜跟行為事實(測試、實際執行、生產觀測)對不上時,不自動信圖譜——查清哪邊錯,立一篇事故筆記。主工具 `lumos`(python3 零依賴,自動找 `docs/*-knowledge/`)。**別用 Grep/Read/Edit/Write 直接碰圖譜的 .md 開頭欄位**——會繞過自驗和防護;正文段落用 Edit 可以。

**指令怎麼找**:`commands/INDEX.md`(本目錄,4k)——先看「grep 衝動對照表」,再按你正在做的事開九個子檔之一。下面只列每個階段最常用的。

## 1. 進場(每個子任務都重來,不是 session 開頭一次)

| 你在想… | 敲 |
|---|---|
| 這件事為什麼這樣 / 圖譜記了嗎 | `lumos search <詞>` → `lumos context <節點>`;0 命中先換同義詞;**中文概念之間加空白**(`作廢 收回 點數`,別黏成一句) |
| 動這段有什麼不能碰 | `lumos contracts <節點>` |
| 要讀全文再下結論 | `lumos show <節點>`(search 只給索引行;拿摘要判「沒記」以前真的錯過——值在筆記第 64 行,靠摘要判成沒有) |
| 篩條件(金流 / 未收案 / 連到 X) | `lumos query --tag 家族/值 [--active] [--linked <節點>]` |
| 開工掌握現況 | `lumos query --tag status/doing`;`lumos recent --days 7` |
| 圖譜空或稀疏(接手 brownfield) | 走節點還原 SOP:`commands/09-節點還原.md`(七步;需要才產節點、有就照慣例用) |

看到筆記有 `core_refs:` 或 `CORE:` → 權威在跨專案核心圖譜,改那邊(`lumos-core-knowledge` skill)。
**查得到才算先行**(Landmark 實測):0 筆看「逐詞覆蓋」標 ★ 的詞換同義詞,換三次再問人,別轉 grep;大節點先 `--brief`;單篇內部新舊打架時摘要有日期的 KEY 行 > 正文,衝突影響決策去 code 裁再回頭修。
**分清你在哪種 session**:本機 Claude Code(含手機/網頁遙控本機)有本機 git 憑證、能 push;網頁版 claude.ai/code 是雲端沙盒,對主分支沒 push 權、只能推 feature branch——「遙控」不等於「遠端版」,曾騙到 AI 一次。
被催「直接改、不用解釋」也一樣:不解釋可以,不查不行——改 code 前至少 `lumos impact --file <檔>` 一行。

## 2. 動手前

- `lumos impact --file <檔>` / `--diff <範圍>`:哪些筆記、驗證、決策會受影響(Edit 前 hook 也會塞一份,但只推你碰到的檔)。
- `lumos pitfalls --diff <範圍>`:風險分級;`tier: high` 要過代碼審(`lumos-code-loop`)。
- 要刪 / 改名東西:`lumos search <舊名> --code` 逐句判哪些筆記還在講它。
- 改了環境 / 流程 / 設定(版本、金鑰、hook、排程):`lumos stale --candidate --match <關鍵字>` 列出寫了「改到這個就該重驗」的驗證紀錄。
- 設計、spec、計劃一律寫成 `Projects/<主題>_計劃` 筆記(`type: project`),不寫到別的路徑;動筆前一行 `PRIOR-ART:`(最小解在哪層 / 世界解過沒 / 借用‧自建‧採用)。

## 3. 寫回(同一次工作內;pre-commit 擋「改 code 沒動圖譜」)

| 要做 | 敲 |
|---|---|
| 新筆記 | `lumos new <system\|issue\|verification\|project> <名>`;驗證紀錄加 `--plan <計劃> --systems <節點>` 自動雙向連 |
| 改狀態 / 日期 | `lumos set <節點> <欄位> <值>`(日期不加引號) |
| 加 / 刪清單項 | `lumos append <節點> <欄位> "[[x]]"` / `lumos remove …` |
| 記決策 / 翻案 | `lumos decision-add <節點> "<內容>" --decided <日期>` / `lumos decision-supersede` |
| 正文段落 | Edit;寫完 `lumos lint <節點>` |

**四條血換的開頭欄位鐵則**:① 多個連結一行一項,擠成一串會長假筆記 ② `summary: |` 區塊裡的 `[[連結]]` 不算連結,要關聯另放 list 欄位 ③ 值含「冒號+空格」要引號或區塊 ④ 同層不能重複鍵。用指令寫天生避開;手改才會踩。

**合約標記(動筆前掃一眼;不確定就不標,嚴禁看 code 反推)**:
```
KEY:★INVARIANT★ <業務合約,改=破壞性> [test:測試名] [audit:模型/日期] [kill:recipes]
KEY:★DEBT★ <偶然行為,可改>
KEY:★IRREVERSIBLE★ <做了回不去> [rollback:decisions]     KEY:★CHECKPOINT★ <改了難救>(建議補 [rollback:])
```
- 綁測試 / 留審計走指令:`lumos guard bind <節點> "<KEY 片段>" <測試名>`、`lumos guard audit …`;裸合約 doctor 擋,未審計 pre-push 擋。綁之前對照 [[Systems/測試假綠形態]](最隱蔽的一型:現場根本走不到被測分支;修 bug 的翻紅測試要配一條「現場成立」的前置斷言)。
- 外部不可逆(信已寄、下游已吃)用 `[guard:decisions]` 寫怎麼防重複。`[test:]` 只證程式對,「規則還符不符合業務」要人確認:`lumos signoff`。
- 從 code 重建的筆記先 `lumos set <節點> regen from-scratch/<日期>`,每條主張標 `[src:]`/`[git:]`/`推測:`/`佚失:`;佚失就寫佚失,嚴禁編。

**摘要區塊**(Systems/Issues 必有):`FLOW:`流程 `KEY:`關鍵概念 `DEP:`依賴 `TEST:`測試;Issues 用 `FLAG:`(只收 TECHNICAL/DECISION/ORIGIN) `DECISION:` `KEY:`。已結案的 Issue 正文第一段要有結案橫幅(status 在開頭欄位,`show --body-only` 看不到,讀者會把修好的當現況)。
**標籤**:`type/` `status/`(值域 lint 硬擋)、`priority/` P0–P3、`scope/`(feature/ area/ 已停用)、`risk/` 金流‧對外送出‧不可逆‧守衛面、`flag/`。

**決策與驗證**:重大決策填四欄(context / alternatives≥2 / why_chosen / trade_offs),缺資訊問人不編。驗證紀錄填 `valid_under`(前提)與 `revalidate_when`(何時重驗),用 `plan_refs` 指回計劃;漏掛 `lumos sync-verified-by --apply`。計劃結案前 `lumos spec-trace <計劃>` 看哪些條款沒人認領。

**承認風險的鐵則**(Enzo 2026-08-22 裁):筆記或訊息裡寫「沒機械守衛 / 只提醒不擋 / 單次量測 / 這數字是拍的」這類承認句,**旁邊必須有「什麼時候回頭看」**(週報、重驗條件、revalidate_when、到期日);寫不出重驗條件的,就是該處理不該承認。**回頭條件要接電**(2026-08-31 回訪案):帶日期的寫成獨立一行 `REVISIT:YYYY-MM-DD 一句要做什麼`(緊鄰原句,doctor 到期會唸、逾 14 天沒人動升級週報);綁事件的明寫事件入口——純散文=52 件盤點實證的死文。

## 4. 收工

1. `lumos lint <每篇動過的>` → `lumos doctor`(紅的段先修;`--verbose` 看全部提醒)。
2. code 有「拿掉 / 反轉」的改動:把那些名字逐個 `lumos search <名> --code`,逐句判筆記還成不成立,不成立當場改或標作廢。動到畫面 → 補可重放的 UI flow 並 `[test:<平台>:<flow>]` 綁回(沒裝置要明寫「未驗+原因」)。
3. 圖譜實質更新後:派乾淨 agent 只讀圖譜還原脈絡,對不上就補到一致,留痕 `lumos self-audit <節點>`。
4. push 後(專案有宣告 ci 區塊才有):`lumos ci-wait`,紅就當輪修,修不完要在收尾明講。
5. 跨 session 傳訊只傳「指標+觸發」(我動了哪篇、你去讀哪篇),不傳內容本身;規則權威在圖譜不在誰的記憶。

    24	## 這是什麼
    25	
    26	程式碼只告訴你「現在長這樣」。它說不出來的有五件事：
    27	
    28	- 當初**為什麼**選這個做法，比較過什麼、否決了什麼。
    29	- 這塊管到**哪裡為止**，動了會波及誰。
    30	- 哪些行為是**說好不能變的**，哪些只是剛好長這樣、可以放心重構。
    31	- 這件事**驗證過沒有**，在什麼前提下才算數。
    32	- 搞砸了**收不收得回來**。
    33	
    34	以前這些事活在資深工程師的腦子裡，人一走就沒了。AI 時代更慘——AI 每個對話都是新人，上次跟它講過的話，這次不算數。
    35	
    36	Lumos 把這五件事寫成一疊互相連結的 Markdown 筆記，然後用 git 的檢查（提交、推送時自動跑的小程式）擋住「改了程式碼卻不更新筆記」這條路。**讓不寫比寫還麻煩，這樣才寫得下去。**
    37	
    38	上面那張圖有兩件事值得停一下看：
    39	
    40	- **金環（合約）不是一開始就在的。** 藍色的功能模組先素著出現，等綠色的驗證紀錄連上去，金環和星號才長出來——**這條規則就是這樣：宣稱「不能改」不算數，綁到真的證據才算。**
    41	- **橘色那條線是回頭的。** 出過的事故不會躺在角落生灰，它會被連進下一份計劃，變成動筆前的必讀。
    42	
    43	**這些筆記不用你手寫，也不用你背指令。** 你就照平常跟 AI 對話的方式做開發——查東西、改東西、做決定。安裝時已經把「什麼時候該查、什麼時候該寫回」注入 Claude Code 和 Codex 的規則檔，**對話過程沉澱下來的脈絡，會被規則逼著留在筆記上。**

    47	## 一篇筆記裡有什麼
    48	
    49	<p align="center">
    50	  <img src="assets/note-anatomy-zh.svg" alt="一篇筆記的解剖:機器讀的欄位、摘要行、掛著證據的合約,分隔線以下才是給人讀的" width="900">
    51	</p>
    52	
    53	那兩個星號記號是整套東西的核心——**重話不能只用嘴講，旁邊必須掛著證據**，掛不上，健檢直接紅。
    54	
    55	所以「這個專案有哪些不能碰的規則」不用問人也不用翻——一行指令就有答案（日常是 AI 幫你敲的）：
    56	
    57	```console
    58	$ lumos contracts
    59	
    60	# Systems/付款串接.md
    61	  ★INVARIANT★ 同一筆訂單絕對不能被扣兩次款——重送、重試、webhook 重複進來都算
    62	      ↳ 綁的測試: test_no_double_charge_on_retry
    63	# Systems/庫存扣減.md
    64	  ★INVARIANT★ 任何情況下庫存都不能變成負數——超賣一件都不行
    65	      ↳ 綁的測試: test_stock_never_goes_negative
    66	# Systems/購物車.md
    67	  ★DEBT★ 購物車存在 Redis 沒有落地資料庫,Redis 一重開就空了。已知,現在可接受,要改隨時可以改
    68	
    69	合約 4 條(改了就是破壞性變更) | 技術債 2 條(可以改)
    70	```
    71	
    72	最後一行的分別很重要：**哪些是規則、哪些只是「目前剛好這樣」，寫清楚，重構的人就不用猜。**

    76	## 跟 Obsidian 差在哪
    77	
    78	**筆記格式跟 Obsidian 相容，你想用 Obsidian 打開它完全沒問題**，也不需要為了 Lumos 裝任何筆記軟體。我們不打算取代它。
    79	
    80	一句話講完差別：**Obsidian 是給人瀏覽的，Lumos 是給 AI 查的。**
    81	
    82	| | 一般筆記軟體 | Lumos |
    83	|---|---|---|
    84	| **AI 要用它** | 把檔案倒進 context，自己撈 | **下一行指令，拿回排序過、壓縮過的答案** |
    85	| **從程式碼反查** | 沒有這個概念 | **給一個原始碼檔，回哪幾篇筆記受影響、哪幾篇帶合約** |
    86	| 你寫「這條規則不能改」 | 存檔，沒事 | 要你指出哪支測試在守它。指不出來，健檢紅 |
    87	| 你改了程式碼、沒動筆記 | 沒人知道 | `git commit` 當下被擋住，要你補或說一句為什麼不用 |
    88	| **當初為什麼這樣決定** | 散在正文裡，自己翻 | **決策是獨立欄位：編號、日期、理由、後來翻案了沒** |
    89	| **筆記過期了** | 沒人知道，繼續信 | **驗證紀錄要寫回頭條件，到期會被唸出來** |
    90	
    91	### 最關鍵的一條：查，不是把整疊倒進去
    92	
    93	一個 AI 拿到 Obsidian 的筆記庫，只能把檔案讀進 context。**這個 repo 的筆記全文是 261 萬字元**——塞不進去；塞得進去，重點也被稀釋成雜訊。
    94	
    95	<p align="center">
    96	  <img src="assets/graph-growth.gif" alt="Lumos 自己的知識圖譜三個月從幾篇長成 440 篇" width="820">
    97	  <br>
    98	  <sub>Lumos 自己的筆記，三個月長出來的樣子：440 篇、1572 條連結。這張是產品畫面直接錄的，不是畫的。</sub>
    99	</p>
   100	
   101	Lumos 的做法是讓它**下查詢**：
   102	
   103	```console
   104	$ lumos context Systems/付款串接 --brief     # 回 783 字元,那篇全文是 1,812
   105	提醒:這篇有「動了會壞」的合約,動手前一定要看:
   106	  ★INVARIANT★ 同一筆訂單絕對不能被扣兩次款 [test:test_no_double_charge_on_retry]
   107	```
   108	
   109	**合約永遠釘在最上面。** 差別不是「比較快」，是**塞不塞得下**。
   110	
   111	還有一種查法 Obsidian 給不了——**從程式碼反查筆記**：
   112	
   113	<p align="center">
   114	  <img src="assets/impact-zh.svg" alt="給一個原始碼檔,圖譜算出哪幾篇筆記受影響、哪幾篇帶合約" width="900">
   115	</p>
   116	
   117	另外標籤是**結構查詢**不是全文搜尋（`lumos query --tag status/doing`），標籤分家族，可以疊「只看還沒收的」「只看連到某篇的」。
   118	
   119	這疊筆記的主要讀者不是人，是**下一個 session 的 AI**——所以它**設計成可以被查詢，不是被閱讀**。

   123	## 越跑越準的循環
   124	
   125	這是 Lumos 跟「一本寫得很好的文件」真正的分野。文件會過期；這套東西每跑一輪，手上的材料就更準一點。
   126	
   127	<p align="center">
   128	  <img src="assets/loop-zh.svg" alt="圖譜餵進審查、審查結果寫回圖譜的循環" width="900">
   129	</p>
   130	
   131	圖上四個階段是照順序跑的。**關鍵在最後一步：交代的結果會寫回圖譜，變成下一輪的材料。**
   132	
   133	**筆記不是最後的產出物，是下一輪的輸入。** 所以第一輪審查員手上可能只有三篇，第五輪會有八篇——而且那八篇都是前幾輪真的被採納過的，不是誰憑印象丟進去的。
   134	
   135	**同一批 AI、同樣的時間，差別只在手上的材料越來越準。**
   136	
   137	> **老實話：** 機器擋得住的是形式——測試存不存在、回退有沒有寫、有沒有找人獨立審過、每條意見有沒有交代。
   138	> 「這條規則今天還符不符合業務」「那個回退步驟真的跑得動嗎」——只有人能答。別把「有掛證據」當成「絕對安全」。

   142	## 適合誰 / 不適合誰
   143	
   144	**適合：**
   145	
   146	- 專案要活超過幾個月，而且會有別人（或別的 AI）接手。
   147	- 大量用 AI 寫程式，你自己不會逐行讀完。
   148	- 系統裡有「動到就會出事」的地方：金流、庫存、權限、資料遷移。
   149	
   150	**不適合：**
   151	
   152	- 兩週寫完就丟的東西。
   153	- 一個人的小工具，你自己每天都在讀，全部記在腦子裡。
   154	- 你要的只是一個漂亮的筆記 app——那 Obsidian 就夠了，真的。
   155	
   156	**代價講在前面：** 這套會讓每次提交多花時間。它換到的是三個月後不用重新考古。**專案活不到三個月，就不划算。**

   160	## 裝起來
   161	
   162	### 專案已經在用 Lumos（接手的人）
   163	
   164	```bash
   165	git clone <你的專案> && cd <你的專案>
   166	python3 scripts/lumos bootstrap
   167	```
   168	
   169	一行搞定：Lumos 本體、給 AI 看的操作手冊、全域指令、git 檢查，全部裝好。裝完**重啟 Claude Code 或 Codex 的對話**（有些提示是開場時載入的）。
   170	
   171	### 全新專案要導入
   172	
   173	站在你的專案目錄裡跑：
   174	
   175	```bash
   176	curl -fsSL https://raw.githubusercontent.com/EnzoHsieh-Android/Lumos/release/get.sh | bash
   177	```
   178	
   179	它會問「要把這個目錄建成 lumos 專案嗎？[y/N]」，按 `y`。
   180	
   181	- **預設是 N**，所以站錯目錄（例如你的 dotfiles）按 Enter 就跳過，不會誤裝。
   182	- 不想盲跑遠端腳本？先 `curl -fsSL <網址> -o get.sh` 抓下來看過再執行。
   183	- CI 這種沒有人在旁邊的環境：結尾加 `-s -- --init` 直接建、不問。
   184	
   185	### 裝好了嗎
   186	
   187	```bash
   188	lumos enforcement
   189	```
   190	
   191	它列出每一層防護「有沒有裝上、接上」——**注意它查的是接線，不是判得對不對**。全綠代表檢查程式註冊了、檔案在、版本對。Codex 那幾行會停在「已註冊，要不要跑本機讀不到」，那是平台限制、不是壞掉。
   192	
   193	<details><summary>Windows（原生 PowerShell）</summary>
   194	
   195	前置：Git for Windows、python 在 PATH、Claude Code。
   196	
   197	```powershell
   198	irm https://raw.githubusercontent.com/EnzoHsieh-Android/Lumos/release/get.ps1 | iex
   199	# 重啟對話;若找不到 lumos,把 %USERPROFILE%\.local\bin 加進 PATH
   200	cd <你的專案>; lumos init
   201	```
   202	</details>
   203	
   204	<details><summary>只裝一半 / 離線裝 / 為什麼分兩層</summary>
   205	
   206	**分兩層的原因**：
   207	- **專案層**——CI 只看得到你的專案 repo，git 檢查也是一個 repo 一份，所以檢查工具必須**複製一份進每個專案**。更新用 `lumos update`。
   208	- **機器層**——給 AI 看的操作手冊是**整台機器共用一份**，用捷徑連到 Claude Code / Codex 的目錄。對 Lumos 目錄 `git pull` 一次，所有專案同時吃到新版。
   209	
   210	只建專案層 `lumos init`（`--no-hooks` 只建筆記資料夾不裝檢查；既有筆記**絕不覆寫**）。只裝機器層 `lumos install`。手動離線：
   211	
   212	```bash
   213	git clone --branch release https://github.com/EnzoHsieh-Android/Lumos ~/harness/lumos-toolchain
   214	cd ~/harness/lumos-toolchain && ./install.sh
   215	python3 scripts/lumos install
   216	scripts/install-graph-toolchain.sh --target <專案路徑> --slug <名稱>
   217	```
   218	
   219	`release` 是對外線，只有維護者會把它往前推。要跟開發線就把 `--branch release` 拿掉。
   220	
   221	**Claude Code 和 Codex CLI 都支援**，同一次安裝接兩家，行為一致。細節在[心智模型與機制](docs/心智模型.md)。
   222	</details>

   226	## 你的第一次
   227	
   228	**裝完之後，你不用背任何指令。** 開一個 Claude Code 或 Codex 的對話，像平常一樣講話就好：
   229	
   230	<p align="center">
   231	  <img src="assets/usage-zh.svg" alt="左邊是你用人話講的三句,右邊是它自己敲的指令與讀到的東西" width="900">
   232	</p>
   233	
   234	左邊那三句就是你要做的全部。右邊那些指令**你不用碰也不用背**——安裝時已經把「什麼情況該查什麼」寫進 Claude Code 的 `CLAUDE.md` 和 Codex 的 `AGENTS.md`，另外掛了五個自動觸發的檢查（開場提醒、改檔前推波及的筆記、派審查員時附相關筆記、收工檢查、CI 狀態）。
   235	
   236	真的要提交而筆記沒動時，會像這樣被擋下來：
   237	
   238	```console
   239	$ git commit -m "調整結帳邏輯"
   240	
   241	擋下:這次 commit 改了程式碼,但知識筆記一個字都沒動。
   242	程式碼記的是「現在長怎樣」,筆記記的是「為什麼這樣做」——只改其中一邊,
   243	下一個人(或下一個 session 的 AI)就會拿舊的理由去理解新的程式碼。
   244	
   245	兩條路選一條:
   246	   1. 把該改的筆記改一改,加進 commit,再提交一次。
   247	   2. 這次真的不需要動筆記(改錯字、排版、註解)→ git commit --no-verify
   248	      跳過會留下紀錄,不是偷偷放行。
   249	```
   250	
   251	**這一擋就是整套東西的本體。** 其他都是為了讓這一擋不討人厭而長出來的。
   252	
   253	> 想自己敲指令當然可以，看[指令參考](docs/指令參考.md)。這份說明貼輸出，是為了讓你看見它讀了什麼、擋了什麼——**看不見的治理等於沒有治理。**

   259	我相信全自動開發的時代有一天會來。
   260	
   261	但**AI 不會憑空知道一個專案的業務經驗，也不會知道那些決斷是怎麼走過來的。** 為什麼當初否決了看起來更快的那個做法、哪一次事故換來現在這條規則、哪個數字是人拍板的而不是算出來的——這些都不在程式碼裡。它們一直活在人的腦子裡，人走了就沒了；而 AI 每個對話都是新人。
   262	
   263	模型會一直變強。但再強的模型，面對一個沒有脈絡的專案，一樣是新人。
   264	
   265	所以我深信：**下一代軟體開發的基石，不會只是更會寫程式的模型，而是把脈絡留下來的工程治理。**
   266	
   267	Lumos 是我對這件事的答案。

     5	# Lumos
     6	
     7	[繁體中文](README.md) · **English**
     8	
     9	> That module you had an AI write three months ago? You need to change it today.
    10	> You don't remember why it was built that way. Neither does the AI — every session, it starts as a stranger.
    11	>
    12	> **Lumos gives a project a second set of notes for everything the code can't say, then uses checks to make sure they actually get written.**
    13	
    14	<p align="center">
    15	  <img src="assets/graph-demo-en.svg" alt="A demo: an online store's notes — plan first, then the module, then a record" width="900">
    16	</p>

    24	## What this is
    25	
    26	Code only tells you what things look like right now. Five things it can't tell you:
    27	
    28	- **Why** this approach — what was compared, what was rejected.
    29	- **Where this part ends**, and who gets hit if you change it.
    30	- Which behaviours are **promises nobody may break**, and which just happen to be that way and are safe to refactor.
    31	- Whether this was **ever verified**, and under what assumptions.
    32	- Whether you can **take it back** if you get it wrong.
    33	
    34	That knowledge used to live in a senior engineer's head, and left when they did. The AI era is worse: an AI is a stranger in every conversation. What you told it last time doesn't count this time.
    35	
    36	Lumos writes those five things into a set of interlinked Markdown notes, then uses git checks (small programs that run when you commit or push) to close off the "changed the code, didn't touch the notes" path. **Not writing has to be more annoying than writing — otherwise nobody writes.**
    37	
    38	Two things in that diagram are worth pausing on:
    39	
    40	- **The gold ring isn't there from the start.** The blue module appears plain; the ring and star only grow once a green verification record is linked to it — because that's the rule: **claiming "this must not change" doesn't count until real evidence is bound to it.**
    41	- **The orange line goes backwards.** An incident doesn't sit in a corner gathering dust; it gets wired into the next plan as required reading before anyone starts.
    42	
    43	**You don't hand-write these notes, and you don't memorise commands.** You develop the way you already do — talking to an AI as you look things up, change things, decide things. Installing injects "when to look something up, when to write it back" into Claude Code's and Codex's rule files, so **the context that settles out of those conversations gets kept, because the rules make it get kept.**
    44

    47	## What's in a note
    48	
    49	<p align="center">
    50	  <img src="assets/note-anatomy-en.svg" alt="The anatomy of a note: machine-read fields, summary lines, contracts with their evidence, and below the divider the part for people" width="900">
    51	</p>
    52	
    53	Those two starred markers are the heart of the whole thing — **a heavy claim can't just be asserted; evidence has to hang off it**, and if it doesn't resolve, the health check goes red.
    54	
    55	So "what rules can't be touched in this project" isn't a question you ask a person. It's one command — usually one the AI runs for you:
    56	
    57	```console
    58	$ lumos contracts
    59	
    60	# Systems/payment-integration.md
    61	  ★INVARIANT★ one order must never be charged twice — resends, retries, duplicate webhooks all count
    62	      ↳ bound test: test_no_double_charge_on_retry
    63	# Systems/stock-deduction.md
    64	  ★INVARIANT★ stock must never go negative — not by a single unit
    65	      ↳ bound test: test_stock_never_goes_negative
    66	# Systems/cart.md
    67	  ★DEBT★ the cart lives in Redis with no database behind it; a Redis restart empties it.
    68	          Known, currently acceptable, changeable any time.
    69	
    70	4 contracts (changing one is a breaking change) | 2 debts (safe to change)
    71	```
    72	
    73	That last line matters more than it looks. **Spelling out which things are rules and which merely happen to be true means the next person refactoring doesn't have to guess.**

    77	## How this differs from Obsidian
    78	
    79	**The note format is Obsidian-compatible — open it in Obsidian if you like**, and you don't need to install any notes app for Lumos to work. We're not trying to replace it.
    80	
    81	The difference in one line: **Obsidian is for people to browse. Lumos is for an AI to query.**
    82	
    83	| | Ordinary notes app | Lumos |
    84	|---|---|---|
    85	| **An AI using it** | Dump files into context and go fishing | **One command back: ranked, filtered, compressed** |
    86	| **Looking up from source code** | No such concept | **Give it a source file, get the notes it affects and which of them carry contracts** |
    87	| You write "this rule must not change" | Saved. Fine. | Name the test that guards it. Can't? Health check goes red. |
    88	| You changed code and touched no notes | Nobody notices | `git commit` stops you — fix it, or say in one line why it isn't needed |
    89	| **Why it was decided that way** | Buried in prose; go read | **Decisions are their own field: id, date, reasoning, whether it was later overturned** |
    90	| **A note has gone stale** | Nobody knows; people keep trusting it | **Verification records must state what would invalidate them, and get nagged when due** |
    91	
    92	### The one that matters most: query it, don't pour it in
    93	
    94	An AI handed an Obsidian vault can only read files into context. **This repo's notes come to 2.61 million characters** — they don't fit; and if they did, the important parts would be diluted into noise.
    95	
    96	<p align="center">
    97	  <img src="assets/graph-growth.gif" alt="Lumos's own knowledge graph growing to 440 notes over three months" width="820">
    98	  <br>
    99	  <sub>Lumos's own notes over three months: 440 of them, 1,572 links. Recorded from the actual tool, not drawn.</sub>
   100	</p>
   101	
   102	Lumos lets it **issue a query** instead:
   103	
   104	```console
   105	$ lumos context Systems/payment-integration --brief   # 783 chars back; the full note is 1,812
   106	Heads up — this note carries a contract. Read it before you touch anything:
   107	  ★INVARIANT★ one order must never be charged twice [test:test_no_double_charge_on_retry]
   108	```
   109	
   110	**Contracts are pinned to the top.** The difference isn't "faster" — it's **fits vs. doesn't fit**.
   111	
   112	One more lookup Obsidian can't give you — a **reverse lookup from source code**:
   113	
   114	<p align="center">
   115	  <img src="assets/impact-en.svg" alt="Give it a source file and the graph works out which notes are affected and which carry contracts" width="900">
   116	</p>
   117	
   118	Tags are also a **structured query**, not full-text search (`lumos query --tag status/doing`). They come in families, and filters stack: "only what's still open", "only what links to this note".
   119	
   120	The primary reader of these notes isn't a human — it's **the next session's AI**. So they're **designed to be queried rather than read**.

   124	## The loop that gets sharper
   125	
   126	This is where Lumos parts ways with "a really well-written document". Documents go stale. This gets a little sharper every time it runs.
   127	
   128	<p align="center">
   129	  <img src="assets/loop-en.svg" alt="The graph feeds each review; each review writes back into the graph" width="900">
   130	</p>
   131	
   132	The four stages run in order. **The point is the last one: what gets accounted for is written back into the graph, and becomes the next round's material.**
   133	
   134	**Notes aren't the final output; they're the next round's input.** Round one might hand a reviewer three notes; round five hands them eight — and all eight already earned their place. Nobody dropped them in from memory.
   135	
   136	**Same reviewers, same time budget — only the material got sharper.**
   137	
   138	> **The honest limit:** what a machine can prove is *form* — that a test exists, that a rollback is written, that someone independent reviewed it, that every finding was accounted for.
   139	> Whether a rule still matches the business, or whether that rollback would actually run — **only a person can answer that.** Don't read "has evidence attached" as "safe".
   140	
   141	---
   142	
   143	## Who this is for
   144	
   145	**A fit if:**
   146	
   147	- The project needs to live longer than a few months, and someone else (or another AI) will pick it up.
   148	- You lean heavily on AI to write code and don't read every line yourself.
   149	- There are places where a mistake really hurts: payments, inventory, permissions, data migrations.
   150	
   151	**Not a fit if:**
   152	
   153	- You'll finish it in two weeks and throw it away.
   154	- It's a small solo tool you read every day and hold entirely in your head.
   155	- You just want a nice notes app — Obsidian is genuinely enough for that.
   156	
   157	**The cost, stated upfront:** this makes every commit take longer. What you buy is not having to do archaeology three months later. **If the project won't live three months, it doesn't pay for itself.**

   161	## Getting it installed
   162	
   163	### The project already uses Lumos
   164	
   165	```bash
   166	git clone <your-project> && cd <your-project>
   167	python3 scripts/lumos bootstrap
   168	```
   169	
   170	One line: Lumos itself, the operating manual the AI reads, the global command, and the git checks. Then **restart your Claude Code or Codex conversation** — some of the prompting loads at session start.
   171	
   172	### Adding it to a new project
   173	
   174	Run this from inside your project directory:
   175	
   176	```bash
   177	curl -fsSL https://raw.githubusercontent.com/EnzoHsieh-Android/Lumos/release/get.sh | bash
   178	```
   179	
   180	It asks "turn this directory into a lumos project? [y/N]" — press `y`.
   181	
   182	- **The default is N**, so if you're standing in the wrong directory (your dotfiles, say), Enter skips it. No accidental installs.
   183	- Don't want to pipe a remote script blind? `curl -fsSL <url> -o get.sh`, read it, then run it.
   184	- Non-interactive environments like CI: append `-s -- --init` to create it without asking.
   185	
   186	### Did it install?
   187	
   188	```bash
   189	lumos enforcement
   190	```
   191	
   192	It lists each layer of protection and whether it's **wired up** — note that it checks the wiring, not whether the judgement is right. All-green means the checks are registered, files are present, versions match. The Codex lines stop at "registered; can't tell locally whether it runs" — that's a platform limit, not a fault.
   193	
   194	<details><summary>Windows (native PowerShell)</summary>
   195	
   196	Prerequisites: Git for Windows, python on PATH, Claude Code.
   197	
   198	```powershell
   199	irm https://raw.githubusercontent.com/EnzoHsieh-Android/Lumos/release/get.ps1 | iex
   200	# Restart the session. If lumos isn't found, add %USERPROFILE%\.local\bin to PATH.
   201	cd <your-project>; lumos init
   202	```
   203	</details>
   204	
   205	<details><summary>Partial install / offline / why there are two layers</summary>
   206	
   207	**Why two layers:**
   208	- **Project layer** — CI only sees your project repo, and git hooks are per-repo, so the checking tool has to be **copied into every project**. Update with `lumos update`.
   209	- **Machine layer** — the operating manual the AI reads is **one copy per machine**, symlinked into the Claude Code / Codex directories. `git pull` the Lumos directory once and every project picks up the new version.
   210	
   211	Project layer only: `lumos init` (`--no-hooks` creates the notes folder without the checks; existing notes are **never overwritten**). Machine layer only: `lumos install`. Fully manual:
   212	
   213	```bash
   214	git clone --branch release https://github.com/EnzoHsieh-Android/Lumos ~/harness/lumos-toolchain
   215	cd ~/harness/lumos-toolchain && ./install.sh
   216	python3 scripts/lumos install
   217	scripts/install-graph-toolchain.sh --target <project-path> --slug <name>
   218	```
   219	
   220	`release` is the public line; only the maintainer moves it forward. Drop `--branch release` to follow the development line instead.
   221	
   222	**Both Claude Code and Codex CLI are supported** — one install wires up both, with matching behaviour. Details in [the mental model](docs/心智模型.md).
   223	</details>

   227	## Your first time through
   228	
   229	**You won't have to memorise a single command.** Open a Claude Code or Codex conversation and talk the way you normally would:
   230	
   231	<p align="center">
   232	  <img src="assets/usage-en.svg" alt="Left: three things you say in plain language. Right: what it runs on its own." width="900">
   233	</p>
   234	
   235	Those three lines on the left are your whole job. The commands on the right **you never touch and never memorise** — installing writes "what to look up, and when" into Claude Code's `CLAUDE.md` and Codex's `AGENTS.md`, and wires up five checks that fire on their own (session-start reminder, pushing affected notes before an edit, attaching relevant notes when reviewers are dispatched, the wrap-up check, CI status).
   236	
   237	When you go to commit with the notes untouched, this is what you get:
   238	
   239	```console
   240	$ git commit -m "adjust checkout logic"
   241	
   242	Blocked: this commit changes code, but not one word of the notes.
   243	Code records what things look like now; notes record why they're that way. Change only
   244	one side and the next person (or the next session's AI) will read new code with old reasons.
   245	
   246	Pick one:
   247	   1. Update the notes that need it, add them to the commit, commit again.
   248	   2. This genuinely needs no note change (typo, formatting, a comment) →
   249	      git commit --no-verify
   250	      Skipping is recorded. It isn't a quiet pass.
   251	```
   252	
   253	**That block is the whole product.** Everything else exists to make it not annoying.
   254	
   255	> You can run the commands yourself — see the [command reference](docs/指令參考.md). This README shows their output so you can see what got read and what got stopped: **governance you can't see is governance that isn't there.**

   258	
   259	## Why this exists
   260	
   261	I believe fully autonomous development is coming.
   262	
   263	But **an AI will never know a project's business experience on its own, and it won't know how the judgement calls were made.** Why the faster-looking approach was rejected. Which incident bought the rule that's in place now. Which number a person decided rather than calculated. None of that is in the code. It has always lived in people's heads — and when they leave, it goes with them. An AI has it worse: it arrives a stranger in every conversation.
   264	
   265	Models will keep getting stronger. But a stronger model facing a project with no context is still a stranger.
   266	
   267	So I'm convinced of this: **the foundation of the next generation of software development won't just be models that write better code — it will be the engineering discipline that keeps the context.**
   268	
   269	Lumos is my answer to that.
