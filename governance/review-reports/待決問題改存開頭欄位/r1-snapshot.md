# 待決問題改存開頭欄位_計劃

> 白話:計劃的「待決問題」原本寫在正文一節、用正規式解析,規格閘拿它來擋還沒決定的阻塞題。代碼審三輪都在這裡換形狀,已撤出([[Projects/後端工程提問與證據擴充_計劃]] 決策 d10)。這篇重做:題目存在開頭欄位、用指令寫入,讀不清楚就整份擋。**狀態是草案,動手前要先過 `lumos spec-gate`。**

## 緣起

- 原做法:正文 `## 待決問題` 一節,一題一行 `- [Q1] 問題 [類:..][階段:..][狀態:..][阻塞] → #d1 出處:… 測試:…`,規格閘、lint、`pitfalls --stage` 共用一支逐行正規式解析,外加一道「題目形狀的行沒被讀到就擋」的外層看門。
- 代碼審 code-後端情境出題 三輪 21 席反覆撞到同一類:圍欄沒關(含四個反引號開三個收、`~~~` 開 ``` 收)把題目藏起來;標題寫成「三、待決問題」、粗體;旗標寫成 `［阻塞］`、`[阻 塞]`;一般敘述文字(`- Q4 上線 [階段一:灰度]`、題目文字裡的 `[阻塞性能]`)被誤擋;幾條正規式對長行平方級回溯。卷證在 governance/review-reports/code-後端情境出題/。

## 外部做法(2026-10-12 與 Codex 外家討論、加上網路查核)

PRIOR-ART:結構化資料與正文分開、只准用指令改,是主流做法;本專案的決策紀錄(開頭欄位 decisions + `lumos decision-add`)已經是這個模式,借用,不自建新格式。
- 開頭欄位(Jekyll、Hugo、Obsidian 的 properties):型別、合法值、編號重複都驗得了;Obsidian 社群普遍把它當比寫在正文裡的欄位更穩、更通用的預設。
- 寫在正文裡的欄位(Dataview 的 `key:: value`):易寫,但仍混在自由文字裡,圍欄、重複、跳脫字問題一樣在;Dataview 的後繼者 Datacore 據論壇轉述改成預設不讀(沒查到官方文件)。
- GFM 勾選清單:只表達做完沒,裝不下階段、阻塞、決策連結。
- 正規的 Markdown 解析器(CommonMark、markdown-it):要外部依賴,違反零依賴;而且解析對了也判斷不了 `[阻塞性能]` 是不是旗標。CommonMark 規定收尾圍欄要同字元、至少一樣長,沒關的圍欄延到檔尾——正文解析要自己重做這套才不漏。
- Issue 追蹤器(GitHub Issues、Jira)與 Backlog.md:標題、狀態、阻塞關係存成有型別的欄位,只透過表單、API 或指令改;Markdown 只負責描述。

## 做法

### 資料放哪、長怎樣

- 計劃筆記開頭欄位一個清單 `pending_questions`,每題一個項目,只收這幾個鍵(都是單行值;`tests` 用半形逗號分隔):

```yaml
pending_questions:
  - id: Q1
    text: 訂單成功的定義是什麼
    class: 需求
    stage: 需求
    status: 待人
    blocking: true
    irreversible: false
    decision: "#d1"
    source: README 第一段
    reason: 等示範跑完再定
    tests: t_a, t_b
```

- 必有:`id`(`Q` 加數字)、`text`、`class`(自由分類,非空單行,不驗值)、`stage`(需求/架構/實作/驗證/效能/交付,跟 `pitfalls --stage` 共用 `PQ_STAGES` 同一組)、`status`(待查/自答/待人/延後/已決/已驗)。其餘選填;`blocking`、`irreversible` 只收 `true`/`false`,沒寫當 `false`。
- 「必附」= 某些狀態必須附的欄位:已決、已驗要 `decision`;已驗另要 `tests`;自答要 `source`;延後要 `reason`。
- `pending_questions` 加進開頭欄位的已知鍵清單(`_KNOWN_FRONTMATTER_KEYS`),新版 lint 不對它報「沒見過的鍵」。
- 寫法照決策紀錄那一套(`cmd_decision_add` 加 `atomic_write_verify`):值的引號與跳脫用同一支格式化函式(錯誤訊息的欄位名改成可傳入),改哪行動哪行;寫檔前先在記憶體組好新內容,用下面的嚴格讀法驗過整份清單讀得懂、且這一題內容相符才寫檔,沒過就不寫。

### 讀法:寧可擋,但只看這一個欄位

- 另寫一支嚴格讀法(決策紀錄的讀法 `parse_decisions` 遇到看不懂的行會略過,不能拿來擋關)。範圍自己掃:從頂格的 `pending_questions:` 那行開始,到下一個頂格的「鍵:」為止;不沿用既有的結構定位,因為它會把頂格的 `- id:`、tab 開頭的行放在範圍外靜默忽略。範圍內每一行都必須是空行、「新的一題」(`  - id: Q<n>`)或「這一題的一個鍵」(比那一題更深一層的 `鍵: 值`),其他一律算讀不懂;tab 開頭、頂格的清單項、`pending_questions:` 後面直接接值(`[]` 除外)、開頭欄位裡出現兩個 `pending_questions:`,也都算讀不懂。
- 讀不懂的情形:看不懂的行、不認得的鍵、同一題同一個鍵寫兩次、編號重複或格式不對、缺必有鍵、`stage`/`status` 值不在清單、`blocking`/`irreversible` 不是 true/false、值裡夾了讀不懂的引號。**只要有一處讀不懂,整份清單當無法判定**:不取最後一個值、不跳過壞的那題。
- 不再看正文。正文寫了什麼〈待決問題〉都不影響判定(這是 [[Projects/後端工程提問與證據擴充_計劃]] d10 撤出的原因)。

### 三個消費端

- 規格閘(前段,放在判門之後、「沒有條款就提早結束」與 `--no-run` 之前,風險高低都一樣):清單無法判定 → 回 1,印「待決問題清單無法判定」與 lint 指令;有題標阻塞、階段是需求或架構、狀態是待查或待人 → 回 1,列出那幾題。只看狀態,不查決策存不存在(那是 lint 的事)。
- lint(掛在新規則那一路,擋不擋照 note_lint.gate):清單無法判定時逐處報原因與行號;讀得懂時查必附——已決、已驗要有 `decision` 且指到存在且有效的決策(可跨篇 `[[節點]]#dN`)、已驗要有 `tests` 且每個都在本篇驗收條款的 `[test:]` 裡、自答要有 `source`、延後要有 `reason`、標不可逆不得自答、標阻塞不得延後。條款那邊取條款綁定(`clause_bindings`)每一列認得的測試名(圍欄與反引號裡的不算),題目的 `tests` 照原字串比對(含平台前綴)。lint 規則只拿到開頭欄位,正文用既有的 `env_text` 讀。
- `pitfalls <計劃> --stage <階段>`:需求風險面照舊,再列那一階段還沒結(待查、待人)的題,依阻塞、不可逆、其餘排序、同級照編號,不截斷;清單無法判定時不列題,印原因並回 2。

### 指令

- `lumos question-add <計劃> "<問題>" --class <類> --stage <階段> [--status 待查] [--blocking] [--irreversible] [--decision …] [--tests …] [--source …] [--reason …]`:給下一個編號(現有最大號加 1),回印全域編號 `<計劃>#Q<n>`;必附不齊(例如 `--status 已決` 卻沒給 `--decision`)就不寫並說缺什麼。
- `lumos question-set <計劃> Q<n> <鍵>=<值> [<鍵>=<值> …]`:一次可改好幾個鍵(例如 `status=已決 decision=#d3`)。寫入前先驗這一題改完是否讀得懂、必附是否齊,不齊就不寫並說缺什麼。
- 不提供刪題:題目改成延後(附理由)或已決;真的寫錯就用編輯器刪,規格閘會因讀不懂而擋,lint 會說哪裡。

### 舊寫法

- repo 裡用過正文〈待決問題〉的只有 [[Projects/後端工程提問與證據擴充_計劃]](7 題),這次用新指令重建、正文那一節改成指向開頭欄位的一句話。不寫遷移工具,也不偵測正文舊寫法(偵測正文就回到猜格式那條路)。

## 驗收條款

- [S1] 當計劃開頭欄位的 `pending_questions` 有一題標阻塞、階段是需求或架構、狀態是待查或待人時,`lumos spec-gate` 不論風險高低、帶不帶 `--no-run`、有沒有驗收條款都應回 1 並列出那一題;沒標阻塞、或階段是實作以後的題不應讓規格閘擋;改成已決後應不再因它擋。[test: t_qfm_gate_holds_blocking]
- [S2] 當 `pending_questions` 有任何一處讀不懂(看不懂的行、tab 開頭或頂格的清單項、不認得的鍵、同鍵寫兩次、編號重複、缺必有鍵、值不在清單、布林寫錯、欄位寫兩次)時,`lumos spec-gate` 應回 1 並說清單無法判定,`lumos lint` 應逐處報原因;正文怎麼寫〈待決問題〉都不應影響判定。[test: t_qfm_strict_parse_fail_closed]
- [S3] 當執行 `lumos question-add` 時,應寫入下一個編號、重讀確認後才回 0;`lumos question-set` 把題目改成已決卻沒有決策連結、改成已驗卻沒有測試名時應回 2 且不改檔;同一次給 `status=已決 decision=#dN` 應成功。[test: t_qfm_commands_write_and_verify]
- [S4] 當清單讀得懂時,`lumos lint` 應報出:已決或已驗指到不存在或已作廢的決策、已驗的測試名不在本篇條款、自答沒出處、延後沒理由、不可逆卻自答、阻塞卻延後;寫齊的題不報。[test: t_qfm_lint_attachments]
- [S5] 當給 `lumos pitfalls <計劃> --stage <階段>` 時,應在需求風險面之後列出那一階段待查與待人的題,阻塞在前、不可逆其次、同級照編號、不截斷;清單無法判定時應回 2 並說原因;需求風險面每一項的階段都應在 `PQ_STAGES` 那六個裡。[test: t_qfm_stage_lists_open_questions]
- [S6] 當計劃沒有 `pending_questions` 欄位時,規格閘、lint、`pitfalls --stage` 的判定與輸出應跟現行相同。[test: t_qfm_absent_field_unchanged]

## 實務隱患

- 守衛面:規格閘多一條擋法,誤擋會訓練人繞過——擋的條件只看開頭欄位這一處、讀不懂時訊息直接說哪一行(S2);沒有這個欄位的計劃完全不變(S6)。
- 已排除:金流:不碰付款或扣款,也不處理任何金額
- 已排除:對外送出:只寫本機筆記,不呼叫外部服務、不寄信
- 已排除:不可逆:寫入走改哪行動哪行、寫完重讀、失敗還原,壞了用 git 還原;不刪檔、不改別的筆記
- 資料相容:舊版 lumos 讀到這個欄位會當成不認得的開頭欄位,照它既有的處理(不擋)——新舊版本混用時,舊版的規格閘不會擋阻塞題;擋法只在新版生效。

## 回退

- 一個功能一個提交,整個提交可單獨回退:回退後規格閘、lint、`pitfalls --stage` 不再讀 `pending_questions`,行為回到撤出正文解析後的樣子(S6 的現行);已經寫進計劃開頭欄位的清單留著,舊版當不認得的欄位忽略,不會因它擋。兩支指令一起拿掉。

## 不做

- 不引入 Markdown 解析器或 YAML 套件。
- 不寫舊格式遷移工具、不偵測正文的舊寫法(只有一篇、7 題,手動重建)。
- 不讓正文與開頭欄位雙寫;正文只放給人看的說明。
- 不做刪題指令、不做「只看待決問題」的顯示指令(`--stage` 已經會列)。
