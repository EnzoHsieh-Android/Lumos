## 2. 帶使用處標的括號註記 `@field:[…]` 和 `@file:[…]` 不被跳過
severity: minor
blocking: 否
引句:「    if j < len(code[i]) and code[i][j] == "[":」
file: `configs/ast-grep/kotlin-android/check.py:1141`(此處附近的 `_one_annotation_end` 只在 `@` 緊接 `[` 時走 `_balanced_end`;名稱之後只試 `<(`)
失敗場景:`// BAD` 下一行是 `@field:[Inject Named("x")]` 或 `@file:[JvmName("x") Suppress("y")]`。名稱正規式吃到 `field:` 後,遇到 `[`,迴圈既不是 `@` 也不是 `<`/`(`,於是 `_annotation_end` 回傳該行本身,BAD 標到註記行而不是被註記的宣告。
說明:計劃和 docstring 都宣稱支援「`@[…]`」。Kotlin 語法允許帶使用處標的的括號寫法,所以宣稱的涵蓋面比實作多一格。修前也不跳過,所以這不是回歸,而是這次改動順手聲稱要涵蓋、卻漏掉的角落。
歸因:有證據的原有漏查。

- 修前沒有跑這個輸入,原因是我讀修前的 `_ANNOTATION_ONLY_RE` 就能確定它同樣不匹配,所以判成原有行為。

- `@Foo` 在檔尾最後一行時回空清單(沒有下一個語句,行為和修前相同)

**註記讀法的邊角**:
- `@Foo<(Int) -> Unit>`,以及 `@ Foo`(`@` 後有空格),會被當成「註記後有程式」而標在註記行。前者 Kotlin 註解類別不能有型別參數,後者不是合法註記,所以不算 finding。
- 沒關的 `@Foo(` 若後面很遠剛好有多出來的 `)`,會被配成「已關」,BAD 標到更後面的語句。這需要原始檔本身括號不平衡,不是合法樣本,所以不列。
- 效能:2000 組 `// BAD` 加 `@Foo(` 共 0.94 秒;20000 層 `@Foo(` 巢狀有跑完。只有刻意構造的輸入才會是平方成長,不列。

**拆函式前後行為**:`_bad_lines` 的問題訊息字串完全相同(`壞例檔 {f.name} 去註解後行數對不上,判不了哪幾行標了 // BAD`),回傳順序也相同,真樣本輸出與修前一致。

**`_unpipe`**:`replace("\\|", "|")` 在 check.py 只剩這一處,呼叫端是 `_snippets` 和 `_unreach_table` 的非整格分支,沒有遺漏。

**新測試的靈敏度**:修前的 `_ANNOTATION_ONLY_RE`(單層括號)擋不了巢狀括號、泛型、`@[…]`、跨行與同行兩個註記,所以新案例在修前會紅。`open.kt` 案例釘住「沒關就回註記行」的分支。
