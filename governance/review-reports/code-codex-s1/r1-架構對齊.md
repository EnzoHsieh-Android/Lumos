## 問題二:命名與錯誤處理

**子問 2a——fail-open/靜默/LUMOS_HOOK_DEBUG 慣例一致嗎?**

不完全一致,minor。`dispatch-lens-hook.py` 的 Claude 路徑 `main()` 對每一個失敗分支(沒有 repo/cwd、找不到 lumos、subprocess 例外、rc≠0、JSON 解析不了)都呼叫一次 `_debug(...)` 留一行 stderr 說明。新加的 `_claim_codex_seat` 只在「沒領到席」這一個分支呼叫 `_debug`,其餘四個提早 return(沒有 repo、找不到 lumos、subprocess 例外、rc≠0、JSON 解析失敗)全部靜默、不留任何除錯線索,跟同檔既有的「每個失敗分支都留一句debug」慣例不同——`LUMOS_HOOK_DEBUG=1` 開著時,Claude 路徑查得到失敗在哪一步,Codex 路徑查不到。
severity: minor
- 引句:「找不到 lumos,放行」
- 對照:`scripts/hooks/claude/dispatch-lens-hook.py:102`(Claude 路徑 `_debug` 覆蓋每個分支)vs `scripts/hooks/claude/dispatch-lens-hook.py:51-66`(`_claim_codex_seat` 對應分支都沒有 `_debug`)

**子問 2b——`_lens_repo_key` 用 realpath 而 `_lens_cache_path` 用原樣字串,兩套 key 算法並存是不是第二種做法?**

是兩套並存,但屬於 S1 表明文要求、且程式碼有寫理由。`_lens_cache_path`(既有,這次沒動)直接把 `git rev-parse --show-toplevel` 吐出的字串接進 sha256;新的 `_lens_repo_key`(armed 目錄用)則先 `os.path.realpath` 再 sha256,理由寫在 docstring(symlink/尾斜線表示法不同會對不上,r1 邊界 F4)。S1 驗收表本身就寫「key=repo realpath 的 sha256 前 32 位」,是有意識的規格選擇——armed 目錄的 key 要跨兩個行程(武裝時的編排者 cwd、認領時的 hook payload cwd)算出同一把鎖,比快取的「同一次函式呼叫內算出的 key」更需要防 symlink 分歧,所以額外加固有功能理由。但 spec 與程式碼都沒有明講「這跟 `_lens_cache_path` 的算法不同」——同一個檔案裡,「repo 路徑→安全檔名 key」這件事現在有兩種寫法,下一個要加類似快取的人可能隨機挑一種抄。
severity: minor
- flag: ⚠(這條要不要算 major,取決於評審把「同檔兩種 key 算法」算不算「第二種做法」——本判斷認為屬於實作細節分歧、非跨層或改變控制流,故列 minor,但保留不同意見的空間)
- 引句:「寫讀兩端同一支:repo 根 realpath 的 sha256(r1 邊界 F4:symlink/尾斜線表示法不同會對不上)。」
- 對照:`scripts/lumos:17106`(`_lens_repo_key`,realpath)vs `scripts/lumos:16818`(`_lens_cache_path`,原樣字串)

**子問 2c——armed 目錄 owner 檢查跟 `_lens_cache_read` 的檢查是不是同一套?**

不是同一套,minor。兩者都在 `~/.cache/lumos/dispatch-lens/` 這個「路徑可預測」的地方(`_lens_cache_read` 自己的註解就寫「$TMPDIR 路徑可預測可偽造」的同類風險),`_lens_cache_read` 除了驗 `st_uid` 是不是自己,還額外擋掉 `group`/`other` 可寫的檔案(防止目錄權限事後被放寬)。新的 `_lens_arm_dir_ok` 只驗 `st_uid`,沒有比照 `_lens_cache_read` 多驗 mode 位元——雖然武裝目錄在建立時就 `chmod 0o700`,但讀端沒有像 `_lens_cache_read` 一樣二次確認,同一威脅模型下防線比既有寫法薄一層。
severity: minor
- 引句:「只信自己 uid 擁有、group/other 不可寫、TTL 內的檔」
- 對照:`scripts/lumos:17120-17129`(`_lens_arm_dir_ok`,只驗 uid)vs `scripts/lumos:16823`(`_lens_cache_read` docstring,uid+mode 位元雙驗)

**子問 2d——回傳三態/JSON 欄位命名一致嗎?**

一致,clean。`cmd_dispatch_lens_claim` 回 `{text, reason, seat, seats, range}`,`reason` 用簡短英文小寫連字號詞(`not-armed`/`not-a-repo`/`broken`/`expired`/`exhausted`/`ok`),跟既有 `_sync_global_hooks` 的三態命名(`ok`/`probe`/`merge-failed`/`absent`)、`--json` 輸出用小寫連字號短詞的慣例同款,沒有另創駝峰或中文鍵名。
severity: clean

## 問題三:第二種做法

**子問 3a——第二個 TTL 機制(armed 600 秒 vs cache 1200 秒 vs impact TTL marker)算不算重複發明?**

不算,clean。三個 TTL 各管不同東西:`_LENS_ARM_TTL_SEC=600` 管「武裝的 token 還有效嗎」(多行程搶佔窗口)、`_lens_cache_read(ttl_sec=1200)` 管「鏡頭內容快取還新鮮嗎」(單一 range 的計算結果快取)、impact-hook 的 `_ttl_marker_path` 管「同一 session 同一檔案的注入冷卻窗」(防洗版)。三者是同一個「TTL 檔案化」手法在三個不同問題上的應用,不是同一個問題被解兩次;600 秒也對得上 S1 驗收表跟計劃筆記寫的「10 分內」,不是隨手挑的數字。
severity: clean
- 引句:「武裝中:{meta.get('range')} 剩 {remaining}/{meta.get('seats')} 席,已過 {age} 秒(TTL {_LENS_ARM_TTL_SEC} 秒,過期自動失效)」
- 對照:`scripts/lumos:17098`(`_LENS_ARM_TTL_SEC = 600`)vs `scripts/lumos:16817`(`_lens_cache_path`/`_lens_cache_read` 預設 1200 秒)vs `scripts/hooks/claude/impact-hook.py:171`(`_ttl_marker_path`,per-session-per-file 冷卻窗)

**子問 3b——第二種「原子認領」:專案有沒有既有鎖/rename 慣例?**

沒有既有慣例,這是本專案第一個「多行程搶佔同一組有限資源」的原子認領機制。全 repo 搜尋 `os.rename`/`.rename(`,`scripts/lumos` 裡只有這一處(另一處 `target.rename(arch)` 是不相干的歸檔邏輯)。既有的 `_lens_cache_write` 用的是「mkstemp+os.replace」這個不同問題的原子寫入慣例(單一寫者寫一份快取,不是多個讀者搶一份有限 token);impact-hook 的 TTL marker 也是單寫者自己標記自己的冷卻窗,不是競態場景。所以 `os.rename(t, t.with_suffix(".claimed"))` 不是「跟既有做法不同的第二種做法」——它是這個問題第一次出現在這個專案,而且是 d3 規格明文要求的機制,不是重複發明。
severity: clean
- 引句:「原子:兩個 hook 同時來只有一個成功(r2 外家 #22/邊界 N3)」
- 對照:`scripts/lumos:17211`(`os.rename` 原子認領)——repo 內查無同型先例(`_lens_cache_write` 是不同問題的 mkstemp+replace 慣例,`scripts/lumos:16836` 起)
