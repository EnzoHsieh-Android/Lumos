# 後端工程提問與證據擴充_計劃

> 白話:讓 Lumos 能帶著 AI 做完一個後端功能的整個過程,但不另蓋一套系統。三件事要補:①開工前 AI 自己找出需求缺口,先自己查,真的要人決定的才問,而且依階段問,不是一開始全丟出來;②知道「這個問題要什麼證據、哪個工具拿得到」,碰真實資料庫或壓測時有權限邊界;③「做完了」要有機器擷取的原始輸出當證據,AI 自己寫的數字不算。示範載體是另開 repo 的高併發訂單系統,但三件事都不綁訂單業務。

## 緣起與現況(2026-10-12 盤點)

- 起點:2026-10-12 使用者在對話中貼了一份任務書(下稱「任務書」,原文沒有進 repo),要 Lumos 延伸成能驅動後端開發全流程的工具,要求先盤點、不重造。本篇用到它的三樣東西:①提問九類——需求、架構、一致性、併發、失敗、擴展、安全、維運、驗證;②七道驗收關卡——需求就緒、架構就緒、實作就緒、功能驗證、可靠性驗證、效能驗證、交付就緒;③示範情境——高併發訂單系統(庫存 100、同時 1000 筆下單不得超賣、冪等鍵、非同步故障、壓測、故障注入)。
- 盤點方式:四個唯讀代理各拿原始問題分頭查(規格與提問、驗證與證據、掛鉤與權限、後端棧與評測),結論都附函式名。以下是摘要;現況以程式碼為準。
- **已經有、直接用**:
  - 計劃筆記+規格閘([[Systems/規格閘]]):依關鍵字判風險,低風險直接做、高風險進多席審查(輪數上限寫在 `_TIER_PARAMS`,滿了交人)。
  - 兩套固定題庫:計劃稿階段的 `_PITFALL_GENERAL` / `_PITFALL_QUESTIONS`(四種風險類,關鍵字觸發),改檔與推送階段的 `_STACK_QUESTION_SPECS`(九種棧,Java 七題,內容源 [[Systems/效能檢核目錄]]);推送前每題表態([[Systems/棧別提問表態閘]])。
  - 合約綁測試、推送前真跑([[Systems/bound-tests-gate]]);破壞測試([[Systems/guard-kill]])在隔離工作目錄把保護拿掉、要求測試變紅——這就是任務書「故障注入」情境要的工具。
  - 決策紀錄(`cmd_decision_add`):內容、背景、理由、日期、有效與否。
  - AI 行為評測(情境探針,[[Systems/ablation-lumos-first]]):無人看守地出題、用規則判工具呼叫順序。
- **部分有、要擴**:
  - 驗證筆記的狀態只有 pass/stale/superseded/pending/abandoned(`_STATUS_ENUM`),寫不出「失敗」;新建範本預設 pass;原始輸出、環境、預期對實際只在正文散文裡。
  - 決策紀錄沒有「回答哪一題、誰決定、否決了哪些選項」三個欄位。
  - 工具呼叫紀錄([[Systems/lumos事件帳]] 那個外掛)只記指令前 500 字,不遮蔽敏感資訊。
- **完全沒有**:
  - 拿需求找缺口、排優先、分階段出題(計劃稿題庫只看關鍵字,`--check` 只驗有沒有〈實務隱患〉小節)。
  - MCP 整合、工具能力清單、工具權限政策(唯一的工具限制在審查子代理身上,見 [[Systems/lumos-guard]])。
  - 破壞性操作要人核准、敏感資訊遮蔽。
  - 「計劃標完成前必須有對應證據」的檢查。
  - Spring Boot、Docker、壓測、應用可觀測性的支援;任何示範後端專案。

## 做法

### A. 情境出題(Question Orchestration)

- **題目住哪**:計劃筆記新增一節 `## 待決問題`,一題一行:
  `- [Q3] <問題> [類:併發][階段:實作][答:人|自查|工具][阻塞][狀態:待人] → <決策或證據連結>`
  - `類` 用任務書的提問九類(見緣起)當起始值域,允許專案在設定裡擴充;`階段` 取 需求/架構/實作/驗證/效能/交付。
  - `狀態` 取 待查/自答/待人/延後/已決/已驗;「延後」必附理由,「已決」必連到一條決策(`#dN`),「已驗」必連到一筆證據列。
- **題目從哪來**:題庫不給固定題目,給「風險面」——每個風險面是一個觸發條件(需求詞或程式碼特徵)加一句「要釐清的是什麼」,AI 依當下需求、既有決策、程式碼、MCP 查得到的事實,寫成具體問題。風險面放進既有的計劃稿題庫(`_PITFALL_QUESTIONS` 那一族)新增一個「後端資料與交易」類;這會改那份題庫的形狀——現有四類的值都是固定題目字串,新類的值是「觸發條件+要釐清什麼」,讀它的程式要能分辨兩種。內容源寫進 [[Systems/效能檢核目錄]],不另開題庫。
- **先查後問**:每題出生時先標「誰答得了」。答得了的(圖譜、程式碼、工具查得到、規格推得出、有安全預設)AI 自己答並標「自答」附出處;只有業務規則、成本、風險接受度、不可逆決定、產品行為,且證據定不了的,才標「待人」。
- **排序規則(透明、不打分)**:待人的題目依序:①標了阻塞的 ②不可逆的 ③影響跨多個模組的 ④其餘。一次最多問人三題,其餘留到下一輪,避免連續轟炸。
- **時機(新做)**:現行 `lumos pitfalls <計劃>` 沒有階段概念、一律全列;本案新增 `--stage` 參數與「風險面→階段」對照,只列那個階段的。階段由呼叫它的關卡帶入,不靠 AI 自報:規格閘帶需求與架構;交付前證據檢查帶驗證、效能、交付;實作階段由人或 AI 在動手前跑 `lumos pitfalls <計劃> --stage 實作`(`pitfalls --diff` 只收改動範圍、不接計劃,不改它)。
- **機械把關**:規格閘讀這一節——還有標阻塞、狀態是待查或待人的題目,規格閘不放行;交付前證據檢查讀這一節——標了要驗的已決題沒有證據列,不放行。
- **先量再接**:A 塊的程式(S1–S3)動工前,先用情境探針做最小對照:同一組刻意不完整的後端需求(至少 6 題,含任務書的訂單需求與兩題非訂單業務),甲組照現行流程、乙組多帶風險面與〈待決問題〉寫法,各跑 3 次,判準=事先寫好的「該被問到的人決定」清單命中數與「不該問人卻問了」的題數。乙組命中沒有多於甲組、或亂問題數多於甲組,A 塊不接進規格閘,只留寫法說明,並回報人裁。
- **決策紀錄擴三欄**:`cmd_decision_add` 加選填的 `--answers Q3`、`--by <誰>`、`--rejected "<不選的方案>"`(可重複),寫進同一條決策;舊決策缺欄照舊合法。

### B. 工具能力與權限(MCP Orchestration)

- **能力清單**:放在專案設定 `.lumos/config.json` 的 `capabilities` 區塊,每項 `{能力, 提供者(MCP 工具名前綴或 CLI 指令), 權限(READ/WRITE/EXECUTE/ADMIN), 用途, 拿得到什麼證據}`;說明與挑選理由寫進新開的 「證據擷取」系統筆記(第 3 階段新開)。
- **`lumos capabilities`**:唯讀,列每項能力現在可不可用(MCP 看 `claude mcp list`、CLI 看指令在不在)與權限等級;問題要的證據對不到可用能力時,印出替代(CLI/SDK)並要求把替代理由寫進證據列。
- **權限邊界**:WRITE/EXECUTE/ADMIN 等級的 MCP 工具,由 Lumos 產出建議的 Claude Code 原生 `permissions.ask` 條目讓人貼進設定(要不要讓安裝器自動寫,見待決問題 Q1);正式環境的連線設定一律標唯讀,能力清單裡不准出現正式環境的 WRITE 項。
- **防失控**:MCP 呼叫的重試由 Claude Code 自己跑,Lumos 管不到單次呼叫;Lumos 管的是「證據層」——工具失敗會變成證據帳上的 BLOCKED 或 FAIL 列,停止條件一律照 E 以「條款」計數,不另設以能力為單位的計數。

### C. 證據擷取與驗證狀態(Evidence-Based Verification)

- **`lumos evidence run`**:`lumos evidence run --verify <驗證節點> --criterion <計劃>#S3 [--env <環境名>] [--expect <判準>] -- <指令>`。
  - 由 Lumos 代跑指令,把 stdout/stderr 原樣存成原始檔,寫一列進證據帳:證據編號、需求(計劃條款)、驗證節點、執行工具、環境、時間、程式版本(HEAD)、指令、退出碼、預期、實際摘要、結果、原始檔位置。
  - 結果只由退出碼與 `--expect` 判準機械決定(PASS/FAIL);指令跑不起來或逾時判 BLOCKED;AI 不能手填結果。
  - 存檔前遮蔽:環境變數裡名字像 TOKEN/PASSWORD/SECRET/KEY 的值、連線字串裡的密碼,一律換成遮罩。
  - 原始檔有大小上限,超過只存頭尾並標截斷。
- **證據帳要被追蹤**:不能像 kill-log 一樣被消費專案的忽略清單擋掉(那會讓 CI 讀不到,[[Projects/併發與效能表態要合約背書_計劃]] 踩過)。
- **驗證筆記狀態**:`_STATUS_ENUM` 的 verification 加 `fail` 與 `blocked`;既有 `pending`(程式註解的語意是「預告了還沒做」)沿用為「未驗證」,不另造新詞;`lumos new verification` 範本預設改成 `pending`,範本裡的 `status/pass` 標籤同步改 `status/pending`。範本改預設與下一條的 pass 限制必須同一個提交(不然新筆記一出生就是 pass,限制碰不到)。
- **pass 要有證據**:2026-10-19 之後新建的驗證筆記,狀態要設成 pass,證據帳裡至少要有一列指向它、結果 PASS、版本等於當時 HEAD,或證據列的版本是 HEAD 的祖先且之間只動簿記檔(沿用 `_codeloop_record_valid` 的判法:簿記檔以 `_BOOKKEEPING_FILES` / `_BOOKKEEPING_DIRS` 兩份名單為準,簿記資料夾裡的程式檔不算);證據帳與原始檔目錄要加進這兩份名單,不然每提交一次帳檔,帳上的證據就全部過期。這兩份名單另有小改動閘、風險掃描、推送前測試範圍三個使用者,加名單時三者的對照測試要一起跑。舊的驗證筆記(2026-10-12 機械數:`status: pass` 276 篇,驗證筆記共 295 篇)不追溯。
- **繞過 `lumos set` 的寫法**:手改開頭欄位把狀態寫成 pass 繞得過 `lumos set`;lint 對 2026-10-19 之後新建、狀態 pass、證據帳沒有有效列的驗證筆記報錯,提交時的 lint 關卡就擋得到。
- **MCP 拿到的資料怎麼變證據**:用等價的 CLI 走 `evidence run` 重跑一次留原始檔;MCP 的回傳值本身不當證據(事件帳外掛不存回傳值,見 Q3)。

### D. 七道關卡對到哪裡

| 任務書的關卡 | 落在 | 新增什麼 |
|---|---|---|
| 1 需求就緒 | 規格閘 | 讀〈待決問題〉,阻塞未決不放行 |
| 2 架構就緒 | 規格閘+多席審查 | 決策紀錄的「不選」欄;Kafka/Redis 這類要有比較 |
| 3 實作就緒 | 表態閘 | 棧別題庫的 java 題組補 Spring 觸發詞(看改動行);「後端資料與交易」風險面屬 A 塊、住計劃稿題庫,不在這一關 |
| 4 功能 / 5 可靠 | 綁定測試+破壞測試 | 無,沿用 |
| 6 效能 | 證據擷取 | k6 輸出走 `evidence run`,只當交付證據 |
| 7 交付 | 交付前證據檢查 | 新寫:擴 `spec-trace` 認 `[evidence:]` 綁定 |

- 依需求啟用:關卡 5 的非同步那半、關卡 6 只在計劃條款有對應項目時才檢查;沒有條款就不檢查,不另做開關。

### E. 失敗後的修復迴圈與停止條件

- 證據帳就是迴圈的計數器:同一條款連續兩列 FAIL、而且失敗原文摘要(去掉時間與路徑後的雜湊)相同,判「同樣修法無效」→ 停,印出交人提示。
- 同一條款累計三列 FAIL,不論原因都停。
- 拿不到證據(BLOCKED)不准把驗證筆記設成 pass,也不准把計劃設成 done。
- 修復前後對照:同一條款的 FAIL 列與之後的 PASS 列都留在帳裡,交付報告直接從帳產生前後對照。

### F. 示範 repo 與 AI 評測

- 示範 repo:Kotlin + Spring Boot + PostgreSQL 模組化單體起步,Docker Compose 起本機環境,JUnit + Testcontainers 驗併發與冪等,k6 壓測;Redis、Kafka 由示範流程本身依需求判斷要不要加,判不需要就照實寫。
- AI 評測:沿用情境探針加一組後端題(不完整需求、矛盾需求、不必要的技術、工具不可用、證據不足等),判準用規則比對工具呼叫與待決問題小節的內容;另加既有探針題當回歸組,確認原工作流沒被破壞。

## 實務隱患

- 併發:證據帳是逐列追加的共用檔,同一工作目錄多個程序同時寫會交錯——沿用既有帳檔的追加寫法與原子寫入慣例,S5 的測試要涵蓋兩個程序同時寫。
- 資源:原始檔可能很大(壓測輸出),設大小上限並截斷,見 C。
- 秘密:遮蔽規則只抓常見命名,抓不到自訂名稱的秘密——示範 repo 的連線資訊一律走環境變數,並在 「證據擷取」系統筆記(第 3 階段新開) 寫明遮蔽的邊界。
- 不可逆:MCP 與 `evidence run` 都能對真實系統下指令,刪表、刪 Topic、大量刪 Redis key 做了回不去。處理:能力清單禁止正式環境出現 WRITE 以上等級(S11);寫入類 MCP 工具一律走 Claude Code 原生的「每次詢問」(B);示範 repo 只連本機 Docker 環境;`evidence run` 只記錄、不替指令背書安全,破壞性指令照 Claude Code 既有權限確認。
- 已排除:金流:本案與示範都不含付款流程(訂單只到建立與扣庫存)。
- 已排除:對外送出:證據擷取與壓測只打本機環境,不寄信、不推通知、不呼叫第三方;k6 目標限定 localhost 寫進示範 repo 的壓測設定。
- 守衛面:本案會改規格閘、`lumos set` 與 `spec-trace` 的判定,誤擋會訓練人繞過——每個新判定都要有「舊行為不變」的對照測試(S4 的位元相同、S8 的舊筆記不受影響),並各自一個提交以便單獨回退。條款新認 `[evidence:]` 不只改 `spec-trace`:合法標籤集合 `INV_TAG_RE`、規格閘的條款文法檢查都要同步,S10 的測試要涵蓋三處。
