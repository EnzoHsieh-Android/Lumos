## 問 1:分層與依賴方向

### 1-1 `_loop_records` 新 helper vs `cmd_loop_next` 既有讀帳迴圈——同一件事兩份實作

`cmd_loop_next` 從第一天就有一段內嵌讀帳迴圈(`scripts/lumos:6185-6197`,本 patch 未動這段,只在它後面插入新邏輯):

```python
rounds = []
try:
    if path.exists():
        for line in path.read_text(encoding="utf-8").splitlines():
            ...
            if d.get("loop") == loop_id:
                rounds.append(d)
except OSError as e:
    print(f"擋下:檔案讀不到({e}): {path}", file=sys.stderr)
    return 2
```

本 patch 在 roster 區新增 `_loop_records(env, loop_id)`(`scripts/lumos:5795-5811`),邏輯**逐行等價**於上面這段(差別只在 `OSError` 時是印錯回 2 還是靜默回已收集的 `out`)。它只被 `cmd_canary` 的 orchestrator 定錨檢查呼叫一次(`scripts/lumos:4148`);`cmd_loop_next` 本身——**本 patch 也改到的那個函式**——仍然用自己那段舊的內嵌迴圈算 `rounds`,沒有改成呼叫新 helper。

結果是:改動後,「給我這個編號的全部記錄」這件事,在同一個檔案裡有兩份手寫實作並存,一份被 `cmd_canary` 用、一份被 `cmd_loop_next` 用,邏輯目前一致是巧合不是機械保證——以後任何一邊修 bug(例如壞行判斷、`OSError` 語意)沒有同步改另一邊,兩處對「這個編號的第一筆 `orchestrator` 是什麼」就可能算出不同答案,而這正是本功能存在的目的(定錨防漂移)所要保護的東西。

這不是「這個 repo 本來就允許到處重寫讀帳迴圈」的舊慣例延伸(那類重複多半彼此篩選條件不同,例如 T6 定錨檢查 `scripts/lumos:4336-4352` 篩的是 `findings_set` 存在與否,不是同一件事);這一次是**同一次 diff 裡、同一個查詢目的**,新寫一份又沒讓既有那份用上,屬於引入第二種做法。

severity: major
引句:「canary-log 裡某編號的全部記錄(唯讀;壞行跳過)。」

## 問 2:命名與錯誤處理

### 2-1 `_ORCHESTRATORS` vs `LOOP_TIERS`——前導底線不一致

`_ORCHESTRATORS = ("claude", "codex")`(`scripts/lumos:5791`)扮演的角色跟 `LOOP_TIERS = ("light", "standard", "high")`(既有,`scripts/lumos:3865`)完全同構:都是「首筆記錄定錨、之後不可換」旗標的合法值域,都在 `cmd_canary` 與 `cmd_loop_next` 兩處各被 domain-check 一次,錯誤訊息也是同一個模板(`只能是 {'/'.join(X)}`)。但 `LOOP_TIERS` 不帶底線(檔案裡不帶底線的模組常數是少數,通常給「跨多個子系統廣泛引用」的詞彙用,如 `CLUSTER_STATES`/`GUARD_TYPES`),`_ORCHESTRATORS` 帶底線(檔案裡多數常數這樣命名,通常是給「只被少數幾個函式用」的範圍用,如 `_ROSTER_EXTERNAL_KEYS`)。`_ORCHESTRATORS` 的實際使用範圍(`cmd_canary`+`cmd_loop_next`+人讀輸出格式化)其實跟 `LOOP_TIERS` 一樣廣,卻採了窄範圍的命名慣例——是它結構上最像的對照物沒對齊,不是嚴重問題,但值得記一筆。

severity: minor
引句:「_ORCHESTRATORS = ("claude", "codex")」
### 2-2 domain-check 錯誤訊息漏「之一」

既有 `--tier` domain-check(`cmd_canary`,不在本 patch 改動範圍但同一函式):

```
擋下:--tier 分級只能是 {'/'.join(LOOP_TIERS)} 之一,你給的是 {tier!r}
```

新 `--orchestrator` domain-check(`cmd_canary` `scripts/lumos:4145`、`cmd_loop_next` `scripts/lumos:6226`,兩處逐字相同):

```
擋下:--orchestrator 只能是 {'/'.join(_ORCHESTRATORS)},你給的是 {orchestrator!r}
```

同一個錯誤訊息模板,新的兩處都少了「之一」兩字。純措辭差異,不影響理解,但既然緊挨著同一函式裡的姊妹檢查,照抄一字不差比較符合這個檔案一路以來「同類擋下訊息共用句式」的慣例。

severity: minor
引句:「擋下:--orchestrator 只能是 {'/'.join(_ORCHESTRATORS)},你給的是 {orchestrator!r}」
### 2-3 `_roster_family` 回傳字串仍是 "claude"/"external",語意變成同門/外家

docstring 自己講得很清楚:

```
family 是★相對編排者★的:"claude"=同門(編排者那一家)、"external"=外家
(保留舊字串,_TIER_ROSTER 的 family 欄同義:claude 席=同門席、external 席=外家席;d4 相對化 2026-09-04)
```

這是**有意識偏離**,不是疏漏——理由站得住腳:改字面值要連動 `_TIER_ROSTER` 整張表(`scripts/lumos:5745` 起,十幾個 seat 定義都寫死 `"family": "claude"`/`"external"`)、`_roster_observe` 裡所有 `f == "claude"`/`f == "external"` 比對、以及既有測試斷言,牽動面遠超出這次 S2 該動的範圍;而且人讀輸出層(`cmd_loop_next` 的 `_fam` 組字、`_roster_observe` 的 `_quiet` 訊息)都已經正確轉譯成「同門[X]」/「外家(不是 X 那一家)」,不會讓終端使用者被裸字串誤導。唯一還帶著舊語意的只剩機器可讀的 JSON/raw 輸出與原始碼閱讀者——這個代價在 docstring 裡明白承認了,判「有意識偏離」,不判「該改名」。

severity: clean
引句:「family 是★相對編排者★的:"claude"=同門(編排者那一家)、"external"=外家」

## 問 3:第二種做法

### 3-1 編排者判定有沒有第二套來源

查過 hook 端的 `--harness`(`scripts/lumos:11271` 起 `_sync_global_hooks(src_repo, harness)`、`_HARNESS_HOME`、`_teardown_global_hooks`)——這個旗標管的是「安裝/同步 hook 註冊時寫進哪個設定檔、hook 命令列印哪個標籤」,是**機械偵測**(哪個事件觸發就是哪個 harness,SessionStart/PreToolUse 給 Claude,SubagentStart 給 Codex),跟本 patch 的 `--orchestrator`(**人工自報**、寫進 `.canary-log.jsonl` 定錨)是完全不同層:一個管「這台機器上哪支腳本該接哪個 CLI 的鉤子」,一個管「這個審查編號由誰主編、外家席該對照誰」。逐一查過 `dispatch-lens`(`--arm`/`--claim`/`--disarm`/`--status`,`scripts/lumos:17208` 起)也沒有另一套「誰在編排」的判斷邏輯——它的分流靠 hook 事件類型(PreToolUse vs SubagentStart)硬編,不讀、也不寫 `--orchestrator`。兩條路徑互不讀寫對方,沒有找到會分岔的第二套來源。

severity: clean
引句:「誰在編排(claude|codex;零記錄必填、不預設;有帳面定錨須一致)——外家席=不是編排者那一家(d4)」

## 另一問:實作是否與 d4 一致——「record/status 讀帳缺=擋」

d4 決策文字(`docs/lumos-toolchain-knowledge/Projects/Codex完全支援_計劃.md:48`)寫的是:「`loop next` 首輪必帶 `--orchestrator`……**`record`/`status` 讀帳缺=擋**」。逐行核對本 patch:

- `cmd_loop_next`(`scripts/lumos:6238`)確實有 `if not rounds and orchestrator is None:` 擋下——這條做到了。
- `cmd_canary` 的整段 orchestrator 邏輯(`scripts/lumos:4143`)包在 `if orchestrator is not None:` 底下——**沒給 `--orchestrator` 這段完全不執行**,不會因為「這是這個編號的第一筆、卻沒帶 orchestrator」而擋下,只有「已經定錨過、這次給的值跟定錨不同」才擋。也就是說,對一個全新編號直接呼叫 `canary record`(跳過 `loop next`)完全可以不帶 `--orchestrator` 成功寫入,orchestrator 欄從頭到尾不會被寫進帳。
- `loop status --roster`(`_roster_observe`,`scripts/lumos:5891-5894`)讀到缺欄時**印一句就過**(「編排者 帳面沒記,視為 claude」+「(舊帳相容;新迴圈 loop next 首輪要帶 --orchestrator)」),不擋、不影響 rc——這跟 `_roster_tail`/roster 全段「advisory 恆不影響 rc」的既有設計原則是一致的(`t_loop_status_roster_check` 也釘死這條:`rc 與不帶 --roster 完全一致`),但也代表它確實不是「缺=擋」。

所以「record/status 讀帳缺=擋」這句話,**只有 `loop next` 真的做到,`record` 和 `status` 都沒做到**——這是實作與決策文字之間的真實落差,列出來。

不過把它放進「架構是否自洽」的框架裡看,結論要分兩層:①**跟這個 repo 既有架構比,`cmd_canary` 這樣寫其實是蕭規曹隨**——`cmd_canary` 對 `--tier` 從來就沒有「這個編號第一筆缺 tier 就擋」的檢查(只驗值域,不驗「有沒有給」),`--orchestrator` 照抄了這個既有的寬鬆前例,沒有無中生有另立規矩;真正在做「零記錄必填」把關的一直只有 `cmd_loop_next`,`--orchestrator` 完全複製了 `--tier` 的分工。②**但這正是 d4 想堵的洞沒堵嚴**——d4 的 why_chosen 明講「預設 claude 會讓 Codex 編排漏旗標時靜默套錯家族」,如果操作者不照 skill 教的順序先跑 `loop next` 就直接 `canary record`(例如腳本化寫帳、或人手漏一步),這個編號整本帳可以永遠沒有 orchestrator 定錨,`--roster` 也只會客氣提醒一句、不會擋——跟決策文字想避免的「靜默套錯家族」是同一種失效模式,只是入口換了一個。實務上三支 skill 都教「每輪開頭先 `loop next`」,把這個缺口用工作流程紀律頂住了,但沒有機械擋。

severity: minor
引句:「if orchestrator is not None:」
