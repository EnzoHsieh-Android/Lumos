## Findings

### f1 — blocker

spec 段落:設計 2,67-69 行。

引句:「★建好後刪沙盒內全部審計脈絡(v5-r1 s2 抓到兩個漏):`governance/review-reports/`、`governance/pending/`、`governance/l4-audit/`、`docs/.governance-log.jsonl`、`docs/.canary-log.jsonl`(=治理帳+審計產物整組;列舉入測試)★」

問題:`make_sandbox`(scripts/scenario_probe.py:91-109)在 rsync 完之後立刻 `git add -A` + commit 成「乾淨狀態」,回傳的 `work` 已經是一個乾淨 HEAD。67-69 行要求「建好後」再刪這五項,但只講刪、沒講刪完要不要再 commit 一次。範圍刀(83 行)用的是 `git -C <sandbox> diff --name-only`——裸 `git diff`,比的是工作樹相對索引(=剛才那個乾淨 HEAD)的未提交改動。若刪除這五項後不補一次 commit,這五項的刪除本身就會**永遠**留在裸 `git diff` 的輸出裡,跟修 agent 之後動的那一篇筆記混在一起。

實查:五項裡有四項是 git 追蹤的——`git ls-files` 逐項算出 `governance/review-reports/` 520 筆、`governance/l4-audit/` 61 筆、兩份 `.jsonl` 各 1 筆,共 **583 筆追蹤中的檔案**;`governance/pending/` 因 `governance/.gitignore:6` 整個被 `pending/` 規則忽略,不進索引(`git check-ignore -v` 已核對),故這一項的刪除本身不會污染 diff,但 rsync(94-95 行的 `--exclude` 只排 `node_modules`/`.venv`)不看 `.gitignore`,仍會把 `governance/pending/` 底下既有內容實體複製進沙盒——見 f5。

後果不只是⑧(範圍刀越界測試)這一條:如果沒有那個補 commit,**任何一次派工只要清了這五項就必然在 `git diff --name-only` 裡看到 583 筆刪除**,跟修 agent 動的那一篇筆記合在一起,範圍刀「與 repo_rel 嚴格相等」(66/83 行)這個判準永遠不可能只等於一篇——等於④/⑤/⑥/⑦這幾條測⑤PASS路徑、⑥FAIL修復鏈路徑,只要牽扯到範圍刀比對就會被誤判越界,整條自動閉環的 happy path 都跑不動,不是只有邊界情境⑧受影響。

本輪另一位審稿人(`governance/review-reports/selfaudit-loop-v5/r2-ext.md` finding #1)已獨立用 `git clone` + 實刪 + `git diff --name-only | wc -l` 的最小重現腳本抓到同一件事,我用 `git ls-files` 交叉核對追蹤檔案數字一致(583),確認不是誤讀。

建議:`make_sandbox(repo)` 回傳 `work` 後,selfaudit.py 自己 `shutil.rmtree`/`os.remove` 四個追蹤路徑與兩份 jsonl(+`governance/pending/` 走實體刪除,見 f5),再補一次 `git add -A && git -c user.name=... -c user.email=... commit -qm "strip audit context" --no-verify`(比照 `make_sandbox` 自己 106-109 行「改動後 commit 成乾淨狀態」的既有手法,不是新發明的模式),讓範圍刀真正比較的基準點是「已清空審計脈絡的 HEAD」。這件事目前 13 條測試裡沒有一條直接斷言「清完之後 `git status --porcelain` 是空的」,建議補上(可以併進②的沙盒建置測試,或獨立一條)。

### f2 — major

spec 段落:設計 4,週帳,97 行。

引句:「★整段「讀配額→派工→終局 append」用 `fcntl.flock` 鎖週帳檔★(標準庫零依賴;同日兩進場不超額,v5-r1 s2f9/Codex f4)」

問題:這句話字面上把「派工」(`subprocess.run(timeout=900)`,可能一輪疊多次到 45 分鐘量級)也包進鎖的臨界區。如果真的照字面實作(鎖橫跨整個派工),兩個「同日兩進場」的 selfaudit 呼叫會彼此互等到逾時或排隊到下一輪——不是「同時獨立跑、只在讀寫配額那一刻互斥」,而是變相序列化整條每日 loop,這跟 spec 沒明講的意圖可能不符,也沒被任何一條測試釘死。

更關鍵的是選派(挑哪幾篇 stem)有沒有算進臨界區:如果每個行程各自先在鎖外做完「選中要派哪幾篇」(讀候選清單、排 PR 序、決定要動哪個 stem),才在鎖內做「append started」,那麼配額本身不會超(鎖保護了計數正確),但**兩個行程完全可能各自獨立選中同一篇 PR 最高的筆記**,兩邊都對同一個 stem append 各自的 started 行、各自建沙盒派工——鎖只擋「總數超額」,不擋「同一篇被派兩次」。這正好命中 selfaudit 本身最想避免的風險(同一篇筆記被兩個沙盒同時修,事後回寫柵欄那邊會二選一 stale,但已經多燒一次真派工的成本,行為也未定義)。

spec 沒有講清楚鎖的臨界區邊界包不包含「重新讀一次本週 started 行 → 決定接下來要派哪些 stem」這個選派決策本身,也沒講是用阻塞式(`LOCK_EX`,願意等)還是既有先例的非阻塞快速失敗(`LOCK_EX|LOCK_NB`,`governance/eval/refresh_labels.py:62`)。兩種選擇下,測試③「模擬兩進場不超額」要斷言的具體現象完全不同(前者斷言第二個行程會等;後者斷言第二個行程立刻報錯退出、不寫任何 started 行)。

建議:明講鎖的臨界區至少要涵蓋「重讀 started 行數→決定本輪要派哪幾個 stem→把這些 stem 的 started 行寫入」這一整段選派決策(派工 subprocess 本身留在鎖外),並二選一阻塞/非阻塞模式(建議比照既有先例走非阻塞快速失敗,行為單純、易測);測試③要順帶斷言「兩個行程不會選中同一個 stem 各自 append 一次」,不是只驗總筆數沒超額。

### f3 — major

spec 段落:測試草案③,130 行。

引句:「★flock:模擬兩進場不超額★」

問題:同一個 Python 行程裡如果用**同一個** file handle 對同一個週帳檔連續呼叫兩次「選派」邏輯(圖省事沒真的另開一個 subprocess 或另一個獨立 `open()`),`flock` 不會擋自己——我實測過:同一個 fd(同一個 open file description)第二次 `flock(LOCK_EX|LOCK_NB)` 永遠立刻成功,不會擋自己;只有各自獨立 `open()` 兩次(兩個獨立 open file description)才會真的互斥、第二個才會等待或報 `BlockingIOError`。如果測試③圖方便共用同一個 handle 模擬「兩進場」,鎖形同虛設、測試會綠但完全沒驗到互斥——這正是本案 r2/r3 教訓反覆講的「宣稱層安全」在測試層的翻版,只是換了個地方。

repo 既有先例已經示範了正確寫法:`scripts/test_lumos.py:21306-21318`(`t_refresh_atomic_and_lock`)測試行程自己先 `open(str(gpath)+".lock"); fcntl.flock(lock, LOCK_EX)` 占住鎖,再用 `subprocess.run` 真的另開一個行程去跑會碰鎖的 CLI 路徑,斷言 rc≠0 且檔案內容沒變。

建議③沿用同一手法:至少每個「進場」各自獨立 `open()` 該週帳檔(不要共用同一個 handle),理想上比照既有先例用真的 `subprocess.run` 撞鎖(不是同行程內兩次函式呼叫),測試草案目前的敘述沒講清楚要用哪種手法,implementer 很容易抄近路寫出一條假綠測試。

### f4 — major

spec 段落:設計 4,88-92/94-98 行;測試草案③,130 行。

引句(跳過判定):「跳過判定=pending/selfaudit/ 未歸檔檔案(可逆,d2)」;引句(週帳):「★派工前先 append kind=started」

問題:設計節把「pending 存在跳過」跟「派工前 append started」寫在不同段落,沒講清楚每篇候選筆記走這兩道關卡的先後順序。如果實作把「配額計算+append started」放在「檢查 pending 是否存在」之前(比如貪圖把配額扣減和 stem 選定都塞進同一段鎖裡,選完才發現這篇其實有未歸檔 pending 該跳過、再回頭作廢),就會出現「有 pending 卡著的筆記還是吃掉了一次週配額」的浪費——這篇本來就不該進入候選池,鎖再怎麼保護配額計算的原子性也補不回浪費掉的一次額度。

對照既有 `gap_select.select`(governance/autonomous_loop/gap_select.py:59-67):pending 檢查是在候選/選派最外層先做、不成立就整批 `return None`,不會混進後面的取值邏輯——但那是 r1 已經 blocker 過的「連坐」模式(任何一個 pending 檔擋掉全部選派),selfaudit 這次要的是「不連坐」的逐篇獨立檢查(r1 教訓 B),不能照抄同一個函式,只能借用「pending 過濾在配額扣減之前」這個順序原則,用在逐篇 filter 上。

建議:選派管線裡把「候選清單先過濾掉 pending 命中的 stem」寫成明確的第一步(純粹讀檔案系統存在性,不需要鎖),配額計算與 `started` 預約放在過濾**之後**、且在鎖內;測試③目前把「pending 存在跳過」與「flock 模擬兩進場」列成兩個並列小項,沒有一條交叉斷言「有 pending 的那篇不會產生 started 行、不佔配額」,建議補這條交叉檢查。

### f5 — minor

spec 段落:設計 4,週帳,95-96 行;測試草案③,130 行。

引句(設計節):「有 started 無終局=視同 abort 補記」;引句(測試草案):「★started 無終局=視同 abort 不重派★」

問題:兩處寫法在「配額計算」上結果一致(quota = N − 本週 started 行數,孤兒 started 行本身已經佔了額度,不需要真的補寫一行 kind=abort 才能算對配額),但在「稽核帳本完整度」上不一致——設計節的「補記」讀起來是要主動 append 一行 `kind=abort` 進週帳 jsonl,測試草案的「不重派」只講行為結果,沒提要不要真的落盤補這一行。如果實作選了「只在記憶體判斷、不落盤」,週帳裡會永遠留著一個沒有終局 kind 的孤兒 `started` 行,任何事後用 kind 分布做觀測(比如巡檢「這週有幾個 abort」)的人或腳本會看不到它,跟 spec 自己在 96 行列出的 kind 枚舉(`started/done/fail/abort/stale/nag`)暗示「每個 started 最終都該配到一個終局 kind」的期待不一致。

建議把「補記」二字講清楚是不是要真的 append 一行 `kind=abort`;若要,測試需要斷言 jsonl 多出這一行(且 `ts` 是偵測當下、不是原 started 的時間);若不要,設計節的措辭要改成跟測試草案一致的「視同」(僅邏輯判斷,不落盤)。

spec 段落:設計 2,67-69 行;`governance/.gitignore:6`。

引句:「刪沙盒內全部審計脈絡…`governance/pending/`…」

### f7 — blocker

spec 段落:全篇設計節;測試草案⑤,131 行。

引句:「★另造主樹派工後被改場景→PASS 也擋下、kind=stale★」

問題:spec 除了 `_self_audit_lists(notes) -> (missing, stale)` 一個函式簽名外,沒有給選派/派工/VERDICT/回寫柵欄/週帳這條管線任何具體的函式切口。但測試草案(126-128 行)明講「直接 import selfaudit.py」「派工層注入假 runner」——這種測法**要求**管線至少拆成幾個獨立可呼叫、可各自灌入手造資料的函式,否則像⑤要的 fixture 幾乎無法乾淨地寫:它需要在「dispatch 那一刻對主樹算好快照 sha」和「複審/PASS 後真正回寫比對」這兩個時間點之間插入一個「改動主樹檔案」的動作。如果 dispatch(建沙盒/跑 agent/算 sha)和 writeback(比對/commit/戳記)被寫成同一個函式裡首尾相連、中間夾著一次 900 秒 `subprocess.run` 的步驟,測試唯一能插入改動的辦法是對一個真跑的長 subprocess 掐時序競態——不現實,也不是測試草案「注入假 runner」想要的那種確定性測法。

以目前 spec 給出的資訊量,測試⑤字面上要求的 fixture **無法**被可靠地寫出來,這不是「implementer 自己會想辦法拆」可以帶過的細節——它直接決定測試草案 13 條裡至少①③⑤⑥⑦⑫⑬這幾條(牽涉快照 sha、假 runner 注入、逐分支清理、翻紅釘)能不能真的被寫成單元測試,還是只能退化成又慢又脆的端到端真跑。

建議至少切出這幾個獨立函式(不預設實作細節,只定切口):
- `snapshot_sha(path) -> str`:dispatch 跟回寫柵欄比對★必須呼叫同一份實作★,不要兩邊各自重寫一次 sha256——這也是預防 r1 f1 已經 blocker 過的「演算法不對稱」(左邊 sha256、右邊語焉不詳的「sha」)在這一輪重演的根本做法,不是額外要求。
- `dispatch(repo, stem) -> (verdict, sandbox_path, snapshot_sha)`:只管建沙盒(含 f1 的清context+補commit)、跑 agent(可被 monkeypatch 的 runner 注入點)、讀 VERDICT,不碰主樹寫入。
- `apply_write_fence(primary_path, snapshot_sha, new_bytes) -> "committed"|"stale"`:純函式,拿到手動製造的 `snapshot_sha`(不管是不是跟主樹現況相符)就能單獨測,不必真的跑過一次 dispatch——⑤的 fixture 因此變成「造一個過期的 snapshot_sha 直接餵給這個函式,斷言回 stale、主樹沒被寫」,幾行就能寫完。
- `cleanup_sandbox(work)`:獨立函式,⑫要求「逐分支都清」時能在每個分支測試後面直接斷言這個函式被呼叫過(或沙盒目錄確實消失),不必逐分支重新推導清理邏輯有沒有埋對位置。

### f8 — major

引句:「⑫沙盒清理:跑完父目錄不殘留(make_sandbox bug 的回歸)」
