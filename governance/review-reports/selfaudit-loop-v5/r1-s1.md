## ①容器統一後「審計/修復/複審看同版」的宣稱

已讀,無 finding——設計 2(60-69 行)「每輪 `make_sandbox(repo)` 建沙盒…審計/複審 agent…修 agent 加 Edit」讀下來是「一輪派工建一個沙盒,審計/修復/複審三個 subprocess 依序共用同一個沙盒目錄」,不是三階段各自重建。範圍刀 `git -C <sandbox> diff --name-only`(74 行)天然是相對同一個「派工快照」commit 算 diff,版本基準單一,r3 worktree 那版「審計看 rsync 現況、修復看 worktree HEAD」的版本歪斜結構性不會重演。這條 delta 本身站得住。

但這個「同版」保證只在**沙盒內部**成立;一旦要把結果帶回主樹(PASS 蓋章 / FAIL 回寫),主樹自己的版本會不會在派工期間漂移,沙盒內的一致性完全保證不了——這正是下面 f1/f2 在講的事。

## 八步與 d1/d2/d3 的一致性

大部分一致:d1「FAIL 路徑改全自動」對應設計 4 的修復鏈;d2「pending 檔存在即跳過,可逆」對應設計 4「跳過判定=pending/selfaudit/ 未歸檔檔案」與 `gap_select.pending_exists` 的既有模式(選路徑不同資料夾,測試⑨「不連坐」方向正確)。d3 只是開輪決定,不對設計內容加約束,沒有牴觸空間。

唯一抓到不一致的是 pending 落地的觸發條件,見 f3。

## Findings

### f1 — blocker

spec 段落:設計 4,FAIL 修復鏈,76 行。

引句:「主樹該篇現況 sha256 == 派工快照 sha」

問題:這個比較式左右兩邊的定義完全不對稱,且 spec 通篇沒有回答「派工快照 sha 是誰、什麼時候、對哪個檔算出來的」。
- **演算法不對稱**:左邊明講 `sha256`,右邊只講「sha」。`make_sandbox` 建沙盒的方式是 `rsync` 整棵樹後 `git add -A` + `git commit`(scripts/scenario_probe.py:94-95、107-109),回傳值只有沙盒路徑 `work`(110 行),完全沒有回傳、也沒有計算任何檔案內容的雜湊。如果實作時偷懶取 `git rev-parse HEAD:<path>` 之類的 git blob 雜湊當「派工快照 sha」,拿到的是 git 物件雜湊(本 repo 未見啟用 `--object-format=sha256`,預設應是 40 字元的 sha1),跟左邊明講的 64 字元 sha256 是兩個不同的雜湊空間、永遠不可能相等——柵欄會恆假,FAIL 修復鏈的「回寫」功能名存實亡,每次都落 pending,d1「全自動閉環」的核心賣點直接失效。
- **計算時機未定**:即使兩邊都改成 sha256,spec 也沒說這個值是在 `make_sandbox` 剛 rsync 完、還沒被修 agent 用 Edit 動過之前,對主樹來源檔算一次(選項 A),還是別的時間點算(選項 B)。這兩者若選錯,比較的基準版本就不是「dispatch 那一刻的主樹現況」,柵欄保護的窗口會跟設計意圖不一致。
- 測試清單(109-114 行)裡⑥「柵欄過→copy+戳+commit」跟⑦「柵欄擋下」各測了一個方向,如果實作用真雜湊(非 mock),⑥、⑦多少能在寫測試時逼出這個 bug,提供一點事後安全網——但這不能取代 spec 本身把「誰、何時、對什麼算、哪種雜湊」講清楚;現在的寫法把這個判斷丟給實作者臨場決定,而這正是本案三輪翻車的固定模式(先例失真/宣稱層安全)。

### f2 — blocker

spec 段落:設計 4,PASS 分支,72-73 行。

引句:「PASS → 蓋章 `auto-<model>` ★+commit★」

問題:回寫柵欄(76-78 行)只掛在 FAIL→修復→複審 PASS→copy 這條鏈上;PASS 分支(審計本身就站得住,不用修)完全沒有任何「主樹有沒有在派工期間被改過」的檢查,直接對「主樹現況」蓋章+commit。但 PASS 判斷本身是審計 agent 在沙盒裡看 dispatch 那一刻 rsync 進去的版本做出來的(設計 2),兩者之間隔著整條 `subprocess.run(timeout=900)`(69 行)的派工時間——如果有人在這 15 分鐘的窗口內改了主樹上那篇筆記的正文,PASS 蓋章會把「agent 根本沒看過的版本」標成「已被乾淨 agent 確認站得住」,且沒有任何機械手段能偵測到這個落差。

實查證實這不是我的臆測,而是現有可重用零件真的沒有這層保護:`cmd_self_audit`(scripts/lumos:7578-7593)呼叫 `cmd_set`(7549-7575),`cmd_set` 一律用 `load_raw_for_edit(path)` 在**呼叫當下**重新讀主樹檔案(7555 行),`atomic_write_verify`(7523-7546)只驗「寫完讀回來,欄位值對不對、有沒有引入新的 lint 指紋」(7534-7538),完全不比對「這次要蓋章的內容,是不是 agent 當初審的那個版本」。如果 PASS 分支照 v4「同 v4」的既有慣例直接複用這條路徑,它結構上就不可能發現主樹漂移。

這正是 r3 s1f5/Codex f1 已經 blocker 過的同一種失效(「copy 回主樹靜默蓋掉派工期間人的改動」,166 行歷史記錄),只是換了個分支——上一輪修的是 FAIL 鏈,PASS 鏈這次完全沒補。且測試清單裡⑤只釘「commit 訊息格式」(111 行),不驗 PASS 分支的新鮮度,13 條測試對這個洞沒有覆蓋。鑑於 self_audit 戳記的可信度是整個機制要解決「44 天沒人看」問題的核心承諾,一個能被悄悄蓋成假綠的分支,嚴重度不低於已經 blocker 過的那條。

### f3 — major

spec 段落:設計 4,pending 落地條件,79-80 行;對照 d1(19-24 行)、d2(25-30 行)。

引句:「複審 FAIL / 範圍刀越界 / 柵欄擋下 → 各記週帳(kind 分 abort/fail/stale)」

問題:d1 把落 pending、轉人工兜底的唯一授權條件寫死為「連續兩輪 FAIL 才落 pending 喊人」;d2 進一步把這句話釘死成「同次派工內『審計 FAIL+修復後複審仍 FAIL』兩關」——也就是說,必須真的發生兩次 FAIL 判定,才輪到人工。但 79 行把三種性質完全不同的結局一視同仁地導去 pending、且不再自動重試(80 行):
- 「複審 FAIL」確實符合 d1/d2(審計 FAIL + 複審 FAIL,兩輪都失敗)。
- 「範圍刀越界」發生在修 agent 動手之後、複審之前(74 行的鏈順序是「修→範圍刀→複審」)——這時只發生過**一次** FAIL(最初的審計),複審根本還沒跑,不滿足「兩輪 FAIL」。
- 「柵欄擋下」按 74-78 行的順序,是在「複審 PASS」**之後**才觸發的(75 行:「複審 PASS → ★回寫柵欄★」)——這時是一次 FAIL(審計)+一次 PASS(複審),連一次「複審 FAIL」都不存在,跟 d1/d2 定義的「兩輪 FAIL」完全對不上。

d1/d2 沒有任何一句話授權「範圍刀越界」或「柵欄擋下」也能觸發「落 pending+不再自動重試」這個人工兜底待遇;設計文字把三種情況合併處理,等於在沒有新決策支撐的情況下,擅自把 pending 的觸發範圍從「連續兩輪 FAIL」擴大到「任何非 happy-path 結局」。這不只是文字不對齊——「柵欄擋下」按定義是**內容修復其實成功了**,只是運氣不好撞上主樹同時被改,這是純粹的時序巧合,跟「這篇筆記修不好」是兩回事;把它跟「修不好」判同一種永久鎖出自動重試(而且要靠人手動歸檔 pending 檔才能恢復,81 行),等於一次無關內容品質的併發巧合就能讓某篇筆記重新掉回「沒人管」的狀態——這正是整個方案要解決的問題本身。建議:要嘛把 d1/d2 的「兩輪 FAIL」明確擴寫成涵蓋這三種結局的新決策,要嘛讓「範圍刀越界」「柵欄擋下」下一輪自動重新派工(而不是直接轉人工兜底),不要三種結局共用同一套「永久停自動」邏輯。

### f4 — major

spec 段落:設計 4,78 行。

引句:「柵欄過=copy+蓋章+commit」

問題:柵欄比對(76 行)驗的是「被審那一篇筆記」的內容雜湊,但比對通過後實際落地的「copy+蓋章+commit」這一步,git 暫存(`git add`)的範圍全篇沒有講。派工/沙盒建置的既有先例——spec 自己在 PRIOR-ART(103 行)點名借用的 `make_sandbox`——建沙盒時用的是 `git add -A`(scripts/scenario_probe.py:107),把整棵工作樹當下所有未提交改動一起打包進一個 commit。如果回寫這一步比照辦理,sha256 柵欄只保護了「被審那篇檔案本身」不被覆蓋,完全沒有機械手段擋住「主樹當下其他人未提交的改動,被這次自動 commit 一起夾帶進去,且 commit 訊息只提這篇筆記」。

這不是憑空假設的風險:spec 自己在 77 行引用的 `[[Issues/同工作區多session並行改動]]` 裡,三個實例中的「② 提交夾帶」(該筆記 32-40 行)描述的就是一模一樣的失效模式——「一邊 `git add -A` 一掃,把另一邊當天全部的交付一起 commit 進去,訊息只寫自己的那件」,且該筆記明講「如果那時已經 push,就只能留一筆對不上的歷史」。柵欄(76 行)防的是「內容被覆蓋」,防不了「commit 範圍夾帶陌生檔案」——這是同一個事故筆記裡的另一種失效模式,而 spec 只接住了第一種。建議 78 行明確寫成「只 `git add <該篇 repo_rel 路徑>`,不得用 `-A` 或整樹 add」,並補一條測試(現有 13 條裡沒有覆蓋這個角度)。

### f5 — minor

spec 段落:設計 4,75-78 行。

引句:「不等=主樹已變,放棄回寫、落 pending」

問題:柵欄本身(「讀主樹現況雜湊→比對→若相等才 copy+commit」)是三個先後發生的步驟,不是一個原子操作。76-78 行的因果鏈保護的是「dispatch 到 copy-back 之間」那個長達一輪派工時間(最壞情況多次 `subprocess.run(timeout=900)` 疊加,可到 45 分鐘量級)的大窗口,這個大窗口確實被機械擋住了。但「讀雜湊→比較→寫入」這三步本身之間,仍留有一個微小但非零的視窗:如果有人剛好在雜湊比對通過、真正執行 copy/commit 的那幾百毫秒之間寫入同一個檔案,柵欄不會抓到。這個殘餘視窗比起被擋下的大窗口小了幾個量級,實務上可以接受,但 78 行「絕不靜默覆蓋」這句話目前寫得像是絕對保證,建議明確承認這個殘餘視窗並給出重驗條件(對照專案自身家規:「承認風險要附回頭看的條件」),或用 `git commit` 失敗即中止(而非各自獨立的檔案 copy)之類的機制把這個縫也收斂掉。
