## 檢查①:NB 快速失敗與選序固定的互動——終局 append 搶不到鎖會怎樣

見 f1、f2。窄鎖鎖了兩小段:「讀配額→append started」與「終局 append」(118 行),兩段都套 `LOCK_EX|LOCK_NB`(120 行),失敗語意寫的是「搶不到=本輪跳過 selfaudit 段、印一行」(120 行)。這句話對**第一段**成立——搶不到就是還沒開始派工,跳過乾淨、零副作用,跟 `_goldset_lock` 的先例(governance/eval/refresh_labels.py:52-53:「搶不到=另一寫入進行中 → 快速失敗,呼叫端 rc 非零、goldset 不動」)完全同構,因為 goldset 那邊鎖住的也是「還沒寫」的那一刻。

但對**第二段**(終局 append),此時審計/修復/複審(最長 3×900s)已經跑完,PASS 分支的主樹 commit 可能已經落地、FAIL 分支的 pending 檔可能已經寫盤——此時「搶不到=跳過」不是「沒發生事」,而是「已經發生的事沒有地方被記下來」。這一行的終局狀態(done/fail/abort/stale)永遠不會進 `selfaudit-week.jsonl`,只留下一筆沒有終局的 `started`。spec 沒有給終局 append 的重試、阻塞等鎖、或耐久暫存(durable deferred append)——`_goldset_lock` 唯一先例的失敗語意(rc 非零、呼叫端知道沒寫入、可以重試整個指令)在這裡不適用,因為終局 append 失敗當下沒有「呼叫端」可以重跑一次同樣的請求,下一次能碰到這筆帳的只有「下次進場」的孤兒回填邏輯(113 行)。

孤兒回填本身還有更嚴重的第二層問題(f2):它判斷「有 started 無終局」的唯一依據是掃 `selfaudit-week.jsonl`,沒有任何 run-id/PID/存活探測/最小年齡欄位(全文 grep `PID`/`pid`/`存活`/`lease`/`attempt`/`age` 零命中)。派工可以跑到 900 秒(85 行),而選序固定+窄鎖的設計前提本身就承認「兩進場」是要防的真實場景(測試③:「flock:兩進場用兩個行程/兩個 open 控柄模擬…後到者快速失敗不超額」,156 行;v5-r2 折入理由「原整段持鎖最壞 90 分鐘會掛死第二進場」,234 行)——這代表第二個進場的行程完全可能在第一個行程仍在 900 秒逾時視窗內、貨真價實地派工中時,把它的 `started` 誤判成孤兒。這直接打臉同一段落自己下的結論:「耐久預約已提供跨程序『已佔用』信號,窄鎖不開回雙派工的洞」(121 行)——窄鎖釋放後,`started` 這一行本身不再攜帶任何「還活著」的資訊,второй進場看到的只是「有 started」,無法分辨「還在跑」與「跑死了」,雙派工的洞事實上開著。

## 檢查②:stale 釋放公式與 orphan 的互動——orphan 該不該釋放配額,spec 有沒有講

見 f3。配額公式明講「quota−(本週 started 行數−其中終局為 stale 的行數)」(115 行),只對 kind=stale 退回名額,理由是「stale 是時序巧合,預約不釋放的話同一篇撞兩次柵欄就吃光整週名額」(115-116 行)。這條理由對 orphan 邏輯上同樣適用甚至更強:stale 是**整條修復鏈跑到複審 PASS 才卡在最後一步**(102-104 行),orphan 是**行程在某個時點被殺,連有沒有跑完都不知道**(113-114 行:「orphan=行程被殺,與筆記無關」)——兩者都被 spec 自己定性為「跟筆記內容無關的意外」,orphan 甚至更明確是「跟這篇筆記無關」,理應比 stale 更沒有理由罰配額。但公式只減 stale、不減 orphan,spec 全文(含四輪折入紀錄的逐條列表,174-243 行)沒有任何一句話解釋這條不對稱——沒有「orphan 故意不退,因為 XXX」這種決策文字,是沉默的缺口,不是裁過的選擇。

這不是憑空的邊界情境:本輪設計節自己記錄了這個 repo 真實發生過的先例——「make_sandbox 的清理 bug(未定義變數,週週 NameError 被吞、/tmp 漏 41 個沙盒)」(61 行)。這正是一種會反覆重現的 orphan 成因(腳本層的例行性 crash,不是罕見的機器斷電)。若同一類 bug 出現在 selfaudit.py 自己身上,一週的配額(N=2)可能被兩次 orphan 完全吃光而沒有任何一篇真的被審完——退化成本案立案理由所描述的那種「沒人看」,而且不會被本案自己的成功判準「≥14 天即有審計紀錄」(53 行)區分出來,因為 orphan 仍然是「有審計紀錄」的一種(帳本上有一行),只是沒有一篇真正產出結論。

測試清單裡③只驗了「配額公式含 stale 釋放…同 stem 兩次 stale 後照樣入選、名額不被吃」(156 行),沒有一條反向驗證「orphan 是否也該/不該釋放」;⑩「週帳:中斷補殘」(159 行)也只驗補殘動作本身,不驗配額互動。

## 檢查④:範圍刀「嚴格相等單篇」在修 agent 產生 lint 自動修改/暫存檔時撐不撐得住

見 f4。分兩層:

**(a) 追蹤檔 vs 未追蹍新檔**:實測空 repo(`git diff --name-only` 對「1 個修改過的追蹤檔+1 個全新未追蹤檔」)只回報追蹤檔那一個,完全不提未追蹍新檔。範圍刀字面是 `git -C <sandbox> diff --name-only`(100 行),沒有 ref、沒有先 `git add`——這是 working tree vs index 的比對,對「修 agent 在沙盒裡新建的檔案」(lint 產出的報告檔、`.bak`、任何暫存檔)天生看不見。若修 agent 只改了目標筆記+額外新建了幾個暫存檔,範圍刀仍會判「diff 恰為單篇」放行——範圍刀對「有沒有動到不該動的既有筆記/程式碼」這件事抓得住(那些是修改既有追蹤檔,會出現在 diff 裡),但對「有沒有在沙盒裡憑空造出東西」這件事是瞎的。實務後果被壓縮:因為「柵欄過=copy+蓋章+commit」的主樹寫回只 `git add` 該篇 pathspec(98、104 行),沙盒裡的暫存檔不會被複製回主樹,加上測試⑫要求逐結局分支斷言沙盒父目錄不殘留(159 行)——暫存檔最終會隨沙盒一起被清掉,不會污染主樹。但範圍刀作為「偵測修 agent 有沒有守規矩」這個機制本身,涵蓋範圍不完整,跟它在白話摘要裡被列為「三道韁繩」之一(46 行)的份量不相稱,而且沒有任何一條測試(①-⑬)對「沙盒內新建未追蹍檔案」這個情境下斷言。

**(b)「lint 必綠」沒有掛接點**:「lint 必綠」在全文只出現一次(165 行,實務隱患守衛面),§4 設計節、測試①-⑬、連動節、PRIOR-ART 節都沒有再提——沒有講清楚誰跑 lint、什麼時候跑、跑不過算哪個結局。查證發現這個 repo **確實有**一個能自動接住它的既有機制:`scripts/hooks/pre-commit` 的 Gate L(87-107 行)對任何 staged 進 `docs/*-knowledge/` 的 `.md` 檔逐一跑 `lumos lint`,rc≠0 就擋下整個 commit(硬擋,非 advisory)。如果 selfaudit.py 主樹寫回那一步用的是普通 `git commit`(不帶 `--no-verify`),Gate L 會免費把「lint 必綠」變成真的機械保證——但 spec 完全沒有點名這個掛接點,也沒有明講寫回 commit 不可以帶 `--no-verify`。風險在於:本案自己的 PRIOR-ART 就是 `make_sandbox`,而 `make_sandbox` 自己的內部快照 commit 習慣性帶 `--no-verify`(scripts/scenario_probe.py:109,且 pre-commit hook 文件本身把 `--no-verify` 定位成「業界標準」bypass 用法,11 行)——照抄同一個模組裡的 git commit 寫法,很容易把這個習慣一併帶進主樹寫回那一步,靜默關掉 Gate L,讓「lint 必綠」變成一句沒有機械後盾的話。13 條測試裡,派工層一律走注入假 runner/monkeypatch subprocess(154、156-157 行「測試⑥用注入假 runner…不真派 agent」),沒有一條測試會真的執行一次帶著真實 `core.hooksPath` 的 `git commit`,所以就算實作真的不慎用了 `--no-verify`,也不會被本案自己的測試清單抓到。另外,commit 這一步本身若被 pre-commit 擋下(不管是 Gate L 或 Gate 1 的污染指紋檢查)該算哪個結局,spec 也沒有講——「柵欄過=copy+蓋章+commit」(98、104 行)把 commit 寫成必然成功的最後一步,沒有第三種「柵欄過但 commit 被 hook 擋下」的分支。

## Findings

### f1 — major

spec 段落:設計 §4 處置,週帳段(117-121 行)。

引句:「搶不到=本輪跳過 selfaudit 段、印一行」

問題:這句失敗語意只精確描述「讀配額→append started」這一段搶不到鎖的情況(此時還沒開始派工,跳過即安全)。同一句話被拿來覆蓋「終局 append」搶不到鎖的情況(118、120 行明講兩小段共用同一套 NB 語意),但終局 append 發生在審計/修復/複審(最長 3×900s)已經跑完之後——PASS 分支的主樹 commit 可能已落地,FAIL 分支的 `pending/selfaudit/<日期>-<stem>.md` 可能已寫盤。此時「跳過」不是零副作用的安全動作,而是「已發生的工作結果沒有終局帳可記」:done/fail/abort/stale 這一行永久遺失,只留一筆沒有終局的 `started`,只能倚賴下次進場的孤兒回填(見 f2,回填本身也不可靠)。與 `_goldset_lock` 這個 spec 自己引用的鎖先例(120 行「鎖模式照 repo 唯一先例 `_goldset_lock`」)比較:先例的 NB 失敗語意是「呼叫端 rc 非零、goldset 不動」(governance/eval/refresh_labels.py:53)——失敗發生在「還沒寫」的那一刻,呼叫端知道沒寫入、可以決定要不要重跑;終局 append 沒有這種對稱性,沒有呼叫端可以重跑「同一次已經跑完的派工結果」。spec 沒有給終局 append 任何重試、阻塞等鎖、或耐久暫存機制。

查證:`/tmp/selfaudit-loop-v5-r3.md:117-121`(窄鎖範圍與 NB 失敗語意原文)、`:85`(`subprocess.run(timeout=900)`)、`:98`、`:104`(commit 落地敘述,佐證終局 append 前主樹寫入可能已完成);`governance/eval/refresh_labels.py:52-73`(`_goldset_lock` 定義與失敗語意,佐證既有先例只用在「整批退出、呼叫端知情」的場景,非「已完成外部工作後結果遺失」的場景)。

### f2 — blocker

spec 段落:設計 §4 處置,週帳段(110-121 行);測試③(156 行)。

引句:「窄鎖不開回雙派工的洞」

問題:孤兒回填(「有 started 無終局=下次進場補記 kind=orphan」,113 行)判斷依據只有「掃到一筆 started 沒有對應終局」,完全沒有 run-id、PID、存活探測或最小年齡欄位(全文對 `PID`/`pid`/`存活`/`lease`/`attempt`/`age` grep 零命中)。派工可以合法跑到 900 秒(85 行),而窄鎖設計的前提本身就承認「同一時間有第二個進場」是要防的真實情境——這不是我推想出來的假設場景,是 spec 自己的測試③明講要模擬:「flock:兩進場用兩個行程/兩個 open 控柄模擬…後到者快速失敗不超額」(156 行),且 v5-r2 把整段鎖改窄的理由正是「原整段持鎖最壞 90 分鐘會掛死**第二進場**」(234 行)——這代表第二進場疊在第一進場派工期間是設計明確承認且要處理的狀況。窄鎖釋放後(append 完 started 立刻放鎖),`started` 這一行本身不再攜帶任何「發起者還活著」的信號;第二個進場看見「有 started 無終局」時,無法分辨這是「第一個進場的行程被殺了」還是「第一個進場正在它自己的 900 秒逾時視窗內正常派工」。若誤判成 orphan 並回填,而原行程稍後正常結束又 append 了自己的 `done`/`fail`/`stale`,同一筆 `started` 就會有兩筆終局,且該篇筆記在 orphan 路徑下已被判定「不落 pending、本週不重派、下週照常入選」(114 行)——也就是原本正在被安全派工的筆記,可能在它自己的派工還沒結束前就被系統認定「可以再選一次」,重新進入候選池,與同一段落緊接著下的結論「耐久預約已提供跨程序『已佔用』信號,窄鎖不開回雙派工的洞」(121 行)直接矛盾:被打臉的正是這句話本身宣稱要防的那個洞。

查證:`/tmp/selfaudit-loop-v5-r3.md:110-121`(週帳 schema、started/orphan 定義、窄鎖範圍、「不開回雙派工的洞」原句)、`:85`(900 秒逾時)、`:156`、`:234`(兩處各自獨立佐證「兩進場」在本設計裡是被承認的真實場景,非我方臆測)。同一份 v7 delta 的另一席外部審稿(`governance/review-reports/selfaudit-loop-v5/r3-ext.md` finding 2)獨立跑出可翻紅的最小重現(模擬正常在途派工被誤判 orphan、terminal 列出現兩筆),與本查證方向一致,互為印證而非互相依賴。

### f3 — major

spec 段落:設計 §4 處置,週帳段(113-116 行);測試③(156 行)。

引句:「配額=quota−(本週 started 行數−其中終局為 stale 的行數)」

問題:公式只對 kind=stale 退回配額,理由是「stale 是時序巧合,預約不釋放的話同一篇撞兩次柵欄就吃光整週名額,退化成另一種『沒人看』」(115-116 行)。這條理由對 orphan 邏輯上同樣站得住、甚至更站得住:orphan 被 spec 自己定性為「行程被殺,**與筆記無關**」(113-114 行),比 stale(整條修復鏈跑到複審 PASS、只在最後一步被柵欄卡下)更明確是「跟這篇筆記內容毫無關係的意外」,理應更沒有理由罰配額。但公式只減 stale、不減 orphan,四輪折入紀錄(174-243 行)裡沒有任何一句話解釋這條不對稱——找不到「orphan 故意不退,因為……」這樣的裁決文字,是沉默的缺口。

這不是純理論情境:設計節自己記了這個 repo 真實發生過的例子——「make_sandbox 的清理 bug(未定義變數,週週 NameError 被吞、/tmp 漏 41 個沙盒)」(61 行),這正是一種會反覆重現、非罕見的 orphan 成因(腳本層的例行性 crash)。若同款 bug 出現在 selfaudit.py 本身,一週僅有的 N=2 配額可能被兩次 orphan 全部吃光而沒有任何一篇真正產出審計結論——這正是本案立案時要解決的那種「沒人看」的翻版,而且不會被本案自己的成功判準「≥14 天即有審計紀錄」(53 行)偵測出來,因為 orphan 本身仍是「有紀錄」的一種,帳面上看起來系統有在動,只是沒有一篇真正有結論。測試③只驗了 stale 釋放這一半(156 行「同 stem 兩次 stale 後照樣入選、名額不被吃」),沒有反向驗證 orphan 該不該釋放、以及「同一週多次 orphan 是否會吃光配額」。

### f4 — major

spec 段落:設計 §4 處置 FAIL 分支範圍刀(100-101 行);實務隱患守衛面(165 行)。

引句:「範圍刀(只准動該篇,diff 越界作廢)、lint 必綠」

問題:兩層。(a) 範圍刀字面是 `git -C <sandbox> diff --name-only`(100 行),沒有指定 ref、沒有先 `git add`,比對的是 working tree 對 index——這種比法對「修 agent 修改了既有追蹤檔」看得見,對「修 agent 在沙盒裡新建的未追蹍檔案」(lint 自動產出的報告檔、`.bak`、任何暫存檔)結構性看不見。實測驗證(空 repo:1 個修改過的追蹍檔+1 個全新未追蹤檔,`git diff --name-only` 只回報前者)確認這個盲點是真的、不是我誤讀 git 語意。雖然主樹寫回只 `git add` 該篇 pathspec(98、104 行「絕不 add -A」)加上沙盒事後整個被清掉(測試⑫,159 行),暫存檔不會污染主樹——但範圍刀作為「偵測修 agent 有沒有守規矩」的機制本身涵蓋不完整,跟它在白話摘要被列為「三道韁繩」之一(46 行)的份量不相稱,13 條測試沒有一條對「沙盒內新建未追蹍檔案」這個情境斷言。

(b)「lint 必綠」全文只在 165 行出現一次,§4/測試/連動/PRIOR-ART 都沒有再提,沒有講誰跑、何時跑、失敗算哪個結局。查證發現這個 repo 已有現成的掛接點:`scripts/hooks/pre-commit` 的 Gate L(87-107 行)對任何 staged 進 `docs/*-knowledge/` 的 `.md` 逐檔跑 `lumos lint`,rc≠0 硬擋 commit——如果主樹寫回那一步是普通 `git commit`,Gate L 會免費兌現「lint 必綠」這句話。但 spec 沒有點名這個掛接點,也沒有明講寫回 commit 不可以帶 `--no-verify`。風險是本案自己的 PRIOR-ART `make_sandbox` 在同一個模組裡示範的正是「內部 commit 習慣性帶 `--no-verify`」(scripts/scenario_probe.py:109),而 pre-commit hook 檔案自己把 `--no-verify` 定位成「業界標準」bypass(scripts/hooks/pre-commit:11)——照抄同模組的 git commit 寫法,很容易把這個習慣一併帶進主樹寫回步驟,靜默關掉 Gate L,讓「lint 必綠」變成沒有機械後盾的一句話。13 條測試的派工層一律用注入假 runner/monkeypatch subprocess(154、156-157 行),沒有一條會真的跑一次帶著 `core.hooksPath` 的 `git commit`,實作萬一真的帶了 `--no-verify`,不會被本案自己的測試抓到。commit 這一步若被 pre-commit 擋下(Gate L 或其他 gate)算哪個結局,spec 也沒講——「柵欄過=copy+蓋章+commit」(98、104 行)把 commit 寫成必然成功的最後一步,缺一個「柵欄過但 commit 被 hook 擋下」的分支。

查證:`/tmp/selfaudit-loop-v5-r3.md:100-101`(範圍刀定義)、`:98`、`:104`(pathspec 規則,佐證主樹寫回範圍受限)、`:159`(測試⑫沙盒清理)、`:154`、`:156-157`(測試層一律走假 runner,無真實 commit/hook 測試)、`:165`(lint 必綠原句,前後文皆無操作化);`scripts/hooks/pre-commit:87-107`(Gate L 硬擋邏輯)、`:11`(`--no-verify` 業界標準 bypass 定位);`scripts/scenario_probe.py:109`(`make_sandbox` 內部 commit 帶 `--no-verify` 的既有習慣,佐證抄襲風險方向);實測(空 repo `git diff --name-only` 對修改追蹍檔可見、對新建未追蹍檔不可見)佐證 (a) 的盲點為真。
