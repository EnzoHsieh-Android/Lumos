### f1 — blocker

spec 段落:設計 §2 派工(67-69 行)對照設計 §4 處置 FAIL 分支範圍刀(83-84 行)。

引句:「與 repo_rel 同空間嚴格相等」

問題:`make_sandbox`(scripts/scenario_probe.py:94-95、107-109)是先 `rsync` 整棵工作樹、再 `git add -A`+`commit` 產生「派工快照」——這個快照 commit 天然把 `governance/review-reports/`、`governance/pending/`、`governance/l4-audit/`、`docs/.governance-log.jsonl`、`docs/.canary-log.jsonl` 全部收進去。v5-r1 這輪新折入的沙盒刪除清單(67-69 行「建好後刪沙盒內全部審計脈絡」)明講「建好後」才刪——也就是在這個快照 commit **之後**才把五個路徑從工作目錄拿掉,而且只刪檔案系統上的東西,沒有再 commit 一次。

實測 `git ls-files governance/review-reports governance/pending governance/l4-audit docs/.governance-log.jsonl docs/.canary-log.jsonl` = **583** 個 tracked 檔案。這代表沙盒建好、刪除脈絡執行完之後,沙盒工作樹相對它自己 HEAD(派工快照)已經有 583 筆「刪除」的未提交差異——在修 agent 對「該篇筆記」動手之前就已經存在。範圍刀(83-84 行)算的是 `git -C <sandbox> diff --name-only`,要求跟 `repo_rel` 「同空間嚴格相等」;但這時 diff 輸出必然是「583 個被刪的審計脈絡檔 + 修 agent 真的動過的那一篇」,不可能等於單一 `repo_rel`。也就是說,**只要沙盒刪除清單(f1 對照的這條折入)照字面實作,FAIL→修復鏈的範圍刀在每一次派工都會判定越界**,無論修 agent 改得多乾淨——d1「全自動閉環」唯一會走到的分支變成「複審 FAIL / 範圍刀越界 / 柵欄擋下」三選一裡的「範圍刀越界」,永遠落 pending、不再自動重試(89 行),整條自動修復鏈名存實亡。這正是本輪兩個各自合理的折入(沙盒脈絡刪除 vs. 範圍刀嚴格相等)撞在一起產生的新洞,兩份 r1 報告(s2 f2/f3 抓沙盒洩漏、Codex f3 抓範圍刀路徑空間)都只各自看了一半,r1 沒有人同時追過這條因果線。

最小可行的解法方向(供裁決參考,非本輪要求):要嘛把這五個路徑在**快照 commit 之前**就從沙盒排除(讓 `make_sandbox` 的 rsync/commit 根本不收它們進去,而不是收了再刪),要嘛範圍刀的 diff 計算明講要排除這五個固定路徑再比對——目前 spec 兩處都沒有講。

查證:`/tmp/selfaudit-loop-v5-r2.md:67-69`(建好後刪除,無再 commit 的敘述)、`:83-84`(範圍刀嚴格相等敘述);`scripts/scenario_probe.py:94-95、107-109`(make_sandbox 的 rsync+`git add -A`+commit 全文);`git ls-files governance/review-reports governance/pending governance/l4-audit docs/.governance-log.jsonl docs/.canary-log.jsonl | wc -l` 實測輸出 = 583。

### f2 — major

spec 段落:設計 §4 處置(88-98 行);測試③(130 行)。

引句:「不落 pending、不鎖,記週帳後重新排隊」

問題:結局分流把「柵欄擋下(stale)」定位成「時序巧合非失敗」,不落 pending、不鎖,下輪照常入選(90-91 行)——這個判斷本身是對的(時序巧合不該跟內容真的有問題的 FAIL 同等對待)。但配額計算的口徑是「配額=quota-本週 started 行數」(130 行測試③,96 行設計節同款敘述),而且 started 是**派工前**就先 append 的耐久預約(94-95 行,本輪另一個折入,理由是「程序中斷不重複消耗配額」)。

這兩條折入合起來的效果:一篇筆記若被柵欄擋下,它在本週的 started 行數已經記了一筆(這筆不會被撤銷、也不該被撤銷,started 的耐久性正是它的設計目的);下一輪它被重新排隊選中,派工前又會再 append 一筆 started——同一篇筆記在同一週的 started 計數變成 2,而配額扣的正是 started 的行數,不是「處理過幾篇不同筆記」。以 N=2/週為例:同一篇連續撞上兩次柵欄擋下,就能把整週僅有的兩個名額全部吃光,而且沒有任何一篇筆記真的被確認或修復——跟「柵欄擋下=時序巧合非失敗、應該幾乎不影響吞吐」的設計意圖完全相反,也直接牴觸症狀節「本案成功=同款空轉結構性不再累積(≥14 天即有審計紀錄)」這個成功判準:配額被自己的重試吃光的那一週,其他真正該審的筆記一篇都排不上,退化成另一種形式的「沒人看」。

13 條測試裡,③只驗了「配額=quota-本週 started 行數」和「started 無終局視同 abort 不重派」兩個方向(130 行),沒有一條驗「同一 stem 因 stale 重新排隊,配額會不會被同一篇吃兩次」。

查證:`/tmp/selfaudit-loop-v5-r2.md:90-91`(stale 重新排隊敘述)、`:94-96`(started 耐久預約+配額只數 started 的敘述)、`:130`(測試③配額公式,無同 stem 重試計數的斷言)。

### f3 — major
