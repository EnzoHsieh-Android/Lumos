## Findings

### f1 — major

spec 段落:設計 2,71-75 行。

引句:「make_sandbox 加排除清單參數,rsync 就不抄 `governance/review-reports/`、`governance/pending/`、」

問題:先講已核實可行的部分——我在 scratchpad 造了一個帶五項排除路徑（含已 commit 的 tracked 檔）的來源 repo,實跑 `rsync -a --exclude node_modules --exclude .venv --exclude "governance/review-reports/" --exclude "governance/pending/" --exclude "governance/l4-audit/" --exclude "docs/.governance-log.jsonl" --exclude "docs/.canary-log.jsonl"`,再走 `make_sandbox` 現有的「`git add -A` + probe snapshot commit」兩步。結果確認:rsync 排除後、commit 之前,`git status --porcelain` 對這五項全部顯示 `D`(因為 `.git` 本身也被 rsync 複製、索引仍記得舊狀態);但 `git add -A` + commit 之後,`git status`/`git diff --name-only` 完全乾淨,那五個刪除被收進同一個 probe snapshot commit 裡當作新基線——之後單獨改一篇筆記,`git diff --name-only` 精準只顯示那一篇。設計節這句話的核心機制是成立的,不是空話。

真正的缺口在簽字面:`make_sandbox` 現簽名是 `def make_sandbox(src):`(scripts/scenario_probe.py:80),只有一個必要參數,且已有兩個既有呼叫者——`main()`(210 行:`work = make_sandbox(src)`)與它自己的翻紅測試 `t_probe_sandbox_cannot_push`(test_lumos.py:443:`work = m.make_sandbox(src)`)——兩處都只傳一個位置參數。spec 只說「加排除清單參數」,沒說這個參數要不要給預設值、預設值是不是空清單。如果 implementer 照字面把它加成必要位置參數(或必要關鍵字參數且無預設),這兩個既有呼叫點會直接 `TypeError`,scenario_probe 自己的探針主流程與翻紅釘測試會全部炸掉——這不是新機制的邊界情境,是對既有、已經在保護「沙盒推不出去」這條安全線的既有測試的迴歸風險。

建議:spec 明講新增參數要有預設值(例如 `exclude: list[str] | None = None`,預設等於現行的 `["node_modules", ".venv"]` 或空清單疊加現行兩項),使 `main()` 與 `t_probe_sandbox_cannot_push` 兩個既有呼叫點零改動下行為不變;測試①或②新增一條斷言「不傳排除清單時,`make_sandbox` 行為與現況一致」,把這條回歸釘死,不要只靠 implementer 自己想到。

### f2 — major

spec 段落:設計 2,87-89 行;設計 4,92-104 行。

引句:「selfaudit.py 至少拆 `snapshot_sha(path)`/`dispatch_note(note, runner)`/`apply_write_fence(path, expected_sha, new_text)→ok|stale`/」

問題:四個切縫裡,`apply_write_fence` 的簽名只回傳 `ok|stale` 這個裸狀態,不吃、也不寫週帳(參數清單裡沒有 ledger/kind 相關的東西)。但設計 4 對 PASS 路徑(98 行「PASS → 柵欄過 → 蓋章 `auto-<model>` +commit」)與 FAIL 鏈路徑(100-104 行「柵欄過=copy+蓋章+commit」)的敘述,都是把「柵欄過/柵欄擋下」到「commit」到「記週帳 kind=done/stale」寫成同一段散文流程,沒有指名這串動作裡哪一段是 `apply_write_fence` 自己做的、哪一段是呼叫它的人(只能是 `run_week`,因為另外兩個函式明顯不是)做的。

這個空白直接命中測試⑤⑦的可寫性:⑤要造「另造主樹派工後被改場景→PASS 也擋下、kind=stale」,⑦要斷言「放棄回寫、記週帳 kind=stale、不落 pending、重新排隊」——如果測試作者對著 `apply_write_fence(path, expected_sha, new_text)→ok|stale` 這個簽名直接單元測,它能斷言的只有回傳值是不是 `stale`、檔案有沒有被寫,斷不到「週帳有沒有多一行 kind=stale」,因為按簽名這根本不是這個函式的職責;但如果測試作者誤以為 `apply_write_fence` 內部就會順手寫週帳(因為散文敘述讀起來像一條龍),就會對著一個沒有這個副作用的函式斷言週帳寫入,測試會穩定假紅或測試作者被迫去 monkeypatch 一個 spec 沒承諾存在的內部呼叫。四個切縫本身足夠獨立呼叫沒錯,但「切縫跟切縫之間誰對週帳負責」這條責任邊界,spec 沒講。

建議:明講 `apply_write_fence` 是純粹的「比對+寫檔」函式、不碰週帳,週帳 append(done/stale/fail/abort/orphan)一律由 `run_week` 在拿到 `apply_write_fence`(或 `dispatch_note`)回傳值之後統一決定並呼叫;測試⑤⑦因此要拆成兩層——一層直接餵 `apply_write_fence` 過期的 `expected_sha` 斷言回 `stale`+檔案沒被寫,另一層測 `run_week` 在收到 `stale` 之後有沒有正確 append 週帳行——不要期待一次呼叫就能兩者都驗到。

### f3 — major

spec 段落:測試草案③,156 行;設計 4,117-121 行。

引句:「flock:兩進場用兩個行程/兩個 open 控柄模擬(v5-r2 s3f3:同控柄 flock 不自阻,照抄會測了個寂寞;樣板照 t_refresh_atomic_and_lock)」

問題:`t_refresh_atomic_and_lock`(test_lumos.py:21279-21318)能照抄成立,是因為它測試行程自己先 `open(str(gpath)+".lock")` 拿到一個獨立的 file handle 去 `flock(LOCK_EX)`,而它撞的鎖檔路徑是寫死的、跟 `_goldset_lock.__init__` 裡 `self.path = str(goldset_path) + ".lock"` 這個既有慣例完全對得上,測試才能不必呼叫任何私有函式就知道要占哪個檔。selfaudit 這邊,spec 只說「鎖模式照 repo 唯一先例 `_goldset_lock`」(120 行),照抄的是 `LOCK_EX|LOCK_NB` 快速失敗這個**行為模式**,但沒有一處明講週帳鎖檔的**路徑**是不是也照 `_goldset_lock` 同一個「`<週帳路徑>.lock`」命名慣例(即 `governance/selfaudit-week.jsonl.lock`)——這件事現在只能靠 implementer 自己去猜,而測試③要能獨立 `open()` 那個鎖檔去模擬「先到者」,前提正是要跟實作用同一個路徑約定,兩邊沒有共同來源(比如一個 `_LOCK_PATH` 常數/一個回傳鎖路徑的函式),測試很容易因為猜錯路徑而形同虛設——占了一個實作根本不用的檔案,鎖永遠不衝突,測試綠但沒驗到任何東西,跟 v5-r2 s3f3 抓到的「同控柄不自阻」是同一種「測了個寂寞」,只是換一個成因。

另外,測試(草)開頭(154 行)講死「全部走 `test_autonomous_loop.py` 直接 import selfaudit.py;CLI 出口走 subprocess;派工層注入假 runner」,只點名兩種例外(CLI 出口、派工層注入)。③要求的「兩個行程」如果真的照字面理解成兩個獨立 OS process(比如各自 `subprocess.run` 呼叫 selfaudit 的入口),既不是「CLI 出口」也不是「派工層注入假 runner」,不屬於這兩條已聲明的例外——測試作者要嘛違反 154 行的總則改用 subprocess,要嘛退而求其次只做「兩個 open 控柄」(在同一個 pytest 行程內各自獨立 `open()` 同一鎖檔,再直接 in-process 呼叫 `run_week`),但後者要能命中 `run_week` 內部真正在用的鎖檔,一樣繞不開上一段講的路徑約定缺口。

建議:selfaudit.py 對外暴露鎖檔路徑(常數或一個 `_lock_path()` 小函式),命名照 `_goldset_lock` 慣例(週帳路徑+`.lock`),讓測試③可以不必碰任何私有實作細節就正確 `open()` 到同一個檔;同時在測試(草)154 行的總則裡明講③屬於第三種例外(允許獨立開檔模擬鎖競爭),不要讓它跟總則打架。

### f4 — major

spec 段落:設計 4,週帳,110-116 行。

引句:「配額=quota−(本週 started 行數−其中終局為 stale 的行數)(v5-r2 s1f2/Codex#2 附重現:stale 是時序巧合,」

問題:這條公式本身是純聚合計數(本週 `started` 行數減本週 `stale` 終局行數),不需要把某一行 `stale` 顯式配對回某一行 `started` 才能算對——這點我推演過:即使同一個 stem 同一週有兩次 `started`+兩次 `stale`(測試③明講的情境),聚合減法照樣得零淨消耗,不需要額外的配對鍵。這部分沒問題,是我原本以為需要「配對規則」但其實不用。

真正的缺口在:週帳的列結構是 `{"week","stem","kind","ts"}`(110 行),沒有任何欄位把一行 `started` 跟它對應的終局行(不管是 `done`/`fail`/`abort`/`stale`/`orphan`)綁在一起,整個「配額釋放」與「孤兒補記」的正確性完全建立在一個沒有寫下來的隱性假設上——「同一個 `started` 一定會在**同一個 ISO 週**內拿到它的終局行」。這個假設在本案自己的立案背景下並不牢靠:立案理由就是「44/40 天沒人看」的實證(症狀節,53-54 行),loop 本身有跳過多天不跑的前科。112-114 行的孤兒補記(「有 started 無終局=下次進場補記 kind=orphan」)沒講清楚「下次進場」如果已經跨進下一個 ISO 週,補記的這行 `orphan` 的 `week` 欄位算哪一週——如果算「補記當下」那一週,原本那個 `started` 所在週的配額公式會永遠少算一筆(該週 `started` 多算了 1,但終局行落在下一週,分母對不上,配額被永久少放一格,靜默發生、沒有任何測試會抓到);如果算「回溯到 `started` 原本那一週」,又跟「ts=偵測當下」這個常見寫法衝突,而 spec 也沒講是哪一種。這正好是本案立案動機那句「退化成另一種『沒人看』」(116 行)要防的同一類靜默失效,只是換了個發生位置。

建議:spec 明講孤兒/終局補記行的 `week` 欄位規則——是永遠沿用原 `started` 行的 `week`(需要補記時去讀那一行的 `week` 值,不是重算當下日期),還是接受配額計算允許「輕微少算」但要有一條週報/月報層級的重驗條件對這件事;測試③④除了「同週兩次 stale 不吃額」,建議至少加一條「`started` 與其終局跨 ISO 週」的情境(可以用 monkeypatch `datetime.now`/直接注入 `week` 字串,不必真等到週界),斷言配額計算不會因此永久漂移。

### f5 — major

spec 段落:測試草案⑫,159 行;設計 2,86 行。

引句:「逐結局分支(PASS/FAIL/stale/越界/例外/timeout)各斷言父目錄不殘留」

問題:⑫把「例外」與「timeout」列成兩個獨立分支,但這兩個詞在整份 spec 裡都不對應週帳 `kind` 枚舉(110 行:`started/done/fail/abort/stale/orphan/nag`,裡面沒有 `timeout` 也沒有 `exception`),也沒有任何一段設計節文字講清楚「dispatch 逾時」或「dispatch 丟未捕捉例外」最終會被歸類成哪個既有 `kind`(照最相近的既有先例——`scenario_probe.py` 的 `run_one`,132-138 行——`subprocess.TimeoutExpired` 被接住之後 `err="timeout"`,但仍然照樣往下跑 `judge()`,最終落進跟其他失敗情境相同的通過/失敗判定,沒有被當成一個結構上獨立的分支)。如果 selfaudit.py 的 `dispatch_note` 照同一個既有慣例處理,那麼「timeout」在系統層面根本不是一個獨立的終局分支,只是 `fail`/`abort` 判定前的一個中繼狀態,⑫把它跟 PASS/FAIL/stale/越界並列成六個平行分支,隱含的假設(它是一條需要獨立驗證清理邏輯的獨立控制流路徑)沒有被設計節證實。

更直接影響「怎麼模擬」這個問題本身的是:`dispatch_note(note, runner)` 的 `runner` 參數契約——它是否允許/預期在測試中直接 `raise subprocess.TimeoutExpired(...)` 來快速、確定性地觸發 timeout 分支,還是 `dispatch_note` 內部自己呼叫 `subprocess.run(timeout=900)`(86 行)、`runner` 只是「用什麼模型/什麼指令」這一層,timeout 判斷完全在 `dispatch_note` 內部、測試若要覆蓋到就得讓假 runner 真的卡住 900 秒(不現實,也違背測試(草)開頭「派工層注入假 runner」想要的確定性、快測性)——spec 沒有講清楚 `runner` 的呼叫介面與例外契約,implementer 兩種寫法都合理,但只有其中一種能讓⑫的 timeout 分支被便宜、確定性地測到。

建議:spec 明講 `runner` 的契約——建議讓 `runner` 直接是「跑一次派工並回傳/丟出結果」的可注入函式(例如 `runner(sandbox, prompt) -> CompletedProcess`,允許丟 `subprocess.TimeoutExpired`),`dispatch_note` 只負責接住並轉譯,測試假 runner 就能直接 `raise subprocess.TimeoutExpired(cmd, 900)` 秒測;同時明講 timeout/例外最終各自落哪個既有 `kind`(或者明講它們不落任何 kind、只影響是否清沙盒),⑫的六個分支才有各自明確、可斷言的終局狀態,不是六個分支裡有兩個只驗「父目錄消失」卻連自己該不該寫週帳都不確定。
