# 過期鎖安全接手_計劃

## 問題與裁定

[[Issues/過期鎖接手可能雙持]] 的跨程序交錯已在主線重現：B 看見過期鎖後暫停，A 搬走舊鎖並取得新鎖，B 恢復後又搬走 A 的新鎖，兩者均回取得。`os.rename` 的單次原子性不能保證它搬走的仍是先前觀察的檔案。筆記庫寫入和派工鏡頭共用 `_excl_lock_try`；後者的鎖記錄的是短命的派工者 PID，背景計算會在派工者結束後繼續。因此即使加輔助鎖，也不能用「鎖內 PID 已死」判定背景工作已停。

本案最小修法是**取消 `_excl_lock_try` 的自動過期接手**，保留 `O_CREAT|O_EXCL` 的正常取鎖。已存在的鎖一律回未取得，不因 mtime 或 PID 推論可刪；不增加第二套 `flock` 或救援輔助鎖。代價是程序異常結束後可能留下鎖，需要先確認真持有者與背景工作均已停止，再由人移除。這個取捨優先避免兩名寫者同時自認持鎖，讓後續治理帳設計有可靠地基。

筆記庫等待上限維持 60 秒，到期訊息須給鎖檔位置與人工查核方向，不能宣稱一定是另一程序仍在寫。派工鏡頭對正常短暫等待保留原 JSON 值與返回碼；若期限到時鎖齡已超過舊過期門檻且仍無快取，回「狀態未知、需檢查鎖」，不能宣稱確有背景工作在算。鎖齡不足門檻也不能證明背景仍活著，所以任何超時文案只能說「可能在算」。不自動刪鎖，也不在此案修改快取與背景工作釋放機制。

## 驗收條款

- [S1] 當兩個不同 PID 在舊鎖與新鎖交錯時，`_excl_lock_try` 應至多讓一人取得主鎖，敗者不得移除勝者的鎖；跨程序屏障先證明舊碼回 `True/True`。 [test:t_excl_lock_stale_takeover_is_single_owner]
- [S2] 當過期鎖已存在時，`_excl_lock_try` 應保留活 PID、死 PID 或符號連結的舊鎖且回未取得；無鎖時仍正常獨佔建立。 [test:t_excl_lock_existing_is_not_stolen]
- [S3] 當筆記庫遇殘留鎖時，`_vault_write_lock` 應在有限等待後拒絕寫入並給鎖位置與人工查核方向；正常取鎖、巢狀與釋放仍須維持。 [test:t_vault_stale_lock_fails_with_path]
- [S4] 當派工鏡頭遇超過舊門檻的鎖且沒有快取時，`_lens_wait_or_warm` 應不新派第二支，超時僅回狀態未知；正常暖快取與原返回碼仍維持。 [test:t_lens_stale_lock_reports_uncertainty]

最小紅燈先用 S1 的跨程序屏障重現雙持，再用 S2–S4 的獨立測試釘住可用性與訊息；每個子程序有逾時，前置斷言要證明確實走進競態間隙或對應呼叫端。修法若要求改派工鏡頭背景工作的所有權或引入新租約協議，本案停止擴張，另開案評估。

PRIOR-ART: [Python `os.open`](https://docs.python.org/3/library/os.html#os.open) 的 `O_CREAT|O_EXCL` 可在鎖不存在時獨佔建立；[Python `os.rename`](https://docs.python.org/3/library/os.html#os.rename) 只保證單次更名原子，不替先前 `stat` 做檔案身份比對。沿用既有獨佔建檔，停掉無法證明安全的自動接手；用本專案跨程序測試驗證 ABA，而非把文件當成競態證明。

RETIRE-IF: 若 S1 在原版主線就無法重現 `True/True`，撤回此方案重查實際競態；若連續四週有兩次以上因殘留鎖阻斷正常寫入，或人工復原成本大於避免雙持的收益，重開具背景工作身份的租約方案，不直接恢復按 mtime 搬鎖。

## 回退

回退程式不得把治理帳新寫者接上舊自動接手邏輯；S1 會重新翻紅時須停止推送。遇到殘留鎖，先從錯誤訊息提供的位置核對使用該筆記庫的程序與派工鏡頭背景工作是否仍在執行；無法確認就保留鎖並重試或再查，確認全部停止後才人工移除。這是人工恢復操作，不是讓工具在 timeout 時替人刪鎖。
