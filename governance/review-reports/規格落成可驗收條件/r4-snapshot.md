# 規格落成可驗收條件_計劃

白話:設計審現在是「派幾個審查員輪流讀散文、折進去、再讀一輪」,你自己的帳說它折進去的九成四是「文件寫得不夠好」、第二輪還有九成七抓到重大——散文收斂在這裡從來沒收斂過。這個計劃把力氣搬家:**驗收條款一律寫成能直接變成測試的句式並綁上測試;做錯能退回的計劃(雙向門)不派人審、只讓機器跑條款;做了回不去的(單向門)才派人。** 退場之後品質有沒有掉,靠自動記的逃逸帳量。

PRIOR-ART: ①最小解層級=改閘門語意與條款格式,不動筆記結構、不做自動生測試 ②世界解過:EARS(Rolls-Royce 出身、Kiro 拿來當規格層,五種觸發式模板轉性質測試)、亞馬遜單向門/雙向門(可逆的直接做,不可逆的才慢慢審)、Meta RADAR(低風險改動不派人審,靠硬排除+安全訊號+分數分流,落地 331K 改動、事故率人審的 1/50——★重點是他們事後量了事故率★)③借用不自建:條款存在性檢查沿用 [[Projects/條款綁測試算進度_計劃]] 的 _classify_one、風險類偵測沿用實務隱患反問、測試執行沿用 .lumos/config.json 的 run_cmd;不採 Kiro 的自動生性質測試(本 repo 2026-07 已實證自動生測試的判準不可靠)
RETIRE-IF: ①任何雙向門計劃出現 blocker 級逃逸,或前 30 份裡 major 以上逃逸 ≥3 份 → 整套退回、雙向門恢復派審(r1 改成絕對門檻,不跟單向門比——兩組本來就不對等) ①b `push-gate-unreviewed` 出現 ≥2 份 → 門判定規則重審(三條門檻的數字是拍的,見第六節) ②句式規則上線 60 天內,有條款的計劃比例反而下降(大家用不寫 [S] 繞過)→ 規則改成軟提醒或收掉 ③逃逸自動記三個月內對回率低於五成 → 對回啟發式要重做,做不好就退回人手記

## 為什麼(數字都從審查帳算;r2 訂正兩格並把口徑寫死)

| 觀察 | 數字 | 意思 |
|---|---|---|
| 折進去的是什麼型 | spec 94% / code 4% / process 1% | 設計審抓到的絕大多數是「文件本身寫得不夠好」,不是「這個做法會做出錯的程式」 |
| 每一輪最高嚴重度是重大的比例 | r1 98% / r2 97% / r3 93% | 條數遞減(11→9→7)但嚴重度沒降;跑到第二輪的 64 條裡 62 條仍抓到重大 |
| 逃逸帳 | 6 筆 / 128 條迴圈(口徑:`loop` 不以 `code-` 開頭且帳列有輪次欄位;不要求輪次則 159 條) | 這套流程從來沒量過自己的漏網率;帳空不代表沒漏,只代表沒人記 |
| 分級用量 | 記錄層級 standard 622 / high 96 / light 12;迴圈層級 93 / 10 / 11(口徑:設計迴圈=`loop` 不以 `code-` 開頭,不要求輪次欄位) | 便宜路徑有人走但少(約一成迴圈)。**r2 簡化席抓到初版「629/83/3」是多加了「帳列要有輪次欄位」的篩選,把 9 筆沒輪次的輕量檔列篩掉的假象**;d3 因此改寫理由,不再拿「沒人走」當硬擋的依據。分級看的是改動規模與風險面,不看 spec 本身的品質,這點不變。d11 的新理由(格式不是提醒)與這個數字獨立,r3 簡化席核可「不是換說法保結論」 |
| 自家硬證據 | 一份自相矛盾的測試 spec 撐過六輪設計審,實作真跑才抓到 | 散文審看不出來的,跑一次就現形(見記憶 design-loop 完整性天花板) |

世界那邊一致的說法:模型自我批評的收穫集中在前一兩輪、二到三輪飽和,**更強的模型做第二輪反而會變差**;根本原因是自我批評修得了表面問題、修不了深層錯誤,**除非有外部工具回饋**(例如測試結果)。這正好解釋上面那筆六輪沒抓到。

**兩個對不上的地方要誠實寫**:世界說二到三輪飽和,本 repo 的帳是第三輪還有九成三抓到重大。可能原因是每一輪折進去的修改本身又帶來新問題(記憶:全折之後別直接放行,再派一席又抓到三十條)——散文修改本身不可驗證,反而支持改成「跑」。另一個:「重大」是審查員自己標的,而受控實驗(在 graph-vs-code 分支的 lumos-gvc 工作樹,`Projects/圖譜效用受控實驗_計劃`)已證明模型判定員不可靠,這 98% 裡有多少是真問題帳上分不出來。

## 兩層要分開(Enzo 2026-09-17 問「不同公司規格格式不同怎麼辦」)

- **規格書**(PRD、需求單、客戶的 Word 檔、Figma)——格式不限,工具不碰。
- **驗收條款**(計劃裡 `[S1]`、`[S2]` 那幾行)——從規格書萃取出來的「可以驗的宣稱」,每份計劃通常五到十條。**句式只約束這一層。** Kiro 也是把自然語言翻成觸發式句子,不是要求一開始就那樣寫;BDD 的 Given/When/Then 同理。
- 翻譯範例:規格書寫「月租到期後給住戶三天緩衝,期間可進出但照臨停收費」→ `[S1] 當租約到期且未滿 72 小時,通行閘應放行 [test:…]`、`[S2] 在寬限期間,計費應套用臨停費率 [test:…]`、`[S3] 當到期滿 72 小時,通行閘應拒絕 [test:…]`。規格書一個字不用改。
- **翻不成句式的就不是驗收條款,是指引**(「程式碼要好讀」「效能要好」),留在散文、不掛 `[S]`、不進閘。這是功能不是缺陷:它逼作者分清「能不能驗」;翻不出來的要嘛拆到能驗(「效能要好」→「當查詢 1000 筆時,系統應在 200 毫秒內回應」),要嘛承認是指引。
- 句式關鍵字中英文都認(當/When、在…期間/While、若啟用/Where、若…則/If…then、應/shall)。**不做設定檔讓團隊自訂句式**——一開放就沒人用標準型;等真有第二個團隊撞到再說。

### 二、條款句式(一條文法,五個名字)

**r1 三席抓到:初版把「狀態」型鎖死在「期間」二字,結果本篇自己的 S4、S12 就過不了自己的句式;S4 還是「在…裡,若…,則…」的複合觸發。**改成一條文法,五個型只是給人讀的名字,機械只驗這條:

```
定義行 = "- [S<n>] " 觸發子句? 主體 "應" 回應 " [test:…]" "[keeps]"?(或單向門的 [manual:…];[keeps] 可在 [test:] 之後任意位置)
觸發子句 = ("當" | "在" | "若啟用" | "若") 內容 分隔 ("則")?      分隔 = "," | "，"
無條件型 = 沒有觸發子句,而且句首不是 當/在/若(★這條排除規則是硬的,否則任何句子都能落入無條件型兜底★)
停用詞   = 當然|當下|當前|在此|在於|若干|若是   (句首命中停用詞 → 視為無條件型,不當觸發詞)
```

- **停用詞表(r2 正確性/邊界席)**:中文沒有詞界,「當然」「在此」「若干」的第一個字元就是觸發關鍵字,又配不出逗號分隔的觸發子句,兩邊都掉不進去、條款會被靜默判成「格式看不懂」。停用詞表寫死在程式、只准增不准刪;閘擋下時訊息要說「句首『在…』被當觸發詞,不是觸發請改寫或用主體開頭;若是常用詞,把它加進 `_TRIGGER_STOPWORDS`」,不能只印「格式看不懂」。**表列不齊是已知的(r3 正確性席:「若不」「在場」「當機」「當初」都不在)**——失敗模式是明確報錯不是靜默放行,誤判率靠使用者回報加詞收斂。

- **一條條款只准一個觸發子句**;複合觸發(「在 X 裡,若 Y,則…」)一律拆成兩條。
- 「在」型不再要求「期間」二字(狀態可以是「在雙向門的計劃裡」「在閘上線前」);英文關鍵字 When/While/Where/If…then/shall 同等。
- 不合文法的定義行 → 不算條款,閘印「格式看不懂」(沿用處置閘第五步那條的處置)。
- **五個名字(無條件/事件/狀態/選項/非預期)只出現在文件與範例,不出現在程式判定裡**——r1 簡化席問「五型換到什麼」,答案是:換到可讀性與寫測試時的提示,機械上就是一條文法。
- 句式只驗形狀不驗意思;擋空話的不是句式,是第四節的「測試要紅」。模糊詞由既有 prose-lint 提醒。**誠實寫:這條文法很鬆**(r2 接手席)——機械上只驗「有沒有觸發詞前綴、有沒有『應』字」,「不應」也含「應」照過;它換到的是「一行一條款、一條款一觸發」的機械可辨識性,不是語意正確性。

### 三、綁定規則

- **雙向門**:每條條款只准 `[test:<測試名>]`,測試要真的存在——存在性走 `_clause_bindings_for`(處置閘第五步實際呼叫的那支;初版寫 `_classify_one` 是錯的,那支判的是 ★INVARIANT★ 合約行)。**每條條款的測試名必須互不相同**(r1 邊界席:十條全綁同一支也能過「全部存在」)。出現 `[manual:]` 就擋,訊息直接說「要嘛綁測試,要嘛把門升成單向」。
- **維持既有行為型的條款**加 `[keeps]` 標記,表示「這條綁的是既有的綠測試、防回歸用」;沒有標記的條款一律視為新行為,其測試在規格閘時必須是紅的(見第四節)。**標記的形狀定死(r2 邊界席)**:半形小寫 `[keeps]`,在同一定義行任意位置,收進 `[test:]`/`[manual:]` 同一個標記家族(`INV_TAG_RE`)解析——**那支正則現在沒有 `keeps` 分支(r3 邊界席 blocker:「同一家族」在程式現況是假的),落地要加一個裸標籤分支,列在「要動什麼」**;`[Keeps]`、全形括號等變體一律當沒標(=新行為要紅),閘印一句「看到疑似 keeps 變體」。**★全標 keeps 的後門(r2 正確性/邊界席 blocker)★**:S6 只驗「沒標 keeps 的每一條要紅」,十條全標 keeps 就是空集合恆真、零支紅直接放行。堵法兩條都要:①雙向門計劃**至少一條未標 keeps**(零條新行為的計劃不該走規格閘——那是純重構,走代碼審);②標 keeps 的測試**必須在計劃建立當天之前的提交樹裡就存在於同一支測試檔**:取測試檔在 `created` 日期之前的最後一次提交(`git log -1 --before=<created> --format=%H -- <測試檔>`),`git show <那個 sha>:<測試檔>` 裡要有 `def <測試名>`;找不到提交、或那版沒有這個名字 → 不合格擋下並印原因。**r2 寫的 `git log -S` 首次出現日期是錯的(r3 正確性席 blocker)**:pickaxe 搜整個歷史、不限路徑、不驗至今存活——把樁測試取一個古早被刪掉的測試名就繞過;看「那一天的樹裡有沒有」不看「歷史上出現過沒有」才擋得住,squash 也不影響(看樹不看首次出現;r3 邊界席)。改過名的測試視為新測試(擋下,訊息說「改名要先把新名字提交進歷史再標 keeps」);未提交的測試找不到 → 擋下。**三層(每條紅/至少一條未標 keeps/既存性)各防不同攻擊面,不合併**(r3 簡化席核可:拿掉任一層都重開一個已知洞)。
- **單向門**:`[test:]` 或 `[manual:≥4 字含實字]` 照舊;**計劃必須有「## 回退」節,內容 ≥20 字含實字**(r1 邊界席:「非空」會被一個標點放行)。
- **關鍵取捨**:雙向門不准 manual 是整套的核心張力。綁不上測試=這條寫得不夠清楚,或這份計劃其實是單向門。

### 四、新閘 `lumos spec-gate <計劃.md>`(印法照處置閘)

1. **門**:單向/雙向,哪個訊號命中(或缺哪一類已排除)。
2. **句式**:幾條合格、幾條看不懂、有沒有複合觸發。
3. **綁定**:缺幾條、manual 違規幾條、測試名重複幾條、回退節有沒有且夠長(單向門)。
4. **跑**:把綁定的測試真的跑一次(沿用 `.lumos/config.json` 的 `test.run_cmd`)。**前提:run_cmd 必須帶 `{method}` 能鎖單支**,沒有就擋下並印怎麼改——整套聚合退出碼歸因不到條款,跟 guard-kill 那支把它標成弱證據(`killed_unattributed`)是同一件事,規格閘不收弱證據(r1 邊界席)。
   **「紅」的判準(r2 邊界席:斷言為假跟指令跑不起來在退出碼上長一樣)**:解析測試工具輸出裡的支數(unittest 的 `Ran N test(s)`、pytest 的 `N failed / N passed` 相加),**N==1 且失敗才算紅;N==0**(匯入錯、檔名錯、環境缺)是弱證據,擋下並印原因,不當紅也不當綠;**N≥2**(r3 正確性席:參數化、同名不同類、`-k` 子字串撞名)也擋下,印「篩選匹配到 N 支,測試名要唯一,換更長的名字」。**PRIOR-ART 訂正(r3 邊界/簡化席)**:r2 寫「借 [[Systems/bound-tests-gate]]」是錯的——那支 `_ran_evidence_check` 自己的註解就寫「證的是有東西跑過,不是跑的是你要的那一支」,只認有沒有出現 `N passed`、不解析數字;解析支數是**新寫的判準**,不是借來的。**真殘餘寫進殘餘段**:本 repo 的 `run_cmd` 是 `-k` 子字串比對,967 支測試裡有 158 組名字互為子字串(簡化席機械數),那些名字的條款在規格閘會被 N≥2 擋下——這是逼作者改名,不是閘壞掉。
   **雙向門放行的條件**:①至少一條條款(零條款一律擋——r1 邊界席:空集合走 `all()` 會放行一份什麼都沒驗的計劃)且**至少一條未標 keeps**(r2)②每條綁定的測試都存在且名字互不相同 ③沒標 `[keeps]` 的每一條,其測試現在都是紅的;標了 `[keeps]` 的可以綠但要通過第三節的既存性檢查。**「至少一支紅」改成「每條新行為各自紅」**(r1 正確性/邊界/簡化三席:一支樁測試就能讓一批不相干的條款集體過關)。**成本誠實寫(r2 簡化席)**:這是把寫測試的工搬到設計審之前——一份八條條款的計劃要先寫八支會紅的測試;S13 健檢要順便印「每份雙向門計劃的條款數與紅測試數」,RETIRE-IF ② 的訊號出現時才分得清是規則太嚴還是沒空。
- **殘餘(寫明,不假裝解掉)**:「綁一支永遠失敗的樁測試」機械上仍擋不住;本 repo 既有的處置是代碼審與 guard-kill 殺傷力驗證,規格閘不重做。「先另開一個不相干的提交預埋樁測試、之後再標 keeps」(r3 簡化席)機械上也擋不住,靠第六節逃逸帳事後量。「鎖單支」靠 `-k` 子字串是做不到的(見上),靠 N≥2 擋下逼改名。

### 五、逃逸自動記(r1 五席在「來源該多寬」上兩個方向都打,這裡定死語意)

**逃逸的定義**:「一個本該在設計審/規格閘被抓到的缺陷,在下游現形」。**流程沒走完**(缺表態、缺審查留痕但計劃本來就是單向門)**不是逃逸**;但**「計劃被判成雙向門、跳過審查,結果下游擋下」是逃逸**——那正是門判錯的訊號(r1 接手/正確性席)。

三個來源,各自的篩法寫死(初版只收窄了推送閘一路,r1 簡化/回滾席抓到另外兩路沒篩):

| 來源 | 記的條件 | 不記 |
|---|---|---|
| 代碼審 | `code-<主題>` 裡**有一條 `finding_kind=code` 的發現、它自己的嚴重度 major 以上**(逐條嚴重度走新的 `--finding-severity`;沒給嚴重度、**或給了嚴重度但沒給型別**(r3 邊界席:分不出是不是 code 型不能謊報成逐條精度)就退回粗判並在逃逸帳標 `precision: round`——r2 回滾席:輪級 severity 是整輪最高值,一條 spec 型 major 配一條 code 型 minor 也會誤記) | spec/process 型的發現(文件缺欄位、流程要求的東西) |
| CI | 結論在 `_CI_RED` **且失敗步驟是測試步**:帳上 `failed_step` 長「工作名/步驟名」、多步用 `;` 串,**只看每段「/」後面的步驟名**(r3 回滾席 blocker:本 repo 唯一的工作叫 `test`,看整串會把 `test/Anchor verify` 這種也當測試步——帳上已有真實列),步驟名切詞後有一個詞等於 test/tests/pytest/unittest/testing、**或含中文「測試」**(r3 邊界席:切詞只認 a-z0-9,「自主迴圈測試」切成空)(`_ci_step_is_test`;r2 正確性席:子字串會把 latest / attestation / contest 當測試步) | build/lint/timeout/startup_failure |
| 推送閘 | ①「受波及合約的測試沒過」;②**只認「tier=high 且…」開頭的缺留痕句**(r2 回滾席:測試紅的擋下句尾巴也帶 `tier=high`,認整個詞會兩筆都記、第二筆歸因錯)、而該計劃有 `kind: spec-gate` 雙向門留痕——階段記成 `push-gate-unreviewed` 分開數(r2 架構對齊席:欄位值一律連字號,本 repo 沒有冒號複合值) | 缺表態;單向門計劃的缺留痕(它本來就該審,是流程沒走完) |

- 對回計劃:代碼審用 `code-<主題>`→`<主題>`;CI 與推送閘用提交範圍碰到的計劃筆記(`git -c core.quotePath=false diff --name-only`,**路徑存在性比對兩邊都做 NFC**,r1 邊界席)。對不回不記。
- 去重鍵(計劃、階段、sha)。**寫側上 `_vault_write_lock`**(r1 回滾席:兩個 hook 同時寫會繞過去重)。
- **fail-open 的失敗要看得見**:每次自動記失敗,往治理帳寫一筆 `kind: escape-auto-failed`(r1 回滾席:無人看顧時 stderr 等於消失)。**治理帳也寫不進去(唯讀、磁碟滿)就只剩 stderr,沒有第三層兜底**(r2 回滾席)——接受,而且**帳上量不到**(r3 回滾席:雙重失敗依定義不會在治理帳留下任何東西,r2 那條「看治理帳有無 escape-auto-failed」的回頭條件是結構性瞎的,已刪);唯一線索是 vault 出現唯讀/磁碟滿的系統層事故,事故筆記要回查逃逸帳斷點。
- **過渡期現況(r2 正確性席)**:`spec-gate` 還沒落地、沒有任何指令會寫雙向門留痕,所以 `push-gate-unreviewed` 這一路現在**恆為零筆、空轉不炸**;看帳的人別把零當機制壞了。
- **帳是 git 追蹤檔,hook 只 append 不 commit**(r1 回滾席):規則寫死——健檢加一段「逃逸帳有未提交列」提醒;提交紀律照既有治理帳(governance-log 同款)。不讓 hook 自己 commit。
- 逃逸紀錄帶門與當時的四行排除理由(從 spec-gate 留痕取):雙向門逃逸時一眼看得到「它當初說已排除什麼、結果撞到什麼」——不補人簽門之後唯一能追責的地方。

### 六、退場條件(先寫死,結果出來前不改)

**r1 簡化席抓到初版的比較不成立**:「雙向門逃逸率高於單向門就退回」——單向門有人審、雙向門沒人審,雙向門逃逸率高幾乎是必然,分不出「門判錯」跟「審查有效」。改成**絕對門檻**,不跟單向門比:

- 健檢加一段:雙向門放行了幾份、逃逸幾筆(按階段分:code-loop / CI / push-gate / push-gate-unreviewed)、單向門同樣(只當描述)。
- **主要指標:雙向門計劃的逃逸率(分母=有 spec-gate 雙向門留痕的計劃數)。**
- **撤除條件(取代 RETIRE-IF ①)**:①任何一份雙向門計劃出現 blocker 級逃逸 → 立刻退回;②前 30 份雙向門計劃裡 major 以上逃逸 ≥ 3 份(10%)→ 退回;③`push-gate-unreviewed` 出現 ≥ 2 份 → 門判定規則重審。**這三個數字是拍的**(r2 簡化席:此刻零份雙向門上線,不可能有經驗分布)——它們的正當性只來自 RETIRE-IF 自己會收斂,不是實證。
- **計數口徑寫死(r2 邊界席:本篇的量法自己就訂正過三次)**:分母=審查帳裡 `kind: spec-gate` 且 `door: two-way` 的計劃,按留痕時間排序取前 30;每筆留痕帶 `door_rule` 版本;門判定規則改版 → 從零重數 30 份,舊帳留著不重分類。**分子只數 `precision: finding` 與手動記的列**(r3 正確性/接手/回滾三席:`precision: round` 是 d12 自己承認的粗判,拿它湊門檻會讓承重牆被假陽性推倒);round 的列 S13 另印一行只當描述。**誰數:S13 健檢印出來,人讀、人裁、不自動擋**(r2 回滾席:「絕對門檻」聽起來像機械閘,其實跟本專案所有 RETIRE-IF 一樣是人執行)。
- **上線順序寫死**(r1 回滾席:承重牆的量測工具現在不存在):逃逸自動記三來源(已落地)→ S13 健檢段 → 才准開放雙向門放行。**S13 沒落地前,規格閘一律當單向門處理。**

## 實務隱患

- **金流/對外送出/不可逆**:本案不碰業務資料,但**它決定哪些計劃可以不審**——判錯門就是把不可逆的改動放進不審的通道。處置:門判定只認機械訊號、作者只能往嚴格調、逃逸帳按門分開量、RETIRE-IF ①。
- **守衛面**:改的是處置閘的不可變合約行。處置:改動綁測試、走設計審(本案自己是單向門)、代碼審。
- **可繞過**:整份不寫 `[S]` 就不進閘。處置:RETIRE-IF ② 量「有條款的計劃比例」;doctor 印。
- **已排除:效能**——閘跑的是綁定的那幾支測試不是全套,理由:全套留給推送閘。
