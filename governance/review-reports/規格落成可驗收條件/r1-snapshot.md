# 規格落成可驗收條件_計劃

白話:設計審現在是「派幾個審查員輪流讀散文、折進去、再讀一輪」,你自己的帳說它折進去的九成四是「文件寫得不夠好」、第二輪還有九成七抓到重大——散文收斂在這裡從來沒收斂過。這個計劃把力氣搬家:**驗收條款一律寫成能直接變成測試的句式並綁上測試;做錯能退回的計劃(雙向門)不派人審、只讓機器跑條款;做了回不去的(單向門)才派人。** 退場之後品質有沒有掉,靠自動記的逃逸帳量。

PRIOR-ART: ①最小解層級=改閘門語意與條款格式,不動筆記結構、不做自動生測試 ②世界解過:EARS(Rolls-Royce 出身、Kiro 拿來當規格層,五種觸發式模板轉性質測試)、亞馬遜單向門/雙向門(可逆的直接做,不可逆的才慢慢審)、Meta RADAR(低風險改動不派人審,靠硬排除+安全訊號+分數分流,落地 331K 改動、事故率人審的 1/50——★重點是他們事後量了事故率★)③借用不自建:條款存在性檢查沿用 [[Projects/條款綁測試算進度_計劃]] 的 _classify_one、風險類偵測沿用實務隱患反問、測試執行沿用 .lumos/config.json 的 run_cmd;不採 Kiro 的自動生性質測試(本 repo 2026-07 已實證自動生測試的判準不可靠)
RETIRE-IF: ①跑滿 30 份雙向門計劃後,雙向門的逃逸率高於單向門 → 整套退回、雙向門恢復派審 ②句式規則上線 60 天內,有條款的計劃比例反而下降(大家用不寫 [S] 繞過)→ 規則改成軟提醒或收掉 ③逃逸自動記三個月內對回率低於五成 → 對回啟發式要重做,做不好就退回人手記

## 為什麼(數字都是 2026-09-16 從審查帳算的,948 筆設計審紀錄)

| 觀察 | 數字 | 意思 |
|---|---|---|
| 折進去的是什麼型 | spec 94% / code 4% / process 1% | 設計審抓到的絕大多數是「文件本身寫得不夠好」,不是「這個做法會做出錯的程式」 |
| 每一輪最高嚴重度是重大的比例 | r1 98% / r2 97% / r3 93% | 條數遞減(11→9→7)但嚴重度沒降;跑到第二輪的 64 條裡 62 條仍抓到重大 |
| 逃逸帳 | 6 筆 / 127 條迴圈 | 這套流程從來沒量過自己的漏網率;帳空不代表沒漏,只代表沒人記 |
| 分級用量 | standard 629 / high 83 / light 3 | 便宜路徑早就有,但幾乎沒人走;而且分級看的是改動規模與風險面,不看 spec 本身的品質 |
| 自家硬證據 | 一份自相矛盾的測試 spec 撐過六輪設計審,實作真跑才抓到 | 散文審看不出來的,跑一次就現形(見記憶 design-loop 完整性天花板) |

世界那邊一致的說法:模型自我批評的收穫集中在前一兩輪、二到三輪飽和,**更強的模型做第二輪反而會變差**;根本原因是自我批評修得了表面問題、修不了深層錯誤,**除非有外部工具回饋**(例如測試結果)。這正好解釋上面那筆六輪沒抓到。

**兩個對不上的地方要誠實寫**:世界說二到三輪飽和,本 repo 的帳是第三輪還有九成三抓到重大。可能原因是每一輪折進去的修改本身又帶來新問題(記憶:全折之後別直接放行,再派一席又抓到三十條)——散文修改本身不可驗證,反而支持改成「跑」。另一個:「重大」是審查員自己標的,而受控實驗(在 graph-vs-code 分支的 lumos-gvc 工作樹,`Projects/圖譜效用受控實驗_計劃`)已證明模型判定員不可靠,這 98% 裡有多少是真問題帳上分不出來。

## 兩層要分開(Enzo 2026-09-17 問「不同公司規格格式不同怎麼辦」)

- **規格書**(PRD、需求單、客戶的 Word 檔、Figma)——格式不限,工具不碰。
- **驗收條款**(計劃裡 `[S1]`、`[S2]` 那幾行)——從規格書萃取出來的「可以驗的宣稱」,每份計劃通常五到十條。**句式只約束這一層。** Kiro 也是把自然語言翻成觸發式句子,不是要求一開始就那樣寫;BDD 的 Given/When/Then 同理。
- 翻譯範例:規格書寫「月租到期後給住戶三天緩衝,期間可進出但照臨停收費」→ `[S1] 當租約到期且未滿 72 小時,通行閘應放行 [test:…]`、`[S2] 在寬限期間,計費應套用臨停費率 [test:…]`、`[S3] 當到期滿 72 小時,通行閘應拒絕 [test:…]`。規格書一個字不用改。
- **翻不成句式的就不是驗收條款,是指引**(「程式碼要好讀」「效能要好」),留在散文、不掛 `[S]`、不進閘。這是功能不是缺陷:它逼作者分清「能不能驗」;翻不出來的要嘛拆到能驗(「效能要好」→「當查詢 1000 筆時,系統應在 200 毫秒內回應」),要嘛承認是指引。
- 句式關鍵字中英文都認(當/When、在…期間/While、若啟用/Where、若…則/If…then、應/shall)。**不做設定檔讓團隊自訂句式**——一開放就沒人用標準型;等真有第二個團隊撞到再說。

## 設計

### 一、門怎麼判(機械;預設單向,雙向要證明)

**★先講帳面事實(2026-09-17 查;前掃訂正過一次:初版寫 34 篇、三類零篇,是錯的)★**:風險標籤是寫筆記的人自己掛的、工具只讀不判;538 篇裡只有 **40 篇**掛了——守衛面 29、不可逆 5、金流 2、對外送出 0。**稀疏、而且集中在守衛面**:靠「掛了標籤才算單向門」會讓多數該審的計劃漏成雙向——往鬆的方向錯,正好是最不能錯的方向。**因此預設翻過來:什麼都沒寫=單向門;雙向門要證明。**

**硬單向門(機械、不可申辯,任一命中即是)**:
1. 實務隱患反問的關鍵字表命中四類任一(金流/對外送出/不可逆/自我治理;表在 `PITFALL_CLASSES`,沿用不另建)。光是**討論**這些詞也會命中——誤判的代價只是多一次審查,落在安全那邊,接受。
2. 計劃連到的節點(`related`、`lands_in`、正文 `[[連結]]`)帶 `★IRREVERSIBLE★` 或 `★CHECKPOINT★` 合約行,或掛任何 `risk/` 標籤。
3. 作者在開頭欄位寫 `door: one-way`。

**雙向門的條件(全部滿足才算)**:硬單向門三條都沒命中,**且**「實務隱患」節裡對四類各有一行 `已排除:<類>:<理由>`,每行理由 ≥4 字含實字(跟 manual 同一條規則)。缺任何一類 → 當單向門,閘印出缺哪一類。

**★這四行通常是 AI 自己寫的——這是自我認證,沒有獨立性(Enzo 2026-09-17 裁:不補人簽門、不派模型看,靠逃逸帳事後量)★**。代價寫明:門判定變成「AI 說它退得回,就當它退得回」,唯一的糾錯是第五節按門分開的逃逸率與 RETIRE-IF ①。為了讓逃逸能追責,規格閘留痕時**要把那四行排除理由一起記進帳**,逃逸紀錄對回計劃時把它們印出來。

作者寫 `door: two-way` 沒有意義(不會比機械判定更鬆);寫 `door: one-way` 有意義(直接硬單向)。

### 二、條款句式(五種觸發式,中文版)

| 型 | 定義行形狀(`- [SN] ` 之後、`[test:]` 之前) |
|---|---|
| 無條件 | `<主體>應<回應>` |
| 事件 | `當<觸發>,<主體>應<回應>` |
| 狀態 | `在<狀態>期間,<主體>應<回應>` |
| 選項 | `若啟用<功能>,<主體>應<回應>` |
| 非預期 | `若<條件>,則<主體>應<回應>` |

不合五型的定義行 → **不算條款**,閘印「格式看不懂」(沿用處置閘第五步「像清單項卻用了不認得的前綴」那條的處置)。**句式只驗形狀不驗意思**——「當使用者按下,系統應正確處理」形狀合格;擋空話的不是句式,是第四節的「測試要紅」。模糊詞由既有的 prose-lint 提醒,不重做。

### 三、綁定規則

- **雙向門**:每條條款只准 `[test:<測試名>]`,測試要真的存在(沿用 `_classify_one`)。出現 `[manual:]` 就擋,訊息直接說「要嘛綁測試,要嘛把門升成單向」。
- **單向門**:`[test:]` 或 `[manual:≥4 字含實字]` 照舊;**但計劃必須有「## 回退」一節且非空**(亞馬遜那條:單向門必須寫回退計劃,雙向門不用因為回退本來就便宜)。
- **關鍵取捨**:雙向門不准 manual 是整套的核心張力。綁不上測試=這條寫得不夠清楚,或這份計劃其實是單向門。

### 四、新閘 `lumos spec-gate <計劃.md>`(印法照處置閘)

1. **門**:單向/雙向,哪個訊號命中。
2. **句式**:幾條合格、幾條看不懂。
3. **綁定**:缺幾條、manual 違規幾條、回退節有沒有(單向門)。
4. **跑**:把綁定的測試真的跑一次(沿用 `.lumos/config.json` 的 `test.run_cmd`)。**雙向門放行的條件:每支測試都存在,而且至少一支是紅的。**

- **為什麼要紅**:規格階段功能還沒做,綁定的測試應該紅;全綠代表綁的是舊測試冒充,什麼都沒驗。這是測試先行的機械版。「維持既有行為」型的條款綁到既有綠測試是合理的,所以要求「至少一支紅」不是「全紅」。
- 雙向門四步全過 → 印 `PASS(雙向門):直接實作,不派審`,並在審查帳寫一筆 `kind: spec-gate` 留痕(推送閘與代碼審才知道這份計劃是這樣放行的)。
- 單向門 → 前三步過了印「接著走 `lumos loop next`」;**處置閘第五步改成呼叫同一支條款檢查器**(單一來源,不留兩份規則——這是改 [[Systems/design-loop]] 的不可變合約行,要綁測試加審計)。
- **推送前**:同一批條款的測試必須全綠才准推(現有推送閘加一條)。**規格閘要紅、推送閘要綠,兩頭夾住。**

### 五、逃逸自動記

- 三個來源:代碼審 major 以上的發現、CI 紅、推送閘擋下——**只認「受波及合約的測試沒過」那型**;缺表態、高風險缺審查留痕這些是流程未完成,不是下游抓到缺陷,記進逃逸帳會把「漏網」跟「沒走完流程」混在一起(前掃抓到第一版掛勾對任何擋下都記,已收窄)。
- 對回計劃:代碼審本來就帶計劃(`pass --note`);CI 與推送閘用**該提交範圍碰到的計劃筆記**對回(`git diff --name-only <範圍> -- docs/*/Projects/`)。對不回的不硬記。
- 去重鍵:(計劃、階段、提交 sha)。寫進既有的 `.escape-log.jsonl`,不開新帳。
- **逃逸紀錄要帶門與當時的四行排除理由**(從 spec-gate 留痕取):雙向門逃逸時,一眼看得到「它當初說已排除什麼、結果撞到什麼」——這是不補人簽門之後,唯一能追責的地方。
- **關鍵取捨**:對回是啟發式,會漏記也會誤記;但現在是 6 筆對 127 條,**先有帳再談精度**。統計時按門分開。

### 六、退場條件(先寫死,結果出來前不改)

- 健檢加一段:雙向門放行了幾份、逃逸幾筆;單向門同樣;逃逸率按門分開印。
- **主要指標只有一個:每種門的逃逸率。**其他一律探索性、不做顯著性宣稱。
