## Finding 1
severity: major
blocking: 是(照字面實作,改動可能一支測試都不跑就放行,這是合約漏洞)
spec 段落:做法 1(affected 的條件)、做法 3(掛鉤行為)

問題:affected 的條件只要求「抽得出關鍵字」和「選中不超過一半」,沒有「至少選中 N 支」,也沒有「每個改到的函式都要有測試對應」。選中 0 支或極少時,掛鉤只印一行說明就放行,只跑了文件子集。

佐證:
- 目前 `scripts/lumos` 有 2817 個頂層函式,其中 1763 個(62.6%)沒有任何一支 `t_` 測試整字提到。這 1763 個只是「完全沒被測試直接點名」,不代表沒被測到。
- 最近 60 個提交裡,56 個抽得出函式名關鍵字。其中 52 個至少有一個改到的函式是 0 命中(93%)。
- 加上 spec 的「擴一層」後,仍有提交只選中 0、1、2、2、4、4 支:`18e8398db`(3 個關鍵字,選中 0)、`d1570f83c`(2 個關鍵字,選中 1)、`36596e03b`、`672e76f61`、`d9b5559af`、`0ebde097e`。
- `18e8398db` 這種改動在 spec 下會是 affected,推送前只跑文件子集就放行。
- 「超過一半就全套」這條在樣本裡一次都沒觸發。最大選中數是 `28c8f505c` 的 940 支,佔 29%,也就是這條門檻形同虛設。真正兜底的只有合併後全套。
- 執行器 `_keys_suite_select` 的 `cap=0.3` 是另一個洞。單一關鍵字選中超過三成就被整個丟掉,只在 stderr 提示。spec 的「一半」跟執行器的「三成」不一致,而且沒說「被丟掉的關鍵字」要不要算抽不出關鍵字。我用目前的函式名沒量到被丟掉的,但 `cmd_` 的子命令名(如 `check`)和檔名這類泛用詞有機會超過三成。丟掉之後,這次改動就少了一個關鍵字的覆蓋,而且不會退全套。

引句:「關鍵字選中的測試數不超過全部的一半(超過就沒有省到,直接全套)。」

引句:「改成「每片都回 3 才算一支都沒選到」」

佐證: `scripts/test_lumos.py:58`(`_keys_suite_select`,cap 預設 0.3)、`scripts/hooks/pre-push:962`(`_krc` 為 3 時只印提示、不擋)

建議:加一條「每個改到的頂層函式(含擴一層後)至少要有一支測試命中,否則整次退全套」,或至少要求選中數有下限。同時說明被 cap 丟掉的關鍵字怎麼處理。

## Finding 2
severity: major
blocking: 是(「擴一層」的口徑不明,選中數可以差到十倍,而且直接影響漏抓率)
spec 段落:做法 1 的「擴一層」

問題:spec 只寫「`_` 開頭輔助的直接呼叫者也算」,有三處沒定義清楚。

1. 呼叫者若是 `cmd_x`,要不要補子命令名 `x`?測試多半走 CLI,用的是字串 `"x"`,不是函式名 `cmd_x`。
   - 我分別算了「不補」和「補」兩種:`ab2a73097` 是 48 對 228,`84804c100` 是 13 對 152,`d080f9efd` 是 6 對 102,`20c3353f5` 是 37 對 113。
   - 兩種口徑差最多約 10 倍。照 spec 字面(只有呼叫者函式名),`cmd_` 呼叫者的 CLI 測試會被漏掉。
2. 非 `_` 開頭的公開輔助(如 `find_vault`)完全不擴。spec 沒說為什麼只擴 `_` 開頭的。
3. 只擴一層。改底層輔助 → 中間函式 → `cmd_` → 測試用 CLI 字串呼叫,第二層就斷了。

佐證:`77317a880` 直接選中 7 支,擴一層選中 448 支,可見選測對呼叫鏈很敏感。

引句:「擴一層:`scripts/lumos` 裡改到的是 `_` 開頭的輔助時,直接呼叫它的頂層函式也算」

另外,spec 的〈現況〉表寫「典型改動選中 2–233 支」。我的樣本是 0 到 940 支,而且有 5 個提交選中 ≤4 支。

## Finding 3
severity: major
blocking: 是(照字面實作,會把部分執行器函式判成「該走關鍵字」,選測失準)
spec 段落:做法 2 的「機械判準」

問題:判準是「非 `t_` 開頭、而且沒有任何一支 `t_` 測試原始碼整字提到」就算執行器。我照字面實作後,`test_lumos.py` 有 833 個非 `t_` 頂層函式,其中 31 個被判成執行器,但分成兩類。

1. 23 個是被別的輔助呼叫的測試輔助鏈,不是執行器。例如 `_keys_suite_select` 和 `_helper_sources_in`。後兩個正是選測邏輯本身,卻因為沒有 `t_` 直接提到而被判成執行器。這種誤判方向是保守的,但會讓判準的名單不穩。
2. 反過來,被任何一支 `t_` 提到的執行器函式會被歸到關鍵字路線。例如 `_load_lumos_inproc` 或 `_isolate_environment`,只要有一支測試整字提到(很容易發生),改它就只跑那幾支。
   - 我沒逐一驗這兩個名字,但判準本身讓這種情況成立:「被一支測試提到」不等於「它不影響其他測試」。
   - `main()` 的註解也寫明它是 `GIT_DIR` 清除與分片入口,影響所有測試。
   - 現行 `_helper_sources_in` 在 `scripts/test_lumos.py:46` 對 `main` 也是硬編碼例外。

另外,`test_lumos.py` 有 271 個模組層級常數和 fixture(`_RC_*`、`_MS_*`、`_MB_*`、`_MS_FAKE_ADB` 等)。改常數時,hunk 標頭只會落在前一個 `def` 上,函式名正則抓不到它。常數改動搭配一個函式改動時,用到該常數的測試會漏。

引句:「機械判準:頂層函式名不是 `t_` 開頭、而且沒有任何一支 `t_` 測試的原始碼整字提到它」

佐證: `scripts/test_lumos.py:48766`(`main`)、`scripts/test_lumos.py:34`(`_HELPER_SRC_CACHE`)

建議:執行器清單寫成明列名單(像 `_SELECTION_FUNCS` 那樣登記),或改成「檔內非 `t_` 頂層函式與模組層級非常數敘述一律全套,只有明確登記的測試輔助才走關鍵字」。
