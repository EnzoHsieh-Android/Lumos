### f3 ⚠

severity: major
blocking: 是

「節點名白名單」的適用範圍跟「分支新增節點只列名」規則的順序沒定義,兩者字面上互相矛盾——這是判不準的地方,附上兩種讀法各自的後果。design §2 point 3 對分支新增節點的行為是「找不到 base 版就列名、標未貼內容」,point 4 才追加一句「節點名同樣過白名單」;但白名單條件是「在 base 的 `git ls-tree` 裡追蹤」,分支新增節點依定義不在 base——若照 point 3 字面(先判斷 base 有無→無則直接列名)實作,白名單檢查很可能只掛在「找得到 base 版本、要不要 git show」那條路徑上,新增節點的原始檔名(允許字元含 CJK/底線/連字號,長度到 120)會整串原樣顯示,等於 r1 blocker②(檔名逐字注入)在「全新節點名」這個特例上原封不動;若白名單真的無差別套用到所有節點名,point 3 講的「分支新增→只列名」就永遠印不出名字(自相矛盾,只能印「(節點名不合規)」之類的佔位符,design 沒寫這條分支)。節點識別(`node` 值)100% 來自工作樹當下的檔案系統列舉(`scripts/lumos:193` `for p in sorted(vault.rglob("*.md")):`、`n.rel`/`n.stem` 直接取自檔案路徑),不是從 base 讀出來的固定值,所以「圖譜節點名本來就是主線的」這個前提本身不成立——這正是修訂稿常見的「補進來的段落自帶未查證宣稱」。

### f4

severity: minor
blocking: 否

已試:讓 `git show <base>:<節點路徑>` 吐出攻擊者內容——擋住。`base` 是標記 `LUMOS-IMPACT: <base>..HEAD` 左側的值,由派工的編排者依實際 diff 範圍寫入(見「跟既有手貼格的關係」一節,標記寫死在模板固定一行),不是攻擊者能在分支內容裡塞進去的東西;攻擊者控制的是分支這一側(HEAD),base 指向主線,`git show` 對 base 那顆 commit 的樹狀態解析是 git 內部機制,分支上重新命名/移動檔案、改工作樹內容都不影響 base 樹裡同一路徑解出來的內容。也試過用「檔案改名成 base 沒有的名字、再讓 hook 誤把工作樹版本當 base 版本讀」——找不到路徑:設計就是「base 不存在→只列名不貼內容」(不是退回工作樹讀),`git show` 找不到就直接是「node 在 base 不存在」的分支,沒有 fallback 到工作樹的邏輯可以濫用。

引句:「內容用 `git show <base>:<節點路徑>` 讀★base 那版★」
