### f2 `--repo` 若指到 repo 子目錄,`ls-tree`/`git show` 吐出的路徑基準會跟白名單用的 repo-root-relative 路徑對不上

severity: major
blocking: 是

實測:在一個 git repo 的子目錄 `sub/` 裡執行 `git ls-tree -r --name-only HEAD`(無 pathspec),回傳的是相對子目錄的路徑(`nested/inner.txt`),不是相對 repo 根的路徑(`sub/nested/inner.txt`)——`git rev-parse --show-toplevel` 雖然正確找得到真正的根,但 `ls-tree` 本身不會自動換算。r3 新訂的 `--repo` 解法「先 `CLAUDE_PROJECT_DIR`、再 payload 的 `cwd`」照抄自 `impact-hook.py:436`,而該函式(以及 `cmd_impact_diff`)拿到 `--repo` 後直接當 `git -C <repo> …` 用、不會往上找 `.git`;若 `CLAUDE_PROJECT_DIR` 剛好指到 repo 子目錄(monorepo 或使用者從子資料夾開 session 都會發生),`ls-tree` 白名單與 `docs/<slug>-knowledge/+node` 這個 repo-root-relative 路徑就永遠對不上,節點永遠判定「不在 base 樹裡」,鏡頭整批靜默熄燈。

引句:「先 `CLAUDE_PROJECT_DIR` 環境變數、再 hook payload 的 `cwd`」
file: `scripts/hooks/claude/impact-hook.py:436`(`repo = os.environ.get("CLAUDE_PROJECT_DIR") or payload.get("cwd", "")`,r3 明講要比照的既有慣例,本身沒有换算成 repo 根的步驟)
file: `scripts/lumos:16344`(`repo_root = Path(repo) if repo else None`——只有省略 `--repo` 才會往上找 `.git`,顯式給值就直接採用,不驗證是否為根目錄)

### f3 SHA-256 倉庫的 40 位十六進位驗證與快取鍵規則,實測必然判假

severity: minor
blocking: 否

實測 `git init --object-format=sha256` 建的 repo,一個真實 commit 的 `git rev-parse HEAD` 輸出是 64 碼十六進位,`re.match(r'^[0-9a-f]{40}$', ...)` 對它回 `False`。這代表在 SHA-256 倉庫下,「base 必須主線可達」的 40-hex 檢查與快取鍵的 sha 格式檢查都會對任何合法 commit 判失敗,鏡頭永久靜默不注入——不是安全漏洞(仍是 fail-open),而是與設計文接受的「查不清就放行」哲學一致的沉默失效,只是規格全文沒把這個情境算進「誠實界線」的清單。本 repo(`lumos-toolchain`)本身用 SHA-1(40 碼),此刻不受影響。

引句:「兩個 sha 都必須通過 `^[0-9a-f]{40}$` 才能當檔名」

### f4 範圍格式檢查只查「含 `..` 且不以 `-` 開頭」,無法排除三段式/空端點等畸形範圍

severity: minor
blocking: 否

實測:標記值 `a..b..c`(兩個 `..`)、`..HEAD`(空 base)、`HEAD..`(空 head)都同時滿足「含 `..`」與「不以 `-` 開頭」,會被判定為合法範圍放行到下一層;`main...HEAD`(三點語法)因整串仍含 `..` 子字串也一樣通過。這些畸形值最終大概率會在 `git rev-parse --verify <base>^{commit}` 或 `lumos impact --diff` 這層因無法解析而失敗、落回 item8 的「算不出→放行」,所以目前看不到會被利用的路徑,但「格式檢查」本身沒有驗證範圍是恰好一個 `..` 分隔的兩端點結構,判準比看起來寬。

引句:「範圍不含 `..` 或以 `-` 開頭→放行」

### f5 本地 `main`/`master` 落後於遠端主線時,合法 base 也會被判「不可達」而靜默放行

severity: minor
blocking: 否

實測重現:在暫存 repo 裡讓「主線」多推進一個新 commit,而本地 `main` 分支還停在舊點,`git merge-base --is-ancestor <新 commit> main` 回傳 rc=1(不成立)。對應到規格「主線 tip 找不到 `refs/remotes/origin/HEAD` 就退回本地 `main`/`master`」的路徑,這代表一個剛從遠端 fetch 但還沒 `git pull` 快轉本地 `main` 的開發者,即使 base 選的是百分之百真實的主線 commit,也會被這條檢查誤判放行——這是常見工作流程(分支切自 origin/main、本地 main 沒跟上)下的假陰性,規格〈誠實界線〉列的已知代價(大 diff 超時)沒有涵蓋這一種。

引句:「再 `git merge-base --is-ancestor <base> <主線 tip>`」

### f6 本 repo 的遠端根本不叫 `origin`,`refs/remotes/origin/HEAD` 這條路徑在此地是恆常死路

severity: minor
blocking: 否

實測本 repo(`/Users/enzo/harness/lumos-toolchain`):`git remote` 只印出一個名為 `Lumos`(大寫 L)的遠端,`git for-each-ref refs/remotes` 只列得到 `refs/remotes/Lumos/main`,沒有任何 `origin` 開頭的 ref。這代表在部署的目標 repo 本身,「主線 tip 找 `refs/remotes/origin/HEAD`」這條主路徑 100% 命中不到,永遠、無條件地走「沒有就本地 main/master」備援——這與 `r3-s2-載荷安全.md` f1(講本地 ref 可被惡意 `post-checkout` 鉤子改寫)是兩件獨立的事:即使完全沒有攻擊者,備援路徑在此地也不是邊界情況而是唯一實際路徑。

引句:「主線 tip=`refs/remotes/origin/HEAD` 解析到的分支,沒有就本地 `main`/`master`」
