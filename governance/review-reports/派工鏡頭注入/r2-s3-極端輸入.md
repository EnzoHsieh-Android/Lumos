### f1 ANCHOR_FILES 登記與 anchor baseline 收錄可脫鉤,無機械交叉核對

r1 blocker①要求本 hook 進 `ANCHOR_FILES` 才放行,但「進常數」跟「真的被錨住」是兩件事:`lumos anchor approve` 只把「當下實際存在的檔案」寫進 `governance/anchor-baseline.json`,若在檔案還沒建好時跑過一次 approve(或建好後忘了重跑),該檔就被印一行提醒後跳過、baseline 裡永遠不會有它。之後 `lumos anchor verify` / `lumos enforcement` 都只核對 baseline 已收錄的項目,會回報「全符,沒被動過」,完全不會提示這支新 hook 沒受保護——這正是 r1 blocker①要防的「錨點可被悄悄繞過」情境的變形,只是這次是「從沒裝上」而非「事後撤掉」。`scripts/test_lumos.py` 沒有任何測試比對 `ANCHOR_FILES` 常數行數與 baseline 實際錨點數是否一致。
引句:「④`ANCHOR_FILES` 加一行並 `lumos anchor approve`」
file: `scripts/lumos:12293`(approve 時檔案不存在→只印提醒、不寫入 baseline)
file: `scripts/lumos:12179-12197`(enforcement 的 anchor-baseline 檢查只比對 baseline 內已有項目,不比對 `ANCHOR_FILES` 常數長度)

### f2 `LUMOS-IMPACT` 標記擷取文法未定義,格式漂移或重複出現時行為不定

設計只講「派工詞含一行 `LUMOS-IMPACT: <base>..HEAD`」,沒給擷取這行的 regex/文法:冒號後空格數、標記重複出現(例如舊範例文字被貼進派工詞、或本 spec 自己的內文被當上下文貼進另一次派工)時取哪一份、要不要 trim,全部未定。本 repo 對同類 sentinel 一貫用「精確子字串比對」(`lumos-entry-hook.py` 的 `<!-- LUMOS:GRAPH-DISCIPLINE:START` 用 `str.find` 全字匹配),若新 hook 沿用同款寫法,格式差一個空格就直接判定「沒帶標記」而靜默不注入——沒有任何錯誤訊號,連 `LUMOS_HOOK_DEBUG=1` 都不會印,因為根本沒進入「有標記」分支。更麻煩的是這會讓 REVISIT 稽核(grep `LUMOS-IMPACT:` 抓派工詞留痕)產生偽陽性:grep 是寬鬆比對,能抓到格式跑掉的那一行,但 hook 內部若用嚴格比對根本沒觸發,稽核會誤判「標記有留下、機制在跑」。
引句:「才動作;沒有就逐位元原樣放行」

### f3 快取鍵靠未檢查 rc 的 `git rev-parse <base>`,失敗時仍逐字印出任意字串

實測:`git rev-parse` 對任何解析不到的字串(分支名、含斜線句點的垃圾字串、甚至 `foo; rm -rf /`)都回傳 rc≠0,但**同時把輸入字串原樣印到 stdout**(git 的已知 fallback 行為)。設計把快取檔命名描述為「存 `$TMPDIR/lumos-dispatch-lens/<sha>.json`」,`<sha>` 來源是「`git rev-parse <base>`」——若實作只取 stdout、沒檢查 returncode(spec 全文沒有一句要求檢查這支 rev-parse 的 rc,不像 `cmd_impact_diff` 對 `git diff` 明確查 `r.returncode != 0`),base 是分支名/遠端專屬分支/shallow clone 缺的 sha 這幾種畸形輸入都會讓「快取鍵」變成攻擊者可控的任意文字,若字面直接進檔名(而非先雜湊)就有路徑跳脫寫入風險。★這條判準:是否雜湊由「沿鄰居形態」暗示但非明文規定,實際風險程度視最終實作而定,標 ⚠。
引句:「存 `$TMPDIR/lumos-dispatch-lens/<sha>.json`」
file: `scripts/lumos:16343-16346`(既有 `cmd_impact_diff` 對 `git diff` 的 rc 有明確檢查,對照組存在但 spec 沒要求新的 `git rev-parse` 呼叫比照辦理)

severity: major
blocking: 是 ⚠(是否真可觸發取決於實作是否雜湊 `<sha>`,spec 文字本身沒排除風險)

### f4 `files`/節點名白名單缺空白字元,合約節點可能整條靜默消失

白名單「`A-Za-z0-9_./-`+CJK」不含空白。實測:一個路徑帶空格的合法追蹤檔(`新檔案 空格.py`)在 `git diff --name-only`(有 `-c core.quotePath=false`)能正確還原成明文,但過白名單會被判定「不合格」。對 `files` 欄位這只是「另有 N 個未列」,可接受;但設計說「節點名同樣過白名單」——若某個帶合約的固定席節點,其**節點路徑本身**含空格(其他專案的圖譜命名習慣不受本 repo 限制,而★誠實界線★明講「本機所有專案每次派工都 fire」),該節點會被整條排除,且截斷規則只講「其餘只列名」的數量提示,沒有對應「因白名單被排除的固定席節點數」計數——一個帶合約的節點可以無聲消失,鏡頭在最該亮的地方啞掉。
引句:「字元只含 `A-Za-z0-9_./-`+CJK、長度 ≤120」

severity: major
blocking: 是

### f5 `git ls-tree` 呼叫未比照既有 `git diff` 加 `core.quotePath=false`,CJK 檔名白名單必然比對失敗

實測重現(用暫存 repo):同一個 CJK 檔名,`git diff --name-only`(現有程式碼已加 `-c core.quotePath=false`)還原成明文 `docs/測試-knowledge/中文節點.md`;但同一個檔在**沒有**加 `core.quotePath=false` 的 `git ls-tree -r --name-only <base>` 下,回傳的是跳脫過的八進位字串 `"docs/\346\270\254...\347\257\200\351\273\236.md"`。設計第4點的白名單核對邏輯是「diff 出來的檔名(已還原明文)在 base 的 `git ls-tree` 輸出裡追蹤」——兩邊字串形式不一致,合法追蹤的 CJK 檔案永遠比對不上,會被誤判成「不在 base 追蹤清單」而被消毒掉。本 repo 對 `git diff` 早就因為同一類 bug 加過 `core.quotePath=false`(code comment 明寫「r2 panel major」),但 spec 對這支全新的 `git ls-tree` 呼叫完全沒提這個旗標,舊坑會在新呼叫點重演。
引句:「在 base 的 `git ls-tree -r --name-only <base>` 裡追蹤」
file: `scripts/lumos:16354`(既有 `git diff --name-only` 呼叫的 `core.quotePath=false` 修復註解:「否則 startswith/endswith 過濾全失效,r2 panel major」)

severity: major
