### f2 — severity: major
**spec 段落**:主案 v2 §2。
引句:「欄位:`lane: "soft-guard"`、`pinned: False`、保留原 score」

**問題**:這句話回應了 r2-s1 f2 指出的「lane 沒有定義排序鍵」的洞,加了 `(-score, node)`
排序鍵和「保留原 score」的說明——但「保留原 score」本身沒有定義清楚,對照現況程式碼有兩種
互斥的讀法,而**兩種讀法的落地結果差很多**:

1. **字面「保留」=沿用被降前那個分支本來會給的分數**:現行 `if contract and hop <= min(...)`
   分支(v3 之後這是 RISK 類要走的判斷)給的是硬編碼常數`round(0.40 + 0.30, 4) = 0.70`
   (`scripts/lumos:14466`),**與 L(詞彙分)、hop 完全無關**。若照這個讀法,同一次查詢裡所有被
   降的 RISK indirect 候選會**全部同分(0.70)**,`(-score, node)` 排序鍵在分數這個主鍵上完全
   打平,cap 選誰進 lane_items、誰被 `lane_dropped`,實際上退化成**按節點路徑字母序**——
   跟這題查詢的相關性(L、hop 距離)毫無關係。
2. **改寫「保留」=沿用一般 indirect 自由席的 R 公式**(`0.60*L + 0.40*G`,`scripts/lumos:14472-14473`,
   free 分支既有邏輯):分數會隨 L/hop 變化,排序才有鑑別力。

主案 §2 自己主張「五個維度全照 rescued 慣例,不是第二種做法」(獨立容器/產生端限量/不過門檻名額/
append 輸出/meta 計數)。但 `rescued` 的分數（direct 分支公式 `_dbase + (1.0-_dbase)*L`,
`scripts/lumos:14453`)本身就**不是常數**、由 L 驅動,所以 rescued 的 `(-score, hop, node)` 排序
(`:14517`)是有鑑別力的。若 lane 走讀法①(重用舊 pin 分支的常數 0.70),則「同 rescued 慣例」
這個類比在**分數這個維度上不成立**——rescued 借來的是「有意義的分數排序」,lane 若照字面
「保留」只借到了「有分數這個欄位」,精神不同。

不影響 §3 的核心結構性保證(cap 造成的截斷仍會誠實反映在 `must_in_out`,見 f4 之前的段落已核實
`out_nodes` 邏輯不受影響)——這不是「棘輪失效」等級的洞,而是「cap 選誰留下」這個機制本身
可能是無鑑別力的隨機/字母序選擇,跟診斷段落強調的「按分數competition」精神不符,而且若讀法①
成立、又疊加 f1(`cmd_impact_diff` 沒排除 lane),0.70 這個偏高的常數混進 `cmd_impact_diff` 的
`free` top-8 排序時會**系統性地**排到真正自由席候選前面(一般 hop1-2 的 R 值常低於 0.70)——
兩個洞疊加會放大彼此的影響。

**查證 file:line**:`scripts/lumos:14453,14466,14472-14473,14507-14521`(direct/indirect-pinned/
indirect-free/rescued 四種分數公式對照)。

### f3 — severity: major
**spec 段落**:工具清單 #4。
引句:「eval:P@8 母體排除 lane(含 rescued 明文化)」

**問題**:這條回應了 r2-s1 f1 提到的「eval 側也要排除 lane」,但範圍寫得不夠精確,存在一個容易
踩中的實作陷阱。`eval_edit` 現況(`retrieval_eval.py:335-359`)有兩個獨立變數都源自同一個 `res`：

```
retrieval_eval.py:335   pins = [x for x in res if x.get("pinned")]
retrieval_eval.py:336   free = [x for x in res if not x.get("pinned")]      # ← P@8/nDCG 母體,#4 要修這行
...
retrieval_eval.py:355   out_nodes = {x["node"] for x in res}                # ← must_in_out 的輸入,不該動
retrieval_eval.py:359   row["must_in_out"] = sum(1 for n in must if n in out_nodes)
```

「P@8 母體排除 lane」字面上只該改第 336 行(`free = [x for x in res if not x.get("pinned") and
not x.get("lane")]`)——這樣改的話,`out_nodes`(第 355 行)仍取自完整的 `res`(含 cap 內
lane_items),`must_in_out` 的因果鏈(被 cap 砍掉的 lane 候選,原本就不在 `res` 裡,天然反映在
`must_in_out` 掉數字;cap 內留下的 lane 候選,雖然不算進 P@8,但仍在 `out_nodes` 裡,`must_in_out`
正確算進)成立——這正是 §2 說的「口徑合一使棘輪重新有效」的機制基礎,也是本輪指名要驗證的
因果鏈,查證下來**在這個具體實作路徑下成立**。

但工具清單 #4 只寫「P@8 母體排除 lane」,沒有明講**只動 `free`、不動 `res`/`out_nodes`**——一個
同樣自然的「順手」寫法是在函式開頭先清資料:`res = [x for x in res if not x.get("lane")]`
（或任何把 336/355 兩行共用同一個「已排除 lane」的 `res`），這樣寫也「滿足」#4 字面要求的
「P@8 母體排除 lane」,但會**連帶**讓 `out_nodes` 也排除 lane——此時即使 lane 候選沒被 cap 砍
(仍在原始 JSON `results` 裡),只要它是 lane,`must_in_out` 就**恆定**漏算它,不再是「cap 觸發
時才誠實掉分」,而是「不管 cap 有沒有動,lane 候選永遠不算在 must_in_out 裡」的系統性低估——這
會**永久性**地讓 §3 宣稱的「must_in_out 結構性不退」失去意義（因為 lane 候選本來就不會被算進
must_in_out,退不退都看不出來),而且這個錯誤實作方式仍然會通過 §2/§3 目前寫法所暗示的驗收
(因為表面上「P@8 不含 lane」的要求確實被滿足了)。

工具清單 #6 測試項⑤「翻紅釘:拿掉 lane 容器→must_in_out 掉」能抓到「完全沒做 lane」的退化,
但抓不到「lane 有做、但連 `out_nodes` 也被誤排除」這種部分退化——因為那種寫法下拿掉 lane 容器
的翻紅釘測試會照樣通過(反正 lane 從來沒真的進過 `must_in_out` 的計算)。

**建議動作**(供落地時採用,非本審查要求的唯一解):工具清單 #4 明確寫成「只改 `free`
(P@8/nDCG 母體),`out_nodes`/`must_in_out` 維持讀完整 `res`」,並在 #6 測試清單加一項「lane 候選
在 cap 內、未被砍 → 仍計入 must_in_out(即使不計入 P@8)」,直接把這個邊界釘成可斷言的測試,
而不是依賴「排除 lane」這句話的字面精確度。
