### f1 — severity: blocker
**spec 段落**:主案 v2 §2/§3;工具清單 #2。
引句:「不過門檻、不佔名額、不進 free 排序」
引句:「降級節點 append 到 rescued 之後」

**問題**:v2 的核心賣點是「free 集合與排序完全不動 → P@8/nDCG 逐 byte 不變」,但工具清單只給了
**一個**錨點(`final = pins + free + rescued`,`scripts/lumos:14523`)。這一行只是最終輸出組裝;
真正決定「誰進 free 池、進去後怎麼算門檻」的是**更早**的過濾與統計:
```
scripts/lumos:14483  free = [r for r in results if not r["pinned"]]
scripts/lumos:14484  max_free = max((r["score"] for r in free), default=0.0)
scripts/lumos:14485  thresh = max(float(min_score), _impact_knob("LUMOS_IMPACT_DYN_COEF", 0.65) * max_free)
```
按 spec §2 的定義,參考道節點的欄位是 `lane:"soft-guard"`、`pinned:False`——**`pinned:False` 這件事
本身就會被 14483 這行既有的 `not r["pinned"]` 篩進 free**,除非另外排除。spec 全文沒有一句話講
lane 節點的 `score` 該給多少;示範最自然的作法(照抄現有 indirect-pinned 分支的 `0.40+0.30=0.70`,
只把 `pinned` 改 `False`)會讓 lane 節點帶著遠高於一般 free 候選的分數混進 free。

**實測**(對 `scripts/hooks/claude/impact-hook.py` 這個真實檔案跑 `impact --ranked --top 8 --json`):

| baseline(v1 現況) | 8 | 8,分數皆 0.30 | truncated=45 |
| 只改 14464 一行(工具清單#1 字面實作)、free 過濾不動 | 4 | **3** | 4 個降級節點(score 0.70)灌進 free,把 `max_free` 從 0.30 拉到 0.70,動態閾值 `0.65*0.70=0.455` 直接把全部真正的 direct 候選(0.30)砍出 free;`truncated:0→`,`rescued:3` 被迫啟動補救 |

### f3 — severity: major
**spec 段落**:主案 v2 §3。
引句:「降誰是決定論的,不需要帶 query 重算」

**問題**:「哪個節點的 `pinned` 布林值」確實與 query 無關——`_impact_contract`(合約/hop)和
`_impact_bfs`(候選圖)都不吃 query,已核實(`scripts/lumos:13872-13931`)。但 spec 把這件事
延伸到「-43/96 是確定值」這個**總數**上,而總數是「哪些筆記算 incident、哪些算 indirect」
這個**分類**的加總——這個分類不是 query 無關的。

去重邏輯(`scripts/lumos:14402-14420`)先跑 `_match_incident_triggers(rel_file, _content_probe, env)`,
`_content_probe` 來自這次改動的 delta 內容(`_delta_q`,`scripts/lumos:14388-14401`);命中 incident
的節點會從 `all_direct`/`all_indirect` 移除,**永遠 `pinned=True`**、完全不受 v2 §1 規則影響。
同一個節點(例如某個掛了 `risk/守衛面` 標籤的 hub 筆記),如果 A 這次的 delta 文字剛好命中它的
incident trigger,它這次算 incident、不受降級;B 那次的 delta 沒命中,它就落進 indirect 分支、
被 v2 §1 降級。也就是說:**同一個 (file, node) 是否被降級,取決於這次改動的實際內容**,
不是純粹由檔案結構決定。

這不影響「pinned 布林值本身跟 query 無關」這句窄敘述,但足以讓「-43/96 不需要帶 query 重算」
這句寬敘述失真——真正要重算(離線,不需要跑 BM25F/L 分數,但**要**跑 incident trigger 比對)
才能準確重現這個計數,不是純看 contract+hop 圖結構就夠。

**查證 file:line**:`scripts/lumos:14383-14420`(`_match_incident_triggers` 呼叫+去重)、
