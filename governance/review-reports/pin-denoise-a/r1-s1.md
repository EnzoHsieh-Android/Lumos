**spec 段落**:反事實
引句:「反事實(2026-08-24 離線算,同一批題)」

**問題**:「反事實」表的口徑重蹈前案已經記下的同一個測量失誤,因此它的結論(「held 43/96
噪音降、必看只降 3」)不能背書「這個設計安全」。

前案(spec 的 DEP、也是本審對照材料之一)明文記著這個教訓:
> 「離線分析為什麼沒預測到:我原本只算『固定席裡的必看被砍幾個』(答案是 0),
> ★沒算『被砍下去之後在自由席擠不擠得進 top_k』★。被砍 → 進自由席 → 分數不夠 → 擠出前 8 →
> 漏檢。這個方法論的洞要記住:降級不等於保留,自由席是會被擠掉的。」
> ——`docs/lumos-toolchain-knowledge/Projects/固定席扇出降權_計劃.md:135-137`

本審拿到的口徑資訊(對照 spec 用詞與派工說明)是這份「反事實」表用 **live vault、無 query**
算出來——即沒有帶各題真實 `delta` 當查詢文字。這正是前案教訓點名的同一種算法:只數「固定席
裡少了幾個」,沒有模擬「降級後在自由席用真實查詢競爭,最後擠不擠得進輸出」。

實測兩種口徑的差異有多大(同樣 patch 過 R1 規則,同一個候選集):
- **無 query**(比照反事實表的口徑):被降級的 RISK indirect 節點(hop=1)全部同分 0.24,
  排在自由候選池第 170~190 名(池子共 266 個候選)——技術上「還在候選名單裡」,只是名次太後面,
  被預設 quota(10)/top(8)排除在最終輸出外。
- **有 query**(真實題目 delta,production 實際用法):同一批節點的動態閾值
  `thresh = max(min_score, 0.65 × 自由席最高分)` 因為有真實詞彙訊號拉高了「自由席最高分」
  (E12 實測最高分到 1.0),導致閾值升到 0.65 這種高度——這些節點**連候選名單都進不去**,直接從
  `results` 消失,不是「排名靠後」而是「篩選就先被砍掉」。

兩種口徑得到的是質不同的失敗模式(排名擠掉 vs 閾值篩掉),而 hook 實際運作**永遠帶著真實
delta 當 query**(`scripts/lumos:14367` 起 `_delta_q = payload.get("query")`,並在
`_impact_mark_about` 之後才做 pin/free 切分與門檻篩選)。反事實表用「無 query」口徑算出來的
「必看只降 3」因此可能系統性低估——f2 的實測(E08 一題就該貢獻 3 個必看流失,不是表格暗示的
均攤到全部 held 才 3 個)已經是這個低估的直接證據。

**這一條不是說 R1 方向錯,是說「反事實驗證通過→可以進 design-loop」這個因果鏈目前立不住**:
表格measures 的東西和 production 實際發生的東西是兩套機制,結論不能互相背書。

**查證**:
- 前案教訓原文:`docs/lumos-toolchain-knowledge/Projects/固定席扇出降權_計劃.md:135-137`
- 無 query 下同分/低排名實測:`scripts/lumos`(patch 版)`impact --file scripts/lumos --ranked
  --json`(不帶 `--stdin-payload`),13 個 RISK-indirect 節點皆 score=0.24、排名 169-186/266
- 有 query 下閾值篩掉實測:同指令加 `--stdin-payload`,payload.query = 該題 goldset `delta`
  欄位,`anchor-integrity`/`design-loop`/`convergence-evidence-gate`/
  `heterogeneous-finder-ensemble` 均不在回傳 `results` 中

### f4 — severity: minor

**spec 段落**:診斷表 + 主案 1
引句:「無(事故)15 / RISK·不可逆 3」

**問題**:合約值域裡有一個容易混淆但 spec 沒說明的地方——「RISK·不可逆」和 R1 規則要保留的
「IRREVERSIBLE」是**兩個不同的軸**,字面上（尤其中文語感)很像同一件事,實際上完全是不同的
判定材料:

- `IRREVERSIBLE`(R1 要保留的硬合約):獨立掃 `summary` 欄裡的 `★IRREVERSIBLE★` 標記,
  `IRREVERSIBLE_RE = re.compile(r"^KEY:\s*(?:\([^)]*\)\s*)?★IRREVERSIBLE★\s*(.*)")`
  (`scripts/lumos:2293`)。
- `RISK·不可逆`(R1 要降級的軟標記之一):`risk/` 標籤家族裡的一個列舉值
  (`_RISK_ENUM = {"金流","對外送出","不可逆","守衛面"}`,`scripts/lumos:2738`),偵測邏輯是
  `tg.startswith("risk/")` 之後把值接在 `"RISK·"` 後面(`scripts/lumos:13898-13903`)。

`_impact_contract` 用**完全字串相等**判斷(`contract == "IRREVERSIBLE"` 才會贏過 INVARIANT,
`contract.startswith("RISK·")` 才是軟標),所以只要實作照抄 `contract in ("INVARIANT",
"IRREVERSIBLE")` 這種精確字串比對,**不會**把 `RISK·不可逆` 誤判成該保送的 `IRREVERSIBLE`
——程式邏輯本身沒有 bug。但 spec 正文自己的診斷表把「RISK·不可逆 3」和「INVARIANT 22」並列,
從未在文字裡明講這是完全不同的軸、跟 R1 規則要保留的「IRREVERSIBLE」不是同一個東西,對只讀
spec、沒去讀 `_impact_contract` 原始碼的實作者/審查員有誤讀風險(例如寫成
`"不可逆" in contract` 這種寬鬆比對就會誤放)。建議 spec 補一句明講「RISK·不可逆是 risk/
標籤家族的值,和硬合約 IRREVERSIBLE 是不同欄位/不同判定路徑,字面像但不是同一物」。

**查證**:
- `_impact_contract` 定義(兩軸/優先序/RISK 前綴組字):`scripts/lumos:13872-13905`
- `IRREVERSIBLE_RE`:`scripts/lumos:2293`
- `_RISK_ENUM` 列舉(含「不可逆」是列舉值之一):`scripts/lumos:2738`

   design-loop 裡沒有明確的「過/不過」判準可審。
2. spec 說「0=舊制逃生」暗示這是整案的回滾閥,但主案 #3(治標籤)寫入的 `about_code` 標記是
   vault 資料變更,不受這顆開關管——開關關掉後資料仍在(通常無害,因為舊制的 pin 判定本來就不
   查 `about_hit`),但「回滾」字面容易被讀成「整案復原」,建議明講「開關只管 pin 排序邏輯,
   不影響已經補上的 about_code 標記」。

兩點都不影響 R1 的核心邏輯對不對,只是讓「這個總開關到底鎖住什麼範圍」在文件層面不夠精確,
list 為 minor。

## 總結

R1 規則本身(收窄 indirect 保送到硬合約、direct 不動)照字面實作沒有邏輯錯誤;about 豁免的
「留人不踢人」方向也確實沒有違反前案 d2 訂下的安全原則(about 只能加分/留人,不能單獨當
降級或新入口的判準)。問題出在**安全網本身有洞,而 spec 判斷「安全網夠不夠」的方法又跟安全網
共享同一個測量盲區**:about 豁免對巨檔(尤其是 goldset 本身就考的 `scripts/lumos`)結構性失效
(f1);治標籤清單只列了實際所需範圍的一小部分(f2);而拿來證明「三層接應夠用」的反事實表,
用的口徑正好是前案已經明文記下會失準的那種算法(f3)。三條finding 互相印證同一個結論:
`must_in_out` 棘輪在目前寫法下極可能翻紅,不是「反事實」暗示的邊緣安全。

**最嚴重 severity:blocker**
