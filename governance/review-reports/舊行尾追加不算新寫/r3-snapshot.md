# 舊行尾追加不算新寫_計劃

白話:清舊筆記時最常做的事,是在舊句後面補一個「(更正:…)」。現在兩道檢查都把那整行當成新寫的來查——第一層(筆記形狀擋)把舊句本來就有的問題算到補更正的人頭上,第二層(筆記內容審)讓判定者重判整句舊話。這份計劃讓兩層都只看**這次補在尾巴的那段括號**。只認「起點版本裡的舊句一個字都沒動、只在尾巴補括號」,其他改法照今天整行查。

依據:
- 消費專案清漂移回傳(2026-10-02,第 3 項,去識別):在舊句後補更正括號,整行被當新寫——舊行原有的「還沒」觸發否定現況句提醒 24 條;一條上線前合法的舊 DEP 被當成新寫的 DEP 擋下,只好改寫成歷史 WHY。
- 本 repo 重現(2026-10-02,用測試小工具 `_ns_repo`/`_ns_note`/`_ns_stage` 建暫存專案):先提交 `DEP:付款走舊閘道 scripts/pay.py 還沒換掉`,再在句尾接「(更正:2026-10-02 已換成新閘道,見 `Systems/Pay`)」並暫存,`note-shape --staged` 回 1(沒寫來源的 DEP),並對原本就有的「還沒」再提醒一次。會寫成 [S1][S2] 的測試。
- 消費專案那兩批清理提交的實測(2026-10-03,`git diff -U0` 逐區塊數):346 個改動區塊裡 345 個是「刪幾行就加幾行」;按位置一對一、新行以舊行開頭的有 193 處,其中 192 處追加段是括號、長度中位 103 字、九成在 190 字內、最長 279 字;唯一不是括號的是在行尾補狀態標籤。上限與括號形狀照這組數字定(〈做法〉1)。
- 前案 [[Projects/舊行插字不算新寫_計劃]]:設計審三輪(97 條、major 27 條),末輪 4 條 major 都在「自己找舊行」的配對規則。本案換掉配對方式,其餘已審過的結論沿用(否定提醒只看新加的字、前綴提醒不套用、放寬帳用獨立種類、喚醒那一路不動)。
- 程式現況:第一層 `_note_shape_eval` 取 `_notelines_new` 的新行,對每行跑 `_ns_check_line`、`_ns_revisit_violations`,再跑「新程式檔喚醒舊引用」(用已報過的行避免重報),提交前另收否定與前綴提醒;第二層 `_note_audit_items` 用同一支取新行,`_note_audit_render_list` 把整行(`>>>` 那行)與前後文交給判定者,判定檔每列記內容編號與判定。兩層取改動都走 `_ns_diff`,解析走 `_notelines_parse_added`。提交前模式用新增行號;推送與 doctor 模式用逐提交新增的文字認新行。推送前掛鉤與 CI 的筆記形狀擋起點相同(都經 `_lens_push_base` 再截到上線點;CI 給的是 `$BEFORE`,也就是推送前遠端那條分支的頂端),淺層 clone 時兩道都整支跳過並記 `skipped-env`。

PRIOR-ART: 「只評這次改到的部分」是 lint 接 PR 的標準做法(reviewdog `-filter-mode=added`、Danger 只看 diff 行);本案在「行」之下再細到「行尾補的括號」,配對直接用 git diff 的改動區塊按位置對,不另寫找舊行的演算法;diff 的區塊讀法改成照 `@@` 計數走(同 `git apply`/unidiff 類解析器的做法);範本雜湊與版本號一起用測試釘住,照抄 `t_note_audit_reread_template_pinned`。
RETIRE-IF: 上線八週後任一成立就撤掉或重想:①從放寬帳(〈做法〉5)抽 20 行對回提交,有一半以上其實是借括號把新的程式現況塞進舊句——改回整行查;②八週內推送時一次放寬都沒有,而且抽查那段期間第二層的送審清單也沒有任何「只判這次補在句尾的」項目(第一層提交前的提醒放寬不記帳,只看這兩處會低估)——機制是死的;③筆記形狀擋改成以「欄位」或「句子」為單位判新舊,這條被取代。
REVISIT:2026-12-01 從 docs/.governance-log.jsonl 數閘 note-shape、種類 relaxed 近八週的筆數(state 是 ok 與 failed 分開數),並抽查同期第二層清單,對 RETIRE-IF ①②;failed 不是 0 先查壞在哪

## 做法

1. **配對(兩層共用一支)**:新寫 `_notelines_append_pairs(repo_root, staged, base_where, tip_where, vault_rel)` → `(配對表, 失敗原因)`。配對表是 `{NFC 路徑: {終點版本行號: 舊行原文}}`;失敗原因平常是 None,只有「git 呼叫失敗」或「例外」才帶字串(例外的類別名),這時配對表是空的、這次全不配對、照今天整行查。例外在這支函式裡吞掉(同 `_ns_negation_prepare` 回元組的先例)。**不算失敗**:沒有起點版本(新分支從空樹、起點是空樹)、沒有候選篇——這些是沒東西可比,回空表、原因 None;單篇讀不到、超過上限、解不開、路徑被 git 加引號——只有那一篇不配對,其他篇照配。
   - **起點就用呼叫端自己的範圍起點,不另算**:提交前是釘住的 HEAD(取改動用 `_ns_diff("--cached", <HEAD 的完整 sha>, "--", 圖譜目錄)`,不在兩次呼叫之間各自解析 HEAD);推送前與 CI 是 `cmd_note_shape` 已經算好的起點(`_lens_push_base` 再截到上線點,兩邊同一個);doctor 是上線點;第二層是 `_note_audit_resolve` 算好的起點。起點版本裡的行在它被推上去時已經過了第一層(或留了跳過帳),跟其他已推上去的行同等,所以拿它當「舊句」;第二層有沒有判過它不保證(天花板 3)。設計審 r1 曾改成「舊句要在主線分岔點裡」,r2 查證:那輪的前提「CI 從主線起點整行再查」不成立(見依據最後一條),而且分岔點算法會是專案裡第三套(既有 `_lens_push_base` 與 `_push_range_start`,收斂路在 [[Issues/推送前其他閘的範圍在合過主線時會多算]]),還會讓沒有本地 main 的 CI 全不配對——撤回。
   - **取改動區塊**:推送、CI、doctor、第二層用 `_ns_diff(<起點>, tip_where, "--", 圖譜目錄)`。不跟 `_NotelinesNet` 共用——它只在 `keep_other` 時建、而且刻意用到才算(代碼審 r2 併發席),本案不動它。什麼時候才跑見〈做法〉2、4。
   - **統一的區塊讀法**:新寫 `_notelines_parse_hunks(raw)`,照 `@@ -a[,b] +c[,d] @@` 的計數走(沒寫計數就是 1,計數 0 的那邊沒有行;標頭後面可以帶函式上下文);`diff --git` 重置狀態;在區塊裡照計數吃 `-`、`+`、空白開頭的上下文行,`\ No newline` 不吃計數;計數吃完才回到檔頭狀態,所以內容行 `++ x`(在 diff 裡是 `+++ x`)不會被當成檔頭。上下文行把一個區塊切成幾個「改動段」。`--- `/`+++ ` 路徑照現行(去掉 `a/`、`b/` 與尾端 TAB;被 git 加引號的路徑、`/dev/null`、改名、二進位或純改名沒有內容)——這幾種不配對。
     - **舊解析器一起改**:`_notelines_parse_added` 改成包這支(只交出被加的行與正確的新行號),所以提交前、推送逐提交、合併提交判不了的退路、`_NotelinesNet` 四處一起修掉「`++ x` 之後同檔新行全漏查」與「上下文行讓行號錯位」兩個既有洞(設計審 r1 正確性、整合、架構三席各自實測,編排者重現)。回傳形狀不變。
     - **同族另兩處不改**:`_ns_deleted_summary_lines` 自己讀被刪行、自己組 git 旗標;它只收像摘要前綴的行,那種行不會以 `--` 開頭,`---` 判斷碰不到它要的行(設計審 r2 架構席點名後查過)。`_diff_added_lines` 只有一支測試在呼叫、正式流程沒用到。
     - **釘住 git 的切法**:`_ns_diff` 加 `--inter-hunk-context=0` 與 `--diff-algorithm=myers`,走 `_ns_diff` 的呼叫端不再受本機設定(`diff.interHunkContext`、`diff.algorithm`)影響,本機與 CI 切法一樣。讀法照計數走,就算有上下文行也不會錯位。
   - **配對規則**:每個改動段裡,被刪的行數等於被加的行數才配,第 i 條被刪的對第 i 條被加的;行數不等的整段不配。插在舊行前面的新行會讓行數不等,搶不走舊行(設計審 r1 正確性席實驗,編排者重現)。
   - **每一對的條件**(常數:`_NS_APPEND_MIN_OLD`=8、`_NS_APPEND_MAX_TAIL`=300、`_NS_APPEND_MAX_LINE`=2000、`_NS_APPEND_BASE_MAX_BYTES`=524288):
     - 兩邊只去掉尾端空白(含 CR):O'=舊行.rstrip()、N'=新行.rstrip();N' 以 O' 開頭而且比 O' 長。開頭的縮排要一樣(縮排變了不算追加)。
     - O' 去頭尾空白後至少 8 個碼點(含 8)。
     - 追加段 T=N'[len(O'):]:去掉頭尾空白後,必須整段由一個或幾個「括號群」組成,群與群之間只能是空白。括號群=從 `(` 或 `(` 開始、照深度數到對應的 `)` 或 `)` 為止(半形全形視為同一種、可以混用、可以巢狀);群外有任何別的字就不算。例:「 (更正:…)」「(更正:…) (見 X)」算;「(更正) 逾時改 30 秒(見 X)」不算(中間有群外的字)。
     - T 去掉頭尾空白後不超過 300 個碼點(含 300);N' 不超過 2000 個碼點(含)。上限固定,不隨舊行變長。
     - 起點版本那一行的文字(去尾端空白)等於這個被刪的行;不等就不配。
     - **同一個脈絡**:舊行在起點版本、新行在終點版本的區塊(`_notelines_regions`)相同、兩邊都在圍欄外(`_visible_lines`)、那篇的重建標記兩個版本相同。起點版本只讀有候選的那幾篇,用 `_nodehome_cat_blobs_capped`,單篇超過 524288 位元組(大於才算超過)就那篇不配;回來的位元組自己用 `utf-8-sig` 解,行照位元組切(不換掉 CR)。拿去 git 讀用 diff 檔頭上的原樣路徑,回傳表的鍵用 NFC,兩層查表時用 `nfc(路徑)`。
   - 成本:配對對每個改動段是線性的(按位置對,不做兩兩比較)。新函式照 `lint-new` 的複雜度上限拆小(`_note_shape_eval`、`cmd_note_shape` 已有放行的複雜度告警,改動讓數字變時照既有放行流程處理,不新增放行)。
2. **第一層:只報多出來的違規**。配到的新行 N(舊行 O):
   - **用到才算、但要在喚醒之前扣**:配對表用一個取得函式包起來(第一次呼叫才跑配對,整個範圍一次、之後重用)。`_note_shape_eval` 逐篇處理時,某篇的 `_ns_check_line`/`_ns_revisit_violations` 有違規才呼叫它;扣減在那一篇的違規收進總表**之前**做,所以被放寬的行不會留在「新程式檔喚醒」那一段用來避免重報的已報集合裡,喚醒那一路會照報它([S20])。
   - `_ns_check_line` 對 N 與 O 各算一次(同一份檔案清單、同一個 regen 與區塊),照計數只報 N 比 O 多的。鍵:程式行號引用、釘版本不合法用(規則, 片段)——括號裡出現一個新的 `路徑:行號` 會產生新片段、照報;其他整行層級規則(沒寫來源的現況描述、SEE 只放連結)用規則名——補一段括號救得了、弄不壞「有沒有來源」;SEE 行補了括號會讓 N 違規而 O 沒有,照報。同一行同一個片段 `_ns_check_line` 只出一條,括號裡重複舊行已有的同一個引用不會多報(天花板 4)。**新規則預設鍵是規則名(整行層級)**;要用片段鍵,在那條規則自己的計劃寫明。
   - `_ns_revisit_violations` 對 N 與 O 各算(兩邊都在圍欄外),鍵(規則, 改法);改法只有「條件寫錯」帶錯誤細節,補一個寫錯的條件會照報。
3. **第一層的提醒**(只在提交前算):
   - 否定現況句:先照今天對 N 整行跑 `_ns_negation_hits`(整行層級的排除——回頭條件行、RETIRE-IF 開頭、規則句、歷史句——照舊生效);N 的可見文字以 O 的可見文字開頭時,只留起點落在追加段的命中,有就出一條提醒、片段從那個命中切;N 的可見文字不以 O 的開頭(行內程式碼的反引號跨在交界)就照今天整行提醒。跨在交界的字眼抓不到(天花板 5)。判定放在 `_ns_negation_hints` 裡,`_ns_negation_collect` 與 `_ns_negation_hints` 各多一個有預設值的參數,轉傳〈做法〉2 那個取得函式(不是算好的表;那一行有命中才呼叫);片段照現行用 `_ns_negation_snippet(可見文字, 位置)` 切(座標是可見文字,不是原文);例外照現行在收集器的 try 裡吞掉。追加的字讓舊命中的修飾語判定改變(例如接上「的時候」)時照 N 的結果。
   - 筆記前綴提醒(`_ns_rule_hints`)不套用:它含筆記格子的寫法警告(現在只提醒、格子開擋後會擋),壓掉會讓開擋那天才第一次擋人;補更正的 RULE 行照樣收到。
4. **第二層:送審時標出補上的那段**。
   - `_note_audit_items` 有送審項目時呼叫配對(一次);五個呼叫端(清單 prepare、record、check、skip、doctor 事後掃描)都會算到,代價是有送審項目時多一次範圍 diff 與讀有候選的篇。
   - **只有同一個內容編號的每一處都配到同一句舊句,才標追加段**:item 多一個欄位 `appended`(終點版本原行從 len(O') 起切下的那段,保留 CR)。同一小標題下一字不差的幾行,只要有一處沒配對、或配到的舊句不同,那個編號的每一處都不標、整行送審(既有 PITFALL「同編號幾處共用一個判定」)。完成審的行不標。
   - **內容編號不變**(`_notelines_content_id` 照舊用整行):各呼叫端的範圍起點不同(prepare 跟推送前、doctor 用上線點),配對結果可能不同;編號若隨配對變,同一行換個入口就對不上判定、doctor 會一直誤報(設計審 r2 正確性席)。改成**判定檔記範圍**:record 對帶 `appended` 的 item 寫的那一列多一個可省略的欄位 `tail`(舊句去頭尾空白後的 sha256 前 16 碼);沒這欄就是判整行,舊判定檔照舊有效。`_note_audit_parse_verdict` 收這個欄位(要是字串)。

## 回退

還原配對與放寬那一個提交即可:兩層都回到「新增的行整行查/整行送審」;設定格式沒變,`relaxed` 帳留著無害;判定檔裡帶 `tail` 的列在退回後被當成整行判定(〈實務隱患〉回滾)。解析器的兩個修洞也會一起退回——退回後 `++ x` 與上下文行錯位的舊洞重現,所以實作分成兩個提交:先修解析器(兩個既有洞)、再加配對與兩層的放寬(第一輪問閘時提示累計折入太多、建議拆小);要退回放寬只還原後面那一個,解析器的修補留著。已經靠這條放行、推上去的舊行不會被追溯擋下,要追查就用還原後的版本跑 `lumos note-shape --diff <起點>..<終點>` 重看那段範圍。

## 天花板

1. 放過的是「舊句本來就犯的違規」:在沒來源的舊 DEP 尾巴補括號、括號裡寫新的程式現況,第一層不重報「沒寫來源」,要靠第二層判定者單獨判括號;第二層接進推送前掛鉤與 CI 之前(2026-10-03 寫這份計劃時沒接),這段只有手動跑才會被判。每次推送後可以再補一段,沒有跨推送的累計上限。回頭時機:第二層接線那一步(入口在 [[Projects/筆記內容審_計劃]] 的接線條件)要一併決定要不要加累計上限。
2. 只認句尾補括號:補更正時順手改了一個字、插在句中、或尾巴有括號外的字,整行照新寫查。
3. 舊句以各道檢查自己的範圍起點為準:起點版本裡的舊句本身有沒有被第二層判過,本案不管(跟所有已推上去的行同等);沒有起點版本(從空樹算)時全不配對。
4. 同一行同一個程式行號引用只算一條:括號裡重複舊行已有的一字不差的引用不會多報。
5. 否定字眼跨在舊句與追加段交界抓不到(只是提醒、不擋)。
6. 配對只靠 git 的改動段:刪的行數跟加的不等(例如同一段裡另外插了新行)、或 git 把舊行與新行分到不同段時配不到,照整行查(偏嚴)。
7. doctor 用上線點當起點:上線點之後分幾次推送各補一段括號,doctor 第一層看到的是累積的那段,超過 300 字就會唸(訊息會列出這個可能);第二層 doctor 不比範圍。
8. 被 git 加引號的檔名(含 TAB、引號、換行)照現行讀不到路徑,本案不改。
9. 提交前與推送前量的範圍不同:同一批工作分幾個提交各補一段,每個提交前各自量、推送前量累積;累積超過 300 字時提交前放行、推送前整行查——壓成一個提交或縮短括號。已推上去的括號要拿掉時,另開提交整段刪括號會讓舊句被當成新寫、整行照查;改寫括號內容才照配。
