# 舊行尾追加不算新寫_計劃

白話:清舊筆記時最常做的事,是在舊句後面補一個「(更正:…)」。現在兩道檢查都把那整行當成新寫的來查——第一層(筆記形狀擋)把舊句本來就有的問題算到補更正的人頭上,第二層(筆記內容審)讓判定者重判整句舊話。這份計劃讓兩層都只看**這次補在尾巴的那段括號**。只認「主線上的舊句一個字都沒動、只在尾巴補一段括號」,其他改法照今天整行查。

依據:
- 消費專案清漂移回傳(2026-10-02,第 3 項,去識別):在舊句後補更正括號,整行被當新寫——舊行原有的「還沒」觸發否定現況句提醒 24 條;一條上線前合法的舊 DEP 被當成新寫的 DEP 擋下,只好改寫成歷史 WHY。
- 本 repo 重現(2026-10-02,用測試小工具 `_ns_repo`/`_ns_note`/`_ns_stage` 建暫存專案):先提交 `DEP:付款走舊閘道 scripts/pay.py 還沒換掉`,再在句尾接「(更正:2026-10-02 已換成新閘道,見 `Systems/Pay`)」並暫存,`note-shape --staged` 回 1(沒寫來源的 DEP),並對原本就有的「還沒」再提醒一次。會寫成 [S1][S2] 的測試。
- 消費專案那兩批清理提交的實測(2026-10-03,`git diff -U0` 逐區塊數):346 個改動區塊裡 345 個是「刪幾行就加幾行」;按位置一對一、新行以舊行開頭的有 193 處,其中 192 處追加段是一段括號、長度中位 103 字、九成在 190 字內、最長 279 字;唯一不是括號的是在行尾補狀態標籤。上限與括號形狀照這組數字定(〈做法〉1)。
- 前案 [[Projects/舊行插字不算新寫_計劃]]:設計審三輪(97 條、major 27 條),末輪 4 條 major 都在「自己找舊行」的配對規則。本案換掉配對方式,其餘已審過的結論沿用(否定提醒只看新加的字、前綴提醒不套用、放寬帳用獨立種類、喚醒那一路不動)。
- 程式現況:第一層 `_note_shape_eval` 取 `_notelines_new` 的新行,對每行跑 `_ns_check_line`、`_ns_revisit_violations`,提交前另收否定與前綴提醒;第二層 `_note_audit_items` 用同一支取新行,`_note_audit_render_list` 把整行(`>>>` 那行)與前後文交給判定者。兩層取改動都走 `_ns_diff`,解析走 `_notelines_parse_added`。提交前模式用新增行號;推送與 doctor 模式用逐提交新增的文字認新行。

PRIOR-ART: 「只評這次改到的部分」是 lint 接 PR 的標準做法(reviewdog `-filter-mode=added`、Danger 只看 diff 行);本案在「行」之下再細到「行尾補的括號」,配對直接用 git diff 的改動區塊按位置對,不另寫找舊行的演算法;diff 的區塊讀法改成照 `@@` 計數走(同 `git apply`/unidiff 類解析器的做法)。
RETIRE-IF: 上線八週後任一成立就撤掉或重想:①從放寬帳(〈做法〉5)抽 20 行對回提交,有一半以上其實是借括號把新的程式現況塞進舊句——改回整行查;②八週內一次放寬事件都沒有(機制是死的);③筆記形狀擋改成以「欄位」或「句子」為單位判新舊,這條被取代。
REVISIT:2026-12-01 從 docs/.governance-log.jsonl 數閘 note-shape、種類 relaxed 與 relaxed-failed 近八週的筆數,對 RETIRE-IF ①②(`gov --stats` 不分這兩種);relaxed-failed 不是 0 先查壞在哪

## 做法

1. **配對(兩層共用一支)**:新寫 `_notelines_append_pairs(repo_root, staged, base_where, tip_where, vault_rel)` → `{NFC 路徑: {終點版本行號: 舊行原文}}`;任何失敗(git 失敗、讀不到、例外)一律回空表(這次全不配對、照今天整行查),另帶一個失敗原因字串給記帳用。這是唯一的失敗出口,呼叫端不分 None 與空表。
   - **舊句要在主線上(配對起點)**:先找主線參照(`_ns_mainline_refs`,只認已推上去的 upstream);找不到就不配對。
     - 推送與 doctor:起點版本若已在主線上(是主線參照的祖先),配對起點就是它;否則用「終點版本與主線的分岔點」(`git merge-base`)。推主線時起點本來就在主線上;CI 用的前一版也在主線上,兩邊算出同一個配對起點。
     - 提交前:HEAD 已在主線上就用 HEAD,否則用 HEAD 與主線的分岔點;取改動用 `_ns_diff("--cached", <配對起點的完整 sha>, "--", 圖譜目錄)`,起點釘成 sha(不在兩次呼叫之間各自解析 HEAD)。
     - 好處:沒進主線的舊句(例如先推到別的分支、用 `--no-verify` 或在第二層上線前推的)不算舊句,整行照查;同一批工作分幾個提交各補一點,提交前與推送前量的都是「相對主線累積補了多少」,兩邊結果一致。
   - **取改動區塊**:推送與 doctor 用 `_ns_diff(<配對起點>, tip_where, "--", 圖譜目錄)`;只在第一層真的有違規或提醒要扣、或第二層有送審項目時才跑(見〈做法〉2、4)。不跟 `_NotelinesNet` 共用——它只在 `keep_other` 時建、而且刻意用到才算(代碼審 r2 併發席),本案不動它。
   - **統一的區塊讀法**:新寫 `_notelines_parse_hunks(raw)`,照 `@@ -a[,b] +c[,d] @@` 的計數走(沒寫計數就是 1,計數 0 的那邊沒有行;標頭後面可以帶函式上下文);`diff --git` 重置狀態;在區塊裡照計數吃 `-`、`+`、空白開頭的上下文行,`\ No newline` 不吃計數;計數吃完才回到檔頭狀態,所以內容行 `++ x`(在 diff 裡是 `+++ x`)不會被當成檔頭。上下文行把一個區塊切成幾個「改動段」。`--- `/`+++ ` 路徑照現行(去掉 `a/`、`b/` 與尾端 TAB;被 git 加引號的路徑、`/dev/null`、改名、二進位或純改名沒有內容)——這幾種不配對。
     - **舊解析器一起改**:`_notelines_parse_added` 改成包這支(只交出被加的行與正確的新行號),所以提交前、推送逐提交、合併提交判不了的退路、`_NotelinesNet` 四處一起修掉「`++ x` 之後同檔新行全漏查」與「上下文行讓行號錯位」兩個既有洞(代碼審 r1 正確性、整合、架構三席各自實測)。回傳形狀不變。
     - **釘住 git 的切法**:`_ns_diff` 加 `--inter-hunk-context=0` 與 `--diff-algorithm=myers`,本機設定(`diff.interHunkContext`、`diff.algorithm`)不再改變區塊怎麼切,本機與 CI 切法一樣。讀法照計數走,就算有上下文行也不會錯位。
   - **配對規則**:每個改動段裡,被刪的行數等於被加的行數才配,第 i 條被刪的對第 i 條被加的;行數不等的整段不配。插在舊行前面的新行會讓行數不等,搶不走舊行(代碼審 r1 正確性席實驗:舊行順手改一下、正上方插一行「舊句+新斷言」)。
   - **每一對的條件**(常數:`_NS_APPEND_MIN_OLD`=8、`_NS_APPEND_MAX_TAIL`=300、`_NS_APPEND_MAX_LINE`=2000、`_NS_APPEND_TAIL_RE`):
     - 兩邊只去掉尾端空白(含 CR):O'=舊行.rstrip()、N'=新行.rstrip();N' 以 O' 開頭而且比 O' 長。開頭的縮排要一樣(縮排變了不算追加)。
     - O' 去頭尾空白後至少 8 個碼點(含 8)。
     - 追加段 T=N'[len(O'):] 整段符合 `\s*[(（].*[)）]`(一段括號,半形全形都收,中間可以有其他括號);T 不超過 300 個碼點(含 300),N' 不超過 2000 個碼點。上限固定,不隨舊行變長。
     - 配對起點版本那一行的文字(去尾端空白)等於這個被刪的行;不等就不配。
     - **同一個脈絡**:舊行在配對起點版本、新行在終點版本的區塊(`_notelines_regions`)相同、兩邊都在圍欄外(`_visible_lines`)、那篇的重建標記兩個版本相同。配對起點版本只讀有候選的那幾篇,用 `_nodehome_cat_blobs_capped`(上限常數 `_NS_APPEND_BASE_MAX_BYTES`=512 KB),回來的位元組自己用 `utf-8-sig` 解,行照位元組切(不換掉 CR);讀不到、超過上限、解不開就這篇不配對。拿去 git 讀用 diff 檔頭上的原樣路徑,回傳表的鍵用 NFC,兩層查表時用 `nfc(路徑)`。
   - 成本:配對對每個改動段是線性的(按位置對,不做兩兩比較)。
2. **第一層:只報多出來的違規**。配到的新行 N(舊行 O):
   - **用到才算**:`_note_shape_eval` 先照今天算;只有某篇筆記有違規或提醒時才呼叫配對(一次,整個範圍),沒有就不跑那次 diff。
   - `_ns_check_line` 對 N 與 O 各算一次(同一份檔案清單、同一個 regen 與區塊),照計數只報 N 比 O 多的。鍵:程式行號引用、釘版本不合法用(規則, 片段)——在舊行既有路徑後面接 `:12` 會產生新片段、照報;其他整行層級規則(沒寫來源的現況描述、SEE 只放連結)用規則名——接一段字救得了、弄不壞「有沒有來源」;SEE 行接了句子會讓 N 違規而 O 沒有,照報。同一行同一個片段 `_ns_check_line` 只出一條,接第二個一字不差的引用不會多報(天花板 4)。**新規則預設鍵是規則名(整行層級)**;要用片段鍵,在那條規則自己的計劃寫明。
   - `_ns_revisit_violations` 對 N 與 O 各算(兩邊都在圍欄外),鍵(規則, 改法);改法只有「條件寫錯」帶錯誤細節,接一個寫錯的條件會照報。
3. **第一層的提醒**(只在提交前算):
   - 否定現況句:先照今天對 N 整行跑 `_ns_negation_hits`(整行層級的排除——回頭條件行、RETIRE-IF 開頭、規則句、歷史句——照舊生效);N 的可見文字以 O 的可見文字開頭時,只留起點落在追加段的命中,有就出一條提醒、片段從那個命中切;N 的可見文字不以 O 的開頭(行內程式碼的反引號跨在交界)就照今天整行提醒。跨在交界的字眼抓不到(天花板 5)。判定放在 `_ns_negation_hints` 裡,`_ns_negation_collect` 與 `_ns_negation_hints` 各多一個有預設值的參數轉傳配對表;片段照現行用 `_ns_negation_snippet(可見文字, 位置)` 切(座標是可見文字,不是原文);例外照現行在收集器的 try 裡吞掉。追加的字讓舊命中的修飾語判定改變(例如接上「的時候」)時照 N 的結果。
   - 筆記前綴提醒(`_ns_rule_hints`)不套用:它含筆記格子的寫法警告(現在只提醒、格子開擋後會擋),壓掉會讓開擋那天才第一次擋人;補更正的 RULE 行照樣收到。
4. **第二層:送審時標出補上的那段**。
   - `_note_audit_items` 有送審項目時呼叫配對(一次);item 多一個欄位 `appended`(終點版本原行從 len(O') 起切下的那段,保留 CR;沒配對、或是完成審的行就沒有這欄)。五個呼叫端(清單 prepare、record、check、skip、doctor 事後掃描)都會算到——check 要重算同一組內容編號,不能略過;代價是有送審項目時多一次範圍 diff 與讀有候選的篇。
   - **內容編號分範圍**:`_notelines_content_id` 多一個有預設值的參數 `tail_of`;有 `appended` 的 item 用 `tail_of=O'.strip()` 算編號(雜湊多一段「尾:」加舊句)。好處:只判尾巴的判定只對這個範圍有效——同一小標題下一字不差、但一處是補括號一處是整行新寫的兩行,編號不同、各判各的;rebase 後配對結果變了,編號跟著變,舊的尾巴判定套不上去(代碼審 r1 正確性、邊界兩席;既有 PITFALL「同編號兩處共用一個判定」)。同一編號的幾處一定是同一個範圍,範本規則 7「同編號給較重的」照舊成立。判定檔格式不變——不另加「範圍」欄(代碼審 r1 整合席建議過),因為範圍已經在編號裡,加欄會變成兩個地方記同一件事。申訴重派(`prepare --only <編號>`)用同一個範圍、同一支配對重算,編號對得上;範圍或配對結果變了,舊編號在這次範圍找不到,照既有的「編號不在這次範圍」處理、要重判。
   - `_note_audit_render_list` 對有這欄的 item 在 `>>>` 那行之後多印兩行「舊句(主線已有,不在這次判的範圍):…」「只判這次補在句尾的:…」,兩行都照原位元組印(CRLF 筆記不換掉 CR,同既有 PITFALL)。
   - 派工詞範本 `scripts/templates/note-audit-judge.md` 在規則段與輸出段之間補一段「有這兩行的項目,只判句尾那段是不是程式碼推得出來;舊句只當上下文、不進標籤;這段優先於規則 2(逐子句判)與規則 5(跨行合起來判)」;新段不得含 `{{`、不得含大寫的 Output(既有測試用它切段)。不動規則段本身。`_NOTE_AUDIT_PROMPT_VERSION` 從 1 升到 2;既有測試 `t_note_audit_record_provenance_trust_direction` 寫死用「版本 1 換成 0」造舊版清單,改成用 `_NOTE_AUDIT_PROMPT_VERSION - 1`(代碼審 r1 整合席:不改會紅)。升版前發出的清單交回的輕判定會因版本對不上被丟掉、要重派(既有設計)。
   - **判定者驗收**:照 [[Systems/筆記內容審]] 的 RULE 重跑 68 句小實驗,另加一組補括號樣本(至少 9 句,從消費專案的真實更正去識別:舊句推得出+括號是脈絡、舊句是脈絡+括號推得出、括號是混合,各至少 3 句)。過關:68 句照 [[Projects/筆記內容審_計劃]] 原本的四項門檻;補括號那組判定者對括號的標籤至少 8/9 對,而且 0 句把舊句的標籤帶進來。這次用目前的編排者(Claude)跑;Codex 那家照筆記內容審計劃原本的規矩,接線進推送前之前再跑。結果記在 [[Projects/筆記內容審_計劃]]〈判定者能不能用〉補一列(接線守門讀那裡),本篇記一行指過去。
   - **作者怎麼處理**:括號被判推得出——刪掉或改寫那段括號(刪掉後整行回到舊句,不再是新行);判混合——刪掉括號裡推得出的子句。寫進 skill 子檔 `06-代碼審與推送.md` 筆記內容審那段與 [[Systems/筆記內容審]]。
5. **放寬也記一筆帳(只在推送時)**:
   - 推送模式(`cmd_note_shape --diff`)第一層有違規因配對被減掉時(推送模式不算提醒,〈做法〉3,所以帳裡只有違規),記一筆治理帳——閘 `note-shape`、種類 `relaxed`(不借 `hinted`:否定提醒的抽樣與格子度量按 `hinted` 數)。`extra` 帶 `check: "append-only"`、`base_sha`(配對起點)、`head_sha`(終點)、減掉的違規數、各規則名條數、配到的 `[路徑, 行號]`、總筆數 `total` 與有沒有被截 `truncated`。
   - 提交前不記:那時新提交還不存在、記不到可對回的 sha,而且同一次放寬推送時會再記一次(重複)。doctor 與跳過逃生口(`_ns_skip_slot_extra`,它也會跑完整評估、付配對成本)不記。
   - 配對失敗(回空表且帶失敗原因)而這次本來有違規時,推送模式記一筆種類 `relaxed-failed`、`extra` 帶 `check: "append-only"` 與例外類別名;RETIRE-IF ② 才分得出「沒機會用」與「壞了」。
