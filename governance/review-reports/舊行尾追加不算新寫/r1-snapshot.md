# 舊行尾追加不算新寫_計劃

白話:清舊筆記時最常做的事,是在舊句後面補一個「(更正:…)」。現在兩道檢查都把那整行當成新寫的來查——第一層(筆記形狀擋)把舊句本來就有的問題算到補更正的人頭上,第二層(筆記內容審)讓判定者重判整句舊話。這份計劃讓兩層都只看**這次接在尾巴的那一段**。只認「舊句一個字都沒動、只在尾巴接上一段」,其他改法照今天整行查。

依據:
- 消費專案清漂移回傳(2026-10-02,第 3 項,去識別):在舊句後補更正括號,整行被當新寫——舊行原有的「還沒」觸發否定現況句提醒 24 條;一條上線前合法的舊 DEP 被當成新寫的 DEP 擋下,只好改寫成歷史 WHY。
- 本 repo 重現(2026-10-02,用測試小工具 `_ns_repo`/`_ns_note`/`_ns_stage` 建暫存專案):先提交 `DEP:付款走舊閘道 scripts/pay.py 還沒換掉`,再在句尾接「(更正:2026-10-02 已換成新閘道,見 `Systems/Pay`)」並暫存,`note-shape --staged` 回 1(沒寫來源的 DEP),並對原本就有的「還沒」再提醒一次。會寫成 [S1][S2] 的測試。
- 前案 [[Projects/舊行插字不算新寫_計劃]]:設計審三輪(97 條、major 27 條),末輪 4 條 major 都在「自己找舊行」的配對規則。本案換掉配對方式,其餘已審過的結論沿用(否定提醒只看新加的字、前綴提醒不套用、放寬帳用獨立種類、喚醒那一路不動)。
- 程式現況:第一層 `_note_shape_eval` 取 `_notelines_new` 的新行,對每行跑 `_ns_check_line`、`_ns_revisit_violations`,提交前另收否定與前綴提醒;第二層 `_note_audit_items` 用同一支取新行,`_note_audit_render_list` 把整行(`>>>` 那行)與前後文交給判定者。兩層取改動都走 `_ns_diff`(`git diff -U0 -M`,已帶關外部差異的旗標)。

PRIOR-ART: 「只評這次改到的部分」是 lint 接 PR 的標準做法(reviewdog `-filter-mode=added`、Danger 只看 diff 行);本案在「行」之下再細到「行尾追加」,配對直接用 git diff 的改動區塊,不另寫找舊行的演算法。
RETIRE-IF: 上線八週後任一成立就撤掉或重想:①從放寬帳(〈做法〉5)抽 20 行對回提交,有一半以上其實是借追加把新的程式現況塞進舊句——改回整行查;②八週內一次放寬事件都沒有(機制是死的);③筆記形狀擋改成以「欄位」或「句子」為單位判新舊,這條被取代。

## 做法

1. **配對(兩層共用一支)**:新寫 `_notelines_append_pairs(repo_root, staged, base_where, tip_where, vault_rel)` → `{NFC 路徑: {新行號: 舊行原文}}`。做法:
   - 取改動區塊:提交前 `_ns_diff(--cached)`,推送前與 doctor 事後掃描 `_ns_diff(base_where, tip_where)`(範圍淨差異,一次)。新寫一支解析器 `_notelines_parse_hunks`:同一份 `git diff -U0` 輸出,但要記「已經進到區塊」——`@@` 之後以 `+`/`-` 開頭的一律是內容(不能照 `_notelines_parse_added` 用 `startswith("+++ ")` 判檔頭,內容行 `++ x` 會變成 `+++ x` 被誤判),`\ No newline` 略過;每個區塊給(舊起始行號、被刪的行、新起始行號、被加的行),區塊標頭沒有逗號(`-2 +2`)與計數 0(`+2,0`)都要收。`--- ` 與 `+++ ` 去掉 `a/`、`b/` 與尾端 TAB 後路徑不同(改名)、任一邊是 `/dev/null`(新增或刪除檔):這篇不配對。
   - **只在同一個區塊裡配**:被加的行照順序,各找同區塊裡第一條還沒配過、滿足下列條件的被刪行。
   - 條件:兩邊先 `str.strip()`;新行 `startswith` 舊行、比舊行長;舊行至少 8 個字;追加的那段(新行去掉舊行之後剩下的)不超過 `max(40, 舊行字數×2)` 也不超過 500 字(常數 `_NS_APPEND_MIN_OLD`、`_NS_APPEND_MAX_ADD`);新行不超過 2000 字。
   - **同一個脈絡**:舊行在起點版本、新行在終點版本的區塊(`_notelines_regions`)相同、兩邊都在圍欄外(`_visible_lines`)、那篇的重建標記兩個版本相同。起點版本只讀有配對候選的那幾篇,用 `_nodehome_cat_blobs_capped`(上限常數 `_NS_APPEND_BASE_MAX_BYTES`=512 KB),回來的位元組自己用 `utf-8-sig` 解;讀不到、超過上限、解不開就這篇不配對,整批回 None(git 失敗、路徑含換行)就這次全不配對。拿去 git 讀用 diff 檔頭上的原樣路徑,回傳表的鍵用 NFC,`_note_shape_eval` 與 `_note_audit_items` 查表時用 `nfc(路徑)`。推送前那次範圍淨差異跟既有的 `_NotelinesNet` 共用同一次 diff(不多跑第二次)。
   - 整支包在 try 裡,任何例外都當「沒有配對」(照今天整行查),不讓閘失敗。
2. **第一層:只報多出來的違規**。配到的新行 N(舊行 O):
   - `_ns_check_line` 對 N 與 O 各算一次(同一份檔案清單、同一個 regen 與區塊),照計數只報 N 比 O 多的。鍵:程式行號引用、釘版本不合法用(規則, 片段)——在舊行既有路徑後面接 `:12` 會產生新片段、照報;其他整行層級規則(沒寫來源的現況描述、SEE 只放連結)用規則名——接一段字救得了、弄不壞「有沒有來源」;SEE 行接了句子會讓 N 違規而 O 沒有,照報。同一行同一個片段 `_ns_check_line` 只出一條,接第二個一字不差的引用不會多報(天花板 4)。
   - `_ns_revisit_violations` 對 N 與 O 各算(兩邊都在圍欄外),鍵(規則, 改法);改法只有「條件寫錯」帶錯誤細節,接一個寫錯的條件會照報。
3. **第一層的提醒**(只在提交前算):
   - 否定現況句:先照今天對 N 整行跑 `_ns_negation_hits`(整行層級的排除——回頭條件行、RETIRE-IF 開頭、規則句、歷史句——照舊生效);N 的可見文字以 O 的可見文字開頭時,只留起點落在追加段的命中,有就出一條提醒、片段從那個命中切;N 的可見文字不以 O 的開頭(行內程式碼的反引號跨在交界)就照今天整行提醒。跨在交界的字眼抓不到(天花板 5)。判定放在 `_ns_negation_hints` 裡,`_ns_negation_collect` 與 `_ns_negation_hints` 各多一個有預設值的參數轉傳配對表;片段照現行用 `_ns_negation_snippet(可見文字, 位置)` 切(座標是可見文字,不是原文);例外照現行在收集器的 try 裡吞掉。追加的字讓舊命中的修飾語判定改變(例如接上「的時候」)時照 N 的結果。
   - 筆記前綴提醒(`_ns_rule_hints`)不套用:它含筆記格子的寫法警告(現在只提醒、格子開擋後會擋),壓掉會讓開擋那天才第一次擋人;補更正的 RULE 行照樣收到。
4. **第二層:送審時標出追加的那段**。`_note_audit_items` 的 item 多一個欄位 `appended`(追加的那段文字;沒配對、或是完成審的行就沒有這欄);`_note_audit_render_list` 對有這欄的 item 在 `>>>` 那行之後多印兩行「舊句(已在主線,不判):…」「只判這次接在句尾的:…」;派工詞範本 `scripts/templates/note-audit-judge.md` 補一段「有這兩行的,只判句尾那段是不是程式碼推得出來;舊句不判」(不動範本的規則段,清單測試要它原樣出現),`_NOTE_AUDIT_PROMPT_VERSION` 從 1 升到 2;照 [[Systems/筆記內容審]] 的 RULE(範本改任何一個字要升版號、重跑 68 句小實驗、結果記進計劃)重跑並把結果記進本篇。升版後,升版前發出的清單交回的輕判定會因版本對不上被丟掉、要重派(既有設計)。內容編號(`_notelines_content_id`)照舊用整行(行文字變了,本來就是新編號),判定檔格式不變。
5. **放寬也記一筆帳**:第一層有違規或提醒因配對被減掉時,`cmd_note_shape` 記一筆治理帳——閘 `note-shape`、種類 `relaxed`(不借 `hinted`:否定提醒的抽樣與格子度量按 `hinted` 數)、`extra` 帶 `check: "append-only"`、`mode`(commit 或 push)、`base_sha`、減掉的違規數與提醒數、各規則名條數、配到的 `[路徑, 新行號]` 照位元組裁到整行 4 KB 內——量法借舊句檢查帳的 `_drift_m1_fit`(用 `_gate_event_build` 組完整事件、量 JSON 一行的位元組、從尾端丟;拆成共用的一支),組事件時先明確給 `head_sha`,量的跟寫的才是同一行。由 `_note_shape_eval` 多收一個容器參數(同 `hints` 的傳法、有預設值),只有 `cmd_note_shape` 傳;doctor 與跳過逃生口那兩個呼叫端不傳、不記。計數在配對與判定都成功之後才寫進容器。這是「沒違規的放行不寫帳」的第三個例外(前兩個是否定與前綴提醒的 `hinted`);寫入走既有寫入器,把這個新寫入者登記進 [[Issues/治理帳多個寫入者都沒上鎖]]。
6. **三種「舊行」各問各的**:本案的「同一個改動區塊裡被刪、被接字的那一行」(問:只多了尾巴嗎);`_note_shape_eval` 後半新程式檔喚醒那一路的上線點版本加 `old_by`(問:這行沒改、是程式那邊變了嗎);筆記格子的同前綴同核心一句文字鍵(問:欄位有沒有補)。**不動的**:`_note_shape_eval` 後半「新程式檔喚醒舊引用」那一路(它問的是「這行沒改、程式那邊變了」,舊版是上線點版本加 `old_by`,照舊用自己的整行集合);被放寬的行若同時碰到新程式檔喚醒,照喚醒那一路報(偏嚴,[S11])。筆記格子的舊行判定(同前綴、同核心一句的文字鍵,問「欄位有沒有補」,見 REVISIT)。`_notelines_new` 交出的 rows。存量漂移檢查。
7. **doctor 事後掃描**:同一支 `_note_shape_eval`,起點是上線點、範圍淨差異配對。上線點之後才寫的行不會在上線點版本裡,照整行查;如果它還唸,表示它寫下的那一刻就違規卻進了主線(warn 模式、繞過,或當時引用的檔後來才變成程式檔)——doctor 那段的訊息改成列出這幾種可能,不再只說「多半是 --no-verify 繞過」。
8. **同步要改的字句**:[[Systems/筆記內容閘]](兩層的放寬、三種舊行各問各的、放寬帳、doctor 訊息);[[Projects/筆記形狀擋_計劃]](〈做法〉與 [S7]、資源併發段的「放行不寫」補例外;RETIRE-IF ①②③ 從本案上線日起分母少了被放寬的行);[[Projects/否定現況句配回頭條件_計劃]](抽樣只取 `check` 是 `negation` 的 `hinted`;S8、S9「判定跟正式工具相同」補這個例外;重產時跳過放寬帳記的行);[[Systems/筆記內容閘]] 摘要裡「判定跟量測程式逐行一致」那句補這個例外;[[Projects/筆記內容審_計劃]] 與 [[Systems/筆記內容審]](送審標出追加段、派工詞第 2 版與 68 句重跑結果);`cmd_note_shape` 與 `_note_shape_doctor_lines` 的 docstring、`t_note_shape_block_message_and_fail_open` 的 docstring;skill 子檔 `03-寫回圖譜.md` 補一句「補更正就接在原句尾巴,別另寫一行」。

## 實務隱患

- **繞過**:另寫一行「舊句+新內容」而舊行還在——不在同一個區塊被刪、不配。刪掉舊行、在遠處寫「舊句+新內容」——不同區塊、不配。在舊行尾巴接一段新的程式現況——行號引用照片段比會擋;沒寫來源這條舊行本來就犯、第一層不重報,追加段由第二層判定者單獨判;追加長度有上限(`max(40, 舊行×2)`、500 字)。
- **效能**:多一次改動區塊解析(提交前本來就跑那支 diff;推送前與 doctor 多一次範圍淨差異);起點版本只讀有候選的篇、有大小上限;配對只在同一區塊裡比,`startswith` 是線性。
- **併發**:只讀 git 物件;放寬時多寫一筆治理帳,走既有寫入器,登記進既有的鎖 Issue。
- **回滾**:還原這一個提交即回到整行查;已寫的 `relaxed` 帳留著無害;第二層派工詞版本退回上一版。
- **相容**:第一層擋得只會變少;第二層的判定檔格式不變,只是送審內容多兩行說明;筆記格子開擋後補更正的舊行仍會被格子要求補齊(見 REVISIT,S1、S2 的測試寫明「格子未開擋」前提)。
- 已排除:金流:這道檢查只讀筆記與 git 物件,不碰任何付款流程
- 已排除:對外送出:不呼叫網路、不寄送、不寫到 repo 之外
- 已排除:不可逆:只決定擋不擋、送審印什麼,還原一個提交就回到原本的判法
- **守衛面**:兩道都是擋提交與推送的閘,改的是「哪些內容算新的」——放得太寬就是一條繞過的路,所以不排除、照走設計審。

## 天花板

1. 放過的是「舊句本來就犯的違規」:在沒來源的舊 DEP 尾巴接一段新的程式現況,第一層不重報「沒寫來源」,要靠第二層判定者單獨判追加段。
2. 只認句尾追加:補更正時順手改了一個字、或插在句中,整行照新寫查。
3. 只看起點版本:提交時以 HEAD、推送時以推送起點、doctor 以上線點為起點;同一批工作先接 A、下一個提交改成 B,對 HEAD 不是句尾追加,照整行查——要改自己剛接的字就 amend 或推前壓成一個提交。改名的篇不配。
4. 同一行同一個程式行號引用只算一條:接第二個一字不差的引用不會多報。
5. 否定字眼跨在舊句與追加段交界抓不到(只是提醒、不擋)。
6. 配對只靠 git 的改動區塊:git 把舊行與新行分到不同區塊(例如中間夾著大段改動)時配不到,照整行查(偏嚴)。
