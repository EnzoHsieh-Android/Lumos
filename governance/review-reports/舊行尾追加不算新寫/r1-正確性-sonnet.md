severity: major

# 外部審稿報告:舊行尾追加不算新寫(r1,正確性/邏輯鏡頭)

白話:這份 spec 想讓「在舊句尾巴補一段」不再被當成整行新寫。核心配對規則是「同一個 git 改動區塊裡,新行以被刪的舊行開頭」。我實跑 `git diff -U0 -M` 證實,這條規則會把「剛好排在前面的新行」也當成追加,所以它的繞過防線有洞。追加上限也只管單次,管不到累積。第二層的判定紀錄沒有記「判了哪一段」。spec 自己點名的 `++ x` 解析錯誤,在舊解析器裡原封不動,而它是整道閘的旁路。

審材外查證的程式碼在 `rw` 臨時副本。實驗在 `scratchpad/exp/r`,是我自己 `git init` 的臨時倉庫。

## 實驗摘要

- 實驗 E1:區塊 `-A_短 -A_長` 配 `+A_長+X +A_短+Y` 時,git 照檔案順序輸出。按 spec 的第一個未配對規則,`A_長+X` 會配到 `A_短`。
- 實驗 E2:舊行 O 結尾加來源標記、正上方插入一行 `O+新斷言`,git 輸出為 `-O +P(=O+新斷言) +N(=O+[來源:部署])`。P 排在前面,先拿走 O。
- 實驗 E3:檔尾沒有換行的檔,在最後一行 `end` 後面新增一行,git 輸出 `-end(No newline) +end +新行`。
- 實驗 E4:`file: scripts/lumos:27178` 的 `_notelines_parse_added` 遇到內容行 `++ x`(diff 裡是 `+++ x`)會把 path 設成 None。同一檔後面所有新增行丟光。實測 `{'n.md': [(6, 'end')]}`,後面的違規行 `DEP: 新的違規 scripts/wh.py:12` 消失。
- 實驗 E5:`_ns_check_line` 對「舊行 `scripts/pay.py:12`,尾巴再接 `scripts/pay.py:12`」只出一條。這確認天花板 4 屬實。
- 實驗 E6:13000 條被刪對 13000 條被加,第一個未配對掃描共 1.7×10⁸ 次比較,實測 17 秒。

**C1**
severity: major
blocking: 是 — 「舊行還在就不配」的繞過防線在同一區塊動到舊行時失效;沒有 `++ ` 之類的雜訊也能繞,沒來源的新斷言等於免檢
引句:「被加的行照順序,各找同區塊裡第一條還沒配過、滿足下列條件的被刪行。」
- 事實:spec〈實務隱患・繞過〉寫「另寫一行『舊句+新內容』而舊行還在——不在同一個區塊被刪、不配」,這句不成立。
- 做法:只要舊行 O 在同一區塊被順手改過(結尾補一個來源標記),再在它正上方插一行 `P = O + 新斷言` 即可。
- 實驗 E2:輸入 `-DEP: 倉庫走舊系統 scripts/wh.py`、`+…wh.py 新斷言:使用 Redis 逾時 30 秒`、`+…wh.py [來源:部署]`。
- 預期:`P` 先拿走 O,按字面實作 `P` 的「現況描述沒寫來源」被減掉,`N` 本身帶來源也乾淨,整個提交放行。
- 後果:這是一條全新的無來源現況句,卻連同 O 的債一起過關。S4 的「舊行還在就整行查」只在 O 沒被動時成立。
- E3 的檔尾無換行是不用刻意構造的同型情境:`-end +end +end+新斷言` 也會讓新行貼到 `end`。
- 建議:配對要求一對一,且舊行配走後,同區塊內其他以舊行為前綴的新行必須整行查。更保險的做法是新行的「剩餘部分」與舊行之間要有位置對應,例如被加行數等於被刪行數,或只配「位置相同」的那一對。

**C2**
severity: minor
blocking: 否 — 錯配方向偏嚴,不會漏檢,但會誤擋合法補字,並把舊斷言當成「追加段」交給判定者
引句:「條件:兩邊先 `str.strip()`;新行 `startswith` 舊行、比舊行長;舊行至少 8 個字;」
- 實驗 E1:舊行 `DEP: 付款走舊閘道 scripts/pay.py` 是另一條舊行 `…pay.py 還沒換掉` 的前綴。
- 輸入:兩條各補更正,並調換順序,得到 `+長+(更正A) +短+(更正B)`。
- 預期(字面實作):第一個新行掃到第一條未配的被刪行,也就是短舊行,於是配成功。
- 後果:追加段變成「還沒換掉(更正A)」,舊句的「還沒」被當成新寫而誤提醒。第二個新行找不到對象,整行查,合法補字被擋。
- 刪掉短行、只對長行補字也有同型錯配。
- 建議:對每個新行取「最長的前綴舊行」,再做一對一。同時要求舊行唯一,出現多個候選就不配(偏嚴)。

**C3**
severity: major
blocking: 是 — spec 宣稱「追加長度有上限」可擋住夾帶,實際上限隨舊行變長、跨推送不累計,第二層又還沒接進推送前
引句:「追加長度有上限(`max(40, 舊行×2)`、500 字)。」
- 上限量的是「這次相對起點」。每次推送後新舊行成為下一次的「舊行」,上限就跟著放大。
- 推導:8 字樁 → 40 → 144(約 2×48 上限)→ 約 430 → 500+。四次推送後尾巴累計 700 字以上。
- 它還獎勵大債:舊行 250 字以上,單次就能追加 500 字。典型一句斷言約 30 到 80 字,這個上限遠高於一句。
- 「現況描述沒寫來源」改用規則名當鍵,所以整段新斷言的無來源違規全被舊債吃掉。
- 問題所問的繞過路(同區塊刪一條舊行、加「舊行+一大段新現況」)走得通,上限內放行。起點可以是任何一條現成的無來源 ≥8 字舊行。
- 兜底靠第二層,但依 `docs/lumos-toolchain-knowledge/Systems/筆記內容審.md` 的說明,第二層「目前還沒接進推送前掛鉤與 CI」,指令只能手動跑。第二層只判每次的尾巴片段,切成多個 ≤上限的片段分批推,每片都單獨被判。
- 建議:上限只依舊行的「本來就有的新增量」計(例如固定 80 字),不隨舊行放大。另要限制同一行在一個範圍內被追加的累計量,或把累計量記進治理帳。

**C4**
severity: major
blocking: 是 — 判定檔格式不變,導致「只判尾巴」的輕判定會涵蓋同一內容編號的未配對複本,正好踩中節點已記載的 PITFALL
引句:「內容編號(`_notelines_content_id`)照舊用整行(行文字變了,本來就是新編號),判定檔格式不變。」
- 內容編號只含路徑、區塊、小標題、整行文字,沒有「判了哪一段」的欄位。
- `docs/lumos-toolchain-knowledge/Systems/筆記內容審.md` 的 PITFALL(2026-09-28 代碼審 r1)記載:同一小標題下一字不差的兩行共用一個編號,輕判定涵蓋兩處。
- 這份 spec 讓同一個編號出現兩種處境:一處有 `appended`(只判尾巴),另一處是未配對的複本(要判整行)。
- 預期:判定者對尾巴判 CONTEXT,同編號的複本被輕判定一起涵蓋,舊句部分(可能是推得出的 CODE)再也沒人判。
- 派工詞範本規則 7「同編號給較重標籤」與新段「有這兩行的只判句尾」互相矛盾。模板又規定「不動規則段」。
- 同型的過期問題:rebase 後原本配對的行變成全新行,舊的尾巴判定仍按編號蓋住它。
- 建議:判定 id 要納入範圍(例如 `id` 加上 `appended` 的雜湊,或讓有 `appended` 的項目換一個編號)。清單解析器要能分出「尾巴判定」與「整行判定」。

**C5**
severity: major
blocking: 是 — 這個旁路讓第一層對同一檔後續新增行全部不檢查,spec 看到了卻只在新解析器避開,舊解析器原封不動
引句:「不能照 `_notelines_parse_added` 用 `startswith("+++ ")` 判檔頭,內容行 `++ x` 會變成 `+++ x` 被誤判」
- file: `scripts/lumos:27178`。實驗 E4 證實:一行以 `++ ` 開頭的新增內容,會讓同一檔後面所有新增行被丟掉。
- 候選集的所有來源都用它:`scripts/lumos:27307`、`27332`、`27358`、`27414`,提交前與推送範圍都中。
- 預期:輸入 `+++ x` 後接 `+DEP: 新的違規 scripts/wh.py:12`,第一層不看第二行。
- 這是已有的洞,但 spec 已發現同一個缺陷卻只在新增的解析器裡修,是典型的「同族沒掃完」。
- 後果:兩個解析器對同一份 diff 看法不同。新解析器配得到的行,舊解析器根本沒交給閘檢查。S16 只會測新解析器,抓不到這個。
- 建議:把舊解析器改成共用新解析器(同一支「進了區塊就當內容」的狀態機),`_NotelinesNet` 和 `_notelines_range_added` 一併改。S16 要在舊解析器路徑加一條紅測試。

**C6**
severity: minor
blocking: 否 — 解析與錨定細節缺漏,實作時容易踩;多半偏嚴或只是誤配區域
引句:「每個區塊給(舊起始行號、被刪的行、新起始行號、被加的行),區塊標頭沒有逗號(`-2 +2`)與計數 0(`+2,0`)都要收。」

## 圖譜鏡頭(LUMOS-SPEC:`Projects/舊行尾追加不算新寫_計劃.md`)

逐條判斷這份設計會不會破壞節點宣稱的行為或合約:

1. `Systems/筆記內容閘` WHY「沒違規的放行不寫治理帳」:有影響但 spec 自己承認並登記為第三個例外,〈做法〉8 也列了要同步改字。不破壞。
2. `Systems/筆記內容閘` PITFALL「路徑 NFC 只當比對鍵、git 用原樣」:spec 〈做法〉1 已明寫兩邊用法。照實作不破壞。
3. `Systems/筆記內容閘` PITFALL「共用抽取器回給既有使用者一定要維持兩欄」:那條針對 `_node_code_ref_tokens`,spec 沒改它。`_notelines_new` 回傳形狀 `(notes, errs, old_by)` 也沒動。不影響。
4. `Systems/筆記內容閘` PITFALL「scripts/lumos 要維持 3.9 能解析」:spec 沒碰語法層。但新寫的解析器與配對函式不能用 3.10 之後的語法。不影響,實作時要守。
5. `Systems/筆記內容閘` 白話「舊筆記不回頭清,只看這次新寫的行」:被 C1、C3 稀釋。「新寫」的定義被放寬,卻沒有對應的累計守衛。
6. `Systems/筆記內容審` PITFALL「同一小標題下一字不差的兩行共用一個內容編號,輕的判定涵蓋兩處」:被破壞(C4)。spec 沒有分範圍的編號,也沒修範本規則 7 的衝突。
7. `Systems/筆記內容審` RULE「派工詞範本改任何一個字要升版號並重跑 68 句」:spec 遵守,但實驗不覆蓋新段(C11)。
8. `Systems/筆記內容審` WHY「輕判定要來源對、上下文沒變才收」:`ctx_fp` 只含前後文,不含 `appended`,同一行不同尾巴共用同一個上下文指紋。與 C4 同一個缺口。
9. `Systems/筆記內容審`「第二層上線只看範圍截斷、不逐提交判」:spec 第二層配對用範圍淨差異,與此一致。不影響。
10. `Systems/筆記內容審`「目前還沒接進推送前掛鉤與 CI」:不破壞,但 spec 〈實務隱患・繞過〉把第二層當後盾,現況其實不擋(見 C3)。

## 資料狀態五問

1. 空/不存在:新增檔、刪除檔、`/dev/null`、起點版本讀不到都有交代為「不配對」。缺一條:計數 0 的區塊(`-a,0`)沒有被刪行,要明寫直接略過(spec 有提到計數 0 要收,但沒說無被刪行時略過)。
2. 單筆:最常見的情境(單一區塊一對一)可行,E2 仍是繞過點(C1)。
3. 大量:上限只量位元組、不量行數與區塊大小,見 C7。
4. 重複/順序:同文字多份、前綴舊行搶長新行、插入行搶舊行,都是第一個未配對規則的弱點(C1、C2、C4)。
5. 髒/過期:CRLF、BOM、`autocrlf`、NFC 與 NFD 路徑、改名,spec 處理了 NFC 與改名,沒要求對一次起點行文字(C6)。

## 實務隱患逐類答

- 金流:同意排除,只讀筆記與 git 物件。
- 對外送出:同意排除。
- 不可逆:同意排除,只有治理帳是追加性寫入,內容可忽略。
