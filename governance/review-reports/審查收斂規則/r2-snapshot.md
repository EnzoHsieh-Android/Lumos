# 審查收斂規則_計劃

> 白話:合約審計的第 3 問「構造一個違反保證、但綁的測試照過的壞法」沒有終點——審計員只要肯重寫設計,永遠構造得出來,只能靠人喊停。改成:照 2026-10-13 那次人裁的判準,把反例分成「局部退化」(一定要被測試殺掉)與「繞過設計」(記成殘留、交給代碼審),而且分類不由想收斂的那一方說了算;殘留用一個獨立標記寫在合約行上,派工鏡頭看得到、碰到它的改動一律走高風險代碼審。原本也想讓資安席修補輪只看變過的檔,審查後決定不做(見〈不做〉)。

## 緣起

- 2026-10-13 後端示範:合約審計連三輪都推翻三條合約,第 3 問每輪補完測試又構造得出新的壞法,最後由需求方人裁收尾(示範計劃決策 d12:修 bug、補實際會發生的三類,刻意繞過設計的三種寫法列為已知殘留)。同一次示範,代碼審第三輪資安席把整份 35 支檔重讀一遍,只因為第二輪修補動了 6 支。出處:使用者 2026-10-14 問「這次示範有什麼 lumos 可以改進」時列的第 5 條;[[Verification/2026-10-13_後端示範交付]] 改進候選第 7 條。
- d12 的人裁:「實際可能發生的退化都補測試;刻意繞過設計的改法屬於代碼審要擋的範圍」。本計劃把它寫成照做的規則,同時守住本 repo「提出的人不准自己認證」的規矩(`skills/lumos-project-notes/reference.md` 審計段:讓提出者自己評必手下留情)。

PRIOR-ART: 變異測試(mutation testing)的業界做法是只用局部改動當壞法,並承認「等價變異」(改了但行為不變)殺不掉、要人工排除;本 repo 的 `guard kill` 破壞配方是同一類工具,借它記錄並真跑局部退化。殘留標記照本 repo 行內標記「一個方括號一個欄位、一個正規式」的慣例(`[test:]`、`[audit:]`、`[kill:]`、`[rollback:]`)另立 `[residual:]`;解析「節點#決策」重用既有的決策指標解析與「節點在、決策在、沒被標無效」的判斷。
RETIRE-IF: 上線後 8 週內,有一次逃逸帳記錄的 `residual_ref` 指到某筆殘留決策、而那個缺陷其實是一個保留設計機制、只是用錯的局部退化——撤回 B 規則,第 3 問回到「構造得出就不合格」。
REVISIT:2026-12-15 數一次:圖譜裡帶 `[residual:]` 的合約行幾條、各指到哪幾筆殘留決策;逃逸帳裡帶 `residual_ref` 的幾筆;照 RETIRE-IF 判。

## 不做

- 不做「資安席修補輪只看變過的檔」。理由:處置閘判資安席涵蓋,看的是帳上掛的凍結 patch,不是席位實際讀了哪幾支;若派工叫資安席只讀清單、清單又以「帳上看過」推下一輪,就會出現一支檔從頭到尾沒有資安席真的讀過、閘卻判涵蓋的情形——這正是 [[Projects/代碼審資安席_計劃]] 第一輪用「同檔名內容改掉」實測出來、改成比內容才堵上的洞(r1 整合席)。現行「每輪整份重讀」是那道防線的代價,保留。上限輪資安席抓到問題、折掉之後,判定的仍是那一輪的凍結 patch,不會卡住,所以也沒有要解的收斂問題。

## 做法

1. **反例分兩類**(寫進 `lumos-project-notes` 的〈[audit:] 獨立合法性審計〉五問段;派工時照那一段的防應試化規則改述措辭,不逐字貼):
   - **局部退化**:保留設計點名的機制(鎖、約束、冪等鍵查詢、交易邊界……),只是用錯或漏用——漏呼叫、條件寫反、範圍或順序錯、錯誤處理吞掉、少了一條約束、新增的一條路徑沒經過那個機制。判準:**透過系統對外的入口(端點、公開函式、資料庫結構)就測得到的**,一律是局部退化,一定要被綁定測試殺掉(審計員附一條 `lumos guard kill-add` 的配方;配方要先提交才算數,`kill-add --try` 的試跑是弱證據;`lumos guard kill` 對它是 `killed` 才算處理完,`survived` 補測試,`killed_unattributed`、`timed_out_weak` 算沒殺掉,`drifted` 先改寫配方)。
   - **繞過設計**:要改架構或部署形態才做得到、對外入口測不出來的(例:把單一資料庫換成多節點並改用程式內互斥、改成另一種儲存的分桶查詢)。這一類不算第 3 問不過,記成殘留決策(四欄齊,內容逐型列出殘留,並寫明「第幾輪審計收斂」;理由:測試無法窮舉刻意繞過設計的改法,屬代碼審要擋的範圍)。
   - **等價或殺不掉**:審計員交的局部退化,行為其實等價、或配方只能寫成多檔多處而 `kill-add` 表達不了——審計員附理由,記進殘留決策的另一段「殺不掉的局部退化」,同樣交給代碼審。
   - **d12 那三型照新判準重分**:「庫存多時另開不加鎖的快路徑」與「拿掉資料庫約束」都是對外入口測得到的(併發壓測打所有下單入口、檢查資料庫結構),屬局部退化,要補測試;「改用程式內互斥並跑多個節點」屬繞過設計。示範 repo 的 d12 依此修訂是那個 repo 的事,本計劃只在手冊裡用這三型當例子。
2. **分類不由想收斂的一方決定**:分類由審計員(無對話脈絡的獨立代理)做;編排者可以把審計員判成「繞過設計」的改成「局部退化」(更嚴),不准反過來。要記成殘留(繞過設計或殺不掉)的每一條,另派一個沒看過審計報告結論的獨立代理,只給那條反例與合約,問「這能不能從對外入口測到」;兩邊都說測不到,才准記殘留。這一步寫進審計派工流程(`lumos-project-notes` 審計段),理由引 maker≠checker。
3. **殘留用獨立標記**:合約行加 `[residual:<節點>#<決策 id>]`(可以多個,一個殘留決策一個標記;節點寫圖譜相對路徑、不帶 `.md`;用最後一個 `#` 切;決策 id 是 `d` 加數字),由新指令 `lumos guard residual <節點> "<KEY 子字串>" <節點>#<決策 id>` 寫入,`--remove` 拿掉。`[audit:]` 照舊,`guard audit` 重審不碰 `[residual:]`,所以重審不會抹掉殘留。
   - **寫入當下就驗**:節點存在、決策存在、沒被標 `valid: false`(缺 `valid` 視為有效,跟既有讀法一致)、內容非空;不合就不寫、回 2。
   - **doctor**:跟 `[audit:]` 同一段檢查(既有的未審合約檢查),多驗 `[residual:]` 指到的決策仍然存在、沒被標無效;用既有的決策指標解析與判斷函式,不另寫一套。
4. **派工鏡頭看得到**:鏡頭印合約行時只印前 200 字,戳記常在後半(r1 整合席數過:36 條帶 `[audit:]` 的合約行有 22 條的戳記在第 200 字之後),所以「帶殘留」改放進接在後面的徽章(跟現在的綁定測試狀態徽章並排,例「⚠帶殘留 2 筆」),不靠行內文字。代碼審派工範本加一句:看到帶殘留徽章,去讀那幾筆殘留決策,那幾型壞法測試抓不到、要靠你看。
5. **碰到帶殘留的合約一律走高風險**:`pitfalls --diff` 算風險分級時,改動碰到的檔若在某篇帶 `[residual:]` 合約的節點 about_code 裡,分級升為 high(會派完整代碼審、派工鏡頭會附那條合約),理由寫進分級說明「改到帶殘留合約守的程式」。不然殘留交給代碼審,改動卻可能被判 standard 而不派代碼審,兩道都沒守。
6. **逃逸能歸因到殘留**:`lumos loop escape` 加選填 `--residual-ref <節點>#<決策 id>`,記進逃逸帳的 `residual_ref` 欄;`loop escape-stats` 印帶 `residual_ref` 的筆數。RETIRE-IF 靠它量。
7. **要一起改的說法**:`skills/lumos-project-notes/reference.md` 的五問段與 `[audit:]` 說明、`commands/06-代碼審與推送.md` 的 `guard` 指令表(加 `guard residual`)、`docs/methodology/圖譜即合約.md` 講第 3 問與 maker≠checker 的兩處、[[Systems/design-loop]] 講五問與防應試化的 KEY 行、`skills/lumos-design-loop/templates.md` 代碼審派工段(徽章那句)。防應試化的「定期無表抽考」照舊;抽考時不帶這套分類,比較兩邊結論時把「帶殘留通過」當成「不合格」看,落差才不會被系統性拉大(r1 整合席)。

## 實務隱患

- 守衛面:B 放寬了「第 3 問構造得出就不合格」。風險是把測得到的退化說成繞過設計。對策:判準改成「對外入口測不測得到」;編排者只能往嚴的方向改分類;記殘留要另一個獨立代理同意;殘留在徽章上看得到、碰到它的改動強制高風險代碼審;逃逸可以歸因到殘留,RETIRE-IF 量得到。
- 已排除:金流:不碰付款或點數。
- 已排除:對外送出:只改本機的審計留痕、分級、鏡頭與手冊。
- 已排除:不可逆:還原提交即回到原規則;`[residual:]` 標記在舊版工具下只是一段不認得的行內文字(不影響 `[audit:]` 的判讀)。

## 回退

照順序:
1. 還原提交。
2. 在圖譜搜 `[residual:`,逐條處理帶殘留的合約:舊規則下它們的第 3 問不算過,要嘛補測試後重審,要嘛把 `[audit:]` 拿掉、合約回到未審(推送前會被未審檢查擋,這是對的)。
3. 殘留決策留在節點上當歷史;逃逸帳的 `residual_ref` 欄舊版讀者不讀,無害。
