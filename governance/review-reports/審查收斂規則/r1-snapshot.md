# 審查收斂規則_計劃

> 白話:兩道審查規則讓人花冤枉力氣或沒有終點。一是代碼審的資安席:每一輪修補之後,處置閘要求「指紋變過的檔」都要有資安席看過新版,實務上等於每輪再派一席資安、整份改動重讀一遍,即使只改了幾支檔。二是合約審計的第 3 問「構造一個違反保證、但綁的測試照過的壞法」:審計員只要肯重寫設計,永遠構造得出來,只能靠人喊停。改成:派資安席時附一份「從它上次看過到現在,哪幾支檔變了」的清單,讓它集中看那幾支(處置閘的規則不動);合約審計第 3 問照 2026-10-13 那次人裁的判準,把反例分成「局部退化」(一定要被測試殺掉)與「繞過設計」(記成殘留、交給代碼審),戳記上分得出「乾淨過」與「帶殘留過」。

## 緣起

- 2026-10-13 後端示範:代碼審第二輪修補動了 6 支檔,第三輪(上限輪)照規矩再派一席資安、掛整份新的凍結 patch(35 支檔),資安席把整份重讀了一遍;其實處置閘只要求那 6 支指紋變過的檔有資安席看過新版。合約審計連三輪都推翻三條合約,第 3 問每輪補完測試又構造得出新的壞法,最後由需求方人裁收尾(示範計劃決策 d12:修 bug、補實際會發生的三類,刻意繞過設計的三種寫法列為已知殘留)。出處:使用者 2026-10-14 問「這次示範有什麼 lumos 可以改進」時列的第 5 條;[[Verification/2026-10-13_後端示範交付]] 改進候選第 7 條。
- 現行處置閘的資安席規則(看整個迴圈:判定輪每支檔的改動指紋,只要在資安席任一筆帳掛的凍結 patch 裡出現過就算涵蓋)本身沒有錯,上限輪也不會卡住:上限輪資安席抓到的問題折掉之後,判定的仍是那一輪的凍結 patch。要改的只是「每輪整份重讀」的成本。
- d12 的人裁其實已經是判準:「實際可能發生的退化都補測試;刻意繞過設計的改法屬於代碼審要擋的範圍」。本計劃把它寫成審計員與編排者照做的規則,下一次不用再人裁。

PRIOR-ART: 變異測試(mutation testing)的業界做法是只用「小的局部改動」當壞法,不把「重寫設計」算進存活變異;本 repo 的 `guard kill` 破壞配方就是同一種工具,借它記錄並真跑局部退化。資安席要看的檔清單重用處置閘既有的逐檔改動指紋比對(`_disposal_security_step` 裡算「沒看過、看過但又改過」的那一段),不另寫一套。
RETIRE-IF: 上線後 8 週內,有一次逃逸追得到「被列為繞過設計的殘留」其實是一個保留設計機制、只是用錯的局部退化,或資安席照清單集中看之後漏掉清單上的檔裡的洞——撤回對應的那一半。
REVISIT:2026-12-15 數一次:帶殘留的審計戳記幾條、殘留裡各幾型;代碼審迴圈裡用了資安席清單的輪數;兩者有沒有對應的逃逸。

## 做法

### A. 資安席只看變過的檔

1. **新指令** `lumos loop sec-delta <迴圈編號> --spec <這一輪的凍結 patch>`:印出這份凍結 patch 裡「資安席在這個迴圈裡還沒看過現在這一版」的檔——沒看過的、看過但改動指紋又變了的,各一段,外加支數。比對規則就是處置閘資安席那一步現在用的(同一支函式抽出來共用),所以清單上沒有的檔,處置閘一定判涵蓋;清單上有的檔,就是這一輪資安席非看不可的。不改處置閘、不加帳欄位。
2. **派工範本**:資安席的派工詞(`templates.md` §7.8)在修補輪多一段:被審材料照舊是這一輪的完整凍結 patch(帳上照舊掛它),另附 `sec-delta` 的清單與修補差異 `rN-repair.patch`,寫明「清單上的檔要逐支看完;其他檔是前幾輪資安席看過的同一版,可以只在需要上下文時翻」。§3.1 第 5 步末句「資安席對最後完整快照的覆蓋規則仍照原制」保留,旁邊補一句「派工時附 `sec-delta` 清單」。
3. 清單是空的(這一輪修補沒碰到資安席看過的檔、也沒有新檔),這一輪仍要派資安席嗎:照舊要——編制表沒變;但派工詞寫明「這一輪沒有新的檔要看,確認修補差異沒有引入新的攻擊面即可」。

### B. 合約審計第 3 問的收斂判準

4. **反例分兩類**(寫進 `lumos-project-notes` 的〈[audit:] 獨立合法性審計〉五問段;派工時照那一段的防應試化規則改述措辭,不逐字貼):
   - **局部退化**:保留設計點名的機制(鎖、約束、冪等鍵查詢、交易邊界……),只是用錯——漏呼叫、條件寫反、範圍或順序錯、錯誤處理吞掉。這一類一定要被綁定測試殺掉:審計員附一條破壞配方(`lumos guard kill-add` 的形狀),編排者記進那條合約的配方,`lumos guard kill` 對它的結果是 `killed` 才算處理完;`survived` 就補測試;`killed_unattributed`、`timed_out_weak` 算沒殺掉;`drifted`(配方原文對不上)先改寫配方再跑。
   - **繞過設計**:拿掉或繞開設計點名的那個機制、另開一條不經過它的路徑、改架構或部署形態(例:另開不加鎖的快路徑、拿掉資料庫約束改用程式內互斥並跑多個節點)。這一類不算第 3 問不過,記成殘留:用 `lumos decision-add` 在一個節點記一筆決策(四欄齊,內容逐型列出殘留),理由寫「測試無法窮舉刻意繞過設計的改法,屬代碼審要擋的範圍」。
   - 分類是語意判斷,不是形狀判斷(破壞配方的替換文字可以任意長,繞過設計也寫得成配方——前掃查過 `kill-add` 不限長度);判準就是「設計點名的機制還在不在」。審計員分類、編排者覆核;判不準的當局部退化(寧可多補一支測試)。
5. **收斂**:一輪審計裡,第 3 問的局部退化反例全部 `killed`、繞過設計的都已記成殘留決策,第 3 問就算過。審計最多三輪,跟設計審一樣;這條沒有機械帳(審計不走迴圈編號),寫成紀律:殘留決策的內容寫明「第幾輪審計收斂」,第三輪還有局部退化沒殺掉就攤給人裁。
6. **戳記分得出殘留**:`lumos guard audit` 加 `--residual <節點>#<決策 id>`,寫成 `[audit:模型/日期 殘留:<節點>#<決策 id>]`(決策 id 只在節點內唯一,所以要帶節點;殘留可以記在計劃節點,例如 d12 在計劃、合約在三個系統節點);沒有殘留照舊 `[audit:模型/日期]`。`lumos guard list` 本來就把戳記整串印出,不另改。doctor 檢查戳記裡的節點存在、那筆決策存在、沒有被標成 `valid: false`(缺 `valid` 視為有效,跟既有讀法一致)、內容不是空的,不合就報錯。
7. **代碼審看得到殘留**:派工鏡頭附合約行時本來就把整行(含戳記)印出,所以審查席看得到「這條帶殘留,見某節點某決策」;不另附決策內容(派工鏡頭的規則是不轉述圖譜裡的自由文字)。代碼審派工範本加一句:看到帶殘留的合約,去讀那筆殘留決策,那幾型壞法測試抓不到、要靠你看。

- [S2] `loop sec-delta` 清單是空的那一份凍結 patch,處置閘的資安席那一步應判涵蓋;清單非空時應判沒涵蓋——兩邊用同一支比對函式,不會不一致。[test: t_loop_sec_delta_matches_disposal]

## 實務隱患

- 守衛面:A 不改處置閘,只改派工時給資安席的提示;風險是資安席照清單只看那幾支、漏掉清單外檔案裡被修補間接影響的洞——清單外的檔是資安席看過的同一版,修補差異也一併附上,派工詞寫明需要上下文時要翻。B 放寬了「第 3 問構造得出就不合格」;風險是把局部退化硬說成繞過設計——判準是「設計點名的機制還在不在」,判不準一律當局部退化,殘留必須寫成有四欄的決策、戳記指得到它、代碼審席看得到戳記。
- 已排除:金流:不碰付款或點數。
- 已排除:對外送出:只改本機的審計留痕、新指令與手冊。
- 已排除:不可逆:還原提交即回到原規則;帶殘留的戳記在舊版工具下照樣判成已審(S4)。

## 回退

- 還原提交即回到原規則。已寫成 `[audit:… 殘留:…]` 的戳記,舊版工具照樣認得是審過;用舊版 `guard audit` 重審同一條會整串覆蓋、殘留標示跟著消失,所以回退後重審帶殘留的合約,要把殘留另外記回那條合約旁。殘留決策照樣留在節點上當歷史。
