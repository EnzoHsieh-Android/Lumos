severity: minor
blocking: 否

**層內註解把被跳脫的反引號當結尾,反引號層提早收掉,雙引號裡的後續指令漏問(be-api-compat、be-authz 兩題都不適用)。**

新程式用 `cmd.find("`", i)` 直接在原文找下一個反引號,沒避開前面有反斜線的那種。bash 是先找「沒被跳脫的」結尾反引號,把內容裡的 `\`` 還原成 `` ` `` 之後才解析。所以 bash 看到的是註解只到換行為止,下一行的指令照跑。掛鉤卻在跳脫的反引號處收層,後面的換行與指令落在雙引號字面裡,結構分類看不到。

這也跟類別說明裡「層內被跳脫的反引號已遮罩,那邊用 find 找結尾不會誤切」的說法不一致,註解這條路徑沒套同樣的遮罩。

重現(`git push` 在實驗腳本裡用字串拼接帶入):

```
指令:  echo "`echo a # \`⏎ git push --no-verify`"
bash (用 g1(){ echo EXEC >&2; } 代替 git 實跑 echo "`echo a # \`⏎ g1 x`"):  印出 EXEC 與 a,g1 有被執行
bypass_reasons(指令, "/tmp") → []   (漏問)
同形但沒有雙引號(echo `echo a # \`⏎ git push --no-verify`)→ ['no-verify'](有問)
註解裡沒有跳脫反引號的版本 → ['no-verify']
```

修補前註解一律吃到換行為止,這個案例會被抓到,所以這是這次修補新增的退步。要觸發,註解裡得有被跳脫的反引號,又要有換行後接繞閘指令。這比家筆記已寫明「不防」的「反引號裡用跳脫反引號再包一層」更偶然,所以我降為 minor。

建議:找結尾反引號時跳過前面有奇數個反斜線的反引號。或者承認這種寫法也屬「反斜線接反引號還原」那一步沒做的範圍,在家筆記補上這個例子。

引句:「t = cmd.find("`", i) if cur[3] else -1」

其他逐項走過,沒有問題:

1. **註解行為與 bash 比對**
   - 註解在反引號層裡、註解後還有換行與指令(`echo "`echo a # c⏎ git push --no-verify`"`):有問,和 bash 一致。
   - 註解在反引號層的內層引號裡:`#` 不在詞首,不算註解,有問。
   - 註解的 `#` 不在詞首(`echo a#c; git push --no-verify`):有問。
   - 反引號層沒有結尾(`echo "`echo a # c`):回空清單。裡面沒有繞閘,和既有案例一致。
   - 反引號層沒有結尾但後面有繞閘:走字面判,有問。
   - 引號外的註解:`cur[3]` 為假,走原路徑,行為沒變。
2. **效能**:最壞輸入實測都不是平方。2 萬字內的 2000 到 5000 個「`` `echo a # x` ``」、1800 層未收尾的註解、4000 行 `# x`,各自 0.1 秒內。換行搜尋被限在結尾反引號之前,沒有重複掃到尾。
3. **測試是否翻紅**
   - 「雙引號裡的反引號內有註解」:把新增的註解邏輯換回舊的「吃到換行」,結構分類失效,走字面判,理由含「切不開或太長」,被測試裡「不是字面判」那條檢查抓到而翻紅。
   - 「反引號裡 case 的單邊右括號」:拿掉 `_paren` 的 `if not cur[3]` 守衛,結果變成空清單(漏問),會翻紅。
   - 這兩個案例看的是實質行為,不是把實作重寫一次。
   - `ignores_mentions` 那條「沒有結尾反引號」的註解改寫,和實測行為(回空清單)一致。
4. **文件**
   - 家筆記新增的「反斜線接錢字號遮罩後仍是錢字號,攔得到」,實測四種跳脫寫法都回 `['no-verify']`;bash 對 `\$(…)` 也確實會執行。
   - 「反斜線接反斜線、反斜線接反引號」的更正符合 bash 規則。
   - 計劃括號更正與程式一致。
