## 2. 誤觸發面

**Finding 2 — severity: blocker / blocking: 是**
判準:雙訊號會誤傷什麼樣的健康輪已有真實案例可指,不是猜測——這决定門檻能不能直接採用還是要先加保護。

Finding 1 的 pc-v2 案就是具體的「健康輪被誤傷」樣本:一份 63 行的中型 spec、一輪審查折了 16 條 blocking(分散在 d1/d3/d4 三處核心裁定)、單輪乾淨收斂——這正是這套新制設計上想鼓勵的「健康輪」典型,卻恰好踩中兩個訊號的門檻。可以歸納出誤觸發的共同特徵:**spec 越短、blocking 分佈越廣(哪怕每條都不嚴重),越容易同時撞上兩條門檻**,因為 30% 是相對值、63 行的分母本來就小,而 16 條 blocking 只要分散到 3 個以上 d 編號就已經越過「≥2」的結構門檻。

**Finding 3 — severity: major / blocking: 是**
判準:反過來,雙訊號漏掉的是哪種真該重寫的案子——這決定門檻上線後會不會有一類爛 spec 被放過。

引句:「兩訊號都到才建議攤人重寫;仍是人裁選項非自動」

會被漏掉的形狀:**地基性錯誤集中在單一核心裁定、其餘裁定與落地件不受影響**的 spec。例如一份 spec 只有 2-3 條核心裁定,審查抓到 1 條 blocking 判定「整個方向錯了」(如 d1 的病根歸因整個錯,後面 d2-d4 其實都建立在錯誤前提上,但措辭修正只需要重寫那一整段落),在這 repo 的寫法下(見下方 Finding 4)一整條核心裁定就是一整行,改寫它在「既有行的比例」分子只貢獻 1 行、結構命中也只有 1 條——兩個訊號都不到,不會被建議重寫。這正是本案自己引的「編輯出版界」判準想抓的情形:「developmental editing 的重寫判準=結構/地基問題……不是表面缺陷數」(`governance/review-reports/loop-friction/web-research.md:25`)——編輯界原始判準是單看地基對不對,不看牽動幾條;本設計把它降格成「核心裁定條目數 ≥2」這個計數指標,恰好會漏掉「地基錯但只集中在一條」的案例,而這正是編輯界那條參照最想攔住的東西。

## 3. 「兩訊號都到才建議」的合取語意

**Finding 4 — severity: blocker / blocking: 是**
判準:合取(AND)是否真的比世界上任何一個單訊號形狀更保守、更不會誤觸——如果推理站不住,門檻的「寧漏勿誤觸」定位就是假的安全感,會讓人誤以為可以放心用低成本方式上線。

引句:「30% 是拍的保守值(高門檻=寧可漏觸發、由人裁補)」
引句:「Fagan 5% 是 rework-工時語意、非行數,本地換算無據,故取保守高值待校準——寧漏勿誤觸」

跟兩個被引的世界先例比,這個設計在「形」上已經比兩者都更保守:Fagan 的 5% 是單一訊號(改動材料比例);編輯界的「結構斷/結構完好」也是單一訊號(地基對不對)。本案不但把單一數值門檻從 5% 拉高到 30%(6 倍),還疊加一個必須同時滿足的第二條件(結構命中 ≥2)——這是雙重保守化。但 Finding 1/2 的 pc-v2 實測顯示:即便疊了兩層保守,一個真實的健康單輪案例依然同時越過兩條線。這說明「合取＝更保守」這個直覺不成立,原因是**兩個訊號高度相關、不是獨立事件**——同一輪審查折入的 diff 越大,自然而然會牽動越多條核心裁定(因為核心裁定本身就是 spec 裡最常被改動、篇幅也最大的段落),所以「波及幅度大」跟「核心裁定命中多」幾乎是同一件事的兩種量法,合取並不能像獨立機率相乘那樣把誤觸發率壓得更低,只是在同一個誤觸發事件上蓋兩個章而已。spec 沒有討論這個相關性,也沒有討論「AND 而非 OR」的選擇理由,「寧漏勿誤觸」這句話在自己引用的資料裡就有反例,站不住。

## 4. 可算性

**Finding 5 — severity: blocker / blocking: 是**
判準:「折入波及幅度」的分子分母定義夠不夠精確,讓兩個不同實作者對同一次折入算出同一個數——這是這條規則能不能被機械或穩定人工執行的前提。

引句:「本輪折入的 diff 動了 spec 既有行的比例(git diff 可算)」

拿 cascade 案(唯一被引用的「不觸發」案例)實測:這份計劃筆記在 git 裡的**第一筆提交就是 `7a026ef`**(`git log --diff-filter=A` 確認),而 `7a026ef` 本身已經是 r1 折入後的 v2(66 行,`git show 7a026ef --stat` 顯示「1 file changed, 66 insertions(+)」,即全新檔案)。也就是說折入前的 v1(59 行)**從未進過 git 歷史**,只存在於 `governance/review-reports/cascade-reminder/r1-snapshot.md` 這個審查快照裡。這造成兩種同樣「合理」但結果南轅北轍的讀法:①照字面用 `git diff`/`git log` 對這份筆記的版本歷史算——得到「這份檔案是全新建立,66 行 100% 是新增」,套用 >30% 門檻**會觸發**,與 spec 宣稱的「不觸發✓」直接矛盾;②改用 review-reports 目錄下的審查快照當分母基準——才能算出 spec 宣稱的 27%。spec 全文沒有交代「用哪個 git diff、對比哪個基準點」,而唯一能重現宣稱結果的方法(用審查快照當基準)完全沒寫進文字裡。這不是邊界情況,而是**唯一一個被引用來驗證「不觸發」的真實案例**,兩種讀法給出相反結論。

**Finding 6 — severity: major / blocking: 是**
判準:即使基準點統一了,「一行」在這個 repo 的實際寫法下能不能量出語意份量——量錯份量會讓門檻測到的不是「改了多少東西」而是「碰了幾個段落」。

file:line 證據:比對 cascade 案 v1→v2 diff(`governance/review-reports/cascade-reminder/r1-snapshot.md` vs `docs/lumos-toolchain-knowledge/Projects/連鎖佇列軟提醒_計劃.md`〈commit `7a026ef` 版〉)第 30 行(現版 d4):v1 原文是「header 損毀帳本跳過不報:損毀已有補網 E2 兜底……」,v2 整條反轉成「header 損毀帳本另列一行計數,不靜默(r1 撤銷 v1 的『E2 兜底』宣稱……)」——這是一條核心裁定的**決定完全推翻**;而同一份 diff 裡第 5 行(summary KEY)只是把「損毀歸 E2 不重喊」改成「★損毀另列一行計數……★」這種措辭級調整。這兩處在這 repo 的寫法下都是「一整段落塞在一行」(本案自己的 d1-d5、KEY 都是如此),於是在「動了幾行既有行」的分子裡**權重完全相同**,都只貢獻 1 行——一個字的潤飾與一條裁定的語意反轉,在這個算法下量不出差別。這代表 >30% 門檻實際測到的更接近「碰了幾個段落/裁定條目」,而不是 spec 文字宣稱的「動了多少內容」,也跟 Fagan 原始「rework 材料百分比」(以工時/字數量測改動份量)不是同一把尺,兩個不同實作者若一個逐字比對、一個逐行比對,在篇幅相近但改動深度不同的兩份 spec 上會排出不同的觸發順序。
