### 設計 4. 處置（第 62–70 行）——d1 一致性 + 資訊隔離

**f1 — blocker**

引句（frontmatter `d1`）：「連續兩輪 FAIL 才落 pending 喊人」

引句（設計 4）：「複審仍 FAIL=落 pending、記 skip 檔、本篇不再自動重試」

問題：這是本輪派工第一問「v3 設計七步彼此與 d1 裁定一致嗎」最直接命中的一條。`d1` 是本案唯一被 Enzo 拍板、`valid: true` 的裁定，字面白紙黑字要求「連續兩輪 FAIL 才落 pending」；但設計 4 實際描述的機制是**單次**失敗即終結：審計 FAIL→修→複審，只要複審這**一次**判 FAIL，立刻「落 pending、記 skip 檔、本篇不再自動重試」——沒有第二次嘗試。測試草案⑤「FAIL 鏈:修→複審 PASS→戳+commit;複審 FAIL→pending/selfaudit/+skip」與設計 1 的重派抑制邏輯「已有未結案 pending 檔的篇跳過,人清 pending 後自動恢復」（第 51 行）互相印證：三處（設計1、設計4、測試⑤）口徑一致，全部是「一次複審 FAIL 就永久跳過，直到人清 pending」，沒有任何地方出現計數器、第二次嘗試、或「兩輪」的字樣。

「連續兩輪」在 d1 裡有兩種讀法，但兩種讀法都跟現有機制對不上：
- **讀法 A（同一週期內：審計判 FAIL + 複審再判 FAIL，算兩輪）**——若這是 d1 原意，那設計 4 現在的機制剛好符合（審計本來就已經 FAIL 才會進修復鏈，複審再 FAIL＝兩次判定），但 `d1` 用「兩輪」這個詞非常容易被下一個讀這篇筆記的人（含未來 session 的 AI，本專案圖譜的主要讀者本來就是「下一個 session 的 AI」）理解成「兩次獨立嘗試」，而不是「同一輪裡的兩個判定點」——決策記錄的字面義跟其想表達的機制錯位，屬於 CLAUDE.md 開宗明義講的「行為事實和圖譜衝突」的同款風險，只是這次衝突發生在同一份文件的兩節之間，不用等實測就能查出來。
- **讀法 B（跨週期：這篇筆記連續兩個獨立派工週期都以 FAIL 收尾，才落 pending）**——若這是 d1 原意，設計 1 的重派抑制邏輯直接讓這個讀法在機制上**不可能發生**：一旦某篇進了複審 FAIL，立刻記進 `selfaudit-skip.jsonl` 且該篇的 pending 檔仍在，下一週的「選目標」步驟因為「已有未結案 pending 檔的篇跳過」而永遠不會把它重新選進來，也就永遠等不到「第二輪獨立嘗試」——想要兩輪，必須先允許至少重選一次，但重派抑制正是為了防止這件事而設計的（呼應 r1 s2f5/s1f6 的「同篇連續重派燒錢」批評）。也就是說，讀法 B 底下 d1 的裁定在目前設計裡是結構性做不到的。

不管取哪種讀法，結論都是：v3 設計節目前的字面機制是「單次複審 FAIL 即終結」，跟 `d1` 明文的「連續兩輪 FAIL」在字面上對不上號；若作者的本意其實是讀法 A，這份 spec 應該把 `d1` 的措辭改成不會被誤讀成「兩次獨立嘗試」的說法（例如「審計與複審兩次判定皆 FAIL 才落 pending」），而不是留著容易讓下一個讀者（含實作者）誤判成需要重試一次的字面表述。

問題：這是派工第三問「修復鏈三個 agent 的資訊隔離嚴不嚴格」。答案是：**工具面隔離有機制，資訊面隔離只有口頭承諾**，而且這正是同一份 spec 兩行前才自己立下的標準被自己違反的例子。

設計 2 對「不動筆記」這件事講得非常明確：「不給 Edit/Bash/Agent——『不動筆記』是工具層擋不是 prompt 口頭」（第 55 行）——白紙黑字把「靠 prompt 口頭約束」判定為不夠格，要求機制層（工具權限）落實。但設計 4 對複審 agent 的資訊隔離，只寫了結果性的一句話「不給報告與修法」，通篇七步設計裡沒有任何一步描述**怎麼保證**這件事：

1. 設計 2 唯一寫出來的 prompt 規格是審計 agent 的：「prompt=今天手動版的**方法論**+★新增★機械判定行」（第 58 行）。修 agent 與複審 agent 各自的 prompt 組裝方式，七步裡完全沒有獨立描述——沒有第二份、第三份 prompt 模板的說明，沒有「複審 agent 的 prompt builder 結構上不含 report/修法欄位」這種結構性保證，只能理解成「口頭上不要把這兩樣東西塞進去」，跟設計 2 明文否定的「prompt 口頭」是同一類風險。
2. 更關鍵的是：`--allowedTools "Read,Grep,Glob"` 這組工具面限制，管的是複審 agent**能用哪些工具**，不是**這些工具能碰到哪些路徑**。`claude -p` 的 `--allowedTools` 目前在本庫既有先例（`governance/autonomous-loop.sh:202`、`governance/ai-governance-research.sh`）裡都只限制工具類型，沒有額外的路徑白名單/沙盒。也就是說，複審 agent 就算沒有被「餵」審計報告或修法說明，它手上的 Read/Grep/Glob 是對整個 repo 開放的——而審計報告（依方法論慣例應落在 `governance/review-reports/self-audit/`，比照今天兩份手動報告的路徑）與 FAIL 分支寫進的 `governance/pending/selfaudit/<日期>-<篇>.md`，都是同一個 repo 裡、複審 agent 用同一組唯讀工具**主動就找得到**的檔案。「不給」描述的是「沒有主動塞進 prompt」，不是「複審 agent 沒有能力自己讀到」——而審計方法論本身（「只讀圖譜還原現況」）鼓勵的正是廣泛瀏覽 `governance/`、`docs/` 底下的相關檔案，複審 agent 若照同款方法論工作，撞見報告檔或 pending 檔的機率不低。spec 沒有交代這份報告/修法說明在複審階段是否已經被搬離工作目錄、改名、或用其他方式讓 Read/Grep 摸不到，「不給」目前只是沒有主動遞送，不是不可得。
3. 對照 d1 自己寫的安全論證：「自動放行的誠實線=修者不自驗+乾淨複審」（`why_chosen`）——整個「PASS→自動蓋章+commit」敢做的前提，就壓在「複審 agent 確實乾淨、看不到修者的自我辯護」這一件事上。這件事目前在 spec 裡沒有任何機制層落地，只有跟設計 2 自我矛盾的口頭承諾，風險等級不亞於設計 2 原本要防的「confused-deputy」——事實上這兩者是同一類風險（agent 拿到超出其職責範圍的資訊/能力）的兩個不同面向，spec 對其中一面（寫入能力）用了工具層擋，對另一面（資訊可得性）卻只用文字承諾，落差沒有被自己發現。
