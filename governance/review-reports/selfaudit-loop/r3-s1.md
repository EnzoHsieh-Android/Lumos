### f5 — blocker(複審PASS「copy 回主樹」對主樹當下若已被改動〔dirty〕沒有偵測或保護)

spec 段落:設計 4 FAIL 分支(66 行),對照「併發」(116 行)、PRIOR-ART(94-97 行)

引句:「複審 PASS=檔案 copy 回主樹+蓋章+commit」

問題:修復 agent 的 worktree 是「從 HEAD 建」(62、65 行)——釘在建立當下主樹所在的那個 commit。從 worktree 建立、修復 agent 編輯、複審 agent 在同一 worktree 判斷 PASS,到「copy 回主樹」之間有一段確實的時間窗(spec 自己的成本錨定「乾淨 agent 一篇 ~10 分鐘/1-2 美金」——修+複審是兩個乾淨 agent 接力,窗口只會更長)。這句話描述的動作是把 worktree 裡修好的檔案「copy」回主樹對應路徑,再蓋章、commit——全文找不到任何一步檢查「主樹上這篇筆記,從 worktree 建立那個 HEAD 到現在,是不是已經被別的東西動過」。如果有,這個 copy 是單純的檔案覆寫,不是 git merge/rebase,不會產生衝突提示——它會直接把主樹上更新的內容原地蓋掉,換成 worktree 裡那份基於舊 HEAD 修出來的版本,照樣 commit 成功,整個過程沒有任何錯誤訊號,是**靜默資料遺失**。

這不是假設性風險:本倉圖譜裡有一篇專門記錄「同一台機器、同一個工作目錄開兩個 Claude 對話一起做事」導致改動互相覆蓋的開放事故筆記,而且就在這份 spec 動筆前兩天(2026-08-22)記錄、「一天撞到三次,兩次有實害」,狀態仍是 `status: open`、明文「★未立案,待裁★」。該筆記把「用 git worktree 隔離」列為選項之一,但明確指出代價是「兩邊看不到對方的即時改動」,並未解決「回寫時可能蓋掉別人剛做的改動」這一段。這份 selfaudit-loop spec 的 PRIOR-ART 段落只提到「派工/週戳/LINE 全抄 run_nags/run_probe 既有慣例」,完全沒有引用或處理這篇高度相關、且尚未有定論的既有事故筆記——不符 CLAUDE.md「設計動筆前先問世界…世界解過沒」的要求。更關鍵的是,spec 的「併發」小節明確宣稱「週戳+循序派工,無共享寫」(116 行)——這句話只論證了「同一時間不會有兩個 self-audit 派工互相搶寫」,完全沒處理、也沒承認「self-audit 的 worktree 修復鏈與主樹上其他來源(人或其他自動化)的寫入」屬於共享寫入的一種,是一句涵蓋範圍不足卻寫成全稱的安全宣稱。對照本倉既有 worktree 慣例(guard-kill spec)的作法:那邊在 worktree 建立**當下**就對「來源」查 `git status --porcelain` 並示警——但解決的是另一半問題(來源在建立當下是否已是乾淨的已提交狀態),不是「目的地在回寫當下是否還跟建立時一致」;self-audit 這裡兩半都沒做。
