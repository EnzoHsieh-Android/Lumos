severity: major

### F1 「時段短於 4 個傾印間隔」有兩種讀法,傾印間隔也沒說從哪裡取得
severity: major
blocking: 是
引句:「時段短於 4 個傾印間隔時寫 failed「樣本不足」」
file: `scripts/templates/android-stability-collect.sh:307`(目前只有 `__PROCESS__` 與 `__DURATION_MS__` 兩個佔位,沒有傾印間隔)
1. 同一節裡「時段」指兩件事:「錄製時段 t0 到 t4」和「四等份裡的一個時段 [t1,t2]」。S7 又照抄「時段短於 4 個傾印間隔」。
   - 讀法 A:t4−t0 小於 4 秒才失敗。
   - 讀法 B:每一等份小於 4 秒才失敗,也就是 t4−t0 要至少 16 秒。
   - 實驗室「8 輪約十幾秒」。讀法 B 下 14 秒的錄製,每份只有 3.5 秒,四種情境全部變 failed,S5 跑不過。讀法 A 下全部放行。
   - 兩種讀法都符合字面,實作者會做出不同的系統。
2. 傾印間隔只存在於 pbtxt 範本(`dump_interval_ms: 1000`)。第 3 步要「再加一個傾印間隔」,第 4 步的 SQL 判「短於 4 個間隔」,兩處都要這個數字。
   - spec 沒說是收集腳本寫第二個常數,還是去解析範本。
   - 寫第二個常數時,改範本不改常數會讓判斷悄悄失準。
   - SQL 範本和 Python 假表測試更拿不到這個值,得靠佔位替換,spec 也沒提。
3. t0 與 t4 的取法有三個缺口:
   - t4 是「最後一列的 ts」,不是錄製結束。尾段沒有配置變化時,t4 比實際結束早。
   - t0 取 trace_bounds 起點。⚠ 我沒有真實 heapprofd 追蹤檔可驗,不知道起點是錄製開始,還是第一個 ProfilePacket 的時間。若是後者,「接上行程的那一兩秒算在第一份裡」不成立。
   - 單獨一個傾印時 t4 可能等於 t0,四個切點全部相同。spec 沒說這種輸入走哪個失敗分支。

應該是:把「時段」定義成 t4−t0(或明確逐份判),寫明傾印間隔的來源(例如由範本解析,或集中成一個常數並加測試綁定),並規定 t4==t0 一律 failed。

### F2 「樣本不足」的兩道檢查擋不住自己宣稱的前提「每一份至少涵蓋一輪」
severity: major
blocking: 是
引句:「前提是每一份至少涵蓋一輪」
1. 四等份按錄製時間切,不是按輪數切。N 小於 4 與 t4−t0 至少 4 秒,都不保證每份涵蓋一輪。
2. 具體例:N=4,前三輪各 4 秒、最後一輪 12 秒(後段變慢很常見)。
   - 一個「每輪配 2 MiB、輪初釋放」的正常來回位置:t4−t0 = 24 秒,窗口是 [6,12] 與 [18,24]。
   - 窗口 1 涵蓋完整的輪切換,取得低點 0。
   - 窗口 2 整段落在第 4 輪中段,沒有任何低點,L2 = 2 MiB。
   - 3×(2−0) ≥ 2,字面實作會把這個位置列為線性增長。S12 要的是不列。
   - ⚠ 後段輪次變慢的頻率我沒量過;這裡只證明檢查沒有覆蓋這個前提。
3. 最小值只取傾印時刻的值(1 秒一次),不是連續值。窗口剛過 4 個傾印間隔時,一份只有 1 到 2 個取樣點(窗口起點的承接值加窗口內的列)。最小值碰到低點的機率沒有保證。
4. 我用 python 模擬過:每輪 3 個傾印、其中 1 個落在低點,N=4 到 8 時窗口都夠長,沒有誤報。所以這個洞要靠「輪長不均」才會觸發。
5. N 剛好等於 4 時,「N 小於 4」不擋,且是最脆弱的情況(每份剛好一輪、沒有餘裕)。

應該是:要嘛用實際輪邊界(driver 每輪的時間戳)切窗,要嘛要求每份至少 M 個傾印,或 N 至少 8。spec 現在的檢查和前提之間沒有對應。

### F3 前 200 個先篩在 callsite 層,但條款和輸出都在呼叫位置層,分段會漏報也會少算
severity: major
blocking: 是
引句:「先篩出最後累計至少 1 MiB 的 callsite、照 L2 取前 200 個」
file: `scripts/templates/android-ui-attribution.sql:20`(只示範過往上走的 `WITH RECURSIVE`,沒有先篩再合併的先例)
1. `heap_profile_allocation.callsite_id` 是整條呼叫鏈的葉節點,從不同 Java 或 JNI 入口進來的同一個 SDK 函式,是不同的 callsite。〈判法〉第 1 條才把它們合併成(函式,.so)。spec 卻把 1 MiB 下限和前 200 名放在合併之前。
2. 漏報例:同一個 `nativeCreate`@libfakesdk.so 從 30 條不同呼叫鏈進來,每條結尾 0.9 MiB,合計 27 MiB 且線性增長。
   - 每條 callsite 都低於 1 MiB,在合併前全被濾掉。
   - 照 S1 這個位置的 L2 遠大於 1 MiB,該列出。字面實作卻一個都不列。
3. 少算例:同一位置有 300 條各 2 MiB 的 callsite。取前 200 後再合併,結尾只剩 400 MiB 而不是 600 MiB。L1 與 L2 一起被截斷,比值失真。
4. 「照 L2 取前 200」的 L2 是 callsite 層還是位置層,spec 沒說。callsite 層算窗口最小值,合併後再算一次,結果不同。因為最小值不可加,合併後的 L2 不等於各 callsite 的 L2 之和。
5. 第 200 名並列時沒有決勝規則。恰好 200 與 201 個時,取到哪一個要看引擎的排序,結果不可重現。歸併後少於 200 個沒有問題,只是列數較少。

應該是:先在位置層(合併後的累計)算 L1、L2、結尾,再篩 1 MiB、再取 200,並規定決勝鍵(例如 L2 降冪、函式名升冪)。

### F4 「沒有符號」的判準與 .so 名稱的來源沒定義,空字串、NULL 與重名會被誤歸併
severity: major
blocking: 是
引句:「沒有符號時寫成「.so 檔名+0x相對位址」並標沒有符號」
1. 「沒有符號」是 name 為 NULL,還是 name 為空字串,還是兩者都算,spec 沒說。實驗查詢只用 `coalesce(name,'?')`,而這不處理空字串。
   - 函式名是空字串時,字面實作的位置是 `'' @ libfoo.so`。
   - 同一個 .so 裡所有沒有符號的框架會合併成一個鍵,不同的洩漏相加、相抵。該是各自 `libfoo.so+0xrel_pc`。
   - ⚠ 真實 TP 對沒符號的框架給 NULL 還是空字串,我沒有追蹤檔可驗。
2. mapping 沒有名字(匿名映射、JIT):`.so` 欄位是 NULL 或空字串,「只記檔名」「是否 /system/ 或 /apex/」在 NULL 上都得到 NULL 而不是 false。
   - 這會讓 `system` 欄位寫出 null,下游的布林形狀不合。
   - spec 要求 `symbol`/`system` 是 true/false,但沒給 NULL 的處理。
3. SQLite 沒有 basename。
   - 我驗證了 `replace(x, rtrim(x, replace(x,'/','')), '')` 在內建 sqlite 上可行,對 `base.apk!/lib/arm64-v8a/libfoo.so` 得 `libfoo.so`。
   - 它對 NULL 回 NULL、對空字串回空字串。
   - 兩個不同路徑的同名 .so(`/system/lib64/libfoo.so` 與 `/data/app/.../libfoo.so`)用檔名當鍵會歸併成一項。
   - 合併後 `system` 取任一或全部,spec 沒說。
4. 解析端:函式簽名帶逗號與引號,spec 要求交給 `csv.reader`,但空字串與 NULL 在 TP 的 CSV 輸出裡都會是空欄位,Python 端分不出。

應該是:規定 `coalesce(nullif(name,''), so||'+0x'||printf('%x',rel_pc))`,mapping 無名時 so 記為固定字樣(例如 `?`)並 `system=false`;鍵加上完整路徑的系統旗標,或規定 `system` 取「任一為系統」。

### F5 呼叫者「累計最大」沒定義量度、並列規則與缺值,輸出不可重現
severity: minor
blocking: 否
引句:「呼叫者記累計最大的那個」
1. 累計指結尾值、L2 還是某個時間點,spec 沒說。三種量度挑出的呼叫者可以不同。
2. 呼叫者並列最大時沒有決勝規則。SQLite 內建與 trace_processor 的排序在並列時不保證一致,同一份追蹤檔重跑可能換人。這會讓 [test:] 的斷言不穩。
3. 位置已經是呼叫鏈最頂端(沒有上一框)時,`caller` 是 NULL。spec 沒有規定寫 null、空字串還是「?」。
4. 呼叫者本身也是配置器包裝(例如 std::function 跳板)時,要不要再往上跳,spec 沒說。第 1 條只規定位置跳過配置器,沒說呼叫者。

### F6 窗口最小值的 SQL 寫法有一個陷阱,spec 只用一句話描述,沒有條款固定它
severity: minor
blocking: 否
引句:「兩端都算、同 ts 的列一起加」
1. 我在內建 sqlite 3.53 驗證:同一個 ts 有兩列(+2000000、−2000000),`sum() over (order by ts)`(預設 RANGE 框)給兩列都是 2000000,同 ts 一起加,正確。`rows unbounded preceding` 給 4000000 與 2000000,同 ts 的列被拆開。同 ts 兩列順序不定時,中間值可能是負的或虛高,最小值被拉壞。
2. spec 自己說 `alloc_delta` 與 `free_delta` 是兩列(配置正、釋放負)。要求「同 ts 一起加」是對的,但在多個 callsite 合併成一個位置時,必須先 `GROUP BY 位置, ts` 再做視窗累計,否則不同 callsite 在同一個 ts 的列仍被拆開。條款沒有規定。
3. S12(每輪配了又還)是唯一涵蓋這點的條款,測試資料必須包含「同 ts、同位置、配與還各一列」才抓得到。目前 [test:待定]。
4. 可攜性:視窗函式與 `WITH RECURSIVE` 在內建 sqlite(3.51.0 與 python3.14 的 3.53.4)和 trace_processor 都可用,語法層面沒有問題。整數除法 `/` 在兩邊都是截斷。我驗證 `t0+(t4-t0)*k/4` 在 (t4−t0) 不能被 4 整除時取下整數,例如 10 → 2、5、7。SQLite 整數乘法溢位會轉成 REAL(`9223372036854775807*3` 得 real),但 ns 時間差遠達不到。

### F7 失敗原因的檢查順序沒定義,空結果會在 NULL 運算裡悄悄通過
severity: minor
blocking: 否
引句:「heap_profile_allocation 沒有任何一列 → failed」
1. 第 2 步的「判斷順序寫死」只涵蓋跑第二段之前的五項。跑完之後的失敗(沒有任何一列、stats 有 error 或 data_loss、樣本不足、逾時)沒有順序。
2. 具體例:`heap_profile_allocation` 為空時 `max(ts)` 是 NULL,t4 − t0 也是 NULL。SQLite 裡 `NULL < 4000` 是 NULL(假),「樣本不足」不觸發。若先判樣本不足、再判沒有任何一列,檢查結果就依實作順序而不是依資料。
3. 同時發生 stats 錯誤與沒有任何一列時,reason 文字取哪一個,S7 的測試無從斷言。
4. 只有一列且 t4 = 該列的 ts 時(trace_bounds 起點可能早於它),窗口算得出來,結果是所有位置 L1 = L2 = 0,不列,不會崩。這個情況本身沒問題,但它會被「樣本不足」或「ok 但零筆」兩條路徑之一吃掉,spec 沒指定哪條。

應該是:規定順序為 stats 錯誤、沒有任何一列、樣本不足、查詢逾時,並在 S7 逐項綁定。

### F8 配置器名單的比對方式沒定義,「operator new 系列」會因寫法不同而漏跳
severity: minor
blocking: 否
引句:「operator new 系列——第一個不是配置器的框架就是呼叫位置」
1. 名單是精確字串還是前綴,沒說。
   - `malloc` 若用前綴匹配,會吃掉使用者自己的 `malloc_wrapper`。
   - 精確比對則漏掉 `operator new(unsigned long)` 這種帶簽名的 demangle 名。
   - 沒有 demangle 時是 `_Znwm`、`_Znam`、`_ZnwmRKSt9nothrow_t`,「系列」沒說包不包含。
2. 檔名那條規則(libc.so、libc++.so 等)會跳過這些 .so 裡的所有框架,包含 SDK 呼叫的 `strdup`、`fopen` 等。這是對的行為(歸責給 SDK),但跟「配置器」這個名字不完全吻合,測試 S3 最好明寫一個 libc.so 內非配置函式的例子。

已查無問題的邊界(沒有 finding):
- L2 剛好 1 MiB:`<` 為不增長,等於走下一條,無歧義。
- 3×(L2−L1) 剛好等於 L2:`≥` 列出,無歧義。
- L1 大於 L2:3×(負數)< L2,落入「停住」,不列出,只是標籤說法不貼切。
- 累計為負:不會從合法資料出現。`_macrobench_stab_val` 對負數與 NaN 回 None,S10 會處理。
- L1 或 L2 超過 2^53:lumos 用 Python 整數運算,不經過浮點,沒有精度問題。
- 切點落在某一列的 ts 上:兩端都算,視窗端點與承接值一致,沒有重複計算。

總結:整份最高嚴重度為 major,blocking 共 4 條
