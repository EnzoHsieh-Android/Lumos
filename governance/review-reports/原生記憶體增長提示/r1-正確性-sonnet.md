### F1 前後兩半按傾印切,尾端 3 秒空轉的傾印會把後半增量稀釋掉,量測輪數少就把真漏判成「停住」
severity: major
blocking: 是
引句:「把量測期間的傾印依時間切成前後兩半」
file: `scripts/templates/android-stability-collect.sh:482-496`(現有量測的前後讀值位置;spec 的錄製設定在 r1-snapshot.md 第 111-119 行)

1. 傾印間隔固定 1 秒(`dump_interval_ms: 1000`)。實驗另外規定量測後「等 3 秒停錄」。所以傾印數取決於牆鐘時間,不取決於 N。
2. spec 沒說「前後兩半」是只算驅動期間,還是連尾端那 3 秒空轉的傾印一起算。照字面,尾端算進去。
3. 反例是 N=3,每輪約 1.5 秒,每輪配 2 MB,配置發生在 0.1、1.6、3.1 秒。傾印落在 1 到 7 秒,共 7 次。
   - 未釋放量依序為 2、4、4、6、6、6、6。
   - 中間那次是第 4 次,值 6。前半增 = 6−2 = 4,後半增 = 6−6 = 0。
   - 照字面判成「停住」,不列。這是持續每輪都漲的真洩漏,卻被分到快取那邊。
4. 實驗用 N=8 沒中招,只因為驅動期間約 12 秒以上,尾端只佔一小部分。REVISIT 只提到「N 小於快取上限會誤判」,沒提到「N 小也會讓真漏被稀釋成停住」。
5. 應該是:切半的邊界取驅動期間,或按輪次切,不按傾印數切。

### F2 「中間那次」在傾印數為偶數、1 次、2 次時沒有定義
severity: major
blocking: 是
引句:「中間那次傾印比第一次多多少」

1. 奇數次有唯一中點,偶數次沒有。
2. 傾印數 k=2 時:若中點取後面那次,後半增 = 0,線性增長永遠判不出;若取前面那次,前半增 = 0,又變成「不增長」。
3. k=1 時,第一次、中間、最後三者同一點,兩個增量都是 0。
4. 還有一個疑點:停錄 `kill -TERM` 後 heapprofd 會不會多補一次收尾傾印,間隔是短的不規則一次。這會讓 k 的奇偶與時間間隔都不可預測。spec 沒查證,⚠。
5. 驅動不到 2 秒時 k 很小,k=1 或 2 的情形一定會發生。spec 沒寫 k 太小時的處理,例如列為「資料不足」。

### F3 三種判法有缺口、有重疊,沒有絕對增量下限
severity: major
blocking: 是
引句:「結尾還留著、前半有增、後半增量至少是前半的一半 → 線性增長」

設前半增為 f,後半增為 b,結尾為 E。spec 的三條:
- 線性:E>0 且 f>0 且 b≥f/2。
- 停住:E>0 且「後半沒有跟著漲」。
- 其他:不增長。

1. **缺口一:f≤0 且 b>0。** 洩漏從量測中段才開始,或前半被第一次傾印吸收。照字面落到「其他→不增長」,但實際在增長。
2. **缺口二:0<b<f/2。** 例如 f=4 MB、b=1 MB。「後半沒有跟著漲」沒定義是 b≤0,還是 b<f/2。b=1 這一格,「停住」和「其他」都能套,兩者互不互斥取決於實作者怎麼猜。
3. **沒有絕對增量下限。** 結尾持有 50 MB 穩定的大物件,取樣估計抖動讓 f=+0.1 MB、b=+0.06 MB,滿足 f>0 且 b≥f/2,判成「線性增長」。
   - spec 只有一個 1 MB 的列出下限,而且 F6 裡那句「結尾或增量」的 OR 語意不清。
   - 若 OR 的意思是結尾超過 1 MB 就列,這個誤報就成立。
   - REVISIT 承認取樣會抖,但把下限留到 2027 年才定,現在的字面規則會誤報。
4. **負增量未涵蓋。** f>0、b<0 是停住,還是別的?spec 沒說。

### F4 「malloc 上一層」在 operator new、wrapper、無符號 .so 時全部併成同一個呼叫位置
severity: major
blocking: 是
引句:「按「malloc 上一層是哪個函式」彙總到每次傾印時還沒釋放的量」

查詢取的是 `c.parent_id` 對應的 frame。實驗的 SDK 直接呼叫 malloc,所以剛好有效。實際專案會碰到下面幾種:

1. **C++ 的 `new`。** 路徑是 `operator new` → `malloc`,malloc 的上一層是 `operator new @ libc++_shared.so`(或 libc.so)。App 與第三方 .so 的所有 `new` 都併成同一列,真正的呼叫者被隱藏。一個持續漲的 `new` 與一個穩定的快取 `new` 加總後,互相掩蓋或互相污染。
2. **自有的 allocator wrapper**,例如 `xmalloc`、池分配器、`je_malloc`、`std::allocator`。同樣把一支 .so 內所有配置併成一列。
3. **calloc、realloc、posix_memalign**:malloc 上一層是否仍等於呼叫者,取決於 libc 實作與 heapprofd 的 hook 剝離哪幾層。spec 只驗了單一 malloc 路徑,calloc/realloc 沒驗。⚠
4. **無符號的第三方 .so。** 查詢用 `coalesce(pf.name,'?')`,所有沒符號的函式併成 `? @ libx.so`。spec 實驗特別註明「這支 .so 沒拿掉匯出符號」,但目標場景正是帶第三方 .so 的專案,它們通常 strip 過。這時提示只能指出「某支 .so 在漲」,不是 spec 白話所說的「哪個函式」。
5. 內聯會使上一層變成呼叫者的呼叫者,同樣誤指。
6. spec 沒寫遇到這些情形時是往上多走幾層,還是標示「位置不精確」。

severity: minor

引句:「結果檔只存每個呼叫位置的數字(函式名、所在 .so、結尾未釋放、前半增、後半增、判法)」

### F6 排序鍵與列出下限的說法,正文與條款不一致
severity: minor
blocking: 否
引句:「線性增長的照增長量排序列成優化建議」

4. 實作者要選一種,選錯就和測試對不起來。
