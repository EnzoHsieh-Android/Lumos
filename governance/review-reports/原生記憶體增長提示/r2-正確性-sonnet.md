### F1 結尾那次傾印的時間點在正式版被拿掉了緩衝,「正常版」會被判成線性增長
severity: major
blocking: 是
引句:「驅動一跑完就停錄 → 讀 pid 與結束紀錄」

### F2 「樣本不足」的門檻和三個時間點的需求對不上,中間點可能與開頭或結尾重合
severity: major
blocking: 是
引句:「驅動跑不到 2 秒時傾印不到 3 次,列成樣本不足」

1. 〈判法〉第 2 條「傾印少於 3 次」算的是整段錄檔的傾印總數,不是量測視窗內的傾印數。
2. 第 3 步在驅動前先等「dump_phase_ms 再加 1 秒」,約 2 秒。這段等待本身就會產生約 2 次傾印(第 1 秒、第 2 秒)。所以〈實務隱患〉說「驅動跑不到 2 秒才不到 3 次」不對,實際上驅動只要跑超過約 1 秒,總數就 ≥ 3。
3. 具體例:傾印落在 1s、2s(驅動前)和 3.1s(驅動剛結束)。
   - 開頭 = 2s,結尾 = 3.1s。
   - 「最接近正中」的候選只有開頭或結尾本身,所以 mid == start 或 mid == end。
   - mid == start 時,後半增量 = 整段增量,任何 ≥ 1 MiB 的增量一律判成線性增長。這對一次性初始化的配置(快取剛填滿、單次大配置)是誤報。
   - mid == end 時,後半增量 = 0,真正的線性增長會被判成「停住」,是漏報。
4. 「一定有開頭」也沒有保證。第 3 步是用 sleep 等第一次傾印,不是等到真的看到它。
   - no_startup 接已在跑的行程,需要 heapprofd 發訊號、client 初始化。慢的裝置上第一次傾印可能晚於 2 秒。
   - 那樣就沒有「驅動前的最後一次傾印」,開頭未定義。
5. 另一個缺口:「驅動量測開始前」與「驅動跑完」是以主機時間為準的事件,傾印時間是追蹤檔的時間軸。spec 沒寫兩者怎麼對時,實作者只能自己猜邊界。
6. 應該改成:量測視窗內的傾印數至少要有可分出前後兩半的數量,並寫明對時方式。

### F6 〈實驗室實測〉用新判法「重算相同」沒有可驗的數字,而且閾值與規則的邊界沒有交代
