### f1(major)—— `governance/eval/build_goldset.py` 的 `edit_pool()` 是 spec 完全沒點名的第六個 `results` 讀者

spec 段落:§2「安置模型」/ opt-in 名單(#2b)

引句:「結構性不受影響;要用 lane 的地方」

問題:spec 宣稱「沒學過 lane 的既有讀者」名單(`cmd_impact_diff`/hook free 桶/`_bound_tests_for_diff`)加上 opt-in 名單五處(①②③④⑤)已經窮盡了 impact JSON `results` 鍵的消費者,但全 repo grep `"results"` + `json.loads` 找到 `governance/eval/build_goldset.py:159-160` 的 `edit_pool()` 完全沒被提到:

```python
ranked = lum_json("impact", "--file", file, "--ranked", "--top", "8",
                  "--stdin-payload", "--json", stdin=payload).get("results", [])
```

它跟 `retrieval_eval.py` 的 `edit_universe`(spec opt-in ③ 點名的那個)是同款呼叫模式(`impact --ranked --json` 後 `.get("results", [])`),但 `edit_universe` 用來給**既有題目**計分,`edit_pool` 是用來給**新題目**建候選池(`build_goldset.py --append N` 出新 edit 題時,從這個 pool 隨機抽 12 個候選給人標)。knob=1 落地後,RISK 類間接節點(現行仍 pinned 進 results 的那批)會整批消失於 `ranked`,`edit_pool` 完全不知道 lane 這個鍵存在——未來 `--append` 出的新題,候選池會系統性漏掉所有 lane 資格節點,連帶這些節點永遠拿不到人工標註,goldset 沒有機會累積 lane 命中的 label=2 證據。這正好打中本案自己想觀測的東西(out_top3_must / 固定席噪音的反面即是漏檢),卻沒被算進「漏的讀者」清單——不是崩潰風險,是評測資產的靜默偏移,且沒有測試會抓到(#6 的 11 條測試全部針對 `eval_edit`/`_touched_edit`/hook/`cmd_impact_diff`,沒有一條碰 `build_goldset.py`)。

查證:`governance/eval/build_goldset.py:159-160`(`edit_pool`)、對照 `governance/eval/retrieval_eval.py:122-139`(`edit_universe`,同款呼叫但被 spec 點名)。

### f2(blocker)—— 落地驗收段自己還留著一句跟 §2 核心模型正面矛盾的 must_in_out 舊句

spec 段落:落地驗收(照症狀指令)

引句:「must_in_out:不變(測試釘:被降節點仍在 JSON results)」

問題:這句話(spec 第 116 行)緊接在「★must_in_out 一句話講死(Codex r3 f2:原文同時寫「不退」與「可能掉」)★:cap 內結構性不退;被 cap 砍的會誠實掉數字且棘輪抓」(第 114-115 行)**正下方**,兩句話講的是同一個量,結論卻不同:
- 114-115 行(r3 折入後、應該是新版本):must_in_out 在 lane cap 內結構性不退,**但被 cap 砍掉的會誠實掉**(可能變化)。
- 116 行(殘留舊句):must_in_out **不變**,理由是「被降節點仍在 JSON `results`」。

後者直接違反 §2 的核心設計:「★被降的節點★自始不進 `results` 共用清單……收進獨立 `lane_items`」「JSON 輸出用獨立頂層鍵 `"lane"`,`results` 完全不含 lane」——被降節點依設計**不在** `results` 裡,它在獨立的 `lane` 鍵裡。116 行說「被降節點仍在 JSON results」是 r3 折入獨立鍵模型**之前**的舊事實(那時候安置模型還沒釘死,`results` 可能還沒跟 lane 分家),r3 把安置模型改掉之後這句話理應被拿掉或改寫成「被降節點仍在 JSON `lane` 鍵(cap 內)」,但沒有被更新,原句原封不動留到了 r4。這正是 Codex r3 f2 當時抓到的「原文同時寫『不退』與『可能掉』」那個矛盾的**同一體裁**——上一輪审计明明已經點名要「一句話講死」,折入時卻只改了緊鄰的那一句(114-115),漏改了同段落內第二處提到 must_in_out 的殘留句(116)。這是本輪 CLAUDE.md 講的「單篇筆記內部新舊打架」的典型案例:如果實作或測試撰寫者按字面讀 116 行,會誤以為「被降節點必須仍出現在 `results` 鍵下」去寫斷言或改代碼,那會直接把獨立鍵模型做壞(退回 r3 之前「不進 results」與「final=...+lane_items」自相矛盾的舊狀態)。

查證:spec 第 114-116 行(比對用);`scripts/lumos:14528`(`out_obj = {"file": rel_file, "results": final, "meta": meta}`,現行 `results`/`final` 就是唯一輸出集合,尚未拆分 lane——確認目前 repo 狀態下「demoted 節點仍在 results」在**現行 code** 是事實,但 spec 改完後就不該再是事實,116 行沒有跟著改)。

### f3(major)—— opt-in ③④ 沒有把 `edit_universe` 的新回傳形狀寫清楚,有很高機率重演 r2 s2f5 那個「lane 被非 pinned=free 分流吃回自由席」的同款漏洞

spec 段落:工具清單 #2b item③④

引句:「④`eval_edit`:★只動兩處★——`out_nodes`/`must_in_out` 讀 results ∪ lane」

問題:item③ 只說 `edit_universe`「現在只抽 `results` 鍵,lane 要一併帶出」,沒說帶出的形狀是什麼——是回傳 `(results, lane)` 兩個分開的 list,還是把 lane 項目併進同一個 list(每項帶 `lane: "soft-guard"` 標記,跟現行 `rescued: True` 的做法同款)？這個沒寫清楚的介面決定,直接關係 item④「只動兩處」這句話是否站得住:

現行 `eval_edit`(`retrieval_eval.py:335-336`)的 `free` 是這樣切的:
```python
pins = [x for x in res if x.get("pinned")]
free = [x for x in res if not x.get("pinned")]
```
item④ 明講這行要改成「明文排除 rescued」(即 `and not x.get("rescued")`),但沒提要不要順手排除 lane。如果 `edit_universe` 選的是「併進同一個 list」這條路(而 spec §2 自己在講「為什麼不擴 rescued」時明講「實作同家族……五個維度全照 rescued 慣例」——即 lane 項目的欄位設計本來就是刻意仿照 rescued,包括讓每項自帶判別標記),那 `free` 這行不加 `and not x.get("lane")` 就會讓 lane 項目(pinned 固定是 `False`,見 §2「欄位:`lane: "soft-guard"`、`pinned: False`」)直接漏進 `free`,進而漏進 `eval_edit` 用 `free` 算的 `orders`(fusion/bm25/graph 三種排序的 P@k/nDCG 母體,:340-352)——這正是 r2 s2f1/s1f1 抓到的「非 pinned=free 分流吃回自由席」同一種漏洞,只是換了消費者(從 CLI 內部搬到 eval 腳本)。這會直接打臉 §3「free 集合與排序完全不動→P@8/nDCG 逐 byte 不變」的結構保證——如果 lane 項目滲入 `free`,P@8/nDCG 的計分母體就變了,不是逐 byte,是真的變了。

工具清單 #6②「P@8 母體不含 lane」這條測試理論上能攔住這個漏洞,但它的有效性完全取決於 `edit_universe` 真的把 lane 帶出來讓測試看得到——如果測試作者跟實作者對「帶出」的理解不一致(比如實作用分開回傳、測試以為是併入,或反過來),测试有可能因為 lane 項目根本沒進到 `res` 而「意外地」通過(P@8 母體查無 lane,不是因為過濾對了,是因為 lane 根本沒被帶進來,跟 `t_impact_contract_risk_axis` 那個假綠是同一種「測到不相干的東西」)。這一段没有一個明確的介面契約,是本輪唯一新定的地方(r3 折入)裡,唯一還留有實作彈性、而這個彈性剛好踩在「本案已經燒過一次的坑」正上方。

查證:`governance/eval/retrieval_eval.py:122-139`(`edit_universe`)、`:335-336`(`eval_edit` 的 pins/free 切法)、`:159-166`(`_touched_edit` 的另一份切法,同一檔案兩種定義,佐證 spec §2b⑤「同檔兩種 free 定義」的診斷準確)。

### f4(blocker)—— opt-in ①②在「要不要用 `.get` 防禦」這件事上互相矛盾,而②那邊的空缺剛好撞上 knob 預設 0 的常態,會讓 PreToolUse hook 在預設設定下每次都拋未捕捉例外

spec 段落:工具清單 #2b item①②

引句:「②hook `build_ranked_context` 新小節讀 `data["lane"]`」

問題:同一行裡,item①明講「`cmd_impact` 人讀純文字分支加 lane 小節(kind 表加 lane,**score 用 `.get`**)」,特別點名要用 `.get` 防禦;item②講 hook 的對應改動卻是「新小節讀 `data["lane"]`」,字面是直接下標,沒有比照①附上同款防禦提醒。這個不對稱在 spec 自己的落地驗收裡有實際殺傷力:工具清單 #4「總開關 `LUMOS_IMPACT_HARD_PIN`,★預設 0(上線即死碼)★」+「參考道整段包在 knob=1 分支內(s2f13:單開關回滾逐 byte)」——合起來的意思是 knob=0 時 CLI 的 JSON 輸出**逐 byte** 等於現在的樣子,也就是完全不含 `"lane"` 這個鍵(不是空陣列,是鍵不存在,才談得上「逐 byte 相同」)。knob 預設值就是 0,代表從這個改動落地那一刻起,一路到「train 網格、held 驗一次、gate 全過才轉預設 1」這整段轉正期間,`lumos impact --ranked --json` 的輸出**都不會有** `"lane"` 鍵。

查證:`scripts/hooks/claude/impact-hook.py:328-330`(現行 `build_ranked_context` 讀 `data.get("results", [])`/`data.get("meta", {})` 都已經是 `.get` 防禦寫法,佐證這支函式自己的既有慣例就是「頂層鍵一律用 `.get`」,新小節若破例直接下標,連風格上都跟同函式其他行不一致)、`:485-492`(`main()` 裡 `inject_ranked_context(impact_data)` 前後沒有 try/except)。
