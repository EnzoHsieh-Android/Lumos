## Finding 1 — MAJOR

引句:「未來出題的候選池要含 lane(人看得到的都該能被標)」

問題:opt-in ⑥ 只講「要含 lane」,完全沒提這件事跟 `ablation_blocked`(消融前置閘,任何未標候選就擋、rc3)之間的互動——而這正是落地驗收唯一的入口:「以 `LUMOS_IMPACT_HARD_PIN=1` 臂的考卷實測為準」(:119)必須先過 `--ablation` 這道閘才拿得到數字。

我把互動鏈逐段跑過一次,結論是「目前參數下大機率安全,但 spec 完全沒寫這段推理,也沒有測試釘住這個不變量」:
- `_touched_edit` 現況(`retrieval_eval.py:159-168`)是 `free[:k] + 全部 pins`(pins 不受 `--top` 限制);`cmd_impact` 的 pins 目前對「有合約」(含 RISK·*)一律無上限收(`scripts/lumos:14457-14468`),所以**今天**所有 RISK-indirect 節點早就在 `_touched_edit` 的觸及集裡。
- 症狀段(:37-40)貼出的 `--ablation` 真跑輸出沒有被 rc3 擋下,代表**今天**這批節點全部已標——這是可驗證的既成事實,不是我的假設。
- 主案把這批節點從「無上限 pinned」改成「產生階段用 `LUMOS_IMPACT_LANE_N`(預設 3)按 `(-score,hop,node)` 砍」(:78-80)。這是對「已標節點集合」取子集,被砍掉的節點整個從輸出消失、根本不進 `_touched_edit`——不會冒出「以前沒出現過的候選」。
- `build_goldset.py` 的 `edit_pool()`(:157-167)出題當時查 `impact --ranked --top 8`,pins 同樣不受 `--top` 限制,所以歷史出題池本來就撈到過同一批節點,不是 opt-in ⑥ 之後才第一次撈到。

但這條推理鏈**成立的前提**是「當初出題時 vault 就長這樣」,而 goldset 標籤在本案凍結(:112「不補標、不改答案」)——期間 vault 若新增一篇 `risk/*` 標籤、剛好 hop=1 連到某個既有 edit 案例的檔,那就是一個**歷史上從未被任何候選池撈過**的全新節點,會被 `_touched_edit`(opt-in ⑤ 改完後 lane 視同 pins 納入未標檢查)第一次撈到、且未標→直接觸發 rc3。retrieval_eval.py 自己的 `vault_note` 欄(:522)承認「活語料:節點增修致數字 ±1pp 漂移」是常態,不是罕見狀況。真的踩到時,凍結決策(:112)又明講不能補標,驗收會卡在一個 spec 沒寫出退路的地方。

這不是「這個設計會壞」的 finding,是「這個設計為什麼不會壞,以及萬一壞了怎麼辦,spec 一個字都沒講」——對一份已經連審五輪、連 must_in_out 一句話怎麼講都要修三次的 spec 來說,這處空白不對稱。

## ⑬ edit_pool 測試的 fixture

已讀,無 finding。`build_goldset.py` 的 `edit_pool()`(:157-167)呼叫的是模組層級裸函式 `lum_json(...)`,而 `retrieval_eval.py` 測試群已經證明這種呼叫可以用 `m.<函式名> = lambda *a, **kw: 假資料` 整個替換掉(`m.edit_universe = lambda case: canned`,同上)。同一招搬到 `build_goldset_fx`/`build_goldset_fx2`(既有兩個動態載入 `build_goldset.py` 的 fixture,:20716、:20794)上,`m.lum_json = lambda *a, **kw: {"results": [...], "lane": [...], "direct": [...], "indirect": [...]}` 即可讓 `edit_pool()` 在完全不碰真 vault/subprocess 的情況下跑出含 lane 候選的池——`.get("lane", [])`/`.get("direct", [])` 這類寫法對缺鍵容忍,不需要為兩次不同呼叫(ranked/legacy)分別造不同回傳值。

## 混版協定 ⑦「install 同步保底」對照 install.sh 現況

已讀,無 finding——宣稱屬實。追蹤了完整鏈路:`install.sh`(4 行)→ `lumos install --force` → `cmd_install`(`scripts/lumos:8666-8703`)→ 尾端呼叫 `_sync_global_claude(Path(__file__).resolve().parent.parent)`(:8693,來源固定是「這份 `scripts/lumos` 所在的 repo 自己」)→ `_sync_global_claude`(:9504-9529)把 `impact-hook.py` 從**同一個 repo 的同一個 commit**複製進 `~/.claude/hooks/`(:9513-9516,`shutil.copy2`)。這代表:只要 hook 與 CLI 的改動落在同一個 commit(spec 承諾「落地 commit 註明『hook 與 CLI 同批更新』」),重跑一次 `lumos install` 就保證兩者版本一致——機制真實存在、行為與宣稱相符。

需要指出的一個限制(不影響「成立與否」的判斷,但值得知道):這個同步是**手動觸發**、不是自動的——`~/.local/bin/lumos` 是 symlink 會隨來源 repo `git pull` 立即生效,但 `~/.claude/hooks/impact-hook.py` 是 `copy2`,舊版會停留到下次有人手動重跑 `install`。也就是說中間會有一段「新 CLI + 舊 hook」的空窗期——但這正是 spec 自己在同一句話裡講的「舊 hook 配新 CLI 在 lane-only 情境=不注入(退化不炸,可接受)」,兩處對得起來,沒有矛盾。
