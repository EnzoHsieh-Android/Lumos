## finding 1:`:(literal)` 前綴加全域 `--literal-pathspecs`,每支文字檔的 diff 都是空的

severity: major
blocking: 是 — 照字面做,文字檔的改動指紋整批失效,可能變成跟程式無關的常數。
引句:「單獨跑一次 diff(路徑用 git 原樣路徑、加」
問題:計劃同時要求兩件事。一是路徑加 `:(literal)` 前綴。二是全域選項放 `diff` 之前,含 `--literal-pathspecs`。我實測,`--literal-pathspecs` 開著時,git 把 `:(literal)a.py` 當成檔名字面上就叫「:(literal)a.py」。這個路徑不存在,所以輸出是空的。
失敗情境:
- 輸入:`git --literal-pathspecs diff HEAD~1 HEAD -- ':(literal)a.py'`,a.py 確實有改。
- 結果:輸出為空,rc=0。拿掉全域旗標,或路徑不加前綴,輸出都正常。
- 後果:`_patch_file_changes("")` 回 `{}`。計劃沒寫這種情形怎麼處理。實作若把它當「未改」或空字串的雜湊,v2 就跟程式內容無關,記過一次後所有同形狀的分支都被當成已對照。
- 測試:S2 應該會翻紅,但計劃本身要改成兩者擇一,並補一句「清單裡有的檔卻拿到空 diff,整篇退回 `v1`」。
file: `scripts/lumos:25875`(`_patch_file_changes` 對空文字回 `{}`)

## finding 2:重用 `_patch_file_changes` 的 `splitlines()` 會吞掉同一行裡換頁符號之後的內容

severity: major
blocking: 是 — 文字檔的真改動拿到同一個指紋,是「該重讀被當已對照」。
引句:「那會把不同的非 UTF-8 位元組變成同一個字」
問題:計劃說「位元組原樣」。但被重用的函式用 `for ln in text.splitlines()` 切行。`splitlines()` 會在 `\x0c`、`\x0b`、`\x1c`~`\x1e`、`\x85`、U+2028、U+2029 切開,連 `\r` 也算行尾。切出來的後半段不以 `+`、`-`、空白開頭,在 hunk 內被丟掉。
失敗情境:
- 輸入:一行 `y = "a<FF>b"` 改成 `y = "a<FF>c"`(`<FF>` 是 `\x0c`)。這是兩個不同的 patch。
- 結果:`_patch_file_changes` 對兩份 diff 都回 `89706b7b…`,指紋相同。
- 後果:換頁符號在 Python 原始碼裡不算罕見(Emacs 分頁線)。作者改了換頁符號之後的字,v2 指紋不變。
- 資安席那邊原本也有這個行為,但計劃把它當成回頭重讀的唯一正規化,又明講位元組原樣。
- 修法:加「改用 `split("\n")`」的參數,或寫一條測試。
file: `scripts/lumos:25905`

## finding 3:v2 沒綁到檔案版本,主線上很久以前的紀錄可以替之後相同文字的 patch 背書

severity: major
blocking: 是 — 守衛面,紀錄永久留在主線,放寬是無時間界限的。
引句:「有一筆已提交、來源核對過的紀錄,開頭是這篇的」
問題:
- 舊指紋含頂端整份 blob,所以一份紀錄只對「那一版程式」背書。
- v2 只含「patch 本文加前後 3 行上下文」,不含檔案其他部分,也不含任何時間或提交錨點。
- 紀錄在主線上永遠留著。之後任何分支只要對同一篇筆記產生逐字相同的 patch(上下文一樣),就命中那份舊紀錄。
- 計劃〈實務隱患〉只論證了「主線改了作者沒碰的地方」,沒討論「同樣的 patch 在不同檔案版本上重現」。
失敗情境:
- 輸入:
  1. 分支 A 把 `DEFAULT_GATE = "warn"` 改成 `"block"`,上下文固定,記了 v2 紀錄,合進主線。
  2. 之後有人改回 warn,筆記句子也跟著改成「預設 warn」。
  3. 分支 C 再做一次「warn 改成 block」,patch 逐字相同。
- 結果:命中 A 當年的 v2 紀錄,筆記沒被重讀。
- 注意:在 v1 之下這需要整份檔案逐位元組相同,幾乎不會發生。
- 建議限制 v2 只認「本分支 分岔點..頂端 之間新增的紀錄」,或把紀錄寫入時的分岔點/頂端記進紀錄並比對。

## finding 4:分岔點把本機 main 還沒推出去的提交當成「主線」,那些改動沒有人重讀

severity: major
blocking: 是 — 推送前閘的核心前提「主線改動有人負責」在這條路徑上不成立。
引句:「主線那邊的改動照常由它自己那次推送(以它自己的候選)處理」
問題:`_codeloop_default_base` 會把本機 `refs/heads/main`、`refs/heads/master` 加進候選,再用 `merge-base --all HEAD <候選…>` 取最近的共同祖先。程式註解寫明是刻意的:「本機主線可能有還沒推上去的提交」。這對算風險分級可以。對 v2 就不行,因為本機 main 上未推送的提交沒有任何一次推送替它重讀過。
失敗情境:
- 輸入:本機 main 上有 M1(動了 `a.py`,沒推)。作者從這個 main 開分支,只動 `b.py`。某篇筆記的 about_code 是 `a.py` 加 `b.py`。推送這條分支,M1 也一起上去。
- 結果:分岔點在 M1 之後。v2 指紋裡 `a.py` 是「未改」,判定者的 diff 只含 `b.py`。M1 對 `a.py` 的改動沒有被任何人對照,卻進了遠端。
- 同一個機制:別的 worktree 或別的 Claude 會談在本機 main 上提交,也有同樣效果。
- 計劃〈做法〉3 的「已知會變的情形」只列了快轉、fetch、多共同祖先,沒列這一種。
- 建議:指紋用的分岔點只收遠端主線候選,不加本機 main/master;或對本機 main 超前遠端的部分退回 `v1`。
file: `scripts/lumos:50982`

## finding 5:分支上記的 v2 紀錄,快轉進 main 後推 main 全部不命中

severity: minor
blocking: 否 — 多列方向,不漏判。
引句:「分岔點就是頂端本身(推的是主線、或頂端已在主線上)」
問題:
- 常見流程是在分支上 prepare 並記 v2 紀錄,再本機快轉合進 main,最後推 main。
- 推 main 時頂端就在主線上,分岔點等於頂端,退回 `v1`。
- 紀錄是 v2,`v1` 對不上,同一批筆記全部被重新列出,閘設為 block 時會擋住。
- 舊指紋在這個流程下是命中的,所以這算新的退步。
- 這對「雙認」的好處是單向的:`v1` 紀錄升級後仍可用,但 `v2` 紀錄在 `v1` 判定時不可用。
- 計劃回退一節只講了還原提交,沒講這個日常流程。
- 建議:prepare 算得出 `v2` 時,同時把 `v1` 指紋寫進紀錄(紀錄內容欄位),check 的 `v1` 路徑比內容欄位而不只比檔名前綴。

## finding 6:事件欄位量不出 RETIRE-IF 要的那一群,也抽查不到具體篇

severity: minor
blocking: 否 — 影響日後撤除判斷的可信度,不影響當下的對照正確性。
引句:「就是新指紋放寬的全部範圍,RETIRE-IF 的漏判抽查從這一群抽」

- 建議:規定先判 `v1`,`v1` 不中才看 `v2`。事件另記「靠 `v2` 命中而 `v1` 不中」的筆記路徑與兩個指紋(上限筆數)。
