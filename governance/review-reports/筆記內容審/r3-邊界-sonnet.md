# r3 邊界可執行審查(筆記內容審_計劃)

範圍聲明:本輪只打「邊界可執行」這支鏡頭,聚焦 r2 新寫的六個細節(小標題跳過圍欄、decisions 用決策編號加欄名、結構行定義、切批 150 行與同篇不拆、清單指紋=檔案雜湊、判定檔檔名格式、decision-amend 的遠端 reflog 新鮮度、skip 空集合、check 批次讀檔)在極端輸入下的正確性。防作弊已被 Enzo 2026-09-28 裁定收窄掉(做法第 0 節),本輪不把「存心刪改判定檔/治理帳能繞過」當缺陷報。以下 F1–F5 全部逐字對過凍結工作副本與程式碼現況,其中 F1 另外用 /tmp 的乾淨 git 倉庫實測驗證。

## F1 decision-amend 的遠端新鮮度檢查,在最常見的兩種情境下永遠拒絕、且工具自己印的補救指令沒用

severity: blocker
blocking: 是 —— 這是「做法」條款 [S12]、也是 r2 剛修好、聲稱解決「全新 clone 沒有 FETCH_HEAD」洞的那個機制;实测显示 r2 的修法沒有真的解決,反而在最常見的兩種情境下讓 decision-amend 永遠不可用,而且工具自己教的補救動作(`git fetch --all`)在最常見的那種情境下完全沒用,使用者會卡死、以為工具壞了或反覆重跑同一個指令。

引句:「對每個遠端,看它底下追蹤參照 reflog 裡最新一筆(fetch、pull、push、clone 都算)距今不超過 10 分鐘,任何一個遠端超過或沒有紀錄就拒絕並印 `git fetch --all`」

我在 /tmp 開了一個乾淨的裸倉庫加一個新 clone,實測 git 的真實行為(命令與輸出如下,可重現):

```
$ git clone remote.git clone1
$ git reflog show refs/remotes/origin/main      # 剛 clone 完
(空,沒有任何輸出)
$ ls .git/FETCH_HEAD
ls: .git/FETCH_HEAD: No such file or directory
```

情境一(全新 clone,r2 聲稱已修好的那個洞):`git clone` 只建立 `refs/remotes/origin/*` 這幾個 ref,不寫任何 reflog 項目到 `.git/logs/refs/remotes/origin/*`(這支檔案根本不存在)。所以照字面規則,一個「剛剛才 clone、資料絕對是新鮮的」倉庫,`decision-amend` 會因為「沒有紀錄」而拒絕——這正是 r2 引句裡承認要修的洞(「原稿只看一個時間、沒說去哪看、全新 clone 沒有 FETCH_HEAD」),但换成 reflog 之後,reflog 一樣是空的,同一個洞用另一個名字原封不動地留著。

情境二(遠端沒有新提交時執行補救指令):我接著在同一個 clone 上跑 `git fetch origin`(此時遠端沒有新東西),`.git/logs/refs/remotes/origin/main` 依然不會被寫入(git 只在 ref 真的移動時才寫 reflog)。等我在遠端造出一個新提交再 fetch,reflog 才第一次出現一筆:

```
$ git fetch origin -q   # 遠端沒有新東西時
$ find .git/logs -type f
.git/logs/HEAD
.git/logs/refs/heads/main
.git/logs/refs/remotes/origin/HEAD     # 沒有 origin/main
$ # 遠端造一個新 commit 後再 fetch
$ git fetch origin -q
$ git reflog show refs/remotes/origin/main
757463f refs/remotes/origin/main@{0}: fetch origin -q: fast-forward
```

也就是說,`decision-amend` 拒絕之後,工具自己印出來的補救指令「`git fetch --all`」只有在「遠端剛好有新提交」時才有效——這是日常開發裡最不典型的情況(多數時候你的分支已經追上遠端、fetch 什麼都不會拿到)。在最常見的「你的本地已經是最新」情境下,照著工具指示跑 `git fetch --all` 不會產生任何新的 reflog 項目,`decision-amend` 會用一模一樣的訊息再次拒絕,形成使用者跑不出來的死循環,唯一的出路是等別人推點東西上遠端、或用 `git push`(我也實測 push 會寫 `update by push` 項目,但這代表你得先製造一次無關的推送才能解鎖 decision-amend,不是合理的操作)。

這條規則直接影響條款 [S12] 的驗收(「任何一個遠端的追蹤參照最新紀錄超過 10 分鐘或沒有紀錄時應拒絕」),而它所防的、以及它給的補救辦法,兩者合起來在真實 git 行為下互相打架。

## F2 「圍欄記號行」的反引號門檻,同一份文件裡自相矛盾,而且其中一種寫法跟 `_visible_lines` 的實際程式碼對不上

severity: blocker
blocking: 是 —— 這是「不審的行」清單的定義句,直接決定 content-id 的收集範圍與 S4 條款「圍欄記號行(含四個反引號)…不應被收進待審」的驗收基準;兩句對同一支函式給出不同數字,任何一種讀法都跟實測到的程式碼行為對不上一半。

同一節(做法 §1「哪些行要審」)裡,兩句話都在描述 `_visible_lines` 認得的圍欄記號,數字不一樣:

引句:「用全檔唯一的圍欄判定 `_visible_lines`,它認得三個以上反引號或波浪號的圍欄」

引句:「圍欄記號行(`_visible_lines` 認的那種,含四個以上反引號與波浪號)」

實際程式碼(file: `scripts/lumos:3262`):

```
is_marker = indent <= 3 and not ln.startswith("\t") and s.startswith(("```", "~~~"))
```

`s.startswith(("```", "~~~"))` 判的是「至少三個」反引號或波浪號(標準 Markdown 圍欄),不是四個。所以第一句(「三個以上」)才符合程式現況,第二句(「含四個以上」)跟 `_visible_lines` 的真實行為不符。這不是筆誤兩選一都無傷:如果實作照字面第二句(四個以上)寫「不審的行」判準,本 repo 裡幾乎所有筆記用的標準三個反引號圍欄行(單獨一行的 ` ``` `)就不會被判成結構行,而會被當成一般新增內容送進 content-id 收集與判定者派工——這條記號行本身沒有任何主張,判定者拿到一行只有標點符號的內容要在 CODE/CONTEXT/MIXED 三類裡選一個,派工詞完全沒有為這種輸入準備分類依據(七句補充裡沒有一句涵蓋「這一行本身沒有語義內容」),結果不可預期且會製造無意義的待審負擔,而且跟同一段文字聲稱的「這些沒有主張,共用編號會互相拖累」(r1 對應理由)自相矛盾。

## F3 「待審超過 150 行切批」與「同一篇筆記盡量不拆開」在單篇筆記本身就超過 150 行時沒有定義誰讓步——而校準流程自己排的測資就會撞上這個情境

severity: blocker
blocking: 是 —— 這兩條規則同時出現在同一句、管的是同一份清單的切法,對「單篇超過 150 行」這個具體、且被計劃自己指定為上線前必測案例的輸入,沒有給出可執行的優先順序,實作者只能自己猜。

引句:「★待審超過 150 行就切成多份清單★,每份不超過 150 行、同一篇筆記的行盡量不拆開」

「盡量」代表這條是盡力而為、不是硬性合約(對照 S5 條款也確實沒有把「同篇不拆」列進驗收項,只驗了「每份不超過 150 行」)。但「上線前校準與接線」那節明講要拿一份超過 150 行的單篇整篇筆記去跑:

引句:「再加一份 300 行以上的已完成計劃整篇」

一篇 300 行以上的計劃收尾時,依「計劃在範圍內被收尾」那條規則,正文、summary、decisions 文字子欄「都」要進完成審,也就是這一篇單獨就會產生遠超過 150 行的待審清單。這時候「每份不超過 150 行」與「同一篇盡量不拆開」兩個目標互斥,規格沒有講清楚是要打破 150 行上限(讓一份清單裝下整篇),還是把同一篇硬拆成多份(讓判定者失去跨行上下文,尤其影響 §2「同一個內容編號列了好幾處時只給一個判定,語境不同給較重的」這條——如果兩處出現在被拆開的不同批次,兩個獨立派出的判定者各自只看到片段語境,拿到的判斷依據跟規格要求的「看到全部語境再取較重」不是同一件事,雖然事後 §2 的折疊規則會用「取最重」兜底,但兜底跟規格明文要求的「同一個判定者能看到全部語境去下一個判定」是兩回事)。這不是我編的極端案例,是計劃自己排進校準流程要跑的資料。

## F4 「清單指紋」的定義是「整份清單檔內容的雜湊」,但判定者要抄進報告的 `prepared:` 值卻要求跟清單「開頭寫的」一致——這是自我指涉,而清單開頭列的欄位裡明確沒有指紋這一項

severity: blocker
blocking: 是 —— 這是 `record` 唯一的來源錨點(§3-5「來源錨點」段的四個必比對欄位之一),比對不合就整份報告拒收;定義本身若無法被一致地實現,等於每一份報告理論上都過不了這道錨點,是核心流程的可執行性缺口。

清單指紋的定義:

引句:「★清單指紋=那份清單檔內容的雜湊★(r2 正確性席:原稿有兩種讀法)」

清單開頭該記哪些欄位,規格逐一列出,四項,沒有指紋:

引句:「每份清單開頭記編排者、判定者模型、派工詞版本、當下頂端提交」

但判定者的報告要求 `prepared:` 這一行「也照抄」清單開頭的值,跟 `model:` 用的是同一種措辭(「照抄清單開頭寫的那個值」):

引句:「`model:`(照抄清單開頭寫的那個值)、`prepared:`(清單指紋,也照抄)」

問題:如果指紋真的等於「整份清單檔內容的雜湊」,而清單開頭又要把這個指紋值原樣寫出來給判定者抄——這個值本身是清單內容的一部分,把它寫進清單裡再拿「整份清單內容」去算雜湊,得到的數字就不等於已經寫進去的那個值(自我指涉,先有雞還是先有蛋)。要讓這件事自洽,唯一辦法是雜湊排除「prepared 那一行」本身再計算,但規格完全沒提這個排除規則,`prepare` 端怎麼算、`record` 端拿 `--prepared <清單檔>` 重新驗證時怎麼算,兩邊要用同一套排除規則才會對得上——這正是規格自己承認「原稿有兩種讀法」想修掉的模糊,但這次修法(把定義從「兩種讀法」收斂成「整份內容的雜湊」)反而製造了一個沒人會有機會意識到、要到寫測試 [S6] t_note_audit_record_provenance 時才會爆掉的自洽性缺口:兩個獨立實作者(claude 編排與 codex 編排各自的 `prepare`)如果對「整份內容」的理解不同(含不含 prepared 那行、以什麼編碼/換行方式算雜湊),彼此的清單永遠核對不上,而 §3-5 講明白了核對不上的後果是「那一份報告整份拒絕(輕重都不收,因為來源不明)」——這正好是要防的「重的判定被較輕的東西蓋掉」的反面極端:合法的重判定因為指紋算法沒講清楚而整份作廢,那一行倒回「沒有判定」的狀態,直接沖銷了做法第 0 節要保證的「①每一行新寫的筆記都有判定」。

## F5 spec 說「decisions 的決策編號與欄名用既有的 `decisions_items` 解析取得」,但 `decisions_items` 實際上不解析決策編號、也不解析欄名——這兩樣都得另外寫

severity: major
blocking: 是 —— 這句話出現在「所屬小標題」的定義裡,是內容編號(§2 四個組成之一)能不能算對的前提,S4 條款直接寫「decisions 的小標題應是決策編號加欄名」;如果援引的函式做不到聲稱的事,實作者要嘛照抄規格文字誤以為一次呼叫就夠、要嘛得自己再摸索出規格完全沒交代的邏輯(尤其是跨行值的歸屬),兩條路都會在寫測試 [S4] 時卡住。

引句:「決策編號與欄名用既有的 `decisions_items` 解析取得」

實際看 `decisions_items` 的回傳值(file: `scripts/lumos:14088`):函式回傳的是 `(block_start, block_end, [(item_start, item_end)], item_indent, sub_indent)`——也就是「decisions 區塊在哪幾行、裡面每一條決策項目各自佔第幾行到第幾行」,是純粹的行範圍定位,不解析任何欄位值,更沒有決策編號(`id: dN`)。全 repo 裡真正把 `id:` 這個欄位從某一條決策項目裡挖出來的地方(例如 `cmd_decision_supersede`),用的是另一段獨立的正則,跟 `decisions_items` 本身無關(file: `scripts/lumos:14883`):

```
m = re.match(rf"^{pad}id:\s*(d\d+)\s*$", fm[i])
```

要拿到欄名(某一行到底屬於 `content`/`context`/`why_chosen` 哪一欄)也不是 `decisions_items` 給的——那需要對 item 範圍內每一行再跑一次「哪一行是 `key:` 開頭、哪些後續行是它的延續(block scalar `|`/`>` 展開的多行值,續行沒有 `key:` 前綴)」這種欄位級解析,現成的是 `parse_decisions`(file: `scripts/lumos:12919`)吐出來的是欄位字典,但那個函式解出來的是「值」不是「哪一行屬於哪一欄」的行對應表,一樣不能直接拿來用。也就是說「所屬小標題」要對 decisions 裡每一行同時標出「這一條決策的編號」與「這一行屬於哪一欄」,需要至少再疊兩層解析(id 抽取 + 欄名歸屬,且要處理多行值的續行問題),而規格把這整段工作壓縮成一句「用既有的 `decisions_items` 解析取得」,讓人誤以為現成函式已經覆蓋。

## 總結
