## 做法 3——F2 在這一節

### F2 同一編排者的兩個併發 prepare,清單檔名的「待審集合指紋」定義不完整,可能讓先派出的判定被整份作廢

severity: minor
blocking: 否 —— 這條路徑的失效方向是 record 整份拒收(fail-closed),不會讓任何一行「該擋的」被放行,只會讓判定者的一次執行被白白浪費、要重跑;不符合本輪「疏忽情境會放過該擋的」定義,所以標 minor 而非 major/blocker。

引句:「兩家 prepare 互蓋 → 檔名含編排者」

本篇自己在〈前身 r3 發現怎麼處理〉裡把「清單檔名含編排者」列成解法,但那解的是**跨編排者**互蓋(claude 派工詞跟 codex 派工詞撞名)。清單檔名同時也含「待審集合指紋」(見下段引句),但本篇從未定義這個指紋的輸入範圍是否包含「當下頂端提交」——而清單**內容**必須包含頂端提交(下段引句),兩者若不是同一顆雜湊,就會出現以下情境:

引句:「檔名 `.lumos/note-audit/<待審集合指紋>-<編排者>-<序號>.md`」

引句:「★清單指紋=那份清單檔內容的雜湊★(r2 正確性席:原稿有兩種讀法)」

可重現的併發序列:
1. 兩個 claude 會談(同編排者)在同一分支上,各自對同一個 `--diff <範圍>` 跑 `prepare`。
2. 會談 A 在提交 T1 起跑;會談 B 在 T1 之後、只多了一個不動 vault 的程式提交 T2(例如另一支平行改動的合併)才起跑。兩邊「範圍裡新寫、終點還在的筆記行」算出來的待審集合(路徑+行文字+區塊+小標題)完全相同,因為 T2 沒有碰任何筆記——若「待審集合指紋」只雜湊這批內容(不含頂端提交),兩邊算出的檔名前綴相同、序號也相同(切分演算法是同一份確定性演算法),於是兩邊都要寫 `.lumos/note-audit/<同一個指紋>-claude-1.md`。
3. 清單「開頭記…當下頂端提交」(本篇做法 3.1)這一項在 A、B 之間必然不同(T1 對 T2),所以兩份清單**內容**不同、「清單指紋」(整份檔案內容的雜湊,見上引句)也不同,但**路徑相同**。
4. `_write_lf`(scripts/lumos:14146)是原子換名寫,不是失敗就是整份成功,不會半殘,但「後寫的贏」——B 的內容會覆蓋 A 在磁碟上的檔案。
5. 會談 A 已經把 T1 版本的清單內容(含它自己的清單指紋)發給判定者;判定者的報告會在開頭原樣抄「prepared: <A 清單指紋>」。
6. A 執行 `record --prepared <該路徑>` 時,做法 3.5 要求「`prepared:` 要等於那份清單的指紋」——但這時候重新雜湊磁碟上那份檔案,拿到的是**B 的**清單指紋(因為路徑上的檔案已經被 B 蓋掉),兩者不等,A 的整份報告依規則「不合就那一份報告整份拒絕(輕重都不收,因為來源不明)」被丟棄。

這個情境不會讓不該過的內容放行(失效方向正確、安全),但它是本篇〈實務隱患〉「資源併發」一節完全沒討論到的一種併發失效模式——那一節只講了「不同編排者」與「同編排者不同序號檔名各自獨立」兩種安全情境:

引句:「兩個會談同時 prepare → 清單檔名含待審指紋、編排者與序號,原子寫入」

這句話沒有講清楚「待審指紋」在**同編排者、同分支、待審內容恰好相同、但頂端提交不同**這個具體場景下是否仍能保證檔名唯一;若指紋定義成不含頂端提交(目前文字最自然的讀法),上面 5 步的覆蓋與整份拒收就會真實發生。修法:讓「待審集合指紋」的輸入額外納入頂端提交(或直接讓檔名跟「清單指紋」用同一顆雜湊,不要兩個概念各自留一個未定義的雜湊輸入),使同編排者、頂端不同的兩次 prepare 必然落在不同檔名。

## 做法 3——F1 在這一節(9. 消費專案的 CI 與 doctor)

### F1 doctor 給消費專案的 CI 貼法沒有把 `github.event.before` 的全零 SHA 換成空樹,note-audit check 在「新分支首推」這個常見時序下會靜默 fail-open,放過整批新增筆記行

severity: blocker
blocking: 是 —— 這正是「收窄成防疏忽」後仍必須守住的三個機械保證之一(「每一行新寫的筆記都有判定」)被完全繞過的情境,而且是靠推送當下最常見的時序(新分支首推)觸發,不需要任何人存心繞過。

引句:「在它後面加一行 `python3 scripts/lumos note-audit check --diff "${{ github.event.before }}..${{ github.sha }}"`」

這是本篇給 doctor 要印給消費專案貼進 CI 的**逐字指令**。問題在於:`github.event.before` 在「這是這個 ref 第一次被推(新分支)」時,GitHub 給的值是全零 40 字元 SHA(`0000000000000000000000000000000000000000`),不是任何真實提交——這正是 CI 併發/時序審查該覆蓋的「最壞時序」之一:新分支的第一次推送,往往一次帶進整篇計劃草稿(本篇〈誠實界線〉自己也講「計劃收尾時可能上千行」)。

程式現況證實:`lumos` 只認固定常數 `_EMPTY_TREE_SHA = "4b825dc642cb6eb9a060e54bf8d69288fbee4904"`(file: `scripts/lumos:29832`)當作「空樹」,從不特判 git 的全零 SHA。第一層 `note-shape` 的 CLI 入口在算出 `base`/`tip` 之後:

file: `scripts/lumos:23978`
file: `scripts/lumos:23979`

```
base = a if a == _EMPTY_TREE_SHA else _lens_full_sha(root, a)
...
if tip is None or base is None:
    print(f"筆記形狀擋:範圍 {diff_range} 在本機找不到,跳過(fail-open)", file=sys.stderr)
    return 0
```

`_lens_full_sha`(file: `scripts/lumos:28101`)對全零 SHA 跑 `git rev-parse --verify -q "<全零>^{commit}"`,這個物件在任何 repo 裡都不存在,回傳 `None`——於是 `base` 是 `None`,整個判斷 fail-open、印一行不起眼的 stderr、rc=0(放行,不算違規、不落治理帳)。我已在乾淨的臨時 repo 裡實測驗證這條路徑:

```
$ python3 scripts/lumos note-shape --diff "0000000000000000000000000000000000000000..<sha>" --repo <repo>
筆記形狀擋:範圍 0000000000000000000000000000000000000000..<sha> 在本機找不到,跳過(fail-open)
rc=0
```
(對照筆記裡有一行明確可推得出程式碼的 `FACT:`,理應被擋而沒有被擋。)

本篇做法第 1 節明講第二層要「借第一層已上線的算法」、「抽出一支共用函式」,PRIOR-ART 也寫「哪些筆記行是這次新寫的」借第一層算法——也就是說 note-audit 的範圍解析會走同一套 `_lens_range_ok`/`_lens_full_sha`/`_EMPTY_TREE_SHA` 機制,除非本篇明確要求另外處理全零 SHA,否則會原樣繼承這個 fail-open 分支。本篇第 9 節給消費專案的貼法完全沒有这個保護,也沒有像第一層自己 doctor 給的貼法那樣至少留一句提醒(見下段);而**工具鏈自己的** `.github/workflows/ci.yml` 對它現有的兩個姊妹閘(code-loop、note-shape)都手動做了這個保護:

file: `.github/workflows/ci.yml:109`
file: `.github/workflows/ci.yml:110`
file: `.github/workflows/ci.yml:111`

```
EMPTY=4b825dc642cb6eb9a060e54bf8d69288fbee4904
case "$BEFORE" in 0000000000000000000000000000000000000000|"") BEFORE="$EMPTY";; esac
git cat-file -e "$BEFORE^{commit}" 2>/dev/null || BEFORE="$EMPTY"
```

本篇第 9 節既沒有要求 note-audit 在自家 `ci.yml` 加這段防護、也沒有要求 doctor 給消費專案的貼法加這段防護(連第一層 doctor 貼法裡至少有的一句提示文字——「新分支首推前一版全零時改從空樹給,lumos 會自己截到上線點」——都沒有一併抄過來,單看第 9 節這行引句,連一句人工提醒都不存在)。結果是:任何照 doctor 提示原樣貼上這行 CI 步驟的消費專案,只要遇到「建立新分支並第一次推送」(功能分支開發是常態,不是罕見事件),note-audit check 就會對那整批新增內容 fail-open 放行,不落治理帳(因為 `_gate_event_or_warn` 只在偵測到違規或明確跳過路徑才呼叫,不在這種「範圍算不出來」的早退路徑上),事後只能靠 doctor 的「已推上遠端卻沒被涵蓋的新增筆記行」掃描(本篇同一節)補抓——但那時內容已經在遠端,而且那支掃描本身也只看遠端最新 200 個提交,是否會漏掉更早的新分支推送不在本篇範圍內交代清楚。

修法方向(供裁定參考,不代審):doctor 給的貼法比照 `ci.yml` 現有兩個姊妹閘,在呼叫 `note-audit check` 之前加上「全零 SHA / 不存在的提交 → 換成 `_EMPTY_TREE_SHA`」的 shell 判斷,並把這段判斷也補進第一層 `note-shape` 現有的 doctor 貼法(那支目前只有一句人工提醒,沒有機械保護,属于本篇引用的既有現況,但既然本篇在同一位置新增一行,是修正這個既有缺口的最低成本時機)。
