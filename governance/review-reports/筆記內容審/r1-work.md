# 筆記內容審_計劃

白話:筆記只准寫程式碼推不出來的東西。第一層([[Projects/筆記形狀擋_計劃]],已上線)在提交時擋兩種形狀固定的寫法;這一篇是第二層:推送前,派一個沒有脈絡、會去讀程式碼的審查員(下稱「判定者」),逐行判這次新寫的筆記內容是不是程式碼推得出來,判是的要刪掉才推得上去。

依據:[[Issues/筆記把程式現況寫進脈絡而漂移_rtb實測回饋]] 的 d1–d6、d8(Enzo 2026-09-27 裁)。

**★這篇是重寫稿★**:前身是 [[Projects/筆記不存程式碼推得出的事_計劃]] 的第二層部分,設計審三輪(r1 38 條、r2 32 條、r3 35 條)後,r3 查出核心設計有洞——通過紀錄重跑一次判定者就能洗掉、計劃轉 done 的整篇重審會空轉、「直接借第一層」借不動、記錄那一步不知道是哪一家判的——Enzo 2026-09-27 裁「重寫、開新一輪審查」。r3 的 34 條折進本篇(對照見文末〈前身 r3 發現怎麼處理〉),1 條駁回。

PRIOR-ART: 借本 repo 四個既有形狀,借法寫死:①「哪些筆記行是這次新寫的」借第一層已上線的算法,但先把它從第一層內部抽成兩層共用的函式(見〈做法〉第 1 節);②判定結果存成「一次判定一個檔」、進版本控制,照關係層連鎖帳本 `governance/rel-cascade/<id>.jsonl` 的做法(那支的註解寫明刻意用可追蹤的逐筆檔);不照新增告警閘放行檔的「一個檔、讀改寫上鎖」,因為那個檔很少寫,這個幾乎每次推送都要寫,兩條分支各自改同一個檔,合併時一定衝突;③推送前查有沒有紀錄、`--no-verify` 硬推時 CI 標紅、帶理由的 skip 出口,照代碼審留痕閘([[Systems/pitfalls-code-loop]]);④設定從被檢查的版本讀、不是 block 時 doctor 每次印一行,照第一層 `note_shape.gate`。判定者照無脈絡審查席的派法(乾淨 agent、只給原始問題不給結論)。世界的做法:文件與程式碼同步多半走「從程式碼生成文件」(見 [[Systems/外部對照-code衍生wiki]]),它讓文件免疫漂移但裝不下程式碼沒有的脈絡——本案反過來,讓筆記只裝那一種。不採用新依賴。
RETIRE-IF: 上線兩個月後任一成立就撤掉或重想:①作者申訴被第二席認同的比例超過三成(判定者不可靠);②對上線後新增的筆記行隨機抽樣,仍有一成以上是程式碼推得出來的(擋不住);③新增的脈絡行月量掉到上線前的三分之一以下(大家乾脆不寫筆記了,擋掉的比救下的多)。
REVISIT:2026-11-27 跑上面三個量;順便在 rtb 重做一次跟 2026-09-27 同方法的漂移抽樣,拿 41% 當基準比;同一天看判定檔目錄的檔數與大小。

## 判定者能不能用:小實驗(2026-09-27)

把 rtb 的 68 句打亂、拿掉標題旁的提示,給兩個沒有脈絡的審查員,各自讀 rtb 程式碼判「程式碼推得出 / 脈絡 / 一半一半」。其中 55 句是稽核逐句對過程式碼的現況句(答案應該是推得出或一半一半),13 句是決策欄位裡的「為什麼選這個」(答案應該多半是脈絡)。卷證在 `governance/audits/2026-09-27-rtb-notes/judge-experiment/`。

| 審查員 | 55 句現況句抓到 | 13 句理由誤判成純程式碼 | 花的時間 |
|---|---|---|---|
| opus | 55(53 推得出、2 一半一半) | 0(9 脈絡、4 一半一半) | 約 4.4 分鐘 |
| sonnet | 54(漏 1 句:在講已刪掉的程式,它判成歷史) | 3 | 約 9.7 分鐘 |

- 兩席在「要不要擋」上 68 句同意 64 句。判成一半一半的理由句我逐句看過,裡面確實夾著程式現況(例如「某函式在第幾階段加的、路由和評估都靠它」)。
- **誠實界線**:正例是稽核挑出來的現況句,比真實新增行好判;反例只有 13 句;對照答案由我一人訂。真正難的是「一句話裡理由跟現況混在一起」,這類樣本太少。所以 claude 編排時判定者用 opus(Codex 編排時用同一家的審查席模型,見〈做法〉第 3 節第 2 點,那一家的準度要另外校準)、派工詞要明寫「描述已刪掉的程式、用現在式寫的,也算推得出」,而上線後的申訴率是第一個要看的數。
- 句型比對做不到這件事:同日對近一個月 25,282 行新增筆記跑「目前沒有/只有 N 種」句型,抽樣約三分之一是真的,見 Issue〈擋什麼的初步實測〉。

## 做法

### 1. 哪些行要審:先把第一層的「新寫的行」抽成共用函式

第一層現在的樣子(以程式碼為準,查法:讀 `scripts/lumos` 的 `_note_shape_eval`):範圍函式 `_ns_range_added` 只回「範圍裡每個提交加過的行文字」的集合,不帶行號、後來刪掉的也還在;「終點版本裡還在、落在哪一塊、第幾行」是 `_note_shape_eval` 在自己的迴圈裡邊查規則邊算的。所以第二層不能只呼叫那支範圍函式(前身 r3 三席實測)。

- **抽出一支共用函式**「範圍裡新寫、而且終點版本還在的筆記行」,回傳每一行的(git 原樣路徑、行號、行文字、所在區塊);第一層改成呼叫它,第二層也呼叫它。區塊判定沿用第一層那支(正文、summary、decisions 文字子欄算;結構欄與開頭欄位其他欄不算)。第一層的所有既有測試不改一字要照綠——這是抽出來沒改壞的證據。
- **命名與家**:抽出來的共用函式與區塊判定改成兩層共用的名字(不再掛在第一層私有的前綴下,前身 r3 架構對齊席),說明寫進 [[Systems/筆記內容閘]](它本來就管「哪些筆記行算新寫的」);上線點與範圍起點那兩支函式的家照舊是 [[Systems/每支檔有家]]。第二層自己的程式開新家 `Systems/筆記內容審`。
- **「寫的時候這道檢查在不在」要能換掛鉤**:目前有三處寫死看提交前掛鉤 `scripts/hooks/pre-commit`——上線點函式、範圍起點截斷函式、範圍函式裡逐提交判上線的那一段(前身 r3 邊界席抓到第三處)。三處都加「看哪支掛鉤」的參數,預設維持提交前掛鉤;第二層傳推送前掛鉤 `scripts/hooks/pre-push` 與自己的標記 `note-audit check`。漏改任何一處,第二層會永遠收不到待審行、而且不報錯,所以另有一條條款專門驗這件事。
- **計劃在範圍內被改成 done**(比對改名前的舊路徑狀態):那篇整篇——正文、summary、decisions 文字子欄——都進「完成審」,不只新增行(d2 的「改到」、d4 的執行方式;前身 r3 外家席:原本只含正文,漏了最容易過期的摘要)。
- 只在推送前與 CI 跑,提交前不跑(要派判定者,提交前等不起)。筆記讀不成 UTF-8:照第一層列成錯誤、擋下並講是哪支檔。

### 2. 內容編號與判定檔

- **內容編號**=(NFC 路徑、所在區塊、去頭尾空白的行文字)的短雜湊。含區塊:同一篇裡 summary 跟正文剛好有一句一樣的話,不共用判定(前身 r3 邊界席)。不含行號:同一句話在同一塊裡移動位置不用重判。同一塊裡一字不差出現兩次的,共用一個編號,清單列出每一處。
- **完成審另用一種編號**:同上三樣再加「完成審」標記。進行中寫的計劃內容當時多半判成脈絡(那時確實是意圖),轉 done 後要重判,所以進行中的判定不涵蓋完成審(前身 r3 正確性席:不這樣分,完成審會被「已涵蓋」整個吃光)。
- **判定檔**:每次 record 或 skip 寫一個新檔 governance/note-verdicts/<時間>-<亂數>.json(新資料夾),內容是這一批的來源(席名、編排者、模型、派工詞版本、時間、是不是申訴、申訴的是哪一批)與每個內容編號的判定(脈絡/推得出/一半一半/略過)。檔名唯一,兩個會談同時寫、兩條分支各自寫,都不會互相蓋或合併衝突,所以不用鎖;寫法照連鎖帳本那支(整檔一次寫、拒絕捷徑)。
- **判定怎麼算**:同一個內容編號在所有判定檔裡,★取最重的那次非申訴判定★(推得出 > 一半一半 > 脈絡);★只有申訴批次能把它調輕★,而且申訴批次的席名要跟被申訴那批不同。所以重跑一次判定者拿到較輕的結果,不會蓋掉先前的推得出(前身 r3 正確性席:原設計只記脈絡,重擲就洗掉了)。略過(skip)單獨算:有略過就算涵蓋,但判定檔標明是略過。
- **涵蓋**=那一行的內容編號最後算出來是「脈絡」或「略過」。推得出、一半一半都不涵蓋——那一行只能消失(一半一半刪掉推得出的子句後是新內容、新編號,要再判)。
- 治理帳只記事件與筆數(判了幾行、各類幾行、申訴幾筆),不列編號,所以每筆都很短(前身 r3 接手席:列上千個編號的長行在同時寫入時可能被切開、連帶弄壞別的閘的紀錄)。

### 3. 指令(`lumos note-audit`)

1. **`prepare --diff <範圍> --orchestrator claude|codex`**(編排者那一家必填,照 `loop next` 的既有規矩):算出第 1 點那批行,扣掉被判定檔涵蓋的——★prepare 讀工作目錄裡的判定檔★(剛 record、還沒提交的也算,免得重派;check 才只認已提交的)。剩下的是待審;空的就說「沒有待審的筆記行」、rc0、不產生檔。清單每行附內容編號、區塊、行號,以及★它前後各兩行的上下文★(一句話拆成兩行寫時,判定者看得到整句;前身 r3 外家席)。清單連同派工詞原子寫入 `.lumos/note-audit/<待審集合指紋>-<編排者>.md`(檔名含編排者,兩家對同一批 prepare 不會互蓋,前身 r3 外家席);清單檔開頭記編排者、判定者模型、派工詞版本。★那個目錄第一次建立時,在裡面放一支只寫 `*` 的 `.gitignore`★——消費專案的根 `.gitignore` 沒有工具會去改(前身 r3 併發席查證 init 與 update 都不碰它),這樣不用動它;順手清掉 14 天前的舊清單。
2. **派判定者**:跟編排者同一家——claude 派 opus、codex 派 Codex 那邊審查席的既有模型;不派外家席。派工詞由 prepare 產生:`governance/audits/2026-09-27-rtb-notes/judge-experiment/judge_prompt.md` 的三類分類定義逐字沿用,專案路徑與技術棧換成被審 repo 的(那支檔開頭寫死 rtb 的路徑與「Python」),再加五句:①用現在式描述已刪掉的程式,也算推得出;②一行有多個子句時逐子句判,一半一半要列出哪幾個子句推得出;③推得出的部分附證據——`file:line`,或 `search: <字串> in <repo 內相對路徑> => <命中數>`(「沒有 X」寫 `=> 0`);④用文字描述程式某一行位置也算推得出;⑤一句話跨好幾行時,看上下文把整句合起來判,每一行都標整句的分類。報告開頭三行固定:`seat:`、`provider:`(只准寫 `claude` 或 `codex`,跟 `--orchestrator` 同一套值)、`model:`;每行判定寫「內容編號 | 分類 | 證據 | 一句理由」。每批不超過 150 行,多了切批平行派。派工詞有版本號,改一個字就要升版並重跑小實驗(條款 S14)。
3. **作者處理**:推得出的整行刪;一半一半刪掉推得出的子句;「引句:」行被判就整句刪、不改字。`decisions` 裡被判的用新的 `lumos decision-amend` 改(第 4 點)。**申訴**:另派一席(席名不同)單判那一行、不給它前一席的結論,用 `record --dispute` 記。★申訴成立只改變要做的事★:降成一半一半,那行仍要消失;降成脈絡才准原樣留。
4. **`decision-amend <節點> <決策編號> …`**:只准改還沒推上去的決策。判法:對每一個遠端追蹤參照,先用改名偵測找出這篇在那個參照上的舊路徑(本機改過名也找得到,前身 r3 兩席),讀那個版本:沒有這個決策編號 → 可改;有、內容一樣 → 拒絕並指向翻案指令;有、內容不一樣 → 拒絕並講「遠端同篇已有同編號、內容不同,這是兩條分支撞號,先把你的決策改號」(前身 r3 邊界席)。沒有任何遠端就都能改。遠端追蹤參照只在 fetch 或 push 時更新,所以同時印出上次 fetch 距今多久;超過一天就提醒先 fetch 再改。
5. **`record --diff <範圍> --prepared <清單檔> --report <報告> [--report …] [--dispute <報告> …]`**:
   - ★來源錨點★:讀 `--prepared` 那份清單檔開頭的編排者、模型、派工詞版本;每份報告開頭三行都要齊,`provider:` 要等於清單檔的編排者、`model:` 要等於清單檔記的判定者模型,否則整份拒絕(前身 r3 兩席:原設計 record 根本不知道 prepare 時是哪一家)。
   - 重算待審集合;報告裡不在目前待審集合的編號忽略並列出來(多半是已刪掉的行)。
   - 同一次呼叫裡兩份非申訴報告對同一編號判得不同 → 拒絕(要走申訴)。★跨次也一樣★:判定檔裡已經有這個編號較重的非申訴判定,這次較輕的非申訴判定一律拒絕並指向申訴(第 2 點「取最重」的寫入端)。
   - 申訴報告的席名要跟被申訴那批不同,而且要指明申訴的是哪一個判定檔。
   - ★證據一律關在 repo 裡★:`file:line` 走既有的 `_validate_repo_ref`(它本來就拒絕絕對路徑與 `..`);`search:` 的路徑要是 repo 內相對路徑、解析後仍在 repo 裡(不跟著捷徑跑出去)、跳過 .git、最多掃 5,000 支檔或 50 MB,超過就判這條證據無效;字串至少 4 個字;命中數要跟報告寫的一致(前身 r3 外家席:原設計可以讀 repo 外的檔、可以遞迴掃整台機器)。
   - 任一不過就整份拒絕、不寫檔、rc1,列出原因。都過就寫一個判定檔,印出「還沒被涵蓋的行」(判了推得出但還在的、沒人判的),並提醒要把判定檔提交。
6. **`check --diff <範圍>`**:推送前與 CI 另開一支平行呼叫(跟 `home check`、`note-shape --diff` 並排)。重算那批行與完成審;★判定檔一律從被推送的那個頂端提交裡讀★(不讀工作目錄;照第一層設定從被檢查版本讀的做法)。每一行都被涵蓋就放行;否則 rc1,列出沒被涵蓋的行(最多 20 行,其餘給筆數)並印 prepare 指令;涵蓋它們的判定檔只在工作目錄、還沒提交時,另外印提交指令。
7. **出口與開關**:
   - `lumos note-audit skip --diff <範圍> --note "<理由至少 4 個字>"`:把當下待審的行寫成一個「略過」判定檔(帶理由),治理帳記 `skipped`;跟判定一樣逐行涵蓋、要提交才算。
   - 專案開關 `.lumos/config.json` 的 `note_audit.gate`:block(預設)/ warn / off,★從被檢查的版本讀★,不是 block 時 doctor 每次印一行。事件種類照第一層:warn 時有不涵蓋的行只印不擋、記 `warned`;off 時直接放行、不寫帳;環境變數 `LUMOS_SKIP_NOTE_AUDIT=1` 單次跳過記 `skipped-env`(只管本機,CI 照查)。這三種★都不寫判定檔、不算涵蓋★,改回 block 後那些行照樣要判(前身 r3 正確性席:原設計三種情況都叫 skipped,改回 block 後會被當成涵蓋)。
   - 模型限流、服務中斷時走 skip。
8. **消費專案的 CI 與 doctor**:`lumos update` 不會動各專案的 CI 設定檔,所以 doctor 檢查專案 CI 有沒有呼叫 `note-audit check`,沒有就印一行並給要貼的那一步(跟第一層那一步並排)。另外 doctor 事後掃「已推上遠端卻沒被涵蓋的新增筆記行」——★判定檔從遠端頂端提交讀★(不讀工作目錄;前身 r3 正確性席),照第一層只看遠端最新 200 個提交、不在 `--ci` 路徑跑。

### 4. 上線前校準與接線

小實驗餵的是稽核員切好的單句,正式跑的是原始整行加上下文。所以接線之前,★兩家都要各做一次、都達標才接線★(推送前掛鉤全 repo 只有一份,分不出這次推送是哪一家在編排;只接一家,另一家的會談照樣會被擋、只能用沒校準的判定者——前身 r3 正確性席):用 prepare 對 rtb 近一週真實的新增行、再加一份 300 行以上的已完成計劃整篇,兩席各自獨立判,編排者抽 30 行人工對照。兩席「要不要擋」一致率低於 85%,或人工對照有超過 2 行純理由被判推得出,就不接線、改派工詞重來。換模型、改派工詞都要重做。

### 5. 規範文字與路由

- 紀律範本〈寫筆記時〉那張表的 FACT/FLOW/DEP 列第一層已改好;第二層在同一段補一句:推送前會派判定者逐行判新寫的筆記,判成程式碼推得出來的要刪,不服可以申訴、真的來不及用 skip(會留帳)。
- ★紀律範本的「遇到這些情境就調用對應 skill」表加一列★:「推送被 note-audit 擋下」→ `lumos-project-notes`(前身 r3 接手席:這串流程跟代碼審同量級,只埋在 skill 內文一行找不到)。skill 裡新開一個子檔,講完整一串:prepare → 派判定者(claude 與 codex 各怎麼派)→ 刪或申訴 → record → 提交判定檔 → 再推。
- 各專案各自跑 `lumos update` 拉新版。

## 回退

照這個順序,反過來會卡住別人推送:
1. **先改 CI**:把工具鏈自己 `.github/workflows/ci.yml` 裡 note-audit check 那一步拿掉(這支檔不在 `lumos update` 的同步清單裡,要手改)。★note-audit 指令改成只印「已撤除」並回 0、永久保留★(照第一層:消費專案自己貼的 CI 工具鏈看不到)。
2. 消費專案不用等中心:各自把 `note_audit.gate` 設成 off 就停。
3. 拿掉推送前掛鉤裡的呼叫與 doctor 那兩段;decision-amend 可以留(它不擋人);各專案 `lumos update` 拉回。
4. 共用函式的抽取不用退:第一層照用,行為不變(S1)。
5. governance/note-verdicts/ 裡的判定檔留著,不會被拿去擋任何東西;要清就整個資料夾刪掉。

## 實務隱患

- 守衛面:新的擋人機制,誤擋會讓人習慣繞過——所以有申訴、skip 與專案開關,關掉或跳過都寫帳、doctor 持續印,全部進 RETIRE-IF 的量。反方向(放過)的已知路子:刻意把一句話拆成很多行並讓每一行單獨看都像脈絡——靠上下文與第⑤句擋大部分,擋不住的靠 RETIRE-IF ② 抽樣(見誠實界線)。
- 對外送出:筆記行、上下文與被讀的程式碼會送到判定者那一家模型;限定跟編排會談同一家、不派外家席,不會多出一家供應商。
- 資源併發:兩個會談同時 prepare → 清單檔名含待審指紋與編排者、原子寫入;同時 record → 各寫各的唯一檔名判定檔,不共用檔、不用鎖;兩條分支各自寫判定檔 → 檔名不同,合併不衝突;治理帳只記短事件(沿用既有寫入器,[[Issues/治理帳多個寫入者都沒上鎖]] 的風險照舊、沒有變大);審查中途斷掉 → 沒有判定檔就是沒涵蓋,重跑 prepare 得到同一檔。
- 可用性:模型限流或服務中斷時走 skip(留理由、進帳)。
- 容量:每次 record 一個檔;本 repo 近一個月 473 個提交,估一個月一兩百個小檔、合計幾 MB 以內。REVISIT 那天看實際檔數與大小,太多再做合併壓縮(把舊檔併成一個、保留每個編號最重的判定)。
- 已排除:不可逆:擋在推送前,提交都還在本機;decision-amend 只改還沒推上去的決策;拿掉閘就恢復原狀
- 已排除:金流:不碰任何付款或計費流程

## 誠實界線

- 判定者的準度只驗過一次、68 句、反例 13 句,而且是切好的單句;所以接線前兩家都要照〈上線前校準〉再驗,上線頭兩週逐筆看申訴。
- 兩席在三類判定上 68 句有 9 句不一致,一半以上是「推得出」對「一半一半」——申訴規則是為這種雜訊設的;「取最重、只有申訴能調輕」讓重擲沒用,但申訴本身仍給作者多一次機會,申訴成立率是 RETIRE-IF ① 的量。
- 逐行判有天生的縫:刻意把一句推得出的話拆成很多行、每行單獨看都像脈絡,上下文擋得住大部分,擋不住存心的。這靠 RETIRE-IF ② 的每月抽樣抓。
- 判定只綁那一行的文字。當初判成脈絡的話,之後程式碼改了變成推得出,不會觸發重審(d2 不回頭清);計劃轉 done 時會整篇重審一次。
- 本機與 CI 的範圍可能不同:本機新分支的起點是「不在任何遠端分支上的最早提交」,CI 從空樹截到上線點、只排除主線。一個分支從另一條還沒合進主線的分支開出來時,CI 可能看到本機沒看到的行,而涵蓋它們的判定檔在另一條分支上——CI 紅、看得見,把那條分支合進來或對那些行再 record 一次就好。不會放過,只會多擋。
- 沒有接 CI 的消費專案,`--no-verify` 推上去當下擋不住;doctor 事後會列出來,但那時已經在遠端了。
- 花費與等待:本 repo 幾乎每次推送都有新增筆記行,所以幾乎每次推送都要派判定者;一次要判幾十到幾百行,計劃轉 done 時可能上千行。Enzo 已表明不在意額度(d6),但推送前要多等判定者跑完。
