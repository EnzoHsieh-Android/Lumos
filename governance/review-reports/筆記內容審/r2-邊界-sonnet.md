問題:這句只講「三個」,沒講「至少三個」或「四個(巢狀外層)」。本庫對「巢狀圍欄要用四個反引號包三個反引號」是有明確記錄的踩坑教訓,`scripts/lumos:7154-7163` 的註解寫:「兩種都讓『把樣板原樣貼進圍欄裡』被算成真的跑過前掃…實測兩種形狀兩邊答案相反:①外層四個反引號、內層三個反引號 ②波浪號圍欄」。若第二層的「圍欄記號行排除」照字面只認恰好三個反引號,一篇筆記裡用四個反引號當外層圍欄(本庫既有的合法寫法)時,那個外層 ```` 記號行不會被判定為「圍欄記號」,會被當成一般內容行送進判定者當作有主張的句子去判——這正是這條排除規則自己說要避免的「共用編號會互相拖累」(不同篇的 ```` 行字面相同,若沒被排除,會共用同一個內容編號)。

## F3 summary 與 decisions 裡「小標題=欄名」沒有具體映射,decisions 一條決策其實有三個文字子欄

spec 位置:〈做法〉第 2 節「內容編號與判定檔」第一條(同上引句)。

問題:「summary 與 decisions 裡是欄名」這句話,在兩個區塊裡的意思其實完全不同,spec 沒有分開講:

- **decisions**:結構完全不同,一條決策底下真的有多個 YAML 鍵。實測 `docs/lumos-toolchain-knowledge/Projects/接手視圖_計劃.md:27-32` 的真實決策條目:`content:`(決策本文)、`id:`、`context:`(脈絡)、`why_chosen:`(為什麼選這個)、`decided:`、`valid:`。依 `_NS_STRUCT_KEY_RE`(`scripts/lumos:23459`:`^\s*(?:-\s+)?(id|decided|valid|superseded_by|ended|decided_by|replaces)\s*:`),`content`、`context`、`why_chosen` 都**不是**結構鍵,三者都會落在 `_ns_regions`(`scripts/lumos:23500`)判給的 `decisions` 區塊裡、都算「decisions 文字子欄」。也就是說一條決策底下其實有三個語意完全不同的文字子欄(決策本文/脈絡/選擇理由),spec 卻只講「decisions 裡是欄名」一句話,沒說這三個 YAML 鍵是不是各自一個「小標題」、多行的區塊字面量(如 `content: |-` 續行)要不要重新往上找欄名、以及萬一某條決策沒有 `context`/`why_chosen` 這種選填欄時怎麼算。

## F5 `decision-amend` 的「上次 fetch」量測機制完全未定義,全新 clone 沒有 FETCH_HEAD

severity: major
blocking: 是 —— S12(`t_decision_amend_fresh_remote_rename_collision`)要求「應在上次 fetch 超過 10 分鐘時拒絕」,但沒定義「上次 fetch」量測的檔案/機制,而全 repo 唯一常見的量測方式(`FETCH_HEAD` mtime)在全新 clone 上不存在,implementer 會得到兩種互不相容的行為(永遠拒絕,或視同剛 fetch 過)。

spec 位置:〈做法〉第 3 節第 4 點「decision-amend」。

引句:「★先要求遠端追蹤參照夠新★:上次 fetch 超過 10 分鐘就拒絕並印 fetch 指令」

問題:通篇 `scripts/lumos` 沒有任何既有的「量測上次 fetch 距今多久」的工具函式(用 `grep -n "FETCH_HEAD\|fetch.*距今\|_fetch_"` 只命中一支跟 git 完全無關的 `_fetch_text`,是抓 CDN JS 用的),所以這是全新邏輯,spec 卻沒講依據哪個檔案或哪個 git 物件的時間戳。若依業界慣例量測 `.git/FETCH_HEAD` 的 mtime,實測(可重現指令如下)`git clone` 本身根本不會建立 `FETCH_HEAD`:
```
git init -q src && cd src && git -c user.email=a@b.c -c user.name=t commit --allow-empty -qm init
cd .. && git clone -q src clone && ls clone/.git/FETCH_HEAD   # ls: No such file or directory
```
遠端追蹤參照(`refs/remotes/origin/main`)倒是有 reflog,訊息是 `clone: from …`,但那是「複製」事件不是「fetch」事件,語意上算不算「上次 fetch」spec 沒講。結果是:一個剛 `git clone` 完、從未手動 `git fetch` 過的工作目錄,decision-amend 的行為完全取決於實作者挑哪個量測依據——挑 `FETCH_HEAD`(不存在)就會被解讀成「上次 fetch 距今無限久」而永遠拒絕(哪怕 clone 這一刻遠端資料明明是全新的);挑 reflog 的 clone 事件時間就會被視為剛 fetch 過而放行。這正是本輪要求核對的邊界「decision-amend 在沒有任何 fetch 紀錄的新 clone」,目前沒有唯一答案。

## 逐項邊界核對清單(本輪指定要核的十項)

- 沒有任何小標題的筆記:每篇筆記的 body 第一行必為 `# 標題`(以程式碼為準,查法:`grep -c '^#' docs/lumos-toolchain-knowledge/**/*.md` 全庫 568 篇皆有至少一個 `#` 行;`lumos new` 的模板 `scripts/lumos:16668` 固定寫 `f"# {target}\n\n" + block`),所以字面上「往上找最近一行 `#`」在 body 區永遠找得到 H1;但 spec 沒說 H1 本身算不算「小標題」(跟 `##` 子節是否同一層級),H1 與第一個 `##` 之間的內容(例如本篇自己的 PRIOR-ART/RETIRE-IF/REVISIT 三行)歸屬哪個小標題沒有明講——併入 F3 的定義缺口一併處理,不單開一條。
- 小標題在圍欄裡:見 F1。
- summary 與 decisions 的「欄名」怎麼算:見 F3。
- 清單記號後只有空白 / 表格分隔行夾文字:見 F8;表格分隔行夾文字(例如 `| --- | 文字 | --- |`)因為含有 `|,-,:,空白` 以外的字元,依 spec 定義「只有 `|`、`-`、`:` 與空白」不會被排除,會照常送審——方向是多審不漏審,已讀,無 finding。
- 四個反引號的圍欄:見 F2。
- 內容編號 16 個十六進位字的撞號:16 進位 16 字元 = 64 bits,生日界限下要約 2^32(超過 40 億)個相異內容編號才有五成碰撞機率,本庫全庫筆記數(568 篇)與可預期的年新增行數(spec 自己估一個月數百個判定檔)遠遠不到這個量級,已讀,無 finding。
- 判定檔資料夾上千個檔時 check 的讀法:見 F6。

- decision-amend 在沒有任何 fetch 紀錄的新 clone:見 F5。
- 完成審遇到一篇上千行的計劃:見 F4。
- record 報告裡同一行被判兩次:「判定怎麼算」的三步算法(做法第 2 節)是對「所有種類=判定的檔裡對它的判定」取最重,沒有區分這些判定來自同一份報告還是不同報告,所以同一份報告內對同一內容編號出現兩筆(甚至互相矛盾的)判定,會自然落入同一套「取最重」邏輯,不需要額外特判,方向仍是偏保守(推得出優先於脈絡),已讀,無 finding。
