## F1 「取最重」只保護已經落進頂端提交的判定;判定者結果在落地前、落地後都能被丟掉重擲
severity: major
blocking: 是 —— 本篇宣稱補掉前身 r3 的核心洞(重擲洗判定),但照設計做出來仍有四條不需要申訴就能把「推得出」換成較輕結果的路

spec 位置:〈做法〉第 2 節「判定怎麼算」、第 3 節第 5 點、第 3 節第 6 點;〈誠實界線〉第 2 條;〈前身 r3 發現怎麼處理〉。
引句:「所以重跑一次判定者拿到較輕的結果,不會蓋掉先前的推得出」
引句:「讓重擲沒用,但申訴本身仍給作者多一次機會」
引句:「判定檔一律從被推送的那個頂端提交裡讀」
引句:「任一不過就整份拒絕、不寫檔、rc1,列出原因」

重現(每條都是照 spec 的指令流程做,不用改工具):
1. **不 record**:prepare → 派判定者 → 報告裡有 12 行「推得出」→ 編排者不呼叫 record,重派一席。record 是自願步驟,spec 沒有任何東西把「派過的判定者」綁到「必須記帳」(prepare 產生的清單檔在 `.lumos/note-audit/`,本身被 `*` 忽略、不進版本控制,也不記「派過幾次」)。寫入端的「較輕拒絕」只比對已經存在的判定檔,沒記的等於沒發生。
2. **刪掉判定檔**:record 寫了 V1(含推得出)→ 還沒提交 → `rm governance/note-verdicts/V1.json`(或 `git clean`、`git stash -u` 也會帶走未追蹤檔)→ 重 prepare(prepare 讀工作目錄,V1 不在了,那幾行回到待審)→ 重派 → record V2(較輕,寫入端找不到較重的,不拒絕)→ 提交 V2 → check 讀頂端只看到 V2,放行。就算 V1 已經提交,在推送前用 `git rm` 或壓提交把它拿掉,頂端也看不到;spec 沒有「判定檔只准新增、不准刪改」的檢查(S10 反而要求壓提交後照放行)。判定檔是作者自己提交的純 JSON,把 `推得出` 改成 `脈絡` 也一樣沒人驗。
3. **整份拒絕等於重擲**:record「任一不過就整份拒絕、不寫檔」——一份 150 行的報告只要一條證據格式不合(見 F7,實驗報告約三分之一的程式行帶不合格式的證據),整份的推得出都不落地;作者照提示重派判定者,拿到的是一次全新的擲骰。
4. **改名或微調文字換編號**:內容編號含路徑、區塊與文字。筆記 `git mv` 一次、或行尾加一個字,編號全換,舊的推得出不再適用,新編號沒有任何先前判定,重判時寫入端沒有東西可比。
5. 另外 record 兩處讀判定檔(「重算待審集合」與「已經有較重的非申訴判定」)沒寫讀哪一份(工作目錄或頂端)。若照 check 讀頂端,第 2 條連 `rm` 都不用——V1 沒提交時較重的判定本來就看不到;若照 prepare 讀工作目錄,就是第 2 條。兩種選法都成立一條重擲路。

## F2 申訴次數沒上限、席名自報,申訴本身就是重擲

blocking: 是 —— 「只有申訴能調輕」的唯一條件是席名不同,作者可以一直換席名申訴到出現「脈絡」為止,RETIRE-IF ① 的量也因此失去定義

spec 位置:〈做法〉第 3 節第 3 點、第 5 點;〈條款〉S8;RETIRE-IF ①。
引句:「另派一席(席名不同)單判那一行、不給它前一席的結論」
引句:「申訴報告的席名要跟被申訴那批不同,而且要指明申訴的是哪一個判定檔」

重現:
1. 某行 N1 判推得出(席名 `opus`)。作者派 D1(`seat: opus-2`)申訴,D1 判推得出 → 沒調輕,那行還是不涵蓋。
2. 作者再派 D2(`seat: opus-3`),指明申訴 N1(席名 `opus-3` ≠ `opus`,合規)。D2 判脈絡 → 調輕 → 涵蓋。

## F3 多筆判定混在一起時怎麼算沒有定義,判定檔的資料形狀也裝不下 record 自己的語法
severity: major
blocking: 是 —— 同一個編號有兩筆以上申訴、申訴對上另一條分支來的非申訴判定、或同一次 record 同時帶一般報告與申訴時,spec 的規則給不出唯一答案,實作只能自己猜

spec 位置:〈做法〉第 2 節「判定檔」「判定怎麼算」、第 3 節第 5 點。
引句:「內容是這一批的來源(席名、編排者、模型、派工詞版本、時間、是不是申訴、申訴的是哪一批)」
引句:「record --diff <範圍> --prepared <清單檔> --report <報告> [--report …] [--dispute <報告> …]」

重現:
1. **一次呼叫寫一個檔,但來源是檔級單值**:語法裡 `--report` 必填、`--dispute` 選填,而且每次 record 寫一個判定檔。同一次呼叫帶 `--report A --dispute B`,檔裡的「是不是申訴」「席名」「申訴的是哪一批」都是單值,裝不下「A 不是申訴、席名 opus;B 是申訴、席名 opus-2、申訴 V1」。多份 `--report`(150 行切批平行派)各有自己的 `seat:`,檔級「席名」也只能留一個——之後有人申訴這個檔時,「席名要跟被申訴那批不同」要比哪一個 seat 沒有答案。反過來,要單獨記一筆申訴,語法逼你再塞一份一般報告。
2. **兩筆申訴結果不同**:N1 推得出;D1 申訴 N1 判一半一半,D2 申訴 N1 判脈絡(或反過來順序)。取最新?取最輕?判定檔的「時間」是各機器自己的時鐘,兩條分支合併後沒有可靠的先後。spec 沒說。
3. **申訴只指到某一批**:N1(分支 A)與 N2(分支 B)對同一編號都判推得出(例如同一個提交被兩條分支帶著、各自 record 過)。D1 申訴 N1 判脈絡。合併後「最重的非申訴」仍有 N2 的推得出;D1 只指明 N1——那行算涵蓋還是不涵蓋?同樣的問題發生在同一條分支上重複 record 同一份報告(同重量的非申訴判定不會被拒絕,只拒「較輕」)。
4. **申訴的申訴、申訴調重**:D1 把 N1 調成脈絡後,有人對 D1 申訴且判推得出——「只有申訴能調輕」沒說申訴能不能調重、能不能指向另一個申訴檔。
S8 只測「一筆較重非申訴+一筆申訴」,上面四種組合都不在條款裡。

## F4 略過(skip)能蓋掉已判的推得出,跟「只有申訴能調輕」自相矛盾
severity: major
blocking: 是 —— 一行已經被判推得出,作者跑一次 skip 就永久涵蓋,不走申訴、不進申訴率,而且 skip 之後才 record 的推得出會被當成「不在待審集合」默默丟掉

spec 位置:〈做法〉第 2 節「判定怎麼算」「涵蓋」、第 3 節第 7 點。
引句:「略過(skip)單獨算:有略過就算涵蓋,但判定檔標明是略過」
引句:「只有申訴批次能把它調輕」
引句:「模型限流、服務中斷時走 skip」

重現:
1. 行 L 被 V1 判推得出 → L 不涵蓋 → 仍在「當下待審的行」裡。

## F8 同塊同文字共用一個編號,加上「整句合判」與「取最重」,會永久毒化常見的結構行
severity: major

## F9 S2 的預期跟「找不到上線點」的既有語意相反
