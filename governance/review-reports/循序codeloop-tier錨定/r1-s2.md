# 審計報告:循序 code-loop tier 錨定 r1-snapshot(守衛象限席)

## Finding 1 [major] 反向守衛連「從第一輪就要 code+standard 全 panel」的合法新用法一併封死

引句：「**循序 legacy 格式=設計行為,放行**;帳面反帶 --round(panel 格式)→ rc2 格式衝突(鏡像 light 的反向守衛)」
引句：「`t_seq_code_std_panel_conflict`:code+standard 帳面帶 --round → rc2 格式衝突(反向守衛)。」

現行(kind-blind)守衛只有 `eff_tier in ("standard","high") and not panel_fmt` 一條。全新 code- loop 第一筆記 `--tier standard --round r1`(3 席全 panel)完全不觸發 rc2——這條路今天是通的。本案反向守衛把「從第一輪起就是 panel、無循序意圖」的帳也判成格式衝突;而它想擋的「先循序、後混 panel 記錄」早被既有 partial-mix 守衛(`n_round not in (0, len(rounds))`)擋住,不需要新守衛。「鏡像 light」類比不成立:light ratchet 有 escalate 逃生路徑,此處沒有對應設計。spec 全篇未承認「原本可用、本案後不可用」的收斂。

## Finding 2 [major] 「補標 standard」邀請詞沒揭露會吃掉既有輪數、可能立刻 cap-reached

引句：「code 循序 loop 修後可補標 standard(格式相容)」
引句：「cap=3(standard 的 cap——本案要買的正是「第 3 輪攤人」取代 legacy 的 6)」
引句：「既有 legacy loop 不受影響(無定錨仍推 legacy)」

`panel_fmt=False` 時 `rounds_count = len(rounds)`(全帳面記錄數,不分有無 tier)。已跑 4-5 筆 legacy 的循序 loop 在第 5 筆補 `--tier standard` → anchor=standard、cap=3、rounds_count 照算舊筆 → 下一次 `loop next` 立刻 cap-reached,零輪 standard 品質審查就被逼停——比不補標更糟(legacy 至少還能跑到 6)。「既有 legacy loop 不受影響」只在不補標前提下成立,而 S3 主動教人補標,兩段矛盾;「途中補標」時間線的唯一實質風險 spec 沒討論。
