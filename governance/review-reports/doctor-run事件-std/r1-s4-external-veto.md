作為外部否決席審查員，我針對此份 `doctor-run事件_計劃` 提出以下審計發現：

### 1. Blocker: 節點清單為空導致無法達成「清帳」判定目標
設計中 `nodes` 欄位固定為空，這與「緣起」中解決「看不出已清」的目標矛盾。若 `doctor-run` 事件不包含受檢節點清單，讀帳工具（如 `gov-stats`）在查詢特定節點狀態時，其「最後一筆事件」仍會停留在舊的警告上，無法得知該節點已在本次 run 中通過檢查。
> 引句：「無條件在 gov_events 末尾加 {"gate": "doctor-run", "kind": "ran", "hard": False, "nodes": [], "note": "issues=<n> gates=<本次有事件的 check-* gate 數>"}`

### 2. Major: 設計與測試案例的欄位名稱定義衝突
設計章節明確要求使用 `note` 欄位以符合 `cmd_gov` 的讀取邏輯，但 TDD 測試案例 1 卻預期資料寫入 `detail` 欄位。若照字面實作，將導致「程式通過測試但 UI 無法顯示」或「UI 正常但測試失敗」。
> 引句：「欄位名 note——cmd_gov 的 governance mapper 讀 d.get("note"),不是 detail」

### 3. Major: 統計語義配置與棘輪分母需求不一致
設計宣稱 `stats` 需讀取此事件作為棘輪分母，卻又聲明 `_STATS_NODE_SEMANTICS` 不需更新且印出 `n/a`。若統計引擎缺乏該 gate 的語義定義（如判定為成功/資訊），則無法將其納入有效計算邏輯，導致棘輪機制無法實作。
> 引句：「stats 要看得到它才能當棘輪分母);node 縮限模式下 nodes 為空本就不命中,無需特判」

### 4. Major: 帳本原始行與顯示層的去重邏輯導致數據不透明
設計要求顯示層按 commit 摺疊，但棘輪（統計）讀取原始行。這會導致使用者在 `gov` 介面看到「一次執行」，但統計數據卻因 CI 重試等因素計算了「多次執行」，造成人機理解落差，且容易在自動化判定時產生誤導。
> 引句：「dedup 鍵含 commit,同 commit 多次 --ci 在 gov 顯示上折成一筆」
