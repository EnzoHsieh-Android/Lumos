## F1 治理帳無鎖並發寫入,壞行會被讀取端靜默丟棄
severity: major
blocking: 是 —— 不改,兩個會談同時完成審查時,其中一筆「通過」紀錄可能在讀取端消失,導致明明審過的內容被推送閘誤擋,而且沒有任何錯誤訊息指出原因是併發寫入。

引句:「都過了才在治理帳寫一筆通過」

第二層 step4(`lumos note-audit record`)明講審核通過後要寫進治理帳,而 PRIOR-ART 段落又明講「機制層照抄本 repo 的代碼審留痕閘」——查現有 code-loop 的治理帳寫法,`scripts/lumos:28796` `_codeloop_gov_log` 用 `with open(path, "a", ...) f.write(json.dumps(event...) + "\n")`(`scripts/lumos:28816-28817`),整個函式沒有任何鎖,也沒有走本專案自己既有的並發寫入保護 `_vault_write_lock`(定義在 `scripts/lumos:14229`,用途正是「同一個筆記庫的 set/append/remove 一次只讓一個程序做讀—改—寫」,`scripts/lumos:14230-14231` 註解直接寫「沒有鎖時,回報成功的項目會被同時跑的另一個程序蓋掉」)。全 repo 目前只有 8 處寫入呼叫會經過這把鎖(`scripts/lumos:5615,9527,9604,9796,14279,14452,14491,21372`),`_codeloop_gov_log` 不在其中。讀取端 `_codeloop_read_from_ledger`(`scripts/lumos:28712-28715`)對解析失敗的行是 `except Exception: continue`——直接跳過,不報錯、不留痕。也就是說:如果 note-audit 的 `record` 沿用同一個無鎖 append 寫同一份 `docs/.governance-log.jsonl`,兩個會談(或一個會談跑 note-audit record、另一個同時跑既有 code-loop pass)同時 append,在多數本機檔案系統上單次 `write()` 對「未超過管線緩衝上限」的資料通常是原子的,但 Python 的文字模式 `write()` 不保證單一 syscall(尤其含中文字元、走 UTF-8 編碼時可能被拆成多次底層寫入),一旦交錯就會產生壞掉的 JSON 行——而壞行在讀取端是靜默丟棄,不是報錯。結果是:剛完成、本該放行的審查紀錄,無聲消失,使用者要重跑整套審查(單次審查在小實驗裡就要 4.4~9.7 分鐘,正式規模「幾十到幾百行」只會更久)。spec 完全沒提到這個共享寫入點需要鎖,也沒有提任何「治理帳同時被寫」的因應。

## F2 「切批平行派」與「單一 --report 輸入」之間沒有合併規則
severity: major
blocking: 是 —— 不改,實作者在筆記量大到需要分批的第一次就會卡住:要嘛自己發明一套合併/編號規則(沒人審過),要嘛把批次結果硬塞進單一 `--report`,兩種做法都可能讓 `record` 把某一批的判定誤套到另一批同編號但不同內容的行上。

引句:「推得出與一半一半必須附一個程式位置。行數多就切批平行派。」

同一段(第二層 step2)只有這一句提到平行分批,之後 step3(作者處理/申訴)與 step4(`lumos note-audit record --report <報告>`,S6 也只講「報告」單數)都只假設「一份報告」。`prepare` 產出的判定者派工檔怎麼編號(是整個範圍全域連號,還是每批各自從 1 開始)、多個批次跑完的多份報告怎麼合併成 step4 吃的那一份、申訴(S7)在批次情境下「第二席」要對哪一批獨立判——這些完全沒有定義。我在 `scripts/lumos` 裡 grep 不到任何 `note_audit`/`note-audit` 字樣(這是全新功能,沒有既有程式碼可以類推),所以這不是「照抄舊機制就好」能解的空白。如果批次各自從 1 編號、又用同一個 `record` 一次吃進去,兩批裡編號相同但指向不同筆記行的項目會在核對時互相踩到,S6 的「報告裡判推得出或一半一半的行,現在的新增行裡已經不在」這條核對邏輯就會核對錯行。

## F3 PRIOR-ART 要照抄的既有失效判定語意跟 S8 要求相反,而且該既有機制的 rebase/squash 失效正是本 repo 五天前才記錄的真事故
severity: blocker
blocking: 是 —— 若實作者真的照 PRIOR-ART 字面「照抄」既有留痕失效判定,新機制會在「這次推送之後每有一個程式碼提交」就整批失效,逼人重新跑一次審查(4~10 分鐘起跳);這正是 RETIRE-IF ③ 自己列的失敗徵兆(「新增的脈絡行月量掉到上線前三分之一以下」)的成因,而且是已知會發生、非臆測的行為。

引句:「機制層照抄本 repo 的代碼審留痕閘」
引句:「通過之後只改程式碼的提交不應讓紀錄失效;新增筆記行有任何變動時紀錄應失效」

現有「代碼審留痕閘」的失效判定是 `_codeloop_record_valid`(`scripts/lumos:29692`):有效的唯一兩條路是「同一個 sha」或「rec_sha 是 marker_sha 的祖先,且中間 `git diff --name-only rec_sha marker_sha` 列出的每一支檔都屬於簿記白名單」(`scripts/lumos:29715-29722`,判準是 `all(f in _BOOKKEEPING_FILES or f.startswith(_BOOKKEEPING_DIRS) for f in files)`)——換句話說,中間只要有**任何一支非簿記檔案**(這在絕大多數情況下就是一般程式碼檔)被改動,紀錄就失效。這跟 S8 要求的方向完全相反:S8 要「改程式碼不失效、改筆記才失效」,現有機制是「改簿記以外的任何檔(含程式碼)都失效」。如果 PRIOR-ART 段落字面上的「照抄」被實作者當成可以直接搬用的演算法,做出來的東西會是:只要這批推送之後有任何後續的程式碼提交,note-audit 的通過紀錄就會失效,逼著重審那些其實根本沒變過的筆記行。

更關鍵的是,這不是我推測的邊角案例——`docs/lumos-toolchain-knowledge/Systems/pitfalls-code-loop.md:24` 的 PITFALL 逐字寫著:「把本機提交壓成一個或 rebase 之後,表態與審查留痕都會失效,內容沒變也一樣」,標記日期是 2026-09-22(rtb-production-agent-demo 回報的真實事故,本 spec 寫於 2026-09-27,只差五天),而這正是同一套 `_codeloop_record_valid` 的祖先鏈判定造成的。這份 spec 在「附加參考資料」裡也把 `Systems/pitfalls-code-loop` 列為固定牽連節點,但 spec 全文對這個已知的 rebase/squash 失效模式沒有一句提及、沒有排除、也沒有講清楚新的指紋要怎麼算才能同時滿足「rebase 後內容沒變就該還算數」跟「只改程式碼不該失效」——這兩個要求合起來意味著指紋必須綁「筆記行的內容」而不是「commit 祖先鏈」,但 PRIOR-ART 段落自己說的是「紀錄綁內容」(spec 原文),而現有可抄的機制其實是綁 sha 祖先鏈+檔案清單,不是內容雜湊。這個矛盾是本 spec 最核心的可執行性缺口:兩層裡負責「東西還算不算數」的那把判定邏輯,唯一寫出來的參照範本在方向上是反的,而且反的那個方向五天前才炸過一次。

## F4 prepare 輸出檔的路徑/命名完全未定義,對照既有同類機制有雙會談覆寫風險
severity: major
blocking: 是 —— 不改,兩個會談在同一個工作目錄、同一分支同時各自跑 `note-audit prepare` 時,後者極可能覆寫前者產生的判定者派工檔;若照本 repo 既有「per-branch 單一檔」的慣例走,這個覆寫是結構性的,不是機率低的巧合。

引句:「連同判定者派工詞寫成一個檔」

全篇 spec 沒有一處講這個檔要放在哪裡、叫什麼名字、要不要進版控、要不要按 branch/時間戳/會談 id 區分。本 repo 目前唯一可比照的既有前例是 `_codeloop_read`(`scripts/lumos:28678-28684`):`governance/code-loop/<branch 扁平化>.json`——單一檔、以 branch 為鍵,不含任何時間戳或程序識別;而這一類「多個程序可能同時寫入的本機狀態檔」正是 `_vault_write_lock` 存在的理由(`scripts/lumos:14229-14237`)。如果 `note-audit prepare` 照抄「per-branch 單一檔」這個唯一能類推的慣例,又沒有像 `_vault_write_lock` 那樣上鎖,兩個會談各自對同一分支跑 `prepare --diff <範圍>`(例如各自在處理不同的新增段落,或單純重跑一次)時,後寫的會蓋掉先寫的判定者派工檔。由於 step2 的編號來自 prepare 當下抓到的那份快照,若審查員 A 拿到被蓋寫前的版本、審查員 B 拿到蓋寫後的版本,兩人交回的報告各自的「編號→內容」對應表就不一致,`record` 用 S6 的核對邏輯去比對「現在的新增行」時,會拿錯一批的判定去核對另一批的行號,而 record 本身沒有辦法偵測到「這份報告其實是對著另一個快照判的」。

## F5 `record` 的命令列介面缺一個它自己描述行為必須要有的範圍參數
severity: major
blocking: 是 —— 不改,實作者無法把 `record` 寫成 spec 描述的樣子:命令簽章只有 `--report`,卻要核對「現在的新增行」,這兩者對不上,審查期間作者若又新增了一行程式碼推得出的內容,`record` 沒有獨立管道知道要拿它跟誰比。

引句:「工具機械驗(每一行都有判定;附的程式位置那支檔真的存在、行號沒超出檔長;報告裡判推得出或一半一半的行,現在的新增行裡已經不在,除非有成立的申訴)」

「現在的新增行」這五個字意味著 `record` 執行當下要重新算一次「範圍內新增的筆記行」(不然就只能盲信報告自己列的清單,那樣「漏判任何一行」這條驗法就無從查起——報告裡沒列的行,record 根本不知道它存在)。但整份 spec 給的 `record` 呼叫方式只有 `lumos note-audit record --report <報告>`,沒有 `--diff <範圍>` 或任何等價的方式讓它知道要用哪個範圍重新抓「現在的新增行」。這正好對上我被指派要查的情境:如果作者在 prepare 產生報告之後、record 驗收之前,又在同一批推送裡新增了一行程式碼推得出的 FACT/FLOW,record 要嘛(a)沒有範圍可用、只能比對報告自己聲稱的行(這樣新加的那行完全不會被檢查到,S6 的「漏判擋」形同虛設,因為它只驗報告內部一致,驗不了報告是否涵蓋了全部新增),要嘛(b)偷偷從別處(例如環境變數或某個隱藏 state)拿到 prepare 用過的範圍,但 spec 沒寫這條路徑存在。這個介面缺口跟 F2(分批合併)是同一種病灶:spec 對「新增行的權威來源」只描述了一次(prepare 那一刻的快照),卻要求後面兩個獨立指令(record、push 檢查)都要能重新驗證同一件事,卻沒有講清楚它們怎麼拿到同一個範圍。

## F6(較低嚴重度)整個第二層審查是一次性對話流程,沒有中斷後恢復/交接機制
severity: minor
blocking: 否 —— 中斷後的預設行為是「沒有完整報告就是沒過」,這在方向上是安全的(fail-closed),只是浪費重跑的時間,不會讓壞內容漏過,所以不判定它會讓實作者做錯決定。

引句:「編排的對話照這個檔派一席乾淨審查員(預設 opus)」

第二層審查明講是「編排的對話」派審查席,這是一次性、跑在對話 session 裡的流程,不是可重入的 CLI 步驟。CLAUDE.md 本身有 `lumos handoff <計劃節點>`(唯讀交接查詢)這類機制因應「上一個 session 做到一半斷了」,但 spec 對「審查跑到一半這個對話就斷了(額度用完、當機、人關掉終端)」完全沒有著墨——沒有部分進度的存檔、沒有可恢復的中繼狀態、也沒講清楚重新跑一次 `prepare` 對同一範圍時,是否會沿用/覆寫上一次沒判完的那份檔案(這又跟 F4 的命名問題疊在一起)。因為 `record` 本來就要求「每一行都有判定」才放行(S6),半途中斷只會讓推送繼續被擋,不會產生假放行,所以我把它列為 minor:成本問題,不是正確性問題。
