# 筆記不存程式碼推得出的事_計劃

白話:筆記只准寫程式碼推不出來的東西(為什麼、否決過什麼、事故、程式看不到的限制)。程式碼推得出來的內容一寫進去就會過期、而且讀的人分不出來——rtb 在新規則下寫的筆記,抽樣現況句 41% 已經跟程式碼對不上。這次不再靠寫法規範,改成兩層機械擋:提交時擋形狀固定的東西,推送前派一個沒有脈絡、會去讀程式碼的審查員,逐行判新增的筆記內容是不是程式碼推得出來,判是的就不准推。

依據:[[Issues/筆記把程式現況寫進脈絡而漂移_rtb實測回饋]] 的 d1–d6(Enzo 2026-09-27 裁);為什麼前一版沒擋住見 [[Projects/Lumos定位_程式碼為主脈絡為輔_計劃]]〈檢討〉。

PRIOR-ART: 機制層照抄本 repo 的代碼審留痕閘([[Systems/pitfalls-code-loop]]):推送前查「這批改動有沒有通過紀錄」、紀錄綁內容、`--no-verify` 硬推時 CI 標紅;判定者照抄無脈絡審查席的派法(乾淨 agent、只給原始問題不給結論)。世界的做法:文件與程式碼同步多半走「從程式碼生成文件」(openwiki 一類,見 [[Systems/外部對照-code衍生wiki]]),它讓文件免疫漂移,但裝不下程式碼沒有的脈絡——本案反過來,讓筆記只裝那一種,兩者不衝突。不採用新依賴:判定者是既有的審查席派工,不接外部服務。
RETIRE-IF: 上線兩個月後任一成立就撤掉或重想第二層:①作者申訴被第二席認同的比例超過三成(判定者不可靠);②對上線後新增的筆記行隨機抽樣,仍有一成以上是程式碼推得出來的(擋不住);③新增的脈絡行(判成 CONTEXT 的)月量掉到上線前的三分之一以下(大家乾脆不寫筆記了,擋掉的比救下的多)。
REVISIT:2026-11-27 跑上面三個量;順便在 rtb 重做一次跟 2026-09-27 同方法的漂移抽樣,拿 41% 當基準比。

## 判定者能不能用:小實驗(2026-09-27)

把 rtb 的 68 句打亂、拿掉標題旁的提示,給兩個沒有脈絡的審查員,各自讀 rtb 程式碼判「程式碼推得出 / 脈絡 / 一半一半」。其中 55 句是稽核逐句對過程式碼的現況句(答案應該是推得出或一半一半),13 句是決策欄位裡的「為什麼選這個」(答案應該多半是脈絡)。卷證在 `governance/audits/2026-09-27-rtb-notes/judge-experiment/`。

| 審查員 | 55 句現況句抓到 | 13 句理由誤判成純程式碼 | 花的時間 |
|---|---|---|---|
| opus | 55(53 推得出、2 一半一半) | 0(9 脈絡、4 一半一半) | 約 4.4 分鐘 |
| sonnet | 54(漏 1 句:在講已刪掉的程式,它判成歷史) | 3 | 約 9.7 分鐘 |

- 兩席在「要不要擋」上 68 句同意 64 句。判成一半一半的理由句我逐句看過,裡面確實夾著程式現況(例如「某函式在第幾階段加的、路由和評估都靠它」)。
- **誠實界線**:正例是稽核挑出來的現況句,比真實新增行好判;反例只有 13 句;對照答案由我一人訂。真正難的是「一句話裡理由跟現況混在一起」,這類樣本太少。所以判定者預設 opus、派工詞要明寫「描述已刪掉的程式、用現在式寫的,也算推得出」,而上線後的申訴率是第一個要看的數。
- 句型比對做不到這件事:同日對近一個月 25,282 行新增筆記跑「目前沒有/只有 N 種」句型,抽樣約三分之一是真的,見 Issue〈擋什麼的初步實測〉。

## 做法

### 第一層:提交時擋形狀固定的東西(只看這次新增或改動的行)

只看這次新增或改動的行,舊行不管(d2)。三條:
1. **程式行號引用**:`檔名.副檔名:數字`、`#L數字` 這種指向程式某一行的寫法。行號只要有人改碼就錯位,抽樣 12/12 都是這類;改寫成「哪支檔的哪個函式」或乾脆刪掉。程式碼圍欄裡的內容與引述別人原文的「引句:」行不算(那是當時的輸出或別人的話,不是指路)。
2. **做完的計劃還留著現況段**:這次提交把計劃的狀態改成 done,或在狀態已是 done 的計劃的「## 現況」那節裡新增或改動了行,而那節非空行超過一行,就擋(只碰到同一篇別處的提交不擋,照 d2);要收成一句「開工時的問題是什麼、為什麼要做」(d4)。`lumos set <計劃> status done` 也先檢查一次,早一步講。
3. **現況描述沒寫出程式碼答不了的來源**:新增的 `FACT:` 行要帶 `[src:部署]` `[src:資料庫]` `[src:生產]` `[src:外部]` `[src:人工]` 其中之一(d3);只寫「以程式碼為準」加查詢不再算數——程式碼查得到的就不該寫。

入口:提交前那道既有的逐篇檢查旁邊加一道,只吃暫存區的差異;推送前與 CI 用同一支指令對整段範圍再跑一次,因為 `--no-verify` 能跳過提交前那道。

### 第二層:推送前的筆記內容審

1. `lumos note-audit prepare --diff <範圍>`:列出範圍內新增的筆記行(去掉開頭欄位裡的連結、標籤、日期、狀態這類結構欄位,去掉程式碼圍欄),編號,連同判定者派工詞寫成一個檔。派工詞就是上面小實驗那份,另加「現在式描述已刪掉的程式也算推得出」。
2. 編排的對話照這個檔派一席乾淨審查員(預設 opus),它要讀程式碼,逐行回「推得出 / 脈絡 / 一半一半」,推得出與一半一半必須附一個程式位置。行數多就切批平行派。
3. 作者處理:推得出的整行刪;一半一半的刪掉程式碼那部分、留理由。覺得判錯的可以申訴——申訴要另派一席不知道前一席結論的審查員單獨判那一行,第二席也判脈絡才算申訴成立。
4. `lumos note-audit record --report <報告>`:工具機械驗(每一行都有判定;附的程式位置那支檔真的存在、行號沒超出檔長;報告裡判推得出或一半一半的行,現在的新增行裡已經不在,除非有成立的申訴)。都過了才在治理帳寫一筆通過,綁「這批新增筆記行」的指紋——之後只改程式、不動筆記的提交不用重審。
5. 推送前與 CI 查:範圍內有新增筆記行、卻找不到指紋對得上的通過紀錄,就擋。沒有新增筆記行的推送直接放行。

### 規範文字跟著改

紀律範本〈寫筆記時〉的 `FACT` 那列改成 d3 的收窄說法,並寫明兩層擋的存在與申訴方式;各專案各自跑 `lumos update` 拉新版(那支指令是從工具鏈原始 repo 拉進本專案,不是由這裡推出去)。skill 裡只指路、不放第二份定義(範本是單一來源)。

## 條款

- [S1] 若暫存區新增或改動的筆記行含程式行號引用,且不在程式碼圍欄內、也不是引句行,則提交應被擋下並列出每一處;同一篇沒改動的舊行含行號時不應擋 [test:t_note_shape_blocks_new_line_refs_only]
- [S2] 若這次提交把某計劃的狀態改成 done、或在狀態已是 done 的計劃的「## 現況」一節裡新增或改動了行,且該節非空行超過一行,則提交應被擋下;只改到同一篇其他節的提交不應被擋;`lumos set <計劃> status done` 遇到同樣情形應回非零且不改檔 [test:t_note_shape_done_plan_current_state_collapsed]
- [S3] 若新增的 `FACT:` 行沒帶五種 `[src:]` 類別之一,則提交應被擋下;只有「以程式碼為準」加查詢的 FACT 行也應被擋下 [test:t_note_shape_fact_requires_non_code_source]
- [S4] 當推送前或 CI 對範圍重跑第一層,結果應跟逐次提交時一致(用 `--no-verify` 跳過提交前那道的違規,推送時應被擋下) [test:t_note_shape_range_catches_no_verify_commits]
- [S5] `lumos note-audit prepare` 列出的行應只含範圍內新增的筆記行,且應排除開頭欄位裡的結構欄位與程式碼圍欄;範圍內沒有新增筆記行時應回報零行 [test:t_note_audit_prepare_lists_added_prose_only]
- [S6] 若報告漏判任何一行、附的程式位置指向不存在的檔或超出檔長的行號,或判推得出與一半一半的行仍在目前的新增行裡且沒有成立的申訴,則 `note-audit record` 應拒絕且不寫帳 [test:t_note_audit_record_rejects_incomplete_or_unfolded]
- [S7] 若申訴行沒有第二席報告、或第二席沒判脈絡,則該申訴不應成立 [test:t_note_audit_dispute_needs_second_seat]
- [S8] 若範圍內有新增筆記行而治理帳沒有指紋相符的通過紀錄,則推送前檢查應擋下;通過之後只改程式碼的提交不應讓紀錄失效;新增筆記行有任何變動時紀錄應失效 [test:t_note_audit_check_fingerprint_binding]
- [S9] 紀律範本的 FACT 那列應寫 d3 的收窄說法,各專案注入的紀律區塊應與範本一致 [test:t_discipline_fact_row_narrowed]
- [S10] 判定者派工詞應逐字沿用 `governance/audits/2026-09-27-rtb-notes/judge-experiment/` 的 `judge_prompt.md`(驗過的那份)的分類定義,改動它要重跑那 68 句的小實驗 [manual:改派工詞前後各跑一次 68 句,抓到數與誤判數不得變差,結果記進本計劃]

## 回退

- 第一層:拿掉提交前與推送前那兩處呼叫即可,不留狀態。已經被擋而改掉的筆記內容不會回來(那是作者自己刪的)。
- 第二層:拿掉推送前與 CI 的查核即可;治理帳裡已寫的通過紀錄留著無害(沒有讀者就不會被用到)。
- 紀律範本的 FACT 那列:改回舊句,各專案各自 `lumos update` 拉回;但回退前要先想好,舊句正是讓現況描述留存的出口(見〈檢討〉第 4 點)。

## 實務隱患

- 守衛面:這是新的擋人機制,誤擋會讓人習慣繞過——所以第二層有申訴、第一層只看新行,RETIRE-IF ① 盯申訴率。
- 已排除:對外送出:推送被擋是本機行為,不送任何內容到外部服務(判定者是對話內派的審查席)
- 已排除:不可逆:筆記內容刪了可以從提交紀錄找回,閘拿掉即恢復原狀
- 已排除:金流:不碰任何付款或計費流程

## 誠實界線

- 判定者的準度只驗過一次、68 句、反例 13 句;混合句樣本不足。上線頭兩週要逐筆看申訴。
- 第二層擋的是「這次推送新增的行」,不會回頭清舊帳(d2),舊筆記裡的現況句還會被讀到,直到有人改到那篇。
- 花費:本 repo 近一個月約 473 個提交新增 25,282 行筆記,平均一次推送要判幾十到幾百行;Enzo 已表明不在意額度(d6),但推送前要多等審查員跑完。
