severity: major

## F1 done 計劃整篇正文審查沒有規模上限,實測會撞上千行

severity: major
blocking: 是 —— 不改,實作者會照字面把「上線前校準」設計成永遠測不到最貴的那一種輸入,讓最貴、最需要驗證品質的那批審查完全跳過校準
引句:「那篇計劃整篇正文都進清單,不只新增行」

1. 輸入:本 repo 現有 113 篇 `status: done` 的計劃,我逐篇讀 frontmatter 與行數統計,最大一篇是 `docs/lumos-toolchain-knowledge/Projects/公開精簡版_實作計畫.md`,共 1098 行(file: `docs/lumos-toolchain-knowledge/Projects/公開精簡版_實作計畫.md:1098` 該檔 `status: done`,是目前 repo 最大的一份已完成計劃)。
2. 走到哪一段:spec 定義「計劃在範圍內被改成 done…那篇計劃整篇正文都進清單,不只新增行」,只要某次推送把這類大計劃從 doing 轉成 done(不論本次實際改了幾行),`prepare` 就要把整篇正文(1000+ 行)全部塞進同一份 note-audit 清單,交給判定者逐行判。
3. 壞在哪:spec 自己在〈誠實界線〉估的花費是「一次推送要判幾十到幾百行」,而〈上線前校準〉的驗收方法是「用 prepare 對 rtb 近一週真實的新增行跑一次…編排者抽 30 行人工對照」——這兩處都只覆蓋「日常新增行」的規模,完全沒設計來驗證「單篇 1000+ 行一次性倒入」這種輸入。也就是說,規格自己承諾的效能估計與校準方法,對它自己定義的 S5 情境(done 轉態整篇審)不成立、也沒驗過,恰好是風險最高(判定者一次要看最多行、最容易漏判)的那批,反而是唯一沒被校準覆蓋到的。
4. 沒有任何條款(S1–S15)對「整篇正文超過 N 行時怎麼辦」給出上限、分批以外的規模控管或额外校準要求;「行數多就切批平行派」只解決能不能派出去,不解決判定品質有沒有驗過。

## F2 改名偵測是相似度門檻,跟 d4「收成一句」的做法互相牴觸

severity: major
blocking: 是 —— 不改,實作者會誤信「改名用 git 的改名偵測認成同一篇」是可靠的原語,寫出的系統在改名同時大幅改寫時,會把整篇舊內容當成全新增,違反本設計自己要避免的「不必要重審」目標
引句:「改名用 git 的改名偵測認成同一篇」

1. 輸入:我在暫存目錄(非本 repo)用 `git init` 建了一份 120 行的筆記檔,先提交,再模擬 spec 自己要求的動作——同一個提交裡「改名 + 依 d4 把現況收成一句」(`git mv old_plan.md new_plan.md`,並把內文從 120 行收成 5 行摘要),然後跑 `git diff --cached --name-status -M` 與明確帶相似度的 `-M50%`。
2. 走到哪一段:兩次都輸出 `A docs/Projects/new_plan.md` / `D docs/Projects/old_plan.md`,git 完全沒有認成 rename——本 repo 既有程式碼本身也承認 `-M` 是相似度門檻判定(scripts/lumos:22627 的註解「★只帶 -M、沒帶 -C★」印證這條路線本來就依賴 git 的相似度啟發式,不是保證)。
3. 壞在哪:spec 的「行」定義明講「改名用 git 的改名偵測認成同一篇,只算真正變動的行」,S3 也重申「改名的筆記應認成同一篇」;但 spec 同時要求 done 轉態時「照 d4 要把現況收成一句」——這正是會把改寫幅度推過相似度門檻、讓 git 判成刪除+新增而非改名的操作。一旦被判成刪除+新增,S3 想要的「認成同一篇、只算真正變動的行」就不成立,新檔會被當成 100% 新增內容整篇塞進審查——這雖然方向上偏安全,但直接違反 PRIOR-ART 段自己講的初衷:「綁定方式照②不照①…本案若照抄就會讓每個後續程式提交都逼人重審」。也就是說,設計為了避免「重審」而選的內容指紋機制,遇到「改名+大改寫同時發生」這個 spec 自己鼓勵的操作序列時,反而製造出一次不必要的整篇重審,而 S1–S15 沒有任何一條測試涵蓋「相似度低於門檻的改名」這個邊界。

## F3 search 證據的機械驗證只查路徑存在,擋不住空字串與目錄路徑

severity: major
blocking: 是 —— record 這一步的存在理由就是「不信報告自己列的清單」,但驗證本身在這兩種輸入下形同不存在,等於信任邊界照樣被繞過
引句:「由工具自己用字串比對跑一次(不開 shell),確認路徑存在」

1. 輸入:判定者(或申訴的第二席)在報告裡對一行「已刪掉的函式現況描述」寫下 `search: "" in docs/`(空字串、且 `<路徑>` 指向一個目錄而非檔案)作為「推得出」的證據。
2. 走到哪一段:`record` 的機械驗證只列了「search 的路徑不存在應拒絕」(S7),沒有規定要拒絕(a)`<字串>` 為空、(b)`<路徑>` 是目錄而非檔案。空字串是任何檔案內容的子字串,`docs/` 這個目錄本身「存在」——兩個條件在字面規格下都會通過檢查。
3. 壞在哪:record 的整段設計前提是「★不信報告自己列的清單,重算範圍的新增行集合★」,但對 search 證據卻只做最表層的存在性檢查,沒有排除空字串與目錄輸入,等於在證據這一關留了一個可以無成本通過的後門——只要判定者(或申訴席)願意寫一個空字串當「search 命中」,record 就會把「推得出」的判定接受下來(反過來,若證據標準太鬆也會讓真正該擋的內容被誤判成「已用 search 驗證,可放行」)。規格沒有講清楚:目錄要不要遞迴掃、字串長度下限是多少、比對是不是要求非空且至少命中一次——這些都不是「以程式碼為準」可以補的,是規格本身要交代的可執行細節。

## F4 record 合併多份報告時,同一內容編號若有衝突判定,沒有決勝規則

severity: major
blocking: 是 —— 未指名決勝順序,兩種常見實作(先到者勝/後到者勝)都符合字面規格,卻會讓「推得出」的判定被同一個編號上另一份較寬鬆的報告悄悄蓋掉而不留痕
引句:「多份報告應以內容編號合併」

1. 輸入:record 支援 `--report <報告> [--report …]`,同一次流程可能因為重跑批次或判定者非決定性(LLM 判定本來就不保證每次結果一致)而對同一個內容編號產生兩份彼此不同意的報告——都不是走 `--dispute` 這條正式申訴路徑(申訴需要「另派一席不知道前一席結論的審查員單判那一行」並「所有申訴與結果都寫進通過紀錄」,S8 才有決勝規則:第二席較輕者勝)。
2. 走到哪一段:S7 只規定「多份報告應以內容編號合併」與「①每一行的內容編號都在某份報告裡有判定…應拒絕」「②判推得出或一半一半的行已不在集合裡,除非有成立的申訴」——這兩條只處理「缺判定」,沒有處理「同一編號、兩份非申訴報告給出不同判定」這種情況該以哪一份為準、要不要視為格式錯誤直接拒絕。
3. 壞在哪:若實作選擇「合併時取任一份/後到者覆蓋」,一個本來被判「推得出」的行,只要另一份報告(不論是重跑批次還是誤帶的舊報告)把它標成「脈絡」,record 就可能悄悄放行,而且這整個過程不會經過 S8 規定的「第二席不知道前一席結論」的申訴紀律,也不會被記進通過紀錄裡的申訴欄位——等於在正式申訴流程之外開了一條沒有留痕的改判路徑。

## F5 內容編號不含行號,同一檔內文字重複時,report 只列一次,作者不知道有幾處要刪

severity: minor
blocking: 否 —— 不會讓壞內容通過(record 重算集合仍會抓到殘留的那一份),但會讓作者反覆推送被擋而摸不清原因,是可用性缺口,不是安全缺口
引句:「路徑加那行文字的短雜湊(行號移動不影響編號)」

1. 輸入:同一篇筆記裡意外重複貼了兩次一模一樣的 `FACT:` 行(例如複製貼上失手),兩處都在本次推送新增的範圍內。
2. 走到哪一段:兩處的內容編號完全相同(定義只吃路徑+行文字,不吃行號),`prepare` 產生的清單依集合語意只會出現一筆;判定者對這一筆給出「推得出」的判定,作者依報告只看到一行要處理。
3. 壞在哪:如果作者只刪掉其中一個物理位置的重複行,`record` 重算新增行集合時仍會在另一個位置找到相同的內容編號、判成仍在集合裡而拒絕(這點是安全的),但錯誤訊息只會回報「這個內容編號還在」,不會告訴作者「你只刪了一半,還有一處在別的地方」——規格沒有要求清單或拒絕訊息附上物理位置/出現次數,作者要自己用文字比對去找剩下那一處在哪裡,徒增來回。

## F6 prepare 對「空集合」輸入沒有明講行為,只有 record 和 check 講了
