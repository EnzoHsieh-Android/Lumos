# 高風險測試證據加嚴_計劃

> 白話:現在越危險的功能,工具對它的測試反而管得越鬆——風險低的計劃要求每條新行為的測試在實作前先紅,風險高的只印不擋,交給設計審與代碼審。但審查本身也是 AI 在判斷,拿它補最重要的那一塊說不通。這份計劃讓風險高的計劃在設計審過了之後,套上風險低那一整套「新行為各自先紅」的檢查;預期值寫成一張表、每列寫需求來源,推送前整張表要有人簽(預設人簽,AI 簽也放行但記下來)。「紅要紅在斷言上」、建置檔讓測試不跑、改到的行跑變異測試這三件要讀 Gradle 的輸出,排第二批。

## 名詞

- 風險高/風險低:規格閘的門判定(`_door_judge`)判的:任一硬訊號命中(連到標了金流、對外送出、不可逆、守衛面的節點等),或〈實務隱患〉缺任一類「已排除」行,就是風險高;作者只能往嚴調。那四行「已排除」是作者自填的。
- 新行為條款:驗收條款裡沒標 `[keeps]`、綁了 `[test:]` 的那幾條;標 `[keeps]` 的是「維持既有行為」,測試本來就該綠。
- 先紅:實作前跑一次條款綁的測試,它要失敗;證明測試真的在驗還沒做的新行為。
- 雙向檢查:風險低計劃現有的那一套「新行為各自紅」規則,分兩段——跑測試前的靜態檢查(`_spec_gate_twoway_static`:至少一條不標 keeps、標 keeps 的測試在計劃建立前就存在)與跑完之後的判定(`_spec_gate_twoway_run_verdict`:每條沒標 keeps 的要紅、標 keeps 的要綠、弱證據不算);沒過時印補紅燈做法的是 `_spec_gate_low_not_red`。
- 弱證據:規格閘紅、綠之外的第三種判定,意思是「這次跑的結果證明不了什麼」——一支都沒跑到、篩選選中好幾支、被跳過(`_spec_gate_verdict`)。
- 設計審判定檔:設計審通過後凍結的 `governance/replay/<迴圈編號>/verdict.json`(`lumos loop replay --freeze` 寫的),裡面 `verdict.rc` 是 0 代表處置閘過了;代碼審留痕(`code-loop pass`)已經拿它當「審查做完了」的證明。
- 先紅模式:規格閘遇到「門判風險高、設計審判定檔讀得懂而且 rc 是 0、迴圈首筆帳不早於生效時間」的計劃,改套雙向檢查;其他風險高計劃照舊紅綠只印不擋。
- 迴圈首筆帳:審查帳裡這份計劃的迴圈編號最早一筆非結局帳的時間(`_loop_first_ts_key`,規格閘句式與回退節的不回溯也用它)。
- 生效時間:程式常數 `_HIGH_RED_SINCE`,寫法同 `_SPEC_GATE_SINCE`(帶時區的完整時間戳),值取本計劃合併上主線那一刻;迴圈首筆帳早於它的計劃不套先紅模式。
- 預期值表:計劃裡一節 `## 預期值表`,底下一張表,逐列寫「哪條條款、輸入什麼、預期什麼、這個預期從哪條需求來」。
- 表指紋:整張預期值表的內容指紋,任一格改了任何一個字就變;換行符號從 CRLF 換成 LF、格子頭尾的空白,不算改。
- 簽核:有人看過預期值表、確認每列對得上需求,工具記下表指紋與簽的是人還是 AI。
- 治理帳與審查帳:治理帳是 `docs/.governance-log.jsonl`,各道閘的事件都寫這裡,設計上進版控;審查帳是 `docs/.canary-log.jsonl`,設計審、代碼審的記帳與規格閘留痕寫這裡,消費專案預設被 git 忽略。規格閘留痕兩本都寫一份,推送前兩本合併讀(`_spec_gate_latest_merged`)。
- 考場:mOrangePos 的演練工作樹與只留本機的分支,拿來實機驗 lumos,不推、不併。
- 逃逸帳:審查放行之後,在實作、CI、正式環境才被發現的洞,用 `lumos loop escape` 記下來的帳。

## 問題與最小解

立案(2026-11-04,Enzo 原話):「風險高的靠review 補位？ 但是重點在於，風險高的測試，到底是不是實在的測試」「直接開新計劃，網路印證方向、做法，排除已有人實驗無效的坑」。

1. **風險高的計劃幾乎都沒有先紅的證據**:審查帳裡規格閘留痕 458 筆(2026-09-17 到 11-03)共 133 份計劃;每份取最新一筆看風險,風險高 102 份(77%);這 102 份裡,任何一筆留痕跑出過紅的只有 13 份(只看最新一筆是 7 份)。風險高的沒有紅燈版,推送前比對抓不到「預期值被改成實作的輸出」,只剩審查。
2. **預期值對不對需求,工具完全沒管**:先紅、紅燈版、防竄改比對都只證明「測試會抓錯」,證明不了預期值本身對;前面每一關都過、預期值寫成打八折而需求是打九折,照樣上線。現有 `lumos signoff` 記一筆「誰點了頭」(棄置合約時 `guard abandon` 會讀它帶的參照),不綁內容,也沒有推送前的閘讀它。
3. **「紅」不分原因**(第二批):Kotlin/Java 的測試輸出讀不出跑了幾支(`_RAN_EVIDENCE` 沒有這兩種),規格閘只能照退出碼判;編譯失敗、`--tests` 篩不到、被測程式還是 `TODO()`,全都判紅。

最小解:不另寫一套風險高的檢查。風險高的計劃在設計審過了之後,規格閘與推送前檢查都把它當風險低一樣查(同一支雙向檢查、同一支推送前逐份檢查,含已完成寬待、兩本帳合併讀、條款指紋過期);只新增預期值表的靜態檢查與整表簽核。紅因判讀要在每支測試跑完當下讀 Gradle 報告,跟第二批的 Gradle 工作一起在考場實跑後再設計。

PRIOR-ART:只要求「修前紅、修後綠」不夠,有 SWE-bench 的實證(UTBoost,ACL 2025:Verified 裡 26/500 題測試不足、345 個錯誤修補被判通過),所以先紅配上紅燈版比對與第二批的變異測試;簽核綁內容指紋、內容改了舊簽作廢,同 GitHub「推新提交作廢舊核可」與 Gerrit copyCondition;表格解析照 GFM 表格規則(格內 `\|` 是字面管線),但欄數不符時不照 GFM 補空格或丟多的(多的那格會悄悄不進指紋),一律擋。借用:風險低的雙向檢查與推送前逐份檢查(`_spec_gate_twoway_static`、`_spec_gate_twoway_run_verdict`、`_spec_gate_low_not_red`、`_spec_gate_push_scan`、`_spec_gate_push_one`)、設計審判定檔的讀法(`_codeloop_pass_read_verdict`)、迴圈首筆帳(`_loop_first_ts_key`)、找節(`_h2_section_lines`)、端到端驗收放行「沒有互動終端記成 AI」(`_waive_origin_tty`)與它的 `by` 欄、既有 `signoff` 閘名;自建:預期值表解析、表指紋與它的推送前檢查。
RETIRE-IF:生效後連續 90 天,先紅模式的計劃在推送前因「沒有先紅留痕」或「預期值表沒簽」被擋的次數為 0(看治理帳 `high-red-missing`、`expected-unsigned` 兩種擋下事件),而且同期逃逸帳裡沒有一筆是「測試預期值抄實作」或「測試沒在驗」——代表這兩道沒在擋任何東西,改回只印;或 AI 簽的次數連續 90 天佔 100% 且逃逸帳沒有預期值類的洞,簽核這道改成只記不擋。

## 調研結論(2026-11-04,四路網路調研)

- **只靠先紅不夠,要配紅燈版與變異測試**:UTBoost(上)與 PatchDiff(Wang、Pradel、Liu,ICSE 2026:通過測試的修補 29.6% 行為跟標準解不同)。先紅是入場券;「事後把實作搬走造假紅」查不到專門對策,對最終程式跑變異測試跟先寫後寫的順序無關,是第二批要補的那一塊。
- **Gradle 報告分不出紅的原因**:Gradle 的 JUnit XML(`JUnitXmlResultWriter`)把 `errors` 寫死成 0,所有例外都歸 `<failure>`;要看失敗的型別。Truth、AssertJ、kotlin.test、MockK 的 verify 都丟 `AssertionError` 子類;Kotlin `TODO()` 丟 `NotImplementedError`(繼承 `Error`,不是 `AssertionError`)。
- **證明「紅發生在實作之前」靠不住**:用提交順序認定 TDD 的研究(Borle 等,EMSE 2017)得放寬到晚一週提交也算才收得到樣本;Fucci 等(TSE 2017)發現順序本身沒有重要影響。不走這條。
- **AI 看得到實作,預期值就會照實作寫**:Konstantinou 等(2024/2026 v2)斷言「mainly capture the actual program behavior」;Charoosaei 等(2026)AI 測試 8–17% 把錯誤行為寫成預期值,其中 83–91% 之後一直通過。支持「預期值逐列寫需求來源」。
- **人工核可會鬆**:審查留言只有 14% 講缺陷(Bacchelli、Bird 2013);先看到 AI 的答案再問人對不對,人多半只看 AI 指的地方(Tufano 2024)。所以只對風險高的要簽,表要小,每列帶出處。
- 已被證明無效、這份計劃避開的:拿 XML 的 failure/error 分紅因;把 LLM 判官當唯一的閘(SWE 類任務上監看器只抓 42–50% 作弊,ImpossibleBench);只靠 TDD 提示詞(TDAD 預印本:回歸錯誤升到 9.94%);用提交順序證明先寫測試;簽核不綁內容(簽完再改預期值等於沒簽)。
- 設計審 r1(2026-11-04)後補查:GFM 表格規則裡格內 `\|` 是字面管線;欄數少於表頭補空格、多於表頭丟掉多的(本計劃不照這個寬鬆做法,見 PRIOR-ART)。

## 做法

### 第一批(本次實作):風險高設計審過後套先紅,加預期值表與簽核

1. **先紅模式**:
   - 規格閘在門判出風險高之後,讀這份計劃的設計審判定檔(讀法照 `_codeloop_pass_read_verdict` 的形狀檢查:讀不懂、路徑不安全、`verdict.rc` 不是整數都當「沒過」),再看迴圈首筆帳是否不早於生效時間;三樣都成立才進先紅模式。
   - 先紅模式下,`_spec_gate_front` 對風險高也算 keeps、跑 `_spec_gate_twoway_static`;跑完測試後走 `_spec_gate_twoway_run_verdict`,沒過交給 `_spec_gate_low_not_red` 印同一套補紅燈做法(訊息裡的「風險低」改照模式講,最後一句「改成 plan_risk: high 走設計審」在先紅模式不印)。全部過了寫留痕:`plan_risk` 照記 high,多一欄 `red_first: true`;印「PASS(風險高,設計審已過、先紅已驗)」。
   - 不在先紅模式的風險高計劃照舊紅綠只印不擋;印紅綠那行後面多一句:設計審過了之後,實作前要再跑一次規格閘拿先紅。
   - 零條款、平台設定讀不動這兩條提早結束的路,先紅模式比照風險低回 1(現在風險高回 0);沒有可跑測試、全靠人驗的條款(全部 `[manual:]`),先紅模式放行、留痕照寫(`manual_only`),不套風險低的小改動閘——那道是給沒人審的風險低計劃的,這裡條款已經過設計審。
2. **推送前把先紅模式的計劃當風險低查**:
   - `_spec_gate_push_scan` 判「走全套」的條件,從「最新留痕風險低」放寬成「最新留痕風險低,或最新留痕帶 `red_first: true`」;之後同一支 `_spec_gate_push_one`:條款指紋過期要重跑、留痕裡的測試全綠才放、起點已 done 的寬待、兩本帳合併讀,全部照舊。
   - `_spec_gate_push_stale` 現在要求門重判仍是風險低;帶 `red_first` 的留痕改成門重判是高是低都算數(只比條款指紋)。

3. **預期值表**(只對先紅模式的計劃):

第二批要實際跑 Gradle,得先在 Android 考場試跑才定得了細節;本計劃只定方向與已知的坑,不寫驗收條款。

7. **紅要紅在斷言上(Kotlin/Java)**:設計審 r1 已抓到的坑,第二批照這些設計(卷證在 `governance/review-reports/高風險測試證據加嚴/`):

9. **CI 對改到的行跑變異測試**(風險高計劃):
   - 照 Google 的三條:只變異改到而且有測試覆蓋的行、每行最多一個變異、跳過不值得測的地方(log、analytics、逾時常數)。Google 的數字:每個改動的變異數中位數全量 820、每行一個 77、再去掉不值得測的剩 7(Petrović 等,TSE 2021)。
   - 擋的是「每個活下來的變異都有處置(補測試殺掉,或附理由放行)」,不擋分數百分比(Google 不擋;flaky 讓分數平均飄 4 個百分點,Shi 等 ISSTA 2019;分數跟抓真 bug 的相關性控制測試數後是 weak,Papadakis 等 ICSE 2018)。
   - 放行紀錄綁檔案、行、變異寫法與程式指紋,程式改了就失效;「改到行卻 0 個變異」要報出來,不當通過。另放一個一定要被抓到的植入變異當自檢,防變異根本沒套上。
   - 只能跑本機單元測試(src/test);跑在手機上的測試沒有工具支援。工具選擇見待決問題。
