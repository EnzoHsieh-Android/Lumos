我查證了三件事:

## F1 證據檔沒有任何大小、數量、總量上限
- 位置:〈實務隱患〉資源行、〈二〉證據圍欄。
- 引句:「資源:閘門每次推送要讀全部登記護欄引用的證據檔;沿用盤點的單檔與總量上限,超限判讀取不完整並擋。」
- 問題:「盤點的上限」只管 Markdown(2 MiB、64 MiB 總量、10000 檔),證據檔(JUnit、SARIF、k6 摘要、capture 目錄)不在其內。
  - 沿用 test_quality 的 `read()` 才有 10 MiB 單檔上限,但 spec 沒這樣寫。
  - SARIF、k6 摘要的讀法是新寫的,沒有任何上限。
  - tq_capture 的 snapshots 筆數沒有上限。
  - 整批證據讀取沒有總量預算,也沒有牆鐘上限。
- 具體例:1000 條護欄 × 10 份證據,每份 10 MiB,理論上要讀 100 GB。
  - 預期:超過預算就擋並指出是哪個檔。
  - 照 spec 會得到:「沿用盤點上限」無法套用,實作者要自己發明數字。spec 自己寫「實作時量一次再定上限」,但 S1–S30 沒有任何大輸入條款。
- 另一個缺口:「超限判讀取不完整」對應的代碼只有整道的 `read_incomplete`,而該代碼是描述盤點 vault 讀取的。一個超大的證據檔會讓全部護欄一起被擋,不是只擋那一條。
- 修法:spec 要寫死單檔上限、全批總量、筆數上限,並寫明超限只判該條該種類 invalid(新代碼 `evidence_too_large`)。要加一條 S 條款(大輸入、超限各一份)。
severity: major
- blocking: 是(不改,實作者會做出可被大檔拖垮或整道誤擋的閘)

## F2 同一份證據檔被多條護欄重複解析
- 位置:〈二〉鍵名表。
- 引句:「涵蓋的護欄 id 與 revision;一項只對一條護欄」
- 問題:一項只對一條護欄,所以專案級的一份 JUnit 報告(常見是整個 gradle test 一份)要被每條護欄各引一次,同一份檔每次都重新解析。
- 具體例:一份 10 MiB JUnit 被 1000 條護欄各引一次,`junit()` 就解析 1000 次(每次都 `root.iter()` 多趟加 `validate_suite_counts`),加上每項各驗一次 blob。
  - 預期:同一次判定內,以 (path, git blob) 為鍵只解析一次。
  - 照 spec 會得到:「每項獨立判」的字面實作,時間隨護欄數線性乘以檔大小。
- 修法:spec 寫明判定內以 (path, blob) 為鍵快取解析結果,並加一個大輸入條款。
severity: major
- blocking: 是(spec 的圍欄結構會逼出這個共用形狀,不寫快取就是實作者的二次方陷阱)

## F3 git 子程序與 blame 的成本沒有預算,`revisions` 還會無限累積
- 位置:〈二〉綁版本;〈四〉例外核准用簽章金鑰。
- 引句:「找出最後改到那幾行的每個提交」
- 問題一:綁版本是「閘門用 git 讀那個提交裡每個綁定檔的 blob」。
  - 護欄數 × 證據數 × 綁定檔數(家節點 about_code 全部列入,可到數十支)都是各自一次 git 呼叫的量級。
  - spec 沒說批次化(`ls-tree`、`cat-file --batch` 一次取)。
- 問題二:blame 是「對每條」例外列各跑一次。
  - 同一個 Systems 節點有多條例外時,同一個檔被整檔 blame 多次,沒說用 `-L` 或一檔一次。
  - `revisions` 陣列是只增不減的(被刪條目的紀錄要「留在原 Systems 節點」),每次推送都得為全部歷史紀錄 blame,沒有修剪規則。
  - 〈四〉說起點版要「跑同一支盤點函式」,卻沒說起點版的 vault 怎麼取出來(逐檔 `git show` 或 `archive`),成本一樣沒寫。
- 具體例:一個 10000 檔 vault,起點版與要推的版各掃一次,加上 1000 條護欄 × 數十綁定檔,在 pre-push 路徑上會是數萬到十萬級的 git 子程序。
  - 預期:批次讀取,時間與檔數近似線性,有預算。
  - 照 spec 會得到:實作者各寫各的 `git` 呼叫,pre-push 變慢,CI 的 20 分鐘工作上限也有風險(ci.yml 該工作是 `timeout-minutes: 20`)。
- 修法:spec 寫明用批次讀取、blame 一檔一次且只涵蓋例外與 revisions 行,並給 `revisions` 的修剪條件(已 retire 且超過 N 天可移除)。
severity: major
- blocking: 是(閘在每次推送的熱路徑上,成本沒界定就會做出慢到被人繞過的閘)

## F4 重試路徑會讓使用者簽的提交失去簽章
- 位置:〈四〉例外核准用簽章金鑰,驗章段。
- 引句:「任一個不成立,那條例外不算數,原因代碼」
- 問題:驗章是對 blame 找到的「最後改到那幾行的提交」。使用者簽的提交一旦被重寫,簽章就不在了,或 blame 改指向未簽的提交。
  - `git pull --rebase`、`commit --amend`、推前壓成一個(CLAUDE.md 規定「做到一半的本機提交,推之前壓成一個」),都會以新的 committer 重寫提交。
  - 重寫後不帶簽章,除非使用者每次都再簽一次。
  - 合併提交(merge commit)也會讓 blame 落在未簽的合併提交上。
- 具體例:使用者簽了例外提交 C1,AI 之後把分支壓成一個提交推送;或推送因非快轉被拒,AI rebase 後重推。
  - 預期:使用者核可過的例外在重試後仍有效,或至少明確告知要重簽。
  - 照 spec 會得到:`exception:exception_unsigned`,底下種類照原判定被擋,而訊息只說「沒簽章」,沒指出是被重寫所致。
- 另一個格式化問題:AI 之後對同一個節點做任何改動這幾行的動作(格式化、`lumos regen`、縮排調整),也會讓 blame 改指向 AI 的提交,已核可的例外無聲失效。
- 修法:spec 要寫明這些重寫情境的行為。
  - 例如:例外列內容(去除空白後)的雜湊綁在簽章提交裡,驗「該列內容的最早引入提交被簽」,而不是逐次 blame 最後修改者。
  - 或明寫「重寫後必須重簽」,並讓擋下訊息指出原因。
  - 目前的 S26 沒有 rebase、squash、merge 的樣本。
severity: major
- blocking: 是(不改,最常見的重試動作就會讓核可無聲作廢,使用者以為例外在、其實擋著)

## F5 沒登記的專案每次推送也要付兩次全 vault 掃描
- 位置:〈四〉位置段與不受影響段。
- 引句:「但**排在所有放行早退之前**」
- 問題:判斷「有沒有資安登記痕跡」要掃要推的版本與起點版兩份 vault。這一步排在所有早退之前,等於把原本幾乎零成本的早退路徑(取不到 HEAD、merge-base 等於 HEAD 等)全部加上整 vault 掃描。
- 具體例:一個 10000 檔 vault 的專案,連 `merge-base 等於 HEAD` 這種空推送都要掃兩份。spec 沒給「快速判無痕跡」的路徑,例如先以 `git grep -l` 找 `lumos-security-v1` 與 `flag/security-relevant`。
- 修法:寫明先用 `git grep` 做廉價的痕跡預檢,有痕跡才跑完整盤點。
severity: minor
- blocking: 否(只影響速度,不影響判定正確性,但實作者可能直接掃兩遍)

## F6 治理帳寫入在重試下不冪等
- 位置:〈四〉例外核可與記帳;〈二〉fault_sensitivity 的本機背書。
- 引句:「用到例外的每次推送,在治理帳記一行(護欄、種類、到期日、核可決策)」
- 問題一:推送被拒、鉤子重跑、`--keep-going` 多道各記,每次重試都附加一行。治理帳是 append-only,會無限增長,而 spec 沒說冪等鍵(護欄、種類、提交)。
- 問題二:這一行寫進工作樹的治理帳,而治理帳已被修改但不在要推的提交裡。
  - 目前 gitStatus 顯示 `docs/.governance-log.jsonl` 就是 M 狀態。
  - 這違反推前「先看 git status」的規矩,又與「推送以提交為準」衝突。
- 問題三:資安背書「閘門只讀治理帳那一筆」,多筆時讀哪一筆沒定義。
- 修法:寫明冪等鍵、同鍵不重記,以及多筆時取 head_sha 相符的最新一筆。
severity: minor
- blocking: 否(帳會髒會長,但不改判定結果)

## F7 時序判定的時鐘定義不全
- 位置:〈二〉依賴掃描結果跟著漏洞庫變;〈四〉例外核可與記帳;〈一〉的 S28。
- 引句:「每次判定都用當天日期重算,過期隔天自動恢復擋,不需要任何人去改狀態。」
- 問題一:「今天」的時區沒定義。
  - 本機是台北時間,CI 是 UTC;台北每天 00:00 到 08:00 這八小時,兩邊的日期不同。
  - 到期日當天或隔天的邊界,本機放行、CI 擋(或反過來)。
  - 這與〈四〉「本機與 CI 判定完全相同」與 S28 的宣稱互相矛盾。
- 問題二:`observed_at` 沒有「不得晚於現在」的檢查。例外有「核可日晚於今天」的檢查,證據沒有。
  - 填未來時間的證據永遠不會 `vulndb_stale`。
- 問題三:`vulndb` 欄位允許「漏洞庫版本或抓取時間」。若填版本號,就算不出幾天,`vulndb_stale` 的判法未定義。
- 修法:寫明用 UTC 日期、`observed_at` 不得晚於現在或晚於要推的提交時間、`vulndb` 只收抓取時間(ISO 8601)。
severity: minor
- blocking: 否(S25 的固定日期接縫只測一個時鐘,不會發現這些)

## F8 判定函式崩潰或逾時的行為未定義
- 位置:〈四〉擋下條件;〈原因代碼〉整道判不清列。
- 問題:證據是不可信資料。深層巢狀 JSON 會讓 `json.loads` 拋 RecursionError,巨大 XML 可能耗盡記憶體,SARIF 欄位型別錯誤會拋 TypeError。
- 具體例:spec 的「整道判不清」代碼表只有 `read_incomplete`、`registration_error` 等盤點層代碼,沒有「判定函式自己崩潰」的對應。
  - 預期:任何未預期例外都轉成擋下,帶 `evaluation_error` 之類的代碼,並指出是哪份證據。
  - 照 spec 會得到:實作者各自決定,可能是整個 pre-push 拋 traceback、可能是放行。
- 修法:寫明例外一律 fail-closed,並加一個巢狀深度與案例數上限(與 F1 同組處理)。
severity: minor
- blocking: 否(風險在實作疏漏,spec 補一行就能杜絕)
