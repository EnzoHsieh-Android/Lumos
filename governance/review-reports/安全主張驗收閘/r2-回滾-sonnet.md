severity: major

審查席:回滾-sonnet,第 2 輪。我盤點的會擋推送、寫治理帳、凍結或重算判定的入口有 8 個:
1. `code-loop check` 的安全判定(分支與 tag 兩條路徑)。
2. `gate: warn` 設定。
3. 例外與修訂紀錄。
4. 公鑰清單與 `.sig`。
5. `security backing` 寫治理帳。
6. 例外用到時的記帳。
7. 起點是 merge-base 的凍結比對。
8. CI 的 `before` 起點。

先給白話結論:這份設計的「煞車」(簽章降級)本身有三個洞。降級簽章可以被重放。第一次釘金鑰沒有驗證。有幾種整道擋下用不了降級。

### 1. 降級簽章與修訂紀錄無期限、無專案綁定,簽過一次就永遠能重放
- 位置:〈四〉的〈擋或只提醒的設定〉、〈核可修訂紀錄〉。
- 問題:`gate_setting` 的簽章內容只有 `type`、`value`、`approved_on`。沒有 `expires_on`,沒有 repo 或專案識別,也沒有 nonce。修訂紀錄也沒有期限,而且規格明說可以直接刪舊紀錄。
- 具體例:
  - 使用者為了過渡期(Q4)簽一次 warn。後來他把設定改回 block,AI 從 git 歷史把那個簽章物件貼回 `.lumos/config.json`,驗章用 merge-base 版公鑰仍然通過,閘門被靜默關掉。使用者沒有任何方式撤銷已簽過的物件,除非換金鑰。
  - 修訂紀錄同理。「X 從雜湊 H1 刪除」被核可過一次。之後 X 以同樣的 H1 重新登記,AI 貼回舊紀錄,X 再次被合法刪掉。
  - 同一把金鑰釘在兩個專案時,warn 簽章可以原封不動貼到另一個專案。
- 與規格的衝突:母計劃 d9 的 30 天上限只套在例外上。降級設定是比例外更大的放行,反而沒有期限。
- 佐證:
引句:「這份設定要有 d7 的內容簽章」
引句:「舊紀錄可以直接刪,刪了只會少一筆可用的核可,不會放寬」
- 照 spec 實作會得到:能永久重放的降級與刪除。
severity: major
blocking: 是
判準:照字面實作會做出一個「簽一次就能被 AI 無限次重用」的放行機制,等於做出壞系統。

### 2. 第一次釘金鑰沒有任何驗證,釘壞了就是死鎖
- 位置:〈內容簽章〉的〈第一次釘金鑰〉與〈清單本身的修改〉。
- 問題:第一次釘金鑰時 merge-base 版沒有清單,新清單「照收」,也沒有要求當場簽一筆、驗一筆。釘進去的格式錯、金鑰類型不收、貼成私鑰或貼錯行,都會單獨合進預設分支。之後要修清單,必須有 merge-base 版清單裡某把金鑰簽的 `.sig`。可是那份清單裡沒有一把能用的金鑰。
- 具體例:`.lumos/security-approvers` 第一版某行多了尾巴,`ssh-keygen -Y verify` 認不得。使用者想修,會得到 `approvers_change_unsigned`。warn 簽章也簽不出來,因為驗章一律用 merge-base 版清單。出路只剩 `--no-verify` 或回退工具。
- 佐證:
引句:「新清單照收,但在它進到預設分支之前,用它簽的東西都不算數」
引句:「因為驗章一律用 merge-base 版的清單」
- 缺少的東西:「釘之前先用新清單當場做一次簽與驗」的步驟或指令(`security payload` 只印要簽的內容,沒有自檢)。也缺「merge-base 版清單裡一把有效金鑰都沒有時,視同沒有清單」的規則。
severity: major
blocking: 是
判準:上線順序第 3 步的人工操作沒有自驗,打錯一個字就把整個專案的例外、降級、修訂永久鎖死。

### 3. 回退一節宣稱「其他判不清的由使用者簽降級設定」,但有幾類整道擋下根本簽不出降級
- 位置:〈回退〉、〈擋或只提醒的設定〉、〈四〉的〈起點一律是 merge-base〉。
- 問題:降級簽章要用 merge-base 版的公鑰清單來驗。下列情況這份清單拿不到,或設定讀不到:
  - `freeze_base_unavailable`:預設分支存在但沒有共同祖先,例如孤兒分支、搬庫、改寫歷史後。
  - 空樹起點:新 repo 的根提交就帶登記。起點是空樹,沒有任何金鑰可驗。
  - `commit_unavailable`:拿不到要推的提交,config 也讀不到。
  - `evaluation_error`:例外若發生在讀 config 或驗章的路徑本身,warn 也沒機會生效。規格沒有說 warn 在這個錯誤上是否覆蓋。
- 具體例:使用者用 filter-repo 清掉一個誤提交的祕密後重推。起點算不出,擋下 `freeze_base_unavailable`。回退段說簽降級設定,但驗章需要的清單正是那個算不出來的 merge-base 版。
- 佐證:
引句:「其他判不清的由使用者簽降級設定」
- 缺少的東西:每個整道代碼要逐一標明降級有沒有效、用哪一版清單驗。至少要規定這幾類是否改讀預設分支遠端 tip 的清單。
severity: major
blocking: 是
判準:誤擋時實作者會照回退段排除路徑,結果幾類擋下沒有出路,只剩 `--no-verify`。

### 4. 治理帳的新閘名沒登記:背書與例外記帳會被靜默丟掉
- 位置:〈四〉的〈要跟著改的地方〉、〈證據從哪來〉的 ①、〈核可物件〉的記帳。
- 查證:`_gate_event` 對不在名單上的閘名「不寫,只印一行警告」。
  - file: `scripts/lumos:1540`,檢查 `_KNOWN_GATES`。
  - file: `scripts/lumos:11086`,名單本體。
  - 同一份名單也被「度量 <閘>.<種類>」的 retire 語法檢查用到,在 `scripts/lumos:4589`。
- 問題:改動清單裡沒有新增閘名(例如 security 背書、例外使用)的條目。
- 具體例:
  - `security backing` 跑成功,但帳沒寫進去。閘門之後永遠判 `missing:backing_missing`,guard kill 這條路完全走不通。
  - 例外用到時的記帳(S24 要「記一行」)同樣被吞掉。「寫不進不改判定」是既有政策,所以放行了卻沒有稽核痕跡。
  - 規格也沒有要求 `t_gov_stats_gate_drift` 那類漂移釘子同步。
- 補充:`security backing` 要寫成「閘門讀得到、CI 也讀得到」的帳,就必須是版控帳,不能落在 `GOV_LOCAL_LOG_NAME` 白名單分流。規格沒講。
severity: major
blocking: 是
判準:照 spec 字面實作,背書帳靜默寫不進去,整條 fault_sensitivity 路徑永遠擋。

### 5. 閘門讀治理帳的來源沒定,本機與 CI 會不同答案
- 位置:〈證據從哪來〉的 ①,〈四〉的〈輸入〉、〈從提交樹產快照〉。
- 問題:快照一節明說「不讀工作目錄」。可是背書帳寫在 `docs/.governance-log.jsonl`,是剛寫、尚未提交的工作目錄行。`_ledger_lines` 只是切行函式,既有讀者(例如 `scripts/lumos:16059`、`33358`)都是直接讀工作目錄的檔。規格沒說閘門是從要推的提交樹讀,還是從工作目錄讀。
- 具體例:使用者跑完 `security backing` 後,帳還沒提交就推 X。若實作者讀工作目錄,本機放行。CI 讀提交樹,看不到那一行,判 `backing_missing`。紅燈出現在已進主線之後,而且 S28 要求的「本機與 CI 判定完全相同」被破壞。
- 佐證:
引句:「閘門(本機與 CI)只讀治理帳那一筆,不讀 kill-log」
- 缺少的東西:明寫「從要推的提交樹讀帳」。S37/S38 要加一個「帳未提交」的反例。
severity: major
blocking: 是
判準:字面實作時兩種讀法都說得通,選錯就做出本機放行、CI 事後紅的壞系統。

### 6. 背書帳:冪等鍵擋住更正、4096 位元組截斷、沒有撤回
- 位置:〈證據從哪來〉的 ① 與「背書的冪等鍵」。
- 問題:
  - 「同鍵已有一筆就不再寫」。若第一筆是工具缺陷造成的錯判,同一個 head_sha 上無法重寫更正。
  - 帳只增不減。錯的那一行對之後所有「只動簿記檔」的提交一直有效,直到有新 head_sha 的新行覆蓋。
  - `_gate_event_fit` 在整行超過 4096 位元組時會從尾端丟清單欄,並加 `_truncated` 旗標(file: `scripts/lumos:1584`)。背書行要帶「配方改到的檔」清單。檔很多時清單被截掉,閘門拿截短的清單去比 `bindings`,`kill_recipe_unbound` 會漏判。規格沒說看到 `_truncated` 要判 invalid。
- 佐證:
引句:「冪等鍵是(護欄、種類、head_sha),同一個提交重試推送不重記」
severity: minor
blocking: 否
判準:都有迂迴(改一個提交再重跑),但截斷漏判是安全面的小洞,實作者該知道。

### 7. 例外記帳每次推送都弄髒工作樹,會拖出連鎖帳本提交
- 位置:〈核可物件〉的記帳、母計劃的「過代碼審的功能多一個帳本提交」。
- 問題:規格寫「這一行留在工作樹、下次提交時帶上」,冪等鍵含 head_sha。帳本提交本身就是新的 head_sha。推送那個帳本提交又寫一行新的,於是只要例外還在,每次推送後工作樹都是髒的。
- 為什麼在意:這段期間每次推送都得再補一個帳本提交,或帶著髒工作樹推。這與「推送前先看 git status、有不是自己造成的改動要停下」的規矩直接衝突。誤擋救援期(最長 30 天)正是此時。
- 佐證:
引句:「治理帳是簿記檔,這一行留在工作樹、下次提交時帶上」
- 補救方向:鍵改成不含 head_sha(例如護欄、種類、核可日),或例外記帳只在「首次用到」時寫。
severity: minor
blocking: 否
判準:既有跳過類記帳也是這個形狀(有先例),只是變吵,不會做錯決定。

### 8. 回退的兩個提交切法不完整,降回 v1 的順序沒講
- 位置:〈回退〉,〈二〉的 ② test-quality 抽函式,〈一〉的 v1/v2 並存。
- 問題:
  - ① 與 ② 沒有收納這幾項,回退時可能只撤了一半:
    - `scripts/test_quality.py` 的純函式抽出。
    - `_TEST_QUALITY_BUNDLE_DIGESTS` 的雜湊更新。這兩個一旦不同步,既有的 `test-quality check` 對所有專案報「部署不完整」,不只對有資安登記的專案。
    - `_secinv_blocks` 參數化。
    - `_secinv_snapshot_tree`。
    - `_KNOWN_GATES`(見 4)。
  - 回退段要消費專案「先把 v2 圍欄降回 1」。可是 v1 讀法下 `threat_categories` 不存在,閘門會判護欄層 `threat_categories_missing`,例外蓋不掉。若此時 ② 還在,降級提交本身就被擋。這一段沒說清「降 v1 必須發生在撤 ② 之後」,唯一出路又是簽 warn。
  - `inputs_sha256` 包含 `threat_categories`。降回 v1 拿掉這個鍵,所有舊例外與修訂紀錄的簽章雜湊都變了。重新升回 v2 時要完全還原才驗得過,否則全部重簽。規格沒提醒。
- 佐證:
引句:「回退到舊工具之前,消費專案要先把 v2 圍欄降回 1」
引句:「撤回只是不再讀。」
severity: minor
blocking: 否
判準:順序可由實作者推得出,但漏掉會讓回退當場卡住,應在規格寫明。

### 9. 時間相依的判定與「同一提交永遠同一答案」不符,也卡住回退本身
- 位置:〈一〉的彙總規則最後一段,〈二〉的 `vulndb_stale`、`review_expired`,〈四〉的例外到期。
- 問題:規格寫「對同一個提交……永遠是同一個答案」。可是 `vulndb_stale`(14 天)、`review_expired`、例外到期都隨 UTC 日期變,同一個提交明天可能從 sound 變 unsound。
- 具體例:上線後出事,使用者要 `git revert` 回上一個已通過的狀態,或對舊 release 補打 tag 重新部署。那份舊證據的漏洞庫抓取時間已超過 14 天。回退用的提交被 `stale:vulndb_stale` 擋下,必須再簽例外才能退。
- 佐證:
引句:「永遠是同一個答案」
- 補救方向:承認這是時間相依。或明寫回退到曾通過樹的提交怎麼放行。
severity: minor
blocking: 否
判準:有簽章例外的出路,但這是會在最不方便的時刻發生的卡點,規格要承認。

### 10. CI 用 `before` 當起點,force-push 回退時會算不出
- 位置:〈四〉的〈起點一律是 merge-base〉。
- 問題:CI push 事件的起點是 `before`。用 `git push --force` 把主線退回舊提交時,舊 tip 不在 `fetch-depth: 0` 抓到的任何 ref 裡,大概率取不到。結果是 `freeze_base_unavailable`,而 3 已說明這一類降級簽不出。
- 影響:CI 變紅。主線已經退回去了,紅燈本身不擋任何東西,但會誤導後續判斷。依 d9,CI 本來就是事後的。
severity: minor
blocking: 否
判準:只是 CI 紅,不改變主線狀態;但回退場景的噪音應預先處理(例如取不到 `before` 時退用 `origin/<預設分支>`)。

### 已讀,無 finding 的部分
- 〈四〉的 tag 刪除:`scripts/hooks/pre-push:464` 對 `local_sha` 全零的 ref 直接 `continue`,刪 tag 與刪分支不會被 `--security-only` 擋下。
- 擋下原因對照表的五句與 `t_prepush_cl_reason_sentences_match_plan` 的同步順序(計劃那一行先改,再改掛鉤與常數):規格寫對了,已讀。
- 「沒有資安登記痕跡的專案行為不變」的早退:已讀,回滾面無額外風險。
- 〈二〉的證據讀法、格式判準、資源上限:屬他席鏡頭,本席已讀,無回滾面 finding。

### 風險類逐類結論
- 守衛面(放寬或收緊擋下判定):有。1(降級可重放,放寬方向)、3(降級無效,收緊方向)。
- 舊資料與舊帳相容:有。4(新閘名沒登記)、6(帳不可撤回)、8(降回 v1 的簽章雜湊失效)。
- 已在途分支要不要重新表態:無新增。金鑰輪替後,在途分支 rebase 到新 main,舊金鑰簽的例外會失效並需重簽,這是設計的預期行為,不報。
- 跟其他會談或其他計劃的交界:7(工作樹被治理帳弄髒,與 `git status` 規矩衝突)。
- 其餘再沒找到具體失敗場景,不硬湊。

最嚴重 severity:major,blocking 共 5 條(1、2、3、4、5)。
