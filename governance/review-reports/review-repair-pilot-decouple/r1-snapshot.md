# 代碼審修復穩定性試行_計劃

先把每次修復驗穩，再看是否比較容易收斂。使用者在 2026-10-03 對話同意先試行五次；「後輪問題通常由前輪修復引入」目前是使用者觀察，尚未逐案回放驗證。

PRIOR-ART: 借用現有先紅後綠、原席驗收、新席查差異及既有 intake 報告；Google Small CLs 建議縮小完整變更並保護既有行為（https://google.github.io/eng-practices/review/developer/small-cls.html）。最小改動落在 skill 說明，沿用既有報告，無新命令或相依套件。

RETIRE-IF: 第五次收尾時若紀錄成本高於找到問題的效益、資料無法支持改善，撤下試行入口或縮減欄位；證據不足不得宣稱有效，也不自動升格為永久要求。第五次收尾必交使用者裁決，未裁決不繼續擴大試行。

## 範圍與條款

- [S1] 當本 repo 新開符合下方分階段資格的程式工作時，編排者應於開工前在候選表領試行序號，首輪 intake 再記同一序號與 loop id，按資格與登記順序取五個不同工作；重開編號接續原工作序號，純文件審不佔名額，已領號後中止或達上限仍計一次，避免只挑成功案例。[manual: 對照兩階段資格、排除紀錄與五格登記表，檢查重開和中止例]
- [S2] 當採信真缺陷並準備修復時，編排者應先彙整相同根因並保留各 finding id，記錄根因、改變行為及保持行為；修復應具備壞例修前紅修後綠、好例修前修後綠及受影響回歸結果，既有測試可沿用，寫入或副作用情境另驗失敗路徑；不能執行則記未驗與原因，不以此取代既有放行判定。[manual: 用非法路徑被拒與合法中文空白路徑仍可用的案例推演]
- [S3] 當下一輪出現新 finding 時，編排者應以同一案例在修復前後版本的結果，分類為原有漏看、修復引入、新需求或偏好、待查；修復引入應連回前輪 finding 與修復版本。來源分類不改嚴重度與處置規則。[manual: 推演修前綠修後紅、兩版皆紅及環境不可用三例]
- [S4] 當進行修復驗收時，編排者應讓原席只驗其原發現，新席依既有編制檢查修復差異、上下文、呼叫者與測試，正式凍結材料與既有必派席覆蓋要求維持；同根因連續兩次修復引入問題時停止疊補丁，重估修法層次與範圍，三輪上限照舊，不另開隱藏審查輪次。[manual: 對照既有席位及上限，推演第三輪仍有真缺陷的情況]
- [S5] 當試行工作收尾時，編排者應在本計劃登記表補結果與報告指標，在表後逐案記修復引入缺陷數、根因修復組數、審查耗時及新增步驟耗時；每輪證據寫入尚未入帳的 intake，已入帳報告保持不動。第五次收尾或到期時彙整，缺值記未知。放行後缺陷沿用既有 escape 紀錄，觀測截止日與追蹤天數必記；五案不足以證明因果，不以三輪通過率單獨決定成效。[manual: 用已入帳 intake、缺耗時、中止與尚無放行後觀測期的案例推演]
- [S6] 當第2至5案要領號時，編排者應先按本計劃的改道生效時間與獨立工作資格判定，以本計劃候選表在程式修改／審查前完成的登記時刻作唯一「開工」時鐘，當場記納入或排除理由、協調者與狀態；納入者於首輪派工前再記基準提交與獨立乾淨 worktree。只取生效後依序登記的前四個合格新工作，不把探針未放行修補、續輪或真模型結果混入樣本。若資格或唯一寫入者無法判定，暫停領號，普通代碼審照舊。[manual: 推演探針續輪、獨立新修補、同一工作重開、同時領號及髒樹只切分支五例]

## 2026-10-04 收斂性診斷與下次試行的最小調整

這段只細化 S2／S3 的試行做法，不新增全域代碼審關卡，也不將儀器修補冒充五案樣本。[[Verification/2026-10-04_代碼審收斂根因盤點]] 用原審查卷證區分兩種浪費輪次的情況：第1案 R2C2 是已證「修前可用、修後壞掉」；R2C1 及 r3、r4 多項同例在修前後都壞，是修法未涵蓋的舊缺口。正式派工修補 r3 的 G11 已證跨日期舊缺口；G10、G12、G13、G16 先保持來源待查，不以審查輪次代替前後版實跑。前者需要保護保持行為，後者需要先把修法邊界找完整；兩者不能用同一個「增加審查輪」對症。

下一個已授權的新工作若遇到同一份資料有多個寫入、讀取或恢復入口，修補前在未入帳 intake 以一個小表列出「資料權威、寫入者、讀取者、失敗後狀態、跨時間／目錄邊界、對應反例」；資料權威欄記來源，每個受影響的寫入、讀取與恢復入口各配一個能從真入口執行的反例，或明記未驗與原因。先固定一個根因組、跑壞例和相鄰好例的前置條件，再做最小自足修補；沒有被反例覆蓋的跨入口承諾不放進當輪修補範圍。新席仍看完整受影響上下文與最後差異，不縮減既有資安或處置閘。這是 S2 既有「根因／改變／保持／失敗路徑」在多消費端情境的展開，不靠多派席位來補事前漏列的讀取路徑。

PRIOR-ART: Google 的 Small CLs 指南主張一個自足變更和相關測試，指出較小變更較易審且較易看出引入的 bug（https://google.github.io/eng-practices/review/developer/small-cls.html）；Martin Fowler 的重構實例以小步、行為保持和測試承接變動（https://martinfowler.com/articles/refactoring-external-service.html）。這些是修補範圍與配對測試的外部依據，不是本案流程有效的實驗結果；原試行單案與 1101 行 r3 快照也不能推出通用行數門檻。

RETIRE-IF: 下一個完成的新工作若顯示這張入口表沒有增加修前查到的消費端缺口，或填表成本超過它避免的補審時間，先撤此展開、保留 S2／S3 原試行；入口是本計劃第2案逐案紀錄的分類與實際起訖時間，第五案或 2026-11-03 再一起回顧。缺時間資料時標未知，不假造成本效益。

### 2026-10-04 改道：第2至5案量代碼審，不等探針

使用者在聽取 [[Verification/2026-10-04_代碼審收斂根因盤點]] 後同意，接下來先用不依賴探針的新程式工作測修復穩定性，不把 `code-probe-postreview-dispatch-ledger` 的第四輪或五小時額度帳當主工作。舊「探針可信後才續測」是當時取捨，不再是第2案前置。此改道只在新設計迴圈 `review-repair-pilot-decouple` 對**凍結的改道計劃快照**執行 `lumos loop status review-repair-pilot-decouple --disposal --spec <該版計劃> --repo .` 得到正式 PASS 後生效；原 `review-repair-pilot` 的舊 PASS 不算。新 [[Verification/2026-10-04_代碼審改道生效驗證]] 記 PASS、凍結檔 hash 與生效時刻，未有三者不得領第2案；後續只追加候選事件不冒稱重新審過設計。探針的正式 r3 FAIL、未折 major、真模型未量與禁止以其結果放行，仍由 [[Verification/2026-10-04_消融派工正式審查修正]] 管，不因改道消失。

第2至5案依生效後**候選登記時刻**依序取前四個合格工作；登記在任何程式修改或審查之前完成，與另用「首輪首次派工」起算的審查耗時是兩支不同時鐘。同一秒以持短鎖寫入的候選表先後順序裁。領號後中止仍佔一格，不能待審查結果出來才挑。合格指本試行唯一協調者接手的本 repo 新程式行為工作、尚未屬於既有 code-loop／其續輪、修補目的和驗收證據均不依賴未放行的探針／消融程式或輸出；現有 probe-postreview、code-repair-pilot 與其後續修補不合格。純文件、既有工作的改號續輪也不合格。候選登記時記時間、工作與當時的資格；若當時排除，記理由且普通代碼審照常。已領號後才改成探針相依或中止，仍保留該格並標範圍偏離／中止，不能事後從五案分母抹去難案。協調者沒有接手的其他 repo 工作不算本試行候選，最後回顧明示此取樣限制。這是有條件的前瞻樣本，五案僅作個案方向，歷史第1案與四件新工作分列，不合併聲稱因果改善率。

領號與唯一協調者仍在本計劃；新工作的程式、測試與完整 code-loop 審材須置於**另一個獨立乾淨 worktree**，先記基準提交與差異範圍，只在目前髒工作樹切分支不算隔離，因測試仍會載入未提交的探針草稿。第2案若找不到可核對的隔離基準或無法確認唯一領號者，先暫停領號，不把普通代碼審停掉。試行沿用 S2–S5 的同例修前後歸因、額外耗時與三輪上限；不啟動真模型探針，也不藉新案替 r3 做第四輪。

回顧比較修復引入缺陷、根因修復組數、總耗時、額外耗時與放行後缺陷。若取歷史對照，使用啟用前最近五個有程式改動的工作並記規模、分級與資料缺漏；無法可靠歸因時只列個案，不補零或硬算改善率。

耗時口徑：總耗時是首輪首次派工到最終問閘或明確中止的牆鐘分鐘，另列有起訖紀錄的暫停時間；跨 session 也保留起訖。新增步驟耗時記根因整理、好例驗證與來源分類的實際區間聯集，同時進行只計一次。席位分鐘不可相加當牆鐘分鐘；缺任一起訖則該項未知，不補估計值。兩席平行各 10 分鐘再驗收 5 分鐘，總耗時是 15 分鐘。

同一根因同一修復目的算一組，重試不增加分母；修復引入缺陷按去重後的具體錯誤行為計數，同一問題被多席報告只算一次，待查另列。完整 finding id 和證據留在各輪入帳前的 intake；已入帳後才取得的資訊寫本計劃逐案紀錄並指向原報告，不覆寫凍結證據。

證據接線：試行每輪有修復或來源分類紀錄時，載體席記帳必帶既有的 `--intake`；零發現且沒有載體席的輪次，擇一一般席帶入。每個 intake 只入帳一次，之後不可追加；補充資料在下一份未入帳 intake 或本計劃逐案紀錄標出時間與原證據指標。這是人工執行要求，工具本身不新增欄位檢查。
