# 新增告警閘_計劃

> 白話：讓檢查工具在每一次推送前真的跑一遍，而且**只擋你這次弄出來的新問題**，舊問題不管。誤報一定會有，所以放行的門第一天就要開好、而且走正式管道會留下紀錄。

## 現況：缺的比想像中少

| 已經有的 | 缺的 |
|---|---|
| 標準格式的橋（工具吐 SARIF、核心解析合併） | **現況**：自動路徑一律帶「不跑 linter」，只有手動敲才跑 |
| 按改動檔的副檔名挑該跑哪些命令 | **現況**：告警只拿來墊高風險分級，自己不會擋——本計劃 [S4] 就是要補上「自己會擋」這一層 |
| 跑命令、逾時保護、解析結果 | 沒有放行管道，誤報只能繞過整個檢查 |
| 把告警對到這次改動 | 對法是「行級過濾」，會靜默漏掉（見那篇事故） |

## 實測數字（2026-09-13，本機）

這些數字決定了下面幾條的門檻，不是拍腦袋定的：

| 量什麼 | 結果 | 影響哪一條 |
|---|---|---|
| 843 行的檔，151 條社群規則 | 1.8 秒（幾乎都是啟動成本） | 正常大小的檔沒有速度問題 |
| 26718 行的主程式，同一批規則 | **105 秒**，跑兩次就三分半 | [S6] 單檔大小上限變成必要配套 |
| 線上規則庫、未登入 | 可用，151 條規則，含下載約 2 秒 | 不需要帳號 |
| 沒有副檔名的檔（掃目錄時） | **靜默跳過**；明確指名就會掃 | [S1] 一定要傳明確的改動檔清單 |
| 基準比對對未提交改動的影響 | 不動改動、不動未追蹤檔、不建暫存 | 安全，但文件說「髒了會拒跑」與實際不符 |
| 首次真跑的命中 | 1 條，是誤報（對刻意設 0700 的目錄建議改成 0644） | [S5] 放行管道不能延後 |

## 條款

- **[S1] 宣告檔支援兩種基準模式，並且一定傳明確檔案清單。** 命令除了現有的輸出檔佔位，新增「基準版本」與「改動檔清單」兩個佔位；命令寫成物件時可以宣告自己會處理基準（工具內建的直接用它的），維持字串的就由核心代跑兩次。傳檔案清單同時解掉「沒有副檔名的檔被靜默跳過」。[test:t_lint_new_declaration]
- **[S2] 核心代跑兩次比差集。** 用 `git archive` 把基準版的改動檔與專案根的設定檔解到暫存目錄跑一次，再跑現在版一次，兩次都用現在這份規則。**不用 git worktree**——這個工作目錄同時有別的 session 在用，動 worktree 註冊表會互相干擾。解出來的位置放在專案設定目錄底下並加進忽略清單（跟既有的測試快取檔同一個慣例），**執行時的工作目錄仍然是專案根**，這樣檢查工具往上找設定檔時找到的是現在版的設定——基準版只提供「程式碼長什麼樣」，規則與設定一律用現在的。[test:t_lint_new_baseline]
- **[S3] 比差集用指紋，不用行號。** 指紋＝規則代號＋檔名＋命中處的程式碼片段；**工具沒給片段的，核心自己去讀那幾行補上**——基準版與現在版的檔案內容兩邊都在手上，照告警的起訖行取出來正規化即可；實測：社群規則庫會附片段，而 Python 那個主流檢查器完全不附（只給行號與欄號），所以「自己補」是常態不是例外。兩邊都取不到行號資訊才退到最後一招：規則代號＋檔名＋訊息的出現次數比對（新版比舊版多出來的算新增）。行號本身會因為上下文位移而變，任何情況下都不能當身分。[test:t_lint_new_fingerprint]
- **[S4] 第四道判定。** 在代碼審那一關的判定序列裡，排在表態之後、留痕之前（便宜的檢查先跑）。有未放行的新增告警就擋，訊息列前幾條並附放行指令。[test:t_lint_new_gate]
- **[S5] 放行管道。** 一條指令把某個指紋標成已放行，要寫理由；紀錄進專案裡的放行檔（跟著 git 走，團隊看得到）並記一筆治理帳。**綁指紋不綁版本**——綁版本的話每次提交都要重新放行，吵到沒人會用。代價是放行永久有效，所以健檢要數「這個專案放行了幾條」。[test:t_lint_waive]
- **[S6] 單檔大小上限。** 超過上限的檔不掃，並且**明白說出來**「這支檔幾行、超過上限多少、所以沒掃」，計入「有東西沒跑到」。預設值依實測訂（正常檔 1.8 秒、26718 行 105 秒，上限取四千行留餘裕），可在設定檔調。[test:t_lint_oversize]
- **[S7] 跑不動一律不靜默放行。** 工具沒裝、逾時、沒網路拉不到規則、檔太大——四種都判成「有東西沒跑到」，要留痕說明才過，跟合約測試跑不動同一套規矩。[test:t_lint_undone_note]
- **[S8] 整條閘有時間預算。** 超過預算就停、明說停在哪、這次放行（跟表態那關同款），避免把推送前那關從十一分鐘拖成不可用。[test:t_lint_budget]
- **[S10] 改名的檔要用舊路徑取基準版。** 版本控制把改名看成「刪一個、加一個」，照字面做的話**改名一個大檔等於它全部的告警都變成新增**，整批擋人。要開啟改名偵測，改名的檔用它在基準版的舊路徑取內容。[test:t_lint_rename]
- **[S11] 工具鏈自己要接上，否則交付即零實證。** 這個 repo 目前一個檢查工具都沒宣告（健檢的第 F 項已經在唸了），所以閘做完也不會對任何東西生效。交付要包含替這個 repo 宣告檢查工具——**但這需要在這台機器上裝東西，屬於人的決定，不自作主張**。[manual:問過人再裝,裝完跑冒煙驗證]
- **[S9] 翻案與文件同步。** 推翻「擋推鏈恆不跑 linter」那條裁定並寫明翻案理由；同步代碼審的 skill、指令速查、上手文件、兩份 README 的說明。[manual:文件同步逐項核]

## 刻意不做

- **不接管 linter 的安裝。** 消費專案自己裝、自己宣告，核心只認格式——這是既有定位，不動。
- **不做離線快取。** 人裁「不管離線」，沒網路就判跑不動、留痕。
- **不按嚴重度分級擋。** 嚴重度是各工具自己標的、跨工具不一致；判準只有「是不是這次新增的」。
- **不動那四十四題棧別提問。** 規則跟提問分工不同，兩邊都留。

## 實務隱患

逐類答，判「不碰」也要寫理由：

- **資源（暫存目錄）**：解基準版程式碼要落到暫存目錄，跑完必須清乾淨。做法：用系統暫存目錄建一個帶前綴的目錄，**用 try/finally 保證清理**，逾時被砍也要清；清不掉就印出來讓人知道有殘骸，不靜默。
- **資源（子行程）**：跑檢查命令是開子行程。沿用現有那條路的既有保護（獨立行程組、逾時到就整組砍掉），不自己再造一套。
- **併發（多 session 共用同一個工作目錄）**：這台機器上同一個 repo 同時有別的 session 在用。**所以不准用 git 的工作樹註冊機制**（那是全域狀態，會互相干擾），改用「把基準版的檔案解出來」這種不留痕的方式。這條是 [S2] 的主要理由。
- **效能**：整條閘有時間預算（[S8]），單檔有大小上限（[S6]），超過都明說不靜默。推送前那關已經十一分鐘，加上去的秒數要實測。
- **併發（放行檔的寫入）**：放行紀錄是一個跟著 git 走的檔，兩個 session 同時寫會互蓋。沿用這個 repo 既有的「寫暫存檔再原子換名」慣例，不做半套。
- **不碰的類**：金流、對外寄送、正式環境不可逆操作——這個計劃一項都不碰，純粹是本機與 CI 的檢查流程。

## 誠實邊界

- **零真專案實證。** 上面所有數字都是在工具鏈自己這個 repo 上量的。誤報率、實際擋下什麼、放行比例，要等第一個消費專案接進來才知道。
- **本 repo 的主程式不會被社群規則覆蓋到**——它兩萬六千行，超過單檔上限。這是刻意的取捨（不這樣做推送前那關會多三分半），但意思是工具鏈自己的核心檔只有快的那些檢查看得到，這一條要寫進交付說明，不要讓人以為全 repo 都被蓋住了。
- **新檔與搬檔會整批算新增。** 一個在基準版不存在的檔，它所有的告警都算新增。從別處搬進來的舊程式碼會一次擋一大批，只能靠放行管道處理。這是「只擋新增」這個判準的固有代價，不是 bug。
- **放行永久有效**是已知的設計缺口：數量會累積，只有健檢會唸。真的變成問題再加期限。
