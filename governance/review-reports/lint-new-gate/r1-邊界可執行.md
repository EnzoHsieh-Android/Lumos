severity: blocker

# 新增告警閘_計劃 — 邊界可執行性審查（極端輸入鏡頭）

姿態：只問「不正常的輸入」——空的、只有一個的、超大的、卡在界線上的、名字很怪的、指令會不會被格式化壞掉的。以下每條都在 repo 裡查過現有程式碼的對應行為當對照組，不是憑空猜。

## Finding 1：單檔大小上限用「行數」當單位，對沒有換行的單行大檔完全失效

- spec：[S6]
- blocking: 是——判準是「這是必要配套不是選配」，單位選錯會讓配套形同虛設，回到 105 秒/檔的原始風險。
- 情境：一支被壓縮過的 JS（webpack bundle）或某些產生出來的檔，全檔只有 1 行（沒有換行字元），但實際位元組數與正常的 26718 行主程式相當甚至更大。照 [S6] 字面，「行數」量出來是 1，遠低於四千行門檻，於是**不會被判定為超大檔、照樣送進 semgrep 掃**——而 spec 自己 2026-09-13 的實測已經證明「跑兩次就三分半」的風險來源是解析成本隨內容量超線性增加，不是行數本身。凡是這種檔（本鏡頭被明確要求逼問的「壓縮過的 JS、產生出來的檔」），大小上限機制對它們就是擺設。
- 查證：spec 自己在「實測數字」表格裡把「843 行的檔」與「26718 行的主程式」相提並論，把行數當成內容量的代理指標，但沒有度量過等量位元組、極少行數的情況；`_lint_run_and_parse`（`scripts/lumos:17156` 起）本身不做任何檔案長度前置檢查，交給宣告的命令自己吃整個檔案，沒有可以攔截「行數騙人」這種輸入的既有機制可以借用。

引句:「預設值依實測訂（正常檔 1.8 秒、26718 行 105 秒，上限取四千行留餘裕），可在設定檔調。」

severity: blocker

## Finding 2：核心用單一 `git archive` 呼叫取基準版，只要改動檔裡有一個新檔，整批基準版擷取就會 128 失敗

- spec：[S2]
- blocking: 是——這不是罕見情境，是「一次提交同時新增一支檔、修改另一支檔」這種每天都會發生的普通改動；一旦踩到，S2 整條「代跑兩次比差集」機制對這批檔案全部失效，不是只有那支新檔失效。
- 情境：改動檔清單 = [existing.py（修改）, brand_new.py（新增，基準版不存在）]。照 [S2] 字面「跑一次」（單一批次呼叫）解出基準版內容，實際執行 `git archive <基準版> -- existing.py brand_new.py` 時，只要清單裡有一個 pathspec 在該 rev 不存在，git 直接整條指令 fatal 失敗、不吐出任何內容——不是「那支新檔跳過、其他照跑」，而是**這批檔案的基準版全部拿不到**。
- 查證：我在乾淨的臨時 repo 實測重現：`git archive HEAD~1 -- existing.txt brand_new.txt` 對「existing.txt 在兩版都有、brand_new.txt 只在後一版新增」的情境，回傳 `fatal: pathspec 'brand_new.txt' did not match any files`，退出碼 128，且沒有任何部分輸出。spec「誠實邊界」段落雖然承認「新檔會整批算新增」是判準的固有代價，但那是在討論*語意*（新檔的告警怎麼算），完全沒討論*機制*會不會直接連基準版擷取這一步都做不下去——兩者是不同層次的問題，前者 spec 已表態接受，後者 spec 沒發現。

引句:「用 `git archive` 把基準版的改動檔與專案根的設定檔解到暫存目錄跑一次」

severity: blocker

## Finding 3：新增的「改動檔清單」佔位符沒有講清楚多檔案要怎麼跳脫，套用既有的單值 `shlex.quote` 慣例會把整批檔名併成一個參數

- spec：[S1]
- blocking: 是——如果照現有唯一先例的模式實作（單一佔位符對單一值做 `shlex.quote`），對帶空白或特殊字元的檔名會產生一個語意完全錯誤的指令，而不是「跑不動、明說」這種可控的失敗。
- 情境：改動檔清單裡有一支檔名帶空白（例：`docs/lumos-toolchain-knowledge/Projects/OpenSpec 調研.md` 這種風格，或消費專案裡真的用空白命名的檔）。若沿用 repo 目前對佔位符替換的唯一寫法——`cmd.replace("{PLACEHOLDER}", shlex.quote(單一值))`——套在一份「先把多個檔名接成一個字串,再整串丟給 shlex.quote」的實作上，得到的是把好幾個檔名黏成**一個**帶引號的參數丟給 linter，等於檢查工具只看到「一個檔名」（內容是好幾個路徑接起來的怪字串），其餘檔案完全沒被檢查到，而且沒有任何錯誤或提示——沒跑到卻沒留痕，正是 [S7] 想擋的那種「靜默沒跑到」，但 [S1] 本身完全沒提這件事怎麼處理。
- 查證：全檔搜尋 `shlex.quote(` 的每一個既有用法（`scripts/lumos:17176`、`9230`、`24040`、`24087`、`783`、`8366`、`8561`、`15275`）無一例外都是「一個佔位符對應一個字串值」，repo 裡沒有任何「一個佔位符對應一份檔案清單」的先例可以直接照抄，[S1] 又沒指定要怎麼組這份清單（`shlex.join` 逐檔跳脫，還是先 join 再整串 quote），這是一個沒被寫進 spec、但確定會被實作到的分岔點。

引句:「命令除了現有的輸出檔佔位，新增」

severity: major

## Finding 4：指紋比對的主要方法沒講「同一指紋在同一檔命中多次」時怎麼配對，只有退到最後一招的次數比對才提到用「出現次數」

- spec：[S3]
- blocking: 是——這個缺口的方向是危險的：同一條規則在同一檔多次命中且片段相同時（例如同一段被複製貼上兩三次），如果指紋庫是用集合（有/無）而非計數（幾次）判斷新舊，從「基準版有 1 個這種指紋」變成「現在版有 3 個這種指紋」會被判成 0 條新增，兩個真正的新問題被吃掉、閘不會擋——比誤擋更糟。
- 情境：基準版某檔第 40 行有一段觸發規則 R 的程式碼，現在版把同一段複製了兩次（第 40、80、120 行內容相同）。三處的指紋（規則代號＋檔名＋正規化後片段）完全相同。若比對邏輯是「這個指紋在基準版出現過嗎」的布林判斷，答案是「有」，於是全部 3 處都判成舊有、不擋；但實際上有 2 處是這次新引入的。
- 查證：[S3] 描述主要方法時只講「指紋＝規則代號＋檔名＋命中處的程式碼片段」如何組成，通篇沒有一句提到「同一指紋出現次數要不要比對」；反而是講到「兩邊都取不到行號資訊」的**最後一招退路**時才明講用「出現次數比對」。主要方法與退路方法在「要不要算次數」這件事上語意不一致，spec 沒有解釋這個落差是有意的還是漏寫。⚠ 這條的嚴重度取決於實作者會不會把主方法也隱含做成 multiset——spec 文字本身讀不出答案，故標記給編排者再核。

引句:「兩邊都取不到行號資訊才退到最後一招：規則代號＋檔名＋訊息的出現次數比對」

severity: major

## Finding 5：「工具沒給片段就自己去讀那幾行補上」沒處理行號是 0、負數或超出檔案長度的情況——而現有程式碼已經示範過這種輸入會發生

- spec：[S3]
- blocking: 是——這條路徑（自己補片段）被 spec 自己定性為「常態不是例外」（因為主流 Python 檢查器完全不附片段），所以這裡沒處理好，受影響的不是邊角案例而是大部分 Python 告警。
- 情境：某條 SARIF 結果沒有 `region` 欄位（工具沒回報行號範圍），現有的 `_lint_run_and_parse` 對這種輸入已經有明確且已驗證的行為：v1 與 v2.1 兩種解析路徑都用 `.get("region", {}).get("startLine", 0)`，缺 region 時 `start_line` 直接預設成 **0**。[S3] 講的「照告警的起訖行取出來正規化即可」完全沒有處理 `start_line=0`（1-index 的檔案沒有第 0 行）這種輸入該怎麼「取出那幾行」——是回退到最後一招的次數比對，還是當成例外去讀第 0 行（很可能是取到錯誤的行或直接索引錯誤），spec 沒講。
- 查證：`scripts/lumos:17226`（SARIF v1 分支 `start_line = rf.get("region", {}).get("startLine", 0)`）與 `scripts/lumos:17237`（v2.1 分支同款寫法）都已示範這個 0 預設值是現有程式碼的真實輸出，不是我臆測的極端情境；另外現有的行級過濾 `lint_claims = [c for c in lint_claims if c["line"] in added.get(c["file"], set())]`（`scripts/lumos:19752`）對 `line=0` 的告警恆為 False（因為 `added` 集合裡的行號從沒有 0），也就是說「行號拿不到就預設 0」這件事在既有機制裡已經會造成告警被靜默濾掉——這正是 DEP 連結的 [[Issues/行級過濾漏掉未改動行的新告警]] 在講的同一類問題，[S3] 沒有講新的指紋機制會不會重蹈覆轍。

引句:「工具沒給片段的，核心自己去讀那幾行補上」

severity: major

## Finding 6：[S10] 要求「開啟改名偵測」，但沒指定在哪一個 git 呼叫開；DEP 指名沿用的那支 diff 呼叫目前沒開，repo 裡其他呼叫點卻明確示範過要另外加 `-M`

- spec：[S10]
- blocking: 是——如果改名偵測沒有接到「決定哪些行算新增」的那一支 diff 上，[S10] 想解決的「改名大檔整批擋人」這個問題並沒有真的被解決，只是看起來解決了。
- 情境：一支 800 行的檔被改名、內容完全沒變（100% 相似度，遠高於 git 預設 50% 的偵測門檻）。本計劃開頭欄位 DEP 點名沿用的 `_pitfall_diff_collect` 的 lint 段，它算「改動檔清單」與每個檔「哪些行算新增」所依賴的那支 `git diff` 呼叫（`scripts/lumos:19622`）目前**沒有帶** `-M`/`--find-renames`，這個 repo 也沒有設定全域或本機的 `diff.renames`。沒有這個旗標，git 對這支改名檔的呈現方式是「舊路徑整檔刪除＋新路徑整檔新增」，也就是說即使 [S10] 在別處另開一支帶 `-M` 的呼叫去抓「這支新檔其實是從舊路徑改名來的」以正確取用基準版內容，**決定「這 800 行算不算新增」的那個 `added` 集合仍然來自沒開 `-M` 的舊呼叫**——它會把這 800 行全部標成新增，[S10] 想避免的「整批擋人」照樣發生，只是換了一個環節出錯。
- 查證：`scripts/lumos:19622`（現行 diff 呼叫只有 `-U3`，沒有 `-M`）；同一支檔案裡其他需要看改動檔清單的呼叫點確實會外加 `-M`，如 `scripts/lumos:18273`（`["diff", "--cached", "--name-status", "-z", "-M"]`）與 `scripts/lumos:18277`、`scripts/lumos:19384`——顯示這是作者知道、但在這支特定 diff 上沒接的既有慣例。⚠ [S10] 文字本身沒交代新的比對機制到底接在哪一支 diff 輸出上，這條判斷有賴實作細節，故標記給編排者。

引句:「要開啟改名偵測，改名的檔用它在基準版的舊路徑取內容。」

severity: major

## Finding 7：放行檔本身壞掉、是空的、或不是合法 JSON 時該怎麼辦，[S5]／[S7] 都沒講——而 repo 對同類宣告檔的既有慣例是靜默吞掉、當作「沒有」

- spec：[S5]／[S7]
- blocking: 是——兩種可能的預設方向都不安全：若沿用「解析失敗當作沒有內容」的慣例，放行檔一壞，所有先前已放行的指紋瞬間全部「復活」變成新告警，整批擋人且沒有任何訊息解釋為什麼（不符合鐵則要求的「不靜默」）；若反過來讓放行檔解析失敗導致整道閘直接不擋，則是更危險的靜默放行，跟 [S7] 明講的精神正面衝突。
- 情境：放行檔因為兩個 session 同時寫（[S5] 自己承認的併發風險）而寫壞成半截 JSON，或被人手動清空成空檔。下一次代碼審跑到 [S4] 這一關，讀放行檔時該回報「有東西沒跑到」還是靜默降級？[S7] 列的四種「有東西沒跑到」情境（工具沒裝、逾時、沒網路、檔太大）明確都是**檢查工具**跑不動，沒有一種對應到「放行檔本身壞掉」這個治理資料層的故障，[S5] 也完全沒提。
- 查證：repo 現有對同類宣告檔（`.lumos/lint.json`）解析失敗的既有慣例是 `_lint_load_config`（`scripts/lumos:17010`-`17020`）用 `except Exception: return None`，呼叫端把 `None` 一律當「沒有宣告」處理（`_pitfall_diff_collect` 裡 `config is None` 直接走 regex-only 分支，`scripts/lumos:19717`-`19722`）——這是一個「解析壞掉＝當沒有」的靜默 fail-open 先例，如果放行檔的讀取抄同一個模式，後果會是上面描述的兩種危險走向之一，但 [S5]／[S7] 都沒有明講要選哪一邊、要不要留痕。

引句:「一條指令把某個指紋標成已放行，要寫理由；紀錄進專案裡的放行檔」

severity: major
