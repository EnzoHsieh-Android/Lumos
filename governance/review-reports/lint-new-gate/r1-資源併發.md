# 新增告警閘 r1 — 資源／併發／最壞時序審查

鏡頭：安排最壞的時序（同時發生、中途死掉、重試）。對照 `scripts/lumos` 既有的子行程保護、暫存檔慣例、原子寫入慣例、既有閘的關閉開關逐條核對。

## Finding 1：基準版暫存目錄的位置，S2 條款和「實務隱患」自相矛盾，兩邊都沒有「保證不會撞名」

- spec：S2
- 引句:「解出來的位置放在專案設定目錄底下並加進忽略清單」
- 引句:「用系統暫存目錄建一個帶前綴的目錄」
- 最壞時序：S2 說解到「專案設定目錄底下」、比照 test-cache 那個慣例；「實務隱患」卻說是「系統暫存目錄」，兩處地點不一致。若照 test-cache 慣例走（固定檔名），兩個 session 同時跑，第二個的 `git archive` 解壓會與第一個交錯讀寫同一目錄，兩邊都拿到摻雜對方內容的錯誤差集卻不自知。
- 查證：`file: \`.gitignore:30\`` 的 `.lumos/test-cache*.json` 是固定檔名（分片才有 `-shardN`，見 `file: \`scripts/test_lumos.py:27745\``），不是逐次隨機；本專案真正「解某版本到暫存、跑完清掉」的既有先例是 `file: \`scripts/lumos:9208\`` 的 `tempfile.mkdtemp(prefix="lumos-kill-")`（系統暫存目錄、逐次天生不同名），比 S2 的選擇更扛得住併發。
- blocking: 是 — 兩個 session 同時跑會拿到摻雜對方檔案內容的基準版，判定結果不可信，不是「慢」而是「錯」。
severity: blocker

## Finding 2：SIGKILL／機器休眠一類的中斷，try/finally 完全不會執行，跟「不靜默」的承諾直接矛盾

- spec：實務隱患「資源（暫存目錄）」
- 引句:「用 try/finally 保證清理」
- 最壞時序：try/finally 只在 Python 例外或正常 return 時執行；整條 lumos 進程被外部強殺（機器休眠恢復判死送 SIGKILL）時它完全不會跑,不是「清不掉但講了」,而是「完全沒清、也完全沒講」,直接跟「不靜默」矛盾。若命中 Finding 1 的固定路徑,殘留的半成品會混進下一輪比對。
- 查證：既有的等價保護是 shell 層的 trap,見 `file: \`scripts/hooks/pre-push:62\``（`trap 'impact_done' EXIT INT TERM`）——連它自己都只敢宣稱擋住 INT/TERM,沒宣稱擋住 KILL;新設計卻用保護範圍更小的純 Python try/finally,去扛一個涵蓋「逾時被砍」的更大承諾。
- blocking: 是 — 「不靜默」是 spec 自己寫的安全承諾，實際能觸發的中斷路徑（SIGKILL/休眠）恰好繞過它，承諾不成立。
severity: blocker

## Finding 3：S8 的時間預算沒有可以中途攔截單一命令的機制，只能「這條跑完才檢查」

- spec：S8
- 引句:「超過預算就停、明說停在哪、這次放行（跟表態那關同款）」
- 最壞時序：真正跑指令的 `_lint_run_and_parse` 是單一阻塞呼叫，逾時是內部固定常數且不接受外部 deadline，跑到一半時不會被喚醒去看「預算還剩多少」，能中止的只有兩條命令「之間」的空檔。表態閘的 20 秒預算能中途喊停，是因為它是快速 in-process 迴圈；lint 命令是可能跑到 105 秒的外部子行程，兩者不是「同款」。最壞情況一次推送被單一 lint 命令拖住到逾時上限（baseline/current 各一次、多棧別再倍增），跟「避免十一分鐘拖成不可用」的目的直接衝突。
- 查證：`file: \`scripts/lumos:16946\`` 的 `LINT_CMD_TIMEOUT = 180`；對照 `file: \`scripts/lumos:24460\`` 的 `_DISP_BUDGET = 20.0` 與其 in-process `deadline_check` 機制。
- blocking: 是 — `t_lint_budget` 這條測試釘的是「超過預算就停」，但底層原語做不到中途停一個正在跑的命令，規格對自己開的測試立不住。
severity: blocker

## Finding 4：放行檔（S5）的讀-改-寫沒有鎖，跟這個 repo 自己定的「atomic 寫入」門檻不符

- spec：實務隱患「併發（放行檔的寫入）」
- 引句:「放行紀錄是一個跟著 git 走的檔，兩個 session 同時寫會互蓋」
- 最壞時序：兩個 session 同時各自放行不同指紋——各自讀到同一份舊放行檔、各自加上自己那條、各自寫暫存檔再原子換名。原子換名只保證檔案不半寫，不保證兩筆更新都留下來：後寫的整份覆蓋先寫的，一條放行靜默消失，那個人下次推送無預警被擋。
- 查證：`file: \`scripts/lumos:11005\`` 的 `_write_lf` docstring 明講讀-改-寫的併發要靠呼叫端上鎖（`_vault_write_lock`）,原子換名只夠應付整檔覆寫；同一支程式碼另一處真長出過這個 bug 又補鎖，見 `file: \`scripts/lumos:24616\``。S5 只做了原子換名這半套，沒做上鎖那半套，卻自稱「不做半套」。
- blocking: 是 — 靜默丟失一筆放行紀錄，會讓已經處理過誤報的人無預警被同一條擋第二次，且無從得知原因。
severity: blocker

## Finding 5：這道閘沒有專屬的「整體關掉」開關，唯一的逃生門是逐條放行

- spec：S4、S9
- 引句:「有未放行的新增告警就擋，訊息列前幾條並附放行指令」
- 最壞時序：spec 自己的 KEY 行已證實首次真跑社群規則庫就命中一條誤報,上線第一天就有假陽性。若某版規則升級後大量誤判（一次掃到很多檔都命中同一條過寬規則）,S4/S5 給的唯一止血方式是逐一指紋放行,沒有「整條閘先關掉」的旗標；唯一的粗暴替代是整批刪掉 `.lumos/lint.json` 宣告,但那會連帶關掉既有「lint 墊高風險分級」的不相干功能。
- 查證：對照這個判定序列裡其他既有閘，各自都有一個布林環境變數可以整道關掉，見 `file: \`scripts/lumos:25105\`` 列出的 `LUMOS_SKIP_BOUND_TESTS`、`LUMOS_STOP_BLOCK_OFF`、`LUMOS_ENTRY_HOOK_OFF`，以及同一支函式自己實作的 `LUMOS_SKIP_CODE_LOOP`。
- blocking: 是 — 已知第一天就有假陽性，卻沒有跟既有每道閘同等級的整體回滾開關，出事時止血速度會明顯慢於這個判定序列裡的其他閘。
severity: major

## Finding 6：基準版與現在版兩次掃描不是同一個時間點的快照，S2 自己承認的併發現實沒有接回這裡

- spec：S2
- 引句:「這個工作目錄同時有別的 session 在用」
- 最壞時序：baseline 掃描可能跑到 105 秒（S6 實測數字），中間另一個 session 對同一支被推送的檔又存了一次檔；current 那一輪讀的是「執行時仍在專案根」的即時檔案，讀到的內容跟真正要 push 的那份已經不是同一個時間點。指紋比對（S3）拿不同時間點的現在版跟基準版比，算出來的「新增告警」集合本身不可信——可能把別的 session 的修正誤判成本次新增，也可能反過來讓真正該擋的新問題被巧合抵消。S2 沒有講兩次掃描之間檔案被動了怎麼辦，也沒有要求先確認樹是穩定的。
- blocking: 是 — 兩次快照不一致會讓「只擋新增」這個核心判準算錯，可能誤放行真正該擋的新問題，直接打到這道閘存在的目的。
severity: major
