# 新增告警閘_計劃

> 白話：讓檢查工具在每一次推送前真的跑一遍，而且**只擋你這次弄出來的新問題**，舊問題不管。誤報一定會有，所以放行的門第一天就要開好、而且走正式管道會留下紀錄。

## 現況：缺的比想像中少

| 已經有的 | 缺的 |
|---|---|
| 標準格式的橋（工具吐 SARIF、核心解析合併） | **現況**：自動路徑一律帶「不跑 linter」，只有手動敲才跑 |
| 按改動檔的副檔名挑該跑哪些命令 | **現況**：告警只拿來墊高風險分級，自己不會擋——本計劃 [S4] 就是要補上「自己會擋」這一層 |
| 跑命令、逾時保護、解析結果 | 沒有放行管道，誤報只能繞過整個檢查 |
| 把告警對到這次改動 | 對法是「行級過濾」，會靜默漏掉（見那篇事故） |

## 實測數字（2026-09-13，本機）

這些數字決定了下面幾條的門檻，不是拍腦袋定的：

| 量什麼 | 結果 | 影響哪一條 |
|---|---|---|
| 843 行的檔，151 條社群規則 | 1.8 秒（幾乎都是啟動成本） | 正常大小的檔沒有速度問題 |
| 26718 行的主程式，同一批規則 | **105 秒**，跑兩次就三分半 | [S6] 單檔大小上限變成必要配套 |
| 線上規則庫、未登入 | 可用，151 條規則，含下載約 2 秒 | 不需要帳號 |
| 沒有副檔名的檔（掃目錄時） | **靜默跳過**；明確指名就會掃 | [S1] 一定要傳明確的改動檔清單 |
| 基準比對對未提交改動的影響 | 不動改動、不動未追蹤檔、不建暫存 | 安全，但文件說「髒了會拒跑」與實際不符 |
| 首次真跑的命中 | 1 條，是誤報（對刻意設 0700 的目錄建議改成 0644） | [S5] 放行管道不能延後 |

## 條款

> r1 折入後的版本。原稿的 [S2]／[S3]／[S7]／[S8] 都被審查員打穿過，重寫的理由寫在「審計修正紀錄」。

- **[S1] 宣告檔擴充：兩個新佔位符，命令可宣告自己會處理基準。** 現有的輸出檔佔位之外，新增 `{LINT_FILES}`（這次要掃的檔案清單，多檔各自跳脫後以空白相接）與 `{LINT_BASE}`（基準版本代號，只給自己會做基準比對的工具用）。命令原本是字串，現在也可以寫成帶「命令」與「基準模式」兩個欄位的物件：模式為 native 表示工具自己會比基準、核心只跑一次；模式為 rerun（字串形式的預設）表示核心代跑兩次。**宣告檔的格式檢查要跟著認得物件形式**，否則新格式一寫進去，健檢會把它判成宣告壞掉。**命令裡沒有檔案清單佔位的，核心無法為它做基準比對**——那條命令的告警只報不擋，並明說「要進閘就在宣告裡加上檔案清單佔位」（舊宣告照樣能跑，不會突然擋人）。[test:t_lint_new_declaration]
- **[S2] 兩邊都從版本庫解出快照來掃，不掃工作樹。** 取基準版與被推送版兩個版本，**逐檔**把內容取出來寫進兩個暫存目錄（逐檔取，不用整批打包——整批打包時只要清單裡有一個檔在基準版不存在，整批會失敗；基準版沒有的檔就是新檔，它的告警全部算新增）。暫存目錄用系統暫存區、每次隨機名（沿用這個專案既有的「跑完即刪的暫存目錄」慣例），不放在專案目錄底下、也不碰版本控制的工作樹註冊機制。**兩次掃的都是版本庫裡的快照，不是當下的工作樹**——這樣別的工作階段在掃描期間改檔也不會讓兩次比對錯位。[test:t_lint_new_baseline]
- **[S3] 掃出來的路徑要還原成專案相對路徑。** 兩次掃描的檔案實際躺在不同的暫存目錄底下，工具回報的位置會帶著各自的目錄前綴；核心必須把它還原成專案相對路徑再進指紋，**否則兩邊的檔名永遠不同、每一條舊告警都會被當成新的**。[test:t_lint_new_pathmap]
- **[S4] 指紋用多重集合比對，算次數不算有無。** 指紋＝規則代號＋專案相對檔名＋正規化後的程式碼片段。**比的是「同一個指紋出現幾次」**：基準版一次、現在版三次，就是新增兩條——用「有沒有出現過」會讓複製貼上多出來的問題被吃掉。正規化的強度講死：逐行去掉首尾空白、內部連續空白壓成一個、丟掉空行，這樣純排版的提交不會讓既有告警整批變成新增。[test:t_lint_new_fingerprint]
- **[S5] 片段取不到時的退路要明講。** 工具沒附片段的（實測：主流 Python 檢查器完全不附），核心自己照起訖行去讀那幾行補上。**行號缺失、小於一、或超出檔案長度時，就是取不到片段**——那條退到「規則代號＋檔名＋訊息」的次數比對，並在輸出裡標明它是弱比對（弱比對容易誤判，讓人知道為什麼）。[test:t_lint_new_weakkey]
- **[S6] 第四道判定，不看風險分級。** 在代碼審那一關的判定序列裡，排在表態之後、留痕之前。**它跟表態一樣對每一次推送都跑，不受風險分級分流影響**——願景要的是覆蓋每一次提交，只在高風險跑就不成立。既有的風險分級計算維持原樣（照舊快算、不跑檢查工具），這道閘是獨立的一條路，不改那條。[test:t_lint_new_gate]
- **[S7] 放行管道，要上鎖。** 一條指令把某個指紋標成已放行、要寫理由，紀錄進專案裡的放行檔並記一筆治理帳。**讀-改-寫要上鎖**（沿用這個專案既有的寫入鎖），只做原子換名不夠——兩個工作階段同時放行不同指紋，後寫的會整份蓋掉先寫的，一條放行靜默消失。放行綁指紋不綁版本；同一支檔裡字面相同的多處會被同一條放行一起蓋掉，這是刻意的（內容相同、判斷也該相同），寫進誠實邊界。[test:t_lint_waive]
- **[S8] 單檔上限同時看行數與位元組數，任一超過就不掃。** 只看行數會被「整支檔只有一行」的壓縮檔騙過去——那種檔行數是一，位元組數卻跟兩萬多行的主程式相當。預設值依實測訂（正常檔一點八秒、兩萬六千多行一百零五秒），兩個門檻都可在設定檔調。超過的檔**明白說出來**：幾行、幾位元組、超過哪個門檻、所以沒掃。[test:t_lint_oversize]
- **[S9] 兩類失敗分開處理，對齊既有的兩套慣例。** [test:t_lint_undone_classes] 這個專案既有的閘本來就把「環境不可用」與「抓到問題被繞過」分成兩條路，新閘照著分：
  - **環境不可用**（工具沒裝、逾時、拉不到規則、檔太大、命令沒有檔案清單佔位、放行檔讀不了）→ **自動放行並自動記一筆帳**，不要求人手寫說明。這跟既有合約測試遇到環境問題的做法一致。
  - **真的有未放行的新增告警** → 擋，逃生門是人手動放行並寫理由。
  - **放行檔讀不了時不可以當成「沒有放行紀錄」**——那會讓所有既有放行瞬間復活、整批擋人；要走環境不可用那條並明說「放行檔讀不了」。
- **[S10] 時間預算要能真的中斷，不能只在命令之間檢查。** 剩餘預算要傳進命令執行層，單條命令的逾時取「既有上限」與「剩餘預算」兩者較小值——否則預算只能在兩條命令之間生效，一條跑一百多秒的命令照樣把推送前那關撐爆。預算用完歸環境不可用類（自動放行＋記帳）。[test:t_lint_budget]
- **[S11] 改名另開一支自己的差異查詢。** 開啟改名偵測，改名的檔用它在基準版的舊路徑取內容。**另開一支只給這道閘用的查詢，不動既有那支共用的**——那支同時餵給風險掃描、棧別提問、架構對照好幾個消費者，在上面加旗標會悄悄改掉它們的既有輸出。新設計比的是兩份快照的差集、不依賴「哪幾行算新增」，所以既有那支不需要動。[test:t_lint_rename]
- **[S12] 整道閘要有關掉的開關。** 跟這個判定序列裡其他每一道閘同級：一個環境變數可以整道關掉，設定檔另有三態（擋／只報告／關閉）。**首次真跑就命中一條誤報**，上線後遇到規則升級造成大量誤判時，逐條放行不是止血手段。[test:t_lint_killswitch]
- **[S13] 工具鏈自己要接上，否則交付即零實證。** 這個 repo 目前一個檢查工具都沒宣告（健檢已經在唸），閘做完也不會對任何東西生效。交付要包含替這個 repo 宣告檢查工具——**但這需要在這台機器上裝東西，屬於人的決定，不自作主張**。[manual:問過人再裝,裝完跑冒煙驗證]
- **[S14] 翻案與文件同步。** 推翻「擋推鏈恆不跑檢查工具」那條裁定並寫明翻案理由；同步代碼審的 skill、指令速查、上手文件、兩份 README 的說明。[manual:文件同步逐項核]

## 刻意不做

- **不接管 linter 的安裝。** 消費專案自己裝、自己宣告，核心只認格式——這是既有定位，不動。
- **不做離線快取。** 人裁「不管離線」，沒網路就判跑不動、留痕。
- **不按嚴重度分級擋。** 嚴重度是各工具自己標的、跨工具不一致；判準只有「是不是這次新增的」。
- **不動那四十四題棧別提問。** 規則跟提問分工不同，兩邊都留。

## 實務隱患

逐類答，判「不碰」也要寫理由：

- **資源（暫存目錄）**：兩份快照要解到磁碟。用系統暫存區、每次隨機名（沿用這個專案既有「跑完即刪的暫存目錄」的做法），**不用固定名字**——固定名字會讓兩個同時跑的工作階段讀到對方的檔案，那不是慢，是算錯。正常結束與一般中斷靠收尾清理；**被強制砍掉（機器休眠判死、外力強殺）時清理不會執行，殘骸會留在系統暫存區**，這點老實承認：那個位置由作業系統定期清，而且每次名字不同、不會污染下一次比對；另外每次開跑前順手清掉同前綴、超過一天的舊目錄。
- **資源（子行程）**：跑檢查命令是開子行程。沿用既有那條路的保護（獨立行程組、逾時到整組砍掉），不自己再造一套；**差別是逾時值要改成可以由呼叫端指定**，否則整條閘的時間預算管不到正在跑的那條命令。
- **併發（多工作階段共用同一個工作目錄）**：這台機器上同一個 repo 同時有別的工作階段在用。所以不碰版本控制的工作樹註冊機制（那是全域狀態），也不把暫存目錄放進專案目錄。**兩次掃描都用版本庫裡的快照而不是當下的工作樹**，所以掃描期間別人改檔不會讓比對錯位。
- **併發（放行檔的寫入）**：放行紀錄是讀了再改再寫的檔。**原子換名只保證檔案不會半寫，不保證兩筆更新都留下來**——兩個工作階段同時放行不同指紋，後寫的會整份蓋掉先寫的，一條放行就這樣消失。所以要沿用既有的寫入鎖，兩件事都做。
- **效能**：整條閘有時間預算（[S10]），單檔有大小上限（[S8]），超過都明說不靜默。推送前那關已經十一分鐘，加上去的秒數要實測。
- **回滾**：整道閘有關掉的開關（[S12]），跟這個判定序列裡其他每一道閘同級。逐條放行不是止血手段。
- **不碰的類**：金流、對外寄送、正式環境不可逆操作——這個計劃一項都不碰，純粹是本機與 CI 的檢查流程。

## 誠實邊界

- **零真專案實證。** 上面所有數字都是在工具鏈自己這個 repo 上量的。誤報率、實際擋下什麼、放行比例，要等第一個消費專案接進來才知道。
- **本 repo 的主程式不會被社群規則覆蓋到**——它兩萬六千行，超過單檔上限。這是刻意的取捨（不這樣做推送前那關會多三分半），但意思是工具鏈自己的核心檔只有快的那些檢查看得到，這一條要寫進交付說明，不要讓人以為全 repo 都被蓋住了。
- **環境不可用一律自動放行，這是可以被利用的。** 工具沒裝、逾時、拉不到規則都走自動放行（只記一筆帳）。也就是說，**把檢查弄慢或把工具移掉，就能繞過這道閘**。選這條是為了跟既有的閘一致（環境問題不該把人鎖在門外），代價是它不是防惡意的機制，只是防疏忽的機制。帳是可以統計的，異常頻繁的自動放行看得出來。
- **同一支檔裡字面相同的多處，會被同一條放行一起蓋掉。** 內容相同、判斷也該相同，這是刻意的；但如果兩處相同的程式碼其實該有不同判斷，放行會蓋過頭。
- **新檔與搬檔會整批算新增。** 一個在基準版不存在的檔，它所有的告警都算新增。從別處搬進來的舊程式碼會一次擋一大批，只能靠放行管道處理。這是「只擋新增」這個判準的固有代價，不是 bug。
- **放行永久有效**是已知的設計缺口：數量會累積，只有健檢會唸。真的變成問題再加期限。
