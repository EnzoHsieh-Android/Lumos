## Q2 命名與錯誤處理（含 fail-open）

判：不對齊，major。

放行管道 [S5] 的命名與寫法對齊良好：`lumos lint-waive` 是扁平單動詞指令，跟 `lumos lint-check` 同一個命名家族（file: `scripts/lumos:24290` 附近 `cmd_bound_tests` docstring 自述的「扁平頂層指令,不包子動詞」慣例）；放行檔「跟著 git 走、進治理帳」也跟 `_codeloop_write` / `_codeloop_gov_log`（file: `scripts/lumos:23790`、`scripts/lumos:23801`）同一套雙軌留痕（本機檔+治理帳）。

但 [S7] 的 fail-open 措辭跟既有機制的實際規矩對不上：

引句:「跑不動一律不靜默放行。工具沒裝、逾時、沒網路拉不到規則、檔太大——四種都判成「有東西沒跑到」，要留痕說明才過，跟合約測試跑不動同一套規矩。」

這句話宣稱「跟合約測試跑不動同一套規矩」，但既有的 `_bound_tests_check`（file: `scripts/lumos:24176`）對「環境不可用」（no-config、range-unavailable、no-vault、whole-suite-deferred 這幾種「跑不動」）的處理是**自動放行＋自動記一句機器產生的原因**（走 `_gate_failopen`／`_bound_tests_log`，file: `scripts/lumos:24433`），不需要人手寫 `--note` 就會過；只有紅／unfilterable（真的抓到問題、人主動選擇繞過）才需要人手寫 `--skip-bound-tests --note "…"`（`scripts/lumos:24273` 附近）。

「工具沒裝／逾時／沒網路／檔太大」這四種在既有分類裡屬於前者（環境不可用，非「抓到問題」），但 [S7] 的「要留痕說明才過」讀起來像是要求人手寫 `--note` 才能通過——這正是後者（真問題被繞過）的規矩，不是前者。這兩條路在既有程式碼裡刻意分開（`_gate_failopen` 的落款就是「hard=False:這是放行不是硬擋，但它必須看得見」，file: `scripts/lumos:24433`），一個是自動、一個是人手動；[S7] 沒有講清楚是要接哪一條，導致同一句「留痕才過」在接手實作時可能被讀成任一種——這正好是「同一件事兩套規矩、接手要猜」的情況。

同一份 r1 材料自己也留了一個更直接的旁證，[S9] 引到的姊妹計劃節點裡有同型措辭：

引句:「沒網路拉不到規則時判「跑不動」、要留痕說明才過，不做本地快取也不做離線降級」（`docs/lumos-toolchain-knowledge/Projects/社群規則覆蓋每次提交_計劃.md` d3）

但那條決策同樣沒有寫死是自動記帳還是要人手 `--note`，同一個含混被原封不動繼承進本計劃，沒有藉這次落地機會釐清。

## Q3 第二種做法

判：不對齊，major——計劃內部對「暫存目錄放哪」自相矛盾，等於同時開了兩條路。

[S2] 明講位置：

引句:「解出來的位置放在專案設定目錄底下並加進忽略清單（跟既有的測試快取檔同一個慣例）」

但「實務隱患」一節的「資源（暫存目錄）」講的是另一個地方：

引句:「做法：用系統暫存目錄建一個帶前綴的目錄，用 try/finally 保證清理，逾時被砍也要清；清不掉就印出來讓人知道有殘骸，不靜默。」

「專案設定目錄底下＋加進 .gitignore」跟「系統暫存目錄＋try/finally 清理」是兩個不同的地方、兩種不同的生命週期管理方式。而且這兩者對照到既有程式碼分別各有一個先例，恰好是不同的兩套：
- 「系統暫存目錄＋`lumos-*` 前綴」是既有的真實慣例：`_run_kill` 的 `tempfile.mkdtemp(prefix="lumos-kill-")`（file: `scripts/lumos:9208`）與簿記備份的 `_tf.mkdtemp(prefix="lumos-bookkeeping-backup-")`（file: `scripts/lumos:13773`），兩者都是「跑完即刪、系統 tmp、不進 git」。
- 「`.lumos/` 底下＋進 `.gitignore`」是既有的另一套慣例，但那是給**輕量狀態快取檔**用的（`.lumos/test-cache*.json`，見 `.gitignore:30`），不是給「解出來的整批原始碼」這種可能上千行、跑完要清空的暫存產物用的。

[S2] 把後者（測試快取檔的慣例）套在前者的場景（解基準版原始碼到磁碟）上，而「實務隱患」段落又寫回前者（系統暫存目錄）——同一份文件兩處講法互斥。實作的人會需要自己挑一邊，這正是 major 錨點寫的「之後接手的人要在兩套之間猜」。

（旁註，非獨立扣分項但支持這條判斷：計劃刻意不用 `git worktree`——引句:「不用 git worktree——這個工作目錄同時有別的 session 在用，動 worktree 註冊表會互相干擾」——這個理由本身是站得住的、也對照到既有 `_run_kill` 用 `git worktree add --detach` 的先例做了有意識的偏離；但既然要繞開 worktree，materialize 到磁碟這件事就更需要明確唯一的目錄慣例，而不是兩處各講一套。）

severity: major
