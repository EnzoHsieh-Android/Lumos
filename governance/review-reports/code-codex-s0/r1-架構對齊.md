## 問題一:分層與依賴方向

**1.1 新函式放的位置、誰呼叫誰——整體乾淨,無跨層直呼**

- `_install_skills`(`scripts/lumos:11058`)把 `~/.agents/skills` 那段連結邏輯加在同一支函式裡,而不是散到別處單獨呼叫——沿用它本來就有的 `_refuse_if_probe("install-skills")` 單點守衛(一次守住兩個迴圈),沒有把 mutation 邏輯下放到沒守衛的呼叫路徑。
- `_sync_global_hooks`(合併器呼叫端)仍然只用 `subprocess.run` 叫 `merge-claude-settings.py`,沒有 import 它的內部函式——跨檔邊界維持 subprocess 呼叫,合乎既有分工(lumos 管全域生命週期原語、merge-claude-settings.py 管設定檔合併細節,兩者只靠檔案+子行程通訊)。
  引句:「args = [sys.executable, str(merge)] + (["--target", "codex"] if harness == "codex" else [])」
- 三個 reinject 呼叫點(`cmd_init`/`_vendor_toolchain`/`cmd_update`)全部收斂成呼叫 `_reinject_all`,沒有任何一處繞過它直接呼叫 `_reinject_claude_block`——`scripts/lumos:10981`、`11001`、`11475` 三處一致。
severity: clean

**1.2 `cmd_install`/`_install_hooks_py` 用迴圈,`cmd_teardown` 用兩行明呼——判不準是不是同一慣例**

- `cmd_install`(`scripts/lumos:10248`)與 `_install_hooks_py`(`scripts/lumos:11271`)都寫成 `for _h in ("claude", "codex"):` 迴圈,把訊息印出委派給 `_sync_msg`。
- `cmd_teardown`(`scripts/lumos:10387-10388`)則是兩行明寫呼叫 `_teardown_global_hooks(..., "claude")` / `_teardown_global_hooks(..., "codex")`,沒有迴圈。
- 這差異可能只是因為兩支函式的回傳值用法不同(`_sync_global_hooks` 回三態字串、外面要各自印訊息,所以需要迴圈接 `_sync_msg`;`_teardown_global_hooks` 自己內部印訊息、回傳值呼叫端沒用,迴圈與否純結構等價),不算「第二種做法」;但也可能是三個本該同構的呼叫點漏了對齊風格。
引句:「_teardown_global_hooks(Path(__file__).resolve().parent.parent, "claude")」
flag: ⚠(結構是否要求一致,判不準,列出供人裁)

## 問題二:命名與錯誤處理

**2.1 三態字串取代 bool——有既有先例,不是新花樣**

- `ReInjectResult.status` 早就是字串列舉(`created|updated|unchanged|appended|sentinel_broken|no_template`,`scripts/lumos:10645`),`_sync_global_hooks` 回 `ok/probe/merge-failed/absent` 是延續同一種「用字串列舉表達多態結果、別硬塞回 bool」的既有慣例,`_sync_global_claude` 也留了相容包裝(`== "ok"`)給舊呼叫者,新舊介面沒有互相打架。
- `_refuse_if_probe` 在每個新變動原語(`_sync_global_hooks`、`_install_skills` 沿用同一次呼叫涵蓋兩個迴圈)都守住,守衛顆粒度(每個「動全域機器狀態的原語」守一次,不是每個子迴圈都守)跟既有 `_install_skills` 的原有守法一致。
severity: clean

**2.2 `_GLOBAL_HOOKS` 別名常數宣告了但沒人用**

`scripts/lumos:11120`:
```
_GLOBAL_HOOKS = _GLOBAL_CLAUDE_HOOKS   # 兩家共用同一批檔(...);舊名留給既有呼叫/測試
```
註解的意思是「舊名 `_GLOBAL_CLAUDE_HOOKS` 留給既有呼叫/測試用,新名 `_GLOBAL_HOOKS` 是給新代碼」,但通篇 `scripts/lumos` 與 `scripts/test_lumos.py` 裡除了這行宣告,`_GLOBAL_HOOKS` 沒有第二處引用——`_sync_global_hooks`/`_teardown_global_hooks` 兩處迴圈仍然直接寫 `_GLOBAL_CLAUDE_HOOKS`。等於這次 diff 立了一個新名字、卻沒有任何一行真的改用它,純粹的死別名,之後有人照著這個新名字去找用法會撲空。
引句:「_GLOBAL_HOOKS = _GLOBAL_CLAUDE_HOOKS   # 兩家共用同一批檔」
severity: minor

**2.3 `enforcement_status` 的 status 列舉文件沒跟上新值**

`scripts/lumos:12220` 函式頭文件仍寫:
```
status: active | inactive | degraded | unknown。root=repo 根、home=~/(測試可注入)。
```
但這次 diff 在同一支函式裡新增了第五個狀態值 `registered-trust-unknown`(`scripts/lumos:12302`),且 `enforcement_summary`/`cmd_enforcement`(`mark` dict)都已經跟著改了——只有函式頭那行「合法值域」清單沒同步。這是給下一個 session 看的合約性文件(狀態值域),沒跟實作對齊。
引句:「add(layer, "registered-trust-unknown", f"{needle} 已註冊、檔在;要不要跑由你在互動 codex 審過 hook 才算數,本機讀不到")」
severity: minor

**2.4 enforcement 新列的命名 schema 換了一套,跟既有 Claude 側五列不同構**

既有 Claude 側五個 hook 層(`scripts/lumos:12252`)命名是「事件+用途」拼接、扁平 kebab-case:
```
for layer, needle in (("session-entry-hook", "lumos-entry-hook.py"),

                      ("stop-graph-sync-hook", "check-graph-sync.py"), ...

                      ("codex-hook:impact", "impact-hook.py"), ...
```
兩組列在同一個 `rows` 輸出裡結構對稱(layer/status/detail 三元組本身沒變),但同一份表格內出現兩套不同的命名文法(`<event>-<purpose>-hook` vs `codex-hook:<purpose>`),讀 `lumos enforcement` 輸出的人得記兩套規則。
引句:「("codex-hook:entry", "lumos-entry-hook.py")」
severity: minor

## 問題三:第二種做法

**3.1 「本機有沒有 Codex」被兩支不同邏輯各自判一次,結果可能不一致**

- `_codex_present()`(`scripts/lumos:11157`,`_sync_global_hooks` 在 `scripts/lumos:11181` 呼叫,決定 install 時要不要動 `~/.codex`)判準是「目錄在 **或** `codex` 在 PATH 上」。
- `enforcement_status()` 裡的 `codex_ok`(`scripts/lumos:12274`,決定 enforcement 九列 Codex 相關列印 unknown 還是往下判)判準只看「目錄在」,完全不看 PATH。

引句 A:`return (home / ".codex").is_dir() or bool(shutil.which("codex"))`
引句 B:`codex_ok = (home / ".codex").is_dir()`

這兩支函式回答的是同一個問題(「這台機器有沒有 Codex」),卻用了兩套不同判準——結果會在「`codex` 裝了、在 PATH 上,但這台機器還沒真的跑過一次 Codex(所以沒有 `~/.codex` 目錄)」這個真實會發生的場景上分岔:`lumos install` 會判定「有 Codex」去寫 `~/.codex/hooks.json`(順帶建出 `~/.codex` 目錄),但 install 之前跑 `lumos enforcement` 會看到 Codex 九列全部 unknown(判「不適用」)。

`codex_ok` 這條寫死用「目錄」判準有在 `scripts/lumos:12271` 附近留註解說明理由(避免入口 hook 對沒裝 Codex 的機器每 session 唸、要跟 HOME 隔離測試一致),且這條理由也回寫進 `Projects/Codex完全支援_計劃.md` 的「實作紀錄 S0」段(標成「★偏離 spec 原文『inactive』★」)——這算是有記理由的偏離,不是漏改。但 `_codex_present()` 那條「或 PATH」的分支本身完全沒有對應理由記錄(不在 d1–d4 任何一條決策裡,實作紀錄也只提到 `_sync_global_hooks` 三態、沒提為什麼要多判 PATH),而且 6 支新測試裡沒有任何一條驗證「codex 在 PATH 但沒有 `~/.codex` 目錄」這個分支(`t_codex_sync_global_tristate` 只測了「兩者都沒有」→absent,沒測「PATH 有、目錄沒有」→ok)——這半支邏輯目前是沒被記錄理由、也沒被驗證覆蓋的死角。兩套判準沒有收斂成一個共用述語(例如讓 `enforcement_status` 也呼叫 `_codex_present`,或反過來讓 `_codex_present` 也提供一個「嚴格模式」旗標),是這次 diff 引入的第二種做法。
severity: major

**3.2 hook 註冊格式、sentinel、skills 安裝路徑判法——都沒有第二套**

- hook 註冊沿用同一個 JSON schema(`{event: [{matcher?, hooks:[{type,command,timeout}]}]}`),`_codex_entries` 只是把既有 `HOOK_ENTRIES` 表逐條轉譯(matcher 改名/搬事件),沒有另建一份格式。
  引句:「if event == "PreToolUse" and e.get("matcher") == "Edit|Write|MultiEdit":」
- AGENTS.md/override 沿用同一組 sentinel 字串(`<!-- LUMOS:GRAPH-DISCIPLINE:START/END -->`),`_deinit_strip_claude` 剝除兩檔用的是同一段判斷邏輯,不是另建一套標記。
  引句:「start_marker = "<!-- LUMOS:GRAPH-DISCIPLINE:START"」
- `~/.agents/skills` 沒有繞開 `_link_or_copy` 另寫一套安裝邏輯——`_link_or_copy_shared` 是一層薄包裝(先判斷 dst 是不是「非我方真目錄」,是就跳過+warn,其餘案例原樣交給既有的 `_link_or_copy`),這正是設計文件裡明寫「不得沿用 `_link_or_copy` 的無條件 rmtree」這條有意識偏離的落地,不是隨手複製一份重寫。
  引句:「跳過+印一行,回 False;其餘交給 _link_or_copy(它會把 symlink/空夾/帶標記的複製物重建)。」
severity: clean
