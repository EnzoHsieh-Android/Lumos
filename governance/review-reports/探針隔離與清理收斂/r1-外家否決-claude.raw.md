**總評：這份設計有 3 個要擋下來的問題、2 個小問題。** 三個要擋的都卡在同一個盲點：設計只在「建好副本、模型還沒啟動」那一刻檢查一次，可是模型執行中做的普通動作，會讓當初檢查過的狀態失效。

---

### 1. Git 設定只在建副本時檢查一次，模型切分支後就可能失效
- **severity: major｜blocking: 是**
- 引句（第 34 行）：「只有 remote 空且 hook 等於本次副本專用目錄才准啟動模型」
- file:/tmp/probe-boundary-convergence-r1.md:34；scripts/scenario_probe.py:550
- **為什麼會出事**
  - Git 有一種「條件式引入」設定：滿足條件才額外讀進一個設定檔，例如「切到某名稱的分支才生效」。
  - 檢查時條件不成立，檢查會過；模型執行中條件成立了，新設定才冒出來。
- **重現**
  - 來源的 Git 設定加一段「分支名稱符合 `feature/**` 時才引入 `push.inc`」。
  - `push.inc` 的內容是把 `core.hooksPath` 改成 `/dev/null`，再加一個 `origin` 指向本機的 bare repo（只存版本歷史、沒有工作目錄的 Git 倉庫）。
  - 建副本時在 main 分支上，所以 remote 是空的、hooksPath 也對，檢查通過。
  - 模型照常建分支、提交、推送：
    ```
    git switch -c feature/x && git commit -am x && git push origin HEAD
    ```
- **壞結果**
  - 引入的設定排在後面，會蓋掉沙盒寫入的 hooksPath，擋推送的 pre-push 掛鉤失效。
  - remote 也出現了，推送真的寫進 bare repo。設計宣稱守住「繼承的 Git 設定」，這個案例正好落在宣稱範圍內。
- **還有一個相近風險（我沒驗證）**：檢查時用的是洗過的環境。如果 Codex 那邊的 shell 環境設定沒把這些變數帶進去，模型執行時讀到的是另一套有效設定。
- **建議**
  - 不要靠「驗一次有效值」。改成整份重寫副本的本機設定（不帶任何引入），或在執行階段用環境變數強制覆蓋這兩個值。
  - 驗收條款二要加一個「切換分支後」的反例。

### 2. 只拒絕「已經存在的巢狀 `.git`」，沒初始化的子模組會漏掉
- **severity: major｜blocking: 是**
- 引句（第 32 行）：「凡來源工作樹含巢狀 `.git` 目錄或 gitfile（含 submodule 與獨立巢狀 repo）」
- file:/tmp/probe-boundary-convergence-r1.md:32；scripts/scenario_probe.py:510-533
- **為什麼會出事**：子模組（掛在主 repo 裡的另一個 Git repo）沒初始化時，工作目錄裡只有 `.gitmodules` 和一個指標，根本沒有 `.git`，所以掃描抓不到。
- **重現**
  - 情況一：來源有一個沒初始化的子模組 `lib`。
  - 情況二：子模組被取消初始化過，但主 repo 的 Git 資料夾裡還留著 `modules/lib`，裡面的 config 帶著 `origin`。
  - 兩種情況都能通過驗收條款一和現有的路徑檢查（子模組資料在副本內、也不是符號連結）。
  - 模型遇到建置失敗時，很常見的修法是：
    ```
    git submodule update --init
    ```
  - 接著在 `lib` 裡提交並執行 `git -C lib push`。
- **壞結果**
  - 子模組的設定是獨立的，不會繼承主 repo 的 hooksPath，也沒有擋推送的掛鉤。
  - 它的 remote 是真的，推送就送出去了。
  - 巢狀 Git 是在模型執行時才長出來的，建副本時的拒絕檢查無從擋起。
- **建議**
  - 掃描範圍要加上 `.gitmodules`、索引裡的子模組指標（mode 160000）、主 Git 資料夾底下的 `modules/`。
  - 一律拒絕，或在建副本時把它們移除。

### 3. 「刪不掉就整批停」會被逾時後還活著的子程序誤觸發
- **severity: major｜blocking: 是**
- 引句（第 36 行）：「刪除失敗為 fatal 儀器錯誤：當次不算有效分數、整批 inconclusive、退出碼 3」
- file:/tmp/probe-boundary-convergence-r1.md:36；scripts/scenario_probe.py:658、736、447-451
- **為什麼會出事**
  - 兩個 runner 逾時時，只會殺掉直接啟動的那一支程式（claude 或 codex）。
  - 模型正在跑的指令是孫程序，會變成孤兒繼續跑。
- **重現**
  - 修程式題裡，模型正在跑一套很長的測試，或任何會持續寫檔的指令。
  - 240 秒逾時到了，claude 被強制終止，但測試還在副本裡產生快取和輸出檔。
- **壞結果（兩種）**
  - 刪副本時剛好有新檔案寫進來，刪除失敗。原本只是「截斷、這場不算分」，現在變成整批退出碼 3、後續全部不跑。修程式試行最常見的逾時情境，會直接被放大成整批作廢。
  - 刪除剛好先完成的話，孤兒程序會繼續吃 CPU，拖慢下一次執行、讓後面的計時和逾時不準。
- **建議**
  - runner 放進自己的程序群組。
  - 刪副本前先殺掉整個群組並等它結束。
  - 驗收條款四要加「逾時時還有子程序在寫檔」的反例。

### 4. 「remote 清空」不等於「推送沒有目的地」
- **severity: minor｜blocking: 否**
- 引句（第 30 行）：「移除 remote／設定 hooksPath 不等於有效 Git 設定安全」
- file:/tmp/probe-boundary-convergence-r1.md:34
- **重現**
  - 來源設定寫 `branch.main.pushRemote` 或 `remote.pushDefault`，值直接填網址，而不是 remote 名稱。
  - `git remote` 列出來是空的，檢查通過。
  - 模型只打 `git push`，就會推到那個網址。
- **為什麼只算小問題**：第二道防線（擋推送的掛鉤）還在。但設計把「remote 空」當成第一道防線成立的證據，這個證據本身不成立。

### 5. 建副本被拒時，結果會被算成「題目沒過」
- **severity: minor｜blocking: 否**
- 引句（第 50 行）：「明確報不支援與替代路徑，不靜默給假安全結果」
- file:/tmp/probe-boundary-convergence-r1.md:36、50；scripts/scenario_probe.py:916-929、994
- **為什麼會出事**：改成每題、每次重試都建自己的副本後，「來源不支援」的拒絕會在每一題的例外處理裡被吞掉。
- **重現**：來源含巢狀 `.git`，跑 10 題。
- **壞結果**
  - 白白複製 10 次。
  - 整批被標成不能下結論，但退出碼是 1，跟「有題沒過」一樣。
  - 開了歷史紀錄的話，會寫進一筆「10 題過 0 題」，看起來像退步，而不是「這個來源不支援」。
- **建議**：先在迴圈外做一次不改檔的預檢，不支援就用獨立的退出碼結束。

### 補充（severity: minor，不擋）：建副本階段本身也會執行設定裡的程式
- 引句（第 34 行）：「此邊界只涵蓋繼承的 Git 設定及意外 `git push`」
- file:scripts/scenario_probe.py:561-565
- **為什麼值得注意**：建副本時的 `git add -A` 和 `git status`，會執行副本設定裡的內容過濾指令（`filter.*.clean`）和檔案監看程式（`core.fsmonitor`）。
- **重現**：來源設定一個內容過濾指令，裡面寫死往來源目錄寫檔；`.gitattributes` 讓所有檔案都套用它。
- **壞結果**：建副本當下，來源就被寫入了。
- **建議**：這屬於範圍說明，不擋。但設計應該講明它不在宣稱範圍內，或在建副本時一併中和掉這些設定。
