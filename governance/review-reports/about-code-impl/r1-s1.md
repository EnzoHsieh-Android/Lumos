## tier 判斷(第一個問題)

spec 自判 #4「只加一道 stable sort 不動評分」、#6「warn_soft 不擋」,兩項都判 light 可
(spec 原文,`/tmp/about-code-impl-r1.md` 419-421 行)。

查證:同一份文件自己在「A 層(過渡)的修法方向」節寫死了判準——

引句:「動 `impact` 排序=演算法密集,規矩是走完整 design-loop,light 硬否決」

這句話講的是 A 層(扇出降權)還沒做的原因。但 #4 做的事,字面上正好落在這句話劃的紅線裡:
它動的不是無關的顯示層,是 `cmd_impact` 的「8.5 ranked 融合」區塊本體——`scripts/lumos:14171-14267`,
就是把 `pins`(固定席)、`free`(自由席)、`rescued`(直連保底)三桶分裝、排序、截斷的那一段。
這段程式碼的敏感度不是我猜的,是這份 spec 自己前 350 行寫的:同一批固定席排序邏輯,
光是把 `LUMOS_IMPACT_DIRECT_BASE` 這種既有旋鈕調一格,就要跑 train/held 兩輪網格才敢下結論
(spec 90-94 行);二元砍除實驗(A 層旋鈕)明明 P@8 漲了 5 格,還是因為悄悄漏檢 3 個必看項被
must-see 棘輪擋下(spec 108-126 行)。#4 要加的「stable sort:`hit=="about"` 者在前」,一樣是在
這個排序區塊裡插一條新規則——差別只在 spec 宣稱這次不影響召回,但這正是 design-loop 存在的
理由:自判「這次不影響」不能替代審查,尤其這份文件自己才剛在 r1→r2→r3 三輪裡連續打穿兩次
「不影響」的自判(r1「有欄但不含→降自由席」被實測打穿必看漏標、r2「零誤放」被 held 巨檔打穿)。

再往下看,#4 本身还有兩個具體問題(見 f2/f3)證明「只加一道 stable sort」的自我描述本身就不準——
它同時在 `results.append` 裡動了一個既有欄位(`hit`)的語意,而且「about 命中是否能讓非固定席
節點升上固定席」這件事,spec 自己前後兩節文字對不上。這兩件事都不是「排序層的小改」,是會動到
固定席**成員**或**既有輸出欄位語意**的改動。

**判斷:tier 應升 standard**。理由:#4 觸及 spec 自己界定為「演算法密集、light 硬否決」的同一塊
`cmd_impact` ranked 融合/固定席組裝邏輯,且存在會影響既有輸出欄位語意與固定席促升規則的未消歧
之處(f2、f3)。#6/#9/#10 本身風險低(#9 純顯示、#10 不進 gate 的觀測指標),不足以單獨要求升級,
但只要送審是「這四項一起審」,#4 一項就把整包拉到 standard。

### f3 — major —「讀側怎麼用」的促升措辭與 #4 的窄範圍判定、巨檔段落的事實陳述互相矛盾

## #6:過期檢查(另開迴圈,輸出對齊 Check S)

### f8 — blocker — 「訊息格式照 Check S」不成立,且「改過 N 次」這個數字沒有資料來源

spec 寫:
引句:「這篇 X 天前標的 about_code,之後改過 N 次,可能過期」

查證 Check S 現況(`scripts/lumos:823-869`):
- `sa_missing` 的訊息是「有 {N} 篇功能筆記從來沒被不知道背景的人重新確認過內容還站不站得住」,
  後面接一份純節點路徑清單(`:864`)。
- `sa_stale` 的訊息是「有 {N} 篇功能筆記在上次確認之後又改過,需要再確認一次」,後面接
  `f"{rel} (self_audit {sa_date} < updated {upd})"` 這種「兩個日期字串直接列出」的格式
  (`:844/868`)。

兩種訊息都沒有「X 天前」這種相對天數描述,也沒有「改過 N 次」這種次數描述——Check S 從頭到尾
只做「日期字串字典序比較」,不算天數差,更不算改動次數。所以「訊息格式照 Check S」這句話本身
不成立,是可查證的錯誤陳述。

更根本的問題是「改過 N 次」這個數字,`git_last_change_dates()` 提供不了——它的實作
(`scripts/lumos:13549-13584`)用 `git log --name-only --format=@%cs` 只取「第一次看到(=最新)
的日期」就 `continue`(`:13579` 的 `if rel not in out`),整個函式的回傳型別就是
`{rel: 最後一次改動日期}`,沒有累計次數。要拿到「改過 N 次」得另外跑一次
`git log --format=%cs -- <檔>` 數行數,或 `git rev-list --count`——這正是 #5 剛用批次呼叫
解決掉的那個效能病的翻版(spec 264 行:逐篇 `git log` 83 次 5.3s vs 批次 0.22s,#5 解法明文寫
「不定義門檻就上線 = 天天複現」)。#6 要「改過 N 次」等於要重新引入一支逐篇 git 查詢,且沒有
任何一句提到要不要批次化。
file:line:`scripts/lumos:823-869`(Check S 全段)、`:13549-13584`(`git_last_change_dates`)。
