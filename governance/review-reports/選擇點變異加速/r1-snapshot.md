# 選擇點變異加速_計劃

## 白話

`lumos choice-kill`(改動選擇點:每一行挑一個壞寫法、跑計劃條款綁的測試,看測試會不會紅)在真實 Android 專案上太慢:每個壞法要把 64 支綁定測試一支一支各叫一次 Gradle(基準每支測試只量一次,但每次叫 Gradle 都要付啟動與設定的固定成本)。好比洗 64 個碗,每洗一個就把熱水器重新燒一次。這份計劃做兩件事:①同一個壞法要跑的測試合成一次 Gradle 呼叫(Gradle 一次可以帶多個 `--tests`),誰殺掉壞法改讀 Gradle 寫出的 JUnit 結果檔判;讀不出來就退回現在的逐支跑。②開 2–3 份隔離工作樹同時跑不同的壞法,基準只量一次、各份共用,治理帳只由主程序一筆一筆寫。另外把「不改工具、一次呼叫跑完不分段」寫成對照基線。

WHY:同一個壞法的綁定測試合成一次 Gradle 呼叫、改讀 JUnit 結果檔判誰殺掉;結果檔讀不出來、缺某支、有歸不到任何一支的失敗、或合併跑逾時,這個壞法就退回逐支跑 [出處:2026-11-23 使用者裁「兩種加速都做」;實驗專案實測存活壞法約 6 分鐘、64 次 Gradle 呼叫] [因:時間花在每次呼叫的固定成本(啟動、設定、測試行程),不是測試本身;論文 2.1 Google 也是一次跑整個測試目標] [不選:新增平台欄位寫合併用的指令範本(Gradle 的形狀從現有 run_cmd 就認得出,多一個欄位多一個要對齊的地方);解析主控台輸出判誰殺掉(多支一起跑時輸出交錯、還會被 256KB 上限截掉;結果檔一支一筆)] [代價:殺掉就停的提早結束沒了,被殺掉的壞法也要跑完 64 支]
WHY:`--jobs N` 開 N 份隔離工作樹,壞法照順序輪流分給各份;基準在第一份量一次、交給其他份共用;各份把每一列交回主程序,由主程序依序判定、寫帳、印 [出處:2026-11-23 使用者裁定;T41 工具意見(機器 10 核、32GB,記憶體夠開 2–3 份)] [因:合併後每個壞法是一次 Gradle 呼叫,單份仍是幾小時;多份同時跑把牆上時間再除以份數(扣掉搶 CPU)] [不選:每個壞法一棵工作樹(既有否決,冷編譯成本太高,見舊否決比對);開多個 lumos 程序各跑一片(各自寫帳要跨程序鎖、各自量基準、中斷要逐一送訊號);動態工作佇列(cmd_guard_kill 一開始就把配方清單與平台分組定下來,改成邊跑邊拿要動它的主迴圈)]

PRIOR-ART: ①Google〈Practical Mutation Testing at Scale〉2.3:每個壞法準備一份暫時的版本控制狀態,所有狀態上的測試平行跑;2.1:用逐行覆蓋率決定每個壞法要跑的最小測試集,測試以「測試目標」(一個目標含多支測試)為單位執行(https://arxiv.org/pdf/2102.11378)。我們照它平行跑,但不是一個壞法一份狀態,而是固定 N 份工作樹輪流用(Android 冷編譯貴)。②PIT FAQ:加速首選「多開執行緒,最佳值通常介於 1 與 CPU 數之間」;只跑覆蓋到被改那一行的測試,其餘丟掉,剩下的依執行時間由短到長排(https://pitest.org/faq/)。我們沒有覆蓋率(既有天花板),排序沿用「計劃落點先」;執行緒數對應 `--jobs`。③Gradle 文件:「可以給多個 `--tests`,每個樣式都生效」;JUnit XML 結果預設寫在 `build/test-results/<測試任務名>`、每個測試類別一個檔(https://docs.gradle.org/current/userguide/java_testing.html)。④本 repo [[Projects/合約測試閘並行執行_計劃]]:自建 daemon 工作執行緒、主流程每 0.1 秒逐條等、開程序經由 `_BtProcs` 登記、出錯不再派新的。本案照它的執行緒與等待形狀接;程序登記沿用 guard kill 自己的 `_KILL_RUN_LIVE`(`cmd_guard_kill` 沒有傳 started 的路徑,不改用 `_BtProcs`);某份當掉時其他份照跑完,不學它「出錯不再派新的」——各份的壞法互不相依,停掉別份只會讓帳缺更多。
RETIRE-IF: ①合併:上線後累計 50 個以上合併判定的壞法中,退回逐支跑的超過三成(結果檔讀法在真專案上靠不住),或出現一次合併判定跟逐支判定不同而查明是讀法的錯,就把合併預設關掉(`--no-merge` 變預設)、回頭換讀法。②平行:`--jobs` 大於 1 的呼叫累計 10 次以上,每個壞法平均秒數(帳上 `run` 的 `secs` 除以 `ran`)沒有比同專案 `--jobs 1` 的呼叫少兩成以上,或出現一次因同時跑造成的假判定(單份重跑結果不同),就拿掉 `--jobs`。
REVISIT:2026-12-31 讀治理帳 choice-kill 的 run 事件(`jobs`、`merged`、`fallback`、`secs`、`ran` 欄),照 RETIRE-IF 兩條判;同時看實驗專案 S13 的實測值跟〈預期效益〉的估算差多少,差兩倍以上就改寫估算

## 舊否決比對

- [[Systems/規格閘]] 記 choice-kill 那行的 `[不選:每個壞法一棵工作樹平行跑(論文的做法,本機成本太高)]`:那條否決的是「一個壞法開一棵工作樹」——每個壞法都付一次 Android 冷編譯。本案是固定 N 份(預設 1、建議 2–3)工作樹,每份依序跑分到的多個壞法、只在第一個壞法付冷編譯,成本形狀跟那條否決的不同;理由不變的部分(冷編譯貴)照樣成立,所以份數設上限、預設 1。使用者 2026-11-23 裁定做平行。
- [[Systems/guard-kill]] 三處 `[不選:另抽一支共用的殺傷力函式]`:本案照舊只給 `cmd_guard_kill` 加選用參數(合併、共用基準),判法仍在它裡面;平行是在 choice-kill 那層開多條執行緒、每條各呼叫一次 `cmd_guard_kill`,不另寫殺傷力函式。
- [[Projects/改動選擇點都要有需求守住_計劃]]〈用詞〉殺掉判定「同一條測試指令的基準只跑一次」「殺掉、編不過、逾時就停」:合併後同一個壞法的測試一起跑,「殺掉就停」在合併模式下不再省時間(見〈做法〉1 的取捨);判定規則(取排序第一支強殺掉的、弱證據記跑不出結果)不改。
- [[Projects/合約測試閘並行執行_計劃]] 不用標準執行緒池的理由(結束時會等工作者、例外浮得晚):本案照用自建 daemon 執行緒。

## 做法

### 1. 合併呼叫(預設開,`--no-merge` 關)

- **認得出才合併**:平台 run_cmd 只出現一次 `{method}`,而且它在一個 Gradle 段裡 `--tests` 後面那個詞(或 `--tests=` 同一個詞)裡;用既有的 `_gradle_task_list` 切段,那一段恰好一個測試任務,而且任務帶模組路徑(`:app:testDebugUnitTest`、`:lib:test`;「測試任務」在這裡指任務名最後一段等於 `test`,或以 `test` 開頭、以 `UnitTest` 結尾(既有 `_gradle_test_module` 只認 `<模組>:test`,不認 `testDebugUnitTest`,這裡另寫一支判斷,不改它);不帶模組的任務名 Gradle 會在每個模組都跑,結果散在多處)。其他形狀(非 Gradle、`{method}` 出現兩次、多個測試任務)一律照現在逐支跑,不印字。不新增平台欄位。
- **組指令**:把 run_cmd 裡「`--tests` 加上含 `{method}` 的那個詞」這一段當片段,每支測試用既有的 `_run_cmd_expand` 各展開一次,依測試名排序後用空白接起來、換回原處。排序讓同一組測試在每一份工作樹、每個壞法組出同一條指令(基準快取的鍵才對得上);判定時的順序仍照〈用詞〉守的測試排序。
- **結果檔在哪**:`<執行目錄>/<-p 的值>/<模組路徑各段>/build/test-results/<任務名>/`(Gradle 預設位置)。每次合併跑之前把這個資料夾刪掉(先確認它的真實路徑在工作樹裡,同 guard kill 套壞法的路徑圍欄),跑完讀到的就一定是這次寫的。專案改過 buildDir、projectDir 或結果檔位置時找不到資料夾 → 這次呼叫印一行「找不到 JUnit 結果檔,改逐支跑」,之後的壞法都逐支跑,不再每個壞法白付一次合併。
- **對回哪一支**:讀資料夾裡每個 `TEST-*.xml` 的 `testcase`,完整名 = `classname` 加 `.` 加 `name`(去掉 JUnit 5 的結尾 `()` 與參數化的 `[…]`);完整名等於測試名、或以「`.` 加測試名」結尾,就算那支測試的結果(`類別.方法` 與只寫方法名兩種綁法都對得上)。testcase 有 `failure` 或 `error` 子元素 → 那支強殺掉(結果檔就是歸因證據,不再看主控台輸出);沒有 → 存活;`skipped` 照逐支跑時的結果算存活(逐支跑時被略過的測試回 0,現在就是記存活)。
- **判讀順序**:合併跑完依序看——①逾時;②編不過(rc 不是 0、輸出符合 `_KILL_COMPILE_RE`);③測試程序被系統訊號收掉(見下);④結果資料夾在不在;⑤乾淨才採信。前三種本來就不會產生結果檔,所以先判、不檢查資料夾,不會誤觸「找不到結果檔、之後全部逐支」。
- **乾淨才採信**:以下全部成立,這個壞法才用合併結果——沒逾時;每支要跑的測試都對到至少一筆 testcase;每筆失敗的 testcase 都對得到某一支要跑的測試;rc 是 0 若且唯若沒有失敗。任一不成立 → 同一次套壞法之內,照現在的方式逐支跑(照守的測試排序、殺掉或編不過或逾時就停);逐支跑的列照舊判。例外:rc 不是 0、沒有新的結果檔、輸出符合 `_KILL_COMPILE_RE` → 壞法編不過,整個壞法一次判定(逐支跑第一支也是同一個結果),不退回。測試程序被系統訊號收掉(記憶體不足時會發生;`_kill_run` 經 shell 開程序,所以看三種:rc 是負數、rc 是 128 以上(shell 回報子程序被訊號結束,例 137)、或輸出含 Gradle 的 `daemon disappeared unexpectedly`——背景程序被收掉時 gradlew 那一端只回 1)→ 記 error「測試程序被系統收掉(可能記憶體不足,降低 --jobs)」,不退回逐支(逐支跑一樣會被收掉,只是白燒時間)。
- **判定一致的理由**:逐支跑時殺掉它的是「排序第一支強殺掉的」;合併時每支都有結果,取排序第一支強殺掉的,是同一支。逐支跑時排在前面的測試掛住會讓壞法記「測試掛住」;合併時同一支掛住會讓整次合併逾時 → 退回逐支 → 同一個結果。唯一刻意的差別:逐支跑時「紅了但輸出裡歸不到這支」的弱證據(killed_unattributed),合併時由結果檔直接歸因,會判成強殺掉(證據比主控台輸出強)。前提是測試彼此獨立:合併時多支測試在同一個測試行程裡跑,共用靜態狀態的測試可能互相影響,由下一點的合併基準擋。
- **合併基準**:每個平台組一開始先跑一次合併基準(全部守的測試一次 Gradle 呼叫)。全綠 → 每支的基準都記綠、耗時記這一次的。有測試紅 → 紅的那幾支各自再量一次單支基準:單支也紅 → 照現在記 abort 拿掉;單支綠(只在一起跑時紅,測試互相影響)→ 那幾支不進合併、每個壞法另外逐支跑。合併基準逾時或結果檔讀不出來 → 這次呼叫整個退回逐支(基準也照現在逐支量)。
- **逾時**(「下限」= 既有的逾時下限環境變數 `LUMOS_KILL_TIMEOUT_FLOOR`,預設 20 秒):合併基準的上限 = max(600 秒, 下限, 30 秒 × 測試支數)(64 支是 1920 秒;現在單支基準上限 max(600, 下限) 不變);合併跑壞法的上限 = max(合併基準耗時 × 5, 下限)(沿用「基準耗時 5 倍」的算法,基準換成合併那一次);退回逐支時每支的上限照現在(那支有單支基準就用它,沒有就先量)。
- **取捨:殺掉就停沒了**:被殺掉的壞法現在不到 1 分鐘(排第一支就殺掉,只跑一兩次);合併後每個壞法都跑完 64 支,但只付一次編譯與一次測試行程啟動,估 1–2 分鐘。存活的從約 6 分鐘降到同一個量級,整體大幅省。考慮過「先單跑排第一的 K 支、沒殺掉再合併其餘」,這一版不做(多一段分流、多一組要對的判定),RETIRE-IF 與 REVISIT 量到被殺掉的壞法合併後比現在慢兩倍以上再加。
- **接線**:`cmd_guard_kill` 多一個選用參數 `merge`(真:同一個 `group` 連續、而且 file、old、new、also 都相同的配方視為同一個壞法,套一次壞法、合併跑、逐條交出列;每條列照舊經 `on_row` 交出,沒有略過列)。不傳時行為與輸出不變。choice-kill 預設傳真,`--no-merge` 傳假。

### 2. 平行分片(`--jobs N`,預設 1)

- **份數與記憶體保護**:`--jobs` 收 1–8 的整數,其他 rc 2。實際份數 = min(N, 這次要跑的壞法數, 記憶體上限);記憶體上限 = floor(實體記憶體 × 0.6 ÷ 每份估計),每份估計讀環境變數 `LUMOS_CHOICE_SHARD_MB`(預設 6144,約等於一個 Gradle 背景程序、一個 Kotlin 編譯背景程序分攤、一個測試行程各 2GB 上下;設 0 跳過這項檢查)。實體記憶體用 `os.sysconf` 的頁大小乘頁數讀(macOS 與 Linux 都有);讀不到 → 只開 1 份並印原因。實際份數小於要求時印一行「要求 N 份、記憶體只夠 M 份(每份估 X MB,可用 LUMOS_CHOICE_SHARD_MB 調)」。32GB 機器預設估計算出來是 3 份。不做跑到一半看剩餘記憶體動態減份(見〈不做〉)。
- **分工**:這次要跑的壞法(`_choice_kill_pick` 排好、`--max-mutants` 截過的清單)依序輪流分給各份(第 i 個給第 i mod M 份),每個壞法恰好在一份裡跑。每份是一條 daemon 執行緒,各自呼叫一次 `cmd_guard_kill`(帶自己那份配方、`source`、`stop_group_on`、`on_row`、`should_stop`、`merge`,以及下一點的共用基準),各自建一棵隔離工作樹、各自編譯。
- **基準只量一次**:`cmd_guard_kill` 多一個選用參數 `baseline_share`(一個帶「基準表」與「量好了」旗號的物件)。表是空的 → 這一份照常量基準(合併模式量合併基準;逐支模式在第一個壞法之前把每條測試指令的基準全量完,不再等用到才量),量完填表、立旗號;表已填 → 直接用表,不量。choice-kill 先只啟動第一份,等旗號立起(或第一份結束)才啟動其餘各份;其餘各份的第一個壞法要付冷編譯,逾時上限由基準耗時(第一份的基準本來就含冷編譯)的 5 倍蓋過。基準表的鍵是展開後的指令字串(不含工作樹路徑,各份相同)。不傳 `baseline_share` 時照現在每條指令用到時才量。
- **帳由主程序串行寫**:各份的 `on_row` 只把列放進一個佇列;主程序的迴圈每次最多等 0.1 秒取列,交給既有的 `_ChoiceKillRun.on_row` 判定、寫治理帳、印一行——判定狀態、嘗試次數、統計只在主程序改。
- **停**:`should_stop` 各份共用:收到第一個中斷訊號、或總時限到了,主程序立停止旗標,各份在配方之間看到就停(合併模式下「配方之間」是每個壞法之間,正在跑的那次合併最多要等它跑完,約 1–2 分鐘)。
- **建與收工作樹排隊**:`_isolated_worktree` 裡 `git worktree add`、`worktree remove`、`worktree prune` 與清殘骸那段包一把模組層的鎖,同一個程序裡同時只有一份在動 git 的工作樹登記(每份的資料夾都叫 `wt`,git 在 `.git/worktrees/` 底下依資料夾名取登記名、重名才加編號,同時建有撞名的可能;沒實測過會不會真的撞,排隊的成本只有幾百毫秒,先排隊,S11 驗)。單執行緒的既有呼叫端拿鎖不會等。清殘骸(`sweep_repo`,清超過一天的 `lumos-kill-*`)要跳過 `_KILL_WT_LIVE` 裡登記中的路徑:多份跑超過一天時,後起的份不能把別份還在用的工作樹當殘骸清掉。
- **輸出**:`cmd_guard_kill` 的逐條輸出收起來那一層(`contextlib.redirect_stdout`)改成由 choice-kill 在啟動各份之前包一次、全部結束才離開(它換的是全程序共用的標準輸出,各執行緒各包一次會互相蓋掉);判定那一行照舊印到 `_ChoiceKillRun` 建立時記下的標準輸出。
- **某份當掉**:那一份的執行緒丟例外、或那份的工作樹建不起來 → 主程序印一行「第 k 份中斷:<原因>」,那一份還沒判完的壞法不記帳、算進「還有 M 個沒跑」,rc 2;其他份照跑完。`_ChoiceKillRun.run` 收尾那段「呼叫正常結束還沒判、但有列的壞法照記缺結果」要跳過當掉那一份的壞法(那一份不是正常結束,缺的列是它當掉造成的,不是測試沒結果)。不把它的壞法改分給別份(下次呼叫會再挑到,帳上沒有它們)。
- **中斷**:第一個訊號(Ctrl-C、SIGTERM、SIGHUP;沿用 `_situation_rule_signals` 的延後模式)→ 停止旗標,各份把正在跑的那次跑完就停、照常收掉自己的工作樹;主程序等各份結束(逐條等、每次 0.1 秒)、把判定完整的壞法記完、記一筆 interrupted 的 run、rc 2。第二個訊號 → 既有的強制結束:收掉 `_KILL_RUN_LIVE` 裡所有份正在跑的測試程序群組、印 `_KILL_WT_LIVE` 裡每一份留下的工作樹路徑、立刻離開。
- **run 那筆多三欄**:`jobs`(實際份數)、`merged`(由合併那次呼叫判定的壞法數,含編不過與被系統收掉)、`fallback`(退回逐支的壞法數,含合併基準整次退回與找不到結果檔之後的壞法;`--no-merge` 時兩欄都是 0),都是整數,照既有欄位登記慣例進型別表與 `_gov_row` 白名單;RETIRE-IF 讀它們。
- **收尾提示**:份數大於 1 時最後印一行「Gradle 背景程序會閒置留著約 3 小時佔記憶體;要立刻釋放跑 ./gradlew --stop(會停掉同一版 Gradle 的全部背景程序,含 IDE 開的)」。工具不自動停。

### 3. 不改工具的基線(現在就能用)

一次呼叫跑完、不分段:`lumos choice-kill --max-mutants 200 --max-seconds 86400`,用 `nohup` 或背景執行。基準只量一次(現在每段重量);中斷時判定完整的照記,重跑會跳過已有紀錄的行。這是本案上線前的做法,也是〈預期效益〉的對照組。限制:要記得開跑後別再改那幾支檔(T44:結果綁 HEAD,改過的行指紋不同,會變缺紀錄重跑)。

## 預期效益(估算,待 S13 實測)

以實驗專案 183 個壞法、64 支測試估:

| 做法 | 每個壞法 | 183 個合計(牆上時間) | 估算依據 |
|---|---|---|---|
| 現在,一段 30 分鐘 | 平均約 5–6 分鐘(含每段重量基準攤進來) | 15–18 小時(約 37 段) | 實測:一段只判 5 個 |
| 基線:一次呼叫不分段 | 平均約 3.6–4.8 分鐘(基準只量一次) | 約 11–15 小時 | 每段省下重量基準的那幾分鐘 |
| 合併 | 約 1–2 分鐘(一次編譯加一次測試行程跑 64 支) | 約 3–6 小時,外加一次合併基準(冷編譯加 64 支,估 5 分鐘內) | 被殺掉的壞法現在不到 1 分鐘(編譯加一兩次呼叫),合併後多的是同一行程裡多跑 60 幾支 |
| 合併加 3 份 | 同上,三份同時 | 約 1.2–3 小時(假設搶 CPU 後實得 2–2.5 倍) | 10 核跑 3 份 Kotlin 編譯加 Robolectric 測試行程 |

估算的不確定:每次編譯多久(專案有沒有 kapt/ksp)、64 支在同一行程裡跑多久、三份同時搶 CPU 實得幾倍,都沒量過;S13 在實驗專案量一次,差兩倍以上就改這張表(REVISIT)。

## 不做

- 不新增平台欄位(合併用的指令範本、結果檔位置):Gradle 形狀從現有 run_cmd 認得出;認不出來的專案照逐支跑。
- 不做「先單跑排前面幾支、再合併其餘」的兩段式(見〈做法〉1 取捨)。
- 不跨呼叫快取基準(綁提交、測試雜湊、指令):合併後基準只剩一次呼叫;跨呼叫快取要管環境(JDK、Gradle、SDK)變了怎麼失效,省的不多。
- 不做動態工作佇列與跑到一半依剩餘記憶體減份;份數開跑前定。
- 不自動停 Gradle 背景程序、不改使用者的 run_cmd(不加 `--no-daemon`、`--no-build-cache`)。
- 不改判定規則、推送閘、回報上限、`--max-mutants` 與 `--max-seconds` 的預設值。
- 不處理 T44「開跑後又改程式」:帳以行指紋為鍵,改過的行自然變缺紀錄;加速只縮短這段窗口。
- 不碰合約殺傷力(`lumos guard kill` 指令本身)與人裁 `situation-rule`:它們不傳新參數、行為不變。
- 非 Gradle 的 kotlin-junit 平台(例:自訂腳本)不合併;`--jobs` 照樣能用。

## 驗收條款

- [S1] 當平台 run_cmd 是 `./gradlew :app:testDebugUnitTest --tests '*{method}'`、同一個壞法守三支測試時,choice-kill 應 組出一條帶三個 `--tests` 片段(依測試名排序)的指令只呼叫一次;run_cmd 不是 Gradle、`{method}` 出現兩次、或測試任務不帶模組路徑時 應 照逐支跑 [test:t_choice_kill_merge_cmd]
- [S2] 當假 Gradle 依結果檔寫出「第二支與第三支都殺掉」「全部存活」「編不過」三種壞法時,合併模式 應 跟 `--no-merge` 判出同樣的判定與殺掉它的測試(取排序第一支強殺掉的),而且每個壞法只呼叫一次 Gradle [test:t_choice_kill_merge_matches_single]
- [S3] 當合併跑之後結果資料夾不在、某支測試對不到 testcase、有失敗的 testcase 對不到任何一支、或 rc 跟結果不一致時,choice-kill 應 對那個壞法退回逐支跑、判定與 `--no-merge` 相同;資料夾不在時 應 印一行並讓這次呼叫之後的壞法都逐支跑 [test:t_choice_kill_merge_fallback]
- [S4] 當合併跑逾時時,choice-kill 應 照原排序逐支重跑那個壞法:排在掛住那支之前有強殺掉的記 killed,否則記跑不出結果「測試掛住」;合併跑的逾時上限 應 是 max(合併基準耗時 × 5, 下限) [test:t_choice_kill_merge_timeout]
- [S5] 當合併基準有一支紅時,choice-kill 應 單獨重量那一支:單獨也紅就記基準不綠拿掉,單獨綠就讓那支在每個壞法另外逐支跑、其餘照合併 [test:t_choice_kill_merge_baseline]
- [S6] 當同一組壞法分別以 `--jobs 1` 與 `--jobs 3` 跑時,兩次的每個壞法判定與殺掉它的測試 應 相同;`--jobs 3` 時 應 觀察到三棵不同的隔離工作樹同時存在、基準指令在整次呼叫只跑一次 [test:t_choice_kill_jobs_matches_single]
- [S7] 當 `--jobs 3` 跑 7 個壞法時,治理帳 應 恰好有 7 筆 choice-kill(每個行指紋一筆、attempt 各加 1)與 1 筆 run(`jobs` 是 3、`merged` 加 `fallback` 等於判定數;`--no-merge` 時兩欄都是 0) [test:t_choice_kill_jobs_ledger_once]
- [S8] 當 `--jobs 3` 跑到一半收到第一個中斷訊號時,各份 應 不再開始新的壞法、正在跑的跑完、判定完整的照記、記一筆 interrupted 的 run、rc 2,結束後 應 沒有留下工作樹與測試程序;第二個訊號 應 收掉所有份的測試程序群組並印出每份工作樹的路徑 [test:t_choice_kill_jobs_interrupt]
- [S9] 當其中一份的工作樹建不起來或執行緒丟例外時,其他份 應 照跑完並記帳,那一份沒判完的壞法(含已交出部分列的) 應 不記帳也不記缺結果、算進沒跑、rc 2;測試程序被訊號收掉時 應 記跑不出結果「測試程序被系統收掉」而且不退回逐支 [test:t_choice_kill_jobs_shard_failure]
- [S10] 當實體記憶體是 16GB、`--jobs 3`、每份估計 6144MB 時,choice-kill 應 只開 1 份並印出要求與實際份數;32GB 時 應 開 3 份;`LUMOS_CHOICE_SHARD_MB=0` 時 應 不檢查;`--jobs` 是 0 或 9 時 應 rc 2 不跑;份數多於壞法數時 應 只開壞法數那麼多份 [test:t_choice_kill_jobs_memory_cap]
- [S11] 當同一個程序裡四條執行緒同時對同一個 repo 建與收隔離工作樹時,四棵 應 都建成、收完後 `git worktree list` 應 只剩主工作目錄 [test:t_isolated_worktree_concurrent]
- [S12] 當 `cmd_guard_kill` 沒傳 `merge` 與 `baseline_share` 時,行為與輸出 應 跟現在相同(既有 rc 優先序、--json 純度、選用參數測試照綠) (擴充既有測試,加這兩個參數的案例) [test:t_choice_guard_kill_new_params]
- [S13] 當在實驗專案用 `--jobs 3` 跑同一批壞法時,每個壞法的平均秒數 應 記下來跟〈預期效益〉對照,而且抽 10 個壞法另用 `--no-merge --jobs 1` 重跑 應 判定相同 [manual:在 Android 實驗專案跑 lumos choice-kill --jobs 3 與 --no-merge --jobs 1 各一次,讀治理帳 run 的 secs、ran、merged、fallback 與兩次的判定逐筆比對]
- [S14] 當逐支跑時某個壞法判成「紅了但輸出裡歸不到這支」(弱證據),合併跑時結果檔裡那支測試確實失敗,應 判成被那支殺掉;結果檔裡那支沒有失敗時 應 不升級、照逐支跑的判定 [test:t_choice_kill_merge_attributes_weak]

## 回退

- 本案上線時壓成一個功能提交,單一提交還原即可回到現在的行為;還原前先把那段期間追加的治理帳行另存、還原後接回帳尾(帳是簿記檔,新欄位舊版讀者會忽略)。
- 不還原程式只想關掉:合併用 `--no-merge`、平行不帶 `--jobs`(預設 1),行為就跟現在相同(S12 守不傳新參數時不變)。
- 帳上新加的 `jobs`、`merged`、`fallback` 三欄:舊版 lumos 讀到不認得的欄位照略過,推送閘只看 choice-kill 每筆的判定欄,不受影響。

## 實務隱患

- 跑太久/資源:三份同時跑會搶 CPU 與磁碟,單一壞法變慢,逼近逾時上限的可能判成「測試掛住」;逾時照各份自己的基準耗時算(第一份量的基準含冷編譯,倍數寬)。份數預設 1,上限由記憶體估計擋;每份估計是粗估,實際用量看專案的 `org.gradle.jvmargs` 與測試行程堆大小,記憶體不夠時 macOS 會開始壓縮與換頁、整機變慢——S13 量一次,REVISIT 照實改預設估計。
- Gradle 背景程序與共用快取:不同工作樹是不同專案資料夾,同時的建置各用一個 Gradle 背景程序;使用者家目錄的 Gradle 快取有自己的檔案鎖、設計上允許多個建置同時用;Kotlin 編譯背景程序 JVM 參數相同時被共用,同時編譯會排隊。建置快取若開著,同樣的輸入會直接取回上次的輸出(含測試結果),結果跟重跑相同,只是不穩定的測試會被「凍」在第一次的結果。Robolectric 第一次跑會下載 Android 映像檔到本機 Maven 庫,多份同時第一次下載可能互搶,實驗專案已下載過;新專案建議先 `--jobs 1` 跑一次。
- 閒置的 Gradle 背景程序:跑完後每份一個背景程序會閒置約 3 小時佔記憶體;收尾印提示,不自動停(會停到 IDE 的)。
- 合併跑時測試互相影響:同一測試行程裡共用靜態狀態的測試,合併時結果可能跟單跑不同;合併基準擋掉「沒改程式就互相影響」的,壞法造成的互相影響擋不到,這時合併可能多判出殺掉——S13 抽查與 RETIRE-IF ① 盯著。
- 結果檔讀法:XML 用標準函式庫剖析;讀不了、檔案過大(單檔超過 16MB 視為讀不了)一律退回逐支,不當掉。資料夾刪除限定工作樹裡,先比真實路徑。
- 指令長度:64 支約 4KB,遠小於系統參數長度上限;守的測試超過 500 支時分成多次合併呼叫(每次最多 500 支),結果合起來判。
- 中斷等待變長:第一個 Ctrl-C 要等正在跑的那次合併跑完(估 1–2 分鐘),提示訊息照舊說「再按一次強制結束」。
- 守衛面:這是推送閘要的紀錄的產生器;誤判的方向——合併只會把「歸不到」升成「殺掉」(結果檔有失敗才算),其他不乾淨的情況一律退回逐支;平行不改判定,只改誰去跑。最壞是誤記殺掉讓一個沒守住的選擇點通過推送閘,由 S2、S3、S6 與 S13 抽查守。
- 併發與交易:同一個程序內多條執行緒;帳只由主程序寫(佇列交列),工作樹登記用一把鎖排隊;不支援兩個 choice-kill 程序同時對同一個 repo 跑(兩邊會挑到同一批壞法、各寫一筆,下次挑行以最新一筆為準,不會壞帳但白跑);T41 的「多程序寫帳」需求由單程序多份取代。
