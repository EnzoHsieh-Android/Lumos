# 選擇點變異加速_計劃

## 白話

`lumos choice-kill`(改動選擇點:每一行挑一個壞寫法、跑計劃條款綁的測試,看測試會不會紅)在真實 Android 專案上太慢:每個壞法要把 64 支綁定測試一支一支各叫一次 Gradle,每次叫 Gradle 都要付啟動、設定與開測試行程的固定成本。好比洗 64 個碗,每洗一個就把熱水器重新燒一次。這份計劃只做一件事:同一個壞法要跑的測試合成一次 Gradle 呼叫(Gradle 一次可以帶多個 `--tests`),誰殺掉壞法改讀 Gradle 寫出的 JUnit 結果檔判;結果讀不出來、或不乾淨,這個壞法就退回現在的逐支跑。同時開多份工作樹平行跑另開 [[Projects/選擇點變異平行_計劃]],等這份上線實測後再設計。另外把「不改工具、一次呼叫跑完不分段」寫成對照基線。

WHY:同一個壞法的綁定測試合成一次 Gradle 呼叫、改讀 JUnit 結果檔判誰殺掉;結果讀不出來、缺某支、有歸不到任何一支的失敗、或合併跑逾時,這個壞法就退回逐支跑 [出處:2026-11-23 使用者裁「兩種加速都做」,同日再裁「這份只做合併,平行另開」;實驗專案實測存活壞法約 6 分鐘、64 次 Gradle 呼叫] [因:時間花在每次呼叫的固定成本(啟動、設定、測試行程),不是測試本身;論文 2.1 Google 也是以測試目標(一個目標含多支測試)為單位跑] [不選:新增平台欄位寫合併用的指令範本(Gradle 的形狀從現有 run_cmd 就認得出,多一個欄位多一個要對齊的地方);解析主控台輸出判誰殺掉(多支一起跑時輸出交錯、還會被 256KB 上限截掉;結果檔一支一筆);另寫一套 JUnit 讀法(專案已有加固過的 `test_quality.junit()`)] [代價:殺掉就停的提早結束沒了,被殺掉的壞法也要跑完 64 支;掛住的壞法要等合併逾時再退回逐支]

PRIOR-ART: ①Google〈Practical Mutation Testing at Scale〉2.1:用逐行覆蓋率決定每個壞法要跑的最小測試集,測試以「測試目標」(一個目標含多支測試)為單位執行(https://arxiv.org/pdf/2102.11378)。我們沒有覆蓋率(既有天花板),跑全部守的測試,但照它一次跑一整批。②PIT FAQ:只跑覆蓋到被改那一行的測試,剩下的依執行時間由短到長排(https://pitest.org/faq/);PIT 增量分析:上次殺掉、而被測類別與殺掉它的測試都沒變,就沿用殺掉的結果,頁面自己寫明依賴改變很少影響結果是「未證明」的假設、這些優化會帶進可能的誤差(https://pitest.org/quickstart/incremental_analysis/)。我們的帳同樣沿用殺掉的結果(以行指紋為鍵),所以判法本身改了時要有辦法讓舊判定作廢:每筆帶判法版本 `merge_ver`,版本升了合併判定就算過期(這一步是本案自訂,不是 PIT 的做法)。③Gradle 文件:「可以給多個 `--tests`,每個樣式都生效」;JUnit XML 結果預設寫在 `build/test-results/<測試任務名>`、每個測試類別一個檔(https://docs.gradle.org/current/userguide/java_testing.html)。④本 repo:JUnit XML 一律經 `scripts/test_quality.py` 的 `junit()` 讀(邊解析邊數深度、拒收代碼 `JUnitRejected`;安全證據閘 `_secev_junit_facts` 也經它),本案照用。
RETIRE-IF: ①累計 `judged` 為 merged 或 fallback 的 choice-kill 判定 50 筆以上之後,fallback 占其中三成以上(結果檔讀法在真專案上靠不住),或 `--recheck --no-merge` 抽查查出一筆合併判定跟逐支不同、而且是讀法的錯 → 把合併預設關掉(`--no-merge` 變預設)、回頭換讀法。②同一專案上線後 run 事件 `merged` 大於 0 的呼叫,`secs` 除以 `ran` 的中位數,沒有比上線前(run 事件沒有 `merged` 欄)的呼叫低一半以上 → 拿掉合併。兩條讀的欄位都在 `_gov_row` 白名單(見〈做法〉6)。

## 用詞

- **守的測試排序**:[[Projects/改動選擇點都要有需求守住_計劃]]〈用詞〉守的測試的排序(計劃落點指到被改檔的家的先、再依計劃名與條款順序);本文的「排序第一支」都指它。
- **合併道與逐支道**:一個平台組的守的測試,在合併基準之後分成兩組——合併道(一起跑一次 Gradle)與逐支道(每個壞法照現在一支一支跑;收:合併基準裡對不到案例、對到多個類別、或只在一起跑時紅,而單獨跑是綠的那幾支)。名稱檢查沒過的、單支基準不綠的,兩道都不進。
- **完整名**:結果檔一筆案例的 `classname` 把 `$` 換成 `.` 之後,加 `.`,加 `name` 去掉參數尾巴(第一個 `(` 或 `[` 起到結尾)。
- **判法**(每一列與每筆治理帳的 `judged`):`merged`(這個壞法的判定來自合併那一次呼叫:結果檔、或那一次判出的編不過、被系統收掉)、`fallback`(這個壞法跑了合併、不乾淨或逾時,改逐支跑判出)、`single`(這個壞法沒跑合併:run_cmd 不能合併、`--no-merge`、這次呼叫整個退回逐支、檔不在平台 repo、old 對不到(drifted)、名稱檢查沒過、基準不綠拿掉)。

## 做法

### 1. 認得出才合併、怎麼組指令

- **條件**(全部成立才合併;任一不成立照現在逐支跑,不印字):
  - 不在 Windows(`_IS_WIN` 為假;下面用的切詞函式是 POSIX 規則)。
  - run_cmd 只出現一次 `{method}`,而且不含 `{python}`。
  - 用標準函式庫 `shlex.split(run_cmd)`(posix 模式)切得開,切出的詞裡沒有 shell 控制字元組成的詞(`;`、`&&`、`||`、`|`、`<`、`>`、`(`、`)`)、也沒有任何詞含 `$` 或反引號——也就是整條就是一個 Gradle 指令(`cd android && ./gradlew …`、`sh -c '…'` 這類照逐支跑)。
  - 含 `{method}` 的詞是 `--tests` 的下一個詞,或本身是 `--tests=<…>` 一個詞。
  - 用既有的 `_gradle_task_list(run_cmd)` 切段:恰好一個 Gradle 段、那一段恰好一個任務被新的 `_gradle_unit_test_task(task)` 認成單元測試任務:任務帶模組路徑、最後一段是 `test` 或符合 `test<變體>UnitTest`(例 `:app:testDebugUnitTest`、`:lib:test`),模組各段用既有的 `_SR_MODULE_PART` 驗;回 (模組各段, 任務名) 或 None。不改既有的 `_gradle_test_module`:它的呼叫端 `_gradle_blocked_tasks` 靠「變體任務回 None」判「不擋」,改了會讓 Android 的 `testDebugUnitTest` 被當成要擋的任務。不帶模組的任務名 Gradle 會在每個模組都跑,結果散在多處,不合併。
  - 組出的指令(UTF-8 位元組數)不超過 32768:`_kill_run` 經 `sh -c` 把整條指令當一個參數交出,Linux 單一參數上限 131072 位元組,留四倍餘裕;超過就這次呼叫不合併、逐支跑(取代初稿的「500 支分批」)。
- **組指令**:`shlex.split` 切出的詞裡,把「`--tests` 加下一個詞」(或 `--tests=…` 那一個詞)換成合併道每支測試各一組:`--tests` 與「原詞裡的 `{method}` 換成 `_name_filter_escape(測試名, 平台的 name_filter)`」的結果;合併道的測試依測試名排序後依序放;最後用 `shlex.join` 把全部詞接回一條指令。`shlex.join` 對每個詞重新加引號:原本寫的引號樣式(單引號、雙引號、`--tests='…'`)不保留字面,保留的是詞的內容,交給 shell 後 Gradle 收到的參數跟逐支跑時一樣。排序讓同一組測試每個壞法組出同一條指令(基準快取的鍵才對得上);判定時的順序仍照守的測試排序。
- **結果資料夾**:`<執行目錄>/<那一段 -p 的值>/<模組各段>/build/test-results/<任務名>/`(Gradle 預設位置)。這個位置只是候選,由合併基準那一次證明(見 3);每次合併跑之前把它刪掉(先確認真實路徑在工作樹裡,同 guard kill 套壞法的路徑圍欄),跑完讀到的就一定是這次寫的。

### 2. 結果檔怎麼讀、怎麼對回哪一支

- **讀法**:資料夾裡每個 `TEST-*.xml` 各自讀成位元組、各自呼叫一次 `test_quality.junit(raw)`(模組經既有的 `_secev_tq()` 取得;取不到 → 這次呼叫不合併)。逐檔呼叫的理由:`junit()` 的合約是「一份文件一個 testsuite(s)」,重複身分、零案例、suite 層錯誤、計數不一致都以整份文件為單位拒收;Gradle 本來就一個類別一個檔,逐檔讀剛好對上它的單位,不用為了合在一起而改它或包一層假的根元素。任一檔被拒收(`JUnitRejected`,含 `zero_cases`、`report_duplicate_identity`、`suite_error`)、剖析錯誤(`ET.ParseError`)、深度過深(`RecursionError`)或讀檔失敗 → 這個壞法當「結果讀不出來」,退回逐支;接例外的寫法照 `_secev_junit_facts`。
- **對名**:案例的 `id` 是 `classname::name`;用〈用詞〉完整名比。一支測試名 m 對到一筆案例:完整名等於 m,或以「`.` 加 m」結尾。巢狀類別 `pkg.Outer$Inner` 換成 `pkg.Outer.Inner` 後,綁成 `Inner.method` 或 `method` 都對得上;JUnit 5 的 `aCase()`、`aCase(int)`、JUnit 4 參數化的 `aCase[0]` 去掉參數尾巴後是 `aCase`;JUnit 5 參數化的顯示名(例 `[1] 5`)沒有方法名,對不到。
- **一支測試的結果**:對到的案例裡任一筆狀態是 `failure` 或 `error` → 那支殺掉;全部是 `passed` 或 `skipped` → 存活(`skipped` 照逐支跑時的結果:被略過的測試回 0,現在就記存活)。
- **歸因夠不夠強**:對到那支測試的案例,完整名(去掉參數尾巴後)只有一個 → 結果檔歸因成立,殺掉記強證據;有兩個以上(例:只綁方法名、兩個類別都有同名方法)→ 有歧義,這個壞法退回逐支(合併基準時就分得出來的,直接放逐支道,見 3)。

### 3. 合併基準

- 每個平台組在第一個壞法之前,對沒套壞法的樹:
  1. 每支守的測試先過現有的兩道檢查:`_test_name_ok`(名稱不合法,拒絕注入)與 `_name_collision_reason`(篩選會連帶選中別支);沒過的照現在記 error 列(判法 single),不進合併、也不進逐支道。
  2. 其餘全部跑一次合併基準(上限 = max(600 秒, 下限, 30 秒 × 支數),64 支是 1920 秒;「下限」= 既有的 `LUMOS_KILL_TIMEOUT_FLOOR`,預設 20 秒)。
  3. 合併基準逾時、結果資料夾不在、或結果檔讀不出來 → 這次呼叫整個不合併(印一行到標準錯誤:「找不到 JUnit 結果檔(或讀不出來),這次改逐支跑」,其後全部照現在逐支跑、基準也照現在用到才量)。只有這一種情況整次關掉。
  4. 結果檔讀得出來:每支測試照 2 對名——對到恰好一個完整名而且沒失敗 → 進合併道,基準記綠、耗時記合併這一次;對到恰好一個完整名而且失敗、或對不到任何案例、或對到兩個以上完整名 → 那支照現在量單支基準(`_kill_run(該支指令, 執行目錄, max(600, 下限))`,存進同一份 `baselines`):單支不綠(含 Gradle 的 No tests found 讓 rc 不是 0)→ 照現在記 abort 拿掉(判法 single);單支綠 → 放進逐支道。
  5. 熱基準(只量耗時):合併道不是空的時,刪結果資料夾後再跑一次合併道的指令(就是之後每個壞法要用的那一條;樹沒變,編譯已是最新,量到的是熱編譯的耗時;上限同第 2 步)。乾淨(沒逾時、沒被系統收掉、rc 是 0、結果檔讀得出來而且合併道每支都對到恰好一個完整名、沒有失敗)→ 記它的耗時當「熱基準耗時」;不乾淨或逾時 → 不改任何分道與綠紅判定,熱基準耗時改用第一次(第 2 步)的耗時,印一行到標準錯誤:「熱基準沒跑乾淨,逾時改用含冷編譯的基準耗時」。第一次負責判綠紅與證明結果檔位置,第二次只負責耗時。刪掉結果資料夾是為了讓 Gradle 不把測試任務判成「已是最新」而略過(略過就沒有結果檔,會落到「不乾淨」、退回第一次的耗時,方向安全);但專案開了建置快取時,第二次可能直接從快取取回結果檔、耗時只有幾秒,熱基準偏短、之後的壞法一律逾時退回——判定不會錯、只是合併白付,見〈實務隱患〉。
- 合併基準有逐支道的測試時,印一行到標準錯誤:「N 支測試在結果檔對不到名字或只在一起跑時紅,每個壞法另外逐支跑(巢狀類別、參數化顯示名、同名方法、測試互相影響)」——讓人知道合併為何沒省到時間。

### 4. 每個壞法怎麼跑、怎麼判

- **跑**:套一次壞法(現有套壞法那段:`_kill_wait_new_second` → 寫入 → `_kill_after_write`)。合併道刪結果資料夾後跑一次合併指令;逐支道照守的測試排序一支一支跑,**不**因殺掉而停(要知道排序第一支殺掉的是誰,見下)。
- **合併那一次怎麼判**(依序看,命中就停):
  1. 逾時 → 退回逐支(見下)。
  2. 被系統收掉:rc 是負數、rc 是 128 以上(`_kill_run` 經 shell 開程序,shell 回報子程序被訊號結束,例 137)、輸出含 Gradle 的 `daemon disappeared unexpectedly`、或輸出含測試行程被收掉的寫法(預期是 `Process 'Gradle Test Executor <N>' finished with non-zero exit value 137` 這類;字樣待實作時在實驗專案實測確認後寫死)→ 合併道每支記 error「測試程序被系統收掉(可能記憶體不足)」(判法 merged),不退回逐支(逐支跑一樣會被收掉,只是白燒時間)。
  3. 編不過:rc 不是 0、**而且**結果資料夾裡沒有這次的新結果檔、**而且**輸出符合 `_KILL_COMPILE_RE`,三者都要 → 合併道排序第一支記編不過(compile_error,判法 merged),其餘(含逐支道還沒跑的)記略過;整個壞法一次判定(逐支跑第一支也是同一個結果)。有新結果檔時不判編不過:測試名或失敗訊息裡剛好有 `Compilation error` 字樣也不會誤判。
  4. 結果資料夾不在(合併基準已證明它在):只有這個壞法退回逐支,不關掉之後的合併(例:壞法讓 kapt、KSP、資源合併失敗,測試任務根本沒跑到)。
  5. 乾淨才採信——全部成立才用合併結果:結果檔每份都讀得出來;合併道每支都對到恰好一個完整名;每筆失敗的案例都對得到合併道某一支;rc 是 0 若且唯若沒有失敗。成立 → 合併道每支照 2 記殺掉(強證據)或存活(判法 merged)。不成立 → 退回逐支。
- **退回逐支**(判法 fallback):
  1. 先還原壞法:用 `cmd_guard_kill` 現有的還原那一步(`git -C <工作樹> checkout -- :(literal)<檔>`,前後照 `_kill_wait_new_second` 等秒、還原後 `_kill_after_write` 讀回修改時間;還原失敗照現在記「revert 失敗」、這一組作廢)。
  2. 這個壞法合併道的測試裡,還沒有單支基準的,在沒套壞法的樹上逐一量(同 3 第 4 步的單支基準那段,存進同一份 `baselines`,這次呼叫內快取,之後再退回不用再量);單支不綠的照現在記 abort 拿掉。
  3. 用現有套壞法那段重套壞法,照現在的方式逐支跑合併道的測試(照守的測試排序、強殺掉或編不過或逾時就停;逾時上限 = max(那支單支基準耗時 × 5, 下限));逐支跑的列照舊判(主控台歸因、弱證據規則不變)。
  4. 跑完照常還原。
- **逾時**:合併跑壞法的上限 = max(熱基準耗時 × 5, 下限)(沿用「基準耗時 5 倍」,基準換成 3 第 5 步量的熱基準;熱基準沒跑乾淨時用第一次合併基準的耗時)。用熱基準的理由:第一次合併基準含冷編譯(估 5 分鐘),拿它乘 5 讓掛住的壞法每個多等約 25 分鐘;熱基準不含冷編譯,壞法那一次只多一次增量編譯,5 倍仍有餘裕(使用者 2026-11-23 裁,實作前就定)。退回後每支照上一點用單支基準。
- **交列與判定時機**:合併模式下,`cmd_guard_kill` 在一個壞法的所有列(合併道、逐支道、退回逐支、略過列)都產生之後才一次經 `on_row` 交出;`_ChoiceKillRun.on_row` 在合併模式下不在第一個決定性的列就判,等這個壞法每支守的測試都有列才呼叫 `_choice_kill_judge`。這樣排序第一支(可能在逐支道)跟合併道的結果一起比,殺掉它的測試與 `--no-merge` 相同。略過列只出現在決定性的列之後,`_choice_kill_judge` 原本的判法不受影響。
- **停**:`should_stop`(第一個中斷訊號、總時限)在合併模式下於壞法之間看,一個壞法不會跑一半就停;第一個 Ctrl-C 最久要等正在跑的那個壞法跑完(含它的合併逾時)。

### 5. 判定一致的範圍與取捨

- **一致的理由**:逐支跑時殺掉它的是「排序第一支強殺掉的」;合併模式每支都有結果(合併道、逐支道都跑完)才判,取排序第一支強殺掉的,是同一支。逐支跑時排在前面的測試掛住會讓壞法記「測試掛住」;合併時同一支掛住讓整次合併逾時 → 退回逐支 → 同一個結果。
- **刻意的差別**(使用者 2026-11-23 裁「一致或更強」):逐支跑時「紅了但輸出裡歸不到這支」的弱證據(killed_unattributed),合併時若結果檔裡那支的案例確實失敗、而且完整名只有一個,判成強殺掉;完整名有歧義的不升級(退回逐支,結果跟逐支相同)。
- **已知限制**:同一測試行程裡共用靜態狀態的測試,壞法讓一支失敗後留下壞狀態、排序在前的另一支跟著失敗時,合併會把殺掉它的測試記成前面那支(判定仍是殺掉,記錯的是 `killing_test` 與 `clauses`)。合併基準只擋得到沒套壞法時就互相影響的;這種壞法造成的互相影響沒有機械檢查,唯一的把關是 S18 的抽查(第一輪設計審 c4,使用者放行)。
- **取捨:殺掉就停沒了**:被殺掉的壞法現在不到 1 分鐘(排第一支就殺掉,只跑一兩次);合併後每個壞法都跑完 64 支,但只付一次編譯與一次測試行程啟動,估 1–2 分鐘。考慮過「先單跑排第一的 K 支、沒殺掉再合併其餘」,這一版不做(多一段分流、多一組要對的判定);S18 量到被殺掉的壞法合併後比現在慢兩倍以上再加。

### 6. 帳、旗標與作廢

- **列與帳的判法欄**:`cmd_guard_kill` 交出的每一列多一個欄位 `judged`(〈用詞〉判法三值;不傳 `merge` 時一律 single)。choice-kill 每個壞法那筆治理帳多 `judged`:任一列是 fallback → fallback;否則任一列是 merged → merged;否則 single(檔不在平台 repo 的列由 choice-kill 自己產生,記 single)。另多 `merge_ver`(整數,工具常數 `_CHOICE_MERGE_VER`,第一版是 1;每筆都帶)。
- **run 事件**:多 `merged`、`fallback`、`single` 三個整數(這次各判法的壞法數;三者相加等於這次判定的壞法數)。`ran`(既有)、`merged`、`fallback`、`single` 進 `_gov_row` 的 choice-kill 白名單;choice-kill 事件的 `judged`、`merge_ver` 也進。新欄位照既有慣例登記進 `_GOV_FIELD_TYPES`(整數用 `type(x) is int` 排除 bool)。
- **作廢舊的合併判定**:`_choice_disposition` 判有效處置時,同鍵最新一筆 `judged` 是 merged、而 `merge_ver` 小於目前的 `_CHOICE_MERGE_VER` → 算過期(推送閘照既有「過期」擋、`_choice_kill_pick` 照「過期」排進先跑)。沒有 `judged` 欄的舊帳當 single,不受影響。判法改了(對名規則、乾淨條件、結果檔讀法)就把常數加 1,舊的合併判定一次全部要重跑。
- **`--recheck`**:跟 `--only <檔>:<行>` 一起用時重跑那一行;單獨用時重跑範圍裡所有有紀錄的行——連已有有效處置的 killed 與「守的測試沒變」帶過去的 survived 都重跑,新紀錄追加在後、以最新一筆為準;放行檔裡已放行的行不重跑(放行優先於帳,重跑也改不了處置,見〈實務隱患〉)。`--max-mutants`、`--max-seconds` 照樣截。
- **全域關閉**:環境變數 `LUMOS_CHOICE_NO_MERGE=1` 等同 `--no-merge`,出事時一次關掉所有呼叫(推送閘與代碼審預判提示的都是不帶旗標的 `lumos choice-kill`)。`--no-merge` 時,除新增的 `judged`(一律 single)、`merge_ver` 與 run 的三個計數欄外,choice-kill 的輸出與帳跟現在相同(S14 守)。
- **印字**:這份新增的提示(整次不合併、逐支道有幾支)一律印到標準錯誤:choice-kill 呼叫 `cmd_guard_kill` 時把標準輸出整段收起來,印到標準輸出的會被吞掉。
- **接線**:`cmd_guard_kill` 多一個選用參數 `merge`(真:同一個 `group` 連續、而且 file、old、new、also 都相同的配方視為同一個壞法,照 3、4 跑)。不傳時行為與輸出不變(S17 守)。choice-kill 預設傳真;`--no-merge` 或 `LUMOS_CHOICE_NO_MERGE=1` 傳假。

### 7. 不改工具的基線(現在就能用)

一次呼叫跑完、不分段:`lumos choice-kill --max-mutants 200 --max-seconds 86400`,用 `nohup` 或背景執行。基準只量一次(現在每段重量);中斷時判定完整的照記,重跑會跳過已有紀錄的行。這是本案上線前的做法,也是〈預期效益〉的對照組。限制:開跑後別再改那幾支檔(T44:帳以行指紋為鍵,改過的行會變缺紀錄重跑)。

## 預期效益(估算,待 S18 實測)

以實驗專案 183 個壞法、64 支測試估。掛住的壞法(讓某支測試無窮等待)比例沒量過,假設 5%(約 9 個),待 S18 實測:

| 做法 | 每個壞法 | 183 個合計(牆上時間) | 估算依據 |
|---|---|---|---|
| 現在,一段 30 分鐘 | 平均約 5–6 分鐘(含每段重量基準攤進來) | 15–18 小時(約 37 段) | 實測:一段只判 5 個 |
| 基線:一次呼叫不分段 | 平均約 3.6–4.8 分鐘(基準只量一次) | 約 11–15 小時 | 每段省下重量基準的那幾分鐘 |
| 合併,沒有掛住的壞法 | 約 1–2 分鐘(一次增量編譯加一次測試行程跑 64 支) | 約 3–6 小時,外加兩次合併基準(第一次含冷編譯估 5 分鐘內、熱基準估 0.5–1 分鐘) | 被殺掉的壞法現在不到 1 分鐘(編譯加一兩次呼叫),合併後多的是同一行程裡多跑 60 幾支 |
| 合併,掛住 5% | 其餘 174 個同上;每個掛住的約 6–8.5 分鐘(合併逾時 max(熱基準 0.5–1 分鐘 × 5, 20 秒) = 2.5–5 分鐘,退回後排在掛住那支前面的約 32 支 × 5.6 秒 ≈ 3 分鐘,掛住那支約 30 秒),第一次退回另付約 6 分鐘量 64 支單支基準 | 約 4–7.3 小時(174 × 1–2 分鐘 + 9 × 6–8.5 分鐘 + 6 分鐘 + 兩次基準約 6 分鐘;其中掛住的 9 個合計約 0.9–1.3 小時) | 現在掛住的壞法只付那支的單支逾時(約 30 秒);若用含冷編譯的基準乘 5,每個掛住的約 29 分鐘、合計 7.5–10.5 小時 |

## 不做

- 平行分片(`--jobs`、記憶體保護、基準共用):移到 [[Projects/選擇點變異平行_計劃]]。
- 不新增平台欄位(合併用的指令範本、結果檔位置):Gradle 形狀從現有 run_cmd 認得出;認不出來的專案照逐支跑。
- 不做「先單跑排前面幾支、再合併其餘」的兩段式(見〈做法〉5 取捨)。
- 不分批合併:組出的指令超過 32768 位元組就整次不合併。
- 不跨呼叫快取基準(綁提交、測試雜湊、指令):合併後基準只剩一次呼叫;跨呼叫快取要管環境(JDK、Gradle、SDK)變了怎麼失效,省的不多。
- 不自動停 Gradle 背景程序、不改使用者的 run_cmd(不加 `--no-daemon`、`--no-build-cache`)。
- 不改判定規則本身、回報上限、`--max-mutants` 與 `--max-seconds` 的預設值;推送閘只多認一種過期(舊版合併判定)。
- 不處理 T44「開跑後又改程式」:帳以行指紋為鍵,改過的行自然變缺紀錄;加速只縮短這段窗口。
- 不碰合約殺傷力(`lumos guard kill` 指令本身)與人裁 `situation-rule`:它們不傳 `merge`、行為不變。
- 不做撤銷放行的新機制:`--recheck` 不蓋過放行檔,要撤放行照現有做法改放行檔(第一輪設計審 rb4,使用者放行)。
- 非 Gradle 的 kotlin-junit 平台、含 shell 控制字元的 run_cmd、Windows 一律不合併。

## 驗收條款

- [S1] 當平台 run_cmd 是 `./gradlew :app:testDebugUnitTest --tests '*{method}'`、同一個壞法守三支測試時,choice-kill 應 組出一條帶三組 `--tests`(依測試名排序、`shlex.join` 接回)的指令只呼叫一次 Gradle;run_cmd 不是 Gradle、`{method}` 出現兩次、含 `{python}`、含 `&&`、任務不帶模組路徑、組出的指令超過 32768 位元組、或在 Windows 時 應 照逐支跑 [test:t_choice_kill_merge_cmd]
- [S2] 當假 Gradle 依結果檔寫出「第二支與第三支都殺掉」「全部存活」「編不過」三種壞法時,合併模式 應 跟 `--no-merge` 判出同樣的判定與殺掉它的測試(取排序第一支強殺掉的),而且每個壞法只呼叫一次 Gradle [test:t_choice_kill_merge_matches_single]
- [S3] 當合併基準找得到結果資料夾、而某個壞法合併跑之後結果資料夾不在、某支測試對不到案例、有失敗的案例對不到合併道任何一支、或 rc 跟結果不一致時,choice-kill 應 只對那個壞法退回逐支、判定與 `--no-merge` 相同,之後的壞法 應 照常合併 [test:t_choice_kill_merge_fallback]
- [S4] 當合併基準就找不到結果資料夾或讀不出來時,choice-kill 應 在標準錯誤印一行並讓這次呼叫全部逐支跑,判定與 `--no-merge` 相同 [test:t_choice_kill_merge_no_results_dir]
- [S5] 當合併跑逾時時,choice-kill 應 照排序逐支重跑那個壞法:排在掛住那支之前有強殺掉的記 killed,否則記跑不出結果「測試掛住」;合併跑的逾時上限 應 是 max(熱基準耗時 × 5, 下限),退回後每支的上限 應 是 max(那支單支基準耗時 × 5, 下限) [test:t_choice_kill_merge_timeout]
- [S6] 當合併基準全綠、某個壞法退回逐支時,choice-kill 應 先還原壞法、在沒套壞法的樹上量缺的單支基準、再重套壞法逐支跑,殺掉它的那支 應 不被當成基準不綠拿掉;同一次呼叫第二個退回的壞法 應 不再重量單支基準 [test:t_choice_kill_merge_fallback_baseline]
- [S7] 當合併基準裡 aCase 失敗而單獨綠、bCase 對不到案例而單獨是 No tests found、cCase 對到兩個類別的同名方法而單獨綠時,choice-kill 應 把 aCase 與 cCase 放逐支道、bCase 記基準不綠拿掉,其餘照合併 [test:t_choice_kill_merge_baseline]
- [S8] 當守的測試有一支名稱不合法(`_test_name_ok` 不過)、平台名稱篩選會撞名時,choice-kill 應 照現在記 error 列、不把它組進合併指令,其餘照合併 [test:t_choice_kill_merge_name_checks]
- [S9] 當合併跑 rc 1、結果檔有新檔而且某支測試名含 `Compilation error` 並失敗時,choice-kill 應 判那支殺掉而不是編不過;rc 1、沒有新結果檔、輸出符合編譯錯誤樣式時 應 判編不過、只呼叫一次 Gradle;rc 137 或輸出含 `daemon disappeared unexpectedly` 或測試行程被收掉的字樣時 應 記跑不出結果「測試程序被系統收掉」而且不退回逐支 [test:t_choice_kill_merge_judge_order]
- [S10] 當守的測試排序是 a、b、c、a 在逐支道而 b 在合併道、兩支都殺掉壞法時,choice-kill 應 判殺掉 by a(等這個壞法所有列到齊才判),跟 `--no-merge` 相同 [test:t_choice_kill_merge_wait_all_rows]
- [S11] 當一次呼叫的 7 個壞法裡有合併判定、退回逐支、檔不在平台 repo、old 對不到各至少一個時,治理帳 應 每個壞法一筆 choice-kill 帶對的 `judged` 與 `merge_ver`,run 那筆 應 有 `merged` + `fallback` + `single` = 7;`gov` 讀帳 應 帶出 `ran`、`merged`、`fallback`、`single`、`judged` [test:t_choice_kill_merge_ledger_counts]

## 回退

- 先關不還原:設 `LUMOS_CHOICE_NO_MERGE=1`(或每次帶 `--no-merge`),之後的新紀錄就回到逐支跑。已寫進帳的合併判定若懷疑有錯,把 `_CHOICE_MERGE_VER` 加 1(一行改動):所有合併判定變過期,下次跑一律重跑;要先抽查就用 `--recheck --no-merge --only`。
- 真要還原程式:功能提交與帳本提交是分開的(choice-kill 的紀錄由使用者另外提交,通過代碼審後只准提交帳本),還原功能提交不會碰到帳,不用另存帳行。但要注意:還原後的舊版不認 `judged` 與 `merge_ver`,錯的合併判定會繼續被當成有效處置——所以還原前先照上一點把可疑的合併判定 `--recheck --no-merge` 重跑一遍,或先升版本讓它們過期再還原。還原會改到被審版本,代碼審留痕綁版本,要重跑代碼審(或照手冊 `code-loop skip` 留痕)。
- 帳上新加的 `judged`、`merge_ver`、`merged`、`fallback`、`single`:舊版 lumos 讀到不認得的欄位照略過,推送閘只看 choice-kill 每筆的判定欄。

## 實務隱患

- 建置快取讓熱基準偏短:專案的 gradle.properties 開了 org.gradle.caching 時,熱基準那一次可能從快取取回結果檔,耗時只有幾秒,壞法合併跑一律逾時、退回逐支,合併沒有效益但判定不會錯。實作時在實驗專案確認它的設定;S18 量到退回裡逾時占多數時看這一條。

- 跑太久:掛住的壞法要先等滿合併逾時(5 倍熱基準,估 2.5–5 分鐘)才退回逐支,見〈預期效益〉。熱基準不含增量編譯,壞法那一次多一次增量編譯:編譯特別慢的專案(大量 kapt/KSP),沒掛住的壞法也可能超過 5 倍熱基準而被判逾時、退回逐支——判定不會錯(逐支照現在判),只是那個壞法多付一次合併的時間;S18 看退回裡逾時占多少。熱基準沒跑乾淨時退回含冷編譯的耗時,倍數變寬、掛住的成本回到每個約 29 分鐘。第一次退回時要量合併道每支的單支基準(64 支約 6 分鐘),之後同一次呼叫不再量。合併逾時時 `_kill_run` 只收 gradlew 那一端的程序群組,Gradle 背景程序底下的測試行程會不會繼續空轉沒驗過,S18 順便看。
- Kotlin 編譯背景程序記憶體不足時,Gradle 也印 `Execution failed for task '…compile…Kotlin…'`,符合 `_KILL_COMPILE_RE`,會被判成「壞法編不過」。它落成跑不出結果:推送閘照擋、下一次 choice-kill 一律重跑(跑不出結果不帶過去),不會誤放行;要提醒的是人不要看到「編不過」就直接放行成「不適用」,先重跑一次。
- 測試互相影響:見〈做法〉5 已知限制;S18 抽查是唯一把關。
- 結果檔讀法:照 `test_quality.junit()` 的上限與拒收,讀不了一律退回逐支,不當掉。資料夾刪除限定工作樹裡,先比真實路徑。
- 對名對不到(巢狀類別以外的特殊命名、參數化顯示名):那支進逐支道,安全但省不到時間;標準錯誤的那一行統計讓人看得到。
- 重判與放行:`--recheck` 只追加新紀錄,不改放行檔;放行檔優先於帳,已放行的行重跑也翻不回,要撤放行照現有做法改放行檔(第一輪設計審 rb4,使用者放行)。
- 中斷等待變長:第一個 Ctrl-C 要等正在跑的那個壞法跑完(一般 1–2 分鐘,碰到掛住的壞法最久到合併逾時),提示訊息照舊說「再按一次強制結束」。
- 守衛面:這是推送閘要的紀錄的產生器;誤判的方向——合併只會把「歸不到」升成「殺掉」(結果檔有失敗而且完整名唯一才算),其他不乾淨的情況一律退回逐支;記錯 `killing_test` 的已知限制見〈做法〉5。出事時的收回路徑:`merge_ver` 升版讓合併判定全部過期、`--recheck` 逐行重判、`LUMOS_CHOICE_NO_MERGE=1` 全域關。由 S2、S3、S10、S16 與 S18 抽查守。
- 併發與交易:一次呼叫一棵工作樹、一條執行緒,帳逐筆追加;不支援兩個 choice-kill 程序同時對同一個 repo 跑(兩邊會挑到同一批壞法、各寫一筆,下次挑行以最新一筆為準,不會壞帳但白跑)。
- 已排除:金流:只在本機跑測試,不碰付款
- 已排除:對外送出:不連網、不寄送;Gradle 下載依賴是專案既有行為
- 已排除:不可逆:只在暫時工作樹裡改檔與刪結果資料夾,收尾整棵移除;治理帳只追加
