## Findings

### 1. 誤記的「殺掉」沒有任何途徑被下一次跑蓋掉
severity: major
blocking: 是

- spec 位置:〈實務隱患〉守衛面、〈回退〉、S14。
- 問題:〈實務隱患〉守衛面的最壞情況,是誤記殺掉讓沒守住的選擇點過閘。但全文沒有「發現誤記後怎麼收回」的機制。
- 程式現況:
  - 挑行函式遇到「放行」或「killed」就直接記為已處置並跳過。`--only` 只限定哪一行,不繞過這個判斷。
  - 處置判定只看同鍵最新一筆。killed 且 `killing_test` 仍被條款綁著,就一直是有效處置。
  - `--only` 的說明文字只說「不受守的測試沒變不重跑限制」,那條限制只針對 survived。
- 例子:合併讀法的 bug 讓某個選擇點誤記成 `killed by cCase`。
  - 修好 bug、改用 `--no-merge` 重跑 `lumos choice-kill --only f.kt:12`,會印「已有有效處置」並跳過。
  - 這一行會一直過閘,直到 cCase 不再被條款綁,或該行內容改了、指紋變了。
- 影響:〈回退〉第 2 條只保證新紀錄跟現在一樣,不救既有錯帳。S14 把原本會擋的 no_result 升成 killed,這類紀錄一旦錯了就是永久放行。
- 引句:「最壞是誤記殺掉讓一個沒守住的選擇點通過推送閘」
- file: `scripts/lumos:78348`
- file: `scripts/lumos:78083`
- file: `scripts/lumos:82117`
- 缺的東西(spec 沒有):重判指令,例如 `--recheck`、`--revoke <run_id>`,或讓 `--only` 對 killed 也重跑。

### 2. 帳上每一筆判定都沒標「是合併判的還是逐支判的」,出事後分不出該複查哪些
severity: major
blocking: 是

- spec 位置:〈做法〉2「run 那筆多三欄」、RETIRE-IF ①。
- 問題:新欄位只加在 run 事件上,是整次呼叫的合計(`merged`、`fallback` 是壞法數)。
  - 每個壞法那筆 choice-kill 事件的 `via` 目前固定寫 `run`,沒有「合併判定」或「逐支判定」的標記。
  - 平行也沒標記是哪一份、是否共用基準。
- 例子:RETIRE-IF ① 觸發,查明合併讀法有錯。帳上有 120 筆 killed,run 事件只告訴你「這次 merged=80」,看不出是哪 80 筆。
  - 不是全部 killed 都該重驗,只有「合併判定且 killed」才該重驗。這個範圍沒法從帳反查,只能全部重驗。
- 引句:「出現一次合併判定跟逐支判定不同而查明是讀法的錯,就把合併預設關掉」
- file: `scripts/lumos:78493`(finish 寫的事件欄位是 `via`、`run_id`,沒有判定方式)
- 缺的東西:每筆事件加判定方式欄位(例如 `judged:merged|single|fallback`、`shard`),並在撤帳或重判指令中使用。

### 3. S13 與 RETIRE-IF 的「抽查判定相同」,在 spec 描述的操作下做不出來
severity: major
blocking: 是

- spec 位置:S13、〈做法〉預期效益、RETIRE-IF ①。
- 問題:S13 要求用 `--jobs 3` 跑一批壞法,再抽 10 個用 `--no-merge --jobs 1` 重跑比對。
  - 這 10 個行在同一份帳、同一個 HEAD 下已有 killed 或 survived 紀錄。
  - killed 的行會被挑行函式直接當已處置(見 finding 1),重跑對象根本不會被選到。
  - survived 的行要靠 `--only`,而且只救 survived。
  - 所以對最重要的「合併判成 killed 的」抽查,指令做不到。
- 抽查成本還有兩個問題:抽樣只有 10 個,對 183 個壞法的誤判率 5% 以下大概抓不到;抽查也沒有判準寫明誰比對、差異怎麼處置。
- 引句:「而且抽 10 個壞法另用 `--no-merge --jobs 1` 重跑 應 判定相同」
- ⚠ 交編排者:做法上可以把結果輸出到暫時的、沒有該帳的 repo 副本比對,但 spec 沒寫。
- file: `scripts/lumos:78348`

### 4. 放行檔蓋過帳,錯的 survived 被人放行後無法由重跑翻回
severity: minor
blocking: 否

- spec 位置:〈做法〉2 平行、〈實務隱患〉(測試互相影響、建置快取凍結第一次結果)。
- 問題:平行或合併造成的假 survived(例如測試受建置快取凍結、基準誤拿掉測試後只剩較弱的判定)。
  - 人處置時最省事的是 `lint-waive choice:<檔>:<行> --note 等價`。
  - 放行檔在處置判定裡優先於帳,之後重跑出 killed 也不會翻回。
  - spec 沒有撤放行或「重跑後自動失效放行」的機制,也沒要求放行時註記是不是用了合併或平行結果。
- file: `scripts/lumos:78079`
- 這是既有行為,但本案新增了造成假 survived 的路徑,所以要把撤放行的指令一併規劃。

### 5. 回退開關不夠:預設變了、沒有全域關閉開關、未驗「關掉就等於現在」
severity: minor
blocking: 否

- spec 位置:〈回退〉第 2 條、〈人裁紀錄〉第 2 條。
- 問題:
  1. 合併預設開,而 `--no-merge` 只能每次手打。推送閘與代碼審通過前自動跑選擇點提示的指令都是 `lumos choice-kill` 不帶旗標(`_CHOICE_PUSH_FIX`、`_CHOICE_PASS_TAIL`)。出事時沒有環境變數或設定能一次關掉預設,所有編排者、skill 提示都要改。
  2. 「不傳新參數時行為不變」只由 S12 擋在 `cmd_guard_kill` 層。choice-kill 層(輸出重導移位、執行緒與佇列、訊號處理)的 `--no-merge --jobs 1` 是否跟現在逐字相同,沒有任何條款釘。spec 也沒寫 `--jobs 1` 是否走新的執行緒與佇列路徑。
  3. 逃生口本身若有問題,被迫「單一提交還原」,而 pass 留痕綁版本,還原後要重審(見 finding 8)。
- 引句:「合併預設開,這會改變不帶參數時的跑法,要完全回到現在的跑法用 `--no-merge`」
- file: `scripts/lumos:78845`

### 6. S9 與 `on_row` 當場判定互相矛盾:當掉那份已交出的「決定性列」要不要記
severity: minor
blocking: 否

- spec 位置:〈做法〉2「某份當掉」、S9。
- 問題:規則寫「那一份沒判完的壞法(含已交出部分列的)不記帳」。但判定的現況是:
  - `_ChoiceKillRun.on_row` 遇到強 killed、編不過或逾時就當場 `finish` 記帳。
  - 主程序從佇列取到決定性列的當下已寫帳,之後那份才當掉。
  - 照字面實作會有兩種結果:佇列裡已有的列照判(寫了),但「還沒判完」又被要求不記;實作者得自行決定是否回收已寫的帳,而帳是只能追加的。
- 結論:應明確為「已判定的照記(強證據不因之後當掉而失效)」,只有「缺結果」補判才跳過。
- 引句:「那一份沒判完的壞法(含已交出部分列的) 應 不記帳也不記缺結果」
- file: `scripts/lumos:78520`(`on_row`)

### 7. 平行路徑:第一份在基準立旗前就結束,其餘份的基準與逾時沒定義
severity: minor
blocking: 否

- spec 位置:〈做法〉2「基準只量一次」。
- 問題:「等旗號立起(或第一份結束)才啟動其餘各份」。若第一份在量基準前就當掉(工作樹建不起來、編不過),表仍是空的。
  - 其餘份各自量基準,且同時冷編譯、搶 CPU。
  - 逾時上限寫「由基準耗時(第一份的基準本來就含冷編譯)的 5 倍蓋過」,但此時沒有第一份的基準耗時可用。
  - 方向上偏安全:逾時落成 no_result,下一次跑一律重跑,不會誤放行。所以只列為規格缺口。
- 引句:「表是空的 → 這一份照常量基準」

### 8. 「單一提交還原」與「另存帳行、接回帳尾」的做法跟帳的實際流向對不上
severity: minor
blocking: 否

- spec 位置:〈回退〉第 1 條。
- 問題:
  - 本專案流程是功能提交之後,帳另走帳本提交。還原功能提交不會碰到那段期間追加的帳,所以「先另存、還原後接回」是多此一舉,甚至有誤操作(覆蓋帳)的風險。
  - 若帳行與功能提交同一提交,還原才會連帶丟掉。spec 沒說是哪一種。
  - 還原改了被審版本,代碼審通過的留痕綁版本,要重審或重凍結。〈回退〉沒提。
- 引句:「還原前先把那段期間追加的治理帳行另存、還原後接回帳尾」
