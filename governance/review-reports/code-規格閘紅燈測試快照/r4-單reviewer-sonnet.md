### F1 留痕還在、檔被刪的那條路徑沒有任何測試守住 sha256 核對與依序比
severity: major
blocking: 是 — 守的是驗收條款 S3(照治理帳行序依序比)與 S4(留痕還在而檔被刪時,照留痕的 sha256 核對刪掉前那一版再比),而且能指出一個合理的改壞,141 支 redbase 測試全綠。
引句:「+            metas.append((tok, path, sha, f"{gone[path]}^:{path}"))」
file:line:`scripts/lumos`(`_tg_rb_metas` 的 `elif path in gone and path not in referenced:` 分支)。

程式本身是對的。問題是這個分支沒有測試守住 sha256 這個參數。

失敗場景:有人把那行寫成 `metas.append((tok, path, None, ...))`,例如照抄下面孤兒檔分支。`None` 同時造成兩個後果:
- 刪掉前那一版不再核對留痕的 sha256。
- `_tg_rb_load` 會把它標成 `loose`,脫離治理帳行序的鏈。

我造了這個輸入:兩份都有留痕的紅燈版,第一份是 900 且檔被刪,第二份是 700 且檔還在,推送版是 900。

|---|---|
| 正確版 | 3 條:被刪的 unreadable、`900 → 第 2 份紅燈版` 預期值被改、`700 → 推送版` 預期值被改 |
| 改壞版 | 2 條:`900 → 第 2 份` 那一步消失(S3 的依序比壞了) |

第二個輸入:留痕記的是 r900 的 sha256,但刪掉前那一版的內容已被換成 800 版。

| | 候選 |
|---|---|
| 正確版 | 2 條:被刪的 unreadable、sha256 對不上留痕 |
| 改壞版 | 1 條:sha256 核對消失,被竄改的內容被默默當成留痕那一版拿去比 |

重現:把 `_tg_rb_metas` 那行的 `sha` 改成 `None`,清 `__pycache__`,跑 `python3.14 scripts/test_lumos.py -k redbase`。結果是 `141 passed, 0 failed`。
我還把作者列在 docstring 的另外七種改壞各跑一次,都如宣稱翻紅:
- `("A","R","C")` 改成只認 `A`

- 拿掉「終點還在」過濾

歸因:有證據的修復回歸(測試覆蓋面)。這個分支是修補才新增的,修前版本 `0fcc214af` 沒有這條路徑。修前 rec'd+gone 會走 `head:path`,得到 size None 而列「被刪了」,不比內容。行為上的修復沒有壞,這裡只有覆蓋缺口。
