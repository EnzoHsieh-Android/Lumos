### F1 pre-commit 既有 Gate 3 會讓新掛鉤在最常見情境下變死碼
severity: major
blocking: 是 — 不講清楚插入位置,實作者八成把呼叫加在檔尾,導致這個檢查對「有記得動圖譜」的最常見合規提交永遠不會執行,整個功能名存實亡。

### F2 全新專案第一次提交會被逐檔擋下,spec 未處理這個情境
severity: major
blocking: 是 — 不處理的話,任何從第一天就採用這套家規的新專案,第一次(或前幾次)真正加程式碼的提交會被幾十到幾百支「新增卻沒家」的檔案擋死,逼人要嘛先手動建幾十篇節點、要嘛集體 `--no-verify`。
引句:「這次新增（含改名成新路徑）的需要家的檔，提交後沒有家」
「範圍外」與「實務隱患」兩節只討論了「舊專案升級」(檔案在提交前已存在,只觸發 S5 提醒)與「兩個舊 Android 專案 100% 沒家」的情境,但那是「改到既有檔案」,不觸發 S3。一個全新 repo 的初始提交裡,所有檔案對 git 而言同樣是「新增」,S3 的擋一律適用,spec 沒有給出任何緩解路徑(例如「初始提交批量豁免」或「先建骨架節點的建議指令」)。

### F3 推送沒有上游的新分支時,「這次要推的提交」若沿用既有 empty-tree 回退會回溯整段歷史
severity: major
blocking: 是 — 不釐清的話,實作者最自然的做法是複用同一支 hook 裡已經算好的 `_range`,結果任何新分支首推(含本 repo 或任何既有專案的日常 `git push -u origin feature/x`)都會把 home-check 套用到從專案誕生以來的每一個提交,對照這套規則生效之前的所有舊提交幾乎必定觸發「新增卻沒家」的擋,而且擋的是別人已經合併過的歷史提交。
引句:「推送前掛鉤對這次要推的提交逐個再查一次，接住跳過提交前檢查的」
file: `scripts/hooks/pre-push:163-172` 既有邏輯對 `remote_sha` 全零(新 ref,含未設上游的新分支)明文採用 `_range="$_EMPTY_TREE..$_lsha"`,註解自承是「保守掃全部引入內容」。這是同一支 pre-push hook 裡,pitfalls/code-loop 檢查已經在用的既有先例,spec 完全沒提到 home-check 的 `--diff` 範圍要不要跟這個先例一致、或要另外只取「這條分支相對 main 的新提交」。

### F5 非 UTF-8 檔名下,git 輸出的解碼慣例與磁碟路徑的解碼慣例不一致,可能讓「家」永遠對不上
severity: major
blocking: 是 — 若照 spec 字面(只講「帶 errors=」不分場景)照搬本 repo 現有慣例,非 UTF-8 檔名的必要檔案會被 home-check 系統性判成「沒家」或「別人的檔」,即使它的 about_code 其實有登記。
引句:「git 輸出一律 `-z` 分隔、帶 `errors=`；非 UTF-8 檔名不炸」
file: `scripts/lumos:99,102,105,567,571,942` 等處確立的既有慣例是「內容/顯示用途一律 `errors="replace"`」(有損,不可解碼的位元組變成替代字元);而 `scripts/lumos:11012-11027` `_about_code_key`/`_disk_spelling` 走的是 `os.listdir`/`Path.resolve()`,Python 對 POSIX 檔名預設用 surrogateescape(無損)解碼。git diff 輸出的檔名若用 `replace` 解碼,跟磁碟枚舉得到的同一支非 UTF-8 檔名字串不會相等,比對鍵永遠對不上。
⚠ 是否代表非 UTF-8 檔名的檔案「永遠無法被 about_code 登記為家」(因為 markdown 是 UTF-8 文字,寫不出那個位元組序列)這一步,我沒有把握到能百分之百斷言,交編排者判斷;但「git-diff 端與磁碟端解碼結果不相等」這件事有 file:line 佐證,是確定的。

### F6 「連結檔、子模組不算」沒有給出偵測機制
severity: major
blocking: 是 — S1 其他每一種排除(程式檔清單、測試檔、工具自裝檔)都明確指到一份既有清單或既有函式可重用;唯獨連結檔/子模組沒有,實作者要嘛漏掉這個排除(讓 symlink 或子模組路徑被當成「需要家的檔」而誤擋),要嘛自己發明一套偵測法,兩者都是未經 spec 審過的行為。
