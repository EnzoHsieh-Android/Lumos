## ① 未定義的詞

1. 「來源錨點四行」——計劃〈做法〉3:「報告開頭照筆記內容審四行來源錨點(`provider:`、`model:`、`prepared:` 等於項目指紋、範本版本)」。計劃自己只點名三個欄位加「範本版本」,沒說第四行是什麼。程式實際的四行是 `seat / provider / model / prepared`(`_note_audit_parse_report` L26272-26279;`prov_ok` L26445-26448),範本版本不在報告裡,是清單檔頭的「派工詞版本」欄(`_note_audit_render_list` L26231-26250)與常數 `_NOTE_AUDIT_PROMPT_VERSION` 比對。→ 建議:寫死四行是 `seat/provider/model/prepared`,版本另說「比對項目檔頭的版本行」。
2. 「同目錄、沒有家的測試檔」(〈做法〉2)——「同目錄」沒說是只看同層還是含子目錄;「沒有家」對測試檔幾乎是空話:測試檔本來就豁免要家(`_nodehome_required` L23833、`_nodehome_is_test` L23636 排除),所以「沒有家」只能解讀成「沒被任何節點的 about_code 列到」,計劃沒這樣寫。→ 建議明寫「同層、`_nodehome_is_test` 判是測試、且沒被任何家的 about_code 列」。
3. 「archived」(〈做法〉1:「status 是 superseded 或 archived」)——system 的合法 status 是 doing/done/planned/deferred/rejected/superseded/stale(`_STATUS_ENUM` L13985-13993),沒有 archived(程式裡 archived 只是路徑含 /Archive/ 的顯示標記,L13931 等)。→ 拿掉 archived,或說明指路徑在 Archive/ 下。
4. 「同一個逐件檔形狀」(〈做法〉3)——筆記內容審判定檔的形狀是 `{version, kind: 判定|申訴|略過, rows:[{id,class,...}]}`(`_note_audit_parse_verdict` L26022-26034);計劃的紀錄檔內容(來源四行、筆記路徑、指紋、點出行)是另一種內容,只有「一報告一檔、亂數檔名、原子寫」共通。→ 改成「同一種檔名格式與同一支寫入函式」,並自訂 home 紀錄檔名的合格正規式(現有 `_NOTE_AUDIT_VERDICT_NAME_RE` L26031 是判定檔專用;_write_lf 中斷留下的 `.tmp-wlf` 靠它排除,home 需要自己的)。
5. 「home-*」命名與既有指令撞名——已有 `lumos home check --diff`(每支檔有家,L39555 附近 `cmd_home_check`、pre-push L347),計劃新增 `note-audit home-check` 與 `LUMOS_SKIP_HOME_CHECK`。兩個「home check」意思不同(一個擋沒家的檔,一個提醒舊句),`LUMOS_SKIP_HOME_CHECK` 讀起來像前者的逃生旗標。→ 換名(例:`note-audit stale-check`)或在計劃裡明寫區別。

## ② 壞引用

1. 「用筆記內容審找『範圍裡碰過的筆記』那支」(〈做法〉1)——程式裡沒有這樣一支獨立函式。「範圍裡任一提交碰過的筆記(含改名)」只是內嵌在 `_notes_status_flipped` 裡的幾行(L25839-25850:`git log --format= --name-only -z -M`),而且後面緊接著要跑 status 翻轉判斷(`_note_flipped_one`),不能單獨呼叫。另一支相近的 `_notelines_range_added`(L24826-24908)回的是「範圍淨改動 AMR 的 .md」,不是逐提交碰過的,兩者集合不同(收尾→改回→再收尾這類,淨差異看不到,見 Systems/筆記內容審 PITFALL)。→ 建議:計劃明寫要抽出哪一支(建議把 L25839-25850 抽成共用函式,`_notes_status_flipped` 改呼叫它),並補一條回歸(改名、改回不變的案例)。
2. 「照每支檔有家那一段判『程式檔』的同一支函式(跟它的豁免清單一致,判定檔、簿記檔不算)」(〈做法〉1)——實際有兩支:`_nodehome_required`(L23822,吃 tip 快照、含 vendored_skip、不讀磁碟)與 `_is_code_file`(L6538,讀磁碟、認 #! 首行、不含 vendored_skip)。兩者都不查 `_BOOKKEEPING_FILES/_BOOKKEEPING_DIRS`;「判定檔、簿記檔不算」之所以成立,純粹因為 .json/.jsonl 不在 `_NODEHOME_CODE_EXTS`(L23441)。→ 指明用哪支(推送時要看 tip 版本,應該用 `_nodehome_required` 的 tip 快照,不是讀磁碟的 `_is_code_file`),並把「簿記檔不算」改成「靠副檔名」。
3. 「範圍終點版本裡 about_code 列了其中任一支檔的節點」——「家」在程式裡是 `_home_map_from_notes`(L23861):只收 Systems/ 下、type=system、status ∈ doing/done/stale(`_NODEHOME_HOME_STATUSES` L23448)。計劃沒引用這支,見③-1。
4. 依據裡的 `governance/eval/home-check/tune/`、`validate/`:存在於 negguard 工作目錄,但 `git ls-files governance/eval/home-check` 為 0 筆(整個資料夾未追蹤)。計劃當「依據」引它,沒提交就無法被下一個 session 重現。→ 實作提交要連這兩個資料夾一起進版控,或計劃註明位置在哪。
5. 其餘引用逐一驗過都存在:Issues/存量筆記漂移三種機制_rtb根因回饋、Projects/筆記內容審_計劃、Projects/存量漂移防線_計劃、Systems/存量漂移守衛、Systems/筆記內容審(lands_in)、Projects/code側刪除傳播守衛_計劃(含 Swimm 與「攔在合併前」,該計劃 L26、L213)、skills/lumos-project-notes/commands/06-代碼審與推送.md(有「筆記內容審」節)、`_CODEX_SEAT_MODEL`(L18757)、`_write_lf`(L14978)、筆記內容審_計劃的 REVISIT 2026-10-12(該計劃 L210)。計劃明說是新檔的(note-audit-home.md、governance/home-verdicts/)不算。

## ③ 範圍自相矛盾

1. 〈範圍〉「不做:計劃與 Issue(不是任何檔的家)」vs 〈做法〉1 候選定義「about_code 列了其中任一支檔的節點」。實際計數(negguard):列 `scripts/lumos` 的 Systems 節點 40 篇(其中 doing/done/stale 的 39 篇),另有 78 篇非 Systems 筆記也列了它(計劃、Issue 等)。若照字面用「about_code 列了」,會把 78 篇計劃/Issue 也當候選,跟〈範圍〉打架;而實驗二的「約 70 篇」正是這種寬口徑(validate/scripts/vcommon.py `homes_ordered` 對整個知識庫 ls-tree -r,任何 .md、不分 type/status;點出行裡有 1 行落在 Issues/)。也就是說:量過準度的母體(任何有 about_code 的筆記)≠ 產品要跑的母體(`_nodehome_homes`:Systems、system、doing/done/stale)。→ 計劃改成「用 `_nodehome_homes` 算」,並在〈誠實界線〉補「實驗母體含少數非 Systems 筆記」;此外〈做法〉1 的「排除 superseded/archived」被 `_home_map_from_notes` 自動包含,可刪。
2. 〈做法〉4「★恆回 0★」與 S6/S8「恆回 0、失敗不影響推送」vs 沿用的 `_note_audit_resolve`:它在 --diff 格式錯、終點在本機找不到時回 2(L26099-26146:`return None, 2, None`)。若 home-check 照筆記內容審 check 的樣子接 resolve 結果(L26514-26516 `return tip`),就不是恆 0。pre-push 是 `set -u`、沒 `-e`,rc2 不會擋;但 CI 的 run 步驟預設 bash -e,非 0 = CI 紅,直接違反「只提醒不擋」。→ 計劃明寫:home-check 把 resolve 的 2 也吞成 0(印警告),並在 CI 那步加 `|| true` 或 `continue-on-error`;S6 補一條「--diff 壞掉也回 0」。
3. 〈做法〉2「內容是實驗的 V3 問法逐字」vs 〈附錄〉「正式範本在這段之外只加兩樣(版本行與來源錨點說明、提示注入那一句)」。同一份計劃對「逐字」有兩種說法;且〈做法〉2 的 ★改任何一個字要升版並重跑實驗二★ 用在 v1 自己身上就已觸發(v1 相對 V3 已多兩樣)。附錄有寫「實作後重跑確認」,但這一步沒有條款([manual:] 或測試);比照筆記內容審 S14 的 `[manual:…沒補不准接線]`。→ 補一條 [S10] manual 條款。
4. 〈範圍〉「做:推送前掛鉤與工具鏈 CI 各加一行」vs 實際 CI 是一整個 step(見 ci.yml L127 note-shape 步的形狀),含 env、`if: push`、BEFORE 預設值。用詞不影響行為,但 S8 的「各呼叫一次」要連 CI 步驟怎麼寫 rc 一起釘(見③-2)。

## ④ 機械宣稱驗語意

格式:計劃原句 → 程式實際做什麼 → 建議改法。

1. 「推送範圍:照筆記內容審 prepare 同一支推送起點判法」(〈做法〉1)→ 屬實:`cmd_note_audit_prepare` → `_note_audit_resolve`(L26099)→ `_note_audit_start`(L26147)→ `_lens_push_base`(L34609)。但有兩個附帶行為計劃沒提:(a) 該函式 docstring(L34620-34622)自承「在合過主線、沒設 upstream、CI 已 fetch 時會算錯」(多算,Issues/推送前其他閘的範圍在合過主線時會多算),drift 檢查因此改走 `_push_range_start`;home-check 若沿用,會在這些情況多出候選與成本(不是漏)。(b) resolve 之後還會用 `mark`(預設 `"note-audit check"`)把起點截到「推送前掛鉤第一次含該字串的提交」(`_nodehome_clamp_base` L24192、`_nodehome_golive` L24181,用 `git log -S` 掃 scripts/hooks/pre-push)。→ 建議:home-check 傳自己的 mark 或明寫「不截上線點」;並在計劃明說接受多算或改走 `_push_range_start`。
2. 【嚴重】上線點誤觸:pre-push 與 ci.yml 現在都沒有 `note-audit check`(grep 兩檔 0 筆;筆記內容審計劃自己也寫「未接線」,L180、L209),所以 `_nodehome_golive` 找不到、`_note_audit_doctor_lines` 的 `wired` 為假(L30480-30481:對 pre-push 全文做子字串比對,註解也算)。計劃〈做法〉4 要在 pre-push 加一行並寫註解「排在 note-audit check 之前」——若註解或指令裡出現連續字串 `note-audit check`,會 (a) 把上線點設成這個提交,讓筆記內容審範圍被截、(b) 讓 doctor 誤認「已接線」而開始唸 CI 沒呼叫。→ 計劃明寫:hook/CI 的註解與指令不得出現 `note-audit check` 這串(用「筆記內容審檢查」),並加一條測試釘(S8 補「pre-push 不含 `note-audit check` 字串,除非那道真的接線」)。
3. 「候選筆記 = … ∩ 範圍裡有提交改過的筆記(…改名照它的改名偵測)」→ 見②-1:沒有現成函式;`_notes_status_flipped` 的 touched 段用 `-M` 的 git log(改名新路徑),再靠 `reader(p)` 在 tip 讀不到就丟掉舊路徑,行為可接受,但要抽出來才能用。另注意它不套 `exclude_remote`(已在主線的提交也算),而 `_notelines_range_added` 套(`_ns_exclusions` L24840-24842)——兩者對「已推過的提交裡改過的筆記」結論不同,計劃要選一邊。
4. 「範圍裡改到的程式檔:照每支檔有家那一段判…同一支函式」→ 見②-2。另一個語意缺口:給判定者的 diff 是「範圍起點到終點、只放那篇 about_code 列了的程式檔」(〈做法〉2)。若某程式檔在範圍內被改名+改內容,tip 的 about_code 列的是新路徑,`git diff base tip -- <新路徑>` 因為路徑過濾看不到舊路徑,不會偵測改名,整個檔會被當成「新增」灌進 diff(可能吃滿 10 萬字元上限)。`_nodehome_changes`(L23900)有 -M 可以先算出新舊對應。→ 計劃補:改名的檔要把舊路徑一起放進 pathspec(或先用 `_nodehome_changes` 對照)。
5. 「`_BOOKKEEPING_DIRS` 的消費者」——程式裡實際使用 `_BOOKKEEPING_DIRS` 的地方是五處(不是註解 L21545 說的「三個」):`_sc_changed_files._bk`(L6581,小改動閘改動量)、`_stack_changed_ok`(L31250,風險掃描 diff 過濾)、`_pitfall_tier`(L31262,風險分級)、docs-only 子集判斷(L31349,推送前測試範圍)、code-loop 留痕有效性 `_codeloop_record_valid`(L37161,「其後皆簿記」)。另有一處註解性引用(L36203 說沿用,但 L36214-36217 那支刻意只用 `_BOOKKEEPING_FILES`、不含 DIRS)。計劃 S7 只釘三個效果(留痕不失效、不算改動量、不抬分級),沒覆蓋 L31349(純簿記提交是否走 docs 子集:實測邏輯上會走,因為過濾後 non_docs 為空,可接受但未釘)。新資料夾要加進的是 L21544 那一個 tuple,五處自動生效,所以「加進豁免清單」的改法本身正確。→ S7 補一條「只含 home-verdicts 檔的推送走 docs 子集」或註明不釘。
6. 「筆記內容審 check 讀 `governance/note-verdicts/` 的方式;新資料夾會不會被讀到」→ 屬實:`_note_audit_load_verdicts`(L26037)硬寫 `_NOTE_AUDIT_VERDICT_DIR = governance/note-verdicts`(L25765),tip 版本用 `ls-tree` 該資料夾;`governance/home-verdicts/` 不會被讀,S9 成立。計劃的理由「格式不合的檔當壞檔印出」只對檔名合 `\d{8}T\d{6}Z-[0-9a-f]{32}\.json` 但內容不合 schema 的檔成立(檔名不合的靜默忽略,L26051、L26058);理由略誇大但結論對。另 doctor 讀 `_NOTE_AUDIT_VERDICT_DIR` 統計「判定檔被刪幾次」(L30497),home 資料夾不會被算,對。
7. 「`.lumos/note-audit/` 目錄與 .gitignore」→ 屬實:`_note_audit_work_dir`(L26326-26339)第一次建立時在目錄內寫 `.gitignore` 內容 `*`;根目錄 .gitignore 沒有這個路徑(只有 testmap、test-cache、lintbase-*)。該函式還會刪除超過 14 天的 `*.md`,所以 `home-<指紋>.md` 也會被 14 天清掉(對「項目檔」是合理,但計劃沒說,且 REVISIT 兩週抽樣時舊項目檔可能已被清)。→ 計劃補一句「項目檔沿用 14 天自動清」;抽樣需要的資料靠 governance/home-verdicts 不靠項目檔。
8. 「推送前掛鉤與 CI 現在有沒有呼叫 note-audit check」→ 都沒有(見 ④-2)。計劃〈做法〉4「排在 note-audit check(若已接線)與 code-loop check 之前」:pre-push 裡 code-loop check 只在 `refs/heads/*` 分支推送才跑(L415 `if [[ "$_rref" == refs/heads/* ]]`),而 `_hrange` 段(L330-364:home check、note-shape)對所有帶範圍的 ref 都跑,天然在 code-loop 之前;應接在 note-shape 之後、`fi` 之前,沿用 `_hrange`。計劃沒說用 `_hrange` 還是 `_range`(兩者刻意不同,L325-330 註解),要選 `_hrange`。CI 這邊,現有順序是 code-loop gate(L104-125)→ note-shape(L127)→ drift(L149),「排在 code-loop 之前」= 新步驟要插在 L104 前面,但 note-shape 那步才有「fetch 遠端分支、建本地 main」的前置(找主線用),新步驟若排在它前面,`_lens_push_base` 找不到主線會退到空樹(整段歷史當新改動)。→ 建議 CI 放在 note-shape 之後(順序限制只寫「不擋別的步驟」),或自己帶 fetch 前置。
9. 「`_write_lf`(同一支原子寫入)」→ 屬實:暫存名 `<name>.<pid>-<uuid8>.tmp-wlf`、`os.replace`、原檔在則 copymode(L14978-15003)。中斷會留下 `.tmp-wlf`,若人 `git add governance/home-verdicts` 會把它一起加進去;判定檔靠檔名正規式擋(見①-4),計劃沒寫 home 版。
10. 「`_KNOWN_GATES`」→ 閘名 `note-audit` 已在名單(L6961),事件種類 `kind` 無白名單(`_gate_event_build` L1147 直接寫),所以 `home-recorded`、`home-reminded` 不需改 `_KNOWN_GATES`;計劃「閘名沿用 note-audit」正確。不過 doctor/gov 有沒有按 kind 統計 note-audit 的地方沒查到讀 kind 的分支(只有寫端),新事件不會被誤算。
11. 「來源錨點四行是哪四行」→ 見①-1。另外 `prov_ok` 只是自我宣告字串的比對(judge 從清單檔頭抄),不驗真偽;record 的信任方向是「重的照收、輕的驗來源」。計劃〈做法〉3 說「不合的項目逐項丟掉」——錨點是整份報告層級,不是逐項;home 版全是「點出的問題行」(等於都是重的),照筆記內容審的信任方向,來源不合的重項目照收。計劃要嘛明說「來源不合整份不收」,要嘛承認錨點在提醒版只是紀錄用。
