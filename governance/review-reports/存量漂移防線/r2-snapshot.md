# 存量漂移防線_計劃

白話:筆記形狀擋與筆記內容審只管「新寫進來的句子該不該寫」。這一篇管另一半的一部分——**已經寫進去的句子,因為別處的狀態或程式變了而過期,要有東西把它指出來**。rtb 抽查 33 處,20 處是這種漂移,現有健檢一處都沒抓到([[Issues/存量筆記漂移三種機制_rtb根因回饋]],證據全文 `governance/audits/2026-09-28-rtb-drift-rootcause/rootcause.md`)。三種產生方式裡,這一篇做兩道誤報低的:**甲**(改狀態時連帶處理,機制③)與**乙**(回頭條件改成機器能判的條件,機制②);第三種(程式改了、舊句還在講,機制①)誤報與漏抓要實測才知道,拆到 [[Projects/舊句偵測實驗_計劃]] 先做實驗。每道做完先拿考卷考一次。

依據:Enzo 2026-09-28 裁「把沒防護到的修一修,然後用新工具健檢一次筆記,看能修復多少」;設計審 r1 後裁「拆開:甲乙先做、丙先實驗」。

PRIOR-ART: 最小解在工具鏈自己這一層(筆記與程式都在同一個 git 裡)。世界解:[[Projects/先問世界_存量掃描裁定]] 點名過 Doorstop 的邊級 suspect 與 Swimm 的行級錨點——要先埋錨點,rtb 現有筆記沒有,留作候選;回頭條件寫成可判定條件的做法,世界上最接近的是 ADR 工具的 superseded 鏈與 feature flag 的「到期條件」,都是作者明寫、工具判定,本計劃照這個形狀。借用:①推送範圍起點借三道檢查共用的推送起點判法(`_lens_push_base`)並截到自己的上線點(`_nodehome_clamp_base` 的做法);②閘的形狀(block/warn/off 三態、略過開關只認 1、只看這次帶進來的、治理帳事件、doctor 印模式行與 CI 沒呼叫的提醒)照筆記形狀擋與筆記內容審;③讀某個提交的樹借 `_nodehome_reader`;④測試檔判定借 `_nodehome_is_test`(路徑規則,可對任何提交的樹用),不借讀工作目錄的測試索引;⑤狀態欄位與標籤同步借 `edit_fm_sync_status_tag`,寫入借 `atomic_write_verify` 並包在 `_vault_write_lock` 裡(照 `cmd_set`);⑥doctor 既有 REVISIT 日期檢查(E5)照舊,只改「條件式那種不算格式壞損」;⑦新寫的 REVISIT 行擋在筆記形狀擋(第一層)裡,照它「只看新行、截到上線點」的規矩。自建:條件語法(`[when-…:…]`)與它的評估、甲的狀態一致檢查、考試指令——既有工具沒有可借的。跟既有的 `drift-history`(沿歷史重放 Check Y 的離線量測)不重疊:那支量「符號還在不在」,本計劃不碰符號存在性(那是 [[Projects/舊句偵測實驗_計劃]] 的題目)。

## 範圍

- **做**:①甲:`guard settle` 轉正時把工具自己寫的預告句改成歷史說法、`lumos set` 把計劃收尾時列出連帶待辦、四種狀態一致檢查;②乙:條件語法、評估、推送閘在「這次推送讓條件成立」時擋、第一層擋新寫的散文回頭條件;③`lumos drift scan`(甲乙的現況健檢)與 doctor Z 段;④`lumos drift exam` 與考卷(甲乙那 11 題加非漂移對照);⑤兩道做完後掃工具鏈自己與 rtb 的圖譜、產出待修清單、修復。
- **不做**:①程式改了、舊句還在講(機制①,考卷 A1–A3、C1–C3、D1–D3)與「筆記點名的符號或測試已不存在」——移到 [[Projects/舊句偵測實驗_計劃]];②跨篇重複句偵測、總索引自動補列、E3 降噪、`[confirmed:]` 只准指令更新、代碼審加「筆記對程式」席(稽核〈4.2 其他防線〉)——另排;③新寫的否定句(「目前沒有 X」)——筆記內容審的事(判定者派工詞規則第 3 條:證據可寫 `search: … => 0` 證明「there is no X」,這類句子判成推得出),本計劃不重做。

## 做法

### 0. 共用:指令家族 `lumos drift`,一支推送閘

- `lumos drift check --diff <起點>..<終點>`:推送前與 CI 的閘(閘名 `drift-check`)。只看**這次推送帶進來的**觸發;有「要處理」的發現才回 1,只有「只列出」的回 0;參數錯回 2。範圍起點照 `_lens_push_base`,再截到這道檢查自己的上線點(推送前掛鉤裡出現標記 `drift check` 的第一個提交)。讀被推送頂端提交的樹(`_nodehome_reader`),不讀工作目錄。
- `lumos drift scan [--at <提交>] [--json]`:對整份圖譜現況(或某個提交的樹)跑甲的四種一致檢查與乙的條件評估,列出全部發現。不擋、不寫帳。
- `lumos drift ack <節點> <內容編號> --reason "<為什麼照留>"`:表態「這行照留」。寫進 `governance/drift-acks.jsonl`(加進簿記豁免);綁①那一行的內容編號(借 `_notelines_content_id`:路徑、區塊、小標題、行文字)②**發現種類**(`probe` 或 `c1`…`c4`)——同一行換一種原因被列,舊表態不算數;那行改過、或筆記改名(路徑變了),表態失效要重表,工具在失效時印出舊表態的理由方便照抄。理由少於 4 個字拒絕;每筆記一筆治理帳 `acked`。同一小標題下一字不差的兩行共用內容編號,一次表態兩行都算——這是 `_notelines_content_id` 的既有取捨,寫進〈誠實界線〉。
- `lumos drift exam <考卷.json> --repo <被考的 repo>`:在被考 repo 的歷史上重放,算甲乙各自擋到、點到、漏、誤報(〈做法〉第 3 節)。
- 開關:`.lumos/config.json` 的 `drift_check.gate` = block / warn / off,讀被推送頂端提交裡的設定;**設定檔沒寫時的預設值**寫在程式裡,照〈做法〉第 4 節第 4 點的考試門檻定——過門檻是 block,沒過是 warn(兩處講的是同一個值);單次略過 `LUMOS_SKIP_DRIFT_CHECK=1`(只認 1,記 `skipped-env`);淺層 clone 跳過並記帳(同兩層筆記閘)。gate 不是 block 時 doctor 印一行(照筆記形狀擋);接線後,專案 CI 沒呼叫 `drift check` 時 doctor 也印一行並給要貼的步驟(照筆記形狀擋與筆記內容審的 CI 提醒)。
- 閘名 `drift-check` 登記進既有閘名單;事件種類:`blocked`、`warned`、`skipped-env`、`skipped`、`degraded`、`acked`。沒發現的放行不寫帳(同筆記形狀擋)。
- **判不了的時候**:條件評估要跑 git(`git grep`、`git ls-tree`、讀筆記),單次沿用 `_lens_git` 的 20 秒逾時;整次 check 或 scan 總預算 60 秒。某一條判不了(git 失敗或逾時)就把那一行列成「判不了」、不擋,整次記一筆 `degraded`;總預算用完,剩下沒判的行數印出來、記 `degraded`、不擋。理由:判不了時擋,大推送就一定被擋;不擋但看得見、有帳可查。

### 1. 甲:狀態指令連帶處理(對應機制③,考卷 A4–A6、E1–E3)

1. **`guard settle` 轉正時,把守衛紀錄裡 `guard plan` 寫的預告句改成歷史說法**(只動工具自己寫出的固定句型):
   - 摘要 `TEST:還沒有測試在守這條…` → `TEST:[<轉正日期>] 預告已轉正,合約改由 [[<家筆記>]] 的正式合約行守`(講「哪天發生了什麼」,不重複寫測試名——那是程式碼答得了的,筆記內容審會判成推得出);
   - 摘要 `WHY:[日期]預告這條合約但還沒做:…` → 同一行尾端加 `(<轉正日期> 已轉正)`;
   - 正文 `為什麼還不做:` → `預告當時為什麼還不做:`。
   - 找不到固定句型(作者手改過)就跳過並印一行提醒,settle 照樣成功。
2. **settle 的寫入順序與補救**:整個 settle 包在 `_vault_write_lock` 裡;先改家筆記的預告行(既有邏輯),再**一次寫入**守衛紀錄(status pending→pass、標籤同步、上面三種句型,同一次 `atomic_write_verify`)。**補救路徑**:再跑一次 settle 時,若家筆記已經是這條合約的正式行(同一句合約、同一個 `[test:]`)而守衛紀錄還是 pending,就只做第二步——中途失敗、或事後用 git 還原了守衛紀錄,都能用同一個指令補完,不會卡成「轉不了正也棄置不掉」。
3. **`lumos set <計劃> status done|superseded` 列出連帶待辦**(只多印,不擋、不寫):①跟這份計劃有連結(任一方向的 `[[連結]]`,連結方向寫出來)而且 status 是 open/doing 的 Issue;②`plan_refs` 指到它、status 是 pending 的驗證紀錄;③全圖譜裡 `[when-status:<這份計劃>=…]` 因此成立的行(乙)。每項給一行要敲的指令。不是計劃、或不是改成 done/superseded 就不印(計劃的合法狀態只有 todo/doing/done/superseded)。
4. **四種狀態一致檢查**(scan 與 check 共用一支函式;每筆發現回報「哪篇、哪一行」,整篇層級的就回報那個欄位所在行):
   - **c1 轉正了還寫預告**:驗證紀錄 status 是 pass、有 `guards` 欄,而且還有 `guard plan` 寫的固定句 `TEST:還沒有測試在守這條` 或以 `為什麼還不做:` 開頭的行。句型是工具自己寫的,不猜。
   - **c2 計劃收尾了、連著的 Issue 還開著**:Issue status 是 open/doing,跟一份 status 是 done/superseded 的計劃有連結(任一方向)。只列出、不擋——連結有時只是參考,是不是該結案要人看(rtb 的 SIGTERM 那篇就是刻意開著的)。
   - **c3 計劃收尾了、驗證紀錄還待定**:驗證紀錄 status 是 pending,`plan_refs` 列的計劃全都已收尾。只列出、不擋。
   - **c4 前提寫「還沒提交」**:`valid_under` 含「未提交」「還沒提交」「uncommitted」任一詞(不含「工作樹」——「釘在某提交的乾淨工作樹」是合法的可重現寫法)。只列出、不擋——這些字也可能描述別的 repo 當時的狀態。
5. **推送閘只擋 c1、而且只擋這次帶進來的**:範圍裡有提交把某篇守衛紀錄從 pending 改成 pass,那一篇的 c1 發現擋;c2、c3、c4 在範圍裡有對應事件(計劃收尾、驗證紀錄新增或改動)時列進「只列出」。範圍外早就不一致的只在 scan 與 doctor 列。

### 2. 乙:回頭條件改成機器能判的條件(對應機制②,考卷 A7、B1–B4)

1. **條件語法**:照既有標記的 `[鍵:值]` 單值形狀,四種鍵,可放在任何筆記行上(建議只放 REVISIT 行,見第 5 點),一行多個時全部成立才算成立;要「任一成立」就寫成兩行:
   - `[when-file:<repo 內相對路徑>]`:那支檔在被檢查的樹裡存在。
   - `[when-symbol:<名稱>]` 或 `[when-symbol:<路徑>::<名稱>]`:在被檢查的樹裡,程式檔有這個名稱的定義行。判法用 `git grep` 對那個提交的樹找定義樣式(Python `def`/`class`/模組層賦值;其他語言找整字——較粗,見〈誠實界線〉)。不解析語法,所以不受「某一版解不開」影響。
   - `[when-test:<測試名>]`:在被檢查的樹裡,`_nodehome_is_test` 認得的測試檔中有這個名稱(Python 找 `def <名>`,其他語言找整字)。
   - `[when-status:<節點>=<值>]`:那篇筆記在被檢查的樹裡 status 等於那個值;值可寫 `done|superseded`(任一)。
2. **回頭條件的新寫法**:`REVISIT:[when-file:src/x/runner.py] 補啟動環境不含金鑰的測試`——日期或條件二擇一放在 `REVISIT:` 後第一格。doctor 既有的 E5 日期檢查改一處:第一格以 `[when-` 開頭的行不算「日期格式壞損」,另印「條件式回頭條件 N 條(由 lumos drift scan 評估)」——這樣就算推送閘拔掉,這些行在 doctor 還看得到。
3. **評估**:scan 列出條件已成立的行(「該處理了」)與寫錯的條件;check 只擋「起點時不成立、終點時成立」的行——就是這次推送讓它成立的。起點時就成立的是舊帳,只在 scan 與 doctor 列。一行在起點不存在(這次新寫的)就只看終點:新寫的回頭條件在終點就成立,等於寫的時候條件已經發生,列進「只列出」提醒作者。
4. **擋新寫的散文回頭條件**:筆記形狀擋(第一層)加一條——新寫的 `REVISIT:` 行(可見行、不在圍欄與表格裡,跟 E5 同一套判定),第一格不是 `YYYY-MM-DD` 也不是 `[when-…:…]` 就擋;條件鍵不認得或值是空的也擋。舊行不管。
5. **跟筆記內容審(第二層)的分工**:`REVISIT:` 行是待辦(程式碼答不了「之後要做什麼」),由 E5 與本計劃管;第二層的待審行排除以 `REVISIT:` 開頭的行,避免條件式被判成「描述程式現況」而要求刪掉。這是第二層 `_note_audit_items` 的一處改動,寫進 [[Systems/筆記內容審]]。非 REVISIT 行帶條件的照舊由第二層判(例:「目前沒有 X」本身就是推得出的現況句,該改寫成 REVISIT)。
6. **舊的回頭條件要人補條件**:rtb 約 45 條、工具鏈自己也有;補寫放進〈做法〉第 4 節的修復階段。

### 3. 考卷與考法

- **考卷**:`governance/eval/drift-exam/rtb-2026-09-28.json`(33 題,本計劃用其中甲乙那 11 題加非漂移對照;機制①那 9 題給實驗計劃)。每題:編號、分類、判定、機制、筆記路徑、行號、原文、小標題、失效提交、失效那時的筆記路徑(`note_at_event`,有改名時)、考法。設計審 r1 查出 4 題失效提交寫錯,已更正並留紀錄(考卷旁 `README.md`)。
- **乙的條件式改寫**:rtb 的回頭條件當時是散文。考卷旁另放 `rtb-2026-09-28-probes.json`:對 A7、B1、B2(拆兩行)、B3、B4 與非漂移的 B5,各給「原文→改寫成條件式的一行」。考試時在記憶體裡把那篇筆記的那一行換掉再評估(起點與終點兩版都換),不改被考 repo。這只證明「寫了條件,評估判得對」;作者會不會寫,靠第 2 節第 4 點擋新寫法。
- **考法**(`lumos drift exam`):
  - 甲的題(A4–A6:守衛紀錄轉正的提交;E3:把驗證紀錄提交進來的提交):對失效提交跑 `drift check --diff <上一版>..<那個提交>`,那一題的筆記(用 `note_at_event`)與行出現在「要處理」算**擋到**、在「只列出」算**點到**。
  - 甲的 E1、E2(計劃改成 done 的提交):在那個提交的樹上重算 `lumos set <那份計劃> status done` 會列的連帶待辦,Issue 出現算**點到**;另跑 check,出現在「只列出」也算點到。
  - 乙的題:套上改寫,對失效提交跑 check,那一行在「要處理」算擋到。
  - **誤報**:非漂移題(A8、A9、B5、D4–D6、E4、I1–I3、R1–R3)在任一考法被列的題數;B5 另記——它的條件確實在 8ff8c95 發生了(被列是對的,只是稽核判它不算漂移,因為日期還沒到、別處已註明),分開報。
  - **噪音**:每個考題提交的「要處理」總筆數。
- 甲、乙各做完考一次,結果寫進〈考試結果〉;兩道都做完再考一次總分。

## 回退

- **推送閘**:掛鉤與 CI 各拿掉一行即不擋;`drift scan`、doctor Z 段與 E5 對條件式的處理**留著**——已經照新寫法寫的條件式回頭條件才有地方被看見。要連評估一起拿掉,得先把條件式改寫成日期(`lumos search "[when-"` 列出全部),否則 E5 退回舊版後會把它們算成格式壞損。
- **第一層的 REVISIT 規則**:專案可設 `note_shape.gate=warn`,或單次 `LUMOS_SKIP_NOTE_SHAPE=1`。
- **guard settle 的改寫**:只動工具自己寫的固定句型;要退回,git 還原守衛紀錄後再跑一次 settle,補救路徑(S5)會把 status 補回 pass、句子不會卡在半套。不打算給開關:改寫是冪等、可補救的,開關只會讓同一個指令有兩種結果。
- **lumos set 的連帶待辦**:只多印,不寫。
- **第二層排除 REVISIT 行**:還原那一處即恢復原判法。
- **消費專案**:更新 lumos 後推送開始被擋,設 `drift_check.gate=warn|off` 即可;doctor 會照慣例印一行模式提醒。
- 表態檔與考卷都是新增檔,刪掉不影響其他功能。

## 實務隱患

- **誤報與表態疲勞**(RETIRE-IF ①):推送時只擋 c1 與「這次推送讓條件成立」兩種,都是作者或工具明寫的東西,不猜語意;c2–c4 只列出。
- **效能**:check 只對帶條件的行跑 git(條件數量小),加上 c1 的判定只看範圍裡改到的守衛紀錄;scan 對全圖譜的條件各跑一次 `git grep`/`ls-tree`,不跑 `git log -G` 這種全歷史搜尋;總預算 60 秒,超過照〈做法〉第 0 節記 `degraded`。doctor 的 Z 段就是 scan,同一個預算。
- **多分支一次推**:check 在推送前掛鉤的逐分支迴圈裡跑,每個分支各自一個 60 秒預算;三個分支一起推最多約 3 分鐘,實際條件少時遠低於此。
- **併發**:settle 整段包在 `_vault_write_lock` 裡(照 `cmd_set`);表態檔是只追加的 jsonl,兩條分支各自追加合併會有衝突行(治理帳同一種問題,見 [[Issues/治理帳多個寫入者都沒上鎖]],那篇 REVISIT 時把本計劃的表態檔與 drift-check 事件也算進去),內容是獨立行,手動合併保留兩邊即可。
- 已排除:金流:不碰任何付款、帳務或金額計算的程式
- 已排除:對外送出:只讀筆記與程式、寫本機檔,沒有寄送或外部寫入
- 已排除:不可逆:新增的檔與改寫都在 git 裡,還原提交即回復
- **守衛面**:碰——新增一道推送閘、改 `guard settle` 的寫入、改第一層與第二層各一處。處置:三態開關、略過留帳、判不了的看得見、settle 可補救;設計審與代碼審照 high 看待。

## 誠實界線

- **乙靠作者寫條件**:條件式只判得了寫了的;舊的散文回頭條件要人補寫;新的散文回頭條件由第一層擋,但作者可以改寫成日期(日期到了照舊由 doctor 唸)。
- **`when-symbol` 對非 Python 是整字比對**:名字出現在註解或字串裡也算「有定義」,條件可能提早成立(多列一次,不會漏)。消費專案(Swift、Kotlin、Dart…)用這種條件時,推送閘可能在條件其實還沒發生時擋一次——條件是作者自己寫的,改寫成帶路徑的 `<路徑>::<名稱>` 能收窄;REVISIT 那天看這些專案的 `blocked` 事件裡 `when-symbol` 佔幾成。
- **「任一成立」要寫兩行**:原本一句話講兩個觸發(考卷 B2:「有啟動程式、或改接外部模型時」),後半沒有明確的檔或名稱可寫就寫不成條件,只能留散文或靠日期。考試也只考得到前半。
- **筆記改名會讓表態失效**:內容編號含路徑,改名後要重表(工具印出舊理由可照抄);不做「跟著改名走」是因為改名同時常伴隨內容改寫,自動沿用可能蓋掉該重看的句子。
- **同一小標題下一字不差的兩行**共用一個內容編號,一次表態兩行都算。
- **c2–c4 只列出**:這三種要靠人看列出來的清單處理;沒人看就還是會留著。
- **程式改了、舊句還在講(機制①)這一篇不管**,在 [[Projects/舊句偵測實驗_計劃]]。
- **只看這次推送帶進來的**:上線前已經過期的句子推送閘不擋,只在 scan 與 doctor 列;靠〈做法〉第 4 節的一次性修復清掉。
