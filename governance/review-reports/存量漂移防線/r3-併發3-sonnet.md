鏡頭:資源與併發(鎖的取得/等待/恢復、多寫入者互相覆蓋、pre-push 耗時與 git 呼叫量、doctor Z 段「不跑 git」的宣稱是否成立),並驗收〈審計修正紀錄〉r2 標記「併發」相關的折入是否真的落進正文。

## F1 drift check 排在 code-loop check 之前,違反同一支掛鉤自己訂的「便宜的先跑、貴的最後」順序

severity: major
blocking: 是 — 照這份接線,worst-case 60 秒的新閘會排在一支實測只要 0.61 秒的閘之前,直接違反同一支腳本上方明文寫死、且是 2026-09-06 特地重排過一次的排序原則,會讓「該閘早就會擋、卻先燒掉 60 秒」的情境重演。
引句:「接線,推送前掛鉤與工具鏈 CI 應呼叫 drift check 並排在 code-loop check 之前」

1. `governance/review-reports/存量漂移防線/r3-snapshot.md` [S18](本檔第 143 行)與〈做法〉第 4 節第 4 點(第 113 行)都寫「drift check…排在 code-loop check 之前」。
2. 同一份 spec 的〈實務隱患〉自己承認:「check 在推送前掛鉤的逐分支迴圈裡跑,每個分支各自一個 60 秒預算……最壞約『分支數 × 60 秒』」(本檔第 159 行)。
3. 但 `scripts/hooks/pre-push` 現在的順序原則寫得很白:file: `scripts/hooks/pre-push:166-169`——「便宜的先跑、貴的最後。實測:除了全套測試以外,所有閘加起來約 13 秒(anchor 0.22s / 簽名檔 0.04s / doctor 1.1s / pitfalls 0.23s / code-loop 0.61s / test-layers 0.21s / 自主迴圈那支 10.3s)……★原本全套排在第四位★,所以被那 13 秒裡任何一道擋下時,8 分鐘已經白燒完了。」這段註解明講:排序的目的就是讓「會擋的便宜檢查」先跑,避免在真正會擋的判定之前先燒掉時間。
4. drift check 的 worst-case(單一分支 60 秒)本身就比「全部既有閘加起來」(13 秒)高出約 4.6 倍,卻被放在 code-loop check(0.61 秒)*之前*——如果 code-loop check 本來就會擋(例如受波及合約測試沒過、tier=high 缺留痕),照這個順序仍要先付出 drift check 的等待成本(git 逾時、預算用完時單次可到 20 秒 × 多個條件,見〈做法〉第 0 節「git 單次沿用 `_lens_git` 的 20 秒逾時;check 總預算 60 秒」,本檔第 61 行),才會走到那支便宜又同樣會擋的閘。這正是 2026-09-06 那次重排要解決的問題的鏡像。
5. spec 沒有交代為什麼要放在 code-loop check 之前而不是之後(或全套測試決定之後);〈做法〉〈落點〉〈回退〉三節都沒有討論這個順位的取捨依據。

## F2 「每個條件最多一次 git grep 或 ls-tree」暗示逐條件各自呼叫 git,沒有沿用同一支掛鉤既有的「整段範圍算一次、大家共用」設計

severity: major
blocking: 是 — 若照字面實作(每條 `when-symbol`/`when-test`/`when-file` 各自起一次 git 子行程),隨著條件數量增長(spec 自己說 rtb 舊帳約 45 條待補、之後還會持續增加),pre-push 的 git 呼叫次數會線性成長,且不會被 [S16]/[S18] 的考卷或門檻量到(考卷量的是判對判錯,不是子行程數與耗時);這跟同一支腳本已經為了同樣理由做過一次架構修正的先例相反。⚠ 這條是對「每個條件最多一次」這句話按字面推論而來,spec 沒有明講實作是否會先把整段 diff 讀成一份、條件在記憶體裡比對——若後者才是真正打算的做法,這條 finding 不成立,但 spec 目前的文字沒有排除前者。
引句:「條件數量小,每個條件最多一次 `git grep` 或 `ls-tree`」

1. 引句出自〈實務隱患〉「效能」段(本檔第 158 行)。
2. 〈做法〉第 0 節「這次推送可能改變結果的條件」定義:file 類要查路徑是否在範圍裡被新增/刪除/改名;symbol/test 類要查名稱「出現在範圍裡程式檔或測試檔的改動行」;status 類要查該筆記「在範圍裡被改了 status、被新增或刪除」(第 54 行)。這三種判準理論上都可以由**同一次** `git diff`(取得範圍內變動的檔名與內容)在記憶體裡對所有條件做字串比對,不需要每條件各自呼叫 git——但 spec 自己給的成本模型卻是「每個條件最多一次 `git grep` 或 `ls-tree`」,讀起來就是逐條件各自起一次子行程。
3. 對照:同一支 `scripts/hooks/pre-push` 已經為了「同一件事不要算兩次」重構過一次,file: `scripts/hooks/pre-push:73`——「★一次推送只算一次波及★(2026-09-07 全 repo 審視 #17,設計 [S1] 第 3 步):以前同步點名與合約測試閘各自呼叫,等於一次推送算兩次——這不是便宜的計算。算一次寫進暫存檔給消費者讀。」`impact_once()`(`scripts/hooks/pre-push:78`)把結果存進 `$_IMPACT_JSON` 給後面好幾道閘共用。drift check 的條件評估落在同一支掛鉤裡,卻沒有比照這個「先把範圍內容算一次、其餘消費者共用」的既有模式,而是用「每個條件一次 git 呼叫」描述成本。
4. 影響範圍:F1 已指出 drift check 排在較貴的位置;F2 進一步指出,即使排序不變,條件數一旦隨著這個計劃自己鼓勵的「補寫舊回頭條件」政策(〈做法〉第 2 節第 6 點:「舊的回頭條件要人補條件:rtb 約 45 條、工具鏈自己也有」,本檔第 92 行)成長,60 秒總預算被逼近的機率會跟著「這個機制推廣得越成功」同向上升——採用率越高、越容易撞預算、越容易觸發「判不了的算要處理」而擋人(本檔第 61 行),形成一個 RETIRE-IF 條款(誤報比例、機制②③抓不住、條件式採用率)都沒有量到的第四種失敗模式:純粹因為 git 呼叫量而變慢、逼人 `--no-verify`,跟「判得準不準」無關。

## F3 guard settle 的補救路徑只認「自己中途斷掉」,沒認「被另一個併發的 settle 完整做完」

severity: minor
blocking: 否 — 不會造成資料損毀或狀態誤判(還是會擋、不會誤放),只是把一個本質上「已經成功」的並發結果,回報成一個要人排查的錯誤,影響的是訊息品質與自動化腳本對 rc 的解讀,不是正確性。
引句:「而守衛紀錄仍是 pending,工具應只補完守衛紀錄那一步並成功」

1. 引句是 [S5](本檔第 130 行);同一段散文版在第 71 行:「再跑一次 settle 時,若家筆記已經有這條合約的正式行……而守衛紀錄還是 pending,就只做第二步——中途失敗也能用同一個指令補完。」這段補救路徑只涵蓋「家筆記已換成正式行、但守衛紀錄還沒來得及轉正(status 仍 pending)」這一種中途狀態。
2. 具體重現:兩個 session A、B 幾乎同時對同一個 pending 的守衛節點跑 `lumos guard settle`。A 先搶到 `_vault_write_lock`,依序把家筆記的預告行換成正式行、再把守衛紀錄 status 改成 pass,兩步都在鎖裡完成(第 65-71 行描述的順序)。B 原本卡在等鎖,等到鎖釋出後才真正讀家筆記與守衛紀錄——這時家筆記已經是正式行,**而且守衛紀錄也已經是 pass、不是 pending**,不符合 [S5] 的補救條件。
3. B 接下來會走到既有(未被本計劃改動)的 `_guard_planned_line` 查找邏輯:對照現有程式碼 file: `scripts/lumos:11670-11697`,找不到預告行時回傳的錯誤是「`{home_rel} 裡找不到預告行『{want[:30]}』(被手改過或已經轉正?)」,`cmd_guard_settle`(file: `scripts/lumos:11792-11830`)原樣印出這句話並回傳 rc=2。這句錯誤訊息雖然已經提示「已經轉正?」這個可能性,但函式仍以**失敗(擋下 + 非零 rc)**收尾,而不是「偵測到已由別的程序完成、視為成功」。
4. spec 沒有把這第三種狀態(家筆記是正式行、且守衛紀錄也已經是 pass)明確納入補救分支——[S5] 與第 71 行的補救路徑只寫了「守衛紀錄仍是 pending」這一種,對「已經被別的 session 完整做完」這個真正的併發情境沒有對應的「視為成功」出口。若 settle 被自動化腳本呼叫(例如批次補轉正、或 CI 重試),這種良性競態會被誤判成失敗而中斷流程。
