## F1 guard settle 的手改撤銷法,會讓那條紀錄被自己的 c1 檢查永久盯上

severity: major
blocking: 是 — 照〈回退〉的指示做,會產生一個本功能自己的一致性檢查(c1)判定為「有問題」的狀態,而〈回退〉沒提也沒給出清靜的收尾動作,使用者會以為撤銷乾淨了、其實留下一條會被 scan/doctor 永遠列出的假發現。
引句:「手改那幾行即可(不動 status)」

1. 〈回退〉「guard settle 的改寫」一節教的撤銷法是:「要撤掉某一篇的改寫,手改那幾行即可(不動 status)」——把守衛紀錄裡被 settle 改寫成「歷史說法」的那幾句,手動改回轉正前的固定句型(TEST:還沒有測試在守…、WHY:…預告這條合約但還沒做…等),同時 status 維持 pass 不動。
2. 但〈做法〉第 1 節第 4 點定義的 c1(見引句「驗證紀錄 status 是 pass、有 guards 欄」)正是:status 是 pass、有 guards 欄、而且還有第 1 點那四種固定句的任一種。手改撤銷後的紀錄——status=pass、guards 欄還在(撤銷步驟沒動它)、固定句型又被手動寫回去——精準命中 c1 的判定條件。
3. 結果:這篇紀錄從此會被 `lumos drift scan`、doctor Z 段持續列成「c1 轉正了還寫預告」,而且是真的漂移(而非誤報)在工具眼裡——工具無法分辨「這是作者故意撤銷 settle 改寫」跟「settle 沒做完就被中斷」。
4. 〈回退〉沒有提到這個副作用,也沒有指向 `lumos drift ack <節點> <行號> --kind c1 --reason "..."`(〈做法〉第 0 節)這個本來就存在的表態機制去清掉這條噪音。對照〈回退〉另一節「第二層排除條件式回頭條件」明確警告了還原順序會有的副作用(「已寫的條件式回頭條件…可能被判成推得出——要還原就先把條件式行改寫成日期式,再還原」),同一篇文件對「guard settle 撤銷」這個結構相同的問題(撤銷動作會撞上自己另一道機制)反而沒有對稱地處理,是本節內部的遺漏,不是判不出對錯的模糊地帶。

## F2 「設 note_shape.gate=warn 撤第一層 REVISIT 規則」的建議,實際上會連帶關掉整道第一層閘的其他既有規則

severity: major
blocking: 是 — 照著這條建議做,使用者以為只是關掉新加的 REVISIT 規則,實際上會靜默放行既有的「程式行號引用」「現況描述沒寫來源」「釘版本不合法」三類舊規則的違規,而〈回退〉沒有揭露這個更大的波及範圍。
引句:「專案可設 `note_shape.gate=warn`,或單次」

1. 〈回退〉「第一層的 REVISIT 規則」一節把「設 `note_shape.gate=warn`」當成這條新規則專屬的撤銷開關來寫,語氣上像是精準關掉這一條。
2. 但 `note_shape.gate` 是整個第一層(筆記形狀擋)唯一的一個模式旗標,不分規則種類:`_note_shape_config` 只讀出單一 `mode` 值(file: `scripts/lumos:23501-23518`),`cmd_note_shape` 用同一個 `mode` 決定整次執行是「擋下」還是「提醒(note_shape.gate=warn,不擋)」(file: `scripts/lumos:24159`)。
3. 第一層現有的規則不只 REVISIT 一種,還包含「釘版本不合法」「程式行號引用」「現況描述沒寫來源」等既有規則,全部由同一支 `_ns_check_line` 在同一次執行裡判定、回同一個 `viol` 清單(file: `scripts/lumos:23862-23899`),沒有按規則種類分開的旗標。
4. 所以照〈回退〉建議把 `note_shape.gate` 設成 `warn` 之後,不只 REVISIT 規則不再擋,連 CLAUDE.md 明文要求「程式碼查得到的一律不寫」「新寫的程式行號引用…提交時會被擋」這幾條既有防線,在這個專案裡也一併變成只提醒不擋——這是〈回退〉沒有講清楚、但實際發生的波及範圍。要精準撤銷只有新規則,現有機制做不到,〈回退〉卻把它寫得像做得到。

## F3 〈實務隱患〉「已排除:不可逆」的用語跟同一篇的 guard settle 回退警告互相矛盾

severity: minor
blocking: 否 — 不會讓人做錯決定(〈回退〉guard settle 那段已經把正確做法講清楚),但兩處對「還原提交能不能直接復原」的說法字面上互相打架,屬於內部不一致,依規則仍要報。
引句:「新增的檔與改寫都在 git 裡,還原提交即回復」

1. 〈實務隱患〉把「不可逆」整類風險排除掉,理由是「新增的檔與改寫都在 git 裡,還原提交即回復」——字面上讀起來是「這個功能引進的任何寫入,git revert 就能單純復原」。
2. 但同一篇〈回退〉「guard settle 的改寫」一節明講了一個反例:「不要單獨用 git 還原守衛紀錄」,理由是「舊程式沒有補救路徑、轉正與棄置都會擋下」(guard-kill 記過這種卡死)——也就是說,對守衛紀錄這個檔案單獨做 git 還原,並不會「回復」,而是進入一個要靠新程式重跑 settle 或手改 status 才能脫困的卡死狀態。
3 兩處合起來看,「已排除:不可逆」給人的印象(git revert 就是安全網)跟緊接在後面的〈回退〉節自己列出的例外(單獨 revert 守衛紀錄反而卡死)不一致。若這句「已排除」的判斷只想涵蓋「整批一次性反安裝這個功能」而不含「單獨還原某一個由這功能寫入的檔案」,那這個範圍限定沒有寫進〈實務隱患〉那一句裡,讀者不看到〈回退〉那段細節就會誤信單獨 revert 永遠安全。

## 其餘章節依回滾角度讀過,無 finding

- 〈回退〉「推送閘」段(掛鉤/CI 拿掉一行):留著 scan/doctor Z/E5 的處理、要求先用 `drift scan --json` 列出條件式行再改寫成日期式——這段內部自洽,且跟現有 E5 舊版「日期格式壞損」判定(file: `scripts/lumos:1983`)吻合,舊版確實會把條件式標記誤判成格式壞損,警告成立。閘名 `drift-check` 要登記進 `_KNOWN_GATES`(file: `scripts/lumos:893-899`)——這段只是「軟停用」(命令仍在、仍可手動呼叫並記帳),不是本專案既有「只退場不痛的機制」那種閘名變假名額的情形(那個問題出在 hook 整個撤掉又沒清 `_KNOWN_GATES`,見 `docs/lumos-toolchain-knowledge/Issues/只退場不痛的機制.md`);本計劃沒有對應的「整個功能都不要了」的收尾步驟,但也沒有宣稱有,不算落差。

- 只提醒/擋下模式切換的一般行為(block→warn→off 三態、gate 讀法、doctor 的模式提醒行):跟既有兩層筆記閘同構(`scripts/lumos:24000-24020` 附近的既有提醒句式),沒有發現新的切換風險;唯一具體問題已寫成 F2。
