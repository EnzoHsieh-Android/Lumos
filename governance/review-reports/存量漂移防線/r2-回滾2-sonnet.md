severity: major

## F1 guard settle 的「回退」步驟其實是原地繞一圈,回不到改寫前的狀態

severity: major
blocking: 是 — 照著〈回退〉這條做的人會以為自己撤銷了 S4 的句型改寫,實際上只是把同一套新程式碼重新跑一次、產生一模一樣的新式句子,沒有任何「退」的效果;而且 spec 明講「不打算給開關」,一旦改寫邏輯本身寫壞(例如把某類合約行改壞了),沒有任何路徑能真正關掉它。
引句:「git 還原守衛紀錄後再跑一次 settle,補救路徑(S5)會把 status 補回 pass、句子不會卡在半套」

1. 現有 `cmd_guard_settle`(`scripts/lumos:11801-11803`)一開頭就檢查 `status != "pending"` 就直接擋下退出:「擋下:{rel} 現在是 {status},只有待完成的才能轉正」。也就是說,要讓「git 還原守衛紀錄後再跑一次 settle」這條路能跑起來,還原後的守衛紀錄**必須**是 `status: pending`,不能是「status 仍是 pass、只是句子換回舊式預告句」——後者會在第一行就被擋下,settle 根本不會執行到補救路徑。
2. 所以唯一能觸發〈回退〉這句話講的補救路徑的情境,是把守衛紀錄整篇還原回「這次 settle 都還沒發生」的舊版(status: pending、句子是舊式預告句)。
3. 但〈回退〉只講「git 還原**守衛紀錄**」,沒提也要還原家筆記(home note)。而 S5 的補救條件正是「家筆記已經是這條合約的正式行(★INVARIANT★+[test:])、守衛紀錄還是 pending」——也就是說,家筆記維持新狀態不動,只有守衛紀錄被還原成 pending。
4. 在這個組合下重跑 settle:S5 判定條件成立 → 走補救路徑 → 用**現在仍然部署著的新版程式碼**重寫守衛紀錄裡的 TEST/WHY/正文三種句子(S4 的邏輯),再把 status 寫回 pass。
5. 結果是:守衛紀錄又變回「新式歷史說法 + status: pass」——跟還原之前一模一樣。整段操作沒有讓任何一篇筆記回到「S4 部署前」的舊式預告句寫法,只是把同一套新程式碼再套用一次。
6. 如果目的真的是「暫停/撤回 S4 這個改寫行為本身」(例如發現它把某類句子改壞了,想讓 settle 恢復成只動 status、不碰句子的舊行為),spec 裡沒有任何一條路徑能做到:沒有開關(「不打算給開關」)、也沒有描述「revert 實作 S4 的那次提交」這個選項。〈回退〉一節其餘每一條(推送閘拿掉一行、note_shape.gate=warn、只多印不寫、還原一處程式碼)講的都是「怎麼把這個行為關掉」,唯獨這一條講的其實是 S5 的正常復原案例,不是行為關閉案例,兩件事被當成同一件事寫。

## F2 〈範圍〉宣稱「甲先做、乙後做」,但甲的 S6 自己就依賴乙的 S9 才能完成

severity: major
blocking: 是 — 照著「①甲…②乙…」與「甲、乙各做完考一次」的順序做事的人,會在甲收尾、要交卷(考一次)時卡住:`lumos set` 列連帶待辦的第三項功能沒有 when 條件求值器可用,S6 的驗收測試過不了,甲事實上做不完,「只做完甲」這個中繼狀態不存在。
引句:「全圖譜裡 `[when-status:<這份計劃>=…]` 因此成立的行(乙)」

1. 〈範圍〉把工作拆成「①甲:… ;②乙:…」,〈做法〉第 3 節也說「甲、乙各做完考一次,結果寫進〈考試結果〉;兩道都做完再考總分」,文字上暗示可以先把甲整個做完、獨立測完,再開始做乙。
2. 但〈做法〉1.3(`lumos set` 列連帶待辦,對應條款 [S6])明寫要列三種東西,其中第三種是「全圖譜裡 `[when-status:<這份計劃>=…]` 因此成立的行」,而且原文自己標注「(乙)」——承認這項要靠乙的 when 條件求值器(S9)才能算。
3. [S6] 的驗收測試 `t_set_plan_closed_lists_followups` 沒有拆成「甲部分」「乙部分」兩顆測試,是同一顆測試涵蓋三種列表(連結的 Issue、pending 驗證紀錄、when-status 行)。也就是說,要讓 S6 過測試,`[when-status:…]` 的求值邏輯(S9,乙的核心)必須已經存在並能正確運作。
4. 結論:甲(S6)對乙(S9)有硬性資料依賴,跟〈範圍〉標的「①甲②乙」施工序矛盾。如果照 spec 字面順序先做甲、且甲要當作可以獨立收尾並考一次,實作者要嘛得先偷跑做完 S9 的核心(等於乙沒有真的排在後面),要嘛把 S6 拆成「先只做前兩項、when-status 那項留白」——但 spec 沒有描述這個拆法,[S6] 條款文字是三項合寫成一條,不留白也不允許分階段驗收。
5. 對回滾/分階段上線的實際影響:如果團隊真的照著「先甲後乙」的順序做事,唯一能落地的中繼狀態其實是「甲做了 3/4(1.1/1.2/1.4 的 guard settle 改寫、狀態一致檢查),1.3 的 when-status 那一項做不出來」,而不是 spec 暗示的「甲做完、乙還沒開始」那種乾淨切分點。

## F3 第二層排除 REVISIT 行(S12)若單獨退回,舊寫的條件式 REVISIT 行會在計劃收尾時被重新送審——這正是 r1 已經抓過的閘互鎖 blocker

severity: major
blocking: 是 — 〈回退〉把這條寫成一句「還原那一處即恢復原判法」,聽起來像單點、無副作用的回退,但沒有交代:退回這一處會讓已經寫好的條件式 REVISIT 行,在對應計劃收尾(status 改 done/superseded)那次推送被第二層閘重新判定,可能被判成「描述程式現況、可從程式碼推出」而要求刪除——這正是 spec 自己在〈審計修正紀錄〉裡記下、r1 外家席判為 blocker 的那種「兩道閘互鎖」,回退步驟卻沒有把這個風險寫進去或給配套。
引句:「第二層的待審行排除以 `REVISIT:` 開頭的行」

1. `_note_audit_items`(`scripts/lumos:24282-24327`)決定哪些行要送第二層審查時,關鍵在第 24320 行:`if not done and i not in new_lines: continue`——只有「這次推送新寫的行」才會被檢查;但如果 `done` 為真(這篇筆記是本次要收尾/翻案的計劃),這個 `continue` 不會觸發,等於**整篇筆記所有行(不論新舊)都要送審**,不只新寫的行。
2. 這意味著:一篇計劃裡舊的、S12 部署之後才寫的條件式 REVISIT 行(`REVISIT:[when-file:…] …`),平常因為不是「新寫的行」不會被第二層碰到;但只要這篇計劃某天真的被 `lumos set <計劃> status done` 收尾,它就會被 `done=True` 的完成審路徑重新掃一遍——而完成審不看「新不新」,是全篇都審。
3. 如果 S12 這處排除被退回(還原成「不排除 REVISIT 行」的舊判法),完成審會把這些條件式 REVISIT 行當成一般本文送第二層判定。條件式 REVISIT 的內容本質上就是在陳述一個「程式碼可查證」的條件(`[when-file:…]`/`[when-symbol:…]` 這類斷言字面上就是可從程式碼推出的現況句),很容易被判成「推得出」而要求刪掉或改寫。
4. spec 自己在〈審計修正紀錄〉裡承認過一模一樣的機制風險:折入清單裡寫著「REVISIT 行從第二層待審排除,避免條件式被判成推得出而兩道閘互鎖(外家 blocker)」——也就是說,S12 這處排除,本來就是為了防止「第一層(S10)允許/要求寫條件式 REVISIT」跟「第二層把條件式判成推得出而要求刪掉」互相打架而加的。
5. 〈回退〉卻只對這一條寫「還原那一處即恢復原判法」,完全沒有提到:如果只退 S12、卻沒有同時退掉 S9/S10(仍然允許甚至鼓勵作者寫 `[when-…]` 條件式 REVISIT),就會重新製造出 r1 已經判過 blocker 的那個互鎖——差別只在於觸發時機從「新寫的每一行」縮小成「計劃收尾那一刻,對舊有的條件式 REVISIT 行」,範圍變小但沒有消失,而且更難被人注意到(因為是舊行,不是這次推送才寫的)。

## F4 fixed.txt 只講「內容編號」,沒說要不要存路徑/原文,回滾機制沒有可執行的查找步驟,也只有 [manual:],沒有機械驗收

severity: major
blocking: 是 — 如果事後發現工具批次修復判錯(比如誤刪了一句其實還沒過期的規則),「整批找出、還原」是唯一寫出來的救濟手段;但照 spec 現在的寫法,fixed.txt 裡到底存了什麼(是純雜湊,還是連路徑/行號/原文都存)完全沒交代,而 `_notelines_content_id` 這個既有函式(spec 明講借用它)是不可逆的雜湊,光憑內容編號本身找不回對應的檔案與行,這條回滾路徑目前是描述性承諾,沒有機制保證做得到。
引句:「改了哪幾筆(內容編號)寫在清單旁的 `fixed.txt`」

1. 〈做法〉第 4 節第 2 步只說修復提交的說明要寫「改了哪幾筆(內容編號)」放進 `fixed.txt`,沒有規定 `fixed.txt` 裡除了內容編號之外,還要不要存路徑、行號、修改前/後文字。
2. `_notelines_content_id`(`scripts/lumos:23822-23827`)的實作是 `hashlib.sha256(...).hexdigest()[:16]`——對 (路徑, 區塊, 小標題, 去頭尾空白的行文字) 取雜湊,是單向、不可逆的。也就是說,光靠 `fixed.txt` 裡一串 16 碼十六進位字串,事後**看不出**它原本對應哪篇筆記、哪一行、原文寫什麼。
3. 要「整批找出、還原」,唯一可行的辦法是拿 `fixed.txt` 裡的編號回去比對 4.1 步驟產出、且要保留下來的 `scan.json`(裡面按 S16/S13 的設計會帶路徑、行號、內容編號),用交叉比對找出原始行,再去那個單獨提交的 diff 裡人工核對、決定要不要 revert 那一段。這整套「編號 → scan.json → 對應提交 diff → 人工核對還原」的流程,spec 沒有寫出來,也沒有一支指令(像 `drift ack` 或 `guard settle` 那樣)去做這件事,純粹靠人工記得「要去翻 scan.json」。
4. [S16] 只掛 `[manual:本計劃〈修復結果〉有兩個圖譜各自的前後筆數;rtb 那份未回報就寫「未回報」與日期]`,沒有 `[test:]`——也就是說,連「fixed.txt 記錄得夠不夠、能不能真的靠它找回原狀」這件事本身都不在任何自動化驗收範圍內,純靠寫的人自覺。
5. 對照〈回退〉其他條目(推送閘拿掉一行、config 切 warn/off、只多印不寫),都是「動作單一、結果可預期」的回退;修復階段這條是本計劃裡少數會實際改寫既有筆記內容的批次操作,理論上最需要一條清楚、機械可核對的復原路徑,但目前只有一句「照這份整批找出、還原」的口頭承諾。

---

總結:最高等級 major,blocking 共 4 條(F1 guard settle 回退是空轉、F2 甲乙施工順序自相矛盾、F3 第二層排除 REVISIT 退回會重現 r1 判過的閘互鎖、F4 fixed.txt 回滾機制缺可執行細節與驗收)。
