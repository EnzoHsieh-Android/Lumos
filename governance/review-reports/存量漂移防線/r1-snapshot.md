# 存量漂移防線_計劃

白話:筆記形狀擋與筆記內容審只管「新寫進來的句子該不該寫」。這一篇管另一半——**已經寫進去的句子,程式後來改了,要有東西把它指出來**。rtb 抽查 33 處,20 處是這種漂移,現有健檢一處都沒抓到([[Issues/存量筆記漂移三種機制_rtb根因回饋]],證據全文 `governance/audits/2026-09-28-rtb-drift-rootcause/rootcause.md`)。三種產生方式各配一道防線,照「誤報低、成本低」的順序做,每道做完先拿那 33 處考一次,再做下一道。

依據:Enzo 2026-09-28 裁「把沒防護到的修一修,然後用新工具健檢一次筆記,看能修復多少」,順序照「先做會抓的工具、拿已查清的 20 處量,再掃全圖譜、再修」。

PRIOR-ART: 最小解在工具鏈自己這一層(筆記與程式都在同一個 git 裡,不需要外部服務)。世界上的做法:文件與程式的連結追蹤多靠①顯式錨點(Doxygen/Sphinx 的交叉引用、ADR 工具的 superseded 鏈)②失效偵測靠「符號不見了」(IDE 的斷連結檢查、mkdocs 的 strict 模式)——兩者都只抓「引用的東西消失」,不抓「數量或行為變了」;本計劃照這個分界,只做機械可判的部分,語意變動誠實列為抓不到。借用:①符號抽取借 `_lens_py_defs` 的 ast 解析技法(base 與 tip 兩版各解一次),不自刻正則——那支只抽頂層 def/class,要擴寫成也抽類別內方法與模組層大寫常數;②筆記行、區塊、小標題、圍欄、內容編號借 [[Systems/筆記內容閘]] 的 `_notelines_*` 共用函式;③推送範圍起點借三道檢查共用的推送起點判法;④閘的形狀(block/warn/off 三態、略過開關只認 1、只看這次帶進來的、治理帳事件、doctor 唸)照筆記形狀擋與筆記內容審;⑤表態留帳借 `lint-waive` 的「綁指紋、要理由、會被統計」;⑥測試索引借 `_platform_test_index`。自建:回頭條件的條件語法(`[when:…]`)、狀態一致檢查、考試指令——既有工具沒有可借的。**沒採用的世界解**:[[Projects/先問世界_存量掃描裁定]] 點名過 Doorstop 的邊級 suspect(連結帶目標摘要指紋)與 Swimm 的行級錨點(筆記引用的程式片段存雜湊、變了就標過期)——精度高,但要作者先在筆記裡埋錨點;rtb 現有約 200 篇筆記沒有錨點,20 處漂移也沒有一處是錨點型引用,改造成本大於收益,留作之後的候選。**跟既有決策的關係**:[[Projects/code側刪除傳播守衛_計劃]] 的 d0(2026-08-10)裁定 delguard「先軟提醒不硬擋」,理由是識別字字面比對誤報未知;它在 mOrangePos 對整份圖譜實測 1697 候選只有 6 處真漂移(約 3%)。本計劃的丙**不翻那條決策**(delguard 在提交時照舊只提醒),另開一道推送閘,而且比 delguard 窄三處:①只收整支檔都不再定義的名稱(Python 用 ast,不是任何被刪的識別字);②只看這次推送帶進來的,不掃存量;③只有家筆記與摘要行擋。誤報是否真的降下來由考試量(噪音門檻見〈做法〉第 6 節第 4 點),量出來太吵就先 warn。
RETIRE-IF: 上線兩個月後任一成立就撤掉或重想:①推送時被擋的舊句,作者表態「沒過期、照留」的比例超過一半(誤報太多,大家學會一律表態);②rtb 用同方法重抽 33 處,真漂移比例沒有降到上線前(61%)的一半以下(擋不住);③表態留帳的筆數月增超過 100(變成例行公事)。

## 範圍

- **做**:①狀態指令連帶處理與狀態一致檢查(甲);②回頭條件改成機器能判的條件(乙);③推送前列出還在講被改東西的舊句(丙);④同一套判法對整份圖譜現況跑的健檢,外加「筆記點名的測試已經不存在」;⑤考試指令與考卷;⑥用新工具掃工具鏈自己與 rtb 的圖譜、產出待修清單,工具鏈這邊直接修,rtb 的交給 rtb 那個會談修。
- **不做**:①語意變動(程式行為改了但名字沒變、數量改了但句子沒寫名字)——機械判不了,誠實列在〈誠實界線〉;②跨篇重複句偵測、總索引自動補列、E3 降噪、`[confirmed:]` 只准指令更新、代碼審加「筆記對程式」席(稽核〈4.2 其他防線〉那幾條)——另排,本計劃不動;③新寫的否定句(「目前沒有 X」)要不要擋——那是筆記內容審的事(判定者派工詞規則第 3 條:證據可寫 `search: … => 0` 證明「there is no X」,這類句子判成推得出),本計劃不重做。

## 做法

### 0. 共用:一個新指令家族 `lumos drift`,一支推送閘

- `lumos drift check --diff <起點>..<終點>`:推送前與 CI 的閘(閘名 `drift-check`)。只看**這次推送帶進來的**觸發(照其他閘的慣例),回傳碼 0 過、1 擋、2 參數錯。範圍起點照三道檢查共用的推送起點判法,並截到這道檢查自己的上線點(推送前掛鉤裡出現標記 `drift check` 的第一個提交)。讀的是被推送頂端提交的樹,不讀工作目錄。
- `lumos drift scan [--at <提交>] [--json]`:對整份圖譜現況(或某個提交的樹)跑同一套判法,列出全部發現。不擋、不寫帳,是健檢與待修清單用的;doctor 開一段(字母 `Z`)印筆數與前幾筆。
- `lumos drift ack <節點> <句指紋> --reason "<為什麼照留>"`:表態「這句沒過期」。寫進 `governance/drift-acks.jsonl`(加進簿記豁免),綁那一行的內容編號(借 `_notelines_content_id`:路徑、區塊、小標題、去空白的行文字),那一行改過就自動失效;每筆記一筆治理帳 `acked`。
- `lumos drift exam <考卷.json> --repo <被考的 repo>`:在被考 repo 的歷史上重放,算每道防線抓到幾題、誤報幾題(〈做法〉第 5 節)。
- 開關:`.lumos/config.json` 的 `drift_check.gate` = block(預設)/ warn / off,讀被推送頂端提交裡的設定;單次略過 `LUMOS_SKIP_DRIFT_CHECK=1`(只認 1,記 `skipped-env`);淺層 clone 跳過並記帳(同兩層筆記閘)。
- 閘名 `drift-check` 登記進既有閘名單;事件種類:`blocked`、`warned`、`skipped-env`、`skipped`、`acked`。沒發現的放行不寫帳(同筆記形狀擋)。
- **撤除過的節**:小標題底下第一個非空行是引用區塊(`> `),而且含「不是現況」「已撤」「撤除」「快照」「歷史脈絡」任一詞——那一節的行一律不擋、只在 scan 列為「已撤節內」(rtb 現行慣例,例:`> 開檔時的快照,不是現況:…`)。

### 1. 甲:狀態指令連帶處理(對應機制③,考卷 A4–A6、E1–E3)

1. **`guard settle` 轉正時,把工具自己寫的預告句改成歷史說法**:守衛驗證紀錄摘要裡 `guard plan` 寫的 `TEST:還沒有測試在守這條…` 換成 `TEST:[<日期> 轉正] 由 [test:<方法>] 守`;`WHY:[日期]預告這條合約但還沒做:…` 換成 `WHY:[日期]預告這條合約(<轉正日期> 已轉正):…`;正文 `為什麼還不做:` 換成 `預告當時為什麼還不做:`。只動工具自己寫出的固定句型,找不到就跳過並印一行提醒(作者手改過的不猜)。寫後自驗照既有 `atomic_write_verify`。
2. **`lumos set <計劃> status done|superseded|abandoned` 印出連帶待辦**(改狀態本身不擋):①跟這份計劃互相連結、而且還開著(status open/doing)的 Issue;②`plan_refs` 指到它、status 還是 pending 的驗證紀錄;③全圖譜裡 `[when:status <這份計劃>=…]` 條件因此成立的行(乙)。每項給一行要敲的指令。不是計劃或不是收尾狀態就不印。
3. **狀態一致檢查**(scan 與 check 共用一支函式,四種):
   - **c1 轉正了還寫預告**:驗證紀錄 status 是 pass、有 `guards` 欄,摘要或正文還有 `還沒有測試在守` 或以 `為什麼還不做:` 開頭的行。
   - **c2 計劃收尾了、連著的 Issue 還開著**:Issue status 是 open/doing,跟一份 status 是 done/superseded 的計劃互相連結(任一方向的 `[[連結]]` 或 `related`),而且 Issue 沒有 `keep_open_reason` 欄。
   - **c3 計劃收尾了、驗證紀錄還待定**:驗證紀錄 status 是 pending,`plan_refs` 列的計劃全都已收尾。
   - **c4 前提是「還沒提交」卻已經提交了**:`valid_under` 含「未提交」「還沒提交」「工作樹」「uncommitted」任一詞,而這篇筆記本身已在被檢查的提交樹裡。
4. **推送閘只擋這次帶進來的**:範圍裡有提交把某計劃改成收尾、把某守衛紀錄從 pending 改成 pass、或新增帶 c4 字眼的驗證紀錄時,只對那幾篇相關的 c1–c4 發現擋下;範圍外早就不一致的只在 scan 與 doctor 列。

### 2. 乙:回頭條件改成機器能判的條件(對應機制②,考卷 A7、B1–B4)

1. **條件語法** `[when:<種類> <值>]`,可放在任何筆記行上,一行多個時全部成立才算成立:
   - `file <repo 內相對路徑>`:那支檔在被檢查的樹裡存在。
   - `symbol <名稱>`:程式碼裡有這個定義。Python 用 ast 找頂層與類別內的 def/class 與模組層大寫常數;其他語言用整字比對程式檔(有誤報,說明見〈誠實界線〉)。可寫 `<路徑>::<名稱>` 限定檔案。
   - `test <測試名>`:測試索引裡有這支測試(借 `_platform_test_index`)。
   - `status <節點>=<值>`:那篇筆記的 status 等於那個值(可寫 `done|superseded`)。
2. **回頭條件的新寫法**:`REVISIT:[when:file src/x/runner.py] 補啟動環境不含金鑰的測試`——日期或條件二擇一放在 `REVISIT:` 後第一格。doctor 既有的 REVISIT 日期檢查改一處:第一格是 `[when:` 開頭的行跳過、不算「日期格式壞損」(不改的話每條新式回頭條件都會被唸成壞損);帶條件的由本計劃評估。
3. **評估**:scan 列出條件已成立的行(「該處理了」);check 只擋「起點時不成立、終點時成立」的行——就是這次推送讓它成立的。起點時就成立的是舊帳,只在 scan 與 doctor 列。
4. **擋新寫的散文回頭條件**:筆記形狀擋(第一層)加一條——新寫的 `REVISIT:` 行,第一格不是 `YYYY-MM-DD` 也不是 `[when:…]` 就擋;條件語法寫錯(不認得的種類、缺值)也擋。舊行不管。
5. **舊的回頭條件要人補條件**:rtb 約 45 條、工具鏈自己也有;補寫放進〈做法〉第 6 節的修復階段,由各自的會談做。

### 3. 丙:推送前列出還在講被改東西的舊句(對應機制①,考卷 A1–A3、C1–C3、D1–D3)

1. **算出這次改了什麼**(對範圍裡淨改動的程式檔,不含筆記、簿記、工具鏈自裝檔):
   - Python:起點版與終點版各用 ast 解一次,比對頂層與類別內的 def/class 名、模組層大寫常數(值用字面量的正規化字串比、清單與 tuple 另比長度)、測試函式名。產出:**消失的名稱**(起點有、終點沒有;改名當成舊名消失)、**改值的常數**。
   - 命令列旗標:`add_argument("--x"…)` 的字串,起點有、終點沒有的算消失。
   - 其他語言:從 delguard 只讀改動行的抽法延伸——刪除行裡的識別字,再讀終點那支檔全文確認整檔都不再出現(delguard 本身不讀全文,只看同一檔的新增行);另外自己加嚴:只收 4 個字以上、含底線或大小寫混合的,避免一般英文單字。
   - 檔案:被刪或改名的舊路徑算消失;**新增的程式檔**另記(給第 4 點)。
2. **在整份圖譜找還在講它們的句子**(讀終點的樹):整字比對上面的名稱與舊路徑;跳過圍欄內的行、這次範圍裡新寫或改過的行(那句作者已經動過)、撤除過的節;已有表態(第 0 節 `drift ack`)而且那行沒改過的跳過。
3. **分兩層**:
   - **要處理**(擋):落在被改程式檔的家(`about_code` 列了它)的筆記裡,或落在任何筆記的摘要行(summary 區塊)。要嘛這次改掉,要嘛 `drift ack`。
   - **只列出**(不擋):其他命中。
4. **新增程式檔喚醒「還沒有」句**:範圍裡新增的程式檔,它的家筆記裡含「尚未」「還沒」「目前沒有」「沒有正式」的行列入「只列出」(考卷 A3 那種:新增 `domain/attempt.py`,家筆記寫「執行側尚未定義」)。不擋——否定詞誤報高。
5. **改值的常數**只找常數名本身;句子沒寫名字的(考卷 A2「三個模型變數」)抓不到,誠實列入〈誠實界線〉。

### 4. 健檢:scan 額外的兩種現況檢查(不綁推送範圍)

1. **筆記點名的測試已經不存在**:任何筆記(不限計劃條款)行內的 `[test:名稱]`,名稱不在測試索引裡,而且不在撤除過的節內。計劃條款那種 doctor S5 已經在唸的照舊,這裡不重複列。
2. **筆記點名的程式符號已經不存在**(mOrangePos 那次全圖掃的精確率約 3%,雜訊類別是測試單號、外部 API 欄位、DB 欄位、別的語言的符號、gradle task、SDK 概念、lint 規則 ID——本條用「曾經在本 repo 程式裡定義過」過濾,就是為了排掉這幾類):筆記行內反引號裡、形狀像程式符號的名稱(含底線或大小寫混合、4 個字以上),不在現在的程式定義裡(Python 用 ast 定義索引,不是全文子字串——註解裡提到不算存在),**而且在 git 歷史上曾經是某支程式檔裡的定義**(`git log -G` 找過去版本;從沒定義過的外部名稱、環境變數名、欄位名不列)。每次 scan 最多查 500 個候選名,超過就印出截斷並給 `--limit` 旗標。

### 5. 考卷與考法

- **考卷**:`governance/eval/drift-exam/rtb-2026-09-28.json`,33 題,每題:編號、稽核分類、判定(漂移/屬實非漂移/不成立)、機制、筆記路徑、行號、那一行原文、小標題、讓它失效的提交、考法(`commit`/`status_command`/`current_state`)。由稽核全文整理、逐題在 rtb 的 067f005 核對過原文(整理過程與核對紀錄存在考卷旁的 `README.md`)。
- **考法**(`lumos drift exam` 做):
  - `commit` 題:對每個讓它失效的提交跑 `drift check --diff <上一版>..<那個提交>`,那一題的筆記與行文字出現在「要處理」算**擋到**、出現在「只列出」算**點到**。
  - `status_command` 題:同上,用改狀態的那個提交。
  - `current_state` 題:`drift scan --at 067f005`,出現算**點到**。
  - 乙的考法另寫:rtb 的回頭條件當時是散文,條件式不存在。考法是在考場複本的 067f005 上照稽核把 A7、B1、B2、B4 的回頭條件改寫成條件式(改寫內容存考卷旁),跑 scan 看條件判成成立的有幾題——這只證明「寫了條件,評估判得對」,不證明作者會寫;後者靠第 2 節第 4 點擋新寫法。
  - **複合考法的題**(考卷裡機制①那 9 題標了 `commit, current_state`):兩種都跑,任一種擋到算擋到;都沒擋到而任一種點到算點到。
  - **誤報**:13 題非漂移裡被列(任一層)的題數;另記每個考題提交的「要處理」總筆數(量噪音,例 b2fc512 一次列幾句)。
- **每道防線做完各考一次**,結果(擋到/點到/誤報/噪音)寫進本計劃〈考試結果〉;三道都做完後再考一次總分。

### 6. 掃全圖譜與修復

1. 三道都做完、考完,對工具鏈自己的圖譜與 rtb(`/Users/enzo/rtb-mainwt` 的主線頂端)各跑一次 `drift scan`,結果存成待修清單(工具鏈的存 `governance/audits/<日期>-drift-scan/`;rtb 的交給 rtb 會談、由它存在 rtb 那邊)。
2. 工具鏈自己的:本會談逐條處理(改句、刪句、補條件、掛撤除橫幅、或 `drift ack`),修完再 scan 一次,前後筆數記進本計劃。
3. rtb 的:用跨會談訊息傳「待修清單在哪、怎麼修、修完怎麼量」(只傳指標,不傳內容),由 rtb 會談修;修完的前後數字由它回報、記進本計劃。
4. 接線:drift check 接進工具鏈自己的推送前掛鉤與 CI(排在 code-loop check 之前),照考試結果決定預設 block 還是先 warn——「要處理」層在考題提交上的平均筆數超過 20 就先 warn、攤給 Enzo 裁。

## 回退

## 實務隱患

- **誤報太多、大家一律表態**(RETIRE-IF ①):「要處理」層只收家筆記與摘要行;考試量噪音;超過門檻先 warn 攤人裁。
- **效能**:check 每次推送要對改動的 Python 檔解兩次 ast、對整份圖譜做整字搜尋。rtb 圖譜約 200 篇、b2fc512 改了 196 支檔,要實測;設上限(名稱數 300、耗時 60 秒),超過就印截斷並記 `degraded` 帳,不靜默放行也不無限跑——超時的那部分當「沒查」印出來。
- **大擠壓提交**:b2fc512 那種一次改上百檔,會列很多句;考試會量到。稽核建議的「依增量分別跑」(增量=rtb 每個 Phase 底下的子批次,擠壓前各有自己的提交)不在本計劃。
- **其他語言的抽法粗**:只借 delguard 的識別字規則,誤報高於 Python;非 Python 專案的「要處理」層照樣擋,考試只考了 Python(rtb),其他棧的誤報沒量——REVISIT 那天看 pos-ios、taroko_app 等專案的擋下事件。
- **併發**:表態檔是只追加的 jsonl,兩條分支各自追加合併會有衝突行(治理帳同一種問題,見 [[Issues/治理帳多個寫入者都沒上鎖]]);內容是獨立行,手動合併保留兩邊即可。已排除更複雜的鎖——同一個問題的整體解在那篇 Issue。
- 已排除:金流:不碰任何付款、帳務或金額計算的程式
- 已排除:對外送出:只讀筆記與程式、寫本機檔,沒有寄送或外部寫入
- 已排除:不可逆:新增的檔與改寫都在 git 裡,還原提交即回復
- **守衛面**:碰——新增一道推送閘、改 `guard settle` 的寫入。處置:三態開關、略過留帳、淺層與超時都印出來不靜默;設計審與代碼審照 high 看待。
