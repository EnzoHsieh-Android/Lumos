## F1 `[when-...]` 值含空白會讓「第一格」抓錯,S9/S10/S11 三處都靠這個抓法

severity: major
blocking: 是 — `when-file`/`when-symbol` 的值本來就是檔案路徑,含空白的路徑(消費專案常見,例如帶空白的資產目錄)一旦被抓錯,S10 的合法性判斷與 S9 的條件評估會對同一個標記給出不一致的結果,乙這整道機制的正確性就沒有保障。
引句:「日期或條件二擇一放在 `REVISIT:` 後第一格。doctor 既有的 E5 日期檢查改一處」

1. spec 唯一講清楚怎麼抓「第一格」的地方是「照舊」沿用 doctor 既有 E5 檢查,只改「`[when-` 開頭不算壞損」這一處(71 行)、S10 也講「跟 E5 同一套判定」(107 行、73 行)。E5 現有實作是空白切法:`scripts/lumos:1965-1966` `_restv = _l5[len("REVISIT:"):]; _datev, _, _sumv = _restv.partition(" ")` ——只切到第一個半形空白。
2. 用 spec 自己給的例子驗證:`REVISIT:[when-file:src/x/runner.py] 補啟動環境不含金鑰的測試`(71 行)這個值裡沒有空白,切得對;但只要路徑本身含空白,例如 `REVISIT:[when-file:assets/My Data/seed.json] 補種子檔測試`,`partition(" ")` 切出來的「第一格」是 `[when-file:assets/My`,不是完整標記 `[when-file:assets/My Data/seed.json]`。
3. 這個殘缺片段仍然 `startswith("[when-")`,所以 S11 的「不算格式壞損」與 S10 的「第一格是 `[when-…:…]` 就不擋」都會判它合法放行;但 S9 真正拿去 `git ls-tree` 查存在性的,如果是同一份「第一格」字串,查的路徑是 `assets/My`(不存在的檔),條件永遠判不成立——這一行 REVISIT 從此不會到期,而且不會被 E5/S11 標成壞損,也不會被 S10 擋下,是一種新機制自己製造出的、抓不到的「靜默漂移」,恰好是本計劃要防的那種問題。
4. spec 全文(含〈誠實界線〉)沒有任何一處提到值含空白時怎麼處理、也沒有規定 `[when-...]` 的抓取要改用「配對到下一個 `]`」的正則(既有慣例可比照 `SINCE_REF_RE = re.compile(r"\[since:\s*([^\]]*)\]")`,`scripts/lumos:2930`,這支是逐 `]` 配對,不受空白影響)。實作者如果照 71/107 行字面「跟 E5 同一套判定」去做,就會複製這個洞;如果改用逐 `]` 配對的正則又會跟「第一格」的空白切法不一致(S10 用第一種、S9 用第二種,兩處各自實作各自的漏洞更難查)。這是 spec 沒定義清楚、兩種讀法會做出不同(而且都有洞)系統的地方。
5. 附帶:同樣的「沒有跳脫機制」問題也發生在值含字面 `]` 的情況——`[^\]]*` 這種正則配對方式一樣會在第一個 `]` 出現處提前結束。spec 沒有規定路徑裡出現 `]` 字元(POSIX 檔名合法字元)時怎麼辦。這兩個問題同源:標記語法沒有定義任何跳脫規則。

## F2 `when-symbol` 的 `<路徑>::<名稱>` 切法未定義,名稱本身含 `::` 時無法判斷

severity: minor
blocking: 否 — 誤判方向是「多列一次/少列一次某個 when-symbol 判斷」,不影響 c1–c4 或推送擋放的主邏輯,且〈誠實界線〉已承認非 Python 判法本來就粗。
引句:「`[when-symbol:<路徑>::<名稱>]`:在被檢查的樹裡,程式檔有這個名稱的定義行」

1. C++/Rust 這類語言的符號名稱本身常帶 `::`(例如 `Foo::Bar::baz`)。寫 `[when-symbol:src/a.cpp::Foo::Bar::baz]` 時,spec 沒說要切第一個 `::` 還是最後一個 `::`:切第一個會把 `<名稱>` 判成 `Foo::Bar::baz`(去掉路徑那段前綴,結果是對的);切最後一個會把 `<名稱>` 判成 `baz`、`<路徑>` 判成 `src/a.cpp::Foo::Bar`(路徑帶了不存在的字尾,`when-file` 式的路徑存在性檢查——如果符號判法內部借用了那段邏輯——會直接找不到檔案)。這兩種讀法在多語言 repo 會給出不同結果,spec 沒裁決。
2. 68 行只給了單一名稱、無 `::` 的例子,沒有測試涵蓋名稱本身含 `::` 的情況(S9 的 `t_drift_when_probes_evaluate_and_trigger` 從條款文字看不出來有沒有覆蓋這個子案例)。

## F3 `when-test` 沒有 `when-symbol` 那種路徑限定寫法,同名測試撞名時無法收窄

severity: minor
blocking: 否 — 最壞結果是「該處理的 REVISIT 因為別的檔案剛好有同名測試而被判成已存在」,即誤判為不需要處理;不會誤擋推送,但會讓機制在有大量同名測試(`test_basic`、`test_it_works` 這類泛用名稱在多語言/多模組 repo 很常見)的專案裡失去意義。
引句:「`[when-test:<測試名>]`:在被檢查的樹裡,`_nodehome_is_test` 認得的測試檔中有這個名稱」

1. 對照 `when-symbol` 明確提供 `<路徑>::<名稱>` 的窄化寫法(68 行)因應「同名定義在多支檔」,`when-test` 只給裸名稱一種寫法(69 行),沒有對應的路徑限定選項。
2. `_nodehome_is_test`(`scripts/lumos:22453-22471`)認得的測試資料夾涵蓋 `tests?/`、`__tests__/`、`specs?/` 等多種棧,一個大一點的 repo(尤其本計劃自己要推的消費專案,如 iOS/Node/Java/Flutter 都有各自測試慣例)很容易在不同模組各自有一支同名的 `test_it_works`/`ItWorks`。作者寫 `[when-test:test_it_works]` 想確認「那支特定的測試」寫了沒,實際判法卻是「整棵樹裡任何一支測試檔有這個名字就算數」——條件可能因為完全不相干的另一支測試而提前判定成立,而且沒有任何寫法能收窄。〈誠實界線〉只講了 `when-symbol` 的粗略性與收窄建議(140 行),沒提到 `when-test` 少了同等的收窄能力這件事。

## F4 `[when-status:<節點>=<值>]` 沒有定義節點找不到(刪除/改名)時的行為

severity: major
blocking: 是 — 沒定義就意味著實作者會用「條件永遠不成立」這個預設行為交差,而這正好複製了本計劃要修的漂移問題:REVISIT 永遠不到期、永遠不會被列進 scan,作者也看不出這行已經死掉。
引句:「`[when-status:<節點>=<值>]`:那篇筆記在被檢查的樹裡 status 等於那個值」

1. §0 定義的「判不了的時候」(46 行)只涵蓋「git 失敗或逾時」兩種情況,對應 S2「條件評估判不了(git 失敗或逾時)」(99 行)。節點名稱在圖譜裡根本找不到(被刪除、或改名但沒人回頭改這一行的 `<節點>`)不屬於「git 失敗」也不屬於「逾時」,是第三種、spec 沒討論到的情況。
2. 對照本專案既有慣例,「節點找不到」一律是要顯式報錯、不能默默略過的一等公民情況——`cmd_guard_settle` 對「守衛節點指名的功能節點找不到」直接 `擋下`(`scripts/lumos:11805-11808`)。`[when-status:...]` 卻沒有這條路徑:它是 scan/check 背景批次評估,不像 `guard settle` 是互動指令能直接印錯誤擋下,若照最省事的寫法(找不到節點就當 status 拿不到、當條件 False)實作,行為會是「永遠不觸發」而不是「degraded」。
3. 〈誠實界線〉逐條列了乙機制的已知弱點(靠作者寫條件、非 Python 粗略比對、任一成立要寫兩行、改名讓表態失效),唯獨沒有「when-status 指到的節點被刪除/改名」這條,而這條的後果(REVISIT 永久沉默,連 scan 都列不出來,因為 scan 只列出「已成立」的行,不會列出「指到的節點消失了」)比清單裡列出的幾條都更嚴重。

## F5 REVISIT 行前面是數字列表記號(或引言符號)時,新舊兩道檢查都看不見

severity: major
blocking: 是 — S10 的存在理由就是擋掉「新寫的散文回頭條件」,如果作者用編號清單寫 REVISIT(常見寫法),這一行對 S10 完全隱形,散文回頭條件照樣能寫進去,新閘沒有真的擋到它宣稱要擋的東西。
引句:「新寫的 `REVISIT:` 行(可見行、不在圍欄與表格裡,跟 E5 同一套判定),第一格不是 `YYYY-MM-DD` 也不是 `[when-…:…]` 就擋」

1. 現有 E5 的行判準只認兩種清單前綴:`scripts/lumos:1961-1963` — `if _l5.startswith(("- ", "* ")): _l5 = _l5[2:].lstrip()`,然後才檢查 `_l5.startswith("REVISIT:")`。數字清單(`1. REVISIT:...`)、`>` 引言(`> REVISIT:...`)、或 `1) REVISIT:...` 這幾種常見 Markdown 寫法,strip 完仍然不是以 `-`/`*` 開頭,於是既不進入「REVISIT 檢查」也不算「表格行跳過」,而是直接被 `continue` 跳掉——doctor 的 E5 完全看不到它,不計入到期也不計入壞損。
2. S10、S11 都明講「跟 E5 同一套判定」(73、107 行),等於這個既有盲點被原封不動繼承進新的推送閘。實測情境:作者在筆記裡用編號步驟寫「3. REVISIT:2026-01-01 補跑一次驗證」,這行:(a) 舊 E5 不會把它算進到期清單;(b) 新 S10 不會把它當成「新寫的 REVISIT 行」去檢查格式,散文式、沒有日期也沒有條件式的寫法可以直接推送過關,S10 對這種寫法形同不存在。
3. spec 沒有一處提到「清單記號只認 `-`/`*`,編號清單不算」是刻意的收斂還是遺漏;鏡像核對段(152 行)也沒提到這一項,顯示 r1 沒查到這個既有函式的既有限制被新功能繼承。

severity: minor

2. 對一份連結很多的計劃(`related`/反向連結、`plan_refs` 大量指入的計劃在本 repo 並不罕見,見 git status 裡本次改動就牽涉好幾篇這類節點),如果實作照 §0 的乙評估函式原樣重用(對每個 when-status 標記各查一次 git 或讀樹),使用者跑一次 `lumos set <計劃> status done` 可能要吃到接近 60 秒甚至更久,而且完全沒有 §0 那種「印出沒判到的行數、記 degraded」的使用者可見退場機制——指令要嘛等、要嘛看起來像卡住。

## F7 guard settle 的歷史說法改寫只處理 `guards:` 清單的第一篇家筆記,多家筆記時其餘幾篇沒人管

severity: major
blocking: 是 — 一份守衛紀錄合法地掛著兩篇以上家筆記時,S4 的改寫只會找到、只會改到第一篇,其餘家筆記裡「還沒有測試在守這條」這種預告句會在守衛紀錄已經轉正之後繼續留著——這正是本計劃要防止的「已經轉正還寫預告」(c1),等於新功能自己會製造出它自己要抓的那種漂移。
引句:「整個 settle 包在 `_vault_write_lock` 裡;先改家筆記的預告行(既有邏輯),再**一次寫入**守衛紀錄」

1. `guards` 欄位本來就是清單型別,而且是刻意設計成可以放多個值:`_guard_touches` 裡有明確註解「`guards` 可以有好幾個值(代碼審 r1 通才席):欄位本來就是清單,只看第一個會讓第二篇家節點管的檔永遠算不到」(`scripts/lumos:11753-11754`),對應的讀取寫法 `homes = [...as_list(gn.fields.get(GUARD_MARK_FIELD))...]`(`scripts/lumos:11755`)確實會把全部值都讀出來——這條路徑(判斷有沒有碰到)是對的。
2. 但「轉正要改哪一篇家筆記的預告行」走的是另一支函式 `_guard_home_of`(`scripts/lumos:11700-11704`):`g = n.fields.get(GUARD_MARK_FIELD); if isinstance(g, list) and g: return str(g[0]).strip()` ——只回傳清單的第一個值。`cmd_guard_settle`(既有指令)就是用這支函式決定要改哪篇(`scripts/lumos:11804`),而 spec 71/55 行講的「先改家筆記的預告行(既有邏輯)」,字面上就是沿用這支只認第一篇的函式。
3. `PRIOR-ART` 段(27 行)列出的六項借用裡沒有提到這個「只認第一個目標」的既有限制,〈誠實界線〉也沒有提到多家筆記時歷史說法改寫的覆蓋範圍;S4(101 行)寫「其他行一字不動,status 與這些句子應同一次寫入」,通篇用單數語氣描述「找到固定句型→改寫」,沒有一處處理「有兩篇家筆記各自有一份預告行」這個既有清單語意允許發生的情況。
4. 這個欄位是否真的會有兩篇以上家筆記同時各自帶著獨立的預告句(而不是只有一篇在等轉正),要看 `guard plan` 建立時是不是只曾經寫進一篇——`_guard_plan_write_node` 建立時只寫入單一 `rel`(`scripts/lumos:11563`),多篇家筆記目前只能靠手改 `guards:` 欄位湊出來。⚠ 我沒有找到某支指令能自動把第二篇家筆記的預告行也補上,所以「兩篇家筆記各自都有一行待轉正的預告句」目前主要靠手改;但正因為是手改、且 CLAUDE.md 鐵則本身就要求耐受「守衛紀錄被手改過」這類情境,這條路徑不能假設不會發生。
