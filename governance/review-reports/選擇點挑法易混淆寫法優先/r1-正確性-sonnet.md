severity: minor

審查摘要:我讀了 `_choice_pick_iter`(`scripts/lumos:79358`)、`_choice_pick`、`_choice_file_points` 的呼叫端,和型錄實際的 55 列選擇點表,自己推了一遍。核心宣稱「只有同一級類別的行,挑到跟改之前同一個壞法」成立,我找不到反例。理由:改之前是 `cats = [categories 順序中這行有的類別]` 一次 `Random(seed).shuffle`。新設計若這行的類別全在同一級,該級子清單等於舊的 `cats`(順序相同、種子相同),打亂結果逐位元一致。API 這級只有一個類別,單元素的 shuffle 不消耗亂數。NUL 與 SBR 那級有 2 個類別,每級各自 `Random(seed)` 重建時結果不受前一級影響。下面是我找到的 gap,都不致挑錯壞法。

## F1 型錄沒有〈用詞〉這一節,「補一句說明三級」的落點指不到
severity: minor
blocking: 否 判準:只影響文件落點、不改挑法行為,實作時改寫落點即可。
引句:「型錄〈選擇點表〉的〈用詞〉補一句說明三級」

1. spec〈做法〉要在型錄〈選擇點表〉的〈用詞〉補一句。
2. 型錄 `## 選擇點表` 一節(`skills/kotlin-idioms/checks-catalog.md:1654`)只有說明段落、「已撤列號」行與表格,沒有名為〈用詞〉的小節。
3. 全型錄 grep `〈用詞〉` 為 0 筆。〈用詞〉是 `_choice_pick_iter` docstring 指向另一份計劃(改動選擇點計劃)的詞。
4. 實作者找不到要補的位置。表頭欄位已有類別欄,但沒有「等級」欄的定義處,「型錄等級欄寫在 kotlin-idioms 型錄」(〈落點〉)也跟〈做法〉說的「補一句」互相矛盾:一個說加欄,一個說補一句。

## F2 等級表怎麼送進 `_choice_pick_iter` 沒寫,手造的 tables 與簽名都會被牽動
severity: minor
blocking: 否 判準:屬可執行性補充,有明確補法(缺等級表時全當第 3 級),不影響設計正確性。
引句:「跟 categories 一起由 choice_tables 交出」

1. `_choice_file_points` 只把 `tables["categories"]` 經 `functools.partial(_choice_pick, ..., tables["categories"], fp, ctx)` 交給挑法(`scripts/lumos:79494`)。`_choice_pick_iter` 與 `_choice_pick` 的簽名都只收 `categories`,等級表進不去。
2. 要嘛擴簽名,要嘛把 `categories` 改成帶等級的結構,兩種都要同步改 partial 與 `_choice_pick` 的轉呼叫。spec 沒寫選哪種。
3. 既有測試直接用 `_choice_pick(..., tables["categories"], fp)` 位置參數呼叫(`scripts/test_lumos.py:143866`、`:148870`),還手造 `{"choice": rows, "arid": [], "categories": [...]}`(`scripts/test_lumos.py:148442`、`:148918`、`:148931`、`:151210`)。這些手造表沒有等級鍵。
4. 若實作寫成 `tables["tiers"]` 直接取值,會 KeyError。S3「不在等級表的類別當第 3 級」只管類別缺,沒管整張等級表缺。
5. 補法:缺等級表時整體退化成全第 3 級,也就等於舊挑法。

## F3 第 1 級「API 全部 35 列」裡混了不是易混淆兄弟寫法的列,會壓過空值與刪陳述
severity: minor
blocking: 否 判準:這是分級的設計取捨,屬使用者原意的邊界,影響放行量但不是挑錯。⚠ 判不準使用者是否要這些列也算第 1 級。
引句:「類別 API 全部 35 列,例:協程串流換法、協程範圍、取消保護、延後啟動、緩衝滿了怎麼辦、Compose 的 key、集合兄弟函式」

1. 型錄 API 類別實際 35 列。其中 C-31、C-54、C-55 的 `special` 是 `drop_call`,C-37 是引數 `delete`,等於刪呼叫或刪引數。這幾列的性質跟第 2 級的 SBR(刪陳述,C-18)相同。
2. C-43、C-44、C-45 是 `toInt`、`toLong`、`toDouble` 互換,是數值轉型。它們比 `>`→`>=` 難測,但不是 spec 例子裡的「時序易混淆」。
3. 輸入例:一行 `val x = f(a)?: b.toInt()`(NUL 的 `?:` 加 API 的 `toInt`)。新順序一律挑 `toInt`→`toLong`。使用者原意(NUL 該排第 2 級)雖仍成立,但這行 NUL 被擠後面。
4. 〈實務隱患〉已預告第 1 級等價放行量會上升,這幾種列又更可能是等價,S4 要特別量。spec 未說明是否要把 `drop_call`、`delete` 與轉型列另分一級。

## F4 〈白話〉表的 UOI 說明「加減反向」與型錄不符
severity: minor
blocking: 否 判準:純文字敘述錯誤,不影響挑法。
引句:「| UOI | 加減反向(`!`) | 2 |」

1. 型錄 C-16 是「拿掉否定」(候選 `$B`),C-17 是「加上否定」(候選 `!$X`),見 `skills/kotlin-idioms/checks-catalog.md:1687`。
2. UOI 沒有「加減」(加減是 AOR),寫成「加減反向」會讓讀者把 UOI 跟 AOR 的 `+ -` 混淆。應寫成「否定加上或拿掉」。
3. 各類列數核對:API 35、NUL 2、SBR 1、AOR 5、ROR 8、LCR 2、UOI 2,與我用 `choice_tables` 實跑的計數相符。

## F5 規格閘現有兩條 WHY 寫著「類別用行指紋當種子洗牌」,spec 只說「補一行」
severity: minor
blocking: 否 判準:是筆記過期風險,不是設計缺陷;這不破壞規格閘宣稱的行為(同一行重跑挑同一個壞法,仍成立)。
引句:「[[Systems/規格閘]](選擇點挑法的守檔筆記)補一行 WHY」

1. 規格閘節點現有的 WHY 寫「每行最多一個壞法照論文 4.1 Listing 2 的迴圈(類別用行指紋當種子洗牌、取第一個產得出的)」。另一條寫「論文整次呼叫洗一次類別…這裡每行各用自己的種子」。
2. 改完後類別不再是整批洗牌,變成「分級再各級洗牌」。只補一行新 WHY 會讓舊句子跟新行為並存,對下一個讀者是矛盾訊號。
3. 要同時改寫或標記該兩行(例如在原 WHY 後加「分級後見某條」),spec 的〈落點〉沒列。
4. 「牽連節點固定席」判定:規格閘節點宣稱的行為(同一行同一內容跨 rebase 挑同一壞法、種子不含行號)不受影響,因為種子仍是行指紋、每級各自重建 `Random(seed)`,穩定性不變。
