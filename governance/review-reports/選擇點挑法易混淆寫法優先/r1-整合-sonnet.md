## I1 設計寫「改挑的行會被當成新的要處置」,程式碼不是這樣:已殺掉、已放行的行不會重判
severity: major
blocking: 是(〈回退〉與〈實務隱患〉對上線後行為的宣稱與程式相反,消費專案推送時會靜默跳過新壞法)

1. 投稿者輸入:一行原本挑到 ROR 壞法,記帳為 killed。上線後同一行改挑 API 壞法。
2. 有效處置只看 (檔, 行指紋) 同鍵最新一筆。killed 只比對 `killing_test` 還有沒有條款綁,不比對 `new_sha`。放行檔的鍵是 `choice:<檔>:<行指紋>`,不含壞法。見 `scripts/lumos:79774`(`_choice_disposition`)。
3. 所以 killed 且測試仍被綁的行、被放行的行,新的 API 壞法不會被跑,也不會被當成新的要處置。
4. 放行的行更糟。放行理由當初是針對 ROR 寫的「等價:…」,現在默默蓋住 API 壞法。第 1 級的兄弟寫法剛好是最需要測試守的那一類,卻不會被重判。
5. 同一件事影響 S4:「批 4a 範圍改挑的行數、改挑後殺/存活數」。在消費專案既有帳本上量,已處置的行不會重跑。計劃沒寫重算是清帳、用 `--only`,還是用空帳本。這一條 S4 因此無法照做。

7. 〈回退〉段寫「跟帳上的身分對不上,推送前那道會把它們當成新的要處置」,同樣與程式不符。

## I5 第 1 級「API 全部 35 列」並不都是易混淆的兄弟寫法,與立論自相矛盾
severity: major

引句:「易混淆的兄弟寫法(類別 API 全部 35 列,」

1. 使用者原話的理由是「運算式靠寫好的測試基本上就一番兩瞪眼」,舉例是 `flatMapLatest`↔`flatMapConcat` 要特定時序才看得出。

4. 型錄統計(API 35、ROR 8 等)我已核對相符,但分級粒度與理由不符。〈不做〉沒有說明為何不按列分級。
