# 選擇點挑法易混淆寫法優先_計劃

## 白話

推送前那道選擇點檢查,把改到的程式一處寫法換成兄弟寫法(叫「壞法」),守的測試紅了叫「殺掉」、全綠叫「存活」(存活就表示沒有測試守住那個選擇)。一行只挑一個壞法(一行挑好幾個,報告會長到沒人看)。同一行同時有好幾類可以挑時,現在照 Google 論文 4.1 的做法讓各類機會相等:類別隨機排序;種子用這一行的指紋(「行指紋」:這一行內容算出的雜湊,同一行每次挑到同一個;論文整次呼叫洗一次、沒規定種子,見 [[Systems/規格閘]])。

類別代號(定義在型錄 `skills/kotlin-idioms/checks-catalog.md`〈選擇點表〉,清單寫死在規則包自檢程式 `configs/ast-grep/kotlin-android/check.py` 的 categories):

| 代號 | 換什麼 | 型錄列數 |
|---|---|---|
| API | 兄弟函式或參數互換(flatMapLatest↔flatMapConcat、supervisorScope↔coroutineScope、NonCancellable、LAZY、BufferOverflow、Compose 的 remember/LaunchedEffect key、filter↔filterNot 這類集合兄弟函式等) | 35 |
| NUL | 空值處理(`?:`、`?.`) | 2 |
| SBR | 刪掉一個陳述 | 1 |
| AOR | 算術運算子(`+ - * / %`) | 5 |
| ROR | 比較運算子(`< <= > >= == !=` 等) | 8 |
| LCR | 邏輯運算子(`&&`、`\|\|`) | 2 |
| UOI | 加減反向(`!`) | 2 |

使用者 2026-11-27 裁:易混淆的寫法比運算子更需要測試。原話:「我覺得那種易混淆的語法問題會比運算式更需要測試,因為運算式靠寫好的測試基本上就一番兩瞪眼」。比方 `flatMapLatest` 跟 `flatMapConcat` 換了,只有特定時序的測試才看得出差別;`>` 換成 `>=`,一般邊界測試就會紅。這份把挑法改成**先分三級、同一級裡照舊打亂**:

1. 易混淆的兄弟寫法(類別 API 全部 35 列,例:協程串流換法、協程範圍、取消保護、延後啟動、緩衝滿了怎麼辦、Compose 的 key、集合兄弟函式)。
2. 空值處理與刪掉陳述(類別 NUL、SBR)。
3. 運算子(類別 AOR、ROR、LCR、UOI)。

依據:實驗專案正式程式 4300 行裡,一行兩個以上方法呼叫的有 226 行(約 5%,其中帶 lambda 的 111 行);以 `.` 開頭的續行只有 12 行。串接多半寫在同一行,所以不同類別撞在同一行的機會不小。

WHY:同一行多類可挑時,易混淆的兄弟寫法先挑,運算子最後 [出處:2026-11-27 使用者裁] [因:運算子換了一般邊界測試就紅,兄弟寫法要特定情境才看得出差別、更需要有測試守] [不選:照論文 4.1 各類機會相等] [代價:不再跟論文同一套挑法;運算子在多類同行時幾乎不會被挑到]

## 做法

- 等級表放在規則包自檢程式 `configs/ast-grep/kotlin-android/check.py`,緊鄰寫死的 categories(一處是唯一來源):`{"API": 1, "NUL": 2, "SBR": 2, "AOR": 3, "ROR": 3, "LCR": 3, "UOI": 3}`,跟 categories 一起由 choice_tables 交出;型錄〈選擇點表〉的〈用詞〉補一句說明三級。不在等級表裡的類別(日後新加沒補等級)當 3。
- 挑壞法那支函式(_choice_pick_iter,`scripts/lumos`)排類別時:每一級各自取出這一行有的類別(照原本 categories 的順序),各用同一個行指紋種子打亂,再由第 1 級往第 3 級串接;節點與候選的順序不動。這樣只有同一級類別的行,打亂的清單跟改之前完全一樣,挑到同一個壞法。
- 合批編譯換候選、跳過集合都從同一支函式往下取,不另寫一套。

- [S2] 挑壞法 應 在同一行只有同一級兩類(例 ROR 與 AOR)時挑到跟改之前同一個 [test:t_choice_pick_tier_same_level_unchanged]

## 不做

- 不改「一行只挑一個」;一行多挑留給 [[Projects/選擇點變異常駐切換最小實驗_計劃]] 量出單個壞法夠快之後再議。
- 不改節點與候選的挑法,只改類別順序。
- 不加新類別;補類別照 [[Projects/選擇點表第四批常用語法_計劃]] 走。

## 回退

把 _choice_pick_iter 排類別那段改回「全部類別一起用行指紋打亂」、拿掉等級表,一次 git revert 那次功能提交即可。選擇點紀錄的「身分」(檔、行指紋、列號、改前改後內容的雜湊)本身不綁挑法順序;但回退後挑法變回舊的,在新挑法下入帳的多類同行那幾行會挑到另一個壞法、跟帳上的身分對不上,推送前那道會把它們當成新的要處置——跟上線時一樣,要在那次推送說明。

## 實務隱患

- 改了挑法,已入帳的選擇點紀錄(身分綁挑到的壞法)會對不上,推送前那道會把改挑的行當成新的要處置;上線時要在同一次推送裡說明、或照既有的身分換版做法處理。
- 第 1 級的兄弟寫法較容易是等價(例:只有一個元素時 flatMapLatest 與 flatMapConcat 行為相同),放行量可能上升;S4 要量。

已排除:金流:只改推送前選擇點那道挑哪個壞法的順序,不碰任何付款或帳務
已排除:對外送出:挑法在本機算,不發任何對外請求
已排除:不可逆:挑法改回原順序就回到原狀;多類同行的幾行要重新處置一次(見〈回退〉),不會留下撤不掉的東西
- 守衛面:會改推送前選擇點那道挑出的壞法(這是守衛面改動,照走設計審);改挑的行在第一次推送會被當成新的要處置,見上一條。
