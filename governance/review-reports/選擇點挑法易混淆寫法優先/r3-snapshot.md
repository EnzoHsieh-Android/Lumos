# 選擇點挑法易混淆寫法優先_計劃

## 白話

推送前那道選擇點檢查,把改到的程式一處寫法換成兄弟寫法(叫「壞法」),守的測試紅了叫「殺掉」、全綠叫「存活」(存活就表示沒有測試守住那個選擇)。一行只挑一個壞法(一行挑好幾個,報告會長到沒人看)。同一行同時有好幾類可以挑時,現在照〈Practical Mutation Testing at Scale〉4.1 的隨機挑法(Listing 2)讓各類機會相等:類別隨機排序;種子用這一行的指紋(「行指紋」:這一行與前後各 2 行內容算出的雜湊,同一行每次挑到同一個;論文整次呼叫洗一次、沒規定種子,見 [[Systems/規格閘]] 那條行指紋的 WHY)。

類別代號(清單寫死在規則包自檢程式 `configs/ast-grep/kotlin-android/check.py` 的 `CHOICE_CATEGORIES`,順序是 AOR、LCR、ROR、UOI、SBR、API、NUL,也是洗牌前的基準順序;每列屬於哪一類寫在型錄 `skills/kotlin-idioms/checks-catalog.md`〈選擇點表〉的類別欄):

| 代號 | 換什麼 | 型錄列數 |
|---|---|---|
| API | 兄弟函式或參數互換(flatMapLatest↔flatMapConcat、supervisorScope↔coroutineScope、NonCancellable、LAZY、BufferOverflow、Compose 的 remember/LaunchedEffect key、filter↔filterNot 這類集合兄弟函式、toIntOrNull→toInt 這類失敗時從回 null 改成丟例外的轉型、拿掉 retry 這類呼叫等) | 35 |
| NUL | 空值處理(`?:`、`?.`) | 2 |
| SBR | 刪掉一個陳述 | 1 |
| AOR | 算術運算子(`+ - * / %`) | 5 |
| ROR | 比較運算子(`< <= > >= == !=` 等) | 8 |
| LCR | 邏輯運算子(`&&`、`\|\|`) | 2 |
| UOI | 否定加上或拿掉(`!`) | 2 |

使用者 2026-11-27 裁:易混淆的寫法比運算子更需要測試。原話:「我覺得那種易混淆的語法問題會比運算式更需要測試,因為運算式靠寫好的測試基本上就一番兩瞪眼」。比方 `flatMapLatest` 跟 `flatMapConcat` 換了,只有特定時序的測試才看得出差別;`>` 換成 `>=`,一般邊界測試就會紅。這份把挑法改成**先分三級、同一級裡照舊打亂**:

1. 兄弟寫法(類別 API 全部 35 列)。
2. 空值處理與刪掉陳述(類別 NUL、SBR)。
3. 運算子(類別 AOR、ROR、LCR、UOI)。

依據:實驗專案正式程式 4300 行裡,一行兩個以上方法呼叫的有 226 行(約 5%,其中帶 lambda 的 111 行);以 `.` 開頭的續行只有 12 行。串接多半寫在同一行,所以不同類別撞在同一行的機會不小。

**上線後帳上已有紀錄的行怎麼走**(有效處置的鍵是 (檔, 行指紋)、不帶壞法,見 [[Systems/規格閘]] 有效處置那條 WHY):

- 殺掉(殺它的測試仍被條款綁著)或放行過的行:照既有決策不重跑,算有效處置——那條 WHY 寫「型錄改了、挑到的壞法換了,同一行的需求證據不該作廢」。本計劃不翻這個案。
- 殺掉但殺它的測試已沒有條款綁(過期)、跑不出結果的行:照舊重跑,用新挑法。
- 依覆蓋判的存活:覆蓋指紋含壞法內容,挑法換了就對不上,照舊重跑,用新挑法。
- 依守的測試雜湊判的存活:現在測試沒變就沿用舊判定。本計劃改成**帳上那筆的壞法(new_sha)跟這次挑到的一樣才沿用**,不一樣就用新挑法重跑——不然帳上寫「存活」、畫面顯示的卻是從沒跑過的新壞法,人會對著錯的壞法補測試或放行。這行之前的判讀紀錄(綁壞法內容)也跟著作廢,要重判。

WHY:同一行多類可挑時,兄弟寫法先挑,運算子最後 [出處:2026-11-27 使用者裁] [因:運算子換了一般邊界測試就紅,兄弟寫法要特定情境才看得出差別、更需要有測試守] [不選:照論文 4.1 Listing 2 各類機會相等;照論文 4.2 Listing 3 依歷史存活率與回饋排序(我們沒有累積到能排序的歷史量)] [代價:多類同行時運算子幾乎不會被挑到;殺掉與放行過的舊行不受益]

WHY:依測試雜湊沿用的存活,要帳上的壞法跟這次挑到的相同才沿用 [出處:設計審 r2 正確性、邊界、整合三席] [因:沿用時畫面顯示的是現行挑法的壞法,帳上的判定卻是另一個壞法的,兩者對不上] [不選:照舊只比測試雜湊(帳與畫面錯位);殺掉與放行也一起比壞法(違反既有有效處置決策)] [代價:上線後第一次推送,多類同行的存活行要重跑、判讀要重做]

## 做法

- 等級表 `CHOICE_TIERS = {"API": 1, "NUL": 2, "SBR": 2, "AOR": 3, "ROR": 3, "LCR": 3, "UOI": 3}` 放在 `configs/ast-grep/kotlin-android/check.py`,緊鄰 `CHOICE_CATEGORIES`(同檔的類別、錨點、型別前提詞表都是這樣寫死的常數)。choice_tables 交出的表多一個鍵 `tiers`。
- choice_tables 的自檢(跟同檔「列的類別不在詞表內」報問題同一個慣例,有問題整張表判壞):
  - `CHOICE_CATEGORIES` 裡有類別不在 `CHOICE_TIERS`,或 `CHOICE_TIERS` 有 `CHOICE_CATEGORIES` 沒有的類別。
  - `CHOICE_TIERS` 的值不是 int 1、2、3 之一(布林值、字串、0、4 都算錯)。
- 挑壞法:`_choice_pick_iter` 與 `_choice_pick` 多一個具名參數 `tiers=None`,`_choice_pick` 轉傳;`_choice_file_points` 的 partial 傳 `tiers=tables.get("tiers")`。排類別時:
  - `tiers` 是 None 或空字典:整個當一級,就是改之前的挑法。
  - 否則每一級各自取出這一行有的類別(順序一律照 `categories`,不照 tiers 字典的順序),各用同一個行指紋種子打亂,再由第 1 級往第 3 級串接;tiers 裡查不到的類別當第 3 級(只是防呆,正式路徑上自檢已擋)。
  - 節點與候選的順序不動;串接後仍是一條候選序列,上一級沒有產得出的壞法(全被型別前提排除、產不出編輯、或全在跳過集合)就往下一級取,全部取完才是用盡(exhausted)。
- 只有同一級類別的行,打亂的清單跟改之前逐項相同(同一份清單、同一個種子),挑到同一個壞法。多級混合的行,第 3 級內部是對縮小後的清單打亂,換候選時的下一個候選順序也會變;跳過集合以壞法內容雜湊(new_sha)比對,換順序不會誤跳或漏跳。
- `_choice_kill_pick` 沿用存活的那個分支(守的測試雜湊沒變的存活)多比一項:帳上最新那筆的 new_sha 等於這次挑到的 new_sha 才沿用,不等就排進要重跑。殺掉、放行、依覆蓋判的存活、過期、跑不出結果的分支不動。
- 既有釘值測試 `t_choice_points_batch2_stable`(`_CB2_S7_PIN`)與 `t_choice_points_batch3_stable`(`_CB3_S7_PIN`)釘的是加入新類別前後挑法不變;三級挑法下其中 8 行會改挑(設計審 r2 正確性席在複本實跑):樣本 `configs/ast-grep/kotlin-choice/samples/arid.kt@f618b62cde0b:18` 由 C-1 改 C-18;樣本 choice.kt(`configs/ast-grep/kotlin-choice/samples/choice.kt@f618b62cde0b:58` 起)第 58、60 行由 C-1 改 C-20、C-22,第 61、66、67、68、69 行由 C-18 改 C-23、C-28、C-29、C-30、C-31。這 8 行照新挑法重釘,其餘照舊;改 `scripts/test_lumos.py` 前先 `lumos anchor approve`。實作時用 `-k choice` 跑一遍找有沒有別的釘值也被帶紅。
- 型錄〈選擇點表〉說明段補一句「同一行多類可挑時照三級先後挑,等級表在 check.py 的 CHOICE_TIERS」;型錄表格不加欄(55 列會重複同一類的值,而且等於第二個等級來源)。
- 第四批新增的 RET(回傳值換預設值):[[Projects/選擇點表第四批常用語法_計劃]]〈做法〉已補「`CHOICE_TIERS` 同時加 `\"RET\": 2`」;歸第 2 級是 AI 自定(2026-11-28:回傳值換成預設值性質接近刪掉陳述,不是兄弟寫法也不是運算子)。落地順序:本計劃先上線;第四批上線時兩個常數在同一個提交一起加,只加一邊自檢就擋。

把 `_choice_pick_iter` 排類別那段改回「全部類別一起用行指紋打亂」、拿掉 `CHOICE_TIERS` 與自檢、`_choice_kill_pick` 沿用存活那個分支拿掉 new_sha 比對、兩支釘值測試的 8 行改回,一次 git revert 那次功能提交即可。殺掉與放行的紀錄不受影響(鍵不帶壞法);回退後新行與要重跑的行回到舊挑法,上線時因 new_sha 不同重跑過的存活行,回退後又會再對不上一次、再重跑一次。
