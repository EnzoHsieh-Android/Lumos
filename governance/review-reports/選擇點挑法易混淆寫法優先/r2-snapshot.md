# 選擇點挑法易混淆寫法優先_計劃

## 白話

推送前那道選擇點檢查,把改到的程式一處寫法換成兄弟寫法(叫「壞法」),守的測試紅了叫「殺掉」、全綠叫「存活」(存活就表示沒有測試守住那個選擇)。一行只挑一個壞法(一行挑好幾個,報告會長到沒人看)。同一行同時有好幾類可以挑時,現在照〈Practical Mutation Testing at Scale〉4.1 的隨機挑法(Listing 2)讓各類機會相等:類別隨機排序;種子用這一行的指紋(「行指紋」:這一行與前後各 2 行內容算出的雜湊,同一行每次挑到同一個;論文整次呼叫洗一次、沒規定種子,見 [[Systems/規格閘]] 那條行指紋的 WHY)。

類別代號(清單寫死在規則包自檢程式 `configs/ast-grep/kotlin-android/check.py` 的 `CHOICE_CATEGORIES`;每列屬於哪一類寫在型錄 `skills/kotlin-idioms/checks-catalog.md`〈選擇點表〉的類別欄):

| 代號 | 換什麼 | 型錄列數 |
|---|---|---|
| API | 兄弟函式或參數互換(flatMapLatest↔flatMapConcat、supervisorScope↔coroutineScope、NonCancellable、LAZY、BufferOverflow、Compose 的 remember/LaunchedEffect key、filter↔filterNot 這類集合兄弟函式、toInt↔toLong 這類轉型、拿掉 retry 這類呼叫等) | 35 |
| NUL | 空值處理(`?:`、`?.`) | 2 |
| SBR | 刪掉一個陳述 | 1 |
| AOR | 算術運算子(`+ - * / %`) | 5 |
| ROR | 比較運算子(`< <= > >= == !=` 等) | 8 |
| LCR | 邏輯運算子(`&&`、`\|\|`) | 2 |
| UOI | 否定加上或拿掉(`!`) | 2 |

使用者 2026-11-27 裁:易混淆的寫法比運算子更需要測試。原話:「我覺得那種易混淆的語法問題會比運算式更需要測試,因為運算式靠寫好的測試基本上就一番兩瞪眼」。比方 `flatMapLatest` 跟 `flatMapConcat` 換了,只有特定時序的測試才看得出差別;`>` 換成 `>=`,一般邊界測試就會紅。這份把挑法改成**先分三級、同一級裡照舊打亂**:

1. 兄弟寫法(類別 API 全部 35 列)。
2. 空值處理與刪掉陳述(類別 NUL、SBR)。
3. 運算子(類別 AOR、ROR、LCR、UOI)。

依據:實驗專案正式程式 4300 行裡,一行兩個以上方法呼叫的有 226 行(約 5%,其中帶 lambda 的 111 行);以 `.` 開頭的續行只有 12 行。串接多半寫在同一行,所以不同類別撞在同一行的機會不小。

**只對還沒處置過的行生效**:已經殺掉(殺它的測試仍被條款綁著)或放行過的行,照既有決策不重挑——[[Systems/規格閘]] 有效處置那條 WHY 寫「型錄改了、挑到的壞法換了,同一行的需求證據不該作廢」,鍵是 (檔, 行指紋)、不帶壞法。本計劃不翻這個案,所以上線後舊行停在舊挑法挑到的那個壞法;新行與存活、跑不出結果要重跑的行才用新順序。

WHY:同一行多類可挑時,兄弟寫法先挑,運算子最後 [出處:2026-11-27 使用者裁] [因:運算子換了一般邊界測試就紅,兄弟寫法要特定情境才看得出差別、更需要有測試守] [不選:照論文 4.1 Listing 2 各類機會相等;照論文 Listing 3 依歷史存活率與回饋排序(我們沒有累積到能排序的歷史量)] [代價:多類同行時運算子幾乎不會被挑到;已處置的舊行不受益]

## 做法

- 等級表 `CHOICE_TIERS = {"API": 1, "NUL": 2, "SBR": 2, "AOR": 3, "ROR": 3, "LCR": 3, "UOI": 3}` 放在 `configs/ast-grep/kotlin-android/check.py`,緊鄰 `CHOICE_CATEGORIES`(一處是唯一來源;同檔的類別、錨點、型別前提詞表都是這樣寫死的常數)。choice_tables 交出的表多一個鍵 `tiers`。
- choice_tables 的自檢:`CHOICE_CATEGORIES` 裡有類別不在 `CHOICE_TIERS`、或 `CHOICE_TIERS` 有 `CHOICE_CATEGORIES` 沒有的類別,都回報問題(跟同檔「列的類別不在詞表內」報問題同一個慣例),整張表判壞。
- 挑壞法:`_choice_pick_iter` 與 `_choice_pick` 多一個具名參數 `tiers=None`;`_choice_file_points` 的 partial 傳 `tiers=tables.get("tiers")`。排類別時:每一級各自取出這一行有的類別(照 `categories` 原本的順序),各用同一個行指紋種子打亂,再由第 1 級往第 3 級串接;`tiers` 是 None 時整個當一級(就是改之前的挑法),表裡查不到的類別當第 3 級(只是防呆,正式路徑上自檢已擋)。節點與候選的順序不動。
- 只有同一級類別的行,打亂的清單跟改之前逐項相同(同一份清單、同一個種子),挑到同一個壞法。多級混合的行,第 3 級內部是對縮小後的清單打亂,換候選(合批編譯跳過)時的下一個候選順序也會變;跳過集合以壞法內容雜湊(new_sha)比對,換順序不會誤跳或漏跳。
- 型錄〈選擇點表〉說明段補一句「同一行多類可挑時照三級先後挑,等級表在 check.py 的 CHOICE_TIERS」;型錄表格不加欄(55 列會重複同一類的值,而且等於第二個等級來源)。
- 第四批新增的 RET(回傳值換預設值):在 [[Projects/選擇點表第四批常用語法_計劃]]〈做法〉補「`CHOICE_TIERS` 加 `\"RET\": 2`」;歸第 2 級是 AI 自定(2026-11-28:回傳值換成預設值性質接近刪掉陳述,不是兄弟寫法也不是運算子)。自檢會擋住漏補。

## 不做

- 不改「一行只挑一個」;一行多挑留給 [[Projects/選擇點變異常駐切換最小實驗_計劃]] 量出單個壞法夠快之後再議。
- 不改節點與候選的挑法,只改類別順序。
- 不讓已處置的舊行改挑(見〈白話〉,照既有有效處置的決策)。
- 不按型錄的列分級:型錄沒有類別以下的屬性,加一欄是第二個等級來源;API 類裡的轉型、拿掉呼叫幾列也進第 1 級,S7 分開量,量出它們多半等價再另議。
- 不加新類別;補類別照 [[Projects/選擇點表第四批常用語法_計劃]] 走,那份補等級。

## 回退

把 `_choice_pick_iter` 排類別那段改回「全部類別一起用行指紋打亂」、拿掉 `CHOICE_TIERS` 與自檢,一次 git revert 那次功能提交即可。帳不用動:有效處置的鍵是 (檔, 行指紋)、不帶壞法,已殺掉或放行的行照舊有效;回退後新行與要重跑的行回到舊挑法。

## 實務隱患

- 舊放行會蓋住新順序:一行之前因為運算子壞法被放行(理由是針對那個運算子寫的),新順序本來會挑兄弟寫法,但這行照既有決策不重挑。這是〈不做〉明列的範圍;S7 在空帳本上量,看得到有多少這種行。
- 第 1 級的兄弟寫法較容易是等價(例:只有一個元素時 flatMapLatest 與 flatMapConcat 行為相同),API 類裡的轉型與拿掉呼叫幾列也進第 1 級,放行量可能上升;S7 分列量。
- 改 `scripts/test_lumos.py` 要先 `lumos anchor approve`(測試總檔有錨點)。

已排除:金流:只改推送前選擇點那道挑哪個壞法的順序,不碰任何付款或帳務
已排除:對外送出:挑法在本機算,不發任何對外請求
已排除:不可逆:有效處置不帶壞法,改挑法與回退都不讓已入帳的紀錄失效;git revert 即回到原挑法
- 守衛面:會改推送前選擇點那道對新行挑出的壞法(這是守衛面改動,照走設計審)。
