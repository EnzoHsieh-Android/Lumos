severity: major

## F1 judge 以同指紋覆蓋會蓋掉人工放行,waive 與 judge 之間也沒有鎖
severity: major
blocking: 是 因為放行是人工裁定,被機器重跑默默蓋掉就不可還原,而且 spec 沒寫合併規則,實作者只能照字面覆蓋。
引句:「同一個指紋再跑一次就覆蓋成新的那份」
spec 的〈資料怎麼流〉第 2 步與第 4 步,加上〈實務隱患〉的「已排除:不可逆」。
問題:
- 放行存在 `.lumos/e2e-records/<指紋>.json` 的 `waiver` 欄位裡,judge 照字面覆蓋整份檔。具體輸入:先 waive 一份 fail 的紀錄,再對同一內容重跑 judge 得到 fail,`waiver` 欄位就消失,CI 又擋。
- 反方向也成立:pass 的紀錄被之後同內容的一次 fail 或 unjudged 蓋掉。
- 這一次放行的人、日期、理由只剩治理帳一筆事件,紀錄上留不下來。
- waive 是「讀紀錄、加欄位、寫回」,judge 是整檔覆蓋,兩者並行時 waive 的寫入會丟失(lost update)。spec 的 S9 沒有寫並行與保留放行的條款。
- 「已排除:不可逆」的理由是「刪掉紀錄就回到沒驗收的狀態」,但覆蓋會讓放行消失,這句沒有涵蓋。
- 預設放行的是「目前提交」的指紋,沒說在工作目錄有未提交的改動時怎麼處理,也沒說放行的指紋是否等於被推送提交的指紋。
佐證:既有原子寫入只保證檔不半寫,不保證讀改寫的互斥或合併,見 ``file: `scripts/lumos:28446` ``。

## F2 查證紀錄沒有版本欄,新舊 lumos 互讀沒有規則
severity: major
blocking: 否 因為第一版只有一種格式,影響在日後加欄位或改語意時才出現,現在補一個欄位就能擋住。
引句:「原始檔只在本機;紀錄只放摘要與數字。」
spec 的〈查證紀錄長怎樣〉整節,以及 S5 的 result 四種值。
問題:
- 全節沒有 `schema` 或 `version` 欄。
- 舊版 lumos 讀到新版紀錄時,碰到不認得的 result 值(例如將來新增一個值)會被當成什麼,沒有規定。若讀不懂就回 2,pre-push 的既有 fail-open 會把它放行。
- 新版 lumos 讀舊紀錄缺少新欄位時,是補預設、算 unjudged 還是回 2,也沒有規定。
- 紀錄進版控,團隊成員的 lumos 版本可能不同,這個情況一定會發生。
佐證:fail-open 行為見 spec 自己的〈實務隱患〉第三條,以及 `code-loop check` 回 2 後 pre-push 放行的既有做法。

## F3 指紋沒定義 symlink、子模組、LFS、檔案模式與串接邊界
severity: major
blocking: 是 因為 S2 的測試只涵蓋「改一個位元組指紋就變」,實作者遇到下列輸入時結果未定,可能崩潰成 rc2(fail-open 等於放行)。
引句:「依路徑排序後「路徑+內容」一起算 sha256;不看提交編號、不看目錄外的檔。」
spec 的〈查證紀錄長怎樣〉指紋一條,以及〈資料怎麼流〉第 3 步的「`git ls-tree` 取 `app_dirs` 底下的檔與內容」。
問題:
- 子模組:`ls-tree` 對子模組給 mode 160000 的 gitlink,`cat-file blob` 對它會失敗。spec 沒說要略過、算 commit 編號,還是回 2。
- symlink:mode 120000 的 blob 內容是目標路徑字串。spec 沒說要不要記模式。只改 `chmod +x` 或把檔換成 symlink 時指紋不變,而這兩種改動都會改行為。
- Git LFS:指紋算的是指標檔(sha 與大小),不是實際內容。換一個大檔但指標一樣是不可能的,但 LFS 檔在 CI 沒有 pull 時內容不影響指紋,這是對的。spec 沒寫這一點,實作者可能去讀工作目錄的真檔。
- 串接邊界:「路徑+內容」沒有分隔或長度前綴。只有一個檔時,路徑 `ab` 內容 `c` 與路徑 `a` 內容 `bc` 串出同一串位元組,指紋相同。
- `app_dirs` 條目的比對方式:若實作用字串前綴,`app/src` 會連 `app/src2/` 一起收進來。
- 非 UTF-8 檔名:`ls-tree` 不加 `-z` 時會被引號跳脫。spec 沒說加 `-z`,也沒說排序用的是位元組序還是字串序。
- 換行符與大小寫:取的是 blob,不受 autocrlf 影響,這是對的,但 spec 沒寫。大小寫不敏感檔案系統上的工作目錄與樹不一致,也因為只讀樹而不影響。
- 這些要補寫成條款並各配一支測試。既有的 `ls-tree -z` 讀法可以借用:``file: `scripts/lumos:9817` ``;它已經把 symlink 與子模組分成 `symlink_rejected` 與 `special_file`,見 ``file: `scripts/lumos:9896` ``。

## F4 `app_dirs` 改動讓所有舊紀錄失效,沒有說明也沒有遷移
severity: minor
blocking: 否 因為失效方向是安全的(多要求一次驗收),只是沒寫會讓人以為是 bug。
引句:「指紋只算這些底下的檔,也是「這個分支有沒有改到 App 程式」的判準。」
spec 的〈設定〉`app_dirs` 條目。
問題:
- 指紋不含 `app_dirs` 這份設定本身。加一個目錄,樹的雜湊就變,所有舊紀錄全部對不上,要全部重跑。這可以接受,但 spec 沒寫。
- 反過來,拿掉一個目錄,可能與舊紀錄的指紋巧合相同,內容不同的設定卻共用同一份紀錄。
- 同一個 `app_dirs` 只列出不存在的路徑時,結果是空集合的固定指紋,所有分支共用這一份紀錄。S1 沒要求路徑必須存在。
佐證:S1 只檢查跳出專案根,見 spec 條款 S1。

## F5 紀錄寫一半或損壞時的處理沒寫,而且會變成放行
severity: major
blocking: 是 因為 spec 自己承認紀錄檔壞掉會變成放行,但沒要求寫入端防半寫,也沒定義「讀不了」的範圍。
引句:「所以紀錄檔壞掉會變成放行」
spec 的〈實務隱患〉第三條,以及〈資料怎麼流〉第 3 步最後一段、S12。
問題:
- 具體輸入:一份被截斷的 JSON 紀錄檔,檔名正好是被推送提交的指紋。`check` 回 2,pre-push 放行,CI 的結果還待確認。
- 沒有條款要求 judge 與 waive 用原子寫入。既有的 `_write_lf` 與暫存檔改名做法可借用,但 spec 沒指定,實作者可以直接 `open(...,"w")`。
- 磁碟滿:寫失敗時要不要保留舊紀錄,沒寫。S12 說「不得留下沒有紀錄的半套結果」,但 judge 自己寫不出紀錄時範本腳本能做的只有印錯,這條無法保證。
- 暫存檔(例如 `.tmp-` 開頭)若放在 `.lumos/e2e-records/` 底下,一次 `git add .lumos` 就會進版控。
- 讀紀錄時是按檔名取指紋那一份,還是掃整個目錄,spec 沒寫。掃目錄時任何一份壞檔都會讓所有提交的判定回 2。
- 「壞檔」與「找不到」要分開:壞檔應回 1 並提示重跑或放行,不該落在 rc2。這一點與「不改 fail-open」並不衝突,因為那是 check 對非 1 的處理,不是判定本身。
佐證:原子寫入的既有寫法見 ``file: `scripts/lumos:28461` `` 與 ``file: `scripts/lumos:63357` ``。

## F6 時間欄位與放行日期的時區、時鐘沒定義
severity: minor
blocking: 否 因為時間只用於記錄,不參與放行判定,錯了不會誤放。
引句:「寫下誰(git 設定的使用者)、哪一天、理由」
spec 的〈資料怎麼流〉第 4 步與〈查證紀錄長怎樣〉的環境一條。
問題:
- 「哪一天」沒說用本地時間還是 UTC。既有程式碼多用 `astimezone().isoformat`,見 ``file: `scripts/lumos:1941` ``,但 spec 沒要求沿用。
- 開始與結束時間在實機與電腦時鐘不同步時,紀錄上的時間會不一致,但不影響判定。
- 放行沒有到期日。因為綁指紋,內容一變就失效,所以不是缺口,但這一點沒寫。
- 「git 設定的使用者」未設定時(CI 或新機器)怎麼辦,沒寫,會讓 `waiver.who` 變空字串。

## F7 run 目錄與紀錄檔隨使用無限增長,指紋在大 repo 的成本沒寫
severity: minor
blocking: 否 因為這是成本問題不是正確性問題,實作時可補。
引句:「原始輸出放 `.lumos/artifacts/android/<run-id>/` 底下的 ui、visual、macrobench、stability 四個子目錄」
spec 的〈資料怎麼流〉第 1 步,以及 `.lumos/e2e-records/`。
問題:
- 每次跑留一個 run 目錄,裡面有截圖三張、報告與 macrobench 輸出,沒有清理規則,也沒有數量上限。
- `.lumos/e2e-records/` 每個指紋一份且進版控。長壽專案與多分支下檔數只增不減,沒有清理或封存規則。
- 指紋算法:`app_dirs` 有上萬檔時,逐檔 `cat-file` 一次一個行程會很慢。pre-push 與 CI 每次都要算。spec 沒要求用一次 `cat-file --batch`,也沒有時間上限或逾時。既有程式碼已有一次 `ls-tree` 搭配批次取 blob 的做法,見 ``file: `scripts/lumos:24344` ``。
- 二進位大檔(圖片、`.so`)整檔讀進記憶體再算雜湊會有記憶體問題,spec 沒要求串流。
