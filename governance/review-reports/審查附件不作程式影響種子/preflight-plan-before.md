## 最小改法

影響分析種子入口沿用原簿記目錄、原程式副檔名／首行辨識與 Git 凍結模式／物件；只排除已知普通非程式附件。程式副檔名、無副檔名腳本與可執行檔保留；無副檔名普通卷證按凍結首行排除，未知或超過既有上限時保守保留；已刪檔用刪除前模式，staged 用索引模式。共享審查角色檔案消費者使用同一入口，不另抄一套程式清單。附件仍由 Git 追蹤。零新依賴，不改評分、鏡頭快取、合約條款、審查輪數與處置語意。

- [S1] 當差異只含既有簿記目錄下的審查附件時，系統應排除歷史片段；當差異同時包含正式程式、已刪檔或相鄰目錄程式時，系統應保留其種子、家與事故，而卷證檔仍被 Git 追蹤。[test:t_impact_diff_review_artifacts]

## 修復驗證的時間前提

角色內容子集三次 58過1敗，失敗均為既有時間上限降級，兩個失敗案例各自單跑綠，凍結 ca6701b2 的同子集也曾59全綠。不能靠多跑直到綠結案。可控時鐘維持真 Git／正式分類，只讓選檔耗時觀測為3.1秒；原三秒預算時两功能案例各失敗1斷言，測試預算30秒時原斷言全部通過，卷證 r2-role-clock-control.json。

因此只在兩個「讀凍結內容」功能案例顯式使用既有 budget=30 接縫；內容與斷言不變，正式 _review_roles 預設3秒、零預算與期限降級案例均另验。不是把失敗分類當成功，也不加入自動重試。這是修復驗證上下文的補正，不是新放行判準。
PRIOR-ART:pytest 官方 flaky 指出過嚴時間斷言与未隔離系統狀態會造成不可靠失敗，來源 https://docs.pytest.org/en/stable/explanation/flaky.html 。本文並未把該來源當本案根因證明；根因依上方真現場與可控時鐘實驗。
RETIRE-IF:若兩個功能案例改為無外部 Git 延遲的固定內容／可控時鐘驗證，撤回顯式30秒測試預算；事件入口為角色功能測試 fixture 改動的代碼審。

最後一條預算案例另外揭露真入口缺陷：budget=0 仍先讀設定與選檔，忙碌現場超過原三秒斷言；不是把它當測試雜訊刪掉。新增零預算禁止 Git／選檔探針先0過2敗，r2-zero-budget-red.json；修 _review_roles 零預算直接回超時空結果，沒有計算過的角色不冒稱已算好。讀數上限的正面段也顯式给足30秒測試預算，原零預算三秒斷言保留。修後角色子集16案例61斷言全綠，r2-role-zero-budget-green.json，正式預設仍3秒。這只修零預算入口，不冒稱已收緊所有正預算 Git 查詢；既有正預算兩趟讀取限制仍沿原角色計劃的事件／日期回頭條件。
