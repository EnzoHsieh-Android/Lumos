# D4 提交時自動更新筆記日期 回滾與時序鏡頭審稿

審的是 /tmp/更新日期-r1.md,對照 /Users/enzo/harness/lumos-d4。
實驗全在 mktemp 臨時 repo 做,沒改任何檔。

派工單沒附合約或事故節點,所以逐條判節點那一步沒有對象。
我改查這功能會碰到的既有「綁版本、讀 updated」的機制,結果寫在最後的「合約與綁版本機制」一節。

## 實驗事實(F1、F2、F3 都用到)

在臨時 repo 裝一支印環境的 pre-commit,各種提交形態下 git 傳給掛鉤的 `GIT_INDEX_FILE`:

| 提交形態 | GIT_INDEX_FILE |
|---|---|
| 一般 `git commit`、`--amend`、rebase 中途 | `.git/index`(相對路徑) |
| `git commit -a` / `-am` | 絕對路徑的 `<repo>/.git/index.lock` |
| `git commit <路徑>` | 絕對路徑的 `<repo>/.git/next-index-<pid>.lock` |
| 連結工作樹(`git worktree add`)裡的一般提交 | 絕對路徑的 `<repo>/.git/worktrees/<名>/index` |

另外兩件實測:
- `-a` 時掛鉤裡 `git add` 成功,而且加進去的內容真的進了這個提交。所以 `-a` 不是臨時索引。
- 連結工作樹裡 `.git` 是一個檔案、不是資料夾,git 目錄在 `.git/worktrees/<名>/`。

## F1 「是不是預設索引」與「進行中狀態」的判法沒定義,照字面做會誤判 -a 與連結工作樹
severity: major
blocking: 是——判準:這道的跳過條件會把最常見的提交形態整批放掉,等於功能在主要路徑不運作,與驗收 S5 矛盾。

位置:〈範圍〉第三條「以下情形整個跳過」。

引句:「`GIT_INDEX_FILE` 指的不是預設索引」
引句:「`rebase-merge`/`rebase-apply` 資料夾、SQUASH_MSG 任一」

問題:spec 沒說「預設索引」怎麼比對、「資料夾」去哪裡找。實測 git 傳給掛鉤的值有四種寫法(見上表)。

具體例:
- 照字面比對 `.git/index`,`git commit -am "…"` 的值是 `…/.git/index.lock`,不相等,被當成指定路徑提交。輸入:改了正文的筆記加 `-am`。預期:`updated` 改成今天。實際:印「這次是指定路徑提交,日期沒自動改」,rc0,什麼都不改。
- 同一條規則在連結工作樹裡,一般提交的值是 `.git/worktrees/<名>/index`,同樣被誤判成臨時索引。使用者全域規則要求每個任務開獨立 git worktree,所以主力使用場景會整個失效。
- 進行中狀態若用 `test -d .git/rebase-merge`,連結工作樹裡 `.git` 是檔案,永遠找不到。在 worktree 裡 `rebase -i` 的 edit 停點再 commit,掛鉤不會跳過。正確寫法要走 `git rev-parse --git-path`(note-shape 的 MERGE_HEAD 判斷已經是這樣,但 spec 只對 MERGE_HEAD 說照 note-shape,其餘幾項沒說)。
- 真正的臨時索引只有 `next-index-` 開頭那一種。判準該寫成「basename 以 `next-index-` 開頭」,而不是「不等於預設路徑」。
- 驗收 S4 只列「指定路徑提交」,沒列 `-a` 與連結工作樹這兩個必須不跳過的情形,所以照字面實作測試照綠、實際漏。

## F2 部分暫存的擋下教人整篇加入,在共用工作目錄會把別的會談寫到一半的內容帶進這個提交
severity: major
blocking: 是——判準:spec 自己宣稱的安全性(不帶入未暫存改動)在並行會談下不成立,而擋下訊息的教法會直接造成這個污染。

位置:〈範圍〉第二條、〈做法〉第 3 點、〈實務隱患〉「提交前掛鉤改了工作目錄」。

引句:「點名那一篇,教 `git add <檔>` 後再提交」
引句:「不會把沒暫存的改動帶進提交」

問題一(教法):使用者全域規則明講同一個 repo 可能有別的 Claude 會談同時在動,別人的未提交改動不准碰。「工作目錄與暫存不一致」在這種環境裡常常就是別人的改動。掛鉤的訊息卻叫人 `git add <檔>`,等於教人把別人寫到一半的內容整篇進這個提交。現有的 `_nodehome_reader`([S38] 註解)的設計正是「另一個會談寫到一半、還沒加進索引的讀不到」,這道的教法與它相反。

問題二(時序):spec 的保證靠「先 `git diff --quiet` 確認一致,再改檔,再 `git add`」。三步之間沒有鎖。別的會談在 diff 之後、add 之前寫了這篇,`git add -- <檔>` 會把它整份加進去。輸入:A 的掛鉤剛確認 N 一致,B 這時存檔 N。預期:只改 `updated` 那一行進提交。實際:B 的半成品進了 A 的提交。

另一種擋法:先比對再用 `git update-index --cacheinfo` 或 `git hash-object -w` 只把「暫存內容 + 換掉那一行」寫進索引,不動工作目錄,就不需要擋部分暫存,也沒有 TOCTOU。要不要換做法是作者的事,但現在的寫法與宣稱不符。

## F3 中途被打斷或工具失敗時留下半成品,spec 沒說怎麼收拾
severity: minor
blocking: 否——判準:每種都能用現有指令收拾,沒有資料遺失;但會讓人看到不是自己造成的改動,而且驗收沒覆蓋。

位置:〈做法〉第 3、4 點、〈實務隱患〉「提交被後面的檢查擋下」、掛鉤 Gate UB。

引句:「其他非零(工具出錯)放行」
引句:「這道已經把日期改好、加進暫存區;修好後重提交會跳過已是今天的,不重複改」

具體例:
1. `git add` 失敗:另一個終端正握著 `.git/index.lock`(例如跑大批 `git add -A`),`git add` 回 128。spec 只定義了 `git diff` 回 2 以上的處理,沒定義 `git add` 失敗。結果:工作目錄那一行已經改了、索引沒進,這次提交放行但不含新日期。之後這篇一直顯示為已修改,下次提交又被判成「部分暫存」擋下,而使用者從沒手動編輯過。
2. 逐篇迴圈的第 k 篇被殺:前 k-1 篇已改已加、其餘沒動。spec 只說擋下時是這樣,沒說被殺時的狀態與重跑是否收斂(重跑會跳過已是今天的,所以會收斂,但沒有測試)。
3. 打斷的種類:pre-push 已有 `pp_stop_if_signaled`(`scripts/hooks/pre-push:50`)處理「回傳碼 128 以上是被訊號殺掉,不能當放行」。Gate UB 照 home check 的「只有 rc1 擋、其他放行」,SIGTERM 或逾時殺掉(143、137)時掛鉤會往下繼續提交。Gate H、Gate NS 目前有同樣的洞,這道要不要複製要明說。
4. 提交訊息編輯器:掛鉤在編輯器開啟之前跑。`git commit` 開了編輯器後放棄(空訊息),日期已經改在工作目錄、也已加進暫存區,沒有提交。使用者重新來過會看到一堆沒做過的 `updated:` 改動。
5. 改檔不是原子寫入。「只換那一行」若是 `write_text`,在改檔那一瞬被殺會留下被截斷的筆記。因為只有工作目錄與暫存一致才改,所以內容可從索引救回,但專案記憶裡有「共用檔原子寫入」的慣例,spec 沒採用。

## F4 設計審迴圈的「文件有沒有被事後改過」檢查看整檔 sha256,自動改日期會讓已通過的審查失效
severity: major
blocking: 是——判準:新功能會讓已通過的設計審在不相干的提交時被判失效,逼人白跑一輪審查,而且〈實務隱患〉與〈驗收〉都沒提到。

位置:〈範圍〉第一條、〈做法〉第 3 點(對象包含計劃筆記本身)。

引句:「暫存版本的 `updated` 不是今天」

事實:`_hash_chain_check` 最後比的是「最後一輪 result_sha256」與 `_sha256_file(spec_path)`(整個檔案的位元組雜湊,含開頭欄位)。見 `scripts/lumos:10275`;`_sha256_file` 在 `scripts/lumos:9146`。不符就回「spec 於審計後被改動(窗末 result ≠ 當前檔),需再過一輪」。對照:風險低的條款留痕用 `_clause_block_sha`,它的註解寫明刻意避開 `updated:`(`scripts/lumos:6858`);正文雜湊 `note_body_hash` 也排除開頭欄位。只有設計審這條鏈看整檔。

具體例:計劃筆記昨天建立、`updated` 是昨天,今天跑完設計審、折完、記帳(result_sha256 = 當時整檔雜湊),接著把計劃筆記連同實作一起提交。計劃筆記今天有正文改動(折審查意見就是改正文),`updated` 不是今天,掛鉤把它改成今天。檔案位元組變了,`loop status` 的 G3 變成「spec 於審計後被改動」。預期:審查仍然有效。實際:要再審一輪。
本案自己的計劃筆記也會踩到:`created: 2026-10-06`,審查若跨過午夜就是這個情形。

修法方向:要嘛排除計劃筆記(有 `Projects/` 開頭且正在走設計審的)、要嘛讓 G3 改成排除開頭欄位的雜湊。這兩個都比現在多一個前提,spec 至少要把它寫進〈實務隱患〉並給驗收條款。

## F5 提交時任何正文改動都自動把 updated 往前推,會靜默吃掉 doctor E2「建在已翻案決策上」的提醒
severity: major
blocking: 是——判準:這是改掉既有偵測的語意,不只是增加欄位更新;原本要有人看過並手動確認才消音,現在打一個錯字就消音。

位置:〈WHY〉的「因」、〈範圍〉第一條。

引句:「正文(開頭欄位之後)或 `summary` 欄位有差」

事實:`scripts/lumos:2486` 起的 E2 用「來源節點 `updated` 早於被翻案決策的 `ended`」判斷「這篇可能還建在已被推翻的決策上、沒跟上」。程式裡的註解寫明已知限制是「量少時手動 bump 消音」,也就是動 `updated` 本來是人的確認動作(`scripts/lumos:2531` 取值、`2532` 比較)。Check S(`scripts/lumos:2095`)也是用 `self_audit < updated` 判「更新後未重審」。

具體例:決策 D 昨天被翻案(`ended: 2026-10-05`),依賴它的節點 A 的 `updated` 是 2026-10-01,E2 會點名 A。今天有人在 A 的正文修一個錯字並提交,掛鉤把 A 的 `updated` 改成 2026-10-06,晚於 `ended`,E2 不再點名 A。預期:A 仍被點名,直到有人確認過。實際:提醒消失,沒人確認過。

spec 的理由只說「讀筆記的人與排序、過期判斷都看這一欄」,沒有寫到「過期判斷」其中一種是靠人確認、不是靠有沒有被動過。需要要嘛限縮(例如只在 E2 判斷後保持原樣、或記另一欄),要嘛明說接受並在 RETIRE-IF 加一條這類提醒的量測。

## F6 「不是今天就改成今天」會把日期往回改
severity: minor
blocking: 否——判準:不會遺失資料,只在機器時鐘或時區不一致時產生一次倒退。

位置:〈範圍〉第一條、〈實務隱患〉「時區」。

引句:「跨午夜提交的那篇記成提交當下的本機日期,接受」

具體例:兩台機器時區不同(或其中一台時鐘錯),甲在本機日期 10-07 凌晨改了筆記 `updated: 2026-10-07`,乙在本機日期仍是 10-06 時改同一篇正文。乙的掛鉤看到 `updated`(10-07)不是今天(10-06),改成 10-06,日期倒退。接著 `self_audit`(10-07)大於 `updated`(10-06),Check S 的比較(`scripts/lumos:2098`)變得不準。判準寫成「早於今天才改」(字串比較即可,格式已有 lint 保證)就沒這個洞;spec 沒說為什麼選「不等於」。

## F7 amend 以 HEAD 為基準,把提交改回與上一版相同的內容時會留下只有 updated 的改動
severity: minor
blocking: 否——判準:只在少見的「amend 時拿掉某篇的正文改動」才發生,結果是一行日期的雜訊,不是資料錯。

位置:〈範圍〉第一條「`--amend` 時 HEAD 是被修改的那個提交」。

引句:「`--amend` 時 HEAD 是被修改的那個提交,照同一規則」

具體例:提交 A 改了筆記 N 的正文(同時掛鉤把 `updated` 改成 10-01)。三天後 `git commit --amend` 前先把 N 還原成 A 的上一版,讓 A 不再含 N 的改動。暫存的 N 的正文與 HEAD(A)不同,`updated`(此時是 A 的上一版值)不是今天,掛鉤改成今天。結果 amend 後的提交對 N 只剩下一行 `updated`,而它的正文與上一版相同。S2 說「只改開頭其他欄位不動」,在這裡被這道自己違反。amend 的比對基準應該是 HEAD 的父提交(沒有父提交時用空樹),而不是 HEAD。

## F8 回退只講「退回提交」,沒說消費專案怎麼單獨關掉,也沒說版本偏斜時每次提交會印錯誤
severity: minor
blocking: 否——判準:不影響正確性,但 RETIRE-IF 預期會有人抱怨,而現有手段只有每次提交一次的環境變數。

位置:〈回退〉、〈範圍〉第四條、RETIRE-IF。

引句:「退回本案的提交即可:只新增一個指令與掛鉤裡一段呼叫;退回後 updated 回到靠人改」
引句:「消費專案要 `lumos update` 才拿到新掛鉤」

問題:
- note-shape 有 `note_shape.gate=off` 的設定可以長期關。這道只有 `LUMOS_SKIP_UPDATED_BUMP=1`,每次提交都要帶。RETIRE-IF 的第二個條件是使用者抱怨,這時使用者沒有長期的關法;掛鉤是 vendored 的,自己改了會被 `lumos update` 蓋掉。
- 版本偏斜:掛鉤與 `scripts/lumos` 不同步時(新掛鉤配舊主程式,或者退回後舊主程式配新掛鉤)呼叫不存在的子指令會 rc2,Gate UB 放行,但 stderr 的 argparse 錯誤每次提交都印。Gate CC 用 `2>/dev/null` 吞掉這種錯(`scripts/hooks/pre-commit` 的 Gate CC 註解),Gate UB 沒說要不要。
- 退回之後已經被自動改過的日期不用處理(它們本來就是真的改動日期),這一點 spec 沒說,但無害。

## F9 `updated:` 行不是單行純量、有 CRLF、或重複時怎麼辦沒定義
severity: minor
blocking: 否——判準:Gate L 會在之後擋下壞格式,不會靜默進版控;問題是擋下的是工具造成的、使用者沒做過的改動。

位置:〈做法〉第 3 點。

引句:「把工作目錄那篇開頭欄位裡唯一一行 `updated:` 換成今天(只動那一行,其他位元組不動)」

具體例:
- `updated` 寫成清單(`parse_frontmatter` 有處理 list,見 `scripts/lumos:1844` 的註解 GAP-2):換掉第一行後清單項目變成孤兒,YAML 壞掉,Gate L 之後擋下,而這時改動已經加進暫存區。
- CRLF 檔:`split_frontmatter` 用 `\n` 切、行尾帶 `\r`,「其他位元組不動」與換行符的處理要明說,否則新行是 LF、其餘是 CRLF。
- 開頭欄位裡有兩行 `updated:`:spec 說「唯一一行」但沒說不唯一時怎麼辦(跳過?擋?),這是個該有條款的分支。
- 已經有的 `updated: "2026-10-01"` 帶引號:Gate 1 會擋新增帶引號的日期,換成不帶引號的今天則沒問題,但要明說替換是整行換。

## F10 測試沒有時鐘注入點,跨午夜會假紅
severity: minor
blocking: 否——判準:只影響測試穩定度。

位置:〈驗收條款〉S1、S5。

引句:「提交進去的版本 updated 應 是今天;部分暫存時掛鉤 應 擋下」

問題:`scripts/lumos` 沒有 `LUMOS_TODAY` 之類的注入點(grep 無)。測試要斷言「今天」只能在測試裡用同一個公式算,23:59:59 時測試算的與掛鉤算的可能差一天。近期提交 `b6490dd0`(兩筆紀錄落在同一秒的假紅)是同一類毛病。spec 要嘛加一個測試接縫(環境變數),要嘛在測試裡把「今天」的取得與掛鉤放在同一行程裡。

## F11 〈天花板〉沒列出被整批跳過的提交形態
severity: minor
blocking: 否——判準:是文件與現實的差距,不是行為錯。

位置:〈天花板〉、〈範圍〉第三條。

引句:「`--no-verify` 繞過提交前掛鉤、`git commit <路徑>` 指定路徑提交時不會改。」

問題:〈範圍〉會跳過合併、cherry-pick、revert、rebase 進行中、squash 之後的提交,但〈天花板〉只列兩種。合併衝突解決與 rebase 的 edit 停點正是筆記內容真的會被手改的時刻,而且 spec 又明說「不做:推送前或 CI 再檢查一次」,所以這些改動的 `updated` 之後沒有任何補救點。這點應列進天花板,並與 RETIRE-IF 的 20 篇抽樣口徑對齊(抽到這類提交算不算「掛鉤被繞過」)。

  - 不可逆:有條件。提交進去的日期可 git 還原,但在 F2 的情形下別人的半成品會被帶進提交,屬資料污染。
  - 並行/鎖:有,見 F2、F3。
  - 時間:有,見 F4(跨日審查)、F6(倒退)、F10(測試)。
  - 回滾:見 F3、F7、F8。
  - 效能:REVISIT 的 100 篇量測合理;每篇一次 `git diff --quiet` 與一次 `git add`,各是一個子行程,量測時要包含這兩段。
- 驗收條款:見 F1(S4 缺 `-a`、連結工作樹)、F10。S6 的標號排在 S5 之前,不影響意思,但順序亂。
- 回退:見 F8。
- 天花板:見 F11。

## 合約與綁版本機制(對照結果)

| 機制 | 是否被這功能影響 | 為什麼 |
|---|---|---|
| 代碼審留痕 `code-loop pass`、表態 `dispositions` | 不影響 | 綁的是提交的 sha(`_codeloop_record_valid`),不是筆記內容;掛鉤的改動發生在提交建立之前,sha 事後才定。`path:line` 錨點只驗存在與行數範圍,而改 `updated` 是原地換一行,不位移行號。 |
| 風險低的條款留痕(`_clause_block_sha`) | 不影響 | 註解寫明排除 `updated:` 這類維護。 |
| `about_code_stamp`(`note_body_hash`) | 不影響 | 雜湊只算開頭欄位之外的正文。 |
| 設計審的文件指紋(`_hash_chain_check`) | 影響 | 見 F4。 |
| doctor E2、Check S、節點日齡 | 影響 | 見 F5、F6。 |
| `rebase -i` 的 edit 停點再 `--amend` | 規則上被跳過 | 見 F1(worktree 判法)、F11(沒補救點)。 |

## 結論

最嚴重 severity:major;blocking 條數:4(F1、F2、F4、F5);minor 7 條(F3、F6、F7、F8、F9、F10、F11)。
