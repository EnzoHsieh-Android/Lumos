### s1-f1 / blocker

佐證:file: `scripts/lumos:4277`(`cur = _sha256_file(spec_path)`,docstring 4253 明寫「窗末 result==sha256(當前檔)」)

說明:白話段只列出「凍結帳」「凍結報告」兩樣被凍住,唯獨沒提 spec 檔。而 G3 hash 鏈是四合取之一(`_loop_status_disposal` 內①),它驗的是「窗末 result_sha256 == 現在這一刻讀 `--spec` 路徑算出來的 sha」——讀的是**當前磁碟上的檔案**,不是任何凍結副本。計劃筆記(被審文件)本身照 CLAUDE.md 自己的規則會持續被 `lumos set`/`append`/`decision-add` 改動(狀態更新、補決策)。只要這份 spec 之後再被合法編輯一次,幾週後對同一個 loop_id 重放,G3 就會判「spec 於審計後被改動,需再過一輪」而 FAIL——不是判定邏輯壞了,是被審文件本來就會活著。這直接打穿「判定是純讀側決定論」這句話的前提,也讓 [S4] 週跑的「漂移=喊人」在最常見情境下必然是假警報,而非真的邏輯漂移。

### s1-f2 / major

引句:「輸入指紋:帳列 sha 集+報告 sha 集」

佐證:file: `scripts/lumos:4277`(G3 依賴 spec_path 的 sha,但此依賴未進指紋)

說明:`--freeze` 的輸入指紋只收「帳列 sha 集」和「報告 sha 集」,沒收 spec 檔的 sha。但 G3 合取項恰恰是拿 spec 檔現在的 sha 去對帳(見 s1-f1)。指紋既然不完整,回放器之後就沒有能力分辨「G3 FAIL 是因為判定邏輯被改壞或帳被動(真的該喊人)」還是「單純 spec 檔案事後被正常編輯(不算漂移)」——這兩者在 [S4] 的通知裡會長得一模一樣,而後者在這個工具鏈的日常運作裡是常態,不是例外。指紋要嘛把 spec 也算進去(那就得先解決 s1-f1 的凍結問題),要嘛在漂移訊息裡明確排除 G3 這一項單獨列,兩者現在都沒有。

### s1-f4 / major

引句:「golden 檔=判定快照非帳(帳不可撤原則不變)」

佐證:file: `scripts/lumos:10126-10147`(`groups.setdefault(rid_, []).append(r)` 後 `rid, latest = next(reversed(groups.items()))`——永遠抓「目前」最新一輪,函式簽章 `scripts/lumos:10101` 也沒有可指定歷史輪次的參數)
