## Finding 1 — blocker

**severity:** blocker · **blocking:** 是
**file:** `governance/review-reports/code-batch19/r1-snapshot.patch:246` (also `governance/autonomous-loop.sh:43` as of the frozen snapshot)
引句:「case "$cmd" in *autonomous-loop*) return 0 ;; *) return 1 ;; esac」
**why:** The identity check that "fixes" bug② (pid-recycling → permanent yield) matches the lock holder's `ps -p <pid> -o command=` output against the *literal substring* `autonomous-loop`. If the script is ever invoked through a path/symlink/wrapper whose command line doesn't contain that literal substring, a genuinely-alive, currently-running holder gets misclassified as "not us" (`lock_holder_alive` returns 1), and — critically — the "recheck" added to guard the takeover (`nowpid != oldpid`, line 300) does **not** catch this case, because the holder's pid genuinely hasn't changed. The taker proceeds straight to `mv "$LOCKDIR" "$dead"`, which succeeds against the still-live holder's lock.

I reproduced this end-to-end using the exact frozen-snapshot code (extracted verbatim from the patch, unmodified), with the holder invoked via a plain symlink (a completely ordinary "renamed/wrapped invocation" scenario, exactly what the task asked to check):

```
holder acquired lock, pid on disk = 87892
holder's actual ps command line: 'bash /tmp/.../renamed-run.sh /tmp/...'
contains 'autonomous-loop'? -> False
TAKER stdout: [22:36:13] 發現殘鎖(pid 87892 不是這支、或鎖齡過老),接管
TAKER_GOT 87903
lock/pid after taker ran: <missing>  (holder's pid was 87892)
HOLDER stdout: HOLDER_GOT 87892
HOLDER still ran to completion (was it still holding while taker acted)? True
```

Both processes (87892 and 87903) believe they hold the exclusive lock **simultaneously** — both printed their "got the lock" marker, and both were still alive/running at the same time. This is exactly the "資料互蓋" (backlog/archive corruption) failure mode this lock exists to prevent, and it fires silently, with no error message — the same "沒有訊息" property the task warns about for the over-tight direction, just on the loose side instead.

This doesn't require a hardcoded-string change, a renamed file, or any modification to the reviewed script — only an ordinary alternate invocation path (symlink, wrapper, a test harness, a future refactor that runs it via `bin/run-with-lock.sh autonomous-loop.sh`, etc.). The currently-configured production path (`daily-governance.sh` calling `"$DIR/autonomous-loop.sh"` by its real name) does not trigger it today, but that's incidental, not structural — nothing in the code prevents a future invocation from tripping this.

**Recommendation:** don't authenticate the lock holder by matching a hardcoded/derived name against `ps` output. Either drop the "look like us" check and accept bug②'s cost (script has other 60-minute staleness backstops), or write a unique per-invocation token into the lock (e.g. a random nonce alongside the pid) that only that exact process instance could have written, and compare tokens instead of process identity via `ps`.

## Checked, confirmed clean (with reproduction)

1. **`set -e` + `lock_holder_alive "$oldpid"; local hv=$?`** (line ~54 of the frozen snapshot): naive reasoning says a non-zero return here should kill the whole script under `set -e` before `local hv=$?` runs. I verified this is exactly what happens for a *bare* function call (`f; local hv=$?` under `set -euo pipefail` in a standalone repro — script died silently, exit 1, "reached inside g" never printed). But `take_lock` is always invoked as `take_lock || { ...; }` (line 127), and bash's documented "errexit ignored in this context" propagates transitively into the entire function-call tree, including nested calls like `lock_holder_alive`. Verified directly: the identical `f; local hv=$?` pattern, when the outer function is called via `g || {...}` instead of bare `g`, correctly prints `reached inside g, hv=1` and continues. **Safe as shipped**, but fragile — it depends entirely on `take_lock` always being called via `||`. A future edit calling `take_lock` as a bare statement would silently reintroduce a crash-on-legitimate-takeover bug. Worth a one-line comment noting this invariant; not itself an action item.

2. **`.steal` recursive TOCTOU** (the `rm -rf "$steal"; mkdir "$steal"` staleness-recovery, patch lines ~278-281): structurally the same anti-pattern as bug① (check staleness, then unconditionally rm+mkdir without re-verifying), so I suspected a second-order version of the same double-open bug when `.steal` itself gets orphaned (crash mid-takeover). Built a probe with a pre-orphaned, already-stale `.steal` dir (simulating exactly that crash) and ran 15 rounds × 8 concurrent processes against it: **0/15 doubled**. Reasoned through why: even if two processes both believe they hold `.steal`, the actual exclusivity is enforced one layer down by `mv "$LOCKDIR" "$dead"` — `mv` on the same source path can only succeed for one caller; the loser's `mv` fails (source gone) and it backs off cleanly (`接管失敗(鎖剛被釋放)`). The `.steal` mutex is real defense-in-depth but not the sole correctness guarantee; the `mv` atomicity is. Not filing as a finding — tested adversarially, didn't reproduce.

3. **`release_lock`'s pid-match judgment** (patch lines ~343-347): pid file missing, dir missing, or unreadable all correctly fall through to "don't delete" (`|| echo ''` fallback makes the comparison fail-safe in all three cases) — verified by code trace, consistent with the deliberately conservative direction used elsewhere in this diff. I tried to construct an independent TOCTOU (pid overwritten between the `cat` check and the `rm -rf`) by injecting a delay inside a scratch copy of `release_lock`, but this doesn't expose a new, independent window: `release_lock` only runs from the *same still-alive* process's own exit trap, so during that gap the process's own pid is still genuinely alive and still correctly identifies as "us" to any other checker. The only way this check-then-act gap becomes exploitable is if it's compounded with Finding 1 (something else has already illegitimately stolen the lock via the identity false-negative) — it isn't an independent vulnerability. Read/reasoned + partial experiment; not filing separately.

4. **Identity check false positive** (any unrelated process whose full command line happens to contain the substring `autonomous-loop`, e.g. a script literally named `check-autonomous-loop-status.sh`, or the author's own test helper `fake-autonomous-loop.sh`): confirmed the substring match is this loose —
   ```
   cmd=[bash /tmp/.../check-autonomous-loop-status.sh]
   MATCH -> lock_holder_alive would return 0 (treated as self)
   ```
   This only matters in practice if that pid also happens to be the one recorded in a stale lock file (requires pid-recycling coincidence — narrow). And the consequence is the *safe* direction (extra yield, not a steal), consistent with "問不出來就當成活著" being the stated conservative bias — except this case isn't "問不出來", it's "問到了但判斷過寬," so I'd call the risk real but low-severity (availability only, not correctness). Not filing as a standalone finding given Finding 1 already covers the dangerous direction of this same mechanism.

5. **Bug①②③ are real, and the tests for them are not false-green** — verified independently by extracting the *old* (pre-patch) code straight from the patch's `-` lines and running it against the same scenarios the new tests construct:
   - Bug②(pid recycled to an unrelated alive process, old lock): old code prints `另一份 autonomous-loop 正在跑...退出` and never reaches "接管" — confirms permanent-yield bug, matching the plan doc's claim.
   - Bug③ (garbage, non-numeric pid content, 0-second-old lock): old code immediately prints `發現殘鎖...接管` — confirms the "even a brand-new lock gets stolen" bug.
   - `test_lock_takeover_is_atomic`: ran the author's actual test — passes (44s wall time across the full `-k lock` suite, 9/9 tests green).
