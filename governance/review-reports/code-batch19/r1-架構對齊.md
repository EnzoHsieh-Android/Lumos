severity: major

**F1 — trap 裝法引入了 daily-governance.sh 沒有的第二種機制（major，blocking：否）**

daily-governance.sh 對「取鎖到裝收尾之間有窗口」這個問題,既有解法是**單一 trap、裝在取鎖之前**,靠 `finalize()` 自己檢查鎖裡的 pid 是不是自己來保安全:

引句:「#  ⑤ ★清除靠 trap EXIT,而且 trap 要裝在取鎖之前★:這支用 set -u,踩到未設變數會立刻中止,」   (governance/daily-governance.sh:51)
- `governance/daily-governance.sh:157` — `trap finalize EXIT                     # ⑤ 裝在取鎖之前;finalize 自己會確認鎖是不是我的`（下一行就是 `take_lock`,全程只有這一個 trap）

autonomous-loop.sh 這批改成**兩段式**：先裝一個只認旗標變數的臨時 trap,拿到鎖後才把旗標扳成 1,等 `finalize()` 定義好幾十行之後再整個換掉:

引句:「★取鎖與收尾之間不能有裸奔的窗口★:這支有 set -e,從這裡到下面 trap finalize EXIT / 之間任何一個指令失敗都會直接中止,鎖就卡到 60 分鐘後才自癒。 / 所以先裝一個只清鎖的 trap,等 finalize 定義好再換成它」   (governance/autonomous-loop.sh:115-117)
- `governance/autonomous-loop.sh:118-128` — `LOCK_HELD=0` / `release_lock() {...}` / `trap 'if [ "$LOCK_HELD" = 1 ]; then release_lock; fi' EXIT` / `take_lock || {...}` / `LOCK_HELD=1`
- `governance/autonomous-loop.sh:201` — `trap finalize EXIT`（第二次裝,取代前面那個）

why：這是同一個問題（取鎖到收尾裝妥之間別留裸奔窗口）的兩套不同解法——一套是「單 trap + 自我認證的 finalize」,一套是「臨時 trap + 全域旗標 + trap 置換」。專案裡沒有第三支腳本用過旗標+置換這種寫法（ai-governance-research.sh、lint-watch-check.sh 根本沒有鎖/trap 機制）。改動本身有寫理由（`finalize()` 依賴 `GAP_JSON`/`LOGDIR`/`SCRATCH` 等要等到鎖拿到之後才逐步賦值的變數,搬不到取鎖之前）,而且我照著測試檔驗證過（`scripts/test_autonomous_loop.py` 裡 `test_lock_takeover_is_atomic` 20 輪 0 雙開）,邏輯是通的——所以不判 blocking。但它確實是「這個專案原本沒有的第二種做法」,建議在這段旁邊補一句對照 daily-governance.sh ⑤ 的說明（為什麼那邊能單 trap、這邊不行）,不然下一個人抄的時候會以為兩邊本來就該長一樣。

**F4 — autonomous-loop.sh 仍未套用 main() 包法（純資訊性,非本批引入,不計入 severity）**
