## f2 — major:「欄位設計」節的 std-r2 註記說「繞回 r1 的雜湊設計」,但文件自己記載的修訂史裡 r1 從頭到尾是日期制,沒有雜湊這回事

嚴重度定 major(非 blocker):不影響任何一處可執行規格(工具清單/#4/#6/合約候選都對雜湊制描述一致,見下),純粹是「為什麼設計成這樣」的歷史敘述錯誤——但這份文件的存在目的正是給下一個 session 交代「為什麼這樣設計」(CLAUDE.md:「docs/…-knowledge 是本專案『為什麼這樣設計』的唯一來源」),歷史敘述本身錯了,會讓後人誤以為雜湊制是「回頭採用一個已經驗證過的舊方案」而非「全新方案、還沒有先例驗證過」——這個誤解會降低後人對「這是本案第一次用雜湊」這件事該有的謹慎。

## f3 — blocker:「回滾路徑」節給的 stamp 範例仍是兩段式,是全文唯一具體示範「批次寫入長什麼樣」的地方,卻沒跟上三段式格式

**spec 段落**:「主案」→「回滾路徑」節(行 275-283)。

## f4 — major:新增 `restamp` 子命令會不會觸發跟 `revert` 一樣的「三道登記守衛」,#11 完全沒交代,而且實際只有三分之一是真的機械守衛

**spec 段落**:工具清單 #7(行 404)與 #11(行 408)。

**引句:「新指令觸發三道登記守衛(help/索引/六份文件指令數 61→62)」**(行 404,#7 那格)

問題:#7(`about-code revert`)落地時明確記了一筆「新指令觸發三道登記守衛」;#11(`about-code restamp`)是本輪(std-r2)新加的另一個子命令,同樣掛在 `about-code` 底下(行 408:「argparse 二層子命令同 `revert`」),但那格完全沒提到會不會再踩到同一批守衛。實際查三道守衛的機械行為(`scripts/test_lumos.py`),三道待遇並不一樣:

1. **「六份文件指令數 61→62」**(`t_docs_command_count`,`scripts/test_lumos.py:16169`,真值取自 `lumos --help` 頂層 `{…}` 選項)——`about-code` 這個**頂層**指令在 #7 落地時已經算過一次(實測現在 `--help` 頂層確實是 62 個選項,跟 #7 宣稱的 61→62 吻合)。`restamp` 是掛在 `about-code` 底下的**第二層**子指令,不會再讓頂層計數往上跳,這道守衛**不會**再被 restamp 觸發——#7 那格的說法對 #11 不成立。
2. **「索引」**(`t_command_index_complete` 的「★二層子指令也都有歸位★」檢查,`scripts/test_lumos.py:4298`)——這個檢查**只**掃一個寫死的 parent tuple:`("loop", "canary", "guard", "testmap", "anchor", "cochange", "code-loop", "rel-cascade")`。`about-code` **根本不在名單裡**。也就是說 `revert` 現在會出現在 `skills/lumos-project-notes/commands/02-動手前算波及.md`(已核對確實有一行)是人工補上去的,不是被這道測試機械擋出來的——如果實作 `restamp` 時沒有人手動補文件,**沒有任何測試會紅**。
3. **「help」**(`t_every_subcommand_has_when`,`scripts/test_lumos.py:4308`)——這條**不看**固定名單,對每個頂層指令的每個子指令都要求 `--help` 裡有「什麼時候用:」,`restamp` 逃不掉這條(已核對 `revert` 現在確實有,`lumos about-code revert --help` 印出「什麼時候用:……」)。

所以「新指令觸發三道登記守衛」這句話對 `restamp` 只有三分之一是真的機械守衛(help),六份文件那道根本不會再跳,索引那道其實是紀律不是機械。#11 那格什麼都沒講,容易讓實作者誤以為跟 #7 一樣有「三道守衛自動接住」,結果最可能被漏掉的正是「索引」——沒有測試會提醒。

證據:`scripts/test_lumos.py:4298`(parent tuple 不含 about-code)、`scripts/test_lumos.py:16169-16200`(頂層計數口徑)、`scripts/lumos:15082-15085`(`about-code`/`revert` 的 argparse 註冊,確認 `revert` 是 `about-code` 底下第二層)、`skills/lumos-project-notes/commands/02-動手前算波及.md:10`(revert 的索引條目)。

## 實務隱患鏡頭(逐類過)

- **知識同步(本鏡頭主軸)**:f1/f2/f3/f5/f6/f7。核心風險是「stamp 格式在這一輪換了骨架設計(兩段日期制 → 三段雜湊制),但文件裡描述『格式長什麼樣』的地方不只一處,而只有部分地方真的跟著換」——「欄位設計」節換了,「過期守衛」節末段換了,但「回滾路徑」節(f3)跟「過期守衛」節裡更早的 r1/r2 段落(f1)沒有跟著動或至少沒被標記作廢。這是典型的「改了被點名的段落,沒有全文追殺同一個欄位的所有出現處」——文件自己在 r2 審計修正紀錄裡就寫過這個教訓(「r1 教訓:只改被點名的段落、沒全文 grep 分身」),這輪同一個病換了個位置(stamp 格式)又犯一次。
- **併發**:沒有新增結構性風險。std-r2 拿掉了 git subprocess 與行程內快取,反而減少了原本 std-r1 方案裡潛在的快取歸屬/競態疑慮(上一輪 r2-s3 f3 抓到的「`_GIT_DATES_CACHE` 快取層級不明」問題,隨 std-r2 整段拿掉 git 一併消失,不需要再處理)。唯一的邊界情況是 `about-code restamp --expired` 批次執行期間,若另一個 session 同時在改同一篇筆記正文,restamp 讀到的雜湊只反映「讀檔那一刻」的內容——但這跟 `lumos set`/`append` 等既有寫入操作面對的併發假設(單人序列操作、無檔案鎖)同量級,不是本案獨有的新風險。
- **效能**:`impact` 熱路徑那半有具體實測數字(懶觸發 + 幾次讀檔 + 毫秒級,行 329),git 退場後原本 std-r1 被打的「沒算 git log 0.2s」那個洞也一起消失,乾淨。`run_doctor`(#6)那半沒有給出量測數字——83 篇要逐篇 `note_body_hash`(讀檔 + sha256),spec 沒附上像 `git_last_change_dates` 那樣的實測時間(0.22s/0.75s 這類)。sha256 計算本身極快,估計不構成問題,但這是 spec 裡少數沒有拿數字說話的角落,跟這份文件其他地方「靠實測數字說服人」的紀律不一致,列為觀察項、非 blocker。
- **資源**:淨減少——不再需要 spawn git 子行程、不用處理 quotepath/中文路徑跳脫、不用 try/except 包 subprocess 例外。`hashlib.sha256` 是標準庫,符合零依賴家規,沒有新增外部依賴。無風險。
- **回滾路徑**:`about-code revert` 本身健全(f7 只是覆蓋率建議,非缺陷)。`restamp` 是冪等操作(重算雜湊寫回),不需要另一個「復原 restamp」的機制。真正的回滾/落地風險已經在 f3 詳列——如果 apply(#8 未完成的那半)照抄「回滾路徑」節那個過時的兩段式範例寫入,會讓新資料落地當天就被判假過期,這是本輪最需要在實作前釐清的一點。
