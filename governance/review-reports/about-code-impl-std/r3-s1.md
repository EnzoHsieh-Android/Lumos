## 專項驗證:body-hash 這條規則沿著程式碼實際路徑走一遍

**結論:核心 body-preservation 主張成立,但有兩個делта 沒接上——frontmatter 自己的 summary 先過期、
restamp 沒有真的解除 revert 風險——都可能讓「about_code 不會自我過期」「回滾不會誤傷已修正節點」這兩句
承諾在特定路徑上落空。細節見 f1/f2。**

### 逐項驗證

1. **`split_frontmatter`(`scripts/lumos:101-108`)本體**:
   ```python
   def split_frontmatter(text):
       if not text.startswith("---"):
           return None, text
       lines = text.split("\n")
       for i in range(1, len(lines)):
           if lines[i].strip() == "---":
               return lines[1:i], "\n".join(lines[i + 1:])
       return None, text
   ```
   - **frontmatter 關閉線後緊接空行**:`body = "\n".join(lines[i+1:])`,而 `text = "\n".join(lines)` 恆成立
     (split/join 對同一分隔字元互為逆運算)。所以 `lines[i+1:]` 重新 join 出來的字串,**精確等於**原始文字裡
     從關閉線後一個字元開始的那段子字串,一個 byte 都不會變形——那個緊接的空行只是「正文的第一行是空字串」,
     結構穩定,不是抓錯位置。✅ 已讀,無 finding。
   - **CRLF**:`text.split("\n")` 只切 `\n`,CRLF 檔的 `\r` 會黏在每行尾端一起被切出來,再用 `"\n".join()`
     接回去時原樣重建——同一份未變動的 CRLF 檔重複算,雜湊穩定(不是本案新洞)。但這條路徑背後有另一個
     問題,見下面「f4」:寫回側(`load_raw_for_edit`)對 CRLF 檔是直接拒寫,不是本函式的問題但會拖累
     restamp 的可執行性。
   - **無 frontmatter 檔**:`text.startswith("---")` 為 False → 回 `(None, text)`,整份原始文字(含任何殘留的
     `---` 標記本身)被當成「正文」去算雜湊。理論上不穩定(結構被破壞的檔案,任何原本屬於 frontmatter 的
     字元變動都會牽動雜湊),但 `note_body_hash` 只會被套在「已經有 `about_code_stamp` 欄位」的節點上——
     這種節點在被 `env.notes` 收錄時 frontmatter 必然可解析。真正會踩進 `(None, text)` 分支的唯一路徑是
     「同一次執行期間檔案被外部改到失去收尾 `---`」,屬既有 accepted 的 TOCTOU 風險(單機 CLI、不上鎖),
     不是本案新增的洞。✅ 無新增 finding,但值得在 #6/#4 實作註解裡點名這是「防呆分支」而非「正常路徑」。
   - **BOM 檔**:見下面 **f3**——這條不成立,是本審最大的洞。

2. **「`lumos set`/`append` 只動 frontmatter,不會過期」**(spec 327 行)追code:
   - `cmd_set`(`scripts/lumos:7514`)/`cmd_append`(`7561`)/`cmd_remove`(`7576`)都經
     `load_raw_for_edit`(`7454`)取得 `(lines, 1, fm_end)`,重寫時一律
     `new_lines = lines[:1] + new_fm + lines[e:]`——`lines[e:]`(從收尾 `---` 起到檔尾)是**原始陣列的未動切片**,
     不是重新產生的字串。`atomic_write_verify`(`7488`)裡 `text = "\n".join(new_lines)` 對這段是逆運算,
     於是寫回後 `---` 起到檔尾的每一個 byte(含結尾換行慣例)跟寫入前逐 byte 相同。
   - 結論:**這句話對現有 `edit_fm_*`/寫回路徑成立**,#4 測試候選⑬(`lumos set about_code_stamp` 改
     frontmatter 後仍不過期)立得住。✅ 已核實成立。
   - **但這個成立有一個沒寫進 spec 的前提**:只在 `load_raw_for_edit` 肯放行的檔案上成立——LF、無 BOM、
     有收尾 `---`。BOM/CRLF 檔案连 `cmd_set` 都進不去(直接 raise),見 f3/f4。

3. **restamp 與 revert 對三段式 stamp 第一段的比對是否一致**:**不一致,見 f2(blocker)**。

### f1 — blocker:frontmatter 自己的 summary 對「過期判準是什麼」新舊打架,而且是本節點被 `--brief` 讀到的那半

**spec 段落**:frontmatter `summary:` 區塊第 3 行 KEY(標「★r2 設計層改動★」)。

**引句:「過期判準改 git 最後改動日期(updated 欄 33% 落後)」**

**問題**:同一個 `summary:` 區塊往下一行(第 4 行 KEY)寫的是
`過期守衛:r1「併入 Check S、記日期」→ r3 另開迴圈 → ★std-r2 改記正文雜湊...★`——這才是正文裡真正落地的
最終設計(std-r2 段,`git 完全退場`)。第 3 行的「過期判準改 git 最後改動日期」是 r2 當時的中間態,後來被
std-r1(加同日計數/dirty set)再被 std-r2(整段換成正文雜湊)兩輪推翻,**但第 3 行 KEY 從沒更新**,跟緊接在
它下面的第 4 行 KEY 直接自相矛盾——同一個 frontmatter summary 區塊內部,相鄰兩行對「現在的過期判準是什麼」
給出兩個不同答案。

這正是本專案 CLAUDE.md 明文點名的風險場景(「單篇筆記內部可能新舊打架,doctor 驗不出——摘要裡有日期的
KEY 行比正文段落新,衝突又影響決策就去 code 裁」),而且命中的是**最容易被相信的那個讀取路徑**:
`lumos context <節點> --brief` 這種快速查詢只讀 header/summary、不讀全文,任何用 `--brief` 查這個節點的人
(包含未來實作這份 spec 的 agent 自己)看到的三行 KEY 裡就有一行在說「過期判準是 git 日期」——跟正文的
`#4`/`#6`/合約候選第 3 條講的「過期 = 正文雜湊 ≠ stamp 第三段」直接衝突。若照這行 KEY 去實作,或只憑
`--brief` 做決策,會做出跟 std-r2 完全不同(而且已被 std-r2 自己判定「表達不了同日序列」而放棄)的東西。

**處置建議**:第 3 行 KEY 的「過期判準改 git 最後改動日期」要嘛整句刪掉(已被第 4 行取代,留一行就夠),
要嘛在後面加註「(此判準已被 std-r2 換成正文雜湊,見下一行)」——不能讓兩行 KEY 對同一件事各說各話。

### f2 — blocker:restamp「重算第三段」與回滾路徑/合約候選#4 對 stamp 第一段的承諾不一致

**spec 段落**:過期守衛節 std-r2 段「恢復動作成立」小節;回滾路徑節(r2 改寫);合約候選第 4 條。

**引句:「lumos about-code restamp <節點>」(或 `--expired` 批次)重算第三段」**

**問題**:
- 回滾路徑節明寫的安全保證是:「人工修正過的節點 stamp 第一段會變成 `claude/...`,不在 batch 範圍,
  不會被誤撤」——這句話被拉進合約候選第 4 條:「批次回滾只動 stamp 第一段 = batch-<日期> 的節點——
  人工修正過的不被誤撤」,列為本案要護住的不變量。
- 但 std-r2 唯一定義出來、而且是 ext-f1 明文要求「恢復動作必須真的能解除過期」才存在的官方復原工具
  `about-code restamp`,通篇(過期守衛節、工具清單 #11 兩處)都只說「重算第三段」——三段式
  `<誰標>/<日期>/<正文 sha256 前 12>` 的第一段(誰標)、第二段(日期)在整份 spec 裡**沒有任何一句話**
  說 restamp 會去動它們。
- 照字面實作:一篇 `批次寫入` 的節點(第一段固定 `batch-2026-08-23`)之後正文改了、過期了,使用者照 doctor
  的建議跑 `lumos about-code restamp <節點>` 解除過期——第三段換成新雜湊,**第一段仍然是 `batch-2026-08-23`
  不變**。之後如果因為某個理由要整批撤銷那天的批次(`about-code revert --batch 2026-08-23`),這個「已經
  被合法重標過、內容跟正文對得上」的節點,依然滿足 revert 的篩選條件(第一段精確等於 `batch-<日期>`),
  會被一起清空——**合約候選第 4 條承諾的「人工修正過的不被誤撤」在「用官方工具 restamp 修正」這條路徑上
  不成立**,只有走「人工手改 `lumos set about_code_stamp` 打一個全新第一段」才躲得掉,而 spec 從未說
  restamp 跟手改 `set` 是等價、可互換的兩條路。
- 連帶的第二個缺口:restamp 對「從未有 `about_code_stamp`(增量寫入、全新節點第一次填 about_code)」這種
  情況行為未定義——「重算第三段」的語意預設第一、二段已經存在;spec 在「存量與增量」節明確說增量節點
  由人/Claude 逐篇填,卻沒說這些節點的 stamp 第一段該寫什麼、由誰寫、restamp 首次呼叫時怎麼決定。

**證據**:`/tmp/about-code-impl-std-r3.md` 279-283 行(回滾路徑)、326-335 行(過期守衛 std-r2 恢復動作)、
408 行(工具清單 #11)、491 行(合約候選第 4 條)——四處對「restamp 動不動第一段」互相沒有一句話銜接。

**處置建議**:要嘛明寫 restamp 也會把第一段換成 `claude/<今天>`(那麼「重算第三段」這個措辭本身要改,
且要跟「批次遷移只補第三段」這個特例分開講清楚差在哪);要嘛明寫「restamp 刻意不動第一段,因為第一段記的
是『誰寫的 about_code 清單』而不是『誰確認過新鮮度』,revert 就是要連同被 restamp 過的批次節點一起清」——
兩種語意都說得通,但現在誰都沒選,合約候選第 4 條的文字承諾跟 restamp 的唯一具體定義正面衝突。

### f3 — major:`note_body_hash` 讀檔編碼未指定,BOM 檔會讓「about_code 不會自我過期」的宣稱失效

**spec 段落**:過期守衛節 std-r2 段,stamp 加第三段那條。

**引句:「新 helper `note_body_hash(vault, rel)`(讀檔→split→hash」**

**問題**:本 repo 讀 vault 筆記的既有慣例是全部用 `read_text(encoding="utf-8-sig")`——`load_vault`
(`scripts/lumos:201`)那行的註解明寫理由:「-sig: BOM 檔也偵測得到 frontmatter」,其後全檔至少 30 幾處
讀 vault 檔案都沿用同一寫法(`grep -n 'utf-8-sig' scripts/lumos` 命中 20+ 處)。`load_raw_for_edit`
(`scripts/lumos:7454-7462`)甚至對 BOM 開頭直接 `raise ValueError`,說明 BOM 檔在這個 vault 是真實會發生、
需要專門處理的情境,不是假想邊界。

但 std-r2 對 `note_body_hash(vault, rel)` 的規格只寫「讀檔→split→hash」,函式簽章是 `(vault, rel)`(不是
複用 `env.notes` 裡已經用 `utf-8-sig` 解過碼的文字),**沒有一個字指定用什麼編碼開檔**。如果實作者順手用
預設 `read_text()`(等於 `utf-8`,不吃掉 BOM),BOM 檔開頭殘留的 `﻿` 字元會讓
`text.startswith("---")`(`split_frontmatter`,`scripts/lumos:102`)判為 False,直接掉進「無 frontmatter」
分支——`split_frontmatter(text)[1]` 這時等於**整份原始檔案**(frontmatter 區塊本身也被算進「正文」)。
後果是:`lumos set about_code_stamp` 改 frontmatter(哪怕只是重標本身)也會改變這份「正文」的雜湊,
直接打臉 std-r2 自己在同一段落緊接著講的那句話——「about_code 自己就在 frontmatter 裡,重標不會自我過期」
在 BOM 檔上不成立,會變成每次重標都讓自己再次過期(或者反過來,任何跟 about_code 無關的欄位編輯都會讓它
無端過期)。

**驗證**:實測本 repo `docs/` 底下 392 篇筆記目前沒有 BOM 檔(`head -c3` 逐篇比對 `\xef\xbb\xbf`,零命中),
風險目前潛伏未爆;但 codebase 既有的雙重防禦(`load_vault` 的 `-sig`、`load_raw_for_edit` 的顯式拒寫)證明
維護者已經真的遇過或防過這個情境,不是我在無中生有。

**處置建議**:`note_body_hash` 規格明寫 `read_text(encoding="utf-8-sig")`,對齊既有慣例;測試候選裡加一條
BOM 檔的 hash 穩定性測試(至少覆蓋「BOM 檔 + frontmatter 编辑不觸發過期」這個既有承諾)。

### f4 — minor:BOM/CRLF 檔案上,官方復原工具 restamp 的寫回步驟會直接失敗

**spec 段落**:過期守衛節 std-r2 段「恢復動作成立」小節(與 f3 相關聯的下游後果)。

**引句:「這次重標真的會讓它不再過期(ext-f1 要求的可操作性)」**

**問題**:即使 f3 修正、`note_body_hash` 正確用 `utf-8-sig` 讀出雜湊,doctor 依然可能把一篇 BOM 或 CRLF
筆記標成「過期」(例如遷移期間混進了這類檔案,或外部工具存檔時帶了 BOM)。使用者照建議跑
`lumos about-code restamp <節點>` 想解除過期,寫回那一步如果是走 `cmd_set`(`scripts/lumos:7514`)寫
`about_code_stamp`,會先經過 `load_raw_for_edit`(`7454`)——那裡對 BOM 開頭與含 `\r\n` 的檔案是**直接
`raise ValueError`**(訊息明講「工具不寫這種檔」「工具不會偷偷幫你改行尾」),不是靜默失敗但也不是
「restamp 一行就好」那麼輕鬆——使用者拿到的是一次會中斷的 CLI 呼叫,得先手動 `dos2unix`/去 BOM 才能重標。
這在這種邊界情況下,跟 ext-f1「恢復動作必須真的能解除過期」的可操作性承諾有落差。

**評級**:目前 vault 沒有 BOM/CRLF 檔(見 f3 的實測),失敗模式是loud、有明確錯誤訊息指路(不是資料損毀),
定 minor,建議在 #11/restamp 的規格裡補一句「BOM/CRLF 檔案會沿用 `load_raw_for_edit` 既有錯誤訊息,先手動
正規化再重標」,把這個已知限制講清楚而不是留白。

## 實務隱患鏡頭(逐類)

- **併發**:無新增風險類別。`atomic_write_verify`(`scripts/lumos:7488`)沿用既有 tmp→`os.replace` 原子寫入,
  讀-改-寫視窗內的 last-write-wins 是既有 accepted 模型(單機 CLI、不上鎖,`_write_lf` 註解自承)。restamp
  的「讀正文算雜湊→`cmd_set` 寫入」中間有極短窗口若被另一個 process 同時改動正文,寫回的雜湊會對應到「讀取
  當下」而非「寫入當下」的正文——這跟既有任何 read-modify-write 操作同一類風險,不是本案新增的洞。
- **效能**:懶觸發(先掃候選有無 about 命中才讀檔算 hash)是合理節流,`hashlib.sha256` 對單篇 markdown
  (數 KB~數十 KB)是毫秒級、無子行程,跟 spec 自己的預期(「幾次讀檔、毫秒級」)一致,沒有牴觸。
- **資源**:讀入的是單篇筆記全文,記憶體/CPU 開銷可忽略;doctor 對「所有有 stamp 的節點」逐篇算一次,83 篇
  規模下也是次秒級,無風險。
- **回滾路徑**:★本輪主要洞所在★——見 f2。restamp 與 revert 對 stamp 第一段的處理沒有對齊,「先合法
  restamp、後執行批次 revert」這個序列下,回滾路徑自己宣稱的安全保證不成立。
