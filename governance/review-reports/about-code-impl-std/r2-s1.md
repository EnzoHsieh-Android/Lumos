## 專項驗證:「同日計數」在 `git log --name-only --format=@%cs` 上數得出來嗎

**結論:數得出來,結構上沒有阻礙,但這條規則實際攔到的情況比 spec 自己講的更寬——見下面 f2。**

實測結構(`git -c core.quotepath=false log --name-only --format=@%cs -- <path>`):輸出是「`@YYYY-MM-DD` 開一個
commit 區塊 → 空行 → 該 commit 改到的檔案清單(zero or more 行)」重複排列,新→舊。例如對
`scripts/lumos` 跑這條指令,前 7 個區塊都是 `@2026-08-23` 各帶一行 `scripts/lumos`(7 個獨立 commit),
之後才轉到 `@2026-08-22`。既有 `git_last_change_dates`(`scripts/lumos:13561-13598`)已經在逐行掃這個結構,
只是只認「第一次看到某檔」(`if rel not in out`)。要擴充成「最後改動日當天有幾個 commit」,邏輯上就是:
第一次看到某檔時記下它的日期 `d`,之後只要同一個檔案又出現在日期仍是 `d` 的區塊裡就累加計數,一旦轉到比 `d`
更早的日期就對這個檔案停止累加——這是對同一份輸出的**單一線性掃描**,不需要第二次呼叫 git、不需要排序,是
真的「順手數」。

用這個演算法對本 repo 實測(`docs/lumos-toolchain-knowledge/Projects/固定席扇出降權_計劃.md`,即這份 spec
自己所在的筆記):2026-08-23 當天有 **15** 個獨立 commit 動過這個檔案,同天沒有再更早的重複——計數邏輯給出
的答案跟直接數 commit log 的答案一致。結構上站得住。

問題不在「數不數得出來」,在「數出來的東西是不是規則真正想防的東西」——見下面 f2:regex 用「同日 ≥2 commit」
當「stamp 之後又改過」的代理指標,但這個代理指標分不出「stamp 之前的兩次改」跟「stamp 之後的一次改」,而且
**觸發門檻比 spec 自己描述的窄(「先改兩次再標」)還要寬**——已用真實已上線資料證實。

## 逐條 finding

### f1 — blocker:排序鍵 `not about_hit` 跟「只在 True 出鍵」互相打架,字面實作會 KeyError 在幾乎每一次 `impact --ranked` 呼叫上

**spec 段落**:「#4 impact 讀 about_code」判定與排序兩個子彈點。

**引句:「★只有 True 才出現這個鍵★(std-r1 s2f2 blocker:寫 `about_hit: False` 會讓「knob=0 逐 byte 相同」必敗)。」**

**引句:「`pins = [...]`(`:14226`)之後加一道 stable sort,鍵 = `(kind != "incident", not about_hit)`——」**

問題:這兩條規則是同一段落裡緊接著的兩個子彈點,但彼此不相容。「只有 True 才出現這個鍵」意思是:沒命中
about_code 的候選項(這是**絕大多數**候選——任何沒有 about_code 欄、欄裡不含目標檔、過期、或撞巨檔門檻的
候選)的 results dict 裡根本沒有 `about_hit` 這個 key。而排序鍵 `not about_hit` 如果字面實作成 `r["about_hit"]`
(直接下標,而不是 `r.get("about_hit")`),對任何沒有這個 key 的 dict 會直接 `KeyError`,讓整個
`pins.sort(...)` 呼叫拋例外——不是排序結果錯,是**整個 `impact --ranked` 呼叫當場崩潰**。

這不是我猜的極端邊界:spec 自己列的 12 條測試裡,②③④⑤ 四條(「有欄不含」「無欄」「過期(三種)」「巨檔≥8」)
描述的場景是「JSON results 與 knob=0 時逐 byte 相同」——這些場景下,`pins` 列表裡唯一會有 `about_hit`
鍵的項目數是 **0**(因為测试刻意設計成沒有命中發生),但 `pins` 列表本身不是空的(既有的 `t_impact_ranked`
基礎 fixture `SvcCore.md` 本來就因為 direct+合約而 pinned,不管 about 命不命中都在 `pins` 裡)。也就是說,
knob=1(預設值)時,②③④⑤ 這四個測試場景一啟動排序步驟就會踩到「pins 列表非空、但沒有任何一項有
`about_hit` 鍵」的組合——如果字面實作用 `r["about_hit"]`,這四條測試會**當場拋例外**,而不是像 spec 預期的
「輸出逐 byte 相同」。

對照組(反面證據,證明這不是我對「字面」的過度苛求):同一份 repo 裡至少兩處已經對「不是所有項目都有這個
key」的欄位用了防禦性 `.get()`——
- `scripts/hooks/claude/impact-hook.py:344-348`(spec 自己在 #9 引用的同一段):`x.get("about_hit")` 判斷
  要不要標 `★關於★`,正確處理了 key 缺席。
- `scripts/lumos:14283`:`free.sort(key=lambda r: (-r["score"], r.get("hop", 0), r["node"]))`——`hop` 同樣
  只在 indirect 分支才會被寫入 dict,既有排序 key 用 `r.get("hop", 0)` 不用 `r["hop"]`。

也就是說「排序鍵裡遇到選擇性欄位要用 `.get()`」在這個 codebase 已經是既定寫法,#9 那段甚至自己也遵守了,
但 #4 的排序鍵這一句偏偏沒寫清楚要用 `.get()`——三輪審查(impl-r1/std-r1)反覆盯著「about_hit 什麼時候該不該
出現」這件事本身(這正是 s2f2 blocker 的內容),卻沒有人往下多問一步:「這個鍵的消費端(排序鍵運算式)
準備好接受它缺席了嗎?」判 blocker,因為字面實作會讓功能在熱路徑(PreToolUse hook)上對絕大多數真實輸入
直接崩潰,而不是「排序錯了」這種可以事後修正的退化。

### f2 — major(合約候選第 3 條):「同日 ≥2 commit」實際觸發門檻比 spec 自己講的窄,用本 repo 已上線資料證實已經誤判

**spec 段落**:「過期守衛」節末 std-r1 改寫段;合約候選第 3 條。

**引句:「★代價(誠實)★:標記當天若先改兩次再標,會被誤判過期——方向是「不加分」,安全;doctor 會列出來,人看一眼 `lumos set about_code_stamp` 就好。」**

問題:spec 把這條規則的誤判場景描述成「先改兩次再標」(當天至少 2 次內容編輯,再加 1 次 stamp commit,
共 ≥3 個 commit)。但規則本身寫的是「`git_date == stamp_date` 且 `n_same_day ≥ 2`」——這個門檻**不需要兩次
內容編輯**,只要「當天有 1 次內容編輯 + stamp 動作本身也是一個 commit」就達到 `n_same_day == 2`,因為
stamp 動作(寫 `about_code`/`about_code_stamp` 進 frontmatter)本身也要 commit 才會被 git 看見,而這正是
「當天編輯完馬上批次標註」這個**最正常、最預期的操作順序**,不是邊界情況。

用本 repo 已經寫入的 83 篇存量資料實測(`grep -rl "about_code_stamp:" docs/lumos-toolchain-knowledge` 全掃,
用批次 `git log --name-only --format=@%cs` 對每篇算 `n_same_day`):**83 篇裡已經有 2 篇在規則生效當下就會
被判定「可能過期」**,即使它們的 stamp 準確反映最新內容:

```
docs/lumos-toolchain-knowledge/Projects/檢索優化_計劃.md   stamp=2026-08-23  git=2026-08-23  n=2
docs/lumos-toolchain-knowledge/Systems/lumos-cli-read.md    stamp=2026-08-23  git=2026-08-23  n=2
```

追這兩篇當天的實際 commit(`git log --format='%H %cs %s' -- <檔>`):

```
檢索優化_計劃.md:
  dbd104f 2026-08-23 feat(about-code): 存量 83 篇雙評審落地——…寫入 frontmatter   ← stamp commit
  4f6c733 2026-08-23 feat(eval): 評測尺四修…                                    ← 不相關的內容編輯,早於 stamp

lumos-cli-read.md:
  dbd104f 2026-08-23 feat(about-code): 存量 83 篇雙評審落地——…寫入 frontmatter   ← stamp commit
  6b5c3bd 2026-08-23 feat(impact): git_last_change_dates…                       ← 不相關的內容編輯,早於 stamp
```

兩篇都是「當天先被別的改動碰過一次,晚一點批次 stamp」——正是「單次編輯 + 隨後補標」的標準流程,不是
「先改兩次」。這代表這條規則一旦上線,#6 的過期迴圈第一天跑起來就會列出這兩篇「可能過期」,即使它們的
資料完全準確,而規則觸發的真正條件(≥1 次同日先行編輯 + 之後的 stamp commit)在文件裡從頭到尾沒有被
準確描述過——三處提到這個代價的地方(過期守衛節本文、#4 詳規、合約候選第 3 條)口徑一致地都寫「改兩次」,
沒有一處寫「改一次也算」。

方向仍然是安全的(誤判方向=不信任已標記的 about_code,不會導致漏掉真正的過期),所以不判 blocker;但這條
「代價」被系統性低估了頻率,而且已經不是理論推演——上線當天就會在既有 83 篇存量資料上冒出至少 2 條假警訊,
值得在合約候選第 3 條和過期守衛節把觸發條件改寫準確(「同日 ≥2 commit」涵蓋「編輯一次+補標一次」,不是
「編輯兩次+補標一次」),否則接手 #6 的人會低估 doctor 噪音量。

### f3 — blocker:`git_dirty_notes`(`git status --porcelain`)沒帶 `-c core.quotepath=false`,對中文檔名靜默失效

**spec 段落**:「過期守衛」節末 std-r1 改寫段;工具清單第 5 列。

**引句:「再一次批次 `git status --porcelain -- <vault>` 抓沒 commit 的:`git_dirty_notes(repo_root, vault)` 回 set,同款行程內快取。」**

問題:同一節緊接在旁邊的 `git_last_change_dates`(既有、已落地)明文帶 `-c core.quotepath=false`,docstring
自己交代理由:「vault 檔名幾乎全中文,預設輸出是八進位跳脫…沒這旗標整張表是空的,而且不報錯」,並且標記為
「翻紅釘實證」——這是這個 repo 這一版才剛學到、代價不小的教訓。但 std-r1 新增的 `git status --porcelain`
呼叫完全沒有提到這面旗標,而它遇到的是**一模一樣的問題**。實測驗證(對本 repo 一個真實中文檔名節點做
uncommitted 修改):

```
$ git status --porcelain -- docs/lumos-toolchain-knowledge
 M "docs/lumos-toolchain-knowledge/Projects/\345\233\272\345\256\232\345\270\255…_\350\250\210\345\212\203.md"

$ git -c core.quotepath=false status --porcelain -- docs/lumos-toolchain-knowledge
 M docs/lumos-toolchain-knowledge/Projects/固定席扇出降權_計劃.md
```

不帶旗標時,輸出把中文路徑整段做八進位跳脫並加上外層雙引號——這個字串**不會**等於程式碼裡拿來比對的
`rel`(候選節點的 vault 相對路徑,是普通 unicode 字串)。既然 spec 自己形容「vault 檔名幾乎全中文」,這代表
`git_dirty_notes` 回傳的 dirty set,一旦照 spec 字面(不加旗標)實作,**幾乎永遠是空集合**(因為集合裡的
「鍵」是一段誰都比對不上的跳脫字串)——`rel 在 dirty set` 這個過期判準因此對幾乎所有真實節點靜默失效,
「dirty 未 commit 視同過期」這個 std-r1 想補的偽陰性缺口,實際上沒有被補上。這正是 std-r1 這一輪自己反覆
強調的病(「s1f1 blocker + ext-e2…新 helper 擴充同日計數+dirty set」的整個立案理由就是要堵掉偽陰性),
現在同一輪裡自己又開了一個同類型的偽陰性缺口。

附帶一點(同一根因、同一風險等級但影響範圍較小):工具清單第 5 列給的參考指令字串「`git log --name-only
--format=@%cs -c core.quotepath=false`」把 `-c` 放在 `log` 子命令的旗標**之後**——這個順序本身會執行失敗
(`-c` 是 git 的全域選項,必須出現在子命令 `log` 之前),實測:

```
$ git log --name-only --format=@%cs -c core.quotepath=false -- scripts/lumos
fatal: bad revision 'core.quotepath=false'
```

實際落地的程式碼(`scripts/lumos:13579-13581`)順序是對的(`git -C <root> -c core.quotepath=false log ...`),
所以這只是文件裡的引用寫錯順序、不是程式碼本身的 bug,但既然 `git status --porcelain` 那句同樣是照著這種
「文件敘述先於實作」的方式寫在同一節,兩處放在一起看,說明這個旗標本身在這份文件裡沒有被當作「每次呼叫
git 子行程都要顯式檢查一次」的固定紀律,而是隨手加/隨手漏的細節。判 blocker,因為主缺口(`git status`
完全沒提旗標)一旦照字面實作,會讓這輪新增的兩個防線之一(dirty set)整個失效,而且是靜默失效、沒有任何
報錯或測試訊號。

### f5 — major:#10 接線把「用 `_macro()` 平均」的做法錯誤類比成「跟 `must_pinned_count` 同一條路徑」,但 `must_pinned_count` 根本不經過 `_macro()`

`_macro()` 本身的行號引用(`:266-268`)跟插入點(`verdict["pin_top3_must"]` 排在 `:410` 旁)都是對的、
照做不會出錯,所以這不構成可執行性缺口;但「要照 must_pinned_count 的路徑走完」這句話本身指錯了既有前例
——如果之後有人真的去照抄 `must_pinned_count` 的**寫法**(`sum(...)` 累加,不過濾 None)而不是照抄
`_macro()` 這個**函式**,對一個「分母為 0 時要回 None」的欄位做 `sum()` 會在遇到 `None` 值時直接
`TypeError`(`int + None`)。這個誤導性不是我憑空猜的:同一輪另一位審 architecture 對齊的審稿人在自己的
報告裡也寫了幾乎一樣的話(「完全沿用 `must_pinned_count` 已經在走的既有管線」),同樣沒有回頭核對
`must_pinned_count` 本身走不走 `_macro()`——這代表這個錯誤類比有一定的迷惑性,連追蹤既有管線一致性的
審查也沒揪出來。判 major:具體指令(用 `_macro()`)是對的、可執行,但精確的前例名稱錯了,對「照案例抄」
的下一步實作是個真實的誤導風險。

### f6 — major(實務隱患鏡頭・回滾路徑):`LUMOS_IMPACT_ABOUT` 逃生旋鈕沒有涵蓋 #6,關掉 #4 不會讓 #6 的過期警告安靜下來

**spec 段落**:#4 詳規總開關子彈點;#6 詳規全段。

**引句:「預設 1、0=整個 about 判定關閉(不標、不排序、不掃計數、不呼叫 git)。同 `LUMOS_IMPACT_BASENAME_MATCH :13609` 的「預設開/0 逃生」慣例。」**

問題:文件裡至少三處把 `LUMOS_IMPACT_ABOUT=0` 描述成「整個 about 判定關閉」的逃生閥(#4 詳規本身、多條
測試候選裡的「knob=0」對照組、審計修正紀錄裡反覆出現的「總開關」用語)。但通讀 #6 詳規全段,**完全沒有
提到這個 knob**——#6 的過期迴圈是「掃全部 type、有 `about_code_stamp` 的節點套過期守衛節的同一條規則,
呼叫同一組 helper」,沒有寫「knob=0 時整段略過」。這代表:如果 `git_last_change_info`/`git_dirty_notes`
這組 helper 本身有問題(例如 f2 的假警訊偏多、或 f3 的 dirty 偵測失效被修正後行為改變),有人想先用
`LUMOS_IMPACT_ABOUT=0` 把功能整個關掉、等修好再開,`cmd_impact` 那一側確實會照描述完全不呼叫 git、不標
`about_hit`,但 `lumos doctor` 每次照樣會跑 #6 的新迴圈、照樣呼叫同一組(可能有問題的)helper、照樣印出
「可能過期」的清單——「總開關」這個詞在文件裡的語感覆蓋了整個 about 功能,實際只覆蓋了 #4 這一半。

這不是本案首創的模式(既有的 Check S 本身也沒有獨立的環境變數開關,doctor 檢查一般是靠 `warn_soft`
不擋、不需要個別關掉),所以我不判 blocker;但考慮到 f2/f3 已經證實這組 helper 目前的規則有實際會產生
假警訊/靜默失效的地方,「總開關」這句話反覆出現、卻只覆蓋一半功能,會讓下一個想暫時停用整個 about 功能
的人誤判「關了 knob 就乾淨了」,結果 doctor 還在吵。建議至少在 #6 詳規補一句「本迴圈是否也受
`LUMOS_IMPACT_ABOUT` 控制」,把這件事講清楚,不管答案是要蓋還是刻意不蓋。

### f7 — minor(實務隱患鏡頭・效能):懶觸發的「+0.2s 一次,可接受」成本估計,是 std-r1 加第二支 git 子行程**之前**量的數字

**spec 段落**:「過期守衛」節末,懶觸發子彈點。

**引句:「實測 0.215s 全庫 git log;hook 每次是新行程,行程內快取對 hook 無用」**

問題:這個 0.215s 數字(以及緊接著寫的「命中時 +0.2s 一次,可接受」)是對**單一支** `git log` 子行程量的
(item #5,已落地那份),std-r1 這一輪在同一個懶觸發路徑上又加了**第二支**子行程(`git status --porcelain`,
供 `git_dirty_notes` 用),但文件裡沒有針對「兩支子行程一起跑」重新量過一次,只是沿用了舊數字。這正是
std-r1 自己在別處抓別人的錯誤模式(s3f6:「這句只算了比字串,沒算 git log 那 0.2s」)換了個位置又發生一次
——沒有算第二支子行程的成本。

我自己在本機對這個 repo 實測(`time` 包住兩支指令跑同一個 vault 範圍):`git log --name-only` 單獨約
0.25-0.6s(視檔案系統快取冷熱而定),`git status --porcelain` 單獨只要約 0.05-0.1s(它只比對工作目錄跟
索引,不用掃整段歷史,天生比 `git log` 便宜)。兩支合計仍在「+0.2~0.7s 一次、懶觸發下不常發生」這個量級,
沒有離譜到會實際壓垮熱路徑——所以這不是功能缺陷,判 minor:純粹是「文件裡引用的成本數字,對照的是修改前
的實作,沒有對修改後(兩支子行程)重新量」,跟 f4 的「行號沒回頭校正」是同一類毛病的效能版本,建議在真正
落地 `git_dirty_notes` 之後補一次兩支合計的實測數字,而不是繼續沿用只算了一半的舊數字。

## 實務隱患鏡頭(逐類過)

- **併發**:讀路徑(`cmd_impact --ranked`、`run_doctor` 新迴圈)全程只讀 git 與筆記檔,不寫入,天生對併發
  安全;寫路徑(`lumos about-code revert`、批次 stamp 寫入)是人工低頻觸發的操作,沒有跨行程鎖,但這不是
  本案新增的缺口——`lumos append`/`set`/`remove` 本來就沒有鎖,若真的兩個寫入行程同時跑同一批筆記,
  行為跟既有寫入路徑一樣脆弱,不是 about-code 這輪新開的先例。無新增獨有風險。
- **效能**:見 f7(懶觸發成本估計沒算到第二支子行程,但實測沒有離譜到位)。`_impact_about_counts` 全掃
  `env.notes` 一次、行程內快取,是純記憶體運算(不叫子行程),對這個規模的 vault(數百篇筆記)可忽略。
- **資源**:新增的兩個模組級快取(`git_last_change_info`/`git_dirty_notes` 各自的字典)跟既有
  `_GIT_DATES_CACHE`/`_BASENAME_COUNTS_CACHE` 同款,大小受 vault 篇數約束(現況 3 百多篇),隨行程結束
  釋放,沒有無界成長或外洩路徑。無新增風險。
- **回滾路徑**:見 f6(逃生旋鈕只蓋 #4、沒蓋 #6)。`lumos about-code revert --batch <日期>` 本身(#7,已落地)
  的部分失敗處理(留 stamp、rc 非 0)經對照 `scripts/lumos:7665-7710` 現況程式碼行為相符,是本案唯一的
  「寫入且需要回滾」路徑,已有清楚且已驗證的回滾機制。
