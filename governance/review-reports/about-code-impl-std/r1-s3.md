### f4 — major
**段落**:#4「巨檔門檻」規格。
**逐字引句**:「★以 `id(env)` 為鍵掛行程內快取★(impl-r1 s1f7;同 `_BASENAME_COUNTS_CACHE :13587` 慣例」
**問題**:兩個層面都有問題。(a)**引用的先例不符**:`_BASENAME_COUNTS_CACHE`(`scripts/lumos:13587`)實際上是以 `repo_root`(字串)為鍵,不是 `id(env)`;`_GIT_DATES_CACHE`(`:13546`)也是以 `(repo_root, vault)` 字串 tuple 為鍵。全庫沒有任何一個既有的行程內快取是用 `id()` 當鍵,「同…慣例」這句話對不上實際程式碼。(b)**`id()` 本身是已知的 Python 陷阱**:CPython 的 `id()` 是記憶體位址,物件被 GC 回收後位址可被下一個物件重用——如果同一行程內先建立 `Env(vaultA)`、算完巨檔計數、該物件被釋放,之後建立 `Env(vaultB)`(不同 repo/vault)剛好拿到同一個位址,`id(env)` 會撞出同一把快取鍵,巨檔計數的快取值會把 vaultA 的統計悄悄套用到 vaultB 頭上,而且不會報錯、不會有任何提示——這正是巨檔門檻要防的那種「靜默判斷失真」。目前程式碼裡唯一在行程內直接呼叫 `cmd_impact()` 的地方是 `cmd_impact_diff`(`scripts/lumos:14389`),它把 `_env_shared` 存在區域變數整個迴圈期間都活著,這條路徑安全;但 spec 自己在 #4 測試清單裡列的 8 條測試(有欄含目標/有欄不含/無欄/過期/巨檔…)如果比照這份文件其他測試常用的手法(`spec_from_file_location` 把 `scripts/lumos`當模組匯入、在同一個 process 裡連續對不同 fixture vault 呼叫)撰寫,就會踩進這個陷阱,而且是那種「十次有九次沒事、突然有一次算錯」的 flaky 樣式,比崩潰更難查。若要保留「行程內快取」設計,應比照既有兩個快取的做法,鍵改成 `(repo_root, vault)` 或 `id(vault)`(vault 是 `Path`,同一支 vault 物件通常是穩定引用,但更保險的做法是直接用字串路徑當鍵)。
**證據**:
```
13546:_GIT_DATES_CACHE = {}   # (repo_root, vault) → {...}
13587:_BASENAME_COUNTS_CACHE = {}   # repo_root → {basename: count}
```
`grep -n "cmd_impact(" scripts/lumos` 只有 3 處呼叫(定義本身、`cmd_impact_diff:14389`、CLI 派發 `:15590`),`test_lumos.py` 目前沒有任何測試直接呼叫 `.cmd_impact(`(全走 subprocess),代表這個風險目前潛伏、尚未被現有測試踩到,但 #4 新測試若沿用既有的模組匯入手法就會踩到。

```
    return 0 if done == len(targets) else 1
```
（`cmd_remove` 失敗與 `_cmd_remove_scalar` 是否成功,兩者互不影響對方的執行與計數邏輯。）

## 實務隱患鏡頭(逐類檢查)

- **併發**:CLI 為單行程單次呼叫模型,frontmatter 寫入走既有 `atomic_write_verify`(既有機制,本案未改);未發現本案新增的併發風險,除 f4 提到的「同一行程內連續建立不同 `Env` 物件」屬性質相近但根因是 `id()` 重用而非典型的執行緒/行程競爭,已併入 f4,不重複列。
- **效能**:見 f6——`cmd_impact` 過期判斷把 `git_last_change_dates()` 全庫掃描接進 PreToolUse hook 的熱路徑,每次 code 編輯都要多付一次 git log 成本,且在行程內快取(每次 hook 都是新行程)下必定 cache miss,spec 對此成本的論證只覆蓋了字串比較,未覆蓋 git log 呼叫本身。#6 的過期迴圈掛在 `doctor`(人工觸發、非熱路徑),同樣的 git log 成本在那裡不構成問題。
- **資源**:未發現新增的檔案代碼/記憶體/暫存檔資源風險;`_GIT_DATES_CACHE`/新提議的巨檔計數快取都是行程內字典,行程結束即釋放,規模最多是 vault 篇數量級(≈330 篇),不構成資源洩漏疑慮。
- **回滾路徑**:見 f8——已落地的 `about-code revert` 在部分失敗時會把「stamp 已清」誤判為「這篇撤除成功」,讓 rc0/「done」計數與實際資料狀態脫鉤。這是本輪隱患鏡頭裡最值得處理的一項,因為它就是這個功能本身用來「防止預標出錯」的最後一道安全網,安全網自己有一個不被察覺的破口。
- **快取正確性(補充類別,非併發也非效能)**:見 f4——`id(env)` 作為快取鍵在 Python 語意上不保證跨物件生命週期唯一,是本輪最值得注意的技術債風險點,雖然目前程式碼裡的實際呼叫路徑(`cmd_impact_diff`)恰好安全,但 spec 引用的「先例」本身是錯的,而且往後最自然的測試寫法(模組匯入、同行程建多個 vault fixture)剛好會踩進這個陷阱。

## 總結

本輪最嚴重的 severity 是 **major**(f3、f4、f6、f8 四條;f1、f2、f5 為 minor)。沒有 blocker 級發現——spec 描述的整體方向(about_code 只加分不降級、about_hit 新欄不覆寫 hit、以 `git_last_change_dates` 統一過期判準)在現有程式碼基礎上是可行的,但 #10 的 history 落點被漏講(f3)、#4 的巨檔快取鍵選型有真實的靜默失真風險且引用先例有誤(f4)、#4 的過期判斷把一次全庫 git log 成本悄悄記到「毫秒級」帳上(f6)、以及已落地的回滾指令在部分失敗時會誤報成功(f8),這四條建議在轉成正式實作前逐一处理或至少留痕承認。
