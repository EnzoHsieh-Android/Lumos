## f1 — blocker:git-log 過期判準有「未提交編輯」盲區,正是它自稱要防的偽陰性

**段落**:### ★過期守衛(沒有這個就別做)★,r2 補段
**逐字引句**:「**處置**:過期判準改成 **git 最後改動日期**(`git log -1 --format=%cs -- <檔>`)> stamp 日期;git 缺席時退回 `updated`。」

**問題**:`git_last_change_dates()`(`scripts/lumos:13549`)完全靠 `git log --name-only --format=@%cs` 取得檔案「最後改動日期」,而 git log 只看得到**已提交**的歷史。若一篇筆記在 `about_code_stamp` 之後被大幅改寫但**尚未 commit**(對這個 repo 是常態——CLAUDE.md 明講「同一次工作內寫回」,寫回和提交常常不同步,且本次對話開始時 `docs/.governance-log.jsonl` 本身就處於未提交狀態),`git_last_change_dates()` 回傳的仍是上一次 commit 的日期(可能早於 stamp 日期),於是 `stamp_date < git_date` 判假 → **不算過期** → 讀側繼續信任這篇筆記的 `about_code`。

這正好複製了 spec 自己在同一節痛批 `updated` 欄的那個失敗模式:「用 `updated` 當過期判準會**沉默放過**這些節點——偽陰性,代價比偽陽性高(正是 about_code 要防的那個方向)」。改用 git log 只是把「忘記 `lumos set updated`」換成「還沒 commit」,同一種偽陰性、同一個代價方向,通篇沒有一處提到或防禦這個情況。

**證據**:`scripts/lumos:13549-13583`(`git_last_change_dates` 全靠 `subprocess.run(["git", ..., "log", ...])`,無任何讀取工作樹/未提交差異的分支);`git_last_change_dates` 自己的 docstring 也只比較「git 最後改動日期」與 `updated` 欄兩者何者更可信,未考慮兩者都可能落後於工作樹現狀的情況。

## f3 — major:`cmd_impact :14024` 不是「往上找 .git」的寫法,引錯了要仿的樣板

    if (cand / ".git").exists():

(`scripts/lumos:13997-14001`)。也就是說 repo 裡現存的兩種「找 repo_root」寫法,一種是「從 cwd 逐層找 `.git`」(13997-14001),另一種是「從 vault 固定跳兩層,不驗 `.git`」(14024)——spec 想要的是第一種的邏輯(逐層搜尋)但用第二種的起點(`vault`),卻引用了**第三種、實際上誰都不是**的行號當樣板。對本專案這個 repo 剛好因為 `vault = docs/{project}-knowledge/` 固定兩層,`vault.parent.parent` 湊巧等於 repo_root,所以字面照抄 `:14024` 也不會立即出錯;但這不代表引用是對的——它會讓後續實作者誤以為「往上找 `.git`」這個更穩健的寫法已經有現成範例可抄,結果抄到的其實是一個不做 `.git` 驗證、對非標準目錄佈局沒有防呆的簡化版。

## f10 — major:about_hit 的 stable sort 沒有排除 incident,可能讓「只是提到」的候選排到「出過事」的警告前面

**段落**:### #4 impact 讀 about_code…「排序」子項;讀側怎麼用節「改寫後的規則」
**逐字引句**:「**排序**:`pins = [...]`(`:14226`)之後加一道 stable sort:`about_hit` 者在前,其餘保持原序。★不動 `contract_priority`,不動 free/rescued★。」

**問題**:`pins`(`scripts/lumos:14226`)目前的組成順序是「先 incidents(全部固定命中)→ 再 direct(依 contract_priority 排)→ 再 indirect(依 hop 排)」——這個順序把「這篇筆記記載的是這支檔曾經出過的事故」放在最前面,是刻意的(參照本文件自己前面舉的例子:`Issues/hook卸載殘留註冊` 這種事故類節點,即使 about_code 沒列到正在改的檔,也要無條件保送)。但 spec 定義的 stable sort key 只有一個布林值 `about_hit`,套用在**整個** `pins` 清單上,不分 kind——若同一次編輯裡,某個 `direct`/`indirect` 候選剛好 `about_hit=True`(它的 about_code 精確列到了這支被改的檔),而某個 `incident` 候選 `about_hit=False`(它是靠 pitfall_when 觸發保送,about_code 沒列這支檔——正是文件自己舉的 `hook卸載殘留註冊` 那個案例的結構),排序後前者會排到後者**前面**。也就是說「這支檔曾經闖過禍」的警告可能被排到「這篇筆記剛好也提到這支檔」的候選後面。

Spec 通篇強調 about_code 只排序不剔除、「對 hook 顯示有影響(前排先看到對的)」,但沒有討論過 about_hit 與 incident 兩個訊號哪個該贏。給定文件自己反覆用事故類節點當「固定席存在理由」的最強論證(訊號段:「那正是固定席存在的理由:接住『字面完全不像但必看』的東西」),讓一個純粹「about_code 命中」的候選能把「出過事故」的候選擠到後面,與這個論證的精神相反。

**證據**:`scripts/lumos:14172-14181`(incident 段落最先 append 進 `results`,`pinned: True` 恆真,無 `about_hit` 相關邏輯);`scripts/lumos:14226`(`pins = [r for r in results if r["pinned"]]` 保留 append 順序,即 incident 最先);spec 227-230 行自己舉的 `hook卸載殘留註冊` 案例正是「about_code 不含目標檔、靠 incident 路徑保送」的活生生例子——若同一輪還有一個 about_hit 命中的候選,新排序規則會讓它排到這個事故警告前面。
