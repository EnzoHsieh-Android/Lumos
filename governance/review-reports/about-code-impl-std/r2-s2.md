## f1 — blocker:`git_dirty_notes` 沒帶 `-c core.quotepath=false`,對中文檔名(vault 幾乎全部)靜默偵測不到 dirty

**段落**:### ★過期守衛(沒有這個就別做)★,std-r1 改寫段
引句:「再一次批次 `git status --porcelain -- <vault>` 抓沒 commit 的:`git_dirty_notes(repo_root, vault)` 回 set,同款行程內快取。」

**問題**:同一節上面幾行,spec 自己才剛把 `git_last_change_dates` 的 quotepath 坑講得很清楚——「`-c core.quotepath=false`……沒這旗標整張表是空的,而且不報錯」(工具清單 #5「翻紅釘實證:★拿掉 quotepath 旗標連英文檔都撈不到★(路徑帶中文目錄名整條被跳脫),表空且不報錯」)。但 `git_dirty_notes` 這個**新增**的姊妹 helper,字面上給的指令就是 `git status --porcelain -- <vault>`,**沒有帶同一個旗標**。

實測驗證(本次審查現場跑):
```
$ git status --porcelain
 M "docs/\344\270\255\346\226\207\346\252\224\345\220\215.md"
$ git -c core.quotepath=false status --porcelain
 M docs/中文檔名.md
```
`git_last_change_dates` 的 docstring 明講這個 repo 的 vault 檔名「幾乎全中文」。如果 `git_dirty_notes` 照 spec 字面實作,對真實 vault 裡任何一個中文檔名節點,回來的 dirty set 永遠不含它(路徑被跳脫成八進位跳脫字串,和 `rel` 完全對不上),**整個 dirty 分支形同虛設**——而 dirty set 這個機制存在的理由,正是 spec 自己在同一節點出來要防的「偽陰性」(未提交編輯被誤判成新鮮)。這是同一個坑在姊妹函式上重犯一次,而且是在剛剛才親自檢討過這個坑的同一段落裡。

**證據**:`scripts/lumos:13564-13592`(`git_last_change_dates` 現行實作,`-c core.quotepath=false` 確實存在於 `subprocess.run` 呼叫裡,對照組);現場 `git status --porcelain` vs `git -c core.quotepath=false status --porcelain` 對同一中文檔名的輸出差異(見上方引用)。

## f2 — minor:`git_dirty_notes` 對 rename 的 porcelain 格式沒有處理

**段落**:同 f1
引句:「再一次批次 `git status --porcelain -- <vault>` 抓沒 commit 的」

**問題**:git status --porcelain 對已 `git mv`/staged rename 的檔案,格式是 `R  <old> -> <new>`(兩個路徑用 ` -> ` 分隔,不是單一 `XY path` 格式)。實測:
```
$ git -c core.quotepath=false status --porcelain
R  docs/中文檔名.md -> docs/新檔名.md
```
一個直覺的 porcelain 解析法(取每行第 4 個字元起當路徑,`line[3:]`)在這種情況下會把整段 `"docs/中文檔名.md -> docs/新檔名.md"` 當成單一路徑,跟 `rel` 兩邊都對不中——結果跟 f1 一樣是「靜默漏偵測」,只是觸發條件是筆記被改名而非改內容。這在一個「筆記常被改動」的活語料庫裡不算完全冷門的場景(重新命名節點是這個 repo 常見的重構動作,`CLAUDE.md` 自己就有「刪掉/改名了一個東西,筆記還在講它嗎」的查詢慣例)。spec 沒有一處提到這個格式,程度上比 f1 輕(rename 中的筆記本來也還沒被 about_code 標過的機率較高),列 minor。

**證據**:同上現場實測輸出。

## f3 — major:#6 doctor 訊息模板在「同日再改」分支裡寫死「< git 最後改動」,兩個相等的日期卻印出「小於」符號

**段落**:### #6 過期檢查:另開迴圈,輸出對齊 Check S
引句:`f"{rel} (about_code_stamp {stamp_date} < git 最後改動 {git_date}{' / 同日再改' if same_day else ''}{' / 未 commit' if dirty else ''})"`

**問題**:「過期」有三種觸發條件(spec 自己在合約候選第 3 條與 std-r1 段都寫清楚):`git_date > stamp_date`,或`git_date == stamp_date 且 n_same_day ≥ 2`(同日再改),或 `rel` 在 dirty set。但上面這個 f-string **不管觸發的是哪一種條件,固定印出 `{stamp_date} < git 最後改動 {git_date}`**——在「同日再改」單獨觸發(即 `git_date == stamp_date`,`n_same_day>=2`,不滿足 `>`)的情況下,套進去會印出類似:

```
X.md (about_code_stamp 2026-08-23 < git 最後改動 2026-08-23 / 同日再改)
```

兩個一模一樣的日期中間卻寫著「<」,是一句字面上不成立的話——讀訊息的人會被誤導以為 git 日期比 stamp 晚一天以上,但實際上是同一天多次 commit。#6 的測試⑤「同日兩 commit → 列、訊息帶『同日再改』」如果照這個模板字面實作並斷言訊息字串,會把這句自相矛盾的話當成正確輸出釘進測試——即測試會通過,但釘住的是一個錯誤的人類可讀訊息。

同一個模板另一個未定義角落:若節點是**從未 commit 過**的新檔(只觸發 dirty,git log 對它完全沒有歷史紀錄),`git_date` 這個變數要嵌進字串時該取什麼值——spec 沒說,若 `git_last_change_info`/`git_last_change_dates` 對它回傳的 dict 裡根本沒有這個 key,`{git_date}` 這段插值要嘛丟 KeyError、要嘛悄悄印出 `None`,兩者都沒在 spec 裡交代。

**證據**:spec 第 293/294/317 行對過期三條件的定義(「過期 = git_date > stamp_date,或(git_date == stamp_date 且 n_same_day ≥ 2),或 rel 在 dirty set」)與第 431 行訊息模板的字面比對——模板只有一種「A < B」形狀,但條件有三種形狀。

## f4 — major:`about_code_stamp` 的日期抽取方法未定義,套用 Check S 既有作法在 batch 格式上有歧義風險

**段落**:### 欄位設計 / ### #6 過期檢查
引句:「格式沿 `self_audit` 兩段式:`about_code_stamp: codex/2026-08-23`(archf2 minor)。」

**問題**:spec 定義了 `about_code_stamp` 的**寫入**格式(`<誰標>/<日期>`,批次是 `batch-<日期>/<日期>`),但從沒定義**怎麼從這個字串裡把 `stamp_date` 抽出來**。#6 明講要「對齊 Check S 實際格式」,而 Check S 現行抽日期的作法是 `re.search(r"(\d{4}-\d{2}-\d{2})", sa_val)`(scripts/lumos:838)——**在整個字串裡搜第一個 `YYYY-MM-DD` 子字串**,不是「取 `/` 後半段」。

批次寫入的格式是 `batch-2026-08-23/2026-08-23`——這個字串裡**兩段都長得像日期**(第一段 `batch-2026-08-23` 本身就含一個合法的 `YYYY-MM-DD` 子字串)。如果實作依「對齊 Check S」的指示直接複用同一個 regex-search,取到的會是**第一段裡那個日期**,不是 `/` 之後的第二段——目前兩者剛好相等(批次寫入時第一段的日期與第二段的日期是同一天),所以現在測不出差異;但這個相等關係只是「目前寫入邏輯剛好這樣寫」造成的巧合,spec 沒有把它訂成不變量,也沒交代抽取應該用 `split("/", 1)[1]`(對齊 `cmd_about_code_revert` 已經在用的 `stamp.split("/", 1)[0]` 手法,只是取另一段)還是沿用 regex-search。兩種寫法在「正常」情況下結果一樣,只有在人工修正 stamp、或未來寫入邏輯改成兩段日期不同步時才會分岔出錯誤答案——但這正是「斷言的東西有沒有定義」這個鏡頭要抓的那種洞:#4/#6 的任何測試都沒有覆蓋這個抽取步驟本身。

**證據**:scripts/lumos:838(`m = re.search(r"(\d{4}-\d{2}-\d{2})", sa_val) if sa_val else None`,Check S 現行抽日期作法);scripts/lumos:7681(`cmd_about_code_revert` 用 `stamp.split("/", 1)[0]` 取「誰標」段,證明程式碼裡已經有「按位置切割」這個替代寫法的先例,但 spec 沒指名 #6 的過期迴圈該用哪一種)。

## f5 — major:#4 測試⑫「monkeypatch helper 計數為 0」與本檔既有 impact 測試的 CLI 子行程呼叫慣例衝突

**段落**:### #4 impact 讀 about_code:只加分、不降級、排前排
引句:「⑫`--incidents-only` → 不呼叫 git(monkeypatch helper 計數為 0)。」

**問題**:`scripts/test_lumos.py` 裡所有 `t_impact_*`(含 spec 指名的 fixture 基礎 `t_impact_ranked`)一律透過 `sp.run([sys.executable, GRAPHCTL, *a], ...)` 開子行程呼叫 `lumos` CLI,而**沒有任何一個**測試直接呼叫模組層級的 `cmd_impact(...)` 函式(全檔 `grep "cmd_impact("` 零命中)。子行程會重新 `exec` 一份全新、未被修改過的 `scripts/lumos`;測試行程裡對 `import` 進來的模組物件做 `m.git_last_change_info = fake` 這種 monkeypatch,對子行程內執行的那份 code **完全沒有作用**——子行程讀到的永遠是磁碟上原封不動的函式。

如果字面照做,兩種結局都不好:要嘛實作者發現 monkeypatch 沒用而卡關;要嘛更糟的情況——測試作者改成「monkeypatch 之後直接呼叫子行程」,子行程照樣呼叫真正的 git,計數器(如果錯放在測試行程那邊的 mock 物件上)永遠是 0,**測試對「有沒有呼叫 git」這件事完全沒有鑑別力,無論實作對錯都印出「呼叫了 0 次」**——變成一個看起來在驗證懶觸發、實際上什麼都沒驗證的假陽性測試。

本檔已經有解法可以直接照抄:`t_git_last_change_dates_batch`(:579)驗證「只呼叫一次 git」用的不是 monkeypatch,是在 PATH 前面塞一支會計數再轉呼叫真正 `git` 的 shell shim:
```python
(shim / "git").write_text(f"#!/bin/sh\necho x >> {cnt}\nexec {real_git} \"$@\"\n", ...)
os.environ["PATH"] = f"{shim}:{old}"
```
這個手法能跨子行程邊界(因為攔截的是 `PATH` 上的可執行檔,不是 Python 物件),⑫應該沿用這個,而不是「monkeypatch helper」。

**證據**:`grep -n "cmd_impact("  scripts/test_lumos.py` 零命中;`t_impact_ranked`(:13957)、`t_impact_diff`(:14022)等全部經 `sp.run([sys.executable, GRAPHCTL, ...])`;`t_git_last_change_dates_batch`(:579)PATH-shim 計數手法的既有實作。

## f6 — minor:#4 測試⑧「輸出與改動前逐 byte 相同」裡的「改動前」缺乏可執行定義

**段落**:### #4 impact 讀 about_code(測試清單)
引句:「⑧knob=0 → 輸出與改動前逐 byte 相同」

**問題**:「改動前」字面上最直接的讀法是「這次改動(本 spec)落地之前,`scripts/lumos` 舊版的輸出」——但單一測試函式沒有機制去跑一份舊版程式碼比對(除非額外 `git show <上一版>:scripts/lumos` 存成暫存檔再跑一次,spec 沒交代要這樣做,也沒人這樣做過)。比較合理、可機械執行的讀法是「同一節點:『有 about_code 欄且會命中』時關掉 knob,輸出應該等於『這個節點乾脆沒有 about_code 欄』時的輸出」——這個讀法技術上可行(跟②③的手法一樣,只是刻意選一個「不關掉的話會命中」的節點來對比更嚴格)。但這只是審稿人的推測讀法,spec 沒有把它寫清楚,容易讓實作者卡在字面的「改動前」上,或誤以為只是②③的重複而隨手跳過(其實不是——⑧測的是「有命中但被關閉」,②③測的是「本來就不命中」,兩者要驗的東西不同)。

**證據**:本節其餘 ②③④⑤ 全部用「knob 開 vs 關」比對來定義「零影響」,⑧單獨換了「改動前」這個沒有機制對應的詞,屬於這一小節內部用詞不一致。

## 實務隱患鏡頭(依 r2-common 審查要求 4)

- **併發**:本輪新增的兩個 git 子行程(`git log`/`git status`)都走「懶觸發+單次批次+行程內快取」設計,跟現行 `_GIT_DATES_CACHE`/`_BASENAME_COUNTS_CACHE` 走同一套路——多個 Claude Code session 同時對同一 repo 觸發 hook 時,各自都是獨立 CLI 子行程(冷快取),彼此之間沒有共用鎖也沒有互踩的寫入(`git status`/`git log` 都是唯讀)。**風險低**:git 對並發讀操作本身是安全的,唯一的邊角是「git status 執行期間剛好有另一個 session 在跑 `git commit`」可能撞到 index.lock 短暫延遲,但這是既有 `git_last_change_dates` 已經承擔的既有風險(不是本輪新增),spec 沒有回頭處理不算新缺口。
- **效能**:`git log` 那條已有實測數字(0.215s/0.224s 全庫);**新增的 `git status --porcelain` 這條完全沒有給效能數字**——spec 只講「懶觸發」讓它在沒有 about 命中時零成本,但命中時的實際耗時未測。這條 repo 的 `.git` 歷史量體不小(工具清單 #5 提到「改最勤的檔」31 次/週),`git status` 内部預設要掃整個工作樹(untracked cache 命中與否會有數量級差異),沒有量測就寫「毫秒級,不構成熱路徑問題」是把 `git log` 的量測結果延伸套用到沒量過的 `git status` 上,屬於未查證宣稱(但因為量級通常同源,不到 blocker,列在此處供實作者留意,不獨立開 f 編號)。
- **資源**:兩個新 helper 都描述為「同款行程內快取」,延續既有 `_GIT_DATES_CACHE` 的 fail-open 慣例(git 缺席/失敗回空);未見資源洩漏或無界增長的跡象。
- **回滾路徑**:`about-code revert`(工具清單 #7)已落地且我實地核對了程式碼(`scripts/lumos:7665-7710` `cmd_about_code_revert`)——重複值先去重(`dict.fromkeys`)避免 `cmd_remove` 對同值二次呼叫崩潰、單篇任一值失敗時 stamp 保留不刪、rc 非 0——與 spec 描述一致,std-r1 s3f8 的修正確實落地。**這條已讀,無 finding**。
