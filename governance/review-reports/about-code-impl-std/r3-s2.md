## 深挖①:④「正文改一字不 commit」在 mkvault(非 git repo)裡怎麼造——雜湊方案下還需要 git 嗎

**不需要,而且已現場驗證整個 about_code 機制在完全沒有 `.git` 的目錄下也能跑。**

```
$ python3 scripts/lumos impact --file src/svc.py --repo <非git目錄> --ranked --json
rc=0
{"file": "src/svc.py", "results": [{"node": "Systems/SvcCore.md", "kind": "direct",
"pinned": true, "score": 0.3, "L": 0.0, "hit": "body-inline-code", "contract": "INVARIANT"}], ...}
```
（現場建的 `<非git目錄>` 完全沒有 `git init`,`about_code: [src/svc.py]` 照樣被 `_impact_reverse_lookup` 用完整路徑(含 `/`)比對命中——git 只在**裸檔名**容錯路徑(`LUMOS_IMPACT_BASENAME_MATCH`)才需要,`git ls-files` 失敗時該路徑本來就 fail-open 成「degrade 為不比對」,不影響完整路徑比對。scripts/lumos:13633-13645。）

`note_body_hash(vault, rel)` 的設計本身(spec:「讀檔→split→hash;★無快取,無 git,無子行程★」)是直接讀工作樹檔案,`split_frontmatter`(scripts/lumos:101-108)回傳 `(fm_lines, body)` 純字串操作,完全不查 git 物件庫、不查 index、不查 HEAD。所以「正文改一字、不 commit」這個場景在雜湊方案下,`commit` 與否**沒有任何差異**——不管 commit 沒 commit,`note_body_hash` 讀到的都是工作樹上那份改過的內容。

**問題(f2,見下)**:spec 這句「正文改一字、不 commit」的措辭是舊版(std-r1 之前,日期/commit 制)遺留下來的框架——那個年代「沒 commit」是真正的邊界條件(git log 看不到未 commit 的變更,是 std-r1 特地加 `git_dirty_notes` 來補的洞)。std-r2 把整個機制換成雜湊後,這句話按字面執行完全沒問題(隨便找個 mkvault 或 t_impact_ranked 的 git fixture,改字不 commit 一樣測得出來),但措辭本身容易誤導實作者去猜「是不是還要驗 git 相關行為」,浪費力氣搭不必要的 git 腳手架。

## 深挖②:⑬「`lumos set` 後不過期」——正文 bytes 實測 before/after diff

現場對一個既有 vault(全新建的測試 vault,非正式 repo)跑了兩次真實 CLI 呼叫,直接比對檔案 bytes:

```python
# before
b"---\ntype: system\nstatus: doing\nabout_code_stamp: batch-2026-08-23/2026-08-23\n---\n# S\n\n正文內容,提到 `scripts/lumos`。\n"
# 執行 `lumos set Systems/S status done`
# after
b"---\ntype: system\nstatus: done\nabout_code_stamp: batch-2026-08-23/2026-08-23\n---\n# S\n\n正文內容,提到 `scripts/lumos`。\n"
```
`body bytes equal: True`(split 出的正文段落 bytes 逐位元相同)。

又針對 spec 測試⑬字面指名的欄位再測一次——直接對 `about_code_stamp` 本身跑 `lumos set`(不是隨便挑一個別的欄位):
```
$ lumos set Systems/S about_code_stamp claude/2026-08-24/bbbbbbbbbbbb
✓ set Systems/S.md: about_code_stamp 已改成 claude/2026-08-24/bbbbbbbbbbbb
body unchanged: True
```
確認 `cmd_set`(scripts/lumos:7514-7534)只動 `lines[1:e]`(frontmatter 段),`lines[e:]`(收尾 `---` 之後的全部,即正文)原封不動地併回新檔——這是 `edit_fm_scalar` 的結構性保證,不是巧合。**⑬的斷言完全成立且已現場證明,無 finding。**

**附帶發現(→ f3)**:上面第二個實驗同時暴露了 `about_code_stamp` 的寫入路徑毫無格式驗證——`fmt_scalar`(scripts/lumos:7287-7300)只對 `DATE_KEYS` 做格式檢查,`about_code_stamp` 不在其中,所以 `lumos set` 接受**任意字串**當 stamp 值(上面故意寫的 `claude/2026-08-24/bbbbbbbbbbbb` 完全沒被擋)。這意味著人手動 `lumos set about_code_stamp` 繞過 `restamp` 子命令時,可以寫出段數不對、第三段非 12 碼、第三段非 hex 的 stamp,而 #4/#6 的 19 條測試都沒有覆蓋這個「格式不合法但欄位存在」的中間態(見 f3 細節)。

## 深挖③:`restamp` 子命令 argparse 怎麼掛在 `about-code` 底下跟 `revert` 並列

現行 `revert` 的實際掛法(scripts/lumos:15082-15086):
```python
ac = sub.add_parser("about-code", help="...")
acsub = ac.add_subparsers(dest="accmd", required=True)
acr = acsub.add_parser("revert", help="...")
acr.add_argument("--batch", required=True, metavar="YYYY-MM-DD", help="批次日期")
acr.add_argument("--dry-run", action="store_true", help="只列不撤")
```
`restamp` 應該在 `acr = acsub.add_parser("revert", ...)` 那三行之後緊接著加一個平行的 `acs = acsub.add_parser("restamp", ...)`。但 spec 工具清單 #11 只寫「argparse 二層子命令同 `revert`」,對兩個具體問題完全沒交代:

1. **`<節點>|--expired` 這種「positional 或 flag 二選一」怎麼在 argparse 裡表達**——`revert` 沒有這個形狀可抄(它只有一個必填 `--batch`)。不過本檔已有現成先例可以直接照抄:`impact` 的 `--file/--diff/--node` 三選一(scripts/lumos:15402-15404,`nargs` 各自獨立,互斥檢查手動寫在 dispatch:`if sum(1 for x in (args.impact_file, args.impact_diff, args.impact_node) if x) > 1: 擋下 rc2`)、`link-candidates` 的 `lc_file nargs="?"` + `--all-goldset`(scripts/lumos:15483-15484,help 文字直接寫「與 --all-goldset 互斥」)。`restamp` 應該一樣用 `note = acs.add_argument("note", nargs="?")` + `acs.add_argument("--expired", action="store_true")`,在 `cmd_about_code_restamp` 內部手動檢查「恰好給一個」,兩者皆無或兩者皆有都 rc2。argparse 本身沒有內建機制表達這個形狀,必須手寫。

2. **dispatch 端需要加新分支,否則靜默失敗**——現行 dispatch(scripts/lumos:15728-15730):
   ```python
   if args.cmd == "about-code":
       if args.accmd == "revert":
           return cmd_about_code_revert(env, args.batch, dry_run=args.dry_run)
   ```
   這是一個裸 `if`,不是 `elif`/窮盡分支。一旦 argparse 允許 `accmd == "restamp"` 卻沒人在這裡加對應分支,`lumos about-code restamp ...` 會通過 argparse 解析、進入這個 `if args.cmd == "about-code":` 區塊、內層 `if args.accmd == "revert"` 為 False、**不 return**,接著往下掉進後面一串完全無關的 `if args.cmd == "canary": ...`、`if args.cmd == "sqlfluff-sarif": ...` 等等(全部因為 `args.cmd` 仍是 `"about-code"` 而不匹配),最終落到檔尾唯一的 catch-all `return 2`(scripts/lumos:15913,`if __name__ == "__main__":` 前一行)——**沒有任何 stderr 訊息**,只有一個裸的 rc=2。這是本 repo 既有的 dispatch 慣例(裸 if 鏈+尾端 `return 2`),不是 std-r2 引入的新洞,但工具清單 #11 沒有提醒「加 argparse 子命令」跟「加 dispatch 分支」是兩件都要做的事,漏一件的失敗訊號是使用者完全看不到任何錯誤字串,只看到 rc2——見 f4。

## 深挖④:83 篇遷移「用 git 列出 08-23 之後改過正文的清單」在雜湊方案下是否還需要 git

**這一步是本案唯一一處雜湊方案退場後仍然合理需要 git 的地方,但屬性跟「執行期過期判準」完全不同——這是一次性、人監督的稽核步驟,不是機器判準,不違反「git 完全退場」的設計原則(那條原則管的是 runtime 的 impact/doctor 熱路徑,不是一次性遷移腳本)。**

原文脈絡:批次遷移是把 83 篇既有的兩段式 `batch-2026-08-23/2026-08-23` stamp 補上第三段(用**現在**的正文算雜湊)。天花板在於:如果某篇筆記在 2026-08-23(原始預標日)之後、遷移執行的當下之前,正文已經被改過,遷移腳本會拿「已經改過的正文」算雜湊蓋上去——雜湊從此刻起「自洽」(不會被誤判過期),但實際上原始的 about_code 預標內容是對著**舊版正文**下的判斷,現在可能已經跟不上新正文,而雜湊制對這件事完全沒有偵測能力(它只能告訴你「正文有沒有變」,不能告訴你「變了以後 about_code 還準不準」)。這是雜湊方案的天生盲區,spec 自己誠實承認(「★天花板★」)。

**這一步確實需要 git**,因為除了 git 沒有別的材料能回答「這篇筆記在 2026-08-23 之後有沒有被改過正文」——雜湊本身做不到(遷移當下算的雜湊必然等於「現在」的正文,無從對比「當初」)。

**具體怎麼做**:不需要新寫 git 呼叫邏輯,直接重用已經上線、已經修過中文檔名 quotepath 坑的 `git_last_change_dates(repo_root, vault)`(scripts/lumos:13564-13598,工具清單 #5,「暫無呼叫者」但函式沒被拔掉)——

```python
dates = git_last_change_dates(repo_root, vault)   # {rel: "YYYY-MM-DD"}
changed_after = [rel for rel, d in dates.items() if rel in batch_83_files and d > "2026-08-23"]
```
這支 helper 已經內建 `-c core.quotepath=false`(對中文檔名必要,vault 幾乎全中文——見它自己的 docstring 與 `t_git_last_change_dates_batch` 的翻紅釘)、已經是「一次 git log 拿全庫」的批次版(不是逐篇跑,83 次 vs 1 次差 18 倍)、已經 fail-open(git 缺席回空 dict)。

**風險(→ f5)**:spec 這段(「遷移時用 git 列出 08-23 之後改過正文的清單,人掃一眼」)只描述了「要做什麼」,沒有指名「用 #5 這支已經現成、已經修過同一個坑的 helper」。如果實作者沒注意到工具清單 #5 就在旁邊,自己重寫一段 `git log`/`git diff --name-only` 邏輯給遷移腳本用,很可能重新踩進 `-c core.quotepath=false` 這個已經被證明代價很高的坑(見 #5 的翻紅釘紀錄:「拿掉 quotepath 旗標連英文檔都撈不到」)——這是同一個坑在姊妹用途上重犯一次的風險,跟 r2-s2 當時抓到 `git_dirty_notes` 沒帶 quotepath 是同一個病灶模式,只是這次不是機制本體、是遷移腳本。

**stamp 第三段 12 碼碰撞與格式驗證(附帶回答)**:
- **碰撞風險**:12 碼 hex = 48 bit。這個比對**不是**跨語料的生日悖論比較(不是「兩篇不同筆記的雜湊會不會撞」)——比對永遠是「同一篇筆記自己的舊 stamp vs 自己現在的正文雜湊」,是自我比對,不是語料內兩兩比較。真正有意義的風險是「同一篇筆記改了正文,新雜湊前 12 碼恰好跟舊的相同,導致改動被漏判」,機率 ≈ 2⁻⁴⁸,對日常編輯量體是天文數字級別的不可能,**無實務風險**。
- **格式驗證(見 f3)**:`lumos set about_code_stamp` 完全不驗證格式(見深挖②的現場實測),`restamp` 子命令算出來的值必然合法(自己算的 hexdigest),但**人手動 `lumos set` 或未來任何腳本直寫**都可能產生非法第三段(段數不對、非 hex、長度不對)。好消息是比對邏輯是純字串 `!=`,任何非法值天然落在「跟現在正文雜湊不相等」→ 判過期(spec 自己說的方向:「代價是不加分,安全」)——**不會 crash,方向正確**,但 #4(13 條)/#6(6 條)裡沒有一條測試專門覆蓋「第三段存在但格式不合法(非 12 碼或非 hex)」這個中間態,是一個測試覆蓋缺口而非邏輯缺口。

## 實務隱患鏡頭

- **併發**:本輪 std-r2 把 git 完全踢出 runtime 路徑,`note_body_hash` 是純讀檔+hash,沒有子行程、沒有共用鎖檔案——比 r2 版(靠 `git log`/`git status` 子行程)併發面更乾淨,無新增風險。83 篇遷移腳本若跟 doctor loop 同時跑,兩者都是唯讀(遷移寫入的是 frontmatter,doctor 只讀),沒有寫入-寫入衝突;若遷移腳本跟人手動編輯同一篇筆記同時發生,走的是既有 `atomic_write_verify` 的 tmp→rename 機制(scripts/lumos:7483-7500),last-write-wins,是既有已知已接受的風險(read-modify-write 窗),非本案新增。
- **效能**:`note_body_hash` 讀檔+sha256,對單篇筆記(vault 節點通常數 KB)是微秒級;懶觸發(先掃候選有無 about 命中,有才讀檔)把成本壓到「只對真正命中的候選」而非全庫,設計本身就是為了避開 std-r1 那版「git status 全庫掃」的效能未知數(r2-s2 當時 f 未列但在隱患段點名「未測」的那個缺口)——std-r2 把這個疑慮從根本上解除了,不是靠優化,是靠整個不再需要那支呼叫。`_impact_about_counts` 全掃 `env.notes` 建 `{檔: 節點數}` 是唯一沒有懶觸發的部分,但這是純記憶體字典操作(遍歷已載入的 frontmatter 欄位,無 IO),量體對齊既有 `_BASENAME_COUNTS_CACHE` 同款掃描,無新風險。
- **資源**:`note_body_hash` 無快取(spec 明文「★無快取★」)——這是刻意設計,理由是懶觸發已經把呼叫量壓低,不需要再疊一層快取複雜度;`_impact_about_counts` 有行程內快取(鍵 `str(env.vault)`),跟既有兩個快取同款寫法,無洩漏疑慮。
- **回滾路徑**:`about-code revert`(#7)已落地且程式碼與測試(`t_about_code_revert_partial_fail`)一致;`restamp`(#11)是新增的「真正能解除過期」動作(ext-f1 要求的可操作性)——但如深挖③/f4 所述,它的 argparse 掛法與 dispatch 分支都還沒實作,目前 `grep -n "restamp" scripts/lumos` 零命中,這條回滾路徑本身還不存在,是本案「剩四項」裡待實作的部分,非既有缺陷。

## 總結

最嚴重 severity:**major**(f1、f4、f5 三條並列)。f1(#4 測試若照 #6 的簡單 helper 寫會靜默查到生產 vault)、f4(`restamp` 的 argparse/dispatch 兩處都要動,spec 只提了一句帶過,漏一處是無訊息的靜默失敗)、f5(83 篇遷移的 git 步驟未指名重用已修好坑的 helper,有重犯 quotepath 坑的風險)三條性質相近——都是「spec 講的方向對,但省略了一個實作者容易漏掉、漏掉後果是靜默失敗或重踩已知坑」的具體步驟。無 blocker 級:雜湊方案本身(#4 的 13 條、#6 的 6 條測試清單)在字面上全部可建、斷言全部有明確定義,沒有一條像上一輪 r2-s2 的 f1(`git_dirty_notes` 缺 quotepath)那樣「字面實作出來的測試會巧合通過、實際什麼都沒驗證」——這是 std-r2 把日期/commit 制整個換成正文雜湊制帶來的結構性簡化,值得記一筆:上一輪那七條 finding(r2-s2 f1-f7)全部隨 git 退場而失去適用對象,新版沒有生出同量級的洞,只有這輪列出的三條 major + 四條 minor,而且集中在「銜接處」(fixture 呼叫慣例、子命令雙處掛載、遷移步驟與既有 helper 的重用)而非核心判準邏輯本身。
