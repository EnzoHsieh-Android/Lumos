## f3 — major:「既有測試不動」的承諾,沒交代 caching 要留在哪一層,現有測試其實踩在一個會被打破的假設上

**spec 段落**:「過期守衛」節 std-r1 改寫段。

**引句:「`git_last_change_dates` 改成它的薄包裝(回傳型別不變,既有測試不動)」**

問題:現況 `scripts/lumos:13564` 的 `git_last_change_dates(repo_root, vault)` 本身就是全部邏輯所在,用模組級 `_GIT_DATES_CACHE = {}`(鍵 `(str(repo_root), str(vault))`)做行程內快取。對應的測試 `t_git_last_change_dates_batch`(`scripts/test_lumos.py:579`)裡有這段:

```python
m._GIT_DATES_CACHE.clear()     # 第一次呼叫已快取;要數的是「冷呼叫幾次 git」
try:
    m.git_last_change_dates(root, root / "docs" / "x-knowledge")
finally:
    _os.environ["PATH"] = old
n = len(cnt.read_text().splitlines()) if cnt.exists() else 0
check("★整個 vault 只呼叫 git 一次(不是逐檔)★", n == 1, f"呼叫了 {n} 次")
```

這段測試**直接操作私有全域變數 `_GIT_DATES_CACHE`** 來製造一次「冷呼叫」,再數 shim `git` 被呼叫幾次。spec 說 `git_last_change_dates` 之後會變成呼叫新函式 `git_last_change_info(repo_root, vault)` 的薄包裝,但沒說**真正做 git subprocess 呼叫、也需要快取的邏輯,搬去 `git_last_change_info` 之後,快取本身要放在哪一層**:

- 如果快取仍然只留在 `git_last_change_dates`(包裝層),`git_last_change_info` 本身不快取——那 `_GIT_DATES_CACHE.clear()` 有效,測試照舊會過。
- 但如果照「薄包裝」最自然的寫法(真正做事的函式順手自己也快取,包裝層只轉型別)——`git_last_change_info` 自己有一份獨立快取(例如 `_GIT_INFO_CACHE`)——那麼測試裡 `m._GIT_DATES_CACHE.clear()` 清的是**沒人在用的舊快取**,`git_last_change_info` 內部快取因為前面 `dates = m.git_last_change_dates(...)` 那次呼叫已經是熱的,第二次呼叫**不會**真的打 git,shim 計數器會是 0,`n == 1` 斷言失敗。

這不是我猜的邊界情況,是「薄包裝」這個詞本身有兩種同樣合理的實作方式,而 spec 沒有指定要選哪種、也沒有把這個決定寫進「剩四項的實作規格」——現況 #5 已經 done,std-r1 這段擴充還沒實作,所以這個坑會在下一個 session 動手寫 `git_last_change_info` 的時候現形。判 major(不是 blocker):因為它的失敗模式是「測試紅」不是「測試綠但行為錯」,屬於會被抓到但沒被規格說清楚該怎麼做,建議在 #5 那格明寫「快取只留在 `git_last_change_dates`,`git_last_change_info` 本身不做行程內快取」或反過來,擇一寫死。

## 實務隱患鏡頭(逐類過)

- **知識同步(本鏡頭主軸)**:上述 f1/f2/f3/f4/f5。核心風險是「文件宣稱『已校正/已確認』的東西,其實只驗證到那一輪審查當下,後面落地的六個『done』項目會讓下一批行號citation 再度漂移」——這不是一次性問題,是這份文件的**結構性**弱點:只要#1/#2/#3/#5/#7/#8 之外的段落存在行號引用,任何後續落地都可能讓它們再次過期。建議是把「剩四項」規格裡的行號引用改成「以函式名/常數名為準,行號僅供參考」的措辭,或者乾脆在落地前最後跑一次全文 grep 校正,不要分次改。
- **併發**:about-code revert 逐篇呼叫 `cmd_remove`,單篇失敗不影響其餘篇(已用 try/except 隔離),沒看到新的併發風險;#4/#6 都是唯讀查詢+行程內快取,doctor 與 impact hook 是各自獨立行程,不共享快取,沒有跨行程競態疑慮。

- **資源**:新增的 `git status --porcelain` 子行程與既有 `git log --name-only` 子行程都走批次(一次呼叫涵蓋全 vault),沒看到會員生洩漏或反覆 spawn 的路徑。
