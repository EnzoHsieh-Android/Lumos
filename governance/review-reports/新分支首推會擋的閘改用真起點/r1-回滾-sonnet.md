# 回滾與時序鏡頭審查:新分支首推會擋的閘改用真起點_計劃

說明:派工沒有附上計劃牽連的合約/事故節點,所以沒有固定席可逐條判;不憑空補。以下直接對程式與 spec 查證。程式對照 /Users/enzo/harness/lumos-firstpush。

## F1 遠端追蹤分支過期會讓範圍變小,spec 斷言「只會變大」是錯的
severity: major
blocking: 是(spec 的守衛面論述有事實錯誤,而且是放寬方向)
段落:實務隱患第一條。
引句:「很久沒 fetch 時,遠端其實已有的提交會被當成新的——範圍變大(多擋),不是變小。」
問題:`--not --remotes` 看的是本機記得的遠端追蹤分支。遠端分支已在伺服器上被刪(PR 合併後自動刪分支、別人刪)而本機沒 `fetch --prune` 時,過期的追蹤分支還撐著那些提交,它們會被當成「已在遠端」排除,但伺服器上其實沒有。
具體例(已在臨時 repo 實跑):遠端 main;w1 推 A(一個提交 a1);另一個 clone 刪掉遠端 A;w1 沒 fetch,從 A 開 B 加 b1 後準備首推。`git rev-list HEAD --not --remotes` 只回 1 個提交(b1,最早的新提交就是 b1),但相對伺服器真正沒有的是 2 個(a1、b1)。a1 被推上伺服器這一次,沒有任何會擋的閘看它。堆疊 PR(B 疊在已squash合併、分支被自動刪的 A 上)正是這條路。
預期 vs 實際:spec 說只會多擋;實際會少擋,而且少的正好是「這次推送真的送上去的提交」。
補:追蹤分支只認「這次推的那個遠端」的(`--remotes=<遠端名>`),並在實務隱患與天花板寫明過期追蹤分支兩個方向都會錯;或首推前要求 `git fetch --prune` 的提醒。
file: `scripts/hooks/pre-push:336`(現行 `--not --remotes` 的位置,spec 要抽成函式的那段)

## F2 S3「所有提交已在遠端 → 會擋的那幾步跑空範圍並放行」對表態閘不成立
severity: major
blocking: 是(驗收條款 S3 與實務隱患的「照常放行」宣稱與程式矛盾,測試要綁的行為本身錯)
段落:驗收條款 S3、實務隱患第三條、做法 3。
引句:「當推送的頂端所有提交都已在遠端分支上時,會擋的那幾步 應 跑空範圍並放行」
問題:`code-loop check` 內部不是只用傳進去的 `--diff`。表態閘(表態不完整會擋)在分支不等於主線、且分支頂端不在主線上時,改用自己算的 `主線分岔點..頂端`,只要它跟傳入的範圍不同就重算、重判;表態記錄與留痕都是按「分支名」找的。空範圍 `頂端..頂端` 當然跟它不同,所以空範圍救不了表態閘。
具體例:`git push origin feature:feature-v2`(改名,feature 的提交都在 origin/feature 上、還沒合進主線),feature 的改動帶有適用的效能檢核題。傳 `頂端..頂端` 進 check,tier 判 standard、新增告警閘沒東西查,但表態閘重算分岔點範圍,找不到分支 `feature-v2` 的表態記錄,回 blocked(「分支 'feature-v2' 還沒有表態記錄」)。實際:擋下;S3 預期:放行。
補充:同一個問題讓做法 3 那句「因此是同一個範圍算出來的」也不成立:check 內部至少有三個範圍(傳入的 diff 管波及/tier/新增告警,分岔點範圍管表態)。S3 只在「合進主線的分支改名」那種表態閘自己早退的情況成立,測試若只造那種就是假綠。
引句:「因此是同一個範圍算出來的(改之前一個空樹、一個真起點會不一致)」
file: `scripts/lumos:45168-45171`(表態閘自己的範圍與 `!= diff_range` 重算)、`scripts/lumos:44896`(`_codeloop_read_dispositions(repo_root, marker_branch)` 按分支名讀)
註:這條行為改前改後一樣,不是新增退步;問題在 spec 把它寫成會放行並要綁測試。

## F4 「CI 也照查」的前提在 feature 分支上不成立
severity: minor
blocking: 否(天花板已承認一半,但理由句有事實錯誤)
段落:實務隱患第二條。
引句:「那些提交在任何遠端分支上就不算這次的新改動,本機不再查——它們被推上遠端那次已經過那個人的推送前掛鉤,CI 也照查」
問題:兩半都有洞。(a)掛鉤自己教的逃生路 `--no-verify`(同檔 code-loop 擋下訊息)讓提交上遠端卻沒過掛鉤;(b)CI 的 code-loop 步只在 `push` 到 main 時跑(`if: github.event_name == 'push'`,且觸發分支只有 main),PR 事件不跑,feature 分支推送根本不觸發。所以「別人用 --no-verify 推上去的未審提交」在堆疊分支首推時被排除,要等整批合進 main 才被 CI 抓(且是事後)。這跟 `_codeloop_marker_skipped` 註解自己寫的「feature 分支推上去根本不跑」互相印證。
補:天花板第 1 條改寫成「承認 --no-verify 推上去的提交,在基於它的新分支上要到合進 main 才被查」,別寫 CI 也照查。
file: `.github/workflows/ci.yml:4-7`、`.github/workflows/ci.yml:172-176`

## F5 `--remotes` 不分遠端:推到第二個遠端會被判成「全部已在遠端」而整段放行
severity: minor
blocking: 否(多遠端 repo 才碰到;但範圍是整個放行含不跑全套)
段落:做法 1、實務隱患第三條。
引句:「沒有新提交輸出空字串」
問題:`_PP_REMOTE` 掛鉤手上就有(`scripts/hooks/pre-push:58`),函式沒用它。具體:repo 有 origin(已有這些提交)與 deploy/mirror 兩個遠端,`git push deploy main:main`(新分支或舊值本機沒有)——所有提交都在 origin/* 上,函式回空,會擋的幾步跑空範圍、空範圍判只動文件,不跑全套。改之前這個推送整個 repo 從空樹掃。「推到另一個遠端」是 spec 的「已在遠端」措辭沒涵蓋的語意。
補:至少範圍限定在目標遠端(`--remotes=$_PP_REMOTE`,網址推送時退回現行),或在實務隱患寫明多遠端不適用。

## F6 回退節:計數與步驟與實際交付形狀對不上
severity: minor
blocking: 否
段落:白話、回退。
引句:「退回本案的提交即可:只改推送前掛鉤腳本」
問題:(a)計數:前掃已把「三道」改成「那幾步」(實際五項:波及、風險分級、雙向門、code-loop check、逃逸記帳),白話與回退兩處還寫「三道」;回退照字面做會漏想逃逸記帳也跟著恢復空樹。(b)形狀:本專案交付是功能提交 + 帳本提交(`chore(lumos): 記錄代碼審通過`)+ 合併 PR,「退回提交」其實是退合併提交(要 `git revert -m 1`),事後想再上線修好的版本得再 revert 那次 revert,否則 git 認為已合併、什麼都帶不回來。回退節沒講。(c)同一個提交還動了 Issue 結案與 Systems 筆記,退回會一併把 Issue 改回開、決策紀錄抽掉,對的;但帳本提交與卷證留在原地,綁的是被退回的版本,不影響閘(留痕只認分支名+版本),但值得寫一句免得下個人以為要補。

## 實務隱患逐類(本鏡頭)

- 退回提交後的行為:見 F6;無持久狀態(沒有寫帳、沒有 schema),純腳本退回即恢復;消費專案掛鉤版本分歧是唯一殘留。
- 推送途中同名分支被別人推:git 對非 force 推送會因非快進直接拒絕,掛鉤收到的舊值是 git 連線時的遠端值;spec 的範圍推導只吃這個值與本機物件,沒有 TOCTOU 讓範圍變小的路。force 推送改寫別人剛推的分支,掛鉤範圍只管我方新提交,這不是本案新增(F3 已列未涵蓋的子情況)。已讀,無額外 finding。
- fetch 與推送之間遠端變了:見 F1(過期方向會少擋);本機未 fetch 到新提交只讓範圍變大。
- force-push 改寫已推分支、舊值本機找不到:見 F3、F1。舊值在本機的 force-push(最常見的 rebase 後 force-push)走 `舊值..頂端` 的兩點樹差,rebase 到新主線時會把主線新變更算進來——這是 S4「跟改之前一樣」保留的現狀,不是本案新增,但 spec 的動機(rtb 被 715 條擋)在這條路仍會復現,天花板沒列。已知範圍外,不標。
- 代碼審留痕在新起點下:留痕只綁「分支名 + 版本」(`_codeloop_read` 與留痕有效性只看祖先與純簿記增量),不綁範圍;所以起點改變不會讓既有留痕對不上。改變的是 tier 的判定範圍:首推以前整個 repo 必定 high、一定要留痕,之後只看新提交——這是預期的放寬。留痕對不上的只有 F2 那種「按分支名找」的表態記錄(改名時)。
- 逃逸記帳範圍變小後統計是否失真:查過。`loop escape --auto --range` 用 `git diff --name-only <範圍>` 找碰到的計劃筆記(`scripts/lumos:10956`);改前首推傳空樹會把全 repo 每篇計劃都算碰到,但實查 `docs/.escape-log.jsonl`(91 筆)裡 stage 為 push-gate 的只有 1 筆,所以歷史灌水量小;改後只記真正碰到的計劃,空範圍不記(印「對不回任何計劃筆記」、rc0)。分母是處置閘放行的迴圈、分子是有漏網的迴圈,不受範圍影響。無 finding;唯一要寫的是:若日後 push-gate 筆數變多,2026-10-06 前後的序列口徑不同,看趨勢時要分開。
