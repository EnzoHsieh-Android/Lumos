# 新分支首推會擋的閘改用真起點_計劃

白話:推送前的掛鉤在推「遠端還沒有的分支」時,沒有舊版本可以比,就拿空樹(什麼都沒有)當起點,等於把整個 repo 當成這次的新改動。只提醒的檢查多掃一點無妨,但會擋的那幾道因此誤擋:風險分級被整個 repo 的舊寫法拉成高風險、新增告警閘把全 repo 的舊告警算成新的(rtb 2026-10-06 推 cap-retro 被 715 條擋下)。同一支掛鉤裡「每支檔有家」和「筆記形狀擋」早就改用另一套起點:找出這次要推的提交裡「還不在任何遠端分支上」的最早那一個,從它的上一個提交算起。這次把會擋的三道也改用同一套。

依據:Enzo 2026-10-06 裁「修工具」;rtb 會談同日回報的重現(本機 `lumos code-loop check` 自己算 merge-base 時沒有新增告警、可以推;同一個頂端經推送前掛鉤就被擋)。

PRIOR-ART: 同一支 `scripts/hooks/pre-push` 每支檔有家那段的 `_hrange` 推導(2026-09-11,[[Systems/每支檔有家]]):`git rev-list --topo-order --reverse <頂端> --not --remotes | head -1` 取最早的新提交、`^` 當起點;全部已在遠端就不查;最早那個沒有上一個提交才從空樹比。lumos 那邊 `_lens_push_base` 對全零起點另有一套(跟主線的分岔點),但它對「明寫的空樹」照字面從空樹比——掛鉤傳的正是明寫的空樹,所以改在掛鉤這一層。
RETIRE-IF: 推送前掛鉤的所有閘改走 lumos 的 `_push_range_start`(帶 --push-remote/--pushed-ref,見 [[Issues/推送前其他閘的範圍在合過主線時會多算]] 的收斂路)時,這套掛鉤層的起點推導整段撤掉。

## 範圍

- 做:掛鉤裡把 `_hrange` 的推導抽成一支函式 `pp_block_range_for <遠端舊值> <本地頂端>`(輸出範圍;全部已在遠端時輸出空字串),每支檔有家、筆記形狀擋照舊用它。
- 做:波及計算(`impact_once`;它的結果經 `--from-json` 餵給 `code-loop check` 的受波及合約測試真跑,高風險時會擋)、分支推送時的風險分級(`pitfalls --diff` 的 JSON 那次與高風險列命中那次)、雙向門放行(`spec-gate --push-check`)、`code-loop check`、逃逸自動記帳(`loop escape --range`)改吃 `pp_block_range_for` 的範圍;它輸出空字串(這次沒有新提交)時,這幾道用「頂端..頂端」的空範圍跑(照常走完、沒有改動就沒有東西可擋)。
- 不做:標籤推送那條路的風險提醒(`pitfalls --diff`,只在推標籤時印)、測試分層建議(`test-layers`)、`pp_touched_file`——只提醒不擋,照舊用 `pp_range_for` 寧可多掃。受波及合約測試提醒(`bound_tests_advisory`,只在標籤路徑呼叫)讀的是波及計算那份結果,跟著變小,它只提醒,無害。
- 不做:CI 那邊(CI 傳全零給 lumos,lumos 的 `_lens_push_base` 已經從跟主線的分岔點算,沒有這個誤擋)。
- 不做:存量漂移檢查與回頭重讀守檔筆記(`note-audit reread-check`)(兩者自己帶 --push-remote/--pushed-ref 由 lumos 算起點)。
- 不做:lumos 本體對明寫空樹的處理。

## 做法

1. 新增 `pp_block_range_for`:跟現在 `_hrange` 那段逐字同一套判斷(遠端舊值不是全零而且本機有那個物件 → `舊值..頂端`;否則找最早的新提交,有上一個提交就 `上一個..頂端`、沒有就 `空樹..頂端`;沒有新提交輸出空字串)。每支檔有家那段改呼叫它,行為不變。
2. 迴圈裡算一次 `_brange="$(pp_block_range_for "$_rsha" "$_lsha")"`;空字串時設成 `"$_lsha..$_lsha"`。
3. `impact_once`、分支路徑的兩處 `pitfalls --diff`(JSON 那次與高風險列命中那次)、`spec-gate --push-check`、`code-loop check --diff`、兩處 `loop escape --range` 改吃 `_brange`;標籤路徑那處 `pitfalls --diff` 與 `test-layers` 照舊 `_range`。`code-loop check` 的 `--diff` 與 `--from-json` 因此是同一個範圍算出來的(改之前一個空樹、一個真起點會不一致)。
4. 註解:`_range` 那段原本寫「給波及計算與風險掃描用,只提醒」——風險掃描其實決定分級、會影響擋不擋,改寫成只列真的只提醒的那幾道,並寫明會擋的用 `_brange`。
5. 舊單 [[Issues/推新分支時風險分級拿空樹當起點]] 結案:寫明採用的是哪個方向、為什麼當初擔心的「解析預設分支會變鬆」不適用。
6. 寫回 [[Systems/每支檔有家]](它是推送前掛鉤這段起點推導的家):會擋的閘共用同一支起點函式。

## 實務隱患

- **遠端追蹤分支沒更新**:`--not --remotes` 看的是本機記得的遠端分支;很久沒 fetch 時,遠端其實已有的提交會被當成新的——範圍變大(多擋),不是變小。
- **別人推上遠端、還沒審的分支**:那些提交在任何遠端分支上就不算這次的新改動,本機不再查——它們被推上遠端那次已經過那個人的推送前掛鉤,CI 也照查;跟每支檔有家既有的取捨一樣。
- **全部已在遠端**(例如把已合進主線的分支推到新名字):會擋的那幾步跑空範圍、照常放行;空範圍的風險分級判成只動文件,所以推送前也不跑全套測試——那些提交當初推上遠端時已經跑過、CI 也照跑。舊行為是把整個 repo 當新改動擋下。
- 已排除:金流:只改推送前掛鉤的範圍推導,不碰任何金流
- 已排除:對外送出:不連網、不送任何東西出去
- 已排除:不可逆:只改掛鉤腳本,退回提交即恢復
- 守衛面:會擋的那幾步在新分支首推時看的範圍變小(從整個 repo 變成這次真正的新提交)——是放寬,但放寬的部分正是誤擋;CI 的 code-loop check 照舊當後盾。

## 驗收條款

- [S1] 當推一個遠端還沒有、只比主線多一個乾淨提交的新分支,而主線本身有大量會被當成「新增告警」的舊寫法時,推送前掛鉤 應 放行(不出現新增告警擋下),而且風險分級只算那一個提交 [test:t_prepush_new_branch_block_range]
- [S2] 當新分支裡那一個新提交真的帶進新告警時,推送前掛鉤 應 照擋 [test:t_prepush_new_branch_block_range]
- [S3] 當推送的頂端所有提交都已在遠端分支上時,會擋的那幾步 應 跑空範圍並放行(在有圖譜的 repo 裡跑,含雙向門放行) [test:t_prepush_new_branch_block_range]
- [S4] 當遠端已有那個分支(一般增量推送)時,範圍 應 跟改之前一樣是「遠端舊值..頂端」 [test:t_prepush_new_branch_block_range]

## 回退

退回本案的提交即可:只改推送前掛鉤腳本,退回後會擋的三道恢復從空樹算(新分支首推會再被誤擋)。消費專案要重跑 `lumos update` 才拿到新掛鉤。

## 天花板

1. 起點只看「在不在任何遠端分支上」,不看在不在主線上:基在別人未合併的遠端分支上的提交不算這次的新改動。
2. 本機很久沒 fetch 時會多擋(見實務隱患),要 `git fetch` 之後再推。
