## Finding 1(blocker)— S1 詞表對否定句/反義句一律誤判為承認句,「靠 schema 而非靠自律」會被當成「靠自律」擋下

引句:「命中詞表的行無標記/型別非 A|B|C/B 的 issue 不存在或非 issue/B 的 downgraded 非法或未來日/C 缺欄 → 一條 finding」

**問題**:Check A 的判定只做子字串命中,不做語意/否定偵測。真實 vault 裡已經有句子用「靠自律」來**否定**風險,而不是承認:

```
docs/lumos-toolchain-knowledge/Projects/design-loop判準重定位.md:259:
   不產生這兩個旗標，兩邊靠 schema 而非靠自律隔開。
```

這句的意思是「兩邊靠 schema(機械)隔開,不是靠自律」——正是 Check A 想鼓勵的那種已守住的狀態,但因為字面上出現「靠自律」三字,會被規則判為命中,要求作者在一句**否認風險存在**的句子後面掛 `<!--lumos:risk=A|B|C-->` 標記,語意上不通(這句既不是「天花板」也不是「可機械但未做」也不是「已接受」,它是「已經不是這個問題了」)。詞表沒有任何否定詞/上下文窗過濾,只有「不驗/純靠 需與『工具』『code』同行才算」這一條窄化規則(檢核收緊五件-r1.md:41),完全沒處理否定句。

**file:line 證據**:`docs/lumos-toolchain-knowledge/Projects/design-loop判準重定位.md:259`(真實內容,已用 grep 核實存在)。

**正確的 spec 應該說什麼**:命中規則至少要排除「而非/不是/並非/不靠」等否定詞緊鄰在詞表字串之前的情形,或改成更精確的片語匹配(如只認「靠自律」前面不是「而非/不」)而非裸子字串;否則詞表規模越大,誤傷的否定句就越多,而且無法窮舉否定詞(這本身又是詞表自己承認的 B 型弱點——漏詞只會讓漏抓變多,這裡是相反方向:多抓成誤傷)。

## Finding 3(major)— 歷史 審計修正紀錄/pre-flight 段落敘述已修正的過去式承認,一樣被當活承認掃

引句:「掃描範圍**:`docs/<slug>-knowledge/**/*.md` 的 body(frontmatter 的 summary 行也掃——承認句多在 KEY 行)」

**問題**:vault 裡大量節點的「審計修正紀錄」/「pre-flight」段落是在**敘述過去某輪審計抓到、且已經處理掉**的承認句,時態是過去式陳述,不是現在式的活風險。例如:

```
docs/lumos-toolchain-knowledge/Projects/驗證層去模型化_計劃.md:72:
[major×9] ... 首航排序 honor-system 如實+note 記閘別 ...
docs/lumos-toolchain-knowledge/Projects/oracle品質包_計劃.md:115:
pre-flight(2026-07-29,機械 checklist＋現碼實查) ... ⑥canary-samples 寫入者=編排者人工,明文不驗。
```

兩處都是在記錄「上一輪 pre-flight/審計已經把這件事講清楚、寫死進文件」的**事後留痕**,不是「這裡還沒守住、我還沒決定怎麼辦」。掃描範圍定義裡沒有對 `## 審計修正紀錄`/`pre-flight` 這類回顧性段落做任何排除,且明文連 frontmatter summary/KEY 行都要掃——時態、段落標題完全不影響命中判定。

**file:line 證據**:`docs/lumos-toolchain-knowledge/Projects/驗證層去模型化_計劃.md:72`、`docs/lumos-toolchain-knowledge/Projects/oracle品質包_計劃.md:115`(皆已用 grep 核實)。

**正確的 spec 應該說什麼**:應明列「`## 審計修正紀錄`/`## pre-flight` 標題下的段落屬歷史留痕,不掃」或等同的時態豁免規則,否則每個做過對抗審計的節點,審計紀錄本身就會變成新的違規來源——形成「寫審計紀錄=製造新的 lint 失敗」的倒果為因。

## Finding 4(minor)— S1 詞表定義句本身命中自己的詞表(含 `不驗`+`工具` 同行的邊界條件)

引句:「**詞表** `_RISK_ADMIT_LEXICON`(常數,封閉集):`靠自律`/`honor-system`/`無機械守衛`/`零檢查`/`零實作`/`純靠`/`不驗`(後兩者需與「工具」「code」同行才算,避免誤傷「純靠 hashlib」類句)」

**問題**:這句話本身列出全部七個詞表字串,且同一行裡「不驗」與「工具」也同時出現,滿足 S1 自己定義的「不驗 需與 工具/code 同行」命中條件。這行目前落在 `docs/lumos-toolchain-knowledge/Projects/檢核收緊五件_計劃.md:41`(本文件已存進 vault,`type: project`),沒有任何 `<!--lumos:risk=...-->` 標記。照 S1 硬度規則(不分新舊、任何含命中行的節點硬擋),**定義 Check A 的這份計劃節點本身,會被 Check A 擋下**,除非實作者記得把自己的定義句也標記。這不是孤例——任何未來討論/回報 Check A 誤判(例如本篇對抗審查報告如果進了 vault)都會因為引用這些詞而重新觸發同一個陷阱,形成「講述這個檢查=製造新命中」的自我指涉稅。

**file:line 證據**:`docs/lumos-toolchain-knowledge/Projects/檢核收緊五件_計劃.md:41`(已用 grep 核實此文字含全部七個詞表項且「不驗」與「工具」同行)。

**正確的 spec 應該說什麼**:詞表常數定義處(或明確標記為「元討論」的段落,如反引號包住的詞表字面值列舉)應被排除在掃描之外,否則每次修訂詞表都要記得同步補標,而且會持續產生「討論這個檢查的文件變成它自己的受害者」的維護陷阱。

## Finding 6(major)— 棘輪按累積歷史 commit 數計數,不要求「連續未間斷」,無法分辨「20 次真的沒人理」與「同一節點反覆合規再復發 20 次」

引句:「同一 (gate, node) 在 **≥20 個不同 commit** 出現、且末次出現在最近 7 天內(=仍在被念,非已停止)→ 該 (gate,node) 升級」

**問題**:判準只看「累積命中的相異 commit 數 ≥20」加「最近一次在 7 天內」,完全沒有「這 20 次之間有沒有被處理過又復發」的資訊。E1(失效背書)這種閘的正常生命週期就是:節點被改動 → 綁定的 Verification 變 stale → 有人重跑驗證改回 pass → 之後節點再被改動 → 又變 stale ……這是**正常的維護節奏**,不是「無人處理」。如果同一個節點在半年內被合規處理過 15 次、但因為驗證天生會隨改動過期而又復發了 5 次、最後一次剛好落在最近 7 天內,棘輪照字面判準一樣會判定「升級」——因為它數的是「這個 (gate,node) 出現過幾次」,不是「這個 (gate,node) 有沒有連續被忽視」。這與判準自己給的理由(「=仍在被念,非已停止」)矛盾:「被念很多次」不等於「被忽視很多次」,尤其對本質上會週期性復發的閘(E1)而言。

**file:line 證據**:`scripts/lumos:864`(`if vst in ("stale", "fail", "superseded")` 是每次 doctor 重新求值的現況判定,不是持久化的「未處理計數器」,`scripts/lumos:868-869` 註解本身寫明合法處置是「重跑驗證改回 pass、或改標記/移除該 verified_by」——即這是一個設計上預期會被反覆觸發又反覆解除的閘,不是單調累積的欠款)。

**正確的 spec 應該說什麼**:判準至少要加上「連續性」條件,例如「最近 N 次 doctor --ci 執行中,該 (gate,node) 持續出現、期間沒有任何一次消失」,而不是對全部歷史 commit 數做無視時間結構的累加;否則會誤傷本質上健康、只是週期性復發的閘(E1 就是活生生的反例)。

## Finding 7(major)— 棘輪計「不同 commit」實際是計「不同 push」,節奏估計(「20 個 commit≈2-3 天」)只在高頻推送團隊下成立

引句:「**為什麼是 20**:check-s 本輪清帳前最高 1,003 次原始/420 commit;20 個 commit 在本 repo 節奏約 2-3 天連續推送」

**問題**:`docs/.governance-log.jsonl` 的寫入者只有兩處——`doctor --ci` 與 anchor approve(`scripts/lumos:421-422` docstring「寫者=doctor --ci + anchor approve」)。`doctor --ci` 只在兩個時機被呼叫:本地 pre-push hook(`scripts/hooks/pre-push:148`)與 GitHub Actions CI 的 `push`/`pull_request` 事件(`.github/workflows/ci.yml:5,7,25`)。也就是說,帳裡的 `commit` 欄位不是「每個 git commit 都留一筆」,而是「每次推送當下的 HEAD 留一筆」——如果開發者把多個本地 commit 累積成一次推送才 push,帳裡只會看到一個 commit hash,不會看到中間那些從未推送過的 commit。文件用「本 repo 節奏約 2-3 天連續推送」來校準 20 這個數字,但這個校準只在「幾乎每個 commit 都各自推送一次」的高頻工作習慣下成立;一旦工作模式改成批次推送(例如一天工作結束才 push 一次),同樣的 20 次門檻累積所需的真實時間會遠超過 2-3 天的估計,而軟提醒被忽視的**實質天數**卻可能已經很久——門檻設計把「推送次數」誤當成「時間流逝」的代理,兩者只在特定工作節奏下等價。

**file:line 證據**:`scripts/lumos:421-422`(`_append_governance_log` docstring)、`scripts/hooks/pre-push:148`(`doctor --ci` 呼叫點)、`.github/workflows/ci.yml:5,7,25`(`on: push`/`pull_request` 觸發 `doctor --ci`)。

**正確的 spec 應該說什麼**:门檻文字應明確承認「commit」實際指「推送事件」,並且要嘛改用時間窗(例如「最早出現至今 ≥N 天,且期間至少 M 次不同推送」)取代單純的推送次數計數,要嘛明講這個門檻假設了高頻推送的工作習慣、並定義低頻情境下的等效條件。

## Finding 8(blocker)— 三個逃生口都可由觸發者本人/本 session 自行簽核,無任何身份或第三方驗證,「人明示」在機制上等於「呼叫者自稱」

引句:「S1 標 `risk=A` 即過(最低成本逃生,但留痕);S2 `ratchet_ack` 30 天窗;S3 `external-waived:` note」

**問題**:三個逃生口在實作層面都沒有「誰可以按下這個逃生口」的限制:

- S1:在同一行加一段 HTML 註解 `<!--lumos:risk=A-->` 即過(檢核收緊五件-r1.md:42),寫入者是編輯這份 Markdown 的任何人/任何代理,沒有審核步驟。
- S2:`ratchet_ack` 走 `lumos set`(檢核收緊五件-r1.md:57)。`cmd_set`(`scripts/lumos:7299-7321`)只檢查 key 是否在 `SCALAR_KEYS` 白名單內(`scripts/lumos:7301-7302`)並自驗寫入結果是否符合預期值——**沒有任何身份、審核者、或與觸發該棘輪的 commit 作者不同人的檢查**。一個正在被 `doctor --ci` 擋下的自動化 agent,可以在同一個會話裡直接執行 `lumos set <node> ratchet_ack <gate>@<date>`,自己解除自己剛觸發的硬擋。
- S3:`--note` 是自由文字(`scripts/lumos:14253` `cr.add_argument("--note", help="備註")`,無格式驗證),寫入者是執行 `canary record` 的人/代理本身。

## Finding 9(blocker)— `external-waived:` 是未錨定的子字串比對,討論/引用這個語法本身的 note 就會誤觸發豁免;且「該輪不計入 FAIL」是否等於「單一輪豁免可讓整個合取永遠不 FAIL」未定義

引句:「人明示 `canary record ... --note` 含 `external-waived:<理由>` 的輪不計入 FAIL」

**問題**:兩個獨立缺口:

① **可意外命中**:`--note` 完全自由文字,判準只說「含」`external-waived:<理由>`,沒有錨定位置(行首/單獨 token)、沒有理由最短長度、沒有跟本輪 external 席實際缺席狀態做交叉驗證。如果某位審計員或編排者在 note 裡**描述**這個豁免機制本身(例如寫「本輪外家有到,未使用 external-waived: 語法」),字面上仍然「含 `external-waived:`」這個子字串,會被判定為豁免,即使原意是說明「沒有豁免」。本文件自己第 65 行的原句就是這個字串最現成的來源——任何把這句話貼進 note 當參考說明的行為,都會意外滿足判準。

② **豁免範圍未定義**:S3 的 FAIL 判準是「最後 K 輪(K=2)內至少一輪有 external」,豁免規則說「豁免的輪不計入 FAIL」。這句話至少有兩種讀法都合語法但後果天差地遠——(a)豁免的輪從 K 輪視窗裡剔除,視窗縮成只剩另一輪,仍要檢查那一輪是否有 external;(b)豁免的輪本身「不算數」意味著只要 K 輪裡有任何一輪被豁免,合取就直接不 FAIL,不再要求另一輪真的有 external 出席。文件沒有寫清楚是哪一種。如果是讀法 (b),則**連續兩輪都沒有外家席**,只要其中一輪的 note 裡有 `external-waived:` 字樣,整個 fail-closed 合取就永遠不會 FAIL——這正好是這條閘存在的目的(逼外家席真的出現)被單一自報字串完全繞過,而且這個結果與本文件自己在同一段承認的立場衝突(「與派工編制資料化 v1『觀測恆 rc0』明確相反,本案即該案預告的『進閘另立案』」)。

**file:line 證據**:`scripts/lumos:14253`(`--note` 無格式/內容驗證);檢核收緊五件-r1.md 全文對「該輪不計入 FAIL」未給出視窗剔除或直接短路兩種語意的判準式或偽代碼。

**正確的 spec 應該說什麼**:① 判準應改成錨定格式(例如整個 note 必須以 `external-waived:` 開頭,或至少限定為獨立一行/固定前綴 token),並要求非空理由有最短長度;② 明確寫出豁免的計算式,例如「若某輪被豁免,則從 K 輪視窗中剔除並要求視窗內其餘輪仍至少一輪有 external;若視窗因此變空,整體仍 FAIL(不得因為兩輪都豁免就直接放行)」,避免「一輪豁免=永遠不擋」的退化解。

## Finding 10(major)— 綜合:文件自己承認的「逃生口太便宜會被濫用」風險沒有機制上的因應,只有事後量測,合規成本 > 逃生成本的結構仍然成立

引句:「反向風險:逃生口太便宜會被濫用(人人標 A)——退場條件裡「詞表漏抓 ≥3」與「ack ≥50%」就是在量這個」

**問題**:文件確實注意到這個風險並承認(檢核收緊五件-r1.md:123),但因應方式是**上線 90 天後回看**的落後指標(退場條件表,檢核收緊五件-r1.md:93-97),不是上線當下就存在的機制性摩擦。結合 Finding 8/9(逃生口可自簽核、`external-waived:` 可被無意間觸發、S1 標記只是同一行加一句註解無需佐證),三件硬擋的**實際邊際成本**排序是:

- 真合規:S1 要正確判斷 A/B/C 型別並(B 型)開真 Issue 或降級散文措辭;S2 要真的處理掉底層軟提醒;S3 要真的找到外家席出席。
- 逃生:S1 一行 HTML 註解;S2 一次 `lumos set`;S3 一句 note 文字含特定子字串。

三個逃生口都比對應的真合規動作便宜至少一個數量級,且都可由同一個被擋下的呼叫者自己執行(Finding 8),在 90 天回看之前沒有任何機制阻止「先逃生、之後再說」成為預設路徑。而 90 天後的退場判準(「ack ≥50%」「詞表漏抓 ≥3」)本身量的是**事後统计信号**,不是事前阻擋——即使濫用被偵測到,結論也只是「調整門檻」或「承認某道軟提醒該整個退場」,不會回溯處罰已經逃生過的個案。這與本案的立案動機(「打我臉的那些,我要有足夠好的優化方法」「功能越改越多,但檢核卻越來越寬鬆」)直接衝突:三道號稱「硬」的閘,在自我簽核零門檻的前提下,防的只是「懶得寫一行註解/一次 set/一句 note 的人」,防不住「原本就打算蒙混過關」的行為者——而這正是七張自我批判單想堵住的那種行為者。

**file:line 證據**:綜合 Finding 8、9 與 檢核收緊五件-r1.md:93-97(退場條件表僅在 90 天後量測,無即時攔阻機制)。

**正確的 spec 應該說什麼**:至少一道逃生口應該要求「與觸發者不同的身份」或「額外的最小舉證」(例如 S1 的 risk=A 標記若配合既有的節點作者/簽核欄位做交叉比對;S3 的 waiver 要求引用具體的 dispatch 檔缺席證據而非自由文字);否則應在文件裡誠實承認這三道「硬擋」對蓄意規避者而言防禦力等同於零,只對無心疏漏有效,並相應調整它們在 Growth test 裡「真事故」論證的份量。
