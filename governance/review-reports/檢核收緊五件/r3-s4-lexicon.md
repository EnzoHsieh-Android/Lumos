## Finding 1(blocker)——`_strip_fences_text` 回傳值丟棄原始行號,spec 指名的實作路徑會讓 finding 訊息回報錯的行

引句:「先經 `_strip_fences_text`」(同段後文:「再逐行比對。★不做區段標題豁免★」,line 51——完整句子中段夾★標記,故引句取不夾★的前段,語意見下方分析)

`_strip_fences_text(text)`(scripts/lumos:1559-1566)實作是 `"\n".join(ln for _no, ln in _visible_lines(text.split("\n")))`——**只回傳字串,丟掉每行的原始行號 `_no`**。它底下的 `_visible_lines()`(scripts/lumos:1535-1557)本身是有保留 `(lineno, line)` tuple 的正確原語,`cmd_search` 用的 `_search_visible_lines`(scripts/lumos:1569-1582)也正確地把 `_no` 傳下去給呼叫端——但 spec 指名要呼叫的是**不保留行號**的 `_strip_fences_text`,而非保留行號的 `_visible_lines`。

spec 判定條款要求「finding(訊息含 rel:line 與命中詞)」(line 57)。任何依 spec 字面「先 `_strip_fences_text` 再逐行比對」寫的實作(對回傳字串 `.split("\n")` 後 `enumerate`,這是最自然、我在對抗腳本裡也這樣寫的做法),算出來的「行號」是**去掉圍欄行之後的第幾行**,不是原始檔案的第幾行。凡是命中行**之前**存在任何圍欄(不論開闔),回報的行號就會偏移。

實測(對本節點自己跑):

```
orig total lines: 124
visible total lines: 119
orig line 91: '| S1 | ...★這條人工盤點本身靠自律★ <!--lumos:risk=A--> |'
same content found at VISIBLE line 86
```

`docs/lumos-toolchain-knowledge/Projects/檢核收緊五件_計劃.md` 原檔 124 行,經 `_strip_fences_text` 後只剩 119 行(詞表圍欄整整 5 行——3 行內容+頭尾兩個 ``` 標記行——被整個丟掉,不是留白佔位)。真正的承認句「這條人工盤點本身靠自律」在**原檔第 91 行**,但依 spec 字面路徑算出來的行號是 **86**——差 5 行,剛好等於詞表圍欄的行數。這不是本節點特有的巧合:任何節點只要在命中行**之前**出現過至少一個圍欄(mermaid 圖、程式碼範例……本 vault 很常見),Check A 印出來的 `rel:line` 就會指向錯的行,而且偏移量隨圍欄位置變動、無法從訊息本身察覺出「這是錯的」。這正是複審指令要抓的「讓硬閘悄悄失準」的一種——閘確實會 FAIL/印 issue(不是沒觸發),但**證據指錯地方**,人去修的時候會對著錯誤行號找不到東西,或改到不相干的行。

**正確規則**:掃描實作必須直接呼叫 `_visible_lines(text.split("\n"))`(保留 `(lineno, line)`),自行組出「可見行對應原始行號」的映射,而不是呼叫 `_strip_fences_text` 再對回傳字串重新編號;或者比照 `_search_visible_lines` 的既有寫法(scripts/lumos:1569-1582)——本庫已經有一份行號正確的參考實作可抄,S1 卻指名了不保行號的那支。

## Finding 2(blocker)——標記文法未定義「同一行多個標記/多個命中詞如何配對」,自然實作會把第二個標記吞進第一個裡

引句:「值一律雙引號,允許任意中文與空白」

spec 明講標記值「允許任意中文與空白」(line 52),也就是 `why="…"`/`revisit="…"` 的值**可以含空白**——這代表任何用「以空白切 token」方式(例如 `(?:\s+\S+)*` 這種最自然的『屬性清單』正則寫法)去抓「標記到 `-->` 為止」的實作,天生沒有能力分辨「值裡的空白」跟「兩個獨立標記之間的空白」。

用這個最直白的文法(`MARKER_RE = <!--\s*lumos:risk=(A|H|B|C)((?:\s+\S+)*)\s*-->`,`ATTR_RE = (\w+)="([^"]*)"`)去解 spec **自己的**退場條件 S1 列(`docs/lumos-toolchain-knowledge/Projects/檢核收緊五件_計劃.md:91`,原文一字不改):

```
| S1 | ... <!--lumos:risk=C why="負事件無法由命中型檢查自記,結構限制" revisit="若 Verification 盤點出漏抓 ≥3 則補詞表或改只列"-->;★這條人工盤點本身靠自律★ <!--lumos:risk=A--> |
```

實測結果(python `re` 標準庫,greedy 語意,`.search()`):

```
matched span: (121, 242)
matched text: '<!--lumos:risk=C why="..."  revisit="..."-->;★這條人工盤點本身靠自律★ <!--lumos:risk=A-->'
does the match consume the SECOND marker too? -> True
```

單一 `.search()` 呼叫回傳的「一個標記」,**整段吞掉了中間的中文散文與第二個 `<!--lumos:risk=A-->`**,因為 greedy 量詞會一路吃到最後一個 `-->` 才回溯。這一行本來是作者刻意寫的**兩個獨立標記**(C 管「漏抓不可量」那句、A 管「人工盤點本身靠自律」那句),解析後卻被壓成「一個 C 型標記,附帶一坨吞進去的垃圾內容」——`ATTR_RE.findall` 照樣能抽到 `why`/`revisit`(因為它們在被吞的範圍最前面),所以本例剛好「意外」判定為合法通過;**但這是運氣,不是規則保證的**。只要把兩個標記順序對調、或第一個標記本身缺一欄(見下方構造案例),同一種吞噬會讓第二個本來合法的標記整個從檢查員視野消失,而輸出的判定訊息只會提到第一個標記的型別:

```python
line = ('這段先講漏抓限制 <!--lumos:risk=C why="only-why-no-revisit"--> '
        '然後才是本案人工盤點本身靠自律 <!--lumos:risk=A-->')
# .search() 仍然把整行吞成一個 match,分類結果 = MALFORMED(缺欄)
# —— 後面那個語法完全合法的 <!--lumos:risk=A--> 從沒被看見過
```

spec 判定條款「命中行無標/型別外/A、H 帶欄/…→ finding」(line 57)是**行級別**的判定,完全沒有講「一行如果有兩個標記、兩個命中詞,怎麼配對」——測試策略 #1-10(line 101)也沒有任何一條測到多標記同行。但 spec **自己的**退場條件表恰好就是這個場景的活例:S1 列必須同時用 C(承認「漏抓不可機械量」的結構限制)和 A(承認「人工盤點」本身又是一句承認句)兩個標記才說得完整。這代表這個未定義場景不是理論邊角,是本文件自己第一個要上線的節點就會撞到的真實輸入。

**正確規則**:標記文法必須明確定義成「不吃跨標記邊界」的形式(例如逐一 `re.finditer` 找出每個 `<!--lumos:risk=...-->` 起訖、屬性只用 `(?:\s+\w+="[^"]*")*` 這種**明確 key=value 重複結構**去比對,而非泛用 `\S+` chunk),並且明確定義「一行多個命中詞 × 多個標記」時的配對規則(逐個標記各自管它相鄰的哪些命中詞?還是「行內任一合法標記即整行過」?)——目前兩者都沒有,行為完全取決於實作者當下怎麼寫正則。

## Finding 3(major)——`why=`/`revisit=` 值遇到值內字面 `"` 會靜默截斷,牴觸測試策略 #9 的宣稱

引句:「why 含空白/中文/等號/引號內 `-->` 以外字元皆解析」

測試策略 #9(line 101)的字面主張是:why 值裡「除了 `-->` 以外」的字元(空白/中文/等號……)都能正確解析。實測發現這個宣稱**不成立**——字面 `"` 字元同樣會壞,而且測試 #9 完全沒把它列進已知例外:

```python
line = '零檢查 <!--lumos:risk=C why="含引號\"的值" revisit="ok"-->'
# ATTR_RE = (\w+)="([^"]*)"  —— 無跳脫機制
# 解析結果: {'why': '含引號\\', 'revisit': 'ok'}
```

`[^"]*` 在遇到值裡任何一個字面 `"` 就立刻停止——因為 spec 全文(line 52-56)沒有定義任何跳脫語法(沒說 `\"` 是跳脫,也沒說禁止值內出現 `"`)。後果:
- 值本身被靜默截斷成垃圾內容,但**因為截斷後仍非空字串**,C 型「兩欄非空」的合法性檢查照樣判過——`--ci` 不會報,人也看不出這行的 why/revisit 已經跟作者原意不一樣了。這正是本文件在別處反覆強調的「宣稱有守衛、實際沒有」同一種病(對照 `Issues/寫下風險當成處理風險.md`)。
- 更壞的情況(未在 60 筆現有命中中出現,但語法上完全可能):如果 `"` 出現在 why 值的**前段**、離 revisit 欄較近,截斷可能連帶讓 `revisit=` 屬性配對錯位或消失,C 型判定從「合法」翻成「缺欄」——這時是**錯的擋**(wrong gate decision),不只是內容髒了。

**正確規則**:測試策略 #9 的敘述需要改成「除了 `-->` **與 `"`** 以外的字元皆解析」,並且要嘛①在文法上禁止值內出現 `"`(掃描時遇到值域含裸 `"` 視為格式非法,直接判 finding,而非靜默接受截斷結果)、要嘛②定義真正的跳脫語法(如 `\"`)並在 `ATTR_RE` 對應處理——目前兩者皆無。

## Finding 4(major)——`issue="Issues/<stem>"` 靠 `by_stem` 解析,但 `by_stem` 不認資料夾、多值時選哪個未定義

引句:「stem 經 `by_stem` 解析到存在節點且 `type: issue`」

`build_index()`(scripts/lumos:230-234)建出的 `by_stem` 是 `defaultdict(list)`,鍵是 `n.stem.lower()`(**純檔名 stem,不含資料夾路徑**),值是**符合該 stem 的全部 rel 清單**——本身就允許同一個 stem 對應到不同資料夾底下的多篇筆記。這不是理論可能性,本 vault 現在就有真實碰撞(`find . -name "*.md" | sed 's#.*/##; s/\.md$//' | sort | uniq -d` 實測):

```
診斷迴圈先行     → Systems/診斷迴圈先行.md
自主loop加法偏食  → Issues/自主loop加法偏食.md
... 共 19 組同名 stem
```

而且本專案自己已經在 `env.find()`(scripts/lumos:294-303)承認「同名筆記解析歧義」是設計上要處理的既知狀況,處理方式是——`print(f"⚠ 同名筆記 {len(hits)} 個,取第一個: {hits[0]}", file=sys.stderr)`——**取第一個、印警告**,而非拒絕解析。`run_doctor` 的 Check G(scripts/lumos:620-625)也專門為此開了一段「同名 basename 守衛」,說明碰撞在這個 vault 是活生生會發生的事,不是邊角案例。

spec 對 `issue="Issues/<stem>"` 的解析規則只講了兩件事:①字面必須以 `Issues/` 開頭(r2 s4-F6,拒絕裸 stem)②`stem` 經 `by_stem` 解析到存在節點且 `type: issue`。**它完全沒講**:
1. 如果 `by_stem[stem]` 回傳多筆(碰撞),挑哪一筆?(照 `env.find()` 的既有慣例是「取第一個」——但 `by_stem` 的清單順序來自 `load_vault()` 對 `vault.rglob("*.md")` 的**字母序**走訪,`Issues/` 資料夾不保證排最前面)
2. 解析出來的那個節點,是否真的要驗證它的 **rel 路徑以 `Issues/` 開頭**?spec 字面規則完全沒有這一條——只驗 `type: issue`,不驗路徑。也就是說,只要某個 `type: issue` 的節點恰好跟 `Projects/`、`Systems/`……底下某篇筆記同 stem(而且它剛好不是那個 issue 節點,是別的同 stem 節點先被 `by_stem` 排到前面),marker 上寫著 `issue="Issues/<stem>"`(文法上合法、`Issues/` 前綴也對)卻可能解析、驗證到**完全不是使用者以為的那篇 Issue**,而 Check A 對此毫無感知——它只看「有沒有解析到一個 `type: issue` 節點」,不看「這個節點是不是真的叫這個名字的那篇」。

r2 s4-F6 修的是「不接受裸 stem」這個**書寫格式**問題,不是「解析結果保證對得上作者寫的路徑」這個**語意**問題——`Issues/` 前綴目前只是裝飾性文字,`by_stem` 本身完全不感知路徑。

**正確規則**:解析後必須額外檢查 `resolved_rel.startswith("Issues/")`,且 `by_stem` 回傳 >1 筆時必須視為**不合法**(fail-closed,印「stem 碰撞,無法唯一解析」)而不是沿用 `env.find()` 的「取第一個」慣例——那個慣例是為了連結解析的舊行為相容,不適合用在一個要決定「這行承認句算不算被正式登記」的硬閘上。

## Finding 5(minor)——否定前綴「命中詞前 6 字內」的邊界讀法未測,構造案例顯示會漏抓 2 字詞的貼界情形

引句:「命中詞前 6 字內出現即不算」

測試策略 #6(line 101)只測了零距離的最小案例(「而非靠自律」——否定詞緊貼在命中詞前面)。用真實語料測試否定窗口,兩個真實案例都測出**正確**行為(否定詞緊鄰時豁免、否定詞其實是在講別的子句時不誤豁免):

```
Issues/寫下風險當成處理風險.md:53  「而非「靠自律」」          → 6 字內含「而非」,正確豁免
Projects/design-loop判準重定位.md:259 「schema 而非靠自律隔開」  → 6 字內含「而非」,正確豁免
Projects/design-loop輕量檔_計劃.md:72 「不是準確度…純靠人記得」  → 6 字視窗未含「不是」(距離 10 字、且語意上「不是」本來就是在否定
                                                                     「準確度」而非「純靠」)——正確不誤觸
```

但用構造案例逼近邊界,發現「命中詞前 6 字內」若照最自然的『子字串完整落在 6 字視窗內』寫法(`tok in line[start-6:start]`),對 2 字否定詞(不是/而非/不再/不靠)有整字截斷的邊界:

```
"不是" + 4 個填充字 + 命中詞  → 視窗="不是XXXX"(6字,完整含"不是") → 正確豁免
"不是" + 5 個填充字 + 命中詞  → 視窗="是XXXXX"(6字,"不"被切掉)   → 不豁免(誤判為現行承認句)
```

`不是` 起點距命中詞第 7 字時(比 spec 字面「前 6 字內」多 1 字),因為詞表裡沒有把裸「不」單獨列為否定詞(只有完整的「不是/不再/不靠」),視窗一旦連 token 的頭一個字都切不到,整個 2 字詞就完全偵測不到——即使直覺上「否定詞出現在命中詞前面沒幾個字」的精神仍然成立。這個邊界目前的行為(照字面最自然實作)是「未豁免」而非「豁免」,所以不是會放過真承認句(不是安全性問題),而是可能對已經用「不是/不再/不靠」表達否定、但中間多插了幾個字修飾語的真實句子**誤判成需要標記的新承認句**——雖然目前 60 筆命中裡沒有真的踩到這條線,但測試策略 #6 沒有覆蓋這個邊界,以後新句子踩到算誰的責任不清楚。

**正確規則**:測試策略 #6 應該加一條邊界案例(否定詞恰好卡在 6/7 字分界),並且明確裁決「6 字」量的是「否定詞起點」還是「否定詞整體必須完全落在視窗內」——目前實作與規格文字都沒有回答這個問題。

## Finding 6(minor)——「存量 61 行命中」是舊規則(v2)量出來的數字,沒有照 v3 最終規則重新驗證過

引句:「r2 s4 席拋棄式腳本實測 61 行命中」

`r2-s4-lexicon.md`(前一輪報告)量出的「61」是用 v2 規則(含區段標題豁免、且用一份近似版 fence-strip)掃出來的。v3 已經撤銷區段豁免、改用真正的 `_strip_fences_text`、掃描範圍明確納入整份 frontmatter(含 `decisions[].content`/`why_chosen`)——這些改動理論上會**增加**命中數(撤區段豁免、加掃 frontmatter),但本輪用真正的 `scripts/lumos._strip_fences_text` 對同一個 vault 實掃,得到的是 **52 相異行 / 60 處 term-occurrence**,跟寫在文件裡的「61」對不上(且「61」是按「行」數,「52」也是按「行」數,兩者是同一口徑卻不同答案)。

這不影響 v3 設計本身的正確性——「存量」段已經明講「實作時以上述規則實掃」,承認這只是一個要在實作階段重跑的暫定數字。但這份文件在別處(`_strip_fences_text` 的 docstring,scripts/lumos:1500 一帶)明確記著自己吃過「把審查員報告裡的數字直接抄進 docstring、沒有自己量」的虧,而這裡「61」正是同一種未重新驗證就沿用的數字,寫進了同一份即將進圖譜的文件裡。

**正確規則**:「存量」段的數字要嘛拿掉具體數字只留「以下規則」的敘述(反正實作時要重算),要嘛真的照 v3 最終規則(不是 v2 規則)重跑一次再寫進文件——目前的「61」介於兩者之間,看起來像已驗證但其實是舊規則的殘留。

## 已驗證、無需 finding 的檢查點

**dual-entry:`cmd_lint` 對 `notes`/`by_stem` 的存取權**——`main()`(scripts/lumos:14201 起)對整個 vault 只建**一個** `Env(vault)` 實例(如 scripts/lumos:14802),`cmd_lint(env, node)`(scripts/lumos:2600)拿到的就是這同一個 `env`,`env.notes`/`env.by_stem` 涵蓋全庫,不是只載入被 lint 的那一篇。也就是說「單檔快檢」只是**檢查範圍**限定單檔,底層資料仍是全庫索引——`cmd_lint` 與 `run_doctor` 對跨節點 `issue=` 解析有完全相同的存取權,沒有雙入口不對稱的問題。
