作為外部否決席，我對本案的「硬擋」邏輯與「存量」假設提出以下 5 條審查意見。本案存在嚴重的「冷啟動死鎖」與「指標漂移」風險，若照字面實作，將導致新專案無法啟動或因開發習慣（如頻繁 commit）導致非預期的流程中斷。

### 1. S3 外家席：初始輪次的「冷啟動」邏輯死鎖 (Major)
引句：「最後 K 輪(K=2)內至少一輪有 ≥1 席 family=external,否則合取 FAIL」
**風險描述：** 照字面實作，一個全新的 `code/high` 專案在第 1 輪（Round 1）執行時，其「最後 2 輪」僅包含自己。若該輪因排班或緊急程度未排入外家席，判定條件（1 輪中 0 席外家）會立即觸發 FAIL。這導致所有高階專案**第一輪必須強制有外家**，否則連啟動都無法通過閘口，完全沒有緩衝空間。
**建議：** 應修正為 `min(current_round, K)` 或明確定義 `Round < K` 時的寬限邏輯。

### 2. S2 棘輪：以「Commit 數」作為無視程度的度量誤判 (Major)
引句：「同一 (gate, node) 在 ≥20 個不同 commit 出現」
**風險描述：** 該判準假設了 commit 頻率與時間流逝成正比（spec 稱 20 commit 約 2-3 天）。但在實際開發中，開發者進行重構、修復 typo 或在 feature branch 頻繁推送時，可能在 **1 小時內產生 20 個 commit**。照字面實作，一個剛發生的軟提醒會在極短時間內被「意外」升級為硬擋，違反了「長期未處理」的初衷。
**建議：** 判準應改為「跨越至少 N 個自然日」且「commit 數 ≥ M」。

### 3. S1 Check A：詞表擴充導致的「存量回溯」崩潰 (Major)
引句：「對任何含命中行的節點硬擋(rc1),不分新舊——因為本案實作時存量全部補標」
**風險描述：** 這是架構假設錯誤。Spec 假設「現在」補標完後存量就清零了，但 S1 退場條件提到「詞表漏抓 ... 補詞表」。一旦未來詞表（Lexicon）增加新詞，原本通過檢查的數千個舊節點會因為含有新詞而**集體在 CI 爆發 rc1**。由於 spec 明確「不分新舊」，這將迫使開發者在處理新任務時，必須先幫全庫補標，造成工作量突發性膨脹。
**建議：** 應引入與 lint 慣例一致的 `cutoff` 機制，僅對新變動行或新節點執行硬擋。

### 4. S3 豁免機制：操作時機的「雞生蛋」死鎖 (Major)
引句：「人明示 canary record ... --note 含 external-waived:<理由> 的輪不計入 FAIL」
**風險描述：** `canary record` 通常發生在該輪結束或產生 findings 時。若 `loop status` 因無外家席已處於 FAIL 狀態，且該狀態會硬擋後續動作（如 `loop next` 或 `deploy`），開發者可能根本無法抵達能夠執行 `record --note` 的階段。照字面實作，豁免機制可能因「閘口已關閉」而無法被寫入，導致流程卡死。
**建議：** 豁免標記應允許在 `loop dispatch` 階段或透過 `lumos set` 獨立寫入。

### 5. S1 Check A：Frontmatter 掃描的語法誤傷 (Minor)
引句：「docs/<slug>-knowledge/**/*.md 的 body(frontmatter 的 summary 行也掃」
**風險描述：** Spec 要求掃描 frontmatter 的特定行，但未規定使用 YAML parser。若照字面實作「逐行掃描詞表」，當詞表包含「不驗」等詞時，若 frontmatter 的其他 Key（如 `related:` 或 `tags:`）或自動生成的 ID 恰巧包含這些字元片段，會觸發誤報。
**建議：** 應明確要求僅針對 YAML 解析後的 `summary` 欄位值進行檢查，而非純文字行掃描。

**審查結論：** 
本案在「自動化收緊」的目標下，忽略了**存量演進**與**流程初始狀態**的邊界情況。特別是 S1 的存量假設與 S3 的初始輪次判定，若不修正將造成嚴重的開發阻礙。建議修正 S1 為 `cutoff` 制，並放寬 S3 在專案初期的判定門檻。(純格式正規化:粗體標籤→裸標籤,內容未動)
