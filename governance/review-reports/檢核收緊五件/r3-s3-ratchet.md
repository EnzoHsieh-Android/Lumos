## Finding 1 — blocker:`_append_governance_log` 對零 events 直接 return,「完全乾淨」的 run 在帳本裡不留任何痕跡——一旦某鍵被修好且此後長期無其他閘同時觸發,棘輪永遠無法確認「已清」也無法繼續累積

引句：「一個 commit 內**至少含一筆 `gate` 以 `check-` 開頭的事件**才算一次 doctor run」

**錯在哪**:`_append_governance_log`(`scripts/lumos:421-423`)開頭即 `if not events: return`——當 `run_doctor` 本輪 `gov_events` 為空(所有七道棘輪輸入閘全部乾淨、零警告)時,函式**不寫任何一行**,連 commit/ts 都不留。而 v3 把「run」定義成「commit 內至少含一筆 `check-` 開頭事件」——這正是該函式**唯一會寫入**的事件類型。兩者疊起來的結果是:一次「doctor --ci 跑過、而且全綠」的執行,在帳本上與「doctor --ci 根本沒跑過」**完全無法區分**,因為兩者都是零行。

後果:假設某鍵 K 已連續出現 19 次 run(即將撞頂),下一次 commit 若全庫恰好完全乾淨(K 已修好,且**同時**其餘六道閘也都沒響)——這次執行完全不留痕,不會被算成「第 20 次 run」,也不會被算成任何「run」。往後只要沒有其他閘再度觸發(check-s/check-e1 目前確實常態性頻繁觸發,但不保證永遠如此,尤其正是本案想追求的「檢核收緊→問題被修掉→閘安靜下來」這個成功結果本身),ledger 就永遠不會再產生新的 `check-*` 事件,`最近 20 次 run` 這個窗口就此**凍結在最後一次有事件的舊 commit**——K 的「已清除」狀態永遠無法被觀測到、也沒有任何新 run 可以讓其他鍵繼續累加。換言之:**機制設計的終極成功狀態(全綠、無提醒)恰好是這套棘輪徹底停擺的觸發條件**——這與 S2 立案要解決的「問題被無視卻沒人發現」目標背道而馳,只是換了一種靜默失效的形式(從「軟提醒被無視」變成「棘輪本身失去感知能力」)。

**正確規則**:「run」的定義不能建立在「該執行**恰好**產生了 check-* 事件」這個偶然條件上;要嘛 `_append_governance_log` 在 `--ci` 模式下**即使 events 為空也要寫一筆哨兵行**(例如 `{"gate": "ci", "kind": "ran"}`,注意 `_KNOWN_GATES` 已有 `"ci"` 這個既有 gate 可能可以借用其語意,需查證是否衝突)以標記「這是一次乾淨的 run」,棘輪的 run 邊界改用這個哨兵而非「至少一筆 check-* 事件」;要嘛在文件裡明講並接受「全綠時棘輪停止感知,直到下一次任何一道閘再度觸發」這個限制,而不是把它當成已解決的問題悄悄放行。

## Finding 2 — major:同一 commit 被 doctor --ci 執行多次(常態,真帳可實證),v3 未定義「該鍵在此 run 是否出現」要用「聯集」還是「最後一次執行」——若implement 走最自然的字面讀法(聯集/任一事件即算出現),已修好的鍵會被同 commit 內較早的失敗執行「拖住」

引句：「run 依**帳本 append 序**(★不 ts 排序,r2 s1-F3/s2-F3:既有慣例且 ts 只到秒★)。」

**錯在哪**:v3 把「run」定義在 commit 粒度,但同一個 commit 在真實工作流裡完全可能被 `doctor --ci` 執行不只一次——這不是假設,真帳裡可實證找到三個案例:

- commit `3aa86d2`:2026-07-26、2026-07-28、2026-07-30 三個不同日子,各自留下一段 `check-s` 事件(帳本行 7596-7603 / 7622-7629 / 8188-8195)——**同一 commit 橫跨 4 天被跑了 3 次**。
- commit `c46905e`:2026-08-09、2026-08-11 兩個不同日子(帳本行 14592-14649 / 15765-15822)。
- commit `5c21803`(**本輪帳本最新一筆,今天**):`2026-08-21T12:57:35+08:00` 與 `2026-08-21T13:02:18+08:00`,相隔 5 分鐘各跑一次,兩次都在 `check-e1` warned 同一組 5 個節點——即題目問的「doctor --ci 跑兩批,算一次還是兩次」場景此刻正在真實帳本裡發生。

v3 對此**只回答了「run 邊界」問題**(同 commit 算一次 run,不管內部幾次執行),卻沒回答**「run 內容」問題**:當同一 commit 的多次執行結果不同(例如第一次還警告某鍵、第二次(vault 已改過但未 commit)已經修好)時,判斷「鍵 K 是否出現在此 run」要看「這個 commit 底下**任一**筆事件有沒有 K」(聯集,最自然的字面實作)還是「**最後一次**執行的結果」?文件對此完全沒有著墨。若走聯集(最容易被字面實作出來的版本),一個鍵在同 commit 內先警告、後修好,仍會被判定為「此 run 出現」——直接違反「最新 run 不出現 → 不升(剛清的不升)」這條 v3 自己反覆強調的正確性保證,只是延後整整一個 commit 週期才生效。目前三個真實案例的兩批/三批內容剛好逐字相同(未實測到分歧),但這只是「同 commit 沒 diff、內容不變」的巧合,不代表機制對「內容有變」的 case 有定義——而 `5c21803` 這筆恰好證明「同 commit 多次執行」在此專案是活躍、非邊角的模式(今天才剛發生)。

**正確規則**:v3 需要明講「run 內某鍵的出現判定 = 該 commit 下**最後一批**(append 序最晚的)`check-*` 事件裡有沒有這個鍵」,而非任一事件即算,並補一條測試:同 commit 兩批執行、前批警告後批已清 → 該 run 判定該鍵「不出現」。

## Finding 3 — major(escalated from r2 s3 minor,r2→v3 未修):ack「本地日期」30 天到期沒有指定用哪個時鐘,而這個專案曾經在同一類問題(UTC ts vs 本地日期混用)上真的中過一次、且 CI 與本機時區確定不同——v3 對此欄位完全沒有 S1 `downgraded=` 已附的時區風險註記

引句：「元素 `"<gate>@<YYYY-MM-DD>"`(本地日期);30 天內不升」

**錯在哪**:r2 s3 report 的 Finding 3(minor)就已指出 ack 到期沒講清楚用哪個時鐘算,v3 文字對這個欄位**完全沒改**(逐字比對 r2 與 r3 draft,「本地日期」四字原封不動),只是把它從「未指定」的狀態原樣搬進 v3——不是新引入,但也不是被修過,是被跳過的 r2 開放項,終審輪理應收斂而未收斂。

比 r2 時多出的、更有份量的證據:
1. `.github/workflows/ci.yml`(行 900-911)證實真的存在獨立於本機的 CI 執行點——`runs-on: ubuntu-latest`,步驟裡直接跑 `python scripts/lumos doctor --ci`(行 920-921),**沒有設定 `TZ` 環境變數**,GitHub-hosted runner 預設時區是 UTC。而帳本裡本機寫入的 `ts` 帶的是 `+08:00`(如 `"2026-08-21T13:02:18+08:00"`)——確認本機(Asia/Taipei)與 CI(UTC)是兩個不同時鐘,且這條 CI job 的檔頭註解自陳其存在意義正是「本機 hooks 可繞…這裡是 push 後必跑的後盾」(`.github/workflows/ci.yml:3`),即 ratchet 的 `--ci` 硬擋**理應**同時在這兩個時鐘上都給出一致答案。
2. 這個專案**已經真的踩過同一類 bug 一次**:`scripts/lumos:934-937` 的 `[tz 跨日修 2026-07-20]` 註解逐字寫著「ledger ts=UTC(_utc_ts)、ended=本地日期(date.today)——兩時間源混用:台北 00:00-08:00 窗口 UTC 日期仍昨天,raw [:10] 比較誤判…」,並附了對應的既有回歸測試錨點(`t_e2_ledger_tz_boundary`)。這證明「用 `date.today()` 這種機器本地日期,去跟另一個以不同時區寫入的時間戳比對」在**這個確切的程式碼庫**是已知、已發生過、已修過一次的 bug 類別。

S2 的 ack 到期判斷,本質上就是同一種比對(30 天視窗邊界比較),而且比 E2 那次更嚴重——它決定的是一道**hard `--ci` 閘**要不要因為過期而重新開火。若本機 pre-push(+08:00)算出「ack 還在 30 天窗內、不升」,同一支 commit 推上去後 CI(UTC)在台北 00:00-08:00 這段窗口內算出「已經過了 30 天、升級」(或反過來),就會出現本機放行、CI 卡住(或本機卡住、CI 放行)的分裂結果——恰恰是 S2/S3 全案想消滅的「靜默失效」的另一種變體:不是完全不擋,而是**擋不擋看跑在哪台機器**,而且沒有任何提示告訴使用者「這是時區造成的」。對照 S1 的 `downgraded=` 欄位(v3 行 41)明講「不得晚於**執行機器本地日期**;時區差屬天花板,H 標」——即 S1 有意識地把這個風險寫下來當作已知上限;S2 的 ack 欄位处理的是同一種日期比較,卻連這句話都沒有,是兩個並列欄位間對同一類風險的處理不一致,且 S2 這邊風險更高(壓的是 hard gate,不是分類標記)。

**正確規則**:比照 `scripts/lumos:934-937` 已經驗證過的修法(比較點統一換算到同一時區的日期再比較),明講 ack 30 天視窗的計算基準(建議:統一以 UTC 日期或統一以 ack 事件寫入時 `ts` 所帶的 offset 換算本地日期,兩端各自 `datetime.fromisoformat(ts).astimezone().date()` 而非裸 `date.today()` 字串比較),並補一條邊界測試覆蓋台北 00:00-08:00 窗口。

## Finding 4 — blocker:「doctor 最頂端」列印位置在 `run_doctor` 程式碼結構上早於本次執行的任何一筆 check-* 事件被收集,若字面實作,棘輪橫幅顯示的「N 項」不可能反映本次 run 自身的結果——直接牴觸「最新 run 不出現 → 不升(剛清的不升)」這條 v3 一再強調的正確性保證

引句：「doctor 最頂端(vault 行後、首個 `[` 段前)印「」

**錯在哪**:v3 明講(行 68)棘輪橫幅要印在「vault 行後、首個 `[` 段前」。實際對照 `run_doctor`(`scripts/lumos:446-`):

```
450:    print(f"...lumos doctor... vault: ...")      ← "vault 行"
452:    issues = 0
453:    gov_events = []          # 本輪 gate findings → governance-log(--ci 才寫)
...
490:    section("1/4", "Verification orphans ...")    ← 首個 "[" 段
```

v3 指定的插入點,就落在 452-453 與 490 之間——也就是**在任何一道 check(check-r/s/e1/e2/e3/k/j)實際跑過之前**。此時 `gov_events` 剛被初始化為空 list,尚未累積本次執行的任何一筆事件(各 gate 的 `gov_events.append(...)` 全部散落在 490 行以後的各個 section 裡,例如 check-s 在 819/825、check-e1 在 866)。

判準「該鍵在最近 20 次 run 每一次都出現 → 升級;**最新 run 不出現 → 不升**」裡的「最新 run」,依上下文語意指的就是**正在執行、正在印這份輸出的這一次**——這正是「剛清的不升」這句話唯一講得通的意思(否則「剛清」要清在哪一次才算數?)。但在文件指定的列印位置,程式碼結構上**不可能知道**本次執行的任何一道棘輪輸入閘等一下會不會觸發——這件事要等到對應 section 執行完才會知道。也就是說,字面實作只有兩條路:
(a) 橫幅完全依賴帳本裡**過去**的 19 或 20 次 run(不含本次),遇到「某鍵剛好在本次被修好」的狀況,橫幅仍會照樣印出「N 項長期未處理」(把本次也算進「仍未處理」),而幾行之後對應 section 卻印出「✓ 沒有問題」——同一份輸出裡上下自相矛盾,使用者看到的是過期資訊;或
(b) 把 `run_doctor` 改成兩段式(先靜默跑完全部 check 收集 `gov_events`,再從頭列印 vault 行+橫幅+各 section)——這是對現有「邊跑邊印」單遍架構的非小改動,v3 文件的測試策略(行 106,test 14「頂端位置+`--ci` issue+`ratchet` 事件」)與實務隱患段完全沒提到需要這種結構性改動,等於把一個真實的實作前提留白。

**正確規則**:要嘛明講橫幅只反映「歷史 19 次(不含本次)+ 若本次任一輸入閘仍在觸發中的鍵視為第 20 次」這種需要重新表述的判準,並接受它與下方各 section 的即時結果可能存在暫時性不一致(需明講並在橫幅文字加註「不含本次尚在計算」);要嘛明講 `run_doctor` 需要改成兩段式執行,並把這個結構變更寫進實務隱患/測試策略,而不是留給實作者字面照抄「頂端」二字時才第一次撞到。
