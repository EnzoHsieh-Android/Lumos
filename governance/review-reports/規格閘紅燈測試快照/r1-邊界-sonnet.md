### F1 「紅」不等於「實作還沒存在時寫的測試」:官方補跑流程與 Kotlin/Java 的假紅,都會把已對齊實作的測試存成紅燈版
severity: major
blocking: 是 — 守衛的前提不成立;照 spec 做出來的是個在系統自己指示的流程裡靜默失效的守衛,實作者還會以為它有效。

位置:白話、名詞「紅」、做法一「寫紅燈版的時機」。

引句:「這份計劃把那一版的測試內容存下來(紅燈版),推送時拿紅燈版當新測試的改動前版本來比」
引句:「Python 有支數證據;Kotlin/Java 沒有(`_RAN_EVIDENCE` 沒收這兩個棧)」

問題:spec 把「規格閘判紅」直接當成「這是實作前寫下的 expected」。對 Kotlin/Java 有兩條路徑會讓紅與「測試內容早於實作」脫鉤,而 spec 對兩條都沒有交代。

- 補跑流程。風險低門遇到「實作後才跑、測試現在已綠」時,工具印的標準補法是先提交實作,再把實作換成空殼讓測試紅,最後在同一個工作目錄跑規格閘。第 2 步明寫「測試檔留現在的」。這時測試檔是實作完成之後、已被改成 `assertEquals(800, …)` 的版本。規格閘 PASS 並寫留痕,紅燈版就把 800 記成「最早、實作前」的基準。這正是計劃要防的動作,而且發生在系統自己指示的流程裡。
- 假紅。Kotlin/Java 的紅只看退出碼非 0。逾時直接記成 red:`_run_bound_tests` 把 `超時(>180s)` 記成 "red",Gradle 冷啟動超過 180 秒很常見。編譯失敗、JDK 或網路壞掉也是 red。已經對齊實作的測試只要碰到任一種,就會被存成紅燈版。
- 紅燈版沒有任何欄位記錄「存的當下,測試內容是否早於實作」,所以事後無法區分真紅燈版與這兩種假紅。
- 規格只把「同時改紅燈版與帳本」列為天花板,沒列這兩條。這兩條是一步就會走到,不需要偽造。

佐證:
file: `scripts/lumos:14886` `_spec_gate_low_not_red` 在 `greens` 非空時印補法。
file: `scripts/lumos:14909` 補法第 2 步「測試檔留現在的」。

### F2 紅燈版讀不到或指紋對不上被定成不可放行的硬錯誤,與比對工具對怪檔的慣例相反,也沒有救不回來時的出口
severity: major
blocking: 是 — 會做出一道一旦誤觸發就只能整道閘關掉(`LUMOS_SKIP_LINT_NEW`)的硬擋,誤觸發來源很普通。

引句:「手動刪紅燈版、或合併時把那個資料夾弄丟,推送會被擋,要從版本紀錄還原。」

問題:「比對沒跑完」進的是 `undone kind=guard`,不是候選。`lint-waive` 只能放行候選的指紋,所以這個擋下沒有放行路徑。

這和比對工具的慣例相反:單一怪檔(配不平、含 NUL、太大、讀不出來)一律落成可放行的候選。`test-guard.md` 的 WHY 也寫明「判錯的代價從推送卡到超時變成多一條要人放行的候選」。

誤擋來源都不需要惡意:

1. JSON 是新增的未追蹤檔,規格閘寫在工作目錄。同工作目錄有別的會談、只用 `git add <路徑>` 提交時,帳本那行進了提交,JSON 沒進。
2. sha256 是對檔案位元組算的,spec 沒規定寫檔位元組,也沒規定與 git 內的位元組一致。Windows 上 `core.autocrlf=true` 或文字模式寫入產生 CRLF,提交時被正規化成 LF,sha256 就永遠對不上。repo 已支援 Windows,並有 `_write_lf` 前例。
3. 全 repo `sed` 改名會改到 JSON 裡內嵌的測試原始碼副本,sha256 對不上。
4. 工作樹丟失後無法重建:測試現在已綠,規格閘不會再寫紅燈版。唯一的出路是手改帳本刪掉那一行,而 spec 自己把這一步定義為「等於沒有紅燈版」。

「要寫出還原方式」只涵蓋 JSON 還在版本紀錄裡的情況。

file: `scripts/lumos:39067` 註解「單一怪檔不走這裡:配不平、含 NUL、太大、讀不出來都是可放行的候選」。
