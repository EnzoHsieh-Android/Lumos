# 規格閘紅燈測試快照_計劃

> 白話:新功能的測試在規格閘跑出紅的那一刻,是「實作還不存在時寫下的 expected」。這份計劃把那一版的測試內容存下來(紅燈版),推送時拿紅燈版當新測試的改動前版本來比;實作期間把 expected 改成實作輸出、放寬斷言、新加 `expected =`、調大逾時,就跟改既有測試一樣會被列出來。

## 問題與最小解

立案(2026-11-03,Enzo 原話依序):「我們當初規劃spec拆任務的時候，是以"需要驗收哪些測試"為spec完成的基準，是不是在這個階段，可以扣回測試這個主旨？」→「只是說法要改嗎？ 我們工具需要把這兩環串接起來？」→「直接開新計劃」。

斷點:`lumos test-guard` 拿主線分岔點當改動前版本。新功能的測試在分岔點不存在,`_tg_fn_cands` 遇到沒有前一版的函式只判 `tq/no-assertion` 與 `tq/catch-no-fail`(跳過與 assume 走另一條次數差,新測試帶 `@Ignore` 今天就會列)。於是「規格閘時 `assertEquals(900, checkout(1000))` 是紅的,實作算成 800 之後把測試改成 `assertEquals(800, …)`」推得出去。這正是預期答案研究裡最強的那條結論要防的事(預期值不能從實作現在的輸出來,`governance/eval/results/ai-test-verification-research-20261102/oracle.md` 結論 1、3)。規格閘手上有實作前的那一版,但 `_spec_gate_record` 只記測試名,沒記內容;推送前會壓提交,只記當時的版本編號也不夠(防竄改計劃的 4 筆規格閘留痕,用各自的版本編號查:第一筆 13 支綁定測試 0 支存在,其後三筆各 1 支存在,`n_red` 全是 0;2026-11-03 查證)。

舊否決比對(開審前,2026-11-03):`lumos rejections` 撞到 [[Projects/規格閘不把不做節的詞算進風險_計劃]] 否決的「內容比對 ratchet」(輕量審抓到 major 後洗不掉的比對,靠帳上自填的編號、輪次、快照,r4–r7 連四輪被繞過;[[Systems/規格閘]] 的 PITFALL 同一件事)。本案也是「留一份內容事後比」,差在紅燈版由工具在跑紅時自己寫、照檔案路徑與函式鍵找、只認最早一份,改名與換綁另列候選,剩下「同時改紅燈版與帳本」照實寫成天花板。問人後 Enzo 裁「照設計開審」。

最小解:規格閘寫留痕時,把判成紅的 Kotlin/Java 綁定測試所在的檔案內容存一份;比對工具遇到「相對分岔點是新測試、但有紅燈版」的函式,拿紅燈版當前一版跑既有的函式級判斷,列成三條專屬規則。不做語意判斷,不建暫時工作樹。

PRIOR-ART: ImpossibleBench 建議實作期間測試唯讀、評分前還原原版(對「改測試」這招最有效,擋不住實作端特判;https://arxiv.org/pdf/2510.20270);社群 TDD 技能有「紅燈先提交、綠燈後請另一個代理判斷綠燈提交有沒有改變紅燈測試的語意」(https://skills.sh/mrsimpson/skills-coding/tdd ,靠模型判斷,這裡不採)與「綠燈後對紅燈階段的不可改紀錄比對」(adev write-test 技能,頁面拒絕存取、細節沒驗到)。本案取 ImpossibleBench 的「保留實作前版本、事後比對」形狀,但不硬性唯讀:比對借 `lumos test-guard` 既有的確定性判斷,合理改動走既有 `lint-waive` 附理由放行。紅燈版的位置記在規格閘留痕的治理帳那一筆(乾淨 clone 讀得到,[[Systems/規格閘]] 的 WHY);比對核心借 `_tg_functions`、`_tg_fn_cands`(吃純文字,不需要 git 版本)。
RETIRE-IF: 人工抽查放行檔(`lumos lint-waive --list`,規則欄看得到 `tq/redbase-*`)時,`tq/redbase-weakened` 三個月內的放行理由多數是「需求在實作期間變了」而不是作弊或誤寫,就改成只提醒;六個月內 `tq/redbase-*` 在全部消費專案零觸發,就撤掉紅燈版的寫入與比對 [retire:人裁] [until:2027-05-03]

## 名詞

- **紅燈版**:規格閘寫留痕那一刻,判成紅的綁定測試所在檔案的完整內容,加上測試名、條款編號、檔案路徑、函式鍵、內容指紋。不是設計審的凍結快照(`spec-freeze`),也不是截圖基準圖(`tq/snapshot-changed` 管的那種)。
- **紅**:`_spec_gate_verdict` 回 red。Python 有支數證據;Kotlin/Java 沒有(`_RAN_EVIDENCE` 沒收這兩個棧),紅等於「跑那支測試的指令退出碼非 0」,含編譯失敗;懸空(找不到測試)也記紅,但找不到檔就存不了,見做法一。
- **函式鍵**:`lumos test-guard` 認測試函式的身分,類別路徑加函式名(同名多載加序號)。
- **分岔點**:被推分支跟遠端主線的共同祖先,`lumos test-guard` 的改動前版本。

## 做法

### 一、規格閘寫紅燈版

- 逐支的紅綠目前拿不到:`_spec_gate_run_clauses` 把同一條款的幾支測試合成一格,逐支結果只在 `_spec_gate_judge_items` 的回傳裡、用完就丟;`_spec_gate_prepare` 傳給留痕的測試名也丟了平台。要改這兩處的回傳形狀,讓 `_spec_gate_record` 拿得到逐支的(條款、平台、測試名、判定)。
- 寫紅燈版的時機跟留痕相同:風險低在 PASS 時、風險高在相依回歸全綠時(其餘出口本來就不寫留痕,也不寫紅燈版)。
- 對判成紅的每支綁定測試:用 `_platform_name_files` 找它所在的檔,只收 `.kt`、`.java`;檔以嚴格 UTF-8 讀(解不開就不存);用 `_tg_functions` 切出那支函式取函式鍵。找到的檔不只一支、同一支檔裡同名函式鍵不只一個、或找不到函式,這支不存。每一種不存都在規格閘輸出印一句(測試名與原因)。
- 規格閘找得到的測試只認 `@Test`、`@ParameterizedTest`、`@RepeatedTest`(`KOTLIN_TEST_RE`);`@TestFactory`、`@TestTemplate`、`@Theory` 的測試規格閘本來就綁不到,也就沒有紅燈版。
- 同一次寫成一份 `governance/redbase/<迴圈編號>/<留痕 token>.json`:`tests` 每支一列(測試名、條款編號、檔案相對路徑、函式鍵),`files` 每支檔一份內容與 sha256。單檔上限沿用 `lumos test-guard`(5 MB 或 10 萬行),超過的那支檔與它的測試不存、印一句;寫入端不另設總量上限,讀取端算進比對工具一次推送 200 MB 的總量。
- 留痕(審查帳與治理帳兩筆)多一個欄位 `redbase: {"path": <相對路徑>, "sha256": <整份 JSON 檔的 sha256>}`。沒有任何可存的測試時不寫檔、不帶欄位。寫檔失敗(磁碟、權限)時照舊寫留痕、不帶欄位並印一句,規格閘本身不因此擋。
- `governance/redbase/`(新增) 加進簿記資料夾清單(`_BOOKKEEPING_DIRS`):它是紀錄不是碼,代碼審通過後補跑規格閘不該讓代碼審留痕失效。只有代碼審留痕失效的判斷會另外看資料夾裡有沒有程式檔;小改動閘、風險掃描、推送前測試範圍、回頭重讀這些消費者只看前綴,放進這個資料夾的檔對它們一律是簿記。

### 二、比對工具讀紅燈版

- 讀哪些紅燈版:比對工具分析 `<起點>..<終點>` 時,用 git 讀起點與終點兩版的 `docs/.governance-log.jsonl`(不讀工作目錄),只取終點有、起點沒有的 `spec-gate-record` 行裡的 `redbase` 欄位,也就是這條分支自己寫的紅燈版;已經合進主線的舊計劃不會被誤套到後來同名的新測試。紅燈版 JSON 檔也從終點那一版用 git 讀。
- 驗:讀不到、不是合法 JSON、或內容的 sha256 對不上欄位 → 記成比對沒跑完(跟比對工具出錯同一條路);新增告警閘在 block 模式擋下,訊息寫路徑與「紅燈版被動過或讀不到」;warn 與 off 模式照既有規則只報告或記帳。路徑必須在 `governance/redbase/`(新增) 底下,不在的當讀不到。
- 同一個「檔案路徑+函式鍵」有好幾份紅燈版時,取留痕時間最早的那份。重跑規格閘時測試仍是紅才會產生新的一份(綠了就不寫),取最早讓這種情況洗不掉實作前那一版。
- 對終點那一版的每支測試函式:
  - 分岔點有同一個函式鍵(或改名配對得上)→ 照舊用分岔點那一版,不看紅燈版。
  - 分岔點沒有、紅燈版有 → 照舊先跑新測試的規則(`tq/no-assertion`、`tq/catch-no-fail`,即使本體跟紅燈版一字不差也跑);再拿紅燈版當前一版跑 `_tg_fn_cands` 的函式級判斷(放寬斷言、改 expected、新加 `expected =`、調大逾時)與跳過、assume 的次數差。這一段的命中一律列成 `tq/redbase-weakened`,原因寫出是哪一種(例「相對規格閘紅燈版(<token>):expected 被改」);次數差那條在分岔點比對已經列過的(例:新測試帶 `@Ignore`,今天就列 `tq/skip-added`),紅燈版那邊次數相同時不重複列。
- 紅燈版記的測試在終點那一版找不到:
  - 路徑不同但函式鍵在終點那一版的測試檔裡唯一 → 當成搬家,照比。
  - 計劃裡同一個條款編號綁的測試名跟紅燈版不同、而紅燈版記的名字在終點那一版不存在 → 列 `tq/redbase-rebound`(可放行),原因寫 token、條款編號、舊名與新名;這支測試不再另列 `tq/redbase-unmatched`。計劃檔或那個條款編號已經不在時不列(整份計劃撤掉,回頭重讀與規格閘會管)。
  - 其餘找不到或不只一處 → 列 `tq/redbase-unmatched`(可放行),原因寫 token、測試名、條款編號。
- 指紋照 `_tg_cand` 的算法,身分字串含紅燈版 token;放行分岔點比對的同名候選不會順帶放掉紅燈版這條。
- 終點那一版的治理帳沒有任何這條分支新寫的 `redbase` 留痕時,行為跟現在逐字相同。
- 新規則代號與「抓不到」的變動,同步寫進 [[Systems/test-quality-cli]] 的規則一覽(`_TG_LIMITS` 跟標準文件是同一份,`t_tq_guard_cli_contract` 釘著)。

### 三、不做

- 不提供更新紅燈版的指令:需求在實作期間真的變了,一律走 `lint-waive` 附理由放行(放行紀錄的規則欄會是 `tq/redbase-weakened`,RETIRE-IF 靠它量)。
- 不改風險高計劃「不強制先紅」的規則;風險高的計劃只有在規格閘時剛好跑出紅,才有紅燈版可比。
- 不支援 Python 等其他語言的測試(比對工具只認 Kotlin、Java);本 repo 自己的 `t_` 測試不受保護。
- 不硬性鎖住測試檔,不做語意判斷,不派模型判斷「綠燈有沒有改變紅燈測試的意思」。
- 不建暫時工作樹([[Systems/規格閘]] WHY:編排者裁走輕量版)。
- 紅燈版內容不寫進治理帳本體(單筆會到數十 KB,帳本是逐行追加、全 repo 共用)。

### 四、待決問題的自答

- 紅燈版比對出來的候選,AI 可不可以自己放行:照既有新增告警閘的放行規則(AI 放的標出來、事後要人看),不另設「只准人放」。來源:使用者 2026-11-02 給這一系列工作最高裁量權與簽核權(「給你最高裁量權＆簽核權」);要不要升成只准人放,看 RETIRE-IF 那次抽查。

## 驗收條款

- [S1] 當規格閘寫留痕而有判成紅的 Kotlin 或 Java 綁定測試時,應寫一份紅燈版(每支測試的測試名、條款編號、檔案路徑、函式鍵,每支檔的內容與 sha256),兩筆留痕都帶 `redbase` 欄位;判成綠或弱證據的、Python 的、檔案或函式鍵找到不只一處的、檔不是合法 UTF-8 的測試不存並印一句;沒有任何可存的測試時不寫檔、留痕不帶 `redbase`;同一條款綁兩支、一紅一綠時只存紅的那支。 [test:t_spec_redbase_written_on_red]
- [S2] 當終點那一版的測試函式在分岔點不存在、而紅燈版裡有同一個檔案路徑與函式鍵時,比對工具應拿紅燈版當前一版:紅燈版是 `assertEquals(900, checkout(1000))`、終點是 `assertEquals(800, checkout(1000))` 應列 `tq/redbase-weakened`(原因寫 expected 被改);改成 `assertTrue(checkout(1000) > 0)`、新加 `@Test(expected = …)`、`@Test(timeout = 30)` 改成 `45` 也應列;測試一字未改、只改被測呼叫的參數、只改正式程式時不列;新測試帶 `@Ignore` 照舊列 `tq/skip-added` 一條、不再多列一條 `tq/redbase-weakened`。 [test:t_tg_redbase_weakened]
- [S3] 當同一個檔案路徑與函式鍵有好幾份紅燈版時,應取留痕時間最早的那份:先存的是 900、之後重跑規格閘仍紅時存了 800、終點是 800,仍應列 `tq/redbase-weakened`。 [test:t_tg_redbase_earliest_wins]
- [S4] 當紅燈版檔讀不到、不是合法 JSON、sha256 對不上欄位、或路徑不在 `governance/redbase/`(新增) 底下時,新增告警閘在 block 模式應記成比對沒跑完並擋下,訊息寫出路徑與「被動過或讀不到」;不得當成沒有紅燈版放行。 [test:t_tg_redbase_tamper_blocks]
- [S5] 當紅燈版記的測試在終點那一版換了檔案、但函式鍵在終點那一版的測試檔裡唯一時,應照比(搬家後改 expected 照樣列);找不到或不只一處時應列 `tq/redbase-unmatched`,原因寫 token、測試名與條款編號。 [test:t_tg_redbase_moved_or_missing]
- [S6] 當計劃裡同一個條款編號綁的測試名跟紅燈版不同、而紅燈版記的名字在終點那一版不存在時,應列 `tq/redbase-rebound` 且不另列 `tq/redbase-unmatched`;計劃檔或那個條款編號已經不在時兩條都不列。 [test:t_tg_redbase_rebound]
- [S7] 當測試函式在分岔點已經存在時,比對工具應照舊拿分岔點當前一版、不看紅燈版;紅燈版留痕只在分岔點那一版的治理帳裡(已合進主線的舊計劃)時應當成沒有紅燈版;終點那一版的治理帳沒有這條分支新寫的 `redbase` 留痕時,比對結果與 `--json` 輸出應跟改動前逐字相同。 [test:t_tg_redbase_absent_unchanged]
- [S8] 當紅燈版本體跟終點一字不差、但那支測試沒有任何斷言時,比對工具應照舊列 `tq/no-assertion`。 [test:t_tg_redbase_still_checks_new_rules]
- [S9] 當 `tq/redbase-*` 候選用 `lumos lint-waive <指紋> --note` 放行之後,新增告警閘應不再擋同一條,放行紀錄的規則欄是那條 `tq/redbase-*`;放行分岔點比對的同名候選不會順帶放掉紅燈版這條;AI 放行照現制標出。 [test:t_tg_redbase_waive]
- [S10] 當在只有提交內容的乾淨 clone 裡推送檢查、工作目錄的治理帳跟終點那一版不同時,比對工具應照終點那一版判紅燈版,結果跟本機相同。 [test:t_tg_redbase_reads_tip]
- [S11] 當 `governance/redbase/`(新增) 裡新增檔案、而其他檔都沒變時,代碼審留痕應照樣有效(簿記豁免);那個資料夾裡出現程式檔時,代碼審留痕的判斷照舊不算簿記。 [test:t_spec_redbase_bookkeeping]

## 回退

## 實務隱患

- 守衛面:新增告警閘對「規格閘時紅過的新測試」變嚴,原本只判有沒有斷言、吞斷言與跳過次數,現在也判放寬、改 expected、新加 `expected =`、調大逾時。需求在實作期間真的變了、測試跟著改是合理的,這種要逐條附理由放行;一個計劃改很多條時會多一批放行。出口與既有閘相同(放行附理由、整道關掉是設定 off 或 `LUMOS_SKIP_LINT_NEW=1`)。

- 守衛面:規格閘多寫一個檔,寫入失敗時規格閘照舊寫留痕、不帶欄位並印一句,不讓規格閘本身因此擋;代價是那一次沒有紅燈版可比。
