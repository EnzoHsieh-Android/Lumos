# 推播miss量測_計劃

> 白話:agent 改一支檔之前,hook 會推幾篇筆記給它。我們想知道兩件事——推的東西它有沒有用上,以及更重要的:它自己跑去讀了、但我們沒推的那些筆記。後者就是推播漏掉的東西,而且是 agent 真實行為告訴我們的,不是我們自己出的題。資料本來就在 Claude Code 的逐字稿裡,既有的量測程式也已經算出「讀了哪些」,只是把沒推的那一半丟掉了;本案把那一半留下來、分類,並定期存檔免得逐字稿被清掉。

## 緣起

- [[Projects/GraphRAG對節點關聯_調研]]:Graph RAG 的招牌手法對我們幫助有限,真正卡住的是「評測題少、而且出題判分同一個來源」。Enzo 2026-09-11 採納建議一(d1)。
- 既有儀器 [[Projects/主session鏡頭利用率_計劃]](`governance/eval/lens-utilization/recount.py`)已經從逐字稿對到每次推播與之後的讀取,但在 `scan_file` 裡把讀取跟推播清單取交集,沒推卻被讀的那一半直接丟掉;而且只解析「必看」那一段,「可能相關」「直接提到這個檔」兩段沒解析。
- 建議二(搜尋零命中時,用圖譜裡的詞共現幫查詢改寫)要先知道零命中有多少、長什麼樣,這個數也在同一支儀器順帶數(S3)。
- 那份計劃還掛著 `REVISIT:2026-09-17`(先跑歷史、Enzo 讀分佈與抽樣裁第二段)。本案的 miss 數字一起在那天交出,不另開一個回頭日。

PRIOR-ART: ①最小解層級=擴充既有唯讀腳本 recount.py(資料已在逐字稿,零新元件、不動 hook、不新增 lumos 寫帳) ②世界解過:搜尋引擎拿點擊當隱性回饋是慣用做法,「沒排上卻被點」比「排上而且被點」可信(位置偏差);本次未另查文獻,只借這個觀念 ③裁定=借用觀念、自建小段;零新依賴

## 條款

- [S1] 推播清單解析三段都認:「必看」「可能相關的 N 篇」「另外 N 篇分數不高但直接提到這個檔」三段的節點都算「推了」;新舊標頭都認,解析不到的段落記 `pushed_complete=false`,不猜 [test:t_lens_recount_parses_all_sections]
- [S2] miss 偵測:同一份逐字稿、那次編輯之後的高信心讀取(沿用既有 `touched` 的判法:Read 工具、單純讀動詞、`lumos context|show|contracts`),減掉推播清單,剩下的就是 miss 候選 [test:t_lens_recount_miss_classify]
  - 每筆 miss 依「跟被改的檔 F 有沒有關」分三類:**規則內**(用現在的圖譜跑 `lumos impact --file F --json`,該筆記出現在 direct 清單——impact 抓直連有兩條規則:正文反引號寫到 F 的完整路徑,或裸檔名在 git 追蹤的檔裡唯一時的檔名比對;直接問 impact,不在儀器裡另寫一套比對)、**關於欄**(該筆記開頭的 about_code 欄位含 F;這個欄位只拿來排序、不建連結,所以不會跟規則內重複)、**判不出**。
  - 那篇筆記在那次編輯之後才新建(git 第一次加入的時間晚於編輯,或還沒進版控)→ 不算 miss,另計「事後才有」:推播當下它根本不存在,推不到不是漏。
  - 規則內與關於欄的 miss = 推播的真漏洞(該推沒推),列出來就是 impact 的回歸案例;判不出的列成候選,交人或雙評審標註,標完進 edit 卷(推播品質評測題庫 `governance/eval/retrieval-goldset.json` 裡「編輯時推播」那一份題目,由 `governance/eval/refresh_labels.py` 維護;走它既有的流水線)。
  - 只出分佈與清單,不出單一命中率、不設門檻——沿用既有儀器的約定(r1 裁「比率量到的是圖譜密度」)。
  - 推播前就讀過的不算 miss(那是 agent 本來就在碰的東西,既有 `pre_touched` 已分開)。
- [S3] 搜尋零命中:從同一批逐字稿數 agent 用 Bash 敲的 `lumos search`,配對它的輸出,判零命中:文字輸出結尾那行是「(共 0 篇候選」,或 `--json` 輸出的 `candidates` 是 0;兩種都對不上的(輸出被截斷、其他模式)記「判不出」,不算零命中;出總數、零命中數、零命中的查詢字串清單(建議二的評測材料) [test:t_lens_recount_search_zero_hits]
- [S4] 每週留存:在每日治理那支排程的週期觀測段加一步「推播利用率週跑」,本週沒跑過才跑,輸出寫到 `governance/eval/lens-utilization/archive/<年>-W<週>.json` [test:t_lens_recount_weekly_archive]
  - 只存推導出來的列:工作階段代號的雜湊、被改的檔、推了哪些節點、之後讀了哪些、miss 分類、零命中查詢字串;**不存逐字稿原文**。
  - 這改動既有儀器「不寫任何帳」的約定:寫的是每週一份的報表檔(同 2026-09-04 那份首報進版控的慣例),不是逐筆追加的帳本、不進 hook、不進 `lumos gov`。
  - 同一週重跑覆寫同一個檔(冪等);跨週不回頭改舊檔。
- [S5] README 同步:recount.py 的 README 補 miss 三類、零命中、週跑三段,並寫明天花板 [manual:讀 README 對照三段是否寫到]

## 邊界與不做

- 不動 impact hook、不動派工鏡頭(派工鏡頭「不擋不驗不記不量」照舊)、不改 `docs/.usage-log.jsonl`(F08)。
- 不出單一命中率、不設門檻、結果不回灌排序——排序要改,另案用 miss 當證據走設計審。
- 只量本 repo 的逐字稿(沿用既有 `cwd` 篩法);消費專案另案。

## 承認的限制(每條附回頭條件)

- **位置偏差**:agent 會讀被推的東西,「推了而且被讀」不能直接當相關;本案只把「沒推卻被讀」當證據。這是方法本身的限制、不隨時間變;事件入口=任何要拿本儀器輸出去改推播排序的計劃,它的設計審要先交代怎麼處理位置偏差(邊界與不做已寫「結果不回灌排序」)。
- **用現在的圖譜判當時的推播**:規則內 / 關於欄都拿現在的筆記內容判,編輯之後才補上 F 路徑的筆記會被算成「該推沒推」(新建的已排除,改寫的排除不了)。
REVISIT:2026-09-17 第一份 miss 清單出來時,抽規則內那一類逐筆看 git 歷史,數有幾筆是「編輯之後才寫上 F」;超過兩成就改成用編輯當時的筆記版本判
- **量不到 Bash 改檔**:impact hook 只在 Edit/Write/MultiEdit/apply_patch 觸發,用 Bash 改檔沒有推播,那段 miss 天生量不到(既有計劃記過一個 session 372 次 Bash、0 次 Edit)。
REVISIT:2026-09-17 跟既有計劃同一天:看推播次數夠不夠(既有計劃門檻 20);不夠就照它的改題「Bash 改檔路徑沒有動手前鏡頭」
- **判不出那一類要人標**:沒標就不會變成評測題。
REVISIT:2026-10-17 數判不出的 miss 累積幾筆、標了幾筆;標不到三成就議要不要把標註併進每週治理流程
- **零命中判法靠輸出字樣**:search 輸出措辭一改就會數錯。驗收要有一條測試釘住「目前的零命中輸出」長什麼樣。

## 實務隱患

- 併發:唯讀逐字稿;週跑寫的是本週一個檔、寫暫存、自驗讀得回來、再整個換名(本 repo 改共用檔的原子寫入慣例;換名會丟執行權限,這個檔不需要),同週重跑覆寫。
- 效能:掃 `~/.claude/projects/*/` 全部逐字稿,現在一次約數秒到十幾秒;放在週跑、本週跑過就跳過。
- 資源:只開檔讀;不開連線。
- 隱私:逐字稿可能含其他專案內容——只存推導列(節點名、檔名、計數、零命中查詢字串),不存原文;工作階段代號存雜湊。
- 金流、對外送出、不可逆:不適用——不碰任何金流或外送程式,檔案可刪可重跑。

## 驗收(測試先行)

- 注入全文含三段 → 三段節點都進「推了」;缺一段 → `pushed_complete=false`。
- 編輯後讀了一篇沒推、正文反引號寫到那支檔的筆記 → miss「規則內」;about_code 含那支檔 → 「關於欄」;都沒有 → 「判不出」;推播前就讀過 → 不算 miss。
- 逐字稿裡一次零命中的 `lumos search`、一次有命中的 → 零命中數 1、清單含那個查詢字串。
- 週跑:本週沒檔 → 寫一份;同週再跑 → 覆寫同一份、不多出檔;輸出不含逐字稿原文(抽一段原文字串斷言不在檔裡)。
- 既有 `t_lens_recount_classify` 全綠。
