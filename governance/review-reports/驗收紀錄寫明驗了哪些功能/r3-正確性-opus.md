# r3 正確性審查(opus)——驗收紀錄寫明驗了哪些功能_計劃

範圍:r3-snapshot.md 全文、r3-delta.diff;對照 repo `scripts/lumos`(提交 b1f1a322),實驗在 `git clone --shared` 的臨時目錄與 scratchpad 假圖譜裡跑,沒動 repo。

結論先講:**這輪有 1 條 blocking(F1)。** 前兩輪的 blocking(判單項的規則、`無` 引出的連鎖、孤兒推薦回 None、sync 提早結束、E1 漏接)都驗過,改法成立。四個「特別驗」裡,抽出 `build_typed_index` 的單項判法在兩個真實圖譜上都能讓索引一字不差;嚴格判法沒有擋到任何現有寫法;改成不分大小寫也不會讓 E1 和孤兒清單互相打架;rtb 回報的 7 篇都靠 `system_refs` 解得掉。剩下一條 major、blocking(建檔指令自動宣告,會讓之後寫進正文的「真的驗了」悄悄不再被檢查,等於漏掉 doctor 3/4 原本的合約)和五條 minor。

## F1 `new verification --systems` 自動寫進 `system_refs`,建檔之後才寫進正文、真的有驗的功能從此不再被檢查,而且沒有任何提示
severity: major
blocking: 是
引句:「落在 `Systems/` 的,用 `env.notes` 裡那篇的真實路徑(檔名大小寫照檔案)寫進新紀錄自己的 `system_refs`」
file: `scripts/lumos:19102`(建檔教學現在寫「讓它驗證的 Systems 筆記用 verified_by 連回這篇(或事後跑 lumos sync-verified-by 補)」)
file: `scripts/lumos:19117`(`--systems` 是「一鍵雙向」的標準建檔路徑)

1. 計劃的〈實務隱患〉漏網段寫的是「寫了 `system_refs` 卻漏列」,前提是作者自己決定要宣告。但照〈做法〉5,只要用標準指令 `new verification --systems Systems/A` 建檔,工具就會自動宣告,作者不一定知道自己已經宣告了。實際流程通常是先建骨架、再寫正文;宣告的內容其實是「建檔那一刻想到的功能」,不是「最後真的驗了的功能」。
2. 實測現況(scratchpad 假圖譜,Systems/A、Systems/B):`new verification 2026-10-03_v --systems Systems/A` → rc 0;接著在正文補一句「驗了 [[Systems/A]] 也驗了 [[Systems/B]] 的匯出」→ `doctor` 3/4 報「Systems/B.md 漏: 2026-10-03_v」,`sync-verified-by` 列「Systems/B.md ← [[Verification/2026-10-03_v]]」。照本設計,這份紀錄建檔時就帶了 `system_refs: [[Systems/A]]`,所以 B 兩邊都不會出現,doctor 全綠。
3. 原本能抓到的漏登記,在最常用的建檔路徑上會悄悄變成抓不到。教學那句「或事後跑 sync-verified-by 補」對這種紀錄也不再成立,但〈做法〉5 只說要「補一句」,沒說要改掉這句。
4. RETIRE-IF 第二條「有一半以上漏列真的驗了的功能」沒有機械量法,REVISIT 那一行也只數「幾篇寫了、有沒有誤報或寫壞」,沒講怎麼量漏列。等於這個代價沒有回頭條件接得上。
5. 建議三選一:(a)建檔時只有使用者明確要求(例如加 `--declare`)才寫 `system_refs`,預設照舊從正文推;(b)doctor 3/4 加一段 `warn_soft`(不算問題數):「紀錄宣告了 `system_refs`,正文另外連到 Systems/B,B 也沒登記這份」,只提醒、不擋推送,rtb 那種指路連結也只會變成提醒;(c)至少把教學那句改成「用 --systems 建的紀錄只看 system_refs,事後在正文補的功能要 `lumos append <紀錄> system_refs`」,再讓 REVISIT 寫明怎麼抽樣量漏列。S8 也要補一個建檔後在正文補連結的案例。

## F2 抽出的單項判法只列「合格或四種不合格」,裝不下索引原本「空目標直接跳過」的行為;照字面抽出來,`[[#段落]]` 這類項目在索引裡會從跳過變成被列出
severity: minor
blocking: 否
引句:「合格(落點 rel)或四種不合格(不是單一連結、寫了路徑但沒有這篇、沒寫路徑而找不到、沒寫路徑而有多篇同名)」
file: `scripts/lumos:760-771`(`if not s: continue`、`t = nfc(...)`、`if not t: continue`、去重鍵 `(rel, t, etype)` 在解析之前)

1. 索引在迴圈裡有兩種「什麼都不做、直接跳過」:整項是空字串,以及連結目標是空的(`[[#段落]]`、`[[|別名]]`)。上面列的五種結果都不是「跳過」。照字面實作,只能把它歸進「不是單一連結」或「找不到」,索引的非連結清單或壞連結清單就會多出東西,跟 S5「四份清單應跟原本一樣」相反。
2. 另外,去重要用原文目標 `t`(還沒去 `.md`、已經正規化),壞連結和不明確的清單也要帶原文和候選清單。所以抽出的函式除了落點和原因,還要回傳 `t` 與候選清單,不然索引得自己再解析一次。
3. 實驗:用「多一種跳過、並帶回 t 與候選」的原型改寫索引,在本 repo 圖譜(rev 539、ghosts 1)和 rtb 圖譜(rev 38、scalars 1)上,輸出跟原本的 `build_typed_index` 完全一樣。兩個圖譜的具名欄位裡,空目標的項都是 0 筆,所以目前不會真的出事。
4. 對 `system_refs` 的影響:如果空目標照索引直接跳過,那麼 `system_refs` 同時有一項合格、一項 `[[#x]]` 時,後者會被悄悄忽略,跟〈白話〉的「寫壞了一律報出來」不合。建議把回傳值定成「合格/跳過/四種不合格」,並帶回 `t` 與候選清單;`system_refs` 把「跳過」當成寫壞的項來報。

## F3 「一項合格的都沒有」的條件比它要描述的「空的」範圍大;每一項都寫壞時,會多報一條講錯原因的「空的或沒縮排」
severity: minor
blocking: 否
引句:「一項合格的都沒有(空值、空清單、清單項沒縮排而解析成空)→ 記一項寫壞」

1. 例:`system_refs:` 下面縮排一項 `"[[Projects/P]]"`。照〈做法〉2,這一項因為「落在別的資料夾」先列為寫壞;接著「一項合格的都沒有」也成立,又記一項「system_refs 讀不出任何一項——空的,或清單項沒縮排」。實際上清單不是空的,縮排也沒錯,這條原因是錯的,問題數也被算成 2。
2. 括號裡的例子講的是「讀出來是空的」,條件文字講的卻是「沒有合格項」,兩種實作會有兩種結果。建議把條件改成「去掉空白項之後一項都沒有」才記這一條;所有項都寫壞的情況,逐項報就夠了。S3 的測試補一個「唯一一項寫壞」的反例。

## 看過沒問題(不列為 finding)

- **抽出單項判法後,索引行為能不能不變**:可以。去重的 `seen`、`nfc`、去 `.md`、`by_stem` 小寫查,都是純粹「輸入一個字串、回傳結果」,留在迴圈裡或搬進函式都不影響。原型在兩個真實圖譜上的比對結果完全相同(細節見 F2)。唯一要補的是「跳過」這種結果,以及要帶回 `t` 和候選清單。
- **合法寫法會不會被擋推送**:
  - 本 repo 與 rtb 兩個圖譜裡,驗收紀錄連到 Systems 的連結共 239 條(143+96)。把它們原樣當成 `system_refs` 的項來嚴格判,壞連結、不明確、不在 Systems 都是 0。
  - 兩個圖譜裡 Systems 檔名撞名的都是 0 組,放在 Systems 子資料夾的也都是 0 篇。
  - 子資料夾的功能筆記寫完整路徑 `[[Systems/sub/X]]`,或寫唯一的裸名 `[[X]]`,都會判合格;只有部分路徑 `[[sub/X]]` 會判寫壞,這點已明寫在〈誤擋〉。
  - 「寫裸名、另有同名計劃」本來就會被 doctor G 段擋(`scripts/lumos:1540-1546` 同檔名一律 `warn`、算問題數),不是本案新增的擋。
  - 用 `--systems` 建檔時寫的是真實路徑,工具自己產出的寫法會判合格。
- **作廢與失效改成不分大小寫,會不會讓 E1 和孤兒清單翻轉**:不會打架。
  - 改了之後,各處跳過的集合不變,只是 `Stale`、`Superseded` 這種寫法也會被認出來。方向一致:3/4 和 sync 跳過、E1 唸死背書(只提醒)、孤兒清單只豁免作廢的,跟現在小寫的行為完全一樣,不會出現「這邊叫拔、那邊叫掛」。
  - 另外,lint 的狀態值域檢查(`scripts/lumos:5940`、`_STATUS_ENUM`)本來就分大小寫:截止日之後建的筆記寫 `Stale` 會在提交時被擋。所以這次的影響只落在舊筆記,計劃的〈相容〉段寫得正確。
- **拿掉 `無` 之後,rtb 的情境有沒有解**:有解。rtb 把指路連結改成純文字的 7 篇驗收紀錄都是 pass,而且每篇都真的驗了至少一個功能:6 篇正文有 3–5 個真的 Systems 連結;Phase14增量2a 正文沒有 Systems 連結,但有 4 篇 Systems 的 `verified_by` 登記了它。每篇都能寫出非空的 `system_refs`,指路連結就不再被要求反向登記。rtb 實際碰到的情況裡沒有「一個功能都沒驗、只有指路連結」的紀錄,所以拿掉 `無` 不影響這次要解的問題。
- **r2 的改法驗收**:
  - sync 的指路句放在 `if not planned` 提早結束之前,對準了 `scripts/lumos:15870`。
  - 孤兒推薦回 None 時照原本推薦,孤兒清單本來就包含失效紀錄(`scripts/lumos:1410-1412`),接得上。
  - E1(`scripts/lumos:2146-2147`)已列入共用的狀態判斷。
  - 多掛提醒只在紀錄沒有寫壞項時才唸、改法照原本登記的字面寫,解了 r2 c7。
  - `remove` 刪光最後一項時不另外提醒,跟〈回退〉一致。
