### 1. `LUMOS_IMPACT_LANE_N` 負值時,cap 語意變成「砍掉最後 N 項」而非「限制筆數」
- severity: **minor**
- file:line: `scripts/lumos:14544-14546`
引句:「lane_items = lane_raw[:_lane_n]」
- 失敗場景:`_lane_n = int(_impact_knob("LUMOS_IMPACT_LANE_N", 3))` 沒有下限保護(對照同函式內 `_rescue_n` 用 `_need = max(0, _rescue_n - _free_direct)` 防負值的既有慣例,這裡漏了同款守門)。負值時 Python `list[:-n]` 語意是「留下除最後 n 項以外的全部」,不是「上限 n 項」也不是「關閉」,結果會隨 `lane_raw` 長度變動而不可預期。
- 最小重現(已重現,見下):對 fixture(Risk1/Risk2 兩個 score=0.24 的 lane 候選)設 `LUMOS_IMPACT_LANE_N=-1`:
  ```
  $ python3 scripts/lumos impact --file src/svc.py --ranked --json \
      --repo <fixture> <<< '{"query":"","prospective":{}}' \
      (env: LUMOS_IMPACT_HARD_PIN=1 LUMOS_IMPACT_LANE_N=-1)
  ```
  實測輸出:`meta.lane=1, meta.lane_truncated=1`,`lane` 陣列有 1 條(留下分數較高的 Risk1,砍掉 Risk2)——不是「無上限」也不是「拒絕/退回預設」,是隨候選數量變的偶然結果。曝險面小(comment 已註明這批 `LUMOS_IMPACT_*` 只給 goldset 網格消融用、非使用者旗標),但網格若不慎掃到負值會拿到一組語意不明的靜默結果,不會報錯提醒。

### 2. `LUMOS_IMPACT_LANE_N=0`:meta 記了 count,但沒有任何管道告訴人「有東西被藏起來」
- severity: **minor**
- file:line: `scripts/lumos:14557-14558`(頂層鍵判斷)、`scripts/hooks/claude/impact-hook.py:364-370`(hook 讀取)
引句:「if lane_items:   # 條件鍵(同 query_gated/stack_questions 慣例):knob=0 或空 → 鍵不存在」
- 失敗場景:實測 cap=0(同一 fixture,`LUMOS_IMPACT_LANE_N=0`)得到 `meta: {"lane": 0, "lane_truncated": 2}`,但因為 `lane_items` 是空 list(falsy),`out_obj["lane"]` 這個頂層鍵完全不存在。人讀分支同理(`if lane_items:` 那段整個跳過,連「另有 N 條守衛面參考未列出」那句提示都不印)。hook 端 `build_ranked_context` 的 `lane = data.get("lane", [])` 拿到空表,同一句「另有 N 條…」提示(`meta.get("lane_truncated")` 那行)也因外層 `if lane:` 直接被短路,永遠印不出來。也就是說 `meta.lane_truncated` 這個欄位在 cap=0 時對 `--json` 消費者(eval/goldset)仍可見,但對「人看的畫面」(CLI 人讀輸出、hook 注入文字)完全不可見——RISK 候選存在過的痕跡在人類可讀輸出裡直接消失,沒有降級提示。註解裡把這個行為併進「knob=0 或空 → 鍵不存在」的既有慣例來解釋,但那個慣例原本描述的是 `LUMOS_IMPACT_HARD_PIN=0`(整個功能關掉)的情境,套到 `LUMOS_IMPACT_LANE_N=0`(功能開著,只是上限設 0)上語意其實不同,容易讓人以為兩種 0 是同一件事。生產預設值是 3,一般使用者摸不到這條路(同樣是網格專用旋鈕),影響面有限。

### 3. `t_impact_hard_pin_lane` 的 ⑧「--diff 聚合不含 lane 節點」斷言是假綠——fixture 沒有真的 diff,恆真
- severity: **minor**(斷言本身失去驗證力,但底層程式碼行為經我直接讀 `cmd_impact_diff` 源碼確認正確,不是功能性 bug)
- file:line: `scripts/test_lumos.py:910-916`
引句:「check("⑧--diff 聚合不含 lane 節點", all("Risk" not in x.get("node", "") for x in d4.get("results", [])), str(d4)[:200])」
- 失敗場景:`_hardpin_fixture()` 只 `git commit` 一次(`git commit -qm "init"`)後就直接對 `HEAD` 跑 `impact --diff HEAD --json`。`git diff HEAD` 比較的是「工作樹 vs HEAD」,commit 完工作樹是乾淨的,所以 `git diff --name-only HEAD` 回傳空清單 → `files=[]` → `merged={}` → `d4["results"]==[]`。我直接執行同一段邏輯重現:
  ```python
  r4 = sp.run([..., "impact", "--diff", "HEAD", "--json"], ..., env={..., "LUMOS_IMPACT_HARD_PIN": "1"})
  # rc=0, stdout: {"range": "HEAD", "files": [], "results": [], "meta": {...}}
  ```
  `all(...)` 對空序列恆真,所以這條 check 不管 `--diff` 聚合有沒有真的碰過 Risk 節點都會通過——它沒有驗到自己宣稱要驗的東西。函式自己的「翻紅釘」註解也只寫「拿掉 lane 收集 → ③翻紅」,沒有把 ⑧ 列進翻紅清單,某種程度上作者可能已經知道這條不夠硬。
  底層行為本身我另外直接讀 `cmd_impact_diff`(`scripts/lumos:14631` 起)確認過:它合併候選只用 `data.get("results", [])`,從未讀取 `data.get("lane", [])`,所以「lane 不進 `--diff` 聚合」這條合約在結構上是成立的——只是這條測試沒有真正驗到它,若未來有人在合併邏輯里手滑加了 `+ data.get("lane", [])`,這條測試不會抓到。建議:fixture 在 commit 後對 `src/svc.py` 再做一次真實修改(不 commit,留在工作樹)使 `git diff HEAD` 非空,才能讓 ⑧ 真的跑過帶 Risk 候選的合併路徑。
