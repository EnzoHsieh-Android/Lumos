## 二、新機制極端輸入(Findings)

### N1:`_link_or_copy` 沒有可執行的「我方複製物」判定演算法,fallback-copy 平台會永久卡死更新

severity: major
blocking: 是
引句:「dst 若是既有真目錄(非 symlink/junction、非我方複製物)→跳過+印一行 warn,不刪」

`_link_or_copy`(`scripts/lumos:10954-10982`)目前對真目錄一律 rmtree 再連結;symlink 建不成時會落到 `shutil.copytree` fallback(10980-10982),把 dst 變成一個「lumos 自己複製出來的真目錄」。r2 要求對 `~/.agents/skills/` 這個新目標「非我方複製物才跳過」,但字面文字沒有定義任何機制去分辨「我方上次 fallback 複製出來的真目錄」跟「外方工具放的真目錄」——兩者在檔案系統上完全相同。照字面最直接的實作(只判斷 `is_dir() and not is_symlink()`)會把自己上次複製的目錄也當「既有真目錄」跳過,結果是:任何 symlink 建立失敗的平台(Windows、或權限受限環境)第一次 install 後,`~/.agents/skills/` 底下的 lumos skill 副本會在後續每次 `lumos update`/`install` 都被跳過,永遠拿不到新內容,且只印一行 warn、沒人會注意到。

### N2:`_sync_global_*` 的 False 語意被既有呼叫端寫死解讀成「LUMOS_PROBE」,合併器失敗時會印出錯誤原因

severity: major
blocking: 是
引句:「檢查合併器 returncode:非 0→印 warn+return False,呼叫端不印成功」

現碼 `cmd_install` 的既有印字分支(`scripts/lumos:10235-10238`)是:`if _sync_global_claude(...): print("✓ …已同步…") else: print("⚠ …同步被擋(LUMOS_PROBE)——未動 ~/.claude")`——False 目前只有一種成因(探針拒絕),訊息寫死成「LUMOS_PROBE」。r2 的修法是讓 `_sync_global_*` 在合併器 rc 非 0 時也回 False,若沿用同一顆布林、不新增第三態或分開訊息,一支損毀的 `~/.codex/hooks.json` 會讓使用者看到「同步被擋(LUMOS_PROBE)」——這句話明講原因是探針模式,但真正原因是設定檔壞掉,會誤導使用者去查一個不存在的探針旗標而不是去修 JSON。

### N3:armed 檔的 seats 讀-改-寫在同 repo 同時多個 SubagentStart 觸發時沒有原子性,會重複扣減、標籤重複

severity: major
blocking: 是
引句:「每次注入 seats−1,歸零即刪」

r2 全文沒有描述 armed 檔的寫入是否加鎖或用原子 rename——只講落一個 JSON 檔、TTL、seats 計數。若兩個子代理幾乎同時觸發 SubagentStart(常見情境:一次代碼審同時派出多席,是本案自己的核心使用場景),兩個 hook 行程各自「讀 seats=N → 算 k=N-N+1 → 寫 seats-1」若中間沒有互斥,會出現：兩者都讀到同一個 seats 值、算出同一個 k,首行都印「LUMOS-LENS … 第 k/N 席」同一個序號給不同子代理(可觀測性欄位本身錯誤),且最終寫回的 seats 值只被扣一次而非兩次(其中一次寫入蓋掉另一次),讓「消耗 N 次即刪」的席位帳目算少,armed 檔存活超過預期次數。

### N4:doctor 估算 AGENTS 鏈總量用的 glob 在同層有 override 時會重複計入 Codex 根本不會載入的位元組

severity: minor
blocking: 否
引句:git 根到本層各 AGENTS*.md 總 bytes/32768

Codex 的規則是「同層若有 `AGENTS.override.md` 則只讀它」(r2 六層表第 1 列已明寫),也就是說某一層若同時有 `AGENTS.md` 與 `AGENTS.override.md`,Codex 實際只吃 override 那份、AGENTS.md 被完全忽略。但 doctor 估算用的萬用字元 `AGENTS*.md` 會把兩個檔的位元組都算進「總量/32768」——這在「git 根與子層(或同層)同時存在 override 與被蓋掉的 AGENTS.md」時,會讓估出來的佔用比例系統性偏高,>75% 警告可能對一個實際遠低於 75% 的 repo 誤報。影響方向是「多喊警報」而非「該喊沒喊」,不影響功能只影響訊息準確度,故列 minor。

### N5:AGENTS 檔「插檔首」在檔案完全沒有標題行時,插入位置沒有定義的 fallback

severity: major
blocking: 是
引句:AGENTS 檔的 absent 路徑把區塊插在第一個標題行之後(不是尾端)

「插在第一個標題行之後」預設檔案裡一定找得到一個 markdown 標題(`#`)。真實世界裡不少手寫的 AGENTS.md 是純散文起頭、完全沒有 `#` 標題行(這正是本題點名的極端輸入)。r2 沒有講「找不到標題行時怎麼辦」——照字面直接實作最常見的寫法是「找第一個 `^#` 那一行、insert after」,對「找不到」這個 None/-1 case 若沒有顯式分支,輕則整份文件被靜默改成尾端追加(等於沒達到「降低截斷機率」的目的但沒人知道)、重則索引運算落在 -1 上直接寫壞檔案內容(把區塊插到字串開頭前一格甚至拋例外讓 `lumos init`/`update` 中止)。兩種結果都是「跟另一個實作者做法不一樣」的真實分歧,不是精度問題。

### N6:enforcement 新狀態值 `registered-trust-unknown` 沒有對應的顯示符號

severity: minor
blocking: 否
引句:狀態值域 `registered-trust-unknown|inactive|unknown`

現碼 `cmd_enforcement`(`scripts/lumos:12228`)的圖示字典 `mark = {"active": "✅", "inactive": "❌", "degraded": "⚠️", "unknown": "❔"}` 沒有 `registered-trust-unknown` 這個鍵;`mark.get(r['status'], '?')` 會回退印一個裸 `?`。純顯示層小洞,不影響 `--json` 輸出或判斷邏輯,補一個鍵就解決。

### N7:armed 檔「TTL 到期但 seats 未歸零」時是否仍會誤注入,r2 這一輪把 r1 已寫的明確答案拿掉了

severity: major
blocking: 是
引句:armed 檔由 `lumos dispatch-lens <range> --arm --seats N` 寫

比對 r1 原稿同一列,原文明寫「沒 armed 檔或過期→什麼都不回」——這句話直接回答了「TTL 到期但 seats 還沒扣完時該不該注入」(答案:不該,過期即不回)。r2 這一輪把整列重寫時,這句明確結論被拿掉,只剩「TTL 10 分;每次注入 seats−1,歸零即刪」並列兩個獨立條件,沒有講兩者的優先序或「其中一個滿足就停止」的字眼。若實作者照 r2 現在的文字,只把 seats 計數當成主要判斷、漏了每次讀取都要先驗 `now - 產生時間 > 600s`,一個 10 分鐘前武裝、只用掉 1/3 席次的過期 armed 檔,會在第 11 分鐘把已經過期的舊 range 鏡頭誤注入給一個跟原審查完全無關的新子代理——這正是本題明確點名的極端輸入,而且是本輪修訂相對上一版的實質倒退,不是單純的措辭精簡。
