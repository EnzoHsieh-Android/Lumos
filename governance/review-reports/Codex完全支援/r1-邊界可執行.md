本機 codex 執行檔內建的 apply_patch 格式說明(`strings` 掃描得到,屬於系統提示詞的一部分)明確寫著:「`*** Update File: <path>` - patch an existing file in place (optionally with a rename)」,並附範例「`*** Update File: src/app.py` \ `*** Move to: src/main.py`」——`file: /Users/enzo/.claude/projects/-Users-enzo-harness-lumos-toolchain/26a6b57a-9efc-4073-b845-c27e42a2fbb1/tool-results/bl55m0cp3.txt:29`(`*** Move to: ` 字串本身也出現在同一支執行檔的語法定義區,行 48454)。impact-hook 適配規則只講「解 `*** Add File: / *** Update File: / *** Delete File:` 標頭取路徑」,完全沒提 `*** Move to:`。具體壞行為:一個 `*** Update File: docs/舊筆記.md` + `*** Move to: src/新模組.py` 的重新命名 patch(把一篇筆記從 `/docs/` 移到程式碼目錄,或反過來),照 spec 字面規則只會抓到 `Update File:` 後面那個**舊路徑**——若舊路徑落在 `EXCLUDE_PATH_CONTAINS`(`/docs/`)而新路徑不在排除清單內,這次改動實質上是把一個檔案移進受追蹤的程式碼區,理應觸發 `lumos impact`,但因為只看到舊路徑「在 /docs/ 底下」而被 `_is_excluded_path` 判定排除,靜默跳過。

---

### F9:「權限/安全」隱患答案完全沒有提到 hook 信任繞過旗標的連帶影響

severity: major
blocking: 是 —— 這是一個安全相關的揭露缺口,跟 F1 同源但屬於不同的具體後果,值得獨立記一條。
引句:「subagent additionalContext 內容沿用 dispatch-lens 的零自由文字消毒原則」

這節只討論了「hooks.json 寫在使用者家目錄」與「additionalContext 內容消毒」兩件事,完全沒有觸及 F1 揭露的機制:若 lumos 自己的驗證腳本或未來的自動化(例如 autonomous-iteration-loop 之類每日排程,或 S1 驗收本身)為了讓 hook 在 `codex exec` 下真的跑起來而加上 `--dangerously-bypass-hook-trust`,這個旗標官方文件明講是「Enabled hooks may run without review for this invocation」——也就是說,那一次 `codex exec` 呼叫裡**所有**已註冊的 hook(不只是 lumos 自己那五支,包含使用者自己在同一個 `~/.codex/hooks.json` 裡寫的任何其他項目,若合併器把它們合併進同一個檔案)都會跳過信任審查一起執行。這是一個實質的權限放寬動作,而且是本案為了讓自己的驗證方法論成立而必須做的選擇(見 F1),卻完全沒有出現在「權限/安全」這個明確要逐類回答的隱患欄位裡。
