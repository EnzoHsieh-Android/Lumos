# 記憶過期清掃 — 安裝/生命週期/跨環境審查(鏡頭:安裝與註冊五張表)

白話總結:這支新 hook 想做的事(揪出記憶檔裡「講當下狀態、但已經被推翻」的宣稱)是好的,五張登記表本身(複製清單、錨點清單、跳過清單、SessionStart 註冊)也確實同步、而且有機械測試互相盯著,這部分做得紮實。但它自己動手做的兩件事——「跑一條檢查」跟「算出這個專案的記憶目錄在哪」——各自藏了一個會在真實環境裡發作的洞,而且都沒有測試擋。

## F1:單條檢查真的跑起來,可以吃穿外層天花板;PER_CMD_CAP 是宣稱存在但沒人用的死碼

severity: major
blocking: 是
引句:「_git("fetch", "-q", up.split("/")[0], cwd=root, timeout=25)」

這支自己在檔頭寫了一整段道理:「★內層一定要明顯小於外層★……內層 ≥ 外層的話,『逾時就好好收尾』那條路結構上永遠跑不到——外面會先 SIGKILL,繞過所有 try/except」。註冊表把外層天花板設成 12 秒(`scripts/merge-claude-settings.py:82` `"memory-sweep.py": 12,`),`_inner_budget()` 算出來的內層 deadline 是 `12*0.7≈8.4` 秒,單看這個算式确实小於外層,`t_hook_inner_timeout_always_below_outer` 這條測試(`scripts/test_lumos.py:13869`)也確實驗過這個算式、而且驗到了新加的 `"memory-sweep.py": 12` 這一列。

問題是:deadline 只在「要不要開始跑下一條檢查」之前擋一次(`check_one` 裡 `if deadline and (deadline - time.monotonic()) <= 0: skip`),**不會在單條檢查正在執行時生效**。而 `_git()` 這個真正發射 subprocess 的函式,預設 `timeout=20`(`scripts/hooks/claude/memory-sweep.py:179`),`_is_pushed()` 裡打 `git fetch` 那一行更是明寫 `timeout=25`(`scripts/hooks/claude/memory-sweep.py:199`)——兩個數字都大於外層天花板 12 秒。文件裡示範的第一個 `verify:` 寫法就是 `pushed: fd7cdc1`,也就是說「連遠端問有沒有推」正是這支東西被設計出來要處理的主力案例,不是冷門邊角。只要一條記憶檔帶 `pushed:`/`not-pushed:`,又遇到網路慢、離線、私有倉庫要認證這類日常狀況,`git fetch` 可以卡到 20~25 秒才回——而外層 12 秒的天花板會先把整支 hook SIGKILL 掉,連「還有幾條沒驗到」那句收尾都印不出來。這正是它自己文件裡警告的那個下場,只是它自己也沒躲過。

更值得注意的是:檔案裡宣告了 `PER_CMD_CAP = 15.0  # 單條檢查最多跑這麼久`(`scripts/hooks/claude/memory-sweep.py:52`),讀起來像是「單條檢查有自己的安全上限」,但**整支檔案沒有任何地方讀取或使用這個常數**——它沒有被傳進 `_git()` 的 `timeout=`,也沒在別處被引用,是純粹的死碼,反而製造「這裡有守衛」的錯覺。

現有測試(`t_hook_inner_timeout_always_below_outer`)只匯入模組、呼叫 `_inner_budget()` 這個算式本身,從沒有真的觸發過 `_git`/`_is_pushed`,所以完全沒有機械測試會告訴你「單條檢查自己會跑多久」這件事已經違反了同一份文件宣稱的規矩。

## F2:記憶目錄的 slug 演算法只換斜線一種字元,跟同一個倉庫裡已經驗證過的規則不一致——空白/中文/底線路徑下會整支靜默失效

severity: major
blocking: 是
引句:「slug = str(pathlib.Path.cwd().resolve()).replace("/", "-")」

`memory_dir()`(`scripts/hooks/claude/memory-sweep.py:163`)自己重新算了一次「這個專案的記憶目錄在哪」,算法是把 cwd 字串裡的 `/` 換成 `-`。但同一個倉庫的 `scripts/lumos` 裡已經有一支專門幹這件事、而且**用兩條真實路徑驗證過**的函式 `_handoff_slug`(`scripts/lumos:26479`),規則是「把非英數字元**全部**換成 `-`」(`re.sub(r"[^A-Za-z0-9]", "-", str(path))`)。

我直接去 `~/.claude/projects/` 底下看真實目錄名做對照:裡面有 `lumos-probe--8zcxzgk` 這種名字(來自 `tempfile.mkdtemp(prefix="lumos-probe-")` 產生的隨機字尾,Python 的隨機字元表 `string.ascii_lowercase+digits+"_"` 本身就會產生底線)。名字裡出現連續兩個 `-`,代表原始路徑裡的底線 `_` **也被 Claude Code 自己換成了 `-`**——證實 Claude Code 真正的慣例是「非英數字元都換」,不是「只換斜線」。我也用 Python 直接跑一次兩種演算法的對照(路徑 `/Users/enzo/my_project (v2) 測試/repo`):
```
naive(現在這支用的)      : -Users-enzo-my_project (v2) 測試-repo
aggressive(_handoff_slug 用的): -Users-enzo-my-project--v2-----repo
```
兩者從第二段開始就完全分岔。也就是說,只要專案路徑帶底線、空白、括號或中文(審查點名的三種案例全部命中),`memory_dir()` 算出來的路徑就不是 Claude Code 實際使用的那個目錄,`here.is_dir()` 恆為 False,main() 直接 `return 0`——整支 hook 對這種專案永遠靜默空轉,**沒有任何錯誤、沒有任何「跳過」的訊息**,看起來裝好了、其實從沒真的驗過一次。這在 Windows 下更糟:cwd 會是 `C:\Users\...` 這種字串,裡面沒有 `/` 可換,`.replace("/", "-")` 完全不動它,slug 會帶著反斜線與磁碟代號冒號原樣留著。

`t_memory_sweep_core`(`scripts/test_lumos.py:39983`)只測了 `verify_blocks`/`_stem`/`stamp`/`is_stamped`/`unstamp` 四件事,完全沒有測 `memory_dir()` 或 `graph_stems()` 對各種路徑字元的行為——這正是這個工具鏈自己在別處提醒過的「同一件事兩套算法一定分岔,而分岔時沒有任何東西會翻紅」的活教材,只是這次分岔的是兩個都自己寫的版本(`usage_scan.py:56` 也是同一種只換斜線的窄版,並非本次新增,但這次新增的 hook 本可以重用 `_handoff_slug` 卻沒有)。

## F3:對 Codex 這一家,這支 hook 要嘛完全沒用、要嘛變成用 Codex 的事件去改 Claude 的狀態檔

severity: minor
blocking: 否
引句:「收下但不用它——這支對兩家做的事一樣。」

`memory-sweep.py` 的 `--harness` 參數(`ap.add_argument("--harness", default="claude")`)確實收得下安裝器多帶的 `--harness codex`,argparse 不會炸;但程式碼裡完全不讀這個值。而 `memory_dir()` 寫死的是 `~/.claude/projects/<slug>/memory`——這是 Claude Code 專屬的自動記憶慣例,Codex 沒有這個資料夾。

後果分兩種:①純 Codex 專案(從沒開過 Claude Code)下,`~/.claude/projects/<slug>/memory` 永遠不存在,這支 hook 在 Codex 的每次 SessionStart 都會被觸發、開一個 Python 行程、算路徑、發現目錄不在、安靜結束——對 Codex 使用者完全沒有保護效果,純粹白跑。②兩家都用同一個專案時,從 Codex 開場觸發的這次執行,實際上會去讀/蓋章 Claude 那邊的記憶檔——變成「由另一個宿主的事件觸發,去改屬於第一個宿主狀態的檔案」,這件事在文件與程式裡都只用一句「這支對兩家做的事一樣」帶過,沒有處理過「這樣做對 Codex 使用者是否有意義」。不算破壞(fail-open、無副作用之外的傷害),但屬於「登記了卻沒有對應語意」的設計落差。

## F4:圖譜比對只認 `.git` 當邊界,非 git repo 或巢狀專案下會一路往上爬、而且找不到圖譜時完全不吭聲

severity: minor
blocking: 否
引句:「if (cand / ".git").exists():」

`graph_stems()`(`scripts/hooks/claude/memory-sweep.py:69`)往上爬父目錄找 `docs/*knowledge*`,唯一的停止條件是「撞到 `.git`」。如果目前目錄不是 git repo(或使用者在 repo 外層某個沒有 `.git` 的巢狀資料夾底下開 Claude),迴圈會一路爬到檔案系統根目錄,途中如果剛好撞到任何一層(哪怕跟目前專案毫不相干)有 `docs/*knowledge*` 資料夾,就會把那份圖譜拿來做「影子副本 / 壞指標」比對——跨專案汙染。找不到圖譜的另一半(真的一路爬到根目錄還是沒找到)則是 `cross_check()` 直接回傳 `False`、什麼都不印;這個工具鏈在 doctor 的 S6 檢查上明文立過「沒有總索引時要出聲說跳過,不是靜默不做」的規矩,這支沒跟上。影響範圍僅止於「影子副本/壞指標」這個啟發式的加分檢查,不影響 `verify:` 那組全機械檢查,所以定為 minor。

## F5:`HOOK_ARGS` 是這批新增的表,完全沒有機械測試覆蓋

severity: minor
blocking: 否
引句:「"memory-sweep.py": "--write --quiet",」

五張表裡,`_VENDORED_TREE_FILES`(有逐檔比對測試)、`ANCHOR_FILES`+`anchor-baseline.json`(有鍵集合相等測試)、`_GLOBAL_CLAUDE_HOOKS`↔`HOOK_ENTRIES`(有 `hook_copy_list_completeness` 通則測試,`scripts/test_lumos.py:14294` 附近,是動態掃 `HOOK_ENTRIES` 產生的,memory-sweep.py 自動被涵蓋)都各自有機械測試守著,漏登記會直接翻紅,這部分做得對。`HOOK_BUDGET` 漏登記則是「吵的」失敗:`HOOK_ENTRIES` 字典字面量裡直接 `HOOK_BUDGET["memory-sweep.py"]` 索引,忘了登記會讓整支安裝器在載入時就 `KeyError` 炸掉,不會被忽略。

但 `HOOK_ARGS`(`scripts/merge-claude-settings.py:87`)是這次新加的表,通篇 `scripts/test_lumos.py` 搜不到一處提到 `HOOK_ARGS`。忘記登記、或把檔名打錯一個字,後果是**完全安靜的**:`_bf += (' ' + HOOK_ARGS[rel_path]) if rel_path in HOOK_ARGS else ''` 這個寫法只會讓最終指令少掉 `--write --quiet`,不會報錯——蓋章功能整個變成唯讀(只看不寫,警告永遠留在終端機那一次性的輸出裡、不會寫回記憶檔),而且因為少了 `--quiet`,每次 session 開場只要有 `verify:` 區塊就會印一次報告,即使什麼都沒過期——這正是這個工具鏈自己記錄過的「喊了幾十天沒人理的空轉週報」那種噪音死法的同型風險。

## 附註(非 finding):跨平台 Windows 的處理跟其餘既有 hook 一致,沒有新落差

`_hook_cmd()` 裡的 Windows 特化(反斜線轉正斜線、python 路徑加引號、Codex 用絕對路徑不用 `${HOME}`)是安裝器端統一處理的,五支既有 hook 跟這支新 hook 一視同仁;而五支既有 hook 本體(`.py` 檔內部)也都沒有任何 `win32`/`platform` 特判(`grep -rn "win32\|Windows\|platform" scripts/hooks/claude/*.py` 全部落空),所以「其他 hook 有特別處理、這支沒跟上」這個猜測不成立——大家在同一條起跑線上。真正在 Windows 下會發作的問題,是 F2 那個 slug 演算法本身沒處理反斜線與磁碟代號冒號,已經併入 F2 陳述,不重複計分。
