## finding 1 — `--restore` 與一般 `--write` 掃描都會穿過符號連結,寫到記憶目錄外面的檔案

r1 資安席原本抓到的是「`--restore ../../etc/passwd` 這種路徑字串可以穿越出去」,r2 的修法是只取 `Path(a.restore).name`(拿掉路徑部分)。但這個修法只防「引數字串裡帶路徑」,沒有防「記憶目錄裡本來就放了一個檔名正常、但實際是指到目錄外面的符號連結」。記憶目錄的信任層級跟記憶檔案本身一樣(docstring 自己講的:「任何能往記憶目錄寫檔的東西都拿到開專案就執行一次的能力」),放一個符號連結進去門檻並不高。

實測(在 `/private/tmp/.../scratchpad/msweep-review` 下做,沒有碰到 lumos-toolchain 這個 repo 本體):

```
memdir2/evil.md -> .../outside2/secret.md   # 連到記憶目錄外面的檔案
$ python3 memory-sweep.py --dir memdir2 --restore evil.md
撤掉蓋章:evil.md
```
結果 `outside2/secret.md`(記憶目錄外面、原本不該被這支 hook 摸到的檔案)真的被讀出來、跑過 `unstamp()`、再寫回去 —— 外面那個檔案的 `status: stale` 等欄位跟警告行都被拿掉了。

同一個洞不只 `--restore` 有,連正常的 `--write` 全量掃描也一樣:記憶目錄裡放一個 `link.md -> outside3/target.md` 的符號連結,`memory-sweep.py --dir memdir3 --write` 直接把 `outside3/target.md` 蓋上章,這個檔案本來完全在記憶目錄之外。

也就是說,只要能在記憶目錄裡放一個檔名正常的符號連結,就能讓這支「每次開場自動執行」的 hook 讀取並且**寫入**任意其他有權限碰到的檔案 —— 這比單純的路徑穿越更嚴重,因為連正常掃描(不需要用到 `--restore`)都中招,而且是寫入不只是讀取。

severity: blocker
blocking: 是
引句:「★只收檔名,不收路徑★(r1 資安席 major:實測可以穿越出去改別的檔)」

## finding 2 — 撤章的「跑完且通過」在 verify 區塊是空的時候會被空歡喜地判定成立

r2 加的不變量是:「撤章只在『這篇的每一條檢查都真的跑完、而且都通過』時才做」,靠 `check_one` 回傳的 `complete` 旗標把關。但 `complete` 初始值是 `True`,而 `verify_blocks(text)` 如果找不到 `verify:` 區塊就回傳空陣列 —— 迴圈一次都沒跑,`complete` 從頭到尾維持 `True`、`unknown` 也是空的。於是一篇「本來被蓋過章、但 verify 區塊後來不見了(被手動改壞、被別的流程截斷開頭欄位…)」的記憶檔,下一輪掃描會被判定成「每一條都真的跑完且成立」,直接撤章 —— 即使實際上一條檢查都沒有真的執行過。

實測(直接呼叫模組函式,不是猜測):
```python
stamped_no_verify = "---\nname: y\nmetadata:\n  type: project\n  status: stale\n  ...\n---\n\n正文\n"  # 沒有 verify: 區塊
failed, unknown, complete = ms.check_one(stamped_no_verify, None, tally, Path("."))
# failed=[] unknown=[] complete=True
ms.apply_one(Path("y.md"), stamped_no_verify, failed, unknown, complete, "2026-09-14", False, tally)
# tally.recovered == 1
# tally.lines == ['✓ y.md(原本蓋過章,現在每一條都跑完且成立,撤掉)']
```
印出來的訊息本身就是假的 ——「每一條都跑完且成立」,但根本沒有任何一條 claim 被跑過。這正是題目要驗的那個漏洞:資訊不完整(零檢查)也能把章撤掉。

severity: major
blocking: 是
引句:「★撤章的唯一條件★:這篇每一條檢查都真的跑完而且都通過。」

## finding 3 — `verify:` 區塊裡「- claim: 打錯字」這種寫法還是會靜靜消失

r2 的 `verify_blocks` 宣稱「不認得的寫法不准靜靜丟掉」,把 claim 沒配到型別鍵、型別鍵打錯字的情況都改成收下、標成 `?<原鍵名>` 或 `?missing`。但只處理了「先出現 `- claim:` 之後接著的鍵打錯字」這一種形狀;如果連 **`- claim:` 這個開頭本身就打錯字**(例如寫成 `- calim:`),迴圈邏輯是:
```python
if s.startswith("- claim:"):        # 打錯字這行不會進來
    ...
if claim is None or ":" not in s:    # claim 還是 None,這裡直接 continue
    continue
```
這一行連帶它底下配的型別(`pushed: abc1234`)整條就這樣消失,不會出現在 `verify_blocks` 的回傳裡,也不會被記成任何一種「驗不了」——跟修之前「三種畸形寫法整條蒸發」是同一個症頭,只是換了個觸發寫法。

實測:
```python
txt 含 "  - calim: 這條claim鍵打錯字\n    pushed: abc1234\n" 加上正常的第二條 claim
ms.verify_blocks(txt) == [('乙', 'not-installed', 'eslint')]   # 第一條完全不見,不是 ?missing 也不是 ?calim
```

severity: major
blocking: 是
引句:「★不認得的寫法不准靜靜丟掉★(r1 正確性席與外家席):原本 claim 沒配到型別鍵、」

## finding 4 — 狀態詞綁同一行,換來的是「節點名跟狀態詞分兩行寫」就抓不到

r2 把「這篇對某節點講了什麼狀態」從「整篇正文搜」改成「只看提到該節點那一行」,理由是修掉「一篇裡兩個節點狀態互相污染」的假陽性。但這個做法本身製造了新的漏報:記憶檔常見的寫法是把節點連結獨立成一行、狀態描述寫在下一行(項目符號、換行條列都很常見),`_claims_near` 逐行比對抓不到跨行的情況。

實測:
```python
body = "[[Projects/Alpha]]\n已交付。\n"
ms._claims_near(body, "Alpha")   # (False, False) —— 沒抓到 live=已交付
# 對照:同一行寫法 "[[Projects/Alpha]] 已交付。" → (False, True) 正常抓到
```
也就是說,只要記憶檔把節點連結跟狀態描述分兩行寫(很自然的寫法),`pointer_problems` 的狀態打架偵測就完全偵測不到 —— 這是修「跨節點誤判」時新換來的盲區,題目第 6 點問的正是這個。

severity: major
blocking: 是
引句:「★要綁到節點,不能拿整篇去套★」

## finding 5 — 記憶目錄裡「剛好是壞掉符號連結」的檔案會完全消失、不進 broken 統計

r2 把 `read_memories` 包了 try/except,宣稱「非 UTF-8、剛好叫 x.md 的目錄…—原本任一種就整支 Traceback」都處理掉了、而且處理不了的檔案會被記進 `tally.broken` 好讓人事後查。但如果記憶目錄裡有一個檔名是 `.md`、實際是**指向不存在路徑的符號連結**,`f.is_file()` 對壞掉的符號連結回傳 `False`(因為 stat 不到目標),於是這一行:
```python
if f.name == "MEMORY.md" or not f.is_file():
    continue
```
直接把它跳過 —— 不進 `tally.broken`、`tally.lines` 裡也沒有任何一行提到它,整個消失得無聲無息,連 `python3 ~/.claude/hooks/memory-sweep.py --dir <記憶目錄>` 這種「查某一篇為什麼」的指引都用不上,因為它根本不會被列進任何清單。這正是這一輪標題「一支壞檔不再靜靜蒸發」宣稱要根除的那一類問題,只是換了一種壞法(壞掉的符號連結)沒被涵蓋到。

實測:
```
memdir1/broken-link.md -> /nonexistent/target/does-not-exist.md
files = ms.read_memories(Path("memdir1"), tally)
# files == [(good.md 的路徑, ...)]   ← broken-link.md 完全沒出現
# tally.broken == 0, tally.lines == []
```

severity: major
blocking: 是
引句:「把記憶檔讀進來。★一支壞檔不准炸掉整輪★(r1 四席獨立抓到的 blocker):」

## 逐條驗過、確認站得住腳的部分

- **第 3 點(git 逾時加起來會不會超過外層 12 秒)**:用假 `git`(`rev-parse` 秒回、`fetch`/`merge-base` 各自掛住)實測 `--budget 12` 的完整流程,兩種組合(fetch 掛住 / fetch 秒回但 merge-base 掛住)實測耗時分別是 8.91 秒與 8.5 秒,都在 12 秒外層天花板之內。追一遍程式碼可以確認結構上也站得住:`_is_pushed` 一旦 `fetch` 失敗或逾時就直接回傳、不會再呼叫 `merge-base`,所以單一 claim 最多兩次 git 呼叫吃滿當時剩餘預算;而 `check_one` 對「下一條 claim」的 deadline 檢查是在每條 claim 開始前重新算「現在幾點」,不是把多條 claim 的配額相加,所以在單執行緒、依序處理的前提下,最多只有一條 claim 能真的「衝過」deadline,不會有多條 claim 各自吃滿 floor(1 秒)疊加爆掉的情況。另外量了一下:`read_memories`/`cross_check`(掃整個知識圖譜)完全沒有納入這個預算換算,但用貼近這個 repo 真實規模的資料(569 篇圖譜筆記、77 篇記憶)量測只要 0.12 秒,就算灌到 4000 篇圖譜筆記 + 300 篇記憶也還是 0.12 秒,在目前的量級下不構成問題,只是要留意「這段完全不受 --budget 保護」這件事沒有寫進說明。
- **第 4 點(fetch 失敗會不會拿舊資料回答)**:追過 `_is_pushed` 全部路徑 —— `_git` 逾時或非零結束碼都回 `None`,`_is_pushed` 收到 `fetched is None or fetched.returncode != 0` 一律直接回傳 `None`(驗不了),不會往下走到用本地既有的 remote-tracking ref 去判斷。沒找到會拿舊資料回答的路徑。
- **第 8 點(注入框、逾時預算兩段跟 `ci-status-hook.py` 逐字比對)**:寫小腳本把兩支檔案裡「注入框」與「逾時預算」兩個區塊各自抓出來字串比對,結果完全一致(`FRAME identical: True`、`BUDGET block identical: True`)。
- **第 9 點(測試的四根翻紅釘)**:在 `/private/tmp/.../scratchpad/msweep-review/canary-repo` 複製一份完整 `scripts/`(沒動到 lumos-toolchain 本體),依序真的把四個保護拆掉重跑 `python3 scripts/test_lumos.py -k t_memory_sweep_core`:
  - `_stem` 換回 `name.rstrip(".md")` → `② 去副檔名不削掉結尾字母` 翻紅
  - `is_stamped` 換成子字串比對(`"status: stale" in text`)→ `④ 正文寫到那幾個字不算蓋過章` 翻紅
  - `apply_one` 撤章條件拿掉 `complete`(`elif was and not unknown`)→ `⑥ 沒驗完就不准撤章` 翻紅
  - `read_memories` 拿掉 try/except → 整支測試直接丟未捕捉的 `UnicodeDecodeError` 中斷
  四根都真的翻紅,不是假守衛。每次拆完都用 `diff` 確認已還原成原檔、沒有留下改動。

**九項逐條驗證方式一覽**:① 用符號連結(壞掉的、指到外部檔案的)直接呼叫 `read_memories`/`--restore`/`--write` 實測;② 直接呼叫 `check_one`/`apply_one` 建構「有章但 verify 為空」的情境;③ 用假 `git` 腳本量測兩種逾時組合的真實耗時,並用真實規模資料量測掃描階段;④ 通讀 `_is_pushed` 全部分支;⑤ 用真實惡意寫法(`- calim:` 打錯字)呼叫 `verify_blocks`;⑥ 建構節點名與狀態詞分行的記憶正文呼叫 `_claims_near`;⑦ 用符號連結測 `--restore` 與 `--dir` 的組合;⑧ 寫腳本逐字串比對兩支檔案的對應區塊;⑨ 在乾淨複本上逐一拆線,實際重跑測試看翻紅。所有 git 操作都在 `/private/tmp/.../scratchpad` 底下用假 `git` 或臨時 repo,沒有在 `/Users/enzo/harness/lumos-toolchain` 裡執行任何 commit/reset/restore/checkout/stash,也沒有修改該目錄下任何檔案。
