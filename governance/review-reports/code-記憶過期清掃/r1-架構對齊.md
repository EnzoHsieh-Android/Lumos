severity: major

鏡頭:架構對齊——只判「這個寫法跟這個 repo 既有的做法一不一樣」，不判 bug、不判風格。

比喻先講:這個 repo 對「一打開資料夾就自動跑」的六支 hook，本來像六個穿同一套制服的哨兵——同一套逾時算法、同一套「跑完了要回報」的機制、同一套「機器附加的文字要框起來」的安全規矩。這次新增的第六支（memory-sweep.py）自己換了一套便服，而且換的三個地方剛好都是這個 repo 過去為了同一類問題吃過虧、專門立守衛盯住的地方。

## finding 1：完全沒接「我跑完了」記帳，`lumos enforcement` 對這支 hook 永遠是隱形的

其他五支 hook（`lumos-entry-hook.py`、`check-graph-sync.py`、`ci-status-hook.py`、`dispatch-lens-hook.py`、`impact-hook.py`）在檔尾都會 `from _hookevent import guard`，把 `main()` 包起來，讓每次執行的成功/逾時/例外被記進 `governance/runtime/hook-events.jsonl`。這件事的動機寫得很白：`_hookevent.py` 檔頭就說「`lumos enforcement` 原本只驗『有沒有註冊』，答不出『它最近有沒有真的跑過』」。

memory-sweep.py 整支 457 行 diff 裡沒有任一處 `_hookevent` 或 `guard(`。檔尾直接：

引句:「if __name__ == "__main__":
+    sys.exit(main())」

對照五支現役 hook 的檔尾寫法：
file: `scripts/hooks/claude/ci-status-hook.py:220`（`from _hookevent import guard as _guard`）、`scripts/hooks/claude/ci-status-hook.py:224`（`sys.exit(_guard("sessionstart-ci-status-hook", __file__, main, swallow=True) if _guard else main())`）
file: `scripts/hooks/claude/check-graph-sync.py:840`-`843`（同樣的 import + guard 包裝）
file: `scripts/hooks/claude/_hookevent.py:127`（`def guard(hook_name, hook_file, main, swallow=False):` 這支是五個 hook 共用的入口）

後果不是「少一行裝飾」：`lumos enforcement` 判各層防護狀態的清單是寫死枚舉的，這支新 hook 根本不在裡面——

file: `scripts/lumos:16146`-`16150`：
```
for layer, needle in (("session-entry-hook", "lumos-entry-hook.py"),
                      ("pretooluse-impact-hook", "impact-hook.py"),
                      ("stop-graph-sync-hook", "check-graph-sync.py"),
                      ("sessionstart-ci-status-hook", "ci-status-hook.py"),
                      ("pretooluse-dispatch-lens-hook", "dispatch-lens-hook.py")):
```

也就是說 memory-sweep.py 不只是「沒記帳」，是**連 `lumos enforcement` 的判準清單都沒把它列進去**——它靜靜卡住、逾時、或每次都丟例外，`lumos enforcement` 一個字都不會說。這正是 `_hookevent.py` 那份設計說自己要防的洞（"它把兩道每次推送都在跑的 git 閘印成 inactive"那次事故），這支新 hook 把同一個洞原樣重開了一次。

severity: major
blocking: 是

## finding 2：輸出走裸 `print()`，跳過「機器附加文字要框」這條全 repo 統一過的規矩

`lumos-entry-hook.py` 和 `ci-status-hook.py` 都是 SessionStart hook，兩支都用同一套結構把要塞進對話的內容包起來：`print(json.dumps({"hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": _frame_injected(msg)}}, ...))`，並且節點名／檔名這類「看起來無害」的欄位一律先過 `_plain_label` 消毒。這套規矩不是隨手加的，兩支檔案裡都用大段註解記著出處：「★2026-09-07 架構審查席裁的:同一個問題不准有兩套慣例★」——上一次就是因為一支 hook 有框、另一支還是舊的「句尾一句話」，被架構審查席當場打回。

memory-sweep.py 的 `main()` 完全不走這條路，直接：

引句:「print("記憶過期清掃:")
+        for ln in tally.lines:」

`tally.lines` 裡塞的是從記憶檔正文抽出來的原文片段——例如 `apply_one()` 裡的 `對不上了:%s"`、`cross_check()` 裡把 `shadow_copies()`/`pointer_problems()` 抓到的「踩到哪個字」「指到哪個節點名」原樣接進字串印出去。這些內容來源正是「記憶目錄裡的檔案」，跟 `ci-status-hook.py` 要框住的「CI 紀錄檔的 workflow 名稱」、`lumos-entry-hook.py` 要框住的「圖譜筆記內容」屬於同一類「repo 裡的人寫得動、會被當成系統話讀進對話」的資料——但這支既沒有 `_frame_injected`，也沒有 `_plain_label`，連框常數 `_FRAME_OPEN`/`_FRAME_CLOSE` 都沒有出現在這支檔案裡一次。

這不是漏測：測試 `t_all_injection_paths_are_framed_and_unified` 的第④段是用 `hooks_dir.glob("*.py")` 掃全部 hook，但判準是「這一行裡有沒有 `"additionalContext"` 這個字」——memory-sweep.py 根本不產生這個欄位，所以掃不到它，測試照樣全綠。是「用了另一套輸出管道」把既有的機械守衛繞過去了，不是守衛本身失效。

severity: major
blocking: 是

## finding 3：內層逾時預算自己重寫一份實作，脫離「複本不准漂」的守衛範圍

`Systems/hook逾時預算` 這段邏輯（外層天花板 × 0.7 減掉已耗、下限 1 秒）在另外五支 hook 裡是逐字相同的複本，而且逐字比對本身就是一道測試：`t_hook_inner_timeout_always_below_outer` 掃 `hooks_dir.glob("*.py")`，抓 `_BUDGET_RATIO = .*?return max(_BUDGET_FLOOR,...)` 這段文字，五支的雜湊必須相同。

memory-sweep.py 沒有沿用這份複本，自己另寫一份概念相同但寫法不同的版本：

引句:「total = (_OUTER if _OUTER else default) * 0.7
+    used = elapsed if elapsed is not None else (time.monotonic() - _T0)」

對照被複製的那一份：
file: `scripts/hooks/claude/lumos-entry-hook.py:116`-`142`（`_outer_budget()` 自己解析 `sys.argv` 找 `--budget`，並把過大的值夾到 600 秒上限）
file: `scripts/hooks/claude/lumos-entry-hook.py:145`-`169`（`_inner_budget()` 用 `_BUDGET_RATIO`/`_BUDGET_FLOOR` 這兩個具名常數）

memory-sweep.py 的版本：① 不自己解析 `--budget`，改靠 `main()` 裡 `argparse` 解出來後存進模組全域 `_OUTER`（見 `_build_parser`/`main` 那段 `_OUTER = a.budget or None`）；② 沒有 600 秒上限夾住的邏輯；③ 完全沒有 `_BUDGET_RATIO`/`_BUDGET_FLOOR` 這兩個名字，於是上面那道逐字比對的守衛測試根本掃不到它——不是「這支也守住了」，是「這支長得不像，測試認不出來要管它」。這正是同一份文件的合約自己講的道理：「同一件事兩套算法一定分岔，而分岔時沒有任何東西會翻紅」（見附帶的 `docs/…/節點範圍與索引守衛.md` INVARIANT）——這裡不是分岔的隱憂，是已經分岔了。

severity: major
blocking: 是

## finding 4：自己重寫 wikilink／frontmatter 解析，而不是沿用 `scripts/lumos` 既有那一套

這點跟本次派工單附的固定席節點 `節點範圍與索引守衛.md` 那條 ★INVARIANT★ 幾乎是同一件事的翻版："三道都★重用既有的抽取與解析★,不自己再寫一套……同一件事兩套算法一定分岔"。`scripts/lumos` 裡已經有一套被全專案共用、而且有明確排除規則的 wikilink 解析（`WIKILINK_RE = re.compile(r"\[\[([^\[\]]+?)\]\]")`，並且明文排除 fenced code block、inline code、block scalar 內的 `[[..]]`——這幾條排除規則有專門的「鐵則 2」在管），以及共用的 frontmatter 解析（`split_frontmatter`/`parse_frontmatter`）。

memory-sweep.py 對「這篇記憶連到哪個節點」「這個節點的 status 是什麼」這兩件事，各自另外寫了一份簡化版正則，完全不呼叫 `scripts/lumos`：

引句:「_LINKED_REF = re.compile(r"\[\[([^\]|#]+)\]\]")」

引句:「m = re.search(r"(?m)^status:[ \t]*([A-Za-z_-]+)", head)」

跟 `scripts/lumos` 既有那套比：
file: `scripts/lumos:177`（`WIKILINK_RE = re.compile(r"\[\[([^\[\]]+?)\]\]")`）
file: `scripts/lumos:229`（`def split_frontmatter(text):`）、`scripts/lumos:240`（`def parse_frontmatter(fm_lines):`）

這不是純粹風格：`_LINKED_REF` 沒有排除 block scalar（`summary: |-` 那種）內的 `[[..]]`，而 `scripts/lumos` 那套為此專門留了規則（"鐵則 2"）——也就是說如果哪篇記憶的 `summary:` 區塊裡寫了 `[[某節點]]`，memory-sweep.py 會把它當成一條真連結去查，跟 `scripts/lumos` 判斷「這算不算連結」的結果可能對不上，正是這個專案自己記錄過會出事的那一種分岔（doctor 曾經因為兩套算法分岔，把「關鍵概念行」的數字誤寫成「合約」）。

severity: major
blocking: 否（目前記憶目錄裡沒有把 wikilink 寫進 block scalar 的先例，屬於「已經是兩套算法」但尚未實際觀察到分岔案例；仍建議在合入前改掉，理由同上）

## finding 5：SessionStart 輸出沒有照「發生什麼→為何在意→指令獨立一行」收尾

check-graph-sync.py 的提醒收在「筆記放在這裡:\n   {graph_rel}/」，ci-status-hook.py 收在「本輪開工前先處理或明確跳過；細節：lumos ci-status」——都在訊息尾端留一行可以直接照做的指令或路徑。memory-sweep.py 的輸出收在：

引句:「print("跑了 %d 條檢查%s。" % (tally.checked, "(已蓋章)" if a.write else "(只看)"))」

列完 `✗`/`★`/`?` 這些條目後，只交代「跑了幾條檢查」，沒有交代「發現對不上了要怎麼辦」——例如沒提到 `--restore <檔名>` 這個撤章指令怎麼下、也沒有像其他 hook 一樣點出下一步該敲哪個 `lumos` 子指令。跟另外五支比是同一個 SessionStart 事件、卻是不同的收尾形狀。

severity: minor
blocking: 否

## 總結

5 條，全部指向同一件事：新加的第六支 hook 在「記帳」「注入安全框」「逾時預算」「圖譜解析」四個已經有機械守衛盯著的地方，各自换了一套自己的做法，而且四套換法沒有一套被既有的漂移測試抓到——不是測試失效，是它們的判準（比對特定變數名／特定 JSON 欄位／特定枚舉清單）認不出這是「同一類東西的第二種做法」。最高等級 major；最嚴重的一條是完全沒有接上 `_hookevent` 記帳與 `lumos enforcement` 判準清單，導致這支會改寫記憶檔的新 hook 一旦逾時或出錯，整個工具鏈對此完全無感。
