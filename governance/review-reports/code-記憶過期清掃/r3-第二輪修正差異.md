## finding 2 — 就算是有修到的 `--write` 掃描路徑,`_inside()` 本身也能被硬連結繞過,而且驗證跟寫入之間有時間差可以換掉檔案

`_inside()` 只比較 `f.resolve(strict=True).parent == here.resolve(strict=True)`。硬連結(hard link)不是路徑指向,是同一個 inode 直接出現在記憶目錄裡——`resolve()` 對硬連結不會「解出」任何別的路徑,所以 `is_symlink()` 回 False、`_inside()` 也回 True,完全被當成一支普通的記憶檔讀進去、蓋章寫回去,而寫回去改的其實是目錄外那個檔案的內容(同一個 inode)。

實測(在 `/tmp/msweep-review/hardlink_test.py`):
```
os.link(outside4/hardlink-victim.md, memdir4/h.md)
_inside(h.md, memdir4) == True   # 完全過關
read_memories 把它當一支正常的記憶檔讀進來、算 broken=0
之後對它做一次改寫 -> outside4/hardlink-victim.md 的內容真的被改了
```

另外,就算不用硬連結,`_inside()` 只在 `read_memories()` 那一次呼叫時檢查過,`sweep()` 真正落筆寫檔是在 `apply_one → _safe_write` 那一步,中間隔著 `check_one` 對每條 claim 跑 `git fetch`/`git merge-base`(每條最多可以吃到 `_budget_left()` 那麼久,好幾秒的量級)。這段時間夠讓一個能寫記憶目錄的人把「讀取時是真檔」的檔案换成指到目錄外的符號連結——實測直接把 `read_memories` 讀出來的檔案在呼叫 `apply_one` 之前換成符號連結,寫入照樣穿過去、改到目錄外的檔案。也就是說 `_inside()` 是「檢查那一刻」有效,不是「整個 sweep 期間」有效。

severity: blocker
blocking: 是
引句:「比只在 --restore 擋路徑穿越更嚴重,因為不需要任何人手動下指令」
查證:`scripts/hooks/claude/memory-sweep.py:538`-`546`(`_inside` 定義)、`:549`-`569`(`read_memories`,只在讀檔當下呼叫一次 `_inside`)、`:507`-`524`(`apply_one`/`_safe_write` 真正落筆的地方,沒有再驗一次)。

## finding 3 — 段落放寬規則沒有檢查「段落裡唯一提到的節點」是不是就是被查的那個節點,兩個名字有子字串關係時會把狀態詞算給錯的節點

這代表 r2 的「跨行也抓得到」修法,換來的是「兩個節點名字有前後包含關係時,狀態詞會被算到錯的、根本沒被提到的那個節點上」——真實圖譜有 500+ 個節點,名字互為前綴/子字串並不罕見,這條規則在真實記憶目錄上會製造新的假陽性(`pointer_problems` 拿這個結果去跟圖譜節點狀態比對,會把衝突報到錯的節點頭上)。

severity: major

## finding 4 — 新加的「?listitem 要出聲」分支,在「一個 claim 還沒配到型別鍵就緊接著下一個列點」時,反而讓那個 claim 整條靜靜消失

`- claim:` 分支在遇到新的 `- claim:` 開頭、且上一條 `claim` 還沒配到型別鍵時,會先補一筆 `?missing` 再覆蓋 `claim` 變數,不會讓上一條平白消失。但新加的 `?listitem` 分支(給「長得像列點卻不是 `- claim:`」的行用)沒有做這個檢查——它直接 `claim = None`,如果這一行出現的時候「上一條 claim 還沒配到型別鍵」,那條 claim 就跟著這次 `claim = None` 一起蒸發,不會被記成 `?missing`,也不會被記成 `?listitem`(因為 `?listitem` 記的是這一行本身的文字,不是被吞掉的那條 claim)。

實測(`- claim:` 後面直接接另一個 `-` 開頭的列點,而不是正常的 `型別: 值`,是完全看得懂的手誤——把每個欄位都寫成列點):
```python
txt 含:
  - claim: 某功能忘了型別鍵,誤把型別也寫成列點
  - pushed: abc1234
  - claim: 乙
    not-installed: eslint

ms.verify_blocks(txt) == [
    ('- pushed: abc1234', '?listitem', ''),
    ('乙', 'not-installed', 'eslint'),
]
```
「某功能忘了型別鍵,誤把型別也寫成列點」這條 claim 完全不在回傳裡——不是 `?missing`,不是 `?listitem`,就是消失了。這正是這一輪修正的標題「不認得的寫法不准靜靜丟掉」宣稱要根除的那個症頭,只是換了個觸發寫法(緊接著另一個列點,而不是打錯型別鍵名)又重新發生一次。

severity: major
blocking: 是
引句:「長得像清單項卻不是 - claim: → 出聲,不要靜靜丟掉(r2 修正差異席 major)」
查證:`scripts/hooks/claude/memory-sweep.py:265`-`296`(`verify_blocks`,`?listitem` 分支在第 283-287 行沒有比照 `- claim:` 分支先把懸空的 `claim` 補成 `?missing` 再歸零)。

## 逐條查證、沒發現新問題的部分

### 項目 2 —「一條都沒跑不算完成」(`complete and ran > 0`)

- 通讀 `check_one` 全部分支:`ran` 只在「沒有因為 deadline 被跳過」時才 +1,跟 `tally.checked` 同步累加,沒有找到「跑了卻算沒跑」或反過來的分支。
- 驗過退化情境:`verify_blocks` 回傳空陣列(沒有 `verify:` 區塊、或區塊被清空)時迴圈一次都不跑,`ran` 維持 0,`complete` 因為 `and ran > 0` 被強制拉成 `False`,不會再誤判「跑完且成立」去撤章——這正是 r2 report finding 2 示範的洞,現在補上了。
- 沒有找到「這條修改讓原本該撤的章永遠撤不掉」的路徑:只要 `verify:` 區塊裡有至少一條能被解析出來的項目(即使是 `?missing`/`?listitem` 這種驗不了的),`ran` 就會 > 0,後續是否撤章仍然由 `complete and not unknown` 決定,不受這次改動影響。

severity: clean
blocking: 否
引句:「verify 區塊被清空時,failed 與 unknown 都是空的,原本會判定成立、印出假訊息、把章撤掉」

### 項目 5 — 壞掉的符號連結要出聲

- `read_memories` 裡 `f.is_symlink()` 對「目標不存在的符號連結」一樣回 True(跟目標存不存在無關),所以第一個判斷式就會攔下來,計入 `tally.broken` 並寫一行 `tally.lines`。
- 實測(`/tmp/msweep-review` 的 `memdir2/broken.md -> memdir2/nope-xyz`,以及混合一支指到目錄外但存在的符號連結):`tally.broken == 2`,兩支都出現在 `tally.lines` 裡,不會無聲消失。

severity: clean
blocking: 否
引句:「★不是只跳過,要出聲★(r2:壞掉的符號連結原本完全消失、不進任何統計)」

### 項目 3 —「?listitem」規則本身會不會誤傷合法寫法(型別鍵的值以 `-` 開頭、verify 區塊裡的多行值)

- 這支工具目前七種型別的值全部是單行純量(sha、日期、工具名、路徑),沒有任何一種支援多行/巢狀清單值,`verify:` 區塊裡只有「`- claim: ...`」這一種寫法允許行首出現 `-`;其餘型別鍵(`pushed`、`file-exists`……)本身的名字都不以 `-` 開頭,所以「這一行以 `-` 開頭」跟「這是合法的型別鍵/值那一行」在目前的語法下不會衝突。
- 檢查過文件裡示範的實際寫法(`docs/lumos-toolchain-knowledge/Systems/記憶過期清掃.md:43`-`46`,型別值後面帶行內註解 `# 或 not-pushed / …`),註解行本身不以 `-` 開頭,不會誤觸。
- 沒有在目前語法邊界內找到會被 `?listitem` 誤傷的合法寫法——但這條規則本身在「懸空 claim 緊接列點」這個組合下有 finding 4 那個真的會漏東西的洞。

severity: clean
blocking: 否
引句:「這一行長得像清單項但不是 - claim:(打錯字?)」
