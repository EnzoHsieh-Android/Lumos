severity: blocker

鏡頭:正確性(邏輯會不會做出錯的行為)。以下每一條都用 `/tmp` 底下的臨時檔案或臨時 git repo 實際跑過 `memory-sweep.py` 的函式重現,不是純讀 code 推論。

## 1. 開頭欄位沒有結尾 `---` 時,`stamp()` 會整支炸掉,拖垮同一輪其他所有檔案

severity: blocker
blocking: 是

引句:「i = text.index("---", text.index("---") + 3)」

`stamp()` 在找不到 `metadata:` 區塊時,退回用「找第二個 `---`」的方式定位插入點:

```
i = text.index("---", text.index("---") + 3)
```

`verify_blocks()` 對「有沒有結尾 `---`」完全不設防——它只認 `^verify:\n` 這個開頭,不要求檔案有合法的 frontmatter。所以只要一篇記憶檔有 `verify:` 區塊、但手寫時忘了帶結尾的 `---`(prompt 明確點名的情境),這篇檔案照樣會被 `verify_blocks()` 收進去、跑檢查、判定失敗,然後進 `apply_one()` 呼叫 `stamp()` 寫回——這時 `text.index("---", ...)` 找不到第二個 `---`,直接丟 `ValueError: substring not found`,而且 `main()`/`sweep()` 全程沒有 try/except 接住它。

實測(用真正的 `sweep()` 入口跑,不是直接呼叫 `stamp()`):

```
---
name: broken
verify:
  - claim: 這個檔案存在
    file-exists: /tmp/msweep_test/definitely-not-here.txt

沒有結尾分隔線的正文
```

```
Traceback (most recent call last):
  File ".../memory-sweep.py", line 388, in sweep
    apply_one(f, text, failed, unknown, today, write, tally)
  File ".../memory-sweep.py", line 369, in apply_one
    f.write_text(stamp(text, failed, today), encoding="utf-8")
  File ".../memory-sweep.py", line 302, in stamp
    i = text.index("---", text.index("---") + 3)
ValueError: substring not found
```

`sweep()` 是 `for f in sorted(here.glob("*.md")): ...` 的單一迴圈,例外會直接沖出迴圈——這代表**一篇畸形的記憶檔會讓同一輪裡排在它後面的所有其他記憶檔都沒被清掃到**,而且 `cross_check()`(圖譜對帳)也永遠跑不到。這支是掛在 SessionStart 的 hook(文件裡寫 `--write --quiet --budget 8`),整支未捕捉例外炸掉意味著每次開專案都會在終端機噴一段 traceback,而且註解自己寫的「hook 不因為有過期就讓 session 失敗」(`main()` 固定 `return 0`)在這條路徑上完全沒生效——例外根本沒機會走到那個 `return 0`。

## 2. `_is_pushed` 完全不管 `git fetch` 有沒有成功,離線/fetch 失敗時會給出自信但錯的答案

severity: major
blocking: 是

引句:「_git("fetch", "-q", up.split("/")[0], cwd=root, timeout=25)」

```
_git("fetch", "-q", up.split("/")[0], cwd=root, timeout=25)
r = _git("merge-base", "--is-ancestor", sha, up, cwd=root)
```

`fetch` 呼叫的回傳值(`CompletedProcess`)整個被丟掉,連 `returncode` 都沒看。這表示如果 `git fetch` 失敗(離線、認證失敗、DNS 失敗——`subprocess.run` 不會因為 git 回傳非 0 就丟例外,只有逾時/找不到執行檔才會被 `_git` 的 try/except 接住),`merge-base --is-ancestor` 還是會照樣拿**上一次成功 fetch 時留下的、可能已經過期**的 remote-tracking ref 去判斷,然後把這個過期答案當成「驗過了」回傳 `True`/`False`,而不是回傳 `None`(驗不了)。

實測:在本機 clone 提交一個新 commit 但**不從這個 clone push**,改由另一個 clone 把同一個 commit push 上遠端;然後把遠端目錄搬走模擬離線,對本機 clone(從沒 fetch 過那次 push)問 `not-pushed`:

```
claim 'not-pushed' check (offline, but actually WAS pushed via another clone):
  _chk_not_pushed -> True
  (expected: should be None/unknown since we cannot confirm offline; got above)
```

也就是說:一條「還沒推」的記憶宣稱,在事實上已經被別人推上遠端之後,只要清掃器這一輪剛好離線,它會回答「對,仍然沒推」——**這正是這支工具存在的理由(抓『還沒推』這種會被時間推翻的宣稱)**,卻在 fetch 失敗時完全不設防地給出確定答案,而不是設計文件反覆強調的「驗不了就回 None、不能假裝驗過」。

## 3. `verify_blocks()` 對至少三種畸形寫法整條靜靜丟棄,不進 checked / unknown / skipped 任何一個統計

severity: major
blocking: 是

引句:「if claim is None or ":" not in s: continue」

```
for line in m.group(1).splitlines():
    s = line.strip()
    if s.startswith("- claim:"):
        claim = s[len("- claim:"):].strip()
        continue
    if claim is None or ":" not in s:
        continue
    k, _, v = s.partition(":")
    k, v = k.strip(), v.strip()
    if k in CHECKS:
        out.append((claim, k, v))
        claim = None
    elif k == "cmd":
        out.append((claim, "cmd", v))
        claim = None
```

程式自己的註解講得很清楚:「舊寫法:明確報成『驗不了』,不要靜靜跳過(靜靜跳過=看起來有守衛其實沒有)」——但這條原則只套用在「舊的 `cmd:` 寫法」這一種畸形上,對其餘畸形完全沒做。用 `verify_blocks()` 實測三種 prompt 點名的畸形(全部繞過真正的檔案,直接餵字串):

- **欄位順序顛倒**(型別鍵寫在 `claim:` 之前):
  ```
  verify:
    - pushed: abc123def4567
      claim: 已經推了
  ```
  → `verify_blocks()` 回 `[]`。整條規則憑空消失,`sweep()` 連「這篇有 verify 區塊」都不知道(`if not verify_blocks(text): continue` 會直接把它當成沒有 verify 區塊的普通記憶檔跳過),`tally.checked`/`unknown_n`/`skipped` 全部不會+1。

- **型別鍵打錯字**(`pushd:` 而非 `pushed:`):
  ```
  verify:
    - claim: 這個東西存在
      pushd: abc123def4567
  ```
  → 也是 `[]`。跟上面一樣整條蒸發,沒有任何「型別不認得」的紀錄。

- **claim 後面完全沒接任何型別鍵,直接接下一個 claim**:
  ```
  verify:
    - claim: 第一句沒有檢查
    - claim: 第二句
      pushed: abc123def4567
  ```
  → 回 `[('第二句', 'pushed', 'abc123def4567')]`,「第一句沒有檢查」整條無聲消失,不會被算進 `unknown`。

以上三種都不會出現在 `check_one()` 的 `unknown` 清單、不會讓 `tally.unknown_n` 增加、更不會被 `tally.skipped` 記到——對照組(t_memory_sweep_core 的 ① 測試)只驗證了「格式正確的 claim/cmd 成對」與「舊 `cmd:` 寫法」兩種形狀,完全沒有涵蓋這三種畸形。結果是:**寫錯格式的記憶檔,清掃器不但不會抓到,連「這篇有一條規則沒被驗到」這件事本身都不會留下任何痕跡**——這正好跟這支程式反覆強調的「不能靜靜跳過」設計原則背道而馳,而且比 `cmd:` 那種已知的舊寫法更隱蔽,因為使用者連錯誤訊息都看不到。

## 4. 單條檢查沒有真正的時間上限:`PER_CMD_CAP` 是死碼,`deadline` 只在「兩條 claim 之間」檢查

severity: major
blocking: 是

引句:「PER_CMD_CAP = 15.0          # 單條檢查最多跑這麼久」

這行常數在全檔只出現這一次(定義),從沒被任何函式讀取或傳給 `subprocess`/`_git`。真正拿去當逾時秒數的是 `_git()` 呼叫點各自寫死的數字:`_upstream_ref` 用預設 20 秒,`fetch` 用 25 秒,`merge-base` 又是預設 20 秒。而 `check_one()` 的預算檢查只發生在**進入下一條 claim 之前**:

```
for claim, kind, arg in verify_blocks(text):
    if deadline and (deadline - time.monotonic()) <= 0:
        tally.skipped += 1
        continue
    tally.checked += 1
    ok = run_check(kind, arg, root)
```

一條 `pushed`/`not-pushed` 的檢查在 `_is_pushed()` 內部依序打三次 `git`(rev-parse → fetch → merge-base),`deadline` 在這三次呼叫**之間完全不會被檢查**——只要其中一次(例如 `fetch` 卡在網路逾時)吃到自己的逾時上限,單單這一條 claim 最壞情況就能吃掉 `20 + 25 + 20 = 65` 秒。文件裡給 SessionStart hook 用的範例是 `--budget 8`(內層預算 `8*0.7=5.6` 秒),也就是說**一條檢查可以讓開場卡住超過一分鐘**,遠遠超出「幾秒鐘就該跳過並誠實計數」的設計意圖,而且這 65 秒完全不會被算進 `tally.skipped`——因為程式根本沒機會執行到下一次 `deadline` 檢查點,使用者只會看到 session 開場卡住,沒有任何「還有幾條沒驗到」的提示。

## 5. `_NODE_REF` 的標點排除清單仍不完整,一個沒列到的符號就能讓節點名「跑飛」到整句話

severity: major
blocking: 否

引句:「r"(?:Projects|Systems|Issues|Verification)/([^\s`。,、;；:：()（）\[\]\"'／|]{2,})"」

這行正則式的註解本身就承認這是修過一次的坑(「原本只排除空白/反引號/頓號/右括號/右方括號…」),但目前的排除清單仍缺很多常見中文標點,例如「！」「？」「」」「』」「…」「—」「《」「》」。實測:

```python
t = "已交付,詳見 Projects/某功能_計劃！這篇說完成了。"
ms._NODE_REF.findall(t)
# ['某功能_計劃！這篇說完成了']
```

因為「！」不在排除字元集合裡,擷取到的「節點名」直接吃到下一個被排除的字元(這裡是句尾的「。」)為止,把整句話都當成節點名。這個集合被 `shadow_copies()`(影子副本偵測)與 `pointer_problems()`(狀態打架偵測)共用:

```
hit = sorted(n for n in {_stem(n) for n in _NODE_REF.findall(t)} if n in stems)
```

擷取到的「節點名」跟 `stems`(圖譜裡真實存在的節點)不可能比對得上,於是這條記憶明明點名了一個貨真價實的圖譜節點,卻因為節點名後面接了清單漏列的標點,而在「記憶說已交付但節點還是 doing」這類對帳裡被靜靜漏掉。這正是這批改動的核心賣點之一(拿記憶跟圖譜比對抓矛盾),卻因為同一種標點排除清單的老毛病(只是這次是另一批符號)而被削弱。

## 6. `stamp()`/`unstamp()` 在「frontmatter 結尾跟正文之間沒有空行」的檔案上不是無損往返,每蓋撤一次多一個空行

severity: minor
blocking: 否

引句:「return head + "\n" + warn + body.lstrip("\n")」

```
warn = (MARK + today + "）：**" + "**、**".join(failed)
        + "**。內容留著沒刪，但引用之前先自己查一次。\n\n")
return head + "\n" + warn + body.lstrip("\n")
```

`warn` 固定以 `\n\n` 收尾,而且不管原始 `body` 前面本來有沒有空行,一律先 `lstrip("\n")` 再接。如果原始檔案的 frontmatter 結尾 `---` 後面**沒有空行、正文緊接著**(手寫記憶檔完全可能長這樣),蓋章之後會多出一行原本不存在的空行;`unstamp()` 只精準吃掉 MARK 那一行本身,不會把這個多出來的空行吃回去:

```
原本: '---\n...\n---\n正文直接接在後面\n'
撤章後: '---\n...\n---\n\n正文直接接在後面\n'
```

`round-trip exact equal: False`。跟既有測試 `t_memory_sweep_core` 的 ④(`ms.unstamp(st).strip() == bare.strip()`)不衝突,是因為那個測試的樣本本來就有空行分隔、而且比對用了 `.strip()`,沒有覆蓋到「原本沒有空行」這個形狀。單次不影響判定正確性,但符合 prompt 問的「反覆蓋章撤章會不會累積失真」——這一種格式的檔案每經過一次蓋章就永久多一行,而且不會被撤回。
