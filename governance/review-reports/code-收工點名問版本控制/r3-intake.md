# 代碼審 r3 收貨留痕（資安終審輪）

編排者:claude（主對話）
日期:2026-09-18
被審材料:`r3-code.patch`
派工:單席資安（全新 agent）。**派工詞明確要求它去打破作者的方案**——「找清單外的第三項，這是你最重要的工作；找到一個就是 blocker，而且證明了『列舉法』這個形狀的極限」。

## 一、★跑滿上限、攤人裁定★

流程規定高風險迴圈上限 3 輪。本輪（第 3 輪）又出一條 blocker，**編排者停手、把現況攤給人裁**，沒有自行再修一輪然後宣布過關。

Enzo 2026-09-18 裁定:**改主程式加那兩個旗標**（三個選項中的第一個；另兩個是「本案先停、漏洞另開 Issue」與「把閘門 3 的判準改回去」）。本輪之後的修正屬於**人核可的加輪**，不是自行超限。

## 二、新 blocker:列舉法原理上不可行

**發現**:被打開的資料夾可以放一份★未提交、未追蹤★的屬性檔，把某支檔指到一個★攻擊者自己命名★的差異驅動器，再用那個名字設定要執行的指令。**鍵名是他取的**，所以「列舉危險設定」這個形狀原理上擋不住——清單再長也列不到他要取的那個名字。

**編排者獨立重現**（不採信單方說法）:

```
清單已含兩項、防護生效 → 攻擊者的指令照樣執行   ★blocker 成立★
改用兩個旗標(關掉整類機制) → 沒執行            ★這個形狀擋得住★
```

**這是同一條資安問題的第三種修法被打穿**:

| 輪 | 修法 | 被什麼打穿 |
|---|---|---|
| r1 | 在新增的兩個呼叫點加參數 | 漏了第三個呼叫點 |
| r2 | 注入環境變數涵蓋所有子行程 | 只關掉一項設定 |
| r2 | 收成具名清單 + 逐項跑的測試 | 鍵名可由攻擊者自取 |
| r3 | **改用旗標關掉整類機制** | 端到端驗過擋住 |

## 三、修正範圍靠實測畫，不靠推論

主程式裡有二十多處差異呼叫。**先實測哪幾種形態會觸發**，再決定改哪些:

| 呼叫形態 | 會觸發嗎 |
|---|---|
| 取差異內容（三種變體） | ★會★ |
| 只取檔名 / 統計 / 狀態 | 不會 |
| 取內容 + 兩個旗標 | 不會 |

依這個判準掃出**五處**取內容的呼叫，全部補上。補一支**結構性測試** `t_lumos_content_diffs_all_disable_external_drivers`:它掃全檔、按同一個判準找「取內容卻沒帶旗標」的位置——★釘的是性質不是行號★，以後新增一處沒帶的，測試自己會紅。

該測試的第一條斷言是「這支檔裡真的找得到帶旗標的呼叫」——**防的是判準寫壞時整條靜靜通過**（先跑過空清單狀態確認它會紅）。

## 四、★一個更難看的發現:修了不等於生效★

端到端驗這條時，攻擊一直打得穿。查下去發現**hook 跑的是系統裝的那份主程式，不是工作區改過的那份**（`_trusted_lumos()` 刻意只找可信來源，那正是它的設計）。

分開驗證，把「修法有效」與「部署有沒有同步」切開:

```
工作區這份(六處防護) → 攻擊被擋住   ★修法有效★
系統裝的那份(零處)   → 攻擊照樣成功 ★部署沒同步★
```

★這件事在同一批工作的設計審階段就被接手席報過★（「改完要跑安裝指令才真的部署，而且已部署的副本已落後，sha256 實測不同」），已寫成條款 S8、寫進圖譜的部署節點、列進驗收條件——**然後還是在這裡被咬了一口**。

**所以 S8 那條「靠人驗」不是形式**:它是這類修正能不能到使用者手上的唯一關口。修安全問題時尤其要先確認「現在跑的是哪一份」。

## 五、誠實邊界（寫進圖譜與程式碼註解，不宣稱更多）

- 兩個旗標關掉的是「外部差異程式」與「文字轉換」兩類機制。**不宣稱版本控制沒有第三類**——只是這三輪試過的攻擊都落在這兩類裡。
- 三輪合計試過六種向量:別名、分頁器、過濾器塗抹、檔案監視、外部差異、自訂驅動器。前三種實測不觸發，後三種觸發且已擋。
- **提交前、推送前那兩道閘沒有走這條路**——那些是使用者主動執行的，不是開資料夾就自動跑，風險形狀不同，本批未處理（已寫進圖譜）。
- 純 clone 不會把這些設定帶過來（實測）;交付路徑是「直接拿到別人的整個目錄」。
