## 二、★新 blocker:防護只補了自己新增的呼叫點★

**發現**:r1 的修法把防護加在新抽出的共用呼叫函式上，涵蓋了 `_git_status_entries` 與 `_head_shebang` 兩處。
但**閘門 3 為真那條路會去呼叫主程式**（`_impact_missing` → `lumos impact --diff HEAD`），而主程式內部的版本控制呼叫（`scripts/lumos:25233`）沒有被補。

**驗收席端到端重現了完整攻擊**:惡意設定 + 一個未提交的程式碼檔 + 一個未提交的圖譜筆記 → 跑完整的 hook → 攻擊者指定的指令執行、證據檔被建出來。

**編排者獨立重現**（不採信單方說法）:

```
跑一次完整的 hook（走到閘門 3 那條路）→ 攻擊者的指令執行了   ★blocker 成立★
改用環境變數注入給所有子行程        → 沒執行             ★解法涵蓋得到★
```

★更難看的一層★:**這批改動自己放寬了那條路的觸發條件**——閘門 3 的判準從「這輪用工具動過筆記」改成「工作樹上有任何未提交的筆記」，等於讓一條沒補的路更容易被踩到。

★這正是本專案記過的一條教訓★:**同一種缺陷要一次掃完所有同構位置**。補兩處漏一處，就是沒補。

**處置**:折。改成在 hook 進入點把設定注入環境變數——版本控制會把它當成命令列參數，**子行程一律繼承**，所以主程式內部的呼叫也涵蓋得到（實測驗過）。
補端到端測試 `t_sync_nudge_hardens_git_for_all_subprocesses`：跑完整的 hook、現場刻意造成會走到閘門 3 為真，逼它去呼叫主程式。翻紅釘驗過（拿掉進入點那行 → 翻紅）。

**誠實邊界（寫進程式碼註解，不宣稱更多）**:
- 只關掉已知會被當成指令執行的那一項;版本控制的設定面很大，**不宣稱所有設定都擋得住**。
- 純 clone 不會把該設定帶過來（實測）;真正的交付路徑是「直接拿到別人的整個目錄」。
- **這支 hook 以外的地方（提交前、推送前那兩道閘）沒有走這條路**——那些是使用者主動執行的，不是開資料夾就自動跑，風險形狀不同，另案處理。
