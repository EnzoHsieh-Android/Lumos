## 一、★編排者失誤:被審材料的範圍打錯了★

**第一版材料是用分支名當起點產的**（`main..HEAD`），而本地主線在開工期間被推進過——算出來的不是「我改了什麼」，而是「我跟現在的主線差在哪」，**含別人改動的反向差異，看起來像我刪掉了他們的功能**。

| 範圍 | 檔數 | 內容 |
|---|---|---|
| `main..HEAD`（錯的，五席看到的） | 4 支 | 含 `scripts/hooks/pre-push`、`scripts/lumos` 兩支我根本沒碰的 |
| `79a7072c..HEAD`（正確） | 2 支 | 就是實際改的那兩支 |

- **誰發現的**:架構對齊席（標 ⚠ 交編排者，不計入它的對齊條數）。它自己用 `git diff --stat` 與 `git show --name-only` 驗過該範圍，並把三問的答案限縮到真正改動的兩支檔。
- **諷刺之處**:前一步才剛算出正確的 merge-base 雜湊值，下一步產材料時順手打了分支名。而「工作區裡用分支名當範圍會算成別人的」正是本專案記過的教訓。
- **影響評估**:六席裡五席看的是這份錯材料（外家備援是最後派的，用的也是錯材料）。但**所有發現都針對真正改動的兩支檔**，錯材料只是多了雜訊，沒有導致任何發現失效或多出假發現。
- **處置**:用正確範圍重產 `r1-code.patch`（650 行）與 `r1-snapshot.patch`，記帳用新指紋。

## 三、★收齊前動了工作目錄,一併記著★

規矩是「所有席收齊之前不要動工作目錄」。實際上**中文檔名那條 blocker 在還有兩席在跑時就先修了**。

- 理由:當時已有兩席獨立報同一條（外家備援、邊界），且編排者自己實測重現（造一支中文檔名的檔，解析出來的路徑指向不存在的檔）。流程允許「多席獨立一致 → 直接折，不用派辯方」。
- 但「收齊才動」這條確實沒完全守住:後到的正確性席看到的工作樹已經是修過的（它自己也注意到並寫進報告——「current working-tree file already has this fixed」）。
- 沒有造成判讀污染（它仍獨立報了同一條，並註明凍結 patch 未含修正），但記在這裡不掩蓋。

- **carrier 選席**:`正確性-sonnet`——quote-check 全數錨定。（架構對齊席發現最關鍵的材料問題，但它有四句引用格式違規，依規矩不選為載體。）
