**Finding 2(major)— S1/S2/S3/S4 都依賴一個從未定義過的 CLI 介面**

> 原文引句:「`build_goldset.py` 加 delta 模式」、「整批 merge 進 goldset `labels`」、「週閘超門檻自動產 delta 表」

問題:`build_goldset.py` 目前完全沒有 argparse/CLI 參數(`main()` 不吃任何參數,直接跑滿血流程),spec 全文從未給出「delta 模式」該用什麼旗標/子命令呼叫、「merge」步驟該跑哪支程式、S3「重釘模式」怎麼觸發。但這介面被三處各自依賴:人工跑 S1、`governance/autonomous-loop.sh`(bash)要自動觸發 S4 的「自動產 delta 表」、以及重釘要靠 S3 斷言擋。三個呼叫點共用一個沒被命名的介面,屬可執行性缺口。

**Finding 3(major)— S3 重釘閘沒提防既有的「重釘=清空全部標註」預設路徑**

> 原文引句:「重釘模式斷言:目標語料全題候選池 `unjudged == 0` 才寫入 `snapshot_commit`」

問題:目前程式碼裡**唯一**會寫入 `snapshot_commit` 的路徑是 `build_goldset.py:104-119` 的 `main()`,而它是無條件整本重建:`gs["labels"][cid] = {n: {"final": None} for n in pool}` 對每一題都執行,會把所有既有 `final` 標註全部清空。現況 `retrieval-goldset.json` 是 0/429 未標(全標完)。這代表:功能上線後只要有人手滑跑一次原本就存在的 `python3 governance/eval/build_goldset.py`(無旗標),就會把整份人工累積的金標全部清空,而 S3 設計的「新機械閘」根本不在這條路徑上。spec 全文沒有提到要 guard/廢棄這個既有破壞性預設,回歸測試清單(驗收線)裡也沒有一條測「重釘不得清空既有標註」。

**Finding 4(major)— S4「unjudged rate」定義有歧義,兩種讀法效果天差地遠**

> 原文引句:「`retrieval_eval.py` 每輪加印 unjudged rate(全題 top-K 候選中無標註佔比)」

問題:現有最接近的計算(`retrieval_eval.py:319`)是 `unl = sum(1 for c in gs["labels"].values() for v in c.values() if v.get("final") is None)`——這只數**已經是 `gs["labels"]` 字典鍵**但 `final` 為 None 的候選,對「壓根沒進過這個字典的全新節點」是瞎的。而 `eval_search`/`eval_edit` 的 `lab.get(n, 0)` 對任何不在 `lab` 裡的即時查詢結果一律當成標 0(噪音),跟「明確標過 0」完全無法區分——這正是 2026-08-08 事故的真實成因。spec 的「全題 top-K 候選中無標註佔比」沒說清楚是要從**即時 search/impact 查詢結果**(能抓到全新節點)算,還是沿用現有這套只看已存 key 的 `unl`(抓不到)。若實作者直接複用現成的 `unl` 邏輯,S4 這顆「事前亮燈」訊號會對這個計畫要防的確切失效模式視而不見。
