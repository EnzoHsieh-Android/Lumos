作為外部審稿人，我針對《標註刷新_計劃》設計文件提出以下審計意見：

*   **severity: blocker**
    *   原文引句：「unjudged rate 超門檻(暫定 10%,實跑校準)→ 自動產 delta 表 + 通知(LINE,同 lint-watch 慣例)→ 等人放行補標。」
    *   **問題說明**：邏輯門檻發生衝突且存在死鎖。S4 宣稱「未標率達 10%」才觸發通知與產表，但 S3 卻規定 `unjudged == 0` 才能重釘快照。這意味著當未標率在 1%~9% 之間時，S4 的「事前亮燈」不會觸發（因為沒到 10%），但 S3 的「機械閘」會直接噴出 rc1 報錯強行中斷開發者流程。這導致警示系統在真正被阻塞時毫無作用，開發者會被迫在無預警情況下處理中斷，失去「事前亮燈」的預緩衝意義。

*   **severity: major**
    *   原文引句：「目標語料全題候選池 unjudged == 0 才寫入 snapshot_commit;否則 rc1 並吐 delta 清單」
    *   **問題說明**：未定義的「全題候選池」範圍將導致實施成本爆炸。S1 提到候選池包含 `search_pool` 與 `edit_pool`，這類池通常包含數百個節點；而 S4 卻定義 unjudged rate 為 `全題 top-K 候選中無標註佔比`。若 S3 literal 地執行「全題候選池 unjudged == 0」，則必須標註池中所有（含 Top-K 以外）的垃圾節點才能通過機械閘，這與 S2 宣稱的「單輪 ~80 筆、Flash 免費額度足夠」完全矛盾。若不限縮 S3 的斷言範圍至 Top-K，補標量將輕易擊穿 LLM 額度與人審體力。

*   **severity: major**
    *   原文引句：「各產 `rater-{claude,gemini}-delta.json`」
    *   **問題說明**：異常退化路徑未定義。S2 在實務隱患中提到「B 席斷供時退化為 A 席+人全批」，但 S2 的主邏輯實作（S2 條目 2）是基於「兩席一致」與「不一致」的路由分流。若 B 席產出的 JSON 缺失或失效，S2 的合併與比對程式碼將因找不到 B 席檔案而 crash，或無法進入「建議 final」邏輯。Spec 未交代在單席模式下，如何決定哪些應進入「人裁 deep-read」，可能導致所有標註被迫由人肉複審，或者機械閘 S3 因等待 B 席結果而永久阻塞。

*   **severity: major**
    *   原文引句：「節點內容改動後舊標註可能過期——v1 僅列「mtime > 標註日」清單軟提醒,不阻塞重釘。」
    *   **問題說明**：資料一致性風險（過期金標比未標更危險）。本案核心動機是解決「語料前進但標註凍結」導致的噪音，但卻只攔截「新節點（未標）」，卻放行「內容已改動但 ID 舊有的節點（過期標註）」。如果一個舊節點內容被修改為完全不相關，但因 ID 存在於 labels 中，S3 會判定 `unjudged == 0` 並准予通過，導致評測分數雖然「綠燈」卻是虛假的（依賴過期的金標）。這與計畫宣稱的「治全系統唯一紅燈的實證阻塞」初衷矛盾。

*   **severity: minor**
    *   原文引句：「整批 merge 進 goldset `labels` 前必經人放行(批次級人閘)」
    *   **問題說明**：人閘介面模糊。Spec 未定義「整批放行」的具體行為。如果「一致案」有 80 筆，人閘放行時是「盲簽（Blind Sign）」還是需要檢視抽樣？若只是點擊確認，則 S2 提到的「pbt-oracle 教訓（自動生成+自動採納）」依然會發生，因為人類在面對大量「LLM 已達成一致」的建議時，極大機率會直接通過。缺乏具體的「人閘」操作形式定義（如：是否產出 diff 預覽），會讓這個閘口流於形式。
