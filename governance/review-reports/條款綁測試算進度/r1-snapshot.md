# 條款綁測試算進度_計劃

> 題目一句:設計審產出的驗收條款清單,實作時「認領→做完勾掉」怎麼不漂?
> 派工者:Enzo 2026-09-08 裁「寫計劃、送設計審、不直接做」。
> 兩份乾淨 agent 調研(不帶結論、只給原始問題)在 `governance/review-reports/條款綁測試算進度/`。
> ★這是 [[Projects/進度從提交推導_計劃]] 四版被打穿之後、[[Projects/接手視圖_計劃]] 落地之後的續案★——
> 那條線仍有效的三條裁定(d3 完成判準掛實作端看測試 / d9 帳不爛只因寫入有驗證+入口綁定 / d12 先造唯讀)是本案的地基,不重審。

## 為什麼(先講現況,每個數字都是 2026-09-08 我自己量的)

- **「認領→勾」的模型這個 repo 已經有了,而且幾乎沒人用。** `[SN]` 條款標記 + `lumos spec-trace`:
  認領 = 某篇 Verification 筆記的 `plan_refs` 欄位回指本計劃、而且那篇筆記全文出現過 `[SN]` 字樣。實算:**有 `[SN]` 條款的計劃 33 篇,
  條款全未認領的 15 篇**(圖譜裡舊的「158 篇 126 篇從沒用」是另一種算法,今天用 `spec-trace --json`
  逐篇跑是這個數)。它沒人用的結構原因,自家調研講得準:**沒東西逼(不掛閘、opt-in)、沒地方消費(只有人跑指令才看得到)**。
- **「勾掉」這個動作本身,世界上能不漂的例子清一色是「狀態不另存,從有代價偽造的產物直接讀」**
  ——BDD 讀測試結果、GitHub 子 issue 關掉父清單自動勾、PR 合併自動關 issue。
  「有人去勾」的全承認沒機械對帳(Beads=給 AI agent 用的 issue 追蹤器、TASKS.md=用 markdown 勾選框、Spec Kit=GitHub 的規格驅動開發套件)。世界調研沒找到「設計審條款原生綁 CI 結果」的現成工具。
- **自家四版「造新狀態源」全被打穿**(提交 trailer / 當場跑測試 / hook 事件帳 / 自報帳),
  四版共同結論:「同步任務狀態在這裡不能靠造,只能靠讀」。

### ★轉述的設計裡三個前提,我開檔驗過,對不上★

| 轉述的前提 | 實際 | 對設計的影響 |
|---|---|---|
| 「完成=不跑測試,讀測試每次跑都留的快取」 | 推送閘寫的 `.lumos/test-cache-shard*.json` **只有 `{"failed": []}`**,是 fail-fast 重跑用的失敗清單,**沒有哪支測試在哪個 commit 幾點綠** | 「讀快取算綠」在現有產物上**不成立**。要另找有代價的證據源(見 [S2]) |
| 「認領=條款旁綁 `[test:]`,可機械驗存在(Check T 那套)」 | Check T 的 `extract_contracts` **只讀任一節點 frontmatter `summary` 欄位裡的 ★INVARIANT★ KEY 行**(不限節點型別,只是今天只有 System 節點這樣寫);**計劃正文它完全不讀**,條款旁的 `[test:]` 不會被看到 | 要新開一條**只驗存在**的小解析路徑,但**沿用** `resolve_test_refs` 與 Check T 的方法集合比對,不自寫第二份 |
| 「`lumos task record` 是否落地」(自家調研沒查到) | **不存在**(`lumos task` 回「沒有這個指令」);v4 那條裁定沒有實作,d12 轉向後不會實作 | 本案不依賴它,也不復活它 |

另外兩個數字更正:**測試撞名今天實算 841 支、同名 0 對**(v2 那個「664 支裡 95 對」是別的算法或舊資料;
多平台消費專案的撞名由 `resolve_test_refs` 的平台前綴處理,本 repo 現在沒有);
`bound-tests` 治理帳一筆記的是 **節點清單 + 「46 綠」這種計數**,★不記測試名★。

## 做什麼

### [S1] 「認領」= 在條款旁綁測試名,跟合約行同一種寫法

- `[S3] 接手視圖印這張表 [test:t_handoff_view]`——寫法照 ★INVARIANT★ 的 `[test:名]`,多平台用同一套 `平台:名` 前綴。
  ★存在性驗吃的是專案設定的 `test.method_regex`★:本 repo 設定只認頂層 `def t_…`,所以 `scripts/test_autonomous_loop.py`
  那 144 支寫在 unittest class 裡的 `test_…` 全部認不到——綁了會被印成「懸空」。這是既有設定的邊界,不是本案發明的;
  本案不改 regex(那會連動 Check T 的合約判定),條款只能綁認得到的測試,認不到的印「懸空(設定認不到這種寫法)」而不是「不存在」。**不再靠寫 Verification 筆記來認領**(那條路 33 篇 15 篇零認領)。
- **存在性機械驗**:新一支唯讀函式讀計劃正文的 `[SN]…[test:]`,解析沿用 `resolve_test_refs`,
  方法集合比對沿用 Check T 那套(同平台真測試集合;懸空=不存在)。**不動 Check T 本身**,不動 doctor 的判定。
- 綁了但懸空 → 這條在 [S2] 的表上印「懸空」,不是「沒綁」——兩種要分開,懸空是寫錯,沒綁是還沒做。

### [S2] 「完成」不用勾,算出來——但證據只用★機器寫的、有代價的★那兩本

三態,★永遠印「在 commit X(時間 T)是綠/紅」,不印「完成」★:

1. **沒綁** → 「散文級,靠人」,明列不假裝。
2. **綁了、測試存在、最近一次有代價證據為綠** → `綠 @<sha>(<時間>)`。
3. **綁了、證據為紅或沒有證據** → `紅 @<sha>` / `尚無證據`。

**證據源(現有、不新造)**:
- **CI 帳** `docs/.ci-log.jsonl`:每次 run(或 no-run / 等待逾時事件)一筆 `conclusion`,由 CI 回流寫、獨立信任根。
  ★同一個 sha 可能有多筆★(實算 127 個 sha 裡 7 個有兩筆,例如先寫「等待逾時」兩分鐘後補一筆 success)——讀的時候取該 sha 最新一筆,而且 no-run / timeout 不算證據。
  粒度是**整套**——「這個 sha 的全套綠」推不出「這條的那支測試綠」,只推得出「那支測試存在於這個 sha 而且整套沒紅」。
  ★這是誠實的降級★:它答的是「這條綁的測試在最近一次 CI 綠的版本裡存在且沒被擋」,不是「這支測試單獨跑綠」。
- **`bound-tests` 治理帳**:推送閘真跑受波及合約測試留的,有 commit、時間、綠/紅、節點清單。
  只有當條款綁的測試同時是某 System 節點 ★INVARIANT★ 的綁定時才蓋得到——蓋到的印得更細(節點級),蓋不到的退回 CI 那本。
- ★不用 `test-cache`★(它只存失敗清單);★不跑測試★(v2 死因);★不新開帳本★(v3/v4 死因)。

**這一刀的天花板要寫在表頭**:「綠」=「綁的測試存在於最近一次 CI 綠的 commit」,不等於「做對」(d3 接受的 oracle 天花板)。
需要單支測試粒度的話,唯一乾淨的路是**讓測試執行器(不是本案)把每支結果連 sha/時間寫進它自己的產物**——
那是「執行器留的產物」不是「本案造的狀態」,但它會改動推送閘寫的快取格式與分片語意,★本案不做,列成候選★。

### [S3] 入口綁定:兩處,都是既有入口,不改 hook

- **`lumos handoff <計劃>` 直接印這張表**——接手的人第一眼看到的就是「哪條綠在哪個 commit、哪條懸空、哪條靠人」。
  這是「有人需要它才能前進」那一半(d9)。
- **設計審過關那一步(現在要列「合約候選」)加一句流程規則:每條驗收條款寫 `[test:]`,寫不出來的標「散文級」**。
  流程規則不改 hook;skill 文件改一行。

### [S4] 範圍刀(每一條都是上一條線的死因反過來寫)

唯讀、不造帳、不改 hook、不跑測試、不動 Check T 判定、沒綁的明列靠人、不動 spec-trace(它照舊,兩者並存:
spec-trace 認「驗證筆記提到」,本案認「綁到測試」;handoff 兩欄都印,讓人看出哪一種有在用)。

## 實務隱患(送審前先把預期會被打的點寫出來)

- **v2 的死因逐條答**:
  - *skip 靜默變綠*:本案不跑測試,所以沒有「這次 skip」的問題;但 CI 那本的「整套綠」裡可能含 skip——
    ★CI 帳沒有 skip 計數★,這一條我答不出來,列給審查席:要嘛接受(印「整套綠,含 skip 不可知」),要嘛把 skip 數納入 CI 回流的欄位(那是 CI 回流那案的事)。
  - *撞名*:今天 0 對;多平台走 `resolve_test_refs` 的前綴,前綴未定義直接 raise 不猜。
  - *快取過期*:根本不用快取;證據永遠帶 sha 與時間,印的是「在 X 時綠」不是「完成」。
  - *test-cache 是推送閘的*:不碰。
  - *「綁了」≠「做對」*:d3 接受的天花板,表頭明寫。
- **「綁測試名」本身仍是一個存起來的動作,為什麼這次不會像 spec-trace 一樣沒人用**:
  ①存在性有機械驗(懸空會被印出來,spec-trace 的認領則不驗);②寫入被綁在設計審出口那一步;
  ③每次接手都被 handoff 消費。★但②③都是流程規則,而 spec-trace 的歷史證明「只靠流程規則會沒人用」★——
  所以本案的成功判準要可量:REVISIT:2026-11-08 量「設計審過關的計劃裡,條款綁測試的比例」,低於五成就承認②沒接上、回頭改成閘。
- **證據粒度的誠實**:整套綠 ≠ 單支綠。一支被 `skip` 或根本沒被收進 runner 的測試,在「整套綠」底下看起來也是綠——
  唯一的防線是 [S1] 的存在性驗(不存在的會印懸空),擋不住「存在但被 skip」。這條要在表頭講。
- **★CI 帳當證據源是上一案 v1 的回鍋,要正面講★**:v1 死在「拿 trailer 定址+拿 CI 推論完成」——定址那半靠提交訊息,四種靜默丟資料;
  本案定址靠條款旁的測試名(碼裡的真符號,改名會被 Check Y 抓)、不推論「完成」只印「在 sha X 整套綠」,而且每道縫都印出來:
  沒推上主線就「尚無證據」(CI 只在推送後跑)、整套綠含 skip 不可知、同 sha 多筆取最新。**審查席請直接拿 v1 的六個 blocker 群逐條打這裡**。
- **多 session 的漂移**:綁在條款旁的 `[test:]` 跟碼一起進版控,合併衝突走 git;不像 v4 的帳「合併實測 100% 衝突」。
- **不涵蓋**:沒有程式碼可掛的工作(skill 散文、圖譜回填、真機驗收)不假裝算得出來,印「靠人」——上一案 v1 就這樣裁(只蓋四分之三),後面四版翻案翻的是載體,這條原則沒被翻。

GitHub 子 issue/PR 合併自動關(讀既有事件)、需求追溯矩陣(自動回填結果、連結仍人工);裁定=borrow-design
