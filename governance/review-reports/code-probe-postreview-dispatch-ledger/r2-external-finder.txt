### finding E1: the failure record is a separate `.pending` file, and archiving the one file the tool names brings back the fake-green results
severity: major
blocking: 是
引句:「unfinished = {p.stem for p in Path(out_dir).glob("*.pending")}」
file: `governance/eval/ablation_lumos_first.py:149`

The delta keeps a failure poisoned only through the separate `.pending` file. The `.json` the child wrote stays on disk with its success-looking rows (`fatal: False`, `passed: True`). This applies when the child exits with a bad return code, when the output is unreadable or health is bad, and when the parent dies while the child is still running.

Only the `.pending` gets flagged. `collect_skills_health` reports just the `.pending` name, because the sibling `.json` has no failure fields. The Markdown banner then says "請先處置 <x>.pending", and the marker's own `retry_policy` is `"archive-fatal-then-rerun"`.

An operator who follows that advice archives the only flagged file. The next run then has no poison, `load_results` no longer skips the `.json` stem, and those rows fill the missing run. That is the same fake green S11 says must not happen, now one manual step later.

The exception path (lines 250–263) avoids this by overwriting `out` with a tombstone. The return-code failure path (line 287) and the parent-killed path do not. Run from the repo root:
```
python3 - <<'EOF'
import importlib.util, json, tempfile
from pathlib import Path
from unittest.mock import patch
s=importlib.util.spec_from_file_location("ab","governance/eval/ablation_lumos_first.py"); m=importlib.util.module_from_spec(s); s.loader.exec_module(m)
d=Path(tempfile.mkdtemp())
def run(cmd,**k):
    Path(cmd[cmd.index("--out")+1]).write_text(json.dumps({"arm":"with","results":[{"id":"a","passed":True}],"fatal":False,"inconclusive":False,"skills_health_bad":[]}))
    return type("R",(),{"returncode":2})()
with patch.object(m.subprocess,"run",side_effect=run): print(m.run_job("with","a",1,["dummy"],1,1,d,1))
hits=m.collect_skills_health(d); print(hits)            # only ...-stamp.pending is named
for name,_ in hits: (d/name).rename(d/(name+".archived"))  # "archive the fatal file"
print(m.collect_skills_health(d), m.needed(m.load_results(d),"with","a",1))  # expected: [] 0  → fake green
EOF
```
Suggested fix: on every non-success path, move the child's `.json` to `.failed` and write the tombstone into `out`, as the exception path already does. Alternatively, make `collect_skills_health` also report and quarantine the sibling `<stem>.json`.

### finding E2: duplicate question ids are silently deduplicated by `load_ids`, then make `--exact-id` fail and poison the directory
severity: minor
blocking: 否
引句:「print("✗ --exact-id 必須且只能選到一題", file=sys.stderr); return 2」
file: `scripts/scenario_probe.py:963`

`load_ids` is documented as tolerating copy-paste duplicate ids and deduplicates them (line 71). The probe gets every question file, and `--exact-id` now finds two matches for a duplicated id and returns 2.

The dispatcher treats return code 2 as a batch failure. No `out` file is written, so the result is unreadable, the `.pending` is left behind and dispatch stops. Every later run in that directory then refuses to dispatch until someone cleans it up by hand. It fails closed, but S12 wants this rejected before dispatch.

Suggested fix: make `load_ids` raise on duplicate ids instead of deduplicating.

### finding E3: any stray `.json` without an `arm` field and without an arm-prefixed name now poisons the whole directory
severity: minor
blocking: 否
引句:「return ["結果檔組別無效，健康狀態不可判"]」
file: `governance/eval/ablation_lumos_first.py:117`

`arm = d.get("arm") or filename_arm` uses `p.name.split("-")[0]`. A file such as `with.json` or `notes.json` without an `arm` field ends up with an arm that isn't `with` or `without`. That returns the invalid-arm evidence, and `collect_skills_health` blocks all dispatch.

Before the delta, such files were simply not counted (`arm in by_arm` was false). Fail-closed, but it's a new way to lock out the directory that the plan doesn't mention.
