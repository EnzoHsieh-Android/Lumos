## 三、程式碼發現(逐 hunk 主動找洞)

### 6. `is_code_file` 先讀檔判斷 shebang、才做 `project_root` 包含檢查——順序顛倒,對無副檔名的 FIFO/特殊檔案路徑會整個掛住

`is_code_file`(`scripts/hooks/claude/check-graph-sync.py:259-267`)原本的防線註解寫「必須在 project_root 之下;避免改 ~/.claude/、/tmp 等外部檔案被誤判」,但這份 diff 新增的 `p.suffix.lower() not in CODE_EXTS and not _shebang_script(p)` 判斷在這道包含檢查**之前**執行,對任何無副檔名路徑一律先 `open(p, "rb")` 讀前 200 bytes,不管這條路徑是不是在 repo 之內。`file_paths` 來源包含 `extract_bash_file_paths` 從 `cp`/`mv`/`rm`/`git mv`/`git rm` 指令裡剝出的任意絕對路徑,只要该次對話的 Bash 指令提到一個無副檔名、且是 FIFO(具名管道)之類特殊檔的路徑,`open()` 之後的 `fh.readline(200)` 會在沒有寫入端時無限阻塞,直到 hook 的註冊 timeout(`scripts/merge-claude-settings.py:140` 的 `"timeout": 10`)把整個 Stop hook 砍斷——結果是這一輪的圖譜同步提醒/擋停整個靜默失效,而不是報錯。

已實跑重現(乾淨環境,5 秒逾時保護):
```
python3 - <<'EOF'
import importlib.util, os, tempfile, threading
from pathlib import Path
spec = importlib.util.spec_from_file_location("cgs", "scripts/hooks/claude/check-graph-sync.py")
m = importlib.util.module_from_spec(spec); spec.loader.exec_module(m)
d = tempfile.mkdtemp(); p = os.path.join(d, "somefifo"); os.mkfifo(p)
r = {}
t = threading.Thread(target=lambda: r.setdefault("v", m.is_code_file(p, Path("/tmp/unrelated-root"))), daemon=True)
t.start(); t.join(timeout=5)
print("HANGS" if t.is_alive() else r)
EOF
```
輸出:`HANGS: is_code_file blocked >5s reading a FIFO with no extension`。這道包含檢查本來就是為了「不去碰 repo 外的東西」而寫,新加的 I/O 卻搶在它前面對 repo 外路徑動手,跟這道檢查自己的既有理由矛盾。

severity: major
blocking: 是
引句:「if p.suffix.lower() not in CODE_EXTS and not _shebang_script(p):」(`r1-snapshot.patch`,`is_code_file` hunk 新增行)
file: `scripts/hooks/claude/check-graph-sync.py:246-267`(`_shebang_script` 與 `is_code_file` 的檢查順序)

### 7. `codex_stop_decision` 的 docstring 宣稱自己「回 True 時已寫下 session 標記」,但這個函式本身不寫檔——是呼叫端另外呼叫 `_stop_mark_write`

`codex_stop_decision`(`scripts/hooks/claude/check-graph-sync.py:500-509`)是純判斷函式,只讀 `_stop_mark_path(session_id).exists()`,沒有任何寫入動作。真正寫標記檔的 `_stop_mark_write` 是在 `main()`(`scripts/hooks/claude/check-graph-sync.py:634-641`)裡,先印完 `decision:block` 的 JSON 之後才另外呼叫。docstring 寫「回 True 時已寫下 session 標記」讀起來像是這個函式回傳 True 的當下標記就已經存在,跟實際「這是兩個獨立呼叫、中間還隔著印 JSON 那一步」的行為對不上——三個月後有人想單獨呼叫 `codex_stop_decision` 做乾跑判斷(dry-run)或寫第二個消費端,照 docstring 字面理解會誤以為呼叫一次就完成了「登記」,漏了要自己接著呼叫 `_stop_mark_write` 才會真的落地。

### 8. `_stop_mark_write` 的 `os.open` 沒配 `try/finally`,`os.write` 失敗時會漏 fd(與 `r1-邊界可執行.md` F1 判定一致,本席獨立核對)

`os.open(...)` 拿到裸 fd 後,`os.write(fd, ...); os.close(fd)` 寫在同一行、包在 `except OSError: return False` 底下——`os.write` 若拋例外,`os.close(fd)` 不會被執行,fd 直到本次 hook 行程結束才由作業系統回收。這支 hook 是短命的一次性 process(`main()` 結束就退出),實際傷害有限,但同一 repo(`scripts/lumos` 已有 try/finally 正確前例)已經證明這不是沒有更安全寫法可抄。

severity: minor
blocking: 否
引句:「fd = os.open(str(_stop_mark_path(session_id)), os.O_CREAT | os.O_EXCL | os.O_WRONLY, 0o600)」
file: `scripts/hooks/claude/check-graph-sync.py:519-520`
