## Findings

### 1. TOCTOU:同一 session_id 兩個 Stop hook 行程並發時,「只擋一次」100% 失效

`codex_stop_decision` 只做「檢查標記檔存不存在」,真正的防重靠之後才呼叫的
`_stop_mark_write`(O_EXCL)。但「檢查」與「印 block」之間完全沒有鎖——O_EXCL 只保護
寫檔那一步,保護不到「兩邊都先檢查到『不存在』、都印了 block」這件事。

實測:兩個行程、同一個 `session_id`,同時打進去,`--harness codex`,3/3 次都是兩邊各印一次
`decision:block`(見下方指令與輸出)。這正是派工詞第一鏡頭問的「兩個 session 同時第一次進
`_stop_block_dir`」情境裡最壞的一種——如果是**同一個** session_id 並發(而不是兩個不同
session),防護直接被繞過。

引句:「回 True 時已寫下 session 標記(呼叫端隨即輸出 block)。」
（`_stop_mark_path` 存在檢查與 `_stop_mark_write` 之間沒有互斥,docstring 自己承諾的「已寫下」
在檢查當下其實還沒發生。）

最小重現(對 repo 現狀跑,兩個 threading.Thread 各起一個子行程,同一 `session_id="sess-1"`,
其餘同 `t_codex_stop_block_once` 的 payload 建法):
```
t1 = Thread(target=run_hook, args=("sess-1",))
t2 = Thread(target=run_hook, args=("sess-1",))
t1.start(); t2.start(); t1.join(); t2.join()
assert not (both stdout contain '"decision": "block"')   # 3/3 次失敗:兩邊都印了
```
實跑三次,`BOTH BLOCKED` 都是 `True`。

真實觸發面:派工詞的背景事實列了「同一台機器可能同時跑多個 Codex session」——若是**不同**
session_id 同時進 `_stop_block_dir`(mkdir/chmod/iterdir 清理),我驗過是安全的(見下方
「未成立」一節);危險的是**同一個** session_id 被並發呼叫兩次,例如 Codex 對同一次 Stop
事件的 hook 呼叫重試、或 hook 命令列在設定檔裡意外重複註冊。本 diff 沒有機制排除後者,程式
碼本身在「同 session 並發」下無防護。

severity: major
blocking: 是
引句:「回 True 時已寫下 session 標記(呼叫端隨即輸出 block)。」
file: `scripts/hooks/claude/check-graph-sync.py:501-502`

### 2. `_stop_mark_write` 失敗會被靜默吞掉,且**沒有下一輪的補救**——同一 session 會反覆擋,不是「只擋一次」

`_stop_block_dir()` 把 `mkdir` + `chmod` + 清理迴圈全包在一個 `except OSError: pass` 裡,失敗時
仍然回傳那個(可能根本不能用的)`Path`。呼叫端 `_stop_mark_write(sid)` 的回傳值在 `main()`
裡直接丟棄,沒有 log、沒有 fallback、沒有重試。

實測:把 `~/.cache/lumos/stop-block` 這個路徑預先建成**一個普通檔案**(不是目錄)——對應
派工詞問的「`os.chmod` 在共用/被別人擁有的目錄上失敗的處置」與「印出 block 後
`_stop_mark_write` 失敗 → 下一輪會不會再擋一次」——同一個 `session_id="sess-1"`,先後跑兩次
(不是並發,是循序的兩個獨立 Stop 事件),兩次都拿到 `decision:block`:

```
run1 stdout: {"decision": "block", ...}
run2 stdout: {"decision": "block", ...}   # 同一 session_id,標記檔從未建成
marker path is a file still? True
```

因為 `_stop_block_dir()` 的 `mkdir(parents=True, exist_ok=True)` 撞到「同名但是檔案」的路徑會
丟 `FileExistsError`(`OSError` 子類),被吞掉;之後 `_stop_mark_path(...).exists()` 永遠是
`False`,`_stop_mark_write` 的 `os.open(..., O_CREAT|O_EXCL)` 永遠拿 `NotADirectoryError`
（`OSError` 子類)失敗。這條路徑會讓「只擋一次」退化成「每次 Stop 都擋」——正是這份改動的
設計文件明講要避免重開的那個場景(2026-07-06 撤 Stop nag 的教訓)。磁碟滿(`ENOSPC`)、目錄
被別人用不同權限建立(`chmod` 失敗但目錄本身可能仍不可寫,`os.open` 一樣拿 `OSError`)是同一
條失敗路徑的其他觸發方式,行為相同,沒有另外測。

引句:「失敗不影響已印的 block」
（這句只講對了一半——失敗確實不影響「這次已印的」,但完全沒提失敗會讓**之後每一次**都重印,
這正是「只擋一次」這個賣點會破的地方。）

severity: major
blocking: 是
引句:「失敗不影響已印的 block」
file: `scripts/hooks/claude/check-graph-sync.py:517`

### 3. `stop_hook_active` 是否真能防住「同一 turn 續做又炸一次」完全靠 Codex 端行為,repo 裡沒有第二個護欄

`codex_stop_decision` 把 `stop_hook_active` 當第一道護欄,`_stop_mark_write` 失敗時**唯一**
能擋住「連續兩次 Stop(同一次續做)都 block」的,就是 Codex 那邊確實在續做後的下一次 Stop
payload 裡把 `stop_hook_active` 設成 `true`。這是照抄 Claude Code 自己 hook 的欄位語意搬過去
用,設計筆記自己也寫了「`stop_hook_active` 語意來自文件,實測要看 f02」「相容/升級:… `stop_hook_active`
欄不在→當 False」——也就是說,如果 Codex 實際上不送這個欄位、或送的語意不同,`_stop_mark_write`
一旦失敗(finding 2),就會變成**每次 Stop 都印一次 block**,沒有第二層擋。這不是這次 diff

### 4. `_impact_missing` 的 25 秒 timeout 落在「不會 block」的那條路徑上——派工詞問的「印一半」在本次 block 邏輯裡不成立

派工詞問「hook 在 `_impact_missing`/`impact` 子行程上花超過 10 秒被 Codex 砍掉時,block 有沒有
可能已印一半」。讀完 `main()` 的控制流:`_impact_missing` 只在**閘門 3(這輪已經動過圖譜)**
那個分支被呼叫,那個分支印完 stderr 提醒就 `return 0`,根本不會走到後面 `codex_stop_decision`
/ `print(json.dumps({"decision":"block",...}))` 的程式碼。會呼叫 `_impact_missing` 的那條路
和會印 `decision:block` 的那條路是互斥的(前者要求「圖譜有動」,後者要求「圖譜沒動」),兩者
不可能在同一次呼叫裡都執行到。所以「25 秒 timeout 的子行程卡在 block 邏輯裡印一半」這個具體
擔心,在目前程式碼結構下**不成立**。

範圍內,不列入這次 severity。

### 5.「兩個不同 session 同時第一次進 `_stop_block_dir`」——查過,沒問題,不是漏洞

派工詞第一鏡頭明確問了這個情境。逐行讀 `_stop_block_dir()`:`mkdir(parents=True, exist_ok=True)`
本身是 idempotent(拿到 `FileExistsError` 会被 `exist_ok=True` 吞掉,不是 bug);`chmod(0o700)`
重複做結果一樣;清理迴圈只刪 `mtime` 超過 7 天的檔案,兩個不同 session 的 `_stop_mark_write`
落在不同檔名(`session_id` 各自 sanitize 後當檔名),彼此不會互相刪除,新建檔案的 `mtime` 必然
是「現在」,不可能被同一輪清理判定成「超過 7 天」而誤刪。也就是說「標記檔被清理迴圈在建檔瞬間
刪掉」這個疑慮,在「7 天保留窗」的設計下沒有可觸發的路徑(除非系統時鐘本身跳到 7 天後,那已經
超出這次 diff 該扛的範圍)。這一鏡頭我判「不影響」有查過、不是預設。

severity: clean
blocking: 否
引句:「d.mkdir(parents=True, exist_ok=True); os.chmod(d, 0o700)」
file: `scripts/hooks/claude/check-graph-sync.py:486`

### 6. `_codex_hook_trace` 讀取正在被砍掉的 `codex exec` 寫的 rollout 檔——不會炸,但 timeout 場的計數會失真

`run_one_codex` 在 `subprocess.run(..., timeout=timeout)` 逾時時,Python 會先 `kill()` 子行程再
丟 `TimeoutExpired`;若 `codex exec` 當下正在往 rollout `jsonl` 檔寫一行,那一行可能被砍在寫到
一半。`_codex_hook_trace` 讀檔用 `read_text().splitlines()`,只做字串包含判斷(`"LUMOS-STOP" in
line`、`'"role":"developer"' in line`),沒有 `json.loads`,所以殘缺的最後一行頂多讓那一行判定
不到、不會拋例外——探針的 `hooks_fired`/`stop_block_seen` 在 timeout 場次可能少算,不是崩潰。
這屬於探針自己的統計準確度問題,對 hook 本身的 block 行為沒有影響。

⚠ 沒有做到「精確重現一次半行寫入」的 repro(需要精準卡在子行程 write() 中途送 SIGKILL,環境
不可控),判準保守下修:低嚴重度、給不出可重複的具體失敗指令,依抑噪原則不升等,只記錄。

severity: minor
blocking: 否
引句:「for line in hits[0].read_text(encoding=\"utf-8\", errors=\"replace\").splitlines():」
file: `scripts/scenario_probe.py:426`

| 2 | `scripts/hooks/claude/check-graph-sync.py:519` | **真隱患,但影響面小** | `fd = os.open(...)` 後接 `os.write(fd, ...)`、`os.close(fd)` 全部在同一個 `try` 裡;若 `os.write` 拋 `OSError`(例如 `ENOSPC`),`fd` 不會被 close,直接落到 `except OSError: return False`,fd 洩漏。因為呼叫端(`main()`)是一支一次性行程、印完 block 幾行程式碼後就結束,fd 會隨行程結束被作業系統回收,實際傷害趨近於零;不是 dangling handle 造成長駐洩漏的那種問題。修法很輕(`os.write`/`os.close` 包一層 `try/finally` 或改 `os.fdopen(fd, "wb") as f`),但目前的寫法本身確實不是「有 with/確定 close」。 |
