# r1 邊界可執行審查——Codex 收工 Stop hook block-once

角色:外部第三方 reviewer,只讀 diff,不改檔。鏡頭:極端輸入實走 + manifest 判真假 + 圖譜固定席逐條判定。

## 一、極端輸入逐項實走(findings)

### F1. `_stop_mark_write` 的 os.open 沒用 try/finally,write 失敗會漏 fd——同 repo 已有 try/finally 前例卻沒跟
severity: minor
blocking: 否
引句:「        os.write(fd, str(time.time()).encode("utf-8")); os.close(fd)」
file: `scripts/hooks/claude/check-graph-sync.py:520`(`os.open` 在同函式第 519 行)

`fd = os.open(...)` 之後緊接 `os.write(fd, ...); os.close(fd)` 寫在同一行、無 try/finally。若 `os.write` 拋 OSError(如磁碟滿、EINTR),`os.close(fd)` 不會執行,fd 就漏在外層 `except OSError: return False` 裡沒人收。同一個 repo 對同一種手法(O_CREAT|O_EXCL 建檔寫 header)已經有正確前例——`scripts/lumos:9404-9414` 的 `rel_cascade_create` 明確用 `try: os.write(...) finally: os.close(fd)`。這支新函式沒跟這個既有慣例走。manifest 對這行的「資源」claim(見下節)是真陽性。

實測(在沙盒直接跑 `os.open` + `os.write` 失敗路徑推演,程式邏輯本身即可直接讀出此結論,不需額外構造失敗 I/O)。因為 hook 是短命子行程、行程結束 OS 會收 fd,實際外洩視窗只有行程存活的幾毫秒,傷害面很小,故列 minor 非 blocking。

### F2. session_id 為 `.` 或 `..` 時,「只擋一次」功能靜默永遠不擋(不是擋太多次,是完全失效)
severity: minor
blocking: 否
引句:「    return _stop_block_dir() / re.sub(r"[^A-Za-z0-9_.-]", "_", session_id)[:120]」
file: `scripts/hooks/claude/check-graph-sync.py:513`

消毒白名單放行 `.`、`-`、`_`,所以 session_id 剛好是 `.` 或 `..` 時不會被取代。`Path(dir) / "."` 會被 pathlib 正規化成 `dir` 自己;`Path(dir) / ".."` 雖不在 Python 端正規化,但 `.exists()` 底層呼叫 `os.stat()` 時由核心解掉 `..`,指回父目錄——兩者都「必然存在」(目錄本身在 `_stop_block_dir()` 一開始就 `mkdir(parents=True, exist_ok=True)` 建了)。於是 `codex_stop_decision` 裡 `not _stop_mark_path(session_id).exists()` 對這兩個 session_id 永遠是 `False`,擋停功能整支從第一次就靜默失效,不是本來設計的「擋一次」而是「一次都不擋」。已用實際程式碼跑出結果驗證(見下方重現指令)。

最小重現:
```
python3 - <<'EOF'
import importlib.util, tempfile, os
from pathlib import Path
spec = importlib.util.spec_from_file_location("cgs", "scripts/hooks/claude/check-graph-sync.py")
m = importlib.util.module_from_spec(spec); spec.loader.exec_module(m)
os.environ["HOME"] = tempfile.mkdtemp()
print(m.codex_stop_decision({"stop_hook_active": False}, "codex", "."))   # False,永遠不擋
print(m.codex_stop_decision({"stop_hook_active": False}, "codex", ".."))  # False,永遠不擋
EOF
```
真實 Codex session_id 幾乎不可能剛好是 `.` / `..`,可及性極低,故列 minor。

### F3. 探針 `_codex_hook_trace` 同 thread_id 多個 rollout 檔時,任取 `glob()` 第一個——結果不確定、可能整個漏掉真正發生過 hook 的那份逐字稿
severity: minor
blocking: 否
引句:「    hits = list(home.glob(f"sessions/*/*/*/rollout-*-{thread_id}.jsonl"))」
file: `scripts/scenario_probe.py:237`

`hits[0]` 直接取 glob 回傳的第一筆,順序取決於檔案系統列目錄順序(非依檔名或時間排序,已實測是 filesystem 回傳序,不保證是最新或最相關那份)。實際造出兩個同 thread_id 的 rollout 檔(一份有真 hook 注入證據、一份只是聊到相同字串的假陽性),`_codex_hook_trace` 挑到哪份是不確定的,曾把有真事件的那份整個丟掉不看,量測數字(`hooks_fired`/`stop_block_seen`)因此可能與實際發生的事情無關。已實跑重現(下方腳本),兩次呼叫因 glob 排序不同給出不同結果。因為是探針/telemetry 用途、不影響正式 hook 的擋停決策,列 minor。

最小重現(節錄,完整腳本已在審查過程跑過):建兩個檔 `rollout-A-<tid>.jsonl`(含真實 LUMOS-STOP)與 `rollout-B-<tid>.jsonl`(只有聊天文字提到相同字串),呼叫 `_codex_hook_trace(tid)`,結果只反映其中一份、且哪份不保證。

### F4. 探針對 `"role":"developer"` / `LUMOS-STOP` 用純字串子字串比對,不驗證是不是真的 JSON 欄位——訊息內容裡剛好出現這串文字就會被算成「hook 真的 fire 了」
severity: minor
blocking: 否
引句:「        if '"role":"developer"' in line and "lumos" in line.lower():」
file: `scripts/scenario_probe.py:244`

用純文字比對 JSON 行,沒有先 `json.loads` 再檢查 `payload.role` 欄位。已實測:造一行 `response_item` 訊息,`content[0].text` 只是「討論這個功能」的說明文字(內含字面 `"role":"developer"` 與 `LUMOS-STOP` 兩個字串,但角色其實是 `role":"user`、根本沒有真的 developer 訊息、也沒有真的擋停事件),`_codex_hook_trace` 仍回報 `stop_block_seen=1`。探針本身的题目正是「Codex 收工擋停」這個主題,情境探針的 prompt/回答文字提到 `LUMOS-STOP` 字樣是完全可預期的場景,不是罕見輸入。因為只影響 telemetry 準確度、不影響擋停執行本身,列 minor。

最小重現:見審查過程實跑,`fileB-only` 情境(無任何真實 hook/擋停事件)下 `_codex_hook_trace` 仍回 `{'hooks_fired': 0, 'stop_block_seen': 1}`。

### F5. `_stop_block_dir` 內兩行註解自相矛盾(一天 vs 七天)——內部不一致,依規一律報
severity: minor
blocking: 否
引句:「        now = time.time()   # lazy 清超過一天的標記」
file: `scripts/hooks/claude/check-graph-sync.py:488`(矛盾的門檻註解在同函式第 491 行)
