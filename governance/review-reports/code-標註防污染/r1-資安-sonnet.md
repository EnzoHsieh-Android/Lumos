# 代碼審 r1——資安鏡頭:標註防污染兩條路徑

審的材料是 `governance/review-reports/code-標註防污染/r1-snapshot.patch`(452 行、7 個檔),對應已提交的 `f6d481c5`。逐檔看完後,把攻擊面收斂成兩個問題:一個是這批改動自己種下的(洗牌種子退化),一個是這批改動沒有真正堵上、只用派工詞口頭交代的(材料防污染沒有機械擋)。另外也照要求核對了題庫/標註檔/治理帳本本身有沒有被這批改動動到。

## 發現一:洗牌種子退化成一個永遠不變的常數,「不同題庫不會洗成同一種排法」是假宣稱

`cmd_delta` 裡新增的洗牌邏輯用這一行決定種子材料:

引句:「_salt = str(gs.get("split_salt") or gs.get("snapshot_commit") or "")」

程式自己的註解說種子「綁題庫身分與案例編號」,而且:

引句:「種子綁題庫身分與案例編號,不同案例各自洗、不同題庫也不會洗成同一種排法。」

問題出在 `or` 的短路順序:只要 `split_salt` 這個欄位存在且非空,`snapshot_commit` 就完全不會被用到。我查了 `governance/eval/retrieval-goldset.json` 的整段 git 歷史(`git log --follow -p`),`split_salt` 從第一次出現到現在只有一個值:`lumos-retr-v1`,從未變過。也就是說,現實中種子材料只有這個固定字串加上案例編號(如 `S01`),跟「這一份題庫現在長怎樣」完全無關。

我在乾淨的隔離環境(`git clone` 到 `/tmp`、`checkout f6d481c5`,不碰工作目錄)做了直接驗證:先確認同一份題庫連跑兩次 `delta` 在 49 個案例上輸出完全一致(排除「上游順序不穩定」這個已知獨立問題的干擾,確認洗牌本身在乾淨環境下真的可重現)。接著把 `snapshot_commit` 改成一個完全虛構、跟原值毫不相干的字串,模擬「這是不同一份題庫/不同一次語料快照」,只跑一次 `delta`——結果 49 個案例的洗牌順序跟原本一字不差,無一改變。這證明 `snapshot_commit` 在種子計算裡是死路,只要 `split_salt` 還是那個從未變過的版本常數,任何案例的洗牌結果就是一個公開、可預先算出、且會在不同題庫版本間原樣重現的固定排列。

這會被利用在哪裡:整套標註流程本來就是分批、跨天甚至因為額度燒光而中途作廢重來的(同一批材料裡的評測尺修復計劃就記了一次「B 席四批只跑完前兩批,下次恢復」)。只要某一題的候選成員在兩次出卷之間沒變,評審或任何看得到 repo 的人重新看到的排列會跟上一次一模一樣——而且不需要側寫或猜測,直接把 `refresh_labels.py` 這段公開程式碼跟公開的 `split_salt` 拿去跑一次就能精準算出任何案例會排成什麼順序。這正好抵銷了 [S8] 這條防線宣稱要達成的效果:洗牌是為了不讓评审的判斷被「系統覺得誰該排前面」或「上一輪看到的順序」錨定,但種子沒有真的跟著題庫內容變,錨定管道換了個形式繼續存在。

值得說明的是,這不影響洗牌的第一層保護(排名不外洩)——因為洗牌前的正規化是按節點名字母排序、不是按系統排名,所以就算種子完全可預測,推算出來的也只是一個跟排名無關的固定排列,不會讓人反推出系統當初給的信心排序。破的是第二層宣稱(不同題庫版本之間不會洗出同一種排法、可以回溯是哪一版),不是頭號宣稱。

補充:我在檢查途中發現同一份工作目錄裡 `governance/eval/refresh_labels.py` 正被另一個並行的工作階段即時修改,其中一版註解明確把這個問題點名出來並著手換成內容指紋當種子(這份修改在材料之外、且仍在變動中,只作為佐證,不算進本報告的判定依據):file: `governance/eval/refresh_labels.py:186`(觀察當下的行號,該檔仍在被其他工作階段編輯,行號會再變)。這與我自己在隔離環境做的直接驗證方向一致,互相佐證這是一個真實、非我誤判的缺口。

severity: major
blocking: 是——這個缺口是這份 diff 自己新增的程式造成的(洗牌邏輯是全新的,先前沒有這段種子選擇),而且程式裡的註解對「不同題庫不會洗成同一種排法」做了明確宣稱,我用可重現的實驗直接證偽了這個宣稱;既然這條防線的第二層保護實際上沒有生效,而且已經確認有現成的簡單修法(把種子換成內容指紋),不應該讓帶著錯誤宣稱的版本先推出去。

## 發現二:材料檔擋得住的是「叫評審去哪裡看」,擋不住「評審自己去開題庫檔」

新增的 `material` 子命令的出身就是上一次真的漏過:

引句:「★但那個檔裡同時就存著既有標註答案★——」

這次的修法是新增一個只印題目、不印答案的檔案,並且把緩解措施寫成:

引句:「派工詞要改成指向這份,不要再叫評審去開題庫檔——那個檔裡同時存著既有答案,已實際逃逸過一次。」

這段話講的完全是「換一句派工指示」,沒有任何程式碼層面阻止評審(不論是人還是有完整檔案存取權的 AI 席位)自己去打開 `governance/eval/retrieval-goldset.json`——那個檔案本來就原封不動留在 repo 裡,`material` 只是額外多產生一份安全的檔案,不是把危險的那份檔案鎖起來或搬走。上一次的逃逸,起因就是評審自己初次翻看題庫檔時無意間看到既有標註,顯示這個管道是評審自己在瀏覽 repo 時很自然會撞到的路徑,而不是需要刻意繞過派工指示才能碰到的路徑。換句話說,造成上一次逃逸的能力(評審對整個 repo 有讀取權)這次原封不動地保留著,只是多提供了一個「本來就該去看」的安全去處。

這批改動自己的知識圖譜裡,對這一類「只靠人/派工詞口頭交代、沒有機器擋著」的殘留風險,原本是有寫成慣例的——同一份 diff 裡另一篇筆記就是這樣寫的:

引句:「機器完全看不見——這次是因為先記帳、後改檔才被抓到。」

但 `cmd_material` 的文件字串與 [S13] 那條任務項,都沒有比照這個慣例明講「沒有機械守衛,全靠派工詞」,也沒有附一個回頭重驗的日期或條件。

severity: minor
blocking: 否——造成這個殘留風險的根因(評審/AI 席位對整個 repo 有完整檔案讀取權,沒有沙箱或存取限制)在這份 diff 之前就存在,這份 diff 沒有讓它變得更糟,只是新增了一個更安全的替代檔案;擋下這份 diff 並不會讓評審少一分讀到題庫檔的能力,所以不構成必須擋這份 diff 的理由,但建議照這份 diff 自己在別處用的慣例(REVISIT 或機械檢查)把這條殘留風險寫清楚。
