# 標註防污染 r1 代碼審查(正確性)

一句話總結:兩個已知的洩漏入口([S8] 名次洩漏、[S13] 題庫夾帶答案)確實補上了,測試也真的咬人不是裝飾。但補法自己又留了兩個新的破口,而且完全沒碰到、卻走同一種洩漏方式的第三個入口也還開著——整體看,這次修法對「評審到底會讀到什麼」這件事想得不夠完整。

以下逐題回答,證據都是我拿 r1 提交(commit f6d481c5,對應本檔審查的 r1-snapshot.patch)的程式碼原封不動跑出來的,操作都在 `/tmp` 進行,repo 裡的檔案沒有被我動過。

## Q1:洗牌那段對嗎?

「先排序再洗」這個結構本身是對的:候選集合只要成員穩定,`sorted()` 的結果只看內容不看輸入順序,所以就算上游候選順序真的不穩(如新增的 Issue 筆記所述),排序後洗出來的東西還是一樣。我用夾具監聽 `collect_unjudged`、把上游順序打亂後重跑一次 delta,輸出跟正常跑一次的結果完全相同——這條防線是實的,不是空話(下方變異測試表也證實測試真的會抓到這段被拆掉)。

問題出在種子的組成,拆成一條發現:

### 發現一:洗牌種子沒有真的綁住「這份題庫」,不同題庫會洗出同一種排法

引句:「種子綁題庫身分與案例編號,不同案例各自洗、不同題庫也不會洗成同一種排法。」

程式把這句承諾寫成 `_salt = str(gs.get("split_salt") or gs.get("snapshot_commit") or "")`。但真實題庫的 `split_salt` 是一個固定不變的版本常數(`lumos-retr-v1`),不是「這份題庫的身分」——它本來是拿來切 train/held 用的鹽,設計上就是每一份題庫、每一次改版都一樣。

file: `governance/eval/retrieval-goldset.json:3`
file: `governance/eval/build_goldset.py:240`

我把 r1 的程式碼原封不動跑起來驗證:造兩份「不同題庫」(`snapshot_commit` 分別是 `aaa1111`、`bbb2222`,代表不同版本的語料快照),都用真實的 `split_salt=lumos-retr-v1`、同一個案例 id、同一組 10 個候選節點,各跑一次 delta——兩份題庫洗出來的候選順序逐一相同(10 個候選的排列完全一致,純屬巧合的機率約 1/3,628,800)。也就是說種子裡唯一真正在起作用的變數是案例編號,題庫本身的身分完全沒有進到種子裡,程式自己講的「不同題庫也不會洗成同一種排法」是一句可以被立即證偽的假宣稱。

severity: major
blocking: 是——這句承諾寫在這次新增的程式碼自己的註解裡,而違反它的正是這次新增的那一行(`_salt = ...`);修法成本不高(把種子換成題庫內容的雜湊即可),沒有理由帶著一個自己講出來、卻立刻可以證偽的安全宣稱推出去。

## Q2:題目卷真的不含答案嗎?

`material` 子命令的設計選擇是對的:它用白名單抽欄位(只印 `id`/`query`/`file`/`delta`),不是整包序列化題庫物件——這代表以後題庫多加欄位不會自動被印出來,不是「剛好沒事」。我把整個 goldset(含 `labels`)塞進材料檔尾巴的變異測過,兩支既有測試都準確翻紅(見下方表格),證明測試守得住「整包印出去」這類粗暴退化。

但白名單裡的 `delta` 欄位本身,內容沒有被檢查。

### 發現二:編輯題的 `delta` 欄位原封不動照抄,而它抄的是這個 repo 的程式碼與註解——這裡的慣例是到處直接寫節點路徑

引句:「lines.append(f"- {c['id']}｜改到的檔:`{c['file']}`｜改動:{c.get('delta', '(未記)')}")」

`delta` 欄位的內容就是被改那一行程式碼或註解的原文(我核對過真實題庫目前的 23 筆編輯題,每一筆都是這種「原句照抄」)。這個 repo 的慣例是註解裡到處直接寫 `Systems/xxx.md`、`Projects/xxx.md` 這類節點路徑——這份審查材料本身、以及 `refresh_labels.py`/`test_lumos.py` 裡新增的大量註解都是這樣寫的。只要未來哪一筆編輯題剛好改到帶節點路徑註解的那一行,`material` 就會把那個節點名稱原封不動印給評審,等於直接告訴評審「這題的答案很可能是它」。

我用 r1 的程式碼實測:造一個 `delta` 內容為「# 見 Systems/Beta.md 的核心規則,補一段」的編輯題,跑 `material` 子命令,輸出檔逐字印出 `Systems/Beta.md`。

severity: major
blocking: 是——`cmd_material` 是這次新增的函式,漏檢查是這次新增程式碼自己的疏漏;現況題庫零命中只是這 23 筆抽樣剛好沒踩到,不是這支函式本身有守住,拖到之後題庫累積更多筆才炸,成本只會更高。

## Q3:第三條洩漏路徑

引句:「★繞開不等於修好★,拿順序當依據的其他地方還在」

這句話寫在這次新增的 Issue 筆記裡,講的雖然是候選順序不穩定的殘留風險,但它點出的原則——「補了一條路徑不代表其他依賴順序的地方都安全」——剛好可以直接拿來檢查這次完全沒動到的地方。

### 發現三:`repin` 擋下時的診斷輸出,原封不動印出未洗牌的候選清單(名次序)
