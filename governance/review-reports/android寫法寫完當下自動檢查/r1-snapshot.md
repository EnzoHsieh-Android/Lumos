# Android寫法寫完當下自動檢查_計劃

> 白話:[[Projects/Android協程與API寫法機械檢查標準_計劃]] 做出型錄與規則包(第一批)之後,這份計劃把檢查接到「AI 寫完當下」與「代碼審查迴圈」:①AI 每回合要收工時,自動對這一回合改過的檔跑規則包,有新增告警就擋下叫它先修;②AI 要改 kt 檔時,把型錄〈情境決策表〉裡相關的一到三列推到它眼前;③代碼審要記「通過」之前,先跑新增告警與表態兩道機械檢查,不乾淨不准記。使用者原話(2026-11-05):「我會希望是 code review 的 loop 中就檢查乾淨,不用等到推送」「最好是自動化檢查,不需要我記得敲什麼指令才去盤點」。2026-11-05 從母計劃拆出(母計劃第二輪設計審 43 條裡 36 條落在這幾個新機制;設計審流程的熔斷提示是「累計折入超過 20 條就建議拆小」);拆出時列的七組未解問題,本版逐組改寫範圍,對照見〈開審前的改寫〉。

PRIOR-ART: ①回合結束擋停借既有收工點名鉤子(擋一次讓模型續做、`stop_hook_active` 與會談標記兩道護欄防無限擋);改檔前推列借既有改檔前影響鉤子的 `--stdin-payload`。②工作樹改動清單:不用暫時索引加 `git add -A`(母計劃 r2 八條問題的根源),改讀 `git --no-optional-locks status --porcelain=v2 -z`——git 官方文件說明 v2 格式是給程式解析的穩定格式,列出未合併(`u` 開頭)、改名(`2` 開頭)與未追蹤(`?`)三種,不寫索引也不算物件雜湊(https://git-scm.com/docs/git-status#_porcelain_format_version_2 )。③「改動當下就給回饋」:ESLint、Clippy 這類工具在編輯器裡即時標錯的慣例;Claude Code 的 Stop 鉤子可以回 `decision: block` 加理由讓模型續做(https://docs.claude.com/en/docs/claude-code/hooks )。採用;不選:每次改檔(PostToolUse)就跑——一回合改十幾次檔會跑十幾次,收工時跑一次就夠。
RETIRE-IF: 回合結束檢查連續三個月零擋停,降成只在審查迴圈跑;改檔前推列連續三個月沒有一列被推出,拿掉;代碼審通過前的機械檢查三個月內沒擋過任何一次,而推送前閘照樣有擋 → 查是不是漏接。

## 用詞

- **告警身分(指紋)**:新增告警閘替每條告警算的身分字串(規則、檔、去掉行號後的內容),用來判斷「同一條告警」;放行紀錄也是用它。「同一批告警」= 這次工作樹檢查新增告警的指紋多重集合(同一指紋出現幾次也算),排序後取雜湊。
- **工作樹檢查**:對「還沒提交的改動」跑新增告警比對——基準是 HEAD 那一版、現在版直接讀工作樹的檔。既有新增告警閘只比兩個提交(終點解不出來時判成環境不可用),本案多一個明示的「工作樹」終點。新增告警閘本體的說明在 [[Systems/pitfalls-code-loop]]。
- **這一回合碰過的檔**:工作樹上有未提交改動的程式碼檔(`git status` 列得到),而且檔案修改時間晚於「上一次回合結束的時刻」:回合結束鉤子每次跑都在自己的標記目錄寫一個這個會談的時間戳檔(新增),下一次讀它;會談第一次收工沒有時間戳檔時,用逐字稿第一筆紀錄的時間。不用「逐字稿最後一則使用者輸入」判回合開始——擋停回饋與壓縮接續的訊息在逐字稿裡跟使用者輸入同形(前掃實查本機逐字稿)。用修改時間而不是逐字稿列舉工具名,shell 寫的檔也算得到([[Systems/graph-sync-coverage]] 記過走 shell 的寫檔遠多於編輯工具)。
- **決策表列編號**:型錄〈情境決策表〉每列第一欄 `D-<n>`(2026-11-05 第一批型錄合併時已加);讀表函式 `_kt_decision_table`(新增)跟 [[Projects/Android寫法語意情境表態與盲判_計劃]] 共用,兩案誰先實作誰建。
- **鉤子時間上限**:鉤子註冊表(`scripts/merge-claude-settings.py` 的 `HOOK_BUDGET`)給每支鉤子的秒數;跟本文〈天花板〉(能力限制)是兩件事。
- **快工具**:`.lumos/config.json` 的 `lint_new.worktree_tools`(新增,字串清單,預設 `["ast-grep", "sg"]`)列的執行檔名。工作樹檢查只跑第一個詞是快工具、而且整條命令通過「安全形狀」檢查的宣告命令。
- **安全形狀**:命令裡除了佔位符與一個 `> {LINT_SARIF_OUT}` 重導向之外,不含 `;`、`|`、`&`、`` ` ``、`$(`、`<`、換行,第一個詞是快工具。只有長這樣的命令會在回合結束時自動執行。
- 型錄、規則包、接電方式、表態、盲判的定義見母計劃與 [[Projects/Android寫法語意情境表態與盲判_計劃]]〈用詞〉。

## 範圍

1. **新增告警指令** `lumos lint-new`(新增):
   - `--diff <範圍>`:對提交範圍跑既有的新增告警判定(跟推送前閘同一支判定函式)。
   - `--worktree [--only <檔>…]`:跑工作樹檢查(見 2)。
   - 兩種都加 `--budget 秒`,預算從指令一開始起算(含抽檔)。
   - 退出碼照判定函式既有的八種狀態分三類(`--diff` 跟推送前閘完全同判:預算不夠沒跑到的命令照既有規則算擋;`--worktree` 例外見範圍 2):**擋**(blocked)rc1,每條印「檔:行、規則訊息、放行用的指紋」,最多印 20 條、其餘印條數;**乾淨或刻意不查**(clean、warn、off、no-config、no-files)rc0,每種各印一句講明是哪一種(warn 照印新增告警但註明「設定成只報告」);**沒檢查到**(not-checked、env-unavailable;`--worktree` 模式下預算不夠沒跑到的命令也歸這類)rc3,印哪條命令沒跑、為什麼(第一個詞找不到執行檔就明說「沒裝 <工具>」),結尾一句「這次沒有被檢查,不算乾淨」。
   - 這支指令不寫治理帳(放行帳只有推送前閘記)。
2. **工作樹檢查**:判定函式多收一個明示參數「終點是工作樹」(不沿用「終點解不出來」那條路,那條照舊判環境不可用)。
   - 改動清單:讀 `git --no-optional-locks status --porcelain=v2 -z --untracked-files=all`,不寫索引、不加物件(`git status` 平常會順手刷新索引檔裡的檔案時間資訊並寫回,`--no-optional-locks` 關掉這件事,git 官方文件 https://git-scm.com/docs/git#Documentation/git.txt---no-optional-locks )。`u` 開頭(合併衝突)的檔不掃,列成「衝突中、沒檢查」;`2` 開頭(已暫存的改名)照它配的舊路徑當基準;未追蹤檔(`?`)基準為空,但若同一份清單裡有一支已刪除的檔、而 HEAD 那一版內容跟這支未追蹤檔逐位元組相同,就當成改名、拿那支當基準(只配完全相同的;部分修改後才改名的照新檔算,推送前閘會用 git 的改名偵測再判一次)。
   - 給了 `--only` 就只看那幾支(跟清單取交集);`--only` 給了但交集是空的 → 整次判 no-files,不擴大成整個工作樹。
   - 路徑在 `.lumos/` 底下的一律不掃。
   - 沒有任何提交的 repo(沒有 HEAD):基準為空、全部算新增,訊息註明。
   - linked worktree:一律在目前工作目錄所屬的 git 工作樹跑,不讀 `.git/index` 路徑(只用 git 指令)。
   - 只跑快工具且符合安全形狀的命令;其他宣告命令(含依賴層 `lint-deps.json` 全部)列成「工作樹模式不跑」(不算沒檢查,推送前閘會跑)。快工具不分先後照宣告順序跑。單條命令保底 1 秒(推送前閘的 30 秒保底不變);預算不夠沒跑到的命令在工作樹模式歸「沒檢查到」(rc3)、不擋。
   - 作弊比對(`_lint_new_guard`,要兩個提交)工作樹模式不跑,輸出註明「作弊比對留給推送前閘」。
   - 宣告檔 `.lumos/lint.json` 與 `.lumos/config.json` 的工作樹內容要跟 HEAD 那一版位元組相同才跑;有沒提交的修改 → 整次不跑、rc3、印「宣告檔有沒提交的修改,工作樹模式不執行」。
3. **回合結束自動檢查**:收工點名那支回合結束鉤子(Claude 與 Codex 共用)多一道「寫法檢查」,跟既有「改 code 沒動圖譜」那道並列、各自判。
   - 位置:插在既有那道所有提早離開(找不到圖譜、動過筆記、同批檔已講過)之前,所以沒有圖譜的專案、這輪也動了筆記的情況照樣跑。
   - 條件:專案根有 `.lumos/lint.json`,而且它與 `.lumos/config.json` 的工作樹內容都跟 HEAD 那一版相同(沒提交的宣告或改過沒提交的宣告都不自動執行,範圍 2 同一條);payload 沒有 `stop_hook_active`;`LUMOS_STOP_LINT_OFF`(新增)不是 1;這一回合碰過的檔(見〈用詞〉)非空。
   - 逐字稿只從尾端往前讀到這一回合的開頭,最多讀 20 MB(既有那道整份讀的做法不在本案改,另記回頭條件)。
   - 呼叫 `lumos lint-new --worktree --only <這一回合碰過的檔>`,用新程序群組開、逾時整個群組一起殺(新增告警閘自己的快照暫存在 `.lumos/lintbase-*`,照既有規則一天後清)。
   - 時間:這道用固定上限 10 秒;鉤子時間上限從 40 秒加到 50 秒。既有那道的內層預算照同一公式(時間上限 × 0.7 減掉已耗時,已耗時含這道),加 10 秒的上限剛好抵掉這道用的時間。
   - 只在 `lint-new` 回 rc1(擋)時擋;rc0 不出聲;rc3 印一行到 stderr。擋下原因寫「這幾條新增告警要先修」加每條「檔:行、規則訊息、放行指紋」,最多 10 條、整段最多 1500 字,結尾一行教放行指令。
   - 防無限擋:同一會談同一批告警只擋一次;一個會談這道最多擋三次。名額標記是新格式(既有那道是「每會談一個空檔、用獨佔建立搶名額」,裝不下批次與次數):同一個目錄、過同一個信任檢查,檔名 `<會談>.lint.json`,內容是擋過的批次雜湊清單,只在真的擋下時寫(既有「這個目錄只有擋過的會談才留東西」不變)。兩道都要擋時兩段原因合成一則,名額各自記。
4. **改檔前推相關列**:比對在 lumos 本體做,鉤子只印。
   - 鉤子照舊一次呼叫 `lumos impact --stdin-payload`(冷卻窗內那條 `--incidents-only` 路徑也一樣帶);payload 多一個鍵 `delta_new`:只放寫入的新內容(Edit 的 `new_string`、MultiEdit 每段的 `new_string`、Write 的 `content`),不含舊字串。既有的 `delta_text` 不動。
   - lumos 讀決策表(跟 [[Projects/Android寫法語意情境表態與盲判_計劃]] 共用同一支讀表函式),對 `delta_new` 先剝掉 Kotlin 的註解與字串字面值(新寫一支 Kotlin 版:處理 `//`、巢狀 `/* */`、`"…"`、`"""…"""`、字串樣板 `${…}` 裡的程式碼保留),再整詞、分大小寫比對每列的觸發字。
   - 一列命中至少一個觸發字就算命中;排除這個會談已經推過的列之後,照命中字數多寡、再照表序取前三列,放在回傳 JSON 的新鍵 `decision_rows`。鉤子要改兩處:既有「影響脈絡是空的就不印、直接返回」那條路,在有 `decision_rows` 時改成單獨印這幾列;冷卻窗內的事故比對路徑也印 `decision_rows`。印完才寫「已推過」標記——新標記(既有的只講一次標記鍵是失敗代碼、先寫後印,冷卻標記鍵是檔案路徑,都不合用):改檔前鉤子標記目錄下 `<會談>.rows`,一行一個列編號。並行兩次改檔可能重推同一列,不另防。
   - 只做 `.kt`、`.kts`。Codex 這一版不做(它的 apply_patch 帶得到全文,另案接)。
   - 型錄的觸發字由第一批的型錄格式檢查把關:不准收一般常用字(`map`、`try`、`let`、`if` 這類;停用字表與檢查在 [[Projects/Android協程與API寫法機械檢查標準_計劃]] S3)。
5. **代碼審通過前先跑機械檢查**:把推送檢查裡「新增告警」與「表態」兩道(只這兩道,不含合約測試、安全證據、端到端驗收與代碼審留痕——帶進留痕那道會讓 pass 自己擋自己)抽成一支共用函式,兩道一律都判完,前面那道出錯不會讓後面那道不跑;推送檢查與 `lumos code-loop pass` 都呼叫它。`pass` 在進留痕驗證(它有「沒有審查帳就回沒東西可驗」與 light 兩條提早返回)之前就先呼叫,所以那兩種情況也會先被機械檢查擋。`pass` 的範圍跟 `code-loop check` 不帶 `--diff` 時相同(跟主線的分岔點到 HEAD)。任一道擋下就不寫留痕、rc1,印擋下原因與修法。`code-loop skip` 不受影響。
6. **代碼審手冊**:lumos-code-loop 手冊在「派審查席」之前加一步「跑 `lumos lint-new --diff <分岔點>..HEAD`,rc0 才派;rc3 代表沒檢查到,不是乾淨,要先裝好工具或在派工詞寫明哪些類別沒被機械檢查」。審查席派工材料附機械檢查結果,寫明「機械已查(rc0 且是 clean)的類別席位不報」。

**不做**:推送前閘的判定結果不變(範圍 2 加參數、範圍 5 抽函式都是行為不變的重構,既有測試釘住);不在推送前閘或回合結束鉤子裡呼叫模型;不在回合結束時跑慢工具或不符安全形狀的命令;表態對程式與盲判在第三批([[Projects/Android寫法語意情境表態與盲判_計劃]])。

## 開審前的改寫(拆出時的七組未解問題 → 本版)

1. 暫時索引加整樹 add → 改讀 `git status --porcelain=v2`,不寫索引不加物件;衝突檔(`u`)列沒檢查;改名只配完全相同的內容;零提交、linked worktree 明定(範圍 2)。
2. 「這一回合寫過的檔」→ 改成「未提交而且修改時間晚於這回合開始」,shell 寫的也算;空清單整道不跑;同一回合先寫後提交的不在範圍內(寫進天花板,推送前閘與代碼審通過會擋)。
3. 預算與子程序 → 回合結束這道固定 10 秒、不切既有那道的預算;程序群組整個殺;預算從指令開頭起算;只跑快工具;逐字稿只讀尾端 20 MB。
4. 擋停語意 → `lint-new` 退出碼分擋 / 乾淨或刻意不查 / 沒檢查到三類;鉤子只在「擋」時擋,warn、off 不擋;原因有條數與字數上限。
5. 改檔前推列 → 用既有 payload 加 `delta_new` 鍵、同一次呼叫;排除已推過的列再取前三;Kotlin 版剝字串;Codex 改寫成「這版不做」;印完才標記、並行重推不防;拿掉強弱字之分,改由型錄格式檢查擋常用字。
6. 代碼審通過前先查 → 共用函式一律走每道都判完的路。
7. 資安(回合結束自動執行宣告命令)→ 只跑在 HEAD 裡被追蹤的宣告、第一個詞是快工具、整條命令符合安全形狀的命令;其他一律不在回合結束時跑。
- 新增設定鍵 `lint_new.worktree_tools` 的最小解檢討:不加的話,要嘛回合結束跑全部宣告(detekt 這類一跑幾十秒,而且會執行任意宣告命令),要嘛寫死 ast-grep(其他棧以後要接就得改程式);加一個清單鍵是兩者之間最小的。

## 實務隱患

- **回合結束檢查拖慢每一輪**:只對這一回合碰過的 kt 這類檔、只跑快工具、上限 10 秒;ast-grep 對幾支檔是毫秒級(母計劃 2026-11-05 實測)。
- **擋停迴圈**:同一批只擋一次、續做那輪不擋、一個會談最多擋三次;推送前閘照擋,逃生門是放行並寫理由。
- **共用工作目錄**:修改時間晚於這回合開始的檔,可能包含同一工作目錄別的會談同時改的檔;擋下訊息每條都帶檔名,模型自己判斷;建議每個會談用自己的工作樹(全域規則本來就這樣要求)。
- **時鐘與修改時間**:檔案修改時間被工具保留成舊值(例如 `cp -p`、`git checkout` 舊檔)時,那支檔不算這一回合碰過,推送前閘兜底。
- **改檔前推列太吵**:最多三列、同列同會談只推一次、常用字不准當觸發字。
