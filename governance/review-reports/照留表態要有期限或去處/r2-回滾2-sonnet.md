## F1 合併到主線時,綁的 Issue 先被別處收尾,主線推送才擋
severity: major
blocking: 是 判準:作者沒改任何東西、分支上全綠,合併那一刻主線 CI 變紅且 spec 沒說誰收拾、怎麼收拾。
位置:範圍第三點、做法第 5 點(不傳 today 時 born_now 只認「status_of 判開著」的 tracked_in)、S6、實務隱患。

問題:狀態是讀「被推送版本」的樹。分支 B 新寫一條已成立的 REVISIT,並照留綁 Issue X(開著),推分支時放行。之後別人在主線把 X 收尾(收尾正是這個機制鼓勵的事)。B 合併進主線時,主線推送的起點是舊主線(`scripts/lumos:41671` 的 `_push_range_start`:頂端不在主線上就取主線分岔點或舊值),這條 REVISIT 對舊主線是「沒有同一條」→ born_now → 合併結果的樹裡 X 已收尾 → 擋。例:分支 B 推送時 X=open 綠;主線上 X 改 resolved;合併 B 的推送輸入同一條 REVISIT、同一筆 ack,結果由綠變紅。spec 的「推送檢查不看日期」只保證同一個提交,合併提交是另一個提交,時間的影響以「別的分支改了 Issue 狀態」繞進來。實務隱患與天花板都沒提這條路徑,收拾的人只能在主線再補一個重綁提交。
修法方向要 spec 自己定:要嘛在實務隱患明寫這條並給重綁指令,要嘛合併提交的判定退回認任何照留;不准留空。
