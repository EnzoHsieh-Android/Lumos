## 2. `_ledger_read`(scripts/lumos:8162)回傳形狀

`_ledger_read` 恆回 `(header|None, transitions_list)`:檔案不存在/讀不到 → `(None, [])`;空檔(0 bytes)→ `splitlines()==[]` → `(None, [])`;header 行是壞 JSON → 該行整行丟棄、header 仍是 `None`(但若之後的行剛好是合法 JSON 的 transition,一樣會被算進 transitions——header 損毀不保證 transitions 也是空的);其他壞行逐行跳過不炸。

spec 例3「header 行是壞 JSON → 該檔跳過,doctor 不 traceback」要成立,T1 的實作**必須**在拿到 header 後明確判 `header is None` 再略過,否則接著算「最老天數」勢必要碰 `header["ts"]`,對 `None` 取值會直接丟 AttributeError——doctor 是鐵則3每次收工必跑的指令,一炸就整段擋。T1 的描述文字(「計 transitions==0 的帳本數與最老天數」)本身沒寫這個保護,只有例3的行為斷言隱含要求它。同檔案裡 `cmd_rel_cascade_list`(scripts/lumos:8288)已經有現成寫法可以照抄。

引句:「header=首行且 event:header 才算(torn header → None,root 不可恢復)」
引句:「root = header.get("root_decision_id") if header else "(header 損毀,root 不可恢復)"」

finding:severity=minor,blocking=否。判準:例3 已把正確行為釘死、T2 測試會在合併前抓到漏保護,不改不會在這次審查放行後就直接出包——但落地時務必照抄 `cmd_rel_cascade_list` 的 `if header else` 寫法,不是空手重寫。

## 4. `cmd_rel_cascade_list --stale`(scripts/lumos:8288)覆蓋「判到一半棄坑」

已核,成立。`--stale N` 判準是「最後事件 ts(header ts 與所有 transition ts 取 max)早於 N 天」,不是只看 header——一個「判了兩個鄰居後棄坑」的帳本(有 transition,但最近一次也是很久以前)一樣會被 `--stale` 撈出來,不會因為 transitions>0 就排除。d2「已覆蓋」機械上成立。

粗糙處(spec 自己已承認、非新發現):`--stale` 只給活動齡,沒有「還剩幾個鄰居沒判」的分母(docstring 自陳「不判開放/完成精確分類」),分不清「棄坑」和「早判完只是沒再動」——這條 spec 的實務隱患段已附回頭看條件,不重複計違規。

引句:「不判開放/完成精確分類——活動齡才是可算的 crash/失敗偵測器」

## 5. 「E2 兜底」宣稱(d4 引 scripts/lumos:8391)

不成立。全檔僅 6 處呼叫 `_rel_cascade_dir`:8103(定義)/8140(create建目錄)/8258(write)/8292(list)/8386(resume);doctor 內唯一用到 rel-cascade 帳本的地方是 E2(從 scripts/lumos:954 起)。E2 讀 `_ledger_read` 只是用來抽 transitions、折成 terminal 事件去**壓制**已判過的邊——`_h, _trs = _ledger_read(_p)` 之後 `_h`(header)整個沒被用到,E2 完全不檢查、也不理會 header 是不是壞的。E2 真正觸發 `build_on_dead` 的條件是「某節點決策 valid:false 且有 ended,連入它的來源節點 updated 早於 ended」,跟某張 cascade 帳本的 header 壞不壞是兩件互不相干的事——一張帳本 header 損毀,不會讓 E2 多印一行,doctor 任何一段都不會提到那個檔案。

「header 損毀,交補網 E2 兜底」這句話(scripts/lumos:8391)出現在 `cmd_rel_cascade_resume`——要人手動打 `lumos rel-cascade resume <cascade_id>` 才會走到的分支,講的是「這個指令救不回這張帳本,死心」,不是「doctor 的 E2 檢查會抓這張壞帳本」。全庫唯一會把「header 損毀」印給人看的,只有兩處手動指令:`cmd_rel_cascade_list`(不加 --stale 時印 `root=(header 損毀,root 不可恢復)`,scripts/lumos:8299)和 `cmd_rel_cascade_resume`(要打對那個 cascade_id 才看得到)。doctor 沒有任何主動推播管道。

引句:「header 損毀,root 不可恢復——本 cascade 放棄,交補網 E2 兜底」
引句:「_h, _trs = _ledger_read(_p)」

finding:severity=major,blocking=是。判準:不改的話,T1 會依 d4 的錯誤前提把 header 損毀的帳本從新提醒裡濾掉,而全庫其實沒有任何主動管道接住這個情況(E2 不做這件事)——會讓一類真實資料損毀永遠沉默不報,而 d4 拿來背書「首版不重做」的機械事實(E2 兜底)查無實據。進實作前應回頭修 d4:要嘛老實承認這是缺口並照專案自己的規矩附回頭看條件,要嘛把 T1 範圍擴大去涵蓋損毀帳本(比照 `cmd_rel_cascade_list` 的 `if header else` 寫法,加一段「N 張帳本 header 損毀,需人工檢視」的提醒)。
