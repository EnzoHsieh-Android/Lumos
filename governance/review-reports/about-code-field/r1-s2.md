### s2f1 — blocker:「存量先只跑 61 篇」與 spec 自己引的驗證證據自相矛盾

### s2f3 — major:過期守衛「誰在什麼時機重算」沒答,且需要一條 doctor 目前沒有的讀盤路徑

spec 204-214 行(過期守衛節)寫了「stamp 記正文 sha,doctor 加一道軟檢查」,但沒回答三個具體問題:

**(1) frontmatter 改了算不算、欄位本身改了 sha 會不會變?**
查 `split_frontmatter`(scripts/lumos:101)已經是既有原語,body 與 frontmatter 分離,spec 若真的照它現在寫的「本檔正文的 sha256」,frontmatter 改動(包含 about_code 自己被人手動改)不會動到這個 sha——這個設計本身自洽,但 spec 沒有點名要重用 `split_frontmatter`,只留一句「要另寫,不能直接借」(214 行),讀者不知道「另寫」要接在哪個既有原語上。

**(2) 誰在什麼時機重算?**
spec 完全沒寫。`about_code` 是 list 欄位、`about_code_stamp` 是 scalar 欄位,兩者理論上要一起改才一致,但查 `lumos set` 是通用單鍵寫入(`cmd_set`,scripts/lumos:7504),沒有「改 about_code 就自動重算 stamp」的耦合機制。如果人事後用 `lumos set about_code ...` 手動修正一條誤標,卻忘了同步更新 `about_code_stamp`,stamp 仍然對得上舊 sha(因為正文沒變)——**doctor 軟檢查會判定「新鮮」,但欄位內容其實剛被人改過而未必經過模型判準**。spec 的過期守衛只防「正文變了、標註沒跟上」,防不了「標註被人手動改了、stamp 沒被要求同步」,這是它自己定義的守衛留的洞。

**(3) 「impact 遇到過期的 about 欄降回 body-inline-code 等級」具體怎麼判、有沒有現成的 hook 點?**
查證 `Note` class(scripts/lumos:187-189)：

```
class Note:
    __slots__ = ("rel", "stem", "fields", "block_keys", "fm_lines",
                 "targets", "lint", "mtime")
```

**沒有 `body` 欄位。** `load_vault`(scripts/lumos:192-231)在第 207 行算出 `body`,只用來抽 `targets`,之後就丟棄,不存進 `Note`。這代表:
- doctor 現有的 Check S(scripts/lumos:823-841,`self_audit` 過期提醒)完全不需要碰 body——純比較兩個 frontmatter 日期字串,零額外讀盤成本。
- 但 about_code 的過期檢查**需要重新整讀那個檔案、重跑一次 `split_frontmatter`、再 sha256**——這是 doctor 目前完全沒有的一條讀盤路徑,spec 拿 Check S 的「軟檢查」語氣去類比,但底層機制不是同一量級的動作。這件事不是不能做(83 篇檔案重讀+雜湊是毫秒級,見 s2f8 效能段),而是 spec 完全沒有點名要新開這條讀盤路徑、沒有指定要掛在 doctor 的哪個 Check 字母。
- `impact` 側同理:`_impact_reverse_lookup`(scripts/lumos:13435 起)本來就會為每個節點重讀原始 `.md`(第 13492 行 `text = md_path.read_text(...)`),所以在這裡順手加 sha256 比對是有現成 hook 點的(這點 spec 沒寫錯,只是沒寫出來——算是一個「查得到但沒寫」的缺口,而不是「查不到」)。

**severity: major**(守衛本身「沒有這個就別做」的自我要求很高,但三個具體機制問題都沒有答案,其中「手動改 about_code 不會同步重算 stamp」是設計上的真實漏洞,不只是沒寫清楚)

### s2f4 — major:「保送前排/後排」在現行排序機制裡不存在,實作出來會改變沒有 about 欄節點的相對順序,牴觸「零退化」

spec 188-192 行(讀側怎麼用):

> 引句:「有 `about` 命中 + 有合約 → 保送前排;只有 `body-inline-code` + 有合約 → 保送後排(或降自由席,交 A 層實驗裁);無 `about` 欄(存量未標)→ 行為與現況完全相同(向後相容,零退化)。」

查證 `cmd_impact` 排序邏輯(scripts/lumos:13920-13922):

```
all_direct.sort(key=lambda x: -contract_priority(x.get("contract")))
```

現況固定席(pins)排序**只有一個維度**:合約等級(IRREVERSIBLE > INVARIANT > None),同等級內用穩定排序保留原始(依路徑字母序)順序。而 `results` 建好後,ranked 模式的 `pins`(scripts/lumos:14073)**沒有再排序一次**——直接 `pins = [r for r in results if r["pinned"]]`,順序完全繼承 `all_direct.sort()` 定的次序。

「保送前排/後排」這個概念,在現行架構裡沒有對應的排序鍵。要落地就必須新增一個以 `hit`(about vs body-inline-code)為鍵的排序維度,疊在既有的 contract 排序之上。這麼一改,**兩個合約等級相同、一個有 about 命中一個沒有的節點,原本並列(按路徑序決定先後),之後會被拆開**——沒有 about 欄的那個節點的絕對名次會後移,即使它自己的分類(body-inline-code、pinned=true)完全沒變。

在另一條路徑 `cmd_impact_diff`(scripts/lumos:14266)裡問題更直接,那裡的 pins **已經是按分數排序**:

```
pins = sorted([v for v in merged.values() if v["pinned"]],
              key=lambda v: (-v["score"], v["node"]))
```

若「保送前排」要落地成真實效果(而不是只在 `--json` 裡多一個 `hit` 欄位讓人肉眼判斷),最自然的實作是給 about 命中加分——但現行 pin 分數公式(`_dbase + (1-_dbase)*L`,scripts/lumos:14047)完全不看 `hit`。一旦為了「前排」給 about 命中加分,`cmd_impact_diff` 的分數排序就會連帶重排所有同層節點,包括沒有 about 欄的節點。

這正是 CLAUDE.md 審稿要求點名的疑慮:**「零退化」的宣稱只驗證了「單一節點的分類邏輯不變」,沒有驗證「群體排序的相對位置不變」**——而後者在 `cmd_impact_diff` 這條路徑上是可觀察、會被下游(code-loop 的受影響節點清單、頭幾名優先顯示)吃到的真實輸出差異。

**severity: major**(不是無法解決,而是 spec 承諾的「零退化」與它自己描述的排序效果二選一無法同時成立,必須明確取捨,但 spec 沒有意識到這個衝突)

## 風險類逐項(併發 / 效能 / 資源 / 回滾)

**併發:minor(未列入 s2f 編號,附帶說明)**
`cmd_set`(scripts/lumos:7504)沒有檔案鎖(全庫搜不到 `flock`/`filelock` 用於節點寫入)。批次標註腳本要連續寫 61-330 個 frontmatter,如果與另一個正在跑的 session(例如 memory 記錄的「自主迭代 loop 每天 09:30」)同時碰到同一批節點,存在 read-modify-write 競態覆蓋彼此欄位的可能。這是既有系統的通用屬性、不是 about_code 特有引入的新洞,但 about_code 是第一個「非人手動、成批寫入上百個節點」的欄位,把既有的隱性風險放大了,spec 完全沒提。

**效能:無,理由如下(已實測)**
```
$ time python3 scripts/lumos impact --file scripts/lumos --repo . --json
0.64s user 0.10s system 98% cpu 0.747 total
```
這是最壞情況(`scripts/lumos` 本身,15742 行)的現況基準,已含 `_impact_reverse_lookup` 對全庫每個節點重讀全文的成本。about_code 的過期比對只需要對「有 `about_code_stamp` 的節點」(83 或 61 篇,遠小於全庫)多算一次 `split_frontmatter` + sha256,量級是毫秒級,不會是 pre-commit/pre-push/PreToolUse hook(30s timeout)的瓶頸。

**資源(token/儲存):無,理由如下**

**回滾:major——見 s2f6**,唯一沒有交代的風險類,且是 CLAUDE.md 鐵則明文要求的項目。

一句話:「主案方向」本身(語意欄位優於字串扇出)有離線驗證撐著,站得住;但「怎麼從驗證走到上線」這一段——範圍怎麼切(s2f1 自相矛盾)、巨檔怎麼擋(s2f2 待審且覆蓋本 repo 最高頻改動)、標錯了怎麼收(s2f6 無回滾)、過期怎麼追(s2f3 機制未定義)、排序改了誰的名次會變(s2f4 牴觸零退化)、新訊號會不會真的被人看到(s2f5 消費端未改)——六個問題全部指向同一個模式:**這份 spec 對「模型該不該標」想得很細,對「標完之後這個系統怎麼活下去」想得很少**。建議在 design-loop 進實作前,至少把 s2f1(範圍矛盾)、s2f2(巨檔門檻)、s2f6(回滾)三條寫清楚——這三條不是「實作時再說」量級的細節,是會決定「61 篇存量現在能不能跑」的前提。
