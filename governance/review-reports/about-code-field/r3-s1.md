## s1f1 — blocker:回滾子命令「刪 stamp」沒有對應指令可用

**位置**:存量與增量 → 回滾路徑段。

引句:「對每篇把 `about_code` 清單逐值 `cmd_remove` 並刪 stamp」

**問題**:`about_code`(清單)用 `cmd_remove` 逐值刪沒問題——`remove` 只認 `LIST_KEYS`
(`scripts/lumos:7244`),而 `about_code` 打算註冊進 `LIST_KEYS`,`cmd_remove`
(`scripts/lumos:7566-7589`)確實是「list 項移除」的合法工具。**但 `about_code_stamp`
是純量**,spec 自己把它放進 `SCALAR_KEYS` 名單。純量欄位的合法寫入路徑只有 `cmd_set`
(`scripts/lumos:7503-7520`),而 `cmd_set` 只能「改成另一個值」,不能「刪掉這個鍵」——
它沒有 unset/清空語意。全庫 grep `cmd_unset|cmd_clear|cmd_delete_key|cmd_drop` 零命中,
`scripts/lumos` 里完全沒有「移除一個純量欄位」的指令。`edit_fm_remove`
(`scripts/lumos:7374-7409`)函式本體也明文寫死「`kind != "list"` 就丟 ValueError」
(第 7392-7393 行:`raise ValueError(f"{key} 是{kind}型欄位,remove 只能從清單型欄位拿掉項目")`)。
所以 spec 說的「刪 stamp」——把 `about_code_stamp` 這個鍵整條拿掉——在目前 `scripts/lumos`
裡沒有任何指令能做到;`about-code revert` 子命令按 spec 字面描述沒辦法完整實作,回滾機制
的最後一步(把 stamp 也清乾淨,避免同一批節點被下一次 revert 誤判為「還沒撤」)是空的。

**file:line**:`scripts/lumos:7244`(LIST_KEYS)、`:7392-7393`(edit_fm_remove 硬擋 scalar)、
`:7503-7520`(cmd_set,只能覆寫不能刪鍵)、`:7566-7589`(cmd_remove,僅認 LIST_KEYS)。

## s1f2 — blocker:過期判準改用 `git log` 後,沿用舊(比字串)的「毫秒級」成本說法未重新驗證,且未採用已在同份 spec 裡用過的批次原則

**位置**:過期守衛 → 讀側段(r2 補丁段落)。

引句:「過期判準改成 **git 最後改動日期**(`git log -1 --format=%cs -- <檔>`)> stamp 日期」

**問題**:緊接在這句之後,spec 讀側段落原封不動保留了 r1 時代的成本論證——

引句:「不是算雜湊;席二實測 impact 全庫重讀 0.75s,這個判斷毫秒級」

這句話是**針對舊機制**(比較兩個已經在記憶體裡的日期字串)算的,r2 把機制換成「每個候選節點
一次 `git log` 子行程」之後,這個論證沒有被重新驗證,直接原句保留。實測(本 repo,同一個
`docs/lumos-toolchain-knowledge` vault):`git log -1 --format=%cs -- <檔>` 單次呼叫連跑 20 次
耗時 2.037s,平均 **約 102ms/次**——比「毫秒級」慢兩個數量級,且比對照組的「impact 全庫重讀
0.75s」基準本身還貴。命中固定席、帶 `about_code` 的候選節點數在 spec 自己舉的例子裡就有
8 席(E10 例),若一次 hook 觸發要對其中每個 about-hit 節點各開一次 git 子行程,單這一步就可能
再加 800ms 以上,把單次 hook 延遲從 0.75s 推到 1.5s 以上,不是「毫秒級不構成熱路徑問題」。

更值得注意的是:**同一份 spec 在「巨檔判準」那段已經展示了批次意識**——反向計數
「`cmd_impact` 開頭對 `env.notes` 全掃一次…單一實作,hook/CLI/eval 共用」,明確是為了不讓
三邊各自算各自、避免 N+1。但過期判準這裡卻沒有套用同一原則:實測用單一 `git log
--name-only --format=%cs` 對整個 `docs/lumos-toolchain-knowledge/`(340 檔)掃一次歷史,
只要 **0.217s** 就能拿到全部檔案的最後改動日期,比對每個候選節點各發一次 `git log -1` 便宜
一個數量級以上。spec 沒有考慮批次查詢,是同一份文件內部方法論不一致。

**file:line**(佐證,非目標檔):以 `git log -1 --format=%cs -- <檔>` 與
`git log --name-only --format=%cs -- docs/lumos-toolchain-knowledge/` 對本 repo 實測。

## s1f3 — blocker:`about_code: []` 空清單語法會被既有 T1 手術層判成 scalar,`lumos append` 對範本生的節點必定 rc2

**位置**:存量與增量表格(增量列)。

引句:「`lumos new` 四種範本與 NEW_HINT 都要加 `about_code:` 空欄與一句提示」

**問題**:沿用既有 `aliases: []` 慣例(範本目前就是這樣寫的,`scripts/lumos:8142/8147`),
但 `fm_structure`(`scripts/lumos:7549-7568`)判斷一個 key 是 scalar 還是 list 的規則是看
「冒號後面那一行是不是空字串」——`val == ""` 才算 list(多行區塊),否則一律歸 scalar
(第 7566-7568 行 else 分支)。`about_code: []` 冒號後面是 `[]`,不是空字串,所以會被判成
**scalar**,不是 list。已直接呼叫 `edit_fm_append` 重現:

```
fm_lines = ['type: system', 'status: doing', 'aliases: []', 'tags:', '  - type/system']
edit_fm_append(fm_lines, 'aliases', '測試別名')
→ ValueError: aliases 是scalar型欄位,append 只能加進清單型欄位
```

這不是我編的邊界情況,是直接跑 `scripts/lumos` 裡的函式重現出來的。spec 明文把
`lumos append`(清單欄位寫入的唯一合法指令)定為 about_code 存量批次寫入與增量填值的路徑
(「寫入用 `lumos append`」段落),而範本又要求每個新節點起手是 `about_code: []`——兩者放在
一起,任何一個從範本生出的節點,第一次要填 about_code 時用 `lumos append` 一定 rc2。這條路
唯一能走的方式是手動改 YAML 文字(先把 `[]` 換成裸 `about_code:` 再逐行加),但 CLAUDE.md
明令「開頭欄位用指令改…別手改」,兩條規矩互撞。這個雷同樣會咬到既有的 `aliases: []`(可能是
既存 bug),但 spec 沒有意識到、也沒有繞開,是直接把既有的坑複製進新欄位的寫入路徑核心。

**file:line**:`scripts/lumos:7549-7568`(`fm_structure`,`val==""` 才判 list)、
`:7342-7345`(`edit_fm_append` 對非 list kind 直接 raise)、`:8142/8147`(既有 `aliases: []`
範本寫法,about_code 打算沿用同款語法)。

## s1f4 — major:「走 refresh_labels.py 同款雙評審」的資料結構跟 about_code 預標格式對不上,spec 沒說是轉接還是另寫

**位置**:存量與增量表格(存量列)。

引句:「走 `refresh_labels.py` 同款雙評審」

**問題**:`refresh_labels.py` 的 `cmd_merge`(`governance/eval/refresh_labels.py:202-240`)
吃的是 `--a`/`--b` 兩份 rater json,argparse help 寫明格式是 `{cid:{node:0|1|2}}`——**考卷 case
id → 候選節點 → 0/1/2 三值分數**,合併邏輯是逐 `cid` 逐 `node` 取兩邊分數比對相等
(`int(av) == int(bv)`)。about_code 的預標資料(spec 已引用的
`about-code-prelabel-2026-08-23.json`)按 spec 全文描述的語意是**節點 → 這篇關於哪幾支檔**,
即 `{節點: [檔路徑, ...]}`——鍵是節點不是考卷 case,值是檔案路徑清單不是 0/1/2 分數。這兩種
結構完全對不上:`cmd_merge` 沒有辦法把「兩份路徑清單哪裡不一樣」映射成它認得的
`int(av) == int(bv)` 純量比對。「走同款雙評審」如果是字面呼叫 `refresh_labels.py merge`,
資料要先轉換成 case/node/score 三元組(那 case 是什麼?每個檔案路徑當一個 case、值是
0/1 表示有沒有列?)才吃得進去;如果是「另外寫一套邏輯只是精神一致」,那應該直接說「仿
refresh_labels.py 的 agreed/disputed/人裁流程另寫」,而不是讓讀者以為能直接復用既有指令。
「已有流程,成本 ×2」這句對「已有流程」的宣稱因此站不住——工具鏈本身要新增或改寫。

**file:line**:`governance/eval/refresh_labels.py:202-240`(`cmd_merge` 邏輯)、
`:350-354`(argparse help:`{cid:{node:0|1|2}}`)。

## s1f6 — minor:批次 stamp「誰標」段本身內嵌合法日期子字串,過期判準若沿用 Check S 的 regex 解析法,依賴「兩段日期永遠相同」這個沒寫明的假設

**位置**:回滾路徑段(r2 改寫)。

引句:「批次預標寫入時 `about_code_stamp` **第一段(誰標)**固定寫 `batch-<日期>`」

**問題**:Check S 現有的 self_audit 過期判定用的是 `re.search(r"(\d{4}-\d{2}-\d{2})", sa_val)`
(`scripts/lumos:834`)——**在整條字串裡搜第一個看起來像日期的子字串**,不是按 `/` 切段取
固定位置。這個寫法對 `self_audit: sonnet/2026-08-23` 沒問題,因為「誰標」段(模型名)裡不含
數字,日期只會在第二段被找到。但 about_code 的批次格式是 `batch-2026-08-23/2026-08-23`——
「誰標」段本身就內嵌一組合法 `YYYY-MM-DD`。若過期判準「同一形狀」沿用同一支 regex,
`re.search` 會在第一段裡先命中日期,巧合的是 spec 給的範例兩段日期相同,所以結果一樣;
但 spec 沒有寫明「批次寫入時兩段日期保證永遠相同」這個不變量(例如批次標註跨午夜、或分批
執行、人工事後補登等情境是否仍保證兩段一致),也沒說過期判準實際上要讀哪一段。這是一個沒被
點名、但一旦兩段日期出現落差就會讓過期判斷抓錯值的隱性假設。

**file:line**:`scripts/lumos:834`(Check S 用 `re.search` 找日期子字串,非按分隔符定位)。
