## s3f1 — blocker:「有欄但不含目標檔 → 降自由席」對 incident 路徑照樣套用,實測會打掉一支現行正確運作的事故防護

**規則**(spec「讀側怎麼用」節):三條保送路徑(direct/indirect/incident)之後再套 about_code 判定,
「不論它是 direct/indirect/incident 進來的」都受它管;沒列到目標檔 → 「不保送,降自由席按分數競爭」。

**具體案例(非假設,實測)**:`Issues/hook卸載殘留註冊.md` 是一篇事故筆記,`pitfall_when` 觸發條件是
`content:HOOK_ENTRIES`。今天執行:

```
python3 scripts/lumos impact --file scripts/test_lumos.py --ranked --json
```

輸出裡這篇是 `{'kind': 'incident', 'pinned': True, 'matched_by': 'content:HOOK_ENTRIES'}`——因為
`scripts/test_lumos.py` 裡也含字串 `HOOK_ENTRIES`(用 `grep -rl HOOK_ENTRIES` 驗過,命中
`scripts/merge-claude-settings.py`、`scripts/test_lumos.py`、`scripts/lumos` 三檔)。但這篇的離線預標
(`governance/eval/about-code-prelabel-2026-08-23.json`)裡 `about_code` 只有
`['scripts/merge-claude-settings.py', 'scripts/lumos']`——**沒有列 `scripts/test_lumos.py`**,因為這篇筆記
講的是「解除安裝時 hook 註冊沒清乾淨」,不是特別針對 test_lumos.py 這個檔。

按 r2 字面規則:這篇筆記有 `about_code` 欄、且不含 `scripts/test_lumos.py` → **降自由席**。今天改
`scripts/test_lumos.py` 若真的把 `HOOK_ENTRIES` 相關邏輯改壞,這篇事故筆記會從「無條件保送」變成
「跟其他候選比分數,分數不夠可能被擠出 top_8」。這正是 review 任務點名的那個案例:
「改 A 出過事」的筆記不會列 B,但改 B 的人看到它不虧——r2 沒有把 incident 路徑排除在降級規則外。

引句:「不論它是 direct/indirect/incident 進來的」
引句:「不保送,降自由席按分數競爭」

## s3f2 — blocker:降級規則用的是「about_code 覆蓋不到必看」的同一批數據——spec 自己的數字證明這條規則會主動傷害已標記的必看節點

**規則**同上。spec 自己在「為什麼不是同一把尺」節承認:about_code 對「必看」有系統性漏標——
train 必看 2/9、held 必看 3/5 被模型判「不關於」。

**具體案例**:假設某篇是 train 或 held 考卷裡的「必看」節點,且被納入 83 篇離線預標範圍(它有 about_code 欄)。
若模型判它「不關於」目標檔(這正是那 2/9、3/5 的情況)——按降級規則,這篇原本靠 direct/indirect/incident
保送的必看節點,現在因為「有 about_code 欄但不含目標檔」被**主動降自由席**。也就是說:標記之前這篇是無條件
保送,標記之後(僅因為模型判準有 40-60% 的必看漏標率)反而變成要跟別人搶分數的候選——**這是負向作用,
不是「零退化」**。

spec 的「零退化」承諾(r1 已改寫)明文只保「無 about 欄的節點,其 pinned 判定不變」;但沒有承諾「有 about
欄但標錯的節點,不會比沒標之前更差」。而 spec 自己給的數字(held 3/5 = 60%)顯示,一旦存量 83 篇標完,
這條降級規則命中「標錯的必看節點」不是邊緣案例,是接近六成的機率。「about_code 是必看的高精確度子集」
這句話只講對了「列進去的都準」,沒講「沒列進去的必看節點,標記完反而變差」。

引句:「train 必看 2/9、held 3/5 被判」

## s3f3 — blocker:回滾第一步指令字面跑不通,`lumos query` 沒有 `--field`/`--match` 旗標

**規則**(回滾路徑節):「整批撤 = `lumos query --field about_code_stamp --match batch-<日期>` 列出」。

**實跑驗證**:

```
$ python3 scripts/lumos query --field about_code_stamp --match batch-2026-08-23
lumos: error: unrecognized arguments: --field about_code_stamp --match batch-2026-08-23
RC=2
```

查 `query` 子命令的 argparse 定義(`scripts/lumos:15100-15112`),旗標只有
`--tag/--no-tag/--active/--contract/--linked/--include-superseded/--json`,完全沒有按任意 frontmatter
欄位值篩選的機制。這條回滾指令不是「還沒實作」的合理待辦(spec 也沒把它列進「要新增的東西」清單),
而是照字面執行會直接吃到 argparse 的 usage error、rc=2、什麼都沒列出來——批次預標若真出包,
按這份 spec 操作根本撤不掉。

引句:「lumos query --field about_code_stamp --match batch-<日期>」

file:line 查證:`scripts/lumos:15100-15112`(query 旗標全集);上方終端輸出。

## s3f4 — major:回滾第二步的指令簽章也對不上,`lumos remove` 需要第三個位置參數(具體值),不是只給欄位名

**規則**同上:「逐篇 `lumos remove about_code`」。

查 `remove` 子命令定義(`scripts/lumos:15139-15143`):`p.add_argument("note")` `p.add_argument("key")`
`p.add_argument("value")`——三個位置參數缺一不可,且 `cmd_remove`(`scripts/lumos:7566-7590`)語意是
「從清單裡拿掉**一個指定的值**」(逆操作是 append,不是「清空整個欄位」)。`about_code` 是清單欄位、
一篇筆記可能列好幾支檔——「逐篇 lumos remove about_code」字面上連 value 都沒給,argparse 會直接噴
`the following arguments are required: value`;就算補上 value,也只能一次拿掉一個檔案路徑,要清空一篇
筆記的 about_code 得對著清單裡每一項各呼叫一次 remove,不是「一篇一次」。回滾流程沒把這個迴圈寫清楚,
批次撤銷會變成「每篇再乘上它的清單長度」次呼叫。

引句:「逐篇 lumos remove about_code」

file:line 查證:`scripts/lumos:15139-15143`(remove 位置參數定義)、`scripts/lumos:7566-7590`
(`cmd_remove` 逐值移除語意)。

## s3f5 — major:過期守衛只討論了「偽陽性可接受」,沒討論更危險的反向失效——`updated` 常常沒跟著正文動,會讓真正過期的 about_code 被判「還新鮮」

**規則**(過期守衛節):`about_code_stamp` 記日期,過期判準 = `updated` > stamp 日期;spec 承認
「正文沒改只改 frontmatter 也算可能過期(偽陽性)」但說「一致性比精確性重要」接受這個代價。

**實測(15 篇隨機抽樣,比對 frontmatter `updated` 欄位 vs 該檔最後一次真的改動內容的 git commit 日期)**:

| 檔 | updated 欄 | 最後改動 commit |
|---|---|---|
| Systems/外部對照-code衍生wiki.md | 2026-07-16 | 2026-08-05 |
| Systems/design-loop.md | 2026-08-14 | 2026-08-21 |
| Projects/CLAUDE注入re-sync與版本標籤_實作計畫.md | 2026-07-06 | 2026-07-20 |
| Systems/pitfalls-lint-adapter.md | 2026-07-04 | 2026-07-24 |
| Projects/連結缺失補全_計劃.md | 2026-08-07 | 2026-08-18 |

15 篇裡 5 篇(33%)的 `updated` 明顯落後於實際最後一次內容變動——正文真的改了,`updated` 卻沒跟著手動
`lumos set` 更新。這是 spec 完全沒討論到的**反方向失效**:`about_code_stamp` 記的日期 < 這種節點的
`updated`?不,問題更糟——是這種節點的 `updated` 本身就沒有反映正文真的改過,所以就算 stamp 記的是標註
當天日期,`updated > stamp` 這個判準在這些節點上永遠不會觸發(`updated` 停在舊值,比 stamp 還舊),
過期守衛會**沉默放過**——這正是 2026-08-22 goldset 過期事故的同一個病灶(候選池釘死、語料前進沒人發現),
r2 說「這跟 goldset 標註過期是同一個病」卻只抄了 Check S 「比日期」這一半機制,沒抄到「Check S 依賴的
`updated` 欄位本身紀律不足」這個已知弱點。偽陽性(不擋、只印)代價低;這個偽陰性代價高——恰好是
about_code 存在的理由(避免用過期語意誤導固定席)失效的那個方向。

引句:「過期判準 = updated > stamp 日期」
引句:「接受,因為 Check S 本來就這樣,**一致性比精確性重要**」

file:line 查證:`scripts/lumos:823-843`(Check S 現行邏輯,`sa_date < upd` 那一行)、上表 git log 抽樣。

## s3f7 — moderate:巨檔失效門檻的反向計數,spec 沒說誰在什麼時候算、算出來的數字有沒有快取

**規則**(巨檔失效條件節):「被改的檔,若 `about_code` 命中它的節點數 ≥ N,該檔視為巨檔,對它關閉
about 判定、退回三軸既有路徑」。

這是一個「先掃全庫、數出某個檔在幾篇 about_code 裡出現」的反向計數,跟現有 `_impact_reverse_lookup`
(`scripts/lumos:13447` 起,已有 `_BASENAME_COUNTS_CACHE` 這種行程內快取先例)是同構問題,但 spec 沒有
交代:①這個計數要在 `cmd_impact` 每次呼叫時,對著已載入記憶體的 `env.notes` 全量掃一遍現算(理論上可行,
因為 `Env(vault)` 已經把全部節點載進記憶體,跟現有 direct 反查同量級),還是要另外維護一份索引檔;
②如果現算,巨檔判定要先算完计数才能決定「這篇的 about_code 判定信不信」,但 about_code 判定又是
在同一次 `cmd_impact` 呼叫裡對每個候選逐一套用的規則——這個「先算全域計數、再逐節點套用」的執行順序
沒有寫進「讀側怎麼用」的規則描述,若日後由不同人實作(hook 一套、CLI 一套、eval script 又一套),
三邊很容易算出不同的巨檔判定,而 spec 在「誠實缺口」節已經承認過一次「量的和用的不是同一支實作會漂」
(扇出算法那條),這裡是同一個風險的另一個實例,且沒被記進誠實缺口清單。

引句:「該檔視為巨檔,對它關閉 about 判定、退回三軸既有路徑」

## 總結

本輪最嚴重等級:**blocker**(s3f1、s3f2、s3f3 三條)。s3f1/s3f2 是同一個核心缺陷的兩面——
「about_code 欄位存在但不含目標檔 → 降自由席」這條規則不分青紅皂白套用在 incident 路徑和已知會
漏標必看項的節點上,用實測(hook卸載殘留註冊.md 案例)和 spec 自己公佈的數字(held 3/5 必看漏標)
都能證明它會讓已標記節點的召回**比沒標記之前更差**,跟「零退化」與「about_code 是精確度工具、
不動召回」的定位自相矛盾。s3f3/s3f4 是回滾機制字面對不上現有 CLI 介面,批次預標一旦出錯,
照 spec 寫的指令操作不了。建議 r3 至少要處理:①about_code 降級規則明確排除 incident 路徑,
且對「有 about_code 欄但可能漏標」的必看類節點另立豁免或人工複核關卡;②回滾路徑改寫成
`query`/`remove` 實際支援的呼叫方式(或者承認需要新增 `query --field` 才能做,把它列進本案要新增的
工具清單裡)。
