## s3f2（major）——must-see 棘輪的「個數不比率」免疫力，防不了 about_code 真正會製造的排擠

**段落**：症狀/成本與風險交叉問題（審稿框架給定，非 spec 單一段落）。

**查證**：`governance/eval/retrieval_eval.py:411-412`
```python
verdict["must_in_out_count"] = must_hit   # ★棘輪比的是個數不是比率★——
verdict["must_total"] = must_t            #   比率會被「總數變了」稀釋,個數不會
```
`must_ratchet`（`retrieval_eval.py:447-479`）比的是 `must_in_out_count`：must-see 節點是否出現在 `impact --ranked --top 50` 回傳的 `res`（`out_nodes = {x["node"] for x in res}`，`retrieval_eval.py:342`）——這個集合**不分固定席/自由席**。所以「固定席總數變了」本身確實不會稀釋這個計數，這點程式碼的設計理由站得住。

但 spec 沒看到的是另一條路徑：自由席有**固定配額**，不隨候選變多而擴張。`scripts/lumos:14086-14088`：
```python
_quota = int(_impact_knob("LUMOS_IMPACT_FREE_QUOTA", 10))
truncated = max(0, len(free) - min(int(top), _quota))
free = free[:min(int(top), _quota)]
```
即使評測呼叫 `impact --top 50`，自由席實際只留 10 個名額（`LUMOS_IMPACT_FREE_QUOTA` 預設 10）。`about_code` 一旦上線，會把過去「正文沒提到、沒有 hop 路徑可達」的節點也判成 direct（新的 `hit="about"` 候選），這些新候選會進來跟既有自由席候選搶那 10 個名額。若某個 must-see 節點目前正好卡在自由席第 8～10 名，多出來的 about 候選只要分數更高，就能把它擠出這個固定配額之外——`must_in_out_count` 因此下降，**這正是「個數不是比率」設計原意要防的另一種攻擊面，只是攻擊來源不是「分母變大稀釋比率」，而是「候選變多、固定配額被擠爆」**。棘輪機制本身會抓到（這是它的職責），但 spec 的「成績單」敘事把 must-see 召回講成是驗證 about_code 準不準的手段，沒有意識到 about_code 上線本身就會製造這種排擠風險，需要跟〈實驗結果〉那節一樣重新拿真資料跑一次棘輪，而不是只看「零誤放」。

**附帶問題**：spec 講「must-see 召回與固定席噪音——這兩個數字就是它的成績單」，但翻遍 `main()` 的 `gates` dict（`retrieval_eval.py:570-578` + 棘輪 `592`），**固定席噪音（`pin_noise`）完全沒有機械 gate**，只在 `report_goldset` 印出、存進 history（`retrieval_eval.py:395-398`）。也就是說「成績單」兩個數字，一個有機械閘（must-see 棘輪），另一個純觀察、不擋。spec 用「這兩個數字就是成績單」這種對等語氣描述，容易讓人誤以為兩者都有機械把關；實際只有一半。

**severity**：major——不影響「about 訊號本身有沒有鑑別力」的結論，但影響「上線後靠什麼機制知道它壞了」的可信度。

但被引用的驗證節點自己在誠實缺口段落明寫（`docs/lumos-toolchain-knowledge/Verification/2026-08-23_關於欄位離線預標驗證.md:90`）：
「**判準文字是我寫的、考卷標註是我裁的**——標的人是 Codex,但兩邊的尺都經過我的手。」

同一份驗證節點的〈做法〉一節也解釋了為什麼標註人選擇 Codex 而非本 session（`:20-21`）：
「**標的人=Codex CLI**(自讀 vault 全文),★不是本 session★——本 session 已是考卷 A 席,再由它預標等於用同一個人的判斷驗自己的判斷(昨日「假的第二個評審」教訓)。」

這說明「預標者不能等於考卷標註者」這件事本身是有明確教訓、有意識避開的——但避開的只是「同一個 session/模型」這一層，**判準文字本身（「改這支檔的人,不看這篇會不會做錯事?」這句話）和考卷「必看」定義的裁決權，仍然都出自同一個人（Enzo/本 session）**。這是比「同一模型」更根本的循環：判準怎麼寫、考卷怎麼判，兩邊的最終解釋權是同一個人，等於用同一把尺量自己畫的尺。

spec 引用這份驗證的結論時（〈離線驗證結果〉：「由此定三條:1.「關於」訊號成立...→ 主案方向確認」），**把「訊號成立」的結論原封不動搬進 spec，卻沒把驗證節點自己標記的誠實缺口一併搬進來**。這不是驗證節點的問題（它誠實揭露了），是 spec 在消化這份驗證結果時，選擇性地只搬了對主案有利的結論。

**額外一層未處理的缺口**：驗證用的標註者是 Codex（離線批次讀全文），但 spec〈存量與增量〉規劃的**增量**路徑寫的是「寫的人(多半是 Claude,那一刻正讀著全文)在 `lumos new` 時就填」（spec:199）。也就是說被驗證過品質的是 Codex 的判斷，但production 上線後大部分新標註來自 Claude——不同標註者群體，spec 沒有討論這個推廣（generalization）落差要不要重新驗證。

**severity**：blocker——「主案方向確認」這個關鍵決策的證據鏈裡，缺了一個文件自己承認存在、但 spec 沒有繼承的循環驗證問題；量測結論的獨立性因此打折扣，而 spec 沒有給讀者判斷這個折扣有多大的材料。

## s3f5（major）——「零誤放」的樣本量存在偽重複計數（pseudo-replication），且底層 goldset 版本可能已經跟 spec 引用的數字對不上

**段落**：〈症狀〉〈訊號:扇出〉〈離線驗證結果〉〈誠實缺口〉。

**引句**（誠實缺口）：
「**train split 只有 8 題、38 席固定席**,門檻是在這上面挑的,★過擬合風險高★。」

**問題一：38/99 席不是 38/99 篇不同筆記**。固定席保送的來源只有「帶合約的 61 篇」節點（spec 自己講：「存量先只跑帶合約的 61 篇——固定席只保送它們」）。8 個 train 題目、38 個固定席，代表同一批（≤61 篇的子集）合約節點被**不同題目重複計次**——比如 spec 自己舉例「`lumos-cli-lifecycle`(5,在 E10/E18/E21/E22 四題裡都出現且都是噪音)」,一篇筆記在四題都出現、算四個「席」。所以「train 18 條噪音零誤放」裡的 18，底層可能對應遠小於 18 篇的 distinct 筆記——同一篇筆記被同一個模型用同一套判準重複判斷四次,**不是四次獨立觀測**,统計上不能簡單當作 n=18 的獨立樣本去支撐「零誤放」這種強宣稱。spec 沒有拆開「(筆記,題目) pair 數」與「distinct 筆記數」這兩個不同的分母來討論置信度。

**問題二：goldset 版本時序有疑點**。目前 repo 的 `governance/eval/retrieval-goldset.json` 已經是 11 個 train edit 案例（`E09/E10/E13/E16/E17/E18/E19/E20/E21/E22/E23`），對應到最新一次 commit：
```
4f6c733 2026-08-23 02:12:22 +0800 feat(eval): 評測尺四修——消融閘/出卷器/must-see 棘輪/加題,並補標 90 筆
```
這與 spec 自己的〈誠實缺口〉「本次 goldset 剛換版(加 3 題、補 90 筆標註,rev 已變)」完全對得上——換句話說，**spec 創建當天(2026-08-23)、goldset 就已經從 8 題 train 換成 11 題**。但〈症狀〉〈訊號:扇出〉〈離線驗證結果〉三節報告的數字全部是「train n=8」「38 席」「held 10 題、99 席」——如果這些分析是在 goldset 已經換版之後才跑的，這些數字理應反映 11 題，卻沒有；如果是在換版之前跑的，那麓 spec 呈現「當前狀態」時混用了舊快照的統計數字。spec〈誠實缺口〉只承認「P@8 門檻 0.70 是舊尺定的...那個門檻在新尺上的意義未重新校準」，**只講門檻,沒講產生「零誤放」「9個必看」這些具體證據數字的樣本集本身可能也是舊尺**。這兩者是不同層次的問題,不能用同一句話帶過。

**severity**：major——不足以推翻「關於訊號有鑑別力」這個方向性結論（fanout 對照組的做法明顯更差，這個相對排序大概率穩健），但足以動搖「零誤放」這種絕對強宣稱的可信區間，而 spec 用這個強宣稱直接支撐「主案方向確認」的決策。

## s3f6（minor）——判準文字「同一把」是語意近似,不是逐字/範圍全等

**段落**：〈欄位設計〉。

**引句**（spec 給模型的判準原話）：
「改這支檔的人,不看這篇會不會做錯事?會 → 列;只是順帶提到 → 不列。」

**查證**（`governance/eval/raters/rater-instructions.md:6`）：
「編輯案例(E01-E20):想像開發者正要改這支 code 檔——這篇筆記該不該被主動推到他眼前?2=必看(**不看會出事:合約/事故/直接規格**) 1=有用(背景參考) 0=噪音」

兩段文字語意接近但不是同一句話，更關鍵的是：rater 對「必看(2)」的定義**明文限定在「合約/事故/直接規格」這個子類**，而給模型的 about_code 判準沒有這個範疇限定（任何「不看會做錯事」都列，不限合約/事故/規格類）。這個範疇差異，加上 s3f1 已指出的「這篇在講誰」vs「改這支時該不該看」的軸線差異，共同構成「同一把」宣稱的兩層鬆動——spec 只處理了後者（在離線驗證結果承認），沒有處理前者（rater 定義的子類限定）。

**severity**：minor——目前沒有證據顯示這個範疇差異實際造成誤判（驗證結果的落差已經被歸因到「實作在哪 vs 影響誰」），但作為「同一把」这个精確宣稱的支撐材料，這裡的措辭不夠嚴謹。

## s3f7（minor）——實務隱患逐類檢查

依審查要求逐類點名：

- **資料/測量完整性**：有隱患，已在 s3f1/s3f2/s3f3/s3f5 具體展開，不重複列。
- **成本（token/人力）**：spec 給了估算依據（「Codex 讀 80 候選燒 83k 推估」外推 330 篇「幾十萬 token」），量級自洽（83k/83篇≈1k/篇 × 330 ≈ 33 萬,落在「幾十萬」範圍內），**無 finding**——這塊算得住。但沒有給預算上限或「超支就停」的止損線，只有量級估計；若批次跑到一半發現實際單價遠高於推估（比如某些長文筆記），spec 沒有中途止損機制。此點併入 minor，不獨立升級。
- **安全/隱私**：無。`about_code` 只是 vault 內部 frontmatter 欄位，值是 repo 相對路徑，不涉及外部資料/憑證/個資，讀寫都在既有 `lumos set` 機制內。
