## s1f1 — blocker:「整批撤」引用的 `lumos query --field/--match` 旗標不存在

**位置**:存量與增量 → 回滾路徑段。

引句:「整批撤 = `lumos query --field about_code_stamp --match batch-<日期>` 列出 →」

**問題**:`cmd_query` 的 argparse 定義(`scripts/lumos:15100-15112`)只有這些旗標:
`--tag`(可重複)、`--no-tag`、`--active`、`--contract`、`--linked`、`--include-superseded`、
`--json`。函式本體(`scripts/lumos:6614-6663`)的篩選邏輯也只認 tag 家族 / status / contract /
linked 四種條件,完全沒有「按任意 frontmatter 欄位值比對」的通路,`--field` 和 `--match` 兩個
旗標在整個 `scripts/lumos` 裡都不存在(全庫 grep 零命中)。CLAUDE.md 索引表裡唯一帶 `--match`
的指令是 `lumos stale --candidate --match <關鍵字>`,語意是「掃 valid_under/revalidate_when」,
跟這裡要的「掃 about_code_stamp 值」完全是兩件事。

這條指令是 r1 判定折入的 s2f6/major、s1f7 兩條 finding 的「解法」,但解法本身沒有這個指令可用
——整批撤銷機制目前無法照 spec 字面執行。是本輪最嚴重的洞:一個已經被標記「已解決」的
major 缺口,實際上換了個一樣不能跑的答案。

**file:line**:`scripts/lumos:15100-15112`(query 的 argparse)、`scripts/lumos:6614-6663`
(`cmd_query` 篩選邏輯,無 field/match 分支)。

## s1f2 — major:`lumos remove about_code` 缺必填的 value 參數,單篇撤也做不到

**位置**:同上段,緊接在 s1f1 引句之後。

引句:「逐篇 `lumos remove about_code`」

**問題**:`remove` 的 argparse(`scripts/lumos:15139-15142`)是三個必填位置參數
`note`、`key`、`value`;函式簽章 `def cmd_remove(env, rel, key, value)`(`scripts/lumos:7566`)
同樣要求具體的 `value`——`remove` 是「list 欄位裡拿掉某一項」,不是「清空整個欄位」,不給
`value` 直接是缺參數的呼叫,rc 非 0。真要撤某節點的 `about_code`,得先知道它欄位裡列了哪幾支
檔案路徑,對每個值各呼叫一次 `lumos remove <note> about_code <value>`——spec 寫的指令連格式都
不完整,且沒有交代要怎麼先拿到那份值清單(`lumos show`?自己解析 frontmatter?)。跟 s1f1 是
同一段「回滾路徑」的兩個獨立洞,合起來看,整段回滾機制目前無一步可照字面執行。

**file:line**:`scripts/lumos:7566`(`cmd_remove` 簽章)、`scripts/lumos:15139-15142`
(`remove` argparse,三個必填位置參數)。

## s1f3 — major:`about_code_stamp` 的段位語意在同一批新增文字裡自相矛盾

**位置**:過期守衛段 vs 回滾路徑段(兩處都是 r1 新增,同一份 88 行 delta 內)。

引句一(過期守衛段,定義段位順序):「格式沿 `self_audit` 兩段式:`about_code_stamp:
codex/2026-08-23`(archf2 minor)。」

引句二(回滾路徑段,使用段位順序):「批次預標寫入時 `about_code_stamp` 第二段(誰標)固定寫」

**問題**:引句一給的範例是「codex/2026-08-23」,對齊 `self_audit` 的寫法——查
`cmd_self_audit`(`scripts/lumos:7534` 一帶)確認寫入邏輯是
`cmd_set(env, rel, "self_audit", f"{model}/{date}")`,即 **第一段是誰(model/who)、第二段是
日期**。但引句二明講「第二段(誰標)」,把第二段當成「誰」——跟引句一定義的段位順序直接相反。
兩句話都是 r1 這次新加的,不是舊文字沒跟上新文字,是**兩段新文字彼此就對不上**。如果真的照
引句二實作(第二段寫 `batch-<日期>` 這串當作「誰」),那 stamp 就會變成
「<日期>/batch-<日期>」這種怪形狀,跟引句一給的 `codex/2026-08-23` 範例完全不同構;如果照
引句一的段位順序(誰在前),回滾要找的「批次寫入」特徵值就該出現在第一段,不是第二段。
兩處至少要改一處,否則寫入程式碼時無所適從。

**file:line**:`scripts/lumos:7534` 一帶(`cmd_self_audit`,`f"{model}/{date}"` 驗證段位順序);
about_code_stamp 本身尚未實作,無程式碼可對照,矛盾只存在 spec 文字內部。

## s1f4 — minor:兩處行號引用偏移(off-by-2),「hop≤1」的措辭也把旋鈕值講成常數

**位置**:讀側怎麼用段;過期守衛段。

引句一:「②`indirect` + 合約且 hop≤1(`:14062`)」

引句二:「Check S 現在只比 `self_audit` 的日期與 `updated`(`scripts/lumos:823-841`,零讀盤)。」

**查證**:
- 引句一實際行號是 `scripts/lumos:14060`(`if contract and hop <= min(eff_depth, _pin_hop):`),
  差 2 行。另外「hop≤1」不是寫死的常數,是 `min(eff_depth, _pin_hop)` 兩個旋鈕的預設值算出來的
  (`eff_depth` 預設 2、`LUMOS_IMPACT_PIN_HOP` 預設 1,`min(2,1)=1`)——旋鈕一動這條線就不是 1
  了,措辭上當成固定規則講,略有簡化。
- 引句二引的範圍 `823-841` 涵蓋 Check S 段落開頭與 `sa_date`/`upd` 取值,但實際做比較的那行
  `if upd and sa_date < upd:` 在 `scripts/lumos:843`,落在引用範圍外 2 行。
- 「零讀盤」這半確認為真:`sa_val`/`upd` 都是從已載入記憶體的 `n.fields` 讀,Check S 段落本身
  沒有額外開檔案。

單獨看都不影響論證方向,但两處都偏移相同的 2 行,值得抽查其他行號引用時留意同款誤差。

**file:line**:`scripts/lumos:14060`(實際的 hop 判定行)、`scripts/lumos:843`
(實際的日期比較行)。

## s1f5 — major:巨檔門檻(about 命中節點數 ≥ N)沒有交代由誰、怎麼算

**位置**:巨檔失效條件的機械判定段。

引句:「定義:★被改的檔,若 `about_code` 命中它的節點數 ≥ N(暫定 N=8,即 top_k),該檔視為
巨檔」

**問題**:全庫 grep `about_code`,除了 `governance/eval/about-code-prelabel-2026-08-23.json`
這份離線預標資料外,`scripts/lumos` 與 `governance/eval/*.py` 裡完全沒有這個欄位的任何讀寫
邏輯(這欄位本身就是本案要新增的)。「被改的檔,若 about_code 命中它的節點數 ≥ N」這句話要能
「機械判定」,前提是有地方把「每支檔 → 有幾篇 about_code 提到它」算出來——這是一個反向索引,
目前完全不存在,也沒有現成的資料結構可以借(既有的 direct/indirect/incident 三軸走的是
inline-code 掃正文,不是掃 frontmatter 清單欄位)。spec 把 N=8 的判定寫得像是「只差挑數字」,
但實際上連「這個數字從哪個函式的哪個回傳值來」都還沒有答案——是每次 `impact` 呼叫時全庫掃一遍
83 篇(或全部)節點的 about_code 欄位現算,還是額外維護一份快取索引,兩種對已量到的 0.75s
熱路徑基準線影響不同,spec 完全沒提。這是 s2f2 blocker 名義上「已折入」的項目,但折入的定義本身
留了一個沒有實作路徑的洞。

**file:line**:`grep -rn about_code scripts/lumos governance/eval/*.py` 零命中(欄位尚未存在);
`governance/eval/about-code-prelabel-2026-08-23.json`(僅有離線資料,83 篇,無讀取/計數程式)。
