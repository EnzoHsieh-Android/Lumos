### s1f5 — severity: **blocker**

**位置**:「為什麼不是用模型即時判」段(L162-169)與「過期守衛」段(L204-211)自相矛盾。

**問題**:「為什麼不是用模型即時判」這一段的核心說服力來自「讀側不變」這句話:

引句:「語意判斷發生在寫入側,**讀側不變**。★這不是退讓,這是把信任放對位置。★」

但緊接著的「過期守衛」段(這段本身標了「★沒有這個就別做★」,代表作者自己認定它是必要條件,不是可選項)寫:

引句:「`impact` 遇到過期的 `about` 欄★降回 `body-inline-code` 等級★(不信過期的語意標)」

要判定「這個 `about` 欄是不是過期」,`impact` 在讀側必須:①讀該節點目前正文、②算一次 sha256(或至少某種指紋)、③跟 `about_code_stamp` 存的雜湊比對、④依比對結果決定要不要降級。這四步都是**新增的讀側計算**,不是「查表」那麼簡單——這正好跟「讀側不變」的說服力主張矛盾。`impact` 目前是掛在 `PreToolUse` hook 上,每次 Edit/Write/MultiEdit 都會觸發(查證:`scripts/hooks/claude/impact-hook.py:2` 開頭註解「PreToolUse hook...攔截 Edit/Write/MultiEdit」),換句話說這個新增的 sha256 比對是要進**熱路徑**、且是每次編輯都要重算(除非另外快取,但 spec 沒提快取設計)。

「讀側不變」是這整節用來反駁「模型不能進計分」疑慮的核心論證——「不是退讓,是把信任放對位置」這句修辭的前提就是讀側毫無變化、風險完全隔離在寫入側。但實際設計裡讀側確實多了一段新邏輯與新的失敗模式(過期判定錯誤 → 誤降級或誤信任),這個矛盾沒有被承認,反而被「讀側不變」這個明確語句蓋掉了。

**建議**:拿掉或改寫「讀側不變」這句話,改成「讀側只多一個雜湊比對,不涉及模型」——精確界定「不變」的是什麼(不重跑模型),而不是暗示讀側邏輯完全沒有增量。

## 實務隱患鏡頭(逐類過)

- **併發**:`about_code`/`about_code_stamp` 走 frontmatter 寫入,`scripts/lumos` 全檔搜尋 `flock`/`fcntl`/`filelock` 無結果——現有 `cmd_set`/`cmd_append` 都是讀檔→改記憶體→`atomic_write_verify` 整檔覆寫,**沒有檔案鎖**。61~330 篇批次標註若拆成多個平行 agent/session 同時跑(spec 沒排除這種執行方式,且「成本估幾十萬 token」的敘述暗示會想平行化省時間),兩個行程同時對同一節點 `atomic_write_verify` 會是「後寫贏、先寫的修改(含人抽驗改過的內容)整段被蓋掉」而不會報錯——因為 `atomic_write_verify` 檢查的是「寫完之後這個 key 的值對不對」,不是「寫入前後這個檔案有沒有被別人動過」。spec 完全沒提「批次標註要單執行緒跑」這個限制,是隱患。
- **效能/熱路徑**:確認 `impact` 掛在 `PreToolUse` hook(`scripts/hooks/claude/impact-hook.py`),每次 Edit/Write/MultiEdit 都觸發。目前 `_impact_direct_nodes` 對每個候選節點都要重讀整篔 `.md` 檔+跑 `_refcheck_scan`+regex,`about_code` 若只是查 frontmatter 清單,理論上比現有全文正規表達式掃描**更省**——這部分沒有性能疑慮。但 s1f5 指出的「過期守衛」sha256 比對是**額外**加上去的,不是取代現有掃描;若一個節點 `about_code` 存在但過期,還要重讀正文算 sha 再降級走 body-inline-code 路徑,等於兩份工都做——目前 61~330 篇裡若有一大部分都標了 `about_code`,熱路徑會比現況更慢,spec 未評估這個增量。
- **資源**:純檔案 I/O + 記憶體內字串處理,沒有連線/lock 需要釋放的疑慮,CLI 進程執行完即結束,無長駐資源。此類**無隱患**——每次 `lumos` 呼叫都是短命獨立進程,沒有跨呼叫共享的檔案控制代碼或網路連線。
- **回滾路徑**:批次跑完後「人抽驗」是唯一品管手段,spec 沒有講「已經進 vault 的錯誤 `about_code` 事後怎麼批次撤銷」。因為欄位是 git 追蹤的 frontmatter,理論上可以用 `git revert` 整批 commit 回滾,但前提是批次寫入要落在**單一乾淨 commit**、且回滾前沒有人手動改過那些節點的其他欄位(否則 revert 會衝突或連帶吃掉無關的手動修改)。這個「批次寫入要走一次性乾淨 commit 才好回滾」的操作限制,spec 完全沒提到,算隱患但非阻斷性,列 minor。
