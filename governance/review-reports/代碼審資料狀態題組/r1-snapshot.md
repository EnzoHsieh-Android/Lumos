# 代碼審資料狀態題組_計劃

> 白話:推送前,如果這次改動碰到「存下來的資料」——寫檔、改格式、快取、時間判斷、刪東西、對外送出——就多問作者幾題 DDIA 式的問題(新舊版本讀得懂嗎、寫一半當掉會怎樣、快取對不對得上來源……),作者表態,審查員拿表態去反駁。沒碰到就不問。

## 現況(2026-09-29 讀程式的觀察,以程式碼為準)

- 棧別檢核題按副檔名分棧(kt/cs/vue/sql/swift/node/py/java/dart),每題有 id 與觸發字;改動行命中觸發字的題才要表態,`code-loop check` 缺表態就擋推送,不看風險分級。
- 風險型樣(pitfalls 的 diff 追問)一命中就把分級拉到 high,那條路不適合掛廣觸發的題。
- 設計審的業務類追問(金流、對外送出、不可逆、自我治理)只在 `pitfalls <md>` 印;`pitfalls --diff` 不印。
- 工具鏈主程式沒有副檔名,現有棧別題對它不出題。

## 設計

1. **新增跨棧題組「資料狀態」**,放進同一張題表(鍵 `data`,題目 id 一律 `ds-` 開頭),所以表態範本、`code-loop check`、`gov --stats`、`recall-miss` 全部照舊運作,不另寫閘。
2. **哪些行算進這個題組**:這次改動裡所有「需要有家的程式檔」(每支檔有家那套判定,含沒副檔名但首行是 `#!` 的腳本)、不是測試檔、不是簿記檔的增刪行,不管副檔名是哪一棧。
3. **副檔名不能誤撞**:副檔名剛好叫 `data` 的檔不得被當成這個題組的棧。
4. **不吃行數門檻**:其他棧超過門檻全表適用的規則照舊,資料狀態題組只看觸發字。
5. **輸出標籤**:人讀輸出印成「資料狀態檢核(跨棧)」,不印成「data 效能檢核」;只列命中的題。
6. **動手前提示(PreToolUse)不接**:那條路按單一檔的棧附題,本次不動。
7. **七題**(措辭可改、id 不改):
   - `ds-evolution` 新舊互讀:這次有沒有改到會被存下來、或跨版本讀的資料形狀(檔案格式、JSON 欄位、帳本欄位、frontmatter、資料表欄位、序列化類別)?新程式讀舊資料、舊程式讀新資料,各會怎樣——缺欄位、多欄位、型別變了、舊值不合新規則?
   - `ds-partial-write` 寫一半:寫到一半被中斷(例外、被 kill、斷電、磁碟滿),留下的檔或資料列是什麼狀態?下次讀的人認得出、救得回嗎?多步寫入有沒有用暫存檔再改名或交易包起來?
   - `ds-derived` 衍生資料:這份資料是真相來源,還是從別處算出來的(快取、索引、彙總、快照、統計)?來源變了它怎麼失效?兩邊對不上時誰說了算?能不能整份丟掉重建?
   - `ds-concurrent` 同時讀改寫:兩個行程、會談或請求同時讀出、修改、寫回同一份資料時,會不會有一方的修改被蓋掉?擋它的是什麼——鎖、原子改名、交易、條件更新、只附加?
   - `ds-time` 時間:用時間做判斷(排序、過期、先後、區間)的地方,遇到時區不同、時鐘被調或倒退、兩台機器時間不一致、檔案修改時間被 git checkout 改掉,結果還對嗎?
   - `ds-irreversible` 做了回不去:有沒有刪除、覆寫、截斷、遷移這種做了就回不去的動作?回滾路徑是什麼(備份、軟刪除、先寫新再刪舊)?遷移的順序與鎖表窗口?(搬自設計審「不可逆」類)
   - `ds-side-effect` 對外副作用:這段會對外送出或改變別人的狀態嗎(寄信、推播、webhook、扣款退款、呼叫外部 API 寫入)?失敗重試會不會重複生效(冪等鍵)、會不會變成重試風暴、收端怎麼去重、部分成功怎麼對帳?(搬自設計審「金流」「對外送出」兩類)
8. **觸發字原則**:沿用範式詞加反面詞;要具體到不誤傷(例如不收單獨的 `index`、`open(`、`.get(`,因為它們在讀取與一般程式裡到處都是)。需要看字串內容的(開檔模式 `'w'`、`'a'`)放 when_raw。

## 驗收條款

- [S1] 當改動含沒有副檔名、首行是 `#!` 的程式檔,且增行寫了 `os.replace(`,pitfalls 的 diff 模式應讓資料狀態題組的 `ds-partial-write` 題列為適用,並在 `stack_questions_meta` 以 `data` 鍵列出全部七題 [test:t_data_questions_extensionless_script]
- [S2] 若改動只有測試檔、文件或簿記檔含觸發字,pitfalls 的 diff 模式應不讓任何 `ds-` 題列為適用 [test:t_data_questions_skip_tests_docs]
- [S3] 當某支程式檔增刪行超過行數門檻卻沒有任何資料狀態觸發字,pitfalls 的 diff 模式應讓該檔所屬的棧全表適用,而 `ds-` 題全部維持不適用 [test:t_data_questions_no_ask_all]
- [S4] 若改動檔的副檔名剛好是 `data`,`_stack_key_for_file` 應回傳 None,不得把它當成資料狀態題組 [test:t_data_questions_ext_not_stack]
- [S5] 當每題各給一行命中樣本、一行不命中樣本、一行只在註解裡出現觸發字的樣本,題組觸發判定應只讓命中樣本亮起它所屬的那一題 [test:t_data_questions_triggers]
- [S6] 當資料狀態題有適用題而分支沒有對應表態,`code-loop check` 應擋下推送並列出缺的 `ds-` 題 id;補上合法表態後應放行 [test:t_data_questions_gate_blocks]
- [S7] 當有資料狀態題適用,pitfalls 的 diff 模式人讀輸出應印「資料狀態檢核(跨棧)」並只列適用的題,不得印成「data 效能檢核」 [test:t_data_questions_human_label]

- 觸發字只看字面;helper 把寫檔藏起來(`_atomic_write(...)`)時看不到,靠審查席與 `recall-miss` 事後補觸發字。
- 表態工具只驗證據存在,不驗答案對錯——答案對不對留給審查席。
- ★會放大一個既有死結★:[[Issues/沒有圖譜的專案答不完表態題]]——沒有 docs/ 的專案表態指令拒寫、推送閘卻照擋。資料狀態題觸發面比棧別題廣(任何程式檔寫檔就可能亮),撞到的機會變多。本計劃不修那個死結(它要先裁「沒有圖譜的專案該不該被這道閘管」),但在那篇 Issue 補一行「受影響面擴大」,並讓測試用的假 repo 照前例帶 docs/。
