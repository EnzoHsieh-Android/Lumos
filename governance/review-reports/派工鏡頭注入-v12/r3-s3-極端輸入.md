## 新極端輸入(7 條)

### f1

問題:「呼叫者」格要對 base 樹上千個 code 檔逐一 `git show`,而既有的 `_lens_git`(已用於 v1.0/v1.1 讀 base 節點內容)用 `subprocess.run(..., text=True, timeout=20)`、沒帶 `errors=`;base 樹裡只要有一個檔案的位元組不是合法 UTF-8(非 UTF-8 編碼的原始碼、誤配副檔名的二進位檔——注意:這跟上一輪已被判「已處理」的「非 python 檔跳過」是不同軸,那條擋的是副檔名不符,擋不住「副檔名是 .py 但內容編碼壞掉」),Python 解碼 stdout 時會擲出 `UnicodeDecodeError`;`_lens_git` 的 except 只接 `(OSError, TimeoutExpired)`,`main()` 結尾又是裸的 `sys.exit(main())`,沒有全域例外捕捉,這顆例外會一路裸奔到頂層。掃描目標是「base 樹**所有** code 檔」而非只有本次改動的檔,repo 歷史上任何一個角落壞一個位元組,以後每次觸發備援都會撞同一顆雷,不是機率事件。
引句:「反查=base 樹 code 檔(`git ls-tree -r <base>` 依 CODE_EXTS_T/CODE_SKIP_DIRS 過濾,內容 `git show`)」
佐證:file: `scripts/lumos:16511-16519`(`_lens_git` 用 `text=True`、無 `errors=`,except 只接 OSError/TimeoutExpired)
佐證:file: `scripts/lumos:18280-18281`(`main()` 結尾 `sys.exit(main())`,無全域 try/except)
severity: major
blocking: 是

### f2

問題:「base 樹 code 檔」用 `git ls-tree -r <base>` 依副檔名過濾、內容用 `git show` 讀,但 symlink(mode 120000)一樣會被 `ls-tree` 列出,而 `git show <ref>:<symlink路徑>` 拿到的是**符號連結目標字串**,不是它指向的檔案內容。現場實測:建一個 `alias.py -> real_target.py` 的追蹤符號連結,`git show HEAD:alias.py` 回傳文字 `real_target.py`,不是該檔裡的原始碼。若候選識別字剛好是目標路徑裡的子字串,ASCII 邊界正規式會命中這串路徑文字,「呼叫者」格就會印出一筆「檔:行(base)」指向一個根本不含程式碼、只是路徑文字的符號連結——而消毒原則主打「零自由文字、只印 base 已追蹤路徑」正是靠這種機制讓審查員信任輸出,這裡卻能生出看起來合法、實際是路徑巧合的假引用。
引句:「反查=base 樹 code 檔(`git ls-tree -r <base>` 依 CODE_EXTS_T/CODE_SKIP_DIRS 過濾,內容 `git show`)」
佐證:指令+輸出:自建 repo 測試 `git ls-tree -r HEAD` → `120000 blob ... alias.py`;`git show HEAD:alias.py` → `real_target.py`(符號連結目標字串,非真內容)
severity: major
blocking: 是

### f3 ⚠

問題:200 檔大 PR 下,「呼叫者」格候選識別字(每個改動檔的頂層 def/class)可輕易上看數百到上千個,spec 只在**輸出**端講截斷(排序後取前 8),對**輸入**端要不要先把候選識別字砍到某個 K 值再反查完全沒講——同段其餘判斷(反查範圍、排序鍵)都明寫沿用哪個既有函式,唯獨這裡沒有;若實作對每個識別字各自跑一次 base 樹全量掃描,成本是「識別字數 × base code 檔數」的乘積,「每次 git show 前檢查剩餘」只防得住「還沒進入下一個檔案」,防不住候選集合本身在填充階段就已經過大。判不準的是「實作會不會自然選到一次性合併正規式掃描」這個更省的做法——spec 沒承諾任何一種,不能假設實作自動選對。
引句:「識別字=base 版改動檔裡 `def`/`class` 頂層名(限 `[A-Za-z_][A-Za-z0-9_]*`」
佐證:本檔 v1.2 節全文 grep 不到「識別字」與「上限/取前 K」同時出現(僅 decisions 摘要句「各上限 8」指的是輸出顯示筆數,見 spec 第 55 行)
severity: major
blocking: 是——就算最終選對省成本的實作,spec 文字本身沒有把這個要求寫下來,是留白不是已解決。

### f4

問題:「識別度不足」判準是「命中次數 ÷ base 測試方法總數 > 20%」,若某 repo 的 base 版本身沒有測試檔(全新專案,或 test profile 的 `file_name_match` 在 base 版剛好比對不到任何檔案),分母會是 0——Python 的 `/` 對分母 0 直接擲 `ZeroDivisionError`,spec 沒交代這種情況該跳過判準、視為必然不足,還是別的處理。dispatch-lens 裝在使用者所有本機專案上、每次派工都 fire,不是只在本 repo 跑,不能假設每個裝這支 hook 的專案 base 都已經有測試。
引句:「任一改動檔命中超過 base 測試方法總數 20%」
佐證:本檔 v1.2 節「受影響測試」段全文未定義分母為 0 的行為;既有 `_cochange_mine`(`scripts/lumos:13455`)雖也做除法但分母恆 ≥1(來自命中本身建構),與此處分母獨立於命中之外不同構,無現成防護可援引。
severity: major
blocking: 是

### f5

問題:「函式本體範圍(定義行到下一個頂層定義前)」留了至少三個沒答的子問題:①**檔案最後一個**頂層 def/class 沒有「下一個」,範圍延伸到檔尾與否未定;②裝飾器(如 `@staticmethod`)算不算「定義行」的一部分——若 hunk 只碰裝飾器那行、沒碰 `def` 本身或函式體,照字面相交判斷可能落空,漏掉一個確實改了函式行為的候選;③「頂層」怎麼判——用縮排(col 0)還是正則掃 `^def`/`^class`,若後者沒排除縮排,class 內的 method 會被誤判成頂層邊界切分點。這三點與同段其餘判斷不同,沒有一句提到演算法細節或「沿用既有函式」。
引句:「函式本體範圍(定義行到下一個頂層定義前)與 hunk 的 base 側行範圍相交」
佐證:本檔 v1.2 節全文 grep 不到「檔尾」「裝飾器」「decorator」「縮排」任何一個字樣,對照同段「反查」「排序」處都明寫沿用哪個既有 helper,這裡沒有
severity: major
blocking: 是

### f6

問題:「呼叫者」格排序鍵是「被引次數降冪+路徑」,但一個 base 檔案可能同時是多個不同識別字的引用地點,或同一識別字在同一檔案多行出現;列的粒度是「檔:行」,若多列共享相同被引次數與相同路徑(只差行號或識別字本身),兩個排序鍵都打平,沒有第三個 tie-break 鍵,相對順序落到底層 collection 疊代順序,不保證可重現——今天被排到第 9 名而被砍掉的候選,下一輪重算可能換人上榜。
引句:「排序=被引次數降冪+路徑」
佐證:同段輸出格式明寫「檔:行(base)」——行號不是排序鍵的一部分,而多識別字/多行同檔是常見情境(如 f5 提到 `if __name__` 慣用語旁常有多個 top-level def 同檔)
severity: minor
blocking: 否——不影響輸出內容的正確性,只影響「哪 8 個上榜」在無 cache 命中時能不能重現;截斷本身已有「另有 N 個未列」揭露,不會讓審查員誤以為看到全部。

### f7

問題:共用 30 秒 deadline 是「每次 git show 前檢查」,若真正吃時間的是第三格(呼叫者,要掃 base 樹全部 code 檔),前兩格(受影響測試、共改夥伴)完全可能已經算完、拿到真實有效的結果——但 spec 字面寫「超過→**整段**備援跳過」,讀起來是連已經算好、沒有額外成本就能印的前兩格結果也一併丟棄,只印「略(超時)」。這剛好是「越大越複雜的 PR、越需要鏡頭」那個情境最容易撞上的路徑,丟掉已完成的部分結果比起「印出前兩格、只把第三格標略過」給審查員的資訊更少,是本可以免費省下的損失,spec 沒討論這個取捨。
引句:「每次 `git show` 前檢查剩餘,超過→整段備援跳過」
佐證:同節「新增檔那行獨立印,與皆空行不互斥」是明確處理過的並存邏輯範例——對照之下,「部分格已完成 vs 另一格超時」這種並存情況完全沒有對應規則
severity: major
blocking: 是
