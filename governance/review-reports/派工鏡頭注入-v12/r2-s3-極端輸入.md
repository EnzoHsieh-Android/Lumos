### f1

問題:「呼叫者」格用「定義行落在 diff hunk 觸及的 base 行範圍內」把候選識別字收窄到「不是整檔 386 個 def」,但這個收窄手段對**整檔刪除**這種極端輸入結構性失效——刪除一整個檔案時,`git diff -U0` 只會產生一個 `@@ -1,N +0,0 @@` 的 hunk,「-」側涵蓋 base 版整份檔案的每一行,於是「落在 hunk 觸及範圍內」這個過濾條件對刪除案例等於沒有過濾,候選識別字集合退化成「整檔所有頂層 def/class」——正是這句話想避免的那個情境。現場驗證:`git show 7e25876 -U0 -- governance/eval/canary_calibration.py` 的 hunk 標頭確實是 `@@ -1,117 +0,0 @@`(整檔 117 行全部落在「-」側範圍內);若刪除的是像 `scripts/lumos` 這種量級的檔案(現場 `grep -cE '^def ' scripts/lumos` = 384),候選識別字會一次逼近四位數,而〈驗收〉六條裡沒有任何一條是針對「刪除檔案」的 fixture(只有「無節點引用」「只新增檔」「非 python」三種)。

引句:「★定義行落在 diff hunk 觸及的 base 行範圍內★(`git diff -U0` 的 `-` 側行號;不是整檔 386 個 def)」

佐證:指令+輸出:`git show 7e25876 -U0 -- governance/eval/canary_calibration.py` → `@@ -1,117 +0,0 @@`(整檔刪除,hunk 涵蓋全部 117 行)
佐證:指令+輸出:`grep -cE '^def ' scripts/lumos` → `384`(本 repo 最大宗被改檔案的頂層 def 數量級)

severity: major
blocking: 是——這個機制的存在理由就是「避免整檔 def 洪水」,對整檔刪除這個常見且未被驗收覆蓋的輸入形態直接失效,而不是效能微調問題;不補一條刪除情境的驗收或另立規則,實作者不會知道這裡沒被守住。
