### f2

### f4

severity: minor
blocking: 否

⚠ spec 用「`grep -F -w` 等級」比對識別字,但 C locale 下 `-w` 的 word-boundary 只認 `[A-Za-z0-9_]` 為 word 字元,CJK 字元(本 repo 大量用中文識別字命名)在此定義下不算 word 字元,會讓短識別字被長識別字的子字串誤判命中(例如比對「作廢訂單」會誤中「作廢訂單量」)。因為輸出只有「檔:行」不含比對文字,這個邊界瑕疵不會洩漏自由字串,只會製造誤導性的「這裡呼叫了 X」假陽性;仍建議實作前明訂 Unicode-aware 邊界規則或改用 `git grep -F -w` 實測驗證,不要留給實作者猜。

引句:「識別字比對,`grep -F -w` 等級,不做語法解析——三輪代碼審的教訓」

### f5

severity: major
blocking: 是

三格各自的資料源在結構上都要求檔案「已經存在於 base/歷史」——testmap 邊只挖既有追蹤檔(scripts/lumos:14528 起)、cochange 規則只挖 git log 裡出現過的 co-commit(scripts/lumos:13416)、呼叫者反查明寫只認 base 版就有的識別字——這代表任何「整份 diff 都是新增檔案」的 PR 不需要任何攻擊技巧,三格會結構性同時皆空。這正好是 v1.2 想補的場景走向反面:全新程式碼、沒有既有節點可釘,理應是最需要既有相依提示的情境,卻因三個機制的共同前提而必然印出「三格皆空」,把「機制測不到」偽裝成審查員讀到的「已確認沒有相依」。spec 的〈界線〉只承認「cochange 規則挖歷史,新檔沒夥伴」這個個別限制,沒有指出三格會同時失效,也沒有比照 d3「藏 ≤ 現狀」的推理明確承認這個組合後果。
