## Q2:命名與錯誤處理

**(a) 三態字串命名跟既有詞彙不統一**

對照:`_reinject_claude_block`(`scripts/lumos:10739`)回傳 `created|updated|unchanged|appended|sentinel_broken|no_template`——「第一次寫出」與「內容有差异改寫」明確拆成 `created`/`updated` 兩種狀態。`_install_codex_agent`(`scripts/lumos:11355`)把這兩種情境合併成單一個 `written`(不分「本來不存在」跟「本來存在但外方標記檔內容不同 needing overwrite,但目前實作根本不會走到這條路——因為只要標記在但內容不同也會直接覆寫算 written」),用字跟既有慣例的「created vs updated」拆法不同,也跟 `_link_or_copy_shared`(`scripts/lumos:11180`)用布林值 + print 訊息(不回字串列舉)的風格不同——同一個「安裝/拆機三態」問題在三處各用一套詞彙。結構是對的(仍是「回傳結果類型讓呼叫端印訊息」的既有模式),只是詞彙沒統一。

severity: minor

**(b) `_teardown_global_hooks` 新增區塊沒有依循既有的①②③④編號註解慣例**

**(c) 三種「我方」標記機制並存**

對照:本專案已有兩套「這是不是我方裝的」判法——`_reinject_claude_block` 用 sentinel 區塊(`<!-- LUMOS:GRAPH-DISCIPLINE:START/END -->`,`scripts/lumos:10739` 起)+ 三態回傳,只覆蓋 sentinel 內容、保留 sentinel 外的使用者內容(★INVARIANT★);`_link_or_copy_shared`/`_SKILL_MARKER` 用旁置的標記檔 `.lumos-managed`(`scripts/lumos:11180`、`:11236`)判斷整個目錄是不是我方裝的。這份 diff 為 TOML 檔又引入第三種寫法:把標記字串直接當成檔案內容的第一行(`# lumos-managed: 由 lumos install 寫入…`),靠「標記字串是否為檔案內容子字串」判斷是不是我方寫的,再用「整檔逐字比對」判斷要不要重寫(`scripts/lumos:11362-11368`)。

這個第三種寫法有其必要性(TOML 是單一小檔,不像 skills 是目錄,放旁置標記檔要多一個檔案;也不像 CLAUDE.md 是使用者共筆檔,需要 sentinel 只保護局部——這裡整檔都是我方的,可以整檔比對),邏輯上跟既有兩套精神一致(先判「是不是我方」,不是我方就不動)。但三種具體標記語法(HTML 注解 sentinel / 旁置 dotfile / 內嵌註解行字串)各自獨立存在、沒有共用的「我方標記」抽象或命名慣例,增加了下一個要裝新東西的人要臨場再發明第四種的風險。

severity: minor
引句:「# lumos-managed: 由 lumos install 寫入,teardown 收走」
