severity: major

我只讀、沒改檔。對程式碼的假設都查過了。第 4 條的耗時是我實際跑出來的。

## Findings

### 1. 補選只讀 base 版，作者同一提交新寫的碼表筆記永遠印不出來
severity: major
blocking: 是(核心機制在最需要它的情境失效,屬 major)

輸入:作者第一次寫外部碼比對,同一提交新增碼表筆記,例如 Q0 那種「最早寫輪詢比對 0000」的情境。
走到哪一段:S3 補選與第三項的建議流程。
壞在哪:這筆新筆記在 base 樹裡不存在,所以印不出來。

引句:
「挑出 base 版全文含外部事實行的筆記,補進列出清單」

程式碼現況:`_dispatch_lens_graph` 對 base 樹裡找不到的節點只計入 `omitted_nodes`,印「另有 N 篇本分支新增節點…未列」。見 `scripts/lumos:40320`。

第三項「沒有就先寫一篇」會把作者導向新增筆記,結果是新增的那篇審查員看不到。第三個洞「沒人寫」因此沒補到:只有以前就存在於主線的筆記才推得到。Spec 只提到「碼表筆記沒進自由席」這個限制,沒提「筆記是新增的」這個限制。

### 2. 補選的筆記排在固定席之後，固定席超過 cap 時只列名、不印外部事實行
severity: major
blocking: 是(補選結果可能整批靜默失效)

輸入:固定席有 8 篇以上,例如大改動且多個檔各有家。
走到哪一段:S3 把補選筆記補進 `listed`,再交給 `_lens_render_listed`。
壞在哪:`_lens_render_listed` 只有 `i < cap`(cap=8)的項目才讀內文,其餘印「(超出上限,只列名)」。見 `scripts/lumos:40010-40012` 與 `scripts/lumos:40039-40040`。補選項目接在尾端,排序在 cap 之外,所以拿不到外部事實行。另外,`max_lines`(400)截斷時也會先砍掉尾端。

引句:
「補進來的筆記照第一項渲染(合約行加外部事實行)。」

Spec 沒講補選項目排在 cap 內還是 cap 外,也沒講占不占 cap。

### 3. 「名稱帶 code」形狀誤傷面太大，會讓八個棧的新題大量誤觸發
severity: major
blocking: 是(spec 自己把這列為守衛面風險,卻沒釘住這條的負樣本)

輸入:`countryCode == "TW"`、`couponCode == "SUMMER"`、`lang_code != "zh"`、`zipCode == "100"`、`if (resultCode == "")`。
走到哪一段:共用形狀第三條。「接引號字串」沒限數字,字串內容不限。
壞在哪:這些都不是外部系統回應碼,卻命中共用形狀,會觸發第三項的 extcode 題和第二項的補選。

引句:
「名稱帶 code 的回應碼欄位跟引號字串比較」

這條放在一般欄,是對「剝掉字串字面後」的行比對。字面剝成 `""` 後,連「是否為數字」都判不出來。`_stack_norm_line` 的剝字面行為見 `scripts/lumos:23871`。

[S1] 只釘「無引號數字、註解」不命中,沒釘「非回應碼的 *code 欄位」不命中。

### 4. 「名稱帶 code」若寫成未錨定的 `\w*code`，在長單字行上是 O(n²)
severity: major
blocking: 是(實測,而且共用形狀同時進推送閘與鏡頭)

輸入:一行 8 萬個英數字,例如 minified JS 或 base64 資料在 `.js`/`.ts`/`.kt` 之類的代碼副檔名檔裡。
我跑的實驗:`re.compile(r"\w*code\s*(==|!=)\s*[\"']", re.I)` 搜 `"a"*20000` 耗時 1.84 秒;搜 `"a"*80000` 耗時 29.5 秒。加 `\b` 前綴後兩者都是 0.0 秒。

壞在哪:
- `_stack_applicability` 對每個改動行都跑所有題目的 pattern,沒有行長上限。見 `scripts/lumos:23897-23905`。
- 鏡頭有 45 秒總帳,補選的形狀掃描也在裡面。
- 推送前閘沒有預算約束,等於可以被一個大 bundle 的 diff 拖住。

Spec 只說「名稱帶 code」,沒規定正規式要錨定或限長,也沒有做大輸入的效能檢查。

### 5. 引號 3–5 位數字的邊界與「不認無引號數字」互相矛盾
severity: major
blocking: 是(漏掉最典型的整數回應碼寫法)

輸入 A:`if (resp.resultCode == 2000)` 或 Java 的 `int` 回應碼。這是 P1 同族的寫法,只差在型別是整數不是字串。
輸入 B:`status == "404"`、`qty == "100"`、`year == "2026"`、`pin == "1234"`。

壞在哪:
- A 漏報:無引號比較整類不認。理由只講了 HTTP 3 位(`== 200`),但範圍排除的是所有無引號數字,包括 4–5 位的 `2000`、`1005`。
- B 誤報:引號 3 位數字會命中 `"404"`、`"200"`,這跟同一段「HTTP 語意公開周知」的理由矛盾。
- 6 位以上與 1–2 位純數字字串只靠 code 欄位名那組補,而那組有第 3、4 條的問題。
- 單引號、反引號:「引號」沒定義包含哪些。Python、JS、Dart、Swift 的單引號字串很常見。

引句:
「刻意不認:沒有引號的數字比較(`== 200`,HTTP 狀態碼語意公開周知,認了會誤傷大量程式)」

### 6. 外部事實行每篇 10 行、每行 200 字，兩邊都是靜默截斷
severity: major
blocking: 是(長碼表會把相關那行吃掉,而審查員看不出有被吃)

輸入:一張有 30 個 respCode 的碼表筆記,每碼一行 FACT;或一行 FACT 把一整張表塞進去。
壞在哪:
- 只取前 10 行,是依檔案順序,不是依這次 diff 碰到的碼。diff 碰的恰好是第 11 行以後的碼時,審查員看到一份「看似完整」但不含該碼的碼表。
- `full[:200]` 沒有省略標記。截掉的尾巴可能是 `[來源:外部]` 或 `[查:]`,或碼的語意本身。
- 合約行有「另有 N 行」之類的提示(見 `scripts/lumos:40033-40040`),事實行沒有。

引句:
「每篇最多 10 行、每行截 200 字;沒有這類行就不印標題。」

### 7. 補選的預算檢查沒有約束單次讀檔，而且超時結果會被快取
severity: minor
blocking: 否(輸出有說明行,屬降級而非錯誤)

輸入:剩餘 1 秒時開始讀一篇。
壞在哪:
- 讀檔沿用 20 秒逾時。「每讀一篇前先看剩餘時間」只擋開始,不夾住單次逾時,最壞超出 45 秒總帳約 20 秒。對照備援段的 `gt()` 是用剩餘預算夾住的。
- 補選要讀一次 base(挑選),渲染時 `_read_base` 又讀一次。Spec 沒講是否共用。
- 快取鍵只有 repo、base、head、schema、表態雜湊。見 `scripts/lumos:39322`。「輸出內容依 base 與 head 決定」不成立:超時中止的輸出會被快取,TTL 20 分鐘內同範圍的派工都吃到缺補選的版本。

引句:
「快取鍵不變(輸出內容依 base 與 head 決定)」

### 8. 固定席 0 篇時，備援段與補選的先後與版面沒定義
severity: minor
blocking: 否(只影響版面)

輸入:固定席 0 篇,自由席有碼表筆記,diff 命中形狀。
走到哪一段:`if not listed:` 先印備援段,`if listed:` 才印鏡頭標頭。見 `scripts/lumos:40343-40358`。
壞在哪:補選發生在這兩個判斷之前還是之後,Spec 沒講。若之後才補,備援段先印了「圖譜沒有釘到節點」,下面又出現標頭和筆記。若之前補,備援段被抑制,而 `_lens_fallback` 的預算也被補選吃掉。

### 9. 補選形狀的改動行來源只排除測試檔，沒套現有的非代碼與簿記過濾
severity: minor
blocking: 否(多讀幾篇筆記,不改結論)

輸入:diff 裡有 `.md` 計劃筆記、`.json`、`governance/review-reports/*.patch`、簿記檔。這份計劃自己就有 `== "0000"` 的範例文字。
壞在哪:Spec 只寫「測試檔(沿用既有的測試檔判斷)」。題目觸發那邊的 `lines_by_stack` 由呼叫端用 `_stack_changed_ok` 過濾(非代碼副檔名、審計證物、簿記檔、測試檔都排除)。見 `scripts/lumos:35693`。鏡頭是新的消費者,Spec 沒說同樣套這支。若不套,筆記或證物裡的範例碼會觸發補選。

### 10. 外部事實行的辨認細節沒定義，且共用的辨認器只認 ASCII
severity: minor
blocking: 否(寫入時多半已被筆記形狀擋攔下,剩下是例外)

輸入:
- `FACT：…`、`[來源：外部]`(全形冒號)。
- `> FACT:…`、`1. FACT:…`(前置符號清單不明)。
- 一個教人怎麼寫筆記的 code fence 裡的 `FACT:… [來源:外部]` 範例行。
- 一行有兩個標記,例如 `[來源:部署] … [來源:外部]`。

壞在哪:
- `SYMBOL_RE` 與 `_CTX_SOURCE_RE` 只認 ASCII 冒號(`scripts/lumos:3342`、`scripts/lumos:3373`)。全形的行辨認不到,不是警告而是整行靜默消失。
- 「列表符號」包含哪些,Spec 沒列。
- 現有的合約行掃描 `_contract_key_matches` 逐行 `strip` 後比對,不分圍欄內外。照用的話,圍欄內的範例會被當真的碼表印出來。

引句:
「(允許前置空白與列表符號)且帶 `[來源:外部]` 標記的行。」

### 11. 第三項在大改動時變成固定要答的題，並讓進行中的分支被新題擋住
severity: minor
blocking: 否(摩擦與誤報,不是錯誤輸出)

輸入:diff 行數超過 `ask_all_over_lines` 門檻的 kt、cs、py 等任一棧的改動。
壞在哪:
- 超過門檻時,該棧「全表適用」(`scripts/lumos:23897`),extcode 題不看形狀也要問。「拿外部系統回來的代碼做判斷」對大多數大改動不適用,作者每次都要表態「不適用」。
- 升級 lumos 後,已有表態紀錄的進行中分支多了八題未表態,Spec 的回退節只講「回退」,沒講「前進」對既有分支的衝擊。
- 題目文字本身括號不成對:「(FACT 行帶 [來源:外部],附官方網址)網址寫在 [查:] 欄,不要寫進來源標記)」。

### 12. 第一項改動的是兩種鏡頭共用的渲染，設計審鏡頭也會變
severity: minor
blocking: 否(輸出增加,不改邏輯)

輸入:spec 模式(設計審)派工的計劃連結筆記帶 `[來源:外部]` 事實行。
壞在哪:`_lens_render_listed` 兩種鏡頭共用(`scripts/lumos:40065`)。Spec 的範圍寫「不在範圍:設計審」,但第一項的效果一定會出現在設計審派工詞。[S2] 也只測 diff 模式,沒有 spec 模式的測試。

## 固定席逐條判定(LUMOS-SPEC)

- **Systems/design-loop 的 `★INVARIANT★`(處置閘第五步)**:不受影響。條件是「審材要是 `.md` 計劃、條款要綁 `[test:]`、句式與回退節要合格」,規則在條款檢查那支函式。這份 spec 的 [S1]–[S5] 都帶 `[test:]`,「## 回退」節也在。這案不碰處置閘。
- **Systems/pitfalls-code-loop**:派工鏡頭與快取的行為被改動。第 2、7、8 條是對其「固定席列表、cap 8、45 秒總帳、快取」宣稱的實質衝擊。「沒命中形狀時鏡頭行為與現在完全一樣」只在第 4 條不發生、且補選不改版面時成立。

最嚴重等級 major,共 6 條 blocking(第 1–6 條),6 條 minor non-blocking(第 7–12 條)。
