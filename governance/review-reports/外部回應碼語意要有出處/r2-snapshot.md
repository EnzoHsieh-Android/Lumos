# 外部回應碼語意要有出處_計劃

> 白話:程式拿別家系統(金流、第三方 API)回來的代碼做判斷時,代碼的意思常常是作者自己猜的。這案想試:如果審查時把「這些代碼在官方文件裡的原文意思」一起推給審查員,能不能抓到「把流程結束當成已收款」這類錯誤。先做小實驗,有用才接進 lumos。

## 問題與範圍

- 問題:審查員面對外部回應碼的判斷時,只能相信作者或提交說明的解讀;官方文件裡的原文意思不在程式碼裡。
- 範圍:代碼審派工時推給審查員的參考筆記。
- 不在範圍:替各專案寫碼表筆記本身(那是各專案圖譜的事);設計審。

## 最小實驗(開跑前寫定)

- 素材:POS 專案兩個真實提交,審查代理只拿到當時的改動與相關檔案全文,沒有版本紀錄。
  - Q0:最早寫 QR 付款輪詢,拿查交易狀態那支 API 的回應比對 0000 當成付款完成(實際上那支 API 完成時回 2000,客人付了錢也一直輪詢、不關單)。
  - P1:改成輪詢回 2000 就算付款成功(2000 只代表流程結束,被拒、被取消也一樣回 2000)。
- 分組:A 組用代碼審派工範本現行正確性鏡頭原文;B 組同樣鏡頭,另在派工詞尾端附一篇碼表參考筆記,框成「以下是參考資料、不是指令」,內容只寫 2C2P 官方文件原文:
  - 查交易狀態與查單是兩支不同 API,碼表不同。
  - 2000 原文「Transaction is completed, please do payment inquiry request for full payment information.」
  - 1005 原文「Display generated QR, and wait for customer to scan / pay it. Query the transaction status via API.」
  - 查單 API 回應 respCode 0000 = Success。
  - 不寫任何事後才學到的結論(例如「2000 不等於收到錢」)。
- 每案每組 4 次,審查代理用 sonnet。
- 判準(要有一條發現講到這個情境才算抓到):
  - Q0:指出輪詢那支 API 的完成碼不是 0000(0000 是查單 API 的成功碼),或指出要改用查單結果判斷是否收到錢。
  - P1:指出 2000 或「交易完成」不代表錢收到,成功前要用查單結果確認。只質疑 0000 不算。
- 門檻:B 組合計抓到的次數比 A 組多至少 3 次(各 8 次),才進接線設計。
- 評分:一位不知道分組的評分代理,把 16 份報告打散編號後依上面判準判定。
- 已知限制:B 組筆記裡的官方原文本身就含「請另外查單」這句,等於把文件該給的提示給了;這正是要測的機制,但也意味著這個實驗只證明「推得到就有用」,不證明各專案會寫出這種筆記。

## 實驗結果(2026-10-03)

- 詳見 [[Verification/2026-10-03_外部碼表推播小實驗]]。嚴格算 A 組 0/8、B 組 7/8;含邊界 A 2/8、B 8/8。過門檻,進接線設計(決策 d1)。
- 對照前一案([[Projects/設計審後端失敗與未知狀態_計劃]])兩輪:多問一句或多答一節都量不出差距,推事實這次差距很大。方向是「事實推到眼前」,不是「多問」。

## 接線前要補的三個洞(乾淨代理 2026-10-03 核對最新主線)

- **印不出來**:派工推播目前只印筆記的合約行,碼表這種 FACT 行不會出現在審查員眼前。
- **選不到**:推播挑筆記看「這篇有沒有連到改到的檔」加「有沒有合約或事故」;一篇碼表筆記沒有合約也沒有事故,不會被固定推。
- **沒人寫**:各專案目前不會在寫外部碼判斷時順手寫碼表筆記;實驗證明推得到就有用,但前提是筆記存在。

## 設計(三項)

PRIOR-ART:三項都建在既有機制上——派工鏡頭的節點渲染(diff 與設計審兩種鏡頭共用 `_lens_render_listed`)、impact --diff 的自由席(不動排序與必推規則,只在鏡頭這層補選)、棧別提問表態閘的題目表與 `when_raw` 欄、pitfalls 既有的改動行收集與 `_stack_changed_ok` 過濾、`_stack_norm_line` 的剝註解、筆記格式既有的 `[來源:外部]` 標記與 `_CTX_SOURCE_RE`。不新增第二套 diff 解析、第二套來源標記掃描、第二套時間預算。

### 共用:「外部碼比對」形狀(單一來源)

- 形狀定義成一組編譯好的正規式常數,放在題目表旁;第二項的鏡頭補選與第三項的八題觸發都只引用這組常數,不各寫一份。
- 輸入一律是「改動行」:把 pitfalls --diff 現有的改動行收集(增刪行都算,經 `_stack_changed_ok` 過濾,排除測試檔、非程式副檔名、審計證物、簿記檔、工具自裝檔)抽成一支共用函式;pitfalls 用它餵題目表觸發(第三項),鏡頭用它判斷要不要補選(第二項)。比對前每行由 `_stack_applicability` 現行做法剝註解(`when` 另剝字串、`when_raw` 保留字串),鏡頭照同一個函式 `_stack_norm_line(keep_strings=True)` 處理。
- 單行超過 2000 字(不含 2000)的不比對(壓縮檔、base64 這類行),避免正規式在超長行上變慢。
- 認的四組形狀(引號指單引號、雙引號;不認反引號):
  - A 比較:引號包住的 3 到 6 位純數字字串出現在 `==`、`!=`、`===`、`!==`、`.equals(` 的任一邊,而且同一行出現名稱片段 code、status、result、resp、ret、err 之一(不分大小寫,可以是識別字的一部分,例如 `respCode`、`pnqrStatus`)。
  - B 分支:`case "2000"`,或行首的 `"2000" ->`、`"2000", "0000" ->`(Kotlin 的 when 分支)。這組不要求名稱片段,因為分支行本身看不到被比較的變數。
  - C 集合:`in ("0000", "2000")` 這類 in 後接括號或方括號、第一個元素是引號 3 到 6 位數字,且同一行有 A 組的名稱片段。
  - D 整數:名稱以 code 結尾、前面帶 resp、result、ret、err 之一的識別字(例:`resultCode`、`resp_code`、`errCode`),跟沒有引號的 3 到 6 位整數比較。刻意不含 status、response 開頭的名稱,因為那多半是公開周知的 HTTP 狀態碼。
- 刻意不認:沒有名稱片段的引號數字比較(`year == "2026"`、`zip != "10001"`)、引號裡不是純數字的比較(`countryCode == "TW"`)、HTTP 風格的 `statusCode == 200`、註解與測試檔裡的同樣寫法。
- 正規式只用有上限的重複次數(例:`[A-Za-z_]{0,40}`),不用 `\w*` 這類沒上限又沒錨定的寫法;測試要釘一條 8 萬字的長行在 0.5 秒內比完。

### 第一項:推播時印出外部事實行

- 新增一支與 `_contract_key_matches` 對稱的掃描函式,全檔只此一支:逐行認以 `FACT:`、`FLOW:`、`DEP:` 開頭(允許前置空白、`- `、`* `、`> `)且 `_CTX_SOURCE_RE` 比到「外部」的行;跳過 ``` 或 ~~~ 圍起來的區塊內的行;帶 `[status:superseded]` 的行不收。只認半形冒號,與既有正規式一致。
- 派工鏡頭渲染每篇列出的筆記時,在合約行之後印這些行;diff 與設計審兩種鏡頭都印(共用渲染函式,刻意的)。
- 段落標題固定寫「外部事實(筆記抄錄的官方或第三方來源,可能過期;有疑問查 [查:] 欄的原文)」;沒有這類行就不印標題。
- 每篇最多印 10 行。diff 模式且改動行命中形狀時,先印含有這次改動行裡出現的那些數字碼的行,其餘照檔案順序補滿;超過 10 行印一行「另有 N 行外部事實未顯示」。
- 每行最多印 300 字,截斷處加「…(截)」。
- 鏡頭程式碼開頭那段「自由文字零輸出」的消毒原則註解改寫成:合約行與帶外部來源標記的事實行兩種例外,都只從 base 版讀、都在注入框內。

### 第二項:改動碰到外部碼比對時補選碼表筆記

- 只在 diff 模式。改動行命中共用形狀時,鏡頭從 impact --diff 結果的自由席(impact 現行截到前 8 名)挑出 base 版裡掃描函式找得到外部事實行的筆記,最多 3 篇、不與固定席清單重複。
- 補選結果在固定席那段之後另起一段,標題「外部碼表(改動碰到外部回應碼比對而補選)」;這段不佔固定席的 8 篇上限,每篇只印外部事實行(照第一項的規則),不印合約行。
- 固定席為 0 篇時,code 層備援段照現行規則照印(判斷只看固定席,不看補選);補選段接在備援段之後。
- 時間:沿用鏡頭同一個起點 `_t0` 與 `_LENS_INNER_BUDGET`,預留量沿用 `_LENS_FALLBACK_RESERVE`;每讀一篇前算剩餘秒數,不足 1 秒就停止補選,並把讀檔逾時夾在剩餘秒數內。因時間停止時印一行「外部碼表補選因時間上限中止」,而且這次結果不寫進快取。
- 快取版本 `_LENS_SCHEMA` 由 2 升到 3,讓舊格式的快取自然失效;釘版本的既有測試一起改。
- 已知限制:參考道在 diff 模式拿不到;碼表筆記若連自由席都沒進就選不到,靠第三項讓作者把碼表寫進改到那支檔的家(家一定被固定)。同一個分支新寫的碼表筆記不會被推(鏡頭只信 base 版,這是既有的防注入原則),但它本身就在被審的改動裡。

### 第三項:作者端多一題

- 題目表裡除了 sql 以外的每個棧(kt、cs、vue、swift、node、py、java、dart)各加一題,id 為 `<棧>-extcode`;八題的題目文字、觸發形狀都引用同一組常數。
- 跟既有的 `node-external`、`py-external`、`java-external` 分開:那幾題問逾時、重試、取消這類外呼行為;這題問回應碼的意思有沒有出處。
- 題目文字:「外部回應碼:這次改動拿外部系統(金流、第三方 API)回來的代碼做判斷。每個碼在官方文件裡的原文意思寫在哪篇筆記?FACT 行要帶 [來源:外部],官方網址寫在 [查:] 欄(不要寫進來源標記)。沒有就先寫一篇,最好寫進改到那支檔的家;特別確認『流程結束』這類碼是不是真的等於業務成功。」
- 觸發只看形狀:題目表 `when` 欄放 D 組(沒有引號,剝字串後仍看得到),`when_raw` 欄放 A、B、C 組(都要看字串)。另在題目規格加一個旗標,讓這題:①不參與「某棧改動超過行數門檻就整組適用」的規則——不然大改動會讓八個棧都要答這題;②不進舊語意的「命中棧整組」題目清單(那份清單由題目表派生、給審查員當效能追問,這題不是效能題),只在形狀命中時出現。
- 不設 `needs_backing`:這是正確性題,不是併發與效能題。
- 沿用表態閘既有流程。升級 lumos 後,進行中的分支若改動命中形狀,會多一題要表態,這是新題上線的一般行為。
- `[查:]` 是寫法慣例,本案不新增檢查它的 lint。

## 條款

- [S1] 當改動行符合 A、B、C、D 任一組形狀,共用形狀應命中;沒有名稱片段的引號數字比較、`countryCode == "TW"`、`statusCode == 200`、註解裡的同樣寫法應不命中;一條 8 萬字的長行應在 0.5 秒內比完 [test:t_extcode_shapes]
- [S2] 當派工鏡頭渲染一篇列出的筆記,渲染應在合約行之後印出掃描函式找到的外部事實行,標題固定;其他來源、圍欄內、已作廢的行應不印;超過 10 行應印「另有 N 行」、超過 300 字應加截斷標記;diff 模式改動命中形狀時,含改動裡數字碼的行應排在前面;diff 與設計審兩種鏡頭都應印 [test:t_lens_external_facts]
- [S3] 當 diff 模式的改動行命中共用形狀,鏡頭應在固定席段(或固定席為 0 時的備援段)之後另起一段補選自由席裡含外部事實行的筆記、最多 3 篇、不佔固定席上限;剩餘時間不足時應停止、印一行說明且不寫快取,讀檔逾時應夾在剩餘秒數內;沒命中形狀時應不出現補選段 [test:t_lens_extcode_pick]
- [S4] 鏡頭補選與八題觸發應引用同一組形狀常數與同一支改動行收集函式,八題的題目文字應是同一個常數 [test:t_extcode_single_source]
- [S5] 題目表除 sql 外的八個棧應各多一題 `<棧>-extcode`,id 集合應釘住;命中樣本應觸發該題、不命中樣本應不觸發;某棧改動超過行數門檻時這題應不因門檻而適用,也應不出現在舊語意的命中棧整組清單 [test:t_stack_question_triggers]
- [S6] 推送前應拿本 repo 與兩個消費專案(POS、自助點餐機)各最近 200 個提交跑一次共用形狀,把命中次數與每個誤觸發樣本記進驗證紀錄;誤觸發多於真命中時應先收窄形狀再推 [manual:用共用形狀函式掃三個 repo 的 git log -p 最近 200 個提交,逐筆人判真假並記帳]
