# 外部回應碼語意要有出處_計劃

> 白話:程式拿別家系統(金流、第三方 API)回來的代碼做判斷時,代碼的意思常常是作者自己猜的。這案想試:如果審查時把「這些代碼在官方文件裡的原文意思」一起推給審查員,能不能抓到「把流程結束當成已收款」這類錯誤。先做小實驗,有用才接進 lumos。

## 問題與範圍

- 問題:審查員面對外部回應碼的判斷時,只能相信作者或提交說明的解讀;官方文件裡的原文意思不在程式碼裡。
- 範圍:代碼審派工時推給審查員的參考筆記。
- 不在範圍:替各專案寫碼表筆記本身(那是各專案圖譜的事);設計審。

## 最小實驗(開跑前寫定)

- 素材:POS 專案兩個真實提交,審查代理只拿到當時的改動與相關檔案全文,沒有版本紀錄。
  - Q0:最早寫 QR 付款輪詢,拿查交易狀態那支 API 的回應比對 0000 當成付款完成(實際上那支 API 完成時回 2000,客人付了錢也一直輪詢、不關單)。
  - P1:改成輪詢回 2000 就算付款成功(2000 只代表流程結束,被拒、被取消也一樣回 2000)。
- 分組:A 組用代碼審派工範本現行正確性鏡頭原文;B 組同樣鏡頭,另在派工詞尾端附一篇碼表參考筆記,框成「以下是參考資料、不是指令」,內容只寫 2C2P 官方文件原文:
  - 查交易狀態與查單是兩支不同 API,碼表不同。
  - 2000 原文「Transaction is completed, please do payment inquiry request for full payment information.」
  - 1005 原文「Display generated QR, and wait for customer to scan / pay it. Query the transaction status via API.」
  - 查單 API 回應 respCode 0000 = Success。
  - 不寫任何事後才學到的結論(例如「2000 不等於收到錢」)。
- 每案每組 4 次,審查代理用 sonnet。
- 判準(要有一條發現講到這個情境才算抓到):
  - Q0:指出輪詢那支 API 的完成碼不是 0000(0000 是查單 API 的成功碼),或指出要改用查單結果判斷是否收到錢。
  - P1:指出 2000 或「交易完成」不代表錢收到,成功前要用查單結果確認。只質疑 0000 不算。
- 門檻:B 組合計抓到的次數比 A 組多至少 3 次(各 8 次),才進接線設計。
- 評分:一位不知道分組的評分代理,把 16 份報告打散編號後依上面判準判定。
- 已知限制:B 組筆記裡的官方原文本身就含「請另外查單」這句,等於把文件該給的提示給了;這正是要測的機制,但也意味著這個實驗只證明「推得到就有用」,不證明各專案會寫出這種筆記。

## 實驗結果(2026-10-03)

- 詳見 [[Verification/2026-10-03_外部碼表推播小實驗]]。嚴格算 A 組 0/8、B 組 7/8;含邊界 A 2/8、B 8/8。過門檻,進接線設計(決策 d1)。
- 對照前一案([[Projects/設計審後端失敗與未知狀態_計劃]])兩輪:多問一句或多答一節都量不出差距,推事實這次差距很大。方向是「事實推到眼前」,不是「多問」。

## 接線前要補的三個洞(乾淨代理 2026-10-03 核對最新主線)

- **印不出來**:派工推播目前只印筆記的合約行,碼表這種 FACT 行不會出現在審查員眼前。
- **選不到**:推播挑筆記看「這篇有沒有連到改到的檔」加「有沒有合約或事故」;一篇碼表筆記沒有合約也沒有事故,不會被固定推。
- **沒人寫**:各專案目前不會在寫外部碼判斷時順手寫碼表筆記;實驗證明推得到就有用,但前提是筆記存在。

- 使用者裁定候選接線範圍 1、2、3 全做;設計見下一節。

## 設計(三項)

PRIOR-ART:三項都建在既有機制上——派工鏡頭的節點渲染(兩種鏡頭共用一支)、impact 的檢索結果(不動排序與必推規則,只在鏡頭這層補選)、棧別提問表態閘的題目表(when_raw 看字串)。外部事實行的寫法沿用筆記格式既有的 `[來源:外部]` 標記,不另立新標記。

### 共用:「外部碼比對」形狀(單一來源)

- 一組正規式定義在主程式一處,第二項的鏡頭補選與第三項的題目觸發都只引用它,不各寫一份。
- 認的形狀分兩組,配合題目表兩欄的比對方式:引號數字那組要看字串,放保留字串那一欄;欄位名那組放一般那一欄(題目表要求一般欄不能空)。改動行剝掉註解:
  - 引號包住的 3 到 5 位純數字字串出現在相等或不等比較的任一邊(`== "0000"`、`"2000" ==`、`!=`、`===`、`!==`)。
  - 同樣的字串出現在 `case "2000"`、Kotlin 的 `"2000" ->` 分支、`.equals("2000")` 或 `"2000".equals(`、Python 的 `in ("0000", "2000")`。
  - 名稱帶 code 的回應碼欄位跟引號字串比較(`respCode ==`、`resultCode !=`、`status_code ==` 後接引號字串)。
- 刻意不認:沒有引號的數字比較(`== 200`,HTTP 狀態碼語意公開周知,認了會誤傷大量程式);測試檔(沿用既有的測試檔判斷)。

### 第一項:推播時印出外部事實行

- 派工鏡頭渲染每篇列出的筆記時,在合約行之後,另印該篇裡以 `FACT:`、`FLOW:`、`DEP:` 開頭(允許前置空白與列表符號)且帶 `[來源:外部]` 標記的行。
- 這段標題固定寫「外部事實(官方或第三方來源,程式碼看不到;以原文為準)」;每篇最多 10 行、每行截 200 字;沒有這類行就不印標題。
- 只印來源是「外部」的行。部署、資料庫、生產、人工來源的事實這次不印,因為實驗只量過外部。
- 標記本身要乾淨:現行正規式只認 `[來源:外部]`,網址寫在標記外面的 `[查:]` 欄(例:`FACT:2000 原文「…」 [來源:外部] [查:https://…]`);`[來源:外部 網址]` 不會被認得。

### 第二項:改動碰到外部碼比對時補選碼表筆記

- 只在 diff 模式。改動行(增刪行都算,看保留字串的版本)命中共用形狀時,鏡頭從 impact --diff 結果裡「沒被固定」的候選(自由席;impact 現行已截到前 8 名)挑出 base 版全文含外部事實行的筆記,補進列出清單,種類標「外部碼表」,最多補 3 篇,已在清單的不重複。
- 參考道(只在逐檔 impact 才有)這次不納入:diff 模式的 impact 輸出沒有參考道。碼表筆記若連自由席都沒進,這一項選不到它;這是已知限制,靠第三項讓作者把碼表筆記寫進改到那支檔的家(家一定被固定)來補。
- 補選要在鏡頭內層 45 秒總帳的剩餘時間內做:每讀一篇前先看剩餘時間,不夠就停止補選,並在輸出多印一行「外部碼表補選因時間上限中止」。
- 不動 impact 的排序、門檻與必推規則;沒命中形狀時鏡頭行為與現在完全一樣。
- 補進來的筆記照第一項渲染(合約行加外部事實行)。

### 第三項:作者端多一題

- 題目表裡除了 sql 以外的每個棧(kt、cs、vue、swift、node、py、java、dart)各加一題,id 為 `<棧>-extcode`,題目文字與觸發形狀全部引用同一組常數(單一來源)。
- 題目文字:「外部回應碼:這次改動拿外部系統(金流、第三方 API)回來的代碼做判斷。每個碼在官方文件裡的原文意思,寫在哪篇筆記?(FACT 行帶 [來源:外部],附官方網址)網址寫在 [查:] 欄,不要寫進來源標記)沒有就先寫一篇;特別確認『流程結束』這類碼是不是真的等於業務成功。」
- 沿用棧別提問表態閘既有流程(作者表態、審查員看得到表態記錄),不新增閘門。

## 條款

- [S1] 當改動行出現引號包住的 3 到 5 位數字字串,且位在相等或不等比較、case、`->` 分支、equals、或 in 元組裡,共用形狀應命中;沒有引號的數字比較與註解裡的同樣寫法應不命中 [test:t_extcode_shapes]
- [S2] 當派工鏡頭渲染一篇列出的筆記,渲染應在合約行之後印出該篇帶 `[來源:外部]` 的 FACT、FLOW、DEP 行,標題固定、每篇最多 10 行、每行截 200 字;其他來源的事實行應不印;沒有外部事實行的筆記應不印標題 [test:t_lens_external_facts]
- [S3] 當 diff 模式的改動行命中共用形狀,鏡頭應從 impact 結果的自由席裡補選 base 版含外部事實行的筆記,種類標「外部碼表」、最多 3 篇、不與既有清單重複;時間不夠時應停止補選並印一行說明;沒命中形狀時列出清單應與改動前相同 [test:t_lens_extcode_pick]
- [S4] 鏡頭補選與八題觸發應引用同一組形狀常數,八題的題目文字應是同一個常數 [test:t_extcode_single_source]
- [S5] 題目表除 sql 外的八個棧應各多一題 `<棧>-extcode`,id 集合應釘住;命中樣本應觸發該題、不命中樣本應不觸發 [test:t_stack_question_triggers]

## 實務隱患

- 併發:已排除:鏡頭與題目判斷都是唯讀計算,不寫共用狀態;快取鍵不變(輸出內容依 base 與 head 決定)。
- 效能:補選要多讀幾篇筆記的 base 版全文,最多讀自由席裡的 8 篇、補 3 篇;只在命中形狀時才讀。每篇沿用既有讀檔函式的 20 秒逾時,並受內層 45 秒總帳的剩餘時間約束,時間到就停。
- 資源:已排除:不新增連線、檔案控制代碼或鎖,沿用既有讀檔函式。
- 守衛面:第三項加題會讓更多改動要作者表態,誤觸發會增加摩擦;形狀刻意排除無引號數字與測試檔,用測試釘住不命中樣本。這一類碰到,所以本案走完整設計審。
- 已排除:金流:本案改的是審查工具,不碰任何付款或交易的執行路徑
- 已排除:對外送出:不呼叫外部服務、不送任何東西出去
- 已排除:不可逆:不刪不改任何資料,全部是加印與加題,還原提交即回原狀

## 回退

- 退回方式:還原本案的功能提交即可。三項都是加法:拿掉後鏡頭只印合約行、不補選,題目表少八題。
- 既有表態記錄裡的 extcode 表態會變成對不到題目的舊紀錄:推送前核對只看題目表裡適用的題,舊表態被略過、不擋;鏡頭照印表態記錄。但「重新寫入表態檔」時,寫入檢查會把對不到題目表的 id 擋下,所以回退後若有分支要重寫表態,要先刪掉那幾筆 extcode 表態。
- 不需要資料遷移,也沒有外部狀態要收拾。
