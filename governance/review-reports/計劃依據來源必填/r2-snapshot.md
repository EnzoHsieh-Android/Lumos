# 計劃依據來源必填_計劃

> 白話:計劃筆記裡每個機制(判法、門檻、範本、設定值)都要寫明「憑什麼這樣定」——官方文件、同類工具的做法、本機實測、使用者原話——集中寫在〈依據來源〉一節,一個機制一行。規格閘對新計劃擋:沒有這一節、或有一行講不出出處,不准進實作;推送前再對這次改到的新計劃查一次,免得實作或審查途中才冒出來的機制沒補;舊計劃只在健檢提醒。Android 寫法型錄同一個道理:每一列的標準寫法要有逐列查證過的權威出處,型錄自檢數出還沒查證的列,查完之前只提醒、補齊之後改成擋。使用者原話(2026-11-06):「我們開發的過程中，所有機制的依據來源，最後也要補回plan，方便後續迭代」「而且我要變成規則，機制來源必填」「Android的規則也一樣，來源、依據，這可以在語意盲判的時候起到輔助判別的作用」。

PRIOR-ART: ①Rust RFC 範本有「Rationale and alternatives」與「Prior art」兩個固定節(https://raw.githubusercontent.com/rust-lang/rfcs/master/0000-template.md );範本本身說沒有先例也沒關係、別人做過不構成理由——本案只借它「固定節」的形式,「必填」與「一個機制一行」是本案自己的規則。②Michael Nygard 的架構決策紀錄(ADR)把「Context」列為必填,理由是「專案生命週期裡最難追的就是某個決定背後的動機」(https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions );一份紀錄只記一個決定——本案借這個粒度,定成「一個可以被單獨質疑為什麼的選擇=一列」。③Wikipedia 可查證性政策要求引用要明確支持那段內容(https://en.wikipedia.org/wiki/Wikipedia:Verifiability ),但「支持不支持」靠人判——本案機器只判格子裡有沒有一個可查的出處,支持與否交給審查席。④Google Tricorder 把「使用者不想看到的報告」當誤報、持續量比例並壓在約 10% 以下(ICSE SEIP 2021,https://lup.lub.lu.se/search/files/91080778/ICSE_SEIP_2021_MEAN_final.pdf )——本案擋下就留帳,回頭抽樣判誤報。⑤lumos 既有的規格閘已經對計劃擋「預期值表」,本案沿用「計劃節的格式檢查在規格閘、有一行不合就擋、退出碼 1」「推送前小改動閘再查一次」「生效日分新舊」三個做法,以及找節、切表的現成函式;但預期值表只對風險高且有新行為條款的計劃查,本案的檢查不能掛在它後面(插入點見範圍 1)。
RETIRE-IF: 治理帳裡規格閘因〈依據來源〉擋下的事件連續三個月零筆(大家已經習慣寫,閘沒在擋東西);或抽樣 20 筆擋下事件有一半以上是格式誤判(出處明明在、判法不認)。

## 用詞

- **機制**:計劃裡一個「換個值或換種做法,程式或流程的行為就不一樣」的選擇——判法、門檻與數字、預設值、擋或不擋、插入位置、格式、生效日、刻意不選的做法。粒度:一個可以被單獨質疑「為什麼是這樣」的選擇算一列;同一個理由撐住的幾個選擇可以併成一列,但「機制」欄要把它們都寫出來。機器判不出機制有沒有列全(見〈天花板〉),由設計審與代碼審席位點名缺列。
- **依據來源節**:計劃筆記裡標題剛好是 `## 依據來源` 的一節,內容是一張三欄表,表頭依序是「機制|依據|出處」。找節用規格閘現成的 `_h2_section_lines`(同一個標題出現兩次、表在程式碼圍欄裡,照預期值表那道的既有處理);切表與切格重用預期值表那組(`_expected_table_lines`、`_expected_split_cells`,格內的 `\|` 不算分隔)。表頭欄名或欄數不對、沒有任何資料列,都算這一節不合格。
- **依據欄與出處欄**:「依據」寫一句為什麼這樣定(理由);「出處」寫讀者去哪裡查得到那個理由。出處要支持依據欄那一句——機器不驗支持與否,審查席驗。
- **出處合格**:「出處」欄裡至少含有下列一個(含即可,不必在開頭;同一格多寫別的文字不影響):①網址:`http://` 或 `https://` 後面接至少一個含點的主機名;②repo 內存在的檔案路徑:反引號包住,用 refcheck 現成的 `_refcheck_scan` 判存在(相對 repo 根,解析後要在 repo 根底下,工作目錄裡有的檔就算);③圖譜節點連結 `[[…]]`,用現成的連結正規式抽出、節點要存在;④使用者原話:「使用者 YYYY-MM-DD:」後面接引號且引號內至少 4 個實字(用現成的 `_real_chars` 算);⑤實測:「實測 YYYY-MM-DD:」後面至少 4 個實字(寫指令、卷證路徑或驗證紀錄節點)。④⑤的日期要是真的日期(月份 1–12、日子在那個月裡)。判法寫成一支共用函式,規格閘、推送前重查、健檢三處都呼叫它。
- **跟其他「出處」判法的關係**:預期值表的「來源」格(只要至少 4 個實字,可以指本計劃的段落)、型錄主表的「來源」欄(登記過的縮寫或網址,由 `check.py` 的 `catalog_problems` 管)、筆記摘要行的 `[出處:]` 欄(提交時的筆記形狀檢查管)是三種不同的東西、各自的門檻,本案不合併也不改它們;本節的出處要能讓接手的人自己去查到,所以門檻比預期值表來源格高。
- **新計劃**:「計劃日期」不早於本案生效日的計劃。計劃日期沿用規格閘現成的 `_plan_effective_day`(開頭欄位 `created` 與第一次進 git 歷史的日期取較晚者,改名跟得過去、複製不跟;淺複製只看 `created`);兩個都讀不到時,計劃日期當成今天(在正式環境等於判新;測試總檔把生效日設成 9999-12-31,等於判舊,既有規格閘測試不受影響)。生效日照預期值表那套另立一個常數 `_PLAN_SOURCES_SINCE`(純日期,值取本案實作合併進主線的隔天,跟 `_HIGH_RISK_EVIDENCE_SINCE` 同一個取法),讀法另寫一支 `_plan_sources_since()` 照 `_expected_since`:環境變數 `LUMOS_PLAN_SOURCES_SINCE` 是 YYYY-MM-DD 就用它(測試與緊急覆寫),否則用常數;測試總檔開頭同樣預設成 9999-12-31。不直接共用 `_HIGH_RISK_EVIDENCE_SINCE`:它的值 2026-11-06 早於本案合併,共用會讓這段期間照舊規矩寫的計劃被追溯擋下,測試總開關也會把兩件事綁在一起。
- **舊計劃**:不是新計劃的計劃。
- **計劃(健檢範圍)**:`Projects/` 底下檔名以 `_計劃.md` 結尾、開頭欄位 `type: project`、狀態是 todo 或 doing 的筆記。
- **三處依據紀錄的分工**:紀律範本要求的 `PRIOR-ART:` 一行是整份設計「查世界」的摘要(照留);審查迴圈收貨紀錄(rN-intake.md)裡的〈先查世界〉是每一輪修補前查證的過程紀錄(照留,屬卷證);〈依據來源〉表是這份計劃每個機制「現在」的依據,是唯一的現況表。審查輪折入新增或改動了機制,就在〈依據來源〉補或改那一列,出處可以直接引收貨紀錄〈先查世界〉裡的網址。

## 範圍

1. **規格閘檢查〈依據來源〉**(`lumos spec-gate`):新計劃——沒有 `## 依據來源` 節、表頭或欄數不對、節裡沒有任何資料列、或任何一列的「出處」欄不合格 → 擋(退出碼 1,同 `cmd_spec_gate` 的「擋下 1」)。網址只驗格式不連網。舊計劃 → 印一行提醒,不擋。
   - **插入點**:新開一支 `_spec_gate_sources_part(env, rel, text)`,在 `_spec_gate_front` 裡排在待決問題(`_spec_gate_pending`)之後、條款綁定(`_spec_gate_clause_part`)之前,形狀同 `_spec_gate_pending`:擋回 1、沒事回 None。
   - **為什麼不掛在預期值表後面**:讀程式的結果——`_spec_gate_clause_part` 遇到計劃沒有 `[SN]` 條款、風險又不是低時直接回 0,後面的預期值表檢查(`_spec_gate_expected_part`)根本不會跑;預期值表本身又只在 `_expected_requirement` 判定「風險高、生效日之後、至少一條新行為條款」時才查。掛在後面的話,零條款的新計劃與風險低的新計劃都會漏判。
   - **獨立於前置條件**:這一道不看門的判定(風險高或低)、不看有沒有條款或新行為條款,只看新舊;零條款的新計劃、風險低的新計劃一樣擋。`--no-run` 也照查(插入點在 `--no-run` 提早收之前)。
   - **訊息形狀**:照預期值表那道——擋下印標頭 `[spec-gate] 依據來源: ✗ — N 處不合:`、逐條 `    • 第 N 行:<機制名>:<缺什麼>`(缺節、表頭不對、沒有資料列各一條)、最後一行範例(一列合格的寫法);通過印一行 `[spec-gate] 依據來源: ✓ N 列`;舊計劃印一行 `[spec-gate] 依據來源: 舊計劃不擋——<缺什麼>`。
   - **擋下留帳**:擋下時用推送前規格閘既有的 `_gate_event` 寫一筆治理帳(閘 `spec-gate`、種類 `sources-missing`、節點是那份計劃、額外欄位帶被擋的格子原文前 200 字),給 RETIRE-IF 與 REVISIT 抽樣誤判用。不加它的最小解(只看 `spec-gate-run` 事件)不夠:擋下的那次不會走到寫 `spec-gate-run` 的地方。
2. **推送前重查**:推送前小改動閘(`lumos spec-gate --push-check <範圍>`)對這次範圍碰到的每一份新計劃,用範圍 1 同一支判定函式再查一次〈依據來源〉,不合格就擋推送(跟它對預期值表簽核的既有做法同一個出口、同一種留帳)。這樣實作中或審查輪才冒出來的機制,只要寫進計劃時漏了出處,推送前會被擋;規格閘過了之後整節被刪也擋得到。不加它的最小解(只靠進實作前那一次規格閘)不夠:使用者要的是「最後也要補回 plan」,只查進實作那一刻,事後冒出的機制沒有任何一道會回頭看。
3. **健檢提醒**:`lumos doctor` 對〈用詞〉定義的「計劃(健檢範圍)」裡、判成新計劃、而且〈依據來源〉不合格的,列名字(最多 20 篇,超過印總數);舊計劃不列(規格閘也不擋它們,列了只會永遠清不掉)。只是提醒,不算進健檢的問題數、不改退出碼。
4. **紀律範本加一句**:`scripts/templates/graph-discipline.md`〈設計與排查〉那段,在 `PRIOR-ART:`、`RETIRE-IF:` 那句後面加:「每個機制的依據寫進計劃〈依據來源〉一節(一個機制一行:官方文件、同類工具做法、實測、使用者原話);`PRIOR-ART:` 那行照寫,是整份設計查世界的摘要;新計劃規格閘與推送前會擋」。注入到消費專案的 CLAUDE.md 照既有的重新注入流程。
5. **審查手冊各加一句**:`skills/lumos-design-loop/SKILL.md` 與 `skills/lumos-code-loop/SKILL.md` 的〈修前先查世界〉那段各加一句:「折入新增或改動了機制,同一次在計劃〈依據來源〉補或改那一列,出處可以引收貨紀錄這一節的網址」。
6. **型錄逐列出處計數**:`configs/ast-grep/kotlin-android/check.py` 新開一支 `catalog_unverified(text)`,回傳主表裡「來源」欄沒有逐列查證紀錄(`〔查證 YYYY-MM-DD:…〕`)而且名稱沒標「(出處不全)」的列編號清單;主程式在既有的問題清單之外另印一行數字與前 20 個編號,不進 `catalog_problems` 的回傳、不改退出碼。讀表口徑跟 `catalog_problems` 同一套(主表列用 `_MAIN_ROW_RE` 認、`_cells` 切欄、第 12 欄是來源)。
   - **兩層口徑**:`catalog_problems` 判的是「這列有沒有來源」(登記過的縮寫或網址就算),是既有的底線,照擋、不改;本條數的是「這列有沒有逐列查證過」——[[Systems/kotlin規則包]] 的 WHY 行(使用者 2026-11-05:每列要有真的打開讀過的官方出處,查不到的列標(出處不全))要的是這一層,現在 324 列沒做到,就是那條 WHY 的存量缺口。本條把缺口變成每次自檢都看得到的數字;補齊由後續另開的計劃做(暫名「Android寫法型錄逐列查證_計劃」),補完之前守那條 WHY 的就是這個數字加文末 REVISIT。只有網址、沒有〔查證〕的列也算還沒逐列查證(網址可能只是縮寫展開的首頁)。
   - 分支 `EnzoHsieh-Android/android-lint-ci` 上的「Android現成檢查接上CI與推送前_計劃」(待合併進主線)也改同一支 `check.py`,本案實作前先等它合併再動,免得衝突。
7. **盲判材料附出處**:已由 [[Projects/Android寫法語意情境表態與盲判_計劃]] 實作(`check.py` 的 `dt_sources`:決策表一列的「對應檢查」到主表找來源欄,縮寫照〈來源縮寫〉表展開成網址),本案不再做。逐列查證補完之前,展開出來的多半是工具或文件首頁那一層,不是逐列查證過的那一頁;盲判材料要不要標「這列出處還沒逐列查證」歸那份計劃決定。

**不做**:不連網驗網址活不活(網址會變,連網判斷放在後續另開的型錄逐列查證計劃,暫名見範圍 6);不判「每個機制都有一行」(機制清單程式抽不出來,交給設計審與代碼審席位);不判出處支不支持依據(交給審查席);不回頭改已經結案的計劃;不改 `_plan_first_day` 用提交日期的做法(預期值表也在用,見實務隱患)。

## 實務隱患

- **格式誤判擋人**:出處寫法五種之外的合理寫法(例:論文只寫作者與年份)會被擋;出口是補一個網址(論文多半有 https://doi.org/ 或 arxiv 網址)。擋下會留帳,RETIRE-IF 抽樣看誤判比例。
- **過度放行**:隨便貼一個格式對的網址、寫一個存在但無關的檔案路徑,機器都會放行;這一層靠審查席(〈天花板〉1)。
- **舊計劃界線**:用 `_plan_effective_day` 判新舊(`created` 與第一次進 git 的日期取較晚者)。拿舊計劃複製一份改寫成新計劃:新檔第一次進 git 的日期在生效日之後,判新,要寫依據(合理);整檔搬目錄或改名:改名跟得過去,維持舊;計劃被 regen 改了 `created`:判新,regen 的計劃本來就要重寫依據,合理;淺複製(CI)讀不到 git 歷史,只看 `created`,複製舊計劃又沒改 `created` 會漏判成舊(同預期值表的既有限制)。
- **rebase 與壓提交讓舊計劃變新**:`_plan_first_day` 取的是提交日期。本機實驗(git 2.39.2,見卷證 r1-intake.md 重現表):rebase 保留作者日期、提交日期變成當下;壓成一個提交(soft reset 或 `merge --squash`)兩個日期都變當下。所以照舊規矩寫、還沒合進主線的計劃,在生效日之後被 rebase 或壓提交,就會被判成新計劃、要補〈依據來源〉。代價是補寫這一節,方向跟使用者要的一致,不另加機制;改用作者日期只解 rebase、解不了壓提交,還會連帶改預期值表的判定,不採。
- **跟預期值表的重疊**:預期值表的「來源」欄講的是每條條款預期值的出處,本節講機制的出處,兩者都要;預期值表已有的出處可以在本節引同一個網址。
- 已排除:金流:不碰付款或點數
- 已排除:對外送出:只讀本機檔,網址只驗格式不連網
- 已排除:不可逆:新增檢查、提醒與一種治理帳事件,退提交即回原狀(已寫進治理帳的事件留著,不影響其他判定)
- 守衛面:不排除——規格閘與推送前各多一道會擋的檢查、健檢多一則提醒,動的是守衛面;判風險高,走完整設計審(lumos-design-loop),不寫成已排除
