# 計劃依據來源必填_計劃

> 白話:計劃筆記裡每個機制(判法、門檻、範本、設定值)都要寫明「憑什麼這樣定」——官方文件、同類工具的做法、本機實測、使用者原話——集中寫在〈依據來源〉一節,一個機制一行。規格閘對新計劃擋:沒有這一節、或有一行講不出出處,不准進實作;舊計劃只在健檢提醒。Android 寫法型錄同一個道理:每一列的標準寫法要有逐列查證過的權威出處,型錄自檢數出還沒查證的列,查完之前只提醒、補齊之後改成擋。使用者原話(2026-11-06):「我們開發的過程中，所有機制的依據來源，最後也要補回plan，方便後續迭代」「而且我要變成規則，機制來源必填」「Android的規則也一樣，來源、依據，這可以在語意盲判的時候起到輔助判別的作用」。

PRIOR-ART: ①Rust RFC 範本每份提案必填「Rationale and alternatives」(為什麼這個設計是最好的、考慮過哪些)與「Prior art」(別的語言或社群怎麼做、經驗如何),並提醒「別人有做」本身不構成理由(https://raw.githubusercontent.com/rust-lang/rfcs/master/0000-template.md )。②Michael Nygard 的架構決策紀錄(ADR)把「Context」(當時有哪些力量在作用)列為必填,理由是「專案生命週期裡最難追的就是某個決定背後的動機」,沒有它後來的人只能盲目接受或盲目推翻(https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions )。採用:借 RFC 的「必填節」形式與 ADR「記下當時的力量」的理由,但粒度到「每個機制一行」(lumos 的計劃一份常有十幾個機制,RFC 整份一節太粗)。③lumos 既有的規格閘已經對計劃擋「預期值表」(每條新行為條款要有輸入、預期、來源四欄),本案沿用「計劃節的格式檢查在規格閘、有一行不合就擋、退出碼 1」的做法與「新舊計劃怎麼分」的生效日機制;但預期值表只對風險高且有新行為條款的計劃查,本案的檢查不能掛在它後面(插入點見範圍 1)。
RETIRE-IF: 連續三個月規格閘因〈依據來源〉擋下零次而且代碼審席位也沒再報「依據對不上程式」(表示大家已經習慣寫,閘本身沒在擋東西);或擋下的有一半以上是格式誤判(出處明明在、格式判讀不認)。

## 用詞

- **依據來源節**:計劃筆記裡標題剛好是 `## 依據來源` 的一節,內容是一張表(欄:機制|依據|出處)。
- **出處**:下列之一,寫在「出處」欄:①網址(`http://` 或 `https://` 開頭);②repo 內存在的檔案路徑(反引號包住,refcheck 驗得到);③圖譜節點連結 `[[…]]`(要存在);④使用者原話(寫成「使用者 YYYY-MM-DD:「…」」);⑤實測(寫成「實測 YYYY-MM-DD:」加指令或卷證路徑)。
- **新計劃**:「計劃日期」不早於本案生效日的計劃。計劃日期沿用規格閘現成的 `_plan_effective_day`(開頭欄位 `created` 與第一次進 git 歷史的日期取較晚者,改名跟得過去、複製不跟;淺複製只看 `created`;兩個都讀不到當新計劃)。生效日照預期值表那套寫法另立一個常數 `_PLAN_SOURCES_SINCE`(純日期,值取本案實作合併進主線的隔天,跟 `_HIGH_RISK_EVIDENCE_SINCE` 同一個取法),讀法照 `_expected_since`:環境變數 `LUMOS_PLAN_SOURCES_SINCE` 是 YYYY-MM-DD 就用它(測試與緊急覆寫),否則用常數;測試總檔開頭同樣預設成 9999-12-31,讓既有規格閘測試停在生效前。不直接共用 `_HIGH_RISK_EVIDENCE_SINCE`:它的值 2026-11-06 早於本案合併,共用會讓這段期間照舊規矩寫的計劃被追溯擋下,測試總開關也會把兩件事綁在一起。
- **舊計劃**:不是新計劃的計劃。

## 範圍

1. **規格閘檢查〈依據來源〉**(`lumos spec-gate`):新計劃——沒有 `## 依據來源` 節、節裡沒有任何資料列、或任何一列的「出處」欄五種都不是 → 印哪一列缺什麼並擋(退出碼 1,同 `cmd_spec_gate` 的「擋下 1」)。網址只驗格式不連網;repo 路徑與節點連結驗存在。舊計劃 → 印一行提醒,不擋。
   - **插入點**:新開一支 `_spec_gate_sources_part(env, rel, text)`,在 `_spec_gate_front` 裡排在待決問題(`_spec_gate_pending`)之後、條款綁定(`_spec_gate_clause_part`)之前,形狀同 `_spec_gate_pending`:擋回 1、沒事回 None。
   - **為什麼不掛在預期值表後面**:讀程式的結果——`_spec_gate_clause_part` 遇到計劃沒有 `[SN]` 條款、風險又不是低時直接回 0,後面的預期值表檢查(`_spec_gate_expected_part`)根本不會跑;預期值表本身又只在 `_expected_requirement` 判定「風險高、生效日之後、至少一條新行為條款」時才查。掛在後面的話,零條款的新計劃與風險低的新計劃都會漏判。
   - **獨立於前置條件**:這一道不看門的判定(風險高或低)、不看有沒有條款或新行為條款,只看新舊;零條款的新計劃、風險低的新計劃一樣擋。`--no-run` 也照查(插入點在 `--no-run` 提早收之前)。
2. **健檢提醒**:`lumos doctor` 數出狀態是 todo 或 doing、沒有〈依據來源〉節或節裡有缺出處列的計劃,列名字(最多 20 篇)。
3. **紀律範本加一句**:`scripts/templates/graph-discipline.md`〈設計與排查〉那段,在 `PRIOR-ART:`、`RETIRE-IF:` 那句後面加:「每個機制的依據寫進計劃〈依據來源〉一節(一個機制一行:官方文件、同類工具做法、實測、使用者原話),新計劃規格閘會擋」。注入到消費專案的 CLAUDE.md 照既有的重新注入流程。
4. **型錄逐列出處**:`configs/ast-grep/kotlin-android/check.py` 的型錄自檢數出主表裡「來源」欄沒有逐列查證紀錄(沒有網址、也沒有 `〔查證 YYYY-MM-DD:…〕`)而且名稱沒標「(出處不全)」的列,印成一行數字與前 20 個編號;不擋。口徑跟 `catalog_problems` 同一套讀表(主表列用 `_MAIN_ROW_RE` 認、`_cells` 切欄、第 12 欄是來源)。逐列查證本身後續另開一份計劃做(暫名「Android寫法型錄逐列查證_計劃」,開了沒由文末 REVISIT 回頭看);那份補完後,把這一條改成擋(回頭條件見文末 REVISIT)。分支 `EnzoHsieh-Android/android-lint-ci` 上的「Android現成檢查接上CI與推送前_計劃」(待合併進主線)也改同一支 `check.py` 的 `catalog_problems`,本案實作前先等它合併再動,免得衝突。
5. **盲判材料附出處**:[[Projects/Android寫法語意情境表態與盲判_計劃]] 的盲判材料(範圍 4 的 `--template`)每個候選列多帶那一列在型錄的出處網址(從決策表「對應檢查」欄找到主表列、取「來源」欄的網址),讓盲判代理照權威說法判「適不適用、有沒有照做」;這一條寫進那份計劃的範圍 4,本案只負責提供「從決策表列找出處」的讀表函式。

**不做**:不連網驗網址活不活(網址會變,連網判斷放在後續另開的型錄逐列查證計劃,暫名見範圍 4);不判「每個機制都有一行」(機制清單程式抽不出來,交給代碼審席位與接手席);不回頭改已經結案的計劃。

## 實務隱患

- **格式誤判擋人**:出處寫法五種之外的合理寫法(例:論文 DOI)會被擋;出口是改寫成網址(DOI 有 https://doi.org/ 網址)。RETIRE-IF 看誤判比例。
- **舊計劃界線**:用 `_plan_effective_day` 判新舊(`created` 與第一次進 git 的日期取較晚者)。拿舊計劃複製一份改寫成新計劃:新檔第一次進 git 的日期在生效日之後,判新,要寫依據(合理);整檔搬目錄或改名:改名跟得過去,維持舊;計劃被 regen 改了 `created`:判新,regen 的計劃本來就要重寫依據,合理;淺複製(CI)讀不到 git 歷史,只看 `created`,複製舊計劃又沒改 `created` 會漏判成舊(同預期值表的既有限制)。
- **跟預期值表的重疊**:預期值表的「來源」欄講的是每條條款預期值的出處,本節講機制的出處,兩者都要;預期值表已有的出處可以在本節引同一個網址。
- 已排除:金流:不碰付款或點數
- 已排除:對外送出:只讀本機檔,網址只驗格式不連網
- 已排除:不可逆:新增檢查與提醒,退提交即回原狀
- 守衛面:不排除——規格閘多一道會擋的檢查、健檢多一則提醒,動的是守衛面;判風險高,走完整設計審(lumos-design-loop),不寫成已排除

## 驗收條款

- [S1] 當新計劃沒有 `## 依據來源` 節時,`lumos spec-gate` 應 擋並印「缺〈依據來源〉」;零條款的新計劃、風險低的新計劃缺這一節 應 一樣擋;`--no-run` 時 應 一樣擋;`created` 早於生效日但第一次進 git 晚於生效日(複製舊計劃)缺這一節 應 擋;有節但沒有資料列 應 擋;有一列的出處欄是「一般知識」 應 擋並印那一列的機制名;出處是 https 網址、存在的 repo 路徑、存在的節點連結、「使用者 2026-11-06:「…」」、「實測 2026-11-06:…」 應 各自放行;repo 路徑不存在 應 擋;舊計劃缺這一節 應 只印提醒不擋 [test:t_spec_gate_sources_section]
- [S2] 當有 todo 或 doing 的計劃缺〈依據來源〉時,`lumos doctor` 應 列出它;有節但有一列出處欄五種都不是 應 列出它;節裡每列都合格 應 不列;done 的計劃 應 不列;超過 20 篇 應 只列 20 篇加總數 [test:t_doctor_plan_sources_missing]
- [S3] 當型錄主表有一列來源欄只有縮寫、沒有網址也沒有查證紀錄、名稱沒標出處不全時,型錄自檢 應 把它算進「還沒逐列查證」並印數字與編號;補上 `〔查證 2026-11-06:https://…〕` 後 應 不算;退出碼 應 不因這個數字改變 [test:t_kt_catalog_unverified_rows]
- [S4] 當讀表函式拿決策表一列(例 D-1,對應檢查 API-1、API-3、API-14)時,應 回傳那幾列主表列來源欄的網址清單;對應檢查欄沒有主表編號 應 回空清單 [test:t_kt_decision_row_sources]
- [S5] 當紀律範本重新注入到一個消費專案時,CLAUDE.md 應 含「每個機制的依據寫進計劃〈依據來源〉一節」 [test:t_graph_discipline_sources_line]
