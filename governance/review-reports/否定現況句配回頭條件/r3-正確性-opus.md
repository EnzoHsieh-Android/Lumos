## F1 「另有 N 行沒列」承諾下次提交會再列，實際上那幾行永遠不會再出現
severity: major
blocking: 是
引句:「另有 N 行沒列(改完這些再提交會再列)」
file: `scripts/lumos:24924`
1. 提醒不擋，所以這次提交照樣成功，第 4 行以後沒印出來的那些否定句會跟著進 HEAD。
2. 下一次提交(包括 `--amend`)，`_notelines_new` 在 `--staged` 下只看 `git diff --cached` 對 HEAD 新增的行。這些行已經在 HEAD 裡，不算新行，所以不會再列。這句「改完再提交會再列」是從「會擋的閘」借來的語意：擋下的時候行還沒進 HEAD,下次才會再列；只提醒時這個前提不成立。
3. 〈範圍〉不做②已經講明，推送前、CI(`--diff`)和 doctor 事後掃描都不算、也不印提醒，所以這些行沒有任何出口看得到，帳上也只記成 `shown=false`,門檻 1、3 都不算它們。
4. 規模：在工具鏈 300 個提交上重放，有 11 個提交超過 3 行，共 26 行被藏；rtb 593 裡有 17 個提交、33 行被藏(spec 表上的數字)。照字面實作，這句字樣會騙人，這些行也就永遠沒人看到。
5. 改法有兩條，擇一：字樣改成真話，例如「另有 N 行沒列，這次提交之後不會再提醒」，並附一條事後列出全部的方法；或者超過 3 行時，其餘各行只印「路徑:行號」不印片段，體積照樣有上限。S5 的逐字條款要跟著改。

## F2 照做追蹤的③把任何改動都算成照做，沒有提醒時的自然基準就已高過撤除門檻
severity: major
blocking: 是
引句:「③**刪掉或改寫**——出現過、14 天內消失,那次沒新增 REVISIT 行」
file: `governance/eval/negation-revisit/neg_revisit_measure.py:415`
1. 〈做法〉7 的②③只看行雜湊有沒有消失，不看新版本裡否定句還在不在。長段落常常被順手改：句尾補一句、改一個字，行雜湊就變了。照字面，這種情況會記成「③刪掉或改寫」，算進照做率。
2. 實測對照組：這個功能還沒有，所以沒有任何提醒。用第三版規則在工具鏈 1200 個提交上重放，得到 337 行會提醒的行；扣掉離頂端不到 14 天的 81 行，剩 256 行可以追。照〈做法〉7 的定義機械分類，結果是②7 行、③40 行、④照留 209 行。也就是說，完全沒有提醒時，「照做率」(不算①)就有 47/256 = 18.4%。
3. 這 47 行裡有 21 行，消失那一版裡還有一行跟原行相似度 ≥ 0.6、而且照樣被第三版判成會提醒。這 21 行是改了別的地方，否定句原封不動。
4. 後果：RETIRE-IF ① 的「照做率不到一成」在提醒毫無作用時也不會成立，因為自然基準約 18%,再加上①當場改掉(見 F4)只會更高。這條撤除條件實際上是空的。升級門檻 3 的 50% 也是拿「提醒後」跟 0 比，沒有跟自然基準比。
5. 改法：②③都要多判一件事：消失那一版裡，同一篇有沒有相似行照樣命中 `_ns_negation_hits`。命中的算「照留」。`followup` 也要能對上線前的歷史重放，拿到同口徑的自然基準，門檻寫成「比基準高幾成」，不要用絕對值。

## F4 綁錯事件的母體只取②，照提醒「當場改、壓成一個再推」的回頭條件行全部抽不到
severity: major
blocking: 是
