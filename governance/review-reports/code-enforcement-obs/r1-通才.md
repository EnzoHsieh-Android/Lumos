## F2 — BLOCKER, blocking: 是 — 寫入端與讀取端的時間戳格式在 Python 3.9/3.10 上兜不起來,造成假 stale

`_hookevent.py` 寫入時間戳:

file: `scripts/hooks/claude/_hookevent.py:62`
引句:「"ts": time.strftime("%Y-%m-%dT%H:%M:%S%z"),」
`_hook_recent_ok` 讀取時解析:

file: `scripts/lumos:11785`(對應片段)
引句:「ts = _dt.datetime.fromisoformat(str(e.get("ts", "")))」
`time.strftime("%z")` 產出的偏移量**沒有冒號**(例如 `+0800`)。`datetime.fromisoformat` 在 **Python 3.11 之前**只接受 `datetime.isoformat()` 自己能吐出來的格式(帶冒號的 `+08:00`),不接受無冒號格式——這是 CPython 官方文件寫明的行為變更點,不是我猜的。

我在這台機器上直接兩個 Python 版本對照實測:

```
$ /opt/homebrew/bin/python3 --version   # 3.14.6(這台機器 PATH 上排前面的 python3)
written: '2026-09-08T11:13:56+0800'
parsed ok: 2026-09-08 11:13:56+08:00

$ /usr/bin/python3 --version            # 3.9.6(這台機器的系統 python3,也是本專案宣告的最低支援版本)
written: '2026-09-08T11:14:18+0800'
parse FAILED: ValueError Invalid isoformat string: '2026-09-08T11:14:18+0800'
```

再串成端到端:用 `/usr/bin/python3` 跑真正的 `_hookevent.record()` 寫一筆 `ok`,再用同一支 Python 跑 `_hook_recent_ok` 去讀它,結果:

```
verdict: stale | note: 近 7 天沒有成功跑完的紀錄(可能只是沒被觸發)
```

——**明明兩秒前才成功記了一筆,卻被判定「沒跑過」**。這是假紅方向(把活著的判成沒活著),不是假綠,所以不會讓警報「消失成綠」,但會讓這支好不容易做出來的「活著沒」儀表板,在任何用 Python 3.9/3.10 執行 hook 的機器上永久顯示 stale,直接打臉這批的核心賣點。任務問「不同 python 版本呢」——3.11+ 沒事,3.9/3.10 全壞,而 3.9 剛好是這個 repo 自己宣告的下限,3.10 是 Ubuntu 22.04 LTS 內建版本,不是冷門情境。

測試 `t_hook_liveness_is_not_just_recently_ran`(patch 1236 行起)完全測不到這個洞,因為它自己造事件時用的是 `datetime.now().astimezone().isoformat()`(帶冒號),從沒有真的呼叫 `_hookevent.record()` 那個寫入器——消費端測試用了跟生產端不同的資料產生方式,兩邊格式從沒被放在一起驗過。

## 其餘任務項目——查過,沒找到問題

- **item 3(guard() 效能與行為保真)**:實測 `git rev-parse --show-toplevel` 開銷約 13-15ms/次,相對 `Systems/hook逾時預算` 記載的 10-40 秒天花板可忽略不計。逐一比對 patch 前後五支 hook 的 `if __name__ == "__main__":` 區塊:三支(check-graph-sync、dispatch-lens、impact-hook)原本例外直接往上丟,改後 `guard(..., swallow 預設 False)` 仍原樣丟出;兩支(ci-status、lumos-entry)原本 `try/except Exception: sys.exit(0)`,改後 `guard(..., swallow=True)` 內部已吞例外回 0,外層那圈 try/except 變成備援但沒改變最終行為。fail-open 政策沒被這批動到。
- **item 4(sys.path 汙染)**:每支 hook 在 `~/.claude/settings.json` 裡是各自獨立的 `python3 <script>` 指令(已核對真實 settings.json),彼此是獨立行程,`sys.path.insert(0, 自己所在目錄)` 不會跨行程汙染,也不會碰到 Claude Code 主程式的環境——而且這行本身是多餘的(Python 執行腳本時本來就會把腳本自己的目錄放進 `sys.path[0]`),但多餘不等於有害。真正的問題是 F1(安裝副本缺檔),不是 sys.path 機制本身。
- **item 5(_KNOWN_GATES 吞帳)**:核對目前所有 `_gate_event_or_warn` / `_gate_failopen` 呼叫點傳入的閘名(`anchor`、`code-loop`、`pitfalls`),全部都在 `_KNOWN_GATES`(`scripts/lumos:4126`)裡,目前不會有帳被吞。但漂移守衛 `t_gov_stats_gate_drift` 的掃描邏輯只認 `"gate": "字面值"` 這種 dict 字面語法,對「函式呼叫傳字串參數」這種寫法(`_gate_failopen(repo_root, "code-loop", ...)`)完全掃不到——換句話說,未來如果有人在新呼叫點打錯閘名,不會有任何測試翻紅,只會在推送當下印一行容易被忽略的 stderr 警告。目前無實際受害,列 minor,建議之後補一條掃 `_gate_event_or_warn(`/`_gate_failopen(` 呼叫點字面參數的釘子。
- **item 6(mutant 驗證)**:自己動手做了兩組翻紅釘測試,而非只讀碼推論:①把 `LUMOS_SKIP_CODE_LOOP` 改成「整段直接跳過、連 JSON 都不算」的天真實作,`t_skip_code_loop_never_skips_bound_tests` 立刻抓到 4 條斷言失敗;②把 `guard()` 改成「進入點就記 ok」的天真實作,`t_hook_event_recorded_only_on_success` 立刻抓到 2 條斷言失敗。兩支測試都是真的在守它們聲稱要守的東西,不是空氣斷言。
