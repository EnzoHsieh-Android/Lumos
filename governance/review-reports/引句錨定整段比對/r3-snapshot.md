# 引句錨定整段比對_計劃

> 白話:審查席每條發現要附一段原文引句,工具檢查那段字真的在被審材料裡——這是收貨時唯一擋「編造證據」的一道。現在的抽取只取到第一個閉引號,後面寫什麼都不看:前半照抄、後半接一個閉引號再編,照樣判「全數錨定」(Issue 2026-09-06 實測)。這篇改成照括號配對切出整段引句,整段都要對得上;引號沒閉合、或引句結束後到下一條引句之前還有落單的收尾引號,判格式不合。哪一版判準由記帳當下蓋在帳上的章決定,處置閘與回放照章重算;分兩階段上線,先讓所有讀帳的地方認得章,再讓寫側開始蓋新判準的章。來源是世界解總覽〈跨類優先順序〉第 6 名(總覽寫「行區間+整段」,本篇只做整段,理由見〈量測〉),也是立案清單第 18 項。

PRIOR-ART: 括號配對(深度計數)是解析巢狀分隔符的標準做法,不另發明判準。「判準版本蓋在資料列上、讀的時候照那一列的版本選判準」在本 repo 是新機制:既有的版本欄位(回放凍結閉包的 `engine_rev`)語意是「版本對不上就視為過期、跳過重算」,不是在兩套活著的判準之間分派;本篇不沿用它,理由見〈判準版本蓋在帳上〉最後一點。外部對照是資料庫的「先擴後縮」遷移(expand/contract:先上線認得新格式的讀者,再上線寫新格式的寫者)與序列化格式的 schema version 欄位。兩個時間切換先例(`_SEV_WRITESIDE_CUTOFF` 純日期字串比對、`_SECURITY_SEAT_SINCE` 帶時區走 `_loop_ts_key`)不採用:它們留下「合入當天舊碼寫帳」與時區兩個坑,蓋章做法兩個坑都沒有。設定區塊沿用 `.lumos/config.json` 的 `bound_tests` 讀法(`_bound_tests_parallel`:寫錯出聲、退回預設)。

- 只改「從報告抽出引句並判格式」這一步;比對前的正規化 `_quote_norm`、10 字下限、比對方式(子字串、空白全剝再比一次)都不變。

- 不改席位交回報告的形狀(仍是文字);結構化引句另案。

## 做法

### 抽取規則(新判準 `full-span-v1`)

「標籤」在本節一律指:「引句」加可選的全形括號註記、可選的粗體星號、全形或半形冒號、任意空白(含換行),後面緊接開引號 `「` 或 `『`——與現行標籤規則相同。後面不是開引號的「引句:」不是標籤,照舊不理,也不當任何邊界。

依序做:
1. 找出所有標籤的位置。
2. 從某個標籤的開引號起,同型引號遇開加一、遇閉減一,往後一路掃到深度回到零為止;另一型引號不計深度;可以跨行。回到零的那段就是整段引句,範圍內出現的其他標籤一律當成引句內容(不另成一條結果)——席位逐字引用含「引句:「」的範本或計劃時,外層整段比對,不截斷、不多出幽靈條目。
3. 掃到報告結尾還沒回到零:這條判格式不合,`kind="unclosed"`;從它之後的下一個標籤繼續抽,後面的引句不受影響。
4. 引句結束後到下一個標籤的開頭(或報告結尾)為止的文字,兩型引號各自計深度,遇到深度為零時的收尾引號(`」` 或 `』`)=落單,這條判格式不合,`kind="stray"`。前綴照抄後接閉引號再編造、換行後再補收尾引號、用另一型收尾引號,三種都會中;尾段裡出現的「引句:」字樣只要後面不是開引號就不是標籤、不截斷這段掃描。
5. 照舊:正規化後整段要是凍結快照正規化後的子字串;正規化後未滿 10 字判錨不到。
6. 結果每條帶 `ok`;格式不合的另帶 `malformed: True` 與 `kind`(沿用現行 `malformed` 鍵,`seat-check` 照舊跳過這種列);`quote` 欄最多存 200 字,超過截斷並加「…(截斷)」。一個標籤一條結果,範圍落在別條引句裡面的標籤不算。

工具保證的範圍(寫進範本與 Issue,不宣稱更多):引號「裡面」那段是真的。引句結束後、沒有落單收尾引號的文字(例如引句後接註記或散文)不算引句內容,工具不驗也不擋——這跟正當的「引句後接註記」在文字上分不開,只能靠讀的人看清楚引號在哪裡結束。

### 判準版本蓋在帳上

- 設定:`.lumos/config.json` 新增 `quote_check` 區塊,兩個鍵:
  - `write_rule`:寫側用哪一版判準,也是蓋在帳上的章;沒寫時用程式預設(第一階段 `legacy`,第二階段 `full-span-v1`)。
  - `read_override`:讀側隔離閥,只認 `"legacy"`;設了之後處置閘與回放對所有帳一律用 `legacy` 重算並印一行警告(給「新判準實作本身有缺陷」時止血用)。
  - 讀法照 `_bound_tests_parallel`:區塊不是物件、值不在認得的集合,印一句提醒並當沒寫。
- 寫側(`cmd_canary` 驗載體引句那段)用 `write_rule` 檢查;檢查通過、寫入的那一列帶 `quote_rule=<write_rule>`,章跟帳在同一行一次寫入。
- 讀章的規則(處置閘、回放、所有拿帳列判引句的地方共用一支小函式):
  - 該列沒有 `quote_rule` 這個鍵 → `legacy`(舊版程式寫的,當年寫側就是舊判準)。
  - 有這個鍵,值是字串且完全等於 `legacy` 或 `full-span-v1` → 用那一版。
  - 有這個鍵但值不是字串、是空字串、或不在集合內 → 判失敗,不 traceback。訊息分兩種:值是非空字串但不認得 → 「這筆帳用了本版不認得的引句判準 <值>,可能是新版程式寫的,請用新版問閘」;其他 → 「這筆帳的引句判準欄格式不合(<值的型別>),帳可能被手改」。
- 處置閘拿哪一列讀章:沿用現行取法——有載體取載體那一列,零發現輪不驗引句。處置閘輸出在引句那一步印「引句判準:<版本>(帳上章|帳上無章|讀側隔離閥)」。
- 第一階段合入日存成常數 `_QUOTE_RULE_STAMP_SINCE`(帶時區完整時間,比較走 `_loop_ts_key`):帳列沒有章但 `ts` 不早於它 → 處置閘多印一行警告「這筆帳沒有引句判準章,卻記在蓋章上線之後,可能是舊版程式寫的或章被刪」,只警告不擋(章本身才是判準來源;這行只讓漏網帳看得見)。
- 手動 `lumos quote-check <報告> --spec <快照>`:預設用 `write_rule`,可加 `--rule legacy|full-span-v1`;人讀輸出第一行印「引句判準:<版本>」,`--json` 輸出在物件裡多一個 `rule` 欄(不多印行,既有 `json.loads(stdout)` 的測試不受影響)。處置閘判失敗時印的診斷指令帶上該列的 `--rule <章>`。
- `seat-check` 用 `write_rule`(它只拿抽出的引句文字比材料範圍,格式不合的列照舊跳過)。
- 回放:凍結閉包裡的帳是整行原樣(含 `quote_rule`),重算照章判;已凍結的 305 個迴圈都沒有這一欄,照 `legacy` 重算,跟凍結當時相同。不推進 `_REPLAY_ENGINE_REV`——推了會讓全部黃金抽查變成「制度已演進、跳過重算」,丟掉回放保護;判準跟著帳上的章走,不需要用引擎版本區分。這推翻 Issue 寫的「改判準必須同時推進回放版本」前提(那個前提假設判準跟著程式走):用 `lumos decision-add` 在本計劃記一條決策(決定:不推進;不選:推進版本、用時間切換;因:章在帳上,回放決定性由章保證;代價:舊版程式讀到新章會誤判,用兩階段上線壓到最小),Issue 結案時在正文補一節說明前提失效並連到這條決策。

### 兩階段上線(先擴後縮)

- 第一階段:合入全部程式(兩版判準、讀章規則、設定區塊、比較指令、擋下事件),程式預設 `write_rule=legacy`——寫側照舊用舊判準檢查,新帳蓋 `legacy` 章。這階段行為上等於沒改,只是所有讀帳的地方都認得章了。
- 第二階段:另一個提交把程式預設改成 `full-span-v1`(本 repo 不必寫設定)。條件:第一階段已在主線、並已用 `lumos quote-check --compare-rules` 重算〈量測〉一次。舊版程式(別的工作樹還沒同步主線)讀到 `full-span-v1` 章時不認得,會照舊判準重算——巢狀那類可能誤判紅;兩階段把這個窗口壓到「第一階段到第二階段之間沒同步的工作樹」。

### 量測與留痕

- `lumos quote-check --compare-rules [--since N] [--carriers] [--json]`:比較模式。這時位置參數(報告)與 `--spec` 改成不必填,跟 `--compare-rules` 互斥;帶了 `--rule` 也拒絕。帳本照 `canary` 指令同一套方式找(專案根的 `docs/.canary-log.jsonl`)。
  - `--since N`:近 N 天(整數,跟 `gov --since` 同義),用 `_loop_ts_key` 比;`ts` 解析不動的列算進「略過」。不給就掃全帳。
  - `--carriers`:只算帶處置清單的載體列(真正會被寫側擋的那些)。
  - 讀不到檔、不是 UTF-8、帳本壞行都略過並各自計數;同一份快照只正規化一次(快取),不把全部文字留在記憶體。
  - 輸出:兩版都錨定、兩版都不過、舊過新不過、舊不過新過、零引句、略過(讀不到 a、非 UTF-8 b、壞行 c、時間解析不動 d)各幾組,以及舊過新不過的逐條清單(報告路徑、kind)。唯讀、不進任何閘。
- 寫側擋下載體時(不論哪一版判準擋的),用 `_gate_event_or_warn(..., "canary", "blocked", note, hard=True)` 記一筆,note 形狀照同檔既有擋下事件:`quote-rule:<write_rule> kind=<new-only|both|legacy-only> cats=<unclosed,stray,miss,short 的集合> loop=<編號> auditor=<席> id=<隨機碼>`;`kind` 由寫側同時用另一版判準算一次得出。`lumos gov --stats` 的「記帳被寫側擋下」分類多一格「引句判準」,以 note 開頭 `quote-rule:` 計數,不再落進「缺 refuted-set」。

## 驗收條款

## 回退

三種情況各走一條路:
- 新判準太嚴(誤傷多):`.lumos/config.json` 設 `quote_check.write_rule: "legacy"`。之後新記的帳蓋 `legacy`、寫側用舊判準;已蓋 `full-span-v1` 的帳照章用新判準重算,判定不變,回放不漂移。手動 `quote-check` 預設也跟著變,要看某輪當時的判準就用處置閘印的 `--rule <章>`。設定檔不在簿記清單,改它要照常走推送閘。
- 新判準實作本身有缺陷(丟例外、誤放):設 `quote_check.read_override: "legacy"`,處置閘與回放對所有帳一律走舊判準(印警告),同時把 `write_rule` 設 `legacy`;修好新判準分支後拿掉 `read_override`。隔離閥開著期間,已凍結且章是 `full-span-v1` 的迴圈若新舊判準結果不同,週跑回放會報漂移——那是預期的,關掉隔離閥後回到一致。
- 完整還原提交(不建議):舊版程式不認得章,會把蓋 `full-span-v1` 的帳用舊判準重算;巢狀被舊判準截在內層那類在處置閘轉紅,已凍結的在週跑回放報邏輯漂移。帳只進不出,轉紅的輪次只能換迴圈編號整輪重記;對漂移的迴圈 `--freeze --note` 重凍會把舊判準的紅燈凍成標準答案,之後再升級回新版又要重凍一次。還原時圖譜也要跟著處理:本計劃、`Systems/design-loop`、`Systems/loop-convergence-recording` 講判準蓋章的句子標 `[status:superseded]`,Issue 重開。
- 不可逆的部分:帳上的 `quote_rule` 欄與擋下事件留在帳本(只進不出);讀帳的地方(本檔約 30 處與 `governance/autonomous_loop/` 的讀帳腳本)都是逐欄 `.get`,多一欄不受影響。
