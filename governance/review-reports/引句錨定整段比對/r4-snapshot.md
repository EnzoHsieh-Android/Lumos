# 引句錨定整段比對_計劃

> 白話:審查席每條發現要附一段原文引句,工具檢查那段字真的在被審材料裡——這是收貨時唯一擋「編造證據」的一道。現在的抽取只取到第一個閉引號,後面寫什麼都不看:前半照抄、後半接一個閉引號再編,照樣判「全數錨定」(Issue 2026-09-06 實測)。這篇改成照括號配對切出整段引句,整段都要對得上;引號沒閉合、或引句結束後到下一條引句之前還有落單的收尾引號,判格式不合。哪一版判準由記帳當下蓋在帳上的章決定,處置閘與回放照章重算;分兩階段上線,先讓所有讀帳的地方認得章,再讓寫側開始蓋新判準的章。來源是世界解總覽〈跨類優先順序〉第 6 名(總覽寫「行區間+整段」,本篇只做整段,理由見〈量測〉),也是立案清單第 18 項。

PRIOR-ART: 括號配對(深度計數)是解析巢狀分隔符的標準做法,不另發明判準。「判準版本蓋在資料列上、讀的時候照那一列的版本選判準」在本 repo 是新機制:既有的版本欄位(回放凍結閉包的 `engine_rev`)語意是「版本對不上就視為過期、跳過重算」,不是在兩套活著的判準之間分派;本篇不沿用它,理由見〈判準版本蓋在帳上〉最後一點。外部對照是資料庫的「先擴後縮」遷移(expand/contract:先上線認得新格式的讀者,再上線寫新格式的寫者)與序列化格式的 schema version 欄位。兩個時間切換先例(`_SEV_WRITESIDE_CUTOFF` 純日期字串比對、`_SECURITY_SEAT_SINCE` 帶時區走 `_loop_ts_key`)不採用:它們留下「合入當天舊碼寫帳」與時區兩個坑,蓋章做法兩個坑都沒有。設定區塊沿用 `.lumos/config.json` 的 `bound_tests` 讀法(`_bound_tests_parallel`:寫錯出聲、退回預設)。
RETIRE-IF: 第二階段合入後 8 週內,寫側記下的引句擋下事件裡 `kind=new-only`(只有新判準擋、舊判準會放)的那些,人工逐條看後誤傷(原文引句正當卻判不合)多於抓到的真截斷或夾帶,就把 `quote_check.write_rule` 改回 `legacy` 並重新設計;或之後改成結構化引句(席位交回 JSON、引句欄位單獨一格),文字抽取不再需要,這套規則整個拿掉。

## 範圍

- 只改「從報告抽出引句並判格式」這一步;比對前的正規化 `_quote_norm`、10 字下限、比對方式(子字串、空白全剝再比一次)都不變。
- `_quote_rows` 是唯一抽取實作(函式說明寫明單一實作),新舊兩版判準都留在它裡面,用必填的 `rule` 參數選(`"legacy"` 或 `"full-span-v1"`),不給預設值——四個呼叫點(記帳寫側、處置閘、手動 `quote-check`、席位核對 `seat-check`)各自明確傳。`legacy` 分支照現行程式原樣保留,一字不改。
- 不改席位交回報告的形狀(仍是文字);結構化引句另案。

## 做法

### 抽取規則(新判準 `full-span-v1`)

「標籤」在本節一律指:「引句」加可選的全形括號註記、可選的粗體星號、全形或半形冒號、任意空白(含換行),後面緊接開引號 `「` 或 `『`——與現行標籤規則相同。後面不是開引號的「引句:」不是標籤,照舊不理,也不當任何邊界。

依序做(整份報告只掃一次,總成本與報告長度成正比):
1. 預先配對:從頭到尾掃一次,兩型引號各自用一個堆疊,遇開引號推入位置、遇同型閉引號且堆疊不空就配對彈出;堆疊空時的閉引號記為「落單收尾引號」。得到每個開引號對應的閉引號(或沒有)。
2. 找出所有標籤位置。依位置由前往後處理:標籤的開引號有配對 → 開引號到配對閉引號之間是整段引句(可巢狀、可跨行);範圍內的其他標籤當成引句內容,不另成一條結果。沒有配對 → 這條判格式不合,`kind="unclosed"`,接著處理下一個標籤。
3. 一條引句被後面某個落單收尾引號「補閉合」(第一條忘了閉合、後面某處多一個同型閉引號)時,照第 1 步的配對,整段變成一條很長的引句——它幾乎必定錨不到,判 `ok=False`(錨不到),仍擋下;被包進去的標籤不另成一條。
4. 尾段:引句結束後到下一條獨立引句的標籤開頭(或報告結尾)為止,這段文字裡若有第 1 步記下的落單收尾引號(兩型都算),這條判格式不合,`kind="stray"`。落單收尾引號只算給它前面最近的那一條引句,不連累其他條。前綴照抄後接閉引號再編造、換行後再補收尾引號、用另一型收尾引號、中間插一個後面不是開引號的「引句:」字樣,四種都會中。
5. 照舊:正規化後整段要是凍結快照正規化後的子字串;正規化後未滿 10 字判錨不到。
6. 每條結果帶 `ok` 與完整 `quote`;格式不合的另帶 `malformed: True` 與 `kind`(沿用現行 `malformed` 鍵,`seat-check` 照舊跳過這種列),而且只有格式不合的列 `quote` 欄截到 200 字並加「…(截斷)」——錨定與錨不到的列保留全文,`seat-check` 拿全文比材料範圍。

工具保證的範圍(寫進範本與 Issue,不宣稱更多):引號「裡面」那段是真的。引句結束後、沒有落單收尾引號的文字(例如引句後接註記或散文)不算引句內容,工具不驗也不擋——這跟正當的「引句後接註記」在文字上分不開,只能靠讀的人看清楚引號在哪裡結束。

### 判準版本蓋在帳上

- 設定:專案根 `.lumos/config.json` 新增 `quote_check` 區塊,只有一個鍵 `write_rule`:寫側用哪一版判準,也是蓋在帳上的章;沒寫時用程式預設(第一階段 `legacy`,第二階段 `full-span-v1`)。
- 讀設定:新增專用小函式 `_quote_check_config(root)`(與 `_quote_rows` 放同一區),回 `(write_rule, 警告或 None)`:
  - 設定檔不存在、或沒有 `quote_check` 區塊、或區塊裡沒有 `write_rule` → 程式預設,不出聲。
  - 設定檔讀不到或不是合法 JSON、最外層不是物件、`quote_check` 不是物件、`write_rule` 不是字串、或去頭尾空白轉小寫後不是 `legacy`/`full-span-v1` → 當 `legacy`,並在 stderr 印「設定讀不懂,引句判準退回舊判準:<原因>」。理由:會去動這個鍵的人多半是要退回,讀不懂時往舊判準退比往新判準退安全;代價是打錯字會讓新判準暫時失效,警告看得見。比對前先判型別是字串,不拿非字串值做集合查詢。
- 專案根從哪來:處置閘與回放用它們既有的 `root`(`root` 是 None 時用 `_vault_repo_root(env)`);記帳寫側用 `_vault_repo_root(env)`;手動 `quote-check` 與 `seat-check` 新增 `--repo`(預設「.」,同 `severity-check` 的先例)。
- 寫側(`cmd_canary` 驗載體引句那段):開頭讀一次設定存成區域變數,檢查、`kind`、章、事件全用同一個值;用 `write_rule` 檢查,通過時寫入的那一列帶 `quote_rule=<write_rule>`,章跟帳在同一行一次寫入;被擋時不寫帳。
- 讀章(處置閘專用一支小函式,與 `_quote_rows` 同區;回放經由處置閘,不另設呼叫點):
  - 該列有 `quote_rule` 鍵、值是 `legacy` 或 `full-span-v1` → 用那一版,來源標「帳上章」。
  - 沒有這個鍵 → `legacy`,來源標「帳上無章」。
  - 有這個鍵但值不是上面兩個字串之一 → 判失敗、不 traceback;值是非空字串 → 「這筆帳用了本版不認得的引句判準 <值>,可能是新版程式寫的,請用新版問閘」,其他 → 「這筆帳的引句判準欄格式不合(<型別>),帳可能被手改」。
- 處置閘輸出在引句那一步印「引句判準:<版本>(<來源>)」;判失敗時印的診斷指令帶 `--rule <章>`(章值不合的列不印診斷指令)。
- **判準一經蓋章就不改它的判定**:之後要調整新判準的判定結果(放寬、收緊、修誤判),一律新增一個版本值(例如 `full-span-v2`)與對應分支,舊版本分支照原樣留著;只修「丟例外、不改任何判定」的錯不算改判定。這是回放能重現已凍結判定的前提,也是不推進回放引擎版本的代價。
- 手動 `lumos quote-check <報告> --spec <快照> [--repo 根] [--rule legacy|full-span-v1]`:預設用設定的 `write_rule`;人讀輸出第一行印「引句判準:<版本>」;`--json` 物件多一個 `rule` 欄(不多印行)。
- `seat-check` 用設定的 `write_rule`;讀設定放在材料驗證之後(現有注入測試把 `cmd_seat_check` 放進只有少數全域名的環境跑,同步把那個測試的替身改成收 `rule=`)。
- 回放:凍結閉包裡的帳是整行原樣(含 `quote_rule`),重算照章判;已凍結的 305 個迴圈都沒有這一欄,照 `legacy` 重算,跟凍結當時相同。不推進 `_REPLAY_ENGINE_REV`——推了會讓全部黃金抽查變成「制度已演進、跳過重算」,丟掉回放保護。
- 這推翻 Issue 寫的「改判準必須同時推進回放版本」前提(那個前提假設判準跟著程式走)。決策照現行指令記:`lumos decision-add Projects/引句錨定整段比對_計劃 "引句判準換版不推進回放引擎版本,改由帳上的章決定" --decided 2026-10-13 --context "不選:推進 _REPLAY_ENGINE_REV(會讓全部黃金抽查跳過重算)、用時間切換(合入當天與時區兩個坑)" --why "章在帳上,回放決定性由章保證;代價是舊版程式讀到新章會誤判,用兩階段上線壓小,且蓋過章的判準不再改判定"`;Issue 結案時在正文補一節說明前提失效並連到這條決策,`lumos set` 改成 done。

### 兩階段上線(先擴後縮)

- 第一階段(本計劃第一個功能提交):合入全部程式,程式預設 `write_rule=legacy`——寫側照舊用舊判準檢查,新帳蓋 `legacy` 章。這階段行為上等於沒改,只是所有讀帳的地方都認得章了。有一支測試釘「沒有設定時寫側用舊判準、新帳蓋 legacy」。
- 第二階段(另一個提交,照常走代碼審):把程式預設改成 `full-span-v1`、把釘預設值的那支測試改成新值。由接手這個計劃的會談做,時機與條件寫在上面第一條 REVISIT。
- 消費專案:lumos 每台機器裝一次、消費專案共用同一份程式,第二階段合入後所有專案的預設一起變;要個別回退就在那個專案的 `.lumos/config.json` 寫 `write_rule: legacy`。
- 舊版程式(別的工作樹還沒同步主線)讀到 `full-span-v1` 章時不認得,會照舊判準重算——巢狀那類可能誤判紅;兩階段把這個窗口壓到「第一階段到第二階段之間沒同步的工作樹」。

### 量測與留痕

- `lumos quote-check --compare-rules [--since N] [--carriers] [--repo 根] [--json]`:比較模式。這時報告與 `--spec` 不必填;帶了報告、`--spec` 或 `--rule` 就手動檢查擋下(中文「擋下:」訊息、rc2,不用 argparse 互斥群組——同檔既有做法);一般模式缺報告或 `--spec` 也改成手動檢查(原本 `--spec` 是 argparse 必填)。
  - 帳本:`<repo>/docs/.canary-log.jsonl`(同 `severity-check`)。報告與快照路徑相對 `<repo>` 解。
  - `--since N`:近 N 天,只收 1 到 36500 的整數,其餘 rc2;用 `_loop_ts_key` 比,`ts` 缺、不是字串或解析不動的列算進「略過·時間解析不動」。不給就掃全帳。
  - `--carriers`:只算帶處置清單的載體列。
  - 讀不到、不是 UTF-8、帳本壞行(不是合法 JSON,或是 JSON 但不是物件)都略過並各自計數。記憶體:先依快照路徑分組,一組一組處理,同一份快照只讀一次、正規化一次,處理完就丟。
  - 輸出逐字(測試照這些字串比對):`兩版都錨定 N`、`兩版都不過 N`、`舊判過新判不過 N`、`舊判不過新判過 N`、`零引句 N`、`略過 N(讀不到 a、非 UTF-8 b、壞行 c、時間解析不動 d)`,以及舊判過新判不過的逐條清單(報告路徑、kind)。唯讀、不進任何閘。
- 寫側擋下載體時(不論哪一版判準擋的,含零引句),用 `_gate_event_or_warn(..., "canary", "blocked", note, hard=True)` 記一筆,note 形狀照同檔既有擋下事件:`quote-rule:<write_rule> kind=<new-only|both|legacy-only|unknown> cats=<unclosed,stray,miss,short,none 的集合> report=<報告路徑> report_sha=<前 12 碼> loop=<編號> auditor=<席> id=<隨機碼>`。`kind` 由寫側另用另一版判準算一次得出,這一次計算整段包例外保護,出錯就記 `kind=unknown cats=err`,擋下照舊——新判準壞掉時寫側不會因為求 `kind` 而丟例外。
- `lumos gov --stats` 的「記帳被寫側擋下」改成四格互斥,依序判 note 開頭:`quote-rule:` → 引句判準、`report-not-normalized` → 報告沒正規化、`findings-over-reported` → findings 多於 reported、其餘 → 缺 refuted-set;輸出逐字 `記帳被寫側擋下 N 次(報告沒正規化 a / 缺 refuted-set b / findings 多於 reported c / 引句判準 d)`,四格相加等於 N。

## 回退

三種情況各走一條路:
- 新判準太嚴(誤傷多):`.lumos/config.json` 設 `quote_check.write_rule: "legacy"`。之後新記的帳蓋 `legacy`、寫側用舊判準;已蓋 `full-span-v1` 的帳照章用新判準重算,判定不變,回放不漂移。手動 `quote-check` 預設也跟著變,要看某輪當時的判準就用處置閘印的 `--rule <章>`。設定檔不在簿記清單,改它要照常走推送閘。消費專案共用同一份程式,要個別回退就在各自的設定寫這個鍵。回退時把計劃第二條 REVISIT 改成「只數回退前的事件」並記回退日。
- 新判準實作本身有缺陷:先照上一條把寫側切回 `legacy`,止住新章;再走一般修正提交。只修丟例外的錯直接改 `full-span-v1` 分支;要改判定結果就照〈判準一經蓋章就不改它的判定〉開新版本值,舊分支不動。修好前,蓋了 `full-span-v1` 章的帳若讓處置閘丟例外,處置閘判失敗(不放行),等修好再問。
- 完整還原提交(不建議):舊版程式不認得章,會把蓋 `full-span-v1` 的帳用舊判準重算;巢狀被舊判準截在內層那類在處置閘轉紅,已凍結的在週跑回放報邏輯漂移。帳只進不出,轉紅的輪次只能換迴圈編號整輪重記;對漂移的迴圈 `--freeze --note` 重凍會把舊判準的紅燈凍成標準答案,之後再升級回新版又要重凍一次——所以要還原,只在第二階段之前做(那時帳上還沒有 `full-span-v1` 章,還原沒有任何漂移)。還原時圖譜也要跟著處理:本計劃、`Systems/design-loop`、`Systems/loop-convergence-recording` 講判準蓋章的句子標 `[status:superseded]` 並帶 `[被取代:<取代的節點或提交>]`,Issue 重開。
- 不可逆的部分:帳上的 `quote_rule` 欄與擋下事件留在帳本(只進不出);讀帳的地方(本檔約 30 處與 `governance/autonomous_loop/` 的讀帳腳本)都是逐欄 `.get`,多一欄不受影響。
