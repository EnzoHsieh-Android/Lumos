## Finding 2 — `rule-check` 用 `endswith` 判「規則有沒有被觸發」,規則 id 命名一撞就假陽性
`cmd_rule_check` 判定樣本是否翻紅的邏輯是 `(c.get("rule") or "").endswith(rid)`。這代表宣告規則 id 為 `no-bad` 時,任何一筆 claim 的 `rule` 欄位只要以 `no-bad` 結尾(例如某工具吐出 `xyz-no-bad`、`always-no-bad`,甚至另一條完全不相干但剛好同字尾的規則)都會被算成「這條規則被抓到了」。用 `python3` 驗證 `"xyz-no-bad".endswith("no-bad")` 回 `True`。這正是 S4 標榜的「出口閘」——規則寫了不等於它抓得到東西,但只要巧合命中字尾,`rule-check` 就會給假通過,等於這道閘可以被完全不相干的規則掩護過關而不自知。現有測試(`t_rule_check`)只用單一規則 `no-bad` 測試,沒有任何一支測試造出「另一條規則 id 剛好是這條的字尾超集」的情境,不會被攔住。
引句:「if any((c.get("rule") or "").endswith(rid) for c in claims):」

## Finding 3 — 規則 id 掃描正則要求「id 是那一行最後一個 token」,JSON 規則檔(明文支援的格式)幾乎抓不到
`_rules_declared_ids` 明確把 `.json` 列為受支援的規則檔副檔名,但 `_RULE_ID_RE` 是 `^\s*(?:-\s*)?(?:"?id"?)\s*:\s*"?([A-Za-z0-9_.\-]+)"?\s*$`——結尾錨定 `\s*$`,只要 id 值後面同一行還有其他字元(JSON 常見的尾隨逗號、或壓縮成一行的 JSON)就整條匹配失敗。實測:`json.dumps({"id":"no-bad","message":"x"}, indent=2)` 這種最常見的縮排 JSON(id 不是物件最後一個欄位,有尾隨逗號)`_RULE_ID_RE.findall()` 回 `[]`;壓縮成一行的 JSON 同樣回 `[]`。只有 id 剛好是物件最後一個欄位(無尾逗號)才抓得到——這是極脆弱、依賴欄位順序的巧合命中。S4 特別強調「同時掃規則檔宣告的規則 id……索引漏列一條規則,那條就永遠沒樣本也沒人發現」,但對 JSON 規則檔而言這道保險網幾乎形同虛設。現有測試(`t_rule_check`)裡的規則檔全部寫成 `.yml`(`r.yml`/`r2.yml`,id 在自己一行、沒有逗號問題),完全沒測過 `.json` 規則檔,所以這個洞不會被攔住。
引句:「_RULE_ID_RE = re.compile(r'^\s*(?:-\s*)?(?:"?id"?)\s*:\s*"?([A-Za-z0-9_.\-]+)"?\s*$', re.M)」

## 總結
兩項最重的洞都在「出口閘」`rule-check` 本身:`endswith` 字尾比對(F2)與 JSON 規則檔幾乎抓不到 id(F3)合起來意味著這道被稱為「規則有沒有真的抓到東西」的機械把關,在字尾撞名或 JSON 格式下會靜默給假通過或漏掉本該擋的登記缺口——正是它自己宣稱要防的那種「規則寫了但其實是死的」。依賴層則有一組對稱的假陽性/假陰性:F1(vendored 檔案誤判成自己的宣告)會誤報第三方碼,F4(Swift/CocoaPods/Elixir 只收鎖檔漏宣告檔)則讓設計稿點名的「AI 捏造套件版本」情境在三個生態系上完全防不到。F5、F6 是次要的路徑/可用性缺口,不影響主線消費專案。4 條 major 均需在合入前修——建議 rule-check 改用規則庫回傳的 ruleId 精確比對(或至少要求以分隔符邊界比對而非任意字尾)、規則 id 掃描改成真正解析 YAML/JSON 而非行級正則、依賴掃描補上路徑排除清單與缺漏的宣告檔名。
