# 社群規則第二批 r1 架構對齊審查

白話總結先講：這批東西大方向沒歪（走既有的 SARIF 適配管線、指令命名也照家族習慣），但有兩個地方是實打實地「另開一條路」——一條是設定檔的語意被混進了兩種東西，另一條是同一件事現在有兩套並行的實作。落點也有一個節點範圍要不要拆的問題，判不準交編排者。

★這批是先寫程式才補設計審，判準沒有因為已經寫好而放寬。★

## 一、分層與依賴方向

新加的 `cmd_rule_check`／`cmd_rule_gap` 跟既有的 `cmd_lint_check`／`cmd_lint_waive` 一樣，都是 `main()` 直接派工的頂層指令、不吃 `env`（vault-free），內部只呼叫 `_anchor_repo_root`／自己的小 helper，沒有跨層直呼 vault 或 loop 層——這一點跟既有指令一致。

`file: \`scripts/lumos:17241\`` 的 `cmd_rule_check` 與 `file: \`scripts/lumos:27534\`` 的分派寫法，跟 `file: \`scripts/lumos:17110\``（`cmd_lint_check`）、`file: \`scripts/lumos:27529\`` 附近的分派寫法同一個模子刻出來的，這條沒問題。

但 `_lint_new_cmd_targets` 取代 `_lint_stacks_for_diff` 在新閘裡的角色這件事，答案是：**`_lint_stacks_for_diff` 沒有被淘汰，它還有別的消費者**——`file: \`scripts/lumos:20463\`` 的 `cmd_pitfalls`（`--diff` 那條路）仍在用它把「副檔名→lint.json 指令」配對出一串命令清單。於是現在專案裡同時存在兩套「拿 lint.json 的鍵去對改動檔、决定要跑哪些命令」的實作：舊的 `_lint_stacks_for_diff`（`file: \`scripts/lumos:17046\``,只回命令清單、去重用「命令本身」當 key）跟新的 `_lint_new_cmd_targets`（只回 `(命令,檔案清單)` 配對、去重用 `(命令,檔案排序後的 tuple)` 當 key）。兩者的去重邏輯已經不一樣，以後有人只改一邊，兩套會悄悄漂移。

引句:「把「哪條命令該吃哪些檔」配對好。回 [(命令, [現在路徑…]) …]」

這句就是新函式自己承認在做「跟舊函式相近但形狀不同」的事——需要「每條命令對應到自己的檔案清單」這個新能力沒錯，但做法是另開一支平行實作，而不是把 `_lint_stacks_for_diff` 擴充成也能回檔案清單、讓兩個呼叫端共用同一份「副檔名比對」邏輯。

不對齊：新增告警閘內部把「副檔名→指令」的比對邏輯另開一支，跟 `pitfalls --diff` 用的舊比對邏輯並存，兩者去重策略不同、以後容易漂移。
severity: major

## 二、命名與錯誤處理

- 命名家族：`rule-check`／`rule-gap` 跟到既有的 `<域>-<動詞>` 命名（`lint-check`／`lint-waive`／`ci-wait`／`ci-status`），沒有走歪。
- 回傳碼語意：`cmd_rule_check` 是 0=乾淨（含沒有自寫規則）／1=有問題／2=repo 找不到或索引讀不了，跟 `cmd_lint_check`（`file: \`scripts/lumos:17110\``）的 0/1/2 語意一致。`cmd_rule_gap` 恆 0（不擋，只是待辦清單），跟 `test-layers`／`testmap affected` 這類「建議不擋」指令的慣例一致，不是隨便定的。
- dest 命名：`rc_repo`/`rc_json`、`rg_repo`/`rg_json`、`esc_rule` 都照既有 `lc_repo`/`lc_json`、`esc_loop_id`/`esc_stage` 那套「指令縮寫當前綴」在取名，一致。
- 錯誤訊息三段式：`cmd_rule_check`／`cmd_rule_gap` 印出「✗ rule-check: N 條規則沒有會翻紅的樣本」→「在意的原因：…」→「接下來：…（指令獨立一行）」，三段都有，甚至比 `cmd_lint_check` 現有的訊息更完整地照著三段式走。

這一問沒有找到不對齊的地方。

## 三、第二種做法

`.lumos/rules/index.json` 本身不算新問題——專案已經有「一個功能一個獨立設定檔」的先例（`test-layers.json`、`lint-waivers.json`、`lint-watch.json` 都是各自獨立的檔，不擠進 `lint.json`），所以另開一個 `.lumos/rules/index.json` 跟著這個既有慣例走，沒有另開一種「設定檔存放方式」。

真正的問題在 `deps` 這個保留鍵：它被直接塞進 `.lumos/lint.json` 這個既有、且被嚴格驗證的字典裡，跟副檔名鍵（`py`／`kt`／…）混在一起。

引句:「宣告用 lint.json 的保留鍵 deps(不是副檔名),命中條件=這次改動碰到任何一支依賴宣告檔」（設計稿 KEY 行）

引句:「既有的「要不要掃」過濾會把 .json/.txt/.lock 整批擋掉,」（patch 內的程式碼註解，`scripts/lumos:17538` 附近）

這正是專案自己先前明文避開的做法。`_lint_new_config`（處理 `lint_new` 的 gate/budget 等設定）的既有 docstring 就寫著：

引句:「★不放 .lumos/lint.json★:那個檔的每個頂層鍵都被當成「副檔名→命令清單」嚴格驗證,」（`file: \`scripts/lumos:17584\``,patch 的 context 行，非本次新增但同在審查材料內）

再對照圖譜已經記下的同一條規則：`file: \`docs/lumos-toolchain-knowledge/Systems/pitfalls-code-loop.md:126\`` 明寫「設定不可以放 `.lumos/lint.json`——那個檔的每個頂層鍵都被當成『副檔名→命令清單』嚴格驗證」，以及 `file: \`docs/lumos-toolchain-knowledge/Systems/lint-version-watch.md:36\`` 記載 lint-watch 當初就是因為同樣理由才「新宣告檔 .lumos/lint-watch.json(lint.json 指令不透明抽不出工具身分)」，沒有塞進 `lint.json`。三處都指向同一件事：這個專案已經有共識——lint.json 只認「副檔名→命令清單」這一種語意，新語意一律另開檔或走 `config.json` 的專屬區塊。

`deps` 這次是直接違反這條已經寫進 code 註解跟圖譜的先例——`t_lint_deps_layer` 這支新測試（`(root / ".lumos" / "lint.json").write_text(_j.dumps({"deps": [cmd]}), ...)`）也證實了它就是寫進 `lint.json`，而且沒有任何程式碼把 `deps` 從「副檔名」語意裡特別摘出來（`_lintcheck_validate`／`cmd_lint_check` 沒有改動去跳過它），也就是說這個檔案現在同時混著「副檔名鍵」跟「保留字鍵」兩種意思，`lint-check`／`doctor` 之後若把 `deps` 當成一個奇怪的「副檔名」報出來也不會有人意外。

不對齊：把 `deps` 這個非副檔名的保留鍵混進 `.lumos/lint.json`，直接牴觸專案自己在 `_lint_new_config` docstring 與圖譜（pitfalls-code-loop、lint-version-watch）裡已經記下的「這個檔只認副檔名鍵」共識，屬於引入第二種語意/第二種做法。
severity: major

## 四、落點

設計稿的 `lands_in` 只列兩篇：

引句:「lands_in:
  - Systems/pitfalls-lint-adapter」

這批實際包含三塊性質不同的東西：①依賴層（延伸既有 SARIF diff 管線的檔案配對邏輯，跟 `pitfalls-lint-adapter` 現有職責貼得上）；②「散文→規則」產線（`cmd_rule_check`/`_rules_load`/`_rules_declared_ids`，操作的是全新的 `.lumos/rules/` 目錄與 `index.json`，走的不是 diff/SARIF 這條既有管線，是「規則有沒有活著」這個新問題）；③逃逸帳閉環（`--rule` 欄位，改的是 `cmd_loop_escape`，這支函式的家目前不在 `lands_in` 列的任兩篇裡）。這三塊的說明目前全部寫進同一篇 `docs/lumos-toolchain-knowledge/Systems/pitfalls-lint-adapter.md` 的新增段落「## 依賴層與規則產線」（已核對 `git diff` 該檔，新增段落把①②③一起塞進去），`Systems/linter精選目錄` 反而還沒看到這批的實際改動內容（只在 `related` 掛了連結）。

`pitfalls-lint-adapter.md` 原本的 `summary` 定位是「偵測 diff 涉及棧 → 跑 lint 指令 → 解析合併 SARIF → 過濾 → 併進 manifest」這一條管線（`file: \`docs/lumos-toolchain-knowledge/Systems/pitfalls-lint-adapter.md:18\``），跟 diff/SARIF 無關的「規則產線出口閘」（`.lumos/rules/` 有沒有活樣本）被寫進同一篇，跟這個專案 2026-09-11 才裁定的「節點範圍列最優先」精神有摩擦——那次的根因診斷就是同一篇節點被連續塞進不相干的功能說明，導致節點膨脹、失去「這篇管什麼」的邊界（原話「如果節點一開始寫的方式不理想,那整套 Lumos 就失去治理基礎」，見使用者記憶 `node-scope-at-birth-top-priority`）。是否要為「規則產線」另開一篇 Systems 節點、或把它掛回 `pitfalls-code-loop`（逃逸帳的家），這是設計取捨而非單純程式對錯，判不準。

不對齊：三塊性質不同的功能（SARIF 管線延伸／全新規則產線／逃逸帳新欄位）全寫進 `pitfalls-lint-adapter.md` 一篇，`lands_in` 沒有涵蓋實際改到的 `pitfalls-code-loop`（escape 欄位的家），跟 2026-09-11 節點範圍裁定的方向不一致，但是否構成「應拆」需要人裁。
判定:⚠ 判不準,交編排者裁。
