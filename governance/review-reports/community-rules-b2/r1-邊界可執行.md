severity: blocker

# 極端輸入審查——社群規則第二批(依賴層/rule-check/rule-gap)

## F1｜依賴宣告檔判定沒有目錄排除,第三方 vendor 檔會被當成本專案依賴

`_is_dep_manifest`(`file: `scripts/lumos:17551``)只比對 `Path(path).name`,對 `node_modules/left-pad/package.json`、`vendor/somejslib/package.json`、`third_party/x/Cargo.toml`、任何 fixture 目錄裡的同名檔一律回真——目錄前綴完全不影響判定。這條路徑餵給 `_lint_new_verdict`(`file: `scripts/lumos:17860``)的 `dep_pairs`,直接進入既有的「新增告警閘」判定,一旦第三方套件版本變動被依賴掃描器抓到,`kept` 非空、`hard=True`、`mode=="block"` 時就會把整次推送判 `blocked`——擋下一次跟本專案自身依賴宣告完全無關的推送,而且是團隊改不了的第三方檔。這個代碼庫自己在別處(`file: `scripts/lumos:3399-3400`` 的 `CODE_SKIP_DIRS`、`file: `scripts/lumos:14203`` 的 `_STACK_SCAN_SKIP`)已經承認 `node_modules`/`vendor`/`build`/`dist` 這類目錄要整批排除,這條新路徑卻沒有沿用同一慣例。
引句:「認得的檔名涵蓋 npm／Python／Go／Rust／Java／Ruby／PHP／.NET／Dart／Elixir／Swift／CocoaPods」
blocking: 是——它接在既有推送前「新增告警閘」的判定路徑上,third-party 檔案被誤判會直接讓合法推送被擋。
severity: blocker

## F2｜依賴掃描沒有按生態系分流,原本修掉的「跨棧誤餵」在依賴層原樣重演

`_lint_new_cmd_targets`(`file: `scripts/lumos:17557``)裡,程式碼路由是逐副檔名分桶(`by_ext`)後才配命令,但依賴路由把 `dep_files = sorted({a for a, _b in dep_pairs})`(`file: `scripts/lumos:17575``)算成一個不分生態系的聯集,`.lumos/lint.json` 底下 `deps` 鍵配置的每一條命令都拿到「這次改動的全部依賴宣告檔」——同一次改動若同時碰到 `package.json`(npm)與 `requirements.txt`(python),兩邊都會被塞給同一支(甚至是為某個生態系寫的專用)掃描器。這正是設計稿自己剛修掉、還特別寫成條款的問題,只是換了一層發生:S2 說的「Python 的檢查器會收到 Kotlin 檔」變成「pip 專用掃描器會收到 package.json」。工具收到看不懂的格式常見結局是整條命令跑不動(`ok=False`)落進 `env` 類 `undone`(`file: `scripts/lumos:17943-17945``),觸發 `out["autopass"] = True`——後果不是誤擋,而是整條新增告警閘連同這次改動裡的程式碼新告警一起被自動放行(fail-open),比 S2/S3 原本要修的問題更嚴重(原本只是白跑一趟、吐錯告警,現在是讓整道閘失效)。
引句:「每條命令只拿自己那個棧的檔。原本是把全部改動檔都丟給每條命令」
blocking: 否——它不是把不該擋的東西擋下,方向相反:它會讓本來該被擋的新增告警,因為某條依賴命令跑不動而整批自動放行,判準是「fail-open 比 false-block 更難被人發現、危害更大」。
severity: blocker

## F3｜rule-check 拿 endswith 比對規則 id,兩個方向都會誤判

`if any((c.get("rule") or "").endswith(rid) for c in claims):`(`file: `scripts/lumos:17287``)是純字串尾碼比對,沒有分隔符邊界。實測驗證:規則 id 若寫成常見的短名 `eval`,任何不相干的發現只要 ruleId 剛好以 `-eval` 結尾(例如某條完全不同規則的 `avoid-eval`)就會被判成「eval 這條規則被自己的樣本抓到了」——`"avoid-eval".endswith("eval")` 在 Python 裡就是 `True`。反過來,若規則 id 寫成 `no-bad`,而真實工具(例如 semgrep)吐出的是帶額外限定詞的 `python.lang.security.no-bad-other`,`endswith("no-bad")` 卻是 `False`——一條真的存在的規則,只因為 ruleId 命名比對不上尾碼,就會被判「死規則」擋下。這條比對正是 S4 條款要守的核心(「不翻紅就擋」的判準本身),兩個方向都能被構造出來的輸入打穿。
引句:「`lumos rule-check` 跑規則對它自己的樣本,不翻紅就擋」
blocking: 否——rule-check 這次沒有接進 pre-push/CI 等任何推送閘,不會擋下這次改動裡的任何操作;但它是 S4 明文的「產線出口閘」本體,一旦按計畫接線,死規則會因此矇混過關,判準是「目前不擋人,但功能承諾本身不成立」。
severity: blocker

## F4｜規則 id 掃描器用逐行正則,JSON 慣用寫法(非末鍵加逗號)整條抓不到 id

`_RULE_ID_RE`(`file: `scripts/lumos:17215``)要求整行必須是 `id: 值` 且以行尾結束(`\s*$`)。`_rules_declared_ids`(`file: `scripts/lumos:17218``)明文接受 `.json` 規則檔,但實測:`{"id": "no-bad",\n"message": "x"}` 這種「id 不是物件最後一個鍵、後面帶逗號」的一般 JSON pretty-print 寫法,整條规则一個 id 都掃不到(逗號卡在 `$` 前面);同一份資料若把 `id` 換成物件的最後一個鍵才抓得到。壓縮成一行的 minified JSON、以及 YAML flow-style(`rules: [{id: no-bad, ...}]`)同樣掃不到。S4 的安全網就是靠「掃規則檔宣告的 id 對照索引」抓「索引漏列規則」,但如果規則本身用最常見的 JSON 排版寫,掃描器連這條 id 存不存在都不知道,索引漏列自然也查不出來——安全網對它自稱支援的格式失效。
引句:「同時掃規則檔宣告的規則 id——索引漏列一條,那條就永遠沒樣本也沒人發現」
blocking: 否——後果是「該報的沒報」,不會擋下任何操作,判準是「這是漏判(false negative)而非誤擋」。
severity: blocker

## F5｜巢狀 metadata.id 被當成頂層規則 id,產生假的「缺樣本」擋下

同一支 `_RULE_ID_RE` 沒有任何層級/縮排判斷,逐行掃、只要那一行單獨長得像 `id: 值` 就算數。實測:
```yaml
rules:
  - pattern: xxx
    metadata:
      id: cwe-123
```
會被掃成宣告了一條規則 id `cwe-123`(這其實是 metadata 底下的 CWE/工單編號,不是規則本體的 id)。`cmd_rule_check`(`file: `scripts/lumos:17287`` 前段的 `declared` 比對)會因為索引裡沒有 `cwe-123` 這條樣本,誤報「規則檔宣告了它,但索引沒登記樣本」,讓一個沒有問題的規則檔被 rc=1 擋下。
引句:「★為什麼要掃檔不是只信索引★:索引漏列一條規則,那條就永遠沒有樣本、也沒人會發現」
blocking: 是——這會讓完全合法、沒有真正缺樣本的規則檔被 rule-check 判紅,判準是「rc=1 就是 rule-check 設計要擋的動作本身,這裡是誤擋」。
severity: major

## F6｜rule-gap 遇到非字串 rule 欄位會整支崩潰,不是優雅跳過

`cmd_rule_gap`(`file: `scripts/lumos:17308``)對 JSON 解析失敗的行已經有 `try/except` 跳過,但 `rid = (ev.get("rule") or "").strip()`(`file: `scripts/lumos:17328``)沒有型別檢查:實測 `{"rule": 123}` 或 `{"rule": ["a","b"]}` 這種一行合法 JSON、但 `rule` 欄位不是字串的逃逸帳紀錄,會在 `.strip()` 丟出未被捕捉的 `AttributeError`,整支指令當場崩潰、看不到任何待辦清單。逃逸帳是 append-only、可能被手動編輯或由非 CLI 路徑寫入的資料檔,這條資料完整性假設不成立。
引句:「`lumos rule-gap` 把「標了該抓但規則還沒寫」列成待辦(附漏過幾次)」
blocking: 否——rule-gap 不是任何推送閘,崩潰的後果是這支診斷指令自己掛掉,不會擋下使用者的其他操作,判準是「失敗方式是崩潰而非優雅降級,但沒有下游閘依賴它的 rc」。
severity: major

## F7｜rule-gap 讀 index.json 失敗時完全吞掉錯誤,悄悄少算「已覆蓋」規則

`cmd_rule_gap` 裡 `idx, _err = _rules_load(repo_root)`(`file: `scripts/lumos:17335``)拿到的錯誤訊息直接丟棄不用(`_err` 沒有被檢查),對照同一支 `_rules_load` 的錯誤在 `cmd_rule_check` 裡會被印成 `✗ rule-check: ...` 並回傳 rc=2。實測:index.json 若被寫壞(非 JSON、或缺 `rules` 欄位),`rule-gap` 會悄悄把 `idx` 當成 `{}`,只靠掃規則檔本身抓到的 id 當「已覆蓋」清單——索引裡登記過但規則檔用了不同 id 寫法的項目就會從「已覆蓋」漏掉,而使用者完全不會被告知 index.json 讀不了,只會看到待辦清單莫名其妙變長。
引句:「`lumos rule-gap` 把「標了該抓、但規則還沒寫」列成待辦」
blocking: 否——後果是待辦清單失真而非任何操作被擋,判準是「沉默的資料損毀,不是擋人」。
severity: major

## 總結

四條 blocker 集中在兩個新機制的核心判準上:依賴宣告檔判定完全靠檔名、不看目錄,會把團隊管不到的第三方 vendor 依賴檔當成本專案依賴觸發既有推送閘;依賴掃描本身不分生態系,重現了 S2/S3 才剛修掉的「跨棧誤餵」但後果更嚴重(整道閘 fail-open);rule-check 的規則 id 比對用未加邊界的 `endswith`、規則 id 掃描器用逐行正則且對常見 JSON 排版(id 非末鍵加逗號)視而不見,兩者都讓 S4 條款自稱的「產線出口閘」在可預期的真實輸入下失去把關能力。另外三條 major 集中在 rule-check/rule-gap 對「不完全乾淨的資料」處理不一致:巢狀 metadata id 被誤認成頂層規則、非字串 rule 欄位讓 rule-gap 直接崩潰、index.json 讀取失敗被靜默吞掉不像 rule-check 一樣報錯。
