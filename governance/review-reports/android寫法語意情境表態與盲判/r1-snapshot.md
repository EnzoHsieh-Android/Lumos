# Android寫法語意情境表態與盲判_計劃

> 白話:型錄裡有一類寫法是機器看長相判不出來的——「這兩支呼叫互不依賴嗎」「這是事件還是狀態」——要先判情境才知道該用哪種寫法。這份計劃讓這類情境走三步:①改動碰到某個情境的觸發字時,AI 推送前要表態「這段屬於決策表哪一列、照那列的寫法寫在哪一行」;②機器到那一行核對,真的出現那列寫法的特徵才算(防「寫了規範卻完全沒參考」);③另派一個沒看過 AI 答案的盲判代理,只看程式與候選列自己判一次,兩邊對不上就擋,再派第二個盲判仲裁。使用者原話(2026-11-05):「判斷當下是什麼情況、該用什麼的是 AI,但有沒有真的照做是機械執行」「我怕出現寫了但完全沒參考的狀況」「有沒有必要起一個 subagent 來覆檢這個情境的狀態,沒有 context 比較沒有偏誤?」→「好,加進去」。是 [[Projects/Android協程與API寫法機械檢查標準_計劃]] 分批表的第三批。

PRIOR-ART: ①同 repo:棧別提問表態閘([[Systems/棧別提問表態閘]])已有「觸發字決定哪題適用 → 推送前逐題表態 → 機器驗證據存在」整條路,四種狀態、改碼後表態過期、治理帳加標記檔的讀寫都現成;本案在它上面多一組題目,並把 satisfied 從「驗行號存在」加嚴成「驗那一行長得像那列的寫法」,不另起新閘。張力表態([[Projects/兩席相反時端出張力_計劃]])是「兩方意見相反時攤開給人裁」的既有形狀。②世界解:架構決策要靠可執行的檢查守住、不靠文件(架構適應度函式,ADR 每條對應至少一支自動檢查,https://concepts.dsebastien.net/concept/architectural-fitness-functions/ ;ArchUnit 把決策寫成測試,https://medium.com/publicis-sapient-france/enforcing-architecture-decisions-with-archunit-4d8b9f61cf4a )——採用「每列決策要有機器核得到的特徵」。③盲判:LLM 當評審時,讓它先看到別人的標籤會被帶著走(錨定),看不到的盲判跟嚴格標註者較一致(https://www.researchsquare.com/article/rs-10688342 ,預印本未同儕審);評審一致度要用扣掉偶然一致的指標看,單看相符率會高估(https://arxiv.org/html/2606.19544 )——採用「盲判材料由工具產生、不含作者答案」,一致度統計用 Cohen's kappa 而不只是相符率。不選:推送前閘裡直接呼叫模型(推送閘不呼叫模型是既有原則,[[Projects/Android寫法寫完當下自動檢查_計劃]]〈不做〉同一條)。
RETIRE-IF: 上線八週後在消費專案用 `lumos gov --stats` 看:①某一列情境題的盲判與作者一致度 kappa ≥ 0.9 且命中 ≥ 20 次 → 那一列拿掉盲判、只留證據樣式核對(盲判沒抓到東西);②某一列的作者表態裡 tension(作者主張證據樣式誤擋)超過該列命中的一成 → 那列的證據樣式重寫或改成只靠盲判;③整組情境題八週內命中少於 5 次 → 撤掉整組,只留告警帶寫法。

## 用詞

- **情境題**:從型錄 `skills/kotlin-idioms/checks-catalog.md`〈情境決策表〉每一列自動生成的棧別題,題號 `kt-sit-D-<n>`(`D-<n>` 就是決策表的列編號,原樣接在 `kt-sit-` 後面,不改寫)。題目文字=那列的「情境」;觸發字=那列的「觸發字」欄,型錄的格式檢查不准收一般常用字(停用字表與檢查由第一批的型錄格式檢查承接,[[Projects/Android協程與API寫法機械檢查標準_計劃]] S3)。只在改動行真的出現觸發字時才適用(跟既有 `shape_only` 題同一種:不因改動行數超過門檻就整組適用),並標 `android_only`。只收決策表的列:語意類主表列裡沒被任何決策表列引用的,只能是名稱標「(出處不全)」或「(人裁)」的列(第一批型錄格式檢查驗)。
- **證據樣式**:決策表新增的一欄,寫「照這列標準寫法寫出來的程式,一定會出現的字面特徵」,用 `主:`、`例外:` 兩段,各一到三條正規式(例:D-1 互不依賴的呼叫 → `主: \basync\s*\{ ; \.await\(\)|awaitAll\(`)。`例外:` 對應那列「不適用時」改用的寫法。證據樣式只是「有照做」的必要條件,不是充分條件(長得像不等於用對),用對沒用對交給盲判。
- **表態對程式**:情境題的 satisfied 表態多兩個必填欄:`row`(`D-<n>`)與 `variant`(`main` 或 `alt`);`evidence` 照既有規則寫單一個 `path:line`。推送前機器到被推的版本讀那一行前後各 3 行的窗,窗裡要有一條符合那列那個 variant 的證據樣式,才算照做。
- **候選列**:這次改動行命中觸發字的所有決策表列(不只題目自己那一列),讓盲判可以判成別列。
- **盲判**:一個沒看過作者表態的代理,拿工具產生的材料(這次改動裡觸發情境題的程式段、前後文、候選列的「情境/標準寫法/不適用時」三欄)逐題判:這段屬於哪一列(或都不屬於)、有沒有照那列寫。寫成盲判記錄,由 `lumos code-loop blind-judge` 寫入。
- **仲裁盲判**:作者與第一個盲判對不上的題,再派一個全新的盲判(材料同上,一樣看不到作者與第一個盲判的答案)。三方取多數。

## 範圍

1. **決策表加欄並由程式讀**:型錄〈情境決策表〉加「列編號」(D-1 起)與「證據樣式」兩欄;lumos 從自己的安裝位置讀這張表(讀不到或格式壞 → 情境題整組不出題、印一行提醒,不擋、不記帳);讀表函式由本案新建(`_kt_decision_table`,新增),第二批的改檔前推列也呼叫它——兩案誰先實作誰建,後做的那案直接用。
2. **情境題接進表態閘**:`kt` 題組既有九題(七題 Android 導向、兩題 Spring)不動;情境題不塞進載入時就編譯好的靜態題目表(`_STACK_QUESTION_SPECS` 與 `_STACK_TRIGGERS` 一一對齊,動態加會錯位),另有一張第一次用到才讀型錄的情境題表,在四處各接一次:適用性判定(`_stack_applicability`)、表態樣板(`_dispositions_template`)、表態驗證的題號查詢(`_stack_spec_by_id`)、題號集合守衛測試。觸發字整詞比對(自己加字界)、分大小寫(`(?-i:…)`,既有題組不分大小寫,情境題的觸發字多是專有 API 名,分大小寫才不誤傷);剝字串與註解照既有適用性判定(既有剝法只剝單行字串與註解,多行註解中間行與無空白的行尾註解剝不掉,照既有天花板)。題目進表態樣板、`--carry`、改碼後過期(同版本或祖先且中間只動簿記檔,用既有同一支判定),全照既有規則;`stack_questions.gate` 設 `high-only` 或 `off` 時情境題與盲判核對跟著不跑。
3. **表態對程式**:情境題的 satisfied 驗 `row`(要等於題號 `kt-sit-` 後面那段 `D-<n>`)、`variant`、`evidence`;那個 path:line 照既有規則驗存在,再讀窗比證據樣式,一條都沒中 → 這題判「沒照做」並擋,訊息印那列的標準寫法與證據樣式。na 照既有理由門檻,但要被盲判覆核(見 4);todo、tension 照既有規則,不跟盲判比(計數進統計,RETIRE-IF ② 看 tension 比例)。
4. **盲判記錄與核對**:
   - `lumos code-loop blind-judge --template [--diff <範圍>]`:印盲判材料(JSON:每個適用情境題的程式段、前後文、候選列三欄;**不含任何表態內容**),以及材料的 sha256。
   - `lumos code-loop blind-judge <盲判結果.json> [--arbiter]`:寫入盲判記錄(治理帳一筆 `blind-judge` 事件加標記檔,同表態的讀寫慣例;新事件種類登記進「不算迴圈收尾的事件」清單 `LOOP_NOT_CLOSE_EVENTS`;記錄綁目標版本與材料 sha256)。結果每題一筆:`{id, row: "D-<n>"|"none", followed: true|false, evidence: "path:line", reason}`。材料超過 8 萬字時 `--template` 分批印,每批各自的 sha256;推送前把這一版所有盲判記錄的題目取聯集,要涵蓋每一個適用的情境題,每筆記錄的 sha256 要對得上重算的那一批。
   - 推送前核對(加在表態那一道裡,不另開一道):有適用的情境題時,要有一筆綁這一版、材料 sha256 對得上的盲判記錄,沒有 → 擋,訊息印「跑盲判」的兩行指令。每題比「作者 vs 盲判」(只比作者 satisfied 與 na 的題):作者 satisfied 的 row 與盲判 row 相同且盲判 followed 為真、或作者 na 而盲判 row 為 none → 一致;其他都是不一致。不一致的題要有一筆仲裁盲判:仲裁跟作者一致 → 放行(記一筆「仲裁採作者」);仲裁跟第一盲判一致或三方都不同 → 擋,訊息印各方的 row 與理由。出口:改碼或改表態後重跑盲判;或作者把那題改表態成既有的 tension(既有欄位照填:existing、hazard、suggestion、chosen),照既有規則不擋、印 ⚠ 給人看,並計入 RETIRE-IF ②。
   - 改碼後盲判記錄過期,規則同表態。
5. **自動拉進代碼審**:分級不動(有 kt 改動本來就至少 standard);改動有適用的情境題時,`lumos pitfalls --diff` 輸出多一段「要跑盲判」並印兩行指令,推送前那一道(範圍 4)沒有盲判記錄就擋,所以不靠人記;代碼審手冊(lumos-code-loop)在「表態」那一步之後加「派盲判席」一步,派工詞由 `--template` 的輸出原樣當材料,寫明不得把表態檔交給盲判席。盲判席用 sonnet,一題一份材料;仲裁一律另開新代理。
6. **統計**:`lumos gov --stats` 的表態段加情境題:每列命中數、作者 satisfied/na 分布、作者與盲判一致度(相符率與 Cohen's kappa,類別=row 加 none)、仲裁採作者與採盲判的次數。RETIRE-IF 吃這幾個數。

**不做**:不在推送前閘或 CI 呼叫模型(盲判在代碼審迴圈裡跑,推送前只核記錄);不改既有九題與其他棧的題;證據樣式不做跨檔或型別判斷;不替 Codex 編排寫盲判派工(手冊先寫 Claude 編排的做法,Codex 照 `--template` 輸出自己派)。

## 實務隱患

- **證據樣式太鬆被敷衍**:作者指一行剛好含 `async {` 的程式就過。這是必要條件不是充分條件,盲判那一道補。
- **證據樣式太嚴誤擋**:同一寫法有多種長相(具名參數、換行、別名匯入)。每列至少兩條正規式,窗前後 3 行;誤擋的出口是改表態成 tension 交人裁,並計數。
- **盲判成本**:只對適用的情境題派,一題一份小材料;仲裁只在不一致時派。命中多的改動(例:一次改 50 支檔)盲判題會多,材料超過 8 萬字時 `--template` 分批印,每批一份記錄。
- **盲判被帶風向**:材料由工具產生、不含表態;但編排者仍可能在派工詞裡夾帶自己的答案——依本工具「單人、AI 依序操作、不防 AI 刻意偽造」的威脅模型不另防,手冊寫明禁止。
- **型錄格式壞掉**:讀表失敗整組不出題、印提醒(不擋),由型錄自己的格式檢查(第一批 S3)在本 repo CI 擋下。
- **常用字當觸發字**:型錄觸發字若收了 `map`、`flow`、`launch` 這類字,幾乎每個 kt 改動都會出題、盲判成本暴增;第一批型錄格式檢查用停用字表擋下,本案依賴那一道。
- **舊否決對照(2026-11-05 跑 `lumos rejections`,438 行,按概念比對)**:[[Systems/棧別提問表態閘]]〈邊界與刻意不做〉寫「不用 LLM 判答案;等 auto-na 比例與 recall-miss 帳說 regex 不夠再開」。本案的盲判就是用模型判答案,跟那條相反;依據是使用者 2026-11-05 明確要求加覆檢代理(見白話段原話),而且只對型錄情境題、在代碼審迴圈裡跑、推送前只核記錄,不動既有題組。[[Systems/doctor-irreversible-hint]] 否決「LLM 判可逆性」是另一件事(推送前提醒的判斷),不衝突。表態閘那篇的那一句在本案落地時改寫成「情境題例外,見本計劃」。
- **跟第二批改同一道表態閘**:第二批把「新增告警+表態」抽成共用函式給代碼審通過與推送共用;本案只在表態判定內部加情境題,兩邊改的函式不重疊;讀表函式兩案共用,誰先實作誰建。
- 已排除:金流:不碰付款或點數
- 已排除:對外送出:盲判在本機代理跑,不送資料到第三方以外的地方(代理本來就是編排者在用的模型服務)
- 已排除:不可逆:新增題目與記錄,退提交即回原狀;治理帳是追加
- 守衛面:改推送前表態閘的判定、會擋人,屬守衛面,走完整設計審(不寫成已排除)
- 資安:不新增自動執行命令的地方;盲判材料只含這次改動的程式段

## 驗收條款

- [S1] 當型錄〈情境決策表〉有一列 D-1 觸發字含 `async`、改動行新增 `val a = async { api.a() }` 時,`lumos pitfalls --diff` 的適用題 應 含 `kt-sit-D-1`;只有註解或字串裡出現 `async` 應 不適用;觸發字大小寫不同(`Async`)應 不適用;決策表讀不到時 應 整組不出題、印提醒、不擋 [test:t_kt_situation_questions_from_catalog]
- [S2] 當情境題 satisfied 表態 `row: D-1, variant: main, evidence: App.kt:12`,而被推版本 App.kt 第 9–15 行含 `async {` 與 `awaitAll(` 時,表態那一道 應 放行;那個窗裡沒有任何證據樣式 應 擋並印 D-1 的標準寫法;`row` 跟題號不符 應 擋;`variant: alt` 但只中 main 的樣式 應 擋 [test:t_dispositions_situation_evidence_pattern]
- [S3] 當有適用的情境題而沒有綁這一版的盲判記錄時,`lumos code-loop check` 應 擋並印跑盲判的指令;盲判記錄材料 sha256 對不上 應 擋;改碼後 應 判過期 [test:t_blind_judge_record_required]
- [S4] 當作者表態與盲判記錄都綁在這一版時,表態那一道 應 照多數決判:作者 satisfied D-1、盲判判 D-1 且 followed 為真 應 放行;作者 na、盲判 none 應 放行;作者 D-1、盲判 D-3 而沒有仲裁 應 擋;仲裁判 D-1 應 放行並記「仲裁採作者」;仲裁判 D-3 應 擋並印兩個盲判理由;三方都不同 應 擋;作者改成合法的 tension 應 不擋並印 ⚠;作者 todo 應 不跟盲判比 [test:t_blind_judge_majority]
- [S5] 當跑 `lumos code-loop blind-judge --template` 時,輸出 應 含每個適用情境題的程式段與候選列三欄,應 不含表態記錄裡的任何 row、variant、reason 字串(先寫一份帶獨特字串的表態再印材料,斷言字串不出現);材料超過 8 萬字 應 分批 [test:t_blind_judge_template_excludes_dispositions]
- [S6] 當改動有適用的情境題時,`lumos pitfalls --diff` 輸出 應 含「要跑盲判」段與兩行指令;沒有適用情境題時 應 不印;新事件種類 `blind-judge` 應 在不算迴圈收尾的事件清單裡 [test:t_pitfalls_situation_blind_judge_hint]
- [S7] 當治理帳有情境題的表態與盲判事件時,`lumos gov --stats` 應 印每列命中數、相符率、Cohen's kappa(用已知答案的小樣本驗算)與仲裁兩種結果次數 [test:t_gov_stats_situation_agreement]
- [S8] 當在實驗專案複本照範本接好、讓 AI 寫一段兩支互不依賴呼叫的串行寫法並推送時,應 被情境題擋下、照決策表改成並行並表態、派盲判後放行;耗時與盲判結果記進驗證紀錄 [manual:在暫存區實驗專案複本實跑一次完整流程,記下每一步的輸出與耗時]
