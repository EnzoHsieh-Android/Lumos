**F2 相鄰命中串接成鏈,段長沒有上限,而且一段裡會混進不同的情境**
severity: major

引句:「同一支檔裡相鄰(間隔不超過 3 行)的命中增行併成一段」

- 後果有五個:
  1. 段的身分把整段原文放進雜湊。
  2. 盲判材料是整段加前後 10 行,一票對應數千行。
  3. 證據範圍跟著變成整段,證據樣式幾乎一定湊得到,「必要條件」形同虛設。
  4. 候選列是整段所有命中的聯集,作者只能選一列,但這段其實含好幾個不同情境。
  5. 這會重新踩回 F1 的卡死。

**F6 盲判結果檔的邊角輸入:驗證順序與格式沒定,拒收時帳與標記檔會分叉**
severity: major

引句:「寫入時拒收(rc2)」

**F7 觸發字的邊界規則對含 `<`、空白、`.` 的觸發字不成立,對常見寫法也漏**

**F8 `_kotlin_strip` 沒有規格,既有的剝除函式有 Kotlin 不吻合之處**
severity: minor
blocking: 否
引句:「比對前先用 Kotlin 版的剝註解與字串函式 `_kotlin_strip`(新增」
file: `scripts/lumos:6795`
- 現有剝除模式(`_C_STRIP_PAT`)認 `'''` 與 `@"` 這些不是 Kotlin 的字串。
- 它的區塊註解用第一個 `*/` 收尾。Kotlin 的區塊註解可以巢狀,巢狀時尾巴會被當成程式碼,產生誤命中。
- 字串樣板 `"${ f("x") }"` 會被雙引號切斷。
- 原始字串 `"""` 跨很多行這一項,現有模式有處理。
- 必須對整份檔案剝,不能只剝視窗。段的視窗若落在 `"""` 或 `/*` 中間,奇偶就錯了。spec 沒寫範圍。
- 行數規則是「保留行數」,但沒說用什麼切行。
  - Python 的 `str.splitlines()` 會把 `\x0c`、`\u2028` 也當換行,和 git 的 `\n` 行號對不上。
  - 這會讓增行號偏移。這點 ⚠ 未實測。

**F9 段身分的邊角:CRLF、檔頭檔尾、相同原文、改名**
severity: minor
blocking: 否
引句:「`sha256(檔路徑 + "\0" + 段範圍的原文 + "\0" + 候選列編號清單)` 取前 16 碼」
- CRLF:原文含 `\r`,同一份程式在 autocrlf 不同的機器上身分不同,標記檔進版控後換機器就失效。
- 檔頭檔尾:段在第 1 行或最後一行時,前後 3 行與 20 行超出檔案。spec 沒說夾到邊界,證據範圍的邊界也沒說。
- 同檔兩處原文相同(複製貼上的樣板,例如測試裡重複的區塊):身分相同。身分裡不含行號。
  - 兩段共用一個身分,`segments` 以身分為鍵就只能寫一筆。
  - 作者怎麼對這兩處各表態,盲判怎麼各判一次,都沒寫。
- 改名:路徑在身分裡,改名加修改會使身分整批作廢。「rebase 後照樣有效」只涵蓋沒搬路徑的情況。
- 範圍 8 的覆核段身分同樣沒有行號,同一規則在兩處原文相同時同樣只有一個身分。這個風險小,因為兩處判定本來應該相同。

**F10 範圍 8 兩條規則命中同一行:能走,但判定有不對稱**
severity: minor
blocking: 否
引句:「段身分=`sha256(檔路徑 + 規則 id + 命中行前後各 3 行原文)` 前 16 碼」
- 規則 id 在身分裡,所以兩條規則命中同一行會得到兩個不同的身分,各自判一次,這樣可以走。
- 材料裡的程式碼視窗相同,同一個代理看兩次同一段,成本被放大。
- 只有第一個盲判、不派仲裁。判 `false-positive` 的覆核段永遠放行,而「同一段只認第一筆」堵掉了重判的路。
  - 盲判如果判錯,只有改碼讓身分改變一條路。
  - 範圍 8 說「判定留痕可複查」,但沒有複查流程或指令。
- 覆核段和情境段共用同一個標記檔,spec 沒說兩種段在同一份 `--template` 輸出裡怎麼區分作答格式。

- 0 段:題視同不適用,有定義。
- 整支檔被刪:沒有增行,所以不出段,正確。
