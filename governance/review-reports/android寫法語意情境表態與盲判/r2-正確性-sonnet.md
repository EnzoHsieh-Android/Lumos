severity: major

這份判法有 4 個會直接判錯的輸入(發現 1、2、3、6),還有 4 個不影響結論的缺口。以下 8 條都已對照 spec 與 repo 現有程式。

## 發現

**1. 段身分只綁前後 3 行,但盲判看 10 行、證據樣式看 20 行,範圍外的改動不會讓舊記錄失效**
severity: major
blocking: 是
引句:「內容不變身分就不變(rebase、壓提交後盲判記錄照樣有效);程式一改身分就變(舊記錄自動不算)。」
- 輸入:一段 `coroutineScope { val a = async { api.a() }; val b = async { api.b() } ... }` 已通過盲判(followed=true)。作者之後在第 8 行外、第 15 行內加一個 `delay` 或把 `awaitAll()` 換成逐一 `await()`。
  - 段範圍(前後 3 行)的原文沒變,身分不變。
  - 盲判看過的 10 行材料已經變了,舊記錄照樣算數。
  - 證據樣式會即時重算,但盲判票是舊的,所以這個改動不會重判。
- 反方向也錯:rebase 到上游剛好改了段旁 3 行內的無關行,身分就變,「rebase 後記錄有效」不成立(S3 只測內容完全不變的 rebase)。
- 覆核段(範圍 8)同病:語意級規則要知道型別,型別宣告通常在 3 行外。把變數型別改掉,命中行前後 3 行沒變,`false-positive` 判定就繼續放行。

**2. `alt`(例外)變體在票結構上對不上,只剩仲裁說謊或人工放行兩條路**
severity: major
blocking: 是
引句:「作者的票是 `(row, 照做)`;盲判的票是 `(row, followed)`;」
- 作者的 `segments` 只有 `{seg,row,variant,evidence}`,沒有 followed 欄,所以作者票只可能是 `(row, 真)` 或 `(none)`。
- 作者選 `D-1` 的 `variant: alt`(這段屬於「不適用時」的例外,正確做法就是不照主寫法):
  - 盲判看到不照主寫法的程式,會填 `(D-1, followed=假)`,或判 `none`。
  - 兩者都跟作者票 `(D-1, 真)` 不同。
- 於是這個例外段一定走到仲裁,仲裁也必須判「照做」才會過。誠實的判斷在這裡一律被擋。
- 盲判結果格式沒有 variant 欄,這個結構缺口補不了。

**3. 「每段單選一列」配上「相隔 3 行就併段」,一段裡有兩個真實情境時單選必錯**
severity: major
blocking: 是
引句:「同一支檔裡相鄰(間隔不超過 3 行)的命中增行併成一段」
- 輸入:ViewModel 裡 `val a = async { ... }`(D-1 的觸發字),往下 2 行是 `_events = Channel<Unit>()`(事件列的觸發字)。兩行併成一段,候選列是 {D-1, 事件列},兩者在這段裡都真實成立。
  - 作者選 D-1,盲判選事件列,雙方都對。
  - 票不同就進仲裁,仲裁選其中一個,必有一方被擋。
  - 唯一出口是段放行。
- 併段是遞移的:每隔 3 行一個命中就串成一整段,一個超大段只能選一列,另一個情境不會被核對。
- 「間隔」的定義(行號差,還是中間隔幾行)沒說。S1 只測相隔 2 行與 10 行,4 到 9 行沒定義。

**4. 證據行跟證據樣式沒有連結,而且證據範圍(前後 20 行)大過段範圍(前後 3 行)**
severity: major
blocking: 否
引句:「一段裡的每一條都要在證據範圍(剝過註解與字串)裡找得到才算(且)。」
- `evidence: path:line` 只要求落在範圍內,不要求那一行就是樣式命中處。作者隨便指範圍內一行就過。
- 樣式比的是整個 ±20 行,包含沒被改動的舊程式和相鄰另一段的程式。
- 輸入:段 A 是串行呼叫,寫成 `D-1 main`;它往下第 15 行是無關函式裡的 `awaitAll`(屬於段 B)。段 A 的證據樣式因此全中,過了表態對程式那一關。
- 這正好破了計劃白話段說的「防寫了規範卻完全沒參考」。
- 唯一的補救是盲判,而發現 1 說明盲判記錄可能是舊的。

**5. 內容相同的兩段拿到同一個身分**
severity: major
blocking: 否
引句:「`sha256(檔路徑 + "\0" + 段範圍的原文 + "\0" + 候選列編號清單)` 取前 16 碼」
- 輸入:同一支檔裡複製貼上的兩個 7 行區塊(測試函式、樣板程式常見)。身分相同,標記檔以身分為鍵,只存一筆。
- `segments` 的兩筆 `seg` 重複,而 evidence 必須落在各自的範圍內,一個 `path:line` 不能同時落在兩處,表態對程式怎麼判沒定義(⚠)。
- 盲判記錄以身分為鍵,兩處共用一筆判定。
- 統計說「同一段身分只算一次」,把兩段算成一段。

**6. 覆核段拿命中位置的方式,跟新增告警閘的比對規則對不上**
severity: major
blocking: 是
引句:「新增命中由新增告警閘既有的基準比對算(只算這次新增的,舊的不管)」
- repo 的算法:
  - file: `scripts/lumos:39698`(`_lint_new_diff_claims`)。
  - 指紋是 `規則+檔+命中片段`(file: `scripts/lumos:39673`),只算次數,不含前後 3 行,第 N+1 次出現才算「新增」。
- 輸入:作者把一段會中規則的程式複製貼上到既有那段的上方。基準 1 次、現在 2 次,閘回報的「新增」是檔案裡排後面的那一筆,實際上是舊程式。
  - 覆核段的材料(命中行前後 3 行、前後 10 行)拿到舊程式的上下文,盲判判的不是新寫的那一段。
  - 放行指紋是片段雜湊,對同檔的兩處相同片段一起生效,放行一處等於放行兩處,而覆核段身分是分開的。
- spec 說這類告警「改進這一道」,但沒說放行名單(file: `scripts/lumos:40003` 附近 `waivers` 扣除新增告警的路徑)怎麼對進新的核對:
  - S9 的「放行後不擋」沒有指出核對讀哪個放行檔、用哪個指紋比。
  - 閘在 no-config、env-unavailable、超時時整條早退,覆核命中也算不出來,「沒判定就擋」不會觸發,spec 沒寫(⚠)。

**7. 覆核判定只有一票、沒有仲裁,判定直接放行**
severity: minor
blocking: 否
引句:「只有第一個盲判,不派仲裁:判 real 時作者可以改碼或放行,不需要多數決」
- 輸入:盲判錯判成 `false-positive`。作者不需要知道,放行是自動的。
- 作者在命中行前後 3 行內改一個空白或註解,身分就變,又抽一次新的第一盲判。
- 統計「判 real 超過九成就升級、低於一成就降級」用的全是同一個盲判的判定,沒有真值校正;重判的同一個命中會重複計數。依據裡引的 Semgrep 準確率底線,本案沒有對應的量測。

**8. Cohen's kappa 在作者票只有一種類別時恆為 0**
severity: minor
blocking: 否
引句:「整體作者與第一盲判的相符率與 Cohen's kappa」
- 作者票只可能是 `(row,照做)` 或 `none`。早期專案若作者幾乎全選同一列,例如 25 段全是 `(D-1,真)`,盲判有 3 段不同:
  - 觀察一致率 = 偶然一致率 = 22/25,kappa = 0。
  - 它只在偶然一致率恰為 1 時才印「樣本不足」,這種情況印出 0,而實際相符 88%。
- 這不是算錯公式,是資料落在 kappa 的退化區。數字會誤導 RETIRE-IF 看的人,建議的做法是另印相符率(spec 已有),但沒規定在 kappa 無意義時加註。

## 次要缺口(併入此處,不單列編號)

- 引用 `import kotlinx.coroutines.flow.flatMapLatest` 這類 import 行不是註解也不是字串,被剝除函式保留,前面是 `.` 可中。每個新 import 都出一個沒有程式的段,徒增盲判量。
- `_kotlin_strip` 是對整份檔還是只對 diff 片段剝,spec 沒說(⚠)。只對片段剝時,開在片段外的三引號字串會讓狀態錯亂。
- 只改縮排、換行符的格式化提交讓檔案所有行都變增行,既有命中全變段。repo 的指紋刻意保留縮排(file: `scripts/lumos:39655`),spec 沒討論這類提交。
- 「同一段只認第一筆盲判,重派到同意為止的路被堵掉」不成立,改一個無關空白就換新身分,新身分重抽。

總結:最高 severity 是 major,沒有更高等級;發現 1、2、3、6 是會得出錯誤結論的輸入,修完才能進實作。
