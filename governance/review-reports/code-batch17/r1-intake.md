# code-batch17 r1 — 收貨與編排者機械重現

分級 standard(1 席 + 架構對齊 + 外家否決)。被審的是「修 `--list` 不理會篩選」。
★被改的是測試執行器本身,也就是裁判★——裁判被改壞的話,後面所有「測試綠」的結論都不可信。

## 這個 bug 從哪來

另一個 session 在做設計審時實測回報:`--list -k 任何字串` 都回全部 666 支。
我自己驗:**連一個完全不存在的關鍵字也回 666 支**——所以拿它判「某支測試存不存在」
會永遠得到「存在」。那個 session 的設計審裡有一席建議「先 `--list -k` 判存不存在」,
第一步等於恆真。

★根因值得記★:**這個 bug 修過一次但只修了一半**。碼裡的註解寫著上一輪把 `--list`
從「篩選之前」移到「分片之後」,而關鍵字那道在更後面,漏了。

## 我自己重現的

1. **`--list -k` 不篩**:`--list` 666 支、`--list -k t_guard_kill` 666 支、
   `--list -k 一個完全不存在的字串` 也 666 支。**HIT。**
2. **另一個 session 說「一次查詢會蓋掉推送閘的快取」——這條要分開講**:
   我量 mtime,`--list`(不管帶不帶 `-k`)**沒動**快取;`-k X` 真的跑**動了**。
   所以會蓋快取的是「真的跑測試」那條路,不是 `--list`。★把它的兩條分開驗才看得清。★
   (通才席後來也在自建 sandbox 裡獨立驗到同一結論。)

## ★我自己第一次改就改壞了★

第一版把 `--list` 搬到關鍵字篩選之後,結果把既有守衛「`-k` 選中 0 支要回 rc=1」
**推進 `return 0` 後面變成死碼**——是既有測試翻紅才發現。
現在分成兩條:`--list -k 對不到` 回 rc=0 + stderr 一句(查詢,「沒有」是合法答案),
`-k 對不到`真的跑才回 rc=1(那是「跑了個寂寞」)。

## 折入的四條

- **f1(外家否決 blocking + 通才 major,兩席自建 mutant 獨立命中)**:
  「兩道篩選要疊」那條斷言沒有鑑別力。舊寫法 `len(_nb) <= len(_ns) and all("loop" in n)`
  ——★`all()` 對空集合永遠為真★,所以「疊出來變空集合」抓不到;而且如果實作忽略分片、
  只對全部 666 支篩 loop,只要含 loop 的總數不超過該片支數,照樣綠。
  通才席用 mutant 實證:快照版本 12 條全綠 0 條紅。
  改成「從這一片的名單再篩關鍵字,兩邊集合完全相等」,並加一條「這一片要真的比全套少」。
- **f2(外家否決 minor + 通才 minor)**:rc=0 的語意沒有機械鎖住,誰改成 1 都不會有人發現。
  已加兩條斷言把 rc 與 stderr 訊息都釘住。
- **f3(架構對齊 minor)**:「現場成立」與「結果正確」合成一條 `and`,翻紅時分不出是
  「篩選沒生效」還是「篩選篩錯」。已拆兩條——這是 `Systems/測試假綠形態` 的明文硬規則。
- **f4(通才席附註,非本批引入)**:`shard_names` 是死碼,而且它的註解寫著
  「`--list` 走的是分片之前的路徑」——**那句話現在正好是反的**。
  刪掉。理由不只是「沒人用」:留一句說反的話比留死碼糟。

## ★rc 語意這題有結論,而且不是我拍的★

外家席認為「介面若要支援 rc 型存在性查詢,無命中應回 rc=1」。
架構對齊席用**三個既有案例**證明相反:這個 repo 的慣例是
「查詢=唯讀,rc 恆 0;閘=會被 CI/hook 消費,0 結果才判非零」——
`search` 0 筆命中 return 0、`contracts` 沒合約 return 0、`loop list` 空帳 return 0,
而且 `loop list` 的說明原文就是「唯讀恆 rc0…**這是查詢不是閘**」。

**採架構席**:rc=0 是對的,而且不是新發明的第二套邏輯,是套用既有的「查詢 vs 閘」二分。
外家席那半「守衛沒鎖住 rc 和 stderr」仍然成立,已折。
