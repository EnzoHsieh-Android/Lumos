severity: blocker

## 複驗一(對應 r1 發現一,污染守衛):量測路徑已經擋了,但擋下去之後留的逃生門 `--allow-contaminated` 產出的東西跟乾淨結果無法分辨,而且沒有留痕

先講複驗結果:**巢狀在 `if a.rebuild_pool:` 底下才擋的洞已經補起來**。我實際重跑了 r1 那套「查詢字串被寫進圖譜」的情境(造一篇筆記逐字含有題庫查詢字串,不帶 `--rebuild-pool`、只帶 `--labels` 跑正常量測):

```
python3 governance/eval/retrieval_eval_multiword.py --labels labels.json --pool pool.json --vault vault2 -k 5
rc=2
```

stderr 印出污染清單並且**不再往下跑**(`main()` 裡 `if bad:` 區塊最後 `if not a.allow_contaminated: ... return 2`),stdout 是空的——不會再有「看起來正常的報告」混進被污染的數字。這一條原本的洞已經堵住,對照 r1 的引句「這行 `return 2` 的擋,寫在 `if bad:` 底下再巢一層 `if a.rebuild_pool:`」,現在 `contaminated()` 的檢查是在 `main()` 一進來就跑、兩條路徑(量測與重組)共用同一段擋法(`governance/eval/retrieval_eval_multiword.py:272-291`)。

**但題目要我驗的三個延伸問題,答案都不理想**,加起來構成一個新的、同等級的洞:

1.「那個旗標會不會變成新的繞道?」——會。只要在同一條指令後面加 `--allow-contaminated`,污染检查照樣跑、照樣印出污染清單,但**不再 `return 2`**,直接往下算分、印報告、rc=0。
2.「產出的數字有沒有辦法跟乾淨的數字分辨?」——**沒有辦法**,我實測比對了兩次輸出:

```
# 不帶旗標(乾淨語料),與帶 --allow-contaminated 但語料被污染:
=== 中文多詞查詢的「0 筆回退」量測(整串查無 → 拆詞 OR 再查;語料釘 /tmp/r2sec/vault2) ===
  每行:題號 查詢 | 候選數 無回退→有回退 | 排序品質 nDCG@5 無→有 | 前 5 名對的比例 | 第一名的標註(2=必看/1=有用/0=不相干,★=第一名不相干)
  q1 污染測試查詢字串             候選  1→1   nDCG@5 1.000→1.000  P@5 1.00   top1=2
...
```

這份 stdout 文字**從頭到尾沒有任何字樣提到污染或 `--allow-contaminated`**——警告「⚠ 你用了 --allow-contaminated,以下分數含測不到東西的題,不得當成證據」只印在 stderr(`governance/eval/retrieval_eval_multiword.py:290-291`)。而這支工具存在的目的正是產出「會拿去做治理決定」的報告,治理報告典型做法就是把 stdout 存檔或貼進筆記——一旦這麼做,污染警告連同它唯一的痕跡一起被留在終端機、沒有進報告。我也用 `--rebuild-pool` 複測了一次同一個情境,持久化到磁碟的候選池 JSON 一樣沒有任何欄位記錄這一份是在 `--allow-contaminated` 下產生的(`n_any`/`n_term`/`n_cooccur`/`n_pool` 四個數字照印,跟乾淨情況格式完全相同)。
3.「有沒有別的參數組合還是能繞過污染檢查?」——沒找到能在不留下 `--allow-contaminated` 這個明文旗標的前提下讓 `contaminated()` 不被呼叫或被跳過的路徑;`bad = contaminated(a.vault, pool)`(`governance/eval/retrieval_eval_multiword.py:273`)在 `main()` 一開頭就對整份題庫跑,沒有旗標能關掉這次呼叫本身。

換句話說:**這一版把「自動、不需要任何人做任何事就會發生」的污染洩漏,換成了「需要一個明文旗標才會發生,但發生之後一樣無法從產出的報告本身察覺」的污染洩漏**。題目給的威脅模型明白列了「其他會談的 AI、被騙的自動化流程」——這正是最容易觸發這種洞的行為者:遇到 `rc=2` 就傾向「加一個看起來像逃生門的旗標讓它變綠」再繼續跑下去,而且不會有人事後從報告本身發現它加過。這不是「一般品質問題」,是這支工具唯一的資安機制(污染守衛)在被繞過之後不留審計痕跡,跟 r1 blocker 的性質相同,只是觸發門檻從「什麼都不用做」變成「加一個旗標」。

severity: blocker
blocking: 是

## 新發現:`write_json_atomic` 在目標路徑是符號連結時,會把新檔案的權限設成該符號連結自己回報的(與目標無關、通常是最寬鬆的)權限位元,而不是安全預設值

引句:「mode = os.stat(path, follow_symlinks=False).st_mode & 0o777」

這是題目點名要驗的延伸問題(「目標路徑本身就是符號連結時會怎樣?」)。r1 發現二的攻擊前提——「先在輸出路徑建一個指向別的檔案的符號連結,再跑重組」——現在**內容不會再被寫穿了**(我重現了一次:對著一個指向 `victim/important.txt`、內容原封不動保留 600 權限的符號連結跑 `write_json_atomic()`,結果 `victim/important.txt` 的內容完全沒被動到,`os.replace()` 換掉的是符號連結本身,不是它指向的檔案——這部分是真的修好了)。

但同一個前提下,**輸出檔案最後的權限不是抄目標檔案的權限,而是抄了那個符號連結自己毫無意義的權限位元**。我實測:

```python
victim = "/tmp/r2sec/victim/important.txt"   # 真正的檔案,權限 0o600
out = "/tmp/r2sec/work/out2.json"            # 攻擊者預先埋的符號連結,指向 victim
os.symlink(victim, out)

os.stat(out, follow_symlinks=False).st_mode & 0o777   # → 0o755
os.stat(victim).st_mode & 0o777                        # → 0o600(真正的檔案權限)
```

`write_json_atomic()` 第 220-222 行讀的是 `os.stat(path, follow_symlinks=False)`——也就是符號連結本身的 lstat,這個數字在系統上原本就是裝飾性的、幾乎跟符號連結真正指向的目標權限無關(Linux 上符號連結的 lstat 權限位元通常固定回報成全開的 `0o777`,不受 umask 影響,`chmod` 對符號連結本身也是沒有實際效果的操作;我在 macOS 上實測回報的是 `0o755`)。這個數字接著被原樣 `os.chmod(tmp, mode)`(第 231-232 行)套用到真正要換上去的新檔案,而 `os.replace()` 換完之後,輸出路徑上那個本來是符號連結的位置,現在變成一個內容乾淨、但**權限被放寬成 0o755(在 Linux 環境通常是 0o777,即全世界可寫)的一般檔案**。我也對照測過「目標本來就是一般檔案」這個正常/預期用例(覆寫一份既有輸出、原本 600 權限),那個情境權限有正確保留:

```
before: 0o600
after (regular file overwrite): 0o600
```

——只有「目標路徑是符號連結」這個攻擊者能主動製造的前提(跟 r1 發現二完全同一個入場券:能把一個符號連結塞進輸出目錄的人或程式)才會觸發權限放寬。也就是說,任何人只要能在這支工具即將寫入的輸出路徑上預先埋一個符號連結(不需要猜中隨機的暫存檔名,直接對著最終輸出路徑本身埋就行,因為 `os.stat(path, ...)` 讀的正是使用者傳進來的 `--rebuild-pool 出檔` 這個固定、可預期的路徑),就能讓這支工具幫他把治理用的候選池/報告檔案的權限鬆綁成全世界可寫——在 Linux 上一旦落地就是任何本機使用者都能之後直接竄改這份「已產出」的治理數字,而且整個過程印的訊息一樣是「✓ 候選池重組好了」,rc=0,看不出任何異狀。這個新洞跟 r1 發現二用的是同一個攻擊入場券,只是被修法堵掉「寫穿內容」之後,從旁邊開了一個「放寬最終權限」的側門。

severity: major
blocking: 是

## 逐條複驗結果彙整

- **發現一(污染守衛只擋重組)**:自動繞過的洞已堵——量測路徑(`--labels`,不帶任何額外旗標)現在會跟重組路徑一樣 `return 2`。但補上的逃生門 `--allow-contaminated` 本身構成新洞,見上方「複驗一」,判定同等級 blocking。
- **發現二(暫存檔名可預測、可被符號連結覆寫任意檔)**:暫存檔名的部分確實修好——`tempfile.mkstemp()` 帶隨機字尾,搭配 `O_EXCL`,我沒能找到可預先猜中並埋連結的暫存名;實際重現 r1 的完整攻擊步驟(埋連結→跑重組),**目標檔案內容沒有被覆寫**,`os.replace()` 對符號連結本身做的是整個換掉而不是解參照寫穿,這點過去我的理解跟這次實測一致。但「目標路徑本身是符號連結」這個 r1 原本沒細究的分支,實測後發現有新的權限放寬問題,見上方新發現。
- **發現三(讀全語料無上限)**:確認已修。全檔案搜尋 `read_text`/`rglob` 用法,現在只剩讀 `--pool`/`--labels` 這兩份小檔案,以及 `vp.rglob("*.md")` 用來確認語料目錄非空(用 `any()` 短路,不把內容讀進來)。原本 `contaminated()`/`rebuild_pool()` 整篇讀 Markdown 進記憶體字典的寫法已經整段拿掉,改成透過 `search_hits()` 呼叫 `lumos search` 子行程,不再由這支檔案自己持有語料內容。

## 新檢查過但沒找到洞的攻擊面

- **子行程參數注入 / 查詢字串被當旗標**:`search_hits()`(`governance/eval/retrieval_eval_multiword.py:117-119`)延續 r1 就驗過的 list 形式呼叫、不經 shell。額外確認了 `scripts/lumos` 的 `search` 子指令定義(`scripts/lumos:27526-27527`)——`term` 是必填的位置參數,若查詢字面剛好等於某個已定義的旗標(如 `--code`),argparse 會判成缺少 `term` 而以非 0 結束,`search_hits()` 對這個詞回傳空字典;這個結果會**同時**影響污染檢查與正式量測(兩者用同一套呼叫路徑),不構成「讓污染分數看起來乾淨、但量測分數仍受污染影響」這種可被利用的不一致,跟 r1 判斷一致。
- **錯誤訊息洩漏**:逐條看過新增的九處 `ERROR:` 訊息,印出的都是使用者自己在命令列給的路徑、或使用者自己準備的 `--pool`/`--labels` 檔案裡本來就有的欄位值(`cid`/`node`/分數 `v!r`)——沒有一處會讀出或印出使用者原本看不到的其他檔案內容或完整系統路徑。跑這支工具的操作者本來就對自己傳進去的檔案有完整讀取權,這些錯誤訊息沒有建立新的資訊揭露管道。
- **`--allow-contaminated` 是否讓 `contaminated()` 的檢查本身被跳過(而不只是跳過擋停)**:沒有找到這樣的路徑——`bad = contaminated(a.vault, pool)` 在 `main()` 一開頭就對整份題庫無條件執行(`governance/eval/retrieval_eval_multiword.py:273`),沒有旗標能讓這次呼叫整個不跑;`--allow-contaminated` 只影響「算出 `bad` 非空之後要不要 `return 2`」,不影響污染清單本身有沒有被算出來、印到 stderr。

severity 彙整:本輪新增/重開的洞判定為 blocker(逃生門無留痕)與 major(符號連結權限放寬)各一;r1 三條裡「暫存檔可預測寫穿內容」與「讀全語料無上限」兩條已確認修復乾淨,「污染守衛巢狀漏洞」修復了自動觸發那半、但衍生出旗標留痕的新洞。
