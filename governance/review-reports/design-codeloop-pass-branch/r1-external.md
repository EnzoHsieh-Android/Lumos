**F1：回退撤不掉新參數寫下的紀錄，撤除條件也量不到**
- severity: major
- blocking: 是
- 引句:「新參數寫入的紀錄本身仍可由既有 `check --branch` 依完整提交核對」
- file: `scripts/lumos:34509`
- **為什麼這是反例：**
  - 撤除條件寫的是「發現指定目的分支會讓不同提交或不同分支的留痕被借用」就撤。
  - 但治理帳寫的那一筆，欄位只有時間、提交、閘名、kind、說明、分支、完整提交，沒有任何一欄記「這筆是用 `--branch` 指定寫的」。
  - 讀帳那邊（`scripts/lumos:34431`）還原時也分不出來源。
  - 治理帳又規定只能追加、不能刪改；本機的 marker（存在本機、不進版控的留痕檔）也照設計保留。
- **後果：**
  - 就算觸發撤除，錯寫的那幾筆 main 留痕對同一個提交，以及它後面「只動帳本檔」的子孫提交，照樣算有效。
  - 回退只拿掉了以後再寫的入口，已經寫壞的紀錄撤不掉。
  - 回退段也沒交代讀側的身分核對要不要一起撤。如果一起撤，撞名的洞會在磁碟上既有的新 marker 上重新打開。
  - Issue 裡那條 2026-10-11 的回頭檢查，要數「分支記成 HEAD 的 pass 有幾筆」。改完之後 detached 的人改用 `--branch`，這個數會歸零，看起來像沒人踩到，其實只是量法失效。
- **建議：**
  - marker 和治理帳各加一欄來源，例如記實際 checkout 分支，或標明是明確指定的。
  - 回退時讀側忽略帶這個標記的紀錄，或改成追加一筆撤銷事件。
  - 撤除條件和 Issue 的回頭檢查都改成數這一欄。

**F2：S1 照字面去驗，會驗出假綠**
- severity: major
- blocking: 是
- 引句:「`code-loop check --branch main --at-sha <同一提交>` 能讀到，而查其他分支不得借用這筆新留痕」
- file: `scripts/lumos:35830`
- **為什麼這是反例：**
  - check 只有在 tier=high（風險掃描判成高風險）時才去讀留痕。沒到 high 就直接回 0，理由是「非 high」。
  - S1 要在全新臨時倉庫裡手動驗。一般臨時提交的 tier 是 standard，所以不管查 main、查別的分支、查撞名分支，一律回 0。
  - 「能讀到」和「不得借用」兩邊都會看起來成立，實際上讀側的身分核對完全沒被執行。
  - 本 repo 的測試檔裡另有一支自己的讀檔函式（`scripts/test_lumos.py:15202`），只照檔名讀、沒有身分核對。新測試若沿用它，也會繞過要驗的那段邏輯。
- **建議：**
  - S1 和 S2 的驗收條件寫明：要用會判成 tier=high 的改動。
  - 斷言 `check --json` 的理由欄：該讀到的含「有效留痕」並註明來源是 marker 還是治理帳，不該借用的要回 1 且理由是缺留痕或留痕過時。

**F3：在不分大小寫的磁碟上，「不能把檔名當身分」這條規則有漏洞**
- severity: minor
- blocking: 否
- 引句:「舊 marker 沒有分支欄且請求名含 `/` 或 `__` 時也退讀治理帳，不能把檔名當身分」
- file: `scripts/lumos:34380`
- **為什麼這是反例：**
  - 這台機器的檔案系統不分大小寫（實測確認過）。
  - 現有的 pass marker 都沒有分支欄（本工作樹那支實測也是）。
  - 查 `Main` 時，請求名不含 `/` 也不含 `__`，所以不會退讀治理帳，而是直接讀到 `main.json`，把 main 的舊留痕當成 Main 的。
  - 因為還是綁同一個提交，實際損害有限，但已經違反 S1 說的「不同分支不得共用」。
- **建議：**
  - 舊 marker 一律不認身分，全部退讀治理帳。
  - 或改成：只要檔名反推不回唯一的分支名就退讀，不再靠列舉 `/` 和 `__`。

**F4：`pass --branch` 可能蓋掉另一個分支的表態 marker**
- severity: minor
- blocking: 否
- 引句:「含 `/` 與 `__` 的兩個不同分支也要分清」
- file: `scripts/lumos:35360`
- **為什麼這是反例：**
  - 用 git 自己的分支名檢查實測，`x.dispositions` 是合法分支名。
  - `pass --branch x.dispositions` 會寫到 `x.dispositions.json`，而這正是分支 `x` 的表態 marker（`scripts/lumos:35338`）。
  - 讀表態的那支函式不核對檔內的分支欄。JSON 又是好的，所以不會退讀治理帳。
  - 結果 `x` 每次推送都被誤擋：要嘛判表態過期，要嘛每題都判缺表態，直到重新表態為止。
  - 以前要 checkout 一個叫這個名字的分支才會撞上；加了參數之後，從任何 checkout 打一行指令就會發生。
  - 這條是誤擋、不是放行，但設計只處理了 `/` 和 `__` 這一種撞名。
- **建議：**
  - 分支名拒絕以 `.dispositions` 結尾。
  - 或把留痕和表態的 marker 分到不同的命名空間。

**F5：目的分支只給了 pass，skip 和擋下時的提示都沒跟上**
- severity: minor
- blocking: 否
- 引句:「當新增 `pass` 的目的分支參數時，工具應維持 `skip`、`dispositions`、`check` 的既有語意」
- file: `scripts/hooks/pre-push:425`
- **為什麼這是反例：**
  - Issue 那個情境（detached 狀態下推 `HEAD:main`）如果是刻意不審、要走 skip，skip 照舊記在 HEAD 名下，推送還是會被擋。
  - pre-push 擋下時印的逃生指令只寫 `pass --note`，沒提 `--branch`；check 自己印的提示也一樣。
  - 照著提示做的人會重記在 checkout 分支下，再被擋一次。表態那邊的提示（`scripts/lumos:35531`）就有帶 `--branch`。
  - pass 和 skip 現在走的是同一段程式（`scripts/lumos:36036`）。設計沒說 skip 要不要一起加，實作者可能順手加上，也可能刻意不加，兩種都會讓設計對不上實作。
- **建議：**
  - 寫明 skip 要不要加這個參數。
  - 推送閘和 check 的提示，在推送目標分支和 checkout 分支不同時，印出帶 `--branch <目的分支>` 的完整指令。

**看過、不算問題的地方：**
- **留痕綁的提交本身是對的。** 讀側要求紀錄的提交跟被推的提交相同，或是它的祖先而且中間只改了帳本檔。所以就算用 `--branch` 寫到 main，也不會讓沒審過的程式碼溜過去，最多是誤擋。
- **分支名的檢查方式有效。** 實測：`HEAD` 和 `-` 會被 git 直接拒絕；`@{-1}` 會被展開成一個提交編號，跟輸入不同，會被「輸出要等於輸入」那條擋下；`refs/heads/main` 這種全名由「不是 `refs/heads/` 全名」那條擋下。`@` 會通過，但 `refs/heads/@` 本身是合法的遠端分支名，兩邊對得上，不算錯位。
- **CI 那邊沒有撞名問題。** CI 用推送的分支名讀治理帳，帳裡存的是完整分支名，不經過檔名轉換。
