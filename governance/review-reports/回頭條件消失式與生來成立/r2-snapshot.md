# 回頭條件消失式與生來成立_計劃

白話:回頭條件的條件鍵(`when-file`、`when-symbol`、`when-test`、`when-status`)全是「等某樣東西出現」,沒辦法寫「等某支檔或某段程式不再出現就回頭」。另一件事:一條條件式回頭條件如果寫下的當下條件就已經成立,它從來沒提醒過任何人;推送時新寫的已經會被擋,但這道檢查上線以前寫的舊行,`lumos drift scan` 只說「條件已經成立」,有人表態照留之後就再也看不出它是「生來就成立」。這份計劃補兩件事:①新的條件鍵 `when-gone`;②scan 對現在成立的條件往回查寫下那一版,標出「寫下時就已成立」,表態過的也照標。

這是消費專案 2026-10-02 清漂移回傳「回頭條件四項」裡的另兩項(第 6、11 項);第 4、7 項在 [[Projects/回頭條件寫法補齊_計劃]]。

依據:
- 消費專案清漂移回傳(2026-10-02,第 6 項,去識別):「等某支檔不再直接讀系統時間就回頭」——when-file、when-symbol、when-test 只能等東西出現。建議 `[when-gone:路徑::樣式]`。
- 同一份回傳第 11 項:drift probe 只說「現在成立」,而且表態後就靜音,看不出它生來就成立、從沒提醒過任何人(四條);建議提交當下就檢查新寫的條件。
- 2026-10-03 乾淨查證員核對現況(唯讀,[[Projects/回頭條件寫法補齊_計劃]] 依據同一次):條件鍵只有四個、全是正向判定;推送時已經會擋「這次新寫(或改了條件)的回頭條件,條件已經成立」(既有測試 `t_drift_when_probes_evaluate_and_trigger` ⑨);提交時只驗寫法、不評估;scan 只看現在成不成立、不看歷史;表態後 scan 標「已表態」、推送不再擋。
- 條件文法、評估與推送判定在 [[Projects/存量漂移防線_計劃]]〈做法〉第 0、2 節;家在 [[Systems/存量漂移守衛]]。

PRIOR-ART: 最小解在工具這一層(條件評估本來就在 lumos 的推送判定與 scan 裡)。世界上最接近「等東西消失」的是 feature flag 平台的清理提醒(旗標在程式碼裡已經沒有引用就提示移除)與 Ruby todo_or_die 的條件式到期;都是「某個符號或文字不在了就觸發」,本案照這個形狀,只認明寫的路徑與字面字串,不做樣式或正則(條件要讀得懂、判得穩)。「寫下時就已成立」照 git blame 式的考古:沿那篇筆記的提交歷史往回看,不另建索引;讀某提交的圖譜沿用 `drift scan --at` 既有的 `_drift_tree_env`,判定沿用同一支 `_drift_probe_line`(設計審 r1 架構對齊席:原稿寫 `git log -S` 與 `drift exam`,前者會找錯提交、後者不是直接在歷史樹上判)。不做:提交時就評估條件(推送時已經擋新寫的已成立條件,提交時再評估要每次提交建樹,成本不划算;寫進天花板)。
RETIRE-IF: 上線兩個月後任一成立就撤掉或改規則:①`when-gone` 兩個月零使用(數圖譜裡 `[when-gone:` 出現幾次),拿掉這個鍵;②scan 的「寫下時就已成立」標記在工具鏈與消費專案各跑一次都是 0 筆,而且兩個月內沒有新的舊行被標,拿掉往回查那一段(只剩成本)。
REVISIT:2026-12-03 數兩邊圖譜 `[when-gone:` 幾處、跑 `lumos drift scan` 數「寫下時就已成立」幾筆,照 RETIRE-IF 判

## 範圍

- **做**:第 6 項(條件鍵 `when-gone`)、第 11 項(scan 標出寫下時就已成立)。
- **不做**:提交時就評估新寫的條件——推送時已經擋(既有),提交時要多建一次樹;寫進天花板。
- **不做**:樣式、正則、萬用字元的消失條件——只認路徑與字面字串。

## 做法

### 1. 條件鍵 `when-gone`(第 6 項)

1. **寫法**:`[when-gone:<路徑>]`——樹上找不到這個路徑就成立;`[when-gone:<路徑>::<字串>]`——找不到這個路徑、或那支檔裡不再出現這段字就成立。
   - 路徑:規矩同 `when-file`(不准 `/` 開頭、不准 `..` 段);反斜線轉斜線與 NFC 正規化**只做在路徑那段**(先切再正規化,設計審 r1 邊界席:不轉會重開已修過的 `..\x` 繞過,整串轉會把字串裡的反斜線也改掉)。
   - `::` 從**第一個**切(字串裡可以有 `::`,路徑裡不會有)。既有的 `_drift_cond_split` 對 symbol/test 從最後一個切;不另開第二支,讓 `_drift_cond_split(v, k)` 依鍵決定切法(`gone` 切第一個、其他切最後一個),判定、預讀、點名讀不出的檔、候選篩選、正規化、值驗證全部呼叫它(設計審 r1 架構對齊席:一個條件碰到哪支檔只有一份算法)。
   - 字串:照字面、分大小寫,去頭尾空白後不能是空的;不能含 `]`(標記在第一個 `]` 結束)、換行、反引號——反引號會被可見文字的規矩剝掉、實際比對的不是作者寫的那串(設計審 r1 正確性席、通才席),新寫的 REVISIT 行原文裡 `[when-gone:` 之後同一個標記內出現反引號,提交時報「條件寫錯」。
   - 沒有不帶路徑的寫法——「整個 repo 都不再出現某段字」要掃全樹,判不穩也太貴。
   例:`REVISIT:[when-gone:src/instrumented.py::time.time()][by:2027-01-31] 不再直接讀系統時間了,把註解裡的警告拿掉`。
2. **評估**(`_DriftProbeTree.one` 多一個分支):
   - **「在」怎麼算**:那一版的樹上這個路徑是一般檔、連結檔或子模組,或它是資料夾(樹上有以 `路徑/` 開頭的條目),都算在;全都沒有才算消失(設計審 r1 正確性席、通才席、邊界席:原稿只看一般檔清單,連結檔、子模組、資料夾會在寫下當下就被判成已消失)。樹的條目清單要包含一般檔以外的種類,`_DriftProbeTree` 建樹時多存一份「全部條目」(既有的 `files` 只放一般檔,不動它的意思)。
   - **帶字串**:路徑在、但不是一般檔(連結檔、子模組、資料夾)→ 判不了,scan 列成問題「when-gone 帶字串時路徑要是一般檔」;是一般檔就讀位元組(既有的 `_read`,讀不出判不了),內容含 NUL 位元組(二進位、UTF-16)或是 Git LFS 指標檔(開頭 `version https://git-lfs.github.com/spec/`)→ 判不了;否則把字串編成 UTF-8 在位元組裡找,找不到 → 成立(設計審 r1 正確性席:誤讀成亂碼也會「找不到」、讓條件提早成立,所以讀不準的一律判不了)。
   - **工作目錄模式**(`drift scan` 不帶 `--at`):清單照既有的工作目錄讀法,sparse-checkout 沒拉下來的檔與還沒暫存的刪除在這個模式下算消失(天花板 5)。
   - `_drift_probe_one`、`_drift_probe_line` 不動(新鍵走同一支)。
3. **推送判定的候選**:`_drift_probe_cond_candidate` 對 `when-gone` 看路徑(`_drift_cond_split` 取)在不在這次推送改到的檔裡,或是以它為前綴的資料夾裡有檔被改到;其餘轉變判定照舊。寫下時就已成立的(字串拼錯、檔名寫錯),推送時照既有規矩被點名「這次新寫(或改了條件)的回頭條件,條件已經成立」——這是 `when-gone` 寫錯時的保險。檔被改名或搬家時,舊路徑「消失」,帶字串的條件也成立(那段字其實搬到新路徑了);推送會點名,作者看了再決定(天花板 3)。
4. **列舉鍵的地方由同一張表產生**:`_PROBE_KEYS` 加 `gone`;`_probe_value_err` 的「只有 file、symbol、test、status」與 `_slot_retire_err` 的「只收 when-file/when-symbol/when-test/when-status、度量、人裁」改成從 `_PROBE_KEYS` 組字;新增漂移守衛測試:這兩句訊息與筆記形狀擋否定現況句提醒裡「條件怎麼選」那段,都要提到 `_PROBE_KEYS` 的每個鍵(設計審 r1 架構對齊席、正確性席、通才席、邊界席:原稿只列一處,另兩處漏改)。`_slot_retire_err` 對 `gone` 照 symbol/test 的規矩要求帶路徑(本來就必帶)。RULE 撤除條件 `[retire:when-gone:…]` 走 `_retire_lines` 改寫成回頭條件標記再交給 `_probe_parse`,判定與推送轉變同一支。技能手冊 `skills/lumos-project-notes/commands/03-寫回圖譜.md` 四種鍵那句補第五種。

### 2. 寫下時就已成立(第 11 項)

1. **什麼叫「寫下時」**:跟系統其餘地方認「同一條」的規矩一樣——同一篇筆記裡、**條件標記一模一樣**的條件式回頭條件(待辦文字、期限改了都還是同一條;[[Projects/存量漂移防線_計劃]]〈做法〉第 0 節)。「寫下時」是這一條**這一世**的開頭:從被掃的那一版往回,一版一版看這篇筆記,找連續都還有這一條的最早那一版;中間有一版沒有(刪掉過),就停在刪掉之後重新出現的那一版(設計審 r1 正確性席、通才席、邊界席:原稿用 `git log -S` 找「第一次出現這段文字」,改過字、搬過位置、刪了又寫、舊的較長行包含它時都會找錯提交)。
2. **怎麼查**:
   - 起點版本:`drift scan --at <提交>` 就是那個提交;不帶 `--at` 是工作目錄,往回查從 HEAD 開始,工作目錄裡還沒提交的行標「判不了寫下時成不成立(還沒提交)」。
   - 這篇筆記改到它的提交清單用 `git log --format=%H <起點> -- <筆記路徑>`(走 `_nodehome_git`,`-c` 關掉外部差異與文字轉換的既有旗標,`--` 隔開路徑);每一版的筆記內容用一次批次讀(`_nodehome_cat_blobs_capped`),逐版用同一支抽取(`_probe_lines`)找同一條——不用 `-S` 字串搜尋,一行含 NUL 也不會讓 git 參數出錯(設計審 r1 邊界席)。
   - 找到「這一世的第一版」後,在那個提交的樹與圖譜上用同一支 `_drift_probe_line` 判一次(圖譜用既有的 `_drift_tree_env`,同 `drift scan --at` 讀某提交圖譜的做法;設計審 r1 架構對齊席:原稿引 `drift exam` 當先例不準)。
3. **結果**:成立 → 這條發現多一個標記「寫下時就已成立(提交 <短碼>),從沒提醒過」;不成立 → 不標;判不了(還沒提交、淺層 clone、找不到、git 失敗、超過預算、那一版的樹讀不出)→ 標「判不了寫下時成不成立(原因)」。只對「條件已經成立」的回頭條件查(含已表態的;RULE 撤除條件不查)。
4. **淺層 clone**:用既有的 `_git_is_shallow` 判;是淺層就整段不往回查,每條成立的都標「判不了寫下時成不成立(淺層 clone 看不到歷史)」(設計審 r1:原稿〈做法〉與〈實務隱患〉兩處講法不同)。
5. **預算**:往回查吃 scan 既有的時間預算(`--budget`),排在本來的評估之後;每個 git 呼叫的逾時取「剩餘預算」與既有 20 秒的較小值(設計審 r1 邊界席:原稿沿用固定 20 秒,不受預算約束);同一個提交的樹與圖譜只建一次。scan 不是閘,判不了不擋。
6. **呈現**:文字輸出那一行後面加標記;`--json` 的發現多一個欄位 `born`,形狀固定是物件:`{"commit": 短碼}` 或 `{"unknown": 原因}`,不標就沒有這欄(設計審 r1 架構對齊席:原稿一個欄位混用物件與字串)。「判不了」留在發現自己的欄位裡、不搬進 `problems`(它不是這條回頭條件寫錯,只是往回查不了)。已表態的照樣標。doctor Z 段不評估條件,不動。
7. **推送判定不改**:新寫的已成立條件推送時本來就擋;本案只補 scan 看存量。

## 實務隱患

- **繞過**:`when-gone` 寫一個本來就不存在的字串,推送時被點名「已經成立」——作者可以表態照留繞過;這是明寫的動作、留在表態檔,不另擋。
- **效能**:`when-gone` 帶字串時讀一支檔(同帶路徑的 symbol,有預讀);scan 往回查每條成立的條件一次 `git log`(只在單一筆記路徑上)、那篇的歷史版本一次批次讀、每個不同提交建一次樹與圖譜;成立的條件通常是個位數,吃 scan 既有預算,超過就標判不了(設計審 r1 正確性席實量:單次 git log 約 0.05 秒、建一次圖譜約 0.19 秒)。推送判定的成本不變。
- **併發**:只讀 git 物件;scan 不寫帳。
- **回滾**:還原本案的提交:`when-gone` 變成「不認得的條件鍵」——新寫的提交時被擋、已寫的 scan 列成寫錯的條件、推送判定不評估(既有對寫錯條件的處理);scan 不再標寫下時成立。沒有資料要收。
- **相容**:新鍵只是多認一種寫法,既有四種鍵的判定不變;`--json` 多一個可省略欄位,讀的人沒有靠它。消費專案要 `lumos update` 之後才認得 `when-gone`,更新前寫了會被舊版擋成「不認得的條件鍵」。
- **跨環境**:淺層 clone 不往回查(第 2 節第 4 點);往回查走 `_nodehome_git` 的既有旗標,本機的外部差異與文字轉換設定不影響;本機與 CI 同一支判定。
- 已排除:金流:只讀筆記與 git 物件
- 已排除:對外送出:不呼叫網路
- 已排除:不可逆:只決定擋不擋、列不列,還原提交就回去
- **守衛面**:推送判定(會擋的閘)多認一種條件鍵——判錯會讓該擋的不擋或不該擋的擋;讀不準的一律判不了(推送時判不了算要處理,既有規矩),用既有的轉變判定與測試守,不新增擋的種類。

## 驗收條款

- [S1] 當 `[when-gone:src/a.py]` 指的檔在樹上,應 不成立;檔被刪掉 應 成立;指到資料夾、連結檔或子模組 應 不成立;`[when-gone:src/a.py::time.time()]` 檔裡還有這段字 應 不成立、拿掉這段字或刪掉檔 應 成立;帶字串而路徑是資料夾、內容含 NUL、是 LFS 指標檔或讀不出 應 判不了 [test:t_drift_when_gone_evaluates]
- [S2] 當這次推送刪掉 `[when-gone:…]` 指的那段字,推送判定 應 點名「這次推送讓條件成立了」;推送沒動那支檔 應 不列;新寫一條 `[when-gone:…]` 而字串本來就不在檔裡 應 點名「這次新寫(或改了條件)的回頭條件,條件已經成立」 [test:t_drift_when_gone_push]

## 回退

## 天花板

1. 提交時不評估條件:新寫的已成立條件要到推送才被點名。
2. 往回查只看這一篇筆記自己的歷史:筆記改過名,找到的是改名後那一版,寫下當時的狀態可能看不到(會標成那一版的判定)。
3. `when-gone` 只認字面字串與原路徑:改寫成同義寫法、或檔改名搬家,都算「不再出現」,條件會提早成立——推送時會被點名,作者挑字串時要挑會真的消失的那段。
4. 字串不能含 `]`、換行、反引號;要比對的程式片段含這些字元時,挑片段裡不含它們的那一段。
5. 工作目錄模式的 scan 照工作目錄看「在不在」:sparse-checkout 沒拉下來的檔、還沒暫存的刪除都算消失;要看提交的狀態用 `--at`。
6. 淺層 clone 不往回查。
