# 回頭條件消失式與生來成立_計劃

白話:回頭條件的條件鍵(`when-file`、`when-symbol`、`when-test`、`when-status`)全是「等某樣東西出現」,沒辦法寫「等某支檔或某段程式不再出現就回頭」。另一件事:一條條件式回頭條件如果寫下的當下條件就已經成立,它從來沒提醒過任何人;推送時新寫的已經會被擋,但這道檢查上線以前寫的舊行,`lumos drift scan` 只說「條件已經成立」,有人表態照留之後就再也看不出它是「生來就成立」。這份計劃補兩件事:①新的條件鍵 `when-gone`;②scan 對現在成立的條件往回查寫下那一版,標出「寫下時就已成立」,表態過的也照標。

這是消費專案 2026-10-02 清漂移回傳「回頭條件四項」裡的另兩項(第 6、11 項);第 4、7 項在 [[Projects/回頭條件寫法補齊_計劃]]。

依據:
- 消費專案清漂移回傳(2026-10-02,第 6 項,去識別):「等某支檔不再直接讀系統時間就回頭」——when-file、when-symbol、when-test 只能等東西出現。建議 `[when-gone:路徑::樣式]`。
- 同一份回傳第 11 項:drift probe 只說「現在成立」,而且表態後就靜音,看不出它生來就成立、從沒提醒過任何人(四條);建議提交當下就檢查新寫的條件。
- 2026-10-03 乾淨查證員核對現況(唯讀,[[Projects/回頭條件寫法補齊_計劃]] 依據同一次):條件鍵只有四個、全是正向判定;推送時已經會擋「這次新寫(或改了條件)的回頭條件,條件已經成立」(既有測試 `t_drift_when_probes_evaluate_and_trigger` ⑨);提交時只驗寫法、不評估;scan 只看現在成不成立、不看歷史;表態後 scan 標「已表態」、推送不再擋。
- 條件文法、評估與推送判定在 [[Projects/存量漂移防線_計劃]]〈做法〉第 0、2 節;家在 [[Systems/存量漂移守衛]]。

PRIOR-ART: 最小解在工具這一層(條件評估本來就在 lumos 的推送判定與 scan 裡)。世界上最接近「等東西消失」的是 feature flag 平台的清理提醒(旗標在程式碼裡已經沒有引用就提示移除)與 Ruby todo_or_die 的條件式到期;都是「某個符號或文字不在了就觸發」,本案照這個形狀,只認明寫的路徑與字面字串,不做樣式或正則(條件要讀得懂、判得穩)。「寫下時就已成立」照 git blame 式的考古:沿那篇筆記的提交歷史往回看,不另建索引;讀某提交的圖譜沿用 `drift scan --at` 既有的 `_drift_tree_env`,判定沿用同一支 `_drift_probe_line`(設計審 r1 架構對齊席:原稿寫 `git log -S` 與 `drift exam`,前者會找錯提交、後者不是直接在歷史樹上判)。不做:提交時就評估條件(推送時已經擋新寫的已成立條件,提交時再評估要每次提交建樹,成本不划算;寫進天花板)。
RETIRE-IF: 上線兩個月後任一成立就撤掉或改規則:①`when-gone` 兩個月零使用(數圖譜裡 `[when-gone:` 出現幾次),拿掉這個鍵;②scan 的「寫下時就已成立」標記在工具鏈與消費專案各跑一次都是 0 筆,而且兩個月內沒有新的舊行被標,拿掉往回查那一段(只剩成本)。
REVISIT:2026-12-03 數兩邊圖譜 `[when-gone:` 幾處、跑 `lumos drift scan` 數「寫下時就已成立」幾筆,照 RETIRE-IF 判

## 範圍

- **做**:第 6 項(條件鍵 `when-gone`)、第 11 項(scan 標出寫下時就已成立)。
- **不做**:提交時就評估新寫的條件——推送時已經擋(既有),提交時要多建一次樹;寫進天花板。
- **不做**:樣式、正則、萬用字元的消失條件——只認路徑與字面字串。

## 做法

### 1. 條件鍵 `when-gone`(第 6 項)

1. **寫法**:`[when-gone:<路徑>]`——樹上找不到這個路徑就成立;`[when-gone:<路徑>::<字串>]`——找不到這個路徑、或那支檔裡不再出現這段字就成立。
   - 路徑:規矩同 `when-file`(不准 `/` 開頭、不准 `..` 段);反斜線轉斜線與 NFC 正規化**只做在路徑那段**(先切再正規化)。
   - `::` 從**第一個**切(字串裡可以有 `::`,路徑裡不會有);沒有 `::` 就是只有路徑、字串是空的(只看路徑在不在)。
   - 字串:照字面、分大小寫,去頭尾空白後不能是空的(帶了 `::` 就要有字串);不能含 `]`(標記在第一個 `]` 結束)、換行、反引號——反引號會被可見文字的規矩剝掉,實際比對的不是作者寫的那串。
   - 沒有不帶路徑的寫法——「整個 repo 都不再出現某段字」要掃全樹,判不穩也太貴。
   例:`REVISIT:[when-gone:src/instrumented.py::time.time()][by:2027-01-31] 不再直接讀系統時間了,把註解裡的警告拿掉`。
2. **拆值與讀鍵的地方逐一列出**(設計審 r2 三席:原稿說「全部呼叫同一支」不是現況):`_drift_cond_split(v, k)` 加鍵參數——`gone` 切第一個 `::`、沒有 `::` 回 (路徑, 空字串);其他鍵照舊切最後一個。下列每一處都改成呼叫它或加上 `gone` 的分支(以 2026-10-03 的程式為準,函式名):
   - `_probe_value_err`:`gone` 走新寫的 `_probe_gone_err`(路徑規矩、字串非空、`..` 與 `/` 開頭照 file);
   - `_probe_norm_value`:`gone` 只正規化路徑那段,字串原樣;
   - `_probe_named_err`:只給 symbol/test,不動;
   - `_DriftProbeTree.prefetch`、`unread_for`、`one`:帶字串的 `gone` 跟帶路徑的 symbol 一樣預讀、點名、判;
   - `_drift_probe_cond_candidate`:見第 4 點;
   - `_drift_row_unread`:帶字串的 `gone` 點名那支檔;
   - `_drift_probe_path_warn`:`gone` 不提示(找不到是它的正常成立狀態;打錯字的保險見第 4 點);
   - `_slot_retire_err`:`gone` 不必另外要求 `::`(它本來就帶路徑),值驗證走 `_probe_value_err` 同一支——RULE 撤除條件與 REVISIT 兩條路的寫法要求一致(設計審 r2 正確性席、邊界席)。
   新寫的 REVISIT 行或 RULE 撤除條件,原文裡 `[when-gone:`(或 `[retire:when-gone:`)那個標記內出現反引號:在筆記形狀擋的回頭條件檢查(`_ns_revisit_violations`)與格子撤除條件檢查(`_slot_retire_err` 的呼叫端)看**原文**報「條件寫錯」——共用解析器拿到的是剝過反引號的文字,放在那裡永遠不會觸發(設計審 r2 通才席)。
3. **評估**(`_DriftProbeTree.one` 多一個分支):
   - **「在」怎麼算**:那一版的樹上這個路徑是一般檔、連結檔或子模組,或它是資料夾(樹上有以 `路徑/` 開頭的條目),都算在;全都沒有才算消失。`_DriftProbeTree` 建樹時多存一份「全部條目」(既有的 `files` 只放一般檔,不動它的意思)。
   - **帶字串**:路徑在、但不是一般檔 → 判不了(scan 的「判不了」照既有的 `_drift_bad_note` 點名那支檔);是一般檔就**另讀原始位元組**——既有的 `_read` 讀完會用替代字元解碼成文字,誤讀的內容也會「找不到字串」(設計審 r2 三席),所以 `_DriftProbeTree` 加一份位元組快取、走同一次批次讀。內容含 NUL、是 Git LFS 指標檔(開頭 `version https://git-lfs.github.com/spec/`)、或不能用嚴格 UTF-8 解碼(Big5 這類沒有 NUL 的舊編碼)→ 判不了;能解碼就在文字裡找字串,找不到 → 成立。
   - **工作目錄模式**(`drift scan` 不帶 `--at`):清單照既有的工作目錄讀法,sparse-checkout 沒拉下來的檔與還沒暫存的刪除在這個模式下算消失(天花板 5)。
   - `_drift_probe_one`、`_drift_probe_line` 不動(新鍵走同一支)。
4. **推送判定**:`_drift_probe_cond_candidate` 對 `when-gone` 看路徑在不在這次推送改到的檔裡,或是以它為前綴的資料夾裡有檔被改到;其餘轉變判定照舊。寫下時就已成立的(字串拼錯、檔名寫錯、全形冒號、被 gitignore 的檔——永遠不會在樹上),推送時照既有規矩被點名「這次新寫(或改了條件)的回頭條件,條件已經成立」;`when-gone` 的路徑在終點版本就找不到時,點名訊息後面多一句「路徑在這一版就找不到——打錯字、全形符號,或是被 gitignore 的檔?」(設計審 r2 邊界席:原本的原因句會讓人以為東西剛被刪)。檔被改名或搬家時,舊路徑消失、條件成立,推送會點名(天花板 3)。
5. **列舉鍵的地方由同一張表產生或逐一同步**:`_PROBE_KEYS` 加 `gone`;程式裡的兩句訊息(`_probe_value_err` 的「只有 file、symbol、test、status」、`_slot_retire_err` 的「只收 when-file/…」)從 `_PROBE_KEYS` 組字;筆記形狀擋否定現況句提醒裡「條件怎麼選」那段補一句 `when-gone`。文件裡列鍵的地方逐一改:`skills/lumos-project-notes/commands/03-寫回圖譜.md`、`skills/lumos-project-notes/reference.md`、`skills/lumos-project-notes/SKILL.md`、注入消費專案紀律區塊的範本 `scripts/templates/graph-discipline.md`(只改列鍵那句;鐵則 4 那行由 `t_graph_discipline_negation_revisit` 逐字釘住,不在範圍內就不動;範本有改就照既有規矩升範本版本)。漂移守衛測試掃這兩句程式訊息、提醒那段、上面四份文件,都要提到 `_PROBE_KEYS` 的每個鍵(設計審 r2 正確性席、邊界席、通才席:原稿漏了範本與 reference)。

### 2. 寫下時就已成立(第 11 項)

1. **什麼叫「寫下時」**:跟系統其餘地方認「同一條」的規矩一樣——同一篇筆記裡、**條件標記一模一樣**的條件式回頭條件(待辦文字、期限改了都還是同一條)。「寫下時」是這一條**這一世**的開頭:沿主幹(`--first-parent`)往回,一版一版看這篇筆記,找連續都還有這一條的最早那一版;中間有一版沒有(刪掉過),就停在刪掉之後重新出現的那一版。只沿主幹:合併提交讓兩條分支的版本交錯,預設的歷史順序不是祖先鏈(設計審 r2 正確性席、通才席實跑);在側分支寫、再合進來的,「寫下時」算成合併進主幹的那一版(天花板 2)。
2. **任何不規則都判不了,不硬猜**:
   - 被掃的那一版裡這篇有兩行以上條件標記一樣 → 判不了(分不出是哪一行;設計審 r2 正確性席);
   - 往回的某一版:那篇不存在 → 這一世的開頭就是它的下一版(正常停);讀不出、超過單篇大小上限、不是嚴格 UTF-8 → 判不了(設計審 r2 正確性席、邊界席:原稿把三種 None 混在一起);
   - 工作目錄裡還沒提交的行、淺層 clone(`_git_is_shallow`)、partial clone(設定了 `extensions.partialClone` 或有 promisor 遠端——讀舊版本可能去網路抓,跟「不呼叫網路」衝突,設計審 r2 邊界席)→ 判不了,整段不往回查;
   - git 失敗、超過預算、那一版的樹或圖譜建不起來 → 判不了。
3. **怎麼查**:
   - 起點版本:`drift scan --at <提交>` 就是那個提交;不帶 `--at` 從 HEAD 開始。
   - 提交清單:`_lens_git(root, "-c", "core.quotePath=false", "log", "--first-parent", "--format=%H", <起點>, "--", ":(literal)<路徑>", binary=True, timeout=<剩餘預算與 20 秒的較小值>)`——路徑用 git 列樹時的原樣路徑(`_nodehome_list` 的原樣那份,不是 NFC 後的),`:(literal)` 讓檔名裡的 `[`、`*` 不被當樣式(設計審 r2 三席:原稿說走 `_nodehome_git`,它沒有 `-c`、沒有逾時參數、也不釘字面路徑)。
   - 每一版的筆記內容:`_nodehome_cat_blobs_capped` 批次讀,單篇上限照既有、總量上限 32 MiB(超過就判不了);逐版用同一支抽取(`_probe_lines`)找同一條。
   - 找到這一世的第一版後,在那個提交的樹與圖譜上用同一支 `_drift_probe_line` 判一次(圖譜用 `_drift_tree_env`,同 `drift scan --at` 讀某提交圖譜的做法)。
4. **資源**:只對「條件已經成立」的回頭條件查(含已表態的;RULE 撤除條件不查),最多查前 20 條,其餘標「判不了(超過上限)」;每個不同的寫下時提交建一次樹與圖譜,判完那一條就丟掉、不留快取(設計審 r2 邊界席、正確性席、通才席:不帶路徑的 symbol/test 在每個提交都要讀整份程式語料,共用的列樹快取上限是 8,不能靠它);吃 scan 既有的時間預算,排在本來的評估之後。
5. **結果與呈現**:成立 → 標「寫下時就已成立(提交 <短碼>)」;不成立 → 不標;判不了 → 標「判不了寫下時成不成立(原因)」。照既有「先前表態」那行的呈現(`_drift_prev_ack_line`),另起一支 `_drift_born_line` 印在那條發現底下(設計審 r2 架構對齊席);`--json` 的發現多一個欄位 `born`,形狀固定是物件:`{"commit": 短碼}` 或 `{"unknown": 原因}`,不標就沒有這欄;判不了留在發現自己的欄位裡、不搬進 `problems`。呼叫點在 `cmd_drift_scan` 拿到 `_drift_probe_scan` 的發現之後。已表態的照樣標。原稿標記裡的「從沒提醒過」拿掉——側分支、改名、拆篇時這句話說得比查到的強(設計審 r2 邊界席)。doctor Z 段不評估條件,不動。
6. **推送判定不改**:新寫的已成立條件推送時本來就擋;本案只補 scan 看存量。

## 實務隱患

- **繞過**:`when-gone` 寫一個本來就不存在的字串,推送時被點名「已經成立」——作者可以表態照留繞過;這是明寫的動作、留在表態檔,不另擋。
- **效能**:`when-gone` 帶字串時讀一支檔(同帶路徑的 symbol,有預讀);scan 往回查每條成立的條件一次 `git log`(只在單一筆記路徑上)、那篇的歷史版本一次批次讀、每個不同提交建一次樹與圖譜;成立的條件通常是個位數,吃 scan 既有預算,超過就標判不了(設計審 r1 正確性席實量:單次 git log 約 0.05 秒、建一次圖譜約 0.19 秒);最多查 20 條、每個提交的樹與圖譜判完就丟。推送判定的成本不變。
- **併發**:只讀 git 物件;scan 不寫帳。
- **回滾**:還原本案的提交:`when-gone` 變成「不認得的條件鍵」——新寫的提交時被擋、已寫的 scan 列成寫錯的條件、推送判定不評估(既有對寫錯條件的處理);scan 不再標寫下時成立。沒有資料要收。
- **相容**:新鍵只是多認一種寫法,既有四種鍵的判定不變;`--json` 多一個可省略欄位,讀的人沒有靠它。消費專案要 `lumos update` 之後才認得 `when-gone`,更新前寫了會被舊版擋成「不認得的條件鍵」。
- **跨環境**:淺層與 partial clone 不往回查(〈做法〉2.2);往回查用 `git log` 只取提交編號、版本內容用 `cat-file` 批次讀,本機的外部差異與文字轉換設定不影響;本機與 CI 同一支判定。
- 已排除:金流:只讀筆記與 git 物件
- 已排除:對外送出:不呼叫網路(partial clone 讀舊版本可能去網路抓,所以 partial clone 不往回查,〈做法〉2.2)
- 已排除:不可逆:只決定擋不擋、列不列,還原提交就回去

## 天花板

1. 提交時不評估條件:新寫的已成立條件要到推送才被點名。
2. 往回查只看這一篇筆記自己的歷史、只沿主幹:筆記改過名或拆過篇,找到的是改名後那一版;在側分支寫下再合併的,算成合併那一版——寫下當時的狀態可能看不到(會標成那一版的判定)。
3. `when-gone` 只認字面字串與原路徑:改寫成同義寫法、或檔改名搬家,都算「不再出現」,條件會提早成立——推送時會被點名,作者挑字串時要挑會真的消失的那段。
4. 字串不能含 `]`、換行、反引號;要比對的程式片段含這些字元時,挑片段裡不含它們的那一段。
5. 工作目錄模式的 scan 照工作目錄看「在不在」:sparse-checkout 沒拉下來的檔、還沒暫存的刪除都算消失;要看提交的狀態用 `--at`。
6. 淺層與 partial clone 不往回查;同一篇兩行條件標記一樣時不往回查。
7. 只用嚴格 UTF-8 讀:Big5 這類舊編碼的程式檔,帶字串的 `when-gone` 永遠判不了(推送時判不了算要處理,會被點名)。
