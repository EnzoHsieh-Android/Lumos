severity: blocker

- [blocker] S2 的第四道檢查在時序上不可能執行——嚴重度對帳是「已入帳之後」的稽核工具,不是「入帳之前」的收貨檢查
  引句:「席位對帳 → ★嚴重度對帳(`severity-check`,既有的第四道收貨)★,算出凍結快照的指紋」
  blocking: 是
  why: 讀了它的 CLI 定義與核心函式。這條既有指令吃的是迴圈、輪次、席名座標,拿去比對帳本裡已經存在的一筆帳;找不到帳列就直接擋下 rc2。但 S2 的產出是「印一條記帳命令給人填」,也就是帳這時候還沒記。照字面把它排在印出記帳命令之前,每一次收貨都會在第四步撞上帳列不存在。這不是邊界情況,是主線必炸。實作者要嘛照抄踩雷,要嘛自己發明繞過既有介面的做法——那就不是「既有的第四道」,而是重寫一份判準,直接牴觸 spec 自己「判準一個字都不動」的界線。

- [major] 前面幾步任一失敗時,已經寫出去的正規化檔案怎麼處理,文件完全沒交代
  引句:「★這條指令本身不寫檔★;會寫檔的只有它第一步呼叫的正規化(見 S1)。」
  blocking: 是
  why: spec 只講清楚誰會寫檔,沒講寫出去之後下游失敗要不要回滾。而「保留原始檔,轉換後另存,不覆蓋」講的「不覆蓋」對象是原始檔,對「正規化輸出本身能不能被重跑覆蓋」隻字未提。猜可覆蓋→人修完重跑,舊的半成品被悄悄換掉,事後看不出試了幾次;猜不可覆蓋→第二次重跑撞檔案已存在,實作者得自己發明命名規則,否則第一次修正重跑就卡死。

- [major] 「只做三件格式轉換」對真實語料的覆蓋率不足,實際挑了八個以上既有迴圈比對過
  引句:「做且**只做**三件格式轉換」
  blocking: 是
  why: 不是推理,是直接用既有解析器唯一認得的格式掃過所有既有席報告,對不上的有幾十份。實際打開讀過的例子:①有一份全文用行內方括號記法,根本沒有任何一行獨立的嚴重度宣告;②一份用全形破折號分隔;③一份用斜線分隔(spec 第三條轉換大概想接住這種,但沒給任何文法,只看過一種寫法的實作者很可能漏掉另外兩種變體);④稽核報告根本是另一種文類,沒有嚴重度、引句、位置任何一個欄位。這些都是今天就存在、隨時可能被拿來跑的真檔案。

- [major] repo 裡「已經正規化」的產物,彼此對「本專案格式」長什麼樣有兩種互不相容的既有慣例——spec 沒有定案哪個才是目標
  引句:「把 `quote:` 標籤改成本專案的引句格式」
  blocking: 是
  why: 那支臨場腳本的輸出把位置標籤改名、用全形冒號、外層固定用一種括號但把內容裡原本的同款括號全部換成另一種;而同一批既有正規化產物保留原標籤與半形冒號、內外層都可以是同一種括號。兩種「已規範化」的產物長得不一樣,spec 卻假設世界上只有一種目標形狀。實作者選哪一種,都會跟另一半既有語料對不上——正是 spec 開篇說的「六份實作就是六種漂移」在收斂之後又長出第七種。

- [major] 重跑與命名的決定點文件都沒交代,不同猜法會導致不同且都有風險的結果
  引句:「**保留原始檔**(`.raw`),轉換後另存,不覆蓋。」
  blocking: 否
  why: ①同一份報告跑兩次,原始檔每次都用當下來源覆蓋還是只在第一次建立?若每次覆蓋,重跑三次後真正的第一手原始稿就消失了——正是 spec 控訴臨場腳本的同一類問題換了個位置發生。②正規化輸出沒有命名規則,兩次落到同一路徑要覆蓋還是拒絕,文件沒說。③印出記帳命令後,材料若在人執行前又被重跑一次,印出的指紋就跟人最終貼上去時的內容不同步,既有的「報告與帳面指紋不符」會在完全合規的操作下觸發,spec 沒有任何鎖定或版本標記機制去防。

- [minor] 「依序跑」沒有講四道檢查是遇錯即停還是全部跑完再彙總
  引句:「依序跑:正規化 → 引句錨定 → 檔案行號核對 → 席位對帳」
  blocking: 否
  why: 遇錯即停的話,人只會看到最早失敗的那一關,永遠不知道後面的狀況;全部跑完的話,又需要另外設計「部分失敗時還要不要印記帳命令」,spec 對此完全沒表態,兩種選擇會被各自選一種,又是一個之後才發現的分歧點。
