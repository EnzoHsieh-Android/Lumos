severity: blocker
- [blocker] 指定複用的嚴重度解析器根本讀不到正規化器必須轉換的表頭格式
  引句:「嚴重度的解析必須複用既有的 `_report_severities`」
  blocking: 是
  why: `_report_severities` 只接受整行 `severity: clean|minor|major|blocker`；表頭型嚴重度正是尚未具備這種宣告的輸入。照字面實作不是無法轉換，就是仍得另寫表頭解析器，直接違反「不得自寫第二份」的核心合約。`_quote_norm` 同樣只正規化已抽出的字串，不會辨認 `quote:` 標籤或產生 `引句:「…」` 語法。

- [blocker] 編排順序要求在記帳前執行一個只能讀既有帳列的嚴重度對帳
  引句:「依序跑:正規化 → 引句錨定 → 檔案行號核對 → 席位對帳 → ★嚴重度對帳」
  blocking: 是
  why: 現有 `severity-check` 不吃待收報告路徑，而是用 loop、round、auditor 定位已寫入的帳列，再讀帳列中的 report 與 severity；本設計又明定編排指令不記帳。照此順序，新報告尚無帳列，第四道必然找不到對象而 rc2，整條編排無法成功。

- [blocker] 圖譜攔截第一條對照把「報告必填」誤當成「新收貨線必跑」
  引句:「不跑收貨線就記不了帳——入口是強制的,不是選擇性的」
  blocking: 是
  why: 現有記帳只強制 `--report`，並不強制報告曾經通過新正規化或新編排子命令；已有合法獨立 severity 行的原報告可以直接記帳，完全繞過收貨線。因此新入口仍是選擇性的，重現停案所指「驗證只在有人選擇跑時才發生」；依文件自己的判準，這條對照不成立即為 blocker。

- [blocker] 保留下來的 `.raw` 原檔不會進現有回放凍結閉包
  引句:「本案動的就是這兩者本身,**不新增閉包外的檔案類型**」
  blocking: 是
  why: 帳列只存一個 `report_path/report_sha256` 與一個 snapshot；若 `--report` 指向轉換後檔案，旁邊新增的 `.raw` 沒有欄位、指紋或閉包收集入口。回放只能證明轉換結果未被改，不能重現原投稿或稽核轉換是否刪改內容，第四條對照字面不成立。

- [major] 無嚴重度報告的退件只規定退出碼，沒有規定退回原審查席而非由編排者補寫
  引句:「找不到任何嚴重度宣告就退件(rc2=本專案 CLI 的「擋下」退出碼」
  blocking: 否
  why: 真實審查席漏寫 severity 時，工具只會擋住記帳；文件沒有交代由誰修、如何保留作者身分或如何重新收件。照字面操作，最短解會是編排者在報告補一行，將原本可辨識的腳本代填變成難以辨識的人工作者冒名，確實把問題從工具推給人。

- [major] S3 同時要求缺家族欄可相容退讀，又要求必要鍵檢查，舊派工單的處置未定義
  引句:「席位對帳先讀家族欄、讀不到才退回猜名字」
  blocking: 否
  why: `_roster_dispatch_entries` 現在回傳 auditor 字串，`_roster_observe` 再猜家族；要優先使用 family 必須改回傳契約。若「必要鍵」包含 family，舊派工單會被判壞並跳過；若不包含，它又不是必要鍵。未裁清前，實作者可能讓舊迴圈從原本的 unknown 提醒變成「沒有派工快照」或直接按顯式但語意不同的 family 靜默錯算。

- [minor] 把 severity 留給人填是可機算資料，保留了高報與漏改占位符的新錯誤面
  引句:「印一條**只留嚴重度與處置給人填**的記帳命令」
  blocking: 否
  why: 正規化成功後最高 severity 已能由共用解析器確定，屬忠實轉錄而非人工判斷；現有寫入端對低報會擋，但對高報只提醒並放行。工具若仍留 `<severity>` 給人，漏改會使命令失敗，填高則會污染後續閘判定。相較人自行拼整條命令，路徑、指紋與固定欄位錯誤會減少，但嚴重度錯誤只是被搬到模板最後一步。
