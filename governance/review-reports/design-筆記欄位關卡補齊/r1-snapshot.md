# 筆記欄位關卡補齊_計劃

PRIOR-ART: 沿用自家已驗過的兩個形狀,不自建:「每支檔有家」的「只擋新違規、上線點之前的算舊帳」與「提交前只讀提交內容」(它的讀取層已經有現成函式);推送前把碰到的筆記清單傳給健檢的管道(`--touched-from`,預告合約那段已在用)。欄位規則本身都是 lint 既有的,這次只是讓推送前再跑一次。
RETIRE-IF: ①推送前這段連續 8 週零次擋下、且提醒段也零筆 → 降成只在 CI 跑(提交前的關已經足夠);②它擋下的案例有一半以上事後判定是誤擋 → 回退成只提醒,重看規則。

## 一句話

把「只在提交前查」的筆記欄位規則補到推送前與 CI,提交前改成讀提交內容,並補上盤點發現沒人查的幾個欄位;**只擋這次碰到的筆記,別的只提醒**。

## 做法

### 一、推送前與 CI 重跑 lint 會擋的那幾條

- 健檢新增一段:對每一篇筆記跑 lint 裡「錯誤」等級的規則(不跑提醒等級,避免重複嘮叨)。
- **有碰到清單時**(推送前掛鉤本來就傳;CI 改成用推送前的起點算出同一份清單):清單裡的筆記有錯誤 → 擋;其他筆記有錯誤 → 只提醒並列出篇名。
- **沒有碰到清單時**(例如 pull request 事件拿不到起點):全部只提醒。寧可少擋,不在拿不到範圍時對整個圖譜擋。

### 二、提交前 lint 改讀提交內容

- 提交前掛鉤跑 lint 時,讀的是這次要提交的內容(提交索引),不是磁碟上的檔——跟「每支檔有家」的讀法一致。
- 手動跑 `lumos lint <節點>` 維持讀磁碟(那是在看自己正在寫的東西)。

### 三、補上沒人查的欄位

以下都只擋**新違規**:這一版有、上一版沒有(提交時上一版=目前最新的提交;推送時=推送的起點;這一版才新建的筆記整篇都算新)。上一版就有的違規只提醒。
為什麼不用「某個日期之後建立的筆記」:這幾條抓的多半是筆記裡的子項目(某條決策、某項 about_code),子項目可以在舊筆記裡新加;看建立日的話,舊筆記裡新犯的錯永遠只會被提醒(首輪前掃指出)。

- `status`:四種類型必填(現在沒填完全不擋)。
- 日期格式:`created`、`updated`、`date`、決策的 `decided` 與 `ended` 必須是年-月-日(現在只擋加引號)。
- 決策的 `valid`:只能是 true 或 false(現在寫成 no、0 會被當成有效)。
- `about_code`:每一項要是這一版提交內容裡存在的檔(現在只有用指令寫入時驗,而且寫入時驗的是磁碟上有沒有,不是版本控制裡有沒有)。寫入指令刻意維持只驗磁碟:常見做法是先建節點再把程式檔加進提交,寫入當下就要求進版控會卡住;到提交時兩者都在提交內容裡了。
- 計劃(專案筆記名稱以「_計劃」結尾)必須有 `lands_in`(現在兩道關都不查)。用檔名不用 `type: project`:研究筆記(「_調研」)也是 project 但不要求落點;設計審的落點那一步用 type 判,是因為它只跑在已經送審的計劃上。兩套刻意不同。

另一件寫入當下的:`lumos set responsibility` 也要求至少 10 個字(現在只有新開節點時要求)。

### 順手修

- 那一篇 `about_code` 寫了筆記路徑的 Issue,改成連結。

### 不在本案範圍

- 沒有程式讀的三個欄位(`signed_off`、`phases`、`commit`)要不要拿掉,另案看。
- 決策 `superseded_by` 指向的目標存不存在、`decisions.id` 唯一性:健檢已有提醒段,本案不升級。

## 條款

- [S1] 當推送前健檢拿到碰到的筆記清單,清單裡的筆記有 lint 錯誤等級的問題時健檢應擋下,清單外的筆記有同類問題時應只提醒並列出篇名 [test:t_doctor_lint_errors_block_touched_only]
- [S2] 若健檢沒有拿到碰到的筆記清單,則 lint 錯誤等級的問題應全部只提醒、不影響退出碼 [test:t_doctor_lint_errors_warn_without_touched]
- [S3] 當 CI 由推送事件觸發且有推送前的起點,CI 應以起點到本次提交的改動算出碰到的筆記清單並交給健檢 [test:t_ci_passes_touched_notes_to_doctor]
- [S4] 當提交前掛鉤檢查一篇部分加入提交的筆記,lint 應判的是提交索引裡的內容而不是磁碟上的內容 [test:t_precommit_lint_reads_index]
- [S5] 若系統、專案、驗證、問題筆記這一版沒有填 status 而上一版有填或這篇是新建的,則應報錯誤;上一版就沒填的應只提醒 [test:t_lint_status_required_new_violation]
- [S6] 若筆記的建立日、更新日、日期、決策日期或結束日這一版不是年-月-日格式而上一版的同一個值是(或是新加的),則應報錯誤 [test:t_lint_date_fields_format]
- [S7] 若一條決策的 valid 這一版不是 true 或 false,且這條決策是新加的或上一版的值是 true/false,則應報錯誤 [test:t_lint_decision_valid_boolean]
- [S8] 若筆記的 about_code 有一項不在這一版的提交內容裡,且這一項是這一版新加的,則應報錯誤;上一版就有的只提醒 [test:t_lint_about_code_must_be_tracked]
- [S9] 若名稱以「_計劃」結尾的專案筆記是這一版新建的、或上一版有 lands_in 而這一版拿掉了,且這一版沒有 lands_in,則應報錯誤 [test:t_lint_plan_requires_lands_in]
- [S10] 當 `lumos set` 寫 responsibility 且去掉空白後不到 10 個字,寫入應被擋下、檔案不變 [test:t_set_responsibility_min_length]
- [S11] 若讀不到上一版(新建的筆記、改名、或上一版讀取失敗),則這一版的違規應全部當成新違規(從嚴) [test:t_lint_new_violation_when_no_previous]

## 回退

- 一、健檢新段落是一個獨立的段,回退=拔掉那段呼叫與 CI 的清單參數。
- 二、提交前改讀提交內容:回退=掛鉤改回呼叫原本的 lint。
- 三、新欄位規則都走「新違規才擋」:回退=把新違規判定改成一律回「舊違規」即全部降成提醒,不必拔程式。

## 實務隱患

- 消費專案:健檢在它們那邊也跑。拿不到碰到清單就全部只提醒、新規則只擋這一版才出現的違規,兩道保險都是為了不一次卡住它們:舊筆記裡原本就有的違規不管碰不碰到都只提醒。
- 提交前讀提交內容:要處理「這篇筆記在提交索引裡被刪掉」與「改名」,讀不到時退回讀磁碟並照舊判(不因讀取失敗而放行)。

## 誠實界線

- 只擋「碰到的筆記」:舊的壞筆記只要沒人碰就一直只是提醒;靠 REVISIT 回頭看提醒量決定要不要升級。
- `about_code` 查的是版本控制裡有沒有這支檔,不查它是不是程式檔、是不是真的歸這篇管。
