## F1 決策沒有強制 id,S6/S7 沒定義「同一條決策」怎麼跨版本配對

severity: blocker
blocking: yes

引句:「若一條決策的 valid 這一版不是 true 或 false,且這條決策是新加的或上一版的值是 true/false,則應報錯誤」
引句:「決策 `superseded_by` 指向的目標存不存在、`decisions.id` 唯一性:健檢已有提醒段,本案不升級」

S6(日期)、S7(valid)都要判「這條決策」在上一版是不是同一條、是不是新加的,前提是能把一份筆記裡的 decisions 陣列跟上一版的 decisions 陣列逐條配對。配對只能靠 `id`,但 `id` 不是必填欄位——`parse_decisions`(`scripts/lumos:12218`)不驗 id 存在與否,`_max_decision_id`/`pre_ids` 那段(`scripts/lumos:14216`)本來就用 `if d.get("id")` 在防「沒有 id」這件事發生。實測本 repo 現在就有 4 條決策沒有 id,例如 `docs/lumos-toolchain-knowledge/Issues/共用工作目錄的未追蹤檔讓全套測試假紅.md:25-33` 那條(`content`/`decided`/`valid` 都有,沒有 `id`)。

沒有 id 的情況下,配對只能退回用陣列順序或內容比對:陣列順序配對——在同一條前面插入一條新決策就會讓後面每一條的 index 全部平移,舊決策被誤判成「新加的」而從嚴擋下;內容比對——只要 content 文字有任何改動(哪怕只是順手改個字)就配不上舊條目,一樣被誤判成新決策。兩種退路都會讓「該只提醒的舊決策被擋下」或「新決策被誤認成舊決策而放行」,而 spec 完全沒交代要用哪一種,也沒有規定 id 這次要一起變成必填。

## F2 S6/S7 逐字讀法會讓「已經壞掉、這次又被改成另一個壞值」的欄位永遠只提醒,擋不到它

severity: blocker
blocking: yes

引句:「若筆記的建立日、更新日、日期、決策日期或結束日這一版不是年-月-日格式而上一版的同一個值是(或是新加的),則應報錯誤」

條件是「上一版的同一個值是年-月-日格式」或「這一版是新加的」,兩者皆非才會落到只提醒。推導:一篇筆記的 `updated` 上一版就已經是壞格式(例如手誤打成 `2026-13-99`),這一版又被改成另一個壞格式(例如 `2026-14-88`,`updated` 幾乎每次寫入都會被程式自動 bump,見 `scripts/lumos:14036` `ended` 缺則自動補今日並同步 bump 頂層 updated 那段)——上一版的值不是合法格式(第一個條件不成立),這個值本來就存在不是新加的欄位(第二個條件不成立)→ 兩個「應報錯誤」的前提都不成立,只能落到「只提醒」。也就是說,一個欄位只要曾經壞過一次,之後不管改寫成什麼壞值、改幾次,都再也不會被判成新違規,即使每次改寫都發生在「這次推送碰到的筆記」裡。這跟做法三開頭「以下都只擋新違規:這一版有、上一版沒有」的目標矛盾——這一版明明多了一個上一版沒有的(不同的)壞值,卻因為「上一版也壞」而被排除在擋下範圍外。S7 的 valid 欄位是同一種句式,同一個問題:上一版 `valid: no`、這一版改成 `valid: "0"`,一樣不會被擋。
