# r1 收貨紀錄(首輪前掃)

前掃由一個便宜代理(sonnet,唯讀)用固定四類清單掃計劃,原報告存 `r1-preflight-sonnet.md`。4 條 HIT,編排者逐條開程式重現後才改真檔;沒有一條動到核心裁定,所以直接改、記在這裡,席位可以覆核推翻。

## HIT-1 未定義的詞:「上線日」——HIT
- 重現:`grep -n "上線日" 計劃` 有 9 處,沒有一處說它是哪一天、怎麼算;`scripts/lumos:4855` 的 `_ENUM_CUTOFF` 是寫死日期,`scripts/lumos:22070` 的 `_nodehome_golive` 是逐專案動態算,兩種先例形狀不同。
- 處置:跟 HIT-2 一起解——拿掉「上線日」,改成「只擋這一版才出現的違規」,不再需要這個詞。

## HIT-2 範圍自相矛盾:用筆記建立日判新舊,舊筆記裡新犯的錯永遠只提醒——HIT
- 重現:決策、about_code、lands_in 都是筆記裡的子項目,可以在建立很久之後才加;`created` 不會變。照原條款,一篇 01 月建立的筆記今天加一條 `valid: no` 的決策,永遠只提醒。
- 前(做法三開頭):「以下都只對『上線日之後建立的筆記』算錯誤、之前的算提醒(建立日沒填或寫壞的,當成新筆記從嚴)」
- 後:「以下都只擋新違規:這一版有、上一版沒有(提交時上一版=目前最新的提交;推送時=推送的起點;這一版才新建的筆記整篇都算新)。上一版就有的違規只提醒。」並附為什麼不用建立日。
- 條款 S5–S9 同步改成「這一版有、上一版沒有」;S11 由「建立日壞了當之後」改成「讀不到上一版就全部當新違規(從嚴)」。

## HIT-3 範圍自相矛盾:「計劃」的範圍跟設計審落點那一步不同——HIT(補說明,不改判準)
- 重現:`scripts/lumos:17948-17950` 落點那一步用 `type == project`;`Projects/TypeSafe-Jev_調研.md` 是 project 但檔名不是 _計劃。
- 前:「計劃(專案筆記名稱以『_計劃』結尾)必須有 `lands_in`(現在兩道關都不查)。」
- 後:同句後補「用檔名不用 type: project:研究筆記(『_調研』)也是 project 但不要求落點;設計審的落點那一步用 type 判,是因為它只跑在已經送審的計劃上。兩套刻意不同。」

## HIT-4 機械宣稱驗語意:寫入驗的是磁碟,不是版本控制——HIT
- 重現:`scripts/lumos:13652-13680` `_about_code_path` 用 `target.is_file()`,不呼叫 git。
- 前:「`about_code`:每一項要是版本控制裡存在的檔(現在只有用指令寫入時驗)。」
- 後:「`about_code`:每一項要是這一版提交內容裡存在的檔(現在只有用指令寫入時驗,而且寫入時驗的是磁碟上有沒有,不是版本控制裡有沒有)。寫入指令刻意維持只驗磁碟:常見做法是先建節點再把程式檔加進提交,寫入當下就要求進版控會卡住;到提交時兩者都在提交內容裡了。」
