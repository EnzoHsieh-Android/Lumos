## 編排者自己重現的(≥major 一律自己查過才折)

1. **「預設關 = 行為一行不變」是不是假的**(兩席獨立判 major)。
   用固定語料(三篇假筆記、五種查詢)跑 base vs 這批,**輸出唯一的差異就是提示措辭那兩行,
   結果行一字不差**。所以兩席都對:那句宣稱按字面讀是錯的,只是把「行為」窄化成「結果集」才成立。
   **注意我第一次比對用的是真實圖譜,結果 diff 出一行差異——那是我自己改了計劃筆記的內容造成的,
   不是行為變。換固定語料才乾淨。**
2. **複用既有切詞器會不會產出不同結果**(架構席 blocking)。十題對照
   (含日文混寫、ASCII 夾雜、空字串、重複字、擴充 A):**兩種寫法輸出完全一致**,
   所以複用的路本來就走得通,我只是沒走。
3. **長查詢會不會慢**(通才席 major)。本庫 441 篇自己量:
   10 字 0.55s / 30 字 0.87s / 50 字 1.18s / 100 字 1.94s / 300 字 5.13s
   ——跟該席量到的同一個量級(它另外量到 3000 字 47.9s)。**HIT。**
4. **零寬字元**(通才席 minor):夾一個 U+200B,修前拿到沉默的 0 筆(連提示都沒有),
   修後正常進回退。**HIT。**
5. **重複建議**(通才席 minor):全字對零覆蓋時,「加空白」修前印 2 次、修後 1 次。**HIT。**

## ★席位的推論我推翻了一半,但它的判斷是對的★

通才席指出設計文件裡「字元域放寬到假名 → 14 過 / 7 紅」那個數字對不上它的獨立重現(它量到 20/1),
並推測我改的是**共用的** `_RANK_CJK_RE`、造成排序被連帶擾動。

**它的推測不對**:我那次的探針只動 `_cjk_bigrams` 自己那顆正則。真正的原因是
**跳脫字元被 shell 吃掉**,正則變成匹配字面反斜線,所以那 7 條紅是探針壞掉的雜訊。

**但它「這張表不能照單全收」的判斷完全正確**,而且比它想的更嚴重——重跑之後發現,
折入架構席意見(改用共用切詞器)之後,**放寬本地正則根本沒有任何作用**:
字元域由那支共用切詞器把關。所以那一列現在是綠的,而且那是設計對了,不是測試弱。
真正有殺傷力的探針是「繞過共用切詞器」,那個會翻紅。

## ★探針這件事,我今天錯了三次,三種形態★

1. **打錯層**:改函式簽名的預設值,測試照樣全綠——CLI 是顯式傳旗標的。
2. **探針自己壞掉**:上面那條,跳脫被吃掉。
3. **斷言沒咬到目標層**:零寬那條我做了三層防護,而斷言只驗得到最外層的閘
   ——拆掉「切字對前剝零寬」那一層,測試照樣綠。補了一個「零寬把漢字段切成兩個太短半段」
   的現場之後才咬得到。

**收束**:探針沒翻紅時要查三件事——打到哪一層、探針自己有沒有壞、斷言咬的是不是目標層。
不要直接下結論說「測試沒鑑別力」,也不要直接下結論說「功能是對的」。
