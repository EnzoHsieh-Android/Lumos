- [major] `--cjk-loose` 沒有查詢長度/字對數上限,長問句會讓 CLI 掛住數十秒。
  引句:「★這個數還沒有實測依據★」
  位置:`scripts/lumos`(`_cjk_bigrams` 無長度上限)、預檢迴圈、主迴圈
  blocking:是
  why: 對凍結快照、本 repo 441 篇真實圖譜實測(`--cjk-loose --files-only`):30 字 0.83s / 50 字 1.14s / 100 字 1.92s / 200 字 3.50s / 500 字 8.19s / **3000 字 47.88s**。機制:字對數約等於 query 長度,預檢對每個字對、每篇筆記做一次子字串比對,主迴圈又對每一行再比一次——複雜度 O(字對數 × 篇數 × 篇幅),沒有任何截斷。而這支旗標設計上就是給自然問句用的,50~150 字的複雜問句已落在 1~4 秒這個「覺得卡住」的區間。設計文件的「實務隱患」段列了雜訊風險、兩態分化、觸發下限,唯獨沒有列這條,是真的漏掉的風險,不是「量測完才裁」範圍內的東西——這條不需要對照組評測,是純粹的演算法複雜度問題。

- [minor] U+200B 零寬空白讓 `--cjk-loose` 與「加空白」提示同時靜默失效。
  引句:「_ANY_SPACE_RE = re.compile(r"\s|[\u3000\u00a0\u2000-\u200b]")」
  位置:`scripts/lumos`
  blocking:否
  why: 這個正則把 U+200B(零寬空白,常見於行動裝置輸入法或網頁複製貼上,肉眼不可見)也算進「有空白」。但 Python 的 `str.split()` 不把 U+200B 當空白(`"​".isspace()` 為 False,實測)。結果是:一串含 U+200B 的無空白中文,`_fb_terms` 仍是單一詞(多詞回退不退),而 `_ANY_SPACE_RE.search()` 又誤判成「已經有空白」擋掉字對回退的閘,兩條路同時失效。實機重現:同一句「檢索優化測試字串占位補長度」,不含 U+200B 時正常找到 1 篇;插入一個 U+200B 後同一指令回傳空結果,連提示都被同一個判準吃掉——使用者拿到完全沉默的 0 筆。
