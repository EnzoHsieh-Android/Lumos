# 派工鏡頭可指定目標repo_計劃

> 白話:派審查席時,掛鉤會自動把「這次改動牽連到的圖譜筆記」貼進派工詞。它一律在「會談開在哪個資料夾」那裡算。全域規則要求每份工作開獨立的 git 工作樹,於是計劃常常只存在別的工作樹裡,掛鉤在會談目錄找不到,只附一行「沒附」。同一個 repo 的工作樹共用同一份 git 物件庫:計劃提交之後,在會談目錄就能用「提交編號:計劃路徑」把它讀出來。改成:設計審的 `LUMOS-SPEC:` 可以寫成 `<提交編號>:<計劃路徑>`,lumos 在會談 repo 裡從那個提交讀計劃,其餘照舊。不去別的目錄跑 git,不新增信任機制;完全不同的 repo 照舊不支援,附說明行。

## 緣起

- 2026-10-13 後端示範:會談開在 lumos 工具鏈,審的是示範 repo `order-demo` 的分支,派工鏡頭算不出牽連筆記(只附了說明行)。2026-10-14 夜裡更普遍:全域規則要求每個工作開獨立的 git 工作樹,我在三個工作樹各開一份計劃、派了十幾席設計審,計劃只存在那些工作樹裡,掛鉤在會談目錄找不到,所有席都沒拿到固定席節點。出處:使用者 2026-10-14 列的示範改進第 4 條;當晚的席報告都寫「派工尾端沒有附固定席節點」。
- 舊裁定:[[Projects/派工鏡頭跨repo不再靜默_計劃]] 的 WHY 行寫「不選:標記行加 repo 路徑讓掛鉤改去那裡算(標記行文法要改、派工詞的自由文字會變成掛鉤去跑 git 的路徑,先不開這個口;說明行給繞法即可)」。**本計劃不推翻它**:第一、二輪設計審試過讓 `LUMOS-REPO:` 指定任意路徑,再用權限位元(r1)或登記清單(r2)判信不信,兩輪共 51 條發現,幾乎全出在「讓派工詞的文字決定去哪裡跑 git」這一層(`commondir` 指到別處、登記清單誰能寫、拒絕說明本身誘導登記、圍欄裡的標記被靜默忽略、被拒時取角色卡會用錯的樹、會談本身是工作樹時怎麼列工作樹)。這正是舊裁定擔心的口。
  - 改走的路:痛的是「同一個 repo 的另一個工作樹」(當晚十幾席都是這種),而工作樹共用物件庫,讀提交裡的計劃只要在會談 repo 跑 git,不碰派工詞指到的任何目錄。示範 repo 那種完全不同的 repo 一晚只出現一次,照舊附說明行、手動貼。

PRIOR-ART: 代碼審那條路已經是這樣:`LUMOS-IMPACT:` 寫完整提交編號,工作樹共用物件庫,在會談目錄就算得出別的工作樹的提交(派工範本已要求寫完整提交編號、不寫 HEAD)。設計審照同一個道理,把計劃路徑換成 git 原生的 `<rev>:<path>` 寫法(`git show` 本來就收這種寫法),不自創文法、不新增信任機制。借用,不自建。
RETIRE-IF: Claude Code 在派工事件帶出子代理的工作目錄(會談目錄與工作目錄不再可能錯開),或連續 8 週派工詞裡的 `LUMOS-SPEC:` 都沒有用到提交編號寫法——拿掉這個寫法。
REVISIT:2026-12-15 數一次掛鉤事件裡 `LUMOS-SPEC:` 帶提交編號寫法的次數與失敗代碼分布,照 RETIRE-IF 判。

## 做法

1. **`LUMOS-SPEC:` 多收一種寫法**:值是 `<提交>:<計劃路徑>` 時(`<提交>` 是 7–40 碼十六進位,冒號後是 repo 根起算的相對路徑、不以 `/` 開頭),當成「這個提交裡的這份計劃」;其他值照現在當工作樹路徑。只用十六進位,不收分支名:分支名可以含冒號以外的各種字,`main:docs/…` 這種寫法跟 Windows 磁碟代號、帶冒號的檔名混在一起判不準,十六進位才沒有歧義。
   - 掛鉤不改標記的找法(`find_spec_marker` 照舊),只把值原樣交給 lumos;掛鉤自己不解析、不跑 git。
2. **lumos `dispatch-lens --spec` 認得這個寫法**:在 `--repo`(照舊是會談目錄)找到的 repo 裡:
   - 用 `_lens_git` 跑 `rev-parse --verify --quiet <提交>^{commit}` 確認提交存在,再 `show <提交>:<路徑>` 讀計劃內容(`cat-file -s` 先查大小,超過 1MB 不讀,跟工作樹那條路的上限同值;沒有上限就補一個)。
   - 路徑先做跟工作樹那條路相同的檢查:不得含 `..` 段、不得是絕對路徑、要在 `docs/*-knowledge/` 底下(計劃一定在圖譜裡),不合就擋。
   - 計劃提到的程式檔「存不存在」改用 `cat-file -e <提交>:<檔>` 判(檔在那個提交裡存在才算),impact 照現在在會談 repo 的主線算。
   - 計劃直接連結的節點照現在從會談 repo 的圖譜讀;只在那個分支上新開、主線還沒有的節點,列名並標「主線還沒有這篇」,不當成錯誤。
   - 目標架構段(`_dispatch_lens_spec_arch_text`)讀的計劃內容換成從提交讀到的那份,宣告與節點照現在從 HEAD 讀。
   - 失敗代碼:提交不存在 `spec_rev_missing`、提交裡沒有這個路徑 `spec_missing`(沿用)、路徑不合 `spec_outside_repo`(沿用)、沒有圖譜 `no_knowledge`(沿用);這三個沿用的代碼在現在的工作樹那條路也印(現在不印,今晚十幾席因此什麼說明都沒拿到),`_dispatch_lens_fail` 說明裡的種數跟著改。
3. **掛鉤的說明行**:設計審那條路也印說明行(現在只有代碼審範圍那條路有),拿掉「只在有範圍時」的條件;值經 `_clean_field` 消毒後顯示。計劃在會談目錄找不到(`spec_missing`)而值不是提交編號寫法時,說明行加一條繞法:「計劃在別的工作樹時,先提交,再寫 `LUMOS-SPEC: <完整提交編號>:<計劃路徑>`」。
4. **範本與手冊**:`lumos-design-loop` 的 `templates.md` 在 `LUMOS-SPEC:` 那一行旁邊寫明:工作目錄不是會談目錄時,先把計劃提交,寫 `LUMOS-SPEC: <完整提交編號>:<計劃路徑>`;`lumos-code-loop` 的代碼審照舊寫完整提交編號(已經是這樣)。完全不同的 repo:照舊從開在那個 repo 的會談派席,或手動 `lumos impact` 貼固定席。
5. **記帳**:掛鉤事件 note 在用到提交編號寫法時記 `spec_rev`(成功)或 `spec_rev <失敗代碼>`,給 RETIRE-IF 量;這是對 [[Projects/派工鏡頭注入_計劃]]「不擋不驗不記不量」的有限鬆綁——只記這個寫法的結果,不記注入次數。
6. **不做**:不讓派工詞指定任意路徑或別的 repo(舊裁定照舊成立);不改 `LUMOS-IMPACT:` 的寫法;不支援分支名或 `HEAD~1` 這類相對寫法;不讀工作樹裡沒提交的改動(凍結快照本來就要先提交)。Codex 編排的 `--arm` 不在範圍內。

## 驗收條款

- [S1] 當派工詞有 `LUMOS-SPEC: <完整提交編號>:docs/x-knowledge/Projects/a_計劃.md`,而那份計劃只在另一個工作樹的那個提交裡時,掛鉤應在會談目錄算出並附上固定席節點(計劃提到的程式檔與直接連結的節點)。[test: t_dispatch_lens_spec_rev_from_other_worktree]
- [S2] 當提交不存在、提交裡沒有那個路徑、路徑含 `..` 或不在 `docs/*-knowledge/` 底下時,lumos 應分別回 `spec_rev_missing`、`spec_missing`、`spec_outside_repo`,掛鉤應附帶那個代碼的說明行,不應附任何節點。[test: t_dispatch_lens_spec_rev_failures]
- [S3] 當值不是提交編號寫法(工作樹路徑)時,行為應與現在相同;計劃在會談目錄找不到時,說明行應帶 `spec_missing` 與「先提交、改寫提交編號」的繞法。[test: t_dispatch_lens_hook_spec_fail_notice]
- [S4] 當計劃只連到分支上新開、主線沒有的節點時,應列名並標「主線還沒有這篇」,rc 照樣是 0。[test: t_dispatch_lens_spec_rev_branch_only_node]
- [S5] 讀提交裡的計劃時,lumos 應只在 `--repo` 的 repo 跑 git(假的 `_lens_git` 記錄每次呼叫的工作目錄,全部等於會談 repo 根)。[test: t_dispatch_lens_spec_rev_git_only_in_session]
- [S6] 掛鉤事件的 note 在成功與失敗時應分別是 `spec_rev` 與 `spec_rev <代碼>`;沒用到這個寫法時 note 跟現在一樣。[test: t_dispatch_lens_hook_spec_rev_event]

- 測試怎麼搭:S1、S4 用 `git worktree add` 造真的第二個工作樹,在那裡提交計劃,會談目錄留在主工作樹;不換 `HOME`。

## 實務隱患

- 守衛面:掛鉤會改寫子代理的派工詞,也是錨點清單裡的檔。這次不新增去別的目錄跑 git 的路:讀計劃只在會談 repo 跑 `rev-parse`、`cat-file`、`show`,這三個不讀 index、不跑過濾器,跟代碼審那條路(在會談 repo 算別的工作樹的提交)同一個風險面。提交編號是派工詞給的,最壞是指到會談 repo 裡別的提交、附上那份計劃的節點——附加段開頭照現在印計劃路徑,加印提交編號前 12 碼,席位對得出來。
- 已排除:金流:不碰。
- 已排除:對外送出:只在本機跑 git 與 lumos。
- 已排除:不可逆:還原提交即回到只認工作樹路徑;派工詞多出的提交編號寫法,舊版會當成工作樹路徑找不到、照舊不附。
- 改了錨點清單裡的掛鉤與測試檔,提交前要 `lumos anchor approve`。

## 回退

照順序:
1. 還原程式、掛鉤、範本與手冊的提交(範本與掛鉤一起退,免得範本還叫人寫提交編號寫法、掛鉤卻不認)。
2. 每個消費專案跑 `lumos update`,再 `lumos anchor approve --note "<為什麼>"` 並提交簽名檔;最後一個跑 update 的專案會把它的掛鉤寫進 `~/.claude/hooks/`,所以要等每個專案都更新過,並核對 `~/.claude/hooks/dispatch-lens-hook.py` 的指紋跟還原後的版本相同。
3. 還有派工詞帶著提交編號寫法的進行中迴圈:舊版當成路徑找不到、不附節點,手動 `lumos dispatch-lens --spec` 貼固定席。
