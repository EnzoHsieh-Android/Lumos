**一、先修正「收斂不了」的統計定義**

目前至少混著四件事：

1. 一輪報告出現 major。
2. 一輪發現尚未全數處置。
3. 修補後的版本尚未經獨立審查。
4. 整個工作超過三輪，仍不能完成交付。

它們不能互相代替。

程式的處置集合條件是：

```text
folded ∪ accepted = findings
folded ∩ accepted = 空集合
accepted 必須有理由
code-loop 只要任一席 severity ≥ major，整輪 accepted 必須為空
```

**它沒有要求這輪報告的最高等級必須低於 major。** major 全折入，這一項仍可過；其他證據條件另驗。另一方面，手冊又要求修補後由全新席掃回歸，所以「處置閘過」與「最終修補版已完成審查」還有距離。依據：[處置閘實作](/Users/enzo/orca/workspaces/lumos-toolchain/Word-wild-search-rst/scripts/lumos:27041)、[code-loop 手冊](/Users/enzo/orca/workspaces/lumos-toolchain/Word-wild-search-rst/skills/lumos-code-loop/SKILL.md:48)。

**二、候選原因的診斷**

證據強度的「強」只適用於該欄明確寫出的主張，不代表已證明改善方案有效。

| 候選原因 | 判斷與證據強度 |
|---|---|
| 每輪全新多席審完整改動，總會找到東西 | **流程存在：強；「總會」：有反證；造成額外輪次：中。** 完整改動仍是審材，修訂輪另附修補差異。但原回放的 257 個續輪中，帳面有 **81/257** 輪最高未達 major，並非必然找出重大問題。 |
| 修補帶出新問題，修補越大越糟 | **修補回歸存在：強；大小與後輪 major 相關：強；壓小能改善的因果證據：弱。** 下文有獨立重算。 |
| 第一輪改動太大 | **相關性：中至強；因果：中以下。** 大案較常到第三輪，但難度、風險、跨模組程度及審查配置都可能共同影響。 |
| 只修點名處，同族沒掃完 | **具體案例：強；是全體首要根因：中。** 回顧分類支持這個方向，但分類很寬，而且只收特定跑滿案件。 |
| major 判準太低 | **判準異質、部分問題被過度升級：中。** 產品錯誤、測試偵測缺口、架構重複、文件問題會被不同席用不同尺度評等；不能一概認為它們都不該阻擋。 |
| 有 major 就連 minor 也必須折入，修補因此膨脹 | **規則與實際修補負擔：強；造成多少額外輪次：中。** 有可追蹤的具體案例，值得優先試驗。 |
| 審查員撞題、席數過多 | **撞題存在：強；應刪多少席：弱。** 重複發現未必是浪費，也可能提供獨立證據；目前資料不足以直接求最佳席數。 |
| 其他 | **原始評等與最終裁決混用、範圍漂移、永久工具擴張審查面、測量口徑失真**，都有值得處理的證據。 |

**修補大小：原數字重現，但因果解讀需要收斂**

我執行驗證筆記內嵌腳本，以下全部重現：

| 兩輪間「新增文字行」級距 | 續輪數 | 該輪修補差異內有 major/blocker |
|---|---:|---:|
| 0–47 | 64 | 19/64，29.7% |
| 47–100 | 64 | 36/64，56.3% |
| 101–223 | 64 | 42/64，65.6% |
| 226–1030 | 65 | 56/65，86.2% |

算法是將符合 standard/high 的 `code-*` 目錄內相鄰 `rN-snapshot.patch` 配對，排除指定簿記路徑，以 `SequenceMatcher` 比較兩份累積 patch 的新增行序列；新增超過 5000 行者排除。四組按排序位置等量切割，**47 的端點重疊是同值被分到不同組，不是互斥門檻區間**。總樣本為 **257 個續輪、123 個迴圈**。來源：[原回放與腳本](/Users/enzo/orca/workspaces/lumos-toolchain/Word-wild-search-rst/docs/lumos-toolchain-knowledge/Verification/2026-10-14_修補大小與下一輪major回放.md)。

我另用以下模型重算：

```text
A = 第 n−1 輪到第 n 輪凍結材料之間的新增行數
F = 第 n−1 輪載體的 folded_set 數量 + accepted_set 數量
Y = 第 n 輪是否有 major/blocker

logit P(Y=1)
  = β0 + β1 log2(1+A) + β2 log2(1+F)
       + β3 I(n≥3) + β4 I(tier=high)
```

有 **8 個續輪**缺前輪處置數，完整控制模型使用 **249 輪、121 個迴圈**。以迴圈分群計算 sandwich 標準誤及近似 95% Wald 區間，沒有把同一迴圈的輪次當成獨立樣本。

| Y 的定義 | 事件／樣本數 | `1+A` 每翻倍的勝算比及區間 |
|---|---:|---:|
| 帳面任何席達 major/blocker | 172/249 | **1.80［1.33，2.43］** |
| 原腳本判在修補差異內的 major/blocker | 150/249 | **1.93［1.39，2.69］** |
| 原腳本解析出的全部 major/blocker | 165/249 | **2.01［1.46，2.77］** |
| 改從帳上報告路徑取件，排除缺件／無頂格 severity，並排除含 `canary／植入／假發現` 的發現區塊 | 157/246 | **1.91［1.38，2.64］** |

最後一列只是敏感度分析：關鍵字也可能出現在真實產品問題中，**不等於已完成假發現清洗**。所有模型都仍受歷史報告解析、評等和樣本選擇限制。

所以我同意「約 1.8 倍」這個關聯量級，**不同意把它當成縮短修補的預期療效**，理由有六個：

- **難題同時造成大修補與後輪缺陷。** 控制前輪條數，沒有控制每條問題的深度、耦合與修復難度。
- F 是「處置 ID 數」，不是經過一致去重的根因數；還包含 accepted，稱「折入數」不完全精確。
- 大修補常包含更多測試。不能把新增測試的成本直接解讀成造成缺陷的程式量。
- 「引句位於修補差異內」不是「這個缺陷由修補造成」。修補可能只是碰到早已有缺口的函式。
- 差異內發現率與差異大小有測量上的連動：可歸到差異內的文字越多，至少有一條被歸進去的機會本來就越大。
- 樣本只包含有續輪、有相鄰快照的工作；不能代表首輪結束、缺證據或中止的全部工作。

另外，勝算比不是機率倍率；`log2(1+A)` 也應如實寫出，不能把零行處理藏起來。

**三、我建議的一組優化，依預估效果／成本排序**

以下排序是工程判斷，不是假裝已量過收益。先以同一個版本化試行處理，不把整套一次升格成永久規則。

**1. 修補前先合併根因、界定必須保持的行為，停止順手擴張**

**改什麼：**沿用既有 `rN-fix.json` 和 intake，每個修復群只回答：

- 壞的是哪一條行為規則？
- 哪些入口共用這條規則？
- 哪些正常行為必須保留？
- 哪些修改只是偏好、整理或額外功能？

同一根因的必要路徑一起修；與修復無關的重構、辯方附送的 nice-to-have 不自動進修補佇列。重用既有 helper 前要比對語意，不能只因名字相似就替換。

**為什麼：**同族漏修與修補擴張都有具體卷證。尤其引句案例曾因改用共用消毒函式而失去原先涵蓋的字元過濾；「重用」本身不保證正確。

**預期效果／量法：**減少同根因跨輪再現，以及修補引入的新缺陷；同時量根因整理耗時、修復成功率、既有好例保留率。

**代價與風險：**前面多花分析時間；若「同族」定得過寬，會變成更大的重構。範圍限於受影響契約、直接呼叫者及共享入口。

**規則關係：**大部分已在修復穩定性試行與 §3.1。應精簡、落實既有要求，而不是再新增一張相似檢查表。另需消除 reference 中「辯方順產 fix 直接轉佇列」與試行排除 nice-to-have 的張力。

**2. 改成逐條決定是否阻擋，解除 major 對所有 minor 的連帶必修**

**改什麼：**

- 原始報告與原始 severity 保持不可改。
- 最終採信、反駁與有效 severity 分開記，必須能連回原 finding 與證據。
- **有效 major/blocker 必須修好或撤回相關改動。**
- minor 可獨立附理由接受或延後，不因同輪另一條 major 而失去此選項。
- 接受 minor 不代表整輪可放行；未解決的重大缺陷仍阻擋。

同步統一評等尺度：

| 類型 | 建議判準 |
|---|---|
| 現行程式可重現錯誤、資料破壞、權限突破、合約違反 | 按後果列 major/blocker |
| 測試抓不住錯誤 | 關鍵合約或具體合理退化缺乏必要保護時可阻擋；一般測試完整性改善另外處置 |
| 第二種寫法、重複 helper | 能證明違反有效架構限制或帶來具體重大維護／行為風險才阻擋；不能只靠「有兩套」 |
| 文件不一致 | 會導致錯誤操作或違反契約時阻擋；一般精度與歷史數字更正可獨立排程 |

**為什麼：**直接切斷「修重大問題時順便強迫修全部小問題」的擴張來源，也讓有證據的反駁真正影響處置。

**預期效果／量法：**看非必要 minor 的修補量、因這些修補新開的驗證工作、總交付成本；同時看盲審是否發現被降級的真重大問題。

**代價與風險：**這是最需要防止作者自行放水的一項。不能只刪除一個 `if`；必須保留原報告、逐條裁決來源及獨立查證，缺裁決證據時維持阻擋。

**衝突：**明確改變 `probe輪退場_計劃` 的既有裁定、嚴重度綁定規則及架構席尺度，需要正式設計審與使用者裁定。這次只提出方案，不視為已授權修改。

Google 的審查標準也區分必要改善與可選細節，並要求以事實和工程原則處理歧見；這支持區分處置的方向，但不能提供本 repo 的效果數字。[Google 審查標準](https://google.github.io/eng-practices/review/reviewer/standard.html)

**3. 把「發現問題」與「驗收修補」分工，讓停止條件綁最終版本**

**改什麼：**

- 首輪仍做完整風險審查。
- 修訂輪明確列出：已知問題驗收、修補影響範圍回歸、必要的完整整合檢查。
- 原席可驗自己提出的問題；全新席獨立查修補副作用。
- 全新席得到固定版本、需求、案例與必要上下文，不得到「作者已判定安全」的結論。
- 只有出現新證據、相關程式改變或前次驗證失效，才重開已裁決問題；發現真重大問題仍須處理。
- **每次修後再找新問題都照實計輪，不把反覆修—審藏進「同一輪驗收」。**

完成條件應同時具備：有效重大問題解決、必要測試與保留案例通過、最終版本的審查範圍已覆蓋、minor 有去向、既有機械閘通過。

**為什麼：**處置集合完成和修補版完成審查目前容易混稱收斂，造成不斷重開完整探索。

**預期效果／量法：**減少重複閱讀與已裁決議題重開；量實際閱讀量、重開原因、驗收時間及獨立品質抽查結果。

**代價與風險：**影響範圍判錯會漏問題。先保留 high 資安席的完整覆蓋，不把這項試行偷換成「第二輪起只能看 delta」。

**衝突：**與目前完整改動閱讀要求有部分差異；而「資安席只讀變動檔」已被否決，原因是帳面覆蓋可能不等於實際閱讀。這個否決仍成立，不能用檔名清單繞過。來源：[既有否決理由](/Users/enzo/orca/workspaces/lumos-toolchain/Word-wild-search-rst/docs/lumos-toolchain-knowledge/Projects/審查收斂規則_計劃.md:35)。

**4. 用「可獨立驗收的行為」拆案，行數只當提醒**

**改什麼：**首輪之前拆開不相依功能、一次性分析工具、廣泛重構與主要修復；必要測試、呼叫端與相容處理跟著功能保留。

修補若越來越大，先問是否選錯修復層、是否能撤除不必要功能，而不是壓縮程式排版或刪測試。

**為什麼：**第一輪大小有關聯；卷證也顯示有些審查面來自附帶機制。引句案例最後的人裁曾直接要求砍掉一次性的比較模式。

**預期效果／量法：**量每個原始工作的總成本、跨模組面積、首次審查有效發現與最終品質；拆出的子案仍合併計入原始工作，避免藉拆案美化三輪率。

**代價與風險：**拆案有整合成本；拆得太碎反而看不到契約。不能拆開同一個原子修復。

**衝突：**支持目前提示版計劃，反對恢復 100 行硬上限。300／100 可作可調提醒，文案不應暗示越線就該拆，或壓線即可降低多少風險。Google 也明確把「小」定義為概念聚焦，要求保留相關測試。[Google Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)

**5. 席位先按責任分工，再試減席**

**改什麼：**讓每席有清楚的主要責任；撞題後以根因群安排一次修復，保留每條證據和驗證義務。新增席位要回答它補哪個既有席未涵蓋的風險。

先對額外通才、重複合約／規格席做影子評估；資安等既有必要席不先刪。

**為什麼：**多份相同題目的報告增加收貨與修補成本，但少席也會跑滿，不能把減席當主解。

**預期效果／量法：**每席獨有且經確認的重大根因、重複群比例、收貨耗時、總 tokens，以及減席後的獨立漏抓率。

**代價與風險：**同模型多席可能有共同盲點，但不同鏡頭仍可能補漏；歷史「這席沒有獨有發現」不代表未來可以刪掉它。

**衝突：**涉及 high 編制與每級架構席要求，需另裁。不要用歷史報告刪一列後仍能過閘，當成減席安全的證明。

**6. 只補必要的量測接線，避免再造大型審查工具**

**改什麼：**沿用現有 intake、finding severity、修復群、固定版本、治理事件與 `review_convergence.py`，補齊可比較的結果。一次性資料清理先留離線分析，不先做永久子指令。

統計至少分開：

- 原報告數、採信缺陷數、修復根因群數。
- 當輪處置完成、最終版本驗收完成。
- 原有漏查、修補引入、未知。
- 工作總時間、模型成本、機械閘／格式返工時間。

**預期效果／量法：**先提高可判讀率，再比較效果；未知保留未知，不補零。

**代價與風險：**量測本身可能變成新的表單工作。只保留會進入決策的欄位，記錄成本若持續高於用途就刪減。

**衝突：**與目前撤掉正式回放子指令的方向一致。[既有 eval 工具](/Users/enzo/orca/workspaces/lumos-toolchain/Word-wild-search-rst/governance/eval/review_convergence.md)已明確區分資料核對與實際效果，不需要重做一套。

**四、怎樣證明有效**

**現有資料可以先回答的事**

| 離線工作 | 能得到什麼 | 不能宣稱什麼 |
|---|---|---|
| 依當時規則、治理事件和凍結 verdict 重建工作結果 | 區分處置完成、補審、人裁、中止與最終完成 | 不能只看最後 severity 或只看有無第三輪 |
| 對有完整逐條評等的輪次回放「minor 可獨立接受」 | 哪些處置選項原本被輪級規則封住 | 不能直接算省幾行、少幾輪；實際修法會改變 |
| 盲判歷史 major 樣本 | 產品錯誤、關鍵測試缺口、一般品質改善各占多少；評等是否一致 | 不能只由想改善收斂的作者重判 |
| 把多席發現映射到根因及覆蓋範圍 | 觀察到的獨有發現與重複工作 | 刪席後其他席的行為可能不同，不能當減席實驗 |

資料清理要保留一份排除清單：原始路徑、hash、輪次、解析方式、植入證據、排除理由。**不能整份含 canary 就判假資料，也不能解析不到 severity 就當 clean。**

回顧中的 `fix-induced` 及帳上的 `regression_set` 也不能直接充當真值。例如引句案 intake 曾把「帶進或沒補齊」放在同一個回歸分類；現行 §3.1 要求的兩版同案例證據比這個嚴格。

**前瞻驗證分成兩階段**

第一階段是可執行性試行。沿用既有五案安排，明確記是哪個流程版本；不回頭把已跑案件重新包裝成新方案樣本。

這階段只回答：

- 編排者是否能一致套用判準？
- 是否真的避免不必要修補？
- 根因與保留案例是否有用？
- 記錄和裁決多花多少時間？
- 有沒有具體的漏擋事故？

**五案可以決定要不要繼續投資，不能證明改善率。**

第二階段才做效果比較：

- 單位是**原始工作**，不是席位、續輪或拆出的子迴圈。
- 同期隨機分配舊流程／候選流程；按風險、工作類型及初始規模分層。
- 固定模型、主要提示與判準版本；變更版本後另列。
- 中止、換 loop、拆案都留在原分配組，不挑成功案例。
- 主要結果：品質驗收成立且在三輪內完成的工作比例。
- 同時報全部工作總成本；不能只比較兩組都成功的案件。
- 獨立品質檢查使用相同尺度；相同放行後觀測窗，未成熟者保持未知。
- 前瞻抽查新發現的真重大缺陷照常處置，不能為完成實驗保留已知錯誤。

**樣本量要從想辨識多大的改善倒推。**

以下是規劃情境，**不是把歷史「到第三輪率」當真實未收斂率**。假設對照組不成功率為 60%，雙側 α＝0.05、檢定力 80%、兩組等大，常用兩比例近似公式為：

```text
每組 n =
[1.96√(2p̄(1−p̄)) + 0.842√(p0(1−p0)+p1(1−p1))]²
÷ (p0−p1)²
```

| 想辨識的改善 | 每組約需 | 合計 |
|---|---:|---:|
| 60% → 40% | 97 個獨立工作 | 194 |
| 60% → 45% | 173 | 346 |
| 60% → 50% | 388 | 776 |

同一功能的子案、同根因反覆工作不獨立；若有這類群聚，還要增加樣本或以群組分派。資料缺失也會增加需求。因此「三案」明顯不足，「四週」則取決於期間能取得多少**獨立且完整**的工作，不能單靠日曆判斷。

建議先選一個值得投入的最小改善幅度，再定最大樣本與固定分析時點；區間仍涵蓋無效與有用效果時，結論就是「判不出」，不是任選保留或撤案理由。

品質也不能用小樣本零事故保證。若 n 個獨立工作零事故，事故率單側 95% 上界為：

```text
1 − 0.05^(1/n)
```

所以 **5 案零事故，上界仍約 45.1%**；**100 案零事故，仍約 3.0%**；要把上界壓到 1% 以下，至少約 **299 案零事故**。這只適用於已定義、能可靠觀測的事故與觀測窗。

對減席、縮閱讀範圍這類可能降低發現能力的方案，應先做影子試行或固定案例的成對比較。既有 eval 可核對案例、模型、流程與結果來源，但其 README 已明說：**收據通過不代表驗收內容是真的**，仍要保留獨立測試與人工裁決。

**五、我不同意 Claude 分析的地方**

1. **不同意「第三輪仍有 major」直接等於未收斂。**  
   72 個第三輪有 major 的迴圈中，64 個帳面全折入。這個指標可以表示仍在產生修補工作，不能直接代表處置閘失敗或最終交付失敗。

2. **不同意用「153 個續輪的 major 落在修補差異裡」推論收斂主要卡在修補造成問題。**  
   原回放中，169 個有 major 的續輪，153 個有差異內 major，這個算式可重現；但文字落點不證因果，也不是完整的語意影響範圍。據此說「只審 delta 救不了收斂」過強：它最多描述同一批已產生報告在該解析方法下還剩多少 major。

3. **同意約 1.8 的關聯，不同意把「控制後仍成立」稱為獨立因果效果。**  
   問題難度、修復類型、審查強度與歷史制度差異仍存在。勝算比也不能直接變成「行數砍半能降低多少失敗」。

4. **不同意把同族 20/20 當完整根因排序。**  
   分母是被記錄的跑滿回顧，而且包含設計審；分類同時收同根因和同類疏漏。它適合選改善候選，不適合估算全體歸因比例。

5. **不同意以 100／300 行作為方案的核心控制量。**  
   它們可以提醒，但容易誘導少寫測試、壓縮寫法或把同一件事拆成多個統計單位。更接近根因的是行為範圍、相依關係及修復義務。

6. **也不同意證據量測席的一個統計理由：把前輪折入數一概稱為修補量效果的「中介變數」。**  
   在這次模型的時間順序裡，前輪發現／處置先於修補量；它可以是修補量的成因和難度代理，不能僅因「它導致修補變多」就判定不應控制。若研究的是整套流程介入，其因果角色又可能不同，應先畫清楚時間關係。來源：[該席報告](/Users/enzo/orca/workspaces/lumos-toolchain/Word-wild-search-rst/governance/review-reports/改動與修補拆小/r1-證據量測-sonnet.md)。

7. **不同意「三個月有人因提示拆案」就足以支持提示有效。**  
   那只能證明有人採用。拆案後原始工作的總成本、品質與完成時間是否改善，仍須另量。

我支持 Claude 後來撤回硬上限、撤回大型回放子指令，以及承認小樣本無法判效的方向。但目前提示版方案處理的是**風險提醒**；使用者真正卡住的**修補義務與停止條件**，還需要前面那組流程調整。

本次確認的既有規則包括：全新席驗修補、high 資安完整覆蓋、重大問題輪不得接受任何條目，以及三輪後須人裁。發現的主要口徑問題是：用原始 major 代替未完成狀態、用修補文字落點代替缺陷來源，以及手冊「辯方後存活評等」與程式原報告最高值的張力。依你的唯讀要求，這些都只在本回答提出，未寫回圖譜。
