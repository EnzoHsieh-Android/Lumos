# 舊行插字不算新寫_計劃

白話:清舊筆記時最常做的事,是在舊句後面補一個「(更正:…)」。筆記形狀擋現在把整行當成新寫的來查,於是舊句本來就有的問題(例如上線前寫的、沒帶來源的 DEP;句子裡原本就有的「還沒」)全部算到補更正的人頭上:擋提交、跳提醒。這份計劃讓它只查「這次插進去的字帶來的新問題」——前提是舊句真的被改掉了(原行不見),不是在旁邊抄一份再加字。

依據:
- 消費專案清漂移回傳(2026-10-02,第 3 項,去識別):在舊句後補更正括號,整行被當新寫——舊行原有的「還沒」觸發否定現況句提醒 24 條;一條上線前合法的舊 DEP 被當成新寫的 DEP 擋下,只好改寫成歷史 WHY。
- 本 repo 重現(2026-10-02,用測試小工具 `_ns_repo`/`_ns_note`/`_ns_stage` 建暫存專案):先提交 `DEP:付款走舊閘道 scripts/pay.py 還沒換掉`,再改成在句尾多一段「(更正:2026-10-02 已換成新閘道,見 `Systems/Pay`)」並暫存,`note-shape --staged` 回 1(沒寫來源的 DEP),而且對原本就有的「還沒」再提醒一次。這段會寫成 [S1][S2] 的測試。
- 程式現況:`_note_shape_eval` 取「這次新增的行」(`_notelines_new`),對每行跑 `_ns_check_line`(只看正文、摘要、決策)、`_ns_revisit_violations`(也看開頭欄位其他欄),提交前另外收否定現況句提醒(`_ns_negation_collect`)與前綴提醒(`_ns_tag_hints_collect`);舊版那一行不看。後半「新程式檔喚醒舊引用」那一路另有整行相等的舊行判定。

PRIOR-ART: 「只評這次改到的部分」是 lint 接 PR 的標準做法——reviewdog 的 `-filter-mode=added`、Danger 的只看 diff 行;它們的粒度是「行」,本案的問題是「行改了、但只多了字」,所以再細到字。「只多了字」就是「舊行是新行的子序列」,用雙指標一趟判、順便得到插入的位置,不用 difflib(r2 量過它最壞一對 0.4 秒,而且不保證找到純插入)。
RETIRE-IF: 上線八週後任一成立就撤掉或重想:①從治理帳的放寬事件(〈做法〉6,帶起點版本、路徑與行號)抽 20 行對回提交,有一半以上其實是借插字把新問題塞進舊句——那就改回整行查;②治理帳八週內一次放寬事件都沒有(沒人補更正,機制是死的);③筆記形狀擋改成以「欄位」或「句子」為單位判新舊,這條被取代。

## 做法

1. **只動新增行那一路**:在 `_note_shape_eval` 前半(對 `_notelines_new` 交出的 rows 判違規)加一張「這條新行配到哪一條舊行」的配對表,每篇算一次。**不動的**:後半「新程式檔喚醒舊引用」那一路——它問的是「這行根本沒改、是程式那邊變了」,舊版是上線點版本加 `old_by`(上線前寫的行),跟本案問的「行改了但只多了字」是兩件事,照舊用自己的整行集合;筆記格子的舊行判定(同前綴、同核心一句的文字鍵、連結只增不減,只套摘要,問的是「欄位有沒有補」);`_notelines_new` 交出的 rows 與新寫行定義;第二層筆記內容審;存量漂移檢查。三種「舊行」各問各的,關係寫進 [[Systems/筆記內容閘]]。
2. **配對條件**(全部要成立,否則照整行查):
   - **起點版本**:`_note_shape_eval` 收到的 `base_where`(提交前是 HEAD;推送前是推送起點、已夾到上線點;doctor 事後掃描是上線點)。沒有起點版本(新 repo 第一次提交、空樹)、那篇在起點版本不存在(含這次改名)、讀不成 UTF-8、批次讀失敗:這篇不配對。起點版本用 `_nodehome_cat_blobs_capped` 批次讀、`utf-8-sig` 解碼,路徑跟讀終點版本用同一個(`_notelines_new` 交給 reader 的那個)。
   - **行的單位**:O、N 都是 `strip()` 後的整行(去行首行尾空白、`\r`、全形空白),以 Python 字元計(碼點、不做 NFC);去空白後相等就不是「改了」,不配。
   - **O 被用掉(整行計數)**:對起點版本與終點版本各建一張「去空白後整行 → 行數」的表;一段文字的配對額度=起點行數 − 終點行數(大於 0 才有)。配一次扣一次,一對一。
   - **只多了字**:O 是 N 的子序列(雙指標由左往右,貪心對齊),N 比 O 長;O 不到 8 個字不配;插入的總字數不超過 500 字、N 不超過 2000 字。對齊同時得到插入的位置(第幾到第幾個字)。
   - **同一個脈絡**:O 在起點版本與 N 在終點版本的區塊相同(`_notelines_regions`)、可見性相同(都在圍欄外,`_visible_lines`)、那篇的重建標記 `regen` 在兩個版本相同。把圍欄裡的舊行搬出來再插字,可見性不同、不配。
   - **候選與順序**:先用計數表只留「額度大於 0」的 O,再篩「開頭 8 個字相同或結尾 8 個字相同」、比 N 短的;N 照終點行號由小到大處理;同一個 O 有多條 N 都對得上時,配給終點行號跟 O 起點行號最接近的那條(真的被改的那行通常在原位,旁邊抄的那份不在);同一條 N 有多個 O 對得上時取最長、同長取起點行號最前。
   - **上限**:配對表在一次 `_note_shape_eval` 呼叫裡是區域變數;每次呼叫最多做 5000 次子序列判定(常數 `_NS_INSERT_MAX_CHECKS`),超過之後的 N 不配。子序列判定是一趟線性掃描,5000 次 × 2000 字是毫秒級。
3. **配到的行怎麼判**:
   - **`_ns_check_line` 的規則**:對 N 與 O 各算一次(兩邊用同一份檔案清單、O 用起點版本的 `regen` 與區塊——條件 2 已要求兩邊相同),**照計數只報 N 比 O 多的**。鍵:程式行號引用、釘版本不合法用(規則, 片段)——在既有路徑後面插 `:12` 會讓片段變成新的、照報;同一行同一個片段 `_ns_check_line` 只出一條,插第二個一字不差的不會多報(天花板 5)。SEE 只放連結、沒寫來源的現況描述用規則名(插字救得了、弄不壞「有沒有來源」;SEE 行插進句子會讓 N 違規而 O 沒有,照報)。
   - **`_ns_revisit_violations`**:同樣 N 與 O 各算(兩邊同一個可見性),鍵(規則, 改法);改法只有「條件寫錯」帶錯誤細節,其餘是常數——在合法的回頭條件行裡插壞條件會照報;舊行本來就寫錯、插字改變了錯誤清單,鍵不同也照報(偏嚴)。
   - **否定現況句提醒**(只在提交前算):配到的行只對**插入的字**判(把各段插入的字依序接起來、段與段之間放一個空白,交給同一支 `_ns_negation_hits`),有命中就出一條提醒、片段從插入的字切。判定放在 `_ns_negation_hints` 裡(多一個有預設值的參數收配對表),例外照現行在收集器的 try 裡吞掉;配對表本身算失敗就當沒配對、整行提醒。跨在舊字與插入字交界的字眼(例如在「還」後面插「沒」)抓不到(天花板 7)。
   - **筆記前綴提醒不套用**:`_ns_rule_hints` 對 RULE 行的提醒(含筆記格子的寫法警告——現在只提醒、格子開擋後會擋)照現行整行出,補更正的 RULE 行照樣收到。
   - 之後加在 `_note_shape_eval` 後面的新規則(例如另一個 session 設計中的 `Projects/筆記測試綁定要存在_計劃`)預設整行判,要套用得自己明寫。
4. **doctor 事後掃描**:呼叫同一支 `_note_shape_eval`,起點是上線點,所以只對「上線點之前就在、這次被改成只多了字」的行放寬。上線點之後才寫、後來被補字的行,doctor 照整行查;這種行如果還唸,表示它**寫下的那一刻**就違規卻進了主線(warn 模式或繞過)——訊息說的「多半是 --no-verify 繞過」指的是那一次寫入,不是後來的補字;這點寫進 doctor 那段的說明與 [[Systems/筆記內容閘]]。
5. **推送範圍的舊版**:起點版本裡沒有的行(這次推送才寫、又在後面的提交補字)不算舊行,照整行查。提交前同理,HEAD 裡沒有就是新;同一批工作先插 A、下一個提交改成 B,對 HEAD 是替換、照整行查(天花板 3)。
6. **放寬也記一筆帳**:有違規或提醒因為配對被減掉時,`cmd_note_shape` 記一筆治理帳——閘 `note-shape`、**種類 `relaxed`**(不借 `hinted`:否定現況句計劃的抽樣與筆記格子的度量都按 `hinted` 數,混進去會污染)、`extra` 帶 `check: "insert-only"`、`mode`(commit 或 push)、`base_sha`、減掉的違規數與提醒數、各規則名的條數、每條配到的 `[路徑, 終點行號]`(最多 50 條,不帶原文)。由 `_note_shape_eval` 多收一個容器參數(同 `hints` 的傳法,有預設值;不傳就不收),只有 `cmd_note_shape` 傳、doctor 不傳(doctor 不寫帳)。這是「沒違規的放行不寫帳」(2026-09-27)的第三個例外(前兩個是否定現況句與前綴提醒的 `hinted`);提交前與推送前各記一筆、用 `mode` 分。寫入走既有寫入器,頻率略增,鎖的問題沿用既有 Issue。
7. **同步要改的字句**:[[Systems/筆記內容閘]](三種舊行的關係、放寬帳、doctor 的訊息解讀)、[[Projects/筆記形狀擋_計劃]]([S7] 與資源併發段的「沒違規放行不寫」補上例外;RETIRE-IF ①②③ 的分母從本案上線日起少了被放寬的行,寫明起算日)、[[Projects/否定現況句配回頭條件_計劃]](抽樣只取 `check` 是 `negation` 的 `hinted`;重產被提醒的行時,跳過放寬帳記的路徑與行號;判定跟量測程式逐行一致的宣稱補上這個例外)、`cmd_note_shape` 的 docstring。

## 實務隱患

- **繞過**:在旁邊抄一份舊行再加字——O 還在(額度 0)、不配;有額度時配給位置最接近的那條。把圍欄裡的舊行搬出來再插字——可見性不同、不配。把舊行改寫成「只多了字」並在插入段塞新的程式現況——行號引用照片段比會擋;沒寫來源這條舊行本來就犯、不重報,新塞的現況靠第二層判定者(天花板 1),插入上限 500 字限制夾帶量;放寬帳記路徑與行號,RETIRE-IF ① 抽得到。
- **效能**:改到的筆記多一次起點版本的批次讀(有大小上限的那支);子序列判定線性,每次呼叫最多 5000 次。記憶體只多起點版本的那幾篇全文。
- **併發**:只讀 git 物件;放寬時多寫一筆治理帳,走既有寫入器,鎖的問題沿用 [[Issues/治理帳多個寫入者都沒上鎖]]。
- **回滾**:還原這一個提交即回到整行查;已寫的 `relaxed` 帳留著無害(種類獨立,不混進 `hinted` 的統計)。
- **相容**:提交與推送時擋得只會變少;doctor 只對上線點前就在的舊行放寬,其餘跟今天一樣;筆記格子開擋後,補更正的舊行仍會被格子要求補齊(見 REVISIT,驗收條款 S1、S2 的測試要寫明「格子未開擋」這個前提)。
- 已排除:金流:這道檢查只讀筆記與 git 物件,不碰任何付款流程
- 已排除:對外送出:不呼叫網路、不寄送、不寫到 repo 之外
- 已排除:不可逆:只決定擋不擋、印什麼,還原一個提交就回到原本的判法
- **守衛面**:這是擋提交與推送的閘,改的是「哪些違規算新的」——放得太寬就是一條繞過的路,所以不排除、照走設計審。

## 回退

出事時還原這一個提交即可:判定回到「新增的行整行查」,沒有改任何帳或設定的格式,多出來的那種帳留著無害。已經靠這條放行、推上去的舊行不會被追溯擋下(閘只看新寫的),要追查就跑 `lumos note-shape --diff <起點>..<終點>` 用還原後的版本重看那段範圍。

## 天花板

1. 放過的是「舊行本來就犯的違規」,不是「插進來的字一定沒問題」:插進一段新的程式現況到沒來源的舊 DEP 裡,第一層不會擋,要靠第二層判定者——送審的是整行,沒標哪一段是新插的。
2. 只認「只多了字」:補更正時順手改了一個錯字,整行照新寫查。
3. 只看起點版本:提交時以 HEAD、推送時以推送起點、doctor 以上線點為起點;同一批工作先插 A、下一個提交改成 B,提交時是替換、照整行查(推送時對最初起點仍是只多了字)——要改自己剛插的字就 amend 或推前壓成一個提交。筆記在範圍內改名就配不到,照整行查(偏嚴)。
4. 只篩「開頭或結尾 8 個字相同」:句首、句尾兩頭都插字,或舊行不到 8 個字,配不到,照整行查(偏嚴)。
5. 同一行同一個程式行號引用只算一條(`_ns_check_line` 先去重):插進第二個一字不差的引用不會多報。
6. 「條件寫在不評估的地方」每行只報一條:舊行已有一個、再插第二個,不會多報。
7. 否定現況句只看插入的字:跨在舊字與插入字交界的字眼抓不到(只是提醒、不擋)。
8. 貪心對齊不一定是「作者真正插入的位置」:同樣的字出現多次時,插入範圍可能落在別處;只影響否定提醒的片段位置,不影響擋不擋。
