**B1 配對只看「有沒有一行舊字串是它的子序列」,不要求舊行被改掉:整行複製舊的違規行再接新字,可繞過**

blocking: 是 — 守衛面被一個免費的繞法打穿,而且不在〈天花板〉承認的範圍裡
引句:「候選只看同一篇、比 N 短、開頭 8 個字相同或結尾 8 個字相同的行」

- staged 模式本來有現成訊號:`git diff -U0` 的同一個 hunk 裡有 `-O` 才是真的改行(`_notelines_parse_added` 目前丟掉減號行)。

**B3 S3「跟舊行已有的那個一字不差的第二個」會被擋、只報一個,但 `_ns_check_line` 同一行同片段只出一條,計數比對永遠 1 對 1**

**B4 兩個上限的計數口徑沒定義,S6 無法唯一判定;另外沒有整次提交/推送的總預算,也沒指定 `autojunk`**
severity: major
blocking: 是 — 「超過的照整行查」指哪些行、單行超過是 O 還是 N,各實作者會猜出不同結果,S6 寫不出唯一預期
引句:「一篇最多比 200 對、單行超過 2000 字不配對,超過的照整行查」
- 「對」未定義:是 (N, 候選 O) 的比較次數,還是 N 的個數。「一篇」是一個檔;推送多個提交時,配對對象是終點版本的行,與提交數無關,spec 也沒說。
- 預算用完後,是前 200 對之後的 N 照整行查,還是整篇都照整行查。順序是行號序還是文字集合序。推送的 `texts` 是 set,無序,輸出會不穩定。
- 「單行超過 2000 字」指 O、N,還是兩者任一。
- 「字」是 Python 碼點(`len(str)`)還是位元組。8 字篩同理(見 B6)。
- 效能(實測):
  - `autojunk=False` 時,2000 字低字母集字串一對約 0.17 秒,200 對約 34 秒。
  - 預設 `autojunk=True` 時速度很快,但對含高頻字元的長行會把純插入判成 replace。實測 2000 字十六進位串中間插 3 字,結果是 `['equal','replace']`,配對失敗。
  - spec 沒指定,這等於「長行是否放行」由 difflib 內部啟發式決定。
- 沒有「整次提交/推送」的總預算:清漂移一次改 100 篇,每篇 200 對,pre-commit 時間沒有上界。
- 建議:定義為「每篇 N 條新行 × 篩過的候選」,總量 cap 設成全域數字,超過的一律整行查,並指定 `autojunk=False` 加行長上限(或乾脆指定 `autojunk=True`),寫進條款。

**B5 否定現況句「N 多出來的字眼」遇到同字眼重複時取哪一個位置沒定義**
severity: minor
blocking: 否 — 只影響提醒的片段位置,不改 rc
引句:「N 多出來的字眼裡取第一個出那一條提醒」
- `_ns_negation_hints` 現行取 `hits[0]`,是 (字眼, 位置) 的清單。照「字眼計數」比,多出來的是「某個字眼」,不是「某個位置」。
- 例:O=`還沒做 X`,N=`還沒做 X(更正:Y 還沒做)`。字眼「還沒」N 有 2、O 有 1。
  - 多出來的是哪一個「還沒」未定。
  - 照 `hits[0]` 慣性取位置最前的,片段會切在舊的那個上,提醒指向沒改的字。
  - 預期應指向插進去的後面那個。
- 測試 S2 只用「尚未」(舊行沒有),涵蓋不到這個同字眼重複的例子。

**B6 空白、行尾、字元單位:「去掉行首空白」只說一半,行尾與全形空白會讓實作者各猜**
severity: minor
blocking: 否 — 會造成各實作輸出不一致,但不開新的繞過口
引句:「配對條件:去掉行首空白後,`SequenceMatcher(None, O, N).get_opcodes()` 只有 `equal` 與 `insert`」
- 現行 `_notelines_rows` 的文字集合用 `.strip()`(兩端),`_ns_check_line` 的片段也用 `.strip()`。spec 只說行首,行尾沒說。
- CRLF:`text.split("\n")` 後行尾帶 `\r`,「結尾 8 個字」會包含 `\r`。
  - O=`…還沒換掉\r`,N=`…還沒換掉(更正:…)\r`:後綴 8 字相同,可配。
  - N 若已被 `.strip()` 去 `\r`,O 沒去,後綴 8 字不同,配不上。
  - 要明寫 O、N 兩邊先 `.strip()` 再比。
- 全形空白 U+3000:Python 的 `str.lstrip()` 會去,`lstrip(" \t")` 不會。「空白」需明寫。
- 只差縮排或只差行尾空白(去空白後 O==N):opcodes 沒有 `insert`,依「至少一段 `insert`」不配對,走整行查。這和推送模式(用 `.strip()` 文字集合,等於縮排不算新)不一致,staged 的縮排重排會被當新寫。需另寫「去空白後相等就算舊行」。
- 「8 字」是 Python 碼點。emoji、組合字符(NFD)一個視覺字元可占 2 個碼點;spec 沒講,建議明寫「`len(str)` 碼點、不做 NFC」。
- BOM:只在第一行(`---`)有影響,可以忽略,但要在條款裡說一句。
- 空行 O、O 少於 8 字:
  - `N.startswith(O[:8])` 對空 O 恆真,`endswith('')` 同。
  - 天花板 4 只說「不到 8 個字配不到」,實作者可能反而全配。
  - 空 O 的違規為 0,不會放行,只是白算,但要明寫「O 為空或不足 8 字不配」。

**B7 O 的「區塊」「可見性」「重複文字」沒寫怎麼取,實作者會拿 N 的資訊判 O**
severity: minor
blocking: 否 — 多為保守方向出錯,但條款 S4、S7 的預期值可能各自不同
引句:「O 用終點版本的檔案清單判,跟 N 同一把尺」
- `_ns_revisit_violations(ln, reg, visible)` 和 `_ns_negation_hints` 都需要「這行在不在圍欄外」(visible)。O 在起點版本的 visible 該用起點全文算,不是 N 的。
  - O 在圍欄內(不算)、N 在圍欄外:O 的違規為 0,N 全報,偏嚴,可接受。
  - 反過來 O 可見、N 不可見:N 本來就不查。
  - 但 spec 沒寫,實作者很可能直接重用 `i in vis` 的 N 版本。
- O 的區塊:起點版本同一段文字可能出現在多處不同區塊(例如摘要和正文各一行同文)。「O 在起點版本的區塊跟 N 相同」要寫成「存在某一行 O 區塊相同」還是「所有」。
- 推送模式的 N 同樣沒有行號:終點版本同文字出現多行時,rows 全部算新(現行行為),配對時每一條各自配,結果相同,但 spec 應說一次「N 的區塊用 `_notelines_regions` 在終點全文上取」。
- 「含範圍內改名就不配對」:`_notelines_range_added` 會把改名往後帶到終點路徑,但讀起點版本用的路徑是舊名;spec 要說「用 `git diff -M base tip` 找舊路徑,找不到(或找到了)都不配」,不然實作者可能其中一半會嘗試。
- 提交前的 base:新倉庫第一次提交沒有 HEAD(`_lens_full_sha` 失敗),與推送模式的 `None` / `_EMPTY_TREE_SHA` 兩種空樹寫法並存,spec 只列「空樹」。

**B8 起點版本讀不成 UTF-8 的行為沒寫**
severity: minor
blocking: 否 — 落到整行查是偏嚴,但實作者可能 crash 或 replace 字元當有效資料
引句:「起點版本整篇一次讀(照 `_ns_base_summary_lines` 用 `_nodehome_cat_blobs` 批次讀的做法)」
- file: `scripts/lumos:28292`,`_ns_base_summary_lines` 對起點用 `decode("utf-8-sig", errors="replace")`;`_notelines_new` 對終點則是嚴格 `utf-8-sig`,失敗時入 `errs` 並略過整篇。
- 照字面抄 `_ns_base_summary_lines`,起點會得到含 U+FFFD 的 O。
- 輸入:起點是 Latin-1 的舊筆記、終點是 UTF-8 的修正版 → 預期:整行查(沒得配對)。
- 實際:O 全是替代字元,幾乎配不到,結果碰巧一樣,但 spec 應明寫「起點解不出 UTF-8 → 不配對」。
- `_nodehome_cat_blobs` 在路徑含換行時整批回 None,spec 也沒說 None 時退到整行查(現行 `_ns_base_summary_lines` 回 None 由呼叫端 fail-open)。這裡要寫:讀不到一律整行查,不 fail-open,否則等於讓整篇放行。

**B9 一對多、並列最長 O 的平手沒決定規則**
severity: minor
blocking: 否 — 影響可重現性,不影響守衛方向
引句:「配到多個取最長的 O」
- 平手(兩個 O 同長)沒說取起點版本檔案中的第一個還是最後一個。
- 「最長」不等於「違規最少的」,所以不同 O 會給出不同結果;又因為 B1,同一個 O 可被多個 N 重用。
- 建議:取檔內行序最前的最長 O,並限定一個 O 只能配給一個 N(一對一配對),順手堵 B1 的一部分。

**B10 回頭條件接電:②依賴的治理帳不存在**
severity: minor
blocking: 否 — 屬於 spec 自己的撤除條件失效,不影響功能
引句:「②治理帳顯示這條一次都沒放行過(沒人補更正,機制是死的)」
- 圖譜 `Systems/筆記內容閘` 的 WHY 寫明:沒違規的放行不寫治理帳,只記擋下、warn 與跳過。
- 純插入放行屬於「沒違規」,不會有任何帳可查。①「抽查被這條放行的行」也同樣缺原始資料(放行行沒有留痕)。
