# 舊行插字不算新寫_計劃

白話:清舊筆記時最常做的事,是在舊句後面補一個「(更正:…)」。筆記形狀擋現在把整行當成新寫的來查,於是舊句本來就有的問題(例如上線前寫的、沒帶來源的 DEP;句子裡原本就有的「還沒」)全部算到補更正的人頭上:擋提交、跳提醒。這份計劃讓它只查「這次插進去的字帶來的新問題」。

依據:
- 消費專案清漂移回傳(2026-10-02,第 3 項,去識別):在舊句後補更正括號,整行被當新寫——舊行原有的「還沒」觸發否定現況句提醒 24 條;一條上線前合法的舊 DEP 被當成新寫的 DEP 擋下,只好改寫成歷史 WHY。
- 本 repo 重現(2026-10-02,`/tmp/repro_append.py` 以測試小工具建的暫存專案):上線前的 `DEP:付款走舊閘道 … 還沒換掉`,補上「(更正:… 已換成新閘道 …)」後 `note-shape --staged` rc1(沒寫來源的 DEP),並對原本就有的「還沒」再提醒一次。
- 程式現況:`_note_shape_eval` 取「這次新增的行」(`_notelines_new`,staged 看 `git diff --cached` 的加號行;推送看逐提交新增的文字),對整行跑 `_ns_check_line`、`_ns_revisit_violations`、否定現況句與前綴提醒;舊版那一行完全不看。筆記格子(第 1 步)有自己的舊行判定(同前綴、同核心一句、只改欄位),但只套格子規則。

PRIOR-ART: 「只評這次改到的部分」是 lint 接 PR 的標準做法——reviewdog 的 `-filter-mode=added`、Danger 的只看 diff 行;它們的粒度是「行」,本案的問題剛好是「行改了、但只多了字」,所以再細到字:用標準函式庫 `difflib.SequenceMatcher` 判「只有插入」,不引新依賴。
RETIRE-IF: 上線八週後任一成立就撤掉或重想:①抽查被這條放行的行,有一半以上其實是借插字把新問題塞進舊句(例如在舊 DEP 裡插進新的程式現況)——那就改回整行查;②治理帳顯示這條一次都沒放行過(沒人補更正,機制是死的);③筆記形狀擋改成以「欄位」或「句子」為單位判新舊,這條被取代。

## 做法

1. **配對舊版那一行**:對每一條要判的新行 N(範圍與現行相同:正文、摘要、決策三塊,另含開頭欄位其他欄給「條件寫在不評估的地方」那條;推送時的 rows 照 `_notelines_new` 現行交出的,不改),在**同一篇筆記的起點版本**找一行 O。起點版本=`_note_shape_eval` 收到的 `base_where`(提交前是 HEAD;推送前是推送起點、已夾到筆記形狀擋的上線點);`base_where` 是空樹、或那篇在起點版本不存在(含範圍內改名)就不配對、照整行查。配對條件:去掉行首空白後,`SequenceMatcher(None, O, N).get_opcodes()` 只有 `equal` 與 `insert`、至少一段 `insert`,而且 O 在起點版本的區塊(`_notelines_regions`)跟 N 在終點版本的區塊相同。候選只看同一篇、比 N 短、開頭 8 個字相同或結尾 8 個字相同的行;一篇最多比 200 對、單行超過 2000 字不配對,超過的照整行查;配到多個取最長的 O。起點版本整篇一次讀(照 `_ns_base_summary_lines` 用 `_nodehome_cat_blobs` 批次讀的做法)。
2. **只報新多出來的違規**:配到 O 的新行,同一個判定對 N 算一次、對 O 算一次(O 用終點版本的檔案清單判,跟 N 同一把尺),**照計數比、只報 N 比 O 多出來的**(同一個鍵 N 有兩個、O 有一個,報一個)。比對的鍵依規則分兩種:
   - 有自己片段的:程式行號引用、釘版本不合法——鍵是(規則, 片段),片段就是那串 `` `路徑:行號` ``。
   - 整行層級的(片段其實是整行前 60 字,插字會改到它):沒寫來源的現況描述、SEE 只放連結、回頭條件格式不合、條件寫錯、條件寫在不評估的地方——鍵只看規則。O 本來就犯,N 照樣犯 → 不報。
3. **提醒的比法**(這兩種只在提交前算,推送與 CI 本來就不算):
   - 否定現況句:現行每行只出一條提醒、只看第一個命中(`_ns_negation_hints` 取 `hits[0]`)。配到 O 的行改成:N 與 O 各取全部命中的字眼,照計數比,N 多出來的字眼裡取第一個出那一條提醒(片段照現行從那個字眼的位置切);沒有多出來的就不提醒。命中受整段文字影響(規則句、歷史句的排除),插字讓舊命中消失或新命中出現都照 N 的結果算。
   - 筆記前綴提醒(`_ns_rule_hints`,只看摘要的 RULE 行):鍵是警告字串本身;O 與 N 同一天算,照計數比。
4. **一起套用的**:doctor 的事後掃描(呼叫同一支 `_note_shape_eval`,讓推送放行的行事後也不再被唸)。**不改的**:`_note_shape_eval` 後半「新程式檔喚醒舊引用」那一路(它自己有整行相等的舊行判定);筆記格子的舊行判定(`_ns_old_keys`/`_ns_slot_key`:同前綴、同核心一句的文字鍵、連結只增不減,只套摘要——插字會改到核心一句,格子仍當新寫,見 REVISIT);`_notelines_new` 的新寫行定義與交出的 rows;第二層筆記內容審;存量漂移檢查。
5. **推送範圍的舊版**:起點版本裡沒有的行(這次推送才寫、又在後面的提交補字)不算舊行,照整行查——起點是唯一的「舊」。提交前同理,HEAD 裡沒有就是新。

## 實務隱患

- **繞過**:有人在舊句中間插一段新的程式現況(例如在舊 DEP 裡插進新的函式名與行號)。行號引用照第 2 點是片段比對,新插的行號引用照擋;沒寫來源這條整行層級的規則,舊行本來就犯、插字不會讓它更糟,不報——新塞的現況描述要靠第二層判定者看。這是取捨,寫進天花板。
- **效能**:改到的筆記多一次起點版本的批次讀;每條新行只跟篩過的候選比,一篇最多 200 對、單行超過 2000 字不配對(SequenceMatcher 最壞接近行長平方)。記憶體只多起點版本的那幾篇全文。
- **併發**:已排除:只讀 git 物件,不寫任何檔;治理帳寫入照舊。
- **回滾**:還原這一個提交即回到整行查;沒有持久狀態。
- **相容**:舊專案升級後擋得變少、不會變多(只減不增);已排除:新舊互讀——不改任何帳或設定格式。
- 已排除:金流:這道檢查只讀筆記與 git 物件,不碰任何付款流程
- 已排除:對外送出:不呼叫網路、不寄送、不寫到 repo 之外
- 已排除:不可逆:只決定擋不擋、印什麼,還原一個提交就回到原本的判法
- **守衛面**:這是擋提交與推送的閘,改的是「哪些違規算新的」——放得太寬就是一條繞過的路(見上面〈繞過〉與天花板 1),所以不排除、照走設計審。

## 回退

出事時還原這一個提交即可:判定回到「新增的行整行查」,沒有寫入任何帳或設定格式,不用收拾。已經靠這條放行、推上去的舊行不會被追溯擋下(閘只看新寫的),要追查就跑 `lumos note-shape --diff <起點>..<終點>` 用還原後的版本重看那段範圍。

## 天花板

1. 插字放過的是「舊行本來就犯的違規」,不是「插進來的字一定沒問題」:插進一段新的程式現況到沒來源的舊 DEP 裡,第一層不會擋,要靠第二層判定者。
2. 只認「純插入」:補更正時順手改了一個錯字,整行照新寫查。
3. 只看起點版本:範圍中間某個提交改過、後面又插字的,以起點為準;筆記在範圍內改名就配不到,照整行查(偏嚴)。
4. 只篩「開頭或結尾 8 個字相同」:句首、句尾兩頭都插字,或舊行不到 8 個字,配不到,照整行查(偏嚴,不是漏洞)。
