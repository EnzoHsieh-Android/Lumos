## 發現

**R2C1** 「O 被用掉」的計次口徑沒定義,字面實作可能讓主要場景永遠配不上
severity: major
blocking: 是 — 口徑選錯,S1、S2 的「句尾補括號」例子直接配不上或誤配,而且規格沒給可驗證的定義
引句:「O 這段文字在終點版本整篇出現的次數比起點版本少(原行真的被改掉了);一個 O 只能配一個 N(一對一,先到先配)」
- **子字串讀法**:「這段文字整篇出現幾次」若照字面用 `text.count(O)`,句尾補更正的 N 本身就含有 O。終點次數等於起點次數,「O 被用掉」永遠不成立。
  - 例:O=`DEP:付款走舊閘道 scripts/pay.py 還沒換掉`,N=O+`(更正:…)`。輸入 → 預期被判「沒配上、照整行查」,S1 的句尾例子就紅了。
- **整行相等讀法**(`strip()` 後的行相等)才對。它還能解決「O 以子字串形式還在別行」的問題,因為別行只含 O、不等於 O,不算數。規格要寫死是哪一種。
- **預算沒寫**:同篇有兩條一字不差的舊行 O×2,只改其中一條,起點 2、終點 1。每段文字要有「預算 = 起點行數 − 終點行數」,配一個扣一個。規格只說「一對一」,沒說預算怎麼算。
- **先到先配的副作用**:另外在旁邊抄一份 O 再加字(N2,行號較前),真正被改的那條 N1 行號較後。
  - 預算只有 1。N2 先配到,拿走豁免。
  - 真正補更正的 N1 反而被整行查而被擋。
  - 誤擋的是誠實的使用者,放行的是抄的那份。
  - 規格說「抄一份」是繞過,卻在重複行的情況下防不住。
- 驗收條款沒有任何一條涵蓋「重複舊行」或「O 以子字串留在別行」。

**R2C2** 用 N 的脈絡去算 O,讓「把舊行移出圍欄再插字」可以便宜繞過
severity: major
blocking: 是 — 一條便宜的繞過路,而這是守衛類的閘
引句:「兩邊都用 N 在終點版本的脈絡(圍欄內外 `visible`、重建標記 `regen`、檔案清單),同一把尺。」
- 程式現況:`_ns_revisit_violations(ln, reg, visible)` 在 `visible` 為假時回空(`scripts/lumos:27611`)。
  - `_ns_check_line` 本身不看圍欄,圍欄由呼叫端用 `vis` 決定要不要查。
  - 所以圍欄內的行在起點版本根本沒有「舊違規」。
- 繞過步驟:
  1. 起點版本圍欄內有一行 `DEP:付款走舊閘道 scripts/pay.py:123`。圍欄內不查,這行沒有違規。
  2. 這次提交刪掉圍欄標記,並在句尾補「(更正:…)」。
  3. O 的區塊同屬 body,所以區塊檢查通過;O 的文字也不再作為獨立行存在,算「被用掉」。
  4. 規格叫 O 也用 N 的脈絡算:O 在「圍欄外」被算出一條行號引用違規。N 也有同一條。計數相等,於是整條被減掉。
- 預期應是:O 照它在起點的脈絡算(圍欄內=0),N 的違規被完整報出。
- `regen` 同理。重建標記是整篇的屬性,起點與終點可能不同(這次才加或才拿掉 regen)。
- 同族的便宜路:規格承認「新塞的現況靠第二層」。但「刪一條舊的無來源行,在同區塊別處寫 `O+新現況`」也能配上,因為只比區塊、不比位置。
  - 應限制為 O 與 N 的圍欄可見性相同,或 O 用自己的起點脈絡算。

**R2C3** 「新程式檔喚醒舊引用」路徑的起點被悄悄改掉,與 S11「跟今天一樣」衝突
severity: major
blocking: 是 — 字面實作會讓這一路比今天更寬鬆,而且與驗收條款矛盾
引句:「`_note_shape_eval` 前半(新增行)與後半(新程式檔喚醒舊引用,原本的 `ln.strip() in old` 整行相等)都改呼叫它」
- 程式現況(`scripts/lumos:28440` 附近):今天的 `old` 取自 `gl_reader(p)`,也就是上線點版本,再加 `old_by`。
- 規格〈做法〉2 把「起點版本」定義為 `base_where`:
  - 提交前是 HEAD。
  - 推送是被夾到上線點的推送起點。
  - doctor 是上線點。
- 這兩個起點不同:
  - 提交前:HEAD 版本比上線點版本新。上線點之後、HEAD 之前才寫、現在因新程式檔而指向它的行,今天會被查。改用 HEAD 後變成「舊帳」而放過。
  - 推送:`base_where` 是推送起點夾到上線點之後的點,同理偏寬。

- 另外,helper 簽名收「起點版本的行」,沒有 `old_by` 的位置,而喚醒路徑今天是 `old ∪ old_by.get(nfc(p))`。

**R2C4** 否定詞表「項目鍵」在現有程式裡拿不到,「插入範圍內的命中」未定義
severity: minor
blocking: 否 — 要多改一支函式與回傳形狀,但不是方向性錯誤;照字面實作多半是過報或例外,而提醒本來就吞例外
引句:「鍵是命中的**詞表項目**(`_NS_NEG_NARROW_*` 裡的那個字眼,`not … yet` 這種浮動區間取「not…yet」這一項,不取比到的整段)」
- `_NS_NEG_NARROW_RE`(`scripts/lumos:27684`)是單一個無分組的 alternation。`_ns_negation_hits` 回的是 `(m.group(0), 位置)`,就是比到的整段文字。
  - 要拿到「項目」得新增回傳、或用 `m.group(0)` 事後反推。反推要處理三件事:
    - 英文 `_CI` 分支比到的是原文大小寫,`Not Yet` 與 `not yet` 要正規化成同一項。
    - 字面的「not yet」分支與浮動的「not…yet」是兩條分支,要決定算不算同一項。
    - 中文詞按長度排序,「目前沒有」與「目前還不」等是不同項。
  - 照字面直接拿現成回傳值當鍵,浮動區間每行文字不同,計數永遠不相等,會多報。
- 命中位置在 `m.start()`。
  - 例:O=`service is not deployed`,N=O+` in prod yet`。新命中 `not deployed in prod yet` 起點在 O 的範圍內、終點在插入範圍內。
  - 規格說「取落在插入範圍內的那一個命中切片段」,這個例子找不到,沒有定義。
- 現有 `_ns_negation_hints` 只用 `hits[0][1]` 出片段。要出「新增項目的那一個命中」得改函式簽名,而規格只說「收集器多收一個參數」。
- 驗收:S2 只測「還沒」→「尚未」這種字面不同詞,沒有浮動區間例。

**R2C5** 2000 對上限擋不住耗時
severity: minor
blocking: 否 — 只在大量長行時才慢,但規格自己的數字說明不了界線
引句:「所以單行 2000 字上限加每次 2000 對總上限」
- 我實測 `SequenceMatcher(autojunk=False)`:2000 字低變化字串一對 0.17 秒(`"ab"*1000` 類)。
- 2000 對約 340 秒,放在提交前掛鉤上。規格的「最壞一對 0.2 秒」乘 2000 就是 400 秒,不是界線。
- 候選篩選只看「開頭或結尾 8 字相同」。表格行(`| 日期 |…`)、`- **` 開頭的條列、同前綴摘要行都很容易同前綴。
- 缺便宜的前置剪枝:
  - 先用 `O` 是否為 `N` 的子序列做 O(n) 判斷,不通過就不跑 `SequenceMatcher`。
  - 先判長度差。
- 補充:插入段長度其實就是 `len(N)-len(O)`。可用 `difflib` 之外的簡單雙指標,把全部比對降到 O(n)。這比 `PRIOR-ART` 說的「用標準函式庫」更簡單。
- `SequenceMatcher` 本身不保證找到最優對齊,O 是子序列時仍可能回出 `replace`,只會偏嚴,不會偏鬆,所以不是正確性問題。

## 逐項回答

**1. 兩條一字不差的舊行,只改其中一條**:起點 2、終點 1,在「整行相等」的讀法下可正確配對。但先到先配加預算不清,可能讓旁邊抄的那份拿到豁免、真正被改的反被擋(R2C1)。

**2. 舊行搬到同篇別的區塊再插字**:跨區塊(body 與 summary)會因區塊不同而不配,這部分正確。同區塊內搬位置則不受限,可以配對。圍欄可見性不同是真洞(R2C2)。

**3. N 比 O 長,但 O 在終點以子字串形式還在別行**:整行讀法下 O 是否被用掉不受影響,正確。子字串讀法下句尾補括號整個失效(R2C1)。

**4. 違規計數與改法字樣**:只有 `條件寫錯` 的改法帶細節,其他是常數(R2C6)。

**5. 詞表項目鍵**:程式碼拿不到,要改回傳;`not…yet` 與字面 `not yet` 是兩條分支,大小寫要正規化。落在插入範圍內的命中,在跨界例子下無定義(R2C4)。

**6. doctor 以上線點為起點、上線點之後才寫又改的行跟今天一樣**:核對成立。起點版本沒有 O,所以不配,整行查,與今天同。S10 的唯一預期要補對照組(R2C8)。

**7. 資料狀態五問**:
- 起點讀不到(新 repo、改名、非 UTF-8)偏嚴,正確。
- `base_where` 為 None 時要小心 `_nodehome_cat_blobs` 的規格,應以空樹或略過處理,規格已寫「沒有起點版本照整行查」。
- NFC:規格說「讀起點版本用原樣路徑」,方向正確,因為 `old_by`、`texts_by` 的鍵是 NFC 過的,而 git 路徑是原樣。
- 路徑含換行會讓批次讀整批失敗(`scripts/lumos:26440`),規格寫了「批次讀失敗照整行查」,吻合。
- BOM:`_notelines_new` 用 `utf-8-sig`,起點版本也要用同一個解碼,否則第一行的 BOM 讓比對錯位。規格沒寫。

## 實務隱患

- **繞過**:除了 R2C2,還有「刪一條有違規的舊行,同區塊別處寫 O+新內容」。規格已承認靠第二層。
- **效能**:R2C5。
- **併發**:只讀 git 物件,同意規格的排除。
- **回滾**:同意,還原一個提交即可。
- **相容**:同意「擋得只會變少」,唯獨喚醒路徑除外(R2C3)。
- **守衛面**:規格正確標為不排除。主要風險在 R2C2。

## 總結

這份修訂稿折入了 r1 的大部分修正(抄一份舊行、doctor 起點、前綴提醒不套用)。但新增的「O 被用掉」、「兩邊用 N 的脈絡」兩段自帶未查證的假設,喚醒路徑的起點則與原文銜接處不一致。實作前這三處要先定死,再補對應驗收條款。
