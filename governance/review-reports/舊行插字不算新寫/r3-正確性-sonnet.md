## 發現

### R3C1 子序列不是「插字」,加上額度就能把一條新寫的行洗成舊債
severity: major
blocking: 是 — 照字面實作,「刪一條有違規的舊行,在遠處寫一條新的」會被整行放行,正是這份 spec 想擋的繞過。
引句:「O 是 N 的子序列(雙指標由左往右,貪心對齊),N 比 O 長;O 不到 8 個字不配;插入的總字數不超過 500 字、N 不超過 2000 字。」

子序列不要求插入是連續的一兩段。再加上「頭 8 字或尾 8 字相同」,條件就很容易滿足。

- **輸入:** 起點版本有 `DEP:付款走舊閘道 還沒換掉(見 Systems/Pay)`,沒寫來源,所以 O 有 1 條「現況描述沒寫來源」。作者在同一個提交裡刪掉這行(清舊帳,額度=1),又在同區塊遠處寫一條 400 字的全新 DEP。這條新 DEP 把 O 的字依序散落在句子裡,並以 `還沒換掉(見 Systems/Pay)` 結尾。
- **預期(spec):** 尾 8 字相同、O 是子序列、N 比 O 長 400 字。只有一條 N,「配給位置最近」不起作用,所以配上。`_ns_check_line` 對 N 與 O 各算出 1 條同規則的違規,N 不比 O 多,整條放行。
- **結果:** 一條全新的、沒來源的現況描述通過了閘。spec 的〈實務隱患·繞過〉只寫了「抄一份舊行」與「搬出圍欄」,沒有涵蓋「刪一條、重寫一條」。
- **規則為何失效:** `context_marker_warnings` 對單行最多回 1 條警告(`scripts/lumos:3932`)。所以「沒寫來源」「SEE 只放連結」「回頭條件格式不合」在計數層其實是 0 或 1 的布林值。N 只要有一條舊債可借,不管它多新,都能整行過關。
- **建議:**
  - 要求 N 和 O 在同一個 diff 區塊裡配成對。提交前 `git diff -U0` 的 `-O`/`+N` 本來就相鄰;推送前用範圍淨差異。
  - 或要求插入段數 ≤ 2、每段連續、O 的字在 N 中不被穿插。
  - 光靠 500 字上限和位置最近,擋不住。

### R3C2 額度按「文字」算,配對按「單行的區塊與可見性」判,同文字多份時 O 的身分沒定義
severity: major
blocking: 是 — S5 沒有唯一預期,而且同文字分散在不同可見性或不同區塊時,額度可以借別份的名額。
引句:「一段文字的配對額度=起點行數 − 終點行數(大於 0 才有)。配一次扣一次,一對一。」

額度表的鍵是去空白後的整行文字,不分區塊也不分可見性。但「同區塊同可見性同 regen」和「O 起點行號」都是單行屬性。起點版本有兩份以上同文字的 O 時,spec 沒說「被用掉的」是哪一份。

- **輸入 A(S5 本身):** 起點版本 O 在第 5 行和第 20 行各一份,額度=2−1=1。作者把第 5 行改成 N,又在第 20 行旁抄一份 N。「原位那條」要看 O 的起點行號,可是 5 和 20 都是 O。取 5 就放寬第 5 行的 N,取 20 就放寬旁邊那份抄本。兩種讀法都合字面,S5 寫不出唯一預期。
- **輸入 B(繞過):** 起點版本 O 同時出現在圍欄內(不可見,違規不計)和圍欄外(可見,有違規)。作者只刪掉圍欄內那份,圍欄外那份不動,再在別處寫 `O+新內容`。額度=1(來自被刪的圍欄內那份),卻拿去配了「可見」的 O,N 的違規被放寬。
- **建議:** 額度改成逐「行實例」記帳,即 (區塊, 可見性, 起點行號) 為鍵。或者規定只在「該文字全部實例的區塊與可見性都相同」時才配。

### R3C3 「N 由小到大處理」與「O 配最近的 N」是兩種相反的演算法,抄本放在前面時 S5 會翻
severity: major
blocking: 是 — 實作者選 N 優先或 O 優先,結果不同,抄本放前面時防繞過規則失效。
引句:「配給終點行號跟 O 起點行號最接近的那條(真的被改的那行通常在原位,旁邊抄的那份不在)」

同一節還寫「N 照終點行號由小到大處理」。若實作成「逐個 N,挑還有額度的 O」,N 優先,先到先得。

- **輸入:** O 在第 40 行,額度=1。作者在第 10 行寫抄本 `O+惡意內容`,在第 40 行(原位)寫真正的補更正 N。
- **預期(spec 字面兩種讀法):**
  - N 優先:第 10 行的抄本先被處理,拿走額度,真正的原位修改反而整行被查。
  - O 優先:O 先選最近的第 40 行,抄本被查。
- **結果:** spec 沒有規定哪個先。「旁邊抄的那份不在原位」只在「O 優先」下成立。
- **建議:** 明寫成兩階段。先對每個 O 收集全部候選 N,再各選最近的;衝突時再依序解。並加一個「抄本在原位之前」的測試。

### R3C4 否定只判插入的字:失去整行語境,接起來的字串也不安全
severity: minor
blocking: 否 — 只影響提醒,不影響擋不擋。但它違背 spec 自己「判定放寬只會變少」的承諾,並且讓天花板 8 的說法失真。
引句:「把各段插入的字依序接起來、段與段之間放一個空白,交給同一支 `_ns_negation_hits`」

三個問題:

1. **整行語境全部遺失。** `_ns_negation_hits`(`scripts/lumos:27742`)的排除判定多半看整行:
   - REVISIT 行(`_revisit_split`)。
   - `RETIRE-IF:` 與 `為什麼還不做:` 開頭。
   - `_NS_NEG_FIELD_RE` 欄位遮罩,例如 `[retire:條件還沒…]`。
   - 同一小段裡的 `_NS_NEG_RULE_RE`(不准、不要等)與 `_NS_NEG_HIST_RE`(當時、原本等)。
   - 否定字眼後 9 字內的修飾語。

   輸入:`RETIRE-IF: 連續四週零觸發`,補上 `(更正:尚未量到)`。今天整行因為 `RETIRE-IF:` 開頭而靜音;依 spec 只判插入的字,「尚未」會出提醒。輸入:`當時支援 A` 插進 `尚未`,整行有 HIST 字眼而靜音,只判插入的字卻會提醒。

2. **「接起來放一個空白」不是斷點。**
   - `_NS_NEG_SEG_CUT_RE` 不含空白。
   - 英文那支 `not ... yet` 的視窗允許空白,最多 40 字。
   - 引號配對 `_ns_neg_quote_spans` 可跨段。

   輸入:兩處各插 `not` 和 `yet`(各自不構成否定),接起來變 `not yet`,命中。另一個輸入:一段插入以 `“` 結尾、另一段以 `”` 開頭,中間會被遮蔽。建議段間用硬斷點(例如 `。`)。

3. **天花板 8 說錯了。** 貪心對齊不只改片段位置,還會改命中本身。
   - 輸入:O=`付款走舊閘道還沒換掉(見 Systems/Pay)`,N=`付款走舊閘道,還好沒事,但還沒換掉(見 Systems/Pay)`。
   - 貪心把 O 的「還、沒」對到 `還好沒事` 裡,於是「插入的字」變成 `事,但還沒`,命中了舊行本來就有的「還沒」。這正是這份 spec 要消除的重複提醒。

### R3C5 效能與上限的口徑不完整
severity: minor
blocking: 否 — 沒有出現錯誤判定,只有成本與邊界沒寫清楚。
引句:「子序列判定是一趟線性掃描,5000 次 × 2000 字是毫秒級。」

- **耗時:** 我用純 Python 逐字迴圈實測 5000 次×約 2000 字,約 0.35 秒,不是毫秒。用 `it=iter(N); all(c in it for c in O)` 才是 C 速度。需要改字句,也要避免實作者寫成慢版。
- **預篩沒設上限:** 上限只算「子序列判定」。「開頭或結尾 8 字相同」的預篩是 N 筆乘 O 筆的對掃,沒有上限。重建筆記(`regen`)一次新增幾千行時是 10⁷ 級的字串比較。建議用 8 字頭、8 字尾建 dict 索引。
- **批次讀沒定上限:** `_nodehome_cat_blobs_capped(repo_root, specs, max_bytes)`(`scripts/lumos:26424`)必須傳 `max_bytes`,spec 沒指定常數,也沒說超限時的行為(應為不配、偏嚴)。〈做法〉2 只列了「讀不成 UTF-8、批次讀失敗」。
- **NFC 路徑:** 路徑 NFC 只能當比對鍵,拿去 git 查要用原樣(見 `Systems/筆記內容閘` 的 PITFALL)。spec 說「路徑跟 reader 同一個」,但 `_notelines_new` 交出的 `p` 本身就是 NFC 化的。這點沿用現狀,不新增風險,但 spec 應順便註明。

### R3C6 放寬帳:「減掉的條數」要算兩遍,單行事件可能變大
severity: minor
blocking: 否 — 只影響記帳完整性與量測,不影響擋不擋。
引句:「由 `_note_shape_eval` 多收一個容器參數(同 `hints` 的傳法,有預設值;不傳就不收)」

- **要算兩遍:** 「減掉的違規數、提醒數」要同時算整行版本和配對版本才能相減。spec 只說容器參數,沒寫要跑兩遍,也沒寫成本。
- **事件變大:** 一筆事件帶最多 50 組 `[路徑, 終點行號]`。這個 repo 的筆記是中文長路徑,一行約 5KB,超過 4KB。治理帳是不上鎖的 `open(..., "a")` 追加(`scripts/lumos:1217`),寫入器沒鎖的問題 spec 沿用既有 Issue。但單行變大就更容易被別的寫入者交錯寫壞 JSON。建議上限降到 10~15 組,或只存計數。
- **放行也寫帳:** 提交被後面別的鉤子擋掉時,帳已經寫了,工作樹多一筆未提交的帳。這與 `Systems/筆記內容閘` 的 WHY「沒違規的放行不寫帳」相衝,spec 已列為例外並要求同步,這點成立。

### R3C7 S5、S6 的字面承諾比演算法強,測試寫不出「任何」
severity: minor
blocking: 否 — 只影響測試的覆蓋,不是行為錯誤。
引句:「當舊行有任何刪除或替換(包括改前綴)、或在起點版本是別的區塊、或在圍欄裡,應 照整行查」

- **「任何替換」不成立。** 子序列判定下,`v1` 改 `v12`、`已` 改 `已經` 都只是插字,放行。「改前綴」若是在行首插新前綴、尾 8 字相同,也配得上。例:O=`FACT:A…(來源:部署)`,N=`DEP:FACT:A…(來源:部署)`。S6 只能列舉具體的替換例,不能寫成通則。
- **S5 沒有唯一預期,** 見 R3C2。
- **其餘 S1~S4、S7~S14:** 各寫得出唯一預期,但有兩個前提。S13 要用 hook 已上線的提交造「上線點前就在的舊行」。S12 的改名要靠 `git diff --cached` 的改名偵測,改名且有修改時,`+++ b/新路徑` 只回變動行,起點版本沒有那個路徑,所以不配,符合預期。
