## Findings

**G1** 配對條件沒要求舊行已被取代,複製舊行再加字也能過
severity: major
blocking: 是 — 守衛面被自己宣稱成「所以不排除」,卻留著一條成本極低、spec 沒涵蓋的繞過路。
引句:「候選只看同一篇、比 N 短、開頭 8 個字相同或結尾 8 個字相同的行」
- 問題:配對只看 N 與 O 的字面關係,沒要求 O 在終點版本已經不見。天花板 1 只講「在舊 DEP 裡插字」,沒講這一種。
- 例:筆記裡有上線前、沒帶來源的 `DEP:付款走舊閘道`,原行不動。作者在它下面新寫一行 `DEP:付款走舊閘道,另外訂單服務目前直連 Redis 叢集`。
  - 這行對 O 是純插入,O 在同一區塊,所以配到。
  - 「現況描述沒寫來源」是整行層級、只看規則,O 本來就犯,所以不報。
  - 結果:一條全新的沒來源現況,原樣過關。
- 同源問題:spec 沒說配對是否一對一。N1、N2 兩條新行可以共用同一個 O。
- 建議:O 與 N 的配對要「消耗」O,也就是 O 在終點版本的出現次數少於起點版本才算被改寫。同時一對一配對。
- 既有先例:`Projects/筆記格子寫法與過期檢查_計劃` 天花板 7 承認複製舊行被放過。那裡只是整行複製,沒有新字進來。本案多了「任意新字」,性質不同。

**G2** 本案是第三套舊行判定,與格子的前綴提醒會對不上,新規則也沒有預設
severity: minor
blocking: 否 — spec 已用 REVISIT 2026-10-15 掛住格子那半。但步驟 3 的做法在開擋時會造成「有預覽、沒擋」的反差,需補一句。
引句:「筆記前綴提醒(`_ns_rule_hints`,只看摘要的 RULE 行):鍵是警告字串本身;O 與 N 同一天算,照計數比。」
- 現在有三套「舊行」判定:
  - 「新程式檔喚醒舊引用」整行相等:`scripts/lumos:28453`。
  - 格子的「同前綴、同核心一句的文字鍵」:`_ns_old_keys` 在 `scripts/lumos:28193`。
  - 本案的「純插入」。
- 例:舊 RULE 行(缺格子的舊寫法)句尾補 `(更正:…)`。
  - 本案的前綴提醒:O、N 的格子警告字串相同,不提醒。
  - 格子開擋後:核心一句變了,算新寫,被要求補齊格子。
- 結果:`_ns_rule_hints` 在 `slot_is_new` 時回的 `筆記格子『RULE:』…` 警告,正是格子擋的預告。本案把它按舊行壓掉,等於預告被關掉,開擋那天才第一次擋人。這剛好重演 spec 想解決的「逼人跳過」。
- 建議:二選一。
  - 步驟 3 的前綴提醒先排除格子類警告,維持預告。
  - 或把 REVISIT 提前到「格子開擋日」,而不是固定日期 10-15。
- 格子計劃自己的回頭日是 2026-12-15(看開擋了沒)與 2026-10-11,兩邊日期不同步。
- spec 未定義「之後加在 `_note_shape_eval` 後面的新規則」的預設。使用者問的 `Projects/筆記測試綁定要存在_計劃` 若出現,新規則該預設整行查(報),不是預設跟隨本案的過濾。
- 要明寫進〈不改的〉,並讓 `Systems/筆記內容閘` 的合約點到這一條。
- `lands_in` 只有 `Systems/筆記內容閘`,該寫的「三套舊行判定怎麼並存」要落在那裡,不要只留在計劃。

**G3** 「只看規則」的鍵會讓舊行的一個錯遮住新插入的另一個錯
severity: minor
blocking: 否 — 影響面限於已經壞掉的 REVISIT 行,但鍵的粒度有明確缺口。
引句:「整行層級的(片段其實是整行前 60 字,插字會改到它):沒寫來源的現況描述、SEE 只放連結、回頭條件格式不合、條件寫錯、條件寫在不評估的地方——鍵只看規則。」
- 「條件寫錯」(`scripts/lumos:27611` 起的 `_ns_revisit_violations`)的訊息是 `;`.join(errs) 組成的清單,同一個規則名底下有多種錯。
- 例:O = `REVISIT:[when-file:a.py][by:2026-13-99] 做了就改`(期限日期無效)。在句中插入 `[when-test:不存在的測試]`。
  - O 與 N 都命中「條件寫錯」,鍵相同,不報。
  - 但新插進去的條件是新問題。
- 例:「條件寫在不評估的地方」(開頭欄位其他欄)同理。O 已有一個不評估的探針記號,N 再插第二個,也不報。
- 建議:這幾種把錯誤清單內容併進鍵,例如鍵取 `errs` 的各項。

**G4** 以 HEAD 為起點,在同一批工作裡改自己剛插的字,會整行重查
severity: minor
blocking: 否 — 偏嚴方向,但會落回 spec 想避免的「逼人繞過」。
引句:「起點版本=`_note_shape_eval` 收到的 `base_where`(提交前是 HEAD;推送前是推送起點、已夾到筆記形狀擋的上線點)」
- 例:提交 1 在舊 DEP 句尾補 `(更正:A)`,過關。提交 2 發現措辭不對,把括號裡改成 `(更正:B)`。
  - 提交 2 的 O = 提交 1 的版本,N 對它是 delete + insert,不是純插入,整行照新寫查,舊 DEP 的沒來源違規又冒出來。
  - 推送範圍(對最初起點)反而是純插入。同一組內容,提交時被擋、推送時能過。
  - doctor 的事後掃描對 golive 起點,結果與提交時也不一致。
- 建議:二選一。
  - 承認「提交時以 HEAD、推送時以起點」並寫入天花板,提醒作者改字用 amend 或壓成一個提交。
  - 或配對時改用「該提交鏈上第一個含 O 的版本」。
- 同一類:staged 的 `_ns_diff` 帶 `-M`(`scripts/lumos:27208`)。筆記同次改名加補更正時,`base_where:path` 讀不到舊路徑,整行照查。spec 只在天花板 3 講推送範圍的改名,staged 沒講。格子計劃有用 `_nodehome_name_status` 帶回舊路徑的先例,本案沒引用。

**G5** 否定現況句:同字眼出現兩次時片段位置沒定,量測基準也會變
severity: minor
blocking: 否 — 影響提醒的精準度與 `Projects/否定現況句配回頭條件_計劃` 的第 8 週抽樣,不是正確性。
引句:「N 多出來的字眼裡取第一個出那一條提醒(片段照現行從那個字眼的位置切);沒有多出來的就不提醒。」
- 例:O 已有一個「還沒」。補更正括號裡又出現一個「還沒」。
  - 計數 N=2、O=1,多出來的是「還沒」。
  - 但要用 N 裡第幾個「還沒」的位置切片段?`_ns_negation_hints` 現行取 `hits[0]`(`scripts/lumos:27784` 起),會切到舊的那個。
  - 提醒念的是舊句,不是剛插進去的,讀的人更困惑。
- 建議:多出來的那次要取 N 裡「最後對上的那個位置」,或明寫取插入範圍內的命中。
- 量測影響:`Projects/否定現況句配回頭條件_計劃` 的 RETIRE-IF 是第 8 週抽 30 行、不到三成就撤,樣本不足延到第 16 週。上線後提醒量變少(補更正的舊行被排除),樣本更容易不足。
  - 該計劃的準度基準(12/30 = 40%)是在「整行當新寫」下抽的。
  - 本案上線後口徑變了,卻沒在該計劃留一句「口徑自某日起排除純插入的舊行」。
- 建議:在該計劃補一行說明,否則第 8 週的結論與基準不可比。
- 另外,`hints["seen"]` 與 `tags["seen"]` 是「要判的新行數」,spec 沒說被配對排除的行算不算 seen,這會影響「只在這次有新寫行時印設定提醒」的行為。

**G6** 效能與讀取失敗語意沒有總量上限
severity: minor
blocking: 否 — 單篇有上限,但提交前掛鉤是同步等待,整批清漂移時沒有整體預算。
引句:「每條新行只跟篩過的候選比,一篇最多 200 對、單行超過 2000 字不配對」
- 「開頭 8 字相同」過濾很弱。摘要行全是 `PITFALL:`、`REVISIT:`、`WHY:[202` 開頭(`PITFALL:` 正好 8 字)。`Systems/筆記內容閘.md` 有 30 多條 PITFALL,候選幾乎全中。
  - 200 對的上限會被毫不相關的候選吃光,後面真正的配對靠運氣落到整行查。
  - 配對順序沒定義,結果隨排序而變。
- 量測:我用 `difflib` 試過。2000 字、低字元多樣性、`autojunk=False` 的最壞情形單次約 0.2 秒。200 對約 40 秒/篇,預設 autojunk 開著快很多。
  - 對 `Systems/筆記內容閘.md` 的長摘要行實測,插在 1/3 處與句尾,24 例全是 equal/insert,沒有因 autojunk 失準。
- 但 spec 沒有「整次提交的總時間預算」。格子計劃已有 20 秒截止的先例(見它〈效能〉),本案可借用。
- 讀取失敗語意沒定。spec 只寫「空樹、那篇不存在」照整行查,沒寫 `_nodehome_cat_blobs` 回 None(逾時、路徑含換行、git 失敗)時怎麼辦。
  - 若沿用 `_note_shape_eval` 的 `return None`,會是整道 fail-open 跳過。
  - 格子計劃的做法是「批次讀失敗回 None,呼叫端 fail-open,不當成沒有舊版」,避免把舊行誤擋。
  - 本案應明寫:讀不到起點版本就照整行查(偏嚴),並記一筆帳。
- NFC 陷阱(`Systems/筆記內容閘` 既有 PITFALL):`old_by` 是以 NFC 路徑為鍵,拿去 git 讀起點版本必須用原樣路徑。spec 只說「照 `_ns_base_summary_lines`」,實作時要避免誤用 NFC 鍵。
- 建議:加一條 S 條款覆蓋「候選過多時的順序與上限」,以及「讀不到起點版本」。

**G7** RETIRE-IF 的觀測量在帳上不存在,接不上電
severity: major
blocking: 是 — 專案鐵則 4 要求回頭條件要能接電;這裡兩個量都沒有帳可看。
引句:「②治理帳顯示這條一次都沒放行過(沒人補更正,機制是死的)」
- `cmd_note_shape`(`scripts/lumos` 約 28560 起)的註解寫明:沒有違規的放行不寫帳(「刻意…沒違規的放行不寫」),只有 blocked、warned、skipped、hinted 會寫。
- 本案的「放行」是靜默減少違規。沒有任何事件記「這行因為純插入被放行」。
- 結果:
  - 「②一次都沒放行過」無法從治理帳判斷,查不到。
  - 「①抽查被放行的行,一半以上借插字塞新問題」沒有名單可抽。
- 抽樣也讀不到:`doctor` 事後掃描跑同一支 `_note_shape_eval`,所以放行的行事後也不再被唸。
- 另外,`Projects/筆記形狀擋_計劃` 的 RETIRE-IF ①(被擋後改用 skip/`--no-verify` 的次數超過被擋次數三成)與 ③(兩條規則零觸發)的分母會變小,卻沒說明口徑自何時起改。
- 建議:放行時記一筆 `hinted` 型的結構欄位事件(幾行、幾篇,加上被放行的規則名),不要印字。並在 `Projects/筆記形狀擋_計劃` 的 REVISIT 2026-11-27 補一句「自本案上線日起口徑改變」。

## 實務隱患:逐類

- **守衛面(繞過)**:G1。另有天花板 1 已承認的插字塞現況,第二層(`_note_audit_items`,`scripts/lumos:28947` 起)確實仍用 `_notelines_new` 的整行看這些行。但送審內容是整行文字,沒有標哪一段是新插的,判定者能否分辨「舊 DEP 加新現況」缺乏保證。

- **併發、回滾、相容、金流、對外、不可逆**:同意 spec「已排除」。只讀 git 物件,還原一個提交即回到整行查。

- **git 呼叫旗標 PITFALL(`_ns_diff` 帶關外部差異、不上色)**:本案只用 `cat-file --batch`,不涉及。若實作改成另寫 `git diff`,必須沿用 `_ns_diff` 的旗標(`t_lumos_content_diffs_all_disable_external_drivers` 會抓)。
