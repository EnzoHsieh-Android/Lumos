## 做法

### 1. c4 卷證目錄

- 取驗證紀錄第一次被提交的提交(`_plan_first_commit`;shallow 由既有 `_git_is_shallow` 先擋)。列那個提交加進來或改名進來的檔:`_nodehome_git(root, "show", "-z", "--name-only", "--diff-filter=AR", "--format=", <提交>)`,`_nodehome_split_z` 拆;只收路徑至少四段、形如 `governance/review-reports/<目錄>/<檔>` 的第三段目錄名,去重。這是「同提交」清單;git 失敗或逾時當空,證據頁寫「同提交:查不到(git 失敗或沒有)」。
- 「計劃名」清單照舊用 `_drift_c4_key` 比對。
- 證據頁全部列出、每個標來源(兩者、同提交、計劃名),排序:兩者 → `code-` 開頭 → 其他,同級照字母;同提交清單超過 3 個時另標「可能含別的計劃的卷證(整批匯入或壓成一個的提交)」。目錄名印到終端前過 `_esc_clean`。
- 範本句改成「提交 <已知就填 sha>;代碼審見 <卷證>」——卷證一律放佔位字,由人從清單挑(整句貼進 `lumos set` 會被第 2 節擋下,逼人換成真的目錄)。
- 預填的 `lumos set` 指令照舊(要改的那項放 `<整項新內容>`),這次不改它的展開與長度處理。

### 2. `lumos set` 多擋兩個佔位字

- `_set_conditions_locked` 的第一道檢查從「值裡有 `_SET_COND_SLOT`」改成「值裡有 `<整項新內容>`、`<卷證>`、`<sha>` 任一個」(三個字串放一個模組常數,跟證據頁印的同一份);訊息點名是哪一個。其他檢查與順序不動。

### 3. c1 與 settle 的訊息

- 兩處印「找不到〈那一種〉」的地方(`_drift_fix_c1` 組的 msg 與 guard settle 的提醒)改用同一支組字函式,字樣改成「找不到〈那一種〉的預告句——可能已經是轉正後的說法(不用改),或被手改過(看一下)」。不改判定、不改回傳值,只改字。

### 4. c3 的理由

- 接線:`_DRIFT_FIX_ALLOWED["c3"]` 加 `"reason"`;argparse `--reason` 的說明改成「c2、c3」;`_drift_fix_c3_args` 裡呼叫既有 `_drift_placeholder_err`(長度與單行由 `_drift_fix_args_err` 既有的 `_drift_fix_reason_ok` 管)。理由先去頭尾空白。
- 補的那一行三種寫法(有 `--by` 且是 pass:「由 [[X]] 解決」;有 `--by` 其他狀態:「參考 [[X]]」;沒 `--by`)都一樣:有給理由就在最後接「;理由:<理由>」,沒給照舊。理由裡的 [[連結]] 不驗存在(同 c2)。

### 5. 刪除守衛跳過工具自裝檔

- `_delguard_parse_diff` 加 `skip` 參數(預設空集合),抽 `-` 行名稱與收 `+` 行回收表兩遍都跳過 `skip` 裡的路徑;跟既有 `_DELGUARD_*` 排除清單分開,不併進去(那份有 `t_precommit_whitelist_drift_guard` 釘著)。
- `cmd_delguard_check`:不是工具鏈本身(`_is_toolchain_repo` 為假)時,`skip = _VENDORED_ALL`;是工具鏈本身時 `skip` 為空(那些檔是它自己的程式)。純路徑判斷,不讀安裝清單、不跑 git,沒有額外時間。
- 跳過時在既有 delguard 治理事件的 `note` 裡加 `vendored-skip=<這次 diff 碰到並跳過的工具檔支數>`(沒碰到就不加)。

## 實務隱患

- 已排除:不可逆:只改本機的工具輸出與檢查,不改筆記內容的寫法;還原提交後外面不用收拾
- 已排除:金流:這是本機命令列工具,不碰任何付款或帳務
- 已排除:對外送出:不寄信、不打外部服務
- 守衛面(碰到):刪除守衛(只提醒不擋)在消費專案少抽工具自裝檔,跳過數記進治理事件;c1 與 settle 只改訊息字樣,不改判定。消費專案自己改工具檔又刪了名稱的情形會被放過,寫進誠實界線
- 資安(碰到):卷證目錄名印到終端前過 `_esc_clean`;範本句不再自動帶目錄名,少一條把外來字串帶進照貼內容的路
- 效能(碰到):卷證目錄多兩次有逾時的 git 查詢(找第一次提交、列那個提交的檔),只在 c4 證據頁跑;刪除守衛的跳過是純路徑比對,沒有額外成本
- 併發(不碰):不新增寫入路徑;set 的寫入與鎖照舊

## 誠實界線

- c4 修正走 `lumos set`,不進漂移修復帳;稽核靠 git 歷史(set 的修改在提交裡看得到)。rtb 回報的第二條(帳上少 c4)因此只以「改成靠 git 稽核」處理,不補帳。
- 卷證目錄的同提交找法,前提是「程式、筆記、卷證放同一個提交」;驗證紀錄另外提交時同提交清單是空的,只剩計劃名比對。範本不自動填,所以找錯不會直接被照貼寫進筆記,但人仍可能從清單挑錯。
- c1 與 settle 的訊息不再區分「已轉正」與「被手改」,由人自己看;rtb 回報的第三條以「措辭不再像出錯」處理。
- 刪除守衛在消費專案一律不看工具自裝檔:消費專案自己改工具檔、刪掉名稱、而圖譜提到那些名稱時,不會提醒。工具檔本來就不該在消費專案被改(更新靠 `lumos update`)。
REVISIT:2026-11-30 看有沒有消費專案自己改工具檔的回報(或 `lumos update` 的指紋檢查抓到被改過的工具檔);有就改成只跳過跟安裝清單一致的
- `lumos set` 多擋 `<卷證>`、`<sha>`:這兩個字串若是某篇驗證紀錄前提裡本來就合法要寫的字,會被擋;機率極低,訊息會說明是佔位字檢查。
