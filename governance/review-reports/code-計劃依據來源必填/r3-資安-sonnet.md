我讀了 r3-repair.patch 全文,重點看了新增的 `git ls-tree -r -z --full-tree`、讀 blob、符號連結解析和 HTML 註解去除這幾段。沒有實跑攻擊,三類都沒找到可利用的洞。

**① 提示注入:已看,無。**
- 計劃內文、路徑和連結目標只進判定函式,沒有進派工詞或 hook 附加段。
- 擋下訊息只回顯路徑,屬於外來文字回顯,依慣例放行。

**② 讀寫與執行越界:已看,無。**
- 所有 git 呼叫都是 list 形式的 `subprocess.run`,沒有 `shell=True`,所以沒有 shell 插值。
- `git cat-file blob` 的參數只有 ls-tree 回傳的物件編號。
- 計劃作者可控的路徑完全不會傳給 git。路徑只拿來在記憶體裡的樹清單查表。
- 符號連結解析只在樹清單內做:
  - 連結內容只拿來讀 blob 當字串。
  - 絕對路徑目標、`..` 跑出 repo 的目標、超過 8 跳的連結,都回 None。
  - 這一段不會讀工作目錄的檔,所以連結指向 `/etc/hosts` 或 `.git/config` 讀不到任何東西。
- 唯一碰到工作目錄的是 `why` 提示裡的 `Path(head[0]) / path` 的 `is_file` 和 `is_symlink`。
  - 它只看存在與否,不讀內容、不寫檔。
  - 路徑已先通過 `_repo_ref_token_unsafe` 和 `normpath` 的檢查,不會含 `..` 或絕對路徑。
  - 最壞只洩漏「這個路徑存在」一個位元,而且只回到作者自己的擋下訊息。
- 快取是程序內的字典,有上限,不落地。
- patch 裡沒有新的密鑰或信箱,也沒有下載來源。
- 測試檔造的符號連結(含 `/etc/hosts`)都建在臨時目錄,而且沒有被讀取。

**③ 非刻意的一步繞過:已看,無。**
- 判定改成查 HEAD 的樹清單,工作目錄裡未提交的路徑不算出處,不會因為檔案剛好存在就意外放行。
- 樹清單讀不到或逾時時回 None,所有 repo 路徑「都不算」。這是失敗時偏嚴格,不是放行。
- HTML 註解去除改走 CommonMark 規則。這是正確性層面的調整,不是資安守衛。要靠註解藏表來通過,需要刻意構造內容,屬系統天花板範圍。
- 這份 diff 沒有新增依賴環境變數的跳過旗標。

總結:最嚴重是「無」,會擋 0 條。
