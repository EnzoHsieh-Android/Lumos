# 正確性審查——code-標籤與評測尺-收斂 r2

白話總結先講:上一輪(r1)折的兩件事,單獨看都修對了,而且都有測試守著,我親手拆過修法、測試真的會翻紅。但這一輪把「跨臂要對齊題目集」那條修法接上以後,漏改了另一個也在用同一批數字的地方——不可逆切換閘自己拿去判斷「新舊尺算不算恆等」的那五個參考值,還在用沒對齊的舊算法。結果是:一旦某一題「只在新排序這邊算數、舊排序那邊算不出來」(或反過來),對外顯示的「提升了幾%」現在算對了,但切換閘自己拿去比對的那個數字反而會跟顯示值兜不起來,判定會說「不恆等」而擋下切換——方向是保守(不會誤放行),但這正是這整條分支想解決的「尺切換恆等斷言反覆不過」那個症狀,以另一種樣子原地重生。我用真實程式碼(未修改)重播過一次,而且拿專案自己現在的知識庫實際跑了一次「對齊 vs 不對齊」的對照組,兩邊算出來的搜尋面數字並不一樣(23/34 題、+75.9% 對 28/34 題、+78.3%)——也就是說,會踩到這個縫隙的情況不是想像出來的極端案例,現在的真實資料裡就有。另外我在審查途中也發現,這份被凍結送審的材料(r2-snapshot.patch)在我審查的當下已經被工作目錄裡尚未提交的修改超前——包含正好修掉我這條發現的一次改動——這件事本身值得記錄,但不影響我對這份材料本身的判定。

## 發現一:跨臂對齊只接到「顯示用的新尺預覽值」,沒有同步接到「切換閘自己拿去比對的參考值」,兩者用了不同批題目

引句:「c_ln, c_rn = _macro(_sal, "c_legacy_ndcg"), _macro(_sal, "c_ranked_ndcg")」

折入一把 `condensed_search`/`condensed_edit`(對外顯示、也是切換後長期驅動 gate 的那組值)改成先取 `_sal`/`_eal`(兩臂/三臂都有效的交集)再算平均,這部分修對了:題級門檻是用「配置窗寬」而非「該題實際候選數」判定有效,search 面 legacy 沒有數量上限、ranked 明講只取前 10,同一題兩邊自然抓回的候選數常常不同,於是一題可能只在其中一臂通過門檻。這個對齊修法我用真實程式碼重播過,行為與宣稱一致(見下方變異測試)。

但同一個函式裡還有另外五個值——`_rn_eq`/`_ln_eq`/`_fp_eq`/`_bp_eq`/`_gp_eq`——是切換判定 `_switch_equal` 真正拿去跟 `cs`/`ce` 比對、決定「新舊尺算不算恆等」的那組參考值,這五個值在這次折入裡完全沒有被碰過:

引句:「verdict["_rn_eq"] = _macro_on(srows, "ranked_ndcg", "c_ranked_ndcg")」

`_macro_on(rows, key, gate_key)` 只用**單一**個 `gate_key`(自己這一臂的 `c_ranked_ndcg` 是否非 None)去篩題,而 `cs["ndcg"]`(即上面引的 `_sal` 那行)現在篩的是**兩臂同時**非 None 的交集。這兩個篩選條件在沒有跨臂落差時剛好命中同一批題(此時 `_switch_equal` 會正確判定恆等),但只要出現「一題只在 ranked 這臂通過門檻、legacy 那臂沒通過」這種折入一本身要處理的情境,`_rn_eq` 篩出的集合就會比 `cs["ndcg"]` 篩出的 `_sal` 集合多出那一題——兩邊拿去比較的分母不再相同,`_switch_equal` 就會判定「不恆等」而擋下切換,即使 `cs["ndcg"]` 這個值本身(折入一修好之後)已經是正確、可以安全拿去切換的數字。

這份材料裡有一句話明確主張兩者是同一批題:

引句:「限縮鍵與新尺值是對同一批列取平均、分母集合相同」

這句話講的是「兩邊同時無資料」那個特例(此時確實同時變 None,這句沒錯);但它被用來支撐整段恆等比對邏輯的前提,而在「只有一臂有資料」的情況下這個前提並不成立——`_rn_eq` 的分母集合(單臂門檻)跟 `cs["ndcg"]` 的分母集合(`_sal` 交集)是兩個不同的集合,不是「相同」。

我在**沒有改動任何程式碼**的情況下,直接呼叫這份材料裡真正的 `report_goldset`/`_switch_equal`,餵進一組人造的兩題資料(一題兩臂都過門檻、一題只有 ranked 過門檻)重現了這個落差:`cs["ndcg"]`(對齊後、正確的顯示值)算出 0.6,但 `_switch_equal` 拿去比對的 `_rn_eq` 卻是 0.75(因為它多算了那題只有 ranked 有效的分數),於是判定回報「search ranked nDCG: 舊 0.75 vs 新 0.6」不相等,擋下這輪切換——即使 `cs["ndcg"]`=0.6 這個值本身是這次修法要保護的正確答案。

實際影響:方向上是保守(★不會讓不該通過的切換誤放行★),但它會讓下一次真的出現跨臂落差的評測輪——不管是這個 repo 的 goldset 之後改版,還是這套工具被 `lumos update` 帶到別的消費端專案、對方自己的歷史帳還沒切過尺——`_switch_equal` 對那幾項指標永遠判不相等,切換永遠卡住,而且不會有任何訊息說明原因出在「顯示值跟比對值分母不一樣」。這正是 [[Issues/尺切換恆等斷言反覆不過]] 這個 issue 本身想根治的症狀,被折入一以新的形狀重新種回去。

我也用這份材料自己的知識庫做了一次不涉及任何合成資料的對照(見下方「作者宣稱數字的獨立查證」):把折入一整段對齊邏輯還原成折入前的寫法,只跑真實 `--goldset`,搜尋面「有效題數/提升率」在同一份語料上確實不一樣(23/34、+75.9% 對 28/34、+78.3%),證明跨臂落差不是我編出來的極端例子,現在的真實資料裡本來就有;`_switch_equal` 現在能不能真的觸發切換,要看它拿到的兩邊題目集合是否對齊,而不是只看 `cs`/`ce` 本身對不對。

severity: major
blocking: 是——恆等判定是這條分支的核心安全論證,而折入一在同一個函式裡改了「顯示/gate 值怎麼算」卻沒有同步改「拿什麼跟顯示值比對」,這是折入本身造成的自相矛盾,不是預先存在、擋了也不會變好的舊帳。方向雖然保守(不會誤放行),但會讓這個機制在跨臂落差真的出現時失去它存在的意義(切換反覆不過),而且沒有任何測試涵蓋這個交互情境。
