## 核心問題:恆等斷言改用交集之後,能不能用題庫/標註構造出「交集清空」來蒙混切換?

結論:**目前找不到能騙過去的構造法**。理由:

1. 觸發 `_switch_equal` 的前提是 `collect_unjudged(...)["count"] == 0`,而這是對「計分觸及集」(search 兩臂各前 10、edit 三條排法各自前 k)裡**每一個節點**都要求已判。只要這個前提成立,對任何一個題目而言,它的計分視窗就是「全窗已判」,而 `_condense` 算出的 `judged` 子列表在這種情況下必然等於視窗本身——不需要交集夠大,一題也一樣,這是集合論上的必然,不是統計上湊出來的。也就是說,只要「未標=0」這個前提是真的,交集大小(1 題或 30 題)不影響恆等式本身成不成立。
2. 我實際推演了「把題庫裡所有搜尋題/改程式題的相關標籤都清空,讓 `eval_search`/`eval_edit` 整批跳過」這條路徑:此時 `srows`/`erows` 會是空陣列,`report_goldset` 裡 `if srows:`/`if erows:` 整段不執行,`_rn_eq` 等鍵根本不會被寫進 `verdict`。這正是新測試 `t_eval_switch_equal_no_data_is_not_equal` 釘住的情境——`v.get(...)` 拿到 `None`,新版 `_switch_equal` 對「兩側同時是 `None`」明確判定不恆等並中止切換,不再走舊版的 `continue`(視同放行)。
3. 我也推演了「讓某些查詢刻意撈不到候選,使 `_sal`/`_eal` 交集為空」這條路徑:結果同上,`_macro([], ...)` 回 `None`,兩側同時 `None`,一樣被新的「兩邊都沒有可比資料」分支擋下,不會誤判為恆等。
4. 檢查了實際落地的 `retrieval-goldset.json` diff:這次只新增了 7 筆 `"final"` 標註(對應 commit 訊息裡「缺陷二讓 7 筆未標現形」),**沒有任何一筆既有標註被修改或刪除**。也就是說,支撐這次真實切換(`eval_head: e75b883c`、`goldset_rev: 6620ac6f9970`、`metric_rev: condensed-v1`)的資料本身,不是靠改動舊答案湊出來的。

引句:「兩邊都沒有可比資料(新尺這條指標零有效題)——不算恆等」

這是我驗證過的正面結果,不構成一條發現,列在這裡是為了交代查證過程與結論依據。

## 發現一:LUMOS_EVAL_HISTORY 現在統一生效,一個環境變數能讓所有寫入點(含觸發不可逆切換那筆)同時不落地

這不是這次改動新開的洞(改動前,`--goldset` 主流程原本就吃這個變數),而是把「防污染」的範圍從一條路徑擴大到全部路徑;它降低了「测试用例意外污染真帳」的機率,同時也讓「一次不小心的環境變數殘留讓正式判定憑空消失」這件事的影響面變大。攻擊者要利用它,前提是已經能控制執行這支評測腳本的行程環境變數,而那已經接近直接控制輸出結果的等級,不算是這份 diff 新開的權限邊界。

引句:「LUMOS_EVAL_HISTORY 優先(測試導向 fixture 帳,不污染真帳),沒設才用本檔旁邊那份正式帳」
