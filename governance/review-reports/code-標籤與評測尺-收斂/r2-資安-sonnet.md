## 發現二:擋「測試污染正式治理帳」的最後一道防線,用的是可以被整行拿掉的 assert

這輪把三處各自組一份的歷史帳路徑收斂成單一解析點 `_history_path()`,也把測試前置從「驗自己剛設的環境變數」改成「驗模組真的解析到哪裡」——方向是對的,而且確實補上了 `--auto`(cochange-proxy)那條原本完全不吃 `LUMOS_EVAL_HISTORY` 的破口。我對照過:環境變數沒設定時,三個寫入點的行為跟改動前一致,沒有影響正常使用;也沒有找到能把這個環境變數塞進外部可控輸入(例如題庫檔內容)、間接改寫路徑的路徑,`open(hist, "a", ...)` 收到的值只來自執行者自己設的環境變數。

問題出在這道「驗模組真的解析到哪裡」的前置檢查本身怎麼寫:

引句:「assert m._history_path() == _hist, \」

Python 的 `assert` 陳述式在直譯器以 `-O`(或 `-OO`、設定 `PYTHONOPTIMIZE`)最佳化模式執行時,整句會被拿掉,不會拋出例外、也不會有任何提示。這一行守的是「測試如果沒有真的把歷史帳導向 fixture,就不准往下跑到 `m.main()`」——一旦這句被拿掉,`main()` 照樣往下跑,而 `main()` 裡真正落地的東西,正是那個一旦寫上就回不了頭的 `metric_rev`/`metric_switch_verified` 旗標,寫進的還是版本控管、供未來每一輪評測讀取的正式治理帳(`governance/eval/retrieval-eval-history.jsonl`)。換句話說,這道「防止把假紀錄寫進正式帳」的最後防線,是靠呼叫方剛好沒開最佳化模式撐著的。

我確認過本 repo 目前找不到任何地方主動加 `-O`/`PYTHONOPTIMIZE`(`grep -rn "PYTHONOPTIMIZE\|python3 -O" .` 沒有命中),所以不是「已經在發生」,是這道防線本身脆弱、依賴一個外部條件。更值得注意的是:目前工作目錄裡 `scripts/test_lumos.py:27231` 已經把同一行換成 `if m._history_path() != _hist: raise RuntimeError(...)`,旁邊還留著理由:「Python 的最佳化模式會把 assert 整行拿掉,守衛就消失了」——代表這個風險已經被專案自己認出來、也已經有現成修法,只是 `r2-snapshot.patch`(這次要送審、標示為「整條分支最終要推出去的完整改動」的材料)裡這一行仍然停在 `assert` 版本,還沒把那個已知修法折進來。

severity: major
blocking: 是——這道防線保護的正是「不可逆」的治理帳旗標(尺一旦切換就回不去),而修法在同一份工作成果裡已經存在、成本很低,沒有理由帶著已知會被 `-O` 整句拿掉的版本推出去。
