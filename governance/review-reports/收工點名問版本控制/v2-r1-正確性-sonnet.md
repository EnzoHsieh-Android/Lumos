## 二、新方案分工帶進來的錯誤

### F1:S6(唯讀輪閉嘴)的驗收條件迴避了 S6 自己承諾要擋的情境

severity: blocker
blocking: 是。判準:S1 定義的觸發規則本身就會讓「唯讀輪」在現實中幾乎不存在,S6 承諾的靜默因此對最常見的唯讀操作不成立,而驗收條件挑了一個不會踩到這個坑的測試掩蓋了它。
觸發規則不解析命令內容,只要跑過 Bash 就算「可能寫檔」;但 `git log`、`cat`、`grep -r`、跑既有測試這類公認的唯讀操作全部都是 Bash 呼叫。照這條規則實作,一輪只做這些事仍會被判定「跑過可能寫檔的動作」而進入下一步,若工作樹上留著別輪或別人的未提交程式碼檔,S6 承諾的「應閉嘴」不會發生——但驗收條件 3 刻意寫成「這一輪只跑 Read/Grep」,不含 Bash,測不到這個最常見的唯讀模式。
引句:「有 Bash 呼叫或編輯工具呼叫就算,不解析命令內容」
引句:「即使工作樹上有未提交的程式碼檔」
引句:「這一輪只跑 Read/Grep,工作樹上留著未提交的程式碼檔,確認它閉嘴(對應 S6)」

### F2:同一輪內「改了又提交」(尤其配 `--no-verify`)會讓新舊兩道閘同時靜默,是純粹的覆蓋率倒退

severity: major
blocking: 是。判準:這是相對舊版的真實覆蓋率倒退——舊版必定會提醒,新版在同一種輸入下必定不提醒,不是「換個形狀」而是「消失了一個安全網」。
`is_code_file` 對有副檔名的檔案只看路徑與副檔名(見 file 引用),完全不管檔案是否已提交、是否還存在;所以舊版「用工具名清單」的做法即使該輪同時把程式碼改了又提交,一樣會抓到並提醒。新版把「是哪幾支檔」全部改問「工作樹上還沒提交的」,一旦該輪內把程式碼提交掉(常見誘因:`git commit --no-verify`,pre-commit 本身就允許此旁路),工作樹立刻乾淨,新版的清單查出來是空的,整條提醒鏈路(stderr 與回 block 兩條)都不會觸發——而 pre-commit 的圖譜同步擋(Gate 2/3)同樣可被同一個 `--no-verify` 繞過,於是兩道閘同時失效,舊版原本仍能守住的這個情境現在完全沒人守。

file: `scripts/hooks/pre-commit:170-173`(Gate 3 只看「這次 commit 有沒有 staged 圖譜 .md」,提交後工作樹乾淨,新版 Stop hook 查無可查)

### F3:刪除的無副檔名程式檔(如本 repo的 `scripts/lumos`)在新方案下結構性地列不出來,直接牴觸 S4

severity: major
blocking: 是。判準:S4 明文要求刪除的程式碼檔要出現在清單裡,而計劃自己承諾沿用的判定函式對這個情境結構上做不到,不是機率性瑕疵。
`is_code_file` 對無副檔名檔案靠 `_shebang_script` 開檔讀首行判斷,而 `_shebang_script` 要求 `p.is_file()` 為真;檔案被刪除後在工作樹上已不存在,這個檢查必定回 False,於是無副檔名的已刪除檔會被判定「不是程式碼檔」而整支從清單消失。計劃在「去向」表明講新路徑「沿用同一支函式即繼承,不另寫」,等於把這個結構性缺口原樣繼承進新方案,而本 repo 主程式 `scripts/lumos` 正是這種無副檔名檔案的真實案例。
引句:「當這一輪刪掉了一支程式碼檔,該檔應出現在清單裡並標示是刪除,不應因為它已不存在而被略過」
引句:「新路徑沿用同一支函式即繼承,不另寫」

### F4:版本控制查詢本身失敗(非 repo、逾時)時該怎麼辦,計劃全篇沒有交代

severity: major
blocking: 是。判準:S1 要求「不得少報」,但查詢失敗時究竟要 fail-open(等同少報,直接違反 S1)還是退回舊法,計劃完全沒有選邊,任一種預設實作都可能違反自己的條款。
這支 hook 現有的 `_impact_missing` 對外呼叫已經明文寫死「rc≠0 視為沒資料,fail-open 回 []」並用 `_inner_budget` 接管逾時預算(檔案本身花了 68 行講清楚外層天花板與內層預算的關係,見 519-587 行),但計劃的「問版本控制」段落只給了一個效能數字,完全沒提新的 git 查詢要不要接同一套預算系統、逾時或非 repo 時回傳什麼。
引句:「零依賴家規下不引入新套件:`git status --porcelain` 即可,本 repo 4074 個追蹤檔實測跑一次約 30 至 40 毫秒」

### F5:被 `.gitignore` 排除的程式碼檔,新方案永遠看不到

severity: minor
blocking: 否。判準:多數會被 gitignore 的程式碼檔本身就是建置產物或個人本機腳本,是否需要圖譜同步存在爭議,且屬可事後追加規則的邊界情況,不影響本次驗收條件的可通過性。
`git status --porcelain` 預設不列出被忽略的檔案,若專案裡有刻意 gitignore 但仍算「程式碼」的檔案(例如本機覆寫腳本),舊版靠工具名清單掃描 transcript 完全不看 `.gitignore`,改動一樣抓得到;新版只問版本控制,這類檔案的改動會永久列不出來。計劃全文沒有提到 `.gitignore` 或忽略檔案。

### F6:子模組內的程式碼檔改動,新方案只看得到指標本身

severity: minor
blocking: 否。判準:本 repo 目前沒有子模組,這是一般性設計缺口而非本 repo 會踩到的具體失敗,留給日後接入子模組專案時再處理不影響這次驗收。
`git status` 在父專案根目錄預設只把子模組整體列成一行「modified content」,不會展開列出子模組內部個別檔案路徑;子模組內被改動的 `.py`/`.ts` 等檔案因此不會出現在「哪些程式碼檔還沒提交」的清單裡。舊版的工具名清單掃描不理會子模組邊界,一樣抓得到子模組內的改動。計劃全文沒有提到子模組。

### F7:回 block 那條路徑會把「別人的」未提交檔名直接送進模型的下一句提示,S3 只修了措辭沒修範圍

severity: major
blocking: 是。判準:S3 只承諾把文字改成「工作樹語意」,計劃自己承認清單裡「還可能含別人的」,但沒有限制回 block 訊息(模型看得到、會被當成下一步指示)裡列出的檔名範圍,模型可能被要求去為它完全不知情的改動補寫圖譜筆記。
`stop_block_reason` 把 `rel`(程式碼檔清單)直接格式化進 `decision:block` 的 reason 文字,這段文字官方通道會讓模型當成下一個提示續做;若這份清單是共用工作目錄下另一個會談留下的未提交檔,這一個會談的模型會被要求去補一批它沒有上下文、甚至看不懂為什麼要改的程式碼的筆記。計劃把這個現象定位成「訊息措辭」問題(S3),但 S3 的驗收條件只檢查文字不再說「這一輪」,沒有檢查回 block 的檔名範圍是否限縮到跟這個會談相關。
引句:「問版本控制之後,這句話會變成假的——清單裡含這輪以外的未提交改動,共用工作目錄下還可能含別人的。」
