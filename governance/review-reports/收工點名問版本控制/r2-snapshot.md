# 收工點名問版本控制

> 白話:收工時那句「這一輪改了 N 個程式碼檔」會少報。實測一輪改三支,它說一支——因為它是靠「看你用了哪個工具」去猜改了什麼,只認得三個編輯工具加五個搬移刪除命令。用 `>` 重導向、`sed -i`、heredoc 改的檔一支都不算數。**不是不響,是少報;少報比不響難發現,因為它看起來像正常運作。**

## 版本沿革

- 前身 [[Projects/收工點名改量檔案樹_計劃]](已 superseded)。設計審七席 42 條發現、28 條 blocking、密度 1.47 條/300 字,**方案本身被否決**(自存快照算內容雜湊=本 repo 第四種做法),人裁整份重寫。卷證 `governance/review-reports/收工點名改量檔案樹/`。
- 本篇 r1 又七席 44 條發現、31 條 blocking(密度 1.18 條/300 字)。**核心沒被推翻,被打的是選型與邊界**,人裁折入不重寫。卷證 `governance/review-reports/收工點名問版本控制/`。本篇是折入後的版本。

## 實測證據(2026-09-18,Claude Code 2.1.274)

手法:造假的對話紀錄餵給那支 hook,看它印什麼。不看模型怎麼說,只看 hook 自己的輸出。

| 情境 | 這輪實際改了 | hook 說改了 |
|---|---|---|
| 只用 Write 改一支 | 1 支 | 1 支 ✅ |
| 只用 `cp` 改一支 | 1 支 | 1 支 ✅ |
| 只用 `echo > 檔` 改一支 | 1 支 | **完全沒輸出** ❌ |
| 只用 `sed -i` 改一支 | 1 支 | **完全沒輸出** ❌ |
| 混用:Write 一支 + `sed -i` 一支 + heredoc 一支 | **3 支** | **1 支** ❌ |

配套量到的使用比例:最近 12 份對話紀錄裡,改程式碼檔的動作 286 次走 shell、31 次走編輯工具——**九成走在不被計入的那條路上**。

## 根因

★先分清楚一個容易混淆的詞★:下文「閘門 3」會指到兩個東西——**閘門 3 的判準**(判「這輪有沒有動過圖譜」,壞了、要修)與**閘門 3 判為真之後那條分支裡的查詢**(算「哪幾篇筆記該動沒動」,本來就對、不用動)。

主流程是四道閘(0–3),閘門 3 之後分岔成兩條互斥的路:

| 閘門 3 的結果 | 印什麼 | 「改了哪些檔」怎麼算的 |
|---|---|---|
| 這輪動過圖譜 | 「動了筆記,但這幾篇直接相關的還沒動」 | 該分支自己呼叫 `lumos impact --diff HEAD --sync-check` |
| 這輪沒動圖譜 | 「這一輪改了 N 個程式碼檔,筆記沒動」 | **用閘門 2 算出來的清單,也就是工具名那一套** |

★兩處都壞★:

1. **閘門 2**(算「這輪改了哪些程式碼檔」)靠列舉工具名,算出空的就整個結束——兩條路都到不了。
2. **閘門 3 的分岔判準同樣靠「認名字」**(r1 正確性席 blocker)。精確講是兩份清單:一份工具名清單、一份寫入子命令名單,但兩份都靠名字,所以是同一種少報。用 shell 同時改了程式碼和圖譜筆記時會誤判「筆記沒動」。只修閘門 2 不夠。

## 方案

**一句話:清單向版本控制要(所以不少報);要不要印,看清單跟上次比有沒有變(所以不刷屏)。**

| 問題 | 現在怎麼算 | 改成怎麼算 |
|---|---|---|
| 是哪幾支程式碼檔? | 列舉工具名 | **`git status --porcelain -uall`**,取工作樹上未提交的程式碼檔 |
| 這輪有沒有動過圖譜?(閘門 3 判準) | 同一批名字清單 | **同上**:未提交的檔裡有沒有圖譜筆記 |
| 要不要印出來? | 看閘門 2 的清單空不空 | **跟「上次印過的清單」比,完全一樣就不印** |
| 哪幾篇筆記該動沒動? | 已經是 `lumos impact --diff HEAD` | **不動**,本來就對 |

### 為什麼非得用 `git status --porcelain -uall`,而不是既有那個查詢

★這是本案唯一刻意偏離既有做法的地方,理由寫在這裡,不要當成疏忽★(r1 邊界席 blocker + 架構對齊席 major)。

本 repo 既有三處算「哪些檔改了」,用的是三種**不同**的查詢:

| 既有位置 | 查詢 | 看得到新建的未追蹤檔嗎 |
|---|---|---|
| 提交前那道閘 | `git diff --cached --name-only`(已暫存清單) | 看得到(因為已經 add 過) |
| 推送前那道閘 | `git diff --name-only <提交範圍>` | 看得到(因為已經提交) |
| 閘門 3 那條分支 | `git diff --name-only HEAD`(工作樹對上次提交) | **看不到** |

**編排者實測(留痕 `v2-r1-repro.md`)**:改一支既有檔 + 用重導向建一支全新檔 + 建一個新目錄含兩支檔,三種查詢的輸出——

- `git diff --name-only HEAD`:只列出既有那一支。**新建的兩類完全不出現。**
- `git status --porcelain`(不帶旗標):新目錄摺成 `?? newdir/` 一行,裡面的檔列不出來。
- `git status --porcelain -uall`:四支全部逐支列出。

**所以:`echo > 新檔.py` 是最常見的 shell 寫法,而它建出來的是「從未被追蹤的新檔」——沿用閘門 3 那個查詢,這個病會原封不動留著。** 既有三處都不需要看未追蹤檔(它們各自關心的是已暫存、已提交、或已追蹤的改動),本案需要,所以必須用第四種查詢。**這不是自創機制,是同一個工具的另一個既有指令;偏離的是「哪一種查詢」,不是「靠什麼算」。**

★`-uall` 這個旗標是斷言不是裝飾★:不帶它,一個全新目錄整包摺成一行,裡面幾支檔一支都列不出來。本 repo 自己的程式碼早已記載這件事。驗收時要先拆掉這個旗標跑一次、確認會漏,才算證明它有作用。

### 為什麼觸發條件不能只看「這輪有沒有跑過 shell」

★r1 兩席各自報 blocker,本節是折入後的改寫★。

初稿寫的是「這輪有 shell 呼叫或編輯工具呼叫就算可能改過檔」。**這個判準在現實裡幾乎永遠為真**——看紀錄、看檔、搜尋、跑測試全是 shell 呼叫。而新的清單來源是「工作樹上未提交的東西」,不限這一輪。兩者疊加的後果是:**只要工作樹上留著任何未提交的程式碼檔,幾乎每一輪都會開口**,等於把 2026-07-06 撤掉的「每回合刷屏」請回來。

現況之所以不刷屏,是因為觸發條件與清單來源是同一份東西:這輪沒用編輯工具改 code,清單就是空的,自然閉嘴。**少報換來了安靜。**

改法:**清單照樣每次向版本控制要,但跟「上次印過的清單」比對,完全一樣就不印。**

★這個狀態跟第一版被否決的快照,差別在它壞掉的後果★:

| | 第一版的快照 | 本案的「上次印過什麼」 |
|---|---|---|
| 用途 | 算差集,決定清單內容 | 只決定「這次要不要重印」 |
| 在哪條路徑 | **正確性路徑** | **體驗路徑** |
| 壞掉/讀不到的後果 | **少報**(致命,正是本案要修的病) | **多印一次**(無害) |
| 因此需要的防護 | 原子寫入、格式版號、跨會談鍵值、清理期限——第一版被要求的全套 | 讀不到就當「沒印過」照印,不需要上述任何一項 |

**同樣是存檔,存在哪條路徑上決定了它壞掉時有多糟。** 這是本案跟第一版的關鍵分野,不是換個名字重來。

## 誠實改口:訊息不能再說「這一輪」

現在那句是「這一輪改了 N 個程式碼檔,但知識筆記沒有跟著動」。清單改成工作樹語意之後,那句話會變成假的——含這輪以外的未提交改動,共用工作目錄下還可能含別人的。要改成:

> 工作樹上有 N 個程式碼檔還沒提交,知識筆記沒有跟著動

★核心代價:不再宣稱切得出「這一輪」。★ 換來的是「用什麼工具改的都看得到」。

**清單會變多長:沒有量到有代表性的數字。** 本次工作開始時觀測過主 clone 一次(31 筆未提交:4 支已追蹤改動 + 27 筆未追蹤,未帶展開旗標、未區分是不是程式碼檔)。這個數字取決於各人的提交習慣,一次觀測不能當通則,**列為上線後要補的量測**(見〈撤除條件〉)。

REVISIT:2026-12-18 重跑卷證裡的情境產生器,並量一次終端機清單長度中位數;兩者任一觸發撤除條件就照〈撤除條件〉處理。

## 失敗時怎麼辦

★r1 三席各自指出初稿沒交代★。版本控制查詢本身可能失敗:專案不是版本控制倉庫、索引被別的程序鎖住、逾時、倉庫損毀、空倉庫還沒有第一個提交。

**一律 fail-open:靜默放行,不印任何東西,不擋。** 理由是照鄰近程式碼的既有慣例(那支 hook 對算不出來的情況一律不擋、寧可漏),而且本機制是提醒不是閘——擋住使用者收工的代價遠大於漏一次提醒。逾時沿用該 hook 既有的內外層預算機制,不另訂。

★這是有意識的取捨,不是沒想到★:代價是「版本控制壞掉的環境下,這個提醒等於不存在」,而且不會有人知道。接受的理由是提交前那道閘仍然會擋,最終防線不依賴本機制。

## 送進模型那條訊息要限縮範圍

★r1 正確性席報的這條,初稿把它併進「清單會變長」的限制裡,那是歸類錯了(折入查帳指出)★。兩者嚴重度不同:

- **人看到的那條(終端機)**:清單變長,人多看幾行,自己會判斷哪些不是自己改的。體驗問題。
- **送給模型的那條(擋停時回的內容)**:★它會被模型當成下一步該做什麼讀進去★。共用工作目錄下,模型可能被指示去為一批它完全不知情、別人留下的改動補寫筆記。**行為問題,不是體驗問題。**

處理:**送給模型的那條,清單只列這一輪的對話紀錄裡出現過的路徑**(兩邊取交集);交集算不出來時,只報數量與一句「工作樹上有未提交的程式碼檔」,不列檔名。人看到的那條不受此限,照列全部。

代價:模型那條會回到「可能少報」——但★這是刻意的不對稱★:給模型的指示寧可少講,給人的清單寧可多列。少報對人的代價是漏一個提醒,對模型的代價是去做一件不該做的事。

## 已知限制(接受,不在本案解決)

r1 席位指出、經判斷後接受的邊界,逐條寫明而不是略過:

| 限制 | 後果 | 為什麼接受 |
|---|---|---|
| 被版本控制忽略的程式碼檔看不到 | 那些檔改了不會提醒 | 被忽略的檔本來就不進版本控制,也不會被提交前那道閘擋;它們不在「該寫回圖譜」的範圍 |
| 子模組內的改動看不到 | 同上 | 子模組有自己的提交流程,本 repo 目前沒有子模組 |
| 同一輪改完又提交(尤其用 `--no-verify` 繞過) | 本機制與提交前那道閘會同時靜默,是相對舊版的覆蓋率倒退 | 繞過閘門本來就是明示的逃生門,且會留下繞過紀錄;不為它增加複雜度 |
| 合併或變基衝突中途的狀態碼 | 那些檔的狀態碼不是常見的兩種,可能被歸類錯 | 衝突中途本來就不是收工的時機;驗收條件會確認至少不會當機 |
| 共用工作目錄下清單含別人的檔(**人看到的那條**) | 清單變長、含不相干的檔 | 這是「不再宣稱切得出這一輪」的直接後果,已在措辭上誠實化 |
| 壞掉或讀不到的對話紀錄 | 跟「這輪沒動作」無法區分,會靜默不提醒 | 與失敗時一律 fail-open 同一取捨 |
| 改名的檔在狀態輸出裡是「舊路徑 -> 新路徑」的特殊格式 | 不處理會把整串當成一個檔名 | ★不接受,要處理★:取新路徑當作被改的檔;已列入驗收條件 |

## 跟另外兩道閘的分工

★r1 接手席指出初稿沒討論★。同一批檔在三個時機會被點名:

| 時機 | 誰在點 | 算的範圍 | 本案改了嗎 |
|---|---|---|---|
| 這一輪結束 | 本案這支 hook | 工作樹上未提交的 | **改了**(清單來源換掉) |
| 提交前 | 提交前那道閘 | 這次要提交的 | 不動 |
| 推送前 | 推送前那道閘 | 這批要推的提交範圍 | 不動 |

**會不會重複點名同一批檔?會,而且是有意的**——三個時機的受眾與時機不同:收工時提醒你「趁還記得補筆記」,提交前擋住「這次別帶著沒同步的東西進歷史」,推送前擋住「分開幾個提交各自過關、整批卻漏了」。本案只換第一個的清單來源,不動另外兩個的範圍,所以不會產生新的重疊。

★但落點那篇節點裡有一張「三個時機」的表,寫的是舊的算法,本案改完要同步更新那張表★——已列入驗收條件。

## 要一起處理的相依

★r1 接手席實測發現,初稿完全沒提★:主程式的接手指令直接引用了這支 hook 的兩個內部名稱(收集這輪動作的函式與編輯工具清單),而現有的鎖定測試只驗「import 得動」,不驗行為等價。**本案改動那兩個東西的語意,必須連帶檢查該指令**,驗收條件已補。

## 這個查詢要怎麼呼叫:直接呼叫,不經信任檢查

★r1 架構對齊席指出初稿沒表態★。這支 hook 裡並存三種對外呼叫方式:純自己算、直接呼叫系統工具(反查筆記那個)、以及經過信任檢查再呼叫本專案的主程式。

**本案選直接呼叫版本控制工具,不經信任檢查。** 理由:

- 信任檢查的存在理由是★別執行「被打開的那個資料夾自己帶的程式碼」★——打開陌生專案時,它的 `scripts/lumos` 可能是惡意的。**版本控制工具不在這個威脅模型裡**:它是系統裝的,不隨被打開的資料夾走。
- 提交前與推送前那兩道閘也是直接呼叫它,本案跟鄰居一致。

★殘留風險,寫明不迴避★:如果執行路徑本身被汙染(有人在路徑前面放了一支假的同名工具),本案會拿到假輸出。但那種情況下整支 hook 都已經不可信(它還會呼叫別的系統工具),不是本案能單獨守的邊界。

## 實務隱患

- 已排除:金流:這支 hook 只讀檔案狀態與印提醒,不碰任何金額、帳務或計價邏輯。
- 已排除:對外送出:全程本機執行,不發任何網路請求。會開子行程的有三處(算波及的 lumos、反查筆記的 obsidian 命令列工具、本案新增的版本控制查詢),三處都在本機跑、都不連外。
- **不能排除:不可逆**:★初稿寫「本方案不寫任何狀態檔」是錯的(r1 回滾席 blocker)★。那支 hook 本來就會在快取目錄寫擋停標記檔,本案又新增一份「上次印過什麼」。兩者都在快取目錄、都可以安全刪除(刪掉只會多印一次),但**不能宣稱零寫入**。另外本案放寬觸發後,會讓更多會談第一次觸發、在標記目錄多留檔案——殘留量是本案增加的,沿用該目錄既有的七天清理。

## 回退

★r1 回滾席第二次以同一理由報 blocker(第一版也是栽在這裡),所以本節不再補條件,改換形狀:承認退不乾淨,並把不能保證的部分明寫成限制,而不是寫一句做不到的指令★。

這支 hook 存在於三類位置,**退得乾淨的只有前兩類**:

| 位置 | 怎麼退 | 保證得了嗎 |
|---|---|---|
| repo 裡的原始檔 | 還原該檔 | ✅ |
| 家目錄下兩個部署位置(兩種 AI 工具各一) | 跑一次安裝指令,再對兩個位置各比一次 sha256 | ✅ 可機械核對 |
| 各接入專案自己的複本 | 每個專案各跑一次更新指令 | ❌ **保證不了** |

★第三類為什麼保證不了★:整個工具裡沒有任何地方登記「這台機器上有哪些專案裝過」,所以沒有清單可以枚舉,也就沒辦法確認是不是都退了。**這是本案的已知限制,不是待辦事項。** 想要可保證,得先做一個安裝登記機制——那是另一個題目,不塞進本案。

★回頭條件(折入查帳指出這是全篇唯一沒配回頭機制的接受)★:下一次因為「某個接入專案跑的是舊版 hook」而踩到坑時,就是重新評估要不要做安裝登記機制的時機——記一筆事故並在該筆裡指回本節。沒有這種事故發生,就當作這個限制的實際代價夠低、不必處理。

退回的代價:回到少報的狀態。除了上述三類複本、快取目錄裡兩份可安全刪除的標記檔,以及各部署位置旁邊的編譯快取(直譯器自己會因為來源檔變動而重建,不必人清)之外,沒有其他殘留。真正擋住壞改動的仍是提交前那道閘(它算的是版本控制索引,跟用什麼工具改的無關),本案成敗不影響它。

## 驗收條件

1. 卷證裡那支情境產生器重跑,**九個情境全綠**。其中三個(管線寫入、一行 python 寫檔、包一層 shell)是本計劃**沒有列舉過**的手法;另外要新增一個「用重導向建全新檔」的情境——那是既有查詢看不到、本案改用新查詢才救得回來的核心案例。
2. **情境產生器本身要進版本控制**(現在只有輸出日誌在卷證),否則撤除條件不可執行。
3. 拆掉 `-uall` 旗標跑一次,確認新目錄的檔會漏掉;裝回去再跑,確認補回來(對應 S7)。
4. 造一個情境:用 shell 同時改一支程式碼和一篇圖譜筆記,確認閘門 3 判定為「動過圖譜」(對應 S2)。
5. 刪掉一支沒有副檔名的程式檔,確認它出現在清單裡並標示刪除(對應 S4)。
6. 同樣的清單連印兩次,確認第二次不印;刪掉「上次印過什麼」那份檔再跑,確認照印不漏(對應 S5)。
7. 在非版本控制目錄、以及空倉庫下各跑一次,確認靜默放行不當機(對應 S6)。
8. 訊息措辭逐字檢查,不得出現「這一輪改了」(對應 S3)。
9. 改完跑一次安裝指令,對家目錄下兩個部署位置各比一次 sha256(對應 S8)。
10. **檢查主程式的接手指令**:它直接引用本案要改的兩個內部名稱,現有鎖定測試只驗 import 不驗行為,要確認語意改變後它仍然正確。
11. 造一個改名的情境(把一支程式碼檔換個名字),確認清單列的是新路徑、不是「舊路徑 -> 新路徑」那一整串。
12. 擋停那條送給模型的訊息,在共用工作目錄情境下確認只列這輪對話紀錄裡出現過的路徑(對應〈送進模型那條訊息要限縮範圍〉)。
13. 落點那篇節點裡的「三個時機」表要同步更新成新的算法。
14. 拆掉守衛要能翻紅:還原前先清 `__pycache__`,否則改動大小相同又落在同一秒,直譯器會沿用舊的編譯快取,你會看到假的綠(同族前例見 [[Systems/記憶過期清掃]])。
