# 編排者機械重現:邊界席兩條 blocker

日期 2026-09-18。唯讀實驗,在臨時倉庫做,不碰本 repo。原始輸出三份:`probe-a.txt`、`probe-b.txt`、`probe-c.txt`。

## 現場

一個乾淨的倉庫,有一個提交(裡面有 `existing.py`)。然後做三件事:

1. 改既有檔 `existing.py`
2. 用重導向建一支全新檔 `newfile.py`(從未被追蹤)
3. 建一個新目錄 `newdir/`,裡面兩支檔 `a.py`、`b.py`

## 結果

| 查詢 | 原始輸出 | 看到幾支 |
|---|---|---|
| `git diff --name-only HEAD`(本版初稿宣稱要沿用的那個) | `probe-a.txt` | **1 支**,只有 `existing.py` |
| `git status --porcelain`(不帶展開旗標) | `probe-b.txt` | **3 行**,新目錄摺成 `?? newdir/` 一行 |
| `git status --porcelain -uall` | `probe-c.txt` | **4 支**,逐支列出 |

三份檔的行數(1 / 3 / 4)本身就是證據。

## 判定

**HIT:邊界席兩條 blocker 都成立。**

1. **既有查詢對從未被追蹤的新檔是瞎的。** 而 `echo > 新檔.py` 正是最常見的 shell 寫法——沿用它,本案要修的病會原封不動留著。這直接推翻本版初稿 PRIOR-ART 的核心宣稱(「沿用既有第三種做法」)。
2. **展開旗標是斷言不是裝飾。** 不帶它,一個全新目錄整包摺成一行,裡面幾支檔一支都列不出來。

## 影響

計劃因此改寫:承認必須用第四種查詢,並把「為什麼非偏離既有做法不可」寫成獨立一節,不假裝一致。
實作的驗收也照這條加了一步——★先拆掉展開旗標跑一次、確認會漏,才算證明它有作用★(實作階段已執行:拆掉之後三條測試翻紅)。
