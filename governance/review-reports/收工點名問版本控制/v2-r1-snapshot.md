# 收工點名問版本控制

> 白話:收工時那句「這一輪改了 N 個程式碼檔」會少報。實測一輪改三支,它說一支——因為它是靠「看你用了哪個工具」去猜改了什麼,只認得三個編輯工具加五個搬移刪除命令。用 `>` 重導向、`sed -i`、heredoc 改的檔一支都不算數。**不是不響,是少報;少報比不響難發現,因為它看起來像正常運作。**

## 這是第二版,第一版被整份重寫

- 前身 [[Projects/收工點名改量檔案樹_計劃]](狀態已改 superseded)。設計審第一輪七席、42 條發現、28 條 blocking,本文 5733 字、密度 1.47 條/300 字,超過「建議整份重寫」的門檻;四席各自報 blocker。
- **被否定的不是細節,是方案本身**:前一版為了切出「這一輪」,自己存一份快照、算內容雜湊、跨輪比對。架構對齊席與簡化席各自獨立指出:**這是本 repo 第四種「算哪些檔改了」的做法**,既有三處全都直接問版本控制,而前一版反把既有做法寫成「不得已才用的降級模式」。
- **其餘大半發現都是那個前提的衍生帳**:快照寫一半損毀、跨會談撞名、沒人清、逐檔算雜湊很慢、中途去提交就失效、分發出去的多份複本退不乾淨。前提換掉,這些一起消失(逐條去向見下面〈第一輪發現的去向〉)。
- 卷證在 `governance/review-reports/收工點名改量檔案樹/`(七份席報告 + 前掃留痕 + 修前基準線)。

## 實測證據(2026-09-18,Claude Code 2.1.274;沿用第一版,未變)

手法:造假的對話紀錄餵給那支 hook,看它印什麼。不看模型怎麼說,只看 hook 自己的輸出。可重跑的情境產生器與修前基準線見卷證目錄的 `baseline-before-fix.txt`。

| 情境 | 這輪實際改了 | hook 說改了 |
|---|---|---|
| 只用 Write 改一支 | 1 支 | 1 支 ✅ |
| 只用 `cp` 改一支 | 1 支 | 1 支 ✅ |
| 只用 `echo > 檔` 改一支 | 1 支 | **完全沒輸出** ❌ |
| 只用 `sed -i` 改一支 | 1 支 | **完全沒輸出** ❌ |
| 混用:Write 一支 + `sed -i` 一支 + heredoc 一支 | **3 支** | **1 支** ❌ |

最後一列是最毒的:提醒響了、看起來正常,清單卻漏掉三分之二。

配套量到的使用比例:最近 12 份對話紀錄裡,改程式碼檔的動作 286 次走 shell、31 次走編輯工具——**九成走在不被計入的那條路上**。

## 根因

那支 hook 的主流程是四道閘(0–3),閘門 3 之後分岔成兩條互斥的路:

★先講清楚一個容易混淆的地方(前掃提醒):下文「閘門 3」會指到兩個東西——**閘門 3 的判準**(判「這輪有沒有動過圖譜」,它壞了、要修)與**閘門 3 判為真之後那條分支裡的查詢**(算「哪幾篇筆記該動沒動」,它本來就對、不用動)。兩者程式碼位置相鄰但職責不同,看到「閘門 3」請先看是指判準還是指分支裡的查詢。★

| 閘門 3 的結果 | 印什麼 | 「改了哪些檔」怎麼算的 |
|---|---|---|
| 這輪動過圖譜 | 「動了筆記,但這幾篇直接相關的還沒動」 | 該分支自己呼叫 `lumos impact --diff HEAD --sync-check`(工作樹 vs 上次提交) |
| 這輪沒動圖譜 | 「這一輪改了 N 個程式碼檔,筆記沒動」 | **用閘門 2 算出來的清單,也就是工具名那一套** |

★兩處都壞,不是只有一處★:

1. **閘門 2**(算出「這輪改了哪些程式碼檔」)靠列舉工具名,算出空的就整個結束——所以兩條路都到不了。
2. **閘門 3 的分岔判準同樣靠「認名字」**(設計審正確性席 blocker)。★精確講是兩份清單不是一份(前掃訂正):一份是閘門 2 那份工具名清單,另一份是一組寫入子命令名單——但兩份都靠名字,所以是同一種少報。★ 用 shell 同時改了程式碼和圖譜筆記時,它會誤判「筆記沒動」——**同一種少報換個位置活下來**。只修閘門 2 不夠。

## 方案:觸發條件寬鬆,檔案清單精確

**一句話:要不要開口,仍然看這一輪做了什麼;開口之後說哪幾支檔,一律問版本控制。**

| 問題 | 現在怎麼算 | 改成怎麼算 |
|---|---|---|
| 這一輪要不要開口? | 讀對話紀錄,列舉工具名算出檔案清單,清單空就閉嘴 | 讀對話紀錄,**只判「這輪有沒有跑過任何可能寫檔的動作」**(有 Bash 呼叫或編輯工具呼叫就算,不解析命令內容) |
| 是哪幾支程式碼檔? | 同一份工具名清單 | **問版本控制:工作樹上有哪些程式碼檔還沒提交** |
| 這輪有沒有動過圖譜?(閘門 3 的分岔) | 同一份工具名清單 | **同上:工作樹上有沒有未提交的圖譜檔** |
| 哪幾篇筆記該動沒動? | 已經是 `lumos impact --diff HEAD`(工作樹 vs 上次提交) | **不動**,本來就對 |

**為什麼這樣分工:**

- 「用什麼工具改的」永遠列舉不完(這次補 `sed`、heredoc,下次還有 `tee`、`patch`、一行 python、包一層 shell、產生器工具)。每補一個名字都是再賭一次「這次列完了」。**量結果不量過程才免疫。**
- 但「這一輪有沒有做事」這個判斷不需要精確——**寧可多開口**。所以觸發條件刻意放寬:只要這輪碰過 shell 或編輯工具就算「可能改過檔」,不去解析命令做了什麼。
- 精確度要放在清單上,不是放在觸發上。**誤觸發的代價是多看一次提醒;少報的代價是漏掉該補的筆記——後者才是這次要修的病。**

## 新方案自帶的一個張力:會不會變成每輪嘮叨

★這是新方案獨有的風險,前一版沒有,必須當面處理★。

問版本控制的是「工作樹上未提交的東西」,**不是「這一輪改的東西」**。所以:上一輪改了程式碼沒提交、這一輪只是跑了幾個唯讀指令——工作樹照樣有未提交的程式碼檔,於是照樣開口。

**這件事重要,是因為 2026-07-06 撤掉過「每回合刷屏」的舊行為**,不能繞一圈把它請回來。

處理方式,分兩個受眾看(這支 hook 有兩條輸出路徑,受眾不同):

| 受眾 | 走哪條路 | 現況頻率 | 新方案下 |
|---|---|---|---|
| 模型 | 回 block(模型看得到) | **同一個會談只有一次**(它會去建一個標記檔,建檔時要求「已經存在就失敗」,所以第一個建成的佔走名額、後面的一律擋不成) | 不變,仍是一次 |
| 人(終端機) | stderr(exit 0 時模型看不到,人看得到) | **每輪都印**(擋停名額用掉後,之後每輪落到 stderr 那行) | 每輪都印,但清單會變長 |

- **對模型:沒有嘮叨問題**,結構上就只有一次。
- **對人:現在就已經每輪印了**,新方案不增加次數,只增加清單長度(含這輪以外的未提交改動)。
- 所以張力的真實形狀不是「變成嘮叨」,而是「**人每輪看到的清單變長、而且含不是這輪的東西**」。這要靠措辭誠實化來處理,不能靠假裝精確。

## 誠實改口:訊息不能再說「這一輪」

現在那句是:

> 這一輪改了 N 個程式碼檔,但知識筆記沒有跟著動

問版本控制之後,這句話會變成假的——清單裡含這輪以外的未提交改動,共用工作目錄下還可能含別人的。**要改成講得出口的語意**,例如:

> 工作樹上有 N 個程式碼檔還沒提交,知識筆記沒有跟著動

★這是本方案的核心代價,寫在最顯眼的地方★:換來的是「用什麼工具改的都看得到」,付出的是「不再宣稱切得出這一輪」。**前一版整套快照機制就是為了保住「這一輪」這三個字而生的,而那三個字換來 28 條 blocking。**

## 第一輪發現的去向

前一版七席 42 條發現,在新方案下逐類交代:

**前提換掉就消失的(不需要再處理):**

| 發現 | 為什麼消失 |
|---|---|
| 快照寫一半損毀、被當成有效基準讀入(邊界席 blocker) | 沒有自己寫的快照檔了 |
| 快照跨會談撞名互相覆寫(正確性/回滾/接手三席一致) | 同上 |
| 快照沒有清理期限、越積越多(回滾/正確性席) | 同上 |
| 快照格式版本欄未定義(接手席) | 同上 |
| 逐檔算內容雜湊在大 repo 會很慢(外家席 blocker) | 不自己算雜湊,交給版本控制(它自己有快取) |
| 會談中途去提交會讓機制失效(外家席 major) | 提交後工作樹清空正是**正確**語意:已提交的不必再提醒 |
| S4 與 S1 自相矛盾(同檔連兩輪改會被排掉,外家席 major) | 沒有「上一輪已經算過」的概念了 |
| 降級模式常態化、警語該走哪條輸出路徑(接手席 blocker、回滾席 major) | 沒有基準,就沒有「取不到基準」的降級模式 |
| 自創第四種做法(架構對齊席 major、簡化席 major) | 改用既有第三種做法,不新增 |

**新方案下仍然存在、本計劃必須處理的:**

| 發現 | 怎麼處理 |
|---|---|
| 這支 hook 有多份分發複本,回退不乾淨(回滾席 blocker) | 寫進〈回退〉節,逐個複本點名 |
| 改完 repo 裡的檔要跑安裝指令才真的部署,而且**實測目前已部署的副本已落後 repo 最新版**(接手席 major) | 寫成條款 S5 + 驗收條件 |
| 「刪掉一支程式碼檔」算不算「改了」沒定義(外家席 minor) | 寫成條款 S4 |
| 撤除條件不可檢查——事件紀錄只記「跑過沒」,不記內容效果(簡化席 major) | 重寫撤除條件,改成查得到的形式 |
| `is_code_file` 會開檔驗 shebang,特殊檔可能卡住(邊界席 minor) | 既有程式碼已有防護(先判位置再開檔、非普通檔不開),新路徑沿用同一支函式即繼承,不另寫 |

## PRIOR-ART

- **本 repo 已經有三處在做同一件事,全部直接問版本控制**:提交前那道閘看已暫存的清單、推送前那道閘看提交範圍、以及這支 hook 自己閘門 3 那條路看工作樹對上次提交。**本方案是沿用第三種,不新增第四種。**
- 零依賴家規下不引入新套件:`git status --porcelain` 即可,本 repo 4074 個追蹤檔實測跑一次約 30 至 40 毫秒(兩次前後量測落在 36 與 38 毫秒)(★這是「問版本控制哪些檔不一樣」的時間,不含逐檔讀內容——本方案不逐檔讀內容,所以這個數字用得上;前一版把它用來論證「比內容也很快」是誤用,外家席已指出★)。

## 撤除條件

★前一版的撤除條件寫了等於沒寫(簡化席 major):它要求統計「有沒有比舊作法多抓到檔」,但現有的事件紀錄只記 hook 跑過沒、不記它印了什麼。★ 改成查得到的形式:

- **查得到的版本**:卷證裡有一份可重跑的情境產生器(`baseline-before-fix.txt` 那支)。**每季重跑一次**;若九個情境全部回到「修前」的結果(也就是這個改動已經被別的改動架空),就撤掉這條路徑、退回原本的列舉法,並記一筆事故。
- **另一條**:若「清單含非本輪改動」在真實使用中造成困擾(判準:使用者主動抱怨,或終端機清單長度中位數超過 10 支檔),則保留量版本控制的做法、但把訊息改成只印數量與一句「詳見 `lumos impact --diff HEAD --sync-check`」,不逐支列。

## 條款

- [S1] 當這一輪用任何方式改了程式碼檔(含重導向、原地取代、heredoc、管線寫入,以及本計劃沒有列舉過的手法),收工點名的清單應含每一支被改的檔,不得少報 [test:t_sync_nudge_lists_shell_written_files]
- [S2] 當這一輪用 shell 手法改了圖譜筆記,閘門 3 應判定為「動過圖譜」,不應誤判成沒動 [test:t_sync_nudge_gate3_sees_shell_written_notes]
- [S3] 當收工點名開口時,訊息不應宣稱那些檔是「這一輪」改的,應改用工作樹語意(未提交)陳述 [test:t_sync_nudge_message_says_uncommitted_not_this_turn]
- [S4] 當這一輪刪掉了一支程式碼檔,該檔應出現在清單裡並標示是刪除,不應因為它已不存在而被略過 [test:t_sync_nudge_counts_deleted_code_file]
- [S5] 當 repo 裡的 hook 檔被改動後,安裝器應把它同步到所有已部署的位置,否則實際生效的仍是舊版 [manual:改完跑一次安裝指令,再去已部署的位置對 sha256,兩邊要一致]
- [S6] 當這一輪完全沒有跑過任何可能寫檔的動作(沒有 shell 呼叫、沒有編輯工具呼叫),收工點名應閉嘴,即使工作樹上有未提交的程式碼檔 [test:t_sync_nudge_silent_on_readonly_turn]

## 實務隱患

- 已排除:金流:這支 hook 只讀檔案狀態與印提醒,不碰任何金額、帳務或計價邏輯。
- 已排除:對外送出:全程本機執行,不發任何網路請求。會開子行程的有兩處(算波及的 lumos、反查筆記的 obsidian 命令列工具),兩處都在本機跑、都不連外。
- 已排除:不可逆:只讀不寫被檢查的檔,本方案不再寫任何狀態檔(這是相對前一版的主要簡化)。
- **不能排除:守衛面**:本案改的就是一個守衛的判定來源。算錯的後果正是本案要修的病(少報看起來像正常運作)。這一項不寫已排除,照走設計審。

## 回退

退回方式:把那支 hook 還原成改動前的版本。**但單還原 repo 裡那一份不夠**——這支檔會被分發到三類位置,每一份都要各自處理:

1. repo 裡的原始檔 `scripts/hooks/claude/check-graph-sync.py`(還原它)
2. 使用者家目錄下的全域複本(要重跑一次安裝指令才會同步回去)
3. 每個接入專案裡各自的複本(每個專案各跑一次更新指令)

★第 1 項單獨還原會產生「repo 是舊版、實際生效的是新版」的錯配,那正是接手席實測到的現況★——所以回退步驟必須三項都走完,並對每一份比對 sha256 確認一致。

退回的代價:回到少報的狀態——收工點名仍會響,但只算得到用編輯工具和搬移複製刪除改的檔。本方案不寫任何狀態檔,所以除了上述三份複本之外**沒有其他殘留要清**。

真正擋住壞改動的仍是提交前那道閘(它算的是版本控制索引,跟用什麼工具改的無關),本案的成敗不影響它。

## 驗收條件

1. 卷證裡那支情境產生器重跑,**九個情境全綠**。其中三個(管線寫入、一行 python 寫檔、包一層 shell)是本計劃**沒有列舉過**的手法——補完列舉表不算修對,要這三個也過才算。
2. 另造一個情境:用 shell 手法同時改一支程式碼和一篇圖譜筆記,確認閘門 3 判定為「動過圖譜」(對應 S2)。
3. 唯讀輪測試:這一輪只跑 Read/Grep,工作樹上留著未提交的程式碼檔,確認它閉嘴(對應 S6)。
4. 訊息措辭逐字檢查,不得出現「這一輪改了」(對應 S3)。
5. 拆掉守衛要能翻紅:還原前先清 `__pycache__`,否則改動大小相同又落在同一秒,直譯器會沿用舊的編譯快取,你會看到假的綠(同族前例見 [[Systems/記憶過期清掃]])。
6. 改完跑一次安裝指令,對三類部署位置各比一次 sha256(對應 S5)。
