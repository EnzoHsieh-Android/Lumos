# 審查跑滿上限提示_計劃

PRIOR-ART: 停不停看「再修一輪預期換到多少」而不是輪數(Wu 等,arXiv 2607.17641v1,舊編號 r1 整合席上網核實過);卡住時拆小改動或往上找人裁(Google eng-practices);連續被擋或累計量過大就退回給人(Claude Code auto 模式的拒絕熔斷器,出處為第三方原始碼分析 openedclaude/claude-reviews-claude 第 07 章,沒有對照原始碼核實)。機制層沿用:處置閘(`loop status --disposal`)與它算出的失敗原因、每輪漏斗的共用函式 `_review_yield_round`(它的「折」欄就是每輪折入數,處置閘尾與 `gov --stats` 已經在用)、定錨分級 `_loop_anchor_tier`、舊閘退役判定 `_panel_retired_for`、治理帳既有的 cap-reached 記號;不另寫第二份。
RETIRE-IF: ①上線後 8 週內,跑滿或熔斷時印的提示,跟事後治理帳記到的走向不一樣的次數多過一樣(提示沒在幫忙);②三個月內零次跑滿也零次熔斷(問題消失了)。

## 一句話

讓 2026-08-26 之後開的多席迴圈真的會說出「跑滿上限」;跑滿時與累計折入過多時,先印閘沒過的原因,再印每輪折了幾條、最後一輪最高嚴重度,加一句依固定規則給人的提示。**只印,不改任何閘的判定與退出碼。**

## 適用範圍

- 只改「2026-08-26 之後開的多席迴圈」(舊閘退役那天起;判法直接呼叫 `_panel_retired_for`,不在文字裡另寫日期)。
- **不動**:light 分級(處置閘跟 light 互斥,light 今天本來就到得了跑滿上限)、代碼審循序單審(沒有輪次記帳,同理)、2026-08-26 以前的舊迴圈。這三種 loop next 的判定路徑完全照舊。

## 做法

### 一、修出口:loop next 要能說出「跑滿上限」

- 適用範圍內的迴圈,loop next 判「過了沒」改問處置閘,不再委派已退役的舊閘(今天帶 `--spec` 會被舊閘擋下、退出碼 2,到不了跑滿上限;重現記在舊編號 r1-intake.md 的更正段)。
- ★**「少了 --spec」照舊排在跑滿之前**★:這是 [[Projects/loop機械脊椎M1包_計劃]] 裁過的規則——資訊不足時連「沒過」都判不了,這時說跑滿是假斷言。本案不推翻它,只在「少了 --spec」那段多印一句「輪數已經 N/上限 M」,並照舊補好帶 --spec 的指令。
- 處置閘過關時它自己會寫收斂記號;loop next 改問處置閘之後**不再自己另寫一筆收斂記號**(避免同一件事記兩次,也讓「寫錯收斂」只剩處置閘一個入口)。沒過且輪數已達上限時,loop next 照既有寫一筆 cap-reached 記號。

### 二、跑滿時印什麼(依序)

1. **閘沒過的原因**:照抄處置閘列出的失敗步驟。只要失敗步驟裡有「處置」以外的(留痕、條款綁定、落點、資安席、材料被改過),提示一律是「先修這些,跟再審幾輪無關」,不看下面的走勢。
2. **每輪折入數**:`_review_yield_round` 的「折」欄。那一輪沒有彙總帳時:各席報的都是 0 條 → 算折 0(處置閘本來就把它當合法的空輪);有人報了條數卻沒有彙總帳 → 印「這輪沒記處置」。
3. **每輪最高嚴重度**:那一輪各席帳的 severity 取最高。
4. **提示**(只在失敗原因只剩「處置」這一步時才給;依序套,第一個成立的就是):
   - 有任何一輪「沒記處置」、或只有一輪 → 「判不了,自己看」。
   - 最後一輪折入數 ≥ 前一輪 → **換做法**:拆小改動、回頭改設計、或整類拿掉。
   - 最後一輪最高嚴重度 ≤ minor → **可考慮附理由放行**(代碼審照舊只准放行 minor)。
   - 其他(在降、但還有 major 以上) → **有進展,但已到上限:要不要破例再一輪,由人裁**。不寫「再一輪」當建議——上限本身就是叫人停(外家席指出原寫法會在明令停止的狀態叫人繼續)。
- 規則只看「最後一輪對前一輪」,不用「第一輪的一半」這種門檻(舊版被抓到把 10→6→5 判成持平)。

### 三、提早熔斷(不等跑滿)

- 同一個審查編號,各輪「折」欄累計超過 20 → 在處置閘輸出印「累計折入已經 N 條,建議拆小改動」。20 是照抄熔斷器的起點,回看後再調。
- 熔斷提示**跟上面第二節獨立**:兩者都成立時兩段都印;只有一輪卻已超過 20 條時,熔斷那段照印,第二節印「判不了」——兩句不互相取代(外家席指出原寫法兩條規則互相否定)。

### 四、印在哪裡

- `loop next` 回跑滿上限時:文字輸出與 `--json` 都要有。文字輸出是逐欄挑著印的,新段落要加進去(回滾席抓到既有欄位就這樣被悄悄吞掉)。`--json` 多一個 `cap_report` 物件:`fail_steps`(失敗步驟名清單)、`rounds`(每輪 `{round, folded, max_severity, disposed}`)、`advice`(提示代碼:`fix-gate`/`unknown`/`reshape`/`accept-with-reason`/`human-decides`)、`breaker`(累計折入,沒觸發為 null)。
- `loop status --disposal`:輪數已達上限、或觸發熔斷時,在判定之後印同一段;**回放與凍結(唯讀呼叫)不印**,照處置閘既有「唯讀時不做附帶動作」的慣例。處置閘因為帳本壞行等原因先擋下時,這段不印。

## 條款

- [S1] 當 2026-08-26 之後開的多席迴圈輪數已達分級上限、帶了 --spec 且處置閘沒過,`loop next` 應回跑滿上限而不是被舊閘擋下 [test:t_loop_next_cap_reached_on_disposal_loop]
- [S2] 當輪數已達上限而沒帶 --spec,`loop next` 應照舊回「少了 --spec」,並多印輪數已達上限的一句與補好的指令;不得回跑滿上限 [test:t_loop_next_missing_spec_still_first_at_cap]
- [S3] 當 `loop next` 回跑滿上限,文字輸出應列出閘沒過的原因、每輪折入數、每輪最高嚴重度與一條提示;`--json` 應有 cap_report 物件且欄位如第四節 [test:t_loop_cap_report_text_and_json]
- [S4] 若閘沒過的原因裡有處置以外的步驟,則提示應是先修這些,不看走勢 [test:t_loop_cap_report_non_disposal_fail_first]
- [S5] 若失敗原因只剩處置,且最後一輪折入數大於或等於前一輪,則提示應是換做法 [test:t_loop_cap_report_not_declining_suggests_reshape]
- [S6] 若失敗原因只剩處置、折入數在降且最後一輪最高嚴重度不高於 minor,則提示應是可考慮附理由放行 [test:t_loop_cap_report_declining_minor]
- [S12] 若失敗原因只剩處置、折入數在降而最後一輪仍有 major 以上,則提示應是由人裁要不要破例再一輪,不得寫成建議再一輪 [test:t_loop_cap_report_declining_major_human_decides]
- [S7] 若某輪各席都報 0 條,則該輪應算折 0 而不是沒記處置;有人報了條數卻沒有彙總帳,才算沒記處置並不給提示 [test:t_loop_cap_report_vacuous_round_counts_zero]
- [S8] 當同一個審查編號各輪折入累計超過 20 條,處置閘輸出應印建議拆小改動,且不改變過關判定與退出碼;只有一輪時熔斷段與「判不了」應並列 [test:t_disposal_early_breaker_total_folded]
- [S9] 當輪數已達上限,`loop status --disposal` 應印出與 S3 相同的一段,且不改變原本的過關判定與退出碼;回放與凍結時不得印 [test:t_disposal_prints_cap_report_without_changing_verdict]
- [S10] 若迴圈是 light 分級、代碼審循序單審,或 2026-08-26 以前開的,則 `loop next` 的判定路徑應與現在相同 [test:t_loop_next_out_of_scope_loops_unchanged]
- [S11] 當 loop next 改問處置閘而處置閘過關,治理帳應只多一筆收斂記號(處置閘寫的那筆) [test:t_loop_next_disposal_pass_single_converged_mark]

## 回退

- 輸出段落:拔掉 loop next 與處置閘裡呼叫報告函式的兩處。
- 出口修正(一):還原 loop next 判定段的改動即回到現狀(新迴圈又到不了跑滿上限,但不會壞別的)。
- ★回退拿不回來的★:改問處置閘之後,loop next 會對新迴圈寫出 cap-reached 記號(以前寫不到);治理帳只追加,寫進去的記號會被 `gov --stats` 的跑滿計數與「還開著的迴圈」判斷讀到。判錯了要人工補記一筆 `loop rewrite` 或在治理帳另記更正;收斂記號只由處置閘寫,這一點跟今天一樣,不因本案多出新的寫錯入口。

## 實務隱患

- 併發:報告函式只讀帳本;處置閘讀帳的方式與壞行擋法照舊,這份不另開讀帳路徑。loop next 改問處置閘後,會跟處置閘一樣讀材料、在過關時寫治理帳(這是處置閘既有行為,不是新增)。
- 效能:loop next 改問處置閘後多讀材料與席報告;舊編號 r1 併發席量過單次在百毫秒內。熔斷只數帳本裡這個編號的「折」欄。
- 不可逆(不排除):新迴圈第一次寫得出 cap-reached 記號,追加寫、不能撤;處置見〈回退〉。
- 已排除:金流:只讀本機帳本、印文字,不碰任何付款或計費
- 已排除:對外送出:不呼叫任何外部服務
- 已排除:守衛面:提示只印不擋,不改處置閘與 loop next 的過關判定和退出碼(S8、S9 綁測試);出口修正只把「到不了跑滿上限」變成到得了,不放寬任何過關條件,範圍外的迴圈路徑不變(S1、S10 綁測試)

## 誠實界線

- 提示只看閘的失敗原因、折入數走勢與最高嚴重度,看不到「後幾輪是不是修正本身帶進來的」——那是舊版被拿掉的訊號,要做得先有能逐行比對 patch 的工具。
- 門檻(20 條、只比最後兩輪)是起點,沒有回測;回看排在 REVISIT。
- 跑滿之後要不要擋第四輪,不在這份;這份只讓資訊在那時出現。
