# 審查跑滿上限提示_計劃

PRIOR-ART: 停不停看「再修一輪預期換到多少」而不是輪數(Wu 等,arXiv 2607.17641v1,設計審 r1 整合席上網核實過);卡住時拆小改動或往上找人裁(Google eng-practices);連續被擋或累計量過大就退回給人(Claude Code auto 模式的拒絕熔斷器,出處為第三方原始碼分析 openedclaude/claude-reviews-claude 第 07 章,沒有對照原始碼核實)。機制層沿用:處置閘(`loop status --disposal`)、每輪彙總那筆的折入清單(`folded_set`)與各席的 severity、治理帳既有的 cap-reached 記號;分級上限用 loop next 現在那一支,不另寫一份。
RETIRE-IF: ①上線後 8 週內,跑滿或熔斷時印的建議,跟事後治理帳記到的走向不一樣的次數多過一樣(建議沒在幫忙);②三個月內零次跑滿也零次熔斷(問題消失了)。

## 一句話

先讓「跑滿上限」真的會被說出來,再在那時(和累計折入過多時)印每輪折了幾條、最後一輪最高嚴重度,加一句依固定規則給的建議。**只印,不改任何閘的判定與退出碼。**

## 做法

### 一、修出口:loop next 要能說出「跑滿上限」

- 2026-08-25 之後開的迴圈(帳首日期在舊閘退役日之後),loop next 判「過了沒」改問處置閘,不再委派舊閘。舊迴圈照舊。
- 輪數已達上限而沒帶 --spec 時,不再先回「少了 --spec」:直接回「跑滿上限」,並把「帶 --spec 問處置閘看有沒有過」那行指令補好(帳上有材料路徑時)。理由:有沒有過要看材料,但「已經跑滿」不用。
- 上限由分級決定,處置閘要印的那段也叫同一支函式算,不寫第二份對照表。

### 二、印什麼

- **每輪折入數**:那一輪彙總那筆帳的折入清單條數;那一輪沒有彙總帳(只有各席留痕)就印「這輪沒記處置」。
- **每輪最高嚴重度**:那一輪各席帳的 severity 取最高。
- **建議**(依序套,第一個成立的就是):
  1. 有任何一輪沒記處置、或只有一輪 → 「判不了,自己看」,不給建議。
  2. 最後一輪折入數 ≥ 前一輪 → **換做法**:拆小改動、回頭改設計、或整類拿掉。
  3. 最後一輪最高嚴重度 ≤ minor → **附理由放行**(代碼審照舊只准放行 minor)。
  4. 其他(在下降、但還有 major 以上) → **再一輪還有進展**。
- 規則只看「最後一輪對前一輪」,不再用「第一輪的一半」這種門檻——舊版被抓到把 10→6→5 這種明明在降的判成持平(正確性席)。

### 三、提早熔斷(不等跑滿)

- 同一個審查編號,各輪彙總帳的折入條數累計超過 20 → 在處置閘輸出印「累計折入已經 N 條,建議拆小改動」。20 是照抄熔斷器的起點,回看後再調。
- 只看帳本裡這個編號的列(處置閘本來就讀進來了),不讀任何凍結審材,所以每輪都算也不拖慢。

### 四、印在哪裡

- `loop next` 回跑滿上限時:文字輸出與 `--json` 都要有(文字輸出是逐欄挑著印的,新欄位要加進去,不然只有 json 看得到——回滾席抓到既有欄位就這樣被悄悄吞掉)。
- `loop status --disposal`:輪數已達上限、或觸發熔斷時,在判定之後印同一段。處置閘因為帳本壞行等原因先擋下時,這段不印(不另開讀帳路徑去繞過既有的擋法)。
- 設計審與代碼審都印同一段;建議第 3 條在設計審也寫「附理由放行」,但處置閘本來就允許設計審放行 major,所以這條只在最後一輪 ≤ minor 時給,兩邊語意一致。

## 條款

- [S1] 當 2026-08-25 之後開的迴圈輪數已達分級上限、帶了 --spec 且處置閘沒過,`loop next` 應回跑滿上限而不是被舊閘擋下 [test:t_loop_next_cap_reached_on_disposal_loop]
- [S2] 當輪數已達上限而沒帶 --spec,`loop next` 應回跑滿上限,並在帳上有材料路徑時補好問處置閘的指令 [test:t_loop_next_cap_reached_without_spec]
- [S3] 當 `loop next` 回跑滿上限,文字輸出應列出每輪折入數、每輪最高嚴重度與一條建議 [test:t_loop_cap_report_text_output]
- [S4] 若最後一輪折入數大於或等於前一輪,則建議應是換做法 [test:t_loop_cap_report_not_declining_suggests_reshape]
- [S5] 若折入數在降且最後一輪最高嚴重度不高於 minor,則建議應是附理由放行;在降但仍有 major 以上,則建議應是再一輪 [test:t_loop_cap_report_declining]
- [S6] 若有任何一輪沒有彙總帳,則應印那一輪沒記處置並不給建議 [test:t_loop_cap_report_missing_carrier_no_advice]
- [S7] 當同一個審查編號各輪折入累計超過 20 條,處置閘輸出應印建議拆小改動,且不改變過關判定與退出碼 [test:t_disposal_early_breaker_total_folded]
- [S8] 當輪數已達上限,`loop status --disposal` 應印出與 S3 相同的一段,且不改變原本的過關判定與退出碼 [test:t_disposal_prints_cap_report_without_changing_verdict]
- [S9] 若迴圈是 2026-08-25 以前開的舊迴圈,則 `loop next` 的判定路徑應與現在相同 [test:t_loop_next_legacy_loop_unchanged]

## 回退

- 輸出段落:拔掉 loop next 與處置閘裡呼叫報告函式的兩處。
- 出口修正(一):還原 loop next 判定段的兩處改動即回到現狀(新迴圈又到不了跑滿上限,但不會壞別的)。不寫任何新帳欄位,沒有資料要搬。

## 實務隱患

- 併發:只讀帳本;處置閘讀帳的方式與壞行擋法照舊,這份不另開讀帳路徑。
- 效能:只數帳本裡這個編號的列;不讀凍結審材,每輪都算也只是一次計數。
- 已排除:金流:只讀本機帳本、印文字,不碰任何付款或計費
- 已排除:對外送出:不呼叫任何外部服務
- 已排除:不可逆:不寫新帳欄位,回退就是還原兩處呼叫與判定段
- 已排除:守衛面:建議只印不擋,不改處置閘與 loop next 的過關判定和退出碼(S7、S8 綁測試);出口修正只把「到不了跑滿上限」變成到得了,不放寬任何過關條件(S1、S9 綁測試)

## 誠實界線

- 建議規則只看折入數走勢與最高嚴重度,看不到「後幾輪是不是修正本身帶進來的」——那是舊版被拿掉的訊號,要做得先有能逐行比對 patch 的工具。
- 門檻(20 條、只比最後兩輪)是起點,沒有回測;回看排在 REVISIT。
- 跑滿之後要不要擋第四輪,不在這份;這份只讓資訊在那時出現。
