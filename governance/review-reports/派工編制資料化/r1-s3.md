# 審計結果:派工編制資料化 r1-snapshot

## Finding 1 — S1/S2 對 `code/standard` 的 (kind,tier) 假設,與 `cmd_loop_next` 真實邏輯正面衝突(已實測重現)

`_TIER_PARAMS`(scripts/lumos:4490)只有 4 個鍵 `{light, standard, high, legacy}`,**不分 design/code kind**——「standard」這個 tier 字串在真碼裡是全域共用的,width 固定吃 3。spec 把 roster 表鍵設計成 `(loop_kind, tier)`,並讓 `code/standard` 用同一個 tier 字串「standard」但宣告只需 1 席(sequential),spec 自己也發現了這個衝突,但只在 roster 表自身的自檢範圍內處理:

引句：「**防雙真相**:`mode=panel` 的條目(design/standard、design/high、code/high),occupies_w 席數必須等於 `_TIER_PARAMS` 的 width;`mode=single/sequential` 條目(design/light、code/standard)佔 W 席數必須=1——**`_TIER_PARAMS` 的 width 只約束 panel 模式**(pre-flight 抓到的結構事實:code/standard 走單 reviewer 循序,不吃 width=3)。」

問題是:`cmd_loop_next` 的 `width, cap = _TIER_PARAMS[eff_tier]` 是**無條件**執行的(scripts/lumos:4567),每次 `emit()` 都會把 `"width": width, "min_seats": width` 原樣塞進同一個 JSON payload(scripts/lumos:4582-4583)。spec 的「mode 只約束 roster 表自己的自檢」完全沒有觸碰這段既有邏輯。我實測驗證了兩層後果:

1. **輸出自相矛盾**:對一個 `code-`前綴、`--tier standard` 的 loop 呼叫 `loop next`,同一份 JSON 會同時印出既有欄位 `"min_seats": 3`,和 S2 新增的 `roster` 欄(code/standard 只宣告 1 個 required 席)——兩個欄位直接打架。實測輸出:
   {"phase": "plant-canary", "tier": "standard", ..., "width": 3, "min_seats": 3, ... "record_cmd": "... --tier standard ..."}
2. **workflow 硬斷**:照 `loop next` 印出的 `record_cmd`(帶 `--tier standard`,無 `--round`,因為 sequential 模式本就不用 `--round`)真的記一輪後,**下一次 `loop next` 直接 rc2 ERROR**:
   ERROR: tier=standard 要求 panel 格式(記錄帶 --round),帳面為 legacy 格式——格式衝突
   這正是 scripts/lumos:4569-4574 那段既有守衛(code-loop r1 折入的 tier↔格式一致性檢查),spec 完全沒提到、也沒有處理。程式碼裡的歷史註解(scripts/lumos:4602-4604)已明講三個真實跑循序模式的 code-loop(`code-slim-python`/`code-teardown-windows`/`code-slim-handoff`)全部因為這個 bug 被迫落到 `tier=None`(legacy),我對 `docs/.canary-log.jsonl` 的實查也證實:**全庫沒有任何一筆 `code-` loop 曾經成功錨定 `tier=standard`**——`code/standard` 這一列在真實資料裡從未被實際命中過。

也就是說,S2 描述的「`loop next` 吐應派清單」,對 spec 自己表格裡五列中最特殊的 `code/standard` 這一列,字面實作出來的東西是:第一次呼叫就已經和既有欄位自相矛盾,第二次呼叫直接把工具打壞(rc2),而這正好是 Growth Test 緣起③(「外家席換代偏離...工具無感知」)點名要接住的場景——結果這一列在目前設計下反而**永遠走不到**。測試策略 #1 也沒接住這個缺口:

引句：「1. `t_tier_roster_table`:表存在;各 (kind,tier) occupies_w 席數==`_TIER_PARAMS` width(防雙真相釘)。」

這句字面上是「每個 (kind,tier) 都要 == width」,若照字面實作,`code/standard`(occupies_w=1)會直接跟 `_TIER_PARAMS["standard"]`(width=3)不等而測試恆紅——這與 S1 段落裡「mode=single/sequential 必須=1」的例外規則自相矛盾;測試策略段完全沒提到這個 mode 分支。而 `t_loop_next_roster` 又刻意只測 `design/standard` 與 `code/high`(兩個 mode=panel、width 天然吻合的案例),**唯一有結構衝突的 `code/standard` 全程未被任何測試涵蓋**,衝突在測試計劃層就被繞過去,不會在收斂前被任何釘子抓到。

severity: blocker(照字面實作會讓 `loop next` 對 `code/standard` 這一列直接產生自相矛盾輸出,並在下一輪造成 rc2 硬斷,已用真 CLI 重現;且測試計劃完全沒有觸及此組合,不會被收斂閘擋下)
