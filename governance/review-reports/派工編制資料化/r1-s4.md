作為獨立審計席，針對《派工編制資料化_計劃》設計文件，聚焦內部自洽性與邏輯漏洞，審核意見如下：

### Finding 1: [Major] `seat_shortfall` 判準對「佔 W 席」與「總席數」的定義存在邏輯衝突
引句：「`seat_shortfall`:實派席數 < 應派 required 席數。」
引句：「`occupies_w`:是否佔 panel 寬度 W(否決席/對答案席不佔)。」
**失敗場景**：在 `code/standard` 條目中，包含 1 席「佔 W 席」與 1 席「不佔 W 席」(外家否決)。若實作時 `seat_shortfall` 僅比對 `_TIER_PARAMS` 的 width（即 1），則會漏掉對「外家否決」席位的缺席檢查；若比對總數（即 2），則與 `_TIER_PARAMS` 的 width 定義衝突。spec 未明確 `seat_shortfall` 的計數對象是「總席數」還是「佔 W 席數」，將導致對帳邏輯在非 panel 模式下產生誤報或漏報。

### Finding 2: [Major] `conditional` 席位導致 `seat_shortfall` 機械判定邏輯崩潰
引句：「`seat_shortfall`:實派席數 < 應派 required 席數。」
引句：「條件真值工具不可判,只印條件供編排者對」
**失敗場景**：在 `code/high` 階級中，`spec-conformance` 席位為 `conditional`。由於 spec 明定「工具不可判」條件真值，程式將無法確定該席位在當前輪次是否屬於「應派」範疇。這導致 `seat_shortfall` 的減法公式（應派 - 實派）因減數不確定而無法在代碼中實作，若強行實作，將在 `code/high` 輪次恆常噴出錯誤的短缺警告或完全跳過檢查。

### Finding 3: [Major] `unknown` 分類與 `external_missing` 判定邏輯存在前後矛盾
引句：「應派 external 席在實派 auditor 中零命中」
引句：「無命中=unknown,列出不判定」
**失敗場景**：若某輪派工快照中的 auditor 名稱為 `custom-model-v1`（不在關鍵字表內），依 spec 字面定義會被歸類為 `unknown` 且「不判定」。然而，`external_missing` 的判準是「external 零命中」，既然 `unknown` 不是 `external`，邏輯上應觸發 `external_missing` 警告。spec 同時要求「零命中就喊 missing」又要求「unknown 不判定」，導致實作時對未知模型的對帳行為處於未定義狀態。

### Finding 4: [Major] `sequential` 模式下多席位的執行順序與 `loop next` 行為未定義
引句：「mode=single/sequential 條目(design/light、code/standard)佔 W 席數必須=1」
引句：「| code/standard(sequential) | 單 reviewer×1(claude,required) | 外家否決×1(external,note-if-absent:standard 退同門+留痕) |」
**失敗場景**：`code/standard` 被定義為 `sequential`（循序）模式，但編制表卻列出了兩席（一席佔 W，一席不佔 W）。spec 未定義這兩席是「同時派發」還是「先後派發」。若 `loop next` 照字面實作，將無法判斷應一次吐出兩席清單，還是依據某種隱含狀態機分兩次吐出，這會直接導致自動化編排工具無法處理循序模式下的多席位派工。

### Finding 5: [Major] `kind` 判定規則與已知例外導致特定 repo 對帳功能失效
引句：「code- 含連字號開頭=code,其餘=design」
引句：「已知限制:歷史帳有 `code側刪除傳播守衛`/`codestage` 兩筆不合慣例 id 會被推定為 design,advisory 誤喊可忽略」
**失敗場景**：當使用者對 `codestage` 執行 `loop status --roster` 時，程式會依規則載入 `design` 的編制表（要求 3 席鏡頭席）來對帳實際為 `code` 的快照（僅 1 席 reviewer）。這將導致該 repo 的對帳輸出充滿無意義的「席位短缺」與「家族錯誤」警告。既然 spec 已識別出這些特定 ID，卻仍強制採用會導致錯誤結果的前綴判定法，屬於明知會產生錯誤行為的邏輯設計漏洞。

### Finding 6: [Minor] `fail-closed` 紀律在 advisory 模式下為無效宣告
引句：「required-fail-closed(缺=喊 missing+提示 fail-closed 紀律)」
引句：「恆不影響 rc**:觀測段只印字,gate 判定與 exit code 完全不動」
**失敗場景**：spec 定義了 `fail-closed`（失敗即關閉/阻斷）的紀律要求，但同時在 S3 宣告「恆不影響 rc」。這使得 `required-fail-closed` 在實作上與普通的 `required` 僅有字串提示的差別，無法達成真正的 fail-closed 行為，術語使用與機制設計存在語意矛盾。
