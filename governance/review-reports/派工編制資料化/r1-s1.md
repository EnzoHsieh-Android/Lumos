# 審計回報:派工編制資料化 r1-snapshot

## Finding 1

severity: major

引句：「帶 `--roster` 且帶 `--repo` 時啟用;逐輪掃 `governance/review-reports/<loop-id>/rN-dispatch*.json`(檔名慣例既有)。」

`loop status` 現有多個互斥旗標(`--disposal`/`--panel`/`--light`/`--settle`)在 `cmd_loop_status` 內各自 early return 到獨立分支/函式——`--disposal` 在 scripts/lumos:4320 直接 `return _loop_status_disposal(...)`,`--panel` 在 4328-4333 直接 `return _loop_status_panel(...)`,`--light` 有自己一串內嵌 return(4336-4375),只有完全不帶這些旗標的「legacy 預設路徑」才會落到函式尾段(4377 起)。spec 全程把 `--roster` 講成「帶就啟用」的附加觀測段,卻沒說它跟這些既有互斥旗標怎麼合成——若照字面在單一處「加一段」,對 roster 表五列中三列(design/standard、design/high、code/high 全是 `mode=panel`)與 design-loop 現行預設流程(SKILL.md:17-19 明講「design-loop 新 loop 一律走處置閘」,即 `--disposal`)完全不會印出任何觀測,恰好是最需要對帳、且是實際最常見呼叫形式(`--gate --panel` / `--disposal`)的場景。S1 的「防雙真相」段有仔細查過 `_TIER_PARAMS` 與實際 code 結構,但 S3 對 `cmd_loop_status` 的分支結構完全沒對照,是同一份 spec 內查證深度不一致的落差。

## Finding 2

severity: major

引句：「以 (loop_kind, tier) 為鍵;loop_kind 由 loop id 前綴判」

S1 的編制表只列 5 組 (kind,tier):design/light、design/standard、design/high、code/standard、code/high,缺 code×light 這一格。而 `--tier` 的合法值(`LOOP_TIERS`=light/standard/high,scripts/lumos 附近 argparse choices)不受 loop id 前綴任何約束——`lumos loop next code-foo --tier light` 在現行工具下是可達的合法呼叫(`_TIER_PARAMS["light"]` 查得到、cmd_loop_next 不檢查 kind)。S2 只講清楚 `legacy` tier 的特例(「沿 `_TIER_PARAMS` 慣例給單席通才」),完全沒講 (code, light) 這個表中不存在的組合要怎麼查——照字面查 `_TIER_ROSTER[(kind, tier)]` 會是未定義行為(查表 miss/例外),而不是像 legacy 那樣有明訂 fallback。

## Finding 3

severity: major

引句：「野字串→unknown 列出不判定(不誤喊 external_missing 的前提=分類 fail-open)」

這句話宣稱的因果不成立,跟同份 spec 自己定義的演算法矛盾。S3 對 `external_missing` 的判準是「應派 external 席在實派 auditor 中零命中」(逐字見上文 line 64),而 unknown 分類的 auditor 不算進「命中」——所以一個因為沒照 `<鏡頭>-<模型>` 慣例命名而被誤分類成 unknown 的**真外家席**,一樣會造成零命中,一樣觸發 `external_missing`。「分類 fail-open(野字串→unknown 而非硬猜某家族)」防的是誤把 unknown 判給 claude/external 哪一邊,並不能防止「零命中判準」本身把 unknown 排除在外造成的假警報。換句話說,spec 自己承諾的「不誤喊」與自己定義的判準邏輯是兩回事,literal 實作會產生跟自身聲稱矛盾的 false positive。

max severity: major
