# impact鏡頭機械化_計劃

> **★v2 重寫(2026-08-29)。v1 方案已作廢,不是修補是換方向。★** r1 五席(三內部+架構對齊+外家)獨立審出 **3 blocker + 17 major**,一致結論=方案選錯。v1 全文見 `governance/review-reports/impact-鏡頭機械化/r1-snapshot.md`,逐條去向見文末〈r1 審計修正紀錄〉。d1 裁定的「只做 S1、走完整設計審」仍有效,**變的是 S1 的內容**。

PRIOR-ART: **借用既有機制層,不自建、不加依賴**——落點=既有 `pitfalls --diff` 的人可讀分支(2026-08-02 已在該處印提醒,本案把「印指令」升成「印結果」);輸出截斷沿用既有「列 8 篇 + 還有 N 篇」慣例(落成核對同款);抑制用旗標(repo 既有做法,非 shell 語法)。**不採**收據+判定式(2026-08-02 已裁不加閘,理由今日仍成立且更強,見下)。外部觸發=讀 OmO 的 codegraph/LSP/AST-Grep,借「結構資訊要送到眼前」的想法,不借工具。

## 問題(數字修正)

code-loop 手冊第 4 步(★r1 F10 訂正:v1 誤寫第 3 步,第 3 步是已停用的植入自檢★)寫著「派 reviewer 前跑 `lumos impact --diff --json`、附 manifest 當第二鏡頭」,但幾乎沒人跑。

**★v1 引的「74 份只有 8 份」是錯的分母★**(r1 整合席與邊界席各自抓到)。今日自量:
- 派工單 **單一形態 75 份 / 逐席形態 100 份**,提到 impact 的共 **14 份**。
- 迴圈目錄 **74 個,其中 code* 只有 27 個**——而 impact 鏡頭**只是 code-loop 的規矩**,把 design 迴圈算進分母本身就錯。

**唯一真在消費 impact 的地方,不是 manifest 檔**:架構對齊席的派工模板 §7.6 有一格 `{lumos impact --diff 的固定席}`,是把節點**內插進派工詞**。這是今天唯一可運作的形態,v1 卻要改成「給路徑讓審查員自己讀」——反而會讓這席在收貨帳上變成「沒觸及材料」。

## v2 設計:把「叫你去跑」換成「結果就在眼前」

**一句話**:在編排者**本來就一定會跑**的那道指令的人可讀輸出裡,直接印出這批改動釘住的節點;不加閘、不寫收據、不碰任何既有欄位。

**落點**:`_pitfall_diff_mode()` 的**人可讀分支**——2026-08-02 已在該處印一行「派審查員之前,先看…\n    lumos impact --diff <range>」。v2 把那一行換成**真的跑 impact 並印出釘住的節點**:

```
派審查員之前,這次改動牽連到這些筆記(★=帶硬合約或出過事故,一定要看):
  ★ Systems/canary-audit.md
  ★ Systems/測試假綠形態.md
  …(列 8 篇)
  還有 12 篇釘住的、5 篇一般的(全部:lumos impact --diff <range>)
```

**為什麼這個落點不貴(★這是 2026-08-02 排除理由的洞★)**:當初排除「掛進 pitfalls」的理由是「pitfalls 在 pre-push 熱路徑上逐 ref 跑,掛上去每次 push 慢 26 倍」。但查 `scripts/hooks/pre-push` 實際呼叫:
- **熱路徑是 `--json`**(`pre-push:113`,每次 push 都跑,**本案完全不動**)。
- 人可讀那兩處(`pre-push:119`、`:151`)**只在 tier=high 或有效能提問時才跑**——那時本來就要停下來看。

**成本(今日實測,★r1 打臉後重量★)**:`pitfalls --diff` 0.26s;`impact --diff` **隨檔數線性成長**——11 檔 5.6s、15 檔 5.5s、24 檔 9.6s;r1 正確性席另量到 64 檔(HEAD~150 那種超大範圍)**52s**。典型代碼審 diff(10–25 檔)約 **5–10s**。
★v1 寫「單次為秒級」是低估,已訂正★。成本落在:①編排者互動式跑 pitfalls 拿 tier 時 +5~10s(**正是你要這份資訊的那一刻**)②pre-push 的 high 分支(罕見,且已在攔你)。超大範圍(>40 檔)會明顯有感,靠 `--no-impact` 逃生。

**抑制旗標**:`pitfalls --diff --no-impact` 供 pre-push 的人可讀呼叫使用(沿用既有 `--no-lint` 的形態),讓 hook 完全不受影響;預設開。

**範圍刀**:本機制天生只服務 code 側——`pitfalls --diff` 吃的就是 git 範圍,設計審審的是計劃筆記、根本不會呼叫它。**不碰 `loop next`**(它沒有 diff 範圍、且 design/code 共用),v1 的分流問題自動消失。

## ★憑什麼這次會有效?(r1 正確性席的致命提問,必須正面答)★

質疑逐字:那行提醒 **2026-08-02 就上線了**,而 75 份派工單**全部建於該日之後**——code 迴圈仍只有 **2/25** 跑過 impact。憑什麼再加一個同樣不硬擋的提醒會從 2/25 跳到接近 100%?

**答:v2 不是「第二個提醒」,它把動作整個拿掉。**
- A 案(現況)印的是**一條要你去跑的指令**——失敗模式是「看到了,但那要多花 5–10 秒,等一下再說」,然後就沒有了。**這個失敗模式已被 2/25 實測。**
- v2 印的是**結果本身**。編排者不需要做任何額外動作,釘住的節點就在他剛剛跑的那道指令的輸出裡、進了他的脈絡。**沒有可跳過的步驟。**

所以本案消滅的失敗模式是「**那個額外步驟被跳過**」,不是「人不聽提醒」。★這是機械成立的:改完之後,跑 pitfalls 就一定看得到內容。★ 至於看到之後有沒有用進派工——**仍不可觀測,不假裝可觀測**(見天花板)。

## 為什麼這樣才算答了 2026-08-02 那道舊題

舊案留下的題目是:**「怎麼在不擋住最常見路徑(standard)的前提下擋到它」**,以及**「收據綁 commit 會變雞生蛋,要先解」**。

v2 的答案是:**不擋。改成讓資訊自己出現在你面前,把「忘了跑」這個失敗模式直接消滅。**

- 舊案拒絕加閘的理由今天**更強**了:r1 邊界席實跑證明,收貨檢查只比對**檔名字串**——派工單列一個**根本不存在**的 manifest、報告寫一句「我讀了它」,檢查**全綠 rc0**。**任何建在這上面的閘都是裝飾。**
- 不寫收據 → **雞生蛋不存在**(那個坑源自「收據綁 head_sha,而寫收據本身就改檔」)。
- 不擋 standard → 不會逼人 `--no-verify`。

## 實務隱患(逐類答)

- **效能/熱路徑**:已排除——`--json` 分支一字不動,pre-push 判定路徑成本不變(實測 0.26s);人可讀分支 +5~10s(典型 10–25 檔;超大範圍更久),只在互動式與 high 分支發生,且 `--no-impact` 可關。
- **併發/資源/鎖**:已排除——純讀 vault 與計算,無連線、無鎖、無交易、無寫檔(★v2 不產任何檔★)。
- **回滾**:改動集中在一個函式的人可讀分支 + 一個旗標,`git revert` 即回;**不產檔、不改欄位、不改任何 rc 語意**,回滾後無殘留狀態。
- **不可逆/對外**:已排除——不寄送、不碰正式環境、不刪不覆蓋任何東西。
- **★真隱患:輸出噪音★**——實測一批改動可釘住 **20 篇**,全印會洗版並稀釋注意力。處置:沿用既有「列 8 篇 + 還有 N 篇」截斷慣例(與落成核對同款),釘住的優先列;要全部就自己跑那行指令。**截斷數字上線後看實際觀感再調**。
  ★訂正(r1 F8)★:v1 寫「既有 impact 已有固定席全保、非固定 top-8 的收斂規則,不是無上限」——**對固定席不成立**:`top-8` 只切非固定席,**固定席完全沒有上限**(本 repo 實測 25~26 席、manifest 21KB)。所以截斷是**本案新增的**,不是沿用既有上限。
- **★真隱患:vault 大或 impact 變慢時,互動體驗變差★**——5~10s 是本 repo 典型範圍的現況(實測隨檔數線性成長),別的專案 vault 更大會更久。處置:`--no-impact` 隨時可關;若日後在本 repo 的典型範圍實測穩定超過 10s,改成只算固定席(需先驗「只算固定席真的比較快」——舊案量過 `--incidents-only` **並不便宜**,成本在載 vault 不在排序,故不預設這條路可行)。
- **與「前置加重一律拒」教義**:已排除——不加席、不加輪、不加審查強度;只是把既有提醒的內容補上。
- **與零依賴家規**:已排除——只用既有 lumos 內部函式。
- **應試化**:不涉——輸出是資料不是評分表,且沒有任何閘可鑽。

## 誠實天花板與重驗條件

- **★天花板不變(2026-08-02 就寫死,不得淡化)★:任何機械化都只能證明「資訊出現在編排者面前」,證明不了「它真的被餵進 reviewer 的 prompt」。** 派工發生在模型腦內,外部不可觀測。r1 邊界席更進一步證明:現有收貨檢查連「檔案存不存在」都驗不出,**所以不要再嘗試用 seat-check 量這件事**。
- **本案真正消滅的失敗模式只有一個**:「連跑都沒跑」。這一條是機械成立的(改完之後它自動跑)。**用了沒有,量不到,不假裝量得到。**
- **重驗條件**:①上線後兩週內,任一次互動式 `pitfalls --diff` 若沒印出釘住清單 = 機制沒生效,回頭查;②若編排者開始習慣性加 `--no-impact` 繞過(治理帳看不到,靠自陳),代表噪音或延遲不可接受 → 調截斷數或改設計;③實測延遲若逾 10s,重評落點。
- **不做的事要記著**:收據+判定式的閘**維持不做**;要重啟,先答出「怎麼在 seat-check 這種字串比對之外,機械證明資訊被消費」——這題今天仍無解。
