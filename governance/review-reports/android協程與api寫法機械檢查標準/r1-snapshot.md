# Android協程與API寫法機械檢查標準_計劃

> 白話:Android(Kotlin 協程、Flow、Compose、架構、資料層)的「標準寫法」原本大多只寫在 kotlin-idioms 慣例文件裡、靠審查員記得看。這份計劃把它們窮舉成一份型錄(473 條,每條寫壞寫法、標準寫法、機器怎麼查、怎麼逼 AI 照做),並分三批接進 lumos 的自動流程:①結構規則包接新增告警閘;②AI 寫完當下、審查迴圈頭尾自動檢查,不靠人記指令;③語意類情境要表態並由盲判席覆核(另開計劃)。目標是「審查迴圈裡就檢查乾淨,推送只是最後確認」,人工審查只剩機器判不了的業務語意。出身:[[Projects/Android協程與API協同機械審_調研]];使用者 2026-11-04「就算窮舉也要把標準寫法的檢查制定下來」「先把機械能檢查的鋪完」、2026-11-05「要全面覆蓋」「審查迴圈中就檢查乾淨」「自動化,不需要我記得敲指令」「怕寫了但完全沒參考」。

PRIOR-ART: ①型錄來源:Android 官方(協程最佳實務、Flow、UI events、State、Side-effects、Data layer、Room、DataStore、WorkManager、Testing)、kotlinx.coroutines 官方文件、現成規則庫逐條對照(detekt 1.23.8、santimattius structured-coroutines、Sonar Kotlin、androidx 隨函式庫附帶的 lint、Android Lint 內建檢查、mrmans0n compose-rules、Slack compose-lints),2026-11-05 五路調研後合併去重;能開現成規則的不自寫。②自寫規則的承載工具用 ast-grep(結構比對、原生 SARIF、`--config` 指定規則包、收空白分隔多檔,2026-11-05 實測),要綁變數名的那幾條用 semgrep;判準借其他生態已上線的做法(react-doctor server-sequential-independent-await、Vercel NO_SERIAL_ASYNC_CALLS、ESLint require-atomic-updates)。③「寫完當下就擋」借 lumos 既有的回合結束擋停機制(收工點名那支鉤子:擋一次讓模型續做、兩道護欄防無限擋);「改檔前推相關脈絡」借既有的改檔前影響鉤子。④「標準寫法要真的被參考」的做法:錯誤訊息直接帶修法是 ESLint/Clippy 的慣例(rule docs + suggestion/fix);ast-grep 規則可附 fix。來源見〈來源〉。
RETIRE-IF: 某條自寫規則上線三個月,在消費專案的放行紀錄(`lumos lint-waive` 寫進 `.lumos/lint-waivers.json` 的那份,每筆帶理由)裡誤報多過真報,就把那條降成提示或拿掉;detekt 2.0、structured-coroutines 或 androidx lint 的現成規則涵蓋到某條自寫規則且能接進推送前檢查時,換成現成的、刪自寫那條;回合結束檢查連續三個月零擋停,降成只在審查迴圈跑。

## 用詞

- **型錄**:`skills/kotlin-idioms/checks-catalog.md`(新增)。473 列,依主題分九張表(API、FLOW、STATE、CO、UI、ARCH、DATA、TEST、PERF),每列欄位:編號、名稱、壞寫法形狀、標準寫法、後果、現成規則、級、情境怎麼認、接電方式、實測狀態、來源。另有〈情境決策表〉一節。型錄是「標準寫法」的單一來源;kotlin-idioms 本文的每條規則改成指向型錄編號,不重抄。
- **級**:A 現成規則可開 / B 能用語法結構比對 / C 只能寫測試驗行為 / D 只能人判。可複選。
- **情境怎麼認**:形狀(從程式長相認得出)/ 語意(要看語意才判得出,例:兩支呼叫是否互不依賴、是事件還是狀態)。2026-11-05 合併後形狀 367 列、語意 106 列。
- **接電方式**(使用者 2026-11-05 要求:每列都要接,沒接電的列不收):
  1. 告警帶寫法——規則訊息寫標準寫法與型錄編號;能一對一替換的附 ast-grep `fix`。
  2. 當下推相關列——改檔前鉤子命中觸發字時,只推型錄〈情境決策表〉相關的一到三列。
  3. 表態對程式——推送前表態要引型錄編號,機器核對改動裡真的出現那個寫法(第三批)。
  4. 行為測試或正向約束——不靠讀:虛擬時間等測試範本、架構測試(第三批之後)。
  5. 盲判席——語意類情境由沒看過作者答案的代理再判一次,機器比一致(第三批)。
  形狀類至少有 1 或 4;語意類必有 3 與 5。
- **表態**:既有的棧別提問表態閘([[Systems/棧別提問表態閘]]):改動碰到某類寫法時,推送前要對那幾題逐題作答;本案的「表態對程式」是在作答時引型錄編號,再由機器核對(批三)。
- **正向約束**:不靠讀文件、用會失敗的測試把寫法釘住,例如架構測試斷言「ViewModel 不得依賴 Context」、虛擬時間測試斷言「兩支互不依賴的呼叫總時間等於較慢那支」。
- **告警身分(指紋)**:新增告警閘替每條告警算的身分字串(規則、檔、去掉行號後的內容),用來判斷「同一條告警」;放行紀錄也是用它。「同一批告警」= 這次工作樹檢查新增告警的身分集合,排序後取雜湊。
- **light 等級、盲判席**:light 是代碼審查迴圈的輕量檔(一到兩席、最多兩輪,見 lumos-code-loop 手冊);盲判席是批三新增的一席,只拿程式段、上下文與型錄候選列,不看作者的表態,自己判這段屬於哪一列。
- **規則包**:`configs/ast-grep/kotlin-android/`(新增):`sgconfig.yml`、`rules/<主題>.yml`、每條規則的壞例好例樣本 `samples/bad/`、`samples/good/`;提示級規則另放 `sgconfig-hints.yml`(同資料夾,範本預設不接);要綁變數名的放 `configs/semgrep/kotlin-android.yml`(新增)。家是 [[Systems/linter精選目錄]]。
- **工作樹檢查**:對「還沒提交的改動」跑新增告警比對——基準是 HEAD 那一版、現在版直接讀工作樹的檔。既有新增告警閘只比兩個提交(終點是工作樹時判成環境不可用),本案擴充成也能比工作樹。

## 範圍(批一、批二)

1. **型錄**:新增上面那份檔;kotlin-idioms 的 SKILL.md 每條規則的機檢欄改成型錄編號;SKILL.md 開頭加一行「寫或審 Kotlin 前先看型錄〈情境決策表〉」。
2. **規則包**:B 級能寫成純語法規則的全部寫成 ast-grep 規則;每條規則:`id` 用 `kt-` 前綴;`message` 開頭是 `[<型錄編號>]`,後面一句「錯在哪;改用 <標準寫法>」;severity 只用 error(必出事)、warning(多半出事)、hint(提示級)。每條至少兩個壞例、兩個好例(含最容易誤報的相似寫法)。做不到零誤報的降 hint;要型別、跨檔、綁名字的不寫,在型錄該列實測狀態寫「純語法做不到:<原因>」。
3. **宣告範本**:[[Systems/linter精選目錄]] 加 Kotlin 規則包的 `.lumos/lint.json` 範本:`ast-grep scan --config <toolchain>/configs/ast-grep/kotlin-android/sgconfig.yml --format sarif {LINT_FILES} > {LINT_SARIF_OUT}`;semgrep 那條同形。hint 級在新增告警閘裡怎麼處理:照工具原樣進 SARIF(閘不分等級,一律算新增),所以 hint 級規則另放一個 `sgconfig-hints.yml`、範本預設不接;要接的專案自己加。
4. **工作樹檢查**:新增告警閘的判定函式多收一種終點「工作樹」:基準取 HEAD、現在版讀工作樹的檔(含未追蹤但沒被忽略的檔),其餘(設定檔取現在版、告警身分、放行紀錄)照舊。跟推送前不同的只有一處:時間預算不夠而沒跑到的命令,工作樹檢查只列出來、不算擋(推送前閘照舊算擋、會再跑完整的)。新指令 `lumos lint-new --worktree [--budget 秒]`(新增):有新增告警 rc1 並印每條的規則訊息;沒有、或環境不可用(工具沒裝、跑不出結果)rc0 並印原因。
5. **回合結束自動檢查**:收工點名那支回合結束鉤子多一道:專案有 `.lumos/lint.json`、工作樹上有未提交的程式碼檔時,跑工作樹檢查(預算預設 20 秒,可用 `.lumos/config.json` 的 `lint_new` 區塊新加的 `stop_budget_sec` 調,跟既有新增告警設定放同一處);有新增告警就回 decision:block,原因寫「這幾條新增告警要先修」加每條規則訊息(訊息裡已有標準寫法與型錄編號)。防無限擋:①payload 帶 `stop_hook_active`(這輪已經是被擋後的續做)時這道一律不擋;②同一會談、同一批告警只擋一次,用它自己的會談標記檔(檔名含那批的雜湊,跟既有「改 code 沒動圖譜」那道的名額標記分開),之後同一批只印提醒;告警變了(修掉一條、又新增一條)算新的一批。`LUMOS_STOP_LINT_OFF=1`(新增)關掉這一道。既有鉤子現在只有一道、一則訊息;改成兩道各自判、各自佔各自的名額,都要擋時把兩段原因合成一則 decision:block。
6. **改檔前推相關列**:改檔前影響鉤子在目標是 `.kt` 檔、而且要寫進去的內容(既有那支取 Edit/MultiEdit/Write 寫入內容的函式)含〈情境決策表〉某列的觸發字時,在既有輸出後面加最多三列「情境 → 標準寫法 → 不適用時」。觸發字是決策表新增的一欄。同一列同一會談只推一次:既有冷卻是「每支檔 20 分鐘」,語意不同,改借既有的「同會談只講一次」標記函式,以列編號為鍵。
7. **代碼審通過前先跑機械檢查**:`lumos code-loop pass` 寫留痕前,對同一版本跑新增告警與表態兩道判定(就是推送檢查裡那兩道的同一支判定函式);任一道擋下就不寫留痕、rc1,印擋下原因與修法。逃生門沿用既有:誤報走 `lumos lint-waive`、整道關閉走既有環境變數 `LUMOS_SKIP_LINT_NEW`。`code-loop skip` 不受影響(那是刻意跳過審查,本來就要寫理由);現在 pass 與 skip 走同一段程式,檢查只加在 pass 那一支。
8. **代碼審手冊**:lumos-code-loop 的手冊第一步改成「先跑 `lumos lint-new --worktree`(改動已提交就對 merge-base 到 HEAD 跑新增告警閘),乾淨才派審查席」;不用 `lumos code-loop check`,因為 tier high 在派席之前必然因為還沒有審查留痕而擋,看不出機械那幾道乾不乾淨。審查席的派工材料附機械檢查結果,寫明「機械已查的類別席位不報」。表態照既有手冊在推送前作答,本案不改。

**不做**:不改推送前閘本身的判定(它照舊跑、當最後確認;判定函式多收工作樹終點,但終點是提交時走原路徑、結果一字不變);不改消費專案的檔;不在推送前閘或回合結束鉤子裡呼叫模型;不寫 detekt 自訂規則 jar;批三到批五不在本計劃。

## 裁決紀錄

- **一次性事件的標準寫法(2026-11-05,使用者授權由 AI 裁)**:原計劃寫「事件用 SharedFlow 或 Channel」,Android 官方 UI events 指南把它列為反模式(畫面在背景時事件會遺失),改成「事件化成狀態、畫面處理完回報已處理」;Channel 只留給真的不屬於畫面狀態的內部訊號,且要 BUFFERED、在 repeatOnLifecycle 裡收。依據:developer.android.com 的 UI events 頁。
- **型錄不進計劃筆記本文**:473 列約 24 萬字元,超過設計審單份材料上限;計劃只寫設計與條款,型錄另存一檔,設計審抽樣審(每主題抽 5 列)並全量跑機械檢查(欄位齊、接電方式符合規則、編號唯一)。
- **hint 級規則預設不接推送閘**:新增告警閘不分等級,接了就會擋;提示級的誤報可能高,擋人會讓人學會無腦放行。

## 批三的進迴圈條件(2026-11-05 使用者確認照建議)

- 改動命中型錄規則(結構規則告警,或改檔內容含〈情境決策表〉觸發字)時,這批改動自動以 light 等級拉進代碼審查迴圈,席位固定多一席「情境盲判席」(只給程式段、上下文與候選列,不給作者答案)。
- 沒命中的改動照舊只在推送前閘確認。
- 理由:使用者要求「審查迴圈中就檢查乾淨,不用等到推送」「不需要我記得敲指令」;只對命中的改動開迴圈,避免每次改動都多一輪審查的成本。細節在批三計劃。

## 實務隱患

- **規則包誤報擋人**:每條至少兩個「最容易誤報的好例」;上線後誤報走既有放行指令,放行會被統計(撤除條件吃這個數)。
- **工具沒裝**:消費專案沒裝 ast-grep 時,新增告警閘照既有規則判環境不可用、自動放行並記帳;回合結束檢查同樣放行並印一行「沒裝 ast-grep,寫法檢查沒跑」,而且同一會談只印一次。
- **回合結束檢查拖慢每一輪**:ast-grep 對幾支檔是毫秒級;detekt 這類慢工具也在同一份宣告裡時,用預算截斷;截斷的命令只列出不擋(見範圍 4;推送前閘會再跑完整的)。
- **擋停迴圈**:修不掉的告警會讓 AI 每輪被擋;同一批只擋一次、續做那輪不擋(範圍 5),推送前閘照擋,逃生門是放行並寫理由。
- **改檔前推列太吵**:最多三列、同列同會談只推一次。
- **代碼審通過變嚴會卡住非 Android 專案**:機械檢查就是推送前會擋的那兩道,通過時先擋只是提早,不新增擋的條件。沒有 `.lumos/lint.json` 的專案新增告警那道本來就放行;表態那道不看宣告、看改動有沒有碰到棧別題,照它在推送前的規則判。
- **跟 detekt 那案改同一道閘**:[[Projects/Android的detekt推送前真的擋_計劃]] 也改新增告警閘(逗號佔位符與探針)。那案先做;本案的工作樹終點在那案合進主線後再接,工作樹檢查對逗號佔位符命令照那案的規則加探針。
- **舊否決對照**:2026-11-05 跑 `lumos rejections`(396 行)按概念比對,沒有撞到本案的否決;相關的三條都同向——新增告警閘出錯就放行(本案沿用)、改檔前推播零命中不講(本案只在命中觸發字時推)、回合結束鉤子只印一行的量測案(本案另加一道,不改那道)。
- 已排除:金流:只讀程式碼,不碰付款或點數
- 已排除:對外送出:檢查只在本機跑,不送任何東西出去
- 已排除:不可逆:新增檔與擴充既有函式,退提交即回原狀;放行檔與治理帳是追加,不改舊紀錄
- 守衛面:本案改回合結束鉤子、代碼審通過與新增告警閘,屬守衛面,走完整設計審
