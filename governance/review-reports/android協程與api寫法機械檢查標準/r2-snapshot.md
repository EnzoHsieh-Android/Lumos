# Android協程與API寫法機械檢查標準_計劃

> 白話:Android(Kotlin 協程、Flow、Compose、架構、資料層)的「標準寫法」原本大多只寫在 kotlin-idioms 慣例文件裡、靠審查員記得看。這份計劃把它們窮舉成一份型錄(473 條,每條寫壞寫法、標準寫法、機器怎麼查、怎麼逼 AI 照做),並分三批接進 lumos 的自動流程:①結構規則包接新增告警閘;②AI 寫完當下、審查迴圈頭尾自動檢查,不靠人記指令;③語意類情境要表態並由盲判席覆核(另開計劃)。目標是「審查迴圈裡就檢查乾淨,推送只是最後確認」,人工審查只剩機器判不了的業務語意。出身:[[Projects/Android協程與API協同機械審_調研]];使用者 2026-11-04「就算窮舉也要把標準寫法的檢查制定下來」「先把機械能檢查的鋪完」、2026-11-05「要全面覆蓋」「審查迴圈中就檢查乾淨」「自動化,不需要我記得敲指令」「怕寫了但完全沒參考」。

PRIOR-ART: ①型錄來源:Android 官方(協程最佳實務、Flow、UI events、State、Side-effects、Data layer、Room、DataStore、WorkManager、Testing)、kotlinx.coroutines 官方文件、現成規則庫逐條對照(detekt 1.23.8、santimattius structured-coroutines、Sonar Kotlin、androidx 隨函式庫附帶的 lint、Android Lint 內建檢查、mrmans0n compose-rules、Slack compose-lints),2026-11-05 五路調研後合併去重;能開現成規則的不自寫。②自寫規則的承載工具用 ast-grep(結構比對、原生 SARIF、`--config` 指定規則包、收空白分隔多檔,2026-11-05 實測),要綁變數名的那幾條用 semgrep;判準借其他生態已上線的做法(react-doctor server-sequential-independent-await、Vercel NO_SERIAL_ASYNC_CALLS、ESLint require-atomic-updates)。③「寫完當下就擋」借 lumos 既有的回合結束擋停機制(收工點名那支鉤子:擋一次讓模型續做、兩道護欄防無限擋);「改檔前推相關脈絡」借既有的改檔前影響鉤子。④「標準寫法要真的被參考」的做法:錯誤訊息直接帶修法是 ESLint/Clippy 的慣例(rule docs + suggestion/fix);ast-grep 規則可附 fix。來源見〈來源〉。
RETIRE-IF: 某條自寫規則上線三個月,在消費專案的放行紀錄(`lumos lint-waive` 寫進 `.lumos/lint-waivers.json` 的那份,每筆帶理由)裡誤報多過真報,就把那條降成提示或拿掉;detekt 2.0、structured-coroutines 或 androidx lint 的現成規則涵蓋到某條自寫規則且能接進推送前檢查時,換成現成的、刪自寫那條;回合結束檢查連續三個月零擋停,降成只在審查迴圈跑。

## 用詞

- **型錄**:`skills/kotlin-idioms/checks-catalog.md`(新增)。473 列,依主題分九張表(API、FLOW、STATE、CO、UI、ARCH、DATA、TEST、PERF),每列欄位:編號、名稱、壞寫法形狀、標準寫法、後果、現成規則、級、情境怎麼認、接電方式、實測狀態、來源。另有〈情境決策表〉一節。型錄是「標準寫法」的單一來源;kotlin-idioms 本文的每條規則改成指向型錄編號,不重抄。
- **級**:A 現成規則可開 / B 能用語法結構比對 / C 只能寫測試驗行為 / D 只能人判。可複選。
- **情境怎麼認**:形狀(從程式長相認得出)/ 語意(要看語意才判得出,例:兩支呼叫是否互不依賴、是事件還是狀態)。2026-11-05 合併後形狀 367 列、語意 106 列。
- **接電方式**(使用者 2026-11-05 要求:每列都要接,沒接電的列不收):
  1. 告警帶寫法——規則訊息寫標準寫法與型錄編號;能一對一替換的附 ast-grep `fix`。
  2. 當下推相關列——改檔前鉤子命中觸發字時,只推型錄〈情境決策表〉相關的一到三列。
  3. 表態對程式——推送前表態要引型錄編號,機器核對改動裡真的出現那個寫法(第三批)。
  4. 行為測試或正向約束——不靠讀:虛擬時間等測試範本、架構測試(第三批之後)。
  5. 盲判席——語意類情境由沒看過作者答案的代理再判一次,機器比一致(第三批)。
  形狀類至少有 1 或 4;語意類必有 3,而且除了標「(人裁)」的業務判斷列,也要有 5。每種接電方式在哪一批真的生效寫在型錄的「通電批次」欄;批一、批二只有 1、2 與部分 4 生效,其餘列要等後面批次(見〈天花板〉)。
- **表態**:既有的棧別提問表態閘([[Systems/棧別提問表態閘]]):改動碰到某類寫法時,推送前要對那幾題逐題作答;本案的「表態對程式」是在作答時引型錄編號,再由機器核對(批三)。
- **正向約束**:不靠讀文件、用會失敗的測試把寫法釘住,例如架構測試斷言「ViewModel 不得依賴 Context」、虛擬時間測試斷言「兩支互不依賴的呼叫總時間等於較慢那支」。
- **告警身分(指紋)**:新增告警閘替每條告警算的身分字串(規則、檔、去掉行號後的內容),用來判斷「同一條告警」;放行紀錄也是用它。「同一批告警」= 這次工作樹檢查新增告警的指紋多重集合(同一指紋出現幾次也算),排序後取雜湊。
- **light 等級、盲判席**:light 是代碼審查迴圈的輕量檔(見 lumos-code-loop 手冊:不帶輪次、席數比完整審少);盲判席是批三新增的一席,只拿程式段、上下文與型錄候選列,不看作者的表態,自己判這段屬於哪一列。
- **規則包**:`configs/ast-grep/kotlin-android/`(新增):`sgconfig.yml`、`rules/<主題>.yml`、每條規則的壞例好例樣本 `samples/bad/`、`samples/good/`;提示級規則另放 `sgconfig-hints.yml`(同資料夾,範本預設不接);要綁變數名的放 `configs/semgrep/kotlin-android.yml`(新增)。規則包與型錄是工具鏈自己的程式與資料,另開一篇 Systems 節點當家(暫名 `Systems/kotlin規則包`,用 `lumos new system` 登記這些檔);[[Systems/linter精選目錄]] 只放宣告範本與指向它的連結。
- **工作樹檢查**:對「還沒提交的改動」跑新增告警比對——基準是 HEAD 那一版、現在版直接讀工作樹的檔。既有新增告警閘只比兩個提交(終點解不出來時判成環境不可用),本案多一個明示的「工作樹」終點。新增告警閘本體的說明在 [[Systems/pitfalls-code-loop]](設定、關閉方式寫在那篇)。

## 範圍(批一、批二)

1. **型錄**:新增上面那份檔;kotlin-idioms 的 SKILL.md 每條規則的機檢欄改成型錄編號;SKILL.md 開頭加一行「寫或審 Kotlin 前先看型錄〈情境決策表〉」。型錄加一欄「通電批次」:這一列的接電方式哪一種在哪一批真的生效(例:A 級現成規則要批四、表態與盲判要批三);〈情境決策表〉加「列編號」欄(D-1 起)。型錄裡指向會談暫存區的路徑(規則草稿、研究稿)在落地時改成 repo 內路徑或拿掉;統計節用程式重算(規則條數照規則包實數)。
2. **規則包**:B 級能寫成純語法規則的全部寫成 ast-grep 規則;每條規則:`id` 用 `kt-` 前綴;`message` 一句、**不超過 120 字**(新增告警閘解析 SARIF 時截在 120 字,超過的修法會被切掉),格式 `[<型錄編號>] 錯在哪;改用 <最短的標準寫法>`,完整寫法留在型錄、用編號找;severity 只用 error(必出事)、warning(多半出事)、hint(提示級)。每條至少兩個壞例、兩個好例(含最容易誤報的相似寫法)。做不到零誤報的降 hint;要型別、跨檔、綁名字的不寫 ast-grep 版,在型錄該列實測狀態寫「純語法做不到:<原因>」——API-1(互不依賴的串行等待)要綁「第二句沒用到第一句的名字」,只放 semgrep 版。
3. **落地前的真實專案量測**:規則包進 repo 之前,對兩個真的 Android 專案(實驗專案複本與一個公開的大型 Android 範例專案)整份原始碼跑一次,每條 warning/error 規則的命中逐條人工判真假;某條規則誤報超過命中的一成(照 Google Tricorder「沒用的告警要壓在一成以下,壓不下就停用」的做法)就降 hint,結果寫進型錄實測狀態欄。
4. **宣告範本**:[[Systems/linter精選目錄]] 加 Kotlin 規則包的 `.lumos/lint.json` 範本:`ast-grep scan --config $HOME/harness/lumos-toolchain/configs/ast-grep/kotlin-android/sgconfig.yml --format sarif {LINT_FILES} > {LINT_SARIF_OUT}`(路徑跟既有 detekt 範本同一種寫法);semgrep 那條同形。範本附「CI 要先裝 ast-grep-cli(釘版本)並 clone 工具鏈,沒裝時新增告警閘判環境不可用、照既有規則放行」。hint 級規則放 `sgconfig-hints.yml`,範本預設不接(新增告警閘不分等級,接了就擋)。
5. **測試檔也要掃(設定開關)**:新增告警閘現在一律排除測試路徑(`src/test/`、`*_test.*` 這類),型錄 TEST 主題的規則因此在閘裡永遠不響。`.lumos/config.json` 的 `lint_new` 區塊加 `include_test_paths`(副檔名清單,預設空 = 照舊排除);Kotlin 範本設 `["kt"]`。不加這個開關的最小解是「TEST 主題只靠行為測試接電」,但那 18 列是形狀類,型錄要求的就是告警,所以加開關。
6. **新增告警指令**:`lumos lint-new`(新增)兩種用法:`--diff <範圍>` 對提交範圍跑既有的新增告警判定;`--worktree [--only <檔>…]` 跑工作樹檢查。兩種都加 `--budget 秒`。有新增告警 rc1,每條印「檔:行、規則訊息、放行用的指紋」;沒有 rc0;環境不可用(工具沒裝、跑不出結果)rc0 並印哪條命令沒跑、為什麼(第一個詞找不到執行檔就明說「沒裝 <工具>」);全部命令都沒跑到時印「沒有檢查到任何東西,不算乾淨」,不印「沒有新增的告警」。這支指令不寫治理帳(放行帳只有推送前閘記,避免每回合灌一筆)。
7. **工作樹檢查**:判定函式多收一個明示參數「終點是工作樹」(不沿用「終點解不出來」那條路,那條照舊判環境不可用);基準取 HEAD,現在版讀工作樹。改動清單用暫時索引算:複製目前索引到暫時檔、在暫時索引上 `git add -A`、`git diff --cached --find-renames HEAD`,真正的索引不動(git 自己的 stash 也用暫時索引;2026-11-05 實驗:未追蹤的改名 `mv Foo.kt Bar.kt` 配得到 R100,真索引仍是 D 加 ??)。合併衝突中的檔(狀態 U)不掃,列成「衝突中、沒檢查」。路徑在 `.lumos/` 底下的一律不掃(新增告警閘自己的快照暫存放在那裡,消費專案不一定忽略它)。`--only` 給了就只看那幾支。時間預算不夠而沒跑到的命令,工作樹檢查只列出、不算擋,但工作樹模式的單條保底降成 1 秒(既有保底 30 秒是給推送前跑 detekt 這種慢工具的,照用會讓 20 秒內的檢查一條都不跑)。
8. **回合結束自動檢查**:收工點名那支回合結束鉤子(Claude 與 Codex 共用同一支)多一道「寫法檢查」,跟既有「改 code 沒動圖譜」那道並列、各自判,插在既有那道的所有提早離開(找不到圖譜、動過筆記、同批檔已講過)之前,所以沒有圖譜的專案、這輪也動了筆記的情況照樣跑。條件:專案根有 `.lumos/lint.json`;這一輪逐字稿裡有寫檔動作;payload 沒有 `stop_hook_active`;`LUMOS_STOP_LINT_OFF`(新增)沒設。檢查範圍只限這一輪逐字稿裡寫過的程式碼檔(`--only`),不碰同一工作目錄別的會談的改動。時間:不另加設定鍵,從鉤子既有的內層預算(外層天花板乘 0.7 扣掉已用)切一半給這道、上限 15 秒,另一半留給既有那道;鉤子天花板只有註冊表一個來源。有新增告警就回 decision:block,原因寫「這幾條新增告警要先修」加每條「檔:行、規則訊息、放行指紋」,結尾一行教放行指令。防無限擋:同一會談同一批告警(這一批告警指紋的多重集合——同一指紋出現幾次也算進去——排序後的雜湊)只擋一次,之後只提醒;一個會談這道最多擋三次,之後只提醒;名額標記放既有擋停名額的同一個目錄、過同一個信任檢查。兩道都要擋時把兩段原因合成一則 decision:block,各自的名額各自記。
9. **改檔前推相關列**:比對在 lumos 本體做,鉤子只印(跟既有棧別題同一個分工)。鉤子把寫入內容交給 `lumos impact --file <檔> --delta-stdin`(新增旗標),lumos 回傳命中的決策表列,鉤子把它們接在既有輸出後面;既有輸出是空的時候單獨輸出。比對規則:只看寫入的新內容(Edit 的新字串、Write 的全文),去掉註解與字串字面值;觸發字整詞比對、分大小寫;決策表的觸發字分「強」(專有 API 名,如 `flatMapLatest`、`supervisorScope`)與「弱」(`map`、`try` 這類常用字),一列要有一個強字或兩個不同的弱字才算命中;命中多列時照命中字數多寡、再照表序取前三列;只有真的印出的那幾列才記「同會談講過」(用既有的同會談只講一次標記,鍵是列編號)。型錄由 lumos 從自己的安裝位置找。只做 `.kt`、`.kts`。Codex 的改檔工具拿不到寫入內容,這一版不推。
10. **代碼審通過前先跑機械檢查**:把推送檢查裡「新增告警」與「表態」兩段抽成一支共用函式,推送檢查與 `lumos code-loop pass` 都呼叫它(不另寫判定)。`pass` 的範圍跟 `code-loop check` 不帶 `--diff` 時的預設範圍相同(跟主線的分岔點到 HEAD);這比推送前只看「遠端已有到這次」的範圍寬,分支裡更早的提交若帶未放行的新增告警,`pass` 會擋,出口是 `lumos lint-waive`。任一道擋下就不寫留痕、rc1,印擋下原因與修法。`code-loop skip` 不受影響;現在 pass 與 skip 走同一段程式,檢查只加在 pass 那一支。
11. **代碼審手冊**:lumos-code-loop 手冊在「派審查席」之前加一步「跑 `lumos lint-new --diff <分岔點>..HEAD`,乾淨才派」(手冊要求凍結前先提交,所以用提交範圍,不用工作樹);不用 `lumos code-loop check`,因為 tier high 在派席之前必然因為還沒有審查留痕而擋,看不出機械那幾道乾不乾淨。審查席的派工材料附機械檢查結果,寫明「機械已查的類別席位不報」。表態時機照手冊既有寫法(派審查員之前做)。

**不做**:不改推送前閘本身的判定(它照舊跑、當最後確認;判定函式多收工作樹終點,但終點是提交時走原路徑、結果一字不變);不改消費專案的檔;不在推送前閘或回合結束鉤子裡呼叫模型;不寫 detekt 自訂規則 jar;批三到批五不在本計劃。

## 裁決紀錄

- **一次性事件的標準寫法(2026-11-05,使用者授權由 AI 裁)**:原計劃寫「事件用 SharedFlow 或 Channel」,Android 官方 UI events 指南把它列為反模式(畫面在背景時事件會遺失),改成「事件化成狀態、畫面處理完回報已處理」;Channel 只留給真的不屬於畫面狀態的內部訊號,且要 BUFFERED、在 repeatOnLifecycle 裡收。依據:developer.android.com 的 UI events 頁。
