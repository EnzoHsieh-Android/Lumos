2. **blocker — S4 沒有定義如何把 testmap 的檔名變成可執行測試**

   引句:「每個變異在**臨時 worktree** 套用 → 測試選擇=對**原始 diff range** 跑一次 `testmap affected` 取聯集」

   問題：`testmap affected` 只輸出測試檔路徑、信心值及來源，不輸出 runner、命令、測試方法或工作目錄。spec 隨後直接說「跑」聯集，卻未定義 Python 測試檔究竟用 pytest、unittest、repo 自有 harness，或如何處理多個測試框架。本 repo 的 `guard kill` 能執行，是因為它明確從 platform config 取得 `run_cmd` 並用 `{method}` 代換；S4 沒有相同合約，因此核心 killed/survived 演算法不可實作。

   證據：`governance/review-reports/驗證層去模型化/r1-snapshot-s4.md:42`；`scripts/lumos:10886`；`scripts/lumos:10933`；`scripts/lumos:4856`

5. **major — 宣稱沿用既有 mutation 分桶，實際輸出模型漏掉 NoCoverage 與 timeout**

   引句:「S4=**把步驟 7 自動化**(取代手動植入,分桶語意沿用),非平行新機制。」

   問題：現行步驟 7 明定 timeout→skipped，活變異再分 `Survived` 與 `NoCoverage`，而 NoCoverage 需以把該行改成 `raise` 再跑來辨識。S4 卻只規定「記殺/活」及「活口清單」，沒有 timeout、skipped、Survived、NoCoverage 的判定流程或輸出欄位。這不是原分桶語意的自動化，而是資訊縮水；尤其測試全綠無法單靠退出碼判斷該行是否被執行。

   證據：`governance/review-reports/驗證層去模型化/r1-snapshot-s4.md:41`；`governance/review-reports/驗證層去模型化/r1-snapshot-s4.md:43`；`skills/lumos-code-loop/SKILL.md:157`

6. **major — testmap 的 stale/fail-open 結果會被誤當成「無測試」**

   引句:「testmap 無邊的檔=如實列「無測試可跑」(這本身就是發現)。」

   問題：`testmap affected` 對 map 缺失、損壞、壞 range、repo 錯誤及未預期例外都 fail-open rc0；map 過期時仍輸出 suggestions/uncovered，只另帶 `stale`。因此「空建議」至少有三種不同含義：真的無邊、map 不可用、git/range 失敗。S4 未要求解析 `stale`、stderr 或 map metadata，也沒有 rebuild/invalid-run 狀態，會把基礎設施失敗錯報成測試覆蓋洞。

   證據：`governance/review-reports/驗證層去模型化/r1-snapshot-s4.md:44`；`scripts/lumos:10789`；`scripts/lumos:10790`；`scripts/lumos:10819`；`scripts/lumos:10850`；`scripts/lumos:10933`

7. **major — 恆 rc0 抹掉「有效觀測」與「根本沒跑成」的差別**

   引句:「輸出:殺率+**活口清單**(哪個變異沒任何測試殺得死=測試網的洞,file:line+變異描述);恆 rc0 **觀測不進閘**」

   問題：觀測不進閘不等於所有基礎設施錯誤都應成功退出。worktree 建立失敗、測試 runner 不存在、baseline 已紅、變異產生非法語法與 timeout 都不能形成有效殺率。既有 `guard kill` 正確區分 survived rc1 與 drifted/abort/error rc2；S4 的「恆 rc0」若沒有結構化 `valid:false/error` 合約，CI 與人都無法區別「0% 殺率」和「0 個變異真正跑完」。

   證據：`governance/review-reports/驗證層去模型化/r1-snapshot-s4.md:43`；`scripts/lumos:4752`；`scripts/lumos:4753`；`scripts/lumos:4840`；`scripts/lumos:4862`

8. **major — cap 抽樣未定義，破壞「機器可重算」主張**

   引句:「變異上限 cap(防大 diff 爆炸,超限抽樣並如實標;`--mutation-budget` 可覆寫)」

   問題：沒有定義預設 cap、候選排序、抽樣演算法、seed、seed 的輸入或輸出欄位。同一 diff 在不同執行中可能抽到不同變異，殺率與活口清單不可重算；若按遍歷順序截斷，又會偏向檔名字典序或 AST 前段。既有 panel 抽查特別採 sha256 決定性公式來保證人人可重算，S4 反而漏掉同等要求。

   證據：`governance/review-reports/驗證層去模型化/r1-snapshot-s4.md:44`；`docs/lumos-toolchain-knowledge/Projects/panel收斂判準改革_計劃.md:71`
