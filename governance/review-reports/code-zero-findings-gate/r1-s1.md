## Finding 1 — blocker

- file:line — `scripts/lumos:9997-9998`(連帶 `10021`「留痕重驗」與 `10090`「PASS 橫幅」兩處既有行,行為被本次改動間接改變)
- 引句:「這輪 0 條發現,沒有東西要處置(空輪即過)」

**失敗場景**:vacuous 分支只要求「這輪每筆記錄都明填 `findings==0`」,完全不要求 `--report`/`--snapshot`。而 ③留痕重驗與④quote-check 兩塊(`if carrier is not None:`,scripts/lumos:10021 起)只在 `carrier` 非 None 時才執行——vacuous 通過時 `carrier` 恆為 `None`,所以這兩塊**整段不會被執行**,不是「驗過且過」,是「根本沒驗」。但最終不分支印出的 PASS 橫幅字面上仍宣稱四項全過:

    ✅ DISPOSAL GATE PASS (... : G3 ∧ 處置全清 ∧ 留痕可重算 ∧ 引句全錨定)

也就是說,一個審查員只要 `canary record none --findings 0 --spec ... --reviewed <當下真檔 sha>`,**完全不附 report/snapshot**,就能讓 disposal 閘印出「留痕可重算 ∧ 引句全錨定」並 rc0 放行——這兩項事實上一次都沒被檢查過。這正是題目點名的「閘讀的是帳,報告內容它驗不了」,但這不是既有天花板的延伸:diff 之前,任何一輪要 PASS 必然要先經過 `carrier` 分支(因為 `carrier is None` 恆 FAIL),而 `carrier` 分支強制要求 report/snapshot 存在、sha256 對得上帳、引句錨定得到快照——也就是說**在此之前,凡是 PASS 就一定留了痕、驗了引句**。這個新分支第一次讓「PASS」和「有留痕證據」脫鉤,是本次改動新開的洞,不是既有天花板。

## Finding 2 — major

- file:line — `scripts/lumos:9997`
- 引句:「int(r["findings"]) == 0 for r in latest):」

**失敗場景**:`.canary-log.jsonl` 由 `json.loads` 逐行讀入(`scripts/lumos:4565` 附近),schema 不受機械保證——手改帳、舊版寫入路徑、merge 衝突殘留都可能讓 `findings` 欄位不是乾淨整數。這一行是全檔唯一一處對 ledger 讀出的 `findings` 值做無防護 `int()` 轉型;同一函式裡其它風險讀取都遵守「壞行 fail-closed、不 traceback」慣例(`n_badlines`/`bad_linenos` 整段、`_hash_chain_check` 外面包 `except OSError`、③留痕重驗對 `_sha256_file` 包 `except OSError`、④quote-check 對讀檔包 `except (OSError, UnicodeDecodeError)`)。這一行沒有比照辦理,壞資料會直接讓整支 CLI 以 unhandled exception 崩潰、印出完整 traceback。
