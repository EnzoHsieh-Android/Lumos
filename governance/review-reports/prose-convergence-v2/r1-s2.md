### 3. d3 治理帳 rewrite 值 —— **blocking:是(blocker,「動一行碼」誠實度)+ blocking:是(major,「雙開即停」可數性)**

**(a)「動一行碼」對 gov --stats 不誠實**

文件原句(L36):「帳面收尾枚舉加 `rewrite` 值(**動一行碼,d1 的『不動』明示收窄至此**)」

查證:`_render_gov_stats`(scripts/lumos:3067-3068)寫死只認兩種 kind:
```
conv = sum(1 for k in by.values() if "converged" in k)
capped = sum(1 for k in by.values() if "cap-reached" in k and "converged" not in k)
```
`len(by)` 是分母(有記帳的所有 design-loop 編號數),`conv+capped` 是分子。若某編號的唯一 design-loop 事件是 `kind="rewrite"`,它會計進分母、卻兩個分子桶都不落,`conv+capped < len(by)` 且畫面不解釋差額——「人裁放行率」的百分比會悄悄失真,且 `_loop_gov_mark` 的 docstring(scripts/lumos:422-423)「kind=converged(閘過了)| cap-reached(跑滿上限沒過)」本身也漏列第三值,文件與碼同時要跟。這不是「動一行碼」,至少要動 `_loop_gov_mark` 呼叫點+`_render_gov_stats` 分桶邏輯+docstring 三處。

**(b)「連續兩次判重寫→強制攤人,不得三開」查無可數的帳**

文件原句(L36):「重寫不重置攤人義務:連續兩次判重寫→強制攤人,不得三開(防無限燒)」

查證:全庫搜尋 `supersede|prev_loop|predecessor|rewrite_of|parent_loop|lineage` 均無 loop-id 層級的鏈接欄位(僅有筆記層 `status: superseded`,與 loop_id 無關)。每次重寫依「開新編號」規則換一個全新字串(如本案 `prose-convergence` → `prose-convergence-v2`),governance-log 裡沒有任何機制把 v1、v2、v3 的 `rewrite` 事件串成同一條血緣——要數「連續兩次」得先知道哪些編號屬於同一案,而這一步無碼可查。「不得三開」目前沒有任何 gate 會擋第三次開新編號。本案自己的實務隱患段(L48-55)也沒有把這條列進「回頭看的條件」清單,等於把一條沒有機械守衛的規則當成已解決的規則寫死。

### 4. d4 兩行格式 vs 中斷恢復對帳(reference.md:160)+ fold-check 鏡像段 —— **blocking:是(major)**

文件原句(L37):「瘦身=該段每輪固定兩行:『rN(日期,席數):N 條/blocking N/一句結論』+指標到 `governance/review-reports/<loop>/` 的席報告」

reference.md:160 原句:「**中斷恢復(第二帳)**:log 無該輪 record 但 spec 審計修正紀錄有該輪條目 → **人工補 record 再繼續**」

逐欄對帳結果:
- `rN`(round-id)↔ canary-log `round` 欄:對得上。
- `日期`↔ `ts` 前綴:對得上(粗略)。
- `席數`↔ 同 round 有幾筆記錄(panel 一席一筆):對得上,但要靠計數,不是單一欄位。

### 5. [S3] blocking 綁定 vs disposal「major 可 accepted」—— **blocking:是(major)**

文件原句(L43):「**綁定規則:blocking:否 ↔ severity 必為 minor;blocking:是 ↔ major/blocker——兩欄矛盾=報告退回該席重判**」

查證:`cmd_canary` 的放行檢查(scripts/lumos:3496-3498)只硬擋一種情況:
```
if severity == "blocker" and AC:
    print("擋下:這輪有 blocker 等級的問題,blocker 只能折掉修正、不能放行...")
```
`major` 完全沒有對應限制——一條 major 級發現**可以**被放進 `accepted_set`(放行,不折)。但 M2 risk-cluster 三態帳(`CLUSTER_STATES = ("resolved", "accepted-minor", "disputed-major")`,scripts/lumos:3314)卻連「accepted-major」這個狀態名都不存在,白名單檢查(3334-3341)直接擋掉——major 若不 resolved 就只能是 disputed-major(還在爭議),不能單純「接受」。

也就是說,repo 裡本來就有**兩套對「major+接受」意見不一的機制**並存:逐條處置帳(`--accepted-set`)容許「major 但接受」,cluster 三態帳結構上不容許「major 但接受」(只能 disputed)。S3 的新綁定規則(major 一律 blocking:是)完全沒處理這個既有分歧:一條被放行(accepted)的 major finding,在新詞彙下到底寫 `blocking: 是`(符合 severity 綁定,但語意上「blocking」通常意味著擋著不能過,跟「已放行」矛盾)還是 `blocking: 否`(符合放行的實際處置,但違反 L43 那條硬性綁定,會觸發文件自己說的「退回重判」)?文件沒給出裁定,兩種寫法都會撞上自己訂的規則。

## 三群彙總

| 群 | 條目 | blocking | 判準句一行 |
|---|---|---|---|
| **blocker** | ①d1 升級條件無欄位可查 | 是 | 照字面實作,任何人想機械判 B 軌升級都查無此欄,條件形同虛設 |
| **blocker** | ③a rewrite 值「動一行碼」 | 是 | 照字面只動一行,`gov --stats` 的 conv/capped 分桶會悄悄少算,數字做錯 |
| **blocker** | ⑤ blocking 綁定 vs accepted-major | 是 | major 被放行時兩欄矛盾無解,退回重判規則會自己打自己 |
| **major** | ③b「連續兩次判重寫」無帳可數 | 是 | 「不得三開」無守衛、無血緣欄,照字面執行時系統擋不住第三次 |
| **major** | ④ 兩行格式 blocking N 無對帳欄+細節外移 fold-check 讀不到 | 是 | 中斷恢復對帳驗不了 blocking 數;鏡像核對實質內容變少且無人承認 |

## 最嚴重 blocking 是否存在

**存在**,且不只一條——①③a⑤三條都達 blocker 級,彼此獨立、成因不同(①③a 是「帳上沒有這個欄位」的同源病根之兩種表現;⑤是既有兩套處置機制本身互相打架,新規則沒處理)。若要挑單一最嚴重者:**①(d1 升級條件無欄位可查)**——因為它是全篇雙軌解的安全閥,B 軌「暫緩但留升級路徑」這個核心讓步能不能兌現,全繫於這條件能不能被查——查不了,B 軌實質上被永久暫緩而文件渾然不覺,這正是 CLAUDE.md「承認風險要附回頭看的條件」那條鐵則要防的情況,而本版恰好把它包裝成「機械可判」四個字端出來,可信度落差最大。
