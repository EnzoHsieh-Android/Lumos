# 合併進主線認合進來那側的留痕_計劃

白話:推送前與 CI 都會跑一道「高風險改動要有審查通過紀錄」的檢查。紀錄記在哪個分支,檢查就只去那個分支找。合併請求在自己的分支審完、記好紀錄,按下合併後,主線的 CI 拿主線的名字去找——找不到(或只找到一筆舊的),就判紅。#28 就是這樣:分支上審過了,主線卻紅。這次讓檢查遇到「合併提交」時,也去看合進來的那一側有沒有有效紀錄;條件是:主線那側在推送前就已經是遠端的現況(檢查過了)、合併本身沒夾帶手改、合進來那側審過。

依據:2026-10-07 主線 CI 紅燈(合併 #28 那次,CI 上的代碼審檢查擋「留痕過時:記錄 sha eeaa6162 之後動了代碼」——eeaa6162 是 10-05 一筆記在主線上的舊紀錄),消費專案 rtb 那邊的會談回報根因、Enzo 指派。實證:#28 的通過紀錄記在 cap-retro 分支的 afb7115c;它到合進來那側頂端 5dbb85e0 之間只動了治理帳與錨點基準兩支簿記檔,既有 `_codeloop_record_valid` 判有效;同分支更早一筆 866f3213 判無效(之後動過程式)。#28 的合併提交 b0b48b7b:第一個母 d0b24391 就是那次 CI 的推送範圍起點;「跟第二個母不同」與「跟第一個母不同」的檔案交集是空的(前三次合併 d0b24391、b4637da0、c150ac43 也都是空的)。

名詞:簿記檔=帳本、留痕這類不算程式的檔(清單見 `_BOOKKEEPING_FILES`/`_BOOKKEEPING_DIRS`,判法沿用 `_codeloop_record_valid_ex` 那套,含「簿記資料夾裡放程式檔照算程式」);留痕=`lumos code-loop pass|skip` 寫進治理帳的那筆紀錄;表態=效能檢核題的回答紀錄;推送範圍起點=推送前檢查拿到的遠端舊值(CI 是 push 事件的前一版,推送前掛鉤是遠端那個分支原本的提交)。

PRIOR-ART: GitHub 自己的做法是「合併請求上的檢查綠了才准合」,合併後不重審;bors / merge queue 的「不是火箭科學規則」是「主線只收測過的合併結果」——兩者都把信任放在合併進來那一側已驗過的內容,外加「合併結果就是那份內容」。本案照同一個想法,證明「合併結果就是兩邊各自的內容」改用逐檔比對(合併後每支非簿記檔等於其中一個母),不依賴 git 版本、也不受帳本兩邊都追加的衝突影響;留痕有效性沿用既有 `_codeloop_record_valid_ex`(同版本,或祖先且之後只動簿記檔;帶剩餘時間預算、有「判不了」)。
RETIRE-IF: 改成合併請求只准 squash 合併(主線上不再出現合併提交),或推送檢查改成只在合併請求上跑、主線不再跑代碼審檢查。

## 範圍

- 做:一支共用函式「認合併提交的合進來那一側」,輸入目標版本、推送範圍起點、時間期限,回 (第二個母, None) 或 (None, 原因)。三個條件都成立才回第二個母:
  1. 目標版本恰好兩個母。
  2. 第一個母等於推送範圍起點(起點是空樹、全零或算不出來 → 不認)。這條擋「未審分支擺第一個母、主線頂端擺第二個母」的假合併,也擋本機 `git pull` 合出來的合併、以及功能分支先在本機多了沒推過的提交再合主線(這兩種的第一個母都是本機沒推過的提交)。功能分支在遠端現況上直接合主線再推(第一個母就是起點)會被認:這次推送新帶進來的只有主線那側的內容,跟一般推送只看這次範圍的做法一致。
  3. `git diff --name-only 第二個母 目標` 與 `git diff --name-only 第一個母 目標` 的交集裡沒有非簿記檔——每支非簿記檔的合併結果要嘛等於主線那側、要嘛等於合進來那側;兩邊都不一樣就是合併時動了手,不認。
  淺 clone(`_git_is_shallow`)→ 原因寫「歷史不全、判不了」,不講成沒有紀錄。git 出錯或逾時 → 不認並附原因。
- 做:新寫一支讀帳函式(共用 `_ledger_lines` 與既有「只有 kind 是 passed/skipped 才算留痕」的篩選,抽成一支給既有讀帳與新讀帳共用,不另立第二套):以第二個母往回走第一母鏈最多 20 個提交當索引(一次 `git rev-list --first-parent -n 20`),在治理帳裡找 `gate=code-loop`、kind 是 passed/skipped、`head_sha` 落在索引裡的紀錄(不看分支名),由近到遠逐筆用 `_codeloop_record_valid_ex(紀錄, 第二個母, 剩餘時間)` 驗,第一筆有效的就是。同一個 head_sha 在 pass 之後又有 blocked 事件不影響(blocked 不是留痕,本來就不讀)。
- 做:審查留痕那關(高風險):目標分支找不到有效紀錄、在 env 跳過判斷之前,呼叫上面兩支;認到就放行,理由寫「合併提交:合進來那一側的留痕(狀態@sha)」。認不到 → 照舊擋,原因後面補一句為什麼沒認(哪個條件不成立)。
- 做:表態那關同一條規則,但讀的是 kind=dispositions 的紀錄(同一支讀帳函式帶 kind 參數),有效性對第二個母驗;適用題照舊用目標的推送範圍算——合進來那側的表態少答了題,照舊擋(只會多擋、不會多放)。
- 做:推送範圍起點由呼叫端傳進判定函式(CI 與推送前掛鉤都已經傳範圍 `起點..目標`,從範圍取起點)。
- 不做:章魚合併(三個以上的母)、squash 合併(主線上是一般提交,照舊)、合併提交本身有手改的(照舊要在主線補審)。
- 不做:改 CI 腳本或推送掛鉤的範圍算法;治理帳簽章(帳本可手寫偽造是既有天花板,不是本案新增)。

## 實務隱患

- **信任範圍擴大**:原本只信目標分支名下的紀錄,本案改成信「head_sha 落在合進來那側最近 20 個提交裡」的任何分支紀錄;帳本是沒簽章的純文字,手寫一筆就能偽造——這在現行規則下寫成 branch=main 也成立,不是新洞,但放寬後被利用的路多一條,所以三個條件缺一不認。
- **舊紀錄誤認**:索引只取合進來那側往回 20 個提交,再加「之後只動簿記檔」的有效性判斷,主線歷史裡舊合併請求的 pass 之後都動過程式,不會被認——測試要涵蓋。
- **效能與時間**:兩次 `git diff --name-only`、一次 `git rev-list`、最多 20 筆有效性判斷(每筆祖先判斷加一次差異);整段用表態閘既有的總預算 `_DISP_BUDGET`,每次 git 用剩餘時間當上限;超過就停、照舊擋並講「時間不夠判不完」。只在「目標分支找不到有效紀錄而且目標是兩個母的合併提交」時才跑。
- **歷史不全**:CI 三處 checkout 都是完整歷史;淺 clone 時明講判不了。
- **查過沒有繞法的**(設計審 r1 繞過席):簿記資料夾裡夾帶程式(既有判法把可執行、程式副檔名、`#!` 開頭、控制字元路徑都算程式)、合併提交裡藏改動(那支檔兩邊都不一樣,不認)、三個以上的母(不認)、GitHub 實際合併結果跟兩個母不同(只會多擋)。
- 已排除:金流:只改推送檢查的判定,不碰任何金流
- 已排除:對外送出:不連網、不送任何東西出去
- 已排除:不可逆:只改判定、不寫資料,退回提交即恢復
- 守衛面:這是守衛的放寬。三個條件各有一格測試證明少一個就照舊擋。

## 驗收條款

- [S1] 當目標是兩個母的合併提交、第一個母等於推送範圍起點、非簿記檔都等於其中一個母、合進來那側有有效 pass 或 skip(記在別的分支名下)時,高風險的推送檢查 應 放行並寫明認的是合進來那側;第一個母不是推送範圍起點(含未審分支擺第一個母的假合併、本機多了沒推過的提交再合主線)、有非簿記檔兩邊都不一樣、三個母、合進來那側沒有紀錄或紀錄之後又改過程式、只有舊合併請求的紀錄 應 照舊擋並講是哪個條件不成立;兩邊都追加帳本(帳本衝突)應 不影響判定 [test:t_codeloop_check_merge_side_pass]
- [S2] 當目標是上述合併提交、有適用的效能檢核題、合進來那側有有效表態時,表態那關 應 放行;合進來那側沒有表態、或第一個母不是推送範圍起點 應 照舊擋 [test:t_codeloop_check_merge_side_dispositions]

## 回退

退回本案的提交即可:只改推送檢查的判定,不寫資料、不改帳本格式。

## 天花板

1. 只認兩個母、而且主線那側就是推送範圍起點的合併;合併時解過非簿記檔衝突的,還是要在主線補審或補記。
2. 主線 #28 那次的紅燈不會變綠(那次 CI 跑的是舊程式);本案合進主線那次的 CI 起才用新判定。
3. 合進來那側的表態少答了推送範圍新觸發的題時照舊擋,要在主線補表態。
