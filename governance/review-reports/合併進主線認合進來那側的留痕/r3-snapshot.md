# 合併進主線認合進來那側的留痕_計劃

白話:推送前與 CI 都會跑一道「高風險改動要有審查通過紀錄」的檢查。紀錄記在哪個分支,檢查就只去那個分支找。合併請求在自己的分支審完、記好紀錄,按下合併後,主線的 CI 拿主線的名字去找——找不到(或只找到一筆舊的),就判紅。#28 就是這樣:分支上審過了,主線卻紅。這次讓檢查遇到「合併提交」時,也去看合進來的那一側有沒有有效紀錄;條件是:主線那側在推送前就已經是遠端的現況、合進來那側合併前已經跟上主線而且合併結果就是它的內容、合進來那側審過。

依據:2026-10-07 主線 CI 紅燈(合併 #28 那次,CI 上的代碼審檢查擋「留痕過時:記錄 sha eeaa6162 之後動了代碼」——eeaa6162 是 10-05 一筆記在主線上的舊紀錄),消費專案 rtb 那邊的會談回報根因、Enzo 指派。實證:#28 的通過紀錄記在 cap-retro 分支的 afb7115c;它到合進來那側頂端 5dbb85e0 之間只動了治理帳與錨點基準兩支簿記檔,既有 `_codeloop_record_valid` 判有效;同分支更早一筆 866f3213 判無效(之後動過程式)。#28 的合併提交 b0b48b7b:第一個母 d0b24391 就是那次 CI 的推送範圍起點;第一個母是第二個母的祖先、`git diff --no-renames --name-only 5dbb85e0 b0b48b7b` 是空的——最近五次合併(b0b48b7b、d0b24391、b4637da0、c150ac43、c4f2b0cf)全部是這個形狀(分支合併前先跟上主線,合併結果跟分支頂端逐位元相同),所以嚴格條件不會擋到現行流程。

名詞:簿記檔=帳本、留痕這類不算程式的檔(清單見 `_BOOKKEEPING_FILES`/`_BOOKKEEPING_DIRS`,判法沿用 `_codeloop_record_valid_ex` 那套,含「簿記資料夾裡放程式檔照算程式」);留痕=`lumos code-loop pass|skip` 寫進治理帳的那筆紀錄;表態=效能檢核題的回答紀錄;推送範圍原始起點=呼叫端傳進來的範圍起點,在判定函式把全零或本機找不到的起點改寫成跟主線的分岔點之前的那個值(CI 是 push 事件的前一版,推送前掛鉤是遠端那個分支原本的提交);全零、空樹或找不到 → 不認。

PRIOR-ART: GitHub 自己的做法是「合併請求上的檢查綠了才准合」,合併後不重審;bors / merge queue 的「不是火箭科學規則」是「主線只收測過的合併結果」——兩者都把信任放在合併進來那一側已驗過的內容,外加「合併結果就是那份內容」。本案照同一個想法、取最嚴的一種:要求合進來那側已經包含主線那側、合併結果除簿記檔外就是合進來那側的內容(GitHub 的「分支要先跟上主線才准合」同一個意思),不依賴 git 版本、不受帳本衝突影響,也沒有「挑哪一側的版本」可鑽;留痕有效性沿用既有 `_codeloop_record_valid_ex`(同版本,或祖先且之後只動簿記檔;帶剩餘時間預算、有「判不了」)。
RETIRE-IF: 改成合併請求只准 squash 合併(主線上不再出現合併提交),或推送檢查改成只在合併請求上跑、主線不再跑代碼審檢查。

## 範圍

- 做:一支共用函式「認合併提交的合進來那一側」,輸入目標版本、推送範圍原始起點與終點、時間期限,回 (第二個母, None) 或 (None, 原因)。條件全部成立才回第二個母:
  1. 範圍終點等於目標版本,目標版本恰好兩個母。
  2. 第一個母等於推送範圍原始起點。這條擋「未審分支擺第一個母、主線頂端擺第二個母」的假合併,也擋本機 `git pull` 合出來的合併。
  3. 第一個母是第二個母的祖先(合進來那側合併前已經跟上主線)。
  4. `git diff --no-renames --name-only 第二個母 目標` 裡沒有非簿記檔(合併結果就是合進來那側的內容;關掉改名偵測,免得刪檔被配成改名藏住)。簿記檔判法沿用 `_codeloop_record_valid_ex` 那套(含簿記資料夾裡的程式檔照算程式)。
  因為 3 與 4,合併結果裡的每一行程式都在合進來那側的歷史裡,也就是它的審查範圍內;要退掉主線的東西只能在分支上另做提交,那個提交會被審。淺 clone(`_git_is_shallow`)→ 原因寫「歷史不全、判不了」。git 出錯或逾時 → 不認並附原因。
- 做:新寫一支讀帳函式(共用 `_ledger_lines` 與既有「只有 kind 是 passed/skipped 才算留痕」的篩選,抽成一支給既有讀帳與新讀帳共用,不另立第二套):帳本內容讀第二個母那棵樹裡的版本(`git show 第二個母:docs/.governance-log.jsonl`)——合併提交本身新增的帳本行不算數,擋「在合併提交裡手寫一筆假紀錄」;以第二個母往回走第一母鏈最多 20 個提交當索引(一次 `git rev-list --first-parent -n 20`),找 `gate=code-loop`、kind 是 passed/skipped、`head_sha` 落在索引裡的紀錄(不看分支名),由近到遠逐筆用 `_codeloop_record_valid_ex(紀錄, 第二個母, 剩餘時間)` 驗,第一筆有效的就是;判不了的不算有效。同一個 head_sha 在 pass 之後又有 blocked 事件不影響(blocked 不是留痕,本來就不讀)。
- 做:審查留痕那關(高風險):目標分支沒有紀錄、或紀錄無效(兩條路都接)、在 env 跳過判斷之前,呼叫上面兩支;認到就放行,理由寫「合併提交:合進來那一側的留痕(狀態@sha)」。認不到 → 照舊擋,原因後面補一句為什麼沒認(哪個條件不成立)。
- 做:表態那關同一條規則,接在「沒有表態紀錄」與「表態紀錄過期」兩個擋下點(主線上有舊表態時走的是過期那個),讀的是 kind=dispositions 的紀錄(同一支讀帳函式帶 kind 參數),有效性對第二個母驗;適用題照舊用目標的推送範圍算——合進來那側的表態少答了題,照舊擋(只會多擋、不會多放)。
- 做:推送範圍原始起點由判定函式在改寫之前先存下來(CI 與推送前掛鉤都已經傳範圍 `起點..目標`)。
- 做:時間:整段用 `_DISP_BUDGET` 起算一個自己的期限,每次 git 用剩餘時間當上限;超過期限 → 不認、照舊擋並講「時間不夠判不完」(跟表態閘「超時放行」相反:這是放寬,判不完就不放)。
- 不做:章魚合併(三個以上的母)、squash 合併(主線上是一般提交,照舊)、合併提交本身有手改的、合進來那側沒跟上主線的(照舊擋,先在分支合主線、重記留痕再合)。
- 不做:改 CI 腳本或推送掛鉤的範圍算法;治理帳簽章(帳本可手寫偽造是既有天花板,不是本案新增)。

## 實務隱患

- **信任範圍擴大**:原本只信目標分支名下的紀錄,本案改成信「head_sha 落在合進來那側最近 20 個提交裡」的任何分支紀錄,而且帳本讀合進來那側樹裡的版本(合併提交本身加的行不算);帳本是沒簽章的純文字,在分支上手寫一筆仍能偽造——這在現行規則下寫成 branch=main 也成立,不是新洞,但放寬後被利用的路多一條,所以條件缺一不認。
- **舊紀錄誤認**:索引只取合進來那側往回 20 個提交,再加「之後只動簿記檔」的有效性判斷,主線歷史裡舊合併請求的 pass 之後都動過程式,不會被認——測試要涵蓋。
- **效能與時間**:一次祖先判斷、一次 `git diff --no-renames --name-only`、一次 `git show` 讀帳、一次 `git rev-list`、最多 20 筆有效性判斷(每筆祖先判斷加一次差異);期限見範圍,超過就停、照舊擋並講「時間不夠判不完」。只在「目標分支找不到有效紀錄而且目標是兩個母的合併提交」時才跑。
- **歷史不全**:CI 三處 checkout 都是完整歷史;淺 clone 時明講判不了。
- **查過沒有繞法的**(設計審 r1 繞過席):簿記資料夾裡夾帶程式(既有判法把可執行、程式副檔名、`#!` 開頭、控制字元路徑都算程式)、合併提交裡藏改動或退掉主線的東西(合併結果跟合進來那側不同,不認)、三個以上的母(不認)、GitHub 實際合併結果跟兩個母不同(只會多擋)。設計審 r2 繞過席另查過:先推只動簿記檔的提交讓起點前進、分兩次推、第二個母本身是合併提交、符號連結、模式位元、子模組、窗口外的舊紀錄、force push 的起點。
- 已排除:金流:只改推送檢查的判定,不碰任何金流
- 已排除:對外送出:不連網、不送任何東西出去
- 已排除:不可逆:只改判定、不寫資料,退回提交即恢復
- 守衛面:這是守衛的放寬。每個條件各有一格測試證明少一個就照舊擋。

## 驗收條款

- [S1] 當目標是兩個母的合併提交、第一個母等於推送範圍原始起點、合進來那側已包含主線那側、合併結果除簿記檔外跟合進來那側相同、合進來那側帳本裡有對它有效的 pass 或 skip(記在別的分支名下)時,高風險的推送檢查 應 放行並寫明認的是合進來那側;目標分支已有一筆過期紀錄時 應 一樣放行;第一個母不是原始起點(含未審分支擺第一個母的假合併、起點全零)、合進來那側沒跟上主線、合併時退掉主線的修補、合併時刪檔(改名偵測不得藏住)、三個母、合進來那側沒有紀錄或紀錄之後又改過程式、只有舊合併請求的紀錄、紀錄只出現在合併提交新加的帳本行 應 照舊擋並講是哪個條件不成立 [test:t_codeloop_check_merge_side_pass]
- [S2] 當目標是上述合併提交、有適用的效能檢核題、合進來那側有有效表態時,表態那關 應 放行(目標分支沒有表態、或有一筆過期表態都一樣);合進來那側沒有表態、或第一個母不是原始起點 應 照舊擋 [test:t_codeloop_check_merge_side_dispositions]

## 回退

退回本案的提交即可:只改推送檢查的判定,不寫資料、不改帳本格式。

## 天花板

1. 只認兩個母、主線那側就是推送範圍原始起點、而且合進來那側已跟上主線的合併;沒跟上的(分支在主線前進後沒再合主線)照舊擋——在分支合主線、重記留痕再合。
4. 合進來那側在 pass 之後又合過主線(而且帶進程式),那筆 pass 對頂端判無效,照舊擋——要在合主線之後重記。
2. 主線 #28 那次的紅燈不會變綠(那次 CI 跑的是舊程式);本案合進主線那次的 CI 起才用新判定。
3. 合進來那側的表態少答了推送範圍新觸發的題時照舊擋,要在主線補表態。
