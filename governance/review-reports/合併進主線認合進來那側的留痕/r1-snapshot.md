# 合併進主線認合進來那側的留痕_計劃

白話:推送前與 CI 都會跑一道「高風險改動要有審查通過紀錄」的檢查。紀錄記在哪個分支,檢查就只去那個分支找。合併請求在自己的分支審完、記好紀錄,按下合併後,主線的 CI 拿主線的名字去找——找不到(或只找到一筆舊的),就判紅。#28 就是這樣:分支上審過了,主線卻紅。這次讓檢查遇到「合併提交」時,也去看合進來的那一側有沒有有效紀錄;條件是合併本身沒夾帶手改(合併後的檔案等於兩邊自動合併的結果)。

依據:2026-10-07 主線 CI 紅燈(合併 #28 那次,CI 上的代碼審檢查擋「留痕過時:記錄 sha eeaa6162 之後動了代碼」——eeaa6162 是 10-05 一筆記在主線上的舊紀錄),消費專案 rtb 那邊的會談回報根因、Enzo 指派。實證:#28 的通過紀錄記在 cap-retro 分支的 afb7115c;它到合進來那側頂端 5dbb85e0 之間只動了治理帳與錨點基準兩支簿記檔,既有 `_codeloop_record_valid` 判有效;同分支更早一筆 866f3213 判無效(之後動過程式)。#28 的合併提交 b0b48b7b 的樹等於 `git merge-tree --write-tree` 兩個母的結果(rc0)。

名詞:簿記檔=帳本、留痕這類不算程式的檔(清單見 `_BOOKKEEPING_FILES`/`_BOOKKEEPING_DIRS`);留痕=`lumos code-loop pass|skip` 寫進治理帳的那筆紀錄;表態=效能檢核題的回答紀錄。

PRIOR-ART: GitHub 自己的做法是「合併請求上的檢查綠了才准合」,合併後不重審;bors / merge queue 的「不是火箭科學規則」是「主線只收測過的合併結果」——兩者都把信任放在合併進來那一側已驗過的內容,外加「合併結果就是那份內容」。本案照同一個想法,用 git 自己的 `git merge-tree --write-tree <母1> <母2>` 重算自動合併的樹、跟合併提交的樹比,證明合併沒夾帶手改;留痕有效性沿用既有 `_codeloop_record_valid`(同版本,或祖先且之後只動簿記檔)。
RETIRE-IF: 改成合併請求只准 squash 合併(主線上不再出現合併提交),或推送檢查改成只在合併請求上跑、主線不再跑代碼審檢查。

## 範圍

- 做:一支共用函式「合併提交的合進來那一側」:目標版本是恰好兩個母的合併提交,而且 `git merge-tree --write-tree 母1 母2` 回傳碼是 0(沒衝突;回 1 時第一行也是一棵樹、但含衝突標記,不能拿來比)、第一行的樹等於合併提交的樹 → 回第二個母(合進來那一側的頂端);其他(不是合併、三個以上的母、回傳碼 1(有衝突)、其他回傳碼(git 太舊不認得 --write-tree、用法錯)、樹不相等(合併時手改過)、git 出錯或逾時)→ 回 None 並附一句原因。
- 做:審查留痕那關(高風險):用目標分支找不到有效紀錄時,若目標是上面那種合併提交,改在治理帳裡找「任何分支」的 pass/skip 紀錄——新寫一支讀帳函式,不改既有 `_codeloop_read`/`_codeloop_read_from_ledger`(它們只讀指定分支,改了會動到一般推送的判定)——挑對第二個母有效的那筆(`_codeloop_record_valid(紀錄, 第二個母)`),依帳本行序由新到舊、最多看最近 50 筆;找到就放行,理由寫「合併提交:合進來那一側的留痕(狀態@sha)」。
- 做:表態那關同一條規則:目標分支的表態紀錄沒有或過期時,同樣去找對第二個母有效的表態紀錄。
- 做:擋下時的訊息(推送檢查的判定函式回的原因,推送前與 CI 印的都是它),目標是合併提交卻認不到時,補一句為什麼(合併時有手改/衝突、合進來那側沒有有效紀錄、git 不支援)。
- 不做:章魚合併(三個以上的母)、squash 合併(主線上是一般提交,照舊)、合併提交本身有手改的(照舊要在主線補審)。
- 不做:改 CI 腳本或推送掛鉤的範圍算法。

## 實務隱患

- **信任誰的紀錄**:合進來那側的紀錄寫在同一份治理帳裡(合併請求本來就把帳本提交帶進主線),跟現在信任目標分支紀錄的程度一樣;沒有新的外部輸入。
- **舊紀錄誤認**:主線歷史裡每個舊合併請求的 pass 都是第二個母的祖先;有效性判斷要求「之後只動簿記檔」,舊的那些之後動過程式,不會被認——測試要涵蓋。
- **git 版本**:`merge-tree --write-tree` 要 git 2.38 以上;本機 2.39、CI 的 ubuntu 映像較新。不支援時回 None、照舊擋,訊息講原因。
- **效能**:多兩次 git(merge-tree、取樹)加最多 50 筆紀錄的有效性判斷(每筆是祖先判斷加一次差異,最多約 100 次 git,每次照既有的單次逾時);整段給一個總預算(照表態閘既有的時間預算),超過就停、照舊擋並講原因。只在「目標分支找不到有效紀錄而且目標是合併提交」時才跑。
- 已排除:金流:只改推送檢查的判定,不碰任何金流
- 已排除:對外送出:不連網、不送任何東西出去
- 已排除:不可逆:只改判定、不寫資料,退回提交即恢復
- 守衛面:這是守衛的放寬。放寬只在「合併沒夾帶手改、而且合進來那側審過」時成立,兩個條件各有一格測試證明少一個就照舊擋(同一支測試的不同格)。

## 驗收條款

- [S1] 當目標是乾淨的合併提交、合進來那側頂端有有效 pass、目標分支沒有對應紀錄時,高風險的推送檢查 應 放行並寫明認的是合進來那側;合併時手改過(樹不等於自動合併)、有衝突、三個母 應 照舊擋並講原因;合進來那側沒有紀錄、或紀錄之後又改過程式 應 照舊擋;舊合併請求的紀錄(之後動過程式)應 不被認 [test:t_codeloop_check_merge_side_pass]
- [S2] 當目標是乾淨的合併提交、有適用的效能檢核題、合進來那側有有效表態時,表態那關 應 放行;沒有 應 照舊擋 [test:t_codeloop_check_merge_side_dispositions]

## 回退

退回本案的提交即可:只改推送檢查的判定,不寫資料、不改帳本格式。
