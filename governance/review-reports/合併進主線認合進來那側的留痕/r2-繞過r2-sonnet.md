## F1 條件 3 只比「等於哪個母」,不比「合併有沒有回退主線」:取舊版即可把已審的主線修補整支退掉
severity: major
blocking: 是 — 未經審查的行為變更(退掉安全修補、關掉守衛)進主線且判放行,屬守衛被繞過

誰:有推送權的開發者,或被注入指令的 AI agent。
從哪:從主線舊點拉分支 S,只做一個小改動並讓它過審留痕(正當的 pass)。主線之後多了一筆安全修補或守衛(例如改 `src/guard.py`)。
做什麼:合併時對每支檔逐檔挑一邊,例如 `git merge --no-commit S; git checkout S -- src/guard.py; git commit`。再用 `git merge -s theirs` 風格的取整棵樹也一樣。
結果:合併結果的 `src/guard.py` 等於 S 的舊版,條件 3 判通過。已審的主線修補被整支退掉,沒有任何人審過這個「退回」。若 S 分岔點早於本守衛上線,取 S 的 `scripts/lumos` 與 `.github/workflows/ci.yml` 就能把守衛本身(包含這條放寬)從主線拿掉,且是帶著「合進來那側有留痕」的放行理由。條件 1(兩個母)與條件 2(第一個母=起點)照樣成立。

實測(臨時 repo):
```
git diff --name-only <S> <M>        -> (空)
git diff --name-only <P1> <M>       -> src/app.py, src/guard.py
交集                                 -> (空)
git diff <P1> <M> -- src/guard.py   -> -guard line 7 SECURITY FIX / +guard line 7
```
spec 的交集判法放行,但 M 相對推送範圍起點 P1 把 SECURITY FIX 那行拿掉了。

引句:「每支非簿記檔的合併結果要嘛等於主線那側、要嘛等於合進來那側;兩邊都不一樣就是合併時動了手,不認。」
引句:「主線那側在推送前已經是遠端現況、檢查過了」

為什麼該擋:留痕只證明 S 相對它自己分岔點的改動被審過;它沒審「主線那側的內容被 S 的舊版蓋回去」。檢查的是推送範圍起點..目標,這個範圍裡出現的正是這個回退。
建議:除了逐檔等於一個母,還要求對每支非簿記檔,「合併結果 ≠ 第一個母」的檔必須等於 S 且該檔在 S 相對 merge-base 有改動(或兩邊 merge-base 版本相同才可取另一邊);等價做法是要求「第一個母→目標」的 diff 的每支非簿記檔,內容都等於 S 對 merge-base 的改動結果(即 git merge-tree 的結果),spec 已因版本與帳本衝突否決 merge-tree,至少要補 merge-base 條件。

## F2 條件 3 用 `git diff --name-only`(沒寫 `--no-renames`):改名偵測讓手動刪檔從兩份清單同時消失
severity: major
blocking: 是 — 條件 3 的「兩邊都不一樣」偵測對刪除可被繞過,合併裡藏程式檔刪除/改動

誰:惡意開發者或被注入的 AI。
從哪:兩個母都有程式檔 F.py 且內容各自不同;主線(P1)另外新增 G.py(內容近似 S 版的 F),S 另外新增 Gp.py(內容近似 P1 版的 F)。
做什麼:合併提交時 `git rm -f F.py`,其他取兩邊現成的檔。F.py 在合併結果裡被刪,既不等於 S 也不等於 P1。
結果:`git diff --name-only` 預設開改名偵測,刪掉的 F.py 在兩個 diff 都被配成「改名來源」,只列目的路徑(只列新路徑)。實測:
```
git diff --name-only <S> <M>          -> G.py
git diff --name-only <P1> <M>         -> Gp.py
交集                                   -> (空)   → 條件 3 通過
git diff --no-renames --name-only 兩份取交集 -> F.py   → 加 --no-renames 就抓得到
```
F.py 是程式檔,被人工刪掉而沒人審,放行。同樣手法可以讓被刪的守衛檔、測試檔消失。

引句:「的交集裡沒有非簿記檔——每支非簿記檔的合併結果要嘛等於主線那側、要嘛等於合進來那側」

對照:既有留痕有效性就因為這個原因加了 `--no-renames`,見 file: `scripts/lumos:46574` 附近(`_codeloop_record_valid_ex` 的 `git diff --no-ext-diff --raw --no-renames -z`,註解寫「改名偵測只列新路徑,把程式檔改名搬進簿記資料夾…就看不到程式檔被刪」);同檔還有不少 `--no-renames --name-only -z` 先例,如 `scripts/lumos:12943`。spec 沒把這個旗標釘進條款,實作者照字面寫就中。
建議:spec 寫死 `--no-renames -z` 與路徑逐字比對,並加一格「改名配對藏刪除」的測試。另外也可以改成對每個非簿記路徑直接比 `git rev-parse <母>:<路徑>`(物件 id 與模式)的三方比對,不靠 diff 清單。

## F3 簿記豁免讓合併提交本身能夾帶任意帳本內容;偽造 head_sha 落在窗口內的紀錄,一個合併提交就夠
severity: minor
blocking: 否 — spec 已自承帳本可手寫是既有天花板,放寬後的邊際增量小(minor↔否)

誰:惡意開發者。
從哪:S 是含未審高風險程式碼的分支頂端(沒有任何真留痕),主線頂端 P1。
做什麼:做合併 M,母=(P1, S),M 只多一筆手寫的 `docs/.governance-log.jsonl` 行:gate=code-loop、kind=passed、head_sha=S、branch 隨便寫。帳本是簿記檔,不受條件 3 的「等於一個母」約束,所以 M 的帳本可以跟兩邊都不一樣。
結果:條件 1、2、3 成立;讀帳不看分支名,head_sha=S 在窗口內、同版本有效,放行。S 的未審程式進主線。
邊際:現行規則下,先提交程式 C 再提交一筆 branch=main、head_sha=C 的手寫帳本也成立(spec 自己寫了這點),所以不是新洞;差別只在「一個合併提交就完成、而且不必寫對分支名」。

引句:「帳本是沒簽章的純文字,手寫一筆就能偽造——這在現行規則下寫成 branch=main 也成立,不是新洞」
引句:「治理帳簽章(帳本可手寫偽造是既有天花板,不是本案新增)」

建議:至少讓讀帳只認「在第二個母那側的樹裡就存在」的紀錄(用 `git show <第二個母>:docs/.governance-log.jsonl` 讀,不讀合併結果的帳本),這樣合併提交本身加的行不算。成本小,把偽造從「合併提交一步」退回「得先在 S 那側有一筆」。

## F4 「第一個母 = 起點 = 已檢查過」的前提不成立:前一次推送的紅燈不擋進主線
severity: minor
blocking: 否 — 現行規則下「紅一次之後下次推送範圍只看新增」本來就成立,不是放寬新造的

誰:有推送權的人。
從哪:直接推主線(本 repo 無分支保護,見 file: `scripts/lumos:46990` 一帶 `_codeloop_marker_skipped` 註解「主線沒有分支保護、零 PR」)。
做什麼:第一次推未審高風險提交 U 到主線(`--no-verify` 或 CI 事後才紅);第二次推 M=merge(U, S),S 有真留痕。
結果:第二次的推送範圍起點 = U = 第一個母,三條件成立,放行;U 的未審程式已在主線。這跟「U 後面再推一筆小提交,下次範圍只看新增所以綠」是同一個既有行為。

引句:「主線那側在推送前已經是遠端現況、檢查過了」

建議:spec 把「檢查過了」改成「不保證」,避免日後有人把它當成條件的安全依據;不必為此另加機制。

## F5 起點為全零/本機找不到時,spec 寫「不認」,但程式實際會把範圍起點改寫成跟主線的分岔點,可能被認
severity: minor
blocking: 否 — 被認的情形(新分支首推 merge(主線頂端, S))內容本來就是「主線+已審 S」,F1/F2 之外沒有新增繞法

誰:推新分支或 force push 的人。
從哪:`_codeloop_guard_verdict` 在拿到判定之前會先把全零或本機找不到的起點換成真起點,見 file: `scripts/lumos:46968`(`_lens_push_base`:`scripts/lumos:43616`),推送前掛鉤對新分支也先換成跟主線的分岔點,見 file: `scripts/hooks/pre-push:48`。CI 則原樣交全零。

## 查過沒有繞法
- 先推一個只動簿記檔的提交讓起點前進再合併:第一個母必須等於「新」起點,未審分支擺第一個母仍不等於起點;只動簿記檔的提交本身不帶未審程式。
引句:「也擋本機 `git pull` 合出來的合併、以及功能分支先在本機多了沒推過的提交再合主線」
- 分兩次推(先推未審 S 到別的分支,再推合併):第二次仍要過條件 2、3 與留痕有效性,S 上的未審程式在 pass 之後都會讓紀錄失效。
引句:「主線歷史裡舊合併請求的 pass 之後都動過程式,不會被認」
