# r2 待驗案例(修前 ccca94927 → 修後見 r2-repair-binding.json 的 after_commit)

案例只是待驗範圍,不是「已修好」的證據;新席自己跑兩版核對,可補案例。測試指令一律 `python3.14 scripts/test_lumos.py -k <關鍵字>`;修前版本用 `git -C <臨時目錄> worktree` 或 `git show ccca94927:scripts/lumos` 取。

| 組 | 角色 | 待驗行為 | 出處 | 選例依據 |
|---|---|---|---|---|
| G1 | repair | 分支名含斜線(`feat/sit`)時 pass 預判照分支全名找本機追蹤的遠端分支,已推過那段不算新增;只在已推之後再加一行時,只算那一行 | 計劃〈做法〉範圍照推送輸入模擬 | 席位指出 `--short` 取名與鄰居不同 |
| G1 | preserve | detached HEAD、沒有遠端 → 印一行「留給推送前判」並放行 | 計劃 S4、S5 | 既有斷言 |
| G2 | repair | pass 擋下時印的是推送前那道的原文(`[spec-gate 推送前]` 開頭的原因),最後補一句 pass 自己的出口,出口含「choice-kill」「--carry」「跟帳本一起提交」 | 計劃〈做法〉訊息;鄰居 `_codeloop_pass_mech` 原樣轉印 | 席位指出字樣替換表是第二種做法 |
| G2 | preserve | 推送前(site 預設 push)那道的訊息、事件 note 一字不變;事件不帶 site 欄 | 計劃 S9 | 既有斷言 |
| G2 | preserve | 同一版同一組原因,push 與 pass 各記一筆擋下,不互相去重 | 計劃〈做法〉去重鍵含場合 | 既有斷言 |
| G3 | repair | 範圍測試含「已推過、再加一行」的增量案例,只算新增那一行 | 席位報告 | 席位指出缺增量案例 |
| G4 | repair | 原本一支四十多秒以上的大測試拆成四支,名字互不為子字串(`-k` 各挑到一支) | 修正關卡要求測試名唯一 | 修正關卡實際擋下 |
| G5 | repair | 系統筆記 pitfalls-code-loop〈代碼審記通過前的選擇點預判〉寫明 pass 呼叫推送前那一圈、帶 site 參數的呼叫關係 | 架構對齊席 a1 | 文件類 |

G5 的 a4(模擬推送輸入)判為不改,理由在計劃〈做法〉;沒有產品案例,核對說法跟程式一致即可。
