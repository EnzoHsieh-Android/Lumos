我實測了這份 patch 的新行為(把 5242975c 版的 `scripts/lumos` 載入,餵攻擊輸入)。沒有找到可直接利用的洞,只有兩條縱深防禦類的缺口。

**發現 1:引號鍵規則漏掉「引號後面先空白再冒號」**
severity: minor
blocking: 否
引句:「引號鍵:收到成對的引號、緊接冒號加空白或行尾才是鍵;」
佐證:`scripts/lumos:7151`
- **攻擊路徑**:惡意或粗心的計劃筆記作者,在 `decisions:` 底下寫 `    "text" : hidden`,或在流式寫法裡寫 `x: {"text" : a}` 或 `{"blocking" : true}`。
- **現象**:引號鍵只認引號後緊接冒號。標準 YAML 允許 `"text" : v`,所以 `_pq_scan` 對這些輸入全部放行,不報「清單範圍外出現題目的鍵」。
- **實測**:`"text" : hidden`、`  - {"text" : a}`、`x: {"text" : a}` 三種都回「通過」,而 `x: {"text": a}` 會被擋。
- **取得什麼**:一道題目形狀的結構被放在 pending_questions 以外。肉眼和 AI 讀到會當成待決題,閘卻不計入。同一條缺口還有 YAML 雙引號跳脫鍵 `"te\u0078t": hidden` 和複雜鍵 `? text` 兩種寫法,實測也都通過。
- **為何只算 minor**:作者直接不寫那道阻塞題就能達到同樣效果,所以這只削弱「清單外不准放題目」這條守衛的完整性。推論:沒有找到作者能多拿到的權限。

**發現 2:放行規則對私用區與未指派碼位沒有額度**
severity: minor
blocking: 否
引句:「去掉空白、DICP、補充空白字與 Mn/Me/Sk 修飾類後沒有可見基底就算空值。」
佐證:`scripts/lumos:7280`(`_pq_scalar_char_problem` 只看 `_pq_bad_char` 和 `_pq_invisible_over_limit`,兩者都不管這類碼位)
- **攻擊路徑**:計劃筆記作者,或被誘導把外部文字貼進題目的人,在題目文字裡塞 `\ue000` 到 `\uf8ff` 或補充私用區(`\U000f0000` 起)的碼位。
- **現象**:這些碼位的類別是 Co 或 Cn,不在 DICP 清單裡,也不計入隱形額度。`_pq_scalar_char_problem("x\ue000\ue001\ue002\ue003")` 回 None。
- **全碼位掃描**:我把所有碼位放在 `a_b` 和 `ا_ب` 兩種上下文裡跑。Co 約 13.7 萬個、Cn 約 81 萬個全部通過,而且沒有數量上限。多數終端和字型會把它們畫成空白或豆腐方塊。
- **取得什麼**:一條不限長度、人眼幾乎看不出的資料通道,可以進題目文字被 AI 讀到。這是本輪 16 位元絕對上限所要堵的那類通道。
- **為何只算 minor**:這條缺口早於本輪,不是這次引入的。模型能不能解出內容是推論。
