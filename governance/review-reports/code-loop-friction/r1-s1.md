## 鏡頭 1:血緣一跳查(讀 .governance-log.jsonl + 子字串比對)

**finding — severity: major, blocking: 是**
判準:子字串比對沒有邊界字元,編號互為前綴時會把兩個完全無關的迴圈誤判成連續重寫鏈,而這條「連續第二次強制攤人」正是本次改動唯一要保正確的邏輯。

引句:`f"successor={loop_id.strip()}" in str(o.get("note", "")):`(`scripts/lumos:454`,原始出自 patch 新增行)

已用可重現實驗證實:先跑 `lumos loop rewrite lf-x --successor lf-a2`(寫入 note 含 `successor=lf-a2`),再對一個**從沒被重寫過**的全新編號跑 `lumos loop rewrite lf-a --successor lf-b`——因為字串 `"successor=lf-a"` 是 `"successor=lf-a2"` 的前綴,子字串比對誤中,程式印出:
```
★這已是連續第二次判重寫(上一段血緣:lf-x → lf-a)——強制攤人,不得三開★
```
但 `lf-a` 和 `lf-x`/`lf-a2` 毫無關係,這是偽造的血緣鏈警告。這條 chain 查找是本指令存在的核心目的(docstring 自己講「連續兩次判重寫→強制攤人,不得三開」),用不帶邊界的 `in` 子字串比對來做編號比對,只要編號體系裡出現任何互為前綴的組合(例如同一批號的 v1/v1a、或簡短編號如 lf-a/lf-a2/lf-ab)就會誤觸。修法:比對時要求後面接分隔字元或字串結尾(如 `re.search(r"successor=" + re.escape(loop_id) + r"(;|$)", note)`),或把 note 改成結構化欄位而非塞進自由文字後子字串搜。

延伸(同一 finding 的補充,不重複計數):`chain_prev` 在 for 迴圈裡沒有 `break`,命中多筆時取檔案裡最後一筆匹配——如果有多筆假陽性,顯示的「上一段血緣」不保證是最早或最相關的一筆,只是巧合地最後匹配到的。

## 鏡頭 3:lineage 組字與 rstrip(";") 邊界

**finding — severity: minor, blocking: 否**
判準:rstrip 本身邏輯正確(空 note 乾淨去尾),但 note 欄位混用「機器血緣 token」與「人類自由文字」又不跳脫、只靠子字串比對解讀,是與 F1 同源的設計脆弱性,只是觸發向量換成使用者輸入。

引句:`f"prev={loop_id.strip()};successor={successor.strip()};{note or ''}".rstrip(";")`(`scripts/lumos:458`)

驗證:`note` 為空字串時,f-string 產出 `"prev=X;successor=Y;"`,`rstrip(";")` 去掉唯一的尾端分號,輸出乾淨的 `"prev=X;successor=Y"`,沒問題。`note` 本身含 `;` 時(如 `"先評估;再重寫"`)會原樣接在後面,不影響現有的 chain 查找(因為查找只找 `successor=<id>` 子字串,不靠分號切欄位),沒有立即的解析錯誤。但因為 note 尾段是使用者可自由輸入的文字,若剛好包含形似 `successor=lf-xxx` 的字樣(例如複製貼上舊筆記、或人手寫「這其實是給 successor=lf-old 用的」這類敘述),下一次血緣查找會把它當成真血緣命中——這是 F1 同一類子字串比對脆弱性的另一入口,只是觸發機率低、且需要使用者主動打出這種字樣。
