## 1. 邊界正則 `(;|$)` 在非 MULTILINE 下對單行 note 字串成立嗎?note 內含換行可能嗎?

已讀,修復正確。

引句:「_pat = _re.compile(r"successor=" + _re.escape(loop_id.strip()) + r"(;|$)")」

判準:成立與否要看 `successor=<id>` 在 note 裡的相對位置是否固定,不是抽象問「$ 語意對不對」。查寫入端 `lineage = f"prev={loop_id.strip()};successor={successor.strip()};{note or ''}".rstrip(";")`(file: `scripts/lumos:464`)——successor 值**永遠**緊接一個字面 `;`(note 非空時)或就是字串絕對結尾(note 空,靠 `.rstrip(";")` 去掉多餘分號)。使用者自由文字(`--note`)一定接在這個邊界「之後」,不會插進 `successor=<id>` 和邊界判定點之間。所以就算 note 內含換行(`--note` 是 argparse 自由字串,shell `$'...'` 可傳入真換行;`json.dumps` 會轉成 `\n` 逃脫字元存成單行,讀回後記憶體字串才還原成真換行),那個換行只會出現在邊界之後,不影響 `(;|$)` 判定。手動實測兩型都還中(見第 5 項)。`kind=rewrite` 事件的唯一寫者就是 `cmd_loop_rewrite`(grep 全檔只有這一處 `_loop_gov_mark(..., "rewrite", ...)`),沒有第二個寫法會打亂這個位置保證。

## 4. 三個新斷言與修復行為一一對應、無假綠?

**Finding — severity: low, blocking: 否**
判準:patch 實際只新增 2 個 `check(...)`,不是「三」。

引句:「check("rewrite: 前綴編號不誤判連續重寫", "連續第二次判重寫" not in r3.stdout, r3.stdout)」
引句:「check("rewrite: 帳內非物件 JSON 行不炸", r4.returncode == 0, str(r4.returncode))」

`grep -n "^+" r2-delta.patch | grep "check("` 只有這兩行;`git show f321a7f -- scripts/test_lumos.py` 的真實 diff 同樣只加 2 個 `check`。但這份 patch 自己的來源提交訊息(`f321a7f`)寫的是「t_loop_rewrite_mark 補三斷言先紅後綠」,任務背景也寫「測試補三斷言」——數字與實際內容對不上。這個專案的治理文化對「審計條數要逐檔數、不能抄摘要」特別敏感(先前已因此犯錯過),所以即使不影響程式正確性,仍記一條 finding,非 blocking。

對這 2 個實際存在的斷言逐一驗證「先紅後綠、無假綠」:
- `pfx-a` 前綴碰撞斷言:在 `f321a7f^`(舊碼,子字串比對)上重跑,實測得到 `✗ rewrite: 前綴編號不誤判連續重寫`,stdout 印出「★這已是連續第二次判重寫…」的偽警告,精確重現 patch 註解描述的 `successor=lf-a` 誤中 `successor=lf-a2` 症狀;新碼上綠。
- 壞 JSON 行斷言:同一份舊碼上實測得到 `✗ rewrite: 帳內非物件 JSON 行不炸`(rc=1),新碼上綠(rc=0)。
兩者都對應到各自要修的行為,無假綠。第三個宣稱的斷言不存在,不是「多算的斷言其實是假的」,而是單純少寫了一個(可能是「多筆時取最後一筆」那條——但比對新舊碼,那行為在修復前就已經隱含成立,聚合迴圈本來就沒有 `break`,一路覆寫到最後一筆,patch 只是替既有行為加註解,不是新邏輯,所以理論上也不強制要求新增專屬斷言;純粹是背景敘述的「三」對不上實際的「二」)。

## 5. 有沒有既有行為被此修復改變(原本合法命中的精確 successor=<id>;<note> 與行尾兩型都還中嗎)?

`;` 型(successor=<id> 後接分號+note):已讀,修復正確。這型由既有(r1 就有的)測試覆蓋:
