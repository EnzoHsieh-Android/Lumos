severity: major

severity: blocker
blocking: 是
若不信任 Git 的 mtime/size 判定而強制對全量檔案進行內容雜湊，將失去 `git status` 帶來的效能優勢。在 Python 零依賴下，對數千個檔案逐一讀取並計算雜湊，其耗時將遠超 30ms，導致每次收工提醒都有明顯卡頓。
引句:「判定一律比內容雜湊,不要只看修改時間加大小。同樣長度的字串換掉、整個動作落在同一秒內,時間和大小兩個都不會變。」

severity: major
blocking: 是
S4 條款規定「不應含上一輪已經算過的改動」，但在同一檔案連續多輪修改的情境下，這會導致後續輪次漏報。若 A 檔在第一輪與第二輪皆有修改，依此邏輯第二輪將因 A 已被「算過」而將其排除，直接違反 S1 的全量報表要求。
引句:「當基準存在,清單不應含上一輪已經算過的改動(每輪重取基準,不是整個會談取一次)」

severity: major
blocking: 是
提案未定義當 AI 或使用者在會談中途執行 `git commit` 或 `git reset` 時的行為。一旦提交，`git status --porcelain` 的輸出會清空，導致快照比對機制遺失該輪在提交前所做的所有檔案變更，造成嚴重的少報。
引句:「量檔案樹(工作樹相對上次提交的內容雜湊,跟上一輪快照取差集)算出改了哪些程式碼檔」

severity: minor
blocking: 否
對於未追蹤檔案（Untracked files），若僅存儲雜湊差集，則每一輪新產生的檔案在未被提交前都會持續出現在「差集」中。這會造成 S4 所欲避免的「重複報同一批檔」現象，除非快照邏輯能精確區分「本輪新增」與「既存未追蹤」。
引句:「當天主 clone 樹上就有 4 支改動 + 27 筆未追蹤,多半不是當前會談造成的」

severity: minor
blocking: 否
S3 的退回路徑（全量比對）在共用工作目錄下會產生極大噪音，可能一次列出數十個無關檔案。雖然提案稱「多報是安全方向」，但過多的噪音會導致使用者習慣性忽略提醒，使守衛機制在降級模式下實質失效。
引句:「退回全量(工作樹 vs 上次提交)只能當標示過的降級模式、不能當預設——共用工作目錄是常態」

severity: minor
blocking: 否
S1 條款與驗收條件均未明確定義「刪除檔案」是否屬於「改了程式碼檔」。若 AI 在該輪刪除了一支程式碼檔，快照差集雖能偵測到變化，但若輸出邏輯只預期「被修改」的檔案，則該動作會被漏掉。
引句:「當這一輪用任何方式改了程式碼檔(含重導向、原地取代、heredoc、管線寫入、以及沒有列舉過的手法)」

最嚴重等級是 blocker、blocking 共 3 條。
