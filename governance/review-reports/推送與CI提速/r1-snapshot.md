# 推送與CI提速_計劃

> 白話:一個功能從推送到能合併常要 25–40 分鐘,因為全套測試其實跑了三次——本機推送前一次、PR 的 CI 一次、合併後主線的 CI 一次;而且 CI 的十六份照名字輪流分,最快一份 4.9 分、最慢 9.1 分。這篇讓每個提交的全套只跑一次,並把各份的耗時拉平。

PRIOR-ART: 世界上的共識是「便宜的子集擋大多數錯、完整測試每個提交只跑一次」:Google TAP 提交前跑受影響的、提交後跑完整(https://abseil.io/resources/swe-book/html/ch23.html);Meta 預測式選測只跑約三分之一仍抓到 99.9% 有問題的改動(https://engineering.fb.com/2018/11/21/developer-tools/predictive-test-selection/);bors(早期的合併機器人)的規則「主線只收已測綠的那個提交,不重測」;依耗時分片同 pytest-split 的做法(各測試耗時表、讓每片總耗時接近);同分支新推送取消舊 CI 用 GitHub 原生的 `concurrency` + `cancel-in-progress`。來源整理見 2026-10-14 兩路調研(Claude 與 Codex 各一份,結論一致)。本 repo 既有的 `Projects/CI加速_計劃` 已把全套分到多台機器;這篇在它之上動分法與觸發,不改測試內容。

RETIRE-IF: 依耗時分片上線後連續 20 次 CI,最慢一份比照名字輪流分時沒有縮短 1 分鐘以上,就退回輪流分;主線重跑略過上線後,只要有一次「略過的主線提交在之後的重跑裡變紅」(代表 PR 測的不是同一個東西),就拿掉略過、恢復主線全套。

## 現況(2026-10-14 量)

- CI(`.github/workflows/ci.yml`)有四個工作:prep(編譯檢查、判這次跑全套還是文件子集)、shards(全套分 16 份給 8 台機器,每台同時跑 2 份)、gates(後盾閘)。最近 300 次:推到 main 206 次、PR 94 次;成功 287 次,整次中位數 12.2 分。抽 4 次成功的 CI,每台 shards 機器跑完兩份要 6.1–14.3 分,最慢的一台每次都在 12.4–14.3 分;份與份之間差這麼多,是因為照名字輪流分、不看耗時(單份耗時 CI 沒印,量不到,只看得到每台)。
- 每個功能,改到程式而且不是輕量改動時:本機全套(推送前掛鉤切 4 片,掛鉤提示寫約 4–5 分,實測常到 5–10 分)+ PR 的 CI 約 12 分 + 主線 CI 約 12 分。只改文件或判成輕量的推送,本機只跑子集。
- 主線重跑的由來:`Projects/CI加速_計劃` 否決過「檔案樹相同就不重跑」——2026-10-04 實際發生過 PR 綠、主線紅,原因是有測試看提交歷史,而 PR 測的是 GitHub 臨時合成的合併提交,不是之後真的進主線的那個提交(那支測試拿主線頂端與前一個提交當範圍,見 [[Systems/測試假綠形態]] 鏡頭逾時暖快取那條 PITFALL)。這篇不比檔案樹,改成比「同一個提交」:PR 直接測分支頂端那個提交,合併用快轉,主線的提交就是被測過的那一個,歷史也一樣,正好消掉那次的根因(使用者 2026-10-14 裁定同意改這條)。

## 範圍

- 這篇:①依耗時分片(本機推送前與 CI 共用同一支分片函式);②同一個 PR 分支有新推送時取消舊的 CI(主線不取消);③PR 的 CI 測分支頂端提交、合併改用快轉、主線上同一個提交已有成功的全套就略過全套;④推功能分支時本機不跑全套——**不在這篇交付**:推送前掛鉤正被另一個會談大改,等它合併後另開下一階段(屆時補條款)。
- 不做:縮小 CI 的測試範圍(要先讓選測器陪跑、證明不漏抓,另案);合併佇列(單人加兩三個會談,搶合併的情況少,GitHub 原生合併佇列依 2023 年正式推出時的官方文件只開放給組織擁有的 repo 與企業版,本 repo 屬個人帳號,現行政策沒實測);快取(零依賴,沒有可快取的建置產物)。

## 做法

- **依耗時分片**:
  - 測試耗時表放新檔 `scripts/test-durations.json`(測試名對秒數),進版控,本機與 CI 讀同一份。
  - 測試執行器(`scripts/test_lumos.py`)每次跑完(不論分不分片)把各支實測秒數寫進 `.lumos/test-durations*.json`(本機、不進版控,只在來源 repo 寫,沿用既有快取同一條件);新增旗標 `--refresh-durations` 把這些合併進 `scripts/test-durations.json`(取最近一次,沒跑到的保留舊值)。
  - `--shard i/n` 讀耗時表:照秒數由大到小、同秒數照名字,逐支丟給目前總秒數最少的那一份(同總秒數取編號小的);表裡沒有的測試以表中位數計;表讀不到或壞掉就退回現行的照名字輪流分,並印一行說明。同一份表、同一份測試清單,各份算出來的分法一模一樣,所以各份聯集仍等於全部、沒有重複。
  - 片數比測試多時照樣會有空片,空片照舊擋下(帶 `--suite`——執行器只跑文件子集或關鍵字子集的旗標——時,子集比片數少造成的空片照舊算過)。
- **取消過期 CI**:`ci.yml` 加 `concurrency`,群組照事件與分支分開;只有 PR 事件 `cancel-in-progress`,推到 main 不取消。
- **主線不重跑同一個提交**:
  - PR 事件各工作 checkout 分支頂端提交(`github.event.pull_request.head.sha`),不再測 GitHub 合成的合併提交。分支落後主線時,PR 的 CI 測不到跟最新主線合起來的結果——這種分支本來就不能快轉合併,要先 rebase。
  - 推到 main 時,prep 用 GitHub API 查同一個提交(`head_sha` 等於這次推送的提交)有沒有已成功完成的 PR 事件 CI;有就把範圍判成 `skip`,shards 不跑,gates 照跑;查不到、API 失敗、權限不足一律跑全套。
  - 合併改用快轉:PR 的 CI 綠了之後 `git push <remote> <分支頂端提交>:main`,GitHub 會自動把 PR 標成已合併;代碼審手冊(`skills/lumos-code-loop/SKILL.md` 第 8 步與 `lumos-project-notes/commands/06-代碼審與推送.md`)的合併步驟改寫成這樣;主線動過時 git 會拒絕快轉(不是後代就推不上去),所以「快轉前必須已含最新主線」由 git 本身擋,不另寫守衛,遇到就先 rebase 再推、等 CI。
- **本機推送前不跑全套**(下一階段,不在這篇交付):推非 main 的分支時,推送前掛鉤只跑受波及合約測試(改動牽連到的合約行綁定的測試)、關鍵字子集(原始碼整字提到改到的函式或檔名的測試)與上次紅過的;推 main、tag 或明示環境變數時才跑全套。

## 驗收條款

- [S1] 當耗時表存在時(以下三支測試與旗標都是這篇新增),`--shard i/n` 應 照耗時由大到小逐支分給總秒數最少的那一份,同一份表下各份聯集 應 等於全部、彼此不重複,而且每份的總秒數 應 比照名字輪流分時更接近 [test:t_runner_shard_by_duration]
- [S2] 當耗時表不存在或讀壞時,`--shard` 應 退回照名字輪流分並印一行說明;片數比測試多時 應 照舊有空片並擋下 [test:t_runner_shard_by_duration]
- [S3] 當跑完測試時,執行器 應 在來源 repo 的 `.lumos/` 寫下各支實測秒數;`--refresh-durations` 應 把它們合併進 `scripts/test-durations.json`、沒跑到的保留舊值 [test:t_runner_durations_refresh]
- [S4] 當 `ci.yml` 被讀時,應 有照事件與分支分組的 `concurrency`,只有 PR 事件取消進行中的工作;PR 事件的各工作 應 checkout 分支頂端提交;推到 main 時 prep 應 能把範圍判成 `skip`(同一個提交已有成功的 PR 事件 CI)且 shards 在 `skip` 時不跑、gates 照跑 [test:t_ci_yml_speed_shape]
- [S5] 當合併已過 CI 的 PR 時,代碼審手冊 應 寫明用快轉推上主線、主線動過先 rebase 再等 CI [manual:讀 lumos-code-loop 第 8 步與 06 子檔的合併步驟,確認寫的是快轉而不是按鈕合併]

## 回退

- 依耗時分片:刪掉 `scripts/test-durations.json` 就退回照名字輪流分(不用改程式)。
- 取消過期 CI、主線略過:把 `ci.yml` 這幾段還原;合併方式改回按鈕合併時,主線照舊跑全套(提交不同就不會略過)。

## 實務隱患

- 已排除:金流:只動測試分片與 CI 觸發,不碰任何付款或計費。
- 已排除:對外送出:不寄信、不發通知,只多一次對 GitHub API 的唯讀查詢。
- 已排除:不可逆:分片表與 CI 設定都能直接還原,不改資料也不刪東西。
- 守衛面:主線略過全套是少跑一次後盾,所以這篇照風險高走設計審。
- 耗時表過期:新測試以中位數計、刪掉的測試忽略,最壞是分得不平均,不會漏跑(聯集由同一份清單保證)。
- PR 改測分支頂端:分支落後主線時測不到合起來的結果;靠「快轉合併前必須已含最新主線」補上,按鈕合併時主線照跑全套兜底。
- API 查詢:prep 需要 `actions: read` 權限;查詢失敗一律跑全套(保守方向是多跑)。
- 併發:取消只作用在同一個 PR 分支的舊工作,主線永遠跑完。
