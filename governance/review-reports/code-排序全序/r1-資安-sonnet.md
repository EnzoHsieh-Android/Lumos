## 發現

### 1. 「全部是機器裁定,不是人裁」這句話跟它自己緊接著給的數字對不上

`Projects/評測尺修復_計劃.md` 那段 KEY 先寫「全部是機器裁定,不是人裁」,下一句立刻列出
「第一輪 52 兩席一致+17 三席多數+3 Enzo 裁」——3 筆是人(Enzo)裁的,不是機器。我用結構化
比對抓出這 245 筆新增標註裡實際 `"by": "Enzo"` 的有 4 筆(不是 3,第 4 筆在「最後 1」那批,
`E13/Issues/收工閘漏掉純Bash改碼.md`,附註是先前已裁、爭議清單漏刪重新過一次)。這 4 筆都
回溯得到:是三席(甲/乙/fable)完全打散(`三席全散.json`/`三席全散-重算.json`)才交給 Enzo
拍板,`by` 欄位如實寫著 "Enzo"、`why` 欄位也誠實寫著三席各自的分數與「Enzo 裁」——**沒有
把人裁偽裝成機器裁,也沒有把機器裁偽裝成人裁,方向上沒有造假**;純粹是這句話的頭一句摘要
講得比實情絕對,跟它自己下一句話矛盾。這種筆記內部前後打架,正是本專案圖譜紀律點名要避免
的狀況,而且是「不可逆判定」的前提說明,措辭不該有歧義。

引句:「★全部是機器裁定,不是人裁★:三席獨立(sonnet 甲/乙 + fable),第一輪 52 兩席一致+17 三席多數+3 Enzo 裁」

severity: minor
blocking: 否——資料本身(by/why 欄位)誠實揭露、可回溯到原始三席裁決檔,不存在冒充;只是筆記摘要句的措辭跟自己給的數字矛盾,修一下措辭即可,不影響這份 diff 的技術正確性,也不影響已經誠實記錄的失敗閘結果(見下)。

### 2. 新函式的「唯一實作」宣稱,跟同檔案裡另一份沒被改到的排序邏輯對不上

新加的 `_sort_pins` 開頭寫「改這裡就是改所有固定席的呈現順序,不要在別處再寫一份」,但
`cmd_impact_diff`(派工鏡頭/審計鏡頭那條路徑,`scripts/lumos:23629`,HEAD=798ce9f3 版本)
自己手寫了一份幾乎同構、但條件判斷不同的排序邏輯,且**這份 diff 沒有去動它**——
`Projects/固定席扇出降權_計劃.md` 裡也老實寫了「`cmd_impact_diff` 有自己的純分數排序,
本案不碰(s3f7,明寫範圍外)」。問題是:`cmd_impact_diff` 那段的舊註解寫著「跟逐檔那側
同一套口徑」,而它的排序鍵其實是「所有固定席都照分數排」,跟 `cmd_impact`(逐檔那側)的
「只有家之間照分數、其餘只看 kind 不看分數」不是同一套規則——這正是本專案自己的「三道都要
重用既有抽取解析、不能自寫第二套」這條不變量想擋的那種分岔,而它已經在分岔。我在核對時
發現工作目錄裡已經有另一名審查者對這個確切問題動手修正中(把 `cmd_impact_diff` 也改成呼叫
同一支排序函式,並在新註解裡承認「實測餵同一批候選給兩份公式順序相反,那句話是假宣稱」),
可佐證這不是我誤判。**但這個分岔是這份 diff 之前就存在、這份 diff 明確選擇不動它**,所以
不算這份 diff 自己引入的洞;只是新加的 docstring 用「唯一實作」這種絕對語氣,跟專案自己
筆記承認的「還有一份沒碰」對不上,容易讓下一個讀者誤以為改一處就等於改了全部。

引句:「★改這裡就是改所有固定席的呈現順序★,不要在別處再寫一份。」

severity: minor
blocking: 否——分岔的根因(`cmd_impact_diff` 那份手寫排序)不在這份 diff 裡新增或修改的程式碼裡,diff 本身也在旁邊的計劃筆記老實承認「本案不碰」;擋下這份 diff 不會讓那個既有分岔消失,而且已有後續修正在處理。建議是下一版把 `_sort_pins` docstring 的「唯一實作」改成「本次涵蓋範圍」或補一句指到未涵蓋的那一側,避免誤導。

### 3. 排序末項改用節點名斷開,理論上可被檔名操弄,但只影響顯示順序、不影響是否被看到

任何能在 `docs/*-knowledge/` 底下新增或改名筆記的人,都能決定自己筆記的 `node`(相對路徑)
字串,進而在「事故優先、家優先、同分」這些條件都打平時,用檔名字母序把自己排到同層裡的
前面。我追蹤了 `pins`(固定席)在三個消費端的用法:`cmd_impact` 本身(`scripts/lumos:23334`
一帶,`final = pins + free + rescued`,pins 全數印出不截斷)、`retrieval_eval.py` 的
`edit_universe`/`_touched_edit`(`governance/eval/retrieval_eval.py:174-200`附近,註解明寫
「全部固定席(pin_noise=事故指標,不受名額限制)」)、以及 `build_goldset.py` 的 `edit_pool`
(呼叫 `impact --ranked --top 8`,`--top` 只裁 free 桶)。三處都證實**固定席從不因為 `--top`
或名額被截斷**,只有 `free`(非固定)桶會被裁。也就是說,節點名能操弄的只是「同一批已經
確定會被完整列出的候選,誰排前面」,不能讓自己的筆記被算進候選、也不能把別人擠出候選集合。
唯一可能有感的地方是 `output_top3_must`(`governance/eval/retrieval_eval.py:297` 附近,
"必看 15/69 坐固定席...前 3 席組成幾乎不變")這種只看「前 3 名是誰」的品質指標,如果剛好有
多筆同分同層的固定席,字母序在前的那筆會佔走前 3 席的位置——但這在改動前(`free` 桶)本來
就是既有慣例(`free.sort` 早就用 `(-score, hop, node)`),這份 diff 只是把同一種慣例延伸到
`pins` 桶,不是新發明的手法,而且觸發它需要先有能寫入這個 repo 的權限——這個工具鏈是給有
repo 寫入權的維護者用的內部治理工具,不是對外服務,門檻本身就已經是「已經信任的人」。

引句:「現在固定席排序是★全序★:末項一律以節點名斷開,抽成單一實作。」

severity: minor
blocking: 否——影響範圍僅止於同層同分候選之間的顯示順序,不影響候選集合本身(固定席不受名額/top_k 限制,三處消費端程式碼皆已核對);要利用它必須先有 repo 寫入權,而這正是這個工具原本就假設的信任邊界,不算這份 diff 新開的攻擊面。

  這次評測是在打包最終提交「之前」跑的(`retrieval-eval-history.jsonl` 裡 `eval_head` 也同樣
  記著 `138eaad6`,兩者互相對得上),不是重釘到一個舊的、刻意避開新內容的提交去造假降低
  未標數。這份提交本身新增的 4 篇圖譜筆記因此沒被算進這次評測語料,`Projects/評測尺修復_計劃.md`
  自己也寫明「每輪補標後都會再浮出新未標...歸零只是某個時間點的快照」,是已知且公開承認的

## 全篇結論

44 個檔案都看過一遍,程式改動小而乾淨,標註資料「只增不改」的宣稱通過結構化全量核對,
機器/人裁的 by 欄位誠實、可回溯,語料快照真實存在且合理,排序改動雖然理論上可被檔名操弄
