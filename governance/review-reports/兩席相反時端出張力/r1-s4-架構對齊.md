## 發現

### A1 evidence 語意在 tension 裡窄化,沒有明講跟 satisfied 的差異

severity: minor
blocking: 否

引句:「只在 `chosen=suggested` 時必附，指到這份改動裡採新做法的那一行」

`satisfied` 狀態的 `evidence` 今天可以是 `path:line` 或 `test:<名>`/`test:<平台>:<名>` 兩種格式(`_dispositions_check_test` file: `scripts/lumos:21372`、`_dispositions_check_test` 的呼叫點 file: `scripts/lumos:21484`)。`tension` 的 `evidence`(`chosen=suggested` 時)只驗 `path:line`(走既有 `_dispositions_check_path_line`),不支援 `test:` 格式。同一個鍵名 `evidence` 在兩種 status 下接受的格式不同,設計文字沒有明講這個差異,容易讓實作或審查席誤以為 `evidence` 全局語意一致(可以填測試名)。結構本身沒問題(仍是既有函式擴充一個分支),只是命名/文件語意層要補一句「tension 的 evidence 只認 path:line,不認 test:」。

### A2 `n_files` 這個 JSON 鍵名沒有跟既有「輸出鍵不帶 n_ 前綴」的慣例對齊

severity: minor
blocking: 否

引句:「並 append 到新欄 out["tensions"]：{id, chosen, existing, n_files, hazard, suggestion}」

這支程式裡,`n_files`/`n_txn`/`n_auto`/`n_sections` 這類 `n_` 前綴變數,序列化成 JSON 輸出鍵時既有慣例是去掉 `n_` 前綴、換成單純名詞——對照 `_cochange_mine` 的 JSON 輸出 file: `scripts/lumos:16406`(`print(json.dumps({"rules": out, "commits": n_txn, "files": n_files}, ...`,`n_files` 這個計數變數對外的 JSON 鍵是 `"files"` 不是 `"n_files"`)。`_lens_dispositions_lines` 裡的 `n_auto` 也只用來組人可讀文字(`f"(另有 {n_auto} 題未觸發...)"`,file: `scripts/lumos:19644`),沒有直接當 JSON 鍵。本案 `out["tensions"]` 的每則物件直接把 `n_files` 當鍵名對外輸出,跟這個既有「內部變數用 `n_` 前綴、對外鍵名脫前綴」的命名慣例不一致。屬於命名層的 minor,不影響結構(這個鍵依然是既有 `tensions` 陣列裡的一個欄位,不是另開一套輸出路徑)。
