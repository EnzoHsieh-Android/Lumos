★席位自述★:它先確認 patch 的 before blob 跟 HEAD 完全一致,然後用隔離的 git clone + git apply 在暫存區重建被審版本,所有實驗都對那份跑。審查途中它發現工作樹被並行改動(例如 pre-push 出現了一個幾分鐘前還沒有的 trap,而那個 trap 的註解自己寫著「代碼審 r1 外家否決席判 minor,屬實」),它沒有碰工作目錄,並在報告裡註明哪幾條在工作樹上看起來已經修好。

★兩條核心安全不變式它都直接測過★:低風險 `--advisory` 一律回 rc=0(用真的紅掉的合約測試、壞掉/不存在的結果檔、mktemp 失敗三種現場測過);高風險 `code-loop check` 仍然會擋(用真的觸發 tier=high 的改動、沒有 pass/skip 留痕 → rc=1)。

- [major] `_IMPACT_JSON` 暫存檔在每次高風險被擋與收到訊號時洩漏(被審快照版本)。
  引句:「local _f; _f="$(mktemp -t lumos-impact 2>/dev/null || true)"」
  位置:`scripts/hooks/pre-push`
  blocking:否
  why: 清理只在 ref 迴圈底部跑,而被審快照裡沒有 trap。它建了一個含 `open()` 呼叫(觸發 tier=high)、沒有 pass/skip 留痕的真 repo,端到端跑 pre-push:rc=1 如預期,但 $TMPDIR 裡留下一個 370 位元組的 impact JSON。也用 SIGTERM 中途中止重現過。每次高風險被擋(而那是很常見的「改了再推」流程)就漏一個檔。

- [major] `_bound_tests_range` 換主線之後,會選到被推的分支根本沒碰過的檔。
  引句:「"新分支首推:起點改用主線 {ml[0]}"」
  位置:`scripts/lumos`
  blocking:否
  why: 它建了一個 repo:feature 從 base 分出去、只動 app/other.py;同時 main 各自往前走、動了 app/pay.py(綁著固定席 ★INVARIANT★ 的檔)。模擬這條分支首推,函式換成 `main..FEATURE`,而 `git diff --name-only main..FEATURE` 會回報 app/pay.py 有改——即使 feature 從沒碰過它,因為 `git diff A..B` 只是比兩棵樹,main 的前進在分支視角下變成一個「反向」的改動。這把 Systems/Pay.md 拉進固定席並跑它綁的測試。它另外確認退化情形:兩個分支沒有共同祖先時(merge-base rc=1),換出來的範圍會 diff 兩棵樹的所有檔——★靜默退化成 [S3] 明說要避免的「跑滿全部」★。而「首推發生在主線已經前進之後」是常態不是罕見邊界。
