# 凍結的實驗材料（政策來源仍為共用手冊）


**測試必須有獨立的判準，並能抓到它宣稱守護的行為被破壞。** 適用於新功能、修 bug 與重構時寫的測試，不限於代碼審的修訂輪。

1. **先說要守什麼。** 寫測試前列出「輸入／預期結果／判準來源／應抓到的錯誤」；來源可以是需求、合約或事故。簡單案例寫在測試名稱或註解即可，不要求每支測試另建筆記。
2. **預期結果要獨立。** 用規格、人工確認的例子或可信參考實作；expected 由上述獨立來源取得，與被測算法分開。fixture 可用正式程式的 helper，但必須另有獨立確認的案例，避免 helper 與功能一起錯、測試一起綠。
3. **斷言實際行為。** 觀察輸出、狀態、寫入結果或錯誤理由。原始碼字串、函式名稱、呼叫次數、內部常數相等可以補充，功能正確另以可觀察行為證明。
4. **讓情境真的成立。** 宣稱測併發、巢狀或寫入失敗，就要建立該情境及前置斷言；宣稱某守衛拒絕，就確認拒絕理由，用可到達目標守衛的輸入，核對該守衛自己的拒絕理由。
5. **修 bug 與關鍵守衛要證明抓得到錯。** 恢復原缺陷，或做一個對應故障變體，確認目標行為斷言翻紅、還原後翻綠；匯入失敗、語法錯、環境錯或逾時不算。只挑與本次改動相關的案例，不要求每輪全套 mutation testing。證據記錄版本、案例、故障與紅綠結果；不可執行時明記原因與未驗範圍，結果保持未驗。隔離與安全執行沿用 lumos-design-loop 的 `templates.md` §3.1：暫存原始碼不代表外部服務、資料庫也已隔離。
6. **保留有目的的結構測試。** 靜態規範、接線與一致性檢查仍有用，說清它守的結構；不一律禁止私有函式測試，也不因形式相似就刪除。功能行為另有對應的行為驗證。

例如「數量 3、單價 5，總價應為 15」的預期值來自已確認例子；把正式程式的乘法重寫一次算 expected，只證明兩份寫法一致。分組功能也不能只比 `split_for(group) == split_for(group)`：另用已確認會落入不同組別的例子，才能抓到永遠回傳同一組的退化。

**開發與審查接點：** 實作者先列四項判準，再寫紅→綠測試；審查者檢查 expected 的來源，問「永遠成功、固定回傳、略過關鍵步驟，這條斷言會紅嗎？」。修 bug 與關鍵守衛需核對實際抓錯證據。這是人工工作規範；CLI 的紀錄形狀檢查不能證明判準獨立或測試有用。

參考：[Matt Pocock 的 TDD 測試指引](https://github.com/mattpocock/skills/blob/main/skills/engineering/tdd/tests.md)。

**完成條件：** 每個新增或修改的測試都已逐項交代守護行為、輸入與预期、獨立判準來源及實跑結果；修 bug 或關鍵守衛逐項附目標斷言紅→綠證據。核對到每項都有結果再交付；未驗項目列原因、範圍與剩餘工作，結論標為未驗。
