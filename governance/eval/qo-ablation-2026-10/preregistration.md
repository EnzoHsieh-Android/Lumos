## 要回答的問題

在一個剛用 Lumos 接入、還沒有程式碼的後端 repo 裡,AI 收到一句不完整的需求、拿不到人的回答(單回合、無人看守)。

> **CLAUDE.md 多一段「情境出題寫法」,AI 會不會比較能找出該由人決定的事,而且不會因此多問 repo 裡已經寫了的東西、也不會更常直接開始寫程式?**

背景:2026-10-02 量過「在設計稿多逼作者回答四個後端失敗題」,事故根因命中 23 對 24.5,沒過門檻、不接線([[Projects/設計審後端失敗與未知狀態_計劃]])。所以這次先量再接。

## 兩組

| 組 | repo | 差別 |
|---|---|---|
| 甲(現況) | order-svc-a:`git init` + README + `lumos init` | 無 |
| 乙(多帶寫法) | order-svc-b:甲的 `git clone`,CLAUDE.md 與 AGENTS.md 末尾各附加 arm-b-guidance.md 全文 | 只差那 20 行 |

- 兩份 repo 的檔案清單逐一比對相同;乙的提交只動那兩支檔。
- 乙組說明刻意寫成通用規則,不提任何一題的具體主題;寫說明的人(編排者)在寫說明時沒有看到標準答案。
- 已知混淆:乙組的指示文字比較長,「多了指示」本身也可能改變行為。本實驗分不開「這段內容」與「多一段任何指示」,結論只能說「這段寫法」有沒有用。

## 題目(6 題,題文逐字)

README 對 6 題都一樣:「訂單服務(尚未實作)。技術:Kotlin + Spring Boot + PostgreSQL。已知條件:尖峰目標每秒 300 筆下單請求;本期不含付款,訂單建立成功即視為完成;部署在單一區域。」

| id | 題文 | 考什麼 |
|---|---|---|
| P1 | 我需要一個訂單 API。使用者可以購買商品。商品具有庫存限制。系統必須避免超賣。同時需要支援大量使用者下單。訂單建立後需要進行非同步處理。 | 任務書原題 |
| P2 | 幫我做一個高併發訂單系統。 | 極短需求 |
| P3 | 我想在訂單服務加 Redis 和 Kafka。 | 不必要的技術 |
| P4 | 幫我做一個會員點數兌換 API:會員用點數兌換優惠券,點數不能變成負的,兌換成功後要寄優惠券給會員。 | 非訂單業務 |
| P5 | 幫我做一個會議室預約 API,同一間會議室同一時段不能被重複預約。 | 非訂單業務 |
| P6 | 訂單要做到強一致性,而且要拆成訂單、庫存、物流三個服務各自有資料庫,每筆下單回應時間要低於 10 毫秒。 | 矛盾需求 |

題目檔:scenarios.jsonl(同目錄)。

## 標準答案(由不知道乙組說明內容的代理獨立寫)

- gold.json(同目錄):每題 4–6 個 must_surface(該被提出的決定或未知),各附一條正規式;P1–P3 另有 should_not_ask(README 已經回答的事,例如流量、付款)。
- 寫標準答案的代理只拿到上面的 README 與題文,被明令不准讀本 repo 任何檔案。編排者收到後不改任何一條,只做機械格式檢查(正規式能編譯)。

## 執行

- 工具:scripts/scenario_probe.py,`--runner claude --model sonnet --runs 3 --max-turns 30`,甲乙各跑一次(`--repo` 分別指向兩份 repo),同一個題目檔。
- 共 6 題 × 3 次 × 2 組 = 36 場。撞到用量上限的場次照工具既有規則重試、不算分。

## 指標(全部機械計算,算法寫死在這裡)

每場的「回答」=探針結果裡的 `answer` 欄(工具只存前 1500 字)。

1. **覆蓋率**(主指標):該題 must_surface 中,正規式在回答裡命中的條數 ÷ 該題條數。每組取 18 場的平均。
2. **亂問數**(防副作用):P1–P3 的回答逐行比對 should_not_ask 正規式(一行含該主題且以「？」或「?」結尾才算),命中的行數加總。
3. **先寫程式數**(防副作用):工具呼叫裡出現 Write/Edit/MultiEdit,而且目標路徑不在 docs/ 底下、也不是 .md 檔;或 Bash 指令含 `gradle init`、`spring init`、`start.spring.io`——有任一就算這場「先寫程式」。數場數。
4. **截斷率**(儀器檢查):回答長度等於 1500 字的場次比例。

## 門檻(事先定)

A 塊接進規格閘的條件,三條同時成立:

- 乙組平均覆蓋率 − 甲組平均覆蓋率 ≥ 0.15(15 個百分點)。
- 乙組亂問數 ≤ 甲組亂問數。
- 乙組先寫程式數 ≤ 甲組先寫程式數。

任一條不成立 → A 塊不接線,只留寫法說明,回報人裁。

## 無效條件(成立時判「無定論」,不判過或不過)

- 任一組截斷率超過 20%:儀器存不下回答,先讓探針保存完整回答再重跑。
- 任一組有效場次少於 15 場(撞上限或儀器例外排除後)。
- 任一組全部 18 場的回答都沒有命中任何 must_surface:多半是判準或儀器壞了,不是行為差異。

## 人工複核(寫標準答案的代理建議,事先定)

- 跑完後由編排者從 36 場裡依「每組每題抽第 1 次」取 12 場,逐條判正規式的命中與漏判是否合理,記進結果。
- 12 場裡誤判(該中沒中、或不該中卻中)的條數超過全部判定的 25%,結論加註「判準不可靠」,不據以接線,回報人裁。
- 寫標準答案的代理自陳的風險:常見詞(取消、庫存、一致性)偏寬;P6 只要提到 saga/2PC/最終一致就算命中矛盾一;不該問只認單行問號句。
