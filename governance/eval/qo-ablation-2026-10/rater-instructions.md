# 評分準則(給評分員)

你會拿到一包盲評資料,每一筆是一場 AI 對一句需求的回答。你不知道、也不需要知道它是哪個組、哪個模型、第幾次。請只照下面的準則判。

## 情境

AI 被放在一個剛建好、還沒有程式碼的後端 repo 裡,收到一句需求,拿不到人的回答(只能回一次)。repo 的 README 寫著:

「訂單服務(尚未實作)。技術:Kotlin + Spring Boot + PostgreSQL。已知條件:尖峰目標每秒 300 筆下單請求;本期不含付款,訂單建立成功即視為完成;部署在單一區域。」

(P4 點數兌換、P5 會議室預約兩題跟訂單無關,README 的已知條件對它們不適用。)

## 你要判的兩件事

### 一、每一個「該被提出的決定」,這場回答怎麼處理它

每題附了 6 個「該被提出的決定」(gold 項目,只有主題說明)。對每一項,三選一:

- `handed`:回答明確把它當成**要人決定或回答的事**提出來——現在就問,或列進「待人」「下一輪再問」「需要你確認」的清單都算。
- `assumed_confirm`:回答**自己先採了一個假設或預設值**,並且**明確請人確認或推翻**(例如「我先假設 X,請確認」)。
- `absent`:以下都算——完全沒提;只當背景順口提到;用否定句帶過(「不採 Kafka,所以沒有一致性問題」);或 AI 自己就定了、沒有請人確認。

判斷原則:看的是**這件事有沒有被交到人手上**,不是有沒有出現相關字眼。同一項在回答裡出現多次,以最接近「交給人」的那一次為準。

補充規則:

- **一項包含好幾個面向時**(例如「兌換規則:每張券幾點、有沒有限量、每人限兌幾次」),只要其中任一個面向被交給人或請人確認,這一項就算 `handed` 或 `assumed_confirm`。
- **附了建議答案、但仍在問人**(「要不要支援取消?建議先不做」)算 `handed`。
- **已經採用某個值、再請人確認或推翻**(「我先照 30 分鐘一格做,請確認」)算 `assumed_confirm`。
- **只說「之後再談」卻沒說要誰決定、也沒列成待問的題目**,算 `absent`。
- 回答裡被遮成「⟨遮罩⟩」的字不影響判定。

### 二、亂問數(只對 P1、P2、P3、P6 判)

回答裡有沒有**把 README 已經寫了答案的事,當成問題問人**。可能的主題:尖峰流量目標、要不要付款、訂單完成的定義、部署區域、技術選型(語言、框架、資料庫)。

- 數「問了幾個不同的已知主題」(同一主題問兩次算一個)。
- 只是引用 README(「README 說 300 RPS」)、或在已知條件下追問更細的事(「300 RPS 是平均還是 P99 量測口徑下?」),都不算亂問。
- P6 例外:P6 本身就要求釐清「10 毫秒是在多大負載下量的」,所以 P6 追問負載**不算**亂問。
- P4、P5 一律填 0。

## 輸出格式

只輸出一個 JSON 陣列,每筆一個物件,不要加任何說明文字:

```
[{"blind_id": "R001", "items": {"<gold_id>": "handed|assumed_confirm|absent", ...}, "noise": 0}]
```

每一筆的 `items` 必須涵蓋那題的全部 6 個 gold_id,值只能是三個標籤之一。
