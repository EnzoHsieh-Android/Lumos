# 測試防竄改比對的考場實跑(2026-11-02)

這是**去識別化之後的摘要**:考場是公司私有的 Android 消費專案,這裡的檔名、測試名、提交編號都換成代稱(`F01`、`c01`、「Kotlin 測試檔」這類),不放考場原始碼與差異;能重跑的完整卷證(原始提交、候選原文、Semgrep 原始報告)留在考場的本機分支。怎麼落到工具與標準見工具鏈圖譜的 `Projects/Android測試防竄改檢查_計劃`。

| 檔 | 內容 |
|---|---|
| `cases.json` | 對照表:15 個壞改動(每條規則至少一個)與 5 個正常改動,各從考場同一個提交長出來;另一筆是同一次推送把閘設成 off 又加 `@Ignore`(`workdir_relaxed_rerun` 是把考場工作目錄的設定也改成 off 再判一次的輸出,判完已還原) |
| `history.json` | 考場 develop 全部非合併提交逐一跟上一個提交比(第一個提交跟空樹比)的候選與人工裁定:作弊樣、合理改動、規則判錯 |
| `semgrep/` | Semgrep 1.183.0 自比規則實跑:`*.txt` 是合成樣本(原本是 `.kt`/`.java`),`unit-output.txt` 是逐檔掃描的行號輸出,`drill-scan-summary.json` 是在考場跑 `lumos test-quality scan --semgrep` 的摘要 |
| `manifest.json` | 本目錄每個檔的 sha256 |

裁定方法照實講:44 條候選裡抽看了 5 條的實際差異(兩條「規則判錯」都是看差異判的),其餘依提交說明載明的需求或契約變更判成合理改動,沒有逐條看差異。

去識別化的範圍照使用者 2026-11-01 明列的:考場的套件名、類別名、測試名與本機路徑一律不進公開 repo(專案名 mOrangePos 可以寫);考場的短提交編號與本機分支名也不寫進這裡與新的筆記。例外是代碼審與設計審的卷證(`governance/review-reports/` 底下的凍結審材、席報告、快照):那些檔的指紋已寫進治理帳,改一個字審查的處置閘就判不過,所以保留當時的寫法;裡面的短編號只在考場本機解得開,不含業務內容。

縮範圍說明(代碼審第四輪後):建置檔與 CI 兩類規則移到計劃的第二批,`cases.json` 裡建置檔加 `ignoreFailures`(Groovy、Kotlin)與 CI 加 `-x test` 那三筆是縮範圍前的結果,縮範圍後這三筆不再列出;`history.json` 的 44 條候選不受影響(都不是建置檔與 CI 的規則)。
