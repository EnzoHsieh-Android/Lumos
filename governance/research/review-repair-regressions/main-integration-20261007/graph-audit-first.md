## 真正矛盾與關鍵缺口

**直接矛盾：未發現。** 三篇對整合目的、人工判讀邊界、未完成事項及 `doing` 狀態的說法一致。

需要補圖譜的關鍵缺口：

1. **合併後完整版本沒有唯一識別。**
   有兩個來源提交、共同基底及 CLI／測試檔 SHA-256，但沒有合併後完整 tree 或 commit 識別。筆記又要求正式審查固定「合併後完整版本」，因此僅靠三篇無法確定正式審查應鎖定哪個完整版本。

2. **測試不可由三篇精確重放。**
   記了分類與 assertion 數量，但沒有測試名稱、命令或測試檔對應；七個 helper 的固定輸入和預期輸出也未列出。因此能知道測了什麼類型，不能由三篇重現同一批測試。

3. **實輪試行入口不自足。**
   三篇多次把安裝及實輪觀察入口指向未准讀取的 `Projects/每輪修補差異派工_計劃`，本身沒有入口命令、位置或完整步驟。日期與十輪條件清楚，但實際從哪裡啟動未記載於這三篇。

4. **正式審查與全套入口只記事件，未記操作入口。**
   「準備推送時重驗」很清楚，但從這三篇找不到具體命令或指標。不能據此推論已排入或已執行。

5. **七項 helper 的證明粒度不足。**
   「符合預期」沒有逐例結果，因此只能接受總結性通過紀錄，不能判斷 S1–S3 各由哪些案例覆蓋。

6. **`doing` 的完成門檻未完整定義。**
   十輪提供保留／撤除判斷，但沒有明載什麼結果可讓計劃及系統由 `doing` 結案。

**最終判定：需補圖譜。** 建議至少補上合併後完整版本識別、精確測試／helper 案例清單、實輪與正式審查入口，以及 `doing` 的結案條件；在全套與正式審查完成前，不得標示整批已放行。
