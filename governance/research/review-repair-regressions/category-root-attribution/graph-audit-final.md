## 結論：PASS

四篇合讀後，已足以還原本案的動機、判讀方式、既有 CLI 邊界、驗證範圍及未決事項。沒有需要補圖譜的實質矛盾或關鍵缺口。

### 本次為什麼改

既有機制會在連續兩輪出現同類問題時，要求填寫前次處理與本輪新做法；但 `why_failed` 這個欄名容易誘導編排者把「分類相同」寫成「前次修補失敗」甚至「前次修補造成退化」。

本案因此補上一條界線：

> 同一個粗分類只觸發回顧，不證明根因相同，也不證明退化由前次修補造成。

目的不是放寬審查，而是保留原有提醒，同時避免為了通過欄位要求而編造因果。

### 判讀方法

判斷兩輪問題的關係時，要逐案核對：

- 前後 finding／group ID 與版本。
- 具體症狀及觸發輸入。
- 受影響需求。
- 實際失效機制。
- 能指回案例的證據。

ID 或位置相同，不足以證明同根因；改名、換 ID 或位置不同，也不足以證明根因不同。證據不足時應記「關係未判定」，不同根因的結論同樣需要證據。

此外要分開三件事：

1. 粗分類是否相同。
2. 前次問題是否殘留或重現。
3. 某次修補是否造成新的退化。

綠轉紅若跨越混合變更區間，仍不能直接歸因；必須有隔離證據才可列入修補造成的 `regression_set`。

### 原 CLI 要求及因果界線

既有要求沒有改動：

- 前一輪同類別、本輪嚴重度至少為 major 時，仍須填 `prior`。
- `other` 不算同類提醒。
- `prior` 內原有 `why_failed`、`new_approach` 兩欄及各至少十字的檢查均保留。
- `fix-check` 仍驗修正紀錄完整、測試存在、修正後測試為綠及受波及合約測試全綠。
- 它不驗證「修正前必須為紅」，也不自動語意判斷根因。
- `loop next` 仍只是提醒，不改派工狀態及回傳碼。
- `--regression-set` 仍只記有依據判定為前次修補造成的發現，不與一般 finding 類別混用。

因果界線也很清楚：字數通過只代表結構合格，不代表關係成立、修補有效或因果已證實。關係未判定不會降低 severity、刪除 finding，或自動把它移入 `regression_set`。

### 實際驗證

驗證是在固定內容 `32a00947` 下，以七項合成 helper 案例進行：

- 同類 major 在 ID／位置相同和不同兩種情況都會觸發。
- 不同類別、`other`、minor 不觸發。
- 誠實描述證據界線或關係未知的兩欄可以通過。
- 表格子集為 2 assertions 通過、0 失敗。
- spec-gate 判為低風險，S1–S3 三條人工核對通過，未進正式設計審查迴圈。

這只證明結構相容及新說明沒有破壞原要求；不是完整 `fix-check` 驗證、實際修訂輪成效、產品 bug 證據或收斂成效。
