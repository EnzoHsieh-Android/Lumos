# LLM 代碼審查成效的學術證據(至 2026-11-01)

標記:**[新]**=兩份既有調研(評測篇、迴圈工程篇)沒收;**[新*]**=這兩篇沒收,但圖譜別篇提過(出處寫在總表);**[已知]**=這兩篇已收,本篇補讀全文或補新數字。等級:同儕受控/預印受控/觀察/意見(定義與每篇出處見最後一節總表)。模型名稱一律照論文原文。

## 最新基準與評測報告了什麼?領先模型對「真實缺陷」的召回與精確度是多少?

### Takeaway
2026 年評測的題目從「像不像人寫的評論」換成「有沒有抓到人確認過的真缺陷」,這改變了結論:前沿代理在開源專案的 top-5 召回已達 64–80%,但換到訓練資料之外的企業內部 repo 最多掉 25.5%。精確度仍是最弱的一環,多數高分基準根本沒量精確度。數字差異主要來自「真值怎麼定義」,跨基準不可直接比。

### Cited Findings
**缺陷接地(最接近「抓不抓得到真 bug」)**
- [新] CRBugBench:1,000 個開源任務(98 repo)+800 個企業內部任務(2 個 monorepo),由人確認過的 bug 回溯到引入它的 PR。最佳代理 claude-opus-5(copilot-cli)top-5 平均抓到 71.9%;審查前被人發現的 bug 79.6%、合併後才發現的 64.2%;recall@1 僅 48.3%/36.2%,@10 為 86.0%/68.6%。opus-4.6 到 opus-5(2 月到 7 月)由 47.7% 升到 71.9%,每任務成本 $2.97 — [2610.13668](https://arxiv.org/abs/2610.13668)
- [新] 同一基準:企業 repo 上「最多掉 25.5%」;內部任務「從 diff 直接看得出」的 bug 只占 22.8%(GitHub 46.1%),這一項可解釋 20% 的落差 — [2610.13668](https://arxiv.org/abs/2610.13668)
- [新] 同一基準:95.6% 的執行有打開含缺陷的檔,80.2% 對該檔產出發現,只有 56.2% 真的命中;opus-5 分別為 91.9%(有發現)與 75%(診斷正確)。審查時實際跑程式碼只占 8% 回合 — [2610.13668](https://arxiv.org/abs/2610.13668)
- [新] 同一基準:依建構方式人類單獨約抓 50%,人加最佳代理聯集 82.1%;人明顯較會抓可維護性問題(OR=2.702)。「50%」是建構假設(發現時點約各半),不是測得的人類召回率 — [2610.13668](https://arxiv.org/abs/2610.13668)
- [新] SecPRBench(資安):265 個真實引入漏洞的變更(Firefox、V8、OpenSSL 等九個系統),八個前沿模型召回 32.5%–78.1%,Grok 4.6 最高 78.1%,前四名彼此無顯著差異。作者明說「不量精確度」 — [2610.33509](https://arxiv.org/abs/2610.33509)
- [新] CyberDual(可執行判定):三個審查代理在 1,088 個有效攻擊上抓到 85–91%(Sonnet 5 85%、Opus 4.8 88%、GPT-6-Sol 91%),但攻擊分散到真實提交窗口時,約六分之一的攻擊名額在審查後仍能利用 — [2610.34435](https://arxiv.org/abs/2610.34435)

**人類評論當真值**
- [新] c-CRAB:184 個 PR、234 條可執行測試、56 repo。Claude-Code 32.1%、Devin 24.8%、PR-Agent 23.1%、Codex 20.1%;四家聯集 41.5%(97/234)。行為類 31.0–38.1%,結構類 16.1–30.7% — [2603.23448 v3](https://arxiv.org/abs/2603.23448)
- [已知] SWE-PRBench:350 PR,8 個模型只偵測到人標問題的 15–31%,前四名統計上分不開(平均分 0.147–0.153) — [2603.26130](https://arxiv.org/abs/2603.26130)
- [已知] SWR-Bench v2:1,000 個人工核實 PR(12 個 Python 專案),最佳組合 PR-Review+Gemini-2.5-Pro 的 F1 只有 19.38%,主因是誤報;CR-Agent 多代理 9.22% — [2509.01494](https://arxiv.org/abs/2509.01494)
- [新] AACR-Bench v3:10 種語言、repo 層脈絡。Claude-4.5-Sonnet 代理模式精確度 39.90% 但召回僅 10.10%,無脈絡模式精確度 8.70%、F1 14.46。同一基準上最佳系統 OpenCodeReview 的 SEM-F1 也只有 25.10% — [2601.19494](https://arxiv.org/abs/2601.19494);[2608.09290](https://arxiv.org/abs/2608.09290)
- [已知] MCR-Bench(多輪):2,269 個真實多輪任務,最佳 F1「略超過 0.55」,輪數越多越差 — [2608.27442](https://arxiv.org/abs/2608.27442)
- [新] ContextCRBench:67,910 筆,品質判斷最佳 F1 59.54,作者結論是「離人類水準還遠」 — [2511.07017](https://arxiv.org/abs/2511.07017)
- [新] SWE-CARE 就是 CodeFuse-CR-Bench(論文開頭的 repo 連結即 SWE-CARE):601 例、70 個 Python 專案,結論是沒有單一模型全面領先;c-CRAB 建在它上面 — [2509.14856](https://arxiv.org/abs/2509.14856);[2603.23448](https://arxiv.org/abs/2603.23448)
- [新] CR-Bench:由 SWE-bench 改造,174(verified)/584(standard)個 PR,用訊噪比衡量;每例只圍一個已知 bug — [2603.11078](https://arxiv.org/abs/2603.11078)
- [新] DesignReviewBench(Linux 核心設計取捨):最強基線 F1 僅 0.213,加歷史設計知識的 DesignLore 0.259 — [2610.21925](https://arxiv.org/abs/2610.21925)
- [新] 2606.15689:模型 150 樣本,真實 PR(n=50)最佳 F1 只有 0.066,合成樣本 0.847(差 92%);小模型 Claude Haiku 4.5 勝 Sonnet 4.6(F1 0.365 vs 0.343,召回高 18%,成本低 3.2 倍) — [2606.15689](https://arxiv.org/abs/2606.15689)
- [新] 生產採用端:Beko 2,604 則留言;CodeRabbit 接受 36.4%、拒絕 56.3%(分母見迴圈工程篇更正);CRA 單獨審的 PR 合併率 45.20%,比人審低 23.17 個百分點 — [2604.24525](https://arxiv.org/abs/2604.24525);[2607.03316](https://arxiv.org/abs/2607.03316);[2604.03196](https://arxiv.org/abs/2604.03196)

### Inferences
- 「LLM 審查很弱(F1 不到 0.3)」與「已抓到七到八成 bug」可以同時成立:前者把人類評論當真值(含風格與主觀要求、又不完整),後者只問已確認的 bug,且只算召回。寫報告時不可把兩邊的數字放在同一欄比。
- 2026 年的快速上升要小心解讀:CRBugBench 五個月升 24 個百分點,但公開 repo 可能在訓練資料內;內部 repo 同向上升、幅度較小,才是較可信的下界。
- 代理主要輸在「看到了卻判錯」(有打開檔 95.6%→命中 56.2%),不是沒看到。這和 SecPRBench 的 68%(見資安節)是同一訊號。

### Gaps
- CRBugBench、SecPRBench 都沒量在一般變更上的精確度;目前沒有同時給高召回與可信精確度的公開基準。
- CR-Bench 的召回原始數字我沒抽到表格,只取得訊噪比(5.11、1.95、0.91)。
- GitHub ReviewBench 本輪沒有重讀,沿用迴圈工程篇紀錄。

## 舊指標為何失效?什麼取代了它?LLM 判官評分有多可靠?

### Takeaway
BLEU 不只是粗糙,在 SWR-Bench 上與人類偏好呈負相關。取代者分三類:可執行預言、對「已確認缺陷」的命中判定、下游效果。LLM 判官在「這條發現是否命中這個具體參考答案」上可達人類水準(κ 0.75–0.89),但判「有不有用」只有中等,判「這條評論對不對」時幾乎全部放行。

### Cited Findings
**舊指標的問題**
- [已知] BLEU 與人類偏好的 Cohen's κ 為 −35 到 −41(論文以 ×100 尺度報告),比亂猜還差;文字相似度與 F1 反向相關,因為它反映格式而非審查內容 — [2509.01494](https://arxiv.org/abs/2509.01494)
- [新] 綜述 99 篇論文(前 LLM 時期 58、LLM 時期 41),LLM 時期近 60% 資料集集中在同儕審查生成,仍常用 BLEU — [2602.13377](https://arxiv.org/abs/2602.13377)
- [新] 真值本身有洞:原始 PR 資料功能性變更不到 15%,多是文件與風格 — [2509.01494](https://arxiv.org/abs/2509.01494);AACR-Bench 用「AI 輔助、專家驗證」後缺陷覆蓋增加 285%,表示人類評論嚴重不完整 — [2601.19494](https://arxiv.org/abs/2601.19494);CRBugBench 指以評論為真值會「人為懲罰原審者漏掉的有效發現」 — [2610.13668](https://arxiv.org/abs/2610.13668)
- [新] 訓練資料有雜訊:LLM 清理偵測有效評論精確度 66–85%(MSR 2025) — [2502.02757](https://arxiv.org/abs/2502.02757);另有研究認為問題在任務定義本身,不只是資料髒(ICSME 2026) — [2607.25851](https://arxiv.org/abs/2607.25851)

**取代方案**
- [新] 可執行測試(c-CRAB):把人類評論轉成測試,評「依這則審查修改後是否通過」;標註者同意 84%。限制在論文自己的例子裡:測試要求 `TextField`,工具建議了另一種有效修法也算失敗 — [2603.23448](https://arxiv.org/abs/2603.23448)
- [新] 重跑 PoC(CyberDual):以審查後的程式碼能否再被利用定勝負,完全不用判官,「代理報告無法作弊」 — [2610.34435](https://arxiv.org/abs/2610.34435)
- [新] 下游效果:SWE-Review 量審查回饋能否提升修復率 — [2607.06065](https://arxiv.org/abs/2607.06065);2606.01859 量能否誘導出與人相同的修改 — [2606.01859](https://arxiv.org/abs/2606.01859)
- [新] 檢查清單覆蓋:Sphinx,自述比基線高最多 40% — [2601.04252](https://arxiv.org/abs/2601.04252)
- [新] 歸因式評分:MalPR-Bench 把判決對、目標漏洞認對、證據驗對分開計,三者都對才算「可歸因的擋下」 — [2608.25730](https://arxiv.org/abs/2608.25730)
- [新] 突變注入的代價:同一批模型在合成樣本 F1 0.847,真實 PR 0.066 — [2606.15689](https://arxiv.org/abs/2606.15689)

**LLM 判官的可靠度**
- [已知] SWR-Bench 100 份報告:Hit 判定 κ 70.6–86.7(人對人、人對 LLM、LLM 對 LLM 皆含);多數決只有邊際改善。LLM-Hit-Judge 與人類偏好 κ 52.8–62.0,與人對人 56.3–62.6 同級;打分型 LLM-Score-Judge 明顯較低 — [2509.01494](https://arxiv.org/abs/2509.01494)
- [新] CRBugBench:三家判官多數決,人對 LLM κ=0.89(n=40),Fleiss κ=0.95 — [2610.13668](https://arxiv.org/abs/2610.13668)
- [已知] SWE-PRBench 判官 κ=0.75 — [2603.26130](https://arxiv.org/abs/2603.26130)
- [新] SecPRBench:Opus 5.5 與 Sonnet 4.6 在 2,143 份非空報告上一致 96.9%;人工抽查 25 筆一致樣本全對,25 筆分歧裡 21 筆支持 Opus。分歧樣本刻意過抽,不能當整體準確率 — [2610.33509](https://arxiv.org/abs/2610.33509)
- [新] 判「有用與否」較差:對 Beko 開發者標籤,G-Eval 與 LLM 判官一致率約 0.44–0.62,隨模型與量表形式變動 — [2604.24525](https://arxiv.org/abs/2604.24525);HalluJudge 判幻覺 F1 0.85,但只有 67% 與開發者偏好一致 — [2601.19072](https://arxiv.org/abs/2601.19072)
- [新] **判「評論對不對」近乎放行**:CRJudgeBench(1,199 例,359 例測試),所有基線對「不可信評論」的召回只有 2.31%–20.77%,可信評論召回 87.77%–98.69%;可信占 63.79%,但每個模型至少把 85.52% 判為可信,Claude-Opus-5 與 GPT-5.5 達 94.99% — [2609.37216](https://arxiv.org/abs/2609.37216)
- [新] 判官可被鑽:一般最佳 N 選一搜尋對照常設定的判官,96 個候選接受 90 與 93 個,全部敗在隱藏測試;判官甚至指出有缺陷的那行並據以給滿分。「先自己解、再比對」降到 0/96,但第二題反而更糟:防線只是從候選移到判官自己的答案 — [2609.00088](https://arxiv.org/abs/2609.00088)
- [新] 清單式評分:固定判官與輸出,改評分表內容能把正確輸出的通過率從 2% 推到 100%,換判官模型只動幾個點;讓模型自審評分表會漂向自己的標準 — [2610.24971](https://arxiv.org/abs/2610.24971)
- [新] 判決與診斷會脫鉤:SecPRBench 的控制組分析指出,若只要發現落在根因檔就算,會接受 74.9% 的已修復變更掃描,高於實際給分的 63.3% — [2610.33509](https://arxiv.org/abs/2610.33509)

### Inferences
- 判官可靠度取決於問題形狀:有具體參考答案的是非題接近人類;開放的「有用嗎」受情境影響;「這條主張對嗎」的預設偏向相信。
- 「多數決判官」對已高一致的命中題幾乎沒增益,把成本投在參考答案品質比投在判官數量划算(依 SWR-Bench 與 2610.24971 的方向推論)。
- 可執行預言不是萬能:c-CRAB 把有效但不同的修法算失敗,所以它的 20–32% 是下界。

### Gaps
- 判官對「遺漏型」代碼缺陷的鑑別力,目前只有醫療病歷與詞表類實驗,沒有代碼上的直接量測(見下節)。
- 2610.13303 只讀到摘要前段與標題,其結論未逐項核對,本篇不引數字。

## 依缺陷類型的偵測率差多少?遺漏與做錯的差別已知多少?

### Takeaway
最穩定的軸不是「邏輯 vs 資安」這類標籤,而是**證據在不在 diff 裡**:看得到就容易,要跨檔、要專案知識、要執行期資訊就急遽下降。遺漏型在代碼上的直接量測仍少,現有資料指向「擋得住但說不清」。

### Cited Findings
- [新] 可見性最強:bug 在 diff 內可見 OR=2.621;diff 大 OR=0.591;修 bug 型 PR OR=0.521;易用性類 OR=0.454;高嚴重度較易抓 OR=1.906 — [2610.13668](https://arxiv.org/abs/2610.13668)
- [新] 跨檔:SecPRBench 根因 1 個檔的召回 69.6%,5 個以上 38.5%;控制 diff 大小後仍存在(2–5 檔 diff:76.5%→55.1%) — [2610.33509](https://arxiv.org/abs/2610.33509)
- [新] AACR-Bench:非代理方法普遍 Diff>File>Repo 遞減;代理模式反向(DeepSeek-V3.2 由 diff 4.28% 升到 repo 8.00%),但絕對值極低 — [2601.19494](https://arxiv.org/abs/2601.19494)
- [新] CodeRabbit 在所需證據位於改動檔內時認出 16/24 目標,證據在改動檔外時 0/7 — [2608.25730](https://arxiv.org/abs/2608.25730)
- [新] 邏輯 vs 記憶體:八個代理平均,邏輯錯誤 51.5%、記憶體安全 73.1% — [2610.33509](https://arxiv.org/abs/2610.33509)
- [新] 2606.15689:資安約 70% 召回(「已商品化」),邏輯 Haiku 24.5%、Sonnet 19.6%,**效能問題(N+1、無界查詢)四個模型 0%、一個 4.5%** — [2606.15689](https://arxiv.org/abs/2606.15689)
- [已知] SWR-Bench v2 表 6(PR-Review 平均):Logic 精確度 17.28/召回 54.60/F1 26.20;Interface 16.97/40.83/23.55;Solution Approach 12.66/19.15/15.21;Textual 15.85/13.03/14.30 — [2509.01494](https://arxiv.org/abs/2509.01494)
- [新] c-CRAB 可維護性通過率 7.9–27.0% — [2603.23448](https://arxiv.org/abs/2603.23448)
- [新] 併發:SecPRBench 十個併發目標,沒有任何直接審查代理找到超過 6 個;Defending Code 找齊 10 個,靠的是廣度(每份報告十幾條發現) — [2610.33509](https://arxiv.org/abs/2610.33509)。其他基準沒有抽到併發類分項數字
- [已知] 多輪:誤報最大宗是狀態時序錯置 32.5%、過度審查 27.8%;漏報是跨輪遺忘 25.1%、長距依賴 23.4%、語意盲點 22.3%;最常見狀態錯誤是把已解決判成新問題 38.29% — [2608.27442](https://arxiv.org/abs/2608.27442)
- [已知] 多缺陷同檔:SWR-Bench 指單 PR 問題數增加時召回急降、精確度持平 — [2509.01494](https://arxiv.org/abs/2509.01494)
- [新] 注入 1/3/5/9 個漏洞的基準顯示 F1 最多掉 40%,Python 複雜檔召回低於 0.30(注入式、舊模型) — [2512.22306](https://arxiv.org/abs/2512.22306)

**遺漏 vs 做錯**
- [新] MalPR-Bench 14 個「缺席型」(該有的檢查沒加)PR:兩系統都擋下 9/14,但 PRGuard 認出 9 個目標、CodeRabbit 只有 3 個 — [2608.25730](https://arxiv.org/abs/2608.25730)
- [已知] 判官對遺漏的成對鑑別力 0.50–0.63(增改為 0.79–0.94),是醫療病歷,不是代碼;代碼上沒做這個實驗 — [2608.31016](https://arxiv.org/abs/2608.31016);[2608.01000](https://arxiv.org/abs/2608.01000)
- [新] 反向訊號:在模型已正確判為有錯的樣本裡,Missing Logic 的原因說明最容易對上(81% 吻合、17% 不吻合),Excess Logic 55% 不吻合。這量的是「原因描述」,不是偵測率,且題目為 HumanEval/MBPP/QuixBugs — [2603.00539](https://arxiv.org/abs/2603.00539)
- [新] 倖存攻擊的特徵之一是**拿掉上游修補帶的回歸測試**;沒差別的是移除防護、崩潰類型、窗口長度 — [2610.34435](https://arxiv.org/abs/2610.34435)
- [新] 跨提交漏洞:15 個 CVE 中,逐提交的傳統 SAST 只抓 13%,累積掃描 27%(n 很小,且是 Semgrep/Bandit,不是 LLM) — [2604.21917](https://arxiv.org/abs/2604.21917)
- [新] 設計約束:SWE-bench 系列上通過測試的修補,完全符合設計約束的不到一半,功能正確與設計符合幾乎無關 — [2604.05955](https://arxiv.org/abs/2604.05955)

### Inferences
- 「模型看得出缺席的東西」與「看不出」的矛盾,多半是問法差異:給定已知有錯時,遺漏最好解釋;開放掃描時,缺少的東西沒有可錨定的 token。MalPR 的 9 vs 3 支持後者。
- 真正要補的是 diff 外證據,不是更多鏡頭:證據在改動檔外時 0/7,比任何類別差異都大。
- 依類別配資源時,效能、可用性、設計取捨是 LLM 明顯的弱區,應改用確定性規則或人(2606.15689 與 CRBugBench 同向)。

### Gaps
- 我沒有找到專門量「代碼審查中遺漏型缺陷」偵測率的 2026 受控研究;併發類只有 n=10 的分項。Augment 指 CWE-862 無模型能處理的說法只見於廠商文,原始論文未打開,不採用。

## 什麼脈絡有幫助、什麼有害?有沒有受控實驗顯示多給脈絡反而變差?

### Inferences
- 研究員自算(Snyk):額外發現 49.7% 只出現一次、13.7% 五次都在;對上參考者 84.8% 五次都在。若要用重複率過濾誤報,這是目前唯一的直接資料,且來自廠商。

- 對 Lumos 評測集的含意:21 題規模解不出小差距(依 2610.04433 的量級推論),比較配置時至少要每題重跑並報區間。

### Gaps
- 專門量「代碼審查重跑一致性」的大樣本研究仍少;Snyk 是廠商、JavaScript、只有 5 次。CRBugBench 與 SecPRBench 都未報重跑變異。

## 有哪些複現失敗、負面結果與資料洩漏導致的灌水?

### Takeaway
最強的負面訊號來自標籤與資料本身:主流漏洞資料集約四成「有漏洞」標籤未獲確認(19.0% 被修正、22.3% 未決),修正後所有模型掉分。「訓練污染」這個常見疑慮反而被幾篇研究打了折扣。作者自我撤回的案例也開始出現,值得當作可信度訊號。

## 哪些新證據與既有調研的說法衝突或需要修正?

### Takeaway
沒有推翻大架構,但有五處需要改口:「多給脈絡有害」太絕對;「跨家族一定更好」要加能力條件;合成植入評測被高估;遺漏盲點在代碼上仍未直接證實;LLM 辯方的方向性偏誤比舊篇寫的更嚴重。

### Cited Findings
1. **迴圈工程篇挑戰 10、其他世界解「給更多脈絡反而全部變差」**:過於絕對。SWE-PRBench 仍成立,但 ContextCRBench(+72.17%)、2606.01859(+3.76pp)、CL4SE 同時顯示有益;正確敘述是「未挑選的程式碼傷、意圖文字與按需取得幫」 — [2511.07017](https://arxiv.org/abs/2511.07017);[2606.01859](https://arxiv.org/abs/2606.01859);[2603.26130](https://arxiv.org/abs/2603.26130)
2. **迴圈工程篇第 7 條、挑戰 4「多模型比同家多席好」**:證據混合。CRBugBench 表 3 異模型 Ensemble@3 @5 為 +1.2/+3.8,**同模型** Ensemble@3 為 +2.4/+4.6,跨模型沒有贏;2606.15689 聯集傷 F1;但 CyberDual 69%、Song 56.7 vs 42.7 支持互補。2607.21656 甚至顯示 Codex 審 Claude 會傷 — [2610.13668](https://arxiv.org/abs/2610.13668);[2606.15689](https://arxiv.org/abs/2606.15689);[2610.34435](https://arxiv.org/abs/2610.34435);[2610.01471](https://arxiv.org/abs/2610.01471);[2607.21656](https://arxiv.org/abs/2607.21656)
3. **迴圈工程篇候選 11、評測篇機制覆蓋(離線植入)**:方向對,但突變注入高估嚴重,要用真缺陷回植,不是合成變異 — [2606.15689](https://arxiv.org/abs/2606.15689);圖譜 canary-audit 已引此篇,結論一致。
4. **迴圈工程篇第 16 條「判官抓不到漏掉的」**:沿用時要標「代碼未直接量」。2603.00539 Missing Logic 81% 是反向訊號(但條件不同);MalPR 9 vs 3 支持漏看診斷 — [2603.00539](https://arxiv.org/abs/2603.00539);[2608.25730](https://arxiv.org/abs/2608.25730)
5. **迴圈工程篇挑戰 1(折入率 98.8%)與挑戰 11(辯方沒消融)**:CRJudgeBench 給出新解釋:前沿模型對不可信評論召回 2.31–20.77%,預設放行。LLM 對發現的判斷本身可能就是 98.8% 的成因之一,增強「折入率不是精確率訊號」 — [2609.37216](https://arxiv.org/abs/2609.37216)
6. **迴圈工程篇第 14 條 Lumos 禁席間互辯**:仍被支持;2608.18167 假共識、2604.19049 十席全錯同向。不過 2608.18167 也顯示結構化反對能提升,不是全無用 — [2608.18167](https://arxiv.org/abs/2608.18167)
7. **迴圈工程篇挑戰 6「嚴重度最不穩」**:要分開看。人與 LLM 對嚴重度四級 κ=0.64,合併兩級 κ=0.90(n=40);自排序 top-3 含 89% 命中。不穩的是細分門檻,不是高低訊號 — [2610.13668](https://arxiv.org/abs/2610.13668)
8. **迴圈工程篇第 18 條 Porter「修後再審不多找到」與挑戰 5**:SWE-Review 的修補迴圈對弱模型大幅提升,但強模型幾乎不動,形狀和 Porter 不是直接反駁,任務也不同 — [2607.06065](https://arxiv.org/abs/2607.06065)
9. **迴圈工程篇第 7 條的「+13.6%」**:本輪沒有獨立複現;只有 GitHub 自報(已被 2026-10-30 更正標示),本篇加入 CRBugBench 的反向數字。
10. **圖譜 Agent 編排篇**:2603.18740 已標 v5 更正,本篇核對無誤;圖譜對 2606.15689 的引用與全文一致。
11. **舊有假設「同模型自審的弱點是偏袒自己」**(若有人這樣寫):2609.30048 顯示模型認不出自己的程式 — [2609.30048](https://arxiv.org/abs/2609.30048)

### Inferences
- 對 Lumos 最值得馬上重看的是第 5 條:處置閘的「折入」與辯方都吃這個偏誤,應優先做反證機械查核(迴圈工程篇候選 2、5)。
- 第 2 條不是說外家沒用,而是外家要用在**強審查者**、用在**難任務**(窗口型),且要量誤拒成本。

### Gaps
- 上述衝突都是跨基準比較,沒有同設定的直接對決;第 5 條是由模擬擾動資料外推到真實折入,需要 Lumos 自己抽查才算成立。
