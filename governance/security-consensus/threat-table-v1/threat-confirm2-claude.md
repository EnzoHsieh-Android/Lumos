## 一、必改

### 必改 1：登成 `admin` 的管理後台畫面，一格 frontend-origin 都長不出來

**定稿原文**：
- 表的 frontend-origin 列，適用入口只寫「`web_page`」。
- 〈誰問什麼〉的盤點規則：「一個功能同時有上傳、下載、匯出、外呼、批次處理或訊息消費這些性質時,每種性質各登一個對應 kind 的入口」，例子是「管理後台的 CSV／ZIP 匯入:登 `admin` 之外另登 `file_upload`」。

**問題**：
- 一個入口只有一個 kind，也不會繼承別的 kind 的題目，這是定稿自己寫的原則（Codex-C#1 的處置理由）。
- 單人專案很常見的管理後台，像伺服器渲染的管理面板或獨立的 admin SPA，作者自然只登 `admin`。
- 盤點規則列舉的「性質」沒有「有瀏覽器畫面」這一項，所以照規則也不會另登 `web_page`。
- 結果是：管理後台不會被問到 frontend-origin 的那幾題，包括不安全的 HTML 插入（DOM XSS）、CSP、點擊劫持、postMessage、瀏覽器儲存放了什麼。
- 管理後台權限最高，偏偏是點擊劫持與 DOM XSS 最值錢的目標。input-injection 只問得到伺服器端輸出到 HTML 的那一段，問不到前端自己用 `innerHTML`／`v-html` 插入的情況。authn-identity 的瀏覽器括號題只管 cookie、CORS、CSRF、跳轉、WebSocket，也不碰這幾項。
- 這不是措辭偏好：照現行規則，這幾個威脅在這種入口上機械地一格都不會出現。`inventory_complete` 也抓不到，因為照規則根本不算漏登。

**改法**（二選一，建議甲，跟定稿現有的「另登」做法一致）：
- **甲**：在〈誰問什麼〉「一個功能兼有多種性質」的例子清單加一項：「管理後台有瀏覽器畫面時:登 `admin` 之外另登 `web_page`,frontend-origin 那一類才問得到 CSP、點擊劫持與不安全的 HTML 插入」。同時在〈對姊妹計劃的連動〉的 `資安風險提問分階段_計劃` 第 7 條，把這句併進 surfaces 的盤點規則。
- **乙**：frontend-origin 的適用入口改成「`web_page`、`admin`」。純 API 的管理入口用 considerations 判不適用。管理入口通常只有少數幾個，180 天重簽的負擔小。

## 三、「不採納／部分採納」的理由是否成立

- **Codex#2 不加 batch**：成立。batch 沒有呼叫進來的人要驗身分，服務帳號的權限歸 authz-object，憑證歸 secrets-mgmt。
- **Codex#4 不加 outbound_call、cli**：成立。費用由觸發外呼的那個入口問（那些入口都在 flow-abuse 清單上），重試風暴已在 outbound 的模板裡。CLI 照「另登」規則落到 batch、file_upload 這些入口。
- **Codex#5、#10、#11 的條件式下限改走護欄或判斷**：成立。閘門的最低種類是每類固定的集合，做不到「宣稱 X 時才多要 Y」。改成另登 `@repo` 護欄，或交給 `category_sufficient` 判斷，是在閘門的能力內。

- **Codex#7 outbound 入口不改「全部」**：成立。每個不外呼的入口都要一列有人簽、180 天到期的 considerations，對單人專案確實太重。改成「使用者給網址的功能必須另登 `outbound_call`」，漏登由 `inventory_complete` 抓。

## 四、有沒有單人專案做不到的下限

前提是「AI 寫程式、人審」（連動第 11 條已列為要寫明的前提）。在這個前提下，表裡沒有單人做不到的下限：

- fault_sensitivity（authz-object、authn-identity）用專案既有的 runner 加 lumos guard kill 就做得到。
- concurrency 可以用 runner 的 junit 並發測試，在本機調低配額的小規模測試即可。
- deployment 與 `manual_check_scope` 都要人，但單人專案裡人本來就是審查人。
- frontend-origin 的 behavior 可以是單元測試檢查回應標頭，不一定要瀏覽器測試基礎設施。

唯一接近做不到的是 **supply-chain 的人工替代**：「紀錄附直接與間接依賴的套件與版本清單、查過的公告來源」。Node 這類專案的間接依賴常有上千個，一個人逐套件查公告不實際。但免費工具（OSV-Scanner）隨時可以裝，所以這是替代路線負擔重，不是下限做不到；不列必改，見建議 4。

## 五、建議（不阻擋）

1. **Claude-C 建議 4（單一請求的資源上限）補一行回頭條件**：「先觀察實際護欄有沒有因此不標 flow-abuse」沒有機械訊號，因為「沒標」本身看不見。建議在〈下限與替代怎麼算〉加一行，例如：`REVISIT:[when-status:Systems/資安威脅類別表=done][by:2027-03-31] 數一次宣稱本文大小、分頁上限、正則逾時這類單一請求上限的護欄裡，有幾條沒標 flow-abuse;有就比照 flow-sequence 拆類`。另外 flow-abuse 的模板只寫「重送、並發或大量操作」，可以補半句「單一請求的大小、分頁筆數、運算量有沒有上限」，讓這題至少問得到。
2. **連動漏了格子數上限的估算**：`資安風險提問分階段_計劃`〈四〉〈規模與上限〉寫的是「九到十一類,約九到十一萬格」，上限是 100000。定稿變成 14 類，authz-object、audit 又各擴到 10 種入口。照原估算的最壞情況（200 個入口、50 個資產，再乘上角色），格子數會更早超過上限，所有格子就只剩計數。建議在連動加一條：重估最壞格子數，必要時調整上限或那段敘述。既有的 REVISIT（2027-01-31 實測）可以順便量這一項。
3. **authn-identity 補「敏感帳號變更要不要重新驗證」**：改密碼、改信箱、改綁定或 MFA 前要不要重新驗證身分，是小型網站最常見的帳號接管路徑（ASVS V6／V7 有這一節）。現在只能從「身分何時可信」間接想到。建議補半句，例如：「改密碼、改 Email、改 MFA 這類敏感變更,要不要先重新驗證身分?」。
4. **secrets-mgmt 的綁定範圍與 supply-chain 的人工替代**：
   - 第 41 行要求 `@repo` 護欄的家只列秘密設定、部署設定、鎖檔，這樣做是對的，可以避免一直重簽。但副作用是：之後 AI 在一支不在綁定裡的原始碼檔寫死一把金鑰時，不論走工具還是走人工核對，舊證據都不會變 stale，閘門照樣放行。定稿只在人工替代那一條把這件事寫進 limitations，工具那條其實也有同樣的限制。
   - 建議在連動第 11 條旁再列一條待辦，請姊妹計劃決定以下兩種做法之一：秘密掃描要求在 CI 每次推送都跑（例如 gitleaks，免費）；或者寫一行 REVISIT，回頭數一次實際漏網的件數。
   - supply-chain 的替代欄可以附註：間接依賴多的專案，實務上走免費的依賴掃描工具。
5. **第 41 行的例子補 crypto-use**：「秘密設定、部署設定、鎖檔這類」沒有涵蓋 crypto-use。crypto-use 真正承擔的檔是做雜湊、加密、驗簽的那幾支模組，建議點名，免得作者照例子只列設定檔，改了加密程式卻不會讓證據變 stale。
