# 06 代碼審與推送(分支要推之前)

| 情境 | 指令 | 結果怎麼讀 | 不用它會怎樣 |
|---|---|---|---|
| 「這批改動風險多高?要不要過審?」 | `lumos pitfalls --diff <merge-base>..HEAD` | `tier: high` → 要過對抗代碼審(`lumos-code-loop` skill),其中必派一席資安席(templates.md §7.8,問閘會擋;工具鏈本 repo:資安席只看三類,見 templates.md §7.8〈工具鏈三類〉;消費專案照舊);standard 派一位審查員加架構對齊、每筆記帳帶 `--round`,light 只派架構對齊席(單源 `lumos-code-loop/SKILL.md`),但**同一份輸出列出的「觸發到的效能檢核題」不看 tier,推送前每題要表態**(下一列)。輸出末段「[架構對齊]」列每支改動檔同層最像的既有檔當對照,逐問三件事(分層依賴 / 命名錯誤處理 / 有沒有第二種做法)——派審查員時一併附上 | pre-push 自己會算,high 沒留痕就擋 |
| 「這次改動觸發了幾題效能檢核,要先交代」 | `lumos pitfalls --diff <範圍> --dispositions-template --carry > /tmp/disp.json`(填 status 留空的題:satisfied 附 evidence `path:line`/`test:<名>`、na 附 reason、todo 附 issue+reason、tension 附 chosen/existing/hazard/suggestion——這題的做法跟鄰居不同、兩席相反時用,不擋、check 印 ⚠ 交人裁;樣板帶 `hint` 的題就是候選)→ `lumos code-loop dispositions /tmp/disp.json [--branch <推送目的分支>]` | 未觸發的題工具已自動記「未觸發」;寫入綁當下版本,改碼後重跑樣板加 `--carry` 只答新題;審查席抓到未觸發題的問題 → `lumos code-loop recall-miss <id> --note` | `code-loop check` 擋(缺表態≠缺審查,訊息分開);`.lumos/config.json` 的 `stack_questions.gate` 可設 all/high-only/off |
| 「審完了/決定不審,要留痕才能推」 | `lumos code-loop pass --note "<審了什麼>"` 或 `lumos code-loop skip --note "<為什麼不審>"` | 留痕綁當下版本;之後再改 code(簿記檔除外)就失效,要重跑。合併請求合進主線時,主線的檢查也認合進來那一側的留痕——條件是分支合併前先跟上主線(合過主線、重記留痕)、合併提交本身不手改;不然主線那邊照擋,要補審或補記 | pre-push 與 CI 都擋 |
| 「我現在推得上去嗎?」 | `lumos code-loop check [--diff … --at-sha … --branch …]` | OK/BLOCKED + 原因,六個獨立判定:有資安登記時安全證據不合格(排最前、不看 tier;沒登記的專案輸出不變)→ 有 e2e 段時 Android 端到端驗收沒過或沒紀錄(不看 tier)→ 受波及合約綁的測試紅(高風險擋;低風險 pre-push 帶 `--bound-tests-advisory` 只提醒)→ 有適用效能檢核題表態不完整(不看 tier)→ 這次改動帶進新的告警(不看 tier)→ high 無審查留痕。不帶旗標是序列早退(先中的先報);帶 `--keep-going` 每一道都判完、每道擋下各印各的,最後多一行 `LUMOS-BLOCKS: <種類,…>`(`--json` 多一個 `blocks` 清單) | pre-push 對每個分支 ref 都呼叫它(2026-09-09 起無條件;2026-10-14 起認得 `--keep-going` 的版本就帶上,一次看到這個 ref 的全部原因) |
| 「推送被『碰到的筆記裡有指不到真測試的綁定』擋下」 | 照它印的改法修那篇筆記(改成真的測試名;測試已刪寫 `[test-gone:名稱]`;作廢的條目把綁定移走)再推;擋不擋看 `.lumos/config.json` 的 `note_shape.test_refs`(沒設是 warn 只提醒、設 block 才擋),只關這組設 warn;誤擋單次 `LUMOS_SKIP_NOTE_SHAPE=1`(留帳) | 碰到的筆記整篇都要乾淨,舊行上的也算;簽出的不是推送終點、或測試檔與設定有沒提交的改動時只提醒、交給 CI | 指不到的 `[test:]` 是假的守衛,讀的人會以為有測試守著 |
| 「推送被 Room 守衛擋下(Android 專案改了 Room 資料庫或 DAO)」 | 照擋下訊息每一條補:升級路徑(`Migration`/`AutoMigration`)、這一版的結構檔(重新編譯後提交 `schemas/<類別>/<版本>.json`)、升級測試(`MigrationTestHelper`)、改到的 DAO 方法用真的 Room(記憶體資料庫)寫測試;手動跑 `lumos room-guard --diff <範圍>` | 升級那半跟主線分岔點比:只存在分支上的版本怎麼改都不擋;DAO 那半只看這次改到的方法,mock 那個 DAO 的測試不算;型別轉換、判不出的升級寫法、`exportSchema = false` 只提醒。只鬆 DAO 那半設 `.lumos/config.json` 的 `room_guard.dao: warn`、整道只提醒 `room_guard.gate: warn`、純快取資料庫列進 `room_guard.allow_destructive`;確定誤擋單次 `LUMOS_SKIP_ROOM_GUARD=1`(留帳) | 升級缺路徑在使用者手機上閃退或清空資料;DAO 只用 mock 測,SQL 寫錯也照綠 |
| 「推送被『資安護欄的證據不合格』擋下,哪一條缺什麼?」 | `lumos security evidence [--commit <sha>] [--json]`(唯讀,跟 `code-loop check` 那一道同一支判定) | 逐條列必驗集合(active 資安護欄)的整體判定、最先要修的代碼與每份證據的判定;沒有資安登記就印「這一道不判」 | 只看到擋下不知道是哪一份證據、哪一個欄位不合格 |
| 「資安護欄的例外、變弱或改成只提醒,要人核可才算數」 | 產生要簽的那一筆 `lumos security approvals payload <type> <target> --signer <principal> --expires-on YYYY-MM-DD --out <檔>`(釘金鑰另帶 `--key <principal>=<公鑰檔>`;例外、人審、修訂、考量、工具清單的內容從 HEAD 那個提交算,要先提交;target:例外 `<護欄 id>#<排序後的 covers_kinds>`、人審 `<護欄 id>#<種類>`、修訂 `<護欄 id>\|<decision_ref>`;考量另帶 `--outcome risk_accepted\|not_applicable`(到期上限照它分 30／180 天)、壓制另帶 `--reason`、內容不從提交算的可用 `--content-file <JSON 檔>`、`--commit <sha>` 改用別的提交算)→ 自己用 `ssh-keygen -Y sign -n lumos-security` 簽 → **在你自己的終端機** `lumos code-loop security-approval-add <檔>` 接進核可鏈(要照抄當場的確認碼);驗整條鏈 `lumos security approvals verify` | 追加前用同一支驗證函式驗過「整條鏈加這一筆」才寫入;非互動或只有一端是終端一律擋(只管這一支指令);鏈跟主線分岔、金鑰已撤或過期、核可日早於前面的筆都不算數 | 手改例外內容(雜湊對不上)閘門照樣不認;繞過這支指令直接把自己簽的一行寫進核可檔,閘門分不出來——依信賴原則屬範圍外(計劃 d19),不要這樣做;把 payload 輸出轉存成檔會多結尾換行、簽章對不上(用 `--out`) |
| 「資安護欄靠故障翻紅當證據,要寫背書」 | 先照 `guard kill` 那一列跑過殺傷力配方,再 `lumos code-loop security-backing <護欄 id> [--supersede]` 把這一版的背書寫進 `docs/.security-backing.jsonl` 並一起提交 | 背書綁程式版本;背書後再改程式就失效、要重跑 | 故障證據判 `backing_missing`,推不上去 |
| 「新增告警閘擋下來,那條是誤報」 | `lumos lint-waive <指紋> --note "<為什麼放行>"`;看放行過什麼 `--list` | 放行綁指紋不綁版本,寫進 `.lumos/lint-waivers.json`(要一起提交)並記一筆治理帳 | 不放行就推不上去;健檢會數這個專案放行了幾條 |
| 「把一個坑固化成每次提交都會跑的規則」 | 規則放 `.lumos/rules/`、會被它抓到的樣本放 `.lumos/rules/samples/`,登記進 `index.json`,再 `lumos rule-check` | 每條規則都要有一支真的翻紅的樣本;沒樣本或樣本不翻紅 rc1 | 沒有會翻紅的樣本的規則可能是死的,跟沒有規則一樣 |
| 「漏網的問題本來哪條規則該抓」 | 記逃逸帳時帶 `--rule <規則id\|none>`;看待辦 `lumos rule-gap` | 列出「標了該抓、但規則還沒寫」的,附漏過幾次 | 逃逸帳只記漏掉了,不標規則就不會長出新守衛 |
| 「這次改動有沒有打破哪條硬合約?」 | `lumos bound-tests --diff <範圍> [--advisory]` | green / red / 沒東西可跑。**紅了是要修測試,不是補審查留痕** | ★2026-09-07 起低風險推送也跑★,紅了印出來記帳但不擋;高風險照舊擋。預設一支一支跑;要同時跑見安裝維運的 `bound_tests.parallel` |
| 「受波及合約的測試真的跑不了(外部 DB 不在)」 | `lumos code-loop check … --skip-bound-tests --note "<為什麼>"` 或 `lumos bound-tests --skip --note "<為什麼>"`;CI 用環境變數 `LUMOS_SKIP_BOUND_TESTS=1` | 留痕進治理帳,被統計(旗標記 `skipped-flag`、環境變數記 `skipped-env`,分開數) | 沒理由拒絕 |

## 筆記內容審:新寫的筆記是不是程式碼推得出來(推送前)

白話:推之前,把這段範圍裡新寫、而且還留著的筆記行一行一行交給一位判定者,問它「這句只看程式碼就能確認嗎」。判成推得出來(CODE)或一半一半(MIXED)的要刪、改,或申訴;判成脈絡(CONTEXT)的才算過。計劃收尾(status 改成 done 或 superseded)那次,整篇再判一次。只防疏忽,不防存心繞過。設計與取捨:[[Projects/筆記內容審_計劃]]。

**★目前還沒接進推送前掛鉤與 CI★**:要等兩家編排者的校準都達標才接。在那之前可以手動跑,結果不會擋推送。

一串做完的順序:
1. **出清單**(判定者跟你同一家,模型工具寫死:claude → opus;codex → 工具裡 Codex 審查席用的那個):
   ```
   lumos note-audit prepare --diff <起點>..<終點> --orchestrator claude|codex
   ```
   超過 150 行會切成多份;每份清單檔開頭有派工詞與要照抄的四行。沒有待審的行就不產生檔。
2. **派判定者**:每份清單派一席(可平行),派工詞就是清單檔整份內容。
   - Claude 編排:Agent、`model: opus`,叫它讀清單檔、照開頭的格式寫報告存檔。
   - Codex 編排:`codex exec -m <清單開頭寫的判定者模型> --sandbox read-only -o <報告檔> - < <清單檔>`(從 repo 目錄裡跑;`-` 叫它從標準輸入讀派工詞)。★別把清單內容貼進 shell 引號裡★:筆記或程式裡的 `$(…)`、反引號會被 shell 執行。
   - 報告開頭四行 `seat:` `provider:` `model:` `prepared:` 照抄清單開頭;之後每行 `內容編號 | CODE|MIXED|CONTEXT | 證據 | 一句理由`。★報告不准改★(跟代碼審席報告同一條規矩)。
3. **記判定**:
   ```
   lumos note-audit record --diff <同一個範圍> --prepared <清單檔> --report <報告> [--report <另一份>]
   ```
   工具照「重的照收、輕的要來源對才收」逐行收:推得出/一半一半一律收;脈絡要報告四行對得上、清單沒被改過、那行的上下文沒變才收。收完印還沒涵蓋的行。
4. **處理判成推得出的行**:刪掉或改成程式碼推不出來的說法(改了就是新的一行,要再 prepare 判);清單裡多兩行「舊句(起點版本已有…)」「只判這次補在句尾的」的,判定只對補上的那段括號:判成推得出或一半一半,★只有推送前★把本機提交 `git reset --soft <範圍起點>` 退回再重提才改得動(拿掉或改寫那段括號);`git commit --amend` 不行(提交前的起點已經有舊括號,改寫後整行照查),已經推上去的括號改寫或刪掉也會整行照查,只能在後面再補一段括號;決策欄還沒推上去可以 `lumos decision-amend <節點> <dN> --field <欄> --text "<新文字>"`,已推上去的只能 `decision-supersede` 翻案。
5. **不服就申訴**(另派一席、席名不同):
   ```
   lumos note-audit prepare --diff <範圍> --orchestrator <同一家> --only <內容編號> …
   lumos note-audit record --diff <範圍> --prepared <新清單> --report <申訴報告> --dispute --disputes <被申訴的判定檔名>
   ```
   申訴只換掉它指名的那一份判定;被好幾份申訴指名時取最重的。
6. **真的來不及**:`lumos note-audit skip --diff <範圍> --note "<理由>"`——只略過從沒被判過的行,會留帳;已判推得出的不能略過。
7. **提交判定檔**:`git add governance/note-verdicts && git commit`。check 只認被推送頂端提交裡的判定檔;判定檔屬於簿記,不會讓代碼審留痕失效,所以順序是先過筆記內容審、再做代碼審留痕、再推。
8. **自己先查一次**:`lumos note-audit check --diff <範圍>`(沒涵蓋 rc1)。誤擋單次 `LUMOS_SKIP_NOTE_AUDIT=1`(留帳);整個專案先只提醒 `.lumos/config.json` 寫 `{"note_audit": {"gate": "warn"}}`,關掉寫 `off`(doctor 會一直唸)。

## 推送前回頭重讀守檔筆記

白話:改了程式、同一次也改了管那支程式的筆記,卻只在後面追加、前面的舊句沒回頭看——這是筆記過期最常見的一種。推送前,把「這次改到的程式檔的家、而且這次也被改過」的每篇筆記,連同這次的程式 diff 交給一位判定者,問「哪幾行被這次改動弄得不成立了」。**本機推送前預設擋**(推送前掛鉤帶 `--gate`,`note_reread.gate` 沒寫就是 block),擋兩層:
- **第一層:還沒對照過這一版程式**——候選沒有來源核對過的已提交紀錄。對照只看程式那一半,而且只認「這條分支對 about_code 那幾支檔的改動」(跟遠端主線的分岔點..頂端):你自己的改動變了(含 rebase 解衝突改到的那一段)、筆記改名、about_code 增減就要重判;主線往前、rebase 上去而你的改動沒變,不用重判——例外是主線改到你那段改動前後三行之內(那三行跟著改動一起算),或改到你那段改動外層那幾行(從改動往上、每一層縮排比它淺的那一行原文都算,只有括號、標點的行(`{`、`):`)跳過——所在函式的簽名、所在類別那一行;所以你那段改動搬到另一個函式裡也要重判,主線改了你那段所在函式的簽名也要重判一次);改筆記不用。算不出分岔點(沒有遠端主線、推的就是主線上的提交)或改動太大、判定者的 diff 會被截掉時,退回看程式在頂端的版本——那時主線帶進別人對同一支程式的改動也算;推送前檢查的時間不夠、沒算出新版指紋的篇,清單會講明「這篇因為逾時沒算出新版指紋,照舊版判」、照擋、記進治理帳(prepare 沒有時間上限、記的是新版紀錄,推送前檢查逾時那次比不到它;逾時看當下機器負載,機器忙時重推可能就會過,一直擋就是改動太大——確定都對照過時用 `LUMOS_SKIP_REREAD_CHECK=1 git push` 單次跳過,跳過記進 docs/.governance-log.jsonl(有進版控,跟著帳本提交送出));推主線(被推的是 `main`、`master` 或主線候選指到的那支分支,不論遠端叫什麼、推的是不是網址)時,分岔點直接用推送給的「遠端那條主線現在的值」算,不看本機的遠端追蹤 ref——那個值本機找不到(還沒 fetch)會擋下、要你先 `git fetch <遠端>`;這時照擋下清單印的 prepare 指令貼(帶同一組 `--push-remote`、`--pushed-ref`),prepare 才跟推送前檢查用同一個分岔點(2026-10-14 前一律照本機主線候選算,由 [[Projects/回頭重讀指紋不因主線前進失效_計劃]] 取代)。推功能分支時分岔點照舊信任本機的遠端追蹤 ref:刻意把它改到藏了改動的提交上,指紋就看不到那段——這屬範圍外天花板(單人本機工具,其他審查同樣信任本機 ref),CI 那一步只印不擋,不會替你補驗。
- **第二層:判定點出的規則類條目沒處理**——判定紀錄點出的行落在摘要的規則類條目(`RULE:`、`★INVARIANT★`、帶 `[test:]` 的摘要條目;標了 `[status:superseded]` 的不算)、那句還在、也沒有照留表態。點出的一般行(正文、`WHY:` 這類沒帶測試綁定的條目)只提醒。
CI 那一步不帶 `--gate`,照舊只提醒、恆回 0。設計與取捨:[[Projects/舊句兩道轉擋_計劃]](原版 [[Projects/守檔筆記對照改動_計劃]])。

一串做完的順序:
1. **出項目檔**(看到推送前的擋下或提醒就照它印的指令貼,或自己先跑):
   ```
   lumos note-audit reread-prepare --diff <起點>..<終點> --orchestrator claude|codex
   ```
   每篇一份項目檔(放 `.lumos/note-audit/`,不進版控、14 天自動清);沒有要對照的筆記就不產生檔。已經有來源核對過的對照紀錄提交進去、對得上這一版程式的那幾篇會略過(跟推送前列的篇數一致),要全部重產加 `--all`。`.lumos` 或 `.lumos/note-audit` 是符號連結時整個拒用(rc2),刪掉連結再跑。
2. **派判定者**:每份項目檔派一席(可平行),派工詞是項目檔裡「---本文---」之後的全部。
   - Claude 編排:Agent、`model: sonnet`(兩次實驗都用它量的),叫它讀項目檔、照派工詞做、把報告存檔。

   - 報告開頭四行 `seat:` `provider:` `model:` `prepared:` 照抄項目檔開頭;最後一段 ```json 區塊是點出的行(`{"line", "quote", "why"}`,沒有就 `[]`)。★報告不准改★:開頭四行對不上的紀錄照寫、標 `provenance_ok: false`,但不算對照,要重派。
3. **記紀錄**:
   ```
   lumos note-audit reread-record --prepared <項目檔> --report <報告>
   ```
   印出點出的行號、原句與理由,寫一份紀錄到 `governance/reread-verdicts/`。
4. **處理點出的行**:照判定改筆記,或確認是誤判就不動。點出的若是規則類條目,推送時會擋——改掉那句,或照留表態:
   ```
   lumos drift ack <節點> <那一條的開頭行號> --kind reread --reason "<為什麼照留>"
   ```
   行號給擋下訊息列的那個(條目開頭;單行 summary 就是 `summary:` 那一行);只有被判定紀錄點出的規則類條目收得下(工作目錄裡要有那份紀錄),表態記下點出它的紀錄指紋。條目之後再改字(例如 `[confirmed:]` 日期)就要重新表態。改筆記不用重新對照(對照只看程式那一半),但改筆記會讓已過的代碼審留痕失效——已過代碼審的推送優先表態。
5. **提交紀錄與表態**:`git add governance/reread-verdicts/<這次寫的那一份> governance/drift-acks.jsonl && git commit`(record、prepare、reread-check 印的提交指令都列具體檔名;不要整個資料夾加,免得夾帶殘檔與別的會談的紀錄)——推送前的檢查只認已提交的紀錄與表態。紀錄與表態檔是簿記,提交它不會讓代碼審留痕失效。
6. **推**。

先後順序:放在筆記內容審之前(照點出的行改筆記會產生新寫的行,筆記內容審要判的是改完的版本;筆記內容審目前還沒接線,接線後照這個順序)、代碼審留痕之前(改筆記會讓留痕失效)。照留表態跟存量漂移共用 `drift ack` 與 `governance/drift-acks.jsonl`,種類是 `reread`。誤擋單次略過 `LUMOS_SKIP_REREAD_CHECK=1 git push`(只管本機;跳過記進 docs/.governance-log.jsonl(有進版控,這次推送不帶它、跟著帳本提交送出);CI 那一步只印不擋);判不了(git 失敗、逾時、判定紀錄讀不懂)在 block 時也擋,同一個略過寫法。沒有 Claude/Codex 環境、或程式碼不能送外部模型的專案,在 `.lumos/config.json` 寫 `{"note_reread": {"gate": "warn"}}`(只提醒)或 `"off"`(不跑)——要提交進被推的提交才算;設定檔不在簿記清單,提交它會讓已過的代碼審留痕失效。

消費專案的 CI:`lumos update` 不會改你的 CI 設定檔。要 CI 也提醒,加一步直接呼叫 `lumos note-audit reread-check --diff "$BEFORE..$SHA" --push-remote origin --pushed-ref "$GITHUB_REF"`——不帶 `--gate` 時它在任何情況都回 0,★不需要 `continue-on-error` 或 `|| true`★(工具鏈自己的 CI 多加了這兩道保險;專案若有「接線不准吞錯」的守衛測試,照它的規矩不加即可,rtb 2026-10-01 就是這樣接的)。CI 不要帶 `--gate`:合併後主線用整個 PR 的累計範圍重算,候選跟作者本機看到的不同;CI 通常沒有本機 main、也可能是淺層 clone,算出的分岔點可能不同或算不出而退回看頂端版本,指紋跟著不同,會誤擋(只印時只是多列)。


## 修訂輪核對修補副作用

上一輪修完、派下一輪前，先按 `lumos-design-loop/templates.md` §3.1 準備修補差異與版本來源，再附三問鏡頭。沿用 `lumos loop fix-check <迴圈> --round <上一輪> --json` 的結果核對版本；它驗修後指定測試，不自動證明新問題由修復造成。起點不明、材料不可得或測試未執行都保留原因，不能填成沒有回歸。詳細做法只在 §3.1 維護。

動手修前先列同一問題的全部出處，見§3.1第0步〈先列出處清單再修〉。

動手修前的根因組配對、保留候選選法與未判定處理，同見§3.1第0步；原問題通過不代表保留案例通過。這是人工流程，既有修正關卡仍驗修後指定測試。

修補與重構的可執行分段點、拆不開的判讀與整理提交後重驗，亦見§3.1第0步；不增加PR或審查輪。

高風險保留案例的抓錯能力抽查、原版／錯誤版／還原對照、weak與真正失敗原因判讀，亦見§3.1第0步；不以CLI成功碼或人工probe充作正式合約背書。

同類提醒與同根因／修補因果的區分、prior兩欄填法，同見§3.1第0步；粗分類相同不證前次修補失敗。

跑滿回顧的修補因果分類與未知處理見共用範本§9；形式檢查不代替兩版案例核對，不挪回顧族別為regression_set。

## 離線比較審查收斂（Claude／Codex 共用）

使用者要比較審查流程、或要把跑滿回顧整理成後續評測時，先用 `lumos loop retro-stats --json` 看回顧；回顧族別是線索，不證明修補因果。再到 **Lumos 工具鏈來源 repo** 讀 `governance/eval/review_convergence.md`；它不是每個消費專案都自帶的 CLI，也尚未接每週排程。來源 repo 可由 `LUMOS_HOME` 或預設 `~/harness/lumos-toolchain` 定位；確認檔案存在與版本，不安裝缺少的依賴或自行替專案開排程。

在工具鏈來源 repo 執行（資料路徑替換成目標專案的絕對路徑，JSON 輸出另存圖譜外的評測目錄）：

```sh
python3.14 governance/eval/review_convergence.py cohort /絕對路徑/專案/docs/.canary-log.jsonl
python3.14 governance/eval/review_convergence.py template code-你的題目
python3.14 governance/eval/review_convergence.py compare /絕對路徑/manifest.json /絕對路徑/trials.jsonl --receipts /絕對路徑/receipts
```

`cohort` 包括正常與跑滿輪編號，不能只挑難題；`template` 的 null 是待核對欄位，不填猜測。人工核對根因群組、隔開訓練與保留案例、固定版本／模型／判準／環境／兩組流程與重複次數後，才準備 trial 原始收據。完整欄位與上限以同目錄說明為單源。

這三個入口只讀資料並印 JSON，**不執行模型、測試或驗收**；版本與 SHA 只核對宣告一致，不能證明它真的跑過。先看原問題修復、既有行為保留與新增缺陷，再看可比較的輪數及完整成本；缺件、未判定、無效收據要保留未知，不能補零或選最好一場。將來源版本、資料指紋、分母與未知範圍寫進驗證紀錄，沒有成對執行證據就不能宣布收斂改善。
