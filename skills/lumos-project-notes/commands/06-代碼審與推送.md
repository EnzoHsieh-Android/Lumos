## 筆記內容審:新寫的筆記是不是程式碼推得出來(推送前)

白話:推之前,把這段範圍裡新寫、而且還留著的筆記行一行一行交給一位判定者,問它「這句只看程式碼就能確認嗎」。判成推得出來(CODE)或一半一半(MIXED)的要刪、改,或申訴;判成脈絡(CONTEXT)的才算過。計劃收尾(status 改成 done 或 superseded)那次,整篇再判一次。只防疏忽,不防存心繞過。設計與取捨:[[Projects/筆記內容審_計劃]]。

**★目前還沒接進推送前掛鉤與 CI★**:要等兩家編排者的校準都達標才接。在那之前可以手動跑,結果不會擋推送。

一串做完的順序:
1. **出清單**(判定者跟你同一家,模型工具寫死:claude → opus;codex → 工具裡 Codex 審查席用的那個):
   ```
   lumos note-audit prepare --diff <起點>..<終點> --orchestrator claude|codex
   ```
   超過 150 行會切成多份;每份清單檔開頭有派工詞與要照抄的四行。沒有待審的行就不產生檔。
2. **派判定者**:每份清單派一席(可平行),派工詞就是清單檔整份內容。
   - Claude 編排:Agent、`model: opus`,叫它讀清單檔、照開頭的格式寫報告存檔。
   - Codex 編排:`codex exec -m <清單開頭寫的判定者模型> --sandbox read-only -o <報告檔> - < <清單檔>`(從 repo 目錄裡跑;`-` 叫它從標準輸入讀派工詞)。★別把清單內容貼進 shell 引號裡★:筆記或程式裡的 `$(…)`、反引號會被 shell 執行。
   - 報告開頭四行 `seat:` `provider:` `model:` `prepared:` 照抄清單開頭;之後每行 `內容編號 | CODE|MIXED|CONTEXT | 證據 | 一句理由`。★報告不准改★(跟代碼審席報告同一條規矩)。
3. **記判定**:
   ```
   lumos note-audit record --diff <同一個範圍> --prepared <清單檔> --report <報告> [--report <另一份>]
   ```
   工具照「重的照收、輕的要來源對才收」逐行收:推得出/一半一半一律收;脈絡要報告四行對得上、清單沒被改過、那行的上下文沒變才收。收完印還沒涵蓋的行。
4. **處理判成推得出的行**:刪掉或改成程式碼推不出來的說法(改了就是新的一行,要再 prepare 判);清單裡多兩行「舊句(起點版本已有…)」「只判這次補在句尾的」的,判定只對補上的那段括號:判成推得出或一半一半,★只有推送前★把本機提交 `git reset --soft <範圍起點>` 退回再重提才改得動(拿掉或改寫那段括號);`git commit --amend` 不行(提交前的起點已經有舊括號,改寫後整行照查),已經推上去的括號改寫或刪掉也會整行照查,只能在後面再補一段括號;決策欄還沒推上去可以 `lumos decision-amend <節點> <dN> --field <欄> --text "<新文字>"`,已推上去的只能 `decision-supersede` 翻案。
5. **不服就申訴**(另派一席、席名不同):
   ```
   lumos note-audit prepare --diff <範圍> --orchestrator <同一家> --only <內容編號> …
   lumos note-audit record --diff <範圍> --prepared <新清單> --report <申訴報告> --dispute --disputes <被申訴的判定檔名>
   ```
   申訴只換掉它指名的那一份判定;被好幾份申訴指名時取最重的。
6. **真的來不及**:`lumos note-audit skip --diff <範圍> --note "<理由>"`——只略過從沒被判過的行,會留帳;已判推得出的不能略過。
7. **提交判定檔**:`git add governance/note-verdicts && git commit`。check 只認被推送頂端提交裡的判定檔;判定檔屬於簿記,不會讓代碼審留痕失效,所以順序是先過筆記內容審、再做代碼審留痕、再推。
8. **自己先查一次**:`lumos note-audit check --diff <範圍>`(沒涵蓋 rc1)。誤擋單次 `LUMOS_SKIP_NOTE_AUDIT=1`(留帳);整個專案先只提醒 `.lumos/config.json` 寫 `{"note_audit": {"gate": "warn"}}`,關掉寫 `off`(doctor 會一直唸)。

## 推送前回頭重讀守檔筆記

白話:改了程式、同一次也改了管那支程式的筆記,卻只在後面追加、前面的舊句沒回頭看——這是筆記過期最常見的一種。推送前,把「這次改到的程式檔的家、而且這次也被改過」的每篇筆記,連同這次的程式 diff 交給一位判定者,問「哪幾行被這次改動弄得不成立了」。**只提醒、不擋**:推送前掛鉤與 CI 會列出還沒對照過的筆記,忽略照推也可以。設計與取捨:[[Projects/守檔筆記對照改動_計劃]]。

一串做完的順序:
1. **出項目檔**(看到推送前的提醒就照它印的指令貼,或自己先跑):
   ```
   lumos note-audit reread-prepare --diff <起點>..<終點> --orchestrator claude|codex
   ```
   每篇一份項目檔(放 `.lumos/note-audit/`,不進版控、14 天自動清);沒有要對照的筆記就不產生檔。已經有對照紀錄提交進去、對得上這一版程式的那幾篇會略過(跟推送前提醒列的篇數一致),要全部重產加 `--all`。`.lumos` 或 `.lumos/note-audit` 是符號連結時整個拒用(rc2),刪掉連結再跑。
2. **派判定者**:每份項目檔派一席(可平行),派工詞是項目檔裡「---本文---」之後的全部。
   - Claude 編排:Agent、`model: sonnet`(兩次實驗都用它量的),叫它讀項目檔、照派工詞做、把報告存檔。
   - Codex 編排:照上一節筆記內容審的派法(`codex exec -m <項目檔開頭的判定者模型> --sandbox read-only -o <報告檔> - < <項目檔>`,從標準輸入讀、不把內容貼進 shell 引號);準度沒量過。
   - 報告開頭四行 `seat:` `provider:` `model:` `prepared:` 照抄項目檔開頭;最後一段 ```json 區塊是點出的行(`{"line", "quote", "why"}`,沒有就 `[]`)。★報告不准改★。
3. **記紀錄**:
   ```
   lumos note-audit reread-record --prepared <項目檔> --report <報告>
   ```
   印出點出的行號、原句與理由,寫一份紀錄到 `governance/reread-verdicts/`。
4. **照點出的行改筆記,或確認是誤判就不動**。這一版不用表態;改筆記不用重新對照(對照只看程式那一半)。
5. **提交紀錄**:`git add governance/reread-verdicts && git commit`——推送前的提醒只認已提交的紀錄。紀錄是簿記,提交它不會讓代碼審留痕失效。
6. **推**。

先後順序:放在筆記內容審之前(照點出的行改筆記會產生新寫的行,筆記內容審要判的是改完的版本;筆記內容審目前還沒接線,接線後照這個順序)、代碼審留痕之前(改筆記會讓留痕失效);跟存量漂移的表態沒有相依。不想要這個提醒的專案在 `.lumos/config.json` 寫 `{"note_reread": {"gate": "off"}}`;單次不跑 `LUMOS_SKIP_REREAD_CHECK=1`(只管本機,會留帳)。

消費專案的 CI:`lumos update` 不會改你的 CI 設定檔。要 CI 也提醒,加一步直接呼叫 `lumos note-audit reread-check --diff "$BEFORE..$SHA" --push-remote origin --pushed-ref "$GITHUB_REF"`——它在任何情況都回 0,★不需要 `continue-on-error` 或 `|| true`★(工具鏈自己的 CI 多加了這兩道保險;專案若有「接線不准吞錯」的守衛測試,照它的規矩不加即可,rtb 2026-10-01 就是這樣接的)。


## 修訂輪核對修補副作用

上一輪修完、派下一輪前，先按 `lumos-design-loop/templates.md` §3.1 準備修補差異與版本來源，再附三問鏡頭。沿用 `lumos loop fix-check <迴圈> --round <上一輪> --json` 的結果核對版本；它驗修後指定測試，不自動證明新問題由修復造成。起點不明、材料不可得或測試未執行都保留原因，不能填成沒有回歸。詳細做法只在 §3.1 維護。

動手修前的根因組配對、保留候選選法與未判定處理，同見§3.1第0步；原問題通過不代表保留案例通過。這是人工流程，既有修正關卡仍驗修後指定測試。

修補與重構的可執行分段點、拆不開的判讀與整理提交後重驗，亦見§3.1第0步；不增加PR或審查輪。

高風險保留案例的抓錯能力抽查、原版／錯誤版／還原對照、weak與真正失敗原因判讀，亦見§3.1第0步；不以CLI成功碼或人工probe充作正式合約背書。

同類提醒與同根因／修補因果的區分、prior兩欄填法，同見§3.1第0步；粗分類相同不證前次修補失敗。

跑滿回顧的修補因果分類與未知處理見共用範本§9；形式檢查不代替兩版案例核對，不挪回顧族別為regression_set。
