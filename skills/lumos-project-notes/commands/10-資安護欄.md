# 資安護欄：什麼時候登記、怎麼登記、怎麼讓推送閘判合格

白話：資安護欄是「別人不該做到的事，系統擋得住」的一條主張，例如「別人不能付款我的訂單」。登記在功能筆記裡之後，`lumos security list` 列得出來，推送閘會要求它拿出真的跑過的工具結果。**沒登記的專案，推送閘這一道整個不判**——不登記，等於這條線沒開。

範例取自 order-demo 實際判過合格的兩條護欄（付款、取消的所有權）；欄位完整規則的單一來源是程式（`lumos security evidence` 的擋下訊息會講缺哪一欄），本篇只寫最常用的部分。

## 一、什麼時候要登記

計劃或改動碰到下面任一種，就要先問「哪些事別人不該做到」，有答案就登記成護欄：

- 登入、身分、工作階段
- 權限：誰能看、誰能改別人的資料（例如別人的訂單、別人的檔案）
- 付款、金額、點數
- 個資或敏感資料的讀取、匯出
- 檔案上傳、下載
- 對外呼叫、webhook 進來的請求
- 管理後台、秘密與金鑰設定

**資安護欄還是業務合約**：被拿掉的後果是「被攻擊」（別人動了我的單）→ 資安護欄；被拿掉的後果是「帳不對」（取消沒回補庫存）→ 業務合約（`★INVARIANT★`）。兩者分開登記，不要同一條寫兩邊。

時機：寫計劃時就登記成「候選」（不擋推送）；證據備齊再改成「生效」（推送閘開始判）。

## 二、登記護欄（必做）

在負責那個功能的 Systems 筆記正文裡，加一塊圍欄。規則：開頭那行整行恰好是三個反引號加 `lumos-security-v1`、從行首開始；結尾整行恰好三個反引號；一篇最多一塊；內容是嚴格 JSON（不准重複鍵、不准沒列的欄位）。

```lumos-security-v1
{
 "schema_version": 2,
 "controls": [
  {
   "id": "OD-01",
   "revision": "2026-10-20",
   "concerns": ["security"],
   "source": {
    "kind": "requirement",
    "claim": "付款只能動自己的訂單:別人付款我的訂單一律回 404 ORDER_NOT_FOUND、訂單與庫存不寫",
    "decision_ref": "Projects/訂單下單_計劃#d13"
   },
   "lifecycle": "candidate",
   "assets": ["order"],
   "surfaces": ["orders-pay"],
   "scope": "付款端點的擁有者檢查",
   "trust_boundary": "HTTP 請求進服務端",
   "enforcement": "PayOrder 在鎖住訂單後呼叫訂單聚合的 requireOwnedBy",
   "legitimate_control": "A 付款自己的待付款單成功(ownerPaysOwnPendingOrder)",
   "abuse_case": "B 付款 A 的待付款、已付款、已取消單都回 404 且不寫入",
   "status_reason": "還沒收證據",
   "owner": "enzo",
   "revalidate_when": "付款入口、所有權判斷或錯誤碼對照改變",
   "required_evidence": ["behavior", "fault_sensitivity", "review"],
   "evidence_refs": [
    {"kind": "behavior", "node": "Verification/2026-10-20_所有權安全證據閘收證.md"},
    {"kind": "fault_sensitivity", "node": "Verification/2026-10-20_所有權安全證據閘收證.md"},
    {"kind": "review", "node": "Verification/2026-10-20_所有權安全證據閘收證.md"}
   ],
   "reported_status": "untested",
   "exception": null,
   "threat_categories": ["authz-object"],
   "threat_table_version": 1
  }
 ]
}
```

幾個最容易寫錯的欄位：

| 欄位 | 怎麼填 |
|---|---|
| `source.decision_ref` | 指到一筆**有效**的決策（`<節點>#dN`）；決策被翻案，護欄判 `source_decision_invalid` |
| `lifecycle` | `candidate`（只列、不擋）→ 證據齊了改 `active`（推送閘判）→ 不用了改 `retired`（另要 `retirement_reason`） |
| `required_evidence` | 這條要哪幾種證據；不能少於威脅類別表要求的最低種類，少了判 `insufficient_required_evidence`。每一類的最低集合都含 `review` |
| `threat_categories` | 威脅類別表的 id（例如 `authz-object` 是物件授權）；空的判 `threat_categories_missing` |
| `evidence_refs` | 每種證據指到哪篇 Verification 筆記；證據本身寫在那篇裡（見〈四〉） |
| `reported_status` | 作者自己說的狀態（`untested`、`partial`、`verified`…）；閘門不採信，只當參考 |

寫完跑 `lumos security list`：護欄出現在「現行與候選」、錯誤數是 0，才算登記成功。登記錯誤（壞 JSON、未知欄位、重複 id）會列出來並退出 2。

## 三、入口盤點與候選題（建議做）

同一塊圍欄可以多一個 `inventory` 物件，列出系統的資產與對外入口。寫了之後，盤點會算出「哪些入口還沒有任何護欄」，並依缺口出候選題：

```
lumos security list --questions [--plan <計劃>]
```

題目只印、不寫檔；要記進計劃，逐題用 `lumos question-add <計劃> "<題目>" --class <類> --stage <階段>`（題目文字保留 `[cell:<id>]`）。

## 四、收證據（要改成 active 之前）

證據不寫在護欄裡，寫在 `evidence_refs` 指到的 Verification 筆記正文，一塊 `lumos-evidence-v1` 圍欄（只准放在 Verification）：`{"schema_version": 1, "items": [...]}`，每一項是一份證據。

**先登記工具**：證據引用的每個工具都要列在受版控的 `.lumos/security-tools.json`（名稱、類別、釘死的版本、安裝來源、預算、准打目標）。**每個工具要用之前都由使用者核可，AI 不自行安裝。**

**每種證據要什麼格式**：

| 種類 | 格式 | 從哪來 |
|---|---|---|
| `behavior` | `junit` | 測試跑出來的 JUnit XML |
| `fault_sensitivity` | `tq_capture` 或 `guard_kill` | `lumos test-quality capture` 正常→弄壞→還原三份收據，或 `guard kill` 背書（`lumos code-loop security-backing`） |
| `concurrency` | `k6_summary` 或 `junit` | 壓測摘要 |
| 各種掃描 | `sarif` | 掃描工具的 SARIF，另附覆蓋證明 |
| `review` | `review_record` | 審查紀錄（見〈五〉） |

**一項證據的必填欄位**（以 `junit` 為例）：`kind`、`format`、`path`（報告檔）、`report_sha256`（報告內容的 sha256）、`tool`、`tool_version`（要等於工具清單）、`control_id`、`control_revision`（要等於護欄現在的 revision）、`bindings`、`test_sources`、`fixture_globs`、`environment_ref`、`environment`、`targets`、`observed_at`。

- **`bindings` 綁版本**：`[{"path": "<檔>", "blob": "<git blob>"}]`。至少要涵蓋護欄那篇 Systems 筆記 `about_code` 列的全部程式檔、`test_sources`、`fixture_globs` 展開出的檔、`environment_ref`。blob 用 `git rev-parse HEAD:<檔>` 取；之後這些檔任一改了，證據判過期，要重收。
- **`report_sha256`**：`shasum -a 256 <報告檔>`。
- **`targets`**：`tests`（反例測試）、`legit_controls`（合法操作的對照測試）、`preconditions`（前置斷言）等，寫測試的完整名稱。
- **`observed_at`**：ISO 8601 含時區；不能晚於要推的那個提交的時間。

報告檔與收據一起提交進版控；閘門只讀提交樹，不讀工作目錄。

## 五、審查紀錄：哪些 AI 審就行，哪些要使用者簽

`review` 種類要有審查紀錄蓋到下列判斷（`judgments` 欄列 id）：

| 判斷 | 誰能蓋 | 什麼時候要 |
|---|---|---|
| `report_provenance` 報告真的跑出來的 | AI 也行 | 一律 |
| `category_sufficient` 證據種類夠不夠 | AI 也行 | 一律 |
| `inventory_complete` 盤點有沒有漏 | AI 也行 | 一律 |
| `not_applicable_sound` 判不適用的理由 | AI 也行 | 一律 |
| `independent_oracle` 預期答案有獨立來源 | **要人** | 一律 |
| `legit_control_real` 合法操作真的能過 | **要人** | 一律 |
| `threshold_meaningful` 門檻有意義 | **要人** | 必要種類有壓測時 |
| `calibration_representative` 校準樣本有代表性 | **要人** | 必要種類有掃描時 |
| `manual_check_scope` 人工核對範圍 | **要人** | 這條走了威脅類別表的替代欄時 |

- AI 審的紀錄 `reviewer_kind` 填 `ai`，審查人要是沒參與收證、沒寫測試的另一個會談。
- 要人的判斷：寫一份 `reviewer_kind: human` 的紀錄（AI 可以整理草稿，列清楚每項要看哪裡），**使用者讀過、同意後用自己的金鑰簽**：
  1. AI 先提交紀錄，再產生要簽的內容：`lumos security approvals payload human_review "<護欄 id>#review" --signer <principal> --expires-on YYYY-MM-DD --out <檔>`
  2. **使用者在自己的終端機**簽：`ssh-keygen -Y sign -n lumos-security -f <私鑰> <檔>`
  3. **使用者在自己的終端機**寫入：`lumos code-loop security-approval-add <檔> --repo <repo>`（要手打確認碼；AI 在非互動的殼裡跑會被擋）
  4. AI 提交 `.lumos/security-approvals.jsonl`，跑 `lumos security approvals verify` 確認那一筆是 ok。
- 核可鏈每筆要接在前一筆後面：兩條護欄要分兩次產生、兩次簽。
- 專案第一次用之前，要先由使用者釘自己的金鑰（`approvers_init`，同樣三步）；**誰先把第一把金鑰合進主線，誰就是信任根**，所以這一步要使用者本人做，AI 不准用自己產的金鑰代做。

## 六、改成 active，看判定

把護欄的 `lifecycle` 改成 `active`、提交，然後：

```
lumos security evidence
```

它跟推送時 `code-loop check` 的安全證據那一道是同一支判定。每條護欄印「整體」與「最先要修」的代碼，照代碼修：

| 代碼 | 意思 | 怎麼修 |
|---|---|---|
| `threat_categories_missing` | 護欄沒填威脅類別 | 補 `threat_categories` 與 `threat_table_version` |
| `missing:no_evidence` | 這種證據一項都沒有 | 收那一種證據，寫進 Verification 的證據圍欄 |
| `stale:binding_changed` | 綁定的檔改過了 | 重跑、重收，更新 blob 與 `observed_at` |
| `invalid:report_hash_mismatch` | 報告內容跟 `report_sha256` 對不上 | 重算雜湊，或確認報告沒被改過 |
| `invalid:binding_incomplete` | 該綁的檔沒綁 | 照訊息補進 `bindings` |
| `missing:review_record_missing` | 有判斷沒有任何審查紀錄蓋到 | 補一份紀錄蓋那一項 |
| `missing:human_review_missing` | 要人的判斷沒有使用者簽過的紀錄 | 照〈五〉請使用者簽 |

真的要先放行：由使用者在核可鏈簽例外（最長 30 天，只蓋證據種類，蓋不掉護欄層的錯）或把 gate 設定降成只提醒（也要簽）。**不准用 `--no-verify` 跳過，跳過檢查一律由使用者本人決定。**

## 七、AI 不能代做的事

- 建金鑰、簽章、寫入核可鏈（第一筆金鑰、人審、例外、降級全部一樣）。
- 安裝掃描或壓測工具。
- 替使用者判「預期答案有獨立來源」「合法操作真的能過」這類要人的判斷——可以整理草稿，不能代簽。

## 天花板

- 證據合格只代表結果對得上版本，不等於產品安全；`security_verdict` 固定 `not_assessed`。
- 閘門只防不小心（忘了重收、證據掛錯），不防刻意偽造（自產金鑰自簽、手寫核可檔）。
- `--no-verify` 跳得過本機閘；CI 在推送後才判。
