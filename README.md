# Lumos

**繁體中文** · [English](README.en.md)

[![CI](https://github.com/EnzoHsieh-Android/Lumos/actions/workflows/ci.yml/badge.svg)](https://github.com/EnzoHsieh-Android/Lumos/actions/workflows/ci.yml)

**讓 AI 寫程式時，把「為什麼這樣改」一起留下來。**

Lumos 是一套給 Claude Code 和 Codex 用的開發工具。你用對話交代需求，AI 負責讀程式、改程式、跑測試、提交；Lumos 則要求 AI 在改程式的同時寫下理由、不能改壞的規則和驗證方式，並在 Git 提交與推送時，檢查其中能機械判斷的部分，例如有沒有動到筆記。

它由四樣東西組成：一個單檔的 Python 命令列工具（只用標準函式庫）、一組 Git hooks、一份安裝時寫進 CLAUDE.md／AGENTS.md 的 AI 工作守則，以及一組跟程式碼放在同一個 repo、彼此互相連結的 Markdown 筆記。

## 為什麼需要它

AI 寫程式很快，但它不會替專案記事情。這一輪對話討論過的取捨、否決掉的方案，下一次重開對話就不見了；「同一筆訂單不能退款兩次」這種規則，程式碼只寫了現在怎麼做，沒寫哪些行為不准變；AI 說測試都過了，事後也查不到它到底跑了哪些。

傳統上，這些靠 ADR（架構決策紀錄）、CODEOWNERS、pre-commit 之類的做法和人的自律來補。Lumos 把這幾件事接在一起，只是這次被檢查的是 AI：改了程式卻沒動筆記，提交就會被擋下；真要跳過得明著跳，而且會留下紀錄。

## 用起來是什麼樣子

假設 AI 改了退款邏輯，卻沒寫任何筆記就提交，它會收到這段訊息（實機輸出，節錄）：

```text
$ git commit -m "feat: 退款前檢查是否已退過"

擋下:這次 commit 改了程式碼,但知識筆記一個字都沒動。
…
這次改到的程式碼(1 個):
   • src/payment.py
…
兩條路選一條:
   1. 把該改的筆記改一改,加進 commit,再提交一次。
   2. 這次真的不需要動筆記(改錯字、排版、註解、還在進行中的半成品)→ 跳過這道檢查:
        git commit --no-verify -m '<訊息>'
      跳過會留下紀錄,不是偷偷放行。
```

讀這段訊息的是 AI，不是你。工作守則要它把筆記補上再提交；真的不需要寫（例如只是改錯字），它可以跳過，但跳過會留下紀錄。你主要在遇到業務取捨、或要不要接受某個風險時做決定。

## 怎麼運作

<p align="center">
  <a href="assets/map-zh.svg">
    <img src="assets/map-zh.svg" alt="一次改動的四步：讀程式碼並補上筆記裡的脈絡、依風險分派 AI 審查、審查並處理每條意見、寫回筆記；外圈定期檢查流程本身" width="760">
  </a>
</p>

1. **讀程式碼，補上脈絡**：AI 先讀程式碼；改檔時，工具把相關筆記推給它，補上程式碼看不出的理由。筆記講的程式行為跟程式碼不一樣時，以程式碼為準；部署狀態、業務限制這類程式碼答不了的，要去查或問人。
2. **依風險派 AI 審查**：詳見下一節。
3. **每條意見都要有去向**：修掉、附理由不修，或用證據證明不成立；沒處理完不能過關。
4. **寫回筆記**：把這次的取捨和驗證方式寫回負責這支檔的筆記，下次改到這裡查得到。

外圈是檢查流程本身：在 Lumos 自己的 repo 上，每個走完審查、附有設計規格的案子，都會把「過關或不過關」的結論存下來；每週用同一版規則重跑（案子多到跑不完時，輪流抽一部分），確認同樣的案子還是得到同樣的結論。結論變了，就代表規則被改壞了，要回頭調整。

筆記彼此連結。下圖是一個線上商店的示意：計劃連到做出來的功能和驗證紀錄；出了事故，就回頭開修正計劃、補上回歸測試。

## 怎麼做 code review

<p align="center">
  <a href="assets/risk-review-zh.svg">
    <img src="assets/risk-review-zh.svg" alt="依風險決定審多重：新增的程式碼先用規則掃風險；一般改動派一到三位審查，高風險每輪最多九位，含另一家模型的找問題與反駁；每條意見要修掉、附理由不修或證明不成立；高風險推送前必須留下審查結果" width="760">
  </a>
</p>

- **先判風險**：推送前，工具用固定規則掃這次新增的程式碼，找容易出事的寫法。
- **再決定派幾個 AI 審**：一般改動派 1 到 3 個；高風險每輪最多 9 個，各看一個角度。其中兩個刻意換成另一家的模型（Claude 主導時就用 Codex），一個找問題、一個專門反駁，因為同一家模型容易有同樣的盲點。
- **高風險沒審完不能推**：推送前必須留下審查結果（通過，或寫明理由的跳過），否則 Git hook 擋下。

審查只是其中一層。風險分級、多個 AI 審查、放行規則、外部規則（linter）、測試，每一層都有漏洞，疊起來問題就比較難一路穿過去（瑞士起司模型）。

<p align="center">
  <a href="assets/swiss-cheese-zh.svg">
    <img src="assets/swiss-cheese-zh.svg" alt="五層瑞士起司防線，以及漏網問題回饋成新規則或測試的流程" width="760">
  </a>
</p>

**人在哪裡？** Lumos 預設不要求人逐行看每個 diff，逐行檢查交給多個 AI 和機器檢查；人負責下面這些判斷。

- 需求、取捨、要不要接受風險、不可逆的操作，由人決定。
- 高風險審查最多跑 3 輪；還沒過就停下來交給人，AI 不自己宣布通過（這條是守則，工具只會在跑滿時提示）。
- 「這條規則還符不符合業務」要人簽核並留紀錄，這是測試證明不了的。
- 每輪的審查報告和處理結果都留在 repo，人隨時可以抽查。

**一個真實的例子。** 第一個小型 Vue 專案接上 Lumos 當天（2026-09-10），工具把自己裝進專案的檔也當成專案程式碼掃。修這件事的改動被判成高風險：第一輪 7 個審查裡有 4 個各自抓到同一個漏洞，第三輪 Codex 又指出修法還有洞，四輪 46 條意見全部處理完才提交。每一輪的[審查報告原文](governance/review-reports/code-工具自裝檔不算消費專案/)都在 repo 裡。

## 怎麼防止筆記過期（drift）

筆記最大的風險是過期：程式改了，筆記還在講舊的事。Lumos 分兩步對付它。

**第一步，少存會過期的東西。** 程式碼查得到的現況（欄位、預設值、流程）不准抄進筆記；真要寫部署設定、資料庫實際值這類原始碼裡沒有的現況，要標來源。實驗顯示這很重要：在一個合成專案裡刻意埋進寫錯的筆記，較小的模型（Haiku 4.5）答對率從 20/25 掉到 12/25；在錯句旁標「以程式碼為準」後回到 20/25。

**第二步，在提交和推送時抓不同步。**

| 抓什麼 | 例子 | 什麼時候 | 擋還是提醒 |
| --- | --- | --- | --- |
| 改了程式，筆記一個字都沒動 | 改了退款邏輯，沒寫任何筆記 | 提交 | 擋 |
| 程式檔沒有負責的筆記 | 新增一支檔，沒指定哪篇筆記管它 | 提交、推送 | 擋 |
| 筆記裡寫了會過期的寫法 | 寫程式行號，或寫現況卻沒標來源 | 提交、推送、CI | 擋 |
| 規則的檢查已經生效，筆記還在預告 | 規則的測試已經綁上並通過，筆記還寫「之後補測試」 | 推送、CI | 擋 |
| 程式刪掉或改名了，筆記還在講舊名字 | 函式改名，筆記還寫舊函式名 | 提交、推送、CI | 只提醒 |
| 筆記連結斷掉 | 連到的筆記被刪了 | 推送、CI | 擋 |
| 還在引用已經失效的驗證紀錄 | 驗證結果已經過期，筆記還拿它當依據 | 推送、CI | 只提醒 |

多數檢查可由專案改成只提醒。

**抓得到多少？** 在另一個接上 Lumos 的專案裡，找到 20 處真的過期，逐處用工具重跑：已經存在的舊漂移抓得到 7 處（35%）；如果當時推送前就有檢查，約可抓到 13.5 處（約三分之二；有一處只抓到一半，算半處）。抓不到的有四種：程式新增了某功能、舊句還說「沒有這功能」；數值變了但名稱沒變；回頭檢查的條件寫成散文；同一次推送裡先加後刪。抓到的有多少是誤報，還沒量完。

**AI 會不會隨便寫筆記應付？** 會，「改程式要動筆記」那道只看有沒有動。在那個專案抽 55 句風險較高的現況描述，能判斷的 54 句裡 22 句已過時；上面第三列的檢查就是因此加的。內容對不對，最後還是要靠審查和人。

<details>
<summary>更多：審查數據與跳過紀錄</summary>

- **多個審查有用嗎？** 在 Lumos 自己 85 輪多人審查裡（2026-07 到 08），822 個問題有 531 個（64.6%）只被一個審查抓到，代表各個審查看到的東西不一樣。這只是描述性統計，不能推算多派或少派一個會差多少；每個問題被幾個審查抓到，是負責分派和收回審查的那個 AI 手填的。
- **意見是不是真的問題？** 截至 2026-09-30，6,195 條審查意見裡只有 58 條（0.9%）被判定不用處理。不過做這個判定的也是 AI。
- **被跳過的檢查有沒有正當理由？** 「改程式要動筆記」在 Lumos 自己約 2,070 個提交裡被跳過 84 次。Claude 和 Codex 各自獨立看過：一致認為「改了行為卻沒寫理由」的 8 次；17 次只改了測試檔；其餘多半是功能分支做到一半、稍後補了筆記。[逐筆判斷](governance/eval/readme-bypass-judge/)
- **較大的模型呢？** Opus 5 在上面的實驗四組都 25/25，不受錯筆記影響，但有筆記時耗時是 2 到 5 倍。
- **筆記有沒有幫上忙？** 另一批 80 場測「程式碼推不出來的規則」：只看程式碼的 AI 5 次都沒答對，有筆記的 15 次答對 8 次。實驗只有一個合成專案、題目是我設計的，只能說方向成立。
- **擋不住的情況**：有些輔助檢查本身出錯時會放行，不讓工具故障卡住開發；提交時跳過會留紀錄，推送時用 `--no-verify` 跳過本機不留紀錄，只有推到 main 或開 PR 時 CI 會再跑。
- 可核對的原始紀錄：[擋下與放行](docs/.governance-log.jsonl)、[跳過紀錄](docs/.bypass-log.jsonl)、[審查報告](governance/review-reports/)。

</details>

## 安裝與限制

需要 Git、Python 3.14 以上，以及 Claude Code 或 Codex。在要導入的專案目錄執行：

```bash
curl -fsSL https://raw.githubusercontent.com/EnzoHsieh-Android/Lumos/release/get.sh | bash
```

腳本問要不要初始化目前目錄時，確認目錄正確再輸入 `y`。裝完重開 AI session，用 `lumos enforcement` 確認檢查都接上了。Windows、離線安裝與移除，見[上手細節](ONBOARDING.md)。

<details>
<summary>已經在用舊版的專案：升級到 Python 3.14 要做的事</summary>

- 更新後，沒有 3.14 的機器，提交與推送會被擋下並說明怎麼裝（macOS：`brew install python@3.14` 或 `uv python install 3.14`）。`python3` 指到舊版沒關係，lumos 會自己找 3.14 重跑。
- 專案 CI 要把 `actions/setup-python` 設成 3.14。
- 裝好之後跑一次 `lumos install`，讓 Claude／Codex 的 hooks 也改用 3.14。
- Codex 的 hook 指令因此改變，可能要再開一次互動式 codex 重新核可。本機讀不到 Codex 的信任狀態，請用 `lumos enforcement` 搭配實際觸發一次確認。

</details>

Lumos 不保證品質或安全，也不取代工程判斷：筆記可能過時，AI 審查可能漏判，有紀錄不代表內容正確；業務取捨、不可逆的操作和要不要承擔風險，仍然要人來決定。
