# Lumos

**繁體中文** · [English](README.en.md)

[![CI](https://github.com/EnzoHsieh-Android/Lumos/actions/workflows/ci.yml/badge.svg)](https://github.com/EnzoHsieh-Android/Lumos/actions/workflows/ci.yml)

**讓 AI 寫程式時，把「為什麼這樣改」一起留下來。**

Lumos 主打用自然語言開發：你描述需求，AI 提出方案並實作，不綁定程式語言。它是套在 AI 開發外面的一層控制與紀錄機制（harness），處理五個問題：黑箱、記憶斷層、筆記過期、難以驗證，以及架構越改越亂。目標是人不必逐行看 diff 也掌握得住 AI，才能把更多開發交給 AI、同時推進多個專案。

舉例來說，透過對話寫程式很快，但討論過的取捨、否決過的方案都只留在那段對話裡。接回對話還找得回來；可是三個月後有人改到同一支檔，沒人記得是哪段對話，同事和別的 AI 工具也看不到。「同一筆訂單不能退款兩次」，程式碼裡頂多看得到一段檢查，看不出它為什麼不能拿掉。AI 說測試都過了，事後也查不到跑了哪些。

Lumos 把這些脈絡留在專案裡。它搭配 Claude Code 或 Codex，要求 AI 每次改程式都寫下理由、必須遵守的規則和驗證方式，存成 Markdown 筆記，跟程式碼一起進版控，換誰、換哪個工具都查得到。提交和推送時，Git hooks 會檢查能自動判斷的部分，例如筆記有沒有跟著改。概念上，它像把三樣常見的東西接在一起：ADR（架構決策紀錄）留下決策、CODEOWNERS 指定每支檔誰負責、pre-commit 在提交前檢查，只是檢查的對象換成 AI。程式碼品質則接上各語言現成的 linter 和社群規則，只擋新增的警告；再依風險派 AI 多角度審查，並確認測試真的跑過、真的抓得到問題。

核心工具是一支單檔的 Python 命令列工具（只用標準函式庫）、一組 Git hooks、一份寫進 CLAUDE.md／AGENTS.md 的 AI 工作守則，加上專案筆記。Claude Code 另有三個外掛：一個記錄會談裡發生的事件；一個在對話被壓縮時，要求留下接手工作需要的狀態；一個限制被標成審查員的 AI 能用哪些工具、能直接寫進哪些位置。這三項目前沒有對應的 Codex 外掛；審查員的限制也不是安全沙箱，它的 Bash 仍能執行完整的 shell。事件帳可用 `lumos events` 查詢。

## 怎麼運作

<p align="center">
  <a href="assets/map-zh.svg">
    <img src="assets/map-zh.svg" alt="一次改動的四步：讀程式碼並補上筆記裡的脈絡、依風險分派 AI 審查、審查並處理每條意見、寫回筆記；外圈定期檢查流程本身" width="760">
  </a>
</p>

1. **讀程式碼，補上脈絡**：AI 先讀程式碼；改檔時，工具會送上相關筆記，補上程式碼看不出的理由。筆記講的程式行為跟程式碼對不上時，以程式碼為準；部署狀態、業務限制這類程式碼答不了的，要查證或問人。
2. **依風險派 AI 審查**：見下面「怎麼做 code review」。
3. **每條意見都要有結果**：修掉、說明不修的理由，或用證據證明不成立；全部處理完才過關。
4. **寫回筆記**：把這次的取捨和驗證方式寫進負責這支檔的筆記，下次改到這裡查得到。

外圈檢查流程本身，見下方「怎麼持續改進這套工具（evals）」。

## 從計劃到驗證，讓筆記一步步連起來

互相連結的筆記合稱「圖譜」，每篇是一個「節點」，分成計劃、功能說明、驗證紀錄和事故。下圖以虛構的線上商店為例：先寫結帳與付款串接的計劃，做出功能，再留下端對端測試和重複付款壓力測試的驗證紀錄。圖上的金環只是示意，表示那篇筆記記了必須遵守的規則，也連到了驗證紀錄；工具裡沒有「受保護」這種狀態。實際的做法是：把重要規則寫成標有 ★INVARIANT★ 的一行（稱為「合約行」），綁上檢查這條規則的測試，再交給沒參與這件工作的 AI 獨立審計。另外可以用 `lumos guard` 在隔離的副本裡故意弄壞程式，確認測試真的會失敗。發生「取消訂單未退點」時，事故連回結帳流程，接著開修復計劃、修正功能、補上回歸測試。

## 怎麼做 code review

<p align="center">
  <a href="assets/risk-review-zh.svg">
    <img src="assets/risk-review-zh.svg" alt="依風險決定審多重：新增的程式碼先用規則掃風險；一般改動派一到兩位審查，高風險每輪至少七位，五個找問題加上架構一致性與資安；每條意見要修掉、附理由不修或證明不成立；高風險推送前必須留下審查結果" width="760">
  </a>
</p>

- **先判風險**：推送前用固定規則掃這次新增的程式碼，找容易出事的寫法。
- **再決定派幾個 AI**：一般改動 1 到 2 個；高風險每輪至少 7 個，5 個找問題、1 個看架構一致、1 個看資安，有定稿的設計規格時再加 1 個對照規格。
- **高風險要有審查結果才能推**：推送前要留下審查結果（通過，或寫明理由的跳過），否則 Git hook 會擋下。

**修好一個問題，也要確認沒有弄壞原本正常的功能。** 修正後的那一輪，工作指引要求固定修正前、後兩個版本，分別確認兩件事：重現原問題的測試修正前失敗、修正後通過；原本正常的行為在兩個版本都正常。接著換一批沒看過的 AI 審查員，檢查修補有沒有副作用。修補裡混了重構時，要保留分段的驗證點；部分高風險案例還要抽查，確認測試抓得到功能退化。`lumos loop fix-check` 會檢查修正紀錄和修正後的測試，但目前只提醒，不取代上面這些驗證，也不取代下一輪審查。審查材料裡的引用、快照和紀錄也會先核對，避免拿不完整的證據當通過依據。詳見 [代碼審工作指引](skills/lumos-code-loop/SKILL.md)。

### 資安怎麼審

業務規則（★INVARIANT★）是不能破的約定；資安另外獨立成一條線，好處是一個指令就查得出「哪些資安護欄的驗證還不夠」。「夠」的標準是有工具真的跑過、留下結果，不是表格填滿就算合格。

<p align="center">
  <a href="assets/security-lane-zh.svg">
    <img src="assets/security-lane-zh.svg" alt="資安這條線的四步：用威脅類別表想到該問的題、盤點已登記的護欄與缺口、由專案自己跑工具收證據並綁版本、推送時由 pre-push 與 CI 判證據；例外只有使用者能用 SSH 金鑰簽、最長 30 天；需要人工判斷的項目 AI 審要標明是 AI；這層只防不小心、不防刻意偽造" width="760">
  </a>
</p>

- **想到該問的資安問題**：計劃在需求、架構、驗證、交付各階段都會被問到資安題，題目來自一張 14 類的威脅類別表（物件授權、身分驗證、注入、流程濫用、資料外洩、對外連線、秘密管理、供應鏈、稽核紀錄等，對照 STRIDE、OWASP ASVS 5.0.0、WSTG、API Top 10）。表的核可與改版由 Claude 與 Codex 兩家各自獨立審、意見一致才升版。
- **盤點護欄**：`lumos security list` 列出專案登記了哪些資安護欄、證據核對到哪、哪些入口還沒有護欄；`--questions` 依沒蓋到的格子出候選題。它只盤點、不執行測試，結果固定標 `not_assessed`——盤點完成不等於安全。
- **證據要是工具真的跑出來的**：每條護欄依類別要求最低證據種類，閘門讀工具輸出自己判合不合格：JUnit 測試、故障注入（guard kill）、k6 壓測與並發摘要、SARIF 掃描結果（例如 Semgrep、gitleaks、OSV-Scanner、ZAP），掃描類另要一份「真的有掃到東西」的覆蓋證明。報告綁版本與雜湊，程式改了沒重收證據就算過期。`lumos security evidence` 和推送時的證據檢查用的是同一套判定程式。
- **推送時擋**：接了 lumos 的專案，pre-push 與 CI 的 `code-loop check` 都多一道安全證據閘，證據不合格、過期或缺件就擋，tag 推送也判。
- **例外只有使用者能簽**：要暫時放行，使用者用自己的 SSH 金鑰簽一筆核可，記在只追加的 `.lumos/security-approvals.jsonl`，最長 30 天到期。需要人工判斷的項目要留審查紀錄：AI 審的要註明審查者是 AI，而且不能代替該由人負責的核可；人審的要使用者用自己的 SSH 金鑰簽過才算。
- **資安工具由導入的專案自己裝、自己跑，lumos 只讀結果**：工具裝在導入 Lumos 的專案裡，由那個專案執行，並把輸出存進版控；lumos 本身維持零依賴。k6、gitleaks、OSV-Scanner、Semgrep、ZAP 這類工具，每個專案要用之前由使用者逐項核可安裝來源、釘版本、時間預算與准打目標，AI 不自行安裝。

這一層的天花板照實寫：

- **只防不小心，不防刻意偽造**：照「信賴原則」，照常操作的 AI 假定誠實；閘防的是忘了重收證據、證據掛錯、殘留設定，擋不住 AI 刻意自產金鑰自簽或直接手寫核可檔。
- **`--no-verify` 跳得過本機閘**：CI 在推送後才紅，收不回已進主線的提交。
- **證據合格不等於產品安全**：工具收證一致只證明結果對得上版本，不證明判準選得對或報告可信。

審查只是其中一層。風險分級、AI 審查、放行規則、外部規則（linter）和測試各有漏洞，疊在一起，問題就難一路穿過，這就是瑞士起司模型。

## 測試要有用，不能只是把程式碼重寫一次

**測試全綠，不等於功能正確。** 如果測試用和正式程式一樣的算法算出預期值，兩邊犯同一個錯還是會過；如果只檢查原始碼含有某個函式名稱，實際行為壞了也可能照樣綠。

例如需求是「3 件商品，每件 5 元，總價應為 15 元」：

```python
# 壞例：把實作的算法再寫一次，無法獨立判斷算法是否符合需求
expected = quantity * unit_price
assert total_price(quantity, unit_price) == expected

# 好例：用已確認的需求案例，檢查實際結果
assert total_price(quantity=3, unit_price=5) == 15
```

這個案例只是起點；折扣、空訂單與錯誤輸入等行為仍要依需求補齊。Lumos 要求開發時先說清楚「輸入、預期結果、判準來源、應抓到的錯誤」，修 bug 與關鍵守衛還要確認故障真的能讓目標斷言翻紅，再還原跑綠。檢查程式結構、各部分有沒有正確接上的測試可以留著，但不能取代對實際行為的驗證。

**能抓到程式被改壞，不等於預期答案正確。** 程式和測試可能一起抄錯需求，所以要先拿獨立的來源核對預期答案，再確認：弄壞相關程式時測試會失敗，還原後會通過。如果懷疑某個行為測試綁死了特定寫法，還要確認重構（不改變行為）之後它仍然通過。各棧的撰寫流程、工具資格考卷與證據邊界見 [測試品質接入標準](skills/lumos-project-notes/commands/test-quality-standard.md)。

完整做法見 [實作測試品質](skills/lumos-project-notes/commands/03-寫回圖譜.md#實作測試品質)，開發與審查工作指引共用這份規範。這是開發及審查要求；自動檢查紀錄格式，不能替人判斷測試是否真的有用。

裝好 Lumos 後，`lumos test-quality scan <測試檔或目錄> --json` 會以唯讀方式列出可疑的測試寫法，供人進一步檢查。Python 能找四類可疑寫法；其他語言（含 PHP）可選用本機的 Semgrep，找出「拿一個值跟自己比較」這類斷言。`capture` 會在你明確指定時執行本機可信的測試程式，保存 JUnit 結果與原始碼快照；`check` 核對「正常→弄壞→還原」三段的證據，也可以加上重構前後的證據。**零候選、綠燈或故障檢出，都不能單獨證明測試有獨立答案。** 工具不提供沙盒、不替代需求來源審查；先用 `capabilities` 看範圍，再讀 [操作與能力邊界](skills/lumos-project-notes/commands/03-寫回圖譜.md#事後掃描與執行收證已安裝-cli)。

## 人在哪裡介入？

Lumos 預設不要求人逐行看 diff，交給 AI 和自動檢查；人負責這些判斷：

- 需求、取捨、要不要接受風險，以及不可逆的操作。
- standard 或 high 分級的審查（設計審、代碼審都算）跑到 3 輪上限仍未通過，就停下交給人，AI 不自行宣布通過。人決定加輪或接受風險後，用 `lumos loop cap-decision` 留下裁定；繼續前用 `lumos loop retro` 記合格回顧，或留下有理由的略過紀錄。人裁定之後兩樣都沒有，就不能再記後續的審查紀錄，也過不了「每條審查意見都已處理」那道關卡。
- 規則還符不符合業務，要人簽核並留紀錄，這是測試證明不了的。
- 每輪的審查報告和處理結果都留在 repo，隨時可以抽查。

## 怎麼防止筆記過期（drift）

程式改了、筆記還在講舊的，AI 讀到就會被誤導。我在合成專案裡埋了錯誤筆記做實驗：較小的模型 Haiku 4.5，25 題原本答對 20 題，掉到只對 12 題。所以 Lumos 在寫筆記、提交、推送三個時間點各設一道關卡。

**第一道：寫筆記時，只寫程式碼看不出的東西。**

- 程式碼查得到的欄位、預設值和流程，不抄進筆記；抄了遲早會過期。
- 工具在提交時自動擋兩種寫法：新寫的程式行號，以及沒註明來源的現況描述（例如部署設定）。其餘靠守則和審查。
- 「目前還沒有退款頁面」這種句子最容易過期：頁面做出來，這句就錯了，卻沒人會回來改。工具會提醒把它改寫成一行「回頭條件」，例如「退款頁面那支檔出現時回來檢查」。寫下回頭條件之後，等那支檔真的出現，那次推送會被擋下：把句子改成現況，或寫明理由照留，才推得出去。

**第二道：提交時，改了程式就要動筆記。**

- 改了程式卻沒動任何筆記，或新增的程式檔沒指定負責的筆記，提交會被擋下。
- 「改程式沒動筆記」這項一定擋，專案關不掉。真的不用改筆記（例如只改錯字），可以用 `git commit --no-verify` 跳過；提交後的掛鉤會自動記下每一次跳過。

**第三道：推送前，找還在講舊東西的筆記。** 以下任一種情況會擋下推送：

- 程式裡的名稱刪了或改名、程式檔刪了或搬走，相關筆記還在提舊的名稱或路徑（範圍見下方細節）。
- 規則的測試已經上線，筆記還寫「之後補測試」。
- 連到的筆記被刪了，或筆記之間的連結斷了。
- 回頭條件已經成立，或規則自己寫的「什麼時候可以撤掉」已經成立。
- 程式和管它的筆記這次都改了，卻沒先讓 AI 對照這次改動重讀整篇筆記、留下重讀紀錄。常見的情況是筆記只在後面補一段，前面的舊句沒人看：程式從三個變數變成四個，筆記還寫三個。字面比對抓不到這種錯，只能靠重讀。這項只擋本機推送，CI 只提醒。

<details>
<summary>細節：檢查範圍、哪些可以調鬆、結案時的收尾</summary>

- **舊名稱檢查的範圍**：看的是 Python 的函式、類別、模組層或類別層的變數與常數、指令旗標，以及程式檔。舊名稱或路徑出現在「負責這次改到的檔案的筆記」或「任一篇筆記的摘要」，就會擋；其他地方提到只列出、不擋。
- **測試名稱對不上**：筆記裡綁的測試名稱找不到真的測試，預設只提醒，專案可以設成擋。
- **重讀之後**：AI 點出不成立的規則行，要嘛改掉，要嘛用 `lumos drift ack --kind reread` 表態照留，否則一樣擋。程式碼不能交給外部模型的專案，可以把重讀改成只提醒或關掉。
- **回頭條件的寫法**：提醒改寫本身不擋提交；但回頭條件要獨立一行，寫在句子中間或表格裡，提交時會擋下。不必再回頭的標上「已結案」，就不再提醒。已成立的回頭條件若決定照留，要寫重看期限或可追查的去處。
- **可以調鬆的**：在 `.lumos/config.json` 能改成只提醒或關掉的有舊說法檢查、回頭重讀、筆記寫法、檔案歸屬，以及新增的 linter 告警（另有幾個較少用的開關，見[指令參考](docs/指令參考.md#專案開關)）。
- **不能調的**：改程式沒動筆記、連結斷掉、高風險改動沒有審查紀錄、測試或掛鉤檔被改過卻沒重新核可、Lumos 自己 repo 的全套測試沒過，以及找不到 Python 3.14。
- **結案時連帶收尾**：一篇計劃收尾、Issue 結案或決策被翻案之後，別篇連到它卻還寫「待裁定」「排隊中」，推送前會列出來，一行指令就能在那句後面補上結論。
- **結 Issue 的兩種方式**：用 `lumos drift fix --kind c2 --close` 結案時，摘要裡的決策還寫待定、或還有沒處理的回頭條件，會先擋下；直接用 `lumos set` 改狀態結案，只列出來、不擋。
- **摘要跟著結案**：筆記結案時摘要沒跟著改會提醒；已結案筆記的摘要仍寫待定，會列入漂移檢查。維護摘要用 `lumos summary-add`（加一行）與 `lumos summary-line`（改一行）；`doctor` 列出更新日期落後時，可先用 `lumos updated-sync --stale --dry-run` 預覽修正。
- **數字綁清單**：筆記寫「共 N 種」這類數字時，可以綁到程式裡那份清單（目前支援 Python）；程式多一項、筆記沒跟上，健康檢查會列出來，一行指令改成現值。

</details>

## 用起來是什麼樣子

以提交時那道關卡為例：假設 AI 改了退款邏輯，卻沒寫任何筆記就提交，它會收到這段訊息（實機輸出，節錄）：

```text
$ git commit -m "feat: 退款前檢查是否已退過"

擋下:這次 commit 改了程式碼,但知識筆記一個字都沒動。
…
這次改到的程式碼(1 個):
   • src/payment.py
…
兩條路選一條:
   1. 把該改的筆記改一改,加進 commit,再提交一次。
   2. 這次真的不需要動筆記(改錯字、排版、註解、還在進行中的半成品)→ 跳過這道檢查:
        git commit --no-verify -m '<訊息>'
      跳過會留下紀錄,不是偷偷放行。
```

這段訊息是給 AI 讀的：守則要它補好筆記再提交；真的不需要（例如只改錯字）也能跳過，但會留下紀錄。你主要負責業務取捨，和要不要接受某個風險。

## 怎麼持續改進這套工具（evals）

規則有沒有改壞、AI 有沒有照規矩做，不能只靠感覺。Lumos 用以下四種評測（evals）檢查，每週各跑一次：

- **審查回放**：審完的案子會存下「過或不過」的結論。用現在的判定程式重算一次（不重新找 AI 審），結論對不上就會標出來，查是不是改規則時改壞了東西。
- **查詢考卷**：用人工標好答案的題目，檢查工具能不能找到該看的筆記。
- **情境探針**：用口語出題，讓 AI 在 repo 的隔離副本裡實際操作，看它會不會主動查筆記、用對指令。每場從同一份凍結副本重新開始，出事故整批停下，壞掉的場次不算分（細節見 [10/7–10/10 更新清點](docs/updates/2026-10-10-readme-audit.md)）。
- **推播漏網**：檢查改檔前送上的筆記，有沒有漏掉該看的。

圖中的「通知人」不是每種檢查都有，哪幾種會通知見下一段。

每週留下結果。會通知人的情況：審查回放遇到案子結論對不上、需要重新凍結、舊案凍不了，或回放與補凍結執行出錯；情境探針有題目沒過。查詢考卷的分數退步只寫進紀錄、不通知；它只在一種情況通知人：計分用到的候選筆記裡，沒人標過的達到一成以上，請人補標。題目有標準答案，不代表候選筆記都標過，所以還是可能觸發。推播漏網只留下清單與分布。修正寫成新規則或測試，下週再測。方向上的大調整則先做受控實驗：「先讀程式碼、筆記只補脈絡」這條原則，就是實驗後才定下的。

另外有 [審查收斂評測工具](governance/eval/review_convergence.md)：從一般審查和跑滿輪數的審查收集候選案例，確認並固定案例、版本與兩種流程後再比較，分開看原問題有沒有修好、原本的行為有沒有保住、有沒有新缺陷、跑了幾輪、花多少成本；缺的資料就標成未知。這是本機的唯讀分析工具，還沒接進上面的每週排程，也不會執行模型或重跑驗收。它用指紋核對資料宣告前後一致，但一致不代表宣告的內容屬實，更不能拿來證明審查輪數已經降低。

這些評測主要在 Lumos 自己的 repo 跑；查詢考卷另外會順帶考排程腳本裡指定的另一個專案（那台機器上有它的考卷時）。它們確保退步會被看見，但不保證每次改動都會變好。

## 安裝與限制

需要 Git、Python 3.14 以上，以及 Claude Code 或 Codex。在要導入的專案目錄執行：

```bash
curl -fsSL https://raw.githubusercontent.com/EnzoHsieh-Android/Lumos/release/get.sh | bash
```

**版本範圍：本 README 描述 `main`；上述一鍵安裝預設取得 `release`。** 兩條分支可能不同步，安裝後請核對工具來源與版本，不能假定已包含 main 的全部更新。[10/1–10/7](docs/updates/2026-10-07-readme-audit.md) 與 [10/7–10/10](docs/updates/2026-10-10-readme-audit.md) 兩份更新清點，列出每次盤點涵蓋的提交、補了哪些文件，以及盤點當時 main 和 release 差在哪裡。

腳本問要不要初始化目前目錄時，確認目錄正確再輸入 `y`。裝完重開一個 AI 對話，執行 `lumos enforcement` 確認檢查都接上了。Windows、離線安裝與移除見[上手細節](ONBOARDING.md)。已經在用的專案要升級時，可以先跑 `lumos update --dry-run`，預覽會改哪些規範檔與工具檔，不會真的動手。

<details>
<summary>已經在用舊版的專案：升級到 Python 3.14 要做的事</summary>

- 更新後，沒有 3.14 的機器，提交與推送會被擋下並說明怎麼裝（macOS：`brew install python@3.14` 或 `uv python install 3.14`）。`python3` 指到舊版沒關係，lumos 會自己找 3.14 重跑。
- 專案 CI 要把 `actions/setup-python` 設成 3.14。
- 裝好之後跑一次 `lumos install`，讓 Claude／Codex 的 hooks 也改用 3.14。
- Codex 的 hook 指令因此改變，可能要再開一次互動式 codex 重新核可。本機讀不到 Codex 的信任狀態，請跑 `lumos enforcement`，再實際觸發一次 hook，確認它真的會執行。

</details>

Lumos 不保證品質或安全，也不取代工程判斷：筆記可能過時，AI 審查可能漏判，有紀錄不代表內容正確。業務取捨、不可逆的操作和要不要承擔風險，仍由人決定。
