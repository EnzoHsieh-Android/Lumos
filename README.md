# Lumos

**繁體中文** · [English](README.en.md)

> 你三個月前叫 AI 寫的那個模組，今天要改。
> 你不記得當初為什麼那樣寫；AI 也拿不到——新開一個對話，上次講過的東西都不在了。

<p align="center">
  <img src="assets/hook-zh.svg" alt="左邊:三個月前那次對話比了三個做法、否決了兩個、講好一條不能破的規則、跑過測試。右邊:三個月後只有程式碼還在,那些取捨全蒸發了" width="900">
</p>

當時那場對話裡，比較過的方案、否決的理由、講好不能破的那條規則，全都在。**交付的時候，只有程式碼留下來。**

這不是誰記性不好，**是程式碼這種東西本來就存不住那些事**。打開一個檔案，它只告訴你「現在長這樣」；至於這五件，它一句都答不出來：

- 當初**為什麼**選這個做法，比較過什麼、否決了什麼。
- 這塊管到**哪裡為止**，動了會波及誰。
- 哪些行為是**說好不能變的**，哪些只是剛好長這樣、可以放心重構。
- 這件事**驗證過沒有**，在什麼前提下才算數。
- 搞砸了**收不收得回來**。

以前這些活在資深工程師的腦子裡。人還在，問一聲就有答案；人一走，就跟著走了。

**Lumos 做的事很單純:把這五件事寫成一疊互相連結的 Markdown 筆記，跟程式碼放在同一個專案裡。**

然後用 git 的檢查——提交跟推送的時候會自動跑的小程式——擋住「改了程式碼卻不更新筆記」這條路。**讓不寫比寫還麻煩，這樣才寫得下去。**

實際跑起來大概是這個樣子。下面是一個線上商店：先有計劃，才長出功能，做完留下紀錄。

<p align="center">
  <img src="assets/graph-demo-zh.svg" alt="示範:一個線上商店的筆記,先寫計劃、才長出功能、做完留紀錄" width="760">
</p>

這張圖有兩件事值得停一下看：

- **金環（合約）不是一開始就在的。** 藍色的功能模組先素著出現，等綠色的驗證紀錄連上去，金環和星號才長出來——**這條規則就是這樣：宣稱「不能改」不算數，綁到真的證據才算。**
- **橘色那條線是回頭的。** 出過的事故不會躺在角落生灰——下一份計劃會把它拉進來，變成動筆前的必讀。

**這些筆記不用你手寫，也不用你背指令。** 你就照平常跟 AI 對話的方式做開發——查東西、改東西、做決定。

安裝的時候已經把「什麼時候該查、什麼時候該寫回」寫進 Claude Code 和 Codex 的規則檔了。**對話裡沉澱下來的脈絡，會被規則逼著留在筆記上。**

## 一篇筆記裡有什麼

<p align="center">
  <img src="assets/note-anatomy-zh.svg" alt="一篇筆記的解剖:機器讀的欄位、摘要行、掛著證據的合約,分隔線以下才是給人讀的" width="900">
</p>

那兩個星號記號是整套東西的核心——**「這裡不能改」這種話不能只用嘴講，旁邊必須掛著證據**；掛不上，健檢直接紅。

所以「這個專案有哪些不能碰的規則」不用問人也不用翻——一行指令就有答案（日常是 AI 幫你敲的）：

```console
$ lumos contracts

# Systems/付款串接.md
  ★INVARIANT★ 同一筆訂單絕對不能被扣兩次款——重送、重試、webhook 重複進來都算
      ↳ 綁的測試: test_no_double_charge_on_retry
# Systems/庫存扣減.md
  ★INVARIANT★ 任何情況下庫存都不能變成負數——超賣一件都不行
      ↳ 綁的測試: test_stock_never_goes_negative
# Systems/購物車.md
  ★DEBT★ 購物車存在 Redis 沒有落地資料庫,Redis 一重開就空了
         已知,現在可接受,要改隨時可以改

合約 4 條(改了就是破壞性變更) | 技術債 2 條(可以改)
```

最後一行的分別很重要：**哪些是規則、哪些只是「目前剛好這樣」，寫清楚，重構的人就不用猜。**

## 跟 Obsidian 差在哪

**先說不衝突。** 這些筆記就是普通的 Markdown 檔，你想用 Obsidian 打開、在裡面編輯，完全沒問題；反過來，不裝任何筆記軟體也一樣跑得起來。

差別只有一句話：**Obsidian 是給人瀏覽的，Lumos 是給 AI 查的。** 底下每一條差異，都是從這句長出來的。

### AI 讀不完，只能查

一個 AI 拿到普通的筆記庫，能做的只有把檔案讀進去。**這個專案的筆記全文是 267 萬字元**——塞不進去；就算塞得進去，重點也被稀釋成雜訊。

<p align="center">
  <img src="assets/graph-growth.gif" alt="Lumos 自己的筆記,三個月從幾篇長成四百多篇" width="820">
  <br>
  <sub>Lumos 自己的筆記三個月長出來的樣子（錄製當下 440 篇、1572 條連結，現在 444 篇）。這張是產品畫面直接錄的，不是畫的。</sub>
</p>

所以換個做法：**讓它下查詢，拿回排序過、壓縮過的答案。**

```console
$ lumos context Systems/付款串接 --brief     # 回 783 字元,那篇全文是 1,812
提醒:這篇有「動了會壞」的合約,動手前一定要看:
  ★INVARIANT★ 同一筆訂單絕對不能被扣兩次款 [test:test_no_double_charge_on_retry]
```

**合約永遠釘在最上面。** 差別不是「比較快」，是**塞不塞得下**。

### 還要能倒過來查

你手上是一個原始碼檔，想知道動它會波及哪幾篇筆記、其中哪幾篇帶著不能破的規則。**這種「從程式碼反查筆記」的方向，筆記軟體裡沒有這個概念。**

<p align="center">
  <img src="assets/impact-zh.svg" alt="給一個原始碼檔,圖譜算出哪幾篇筆記受影響、哪幾篇帶合約" width="900">
</p>

標籤也是同樣的道理：它是拿來**下結構查詢**的，不是全文搜尋（`lumos query --tag status/doing`）。標籤分家族，條件可以疊——「只看還沒收的」「只看連到某篇的」。

### 剩下三條，是筆記軟體不會替你管的

| 你做了什麼 | 一般筆記軟體 | Lumos |
|---|---|---|
| 寫下「這條規則不能改」 | 存檔，沒事 | 要你指出**哪支測試在守它**。指不出來，健檢紅 |
| 改了程式碼、沒動筆記 | 沒人知道 | `git commit` 當下**被擋住**，要你補、或說一句為什麼不用 |
| 記下「當初為什麼這樣決定」 | 散在正文裡 | **獨立欄位**：編號、日期、理由、後來有沒有被推翻 |
| 一份驗證放久了 | 沒人知道它過期了 | 寫的時候就要**留回頭條件**，到期健檢會唸你 |

一句話收尾：**這疊筆記的主要讀者不是人，是下一個 session 的 AI。** 所以它是設計來被查的，不是被讀的。

## 越跑越準的循環

**這是 Lumos 跟「一本寫得很好的文件」真正的分野。** 文件寫完那天最準，之後只會往下掉；這套東西相反，每跑一輪手上的材料就更準一點。

<p align="center">
  <img src="assets/loop-zh.svg" alt="圖譜餵進審查、審查結果寫回圖譜的循環" width="900">
</p>

四個階段照順序跑，關鍵在最後一步：**每條意見的處置結果會寫回圖譜，變成下一輪的材料。**

**筆記不是最後的產出物，是下一輪的輸入。** 第一輪審查員手上可能只有三篇，第五輪會有八篇——而且那八篇是前幾輪真的被採納過的，不是誰憑印象丟進去的。

同一批 AI、同樣的時間，**差別只在手上的材料越來越準**。

> **老實話：** 機器擋得住的是形式——測試存不存在、回退有沒有寫、有沒有找人獨立審過、每條意見有沒有交代。
> 「這條規則今天還符不符合業務」「那個回退步驟真的跑得動嗎」——只有人能答。別把「有掛證據」當成「絕對安全」。

## 換一種語言也一樣

上面那套審查迴圈是通用的。但「這段 Kotlin 的協程有沒有開錯執行緒」「這條 SQL 會不會全表掃描」——**這種問題跟語言綁死，通用審查問不出來。**

**這個工具其實一直有在問。** 改檔前、推送前，它都會把「這個技術棧該問自己的效能問題」推到眼前。

**但推到眼前，不等於有人回答。** 翻治理帳：**178 筆審查留痕裡，只有十幾筆對這類問題留過一句回應**——而且**其中 13 筆答的是 Python，一個根本不在題表上的語言**。

也就是說：**看到了，然後略過**；少數認真回答的，還答錯了對象。這一段講的就是怎麼把後面那一半補上。

<p align="center">
  <img src="assets/stack-gate-zh.svg" alt="一次改動的旅程:副檔名認棧、取出該棧的題;改檔前只推踩到的題;推送前每題要有交代;推送與 CI 缺一題就擋;審查席拿表態當可反駁的宣稱" width="900">
</p>

### 只問你真的碰到的

六個技術棧（Kotlin、C#、Vue、SQL、Swift、Node）**共 32 題**，每一題掛著一組觸發字。工具拿這次改動的增刪行去比對——**只有真的踩到的題才會推到眼前**，其他自動記「未觸發」。

這一點很重要：**不是把 32 題全丟給你**。丟全部等於沒丟，看的人會直接略過。

### 推送前，每一題都要有交代

三種答法，選一個：

| 你的答案 | 要附什麼 |
|---|---|
| **做到了** | 證據——哪個檔哪一行，或哪支測試在守 |
| **不適用** | 一句理由 |
| **還沒做** | 連到一個開著的待辦 |

**缺一題就擋，而且不看風險分級。** 這跟前面那道「高風險才要過審」的閘是分開的兩件事——**你這次改動只要碰到了某一題，就要回答它，不管改動大不大。**

### 工具驗什麼、不驗什麼

這條線要講得很清楚，不然會被誤讀成「機器幫你保證品質」：

| 你說 | 工具會查 | 工具**不會**查 |
|---|---|---|
| 做到了，看這一行 | 那個檔在不在、行號在不在範圍內 | **那一行是不是真的解決了那題** |
| 做到了，有測試 | 那支測試找不找得到、在不在被推送的樹裡 | **那支測試有沒有殺傷力** |
| 不適用 | 理由有沒有寫、長度夠不夠 | **理由成不成立** |
| 還沒做 | 那個待辦存不存在、是不是還開著 | **那個待辦會不會被做** |

**答案對不對，工具一個字都不判。** 那些答案會被附進審查員的派工單裡——**審查席要反駁的就是這些答案**。

### 換一種語言，只有一格不一樣

整條路是共用的，**各語言唯一的差別是最前面那一格**：副檔名認出是哪個棧、取出那個棧的題。`.ts` 和 `.js` 再看專案設定檔判斷是前端還是後端。

**沒在表裡的語言，這道閘就不觸發**——包括 Python 自己也不在。那種情況只剩「高風險才要過審」那條路。想過渡的專案也可以在設定裡把它調成「只有高風險才問」或整個關掉。

> **老實話：這道閘擋得住「懶得回答」，擋不住「隨便回答」。**
> 寫「不適用」而理由是唬爛的，工具看不出來；貼一個測試名而那支測試根本測不到重點，工具也看不出來。
> **它抓的是最懶的那種謊，剩下的交給審查席跟你自己。**

## 適合誰 / 不適合誰

**適合：**

- 專案要活超過幾個月，而且會有別人（或別的 AI）接手。
- 大量用 AI 寫程式，你自己不會逐行讀完。
- 系統裡有「動到就會出事」的地方：金流、庫存、權限、資料遷移。

**不適合：**

- **程式主要還是你自己手寫，或者可支配的 token 不夠。** 這套的前提是脈絡從對話裡沉澱下來——你不跟 AI 講，就沒有東西可以留；而審查迴圈本身也要燒 token。
- 兩週寫完就丟的東西。
- 一個人的小工具，你自己每天都在讀，全部記在腦子裡。

**代價講在前面：** 這套會讓每次提交多花一點時間，換來的是三個月後不用重新考古。**專案活不到三個月，就不划算。**

## 為什麼是自然語言開發

上面那條「程式主要還是你自己手寫就不適合」，理由在這裡。

<p align="center">
  <img src="assets/shift-zh.svg" alt="自己動手:一次一條線,取捨與否決的方案只在腦子裡。自然語言:同時開好幾條,取捨落成節點" width="900">
</p>

你自己動手寫，會同時發生三件事：

- **一次只能一條線。** 這不是效率高低的問題,是物理限制——手在鍵盤上，就不可能同時推進三件事。
- **之後的 AI 只能從程式碼反推。** 而程式碼裡本來就沒有「為什麼」，它只還原得出「現在長怎樣」。
- **最貴的那一塊根本沒有出現過。** 你比較過哪些方案、為什麼否決那一個、當時在什麼前提下決定——這些從來沒離開你的腦子，因為你沒有對誰講過。

改用自然語言開發，這三件事同時反過來。**你負責決策、需求和取捨，實作可以同時開好幾條。**

而且**取捨本來就發生在對話裡**，不用另外抽時間補文件——規則會逼著它落成節點。

**這個差距只會越拉越大。** 模型越強，你自己動手就越不划算；但模型再強，讀不到的東西就是讀不到。**你練的那件事在貶值，你留下的脈絡不會。**

## 裝起來

### 專案已經在用 Lumos（接手的人）

```bash
git clone <你的專案> && cd <你的專案>
python3 scripts/lumos bootstrap
```

一行搞定：Lumos 本體、給 AI 看的操作手冊、全域指令、git 檢查，全部裝好。裝完**重啟 Claude Code 或 Codex 的對話**（有些提示是開場時載入的）。

### 全新專案要導入

站在你的專案目錄裡跑：

```bash
curl -fsSL https://raw.githubusercontent.com/EnzoHsieh-Android/Lumos/release/get.sh | bash
```

它會問「要把這個目錄建成 lumos 專案嗎？[y/N]」，按 `y`。

- **預設是 N**，所以站錯目錄（例如你的 dotfiles）按 Enter 就跳過，不會誤裝。
- 不想盲跑遠端腳本？先 `curl -fsSL <網址> -o get.sh` 抓下來看過再執行。
- CI 這種沒有人在旁邊的環境：指令結尾加上 `-s -- --init`，直接建、不問。

### 裝好了嗎

```bash
lumos enforcement
```

它列出每一層防護「有沒有裝上、接上」——**注意它查的是接線，不是判得對不對**。全綠代表檢查程式註冊了、檔案在、版本對。Codex 那幾行會停在「已註冊，要不要跑本機讀不到」，那是平台限制、不是壞掉。

前置：Git for Windows、python 在 PATH、Claude Code。

```powershell
irm https://raw.githubusercontent.com/EnzoHsieh-Android/Lumos/release/get.ps1 | iex

```

<details><summary>只裝一半 / 離線裝 / 為什麼分兩層</summary>

**分兩層的原因**：
- **專案層**——CI 只看得到你的專案 repo，git 檢查也是一個 repo 一份，所以檢查工具必須**複製一份進每個專案**。更新用 `lumos update`。
- **機器層**——給 AI 看的操作手冊是**整台機器共用一份**，用捷徑連到 Claude Code / Codex 的目錄。對 Lumos 目錄 `git pull` 一次，所有專案同時吃到新版。

只建專案層 `lumos init`（`--no-hooks` 只建筆記資料夾不裝檢查；既有筆記**絕不覆寫**）。只裝機器層 `lumos install`。手動離線：

```bash
git clone --branch release https://github.com/EnzoHsieh-Android/Lumos ~/harness/lumos-toolchain
cd ~/harness/lumos-toolchain && ./install.sh
python3 scripts/lumos install
scripts/install-graph-toolchain.sh --target <專案路徑> --slug <名稱>
```

`release` 是對外線，只有維護者會把它往前推。要跟開發線就把 `--branch release` 拿掉。

**Claude Code 和 Codex CLI 都支援**，裝一次就把兩邊都設好，行為一致。細節在[心智模型與機制](docs/心智模型.md)。
</details>

## 你的第一次

裝完之後，開一個 Claude Code 或 Codex 的對話，像平常一樣講話就好：

<p align="center">
  <img src="assets/usage-zh.svg" alt="左邊是你用人話講的三句,右邊是它自己敲的指令與讀到的東西" width="900">
</p>

左邊那三句就是你要做的全部，右邊那些指令**你不用碰也不用背**。

安裝時已經把「什麼情況該查什麼」寫進 Claude Code 的 `CLAUDE.md` 和 Codex 的 `AGENTS.md`，另外掛了五個會自動觸發的檢查：開場提醒、改檔前推波及的筆記、派審查員時附相關筆記、收工檢查、CI 狀態。

真的要提交而筆記沒動時，會像這樣被擋下來：

```console
$ git commit -m "調整結帳邏輯"

擋下:這次 commit 改了程式碼,但知識筆記一個字都沒動。
程式碼記的是「現在長怎樣」,筆記記的是「為什麼這樣做」——只改其中一邊,
下一個人(或下一個 session 的 AI)就會拿舊的理由去理解新的程式碼。

兩條路選一條:
   1. 把該改的筆記改一改,加進 commit,再提交一次。
   2. 這次真的不需要動筆記(改錯字、排版、註解)→ git commit --no-verify
      跳過會留下紀錄,不是偷偷放行。
```

**這一擋就是整套東西的本體。** 其他都是為了讓這一擋不討人厭而長出來的。

> 想自己敲指令當然可以，看[指令參考](docs/指令參考.md)。這裡把實際輸出貼出來，是為了讓你看見它讀了什麼、擋了什麼——**看不見的治理等於沒有治理。**

## 為什麼做這個

全自動開發的時代總有一天會到來。

但**AI 不會憑空知道一個專案的業務經驗，也不會知道那些決斷是怎麼走過來的。** 為什麼當初否決了看起來更快的那個做法、哪一次事故換來現在這條規則、哪個數字是人拍板的而不是算出來的——這些都不在程式碼裡。它們一直活在人的腦子裡，人走了就沒了。

**而 AI 拿不到，有兩層原因：**

- **新開一個對話，它讀不到上一次講過什麼。** 你上次跟它花半小時談定的取捨，這次它一個字都不知道。
- **同一個對話跑久了，前面的也會被擠掉。** 脈絡視窗有上限，撐到某個長度，最早那段就會被丟掉——**你以為它還記得，其實已經沒了。**

模型會一直變強。但這兩件事不會因為模型變強而消失——**它們是「拿不拿得到」的問題，不是「聰不聰明」的問題。**

**所以要把脈絡寫在模型外面。但光是寫下來還不夠。**

寫下來的東西如果不跟著開發一起走，三個月後它講的是三個月前的世界——**那比沒有更糟，因為下一個人會相信它。** 這是所有「我們來好好寫文件」最後失敗的地方：不是沒人寫，是寫完之後沒有任何東西逼它同步。

所以真正要保證的不是「有沒有寫」，是**「它有沒有跟著程式一起改」**。那件事靠自律做不到，只能靠機械——**改了程式碼卻沒動筆記，提交當下就過不去。**

所以我深信：**下一代軟體開發的基石，不會只是更會寫程式的模型，而是把脈絡留下來、而且逼它不准腐爛的工程治理。**

要的是一套**跟著開發一起長**的東西——**而不是一個只寫第一次、之後就開始腐壞的系統。**

Lumos 是我對這件事的答案。

## 邊界

Lumos 只放**通用的工具組**：筆記的指令列工具、各種檢查、git hook，以及跨專案通用的技術棧慣例手冊。

kotlin、vue、csharp 那幾份手冊不綁任何一個專案，所以住在這裡。

各專案自己的東西不進來：業務筆記內容、發版腳本、只有那個專案在用的框架選型。
